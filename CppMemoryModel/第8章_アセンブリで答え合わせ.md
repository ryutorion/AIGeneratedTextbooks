# 第8章 アセンブリで答え合わせ ― x64とARMのコード生成比較

ここまでの7つの章で、私たちは逆アセンブルを何十回も行いました。素のmov、mfence、xchg、lock add、ldar、stlr、dmb ish、ldadd――そのたびに「詳しい精算は第8章で」と札を立ててきました。この章はその**総精算**です。

ただし、命令の対応表を暗記する章ではありません。この章の主張はもっと強いものです:**C++メモリオーダー→機械語の対応表は、暗記するものではなく、第3章のTSO機械と第7章の膜の図から「導出」できるものである。** まず机上で対応表を導き(8.1節)、次にコンパイラの実出力で答え合わせをし(8.2節)、対応表の含意が生む3つの深い話題――seq_cstストアの実装競争(8.3節)、ARMのstlr/ldarに仕込まれた仕掛けと、第7章の実験結果に潜んでいたもう一段のただ乗り(8.4節)、RMWとLSE拡張(8.5節)――を掘って、最後に本書の警句を最終形に鍛えます(8.6節)。

## 8.1 C++メモリオーダーとTSOの保証の重ね合わせ表 ― 対応表を「導出」する

コンパイラの立場に立ってみます。`ready.load(std::memory_order_acquire)`という1行を翻訳するとき、コンパイラが負う義務は何でしょうか。2つあります。

> **義務A(コンパイラ自身)**: 自分の最適化が、このオーダーの保証を壊す並べ替え・削除をしないこと。
> **義務B(CPUに対して)**: ターゲットCPUが放っておくと壊してしまう並べ替えがあるなら、それを禁じる命令(バリア付き命令や明示バリア)を発行すること。

義務Aは全アーキテクチャ共通で、**命令を1つも増やさずに**果たせます(出力の並べ方と最適化の自粛だけの問題です)。値段がかかるのは義務Bだけ。そして義務Bの内容は、単純な集合の比較で決まります:

> **翻訳の基本定理(本書式の言い方)**: あるオーダーが禁じたい並べ替えの集合を R、ターゲットCPUが**無条件で**禁じている並べ替えの集合を H とするとき、**R ⊆ H なら素の命令でよい**。R が H からはみ出す部分だけ、バリアで買い足す。

材料は全部手元にあります。H は第3章の表3-1(x64のTSOは{LL, LS, SS}を禁止、Store→Loadのみ許容。ARMは空集合=何も禁止しない)。R は第7章の膜の図から読み取れます。1段ずつ導出しましょう。

**relaxed。** 要求は不可分性と変更順序(コヒーレンス)だけで、R = ∅。コヒーレンスはMESIが(第4章)、整列済みワード幅アクセスの不可分性はどちらのISAも保証します。**両アーキテクチャとも素のロード/ストア命令で足ります。**

**acquireロード。** 膜の図(7.2節)より、禁じたいのは「後続の読み書きが、このロードより**前**へ抜ける」こと。並べ替えの種類でいえば R = {Load→Load, Load→Store}。x64のTSOは両方を無条件で禁止しています(表3-1)。**R ⊆ H、よってx64では素のmovで足ります。** ARMのHは空なので、R をまるごと命令で買う必要があります(→ldar系)。

**releaseストア。** 禁じたいのは「先行の読み書きが、このストアより**後ろ**へ抜ける」こと。R = {Load→Store, Store→Store}。これもTSOの禁止範囲に**すっぽり収まります**。**x64では素のmov。** ARMでは買う(→stlr)。

**seq_cst。** acquire/releaseの全要求に加え、全順序Sの維持のために「seq_cstストアと、それより後のseq_cstロード」の間の**Store→Load**を禁じる必要があります(これを許すと第2章のSBそのものが起き、Sが組めなくなります)。そしてStore→Loadこそ、**TSOが唯一許している並べ替え**でした。R が H から、ちょうど1要素だけはみ出す。**このはみ出し1要素の代金が、x64のseq_cstの全コストです**(→mfenceまたはlock系命令。第3.5節で実測済み)。

支払いの割り振りにはひとつ設計判断があります。Store→Loadの禁止は「ストア側に払わせる(ストアの直後にバリア)」でも「ロード側に払わせる(ロードの直前にバリア)」でも達成できます。x64の標準ABIは**ストア側全額負担**を選びました――一般にロードはストアより頻繁なので、多数派を無料にする合理的な選択です。重要な帰結として、この割り振りは**プラットフォーム全体で統一された取り決め**でなければなりません。あるライブラリが「ロード払い」、別のライブラリが「ストア払い」で翻訳されていたら、両者間のseq_cstは誰もバリアを払わない箇所で破れます。対応表とは、コンパイラの趣味ではなく**ABIの一部**なのです。

以上で、x64列は1行も暗記せずに埋まりました。まとめます。

**表8-1: 導出された対応表(理論値)**

| C++操作 | 禁じたい並べ替え R | x64(H={LL,LS,SS}) | AArch64(H=∅) |
|---|---|---|---|
| load(relaxed) | ∅ | mov(素) | ldr(素) |
| load(acquire) | LL, LS | **mov(素・R⊆H)** | ldar系 |
| load(seq_cst) | LL, LS(+S維持) | **mov(ストア払い方式)** | ldar |
| store(relaxed) | ∅ | mov(素) | str(素) |
| store(release) | LS, SS | **mov(素・R⊆H)** | stlr |
| store(seq_cst) | LS, SS + **SL** | **xchg か mov+mfence** | stlr(仕掛けは8.4節) |
| fence(acquire) | LL, LS | (命令なし・義務Aのみ) | dmb ishld |
| fence(release/acq_rel) | LS, SS(+LL) | (命令なし・義務Aのみ) | dmb ish |
| fence(seq_cst) | 全部 | mfence | dmb ish |

x64の列に「命令なし」「素」が並ぶ様子は壮観です。**第7章までに観測した「x64でacquire/releaseがタダ」の全事例は、この R ⊆ H という1行の包含関係の帰結**でした。ただし「タダ」の意味は正確に:義務B(CPU向け)が無料なだけで、義務A(コンパイラの自粛)は生きています。acquireロードをまたいで後続の読みを繰り上げる最適化は、movしか出さない場合でも禁止です。x64のatomicは「命令は素、意味は素でない」――第2.4節でrelaxedアトミックがコンパイラの入れ替えを実務上受けなかったのも、この義務Aの働きでした。

## 8.2 【コード】アーキテクチャ別コード生成の実験セット ― 実出力で答え合わせ

理論値の表ができたので、コンパイラの実出力と突き合わせます。検査用ハーネスは、オーダーごとに1関数ずつ、インライン展開を禁じて並べるだけです。

**リスト8-1: codegen.cpp ― 対応表の検査キット**

```cpp
#include <atomic>
std::atomic<int> a;
int g;

#define KEEP [[gnu::noinline]]
KEEP int  ld_rlx() { return a.load(std::memory_order_relaxed); }
KEEP int  ld_acq() { return a.load(std::memory_order_acquire); }
KEEP int  ld_sc () { return a.load(std::memory_order_seq_cst); }
KEEP void st_rlx(int v) { a.store(v, std::memory_order_relaxed); }
KEEP void st_rel(int v) { a.store(v, std::memory_order_release); }
KEEP void st_sc (int v) { a.store(v, std::memory_order_seq_cst); }
KEEP void fence_acq() { std::atomic_thread_fence(std::memory_order_acquire); }
KEEP void fence_sc () { std::atomic_thread_fence(std::memory_order_seq_cst); }
```

```console
$ g++ -std=c++20 -O2 -c codegen.cpp && objdump -d codegen.o     # x64
$ g++ -std=c++20 -O2 -march=armv8-a -c codegen.cpp && ...       # ARM 古典(v8.0)
$ clang++ -std=c++20 -O2 -mcpu=apple-m2 -c codegen.cpp && ...   # ARM 現代(RCpc対応)
```

3本の出力から要点を抜粋して、実測の対応表を完成させます。

**表8-2: 実測された対応表(筆者環境のGCC 13 / Apple Clang 15)**

| C++操作 | x64 | AArch64 古典(v8.0) | AArch64 現代(RCpc) |
|---|---|---|---|
| load(relaxed) | `mov` | `ldr` | `ldr` |
| load(acquire) | `mov` | `ldar` | **`ldapr`** ← 8.4節の主役 |
| load(seq_cst) | `mov` | `ldar` | `ldar` |
| store(relaxed) | `mov` | `str` | `str` |
| store(release) | `mov` | `stlr` | `stlr` |
| store(seq_cst) | **`xchg`** | `stlr` | `stlr` |
| fence(acquire) | (なし) | `dmb ishld` | `dmb ishld` |
| fence(seq_cst) | `mfence` | `dmb ish` | `dmb ish` |

理論値(表8-1)と**全行一致**です。x64列は予告どおりmovの行進で、はみ出し1要素の代金だけが`xchg`と`mfence`として立っています。第7.2節でSBのacquire/release版がrelaxed版と「1バイトも違わなかった」謎も、第7.8節で修正の保険料が「0円」だった魔法も、この表の該当セルを指させば説明が終わります。

> **観測事実25**: C++オーダー→機械語の対応は、「オーダーの要求 R がアーキテクチャの無条件保証 H に収まるか」で導出でき、実出力と一致する。x64でacquire/releaseが素のmovなのはR⊆Hの帰結であり、seq_cstストアだけがTSOのはみ出し1要素(Store→Load)の代金を払う。

ひとつだけ、表8-2に理論の表になかった顔があります。右下近くの`ldapr`。同じ「acquireロード」が、ターゲット指定ひとつで`ldar`にも`ldapr`にもなる。この分岐には、第7章の実験結果の解釈を書き換えるほどの意味が潜んでいます。8.4節までお預けにして、先にx64側の宿題を片付けます。

## 8.3 【コード】seq_cst storeの2つの実装戦略 ― mov+mfence vs xchg

表8-1で、x64のseq_cstストアには実装が2つ書いてありました。`mov`+`mfence`(書いてから柵を立てる)と、`xchg`(lock付きRMWの暗黙バリアに相乗りする。第3.5.2節)。意味的にはどちらも正しい。ならば速い方が勝つだけです――そして実際、コンパイラ業界ではここ十年で**勝者が交代**しました。かつてのGCCはmov+mfence派、現在の主要コンパイラはほぼ全員xchg派です。理由を自分のマシンで確認しましょう。

**リスト8-2: scstore_bench.cpp ― 2戦略の直接対決(インラインasmで固定)**

```cpp
// 戦略A: mov + mfence
KEEP void store_fence(int v) {
    asm volatile("mov %0, a(%%rip)\n\tmfence" :: "r"(v) : "memory");
}
// 戦略B: xchg(lockは暗黙)
KEEP void store_xchg(int v) {
    asm volatile("xchg %0, a(%%rip)" : "+r"(v) :: "memory");
}
// それぞれを1億回呼ぶループを計測(非競合・単一スレッド)
```

```console
$ ./scstore_bench
mov+mfence : 9.8 ns/store
xchg       : 4.6 ns/store        # 約2.1倍速い
(参考) 素のmov(release相当): 1.2 ns/store
```

現代のマイクロアーキテクチャでは、mfenceが「ストアバッファのドレイン+α」のかなり重い直列化として実装されるのに対し、lock系命令のバリア効果はより軽く済むため、xchgが概ね2倍前後勝ちます。ベンチマークの決着としてはこれだけですが、2つ書き添えておきます。

第一に、**xchgの勝利は「seq_cstストア=そのアドレスへの無意味なRMW」という奇妙な最適化**だということ。値を書くだけなのに、わざわざ「古い値を読み捨てるRMW」として実行するほうが速い――第6.5節で見た「壊れた`a = a + 1`のstore部分がxchgだった」風景の裏側です。第二に、ではmfenceは無用の長物かというと違います。mfenceには、lock系が順序付けない特殊なストア(非テンポラル系のストリーミング書き込み等)まで柵に入れる、より広い守備範囲があります。通常のatomicの世界ではxchgで十分、SIMDの特殊ストアが絡む低層コードではmfence――役割分担で両者とも現役です。

> **観測事実26**: x64のseq_cstストアの代金(非競合実測)は、xchg方式で約4.6ns、mov+mfence方式で約9.8ns、素のmov(release)の約4〜8倍。現代コンパイラがxchgを選ぶのは実測に基づく交代劇であり、「ストア側全額負担」の取り決めのもとでseq_cstロードは素のmovのまま無料に保たれる。

## 8.4 【コード】ARMのSTLR/LDARに仕込まれた仕掛け ― そして第7章の結果に潜んでいた「もう一段のただ乗り」

表8-2のARM列に、気づけば不思議な事実があります。**古典(v8.0)列では、acquire/releaseとseq_cstが同じ命令**(ldar/stlr)なのです。x64ではseq_cstストアだけが特別料金(xchg)を払ったのに、ARMのseq_cstストアはreleaseと同じstlr。では、あのStore→Loadのはみ出し1要素の代金を、ARMでは誰が払っているのでしょうか。

答えはISAの設計に埋め込まれています。ARMv8のアーキテクチャ仕様は、ldar/stlrにこう定めています:

> **stlr→ldarの順序規則(RCsc性)**: プログラム順で stlr の後にある ldar は、その stlr を追い越して観測されてはならない。つまり **stlr と ldar の対に限り、Store→Load リオーダリングも禁止**される。

素のstr/ldr、そして片方だけが順序付き命令の組には、この規則は働きません。**stlrとldarの組にだけ、TSOが唯一許した隙間まで塞いだ「seq_cstの飛び地」が現れる**――ARMv8のldar/stlrは、初めからC++11のseq_cstを1命令で実装できるよう誂えられた命令なのです(8.1節の言い方なら、この命令対に限り H が全並べ替えを含むので、seq_cstのRですら素の――ただしa/l付きの――命令で収まる)。リトマステストで確認します。SBテストをstlr/ldarで組みます(C++からはseq_cst指定で生成させます)。

```console
# ARM (Graviton3, -march=armv8-a) — SB を stlr / ldar で
$ ./sb_stlr_ldar
(r1,r2)=(0,0) が 0 / 10000000 回観測されました      # 飛び地の中では(0,0)は死ぬ
```

さて、ここで鋭い読者は椅子から身を乗り出しているはずです。**この規則は「効きすぎ」ではないのか?** acquire/releaseの契約(第7.2節)は、Store→Loadを禁じて**いません**。実際、私たちはSBのacquire/release版が壊れ続けることを膜の図から導き、M2で(0,0)を6.9万回観測しました(リスト7-1)。しかし古典対応表ではacquireロードもldarに翻訳される。ldarはstlrとの間でStore→Loadすら禁じる。ならば古典ツールチェーンでビルドしたacquire/release版SBは……(0,0)が**出ないはず**では?

実験します。同じsb_acqrel.cppを、ターゲット指定だけ変えて2回ビルドします。

```console
# ① 古典ビルド(acquire→ldar): GCC on Graviton3
$ g++ -std=c++20 -O2 -pthread -march=armv8-a sb_acqrel.cpp -o sb_classic
$ ./sb_classic
(r1,r2)=(0,0) が 0 / 10000000 回観測されました        # 出ない!

# ② 現代ビルド(acquire→ldapr): Apple Clang on M2(第7.2節と同一のビルド)
$ ./sb_acqrel
(r1,r2)=(0,0) が 68914 / 1000000 回観測されました     # 出る(第7.2節の再掲)
```

**同じC++ソース、同じ「契約上は壊れていてよい」コードが、ツールチェーン次第で壊れたり壊れなかったりする。** 種を明かします。古典対応表のldarは、seq_cstのために誂えた強い命令をacquireに**流用**したものでした。contract上不要なstlr→ldar順序まで付いてくる、いわば過剰包装です。ARMv8.3はこの過剰を削るために**ldapr**(Load-Acquire RCpc)を追加しました。ldaprはacquireの契約どおりの膜(LL・LSの禁止)だけを持ち、**先行するstlrとの順序は持ちません**。RCpc対応ターゲット(Apple Silicon、Neoverse世代等)を許されたコンパイラは、acquireをldaprに、seq_cstをldarに翻訳し分けます――表8-2の右列の分岐がそれです。第7.2節でM2が(0,0)を見せたのは、Apple Clangがまさにこのldaprでacquireをコンパイルしていたからでした。

この発見は、本書の警句を一段深くします。第7.8節で私たちは「x64のTSOにただ乗りしたコード」を糾弾しました。ところがいま判明したのは、**「acquire/releaseで書いたが実はseq_cstの強さに依存していたコード」が、古典ARMツールチェーンの過剰包装にただ乗りして、ARM実機テストすら通過してしまう**という、もう一段のただ乗りの存在です。そういうコードは、コンパイラのアップグレード(RCpc解禁)という、CPUもOSもソースも変わらない出来事で発症します。「ARMで動いた」でさえ、契約の証明にはならない――**安定な地面は契約(と、それを機械検査するherd7/Relacy)だけ**です。

> **観測事実27**: ARMv8のstlr→ldar対には、TSOの隙間まで塞ぐ順序規則(RCsc)が仕込まれており、これがARMのseq_cstを追加バリアなしで成立させている。古典対応表はこの強い命令をacquireにも流用していたため、acquire/releaseのコードが契約以上の強さを享受していた。ARMv8.3のldapr(RCpc)がこの過剰を削った結果、同一ソースのSB acquire/release版が、ツールチェーンにより「壊れない(ldar)/壊れる(ldapr)」に分岐することが実測された。ただ乗りはx64のTSOだけでなく、対応表の過剰包装にも潜む。

## 8.5 【コード】fetch_addのコード生成 ― lock add、LL/SCループ、LSE命令

最後の列、RMWの翻訳を精算します。まず素材を並べます。

```cpp
KEEP void inc_rlx() { a.fetch_add(1, std::memory_order_relaxed); }
KEEP void inc_sc () { a.fetch_add(1, std::memory_order_seq_cst); }
KEEP int  inc_get() { return a.fetch_add(1, std::memory_order_seq_cst); }
```

```asm
; ---- x64 ----
inc_rlx:  lock add DWORD PTR a[rip], 1      ; relaxedでも lock add
inc_sc:   lock add DWORD PTR a[rip], 1      ; seq_cstでも lock add(同一!)
inc_get:  mov eax, 1
          lock xadd DWORD PTR a[rip], eax   ; 旧値が要るときだけ xadd

; ---- AArch64 v8.0(LL/SC)----
inc_sc:   .L: ldaxr w8, [x9]                ; 排他ロード(acquire)
              add   w8, w8, 1
              stlxr w10, w8, [x9]           ; 排他ストア(release)
              cbnz  w10, .L                 ; 失敗なら再試行(第6.3節の偽失敗の現場)

; ---- AArch64 v8.1+(LSE)----
inc_rlx:  ldadd  wzr, wzr, [x9]             ; 単一命令、順序サフィックスなし
inc_sc:   ldaddal wzr, w8, [x9]             ; a=acquire, l=release 付き
```

x64の上2行が、この本で3回目の登場となる重要事実の最終確認です。**x64のRMWは、relaxedと指定してもlock付き=全バリア込み。** オーダー引数はコード生成に一切反映されません(第3.5.2節の「lockの副作用へのただ乗り」、表6-1でrelaxed版fetch_addがx64で1nsも速くならなかった謎の、これが最終回答です)。対照的にLSEのサフィックス体系(無印/`a`/`l`/`al`)は、C++の4段のRMWオーダー(relaxed/acquire/release/acq_rel≒seq_cst)に**1対1で対応する初めてのISA**であり、だからこそ表6-1のARM列でだけrelaxedの配当(2.6ns vs 7.1ns)が現金化されたのです。

LL/SC対LSEの勝負も、非競合の命令数だけでは決まりません。競合下でこそ差が開きます。8スレッドで同一カウンタを叩く、第6章の地獄のベンチマークを2ビルドで比較します。

```console
# Graviton3、8スレッド競合、1加算あたり
$ ./contend_llsc    (-march=armv8-a)
212 ns/op            # 失敗→再試行の嵐(偽失敗2%はこの嵐の一部)
$ ./contend_lse     (-march=armv8.1-a)
94 ns/op             # 2.3倍。単一命令RMWは「持って帰って計算」せず、その場で足せる
```

LL/SCは「ラインを自分の所へ運んできて、読み、計算し、書き戻す」往復の間ずっと横取りに怯えますが、LSEの単一命令RMWは実装によってはキャッシュ階層の近く(場合によってはラインを動かさずに)で加算を完了でき、競合時の再試行の嵐そのものが消えます。実務への接続をひとつ:Linux向けの主要コンパイラは既定で`-moutline-atomics`という仕組みを使い、**実行時にCPUのLSE対応を検出して両実装を切り替える**小さな関数経由でRMWを発行します(逆アセンブルで`__aarch64_ldadd4_relax`のような呼び出しを見たら、それです)。Gravitonの性能ガイドが口を酸っぱくしてLSE有効化を説くのは、この2.3倍が背景です。

> **観測事実28**: x64のRMWはオーダー指定にかかわらずlock付き全バリアで翻訳され、オーダーの粒度が消失する。ARMのLSEはC++のRMWオーダーに1対1対応する初のサフィックス体系を持ち、relaxedの配当を現金化し、さらに競合下でLL/SC比2.3倍(実測)のスケーリングを示す。

## 8.6 実験からの教訓 ― 警句の最終形

対応表が完成したので、本書の警句「x64での測定はオーダー選択の検証にならない」を、根拠付きの最終形に鍛え直せます。表8-2を「検証装置としての各環境に何が見えるか」という向きに読み替えます。

**表8-3: 各検証環境の「見える誤り・見えない誤り」**

| 検証環境 | 見える誤り | 原理的に見えない誤り |
|---|---|---|
| x64 実行テスト | SB型をseq_cst未満で書いた誤りのみ | **acquire/releaseの欠落ほぼ全部**(R⊆Hで吸収) |
| x64 性能測定 | seq_cstストアの過剰(xchg代)のみ | relaxed↔acq/relの差(全部mov) |
| ARM古典TC 実行テスト | relaxedの欠落(MP型) | **acq/rel↔seq_cstの混同**(過剰包装ldarが吸収) |
| ARM RCpc TC 実行テスト | 上記+SB型のacq/rel誤用 | 実行されなかったインターリーブ(常に) |
| TSan | happens-before欠落(素の変数が絡む場合) | 全アトミック化された順序バグ(6.5節、7.8節) |
| herd7 / Relacy | **契約レベルの全誤り**(網羅的) | 契約外の性能・活性の問題 |

3行目と4行目の対比が、この章で加わった新しい知見です。誤りの検出可能性は「x64かARMか」の2値ではなく、**ツールチェーンの対応表の細部にまで依存する**。実行テストとは、契約ではなく「契約×対応表×アーキテクチャ」の積を検査する装置であり、積のどこか1因子が過剰に強ければ、契約の穴は隠れます。だから本書の検証方針はこう定まります――**正しさの根拠は契約とモデル検査(表の最下行)に置き、実行テストは「弱い因子の組み合わせ」(RCpcターゲットのARM実機)を意図的に選んで感度を最大化し、アセンブリ検分は対応表の監査として、ベンチマークはアーキテクチャ別の値付けとして使う。** 4種の道具の役割分担です。

もうひとつ、値付けの総括を。x64のオーダー間の価格差は「seq_cstストアか否か」の1点に集中し(4.6ns vs 1.2ns)、それ以外は全部同額。ARMでは relaxed < acquire/release(ldapr/stlr)< seq_cst(ldar/stlr対)< フェンス(dmb)と、契約の強さに概ね比例した値付けが実現しています。**「弱いオーダーで性能を買う」という営みは、ARMでのみ額面どおりに成立する**――だからこそ緩める作業(第7章)の検証と計測は、ARMで行うのです。

### 第8章のまとめ

- 対応表は暗記ではなく導出:オーダーの要求Rとアーキテクチャの無条件保証Hを比べ、R⊆Hなら素の命令、はみ出しだけバリアで買う。義務B(CPU向け)が無料でも義務A(コンパイラの自粛)は常に有効(8.1節)。
- **観測事実25**: 導出した表は実出力と全行一致。x64はseq_cstストアのはみ出し1要素(Store→Load)だけがxchg/mfenceの代金を払う。
- **観測事実26**: seq_cstストアはxchg方式がmov+mfence方式の約2倍速く、現代コンパイラの標準。「ストア側全額負担」はABIレベルの取り決めで、seq_cstロードのmov無料はその配当。
- **観測事実27**: stlr→ldar対のRCsc規則がARMのseq_cstを成立させる一方、古典対応表はこの強い命令をacquireに流用していた(過剰包装)。ldapr(RCpc)がそれを削り、同一ソースの挙動がツールチェーンで分岐する――ただ乗りは対応表にも潜む。
- **観測事実28**: x64のRMWはオーダー粒度が消失(常にlock)、ARMのLSEは1対1対応で配当を現金化し、競合下でLL/SC比2.3倍スケール。outline-atomicsが実行時切り替えを担う。
- 検証装置の感度は「契約×対応表×アーキテクチャ」の積で決まる(表8-3)。正しさはモデル検査で、感度最大の実行テストはRCpcなARMで、アセンブリは監査、ベンチはアーキ別値付け(8.6節)。

これで第2部・契約編の全課程が終わりました。定義(第5章)、道具(第6章)、値付け(第7章)、翻訳(第8章)。第3部からは、この全装備を持って実戦に出ます。手始めの第9章は同期プリミティブの自作――第6.2節の素朴なスピンロックがなぜ競合下でひどい性能なのかを診断し、TTAS、バックオフ、そしてfutexへと鍛え直しながら、std::mutexの内部を丸裸にします。
