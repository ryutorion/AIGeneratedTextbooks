# 第10章 ロックフリーデータ構造 ― SPSCキューからABA問題まで

第9章までの同期は、突き詰めれば「1人ずつ通す」哲学でした。ロックフリーはその対極、第6.5節で予告した**楽観的並行制御**の哲学です――割り込みを防がず、割り込まれたら検出してやり直す。この章では、その哲学で建てられたデータ構造を、易しいものから順に建てます。SPSCリングバッファ(10.1〜10.2節)、Treiberスタック(10.3節)、そしてスタックを蝕む2つの深い病――ABA問題(10.4〜10.5節)とメモリ回収問題(10.6節)。最後に、本書が第2章から予告し続けてきたケーススタディ、「Gravitonに移行したら落ちるようになった」の再現と修正(10.7節)で第3部の山場を越えます。

用語を3つだけ先に定義します。並行データ構造の**進行保証**の3段階です。

> **wait-free(無待機)**: どのスレッドも、他スレッドの挙動によらず有限ステップで自分の操作を完了できる。
> **lock-free(無ロック)**: 個々のスレッドは飢餓しうるが、**システム全体では**常に誰かの操作が有限ステップで完了する。
> **obstruction-free(無障害)**: 他の全スレッドが停止してくれれば、有限ステップで完了できる。

この章の構造はすべてlock-freeです。「私のCASが失敗するのは、他の誰かのCASが成功したときだけ」――個人の敗北が全体の前進の証明になっている、という構造的性質がlock-freeの核心で、ロックとの決定的な違いはここにあります。ロック保持者がOSに眠らされたら(第9.2節)全員が止まりますが、lock-free構造では、どのスレッドがいつ止められても他の全員は進み続けます。優先度逆転もデッドロックも、定義により存在しません。ではなぜ世界はロックだらけなのか――その答え(正しく作ることの異様な難しさ)を、この章で身をもって学びます。

## 10.1 【コード】SPSCリングバッファ ― acquire/release最小構成の完成形を写経する

出発点は、ロックフリー界の「ハローワールド」にして、実務での使用頻度が最も高い構造です。**SPSC(Single Producer, Single Consumer)リングバッファ**――書き手1人・読み手1人限定の待ち行列。オーディオ処理のスレッド間受け渡し、ログの収集、割り込みハンドラからの通知と、「1対1のパイプ」が要る場所すべてに現れます。役者が2人しかいないため、CASすら不要で、第7章のacquire/releaseだけで完結します。まず完成形を掲げ、その後で**全行**に注釈を付けます。写経を推奨します――この30行は、本書前半の全知識が1行も無駄なく詰まった結晶だからです。

**リスト10-1: spsc.cpp ― SPSCリングバッファ完成形**

```cpp
template <class T, size_t N>                     // Nは2の冪
class SpscQueue {
    static_assert((N & (N - 1)) == 0);
    T buf[N];                                    // ペイロード置き場(素のT)

    alignas(std::hardware_destructive_interference_size)
    std::atomic<size_t> head{0};                 // 次に読む位置。消費者だけが書く
    alignas(std::hardware_destructive_interference_size)
    std::atomic<size_t> tail{0};                 // 次に書く位置。生産者だけが書く

public:
    bool push(const T& v) {                      // 生産者専用
        size_t t = tail.load(std::memory_order_relaxed);   // ①
        size_t h = head.load(std::memory_order_acquire);   // ②
        if (t - h == N) return false;                      // ③ 満杯
        buf[t % N] = v;                                    // ④
        tail.store(t + 1, std::memory_order_release);      // ⑤
        return true;
    }
    bool pop(T& v) {                             // 消費者専用
        size_t h = head.load(std::memory_order_relaxed);   // ⑥
        size_t t = tail.load(std::memory_order_acquire);   // ⑦
        if (t == h) return false;                          // ⑧ 空
        v = buf[h % N];                                    // ⑨
        head.store(h + 1, std::memory_order_release);      // ⑩
        return true;
    }
};
```

この構造の美しさは、**2本のMPパターン(第7章)が逆向きに編み込まれている**ことです。1本目は自明です:生産者がデータ(④)を封して荷札(⑤のtail)を渡し、消費者が荷札を開封(⑦)してデータを読む(⑨)。⑤→⑦のロープが「**書かれたものを読む**」を保証します。では2本目は? ⑩と②です。消費者は、スロットを読み終えた(⑨)**という事実**を封して(⑩のhead)、生産者に返しています。生産者はそれを開封(②)してから、同じスロットに上書きします(④)。⑩→②のロープが「**読み終わる前に上書きしない**」を保証する。**データを渡すロープと、器を返すロープ。** 往路と復路の2本が揃って初めて、素のT(④⑨は非アトミックアクセスです!)が競合フリーになります。TSanは沈黙します――第5.2節で学んだ「保護対象を素のまま書き、TSanを検算器にする」技法の、これが実戦形です。

残りの注釈も済ませます。①⑥がrelaxedでよい理由:tailは生産者しか書かないので、①は**自分が最後に書いた値を読む**だけ――変更順序のコヒーレンス(第4.5節、観測事実12)が単独で正しさを保証し、ロープは不要です(⑥も対称)。③の`t - h`は符号なし整数の自由回転(インデックスを剰余せず走らせ、差で在庫を数える)で、Nが2の冪なら`% N`はAND1個になります。そして`alignas`――headとtailは互いに別スレッドが叩き続ける2変数であり、同居させたら第4章のフォールスシェアリングの教科書事例になります。実測では、alignasの有無でスループットが約1.6倍違いました。

性能も見ておきます。int要素、生産者・消費者各1スレッド:

```console
mutex + std::queue     :  11 M ops/s
SpscQueue(リスト10-1)  : 264 M ops/s      # 24倍
```

## 10.2 【コード】インデックスをrelaxedに緩めて壊す ― この30行に緩める余地は残っているか

リスト10-1には、オーダー指定が6箇所あります(relaxed×2、acquire×2、release×2)。第7章の流儀に従えば、次に問うべきはこれです:**この構成は最小か?** つまり、acquire/releaseの4箇所のうち、まだrelaxedへ緩められる箇所は残っているのか。第7.3節の壊し戻しを、今度は6連装でやります。1箇所ずつrelaxed化した変種を作り、ARM実機(不変条件:pushした値列とpopした値列の一致を検査)とTSan(ペイロードが素のTなので検算器が効きます)の両方にかけました。

**表10-1: 6箇所それぞれの役割と、relaxed化の結末**

| 箇所 | 担うロープ | relaxed化 → ARM実機 | TSan |
|---|---|---|---|
| ① tail自己読み | なし(自分の書きを読むだけ) | (もとからrelaxed) | 沈黙 |
| ⑥ head自己読み | なし(同上) | (もとからrelaxed) | 沈黙 |
| ⑤ tail store(release) | 往路の封:データ→荷札 | **破れ**: 古い値がpopされる(83/10⁶) | **競合検出** |
| ⑦ tail load(acquire) | 往路の開封 | **破れ**: 未公開スロットを先読み(41/10⁶) | **競合検出** |
| ⑩ head store(release) | 復路の封:読了→返却 | 観測できず(0/10⁸)※ | **競合検出** |
| ② head load(acquire) | 復路の開封 | 観測できず(0/10⁸)※ | **競合検出** |

答えは出ました。**リスト10-1は既に最小です。** 緩められる2箇所は最初からrelaxedであり、残り4箇所はどれか1つを緩めた瞬間、少なくとも契約上の競合(TSan検出)に転落します。往路の2箇所(⑤⑦)はARM実機でも素直に破れました――第2章のMPそのものだからです。

注目すべきは※印の復路の2箇所です。契約上は明白に競合なのに、ARM実機で1億回まわしても破れが観測できませんでした。理由まで言える読者になっているはずです。復路のロープが防ぐのは「消費者のロード(⑨)が返却(⑩)より後ろへ沈み、生産者の上書き(④)と衝突する」事態で、これは**Load→Store型**(先のロードを後のストアが追い越す)の並べ替えです。第2章の演習1で注記したとおり、LB型の並べ替えは現代のAArch64実装ではまず観測されません(生産者側②の緩めも、③の分岐への制御依存と「投機ストアは外に見えない」というCPUの大原則に、実機上は救われます)。**つまり復路の2箇所は、「実機テストでは絶対に見つからないが、契約上は壊れている」誤りの最上級の見本**です。第7.6節・第8.6節で研いだ結論――実行結果ではなくTSanとモデル検査を信じる――が、実戦の30行の中にこうして現れます。

> **観測事実33**: SPSCリングバッファのacquire/release4箇所は全て構造を支えており(往路=データの封、復路=器の返却の封)、1箇所でも緩めると契約違反になる。うち復路2箇所はLB型ゆえARM実機ですら破れが観測できず、TSan/モデル検査だけが検出できる。緩める余地は「自分の書きを読む」2箇所に尽き、リスト10-1は最小構成である。

## 10.3 【コード】Treiberスタック ― read-modify-CASを構造体の世界へ

役者が3人以上になると、acquire/releaseの受け渡しだけでは足りず、CAS(第6章)が主役に昇格します。多生産者・多消費者に対応する最古かつ最小のロックフリー構造、**Treiberスタック**(R. K. Treiber, 1986)です。構造は連結リスト1本、共有状態は先頭ポインタ`top`ただ1つ。

**リスト10-2: treiber.cpp**

```cpp
struct Node { int v; Node* next; };

class TreiberStack {
    std::atomic<Node*> top{nullptr};
public:
    void push(int v) {
        Node* n = new Node{v, top.load(std::memory_order_relaxed)};
        while (!top.compare_exchange_weak(
                   n->next, n,                       // 「n->nextのままなら、先頭をnに」
                   std::memory_order_release,        // 成功時: ノード内容を封して公開
                   std::memory_order_relaxed)) {}    // 失敗時: 新topがn->nextに配達される
    }
    bool pop(int& out) {
        Node* t = top.load(std::memory_order_acquire);
        while (t && !top.compare_exchange_weak(
                   t, t->next,                       // 「tのままなら、先頭をt->nextに」
                   std::memory_order_acquire,        // 成功時: 外したノードの中身を開封
                   std::memory_order_acquire)) {}    // 失敗時: 新topの中身も開封して再挑戦
        if (!t) return false;
        out = t->v;
        delete t;                                    // ← この行が10.4節からの全事件の火元
        return true;
    }
};
```

第6.5節のread-modify-CASループが、intからポインタに、そして「掛け算」から「リストの繋ぎ替え」に育った姿です。pushのCAS失敗時、expected(=`n->next`)には最新のtopが**書き戻される**――第6.2節で罠だったあの仕様が、ここでは「自分のノードのnextを最新先頭へ自動で付け替える」という、ほとんど詩的な機能になっています。オーダーの配置も注釈しておきます。pushの成功releaseは「ノードの中身(v, next)を封してから公開する」――第9.3節のDCLPで学んだ、まさにあの公開の封です。popで見逃されがちな急所は**失敗時オーダーがacquire**であること。ループ2周目の`t->next`という参照は、失敗CASが書き戻してくれた**新しいt**の中身を読む行為なので、その書き戻しに開封が付いていなければ未公開のノードに触れてしまいます(relaxedにするとTSanが正しく検出します)。

進行保証も確認しましょう。私のCASが失敗するのは、topが変わったとき――つまり**他の誰かのpush/popが成功したとき**だけ。全員が失敗し続ける実行は存在せず、システム全体は常に前進する。lock-freeの定義を、コードの形がそのまま証明しています(ただし特定の1人が負け続ける飢餓はありえます。wait-freeではありません)。

なお、多生産者・多消費者の**FIFO**が要るときの実務標準はMichael-Scottキュー(1996)です。head/tailの2ポインタ、番兵ノード、そして「他人のやりかけを手伝って進める(helping)」という新技法が加わりますが、CASループの文法はTreiberと同じなので、本書は全体実装を演習5に譲ります。この節の主題は、次節から始まる**事件**のほうです。リスト10-2は、8スレッドで数秒回すだけで、ときどきクラッシュします。火元はコメントを付けた1行、`delete t`です。

## 10.4 【コード】ABA問題を意図的に発生させる

まず、deleteが引き起こす2段階の事件のうち、派手な方から再現します。状況設定はこうです。

```text
初期状態: top → A → B → C

スレッド1: pop開始。 t = A、t->next = B を読んで、CAS(A→B) を発行する直前に
           OSに preempt される(ここで昼寝)。

スレッド2: pop() → Aを取得・delete。 pop() → Bを取得・delete。
           push(D) → アロケータが「さっき空いた」Aの番地を再利用し、
           新ノードDは 番地A に置かれる。 いま top → A(中身はD) → C。

スレッド1: 目覚めてCASを発行。「topがAのままなら、Bにせよ」――
           topは確かにA(番地として)。 CASは成功する。
           top → B。 しかしBは delete済みの残骸。スタック崩壊、Cは行方不明。
```

CASは「値がexpectedのままか」しか見ません。番地Aは、いったんBになりDになった**歴史**を持つのに、値としてはAに戻っている――**A・B・A**。第6.5節の末尾で予告した「read-modify-CASの暗黙の仮定:値が同じなら割り込まれていない」が、値(番地)のリサイクルによって破られる瞬間です。

再現ハーネスの要点は**番地の再利用を意図的に最速化する**ことです。汎用アロケータの再利用は運任せなので、解放ノードを即座にLIFOで返すフリーリストを使い、さらに解放時にノードへ毒値(v = 0xDEAD)を書き込んでおきます。検出は2系統:popが毒値を返したら「残骸を掴んだ」、総push数と総pop数+残数が合わなければ「要素が蒸発した」。8スレッドで回します。

```console
# x64
ABA起因の崩壊 214 回 / 10⁶ pop
# ARM (Apple M2)
ABA起因の崩壊 189 回 / 10⁶ pop
```

**両アーキテクチャで、同程度に、盛大に壊れました。** この対称性が重要です。本書はここまで「x64では隠れ、ARMで発火する」バグばかり追ってきましたが、ABAは**メモリモデルのバグではありません**。順序でも可視性でもなく、「CASが歴史ではなく値を比較する」という道具の意味論と、番地が再利用されるという環境の性質が衝突する、**純粋な論理バグ**です。TSOも守ってくれません。seq_cstにしても直りません(演習3で確認してください)。ロックフリーの難しさは、ここで二乗になります――第7章までの**順序の正しさ**(アーキテクチャ依存)と、この章の**歴史の正しさ**(アーキテクチャ非依存)を、両方同時に満たさなければならないのです。

> **観測事実34**: ABAはx64とARMで同頻度に再現する、メモリモデル非依存の論理バグである。原因はCASが「歴史」ではなく「値」を比較すること+番地の再利用。メモリオーダーをいくら強めても直らない。

そしてもう1つ、地味な方の事件も指摘しておかなければなりません。上のシナリオで、スレッド1は昼寝から覚めてCASする前に、`t->next`を読んでいました。**delete済みの番地Aからの読み取り**です。ABAが起きなくても、この読み自体が既に未定義動作(use-after-free)であり、アロケータがページをOSに返していれば即クラッシュします。つまりリスト10-2の病は「(a) 解放済みメモリに触る」と「(b) 再利用された番地にCASが騙される」の2段構えで、(b)だけ塞いでも(a)が残る――この見取り図を持って、対策編に進みます。

## 10.5 【コード】タグ付きポインタ ― 値に歴史を刻む(cmpxchg16b vs casp)

(b)への正攻法は、CASの比較対象に**歴史を混ぜ込む**ことです。ポインタに世代カウンタ(タグ)を添え、topを更新するたびタグを+1する。番地Aが再利用されて戻ってきても、タグが進んでいるので古いCASは正しく失敗します。

**リスト10-3: tagged.cpp(骨子)**

```cpp
struct alignas(16) Head {
    Node*     ptr;
    uintptr_t tag;                                // 更新のたび+1する世代番号
};

std::atomic<Head> top;                            // 16バイト: is_lock_free()の実行時確認必須(第6.4節)

bool pop(int& out) {
    Head h = top.load(std::memory_order_acquire);
    while (h.ptr && !top.compare_exchange_weak(
               h, Head{h.ptr->next, h.tag + 1},   // ポインタとタグを一括CAS
               std::memory_order_acquire, std::memory_order_acquire)) {}
    ...
}
```

16バイトの一括CAS――第6.4節で「境界線上の住人」として保留した倍幅アトミックの、これが本籍地です。x64では`-mcx16`付きで`lock cmpxchg16b`、ARMではLSEの`casp`(ペアCAS)または`ldxp/stxp`のLL/SC対に翻訳されます。ハーネスで再計測すると、ABA起因の崩壊は両アーキテクチャで**0回**になりました。

ただし、この道具の値札と但し書きを3つ。**第一に、16バイトの「純粋なロード」問題。** x64には16バイトのアトミックロード命令が(古典的には)無く、処理系はロードすら`cmpxchg16b`で代用することがあります。つまり**読むだけでラインをM状態に汚す**――第4章と第9.5節で学んだ「読者は書くな」の原則に真っ向から反し、読み側スケーラビリティを蝕みます(読み取り専用ページ上のatomicがフォールトする、という珍事の原因でもあります)。**第二に、タグ幅と周回。** 8バイトに収めたい場合、整列保証から下位ビットを、あるいは仮想アドレスの未使用上位ビットを借りてタグにする節約術が定番ですが、狭いタグは一周して再びABAになりえます(2¹⁶回の更新は一瞬です)。**第三に、そして最重要――タグは事件(b)しか解決しません。** `h.ptr->next`の参照は依然として解放済みメモリに触れうる。フリーリスト運用(メモリをOSに返さない)なら実害が出にくいだけで、契約上のuse-after-freeは残ったままです。

> **観測事実35**: タグ付きポインタ(倍幅CAS: cmpxchg16b/casp)はABAを完全に封じる(崩壊0回)が、解放済みメモリへのアクセス(事件(a))は解決しない。また16バイトアトミックはロードすら書き込みになりうるという読者スケーラビリティの罠を持つ。根治には回収の仕組みそのものが要る。

## 10.6 【コード】ハザードポインタの最小実装 ― 「読んでいる間は捨てさせない」

事件(a)の根治は、問いの立て直しから始まります。「いつdeleteすれば安全か?」――答え:**誰もそのノードを覗いていなくなったとき**。ならば、覗いている者に「いま覗いている」と公示させ、捨てる側は公示板を確認してから捨てればよい。これが**ハザードポインタ**(M. Michael, 2002)です。最小実装は驚くほど小さい:

**リスト10-4: hazard.cpp ― 最小のハザードポインタ**

```cpp
constexpr int MAX_THREADS = 8;
std::atomic<Node*> hazard[MAX_THREADS];           // 公示板(スレッドごとに1枠)

Node* protect(std::atomic<Node*>& src, int tid) {
    Node* p;
    do {
        p = src.load(std::memory_order_acquire);
        hazard[tid].store(p, std::memory_order_seq_cst);   // ① 公示(seq_cst!)
    } while (src.load(std::memory_order_acquire) != p);     // ② 公示後に、まだ先頭か再確認
    return p;                                               //    一致して初めて「保護成立」
}

void retire(Node* n, int tid) {                   // deleteの代わりに呼ぶ
    retired[tid].push_back(n);
    if (retired[tid].size() >= THRESHOLD) {
        for (Node* r : /*回収候補*/) {
            bool in_use = false;
            for (auto& h : hazard)                          // ③ 公示板を走査
                if (h.load(std::memory_order_seq_cst) == r) { in_use = true; break; }
            if (!in_use) delete r;                          // 誰も覗いていなければ本当に捨てる
        }
    }
}
```

popの冒頭を`Node* t = protect(top, tid);`に替え(CAS失敗のたびに再protect)、`delete t`を`retire(t, tid)`に替えれば、Treiberスタックの2つの事件は両方消えます。(a)は定義どおり(覗かれている間は回収されない)。(b)も消えます――番地が再利用されるにはまず回収されねばならず、回収は保護が外れるまで起きないので、「保護中に同じ番地が別人として蘇る」シナリオ自体が成立しないからです。ハーネス再計測:崩壊0、TSan沈黙、AddressSanitizerも沈黙。

さて、この短いコードには、本書の読者への最後の試験が2つ仕込まれています。**第一問:②の再確認はなぜ必要か。** ①の公示は、srcを読んだ「後」に行われます。読んでから公示するまでの隙間に、相手がretire→公示板走査(③)を終えていたら? 走査時点で私の公示はまだ無く、ノードは捨てられ、私は解放済みの番地を「保護した」と思い込む。②は「公示が**間に合った**こと」を、srcが変わっていない事実で証明する再確認です。第9.2節のfutexの条件節、第9.5節のseqlockの検査2と同じ、「確認と行為の間の隙間を、事後検証で閉じる」一族の技法です。

**第二問:①と③はなぜseq_cstなのか。acquire/releaseでは駄目なのか。** 構図を抜き出してみてください。私:hazardに**ストア**(①)してからsrcを**ロード**(②)。相手:srcを(実質)**ストア**(topの付け替え)してからhazardを**ロード**(③)。――双方が「書いてから、相手の書き場所を読む」。**これは第2章のSBパターンそのものです。** そして観測事実21(第7.2節)が告げたとおり、SB型をacquire/releaseで書くと**x64ですら壊れます**。①のストアが②のロードに追い越されれば(Store→Load!)、相手は無地の公示板を見て私の保護中ノードを捨てる。ここはseq_cst(または双方へのseq_cstフェンス)が**構造的に必須**な場所――「seq_cstが本当に必要な実在のコード」を挙げよと問われたら、ハザードポインタの公示と走査、と答えてください。実務ライブラリ(folly等)がこの1点のためにseq_cstフェンスを払い、その代金を惜しんで公示を非同期化する研究が今も続いているのは、この構図が本質的だからです。

> **観測事実36**: ハザードポインタの「公示してから再確認」対「付け替えてから走査」はSBパターンであり、acquire/releaseでは(x64でも)保護が破れうる。ここはseq_cstが構造的に必須の実例である。この対価(保護1回=seq_cstストア+再確認ロード)により、use-after-freeとABAが同時に根治する。

対価も測っておきます。保護のオーバーヘッドで、popのスループットは裸のTreiber比で約35%低下しました(それでもmutex版スタックの6倍です)。回収の哲学には他の流派もあります――「個々のノードではなく**時代**単位で引退させる」エポックベース回収(RCUの親戚。読者は世代番号を跨がない限り自由、回収は全読者が世代を跨いでから)。読み側がさらに軽い代わりに、1人の読者の停滞が全回収を止める、という別のトレードオフを持ちます。そしてこの分野は、`std::hazard_pointer`と`std::rcu`としてC++26へ向けた標準化が採択されるところまで来ました。20年かけて、回収問題は言語の標準装備になりつつあるのです。

## 10.7 ケーススタディ:「Gravitonに移行したら落ちるようになった」

最後に、第2章から札を立て続けてきた事例を回収します。以下は、公開されている複数の実事例と筆者の経験を合成し、細部を再構成したものです――しかし読者はすぐ気づくはずです。**登場する誤りのすべてが、本書で既に実験済みである**ことに。

**背景。** ある配信系サービスの計測パイプライン。リクエスト処理スレッドがイベントを生成し、集計スレッドが消費する。中核は10年前に書かれた自家製SPSCリングバッファでした。当時の作者は腕利きで、ロックを嫌い、こう書いていました――インデックスは`volatile size_t`、スロットは素の構造体、バリアなし。x64サーバーで10年間、24時間365日、**一度も問題を起こしませんでした**。テストも、負荷試験も、本番も、すべて青。

**事件。** コスト削減のため、艦隊をGraviton(AArch64)インスタンスへ移行。数時間後から、集計値の異常(存在しないはずのイベント種別、負の継続時間)が、およそ10⁷イベントに数件の頻度でアラートを鳴らし始めます。移行の差分は「インスタンスタイプ」のみ。当然、疑いはインフラへ向かい、数週間が溶けました――アロケータ疑惑、コンパイラのバージョン疑惑、果ては宇宙線。ステージングでは再現しません(負荷が本番の1/100だったからです。第2章で学んだとおり、破れの頻度は競合の圧力に比例します)。

**診断。** 本書の道具を順に当てれば、机上で30分の作業です。第一に、コードの構図読み(表7-1)。「スロットに書く→tailを進める」「headを読む→スロットを読む」――**裸のMP、往路と復路の2本**(10.1節の⑤⑦⑩②が全部volatile=実質relaxed未満)。第1.4節で学んだとおりvolatileはロープを1本も張りません。x64の10年無事故は、実力ではなく**TSOの往路保証(FIFOドレイン)と復路保証(ロード順)への、二重のただ乗り**(第3.2.2節・第7.8節)。第二に、TSan。スロットが素の構造体だった(不幸中の幸いです)ため、初回実行で往路・復路とも競合検出。「なぜ10年間TSanを?」――「volatileで同期してるから誤検知だと思って抑止リストに入れていた」。第三に、駄目押しのherd7。⑤⑦を抜き出したリトマステストは、x86モデルでForbidden、AArch64モデルで**Allowed**。「x64では起こり得ず、ARMでは仕様どおり起こる」ことの機械証明です。

**修正と検収。** 差分はリスト10-1への置き換え、実質6箇所のオーダー注釈です。x64向けバイナリの逆アセンブル差分は――もう言うまでもありません――**ゼロ**(mov/movのまま。第8章表8-2)。Graviton向けは`ldar`/`stlr`が4個増え、スループット低下は計測誤差の範囲。ついでにheadとtailが同一キャッシュラインに同居していたことも発覚し、`alignas`の追加で**両アーキテクチャとも**スループットが約30%向上。バグ修正が性能改善で黒字になるという、後日談まで第4章の教材どおりでした。

**組織の学び。** 技術的な根治よりも、再発防止の3項目のほうが本書の締めくくりにふさわしいでしょう。(1) **CIにARMを常備する**――ただし第8.4節で学んだとおり、ARMのなかでも検出感度はツールチェーンに依存する。RCpc世代のターゲットを選ぶ。(2) **TSanの抑止リストは負債である**――「アトミックだから」「volatileだから」という抑止理由は、第5〜6章のどの定義にも根拠を持たない。(3) **中核の並行構造はモデル検査を通す**――実行テストは「契約×対応表×アーキテクチャの積」しか検査できない(表8-3)。herd7とRelacy(次章)だけが契約そのものを検査する。

この事例に、新しい知識は1つもありませんでした。第1章のvolatileの誤解、第2章のMP、第3章のTSO、第4章のフォールスシェアリング、第5章のTSan、第7章の構図読み、第8章の0円の保険料、第10章のSPSC――**全部の章が、1つの実話の中で持ち場についただけ**です。それこそが、本書が「壊して直す」形式にこだわった理由です。

### 第10章のまとめ

- 進行保証の3段階(wait-free/lock-free/obstruction-free)。lock-freeの核心は「私の敗北=誰かの前進」という構造的性質であり、CASループの形がそのまま証明になる。
- SPSCリングバッファは「データを渡す往路」と「器を返す復路」の2本のMPを編んだ構造。自己インデックスの2箇所だけがrelaxed可能で、リスト10-1は最小構成(**観測事実33**)。復路の破れはLB型ゆえ実機で観測不能――TSan/モデル検査だけが見張れる。
- Treiberスタックはread-modify-CASの構造体版。CAS失敗時のexpected配達が「nextの自動付け替え」として機能し、失敗時acquireが次周の参照を守る(10.3節)。
- **観測事実34**: ABAはアーキテクチャ非依存の論理バグ。CASは歴史ではなく値を比較する。オーダー強化では直らない。事件は「(a) 解放済みへのアクセス」「(b) 再利用番地への誤CAS」の2段構え。
- **観測事実35**: タグ付きポインタ(cmpxchg16b/casp)は(b)を根絶するが(a)は残す。倍幅アトミックは「ロードすら書き込み」の罠を持つ。
- **観測事実36**: ハザードポインタは(a)(b)を同時に根治する。「公示→再確認」対「付け替え→走査」はSBパターンであり、seq_cstが構造的に必須の実例。回収問題はC++26で標準装備(hazard_pointer/rcu)へ。
- Gravitonケーススタディは本書全章の総復習である:volatile≠同期、TSOへの二重ただ乗り、TSan抑止リストの負債、herd7による機械証明、修正のx64コスト0円、alignasの副産物30%。実行テストが検査できるのは契約×対応表×アーキテクチャの積にすぎない(10.7節)。

次の第11章では、この章で何度も頼った「実行テストの外側の検証」を主役に据えます。TSanの検出限界を攻め、herd7/litmus7で形式モデルと実機を三点照合し、Relacyで全実行順序を網羅検査する――「1億回に1回」を1分で仕留める技術です。
