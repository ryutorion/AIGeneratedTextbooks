# 第2章 リオーダリングを観測する

第1章のバグは、いわば「わかりやすい」バグでした。`counter++`が3命令に分かれ、その隙間に他スレッドが割り込む――時系列を1本の表に描けば、誰でも納得できる壊れ方です。

この章で観測する現象は、そういう納得を許してくれません。**「プログラムに書いた順番どおりに実行される」という、疑ったことすらない前提そのもの**が崩れます。しかも崩れ方がアーキテクチャによって違う。同じソースコード、同じロジックが、x64ではある壊れ方だけをし、ARMではさらに別の壊れ方を上乗せしてきます。

この章の進め方は第1章と同じです。まず壊す。回数を数える。そして章の最後に、観測結果の一覧表から**x64の壊れ方には奇妙な「規則性」がある**ことを見つけます。その規則性に名前を付けるのが第3章の仕事です。

> **リトマステストという道具**
> これから書くプログラムは、並行システムの研究で「リトマステスト(litmus test)」と呼ばれる形式です。各スレッドに2〜3命令だけの極小コードを与え、何百万回も走らせて、「起こりうる結果」と「決して起こらない結果」の境界線をあぶり出します。化学のリトマス試験紙と同じで、テスト自体は単純ですが、アーキテクチャの性質を鋭敏に検出します。主要なテストには SB、MP、LB、IRIW といった略称が付いており、本書でも以後この名前で呼びます。

## 2.1 【コード】Store Bufferingリトマステスト ― 「両方0」という"ありえない"結果をx64で出す

最初のテストは **SB(Store Buffering)** と呼ばれる、この分野でもっとも有名なテストです。骨格はこれだけです。

```text
初期状態: x = 0, y = 0

スレッド1:            スレッド2:
  x = 1;                y = 1;
  r1 = y;               r2 = x;

問い: r1 == 0 かつ r2 == 0 になることはあるか?
```

直感で考えてみてください。2スレッドの4命令がどんな順序で交互実行(インターリーブ)されたとしても――全部で6通りの並べ方がありますが――**最初に実行される命令は必ずどちらかのストア**です。`x = 1`が先なら、後で実行される`r2 = x`は1を読むはず。`y = 1`が先なら`r1 = y`が1を読むはず。つまり`r1`と`r2`の**少なくとも一方は必ず1**になる。両方0は論理的にありえない。……はずです。

実験しましょう。リスト2-1は、この4命令を100万回繰り返して(0,0)の回数を数えるハーネスです。

**リスト2-1: sb.cpp ― Store Bufferingテスト**

```cpp
#include <atomic>
#include <cstdio>
#include <thread>

using std::memory_order_relaxed;
using std::memory_order_acquire;
using std::memory_order_release;

std::atomic<int> x{0}, y{0};        // テスト対象の共有変数
int r1, r2;                         // 各スレッドの観測結果

std::atomic<long> go{0};            // イテレーション開始の合図
std::atomic<int>  done{0};          // 両スレッドの完了カウント

constexpr long ITER = 1'000'000;

void thread1() {
    for (long k = 1; k <= ITER; ++k) {
        while (go.load(memory_order_acquire) < k) {}  // スタートを待つ
        // ---- テスト本体(たった2行)----
        x.store(1, memory_order_relaxed);
        r1 = y.load(memory_order_relaxed);
        // --------------------------------
        done.fetch_add(1, std::memory_order_acq_rel);
    }
}

void thread2() {
    for (long k = 1; k <= ITER; ++k) {
        while (go.load(memory_order_acquire) < k) {}
        // ---- テスト本体 ----
        y.store(1, memory_order_relaxed);
        r2 = x.load(memory_order_relaxed);
        // --------------------
        done.fetch_add(1, std::memory_order_acq_rel);
    }
}

int main() {
    std::thread t1(thread1), t2(thread2);
    long both_zero = 0;

    for (long k = 1; k <= ITER; ++k) {
        x.store(0, memory_order_relaxed);             // 初期化
        y.store(0, memory_order_relaxed);
        go.store(k, memory_order_release);            // 位置について、どん!
        while (done.load(memory_order_acquire) < 2 * k) {}  // 両者の完了を待つ
        if (r1 == 0 && r2 == 0) {
            ++both_zero;
        }
    }
    t1.join(); t2.join();
    std::printf("(r1,r2)=(0,0) が %ld / %ld 回観測されました\n", both_zero, ITER);
}
```

コードについて2点、先に釈明しておきます。

**なぜ`std::atomic`+`relaxed`を使うのか。** 第1章で学んだとおり、素の`int`を2スレッドで読み書きするとデータ競合=未定義動作になり、コンパイラに何をされても文句が言えません(1.2節のループ畳み込みの悪夢を思い出してください)。`memory_order_relaxed`のアトミック操作は、**未定義動作を回避しつつ、順序については何も要求しない**という、この実験にうってつけの設定です。第7章で正式に学びますが、relaxedのload/storeは両アーキテクチャとも素の`mov`/`ldr`/`str`にコンパイルされます。つまりハードウェアに対しては第1章の裸のコードと同じ姿で届き、ハードウェアの生の挙動が観測できるのです。

**`go`/`done`の同期部分にはacquire/releaseを使っています。** これは「テストの計測装置」であり、テスト対象ではありません。計測装置まで壊れていては実験になりません(acquire/releaseの意味は第7章で学びますが、ここでは「正しく動く柵」だと思ってください)。

では実行します。まずx64で。

```console
$ g++ -std=c++20 -O2 -pthread sb.cpp -o sb
$ ./sb
(r1,r2)=(0,0) が 32458 / 1000000 回観測されました
$ ./sb
(r1,r2)=(0,0) が 29817 / 1000000 回観測されました
```

**「ありえない」はずの(0,0)が、100万回中3万回。** 3%です。珍しい現象を苦労して捕まえるどころか、うんざりするほど頻発しています。ARM(Apple M2)でも実行します。

```console
$ clang++ -std=c++20 -O2 sb.cpp -o sb
$ ./sb
(r1,r2)=(0,0) が 74102 / 1000000 回観測されました
```

ARMでも出ます。むしろ多い。まずこの事実を記録します。

> **観測事実4**: SBテストの(0,0)――どのインターリーブでも説明できない結果――は、x64でもARMでも高頻度で観測される。

「コンパイラが並べ替えたのでは?」と疑った方、良い疑いです。確かめましょう。テスト本体部分の逆アセンブルです。

```asm
; x64 (GCC 13, -O2) thread1 のテスト本体
mov    DWORD PTR x[rip], 1        ; x = 1     ← ソースの順序どおり
mov    eax, DWORD PTR y[rip]      ; r1 = y    ← ソースの順序どおり
```

```asm
; AArch64 (Clang 15, -O2) thread1 のテスト本体
mov    w9, #1
str    w9, [x8]                   ; x = 1     ← ソースの順序どおり
ldr    w10, [x11]                 ; r1 = y    ← ソースの順序どおり
```

機械語のレベルでも、ストアが先、ロードが後。**コンパイラは並べ替えていません。** 命令列は正しい順序でCPUに渡され、それでも(0,0)が出る。つまり犯人は**CPUそのもの**です。ストアとロードが、プログラム順とは逆に「見える」順序で実行されている――各スレッドのストアがロードを**追い越されている**のです。この並べ替えを **Store→Loadリオーダリング** と呼びます(「Storeの後のLoadが、Storeを追い越して先に完了する」の意)。

なぜCPUがそんなことをするのか、その物理的なからくり(ストアバッファ)は第3章で解剖します。この章では観測に徹しましょう。次のテストが本章の山場です。

## 2.2 【コード】Message Passingパターン ― x64では壊れないがARMでは壊れるコード

2つめのテストは **MP(Message Passing)** です。これはリトマステストの中でも特別な存在で、実務のコードに**そのままの形で**現れます。「データを用意してから、完了フラグを立てる」――誰もが一度は書くパターンです。

```text
初期状態: data = 0, ready = 0

スレッド1(送信側):        スレッド2(受信側):
  data = 42;                  while (ready == 0) {}   // フラグを待つ
  ready = 1;                  r = data;

問い: r == 0 (フラグは立っているのにデータが空) はありうるか?
```

直感的には、`ready == 1`を見た時点で`data = 42`は完了済みのはずです。書いた順に見えるなら、`r`は必ず42。

**リスト2-2: mp.cpp ― Message Passingテスト(ハーネスはリスト2-1と共通構造)**

```cpp
#include <atomic>
#include <cstdio>
#include <thread>

using std::memory_order_relaxed;
using std::memory_order_acquire;
using std::memory_order_release;

std::atomic<int> data_{0}, ready{0};
int r;

std::atomic<long> go{0};
std::atomic<int>  done{0};
constexpr long ITER = 1'000'000;

void sender() {
    for (long k = 1; k <= ITER; ++k) {
        while (go.load(memory_order_acquire) < k) {}
        // ---- テスト本体 ----
        data_.store(42, memory_order_relaxed);
        ready.store(1,  memory_order_relaxed);
        // --------------------
        done.fetch_add(1, std::memory_order_acq_rel);
    }
}

void receiver() {
    for (long k = 1; k <= ITER; ++k) {
        while (go.load(memory_order_acquire) < k) {}
        // ---- テスト本体 ----
        while (ready.load(memory_order_relaxed) == 0) {}  // フラグ待ち
        r = data_.load(memory_order_relaxed);
        // --------------------
        done.fetch_add(1, std::memory_order_acq_rel);
    }
}

int main() {
    std::thread t1(sender), t2(receiver);
    long broken = 0;

    for (long k = 1; k <= ITER; ++k) {
        data_.store(0, memory_order_relaxed);
        ready.store(0, memory_order_relaxed);
        go.store(k, memory_order_release);
        while (done.load(memory_order_acquire) < 2 * k) {}
        if (r != 42) {
            ++broken;
        }
    }
    t1.join(); t2.join();
    std::printf("r != 42 が %ld / %ld 回観測されました\n", broken, ITER);
}
```

まずx64で実行します。

```console
$ g++ -std=c++20 -O2 -pthread mp.cpp -o mp
$ ./mp
r != 42 が 0 / 1000000 回観測されました
$ ./mp
r != 42 が 0 / 1000000 回観測されました
```

100万回まわして0回。筆者は累計10億回以上まわしましたが、x64でこのテストが壊れたことは**一度もありません**。SBではあれほど簡単に壊れたx64が、MPでは鉄壁です。

同じバイナリロジックをARMに持っていきます。

```console
$ clang++ -std=c++20 -O2 mp.cpp -o mp
$ ./mp
r != 42 が 217 / 1000000 回観測されました
$ ./mp
r != 42 が 189 / 1000000 回観測されました
```

**壊れました。** 100万回中200回前後、「フラグは立っているのにデータが空」が観測されます。頻度はSBよりずっと低いものの、確実に起きています(頻度はコアの組み合わせに強く依存します。Apple Siliconなら高効率コアと高性能コアをまたぐ配置、Linuxなら`taskset`で異なるクラスタのコアに縛ると出やすくなります)。

念のため、ここでもコンパイラのアリバイを確認します。sender側テスト本体の逆アセンブルです。

```asm
; AArch64 (Clang 15, -O2) sender のテスト本体
mov    w9, #42
str    w9, [x8]        ; data_ = 42   ← ソース順どおり
mov    w9, #1
str    w9, [x10]       ; ready = 1    ← ソース順どおり
```

命令はソース順どおり。receiver側も`ldr`(ready) → `ldr`(data)の順で並んでいます。それでも壊れる。つまりARMのCPUは、**2つのストアを書いた順と逆に他コアへ見せる**(Store→Storeリオーダリング)、あるいは**2つのロードを逆順に実行する**(Load→Loadリオーダリング)、少なくともどちらかをやっているのです。どちらの犯行かをこのテストだけで切り分けることはできませんが、第3章のバリア実験で片側ずつ柵を立てて特定します。

> **観測事実5**: MPテスト(書いてからフラグを立てる)は、x64では10億回まわしても壊れないが、ARMでは100万回に数百回壊れる。

この観測事実5を、少し立ち止まって噛みしめてください。これは本書でもっとも実務に直結する実験結果です。「データを用意してからフラグを立てる」コードをrelaxed(あるいは第1章のような裸の変数)で書いてしまったとき――**x64ではテストも本番も含めて一度も壊れないまま、何年でも動き続けます**。そのコードをARMサーバーに移した日から、1万リクエストに数回、説明のつかない壊れたデータが混ざり始めるのです。第10.7節のケーススタディ「Graviton移行で落ちるようになったバグ」は、まさにこの現象の実物です。

## 2.3 x64で唯一観測できた並べ替えは「Store→Load」だけだった ― TSOという仮説の提示

2つの実験結果を並べます。

| テスト | 検出できる並べ替え | x64 | ARM |
|---|---|---|---|
| SB(2.1節) | **Store→Load**(ストアを後続ロードが追い越す) | **観測された**(〜3%) | 観測された(〜7%) |
| MP(2.2節) | **Store→Store** または **Load→Load** | **観測されない**(0/10億) | 観測された(〜0.02%) |

x64の結果には、はっきりした非対称があります。Store→Loadの並べ替えは日常茶飯事なのに、MPが要求する種類の並べ替えは頑として起こさない。メモリアクセスの並べ替えは、前後の命令の種類で分類すると全部で4種類あります。ここまでの実験と、まだやっていない実験を整理するとこうなります。

| # | 並べ替えの種類 | 検出するリトマステスト | x64での観測 |
|---|---|---|---|
| 1 | Load → Load | MP(受信側) | されない |
| 2 | Load → Store | LB(Load Buffering・章末演習1) | されない |
| 3 | Store → Store | MP(送信側) | されない |
| 4 | **Store → Load** | **SB** | **される** |

ここから、次の仮説が立てられます。

> **仮説(この時点では仮説)**: x64は、4種類の並べ替えのうち**Store→Loadだけを許し、残り3つを禁止する**規則で動いているのではないか。

実は、この規則には名前があります。**TSO(Total Store Order)** ――x86-64アーキテクチャが公式に保証するメモリモデルです。「なぜよりによってStore→Loadだけが特別扱いなのか」には、ストアバッファという明快な物理的理由があります。それを解剖し、この仮説を「x64のすべての挙動を予測できるモデル」に鍛え上げるのが第3章です(章末演習1のLBテストで、表の2行目を自分の手で埋めてから進むことを勧めます)。

一方ARMは、SBもMPも壊しました。第3章で確認しますが、ARMは**4種類すべての並べ替えを許す**「弱い」メモリモデルを採用しています。x64開発機で並行コードの正しさを「テストが通ったから」で判断することが、いかにTSOという安全網に**ただ乗り**した行為か――この表がその最初の証拠です。

## 2.4 【コード】コンパイラリオーダリングだけを切り出す実験(単一スレッド+シグナルハンドラ)

ここまでの2つの実験では、逆アセンブルで「コンパイラは並べ替えていない」ことを確認してから、CPUを犯人と断定しました。しかし第1.2節で見たとおり、コンパイラにも並べ替え・削除の権利があります。つまり本書の敵は**二段構え**です。

```
C++ソース ──(コンパイラの並べ替え)──> 機械語 ──(CPUの並べ替え)──> 実際の実行
```

この節では、CPUの並べ替えが**原理的に起こりえない状況**を作って、コンパイラ単独の犯行を現行犯逮捕します。使うのはスレッド1本とシグナルハンドラです。シグナルハンドラは「同じスレッドの実行を任意の命令間で中断して割り込む」ため並行性の風味を持ちますが、実行するコアは1つ。**コアは自分自身のストアを必ずプログラム順(正確には機械語順)で観測する**ので、機械語レベルの順序異常はすべてコンパイラの仕業だと断定できるのです。

**リスト2-3: hoist.cpp ― コンパイラに「消される」ループ**

```cpp
#include <csignal>
#include <cstdio>

int stop = 0;                       // わざと普通のint(volatileでもatomicでもない)

void handler(int) {
    stop = 1;                       // Ctrl+C でフラグを立てる
}

int main() {
    std::signal(SIGINT, handler);
    std::puts("Ctrl+C で止めてください...");
    long spins = 0;
    while (stop == 0) {             // フラグが立つまで待つ……つもり
        ++spins;
    }
    std::printf("止まりました spins=%ld\n", spins);
}
```

`-O0`でビルドすると、期待どおりに動きます。

```console
$ g++ -std=c++20 -O0 hoist.cpp -o hoist_O0
$ ./hoist_O0
Ctrl+C で止めてください...
^C止まりました spins=48291042
```

`-O2`でビルドすると――

```console
$ g++ -std=c++20 -O2 hoist.cpp -o hoist_O2
$ ./hoist_O2
Ctrl+C で止めてください...
^C^C^C^C（何度押しても止まらない。kill -9 するしかない）
```

**永遠に止まりません。** シグナルハンドラは呼ばれ、`stop`には1が書き込まれているのに、ループは終わらない。逆アセンブルすると理由は一目瞭然です。

```asm
; hoist_O2 の main のループ部分
.L3:
    jmp    .L3        ; 無限ループ。stopのロードが存在しない!
```

コンパイラの推論はこうです。「ループ本体は`stop`を変更しない。この関数内に`stop`を変更するコードはほかにない。データ競合のないプログラムなら他スレッドが黙って変えることもない(変えたらそれは未定義動作なので考慮不要)。ゆえに`stop`のロードはループの外に1回だけ吊り上げ(hoist)てよい。初回が0なら永遠に0だ」――そして条件判定ごと消去しました。第1.2節のループ畳み込みと同じ「as-ifルール」の帰結です。

これはメモリアクセスの**削除**でしたが、**並べ替え**も同様に起こります。こちらは実行するまでもなく、アセンブリを見るだけで確認できます。

**リスト2-4: reorder.cpp ― コンパイラによるストアの並べ替え(Compiler Explorerで観察)**

```cpp
int a, b;

void writer(int v) {
    a = v * 3 + 1;      // ① 計算してaに格納
    b = 1;              // ② フラグを立てる……つもり
}
```

```asm
; GCC 13 -O2 (x64) の出力
writer(int):
    mov    DWORD PTR b[rip], 1      ; ② が先!
    lea    eax, [rdi+1+rdi*2]
    mov    DWORD PTR a[rip], eax    ; ① が後!
    ret
```

ソースでは①→②なのに、機械語では②→①。単一スレッドの世界では`a`と`b`に依存関係がないため、コンパイラは命令スケジューリングの都合で自由に入れ替えます。もしこの`b`をMPパターンの`ready`フラグとして使っていたら――**CPUが1命令も並べ替えなくても**、MPは壊れます。2.2節でx64のMPが壊れなかったのは、`std::atomic`(relaxed)を使ったことでコンパイラがこの種の入れ替えを(実務上)しなかったからでもあるのです。

> **観測事実6**: コンパイラは、CPUと独立に、メモリアクセスの削除(リスト2-3)と並べ替え(リスト2-4)を行う。単一コアですら「書いた順に起きる」保証はソースコードには存在しない。

まとめると、第7章で学ぶC++のメモリオーダー指定は、この**二段構えの敵を1つの指定で同時に黙らせる**仕組みです。`memory_order_release`と書けば、コンパイラは並べ替えを自粛し、かつ必要なアーキテクチャ(ARM)では`stlr`のような順序保証付き命令を発行し、不要なアーキテクチャ(x64、TSOのおかげ)では素の`mov`のままにする――ソース1箇所の指定が、コンパイラとCPUの両方への契約になっているのです。

## 2.5 実験結果整理シート ― x64で観測できたこと/ARMでしか観測できなかったこと

この章の全戦果を1枚にまとめます。第3章以降、この表に何度も戻ってきます。

**表2-1: 第2章の観測結果一覧(筆者環境での代表値)**

| 実験 | 現象 | x64 (Core i7) | ARM (Apple M2) | 犯人 |
|---|---|---|---|---|
| SB(リスト2-1) | Store→Load並べ替え | **観測** 〜3% | **観測** 〜7% | CPU |
| MP(リスト2-2) | Store→Store / Load→Load並べ替え | 観測されず(0/10⁹) | **観測** 〜0.02% | CPU |
| LB(章末演習1) | Load→Store並べ替え | 観測されず | (演習で確認せよ) | CPU |
| ロード吊り上げ(リスト2-3) | ループからのロード削除 | **観測**(両者共通) | **観測**(両者共通) | コンパイラ |
| ストア入れ替え(リスト2-4) | 独立ストアの並べ替え | **観測**(両者共通) | **観測**(両者共通) | コンパイラ |

読み取るべきことは3つです。

**第一に、コンパイラの並べ替えはアーキテクチャを選びません。** 表の下2行はx64でもARMでも同じように起こります。コンパイラはC++の抽象機械に対して最適化しているのであって、ターゲットCPUのメモリモデルの強さに応じて自粛したりはしないからです。

**第二に、CPUの並べ替えには明確なアーキテクチャ差があります。** x64が起こすのはStore→Loadただ1種類。ARMは(少なくとも)SBとMPの両方を壊しました。この非対称こそが「x64で動いた=正しい」を成立させない根本原因です。

**第三に、頻度の低さは安全を意味しません。** ARMのMP破れは0.02%でした。1秒に1万回実行されるコードパスなら、毎秒2回壊れる計算です。逆に、テストハーネスの回し方が悪ければ100万回で0回のこともあります(「1億回に1回」を1分で再現させる技法は第11.5節で扱います)。

最後に、この章で**まだ観測していないもの**を正直に挙げておきます。Load Bufferingテスト(演習1)、依存関係があるときの挙動(アドレス依存・制御依存)、そして3コア以上が絡むIRIWテスト。IRIWは「そもそもストアに全員が合意する単一の順序はあるのか」というTSOの核心を突くテストで、第3.6.3節で登場します。

### 第2章のまとめ

- **観測事実4**: SBテストの「両方0」はx64でもARMでも高頻度で起こる。犯人はコンパイラではなくCPU(Store→Loadリオーダリング)。
- **観測事実5**: MPテスト(データを書いてからフラグを立てる)はx64では決して壊れず、ARMでは壊れる。実務コードに直結する最重要の非対称。
- **仮説**: x64は4種類の並べ替えのうちStore→Loadだけを許すのではないか。この規則の名はTSO。検証は第3章で。
- **観測事実6**: コンパイラは単一コアでもメモリアクセスを削除・並べ替える。敵は「コンパイラ+CPU」の二段構え。
- リトマステストのハーネス(go/doneによる開始同期+relaxedのテスト本体+逆アセンブルでのアリバイ確認)は、本書全体で使い回す基本装備。

### 章末演習

1. **LB(Load Buffering)テストを実装せよ。** スレッド1: `r1 = y; x = 1;`、スレッド2: `r2 = x; y = 1;`。問いは「(r1,r2)=(1,1)はありうるか」。x64とARMの両方で100万回×10セットまわし、表2-1の3行目を自分のデータで埋めよ(注意: 現代のAArch64実装ではLBの観測は難しい場合がある。観測されない≠禁止されている、である点も含めて考察せよ)。
2. リスト2-1のSBテストで、2つのストアを`memory_order_seq_cst`に変更して再実行し、(0,0)が消えることを確認せよ。さらに実行時間を計測し、relaxed版と比較せよ。x64とARMで「正しさの値段」がどう違うか。
3. リスト2-2のMPテストをLinuxのARMマシンで`taskset -c 0,1`(同一クラスタ)と`taskset -c 0,4`(クラスタまたぎ、コア番号は環境に合わせよ)で実行し、破れの頻度がどう変わるか計測せよ。
4. リスト2-3を`volatile int stop`に変えて`-O2`でビルドし、(a) 止まるようになること、(b) しかし第1.4節で学んだとおりこれはスレッド間同期の正解ではないこと、を確認せよ。`std::atomic<int>`(relaxed)版とアセンブリを比較し、この特定のケースでは両者がほぼ同じコードになる理由を説明せよ。
5. リスト2-4をClangとGCC、最適化レベル-O1/-O2/-O3で比較し、ストアの並べ替えが起こる条件を調査せよ。並べ替えを防ぐ標準的な手段を第7章を先読みして試してもよい(`std::atomic_signal_fence`がこの用途の専用道具である)。
