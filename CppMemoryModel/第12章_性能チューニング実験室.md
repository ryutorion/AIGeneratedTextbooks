# 第12章 性能チューニング実験室

第11章で検証の体系が完成しました。この最終実験章のテーマは、その体系の上でだけ安全に行える営み――**速さの追求**です。

順番が重要です。本書が性能の章を最後に置いたのは、体裁ではありません。並行コードの高速化とは、多くの場合「保証を削る」ことです(seq_cstを緩める、ロックを外す、共有をやめる)。保証を削る作業を、削った結果を検証する装置なしに行うのは、命綱を外してから壁を登るのと同じです。逆に、装置が揃った今なら大胆になれます。この章の構成は、料金表の作成(12.1節)、診断器の習得(12.2節)、最強の処方の実装(12.3節)、削る作業の規律化(12.4節)、そして全部品を統合する最終演習(12.5節)です。

もうひとつ、この章の合言葉を先に。第6.1節の表6-1が予告していたとおり、**並行性能の最大の敵はオーダーでもロックでもなく、競合そのもの**です。オーダー緩和で2倍を拾う前に、競合除去で10倍を拾う――優先順位を、まず実測で確定させましょう。

## 12.1 【コード】アトミック操作の料金表 ― x64 vs Apple Silicon vs Graviton

チューニングの第一歩は、憶測の排除です。「atomicは重い」「seq_cstは遅い」「ARMは安い」――どれも半分だけ正しい標語を、数字に置き換えます。本書の計測ハーネス(第2章流+第11.5節の作法:コア固定、ウォームアップ、外れ値処理、種の記録)で、基本操作の1回あたりコストを3台で測りました。**非競合**(1スレッド、ラインは手元のキャッシュに常駐)と**競合**(8スレッドが同一ラインを叩く)の2域です。

**表12-1: アトミック操作の料金表(ns/op、筆者環境の代表値)**

| 操作 | x64 非競合 | x64 競合 | M2 非競合 | M2 競合 | Graviton3 非競合 | Graviton3 競合 |
|---|---|---|---|---|---|---|
| 素のload/store | 0.9 | ― | 0.7 | ― | 1.0 | ― |
| load(relaxed)/store(relaxed) | 0.9 | 44 | 0.7 | 46 | 1.0 | 52 |
| load(acquire)/store(release) | 0.9 | 44 | 1.1 | 47 | 1.4 | 53 |
| store(seq_cst) | 4.6 | 48 | 1.9 | 49 | 2.3 | 55 |
| fetch_add(relaxed) | 5.5 | 42 | 2.6 | 45 | 3.1 | 94※ |
| fetch_add(seq_cst) | 5.5 | 42 | 7.1 | 49 | 7.8 | 96※ |
| CAS(成功) | 5.8 | 45 | 3.0 | 47 | 3.4 | 98※ |
| mutex lock+unlock | 15.8 | 96 | 17.2 | 122 | 18.9 | 131 |

(※GravitonのLL/SC版ビルド。LSE版は競合域で約半減――第8.5節の2.3倍の再確認)

この表の読み方を3段で。

**第一に、非競合の列は第8章の対応表の写像です。** x64は「素≈relaxed≈acquire/release」(全部mov)で、seq_cstストア(xchg)とRMW(lock)だけ段差がある。M2/Gravitonは「relaxed < 順序付き(ldar/stlr) < seq_cst < RMW」と、契約の強さに沿った素直な値付け。オーダー選択の性能検証がARMでしか成立しない(観測事実22)ことが、料金表の形そのものに現れています。

**第二に、そして決定的に――競合の列では、行の差がほぼ消えます。** relaxedもseq_cstもmutexすら、40〜130nsの同じ桁に押し込まれる。理由は第4章で学習済みです:競合域のコストの主成分は演算でもバリアでもなく、**キャッシュラインの輸送(RFO往復)**だから。ラインが8コアの間を引きずり回される数十nsの前では、バリアの数ns差はノイズです。ここから、この章全体の優先順位が確定します。

> **観測事実41**: コスト階層は「素≈relaxed(≈1ns)< 順序付き < RMW(数ns)≪ **競合した何か**(数十〜百ns)」。競合の代金は非競合のオーダー代金の10倍級であり、競合下ではオーダー間の価格差がノイズに沈む。**チューニングの第一手は競合の除去(12.2〜12.3節)、オーダー緩和(12.4節)はその後**である。

**第三に、脇の実測もひとつ。** 競合コストは「誰と競合するか」でも変わります。コア間レイテンシを総当たりで測ると、M2ではPコア同士が約40ns、PコアとEコアをまたぐと約100nsと、2.5倍の差がありました(Gravitonでもソケット内の距離で同様の勾配)。第11.5節S2の「敵対的コア配置」が感度を稼げた物理的裏付けであり、逆にチューニング側では「**通信の多いスレッド対は近くに置く**」というアフィニティ設計の根拠になります。

## 12.2 【コード】perf c2cハンズオン ― ライン競合の犯人を指名手配する

競合が主敵と決まれば、次は**どのラインで誰が競合しているか**を突き止める診断器です。第4章では「性能が変だ→alignasしてみる→直った」という試行錯誤で済ませましたが、実務の巨大なコードベースでは犯人の当たりすらつきません。Linuxの`perf c2c`(cache-to-cache)は、この捜査を機械化します。原理は、CPUのサンプリング機構(IntelのPEBS、ARMではNeoverse系のSPE)でメモリアクセスの実アドレスとレイテンシを採取し、**HITM**――「他コアのModified状態のラインにヒットした」イベント、つまりライン奪い合いの現行犯記録――を集計するものです。

被疑者には、第4章のリスト4-2(フォールスシェアリングするカウンタ)に再登場してもらいます。

```console
$ perf c2c record -- ./false_sharing        # 実行しながら採取
$ perf c2c report --stdio
=================================================
     Shared Data Cache Line Table
=================================================
  # ----------- Cacheline ----------   Tot  ----- LLC Load Hitm -----
  #        Address   Node  PA cnt     Hitm    Total    Lcl      Rmt
  # ..............  .....  ......  .......  .......  ......  .......
  0  0x5601a3c04140      0    3897   91.2%     8123    8123        0   ← 主犯
  1  0x7f31c82ddf80      0      12    0.4%       31      31        0
```

HITMの91%が単一のライン`0x...140`に集中――主犯の指名手配です。さらにライン内の内訳へ潜ります。

```console
=================================================
   Cacheline 0x5601a3c04140 の内訳
=================================================
  ---- HITM ----  -- Store --   Data address   ---------- Source ----------
     Rmt    Lcl                    Offset          Pid   Code address / line
   .....  .....   ..........   ...........       .....   ....................
    0.0%  27.1%       31.2%          0x0         42137   worker  false_sharing.cpp:14
    0.0%  25.8%       29.9%          0x8         42137   worker  false_sharing.cpp:14
    0.0%  24.0%       28.4%         0x10         42137   worker  false_sharing.cpp:14
    0.0%  23.1%       30.5%         0x18         42137   worker  false_sharing.cpp:14
```

決定的な証拠がここにあります。**同じラインの中の、異なるオフセット(0x0/0x8/0x10/0x18)を、別々のスレッドが叩いている。** これがフォールスシェアリングの指紋です。もしHITMが**同一オフセット**に集中していたら、それは真の共有(全員が同じ変数を叩いている=12.3節の出番)。オフセットの分布ひとつで、処方(alignas か、シャーディングか)が分岐する――診断が機械化されるとはこういうことです。alignas修正版で再採取すると、当該ラインはHITM表から消滅し、捜査完了です。

環境の但し書きを3つ。x64ではIntel(PEBS)が最も充実し、AMDはIBSで概ね可。ARMサーバーではGraviton3以降などSPE搭載のNeoverse系で`perf c2c`が使えます。Apple Silicon上のmacOSにはperfが無く、Instrumentsとカウンタで間接推定するか、この用途はLinux機に持ち込むのが現実的です。また、c2cが使えない環境の「貧者の診断」も控えに:`perf stat -e machine_clears.memory_ordering`(x64。メモリ順序違反による投機やり直しの回数――第4.4節で触れた「x64の順序監視」が実際に働いた回数です)や、cache-missesの偏り、そして最終手段の「alignas二分探索」です。

> **観測事実42**: perf c2cはHITM(他コアの改変済みラインへのヒット)でライン競合の主犯を特定し、ライン内オフセットの分布まで示す。**異なるオフセット=フォールスシェアリング(alignasで治療)、同一オフセット=真の共有(シャーディングで治療)**という分岐まで、証拠から機械的に読める。修正後の再採取でHITM消滅を確認して完了とする。

## 12.3 【コード】シャーディングカウンタ ― 競合を「除去」する側の最強手

表6-1以来の宿題を回収します。8スレッドが1本のカウンタをfetch_addすると8倍遅くなり、それは**真の共有**なのでalignasでは直らない(観測事実16)。処方は発想の転換です:**全員で1個を数えるのをやめ、各自が自分の帳簿に付け、読むときだけ合算する。**

**リスト12-1: sharded.cpp ― シャーディングカウンタ**

```cpp
class ShardedCounter {
    static constexpr int MAX = 64;
    struct alignas(std::hardware_destructive_interference_size) Slot {
        std::atomic<long> v{0};
    };
    Slot slots[MAX];                                  // 1人1ライン(第4章の教え)
    std::atomic<int> nthreads{0};

    static int my_slot(ShardedCounter* self) {        // スレッドに帳簿を1冊割り当てる
        thread_local int idx = self->nthreads.fetch_add(1, std::memory_order_relaxed);
        return idx;                                   // (本実装は簡略版。演習1で堅牢化)
    }
public:
    void add(long d) {                                // ホットパス
        slots[my_slot(this)].v.fetch_add(d, std::memory_order_relaxed);
    }
    long read() const {                               // コールドパス
        long sum = 0;
        for (auto& s : slots) sum += s.v.load(std::memory_order_relaxed);
        return sum;
    }
};
```

正しさの根拠は、すべて既習の部品です。各スロットは**単一書き手**――SPSCの自己インデックス(第10.1節①⑥)と同じ構図で、書き手にとっては変更順序のコヒーレンスだけで閉じ、relaxedが完全に正当。しかも書き手同士は**別ライン**なので、addは非競合のfetch_add、つまり表12-1の左側の世界(2〜5ns)に戻れます。計測:

```console
# 8スレッド、add 1回あたり
共有fetch_add(表6-1再掲)  : 42 ns/op
ShardedCounter             : 2.5 ns/op        # 17倍
```

競合下の42nsが、非競合の2.5nsへ。オーダーをいくら緩めても届かなかった1桁改善が、**共有の設計的除去**では一撃です(観測事実41の実証です)。

無料ではありません。支払った代償を正確に記帳しておきます。**第一に、読みのコスト**がO(スレッド数)になりました(64スロット合算で約80ns)。書き多・読み稀の統計カウンタでは理想の交換ですが、読み頻度が高い用途では逆転します。**第二に、意味論の弱化。** read()の合計は「ある一瞬の値」では**ありません**――スロットを順に読む間にも他スレッドは加算を続けるので、合計はどの時点のスナップショットとも一致しない「揺らぎ込みの近似値」です(単調増加カウンタなら「読み開始時以上・読み終了時以下」という挟み込みは言えます)。厳密な一時点値が要る局面――終了時の総数など――では、第7.4節で学んだとおり**joinのロープ**が全帳簿を確定させてくれるので、静止後のread()は厳密値になります。**第三にメモリ**:64スロット×128Bで8KB。カウンタ1本には贅沢ですが、42ns/opの継続支出と比べれば安い買い物です。

この「**局所に書き、まれに集計**」は、カウンタに限らない万能形です。スレッドローカルの統計をエクスポート時に合算する監視ライブラリ、コアごとのマガジンを持つメモリアロケータ、スレッドごとのfree-list、JavaのLongAdder――正体はすべてこの1パターンです。perf c2cの報告書で「同一オフセットのHITM」を見たら、まずこの型に変換できないかを考える。それが12.2節と本節を接続する実務の反射神経です。

> **観測事実43**: シャーディングは競合そのものを設計から除去し、8スレッドで17倍(42ns→2.5ns)。対価は読みのO(N)化と「合計は一時点値ではない」という意味論の弱化(静止後はjoinのロープで厳密化できる)。「局所に書き、まれに集計」は並行性能設計の万能形である。

## 12.4 【コード】seq_cstだらけのコードを段階的に緩和する ― 規律あるリファクタリング演習

競合除去(大鉈)を振るい終えたら、最後にオーダー緩和(彫刻刀)の出番です。ただしこの作業は、第7章の知識を持つ者が**規律なしに**やると最悪の結果を生みます――「速そうだからrelaxed」は、x64のCIを全通過してARM本番で爆発する時限装置の製造工程だからです(第7.8節)。この節は、緩和を**工程として**定義します。

題材は、意図的に「全部seq_cst」で書かれた60行の小さなジョブシステムです(リポジトリのstage0/を参照)。ジョブ投入キュー(有界)、処理済みカウンタ、シャットダウンフラグ、そして「全ワーカー停止を確認してから統計を確定する」終了処理を持ち、アトミック操作は9箇所。すべてデフォルト(seq_cst)。**これは恥ずかしい初期状態ではなく、正しい初期状態です**――第7.3節の手順(3)「迷ったらseq_cstに置いてから、証明できた箇所だけ緩める」の出発点です。工程は5段です。

**工程1: 検証の足場を先に組む。** 緩和前に、(a) 不変条件を列挙してアサート化(投入数=処理数+残数、二重処理なし、シャットダウン後の投入拒否)、(b) Relacy移植(最小宇宙:ワーカー2、ジョブ3)で全探索パス、(c) TSanベースライン(ペイロードは素の構造体で!)、(d) ARM(M2)でのベンチマーク基準値。**x64のベンチはこの工程では取りません**――観測事実22・25により、緩和の性能検証はARMでしか意味を持たないからです。

**工程2: 9箇所を構図で分類する。** 表7-1を判定基準に、全アトミック操作に構図のラベルを貼ります。この分類が緩和の全根拠になるので、コードコメントとして残します(後述の台帳)。

**工程3: 台帳を付けながら、1グループずつ緩める。** 本書がこの工程で最重要と考える規律が「**オーダー台帳**」です。デフォルト(seq_cst)以外のオーダーを書く全箇所に、**相方と根拠を名指しするコメント**を義務付けます:

```cpp
job_slot[i] = j;                                   // ペイロード書き込み
seq.store(pos + 1, std::memory_order_release);     // REL: consume()のACQ(L58)と対。
                                                   //      slot[i]の内容を封して公開(MP往路)
...
done.fetch_add(1, std::memory_order_relaxed);      // RLX: 統計カウンタ。可視性は
                                                   //      join後の集計(L102)のロープが担保
```

release/acquireは**対**でしか意味を持たない(表5-2)のに、コード上は物理的に離れた2行です。台帳は、その見えない対を可視化し、片方だけの変更(第7章演習6の「片側だけの誠意」)をレビューで検挙可能にします。緩和は1グループ(1本のロープ、または1つのカウンタ)ずつ行い、**各段階で工程1の足場を全部通します**:Relacy全探索→TSan→ARMストレス(第11.5節のS3構成)→ベンチ差分。

**工程4: 緩められない箇所を、緩めない。** この題材には、意図的に1箇所、SB型が仕込んであります――アイドルワーカーの「仕事が無いことを確認してから寝る」と、投入側の「投入してから寝ている者を起こすか確認する」。双方が「書いてから相手の場所を読む」、第9.2節・第10.6節で学んだあの構図です。ここをacquire/releaseに緩めた変種は、Relacyが即座に反例(投入されたのに誰も起きない=lost wakeup)を出します。**seq_cstが残ることは緩和の失敗ではなく、構図の証明の成功です。** 台帳には「SC: 投入側L33とSB対。緩和不可(Relacy反例 #4471)」と、緩められない理由まで記帳します。

**工程5: 損益分岐で止める。** 全段階の結果です:

**表12-2: 緩和の各段階(M2、スループット。x64は参考)**

| 段階 | 緩めた箇所 | M2 | x64 | 判定 |
|---|---|---|---|---|
| S0 | 全seq_cst(基準) | 100% | 100% | ― |
| S1 | 統計カウンタ2箇所→relaxed | 119% | 101% | 採用 |
| S2 | キュー授受の対→release/acquire | 134% | 106% | 採用 |
| S3 | 停止フラグ→relaxed | 134.5% | 106% | **不採用**(利得<ノイズ) |
| S4 | 就寝ハンドシェイク→acq/rel | ―(Relacy反例) | ― | **却下** |

M2で+34%、うち8割はホットパスの2グループ(S1+S2)で獲得。S3のような**冷たい経路は、正しくてもseq_cstのまま残すのが正解**です――利得ゼロの緩和は、可読性と将来のレビューコストだけを支払う取引だからです。x64の+6%がseq_cstストア削減分だけなのも、表12-1どおり。

> **観測事実44**: 段階的緩和の工程は「足場(不変条件+Relacy+TSan+ARM基準値)→構図分類→**台帳**(全オーダーに相方と根拠を記帳)→1グループずつ緩めて毎回全検証→損益分岐で停止」。実測ではホット2グループが利得の8割(M2で+34%、x64は+6%)。緩められないseq_cst(SB型)の発見と記帳は、緩和と同格の成果である。

## 12.5 最終演習:MPMCキュー ― 全部品の統合

卒業制作です。多生産者・多消費者(MPMC)の有界キュー――スレッドプール、パイプライン、あらゆる並行システムの心臓部――を、実装・検証・3機ベンチマークまで通しで行います。採用アルゴリズムはVyukovの有界MPMCキュー。本書の全部品が1つの設計に合流する、最良の教材だからです。

**リスト12-2: mpmc.cpp ― Vyukov型有界MPMCキュー**

```cpp
template <class T, size_t N>                          // Nは2の冪
class MpmcQueue {
    struct Cell {
        std::atomic<size_t> seq;                      // このマスの「順番札」
        T data;                                       // ペイロード(素のT!)
    };
    alignas(std::hardware_destructive_interference_size) Cell cells[N];
    alignas(std::hardware_destructive_interference_size) std::atomic<size_t> enq{0};
    alignas(std::hardware_destructive_interference_size) std::atomic<size_t> deq{0};

public:
    MpmcQueue() { for (size_t i = 0; i < N; ++i) cells[i].seq.store(i, std::memory_order_relaxed); }

    bool push(const T& v) {
        size_t pos = enq.load(std::memory_order_relaxed);
        for (;;) {
            Cell& c = cells[pos & (N - 1)];
            size_t s = c.seq.load(std::memory_order_acquire);          // (A) マスの札を確認
            intptr_t d = (intptr_t)s - (intptr_t)pos;
            if (d == 0) {                                              // 札==チケット: 空きマス
                if (enq.compare_exchange_weak(pos, pos + 1,
                                              std::memory_order_relaxed)) {  // (B) 席の予約
                    c.data = v;                                        // (C) 荷物を置き
                    c.seq.store(pos + 1, std::memory_order_release);   // (D) 札を進めて公開
                    return true;
                }                                                      // CAS敗北: posに最新値が配達済み
            } else if (d < 0) {
                return false;                                          // 満杯
            } else {
                pos = enq.load(std::memory_order_relaxed);             // 出遅れ: 取り直し
            }
        }
    }
    bool pop(T& v) {                                  // pushと鏡映対称。期待する札は pos+1
        size_t pos = deq.load(std::memory_order_relaxed);
        for (;;) {
            Cell& c = cells[pos & (N - 1)];
            size_t s = c.seq.load(std::memory_order_acquire);
            intptr_t d = (intptr_t)s - (intptr_t)(pos + 1);
            if (d == 0) {
                if (deq.compare_exchange_weak(pos, pos + 1, std::memory_order_relaxed)) {
                    v = c.data;
                    c.seq.store(pos + N, std::memory_order_release);   // 札を1周ぶん進めて返却
                    return true;
                }
            } else if (d < 0) { return false; }        // 空
            else { pos = deq.load(std::memory_order_relaxed); }
        }
    }
};
```

設計を、本書の語彙で読み解きます(これ自体が卒業試験です)。

**マスごとの順番札seqは、チケットロック(第9章演習1)とSPSCの2本のロープ(第10.1節)の融合です。** 札の値は「このマスは今、通番いくつの客のものか」を告げます。空きマスの札はpos、詰まったマスはpos+1、次周で再び空くとpos+N。生産者のロープは (C)→(D) の封と、消費者側(A)の開封――消費者は札pos+1を見て初めてdataを読むので、**MP往路**が各マスに1本ずつ張られます。消費者が読了後に札をpos+Nへ進める行為は**復路**(器の返却)で、次周の生産者の(A)が開封してから(C)で上書きします。SPSCでは全体で2本だったロープが、ここでは**マスごとに対で**張られている――だからこそ複数の生産者・消費者が別々のマスで同時に作業できるのです。

**enq/deqのCAS(B)がrelaxedでよい理由**が、この設計の白眉です。一見、席の予約こそ厳重にすべきに見えます。しかしdataの可視性は上記のとおり**すべてseqのロープが運んでおり**、enq/deqは「次の客の整理券番号」を配るだけの純粋なカウンタ――可視性の責務を負っていません(表7-1の3行目の仕事)。CAS敗北時のexpected配達(第6.2節)が最新番号を無料で届ける点も、Treiber(第10.3節)と同じ文法です。**そしてABAがありません**:CASの対象は単調増加する整数の通番であり、ポインタの再利用という第10.4節の病因が設計ごと存在しない。有界配列ゆえ回収問題(第10.6節)も無縁。ロックフリー2大疾病を、アルゴリズムの選択だけで回避しています(なお厳密にはこのキューはlock-freeでなく、席を予約した(B)のスレッドが(C)(D)の前に眠ると当該マスの後続が待たされる、という進行保証の弱さを持ちます。実務では問題になりにくい弱さですが、台帳に記帳すべき性質です)。

**検証バッテリー**(第11章の表11-2をこの1クラスに適用):TSan――dataが素のTなので検算器が全開で効き、沈黙を確認。Relacy――最小宇宙(N=2、生産者2+消費者2、各2操作)で全探索パス。意地悪検査として(D)をrelaxed化した変種はRelacyが即座に反例(未公開dataの読み)を出し、(A)のrelaxed化も同様。litmus化――seqを介した1マス分の授受骨格をC11リトマスにしてherd7でForbiddenを確認し、回帰資産に。ARMストレス――第11.5節S3構成で夜間相当を実行、破れゼロ。

最後に、perf c2c(12.2節)をこの勝者にかけてみます。HITMの首位は――`enq`と`deq`のライン、**同一オフセット**。つまり真の共有です。マスごとのロープで分散できたのはデータの授受だけで、「整理券の発行機」は依然1台きり。これがこの設計の、そしてあらゆる中央キューの**天井**です。天井を破る道は、もはや実装技巧ではなく設計の転換――スレッド対ごとのSPSCメッシュ、各自が自分のdequeを持ち暇な者が盗みにいくワークスティーリング――すなわち12.3節の万能形「局所に書き、まれに(盗むときだけ)共有する」への回帰です。**最速のMPMCとは、MPMCを不要にする設計である。** 料金表(12.1節)から始まったこの章の結論として、これ以上のものはありません。

> **観測事実45**: Vyukov型MPMCキューは本書の全部品(マスごとのMP往復路、チケット、relaxedカウンタ、CASのexpected配達、ABA/回収の設計的回避、alignas)の合成として読め、検証バッテリー一式を通過し、3機でmutex比約10倍。その天井はenq/deqの真の共有であり、突破口は実装技巧ではなく共有の設計的回避(SPSCメッシュ/ワークスティーリング)にある。

### 第12章のまとめ

- **観測事実41**: 料金表の教え――競合の代金(ライン輸送、数十ns)は非競合のオーダー代金(数ns)の10倍級。競合下ではオーダー差が消える。第一手は競合除去、緩和はその後。
- **観測事実42**: perf c2cはHITMで主犯ラインを特定し、オフセット分布で処方が分岐する(異なるオフセット=alignas、同一=シャーディング)。修正後のHITM消滅確認までが捜査。
- **観測事実43**: シャーディング(局所に書き、まれに集計)は競合を設計から除去し17倍。対価は読みのO(N)と一時点値の放棄。並行性能設計の万能形。
- **観測事実44**: 緩和は工程である――足場→構図分類→オーダー台帳→1グループずつ全検証→損益分岐で停止。ホット2箇所が利得の8割。緩められないseq_cst(SB型)の記帳は成果である。
- **観測事実45**: MPMCキューは全部品の統合として書け、10倍を達成し、その天井(中央カウンタの真の共有)が「共有の設計的回避」という最終原理を指し示す。

これで本書の実験は全て終わりました。第1章で`counter++`が壊れる様を初めて見た読者は、45個の観測事実を経て、いま自分の手でMPMCキューを実装し、契約レベルで検証し、3つのアーキテクチャで値付けできるところまで来ています。締めくくりの第13章では、実験室を出て地平線を眺めます――out-of-thin-air問題という契約の未解決の穴、RISC-V(RVWMO)とCHERIが示すアーキテクチャの未来、そして形式手法によるメモリモデル研究の現在地です。
