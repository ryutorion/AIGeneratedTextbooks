# 第7章 メモリオーダーを一段ずつ緩める

道具(第6章)と契約の語彙(第5章)が揃い、ついに本書の中心に着きました。`std::atomic`の全操作が受け取る最後の引数、**メモリオーダー**です。

この章の方法論を最初に宣言します。メモリオーダーは6段階ありますが、仕様書の強い順に朗読しても輪郭は掴めません。保証の輪郭は**境界の内側と外側の両方から**なぞって初めて見えます。そこで、おなじみのMPテストを実験台に、**seq_cst(最強)で直す→acquire/releaseに緩めてもまだ直っている→relaxedまで緩めて再び壊す**、という往復運動をします。「どこまで緩めても大丈夫か」と「どこから壊れるか」は同じ線の表裏であり、その線を自分の実験データで引くこと――それがこの章の目標です。

もうひとつ、この章はいくつもの伏線を回収します。表6-1の右下の太字(relaxedがM2でだけ2.7倍速い)、第3.6.2節の4変種実験、第5章のDRF-SC定理、そして本書の警句「x64での検証はオーダー選択の検証にならない」。最後の7.8節では、その警句を**実感として植え付ける**ための、意地の悪い実験を用意しました。

---

## 7.1 【コード】MPをseq_cstで直す → ARMでも壊れないことを確認

まず最強から。`memory_order_seq_cst`はすべてのアトミック操作のデフォルトであり、契約が提供する最上位の保証です。条文を要約します。

> **seq_cstの保証**: acquire/releaseの全保証(7.2節)に加えて、**プログラム中の全seq_cst操作を1本に並べた全順序S**が存在し、すべてのスレッドがSと矛盾しない観測をする。

「全操作を1本に並べた順序」――第2章の冒頭で粉砕された、あの素朴なインターリーブの直感そのものです。第5.3節のDRF-SC定理が約束したとおり、競合フリーのプログラムでアトミックをすべてseq_cstにしておけば、6通りのインターリーブを数え上げる高校数学的な推論が**正当な証明手段として復活**します。

実験は簡潔に済みます。リスト2-2のMPテストで、4つのアトミック操作のオーダー指定をすべて削除します(デフォルト=seq_cstになります)。

```cpp
// 送信側                        // 受信側
data_.store(42);                 while (ready.load() == 0) {}
ready.store(1);                  r = data_.load();
```

```console
# ARM (Apple M2)
$ ./mp_seqcst
r != 42 が 0 / 10000000 回観測されました
```

relaxedでは100万回に200回壊れていたARMで、1000万回ゼロ。ついでに第2章の章末演習2で予告したとおり、SBテストもseq_cstにすれば(0,0)は両アーキテクチャで消滅します。**seq_cstはこの章で扱う全パターンを直します。** 直せることに驚きはありません。問題は値段です。逆アセンブルすると、ARMの受信側ループには`ldar`が、送信側には`stlr`が並び、x64の送信側にはあの`xchg`(第3.5.2節の暗黙バリア)が現れています。値札の精算は第8章に譲り、この章では「**seq_cstは常に正しい基準線**」という位置だけ確定させて、緩めに入ります。

> **観測事実20**: 全アトミック操作をseq_cst(デフォルト)にすると、MPもSBも全アーキテクチャで矛盾なく動き、インターリーブの直感(DRF-SC)が復活する。以後の全実験の「正解の基準線」はこれである。

## 7.2 【コード】acquire/releaseに緩めて再実験 → まだ壊れない ― そして「直らないもの」を発見する

一段緩めます。`memory_order_release`(ストア用)と`memory_order_acquire`(ロード用)の対です。条文はもう第5.3節で学んであります――**acquireロードがreleaseストアの書いた値を読んだとき、その対にsynchronizes-with辺が張られる**。加えて、機械側の直感としては**一方通行の膜**のイメージが役立ちます。

```
      (先行する読み書き A, B, C)              (X を読む)
   ────────────────────────────         ready.load(acquire)
   ready.store(1, release)              ─────────────────────────
      ↑ A,B,Cはこの膜を下向きに           ↓ 後続のD,E,Fはこの膜を
        通過できない(閉じ込め)              上向きに通過できない
      ↓ ただし膜より後の操作が               ↑ ただし膜より前の操作が
        上に染み出すのは自由                  下に染み出すのは自由
```

releaseは「**私がこれまでにしたことを全部封をして荷札を付ける**」操作、acquireは「**荷札を確認してから開封する**」操作です。荷札(値)の受け渡しが成立した対にだけ、封の中身(先行する全書き込み、非アトミック含む)の可視性が保証される。MPテストはまさに封と開封の構図なので、直るはずです。第3.6.2節の変種Dで実機確認済みですが、基準線との比較のため再実行しておきます。

```console
# ARM (Apple M2) — release/acquire版MP
r != 42 が 0 / 10000000 回観測されました
```

壊れません。ではacquire/releaseはseq_cstと等価なのでしょうか。**ここからがこの節の本番です。** 同じ緩め方を、もうひとつの古典・SBテストに適用してみます。

**リスト7-1: sb_acqrel.cpp(リスト2-1との差分のみ)**

```cpp
// コア0のテスト本体
x.store(1, std::memory_order_release);
r1 = y.load(std::memory_order_acquire);
// コア1も対称
```

```console
# x64
$ ./sb_acqrel
(r1,r2)=(0,0) が 31207 / 1000000 回観測されました   # 消えない!
# ARM (Apple M2)
$ ./sb_acqrel
(r1,r2)=(0,0) が 68914 / 1000000 回観測されました   # 消えない!
```

**releaseとacquireを最大限まじめに付けたのに、(0,0)は1つも減りません。** x64での逆アセンブルが雄弁です――releaseストアもacquireロードも**素のmov**のままで、relaxed版と1バイトも違わないのです(第8章の対応表の先取りです)。

理屈で言い直します。膜の図をもう一度見てください。releaseストアの膜は「先行操作が**後ろへ**抜けること」を禁じ、acquireロードの膜は「後続操作が**前へ**抜けること」を禁じます。ではSBで問題だった並べ替え――**ストアの後ろのロードが前へ抜ける(Store→Load)**――はどうか。ストアのreleaseの膜は「後続が前に染み出すのは自由」、ロードのacquireの膜は「先行が後ろに染み出すのは自由」。**両方の膜が、この方向の通過を素通しにしています。** さらに契約の側から言えば、synchronizes-with辺は「値の受け渡し」に付随する(表5-2)ところ、SBの(0,0)実行では**どちらのロードも相手のストアの値を読んでいない**――辺の張りようがないのです。

acquire/releaseとseq_cstの差は、まさにここにあります。acquire/releaseは**荷札が渡った2者間**の順序を作る道具であり、**荷札の渡っていない者どうしを含む全員の合意**(全順序S)は作りません。SBパターン――お互いに「私が先に書いたか、あなたが先に書いたか」の**全員合意**を必要とする構図――を正しく書けるのはseq_cstだけです。実務でこの構図が現れる代表が、Dekker/Petersonの相互排他や「両者が相手の不在を確認してから進む」型の重複実行防止で、これらをacquire/releaseで書くのは、この節の実験が示すとおり**両アーキテクチャで壊れる**誤りです。

> **観測事実21**: acquire/releaseはMPを直すがSBは直さない(x64でもARMでも(0,0)は残る)。この対は「値を受け渡した2者間のロープ」を張る道具であり、全員が合意する1本の順序(seq_cstのS)は提供しない。相互排他型・SB型の構図にはseq_cstが必要である。

## 7.3 【コード】relaxedまで緩める → ARMで再び壊れる(壊し戻し実験)

境界線の反対側も踏んでおきます。MPをrelaxedまで緩め戻すと――これは第2章のオリジナル(リスト2-2)そのものです――ARMで再び壊れます。

```console
# ARM (Apple M2) — relaxed版MP(再掲)
r != 42 が 217 / 1000000 回観測されました
```

これで往復が完了し、3段×2パターンの**保証の輪郭**が実験データとして手に入りました。

**表7-1: メモリオーダーの階段と、各パターンの生死(実測)**

| パターン | relaxed | acquire/release | seq_cst |
|---|---|---|---|
| MP(荷札の受け渡し) | **✗** ARMで破れ | ✓ | ✓ |
| SB(全員の合意) | **✗** 両方で破れ | **✗** 両方で破れ | ✓ |
| カウンタ(join後に合計を読む) | ✓(7.4節) | ✓ | ✓ |
| 上記のx64での見え方 | MP・カウンタは✓ | 同左+SBのみ✗ | すべて✓ |

最下行に注目してください。x64ではTSOのおかげでMPの行の✗が**✓に化けます**。表7-1のうち、x64上のテストで検出できる誤りは「SBパターンをseq_cst未満で書いた」場合**だけ**。オーダー選択の誤りの大半は、x64というテスト環境では**原理的に見えない**のです。この不吉な事実は7.8節で実弾になります。

この表の使い方が、そのまま実務のオーダー選択手順になります。**(1) 自分のコードの構図はどのパターンか(何かを封して渡すのか、全員の合意が要るのか、数を数えるだけか)を見極める。(2) 表で最弱の✓を選ぶ。(3) 迷ったらseq_cstに置いてから、証明できた箇所だけ緩める。** 順序が逆――「速そうだからrelaxedで書いてから、壊れたら強める」――は、壊れたことをx64が教えてくれない以上、成立しません。

## 7.4 【コード】relaxedが正しく使える場所 ― 統計カウンタとshared_ptrの参照カウント

表7-1の3行目、relaxedでも✓が付く行を精査します。relaxedの保証は「不可分性と変更順序(第5.3節)だけ。happens-beforeは運ばない(観測事実14)」でした。逆に言えば、**不可分性と変更順序だけで正しさが完結する仕事**なら、relaxedは完全に正しい選択です。代表を3つ挙げます。

**(1) 統計カウンタ。** 第6.1節の版R、`ctr.fetch_add(1, relaxed)`です。正しさの根拠を厳密に述べます。加算の無消失は「RMWは変更順序上の直前の値を読む」保証(第6.1節)が単独で担い、順序保証は不要。では最後に合計を**読む**側の可視性は? ここに隠れた伏線があります――mainは`t.join()`の**後**で読んでおり、joinは表5-2に載った立派なsynchronizes-with辺です。**ロープはrelaxedカウンタの外側で、joinが既に張ってくれている。** だからカウンタ自身は裸でよいのです。relaxedの正しい使用には、たいていこのように「別の場所に順序の後ろ盾がある」構造が隠れています。性能の回収もここでしておきます。表6-1の再掲と追試です。

```console
# 非競合1スレッド、1加算あたり
x64:  seq_cst 5.4ns / relaxed 5.4ns      (差なし: どちらも lock add)
M2:   seq_cst 7.1ns / relaxed 2.6ns      (2.7倍: ldaddal → ldadd)
```

**relaxedの配当はARMでだけ支払われる**――表6-1の太字の、これが全回収です。

**(2) 停止フラグ。** 第2.4節のリスト2-3(コンパイラに消されたstopフラグ)の正式な直し方は、`std::atomic<int> stop`への**relaxedアクセス**です。ハンドラ側`stop.store(1, relaxed)`、ループ側`stop.load(relaxed)`。守るべきデータが何もなく、「いつかは見える」ことだけが要件(規格も、アトミックストアは有限時間内に他スレッドから見えるべきと定めています)なので、hbは不要。volatileと違って未定義動作の疑いも消え、コンパイラの吊り上げも封じられます。

**(3) shared_ptrの参照カウント――relaxedとreleaseの実戦的な使い分けの教科書。** libstdc++等の実装は、参照カウントの**増加**をrelaxedで、**減少**をacq_rel系で行います。この非対称に、この章の全部が詰まっています。増加がrelaxedでよい理由:カウントを増やせるのは、いま有効なshared_ptrを**手に持っている**スレッドだけであり、オブジェクトの生存は増加の成否と無関係にその手持ちが保証している。増加は「数を数える」仕事(表7-1の3行目)です。減少がrelaxedでは**いけない**理由:カウントを0にしたスレッドはデストラクタを走らせますが、その直前まで**他の**スレッドがオブジェクトに書き込んでいたかもしれない。破壊は全使用にhappens-afterでなければならず、これは紛れもなくMP構図(各利用者が「使い終えた」印を封して渡し、最後の1人が全員の封を開けてから破壊する)。だから減少はreleaseで行い、0を見た者がacquire(実装ではfetch_subをacq_relにするか、0検出後にacquireフェンス)で受けるのです。**同じ1本のカウンタの中に、relaxedで足す仕事とrelease/acquireで渡す仕事が同居する**――オーダーは変数に付くのではなく、操作の「構図」に付く、という本章の教えの縮図です。

> **観測事実22**: relaxedが正しいのは、不可分性+変更順序だけで正しさが閉じる仕事(数える・旗を立てる)であり、可視性は多くの場合joinなど外部のロープが担っている。その配当(M2で2.7倍)はARMでのみ支払われ、x64では正しさの検証も性能の検証もできない。

## 7.5 【コード】フェンス版への書き換えと、atomic操作版との等価性確認

ここまでのrelease/acquireは、特定のstore/loadに**貼り付いた**指定でした。C++にはもうひとつ、操作から独立して膜だけを立てる道具があります。`std::atomic_thread_fence`です。実は既に一度使っています――リスト3-2、SBに挿した`atomic_thread_fence(seq_cst)`(x64でmfenceになったあれ)です。今回はrelease/acquireフェンスでMPを書き換えます。

**リスト7-2: mp_fence.cpp(テスト本体)**

```cpp
// 送信側                                          // 受信側
data_.store(42, std::memory_order_relaxed);        while (ready.load(std::memory_order_relaxed) == 0) {}
std::atomic_thread_fence(std::memory_order_release);   std::atomic_thread_fence(std::memory_order_acquire);
ready.store(1, std::memory_order_relaxed);         r = data_.load(std::memory_order_relaxed);
```

位置に注意してください。**releaseフェンスは「守りたい書き込み」と「荷札のストア」の間**、**acquireフェンスは「荷札のロード」と「開封する読み取り」の間**です(貼り付き版と前後関係が対応します)。契約上も、「releaseフェンス→後続のatomicストア」と「atomicロード→後続のacquireフェンス」が値の受け渡しで結ばれると、**フェンスどうし**がsynchronizes-withします。実行結果はARMで0/1000万――貼り付き版と同じくMPを直します。TSanも両版で沈黙し、herd7(第11.2節)も両版のMP破れをForbiddenと判定します。

では完全に等価かというと、2つの差があります。**第一に意味の広さ。** 貼り付き版releaseは「そのストア1個」に封をしますが、releaseフェンスは「フェンス以降に実行される**あらゆる**relaxedストア」を荷札化します。100個のフラグを順に立てる一括公開では、フェンス1枚で済む――これがフェンスの存在意義です(第3章演習4で予告した意味論の違いがこれです)。**第二に値段。** ARMで逆アセンブルすると、貼り付き版は`stlr`/`ldar`、フェンス版は`dmb ish`(全方向バリア)になります。M2で計測すると、MPの1往復あたりフェンス版が2〜3割高くつきました。守備範囲が広いぶん高い――道理です。実務則は「**1点の受け渡しは貼り付き版、まとめ売りはフェンス**」。なお、第2章演習5で触れた`atomic_signal_fence`は、この膜の**コンパイラにだけ効く版**(CPU命令ゼロ)で、シグナルハンドラとの同期専用です。

## 7.6 【コード】リリースシーケンスが切れるコードと切れないコードの比較実験

release/acquireのロープには、知らないと切れる細い箇所が1つあります。荷札のストアと開封のロードの**間に、第三者が同じ変数を触った**らどうなるか、という問題です。実務では「状態フラグを複数段階で進める」コードで頻出します。

**リスト7-3: relseq.cpp ― 第三者の介入、2つの流儀**

```cpp
int payload = 0;                       // わざと素のint(TSanを検算器にする)
std::atomic<int> stage{0};

void writer()  { payload = 42; stage.store(1, std::memory_order_release); }

// 第三者: stageを1→2に進める(自分はacquireで読まず、relaxedで進めるだけ)
void helper_rmw()   { int e = 1; while (!stage.compare_exchange_weak(
                          e, 2, std::memory_order_relaxed)) e = 1; }        // 流儀①: RMWで進める
void helper_store() { while (stage.load(std::memory_order_relaxed) != 1) {}
                      stage.store(2, std::memory_order_relaxed); }          // 流儀②: 素のstoreで進める

void reader()  { while (stage.load(std::memory_order_acquire) != 2) {}
                 r = payload; }        // 2を見てからpayloadを開封
```

readerが読む値2を書いたのは、writerではなく**第三者**です。ではwriterのreleaseの封は、readerまで届くのでしょうか。契約の答えは、第三者の**書き方**で分かれます。

> **リリースシーケンス**: releaseストアを起点に、**RMW操作(オーダー不問)だけを連ねた**書き込みの列を、そのreleaseの「リリースシーケンス」と呼ぶ。acquireロードが**列上のどの値**を読んでも、起点のreleaseとsynchronizes-withが成立する。**素のストアは列を断ち切る。**

流儀①(CAS=RMW)は列を継ぎ、流儀②(store)は列を断つ――机上ではそうなります。検算器にかけます。

```console
$ ./relseq_rmw_tsan
(沈黙)                                    # ロープは通っている
$ ./relseq_store_tsan
WARNING: ThreadSanitizer: data race       # payloadへの競合!ロープは切れた
  Read of size 4 ... (r = payload)
  Previous write of size 4 ... (payload = 42)
```

TSanは契約どおりの判定を下しました。なお実機のARMで流儀②を回しても、破れはそう簡単には観測できません(helperの介入タイミングという狭い窓が必要なためです)。**「実機で壊れないこと」と「契約上競合であること」は両立する**――第5章の教えのとおり、こういうときこそ実行結果ではなくTSanとherd7を信じるべき場面です。契約上の競合は、次のコンパイラ、次のCPU、次の最適化フラグで実弾になります。

なぜRMWだけが列を継げるのか、直感も添えておきます。RMWは「変更順序上の直前の値を読んで」書く(第6.1節)ので、封の荷札を**引き継いで**上書きします。素のstoreは前の値と無関係に**新しい荷札で上書き**するので、元の封の情報が失われる――そういう建付けです(歴史的補足: C++17までは「同じスレッドの素のstore」も列を継げましたが、実装困難と誤用の温床のためC++20で削除されました。古い解説記事を読むときは注意してください)。

> **観測事実23**: releaseの封は、後続がRMWである限り第三者を経由しても届く(リリースシーケンス)が、素のstoreが1回挟まると断ち切られる。多段フラグ・多者更新のフラグは**RMW(exchange/CAS/fetch系)で進める**のが安全側の定石である。

## 7.7 memory_order_consumeを使ってはいけない理由

6段のオーダーのうち、本書がまだ触れていないものが1つ残っています。`memory_order_consume`。結論から言います――**書いてはいけません**。しかし「存在理由」は本書の読者にはとても面白いはずなので、墓碑銘だけ読んでいきます。

consumeが夢見たのは、acquireの**依存関係限定版**です。ポインタ公開のコードを見てください。

```cpp
Config* p = cfg_ptr.load(std::memory_order_acquire);   // 荷札を確認して
use(p->value);                                          // 開封する
```

acquireの膜は「後続の**全**読み取り」を守りますが、この構図で本当に守りたいのは`p->value`、つまり**読んだポインタpに依存する読み取りだけ**です。そしてARMのハードウェアには、第3章では触れなかった素敵な性質があります――**アドレス依存のあるロードの対は、バリアなしでも順序が守られる**のです(`ldr x0, [x1]`→`ldr x2, [x0]`の形。2発目のアドレスが1発目の結果に依存する限り、弱いモデルでも並べ替え不能)。ならば依存だけ守ればよい場面では、`ldar`(膜つき)ではなく素の`ldr`が使える。Linuxカーネルの読者側ほぼ無コスト同期・RCUがまさにこの性質の上に建っており、consumeはそれをC++の契約に輸入する試みでした。

夢の死因は、コンパイラです。依存関係はソース上では明白でも、最適化の通過後に消えます(例:`p->value`を`if (p == cached_p) use(cached_value);`に書き換えた瞬間、アドレス依存は制御依存に化けて保証が消える)。全最適化パスに依存追跡を教え込むのは非現実的で、主要コンパイラは全会一致で**consumeをacquireに黙って格上げ**する実装を選びました。確認は一瞬です。

```console
$ clang++ -O2 -S consume_vs_acquire.cpp   # 両版の読み側を並べる(AArch64)
; consume版                 ; acquire版
    ldar   x0, [x8]             ldar   x0, [x8]      # 完全に同一
```

**1バイトも違いません。** つまりconsumeと書く行為は、(a) 性能はacquireと同じ、(b) 意味論は規格改定で動く不安定地帯(C++17で「一時的に使用を推奨しない」と明記)、(c) 読み手に「依存で守るつもりらしい」という**果たされない意図**を伝える、の三重苦だけを買う行為です。書くべきはacquire。依存順序の恩恵は、ARMでは`ldr`+依存としてカーネル流の職人芸に残り、標準化のやり直し(依存を型で明示する提案など)は現在も委員会の宿題です。

## 7.8 【コード】「TSOに甘えたコード」を書いてみる ― relaxedなのにx64では絶対に壊れず、ARMで壊れる

最終節は、この章の知識の**確認テストを兼ねた実弾演習**です。目標は挑発的です:**relaxedで書かれていて、契約上は明白に不正(表7-1でMP構図の✗)なのに、x64ではどれだけ回しても絶対に壊れないコード**を、意図的に作ります。

題材は実務で頻出の「設定のホットリロード」です。書き手が設定を書き換え、世代番号を進める。読み手は世代番号の変化を見たら設定を読み直す。ミソは、読み手が**固定アドレスの構造体**を直接読むことです(7.7節のアドレス依存が発生しない形をわざと選びます。依存があるとARMのハードウェアに救済されてしまい、実験になりません)。

**リスト7-4: hotreload.cpp ― TSOに甘えた設定リロード**

```cpp
// 設定: 不変条件は「aとbは常に同じ値」(片方だけ新しい状態は壊れたスナップショット)
std::atomic<int> cfg_a{0}, cfg_b{0};          // relaxedアトミック(競合は回避し、順序の罪だけを残す)
std::atomic<int> generation{0};

void writer() {
    for (int g = 1; g <= G; ++g) {
        cfg_a.store(g, std::memory_order_relaxed);       // ① 設定本体を更新し
        cfg_b.store(g, std::memory_order_relaxed);       // ②
        generation.store(g, std::memory_order_relaxed);  // ③ 世代番号を進める
    }
}

void reader() {
    int last = 0;
    while (last < G) {
        int g = generation.load(std::memory_order_relaxed);   // ④ 世代を確認
        if (g != last) {
            int a = cfg_a.load(std::memory_order_relaxed);    // ⑤ 設定を読む
            int b = cfg_b.load(std::memory_order_relaxed);    // ⑥
            if (a < g || b < g) ++torn;    // 世代gを見たのに古い設定 = 破れ
            last = g;
        }
    }
}
```

診断は読者自身でできるはずです。①②→③はStore→Storeの封なしの公開、④→⑤⑥はLoad→Loadの開封――**両側とも裸のMP構図**であり、表7-1の左上、✗の枠のど真ん中です。しかしx64は? ①②③の順はTSOのFIFOバッファが守り(第3.2.2節の証明)、④⑤⑥の順はTSOのロード順保証が守る。**契約は破っているが、x64というアーキテクチャが勝手に履行してくれる。** 回します。

```console
# x64 (Core i7) — 一晩、繰り返し実行
$ ./hotreload
破れたスナップショット 0 / 10000000 世代
(…計21億世代、破れゼロ)

# ARM (Apple M2) — 初回実行
$ ./hotreload
破れたスナップショット 1893 / 10000000 世代
```

x64で21億世代無傷、ARMで**初回から**1万世代に2件の壊れたスナップショット。これが「TSOへのただ乗り」の実物です。恐ろしいのは検出可能性の壁です――このコードは全操作がアトミックなので**TSanも沈黙します**(第6.5節と同じ、検算器の空白地帯)。x64のCIでは、ストレステストも、サニタイザも、コードレビューでの「動いてる実績」も、全部が青信号を出す。誤りを検出できる装置は、(a) 表7-1を頭に入れたレビュアーの目、(b) herd7/Relacyのようなモデル検査(第11章)、(c) ARM実機のCI、の3つしかありません。第10.7節で扱う実話「Graviton移行の日から落ち始めたサービス」の原型が、この40行です。

直しは、この章の読者には1分の仕事です。③をreleaseに、④をacquireに(封と開封の1点ずつ。⑤⑥や①②はrelaxedのままでよい――acquireの膜が④の後続全部を守るからです)。そして直した後の値札を見てください。

```console
# 修正版の逆アセンブル差分
x64:   ③ mov → mov、④ mov → mov      # 1バイトも変わらない(コストゼロ)
ARM:   ③ str → stlr、④ ldr → ldar    # ここだけ膜の実費を払う
```

**x64では、正しさの保険料が0円なのです。** 「x64しか使わないから直さない」という判断すら、この事実の前では成立しません――直しても何も遅くならないのだから。逆に言えば、relaxedと書いてx64で速くなることも(この形では)ない。x64上のrelaxedの大半は、性能を買っておらず、**移植性だけを売っている**のです。

> **観測事実24**: 契約違反(裸のMP構図)のコードが、TSOの保証にただ乗りしてx64では21億世代無傷で動き、ARMでは初回から破れた。TSanも沈黙する。修正(release/acquireを1点ずつ)のx64でのコストは機械語レベルでゼロ――x64でrelaxedを選ぶことは、多くの場合、性能を買わずに移植性を売る行為である。

### 第7章のまとめ

- 方法論:保証の輪郭は「緩めて壊し、強めて直す」往復で、境界の両側からなぞる。成果物が表7-1(パターン×オーダーの生死表)であり、オーダー選択とは「構図を見極めて最弱の✓を選ぶ」ことである。
- **観測事実20**: seq_cstは全パターンを直し、インターリーブの直感(DRF-SC)を復活させる基準線。
- **観測事実21**: acquire/releaseは荷札を渡した2者間のロープ。MPは直るがSBは直らない(x64でも!)。全員合意が要る構図(相互排他・SB型)はseq_cst。
- **観測事実22**: relaxedは「数える・旗を立てる」仕事の道具。可視性はjoin等の外部ロープが担う。shared_ptrのカウンタ(増加relaxed/減少release)が使い分けの教科書。配当はARM限定。
- フェンスは膜の独立販売品:守備範囲が広く(一括公開向き)、ARMではdmb ishのぶん貼り付き版(stlr/ldar)より高い。1点渡しは貼り付き、まとめ売りはフェンス(7.5節)。
- **観測事実23**: releaseの封はRMWの列(リリースシーケンス)を伝って届くが、素のstoreで断ち切られる。多者が触るフラグはRMWで進めよ。
- consumeは書かない。全コンパイラがacquireに格上げしており(アセンブリ同一)、依存順序の夢はARMのハードウェア(アドレス依存の無償順序)とRCUの職人芸に残った(7.7節)。
- **観測事実24**: TSOただ乗りコードはx64の全検査をすり抜け、ARMで初日に壊れる。修正のx64コストは0円。

次の第8章は、この章で何度も先取りした「値札」の総精算です。6段のオーダーそれぞれが、x64とARMでどの機械語に翻訳されるのかの完全な対応表を作り、Compiler Explorerと実測ベンチで裏を取ります。「acquireがx64でタダなのはなぜか」に、TSOの語彙で最終的な答えを出します。
