# 第9章 同期プリミティブを自作する

第3部へようこそ。ここからは、第2部で手に入れた全装備――契約の語彙、道具箱、値付け表、翻訳表――を持って、実戦のコードを**作る**側に回ります。

手始めは同期プリミティブです。std::mutexやセマフォを、私たちはこれまで「買ってきた既製品」として使ってきました。この章では全部自作します。目的は車輪の再発明の推奨ではありません(実務では既製品を使ってください)。**既製品の性能特性と限界は、中身を一度作った者にしか正しく読めない**からです。進め方はいつもどおり:作る→計測する→第1部の語彙で診断する→改良する。そして各節の終わりに「既製品はこの問題をどう解いているか」を突き合わせます。

この章の題材は6つ。スピンロックの3段進化(9.1節)、futexとstd::mutexの解体(9.2節)、悪名高いダブルチェックドロッキング(9.3節)、コンパイラが自動生成する同期コード(9.4節)、読者が何も書かないseqlock(9.5節)、そしてC++20のatomic::waitで作るセマフォ(9.6節)です。

## 9.1 【コード】TAS → TTAS → 指数バックオフ ― スピンロック3段進化

出発点は第6.2節で作った2つの最小ロックです。再掲します。

```cpp
// TASロック(exchange版)                 // CASロック(6.2節版)
void lock() {                             void lock() {
    while (locked.exchange(true,              bool e = false;
           std::memory_order_acquire)) {}     while (!locked.compare_exchange_weak(
}                                                 e, true, std::memory_order_acquire))
                                                  e = false;
                                          }
```

「動く最小品」としては合格でした。では性能は? 恒例のベンチマーク――Nスレッドがロックを取ってカウンタを1増やして解放する――を8スレッドで回します。

```console
# x64、8スレッド、lock+increment+unlock 1回あたり
TAS  : 847 ns/op
CAS  : 812 ns/op
(参考)std::mutex : 158 ns/op
```

自作品は既製品の**5倍遅い**。診断に入りましょう。読者はもう聴診器(第4章)を持っています。TASの待機ループは`exchange`、すなわち**RMW**の連打です。RMWはラインの**M状態での独占**を要求する(第4.4節)。つまり待機中の7スレッドは、ロックを取れもしないのに、1回スピンするたびにラインの所有権を奪い合い、RFOの往復代金を払い続けている。最悪なのは、この奪い合いが**ロック保持者まで巻き込む**ことです。保持者がunlockのstoreをしようにも、ラインは待機者たちに引きずり回されていて手元にない。**待つ側の熱心さが、待たれる側の解放を遅らせる**――スピンロック性能問題の第一病巣です。

処方は「**待つときは書くな、読め**」。ロードならラインをS(共有)状態で全待機者のキャッシュに置けて、ロックが保持されている間、待機ループは**完全にローカルなキャッシュヒット**になり、バス上の交通量はゼロになります。これがTTAS(Test-and-Test-and-Set)です。

**リスト9-1: ttas.cpp ― 読んでから挑む**

```cpp
void lock() {
    for (;;) {
        // 第1のT: まず読むだけ(ラインはS状態、待機コストはローカルヒットのみ)
        while (locked.load(std::memory_order_relaxed)) { cpu_relax(); }
        // 第2のT: 空きを見てから初めてRMWで挑戦
        if (!locked.exchange(true, std::memory_order_acquire)) return;
    }
}
```

`cpu_relax()`は待機ループの礼儀作法で、x64では`pause`命令(投機の抑制と同時マルチスレッディングの相棒への譲歩、省電力)、ARMでは`yield`をインラインasmで発行します。待機ロードがrelaxedでよい理由も装備済みの知識で言えます――ここは「旗を見る」だけの仕事(表7-1の3行目)で、荷札の開封(acquire)は**獲得に成功したexchange**が担うからです。計測:

```console
TTAS : 316 ns/op      # TASの2.7倍改善
```

大幅改善ですが、まだ既製品の2倍。第二病巣が残っています。ロックが解放される**瞬間**を想像してください。7待機者のS状態の写しが、保持者のstoreで一斉に無効化され、7スレッドが**同時に**「空きだ!」を見て、7つのexchangeが**同時に**RFOへ殺到する。勝者は1人、残り6回のRMWは純粋な交通渋滞です。解放のたびに起きるこの**雪崩**が第二病巣。処方は、挑戦に失敗した者を指数的に長く待たせて、殺到をばらけさせることです。

**リスト9-2: backoff.cpp ― 敗者は下がって待つ**

```cpp
void lock() {
    int delay = 1;
    for (;;) {
        while (locked.load(std::memory_order_relaxed)) { cpu_relax(); }
        if (!locked.exchange(true, std::memory_order_acquire)) return;
        for (int i = 0; i < delay; ++i) cpu_relax();     // 敗者のペナルティ
        delay = std::min(delay * 2, MAX_DELAY);          // 指数的に伸ばす
    }
}
```

```console
TTAS+指数バックオフ : 141 ns/op    # std::mutex(158ns)をわずかに上回った
```

3段進化の全景をまとめます。

> **観測事実29**: スピンロックの性能病巣は2つ――(1) RMWでの待機がラインを引きずり回し保持者の解放まで遅らせる(TAS、847ns)、(2) 解放の瞬間に全待機者のRMWが殺到する雪崩(TTAS、316ns)。「待つときは読む」と「敗者は指数的に下がる」の2処方で、8スレッド競合でTAS比6倍(141ns)まで改善する。

ただし勝利宣言の前に、値札の裏を読んでください。バックオフは**公平性を売って**スループットを買っています。長く下がった古参より、来たばかりの新参が勝ちやすい(最悪、古参は飢餓します)。到着順を保証したければチケットロック(演習1)、さらに各待機者を**自分専用のフラグ**で待たせて雪崩を構造的に消すMCS/CLHロック(演習2)へと発展します。もうひとつ、ARMには待機の美しい別解があります――`ldaxr`で監視を仕掛けてから`wfe`(Wait For Event)で**低電力の眠り**に入り、ラインへの書き込みが監視を破った瞬間に目覚める。スピンともスリープとも違う第三の待ち方で、Linuxカーネルのarm64ロックの基盤です(演習3)。

## 9.2 std::mutexとfutexの仕組み ― 「寝る」ためのシステムコール1個

スピンロックには構造的な限界があります。クリティカルセクションが長い、あるいはコア数よりスレッドが多い(オーバーサブスクリプション)とき、スピンは**CPUを燃やしてライバルの進行を妨げる**最悪の待ち方になります。長い待ちはOSに頼んで**寝る**べきです。しかし素朴に「毎回システムコールでロック」を実装すると、非競合の1回すら1μs級の往復になり、9.1節の141nsから7倍の退化です。

この矛盾を解いたのがLinuxの**futex**(fast userspace mutex)です。設計思想は一行で言えます:**非競合の道はユーザー空間のアトミック操作だけで完結させ、カーネルには「競合して寝るとき」だけ入る。** カーネル側の口はシステムコール1個で、本質は2動詞です。

```cpp
// futexの生の口(Linux)
futex_wait(addr, expected);  // 「*addr がまだ expected なら」私を寝かせて、addrの待機列に載せよ
futex_wake(addr, n);         // addrの待機列から n 人起こせ
```

waitの条件節「まだexpectedなら」が、この仕組みの心臓です。もし無条件に寝るAPIだったら、「私が値を確認してから寝るまでの隙間」に相手がwakeを撃ち、**誰もいない待機列を起こして、私は永眠する**(lost wakeup)。futexは値の再確認を**カーネル内・待機列のロック下**で行うことで、この隙間を構造的に閉じます。第6.2節のCASが「確認と書き込み」を不可分にしたのと同型の、「確認と就寝」の不可分化です。

では、この2動詞でmutexを組みます。有名なDrepperの3状態設計(0=空き、1=施錠、2=施錠+待機者あり)の最小実装です。

**リスト9-3: futex_mutex.cpp ― 25行のstd::mutex(の骨格)**

```cpp
class FutexMutex {
    std::atomic<int> s{0};                    // 0:空き 1:施錠 2:施錠+待機者
public:
    void lock() {
        int e = 0;
        if (s.compare_exchange_strong(e, 1, std::memory_order_acquire))
            return;                           // 高速路: 非競合ならCAS1発、syscallゼロ
        do {                                  // 低速路: ここからが競合
            if (e == 2 ||                     // 既に待機者あり、または
                s.compare_exchange_strong(e, 2, std::memory_order_relaxed))
                futex_wait(&s, 2);            //   1→2に格上げできたら「2のままなら寝る」
            e = 0;
        } while (!s.compare_exchange_strong(e, 2, std::memory_order_acquire));
    }                                         // 目覚めたら「空きなら2で施錠」を挑み直す
    void unlock() {
        if (s.exchange(0, std::memory_order_release) == 2)
            futex_wake(&s, 1);                // 待機者がいた時だけ、1人起こす
    }
};
```

設計の要点を3つだけ。**(1) syscallは有罪確定後のみ。** unlockのexchangeが旧値2を返した(=待機者がいる)ときだけwakeを呼ぶ。旧値1(誰も待っていない)なら、storeだけで完了です。**(2) 目覚めは資格ではない。** 起こされたスレッドは施錠をもらったのではなく、**挑戦権**をもらっただけで、CASで挑み直します(そして再獲得時は2で施錠します――自分の後ろにまだ待機者が残っているかもしれないから)。**(3) ロープは第5.4節のまま。** lockの成功CASがacquire、unlockのexchangeがrelease。futexという舞台装置が増えても、happens-beforeの構造は観測事実15で解剖したものと寸分違いません。

答え合わせはstraceで行います。

```console
$ strace -f -e futex ./bench_futexmutex --threads=1     # 非競合
(futexの行なし)                                           # 高速路のみ、syscallゼロ
$ strace -f -e futex ./bench_futexmutex --threads=8     # 競合
futex(0x4041c0, FUTEX_WAIT_PRIVATE, 2, NULL) = 0
futex(0x4041c0, FUTEX_WAKE_PRIVATE, 1)      = 1
...(WAIT/WAKEの応酬)
```

> **観測事実30**: futexの設計は「非競合はユーザー空間のCAS1発(実測15ns、syscallゼロ)、競合時のみカーネルで寝る(wake往復は1〜2μs)」。lost wakeupは「値の再確認をカーネル内で行うwait」が構造的に封じる。3状態(空き/施錠/施錠+待機者)は「不要なwake syscallを撃たない」ための会計である。

これでstd::mutexの読み方が変わるはずです。glibcのpthread_mutexはこの構造の産業版(所有者記録、適応スピン=寝る前に少しだけ9.1節式に粘る、優先度継承等のオプション)であり、macOSはfutexの代わりに`__ulock_wait`系とos_unfair_lockで同じ思想を実装します。9.1節の自作スピンロックがstd::mutexに勝った141ns vs 158nsという結果も、いまなら正しく読めます――あの勝負は「クリティカルセクションが極小・スレッド数≦コア数」というスピン最適の土俵でのもの。土俵をオーバーサブスクリプション(16スレッド/8コア)に変えると、スピンロックは数μs/opまで崩壊し、futex系は粛々と160ns前後を保ちます(演習4)。**待ち方の選択とは、ワークロードの仮定の宣言**なのです。

## 9.3 【コード】ダブルチェックドロッキング ― 壊れた版をARMで発火させてから直す

ここからの2節は「遅延初期化」という1つの問題の、暗黒時代と現代を見比べます。問題:高価なオブジェクトを最初の利用時に一度だけ構築し、以後は全スレッドから素早く参照したい。素朴解「毎回mutex」は、初期化後の定常状態でもロック代を払い続けます。そこで1990年代に、こういう「賢い」コードが発明されました。

**リスト9-4: dclp_broken.cpp ― C++03流ダブルチェックドロッキング(壊れている)**

```cpp
Widget* inst = nullptr;                    // 素のポインタ(暗黒時代なので)
std::mutex m;

Widget* get() {
    if (inst == nullptr) {                 // 検査1: ロックなしの早道
        std::lock_guard g(m);
        if (inst == nullptr) {             // 検査2: ロック下で再確認
            inst = new Widget(42, 42);     // 構築して公開
        }
    }
    return inst;                           // ほとんどの呼び出しはここへ直行
}
```

一見、隙がありません。二重の検査で構築の一意性を守り、定常状態はロードと分岐だけ。この発明は当時広く称賛され、教科書に載り――そして2000年代に「壊れている」ことが示され、C++メモリモデル誕生の推進力の一つになりました。本書の読者なら、どこが壊れているか自力で診断できるはずです。2つあります。

**第一に、契約違反(これだけで死刑)。** 検査1の`inst`読みと、構築スレッドの`inst`書きは、非アトミック同士・ロープなしの衝突対。5.1節の定義そのもののデータ競合、未定義動作です。TSanは即座に検出します。

**第二に、たとえ競合を見逃してもらっても、順序が壊れています。** `inst = new Widget(42,42)`は、(a) 領域確保、(b) コンストラクタのフィールド書き込み、(c) ポインタの公開、の3段です。(b)と(c)は別アドレスへのストアの列――**Store→Store**。第3章の表3-1を見てください。ARMはこれを並べ替えてよい。つまり**中身が書かれる前にポインタが公開され**、別スレッドが「非nullなのに未構築のWidget」を掴みうる。読み手側は`p->x`というアドレス依存ロードなのでARMハードウェアの依存順序(7.7節)に守られますが、**書き手が遅れて書いたものは依存でも救えません**。

発火させます。シングルトンは「プロセスに一度」しか壊れる機会がないので、ハーネスで初期化を人工的に何百万回も繰り返します(アリーナ上でinstをリセット→スレッドAがget()で構築→スレッドBがget()の返値のフィールドを検査、を1イテレーションとする)。

```console
# x64 — 一晩
未構築Widgetの観測 0 / 300000000 回          # TSOのStore→Store禁止に、またしても救われている
# ARM (Apple M2)
未構築Widgetの観測 37 / 10000000 回          # 発火。x==0のWidgetが漏れ出た
```

第7.8節と同じ構図の再演です:x64では**発明当時から今日まで一度も再現しない**からこそ、このイディオムは何年も正しいと信じられた。修正は、いまや定型作業です――公開点にrelease、検査点にacquire。

**リスト9-5: dclp_fixed.cpp(差分のみ)**

```cpp
std::atomic<Widget*> inst{nullptr};

Widget* get() {
    Widget* p = inst.load(std::memory_order_acquire);        // 検査1
    if (p == nullptr) {
        std::lock_guard g(m);
        p = inst.load(std::memory_order_relaxed);            // 検査2(mのロープ下なのでrelaxedで可)
        if (p == nullptr) {
            p = new Widget(42, 42);
            inst.store(p, std::memory_order_release);        // 構築の封をしてから公開
        }
    }
    return p;
}
```

ARMで破れゼロ、TSan沈黙。そして恒例の値札確認――x64では修正前後でホットパス(検査1)の機械語は`mov`のまま**不変**、ARMでは`ldr`が`ldar`に変わるだけ。ちなみにこのポインタ公開こそ、7.7節で葬ったconsumeが夢見た本籍地です。私たちはacquireと書き、ARMの実費は`ldar`(RCpc環境なら`ldapr`)1個。定常状態のこの1命令すら惜しい読み手最適化の道は、カーネルのRCUに続いています。

> **観測事実31**: DCLPの故障は書き手側のStore→Store並べ替え(構築より先の公開)であり、ARM実機で1000万回に37回発火、x64では3億回無傷だった。読み手のアドレス依存は書き手の遅配を救えない。修正はポインタへのrelease/acquireで、x64のホットパスの機械語は不変(保険料0円)。

## 9.4 【コード】static局所変数の初期化 ― コンパイラが書いた「正しいDCLP」を読む

修正版DCLPを自分で書く必要は、現代のC++ではほぼありません。C++11以降、この1行が同じ仕事を、正しく、やってくれます。

```cpp
Widget& get() {
    static Widget instance(42, 42);     // マジックスタティック: 初期化のスレッド安全性を言語が保証
    return instance;
}
```

「言語が保証」の実体を、いつもの流儀で確かめましょう。逆アセンブルです。

```asm
; ---- AArch64 (Clang -O2) ----
get():
    adrp   x8, guard_variable_for_get::instance
    ldarb  w9, [x8, :lo12:...]          ; ① ガードバイトを acquire ロード!
    tbz    w9, #0, .Lslow               ; ② 未初期化なら低速路へ
    adrp   x0, get::instance            ; ③ 初期化済み: そのまま返す(高速路はこれだけ)
    ret
.Lslow:
    bl     __cxa_guard_acquire          ; ④ ガード獲得(内部は9.2節のfutex系)
    cbz    w0, .Ldone                   ;    0が返る=他スレッドが構築済みだった
    ...Widgetのコンストラクタ呼び出し...
    bl     __cxa_guard_release          ; ⑤ 構築完了の封をして公開
.Ldone: ...

; ---- x64 (GCC -O2) ----
get():
    movzx  eax, BYTE PTR guard[rip]     ; ①' 素のmov(acquireはR⊆Hで無料: 第8章)
    test   al, al
    je     .Lslow
    ...
```

見事なまでに、**リスト9-5と同じ形**です。ガードバイト=instポインタの役、①のacquireロード=検査1、④の`__cxa_guard_acquire`=mutex+検査2(実装はglibcではまさにfutexで、9.2節の低速路がここでも回っています)、⑤の`__cxa_guard_release`=releaseストアによる公開。ARMの①に`ldarb`(acquireつきバイトロード)が律儀に置かれ、x64の①'が素の`movzx`で済んでいる対比は、第8章の対応表の生きた標本です。

つまりマジックスタティックとは、**コンパイラとランタイムが共同で自動生成する、監査済みのDCLP**です。定常コストは「acquireロード1回+分岐1回」――人間が9.3節の地雷原を歩いて得られる成果の上限と同じものが、1行で手に入る。実務の結論は明快です:遅延初期化は、まずマジックスタティック(またはstd::call_once――こちらも中身は同族です)。手書きDCLPが正当化されるのは、ガード1バイトの間接参照すら統計に現れるような、計測で証明された特殊事情がある場合だけです。

## 9.5 【コード】seqlock ― 読者が何も書かない同期、そして第7.8節の答え合わせ

mutexにもスピンロックにも、読者視点で共通の税があります。**読むだけでも書く**(ロック変数へのRMW)こと。第4章で学んだとおり、共有ラインへの書き込みはコア数分のスケーリングを殺します。読者が圧倒的多数で、データが小さく、書き手が稀――統計スナップショット、設定値、時刻――という状況のために、「**読者は共有メモリに1バイトも書かない**」同期が存在します。seqlock(sequence lock)です。

プロトコルは世代番号1本で回ります。**書き手**:番号を+1して奇数にする(工事中の札)→データを書く→+1して偶数に戻す(開店の札)。**読み手**:番号を読む(奇数なら工事中、引き返す)→データを読む→番号を**もう一度**読む→2回の番号が一致すれば、読んでいる間に工事がなかった証拠なので採用。不一致ならやり直し。

この筋書き、既視感があるはずです。**第7.8節の「TSOに甘えたホットリロード」は、seqlockの出来損ない**でした――世代番号のアイデアだけ借りて、奇数の札も、2回目の検査も、膜も欠いた姿です。ここで完成形を書きます。膜の配置は第7.5節のフェンス(「まとめ売り」の膜)の、本書での最重要の使用例です。

**リスト9-6: seqlock.cpp**

```cpp
class SeqLock {
    std::atomic<unsigned> seq{0};
    std::atomic<int> a{0}, b{0};        // ペイロード。relaxedアトミックである理由は本文で
public:
    void write(int va, int vb) {        // 書き手は1人と仮定(複数ならここを外部mutexで)
        unsigned s = seq.load(std::memory_order_relaxed);
        seq.store(s + 1, std::memory_order_relaxed);            // 奇数 = 工事中の札
        std::atomic_thread_fence(std::memory_order_release);    // 膜: 札がデータより先に立つ
        a.store(va, std::memory_order_relaxed);
        b.store(vb, std::memory_order_relaxed);
        seq.store(s + 2, std::memory_order_release);            // 偶数に戻して公開(封)
    }
    bool try_read(int& ra, int& rb) {
        unsigned s1 = seq.load(std::memory_order_acquire);      // 検査1(開封)
        if (s1 & 1) return false;                               // 工事中
        ra = a.load(std::memory_order_relaxed);
        rb = b.load(std::memory_order_relaxed);
        std::atomic_thread_fence(std::memory_order_acquire);    // 膜: データ読みが検査2を追い越さない
        unsigned s2 = seq.load(std::memory_order_relaxed);      // 検査2
        return s1 == s2;                                        // 一致すれば無傷の証明
    }
    // 利用側: while (!try_read(x, y)) ; のリトライループ
};
```

膜の座席表を確認してください。読み手側:s1のacquireが「データ読みは検査1より前に浮き上がらない」を、途中のacquireフェンスが「データ読みは検査2より後ろに沈まない」を担い、データ読みは2つの検査に**挟み込まれ**ます。書き手側:releaseフェンスが「データ書きは奇数の札より前に浮き上がらない」を、最後のreleaseストアが「偶数の札はデータ書きの後」を担い、データ書きは2枚の札に挟み込まれます。この対称な挟み込みが、「2回の番号一致=その間に工事なし」という推論を契約レベルで正当化します。ARM実機で読み手8本+書き手1本を回して、破れ(a≠bのスナップショット)ゼロ。第7.8節のリベンジ完了です。

さて、ペイロードがなぜ**relaxedアトミック**なのか。ここにseqlock最深の落とし穴があります。読み手は、工事中のデータを**読んでしまってから捨てる**ことがあります(s1≠s2で棄却する経路)。捨てるのだから無害――と思いたいところですが、C++の契約では、**捨てる読み取りも読み取りです**。素のintにすると、その「どうせ捨てる読み」と書き手の書きが、ロープなしの衝突対=データ競合=未定義動作。実害の直感でも、引き裂かれた値での一時的な演算(例:ゼロ除算)がクラッシュを起こしえます。TSanで両版を検分すると、素のint版は正しく有罪、relaxedアトミック版は無罪の判定が出ます。**「結果を使わなければ競合ではない」という直感は契約に存在しない**――seqlockが教えてくれる、最後の定義の授業です。

値打ちも計測しておきます。8読者スレッドでの総読み取りスループット:

```console
mutexで保護した読み           :  24 M reads/s (8スレッド合計)
seqlock                       : 917 M reads/s (38倍)
```

38倍の源泉は第4章の語彙で一行:**読者が共有ラインを一切ダーティにしないので、seqとa,bのラインは全読者のキャッシュにS状態で常駐し、読み取りは全部ローカルヒット**になるからです。落とし穴一覧も再掲します:検査2を忘れれば7.8節の破れ、奇数検査を忘れれば工事中読み、ペイロードを素の型にすれば未定義動作、書き手を2人にすれば札が壊れる(外部排他が必要)、読み手のリトライは書き手優先ゆえ**書き込み豪雨の下では読者が飢餓**する。適用条件(小さいデータ・読み超多数・書き稀)の外では使わない道具です。

> **観測事実32**: seqlockは「読者が共有メモリに書かない」ことで8読者時mutex比38倍(実測)にスケールする。正しさは2枚の札+2回の検査+対称な膜の挟み込みが担い、棄却される読み取りすらrelaxedアトミックでなければ契約違反になる。第7.8節の壊れたホットリロードは、この構造の欠損版だった。

## 9.6 【コード】C++20 atomic::wait/notifyでセマフォを作り、futexをstraceで観察する

最後に、9.2節で開けた「寝る」道具箱が、C++20で標準ライブラリの表玄関に来たことを確認します。`std::atomic<T>::wait(old)`は「値が`old`から変わるまで効率よく待つ」、`notify_one/notify_all`は「この変数で寝ている者を起こす」。Linux実装の裏側はまさにfutexです。これでOS依存のsyscall包みなしに、待機つきプリミティブが書けます。総仕上げとして、計数セマフォを自作します。

**リスト9-7: semaphore.cpp ― atomic::waitで作る計数セマフォ**

```cpp
class Semaphore {
    std::atomic<int> n;
public:
    explicit Semaphore(int init) : n(init) {}

    void release(int k = 1) {                        // 資源を返す(V操作)
        n.fetch_add(k, std::memory_order_release);   // 封: 資源に伴う成果物を荷札ごと渡す
        if (k == 1) n.notify_one();
        else        n.notify_all();
    }
    void acquire() {                                 // 資源を取る(P操作)
        int cur = n.load(std::memory_order_relaxed);
        for (;;) {
            while (cur == 0) {
                n.wait(0, std::memory_order_relaxed);   // 0のままなら寝る(9.2節のwaitと同じ意味論)
                cur = n.load(std::memory_order_relaxed);
            }
            if (n.compare_exchange_weak(cur, cur - 1,
                                        std::memory_order_acquire))
                return;                              // 開封: 減算成功=資源(と成果物)の受領
        }
    }
};
```

設計の読みどころは、これまでの章の再演として全部説明がつきます。`wait(0)`の意味論は「**まだ0なら**寝る」――9.2節のfutex_waitの条件節そのもので、lost wakeupを同じ理屈で封じます。目覚めてからの再検査ループは「目覚めは資格ではなく挑戦権」(9.2節)と、偽の目覚めが仕様上許される(condition_variableと同じ規律)ことの両方に対応します。CASはweak(ループの中なので、第6.3節の指針どおり)。オーダーはrelease(返却=封)/acquire(受領成功=開封)で、「資源と一緒にその資源で作った成果物の可視性を渡す」MP構図です。

straceで裏取りします。生産者1・消費者1で、(a) 消費者が常に待たされる枯渇シナリオと、(b) 資源が常に潤沢なシナリオを比較:

```console
$ strace -f -e futex ./sem_demo --starve        # (a) 枯渇
futex(0x4040a0, FUTEX_WAIT_PRIVATE, 0, NULL) = 0     # n.wait(0) の正体
futex(0x4040a0, FUTEX_WAKE_PRIVATE, 1)      = 1     # n.notify_one() の正体
...
$ strace -f -e futex ./sem_demo --plenty        # (b) 潤沢
(futexの行なし)                                       # 高速路のみ。waitは値を見て即帰還
```

なお、この自作品の完成形は標準に既にあります――`std::counting_semaphore` / `std::binary_semaphore`(C++20)。同期の始動・合流にはさらに`std::latch`(使い捨てのカウントダウン)と`std::barrier`(再利用可能な集合点)が加わり、本書のベンチマークハーネスの「go/done」(第2章)も、現代的にはlatch/barrierで書き直せます(演習6)。**車輪は既製品を使う。ただし、いまや私たちは全既製品の内側を、futexの条件節1個まで遡って説明できる**――それがこの章の到達点です。

### 第9章のまとめ

- **観測事実29**: スピンロックの二大病巣は「RMWでの待機によるライン引きずり回し」と「解放時の挑戦の雪崩」。TTAS(待つときは読む)+指数バックオフ(敗者は下がる)でTAS比6倍。ただしバックオフは公平性を売る(チケット/MCSが買い戻す)。
- **観測事実30**: futexは「非競合はユーザー空間CAS1発・syscallゼロ、競合時のみカーネルで就寝」。lost wakeupはカーネル内の値再確認が封じ、3状態設計は不要なwakeを撃たない会計。std::mutexはこの産業版であり、スピンとの優劣はワークロードの仮定(CS長・オーバーサブスクリプション)で反転する。
- **観測事実31**: DCLPの故障は書き手側Store→Store(構築前の公開)。ARMで発火・x64は3億回無傷という「発明が信じられた理由」ごと再現した。修正はポインタへのrelease/acquire、x64ホットパスの機械語は不変。
- マジックスタティックは、コンパイラが自動生成する監査済みDCLP(ガードのacquireロード=ARMではldarb、低速路は__cxa_guard=futex族)。遅延初期化の第一選択(9.4節)。
- **観測事実32**: seqlockは読者無書き込みにより38倍スケール。正しさは2枚の札・2回の検査・対称な膜。棄却される読みもrelaxedアトミック必須(「捨てる読みも読み」)。7.8節はこの欠損版だった。
- atomic::wait/notify(C++20)はfutexの標準玄関。自作セマフォの全設計判断(条件付き就寝・挑戦権・weak CAS・release/acquire)が本書前半の再演で説明できる(9.6節)。
