# 第16章 メモリの中身を塗りつぶす 〔v0.11〕

---

## この章のゴール

ここまでの2章は「数を数える」話でした。この章から **「壊れているかどうかを見つける」** 話に移ります。

やることは単純です。

- 確保した領域を `0xCD` で埋める
- `Reset()` / `Rewind()` で捨てた領域を `0xDD` で埋める
- パディングで無駄になった部分を `0xAB` で埋める

これだけで、次の2種類のバグが **一瞬で見つかるようになります**。

**初期化を忘れて読んでいるバグ。** 値が `-842150451` という異様な数字になります。

**`Reset()` 後の古いポインタを使っているバグ。** 第8章で「アクセス違反にならないので手がかりがない」と書いた、あの問題です。

第3章で作った `DumpBytes` が、ここでようやく本領を発揮します。

---

## 16.1 なぜ塗りつぶすのか

### 問題1:確保直後の中身は「前のゴミ」

第8章で確認したとおり、`Reset()` は中身を消しません。次に確保した領域には、前の周期のデータがそのまま残っています。

```cpp
auto r = arena.NewArrayUninit<int>(10);
std::println("{}", (*r)[0]);   // 何が出るか?
```

**答えは「前に何が入っていたかによる」です。**

たちが悪いのは、**それらしい値が出てしまうこと** です。前フレームに座標が入っていれば、それらしい浮動小数点数が読めます。カウンタが入っていれば、それらしい整数が読めます。「初期化を忘れているのに、なんとなく動いているように見える」——最悪のパターンです。

そして本番環境や、別のタイミングで実行したときに、突然おかしくなります。

### 問題2:リセット後のポインタが「使えてしまう」

第8章の実演を思い出してください。

```cpp
int* p = /* 確保して 42 を書いた */;
arena.Reset();
int* q = /* もう一度確保 */;
*q = 99;

std::println("{}", *p);   // → 99
```

`p` は板の内側を指しています。有効なアドレスなので、アクセス違反は起きません。**読めてしまう。** しかも読めた値は、まったく別のデータのものです。

### 解決:ありえない値で埋める

どちらの問題も、根は同じです。**「無効なメモリ」と「有効なメモリ」が区別できない。**

区別できるようにします。無効な領域を、**明らかにおかしいと分かる値** で埋めておくのです。

```
初期化を忘れて読んだ  → -842150451  (0xCDCDCDCD)
リセット後に読んだ    → -572662307  (0xDDDDDDDD)
```

こういう数字が出たら、それは「たまたまそういう値だった」のではなく、**バグの証拠** です。

## 16.2 なぜ `0xCD` と `0xDD` なのか

この2つの値は、私たちの発明ではありません。**MSVC のデバッグヒープが昔から使っているパターン** です。

| 値 | 意味 | 誰が使うか |
|---|---|---|
| `0xCD` | Clean Memory:確保したが未初期化 | CRT デバッグヒープ |
| `0xDD` | Dead Memory:解放済み | CRT デバッグヒープ |
| `0xFD` | No Man's Land:確保領域の前後の番兵 | CRT デバッグヒープ |
| `0xCC` | 未初期化のスタック領域 | `/RTC1` 有効時 |
| `0xAB` | Windows ヒープの確保領域の後ろ | デバッグヒープ |
| `0xFE` / `0xFEEEFEEE` | `HeapFree` された領域 | Windows ヒープ |
| `0xBAADF00D` | `LocalAlloc` の未初期化領域 | Windows |

**同じ値を使う理由は、既存の知識がそのまま通じるからです。**

C++ 開発者の多くは、デバッガで `0xCDCDCDCD` を見た瞬間に「未初期化だ」と分かります。私たちのアロケーターが独自のパターンを使ったら、その勘が働きません。**慣習に合わせることに価値があります。**

### なぜこれらの値が選ばれたのか

適当に決められたわけではありません。良いパターンには条件があります。

**1. ゼロではない。** ゼロは「たまたま正しい値」であることが多すぎます。`nullptr` チェックもすり抜けます。

**2. 奇数である。** `0xCD` は奇数です。4バイト並べた `0xCDCDCDCD` も奇数です。これをポインタとして使うと、**アラインメント違反になります**。第6章で見たとおり、多くの型は偶数アドレスを要求するので、早い段階で問題が表面化します。

**3. ポインタとして無効。** 64ビット環境で `0xCDCDCDCDCDCDCDCD` は、正規のアドレス範囲(canonical address)の外です。触った瞬間にアクセス違反になります。

**4. 目立つ。** メモリダンプで `cd cd cd cd` が並んでいれば、一目で分かります。`00 00 00 00` や `01 02 03 04` では気づけません。

**5. ASCII 文字ではない。** 文字列として表示しても意味のある文字にならないので、文字列バッファの未初期化にも気づけます。

## 16.3 どこを、いつ塗るか

3か所あります。

```
        ┌──────────┬────────────────┬──────────────────────┐
        │ padding  │  確保した領域   │      まだ未使用       │
        │  0xAB    │     0xCD       │                      │
        └──────────┴────────────────┴──────────────────────┘
```

**確保時。** アラインメントのために捨てたパディング部分を `0xAB`、返す領域を `0xCD` で埋めます。

**`Reset()` / `Rewind()` 時。** 捨てる範囲を `0xDD` で埋めます。

### パディングを別の色にする理由

`0xAB` は必須ではありませんが、あると便利です。メモリダンプを見たとき、**アラインメントで捨てられた部分が視覚的に分かります**。

```
ab ab ab ab cd cd cd cd cd cd cd cd 00 00 00 00
^^^^^^^^^^^ 4バイト無駄にしている
```

第6章で `Padding()` の合計値は取れるようにしましたが、「どこで無駄が出たか」までは分かりませんでした。塗り分ければ一目です。

### 順序に注意:破棄が先、塗りつぶしが後

`Reset()` の中で、第11章のファイナライザ実行と塗りつぶしの順序を間違えてはいけません。

```cpp
    void Reset() noexcept
    {
        RunFinalizersUntil(nullptr);        // ① デストラクタを呼ぶ
        FillPattern(...);                   // ② 塗りつぶす
        // ...
    }
```

逆にすると、**まだ生きているオブジェクトを `0xDD` で塗りつぶしてから、そのデストラクタを呼ぶ** ことになります。`std::string` のデストラクタが `0xDDDDDDDD` というアドレスを解放しようとして、即座にクラッシュします。

第11章で「破棄を先に、巻き戻しを後に」と書いたのと同じ話です。**片づけの処理は、常に順序が命です。**

## 16.4 実装する 〔v0.11〕

### パターンの定義

```cpp
// ga/Pattern.h
#pragma once

#include <cstddef>
#include <cstring>

namespace ga
{
    inline constexpr std::byte kPatternAllocated{ 0xCD };   // 確保直後(未初期化)
    inline constexpr std::byte kPatternFreed    { 0xDD };   // 破棄済み
    inline constexpr std::byte kPatternPadding  { 0xAB };   // アラインメントの詰め物

    // 大きすぎる領域を全部塗ると Debug が実用にならないので、上限を設ける
    inline constexpr std::size_t kMaxPatternFillBytes = 64 * 1024;

    inline void FillPattern(void* p, std::size_t size, std::byte pattern) noexcept
    {
        if (size == 0) { return; }

        const std::size_t n = (size < kMaxPatternFillBytes) ? size : kMaxPatternFillBytes;

        std::memset(p, std::to_integer<int>(pattern), n);
    }
}
```

### 有効・無効の切り替え

```cpp
// ga/Core.h
#ifndef GA_ENABLE_MEMORY_PATTERN
#  ifdef NDEBUG
#    define GA_ENABLE_MEMORY_PATTERN 0
#  else
#    define GA_ENABLE_MEMORY_PATTERN 1
#  endif
#endif
```

> **この機能はメンバ変数を増やしません。** 第9章と第14章で注意した「構成によってクラスのサイズが変わる」問題は、ここでは起きません。処理を消すだけなので、安全に `#if` で切り替えられます。
>
> **消してよい機能と、消すと危険な機能がある** ということです。判断基準は「クラスのレイアウトが変わるか」です。

### `Allocate()` に組み込む

```cpp
        // ... 検査を通過した後 ...

        offset_   = alignedOffset + size;
        padding_ += padding;

        void* result = reinterpret_cast<void*>(aligned);

#if GA_ENABLE_MEMORY_PATTERN
        FillPattern(reinterpret_cast<void*>(current), padding, kPatternPadding);
        FillPattern(result, size, kPatternAllocated);
#endif

        RecordAllocation(result, size, alignment, padding, loc);
        return result;
```

### `Reset()` と `Rewind()` に組み込む

```cpp
    void Reset() noexcept
    {
        RunFinalizersUntil(nullptr);

#if GA_ENABLE_MEMORY_PATTERN
        FillPattern(buffer_.data(), offset_, kPatternFreed);
#endif

        // ... 統計とオフセットのクリア ...
    }

    void Rewind(const Marker& m) noexcept
    {
        // ... 検査 ...

        RunFinalizersUntil(m.finalizers);

#if GA_ENABLE_MEMORY_PATTERN
        FillPattern(buffer_.data() + m.offset, offset_ - m.offset, kPatternFreed);
#endif

        // ... オフセットの復元 ...
    }
```

`Rewind()` では、巻き戻す範囲 `[m.offset, offset_)` だけを塗ります。マーカーより手前は生きているので、触ってはいけません。

## 16.5 実演1:未初期化を読んでいるバグ

第12章で作った `NewArrayUninit` を使います。この関数は、意図的に初期化を省くものでした。

```cpp
#include "ga/Allocator.h"

int main()
{
    ga::Bump arena(4096);

    auto r = arena.NewArrayUninit<int>(8);
    std::span<int> values = *r;

    std::println("--- 初期化せずに読む ---");
    for (int v : values)
    {
        std::println("  {}", v);
    }

    std::println("");
    std::println("--- バイト列 ---");
    DumpBytes(values.data(), values.size_bytes());
}
```

Debug 構成での出力です。

```
--- 初期化せずに読む ---
  -842150451
  -842150451
  -842150451
  -842150451
  -842150451
  -842150451
  -842150451
  -842150451

--- バイト列 ---
cd cd cd cd cd cd cd cd cd cd cd cd cd cd cd cd
cd cd cd cd cd cd cd cd cd cd cd cd cd cd cd cd
```

**`-842150451` が並びました。** これは `0xCDCDCDCD` を符号付き32ビット整数として読んだ値です。

塗りつぶす前は、たまたまゼロだったり、それらしい値だったりして気づけませんでした。いまは、**この数字を見た瞬間に「初期化を忘れている」と分かります**。

### 型による見え方

| 読み方 | 値 |
|---|---|
| `int`(32ビット) | `-842150451` |
| `unsigned` | `3452816845` |
| `float` | 約 `-4.32e+08` |
| `double` | 約 `-9.26e+61` |
| `char*` | 非 ASCII の文字化け |
| ポインタ | `0xCDCDCDCDCDCDCDCD` → **触ると即アクセス違反** |

**覚えておくべきは `-842150451`(`int`)と `0xCDCDCDCD` の2つ** です。デバッガのウォッチ窓でこれを見たら、初期化漏れを疑ってください。

### `float` の場合が特に有用

浮動小数点数で `-4.32e+08` という値が出たら、明らかにおかしいと分かります。座標や速度としてありえない大きさです。しかもゼロではないので、`if (x == 0.0f)` のような検査をすり抜けます。

**「巨大でおかしな float」は、未初期化の典型的なサインです。**

## 16.6 実演2:リセット後のポインタ

第8章の危険なコードを、もう一度実行します。

```cpp
int main()
{
    ga::Bump arena(1024);

    auto r1 = arena.New<int>(42);
    int* p = *r1;

    std::println("リセット前 : *p = {}", *p);

    arena.Reset();

    std::println("リセット後 : *p = {}", *p);
}
```

**第8章(v0.4)での出力:**

```
リセット前 : *p = 42
リセット後 : *p = 42        ← 何も起きていないように見える
```

**v0.11 での出力:**

```
リセット前 : *p = 42
リセット後 : *p = -572662307
```

`-572662307` は `0xDDDDDDDD` です。

**「まだ使えている」という錯覚が消えました。**

第8章では「アクセス違反にならないので手がかりがない」と書きました。手がかりができました。この数字が見えたら、**リセット済みの領域を触っている** ということです。

### 構造体でも同じ

```cpp
struct Enemy { int hp; float x, y; };

auto r = arena.New<Enemy>();
Enemy* e = *r;
e->hp = 100;

arena.Reset();

std::println("hp = {}, x = {}", e->hp, e->x);
```

```
hp = -572662307, x = -1.99e+18
```

**すべてのメンバがおかしくなります。** 1つでも気づけば、原因にたどり着けます。

### テストとして固定する

```cpp
void Test_ResetFillsWithDeadPattern()
{
#if GA_ENABLE_MEMORY_PATTERN
    ga::Bump arena(256);

    auto r = arena.Allocate(16, 1);
    assert(r.has_value());

    std::byte* p = static_cast<std::byte*>(*r);
    std::memset(p, 0x11, 16);

    arena.Reset();

    for (std::size_t i = 0; i < 16; ++i)
    {
        assert(p[i] == ga::kPatternFreed);
    }

    std::println("[ OK ] Test_ResetFillsWithDeadPattern");
#endif
}
```

`#if` で囲んでいるのは、Release 構成ではこのテストが成立しないためです。**テストも構成に応じて切り替える必要がある** ことに注意してください。

## 16.7 コストを測る

塗りつぶしはタダではありません。**確保サイズに比例します。**

### 小さい確保

```
v0.10 (塗りつぶしなし)   median=      4.3  p95=      4.5  max=        6.1
v0.11 (塗りつぶしあり)   median=      6.9  p95=      7.2  max=        9.8
```

16 バイトの確保で **+2.6 ns**。`memset` の呼び出しコストが支配的です。

### 大きい確保

```
1 MB の確保 (塗りつぶしなし)   median=    120.0 ns
1 MB の確保 (塗りつぶしあり)   median=  28400.0 ns
```

**236 倍。** メモリ帯域で決まる時間なので、これ以上速くはできません。

`kMaxPatternFillBytes` で上限(64 KB)を設けているのは、このためです。上限なしなら、1 MB の確保に 28 µs ではなく、もっとかかっていました。

> **上限を設けると、64 KB を超える部分は塗られません。** 検出漏れの可能性が生まれます。トレードオフです。上限を大きくすれば検出率は上がり、Debug ビルドは遅くなります。プロジェクトに合わせて調整してください。

### `Reset()` のコスト

これが最も影響の大きい部分です。

```
8 MB 使用後の Reset (塗りつぶしなし)   median=      0.0 ns
8 MB 使用後の Reset (塗りつぶしあり)   median= 412000.0 ns
```

**412 マイクロ秒。**

第8章で「`Reset()` は O(1)」と誇りましたが、**塗りつぶしを入れると O(n) に戻ります**。第11章のファイナライザに続いて、2度目です。

| | `Reset()` の計算量 |
|---|---|
| v0.4(素の Bump) | O(1) |
| v0.7(ファイナライザ) | O(登録数) |
| **v0.11(塗りつぶし)** | **O(使用バイト数)** |

**だから Release では消します。** デバッグ機能の価値は、開発中にバグを見つけることであって、製品の性能ではありません。

## 16.8 落とし穴

### 「たまたま動いていた」コードが壊れる

塗りつぶしを有効にした途端、これまで動いていたコードが落ち始めることがあります。

**それは退化ではなく、発見です。**

もともと未初期化のメモリに依存していたコードが、ゼロで埋まっていたおかげで偶然動いていた。塗りつぶしによって、その依存が表面化しただけです。

いま直せば、本番環境で起きるはずだった障害を1つ潰したことになります。

### Debug と Release で挙動が変わる

これは承知の上で受け入れます。「Debug では落ちるが Release では動く」という状況は不安ですが、逆(Release だけで落ちる)よりはるかにましです。

ただし、**Debug でしか検出できない** という限界も意味します。より強力な手段が必要なら、

- 第17章:ガードバイト(はみ出しの検出)
- 第31章:ガードページ(`VirtualAlloc` による、Release でも使える保護)
- 第36章:AddressSanitizer(最も強力。ただし遅い)

と段階が用意されています。

### 値初期化との二度手間

第12章の `NewArray<T>` は値初期化を行います。塗りつぶしと合わせると、

1. `0xCD` で埋める
2. ゼロで埋める

という二度手間になります。Debug ビルドが遅くなる一因です。

`NewArrayUninit<T>` なら塗りつぶしだけで済み、しかも **初期化漏れを検出できる** ようになります。皮肉なことに、「速いから危ない」はずの関数が、Debug では「安全側」になります。

namespace ga
{

## 次章の予告

塗りつぶしは、**間違ったメモリを読んでいる** ことを教えてくれます。しかし、**書き込みのはみ出し** は検出できません。

```cpp
auto r = arena.NewArray<int>(10);
(*r)[10] = 1;   // ← 1つ外に書いた。誰も気づかない
```

書き込んだ先は、次の確保が使う領域です。塗りつぶしのパターンが上書きされるだけで、警告は出ません。

第17章では **ガードバイト**(カナリア)を入れます。確保領域の前後に見張り番のバイト列を置き、`Reset()` のときに壊れていないか検査します。

```
┌────────┬──────────────────┬────────┐
│ 0xFD×8 │  ユーザーの領域   │ 0xFD×8 │
└────────┴──────────────────┴────────┘
  番兵                          番兵
```

炭鉱のカナリアと同じ発想です。壊れやすいものをわざと置いて、異変を知らせる。第16章と第17章がそろって、はじめて「読み」と「書き」の両方を見張れるようになります。

---

> **コラム:16進数で読める単語たち**
>
> `0xDEADBEEF` を見たことがあるでしょうか。16進数は `0` から `9` と `A` から `F` しか使えませんが、この範囲でも英単語がいくつか作れます。プログラマは古くから、この遊びを実用に使ってきました。
>
> | 値 | 読み | 使われる場所 |
> |---|---|---|
> | `0xDEADBEEF` | dead beef | 汎用の「無効値」。IBM 系が起源とされる |
> | `0xBAADF00D` | bad food | Windows の `LocalAlloc` 未初期化領域 |
> | `0xFEEDFACE` | feed face | Mach-O 実行ファイルの識別子 |
> | `0xCAFEBABE` | cafe babe | Java のクラスファイルの先頭 |
> | `0xDEADC0DE` | dead code | 到達しないはずのコード |
> | `0x8BADF00D` | ate bad food | iOS のクラッシュレポート(起動タイムアウト) |
>
> なぜ、わざわざ読める値を選ぶのか。**人間が認識しやすいから** です。
>
> メモリダンプを眺めているときに `0x4A7B2C91` が見えても、それが意味のある値なのかゴミなのか判断できません。しかし `DE AD BE EF` が並んでいたら、誰かが意図的に置いた印だと即座に分かります。
>
> ---
>
> MSVC の `0xCD` / `0xDD` / `0xFD` は、読める単語ではありません。しかし別の合理性があります。
>
> **1バイトのパターンとして最適化されている** のです。`memset` は1バイトの値を繰り返すので、`0xCD` を指定すれば `0xCDCDCDCD` にも `0xCDCDCDCDCDCDCDCD` にもなります。どんな型で読んでも、ちゃんとおかしな値になります。
>
> `0xDEADBEEF` を使おうとすると、4バイト単位で書く必要があり、`memset` が使えません。サイズが4の倍数でない場合の扱いも面倒です。**実装の単純さが、覚えやすさに勝った** 例と言えます。
>
> ---
>
> ちなみに、`0xCC` にも由来があります。x86 の機械語で `0xCC` は **`int 3`、つまりブレークポイント命令** です。
>
> 未初期化のスタック領域が `0xCC` で埋まっていれば、そこに間違って処理が飛び込んだ瞬間にデバッガが止まります。**「ゴミデータが、そのままトラップになる」** という、たいへん美しい設計です。
>
> Visual Studio が `/RTC1` オプションでスタックを `0xCC` で埋めるのは、この効果を狙ってのことです。私たちが `0xCD` を選んだのは、単に「確保済みメモリ」の慣習に従っただけですが、こうした先人の工夫を知っておくと、自分でパターンを設計するときの参考になります。
