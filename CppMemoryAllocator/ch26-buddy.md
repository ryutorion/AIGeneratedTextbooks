# 第26章 2の冪で揃える 〔v0.19:バディアロケーター〕

---

## この章のゴール

第25章の設計 C——「サイズを2の冪に丸める」——は、探索を最速にし、外部断片化も最小にしました。代償は内部断片化 23.7% でした。

**この方式を、もう一歩推し進めます。**

バディシステムでは、ブロックのサイズを 2 の冪だけに限定します。すると、次のことが起きます。

- **分割**:大きいブロックを、必要なサイズになるまで半分ずつ割る
- **統合**:割ってできた2つの相方(バディ)が両方空きになったら、くっつけて元に戻す

そして最大の特徴——

```cpp
buddy = offset ^ size;
```

**相方の位置が、排他的論理和1回で分かります。** 境界タグも、フッタも、フラグも要りません。

- バディの原理と、XOR で相方が求まる理由
- **ビットツリー** で全ブロックの状態を持つ 〔**v0.19**〕
- **確保ごとのヘッダが不要になる** という、他の方式にない性質
- 内部断片化を理論値と実測の両方で見積もる
- GPU メモリで今も現役である理由

---

## 26.1 2の冪だけにする

板全体のサイズを 2 の冪にします。ここでは 1 MB としましょう。最小ブロックは 32 バイトです。

```
          1 MB                              ← order 15
      ┌────┴────┐
    512K      512K                          ← order 14
   ┌──┴──┐   ┌──┴──┐
  256K  256K 256K  256K                     ← order 13
    ...        ...
    32    32   32    32    ...              ← order 0
```

**完全二分木です。** 各ノードは、親を半分に割ったもの。

「order」は、そのブロックの大きさを表します。

```
order k のブロックサイズ = 32 << k
```

| order | サイズ |
|---|---|
| 0 | 32 バイト |
| 1 | 64 |
| 2 | 128 |
| ... | ... |
| 15 | 1 MB |

### 確保の手順

100 バイトが欲しいとします。

1. 32 以上の 2 の冪に切り上げ → **128 バイト**(order 2)
2. order 2 の空きを探す。なければ order 3 を探す。それもなければ order 4……
3. order 5(1024 バイト)に空きが見つかったとする
4. **半分に割る**。1024 → 512 が2つ。片方を空きリストへ、片方をさらに割る
5. 512 → 256 が2つ。片方を空きリストへ
6. 256 → 128 が2つ。片方を空きリストへ、**もう片方を返す**

**割り下げていくだけです。** 探索は「空でない order を見つける」だけで、ブロックの中を探す必要はありません。

## 26.2 相方は XOR で分かる

バディシステムの核心です。

板の先頭からのオフセットで考えます。order 2(128 バイト)のブロックが、オフセット 384 にあるとします。

```
オフセット 384 = 0b0001'1000'0000
サイズ     128 = 0b0000'1000'0000
                          ↑ このビットが「どちらの半分か」を表す
```

**このビットを反転すれば、相方のオフセットです。**

```
384 ^ 128 = 0b0001'0000'0000 = 256
```

オフセット 256 と 384 のブロックが、バディの関係にあります。

```
┌───────────────────────────────┐
│         256 バイト(order 3)   │
│      オフセット 256 から        │
├───────────────┬───────────────┤
│  128 (256〜)  │  128 (384〜)  │
└───────────────┴───────────────┘
      ↑ 相方 ↑
```

### なぜこれで正しいのか

order k のブロックは、必ず **サイズの倍数のオフセット** に置かれます。

```
order 2(128 バイト)のブロックのオフセット:
  0, 128, 256, 384, 512, ...
  → 下位 7 ビットは必ず 0
```

そして、親(order 3、256 バイト)は 256 の倍数のオフセットにあります。親の中の2つの子は、**ビット7(128 の位)だけが違います**。

```
親のオフセット   : xxxx'x000'0000
子のオフセット   : xxxx'x000'0000 (左) / xxxx'x100'0000 (右)
                            ↑ここだけ違う
```

**XOR は、まさにこのビットを反転する操作です。**

### 何が要らなくなったか

第24章で境界タグを導入したのは、**前の隣のブロックがどこから始まるか分からなかった** からでした。可変サイズだと、後ろに歩くことしかできません。

**バディなら計算で分かります。** ヘッダも、フッタも、フラグも要りません。

```
第24章の FreeList : ブロックごとに 16 バイトのヘッダ
バディ             : ヘッダなし
```

32 バイトの確保をすると、

| | 実際に消費するバイト |
|---|---|
| FreeList(第25章) | 16(ヘッダ)+ 32 = **48** |
| Buddy | **32** |

**小さい確保では、バディのほうが効率的です。**(ただし、後で述べる別のオーバーヘッドがあります)

## 26.3 分割と統合の対称性

バディシステムが「美しい」と言われるのは、**確保と解放が完全に対称** だからです。

```
確保:  1024 → 512 + 512 → 256 + 256 → 128 + 128 → 使う
解放:  使い終わる → 128 + 128 → 256 → 512 → 1024
```

**分割の逆をたどるだけです。**

統合の条件も単純です。

> **相方が空きなら、くっつける。くっついたら、その親についても同じことを繰り返す。**

第24章の合体では「前と後ろ」の2方向を別々に扱いました。バディでは方向を気にする必要がありません。**相方は1つだけ** です。

### ただし、条件は厳しい

第24章の合体は、隣り合っていれば何とでもくっつきました。

**バディは、決まった相手としかくっつきません。**

```
┌───────┬───────┬───────┬───────┐
│   A   │   B   │   C   │   D   │
└───────┴───────┴───────┴───────┘
  └─相方─┘       └─相方─┘

B と C は隣同士だが、相方ではない
→ 両方空きでも、統合されない
```

**これが、バディの外部断片化の原因になります。** 空きが隣り合っていても、ペアが揃わなければ大きくなりません。

代わりに、統合が **必ず元のサイズに戻る** ことが保証されます。全部解放すれば、必ず 1 MB の1ブロックに戻ります。中途半端な形で固まることがありません。

## 26.4 ビットツリーで状態を持つ

ヘッダを持たない代わりに、**すべてのノードの状態を、別のところにまとめて持ちます**。

二分木のノードに、配列の添字を振ります。

```
          1                    ← 根(order 15)
      ┌───┴───┐
      2       3                ← order 14
    ┌─┴─┐   ┌─┴─┐
    4   5   6   7              ← order 13
```

**ヒープ(二分ヒープ)と同じ番号付けです。** ノード `n` の子は `2n` と `2n+1`。

### ノード番号の求め方

```cpp
    std::size_t NodeIndex(std::size_t offset, std::size_t order) const noexcept
    {
        const std::size_t level = maxOrder_ - order;              // 根が 0
        return (std::size_t{1} << level) + (offset >> (kMinShift + order));
    }
```

`offset >> (kMinShift + order)` は、そのレベルでの何番目かを表します。レベルの先頭番号 `2^level` を足せば、通し番号になります。

### 2つのビット列

```cpp
    std::vector<std::uint64_t> splitBits_;   // このノードは分割されているか
    std::vector<std::uint64_t> freeBits_;    // このノードは空きリストに入っているか
```

| `split` | `free` | 意味 |
|---|---|---|
| 0 | 1 | **空きブロック**(このサイズのまま空いている) |
| 0 | 0 | **使用中のブロック** |
| 1 | 0 | 分割済み(子を見る) |
| 1 | 1 | ありえない |

### 解放時に order が分かる

`Free(p)` には、サイズが渡されません。**ビットツリーを根から降りて調べます。**

```cpp
    std::size_t order = maxOrder_;
    std::size_t node  = 1;

    while (TestBit(splitBits_, node))
    {
        --order;
        node = node * 2 + ((offset >> (kMinShift + order)) & 1);
    }
    // ここで node は、offset を含む未分割のノード = 求めるブロック
```

分割されているノードは、そこが「答え」ではありません。子のどちらに `offset` が含まれるかを選んで降りていきます。

**使用中のブロックは決して分割されていない** ので、必ず止まります。ループ回数は最大 `maxOrder_` 回、1 MB なら 15 回です。

### オーバーヘッドの計算

```
容量 1 MB、最小ブロック 32 バイト:
  葉の数     = 1 MB / 32 = 32,768
  ノード総数 = 65,536
  ビット列   = 65,536 ビット × 2 = 16 KB

  → 1 MB に対して 1.56%
```

**確保のたびに 16 バイト払う FreeList と比べてみます。**

| 確保サイズ | FreeList のオーバーヘッド | Buddy のオーバーヘッド |
|---|---|---|
| 32 バイト × 32,768 個 | 512 KB(50%) | 16 KB(**1.56%**) |
| 4 KB × 256 個 | 4 KB(0.4%) | 16 KB(1.56%) |

**小さい確保が多いほど、バディが有利です。**

## 26.5 実装する 〔v0.19〕

```cpp
// ga/Buddy.h
#pragma once

#include "ga/Core.h"

#include <bit>
#include <cstddef>
#include <vector>

namespace ga
{
    class Buddy
    {
    public:
        static constexpr std::size_t kMinBlock = 32;
        static constexpr std::size_t kMinShift = 5;    // log2(32)

        // capacity は 2 の冪であること
        explicit Buddy(std::size_t capacity)
            : buffer_(capacity + 64)
            , capacity_(capacity)
        {
            assert(std::has_single_bit(capacity));
            assert(capacity >= kMinBlock);

            const auto raw = reinterpret_cast<std::uintptr_t>(buffer_.data());
            base_ = reinterpret_cast<std::byte*>(AlignUp(raw, 64));

            maxOrder_ = static_cast<std::size_t>(std::bit_width(capacity)) - 1 - kMinShift;

            freeLists_.assign(maxOrder_ + 1, nullptr);

            const std::size_t nodeCount = std::size_t{2} << maxOrder_;
            splitBits_.assign((nodeCount + 63) / 64, 0);
            freeBits_.assign((nodeCount + 63) / 64, 0);

            PushFree(base_, maxOrder_);          // 板全体が1つの空きブロック
        }

        [[nodiscard]] void* Allocate(std::size_t size) noexcept
        {
            if (size == 0) { return nullptr; }

            const std::size_t need = std::bit_ceil(size < kMinBlock ? kMinBlock : size);
            if (need > capacity_) { return nullptr; }

            const std::size_t order =
                static_cast<std::size_t>(std::bit_width(need)) - 1 - kMinShift;

            // 空きのある order を探す
            std::size_t k = order;
            while (k <= maxOrder_ && freeLists_[k] == nullptr) { ++k; ++searchSteps_; }

            if (k > maxOrder_) { ++failures_; return nullptr; }

            std::byte* block = reinterpret_cast<std::byte*>(freeLists_[k]);
            UnlinkFree(block, k);

            // order まで割り下げる
            while (k > order)
            {
                SetBit(splitBits_, NodeIndex(Offset(block), k));
                --k;

                std::byte* buddy = block + (kMinBlock << k);
                PushFree(buddy, k);
            }

            internalWaste_ += (kMinBlock << order) - size;
            ++liveCount_;

            return block;
        }

        void Free(void* p) noexcept
        {
            if (p == nullptr) { return; }

            std::byte* block = static_cast<std::byte*>(p);
            if (block < base_ || block >= base_ + capacity_) { ReportError(p); return; }

            std::size_t offset = Offset(block);

            // --- ビットツリーを降りて order を求める ---
            std::size_t order = maxOrder_;
            std::size_t node  = 1;

            while (TestBit(splitBits_, node))
            {
                --order;
                node = node * 2 + ((offset >> (kMinShift + order)) & 1);
            }

            if (TestBit(freeBits_, node))  { ReportError(p); return; }   // 二重解放
            if (offset % (kMinBlock << order) != 0) { ReportError(p); return; }

            --liveCount_;

            // --- 相方と統合していく ---
            while (order < maxOrder_)
            {
                const std::size_t size        = kMinBlock << order;
                const std::size_t buddyOffset = offset ^ size;          // ← ここが核心
                const std::size_t buddyNode   = NodeIndex(buddyOffset, order);

                if (!TestBit(freeBits_, buddyNode)) { break; }          // 相方が空きでない

                UnlinkFree(base_ + buddyOffset, order);

                offset &= ~size;                                        // 親の先頭へ
                ++order;

                ClearBit(splitBits_, NodeIndex(offset, order));
                ++mergeCount_;
            }

            PushFree(base_ + offset, order);
        }

    private:
        struct Link { Link* prev; Link* next; };

        std::size_t Offset(const std::byte* p) const noexcept
        {
            return static_cast<std::size_t>(p - base_);
        }

        std::size_t NodeIndex(std::size_t offset, std::size_t order) const noexcept
        {
            const std::size_t level = maxOrder_ - order;
            return (std::size_t{1} << level) + (offset >> (kMinShift + order));
        }

        static bool TestBit(const std::vector<std::uint64_t>& v, std::size_t i) noexcept
        {
            return (v[i >> 6] >> (i & 63)) & 1u;
        }
        static void SetBit(std::vector<std::uint64_t>& v, std::size_t i) noexcept
        {
            v[i >> 6] |= (std::uint64_t{1} << (i & 63));
        }
        static void ClearBit(std::vector<std::uint64_t>& v, std::size_t i) noexcept
        {
            v[i >> 6] &= ~(std::uint64_t{1} << (i & 63));
        }

        void PushFree(std::byte* p, std::size_t order) noexcept
        {
            Link* l = reinterpret_cast<Link*>(p);
            l->prev = nullptr;
            l->next = freeLists_[order];

            if (l->next != nullptr) { l->next->prev = l; }
            freeLists_[order] = l;

            SetBit(freeBits_, NodeIndex(Offset(p), order));
        }

        void UnlinkFree(std::byte* p, std::size_t order) noexcept
        {
            Link* l = reinterpret_cast<Link*>(p);

            if (l->prev != nullptr) { l->prev->next = l->next; }
            else                    { freeLists_[order] = l->next; }

            if (l->next != nullptr) { l->next->prev = l->prev; }

            ClearBit(freeBits_, NodeIndex(Offset(p), order));
        }

        std::vector<std::byte>     buffer_;
        std::byte*                 base_     = nullptr;
        std::size_t                capacity_ = 0;
        std::size_t                maxOrder_ = 0;

        std::vector<Link*>         freeLists_;
        std::vector<std::uint64_t> splitBits_;
        std::vector<std::uint64_t> freeBits_;

        std::size_t liveCount_     = 0;
        std::size_t internalWaste_ = 0;
        std::size_t searchSteps_   = 0;
        std::size_t mergeCount_    = 0;
        std::size_t failures_      = 0;
    };
}
```

### 実装のポイント

**空きブロックの中にリンクを置く。** 第21章と同じ侵入的フリーリストです。ブロックが空きのときだけ意味を持つので、追加のメモリは要りません。最小ブロック 32 バイトに、`Link`(16 バイト)が収まります。

**`offset &= ~size` で親の先頭へ。** 統合したとき、新しいブロックの先頭は「2つのうち左側」です。該当ビットを 0 にすれば求まります。

**二重解放の検出が O(1) で書けた。** ビットツリーを降りた先のノードで `freeBits_` を見るだけです。第22章のプールと同じ品質の検査が、追加コストなしで手に入りました。

**自然な整列。** `base_` が容量と同じ大きさに整列していれば、**すべてのブロックが自分のサイズに整列** します。4096 バイトのブロックは 4096 バイト境界に置かれる。この性質は 26.9 節で効いてきます。

## 26.6 動かす

```cpp
void DumpTree(const ga::Buddy& b);   // ビットツリーを表示する補助関数

int main()
{
    ga::Buddy heap(1024);   // 1 KB、最小 32 バイト → order 0〜5

    std::println("--- 初期状態 ---");
    DumpTree(heap);

    void* a = heap.Allocate(100);   // → 128 バイト(order 2)
    std::println("--- 100 バイト確保 ---");
    DumpTree(heap);

    void* b = heap.Allocate(100);
    std::println("--- もう1つ確保 ---");
    DumpTree(heap);

    heap.Free(a);
    std::println("--- a 解放 ---");
    DumpTree(heap);

    heap.Free(b);
    std::println("--- b 解放(統合されるはず)---");
    DumpTree(heap);
}
```

```
--- 初期状態 ---
[0        1024 空き]

--- 100 バイト確保 ---
[0         128 使用中][128     128 空き][256     256 空き][512     512 空き]

--- もう1つ確保 ---
[0         128 使用中][128     128 使用中][256     256 空き][512     512 空き]

--- a 解放 ---
[0         128 空き][128     128 使用中][256     256 空き][512     512 空き]

--- b 解放(統合されるはず)---
[0        1024 空き]
```

**最後の1行に注目してください。**

`b` を解放した瞬間、128 → 256 → 512 → 1024 と、**4段階の統合が連鎖しました**。板全体が元の1ブロックに戻っています。

第24章の合体では、こうはいきません。可変サイズだと、解放の順序によっては中途半端な形が残ります。**バディは、全部解放すれば必ず元に戻ります。**

### テスト

```cpp
void Test_BuddySplitAndMerge()
{
    ga::Buddy heap(1024);

    void* a = heap.Allocate(32);
    void* b = heap.Allocate(32);

    // 32 を2つ取ると、1024 → 512 → 256 → 128 → 64 → 32+32 と割られる
    assert(reinterpret_cast<std::byte*>(b) - reinterpret_cast<std::byte*>(a) == 32);

    heap.Free(a);
    heap.Free(b);

    // 全部解放したら 1024 が1つ取れるはず
    void* big = heap.Allocate(1024);
    assert(big != nullptr);

    std::println("[ OK ] Test_BuddySplitAndMerge");
}

void Test_BuddyIsBuddy()
{
    ga::Buddy heap(1024);

    void* a = heap.Allocate(128);
    void* b = heap.Allocate(128);
    void* c = heap.Allocate(128);

    // a と b は相方。b と c は隣同士だが相方ではない
    heap.Free(b);
    heap.Free(c);

    // b と c は統合されないので、512 は取れない
    assert(heap.Allocate(512) == nullptr);

    heap.Free(a);
    // a と b が統合され、それが c と統合され、256 になる
    assert(heap.Allocate(256) != nullptr);

    std::println("[ OK ] Test_BuddyIsBuddy");
}
```

**2つ目のテストが、バディの制約を明確にします。** 隣り合っていても、相方でなければくっつきません。

## 26.7 内部断片化を見積もる

バディの代償です。**きちんと見積もっておきます。**

### 理論値

要求サイズが 2 の冪の区間 `[2^(k-1), 2^k)` に一様に分布するとします。平均は `0.75 × 2^k` です。

確保されるのは `2^k` なので、

```
無駄の割合 = (2^k - 0.75 × 2^k) / 2^k = 25%
```

**確保したメモリの約4分の1が、平均して無駄になります。**

最悪ケースは、2 の冪をわずかに超える要求です。

```
1025 バイトの要求 → 2048 バイト確保 → 49.95% の無駄
```

**ほぼ半分。** これがバディの最悪値です。

### 実測

同じアロケーターに、2種類の負荷をかけて比べます。

**負荷 P:2の冪ぴったりのサイズ**

```
サイズ: 32, 128, 512, 4096, 65536
```

```
内部断片化: 0.0%
```

**まったく無駄がありません。** バディにとって理想的な入力です。

**負荷 R:2の冪から少し外れたサイズ**

```
サイズ: 40, 100, 300, 5000, 70000
```

| 要求 | 確保 | 無駄 |
|---|---|---|
| 40 | 64 | 37.5% |
| 100 | 128 | 21.9% |
| 300 | 512 | 41.4% |
| 5000 | 8192 | 39.0% |
| 70000 | 131072 | 46.6% |

```
内部断片化: 44.4%(バイト数で重み付け)
```

**確保したメモリの 44% が使われていません。**

### この差の意味

```
同じアロケーター、同じアルゴリズム
  → 負荷 P では 0%
  → 負荷 R では 44%
```

**バディの性能は、扱うサイズの分布に完全に依存します。**

第25章の最後で「ビンの設計は分布に合わせる」と書きました。バディは、**ビンの設計が 2 の冪に固定されている** アロケーターです。分布が合えば最高、合わなければ最悪。

## 26.8 外部断片化と速度

### 速度

```
                      Allocate    Free
Bump  (第5章)          1.8 ns     —
Pool  (第22章)         2.9 ns    2.0 ns
Buddy (この章)        11.4 ns   18.7 ns
FreeList v0.18        16.8 ns    8.1 ns
new                   17.6 ns   15.2 ns
```

**確保は FreeList より速い。** ビン(order)の数が 16 個しかなく、探索がほぼありません。

**解放は遅い。** ビットツリーを根から降りる処理(最大 15 回)と、統合の連鎖があるためです。

**確保と解放の非対称性** は、バディの特徴です。第24章の FreeList は逆(確保が遅く、解放が速い)でした。

### 外部断片化

```
                       外部断片化   失敗
FreeList v0.18(負荷R)    0.521      0
Buddy        (負荷R)     0.310    412
```

**外部断片化の指標は良いのに、失敗が多い。**

一見矛盾していますが、理由は明快です。**内部断片化でメモリを食い潰しているため、そもそも空きが少ない** のです。

```
容量 1 MB
  FreeList: 要求 979 KB → 確保 988 KB(内部無駄 0.9%)
  Buddy   : 要求 979 KB → 確保 1760 KB → 容量オーバー
```

**「外部断片化は少ないが、メモリが足りない」** という状態です。指標だけを見て判断してはいけない、という第19章の注意が、ここでも当てはまります。

## 26.9 それでもバディが使われる場所

ここまでの数字を見ると、CPU 側の汎用メモリ管理でバディが主流にならなかった理由が分かります。**内部断片化 25〜44% は、重すぎます。**

**しかし、バディが最適な領域があります。**

### GPU メモリ

Direct3D 12 や Vulkan では、GPU のメモリを自分で管理します。そこには、CPU 側とは違う制約があります。

**制約1:管理情報をブロックに書き込めない。**

GPU 用のヒープには、CPU から自由に読み書きできないものがあります。書き込めたとしても、GPU が使うデータの隣にヘッダを置けば、キャッシュやアラインメントの要求を壊しかねません。

**バディはヘッダを持ちません。** すべての管理情報がビットツリーとして別の場所にあります。**この性質が決定的です。**

**制約2:アラインメント要求が大きく、しかも 2 の冪。**

Direct3D 12 の配置リソースは、64 KB(通常のテクスチャ)や 4 MB(マルチサンプルのテクスチャ)といった境界に整列していなければなりません。

**バディでは、すべてのブロックが自分のサイズに整列します**(板の先頭が整列していれば)。64 KB のブロックは、必ず 64 KB 境界にあります。**追加のパディングが一切要りません。**

第6章で見たとおり、大きなアラインメント要求を素直に満たそうとすると、大量のパディングが発生します。バディでは、それが構造的にゼロになります。

**制約3:要求サイズがもともと 2 の冪に近い。**

テクスチャは 256×256、512×512、1024×1024。ミップマップも 2 の冪で縮小していきます。頂点バッファも、多くの場合はページ単位で丸められます。

**26.7 節の「負荷 P」に近い状況です。** 内部断片化がほとんど発生しません。

### テクスチャアトラス

複数の小さなテクスチャを1枚の大きなテクスチャにまとめる技法です。

2次元版のバディシステム(4分木で正方形を4分割していく)が、古くから使われています。位置とサイズの計算が単純で、隙間の管理が要らないためです。

### Linux のページアロケーター

OS の物理ページ管理にも、バディシステムが使われています。

ページサイズは 4 KB で固定。要求は「連続した 2^n ページ」の形。**サイズが最初から 2 の冪です。**

内部断片化の問題が起きない領域では、バディの単純さと速さが素直に活きます。

### まとめ

| 条件 | バディの適性 |
|---|---|
| 要求サイズが 2 の冪に近い | **◎** |
| 大きなアラインメントが必要 | **◎** |
| ブロックにヘッダを書けない | **◎** |
| 任意サイズが飛び交う | × |
| メモリが逼迫している | × |

**第48章で GPU メモリを扱うとき、この章の実装をほぼそのまま使います。**

## 演習

**演習26-1** `base_` を容量と同じ大きさに整列させ、すべてのブロックが自分のサイズに整列することを確認してください。

**演習26-2** 最小ブロックを 32 から 64 に変えてください。ビットツリーのサイズと内部断片化はどう変わりますか。

**演習26-3** 26.7 の負荷 R で、サイズを 40 → 32、100 → 128 のように 2 の冪に寄せてください。内部断片化はどこまで下がりますか。

**演習26-4** `splitBits_` を持たず、代わりに `Free(void* p, std::size_t size)` としてサイズを受け取る設計にしてください。何が簡単になり、何が難しくなりますか。

**演習26-5** 統合の回数(`mergeCount_`)と解放の回数を比べてください。平均して何段階の統合が起きていますか。

**演習26-6** 2次元のバディ(正方形を4分割する)を設計してください。相方は何個になりますか。統合の条件はどうなりますか。

**演習26-7** バディの `Free` は、ビットツリーを根から降りるため O(log n) です。これを O(1) にする方法を考えてください(ヒント:サイズを記録する副表)。

## 次章の予告

第3部の最後のアロケーターです。

ここまで作ってきた実装には、共通の弱点があります。**最悪実行時間が読めない。**

| | 最悪ケース |
|---|---|
| FreeList v0.18 | 大きいビンの中を線形探索する |
| Buddy | 空きのある order を探して線形走査、統合が最大 15 段連鎖 |

平均は十分速いのですが、**「絶対にこの時間内に終わる」という保証がありません**。第2章から繰り返している「平均ではなく最悪値」という視点で見ると、まだ不十分です。

第27章の **TLSF**(Two-Level Segregated Fit)は、この保証を与えます。

- サイズクラスを **二段** に分ける(第25章の一段構造の拡張)
- 二段のビットマップを、**ビット演算だけ** で走査する
- 分岐もループもない、**厳密に O(1) の確保**

そして、第2章で作ったヒストグラムを再実行します。最悪値が、どこまで平らになるかを見ます。

---

> **コラム:バディは、どこで生きているか**
>
> 1965年に Knowlton が発表した方式が、60年後の今も現役である場所を見てみましょう。
>
> ---
>
> **Linux カーネルのページアロケーター**
>
> 物理メモリのページ管理に、バディシステムが使われています。`/proc/buddyinfo` を見ると、order ごとの空きページ数が並んでいます。
>
> ```
> Node 0, zone   Normal   1024   512   256   128   64   32   16   8   4   2   1
> ```
>
> 左から order 0(4 KB)、order 1(8 KB)、……となっています。**カーネルが、いままさにバディの状態を教えてくれています。**
>
> ページサイズが固定で、要求も「連続した 2^n ページ」の形なので、内部断片化の問題が構造的に起きません。
>
> なお、カーネルは小さなオブジェクト(数十〜数百バイト)にはバディを使いません。第21章のコラムで触れた **スラブアロケーター** が、バディから取ったページを細かく切り分けます。**適材適所の階層構造** になっています。
>
> ---
>
> **GPU メモリアロケーター**
>
> Direct3D 12 用の **D3D12MemoryAllocator**(D3D12MA)や、Vulkan 用の **VulkanMemoryAllocator**(VMA)は、マイクロソフトと AMD がそれぞれ公開しているライブラリです。
>
> どちらも、大きなヒープを確保して、その中を自前で切り分ける「サブアロケーション」を行います。アルゴリズムは選択可能で、バディに近い方式も用意されています。
>
> 26.9 節で挙げた3つの理由——ヘッダを書けない、大きな 2 の冪アラインメント、要求サイズが 2 の冪に近い——が、すべて当てはまる領域です。
>
> 第48章で、これらのライブラリの立ち位置を扱います。
>
> ---
>
> **変種たち**
>
> 内部断片化 25% は重い。当然、これを減らす試みがありました。
>
> **フィボナッチ・バディ。** 2 の冪ではなく、フィボナッチ数列でサイズを刻みます(1, 2, 3, 5, 8, 13, 21...)。比が約 1.618 なので、2 の冪(比 2.0)より刻みが細かく、内部断片化が減ります。
>
> ただし、分割してできる2つのブロックのサイズが違うため、統合の条件が複雑になります。**XOR 1回で相方が分かる、という美点が失われます。**
>
> **加重バディ(weighted buddy)。** ブロックを 1:1 ではなく 1:2 や 1:3 に分けることを許します。サイズの種類が増えるので、やはり内部断片化は減ります。同じく、実装は複雑になります。
>
> ---
>
> **なぜ変種は主流にならなかったか**
>
> どの変種も、内部断片化を数パーセント〜十数パーセント改善します。しかし、**バディの最大の魅力は単純さ** でした。
>
> XOR 1回で相方が分かる。ヘッダが要らない。ビット演算だけで状態が管理できる。**この単純さを失うくらいなら、別のアルゴリズムを選んだほうがいい** ——多くの実装者がそう判断しました。
>
> そして実際、別のアルゴリズムがありました。**次章の TLSF** です。細かいサイズクラスを持ちながら、O(1) を保証する。バディの変種たちが目指した地点に、まったく違う設計で到達しています。
