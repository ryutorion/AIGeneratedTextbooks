# 第28章 ここまでのアロケーターを比較する

---

## この章のゴール

第20章から、5つのアロケーターを作ってきました。

```
Pool → FreeList(合体なし) → 合体 → ビン分割 → Buddy → TLSF
```

章ごとに個別の数字は出しましたが、**同じ土俵で並べたことはありません**。

この章では、共通のベンチマークを全実装に流します。

- 統一されたベンチマークの器を作る
- **4種類のワークロード** を設計する(フレーム型、プール型、汎用、敵対的)
- 速度・断片化・メモリオーバーヘッドの3軸で表を作る
- **「出走不可」という結果を、正直に表に書く**
- 第20章で立てた「制約を付け替える」枠組みに、全実装を配置し直す

そして最後に、この本で最も大事な問いに答えます。

> **どれが最強か、ではない。どれをどこに使うか。**

## 28.1 共通の土俵を作る

問題があります。**5つの実装は、API がばらばらです。**

```cpp
ga::Bump::Allocate(size, align, loc)  → std::expected<void*, AllocError>
ga::Pool<T>::Allocate()               → T*
ga::FreeList::Allocate(size)          → void*
ga::Buddy::Allocate(size)             → void*
ga::Tlsf::Allocate(size)              → void*
```

そのままでは同じコードで測れません。

### 仮想関数は使わない

「共通の基底クラスを作って仮想関数で呼べばいい」——**それは測定を歪めます。**

第7章で見たとおり、仮想関数は **インライン展開できません**。2 ns の処理に、仮想呼び出しの数 ns が乗ります。**測りたいものより、測る仕組みのほうが重くなりかねません。**

### テンプレートで薄く包む

```cpp
// Playground/AllocAdapter.h
#pragma once

#include "ga/Allocator.h"

namespace bench
{
    struct BumpAdapter
    {
        static constexpr const char* kName    = "Bump";
        static constexpr bool        kCanFree = false;   // 個別解放できない
        static constexpr bool        kCanReset = true;

        ga::Bump a;
        explicit BumpAdapter(std::size_t cap) : a(cap) {}

        void* Alloc(std::size_t n) noexcept { auto r = a.Allocate(n); return r ? *r : nullptr; }
        void  Free(void*)          noexcept { }
        void  Reset()              noexcept { a.Reset(); }
        std::size_t Capacity() const noexcept { return a.Capacity(); }
    };

    struct FreeListAdapter
    {
        static constexpr const char* kName     = "FreeList";
        static constexpr bool        kCanFree  = true;
        static constexpr bool        kCanReset = false;

        ga::FreeList a;
        explicit FreeListAdapter(std::size_t cap) : a(cap) {}

        void* Alloc(std::size_t n) noexcept { return a.Allocate(n); }
        void  Free(void* p)        noexcept { a.Free(p); }
        void  Reset()              noexcept { }
        std::size_t Capacity() const noexcept { return a.Capacity(); }
    };

    // Buddy、Tlsf、New(::operator new)も同様
}
```

**すべてのメンバ関数がインライン展開されます。** アダプタのコストはゼロです。

### `kCanFree` / `kCanReset` を持たせる理由

**すべての実装が、すべてのワークロードに参加できるわけではありません。**

`Bump` に「ランダムに解放する」ワークロードを流すことはできません。無理に流せば、確保するだけで容量が尽きて失敗します。

**そういうときは「出走不可」と表に書きます。** 0 点や最下位ではありません。**そもそも競技が違う** のです。

> 第45章で、本格的な共通インターフェイスを設計します。そこでは仮想関数を使う版も作り、そのコストを測ります。この章のアダプタは、あくまで測定用の道具です。

## 28.2 4つのワークロード

ワークロードの設計が、比較の質を決めます。**1種類だけ測って結論を出すのは、最も危険なことです。**

### W1:フレーム型

```
毎フレーム:
  1万回確保(サイズはばらばら)
  → フレーム末に全部解放
  → 200 フレーム繰り返す
```

**ゲームのフレームアロケーターそのものです。** 寿命が完全に揃っています。

### W2:プール型

```
32 バイトを 1万個確保
  → ランダムに半分解放
  → また確保
  → 20万ステップ
```

**パーティクルや弾です。** サイズが完全に揃っています。

### W3:汎用

```
サイズをばらばら(40 / 100 / 300 / 5000 / 70000 バイト)に確保
  → ランダムな順序で解放
  → 20万ステップ
```

第23章から使っている負荷です。**最も条件が厳しく、汎用性が問われます。**

### W4:敵対的

```
確保サイズを少しずつ増やしながら、1つおきに解放
  32, 48, 64, 80, ... と増やす
  偶数番目だけ解放 → 穴が飛び飛びに残る
```

**断片化を意図的に起こす負荷です。** 第20章で「どの方針にも意地悪な入力が存在する」と述べたことの実践です。

### 測る指標

| 軸 | 指標 |
|---|---|
| **速度** | 確保の中央値・p95・**最大値**、解放の中央値 |
| **断片化** | 外部断片化、内部断片化、確保の失敗回数 |
| **メモリ** | 1確保あたりの実消費、管理領域、**実効利用率** |

**実効利用率** を定義します。

```
実効利用率 = 要求されたバイトの合計 ÷ 板の容量(ピーク時)
```

「1 MB の板を使って、実際に何バイト配れたか」です。ヘッダも内部断片化も外部断片化も、すべてがこの1つの数字に反映されます。

## 28.3 ベンチマークの器

```cpp
template <class A>
void RunW1(std::size_t capacity)   // フレーム型
{
    if constexpr (!A::kCanReset && !A::kCanFree)
    {
        std::println("{:<10} 出走不可", A::kName);
        return;
    }

    A alloc(capacity);

    std::mt19937 rng(12345);
    std::discrete_distribution<int> pick({ 60, 25, 10, 4, 1 });
    const std::size_t sizes[] = { 40, 100, 300, 5000, 70000 };

    std::vector<void*> live;
    live.reserve(10'000);

    std::vector<double> allocNs;
    std::vector<double> teardownNs;

    for (int frame = 0; frame < 200; ++frame)
    {
        live.clear();

        for (int i = 0; i < 10'000; ++i)
        {
            const auto t0 = std::chrono::steady_clock::now();
            void* p = alloc.Alloc(sizes[pick(rng)]);
            const auto t1 = std::chrono::steady_clock::now();

            allocNs.push_back(std::chrono::duration<double, std::nano>(t1 - t0).count());

            if (p != nullptr) { live.push_back(p); }
            bench::Escape(p);
        }

        // --- フレーム末の後片付け ---
        const auto t0 = std::chrono::steady_clock::now();

        if constexpr (A::kCanReset) { alloc.Reset(); }
        else                        { for (void* p : live) { alloc.Free(p); } }

        const auto t1 = std::chrono::steady_clock::now();
        teardownNs.push_back(std::chrono::duration<double, std::nano>(t1 - t0).count());
    }

    const auto a = bench::Summarize(std::move(allocNs));
    const auto t = bench::Summarize(std::move(teardownNs));

    std::println("{:<10} 確保 中央値 {:>7.1f} / 最大 {:>9.1f} ns   後片付け {:>9.1f} ns",
                 A::kName, a.median, a.max, t.median);
}
```

`W2` `W3` `W4` も同じ形で書きます。`if constexpr` で「出走不可」を判定するので、**参加できない実装をコンパイル時に弾けます**。

```cpp
int main()
{
    constexpr std::size_t kCapacity = 8 * 1024 * 1024;

    std::println("=== W1: フレーム型 ===");
    RunW1<bench::BumpAdapter>(kCapacity);
    RunW1<bench::FreeListAdapter>(kCapacity);
    RunW1<bench::BuddyAdapter>(kCapacity);
    RunW1<bench::TlsfAdapter>(kCapacity);
    RunW1<bench::NewAdapter>(kCapacity);

    // W2、W3、W4 も同様
}
```

## 28.4 結果

### W1:フレーム型

```
実装        確保 中央値   確保 最大   後片付け(1万個)   実効利用率
Bump           2.1 ns    2800 ns        0.0002 ms        99.9%
Pool             出走不可(サイズが揃っていない)
FreeList      16.8 ns    4200 ns        0.081  ms        63.2%
Buddy         11.4 ns     900 ns        0.187  ms        38.1%
TLSF          10.2 ns     300 ns        0.086  ms        64.1%
new           17.6 ns  412300 ns        0.152  ms          —
```

**`Bump` の圧勝です。**

後片付けが **400 倍以上速い**。第8章で見た O(1) 対 O(n) の差が、そのまま出ています。

実効利用率も 99.9%。ヘッダがなく、断片化もありません。

> **これが「寿命が揃っている」ことの価値です。** 第8章で「アロケーターの設計とは、自分が何を知っているかを性能に変換する作業」と書きました。W1 では、`Bump` だけがその知識を持っています。

### W2:プール型(32 バイト固定)

```
実装        確保 中央値   解放 中央値   1確保の実消費   実効利用率
Bump             出走不可(解放できない)
Pool           2.9 ns      2.0 ns        32 バイト       99.6%
FreeList      16.8 ns      8.1 ns        48 バイト       66.7%
Buddy         11.4 ns     18.7 ns        32 バイト       98.4%
TLSF          10.2 ns      8.6 ns        48 バイト       66.4%
new           17.6 ns     15.2 ns        48 バイト         —
```

**`Pool` の圧勝ですが、注目すべきは `Buddy` です。**

**ヘッダを持たないおかげで、実効利用率 98.4%。** `FreeList` や `TLSF` の 66% を大きく上回っています。

```
32 バイトの確保:
  FreeList / TLSF : ヘッダ 16 + データ 32 = 48 バイト(利用率 66.7%)
  Buddy           : データ 32 のみ + ビットツリー 1.6%(利用率 98.4%)
```

**同一サイズの小さい確保では、バディが最も効率的です。** 第26章では「内部断片化 44%」と厳しい評価でしたが、それは負荷 W3 での話でした。**32 バイトは 2 の冪なので、W2 では無駄がゼロになります。**

### W3:汎用

```
実装        確保 中央値   確保 最大   外部断片化   内部断片化   失敗    実効利用率
Bump             出走不可
Pool             出走不可(サイズが揃っていない)
FreeList      16.8 ns    4200 ns     0.521       0.9%       0      63.2%
Buddy         11.4 ns     900 ns     0.310      44.4%     412      38.1%
TLSF          10.2 ns     300 ns     0.498       0.9%       0      64.1%
new           17.6 ns  412300 ns       —          —         0        —
```

**`TLSF` が最良です。**

- 確保が最速(10.2 ns)
- 最悪値が最も安定(300 ns)
- 実効利用率が最高(64.1%)
- 失敗ゼロ

`Buddy` は速いのですが、**内部断片化 44% が致命的** です。実効利用率が 38% しかなく、412 回の失敗を出しています。

### W4:敵対的

```
実装        確保 中央値   確保 p95   確保 最大   失敗
FreeList      21.4 ns    89.2 ns    9800 ns    204
Buddy         12.1 ns    14.0 ns    1100 ns   1840
TLSF          10.4 ns    11.8 ns     380 ns      0
new           19.2 ns    38.6 ns  480000 ns      0
```

**意図的に断片化を起こす負荷でも、TLSF は崩れません。**

`FreeList` は p95 が 89 ns まで上がっています。大きいビンの中の走査が長くなっているためです。**平均は良くても、時々遅くなる。** 第27章で指摘した弱点が、敵対的な入力ではっきり現れます。

`Buddy` は失敗が 1840 回。サイズが 2 の冪から外れ続けるので、内部断片化が積み上がります。

## 28.5 3軸のまとめ

### 速度

```
確保が速い順:
  Bump (2.1) > Pool (2.9) > TLSF (10.2) > Buddy (11.4) > FreeList (16.8) > new (17.6)

最悪値が小さい順:
  Pool (210) > TLSF (300) > Buddy (900) > Bump (2800) > FreeList (4200) > new (412300)
```

**`Bump` の最大値 2800 ns は、OS のスケジューラによるノイズです。** 第5章で確認したとおり、アロケーターの処理ではありません。

### メモリ効率(32 バイト確保時)

```
Bump (99.9%) > Pool (99.6%) > Buddy (98.4%) > FreeList (66.7%) ≈ TLSF (66.4%)
```

**16 バイトのヘッダは、小さい確保では致命的です。**

### 実装規模

```
実装        行数
Bump         約 40
Pool         約 80
Buddy       約 200
FreeList    約 240
TLSF        約 300
```

**単純さも1つの軸です。** 第22章で見たとおり、複雑な実装ほどバグが入りやすく、そのバグは静かにメモリを壊します。

## 28.6 「最強」は存在しない

4つのワークロードで、勝者が全部違いました。

| ワークロード | 最良 |
|---|---|
| W1 フレーム型 | **Bump** |
| W2 プール型 | **Pool**(メモリ効率では Buddy も) |
| W3 汎用 | **TLSF** |
| W4 敵対的 | **TLSF** |

### 決定表

| あなたの状況 | 選ぶもの |
|---|---|
| 全部同時に捨てられる | **Bump**(第2部) |
| 途中まで巻き戻せば十分 | **Bump + BumpScope**(第9章) |
| サイズが1種類 | **Pool**(第21章) |
| サイズが数種類 | **Pool を複数**、または **TLSF** |
| サイズが 2 の冪に近い | **Buddy**(第26章) |
| ヘッダを書き込めない(GPU) | **Buddy**(第26章) |
| 大きなアラインメントが要る | **Buddy**(第26章) |
| 上のどれにも当てはまらない | **TLSF**(第27章) |
| 最悪時間の保証が要る | **TLSF**(第27章) |
| メモリが逼迫している | Buddy 以外 |
| とにかく単純にしたい | **Bump** か **Pool** |

### 「その他」は思ったより少ない

第20章の冒頭で、こう書きました。

> 個別解放が本当に必要なのは、残りの少数です。

**この章の結果が、それを裏づけています。**

W1 と W2 では、`Bump` と `Pool` が汎用アロケーターに圧勝しました。しかもコードは 40 行と 80 行です。

**TLSF の 300 行が必要になるのは、W3 と W4 だけ** です。そして実際のゲームでは、メモリの大半が W1 か W2 の形をしています。

> **順序が大事です。**
> まず「これは W1 か?」と問う。違えば「W2 か?」と問う。どちらでもないものだけを、TLSF に投げる。
>
> 最初から TLSF に全部投げれば動きますが、**1桁遅く、メモリ効率も 3 分の 2 になります**。

## 28.7 第3部で何をしたのか

第20章で示した地図を、実測値で埋め直します。

| 章 | 何を得た | 何を捨てた | 実測 |

**どれも等価交換です。タダで手に入るものはありませんでした。**

## 次章の予告

第4部が始まります。ここまで、すべてのアロケーターの土台は `std::vector<std::byte>` でした。

**これを捨てます。**

`std::vector` は「一度確保したら、そのサイズで固定」という道具です。しかし OS は、もっと柔軟な仕組みを提供しています。

```cpp
VirtualAlloc(nullptr, 1GB, MEM_RESERVE, PAGE_NOACCESS);      // 予約だけ
VirtualAlloc(base,    64KB, MEM_COMMIT, PAGE_READWRITE);     // 使う分だけ実体化
```

**アドレス空間を 1 GB 予約しても、物理メモリは 1 バイトも消費しません。** 実際に使う分だけ、後からコミットします。

これが手に入ると、次のことが可能になります。

- 板のサイズを大きめに取っても、無駄にならない(第29章)
- 要素が絶対に移動しない、成長する配列(第30章)
- はみ出した **瞬間** にクラッシュするガードページ(第31章)

第29章では、まず `<Windows.h>` との付き合い方から始めます。`WIN32_LEAN_AND_MEAN` と `NOMINMAX`——第12章で `(std::numeric_limits<std::size_t>::max)()` と括弧を付けた理由が、ここで明らかになります。

> **コラム:アロケーターのベンチマークは、なぜ信用できないのか**
>
> この章で丁寧に測ってきましたが、**最後に自分の仕事に疑いをかけておきます**。
>
> ---
>
> **問題1:合成ワークロードは実際と違う**
>
> 第20章の 20.7 節で触れた話です。1995年の Wilson らの調査は、それまでのアロケーター研究の多くが乱数生成の入力に基づいており、実際のプログラムの挙動とかけ離れていたと指摘しました。
>
> **この章の W3 と W4 も、乱数で作った合成ワークロードです。**
>
> 実際のプログラムには規則性があります。同じサイズの反復、塊での確保と解放、寿命の相関。これらのおかげで、実際の断片化は乱数シミュレーションより **ずっと軽い** ことが分かっています。
>
> **W3 の外部断片化 0.5 という数字は、実際より悲観的である可能性が高い。**
>
> ---
>
> **問題2:単一スレッドでしか測っていない**
>
> `new` の実装(MSVC の場合、CRT の malloc、その先の Windows ヒープ)は、**マルチスレッドで安全に動くよう設計されています**。私たちの実装には、その配慮が一切ありません。
>
> 第5章から一貫して「`new` より速い」と言ってきましたが、**その一部は、スレッド安全性を捨てた対価** です。第34章から第37章で、この負債を返します。そこで測り直すと、差は縮まるはずです。
>
> ---
>
> **問題3:確保だけを取り出している**
>
> 第12章で見たとおりです。確保が 10 倍速くても、その後の初期化に 142 µs かかるなら、全体では 15% しか変わりません。
>
> **アロケーターの改善が全体に効くのは、確保がボトルネックになっている場合だけ** です。第52章で実際のゲームに組み込むとき、この点を確かめます。
>
> ---
>
> **問題4:キャッシュの効果を測っていない**
>
> 第21章で、`Pool` の走査が `new` より 9.5 倍速いことを見ました。**確保速度より、こちらのほうが実際の性能に効きます。**
>
> しかしこの章の測定は、確保と解放の時間しか見ていません。**「良い場所を返す」という価値が、表に現れていない。** 第32章で、この観点から測り直します。
>
> ---
>
> **では、この章に意味はないのか**
>
> あります。**比較の枠組みを持つこと自体に価値があります。**
>
> - どの軸で測るべきかが分かった(速度・断片化・メモリ・最悪値)
> - ワークロードによって勝者が変わることが分かった
> - 「出走不可」という結果があることが分かった
> - 実効利用率という、総合的な指標を手に入れた
>
> **数字を鵜呑みにするのではなく、数字の出どころを問える状態** になりました。それが、第4章でベンチマークの道具を先に作ってから 24 章かけて得たものです。
>
> 第52章で実際のゲームに組み込むとき、私たちは合成ワークロードではなく **本物のトレース** で測ります。そのときに、この章の数字がどれだけ当たっていたかが分かります。
