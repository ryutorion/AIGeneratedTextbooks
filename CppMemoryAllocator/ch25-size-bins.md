# 第25章 探索を速くする 〔v0.18:サイズ別ビン〕

---

## この章のゴール

合体によって、断片化は制御下に入りました。**残る問題は探索です。**

```
FreeList(合体あり) : 45 ns
new                : 17.6 ns
```

まだ 2.5 倍負けています。原因は first fit の線形探索です。空きブロックが 84 個あれば、平均 11 個を辿ります。しかもポインタを追うので、キャッシュに乗りません。

**フリーリストを1本から複数本に分けます。**

```
32 バイト   → ビン2
48 バイト   → ビン3
64 バイト   → ビン4
   ...
1024 以上   → 2の冪ごとのビン
```

64 バイトが欲しければ、ビン4の先頭を見るだけ。**探索がほぼ消えます。**

- サイズクラスを設計する(細かさをどう決めるか)
- 空でないビンを、ビット演算で一発で見つける
- ビン分割を実装する 〔**v0.18**〕
- 探索回数を測り、劇的に減ることを確認する
- **ビンの粒度と内部断片化の交換関係** を、3つの設計で比べる

最後の項目が、第26章のバディシステムへの橋になります。

## 25.1 分けて持つ、という発想

第23章から、フリーリストは1本でした。

```
free → [32] → [4096] → [48] → [128] → [64] → ...
```

サイズがばらばらに混ざっています。64 バイトが欲しいとき、先頭から順に見て「32 は小さい、4096 は大きすぎるが使える、48 は小さい……」と判定していきます。

**サイズごとに分けておけば、探す必要がありません。**

```
ビン2  (32)   → [32] → [32] → [32]
ビン3  (48)   → [48]
ビン4  (64)   → [64] → [64]
ビン8  (128)  → [128]
ビン64(1024〜)→ [4096]
```

64 バイトが欲しければ、ビン4を見る。**あれば先頭を取るだけ。O(1)。**

これを **セグリゲート・フィット**(segregated fit)と呼びます。

### おまけの効果

もう1つ、副次的な利点があります。

**「入る中で最も小さいクラス」から取る** ので、これは近似的な **best fit** になっています。

第20章で、best fit は探索コストが高いから割に合わないと結論しました。**ビンに分ければ、探索コストなしで best fit に近い挙動が得られます。** 断片化の面でも有利になるはずです(25.6 節で確認します)。

## 25.2 サイズクラスを設計する

「どの範囲を1つのビンにまとめるか」を決めます。

### 細かすぎると

1バイト刻みでビンを作れば、ビンの数は膨大になります。64 KB までなら 65,536 個。ビン配列だけで 512 KB です。しかも、ほとんどのビンは空のまま。

### 粗すぎると

「2の冪ごと」にすると、ビンは 64 個で済みます。しかし1つのビンが `[1024, 2047]` のような広い範囲を持つので、**中を探す必要が出てきます**。

さらに、要求を切り上げてビンのサイズに合わせるなら、**内部断片化** が発生します。1025 バイトの要求に 2048 バイトを渡すことになります。

### 二層構造にする

実物のアロケーターが採る解決策は、**サイズによって刻み方を変える** ことです。

| 範囲 | 刻み | ビン数 |
|---|---|---|
| 32 〜 1023 バイト | **16 バイト刻み** | 64 |
| 1024 バイト以上 | **2の冪刻み** | 54 |

小さいサイズは細かく、大きいサイズは粗く。

**理由は、無駄の割合が相対的だからです。**

```
32 バイトの要求に 48 バイト渡す  → 50% の無駄
4096 バイトの要求に 4200 渡す   → 2.5% の無駄
```

小さいところでは絶対値の差が効き、大きいところでは比率が効きます。**対数的な刻み方が理にかなっています。**

### 実装

```cpp
    static constexpr std::size_t kSmallMax  = 1024;
    static constexpr std::size_t kSmallBins = kSmallMax / kDefaultAlignment;   // 64
    static constexpr std::size_t kBinCount  = 128;

    static std::size_t BinOf(std::size_t size) noexcept
    {
        if (size < kSmallMax)
        {
            return size / kDefaultAlignment;          // 16 バイト刻み
        }

        const std::size_t k   = static_cast<std::size_t>(std::bit_width(size));
        const std::size_t bin = kSmallBins + (k - std::bit_width(kSmallMax));

        return (bin < kBinCount) ? bin : kBinCount - 1;
    }
```

`std::bit_width(1024)` は 11 です(1024 = 2^10 を表すのに 11 ビット必要)。したがって:

| サイズ | `bit_width` | ビン |
|---|---|---|
| 1024 〜 2047 | 11 | 64 |
| 2048 〜 4095 | 12 | 65 |
| 4096 〜 8191 | 13 | 66 |

第15章でサイズ分布のヒストグラムを作ったときと、**まったく同じ計算** です。あのときは統計のためでしたが、いまは実際の配置に使っています。

### 小さいビンは「厳密一致」になる

重要な性質があります。

**すべてのブロックサイズは 16 の倍数です**(第23章で `AlignUpSize` してから確保しているため)。

したがって `size < 1024` のとき、`size / 16` は **サイズを一意に決めます**。

```
ビン4 に入っているブロックは、すべてちょうど 64 バイト
```

**中を探す必要がありません。** 先頭を取れば必ず合います。

大きいビンは範囲を持つので、中を探す必要があります。しかし大きいブロックは数が少ないので、実害は小さい。

## 25.3 空でないビンを、一発で見つける

ビン4を見て空だったら、次はどうするか。

```
ビン5、ビン6、ビン7、……と順に見ていく
```

128 個のビンを全部見るのは無駄です。**しかも、ほとんどが空です。**

### ビットマップを使う

「どのビンが空でないか」を、ビットで持ちます。

```cpp
    std::uint64_t binMap_[2] = {};   // 128 ビン分
```

ビンにブロックを入れたらビットを立て、空になったら降ろします。

**「i 番目以降で最初に立っているビット」を探すのは、ビット演算1回です。**

```cpp
    std::size_t FindBinAtLeast(std::size_t i) const noexcept
    {
        std::size_t w = i >> 6;

        // 現在のワードのうち、i 番目以降だけを見る
        std::uint64_t bits = binMap_[w] & (~std::uint64_t{0} << (i & 63));

        if (bits != 0)
        {
            return (w << 6) + static_cast<std::size_t>(std::countr_zero(bits));
        }

        for (++w; w < 2; ++w)
        {
            if (binMap_[w] != 0)
            {
                return (w << 6) + static_cast<std::size_t>(std::countr_zero(binMap_[w]));
            }
        }

        return kBinCount;    // 空きなし
    }
```

`~0ull << (i & 63)` で、下位ビットをマスクします。`std::countr_zero` で最下位の 1 の位置を得ます。

**128 個のビンを、最悪2ワードの走査で判定できます。**

> **この構造は、第27章の TLSF で本格的に使います。** TLSF は同じ発想を **二段** にして、サイズクラスをさらに細かく保ちながら O(1) を維持します。ここはその一段目です。

### より大きいビンなら必ず入る

`FindBinAtLeast(bin + 1)` で見つかったビンのブロックは、**必ず要求より大きい** と言えます。

理由:ビン `bin+1` に入るブロックの最小サイズは、ビン `bin` の上限より大きいからです。そして `need` はビン `bin` の範囲内にあります。

```
need = 100 → ビン6([96, 111] のうち 100)
ビン7 のブロックは 112 バイト以上 → 必ず入る
```

**探索が完全に不要になります。**

## 25.4 実装する 〔v0.18〕

第24章からの変更は、**フリーリストが1本から128本になる** ことだけです。合体のロジックは変わりません。

```cpp
class FreeList
{
public:
    static constexpr std::size_t kSmallMax  = 1024;
    static constexpr std::size_t kSmallBins = kSmallMax / kDefaultAlignment;
    static constexpr std::size_t kBinCount  = 128;

    [[nodiscard]] void* Allocate(std::size_t size) noexcept
    {
        if (size == 0) { return nullptr; }

        const std::size_t payload = AlignUpSize(size, kDefaultAlignment);
        if (payload < size) { return nullptr; }

        std::size_t need = payload + kHeaderSize;
        if (need < payload)       { return nullptr; }
        if (need < kMinBlockSize) { need = kMinBlockSize; }

        ++searches_;

        const std::size_t bin = BinOf(need);

        // ① 該当するビンの中を探す
        //    小さいビンは厳密一致なので、先頭で必ず当たる
        for (Header* h = bins_[bin]; h != nullptr; h = h->nextFree)
        {
            ++searchSteps_;
            if (detail::SizeOf(h) >= need) { return Take(h, need); }
        }

        // ② より大きいビンから取る(必ず入る)
        const std::size_t j = FindBinAtLeast(bin + 1);
        if (j < kBinCount)
        {
            ++searchSteps_;
            return Take(bins_[j], need);
        }

        ++failures_;
        return nullptr;
    }

private:
    // 見つけたブロックを使う(必要なら分割する)
    void* Take(Header* h, std::size_t need) noexcept
    {
        const std::size_t blockSize = detail::SizeOf(h);

        UnlinkFree(h);

        if (blockSize - need >= kMinBlockSize)
        {
            MarkUsed(h, need);

            Header* rest = NextOf(h);
            MarkFree(rest, blockSize - need);
            PushFree(rest);
        }
        else
        {
            MarkUsed(h, blockSize);
            internalWaste_ += blockSize - need;
        }

        ++liveCount_;
        return BytesOf(h) + kHeaderSize;
    }

    // ---- フリーリスト(ビンごと)----

    void PushFree(Header* h) noexcept
    {
        const std::size_t bin = BinOf(detail::SizeOf(h));

        h->nextFree = bins_[bin];
        detail::PrevFreeOf(h) = nullptr;

        if (bins_[bin] != nullptr) { detail::PrevFreeOf(bins_[bin]) = h; }

        bins_[bin] = h;
        SetBinBit(bin);
    }

    void UnlinkFree(Header* h) noexcept
    {
        const std::size_t bin = BinOf(detail::SizeOf(h));

        Header* prev = detail::PrevFreeOf(h);
        Header* next = h->nextFree;

        if (prev != nullptr) { prev->nextFree = next; }
        else                 { bins_[bin] = next; }

        if (next != nullptr) { detail::PrevFreeOf(next) = prev; }

        if (bins_[bin] == nullptr) { ClearBinBit(bin); }
    }

    void SetBinBit(std::size_t i)   noexcept { binMap_[i >> 6] |=  (std::uint64_t{1} << (i & 63)); }
    void ClearBinBit(std::size_t i) noexcept { binMap_[i >> 6] &= ~(std::uint64_t{1} << (i & 63)); }

    Header*       bins_[kBinCount] = {};
    std::uint64_t binMap_[2]       = {};
};
```

### ⚠ サイズを変える前に外す

`UnlinkFree` は `BinOf(SizeOf(h))` でビンを特定します。つまり、**サイズが変わる前に呼ばなければなりません**。

```cpp
    // 正しい
    UnlinkFree(next);
    size += SizeOf(next);

    // 間違い(別のビンから外そうとする)
    size += SizeOf(next);
    UnlinkFree(next);
```

第24章の `Free` では、すでに正しい順序で書いていました。**ビンを導入したことで、その順序が「望ましい」から「必須」に変わりました。**

こういう暗黙の依存が、あとから機能を足したときに壊れます。テストで固定しておくべき箇所です。

## 25.5 測る:探索が消える

第23章・第24章とまったく同じ負荷をかけます。

```
                        単一リスト(v0.17)   ビン分割(v0.18)
step   5000  平均探索        8.4                1.1
step  10000  平均探索        9.9                1.2
step  15000  平均探索       10.6                1.3
step  20000  平均探索       11.2                1.3
```

**11.2 → 1.3。ほぼ1回で見つかっています。**

残る 0.3 は、大きいビンの中を探すぶんです。小さいビンは厳密一致なので、必ず1回で当たります。

### 速度

```
                     v0.17     v0.18
Allocate            45.0 ns   16.8 ns
Free                 7.4 ns    8.1 ns
```

**確保が 2.7 倍速くなりました。**

解放は 0.7 ns 遅くなっています。`BinOf` の計算(`bit_width` とシフト)と、ビットマップの更新が加わったためです。**十分に元が取れています。**

### 他の実装との比較

```
Bump   (第5章)              1.8 ns
Pool   (第22章)             2.9 ns
FreeList v0.18(この章)     16.8 ns   ← 今回
new                        17.6 ns
FreeList v0.17(第24章)     45.0 ns
FreeList v0.16(第23章)   2940.0 ns
```

**ついに `new` に並びました。**

第23章では 167 倍負けていた相手に、2章で追いつきました。しかも私たちの実装は、まだ 200 行程度です。

> **もちろん、これは限定的な勝利です。** `new` はマルチスレッド対応で、任意のサイズを扱い、OS からメモリを追加取得します。私たちのアロケーターにはどれもありません。**同じ土俵ではない** ことは忘れないでください。


**わずかに改善しました。**

25.1 節で述べた「近似 best fit」の効果です。入る中で最も小さいクラスから取るので、大きな空きブロックが温存されます。

**探索を速くするための工夫が、断片化にも効いた** ——これは幸運ですが、偶然ではありません。サイズごとに整理するという行為自体が、秩序をもたらしています。

## 25.6 ビンの粒度と内部断片化

ここまでの設計では、**内部断片化がほとんど発生していません**。

理由は、要求サイズを切り上げていないからです。100 バイトの要求には、ちょうど 112 バイト(ヘッダ込み)のブロックを作ります。ビンは「入れる場所」を決めるだけで、サイズを変えていません。

**では、切り上げたらどうなるか。**

### 3つの設計を比べる

| 設計 | ビンの決め方 | 要求の切り上げ |
|---|---|---|
| **A** | ビンなし(単一リスト) | なし |
| **B** | 16 刻み + 2の冪(この章) | なし |
| **C** | **2の冪のみ** | **ビンのサイズまで切り上げ** |

設計 C は、`BinOf` を単純化して、要求を必ず 2 の冪に丸めます。

```cpp
    // 設計 C
    std::size_t RoundUpToPowerOfTwo(std::size_t n) noexcept
    {
        return std::bit_ceil(n);      // C++20
    }
```

`std::bit_ceil` は、その値以上で最小の2の冪を返します。

### 結果

```
設計   平均探索  Allocate   内部断片化   外部断片化   失敗
A       11.2     45.0 ns     0.9%       0.558       0
B        1.3     16.8 ns     0.9%       0.521       0
C        1.0     14.1 ns    23.7%       0.402       0
```

### 読み取れること

**設計 C は最速です。** ビンの中は完全に均一なので、探索が1回で確定します。

**設計 C は外部断片化も最も低い。** サイズの種類が少ないので、解放されたブロックが再利用されやすくなります。

**しかし内部断片化が 23.7%。** 確保したメモリの約4分の1が、使われないまま埋まっています。

```
100 バイトの要求 → 128 バイト確保(28% の無駄)
1025 バイトの要求 → 2048 バイト確保(50% の無駄)
```

### これが第26章への橋です

**設計 C は、実質的にバディシステムのサイズ方針です。**

第26章で実装するバディシステムは、この「2の冪に丸める」方式に、**分割と統合の仕組み** を加えたものです。

- 分割:大きいブロックを半分に割って使う
- 統合:相方(バディ)が両方空いたら、くっつけて元に戻す

相方の位置がアドレスから **計算だけで求まる** のが、バディの美しいところです。境界タグも探索も要りません。

代償は、いま見た内部断片化です。**最悪でほぼ 50%。** 第26章では、これを実測します。

## 25.7 分布に合わせて設計する

ビンの設計に「正解」はありません。**扱うサイズの分布に依存します。**

第15章で作ったヒストグラムを思い出してください。

```
  サイズ分布:
        32 B -      63 B :      114 ####
        64 B -     127 B :      686 ############
       128 B -     255 B :        0
      ...
     32.00 KB - 63.99 KB :       80 ########
    256.00 KB - 511.9 KB :       12 ########
```

**この分布なら、64〜127 バイトの範囲を細かく分けるべきです。** 686 件が集中しています。逆に 128〜255 の範囲にビンを用意しても、永久に空のままです。

### 実際のチューニング手順

1. 第15章のヒストグラムで、実際の分布を測る
2. 件数の多い範囲を細かく、少ない範囲を粗く分ける
3. 空のままのビンが多ければ、粒度を粗くする
4. 1つのビンに大量に溜まるなら、細かくする

**測ってから設計する。** 第4章から一貫している方針です。

### 汎用アロケーターにはできないこと

`malloc` は、どんなプログラムから呼ばれるか分かりません。だから、あらゆる分布に対して「そこそこ」のビン設計をするしかありません。

**私たちは、自分のゲームの分布を知っています。** パーティクルは 32 バイト、描画コマンドは 64 バイト、テクスチャは数百 KB——それが分かっているなら、そこに合わせられます。

第5章から繰り返している「知識を性能に変換する」の、また別の形です。

## 次章の予告

設計 C で見た「2の冪に丸める」方式は、内部断片化と引き換えに、探索と外部断片化を改善しました。

**この方式を、もう一歩推し進めます。**

第26章の **バディシステム** では、ブロックのサイズを 2 の冪だけに限定します。すると、次のことが起きます。

**分割:** 大きいブロックが必要なサイズになるまで、半分ずつに割っていく。

**統合:** 割ってできた2つの相方(バディ)が、両方とも空きになったら、くっつけて元のサイズに戻す。

そして最大の特徴——**相方の位置が、アドレスの排他的論理和だけで求まります。**

```cpp
buddy = address ^ size;
```

境界タグも、フッタも、フラグも要りません。**1回の XOR で隣が分かります。**

美しい方式ですが、代償ははっきりしています。最悪でメモリの半分が無駄になる。GPU メモリやテクスチャアトラスで今も現役である理由と、ゲームの CPU 側メモリで主流にならなかった理由を、実測しながら考えます。

---

> **コラム:dlmalloc(1987)が確立した設計**
>
> Doug Lea が1987年に公開した `dlmalloc` は、**現代の汎用アロケーターの原型** と呼ばれています。glibc の malloc(ptmalloc)はこれをマルチスレッド対応に改造したものですし、多くの組み込み向け実装も dlmalloc の系譜にあります。
>
> **この章までに私たちが作ったものは、dlmalloc の骨格とかなり近い形をしています。**
>
> ---
>
> **境界タグとフラグ**
>
> 第24章で実装したとおりです。dlmalloc も、サイズフィールドの下位2ビットをフラグに使っています。1つは `PREV_INUSE`(前のブロックが使用中か)、もう1つは `IS_MMAPPED`(この領域は mmap で取ったか)。
>
> 私たちの `kFlagPrevFree` は、`PREV_INUSE` の裏返しです。dlmalloc は「使用中なら 1」、私たちは「空きなら 1」。どちらでも構いません。
>
> ---
>
> **二層のビン**
>
> 第25章で実装したものです。dlmalloc では:
>
> - **small bins**:8 バイト刻みで 32 個。厳密一致
> - **tree bins / large bins**:対数刻み。中はサイズ順に並ぶ
>
> 私たちは 16 バイト刻みで 64 個にしましたが、発想は同じです。dlmalloc は大きいビンを木構造(トライ)で持ち、範囲内の探索も O(log n) にしています。
>
> **ビットマップによる「空でないビンの検索」も同じです。** dlmalloc は `binmap` という配列を持ち、ビット演算で次のビンを探します。
>
> ---
>
> **私たちが持っていないもの**
>
> dlmalloc には、まだ実装していない工夫がいくつもあります。
>
> **designated victim(dv)。** 直前に分割したブロックの残りを、ビンに戻さず「次の候補」として手元に置いておきます。同じサイズの確保が続くとき、ビンを検索せずに済みます。局所性を利用した最適化です。
>
> **fastbins。** 第24章で触れた遅延合体です。小さいブロックは解放しても合体せず、専用のリストに置きます。
>
> **top chunk。** ヒープの末端にある大きな空きブロックを特別扱いします。どのビンにも入らず、最後の手段として使われます。私たちの実装では、これも普通のブロックとしてビンに入っています。
>
> **mmap しきい値。** 大きな確保(既定 128 KB 以上)は、ヒープからではなく `mmap` で個別に取ります。解放時にそのまま OS へ返せるので、大きなブロックがヒープを分断しません。
>
> ---
>
> **設計思想:「そこそこ」を徹底する**
>
> Doug Lea 自身が書いている設計方針が興味深いものです。要約すると、**特定のパターンに最適化するのではなく、あらゆるパターンで極端に悪くならないことを目指す** というものでした。
>
> 汎用アロケーターは、次に何が来るか分かりません。第20章で見たとおり、どんな方針にも意地悪な入力が存在します。ならば「平均的に良い」より「**最悪でもそこそこ**」を狙う——これが汎用アロケーターの取るべき態度です。
>
> ---
>
> **そして、私たちの立場**
>
> この本の主題は、その正反対です。
>
> **私たちは、次に何が来るか知っています。** パーティクルは 32 バイト、フレームの終わりに全部消える、シーンごとにまとめてロードされる。
>
> だから、汎用アロケーターが払っている「あらゆる場合に備えるコスト」を、払わずに済みます。第5章で `Bump` が `new` に10倍勝ったのも、第21章で `Pool` が9倍勝ったのも、すべてこの構図でした。
>
> **dlmalloc は敵ではありません。** 万能を目指した先人の到達点であり、私たちが「何を捨てているか」を測るための基準です。第28章で全実装を比較するとき、この視点をもう一度使います。
