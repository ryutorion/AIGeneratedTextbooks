# 第1章 なぜモジュールが必要なのか

## この章について

本書は最終的に、`GameMath` というゲーム向けの数学ライブラリを C++20 モジュールで書き上げます。ベクトル、行列、クォータニオン、衝突判定 ── ゲーム開発者にとって馴染み深い題材を使いながら、モジュールの構文と設計を一つずつ身につけていきます。

ただし、この第1章にビルドするコードはありません。

いきなり `export module` と書き始めることもできますが、それでは「新しい書き方を覚えた」で終わってしまいます。モジュールは単なる構文の追加ではなく、C++ が40年間使ってきた「テキストを貼り付ける」というコード共有の仕組みそのものを置き換えるものです。何を置き換えるのかを知らないまま新しい道具を使うと、道具の形に合わない使い方をして、かえって苦労することになります。

そこでこの章では、次の3つを扱います。

1. いま私たちが使っているヘッダファイルという仕組みが、何を犠牲にして成り立っているのか(1.1、1.2)
2. モジュールがその犠牲のうち何を取り戻すのか(1.3)
3. モジュールでも取り戻せないものは何か(1.4)

特に 1.4 は重要です。モジュールには「ビルドが劇的に速くなる魔法」といった過剰な期待が寄せられがちで、その期待のまま導入すると失望します。最初に期待値を正しく設定しておきましょう。

なお、ビルドはしませんが、**手を動かす場面が2か所あります**。Visual Studio 2026 で追加された「プリプロセス」機能を使って、これから述べる問題を自分の目で確認してもらいます。ビルドを伴わないので、環境構築が済んでいなくても実行できます。

## 1.1 ヘッダファイルとプリプロセッサの限界

### 1.1.1 まず、いまのやり方を確認する

これから作る `GameMath` を、従来のヘッダファイルで書くとこうなります。

```cpp
// GameMath/Vector3.h
#pragma once

namespace gamemath {

struct Vector3 {
    float x, y, z;

    float Length() const;
    Vector3 Normalized() const;
};

Vector3 Cross(const Vector3& a, const Vector3& b);

} // namespace gamemath
```

```cpp
// GameMath/Matrix4x4.h
#pragma once
#include "Vector3.h"

namespace gamemath {

struct Matrix4x4 {
    float m[4][4];

    static Matrix4x4 Translation(const Vector3& t);
    static Matrix4x4 Scale(const Vector3& s);
};

} // namespace gamemath
```

```cpp
// GameMath/Quaternion.h
#pragma once
#include "Vector3.h"
#include "Matrix4x4.h"

namespace gamemath {

struct Quaternion {
    float x, y, z, w;

    Matrix4x4 ToMatrix() const;
    static Quaternion FromAxisAngle(const Vector3& axis, float radians);
};

} // namespace gamemath
```

ごく普通のコードです。何十年もこうやって書かれてきましたし、これで動きます。

そして、ゲーム本体の側にはこういうファイルが並びます。

```cpp
// Player.cpp
#include "GameMath/Quaternion.h"
#include "GameMath/Matrix4x4.h"
// ...
```

```cpp
// Enemy.cpp
#include "GameMath/Quaternion.h"
// ...
```

```cpp
// Camera.cpp
#include "GameMath/Matrix4x4.h"
// ...
```

`.cpp` ファイルが 300 個あるプロジェクトを想像してください。そのうち 250 個が、直接または間接的に `Vector3.h` を取り込んでいるとします。

このとき何が起きているのかを、正確に把握しておく必要があります。

### 1.1.2 `#include` は「コピー&ペースト」である

`#include` について、多くの入門書はこう説明します。「他のファイルの内容をその場所に取り込む」と。

この説明は正しいのですが、控えめすぎます。もっと正確に言えば ── `#include` は、コンパイラが C++ を理解し始める前に、単なるテキストとして丸ごと貼り付けられます。

プリプロセッサは C++ の文法を知りません。名前空間も、クラスも、テンプレートも知りません。知っているのは行と文字だけです。`#include "Vector3.h"` と書いてある行を、`Vector3.h` の中身に置き換える。それだけです。そして置き換えた結果に対して、また `#include` を探して置き換える。これを再帰的に繰り返します。

その結果できあがった巨大な一枚のテキストを、コンパイラが最初から読み始めます。この一枚のテキストが**翻訳単位(Translation Unit、TU)**です。

つまり、`Player.cpp` をコンパイルするとき、コンパイラが実際に読んでいるのは `Player.cpp` ではありません。`Player.cpp` を起点にすべての `#include` を展開しきった、何万行もあるテキストです。

### 1.1.3 【手を動かす1】プリプロセス結果を見てみる

言葉で説明するより、実物を見たほうが早いでしょう。

かつてこれを確認するには、コマンドプロンプトから `cl /P` を実行するか、プロジェクトのプロパティで「前処理ファイルの生成」を有効にしてビルドし直す必要がありました。設定を戻し忘れて後で困る、という定番の失敗もありました。

Visual Studio 2026(バージョン 18.0)からは、その手間がなくなりました。**ソリューションエクスプローラーでファイルを右クリックして「プリプロセス」(Preprocess)を選ぶだけ**で、そのファイル1つ分のプリプロセス結果が生成されます。プロジェクト設定は変更されませんし、プロジェクト全体のビルドも走りません。

早速使ってみましょう。

**手順**

1. Visual Studio 2026 を起動し、「新しいプロジェクトの作成」から **C++ の「コンソール アプリ」** を選びます(プロジェクトの詳しい設定は第2章で扱います。ここでは既定のままで構いません)
2. 生成された `.cpp` ファイルの中身を、次の内容に置き換えます

```cpp
#include <vector>

int main()
{
    std::vector<int> v;
    v.push_back(42);
    return static_cast<int>(v.size());
}
```

3. ソリューションエクスプローラーでその `.cpp` ファイルを**右クリック**し、コンテキストメニューから **[プリプロセス]**(英語版では **[Preprocess]**)を選びます

しばらくすると、プリプロセス結果がエディタで開きます。

**確認すること**

まず、行数を見てください。開いたファイルで `Ctrl + End` を押して末尾へ移動し、エディタ下部に表示されている行番号を確認します。

環境によって差はありますが、**数万行**という結果になるはずです。元のソースは8行、`#include` は1つだけだったのに、です。

次に、中身をざっと眺めてみてください。`std::vector` の実装だけでなく、アロケータ、イテレータ、例外クラス、型特性(type traits)、その他ありとあらゆるものが展開されています。私たちが使ったのは `push_back` と `size` の2つだけなのに。

さらに、`#include <iostream>` や `#include <Windows.h>` を追加して、もう一度 [プリプロセス] を実行してみてください。行数は跳ね上がります。ビルドを挟まずに何度でも試せるので、気になったヘッダを片っ端から入れてみるとよいでしょう。

> **補足: コマンドラインで同じことをする**
>
> この機能は内部的にはコンパイラの `/P` オプション(プリプロセスのみ実行してファイルに出力する)に相当します。CI やスクリプトから使いたい場合は、「Developer Command Prompt for VS 2026」で次のように実行できます。
>
> ```
> cl /std:c++latest /EHsc /P test.cpp
> ```
>
> `test.i` が生成されます。IDE の [プリプロセス] は、これを設定変更なしで手軽に行えるようにしたものです。

これが `#include` の実体です。そして、ここから5つの問題が生まれます。

### 1.1.4 問題1 ── 同じものを何度も解析している

先ほど見た数万行を、コンパイラは律儀に全部読みます。字句解析し、構文解析し、意味解析し、テンプレートを処理します。

そして `Player.cpp` でも、`Enemy.cpp` でも、`Camera.cpp` でも、**まったく同じことを最初からやり直します**。

`vector` の中身は `Player.cpp` をコンパイルするときも `Enemy.cpp` をコンパイルするときも1文字も変わりません。にもかかわらず、コンパイラは毎回ゼロから解析します。前回の結果を覚えておく仕組みがないからです。

コストの構造を書くとこうなります。

```
総ビルドコスト ≒ 翻訳単位の数 × 1つの翻訳単位に含まれるヘッダの総量
```

掛け算です。ここが問題の核心です。

`.cpp` ファイルを1つ追加すると、そのファイルが `#include` するヘッダの解析コストが丸ごと1回分増えます。ライブラリを1つ導入してヘッダを `#include` すると、それを使うすべての `.cpp` にコストが乗ります。プロジェクトが大きくなるほど、両方の数が同時に増えていきます。

`GameMath` の例で言えば、`Vector3.h` は 250 回解析されます。1回あたりが数ミリ秒でも、250 倍されれば無視できません。そして実際のプロジェクトでは、`Vector3.h` の裏には `<cmath>` があり、`<type_traits>` があり、それらの裏にさらに別のヘッダがあります。

### 1.1.5 問題2 ── マクロが漏れる

プリプロセッサはテキストしか見ていません。ということは、`#define` で定義された名前も、以降のテキスト全体に無差別に効きます。名前空間もクラスも、マクロを止められません。

C++ プログラマなら誰もが一度は踏む例を挙げます。

```cpp
// Player.cpp
#include <Windows.h>
#include "GameMath/Vector3.h"
```

`Windows.h` は、内部で次のようなマクロを定義します。

```c
#define max(a, b) (((a) > (b)) ? (a) : (b))
#define min(a, b) (((a) < (b)) ? (a) : (b))
```

一方、`Vector3.h` の中でこう書いていたとします。

```cpp
inline Vector3 Vector3::Normalized() const
{
    const float len = Length();
    if (len < std::numeric_limits<float>::min()) {  // ここ
        return Vector3{0.0f, 0.0f, 0.0f};
    }
    // ...
}
```

`std::numeric_limits<float>::min()` の `min` がマクロとして展開され、意味不明なコンパイルエラーになります。エラーメッセージは `<limits>` の中を指しており、初見では何が起きたのか分かりません。

#### 【手を動かす2】マクロ汚染を目で見る

これも [プリプロセス] で確認できます。先ほどのプロジェクトのファイルを、次の内容に書き換えてください。

```cpp
#include <Windows.h>

int main()
{
    return 0;
}
```

右クリック → [プリプロセス] を実行し、開いた結果の中を `Ctrl + F` で検索してみます。

- `numeric_limits` を検索 ── まだ出てきません(`<limits>` を入れていないので)
- では、1行目を `#include <Windows.h>` と `#include <limits>` の2行にして、もう一度プリプロセスしてください
- 結果の中で `min` を検索すると、`std::numeric_limits` の `min` 関数が、`Windows.h` のマクロによって置き換えられた無残な姿を見つけられるはずです

続いて、ファイルの先頭に `#define NOMINMAX` を1行追加して、3度目のプリプロセスをします。今度は `min` / `max` が壊れていないことを確認してください。

たった1行のマクロ定義の有無で、まったく無関係なヘッダの中身が変わる ── これがテキスト置換モデルの実態です。**同じヘッダが、取り込む側の事情によって挙動を変える**わけです。

しかも、`Enemy.cpp` が `Windows.h` を `#include` していなければ、そちらでは何の問題も起きません。ヘッダを書いた人には、どちらの世界で自分のコードが展開されるのか予測できません。

対策として `#define NOMINMAX` を書く定型句が知られていますが、これは「あらかじめ知っている人だけが回避できる」対処であり、しかも `Windows.h` に限った話でもありません。

- `<rpcndr.h>` は `small` を `char` として定義します。`int small = 3;` と書けなくなります
- Windows API の多くの関数名には、`#define DrawText DrawTextW` のような A/W 切り替えマクロが仕込まれています。自作のクラスに `DrawText` というメンバ関数を作ると、リンクエラーになります
- かつて `near` / `far` がマクロとして定義されていた時代には、カメラの `float near;` `float far;` というメンバが軒並み壊れました

これらはすべて「テキスト置換が名前空間の壁を越えてしまう」という一点から生じています。C++ は名前の衝突を防ぐために名前空間を用意しましたが、マクロは名前空間より前の層で動くため、その保護がまったく効きません。

### 1.1.6 問題3 ── 隠せない

ライブラリを設計するとき、「利用者に見せたいもの」と「見せたくない実装の詳細」を分けたくなります。

しかしヘッダには、利用者に見せたくないものまで書かざるを得ません。

```cpp
// GameMath/Quaternion.h
#pragma once
#include "Vector3.h"
#include "Matrix4x4.h"
#include <cmath>

namespace gamemath {

namespace detail {
    // 内部でしか使わないヘルパー
    inline float FastInverseSqrt(float x) { /* ... */ }
    constexpr float kEpsilon = 1e-6f;
}

struct Quaternion {
    float x, y, z, w;

    Matrix4x4 ToMatrix() const;

private:
    void NormalizeInPlace();   // private だが、ここに書くしかない
};

} // namespace gamemath
```

問題は3つあります。

第一に、`detail` 名前空間は「見ないでください」というお願いにすぎません。利用者が `gamemath::detail::FastInverseSqrt` と書けば、普通に呼べてしまいます。呼ばれてしまえば、それは事実上の公開 API です。次のバージョンで削除すると、誰かのコードが壊れます。

第二に、`private` メンバは**アクセスできないだけで、見えています**。コンパイラはクラス定義全体を読み込みますし、そのメンバの型が必要とするヘッダもすべて `#include` する必要があります。だから `Quaternion.h` は、利用者が絶対に触らない実装の都合のために `<cmath>` を引きずり込みます。

第三に、`private` メンバを1つ追加しただけで、`Quaternion.h` を `#include` しているすべてのファイルが再コンパイルされます。公開インターフェースは何も変わっていないのに、です。

C++ のアクセス制御(`public` / `private`)は「使えるかどうか」を制御しますが、「見えるかどうか」は制御しません。この差が、ヘッダの肥大化と再コンパイルの連鎖を生みます。

### 1.1.7 問題4 ── 順序に依存する

`#include` は書いた順にテキストを貼り付けます。したがって、順序を変えると結果が変わり得ます。

先ほどの `Windows.h` の例がまさにそれでした。

```cpp
#include <Windows.h>
#include "GameMath/Vector3.h"   // 壊れる

#include "GameMath/Vector3.h"
#include <Windows.h>            // 壊れない
```

ヘッダが「自己完結している」(必要なものを自分で `#include` している)よう気をつけていても、マクロによる汚染は防げません。

これは、コードレビューで指摘しづらく、自動整形ツールが `#include` をアルファベット順に並べ替えた瞬間に壊れる、という性質の悪い依存関係です。

### 1.1.8 問題5 ── 静かに壊れる

ここまでの問題はコンパイルエラーになるので、まだ救いがあります。最後に、エラーにならない問題を挙げます。

`Transform` 構造体に、ビルド設定でスケールを持たせるかどうかを切り替えたいとします。

```cpp
// GameMath/Transform.h
#pragma once
#include "Vector3.h"
#include "Quaternion.h"

namespace gamemath {

struct Transform {
    Vector3 position;
    Quaternion rotation;
#ifdef GAMEMATH_ENABLE_SCALE
    Vector3 scale;
#endif
};

} // namespace gamemath
```

そして、あるファイルではマクロが定義されていて、別のファイルでは定義されていなかったとします。

```cpp
// Renderer.cpp
#define GAMEMATH_ENABLE_SCALE
#include "GameMath/Transform.h"
// Transform のサイズは 32 バイト
```

```cpp
// Physics.cpp
#include "GameMath/Transform.h"
// Transform のサイズは 20 バイト
```

同じ名前の型が、翻訳単位ごとに違うレイアウトを持ちました。これは **ODR(One Definition Rule、単一定義規則)違反**です。

C++ の規格上、この動作は未定義です。しかし現実には、**コンパイルは通り、リンクも通ります**。リンカは `Transform` のサイズを検証しませんし、そもそも検証する情報を持っていません。

そして実行時、`Renderer.cpp` の関数が書き込んだ `scale` の領域を、`Physics.cpp` 側は別の変数の領域だと思って読み書きします。メモリが静かに壊れます。

クラッシュするのは、たいてい無関係な場所です。デバッガで追っても原因にたどり着けません。再現条件が「Release ビルドのときだけ」だったりします。

余談ですが、この種の問題を追うときにも [プリプロセス] は有効です。両方のファイルのプリプロセス結果を生成し、`Transform` の定義部分を見比べれば、レイアウトが違うことを目視で確認できます。ただし ── これは**問題が起きた後に原因を突き止める**手段であって、問題を**未然に防ぐ**手段ではありません。

これは極端な作り話に見えるかもしれませんが、ビルド構成が増え、プラットフォームが増え、プリコンパイル済みヘッダーやビルドシステムのマクロ定義が絡み合ってくると、現実に起こります。**プリプロセッサは、同じ名前のものが同じであることを保証する仕組みを一切持っていない**からです。

## 1.2 インクルードガードと `#pragma once` が解決できなかったこと

「その問題ならインクルードガードで解決するのでは」と思われたかもしれません。ここを整理しておきます。

### 1.2.1 インクルードガードが守る範囲

インクルードガードはこういうものでした。

```cpp
#ifndef GAMEMATH_VECTOR3_H
#define GAMEMATH_VECTOR3_H
// ...
#endif
```

これが防いでいるのは、**1つの翻訳単位の中で、同じヘッダのテキストが2回展開されること**です。

`Quaternion.h` は `Vector3.h` と `Matrix4x4.h` を `#include` し、`Matrix4x4.h` もまた `Vector3.h` を `#include` していました。ガードがなければ `Vector3` の定義が2回現れ、「クラスの再定義」というコンパイルエラーになります。ガードはこれを防ぎます。

ここで重要なのは、**この範囲しか守っていない**ことです。

`Player.cpp` のコンパイルが終わり、`Enemy.cpp` のコンパイルが始まるとき、`GAMEMATH_VECTOR3_H` というマクロは消えています。翻訳単位が変われば、プリプロセッサの状態は完全にリセットされます。だから `Vector3.h` は 250 個の `.cpp` すべてで、250 回まるごと展開され、250 回解析されます。

先ほど [プリプロセス] で見た数万行を思い出してください。あれは、インクルードガードがすべて正しく機能した**後**の姿です。ガードがあってもなお、あの量になります。

インクルードガードは正しさのための仕組みであって、速度のための仕組みではありません。1.1.4 で見た掛け算の構造には、まったく手を触れていないのです。

同様に、マクロ汚染も、隠蔽できない問題も、順序依存も、ODR 違反も、インクルードガードとは無関係です。

### 1.2.2 `#pragma once` も同じ

`#pragma once` はインクルードガードを1行で書けるようにしたもので、守る範囲は変わりません。加えて、こちらは「同じファイルかどうか」をファイルシステム上の同一性で判定するため、シンボリックリンク、ネットワークパス、同じファイルへの複数の相対パスが絡むと判定を誤ることがあります。

書きやすさの改善であって、モデルの改善ではありません。

### 1.2.3 プリコンパイル済みヘッダー(PCH)

では、ビルド時間の問題に対する既存の答えはあったのでしょうか。

あります。プリコンパイル済みヘッダー(PCH)です。「よく使うヘッダ群をあらかじめ解析して、その状態をファイルに保存しておき、各翻訳単位ではそれを読み込むところから始める」という仕組みです。

これは 1.1.4 の掛け算に対する、初めての本格的な対策でした。実際に効果もあります。

しかし制約が多いのです。

- **全部か無か**。PCH は「ここまで解析した状態のスナップショット」なので、その中身を部分的に取り出すことはできません。`Vector3` だけが欲しくても、PCH に含まれるすべてを読み込みます
- **順序が固定される**。PCH に入れるヘッダの順序は1通りに決まります。前節の順序依存問題は解決せず、むしろ固定化されます
- **プロジェクト単位**。1つのプロジェクトが同時に使える PCH は基本的に1つです。ライブラリごとに最適な PCH、といった使い分けができません
- **マクロは相変わらず漏れる**。PCH に `Windows.h` を入れれば、`min` / `max` マクロはプロジェクト全体に漏れます
- **依存が太る**。PCH に含まれるヘッダを1つ書き換えると、PCH を作り直し、プロジェクト全体をリビルドすることになります
- **配布できない**。PCH はコンパイラのバージョンやオプションに強く結びついたバイナリで、ライブラリの配布物にはなりません

つまり PCH は、「テキスト展開を毎回やり直すのが遅い」という症状に対する、プロジェクト内部限定の緩和策です。原因であるテキスト展開モデルそのものは残っています。

### 1.2.4 前方宣言と Pimpl

ヘッダの肥大化と再コンパイルの連鎖に対しては、前方宣言と Pimpl イディオムという定石があります。

```cpp
// 前方宣言でヘッダの依存を切る
namespace gamemath { struct Vector3; }
```

```cpp
// Pimpl で実装を隠す
class Renderer {
public:
    Renderer();
    ~Renderer();
    void Draw();
private:
    struct Impl;
    std::unique_ptr<Impl> impl_;
};
```

どちらも有効なテクニックですが、`GameMath` のようなライブラリでは特に相性が悪いのです。

前方宣言はテンプレートに対してほぼ使えません。`Vector<T, N>` のようなテンプレートは、使う側が定義全体を見られなければインスタンス化できないからです。第8章で詳しく扱いますが、テンプレートが増えるほど前方宣言でできることは減っていきます。

Pimpl はさらに深刻です。`Vector3` の加算のたびにポインタを1つ辿り、インライン展開の機会を失う ── ゲームの内側のループで毎フレーム何万回も呼ばれる関数に対して、これは受け入れられません。数学ライブラリにとって、インライン展開されることは機能要件の一部です。

そして両者に共通するのは、**これらが人間の手作業だ**という点です。前方宣言できる箇所を探し、Pimpl に切り出す判断をし、それを保守し続ける。誰かが `#include` を1行足せば、積み上げた工夫は崩れます。

### 1.2.5 Unity ビルド

もう1つの定番が Unity ビルド(Jumbo ビルド)です。複数の `.cpp` を1つのファイルに `#include` してまとめてコンパイルし、翻訳単位の数そのものを減らします。

```cpp
// Unity_Gameplay.cpp
#include "Player.cpp"
#include "Enemy.cpp"
#include "Camera.cpp"
// ...
```

1.1.4 の掛け算の、左側の項を小さくするアプローチです。効果は大きく、ゲーム業界では広く使われてきました。

代償も大きいのですが。翻訳単位が統合されるということは、**それまで別々だったものが全部つながる**ということです。マクロは以前より遠くまで漏れ、`static` 変数や無名名前空間の名前が衝突し、`using namespace` の影響範囲が広がります。ファイルの並び順を変えただけでビルドが壊れることもあります。そして、1ファイルを編集したときの再ビルド範囲は、まとめた分だけ大きくなります。

要するに、ビルド時間のために、カプセル化をさらに犠牲にしています。

### 1.2.6 共通する限界

インクルードガード、`#pragma once`、PCH、前方宣言、Pimpl、Unity ビルド。

これらはすべて有効な技術で、実際に多くのプロジェクトを支えてきました。しかし共通点があります。**どれもプリプロセッサによるテキスト展開という前提を受け入れた上での、その中での工夫だ**ということです。

テキスト展開を前提にする限り、次のことは原理的に避けられません。

- 展開されたテキストは、翻訳単位ごとに毎回解析し直すしかない
- テキスト置換であるマクロは、C++ の名前空間やアクセス制御では止められない
- テキストとして貼り付けたものは、貼り付けた側から全部見える
- 順序を変えれば結果が変わり得る
- 同じ名前のものが同じである保証はどこにもない

C++20 のモジュールは、この前提そのものを置き換えます。

## 1.3 モジュールが持ち込む3つの変化

先に、完成形の雰囲気だけ見ておきましょう。第4章で実際に書くコードの先取りです。

```cpp
// GameMath/Vector3.ixx
module;                       // グローバルモジュールフラグメント(第6章)
#include <cmath>

export module gamemath.vector;   // このファイルは gamemath.vector モジュールである

namespace gamemath {

export struct Vector3 {          // export したものだけが外から見える
    float x, y, z;

    float Length() const;
    Vector3 Normalized() const;
};

export Vector3 Cross(const Vector3& a, const Vector3& b);

// export なし = このモジュールの外からは存在しない
float FastInverseSqrt(float x) { /* ... */ }
constexpr float kEpsilon = 1e-6f;

} // namespace gamemath
```

```cpp
// Player.cpp
import gamemath.vector;       // #include ではなく import

int main()
{
    gamemath::Vector3 v{1.0f, 2.0f, 3.0f};
    float len = v.Length();
    // gamemath::FastInverseSqrt(4.0f);  // ← コンパイルエラー。存在しない
}
```

見た目の差は `#include "..."` が `import ...;` になった程度に見えます。しかし、起きていることはまったく違います。3つの変化として整理します。

### 1.3.1 変化1 ── テキストではなく「意味」を取り込む

`#include` はテキストを貼り付けました。`import` は貼り付けません。

`gamemath.vector.ixx` をコンパイルすると、コンパイラは中身を解析し、その結果を**構造化されたデータ**として保存します。MSVC ではこれを `.ifc` という拡張子のファイルに出力します(第2章で実物を見ます)。

`import gamemath.vector;` と書いた翻訳単位は、この `.ifc` を読み込みます。テキストを解析し直すのではなく、解析済みの「意味」を直接受け取ります。

ここで一つ、実感を伴う確認をしておきます。1.1.3 で作ったプロジェクトで、`import` を使ったファイルを [プリプロセス] にかけると、`import` の行はそのまま残ります。プリプロセッサは `import` を展開しないからです ── そもそも展開すべきテキストが存在しません。プリプロセッサの仕事はそこで終わり、続きはコンパイラが `.ifc` を読んで行います。

この違いから、いくつかの性質が自動的に導かれます。

**マクロは越えてこない。** `.ifc` に入っているのは C++ の宣言や定義であって、プリプロセッサの状態ではありません。モジュール内で `#define` したマクロは、`import` した側に一切影響しません。1.1.5 で目撃した `min` / `max` 問題は、構造的に起こり得なくなります。

同じ理由で、`import` する側で定義したマクロも、モジュールの中身に影響しません。モジュールは、それを書いたときの状態でコンパイルされ、その結果が配られます。取り込む側の事情でモジュールの意味が変わることはありません。1.1.8 の ODR 違反は、少なくともマクロを原因としては発生しなくなります。

**順序が意味を持たない。** テキストの貼り付けではないので、`import` を書く順序は結果に影響しません。

```cpp
import gamemath.vector;
import gamemath.matrix;

// これと完全に同じ
import gamemath.matrix;
import gamemath.vector;
```

自動整形ツールが並べ替えても壊れません。

**依存が伝染しない。** `Vector3.ixx` が内部で `<cmath>` を使っていても、`import gamemath.vector;` した側に `<cmath>` の中身は流れ込みません。ヘッダなら、`#include "Vector3.h"` した時点で `<cmath>` のすべてが降ってきていました。

### 1.3.2 変化2 ── 公開するものを自分で選べる

モジュールでは、`export` を付けたものだけが外から見えます。付けなかったものは、外から**存在しないのと同じ**になります。

1.1.6 で書いた `detail` 名前空間を思い出してください。あれは「見ないでください」というお願いでした。モジュールでは、`export` しない限りそれは本当に見えません。呼ぼうとすればコンパイルエラーです。

これはコメントや命名規則による約束ではなく、言語機能による保証です。`detail` という名前空間を作る必要すらなくなります。

技術的には、名前付きモジュール内で `export` されていない実体は**モジュールリンケージ**を持ちます。外部リンケージでも内部リンケージでもない、第三のリンケージです。これは次のことを意味します。

- 他の翻訳単位から名前で参照できない
- **他のモジュールが同じ名前を使っても衝突しない**

2番目は地味ですが重要です。`gamemath.vector` と `gamemath.matrix` が、それぞれ独立に `Clamp` という非公開のヘルパー関数を持てます。互いの存在を気にする必要がありません。ヘッダの世界では、`static` を付けるか無名名前空間に入れるかして自衛する必要がありました。

そして、非公開の実装を変更しても、公開インターフェースが変わらなければ、`import` している側の再コンパイルは不要になります(第11章で詳しく扱います)。1.1.6 で見た「`private` メンバを1つ足したら全部リビルド」から解放されます。

なお、ここには「見える(visible)」と「到達可能(reachable)」という微妙な区別があり、これを理解していないと後半のエラーメッセージが読めなくなります。第7章でまとめて扱いますので、いまは「`export` しないと使えない」で十分です。

### 1.3.3 変化3 ── 解析は1回だけ

1.1.4 の掛け算をもう一度見ます。

```
ヘッダ:     翻訳単位の数 × ヘッダの総量
```

モジュールではこう変わります。

```
モジュール: モジュールの数 × 1回の解析  +  翻訳単位の数 × .ifc の読み込み
```

掛け算が足し算に分解されました。`Vector3` の解析は、`.ifc` を作るときの1回だけです。250 個の `.cpp` は、その結果を読むだけになります。

`.ifc` の読み込みは、テキストの解析よりずっと安価です。すでに構造化されたデータなので、字句解析も構文解析も必要ありません。必要な部分だけを取り出すこともできます。

ただし、ここで新しいコストが1つ生まれます。**ビルド順序の依存**です。

`Player.cpp` をコンパイルするには、`gamemath.vector.ifc` が先に存在していなければなりません。ヘッダの時代には、`.cpp` ファイルはどんな順序でも(何なら全部同時に)コンパイルできました。モジュールでは、依存関係の順にビルドする必要があります。

そのため、ビルドシステムは事前にソースを走査して「どのファイルがどのモジュールを `import` しているか」を調べ、ビルドの順序を決める必要があります。Visual Studio はこれを自動でやってくれますが、無料ではありません。並列度が下がる場面もあります。

このトレードオフは、第20章と第21章で実際に計測しながら確認します。

### 1.3.4 3つの変化が同時に効く例

3つの変化は独立したものではなく、組み合わさって効きます。1.1 で挙げた問題との対応を整理しておきます。

| 1.1 で見た問題 | モジュールでは |
|---|---|
| 何度も解析する | 解析は1回、以降は `.ifc` を読むだけ |
| マクロが漏れる | マクロは `import` を越えない |
| 隠せない | `export` しないものはモジュールリンケージで真に隠れる |
| 順序に依存する | `import` の順序は意味を持たない |
| 静かに壊れる(ODR) | 取り込む側の事情でモジュールの意味は変わらない |

> **コラム: `.ifc` ファイルの正体**
>
> `.ifc` は IFC(Interface File Format)の略で、MSVC がモジュールのインターフェースを保存する形式です。他のコンパイラは別の形式を使います(Clang は `.pcm`、GCC は `.gcm`)。
>
> 規格用語ではこれらをまとめて **BMI(Binary Module Interface)** と呼びます。ただし、規格は BMI の存在すら要求していません。「`import` したときに同じ意味になること」だけが規定されていて、どう実装するかはコンパイラの自由です。
>
> 実用上重要なのは、**`.ifc` は配布物ではない**という点です。コンパイラのバージョン、コンパイルオプション、ターゲットアーキテクチャに強く結びついており、少しでも違えば読めません。ソースからビルドする中間生成物であって、ヘッダファイルの代わりに配るものではありません。第20章で改めて扱います。

## 1.4 モジュールが解決しないこと

ここまで読むと、モジュールが万能に思えてくるかもしれません。過剰な期待は失望のもとですので、限界を先に押さえておきます。

### 1.4.1 「モジュールにすれば速くなる」わけではない

これが最も広く誤解されている点です。

モジュールがビルド時間を改善する仕組みは 1.3.3 で見たとおりですが、その効果は**モジュールの分割設計**に完全に依存します。

たとえば、`GameMath` のすべてを1つの `gamemath` モジュールにまとめ、そこからすべてを `export` したとします。すると、

- `Vector3` しか使わない `.cpp` も、行列やクォータニオンや衝突判定を含む巨大な `.ifc` を読み込みます
- `Quaternion` の宣言を1行変えると、`gamemath` を `import` しているすべての翻訳単位が再コンパイルされます

これは、巨大な `GameMath_All.h` を全員が `#include` しているのと構造的に変わりません。ヘッダ版より遅くなることさえあります。

さらに、既存のコードを機械的にモジュールに置き換えただけでは、効果はほとんど出ません。もともとヘッダの依存関係が絡み合っているなら、モジュールにしても絡み合ったままです。**依存関係の設計をやり直して初めて**、モジュールの利点が出ます。

本書が第9章から第12章までを分割設計に費やすのは、そのためです。

### 1.4.2 パッケージ管理でもバージョン管理でもない

`import gamemath.vector;` という記述を見ると、Python や Rust や JavaScript のモジュールシステムを連想するかもしれません。しかし C++ のモジュールは、それらとは役割の範囲が違います。

- **モジュール名とファイルパスの対応は規定されていません。** `gamemath.vector` というモジュールが `Vector3.ixx` に書かれていても構いません。ドットは階層構造ではなく、ただの名前の一部です
- **バージョンの概念がありません。** 「`gamemath` の 2.0 以上」を要求する手段は言語にはありません
- **依存の取得も解決もしません。** ライブラリの入手は、これまで通り vcpkg や NuGet や手動配置の仕事です

C++ のモジュールが担当するのは、**1つのビルドの中でのコードの構造化**だけです。その外側は従来通り、ビルドシステムとパッケージマネージャの領分です。

### 1.4.3 バイナリ配布の問題は解決しない

`GameMath` を `.lib` として配布したいとします。利用者は `.ifc` を受け取れば `import` できる ── とはいきません。

1.3.3 のコラムで触れたとおり、`.ifc` はコンパイラのバージョンやオプションに強く依存します。あなたがビルドした `.ifc` は、利用者の環境ではまず読めません。

現実的な選択肢は、モジュールのソース(`.ixx`)を配布して利用者側でビルドしてもらうか、従来通りヘッダを併せて提供するかです。C++ の ABI 問題そのものは、モジュールでは何も変わっていません。

### 1.4.4 マクロがなくなるわけではない

モジュールは名前付きモジュールからのマクロのエクスポートを禁じますが、マクロ自体を廃止したわけではありません。

プラットフォーム分岐、ビルド構成の切り替え、コンパイラ固有の属性 ── これらは今もマクロの仕事です。そして、`.ixx` ファイルの中でも `#include` や `#ifdef` は動きます(第6章で扱うグローバルモジュールフラグメントという領域で)。[プリプロセス] 機能が今後も役に立つ、ということでもあります。

むしろ注意が必要なのは、**マクロで制御していた設定がモジュール境界を越えなくなる**ことです。第16章で SIMD の有効・無効をマクロで切り替えようとして行き詰まり、コンセプトによる代替に書き換える、という体験をしてもらいます。これはモジュール移行でよく詰まる箇所です。

なお、第18章で扱う**ヘッダユニット**は例外で、こちらはマクロをエクスポートします。名前付きモジュールとヘッダユニットの、この違いは重要です。

### 1.4.5 テンプレートのコストは消えない

`Vector<T, N>` のようなテンプレートは、使われた場所でインスタンス化されます。これはモジュールでも変わりません。

モジュールが削るのは「テンプレートの**定義を読む**コスト」です。「テンプレートを**実体化する**コスト」ではありません。テンプレートを多用したライブラリでは、後者が支配的なことも珍しくありません。

### 1.4.6 周辺環境はまだ発展途上

C++20 が策定されてから年月が経ち、MSVC のモジュール対応はかなり成熟しました。しかし周辺はまだ追いついていません。

- サードパーティライブラリの大半は、今もヘッダで提供されています
- IntelliSense や静的解析ツールが、モジュールをまたぐ解析で不完全な挙動を見せることがあります
- コンパイラごとに実装の細部が異なり、MSVC で通るコードが Clang で通らないことがあります(付録E)
- エラーメッセージが、ヘッダの時代よりさらに読みにくいことがあります(付録B)

本書が MSVC と Visual Studio 2026 に限定するのは、こうした差異に振り回されずに、まず言語機能そのものを理解してもらうためです。

### 1.4.7 それでもモジュールを学ぶ理由

限界を並べましたが、モジュールを避ける理由にはなりません。

ビルド時間は、正しく設計すれば確かに改善します。それ以上に価値があるのは、**カプセル化が言語機能として保証される**ことです。「見せたくないものを本当に見せない」は、規約やレビューでは達成できず、モジュールで初めて可能になりました。マクロ汚染と順序依存が原理的に消えることも、大規模なコードベースでは相当な安心感があります。

そして何より、これが C++ の標準的な書き方になっていく方向は、もう定まっています。標準ライブラリ自体が `import std;` として提供され、新しい規格の機能はモジュールを前提に設計されつつあります。

## 1.5 この章のまとめ

- `#include` はプリプロセッサによるテキストの貼り付けであり、C++ の文法より前の層で動く
- Visual Studio 2026 の [プリプロセス] 機能を使えば、その実態(8行のソースが数万行になること、マクロが他のヘッダを壊すこと)を自分の目で確認できる
- そこから5つの問題が生じる ── 重複した解析、マクロ汚染、隠蔽の不可能さ、順序依存、ODR 違反
- インクルードガードは、1つの翻訳単位内での重複展開しか防がない。ビルド時間もマクロ汚染も守備範囲外
- PCH、前方宣言、Pimpl、Unity ビルドはいずれも有効だが、テキスト展開という前提の内側での工夫にとどまる
- モジュールは3つの変化をもたらす ── 意味の取り込み、明示的なエクスポート、1回だけの解析
- ただしモジュールは、自動的にビルドを速くする魔法ではなく、パッケージ管理でもなく、ABI 問題も解決しない。効果は分割設計に依存する

## 次章に向けて

第2章では、Visual Studio 2026 でモジュールをビルドできる環境を作ります。プロジェクトを作り、コンパイラオプションを設定し、`.ifc` ファイルが実際に生成される様子を確認します。

コードはまだ書きません。書くのは第3章、`export module hello;` の1行からです。
