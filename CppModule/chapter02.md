# 第2章 環境を整える

## この章について

第1章では、ヘッダファイルという仕組みが何を犠牲にしているか、モジュールがそれをどう変えるかを見ました。この章では、実際にモジュールをビルドできる環境を作ります。

やることは4つです。

1. Visual Studio 2026 に必要なものが入っているか確認する(2.1)
2. プロジェクトを作り、言語標準を設定する(2.2)
3. モジュールに関係するプロジェクト設定を、1つずつ意味を確かめながら見ていく(2.3)
4. 生成された `.ifc` ファイルを実際に探して覗いてみる(2.4)

そして最後に、うまくいかないときのチェックリストを用意します(2.5)。

### この章で書くコードについて

第1章の最後に「コードを書くのは第3章から」と書きました。しかし `.ifc` ファイルを見るには、モジュールを1つビルドする必要があります。矛盾しているようですが、そうではありません。

**この章で書くコードは、教材ではなく体温計です。**

環境が正しく組み上がっているかを測るためだけのもので、意味は説明しません。「なぜこう書くのか」は第3章で改めて、一行ずつ扱います。この章では、写して、ビルドが通ることだけを確認してください。

この章で作るプロジェクトは**使い捨て**です。第3章では新しく作り直しますので、動作確認が済んだら消してしまって構いません。

## 2.1 Visual Studio 2026 のインストールと必要なワークロード

### 2.1.1 前提とするバージョン

本書は次の環境を前提とします。

| 項目 | 前提 |
|---|---|
| OS | Windows 11 |
| IDE | Visual Studio 2026 バージョン 18.0 以降 |
| コンパイラ | MSVC ビルドツール v14.50 以降 |
| ターゲット | x64 |

エディションは Community / Professional / Enterprise のいずれでも構いません。本書で使う機能に差はありません。

### 2.1.2 必要なワークロード

Visual Studio Installer を起動します。すでに Visual Studio 2026 をインストール済みの場合は、一覧から「変更」を選んでください。

必要なワークロードは1つだけです。

- **C++ によるデスクトップ開発**(Desktop development with C++)

これにチェックを入れると、MSVC ビルドツール、Windows SDK、CMake ツールなどが一式入ります。ゲーム開発をされている方は「C++ によるゲーム開発」も入っているかもしれませんが、本書の範囲では不要です(入っていても支障はありません)。

### 2.1.3 個別コンポーネントの確認

インストーラーの「個別のコンポーネント」タブで、次の2つが選択されていることを確認しておくと安心です。通常はワークロードに含まれているので、確認だけで済むはずです。

- **MSVC v145 - VS 2026 C++ x64/x86 ビルド ツール**(バージョン番号は更新される可能性があります)
- **Windows 11 SDK**

もう1つ、本書の後半で使うものがあります。

- **Windows 用 C++ CMake ツール**

これは第20章で CMake を扱うときに必要になります。今すぐ入れなくても構いませんが、後で入れ直す手間を考えると、今チェックしておくのが楽です。

> **モジュール専用のコンポーネントは要りません**
>
> かつて、モジュールを使うために「C++ Modules for v143 build tools(実験的)」という個別コンポーネントが必要だった時期がありました。現在は不要です。標準的な C++ ワークロードに、モジュールのサポートは完全に含まれています。
>
> 古い記事を参考にしてこのコンポーネントを探し、見つからずに困る ── というのはよくある躓きです。探す必要はありません。

### 2.1.4 バージョンを確認する

インストールが済んだら、実際のバージョンを確認しておきましょう。後でトラブルが起きたとき、この情報が切り分けの出発点になります。

**IDE のバージョン**

Visual Studio を起動し、メニューの **[ヘルプ] → [Microsoft Visual Studio のバージョン情報]** を開きます。「Visual Studio Professional 2026 バージョン 18.x.x」のように表示されます。

**コンパイラのバージョン**

Windows のスタートメニューから「**Developer Command Prompt for VS 2026**」を起動し、次のように入力します。

```
cl
```

引数なしで `cl` を実行すると、バージョン情報だけが表示されます。

```
Microsoft(R) C/C++ Optimizing Compiler Version 19.5x.xxxxx for x64
```

`19.5x` の部分がコンパイラのバージョンです。MSVC ツールセットのバージョン(14.5x)とは表記が違うので混乱しやすいのですが、対応関係はこうなっています。

| ツールセット | コンパイラ | 同梱 |
|---|---|---|
| v14.4x | 19.4x | Visual Studio 2022 |
| v14.5x | 19.5x | Visual Studio 2026 |

`19.5` 未満が表示された場合は、VS 2022 のコマンドプロンプトを起動しているか、古いツールセットが選択されています。

## 2.2 プロジェクトを作り、言語標準を設定する

### 2.2.1 「空のプロジェクト」を作る

Visual Studio を起動し、「新しいプロジェクトの作成」を選びます。

テンプレートの一覧から、**C++ の「空のプロジェクト」**(Empty Project)を選んでください。「コンソール アプリ」ではありません。

第1章の実験では「コンソール アプリ」を使いましたが、この章では「空のプロジェクト」を使います。理由は、コンソール アプリのテンプレートが `pch.h` や `framework.h` といったファイルを自動生成することがあり、それらがプリコンパイル済みヘッダーの設定を伴うためです。第1章で見たとおり PCH はモジュールとは別系統の仕組みで、両方が有効だと観察したいものが見えにくくなります。何もない状態から積み上げたほうが、設定の意味がはっきりします。

プロジェクト名は `ModuleSmokeTest` としておきましょう。「体温計」という位置づけがファイル名からも分かるようにしておきます。

作成すると、ソリューションエクスプローラーにはフィルター(ソース ファイル、ヘッダー ファイル、リソース ファイル)だけがあり、ファイルは1つもない状態になります。

### 2.2.2 構成とプラットフォームを固定する

プロジェクト設定に触る前に、**必ず**押さえておくべき点があります。

Visual Studio のプロジェクトプロパティは、**構成**(Debug / Release)と**プラットフォーム**(x64 / Win32)の組み合わせごとに別々の値を持ちます。Debug で設定した内容は、Release には反映されません。

「設定したはずなのに動かない」というトラブルの、体感でいえば半分近くがこれです。

そこで、これから設定を変更するときは、毎回次の手順を踏んでください。

1. ソリューションエクスプローラーでプロジェクト名を右クリック → **[プロパティ]**
2. ダイアログ上部の **[構成]** を **「すべての構成」** に変更
3. **[プラットフォーム]** を **「すべてのプラットフォーム」** に変更
4. その状態で設定を変更する

本書では、以降この手順を毎回は書きません。「プロパティを開く」と書いてあったら、この4ステップだと思ってください。

なお、ツールバーの構成は **Debug / x64** にしておきます。本書は x64 前提です。

### 2.2.3 C++ 言語標準を設定する

プロパティを開き(上記の手順で)、左のツリーから **[構成プロパティ] → [C/C++] → [言語]** を選びます。

**C++ 言語標準**(C++ Language Standard)という項目があります。

Visual Studio 2026 では、新規 C++ プロジェクトの既定がすでに **ISO C++20 標準 (/std:c++20)** になっています。以前のバージョンでは C++14 が既定だったので、ここは改善されました。

C++20 のままでもモジュールは使えます。モジュールは C++20 の機能だからです。

しかし本書では、これを **ISO C++ 最新 (/std:c++latest)** に変更します。

理由は `import std;` です。標準ライブラリをモジュールとして取り込む機能は C++23 で入ったもので、`/std:c++20` では使えません。そして次の項で設定する「ISO C++23 標準ライブラリ モジュールのビルド」は、`/std:c++latest` との組み合わせでのみ機能します。

```
C++ 言語標準 : ISO C++ 最新 (/std:c++latest)
```

> **`/std:c++latest` の注意点**
>
> `/std:c++latest` は「今のコンパイラが実装している最新のものを全部有効にする」という設定です。つまり、まだ標準として確定していない機能や、将来仕様が変わるかもしれない機能も含まれます。
>
> 業務プロジェクトでは、`/std:c++20` や `/std:c++23`(利用可能になり次第)のように、バージョンを固定するほうが安全です。本書が `c++latest` を使うのは、`import std;` を扱うためであって、推奨しているわけではありません。第6章で改めて方針を整理します。

### 2.2.4 動作確認用のファイルを追加する

いよいよファイルを追加します。冒頭に書いたとおり、**このコードの意味は説明しません**。第3章で扱います。

**1つ目: モジュールのファイル**

ソリューションエクスプローラーで「ソース ファイル」を右クリック → **[追加] → [新しい項目]** を選びます。

ファイルの種類の一覧に **「C++ モジュール インターフェイス ユニット (.ixx)」** があるはずです。これを選び、ファイル名を `SmokeTest.ixx` にして追加します。

一覧に見当たらない場合は、「C++ ファイル (.cpp)」を選んで、ファイル名を **`SmokeTest.ixx`** と拡張子まで明示的に入力してください。結果は同じです(理由は 2.3.1 で説明します)。

内容を次のようにします。

```cpp
// SmokeTest.ixx
export module envcheck;

export int GetAnswer()
{
    return 42;
}
```

**2つ目: 実行のためのファイル**

同じ手順で、今度は **`main.cpp`** を追加します。

```cpp
// main.cpp
#include <cstdio>

import envcheck;

int main()
{
    std::printf("envcheck: %d\n", GetAnswer());
    return 0;
}
```

### 2.2.5 ビルドして実行する

**[ビルド] → [ソリューションのビルド]**(Ctrl + Shift + B)を実行します。

出力ウィンドウに次のような行が出れば成功です。

```
1>SmokeTest.ixx
1>main.cpp
1>ModuleSmokeTest.vcxproj -> ...\x64\Debug\ModuleSmokeTest.exe
```

注目してほしいのは、**`SmokeTest.ixx` が `main.cpp` より先にコンパイルされている**ことです。ソリューションエクスプローラーでの並び順とは関係ありません。第1章 1.3.3 で述べた「ビルド順序の依存」が、ここに現れています。`main.cpp` は `envcheck` モジュールの `.ifc` を必要とするので、それが先に作られなければなりません。

**[デバッグ] → [デバッグなしで開始]**(Ctrl + F5)で実行します。

```
envcheck: 42
```

これが出れば、環境は正しく組み上がっています。おめでとうございます。

うまくいかなかった場合は、2.5 のチェックリストに進んでください。

## 2.3 モジュール関連のプロジェクト設定を1つずつ確認する

動くようになったところで、いま何が効いているのかを確認します。設定を「変える」のではなく、「見る」ことが目的の節です。

### 2.3.1 `.ixx` という拡張子が持つ意味

先ほど、`SmokeTest.ixx` について特別な設定を何もしませんでした。それでもモジュールとしてビルドされました。なぜでしょうか。

MSVC は、**`.ixx` という拡張子のファイルを、自動的にモジュールインターフェイス単位として扱う**からです。

これを確認してみましょう。ソリューションエクスプローラーで `SmokeTest.ixx` を右クリック → **[プロパティ]** を選びます(プロジェクトではなく、ファイルのプロパティです)。

**[C/C++] → [詳細設定]** の **コンパイル言語の選択**(Compile As)という項目を見てください。

```
C++ モジュール コードとしてコンパイル (/interface)
```

となっているはずです。この `/interface` が「このファイルはモジュールインターフェイス単位である」という指定です。`.ixx` の場合、Visual Studio がこれを自動で設定しています。

逆に言えば、**別の拡張子を使いたい場合は、この項目を手動で設定すればよい**ということです。Clang や GCC の世界では `.cppm` という拡張子が一般的で、クロスプラットフォームのプロジェクトでは `.cppm` に揃えたくなることがあります。その場合、ファイルごとに「コンパイル言語の選択」を `/interface` にします。

ただし、Visual Studio の IntelliSense は `.ixx` を前提にした挙動をすることがあります。本書では素直に `.ixx` を使います。

なお、このドロップダウンには他にも選択肢があります。

| 選択肢 | 意味 | 本書での扱い |
|---|---|---|
| C++ モジュール コードとしてコンパイル (`/interface`) | モジュールインターフェイス単位 | 第3章以降ずっと使う |
| C++ 内部パーティションとしてコンパイル (`/internalPartition`) | 内部パーティション | 第10章 |
| C++ ヘッダー ユニットとしてコンパイル (`/exportHeader`) | ヘッダユニット | 第18章 |

いま意味が分からなくて構いません。「モジュール関連の指定は、ここに集まっている」とだけ覚えておいてください。

### 2.3.2 モジュール依存関係のソースをスキャンする

プロジェクトのプロパティに戻り、**[C/C++] → [全般]** を開きます。

**モジュール依存関係のソースをスキャンする**(Scan Sources for Module Dependencies)という項目があります。既定は「いいえ」です。

「いいえ」なのに、なぜ先ほどのビルドは成功したのでしょうか。

答えは、**`.ixx` 拡張子のファイルは、この設定に関係なく常にスキャンされる**からです。ヘッダユニットとしてコンパイルするよう設定されたファイルも同様です。だから、モジュールインターフェイスを `.ixx` で書いているかぎり、既定のままで依存関係は解決されます。

では「はい」にすると何が変わるのか。**すべての C++ ソース(`.cpp` を含む)がスキャン対象になります。** ビルドシステムはプロジェクト全体の依存グラフを構築し、`import` されているモジュールやヘッダユニットが、それを使うファイルより先にビルドされることを保証します。

これが必要になるのは主に第18章です。ヘッダユニットを扱うようになると、`.cpp` の中の `import <vector>;` のような記述もスキャンしてもらう必要が出てきます。

**本書では、当面この設定を「いいえ」のままにします。** 変更するタイミングは第18章で指示します。

> **なぜ既定が「いいえ」なのか**
>
> スキャンはタダではないからです。全ソースを一度読んで依存関係を洗い出す処理が、ビルドの前段に入ります。モジュールを使っていないプロジェクトにとっては、純粋な追加コストです。
>
> 一方で、大規模なプロジェクトではこの設定を「はい」にしたほうがビルドが速くなったという報告もあります。依存グラフが正確になることで並列度が上がるためです。効果はプロジェクトの構造次第で、第21章で計測の仕方を扱います。

### 2.3.3 ISO C++23 標準ライブラリ モジュールのビルド

**[C/C++] → [言語]** に戻ります。先ほど「C++ 言語標準」を設定した画面です。

同じ画面に **ISO C++23 標準ライブラリ モジュールのビルド**(Build ISO C++23 Standard Library Modules)という項目があります。

これを **「はい」** に変更してください。

この設定を有効にし、かつ C++ 言語標準が `/std:c++latest` であるとき、Visual Studio は標準ライブラリのモジュール(`std` と `std.compat`)を自動的に見つけてビルドします。これによって、コードの中で `import std;` と書けるようになります。

**確認してみる**

`main.cpp` を次のように書き換えて、ビルドしてみてください。

```cpp
// main.cpp
import std;

import envcheck;

int main()
{
    std::println("envcheck: {}", GetAnswer());
    return 0;
}
```

初回のビルドは、これまでより明らかに時間がかかるはずです。標準ライブラリ全体をモジュールとしてコンパイルしているためです。2回目以降は、生成された `.ifc` が再利用されるので速くなります。

`envcheck: 42` と表示されれば成功です。

**`std.ixx` はどこにあるのか**

標準ライブラリのモジュールは、魔法で現れるわけではありません。MSVC のインストールディレクトリに、ソースが置かれています。

Developer Command Prompt で次を実行してみてください。

```
dir "%VCToolsInstallDir%modules"
```

`std.ixx` と `std.compat.ixx` が見つかるはずです。中を覗いてみるのも面白いでしょう。標準ライブラリが、まさにこれから私たちが学ぶ構文で書かれています。

`std` と `std.compat` の違いは、C 由来の関数をグローバル名前空間にも置くかどうかです。`std` は `std::printf` を提供しますが `::printf` は提供しません。`std.compat` は両方を提供します。既存コードとの互換性が必要なときに `std.compat` を使います。

> **`#include` と `import std;` を混ぜないでください**
>
> 同じファイルの中で `#include <vector>` と `import std;` を併用したり、ヘッダユニットの `import <vector>;` と `import std;` を併用したりすると、問題が起きることがあります。
>
> これは本書の重要なテーマの1つで、第6章で正面から扱います。いまは「混ぜると危ない」とだけ覚えておいてください。先ほど `main.cpp` を書き換えたとき、`#include <cstdio>` の行を消したのはそのためです。

**この設定を有効にしておくべきか**

第6章まで、本書では `import std;` を使いません。しかし、設定は今のうちに「はい」にしておいてください。後で設定を思い出すより、最初から入れておくほうが確実です。

モジュールを使わないプロジェクトでは、この設定は不要です(むしろ無効にしておくべきです)。標準ライブラリモジュールのビルドコストが無駄になります。

### 2.3.4 モジュール出力ファイル名

**[C/C++] → [出力ファイル]** を開きます。

**モジュール出力ファイル名**(Module Output File Name)という項目があります。コンパイラオプションでいう `/ifcOutput` です。

既定では、コンパイラは**モジュール名から `.ifc` のファイル名を導出します**。`envcheck` というモジュールなら `envcheck.ifc` です。ソースファイル名(`SmokeTest.ixx`)ではなく、モジュール名が使われる点に注意してください。

この項目を変更すると、出力先のディレクトリやファイル名を指定できます。ディレクトリを指定したい場合は、末尾に `\` を付けます。

**本書では、この設定を変更しません。** 既定のままで動きます。

ただし、意味は知っておいてください。第12章でモジュール構成を設計するとき、そして第20章でライブラリとして配布する話をするとき、`.ifc` がどこに出るかは重要になります。

### 2.3.5 設定のまとめ

この章で触った設定を整理します。

| 場所 | 項目 | 本書での値 | 意味 |
|---|---|---|---|
| C/C++ → 言語 | C++ 言語標準 | `/std:c++latest` | `import std;` を使うため |
| C/C++ → 言語 | ISO C++23 標準ライブラリ モジュールのビルド | はい | 同上 |
| C/C++ → 全般 | モジュール依存関係のソースをスキャンする | いいえ(第18章で変更) | `.ixx` は常にスキャンされるので当面不要 |
| C/C++ → 出力ファイル | モジュール出力ファイル名 | 既定のまま | `.ifc` の出力先 |
| ファイルのプロパティ<br>C/C++ → 詳細設定 | コンパイル言語の選択 | 自動(`.ixx` なら `/interface`) | 拡張子から自動判定される |

驚くほど少ないと思われたかもしれません。実際、少ないのです。モジュールを使うために必要な設定は、`.ixx` という拡張子を使うだけならほぼゼロです。

## 2.4 出力される `.ifc` ファイルを覗いてみる

第1章で、モジュールは「解析済みの意味」を `.ifc` というファイルに保存する、と説明しました。実物を見てみましょう。

### 2.4.1 `.ifc` を探す

ソリューションエクスプローラーでプロジェクト名を右クリックし、**[エクスプローラーでフォルダーを開く]** を選びます。

エクスプローラーの検索ボックスに次のように入力してください。

```
*.ifc
```

いくつか見つかるはずです。プロジェクトの中間ディレクトリ(構成とプラットフォームごとに分かれたフォルダー)の下にあります。

見つかったファイルの名前を確認してください。

- **`envcheck.ifc`** ── 私たちが作ったモジュールです。ソースファイル名は `SmokeTest.ixx` でしたが、`.ifc` の名前は**モジュール名**から来ています(2.3.4 で述べたとおりです)
- 2.3.3 の設定を有効にした場合、**`std.ifc`** も見つかるはずです。こちらもモジュール名そのままです

`envcheck.ifc` と `std.ifc` のファイルサイズを比べてみてください。桁が違うはずです。標準ライブラリ全体の「意味」がどれだけの量なのかが分かります。

### 2.4.2 中身を覗いてみる

`.ifc` はバイナリファイルです。テキストエディタで開いても文字化けするだけですが、Visual Studio のバイナリエディターなら開けます。

**[ファイル] → [開く] → [ファイル]** で `envcheck.ifc` を選び、**[開く] ボタンの右側にある矢印**から **[プログラムから開く]** を選択、一覧から **[バイナリ エディター]** を選びます。

16進数の羅列が表示されますが、右側の文字表示に注目してください。`envcheck`、`GetAnswer` といった、私たちが書いた識別子の文字列が見つかるはずです。

`.ifc` は独自のバイナリ形式で、その仕様は公開されています。ただ、私たちが日常的に中身を読む必要はありません。ここで確認したかったのは、**これがテキストではなく、コンパイラが解析した結果を格納した構造化データである**という一点です。ヘッダファイルとの決定的な違いがここにあります。

### 2.4.3 【実験】依存関係を体感する

もう1つ実験をしてみましょう。

1. `main.cpp` を**一切変更せず**に、`SmokeTest.ixx` の `return 42;` を `return 43;` に書き換えます
2. ビルドします

出力ウィンドウを見てください。`SmokeTest.ixx` だけでなく、**`main.cpp` も再コンパイルされている**はずです。

`main.cpp` の中身は1文字も変わっていません。それでも再コンパイルされるのは、`main.cpp` が `envcheck.ifc` に依存しており、その `.ifc` が更新されたからです。

これは、ヘッダファイルを書き換えたときに、それを `#include` しているすべての `.cpp` が再コンパイルされるのと同じ構図です。**モジュールにしても、インターフェイスを変えれば利用者は再コンパイルされます。**

第1章 1.4.1 で「モジュールにすれば速くなるわけではない」と書いた理由の一端が、ここにあります。何をインターフェイスに置き、何を隠すか ── その設計が再コンパイルの範囲を決めます。第11章と第12章の主題です。

### 2.4.4 `.ifc` はソース管理に入れない

最後に、実務上の注意を1つ。

**`.ifc` はビルドの中間生成物です。** `.obj` や `.pdb` と同じ扱いで、Git などのソース管理に入れてはいけません。

Visual Studio の標準的な `.gitignore`(GitHub の VisualStudio テンプレートなど)には、中間ディレクトリ全体を除外する設定が入っているので、通常は自動的に除外されます。ただし、`/ifcOutput` で出力先を変更した場合は、その場所を明示的に除外する必要があります。

第1章のコラムで書いたとおり、`.ifc` はコンパイラのバージョン・オプション・ターゲットに強く結びついたファイルです。他人の環境はもちろん、自分の環境でも Visual Studio を更新すれば読めなくなる可能性があります。

## 2.5 うまくいかないときの最初のチェックリスト

環境構築でつまずいたとき、闇雲に設定をいじると状況が悪化します。上から順に確認してください。

### 2.5.1 症状別の対処

**「モジュール 'envcheck' が見つかりません」(C2230)**

最も多いエラーです。原因の候補を上から順に。

1. **`.ixx` ファイルがプロジェクトに追加されていない。** エクスプローラー上にファイルを作っただけでは、プロジェクトの一部になりません。ソリューションエクスプローラーに `SmokeTest.ixx` が表示されているか確認してください
2. **拡張子が `.ixx` になっていない。** `SmokeTest.ixx.cpp` のようになっていませんか。エクスプローラーで拡張子を表示する設定にして確認してください
3. **モジュール名の綴りが違う。** `export module envcheck;` と `import envcheck;` は完全に一致する必要があります
4. **C++ 言語標準が C++20 未満。** 2.2.3 を確認してください
5. **ファイルのプロパティで「コンパイル言語の選択」が別の値になっている。** 2.3.1 を確認してください

**「モジュール 'std' が見つかりません」**

1. **C++ 言語標準が `/std:c++latest` になっていない。** `/std:c++20` では `import std;` は使えません
2. **「ISO C++23 標準ライブラリ モジュールのビルド」が「いいえ」のまま。** 2.3.3 を確認してください
3. この2つは**両方**必要です。片方だけでは動きません

**Debug では通るのに Release で通らない(またはその逆)**

2.2.2 の問題です。プロパティを開き、[構成] を「すべての構成」、[プラットフォーム] を「すべてのプラットフォーム」にして、設定を入れ直してください。

**ビルドは通るのに、エディタに赤い波線が出る**

IntelliSense がモジュールの解析に追いついていないケースです。ビルドが通っているなら、コードは正しいと考えて構いません。

対処:

1. **[ビルド] → [ソリューションのリビルド]** を実行する
2. それでも消えなければ、Visual Studio を再起動する
3. さらに消えなければ、ソリューションを閉じてから、ソリューションファイルと同じ場所にある **`.vs` フォルダー**(隠しフォルダー)を削除する。IntelliSense のデータベースがここに入っています

`.vs` フォルダーの削除は安全です。ソースコードは含まれておらず、次回起動時に再生成されます。

**エラーメッセージが意味不明**

モジュール関連のコンパイルエラーは、慣れないうちは本当に読めません。付録B にエラーコード別の対処をまとめていますので、そちらを参照してください。

### 2.5.2 困ったときの順番

原因が特定できないときは、この順に試してください。

1. **[ビルド] → [ソリューションのリビルド]**(中間ファイルを消してビルドし直す)
2. 中間ディレクトリを**手動で削除**してビルド
3. `.vs` フォルダーを削除して Visual Studio を再起動
4. 2.2.4 の最小構成に戻して、それが動くか確認する

4番目が重要です。**動く状態がどこかにあることを確認してから、そこに戻って一歩ずつ進める。** これが本書全体の進め方でもあります。

### 2.5.3 最小構成の再掲

何かおかしくなったとき、ここに戻ってください。

```cpp
// SmokeTest.ixx
export module envcheck;

export int GetAnswer()
{
    return 42;
}
```

```cpp
// main.cpp
#include <cstdio>

import envcheck;

int main()
{
    std::printf("envcheck: %d\n", GetAnswer());
    return 0;
}
```

必要な設定は、C++ 言語標準を `/std:c++20` 以上にすること。それだけです。この2ファイルが動かないなら、問題はコードではなく環境にあります。

## 2.6 この章のまとめ

- 必要なワークロードは「C++ によるデスクトップ開発」1つ。モジュール専用の実験的コンポーネントはもう存在しない
- プロジェクト設定を変えるときは、必ず [構成] と [プラットフォーム] を「すべて」にする
- VS 2026 の新規プロジェクトは既定で C++20。ただし `import std;` のために本書では `/std:c++latest` にする
- `.ixx` 拡張子のファイルは、自動的にモジュールインターフェイス単位として扱われる。設定は不要
- `.ixx` は「モジュール依存関係のソースをスキャンする」設定に関係なく常にスキャンされる。この設定が要るのは第18章から
- `import std;` には `/std:c++latest` と「ISO C++23 標準ライブラリ モジュールのビルド」の**両方**が必要
- `.ifc` の名前は、ソースファイル名ではなく**モジュール名**から決まる
- `.ifc` はビルドの中間生成物。ソース管理に入れない、配布しない
- モジュールのインターフェイスを変更すれば、それを `import` している側は再コンパイルされる
