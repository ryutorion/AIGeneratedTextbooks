# 第19章 既存プロジェクトの移行戦略

## この章について

ここまでの18章で、`GameMath` をゼロからモジュールで書いてきました。何もないところから始めたので、迷いなく進められました。

**実務では、そうはいきません。**

すでに何万行、何十万行のコードがあります。ヘッダが数百ある。ビルド構成が複雑に絡んでいる。マクロで挙動を切り替えている箇所が何十もある。そして、明日もリリースしなければなりません。

この章では、そういう現実のコードベースをどう扱うかを考えます。

内容は4つです。

1. 一気に移行してはいけない理由 ── そして**そもそも移行すべきか**(19.1)
2. ヘッダとモジュールを**両方**提供する方法(19.2)
3. どこから手をつけるか(19.3)
4. チェックリスト(19.4)

最初の項目に、本書でいちばん実務的な問いが含まれています。**「移行しない」も正当な選択肢です。** そこから始めます。

## 19.1 一気に移行してはいけない理由

### 19.1.1 そもそも移行すべきか

この本を読んでいる方に「移行しなくてよい」と言うのは奇妙に思えるかもしれません。しかし、これを最初に書かない技術書は信用できないと思います。

**移行には費用がかかります。** そして、費用に見合う効果が出るとは限りません。

第1章 1.4 で「モジュールが解決しないこと」を並べました。あの内容は、移行を検討するときにこそ効いてきます。もう一度確認してください。

- ビルドは自動的に速くならない(1.4.1)
- パッケージ管理でもバージョン管理でもない(1.4.2)
- バイナリ配布の問題は解決しない(1.4.3)
- マクロがなくなるわけではない(1.4.4)
- テンプレートのコストは消えない(1.4.5)
- 周辺環境はまだ発展途上(1.4.6)

### 19.1.2 移行の動機になるもの、ならないもの

**動機になるもの**

**1. ビルド時間 ── ただし測ってから**

最も多い動機です。しかし第1章 1.4.1 で書いたとおり、機械的に置き換えても効果は出ません。依存関係の設計をやり直して初めて効果が出ます。

**移行の前に測ってください。** 何が遅いのか。ヘッダの解析なのか、テンプレートの実体化なのか、リンクなのか。テンプレートの実体化が支配的なら、モジュール化しても改善しません。

第21章で計測の方法を扱います。**第21章を読んでから移行を決めても遅くありません。**

**2. カプセル化 ── 実際に困っているなら**

内部ヘッダが利用者に見えていて、勝手に使われている。`detail` 名前空間が事実上の公開 API になっている。ライブラリの内部を変えると誰かのコードが壊れる ── こういう問題が**現に起きている**なら、モジュールは直接的な解決になります(第7章 7.2)。

**3. マクロ汚染で事故が起きているなら**

`min` / `max` 問題や、それに類する事故が繰り返し起きているなら、動機として十分です(第1章 1.1.5)。

**4. 新しくコードを書き始めるなら**

新規のライブラリやサブシステムなら、最初からモジュールで書くのが素直です。移行の費用がかかりません。

**動機にならないもの**

**「モダンな C++ だから」** ── 理由になっていません。

**「いつかやらなければならないから」** ── 「いつか」は「いま」の理由になりません。周辺環境が成熟してからのほうが、費用は下がります。

**「速くなるらしいから」** ── 測っていないなら、動機ではなく期待です。

### 19.1.3 移行しないほうがよい状況

次のどれかに当てはまるなら、いまは見送るのが賢明です。

- **コードベースが安定していて、変更頻度が低い。** 触らないコードを書き換える理由はありません
- **ビルド時間が問題になっていない**
- **サードパーティ依存が多く、そのほとんどがヘッダオンリー。** 第18章で見たとおり、外部のヘッダはモジュール化の恩恵を受けにくく、扱いが面倒です
- **チームに C++20 の知識が行き渡っていない。** 本書で扱った「見える/到達可能」「モジュールリンケージ」「循環依存」を全員が理解していないと、移行の途中で身動きが取れなくなります
- **コンパイラを更新できない事情がある**
- **マクロによる設定切り替えが設計の中心にある。** 第16章 16.4 の問題に真正面からぶつかります

最後の項目が、実務ではいちばん重い障害になることがあります。プラットフォームごと、ビルド構成ごとにマクロで挙動を変える設計は、ゲーム開発では珍しくありません。それを型による切り替えに書き換える作業は、モジュール化とは別種の、大きな設計変更です。

### 19.1.4 一気にやると何が起きるか

移行すると決めた場合でも、**一括変換はやめてください。** 何が起きるかを並べます。

**1. 循環依存が一斉に噴出する**

これがいちばん厳しいものです。

ヘッダの世界では、循環依存は前方宣言でごまかせました(第10章 10.4.2)。だから、**大規模なコードベースには、ほぼ確実に循環依存が潜んでいます。** 数十年続いたプロジェクトなら、数百か所あっても不思議ではありません。

モジュールでは、循環はコンパイルエラーです。一括変換すると、それが全部同時に噴き出します。しかも、1つ解こうとすると別のところが崩れます。

**2. マクロによる設定切り替えが全部止まる**

第16章 16.4 のとおりです。`#ifdef` で挙動を変えていた箇所が、モジュール境界を越えられなくなります。

**3. ビルドが通らない期間が長引く**

一括変換すると、全部が終わるまでビルドが通りません。その間、リリースできません。

そして、ビルドが通らない状態が長引くほど、「元に戻す」という判断が難しくなります。

**4. 効果が出ない**

第1章 1.4.1 のとおりです。機械的な置き換えは、依存関係を変えません。絡み合ったヘッダは、絡み合ったモジュールになるだけです。

**5. 戻れない**

数百ファイルを書き換えたあとで「遅くなった」と分かっても、戻す作業がまた数百ファイルです。

### 19.1.5 段階的移行という前提

だから、**一度に1つのモジュールずつ**移行します。

そのためには、**移行済みの部分と未移行の部分が共存できなければなりません。**

- モジュール化した部分を、まだヘッダのままのコードから使えるか
- ヘッダのままの部分を、モジュール化したコードから使えるか

後者は簡単です。第6章のグローバルモジュールフラグメントで `#include` すればよいのです(第18章 18.4.2)。

**前者が問題です。** これが 19.2 の主題です。

## 19.2 ヘッダとモジュールを両方提供する

### 19.2.1 なぜ両方必要になるのか

`GameMath` を、既存の巨大なゲームエンジンの中で移行することを考えてください。

`Vector3.h` を `import gamemath;` に置き換えるには、それを `#include` している 250 個のファイルを全部書き換える必要があります。

**一度にはできません。** だから、移行期のあいだは両方の入口が必要です。

```cpp
// 移行済みのファイル
import gamemath;

// まだ移行していないファイル
#include "GameMath/Vector3.h"
```

**どちらも同じ実体を指していなければなりません。** 別々の実体になったら、型が食い違ってリンクエラーになります(第6章 6.1.5 で見た問題です)。

### 19.2.2 どちらを「正」にするか

2つの構成が考えられます。

**構成A: ヘッダが正、モジュールは薄い入口**

実装はヘッダに書いたまま。モジュールのファイルは、それを取り込んで再公開するだけ。

**構成B: モジュールが正、ヘッダは薄い入口**

実装はモジュールに移す。ヘッダは `import` するだけ。

**構成B は使えません。**

ヘッダは、任意の場所に `#include` されます。関数の中かもしれません。名前空間の中かもしれません。一方 `import` は、書ける場所が決まっています ── グローバルスコープであり、モジュール単位の中ならプリアンブルです(第6章 6.4.2)。

**ヘッダの中に `import` を書いても、それが安全に展開される保証がありません。**

したがって、移行期は**構成A**を採ります。**実装はヘッダに置いたまま、モジュールという入口を追加する**のです。

### 19.2.3 方法1 ── `export using` で再公開する

いちばん素直な方法です。

```cpp
// GameMath.ixx ── モジュールという入口
module;

#include <cmath>
#include "GameMath/Vector3.h"
#include "GameMath/Matrix4x4.h"

export module gamemath;

export namespace gamemath {

using ::gamemath::Vector3;
using ::gamemath::Matrix4x4;
using ::gamemath::Dot;
using ::gamemath::Cross;
using ::gamemath::Transpose;
// ...公開したいものを1つずつ

} // namespace gamemath
```

ヘッダをグローバルモジュールフラグメントで取り込み、購買域で **using 宣言**を使って名前を再公開します。

`export using` が使えるのは、**再公開する実体が外部リンケージを持つ場合**です。ヘッダに書かれた通常の関数や型は外部リンケージなので、問題ありません。

**この方法の利点**

- ヘッダを1行も書き換えなくて済みます
- 何を公開するかを、モジュール側で選べます。ヘッダには載っているが公開したくないものを、除外できます

**この方法の欠点**

- **公開するものの数だけ、`using` を書く必要があります。** 型が50個、関数が200個あれば、250行です
- ヘッダに何かを追加するたびに、モジュール側にも追加する必要があります。**二重管理**です
- 忘れると、第7章 7.5 や第13章 13.3.2 で見たエラーが起きます

### 19.2.4 `export using` の制約

もう1つ、知っておくべき制約があります。

**型には別名を付けられますが、関数には付けられません。**

```cpp
export using Vec3 = ::gamemath::Vector3;      // 型なら別名を付けられる
export using ::gamemath::Dot;                 // 関数は名前をそのまま引き継ぐだけ
```

C++ には関数の別名という仕組みがありません。だから、移行のついでに関数名を整理する、といったことはできません。

第18章 18.3.3 で「ラッパーモジュールは思ったほど透過的ではない」と書きましたが、その理由の1つがこれです。

### 19.2.5 方法2 ── ヘッダに `EXPORT` マクロを仕込む

`using` を250行書くのが現実的でない場合、もう1つの方法があります。**ヘッダ側に仕掛けを入れます。**

```cpp
// GameMath/Vector3.h
#pragma once

// モジュールから取り込まれているときは、標準ヘッダを重ねて取り込まない
#ifndef GAMEMATH_IN_MODULE
#include <cmath>
#endif

// モジュールから取り込まれているときだけ export が付く
#ifdef GAMEMATH_IN_MODULE
#define GAMEMATH_EXPORT export
#else
#define GAMEMATH_EXPORT
#endif

namespace gamemath {

GAMEMATH_EXPORT struct Vector3
{
    float x, y, z;
    float LengthSquared() const { return x * x + y * y + z * z; }
    float Length() const;
};

GAMEMATH_EXPORT float Dot(const Vector3& a, const Vector3& b);
GAMEMATH_EXPORT Vector3 Cross(const Vector3& a, const Vector3& b);

} // namespace gamemath
```

普通に `#include` したときは、`GAMEMATH_EXPORT` は空文字列になります。**従来どおりのヘッダです。**

モジュール側は、こう書きます。

```cpp
// GameMath.ixx
module;

#include <cmath>          // ヘッダが必要とする標準ヘッダは、ここで取り込む

export module gamemath;

#define GAMEMATH_IN_MODULE

extern "C++" {
#include "GameMath/Vector3.h"
#include "GameMath/Matrix4x4.h"
}
```

**`GAMEMATH_IN_MODULE` を定義してから `#include` します。** すると `GAMEMATH_EXPORT` が `export` に展開され、ヘッダの中の宣言がそのまま公開されます。

**利点**

- **`using` を1つずつ書く必要がありません**
- ヘッダに宣言を追加すれば、自動的にモジュールからも公開されます。**二重管理がありません**
- ヘッダとモジュールで、公開範囲が必ず一致します

**欠点**

- **ヘッダを書き換える必要があります。** すべての公開宣言に `GAMEMATH_EXPORT` を付けます
- 公開したくないものまで公開されます。細かい制御ができません
- 見た目が汚くなります

### 19.2.6 `extern "C++"` は何をしているのか

方法2のコードで、いちばん不可解なのがこの部分でしょう。

```cpp
extern "C++" {
#include "GameMath/Vector3.h"
}
```

**これは購買域での `#include` です。** 第6章 6.1 で「やってはいけない」と繰り返し書いたことです。

なぜ許されるのか ── **`extern "C++" { }` で囲むと、その中の宣言はモジュールではなく、グローバルモジュールに属するからです。**

第6章 6.1.5 で説明した問題を思い出してください。

> 購買域に `#include` を書くと、取り込んだ宣言がすべてそのモジュールに属してしまい、他所の同名の実体と別物になる。

`extern "C++"`(言語リンケージ指定)の中に書かれた宣言は、購買域にあっても**グローバルモジュールに属します**。だから、ヘッダ版を `#include` したコードと、モジュール版を `import` したコードが、**同じ実体を指します。**

これが、両方の入口を成立させている仕掛けです。

そして購買域にいるので、`export` を付けられます。グローバルモジュールフラグメントでは `export` を書けませんでした(第6章 6.3.2)。**「グローバルモジュールに属しながら、公開される」**という、この方法にしか作れない状態です。

> **注意**
>
> この手法には、コンパイラごとの差があります。MSVC と GCC は受け付けますが、**Clang は `extern "C++"` の中の `export` を拒否します**(標準の解釈が分かれている箇所です)。
>
> クロスプラットフォームのプロジェクトでは、方法1(`export using`)のほうが安全です。付録E も参照してください。
>
> また、購買域での `#include` なので、警告 C5244 が出る可能性があります。この場合は所属の問題が `extern "C++"` で解決しているので、警告の意味を理解したうえで判断してください。

### 19.2.7 2つの方法の比較

| | 方法1(`export using`) | 方法2(`EXPORT` マクロ) |
|---|---|---|
| ヘッダの書き換え | **不要** | 必要 |
| モジュール側の記述量 | 公開する数だけ | 数行 |
| 二重管理 | **あり** | なし |
| 公開範囲の制御 | **細かくできる** | できない |
| 別名を付ける | 型なら可能 | 不可 |
| コンパイラ間の移植性 | **高い** | MSVC / GCC のみ |

**ヘッダを書き換えられる立場なら方法2、書き換えられないなら方法1**、というのが基本的な選び方です。

サードパーティのヘッダは書き換えられないので、方法1になります。自社のコードなら方法2が楽です。

### 19.2.8 この橋が提供しないもの

大事なことを確認しておきます。**構成A(ヘッダが正)は、モジュールの利点をほとんど提供しません。**

| 第1章で挙げた問題 | 構成A で解決するか |
|---|---|
| 何度も解析する | **一部**。`import gamemath;` した側だけ |
| マクロが漏れる | 解決する(`import` した側には) |
| 隠せない | **解決しない**。ヘッダには全部書いてある |
| 順序に依存する | 一部 |
| 静かに壊れる(ODR) | **解決しない** |

とくに「隠せない」が重要です。実装がヘッダに書いてある以上、**`#include` する人からは全部見えます。** 第7章で得たカプセル化は、構成A では手に入りません。

**構成A は橋です。渡り終えたら、実装をモジュール側に移す必要があります。**

移行の全体像は、こうなります。

```
第1段階:  ヘッダのみ
              ↓
第2段階:  ヘッダが正 + モジュールという入口(構成A)   ← 両方使える
              ↓
第3段階:  利用側を全部 import に置き換える
              ↓
第4段階:  実装をモジュールに移す。ヘッダを削除する
```

**第2段階に長く留まらないでください。** 二重管理のコストが継続的にかかり、モジュールの利点は得られていない状態です。

## 19.3 葉から移行する / 幹から移行する

### 19.3.1 依存の向きは対称ではない

「末端から移行するか、基盤から移行するか」── ヘッダの時代のリファクタリングでは、この2択がよく議論されました。

**モジュールでは、この2つは対称ではありません。**

決定的な非対称があります。

| | 可能か | 方法 |
|---|---|---|
| **モジュールが、ヘッダに依存する** | **できる** | グローバルモジュールフラグメントで `#include`(第18章 18.4.2) |
| **ヘッダが、モジュールに依存する** | **難しい** | ヘッダに `import` を書けない(19.2.2) |

つまり、**モジュール化された部分は、まだヘッダのままの部分を自由に使えます。** 逆はできません。

この非対称から、進む方向が決まります。

### 19.3.2 基盤から移行する

**依存される側 ── 基盤にあるヘッダ ── から順にモジュール化します。**

```
        Player.cpp   Enemy.cpp   Camera.cpp        ← まだヘッダのまま
              ↓          ↓           ↓
        ┌─────────────────────────────────┐
        │  Vector3.h  Matrix4x4.h          │       ← ここから移行する
        └─────────────────────────────────┘
```

`Vector3.h` を `gamemath` モジュールにします。しかし `Player.cpp` はまだ `#include "Vector3.h"` のままです。

**だから 19.2 の橋が必要になります。** 構成A で両方の入口を用意すれば、`Player.cpp` を書き換えずに `Vector3` をモジュール化できます。

そして、`Player.cpp` を1つずつ `import gamemath;` に置き換えていきます。**1ファイルずつ、ビルドが通ることを確認しながら**進められます。

**長所**

- 基盤ほど多くのファイルから使われるので、ビルド時間の改善が大きくなります
- 依存の向きに沿っているので、無理がありません

**短所**

- 基盤ほど変更の影響範囲が大きく、慎重さが要ります
- 基盤ほど循環依存が絡んでいることが多い

### 19.3.3 末端から移行する ── 実は「移行」ではない

逆方向を考えてみます。`Player.cpp` を先にモジュール化したら?

`Player.cpp` は `.cpp` です。誰からも `#include` されません。だから、こう書けます。

```cpp
// Player.cpp
module;

#include "Vector3.h"        // まだヘッダのまま
#include "Matrix4x4.h"

module myapp;               // あるいは、モジュールにしない

// ...
```

**動きます。** 19.3.1 の非対称の、恩恵を受ける側です。

しかし、これは移行でしょうか。`Player.cpp` をモジュールの実装単位にしても、**得られるものはほとんどありません。** `.cpp` は誰からも参照されないので、解析回数は変わりません。

**末端から始めるのは、練習にはなっても、効果は出ません。**

### 19.3.4 現実的な第3の道 ── 新規コードだけモジュールにする

いちばん費用対効果が高い方法があります。

**既存コードには一切手を触れず、新しく書くコードだけをモジュールにする。**

```cpp
// NewSubsystem.ixx  ── 新規に書くコード
module;

#include "Legacy/Common.h"       // 既存のヘッダをそのまま使う
#include "Legacy/Renderer.h"

export module myapp.newsubsystem;

import std;

namespace myapp {

export void RunNewFeature();

} // namespace myapp
```

**長所**

- 既存コードのリスクがゼロです
- 新しい部分は、最初から正しい設計で書けます
- チームがモジュールに慣れる場になります
- **失敗しても、その部分だけを捨てられます**

**短所**

- 既存部分のビルド時間は改善しません

しかし、既存部分のビルド時間には**別の手があります。** 第18章 18.2.5 で扱った `/translateInclude` です。

**ソースを1行も書き換えずに、既存の `#include` をヘッダユニット経由に変えられます。** モジュール化とは別系統の改善なので、並行して進められます。

つまり、現実的な戦略はこうなります。

```
既存コード  →  /translateInclude でビルド時間を改善(ソース変更なし)
新規コード  →  最初からモジュールで書く
基盤ヘッダ  →  余力ができたら、19.2 の橋を架けて移行する
```

### 19.3.5 循環依存という関門

どの道を選んでも、いずれ循環依存にぶつかります。19.1.4 で挙げた最大の障害です。

**移行の前に、循環依存を洗い出してください。**

方法は2つあります。

**方法1: ヘッダのまま、依存グラフを作る**

`/showIncludes` オプション(**[C/C++] → [詳細設定] → インクルード ファイルの一覧を表示**)を使うと、各翻訳単位が取り込んだヘッダの一覧が出力されます。これを集計すれば、依存グラフを作れます。

商用・オープンソースの依存関係解析ツールもあります。

**方法2: 1つずつモジュール化して、ぶつかったら解く**

段階的移行なら、循環は1つずつ現れます。第10章 10.4.5 の3つの対処で、そのつど解きます。

1. 共通部分を下の層に抽出する
2. 依存の向きを1つに決める
3. 宣言と定義を分ける(ただし第14章 14.2.3 の制約あり)

**重要な認識**

循環依存を解く作業は、**モジュール化の作業ではありません。設計の是正です。**

だから、**モジュール化を決める前でも着手できます。** ヘッダのままでも、循環依存は減らしたほうがよいのです。

「モジュール移行の準備」として循環依存の整理を始めれば、移行しないと決めた場合でも無駄になりません。**いちばんリスクの低い第一歩です。**

### 19.3.6 どこまで移行するか

全部を移行する必要はありません。

- **基盤のライブラリ** ── 多くのファイルから使われるので、効果が大きい。移行の価値が高い
- **中間層** ── 状況次第
- **末端のアプリケーションコード** ── `.cpp` のまま `import` するだけでよい。モジュールにする必要はない

第12章 12.4.2 で「サブモジュールの境界 = 利用者に提示する選択肢」と書きました。移行でも同じです。**「利用者が `import` したい単位」だけモジュールにすればよく、その内側は `.cpp` のままで構いません。**

## 19.4 移行チェックリスト

### 19.4.1 移行を決める前に

```
□ ビルド時間を計測したか(第21章)
□ 遅い原因を特定したか(ヘッダ解析か、テンプレート実体化か、リンクか)
□ 循環依存の数を把握したか
□ マクロによる設定切り替えが何か所あるか数えたか
□ サードパーティ依存のうち、ヘッダオンリーがどれだけあるか確認したか
□ チーム全員が第7章(見える/到達可能)を理解しているか
□ コンパイラとビルドシステムを更新できるか
□ 移行しないという選択肢を検討したか
```

最後の項目を飛ばさないでください。

### 19.4.2 移行を始める前に

```
□ 循環依存を減らす作業を先に済ませたか(モジュール化と独立に着手できる)
□ /Zc:preprocessor を単独で有効にしてビルドが通るか確認したか(第18章 18.2.6)
□ /std:c++20 でビルドが通るか確認したか
□ 新規コードをモジュールで書く体制ができているか
□ 移行の単位(どのライブラリから)を決めたか
□ 失敗したときに戻せる状態か(ブランチを切ったか)
```

### 19.4.3 1つの単位を移行するとき

```
□ そのライブラリが依存しているものが、すべて移行済みかヘッダのままか確認した
□ 構成A(ヘッダが正)で、モジュールの入口を作った
□ 方法1(export using)か方法2(EXPORT マクロ)かを選んだ
□ 公開すべき宣言をすべて再公開したか確認した
   □ 型
   □ 自由関数・演算子(第4章 4.3.2)
   □ 公開する関数のシグネチャに出る型(第7章 7.5)
   □ エイリアス・コンセプト(第8章 8.1.4 / 8.3.4)
   □ オーバーロード集合の全部(第14章 14.1.4)
□ 既存のテストが通ることを確認した
□ 利用側を1ファイルずつ import に置き換えた
□ すべての利用側が移行したら、実装をモジュールに移した
□ ヘッダを削除した(または非推奨にした)
```

### 19.4.4 詰まったときの逃げ道

```
□ 循環依存 → 第10章 10.4.5 の3つの対処
□ マクロが届かない → 第16章 16.5 の型による切り替え
□ ADL によるカスタマイズが壊れた → 第13章 13.3.4、第15章 15.4.6
□ 識別子が見つからない → 第17章 17.3.5 の auto による切り分け
□ ビルド順序が不安定 → 第18章 18.2.3 のスキャン設定
□ どうしても解けない → その単位は移行しない。ヘッダのまま残す
```

最後の項目が重要です。**すべてを移行する必要はありません。** 1つのライブラリが解けないなら、そこは残して先に進んでください。19.3.1 の非対称のおかげで、モジュール化された部分はヘッダのままの部分を使えます。

### 19.4.5 完了の判定

移行が終わったと言えるのは、次の状態です。

```
□ そのライブラリのヘッダが、プロジェクトから削除された
□ 実装がモジュール単位に置かれている
□ 公開したくないものが、実際に外から見えなくなっている
□ ビルド時間を再計測し、改善を確認した
```

3番目に注目してください。**カプセル化が実際に効いているか**を確認します。19.2.8 で書いたとおり、構成A のままでは隠蔽できていません。

4番目も忘れないでください。**改善しなかったなら、移行は失敗しています。** その原因(依存関係の設計か、そもそも動機が間違っていたか)を確認してください。

## 19.5 この章のまとめ

- **移行しないという選択肢がある。** コードベースが安定している、ビルド時間が問題でない、サードパーティ依存が多い ── どれかに当てはまるなら見送ってよい
- 移行の動機になるのは、**測定に基づくビルド時間**、実際に困っているカプセル化、マクロ汚染の事故、新規開発
- 「モダンだから」「いつかやるから」は動機ではない
- 一括変換は避ける。**循環依存が一斉に噴出し、ビルドが通らない期間が長引き、戻れなくなる**
- 段階的移行には、**ヘッダとモジュールの両方の入口**が必要
- **ヘッダを正、モジュールを薄い入口にする(構成A)。** 逆はできない ── ヘッダの中に `import` は書けない
- **方法1: `export using`** ── ヘッダを書き換えなくてよいが、公開する数だけ記述が要る。移植性は高い
- **方法2: ヘッダに `EXPORT` マクロを仕込み、`extern "C++"` で囲んで取り込む** ── 記述量は少ないが、ヘッダの書き換えが必要。Clang では通らない
- `extern "C++" { }` の中の宣言は、購買域にあっても**グローバルモジュールに属する**。だから同じ実体になる
- **構成A はモジュールの利点をほとんど提供しない。** とくにカプセル化は得られない。長く留まらない
- **モジュールはヘッダに依存できるが、逆はできない。** この非対称が移行の方向を決める
- **基盤から移行する。** 末端から始めても効果は出ない
- 現実的な第一歩は、**既存コードに触れず新規コードだけモジュールで書く**こと。`/translateInclude` と併用する
- **循環依存の整理は、モジュール化と独立に着手できる。** 移行しないと決めても無駄にならない
- すべてを移行する必要はない。解けない単位は残してよい
