# 第21章 ビルド時間を測る

## この章について

第1章から一貫して、こう書いてきました。

> ビルドは自動的に速くならない。効果は分割設計に依存する(1.4.1)
> 移行の動機になるのは、**測定に基づく**ビルド時間(19.1.2)
> まず測ってください(19.4.1)

この章で、実際に測ります。

**先に断っておきます。この章には、具体的な秒数を書きません。**

理由は2つあります。

**理由1: 数字が環境に強く依存するから。** CPU のコア数、ストレージの速度、ウイルス対策ソフトの設定、コンパイラのバージョン ── これらで簡単に数倍変わります。本書に「1.8倍速くなった」と書いても、あなたの環境では意味を持ちません。

**理由2: 数字を覚えてほしくないから。** 覚えてほしいのは、**測り方**と、**結果の読み方**です。それさえ身につけば、自分の環境で自分の答えを出せます。

内容は6つです。

1. 何を測るのか(21.1)
2. 計測の道具(21.2)
3. 実験A ── 標準ライブラリだけを比べる(21.3)
4. 実験B ── 同一ライブラリの2つの版を比べる(21.4)
5. 結果をどう読むか(21.5)
6. 遅かったらどうするか(21.6)

## 21.1 何を測るのか

### 21.1.1 「速くなった」とは何か

「ビルドが速くなった」という言葉は曖昧です。何のビルドでしょうか。

開発者が1日に経験するビルドを思い浮かべてください。

- 朝、リポジトリを更新して**フルビルド** ── 1日1〜2回
- コードを1行直して**増分ビルド** ── 1日に数十回
- 何も変えずにビルド(テスト実行前など) ── 1日に数回
- CI サーバーでの**クリーンビルド** ── コミットごと

**待ち時間の合計に効くのは、圧倒的に増分ビルドです。**

1回20秒のフルビルドが15秒になっても、1日で数十秒しか変わりません。1回5秒の増分ビルドが3秒になれば、1日で1分以上変わります。そして、**短いビルドのほうが集中力への影響が大きい**という面もあります。

だから、フルビルドだけを測って「速くなった/ならなかった」と判断しないでください。

### 21.1.2 4種類のビルドを測る

最低限、次の4つを測ります。

| 種類 | 操作 | 何が分かるか |
|---|---|---|
| **フルビルド** | 中間ディレクトリを削除してビルド | 総解析コスト。CI に効く |
| **利用側の増分** | `main.cpp` を1行変えてビルド | 日常の待ち時間 |
| **実装の増分** | 実装単位を1行変えてビルド | 実装を変えたときの波及 |
| **インターフェイスの増分** | `.ixx` / `.h` を1行変えてビルド | **設計の良し悪しが出る** |
| **何も変えない** | そのままビルド | **スキャンのオーバーヘッド** |

4番目が、この章でいちばん重要です。

インターフェイスを変えたときに何ファイルが再コンパイルされるか ── これは**設計の指標**です。第5章 5.1.3 と 5.6.4 で体験したとおりです。モジュール化しても、インターフェイスに全部書いていれば波及範囲は変わりません。

5番目も忘れないでください。モジュールはビルド前に**スキャン**を行います(第20章 21.1.2)。何も変わっていなくても、この時間はかかります。**モジュール化すると no-op ビルドが遅くなることがあります。**

### 21.1.3 測る前に揃えること

比較の前提を揃えないと、測った数字は意味を持ちません。

**必ず揃えるもの**

- **ビルド構成**(Debug / Release)
- **プラットフォーム**(x64)
- **最適化オプション**(`/O2` など)
- **`/MP`(複数プロセッサ)の有無と並列数**
- **コンパイラのバージョン**

**必ず排除するもの**

- **ウイルス対策ソフトのリアルタイムスキャン。** これは冗談ではありません。中間ディレクトリを除外設定に入れるだけで、ビルド時間が半分になることがあります。**モジュール化より効果が大きい可能性があります**
- **他の重いプロセス**(ブラウザ、別のビルド、インデックス作成)
- **ノート PC の電源設定。** バッテリー駆動だと CPU の周波数が下がります

**注意すべきもの**

- **初回はディスクキャッシュが冷たい。** 1回目は捨てて、2回目以降を使います
- **ストレージの種類。** NVMe SSD と HDD では話が変わります

> **測る前に、まずウイルス対策の除外設定を確認してください。**
>
> モジュール化に何週間もかけるより、除外設定を1つ足すほうが速いことがあります。これは冗談まじりですが、事実です。

## 21.2 計測の道具

### 21.2.1 全体の時間を測る

いちばん単純な方法です。PowerShell で `Measure-Command` を使います。

```powershell
Measure-Command { msbuild GameMath.sln /p:Configuration=Release /p:Platform=x64 /t:Rebuild }
```

CMake なら、こうです。

```powershell
Measure-Command { cmake --build build --config Release }
```

`TotalSeconds` の値を見ます。

**Visual Studio の GUI からビルドした時間は使わないでください。** IDE の処理が混ざり、再現性が下がります。

### 21.2.2 MSBuild のビルドタイミング

Visual Studio の設定で、ビルドごとの経過時間を出力ウィンドウに表示できます。

**[ツール] → [オプション] → [プロジェクトおよびソリューション] → [ビルド/実行]** で、**MSBuild プロジェクト ビルドの出力の詳細** を「標準」以上にします。

コマンドラインなら、詳細度を上げます。

```
msbuild GameMath.sln /v:normal
```

プロジェクト単位・ターゲット単位の時間が分かるので、**どのプロジェクトが遅いのか**を切り分けられます。

### 21.2.3 Build Insights で内訳を見る

Visual Studio には **Build Insights** という機能があり、ビルドの内訳を可視化できます。

**[ビルド] → [Build Insights の実行]** から起動します(メニューの位置はバージョンによって異なります)。ビルドが完了すると、トレースが表示されます。

見るべきものは3つです。

**1. どのファイルのコンパイルが遅いか**

上位数個が全体の大半を占めていることがよくあります。そこだけ手を入れれば済むかもしれません。

**2. どのヘッダの解析に時間がかかっているか**

ヘッダ版を測るときに効きます。「`<algorithm>` の解析に全体の30%」といったことが分かります。

**3. テンプレートの実体化にかかっている時間**

**ここが重要です。** 第1章 1.4.5 で書いたとおり、**モジュールはテンプレートの実体化コストを削りません。** 実体化が支配的なら、モジュール化しても改善しません。

**移行を検討しているなら、まず Build Insights で「解析」と「実体化」の比率を見てください。** それだけで判断がつくことがあります。

### 21.2.4 取り込んでいる量を数える

**[C/C++] → [詳細設定] → インクルード ファイルの一覧を表示**(`/showIncludes`)を有効にすると、各翻訳単位が取り込んだヘッダの一覧が出力されます。

行数を数えれば、「1つの `.cpp` が何個のヘッダを読んでいるか」が分かります。第1章 1.1.3 のプリプロセス結果と合わせて見ると、規模感がつかめます。

第19章 19.3.5 で書いたとおり、この出力は**依存グラフを作る材料**にもなります。

### 21.2.5 3回測って中央値

1回の計測は信用できません。

**最低3回、できれば5回測って、中央値を使ってください。** 平均ではなく中央値にするのは、外れ値(別のプロセスが割り込んだ回)の影響を避けるためです。

そして、**1回目は捨ててください。** ディスクキャッシュが温まっていないので、他と条件が違います。

```powershell
1..5 | ForEach-Object {
    Remove-Item -Recurse -Force build -ErrorAction SilentlyContinue
    cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release | Out-Null
    (Measure-Command { cmake --build build }).TotalSeconds
}
```

## 21.3 実験A ── 標準ライブラリだけを比べる

### 21.3.1 いちばん単純で、いちばん効果が大きい比較

自作のライブラリを2つの版で用意するのは手間がかかります。まず、**準備がほとんど要らないのに効果が大きい**比較から始めます。

**標準ライブラリを `#include` するか、`import std;` するか。**

実務のコードベースでも、ビルド時間の大半は標準ライブラリの解析が占めていることがよくあります。だから、この比較だけで判断がつく場合があります。

### 21.3.2 測定用のファイルを生成する

同じ内容の `.cpp` を、100個ずつ2組作ります。手で書くのは無理なので、PowerShell で生成します。

**ヘッダ版**

```powershell
New-Item -ItemType Directory -Force bench_include | Out-Null

1..100 | ForEach-Object {
    $n = $_
    @"
#include <vector>
#include <string>
#include <algorithm>
#include <map>
#include <cmath>

void Func$n()
{
    std::vector<int> v{ 3, 1, 2 };
    std::sort(v.begin(), v.end());
    std::string s = "x";
    std::map<int, std::string> m;
    m[1] = s;
}
"@ | Set-Content -Encoding UTF8 "bench_include/inc_$n.cpp"
}
```

**モジュール版**

```powershell
New-Item -ItemType Directory -Force bench_import | Out-Null

1..100 | ForEach-Object {
    $n = $_
    @"
import std;

void Func$n()
{
    std::vector<int> v{ 3, 1, 2 };
    std::sort(v.begin(), v.end());
    std::string s = "x";
    std::map<int, std::string> m;
    m[1] = s;
}
"@ | Set-Content -Encoding UTF8 "bench_import/imp_$n.cpp"
}
```

**中身は同じで、取り込み方だけが違います。**

### 21.3.3 測る

それぞれを別のプロジェクトにして、フルビルドを測ります。`main` は不要なので、静的ライブラリにします。

CMake なら、こうです。

```cmake
cmake_minimum_required(VERSION 3.28)
project(Bench LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 23)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

file(GLOB INC_SOURCES bench_include/*.cpp)
add_library(bench_include STATIC ${INC_SOURCES})

file(GLOB IMP_SOURCES bench_import/*.cpp)
add_library(bench_import STATIC ${IMP_SOURCES})
# import std; を使うには第20章 20.2.4 の設定が必要
```

Visual Studio でやるなら、空のプロジェクトを2つ作って、それぞれのフォルダーのファイルを追加します。**`import std;` のほうは、第2章 2.3.3 の設定が必要です。**

21.2.5 の手順で、それぞれ5回測ってください。

### 21.3.4 何が見えるか

結果を書き込む表を用意しておきます。

| 翻訳単位の数 | ヘッダ版(秒) | モジュール版(秒) | 比 |
|---|---|---|---|
| 10 | | | |
| 50 | | | |
| 100 | | | |
| 200 | | | |

**1つの数字ではなく、翻訳単位の数を変えて測ってください。** これが重要です。

第1章 1.1.4 で見たコストの構造を思い出してください。

```
ヘッダ:     翻訳単位の数 × ヘッダの総量        ← 掛け算
モジュール: 1回の解析 + 翻訳単位の数 × .ifc 読み込み  ← 足し算
```

**この構造が正しければ、翻訳単位を増やすほど差が開くはずです。**

- 翻訳単位が 10 個 ── モジュール版は `std.ifc` を作るぶん、**遅いかもしれません**
- 翻訳単位が 100 個 ── 差が出はじめるはずです
- 翻訳単位が 200 個 ── 差が広がるはずです

もし差が開かないなら、**あなたの環境では別の要因が支配的です。** 21.5.3 に進んでください。

そして、この形は `import std;` に限りません。**自作ライブラリでも同じ構造が成り立つはずです。** それを次の実験で確かめます。

## 21.4 実験B ── 同一ライブラリのヘッダ版とモジュール版

### 21.4.1 公平な比較の条件

自作ライブラリを比べるときは、条件を揃えるのが難しくなります。次の3つを守ってください。

**条件1: 中身が同じであること**

「モジュール版のほうが設計を見直したから速い」では、モジュールの効果を測ったことになりません。**同じ関数、同じテンプレート、同じ実装**にします。

**条件2: 使われ方が同じであること**

消費側のコードが、両方で同じ関数を同じ回数呼ぶようにします。

**条件3: 翻訳単位が十分にあること**

21.3.4 で見たとおり、翻訳単位が少ないと差が出ません。**最低でも50、できれば100以上**用意してください。

### 21.4.2 ヘッダ版を用意する

`GameMath` のヘッダ版が必要です。

**本書にヘッダ版の全文は載せません。** 第4章から第16章までのコードから、モジュール特有の構文を取り除けば作れます。作業は機械的です。

| モジュール版 | ヘッダ版 |
|---|---|
| `export module gamemath.core:vector;` | `#pragma once` |
| `import :matrix;` | `#include "Matrix.h"` |
| `import std;` | `#include <cmath>` など |
| `export struct Vector { ... };` | `struct Vector { ... };` |
| `export template <...> ...` | `template <...> ...` |
| 実装単位(`.cpp`) | そのまま `.cpp` |
| 内部パーティション | `detail/` の内部ヘッダ |
| プライベートモジュールフラグメント | `.cpp` に移す |

**第19章 19.2 の構成A を使う手もあります。** ヘッダを正として、モジュールの入口を追加する形です。これなら中身が完全に同一であることが保証されます。

ただし、19.2.8 で書いたとおり、構成A のモジュール版は「ヘッダの内容をそのまま `.ifc` に載せたもの」になります。**モジュール版の `.ifc` が大きくなるので、本来の設計より不利な条件になります。** それを承知のうえで測るなら、下限の見積もりとして有用です。

### 21.4.3 消費側を生成する

100個の `.cpp` を生成します。

```powershell
1..100 | ForEach-Object {
    $n = $_
    @"
#include "GameMath/All.h"

float Consume$n(float t)
{
    const gamemath::Vector3 a{ t, t * 2.0f, t * 3.0f };
    const gamemath::Vector3 b{ 1.0f, 0.0f, 0.0f };
    const gamemath::Matrix4x4 m = gamemath::RotationZ(t);
    const gamemath::Quaternion q = gamemath::FromAxisAngle(b, t);
    const gamemath::Vector3 r = gamemath::TransformDirection(m, a);
    return gamemath::Dot(r, gamemath::Rotate(q, b)) + a.Length();
}
"@ | Set-Content -Encoding UTF8 "consumer_header/use_$n.cpp"
}
```

モジュール版は、1行目を `import gamemath;` に変えるだけです。

**複数の型と関数を使ってください。** `Vector3` だけを使うコードでは、`Matrix4x4` や `Quaternion` を含むヘッダの解析コストが見えません。実際のゲームコードは、たいてい複数を使います。

### 21.4.4 4種類のビルドを測る

21.1.2 の表に従って測ります。

| ビルドの種類 | 変更する場所 | ヘッダ版 | モジュール版 |
|---|---|---|---|
| フルビルド | ── | | |
| 利用側の増分 | `use_1.cpp` に空行を1行 | | |
| 実装の増分 | `Basis.cpp` に空行を1行 | | |
| インターフェイスの増分 | `Vector.h` / `Vector.ixx` に空行を1行 | | |
| no-op | 何も変更しない | | |

**「空行を1行」でよいのか**と思うかもしれません。よいのです。ビルドシステムはタイムスタンプで判断するので、内容の変更量とは無関係です。**測りたいのは波及範囲**です。

## 21.5 結果をどう読むか、どこで効いてくるか

### 21.5.1 モジュールが速くなる条件

理屈から予測できることを整理します。

**条件1: 翻訳単位が多い**

掛け算が足し算になる効果は、翻訳単位の数に比例します。10個では差が出ませんが、1000個なら大きく出ます。

**条件2: インターフェイスが重い**

標準ライブラリを大量に取り込んでいる、テンプレートが多い ── ヘッダの解析コストが大きいほど、削れる量も大きくなります。

**条件3: 依存が浅い**

第20章 20.1.4 で見たとおり、依存が深いと並列度が下がります。土台が薄く、その上が横に広がっている構造が有利です。

**条件4: インターフェイスの変更が少ない**

インターフェイスを変えると、`import` している全部が再コンパイルされます(第5章 5.1.3、第7章 7.4.5)。安定したライブラリほど有利です。

### 21.5.2 モジュールが遅くなる条件

正直に書きます。**モジュール版のほうが遅くなることがあります。**

**原因1: スキャンのオーバーヘッド**

no-op ビルドで顕著に出ます。何も変わっていなくても、依存グラフの構築は走ります。

**原因2: 依存が深く、並列度が下がっている**

`:vector` → `:detail` → `:basis` → ... と直列に並んだ構造だと、CPU のコアが遊びます。ヘッダなら全部同時にコンパイルできました。

**原因3: 巨大な `.ifc` を全員が読んでいる**

第1章 1.4.1 と第12章 12.3.4 で警告したことです。傘モジュールだけを提供し、全員が `import gamemath;` と書いていると、`Vector2` しか使わないファイルも全部を読みます。

**原因4: インターフェイスに実装を書きすぎている**

数学ライブラリは、性能のためにインターフェイスへ寄せる判断をしました(第8章 8.5.5)。その代償として、`.ifc` が大きくなり、インターフェイスの変更が広く波及します。**トレードオフを受け入れた結果であって、失敗ではありません。**

### 21.5.3 差が出ない場合 ── 何が支配的か

測ったが、ほとんど変わらなかった。よくあることです。

**Build Insights(21.2.3)で内訳を見てください。** 支配的な要因は、たいてい次のどれかです。

| 支配的な要因 | モジュールの効果 | 対処 |
|---|---|---|
| **ヘッダの解析** | **大きい** | モジュール化が効く |
| **テンプレートの実体化** | **なし** | 明示的インスタンス化、型消去、実体化の削減 |
| **最適化(コード生成)** | **なし** | Debug ビルドで測ってみる、`/O` の見直し |
| **リンク** | **なし** | 増分リンク、`/DEBUG:FASTLINK`、ライブラリ分割 |
| **ディスク I/O** | **なし** | SSD、除外設定、中間ディレクトリの場所 |

**テンプレートの実体化が支配的なら、モジュール化しても速くなりません。** 第1章 1.4.5 で書いたとおりです。

これは重要な発見です。**「モジュール化しても効果がない」と分かったことは、失敗ではなく成果です。** 何週間もかけて移行する前に判明したのですから。

### 21.5.4 no-op ビルドが遅い場合

スキャンのコストです。

**対処1: スキャンの範囲を絞る**

第18章 18.2.3 で「モジュール依存関係のソースをスキャンする」を「はい」にしました。これは全ソースをスキャンします。

`.ixx` だけで足りるなら、「いいえ」に戻せます。ただし実装単位の依存が追跡されなくなるので、第17章 17.3.9 のビルド順序問題が起きる可能性があります。**トレードオフです。**

**対処2: プロジェクトを分割する**

変更しない部分を別のプロジェクトにして、そちらのスキャンを走らせないようにします。

**対処3: 受け入れる**

no-op ビルドは、開発中に何度も走るものではありません。数秒の増加なら、増分ビルドの改善で十分に取り返せます。

### 21.5.5 インターフェイスの増分が遅い場合

**これがいちばん重要な指標です。**

`.ixx` を1行変えたときに、100ファイル全部が再コンパイルされるなら、設計を見直す余地があります。

第5章 5.6.4 で確認したとおり、実装単位に置いた関数は変更しても波及しません。**インターフェイスに書きすぎていないか**を確認してください。

ただし、数学ライブラリでは性能のためにインターフェイスへ寄せる判断をしました(第8章 8.5.5)。**波及範囲と実行速度は、しばしばトレードオフです。** どちらを優先するかは、そのライブラリの性質で決めます。

### 21.5.6 数字を報告するときの作法

チームや記事で結果を共有するときは、次を必ず添えてください。

```
□ CPU(モデル名とコア数)
□ ストレージの種類
□ コンパイラのバージョン(cl のバージョン文字列)
□ ビルド構成(Debug / Release)、最適化オプション
□ /MP の有無と並列数
□ 翻訳単位の数
□ 測定回数と、中央値であること
□ ウイルス対策の除外設定の有無
```

これらが書かれていない「モジュールで N 倍速くなった」という報告は、参考になりません。**自分が書くときも同じです。**

## 21.6 遅かったらどうするか

測って期待外れだった場合の手順です。

### 21.6.1 まず、支配的な要因を確認する

21.5.3 の表です。そもそもモジュールの守備範囲外なら、これ以上やっても無駄です。**撤退の判断も成果です。**

### 21.6.2 依存グラフの形を見直す

第20章 20.1.4 で見たとおり、依存が深いと並列度が下がります。

```
悪い形(直列)          良い形(横に広い)

  A                        A
  ↓                    ↙ ↓ ↘
  B                   B   C   D
  ↓                    ↘ ↓ ↙
  C                        E
  ↓
  D
```

第12章 12.1.5 の指針に、もう1つ加えることになります。**土台は薄く、その上は横に広げる。**

`GameMath` の依存グラフ(第14章 14.2.8)を見返してください。`:vector` を土台に、`:matrix` と `:quaternion` が横に並んでいます。悪くない形です。

### 21.6.3 インターフェイスを薄くする

`.ifc` が大きいと、読み込みのコストが上がり、変更の波及も広がります。

- 実装単位に移せるものはないか(第5章 5.6.5)
- 内部パーティションに移せるものはないか(第10章 10.3.2)
- 明示的インスタンス化で隠せるテンプレートはないか(第8章 8.4)

ただし、**インライン展開と `constexpr` を失う代償があります**(第8章 8.5.5)。数学ライブラリでは、この判断は慎重に。

### 21.6.4 傘を使わせない

第12章 12.3.4 の問題です。全員が `import gamemath;` と書いていると、分割した意味がありません。

消費側の `import` を、必要なサブモジュールに変えてみてください。

```cpp
import gamemath.core;        // 幾何も乱数も要らない場合
```

**これだけで改善することがあります。** そして、これはライブラリ側の変更を必要としません。いちばん安い対処です。

### 21.6.5 それでも駄目なら

**元に戻す判断をしてください。**

第19章 19.1 で「移行しないという選択肢」を書きました。測って効果がないと分かったなら、それは正しい判断材料です。

ただし、モジュール化で得たものはビルド時間だけではありません。

- カプセル化が言語で保証される(第7章)
- マクロ汚染が原理的に起きない(第3章 3.6.4)
- ODR 違反が構造的に防がれる(第16章 16.4.5)
- 循環依存が設計時に発見される(第10章 10.4.2)

**ビルド時間が変わらなくても、これらに価値があると判断するなら、続ける理由になります。** それも測定に基づく判断です。

## 21.7 この章のまとめ

- **具体的な秒数は環境依存。** 覚えるべきは測り方と読み方
- 待ち時間の合計に効くのは、フルビルドではなく**増分ビルド**
- 最低4種類を測る ── フルビルド / 利用側の増分 / **インターフェイスの増分** / no-op
- **インターフェイスの増分が、設計の良し悪しを最もよく表す**
- 測る前に条件を揃える。**ウイルス対策の除外設定は、モジュール化より効果が大きいことがある**
- 3〜5回測って中央値。**1回目は捨てる**
- 道具 ── `Measure-Command`、MSBuild の詳細出力、**Build Insights**、`/showIncludes`
- **Build Insights で「解析」と「実体化」の比率を見る。** 実体化が支配的ならモジュール化は効かない
- **翻訳単位の数を変えて測る。** 掛け算が足し算になっているなら、数を増やすほど差が開く
- 速くなる条件 ── 翻訳単位が多い / インターフェイスが重い / 依存が浅い / インターフェイスが安定している
- 遅くなる条件 ── スキャンのオーバーヘッド / 依存が深い / 巨大な `.ifc` を全員が読む / インターフェイスに書きすぎ
- 差が出ないなら、支配的な要因を確認する。**テンプレートの実体化・リンク・I/O にはモジュールは効かない**
- **「効果がない」と分かったことは失敗ではなく成果。** 移行前に判明したのだから
- 数字を報告するときは、環境と条件を必ず添える
- 遅かったら ── 依存グラフを横に広げる / インターフェイスを薄くする / **傘を使わせない**
- それでも駄目なら戻す。ただし**ビルド時間以外の価値**を評価に含める

## 次章に向けて

最終章です。第22章では、`GameMath` を**実際のゲームコードから使います。**

- 簡単な描画サンプルから `import gamemath;` する
- 他ライブラリのヘッダと混ぜたときに何が起きたか
- そして、完成したライブラリの全体像を振り返る

第18章で学んだ「サードパーティのヘッダとの共存」が、今度は**自分がその立場**になって現れます。ウィンドウ管理や描画 API のヘッダは、モジュールになっていません。それらと `GameMath` を同じ翻訳単位で使うと、何が起きるのか。

本書で積み上げてきた判断が、最後に実地で試されます。
