# 第16章 SIMD 対応

## この章について

**この章は難度が上がります。**

扱うのは SIMD ── 1つの命令で複数のデータを同時に処理する仕組みです。ゲーム開発では避けられない話題ですが、モジュールの学習という観点からは応用的な内容になります。

**読み飛ばして第17章に進んでも支障はありません。** ここで作るものは、後の章の前提になっていません。

とはいえ、この章には本書全体を通じていちばん鮮明な場面があります。

```cpp
#ifdef GAMEMATH_USE_SIMD
// SIMD 版
#else
// スカラー版
#endif
```

**この設計が、モジュールでは成立しません。**

第7章 7.1.3 で予告し、第13章 13.3.4 でも触れた問題です。マクロはモジュール境界を越えません。ヘッダの時代に当たり前だった「利用者がマクロを定義してライブラリの振る舞いを変える」という手法が、丸ごと使えなくなります。

何が失われ、何が代わりになるのか。**モジュールが何を封じたのか**が、この章でもっとも具体的に見えます。

内容は5つです。

1. `<immintrin.h>` をどこに書くか(16.1)
2. スカラー版と SIMD 版を書く(16.2)
3. 切り替える ── `if consteval` と `if constexpr`(16.3)
4. マクロによる切り替えが効かないことを確認する(16.4)
5. 型による切り替えに置き換える(16.5)

---

## 16.1 `<immintrin.h>` をどこに書くか

### 16.1.1 SIMD の最小限の説明

現代の CPU には、4個の `float` を1命令で足す命令があります。

```
通常:  a0+b0, a1+b1, a2+b2, a3+b3   ← 4命令
SIMD:  [a0 a1 a2 a3] + [b0 b1 b2 b3] ← 1命令
```

C++ からこれを使うには、**組み込み関数**(intrinsics)を呼びます。x64 では `<immintrin.h>` が提供します。

```cpp
__m128 va = _mm_loadu_ps(a);      // 4個の float を読み込む
__m128 vb = _mm_loadu_ps(b);
__m128 vr = _mm_add_ps(va, vb);   // 4個同時に加算
_mm_storeu_ps(result, vr);        // 書き戻す
```

`__m128` は「4個の `float` を保持する 128 ビットのレジスタ」を表す型です。コンパイラが特別に扱う型で、通常の C++ の型とは性質が違います。

`Matrix4x4` の積を SIMD 化します。4×4 行列の積は掛け算 64 回と足し算 48 回で、ゲームのフレームごとに数千回から数万回実行されます。効果が出やすく、実装も比較的短くて済む題材です。

### 16.1.2 `import std;` では取り込めない

第6章で、標準ライブラリは `import std;` で取り込むと決めました(6.6.1)。

**`<immintrin.h>` は標準ライブラリではありません。** コンパイラベンダーが提供するヘッダです。`import std;` には含まれていません。

そこで第6章 6.6.1 の方針3が発動します。

> グローバルモジュールフラグメントは、`import` できないヘッダのために取っておく。

いよいよその場面です。

### 16.1.3 3つの候補と、正解

`Matrix.ixx` のどこに `#include <immintrin.h>` を書くか。候補は3つあります。

**候補1: モジュール宣言より後ろ(購買域)**

```cpp
export module gamemath.core:matrix;

#include <immintrin.h>      // ← 駄目
```

第6章 6.1.2 で見たとおり、警告 **C5244** が出ます。そしてビルドは通ってしまいます。だから危険です。

**候補2: 実装単位のグローバルモジュールフラグメント**

```cpp
// Matrix.cpp
module;
#include <immintrin.h>
module gamemath.core;
```

これは正しい書き方です。第6章 6.3.5 で確認した「実装単位に閉じ込める」やり方です。

しかし、**この場合は使えません。** 行列の積は `operator*` として実装しており、それは隠しフレンド ── つまりインターフェイスに書かれたインライン関数です。実装単位に移せば、インライン展開されなくなります(第5章 5.6.1)。

SIMD 化して速くしたいのに、関数呼び出しのオーバーヘッドを増やしては本末転倒です。

**候補3: インターフェイスパーティションのグローバルモジュールフラグメント**

```cpp
// Core/Matrix.ixx
module;
#include <immintrin.h>

export module gamemath.core:matrix;
```

**これが正解です。**

### 16.1.4 書く

`Core/Matrix.ixx` の先頭を書き換えてください。

```cpp
// Core/Matrix.ixx
module;

#include <immintrin.h>

export module gamemath.core:matrix;

import :vector;
import std;

namespace gamemath {
// ...
```

第6章 6.3.1 の規則を思い出してください。**`module;` の前に置けるのはコメントと空白だけ**です。ファイルの先頭にコメントを書くなら、`module;` より前に置けます。

ビルドしてください。警告なしで通ります。

代償があります。第6章 6.3.5 で述べたとおり、**インターフェイスパーティションの GMF に書いたものは `.ifc` に反映されます。** `gamemath.core` を `import` する側のコンパイル時間に、わずかながら影響します。

インライン展開を取るか、`.ifc` の軽さを取るか ── ここでは前者を取りました。数学ライブラリでは、ほぼ常にそうなります(第8章 8.5.5)。

### 16.1.5 なぜ購買域では駄目なのか、もう一度

第6章 6.1.5 で説明した理屈を、`__m128` に当てはめておきます。ここは実害が分かりやすい例です。

購買域に `#include <immintrin.h>` を書くと、`__m128` という型が **`gamemath.core` モジュールに属する**ことになります。

一方、利用者のコードが `#include <immintrin.h>` していれば、そちらの `__m128` は**グローバルモジュールに属します**。

**同じ名前の、別の型です。**

```cpp
// main.cpp
#include <immintrin.h>
import gamemath;

__m128 v = SomethingFromGameMath();   // 型が違うのでエラー
```

`GameMath` が `__m128` を返す関数を公開していたら、利用者はそれを受け取れません。名前も定義も同じなのに、コンパイラにとっては別物だからです。

グローバルモジュールフラグメントに書けば、両方が同じ実体になります。**これが GMF の存在理由です。**

### 16.1.6 `__m128` を公開インターフェイスに出さない

そして、もう1つ重要な設計判断があります。

**`__m128` を、公開する宣言のシグネチャに出しません。**

第12章 12.3.2 で立てた規則を思い出してください。

> 公開する宣言のシグネチャに、他のモジュールの型が現れるなら、そのモジュールを `export import` する。

`__m128` はモジュールの型ではありませんが、同じ問題が起きます。もし公開シグネチャに `__m128` が現れたら、**利用者は `<immintrin.h>` を自分で `#include` しなければ型名を書けません。**

第15章 15.3.3 で `std::optional` について検討したのと、まったく同じ構図です。「使えるが名前が書けない」状態になります。

さらに悪いことに、`__m128` には **16 バイト境界のアラインメント要求**があります。これがクラスのメンバに現れると、`sizeof` と `alignof` が変わり、利用者の構造体レイアウトに影響します。第11章 11.3.4 で扱った ABI の問題です。

**`__m128` は、関数の中だけで使います。** 引数にも戻り値にもメンバ変数にも現れさせません。

この方針は、`GameMath` の公開 API から標準ライブラリの型を排除してきたのと同じ考え方です(第6章 6.5.4)。**外部の型を公開インターフェイスに出さない**という一貫した方針が、SIMD 対応でも効いています。

## 16.2 スカラー版と SIMD 版を書く

### 16.2.1 スカラー版を切り出す

第13章 13.4.2 で書いた `operator*` の中身を、`static` メンバ関数に切り出します。

```cpp
// Core/Matrix.ixx(Matrix4x4 の中)

export struct Matrix4x4
{
    float m[4][4];

    static constexpr Matrix4x4 Identity() { /* 変更なし */ }

    constexpr float& operator()(std::size_t row, std::size_t col) { /* 変更なし */ }
    constexpr float operator()(std::size_t row, std::size_t col) const { /* 変更なし */ }

    // ───── 実装方式ごとの積 ─────

    static constexpr Matrix4x4 MultiplyScalar(const Matrix4x4& a, const Matrix4x4& b)
    {
        Matrix4x4 r{};
        for (std::size_t i = 0; i < 4; ++i) {
            for (std::size_t j = 0; j < 4; ++j) {
                float sum = 0.0f;
                for (std::size_t k = 0; k < 4; ++k) {
                    sum += a.m[i][k] * b.m[k][j];
                }
                r.m[i][j] = sum;
            }
        }
        return r;
    }

    // ...(SIMD 版は次の項)
};
```

`static` メンバ関数にしたのは、**呼び出しの順序の問題を避けるため**です。

自由関数として書くと、`operator*`(隠しフレンド)の中から呼ぶために、クラス定義より前に宣言しておく必要があります。そのためには `Matrix4x4` の前方宣言も必要で、コードが読みにくくなります。

`static` メンバ関数なら、クラスの中で完結します。そして第4章 4.3.4 で確認したとおり、**クラスを `export` すれば `public` な `static` メンバ関数も一緒に使えるようになります。** 個別の `export` は不要です。

### 16.2.2 SIMD 版を書く

続けて書きます。

```cpp
    static Matrix4x4 MultiplySimd(const Matrix4x4& a, const Matrix4x4& b)
    {
        Matrix4x4 r{};

        // b の各行を 128 ビットレジスタに読み込む
        const __m128 b0 = _mm_loadu_ps(b.m[0]);
        const __m128 b1 = _mm_loadu_ps(b.m[1]);
        const __m128 b2 = _mm_loadu_ps(b.m[2]);
        const __m128 b3 = _mm_loadu_ps(b.m[3]);

        for (std::size_t i = 0; i < 4; ++i) {
            // a[i][k] を4つ複製したレジスタを作る
            const __m128 a0 = _mm_set1_ps(a.m[i][0]);
            const __m128 a1 = _mm_set1_ps(a.m[i][1]);
            const __m128 a2 = _mm_set1_ps(a.m[i][2]);
            const __m128 a3 = _mm_set1_ps(a.m[i][3]);

            // r[i] = a[i][0]*b[0] + a[i][1]*b[1] + a[i][2]*b[2] + a[i][3]*b[3]
            __m128 row = _mm_mul_ps(a0, b0);
            row = _mm_add_ps(row, _mm_mul_ps(a1, b1));
            row = _mm_add_ps(row, _mm_mul_ps(a2, b2));
            row = _mm_add_ps(row, _mm_mul_ps(a3, b3));

            _mm_storeu_ps(r.m[i], row);
        }

        return r;
    }
```

行優先の格納順序(第13章 13.1.2)が、ここで効いています。`b.m[0]` は連続した4個の `float` なので、そのまま1つのレジスタに読み込めます。

**`constexpr` が付いていません。** 組み込み関数は `constexpr` ではないからです。これが 16.3 の課題になります。

### 16.2.3 `alignas` をどうするか

`_mm_loadu_ps` の `u` は unaligned(アラインメントされていない)を意味します。アドレスが 16 バイト境界に揃っていなくても読める命令です。

揃っていれば `_mm_load_ps`(`u` なし)が使えて、わずかに速くなります。そのためには、こう書くことになります。

```cpp
export struct Matrix4x4
{
    alignas(16) float m[4][4];      // 16 バイト境界に揃える
    // ...
};
```

**採用しません。** 理由が2つあります。

**理由1: ABI が変わります。**

`alignas(16)` を付けると、`Matrix4x4` の `alignof` が 4 から 16 になります。すると `Matrix4x4` を含む利用者の構造体のレイアウトが変わり、配列のパディングが変わります。

そして第11章 11.3.4 で確認したとおり、**データレイアウトは公開インターフェイスの一部です。** 後から変えれば、利用者は再コンパイルが必要になります。

**理由2: 効果が小さくなっています。**

Skylake 世代以降の CPU では、アラインメントされていないロードの追加コストはほとんどありません。かつては大きな差でしたが、いまは測っても見えにくい程度です。

「揃えれば速くなる」という古い常識に従って ABI を固くするのは、費用対効果が悪い判断です。

> **もし揃えたくなったら**
>
> `Matrix4x4` そのものではなく、**SIMD 専用の別の型**を用意するのが安全です。
>
> ```cpp
> export struct alignas(16) Matrix4x4Aligned { float m[4][4]; };
> ```
>
> 利用者が明示的に選べるようになり、既存のコードには影響しません。第15章 15.3.5 で `RayHit` を自前の型にしたのと同じ発想です ── **選択肢を型として提示する**。

### 16.2.4 いったん動かしてみる

`operator*` はまだスカラー版を呼んでいます。SIMD 版が正しいかどうか、直接呼んで確かめましょう。

```cpp
// main.cpp

const gamemath::Matrix4x4 mA = gamemath::RotationZ(half);
const gamemath::Matrix4x4 mB = gamemath::Translation(t);

const gamemath::Matrix4x4 byScalar = gamemath::Matrix4x4::MultiplyScalar(mA, mB);
const gamemath::Matrix4x4 bySimd   = gamemath::Matrix4x4::MultiplySimd(mA, mB);

std::println("Scalar == Simd : {}", gamemath::NearlyEqual(byScalar, bySimd));
```

ビルドして実行してください。

```
Scalar == Simd : true
```

一致しました。第14章 14.4.2 で用意した `NearlyEqual` が役に立っています。

**厳密な `==` ではなく `NearlyEqual` を使っている**ことに注意してください。SIMD 版とスカラー版で、浮動小数点の加算の順序が違います。結果は数学的に同じですが、ビット単位では一致しないことがあります。

これは SIMD 化で必ず問題になる点です。**「速くなったが、結果が変わった」** ── リプレイやネットワーク同期で決定論が必要なゲームでは、深刻な問題になりえます。SIMD 化の前に、どこまでの差を許容するのか決めておいてください。

## 16.3 SIMD 版とスカラー版を切り替える設計

### 16.3.1 使える環境かどうかを表す定数

`operator*` が自動的に速いほうを選ぶようにします。まず、この環境で SIMD が使えるかどうかを表す定数を作ります。

```cpp
// Core/Matrix.ixx(namespace gamemath の先頭あたり)

// このビルドで SIMD 版が使えるか
export inline constexpr bool kSimdAvailable =
#if defined(_M_X64)
    true;
#else
    false;
#endif
```

x64 では SSE2 が必ず使えるので、`_M_X64` の判定だけで十分です。

`export` を付けています。**利用者が知りたい情報だから**です。「このビルドでは SIMD が有効か」をログに出したり、ベンチマークの条件に使ったりします。第15章 15.4.3 の「使えないものは公開すべきのサイン」と同じ判断です。

### 16.3.2 `constexpr` が失われる

素直に書くと、こうなります。

```cpp
    friend Matrix4x4 operator*(const Matrix4x4& a, const Matrix4x4& b)
    {
        if constexpr (kSimdAvailable) {
            return MultiplySimd(a, b);
        }
        else {
            return MultiplyScalar(a, b);
        }
    }
```

ビルドすると、**別のところが壊れます。**

第13章 13.1.5 で書いた `static_assert` が通りません。

```cpp
static_assert(id * id == id);      // ← エラー
```

`operator*` から `constexpr` が消えたからです。組み込み関数は `constexpr` ではないので、付けられませんでした。

第14章 14.3.4 で整理した「2つの門」のうち、門1(`constexpr` として書けるか)を通れなくなったわけです。

これは損失です。単位行列の積や、固定の変換行列の合成は、コンパイル時に確定できたはずのものです。

### 16.3.3 `if consteval` で解決する

C++23 の `if consteval` を使います。「いまコンパイル時評価の途中かどうか」で分岐する構文です。

```cpp
    friend constexpr Matrix4x4 operator*(const Matrix4x4& a, const Matrix4x4& b)
    {
        if consteval {
            // コンパイル時評価中 ── スカラー版しか使えない
            return MultiplyScalar(a, b);
        }
        else {
            // 実行時 ── 速いほうを使う
            if constexpr (kSimdAvailable) {
                return MultiplySimd(a, b);
            }
            else {
                return MultiplyScalar(a, b);
            }
        }
    }
```

`constexpr` が戻りました。ビルドして、`static_assert` が通ることを確認してください。

仕組みはこうです。

- **コンパイル時**に評価されるときは `if consteval` の真の側が選ばれ、`MultiplyScalar`(`constexpr`)が呼ばれます
- **実行時**には偽の側が選ばれ、SIMD 版が呼ばれます

`constexpr` 関数の中に `constexpr` でない関数の呼び出しがあっても、**コンパイル時評価の経路で実行されなければ構いません。** `if consteval` は、まさにこのために用意された構文です。

2段階の分岐になっている理由も押さえておいてください。

- `if consteval` ── コンパイル時か実行時か(**評価の文脈**による分岐)
- `if constexpr` ── SIMD が使えるビルドか(**コンパイル時に確定した条件**による分岐)

役割が違います。前者は文脈、後者は設定です。

### 16.3.4 動作確認

```cpp
// main.cpp

std::println("SIMD available : {}", gamemath::kSimdAvailable);

// コンパイル時計算(スカラー版で評価される)
static_assert(gamemath::Matrix4x4::Identity() * gamemath::Matrix4x4::Identity()
              == gamemath::Matrix4x4::Identity());

// 実行時計算(SIMD 版が使われる)
const gamemath::Matrix4x4 product = mA * mB;
std::println("operator* == Simd : {}",
             gamemath::NearlyEqual(product, bySimd));
```

ビルドして実行してください。

```
SIMD available : true
operator* == Simd : true
```

`static_assert` がコンパイル時に通り、実行時には SIMD 版と同じ結果になっています。**両方を1つの `operator*` で実現できました。**

> **コラム: 他のプラットフォーム**
>
> `<immintrin.h>` は x86 / x64 専用です。Windows on ARM(ARM64)では存在せず、代わりに NEON(`<arm_neon.h>`)を使います。
>
> 対応するには、グローバルモジュールフラグメントを条件分岐させます。
>
> ```cpp
> module;
> #if defined(_M_X64)
> #include <immintrin.h>
> #elif defined(_M_ARM64)
> #include <arm_neon.h>
> #endif
> export module gamemath.core:matrix;
> ```
>
> **グローバルモジュールフラグメントにプリプロセッサ指令を書けるのは、こういう場面のためです**(第6章 6.3.2)。「C++ のコードは書けないが、プリプロセッサ指令は書ける」という一見半端な仕様に、はっきりした理由があります。
>
> ただし、`MultiplySimd` の中身も分岐させることになり、コードは倍になります。本書は x64 に限定して、この分岐を扱いません。

## 16.4 マクロによる切り替えがモジュールでは効かない問題

ここまで、SIMD を使うかどうかは `kSimdAvailable` ── つまり**ライブラリ側が決めた条件**で決まっていました。

利用者に選ばせたい場面があります。「決定論が必要なので、SIMD を切ってほしい」という要求は現実にあります(16.2.4 で触れた浮動小数点の差の問題です)。

ヘッダの時代なら、こう設計していました。

### 16.4.1 【実験】利用者がマクロを定義する

ライブラリ側を、マクロで切り替えられるように書いてみます。

```cpp
// Core/Matrix.ixx(実験)
export inline constexpr bool kSimdAvailable =
#if defined(_M_X64) && !defined(GAMEMATH_NO_SIMD)
    true;
#else
    false;
#endif
```

「`GAMEMATH_NO_SIMD` を定義すれば SIMD を切れる」という設計です。ヘッダなら、これで動きました。

利用者側で定義してみます。

```cpp
// main.cpp
#define GAMEMATH_NO_SIMD        // ← import より前に定義
import std;
import gamemath;

int main()
{
    std::println("SIMD available : {}", gamemath::kSimdAvailable);
    // ...
}
```

ビルドして実行してください。

```
SIMD available : true
```

**変わりません。** `GAMEMATH_NO_SIMD` は完全に無視されました。警告も出ません。

これがこの章でいちばん重要な事実です。**何も起きない**のです。エラーになれば気づけますが、静かに無視されます。

**追加した `#define` の行を削除してください。**

### 16.4.2 なぜ届かないのか

理由は2つあり、どちらも決定的です。

**理由1: マクロはモジュール境界を越えない**

第7章 7.1 で確認しました。マクロはプリプロセッサの世界のもので、`.ifc` に入るのはコンパイラが解析した後の宣言です。**プリプロセッサとモジュールは、住んでいる時間軸が違います。**

`main.cpp` で `#define` したマクロは、`main.cpp` のプリプロセスにしか影響しません。`Matrix.ixx` は別の翻訳単位で、別のタイミングでコンパイルされます。

**理由2: モジュールは一度だけコンパイルされる**

こちらのほうが本質的です。

ヘッダの時代、`Matrix.h` は**それを `#include` した翻訳単位ごとに**展開・解析されました。だから翻訳単位ごとに違うマクロ状態で解析させることができました。それが「利用者がマクロで切り替える」という手法の土台でした。

モジュールでは、`Matrix.ixx` は**ビルド全体で1回だけ**コンパイルされます(第1章 1.3.3)。生成された `.ifc` が全翻訳単位で共有されます。

**「翻訳単位ごとに違う設定でコンパイルする」ということが、構造的に不可能になりました。**

第1章で「モジュールは解析を1回に減らす」と書きました。その性質の裏側が、これです。1回しか解析しないなら、1通りの結果しか作れません。

### 16.4.3 ビルド設定のマクロなら効く

誤解を避けるために、はっきりさせておきます。**マクロが完全に死んだわけではありません。**

プロジェクトのプロパティで定義すれば、効きます。

**[C/C++] → [プリプロセッサ] → プリプロセッサの定義** に `GAMEMATH_NO_SIMD` を追加してください。16.4.1 のコードを戻して(あるいはそのまま)、ビルドしてみます。

```
SIMD available : false
```

**効きました。**

プロジェクトのプリプロセッサ定義は、そのプロジェクトの**すべての翻訳単位**に適用されます。`Matrix.ixx` もその1つなので、`#if` が反応します。

つまり、切り替えの粒度が変わったのです。

| | ヘッダ | モジュール |
|---|---|---|
| 切り替えの単位 | **翻訳単位ごと** | **ビルドごと** |
| 誰が決めるか | ソースを書く人 | ビルドを構成する人 |
| 1つのビルドに両方の版が共存できるか | できる | **できない** |

**確認できたら、プリプロセッサの定義を削除してください。** そして 16.4.1 の `!defined(GAMEMATH_NO_SIMD)` も削除して、元に戻してください(理由は 16.5 で説明します)。

### 16.4.4 それでも失われた3つのこと

ビルド設定のマクロが効くなら、大した問題ではないのでは ── そうもいきません。3つのことが失われています。

**失われたもの1: ソースコードでの選択**

ライブラリの利用者が、自分のソースファイルの中で「ここは SIMD を切りたい」と書くことができません。ビルド構成を変えるしかありません。

これは、ライブラリとして提供できる自由度が下がったということです。「ヘッダをインクルードする前に `#define` する」という、C++ で何十年も使われてきた作法が使えません。

**失われたもの2: 1つのビルドでの共存**

同じビルドの中で、あるファイルは SIMD 版、別のファイルはスカラー版 ── ということができません。

決定論が必要な物理シミュレーションだけスカラー版を使い、描画は SIMD 版を使う、という設計が取れません。

**失われたもの3: 何が有効なのか、ソースから読み取れない**

これがいちばん厄介です。

ヘッダの時代なら、`#include` の前後を見れば何が有効かが分かりました。モジュールでは、**`.ifc` がどんな設定でビルドされたのか、利用者のソースからは判断できません。**

だから `kSimdAvailable` を `export` して、実行時に確認できるようにしておく価値があります(16.3.1)。**設定が見えなくなったぶん、設定を問い合わせる手段を用意する**必要が出てきたわけです。

### 16.4.5 副作用としての利点 ── ODR 違反が起きなくなった

失ったものだけではありません。得たものもあります。

第1章 1.1.8 で扱った問題を思い出してください。

```cpp
// Renderer.cpp
#define GAMEMATH_ENABLE_SCALE
#include "GameMath/Transform.h"      // Transform は 32 バイト
```

```cpp
// Physics.cpp
#include "GameMath/Transform.h"      // Transform は 20 バイト
```

同じ型が翻訳単位ごとに違うレイアウトを持ち、**コンパイルもリンクも通って、実行時にメモリが静かに壊れる** ── ODR 違反です。

**モジュールでは、これが構造的に起こりません。**

理由は 16.4.2 の理由2そのものです。モジュールは1回だけコンパイルされ、全翻訳単位が同じ `.ifc` を読みます。**「翻訳単位ごとに違う」という状態を作れないのだから、食い違いも起きません。**

第1章 1.3.4 の表に「静かに壊れる(ODR)」の行がありました。あの解決は、この章で失ったものと**同じ性質の裏表**です。

- 1回だけコンパイルする → 翻訳単位ごとの切り替えができない(失った)
- 1回だけコンパイルする → 翻訳単位ごとの食い違いが起きない(得た)

トレードオフとして納得できるかどうかは、プロジェクトの事情によります。しかし、**ランダムなメモリ破壊のデバッグに費やした時間を思い出せば、悪くない取引だと感じる人は多いはずです。**

## 16.5 コンセプトとタグディスパッチによる代替

失われた自由度を、別の手段で取り戻します。

### 16.5.1 方針 ── マクロではなく型で切り替える

本書で繰り返し出てきた原則が、ここで完成します。

| 章 | 場面 | マクロ/ADL による方法 | 代わりに使うもの |
|---|---|---|---|
| 7.1.3 | 設定の切り替え | `#ifdef` | ── |
| 13.3.4 | 利用者による拡張 | ADL でのカスタマイズ | コンセプト + メンバ関数 |
| 15.4.6 | 形状の追加 | ADL の `Bounds(s)` | `s.Bounds()` とコンセプト |
| **16.5** | **実装方式の選択** | **`#ifdef`** | **型による選択** |

**マクロで切り替えていた設計は、型で切り替える設計に置き換える。**

型はモジュール境界を越えます。マクロは越えません。だから、**切り替えたいものを型に載せる**のです。

### 16.5.2 明示的に選べるようにする ── いちばん単純な形

実は、すでにできています。16.2 で `MultiplyScalar` と `MultiplySimd` を `public` な `static` メンバ関数にしたからです。

```cpp
// 利用者側

// 通常は自動選択
const Matrix4x4 r1 = a * b;

// 決定論が必要な箇所では明示的にスカラー版
const Matrix4x4 r2 = Matrix4x4::MultiplyScalar(a, b);
```

これで、16.4.4 の「失われたもの2(1つのビルドでの共存)」が取り戻せました。**同じビルドの中で、呼ぶ関数を選べます。**

しかも、マクロ版よりも優れています。

- **どちらを使っているかがコードに書いてある。** マクロは、そのファイルがどう解析されたかを見ないと分かりません
- **同じ関数の中で両方使える。** 検証コードで結果を比較する、といったことができます
- **`kSimdAvailable` で条件を確認できる**

これが本書でいちばん単純な「型による切り替え」です。**関数を選べるようにするだけ**です。

### 16.5.3 ポリシーテンプレート ── 選択を型引数にする

「行列の積だけでなく、ライブラリ全体の方式を一括で切り替えたい」となると、もう一段必要です。

**タグ型**を用意して、テンプレート引数で渡します。

```cpp
// Core/Matrix.ixx(namespace gamemath の中)

// 実装方式を表すタグ
export struct ScalarPolicy {};
export struct SimdPolicy {};

// このビルドで既定となる方式
export using DefaultPolicy =
    std::conditional_t<kSimdAvailable, SimdPolicy, ScalarPolicy>;

export template <typename Policy = DefaultPolicy>
constexpr Matrix4x4 Multiply(const Matrix4x4& a, const Matrix4x4& b)
{
    if constexpr (std::same_as<Policy, SimdPolicy>) {
        if consteval {
            return Matrix4x4::MultiplyScalar(a, b);
        }
        else {
            return Matrix4x4::MultiplySimd(a, b);
        }
    }
    else {
        return Matrix4x4::MultiplyScalar(a, b);
    }
}
```

利用者はこう書けます。

```cpp
const Matrix4x4 r1 = gamemath::Multiply(a, b);                        // 既定
const Matrix4x4 r2 = gamemath::Multiply<gamemath::ScalarPolicy>(a, b); // 明示
const Matrix4x4 r3 = gamemath::Multiply<gamemath::SimdPolicy>(a, b);   // 明示
```

**タグ型もエイリアスも `export` が必要です。** 第8章 8.1.4 と 8.3.4 で確認したとおりです。利用者が型名を書くのだから、当然です。

そして、**このテンプレートはインターフェイスパーティションに定義しなければなりません。** 第8章 8.2 の結論です。利用者の翻訳単位で実体化されるからです。

`Policy` を関数の引数として渡す形(タグディスパッチ)もあります。

```cpp
export constexpr Matrix4x4 Multiply(const Matrix4x4& a, const Matrix4x4& b, ScalarPolicy);
export Matrix4x4 Multiply(const Matrix4x4& a, const Matrix4x4& b, SimdPolicy);
```

```cpp
const Matrix4x4 r = gamemath::Multiply(a, b, gamemath::ScalarPolicy{});
```

こちらはオーバーロード解決で選ばれるので、`if constexpr` が不要になります。関数が分かれるので、それぞれに最適な実装を書けます。

**`GameMath` では、16.5.2 の単純な形(関数を分けて公開する)にとどめます。** ポリシーテンプレートは、切り替えたい箇所が10か所20か所に増えてから導入すべきものです。行列の積1つのために導入するのは過剰です。

### 16.5.4 実行時ディスパッチ

もう1つの層があります。**CPU が対応しているかどうかは、実行時にしか分かりません。**

`kSimdAvailable` が判定しているのは「コンパイル時に SSE2 命令を出せるか」です。AVX2 や AVX-512 を使いたい場合は、話が変わります。実行するマシンが対応していなければ、命令が実行できずクラッシュします。

だから、実行時に問い合わせます。

```cpp
// 実装単位に置く

namespace gamemath {

bool HasAvx2()
{
    static const bool cached = []() {
        int info[4]{};
        __cpuid(info, 0);
        if (info[0] < 7) { return false; }
        __cpuidex(info, 7, 0);
        return (info[1] & (1 << 5)) != 0;      // AVX2 のビット
    }();
    return cached;
}

} // namespace gamemath
```

**これはモジュールとは無関係な話です。** ヘッダでもモジュールでも、書き方は同じです。実行時の分岐なので、マクロもテンプレートも関係ありません。

`__cpuid` は `<intrin.h>` にあるので、グローバルモジュールフラグメントに書きます。

`GameMath` では実装しません。SSE2 は x64 で必ず使えるので、実行時判定が不要な範囲にとどめています。

### 16.5.5 3つの層を整理する

SIMD の切り替えには、性質の違う3つの層があります。混同すると設計を誤ります。

| 層 | 決まるタイミング | 手段 | モジュールの影響 |
|---|---|---|---|
| **ターゲットが対応しているか** | コンパイル時 | `#if defined(_M_X64)` | ビルド単位で決まる。**モジュールでは全体で1つ** |
| **どの実装を呼ぶか** | コンパイル時 | **型 / 関数の選択** | 型は境界を越える。**問題なし** |
| **CPU が対応しているか** | 実行時 | `__cpuid` と分岐 | **影響なし** |

第1層はマクロの領分ですが、**ビルド全体で1つの値になります**(16.4.3)。ライブラリの作者が決めるものだと考えてください。

第2層が、この章の主題でした。**型で表現すれば、利用者が選べます。**

第3層は、モジュールとは無関係です。

**マクロで済ませていた設計を、この3層に分解する** ── これがモジュール移行における設計作業の実体です。

## 16.6 この章のまとめ

- `<immintrin.h>` は標準ライブラリではないので `import std;` では取り込めない。**グローバルモジュールフラグメント**に書く
- インライン展開させたいコードで使うなら、**インターフェイスパーティションの GMF** に書く。`.ifc` は重くなるが、それが代償
- 購買域に書くと `__m128` がモジュールに属し、利用者の `__m128` と別の型になる
- **`__m128` を公開シグネチャに出さない。** 型名が書けなくなり、アラインメント要求が ABI に漏れる
- `alignas(16)` は ABI を変えるので採らない。必要なら**別の型**として提示する
- SIMD 版とスカラー版で浮動小数点の結果がビット単位で一致しないことがある。決定論が必要なら要注意
- 組み込み関数は `constexpr` でないので、素直に書くと `constexpr` が失われる
- **`if consteval`** で、コンパイル時はスカラー版・実行時は SIMD 版という分岐ができる
- `if consteval`(評価の文脈)と `if constexpr`(コンパイル時の条件)は役割が違う
- **利用者がソースで `#define` してもモジュールには届かない。エラーにもならず、静かに無視される**
- 理由は2つ ── マクロは境界を越えない / **モジュールはビルド全体で1回しかコンパイルされない**
- ビルド設定(プロジェクトのプリプロセッサ定義)のマクロは効く。**切り替えの粒度が「翻訳単位ごと」から「ビルドごと」に変わった**
- 失われたもの ── ソースでの選択 / 1つのビルドでの共存 / 何が有効かをソースから読み取ること
- 得たもの ── **第1章 1.1.8 の ODR 違反が構造的に起こらなくなった**。同じ性質の裏表
- **マクロで切り替えていた設計は、型で切り替える設計に置き換える**
- いちばん単純な形は「関数を分けて公開する」。それで「1つのビルドでの共存」は取り戻せる
- ポリシーテンプレートやタグディスパッチは、切り替え箇所が増えてから
- SIMD の切り替えは3層に分かれる ── ターゲット対応(マクロ)/ 実装選択(型)/ CPU 対応(実行時)

## 次章に向けて

第4部の最後は、地味ですが実務では毎日使う話です。**エラー処理と診断**です。

- `assert` と `NDEBUG` は、モジュールでどう扱うのか(これもマクロの問題です)
- デバッグ用の出力ヘルパーを、どうやってモジュール内に閉じ込めるか
- そして **コンパイルエラーメッセージの読み方**

最後の項目が本題です。ここまでの章で何度もエラーを出してきましたが、モジュール特有のエラーには読み方のコツがあります。「モジュールが見つからない」「識別子が見つからない」「循環依存」── どれも原因の候補が決まっているので、順番に潰していけば必ず解決します。

第17章を読めば、付録B のエラーコード表がずっと使いやすくなります。
