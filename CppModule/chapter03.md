# 第3章 最初のモジュール

## この章について

第2章では、意味を説明しないまま `export module envcheck;` と書いてもらいました。この章では、あの1行が何だったのかを一語ずつ確かめていきます。

この章で覚える構文は、たった2つです。

```cpp
export module 名前;   // モジュールを定義する
import 名前;          // モジュールを取り込む
```

これだけです。第4章以降で扱う話 ── 名前空間、実装の分割、パーティション、テンプレート ── はすべて、この2つの上に積み上がっていきます。

進め方は本書全体の方針どおりです。

- 1つの節で1つのことだけを変える
- **各節の終わりで、必ずビルドが通る状態にする**
- 壊れた状態のまま次に進まない

途中に「実験」がいくつかあります。わざとエラーを起こす回もありますが、必ず元に戻してから次へ進みます。エラーメッセージを読む練習は、モジュールを扱ううえで避けて通れないので、早いうちに慣れておきましょう。

## 3.1 プロジェクトと `.ixx` ファイルを用意する

### 3.1.1 プロジェクトを作る

第2章と同じ手順で、新しいプロジェクトを作ります。

1. 「新しいプロジェクトの作成」→ **C++ の「空のプロジェクト」**
2. プロジェクト名は `HelloModule`
3. プロパティを開き、**[構成] を「すべての構成」、[プラットフォーム] を「すべてのプラットフォーム」** にする
4. **[C/C++] → [言語] → C++ 言語標準** を `/std:c++latest` に
5. 同じ画面の **ISO C++23 標準ライブラリ モジュールのビルド** を「はい」に

手順の詳細は 2.2 を参照してください。5番目は、この章ではまだ使いませんが、後で設定し忘れないよう今のうちに入れておきます。

### 3.1.2 まず、ビルドが通る状態を作る

いきなりモジュールを書き始めたくなりますが、その前に**出発点**を作ります。

「ソース ファイル」を右クリック → **[追加] → [新しい項目]** → 「C++ ファイル (.cpp)」を選び、`main.cpp` として追加します。

```cpp
// main.cpp
int main()
{
    return 0;
}
```

Ctrl + Shift + B でビルドしてください。通るはずです。何もしないプログラムですが、これが出発点です。

「動く状態から始めて、一歩ずつ変えていく」── 遠回りに見えますが、モジュールのように新しい仕組みを学ぶときは、これが結局いちばん速い道です。何かがおかしくなったとき、**直前の一歩だけを疑えばよい**からです。

### 3.1.3 `hello.ixx` を追加する

次に、モジュールのファイルを追加します。

「ソース ファイル」を右クリック → **[追加] → [新しい項目]** → **「C++ モジュール インターフェイス ユニット (.ixx)」** を選び、`hello.ixx` として追加します。

テンプレートが何か中身を書き込んでいたら、**すべて削除して空にしてください。**

> **この時点ではビルドしないでください**
>
> 空の `.ixx` をビルドするとエラーになります。モジュールインターフェイス単位には、モジュール宣言が必ず必要だからです。次の節ですぐに書きます。

なぜ拡張子が `.ixx` なのか ── これは 2.3.1 で確認しました。MSVC はこの拡張子のファイルを、自動的にモジュールインターフェイス単位(コンパイラオプションでいう `/interface`)として扱います。追加の設定は要りません。

## 3.2 `export module hello;` と書いてビルドする

### 3.2.1 1行だけ書く

`hello.ixx` に、次の1行だけを書いてください。

```cpp
// hello.ixx
export module hello;
```

以上です。関数も変数も何もありません。

ビルドしてください。**通ります。**

何も入っていないモジュールですが、これは正当な C++ です。空の名前空間や空のクラスが書けるのと同じことです。

### 3.2.2 この1行を分解する

たった3語ですが、それぞれに役割があります。

```
export   module   hello   ;
  ①        ②       ③     ④
```

**② `module hello`** ── これが**モジュール宣言**(module declaration)です。「このファイルは `hello` という名前のモジュールの一部である」と宣言しています。中心はここです。

**① `export`** ── モジュール宣言に `export` が付くと、そのファイルは**モジュールインターフェイス単位**(module interface unit)になります。「このモジュールの、外向きの顔を定義するファイル」という意味です。

`export` を付けない `module hello;` という書き方もあり、そちらは**モジュール実装単位**になります。第5章で扱います。

**③ `hello`** ── モジュール名です。次の項で詳しく見ます。

**④ `;`** ── セミコロンです。忘れがちなので念のため。これは宣言なので、必要です。

そして重要な決まりごとが1つ。

**モジュール宣言は、そのファイルの最初の宣言でなければなりません。**

より正確には、モジュール宣言より前に書けるのは、コメント・空行と、第6章で扱う「グローバルモジュールフラグメント」だけです。

### 3.2.3 【実験1】モジュール宣言の前に何か書いてみる

確かめてみましょう。`hello.ixx` を一時的にこうしてください。

```cpp
// hello.ixx
int x = 0;              // ← 追加

export module hello;
```

ビルドすると、エラーになります。「モジュール宣言はファイルの先頭になければならない」という趣旨のメッセージが出るはずです。

次に、こうしてみてください。

```cpp
// hello.ixx

// これはコメントです
// 空行もコメントも問題ありません

export module hello;
```

こちらは通ります。コメントと空行は宣言ではないので、いくら書いても構いません。ライセンス表記やファイルヘッダのコメントは、モジュール宣言の前に置けます。

**確認できたら、`hello.ixx` を 3.2.1 の1行だけの状態に戻してください。**

なお、`#include` を前に置きたい場合はどうするのか ── これには専用の仕組みが必要です。第6章で扱います。

### 3.2.4 モジュール名の決まりごと

モジュール名について、知っておくべきことを整理します。

**ドットが使える。ただし階層の意味はない**

```cpp
export module gamemath.vector;   // 有効なモジュール名
```

これは「`gamemath` の下の `vector`」ではありません。C++ の言語仕様上、`gamemath.vector` という**ひとかたまりの名前**です。ドットは名前の一部として許された文字にすぎず、`gamemath` というモジュールとの間に親子関係は一切ありません。

では何のために使うのか ── **人間が読んで理解しやすくするため**です。慣習として、関連するモジュールをドット区切りで命名します。これは規約であって、言語機能ではありません。第12章でモジュール構成を設計するとき、この点が効いてきます。

**ファイルパスとは無関係**

`gamemath.vector` というモジュールが `Vector3.ixx` に書かれていても、`src/math/v.ixx` に書かれていても構いません。言語仕様は、モジュール名とファイルの場所の対応を一切規定していません。

第2章 2.4.1 で、`SmokeTest.ixx` から `envcheck.ifc` が生成されるのを確認しました。あれがこの性質の現れです。

**名前空間とは別物**

これは非常に間違えやすいところです。

```cpp
export module hello;
```

と書いても、`hello` という名前空間はできません。この章のコードで定義する関数は、すべてグローバル名前空間に置かれます。

モジュール名と名前空間は、まったく独立した概念です。第4章 4.5 で、実際に両方を使いながら確認します。

**大文字と小文字は区別される**

`export module Hello;` と `import hello;` は一致しません。

**`std` で始まる名前は使えない**

`std`、`std2`、`std.compat` のように、最初の要素が `std`(または `std` に数字が続いたもの)であるモジュール名は、標準ライブラリのために予約されています。自分のモジュールに使ってはいけません。

### 3.2.5 生成物を確認する

第2章と同じように、`.ifc` ができているか見てみましょう。

プロジェクトのフォルダーをエクスプローラーで開き、`*.ifc` を検索します。

**`hello.ifc`** が見つかるはずです。中身は空同然ですが、ファイルとしては存在します。

ここまでで、モジュールを1つ作りました。まだ何も入っていませんが。

## 3.3 関数を1つ `export` する

### 3.3.1 まず、`export` なしで関数を書く

`hello.ixx` に関数を追加します。**まだ `export` は付けません。**

```cpp
// hello.ixx
export module hello;

int Add(int a, int b)
{
    return a + b;
}
```

ビルドしてください。通ります。

いま `Add` は、`hello` モジュールの内部にだけ存在する関数です。誰も使えませんが、文法的には何の問題もありません。

ここで押さえておきたいのは、**モジュールインターフェイス単位に関数の定義(本体)を書いてよい**ということです。ヘッダファイルなら、`inline` を付けなければ多重定義でリンクエラーになりました。モジュールではその心配がありません。テキストが複数の翻訳単位に貼り付けられることがないからです。

### 3.3.2 `export` を付ける

`Add` の前に `export` を付けます。

```cpp
// hello.ixx
export module hello;

export int Add(int a, int b)
{
    return a + b;
}
```

ビルドしてください。通ります。

これで `Add` は、`hello` モジュールを `import` した側から使えるようになりました。

同じ `export` という語が、2か所で違う意味を持っている点に注意してください。

| 書き方 | 意味 |
|---|---|
| `export module hello;` | このファイルはモジュール `hello` のインターフェイス単位である |
| `export int Add(...)` | この宣言をモジュールの外に公開する |

紛らわしいのですが、慣れてしまえば混乱しません。前者はファイルの先頭に1回だけ、後者は公開したいものの前に何度でも書きます。

### 3.3.3 `export` の書き方は2通りある

公開したいものが増えてくると、毎回 `export` を書くのが煩わしくなります。ブロックでまとめる書き方があります。

`hello.ixx` をこうしてください。

```cpp
// hello.ixx
export module hello;

export {

int Add(int a, int b)
{
    return a + b;
}

int Sub(int a, int b)
{
    return a - b;
}

}
```

ビルドが通ります。`export { ... }` の中の宣言は、すべて公開されます。

どちらの書き方でも結果は同じです。使い分けの目安はこうなります。

- 公開するものが少なく、非公開のものと混在する → 個別に `export` を付ける
- 公開するものが大半で、まとまっている → `export { }` でくくる

本書では、**個別に `export` を付ける書き方**を基本にします。1行を見ただけで公開・非公開が分かるほうが、読み手にとって安全だからです。`export { }` のブロックが長くなると、そのブロックの中にいるかどうかを目で追う必要が出てきます。

というわけで、`hello.ixx` を次の形に戻してください。**この形が、この章の基準になります。**

```cpp
// hello.ixx
export module hello;

export int Add(int a, int b)
{
    return a + b;
}

int Sub(int a, int b)
{
    return a - b;
}
```

`Add` は公開、`Sub` は非公開です。この非対称が 3.5 で効いてきます。

ビルドが通ることを確認してください。

### 3.3.4 `export` を書ける場所

`export` は、どこにでも書けるわけではありません。

**名前空間スコープの宣言にしか付けられません。** 関数の中は駄目です。

```cpp
export int Add(int a, int b)
{
    export int temp = a + b;   // ← エラー
    return temp;
}
```

これは考えてみれば当然で、関数の中のローカル変数を「外に公開する」ことに意味はありません。

同様に、クラスのメンバに個別に `export` を付けることもできません。クラスを `export` すれば、その `public` メンバは使えるようになります。第4章でクラスを扱うときに確認します。

## 3.4 `import hello;` して呼び出す

### 3.4.1 `main.cpp` から使ってみる

いよいよ使います。`main.cpp` をこう書き換えてください。

```cpp
// main.cpp
#include <cstdio>

import hello;

int main()
{
    std::printf("2 + 3 = %d\n", Add(2, 3));
    return 0;
}
```

ビルドして、Ctrl + F5 で実行します。

```
2 + 3 = 5
```

動きました。これで、モジュールを作って使う一往復が完成です。

### 3.4.2 `import hello;` を分解する

こちらは2語です。

```
import   hello   ;
  ①       ②      ③
```

`#include` と見比べてみましょう。

```cpp
#include "hello.h"     // ヘッダ
import hello;          // モジュール
```

違いが3つあります。

**引用符も山括弧もない。** `#include` は「ファイルを指定する」構文でした。`import` は「モジュール名を指定する」構文です。書くのはモジュール名だけです。

**パスも拡張子も書かない。** `import "src/hello.ixx";` のようには書けません。`hello` というモジュールがどのファイルにあり、その `.ifc` がどこに生成されているかは、**ビルドシステムが知っています**。私たちが書くのは名前だけです。

これは大きな違いです。ヘッダの世界では、インクルードパスの設定に苦しめられてきました。相対パスが深くなり、`-I` オプションが増え、プロジェクトを移動すると壊れる ── モジュールでは、少なくともソースコードの側にパスは現れません。

**先頭に `#` が付かない。** `import` はプリプロセッサディレクティブではなく、**C++ の宣言**です。だから末尾にセミコロンが要ります。

この「宣言である」という点が、第1章 1.3.1 で説明した性質のすべての根っこです。プリプロセッサの仕事ではないので、テキストは展開されず、マクロも越えてきません。

### 3.4.3 【実験2】`import` を2回書く

`main.cpp` をこうしてみてください。

```cpp
// main.cpp
#include <cstdio>

import hello;
import hello;   // ← 2回目

int main()
{
    std::printf("2 + 3 = %d\n", Add(2, 3));
    return 0;
}
```

ビルドしてください。**通ります。**

ヘッダファイルなら、インクルードガードがなければ「再定義」エラーになるところです。モジュールには、そもそも何も展開されないので、何回 `import` しても同じです。

**インクルードガードという概念が消滅しました。** `#pragma once` も要りません。書く場所がありません。

第1章 1.2 で「インクルードガードが守る範囲」を長々と論じましたが、その問題自体がなくなったわけです。

確認できたら、2行目の `import hello;` を消してください。

### 3.4.4 【実験3】書く順序を入れ替える

次はこうしてみます。

```cpp
// main.cpp
import hello;
#include <cstdio>   // ← 順序を入れ替えた

int main()
{
    std::printf("2 + 3 = %d\n", Add(2, 3));
    return 0;
}
```

ビルドが通ります。当たり前に見えますが、第1章 1.1.7 で見た `#include <Windows.h>` の順序問題を思い出してください。あれは「先に貼り付けられたテキストが、後のテキストに影響する」から起きていました。

`import` にはその性質がありません。順序を変えても結果は変わりません。

ただし、**普通のソースファイル(`.cpp`)での話です。** モジュールのファイル(`.ixx`)の中では、`import` を書ける場所に制約があります。第5章と第6章で扱います。

本書では、読みやすさのために `#include` を先、`import` を後に書く順序で統一します。順序に意味はありませんが、揃っているほうが読みやすいので。

**元の順序に戻してください。**

### 3.4.5 ビルド順序を確認する

出力ウィンドウをもう一度見てください。

```
1>hello.ixx
1>main.cpp
```

`hello.ixx` が先です。第2章 2.2.5 でも見ましたが、改めて意味を確認しておきます。

`main.cpp` をコンパイルするには、`hello.ifc` が存在していなければなりません。存在しなければ、`import hello;` の行で「モジュールが見つからない」となります。だからビルドシステムは、`hello.ixx` を先にコンパイルする必要があると判断します。

第1章 1.3.3 で「モジュールが持ち込む新しいコスト」として挙げた**ビルド順序の依存**が、この2行です。ヘッダの時代には、`.cpp` は互いに独立していて、どんな順序でも並列にコンパイルできました。

いまはファイルが2つしかないので何ということもありませんが、これが数百ファイルになり、モジュール同士が依存し合うようになると、話は変わってきます。第20章と第21章で扱います。

## 3.5 `export` を外すとどうなるか実験する

ここからがこの章の山場です。`export` の有無で何が変わるのかを、目で見て確認します。

### 3.5.1 非公開の関数を呼んでみる

3.3.3 で、`Sub` には `export` を付けませんでした。呼んでみましょう。

```cpp
// main.cpp
#include <cstdio>

import hello;

int main()
{
    std::printf("2 + 3 = %d\n", Add(2, 3));
    std::printf("5 - 3 = %d\n", Sub(5, 3));   // ← 追加
    return 0;
}
```

ビルドすると、エラーになります。

### 3.5.2 エラーメッセージを読む

出るエラーは、こういう趣旨のものです(正確な文言はバージョンによって異なります)。

```
error C3861: 'Sub': 識別子が見つかりませんでした
```

ここで立ち止まってください。**このメッセージは何と言っていますか。**

「`Sub` にはアクセスできません」ではありません。
「`Sub` は非公開です」でもありません。

**「`Sub` という名前が見つからない」**と言っています。

C++ の `private` メンバにアクセスしたときのエラーと比べてみてください。あちらは「アクセスできません」でした。コンパイラは `private` メンバの存在を知っていて、その上でアクセスを拒否していたのです。

モジュールは違います。`main.cpp` から見て、**`Sub` は存在しません。** 名前を解決しようとして、どこにも見つからなかった ── それがこのエラーの意味です。

第1章 1.1.6 で、`detail` 名前空間は「見ないでください」というお願いにすぎない、と書きました。モジュールでは、お願いではなくなりました。

### 3.5.3 【実験4】自分で宣言すればいいのでは?

疑い深い読者のために、もう一歩踏み込みます。

「名前が見つからないだけなら、こちらで宣言してやればいいのでは?」

やってみましょう。

```cpp
// main.cpp
#include <cstdio>

import hello;

int Sub(int a, int b);   // ← 自分で宣言する

int main()
{
    std::printf("2 + 3 = %d\n", Add(2, 3));
    std::printf("5 - 3 = %d\n", Sub(5, 3));
    return 0;
}
```

ビルドしてください。

**コンパイルは通ります。** そしてリンクで失敗します。

```
error LNK2019: 未解決の外部シンボル "int __cdecl Sub(int,int)" が関数 main で参照されました
```

これが決定的です。

私たちが `main.cpp` で宣言した `Sub` は、`hello` モジュールの中の `Sub` とは**別の関数**として扱われました。名前も引数も戻り値も同じなのに、別物です。だからリンカは定義を見つけられません。

### 3.5.4 モジュールリンケージ

いま起きたことには名前があります。

`hello` モジュールの中で `export` されていない `Sub` は、**モジュールリンケージ**(module linkage)を持ちます。

C++ には、これまで2種類のリンケージがありました。

| リンケージ | 意味 | 指定方法 |
|---|---|---|
| 外部リンケージ | 他の翻訳単位から参照できる | 既定 |
| 内部リンケージ | その翻訳単位の中だけ | `static`、無名名前空間 |

C++20 で、3つ目が加わりました。

| リンケージ | 意味 | 指定方法 |
|---|---|---|
| **モジュールリンケージ** | **同じモジュールの中だけ** | モジュール内で `export` しない |

`Sub` は「`hello` モジュールの中でだけ通用する名前」になりました。外から同じ名前を書いても、それは別の実体を指します。

この性質には、地味ですが重要な効果があります。**他のモジュールが同じ名前を使っても衝突しません。**

第4章以降、`gamemath.vector` と `gamemath.matrix` がそれぞれ独立に内部ヘルパーを持つようになりますが、名前を気にする必要はありません。ヘッダの世界では、`static` を付けるか無名名前空間に入れるかして自衛していた場面です。

### 3.5.5 では `.ifc` の中に `Sub` はあるのか

もう1つ、気になる点があるはずです。

`Sub` は `hello.ifc` の中に入っているのでしょうか。それとも、コンパイラが捨てているのでしょうか。

**入っています。**

理由は、第8章でテンプレートを扱うと痛感することになるのですが、ひとことで言えば「コンパイラが必要とすることがあるから」です。たとえば `Add` の中から `Sub` を呼んでいた場合、`main.cpp` 側で `Add` をインライン展開しようとすれば、`Sub` の本体が必要になります。

つまり、`.ifc` の中には「外から名前で参照できるもの」と「参照はできないが、コンパイラは知っているもの」が両方入っています。

この区別を、C++ の規格は**見える(visible)**と**到達可能(reachable)**という2つの言葉で説明します。

- `Add` は visible かつ reachable
- `Sub` は visible ではないが reachable

いまは「そういう区別があるらしい」で十分です。ただ、この区別を知らないと、後半で出会うコンパイルエラーがまったく読めなくなります。**第7章で最も丁寧に扱う章を用意してあります。**

### 3.5.6 元に戻す

実験は終わりです。`main.cpp` を元に戻してください。

```cpp
// main.cpp
#include <cstdio>

import hello;

int main()
{
    std::printf("2 + 3 = %d\n", Add(2, 3));
    return 0;
}
```

ビルドが通り、`2 + 3 = 5` と表示されることを確認してください。

## 3.6 ヘッダ版と比べてみる

最後に、同じものをヘッダファイルで書いて、並べてみます。第1章で理屈として説明したことを、動くコードで確認する節です。

### 3.6.1 ヘッダ版のプロジェクトを作る

同じソリューションに、もう1つプロジェクトを追加します。

1. ソリューション名を右クリック → **[追加] → [新しいプロジェクト]**
2. **C++ の「空のプロジェクト」**、名前は `HelloHeader`
3. 言語標準の設定は不要です(ヘッダ版なので)

ファイルを3つ追加します。

```cpp
// hello.h
#pragma once

int Add(int a, int b);
int Sub(int a, int b);
```

```cpp
// hello.cpp
#include "hello.h"

int Add(int a, int b)
{
    return a + b;
}

int Sub(int a, int b)
{
    return a - b;
}
```

```cpp
// main.cpp
#include <cstdio>
#include "hello.h"

int main()
{
    std::printf("2 + 3 = %d\n", Add(2, 3));
    return 0;
}
```

実行するには、**スタートアップ プロジェクト**を切り替える必要があります。ソリューションエクスプローラーで `HelloHeader` を右クリック → **[スタートアップ プロジェクトに設定]** を選んでください。

ビルドして実行し、`2 + 3 = 5` が出ることを確認します。

### 3.6.2 違い1 ── ファイルの数と、定義の置き場所

モジュール版は2ファイル、ヘッダ版は3ファイルになりました。

| | モジュール版 | ヘッダ版 |
|---|---|---|
| 宣言 | `hello.ixx` | `hello.h` |
| 定義 | `hello.ixx`(同じファイル) | `hello.cpp` |
| 利用側 | `main.cpp` | `main.cpp` |

ヘッダ版で宣言と定義を分けたのは、`inline` を付けずに定義をヘッダに書くと、複数の `.cpp` から `#include` されたときに多重定義になるからです。避けるには、定義を `.cpp` に置くか、`inline` を付けるかの二択でした。

モジュール版にはこの制約がありません。テキストが複数の翻訳単位に貼り付けられることがないので、定義をそのまま書けます。

ただし、**インターフェイス単位に定義を全部書くのが正しいわけではありません。** 定義を書けば、それを読むコストが `import` する側に乗ります。何をインターフェイスに置くかは設計判断です。第5章で、モジュールでも宣言と実装を分ける方法を扱います。

### 3.6.3 違い2 ── インクルードガードが要らない

ヘッダ版には `#pragma once` があります。モジュール版にはありません。

3.4.3 で確認したとおり、`import` を何回書いても問題は起きません。守るべきものがないのです。

### 3.6.4 【実験5】違い3 ── マクロは漏れるか

いちばん分かりやすい違いを、実際に確かめます。

**ヘッダ版でやってみる**

`hello.h` の先頭に、マクロを1つ足します。

```cpp
// hello.h
#pragma once

#define HELLO_VERSION 100   // ← 追加

int Add(int a, int b);
int Sub(int a, int b);
```

`main.cpp` でこれを使ってみます。

```cpp
// main.cpp
#include <cstdio>
#include "hello.h"

int main()
{
    std::printf("2 + 3 = %d\n", Add(2, 3));
    std::printf("version = %d\n", HELLO_VERSION);   // ← 追加
    return 0;
}
```

ビルドして実行してください。

```
2 + 3 = 5
version = 100
```

**漏れました。** `hello.h` の中で定義したマクロが、それを `#include` した `main.cpp` で使えています。

第1章 1.1.5 で見た `min` / `max` 問題と、まったく同じ仕組みです。便利に見えますが、これは「止められない」ということでもあります。

**モジュール版でやってみる**

今度は `HelloModule` プロジェクトです。スタートアップ プロジェクトを `HelloModule` に切り替えてください。

`hello.ixx` にマクロを足します。

```cpp
// hello.ixx
export module hello;

#define HELLO_VERSION 100   // ← 追加

export int Add(int a, int b)
{
    return a + b;
}

int Sub(int a, int b)
{
    return a - b;
}
```

`main.cpp` で使ってみます。

```cpp
// main.cpp
#include <cstdio>

import hello;

int main()
{
    std::printf("2 + 3 = %d\n", Add(2, 3));
    std::printf("version = %d\n", HELLO_VERSION);   // ← 追加
    return 0;
}
```

ビルドしてください。

```
error C2065: 'HELLO_VERSION': 定義されていない識別子です。
```

**漏れませんでした。**

`export` を付ければ漏れるのでしょうか。試すまでもなく、書けません。`export #define ...` という構文は存在しないからです。

**名前付きモジュールは、マクロをエクスポートしません。例外はありません。**

`.ifc` に入るのは C++ の宣言や定義であって、プリプロセッサの状態ではないからです。第1章 1.3.1 で説明したことが、そのまま現れています。

このことは、良い面と面倒な面の両方を持っています。

- 良い面: `min` / `max` 問題のような事故が原理的に起きなくなる
- 面倒な面: マクロで設定を切り替えるという既存の設計が、モジュール境界を越えられなくなる

後者は第16章で正面からぶつかります。SIMD の有効・無効をマクロで切り替えようとして行き詰まる回です。

**確認できたら、両方のプロジェクトから `HELLO_VERSION` の行を削除してください。**

### 3.6.5 違い4 ── 隠せるかどうか

ヘッダ版で、`Sub` を隠せるでしょうか。

`hello.h` から `Sub` の宣言を消せば、`main.cpp` からは呼べなくなります。しかしそれは「宣言を書かなかった」だけです。3.5.3 でやったように、利用者が自分で `int Sub(int, int);` と宣言すれば、今度は**リンクが通ってしまいます**。ヘッダ版の `Sub` は外部リンケージを持っているからです。

試してみてください。`hello.h` から `Sub` の行を消し、`main.cpp` に自分で宣言を書いて呼ぶ ── 動いてしまいます。

モジュール版では、3.5.3 で見たとおりリンクエラーになりました。この差がモジュールリンケージです。

「ヘッダに書かない」は隠蔽ではなく、単なる**非公開の申し合わせ**でした。モジュールで初めて、言語による保証になったのです。

### 3.6.6 比較表

| 観点 | ヘッダ版 | モジュール版 |
|---|---|---|
| 取り込み方 | テキストの貼り付け | 解析済みデータの読み込み |
| インクルードガード | 必要 | 概念が存在しない |
| 取り込む順序 | 影響することがある | 影響しない |
| マクロ | 漏れる | 漏れない |
| 定義の置き場所 | `.cpp` か `inline` | インターフェイスに書ける |
| 隠蔽 | 申し合わせ | 言語による保証(モジュールリンケージ) |
| ビルド順序 | 自由 | 依存関係の順に制約される |
| 解析回数 | 取り込んだ翻訳単位の数だけ | 1回 |

最後の2行だけがモジュールの「代償」で、それ以外は改善です。そして最後の1行が、多くの人がモジュールに期待する項目でもあります。

## 3.7 この章のまとめ

- `export module 名前;` は**モジュール宣言**。そのファイルをモジュールインターフェイス単位にする
- モジュール宣言は、そのファイルの最初の宣言でなければならない(コメントと空行は例外)
- モジュール名のドットに階層の意味はない。ファイルパスとも名前空間とも無関係
- `export` を付けた宣言だけが外から見える。`export { }` でまとめることもできる
- `export` は名前空間スコープの宣言にしか付けられない
- `import 名前;` はプリプロセッサディレクティブではなく**宣言**。だからセミコロンが要る。パスも拡張子も書かない
- `import` は何回書いても、どの順序で書いてもよい。インクルードガードは不要
- `export` されていない実体は**モジュールリンケージ**を持つ。外から見えないだけでなく、外で同じ名前を宣言しても別物になる
- ただし `.ifc` の中には存在する。「見える」と「到達可能」の区別は第7章で
- 名前付きモジュールはマクロをエクスポートしない。例外はない

## 次章に向けて

モジュールの骨格は、これで一通り触りました。`export module` と `import` の2つだけで、ここまで確認できたことになります。

第4章から、いよいよ `GameMath` の実装に入ります。最初のお題は `Vector3` です。まずヘッダファイルで書いたものを用意し、それを `.ixx` に移すところから始めます。

そして、この章で「別物です」と強調した**モジュール名と名前空間**を、実際に両方使いながら整理します。ここは本当に間違えやすいところなので、手を動かして確かめてもらいます。
