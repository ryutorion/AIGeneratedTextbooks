第 34 章

プロファイルの陳腐化
— ソース変更への追従と警告の読み方

プロファイルは、ある時点のソースコードに結び付いた記録です。コードを直せば、その記録は少しずつ現実と食い違っていきます。Clang はこれを検出できますが、警告の名前が計装方式によって違うという罠があります。

この章のゴール

  • プロファイルとソースがどう結び付いているかを理解する
  • 陳腐化したときに何が起きるかを実測で確認する
  • 二つの警告オプションを正しく使い分ける
  • プロファイルの運用方針を決める

34.1 関数ハッシュによる照合

第 29 章でプロファイルをテキスト形式にしたとき、こういう項目がありました。

_ZN6loglab10parse_lineESt17basic_string_viewIcSt11char_traitsIcEERNS_6RecordE
# Func Hash:
547674798947670709
# Num Counters:
25

Func Hash は、その関数の制御フロー構造から計算された値です。分岐が増えれば変わり、ループが増えても変わります。

-fprofile-use でコンパイルするとき、Clang は今まさにコンパイルしている関数のハッシュを計算し、プロファイル内のハッシュと突き合わせます。

照合結果Clang の動作
一致カウンタを使う
不一致その関数のプロファイルを捨てる。警告を出す
プロファイルに無いプロファイル無しとして扱う。警告は出ない

三行目が厄介です。関数を新しく追加した場合と、トレーニングで一度も通らなかった場合が区別できません。

34.2 実測 — 一行足すとどうなるか

Stats::add() に分岐を一つ追加してみます。

void Stats::add(const Record& r)
{
    ++accepted_;
    if (r.code > 100000) { hash_ ^= 1; }   // ← 追加した行
    ...

プロファイルはそのままで、-fprofile-use でコンパイルします。

warning: src/stats.cpp: function control flow change detected (hash mismatch)
  _ZN6loglab5Stats3addERKNS_6RecordE Hash = 238984482720105921
  up to 1983640 count discarded [-Wbackend-plugin]

読み取れることは三つあります。

  • 関数名が明示される（Stats::add）
  • 「制御フローの変化を検出した」——ハッシュの不一致
  • up to 1983640 count discarded——約 198 万回ぶんの記録が捨てられた

この関数は、以後プロファイル無しとして扱われます。第 32 章で見た「しきい値の絞り込み」も、この関数には適用されません。

34.3 警告オプションの罠

ここが本章で最も実用的な部分です。上の警告に付いている名前を見てください。

[-Wbackend-plugin]

-Wprofile-instr-out-of-date ではありません。実は、計装方式によって警告の出どころが違います。

計装方式使うオプション警告の名前メッセージ
IR レベル（本書の PGO）-fprofile-use=-Wbackend-plugin関数ごとに 1 件ずつ、ハッシュ値と捨てた回数つき
フロントエンド-fprofile-instr-use=-Wprofile-instr-out-of-dateファイル単位で要約

フロントエンド計装の場合はこうなります。

warning: profile data may be out of date: of 7 functions, 1 has mismatched data
  that will be ignored [-Wprofile-instr-out-of-date]
「警告を有効にしたのに出ない」の原因

PGO の解説記事の多くは -Wprofile-instr-out-of-date を紹介しています。しかし本書の方式（IR レベル計装）では、そのオプションを付けても何も変わりません。すでに -Wbackend-plugin として既定で有効だからです。

逆に言えば、IR レベル計装では黙って無視されることはありません。ビルドログを見れば必ず警告が出ています。埋もれて気づかないだけです。

34.3.1 エラーにする

CI で確実に気づきたいなら、警告をエラーに昇格させます。

/clang:-Werror=backend-plugin

実際にビルドすると、こうなります。

error: src/stats.cpp: function control flow change detected (hash mismatch)
  _ZN6loglab5Stats3addERKNS_6RecordE Hash = 238984482720105921
  up to 1983640 count discarded [-Werror,-Wbackend-plugin]

逆に、意図的に古いプロファイルを使い続けたい場面では黙らせられます。

/clang:-Wno-backend-plugin
-Wno-backend-plugin は乱暴です

この警告グループには、プロファイル以外のバックエンドからの診断も含まれます。まとめて黙らせることになるので、常用は勧められません。「プロファイルの陳腐化は承知のうえで、いまはビルドを通したい」という一時的な用途に留めてください。

34.4 どこまでの変更が許されるか

ハッシュは制御フローの構造から計算されるので、変更の種類によって影響が違います。

変更ハッシュ影響
コメントの追加・変更変わらないなし
変数名の変更変わらないなし
式の中身の変更（分岐を増やさない）変わらないなし
if / ループ / && / ?: の追加変わるその関数のプロファイルが失われる
関数の分割両方変わる両方失われる
関数名の変更照合できないプロファイル無し扱い（警告も出ない）
他の関数の変更—この関数には影響しない
影響は関数単位に閉じます

一つの関数を書き換えても、失われるのはその関数のプロファイルだけです。ファイル全体、ましてプロジェクト全体が無効になるわけではありません。

つまりプロファイルは、ゆっくり劣化していきます。ある日突然使えなくなるのではなく、変更した関数から順に効果を失っていく。これが運用を考えるうえでの基本的な性質です。

34.5 運用をどうするか

34.5.1 プロファイルをどこに置くか

方針利点欠点
毎回トレーニングから作る常に最新。陳腐化しないビルドに時間がかかる。トレーニング環境が必要
リポジトリにコミットする誰でも同じ結果になる。ビルドが速いバイナリファイルが履歴に残る。更新の運用が要る
成果物置き場に保管するリポジトリが汚れない取得の仕組みが要る

中規模までのプロジェクトなら、二番目が扱いやすい選択です。第 29 章の -sparse でサイズを削っておくと、履歴への負担が減ります。

34.5.2 いつ取り直すか

「毎回」が理想ですが、コストと釣り合わないことも多いはずです。実用的な判断材料を挙げます。

  • 警告の件数を数える。 ビルドログの hash mismatch の行を数え、一定数を超えたら取り直す
  • 捨てられたカウント数を見る。 警告には up to N count discarded が出ます。この合計が大きければ、影響も大きい
  • ホットな関数が含まれているかを見る。第 30 章の --topn で上位に来ていた関数が陳腐化していたら、優先度は高い
:: 陳腐化した関数の数を数える
msbuild ... 2>&1 | findstr /C:"hash mismatch" | find /c /v ""
CI に組み込むなら

第 41 章で扱いますが、方針だけ先に書いておきます。

  • 通常のビルドでは、保管してあるプロファイルを使う
  • 陳腐化した関数の数が閾値を超えたら、警告として報告する
  • 定期的（週次など）にトレーニングを実行してプロファイルを更新する
  • リリース前には必ず取り直す

34.6 プロファイルに無い関数

34.1 節の表の三行目、「プロファイルに無い」ケースです。警告が出ないため、気づきにくい問題です。

原因は二つあります。

原因望ましいか対処
関数を新しく追加した—次のトレーニングで拾われる
トレーニングでその関数を一度も通らなかった場合による本当にコールドならそれで正しい。ホットなはずならトレーニングの不備

後者を検出したいなら、第 30 章の方法が使えます。llvm-profdata show --topn の顔ぶれと、第 12・13 章のプロファイラの結果を突き合わせる。プロファイラで上位に出ている関数がプロファイルに無ければ、トレーニングが本番を代表していません。

34.7 ハンズオン

  1. src\stats.cpp の Stats::add() に if を一行追加する
  2. -fprofile-use のままビルドし、hash mismatch の警告が出ることを確認する
  3. 警告に含まれる「捨てられたカウント数」を読む
  4. /clang:-Werror=backend-plugin を付けて、エラーになることを確認する
  5. コメントだけを追加した場合は警告が出ないことを確認する
  6. 追加した行を元に戻し、警告が消えることを確認する
  7. （余裕があれば）陳腐化したまま性能を測り、効果がどれだけ落ちるかを見る

34.8 まとめ

  • プロファイルは関数ごとの制御フローのハッシュでソースと結び付いている
  • ハッシュが変わると、その関数のプロファイルだけが捨てられる。影響は関数単位に閉じる
  • 実測では、if を一行足しただけで約 198 万回ぶんの記録が破棄された
  • IR レベル計装の警告は -Wbackend-plugin。-Wprofile-instr-out-of-date はフロントエンド計装用
  • CI では /clang:-Werror=backend-plugin で確実に気づけるようにする
  • 制御フローを変えない編集（コメント、変数名、式の中身）ではハッシュは変わらない
  • プロファイルはゆっくり劣化する。警告の件数と捨てられたカウント数で取り直しを判断する
  • 「プロファイルに無い関数」は警告が出ない。トレーニングの不備を疑う手段は第 30 章の照合

第 5 部を終えて

PGO について、次のことが分かりました。

  • 三段階の手順——計装ビルド、トレーニング、最適化ビルド（第 26・27・31 章）
  • 計装ビルドは .text が 4.2 倍、実行時間が 1.9 倍になる（第 26 章）
  • トレーニングの品質がすべてを決める。不適切なトレーニングは性能を悪化させる（第 28 章）
  • プロファイルは llvm-profdata で読める。トレーニングの妥当性を事前に判断できる（第 30 章）
  • 実行時間への効果は環境に依存した。環境 A で 6.5〜9.0% 短縮、環境 B ではノイズ床以下（第 31 章）
  • その正体は、しきい値が 3 分の 1 に絞られ、インライン化が減ったこと（第 32 章）
  • atomic なカウンタは高くつく。既定で十分（第 33 章）
  • プロファイルは関数単位でゆっくり劣化する（第 34 章）

第 4 部で LTO の判断がほとんど変わらず、第 5 部で PGO が 600 以上の判断を変えた——同じ題材、同じ手順で。この対比が示しているのは、最適化には「効く場所」があり、それはコードの性質で決まるということです。そして第 31 章では、その判断の変化が実行時間に現れるかどうかがハードウェア次第であることも見ました。手当たり次第にオプションを足すのではなく、どこに効くのかを理解し、自分の環境で測って選ぶ。第 1 章から一貫して主張してきたことが、実測として形になりました。

ただし、PGO にもまだ届いていない領域があります。第 32 章で見たとおり、プロファイルは「この関数のこの分岐は 0.348%」という情報を持っていますが、「どこから呼ばれたときに 0.348% なのか」は区別していません。インライン展開された後の姿では、呼び出し元ごとに違う偏りを持つはずのコードが、平均された一つのプロファイルで最適化されています。

その最後の隙間を埋めるのが、次の第 6 部です。

次章から第 6 部（CSPGO）です。 まず、いま述べた「文脈の欠落」がどういう問題なのかを具体的に見ます。そのうえで、プロファイルをもう一周取る二段構えの手順を扱います。第 4 部で見た lld-link の /lto-cs-profile-generate というオプションが、そこで登場します。
