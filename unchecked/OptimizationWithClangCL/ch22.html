第 22 章

静的ライブラリ・DLL と LTO
— ビットコードアーカイブとエクスポート

実際のプロジェクトは、単一の .exe ではありません。自前の静的ライブラリがあり、サードパーティの .lib があり、DLL に分かれています。LTO はその境界をどこまで越えられるのか。ここが導入時の最大の関門です。

この章のゴール

  • ビットコードを含む .lib を作る
  • LTO が静的ライブラリの境界を越えることを確認する
  • ビットコードとネイティブの混在がどうなるかを知る
  • DLL があると何ができなくなるかを理解する

22.1 静的ライブラリ — 境界は越えられる

結論から言うと、静的ライブラリの境界は問題になりません。.lib の中身がビットコードであれば、LTO は普通に働きます。

22.1.1 ビットコードの .lib を作る

llvm-lib を使います。第 3 章で確認したとおり、ClangCL ツールセットは既定でライブラリアンにも LLVM のもの（UseLlvmLib）を使うので、Visual Studio でスタティックライブラリのプロジェクトを作れば自動的にこうなります。

:: コンパイル（ビットコードの .obj ができる）
clang-cl /c /O2 /clang:-flto=thin lib.cpp

:: アーカイブ
llvm-lib /out:mylib.lib lib.obj

中身を確認できます。

llvm-lib /list mylib.lib
  lib.obj

22.1.2 越えられることを確認する

第 17 章の scale の例を、ライブラリ経由にして測りました。

構成call 命令の数リンク時リマーク
ネイティブの .lib（LTO なし）1—
ビットコードの .lib（LTO あり）0'?scale@@YAHHH_N@Z' inlined into 'mainCRTStartup'

実測の一例

.lib に格納されていても、ビットコードならリンク時に取り出されて最適化の対象になります。翻訳単位の壁と同じく、ライブラリの壁も消えます。

自社ライブラリには LTO を入れる価値があります

「アプリ本体は最適化しているが、共通ライブラリは別チームが作った .lib なので手が出ない」という状況はよくあります。そのライブラリを LTO 対応でビルドしてもらえれば、アプリ側から見た壁が消えます。効果が大きいのは、小さな関数を大量に提供するライブラリ（数学ライブラリ、コンテナ、文字列処理など）です。

22.2 ビットコードとネイティブの混在

実際のプロジェクトでは、すべてを LTO 対応にできるとは限りません。サードパーティの .lib はネイティブのままでしょうし、古いプロジェクトを段階的に移行することもあります。

混在は問題なく動きます。 lld-link は、入力ファイルごとに中身を判別します。

入力扱い
ビットコードの .obj / .libLTO の対象になる。互いにインライン化できる
ネイティブの .obj / .libそのままリンクされる。壁は残る

つまり LTO は「LTO 対応にした部分どうし」の間でだけ働きます。段階的な導入が可能ということでもあり、逆に「一部だけ LTO にしても効果が限定される」ということでもあります。

効果が出ないときは、まず範囲を確認

「LTO を有効にしたのに効果がない」というとき、ホットな処理がネイティブのライブラリ側にある、という可能性があります。.obj や .lib のどれがビットコードになっているかを、第 17 章の方法（llvm-readobj）で確認してください。

22.2.1 /wholearchive

リンカは通常、.lib から「必要なオブジェクトだけ」を取り出します。次のオプションで、すべてを取り込ませることができます。

/wholearchive:mylib.lib     <- この .lib のすべてを取り込む
/wholearchive               <- すべての .lib のすべてを取り込む

LTO の文脈では、取り込まれなかったオブジェクトは最適化の視野に入らないので、これを使うと視野が広がることがあります。ただし使われないコードまで実行ファイルに入るため、サイズは増えます。静的初期化に副作用があるライブラリで必要になる場合が主な用途で、LTO の効果を上げる目的で常用するものではありません。

22.3 DLL — ここからが本題

DLL は、LTO にとって根本的な制約になります。理由は単純で、DLL の境界の向こう側は、リンク時にも見えないからです。

22.3.1 エクスポートされた関数に起きること

__declspec(dllexport) を付けた関数は、外部から呼ばれる可能性があります。すると LTO は次のことができなくなります。

できないこと理由
削除する誰も呼んでいないように見えても、外から呼ばれるかもしれない
内部化するシンボルとして公開し続ける必要がある
引数の受け渡し方を変える呼び出し規約を守らなければならない
この関数を通じたデバーチャライズ外部から派生クラスが来る可能性がある（第 21 章）

関数の中身は最適化されますし、その関数が内部で呼んでいる関数のインライン化も行われます。制約がかかるのは「その関数自身をどう扱うか」の部分です。

22.3.2 実務上の指針

エクスポートは必要最小限に

これは LTO に限らない一般的な設計指針ですが、LTO を使うと効果がはっきりします。__declspec(dllexport) を付ける対象を絞れば絞るほど、LTO が自由に動ける範囲が広がります。

逆に、ヘッダ全体に dllexport マクロを撒いているようなコードでは、LTO の効果は大きく削がれます。

DLL 構成での現実的な選択肢は次のようになります。

方針内容
DLL ごとに LTO をかける各 DLL の内部は最適化される。境界は残る。最も現実的
ホットな部分を DLL から出す性能が重要なコードを実行ファイル側か静的ライブラリに移す
DLL をやめて静的リンクにする効果は最大だが、配布やビルド時間に影響する。判断は LTO 以外の要因が大きい

22.4 LogLab で確認する

LogLab は単一の実行ファイルなので DLL の問題は起きませんが、静的ライブラリの構成は試せます。

  1. ソリューションに「スタティック ライブラリ」プロジェクト LogLabCore を追加する
  2. プラットフォームツールセットを LLVM (clang-cl)、C++ 標準を C++23 にする
  3. tokenizer.cpp、filter.cpp、stats.cpp、generator.cpp をそちらに移す
  4. 両方のプロジェクトに /clang:-flto を設定する
  5. ClangOptLab から LogLabCore を参照する
  6. ビルドして checksum が変わらないことを確認する
  7. リンク時リマーク（第 20 章）を取り、parse_line が main にインライン化されているかを確認する

ライブラリに分けても結果が変わらなければ、「LTO はライブラリの壁を越える」ことを自分の手で確認したことになります。

片方だけ LTO にしてみる

余裕があれば、LogLabCore の /clang:-flto だけを外してビルドしてみてください。.lib がネイティブになり、parse_line のインライン化が消えるはずです。「壁がどこにあるか」が体感できます。

22.5 まとめ

  • 静的ライブラリの境界は越えられる。llvm-lib でビットコードの .lib を作れば、LTO はその中身も最適化する
  • 実測では、ライブラリ経由の呼び出しが 1 → 0 になった
  • ビットコードとネイティブの .obj / .lib は混在できる。LTO 対応にした部分どうしの間だけ壁が消える
  • 効果が出ないときは、ホットな処理がネイティブ側にないかを確認する
  • DLL の境界は越えられない。 エクスポートされた関数は削除・内部化・デバーチャライズの対象外になる
  • エクスポートを最小限に絞ることが、そのまま LTO の効果につながる
  • DLL 構成では「各 DLL の内部を LTO で最適化する」が現実的な落とし所

次章では、LTO の代償を正面から扱います。ビルド時間、メモリ、増分ビルド、デバッグのしにくさ。そして「LTO を有効にしたらビルドが通らなくなった」「動作がおかしくなった」というときの切り分け方。導入を判断するために必要な材料を揃えます。
