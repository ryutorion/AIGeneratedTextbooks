第 16 章

LTO とは何か
— 翻訳単位の壁を越える

ここから第 4 部です。第 9 章で見た function definition is not available というリマーク——「定義が見えないのでインライン化できない」という報告を覚えているでしょうか。LTO はこの壁を壊す仕組みです。まずは何が起きているのかを理解します。

この章のゴール

  • 翻訳単位の壁が何を妨げているのかを整理する
  • LTO を有効にすると .obj の中身が変わることを知る
  • 最適化がいつ走るのかを理解する
  • Full LTO と ThinLTO の違いの見取り図を持つ

16.1 壁の正体

第 11 章で使った例をもう一度見ます。

// lib.cpp
int scale(int v, int factor, bool clamp) {
    int r = v * factor;
    if (clamp) { if (r > 1000) r = 1000; if (r < -1000) r = -1000; }
    return r;
}

// app.cpp
int scale(int v, int factor, bool clamp);   // 宣言だけ
int total = 0;
for (int i = 0; i < 64; ++i) total += scale(seed + i, 2, false);

app.cpp をコンパイルしているとき、コンパイラが scale について知っているのは宣言だけです。引数を三つ取って int を返す、それだけ。中身が分からないので、次のことができません。

  • clamp = false が定数だと分かっても、それを活かせない
  • 展開して if を消すことができない
  • この関数がメモリに触るのか、例外を投げるのか、いつ戻るのかも分からない

結果、app.obj には call 命令が残ります。lib.obj の側では scale が独立した関数として最適化されて存在していますが、二つの .obj は互いを知らないまま完成します。

リンカは、この二つを機械語のまま繋ぐだけです。 最適化の機会は、リンクの時点ではとうに失われています。

16.2 LTO の考え方 — 最適化を後回しにする

LTO（Link Time Optimization）の発想は単純です。コンパイル時に機械語まで作ってしまうのをやめる。

コンパイラは .obj に機械語ではなく LLVM IR（第 7 章で見たあの中間表現）を書き込みます。リンカはそれらを集め、プログラム全体が揃った状態で最適化パイプラインを走らせ、そのあとで機械語を生成します。

16.3 .obj は本当に変わる

これは概念的な説明ではありません。実際にファイルの種類が変わります。

:: 通常のビルド
clang-cl /c /O2 lib.cpp
  → lib.obj : Intel amd64 COFF object file, 6 sections, 1st section name ".text"

:: LTO を有効にしたビルド
clang-cl /c /O2 /clang:-flto=thin lib.cpp
  → lib.obj : LLVM IR bitcode

COFF のオブジェクトファイルですらなくなっています。オブジェクトファイルを読むツールに渡すと拒否されます。

llvm-readobj --file-headers lib.obj
llvm-readobj: warning: 'lib.obj': bitcode files are not supported
だから link.exe ではリンクできません

MSVC のリンカは COFF しか理解しません。ビットコードが入った .obj を渡してもオブジェクトファイルとして解釈できず、リンクは失敗します。第 3 章で「UseLldLink を true のままにしておいてください」と念を押したのは、この章のためでした。

LTO を使うなら lld-link が必須です。

16.4 LTO で何ができるようになるか

「翻訳単位をまたいでインライン化できる」が代表的な効果ですが、それだけではありません。プログラム全体が見えることで、次の四つが可能になります。

できること内容本書での扱い
翻訳単位をまたぐインライン化call が消え、第 11 章で見た最適化の連鎖が始まる第 20 章で確認
関数属性の伝播第 7 章で見た memory(none) や willreturn といった性質が、翻訳単位を越えて伝わる。インライン化されなくても効く第 20 章
未使用コードの削除どこからも呼ばれない関数、使われないグローバル変数を消せる第 20 章
仮想関数の解決「この基底クラスの実装は全部でこれだけ」と結論できる第 21 章
二番目は見落とされがちです

インライン化されなくても、「この関数はメモリに触らない」と分かれば、呼び出しの前後でレジスタを退避する必要が減り、呼び出しをループの外に出せる場合もあります。LTO の効果は call が消えることだけではありません。 第 20 章で call の数を数えるとき、この点を忘れないでください。

16.5 Full LTO と ThinLTO

LLVM の LTO には二つの方式があります。詳しくは第 18 章で扱いますが、見取り図だけ先に示します。

Full LTO（-flto）ThinLTO（-flto=thin）
やり方全ビットコードを一つの巨大なモジュールに統合してから最適化各モジュールの要約を作り、必要なものだけを取り込んで並列に最適化
最適化の深さ深い。全体を見渡せるやや浅い。取り込む範囲を絞るため
リンク時間長い。並列化しにくい短い。コア数に応じて並列化できる
メモリ大量に必要。大規模プロジェクトでは破綻することがある抑えられる
キャッシュなしあり。再リンクが速い

実務ではまず ThinLTO を選びます。 Full LTO は小〜中規模のプロジェクトか、最後の一押しを求めるときの選択肢です。本書では第 17 章で Full LTO、第 19 章で ThinLTO を扱い、第 20 章で両方の効果を比較します。

16.6 最適化はいつ走るのか

LTO を有効にしても、コンパイル時にまったく何もしないわけではありません。

段階行われること
コンパイル時構文解析、意味解析、そして翻訳単位内で完結する最適化の一部。結果を IR のまま .obj に書き出す
リンク時IR を集め、関数間の最適化を含む本番のパイプラインを走らせ、機械語を生成する

この分担には実務上の意味があります。第 10 章で作った最適化レコードは、コンパイル時のものです。 LTO を有効にすると、面白い部分はリンク時に移動してしまうため、コンパイル時のレコードを見ても変化がほとんど現れません。

実際、LogLab で確認すると次のようになります。

コンパイル時レコードの件数（全 5 ファイル合計）
  LTO なし   : 2223 件
  ThinLTO    : 1460 件
  Full LTO   : 1672 件

件数が減っています。コンパイル時のパイプラインが途中で打ち切られているためです。「LTO を有効にしたらレコードが減った、効果が無いのでは」と誤解しないでください。リンク時のリマークを別に取る必要があります。 その方法は第 20 章で扱います。

16.7 まとめ

  • 翻訳単位の壁とは、「他の .cpp の関数の中身が見えない」という制約である
  • LTO は .obj に機械語ではなく LLVM IR（ビットコード）を書き、最適化と機械語生成をリンク時に行う
  • .obj は COFF ですらなくなる。lld-link が必須で、link.exe ではリンクできない
  • LTO が可能にするのは、TU をまたぐインライン化・関数属性の伝播・未使用コードの削除・仮想関数の解決の四つ
  • Full LTO は深いが重い、ThinLTO は速く並列化できる。実務ではまず ThinLTO
  • LTO を有効にするとコンパイル時のレコードは減る。評価はリンク時のリマークで行う

次章では、まず Full LTO を実際に有効にします。設定はオプション一つですが、確認すべきことがいくつかあります。.obj が本当にビットコードになったか、リンカは lld-link か、そしてチェックサムは変わっていないか。最小構成の例で、call 命令が実際に消えるところまで確認します。
