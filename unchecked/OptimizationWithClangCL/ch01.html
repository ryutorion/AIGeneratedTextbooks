第 1 章

本書の狙いと進め方
— 「勘」ではなく「計測」で最適化する

最適化オプションは、付ければ付けるほど速くなるものではありません。本書は「効果を確認する手段」を先に用意し、そのうえで LTO・PGO・CSPGO を一つずつ導入していきます。この章では、その進め方と本書の前提を確認します。

この章のゴール

  • 本書が扱うもの／扱わないものを把握する
  • LTO・PGO・CSPGO の関係を一枚の図で理解する
  • MSVC ではなく ClangCL を使う理由を納得する
  • 以降の章で前提とする環境と作法を確認する

1.1 最適化はどこで失敗するか

C++ のプロジェクトで「速くしてほしい」と言われたとき、まず何をするでしょうか。多くの場合、次のような手が打たれます。リリース構成が /O2 になっているか確認する。インライン展開の設定を上げてみる。どこかで見た最適化オプションを追加してみる。ビルドして、実行して、「なんとなく速くなった気がする」ので、そのままコミットする。

この流れには三つの罠があります。

第一に、測っていない。 実行時間は、同じバイナリを同じマシンで動かしても数パーセントは平気で揺れます。CPU の周波数制御、ページフォルト、他のプロセス、ディスクキャッシュ。1 回ずつ実行して比べた「速くなった気がする」は、その揺らぎと区別がついていません。

第二に、測る場所が違う。 小さなループだけを切り出したベンチマークは、本番のコードとはまったく別の挙動をします。命令キャッシュの状況も、分岐予測器の状態も、呼び出しの深さも違うからです。マイクロベンチで 3 倍速くなった関数が、アプリ全体では 0.2% しか効かない、というのはごく普通に起きます。

第三に、効いた理由が分からない。 これがいちばん厄介です。理由が分からない改善は、再現できず、他のコードに横展開もできず、リファクタリングで簡単に失われます。半年後にそのオプションを見た人は、外していいのかどうかを判断できません。

本書の立場

最適化オプションは「効くらしいから入れる」ものではなく、「入れた結果こう変わった、と説明できる」ものです。本書では、あるオプションを紹介するたびに、その効果を確認する手段とセットで扱います。確認できない改善は、本書では改善として扱いません。

そのため本書は、第 2 部と第 3 部を丸ごと「観察と計測の準備」に充てています。LTO の話が始まるのは第 16 章です。遠回りに見えるかもしれませんが、この準備がないまま第 4 部以降に進むと、結局「なんとなく速くなった気がする」に戻ってしまいます。

1.2 本書が扱う三つの武器

コンパイラがどこまで賢く最適化できるかは、突き詰めるとコンパイラがどれだけの情報を持っているかで決まります。本書で扱う三つの技術は、いずれも「コンパイラに渡す情報を増やす」ための仕組みです。

1.2.1 LTO — 翻訳単位の壁を越える

C++ のビルドは .cpp ごとに独立して行われます。a.cpp をコンパイルしているとき、コンパイラは b.cpp に書かれた関数の中身を知りません。ヘッダに書かれた関数ならインライン化できますが、.cpp に実装がある関数は「呼び出す」しかない。これが翻訳単位の壁です。

LTO（Link Time Optimization）は、コンパイル時に機械語ではなく LLVM の中間表現（IR）を .obj に埋め込んでおき、リンク時にそれらをまとめて最適化します。壁が消えるので、翻訳単位をまたいだインライン化ができ、どこからも呼ばれていない関数を削除でき、仮想関数の呼び出し先を一つに絞れる場合もあります。

1.2.2 PGO — 実行時の事実を教える

次のようなコードを考えてみます。

if (auto* p = cache.find(key)) {
    return decode(p);          // A
} else {
    return load_from_disk(key); // B
}

A と B のどちらが「よく通る道」なのか、ソースコードだけを見て判断することはできません。キャッシュのヒット率が 99% ならほとんど A ですし、初回起動時なら B ばかりです。コンパイラは静的なヒューリスティクス（たとえば「ループは回りやすい」「nullptr チェックは成立しにくい」）で推測しますが、それはあくまで推測です。

PGO（Profile-Guided Optimization）は、この推測を実測に置き換えます。まず計測用の情報を埋め込んだバイナリ（計装ビルド）を作り、代表的なワークロードで走らせて「どの分岐が何回成立したか」を記録します。その記録を読ませて本番用のビルドを行うと、コンパイラはよく通る道を優先してコードを配置し、めったに呼ばれない関数はインライン化の対象から外します。

1.2.3 CSPGO — 文脈を区別する

PGO のプロファイルには弱点があります。ある関数 f() の中の分岐が「70% は成立した」と記録されていても、その内訳が「呼び出し元 X からは常に成立、呼び出し元 Y からは常に不成立」なのかは分かりません。しかも f() がインライン展開されると、展開先ごとに本当は違う偏りを持つはずのコードが、平均された一つのプロファイルで最適化されてしまいます。

CSPGO（Context-Sensitive PGO）は、インライン展開が済んだ後の姿でもう一度プロファイルを取り、呼び出し文脈ごとに区別された情報を得ます。手順が二段構えになるぶんコストは上がりますが、PGO が取りこぼしていた部分に届きます。詳しくは第 6 部で扱います。

三つの関係

LTO・PGO・CSPGO は択一ではなく、重ねて使うものです。実務では「ThinLTO + PGO」がまず基本形になり、そのうえで CSPGO を足すかどうかを検討する、という順番になります。組み合わせ方と適用順序は第 38 章で扱います。

1.3 なぜ MSVC ではなく ClangCL なのか

ここまで読んで、「それは MSVC にもある」と思われたかもしれません。そのとおりです。MSVC にも LTO 相当の /GL + /LTCG があり、PGO 相当の /GENPROFILE + /USEPROFILE があります。

それでも本書が ClangCL を選ぶ理由は、速いからではありません。中で何が起きたかを見せてくれるからです。

やりたいことMSVCClang / ClangCL
翻訳単位をまたぐ最適化/GL + /LTCG-flto / -flto=thin
プロファイルに基づく最適化/GENPROFILE + /USEPROFILE-fprofile-generate + -fprofile-use
文脈を考慮した二段階 PGO—-fcs-profile-generate（CSPGO）
インライン化されたか／されなかったかの理由限定的-Rpass / -Rpass-missed / -Rpass-analysis
最適化の判断を機械可読な形で保存—-fsave-optimization-record（YAML）
プロファイルそのものを人間が読む限定的llvm-profdata show / llvm-cov

下の三行が本書にとって決定的です。「なぜこの関数はインライン化されなかったのか」をコンパイラ自身に説明させられること、そして「プロファイルに何が記録されているのか」をテキストとして読めること。この二つがあるおかげで、本書は「オプションを入れたら速くなりました」で終わらずに済みます。

MSVC を否定するものではありません

本書は ClangCL を「学習と分析のための道具」として使います。ここで身につけた見方 — どこがホットで、なぜインライン化され、プロファイルが何を語っているか — は、MSVC に戻ったときにもそのまま役立ちます。実際、最終的に MSVC でビルドする製品に対して、調査だけ ClangCL で行うという使い方も十分ありえます。

1.4 本書の前提

項目本書での前提
IDEVisual Studio 2026（Community 版で構いません）
ツールセットLLVM (clang-cl) — 通称 ClangCL
言語標準C++23
C++ モジュール使いません（従来のヘッダ + .cpp 構成）
ターゲットx64 / Windows
ビルド構成MSBuild（.vcxproj）が主軸、CMake は第 40 章で補足
計測ツールllvm-profdata / llvm-cov、PIX for Windows、ETW + Windows Performance Analyzer
モジュールを使わない理由

C++20 モジュールは、それ自体がビルドシステムと密に絡む大きなテーマです。本書の主題である LTO・PGO とモジュールを同時に扱うと、問題が起きたときに「どちらが原因か」の切り分けが難しくなります。本書では従来の翻訳単位モデルに絞ります。むしろ「翻訳単位の壁」という概念が LTO の説明の土台になるため、この選択は本書にとって好都合でもあります。

想定する読者

  • C++ の実務経験があり、Visual Studio でのビルドに慣れている
  • /O2 は付けているが、その中身を説明したことはない
  • プロファイラを使ったことはあるが、PGO は使ったことがない

本書が扱わないこと

  • アルゴリズムやデータ構造の改善（これはこれで重要ですが、別の話です）
  • SIMD 組み込み関数の手書き最適化
  • GPU / 描画の最適化
  • Linux / macOS 向けのビルド（考え方は共通ですが、手順は Windows に絞ります）

1.6 数値についての約束

本書には「何秒かかった」という数値がしばしば出てきますが、これらは再現できません。CPU の世代、コア数、メモリ、電源プラン、他に動いているプロセス、Windows のバージョン — どれか一つ違えば結果は変わります。

そこで本書は、次の書き方を徹底します。

  • 「◯% 速くなります」とは書きません
  • 代わりに「こう測ると、こういう差が確認できます」と書きます
  • 差が出ない場合、出ない理由の見当を付ける方法も併せて書きます

最後の項目が重要です。最適化オプションは、効かないことも普通にあります。LTO を入れてもビルド時間だけ伸びて実行時間が変わらない、PGO を入れても誤差の範囲、ということは起こります。そのとき「効かなかった」で終わらせず、「なぜ効かなかったか」まで辿れるようになることが、本書の目標です。

手を動かしてください

本書は読み物ではなくハンズオンです。各章は前の章で作ったプロジェクトを引き継いで進みます。第 3 章で作るプロジェクトと第 4 章で作る題材アプリは、最後の第 42 章まで使い続けます。ここだけは必ず手元で作ってください。

1.7 まとめ

  • 最適化の失敗は「測っていない」「測る場所が違う」「理由が分からない」の三つに集約される
  • LTO・PGO・CSPGO は、いずれもコンパイラに渡す情報を増やす仕組みである
  • ClangCL を選ぶのは速いからではなく、最適化の中身を観察する道具が揃っているから
  • 本書は「効果を確認する手段」を第 2 部・第 3 部で先に用意し、そのうえで最適化に進む
  • 本書の数値は再現できない。必ず自分の環境で測ること

次章では、Visual Studio 2026 に ClangCL をインストールし、コマンドラインからバージョンを確認できるところまで進みます。あわせて、Visual Studio に同梱される LLVM を公式版に差し替える方法も扱います。これは本書の後半、比較的新しい機能（特に CSPGO）を使うときに効いてきます。
