第 41 章

CI/CD への組み込み
— プロファイルの保管・再現性・フォールバック

手元で回るようになった手順を、自動化された仕組みに載せます。毎回トレーニングを回すのか、プロファイルを保管するのか。そして第 31 章で学んだ「効果は環境に依存する」という教訓を、どう設計に反映するか。

この章のゴール

  • CI で何を毎回やり、何を定期的にやるかを決める
  • プロファイルの保管方法を選ぶ
  • 陳腐化を自動で検出する
  • 性能の回帰を検出する仕組みを作る

41.1 二つのパイプライン

PGO を CI に載せるとき、すべてを毎回やろうとすると破綻します。計装ビルド（1.9 倍遅い）でトレーニングを流し、さらにもう一度ビルドする——これを全コミットでやるのは現実的ではありません。

役割を分けます。

通常のパイプラインプロファイル更新パイプライン
頻度コミットごと週次、あるいはリリース前
やること保管してあるプロファイルでビルド計装 → トレーニング → マージ → 保管
所要時間通常のビルド ＋ わずか長い
失敗させる条件陳腐化が閾値を超えた／プロファイルが無いトレーニングが失敗した

41.2 プロファイルの保管

第 34 章で三つの選択肢を挙げました。CI の観点で見直します。

方式CI での扱い向いている規模
リポジトリにコミットチェックアウトすれば手に入る。追加の仕組み不要プロファイルが数 MB 以下
成果物（artifact）として保管更新パイプラインが公開し、通常パイプラインが取得ほとんどの場合これ
毎回生成仕組みは単純だがビルドが長いビルドが元々短い場合
バージョンを添えて保管する

プロファイルには、少なくとも次の情報を添えてください。

  • 生成元のコミットハッシュ
  • 使用した clang-cl のバージョン（第 29 章のバージョン不一致問題）
  • トレーニングに使ったワークロードの内容

「このプロファイルはいつの何なのか」が分からなくなると、陳腐化の判断ができません。

41.3 陳腐化の自動検出

第 34 章の内容を CI に落とします。二段構えにするのが実用的です。

41.3.1 まず数える

@echo off
:: check-profile.cmd — 陳腐化した関数の数を数えて判定する
setlocal enabledelayedexpansion

set LOG=%TEMP%\build.log
msbuild ClangOptLab.sln /p:Configuration=Release-Opt /p:Platform=x64 ^
    /t:Rebuild /v:normal > "%LOG%" 2>&1
if errorlevel 1 (
    type "%LOG%"
    exit /b 1
)

for /f %%c in ('findstr /C:"hash mismatch" "%LOG%" ^| find /c /v ""') do set STALE=%%c
echo 陳腐化した関数: !STALE!

if !STALE! GTR 20 (
    echo ##[error] プロファイルが古すぎます。更新パイプラインを実行してください。
    exit /b 1
)
if !STALE! GTR 5 (
    echo ##[warning] プロファイルの陳腐化が進んでいます。
)
exit /b 0

リスト 41-1　check-profile.cmd

閾値は、プロジェクトの規模と変更の頻度で決めてください。「関数の総数の 5%」くらいから始めて調整するのが現実的です。

41.3.2 リリースビルドでは厳しく

出荷するバイナリについては、陳腐化をエラーにします。第 39 章のプロパティシートに入れた -Werror=backend-plugin がこれです。

msbuild ... /p:Configuration=Release-Opt /p:StrictProfile=true
<!-- UseProfile.props -->
<ClCompile Condition="'$(StrictProfile)'=='true'">
  <AdditionalOptions>/clang:-Werror=backend-plugin %(AdditionalOptions)</AdditionalOptions>
</ClCompile>

41.4 プロファイルが無いときのフォールバック

第 39 章 39.6 節の続きです。CI では「無いことに気づかず最適化されていないバイナリを出荷する」のが最悪なので、明示的に失敗させます。

<Target Name="RequireProfile" BeforeTargets="ClCompile"
        Condition="'$(RequireProfile)'=='true' And !Exists('$(ProfileData)')">
  <Error Text="プロファイル $(ProfileData) が見つかりません。" />
</Target>

<Target Name="WarnNoProfile" BeforeTargets="ClCompile"
        Condition="'$(RequireProfile)'!='true' And !Exists('$(ProfileData)')">
  <Warning Text="プロファイルが見つかりません。PGO 無しでビルドします。" />
</Target>
場面RequireProfile挙動
開発者の手元未指定警告して PGO 無しでビルド
プルリクエストの CI未指定同上（プロファイル取得が失敗しても止まらない）
リリースビルドtrue失敗させる

41.5 性能の回帰を検出する

ここで第 15 章と第 31 章の教訓が効いてきます。

41.5.1 ノイズ床を毎回測る

CI のマシンは、実行のたびに条件が違います。共有ランナーなら、他のジョブと同じ物理マシンで動いているかもしれません。固定の閾値（「5% 以上遅くなったら失敗」など）を決め打ちするのは危険です。

第 15 章の空試験を、毎回のジョブの中で行います。

:: 同じバイナリを 2 つ用意して比較 → その回のノイズ床
copy /y out\app.exe out\app_copy.exe
python bench.py out\app.exe out\app_copy.exe -n 10 --args ... > noise.txt

:: 前回のリリースと比較
python bench.py baseline\app.exe out\app.exe -n 10 --args ... > result.txt

そして「差がノイズ床の 3 倍を超えたら報告する」といった相対的な判定にします。

CI での性能測定は難しい

正直に言えば、共有ランナー上での性能測定は信頼性が低いものです。ノイズ床が 10% を超えることも珍しくありません。その状態で数パーセントの改善を検出することはできません。

現実的な落とし所は次のあたりです。

  • 大きな回帰だけを検出する。 「2 倍遅くなった」なら、どんなノイズでも見えます
  • 専用のマシンを用意する。 本気で性能を追うなら、これが唯一の解
  • 時間ではなく決定的な指標を見る。 次節

41.5.2 決定的な指標を CI で見る

第 31 章で得た最大の教訓——コンパイラの判断は決定的、実行時間は環境依存——を、そのまま CI の設計に反映できます。

指標CI での扱い
.text のサイズ閾値を超えた増加を報告。完全に決定的
最適化レコードの集計（第 10 章）Inlined / TooCostly の件数を記録。急変を報告
陳腐化した関数の数41.3 節
リンク時リマークの件数（第 20 章）LTO を使っている場合
実行時間ノイズ床との比較。大きな回帰のみ
 
:: 決定的な指標を記録する
llvm-objdump --section-headers out\app.exe | findstr ".text" > metrics.txt
python summarize.py out\*.opt.yaml >> metrics.txt
これが一番実用的です

「ある変更で Inlined が 600 件から 200 件に減った」なら、何かがおかしい。プロファイルが効かなくなったか、コードの構造が変わったか。実行時間を測るより早く、確実に異常を検出できます。

41.6 パイプラインの例

# 通常のパイプライン（擬似コード）
steps:
  - checkout
  - download_artifact: name=profile, path=app.profdata
  - run: |
      msbuild ClangOptLab.sln /p:Configuration=Release-Opt /p:Platform=x64 ^
        /p:RequireProfile=true /t:Rebuild /v:normal > build.log
  - run: check-profile.cmd          # 陳腐化の判定
  - run: run-tests.cmd              # checksum を含む正しさの検証
  - run: collect-metrics.cmd        # 決定的な指標の記録
  - publish_artifact: metrics.txt

# プロファイル更新パイプライン（週次）
schedule: "0 3 * * 1"
steps:
  - checkout
  - run: build-pgo.cmd              # 第 39 章のリスト 39-5
  - run: |
      llvm-profdata show app.profdata | findstr "Maximum function count"
      llvm-profdata overlap old.profdata app.profdata   # 傾向の変化を確認
  - publish_artifact: name=profile, path=app.profdata
overlap を更新時に取る

新旧のプロファイルを overlap（第 30 章）で比較すると、「本番の傾向そのものが変わっていないか」が分かります。急に一致度が落ちたら、アプリケーションの使われ方かトレーニングの内容が変わったということです。

41.7 再現性の確保

CI で最も重要なのは、同じ入力から同じ出力が得られることです。PGO はこれを壊しやすい仕組みなので、注意点を挙げます。

再現性を壊す要因対処
プロファイルが実行ごとに変わるトレーニングを決定的にする（乱数のシード固定、入力を固定）
マルチスレッドで記録が揺らぐ（第 33 章）複数回トレーニングしてマージする
ツールのバージョンが変わるclang-cl と llvm-profdata のバージョンを固定・記録する
プロファイルの取り違えコミットハッシュを添えて保管する
ビルドの並列度でリンク結果が変わる通常は変わらないが、/Brepro などの再現ビルド機能も検討

41.8 ハンズオン

  1. リスト 41-1 の check-profile.cmd を作る
  2. ソースを一箇所変更して、陳腐化の件数が増えることを確認する
  3. 閾値を小さくして、意図的に失敗させてみる
  4. ビルドの後に .text のサイズを記録するスクリプトを書く
  5. 空試験と本番比較を続けて行うスクリプトを書き、ノイズ床との比を出す
  6. プロファイルを削除して RequireProfile=true を渡し、ビルドが失敗することを確認する

41.9 まとめ

  • CI は二つのパイプラインに分ける。通常ビルドは保管したプロファイルを使い、更新は定期的に行う
  • プロファイルは成果物として保管し、コミットハッシュとツールのバージョンを添える
  • 陳腐化は hash mismatch の件数で判定する。リリースビルドでは -Werror=backend-plugin
  • プロファイルが無いときの挙動を、開発者の手元とリリースで切り替える
  • CI での性能測定は信頼性が低い。ノイズ床を毎回測り、相対的に判定する
  • より確実なのは決定的な指標——.text のサイズ、レコードの集計、陳腐化の件数
  • トレーニングを決定的にし、ツールのバージョンを固定して再現性を確保する
