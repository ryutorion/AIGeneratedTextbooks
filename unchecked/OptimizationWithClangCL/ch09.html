第 9 章

最適化リマークを読む
— -Rpass / -Rpass-missed / -Rpass-analysis

逆アセンブルは最適化の「結果」を見せてくれますが、「なぜそうなったか」は教えてくれません。Clang には、最適化パス自身に判断の理由を語らせる仕組みがあります。本書で最も出番の多い道具です。

この章のゴール

  • 三種類のリマークの違いを理解する
  • clang-cl での正しい書き方を身につける
  • インライン化のリマークから cost と threshold を読む
  • 大量に出るリマークを実用的な量に絞る

9.1 三種類のリマーク

オプション報告される内容
-Rpass=<正規表現>最適化を行ったとき
-Rpass-missed=<正規表現>最適化を行わなかったとき
-Rpass-analysis=<正規表現>判断の材料となった解析結果

引数はパス名に対する正規表現です。inline と書けばインライナだけ、inline|loop-vectorize で二つ、.* ですべてになります。パス名は第 7 章で見たパイプラインに出てくるものです。

実務でよく使うのは次の三つです。

/clang:-Rpass=inline                 <- インライン化されたもの
/clang:-Rpass-missed=inline          <- されなかったもの
/clang:-Rpass-analysis=loop-vectorize  <- ベクトル化できない理由

9.2 clang-cl での書き方

/clang: が必須です

第 6 章で確認したとおり、-Rpass=inline をそのまま clang-cl に渡すと unknown argument ignored in clang-cl という警告が出るだけで何も表示されません。必ず /clang: を付けてください。

× clang-cl /c /O2 /Rpass=inline    src\tokenizer.cpp
× clang-cl /c /O2 -Rpass=inline    src\tokenizer.cpp
○ clang-cl /c /O2 /clang:-Rpass=inline src\tokenizer.cpp

MSBuild で使う場合は、C/C++ > コマンド ライン > 追加のオプション に書きます。ビルド出力ウィンドウにリマークが流れてきます。

9.2.1 デバッグ情報との関係

リマークを出すのにデバッグ情報は不要です。ただし /Zi や /Z7 を付けている場合、報告される位置情報の精度が変わります。

設定報告される位置
デバッグ情報なしr2.cpp(4,38) — 行と桁
/Z7 または /Zir2.cpp(4,1) — 桁が失われる
/Z7 + /clang:-gcolumn-infor2.cpp(4,38) — 桁が戻る

これは、Windows のデバッグ情報形式（CodeView）が既定で桁情報を持たないためです。一行に複数の呼び出しがあるコードでは桁が無いと区別できないので、リマークを読むときは /clang:-gcolumn-info を足しておくとよいでしょう。

9.3 インライン化のリマークを読む

第 6 章でも使った小さなコードで試します。

int helper(int a, int b) { return a * b + 7; }
int caller(int n) {
    int s = 0;
    for (int i = 0; i < n; ++i) s += helper(i, s);
    return s;
}
clang-cl /c /O2 /clang:-Rpass=inline sample.cpp
sample.cpp(4,38): remark: '?helper@@YAHHH@Z' inlined into '?caller@@YAHH@Z'
  with (cost=-30, threshold=337) at callsite caller:2:38; [-Rpass=inline]
    4 |     for (int i = 0; i < n; ++i) s += helper(i, s);
      |                                      ^

実際の出力（改行は読みやすさのため）

この一行に、インライナの判断がすべて入っています。

部分意味
'?helper@@YAHHH@Z'展開された関数（呼び先）。MSVC 形式のマングル名
inlined into '?caller@@YAHH@Z'展開先の関数（呼び元）
cost=-30展開したときの見積もりコスト。負なら「展開したほうが小さくなる」
threshold=337この呼び出し箇所での許容上限
at callsite caller:2:38呼び出し箇所の位置

判定は単純で、cost が threshold 以下なら展開するです。ここでは -30 ≤ 337 なので展開されました。cost が負になるのは、呼び出し命令や引数の受け渡しが消える分の得が、本体を複製するコストを上回っているからです。この数値の詳細は第 11 章で扱います。

9.3.1 属性によるリマーク

__forceinline や __declspec(noinline) を付けると、コスト計算そのものが行われません。

remark: '?ff@@YAHH@Z' inlined into '?u@@YAHH@Z'
  with (cost=always): always inline attribute at callsite ?u@@YAHH@Z:0:0; [-Rpass=inline]

remark: '?nf@@YAHH@Z' not inlined into '?u@@YAHH@Z'
  because it should never be inlined (cost=never): noinline function attribute [-Rpass-missed=inline]

cost=always / cost=never という表示が、属性による強制を示しています。

9.4 「されなかった」理由を読む

-Rpass-missed のほうが、実は役に立つ場面が多いものです。

remark: '?big@@YAHH@Z' not inlined into '?user@@YAHH@Z'
  because too costly to inline (cost=5, threshold=0) [-Rpass-missed=inline]

よく見る理由と、その意味は次のとおりです。

理由意味と対処
too costly to inlineコストがしきい値を超えた。しきい値を上げるか（第 11 章）、PGO でホットだと教える（第 32 章）
noinline function attribute属性で禁止されている
recursive再帰関数。展開の深さに制限がある
function definition is not available定義が見えない。別の翻訳単位にある。← LTO の出番
indirect call呼び先が確定していない。仮想関数など
下二つが本書の核心です

function definition is not available は「壁があるので展開できない」という報告であり、これこそ LTO が解決する問題です。indirect call は「呼び先が分からないので展開できない」という報告で、デバーチャライズ（第 21 章）と間接呼び出しの投機的展開（第 32 章）が対象とする問題です。第 4 部・第 5 部でこのリマークがどう変化するかを追いかけます。

9.5 ベクトル化のリマーク

ループのベクトル化は、失敗の理由が具体的に返ってくるので特に有用です。

void acc(float* a, const float* b, int n) {
    for (int i = 0; i < n; ++i) a[i] = a[i] * b[i] + a[i - 1];
}
clang-cl /c /O2 /clang:-Rpass-missed=loop-vectorize ^
                /clang:-Rpass-analysis=loop-vectorize sample2.cpp
remark: loop not vectorized: unsafe dependent memory operations in loop.
  Use #pragma clang loop distribute(enable) to allow loop distribution to attempt
  to isolate the offending operations into a separate loop
  Backward loop carried data dependence. Memory location is the same as accessed
  at sample2.cpp:2:54 [-Rpass-analysis=loop-vectorize]

remark: loop not vectorized [-Rpass-missed=loop-vectorize]

-Rpass-analysis が「後ろ向きのループ伝搬依存がある」という具体的な理由と、依存元の位置まで示しています。a[i] が a[i-1] に依存しているので、並列に計算できないという指摘です。

成功した場合は次のように出ます。

remark: vectorized loop (vectorization width: 4, interleaved count: 2) [-Rpass=loop-vectorize]

9.6 リマークの量をどうにかする

ここまでは小さなサンプルでした。実際のコードにそのまま適用すると、大量のリマークに埋もれます。

LogLab の main.cpp を -Rpass=inline でコンパイルすると、リマークは 136 件。そのうち自分が書いたソース由来のものは 28 件だけでした。残りの 8 割は標準ライブラリのヘッダ内部で起きたインライン化です。

...\include\vector(735,2): remark: '??$_Destroy@...' inlined into
  '??1?$vector@V?$unique_ptr@...' with (cost=always): always inline attribute ...

読む気にならない、というのが正直なところでしょう。対処は三つあります。

9.6.1 自分のソース由来だけに絞る

:: Developer Command Prompt
clang-cl /c /O2 /Iinclude /clang:-Rpass=inline src\tokenizer.cpp 2>&1 ^
  | findstr /B "src\\"
# Developer PowerShell
clang-cl /c /O2 /Iinclude /clang:-Rpass=inline src\tokenizer.cpp 2>&1 `
  | Select-String '^src\\'

9.6.2 マングル名を戻す

読みたい名前が出てきたら、llvm-undname にかけます。

echo ?parse_line@loglab@@YA_N... | llvm-undname

9.6.3 そもそもリマークで読むのをやめる

これが本命です。リマークは流れて消えるテキストであり、集計にも保存にも向いていません。 同じ情報を機械可読な形で保存する仕組みが次章の最適化レコードです。「この関数のインライン化だけを今すぐ見たい」ときはリマーク、「全体を俯瞰したい・前回と比べたい」ときはレコード、と使い分けます。

9.7 ハンズオン — LogLab で読む

プロジェクトの 追加のオプション に次を書いてリビルドしてください。

/clang:-Rpass-missed=inline /clang:-gcolumn-info

出力ウィンドウを「ビルド」にして、src\ で始まる行を探します。次のことを確認してください。

  1. main.cpp から parse_line を呼ぶ箇所に、function definition is not available のリマークが出ているか
  2. Filter::accept() の呼び出しについて、間接呼び出しに関するリマークが出ているか
  3. Stats::add から handle_error への呼び出しはどう扱われているか

1 番が確認できれば、それが第 4 部で LTO を導入する直接の動機になります。確認できたら追加のオプションは消しておいてください（ビルドが遅くなり、出力も長大になるため）。

9.8 まとめ

  • リマークは最適化パス自身による判断の説明である
  • -Rpass（やった）／-Rpass-missed（やらなかった）／-Rpass-analysis（その材料）の三種類。引数はパス名の正規表現
  • clang-cl では /clang: が必須。付けないと警告だけ出て何も表示されない
  • インライン化の判定は cost ≤ threshold。cost=always / cost=never は属性による強制
  • function definition is not available は LTO が、indirect call はデバーチャライズと PGO が解決する問題
  • /Z7 を使うと桁情報が落ちる。/clang:-gcolumn-info で戻せる
  • 実コードではリマークの 8 割が標準ライブラリ由来。フィルタするか、次章のレコードに移行する

次章では、同じ情報を YAML ファイルとして保存する -fsave-optimization-record を扱います。ファイルになれば、集計もできますし、前回のビルドとの比較もできます。さらに opt-viewer を使えば、ソースコード上に最適化の判断を重ねた HTML を生成できます。第 4 部以降で「LTO の前後を比べる」ときの主力になります。
