第 13 章

ETW と Windows Performance Analyzer の基本

Windows には、OS 自身に組み込まれたトレース機構があります。コマンド 2 行でトレースが採れ、どんなプロセスでも対象にでき、CI にも組み込めます。本書の計測の本命です。

この章のゴール

  • wpr コマンドで CPU トレースを採る
  • WPA でトレースを開き、シンボルを読み込む
  • Sampled と Precise の違いを理解する
  • ホット関数を特定する定型手順を身につける

13.1 ETW とは

ETW（Event Tracing for Windows）は、カーネルとユーザーモードの双方からイベントを高速に記録する仕組みです。CPU サンプリング、コンテキストスイッチ、ディスク I/O、ページフォルト、ヒープ確保——Windows で起きるほとんどのことが、ETW のイベントとして取り出せます。

本書で使うのは、その中の CPU サンプリングです。第 12 章で説明したとおり、一定間隔でコールスタックを記録するものです。実は PIX のタイミングキャプチャも、内部ではこの仕組みを使っています。

役割分担は次のようになっています。

ツール役割入手方法
WPR（wpr.exe）トレースを採る。Windows に標準で入っている標準搭載
WPAトレースを見るMicrosoft Store、または Windows ADK の Windows Performance Toolkit
xperf.exeWPR より低レベルな採取コマンドWindows Performance Toolkit

13.2 トレースを採る

管理者権限の コマンドプロンプトまたは PowerShell を開きます。カーネルのイベントを扱うため、昇格が必要です。

:: 1. 記録を開始する
wpr -start CPU -filemode

:: 2. 測りたい処理を実行する
cd x64\Release
ClangOptLab.exe

:: 3. 記録を停止し、ファイルに保存する
wpr -stop loglab_O2.etl "LogLab baseline /O2"

これだけです。loglab_O2.etl が生成されます。

13.2.1 主なコマンド

コマンド意味
wpr -start <プロファイル> [-filemode]記録を開始する
wpr -stop <file.etl> "<説明>"記録を停止して保存する。説明は省略できるが付けておくとよい
wpr -cancel保存せずに記録を中止する
wpr -status記録中かどうか、取りこぼしがないかを確認する
wpr -profiles使える組み込みプロファイルの一覧を表示する
-filemode を付ける理由

-filemode を省略するとメモリモードになり、固定サイズの循環バッファに記録されます。長時間動くアプリの「最後の数秒」を捕まえるのには向いていますが、LogLab のように短い処理を最初から最後まで記録したい場合は -filemode を付けます。こちらはディスクに直接書き続けるので、記録が上書きで消えることがありません（そのかわりファイルは際限なく大きくなります）。

トレースが大きすぎるとき

CPU プロファイルは既定で verbose（詳細）です。ファイルが大きくなりすぎる場合は CPU.light を使うと軽くなります。

wpr -start CPU.light -filemode

また、wpr -status で Dropped event が 0 でない場合は、イベントを取りこぼしています。この状態のトレースは統計として信用できないので、軽いプロファイルにするか、測る範囲を狭めてください。

13.2.2 スクリプトにしておく

第 4 部以降、LTO や PGO のたびにトレースを採り直します。バッチファイルにしておきましょう。

@echo off
:: capture.cmd <出力名>
:: 管理者権限で実行すること
set NAME=%1
if "%NAME%"=="" set NAME=trace

wpr -cancel >nul 2>&1
wpr -start CPU -filemode || exit /b 1

pushd x64\Release
ClangOptLab.exe
popd

wpr -stop %NAME%.etl "LogLab %NAME%"
echo saved: %NAME%.etl

リスト 13-1　capture.cmd

冒頭の wpr -cancel は、前回の記録が止まっていなかった場合の保険です。WPR は同時に複数の記録を開始できないため、これが残っていると -start が失敗します。

13.3 WPA で開く

.etl ファイルを WPA で開きます。左側の Graph Explorer に、記録された内容がカテゴリごとに並びます。

13.3.1 まずシンボルを読み込む

これを忘れると何も分かりません。 関数名の代わりにアドレスが並ぶだけです。

まず、環境変数でシンボルの場所を教えます。WPA を起動する前に設定してください。

set _NT_SYMBOL_PATH=srv*C:\symbols*https://msdl.microsoft.com/download/symbols;C:\work\ClangOptLab\x64\Release

前半が Microsoft のシンボルサーバ（OS の DLL 用）、セミコロンの後ろが自分のプロジェクトの PDB がある場所です。両方が必要です。

WPA でトレースを開いたら、メニューの Trace > Load Symbols を実行します。初回は OS のシンボルをダウンロードするため数分かかることがあります。

シンボルが読めているかの確認

スタックに ClangOptLab.exe!0x1a3f のような表示が残っていたら、自分の PDB が見つかっていません。_NT_SYMBOL_PATH に x64\Release を含めたか、そこに ClangOptLab.pdb があるかを確認してください。シンボル解決のより詳しい話は次章で扱います。

13.3.2 Sampled と Precise

CPU 関連のグラフは二種類あります。名前が紛らわしいので整理しておきます。

CPU Usage (Sampled)CPU Usage (Precise)
記録するもの一定間隔（通常 1 ms）のサンプルコンテキストスイッチ（スレッドの切り替え）
1 行の意味1 個のサンプル1 回のスイッチ
得意なことどの関数が CPU を使っているかスレッドがいつ動き、何を待っていたか
苦手なこと短時間の事象（DPC / ISR など）関数単位の時間配分

本書で使うのは Sampled のほうです。 「Precise」という名前につられないでください。Precise が精密なのはスイッチの時刻であって、関数ごとの時間配分ではありません。

13.3.3 列の意味

列意味
Weightそのサンプルが代表する時間（ミリ秒）。前のサンプルとの時刻差
Countサンプルの個数（アイドルを除く）
All Countアイドルを含むサンプルの個数
% Weight表示中の時間範囲に占める割合。これを見る

13.4 ホット関数を見つける定型手順

WPA は自由度が高すぎて最初は迷います。次の手順を型として覚えてしまうのが早道です。

  1. Trace > Load Symbols を実行する
  2. Graph Explorer から Computation > CPU Usage (Sampled) をドラッグして解析ビューに置く
  3. タイムライン上で、測りたい区間をドラッグして選択し、右クリックから Zoom する
  4. プリセットを Utilization by Process and Thread にする
  5. ClangOptLab.exe の行を展開し、スレッドを展開する
  6. Stack 列を Thread ID の右隣に配置する（すでにあればそのまま）
  7. スタックツリーを、% Weight の大きい枝から順に展開していく

13.4.1 <itself> が排他時間

スタックツリーを展開していくと、子ノードのひとつに <itself> という項目が現れます。これがその関数自身で消費した時間、つまり第 12 章で説明した排他時間です。

ClangOptLab.exe (100.0%)
  └ main (99.8%)
      ├ loglab::parse_line (52.1%)
      │   └ <itself> (52.1%)        <- parse_line 自身が 52.1%
      ├ loglab::Stats::add (18.4%)
      │   └ <itself> (18.4%)
      ├ <itself> (21.0%)             <- main に展開されたコード（accept など）
      └ ...

スタックツリーの読み方（数値は例）

main の <itself> が大きいとき

これは main のループ本体そのものと、main にインライン展開された関数の合計です。LogLab では Filter::accept() のうち展開されたものがここに含まれます。第 12 章で触れた「インライン化された関数は見えない」問題が、こういう形で現れます。

13.4.2 Butterfly ビュー

ある関数が複数の場所から呼ばれている場合、「どこから呼ばれたぶんが重いのか」を知りたくなります。関数を右クリックして View Callers / View Callees を選ぶと、呼び出し元・呼び出し先の内訳が見られます。

これは第 6 部の CSPGO と直接つながる話です。CSPGO が解決しようとしているのは、まさに「同じ関数でも呼び出し元によって挙動が違う」という問題だからです。

13.5 落とし穴

トレースにシステム全体が入っている

WPR はマシン全体を記録します。ブラウザやウイルス対策ソフトが動いていれば、それも全部入ります。まず ClangOptLab.exe の行を選び、そこにズームしてから解析してください。

ファイルが巨大になる

-filemode は際限なく書き続けます。数分のトレースで数百 MB になることもあります。測る範囲は短く保ち、不要な .etl は消してください。

計測対象外の処理が混ざる

LogLab は起動時に generate_lines() でログを生成します。この時間もトレースには含まれます。タイムラインで区間を選ぶときは、実際の計測ループの部分だけを選んでください。区間の見分けがつかない場合は、行数を増やして計測ループを相対的に長くすると分かりやすくなります。

1 回のトレースを信じすぎる

プロファイルもまた 1 回の実行結果です。上位の関数が入れ替わる程度のばらつきは普通に起こります。判断に迷うときは 2、3 回採って傾向を見てください。この話は次々章（第 15 章）で本格的に扱います。

13.6 ハンズオン

  1. リスト 13-1 の capture.cmd を作る
  2. 管理者権限で capture.cmd baseline_O2 を実行する
  3. _NT_SYMBOL_PATH を設定してから WPA を起動し、baseline_O2.etl を開く
  4. Trace > Load Symbols を実行する
  5. 13.4 節の手順でスタックツリーを展開する
  6. 排他時間の上位 5 関数と % Weight をメモする ← 第 3 部の成果物
  7. .etl ファイルを作業フォルダに保存しておく（第 20 章・第 32 章で比較します）

13.7 まとめ

  • ETW は Windows 標準のトレース機構。PIX のタイミングキャプチャも内部ではこれを使っている
  • 採取は wpr -start CPU -filemode と wpr -stop <file>.etl の 2 行。管理者権限が必要
  • 短い処理を丸ごと採るには -filemode。wpr -status で Dropped event が 0 であることを確認する
  • WPA では最初に Load Symbols。_NT_SYMBOL_PATH に自分の PDB のフォルダを含める
  • 関数ごとの時間配分を見るのは Sampled。Precise はスレッドのスケジューリング用
  • 定型手順は「Load Symbols → CPU Usage (Sampled) → 区間をズーム → Utilization by Process and Thread → Stack 列を展開」
  • <itself> が排他時間。インライン展開された関数はここに吸収される

次章では、この章で「読み込む」としか書かなかったシンボルの話を掘り下げます。clang-cl の /Zi は MSVC の /Zi とは違うこと、PDB を作っているのは実はリンカであること、そしてリンカの設定次第でプロファイルのシンボルが壊れることを扱います。
