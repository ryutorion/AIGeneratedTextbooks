第 35 章

コンテキスト非依存プロファイルの限界
— インライン後に失われる情報

ここから第 6 部です。第 5 部のプロファイルには「この分岐は 0.348% 成立する」という情報がありました。しかし「どこから呼ばれたときに 0.348% なのか」は記録されていません。その欠落が何を招くのかを見ます。

この章のゴール

  • プロファイルが持っていない「文脈」という情報を理解する
  • インライン展開がこの欠落を悪化させる仕組みを知る
  • 一周目のプロファイルでは原理的に解決できない理由を理解する
  • CSPGO の発想を掴む

35.1 同じ関数、違う挙動

次のようなコードを考えます。ログの整形を行う共通関数と、その二種類の呼び出し元です。

// 共通の整形関数
std::string format(const Record& r, bool verbose) {
    std::string s = to_text(r.level);
    if (verbose) {                       // ← この分岐
        s += " [" + std::string(r.component) + "]";
        s += " ts=" + std::to_string(r.timestamp);
    }
    return s + " " + std::string(r.message);
}

// 呼び出し元 A：本番のログ出力（毎秒何万回）
void emit_production(const Record& r) { write(format(r, false)); }

// 呼び出し元 B：デバッグダンプ（起動時に数回）
void emit_debug(const Record& r)      { write(format(r, true)); }

format() の中の if (verbose) は、呼び出し元によって完全に決まります。A からは常に false、B からは常に true。

ところがプロファイルに記録されるのは、合計された一つの数字です。A から 100 万回、B から 3 回呼ばれたなら、こう記録されます。

if (verbose) の成立回数: 3 / 1000003  （0.0003%）

この数字自体は正しい。しかし「A からは 0%、B からは 100%」という実際の構造は、完全に失われています。

35.2 なぜそれが問題になるのか

プロファイルを見たコンパイラは、「if (verbose) はほぼ成立しない」と判断します。これは A に対しては最適な判断ですが、B に対しては最悪です。B の経路では、コールドと判定されたコードを毎回通ることになります。

B が本当に稀ならそれで構いません。問題は両方ともホットな場合です。

35.3 インライン展開が状況を変える

ここが核心です。format() が emit_production() と emit_debug() の両方にインライン展開されたとしましょう。展開後は、二つの独立したコードになっています。

void emit_production(const Record& r) {
    // format の本体（A 版）
    ... if (false) { ... }      ← 定数なので消せるはず
}

void emit_debug(const Record& r) {
    // format の本体（B 版）
    ... if (true) { ... }       ← 常に通るはず
}

この例では verbose が定数リテラルなので、定数伝播だけで解決します。しかし実際のコードでは、そう単純ではありません。

void emit_production(const Record& r) { write(format(r, g_prod_verbose)); }

変数になった途端、コンパイラは中身を知りません。頼れるのはプロファイルだけです。そしてそのプロファイルは、A と B を平均したものなのです。

「コンテキスト非依存」の意味

第 5 部で使ったプロファイルは、関数ごとに 1 組のカウンタを持ちます。呼び出し文脈（コンテキスト）を区別しないので、コンテキスト非依存（context-insensitive）と呼ばれます。

CSPGO の CS は Context-Sensitive、つまり文脈を区別するという意味です。

35.4 一周目では解決できない理由

「では、最初から呼び出し元ごとにカウンタを分ければよいのでは」と考えたくなります。しかし、それは原理的に無理があります。

理由 1 — どこまで区別すればよいか決められない

呼び出し元の呼び出し元、そのまた呼び出し元……と遡り始めると、区別すべき文脈の数は指数的に増えます。すべてを記録するのは現実的ではありません。

理由 2 — 展開されるかどうかは、まだ分からない

より本質的なのはこちらです。計装を行う時点では、その関数がインライン展開されるかどうかがまだ決まっていません。展開されない関数について文脈を区別しても、意味がありません（実体が一つしかないので、平均されたプロファイルで正しい）。

つまり、文脈を区別する価値があるのは展開された箇所だけ。そして展開されたかどうかは、最適化が済んでみないと分からないのです。

35.5 CSPGO の発想

解決策は、いささか力技です。

一周目のプロファイルで最適化する。インライン展開が済んだ状態でもう一度計装する。展開後のコードにはすでに文脈が焼き込まれているので、そこで数えれば文脈ごとのカウンタが得られる。

展開後の emit_production() の中の if と、emit_debug() の中の if は、この時点では別々のコードです。それぞれに独立したカウンタを置けば、A では 0%、B では 100% という記録が取れます。

一周目（通常の PGO）二周目（CSPGO）
計装する時点最適化の前インライン展開の後
カウンタの単位ソース上の関数展開後のコード片
文脈の区別できないできる
使うもの—一周目のプロファイル（展開を再現するため）
二周目は一周目を必要とします

二周目の計装ビルドは、一周目のプロファイルを適用した状態で作ります。そうしないと、最終的に出荷するビルドとは違うインライン展開が起きてしまい、測った文脈が的外れになるからです。

この依存関係が、次章で見る「五段階の手順」の形を決めています。

35.6 LogLab に当てはめると

本書の題材で、文脈依存性がありそうな箇所を探してみます。

候補文脈による違いはあるか
next_field()parse_line から 4 回呼ばれるが、いずれも同じ性質の入力
Filter::accept()実装ごとに別の関数。文脈というより実装の違い
mix()Stats::add と handle_error の両方から呼ばれる。頻度は大きく違う
Stats::add()main からしか呼ばれない

三行目に少し可能性がありますが、mix() は分岐を持たない小さな関数なので、文脈を区別しても得るものは多くありません。

率直に言えば、LogLab は CSPGO の題材として弱いです

呼び出し構造が浅く、同じ関数が性質の違う複数の文脈から呼ばれる、という状況がほとんどありません。第 37 章で実測しますが、結果は「効果なし」でした。

それでも第 6 部を設けるのは、CSPGO の仕組みを理解しておく価値があるからです。そして「効かない」という結果もまた、どういうコードなら効くのかを教えてくれます。第 21 章のデバーチャライズと同じ構図です。

35.7 CSPGO が効きやすいコード

逆算すると、次のような特徴を持つコードが対象になります。

  • 共通のユーティリティ関数が、性質の違う複数の場所から呼ばれる（文字列処理、ロギング、シリアライズ、コンテナ操作）
  • その関数が分岐を持つ（フラグ引数、型による場合分け、エラー処理）
  • 呼び出し元ごとに分岐の偏りが大きく違う
  • その関数がインライン展開される程度に小さい
  • プログラムの規模が大きく、呼び出しの階層が深い

大規模なアプリケーション、特にテンプレートやコールバックを多用するコードベースが典型例です。

35.8 まとめ

  • 通常の PGO のプロファイルは、関数ごとに1 組のカウンタしか持たない
  • 同じ関数が性質の違う文脈から呼ばれると、その違いは平均されて消える
  • インライン展開されると、平均されたプロファイルが複数の実体に適用されることになる
  • 一周目で文脈を区別できないのは、展開されるかどうかがその時点で未定だから
  • CSPGO の発想は、展開が済んだ状態でもう一度計装すること
  • 二周目の計装ビルドは、一周目のプロファイルを適用した状態で作る必要がある
  • 効くのは「共通の小さな関数が、偏りの違う複数の文脈から呼ばれる」コード。LogLab は該当しない

次章では、CSPGO の手順を実際に踏みます。三段階だった PGO が五段階になります。オプションは -fcs-profile-generate、マージの仕方には少しコツがあり、LTO と組み合わせる場合はリンカ側にも対応するオプションがあります。
