第 11 章

インライン化としきい値
— -mllvm -inline-threshold の効果と副作用

インライン化は本書で最も重要な最適化です。LTO も PGO も、突き詰めれば「インライナにより良い判断をさせる」ための仕組みだと言えます。この章ではその判断の仕組みを解剖し、手動でしきい値を動かして何が起きるかを実測します。そしてなぜそれが最後の手段なのかを確認します。

この章のゴール

  • インライン化が「最適化の入り口」と呼ばれる理由を理解する
  • cost と threshold のモデルを読めるようになる
  • しきい値を変えたときの実際の効果を測る
  • しきい値の手動調整が抱える問題を理解する

11.1 インライン化は何のためにあるのか

「関数呼び出しのオーバーヘッドを無くすため」——これは正しいのですが、副次的な効果にすぎません。本当の価値は別のところにあります。

インライン化は、呼び出し先のコードを呼び出し元の文脈に持ち込みます。 すると、それまで不可能だった最適化が一気に可能になります。

// 別の場所で定義されている
int scale(int v, int factor, bool clamp) {
    int r = v * factor;
    if (clamp) {
        if (r > 1000) r = 1000;
        if (r < -1000) r = -1000;
    }
    return r;
}

// 呼び出し側
int total = 0;
for (int i = 0; i < n; ++i) {
    total += scale(data[i], 2, false);   // factor も clamp も定数
}

scale() が呼び出しのままなら、clamp が false であることをコンパイラは活かせません。毎回引数を積み、分岐を評価します。

インライン化されると、話が変わります。

  1. factor = 2、clamp = false が定数として伝播する
  2. if (clamp) の中身がまるごとデッドコードとして削除される
  3. 残るのは data[i] * 2 だけ
  4. それがループ本体に溶け込み、ベクトル化の対象になる

呼び出しコスト数サイクルの節約ではなく、ループ全体が SIMD 化されるかどうかの差になりました。これが「入り口」と呼ばれる所以です。第 7 章で見たパイプラインが、インライン化のたびに掃除のパス（instcombine、simplifycfg）を挟んでいるのは、まさにこの連鎖を回すためです。

だから翻訳単位の壁が痛い

上の例で scale() が別の .cpp にあれば、この連鎖は一つも起きません。第 9 章のリマークでいう function definition is not available です。LTO が価値を持つのは、呼び出しコストを削るからではなく、この連鎖の入り口を開けるからです。

11.2 cost と threshold

インライナの判断は、第 9 章で見たとおり単純な比較です。

cost ≤ threshold  ならば展開する

11.2.1 cost — 展開したときの見積もり

cost は「この呼び出し箇所で展開したら、コードがどれだけ増えるか」の見積もりです。関数の大きさだけで決まるのではなく、その呼び出し箇所に固有の値である点が重要です。

先ほどの例なら、clamp = false が渡される呼び出し箇所では「展開すると if の中身が消える」と見積もられ、cost は小さくなります。同じ関数でも、clamp が変数である呼び出し箇所では cost は大きくなります。

cost は負にもなります。第 9 章で見た例がそうでした。

with (cost=-30, threshold=337)

これは「展開したほうがコードが小さくなる」という意味です。呼び出し命令、引数の設定、スタックフレームの出し入れが消える分が、本体を複製するコストを上回っています。小さな関数ではよくあることです。

11.2.2 threshold — 呼び出し箇所ごとの許容上限

threshold も呼び出し箇所ごとに変わります。基準値から出発して、状況に応じて上下します。

threshold を上げる要因理由
関数が inline 指定されているプログラマが展開を望んでいるヒントとみなす
呼び出し元が小さい展開しても全体が肥大しない
引数に定数が渡っている展開後に簡約が進む見込みがある
その呼び出し箇所がホットだと分かっているPGO のプロファイルがある場合。第 32 章
-O3 を指定している速度優先の姿勢
threshold を下げる要因理由
-Os / -Oz（＝ clang-cl の /O1）サイズ優先
その呼び出し箇所がコールドだと分かっているPGO のプロファイルがある場合

実測すると、-inline-threshold=225 を指定したときにリマークが表示する値は 337 でした。100 を指定すれば 150、1000 なら 1500。この呼び出し箇所では基準値の 1.5 倍のボーナスが乗っていたことになります。

係数を暗記しないでください

ボーナスの倍率も基準値も、LLVM の内部実装であり、バージョンによって変わります。覚えるべきは数値ではなく構造です。すなわち「しきい値は一律ではなく、呼び出し箇所ごとの状況で決まる」ということ。そしてその状況判断の材料として最も強力なものが、次章以降で扱う実行時プロファイルだということです。

11.3 しきい値を動かしてみる

基準値は -mllvm 経由で変更できます。

-mllvm -inline-threshold=500

LogLab で、値を変えながらコードサイズと実行時間を測った結果です。

thresholdコードサイズ実行時間（3 回の最短）checksum
09,847 B803 ms一致
508,422 B619 ms一致
225（既定）8,103 B470 ms一致
10008,247 B483 ms一致
50008,247 B463 ms一致

実測の一例。絶対値は環境に強く依存します

この表から三つのことが読み取れます。

1. 既定値がほぼ最適だった

225 から 5000 まで 20 倍以上動かしても、実行時間はほとんど変わりません。上げても得はしないのです。LLVM の既定値は、多数の実プログラムに対するチューニングの結果であり、素人が思いつきで動かして勝てるものではありません。

2. 下げると明確に悪化する

0 にすると 1.7 倍遅くなりました。インライン化が実際に効いていることの裏返しです。-mllvm -inline-threshold=0 は「インライン化の寄与を測る」ための道具として使えます。

3. インライン化しないほうがコードは大きい

これが直感に反する点でしょう。threshold=0 のとき、コードサイズは既定値より2 割ほど大きくなっています。展開しないと、呼び出し規約に従って引数をレジスタに並べ、スタックを調整し、戻り値を受け取るコードが呼び出し箇所ごとに必要になるからです。cost が負になるという話の、実物での確認になります。

11.4 /Ob との関係

第 6 章で見た /Ob は、しきい値より上位の制御です。

設定挙動使いどころ
/Ob0展開しない切り分け。デバッグ
/Ob1inline 指定のあるものだけ—
/Ob2コンパイラの判断（Release 既定）通常はこれ
/Ob3より積極的試す価値はあるが、上表と同じく効果は限定的

11.5 属性で個別に指示する

全体のしきい値を動かすより、特定の関数を名指しするほうが副作用は小さくなります。

書き方意味
__forceinline必ず展開する（MSVC 互換。clang-cl でも有効）
[[clang::always_inline]]同上（Clang の属性構文）
__declspec(noinline)展開を禁止する
[[clang::noinline]]同上

これらを付けると、リマークは cost=always / cost=never を表示し、コスト計算そのものが行われなくなります。

inline キーワードは最適化の指示ではありません

C++ の inline は、複数の翻訳単位に同じ定義があってもよい（ODR 違反にしない）ための言語機能です。「展開してほしい」というヒントとしても扱われますが、それは副次的な扱いにすぎません。inline を付けても展開される保証はなく、付けなくても展開されます。展開を強制したいなら __forceinline を使ってください。

__declspec(noinline) は調査に便利です

「この関数がホットスポットのはずなのに、プロファイラに出てこない」というとき、原因はたいていインライン化です。展開されて呼び出し元に溶けてしまい、独立した関数として計測できなくなっています。一時的に __declspec(noinline) を付けると、プロファイラから見えるようになります。第 3 部で計測を始めたら、この手を思い出してください。

11.6 上げたときに起きること

実測では効果がありませんでしたが、しきい値を上げると何が起きうるのかは知っておくべきです。

副作用内容
命令キャッシュの圧迫コードが膨らむとキャッシュミスが増え、かえって遅くなる。大きなプログラムほど顕著
レジスタ不足展開で生存変数が増えるとスタックへの退避（スピル）が発生する
ビルド時間の増大展開後のコードに対して全パスが動くため、コンパイル時間が伸びる
デバッグの困難化スタックトレースから関数が消える
再現性の低下-mllvm は非公式オプション。LLVM を更新すると挙動が変わりうる

最初の項目が本質的です。インライン化は「速くなるか遅くなるか」が測ってみないと分からない最適化です。小さなベンチマークでは命令キャッシュに全部載るので常に速くなり、実アプリでは載らないので遅くなる、という食い違いも普通に起こります。

11.7 なぜ手動調整は最後の手段なのか

ここまでの話を一つにまとめます。-mllvm -inline-threshold=N には、原理的な問題が二つあります。

問題 1 — 全部に一律に効く

しきい値は翻訳単位内のすべての呼び出し箇所に同じように適用されます。しかし実際に上げたいのは、たいていホットループの中の数箇所だけです。それ以外の何百もの箇所まで巻き込んで展開すると、得た分をキャッシュミスで失います。

問題 2 — 判断材料が足りない

そもそも「どの呼び出し箇所がホットか」をコンパイラは知りません。知らないから一律のしきい値で妥協しているのであって、しきい値の数字をいじってもその根本は変わりません。

PGO はこの二つを同時に解決します

プロファイルがあれば、インライナは呼び出し箇所ごとに「ここは何回通った」を知ることができます。ホットな箇所ではしきい値を大きく引き上げ（実装上は数千規模の別のしきい値が使われます）、コールドな箇所では逆に引き下げる。一律ではなく、箇所ごとに、実測に基づいて。

これが、本書がしきい値の手動調整に一章しか割かない理由です。同じ目的をより正確に達成する方法が、第 5 部にあります。

11.8 ハンズオン

  1. LogLab の 追加のオプション に -mllvm -inline-threshold=0 を書いてビルドし、実行時間とチェックサムを記録する
  2. チェックサムが 0x0e8685105a08f105 のまま変わらないことを確認する（変わったらどこかがおかしい）
  3. 値を 50、1000、5000 と変えて同じことを繰り返す
  4. それぞれの .exe のサイズも記録する
  5. -mllvm -inline-threshold=0 のときに /clang:-Rpass-missed=inline を併用し、too costly to inline (cost=..., threshold=0) が大量に出ることを確認する
  6. すべて消して /O2 の素の状態に戻す

3 番で「上げても速くならない」ことを自分の目で確認しておくのが、この章のいちばんの収穫です。

11.9 まとめ

  • インライン化の価値は呼び出しコストの削減ではなく、定数伝播・デッドコード削除・ベクトル化の連鎖を開くこと
  • 判定は cost ≤ threshold。どちらも呼び出し箇所ごとに決まる
  • cost は負にもなる。展開したほうが小さくなる場合があるため
  • 実測では、既定のしきい値がほぼ最適だった。上げても得しない、下げると明確に損をする
  • インライン化しないほうがコードは大きくなる
  • inline キーワードは ODR のための言語機能。展開の強制は __forceinline
  • しきい値の手動調整は「全箇所に一律」「判断材料が無い」という原理的な弱点を持つ。それを解決するのが PGO

第 2 部を終えて

ここまでで、最適化の中身を観察する道具が揃いました。オプションの正しい渡し方（第 6 章）、パイプラインの構造（第 7 章）、生成コードの読み方（第 8 章）、コンパイラ自身による説明（第 9・10 章）、そしてインライン化の判断モデル（第 11 章）。

手元には三つのベースラインがあるはずです。baseline_O2_calls.txt（call 命令の一覧）、records_O2.txt（最適化レコードの集計）、そして LogLab の実行時間とチェックサム。これらが、第 4 部以降で「何が変わったか」を語るための基準になります。

ただし、まだ一つ足りません。時間を正しく測る方法です。ここまで「実行時間」と気軽に書いてきましたが、1 回の実行時間を比べて「速くなった」と言うのは、第 1 章で戒めたことそのものです。第 3 部では、Windows 上で信頼できる計測を行うための道具と作法を扱います。

次章から第 3 部に入ります。まず PIX for Windows を導入し、LogLab のどこに時間が費やされているのかを実際に見ます。「parse_line が重いはずだ」という予想が正しいのかどうか、ここで初めて確かめることになります。
