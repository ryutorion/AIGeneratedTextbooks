第 21 章

-fwhole-program-vtables
— 仮想関数のデバーチャライズ

第 8 章の逆アセンブルに call qword ptr [rax + 0x10] という行がありました。仮想関数テーブル経由の間接呼び出しです。LTO はこれを直接呼び出しに変えられる場合があります。ただし条件は厳しく、LogLab では成立しません。その理由を理解することが、この章の本題です。

この章のゴール

  • 間接呼び出しが最適化を妨げる理由を理解する
  • デバーチャライズが成立する条件を知る
  • -fwhole-program-vtables を有効にし、効果を測定する
  • 効かなかったときに、なぜ効かないのかを説明できるようになる

21.1 間接呼び出しの何が問題か

仮想関数の呼び出しは、機械語では次のようになります。

mov     rdi, qword ptr [r13]        ; オブジェクトのポインタ
mov     rax, qword ptr [rdi]        ; vtable のアドレスを取り出す
mov     rsi, r12                    ; 引数
call    qword ptr [rax + 0x10]      ; vtable の 3 番目のエントリを呼ぶ

コスト自体は数命令ですが、本当の損失はそこではありません。

コンパイラは、この call がどこへ行くのかを知りません。 第 11 章で見たインライン化の連鎖——定数伝播、デッドコード削除、ベクトル化——は、呼び先が分からなければ一つも始まりません。第 9 章のリマークでいう indirect call がこれです。

21.2 デバーチャライズの条件

間接呼び出しを直接呼び出しに変えることをデバーチャライズと呼びます。成立するのは、コンパイラが呼び先を一つに絞れるときです。そのためには二つのことが必要です。

必要なこと誰が担うか
ある基底クラスの派生クラスが全部で何個あるかを知るLTO（プログラム全体が見えるから）
プログラムが閉じていると保証する（外から新しい派生クラスが来ない）リンカの設定と、DLL の有無

一つ目が -fwhole-program-vtables の役割です。仮想関数テーブルに関する情報を IR に載せ、LTO の段階で「この基底クラスの実装はこれで全部だ」と結論できるようにします。

21.3 有効にする

構成プロパティ > C/C++ > コマンド ライン > 追加のオプション

/clang:-flto  /clang:-fwhole-program-vtables
LTO が前提です

-fwhole-program-vtables は単独では機能しません。プログラム全体を見る仕組みが無ければ、「派生クラスはこれで全部」と結論できないからです。-flto または -flto=thin と必ず併用してください。

21.4 実測 — 実装が一つのとき

最小の例で確かめます。基底クラス Sink と、その実装が一つだけあるプログラムです。

// iface.h
struct Sink {
    virtual ~Sink() = default;
    virtual int put(int v) = 0;
};
Sink* make_sink();

// impl.cpp
namespace {
struct CountSink final : Sink {
    int n = 0;
    int put(int v) override { n += v; return n; }
};
}
Sink* make_sink() { static CountSink s; return &s; }

// main.cpp
Sink* s = make_sink();
int r = 0;
for (int i = 0; i < 1000; ++i) r = s->put(i);

ビルド方法を変えながら、間接呼び出し（call qword ptr）の数を数えました。

ビルド間接呼び出しの数
LTO なし2
LTO のみ2
LTO + -fwhole-program-vtables2
LTO + -fwhole-program-vtables + リンカに「閉じている」と指示1

実測の一例

三行目に注目してください。-fwhole-program-vtables を付けただけでは変化がありません。 リンカが「このプログラムに外から派生クラスが追加されることはない」と認めて初めて、デバーチャライズが起きました。

プラットフォームによる違い

この「閉じている」保証の必要性は、動的リンクの仕組みに由来します。ELF（Linux など）では、実行時に共有ライブラリのシンボルが別の定義で置き換わりうるため、リンカに明示的に指示する必要があります（--lto-whole-program-visibility）。

Windows の PE/COFF にはこのシンボル置き換えの仕組みがありません。そのため lld-link には対応するオプションが用意されていません。実際にどう振る舞うかは、必ずご自身の環境で確認してください。 確認方法は単純です。

llvm-objdump -d --x86-asm-syntax=intel --no-show-raw-insn ClangOptLab.exe ^
  | findstr /C:"call    qword ptr" | find /c /v ""

この数がオプションの有無で減れば、効いています。

21.5 実測 — 実装が二つになると

同じプログラムに、派生クラスをもう一つ足しました。

struct XorSink final : Sink { int n = 0; int put(int v) override { n ^= v; return n; } };
実装の数間接呼び出しの数
1 個1（デバーチャライズされた）
2 個2（変化なし）

実装が二つになった瞬間、効果が消えました。呼び先が一つに絞れないからです。

21.6 LogLab では効きません

ここで LogLab に戻ります。Filter の実装は三つありました。

class LevelFilter final : public Filter { ... };
class ComponentFilter final : public Filter { ... };
class MessageFilter final : public Filter { ... };

実際に測っても、変化はありませんでした。

ビルド間接呼び出しloglab:: への call.text
Full LTO867,911 B
Full LTO + -fwhole-program-vtables867,911 B

実測の一例。バイト単位まで完全に同一でした

これが本章でいちばん重要な結果です

-fwhole-program-vtables は「仮想関数呼び出しを速くするオプション」ではありません。実装が事実上一つしかない抽象化を、抽象化のコストごと消し去るオプションです。

だからこそ効く場面は限られます。逆に言えば、効く場面ははっきりしています。「将来の拡張のために」インターフェースを切ったものの、実装が一つしかないまま数年が経った——そういうクラスが、このオプションの本命です。

21.7 それでも間接呼び出しを減らしたいなら

デバーチャライズが成立しない場合の選択肢を挙げておきます。

手段内容本書での扱い
final を付けるクラスや仮想関数に final を付けると、そのポインタ型経由の呼び出しは LTO 無しでもデバーチャライズできる。ただし基底クラスのポインタ経由では効かない本章
ポインタの型を絞るSink* ではなく CountSink* として持てば、そもそも仮想呼び出しにならない設計の問題
間接呼び出しの投機的展開プロファイルで「この間接呼び出しの 95% は LevelFilter::accept に行く」と分かれば、その場合の分岐を作って展開できる第 32 章（PGO）
仮想関数を使わない設計にするテンプレート、std::variant など本書の範囲外

三つ目に注目してください。LogLab のように実装が複数あるが、実行時の分布が偏っているケースこそ、PGO が力を発揮する場所です。-fwhole-program-vtables が「静的に一つに絞れるか」を問うのに対し、PGO は「実際にはどこへ行っているか」を問います。第 5 部で LogLab の Filter::accept() に戻ってきます。

final について補足

final は無料で付けられる有用な指定ですが、万能ではありません。LogLab の三つのフィルタはすべて final が付いていますが、呼び出しは Filter* 経由なので効果がありません。final が効くのは「CountSink* p; p->put(x);」のように、派生クラスの型が分かっている場合です。

21.8 DLL があると成立しません

もう一つの前提「プログラムが閉じている」は、DLL を使うと崩れます。DLL からエクスポートされたクラスは、どこから派生されるか分かりません。逆に、実行ファイル側のクラスが DLL 側から派生される可能性もあります。

この話は次章で扱います。

21.9 ハンズオン

  1. 追加のオプションに /clang:-fwhole-program-vtables を足してリビルドする
  2. 間接呼び出し（call qword ptr）の数を、付ける前と後で数える
  3. .text のサイズも比べる
  4. 変化がないことを確認する（LogLab では変わりません）
  5. 21.4 節の Sink の例を自分で作り、実装が一つのときの挙動を確かめる
  6. 実装を二つに増やして、効果が消えることを確かめる

21.10 まとめ

  • 間接呼び出しの真のコストは命令数ではなく、インライン化の連鎖が始まらないこと
  • デバーチャライズには「派生クラスの全体像」と「プログラムが閉じていること」の両方が要る
  • -fwhole-program-vtables は LTO との併用が前提。単独では機能しない
  • 実測では、実装が 1 個のときだけデバーチャライズされた。2 個になると効果が消える
  • LogLab は Filter の実装が 3 個あるため、バイト単位で何も変わらなかった
  • このオプションの本命は「実装が一つしかない抽象化」を消すこと
  • 実装が複数あって分布が偏っている場合は、PGO の出番（第 32 章）

次章では、LTO と静的ライブラリ・DLL の関係を扱います。ビットコードを含む .lib は作れるのか、LTO はライブラリの境界を越えられるのか、DLL があると何ができなくなるのか。実際のプロジェクトで LTO を導入するときに、必ずぶつかる問題です。
