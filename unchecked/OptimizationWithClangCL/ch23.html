第 23 章

LTO の代償
— デバッグ情報・ビルド時間・メモリと、失敗時の切り分け

ここまで LTO の効果を見てきました。この章では支払うものを整理します。導入するかどうかは、効果と代償を並べて初めて判断できます。あわせて「LTO を入れたら壊れた」ときの切り分け方も扱います。

この章のゴール

  • ビルド時間がどこに移動するのかを知る
  • 増分ビルドとデバッグへの影響を理解する
  • LTO 特有の失敗パターンと切り分け手順を身につける
  • 導入するかどうかの判断基準を持つ

23.1 ビルド時間は「移動する」

LogLab（5 翻訳単位）で、コンパイルとリンクの時間を分けて測りました。

ビルドコンパイル合計リンク.obj の合計サイズ
LTO なし5.07 秒0.06 秒568 KB
ThinLTO4.87 秒0.24 秒（4 倍）600 KB
Full LTO4.81 秒0.34 秒（5.7 倍）612 KB

実測の一例

興味深いのはコンパイルがわずかに速くなっていることです。LTO ではコンパイル時に機械語を生成しないので、その分の仕事が減っています。減った仕事はリンクに移動し、そこで数倍に膨らんでいます。

LogLab は小さいので絶対値はどうでもよい水準ですが、比率は規模に応じて効いてきます。数千の翻訳単位を持つプロジェクトでは、リンクだけで数分から数十分になることも珍しくありません。

23.1.1 メモリ

Full LTO の最大の弱点はメモリです。全ビットコードを一つのモジュールに統合するため、必要なメモリはプロジェクトの規模にほぼ比例します。大規模プロジェクトで「リンカが落ちる」「マシンがスワップし始める」という報告の多くは、これが原因です。

ThinLTO はモジュール単位で処理するのでメモリ使用量を抑えられます。大規模プロジェクトで LTO を使うなら、選択肢は実質 ThinLTO 一択です。

23.2 増分ビルドが効かない

第 19 章でも触れましたが、改めて整理します。

LTO なしLTO あり
1 ファイル変更その .obj のみ再生成 → 軽いリンクその .obj のみ再生成 → 全体を再最適化
体感数秒プロジェクト全体の規模に比例

対策は二つです。

  • ThinLTO キャッシュ（第 19 章）。変更していないモジュールのバックエンド処理を省ける
  • 構成を分ける。日常の開発は LTO なし、性能検証とリリースだけ LTO（第 39 章）

23.3 デバッグへの影響

スタックトレースから関数が消える

翻訳単位をまたいでインライン化されるので、クラッシュダンプのスタックに parse_line が現れず、main だけになる、ということが起こります。第 14 章で扱ったインラインサイト情報（S_INLINESITE）は LTO でも生成されるので、対応したツールなら展開できます。

ステップ実行がさらに飛ぶ

もともと最適化されたコードのステップ実行は行が飛びますが、LTO ではその範囲が翻訳単位を越えます。第 8 章で書いたとおり、逆アセンブルウィンドウで命令単位に追うのが確実です。

PDB は普通に作られる

第 14 章のとおり、PDB を作るのは lld-link です。LTO でもこの流れは変わりません。/DEBUG を付けていれば PDB は生成され、プロファイラもシンボルを解決できます。

23.4 LTO 特有の失敗

23.4.1 リンクが通らない

症状原因と対処
オブジェクトファイルとして読めないと言われるリンカが link.exe になっている。UseLldLink を確認（第 3 章）
未定義シンボルが急に出るLTO によって未使用と判断され削除されたコードが、実は必要だった。インラインアセンブラや、リンカスクリプト経由でしか参照されないシンボルで起きる
リンクが終わらない・メモリを使い果たすFull LTO の規模的な限界。ThinLTO に切り替える

23.4.2 動作が変わる — チェックサムが命綱

LTO は未定義動作を顕在化させます

LTO はプログラムの意味を変えません。意味が定義されている限りは。 未定義動作を含むコードは、最適化の条件が変わると挙動が変わります。LTO は最適化の視野を大きく広げるので、それまで表面化していなかった問題が一気に出ることがあります。

典型的なのは、初期化されていない変数、寿命の切れたオブジェクトへの参照、strict aliasing 違反、そしてODR 違反です。

ODR 違反は警告なしに通ります

実際に試してみました。同じ名前の struct を、二つの翻訳単位で異なるメンバで定義した——明白な ODR 違反のプログラムです。

// a.cpp
struct Cfg { int a; int b; };

// b.cpp
struct Cfg { int a; int b; int c; };   // メンバが違う

Full LTO でビルドしたところ、警告もエラーも出ず、リンクは成功しました。

LTO は ODR 違反を検出する仕組みではありません。両方の定義が IR に載り、どちらかが採用され、静かに壊れたプログラムができあがります。しかも「壊れ方」は最適化の判断次第で変わるので、再現性が低い厄介なバグになります。

だからチェックサムを用意しました

第 4 章で LogLab にチェックサムを組み込んだのは、この瞬間のためです。LTO を有効にしてチェックサムが変わったら、それは LTO のバグではなく、あなたのコードに未定義動作がある合図だと考えるのが妥当です。

最適化オプションを追加するたびに結果を検証する仕組みがあるかどうか。それが、LTO を安心して使えるかどうかを分けます。

23.4.3 切り分けの手順

  1. LTO を外して直るかを確認する。直らなければ LTO は無関係
  2. Full LTO なら ThinLTO で、ThinLTO なら Full LTO で試す。片方だけで起きるなら最適化の深さの問題
  3. /opt:lldlto=1 や 0 でリンク時の最適化レベルを下げてみる
  4. 一部のファイルだけ LTO を外して範囲を狭める（ビットコードとネイティブは混在できる、第 22 章）
  5. サニタイザ（UBSan / ASan）を LTO 無しでかけて、未定義動作を探す

23.4.4 /lldsavetemps で途中を見る

リンク時に何が起きているのかを直接見たいときは、中間結果を保存できます。

/lldsavetemps

ThinLTO の場合、モジュールごとに次のファイルが出力されます。

tokenizer.obj.0.preopt.bc        <- 入力のビットコード
tokenizer.obj.1.promote.bc       <- シンボルの昇格
tokenizer.obj.2.internalize.bc   <- 内部化（外から見えないシンボルを internal に）
tokenizer.obj.3.import.bc        <- 他モジュールからの取り込み後
tokenizer.obj.4.opt.bc           <- 最適化後
tokenizer.obj.5.precodegen.bc    <- 機械語生成の直前

第 18 章で説明した ThinLTO の三段階が、そのままファイル名になっています。llvm-dis でテキストの IR に戻せば、どの段階で何が起きたかを追えます。

llvm-dis tokenizer.obj.3.import.bc -o import.ll
llvm-dis tokenizer.obj.4.opt.bc    -o opt.ll

3.import と 4.opt を比べれば、リンク時の最適化が何をしたかが分かります。深追いする場面は多くありませんが、「取り込まれているはずの関数が入っていない」といった疑いを確かめるときには決定的な手段になります。

23.5 導入するかどうかの判断

状況判断
翻訳単位が多く、小さな関数を跨いで呼び合う試す価値が大きい
ホットな処理が一つの翻訳単位に閉じている効果は限定的（LogLab がこれ）
大規模で、リンク時間が許容できるThinLTO ＋ キャッシュ
中小規模で、最後の一押しが欲しいFull LTO も選択肢
DLL 境界にホットな処理があるLTO の前に構成の見直し（第 22 章）
結果を検証する手段が無いまずそれを作る。 話はそれから
最後の行が本書の立場です

チェックサムでも、回帰テストでも、出力の比較でも構いません。「最適化オプションを変えても結果が同じ」を機械的に確認できる仕組みが無いまま LTO を入れるのは、勧められません。効果が測れないだけでなく、壊れたことにも気づけないからです。

23.6 ハンズオン

  1. LogLab のコンパイル時間とリンク時間を、LTO なし／ThinLTO／Full LTO で測る
  2. リンカーの追加のオプションに /lldsavetemps を設定してリビルドする
  3. 出力された .bc ファイルの名前を眺め、第 18 章の三段階と対応づける
  4. llvm-dis で 3.import.bc と 4.opt.bc をテキストにして、main の中身を比べる
  5. /lldsavetemps は外しておく（ファイルが大量に出るため）

23.7 まとめ

  • LTO はビルド時間をコンパイルからリンクへ移す。実測ではリンクが 4〜5.7 倍になった
  • Full LTO のメモリ使用量は規模に比例する。大規模プロジェクトでは ThinLTO 一択
  • 増分ビルドのコストが上がる。ThinLTO キャッシュと構成の分離で緩和する
  • PDB は普通に生成される。ただしスタックトレースやステップ実行は読みにくくなる
  • LTO は ODR 違反を検出しない。 警告なしにリンクが通り、静かに壊れる
  • 結果が変わったら、LTO のバグではなく自分のコードの未定義動作を疑う
  • 切り分けは「LTO を外す → 方式を変える → レベルを下げる → 範囲を狭める → サニタイザ」の順
  • /lldsavetemps でリンク時最適化の各段階を .bc として取り出せる

次章で第 4 部を締めくくります。 MSVC にも /GL と /LTCG という同じ目的の機能があります。何が同じで何が違うのか。既存の MSVC プロジェクトを ClangCL に移すとき、設定をどう読み替えればよいのか。そして、PGO との組み合わせ方がどう違うのか——これは第 5 部への橋渡しになります。
