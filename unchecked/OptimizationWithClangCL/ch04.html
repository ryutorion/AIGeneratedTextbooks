第 4 章

題材アプリの用意
— 最適化の効果が見えるプログラムを作る

Hello World に LTO を掛けても何も起きません。最適化の効果を観察するには、それにふさわしい題材が必要です。この章では「なぜその条件が必要なのか」を確認しながら、本書を最後まで使い続けるサンプルアプリを作ります。

この章のゴール

  • 最適化の題材が満たすべき六つの条件を理解する
  • 題材アプリ「LogLab」を作り、ビルドして動かす
  • ベースラインの実行時間とチェックサムを記録する
  • ベンチマークが最適化に消されないための書き方を知る

4.1 良い題材が満たすべき六つの条件

最適化の実験用プログラムには、満たすべき条件があります。どれか一つでも欠けると、本書の後半で「何も起きない」という壁にぶつかります。

#条件欠けるとどうなるか効いてくる章
1実行時間が十分に長い（数百ミリ秒以上）計測ノイズに埋もれて差が読めない第 15 章
2複数の翻訳単位に分かれている翻訳単位の壁が無く、LTO が何もすることがない第 4 部
3間接呼び出し（仮想関数）があるデバーチャライズや間接呼び出しの最適化を観察できない第 21・32 章
4分岐の成立率に偏りがあるPGO が教える情報が静的な推測と変わらない第 5 部
5決定的である（毎回同じ結果）実行ごとに結果が変わり、比較が成立しない全章
6結果を検証できる最適化でコードが壊れても気づけない全章

特に 5 と 6 は軽視されがちですが、後になって効いてきます。最適化オプションを付けたら結果が変わった、というのは実際に起こります。原因はコンパイラのバグかもしれませんし、そもそも元のコードに未定義動作があってオプション次第で挙動が変わっただけかもしれません。いずれにせよ、気づける仕組みが無ければ気づけません。

4.2 題材 — 簡易ログ解析パイプライン「LogLab」

本書の題材は、テキストのログ行を解析して集計するプログラムです。実務でよく書くコードの形をしていて、上の六条件をすべて満たします。

処理の流れはこうです。まず疑似ログを生成し（この部分は計測対象外）、各行をパースして構造体に直し、いくつかのフィルタを通し、通ったものを集計する。集計結果はチェックサムとして出力します。

4.2.1 各ファイルの役割

ファイル役割最適化の観点での意味
include/loglab.h共通の型と宣言実装はヘッダに置かない（＝翻訳単位の壁を作る）
src/generator.cpp決定的な疑似ログの生成レベルの出現比率を意図的に偏らせてある
src/tokenizer.cpp行のパース最もホットな処理。小さな関数の呼び出しが多い
src/filter.cppフィルタ群（仮想関数）間接呼び出しの発生源
src/stats.cpp集計とチェックサム1000 行に 3 行程度しか通らない重い経路を含む
src/main.cpp計測ループと結果出力生成処理を計測区間の外に出してある
実装をヘッダに置かない理由

C++ では、ヘッダに書いた関数はどの翻訳単位からもインライン化できます。もし parse_line() をヘッダに書いてしまうと、LTO を使わなくてもインライン化されてしまい、第 4 部で「LTO で何が変わったか」を観察できません。本書の題材は意図的に、実装を .cpp 側に置いています。

4.3.2 src/generator.cpp

#include "loglab.h"

#include <array>
#include <charconv>

namespace loglab {
namespace {

// 決定的な擬似乱数（xorshift64*）。環境によらず同じ列を生成する。
class Rng {
public:
    explicit Rng(std::uint64_t seed) : s_(seed ? seed : 0x9E3779B97F4A7C15ull) {}

    std::uint64_t next()
    {
        s_ ^= s_ >> 12;
        s_ ^= s_ << 25;
        s_ ^= s_ >> 27;
        return s_ * 0x2545F4914F6CDD1Dull;
    }

    std::uint32_t below(std::uint32_t n) { return static_cast<std::uint32_t>(next() % n); }

private:
    std::uint64_t s_;
};

constexpr std::array<const char*, 5> kLevelNames{
    "TRACE", "DEBUG", "INFO", "WARN", "ERROR"
};

constexpr std::array<const char*, 6> kComponents{
    "net.socket", "net.http", "io.file", "io.cache", "gfx.device", "core.init"
};

constexpr std::array<const char*, 6> kMessages{
    "connection established", "read completed", "cache entry evicted",
    "handshake retried", "buffer resized", "device lost"
};

// レベルの出現比率を偏らせる。ERROR は 1000 行に 3 行程度。
Level pick_level(Rng& rng)
{
    const std::uint32_t r = rng.below(1000);
    if (r < 600) return Level::Info;
    if (r < 850) return Level::Debug;
    if (r < 960) return Level::Trace;
    if (r < 997) return Level::Warn;
    return Level::Error;
}

void append_uint(std::string& s, std::uint64_t v)
{
    char buf[24];
    auto [ptr, ec] = std::to_chars(buf, buf + sizeof(buf), v);
    s.append(buf, ptr);
}

} // namespace

std::vector<std::string> generate_lines(std::size_t count, std::uint64_t seed)
{
    Rng rng(seed);

    std::vector<std::string> lines;
    lines.reserve(count);

    std::uint64_t ts = 1'700'000'000'000ull;

    for (std::size_t i = 0; i < count; ++i) {
        ts += 1 + rng.below(7);

        const Level level = pick_level(rng);
        const char* comp  = kComponents[rng.below(kComponents.size())];
        const char* msg   = kMessages[rng.below(kMessages.size())];

        // ERROR のときだけ 0 以外のコードが入る
        const std::uint32_t code =
            (level == Level::Error) ? (1000 + rng.below(9000)) : 0;

        std::string line;
        line.reserve(80);
        append_uint(line, ts);
        line.push_back(' ');
        line.append(kLevelNames[static_cast<std::size_t>(level)]);
        line.push_back(' ');
        line.append(comp);
        line.push_back(' ');
        line.append(msg);
        line.append(" code=");
        append_uint(line, code);

        lines.push_back(std::move(line));
    }

    return lines;
}

} // namespace loglab

4.3.3 src/tokenizer.cpp

#include "loglab.h"

namespace loglab {
namespace {

// 空白で区切られた次のフィールドを切り出す。pos は呼び出しのたびに前進する。
std::string_view next_field(std::string_view s, std::size_t& pos)
{
    while (pos < s.size() && s[pos] == ' ') {
        ++pos;
    }
    const std::size_t begin = pos;
    while (pos < s.size() && s[pos] != ' ') {
        ++pos;
    }
    return s.substr(begin, pos - begin);
}

bool parse_uint(std::string_view s, std::uint64_t& out)
{
    if (s.empty()) {
        return false;
    }
    std::uint64_t v = 0;
    for (const char c : s) {
        if (c < '0' || c > '9') {
            return false;
        }
        v = v * 10 + static_cast<std::uint64_t>(c - '0');
    }
    out = v;
    return true;
}

bool parse_level(std::string_view s, Level& out)
{
    // 出現頻度の高い順に比較する
    if (s == "INFO")  { out = Level::Info;  return true; }
    if (s == "DEBUG") { out = Level::Debug; return true; }
    if (s == "TRACE") { out = Level::Trace; return true; }
    if (s == "WARN")  { out = Level::Warn;  return true; }
    if (s == "ERROR") { out = Level::Error; return true; }
    return false;
}

} // namespace

bool parse_line(std::string_view line, Record& out)
{
    std::size_t pos = 0;

    if (!parse_uint(next_field(line, pos), out.timestamp)) {
        return false;
    }
    if (!parse_level(next_field(line, pos), out.level)) {
        return false;
    }

    out.component = next_field(line, pos);
    if (out.component.empty()) {
        return false;
    }

    // " code=" が現れるまでがメッセージ
    const std::size_t msg_begin = pos + 1;
    const std::size_t eq = line.find(" code=", pos);
    if (eq == std::string_view::npos || msg_begin > eq) {
        return false;
    }
    out.message = line.substr(msg_begin, eq - msg_begin);

    std::uint64_t code = 0;
    if (!parse_uint(line.substr(eq + 6), code)) {
        return false;
    }
    out.code = static_cast<std::uint32_t>(code);

    return true;
}

} // namespace loglab

リスト 4-3　src/tokenizer.cpp

ここが最適化の観察ポイントになります

next_field()・parse_uint()・parse_level() は無名名前空間にある小さな関数で、同じ翻訳単位の parse_line() から呼ばれています。つまり /O2 でもインライン化される可能性が高い。一方 parse_line() 自身は main.cpp から呼ばれるため、翻訳単位の壁を越えます。この壁がどうなるかが第 20 章の主題です。

4.3.4 src/filter.cpp

#include "loglab.h"

namespace loglab {
namespace {

// ほとんどの行を通すフィルタ
class LevelFilter final : public Filter {
public:
    bool accept(const Record& r) const override
    {
        return static_cast<int>(r.level) >= static_cast<int>(Level::Debug);
    }
    const char* name() const override { return "LevelFilter"; }
};

// 半分ほどを落とすフィルタ
class ComponentFilter final : public Filter {
public:
    bool accept(const Record& r) const override
    {
        return r.component.starts_with("net.") || r.component.starts_with("io.");
    }
    const char* name() const override { return "ComponentFilter"; }
};

// ほとんど何も落とさないフィルタ
class MessageFilter final : public Filter {
public:
    bool accept(const Record& r) const override
    {
        return !r.message.empty() && r.message.find("lost") == std::string_view::npos;
    }
    const char* name() const override { return "MessageFilter"; }
};

} // namespace

std::vector<std::unique_ptr<Filter>> make_filters()
{
    std::vector<std::unique_ptr<Filter>> v;
    v.push_back(std::make_unique<LevelFilter>());
    v.push_back(std::make_unique<ComponentFilter>());
    v.push_back(std::make_unique<MessageFilter>());
    return v;
}

} // namespace loglab

リスト 4-4　src/filter.cpp

三つのフィルタは、それぞれ通過率が大きく違います。この差が、PGO を導入したときの間接呼び出し最適化に効いてきます。また、派生クラスがすべてこの .cpp の無名名前空間に閉じている点も重要です。プログラム全体を見渡せれば「Filter の実装はこの三つしかない」と結論できるからです。これができるのが LTO です（第 21 章）。

4.3.5 src/stats.cpp

#include "loglab.h"

#include <cstdio>

namespace loglab {
namespace {

constexpr std::uint64_t kFnvPrime = 1099511628211ull;

inline std::uint64_t mix(std::uint64_t h, std::uint64_t v)
{
    h ^= v;
    h *= kFnvPrime;
    return h;
}

} // namespace

void Stats::add(const Record& r)
{
    ++accepted_;
    ++per_level_[static_cast<std::size_t>(r.level)];

    hash_ = mix(hash_, r.timestamp);
    hash_ = mix(hash_, static_cast<std::uint64_t>(r.level));
    hash_ = mix(hash_, r.component.size());
    hash_ = mix(hash_, r.message.size());
    hash_ = mix(hash_, r.code);

    // 1000 行に 3 行程度しか通らない経路。
    // ここに [[unlikely]] は意図的に書かない（第 32 章で PGO に見つけさせる）。
    if (r.level == Level::Error) {
        handle_error(r);
    }
}

void Stats::handle_error(const Record& r)
{
    // 「稀だが重い」処理の代役。文字ごとに丁寧に走査する。
    std::uint64_t h = hash_;
    for (const char c : r.component) {
        h = mix(h, static_cast<std::uint64_t>(static_cast<unsigned char>(c)));
    }
    for (const char c : r.message) {
        h = mix(h, static_cast<std::uint64_t>(static_cast<unsigned char>(c)));
    }
    hash_ = mix(h, r.code);
    error_bytes_ += r.component.size() + r.message.size();
}

void Stats::report() const
{
    static const char* const names[] = { "TRACE", "DEBUG", "INFO", "WARN", "ERROR" };
    for (std::size_t i = 0; i < 5; ++i) {
        std::printf("  %-5s : %llu\n", names[i],
                    static_cast<unsigned long long>(per_level_[i]));
    }
    std::printf("  error bytes : %llu\n",
                static_cast<unsigned long long>(error_bytes_));
}

} // namespace loglab

リスト 4-5　src/stats.cpp

[[unlikely]] を書かない理由

if (r.level == Level::Error) は 1000 回に 3 回しか成立しません。C++20 の [[unlikely]] 属性を書けば、コンパイラにその旨を伝えられます。しかしここではあえて書きません。書かずにおくことで、第 32 章で「PGO がこの偏りを自力で発見し、handle_error() をコールドなコードとして配置し直す」様子を観察できるからです。手で属性を書く方法と PGO に任せる方法の比較も、その章で扱います。

4.3.6 src/main.cpp

#include "loglab.h"

#include <charconv>
#include <chrono>
#include <cstdio>

namespace {

std::size_t arg_or(int argc, char** argv, int index, std::size_t fallback)
{
    if (index >= argc) {
        return fallback;
    }
    std::size_t v = fallback;
    const std::string_view s{argv[index]};
    const auto [ptr, ec] = std::from_chars(s.data(), s.data() + s.size(), v);
    return (ec == std::errc{}) ? v : fallback;
}

} // namespace

int main(int argc, char** argv)
{
    const std::size_t line_count = arg_or(argc, argv, 1, 200'000);
    const std::size_t iterations = arg_or(argc, argv, 2, 50);

    // 入力の生成は計測対象に含めない
    const std::vector<std::string> lines = loglab::generate_lines(line_count, 20260910ull);
    const std::vector<std::unique_ptr<loglab::Filter>> filters = loglab::make_filters();

    loglab::Stats stats;

    const auto begin = std::chrono::steady_clock::now();

    for (std::size_t it = 0; it < iterations; ++it) {
        for (const std::string& line : lines) {
            loglab::Record rec;
            if (!loglab::parse_line(line, rec)) {
                continue;
            }

            bool accepted = true;
            for (const auto& f : filters) {
                if (!f->accept(rec)) {
                    accepted = false;
                    break;
                }
            }
            if (accepted) {
                stats.add(rec);
            }
        }
    }

    const auto end = std::chrono::steady_clock::now();
    const double ms = std::chrono::duration<double, std::milli>(end - begin).count();

    std::printf("lines      : %llu x %llu iterations\n",
                static_cast<unsigned long long>(line_count),
                static_cast<unsigned long long>(iterations));
    std::printf("accepted   : %llu\n",
                static_cast<unsigned long long>(stats.accepted()));
    std::printf("checksum   : 0x%016llx\n",
                static_cast<unsigned long long>(stats.checksum()));
    std::printf("elapsed    : %.1f ms\n", ms);
    stats.report();

    return 0;
}

4.5 ベースラインを取る

Release / x64 でビルドし、実行します。Visual Studio から実行するとコンソールがすぐ閉じるので、Developer Command Prompt から直接起動するほうが確実です。

cd x64\Release
ClangOptLab.exe

次のような出力になります。

lines      : 200000 x 50 iterations
accepted   : 4941900
checksum   : 0x0e8685105a08f105
elapsed    : 812.4 ms
  TRACE : 0
  DEBUG : 1398650
  INFO  : 3320500
  WARN  : 205550
  ERROR : 17200
  error bytes : 443400

実行結果の一例。elapsed は環境によって大きく変わります

確認すべき点が三つあります。

  1. checksum と accepted は、あなたの環境でも上とまったく同じ値になるはずです。 疑似乱数のシードを固定してあるためです。違う値が出たら、コードの写し間違いを疑ってください
  2. TRACE が 0 なのは正常です。LevelFilter が Debug 未満を落としているためです
  3. elapsed が 100 ミリ秒を大きく下回る場合は、第 2 引数で反復回数を増やしてください（例：ClangOptLab.exe 200000 200）。逆に数秒かかりすぎる場合は減らします。500 ミリ秒から 2 秒の範囲に収めておくと、以降の章で扱いやすくなります
ベースラインを記録しておく

この時点の checksum と elapsed をメモに残してください。checksum は「最適化でプログラムが壊れていないか」の判定に、elapsed は「何と比べて速くなったのか」の基準に、それぞれ最後の章まで使い続けます。ただし elapsed は 1 回の実行では信頼できません。適切な取り方は第 15 章で扱います。ここでは「だいたいこのくらい」で十分です。

4.5.1 最適化が効いていることを確認する

念のため、最適化そのものが機能していることも見ておきましょう。プロパティで C/C++ > 最適化 > 最適化 を一時的に 無効 (/Od) にしてビルドし直し、実行してみてください。

実行時間は数倍に伸びるはずです。そして checksum は変わりません。この二つが同時に成立していることが、題材として正しく機能している証拠です。確認できたら /O2 に戻してください。

4.6 ベンチマークが最適化に消される問題

自作のベンチマークでよくある失敗が、測りたい処理をコンパイラに丸ごと削除されることです。次のコードを考えてみます。

const auto begin = std::chrono::steady_clock::now();
for (int i = 0; i < 1000000; ++i) {
    heavy_computation(i);       // 戻り値を誰も使っていない
}
const auto end = std::chrono::steady_clock::now();

heavy_computation() に副作用が無く、その定義がコンパイラから見えていれば、この呼び出しはループごと削除されます。結果は「0.0 ミリ秒」。「劇的に速くなった」わけではなく、何も実行されていないだけです。

LogLab では、次の三つでこれを防いでいます。

対策該当箇所
計算結果を必ず出力するchecksum を printf している。ハッシュ値は全レコードに依存するため、どのレコードの処理も省略できない
入力を実行時に決める行数と反復回数をコマンドライン引数から取る。コンパイル時に畳み込めない
計測対象外の処理を区間の外に出すgenerate_lines() を steady_clock の外で呼んでいる
LTO を入れると、この問題は厳しくなります

いまは parse_line() の実装が別の翻訳単位にあるため、main.cpp のコンパイル時点では「中で何をしているか分からない＝削除できない」という状態です。しかし第 4 部で LTO を有効にすると、コンパイラはプログラム全体を見渡せるようになります。LTO を入れた瞬間にベンチマークが消えて「無限に速く」なった、というのは実際に起こる事故です。結果を必ず使う、という原則は、LTO 導入後にこそ重要になります。

4.7 チェックリスト

  • include / src の 6 ファイルを配置し、プロジェクトに追加した
  • 追加のインクルードディレクトリに $(ProjectDir)include を設定した
  • Release / x64 でビルドが通る
  • checksum が 0x0e8685105a08f105、accepted が 4941900 になる
  • elapsed が 500 ミリ秒〜2 秒の範囲に収まるよう反復回数を調整した
  • /Od にすると遅くなり、checksum は変わらないことを確認した
  • ベースラインの数値をメモに残した

4.8 まとめ

  • 最適化の題材には六つの条件がある。特に「複数の翻訳単位」「間接呼び出し」「偏った分岐」は、LTO と PGO の効果を観察するための必須条件である
  • 実装をヘッダに置かないことで、翻訳単位の壁を意図的に作っている
  • チェックサムは、最適化でプログラムが壊れていないことを確かめるための命綱である
  • ベンチマークは結果を必ず使う。使わない計算は削除されうる。この危険は LTO を入れると増す
  • /Od と /O2 で「時間は変わるがチェックサムは変わらない」ことが、題材が正しく機能している証拠

次章では、本書で使う LLVM 付属ツール（llvm-profdata、llvm-cov、llvm-objdump など）が揃っているかを確認します。特に PGO で使う llvm-profdata は環境によって同梱されていないことがあり、そのときの対処が必要です。あわせて「なぜコンパイラとツールのバージョンを揃える必要があるのか」も扱います。ここまでで第 1 部は完了です。
