第 14 章

シンボル解決と PDB
— clang-cl の /Z7・/Zi とリンカ設定

プロファイラが関数名を表示できるかどうかは、PDB にかかっています。そして clang-cl の PDB の作られ方は、MSVC のそれとは違います。ここを知らないまま進むと、「なぜかシンボルが出ない」「別の関数の名前が表示される」という状況に必ず出会います。

この章のゴール

  • clang-cl における /Z7 と /Zi の関係を正しく理解する
  • PDB を作っているのが誰なのかを知る
  • llvm-pdbutil で PDB の中身を確認する
  • リンカ設定がシンボルを壊す仕組みを理解する
  • 最適化されたコードでシンボルに何が起きるかを知る

14.1 シンボルが無いとどうなるか

前章で Load Symbols を忘れた場合、WPA のスタックはこうなります。

ClangOptLab.exe!0x140001a3f     31.2%
ClangOptLab.exe!0x1400023c1     18.7%
ClangOptLab.exe!0x140001f04     12.4%

アドレスは分かりますが、それがどの関数かは分かりません。逆アセンブルと突き合わせれば手作業で辿れますが、実用的ではありません。PDB は、アドレスと関数名を対応づける辞書です。

14.2 clang-cl の /Zi は MSVC の /Zi ではない

MSVC には二つのデバッグ情報の形式があります。

MSVC のオプションMSVC での挙動
/Z7デバッグ情報を .obj の中に埋め込む。PDB は作らない
/Ziコンパイラが vc143.pdb のような中間 PDB を作り、そこにデバッグ情報を置く

clang-cl ではこの区別がありません。 実測で確認すると、/Z7 と /Zi はまったく同じ引数を生成します。

:: /Z7 でも /Zi でも、内部に渡るのは同じ
"-gno-column-info" "-gcodeview" "-debug-info-kind=constructor"

どちらの場合も、デバッグ情報は .obj の中の CodeView セクションに入ります。

llvm-readobj --sections tokenizer.obj

  Name: .debug$S      <- シンボル情報
  Name: .debug$T      <- 型情報

つまり clang-cl の /Zi は、実質的に /Z7 です。 コンパイラは PDB を一切作りません。

/Fd は無視されます

MSVC で中間 PDB のファイル名を指定する /Fd は、clang-cl でも受け付けられますが何も起こりません。実際に /Fd foo.pdb を指定してコンパイルしても、foo.pdb は生成されません。

第 3 章でプロパティページのコマンドラインに /Fd"x64\Release\vc143.pdb" が入っていたのを覚えているでしょうか。あれは MSBuild が MSVC 向けに生成しているもので、ClangCL では効果がありません。害もないので放置して構いません。

ではどちらを指定すべきか

どちらでも同じ結果になりますが、意味が正しいのは /Z7 です。/Zi を選ぶと「中間 PDB が作られる」という誤解が残ります。とはいえ Visual Studio のプロパティページの既定は /Zi であり、そのままでも動作に違いはありません。本書はどちらでも進められます。

14.3 PDB を作っているのはリンカ

では最終的な ClangOptLab.pdb は誰が作っているのか。リンカ（lld-link）です。

14.3.1 リンカ側の設定

構成プロパティ > リンカー > デバッグ > デバッグ情報の生成

設定lld-link での挙動
/DEBUG / /DEBUG:FULL完全な PDB を生成する。本書はこれ
/DEBUG:GHASH型のハッシュを使って PDB 生成を高速化する。結果の PDB は FULL と同等
/DEBUG:FASTLINK非対応。警告を出して FULL にフォールバックする
なしPDB が作られない。プロファイラでシンボルが出ない

/DEBUG:FASTLINK を指定すると、次の警告が出ます。

lld-link: warning: /debug:fastlink unsupported; using /debug:full

MSVC のプロジェクトを ClangCL に移行すると、この警告が出ることがあります。動作に支障はありませんが、リンク時間は FULL 相当になります。

14.4 PDB の中身を見る

llvm-pdbutil で PDB を検査できます。「PDB は本当に作られているのか」「自分の関数は入っているのか」を確かめる道具です。

llvm-pdbutil dump --summary ClangOptLab.pdb
                          Summary
============================================================
  Block Size: 4096
  Number of streams: 15
  Age: 1
  GUID: {C944909C-8F26-11EF-4C4C-44205044422E}
  Has Debug Info: true
  Has Types: true
  Has Globals: true
  Has Publics: true
  Is stripped: false

Has Debug Info と Has Publics が true であることを確認します。

コマンド用途
llvm-pdbutil dump --summaryPDB 全体の概要
llvm-pdbutil dump --modulesどの .obj が寄与しているか
llvm-pdbutil dump --publics公開シンボルの一覧とアドレス
llvm-pdbutil dump --symbols詳細なシンボルレコード
GUID と Age が一致していないと使われません

PDB は実行ファイルと GUID・Age で結び付けられています。.exe を作り直したら PDB も作り直されるので、古い PDB を新しい exe と組み合わせることはできません。プロファイラが「シンボルが見つからない」と言うとき、PDB が古いだけということがよくあります。トレースと PDB はセットで保存してください。

14.5 リンカ設定がシンボルを壊す — /OPT:ICF

ここが実務で最も厄介な落とし穴です。

/OPT:ICF（Identical COMDAT Folding）は、機械語が完全に一致する関数を一つにまとめる最適化です。コードサイズが減るので、Release 構成では既定で有効になっています。

しかし、まとめられた関数は同じアドレスを共有します。実際に確認してみましょう。中身が同一の関数を二つ用意し、リンクして PDB を覗きます。

extern "C" int f1(int x) { return x * 3 + 1; }
extern "C" int f2(int x) { return x * 3 + 1; }
:: /OPT:NOICF の場合
llvm-pdbutil dump --publics app.pdb

  S_PUB32 `f1`   addr = 0001:0000
  S_PUB32 `f2`   addr = 0001:0016    <- 別のアドレス

:: /OPT:ICF の場合
  S_PUB32 `f1`   addr = 0001:0000
  S_PUB32 `f2`   addr = 0001:0000    <- 同じアドレス

/OPT:ICF のとき、f1 と f2 はどちらも 0001:0000 にいます。プロファイラがこのアドレスでサンプルを拾っても、それが f1 だったのか f2 だったのかを区別する方法はありません。表示される名前は、たまたま先に見つかったほうです。

C++ ではこれが頻繁に起こります

テンプレートの実体化は、型が違っても機械語が同じになりがちです。std::vector<int*> と std::vector<char*> のメンバ関数は、ポインタのサイズが同じなら同一のコードになります。プロファイルに「なぜこの関数が」という名前が出てきたら、ICF を疑ってください。

プロファイルを取るときだけ /OPT:NOICF にする、という運用が有効です。

構成プロパティ > リンカー > 最適化 > COMDAT の折りたたみ → COMDAT の折りたたみを行わない (/OPT:NOICF)

ただし、これはコードサイズと配置を変えるので、性能そのものが変わりえます。最終的な性能測定は、本番と同じリンカ設定で行ってください。ICF を切るのはあくまで「どの関数が重いのかを特定する」段階の話です。

14.6 最適化されたコードのシンボル

14.6.1 インライン展開された関数

第 12 章で触れた「インライン化された関数はプロファイルに出てこない」問題ですが、情報自体は PDB に入っています。S_INLINESITE というレコードがそれです。

llvm-pdbutil dump --symbols ClangOptLab.pdb

  S_GPROC32  `main`
  S_INLINEES
  S_INLINESITE          <- ここに展開された関数の情報がある
  S_INLINESITE_END

これを解釈できるツールなら、インライン展開された関数を独立した行として表示できます。WPA や PIX はこれに対応していますが、表示上は元の関数の中に入れ子で現れるため、見落としやすいところです。「この関数が見当たらない」と思ったら、呼び出し元を展開してみてください。

14.6.2 フレームポインタとスタックウォーク

サンプリングプロファイラはコールスタックを辿る必要があります。その方法として、伝統的には rbp レジスタ（フレームポインタ）の連鎖を辿る方式がありました。最適化するとこのレジスタが汎用に使われてしまうため、「最適化するとスタックが辿れない」という問題が古くから知られています。

x64 の Windows では、この心配は基本的に不要です。 x64 の呼び出し規約は、すべての関数に巻き戻し情報（.pdata / .xdata セクション）を持つことを義務づけています。ETW のスタックウォークはこの情報を使うので、フレームポインタが無くてもスタックを辿れます。

それでも知っておくべき罠：/Oy- は効きません

MSVC では /Oy- が「フレームポインタを省略しない」という指示でした。clang-cl でも受け付けられますが、実際には何も起こりません。実測すると、内部には -mframe-pointer=none が渡り続けます。

本当にフレームポインタを残したい場合は、Clang 形式のオプションを使います。

/clang:-fno-omit-frame-pointer

こちらを指定すると、生成コードに実際にプロローグが現れます。

"?caller@@YAHH@Z":
.seh_proc "?caller@@YAHH@Z"
        push    rbp
        .seh_pushreg rbp
        mov     rbp, rsp
        .seh_setframe rbp, 0

通常は必要ありませんが、フレームポインタを前提とするサードパーティのプロファイラやクラッシュレポータを使う場合には効いてきます。「/Oy- を付けたのに直らない」という状況に陥ったら、この事実を思い出してください。

14.7 シンボルパスの設定

前章でも触れましたが、まとめておきます。

set _NT_SYMBOL_PATH=srv*C:\symbols*https://msdl.microsoft.com/download/symbols;C:\work\ClangOptLab\x64\Release
部分意味
srv*C:\symbols*https://...Microsoft のシンボルサーバから OS の PDB を取得し、C:\symbols にキャッシュする
;C:\work\...\x64\Release自分のプロジェクトの PDB があるフォルダ

OS 側のシンボルも入れておく理由は、スタックの根元が kernel32.dll や ntdll.dll だからです。これらが解決できないと、スタックツリーが途中で切れて読みにくくなります。

14.8 ハンズオン

  1. x64\Release\ClangOptLab.pdb が存在することを確認する
  2. llvm-pdbutil dump --summary で Has Debug Info: true を確認する
  3. llvm-pdbutil dump --modules で 5 つの .cpp がすべて含まれていることを確認する
  4. プロパティで /Fd の指定を変えても PDB のファイル名が変わらないことを確認する（clang-cl では無効なため）
  5. リンカーの COMDAT の折りたたみを /OPT:NOICF にしてリビルドし、.exe のサイズが変わることを確認する
  6. 前章のトレースを取り直し、シンボルが正しく出るか確認する

14.9 まとめ

  • clang-cl では /Zi と /Z7 が同じ。どちらもデバッグ情報を .obj の CodeView セクションに埋める。コンパイラは PDB を作らない
  • /Fd は受け付けられるが無効
  • PDB を作るのは lld-link の /DEBUG。/DEBUG:FASTLINK は非対応で FULL にフォールバックする
  • llvm-pdbutil で PDB の中身を検査できる。PDB と .exe は GUID で結び付いており、組み合わせを間違えると使われない
  • /OPT:ICF は同一の関数を同じアドレスにまとめる。プロファイルで別の関数名が表示される原因になる。調査中は /OPT:NOICF
  • インライン展開された関数の情報は S_INLINESITE として PDB に入っている
  • x64 Windows のスタックウォークは .pdata を使うのでフレームポインタは不要。/Oy- は clang-cl では効かず、必要なら /clang:-fno-omit-frame-pointer

次章では、第 3 部の締めくくりとして「時間の測り方」そのものを扱います。同じバイナリを 30 回走らせると実行時間が何パーセント揺れるのか、その揺れの中で「速くなった」と言うには何が必要なのか。実測データを添えて、本書で使う計測手順を確定させます。
