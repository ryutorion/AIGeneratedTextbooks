第 31 章

最適化ビルド
— -fprofile-use を適用する

三段階の最後です。集めたプロファイルをコンパイラに渡し、その結果を第 15 章の手順で測ります。そして本書で最も重要な計測上の教訓が、この章で出てきます——同じバイナリでも、マシンが変われば結論が変わりました。

この章のゴール

  • プロファイルを使って最適化ビルドを作る
  • 正しさを検証する
  • 効果を測定し、ノイズ床と比較する
  • その結果がハードウェアに依存することを知る
  • 三段階を一つのスクリプトにまとめる

31.1 オプション

構成プロパティ > C/C++ > コマンド ライン > 追加のオプション

/clang:-fprofile-use=C:\work\ClangOptLab\app.profdata

計装ビルドの /clang:-fprofile-generate は外してください。両方を同時に指定してはいけません。

相対パスとマクロ

MSBuild のマクロが使えるので、プロジェクトを移動しても壊れない書き方ができます。

/clang:-fprofile-use=$(ProjectDir)app.profdata

ただしパスに空白が含まれる場合は注意が必要です。うまくいかないときは、まず絶対パスで動くことを確認してから調整してください。

31.2 ビルドと検証

  1. 追加のオプションを /clang:-fprofile-use=... に変える
  2. /O2 はそのまま
  3. リビルドする
  4. 実行して checksum が 0x0e8685105a08f105 であることを確認する
  5. accepted が 4941900 であることを確認する
  6. できた .exe と .pdb を builds\pgo\ に退避する
プロファイルが見つからないとき

指定したファイルが存在しない場合、Clang はエラーを出します。逆に、プロファイルにその関数の記録が無い場合はエラーになりません。黙って「プロファイルの無い関数」として扱われます。

つまり「パスを間違えていた」以外に「トレーニングでその関数を通っていなかった」という可能性が常にあります。第 34 章でこの区別を扱います。

31.3 測る

第 15 章の手順です。まず空試験でノイズ床を確認してから比較します。

:: 空試験
copy builds\baseline\ClangOptLab.exe builds\baseline2\ClangOptLab.exe
python bench.py builds\baseline\ClangOptLab.exe builds\baseline2\ClangOptLab.exe -n 10 --args 200000 30
  最小値の差: +0.38%          <- ノイズ床

:: 本番
python bench.py builds\baseline\ClangOptLab.exe builds\pgo\ClangOptLab.exe -n 10 --args 200000 30

31.3.1 結果 — 環境 A

試行 1−7.96%

A と B を入れ替えて基準ビルドが +11.19% 遅い（同じ結論）

6 回すべてで同じ向きの結果が出ており、ノイズ床 0.38% を一桁上回っています。第 15 章の基準では、疑いようのない差です。

31.3.2 ところが — 環境 B では差が消えました

本書の実測は、途中で別のマシンに移りました。まったく同じ実行ファイルを、まったく同じ手順で測り直した結果がこれです。

ビルド環境 A（基準比）環境 B（基準比）
空試験（ノイズ床）+0.38%+0.00%
ThinLTO（第 20 章）−0.35%−0.35%
Full LTO（第 20 章）+0.23〜+0.62%+0.68%
PGO−6.5 〜 −9.0%−0.66%

環境 B は Intel Xeon 2.80GHz / L3 33 MB / 2 コア。n=30、交互実行

PGO の効果が、環境 B ではノイズ床の水準まで縮みました。 中央値で比べると +0.21%、つまり逆方向です。バイナリは同一で、第 32 章で確認するコンパイラの判断も同一です。

これは測定の失敗ではありません

LTO の結果は両環境で一致しています（どちらもノイズ床以下）。ノイズ床自体も 0.38% と 0.00% で、測定が壊れていたわけではありません。PGO の効果だけが、ハードウェアによって現れたり現れなかったりしたのです。

31.3.3 なぜ環境で変わるのか

第 32 章で詳しく見ますが、LogLab における PGO の効果の正体はコード配置とインライン化の抑制——つまり命令キャッシュに関わる効果でした。そして命令キャッシュの挙動は、CPU によって大きく異なります。

  • キャッシュの容量と構成
  • プリフェッチャの賢さ
  • 分岐予測器の規模
  • 命令デコーダやマイクロオペキャッシュの構造

環境 B は L3 が 33 MB あります。LogLab の .text は 8 KB 程度でした。コードも作業データもキャッシュに余裕で収まる環境では、配置を改善しても得るものがありません。

これは第 20 章で LTO の効果が測れなかった理由として挙げた分析——「題材が小さく、命令キャッシュに全部載ってしまう」——と同じ話です。環境 A ではその余裕が少なく、環境 B では十分にあった、ということになります。

本書の報告の仕方

第 15 章 15.8 節の書式に、環境の情報を足します。

LogLab において、PGO による実行時間の差は環境に強く依存した。環境 A では最小値で 6.5〜9.0% 短縮（n=8〜10、交互実行、6 回試行、ノイズ床 0.38%）。環境 B（Xeon 2.80GHz / L3 33MB）では −0.66%（n=30、ノイズ床 0.00%）で、差は測れなかった。コンパイラの判断は両環境で同一（第 32 章）。
この経験から学べること

本書はここまで「自分の環境で測れ」と繰り返してきました。その理由が、いま具体的な形で現れました。他人が報告した最適化の効果は、あなたの環境では再現しないかもしれません。 本書の数字も例外ではありません。

そして、だからこそ二本立ての評価が要ります。

  • コンパイラの判断（最適化レコード）——決定的。環境によらず同じ
  • 実行時間——確率的。ハードウェアに依存する

前者で「最適化が機能していること」を確認し、後者で「あなたの環境で得があるか」を判断する。第 10 章でレコードを重視した理由が、ここに帰結します。

31.4 三段階をスクリプトにまとめる

PGO は手順が多く、順番を間違えやすいものです。一連の流れをスクリプトにしておきます。

@echo off
:: pgo.cmd — 計装 → トレーニング → 最適化 を一気に行う
setlocal
set ROOT=%~dp0
set SLN=%ROOT%ClangOptLab.sln
set PROFDIR=%ROOT%prof
set PROFDATA=%ROOT%app.profdata

echo ========== [1/4] 計装ビルド ==========
msbuild "%SLN%" /p:Configuration=Release /p:Platform=x64 ^
    /p:ClangExtraOptions=/clang:-fprofile-generate /t:Rebuild || exit /b 1
if not exist "%ROOT%builds\instr" mkdir "%ROOT%builds\instr"
copy /y "%ROOT%x64\Release\ClangOptLab.*" "%ROOT%builds\instr\" >nul

echo ========== [2/4] トレーニング ==========
if exist "%PROFDIR%" rmdir /s /q "%PROFDIR%"
mkdir "%PROFDIR%"
set LLVM_PROFILE_FILE=%PROFDIR%\run-%%p.profraw
"%ROOT%builds\instr\ClangOptLab.exe" 200000 10 >nul
"%ROOT%builds\instr\ClangOptLab.exe"  20000 20 >nul
"%ROOT%builds\instr\ClangOptLab.exe" 500000  4 >nul
set LLVM_PROFILE_FILE=

echo ========== [3/4] マージ ==========
llvm-profdata merge -output="%PROFDATA%" "%PROFDIR%\*.profraw" || exit /b 1
llvm-profdata show "%PROFDATA%" | findstr /C:"Total functions" /C:"Maximum function count"

echo ========== [4/4] 最適化ビルド ==========
msbuild "%SLN%" /p:Configuration=Release /p:Platform=x64 ^
    /p:ClangExtraOptions=/clang:-fprofile-use=%PROFDATA% /t:Rebuild || exit /b 1
if not exist "%ROOT%builds\pgo" mkdir "%ROOT%builds\pgo"
copy /y "%ROOT%x64\Release\ClangOptLab.*" "%ROOT%builds\pgo\" >nul

echo.
echo 完了: builds\pgo\ClangOptLab.exe
endlocal

リスト 31-1　pgo.cmd

ClangExtraOptions について

このスクリプトは、追加のオプションを MSBuild のプロパティ経由で切り替えています。そのためには .vcxproj 側で、そのプロパティを受け取る記述が必要です。

<ClCompile>
  <AdditionalOptions>$(ClangExtraOptions) %(AdditionalOptions)</AdditionalOptions>
</ClCompile>

プロパティシートを使ったより整った方法は第 39 章で扱います。まずは手でプロパティを切り替える運用でも構いません。大事なのは、三段階が順番どおりに実行され、途中の成果物が正しく引き継がれることです。

31.4.1 順番を間違えるとどうなるか

間違い症状
トレーニング前の古いプロファイルを使ってしまうソースを変えていれば第 34 章の警告が出る。変えていなければ気づけない
計装ビルドで測ってしまう2 倍遅い数字が出る。「PGO で遅くなった」と誤解する
プロファイルを消し忘れて足し込む意図しない配合になる
-fprofile-generate を外し忘れる計装と最適化が同時指定になり、意図が不明な状態になる

二番目が特に多い失敗です。測るのは必ず最適化ビルド（第 4 段階の成果物）です。

31.5 効かなかったときの調べ方

あなたのプロジェクトで効果が出なかった場合、次の順で確認してください。

  1. 本当に最適化ビルドを測っているか。 .exe のサイズと更新日時を確認する
  2. プロファイルが渡っているか。 ビルドログで -fprofile-use= の行を確認する（第 3 章）
  3. プロファイルの中身は妥当か。 llvm-profdata show --topn（第 30 章）
  4. トレーニングは代表的か。 overlap で規模違いを比較（第 28 章）
  5. コンパイラの判断は変わったか。 最適化レコードを比較（第 32 章）
  6. そもそも測れる差なのか。 ノイズ床を確認（第 15 章）

5 番が重要です。時間が動かなくても、コンパイラの判断が変わっていれば PGO は機能しています。あとは「その判断の変化が、この題材では時間に現れなかった」という第 20 章と同じ話になります。

31.6 ハンズオン

  1. 追加のオプションを /clang:-fprofile-use=<絶対パス> に変えてリビルドする
  2. checksum と accepted を確認する
  3. builds\pgo\ に退避する
  4. 空試験でノイズ床を測る
  5. bench.py で基準ビルドと比較する
  6. 少なくとも 3 回試行し、向きが揃うことを確認する
  7. A と B を入れ替えても同じ結論になることを確認する

31.7 まとめ

  • 最適化ビルドは /clang:-fprofile-use=<file>。-fprofile-generate は外す
  • プロファイルに記録の無い関数はエラーにならず、単にプロファイル無しとして扱われる
  • LogLab では、環境 A で 6.5〜9.0% 短縮（ノイズ床 0.38%、6 回試行で再現）。環境 B では −0.66% でノイズ床以下だった
  • 同じバイナリ・同じ手順でこの差が出る。PGO の効果は命令キャッシュに関わるため、CPU に強く依存する
  • 評価は二本立てで行う。コンパイラの判断は決定的、実行時間は環境依存
  • 三段階はスクリプト化する。測るのは最適化ビルドという点を間違えない
  • 効果が出ないときは「測っている対象 → オプション → プロファイルの中身 → トレーニング → 判断の変化 → ノイズ床」の順で確認する

次章は第 5 部の山場です。 なぜ 7% 速くなったのか。コンパイラは何を変えたのか。最適化レコードを突き合わせると、直感に反する事実が見つかります——PGO はインライン化を「減らし」ていました。
