第 30 章

プロファイルの中身を読む
— llvm-profdata show / overlap と llvm-cov

プロファイルはブラックボックスではありません。中身を読めば、トレーニングが妥当だったかを最適化ビルドを作る前に判断できます。ここが Clang の PGO の大きな強みです。

この章のゴール

  • llvm-profdata show でホットな関数を特定する
  • 第 12・13 章のプロファイラの結果と照合する
  • overlap でプロファイルどうしを比較する
  • llvm-cov でソース上にカウンタを重ねる（と、その制約）

30.1 サマリを見る

llvm-profdata show app.profdata
Instrumentation level: IR  entry_first = 0
Total functions: 40
Maximum function count: 52000000
Maximum internal block count: 116121080
項目意味
Instrumentation level: IRIR レベル計装（第 25 章）。Front-end なら別方式
Total functionsプロファイルに含まれる関数の数
Maximum function count最も多く呼ばれた関数の呼び出し回数
Maximum internal block count最も多く通った基本ブロックの通過回数
まずここで異常に気づけます

Maximum function count が極端に小さい（数千程度）なら、トレーニングが足りていません。Total functions が想定よりずっと少なければ、プロファイルの取り漏らしを疑います。第 28 章の極小トレーニングは、この段階で見破れる類のものです。

30.2.1 プロファイラの結果と一致するか

第 12・13 章で、私たちは「parse_line が最もホットなはず」と予想し、プロファイラで確認しました。上の表はそれを裏付けています。1 位の next_field は parse_line の中で呼ばれる関数なので、実質的に同じ場所です。

二つの計測は別物です

混同しないでください。

  • プロファイラ（第 12・13 章）：サンプリング。時間を測る。1 ミリ秒ごとの統計
  • PGO のプロファイル：計装。回数を数える。すべての実行を漏れなく記録

「よく呼ばれる」と「時間を食う」は別です。1 億回呼ばれても中身が 2 命令なら大した時間ではありませんし、1 回しか呼ばれなくても中で 10 秒かかるなら、それがボトルネックです。

とはいえ両者は多くの場合一致します。食い違ったときこそ面白い——「回数は少ないのに時間を食っている関数」は、中身が重い証拠です。

30.2.2 フィルタの分布

6 位と 7 位に注目してください。

LevelFilter::accept       4,000,000
ComponentFilter::accept   3,564,220

LevelFilter を通過したレコードだけが ComponentFilter に渡るので、この二つの比が通過率です。3,564,220 ÷ 4,000,000 ≒ 89%。第 4 章の設計（TRACE を落とす＝約 11%）と一致します。

そして Filter::accept() は仮想関数でした。この分布こそ、第 21 章で「デバーチャライズできない」と結論した間接呼び出しに対して、PGO が持ち込む新しい情報です。

30.3 プロファイルどうしを比べる

llvm-profdata overlap base.profdata test.profdata

二つのプロファイルがどれだけ似ているかを数値化します。第 28 章で使った機能です。

Program level:
  # of functions overlap: 40
  Edge profile overlap: 88.154%
  Edge profile base count sum: 616483160
  Edge profile test count sum: 700799
  IndirectCall profile overlap: 50.000%
  MemOP profile overlap: 78.422%
項目意味
Edge profile overlap分岐の分布の一致度。最も重要
IndirectCall profile overlap間接呼び出しの行き先の分布の一致度
MemOP profile overlapmemcpy などのサイズ分布の一致度
count sumそれぞれの総カウント。規模の違いが分かる

30.3.1 使いどころ

比べる相手分かること
トレーニングの規模違いどこまで増やせば飽和するか（第 28 章）
実行ごとのプロファイル実行間のばらつき。極端に違う実行があれば異常
先月のプロファイルと今月のプロファイル本番の傾向が変わっていないか
トレーニングと本番のプロファイルトレーニングの妥当性そのもの

最後の使い方が理想です。本番環境で計装ビルドを短時間だけ動かせるなら、そのプロファイルとトレーニング用プロファイルを overlap で比べることで、トレーニングの代表性を直接検証できます。

30.4 llvm-cov でソース上に重ねる

数字の羅列より、ソースコードの各行に回数が書いてあるほうが分かりやすい。それをやるのが llvm-cov です。

ただし、PGO のプロファイルは llvm-cov で読めません

実際に試すとこうなります。

llvm-cov show ClangOptLab.exe -instr-profile=app.profdata
error: failed to load coverage: 'ClangOptLab.exe': no coverage data found

第 25 章で触れた二つの計装方式の違いが、ここで効いてきます。llvm-cov が必要とするのはカバレッジマッピング——「このカウンタはソースのこの範囲に対応する」という情報です。これはフロントエンド計装でしか生成されません。

30.4.1 可視化専用のビルドを作る

カウンタをソース上で見たいなら、別にビルドします。

clang-cl /c /O2 /std:c++23 /Iinclude ^
    /clang:-fprofile-instr-generate /clang:-fcoverage-mapping src\*.cpp

:: 実行
set LLVM_PROFILE_FILE=cov\c.profraw
ClangOptLab_cov.exe 50000 3

:: マージ（これは同じ）
llvm-profdata merge -output=cov.profdata cov\c.profraw

:: 表示
llvm-cov show ClangOptLab_cov.exe -instr-profile=cov.profdata src\stats.cpp

30.4.2 第 4 章の設計が数字になった

33 行目を見てください。

   32|  74.2k|    if (r.level == Level::Error) {
   33|    258|        handle_error(r);

74,200 回のうち 258 回。 割合にして 0.348% です。第 4 章で「1000 行に 3 行程度」と設計した比率が、そのまま現れています。

そして第 4 章では、この if に [[unlikely]] を意図的に書きませんでした。コンパイラはソースからこの 0.348% を知る術がありません。しかしプロファイルには、はっきりと記録されています。

これが第 32 章の主役になります

この 258 という数字を渡されたコンパイラが、何を変えるのか。それが次々章のテーマです。

30.4.3 llvm-cov の他の使い方

コマンド用途
llvm-cov showソースに重ねて表示
llvm-cov reportファイル単位の要約表
llvm-cov show --format=html --output-dir=<dir>HTML で出力。色分けされて読みやすい
可視化用ビルドは最適化の判断には使わないでください

フロントエンド計装のプロファイルも -fprofile-instr-use で最適化に使えますが、第 25 章の表のとおり PGO には向きません。カウンタの位置が最適化前のソース構造に固定されているためです。

可視化はフロントエンド計装、最適化は IR 計装。 二つのビルドを使い分けてください。

30.5 確認の手順としてまとめる

最適化ビルドを作る前に、次を確認する習慣をつけると事故が減ります。

  1. llvm-profdata show で Maximum function count が十分大きいか
  2. --topn の顔ぶれが、プロファイラの結果と矛盾しないか
  3. 規模の違うトレーニングと overlap を取り、飽和しているか
  4. （必要なら）llvm-cov で、気になる分岐の実際の比率を確認する

30.6 ハンズオン

  1. llvm-profdata show app.profdata でサマリを見る
  2. --topn=10 でホットな関数を並べ、第 12・13 章のメモと比べる
  3. LevelFilter と ComponentFilter のカウントから通過率を計算する
  4. 小さいトレーニングのプロファイルを作り、overlap で比較する
  5. フロントエンド計装のビルドを別に作り、llvm-cov show で stats.cpp を表示する
  6. 33 行目のカウントを確認する

30.7 まとめ

  • llvm-profdata show でサマリ、--topn でホットな関数のランキングが得られる
  • LogLab では next_field / parse_line が上位に来て、第 12・13 章のプロファイラの結果と一致した
  • サンプリング（時間）と計装（回数）は別物。食い違ったときこそ調べる価値がある
  • overlap でプロファイルどうしの一致度を数値化できる。Edge profile overlap が最重要
  • PGO 用の IR 計装プロファイルは llvm-cov で読めない。 可視化には -fprofile-instr-generate -fcoverage-mapping の別ビルドが要る
  • 実測では handle_error の呼び出しが 74,200 回中 258 回（0.348%）と記録されていた

次章では、いよいよプロファイルを使って最適化ビルドを作ります。オプションは一つ、確認することも決まっています。そして第 15 章の手順で測ります。第 20 章の LTO とは違う結果になります。
