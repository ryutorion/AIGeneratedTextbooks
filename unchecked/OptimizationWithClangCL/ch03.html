第 3 章

最初のプロジェクト
— C++23 / ClangCL のビルド設定を作る

本書を通して使うプロジェクトをここで作ります。単に動くようにするだけでなく、「clang-cl に実際どんな引数が渡っているか」「リンカは何が使われているか」を自分の目で確認できる状態にしておきます。第 4 部以降の作業はすべてこの確認が土台になります。

この章のゴール

  • プラットフォームツールセットを LLVM (clang-cl) に切り替える
  • C++23 でビルドできることをコードで検証する
  • ビルドログから clang-cl.exe の実体パスと引数を読み取る
  • リンカが lld-link.exe であることを確認する
  • Release 構成でもデバッグ情報を残す設定にする

3.1 プロジェクトを作る

Visual Studio 2026 を起動し、新しいプロジェクトを作成します。

  1. 新しいプロジェクトの作成 を選択
  2. テンプレートから コンソール アプリ（C++）を選択
  3. プロジェクト名を ClangOptLab、ソリューション名も同じにします
  4. 「ソリューションとプロジェクトを同じディレクトリに配置する」はチェックしないでおきます。第 4 章で複数のソースファイルを足すため、また第 39 章でプロパティシートを追加するため、ソリューション階層があるほうが扱いやすくなります

作成できたら、まず構成を整えます。画面上部のツールバーで、構成を Release、プラットフォームを x64 にしてください。本書では原則として Release / x64 で作業します。最適化の話をするのに Debug 構成で測っても意味がないためです。

3.2 プラットフォームツールセットを切り替える

ソリューションエクスプローラーでプロジェクト ClangOptLab を右クリックし、プロパティ を開きます。

最初にここを変える

プロパティページの左上にある 構成 を「すべての構成」、プラットフォーム を「すべてのプラットフォーム」に変えてから設定を始めてください。ここを既定のままにすると、Release だけ設定して Debug を忘れる、あるいはその逆、という事故が起きます。本書で今後「プロパティを変える」と書いたときは、常にこの状態から始めるものとします。

構成プロパティ > 全般 > プラットフォーム ツールセット → LLVM (clang-cl)

ここに LLVM (clang-cl) が出てこない場合は、第 2 章のコンポーネントが足りていません。2.6 節を確認してください。

設定したら、いったんビルドしてみます（Ctrl+Shift+B）。テンプレートが生成した Hello World がそのままビルドできれば、切り替えは成功しています。

3.3 C++23 にする

構成プロパティ > C/C++ > 言語 > C++ 言語標準

ドロップダウンに ISO C++23 標準 (/std:c++23) があればそれを選びます。無ければ プレビュー - 最新の C++ 標準機能 (/std:c++latest) を選んでください。ここは Visual Studio と LLVM のバージョンの組み合わせによって選択肢が変わります。

設定できたら、本当に C++23 になっているかをコードで確認します。ClangOptLab.cpp を次の内容に置き換えてください。

#include <cstdio>
#include <utility>
#include <version>

static_assert(__cplusplus >= 202302L, "C++23 でビルドされていません");

enum class Level : int { Low = 1, High = 9 };

int main()
{
    // std::to_underlying は C++23 で追加されたもの
    std::printf("__cplusplus = %ldL\n", static_cast<long>(__cplusplus));
    std::printf("Level::High = %d\n", std::to_underlying(Level::High));
    return 0;
}

リスト 3-1　ClangOptLab.cpp（C++23 の確認）

ビルドして実行し、次のように表示されれば成功です。

__cplusplus = 202302L
Level::High = 9
/Zc:__cplusplus は要りません

MSVC（cl.exe）は互換性のため、既定では __cplusplus が 199711L のままという有名な挙動を持っており、正しい値を得るには /Zc:__cplusplus が必要でした。clang-cl はこの点で MSVC の互換動作を引き継いでおらず、標準どおりの値を返します。上の static_assert がそのまま通るのはそのためです。

/std:c++latest を選んだ場合

__cplusplus の値が 202302L より大きくなることがあります（C++26 の作業版を指す値）。static_assert は >= で書いてあるので通りますが、意図せず C++26 の機能を使ってしまう余地は残ります。可能であれば /std:c++23 を明示するほうが、本書の趣旨には合っています。

3.4 Release 構成の中身を確認する

最適化の実験をする前に、いま Release 構成が何をしているのかを確認しておきます。

構成プロパティ > C/C++ > 最適化

プロパティRelease の既定意味
最適化最大限の最適化 (速度優先) (/O2)速度重視の最適化一式。本書の出発点
インライン関数の展開任意の適切なもの (/Ob2)インライン化の積極度
組み込み関数を使用するはい (/Oi)memcpy などを組み込み命令に置き換える

/O2 が具体的にどんな最適化パスの集合なのかは第 6 章で分解します。ここでは「Release は /O2 から始まっている」という事実だけ押さえておいてください。

3.4.1 Release でもデバッグ情報を残す

この設定変更は、後の章のために必ずやっておいてください。

構成プロパティ > C/C++ > 全般 > デバッグ情報の形式 → プログラム データベース (/Zi)

構成プロパティ > リンカー > デバッグ > デバッグ情報の生成 → デバッグ情報ファイルを生成 (/DEBUG)

デバッグ情報を付けても、最適化そのものは変わりません。生成されるコードは同じで、PDB ファイルが追加で作られるだけです。

なぜこれが必要かというと、第 3 部で使うプロファイラ（PIX、Windows Performance Analyzer）が、アドレスを関数名に対応づけるために PDB を必要とするからです。PDB が無いと、プロファイル結果が ClangOptLab.exe+0x1a3f のような数字の羅列にしかなりません。「ホットスポットが分からない」という状態でチューニングを始めることになります。

PDB は「最適化前の姿」ではありません

最適化されたコードの PDB は、行番号と機械語の対応が一対一ではありません。インライン化された関数、並べ替えられた命令、消えたローカル変数。デバッガでステップ実行すると行が飛び回ります。これは壊れているのではなく、最適化されたコードとはそういうものです。この対応関係の読み方は第 14 章で扱います。

3.5 clang-cl に渡っている引数を見る

ここが、この章でいちばん重要な節です。

プロパティページで設定した内容は、最終的にコマンドライン引数に変換されて clang-cl.exe に渡ります。本書ではこれから多くのオプションを足していきますが、「プロパティページで設定したつもりが渡っていない」という事故は頻繁に起きます。確認する術を先に持っておきます。

3.5.1 方法 1 — プロパティページのコマンドライン

構成プロパティ > C/C++ > コマンド ライン

ここに、現在の設定から生成される引数がそのまま表示されます。次のような内容が見えるはずです。

/c /I"..." /Zi /W3 /WX- /diagnostics:column /O2 /Ob2 /Oi /D "NDEBUG"
/D "_CONSOLE" /D "_UNICODE" /D "UNICODE" /Gm- /EHsc /MD /GS /fp:precise
/permissive- /std:c++23 /Fo"x64\Release\" /Fd"x64\Release\vc143.pdb"
/external:W3 /Gd /TP /FC

下部の 追加のオプション 欄は、プロパティページに対応する項目が無いオプションを直接書き込む場所です。本書では -flto=thin や -fprofile-use=... を、しばしばここに書き足すことになります。

3.5.2 方法 2 — ビルドログ（こちらが本命）

プロパティページのコマンドラインは「これから渡す予定の引数」です。実際に起動された実行ファイルのパスまでは分かりません。第 2 章で公式 LLVM への差し替えを行った場合、それが効いているかどうかを確認するには、ビルドログを見る必要があります。

MSBuild の出力詳細度を上げます。

ツール > オプション > プロジェクトおよびソリューション > ビルド / 実行
→ MSBuild プロジェクト ビルドの出力の詳細 を 詳細（Detailed）に

この状態でリビルドし、出力ウィンドウを「ビルド」に切り替えると、次のような行が見つかります。

C:\Program Files\Microsoft Visual Studio\2026\Community\VC\Tools\Llvm\x64\bin\clang-cl.exe
  /c /I"..." /Zi /W3 ... /std:c++23 ... ClangOptLab.cpp

先頭のフルパスが、実際に動いた clang-cl.exe です。Directory.Build.props で LLVMInstallDir を指定したなら、ここが C:\Program Files\LLVM\bin\clang-cl.exe に変わっているはずです。変わっていなければ、props ファイルの置き場所が間違っています（ソリューションファイルと同じ階層か、その上位に置く必要があります）。

詳細度は戻しておいても構いません

詳細度を上げるとビルドが目に見えて遅くなり、出力も長大になります。確認が済んだら「最小」に戻し、必要なときだけ上げるのが実用的です。本書では以後、「ビルドログで確認する」と書いたらこの操作を指します。

3.6 リンカを確認する — lld-link

同じビルドログを下にスクロールすると、リンク工程の行があります。

C:\Program Files\Microsoft Visual Studio\2026\Community\VC\Tools\Llvm\x64\bin\lld-link.exe
  /OUT:"x64\Release\ClangOptLab.exe" /DEBUG /MACHINE:X64 ... ClangOptLab.obj

link.exe ではなく lld-link.exe です。 ClangCL ツールセットは、既定でリンカとライブラリアンも LLVM のものを使います。これは MSBuild の次のプロパティで制御されています。

プロパティ既定値意味
UseLldLinktrueLLVM のリンカを使うかどうか
LinkToolExelld-link.exe実際に起動されるリンカの実行ファイル名
UseLlvmLibtrueLLVM のライブラリアン（llvm-lib）を使うかどうか
LibToolExellvm-lib.exe実際に起動されるライブラリアン

MSVC のリンカに戻したい場合は .vcxproj または Directory.Build.props に次のように書きます。

<PropertyGroup>
  <UseLldLink>false</UseLldLink>
  <LinkToolExe>link.exe</LinkToolExe>
  <UseLlvmLib>false</UseLlvmLib>
  <LibToolExe>lib.exe</LibToolExe>
</PropertyGroup>

リスト 3-2　MSVC のリンカに戻す場合（本書では行いません）

LTO には lld-link が必要です

第 4 部で扱う LTO は、.obj の中に機械語ではなく LLVM ビットコードを入れる方式です。MSVC の link.exe はこの形式を理解できないため、LTO を有効にしたまま link.exe でリンクすると失敗します。本書では UseLldLink を既定の true のままにしておいてください。 既存プロジェクトを ClangCL に移行した際、何らかの理由でこれが false になっていることがあり、第 17 章でつまずく典型的な原因になります。

3.7 この章の成果物チェックリスト

  • プロジェクト ClangOptLab が Release / x64 でビルドできる
  • プラットフォームツールセットが LLVM (clang-cl) になっている
  • リスト 3-1 が実行でき、__cplusplus が 202302L 以上と表示される
  • C/C++ > デバッグ情報の形式が /Zi、リンカー > デバッグ情報の生成が /DEBUG
  • ビルドログで clang-cl.exe のフルパスを確認した
  • ビルドログで lld-link.exe が使われていることを確認した

3.8 よくあるつまずき

Debug 構成だけビルドが通らない

プロパティを「すべての構成」で変更していません。3.2 節の警告を参照してください。特に言語標準は構成ごとに独立しているため、片方だけ C++23 になっている状態が起きます。

static_assert が失敗する

言語標準の設定が反映されていません。プロパティページの C/C++ > コマンド ライン を開き、/std:c++23 または /std:c++latest が実際に含まれているかを確認してください。「追加のオプション」欄に古い /std: 指定が残っていて、そちらが優先されているケースもあります。

ビルドログに cl.exe が出てくる

ツールセットの切り替えが特定の構成にしか適用されていないか、そもそも切り替えが保存されていません。プロパティページを開き直して確認してください。

リンカが link.exe になっている

既存プロジェクトを流用した場合に起こりえます。.vcxproj をテキストエディタで開き、UseLldLink や LinkToolExe の記述が無いかを確認してください。3.6 節の警告のとおり、LTO の章でつまずく原因になります。

3.9 まとめ

  • プロパティは必ず「すべての構成 / すべてのプラットフォーム」から編集する
  • C++23 になっているかは static_assert(__cplusplus >= 202302L) で検証する。clang-cl に /Zc:__cplusplus は不要
  • Release でも /Zi と /DEBUG を有効にしておく。最適化結果は変わらず、後の計測で必須になる
  • 設定が本当に渡っているかは ビルドログで確認する。プロパティページのコマンドラインだけでは実体パスが分からない
  • ClangCL は既定で lld-link.exe を使う。これは LTO の前提条件なので変更しない

次章では、最適化の効果を観察するための題材アプリを作ります。単なる Hello World では LTO も PGO も効果が見えないため、「複数の翻訳単位に分かれている」「処理時間に明確な偏りがある」「結果を検証できる」という条件を満たすプログラムを設計します。あわせて、最適化に消されないベンチマークの書き方も扱います。
