第 33 章

マルチスレッド計装
— -fprofile-update=atomic とオーバーヘッド

計装ビルドはカウンタを加算します。複数スレッドが同じカウンタを同時に更新したら、どうなるのか。正確にするオプションはありますが、実測すると計装ビルドが 7 倍以上遅くなりました。

この章のゴール

  • カウンタの競合で何が起きるかを理解する
  • -fprofile-update の三つの値を知る
  • atomic のコストを実測で把握する
  • どちらを選ぶべきかの判断基準を持つ

33.1 カウンタの競合

計装ビルドが挿入するのは、要するにこれです。

counter[k]++;

この加算は、機械語では「読む・足す・書く」の三段階になります。二つのスレッドが同時に実行すると、片方の更新が失われます。いわゆるロストアップデートです。

スレッド A          スレッド B
read  counter = 100
                    read  counter = 100
add   → 101
                    add   → 101
write counter = 101
                    write counter = 101    ← 2 回数えたのに 101

結果として、記録される回数は実際より少なくなります。

33.1.1 どれくらい問題になるか

これは意外に微妙な問題です。実測してみました。8 スレッドで同じ関数を 20 万回ずつ回すプログラムを、既定（非アトミック）とアトミックの両方で計装し、記録されたカウントを比べます。

-fprofile-update=single   Maximum internal block count: 800000
-fprofile-update=atomic   Maximum internal block count: 800000

同じでした。 取りこぼしは観測されませんでした。

これは「競合が起きない」という意味ではありません。ロストアップデートが起きるのは、二つのスレッドの読み書きが正確に重なった瞬間だけです。加算は数ナノ秒で終わるので、確率的には稀な事象です。

PGO が求める精度

ここで思い出したいのは、PGO が使うのは比率だということです。「この分岐は 99% 成立する」という情報が欲しいのであって、絶対値が 0.1% ずれても判断は変わりません。

多少の取りこぼしがあっても、それが均等に起きるならば比率は保たれます。PGO の目的に対しては、非アトミックのカウンタで十分なことがほとんどです。

33.2 -fprofile-update

値挙動
single単純な加算。競合を考慮しない。既定
atomicアトミックな加算。取りこぼしが起きない
prefer-atomicターゲットが対応していればアトミック、そうでなければ単純加算
 
/clang:-fprofile-update=atomic

指定できない値を渡すと、きちんとエラーになります。

error: unsupported argument 'zzz' to option '-fprofile-update'

33.3 コストを実測する

ここが本章の要点です。二つのプログラムで測りました。

33.3.1 マルチスレッドのプログラム（8 スレッド）

ビルド実行時間
通常ビルド4 ms
計装（single）4 ms
計装（atomic）32 ms（8 倍）
計装（prefer-atomic）32 ms

33.3.2 LogLab（シングルスレッド）

ビルド実行時間
通常ビルド144 ms
計装（既定 = single）243 ms（1.7 倍）
計装（atomic）1,793 ms（通常の 12.5 倍、single の 7.4 倍）

実測の一例。いずれも 3 回実行して最小値

シングルスレッドのプログラムでも 7 倍以上遅くなります

LogLab はスレッドを一つしか使いません。競合など起こりようがないのに、atomic を指定すると single の 7.4 倍遅くなりました。

アトミック命令は、競合の有無にかかわらずキャッシュラインの排他所有を要求します。ホットループの中で 1 命令ごとに実行されれば、この差になります。「念のため atomic にしておこう」は、非常に高くつきます。

33.4 どちらを選ぶか

状況選択
シングルスレッドsingle（既定）。 atomic にする理由が無い
マルチスレッドだが、スレッドごとに違うコードを実行するsingle。同じカウンタを叩かないので競合しない
マルチスレッドで、同じホットループを全スレッドが回るまず single で試す。プロファイルが不自然なら atomic を検討
計装ビルドが遅すぎて実行できないsingle 一択。それでも遅ければトレーニングを短くする
カウントの絶対値が正確である必要があるatomic。ただし PGO でこれが必要になる場面は稀
本書の推奨

既定（single）のまま使ってください。 atomic は「プロファイルの結果が明らかにおかしく、その原因がカウンタの競合だと切り分けられたとき」の対処であって、最初から付けるものではありません。

そして、切り分けの方法はあります。同じトレーニングを single と atomic でそれぞれ実行し、llvm-profdata overlap（第 30 章）で比較するのです。分布がほぼ一致するなら、競合は問題になっていません。

33.5 マルチスレッドでのその他の注意

スレッドごとの偏り

ワーカースレッドが 8 本あって、そのうち 1 本だけが特殊な処理をしている、という構造では、その 1 本ぶんの記録が全体に埋もれます。プロファイルはプロセス全体で 1 セットだからです。特殊なスレッドの挙動を最適化したいなら、そのコードを別の関数に分けておくと区別しやすくなります。

プロファイル出力の競合

第 27 章で扱ったとおり、複数プロセスで %m を使うとファイルロックの競合が起きます。%Nm で分散させるか、%p を使ってください。スレッドは同一プロセス内なので、この問題は起きません。

実行順序による揺らぎ

マルチスレッドのプログラムは、実行のたびにスレッドのスケジューリングが変わります。プロファイルも実行ごとに揺らぎます。複数回のトレーニングをマージする（第 29 章）ことで、この揺らぎは平均化されます。シングルスレッドのプログラム以上に、複数回のトレーニングが効いてきます。

33.6 ハンズオン

  1. LogLab の計装ビルドに /clang:-fprofile-update=atomic を付けてビルドする
  2. 実行時間を既定のものと比べる（大幅に遅くなるはずです）
  3. 両方でトレーニングを行い、それぞれプロファイルを作る
  4. llvm-profdata overlap で二つを比較する
  5. ほぼ一致することを確認し、atomic が不要だったと判断する
  6. オプションを外す

33.7 まとめ

  • 計装のカウンタ更新は、複数スレッドから同時に行われると取りこぼしが起きうる
  • ただし PGO が使うのは比率なので、多少の取りこぼしは判断を変えない
  • -fprofile-update は single（既定）/ atomic / prefer-atomic
  • 実測では、8 スレッドのプログラムで atomic は 8 倍、シングルスレッドの LogLab でも 7.4 倍遅くなった
  • アトミック命令は競合が無くてもコストを払う。「念のため」で付けてはいけない
  • 既定のまま使う。 疑いが生じたら overlap で分布を比較して切り分ける
  • マルチスレッドではプロファイルが実行ごとに揺らぐ。複数回トレーニングしてマージする

次章で第 5 部を締めくくります。 プロファイルは、そのコードのある時点の姿を記録したものです。ソースを直したら、その記録はどうなるのか。Clang は関数ごとにハッシュを持っていて、食い違いを検出できます。ただし、警告の出し方が計装方式によって違うという罠があります。
