第 8 章

生成コードを見る
— /FA、llvm-objdump、逆アセンブルウィンドウ

最適化の結果を最終的に裏付けるのは、生成された機械語です。この章では三つの見方を使い分けられるようにし、そこから何を読み取るべきかを整理します。全部を読む必要はありません。見るべき場所は決まっています。

この章のゴール

  • /FA でアセンブリリストを出力する
  • llvm-objdump を読みやすい設定で使う
  • Visual Studio の逆アセンブルウィンドウを使う
  • 最適化の痕跡をどこに探せばよいかを知る
  • ベースラインを保存し、あとで差分を取れる形にしておく

8.1 三つの見方の使い分け

手段見えるもの向いている場面
/FA（アセンブリリスト）コンパイル時点の 1 翻訳単位。ラベル名・セクション情報が残る特定の関数がどう出力されたかを丁寧に読む
llvm-objdumpリンク後の .exe / .obj 全体LTO の効果を見る。全体を検索・差分する
逆アセンブルウィンドウ実行中のプロセスの実際のコードデバッガで止めた場所の周辺を確認する

本書でいちばん使うのは llvm-objdump です。LTO はリンク時に働くため、コンパイル時点の /FA では効果が見えないからです。

8.2 /FA — アセンブリリストを出す

clang-cl /c /O2 /FA sample.cpp

sample.asm が生成されます。第 7 章のリスト 7-1 に対する出力から、caller の部分を抜き出したものが次です。

"?caller@@YAHH@Z":                      # @"?caller@@YAHH@Z"
# %bb.0:
        test    ecx, ecx
        jle     .LBB1_1
# %bb.2:
        mov     edx, ecx
        and     edx, 3
        cmp     ecx, 4
        jae     .LBB1_7
# %bb.3:
        xor     r8d, r8d
        xor     eax, eax
        jmp     .LBB1_4
.LBB1_1:
        xor     eax, eax
        ret
.LBB1_7:
        and     ecx, 2147483644
        xor     r8d, r8d
        xor     eax, eax
        .p2align        4, 0x90
.LBB1_8:                                # =>This Inner Loop Header: Depth=1
        mov     r9d, r8d

clang-cl /FA の出力（抜粋）

ここから読み取れることが三つあります。

  • Intel 構文である。 出力の先頭に .intel_syntax noprefix が付きます（mov 宛先, 元 の順）。MSVC のリストと同じ向きなので、読み替えは不要です
  • ループが 4 回展開されている。 and edx, 3 と cmp ecx, 4、and ecx, 2147483644（＝ ~3）は、反復回数を 4 で割った商と余りに分ける処理です。helper() はインライン化され、その本体が 4 つ並べられています
  • # %bb.0 や Depth=1 といったコメントが付く。 これは LLVM が付ける基本ブロックの識別子で、IR の構造を追うときの手がかりになります
/FAsc は MSVC と同じようには動きません

MSVC の /FAsc は、アセンブリにソース行と機械語バイトを織り交ぜた読みやすいリストを出します。clang-cl も /FAsc を受け付けますが、出力は /FA とまったく同じです（実測で確認済み）。ソースとの対応を見たい場合は、次節の llvm-objdump か、逆アセンブルウィンドウを使ってください。

8.3 llvm-objdump — リンク後の姿を見る

第 5 章で一度使いましたが、あらためて読みやすい設定を決めておきます。

llvm-objdump -d --demangle --x86-asm-syntax=intel --no-show-raw-insn ^
    ClangOptLab.exe > disasm.txt
オプション効果
-d実行可能セクションを逆アセンブルする
--demangleC++ の名前を読める形に戻す
--x86-asm-syntax=intelIntel 構文にする（既定は AT&T 構文）
--no-show-raw-insn機械語のバイト列を省く。差分を取るときに重要

この設定での出力例です。

    3766:       call    0x3d20 <loglab::parse_line(std::basic_string_view<char, ...>, loglab::Record&)>
    376b:       test    al, al
    376d:       je      0x372d <main+0x1fd>
    376f:       mov     r13, qword ptr [rsp + 0x18]
    3774:       mov     r14, qword ptr [rsp + 0x20]
    3779:       cmp     r13, r14
    377c:       je      0x3720 <main+0x1f0>
    377e:       nop
    3780:       mov     rdi, qword ptr [r13]
    3784:       mov     rax, qword ptr [rdi]
    3787:       mov     rsi, r12
    378a:       call    qword ptr [rax + 0x10]

8.3.1 関数を絞る

実行ファイル全体は数万行になります。特定の関数だけを見たいときは --disassemble-symbols を使います。

llvm-objdump -d --demangle --x86-asm-syntax=intel --no-show-raw-insn ^
    --disassemble-symbols="?parse_line@loglab@@YA_NV?$basic_string_view@DU?$char_traits@D@std@@@std@@AEAURecord@1@@Z" ^
    ClangOptLab.exe

マングル名を手で打つのは現実的ではないので、次のようにシンボル一覧から探すのが実用的です。

:: 関数の一覧を出す
llvm-objdump --syms --demangle ClangOptLab.exe | findstr parse_line

8.4 Visual Studio の逆アセンブルウィンドウ

デバッグ実行中に デバッグ > ウィンドウ > 逆アセンブル（Ctrl+Alt+D）で開きます。デバッグを開始していないと開けませんので、まずブレークポイントを置いて止めてください。

このウィンドウの利点は、ソース行と機械語が対応付けて表示されることです。/FA では得られない情報が、ここでは見られます。

最適化されたコードのデバッグは混乱します

Release 構成でステップ実行すると、カーソルが行を飛び越え、逆戻りし、ローカル変数が「最適化により使用できません」と表示されます。これは壊れているのではなく、命令が並べ替えられ、変数がレジスタに載り、関数が展開された結果です。

混乱を避けるコツは、ソース行を追うのをやめて、逆アセンブルウィンドウだけを見ることです。行単位ではなく命令単位でステップ実行すれば、実際に起きていることと表示が一致します。

8.5 どこを見るのか — 四つの着眼点

逆アセンブルを頭から読む必要はありません。本書で追いかけるのは次の四つです。

8.5.1 呼び出しの形

見た目意味本書での扱い
call 0x3d20 <関数名>直接呼び出し。呼び先が確定しているLTO でこれが消える（＝インライン化される）かを見る。第 20 章
call qword ptr [rax + 0x10]間接呼び出し。仮想関数テーブル経由デバーチャライズ（第 21 章）、間接呼び出しの投機的展開（第 32 章）
呼び出しが無いインライン展開されたこれが最も見たい状態

8.5.2 ループ展開の痕跡

同じ演算パターンが 2 回、4 回、8 回と繰り返されていたら展開されています。前節の and edx, 3 のような「余りを分離する」処理が近くにあるのも目印です。

8.5.3 ベクトル化の痕跡

xmm / ymm レジスタが出てきたら SIMD 化されています。movdqu、paddd、vpmulld のような命令が並びます。LogLab は文字列処理が中心なのでベクトル化は限定的ですが、memcmp 相当の比較などで現れることがあります。

8.5.4 コールドコードの配置

関数の末尾や、別セクションに追いやられたコード片。第 4 章で作った handle_error() のような「めったに通らない処理」が、ホットな経路から離れた場所に置かれているかどうかを見ます。いまの /O2 ではまだ分離されていません。 PGO を有効にすると変わります（第 32 章）。

8.6 ベースラインを保存する

この章の実用的な成果物は、あとで差分を取るための基準ファイルです。

cd x64\Release
llvm-objdump -d --demangle --x86-asm-syntax=intel --no-show-raw-insn ^
    ClangOptLab.exe > ..\..\baseline_O2.asm
差分を取りやすくする工夫

--no-show-raw-insn を付けるのは、機械語のバイト列が差分のノイズになるからです。それでも命令が一つ増減するだけで以降のアドレスがすべてずれるため、素直に fc や diff にかけると全行が差分として出てしまいます。

実用的なのは、次のような比較です。

  • 特定の関数だけを --disassemble-symbols で切り出して比較する
  • 関数ごとの命令数を数えて比較する（findstr /C:"call" | find /c /v "" など）
  • call 命令の一覧だけを抜き出して比較する ← LTO の効果を見るにはこれが最も分かりやすい

最後の方法を、いま作っておきましょう。

:: call 命令だけを抜き出す
findstr /C:"call" baseline_O2.asm > baseline_O2_calls.txt

第 20 章では、LTO を有効にしたあとの同じファイルを作り、この行数と中身を比較します。翻訳単位をまたぐ call が減っていれば、LTO が効いた証拠です。

8.7 ハンズオン

  1. LogLab を Release / x64 でビルドする
  2. llvm-objdump で baseline_O2.asm を作る
  3. parse_line を検索し、main からの call が残っていることを確認する
  4. call qword ptr [ で検索し、Filter::accept() の間接呼び出しを見つける
  5. handle_error を検索し、それが Stats::add の直後に置かれているか、別の場所にあるかを確認する
  6. baseline_O2_calls.txt を作り、行数をメモする

8.8 まとめ

  • /FA はコンパイル時点の 1 翻訳単位、llvm-objdump はリンク後の全体を見る。LTO の確認には後者が必要
  • clang-cl の /FA は Intel 構文。/FAsc は受け付けるが /FA と同じ出力になる
  • llvm-objdump -d --demangle --x86-asm-syntax=intel --no-show-raw-insn を定型として覚える
  • 逆アセンブルウィンドウはデバッグ中のみ。最適化コードでは行単位ではなく命令単位でステップする
  • 着眼点は四つ：呼び出しの形、ループ展開、ベクトル化、コールドコードの配置
  • call 命令の一覧を抜き出したファイルを、LTO 前のベースラインとして保存しておく

次章では、機械語を読む代わりに、コンパイラ自身に説明させる方法を扱います。「この関数をインライン化した／しなかった、その理由はこれだ」を出力させる最適化リマークです。逆アセンブルが「結果」を見るものだとすれば、リマークは「判断」を見るものです。本書で最も使う道具になります。
