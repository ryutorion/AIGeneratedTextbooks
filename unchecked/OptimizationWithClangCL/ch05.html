第 5 章

LLVM 付属ツールの確認
— 最適化を観察するための道具箱

Clang の最適化を追いかける作業の大半は、コンパイラ本体ではなく周辺ツールが担います。この章では本書で使うツールを一通り確認し、足りないものがあれば補い、そして「なぜバージョンを揃える必要があるのか」を理解します。第 1 部の最後の章です。

この章のゴール

  • 本書で使う LLVM ツールと、それぞれの登場章を把握する
  • 手元の環境に何が入っていて何が無いかを確認する
  • 足りないツールを補う手順を知る
  • コンパイラとツールのバージョンを揃えるべき理由を理解する
  • llvm-objdump で自作の実行ファイルを逆アセンブルしてみる

5.1 本書で使うツール

ツール役割主な登場章
clang-clコンパイラ（MSVC 互換のコマンドライン）全章
lld-linkリンカ。LTO の実行主体でもある第 4 部
llvm-libライブラリアン。ビットコードを含む .lib を扱える第 22 章

この中で本書にとって特に重要なのは llvm-profdata です。第 5 部と第 6 部の作業は、ほぼすべてこのツールを経由します。逆に言うと、llvm-profdata が無い環境では PGO の章に進めません。

5.2 何があるかを確認する

Developer Command Prompt for VS 2026 を開き、次を実行します。

where clang-cl
where lld-link
where llvm-lib
where llvm-objdump
where llvm-profdata
where llvm-cov
where llvm-readobj

PowerShell を使っているなら、まとめて確認できます。

@('clang-cl','lld-link','llvm-lib','llvm-objdump',
  'llvm-profdata','llvm-cov','llvm-readobj') | ForEach-Object {
    $p = (Get-Command $_ -ErrorAction SilentlyContinue).Source
    '{0,-16} {1}' -f $_, ($p ? $p : '*** 見つかりません ***')
}

リスト 5-1　ツールの存在を一括確認する（Developer PowerShell）

すべて見つかれば、5.4 節まで飛ばして構いません。

llvm-profdata と llvm-cov が無いことがあります

Visual Studio に同梱される LLVM は、LLVM プロジェクトのフルセットとは限りません。Microsoft がビルドとリンクに必要と判断した範囲が入っており、解析系のツールが省かれていることがあります。ここで見つからなかった場合は、次節の手順で補ってください。「自分の環境が壊れている」わけではありません。

5.3 足りないツールを補う

第 2 章で触れた公式 LLVM を入れます。まだ入れていなければ、次のいずれかで導入します。

winget install LLVM.LLVM

あるいは GitHub の llvm/llvm-project の Releases から Windows 用インストーラを入手します。既定では C:\Program Files\LLVM\ に入ります。

ここで、二つの話を分けて考えるのが大切です。

対象切り替え方法
(A) ビルドに使うコンパイラ・リンカclang-cl、lld-link、llvm-libMSBuild の LLVMInstallDir（第 2 章 2.4 節）
(B) 手作業で叩く解析ツールllvm-profdata、llvm-cov、llvm-objdump ほかシェルの PATH

(B) だけが必要なら、(A) は同梱版のままで構いません。ただしその場合もバージョンは揃えるべきです。理由は次節で説明します。

5.3.1 PATH を通す

システムの環境変数を恒久的に書き換えるのは、後で「どのツールが使われているか分からない」状態を招きます。本書では、作業しているシェルの中だけで PATH を延長する方法を推奨します。

:: Developer Command Prompt（そのウィンドウの中だけ有効）
set PATH=C:\Program Files\LLVM\bin;%PATH%
where llvm-profdata
# Developer PowerShell（そのセッションの中だけ有効）
$env:PATH = "C:\Program Files\LLVM\bin;" + $env:PATH
where.exe llvm-profdata
スクリプトにしておく

この設定は第 5 部・第 6 部で毎回必要になります。setup-env.cmd のような短いバッチファイルをプロジェクトのルートに置いて、作業開始時に実行する習慣にしておくと楽です。第 41 章で CI に組み込むときも、この形がそのまま使えます。

5.4 バージョンを揃える

ここは PGO でつまずく人がいちばん多いところです。先に理屈を押さえておきます。

5.4.1 プロファイルはバージョン付きのバイナリ形式

PGO で生成されるプロファイルデータ（.profraw / .profdata）は、人間が読めるテキストではなく、バージョン番号を持つバイナリ形式です。そしてこの形式は LLVM のバージョンによって変わります。

PGO の作業では、二つの別々のプログラムがこのファイルを扱います。

  • プロファイルを書くのは、clang-cl が実行ファイルに埋め込んだプロファイルランタイム
  • プロファイルを読んでマージするのは、llvm-profdata

この二つのバージョンが食い違うと、次のようなエラーになります。

error: xxx.profraw: unsupported instrumentation profile format version

あるいは、マージ自体は通ったのに -fprofile-use で読み込む段階で拒否される、という形で現れることもあります。

鉄則：clang-cl と llvm-profdata のメジャーバージョンを揃える

厳密に同一ビルドである必要はありませんが、メジャーバージョンが違う組み合わせは避けてください。同梱版の clang-cl（たとえば LLVM 21）と、後から入れた公式版の llvm-profdata（たとえば LLVM 24）を混ぜる、というのが典型的な事故です。

5.4.2 バージョンを一覧する

作業を始める前に、次のコマンドで全ツールのバージョンを確認する習慣をつけてください。

clang-cl --version
lld-link --version
llvm-profdata --version
llvm-cov --version

出力例です。

clang version 21.1.0
Target: x86_64-pc-windows-msvc
Thread model: posix
InstalledDir: C:\Program Files\Microsoft Visual Studio\2026\Community\VC\Tools\Llvm\x64\bin

LLVM (http://llvm.org/):
  LLVM version 21.1.0
  Optimized build.

数字の 21 の部分が揃っていることを確認します。揃っていなければ、PATH の順序を調整するか、第 2 章の LLVMInstallDir でコンパイラ側を公式版に寄せてください。

いま全部を理解する必要はありません。llvm-profdata がこの図の中心にいることだけ頭に入れておいてください。第 26 章からこの図に戻ってきます。

5.6 ハンズオン — llvm-objdump で覗いてみる

ツールが揃っていることの確認を兼ねて、第 4 章でビルドした実行ファイルを逆アセンブルしてみましょう。

cd x64\Release
llvm-objdump -d --demangle ClangOptLab.exe > disasm.txt
オプション意味
-d実行可能なセクションを逆アセンブルする
--demangleマングルされた C++ の名前を人間が読める形に戻す

出力は数万行になるので、ファイルに落としてエディタで開きます。parse_line で検索すると、次のような箇所が見つかるはずです（アドレスは環境によって変わります）。

    3766: e8 b5 05 00 00    callq  0x3d20 <loglab::parse_line(std::basic_string_view<char, ...>, loglab::Record&)>
    376b: 84 c0             testb  %al, %al
    376d: 74 be             je     0x372d <main+0x1fd>
    ...
    3780: 49 8b 7d 00       movq   (%r13), %rdi
    3784: 48 8b 07          movq   (%rdi), %rax
    3787: 4c 89 e6          movq   %r12, %rsi
    378a: ff 50 10          callq  *0x10(%rax)
    378d: 84 c0             testb  %al, %al

出力の一例（main の内側）

読み方はまだ分からなくて構いませんが、二種類の callq があることだけ見ておいてください。この対比が、本書の第 4 部と第 5 部の出発点になります。

命令正体本書での位置づけ
callq 0x3d20 <loglab::parse_line(...)>アドレスが確定した直接呼び出し。main.cpp から別の翻訳単位の関数を呼んでいる翻訳単位の壁。LTO でこれが消えるかどうかを第 20 章で確認する
callq *0x10(%rax)レジスタが指す先を呼ぶ間接呼び出し。仮想関数テーブル経由の Filter::accept()デバーチャライズ（第 21 章）と間接呼び出しの最適化（第 32 章）の対象
この disasm.txt は保存しておいてください

第 20 章で LTO 有効時の逆アセンブルと差分を取ります。ファイル名を disasm_baseline.txt のように分かりやすく変えて、ベースラインとして残しておくと便利です。fc コマンドや Git の差分表示で比較できます。

5.7 opt-viewer について

第 10 章で使う opt-viewer は、他のツールと違って単体の実行ファイルではなく、Python スクリプトの集まりです。LLVM のソース配布物または公式インストーラの share\opt-viewer\ に置かれています。

実行には Python 3 と、いくつかのパッケージ（PyYAML、Pygments）が必要です。

python --version
pip install pyyaml pygments

使うのは第 10 章なので、いまは Python が入っているかだけ確認しておけば十分です。入っていなければ、その章までに用意してください。opt-viewer が無くても、最適化レコードの YAML を直接読むことはできます。

5.8 チェックリスト

  • clang-cl、lld-link、llvm-lib が見つかる
  • llvm-objdump、llvm-readobj が見つかる
  • llvm-profdata と llvm-cov が見つかる（無ければ公式 LLVM を導入した）
  • clang-cl と llvm-profdata のメジャーバージョンが一致している
  • llvm-objdump -d --demangle で ClangOptLab.exe を逆アセンブルできた
  • その出力に直接呼び出しと間接呼び出しの両方があることを確認した
  • ベースラインの逆アセンブル結果をファイルに保存した

5.9 まとめ

  • Clang の最適化を追う作業は、周辺ツールが主役。特に llvm-profdata は PGO の全工程に登場する
  • Visual Studio 同梱の LLVM には解析系ツールが揃っていないことがある。その場合は公式 LLVM を入れて PATH で補う
  • 「ビルドに使うコンパイラ」と「手で叩く解析ツール」は切り替え方法が別（LLVMInstallDir と PATH）
  • プロファイルデータはバージョン付きのバイナリ形式。clang-cl と llvm-profdata のメジャーバージョンは揃える
  • 逆アセンブルに現れる直接呼び出しと間接呼び出しの対比が、第 4 部・第 5 部の出発点になる

第 1 部を終えて

ここまでで、ClangCL でビルドできる環境と、最適化の効果が観察できる題材と、それを調べるための道具が揃いました。まだ最適化オプションは一つも足していません。/O2 のままです。

第 2 部では、その /O2 が何をしているのかを分解します。最適化パイプラインの構造、生成されたコードの読み方、そして「なぜこの関数はインライン化されなかったのか」をコンパイラ自身に説明させる方法。第 4 部で LTO を有効にしたとき、その効果を自分の目で確かめられるようにするための準備です。

次章では、/O2 というオプションの中身に踏み込みます。MSVC のオプションと Clang のオプションがどう対応しているのか、/O2 は -O2 と同じなのか、そして clang-cl が受け付ける -f 系オプションをどう書けばよいのか。本書でこれから追加していくオプションの、書き方の作法を固めます。
