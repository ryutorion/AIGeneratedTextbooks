第 27 章

プロファイル出力の制御
— LLVM_PROFILE_FILE と %p / %m

既定では、プロファイルはカレントディレクトリに固定の名前で出力されます。二回実行すれば二回目が一回目を上書きします。複数回・複数プロセスの実行結果を集めるには、出力先を制御する必要があります。

この章のゴール

  • 既定の出力先と命名規則を知る
  • 上書き事故が起きることを実際に確認する
  • LLVM_PROFILE_FILE のパターン指定を使い分ける
  • 複数プロセスのアプリでの採り方を知る

27.1 既定の出力

計装ビルドを実行すると、カレントディレクトリに次のようなファイルができます。

default_6242892255425663173_0.profraw

数字はバイナリごとに決まる識別子です。同じバイナリを何度実行しても、同じ名前になります。

27.1.1 上書きされることの確認

実際に確かめてみましょう。同じ名前に二回出力させ、中身を比べます。

set LLVM_PROFILE_FILE=fixed.profraw
ClangOptLab.exe 50000 2
llvm-profdata show fixed.profraw | findstr "Maximum function count"
  Maximum function count: 1300000

ClangOptLab.exe 50000 2
llvm-profdata show fixed.profraw | findstr "Maximum function count"
  Maximum function count: 1300000

二回実行しても値が同じです。足し込まれてはいません。上書きされています。

「たくさん実行したから精度が上がったはず」は間違いです

トレーニングとして何十回もアプリを起動しても、既定の設定では最後の一回ぶんしか残りません。「何回も走らせたのに効果が出ない」という失敗の、地味だが実際にある原因です。

27.2 出力先を指定する三つの方法

方法指定するもの優先順位
-fprofile-generate=<dir>ビルド時に既定の出力ディレクトリを埋め込む低
LLVM_PROFILE_FILE 環境変数実行時にファイル名（パス込み）を指定する高
プログラムから API を呼ぶ__llvm_profile_set_filename()最高

27.2.1 ビルド時に指定する

/clang:-fprofile-generate=C:\work\ClangOptLab\prof

このディレクトリが出力先になります。実行時にカレントディレクトリを気にしなくてよくなるので、実務では便利です。ただしパスがバイナリに焼き込まれるため、別のマシンで実行すると存在しないパスを指すことになります。

27.2.2 実行時に指定する

set LLVM_PROFILE_FILE=C:\work\prof\run.profraw
ClangOptLab.exe 200000 10

環境変数のほうが強いので、ビルド時の指定を上書きできます。本書ではこちらを主に使います。 トレーニングをスクリプト化するときに扱いやすいためです。

27.3 パターン指定

LLVM_PROFILE_FILE には、実行時に展開される特殊な記号を書けます。

記号展開されるもの実測での例
%pプロセス IDr-2191.profraw
%hホスト名b-vm.profraw
%mバイナリごとの識別子。同じファイルに足し込む（オンラインマージ）後述
%Nm同上。N 個のファイルに分散して競合を減らす%4m など
%t環境変数 TMPDIR の値—
%%文字としての %—

27.3.1 %p — 実行ごとに別ファイル

set LLVM_PROFILE_FILE=prof\run-%p.profraw
ClangOptLab.exe 50000 2
ClangOptLab.exe 50000 4

dir prof
  run-2191.profraw
  run-2192.profraw

両方が残りました。あとで llvm-profdata merge（第 29 章）でまとめます。実際にまとめると、二回ぶんの合計になっていることが確認できます。

llvm-profdata merge -output=both.profdata prof\run-*.profraw
llvm-profdata show both.profdata | findstr "Maximum function count"
  Maximum function count: 3900000       <- 1300000 + 2600000
Windows のバッチファイルでは % の扱いに注意

バッチファイル（.cmd / .bat）の中では % が変数展開に使われるため、二重に書く必要があります。

:: コマンドプロンプトで直接打つとき
set LLVM_PROFILE_FILE=prof\run-%p.profraw

:: バッチファイルの中に書くとき
set LLVM_PROFILE_FILE=prof\run-%%p.profraw

PowerShell ではこの問題は起きません。

$env:LLVM_PROFILE_FILE = "prof\run-%p.profraw"

27.3.2 %m — 実行時に足し込む

%m を使うと、プロセス終了時に既存のファイルへ足し込まれます。実測してみます。

set LLVM_PROFILE_FILE=m-%m.profraw

ClangOptLab.exe 50000 2
llvm-profdata show m-*.profraw | findstr "Maximum function count"
  Maximum function count: 1300000

ClangOptLab.exe 50000 2
llvm-profdata show m-*.profraw | findstr "Maximum function count"
  Maximum function count: 2600000       <- 足し込まれた

ファイルが一つで済むので、何百回も実行するトレーニングでは %p より扱いやすくなります。

%p%m
ファイル数実行回数ぶん1 つ（%Nm なら N 個）
あとで merge必要必要（形式変換のため）
実行ごとの寄与個別に確認できるできない
並列実行安全ファイルロックで競合しうる。%Nm で緩和
向いている場面数回〜数十回のトレーニング数百回以上、あるいはプロセスが多数
本書では %p を使います

実行ごとのプロファイルが個別に残っていると、「この実行だけ極端に違う」といった異常に気づけます。第 30 章の llvm-profdata overlap で、実行どうしを比べることもできます。トレーニングの回数が現実的な範囲なら、%p のほうが情報が多く残ります。

27.4 トレーニング用のスクリプト

ここまでを踏まえて、トレーニング実行のスクリプトを作ります。

@echo off
:: train.cmd — 計装ビルドを複数回実行してプロファイルを集める
setlocal

set PROFDIR=%~dp0prof
set EXE=%~dp0builds\instr\ClangOptLab.exe

if exist "%PROFDIR%" rmdir /s /q "%PROFDIR%"
mkdir "%PROFDIR%"

set LLVM_PROFILE_FILE=%PROFDIR%\run-%%p.profraw

echo [1/3] 通常のワークロード
"%EXE%" 200000 10
echo [2/3] 小さめの入力
"%EXE%"  20000 20
echo [3/3] 大きめの入力
"%EXE%" 500000  4

echo.
dir /b "%PROFDIR%"
endlocal

リスト 27-1　train.cmd

古いプロファイルを消してから始めているのが重要です。前回の残骸が混ざると、何を測ったのか分からなくなります。

27.5 複数プロセスのアプリ

実際のアプリケーションでは、子プロセスを起動したり、複数の実行ファイルが連携したりします。

  • LLVM_PROFILE_FILE は環境変数なので、子プロセスにも引き継がれます
  • そのため %p を入れておかないと、親子でファイル名が衝突します
  • 複数の実行ファイル（app.exe と tool.exe）が同時に動く場合は %m も入れると、バイナリごとに分かれます
set LLVM_PROFILE_FILE=prof\%m-%p.profraw
プロファイルはプロセス終了時に書かれます

第 26 章でも触れましたが、重要なので繰り返します。abort()、TerminateProcess()、クラッシュ——いずれの場合もプロファイルは書き出されません。テストの中でプロセスを強制終了している場合、そのぶんの実行は記録されないことになります。

どうしても必要なら、実行中に書き出す API（__llvm_profile_write_file()）を呼ぶ方法がありますが、本書では扱いません。

27.6 ハンズオン

  1. 計装ビルドを builds\instr\ に退避する
  2. 固定名で二回実行し、llvm-profdata show の値が変わらないことを確認する（上書きの実感）
  3. %p に変えて二回実行し、ファイルが二つできることを確認する
  4. リスト 27-1 の train.cmd を作る
  5. 実行して prof\ に三つの .profraw ができることを確認する
  6. それぞれのファイルサイズを見る（入力の規模で変わるはずです）

27.7 まとめ

  • 既定の出力はカレントディレクトリの固定名。複数回実行すると上書きされる
  • 出力先はビルド時（-fprofile-generate=<dir>）と実行時（LLVM_PROFILE_FILE）で指定でき、後者が優先される
  • %p はプロセス ID、%h はホスト名、%m は同じファイルに足し込む
  • 実測では %p で分けた二回ぶんを merge すると、値が合計になった
  • バッチファイル内では %%p と二重に書く
  • 環境変数は子プロセスに継承される。プロセスが複数なら %p は必須
  • トレーニングは古いプロファイルを消してから始める

次章では、そのトレーニングで「何を実行するか」を考えます。カバレッジを上げればよいのか、本番と同じ入力を使えばよいのか。ここを間違えると、PGO はむしろ性能を悪化させます。
