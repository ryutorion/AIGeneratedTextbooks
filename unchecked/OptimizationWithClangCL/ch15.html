第 15 章

ベンチマークの取り方
— ばらつき・ウォームアップ・有意差の判定

第 1 章で「測っていない最適化」を戒めました。しかし測り方が悪ければ、測らないのと大差ありません。この章では、同じバイナリの実行時間がどれだけ揺れるかを実測し、その揺れの中で「速くなった」と言うための手順を確定させます。第 3 部の締めくくりです。

この章のゴール

  • 自分の環境のノイズ床を測る
  • ばらつきの原因と、Windows でできる対策を知る
  • 交互実行（A/B インターリーブ）がなぜ効くのかを理解する
  • 本書で使う計測スクリプトを用意する
  • 「差が無い」と正しく言えるようになる

15.1 まず、何もしないで測ってみる

最適化の話をする前に、実験をひとつ。まったく同じバイナリを 30 回続けて実行し、報告された elapsed を集めます。コードは一行も変えていません。理屈のうえでは、30 回とも同じ時間になるはずです。

n = 30
最小       443.5 ms
中央値     453.9 ms
平均       461.0 ms
最大       551.9 ms
標準偏差    20.4 ms

最大 / 最小 = 1.244   ← 24.4% の開き

同一バイナリを 30 回実行した結果（実測の一例）

同じバイナリで 24% の開きが出ました。

この事実の意味は重大です。もし「最適化前」を 1 回、「最適化後」を 1 回だけ実行して比べていたら、何もしていないのに「20% 速くなった」という結論を出せてしまいます。逆に、本当に 10% 速くなった改善を「効果なし」と切り捨てることもできます。

1 回の実行時間を比べてはいけません

これが本書で最も重要な計測上の約束です。第 4 部以降、LTO や PGO の効果を測るときは必ず複数回実行し、この章で決める手順に従います。

もう少し数字を見ると、性質が分かります。

最も速かった 5 回 : 443.5  449.1  449.2  449.3  449.4
最も遅かった 5 回 : 477.1  479.2  483.8  487.9  551.9

速い側は 449 ミリ秒付近に密集していますが、遅い側は散らばっていて、551.9 という飛び抜けた値もあります。これはノイズが一方向にしか働かないことを示しています。何かが邪魔をすれば遅くなりますが、邪魔が入らないからといって理論値より速くなることはありません。

15.2 ばらつきの原因

原因内容
CPU 周波数の変動ターボブースト、省電力状態からの復帰、温度による低下
他プロセスとの競合ウイルス対策ソフト、インデックス作成、更新のダウンロード
スケジューリングどのコアに割り当てられるか。P コア／E コアの違い
キャッシュの状態直前に何が動いていたかで、L3 キャッシュの中身が変わる
ページフォルト初回アクセス時に物理メモリを割り当てるコスト
メモリの配置ASLR により、実行のたびにアドレスが変わる。キャッシュの当たり方が変わる
ディスクキャッシュ実行ファイルや入力データが OS のキャッシュに載っているかどうか

15.3 Windows でできる対策

ノイズを完全に消すことはできませんが、減らすことはできます。

電源プランを高パフォーマンスにする

コントロールパネルの電源オプションで「高パフォーマンス」を選び、詳細設定で「プロセッサの電源管理 > 最小のプロセッサの状態」を 100% にします。周波数の上下によるばらつきが小さくなります。ノート PC の場合は必ず電源に接続してください。バッテリー駆動では話になりません。

ウイルス対策ソフトの除外設定

ビルド出力フォルダを除外に登録します。実行ファイルを作り直すたびにスキャンが走ると、初回実行が大きく遅くなります。

デバッガから実行しない

Visual Studio の F5 ではなく、コマンドプロンプトから直接起動します。デバッガがアタッチされていると、ヒープの動作が変わり（デバッグヒープ）、例外処理にフックが入ります。Ctrl+F5（デバッグなしで開始）でも構いませんが、コマンドラインから測るほうが自動化しやすいでしょう。

優先度とアフィニティ（効果は限定的）

:: 高優先度で、コア 0〜3 に固定して実行する
start /high /affinity F /wait ClangOptLab.exe

固定すると再現性は上がりますが、そのコアが E コアだった場合など、本番とは違う条件になることもあります。まずは電源プランとデバッガの二つを押さえるだけで十分です。

他のことをしない

測っている間にブラウザを触らない、ビルドを走らせない。当たり前ですが、いちばん効きます。

15.4 どの統計量を使うべきか

「最小値を使え」「いや中央値だ」という議論があります。実際に確かめてみましょう。5 回を 1 組として 6 組取り、それぞれの最小値・中央値・平均を比べた結果です。

組最小中央値平均
1475.1476.3481.0
2483.5488.1487.9
3473.5476.3476.7
4479.0482.2486.0
5458.0463.6463.6
6462.6467.8466.6
組の間のばらつき
—2.07%1.89%2.10%

実測の一例

結果はどれもほぼ同じでした。最小値を使えば安定する、という単純な話ではありません。

表をよく見ると理由が分かります。組 1〜4 は 473〜483 ミリ秒あたり、組 5〜6 は 458〜467 ミリ秒あたりに固まっています。組の中でのばらつきではなく、組と組の間で全体が動いているのです。測定を続けるうちにマシンの状態が変わった、いわゆるドリフトです。

ドリフトは統計量の選択では消せません

ランダムなノイズなら、たくさん測って平均や最小を取れば減らせます。しかしドリフト——時間とともに環境がじわじわ変わる現象——は、同じ条件で何回測っても消えません。「最適化前を 10 回測ってから、最適化後を 10 回測る」という順番で比較すると、この差をまるごと拾ってしまいます。

15.5 交互実行という解決策

ドリフトへの対処は単純です。A と B を交互に実行する。

× A A A A A  B B B B B     ドリフトが A と B の差として現れる
○ A B A B A B A B A B      ドリフトが A にも B にも等しくかかる

効果を確かめるため、同じバイナリを二つ用意して（片方をコピーしただけ）交互に 10 回ずつ実行してみます。中身が同一なので、正しく測れていれば差は 0 になるはずです。

A の最小値 : 449.0 ms
B の最小値 : 451.9 ms
差         : 2.9 ms （0.65%）

同一バイナリ同士の交互実行（実測の一例）

0.65% まで縮みました。別々に測ったときの 2% から、大きく改善しています。

この 0.65% が「ノイズ床」です

差が無いことが分かっているもの同士を比べて出た差。これが、その環境・その手順で測れる限界です。今後、これより小さい差は「差が無い」と扱います。

ノイズ床は環境ごとに違います。必ず自分の環境で測ってください。そして、測定手順を変えたら測り直してください。

15.6 計測スクリプト

ここまでの内容——ウォームアップ、交互実行、最小値での比較——を実装したスクリプトです。第 4 部以降、これを使い続けます。

"""2 つのビルドを交互に実行し、最小値で比較する。"""
import argparse, re, statistics as st, subprocess, sys

PAT = re.compile(r'elapsed\s*:\s*([\d.]+)\s*ms')

def run_once(exe, args):
    out = subprocess.run([exe, *args], capture_output=True, text=True).stdout
    m = PAT.search(out)
    if not m:
        sys.exit(f'{exe}: elapsed 行が見つかりません')
    return float(m.group(1))

def main():
    p = argparse.ArgumentParser()
    p.add_argument('exe_a')
    p.add_argument('exe_b', nargs='?')
    p.add_argument('-n', type=int, default=10, help='各ビルドの実行回数')
    p.add_argument('-w', type=int, default=2, help='捨てるウォームアップ回数')
    p.add_argument('--args', nargs='*', default=[])
    a = p.parse_args()

    for _ in range(a.w):                      # ウォームアップ
        run_once(a.exe_a, a.args)
        if a.exe_b:
            run_once(a.exe_b, a.args)

    A, B = [], []
    for _ in range(a.n):                      # 交互に走らせて環境の変動を打ち消す
        A.append(run_once(a.exe_a, a.args))
        if a.exe_b:
            B.append(run_once(a.exe_b, a.args))

    def report(name, v):
        print(f'{name:<12} n={len(v)}  最小 {min(v):7.1f}  中央値 {st.median(v):7.1f}  '
              f'最大 {max(v):7.1f}  ばらつき {(max(v)/min(v)-1)*100:4.1f}%')

    report(a.exe_a, A)
    if not B:
        return
    report(a.exe_b, B)
    d = (min(B) - min(A)) / min(A) * 100
    print(f'\n最小値の差: {d:+.2f}%  ({min(B)-min(A):+.1f} ms)')
    print('※ 空試験で出た差より小さければ「差は測れなかった」と判断する')

if __name__ == '__main__':
    main()

リスト 15-1　bench.py

15.6.1 使い方

:: 1 つのビルドを測る
python bench.py x64\Release\ClangOptLab.exe -n 10 --args 200000 50

:: 2 つのビルドを比べる
python bench.py baseline\ClangOptLab.exe lto\ClangOptLab.exe -n 10 --args 200000 50

出力はこうなります。

baseline\ClangOptLab.exe  n=8  最小   474.1  中央値   476.9  最大   486.5  ばらつき  2.6%
lto\ClangOptLab.exe       n=8  最小   471.7  中央値   474.8  最大   476.3  ばらつき  1.0%

最小値の差: -0.51%  (-2.4 ms)
※ 空試験で出た差より小さければ「差は測れなかった」と判断する
ウォームアップを捨てる理由

初回の実行は、実行ファイルのディスク読み込み、ページフォルト、ウイルス対策ソフトのスキャンなどで確実に遅くなります。この値を含めると最大値が跳ね上がり、ばらつきの評価を狂わせます。スクリプトでは最初の 2 回を捨てています。

15.7 空試験を必ず行う

新しい環境で測り始めるとき、あるいは久しぶりに測るときは、まず空試験をしてください。

:: 同じ exe をコピーして、それ同士を比べる
copy x64\Release\ClangOptLab.exe x64\Release\ClangOptLab_copy.exe
python bench.py x64\Release\ClangOptLab.exe x64\Release\ClangOptLab_copy.exe -n 10 --args 200000 50

ここで出た差が、あなたの環境のノイズ床です。この数字をメモしてください。 第 4 部以降、「LTO で 0.8% 速くなった」という結果が出たとき、ノイズ床が 0.65% なら「たぶん差は無い」、0.1% なら「差はありそうだ」と判断できます。

15.8 報告の仕方

本書では、性能の変化を次の形で書きます。

× 避ける書き方○ 本書の書き方
「LTO で 5% 速くなりました」「最小値で 5.2% 短縮（n=10、交互実行、ノイズ床 0.7%）」
「効果がありませんでした」「差は 0.3% で、ノイズ床（0.7%）を下回った。この環境では差は測れなかった」
「劇的に速くなりました」数字を書く

「差が測れなかった」は「効果が無い」とは違います。測定精度が足りないのか、本当に差が無いのか、この題材では効かないだけなのか——それを区別するには、より長く走らせるか、プロファイラで内訳を見るか、第 10 章の最適化レコードでコンパイラの判断が変わったかどうかを確認します。

時間が動かなくても、判断は変わっているかもしれません

これが本書で最適化レコードを重視する理由です。実行時間は環境ノイズに埋もれますが、「インライン化された箇所が 4 件増えた」という事実にノイズはありません。時間で語れないときは、コンパイラの判断で語る。 第 4 部以降、この二本立てで評価していきます。

15.9 ハンズオン

  1. 電源プランを高パフォーマンスにする（ノート PC なら電源に接続する）
  2. リスト 15-1 の bench.py を作る
  3. LogLab を 1 つだけ渡して 20 回実行し、ばらつきの割合を確認する
  4. exe をコピーして空試験を行い、ノイズ床をメモする
  5. 参考までに、Visual Studio から F5 で起動した場合の実行時間も見てみる（コマンドラインより遅いはずです）

15.10 まとめ

  • 同じバイナリを 30 回実行すると、最大 24% の開きが出た。1 回の実行を比べるのは無意味である
  • ノイズは一方向にしか働かない。邪魔が入れば遅くなるだけで、速くはならない
  • 最小値・中央値・平均のどれを選んでも、ドリフトは消せない
  • 解決策は交互実行。同一バイナリ同士の差が 2% から 0.65% に縮んだ
  • 新しい環境ではまず空試験を行い、ノイズ床を把握する。それより小さい差は報告しない
  • 報告には必ず「何回」「どう測ったか」「ノイズ床」を添える
  • 時間で語れないときは、最適化レコードでコンパイラの判断の変化を語る
