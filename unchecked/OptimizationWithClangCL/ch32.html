第 32 章

PGO は何を変えたか
— 分岐レイアウト、ホット/コールド分割、インライン判断

前章で見たとおり、実行時間への効果は環境に左右されました。しかしコンパイラの判断の変化は決定的で、環境によりません。何が変わったのか。最適化レコードを突き合わせると、直感に反する事実が出てきます。PGO はインライン化を減らしていました。

この章のゴール

  • PGO の前後で最適化レコードを比較する
  • しきい値が呼び出し箇所ごとに変わったことを確認する
  • 第 4 章で仕込んだ伏線を回収する
  • 判断の変化を根拠に、効果の理由を説明できるようになる

32.1 比較の方法

第 10 章で作った集計スクリプトを使い、PGO 有り／無しで最適化レコードを比べます。

:: PGO 無し
clang-cl /c /O2 /std:c++23 /Iinclude ^
    /clang:-fsave-optimization-record src\*.cpp

:: PGO 有り
clang-cl /c /O2 /std:c++23 /Iinclude ^
    /clang:-fprofile-use=app.profdata ^
    /clang:-fsave-optimization-record src\*.cpp

32.2 予想と結果

まず、直感的な予想を立ててみましょう。「ホットな箇所が分かるのだから、そこを積極的にインライン化するはずだ」——多くの人がそう考えます。結果はこうでした。

レコードPGO 無しPGO 有り
!Passed inline Inlined639614（減少）
!Missed inline TooCostly3193（3 倍）
!Missed inline NoDefinition59204
!Analysis pgo-instrumentation bfi-verify046（新規）

実測の一例（全 5 翻訳単位の合計）

インライン化は 639 件から 614 件に減り、「コストが高すぎる」という拒否が 31 件から 93 件へ 3 倍になりました。

32.3 しきい値が動いた

理由は、インライン化のしきい値の分布を見ると一目で分かります。第 11 章で「threshold は呼び出し箇所ごとに決まる」と書いた、その値です。

実測の一例

きれいな移動が起きています。

  • 337 が 414 件 → 0 件。 代わりに 112 が 416 件
  • 225 が 173 件 → 1 件。 代わりに 75 が 172 件
  • しきい値 45（コールド用）も 15 件から 28 件に増加

337 の約 3 分の 1 が 112、225 の 3 分の 1 が 75。PGO は、ほぼすべての呼び出し箇所でしきい値を 3 分の 1 に絞りました。 そしてしきい値が上がった箇所は一つもありませんでした。

なぜ全部下がったのか

LogLab で最もホットな基本ブロックの通過回数は 1 億 1600 万回でした（第 30 章）。それに比べれば、他のほとんどの場所は「相対的にコールド」です。プロファイルを得たコンパイラは、その相対関係に基づいてしきい値を割り当てます。

つまり PGO がやったのは、「本当にホットな一点を除いて、あとは全部コールド扱いにする」という大胆な絞り込みでした。プロファイルが無いときの一律 225／337 は、この題材に対しては「全体的に甘すぎた」ということになります。

32.4 伏線の回収 — handle_error

第 4 章で、私たちは Stats::add() のこの分岐に [[unlikely]] を意図的に書きませんでした。

// 1000 行に 3 行程度しか通らない経路。
// ここに [[unlikely]] は意図的に書かない（第 32 章で PGO に見つけさせる）。
if (r.level == Level::Error) {
    handle_error(r);
}

第 30 章の llvm-cov で、この分岐が 74,200 回中 258 回（0.348%）しか成立しないことを確認しました。では、そのプロファイルを渡されたコンパイラは何をしたか。

PGO 無し:  !Passed  Inlined    cost=95  threshold=225   ← 展開された
PGO 有り:  !Missed  TooCostly  cost=85  threshold=75    ← 拒否された

handle_error のインライン化が拒否されました。

コストは 95 から 85 へわずかに下がっているのに、しきい値が 225 から 75 に絞られたため、判定が逆転しています。

これが効果の正体（の一部）です

handle_error は「稀だが重い」処理でした。文字を 1 バイトずつ走査するループを二つ含んでいます。これが Stats::add() に展開されると、1000 回に 3 回しか使われないコードが、ホットな関数の本体を膨らませます。

命令キャッシュに載るのは実行されるコードだけではありません。展開された handle_error の本体も、Stats::add() の一部としてキャッシュラインを占有します。第 11 章で「インライン化は測ってみないと分からない」と書いた、その悪い側が起きていたわけです。

PGO はそれを見抜いて、展開をやめさせました。この改善が実行時間に現れるかどうかは、その CPU の命令キャッシュに余裕があるかどうかで決まります（第 31 章）。

32.4.1 コードの配置も変わった

実行ファイル内での関数の位置を比べると、こうなっていました。

ビルドStats::addStats::handle_error
PGO 無し0x39000x3af0（すぐ後ろ）
PGO 有り0x34200x2ac0（約 2.4 KB 離れている）

PGO 無しでは handle_error が Stats::add の直後に置かれており、同じ領域に居ます。PGO 有りでは離れた場所に移されました。ホットなコードどうしを近くに集める配置になっています。

32.5 他に何が拒否されたか

tokenizer.cpp でも拒否が起きていました。

[PGO で拒否] cost=150 threshold=75  std::string_view::find(...)
[PGO で拒否] cost=140 threshold=75  std::string_view::find(...)
[PGO で拒否] cost=100 threshold=75  loglab::(匿名)::next_field(...)
[PGO で拒否] cost=100 threshold=75  loglab::(匿名)::next_field(...)
[PGO で拒否] cost=100 threshold=75  loglab::(匿名)::next_field(...)

next_field は parse_line の中から 4 回呼ばれます。PGO 無しでは全部が展開され、parse_line が大きく膨らんでいました。PGO 有りでは、そのうち 3 箇所が拒否されています。

「インライン化＝善」ではありません

第 11 章の実測で、しきい値を上げても速くならないことは確認していました。今回はその先です。環境 A では、しきい値を下げたほうが速くなりました。

小さな関数を呼び出す形のまま残すと、コードサイズが抑えられ、ホットループが命令キャッシュに収まりやすくなります。呼び出しのコストはありますが、それを上回る得があった、ということです。

ただしこれは LogLab という題材での結果です。別のコードでは逆になることもあります。だから測るのです。

興味深いことに、.text はわずかに大きくなり、call 命令は増えています。第 20 章の LTO では逆でした（call が減り、.text も減った）。にもかかわらず、環境 A で速くなったのは PGO のほうです。

機械語の指標は目的ではありません

第 8 章で call 命令を数える手順を用意し、第 20 章でそれを使いました。しかし call が減ること自体が目的ではありません。あれは「LTO が働いたことの証拠」として数えたのです。

PGO の効果は別の形で現れます。命令の総数ではなく、ホットな経路にどれだけコードが詰まっているか。 全体が少し大きくなっても、ホットループが小さくなれば速くなります。指標は最適化の種類ごとに選ぶ必要がある、ということです。

32.7 間接呼び出しについて

第 21 章で、Filter::accept() の間接呼び出しはデバーチャライズできないと結論しました。実装が三つあるためです。

PGO には、実装が複数あっても使える手があります。間接呼び出しの投機的展開（indirect call promotion）です。「この呼び出しの 90% は LevelFilter::accept に行く」と分かれば、次のような形に書き換えられます。

if (呼び先 == LevelFilter::accept) {
    ... LevelFilter::accept の本体をインライン展開 ...
} else {
    呼び先を間接呼び出し;         // 残りの 10%
}

第 30 章で見たプロファイルには、この判断のための情報（IndirectCall profile）が含まれていました。

ただし LogLab では、機械語上の間接呼び出しは 8 個から 9 個へと、むしろ増えています。三つのフィルタが順に呼ばれる構造なので、特定の呼び先に強く偏っているわけではないためです。この最適化が効くのは「ほぼ一つの実装に集中している」場合で、その点では第 21 章のデバーチャライズと条件が似ています。

32.8 手で [[unlikely]] を書く場合との比較

ここまで見てきた効果の一部は、属性を手で書いても得られます。

if (r.level == Level::Error) [[unlikely]] {
    handle_error(r);
}
手で書くPGO
正確さ書いた人の想像実測
対象書いた箇所だけ全箇所
粒度ホット／コールドの二値回数そのもの
コードの変更必要不要
保守コードが変われば見直しが要るプロファイルを取り直す（第 34 章）
ビルドの手間なし三段階

第 32 章の実測では、しきい値が変わった箇所が 600 以上ありました。これを手で書くのは現実的ではありません。一方、PGO の仕組みを持ち込めない事情があるなら、最もホットな数箇所に属性を書くのは十分に有効な手です。

両立もできます

[[likely]] / [[unlikely]] とプロファイルが食い違った場合、Clang はプロファイルを優先します。属性は「プロファイルが無いときの保険」として機能するので、両方書いておくのは合理的です。

32.9 まとめ — 何が起きたのか

説明を一つにまとめます。

LogLab の実行時間の大半は parse_line とその内部に集中している。プロファイルの無いコンパイラは、この一点集中を知らず、一律のしきい値で全体をインライン展開していた。その結果、稀にしか通らない handle_error のような重いコードまでホットな関数に取り込まれ、ホットループが必要以上に膨らんでいた。

PGO はこの集中を数字で示し、コンパイラはしきい値を 3 分の 1 に絞った。600 以上の呼び出し箇所で判断が変わり、handle_error を含む複数の展開が取りやめになった。ここまでは決定的な事実で、どの環境でも同じ結果になる。

その結果ホットな経路のコードが小さくなった。それが実行時間に現れるかどうかは、命令キャッシュに余裕があるかどうか——つまり CPU 次第である。環境 A では 6.5〜9.0% の短縮として現れ、環境 B では現れなかった（第 31 章 31.3.2 節）。

32.10 ハンズオン

  1. PGO 有り／無しで最適化レコードを生成する
  2. 第 10 章の summarize.py で件数を比較する
  3. Inlined が減り、TooCostly が増えていることを確認する
  4. Threshold の値を集計し、分布が移動していることを確認する
  5. stats.opt.yaml で handle_error のレコードを探し、判定が逆転していることを確認する
  6. llvm-objdump --syms で Stats::add と handle_error の位置関係を比べる

32.11 まとめ

  • PGO はインライン化を減らした。 639 件 → 614 件、拒否は 31 件 → 93 件
  • しきい値が呼び出し箇所ごとに 3 分の 1 に絞られた（337→112、225→75）。上がった箇所は一つも無かった
  • 第 4 章で仕込んだ handle_error の展開が、cost=85 / threshold=75 で拒否された
  • コードの配置も変わり、コールドな関数がホットな関数から離された
  • .text と call の数は増えたのに速くなった。指標は最適化の種類ごとに選ぶ
  • 間接呼び出しの投機的展開は、呼び先が一つに偏っているときに効く。LogLab では偏りが足りなかった
  • ここで見た判断の変化はすべて決定的である。実行時間に現れるかどうかとは別の話（第 31 章）
  • 手で [[unlikely]] を書くのは有効だが、600 箇所を手で書くことはできない

次章では、マルチスレッドのプログラムで計装するときの問題を扱います。カウンタの更新は複数スレッドから同時に起こりえます。それを正確にする -fprofile-update=atomic というオプションがありますが、実測したところ計装ビルドが 7 倍以上遅くなりました。
