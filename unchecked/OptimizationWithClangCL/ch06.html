第 6 章

/O2 の正体
— clang-cl と MSVC のオプション対応関係

本書はこれから多くのオプションを追加していきます。その前に、clang-cl がオプションをどう解釈するのかを押さえておきます。ここを飛ばすと「書いたのに効かない」という、気づきにくい失敗を繰り返すことになります。

この章のゴール

  • clang-cl が持つ「二重の語彙」を理解する
  • /O2 が LLVM 内部で何になるかを自分で確認する
  • /clang: と -mllvm の使い分けを覚える
  • 黙って無視されるオプションの存在を知り、検出できるようにする

6.1 clang-cl は「MSVC の顔をした Clang」

clang-cl.exe は、Clang 本体とは別のコンパイラではありません。同じ Clang に、MSVC 互換のコマンドライン解釈をかぶせたドライバです。つまり内部では、受け取った /O2 のような MSVC 形式のオプションを Clang 内部の形式に翻訳しています。

この構造から、二つのことが導かれます。

  • MSVC のオプションがすべて対応しているわけではない（対応表に無いものは無視される）
  • Clang 固有の機能を使うには、MSVC 形式ではない書き方が必要になる

本書で扱う LTO や PGO は、まさにこの「Clang 固有の機能」です。書き方の作法をここで固めます。

6.1.1 翻訳結果を確認する — -###

-### を付けると、コンパイルを実行せずに「実際に起動されるコマンドと引数」を表示できます。オプションの効果を確認する最も確実な手段です。

clang-cl /c /O2 src\tokenizer.cpp -###

出力は長いので、興味のある部分だけ取り出します。

:: Developer Command Prompt
clang-cl /c /O2 src\tokenizer.cpp -### 2>&1 | findstr /C:"-O"
# Developer PowerShell
(clang-cl /c /O2 src\tokenizer.cpp -### 2>&1) -split ' ' | Select-String '^"-O'
この確認手段を覚えておいてください

本書ではこれ以降、「オプションが効いているか」を疑うたびに -### に戻ってきます。第 3 章のビルドログ確認が「どのオプションが渡ったか」を見るものだとすれば、-### は「渡ったオプションが内部で何になったか」を見るものです。

6.2 /O2 は -O2 だった

実際に確認すると、MSVC 形式の最適化オプションは次のように翻訳されています。

clang-cl に渡すもの内部で使われる Clang の最適化レベル備考
/Od-O0最適化なし
/O1-Os速度ではなくサイズ優先。-O1 ではない
/O2-O2本書の出発点
/Ox-O2/O2 と同じ
/Ot-O2単独で指定した場合

注目すべきは /O1 です。MSVC における /O1 は「サイズ優先の最適化」なので、clang-cl はこれを -O1 ではなく -Os に対応づけています。「レベルを一段下げたつもり」で /O1 を指定すると、意味が変わることになります。

6.3 -O3 の罠

ここで多くの人がつまずきます。「/O2 が -O2 なら、-O3 を指定すればもっと最適化されるのでは」と考えて、次のように書きます。

clang-cl /c -O3 src\tokenizer.cpp

これは動きません。正確には、エラーにはならないのに何の効果もありません。-### で確認すると、内部には -O がひとつも渡っていないことが分かります。つまり最適化レベルは -O0 のままです。

唯一の手がかりは、次の警告です。

clang-cl: warning: argument unused during compilation: '-O3' [-Wunused-command-line-argument]
この警告は MSBuild のビルドでは埋もれます

Visual Studio の出力ウィンドウは既定で詳細度が低く、警告の数も多いため、この一行に気づくのは困難です。「最適化オプションを足したのに速くならない」と悩んだときは、まず -### で内部の -O レベルを確認してください。足したつもりのオプションが、足した瞬間に最適化を無効化していたという事態は実際に起こります。

正しい書き方は次のとおりです。

clang-cl /c /clang:-O3 src\tokenizer.cpp

6.4 オプションの渡し方 — 三つの流儀

clang-cl に対するオプションの渡し方は三種類あります。この区別が本書の残り全体で効いてきます。

6.4.1 (a) MSVC 形式 — そのまま書く

/O2、/Zi、/Ob2、/EHsc など。Visual Studio のプロパティページが生成するのはすべてこの形式です。clang-cl の対応表に載っているものだけが翻訳されます。

6.4.2 (b) Clang 形式 — /clang: を付ける

/clang: に続けて書いたものは、翻訳されずにそのまま Clang のフロントエンドに渡されます。

/clang:-O3
/clang:-Rpass=inline
/clang:-fsave-optimization-record

ここで重要な事実があります。一部の -f 系オプションは /clang: なしでも通りますが、通らないものもあります。 しかも通らない場合はエラーではなく警告です。実測した結果が次の表です。

オプション/clang: なしで直接渡す
-flto=thin通る
-fprofile-generate / -fprofile-use=通る
-fcs-profile-generate通る
-fwhole-program-vtables通る
-fprofile-update=atomic通る
-mllvm <opt>通る
-Rpass=...通らない（unknown argument ignored in clang-cl）
-fsave-optimization-record通らない（同上）
-O3通らない（argument unused）
本書の方針：Clang 形式には常に /clang: を付ける

どれが通ってどれが通らないかを暗記する必要はありません。Clang 形式のオプションには一律で /clang: を付けると決めてしまえば、この問題は起きません。/clang:-flto=thin のように、通るものに付けても問題ありません。本書では以後この書き方に統一します。

6.4.3 (c) LLVM 内部オプション — -mllvm

フロントエンドではなく、LLVM の最適化パスそのものが持つ内部オプションを触るための入口です。第 11 章で使う -inline-threshold がこれにあたります。

-mllvm -inline-threshold=500
-mllvm は非公式な裏口です

これらは LLVM の開発者向けデバッグオプションであり、互換性の保証がありません。オプション名も既定値も、LLVM のバージョンが上がると予告なく変わりえます。実験や調査には有用ですが、製品のビルド設定に恒久的に残すべきものではありません。第 11 章でこの点を改めて扱います。

6.5 /Ob — インライン展開のレベル

最適化レベルとは別に、インライン展開だけを制御するオプションがあります。LogLab のような小さな関数が多いコードでは、これが効きます。

オプション意味実測（/O2 と併用）
/Ob0インライン展開を行わない展開されない
/Ob1inline 指定のあるものだけ展開されない
/Ob2コンパイラの判断で展開（Release の既定）展開される
/Ob3/Ob2 より積極的展開される

実測の欄は、次のような小さなコードで -Rpass=inline（第 9 章）を使って確認した結果です。

int helper(int a, int b) { return a * b + 7; }
int caller(int n) {
    int s = 0;
    for (int i = 0; i < n; ++i) s += helper(i, s);
    return s;
}

/Ob0 は「インライン化を止めたときの挙動」を調べる道具として便利です。ある関数がインライン化に依存して速くなっているのかどうかを、切り分けるのに使えます。

6.7 MSBuild でこれらを書く

プロパティページに対応する項目が無いオプションは、次の場所に書きます。

構成プロパティ > C/C++ > コマンド ライン > 追加のオプション

複数書く場合は空白またはあらためて改行で区切ります。第 3 章で確認したとおり、ここに書いた内容がコマンドラインの末尾に付きます。後から来たオプションが優先されるため、たとえばプロパティページで /O2 を選んだうえで、ここに /clang:-O3 を書けば -O3 が使われます。

6.7.1 ハンズオン — 確認してみる

LogLab のプロジェクトで、追加のオプションに次を書いてビルドし直してください。

/clang:-O3

ビルドログ（第 3 章 3.5.2 節）で clang-cl.exe の行を確認し、末尾に /clang:-O3 が付いていることを見ます。そのうえで実行し、チェックサムが 0x0e8685105a08f105 のまま変わらないことを確認してください。

実行時間はどうでしょうか。おそらく、目に見えるほどの差は出ません。-O3 は -O2 より少しだけ積極的なだけで、劇的な違いはありません。 なぜそうなのかは次章のパイプラインの話で分かります。確認できたら /clang:-O3 は消して、/O2 に戻しておいてください。

6.8 まとめ

  • clang-cl は MSVC 形式のオプションを Clang 内部の形式に翻訳する。対応表に無いものは黙って消える
  • /O2 → -O2、/O1 → -Os（-O1 ではない）、/Od → -O0
  • clang-cl -O3 は効かない。/clang:-O3 と書く。警告は出るが埋もれやすい
  • Clang 形式のオプションには一律 /clang: を付ける、と決めてしまうのが安全
  • LLVM のパス内部を触るのは -mllvm。ただし互換性の保証はない
  • 疑わしいときは -### で「内部で何になったか」を確認する

次章では、その -O2 が具体的に何をしているのかを見ます。LLVM の最適化パイプラインの構造、-O1 から -O2、-O3 へと何が足されていくのか、そしてなぜ -O3 にしても大して変わらないのか。パイプラインを実際に表示させて確認します。
