第 7 章

LLVM 最適化パイプライン概観
— -O0 から -O3 まで、何が足されていくのか

前章で /O2 が -O2 であることは分かりました。では -O2 とは何なのか。この章では最適化パイプラインの構造を眺め、レベルごとに何が加わるのかを実際に表示させて確認します。LTO と PGO がどこに効くのかを理解するための土台です。

この章のゴール

  • コンパイラの三層構造と、最適化が行われる場所を理解する
  • LLVM IR を実際に出力して、最適化の前後を見比べる
  • 最適化パイプラインを表示させ、その構造を読む
  • -O1 / -O2 / -O3 の差が何なのかを具体的に知る

7.1 コンパイラの三層構造

Clang / LLVM は大きく三つの層に分かれています。

最後の一行が本書の主題そのものです。LTO も PGO も、新しい最適化アルゴリズムを追加するものではありません。 どちらも、既存のミドルエンドに「より多くの情報」または「より多くの機会」を与える仕組みです。だからこそ、まずミドルエンドが何をしているかを知る必要があります。

7.2 LLVM IR を見てみる

百聞は一見に如かず、です。実際に IR を出力してみましょう。

clang-cl /c /O2 /clang:-emit-llvm /clang:-S sample.cpp

.ll という拡張子のテキストファイルが生成されます。次のような小さなコードで試すのが分かりやすいでしょう。

int helper(int a, int b) { return a * b + 7; }
int caller(int n) {
    int s = 0;
    for (int i = 0; i < n; ++i) s += helper(i, s);
    return s;
}

リスト 7-1　sample.cpp

7.2.1 /Od のときの IR

define dso_local noundef i32 @"?helper@@YAHHH@Z"(i32 noundef %0, i32 noundef %1) #0 {
  %3 = alloca i32, align 4
  %4 = alloca i32, align 4
  store i32 %1, ptr %3, align 4
  store i32 %0, ptr %4, align 4
  %5 = load i32, ptr %4, align 4
  %6 = load i32, ptr %3, align 4
  %7 = mul nsw i32 %5, %6
  %8 = add nsw i32 %7, 7
  ret i32 %8
}

引数がいったんスタック（alloca）に書き出され（store）、すぐに読み戻されて（load）から計算されています。これはフロントエンドが素直に翻訳した結果で、C++ の変数を機械的にメモリ上の箱として扱っています。

7.2.2 /O2 のときの IR

; Function Attrs: mustprogress nofree norecurse nosync nounwind sspstrong willreturn memory(none) uwtable
define dso_local noundef i32 @"?helper@@YAHHH@Z"(i32 noundef %0, i32 noundef %1) local_unnamed_addr #0 {
  %3 = mul nsw i32 %1, %0
  %4 = add nsw i32 %3, 7
  ret i32 %4
}

メモリ操作がすべて消え、掛けて足して返すだけになりました。これを行ったのが mem2reg と sroa というパスです。最適化の第一歩は、ほぼ常にこの「メモリからレジスタへ」の変換です。 これが済まないと、後続の最適化はほとんど何もできません。

また、関数の上に memory(none)（メモリに触らない）、nofree、willreturn といった属性が付いていることにも注目してください。これらは後続のパスが判断に使う情報で、LTO を有効にすると翻訳単位をまたいでこれらが伝播するようになります（第 20 章）。

名前が読めない場合

@"?helper@@YAHHH@Z" は MSVC 形式にマングルされた名前です。llvm-undname で元に戻せます。

echo ?helper@@YAHHH@Z | llvm-undname
int __cdecl helper(int, int)

7.3 パイプラインを表示する

-O2 が具体的にどんなパスの並びなのかは、LLVM 自身に聞くことができます。

clang-cl /c /O2 -mllvm -print-pipeline-passes sample.cpp

長大な一行が出力されます。冒頭はこうなっています（実際の出力から抜粋）。

annotation2metadata,forceattrs,declare-to-assign,inferattrs,coro-early,
function<eager-inv>(lower-expect,simplifycfg<...>,sroa<modify-cfg>,early-cse<>),
openmp-opt,ipsccp,called-value-propagation,globalopt,
function<eager-inv>(mem2reg,instcombine<...>,simplifycfg<...>),
always-inline,require<globals-aa>, ...

7.3.1 読み方 — 入れ子の意味

この文字列は、パスの階層構造を表しています。

表記意味
括弧の外側に直接あるものモジュール（＝翻訳単位）全体に対して 1 回動くパス
function(...)各関数に対して順に動くパス群
cgscc(...)呼び出しグラフの強連結成分ごとに動くパス群。インライン化はここ
loop(...)各ループに対して動くパス群
<...>そのパスに与えられたパラメータ

この入れ子は「同じパスが何度も出てくる」理由でもあります。たとえば instcombine（命令の組み合わせによる簡約）や simplifycfg（制御フローの整理）は、パイプライン全体を通して十数回登場します。あるパスが変換を行うと、その結果としてまた別の簡約の機会が生まれるためです。

最適化は「掃除」と「変換」の繰り返し

LLVM の最適化パイプラインは、大きな変換を一発で決めるのではなく、小さな整理（instcombine、simplifycfg、early-cse）と大きな変換（inline、loop-vectorize、gvn）を交互に繰り返す構造をしています。インライン化が「最適化の入り口」と呼ばれるのは、インライン化そのものが速いからではなく、インライン化のあとに掃除のパスが働くと、定数畳み込みやデッドコード削除が一気に進むからです。第 11 章で改めて扱います。

7.4 -O レベルの実際の差

各レベルのパイプラインを取り出して比較すると、次のことが分かります。

7.4.1 -O0 はほとんど何もしない

-O0 のパイプラインはごく短く、実質的に always-inline（__forceinline の処理）くらいしか行いません。「最適化を切る」というより「最適化パイプラインを組み立てない」という状態です。

7.4.2 -O1 でほぼすべてが揃う

意外に思われるかもしれませんが、最適化パスの大半は -O1 の時点で有効になっています。mem2reg、sroa、instcombine、simplifycfg、インライナ、ループ最適化の基本、そしてループのベクトル化までが -O1 に含まれます。

7.4.3 -O2 が -O1 に加えるもの

実測して差分を取ると、次のパスが追加されます。

パスやること
gvn大域的な共通部分式の削除。同じ計算の使い回し
dseデッドストア除去。誰も読まない書き込みを消す
slp-vectorizerループ以外の場所で、隣接する演算をまとめて SIMD 化する
jump-threading結果が分かっている分岐を飛ばして直結する
correlated-propagation分岐条件から導ける値の情報を伝播する
aggressive-instcombineより踏み込んだ命令の簡約
constraint-elimination比較の関係から冗長な条件を消す
mldst-motionロード／ストアの移動
speculative-execution投機的な実行のための命令移動

7.4.4 -O3 が -O2 に加えるもの

ここが前章の答えです。-O3 が追加するのは、たった三つです。

パスやること
argpromotionポインタ渡しの引数を値渡しに昇格させる
callsite-splitting呼び出し箇所を条件ごとに分割し、それぞれで特殊化しやすくする
chrControl Height Reduction。分岐の入れ子を平坦化する

加えて、-O3 ではインライン化のしきい値も引き上げられます。しかし追加されるパス自体は三つだけです。前章で /clang:-O3 を試して差が出なかったのは、これが理由です。

chr は PGO を待っている

三つのうち chr（Control Height Reduction）は、「どの分岐がホットか」の情報が無いとほとんど何もできません。プロファイルがあって初めて本領を発揮するパスです。つまり -O3 の一部は、PGO と組み合わせて初めて意味を持ちます。第 32 章で、PGO を有効にした状態の最適化レコードを見ると、このパスが働き始めるのを確認できます。

7.5 覚えておきたい主要パス

本書の残りで名前が出てくるものを、役割別にまとめておきます。すべてを覚える必要はありませんが、リマーク（第 9 章）や最適化レコード（第 10 章）を読むときに、パス名から見当が付くと理解が速くなります。

分類パス役割
土台mem2reg / sroaメモリ上の変数を SSA のレジスタに昇格させる。すべての前提
instcombine / simplifycfg命令と制御フローの整理。何度も繰り返し動く
関数間inlineインライン展開。本書で最も重要なパス（第 11 章）
globalopt / ipsccpグローバル変数の最適化、関数間の定数伝播
ループlicmループ不変式の外出し
loop-unrollループ展開
loop-vectorizeループの SIMD 化（第 9 章でリマークを読む）
冗長性除去gvn同じ値を計算し直さない
dse読まれない書き込みを消す
配置hot-cold-splitめったに通らない部分を別の関数に切り出す（PGO 前提）
chr分岐の平坦化（PGO 前提、-O3）

最後の二つに注目してください。プロファイルがなければ働かないパスが、最初から用意されているのです。第 5 部で PGO を有効にするとき、私たちは新しい最適化を追加するのではなく、眠っていたこれらのパスを起こすことになります。

7.6 ハンズオン — LogLab で確かめる

実際に手を動かして確認しましょう。Developer Command Prompt でプロジェクトのフォルダに移動し、次を実行します。

clang-cl /c /O2 /std:c++23 /Iinclude src\tokenizer.cpp ^
  /clang:-emit-llvm /clang:-S

tokenizer.ll が生成されます。エディタで開き、次を確認してください。

  1. parse_line のマングル名で検索し、関数定義を見つける
  2. その中に next_field や parse_uint の呼び出しが残っていないこと（同じ翻訳単位内なのでインライン化済み）
  3. 一方、std::string_view::find にあたる標準ライブラリの呼び出しがどう扱われているか（マングル名は llvm-undname で戻せます）

次に、同じことを main.cpp でやってみます。

clang-cl /c /O2 /std:c++23 /Iinclude src\main.cpp ^
  /clang:-emit-llvm /clang:-S

main.ll の中で parse_line を探すと、今度は call 命令として残っているはずです。定義が別の翻訳単位にあるため、中身が見えず、インライン化できないからです。

これが「翻訳単位の壁」の正体

tokenizer.ll の中では消えている呼び出しが、main.ll の中では残っている。この差が、第 4 部で LTO を導入する動機のすべてです。第 20 章では、LTO を有効にしたあとの IR を同じ方法で取り出し、この call がどうなるかを確認します。いま生成した main.ll は保存しておいてください。

7.7 まとめ

  • 最適化のほとんどはミドルエンドで LLVM IR に対して行われる。言語も CPU も関係ない層である
  • LTO も PGO も新しい最適化ではない。ミドルエンドに機会と情報を与える仕組みである
  • IR は /clang:-emit-llvm /clang:-S でテキストとして取り出せる
  • 最適化の第一歩は mem2reg / sroa による「メモリからレジスタへ」の変換
  • パスの大半は -O1 で揃う。-O2 は 9 つほど、-O3 はわずか 3 つを追加するだけ
  • hot-cold-split や chr のように、プロファイルがないと働かないパスが最初から用意されている

次章では、IR よりもう一段下、実際に生成された機械語を見る方法を扱います。/FA によるアセンブリリスト、llvm-objdump による逆アセンブル、Visual Studio の逆アセンブルウィンドウ。三つの手段の使い分けと、最適化の痕跡をどこに探せばよいかを整理します。
