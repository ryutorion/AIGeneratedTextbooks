第 17 章

Full LTO を有効にする
— -flto と lld-link への切り替え

設定そのものはオプション一つです。しかし「設定したつもりで効いていない」という状態が起きやすいところでもあります。確認の手順をセットで身につけます。

この章のゴール

  • LogLab で Full LTO を有効にする
  • .obj がビットコードになったことを確認する
  • 最小構成で call が消えるところを見る
  • リンク時の最適化レベルを制御する方法を知る

17.1 オプション

構成プロパティ > C/C++ > コマンド ライン > 追加のオプション

/clang:-flto

第 6 章で決めた方針どおり、Clang 形式のオプションには /clang: を付けます。-flto は /clang: 無しでも通りますが、統一しておくほうが安全です。

すべての構成に設定してください

第 3 章で確認したとおり、プロパティページの左上を「すべての構成／すべてのプラットフォーム」にしてから編集します。ただし LTO は Debug 構成では意味がありません（/Od なので最適化しない）。実務では Release 構成だけに設定するのが普通です。本書でも Release だけで構いません。

17.2 リンカ側の確認

コンパイラ側の設定は不要ですが、リンカが lld-link であることを確認してください。第 3 章 3.6 節の内容です。

<!-- Directory.Build.props または .vcxproj -->
<PropertyGroup>
  <UseLldLink>true</UseLldLink>   <!-- ClangCL の既定値。念のため確認 -->
</PropertyGroup>

ビルドログ（第 3 章 3.5.2 節）で lld-link.exe が起動されていることを目で見て確認するのが確実です。

17.3 .obj を確認する

ビルドしたら、x64\Release\ の .obj を調べます。

llvm-readobj --file-headers x64\Release\tokenizer.obj

次のように出れば、LTO が効いています。

llvm-readobj: warning: 'tokenizer.obj': bitcode files are not supported

逆に COFF のヘッダが表示されたら、-flto が渡っていません。追加のオプション欄のタイプミスか、設定した構成が違うかのどちらかです。第 6 章で扱ったとおり、clang-cl は理解できないオプションを警告だけ出して無視するので、静かに失敗します。

サイズでも見分けられます

ビットコードの .obj は、同じソースの COFF 版とサイズが大きく異なります。「リビルドしたら .obj のサイズが一斉に変わった」のも、LTO が効いた合図です。

17.4 最小構成で効果を見る

LogLab はファイルが多いので、まずは 2 ファイルの最小例で確かめましょう。第 16 章の scale の例をそのまま使います。

:: lib.cpp / app.cpp を用意して

:: (A) LTO なし
clang-cl /c /O2 app.cpp lib.cpp
lld-link app.obj lib.obj /out:nolto.exe ...

:: (B) Full LTO
clang-cl /c /O2 /clang:-flto app.cpp lib.cpp
lld-link app.obj lib.obj /out:lto.exe ...

それぞれの call 命令を数えます。

llvm-objdump -d --no-show-raw-insn nolto.exe | findstr /C:"call" | find /c /v ""
llvm-objdump -d --no-show-raw-insn lto.exe   | findstr /C:"call" | find /c /v ""
ビルドcall 命令の数
LTO なし1（scale への呼び出し）
Full LTO0

呼び出しが消えました。scale は mainCRTStartup にインライン展開され、clamp = false が定数として伝播し、if の中身が削除されています。第 11 章で「インライン化は最適化の入り口」と書いた、その連鎖が翻訳単位をまたいで起きたということです。

17.5 LogLab をビルドする

本番の題材でもやってみます。手順は同じです。

  1. 追加のオプションに /clang:-flto を書く
  2. Release / x64 でリビルドする
  3. 実行して checksum が 0x0e8685105a08f105 のままであることを確認する
  4. accepted が 4941900 のままであることを確認する
チェックサムが変わったら止まってください

LTO はプログラムの意味を変えない最適化です。結果が変わったということは、どこかに未定義動作があり、それが LTO によって顕在化した可能性が高い。第 23 章でこの問題を扱いますが、その状態で性能を測っても意味がありません。まず正しさ、次に速度です。

17.6 リンク時の最適化レベル

LTO では最適化がリンク時に行われるため、リンカ側にも最適化レベルの指定があります。

オプション意味
/opt:lldlto=0〜3リンク時の最適化レベル。既定は 2
/opt:lldltopartitions=<N>Full LTO のコード生成を N 分割して並列化する
/mllvm:<opt>リンク時の LLVM に内部オプションを渡す（第 6 章の -mllvm のリンカ版）

構成プロパティ > リンカー > コマンド ライン > 追加のオプション

/opt:lldlto=3

/opt:lldltopartitions は、Full LTO の弱点であるコード生成の直列性を緩和するためのものです。統合されたモジュールを N 個に分けて並列に機械語へ落とします。分割すると分割境界をまたぐ最適化ができなくなるので、速度と最適化の深さのトレードオフになります。

コンパイル時の -O はどうなるのか

/O2 は依然として必要です。コンパイル時の -O レベルは、IR を生成する前段の処理と、LTO のパイプライン構成に影響します。/Od のまま -flto を付けても、期待した結果にはなりません。/O2 と /clang:-flto は併用します。

17.7 よくある失敗

リンクエラーになる

まずリンカを確認してください。ビルドログに link.exe が出ていれば、それが原因です。UseLldLink が false になっていないか、LinkToolExe が上書きされていないかを見ます。

一部の .obj だけビットコードになっている

これは問題ありません。ビットコードとネイティブの .obj は混在できます。 ビットコードのものだけが LTO の対象になり、ネイティブのものはそのままリンクされます。ただし、混ざっている部分では翻訳単位の壁が残ります。詳しくは第 22 章で扱います。

ビルドが極端に遅くなった

Full LTO では正常な挙動です。リンク時にプログラム全体の最適化を行うため、リンクだけで数十秒から数分かかることがあります。第 19 章の ThinLTO で改善します。

リンク時にメモリを使い果たす

Full LTO は全ビットコードを一つのモジュールに統合するため、大規模プロジェクトではメモリが足りなくなります。これも ThinLTO で解決すべき問題です。

__declspec(dllexport) した関数が最適化されない

エクスポートされた関数は、外部から呼ばれる可能性があるため削除もインライン化専用の内部化もできません。第 22 章で扱います。

17.8 ハンズオン

  1. LogLab の追加のオプションに /clang:-flto を設定してリビルドする
  2. llvm-readobj --file-headers で .obj がビットコードになったことを確認する
  3. ビルドログで lld-link.exe が使われていることを確認する
  4. 実行して checksum と accepted が変わっていないことを確認する
  5. ビルド（特にリンク）にかかった時間を記録する
  6. この .exe を lto_full\ のようなフォルダに退避しておく（第 20 章で比較します）
ビルドを使い分ける準備

これから /O2 のみ、Full LTO、ThinLTO、そして第 5 部では PGO 版と、複数のビルドを比較していきます。毎回設定を変えてリビルドするより、できた .exe と .pdb を名前を付けたフォルダにコピーしていくほうが実用的です。第 15 章の bench.py は 2 つの実行ファイルを引数に取るので、その形に合わせておきます。

builds\
  baseline\  ClangOptLab.exe  ClangOptLab.pdb
  lto_full\  ClangOptLab.exe  ClangOptLab.pdb
  lto_thin\  ...

17.9 まとめ

  • Full LTO は /clang:-flto を追加のオプションに書くだけ。/O2 は併用する
  • 効いたかどうかは llvm-readobj が bitcode files are not supported と言うかで確認する
  • リンカが lld-link であることをビルドログで確認する
  • 最小構成では、翻訳単位をまたぐ call が 1 → 0 になった
  • checksum が変わっていないことを必ず確認する。変わったら性能を測る前に原因を追う
  • リンク時の最適化レベルは /opt:lldlto=<N>、並列化は /opt:lldltopartitions=<N>
  • ビルドが遅い・メモリを食うのは Full LTO の宿命。ThinLTO で解決する

次章では、その ThinLTO の仕組みを見ます。「全部を統合する」のをやめて、代わりに何をしているのか。サマリインデックスという考え方を理解すると、ThinLTO が Full LTO より効果が小さくなる理由も、リンクが速い理由も、同じ一つの設計から説明できるようになります。
