第 10 章

最適化レコードで記録する
— -fsave-optimization-record と opt-viewer

前章のリマークは、出力ウィンドウを流れて消えていきます。同じ情報を YAML ファイルとして保存できれば、集計もできますし、LTO の前後で比べることもできます。第 4 部以降で「何が変わったか」を語るための土台をここで作ります。

この章のゴール

  • 最適化レコードを出力し、置き場所を把握する
  • YAML の構造を読めるようになる
  • レコードを集計するスクリプトを用意する
  • opt-viewer でソース上に重ねて表示する
  • ビルド間で比較できる形に整える

10.1 リマークでは足りない理由

第 9 章のリマークには三つの限界があります。

  • 残らない。 ビルドし直せば消えます。「先週のビルドではどうだったか」は分かりません
  • 集計できない。 「インライン化されなかった箇所は全部でいくつか」を数えるには、テキストを正規表現で刻むしかありません
  • 構造がない。 cost や threshold は文章に埋め込まれた文字列であって、フィールドではありません

最適化レコードは、まったく同じ情報を構造化された YAML として出力します。リマークが「画面に出す版」、レコードが「ファイルに残す版」だと考えてください。

10.2 出力する

clang-cl /c /O2 /std:c++23 /Iinclude ^
    /clang:-fsave-optimization-record src\tokenizer.cpp

オブジェクトファイルと同じ場所に tokenizer.opt.yaml が生成されます。

MSBuild では中間ディレクトリに出ます

Visual Studio からビルドした場合、レコードは .obj と同じ場所、つまり x64\Release\ の中に出力されます。プロジェクトのルートを探しても見つかりません。「リビルドすると消える場所」でもあるので、比較用に残したいときは別のフォルダにコピーしてください。

10.2.1 出力先と対象を制御する

オプション効果
/clang:-fsave-optimization-recordレコードを出力する（既定は YAML 形式）
/clang:-foptimization-record-file=<path>出力先を明示する
/clang:-foptimization-record-passes=<正規表現>記録するパスを絞る

絞り込みは実用上ほぼ必須です。LogLab の tokenizer.cpp ひとつで、レコードは約 100 KB になります。 インライン化だけを追いたいなら、次のようにします。

/clang:-fsave-optimization-record
/clang:-foptimization-record-passes=inline

10.3 YAML の構造

実際のレコードから一件を抜き出したものです。

--- !Missed
Pass:            inline
Name:            NoDefinition
DebugLoc:        { File: src\tokenizer.cpp, Line: 73, Column: 7 }
Function:        '?parse_line@loglab@@YA_N...'
Args:
  - Callee:          '?find@...'
  - String:          ' will not be inlined into '
  - Caller:          '?parse_line@loglab@@YA_N...'
    DebugLoc:        { File: src\tokenizer.cpp, Line: 71, Column: 0 }
  - String:          ' because its definition is unavailable'
...
フィールド意味
ドキュメントのタグ!Passed（やった）／!Missed（やらなかった）／!Analysis（解析結果）
Passパス名。inline、loop-vectorize、licm など
Nameそのパスの中での事象の種類。集計するならこのフィールド
DebugLocソース上の位置
Function対象の関数（マングル名）
Argsリマークの文章を組み立てる部品。Cost、Threshold などがここに入る

前章で見たリマークの文章は、この Args を連結して作られています。つまりレコードのほうが元データで、リマークはその整形結果です。

10.4 集計する

YAML のままでは読めないので、集計スクリプトを用意します。Python と PyYAML を使います。

pip install pyyaml
import sys, collections, yaml

# !Passed などのタグを保持したまま読み込むためのローダ
class L(yaml.SafeLoader):
    pass

def keep_tag(loader, tag_suffix, node):
    d = loader.construct_mapping(node, deep=True)
    d['_kind'] = tag_suffix
    return d

L.add_multi_constructor('', keep_tag)

counts = collections.Counter()
for path in sys.argv[1:]:
    with open(path, encoding='utf-8') as f:
        for doc in yaml.load_all(f, Loader=L):
            if not doc:
                continue
            counts[(doc.get('_kind'), doc.get('Pass'), doc.get('Name'))] += 1

for (kind, p, n), v in counts.most_common(20):
    print(f"{v:6}  {kind:<10} {p:<18} {n}")

注目すべき一行

10.4.1 プロジェクト全体で集計する

複数のレコードをまとめて渡せます。

python summarize.py x64\Release\*.opt.yaml > records_O2.txt

この records_O2.txt が、第 2 部で作る最後のベースラインです。第 8 章の baseline_O2_calls.txt と並べて保管しておいてください。

10.5 opt-viewer で見る

集計は全体像を掴むのに向いていますが、「ソースのどこで何が起きたか」を見るには opt-viewer が便利です。ソースコードの各行に、その行で起きた最適化を重ねた HTML を生成します。

10.5.1 準備

opt-viewer は実行ファイルではなく Python スクリプト群です。LLVM のソースツリーの llvm/tools/opt-viewer/ にあり、公式 Windows インストーラでは share\opt-viewer\ に置かれることがあります。無ければ LLVM のソース配布物から取得してください。

pip install pyyaml pygments

10.5.2 実行

python "C:\Program Files\LLVM\share\opt-viewer\opt-viewer.py" ^
    --output-dir html_O2 ^
    x64\Release\tokenizer.opt.yaml

html_O2\index.html をブラウザで開くと、最適化の件数が多い順に関数が並びます。関数名をクリックするとソースが表示され、各行の左側に Inlined、NoDefinition、MissedDetails といった事象が色分けで並びます。

opt-viewer が無くても困りません

本書の以降の章で opt-viewer は必須ではありません。前節の集計スクリプトのほうが、「前回と比べて何件減ったか」という本書の使い方には向いています。opt-viewer は「特定の関数を掘り下げたい」ときの道具だと考えてください。

10.6 比較する運用にする

レコードの価値は、単発で読むことではなく比べることにあります。本書では以降、次の形で使います。

時点保存するもの比べる相手
いま（/O2 のみ）records_O2.txt—（基準）
第 20 章（LTO 有効）records_lto.txtNoDefinition が減ったか
第 32 章（PGO 有効）records_pgo.txtInlined の内訳が変わったか、hot-cold-split が現れたか
第 37 章（CSPGO）records_cspgo.txtPGO 版との差

ファイル名を決めて、プロジェクトの外の作業フォルダに置いておいてください。x64\Release\ の中に置くと、リビルドで消えます。

LTO ではこれだけでは足りません

ここで扱ったのはコンパイル時のレコードです。LTO を有効にすると最適化の主戦場はリンク時に移るため、コンパイル時のレコードには LTO による変化がほとんど現れません。リンク時のレコードをどう取るかは第 20 章で扱います。いまは「コンパイル時とリンク時は別物」という点だけ意識しておいてください。

10.7 ハンズオン

  1. LogLab のプロジェクトの 追加のオプション に /clang:-fsave-optimization-record を追加してリビルドする
  2. x64\Release\ に *.opt.yaml が 5 つできていることを確認する
  3. リスト 10-1 の summarize.py を作る
  4. 全 5 ファイルを渡して集計し、records_O2.txt として保存する
  5. !Missed inline NoDefinition の件数をメモする
  6. 追加のオプションからレコードの指定を消す（ビルドが遅くなるため）

10.8 まとめ

  • 最適化レコードはリマークと同じ情報の構造化された版。むしろレコードが元データである
  • /clang:-fsave-optimization-record で .obj と同じ場所に *.opt.yaml が出る。MSBuild では中間ディレクトリ
  • 1 翻訳単位で 100 KB 規模。-foptimization-record-passes= で絞る
  • Pass と Name で集計すると全体像が一目で分かる
  • !Missed inline NoDefinition の件数が、LTO の効果を測る最初の指標になる
  • レコードは比較して初めて価値が出る。ベースラインを外部フォルダに保存しておく
  • LTO のレコードはリンク時に別途取得する必要がある（第 20 章）

次章では、第 2 部の締めくくりとしてインライン化そのものを掘り下げます。cost と threshold のモデル、-mllvm -inline-threshold でしきい値を動かしたときに何が起きるか、そしてなぜしきい値をいじるのが最後の手段なのか。第 5 部の PGO へ橋を渡す章になります。
