第 12 章

PIX for Windows で CPU 時間を取る

ここから第 3 部です。第 2 部で「最適化の中身を観察する」道具を揃えました。次は「時間を測る」道具です。まずは PIX for Windows のタイミングキャプチャで、LogLab のどこに時間が費やされているのかを見てみます。

この章のゴール

  • サンプリングプロファイラの原理と限界を理解する
  • PIX for Windows を導入し、タイミングキャプチャを取る
  • コールスタックの集計からホットスポットを特定する
  • 「parse_line が重いはずだ」という予想を検証する

12.1 サンプリングプロファイラとは何か

本章と次章で使うのは、どちらもサンプリング型のプロファイラです。仕組みは驚くほど単純です。

一定間隔（Windows では既定で 1 ミリ秒）ごとにタイマ割り込みをかけ、そのとき動いていたスレッドのコールスタックを写真に撮る。それだけです。1 秒間の実行なら 1000 枚の写真が集まります。そのうち 300 枚に parse_line が写っていれば、「実行時間のおよそ 30% を parse_line の中で過ごした」と推定できます。

ここから二つの性質が出てきます。

  • これは計測ではなく統計です。 サンプル数が少なければ誤差が大きくなります。1 回の実行が 10 ミリ秒しかなければ、サンプルは 10 個しか集まりません
  • 短い事象は写りません。 100 マイクロ秒で終わる処理は、1 ミリ秒間隔のサンプリングには 10 回に 1 回しか写りません

第 4 章で LogLab の実行時間を「500 ミリ秒から 2 秒」に調整するよう書いたのは、この理由からです。数百から数千のサンプルが集まれば、統計として意味のある結果になります。

12.2 PIX for Windows の導入

PIX は Microsoft が提供する Windows 向けのパフォーマンス解析ツールです。公式サイト（devblogs.microsoft.com/pix）からインストーラを入手できます。Visual Studio とは別に配布されているので、個別にダウンロードが必要です。

PIX には複数のキャプチャ種別がありますが、本書で使うのはタイミングキャプチャ（Timing Capture）です。CPU の時間配分を見るのがこの機能です。

12.2.1 タイミングキャプチャで取れるもの

オプション内容
CPU Samplesサンプリングによる CPU 時間の配分。サンプル間隔は設定可能。本書で主に使うのはこれ
Callstacks on Context Switchesスレッドが切り替わるたびにコールスタックを記録する
File Accessesファイル入出力の記録
Custom AllocatorsVirtualAlloc / HeapAlloc などのメモリ確保の記録
Page Fault Eventsページフォルトの記録

記録モードは二つあります。

モード挙動向いている場面
Sequential開始から停止までのすべてを記録するLogLab のように短時間で終わる処理
Circular固定サイズのバッファに記録し、直近の数秒だけを残す長時間動くアプリの、問題が起きた瞬間を捕まえる

12.3 キャプチャを取る

  1. PIX を起動し、左側の Connection ビューを開く
  2. 対象のマシン（通常は localhost）に接続する
  3. プロセスを起動するか、動作中のプロセスにアタッチする
    • 起動する場合は実行ファイルのパスと引数を指定する
    • GPU キャプチャ用のオプションは外しておく（CPU の解析には不要で、余計なフックが入ります）
  4. Start Timing Capture をクリックする
  5. 対象の処理が終わったら Stop Timing Capture（またはアプリの終了）で停止する
LogLab のようなコンソールアプリについて

PIX は本来、Direct3D 12 を使うゲームタイトルの解析を主目的に設計されたツールです。タイミングキャプチャ自体は ETW（次章で扱う Windows の標準的なトレース機構）を土台にしているため、原理的にはグラフィックスを使わないプロセスでも成立します。しかしコンソールアプリがプロセス一覧に現れるかどうかは PIX のバージョンに依存します。

まずは実際にアタッチできるか試してください。うまくいかない場合は、次の二つの道があります。

  • 第 13 章の WPR / WPA を使う。 こちらは Windows 標準の仕組みで、どんなプロセスでも確実に採れます。得られる情報も解析の考え方も本質的に同じです
  • LogLab に WinPixEventRuntime を組み込み、PIXBeginEvent / PIXEndEvent で区間に名前を付ける。PIX のタイムラインに自分の区間が並ぶようになり、格段に読みやすくなります。ただし外部ライブラリへの依存が増えます

本書は「どちらでも進められる」ように書いてあります。第 4 部以降で「プロファイラで確認する」と書いたときは、お使いのほうを使ってください。

12.4 何を見るのか

キャプチャが取れたら、見るべき順番は決まっています。

12.4.1 まずスレッドのタイムライン

LogLab は単一スレッドなので、一本の帯が実行時間いっぱいに伸びているはずです。ここで確認したいのは次の点です。

  • 帯が途切れていないか。途切れていればスレッドが待たされている（ページフォルト、I/O、他プロセスに CPU を奪われた）
  • 計測区間の前後に、想定外の時間が入っていないか（generate_lines() は計測対象外にしたはずですが、実際どうか）

12.4.2 次にコールスタックの集計

CPU サンプルを関数ごとに集計したビューを開きます。ここで見るのは二種類の数字です。

種別意味
排他時間（self / exclusive）その関数自身の中でサンプルが取られた回数。実際に命令を実行していた時間
包括時間（total / inclusive）その関数と、そこから呼ばれた関数すべてを合わせた回数

最適化の対象を探すときは排他時間を見ます。包括時間で並べると main が 100% で一位になるだけで、何の情報にもなりません。

12.4.3 予想を検証する

第 4 章で LogLab を設計したとき、私たちは「parse_line が最もホットなはずだ」と書きました。実際にそうなっているでしょうか。

期待される並びは、おおよそ次のようなものです。

  1. parse_line と、そこにインライン化された next_field / parse_uint — 文字を 1 バイトずつ見る処理なので最も重い
  2. Filter::accept() の各実装 — 仮想呼び出しが行数ぶん発生する
  3. Stats::add — ハッシュの更新
  4. handle_error — ほとんど出てこないはず（全体の 0.3% の行しか通らない）
予想と違ったら、それが収穫です

プロファイルの価値は「予想が当たること」ではなく「予想が外れることが分かること」にあります。もし Stats::add が想定より重ければ、ハッシュの計算が思ったよりコストが高いということです。もし std::string_view::find のような標準ライブラリの関数が上位に来たら、parse_line の中の find(" code=") が効いているということです。

いずれにせよ、それが第 4 部以降で「どこが速くなったか」を見る場所になります。

12.5 サンプリングの限界 — インライン化された関数は見えない

プロファイルを見て「あるはずの関数が出てこない」ということがよく起こります。原因はたいていインライン化です。

LogLab の next_field() は parse_line() の中に展開されているので、独立した関数としては存在しません。サンプリングの写真には parse_line としか写らないのです。

対処は二つあります。

方法内容注意
インラインフレーム情報を使うPDB には「この命令はもともとどの関数だったか」という情報（インラインサイト情報）が入っている。対応したプロファイラなら展開して表示できるツール側の対応が必要。第 14 章で扱う
一時的に展開を止める第 11 章で触れた __declspec(noinline) を調べたい関数に付けるそれ自体が性能を変える。あくまで調査用で、その状態の数字を「本当の性能」として扱わない
調査のための改変は、必ず元に戻す

__declspec(noinline) を付けたまま最適化の効果を測ると、まったく無意味な比較になります。第 11 章の実測で見たとおり、インライン化の有無は 1.7 倍の差を生みます。調査用の改変はコミットせず、測るときは必ず外してください。

12.6 ハンズオン

  1. LogLab を Release / x64 でビルドする（/Zi と /DEBUG が有効なことを確認）
  2. PIX でタイミングキャプチャを取る。取れなければ第 13 章に進み、そちらで同じことを行う
  3. CPU サンプルを排他時間で並べ替える
  4. 上位 5 関数とその割合をメモする ← これが第 3 部の成果物のひとつ
  5. handle_error が上位に来ていないことを確認する
  6. 計測区間の外（generate_lines()）にどれだけ時間がかかっているかも見ておく

12.7 まとめ

  • サンプリングプロファイラは一定間隔でコールスタックを撮る。計測ではなく統計である
  • 1 ミリ秒より短い事象は写らない。だから題材の実行時間を十分長くしてある
  • PIX のタイミングキャプチャで CPU サンプルとコールスタックが取れる
  • PIX は D3D12 タイトル向けの設計。コンソールアプリで使えなければ第 13 章の WPR / WPA を使う
  • 最適化対象を探すときは排他時間で並べる。包括時間では main が一位になるだけ
  • インライン化された関数はプロファイルに現れない。これは第 14 章のシンボルの話につながる

次章では、Windows 標準の ETW と Windows Performance Analyzer を扱います。コマンドライン一つでトレースを採れるので、自動化にも向いています。PIX が使えなかった場合の代替であると同時に、CI に組み込むときの本命でもあります（第 41 章）。
