第4部の最後は、**性能の話に戻ります**。

## 32.1 桁が違う

まず、数字の桁を揃えておきます。

| 操作 | おおよその時間 |
|---|---|
| CPU の1命令 | 0.3 ns |
| **`Bump::Allocate`** | **1.8 ns** |
| L1 キャッシュヒット | 1 ns |
| L2 キャッシュヒット | 4 ns |
| L3 キャッシュヒット | 15 ns |
| **DRAM アクセス** | **80 ns** |

**1回のキャッシュミスは、`Bump::Allocate` の 44 回分です。**

第5章で `new` と `Bump` の差(15.8 ns)を喜びましたが、**キャッシュミスが1回増えれば、その努力は帳消しになります**。

**そして、確保されたメモリの配置は、キャッシュミスの回数を左右します。**

これが、この本を通して繰り返してきた言葉の意味です。

> **アロケーターの仕事は、速く返すことではなく、良い場所を返すこと。**

## 32.2 メモリ階層を実測する

数字を暗記するのではなく、**自分の環境で測ります**。

### ポインタチェイス法

キャッシュのレイテンシを測るには、**次のアクセス先が、前のアクセスの結果に依存する** ようにします。そうしないと、CPU が複数のアクセスを並行して実行してしまい、レイテンシではなくスループットを測ることになります。

```cpp
// 単一の巡回を作り、それをたどる
double MeasureLatency(std::size_t bytes)
{
    const std::size_t count = bytes / sizeof(std::size_t);
    if (count < 2) { return 0.0; }

    // 0..count-1 をシャッフルして、ひと繋がりの巡回にする
    std::vector<std::size_t> perm(count);
    std::iota(perm.begin(), perm.end(), 0);

    std::mt19937 rng(12345);
    std::shuffle(perm.begin(), perm.end(), rng);

    std::vector<std::size_t> next(count);
    for (std::size_t i = 0; i < count; ++i)
    {
        next[perm[i]] = perm[(i + 1) % count];
    }

    // ウォームアップ
    std::size_t index = 0;
    for (std::size_t k = 0; k < count; ++k) { index = next[index]; }

    constexpr std::size_t kSteps = 20'000'000;

    const auto t0 = std::chrono::steady_clock::now();
    for (std::size_t k = 0; k < kSteps; ++k)
    {
        index = next[index];
    }
    const auto t1 = std::chrono::steady_clock::now();

    bench::Escape(index);

    return std::chrono::duration<double, std::nano>(t1 - t0).count() / kSteps;
}

int main()
{
    for (std::size_t kb : { 4, 16, 32, 64, 128, 256, 512, 1024, 4096, 16384, 65536 })
    {
        std::println("{:>8} KB : {:>6.2f} ns", kb, MeasureLatency(kb * 1024));
    }
}
```

### 結果

```
       4 KB :   1.08 ns
      16 KB :   1.09 ns
      32 KB :   1.12 ns   ← L1 の境界(32 KB)
      64 KB :   3.42 ns
     128 KB :   3.81 ns
     256 KB :   3.88 ns
     512 KB :   4.02 ns   ← L2 の境界(512 KB)
    1024 KB :  12.60 ns
    4096 KB :  14.20 ns
   16384 KB :  21.40 ns   ← L3 の境界(16 MB あたり)
   65536 KB :  82.10 ns   ← DRAM
```

**階段状になっています。** 作業セットが各階層の容量を超えるたびに、レイテンシが跳ね上がります。

**このグラフが、あなたのマシンのキャッシュ構成です。** 段差の位置が、L1・L2・L3 の容量に対応します。

> **測ってみてください。** 環境によって段差の位置は違います。この数字を知っていることが、性能を議論するときの土台になります。

### アロケーターの文脈で読む

**作業セットが 32 KB に収まれば、メモリアクセスは 1 ns です。** 82 ns の 80 分の 1。

第21章で `Pool` が `new` に走査で 9.5 倍勝ったのは、**同じデータ量でも、実際に触るキャッシュラインの本数が違った** からです。

## 32.3 キャッシュライン

CPU がメモリを読むとき、**1バイトだけ読むことはできません**。必ず 64 バイト単位で読みます。この単位を **キャッシュライン** と呼びます。

```
┌────────────────────────────────────────────────────────────────┐
│                    キャッシュライン(64 バイト)                  │
└────────────────────────────────────────────────────────────────┘
 ↑
 1 バイト読んでも、64 バイトが運ばれる
```

### 間隔を変えて測る

```cpp
double MeasureStride(std::size_t stride, std::size_t totalTouches)
{
    constexpr std::size_t kBufferSize = 64 * 1024 * 1024;
    std::vector<std::byte> buffer(kBufferSize);

    volatile std::byte sink{};

    const auto t0 = std::chrono::steady_clock::now();

    std::size_t offset = 0;
    for (std::size_t i = 0; i < totalTouches; ++i)
    {
        sink = buffer[offset];
        offset += stride;
        if (offset >= kBufferSize) { offset = 0; }
    }

    const auto t1 = std::chrono::steady_clock::now();

    return std::chrono::duration<double, std::nano>(t1 - t0).count() / totalTouches;
}
```

```
 間隔      1アクセスあたり
   4 B      0.28 ns
   8 B      0.30 ns
  16 B      0.35 ns
  32 B      0.51 ns
  64 B      0.94 ns   ← ここから、毎回新しいキャッシュラインになる
 128 B      1.02 ns
 256 B      1.08 ns
1024 B      1.15 ns
4096 B      4.80 ns   ← ここから TLB ミスが効いてくる
```

**64 バイトを境に、コストが跳ね上がります。**

間隔 4 バイトなら、1本のキャッシュラインで 16 回のアクセスがまかなえます。間隔 64 バイトなら、毎回新しいラインです。

### 構造体のサイズが効く

```cpp
struct Small  { float x, y, z; int id; };            // 16 バイト → 1ラインに4個
struct Medium { float x, y, z; int id; char pad[48]; };  // 64 バイト → 1ラインに1個
```

**同じ処理でも、構造体が大きいだけで4倍のメモリ帯域を使います。**

第6章で「構造体のメンバ順を並べ替えて `sizeof` を縮める」演習を出しました。**その効果が、ここに現れます。**

## 32.4 プリフェッチ

CPU には、**次に使いそうなデータを先読みする** 回路があります。ハードウェアプリフェッチャです。

**「順番にアクセスしている」と判断すると、先のキャッシュラインを取ってきます。** うまく働けば、メモリのレイテンシがほぼ隠れます。

### 走査順を変えて測る

```cpp
constexpr std::size_t kCount = 4 * 1024 * 1024;   // 16 MB(L3 に収まらない)
std::vector<int> data(kCount, 1);

// ① 昇順
// ② 降順
// ③ 64 バイト刻み
// ④ ランダム順(インデックス配列を用意)
```

```
走査方法              1要素あたり
昇順                    0.31 ns
降順                    0.36 ns
16 要素(64B)刻み        0.98 ns
ランダム順              4.90 ns
```

**昇順と降順は、ほぼ同じです。** プリフェッチャは、両方向の連続アクセスを検出できます。

**ランダム順は 16 倍遅い。** 規則性がないので、プリフェッチが働きません。

### プリフェッチが効く条件

| アクセスパターン | プリフェッチ |
|---|---|
| 連続(昇順/降順) | **効く** |
| 一定の間隔(ストライド) | 多くの場合効く |
| ポインタを辿る(リンクリスト) | **効かない** |
| ランダム | **効かない** |

**最後の2つが重要です。**

ポインタを辿る場合、「次にどこを読むか」は **いま読んだ値を見るまで分かりません**。CPU は先読みできません。**必ずレイテンシが露出します。**

第23章で、フリーリストの走査が遅かった理由がこれです。

## 32.5 TLB

もう1つの階層があります。**アドレス変換のキャッシュ** です。

第29章で見たとおり、プログラムが使うのは仮想アドレスです。物理アドレスへの変換には **ページテーブル** を引く必要があります。

**この変換結果をキャッシュしているのが TLB**(Translation Lookaside Buffer)です。

```
TLB のエントリ数 : 数百〜1500 程度
1エントリがカバー : 4 KB
────────────────────────────────
TLB でカバーできる範囲 : 数 MB
```

**作業セットが数 MB を超えると、TLB ミスが起きはじめます。**

32.3 節の表で、間隔 4096 バイトのときに 4.80 ns まで跳ね上がったのがこれです。**1ページに1回しか触らないので、TLB が全然効きません。**

### ラージページ

Windows には、4 KB ではなく **2 MB のページ** を使う仕組みがあります。

```cpp
const std::size_t large = GetLargePageMinimum();   // 通常 2 MB

VirtualAlloc(nullptr, size,
             MEM_RESERVE | MEM_COMMIT | MEM_LARGE_PAGES,
             PAGE_READWRITE);
```

**1エントリで 2 MB をカバーできるので、TLB の効きが 512 倍良くなります。**

ただし条件が厳しい。

- **`SeLockMemoryPrivilege` が必要**(管理者権限で設定し、再ログオンが必要)
- サイズが 2 MB の倍数でなければならない
- **物理メモリが連続していなければならない** ため、断片化が進むと失敗する
- コミットは即座に物理メモリを消費する(デマンドページングが効かない)

**大きなデータを扱う場面では、大きな効果があります。** 実測すると、TLB ミスが支配的な処理で 20〜30% 速くなることがあります。

**しかし、ゲームで常用するには制約が重すぎます。** 演習に回します(演習32-6)。

## 32.6 実験1:プールの走査順

第21章の 21.8 節で見た現象を、**原因を分解して** 測り直します。

```cpp
ga::Pool<Particle> pool(100'000);

// ① 確保順のポインタ配列
std::vector<Particle*> inOrder;
for (int i = 0; i < 100'000; ++i) { inOrder.push_back(pool.New()); }

// ② シャッフルしたポインタ配列(要素の位置は同じ)
std::vector<Particle*> shuffled = inOrder;
std::shuffle(shuffled.begin(), shuffled.end(), rng);

// ③ ビットマップ走査(第22章の ForEachLive)
```

```
走査方法                          1要素あたり   作業セット
① 確保順のポインタ配列               0.44 ns      3.2 MB
② シャッフルしたポインタ配列          3.90 ns      3.2 MB
③ ForEachLive(ビットマップ)         0.46 ns      3.2 MB
```

**データはまったく同じ場所にあります。** 違うのは **触る順番** だけです。

### なぜ 8.9 倍も違うのか

**①と③** は、メモリを昇順に舐めます。プリフェッチャが働き、キャッシュラインを無駄なく使い切ります。

**②** は、3.2 MB の範囲を飛び回ります。

- プリフェッチが効かない
- 1回のアクセスで運ばれた 64 バイトのうち、32 バイト(Particle 1個)しか使わない
- TLB も効きにくい

**アロケーターは正しく連続配置しています。使う側が台無しにしています。**

第21章で「プールを使えば自動的に速くなるわけではない」と書いたのは、このことです。

## 32.7 実験2:リンクリストは、本当に遅いのか

「リンクリストは遅い、配列を使え」——よく言われます。**本当でしょうか。**

3つの条件で測ります。

```cpp
struct Node { int value; Node* next; };

// ① std::vector<int>
// ② new で確保したリンクリスト(他の確保が混ざり、ノードが散在)
// ③ Pool で確保したリンクリスト(ノードが連続)
```

```cpp
// ③ の構築
ga::Pool<Node> pool(1'000'000);

Node* head = nullptr;
Node* tail = nullptr;

for (int i = 0; i < 1'000'000; ++i)
{
    Node* n = pool.New();
    n->value = i;
    n->next  = nullptr;

    if (tail) { tail->next = n; } else { head = n; }
    tail = n;
}
```

### 結果

```
                                       1要素あたり
① std::vector<int>                        0.31 ns
② new で確保したリンクリスト                4.20 ns
③ Pool で確保したリンクリスト               0.95 ns
```

### この表が言っていること

**②と③は、まったく同じデータ構造です。** 同じ `Node`、同じポインタの辿り方、同じ要素数。

**違うのはノードがどこに置かれているかだけ。それで 4.4 倍です。**

> **「リンクリストが遅い」のではありません。**
> **「ノードが散らばっていると遅い」のです。**

### ③が①に負ける理由

`Pool` 版でも、`std::vector` の 3 倍かかっています。理由は2つ。

**1. ノードが 16 バイトある。** `int` は 4 バイトです。`next` ポインタのぶん、**4 倍のメモリ帯域** を使います。

**2. 依存の連鎖がある。** 次のノードのアドレスは、いまのノードを読むまで分かりません。プリフェッチャは、連続アクセスだと **推測** できますが、確実ではありません。

**それでも、②の 4.4 倍改善は大きい。** データ構造を変えられない場面(既存コード、外部ライブラリ)でも、**アロケーターを変えるだけで手に入る改善** です。

## 32.8 「良い場所」とは何か

ここまでの実測から、アロケーターが目指すべきことを定義できます。

### 1. 空間的局所性:一緒に使うものを、近くに置く

```
悪い: [Particle][string][Particle][string][Particle]...
良い: [Particle][Particle][Particle]...  [string][string]...
```

**アロケーターにできること:**

- **アリーナを分ける。** 第15章のタグ、第43章のフレームアロケーター、第44章のシーンアロケーター
- **プールを使う。** 同じ型が必ず連続する(第21章)
- **寿命で分ける。** 長寿命と短命が混ざらないようにする

### 2. 時間的局所性:直前に使ったものを、また使う

```
Pool のフリーリスト : 直前に解放したブロックを、次に返す(LIFO)
Bump の Reset       : 毎フレーム同じアドレス範囲を使い回す
```

**どちらも、キャッシュに残っている領域が再利用されます。**

第22章で「フリーリストは LIFO なのでキャッシュに熱い」と書いたのは、この性質です。

### 3. 無駄なバイトを運ばない

```
ヘッダ 16 バイト + データ 32 バイト = 48 バイト
  → キャッシュラインの 1/4 がヘッダ
```

第26章のバディがヘッダを持たないこと、第21章のプールがヘッダを持たないことは、**キャッシュの観点でも有利** です。

第28章の表で「実効利用率」を測りましたが、あれは **キャッシュ効率の指標でもあります**。

### アロケーターにできないこと

**構造体の中身の並び方は、アロケーターには変えられません。**

```cpp
struct Particle
{
    float x, y, z;        // 毎フレーム更新する
    float vx, vy, vz;     // 毎フレーム更新する
    char  name[32];       // めったに触らない
    int   id;
};
```

この構造体を連続配置しても、**毎回 name[32] まで運ばれます**。

これは **データのレイアウトの問題** であり、次節のテーマです。

## 32.9 AoS と SoA

### 2つのレイアウト

**AoS**(Array of Structures):構造体の配列。私たちがずっと使ってきた形です。

```
[x y z vx vy vz name id][x y z vx vy vz name id][...]
```

**SoA**(Structure of Arrays):メンバごとに別の配列。

```
x:  [x x x x x x ...]
y:  [y y y y y y ...]
z:  [z z z z z z ...]
vx: [vx vx vx ...]
```

### 測る

位置の更新(`x += vx` など)だけを行う処理で比べます。

```cpp
struct ParticleAoS
{
    float x, y, z;
    float vx, vy, vz;
    char  name[32];
    int   id;
};    // 64 バイト

struct ParticlesSoA
{
    std::span<float> x, y, z;
    std::span<float> vx, vy, vz;
    // name, id は別に持つ
};
```

```
                     1要素あたり   1要素で運ばれるバイト
AoS(64 バイト)         1.85 ns          64
SoA                     0.42 ns          24
```

**4.4 倍。**

AoS では、`x` を読むために 64 バイトのキャッシュラインが運ばれ、そのうち 24 バイトしか使いません。`name[32]` も一緒に運ばれています。

SoA では、運ばれたバイトが **100% 使われます**。

### 16.6 ms 予算で

```
10 万パーティクル × 毎フレーム:
  AoS : 185 µs
  SoA :  42 µs
  差  : 143 µs = 16.6 ms 予算の 0.86%
```

1つのシステムで 0.86%。パーティクル、敵、弾、当たり判定、アニメーション——**同じ構造のものが10種類あれば、8.6%** です。

### アロケーターとの関係

**SoA は、アロケーターの仕事ではありません。** データ構造の設計です。

しかし、**SoA を採用すると、アロケーターへの要求が変わります**。

```cpp
// 6本の配列を、それぞれ確保する
auto x  = arena.NewArray<float>(count);
auto y  = arena.NewArray<float>(count);
auto z  = arena.NewArray<float>(count);
// ...
```

**同時に確保すれば、6本が連続して並びます。** バンプアロケーターなら自然にそうなります。

`new` で確保すると、6本がどこに置かれるか分かりません。**アロケーターが SoA を支えている** 形です。

> **第53章で、データ指向設計を扱います。** そこでは「アロケーターを速くする」から「そもそも触るメモリを減らす」へと視点が移ります。この章は、その入り口です。

## 32.10 第4部のまとめ

| 章 | 何を手に入れたか |
|---|---|
| 29 | 予約とコミットの分離。1 GB 予約が実質タダ |
| 30 | 移動しない配列。ポインタの安定性 |
| 31 | ガードページ。はみ出した瞬間の検出 |
| 32 | **配置が性能を決めるという理解** |

**第4部は「OS と本気で付き合う」章でした。**

`std::vector` という抽象の下に降りて、仮想メモリ、ページ、キャッシュ、TLB を直接扱いました。その結果、

- メモリを大きく予約しても損しなくなった
- ポインタが無効にならない配列が手に入った
- メモリ破壊を瞬時に検出できるようになった
- **そして、確保の速さだけを追いかけるのをやめました**

最後の項目が、いちばん大きな収穫かもしれません。

## 次章の予告

第4部の締めくくりとして、**比較対象の中身を覗きます**。

第5章から一貫して、私たちは `new` を相手に戦ってきました。しかし、`new` が実際に何をしているのかは、まだ調べていません。

第33章では、その正体を追います。

```
new → operator new → malloc → HeapAlloc → Windows ヒープ
```

- Low Fragmentation Heap(LFH)は何を解いたのか
- `HeapAlloc` を直接叩くと、`malloc` とどれだけ違うのか
- MSVC の CRT は、どこでどう介在しているのか

そして、**tcmalloc / jemalloc / mimalloc** といった現代の高性能アロケーターが、私たちが第3部で作ったものと何を共有し、何が違うのかを整理します。

第5部(マルチスレッド)に入る前に、**「汎用アロケーターは、なぜあの速度なのか」** に決着をつけます。

---

> **コラム:メモリは、相対的に遅くなり続けた**
>
> 32.1 節で「DRAM アクセスは CPU の1命令の 260 倍」と書きました。**昔からそうだったわけではありません。**
>
> ---
>
> **1980 年代**
>
> 初期の 8 ビット CPU では、メモリアクセスは 1〜2 クロックで済みました。**CPU とメモリの速度が釣り合っていました。**
>
> キャッシュは必要ありませんでした。存在しても、効果が小さかったのです。
>
> ---
>
> **その後の分岐**
>
> CPU の性能は、年率 50% 以上で向上し続けました。一方、DRAM のレイテンシは、年率 10% 程度しか改善しませんでした。
>
> **容量と帯域は劇的に増えましたが、レイテンシはほとんど変わりませんでした。** 1回のアクセスにかかる時間は、数十年の間にせいぜい数倍しか縮まっていません。
>
> この差が積み重なった結果が、現在の状況です。この現象は **メモリの壁**(memory wall)と呼ばれます。
>
> ---
>
> **キャッシュ階層は、その対策として生まれた**
>
> ```
> 1980年代後半 : L1 キャッシュが CPU に統合される
> 1990年代     : L2 が基板上に、やがてチップに統合
> 2000年代     : L3 が登場。マルチコアで共有
> 現在         : L1(数十 KB)/ L2(数百 KB)/ L3(数十 MB)の3階層が標準
> ```
>
> **階層が増え続けているのは、壁が高くなり続けているからです。**
>
> ---
>
> **なぜ 64 バイトなのか**
>
> キャッシュラインのサイズは、トレードオフの結果です。
>
> **大きいほうが良い理由:** DRAM は、連続した領域を読むのが得意です。1回の転送で多く運べば、帯域を有効に使えます。また、タグ(どのアドレスをキャッシュしているかの記録)のオーバーヘッドが相対的に減ります。
>
> **小さいほうが良い理由:** 使わないバイトを運ぶのは無駄です。ランダムアクセスが多いプログラムでは、大きなラインは帯域を浪費します。
>
> **64 バイトは、この釣り合いが取れる点として選ばれました。** 過去には 32 バイトの実装も、128 バイトの実装もありました。
>
> ---
>
> **プログラマにとっての意味**
>
> **「メモリは遅い」という前提が、プログラミングの常識を変えました。**
>
> かつては「命令数を減らす」ことが最適化でした。いまは **「メモリアクセスを減らす」** ことが最適化です。
>
> ```
> 昔の常識: リンクリストは挿入が O(1) だから速い
> 今の現実: 配列を全部ずらすほうが速いことが多い
> ```
>
> 32.7 節で見たとおり、`std::vector` への挿入(要素をずらす)は連続アクセスなので、リンクリストのポインタ追跡より速いことがよくあります。**計算量が同じでも、メモリの触り方で桁が変わります。**
>
> ---
>
> **そして、アロケーターの役割が変わった**
>
> `malloc` が発明された 1970 年代、アロケーターの仕事は **「速く返すこと」** でした。メモリの配置が性能に与える影響は、無視できるほど小さかったからです。
>
> **いまは違います。**
>
> どこに置くかが、その後の何千回ものアクセスの速度を決めます。**確保に 10 ns 余分にかかっても、キャッシュミスを1回減らせるなら、それは得な取引です。**
>
> この本が第2部から「連続配置」「寿命で分ける」「同じ型をまとめる」と言い続けてきたのは、この変化を踏まえてのことです。
