# 第52章 小さな 2D ゲームに組み込む

---

## この章のゴール

**この本の実践編です。**

小さな 2D ゲームを用意し、**`new` 版から自作アロケーター版へ、段階的に移行します。**

```
段階0: すべて new / delete            → 基準を測る
段階1: フレーム単位のデータをアリーナへ  → 第43章
段階2: 弾とパーティクルをプールへ       → 第21章
段階3: シーンのロードをアリーナへ       → 第44章
段階4: 残りを TLSF へ                 → 第41章、第27章
```

**各段階で必ず測ります。** フレーム時間、最悪フレーム、ピークメモリ、断片化。

そして——

> **「本に書いてあるとおりにやったら、すんなり動いた」という話にはなりません。**

**移行中に踏んだバグと、予想が外れたことを、正直に書きます。**

---

## 52.1 題材

**2D の見下ろし型シューティングです。**

```
自機        : 1体
敵          : 最大 1,000 体(ウェーブごとに出現)
弾          : 最大 5,000 発(敵弾を含む)
パーティクル : 最大 20,000 個(爆発、軌跡)
タイルマップ : 256 × 256 のステージ、10 ステージ
UI          : スコア、HP バー、ダメージ表示
音声        : BGM 1本 + 効果音 32 種
```

**ソースは約 3,000 行です。**

### 現状の実装

**「素直な C++」で書かれています。**

```cpp
class Enemy { /* ... */ };

std::vector<std::shared_ptr<Enemy>>   enemies_;
std::vector<std::unique_ptr<Bullet>>  bullets_;
std::vector<Particle>                 particles_;

void Update(float dt)
{
    for (auto& e : enemies_) { e->Update(dt); }

    // 当たり判定の候補を集める
    std::vector<Enemy*> candidates;
    for (auto& e : enemies_)
    {
        if (InRange(*e, player_)) { candidates.push_back(e.get()); }
    }
    // ...
}
```

**多くのプロジェクトが、この形から始まります。**

### なぜ 2D か

**単純ですが、メモリの使い方はゲームの構造を持っています。**

- フレーム単位の一時データがある
- 同じ型の大量生成がある
- シーンの切り替えがある
- 寿命が読めないものもある

**第3章の4分類が、すべて登場します。**

## 52.2 段階0:基準を測る

**何よりも先に、現状を測ります。**

### 測るもの

| 指標 | 意味 |
|---|---|
| **フレーム時間**(中央値 / p95 / 最大) | 第4章、第5章の方針 |
| **確保回数 / フレーム** | どれだけ確保しているか |
| **ピークメモリ** | 第8章の `Peak()` |
| **ロード時間** | シーン切り替えのコスト |
| **断片化** | 第19章の指標 |

### 仕込み方

**第41章の `operator new` 置換を使います。**

**自分で書いていないコードも含めて、すべての確保を捕捉できます。**

```cpp
// GlobalNew.cpp(EXE のソースに直接置く。第41章 41.7 節)
void* operator new(std::size_t size)
{
    return ga::GlobalAllocate(size, __STDCPP_DEFAULT_NEW_ALIGNMENT__);
}
// ... 残り 19 個 ...
```

**この時点では、アロケーターを差し替えません。** 統計を取るためだけに置換します。

```cpp
void* ga::GlobalAllocate(std::size_t size, std::size_t alignment) noexcept
{
    RecordAllocation(size, CurrentTag(), CurrentThreadToken());
    return _aligned_malloc(size, alignment);        // ← 中身は CRT のまま
}
```

> **これが移行の第一歩です。** **何も変えずに、見えるようにする。**
>
> 第4章で「測る道具を先に作る」と書いたのと、同じ順序です。

### 結果

```
=== 段階0:基準(ステージ3、敵 640 体、弾 2,100 発、パーティクル 12,400 個)===

  フレーム時間
    中央値       :  8.42 ms

    最大         : 42.61 ms   ← 16.6 ms 予算の 2.6 倍
```

**フレームの 4.8% が予算を超えています。** プレイしていると、はっきりカクつきます。

**最大 42.61 ms は、予算の 2.6 倍。** そのフレームは確実に落ちます。

## 52.3 何が確保しているのかを見る

**第15章のタグと、第18章のスタックトレースを組み合わせます。**

```cpp
{
    GA_TAG_GLOBAL(ga::MemoryTag::Physics);
    UpdateCollisions();
}
```

### 確保回数の内訳

```
=== 1フレームあたりの確保(18,412 回)===

  発生源                                 回数     割合
  ─────────────────────────────────────────────────
  std::string の一時オブジェクト          3,240   17.6%
  std::function のコピー                 1,820    9.9%
  std::vector の再確保                     412    2.2%
  shared_ptr の制御ブロック                 904    4.9%
  当たり判定の候補リスト                  2,180   11.8%
  描画コマンド                           4,100   22.3%
  パーティクルの生成                      3,120   16.9%
  弾の生成                               1,840   10.0%
  その他                                   796    4.4%
```

### 意外だったこと

**① 文字列が 17.6%**

```cpp
void DrawDebugInfo()
{
    DrawText(std::format("FPS: {:.1f}", fps));            // ← 毎フレーム確保
    DrawText(std::format("Enemies: {}", enemies_.size()));
    // ... 20 行ほど続く
}
```

**デバッグ表示のフォーマットが、フレームあたり 3,240 回の確保を生んでいました。**

**「ゲームロジックが確保している」と思い込んでいましたが、違いました。**

**② `std::function` のコピーが 9.9%**

```cpp
void RegisterEvent(std::function<void(const Event&)> handler);   // ← 値渡し
```

**イベント登録のたびに、ラムダのコピーが確保されていました。**

**③ `shared_ptr` の制御ブロックが 4.9%**

**第40章で見たとおりです。** `std::make_shared` を使っていない箇所で、確保が2回起きていました。

> **これが、測ることの価値です。**
>
> **予想:** ゲームロジックが大量に確保している
> **実測:** **周辺コードが半分近くを占めていた**
>
> **第4章から一貫している方針が、ここで報われます。**

### 最初にやったこと

**移行を始める前に、明らかな無駄を潰しました。**

```cpp
// ① 文字列のフォーマットを、固定バッファへ
char buffer[128];
std::format_to_n(buffer, sizeof(buffer), "FPS: {:.1f}", fps);

// ② std::function を参照渡しに
void RegisterEvent(const std::function<void(const Event&)>& handler);

// ③ make_shared を使う
auto e = std::make_shared<Enemy>(...);
```

```
確保回数 / フレーム : 18,412 → 13,180(28% 減)
中央値              : 8.42 → 8.11 ms
最大                : 42.61 → 38.20 ms
```

**アロケーターを1行も変えずに、28% 減りました。**

> **「アロケーターを速くする」より「確保を減らす」ほうが、たいてい効きます。**
>
> **第53章で、この話に戻ってきます。**

## 52.4 段階1:フレームアリーナ

**第43章の実装を導入します。**

### 何を移すか

```
当たり判定の候補リスト  2,180 回
描画コマンド           4,100 回
一時的な計算バッファ      840 回
───────────────────────────────
                      7,120 回(54%)
```

**「このフレームだけ生きる」ものです。**

### 移行

```cpp
// 変更前
std::vector<Enemy*> candidates;
for (auto& e : enemies_) { if (InRange(*e, player_)) candidates.push_back(e.get()); }

// 変更後
ga::BumpScope scope(g_frameArena);

auto candidatesResult = g_frameArena.NewArrayUninit<Enemy*>(enemies_.size());
std::span<Enemy*> candidates = *candidatesResult;
std::size_t count = 0;

for (auto& e : enemies_)
{
    if (InRange(*e, player_)) { candidates[count++] = e.get(); }
}
candidates = candidates.first(count);
```

**「最大数で確保して、使った分だけ使う」** という形に変わります。

**`std::vector` の `push_back` に慣れていると、最初は面倒に感じます。**

### 踏んだバグ①:フレームをまたいだ参照

**移行して 30 分後、敵の挙動がおかしくなりました。**

```
敵が突然、画面外へワープする
毎回ではない。10 秒に1回程度
```

**第16章の塗りつぶしを有効にして、値を表示しました。**

```
enemy->x = -572662307.0
```

**`0xDDDDDDDD` です。**

**原因:**

```cpp
class CollisionSystem
{
    std::span<Enemy*> lastFrameCandidates_;    // ← フレームをまたいで保持していた

    void Update()
    {
        // 「前フレームと同じ相手か」を判定するために保持していた
    }
};
```

**第43章 43.3 節で予告したとおりの問題です。**

**対処:** ダブルバッファにするか、必要な情報だけを別の場所にコピーするか。

**この場合は「前フレームに衝突していた相手の ID」だけが必要だったので、`std::vector<std::uint32_t>` に ID を保持する形に変えました。**

> **フレームアリーナに移すとき、「そのデータは本当にフレーム単位か」を確認してください。**
>
> **第16章の塗りつぶしがなければ、原因の特定に数時間かかっていたはずです。**

### 結果

```
=== 段階1:フレームアリーナ ===

  確保回数 / フレーム : 13,180 → 6,060(54% 減)

  フレーム時間
    中央値  : 8.11 → 7.62 ms   (-6.0%)
    p95     : 10.84 → 9.10 ms  (-16.1%)
    最大    : 38.20 → 18.42 ms (-51.8%)   ★
    予算超過率 : 4.2% → 0.9%

  ピークメモリ : 408 → 398 MB
```

**最大フレーム時間が半分以下になりました。**

**中央値の改善は 6% ですが、最大値は 52% 改善。**

> **第5章で「平均ではなく最悪値」と書いた理由が、ここに出ています。**
>
> **プレイした感触が、明確に変わりました。** カクつきがほぼ消えます。

## 52.5 段階2:プール

**第21章と第22章の実装を導入します。**

### 何を移すか

```
パーティクルの生成  3,120 回
弾の生成           1,840 回
敵の生成             180 回
───────────────────────────
                   5,140 回
```

**「同じ型の大量生成」です。**

### 上限を決める必要がある

**第21章で述べたとおり、プールは固定容量です。**

```cpp
ga::Pool<Particle> g_particlePool(20'000);
ga::Pool<Bullet>   g_bulletPool(5'000);
ga::Pool<Enemy>    g_enemyPool(1'000);
```

**「最大何個か」を決めなければなりません。**

**これは技術的な判断ではなく、ゲームデザインの判断です。**

```
「パーティクルは最大 20,000 個」
    → それを超えたら、古いものを消すか、新しいものを出さないか
    → 見た目にどう影響するか
```

**デザイナーとの合意が必要でした。** 想定外の作業でした(52.9 節)。

### 移行

```cpp
// 変更前
std::vector<Particle> particles_;
particles_.push_back(Particle{ ... });

// 変更後
if (Particle* p = g_particlePool.New(...))
{
    // 成功
}
else
{
    // 上限に達している
}
```

### 走査も変える(第22章)

```cpp
// 変更前:ポインタ配列を走査
for (Particle* p : particlePtrs_) { p->Update(dt); }

// 変更後:ビットマップで走査(第22章 22.5 節)
g_particlePool.ForEachLive([dt](Particle& p) { p.Update(dt); });
```

**第21章 21.8 節と第32章 32.6 節で見たとおり、走査順序が性能を決めます。**

### 踏んだバグ②:静かな失敗

**「爆発のパーティクルが、たまに出ない」という報告がありました。**

**クラッシュしません。エラーも出ません。**

```cpp
if (Particle* p = g_particlePool.New(...))
{
    // ...
}
// ← else を書いていなかった
```

**プールが満杯のとき、`New()` は `nullptr` を返します。** それを無視していました。

**第7章で扱った「エラーの伝え方」の問題です。** `nullptr` は、無視できてしまいます。

**対処:**

```cpp
if (Particle* p = g_particlePool.New(...))
{
    // ...
}
else
{
    ++g_particleOverflowCount;      // ← 記録する

#if GA_CONFIG_DEVELOPMENT
    Log(LogLevel::Warning, "パーティクルプールが満杯です({} 個)",
        g_particlePool.Capacity());
#endif
}
```

**第49章の予算管理と同じ考え方です。** **黙らせない。**

**実際、ピーク時に 20,000 個の上限に達していました。** 容量を 32,000 に増やしました。

### 結果

```
=== 段階2:プール ===

  確保回数 / フレーム : 6,060 → 920(85% 減)

  フレーム時間
    中央値  : 7.62 → 6.14 ms   (-19.4%)   ★
    p95     : 9.10 → 7.28 ms   (-20.0%)
    最大    : 18.42 → 14.20 ms (-22.9%)
    予算超過率 : 0.9% → 0.1%

  ピークメモリ : 398 → 386 MB
```

**中央値が 19% 改善しました。段階1より大きい。**

**理由は、確保の速度ではなく走査の速度です。**

```
パーティクル 12,400 個の更新:
  変更前(散在)  : 48.2 µs
  変更後(連続)  : 12.4 µs
```

**第21章 21.5 節と第32章 32.6 節で測ったとおりの結果です。**

> **「確保を速くした」のではなく、「配置を良くした」効果です。**
>
> **第32章の主張が、実際のゲームで確認されました。**

## 52.6 段階3:シーンアリーナ

**第44章の実装を導入します。**

### 何を移すか

```
タイルマップのデータ
テクスチャの管理情報
音声データ
ステージのスクリプト
敵の出現テーブル
```

**「このステージにいる間だけ必要なもの」です。**

### `std::pmr` で入れ子まで載せる

**第39章 39.8 節の uses-allocator 構築を使います。**

```cpp
class Stage
{
public:
    using allocator_type = std::pmr::polymorphic_allocator<>;

    explicit Stage(allocator_type alloc = {})
        : name_(alloc)
        , tiles_(alloc)
        , spawnTable_(alloc)

    }

private:
    std::pmr::string             name_;
    std::pmr::vector<Tile>       tiles_;
    std::pmr::vector<SpawnEntry> spawnTable_;
};
```

**`Stage` の中のすべてが、シーンアリーナに載ります。**

### 踏んだバグ③:アリーナより長生きするポインタ

**ステージを 5 回切り替えたところで、UI の表示が化けました。**

```
スコア表示: "�?��?!#$"
```

**第31章のガードページを、シーンアリーナに適用しました。**

```cpp
=== アクセス違反 ===
  アドレス : 0x000001F3A8C2C000
  種別     : 読み取り
  詳細     : StageLoader.cpp:142 で確保し、すでに解放済みの 32 バイトの領域(+0)
  現在のスタック:
    DrawStageName    Hud.cpp(88)
    DrawHud          Hud.cpp(210)
    Render           Game.cpp(94)
```

**原因:**

```cpp
class Hud
{
    std::string_view stageName_;      // ← シーンアリーナ上の文字列を指していた
};
```

**`std::string_view` は、参照するだけです。** ステージがアンロードされても、`Hud` は気づきません。

**第44章 44.7 節で予告した問題です。**

**対処:** `Hud` は永続アリーナに属するので、**文字列をコピーして保持する** ようにしました。

> **`std::string_view` は便利ですが、寿命の管理を利用側に押し付けます。**
>
> **アリーナと組み合わせると、この危険が増幅されます。** 「どのアリーナのデータを指しているか」を意識する必要があります。

### 結果

```
=== 段階3:シーンアリーナ ===

  ロード時間 : 1.82 → 0.94 s / ステージ  (-48%)

  10 ステージ切り替え後
    断片化      : 0.58 → 0.00   ★
    最大の空き  : 42 MB → 全容量

  ピークメモリ : 386 → 344 MB  (-11%)

  フレーム時間 : ほぼ変わらず(6.14 → 6.08 ms)
```

**フレーム時間は変わりません。** ロード時のデータなので、当然です。

**しかし、断片化がゼロになりました。**

**第44章 44.2 節で見た「100 回の切り替えで最大確保サイズが 6分の1」という問題が、構造的に消えました。**

> **これは「速くなった」のではなく、「壊れなくなった」改善です。**
>
> **長時間プレイしたときの安定性が、目に見えない形で向上しています。**

## 52.7 段階4:残りを TLSF へ

**第41章の `operator new` 置換を、本格的に使います。**

```cpp
void* ga::GlobalAllocate(std::size_t size, std::size_t alignment) noexcept
{
    if (size <= 2048) { return CurrentThreadCache().Allocate(size); }   // 第36章

    std::lock_guard guard(g_heapLock);
    return g_tlsf.Allocate(size, alignment);                            // 第27章
}
```

### 踏んだバグ④:静的初期化順序

**起動直後にクラッシュしました。**

```
アクセス違反:0x0000000000000010 を読み取ろうとしました
```

**第41章 41.4 節で予告したとおりです。**

```cpp
// Logger.cpp
Logger g_logger;      // ← main より前に構築される。中で new を呼ぶ
```

**アロケーターがまだ初期化されていない状態で、`operator new` が呼ばれました。**

**対処:** 第41章 41.4 節の対策3(フォールバック)を実装しました。

```cpp
void* ga::GlobalAllocate(std::size_t size, std::size_t alignment) noexcept
{
    EnsureInitialized();

    if (!g_ready) { return _aligned_malloc(size, alignment); }   // ← 初期化前

    // ...
}
```

**そして、41.5 節の所有権判定も必要でした。**

```cpp
void ga::GlobalFree(void* p, std::size_t, std::size_t) noexcept
{
    if (g_ready && g_tlsf.Owns(p)) { g_tlsf.Free(p); return; }
    _aligned_free(p);                                            // ← CRT に返す
}
```

### 結果

```
=== 段階4:operator new の置換 ===

  確保回数 / フレーム : 920 → 920(変わらない。経路が変わっただけ)

  フレーム時間
    中央値  : 6.08 → 5.94 ms   (-2.3%)
    p95     : 7.28 → 7.02 ms   (-3.6%)
    最大    : 14.20 → 13.82 ms (-2.7%)

  ピークメモリ : 344 → 340 MB
```

**効果は 2〜3% です。**

**理由は明白です。** 段階1〜3で、確保回数が 18,412 から 920 に減りました。**残りは、もう大した量ではありません。**

> **アロケーターを速くしても、確保が少なければ効果は小さい。**
>
> **第12章で「確保が 10 倍速くても、初期化に時間がかかるなら全体では変わらない」と書きました。** 同じ話です。

## 52.9 予想が外れたこと

**正直に書きます。**

### ① `std::pmr` への移行が、想定の3倍かかった

```cpp
std::string  → std::pmr::string
std::vector  → std::pmr::vector
```

**型を変えると、それを受け取る関数もすべて変わります。**

```cpp
void SetName(const std::string& name);        // ← pmr::string を渡せない
```

**関数のシグネチャを `std::string_view` に変える作業が、数百箇所に及びました。**

**第38章 38.9 節で「型名が長くなる問題」に触れましたが、実際の作業量は想像以上でした。**

### ② プールの上限を決めるのに、合意形成が必要だった

**技術的には `Pool<Particle>(20'000)` と書くだけです。**

**しかし、「20,000 で足りるか」を決めるには、**

- 最も派手なステージでの実測
- デザイナーへの説明(「これ以上は出ません」)
- 上限に達したときの挙動の合意(古いものを消す? 出さない?)

**が必要でした。3日かかりました。**

> **第21章で「プールが捨てたもの:容量の上限」と書きました。**
>
> **その代償は、技術的な制約ではなく、組織的な調整コストとして現れます。**

### ③ 段階4のリスクが、効果に見合わなかった

**`operator new` の置換は、第41章で挙げた4つの危険地帯をすべて踏みました。**

- 静的初期化順序(52.7 節)
- 所有権判定(52.7 節)
- リンク順(静的ライブラリに置いて、静かに効かなかった)
- DLL 境界(サードパーティの DLL には効かない)

**2日かけて、改善は 1%。**

**このプロジェクトでは、段階4は「やらなくてもよかった」というのが結論です。**

**ただし、副産物として全体の統計が取れるようになりました。** 第49章の予算管理には、これが必要です。**目的が違えば、判断も違います。**

### ④ Debug ビルドが遅すぎて、開発構成が必須になった


**Debug では、ゲームプレイのバグを見つけられません。**

**第51章の3構成を、段階1の途中で導入することになりました。**

## 52.10 移行の進め方

**技術より、段取りのほうが重要でした。**

### ① 一度に全部変えない

**段階ごとに区切り、各段階でコミットしました。**

**もし全部を一度に変えていたら、52.4 節・52.5 節・52.6 節の3つのバグが同時に出て、原因の切り分けができませんでした。**

### ② 各段階で測り、記録する

```
段階0.csv, 段階1.csv, ...
```

**第49章の記録機構を、そのまま使いました。**

**「段階2で中央値が悪化した」といった異常に、すぐ気づけます。**

### ③ 戻せるようにする

**各段階を、機能フラグで切り替えられるようにしました。**

```cpp
#if GA_USE_FRAME_ARENA
    // 新しい実装
#else
    // 元の実装
#endif
```

**「新しい実装で問題が出たら、すぐ戻して比較する」** ことができます。

**移行が終わったら、古いコードは削除します。**(残すと、両方を保守することになります)

### ④ チームに説明する

**「メモリの確保方法を変えます」では、伝わりません。**

**測定結果を見せました。**

```
最大フレーム時間 : 42.6 ms → 13.8 ms
→ カクつきが、ほぼなくなります
```

**そして、使う側に必要な変更を、具体的に示しました。**

```
・フレームをまたぐデータは、フレームアリーナに置かない
・パーティクルの上限は 32,000。超えたら出ません
・ステージのデータへのポインタを、ステージをまたいで保持しない
```

**規約として文書化し、レビューで確認するようにしました。**
