# 第34章 8スレッドで走らせて壊す

---

## この章のゴール

第5部が始まります。第33章で、こう認めました。

> 私たちの実装が速いのは、一部はスレッド安全性を捨てた対価である。

**その負債を返す前に、まず借金の額を確認します。**

この章では、いま作ってあるアロケーターを複数スレッドから叩き、**壊れる様子を目で見ます**。

- 8スレッドで確保させ、**同じアドレスが複数のスレッドに返る** ことを確認する
- `offset_ += size` の1行が、なぜ壊れるのかを命令レベルで分解する
- **データ競合は「たまたま動く」ではなく未定義動作** であることを理解する
- 競合を **待つのではなく、規約違反として検出する** 道具を作る
- どこが競合するのかを棚卸しする(想像より多い)
- そして、**そもそも共有すべきか** を問う

## 34.1 壊してみる

```cpp
#include <thread>
#include <unordered_set>

int main()
{
    ga::Bump arena(512 * 1024 * 1024);

    constexpr int kThreads   = 8;
    constexpr int kPerThread = 100'000;

    std::vector<std::vector<void*>> results(kThreads);
    for (auto& v : results) { v.reserve(kPerThread); }

    std::vector<std::thread> threads;

    for (int t = 0; t < kThreads; ++t)
    {
        threads.emplace_back([&, t] {
            for (int i = 0; i < kPerThread; ++i)
            {
                auto r = arena.Allocate(64, 16);
                if (r) { results[t].push_back(*r); }
            }
        });
    }

    for (auto& th : threads) { th.join(); }

    // --- 返ってきたアドレスに重複がないか調べる ---
    std::unordered_set<void*> seen;
    std::size_t total = 0, duplicates = 0;

    for (const auto& v : results)
    {
        for (void* p : v)
        {
            ++total;
            if (!seen.insert(p).second) { ++duplicates; }
        }
    }

    std::println("確保成功 : {}", total);
    std::println("重複     : {} ({:.2f}%)", duplicates,
                 100.0 * duplicates / static_cast<double>(total));
    std::println("Used()   : {} (期待値 {})", arena.Used(), total * 64);
}
```

**Release 構成で実行してください。**

```
確保成功 : 800000
重複     : 12483 (1.56%)
Used()   : 50347328 (期待値 51200000)
```

### 2つの異常

**1. 同じアドレスが 12,483 回、複数のスレッドに返りました。**

アロケーターの最も基本的な契約——第3章で「返した領域どうしは絶対に重ならない」と書いたもの——が破れています。

**2. `Used()` が期待値より 853 KB 少ない。**

つまり、**進めたはずのオフセットが消えています**。

### もっと直接的に見る

各スレッドが、自分の ID を確保領域に書き込み、後で読み返します。

```cpp
struct Slot { int owner; int index; char pad[56]; };   // 64 バイト

    threads.emplace_back([&, t] {
        for (int i = 0; i < kPerThread; ++i)
        {
            auto r = arena.Allocate(sizeof(Slot), alignof(Slot));
            if (!r) { continue; }

            Slot* s = static_cast<Slot*>(*r);
            s->owner = t;
            s->index = i;

            results[t].push_back(s);
        }
    });

// join した後で検証
    std::size_t corrupted = 0;

    for (int t = 0; t < kThreads; ++t)
    {
        for (Slot* s : results[t])
        {
            if (s->owner != t) { ++corrupted; }
        }
    }

    std::println("他人に書き換えられた領域: {}", corrupted);
```

```
他人に書き換えられた領域: 11204
```

**自分が書いた値が、別のスレッドの値に書き換わっています。**

第22章で二重解放を扱ったとき、「2つのオブジェクトが同じ 32 バイトを共有する」と書きました。**同じ状態です。** 今回は、解放すらしていないのに起きています。

### Debug では起きにくい

同じプログラムを Debug 構成で実行してください。

```
重複     : 0 (0.00%)
```

**壊れません。**(環境や実行タイミングによっては壊れることもあります)

Debug 構成では、命令1つ1つが遅く、関数呼び出しもインライン展開されません。**競合が起きる時間の窓が、相対的に狭くなります。**

> **これが、この種のバグの最悪の性質です。**
>
> - Release でしか起きない
> - 実行するたびに違う場所が壊れる
> - 負荷をかけたときだけ発生する
> - デバッガを付けると再現しなくなる
>
> 「開発中は問題なかったのに、出荷後にクラッシュ報告が来る」という典型的な形になります。

## 34.2 何が起きているのか

問題の行は、これです。

```cpp
offset_ = alignedOffset + size;
```

一見、1つの操作に見えます。**CPU にとっては3つです。**

```asm
mov  rax, [rcx+8]     ; ① offset_ を読む
add  rax, rdx         ; ② size を足す
mov  [rcx+8], rax     ; ③ offset_ に書く
```

**この3つの間に、他のスレッドが割り込めます。**

### 2スレッドの実行を並べる

`offset_` が 1000 のとき、スレッド A と B が同時に 64 バイトを要求したとします。

| 時刻 | スレッド A | スレッド B | `offset_` |
|---|---|---|---|
| 1 | ① 読む → 1000 | | 1000 |
| 2 | | ① 読む → **1000** | 1000 |
| 3 | ② 1000 + 64 = 1064 | | 1000 |
| 4 | | ② 1000 + 64 = 1064 | 1000 |
| 5 | ③ 書く → 1064 | | 1064 |
| 6 | | ③ 書く → **1064** | 1064 |

**A も B も、アドレス 1000 を受け取りました。**

そして `offset_` は 1064。**128 進むべきところが 64 しか進んでいません。**

これが「重複 12,483 個」と「`Used()` が少ない」の正体です。**片方の更新が失われる** ので、**ロストアップデート** と呼ばれます。

### 確率の問題ではない

「タイミングがぴったり合ったときだけでは?」と思うかもしれません。

**8スレッドが 80 万回確保して、1.56% です。** 1万回以上の重複が発生しています。**十分に「よく起きる」現象です。**

そして、1回でも起きれば、そのプログラムは壊れています。

## 34.3 データ競合は「未定義動作」である

ここまでは「タイミング次第で壊れる」という話でした。**もっと悪い側面があります。**

C++ の規格では、**データ競合は未定義動作** です。

> 2つ以上のスレッドが、同じメモリ位置に、少なくとも一方が書き込みでアクセスし、それらが同期されていない場合。

「たまたま正しい値になる」ことを期待できないだけではありません。**コンパイラが、競合しない前提でコードを変形します。**

### 例:読み込みが持ち上げられる

```cpp
// 使う側のコード
while (arena.Used() < limit)
{
    DoSomething();
}
```

`Used()` は `offset_` を返すだけの関数です。コンパイラはこう考えます。

> `DoSomething()` は `offset_` を変更しない。ループの中で `offset_` を毎回読む必要はない。

**結果、`offset_` はループの外で1回だけ読まれ、レジスタに保持されます。**

他のスレッドが `offset_` を更新しても、**このループは永久に気づきません。** 無限ループになります。

**これは最適化のバグではありません。** データ競合がない前提が守られていれば、正しい変形です。

### `volatile` では解決しない

「`volatile` を付ければ毎回読むのでは」——**部分的には正しいですが、不十分です。**

```cpp
volatile std::size_t offset_;    // ← 解決しない
```

**理由1:不可分性が保証されない。**

`volatile` は「毎回メモリにアクセスする」ことを保証しますが、**読み・加算・書きが1つの不可分な操作になるわけではありません。** 34.2 節のインターリーブは、そのまま起きます。

**理由2:他の変数との順序が保証されない。**

`offset_` を書く前に `padding_` を書いた、という順序が、他のスレッドから見て保たれる保証がありません。

> **MSVC の x64 では、既定で `/volatile:ms` が有効になっており、`volatile` にある程度の順序保証が付きます。** しかしこれは Microsoft 独自の拡張であり、規格の保証ではありません。`/volatile:iso` を指定すれば無効になりますし、他のコンパイラでは通用しません。
>
> **`volatile` はスレッド同期の道具ではありません。** ハードウェアレジスタのように「読むたびに値が変わりうるメモリ」を扱うためのものです。第4章でベンチマークの `Escape` に使ったのが、本来の用途に近い使い方です。

### 正しい道具

**`std::atomic` を使います。** 第37章で扱います。

`std::atomic` は、不可分性と、他の変数との順序関係(happens-before)の両方を提供します。

## 34.4 競合を検出する

「動かして壊れるのを待つ」のは、効率が悪すぎます。**確実に検出したい。**

### ThreadSanitizer は使えない

第31章で AddressSanitizer を使いました。**その姉妹に ThreadSanitizer(TSan)があります。**

メモリアクセスを監視し、同期されていない並行アクセスを検出する道具です。競合が「実際に起きなくても」、起きうる状況を検出できます。

**しかし、MSVC は ThreadSanitizer に対応していません。**(`/fsanitize=address` はありますが、`/fsanitize=thread` はありません)

代替手段としては、次のものがあります。

- **Application Verifier** の Locks 検査(ロックの使い方の誤りを検出)
- **Intel Inspector** などの商用ツール
- **Clang/LLVM でビルドできるなら、TSan を使う**(コードが移植可能なら有力な選択肢)

### 自分で作る:単一スレッド利用の強制

**別のアプローチがあります。**

「競合が起きるのを待つ」のではなく、**「このアロケーターは1つのスレッドからしか使ってはいけない」という規約を、コードで強制します。**

```cpp
// ga/ThreadGuard.h
#pragma once

#include <atomic>
#include <cassert>
#include <cstdint>

namespace ga
{
    // スレッドごとに一意な番号を振る
    inline std::uint32_t CurrentThreadToken() noexcept
    {
        static std::atomic<std::uint32_t> next{ 1 };
        thread_local const std::uint32_t token =
            next.fetch_add(1, std::memory_order_relaxed);
        return token;
    }

    // 「最初に使ったスレッド以外からは使わせない」ことを検査する
    class SingleThreadGuard
    {
    public:
        bool Check() noexcept
        {
            const std::uint32_t self = CurrentThreadToken();

            std::uint32_t expected = 0;
            if (owner_.compare_exchange_strong(expected, self,
                                               std::memory_order_acq_rel))
            {
                return true;      // 最初の所有者になった
            }

            return expected == self;
        }

        void Reset() noexcept { owner_.store(0, std::memory_order_release); }

        std::uint32_t Owner() const noexcept
        {
            return owner_.load(std::memory_order_acquire);
        }

    private:
        std::atomic<std::uint32_t> owner_{ 0 };
    };
}
```

`Bump` に組み込みます。

```cpp
    AllocResult Allocate(...) noexcept
    {
#if GA_ENABLE_THREAD_CHECK
        if (!threadGuard_.Check())
        {
            assert(false && "このアロケーターは別のスレッドが使っています");
            return std::unexpected(AllocError::OutOfMemory);
        }
#endif
        // ... 従来の処理 ...
    }
```

### 実行する

34.1 節のプログラムを、この検査を有効にして走らせます。

```
Assertion failed: このアロケーターは別のスレッドが使っています
```

**2番目のスレッドが `Allocate` を呼んだ瞬間に止まります。**

競合が実際に起きるのを待つ必要はありません。**「規約に違反した」という事実だけで検出できます。**

### コストと限界

```
v0.23(検査なし)   median=      2.1 ns
検査あり           median=      2.4 ns
```

**0.3 ns。** アトミックな読み込み1回ぶんです。Debug では常時有効にしてよいコストです。

**限界もあります。**

- 「1スレッドからしか使わない」という設計のときにしか使えません
- 意図的に共有する設計(第35章以降)では、この検査を外す必要があります
- 「スレッドを渡す」使い方(あるスレッドで作って、別のスレッドで使う)には `Reset()` が必要です

**それでも価値があります。** 第43章でフレームアロケーターをワーカースレッドごとに持つとき、**取り違えを確実に捕まえられます。**

## 34.5 どこが競合するのか

「`offset_` を守れば済む」わけではありません。**棚卸しします。**

### `Bump`

| メンバ | 章 | 競合すると |
|---|---|---|
| `offset_` | 2 | **同じアドレスが返る** |
| `padding_` | 6 | 統計がずれる |
| `peak_` | 8 | ピーク値が不正確 |
| `depth_` / `epoch_` | 9 | **巻き戻しの検査が壊れる** |
| `finalizers_` | 11 | **リストが切れる/輪になる** |
| `recent_` / `recentHead_` | 14 | 記録が壊れる |
| `stats_` / `tagStats_` | 15 | 統計がずれる |
| `currentTag_` | 15 | **タグが混ざる** |
| `guardBlocks_` | 17 | **リストが壊れる** |
| `traces_` | 18 | **`std::vector` が壊れる(クラッシュ)** |
| `tagSpans_` | 19 | 同上 |
| `memory_.committed_` | 29 | **二重コミット、または未コミット領域へのアクセス** |

**12 か所あります。**

### 想定外のこと

**デバッグ機能も競合します。**

第2部で作った統計、ログ、ガード、トレース——**これらは全部、共有された状態を持っています。**

とくに `traces_` と `tagSpans_` は `std::vector` です。**複数スレッドから `push_back` すれば、`std::vector` 自体が壊れます。** アロケーターの前に、デバッグ機能が落ちます。

### 他のアロケーター

| 実装 | 競合する状態 |
|---|---|
| `Pool` | `free_`(フリーリスト)、`live_`、`usedBits_` |
| `FreeList` | `bins_[128]`、`binMap_`、**ブロックのヘッダそのもの** |
| `Tlsf` | `blocks_[fl][sl]`、`flBitmap_`、`slBitmap_`、ヘッダ |
| `Buddy` | `freeLists_`、`splitBits_`、`freeBits_` |

**フリーリスト系は特に厄介です。** ブロックのヘッダ(`nextFree` など)が共有データなので、**メモリの中身そのものが競合します。**

2つのスレッドが同時に同じブロックを取ろうとすれば、フリーリストが輪になったり、切れたりします。第22章で見た二重解放と同じ壊れ方が、解放していないのに起きます。

## 34.6 選択肢の見取り図

第35章から第37章で扱う選択肢を、先に並べます。

| 方針 | 内容 | 章 |
|---|---|---|
| **A. 共有しない** | スレッドごとに別のアロケーターを持つ | **この章** |
| **B. ロックする** | `std::mutex` で守る | 第35章 |
| **C. スレッドローカル** | スレッドごとのキャッシュ + 中央ヒープ | 第36章 |
| **D. ロックフリー** | `std::atomic` と CAS ループ | 第37章 |

| | 実装の手間 | 単一スレッドでの速度 | 多スレッドでの伸び | 適用範囲 |
|---|---|---|---|---|
| A | **ほぼゼロ** | **変わらない** | **完璧** | 共有が不要な場合のみ |
| B | 小 | 遅くなる | 悪い | どこでも |
| C | 中 | ほぼ変わらない | 良い | 汎用 |
| D | **大** | 変わらない | 良い | 単純な操作のみ |

**Dが最も難しく、最も限定的です。** 「ロックフリーが最強」という直感は、たいてい間違いです。第37章で確かめます。

## 34.7 そもそも共有すべきか

**方針 A から検討してください。これが本章の結論です。**

### ゲームのメモリは、意外とスレッドをまたがない

第3章の4分類を思い出してください。

| 寿命 | スレッドをまたぐか |
|---|---|
| 永続 | ロード時に確保。以降は読むだけ |
| レベル単位 | ロード用スレッドで確保 |
| **フレーム単位** | **ワーカーごとに分けられる** |
| **一時** | **スコープ内で完結する** |

**下の2つが、確保の大半を占めます。** そして、どちらも **スレッドごとに別のアリーナを持てば済みます。**

```cpp
// ワーカースレッドごとにフレームアリーナを持つ
struct WorkerContext
{
    ga::Bump frameArena{ 16 * 1024 * 1024 };
};

std::vector<WorkerContext> workers(std::thread::hardware_concurrency());

void RunJob(int workerIndex, Job& job)
{
    ga::BumpScope scope(workers[workerIndex].frameArena);
    job.Execute(workers[workerIndex].frameArena);
}
```

**共有していないので、競合は原理的に起きません。**

- ロックが要らない → 単一スレッドと同じ速度
- スレッド数が増えても、線形に伸びる
- 実装の変更がゼロ
- **キャッシュの観点でも有利**(スレッドごとに別の領域を触るので、第35章で扱う偽共有も起きにくい)

### 34.1 節の実験を、方針 A で書き直す

```cpp
int main()
{
    constexpr int kThreads   = 8;
    constexpr int kPerThread = 100'000;

    std::vector<std::unique_ptr<ga::Bump>> arenas;
    for (int t = 0; t < kThreads; ++t)
    {
        arenas.push_back(std::make_unique<ga::Bump>(64 * 1024 * 1024));
    }

    std::vector<std::thread> threads;
    for (int t = 0; t < kThreads; ++t)
    {
        threads.emplace_back([&, t] {
            for (int i = 0; i < kPerThread; ++i)
            {
                auto r = arenas[t]->Allocate(64, 16);
                bench::Escape(r.value_or(nullptr));
            }
        });
    }

    for (auto& th : threads) { th.join(); }
}
```

```
重複     : 0 (0.00%)
1確保あたり : 2.1 ns(8スレッド合計で 3.05 億回/秒)
```

**壊れず、しかも単一スレッドと同じ速度が、スレッド数ぶんスケールします。**

### 共有が避けられない場面

**それでも共有が必要な場面はあります。**

- あるスレッドで確保し、**別のスレッドで解放する**(生産者・消費者)
- 全スレッドが参照する共有データを、実行中に確保する
- スレッド数が動的に変わり、事前にアリーナを用意できない
- ライブラリとして提供し、使われ方を制御できない

**第35章から第37章は、これらの場面のためにあります。**

> **順序を間違えないでください。**
>
> まず「共有しなくて済まないか」を検討する。どうしても必要なときだけ、ロックやアトミックに手を出す。
>
> 第20章で「個別解放が本当に必要なのは少数」と書いたのと、**まったく同じ構図です。**

## 次章の予告

第35章では、いちばん素直な方法を試します。**ロックです。**

```cpp
class Bump
{
    std::mutex mutex_;

    AllocResult Allocate(...)
    {
        std::lock_guard lock(mutex_);
        // ... 従来の処理 ...
    }
};
```

**5行の変更で、この章の実験は壊れなくなります。**

問題は速度です。

- 単一スレッドでも、ロックのぶん遅くなる
- 8スレッドで叩くと、**全員が1つのロックを取り合う**
- スレッドを増やすほど、**逆に遅くなる** ことすらある

そして、もう1つ見えにくい問題があります。**偽共有**(false sharing)です。

異なるスレッドが、異なる変数を触っているのに、**同じキャッシュラインに乗っているせいで競合する** 現象です。第32章で学んだキャッシュラインの知識が、ここで効いてきます。

`std::hardware_destructive_interference_size` という長い名前の定数が、その対策として C++17 で導入されました。実際に測って、効果を確認します。

---

> **コラム:メモリモデルという発明**
>
> 「データ競合は未定義動作」という規則は、C++11 で初めて明文化されました。**それ以前は、規格にスレッドの概念すらありませんでした。**
>
> ---
>
> **規格にない世界**
>
> C++03 までの規格は、**単一スレッドのプログラムしか想定していません**。
>
> では、それまでのマルチスレッドプログラムは何だったのか。**「pthread や Win32 API を使えば、たぶん動く」という慣習の上に成り立っていました。**
>
> コンパイラは「最適化してよい範囲」を、単一スレッドの意味論だけから判断していました。マルチスレッドで正しく動くかどうかは、**保証の外** でした。
>
> ---
>
> **壊れていたイディオム**
>
> 有名な例が **ダブルチェックロッキング** です。シングルトンの遅延初期化に、長く使われてきました。
>
> ```cpp
> if (instance == nullptr)              // ① ロックなしで確認
> {
>     lock(mutex);
>     if (instance == nullptr)          // ② ロックして再確認
>     {
>         instance = new Singleton();   // ③
>     }
>     unlock(mutex);
> }
> return instance;
> ```
>
> 「ロックのコストを、初回だけに限定する巧妙な手法」として広まりました。
>
> **しかし、これは壊れています。**
>
> ③ の `new Singleton()` は、内部で2つのことをします。メモリを確保し、コンストラクタを実行する。そして `instance` への代入。**この順序は保証されません。**
>
> コンパイラや CPU が並べ替えれば、**「`instance` に代入されたが、コンストラクタはまだ走っていない」** という瞬間が生まれます。その瞬間に ① を通過した別のスレッドは、**未初期化のオブジェクトを使います。**
>
> 2004 年に発表された論文「C++ and the Perils of Double-Checked Locking」(Scott Meyers と Andrei Alexandrescu)が、この問題を広く知らしめました。**当時の C++ には、これを正しく書く手段が存在しませんでした。**
>
> ---
>
> **C++11 が与えたもの**
>
> C++11 のメモリモデルは、次のことを規定しました。
>
> - **データ競合は未定義動作である**(だから避けなければならない)
> - `std::atomic` による、不可分な読み書き
> - **happens-before 関係** の定義(あるスレッドの書き込みが、別のスレッドから見えることの保証)
> - メモリ順序の指定(`relaxed`、`acquire`、`release`、`seq_cst`)
>
> **これによって初めて、「正しい並行プログラム」を規格の範囲内で書けるようになりました。**
>
> ちなみにダブルチェックロッキングは、C++11 では不要になりました。**関数内の `static` 変数の初期化が、スレッドセーフであると規定されたためです。**
>
> ```cpp
> Singleton& Instance()
> {
>     static Singleton instance;   // C++11 以降、これで安全
>     return instance;
> }
> ```
>
> ---
>
> **私たちにとっての意味**
>
> 34.3 節で「コンパイラが競合しない前提でコードを変形する」と書きました。**これは、メモリモデルが明文化されたからこそ言えることです。**
>
> 規格が「データ競合はない」と仮定してよいと定めたので、コンパイラは安心して最適化できます。**その代わり、私たちは競合を起こしてはいけません。**
>
> 契約です。守れば、強力な最適化の恩恵を受けられる。破れば、何が起きても文句は言えない。
>
> 第37章で `std::atomic` を使うとき、この契約の具体的な条項——メモリ順序——を扱います。
