# 第53章 いつ自作すべきで、いつすべきでないか

---

## この章のゴール

**最終章です。**

この本では、53 章かけて **アロケーターを自作する方法** を扱ってきました。

**最後に、その逆を問います。**

> **いつ自作すべきで、いつすべきでないか。**

- **既製品を差し替えるだけで済むケース** ——実測で比べる
- 自作が勝つ条件と、勝てない条件
- **計測なき最適化への戒め** ——この本で最も多く書いた言葉
- ここから先の道

**「作れる」ことと「作るべき」ことは違います。**

**その判断ができるようになることが、この本の最終的な目的です。**

---

## 53.1 まず、差し替えを試す

**第52章のゲームで、もう1つの選択肢を測ります。**

**何も自作せず、`new` の実装だけを既製品に差し替えます。**

### 差し替えは、驚くほど簡単

**mimalloc のような高性能アロケーターは、静的ライブラリをリンクするだけで `malloc` / `new` を置き換えられます。**

**コードの変更は、ほぼゼロです。**

### 結果

```
=== 第52章のゲーム、段階0 の状態から ===

                    中央値    p95      最大     ピーク   作業時間
  標準の new       8.42 ms  11.24 ms  42.61 ms  412 MB      —
  高性能な既製品   7.88 ms  10.12 ms  28.40 ms  398 MB   数時間
  自作(段階4)     5.94 ms   7.02 ms  13.82 ms  340 MB   1〜2 週間
```

### 費用対効果

```
最大フレーム時間の改善:

  既製品への差し替え : 42.61 → 28.40 ms(-33.4%)  作業:数時間
  自作(全段階)      : 42.61 → 13.82 ms(-67.6%)  作業:1〜2 週間
```

**既製品は、自作の半分の効果を、20 分の 1 の労力で得られます。**

> **これが、この章の出発点です。**
>
> **「まず差し替えを試す。それで足りるなら、そこで終わり。」**

### 差し替えで足りないもの

**しかし、既製品では得られないものもあります。**

| | 既製品 | 自作 |
|---|---|---|
| 確保の速度 | 良い | **より良い**(条件次第) |
| **タグ別の内訳**(第15章) | **なし** | あり |
| **メモリ予算の管理**(第49章) | **なし** | あり |
| **最悪値の保証**(第27章) | 保証なし | あり |
| **GPU メモリ**(第48章) | **対象外** | 必須 |
| 走査の速さ(第32章) | 運次第 | **制御できる** |
| 断片化の構造的回避(第44章) | なし | あり |

**「速さ」だけが目的なら、差し替えで足りることが多い。**

**「見えること」「保証されること」が目的なら、自作が要ります。**

## 53.2 自作が勝つ条件

**第5章から繰り返してきた一文が、答えです。**

> **アロケーターの設計とは、「自分が何を知っているか」を性能に変換する作業です。**

**汎用アロケーターが知らないことを、私たちが知っているとき、自作が勝ちます。**

| 知っていること | 使う道具 | 効果 |
|---|---|---|
| **全部同時に捨てられる** | `Bump`(第8章) | **10 倍**、解放は O(1) |
| **サイズが揃っている** | `Pool`(第21章) | **9 倍**、走査も速い |
| **スレッドをまたがない** | 共有しない(第34章) | **210 倍**(8スレッド) |
| **2の冪に近い + ヘッダを置けない** | `Buddy`(第26章) | GPU で必須 |
| **最悪時間の保証が要る** | `Tlsf`(第27章) | 最大値が 1374 倍改善 |
| **カテゴリ別の内訳が要る** | タグ(第15章) | 既製品では不可能 |
| **ファイルの形式を決められる** | ベイク(第47章) | ロード 3.6 倍 |

**逆に、何も知らなければ、汎用アロケーターに勝てません。**

**第33章で確認したとおりです。**

> 同じ条件(単一スレッド、汎用)で比べると、TLSF は 10.2 ns、Windows ヒープは 11.4 ns。**差は 12% しかありません。**

## 53.3 自作すべきでない条件

**5つ挙げます。1つでも当てはまるなら、立ち止まってください。**

### ① 確保がボトルネックでない

**第52章で見たとおりです。**

```
確保回数を 18,412 → 920 に減らした後、
アロケーターを差し替えても、効果は 2〜3% だった
```

**第12章でも、同じことを確認しました。**

> 確保が 10 倍速くても、初期化に 142 µs かかるなら、全体では 15% しか変わらない。

**プロファイラで、確保が上位に来ていますか。**

**来ていないなら、他を最適化してください。**

### ② 測っていない

**53.4 節で詳しく扱います。**

### ③ 保守する人がいない

**第27章の TLSF は 300 行です。**

**書いた人が抜けたら、誰が直すのでしょうか。**

```
「なぜここで UnlinkFree を先に呼ぶのか」
「なぜ MappingSearch だけ切り上げるのか」
「なぜ this == &other で比較しているのか」
```

**この本を読んでいない人には、分かりません。**

**コメントとテストで補えますが、限界があります。**

> **「自分しか直せないコード」は、負債です。**
>
> **既製品なら、ドキュメントがあり、コミュニティがあり、他の人も使っています。**

### ④ 既製品で足りる

**53.1 節のとおりです。**

**「試してみて、足りなかった」なら自作の理由になります。**

**「試さずに、足りないと思った」は、理由になりません。**

### ⑤ チームが小さい

**メモリ管理の専任者がいないなら、自作の維持は難しい。**

**第49章のコラムで書いたとおりです。**

> 多くの現場では、「メモリを見ている人」が1人います。

**その役割を担う人がいないなら、既製品に任せるべきです。**

## 53.4 計測なき最適化への戒め

**この本で最も多く書いた言葉は、「測る」でした。**

**理由は単純です。予想は、驚くほど当たりません。**

### 予想が外れた事例集

**この本の中で、実測が予想を裏切った場面を集めます。**

| 章 | 予想 | 実測 |
|---|---|---|
| **12** | 確保が 10 倍速ければ、全体も速くなる | **初期化コストが支配的で、15% しか変わらない** |
| **20** | best fit は無駄が少ないので有利 | **削りかすを量産し、first fit に劣る** |
| **21** | 確保の速さが重要 | **走査の速さのほうが効く(9.5 倍)** |
| **26** | バディの内部断片化は 25% 程度 | **分布次第で 0% にも 44% にもなる** |
| **28** | 最も優れたアロケーターがあるはず | **ワークロードごとに勝者が変わる** |
| **32** | リンクリストは遅い | **散らばっていると遅い。連続なら 4.4 倍速い** |
| **33** | 自作は `new` より 10 倍速い | **同条件では 12% しか違わない** |
| **35** | ロックは重いが、まあ許容範囲 | **単一スレッドで `new` より遅くなる** |
| **37** | ロックフリーは速い | **共有しない方式に 71 倍負ける** |
| **52** | ゲームロジックが確保している | **周辺コードが半分近くを占めていた** |

**10 件のうち、直感が当たったものは1つもありません。**

### なぜ外れるのか

**① 現代のハードウェアは複雑すぎる**

キャッシュ、プリフェッチ、分岐予測、TLB、メモリ帯域。**第32章で見たとおり、命令数よりメモリの触り方が支配的です。**

**「この処理は命令が少ないから速い」という推論は、もう通用しません。**

**② 全体の中での割合が見えない**

```
確保を 10 倍速くした!
→ 全体の 2% だった
→ 全体では 1.8% の改善
```

**アムダールの法則です。** 部分を改善しても、その部分が小さければ効果も小さい。

**③ 前提が変わっている**

**第20章の best fit、第32章のリンクリスト。** どちらも「昔は正しかった」判断です。

**メモリが CPU に対して相対的に遅くなり続けた結果、常識が変わりました。**

### だから、順序が決まる

```
① 測る
② ボトルネックを特定する
③ そこだけ直す
④ また測る
```

**第4章でベンチマークの道具を先に作ったのは、この順序を守るためでした。**

**第52章で「測る道具だけ入れて、何も変えない」から始めたのも、同じ理由です。**

> **「速くなったはず」ではなく「速くなった」と言えること。**
>
> **それが、この本で身につけてほしい習慣です。**

## 53.6 ここから先の道

**この本の先に、3つの方向があります。**

### ① カスタムコンテナ

**第38章で、標準コンテナの制約を見ました。**

- `Allocator` 要件が複雑(`propagate_on_container_*`)
- アラインメントを指定できない(C++17 まで)
- `std::vector` の再確保が制御できない

**ゲーム業界には、独自のコンテナライブラリを持つ文化があります。**

**EASTL** が公開されているので、実装を読んでみてください。**「なぜ標準と違う設計にしたのか」が、この本を読んだ後なら理解できます。**

**そして、第30章の `GrowingArray` は、その第一歩でした。**

> **標準に従わない選択もある。** 第38章のコラムで書いたとおりです。

### ② データ指向設計

**第32章で、AoS と SoA の差を測りました。**

```
AoS : 1.85 ns/個
SoA : 0.42 ns/個
```

**「アロケーターを速くする」から「そもそも触るメモリを減らす」への転換です。**

**この方向を突き詰めると、ECS(Entity Component System)に行き着きます。**

- コンポーネントを型ごとに連続配列で持つ(第32章)
- 参照は ID で持つ(第45章のハンドル)
- システムが配列を一括処理する

**第45章 45.8 節で触れたとおり、この本の `HandlePool` は ECS の Entity 管理の最小形です。**

**そして、ECS を支えるのはアリーナです。** コンポーネント配列をどこから確保するか、削除された要素をどう詰めるか——**この本で扱った問題ばかりです。**

### ③ アリーナ中心のアーキテクチャ

**より過激な方向です。**

> **プログラム全体を、アリーナだけで構成する。**

```
起動時    : 永続アリーナを確保
シーン    : シーンアリーナ
フレーム  : フレームアリーナ
一時      : スコープアリーナ

個別解放  : しない
```

**第44章 44.9 節の3層構成を、徹底したものです。**

**汎用ヒープを、まったく使いません。**

**利点:**

- 断片化が原理的に起きない
- 解放漏れが起きない(アリーナ単位で片づく)
- **メモリの使用量が完全に予測できる**
- コードが単純になる(`delete` を書かない)

**制約:**

- **設計段階で、寿命を決めなければならない**
- 「いつ死ぬか分からないもの」を扱いにくい

**すべてのプロジェクトに向くわけではありません。**

**しかし、この本を読んだ後なら、「その選択肢がある」と分かります。**

### ④ さらに深く

**メモリ管理の周辺には、まだ広い世界があります。**

**ガベージコレクション。** 第46章で少し触れました。世代別、インクリメンタル、並行。**「自動化のコスト」を理解した上で読むと、設計判断が見えてきます。**

**リージョンとライフタイム。** 第20章のコラムで、Tofte と Talpin のリージョン推論に触れました。**Rust の所有権とライフタイムは、その系譜にあります。**

**「コンパイル時に寿命を検査する」という発想は、この本で扱った「実行時に寿命を管理する」の対極です。**

**両方を知っていると、設計の幅が広がります。**

**アロケーターの最新研究。** 第33章のコラムで挙げた mimalloc、snmalloc の論文は、公開されています。**この本を読んだ後なら、読めるはずです。**

## 53.8 最後に

**第2章で、こう書きました。**

> **アロケーターとは、大きなバイト列を、要求されたぶんだけ切り分けて渡す役でしかない。**

**その通りです。核心は、いまも `offset_ += size` の1行です。**

**残りの 52 章は、すべて「その周りに何が必要か」の話でした。**

- 正しく切り分けるには(アラインメント、エラー処理)
- 安全に使うには(検証、可視化、テスト)
- 返してもらうには(解放、合体、断片化)
- OS と付き合うには(仮想メモリ、ページ)
- 複数のスレッドで使うには(ロック、キャッシュ)
- C++ の世界で使うには(標準コンテナ、`operator new`)
- ゲームで使うには(フレーム、シーン、GPU、予算)

**そして最後に——本当に必要かを判断するには。**

### 20 行が、どこへ行ったか

**第2章の `Bump` は、いまも本の中に残っています。**

**第43章のフレームアロケーターの中で、毎フレーム回っています。**

**第47章では、シリアライザとして働きました。**

**最も単純なものが、最も長く使われました。**

**これは偶然ではありません。**

**第2章のコラムで書いた一文です。**

> **コラム:制約が、設計を生む**
>
> **この本のすべてのアロケーターは、制約から生まれました。**
>
> ---
>
> **`Bump`(第2章)は、「解放しない」という制約から生まれました。**
>
> 制約を受け入れた結果、確保が `offset_ += size` の1行になりました。
>
> **`Pool`(第21章)は、「サイズが1種類」という制約から生まれました。**
>
> 制約を受け入れた結果、探索が不要になり、断片化が消えました。
>
> **`Buddy`(第26章)は、「2の冪だけ」という制約から生まれました。**

>
> **`GrowingArray`(第30章)は、「上限がある」という制約から生まれました。**
>
> 制約を受け入れた結果、要素が移動しなくなりました。
>
> **フレームアロケーター(第43章)は、「フレーム末に全部捨てる」という制約から生まれました。**

>
