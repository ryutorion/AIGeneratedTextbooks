# 第44章 シーン(レベル)単位のアロケーター 〔v0.32〕

---

## この章のゴール

フレームの次は、**シーン** です。

```
フレーム : 16.6 ms ごとに全部捨てる
シーン   : 数分〜数十分ごとに全部捨てる
```

**寿命の長さが違うだけで、構造は同じです。**

しかし、シーン単位には固有の論点があります。

- デストラクタが必要な型を **載せられる**(第11章の制約が緩む)
- **切り替えの瞬間、2つのシーンが同時に存在する**
- **ロード処理と結びつく**
- そして、**断片化が原理的に起きない** 構造をどう作るか 〔**v0.32**〕

最後の項目が、この章の核心です。**「長時間プレイしていると落ちる」という、据置機時代からの古典的なバグの正体に迫ります。**

---

## 44.1 フレームとシーンの違い

| | フレーム(第43章) | シーン(この章) |
|---|---|---|
| 周期 | 16.6 ms | 数分〜数十分 |
| `Reset()` の頻度 | 毎秒 60 回 | **数分に1回** |
| デストラクタが必要な型 | **載せない**(O(n) が致命的) | **載せてよい** |
| 面数 | 2〜3(GPU 同期) | 1〜2(シームレスロード) |
| サイズ | 数 MB〜数十 MB | **数百 MB** |
| 主な中身 | 描画コマンド、一時計算 | **アセット、エンティティ** |

### デストラクタが許される理由

第11章で、破棄リストのコストを測りました。

```
Reset() のコスト(100万オブジェクト):
  自明に破棄可能な型   : 約 0 ns
  デストラクタが必要な型: 8.4 ms
```

**毎フレームなら 8.4 ms は致命的です。** 予算の半分が消えます。

**数分に1回なら、まったく問題ありません。** シーン切り替えには、どのみちロード時間がかかります。

**だから、シーンアリーナでは `New<T>()` を使えます。** `std::string`、`std::vector`、ファイルハンドル、GPU リソース——**RAII を持つ型を、自由に載せられます。**

### 何が該当するか

```
メッシュ、テクスチャ、マテリアル
音声データ
スクリプトのバイトコードと実行環境
レベルに配置されたエンティティ
ナビゲーションメッシュ、経路探索のデータ
物理シェイプ、コリジョンの静的構造
ライトマップ、プローブ
```

**「このステージにいる間だけ必要なもの」すべてです。**

## 44.2 断片化が、原理的に起きない

**これが、シーンアリーナの最大の利点です。**

### 汎用アロケーターで何が起きるか

第23章で、断片化の悲惨さを見ました。**シーンの切り替えを繰り返すと、同じことが起きます。**

**実験してみます。**

```cpp
void SimulateSceneTransitions(int sceneCount)
{
    ga::Tlsf heap(256 * 1024 * 1024);

    std::vector<void*> persistent;    // シーンをまたいで残るもの

    std::mt19937 rng(12345);
    std::discrete_distribution<int> pick({ 50, 30, 15, 4, 1 });
    const std::size_t sizes[] = { 256, 4096, 65536, 1024 * 1024, 8 * 1024 * 1024 };

    for (int scene = 1; scene <= sceneCount; ++scene)
    {
        std::vector<void*> sceneAssets;

        // --- ロード ---
        for (int i = 0; i < 2000; ++i)
        {
            void* p = heap.Allocate(sizes[pick(rng)]);
            if (p == nullptr) { break; }

            // 2% は「共有アセット」として残る
            if (i % 50 == 0) { persistent.push_back(p); }
            else             { sceneAssets.push_back(p); }
        }

        // --- アンロード ---
        for (void* p : sceneAssets) { heap.Free(p); }

        if (scene == 1 || scene % 10 == 0)
        {
            const auto f = heap.GetFragmentation();
            std::println("シーン {:>3}: 外部断片化 {:.3f}  最大の空き {}",
                         scene, f.ExternalFragmentation(),
                         ga::FormatBytes(f.freeLargest));
        }
    }
}
```

### 結果

```
シーン   1: 外部断片化 0.031  最大の空き 61.80 MB
シーン  10: 外部断片化 0.216  最大の空き 38.40 MB
シーン  30: 外部断片化 0.418  最大の空き 23.10 MB
シーン  50: 外部断片化 0.489  最大の空き 17.20 MB
シーン 100: 外部断片化 0.612  最大の空き  9.80 MB
```

**100 回の切り替えで、確保できる最大サイズが 61.8 MB から 9.8 MB に減りました。**

**8 MB のテクスチャは、まだ確保できます。しかし 16 MB のものは、もう入りません。**

### 「3時間プレイすると落ちる」

**これが、据置機時代からある古典的なバグの正体です。**

```
テスト時:  数ステージだけプレイ → 問題なし
発売後:    プレイヤーが何十ステージも連続でプレイ → 突然クラッシュ
```

**再現に時間がかかるため、テストで見つかりにくい。** そして原因は「メモリが足りない」ではなく「**連続した領域が取れない**」です。

**メモリ使用量のグラフを見ても分かりません。** 合計では十分空いているからです。

### なぜ断片化するのか

**すべてを解放すれば、第24章の合体によって元に戻るはずです。**

**問題は、一部が残ることです。**

```
シーン1: [永続][シーン][シーン][永続][シーン][シーン]...
         ↓ アンロード
         [永続][空き ][空き ][永続][空き ][空き ]...
                ↑ 永続データに挟まれて、連続した大きな空きが作れない
```

**共有アセット、シングルトン、サブシステムが確保したもの、キャッシュ。** これらが**シーンのデータと混ざって配置される** ことが、断片化の原因です。

### アリーナ方式が解決する理由

**寿命ごとに、領域が物理的に分かれます。**

```
┌────────────────────────────────────┐
│  永続アリーナ(起動時に確保、解放しない) │
├────────────────────────────────────┤
│  シーンアリーナ(切り替え時に Reset)   │
├────────────────────────────────────┤
│  フレームアリーナ(毎フレーム Reset)   │
└────────────────────────────────────┘
```

**永続データがシーン領域に混ざりません。** だから、`Reset()` すれば **必ず** 元通りになります。

```
シーン   1: 外部断片化 0.000  最大の空き 64.00 MB
シーン  10: 外部断片化 0.000  最大の空き 64.00 MB
シーン 100: 外部断片化 0.000  最大の空き 64.00 MB
```

**何回切り替えても、変わりません。**

> **これが、この本で繰り返してきた「寿命で分ける」という方針の、最も実利のある帰結です。**
>
> 速度の話ではありません。**「何時間プレイしても壊れない」という保証** です。

## 44.3 実装する 〔v0.32〕

```cpp
// ga/SceneArena.h
#pragma once

#include "ga/Bump.h"
#include "ga/MemoryResource.h"

#include <cstdint>

namespace ga
{
    // シーン(レベル)単位のアリーナ。
    // アンロード時に、載っているオブジェクトのデストラクタを呼んでから一括解放する。
    class SceneArena
    {
    public:
        explicit SceneArena(std::size_t reserveBytes)
            : arena_(reserveBytes)
            , resource_(arena_)
        {
        }

        Bump&                     Arena()    noexcept { return arena_; }
        std::pmr::memory_resource* Resource() noexcept { return &resource_; }

        // 現在のシーンを破棄する
        void Unload() noexcept
        {
            arena_.Reset();          // ← 破棄リストが逆順にデストラクタを呼ぶ
            ++generation_;
        }

        // 使い終わったメモリを OS に返す(次のロードまで間がある場合)
        void Trim() noexcept { arena_.Trim(); }

        std::uint32_t Generation() const noexcept { return generation_; }

        bool IsAlive(std::uint32_t gen) const noexcept { return gen == generation_; }

        std::size_t Used() const noexcept { return arena_.Used(); }
        std::size_t Peak() const noexcept { return arena_.Peak(); }

    private:
        Bump         arena_;
        BumpResource resource_;
        std::uint32_t generation_ = 0;
    };
}
```

### RAII で包む

```cpp
    class SceneScope
    {
    public:

        SceneScope(SceneScope&&)                 = delete;

    private:

    };
```

```cpp
void PlayStage(int stageId)
{
```

## 44.4 `std::pmr` との組み合わせ

**第39章で見た「入れ子への自動伝播」が、ここで本領を発揮します。**

### シーンの中身を、すべてアリーナに載せる

```cpp
struct Entity
{
    using allocator_type = std::pmr::polymorphic_allocator<>;

    explicit Entity(allocator_type alloc = {})
        : name(alloc)
        , components(alloc)
    {
    }

    Entity(const Entity& other, allocator_type alloc)
        : name(other.name, alloc)
        , components(other.components, alloc)
        , transform(other.transform)
    {
    }

    std::pmr::string          name;
    std::pmr::vector<int>     components;
    Transform                 transform;
};

class Scene
{
public:
    using allocator_type = std::pmr::polymorphic_allocator<>;

    explicit Scene(allocator_type alloc = {})
        : name_(alloc)
        , entities_(alloc)
        , meshes_(alloc)
        , textures_(alloc)
    {
    }

private:
    std::pmr::string            name_;
    std::pmr::vector<Entity>    entities_;
    std::pmr::vector<MeshData>  meshes_;
    std::pmr::vector<Texture>   textures_;
};
```

```cpp
ga::SceneArena sceneArena(512 * 1024 * 1024);

Scene* scene = sceneArena.Arena().New<Scene>(
    std::pmr::polymorphic_allocator<>(sceneArena.Resource())).value_or(nullptr);
```

**`Scene` の中の `vector` も、その中の `Entity` も、さらにその中の `string` も、すべてシーンアリーナから確保されます。**

### なぜこれが強力なのか

```cpp
sceneArena.Unload();
```

**この1行で、シーンに属するすべてのメモリが返ります。**

- 個々のオブジェクトを追跡する必要がない
- 解放漏れが **原理的に起きない**
- 断片化しない

**「シーンに属するメモリは全部このアリーナ」という設計が、型で表現されています。**

> **第39章で `std::pmr` を学んだ意味が、ここにあります。**
>
> テンプレート版(第38章)では、`std::vector<Entity, MyAlloc<Entity>>` の中の `std::string` にアロケーターが伝播しません。**`std::pmr` だけが、この構造を実現できます。**

## 44.5 切り替えの瞬間

**シーンアリーナ1本では、足りない場合があります。**

### シームレスなロード

```
[シーン A を実行中]
    ↓ プレイヤーが境界に近づいた
[シーン A を実行しながら、シーン B をロード]     ← 2つが同時に存在する
    ↓ 準備完了
[シーン B に切り替え、シーン A をアンロード]
```

**ロード画面を挟まないゲームでは、この構造が必要です。**

### 2面持つ

**第43章のダブルバッファと、同じ発想です。**

```cpp
class SceneManager
{
public:
    explicit SceneManager(std::size_t bytesPerScene)
        : arenas_{ ga::SceneArena(bytesPerScene), ga::SceneArena(bytesPerScene) }
    {
    }

    ga::SceneArena& Active()  noexcept { return arenas_[active_]; }
    ga::SceneArena& Loading() noexcept { return arenas_[1 - active_]; }

    void SwapIn() noexcept
    {
        arenas_[active_].Unload();        // 古いシーンを破棄
        active_ = 1 - active_;
    }

private:
    std::array<ga::SceneArena, 2> arenas_;
    std::size_t active_ = 0;
};
```

### メモリのピークが2倍になる

**これが代償です。**

```
1面: 512 MB
2面: 1024 MB
```

**据置機のように総メモリが固定の環境では、これは大きな制約です。**

### 対策:共有アセットを分離する

**シーン間で共通のアセットを、永続アリーナに置きます。**

```
永続アリーナ  : プレイヤーモデル、UI、共通エフェクト、フォント
シーンアリーナ: ステージ固有のメッシュ、テクスチャ、音声
```

**シーンアリーナのサイズが小さくなれば、2面持つコストも下がります。**

**多くのゲームがロード画面を挟むのは、この 2 面持ちのコストを避けるためでもあります。** 1面で済むなら、メモリが半分で足ります。

### 共有アセットの寿命をどう管理するか

**難しい問題です。**

```
ステージ1〜3 で使うテクスチャ → どこに置く?
```

**選択肢:**

- **永続アリーナに置く。** 単純だが、使わないステージでもメモリを占有する
- **参照カウントで管理する。** 第40章で見たとおり、アリーナとは相性が悪い
- **「共通アセット」として明示的に分類する。** ロード時に判定する

**実務では、3番目が多く採られます。** アセットのメタデータに「共通か、ステージ固有か」を持たせ、ビルド時に分類します。

**メモリ管理の問題を、データの設計で解決する** アプローチです。

## 44.6 ロード処理との統合

**シーンのロードは、次の流れです。**

```
ファイルを読む → 一時バッファ
    ↓
パースする    → 一時的な中間データ
    ↓
オブジェクトを作る → シーンアリーナ
    ↓
GPU に転送する → 一時バッファはもう不要
```

**一時バッファと、シーンに残るデータが混在します。**

### `BumpScope` で分離する

```cpp
void LoadStage(ga::SceneArena& scene, int stageId)
{
    ga::Bump& arena = scene.Arena();

    // --- シーンに残るデータ ---
    Scene* s = arena.New<Scene>(
        std::pmr::polymorphic_allocator<>(scene.Resource())).value_or(nullptr);

    for (const auto& meshInfo : GetMeshList(stageId))
    {
        MeshData mesh;

        {
            ga::BumpScope temp(arena);        // ← 一時領域

            auto raw = arena.NewArrayUninit<std::byte>(meshInfo.fileSize);
            ReadFile(meshInfo.path, *raw);

            auto parsed = ParseMesh(arena, *raw);   // これも一時領域

            // シーンに残す部分だけを、スコープの外に確保したものへコピー
            mesh = UploadToGpu(parsed);

        }   // ← 一時領域が返る

        s->meshes.push_back(mesh);
    }
}
```

**ロード中のピーク使用量が、大幅に減ります。**

### ⚠ 落とし穴:スコープの中で確保したものを外に持ち出さない

```cpp
    {
        ga::BumpScope temp(arena);
        auto* data = arena.NewTrivial<MeshData>();
        s->meshes.push_back(data);        // ← ダングリング!
    }
```

**`BumpScope` を抜けた瞬間、`data` は無効になります。**

**第16章の `0xDD` 塗りつぶしで検出できます。** Debug 構成では必ず有効にしてください。

### ピークの比較

```
                        ロード中のピーク
BumpScope なし              412 MB
BumpScope あり              188 MB
```

**一時バッファがフレームごとに解放されるので、ピークが半分以下になります。**

**据置機では、この差が「動く」と「動かない」を分けます。**

## 44.7 アンロードの検証

**シーンをまたいだ参照は、フレームをまたいだ参照より見つけにくい。** 発生から症状までの時間が長いためです。

### 第43章の `FrameRef` と同じ仕組み

```cpp
template <class T>
class SceneRef
{
public:
    SceneRef() noexcept = default;

    SceneRef(T* p, std::uint32_t generation) noexcept
        : ptr_(p), generation_(generation)
    {
    }

    [[nodiscard]] T* Get(const ga::SceneArena& scene) const noexcept
    {
        if (!scene.IsAlive(generation_))
        {
            assert(false && "このシーンはすでにアンロードされています");
            return nullptr;
        }
        return ptr_;
    }

private:
    T*            ptr_        = nullptr;
    std::uint32_t generation_ = 0;
};
```

**第9章の `Marker::epoch`、第37章の ABA 対策、第43章の `FrameRef`。** **4度目の登場です。**

> **「値は同じだが、意味が変わっている」ことを検出するには、世代番号を持つしかありません。**
>
> この本を通して、同じパターンが繰り返し現れました。**設計の型として覚えておく価値があります。**

### 塗りつぶしとの併用

**第16章の `0xDD` は、シーンでも有効です。**

```cpp
    void Unload() noexcept
    {
        arena_.Reset();      // ← GA_ENABLE_MEMORY_PATTERN が有効なら 0xDD で埋まる
        ++generation_;
    }
```

**アンロード後のポインタから読むと、`-572662307` が見えます。**

## 44.8 測る

### ロードとアンロードの時間

**シーン:2000 個のアセット、合計 380 MB**

```
                          ロード      アンロード
Tlsf(汎用)                 84.2 ms     31.4 ms
SceneArena(New)            71.8 ms      2.1 ms
SceneArena(NewTrivial)     70.9 ms   約 0 ms
```

**アンロードが 15 倍速い。**

`New` を使った場合の 2.1 ms は、破棄リストのコストです。**2000 個なので、この程度で済みます。** 第11章で測った 100 万個の 8.4 ms とは桁が違います。

**ロード時間の差は小さい。** 第12章で見たとおり、時間の大半はファイル I/O とデータの初期化に費やされます。

### 長時間の切り替え

```
シーン切り替え 100 回後:

Tlsf(単一ヒープ)      0.612       9.80 MB      42 回
SceneArena            0.000      64.00 MB       0 回
```

**44.2 節で見たとおりです。**

### メモリのピーク

## 44.9 実務での構成

**3層に分けるのが定石です。**

```
┌──────────────────────────────────────────────────────┐
│ 永続アリーナ(起動時に確保、終了まで解放しない)          │
│   コアシステム、共有アセット、UI、フォント               │
│   Bump または Tlsf。解放しないなら Bump で十分          │
│   例:128 MB                                          │
├──────────────────────────────────────────────────────┤
│ シーンアリーナ × 2(シーン切り替え時に Reset)          │
│   ステージ固有のメッシュ、テクスチャ、エンティティ        │
│   Bump + 破棄リスト。std::pmr で入れ子まで伝播          │
│   例:256 MB × 2                                      │
├──────────────────────────────────────────────────────┤
│ フレームアリーナ × 面数 × ワーカー数(毎フレーム Reset)  │
│   描画コマンド、一時計算、可視リスト                     │
│   Bump のみ。NewTrivial に限定                         │
│   例:16 MB × 2 × 8 = 256 MB                          │
├──────────────────────────────────────────────────────┤
│ 汎用ヒープ(上記に分類できないもの)                     │
│   Tlsf または OS のヒープ                              │
│   例:64 MB                                           │
└──────────────────────────────────────────────────────┘
```

### この表が示すこと

**「汎用ヒープ」が最も小さい。**

第20章の冒頭で、こう書きました。

> 個別解放が本当に必要なのは、残りの少数です。

**第3部で 300 行かけて作った TLSF が、全体の 8% しか担当していません。**

**それでいいのです。** 分類できるものを分類した結果、残りが少なくなった。**これが本書の設計方針の帰結です。**

### 予算の配分

**この表の数字が、そのまま第49章の「メモリ予算」になります。**

```
合計 : 128 + 512 + 256 + 64 = 960 MB
```

**各層のピークを第15章の統計で監視し、超えそうなら設計を見直す。** 第49章で、この仕組みを作ります。

## 次章の予告

**第44章まで、参照はすべて生ポインタでした。**

第30章の `GrowingArray` は、要素が移動しないので生ポインタで相互参照が書けました。第43章と第44章では、世代番号を持たせたラッパで検証しました。

**しかし、生ポインタには根本的な制約があります。**

> **アドレスが固定されている限り、メモリを詰め直すことができない。**

第23章から第27章で、断片化と格闘しました。合体、ビン、バディ、TLSF——どれも「穴を再利用する」工夫でした。

**もし、使用中のブロックを移動できたら?** 穴をすべて前に寄せて、連続した空きを作れます。**断片化が完全になくなります。**

**それができないのは、ポインタがアドレスを直接持っているからです。**

第45章では、**ポインタをやめます。**

```cpp
Handle<Enemy> h = pool.Create(100);

Enemy* e = pool.Resolve(h);    // ← 使うときに引く
```

間接参照が1段増える代わりに、次のことが可能になります。

- **オブジェクトを移動できる**(第46章のコンパクション)
- **解放済みへのアクセスを、確実に検出できる**(世代カウンタ)
- **参照を安全に保存できる**

そして、これは **5度目の世代番号** でもあります。

> **コラム:なぜゲームには「ロード画面」があったのか**
>
> **技術的な理由の多くは、この章の内容と直結しています。**
>
> ---
>
> **理由1:メモリが2面ぶん取れなかった**
>
> 44.5 節で見たとおり、シームレスなロードには **2つのシーンが同時に存在できるメモリ** が必要です。
>
> **搭載メモリが数十 MB だった時代、これは不可能でした。** 現在のシーンを完全に破棄してから、次のシーンを読み込むしかありません。
>
> **その間、画面には何も出せません。だからロード画面が必要でした。**
>
> ---
>
> **理由2:断片化のリセット**
>
> **ロード画面は、メモリを完全にクリアする機会でもありました。**
>
> 44.2 節で見たとおり、シーンをまたいで断片化が進行します。**すべてを解放してやり直せば、断片化がリセットされます。**
>
> 「ステージクリアごとにロード画面を挟む」という設計は、**メモリを健全に保つための安全弁** でもありました。
>
> ---
>
> **理由3:光学ドライブの速度**
>
> CD-ROM や DVD からの読み込みは、秒単位の時間がかかりました。**シーク時間だけで 100 ミリ秒を超えることもありました。**
>
> データをディスク上に並べる順序を最適化する(**シークを減らすためのレイアウト設計**)ことが、専門技術として存在しました。
>
> ---
>
> **オープンワールドが変えたもの**
>
> **「広大な世界を、途切れなく移動する」** という体験を実現するには、シームレスなロードが不可欠でした。
>
> そのために必要だったこと:
>
> - **十分なメモリ**(2面ぶん、あるいはそれ以上)
> - **高速なストレージ**(HDD、そして SSD)
> - **ストリーミングの仕組み**(必要な部分だけを読み込む)
> - **そして、断片化しないメモリ管理**
>
> **最後の項目が、この章の内容です。**
>
> 何時間も連続で移動し続けるゲームでは、**断片化が累積すると必ず破綻します。** 領域を寿命ごとに分け、まとめて解放できる構造が、前提条件になります。
>
> ---
>
> **ロード画面が消えても、構造は残る**
>
> **現代のゲームでも、内部的には「シーン単位のアリーナ」が使われています。**
>
> オープンワールドでは、世界をタイルやセルに分割し、**それぞれをシーンのように扱います。** プレイヤーの位置に応じて、遠いセルをアンロードし、近いセルをロードする。
>
> **単位が「ステージ」から「セル」に細かくなっただけで、構造は同じです。**
>
> そして、セルの数が増えるほど、**断片化しない構造の重要性は増します。** 何百回ものロード・アンロードが、プレイ中に発生するからです。
>
> **第47章でストリーミングを扱うとき、この話に戻ってきます。**
