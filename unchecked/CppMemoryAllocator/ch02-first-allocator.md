## 2.1 アロケーターは何をする道具なのか

いきなりコードに行く前に、30秒だけ考えてください。

あなたの手元に、**1メートルの板が1枚**あるとします。ここに人が次々やってきて、こう言います。

> 「10センチちょうだい」
> 「25センチちょうだい」
> 「3センチちょうだい」

あなたの仕事は、板を切って渡すことです。

このとき、あなたは何を覚えておく必要があるでしょうか。

答えは1つだけです。**どこまで切ったか。**

左端から順に切っていくなら、覚えておくべきは「今、左端から何センチのところに刃を入れればいいか」という数字だけです。10センチ渡したら、次は10センチの位置から。さらに25センチ渡したら、次は35センチの位置から。

これがアロケーターの正体です。

> **アロケーターとは、大きなバイト列を、要求されたぶんだけ切り分けて渡す役でしかない。**

「メモリを作り出す」わけでも「メモリを管理する」わけでもありません。すでにある領域を、切って、渡す。それだけです。

この章で書くのは、まさにこの板の話をそのままコードにしたものです。

## 2.2 「進めるだけ」という戦略

板の例をメモリに置き換えます。

```
  buffer_
    │
    ▼
    ┌───────────────────────────────────────────────┐
    │                                               │  1024バイト
    └───────────────────────────────────────────────┘
    ↑
  offset_ = 0     ← 次に切る位置
```

ここで「4バイトください」と言われたら、今の位置を返して、位置を4進めます。

```
    ┌────┬──────────────────────────────────────────┐
    │////│                                          │
    └────┴──────────────────────────────────────────┘
     返した    ↑
            offset_ = 4
```

さらに「4バイトください」。

```
    ┌────┬────┬─────────────────────────────────────┐
    │////│////│                                     │
    └────┴────┴─────────────────────────────────────┘
                ↑
             offset_ = 8
```

これだけです。この方式には名前があります。**バンプアロケーター**(bump allocator)、あるいは**リニアアロケーター**、**アリーナアロケーター**とも呼ばれます。

"bump" は「こつんと突く」「押し上げる」という意味で、ポインタを押し進めるイメージから来ています。本書ではクラス名を `Bump` にします。

確保の処理は、たった2行になります。

1. 今の位置を返す
2. 位置をサイズぶん進める

これより単純なアロケーターは存在しません。

## 2.3 書いてみる

第1章で作った `Playground.cpp` を、次のように書き換えていきます。1ステップずつ進めましょう。

### ステップ1:空のクラスを置く

まず器だけ作ります。

```cpp
#include <cstddef>
#include <vector>
#include <print>

class Bump
{
};

int main()
{
    Bump bump;
    std::println("できた");
}
```

ビルドが通ることを確認してください。何もしないクラスですが、ここから足していきます。

### ステップ2:メモリの塊を持たせる

切り分ける元になる「板」が必要です。`std::vector<std::byte>` を1本持たせます。

```cpp
class Bump
{
public:
    explicit Bump(std::size_t capacity)
        : buffer_(capacity)
    {
    }

private:
    std::vector<std::byte> buffer_;
};
```

`main` も直します。

```cpp
int main()
{
    Bump bump(1024);   // 1024バイトの板を用意する
    std::println("できた");
}
```

**ここで気になった人へ:** 「メモリを配るクラスを作るのに、メモリを配るクラス(`std::vector`)を使うのか?」

はい、使います。これは矛盾ではなく、**ブートストラップ**です。

`std::vector` の確保は、コンストラクタで**1回だけ**起きます。そのあと `Bump` が何万回確保要求を受けても、`std::vector` は一切登場しません。「最初に1回だけ大きく借りて、あとは自分で切り分ける」——これがアリーナ方式の基本形です。

とはいえ、この土台には後で不満が出ます。第29章で `std::vector<std::byte>` を捨てて、Windows の `VirtualAlloc` に置き換えます。それまでの27章間は、これで十分です。

#### `std::byte` について

`char` でも `unsigned char` でもなく `std::byte` を使っています(C++17 で追加)。

`char` は「文字」であり「数値」でもあります。`+` や `-` が使えてしまいますし、`std::println` に渡せば文字として表示されます。しかし今ほしいのは、**意味のない生のバイト**です。

`std::byte` は算術演算ができません。ビット演算と、明示的なキャストだけができます。「ここは型のない生メモリだ」という意図がコードに書かれる、という価値があります。本書では生メモリを扱う場面で一貫して `std::byte` を使います。

### ステップ3:確保する

いよいよ本体です。`Allocate` を足します。

```cpp
class Bump
{
public:
    explicit Bump(std::size_t capacity)
        : buffer_(capacity)
    {
    }

    void* Allocate(std::size_t size)
    {
        std::byte* result = buffer_.data() + offset_;   // ① 今の位置
        offset_ += size;                                // ② 進める
        return result;                                  // ③ 返す
    }

private:
    std::vector<std::byte> buffer_;
    std::size_t            offset_ = 0;
};
```

これで完成です。本体は3行しかありません。

- `buffer_.data()` は板の左端のアドレス
- そこに `offset_` を足せば「次に切る位置」
- 返したあと、`offset_` を要求サイズぶん進める

戻り値が `void*` なのは、「型のない生メモリ」を返しているからです。`malloc` も `operator new` も `void*` を返します。同じ流儀に合わせています。

## 2.4 使ってみる:`int` を3つ

書いたものを使います。`main` を次のようにしてください。

```cpp
int main()
{
    Bump bump(1024);

    // int を3つ確保する
    int* a = static_cast<int*>(bump.Allocate(sizeof(int)));
    int* b = static_cast<int*>(bump.Allocate(sizeof(int)));
    int* c = static_cast<int*>(bump.Allocate(sizeof(int)));

    // 値を書く
    *a = 10;
    *b = 20;
    *c = 30;

    // 読む
    std::println("a = {}", *a);
    std::println("b = {}", *b);
    std::println("c = {}", *c);
}
```

**Ctrl + F5** で実行。

```
a = 10
b = 20
c = 30
```

**動きました。** あなたは今、自分で書いたメモリアロケーターの上に、変数を3つ置いたことになります。

### `static_cast` が必要な理由

`Allocate` は `void*` を返します。`void*` は「アドレスは知っているが、そこに何があるかは知らない」ポインタです。そのままでは `*a` で読み書きできません。

だから「ここには `int` があると思って扱う」と宣言する必要があります。それが `static_cast<int*>` です。

書いていて煩わしいと感じたはずです。実際、煩わしいです。これは第10章で `New<T>()` という関数を作って解消します。今は「生メモリを型に見せかけるには変換がいる」という事実だけ確認してください。

> **細かいことが気になる人へ**
> 「生メモリに `int` の値を書く」という操作は、C++ の規格の上では実は微妙な議論があります(オブジェクトの生存期間が始まっていないのでは、という話です)。この点は第42章で C++23 の `std::start_lifetime_as` を使って正式に片づけます。それまでは実用上問題なく動くので、先に進んでください。

## 2.5 アドレスを見て、何が起きたか確かめる

「動いた」だけでは面白くありません。返ってきたアドレスを実際に見てみましょう。

```cpp
#include <cstddef>
#include <cstdint>
#include <vector>
#include <print>

// ... Bump クラスは省略 ...

int main()
{
    Bump bump(1024);

    void* p0 = bump.Allocate(4);
    void* p1 = bump.Allocate(4);
    void* p2 = bump.Allocate(4);

    std::println("p0 = {}", p0);
    std::println("p1 = {}", p1);
    std::println("p2 = {}", p2);

    // 差を見る
    auto n0 = reinterpret_cast<std::uintptr_t>(p0);
    auto n1 = reinterpret_cast<std::uintptr_t>(p1);
    auto n2 = reinterpret_cast<std::uintptr_t>(p2);

    std::println("");
    std::println("p1 - p0 = {} バイト", n1 - n0);
    std::println("p2 - p1 = {} バイト", n2 - n1);
}
```

実行結果の例です(アドレスの値は実行のたびに変わります)。

```
p0 = 0x1d4f2c8a3b0
p1 = 0x1d4f2c8a3b4
p2 = 0x1d4f2c8a3b8

p1 - p0 = 4 バイト
p2 - p1 = 4 バイト
```

**ぴったり4バイトずつ並んでいます。** 隙間はゼロです。

これがバンプアロケーターの重要な性質です。確保したデータが**メモリ上に連続して並ぶ**。この性質が、なぜゲームで効くのか。それは第32章でキャッシュの話をするときに、数字で見ることになります。

### サイズを変えてみる

要求サイズを変えると、進み方がどう変わるか確認してください。

```cpp
void* p0 = bump.Allocate(1);
void* p1 = bump.Allocate(7);
void* p2 = bump.Allocate(100);
```

```
p1 - p0 = 1 バイト
p2 - p1 = 7 バイト
```

要求されたぶんだけ、正確に進んでいます。1バイトも無駄がありません。

……ただし、これは実は **問題** でもあります。`p1` は1バイトずれた位置にあり、ここに `int` を置くと具合が悪いのです。この話は第6章でやります。今は「無駄なく詰まっている」という事実だけ覚えておいてください。

## 2.6 解放しない、という選択

ここまで読んで、当然こう思ったはずです。

> **「解放は?」**

ありません。`Free` も `Deallocate` も書いていません。書く予定も、当分ありません。

これは手抜きではなく、**設計上の選択**です。

### 解放を許した瞬間に何が起きるか

もし個別の解放を許したら、こうなります。

```
    ┌────┬────┬────┬────┬────┬────────────────┐
    │ A  │ B  │ C  │ D  │ E  │                │
    └────┴────┴────┴────┴────┴────────────────┘

  B と D を解放すると……

    ┌────┬────┬────┬────┬────┬────────────────┐
    │ A  │    │ C  │    │ E  │                │
    └────┴────┴────┴────┴────┴────────────────┘
           穴        穴
```

穴ができます。すると次の要求が来たとき、こう考えなければなりません。

- どこに穴があるか、記録しておく必要がある
- 要求サイズに合う穴を **探す** 必要がある
- 合う穴がなければ、後ろから取る
- 隣り合った穴は、くっつけたほうがいい
- 穴が細かく散らばると、合計では足りているのに確保できなくなる(**断片化**)

「ポインタを進めるだけ」だった処理が、いきなり難問になります。しかもこの難問は、60年かけて多くの人が取り組んできたのに、**万能の答えがない**種類の問題です。

だから本書は、この問題を**第20章まで先送りします**。

### 先送りは逃げではない

18章ぶんも解放なしで過ごすと言うと、非現実的に聞こえるかもしれません。しかし、実際のゲーム開発では「解放しない設計」がきわめて有効に働く場面がたくさんあります。

たとえば、フレーム中に作られる一時データを考えてください。当たり判定の候補リスト、描画コマンド、パーティクルの中間計算。これらはすべて **そのフレームが終われば全部いらなくなります**。

だったら、1つずつ丁寧に解放する意味がありません。フレームの最後に「はい、全部おしまい」と `offset_` を 0 に戻せば、それで全解放です。**コスト、1命令。**

これが第8章でやることです。そして第43章で、これをフレーム単位の仕組みとして本格的に組み上げます。

> 解放しないのではなく、**まとめて捨てる**。
> この本の中心にあるアイデアです。

## 2.7 これは本当にアロケーターなのか

20行のクラスを「アロケーター」と呼んでいいのか、確認しておきましょう。

`new` や `malloc` と、役割を比べてみます。

| | `Bump::Allocate` | `malloc` / `operator new` |
|---|---|---|
| やること | 生メモリのアドレスを返す | 生メモリのアドレスを返す |
| 戻り値 | `void*` | `void*` |
| 型のことを知っているか | 知らない | 知らない |
| 生メモリはどこから来るか | 事前に確保した1本の板 | OSから随時 |
| 解放 | できない | できる |
| 空き領域の探索 | しない | する |
| スレッド安全 | ない | ある |

**上半分は同じです。** 役割としては、同じものです。下半分が違うだけで、これは「機能の欠落」です。

そして重要なのは、`new` も内部では最終的に「どこかのバイト列のこの位置を使ってください」と返しているにすぎない、ということです。第33章で Windows のヒープを覗くと、その実態が見えます。

**アロケーターは魔法の箱ではありません。** ポインタと数字を管理しているだけです。だからこそ、自分で書けます。

## 2.9 この章の完成コード

最終的な `Playground.cpp` の全体です。

```cpp
#include <cstddef>
#include <cstdint>
#include <vector>
#include <print>

// ---------------------------------------------------------
// Bump アロケーター v0.1
//   大きなバイト列を1本持ち、要求されたぶんだけ
//   ポインタを進めて返す。解放はできない。
// ---------------------------------------------------------
class Bump
{
public:
    explicit Bump(std::size_t capacity)
        : buffer_(capacity)
    {
    }

    void* Allocate(std::size_t size)
    {
        std::byte* result = buffer_.data() + offset_;
        offset_ += size;
        return result;
    }

private:
    std::vector<std::byte> buffer_;
    std::size_t            offset_ = 0;
};

int main()
{
    Bump bump(1024);

    int* a = static_cast<int*>(bump.Allocate(sizeof(int)));
    int* b = static_cast<int*>(bump.Allocate(sizeof(int)));
    int* c = static_cast<int*>(bump.Allocate(sizeof(int)));

    *a = 10;
    *b = 20;
    *c = 30;

    std::println("a = {}  ({})", *a, static_cast<void*>(a));
    std::println("b = {}  ({})", *b, static_cast<void*>(b));
    std::println("c = {}  ({})", *c, static_cast<void*>(c));
}
```

コメントと空行を除けば、`Bump` クラスは **17行** です。

> **コラム:20行のアロケーターは、実は現役である**
>
> この章で書いたものを「おもちゃ」だと思ったかもしれません。しかし、バンプアロケーターは今もあちこちで現役です。
>
> C++ の標準ライブラリにも入っています。C++17 で追加された `std::pmr::monotonic_buffer_resource` は、まさにこの方式です。名前の "monotonic"(単調)は、ポインタが一方向にしか進まないことを指しています。第39章で実際に使います。
>
> コンパイラにも使われています。多くのコンパイラは、構文解析中に大量の小さなノードを作りますが、それらは「コンパイルが終わるまで生き、終わったら全部いらなくなる」という寿命を持ちます。個別に解放する意味がないので、アリーナから取って最後にまとめて捨てます。
>
> ゲームエンジンでは言うまでもありません。フレームアロケーター、レベルアロケーター、ロード時のテンポラリバッファ。どれもこの20行の親戚です。
>
> **単純だから弱い、わけではありません。** 用途が合っていれば、単純さそのものが最大の武器になります。この本で複雑なアロケーターをいくつも作ったあとで、もう一度この章に戻ってくると、そのことがよく分かるはずです。
