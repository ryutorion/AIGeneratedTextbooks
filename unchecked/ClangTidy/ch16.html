第 16 章

bugprone-* ── バグの温床を突く

第4部に入ります。ここからは中身の話です。まず bugprone-* から始めるのには理由があります。導入コストに対する見返りが最も大きいモジュールだからです。好みの問題がほとんど絡まず、指摘されたら大抵は直したほうがよい。最初に有効にすべきものが何かと聞かれたら、答えはこれです。

16.1 このモジュールの性格

bugprone- という名前が示すとおり、「バグを生みやすい書き方」を集めたモジュールです。特徴は3つあります。

  • 規格違反ではない。 どれもコンパイルは通ります。だからコンパイラは黙ります（第1章）。
  • 好みの問題が少ない。 「auto を使うべきか」のような論争になりにくく、チームの合意を取りやすい。
  • 大半が AST の形だけで判定できる。 第2章の①方式なので速い。日常のビルドに入れても耐えます。

一方で、自動修正が付いているものは少数派です。「この書き方は危ない」と指摘はできても、何が正しいかは文脈次第だからです。指摘されたら人間が考える、という前提のモジュールです。

16.2 四つの系統で捉える

100件近いチェックがありますが、性質でまとめると見通しが立ちます。

16.3 題材コードに当ててみる

第1章のリスト1-1 に bugprone-* を当てると、複数の系統から指摘が出ます。

> clang-tidy --checks="-*,bugprone-*" config_loader.cpp -- -std=c++23
config_loader.cpp:31:9: warning: function 'strcpy' is marked as unsafe [bugprone-unsafe-functions]
config_loader.cpp:22:5: warning: the result of 'fread' is unused [bugprone-unused-return-value]
…
出る警告はバージョンと設定で変わる

本書に載せた出力はあくまで例です。第4章で確認したバージョンによって、チェックの追加・改名・検出精度の向上があります。自分の環境で実際に何が出るかを、必ず自分の目で確認してください。 以降の章でも同じです。

16.4 掘り下げ ── 三つの代表的なチェック

bugprone-use-after-move ── ムーブ後の使用

C++ で最も静かに壊れるバグの一つです。ムーブ後のオブジェクトは「有効だが未規定の状態」であり、読み取っても未定義動作ではありませんが、値の保証はありません。

void send(std::string payload);

void process(std::string msg) {
    send(std::move(msg));
    log("sent: " + msg);   // ← msg の中身は保証されない
}

bugprone-unsafe-functions ── 危険な C 関数

strcpy、strcat、sprintf、gets のように、境界チェックのない関数の使用を指摘します。題材コードの strcpy(e.name, line) がこれに当たります。

この章と第6部のつながり

「禁止したい関数のリスト」は、チームごとに違います。標準の bugprone-unsafe-functions は一般的に危険な関数を扱いますが、「うちのコードベースでは LegacyCopy() を使わない」といったルールは、標準チェックには入っていません。それを自分で書くのが第32章「実践1：禁止 API を検出する」です。この章で標準チェックの限界を体感しておいてください。

bugprone-easily-swappable-parameters ── 偽陽性の代表

同じ型の引数が連続していると「呼び出し側で取り違えうる」と警告します。

void drawRect(int x, int y, int w, int h);   // ← int が4つ並ぶ

指摘としては正しいのですが、実際のコードでは大量に出ます。既定の MinimumLength を上げるか、そもそも Checks から外すのが現実的です。「正しい指摘」と「有用な指摘」は別物という、静的解析の本質的な問題がよく表れているチェックです。

CheckOptions:
  bugprone-easily-swappable-parameters.MinimumLength: '4'

16.5 自動修正がないことの意味

第11章で扱った FixIt は、bugprone-* では少数派です。修正が付くのは、正しい形が一意に決まるものに限られます。

修正が付く例理由
bugprone-macro-parentheses括弧を足せばよいだけ
bugprone-swapped-arguments入れ替えればよい
bugprone-string-integer-assignment変換を明示すればよい
bugprone-terminating-continuecontinue を break にする
修正が付かない例理由
bugprone-use-after-move再代入すべきか、ムーブをやめるべきかは設計判断
bugprone-unsafe-functions代替関数の選択とバッファサイズの決定が必要
bugprone-narrowing-conversions型を変えるのか、明示キャストするのかは意図次第
bugprone-branch-clone片方が書き間違いなのか、意図的な重複なのか分からない

16.6 【ハンズオン】bugprone-* を評価する

HANDS-ON 16　自分のコードにとっての価値を測る
  1. 件数を把握する。 .clang-tidy を Checks: '-*,bugprone-*' だけにして、プロジェクト全体を回します（第15章）。 
    python "C:\Program Files\LLVM\bin\run-clang-tidy" -p out\build\ninja -j 4
  2. チェック名で集計する。 出力をファイルに落とし、どのチェックが何件出たかを数えます。 
    python "C:\Program Files\LLVM\bin\run-clang-tidy" -p out\build\ninja > tidy.log 2>&1
findstr /c:"[bugprone-" tidy.log | sort
    件数の多い上位3つを特定してください。導入の成否は、たいていこの上位3つの扱いで決まります。
  3. 危険度で分類する。 上位のチェックそれぞれについて、公式ドキュメントで内容を確認し、次のどれかに分類します。
    • A：直すべき ── 実際にバグ、または将来バグになる
    • B：オプションで調整 ── 指摘は正しいが、しきい値が自分たちに合わない
    • C：外す ── 自分たちのコードでは価値が薄い
  4. 四系統で試す。 系統ごとに絞って回し、どの角度からの指摘が多いかを見ます。 
    --checks="-*,bugprone-use-after-move,bugprone-dangling-handle,bugprone-undefined-memory-manipulation"
--checks="-*,bugprone-narrowing-conversions,bugprone-integer-division,bugprone-too-small-loop-variable"
--checks="-*,bugprone-branch-clone,bugprone-suspicious-semicolon,bugprone-assignment-in-if-condition"
--checks="-*,bugprone-unsafe-functions,bugprone-unused-return-value,bugprone-string-constructor"
  5. 偽陽性を体験する。 bugprone-easily-swappable-parameters だけを有効にして回し、件数を見ます。次に MinimumLength を 3 → 4 → 5 と上げ、件数の変化を記録します。
  6. note を読む。 use-after-move の警告が出た箇所があれば、警告本体だけでなく続く note: の行も読みます。「どこでムーブされたか」が示されているはずです。note を読む習慣は、第17章のフロー解析で決定的に重要になります。
  7. 採用セットを決める。 手順3の分類に基づき、.clang-tidy を次の形に整えます。 
    Checks: >
  -*,
  bugprone-*,
  -bugprone-easily-swappable-parameters

CheckOptions:
  bugprone-narrowing-conversions.WarnOnIntegerNarrowingConversion: 'true'
    除外したものについて、なぜ外したかを設定ファイルにコメントで書いてください。 第22章でこの記録が効いてきます。
「全部直す」から始めない

既存コードで数百件出たとき、全部直そうとすると挫折します。第15章の差分解析を使い、「新しく書く行では bugprone-* を守る」 から始めてください。既存分は、そのファイルを触るときに直す。この進め方は第39章で詳しく扱います。

この章のまとめ

  • bugprone-* は導入コストに対する見返りが最大。好みの問題が少なく、合意を取りやすい。
  • 四系統で捉える。①メモリ・所有権、②数値・型変換、③制御フロー・条件、④API の誤用。
  • 大半は AST の形で判定できるので速い。日常のビルドに入れられる。
  • 自動修正が付くのは「正しい形が一意に決まる」ものだけ。 大半は人間が判断する前提。
  • use-after-move は変数の状態を追う。再代入で状態は戻る。note に「どこでムーブされたか」が出るので必ず読む。
  • easily-swappable-parameters は「正しいが有用でない」指摘の代表。オプションで調整するか外す。
  • チーム固有の禁止 API は標準チェックには入っていない。それが第6部の主題になる。

次章： 第17章「clang-analyzer-* ── パス感度のある解析」では、AST の形ではなく実行経路をたどる解析に入ります。強力ですが遅く、偽陽性の性質も違います。
