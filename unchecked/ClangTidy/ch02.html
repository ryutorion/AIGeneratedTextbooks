第 2 章

Clang-Tidy とその仲間たち

Clang-Tidy は「文字列をパターンマッチする lint」ではありません。実際に C++ をコンパイルするのと同じ手順でソースを解析し、構文木を組み立て、その木に対して問い合わせを行います。この仕組みを理解しておくと、後半で自分でルールを書くときに迷いません。あわせて clang-query、run-clang-tidy、clang-apply-replacements といった周辺ツールの役割分担も押さえます。

2.1 Clang-Tidy は「コンパイラの目」を借りている

古典的な lint ツールの多くは、ソースコードをテキストとして正規表現で検査していました。手軽ですが限界があります。たとえば「strcpy の呼び出しを検出したい」とき、テキスト検索では次を区別できません。

strcpy(dst, src);          // 検出したい
// strcpy(dst, src);       // コメント。検出したくない
const char* s = "strcpy";  // 文字列リテラル。検出したくない
MyClass::strcpy(a, b);     // 自作の別物。検出したくない
#define strcpy my_strcpy   // マクロで置換済み。さて？

Clang-Tidy はこの問題を、根本から回避します。テキストではなく Clang が構築した抽象構文木（AST: Abstract Syntax Tree） を見るからです。AST の段階ではコメントも文字列リテラルもマクロも解決済みで、「これは ::strcpy という関数への呼び出し式である」という意味レベルの情報が付いています。

つまり Clang-Tidy を動かすにはコンパイルが必要

AST を作るということは、実際にプリプロセスとパースを通すということです。したがって Clang-Tidy には コンパイルオプション（インクルードパス、マクロ定義、言語規格）を正しく渡さなければなりません。「なぜかヘッダが見つからないと言われる」という初学者の詰まりどころは、ほぼ全部ここに由来します。第12章で正面から扱います。

2.2 内部で起きていること

Clang-Tidy が1つのソースファイルを処理する流れを図にすると、次のようになります。

図の①〜③がチェックの実装方式です。それぞれ性格が違います。

方式見ているもの速度得意なこと
① AST Matcher構文木の形速い「この形のコードを禁止」「この書き方に置き換え」。自作ルールの主戦場
② フロー解析実行経路と値の状態遅い「この経路を通ると NULL 参照になる」といった経路依存の欠陥
③ プリプロセッサマクロ・インクルード速いAST に残らないもの（マクロ名、include の順序）

第1章のリスト1-1 に当てはめると、new[] と delete の不一致は①（形を見れば分かる）、fopen の戻り値未チェックによる NULL 参照は②（経路をたどらないと分からない）です。

ここが本書の要

第6部で扱う Query Based Custom Check は ① の仕組みをそのまま設定ファイルから使えるようにしたもの です。つまり、C++ を一行も書かずに「AST の形を指定して警告を出す」ができる。逆にいえば、②のフロー解析が必要なルールはクエリでは書けません。この線引きが第42章の主題になります。

2.3 チェックの名前はモジュール名で始まる

Clang-Tidy のチェックは モジュール名-チェック名 という命名になっています。

bugprone-use-after-move
modernize-use-nullptr
performance-unnecessary-value-param
readability-identifier-naming
clang-analyzer-core.NullDereference

モジュールは出自や目的でまとまっています。主なものだけ挙げます。

モジュール性格
bugprone-バグになりやすい書き方。最初に有効化する価値が高い
clang-analyzer-Clang Static Analyzer によるフロー解析
modernize-古い書き方をモダンな C++ に置き換える
performance-不要なコピー・変換など性能上の無駄
readability-可読性・命名規則
cppcoreguidelines- / cert- / hicpp-各種コーディング標準の機械化
misc- / portability- / concurrency-その他、移植性、並行性
custom-Query Based Custom Check で定義した自作チェックが入るモジュール

最後の custom- に注目してください。設定ファイルに Name: no-strcpy と書いたチェックは、有効化するときには custom-no-strcpy という名前になります。標準チェックと名前が衝突しないよう、専用のモジュールに隔離される仕組みです。第30章で実際に書きます。

2.4 周辺ツールの役割分担

Clang-Tidy は単体で完結せず、いくつかのツールと組で使われます。それぞれ「いつ使うか」がはっきり分かれています。

clang-query ── 対話的に AST を探る

Clang-Tidy のカスタムチェックを書くうえで、最も時間を使うのがこのツールです。ソースを読み込ませて match functionDecl(hasName("load")) のような問い合わせを打ち、何がマッチするかを即座に確認できます。いきなり .clang-tidy にクエリを書くのは悪手 で、まずここで確定させてから設定ファイルに移すのが定石です（第36章）。

run-clang-tidy ── 一括実行

clang-tidy 本体は原則1ファイルずつです。プロジェクト全体を回すには、コンパイルデータベース（compile_commands.json）を渡して run-clang-tidy で並列実行します。CI で使う主力はこちらです。

clang-apply-replacements ── 修正の一括適用

並列実行では、複数の翻訳単位が同じヘッダを修正しようとして衝突します。そこで各プロセスは修正案を YAML に書き出すだけにしておき、後からこのツールで重複排除しつつ適用します。

2.5 MSVC のコード分析との関係

Visual Studio にはもともと Microsoft 製のコード分析（/analyze、C++ Core Check）が載っています。Clang-Tidy はこれを置き換えるものではなく、並べて使えます。

Microsoft コード分析Clang-Tidy
パーサMSVC 本体Clang
強みSAL 注釈の活用、Windows API の知識、MSVC 拡張の完全な理解チェックの豊富さ、自動修正、ルールの自作
設定ルールセット（.ruleset）.clang-tidy（テキスト、リポジトリで共有しやすい）
注意点—MSVC 固有の拡張構文でパースエラーになることがある
Clang でパースできないコードは解析できない

Clang-Tidy は Clang でソースを読みます。MSVC 固有の拡張（一部の __declspec、古い COM ヘッダの書き方など）を含むコードでは、パースエラーが出て解析が途中で止まることがあります。この場合、解析対象から除外するか、--extra-args で MSVC 互換モードの指定を調整します（第12章）。「警告が0件だ、素晴らしい」と思ったら実はパースに失敗していた、というのはよくある落とし穴です。

2.6 【ハンズオン】検出方式を見分ける

この章のハンズオンは机上作業です。まだツールは動かしません。しかしこの分類ができるかどうかが、第6部でカスタムチェックを書けるかどうかを決めます。

HANDS-ON 2　問題を検出方式に振り分ける
  1. 第1章のリスト1-1 をもう一度開きます。
  2. 次の各問題について、図2-1 の ①AST Matcher / ②フロー解析 / ③プリプロセッサ のどれで検出できるかを考え、理由を一行で書きます。
    • (a) delete buffer_; が new char[4096] に対応していない
    • (b) fopen の戻り値が NULL のまま fread に渡される
    • (c) strcpy を呼んでいる
    • (d) entries() が値返しでコピーを起こす
    • (e) ConfigLoader(const char*) に explicit が付いていない
  3. 「①で検出できる」と判断したものについて、どんな「形」を探せばよいか を日本語で言語化してみます。たとえば (c) なら「strcpy という名前の関数への呼び出し式」。この日本語が、後に Matcher の式になります。
解答の目安

(a) ①：new[] 式で初期化されたポインタに対する delete 式、という形の問題。(b) ②：fopen が NULL を返す経路をたどる必要がある。(c) ①：呼び出し式の形だけで判定できる。ここが自作ルールで最も作りやすいパターン。(d) ①：戻り値型がコンテナで、値返ししているメンバ関数、という形。(e) ①：引数1個の非 explicit コンストラクタ、という形。
つまり5つのうち4つが AST Matcher で扱えます。これが「クエリだけで実用的なルールが書ける」根拠です。

この章のまとめ

  • Clang-Tidy はテキストではなく Clang が構築した AST を見る。だから正しいコンパイルオプションが必要になる。
  • チェックの実装は3方式ある。①AST Matcher（大多数）、②フロー解析（clang-analyzer-*）、③プリプロセッサ。
  • Query Based Custom Check は①の仕組みを設定ファイルから使う機能。②が必要なルールはクエリでは書けない。
  • チェック名は モジュール名-チェック名。自作チェックは custom- モジュールに入る。
  • ルールは clang-query で試作 → .clang-tidy に確定 → clang-tidy / run-clang-tidy で実行、という流れで作る。
  • Microsoft コード分析とは併用可能。ただし Clang がパースできないコードは解析できない点に注意。
