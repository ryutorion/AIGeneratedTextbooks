第 13 章

MSBuild プロジェクトでの解析

前章でコマンドラインの仕組みが分かりました。この章では、Visual Studio がその引数をどう組み立てているのかを実際に覗きます。解析が走るタイミングは2種類あり、それぞれ用途と代償が違います。「ビルドが遅くなった」への対処も、ここで型を作っておきます。

13.1 二つの実行タイミング

おすすめの構成

Debug 構成ではバックグラウンド解析のみ、Release 構成（あるいは専用の Analysis 構成）でビルド時解析を有効にする、という分け方が扱いやすいです。日常の編集は速いまま、コミット前に一度だけ重い構成でビルドすれば、CI で落ちる前に気づけます。構成ごとの設定管理は 13.4 節で扱います。

13.2 Visual Studio は何を渡しているのか

MSBuild 統合は、プロジェクトの設定を第12章のコマンドライン引数に変換して clang-tidy.exe を起動しています。対応関係は次のとおりです。

実際のコマンドラインを見る

推測ではなく事実を確認します。ビルド出力の詳細度を上げると、Visual Studio が組み立てたコマンドラインが出力ウィンドウに現れます。

ツール > オプション > プロジェクトおよびソリューション > ビルド/実行
  > MSBuild プロジェクト ビルド出力の詳細度 : 「詳細」または「診断」

この状態でビルドし、出力ウィンドウ（「ビルド」）で clang-tidy を検索してください。解析が動いていない・引数が意図と違う、という問題の9割はここで判明します。

.vcxproj を直接読むのも早い

プロパティで設定した値は .vcxproj に XML 要素として保存されます。テキストエディタで開けば、どの構成にどの値が入っているかが一目で分かります。「Debug には入っているが Release には入っていない」といった設定漏れを見つけるには、GUI を構成ごとに切り替えるより速い方法です。

13.3 速度の話

Clang-Tidy はソースをもう一度コンパイルします。ビルド時間が増えるのは避けられません。増え方はチェックの選び方に強く依存します。

チェックコスト理由
clang-analyzer-*高い実行経路を網羅的にたどる（第2章の②方式）
bugprone-* / modernize-* など低いAST の形を照合するだけ（①方式）
ヘッダを広く対象にする設定中〜高翻訳単位ごとにヘッダを再解析（第10章）

並列度を上げる

「プロセスの最大数」で並列実行できます。0 を指定すると論理プロセッサ数すべてを使います。

並列化はメモリを食う

各プロセスが独立して AST を構築します。テンプレートを多用したコードでは1プロセスあたりのメモリが大きく、並列度を上げすぎるとスワップしてかえって遅くなることがあります。まず論理プロセッサ数の半分程度から試し、タスクマネージャでメモリを見ながら調整してください。

それでも遅いときの手順

  1. チェックを絞る。 日常のビルドでは clang-analyzer-* を外し、AST ベースのチェックだけにする。重い解析は CI に寄せる（第40章）。
  2. ヘッダの対象を狭める。 ExcludeHeaderFilterRegex で外部ヘッダを外す（第10章）。
  3. 構成で分ける。 Debug は軽く、専用構成でだけ全部走らせる。
  4. そもそもビルド時解析を切る。 バックグラウンド解析だけにして、全体解析は run-clang-tidy でまとめて回す（第15章）。

13.4 構成の組み合わせ爆発に備える

ここまでの章で何度も「すべての構成に設定してください」と書きました。実際、構成とプラットフォームの組み合わせは簡単に増えます。

プロパティシートは「プロパティ マネージャー」ウィンドウから追加します（表示 > その他のウィンドウ > プロパティ マネージャー）。.props ファイルを作り、すべての構成に対して追加すれば、そこに書いた設定が全構成に効きます。

設定の置き場所の整理

ここまでで設定の置き場所が3つになりました。役割を分けておくと混乱しません。

  • .clang-tidy：チェックの選択、オプション、フィルタ、カスタムチェック。解析の中身。リポジトリで共有し、CI でもそのまま使う。
  • .props：Clang-Tidy を有効にするか、どの実行ファイルを使うか、並列度。Visual Studio での動かし方。
  • プロパティページ直書き：一時的な実験のみ。恒久的な設定は置かない。

13.5 【ハンズオン】計測して制御する

HANDS-ON 13　解析のコストを測り、設定を一元化する
  1. 基準を測る。 Clang-Tidy を無効にした状態でソリューションをリビルドし、出力ウィンドウ末尾の経過時間を記録します。
  2. ビルド時解析を有効にする。 構成プロパティ > コード分析 > 全般 で「ビルドに対するコード分析を有効にする」を「はい」にします。.clang-tidy の Checks は第2部で作った内容（bugprone-*、clang-analyzer-*、performance-* など）のままにします。
  3. コストを測る。 リビルドし、経過時間を記録します。手順1と比べて何倍になったかを確認します。
  4. 重いチェックを外して測る。 .clang-tidy から clang-analyzer-* だけを外してリビルドし、時間を記録します。フロー解析がコストの大半を占めていることを、自分の数字で確認してください。
  5. 並列度を変えて測る。 clang-analyzer-* を戻し、「プロセスの最大数」を 0（全論理プロセッサ）にしてリビルドします。時間とメモリ使用量を見て、適切な値を決めます。
  6. 実際のコマンドラインを見る。 ビルド出力の詳細度を「詳細」にしてリビルドし、出力ウィンドウで clang-tidy を検索します。--checks、--extra-args、-I、-D がどう渡っているかを読みます。
  7. プロパティシートに移す。
    • プロパティ マネージャーを開き、TidyLab プロジェクトの構成の一つを右クリックして「新しいプロジェクト プロパティ シートの追加」を選び、TidyLab.Analysis.props を作ります。
    • 作ったシートのプロパティで、Clang-Tidy の有効化・ツールディレクトリ・事前追加オプション（-std=c++23）・プロセスの最大数を設定します。
    • 他のすべての構成に、同じシートを「既存のプロパティ シートの追加」で追加します。
    • プロジェクト側に直接書いていた値を削除し、シートの設定だけで動くことを確認します。
  8. 構成を切り替えて確認する。 Debug / Release、x64 / x86 を切り替えてビルドし、どの構成でも同じ警告が出ることを確認します。これが一元化の成果です。

この章のまとめ

  • 解析のタイミングは2つ。バックグラウンド解析（既定・速い・ログに残らない）と、ビルド時解析（遅い・ログに残る・CI に近い）。
  • MSBuild 統合はプロジェクト設定を --checks や -I / -D に変換して clang-tidy.exe を起動している。
  • ビルド出力の詳細度を上げれば、実際のコマンドラインが出力ウィンドウで確認できる。トラブルの9割はここで判明する。
  • コストの大半は clang-analyzer-*。日常ビルドから外し、CI に寄せるのが定石。
  • 並列化はメモリを消費する。上げすぎると逆効果。
  • 構成の組み合わせ爆発にはプロパティシートで対処する。設定の置き場所は「解析の中身は .clang-tidy、動かし方は .props」と分ける。
