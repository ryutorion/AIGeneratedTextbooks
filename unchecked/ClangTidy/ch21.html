第 21 章

cppcoreguidelines-* / cert-* / misc-*

既存のコーディング標準を機械化したモジュール群です。「C++ Core Guidelines に準拠したい」という動機で全部有効にすると、たいてい失敗します。前提となるライブラリを要求するチェックが混ざっていること、そして別モジュールに同じ実体のチェックが別名で入っていることが原因です。この二つを見抜けるようにします。

21.1 ガイドライン系の性格

これらのモジュールは、外部の規範文書に対応しています。

モジュール由来性格
cppcoreguidelines-C++ Core Guidelines現代 C++ の設計指針。範囲が広く、思想も強い
cert-CERT セキュアコーディング標準大半が他モジュールへのエイリアス
hicpp-High Integrity C++同上。エイリアスが多い
misc-どこにも属さないもの寄せ集めだが、実用的なものが混ざっている

「規範に準拠する」という目的は立派ですが、規範は自分たちの環境を知りません。 ガイドラインが前提としている書き方（GSL ライブラリの使用など）を採用していないなら、対応するチェックは意味を成しません。

21.2 cert-* の正体はエイリアス

cert- モジュールを開くと、実体を持つチェックはごくわずかで、大半が他モジュールへの別名だと分かります。

cert- の名前実体
cert-arr39-cbugprone-sizeof-expression
cert-dcl03-cmisc-static-assert
cert-dcl16-creadability-uppercase-literal-suffix
cert-dcl37-c / cert-dcl51-cppbugprone-reserved-identifier
cert-dcl54-cppmisc-new-delete-overloads
cert-dcl58-cppbugprone-std-namespace-modification
cert-dcl59-cppmisc-anonymous-namespace-in-header
cert-env33-cbugprone-command-processor
cert-con36-c / cert-con54-cppbugprone-spuriously-wake-up-functions
実体を持つもの（少数）： cert-err33-c, cert-err60-cpp, cert-flp30-c, cert-msc50-cpp, cert-oop58-cpp
エイリアスの見分け方

公式のチェック一覧では、エイリアスは実体へのリンクとして表示されます。実務上は次の手順が早い。

  1. 同じ箇所に複数の警告が出ていたら、角括弧の中のチェック名をすべて控える。
  2. それぞれのドキュメントページを開く。エイリアスなら実体のページに転送される。
  3. 実体側だけを Checks に残し、エイリアス側を - で外す。

本書の推奨は 「cert-* や hicpp-* をモジュールごと有効にしない」です。必要な規範は、実体側のチェック名で直接指定してください。

21.3 cppcoreguidelines-* の取捨

そのまま入れられるもの

チェック内容
cppcoreguidelines-init-variables初期化されていない変数を検出（自動修正あり）
cppcoreguidelines-prefer-member-initializerコンストラクタ本体での代入 → メンバ初期化子リスト
cppcoreguidelines-pro-type-member-init初期化されないメンバを検出
cppcoreguidelines-special-member-functions五の法則。一部だけ定義している型を検出
cppcoreguidelines-virtual-class-destructor多相基底クラスのデストラクタが仮想でない
cppcoreguidelines-slicingオブジェクトスライシング
cppcoreguidelines-pro-type-cstyle-castC 形式キャスト → C++ キャスト
cppcoreguidelines-macro-usage定数・関数の代わりにマクロを使っている
cppcoreguidelines-rvalue-reference-param-not-movedT&& で受けたのにムーブしていない
cppcoreguidelines-missing-std-forward転送参照を std::forward していない
cppcoreguidelines-use-enum-classスコープなし列挙型 → enum class

題材コードの ConfigLoader は、この上から3つに引っかかります。path_ = path; をコンストラクタ本体で代入している点（prefer-member-initializer）、デストラクタだけ定義してコピーコンストラクタを定義していない点（special-member-functions）です。後者は実際に危険です。 ConfigLoader をコピーすると buffer_ が二重解放されます。

前提ライブラリを要求するもの

ほかに cppcoreguidelines-pro-type-vararg（可変長引数の禁止）も、C 系 API を多用する Windows プログラミングでは大量に出ます。「守れない規範は入れない」が原則です。

21.4 misc-* の掘り出し物

寄せ集めのモジュールですが、実用性の高いものが混ざっています。

チェック内容
misc-const-correctness変更されないローカル変数に const を付ける（自動修正あり）
misc-include-cleaner使っていない #include の削除と、使っているのに直接 include していないヘッダの追加
misc-use-internal-linkage他の翻訳単位から使われない関数・変数を static に
misc-use-anonymous-namespacestatic より無名名前空間を使う
misc-definitions-in-headersヘッダに非 inline の定義がある（ODR 違反の温床）
misc-header-include-cycleヘッダの循環参照
misc-unused-parameters使われていない引数
misc-unused-using-decls使われていない using 宣言
misc-no-recursion再帰呼び出し（組込みなどスタック制約が厳しい環境向け）
misc-non-private-member-variables-in-classespublic なメンバ変数
misc-throw-by-value-catch-by-reference例外は値で投げて参照で受ける
misc-unconventional-assign-operator代入演算子のシグネチャが慣例から外れている

misc-include-cleaner を掘り下げる

ビルド時間に直接効く数少ないチェックです。「このファイルが実際に使っているシンボルは何か」を AST から調べ、それに対応するヘッダだけを include すべきだと指摘します。

推移的インクルードに依存したコードでは荒れる

「a.h が b.h を include しているから、b.h の中身も使える」という書き方をしていると、大量の「include を追加せよ」が出ます。指摘自体は正しく、直せばビルドは頑健になりますが、件数が多いので段階導入が前提です。第39章の進め方に従ってください。

21.5 モジュールをまとめて有効にしない

この章の結論はこれに尽きます。cppcoreguidelines-*、cert-*、hicpp-* は、ワイルドカードで有効にしないでください。 理由が3つ揃っています。

  1. エイリアスが重複して同じ箇所に複数の警告が出る（図21-1）
  2. 前提ライブラリを要求するチェックが混ざっている（図21-2）
  3. バージョンが上がると勝手に新しいチェックが増える（第6章）

個別のチェック名で列挙するのが正解です。第6章のパターンC の使いどころが、まさにここです。

21.6 【ハンズオン】重複を見つけて整理する

HANDS-ON 21　エイリアスと前提を切り分ける
  1. あえて失敗させる。 .clang-tidy の Checks を一時的に次にして、題材コードを解析します。 
    Checks: '-*,cppcoreguidelines-*,cert-*,hicpp-*'
    件数を記録してください。おそらく想定よりずっと多いはずです。
  2. 二重警告を確認する。 同じ行番号に複数の警告が出ている箇所を探します。 
    clang-tidy config_loader.cpp -- -std=c++23 > guideline.log 2>&1
findstr /c:"warning:" guideline.log | sort
    同じファイル・同じ行が並んでいる箇所のチェック名を控えます。
  3. 実体を特定する。 控えたチェック名を公式ドキュメントで引き、エイリアスがどれかを確認します。実体側だけを残す形に Checks を書き換えます。
  4. 前提が要るチェックを外す。 owning-memory と pro-bounds-* だけを有効にして件数を見ます。 
    --checks="-*,cppcoreguidelines-owning-memory,cppcoreguidelines-pro-bounds-*"
    GSL を採用していないなら、これらは外す判断になります。件数を見てから判断してください。
  5. 価値の高いものを個別に入れる。 21.3 節の「そのまま入れられるもの」の表から、個別に指定します。 
    Checks: >
  -*,
  cppcoreguidelines-init-variables,
  cppcoreguidelines-prefer-member-initializer,
  cppcoreguidelines-pro-type-member-init,
  cppcoreguidelines-special-member-functions,
  cppcoreguidelines-virtual-class-destructor,
  cppcoreguidelines-slicing,
  cppcoreguidelines-pro-type-cstyle-cast
  6. 実際の危険を確認する。 special-member-functions の警告が ConfigLoader に出ることを確認し、なぜ危険かを説明できるか自分で確かめてください。次のコードを書いて実行すると、二重解放が起きます。 
    ConfigLoader a("app.ini");
a.load();
ConfigLoader b = a;   // 暗黙のコピー。buffer_ が共有される
    確認したら、コピーを禁止するか正しくコピーするかを決めて修正します。
  7. misc- の掘り出し物を試す。 
    --checks="-*,misc-const-correctness,misc-use-internal-linkage,misc-definitions-in-headers"
    const-correctness は自動修正付きなので、第11章の手順で当ててみてください。
  8. include-cleaner の件数を見る。 
    --checks="-*,misc-include-cleaner"
    件数が多ければ、いまは採用せず「第39章で段階導入する候補」として記録に残します。

この章のまとめ

  • ガイドライン系モジュールは外部の規範に対応する。規範は自分たちの環境を知らない。
  • cert-* の大半は他モジュールへのエイリアス。hicpp-* も同様。
  • エイリアスを重ねて有効にすると、同じ箇所に複数の警告が出て、オプションも名前ごとに個別設定が必要になる。
  • cppcoreguidelines-owning-memory と pro-bounds-* は GSL の使用が前提。採用していなければ既存コードのほぼ全行が違反になる。
  • そのまま入れられるものは多い。init-variables, prefer-member-initializer, special-member-functions, virtual-class-destructor, slicing など。
  • misc- には掘り出し物がある。const-correctness, include-cleaner, use-internal-linkage, definitions-in-headers。
  • これらのモジュールはワイルドカードで有効にせず、チェック名で個別に列挙する。
