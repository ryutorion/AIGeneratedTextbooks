第 29 章

Query Based Custom Check とは何か

本書の主題に到達しました。第4部で標準チェックを使い尽くし、第5部でクエリを書けるようになった。あとは、そのクエリを Clang-Tidy のチェックとして登録するだけです。C++ のコードは一行も書きません。.clang-tidy に数行足すだけで、あなたのチームにしか存在しないルールが警告として出るようになります。

29.1 標準チェックには存在しないもの

第4部を振り返ってください。数百のチェックを見てきましたが、次のようなルールは一つもありませんでした。

右側のルールは、いまはコードレビューで人間が指摘しているはずです。しかし人間のレビューは、疲れるし、見落とすし、新しいメンバーは規約を知りません。機械にやらせるべき仕事です。

29.2 拡張の二つの道

Clang-Tidy に独自チェックを追加する方法は2つあります。

「できることが少ない」は欠点ではない

第2章の図2-1 を思い出してください。Clang-Tidy のチェックには3方式あり、そのうち ①AST Matcher 方式が大多数を占めていました。第2章のハンズオンでも、5つの問題のうち4つが AST の形だけで検出できました。実務のルールの大半は、形の照合で足ります。 足りない場合の話は第42章で扱います。

29.3 仕組み

公式ドキュメントはこう説明しています。「カスタムチェックは clang-query の構文に基づく。すべてのカスタムチェックは、名前の衝突を避けるため custom モジュールに登録される」。

29.4 実験的機能であることの意味

公式ドキュメントの明記事項

「この機能は現在実験段階であるため、--experimental-custom-checks によって明示的に有効化する必要がある」
「設定の構造は将来変更される可能性がある（ただし将来の変更は前方互換性を目指している）」
「機能は完全に AST マッチャーライブラリに依存しているため、クエリの記述は AST マッチャーの更新に伴って変わりうる」

これを実務の言葉に翻訳すると、次の3つになります。

ドキュメントの記述実務上の対処
明示的な有効化が必要フラグを渡す経路を確保する（29.5 節）。渡せない環境では動かない
設定の構造が変わりうるLLVM 更新時にカスタムチェックが動くことを確認する手順を持つ（第22章の図22-3 に追加）
クエリの記述が変わりうる回帰テスト用のソースを用意しておく（第37章）。「昨日まで動いていた」を検出できるようにする

第4章で「バージョンを確認する習慣」を作ったのは、このためです。

29.5 有効化の経路 ── Visual Studio での制約

コマンドラインからは単純です。

> clang-tidy --experimental-custom-checks config_loader.cpp -- -std=c++23

問題は Visual Studio です。第13章の図13-2 を思い出してください。プロパティページから渡せるのは次の3種類でした。

プロパティ渡り先--experimental-custom-checks を渡せるか
Clang-Tidy チェック--checks の値×（チェック名を書く欄）
Clang-Tidy 追加オプション--extra-args → コンパイラへ×（clang-tidy 自身への引数ではない）
Clang-Tidy 事前追加オプション--extra-args-before → コンパイラへ×（同上）
プロパティページから直接は渡せない

Visual Studio の統合には、clang-tidy 本体に任意の引数を渡すための項目がありません。 したがって、IDE のバックグラウンド解析でカスタムチェックを動かすには工夫が要ります。この制約は本書執筆時点のものです。将来のバージョンで対応が入る可能性はあるので、--help やプロパティページを確認してみてください。

現実的な三つの経路

29.6 【ハンズオン】有効化を確認する

HANDS-ON 29　自分の環境で機能が使えるかを確定させる
  1. フラグの存在を再確認する。 第4章でやった確認を、もう一度行います。 
    clang-tidy --help | findstr experimental-custom-checks
    • 出力あり → 次へ進みます。
    • 出力なし → 第4章 4.4 節に戻り、LLVM 22 以降を導入してください。ここが通らないと第6部は先に進めません。
  2. 設定キーが認識されるか確かめる。 .clang-tidy に空のカスタムチェック定義を書きます。 
    CustomChecks: []
    そのうえで、 
    clang-tidy --experimental-custom-checks --dump-config config_loader.cpp -- -std=c++23
    を実行し、出力に CustomChecks が含まれるかを確認します。
  3. フラグなしとの違いを見る。 同じコマンドから --experimental-custom-checks を外して実行し、出力を比較します。この差が「実験的機能が有効かどうか」の目印になります。
  4. Visual Studio の制約を確認する。 プロパティページ（コード分析 > Clang-Tidy）を開き、clang-tidy 本体に任意の引数を渡す項目がないことを自分の目で確認してください。もし本書執筆時点になかった項目が増えていれば、それが使えます。
  5. 作業手順を決める。 図29-4 の3経路から選びます。本書は経路1（コマンドライン）で進めますが、最終的にどうするかを決めておいてください。第38章で配布方法を扱うとき、この選択が効いてきます。
  6. クエリを準備する。 第28章のハンズオンで作った3つのクエリファイルを開き、内容を確認します。次章で、この最初の1つを .clang-tidy に移します。
  7. 回帰テスト用のファイルを用意する。 第28章の ch28_rules.cpp を tests\custom-checks\rules.cpp にコピーします。29.4 節で述べたとおり、クエリの記述は将来変わりえます。 「以前は検出できていたものが検出されなくなった」を発見するための土台を、いま作っておきます。

この章のまとめ

  • 標準チェックは「誰が書いても問題になること」を扱う。「あなたのチームにしか存在しないルール」は自分で書くしかない。
  • 拡張には C++ 実装とクエリベースの2つがある。クエリベースはできることが狭い代わりに、ビルドも配布も不要。
  • クエリは起動時に解析され、Matcher が動的に生成される。登録後は標準チェックと区別がない（-checks、NOLINT、WarningsAsErrors がそのまま効く）。
  • チェックは custom モジュールに登録される。Name: no-strcpy → custom-no-strcpy。
  • 実験的機能であり、--experimental-custom-checks による明示的な有効化が必要。設定構造もクエリの記述も将来変わりうる。
  • Visual Studio のプロパティページからこのフラグは渡せない。 コマンドライン／ラッパー／役割分担の3経路から選ぶ。
  • 将来の変更に備え、回帰テスト用のソースを最初に用意する。
