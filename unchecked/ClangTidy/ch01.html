第 1 章

静的解析でしか見つからないバグがある

コンパイルは通る。テストも通る。それでも壊れているコードがある。この章では本書を通して使う題材コードを用意し、コンパイラ・テスト・静的解析という三つの目がそれぞれ何を見ているのかを整理します。Clang-Tidy をまだ動かしません。「なぜ必要なのか」を先に腹落ちさせるための章です。

1.1 「動くコード」に潜むもの

次のコードは、テキスト形式の設定ファイルを読み込む小さなクラスです。C++ の実務経験がある方なら、5秒眺めればどこかムズムズするはずです。ただし、これは コンパイルが通り、手元のテストも通ってしまう コードです。

// config_loader.h
#pragma once
#include <string>
#include <vector>

struct Entry {
    char name[32];
    int  value;
};

class ConfigLoader {
public:
    ConfigLoader(const char* path);
    ~ConfigLoader();

    bool load();
    std::vector<Entry> entries();

private:
    std::string        path_;
    char*              buffer_ = nullptr;
    std::vector<Entry> entries_;
};
// config_loader.cpp
#include "config_loader.h"
#include <cstdio>
#include <cstring>
#include <cstdlib>

ConfigLoader::ConfigLoader(const char* path) {
    path_ = path;
}

ConfigLoader::~ConfigLoader() {
    delete buffer_;
}

bool ConfigLoader::load() {
    FILE* fp = fopen(path_.c_str(), "r");

    buffer_ = new char[4096];
    size_t n = fread(buffer_, 1, 4095, fp);
    buffer_[n] = '\0';

    char* line = strtok(buffer_, "\n");
    while (line != NULL) {
        char* eq = strchr(line, '=');
        if (eq) {
            *eq = '\0';
            Entry e;
            strcpy(e.name, line);
            e.value = atoi(eq + 1);
            entries_.push_back(e);
        }
        line = strtok(NULL, "\n");
    }
    return true;
}

std::vector<Entry> ConfigLoader::entries() {
    return entries_;
}

リスト1-1　本書を通じて改善していく題材コード（ConfigLoader）

このコードには、少なくとも次の問題が含まれています。

箇所問題症状の出方
fopen の戻り値NULL チェックがないファイルが無い環境でのみクラッシュ
new char[4096] / delete buffer_new[] に delete を対応させている（未定義動作）多くの環境では「動いてしまう」。ヒープが荒れる
strcpy(e.name, line)32 バイトを超えるキー名でバッファオーバーラン長い設定キーを書いた顧客だけで発生
load() の二重呼び出しbuffer_ がリークする症状として現れない。じわじわ増える
entries()呼ぶたびに vector をまるごとコピーバグではないが、ループ内で呼ぶと致命的に遅い
コンストラクタメンバ初期化子リストを使っていない／explicit がない意図しない暗黙変換が通る

重要なのは、これらがどれも「そのコードを読んだ人間なら指摘できる」種類の問題 だという点です。天才的な洞察は要りません。ルールを知っていて、機械的に照合すればよい。だからこそ機械にやらせる価値があります。

1.2 三つの目 ── コンパイラ・テスト・静的解析

ソフトウェアの欠陥を捕まえる手段は一つではありません。それぞれ「見ている対象」が違います。

リスト1-1 を MSVC の /W4 でビルドすると、いくつかの警告は出ます。fopen、strcpy、strtok は Microsoft の安全版（fopen_s など）を推奨する非推奨警告 C4996 の対象なので、そこは引っかかります。

しかし、次の問題はコンパイラからは何も言われません。

  • fopen の戻り値を確かめずに fread に渡している
  • new[] で確保したものを delete で解放している
  • load() を2回呼ぶと前の buffer_ が漏れる
  • entries() が毎回コピーを返している

どれも C++ の規格上は完全に合法です。コンパイラの仕事は「規格に適合しているか」の判定であって、「書いた人間が意図した通りか」の判定ではない。ここに、埋めるべき隙間があります。

補足：警告レベルを上げればいいのでは？

それは正しい第一歩です。/W4 や /W4 /WX は必ず有効にすべきで、静的解析はその代わりではありません。ただしコンパイラの警告は「コンパイルの副産物として安く出せるもの」に限られます。フロー解析やコーディング規約の照合まで背負わせると、ビルドが現実的でない速度になります。だから別のツールとして切り出されているのです。

1.3 静的解析が得意なこと・苦手なこと

静的解析は万能ではありません。過剰な期待をすると「警告が多すぎて誰も見なくなる」という、よくある失敗に直行します。得意・不得意をあらかじめ言語化しておきます。

得意なこと

  • 局所的なパターンの照合：「new[] のペアが delete[] でない」のように、コードの形だけで判定できるもの。
  • 網羅性：テストが通らなかった分岐にも等しく目を通す。稀にしか実行されない経路こそ、静的解析の主戦場です。
  • 規約の機械化：「この関数はうちのコードベースでは使わない」といったチーム固有のルール。人間のレビューで指摘し続けるのは消耗しますが、機械なら疲れません。これが本書の中心テーマである Query Based Custom Check の出番です。

苦手なこと

  • 実行時にしか決まらない値：ユーザー入力の長さ、ファイルの中身、スレッドの実行順序。
  • 仕様との照合：「この計算式が業務ルール上正しいか」は静的解析には分かりません。テストの領分です。
  • 偽陽性ゼロ：静的解析は必ず誤検出を出します。誤検出との付き合い方（第37章）まで含めて運用です。

1.4 早く見つけるほど安い

静的解析を導入する動機を一言でいえば「検出を左に寄せる」ことです。同じバグでも、見つかる場所によってコストが桁で変わります。

ここで注目してほしいのは、Clang-Tidy の帯が長いことです。Visual Studio の中で書いている最中に波線として出すことも、ビルド時に警告として出すことも、CI で差分だけチェックすることもできます。しかも そのすべてが同じ .clang-tidy ファイル一つで制御される。「手元では出ないのに CI では落ちる」という一番つらい状況を避けられます。

1.5 【ハンズオン】題材コードを手元に置く

この章の作業は、リスト1-1 を実際にビルドして「コンパイラが何を言い、何を言わないか」を自分の目で確かめることです。環境構築の詳細は第3章で扱うので、ここでは既存の C++ プロジェクトがあればそれを使っても構いません。

HANDS-ON 1　コンパイラの沈黙を確認する
  1. Visual Studio 2026 で空の C++ コンソールアプリを作成し、config_loader.h と config_loader.cpp をリスト1-1 の内容で追加します。
  2. main.cpp に次のコードを書きます。 
    #include "config_loader.h"
#include <print>

int main() {
    ConfigLoader loader("app.ini");
    loader.load();
    for (const auto& e : loader.entries()) {
        std::println("{} = {}", e.name, e.value);
    }
}
  3. プロジェクトのプロパティで警告レベルを /W4 に設定してビルドします（構成プロパティ > C/C++ > 全般 > 警告レベル）。
  4. 出力ウィンドウとエラー一覧に何が出たかを書き出します。おそらく C4996（非推奨関数）が数件出るだけのはずです。
  5. 次に、1.1 節の表に挙げた6つの問題のうち、いくつがコンパイラに指摘されたか を数えます。
C4996 が出ない場合

プロジェクトに _CRT_SECURE_NO_WARNINGS が定義されていると非推奨警告は抑制されます。テンプレートによっては既定で入っていることがあるので、プリプロセッサ定義を確認してください。なお <print> と std::println は C++23 の機能なので、言語規格の設定が必要です。これも第3章で扱います。

1.6 コンパイラが黙ったところから先へ

ハンズオンの結果、おそらく「6つのうち3つ」程度しか指摘されなかったはずです。残りは、コードを読んだ人間なら気づけるのに、機械は何も言わなかった問題です。

この隙間を埋めるのが Clang-Tidy です。そして本書の主題は、その先にあります。上の表の問題は Clang-Tidy が標準で持っているチェック で拾えますが、実務で本当に効くのは「うちのコードベースでは strcpy ではなく SafeCopy() を使う」「この基底クラスを継承したら必ず接尾辞 Component を付ける」といった、あなたのチームにしか存在しないルール です。

そうしたルールを、C++ を一行も書かずに .clang-tidy の設定だけで実装する仕組みが Query Based Custom Check です。第6部でそこに到達します。

この章のまとめ

  • コンパイラは「規格に合っているか」、テストは「この入力で正しいか」を見る。「合法だが危ういか」を見る目は別に必要。
  • リスト1-1 の ConfigLoader を本書の題材とする。new[]/delete の不一致、戻り値の未チェック、不要なコピーなど、コンパイラが黙る問題を意図的に含めてある。
  • 静的解析は「局所的なパターンの照合」と「網羅性」が得意で、「実行時の値」と「仕様との照合」は苦手。偽陽性は必ず出る前提で運用する。
  • Clang-Tidy はエディタ・ビルド・CI のすべてを同一の設定ファイルで統一できる。

次章： 第2章「Clang-Tidy とその仲間たち」では、Clang-Tidy が内部でソースコードをどう扱っているのか、そして clang-query、run-clang-tidy、clang-apply-replacements といった周辺ツールとの役割分担を、仕組みから押さえます。
