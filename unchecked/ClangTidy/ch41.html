第 41 章

.clang-format との役割分担

第7部の最終章です。clang-format は Clang-Tidy と同じ LLVM 由来のツールで、設定ファイルの名前も似ています。しかし守備範囲はきれいに分かれています。書式は clang-format、意味は clang-tidy。 それでも接点はあり、そこを整理しないと自動修正のたびに差分が荒れます。

41.1 守備範囲

境界にあるもの

readability-braces-around-statements は、if (x) return; に波括弧を付けます。これは書式のようで、実は意味の問題です。 波括弧がないと、後から行を足したときにスコープが変わってバグになる。だから clang-tidy が扱います。
一方 clang-format は、既にある波括弧をどこに置くかを決めます。付けるかどうかは決めません。

41.2 実行順序

両方を自動適用する場合、順序が問題になります。

# .clang-tidy
FormatStyle: file      # 修正箇所の周辺を .clang-format に従って整形する

41.3 設定ファイルを並べる

2つの設定ファイルは、同じディレクトリに並べます。どちらもディレクトリ階層をたどって探されます。

MyProject\
├─ .clang-format      ← 書式
├─ .clang-tidy        ← 意味
└─ …

.clang-format の最小構成は次のようなものです。

# .clang-format
BasedOnStyle: Microsoft
IndentWidth: 4
ColumnLimit: 120
PointerAlignment: Left
SortIncludes: true
Visual Studio は .clang-format を既定で使う

Visual Studio の C++ エディタは、.clang-format があればそれに従って整形します（ツール > オプション > テキスト エディター > C/C++ > 書式設定）。設定ファイルを置くだけで、チーム全員のエディタの整形が揃います。 Clang-Tidy と違って追加の仕掛けは要りません。

41.4 重なる領域の調停

両者の設定が食い違うと、直しては戻されるループが起きます。よくある組み合わせを整理します。

clang-tidy 側clang-format 側調停
readability-braces-around-statementsAllowShortIfStatementsOnASingleLinetidy が波括弧を付け、format が配置を決める。矛盾しない
readability-isolate-declaration─tidy が宣言を分割。format は分割後を整形
misc-include-cleanerSortIncludes / IncludeCategoriestidy が include を追加、format が並べ替える。順序に注意
modernize-use-trailing-return-typeColumnLimit戻り値型が後置になると行が伸びる。format が折り返す
include の扱いだけは順序が効く

misc-include-cleaner が include を追加したあと、clang-format の SortIncludes が並べ替えます。この2つを別々のタイミングで走らせると、「tidy が追加 → format が並べ替え → 次の tidy で位置が変わって再検出」のような揺れが起きることがあります。include に関わるチェックを入れる場合は、FormatStyle: file を設定して同じ実行の中で整形させてください。

41.5 CI での組み合わせ

書式は「違反していたら落とす」が明快です。意味と違って、議論の余地がないからです。

# .github/workflows/format.yml
name: clang-format

on:
  pull_request:

jobs:
  format:
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - name: Install LLVM
        run: |
          choco install llvm --version=22.1.0 -y --no-progress
          echo "C:\Program Files\LLVM\bin" >> $env:GITHUB_PATH
      - name: Check formatting of changed files
        shell: pwsh
        run: |
          $files = git diff --name-only origin/${{ github.base_ref }}... |
                   Where-Object { $_ -match '\.(cpp|h|hpp)$' }
          if (-not $files) { exit 0 }
          $bad = @()
          foreach ($f in $files) {
            $formatted = clang-format --style=file $f
            $current   = Get-Content $f -Raw
            if (($formatted -join "`n") -ne $current.TrimEnd()) { $bad += $f }
          }
          if ($bad) {
            Write-Host "::error::次のファイルが整形されていません:"
            $bad | ForEach-Object { Write-Host "  $_" }
            exit 1
          }
clang-formatclang-tidy
CI で落とすか常に落とすTier 0 のみ（第40章）
理由直し方が一意。議論の余地がない判断が要る。段階導入が必要
直す手間clang-format -i を実行するだけ人間が考える

41.6 【ハンズオン】両者を共存させる

HANDS-ON 41　書式と意味を分けて運用する
  1. .clang-format を作る。 41.3 節の内容をソリューション直下に置きます。既存コードの多数派に合わせて調整してください（第20章と同じ考え方です）。
  2. Visual Studio で効くことを確認する。 エディタで Ctrl+K, Ctrl+D（ドキュメントのフォーマット）を実行し、.clang-format の設定に従うことを確認します。IndentWidth を変えて、挙動が変わることも見てください。
  3. 全体整形を1コミットで行う。 
    clang-format -i --style=file (対象ファイル群)
git add -A
git commit -m "style: apply clang-format to all sources"
    このコミットのハッシュを記録してください。
  4. blame の無視リストを作る。 リポジトリ直下に .git-blame-ignore-revs を作り、手順3のコミットハッシュを書きます。 
    # 全体整形コミット（内容の変更なし）
a1b2c3d4e5f6...
    git config blame.ignoreRevsFile .git-blame-ignore-revs
    git blame で整形コミットが飛ばされることを確認します。
  5. FormatStyle の効果を見る。 .clang-tidy の FormatStyle を none にして自動修正を当て、差分を確認します。次に file にして同じ修正を当て、差分の見え方が変わることを確認してください。 
    clang-tidy --checks="-*,modernize-use-nullptr" --fix --format-style=none config_loader.cpp -- -std=c++23
git diff
git checkout -- .
clang-tidy --checks="-*,modernize-use-nullptr" --fix --format-style=file config_loader.cpp -- -std=c++23
git diff
  6. include の揺れを確認する。 misc-include-cleaner を有効にして自動修正を当て、そのあと clang-format -i を実行します。include の位置が変わるかどうかを確認してください。変わるなら、FormatStyle: file を設定して同じ実行の中で整形させます。
  7. CI に書式チェックを追加する。 41.5 節の YAML を追加し、わざと整形を崩した PR で落ちることを確認します。エラーメッセージに「clang-format -i を実行してください」と書いておくと親切です。
  8. 役割分担を文書化する。 docs\ に、次の1行を書きます。 
    書式は clang-format、意味は clang-tidy。
書式は CI で必ず落とす（直し方が一意なので議論不要）。
意味は Tier 0 のみ落とす（判断が要るので段階導入）。
    この分担が明文化されていれば、「なぜこっちは落ちてこっちは落ちないのか」という疑問が生まれません。

この章のまとめ

  • 書式は clang-format、意味は clang-tidy。 分ける基準は「実行しても意味が変わらないか」。
  • 波括弧を付けるかは clang-tidy、どこに置くかは clang-format。
  • FormatStyle: file を設定すれば、自動修正した箇所の周辺だけが整形される。差分が荒れない。
  • 全体整形は1コミットにまとめ、.git-blame-ignore-revs に登録する。
  • include に関わるチェックは、format との実行順序で揺れることがある。同じ実行の中で整形させる。
  • CI では書式は常に落とし、意味は Tier 0 のみ落とす。 書式は直し方が一意で議論の余地がないため。
  • Visual Studio は .clang-format を既定で使う。置くだけで全員のエディタが揃う。
