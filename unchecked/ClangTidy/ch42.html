「レビューに残す」は正当な結論

すべてを機械化する必要はありません。年に数回しか起きない違反のために、保守コストの高いチェックを持つのは割に合いません。 第33章で書いたとおり、「8割を機械が拾い、2割を人間が見る」は健全な状態です。

42.3 C++ でチェックを実装する

それでも必要になったときのために、全体像を示します。本書はここに踏み込みませんが、道筋を知っていることには意味があります。

雛形を生成する

LLVM のソースツリーには、新しいチェックの雛形を作るスクリプトがあります。公式ドキュメントによれば、このスクリプトは次を行います。

  • 指定したモジュールのディレクトリにチェックのクラスを作り、モジュールとビルドシステムに登録する
  • test/clang-tidy/ にテストファイルを作る
  • ドキュメントファイルを作り、チェック一覧に追加する
$ clang-tidy/add_new_check.py readability awesome-function-names

チェッククラスの構造

第5部の学習は無駄にならない

C++ で実装する場合も、核心は AST Matcher 式です。 第23〜28章で身につけたものが、そのまま registerMatchers() の中身になります。違うのは、check() という手続きを書ける場所が増えることです。

テストの書き方

LLVM のテストは check_clang_tidy.py というスクリプトを使い、CHECK-MESSAGES と CHECK-FIXES のディレクティブで期待を書きます。

// RUN: %check_clang_tidy %s readability-awesome-function-names %t
void bad_name();
// CHECK-MESSAGES: :[[@LINE-1]]:6: warning: function name is not awesome

第37章で作った回帰テストの仕組みと、発想は同じです。 「期待をソースに書いて、機械が突き合わせる」という形は変わりません。

42.4 配布方式と Windows の現実

C++ で実装したチェックを使うには、2つの方式があります。ここに Windows 固有の事情があります。

本体ビルド方式プラグイン方式
やることLLVM のソースにチェックを追加し、clang-tidy をビルドして配布チェックを共有ライブラリにし、-load で読み込ませる
ビルドLLVM 全体（数時間・数十 GB）自分のコードだけ
配布ビルドした実行ファイルを全開発者・CI に配るDLL / .so を配る
Windows での可否可能（時間はかかる）歴史的に困難
Windows におけるプラグイン方式の状況

Clang/LLVM のプラグイン機構は、長らく Windows で動きませんでした。理由は ELF と PE/COFF の違いです。ELF ではシンボルが暗黙にエクスポートされるのに対し、Windows の PE 形式では明示的なエクスポート指定が必要で、しかもエクスポートできるシンボル数に上限があります。

この問題に対しては LLVM 側で改善作業が進んでおり、2024 年の Google Summer of Code で Windows 向けの共有ライブラリ構成が実装され、一部は本体に取り込まれています。ただし本書執筆時点では作業が継続中で、MSVC でビルドしたコードから消費できないといった制約も残っています。

つまり Windows での実用的な選択肢は、当面「本体ビルド方式」か「Query Based Custom Check」の二択だということです。最新の状況は、お使いの LLVM のリリースノートで確認してください。

本書が Query Based Custom Check を主題に選んだ理由

ここまで読んでいただければ、その理由は明らかだと思います。Windows + Visual Studio という環境で、独自ルールを現実的なコストで運用できる手段は、いまのところこれしかありません。 実験的機能であるという弱点を抱えてなお、代替が存在しないのです。だからこそ、第37章の回帰テストと第38章のバージョン管理を、あれほど強調しました。

本書を終えるにあたって

第1章で、リスト1-1 の ConfigLoader を見ました。コンパイルは通り、テストも通る。それでも6つの問題を抱えたコードでした。

あのとき、コンパイラが指摘できたのは半分以下でした。残りは 「合法だが危うい」 という、機械が黙る領域にありました。

本書を通じて、その領域を埋める道具を一つずつ積み上げてきました。標準チェックが問題の多くを拾い、設定とオプションでそれを自分たちの基準に合わせ、CI が新しいコードを守る。そして最後に、標準チェックにも存在しない「あなたのチームにしかないルール」を、自分の手で書けるようになりました。

Query Based Custom Check は実験的機能です。設定の形も、クエリの記述も、これから変わるかもしれません。しかし本書で本当に身につけたのは、設定ファイルの書式ではありません。AST を読み、条件を式にし、件数で判断し、記録を残す ── この一連の作業の型です。仕組みが変わっても、この型は残ります。

そして最も大事なことを、もう一度。静的解析の目的は、警告を出すことではありません。 出た警告が読まれ、直され、次から同じ問題が起きなくなること。そのために本書では、件数を数え、Tier を分け、メッセージの書き方にこだわり、導入の順序を設計しました。ツールは、人が使って初めて意味を持ちます。

あなたのプロジェクトの .clang-tidy が、これから育っていきますように。

この章のまとめ

  • クエリで書けないものは3つ。①状態を追うもの ②翻訳単位をまたぐもの ③計算や複雑な条件が必要なもの。
  • 突き当たったら、標準チェックで代用 → ルールを分割 → 価値とコストを比較の順に検討する。C++ 実装は最後。
  • 「レビューに残す」は正当な結論。 すべてを機械化する必要はない。
  • C++ 実装の核心も AST Matcher 式（registerMatchers()）。第5部の学習はそのまま活きる。
  • check() に手続きを書けるので②③が解決する。storeOptions() でオプションも持てる。
  • Windows ではプラグイン方式が歴史的に困難。 改善作業は進行中だが、当面は「本体ビルド」か「Query Based Custom Check」の二択。
  • だからこそ本書は Query Based Custom Check を主題に選んだ。実験的機能であることを、回帰テストとバージョン管理で補う。
