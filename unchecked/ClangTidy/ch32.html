第 32 章

実践1：禁止 API を検出する

ここから4章にわたって実践編です。最初は「使ってはいけない関数を検出する」── カスタムチェックの需要として最も多いパターンです。単純に見えますが、実運用に耐える形にするには 除外の設計と、移行の設計が要ります。作りながら、その二つを身につけます。

32.1 要件を定義する

いきなりクエリを書きません。何を検出したいのかを言葉で確定させてから始めます。

32.2 段階的に作る

第25章の「広いところから絞る」を、そのまま実践します。各段階で件数を記録してください。

v1：名前で捕まえる

match callExpr(
  callee(functionDecl(hasAnyName("strcpy", "strcat", "sprintf")))
).bind("call")

まず動くことを確認します。この時点では件数が多すぎるはずです。

v2：完全修飾で絞る

match callExpr(
  callee(functionDecl(hasAnyName("::strcpy", "::strcat", "::sprintf")))
).bind("call")

:: を付けて、グローバル名前空間の関数に限定します（第27章）。自作の MyString::strcpy のようなメンバ関数を巻き込まなくなります。

v3：解析対象を絞る

match callExpr(
  callee(functionDecl(hasAnyName("::strcpy", "::strcat", "::sprintf"))),
  isExpansionInMainFile()
).bind("call")

ヘッダ由来を除外します。ヘッダ内のコードも検査したい場合は、これを外して HeaderFilterRegex 側で制御します（第10章）。

v4：例外を除外する

match callExpr(
  callee(functionDecl(hasAnyName("::strcpy", "::strcat", "::sprintf"))),
  isExpansionInMainFile(),
  unless(hasAncestor(functionDecl(matchesName("^::.*[Tt]est"))))
).bind("call")

テスト関数の中を除外します。ただし、この方法には限界があります。

除外はクエリでやるべきか、設定でやるべきか

「テストコードを除外」は、クエリの条件（unless(hasAncestor(...))）でも、ディレクトリ単位の設定（第7章の InheritParentConfig）でも実現できます。後者を優先してください。

  • クエリでやると、除外条件がチェックごとに散らばる
  • 設定ファイルでやると、tests/.clang-tidy の1か所で全チェックに効く
  • 命名規約に依存した除外（matchesName("Test")）は、命名が変わると壊れる

クエリでの除外は、ディレクトリでは分けられない例外（「この関数の中だけは許す」など）に限定するのが健全です。

32.3 メッセージを完成させる

禁止 API のチェックでは、代替 API ごとにチェックを分けるのが有効です。メッセージを具体的にできるからです。

CustomChecks:
  # 文字列コピー系
  - Name: no-unsafe-string-copy
    Query: |
      match callExpr(
        callee(functionDecl(hasAnyName("::strcpy", "::strcat", "::wcscpy", "::wcscat"))),
        isExpansionInMainFile()
      ).bind("call")
    Diagnostic:
      - BindName: call
        Message: "境界チェックのない文字列コピーは禁止です。util::SafeCopy() を使ってください"
        Level: Warning

  # 書式出力系
  - Name: no-unsafe-format
    Query: |
      match callExpr(
        callee(functionDecl(hasAnyName("::sprintf", "::vsprintf", "::swprintf"))),
        isExpansionInMainFile()
      ).bind("call")
    Diagnostic:
      - BindName: call
        Message: "sprintf 系は禁止です。std::format または std::print を使ってください（C++23）"
        Level: Warning
チェックを分ける三つの利点
  • メッセージが具体的になる：代替 API を名指しできる
  • 段階導入ができる：文字列コピーは Tier 1、書式出力は Tier 2、といった配置が可能
  • 抑制が細かくできる：NOLINT(custom-no-unsafe-format) で片方だけ許可できる

32.4 Windows 固有の事情

Windows の C++ コードでは、次の点に注意が必要です。

事情対処
Microsoft の安全版（strcpy_s など）があるそれを推奨するなら、メッセージに書く。禁止リストには入れない
TCHAR 系マクロ（_tcscpy）マクロは展開後の名前（strcpy / wcscpy）で AST に現れる。展開後の名前で捕まる
Windows SDK のヘッダが大量の関数を宣言しているisExpansionInMainFile() やヘッダフィルタで除外（第10章）
C4996（非推奨警告）が既に出ている重複する。コンパイラ警告と自作チェックのどちらを正とするか決める
マクロ経由の呼び出し

_tcscpy(a, b) は、ビルド設定に応じて strcpy または wcscpy に展開されます。AST には展開後の姿が現れるので、クエリは展開後の名前で書きます。 一方、警告が出る位置はマクロの使用箇所か定義箇所かで変わりえます（第9章 9.3 節）。NOLINT が効かないときは、この点を疑ってください。

32.5 【ハンズオン】実運用に耐える形まで作る

HANDS-ON 32　禁止 API チェックを完成させる
  1. 要件を書く。 図32-1 の4欄を、docs\clang-tidy-decisions.md（第22章）に追記する形で埋めます。 
    ## custom-no-unsafe-string-copy
- 禁止: strcpy, strcat, wcscpy, wcscat
- 代替: util::SafeCopy()
- 例外: third_party/ 配下、tests/ 配下
- 既存件数: （手順3で記録）
  2. 検証ファイルを充実させる。 tests\custom-checks\unsafe-api.cpp を作り、検出されるべき例と、されるべきでない例を両方入れます。 
    #include <cstring>
#include <cstdio>

namespace util { void SafeCopy(char*, const char*, size_t); }

struct MyString {
    static void strcpy(char* d, const char* s) {}   // 同名の自作関数（検出しない）
};

void bad(char* d, const char* s) {
    strcpy(d, s);                    // 検出する
    strcat(d, s);                    // 検出する
    sprintf(d, "%s", s);             // 検出する（別チェック）
}

void good(char* d, const char* s, size_t n) {
    util::SafeCopy(d, s, n);         // 検出しない
    strncpy(d, s, n);                // 検出しない
    MyString::strcpy(d, s);          // 検出しない ← v2 の効果
}
  3. v1 から順に作る。 clang-query で v1 → v2 → v3 を実行し、各段階の件数を記録します。特に v1 と v2 の間で MyString::strcpy が消えることを確認してください。
  4. 設定ファイルに移す。 32.3 節の内容を .clang-tidy に書きます。2つのチェックに分けてください。
  5. 件数を突き合わせる。 
    clang-tidy --experimental-custom-checks unsafe-api.cpp -- -std=c++23
    clang-query での件数と一致することを確認します。
  6. ディレクトリ単位の除外を作る。 tests\.clang-tidy を作り、カスタムチェックを無効にします。 
    InheritParentConfig: true
Checks: '-custom-no-unsafe-string-copy,-custom-no-unsafe-format'
    クエリの条件ではなく設定で除外するという 32.2 節 v4 の方針の実装です。ただし今回の検証ファイルは tests\ 配下にあるので、確認のときは一時的に外してください。
  7. 抑制の粒度を確認する。 
        sprintf(d, "%s", s);   // NOLINT(custom-no-unsafe-format)
    書式出力の警告だけが消え、文字列コピーの警告は残ることを確認します。チェックを分けた効果です。
  8. Tier を決める。 実プロジェクト（TidyLab 全体）に対して実行し、既存件数を数えます。
    • 0〜十数件 → Checks に入れて Tier 1。さらに WarningsAsErrors で Tier 0 も検討
    • 数十件以上 → Tier 2 の設定ファイル（第22章 22.5 節）に入れ、差分解析でのみ適用
    決めた内容を判断記録に書きます。
  9. 期待動作を記録する。 tests\custom-checks\README.md の表に、今回のチェックを追加します。 
    | custom-no-unsafe-string-copy | unsafe-api.cpp | 2 | strcpy/strcat | MyString::strcpy, strncpy |
| custom-no-unsafe-format      | unsafe-api.cpp | 1 | sprintf       | ─ |

この章のまとめ

  • クエリを書く前に4欄を埋める。①何を禁止 ②代わりに何を使う ③例外 ④既存件数。
  • ②が決まっていないルールは導入しない。「使うな」だけでは開発者の手が止まる。
  • 段階的に絞る。名前 → 完全修飾（::）→ 解析対象 → 例外。各段階で件数を記録する。
  • 除外はクエリの条件より、ディレクトリ単位の設定を優先する。 条件が散らばらず、命名規約の変更にも強い。
  • 代替 API ごとにチェックを分ける。 メッセージが具体的になり、段階導入と個別抑制ができる。
  • マクロ経由の呼び出しは展開後の名前で AST に現れる。クエリは展開後の名前で書く。
  • 既存件数が Tier を決める。件数を見てから配置を決める。
