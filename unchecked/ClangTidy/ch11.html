第 11 章

自動修正を体験する

Clang-Tidy の警告の多くは、修正案を伴っています。コマンド一つで数百箇所を直せる ── 便利ですが、同時に本書で最も危険な機能でもあります。仕組みを理解し、安全な手順を確立してから使ってください。この章で第2部が完結します。

11.1 FixIt ── 診断に付いてくる修正案

チェックが診断を出すとき、多くの場合それは単なるメッセージではありません。「ソースのこの範囲を、この文字列に置き換えればよい」という具体的な指示（FixIt） が添えられています。

> clang-tidy --checks="-*,modernize-use-nullptr" ch05_first_run.cpp -- -std=c++23
ch05_first_run.cpp:5:14: warning: use nullptr [modernize-use-nullptr]
    5 |     int* p = NULL;
      |              ^~~~
      |              nullptr

3行目の ^~~~ が置換範囲、4行目の nullptr が置換後の文字列です。これが FixIt の実体で、単なる表示ではなく機械可読なデータとして保持されています。

すべての警告に修正案があるわけではない

「危険な設計だ」という指摘のように、機械が正解を決められない警告には FixIt が付きません。目安として、

  • 付きやすい：modernize-*（書き換え規則が明確）、readability-* の一部
  • 付きにくい：clang-analyzer-*（何が正しい修正かは文脈依存）、bugprone-* の多く

11.2 修正を適用するオプション

オプション意味
--fix修正案を適用する。コンパイルエラーが1つでもあると何もせず終了する
--fix-errorsコンパイルエラーがあっても適用する。コンパイラ側の FixIt も当てる
--fix-notes警告自体に修正案がなくても、付随する note に単一の修正案があれば当てる
--format-style修正した箇所の周辺を整形する（none / file / llvm など）
--export-fixes適用せず YAML に書き出す
--fix-errors は慎重に

--fix がコンパイルエラー時に何もしないのは安全装置です。パースに失敗した状態の AST は不完全で、そこから導かれた修正案は信用できません。--fix-errors はその安全装置を外すオプションです。使うのは、コンパイルエラーの原因を把握したうえで、それが修正内容に影響しないと確信できるときだけにしてください。

--format-style を付ける理由

FixIt はテキストの置換なので、置換後に行が長くなったりインデントが崩れたりします。--format-style=file を指定すると、.clang-format の設定に従って修正箇所の周辺だけを整形してくれます。

# .clang-tidy
FormatStyle: file

ただしこれは 修正した箇所の周辺だけ です。ファイル全体の整形は clang-format の仕事で、両者の役割分担は第41章で扱います。

11.3 自動修正が危険な場面

FixIt は「このチェックの観点では正しい」修正です。プログラム全体として正しいかは保証されていません。 典型的な危険を挙げます。

意味が変わる修正

// modernize-pass-by-value の提案
- void setName(const std::string& name) { name_ = name; }
+ void setName(std::string name) { name_ = std::move(name); }

多くの場合これは改善ですが、呼び出し側が常に左辺値を渡している場合は、コピーが1回増えることがあります。「性能のための修正」が性能を落とすことがある、という点に注意が必要です。

影響範囲が広い修正

readability-identifier-naming の自動修正は、識別子の定義と参照をまとめてリネームします。これは強力ですが、

  • 解析対象外のファイル（第10章のフィルタで除外したもの）にある参照は書き換わらない
  • マクロや文字列リテラルの中に埋め込まれた名前は書き換わらない
  • 外部に公開している API 名を勝手に変えてしまう可能性がある

という穴があります。翻訳単位をまたぐリネームは、必ずプロジェクト全体を対象にして一度に実行し、直後にビルドを通す 必要があります。

コメントと乖離する修正

コードだけが書き換わり、隣のコメントは古いまま残ります。機械はコメントの意味を知りません。

11.4 安全な適用手順

差分を読まない自動修正は、自動でバグを入れる行為

「500件直りました」は成果ではありません。500件の差分を読んでいないなら、それは 500件のレビューされていない変更をコミットしたということです。件数が多すぎて読めないなら、それはチェックの選び方かディレクトリの絞り方が粗すぎるサインです。

11.5 【ハンズオン】修正を当ててみる

HANDS-ON 11-A　1件だけ直す
  1. コミットしておく。 TidyLab の変更をすべてコミットし、git status がきれいな状態にします。バージョン管理を使っていない場合は、フォルダごとコピーしてバックアップします。この手順を飛ばさないでください。
  2. 修正対象を用意する。 ch05_first_run.cpp に int* p = NULL; が残っていることを確認します。
  3. まず書き出す。 
    clang-tidy --checks="-*,modernize-use-nullptr" --export-fixes=fixes.yaml ch05_first_run.cpp -- -std=c++23
    生成された fixes.yaml をエディタで開き、FilePath、Offset、Length、ReplacementText といったフィールドを確認します。FixIt がどういうデータなのかを、一度自分の目で見ておいてください。
  4. 適用する。 
    clang-tidy --checks="-*,modernize-use-nullptr" --fix ch05_first_run.cpp -- -std=c++23
  5. 差分を読む。 
    git diff
    NULL が nullptr になっていることを確認します。
  6. ビルドして戻す。 ビルドが通ることを確認したら、次の手順のために git checkout -- . で元に戻します。
HANDS-ON 11-B　安全装置と危険な修正を確かめる
  1. --fix の安全装置を見る。 ch05_first_run.cpp にわざと構文エラー（行末のセミコロンを消すなど）を入れ、手順4のコマンドを実行します。修正が一切適用されないことを確認してください。確認したら構文エラーを戻します。
  2. 整形の有無を比べる。 --format-style=none と --format-style=file で同じ修正を当て、周辺の整形が変わることを確認します（.clang-format がない場合は llvm を指定）。
  3. 影響範囲の広い修正を観察する（適用はしない）。 第8章で設定した命名規約を使い、--fix を付けずに 書き出しだけ行います。 
    clang-tidy --checks="-*,readability-identifier-naming" --export-fixes=rename.yaml config_loader.cpp -- -std=c++23
    rename.yaml を開き、何ファイルの何箇所が書き換わる予定か を数えます。ヘッダも対象に入っていることを確認してください。
  4. 実際に当てて、差分を読む。 手順3の対象を config_loader.cpp と main.cpp の両方にして --fix で適用し、git diff をすべて読みます。読んだうえで、これを人手でレビューできる量かどうかを自分に問うてください。
  5. ビルドする。 通らなければ、リネームが届いていない参照があるということです。第10章のヘッダフィルタとの関係を思い出してください。
  6. 元に戻す。 git checkout -- . で復元し、生成した YAML ファイルを削除します。
Visual Studio のクイックフィックス

エディタ上の波線にカーソルを合わせると、修正案が提示されることがあります。1件ずつ差分を見ながら適用できるので、日常の作業ではこれが最も安全で速い経路です。--fix の出番は「新しいチェックを導入して、既存コードを一気に追従させる」ような、まとまった作業のときだけと考えてください。

第2部の終わりに

ここまでで、Clang-Tidy を実運用に耐える形に整える道具が揃いました。

  • チェックをグロブで自在に選べる（第6章）
  • 設定を .clang-tidy に一本化し、ディレクトリ単位で使い分けられる（第7章）
  • オプションでチェックの挙動を自分の基準に合わせられる（第8章）
  • 個別の例外を作法に沿って抑制できる（第9章）
  • ヘッダの見え方を制御できる（第10章）
  • 修正を安全に適用できる（第11章）

ここまでは 「用意されたチェックを使う」 話でした。第3部でコマンドラインとビルドへの組み込みを固め、第4部で標準チェックの中身をツアーしたあと、第5部・第6部で 「自分でチェックを作る」 側へ移ります。

この章のまとめ

  • 多くの診断には FixIt（置換範囲と置換文字列）が付いている。clang-analyzer-* のような文脈依存のチェックには付きにくい。
  • --fix はコンパイルエラーがあると何もしない。これは安全装置であり、--fix-errors はそれを外すオプション。
  • 並列実行時は --export-fixes で YAML に書き出し、clang-apply-replacements で重複と競合を解決しながら適用する。
  • --format-style（FormatStyle）で修正箇所の周辺を整形できる。ファイル全体の整形は clang-format の仕事。
  • FixIt は「そのチェックの観点で正しい」だけ。意味が変わる修正、影響範囲の広いリネーム、コメントとの乖離に注意する。
  • 安全な手順は 作業ツリーをきれいに → 1チェックずつ → 書き出して確認 → 適用 → 差分を全部読む → ビルドとテスト → チェック単位でコミット。
  • 差分を読まない自動修正は、自動でバグを入れる行為に等しい。
