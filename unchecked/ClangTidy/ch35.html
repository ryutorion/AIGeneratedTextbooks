35.2 new[] / delete の不一致を完成させる

第27章で clang-query 上で完成させたクエリを、設定ファイルに移します。

  - Name: array-delete-mismatch
    Query: |
      match cxxDeleteExpr(
        unless(isArrayForm()),
        has(ignoringImplicit(
          declRefExpr(to(varDecl(
            hasInitializer(ignoringImplicit(cxxNewExpr(isArray()).bind("alloc")))
          ).bind("var")))
        )),
        isExpansionInMainFile()
      ).bind("del")
    Diagnostic:
      - BindName: del
        Message: "new[] で確保した領域を delete で解放しています。delete[] を使ってください"
        Level: Warning
      - BindName: alloc
        Message: "ここで new[] により確保されています"
        Level: Note
      - BindName: var
        Message: "対象の変数はこれです"
        Level: Note

35.3 Note の設計原則

原則1：読み手の次の行動を減らす

Note を足すかどうかの基準は、「読み手が Warning だけを見て、次に何をすべきか分かるか」です。分かるなら不要です。

原則2：数は最小に

上の例では "var" の Note を出していますが、これは削るべきです。 "alloc" の Note があれば、変数の位置も自然に分かるからです。Note が増えるとエラー一覧が埋まり、かえって読まれなくなります。

    Diagnostic:
      - BindName: del
        Message: "new[] で確保した領域を delete で解放しています。delete[] を使ってください"
        Level: Warning
      - BindName: alloc
        Message: "ここで new[] により確保されています"
        Level: Note

原則3：Note は単独で意味を持たなくてよい

「ここで確保されています」というメッセージは、単独では何のことか分かりません。それでよいのです。 Note は Warning に付随するものであり、Warning のメッセージと合わせて読まれます。

メッセージの分業
  • Warning：何が問題か ＋ どう直すか（第31章の3要素）
  • Note：なぜそう判定したのか（根拠となる位置を指す）

Note に長い説明を書く必要はありません。位置を指すこと自体が情報だからです。

35.4 Note が有効なパターン

パターンWarning の位置Note の位置
確保と解放の不一致解放（delete）確保（new[]）
規約違反（継承由来）違反しているクラス根拠となる基底クラス（第34章）
非推奨 API の使用呼び出し箇所関数の宣言（[[deprecated]] が付いている位置）
ペアで使うべき API の片方欠落片方だけを呼んでいる箇所対になるべき API の位置
型の不整合使用箇所型の宣言

35.5 Note の限界

AST 上で結べる範囲しか指せない

Note を出せるのは、クエリのマッチの中で bind できたノードだけです。つまり、1つの Matcher 式でたどり着ける範囲に限られます。

  • 指せる：同じ翻訳単位内で、AST 上の経路でつながっているもの
  • 指せない：別の翻訳単位にあるもの、経路がつながっていないもの
  • 指せない：「この変数が過去にどう使われたか」のような、経路をたどる情報（第17章のフロー解析の領分）

たとえば「確保と解放が別の関数にある」ケースは、AST では結べません。それはフロー解析が必要な問題であり、Query Based Custom Check の限界です（第42章）。

35.6 【ハンズオン】読み手に届く診断を作る

HANDS-ON 35　多点診断を設計する
  1. 検証ファイルを作る。 tests\custom-checks\notes.cpp に、多点診断が効く例を書きます。 
    #include <cstddef>

void localCase() {
    char* buf = new char[256];
    // …長い処理…
    delete buf;                  // 検出：同じ関数内
}

void correctCase() {
    char* buf = new char[256];
    delete[] buf;                // 検出しない
}

void scalarCase() {
    char* p = new char;
    delete p;                    // 検出しない（new[] ではない）
}

char* allocate() { return new char[256]; }
void crossFunction() {
    char* buf = allocate();
    delete buf;                  // 検出できない（関数をまたぐ）← 限界の実例
}
  2. クエリを確認する。 clang-query で 35.2 節のクエリを実行し、localCase だけが検出されることを確認します。crossFunction が検出されないことも確認してください。これが 35.5 節の限界の実例です。
  3. bind の位置を1つずつ確認する。 3つの bind（del / var / alloc）が、それぞれソースのどこを指すかを clang-query の出力で確認します。行だけでなく列も見てください。
  4. 設定ファイルに移す。 まず3つの Note をすべて出す形で書き、実行します。エラー一覧がどう見えるかを確認してください。
  5. Note を削る。 原則2 に従って "var" の Note を削除し、再度実行します。情報が減っても、直すのに困らないことを確認してください。 これが「最小の Note」という判断です。
  6. Visual Studio で見る。 エラー一覧に Warning と Note がどう並ぶかを確認します。Note の行をダブルクリックして、確保箇所にジャンプできるかを試してください。これが多点診断の実用価値です。
  7. 第34章のチェックに Note を足す。 component-naming で、基底クラスを指す Note が出ることを確認します。SpriteRenderComponent のような間接継承の場合、note がどの基底を指すかを確認してください。
  8. 限界を記録する。 docs\clang-tidy-decisions.md に、array-delete-mismatch の限界を明記します。 
    ## custom-array-delete-mismatch
- 検出できる: 同一関数内で、変数の初期化式が new[] のケース
- 検出できない: 関数をまたぐケース、宣言と代入が分かれているケース
- 補完手段: clang-analyzer-cplusplus.NewDelete（CI の Tier 2）で拾う
    「何が検出できないか」を書いておくことが、過信を防ぎます。
  9. 標準チェックと比較する。 同じファイルに clang-analyzer-* を当て、crossFunction が検出されるかを確認します。カスタムチェックと標準チェックは競合ではなく補完関係にあることを確認してください。

この章のまとめ

  • Note の価値は情報量ではなく、直してもらえる確率を上げること。
  • bind は Matcher 式の経路の途中に何個でも置ける。それぞれが別のソース位置を指せる。
  • 原則1：読み手が Warning だけで次の行動が分かるなら Note は不要。
  • 原則2：Note は最小に。増えるとエラー一覧が埋まり、読まれなくなる。
  • 原則3：Note は単独で意味を持たなくてよい。位置を指すこと自体が情報。
  • メッセージの分業 ── Warning は「何が問題でどう直すか」、Note は「なぜそう判定したか」。
  • Note を出せるのは、1つの Matcher 式でたどり着ける範囲だけ。 関数をまたぐ関係は結べない ── それはフロー解析の領分。
  • 検出できないケースを記録に残す。過信を防ぐ。
