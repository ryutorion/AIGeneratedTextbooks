第 40 章

CI で回す

第29章で見たとおり、カスタムチェックは Visual Studio から直接は動かせません。CI がカスタムチェックの本拠地になります。 あわせて、重いフロー解析、回帰テスト、件数の記録も CI に置きます。この章で、第39章の計画を実際の設定として実装します。

40.1 CI に置く三つのジョブ

40.2 GitHub Actions の設定

ジョブ① 差分解析

# .github/workflows/clang-tidy-diff.yml
name: clang-tidy (diff)

on:
  pull_request:

jobs:
  diff:
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0          # 分岐点を取るために全履歴が要る

      - name: Install LLVM
        run: |
          choco install llvm --version=22.1.0 -y --no-progress
          echo "C:\Program Files\LLVM\bin" >> $env:GITHUB_PATH

      - name: Verify version
        run: |
          clang-tidy --version
          clang-tidy --help | Select-String experimental-custom-checks

      - name: Configure (Ninja)
        run: |
          cmake -S . -B out/build/ninja -G Ninja -DCMAKE_EXPORT_COMPILE_COMMANDS=ON

      - name: Run clang-tidy on diff
        shell: pwsh
        run: |
          git diff -U0 origin/${{ github.base_ref }}... |
            python "C:\Program Files\LLVM\share\clang\clang-tidy-diff.py" `
              -p1 -path out/build/ninja -j 4 `
              -config-file tools/clang-tidy-diff.yml `
              -- --experimental-custom-checks
確認すべき3点
  • fetch-depth: 0：既定の浅いクローンでは origin/main... の分岐点が取れません
  • LLVM のバージョン固定：--version= を明示。省くと、ある日突然挙動が変わります（第38章）
  • --experimental-custom-checks の渡し方：clang-tidy-diff.py が clang-tidy へ引数を中継する方法は、スクリプトの版によって異なります。ローカルで動作を確認してから CI に入れてください。 中継できない場合は、変更ファイルを列挙して clang-tidy を直接呼ぶ形にします

ジョブ② 回帰テスト

  regression:
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install LLVM
        run: |
          choco install llvm --version=22.1.0 -y --no-progress
          echo "C:\Program Files\LLVM\bin" >> $env:GITHUB_PATH
      - name: Run custom check regression tests
        run: python tests/custom-checks/run_tests.py

第37章で作ったスクリプトを、そのまま呼ぶだけです。数秒で終わり、しかも「昨日まで動いていたものが動かなくなった」を確実に捕まえます。

ジョブ③ 全体解析

  full:
    if: github.event_name == 'schedule'
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install LLVM
        run: |
          choco install llvm --version=22.1.0 -y --no-progress
          echo "C:\Program Files\LLVM\bin" >> $env:GITHUB_PATH
      - name: Configure
        run: cmake -S . -B out/build/ninja -G Ninja -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
      - name: Full analysis
        continue-on-error: true          # 落とさない
        run: |
          python "C:\Program Files\LLVM\bin\run-clang-tidy" -p out/build/ninja -j 4 > tidy-full.log 2>&1
      - name: Count warnings
        run: |
          Select-String -Path tidy-full.log -Pattern '\[([\w\-\.]+)\]$' |
            ForEach-Object { $_.Matches.Groups[1].Value } |
            Group-Object | Sort-Object Count -Descending |
            Format-Table Count, Name
      - uses: actions/upload-artifact@v4
        with:
          name: clang-tidy-full-log
          path: tidy-full.log
continue-on-error: true が重要

全体解析は件数を記録することが目的で、開発を止めることが目的ではありません（第39章）。ここで落とすようにすると、夜間ジョブが常に赤になり、誰も見なくなります。

40.3 プルリクエストに結果を出す

ログを見に行かせるのではなく、変更行に直接コメントとして出すと、修正率が大きく変わります。GitHub Actions のワークフローコマンドを使えば、追加のツールなしで実現できます。

40.4 落とすか、警告に留めるか

第22章の Tier が、そのまま CI の挙動に対応します。

TierCI での扱い実装
Tier 0落とすWarningsAsErrors に列挙 → clang-tidy が非ゼロ終了
Tier 1注釈として出す（落とさない）ワークフローコマンドで ::warning
Tier 2差分ジョブで注釈として出す差分用の設定ファイルを使う
回帰テスト常に落とすスクリプトの終了コード
終了コードの扱い

clang-tidy は、WarningsAsErrors に指定したチェックの違反があると非ゼロで終了します。逆に言うと、単なる警告では終了コードは 0 のままです。CI を落としたいなら WarningsAsErrors を使うのが正攻法で、ログを findstr して件数で判定するのは補助手段と考えてください。

40.7 【ハンズオン】CI を組む

HANDS-ON 40　三つのジョブを実装する
  1. ローカルで全手順を再現する。 CI に書く前に、同じコマンドをローカルで順に実行して通ることを確認します。CI で初めて試すと、デバッグに何倍も時間がかかります。 
    cmake -S . -B out\build\ninja -G Ninja -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
git diff -U0 origin/main... | python "C:\Program Files\LLVM\share\clang\clang-tidy-diff.py" -p1 -path out\build\ninja
python tests\custom-checks\run_tests.py
  2. カスタムチェックの中継を確認する。 clang-tidy-diff.py から --experimental-custom-checks が clang-tidy に届くかを確認します。届かない場合の代替として、変更ファイルを列挙して clang-tidy を直接呼ぶスクリプトを書いてください。 
    # tools/analyze-changed.ps1
$files = git diff --name-only origin/main... | Where-Object { $_ -match '\.(cpp|h)$' }
foreach ($f in $files) {
    clang-tidy --experimental-custom-checks -p out/build/ninja $f
}
    ※ これは差分行ではなく差分ファイル単位になります。件数が増えるので、既存の警告が多いプロジェクトでは注意してください。
  3. 差分ジョブを作る。 40.2 節の YAML をリポジトリに置きます。fetch-depth: 0 とバージョン固定を忘れずに。
  4. 回帰テストジョブを作る。 数秒で終わるはずです。わざとクエリを壊した PR を作り、ジョブが赤くなることを確認してください。
  5. 注釈に変換する。 40.3 節のスクリプトを差分ジョブに組み込み、PR の差分ビューに警告が表示されることを確認します。
  6. Tier 0 で落ちることを確認する。 WarningsAsErrors に指定したチェックに違反する変更を含む PR を作り、CI が落ちることを確認します。次に Tier 1 のチェックだけに違反する PR で、落ちずに注釈だけ出ることを確認します。
  7. 夜間ジョブを作る。 schedule トリガーで全体解析を回し、ログをアーティファクトとして保存します。continue-on-error: true を必ず付けてください。
  8. 時間を測る。 各ステップの所要時間を CI のログで確認し、記録します。LLVM の導入が支配的なら、キャッシュか自前イメージを検討します。
  9. 手順書を更新する。 docs\setup-static-analysis.md に、「CI で落ちたときにローカルで再現する手順」を追記します。これがないと、開発者は CI のログとにらめっこすることになります。 
    ## CI で clang-tidy が落ちたとき
1. git fetch origin main
2. git diff -U0 origin/main... | python …clang-tidy-diff.py -p1 -path out\build\ninja
   → CI と同じ結果が手元で再現する
3. 直らないときは docs\clang-tidy-troubleshooting.md へ

この章のまとめ

  • CI に置くジョブは3つ。①差分解析（PR ごと・速い）②回帰テスト（PR ごと・数秒）③全体解析（夜間・落とさない）。
  • カスタムチェックの本拠地は CI。 Visual Studio からは --experimental-custom-checks を渡せないため（第29章）。
  • fetch-depth: 0 がないと origin/main... の分岐点が取れない。
  • LLVM のバージョンは必ず固定する。 しないと、ある日突然カスタムチェックが動かなくなる。
  • Tier と CI の挙動を対応させる。落とすのは Tier 0 と回帰テストだけ。
  • 終了コードで落としたいなら WarningsAsErrors を使う。ログの件数判定は補助手段。
  • 警告はワークフローコマンドで PR の差分に注釈として出す。「見に行く」を「目の前に出る」に変える。
  • 時間はまず測る。解析以外（LLVM 導入・CMake 構成）が支配的なことが多い。
  • CI に書く前に、必ずローカルで全手順を再現する。
