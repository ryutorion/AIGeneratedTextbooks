第 22 章

自分たちの .clang-tidy を育てる

第4部の総仕上げです。ここまで6つのモジュールを見てきました。それぞれ性格が違い、扱い方も違う。この章では、それらを一つの設定ファイルにまとめ、運用に耐える形に組み上げます。同時に、「なぜこのチェックを採用し、なぜあれを外したのか」を記録に残す仕組みを作ります。これがないと、半年後に誰も設定を触れなくなります。

22.1 モジュールの性格・総まとめ

モジュール目的自動修正速度置き場所
bugprone-バグの温床少ない速い常時（ローカル＋CI）
clang-analyzer-経路依存の欠陥ほぼない遅いCI 中心
modernize-書き方の刷新ほぼ全部速い移行時に一括、以後は少数
performance-無駄の除去多い速い常時
readability-可読性・命名多い速い合意した分だけ常時
cppcoreguidelines- ほか規範の機械化まちまち速い個別指定のみ

22.2 四つの層に分ける

チェックを「入れる／入れない」の二択で考えると行き詰まります。強さの段階を設けると、現実的な設計ができます。

22.3 採用の判断フロー

WarningsAsErrors の注意

ここに書いたチェックは、Checks で有効になっているものだけが対象です。有効になっていないチェックを WarningsAsErrors に書いても何も起きません。また、書式は Checks と同じグロブなので、bugprone-* のようにまとめて指定することもできます ── ただし Tier 0 は「例外を認めない」層なので、個別に列挙するのが安全です。

22.5 Tier 2 と Tier 3 をどこに書くか

.clang-tidy には「有効にするもの」しか書けません。Tier 2 と Tier 3 は別の場所に記録します。

Tier 2 ── 差分解析用の設定ファイル

CI の差分解析（第15章）でだけ使う設定を、別ファイルとして持ちます。

# tools/clang-tidy-diff.yml （差分解析専用）
InheritParentConfig: true
Checks: >
  clang-analyzer-*,
  misc-include-cleaner,
  readability-function-size,
  readability-function-cognitive-complexity

CheckOptions:
  readability-function-size.LineThreshold: '80'
  readability-function-size.NestingThreshold: '5'
  readability-function-cognitive-complexity.Threshold: '25'
> git diff -U0 | python clang-tidy-diff.py -p1 -path out\build\ninja -config-file tools\clang-tidy-diff.yml

Tier 3 ── 決定の記録

「採用しなかった」という判断は、記録がないと 「検討していない」と区別できません。リポジトリにドキュメントを1枚置きます。

<!-- docs/clang-tidy-decisions.md -->
# Clang-Tidy チェック採用の判断記録

| チェック | 判断 | 理由 | 見直し条件 |
|---|---|---|---|
| bugprone-easily-swappable-parameters | 不採用 | 既存コードで 340 件。ほぼ描画系の座標引数で、実際の取り違えは発生していない | 型安全な座標型を導入したら再検討 |
| cppcoreguidelines-owning-memory | 不採用 | GSL を採用していないため、生ポインタ全箇所が違反になる | GSL 導入を決めたら再検討 |
| cppcoreguidelines-pro-bounds-* | 不採用 | 同上 | 同上 |
| cert-* / hicpp-* | 不採用 | 大半が他モジュールのエイリアス。二重警告になる | ─ |
| misc-include-cleaner | Tier 2 | 既存コードで 1200 件。新規コードのみ適用 | 違反が 100 件を切ったら Tier 1 へ |
| clang-analyzer-* | Tier 2 | ローカルビルドが 3.4 倍に。CI の差分解析のみ | ビルドマシンが速くなったら再検討 |
| modernize-use-trailing-return-type | 不採用 | チーム内で合意が取れなかった（2026-08 の議論） | 合意が変われば再検討 |
「見直し条件」の欄が効く

不採用の理由は変わります。「GSL を導入したら」「件数が減ったら」「ビルドマシンが速くなったら」── その条件を書いておくと、状況が変わったときに設定を見直すきっかけになります。書いていないと、一度不採用にしたチェックは永遠に不採用のままです。

22.6 バージョン更新への備え

LLVM を更新すると、警告件数が変わります（第4章）。手順を決めておきます。

22.7 【ハンズオン】設定を完成させる

HANDS-ON 22　運用可能な設定に仕上げる
  1. 候補を全部走らせて件数を出す。 第16〜21章で見たモジュールについて、モジュール単位で件数を記録します。表を作ってください。 
    for %m in (bugprone modernize performance readability misc) do @(
  echo === %m ===
  clang-tidy --checks="-*,%m-*" config_loader.cpp main.cpp -- -std=c++23 2^>nul | findstr /c:"warning:" | find /c /v ""
)
  2. 四層に振り分ける。 図22-2 のフローに従い、各チェックを Tier 0〜3 に分類します。件数を見てから判断するのが要点です。
  3. Tier 1 の違反をゼロにする。 Tier 1 に置いたチェックについて、既存コードの違反をすべて直します。直せないものは Tier 2 に落とすか、Tier 3 にします。「Tier 1 なのに違反が残っている」状態を作らないでください。 警告が常時出ていると、人はそれを見なくなります。
  4. 設定ファイルを書く。 22.4 節の内容を、自分の判断に合わせて調整して .clang-tidy に書きます。各行にコメントで Tier と理由を残してください。
  5. Tier 2 用の設定を作る。 tools/clang-tidy-diff.yml を作り、InheritParentConfig: true で親を引き継ぐ形にします（第7章）。
  6. 差分解析で動作確認する。 適当な変更を1行加え、Tier 2 の設定で差分解析を実行します。 
    git diff -U0 | python clang-tidy-diff.py -p1 -path out\build\ninja -config-file tools\clang-tidy-diff.yml
    変更した行だけがチェックされることを確認します。
  7. Tier 0 を検証する。 WarningsAsErrors に指定したチェックに違反するコードをわざと書き、警告ではなくエラーになることを確認します。確認したら削除します。
  8. 判断記録を書く。 docs/clang-tidy-decisions.md を作り、Tier 2・Tier 3 のチェックについて「理由」と「見直し条件」を書きます。この文書が第4部の最終成果物です。
  9. 基準を保存する。 現在の警告件数を記録しておきます。次に LLVM を更新したとき、この数字と比較します（図22-3）。 
    python "C:\Program Files\LLVM\bin\run-clang-tidy" -p out\build\ninja > baseline-llvm22.log 2>&1
findstr /c:"warning:" baseline-llvm22.log | find /c /v ""

第4部の終わりに

標準チェックの全体像をつかみ、自分たちの設定を組み上げました。

  • モジュールごとの性格と、置き場所（ローカル／CI／一括変換）を理解した（第16〜21章）
  • 四層モデルで「入れる／入れない」の二択から抜け出した（第22章）
  • 採用・不採用の判断を記録に残す仕組みを作った

ここまでで 「用意されたチェックを使いこなす」 は完了です。しかし、実務で本当に効くルールの多くは標準チェックには存在しません。「うちのコードベースでは LegacyCopy() を使わない」「この基底クラスを継承したら接尾辞を付ける」── こうしたルールは、あなたのチームにしか存在しないからです。

第5部では、そのルールを書くための土台である Clang AST と AST Matcher を学びます。そして第6部で、C++ を一行も書かずに .clang-tidy だけで独自チェックを実装します。本書の主題は、ここから始まります。

この章のまとめ

  • チェックを「入れる／入れない」の二択で考えない。四つの層に分ける。
  • Tier 0（エラー・少数）／Tier 1（常時・違反ゼロを保つ）／Tier 2（新規コードのみ・差分解析）／Tier 3（不採用・理由を記録）。
  • 判断フローの要点は「実際に走らせて件数を数えてから決める」こと。
  • WarningsAsErrors は Checks で有効なチェックにしか効かない。Tier 0 は個別列挙が安全。
  • Tier 2 は InheritParentConfig: true の別ファイルにして、差分解析で使う。
  • Tier 3 は文書に記録する。 「理由」と「見直し条件」を書かないと、「検討していない」と区別できない。
  • LLVM 更新時は、件数の記録・--list-checks での名前検証・--dump-config での既定値確認を行う。
  • Tier 1 に違反を残さない。 常時出ている警告は、いずれ誰も見なくなる。
