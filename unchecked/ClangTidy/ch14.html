第 14 章

CMake プロジェクトで使う

本書は MSBuild を主軸にしていますが、CMake も押さえておく価値があります。理由は二つ。CI で回すときに扱いやすいこと、そして compile_commands.json が手に入ることです。このファイルは第5部で clang-query を使うときにも効いてきます。一方で、VS の CMake 統合にはツールセットの制約があります。そこを最初に押さえます。

14.1 三つの実行経路

CMake プロジェクトで Clang-Tidy を走らせる方法は、大きく3つあります。どれを選ぶかで、必要な準備も制約も変わります。

14.2 経路A：CMakePresets.json に書く

Visual Studio の CMake 統合は、CMakePresets.json の vendor マップ に置いた設定を読みます。マップ名は microsoft.com/VisualStudioSettings/CMake/1.0 です。

{
  "version": 3,
  "configurePresets": [
    {
      "name": "x64-clang-analysis",
      "generator": "Ninja",
      "binaryDir": "${sourceDir}/out/build/${presetName}",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Debug",
        "CMAKE_CXX_STANDARD": "23"
      },
      "vendor": {
        "microsoft.com/VisualStudioSettings/CMake/1.0": {
          "enableClangTidyCodeAnalysis": true,
          "clangTidyChecks": "-*,bugprone-*,performance-*",
          "enableMicrosoftCodeAnalysis": false,
          "intelliSenseMode": "windows-clang-x64"
        }
      }
    }
  ]
}
キー意味
enableClangTidyCodeAnalysisClang-Tidy 解析を有効にする（既定 false）
clangTidyChecksカンマ区切りのチェック指定。ワイルドカードと - 除外が使える（第6章と同じ文法）
enableMicrosoftCodeAnalysisMicrosoft コード分析を有効にする
disableExternalAnalysis外部ヘッダに対して解析を走らせるか
経路A の最大の落とし穴：clang-cl でビルドしていないと効かない

公式ドキュメントには、enableClangTidyCodeAnalysis は「clang-cl でビルドするときに Visual Studio の clang-tidy コード分析を有効にする」と明記されています。MSVC ツールセットのままの CMake 構成では、この設定を true にしても解析は走りません。

MSBuild プロジェクト（第13章）では MSVC ツールセットのままでも Clang-Tidy が動いたので、ここは前提が違います。「CMake に移したら急に警告が出なくなった」の典型的な原因です。

ツールセットを clang-cl にするには、プリセットでツールチェーンを指定します。

      "cacheVariables": {
        "CMAKE_C_COMPILER": "clang-cl",
        "CMAKE_CXX_COMPILER": "clang-cl"
      }

ビルドまで Clang に変えたくない場合は、経路A を諦めて経路C に寄せるのが素直です。

14.3 経路B：ビルドに組み込む

CMake には、コンパイルのたびに Clang-Tidy を一緒に起動する仕組みがあります。ターゲットプロパティ CXX_CLANG_TIDY（およびそれを初期化する変数 CMAKE_CXX_CLANG_TIDY）です。

# CMakeLists.txt
set(CMAKE_CXX_CLANG_TIDY
    "clang-tidy;--warnings-as-errors=bugprone-*")

値は セミコロン区切りのコマンドライン です。CMake はここに対象ソースファイルを足し、さらに -- の後ろに完全なコンパイラコマンドラインを付けて起動します。第12章の「形態A」がビルドシステムによって自動生成される、と考えると分かりやすいはずです。

項目内容
対応ジェネレータMakefile 系と Ninja が、コンパイラと一緒にこのツールを実行する
導入バージョンCMake 3.6
引数の渡り方ソースファイル＋ -- ＋完全なコンパイラコマンドライン
CMake 3.25 以降指定に -p が含まれる場合は -- を付けず、コンパイルデータベース参照に切り替わる
経路B の性格

この方式の価値は「解析を忘れられなくなる」ことです。ビルドが成功したなら解析も走っています。CI の門番として優秀です。一方、日常の開発ビルドに入れると、第13章で測ったとおりの時間増がそのまま乗ります。CI 用のプリセットにだけ入れるのが実践的です。

14.4 経路C：コンパイルデータベースを作る

第12章の「形態B」で使う compile_commands.json は、CMake が生成できます。

> cmake -S . -B out\build\ninja -G Ninja -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
ジェネレータの制約

CMake の公式ドキュメントは CMAKE_EXPORT_COMPILE_COMMANDS についてこう述べています。「このオプションは Makefile ジェネレータと Ninja ジェネレータでのみ実装されている。他のジェネレータでは無視される」。

つまり Visual Studio ジェネレータ（-G "Visual Studio 17 2022" のような指定）では compile_commands.json は生成されません。エラーも出ず、ただファイルができないだけです。Windows で作るなら Ninja ジェネレータを使ってください。

生成したら、第12章の形態B で使えます。

> clang-tidy TidyLab\config_loader.cpp -p out\build\ninja

-p にはディレクトリを渡します（ファイル名ではありません）。-- は不要です。

MSBuild プロジェクトでも DB がほしいとき

.vcxproj ベースのプロジェクトには、compile_commands.json を生成する標準の仕組みがありません。第5部で clang-query を使うときに DB があると便利なので、選択肢を挙げておきます。

  • 解析用に CMake + Ninja の構成を別に用意する（同じソースを指す最小の CMakeLists.txt を書く）
  • DB を使わず、-- 方式で通す（第12章）。小さなプロジェクトならこれで十分

本書のハンズオンは -- 方式でも進められるように書いてあります。

14.5 MSBuild との設定対応表

やりたいことMSBuild（第13章）CMake
解析を有効にするプロパティ「Clang-Tidy を有効にする」enableClangTidyCodeAnalysis（clang-cl 時のみ）／ CMAKE_CXX_CLANG_TIDY
チェックを選ぶプロパティ「Clang-Tidy チェック」clangTidyChecks
実行ファイルを変えるプロパティ「ツール ディレクトリ」CMAKE_CXX_CLANG_TIDY にフルパスを書く
追加引数プロパティ「追加オプション」.clang-tidy の ExtraArgs、または DB に含まれる
解析の中身どちらも .clang-tidy。ここは共通

最終行が重要です。チェックの選択・オプション・カスタムチェックは、ビルドシステムに依存しません。 第2部で作った .clang-tidy はそのまま使えますし、第6部で書くカスタムチェックも同様です。

14.6 【ハンズオン】CMake 構成を作る

HANDS-ON 14　同じソースを CMake からも解析する
  1. 最小の CMakeLists.txt を書く。 TidyLab のソリューション直下に置きます。既存の .vcxproj はそのまま残して構いません。 
    cmake_minimum_required(VERSION 3.25)
project(TidyLab CXX)

set(CMAKE_CXX_STANDARD 23)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)

add_executable(TidyLab
    TidyLab/main.cpp
    TidyLab/config_loader.cpp
)
target_include_directories(TidyLab PRIVATE TidyLab)
  2. Ninja で構成する。 開発者コマンドプロンプトで、 
    cmake -S . -B out\build\ninja -G Ninja
    out\build\ninja\compile_commands.json が生成されたことを確認します。
  3. VS ジェネレータでは生成されないことを確認する。 
    cmake -S . -B out\build\vs -G "Visual Studio 18 2026"
    （ジェネレータ名はお使いのバージョンに合わせてください。）out\build\vs に compile_commands.json が作られないことを確認します。エラーも警告も出ないことが重要な観察点です。
  4. DB の中身を読む。 生成された compile_commands.json を開き、directory / command / file の3つを確認します。command に -I や規格の指定が入っていることを見てください。
  5. DB を使って解析する。 
    clang-tidy TidyLab\config_loader.cpp -p out\build\ninja
    -- なしで動くこと、そして第12章で手動で -std や -I を渡したときと同じ警告が出ることを確認します。
  6. ビルドに組み込む（経路B）。 CMakeLists.txt に次を追加して再構成・ビルドします。 
    set(CMAKE_CXX_CLANG_TIDY "clang-tidy")
    cmake -S . -B out\build\ninja -G Ninja
cmake --build out\build\ninja
    ビルド出力に警告が混ざることと、ビルド時間が増えることを確認します。
  7. プリセットにまとめる。 CMakePresets.json を作り、14.2 節の内容を書きます。Visual Studio でフォルダを開き、構成の切り替えでプリセットが選べることを確認します。
  8. 設定が共通であることを確かめる。 .clang-tidy の Checks を書き換えて、MSBuild ビルドと CMake ビルドの両方で警告の内容が変わることを確認します。これが「解析の中身はビルドシステムに依存しない」という意味です。

この章のまとめ

  • CMake での実行経路は3つ。A：VS の CMake 統合、B：CMAKE_CXX_CLANG_TIDY でビルドに組み込む、C：compile_commands.json を作って外部から回す。
  • 経路A の enableClangTidyCodeAnalysis は clang-cl でビルドするときのみ有効。MSVC ツールセットのままでは走らない。MSBuild とはここが違う。
  • 経路B は Makefile / Ninja ジェネレータでコンパイラと一緒に走る。CMake 3.6 以降。ソースファイルと -- の後ろに完全なコンパイラコマンドラインが渡される。
  • CMAKE_EXPORT_COMPILE_COMMANDS は Makefile / Ninja でのみ実装。Visual Studio ジェネレータでは無視され、ファイルは作られない（エラーも出ない）。
  • compile_commands.json があれば -p でディレクトリを渡すだけで解析できる。ビルドと完全に同じ引数が使われる。
  • チェックの選択・オプション・カスタムチェックは .clang-tidy に集約され、ビルドシステムに依存しない。
