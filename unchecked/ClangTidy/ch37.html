第 37 章

誤検出とどう付き合うか

動くようになった後の話です。自作チェックの偽陽性は、標準チェックのそれとは性質が違います。直せるのが自分たちしかいない。 そして実験的機能である以上、ある日突然、挙動が変わることもある。 放置すれば「うちの静的解析はうるさいだけ」という評判が定着します。そうさせない仕組みを作ります。

37.1 責任の所在が違う

37.2 偽陽性を減らす4つの手段

手段やることいつ使うか
① クエリを絞るunless(...) で除外条件を足す誤検出に共通の構造があるとき
② 対象範囲を狭めるディレクトリ単位の設定で除外（第7章）特定の場所にだけ誤検出が集中するとき
③ 例外の層を作る「ここだけは許す」クラス・名前空間を設け、クエリで除外設計として例外を認めるとき（第33章）
④ NOLINT を許す個別に抑制させる（第9章）①〜③で表現できない個別事情のとき
④に逃げる前に①〜③を検討する

NOLINT が増えているなら、それはルールが実態に合っていないサインです。第9章で「抑制の件数を棚卸しする」と書きました。自作チェックについては、さらに厳しく見てください。自分たちが作ったルールなのに NOLINT だらけ、という状態は設計の失敗です。

37.3 回帰テストを作る

第29章で「実験的機能なのでクエリの記述が変わりうる」と述べました。そして第30章から、期待動作を README.md の表に書き溜めてきました。それを機械が検証する形にします。

検証用ソースに期待を書く

// tests/custom-checks/expect.cpp
#include <cstring>

void bad(char* d, const char* s) {
    strcpy(d, s);                  // EXPECT: custom-no-unsafe-string-copy
}

void good(char* d, const char* s, size_t n) {
    strncpy(d, s, n);              // NO-WARN
}

void alloc() {
    char* buf = new char[16];      // EXPECT: custom-no-raw-owning-pointer
    delete buf;                    // EXPECT: custom-array-delete-mismatch
}

突き合わせるスクリプト

# tests/custom-checks/run_tests.py
import re, subprocess, sys, pathlib

SRC = pathlib.Path(__file__).parent / "expect.cpp"
CMD = ["clang-tidy", "--experimental-custom-checks", str(SRC), "--", "-std=c++23"]

# 1. 期待を読む： 行番号 → 期待するチェック名の集合
expected = {}
for i, line in enumerate(SRC.read_text(encoding="utf-8").splitlines(), start=1):
    m = re.search(r"//\s*EXPECT:\s*(\S+)", line)
    if m:
        expected.setdefault(i, set()).add(m.group(1))

# 2. 実際の警告を読む： 行番号 → 出たチェック名の集合
out = subprocess.run(CMD, capture_output=True, text=True).stdout
actual = {}
for m in re.finditer(r":(\d+):\d+:\s+warning:.*\[([\w\-\.]+)\]", out):
    actual.setdefault(int(m.group(1)), set()).add(m.group(2))

# 3. 突き合わせる
ok = True
for line in sorted(set(expected) | set(actual)):
    exp = expected.get(line, set())
    act = {c for c in actual.get(line, set()) if c.startswith("custom-")}
    if exp - act:
        print(f"NG line {line}: 検出されなかった {sorted(exp - act)}")
        ok = False
    if act - exp:
        print(f"NG line {line}: 予期しない検出 {sorted(act - exp)}")
        ok = False

print("PASS" if ok else "FAIL")
sys.exit(0 if ok else 1)
> python tests\custom-checks\run_tests.py
PASS
100 行に満たないスクリプトの価値

このスクリプトが検出するのは、「昨日まで動いていたものが動かなくなった」です。実験的機能を実務で使う以上、これは必須の保険です。第40章で CI に組み込みます。

37.4 件数を監視する

回帰テストは「期待した箇所で警告が出るか」を見ます。もう一つ、実プロジェクト全体での件数も記録してください。

> clang-tidy --experimental-custom-checks --checks="-*,custom-*" ^
    (対象ファイル群) -- -std=c++23 > custom.log 2>&1
> findstr /c:"[custom-" custom.log | find /c /v ""
件数の変化疑うこと
急に増えたクエリを緩めすぎた／コードベースに新しいパターンが入った
急に減ったクエリが動かなくなった（LLVM 更新、YAML の破損）
じわじわ増えるルールが守られていない。周知か Tier の見直しが必要
ゼロが続く役目を終えた。引退を検討（37.6 節）

37.5 NOLINT の許容ライン

自作チェックに対する NOLINT は、ルールへの異議申し立てとして扱ってください。

// この関数は Windows API のコールバックで、シグネチャを変えられない。
// バッファ長は呼び出し元が MAX_PATH で保証している（仕様書 3.2 節）。
// NOLINTNEXTLINE(custom-no-unsafe-string-copy)
strcpy(dst, src);
3件を超えたら設計を見直す

同じチェックに対する NOLINT が3件を超えたら、その3件の理由を並べて読んでください。 共通の構造があるなら、クエリで除外できるはずです（手段①）。共通点がないなら、ルール自体が広すぎます。

37.6 チェックを引退させる

引退させるときは、削除した理由を docs\clang-tidy-decisions.md に残してください。「なぜこのチェックが不要になったか」は、将来また同じルールを作ろうとしたときに役立ちます。

37.7 【ハンズオン】保守の仕組みを作る

HANDS-ON 37　回帰テストと監視を整える
  1. 検証用ソースを整理する。 これまで作った tests\custom-checks\*.cpp を統合し、expect.cpp にまとめます。各行に // EXPECT: または // NO-WARN を書いてください。
  2. スクリプトを置く。 37.3 節の run_tests.py を tests\custom-checks\ に作り、実行します。 
    python tests\custom-checks\run_tests.py
    PASS になるまで、期待とクエリの両方を調整します。
  3. わざと壊して検出させる。 .clang-tidy のクエリを1つ壊し（第36章の症状④）、スクリプトが FAIL を返すことを確認します。これが「動かなくなったことに気づける」ということです。
  4. 予期しない検出も落ちることを確認する。 NO-WARN と書いた行が検出されるようにクエリを緩め、スクリプトが FAIL になることを確認します。偽陽性の混入も検出できます。
  5. 件数のベースラインを取る。 TidyLab 全体に対してカスタムチェックのみを実行し、件数を記録します。 
    python "C:\Program Files\LLVM\bin\run-clang-tidy" -p out\build\ninja > custom-baseline.log 2>&1
    ただし run-clang-tidy から --experimental-custom-checks を渡す方法を確認してください。 渡せない場合は、対象ファイルを列挙して clang-tidy を直接呼ぶスクリプトを書きます（第29章の経路1）。
  6. 偽陽性を1つ作って対処する。 expect.cpp に、ルールの意図には反しないが検出されてしまうコードを追加します。たとえば、 
    namespace compat {
    // 外部ライブラリとの互換層。ここでは strcpy を許す
    void bridge(char* d, const char* s) { strcpy(d, s); }
}
    これに対して、手段①〜④のどれで対処するかを検討し、実装します。①（クエリで compat 名前空間を除外）が第一候補のはずです。
  7. NOLINT の運用ルールを決める。 37.5 節を参考に、自作チェックに対する NOLINT のルールを docs\ に書きます。 
    ## 自作チェックへの NOLINT
- 理由を必ずコメントで書く（外部要因・仕様書の参照先を含める）
- チェック名を括弧で明示する
- 同一チェックに 3 件を超えたら、ルールの見直しを提起する
  8. 監視の手順を決める。 件数の記録をいつ・誰が取るかを決めます。LLVM を更新したときは必ず取ることを、第22章の図22-3 の手順に追記してください。
  9. 引退の条件を書く。 現在あるカスタムチェックそれぞれについて、「いつ削除するか」を判断記録に追記します。条件が書けないチェックは、そもそも目的が曖昧な可能性があります。

この章のまとめ

  • 自作チェックの偽陽性は直せるのが自分たちだけ。判断材料も自分たちで作る必要がある。
  • 減らす手段は4つ。①クエリを絞る ②対象範囲を狭める ③例外の層を作る ④NOLINT を許す。 ④は最後。
  • 回帰テストを作る。 検証用ソースに // EXPECT: を書き、スクリプトで突き合わせる。100 行に満たないコードで、実験的機能への保険になる。
  • テストは「検出されるべきものが出る」と「出るべきでないものが出ない」の両方を見る。
  • 実プロジェクト全体での件数も記録する。急減はクエリが壊れたサイン。
  • 自作チェックへの NOLINT はルールへの異議申し立て。3件を超えたら設計を見直す。
  • チェックは引退させる。 解析時間・保守コスト・理由の風化がその根拠。削除理由も記録に残す。
