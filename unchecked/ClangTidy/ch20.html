第 20 章

readability-* と命名規則

これまでのモジュールは「正しさ」を扱ってきました。ここからは違います。readability-* が扱うのは好みです。だから技術的な判断より先に、チームの合意が要ります。合意なしにこのモジュールを有効にすると、レビューが宗教戦争になります。逆に、合意さえあれば readability-identifier-naming は本書で最も実用的なチェックの一つです。

20.1 順序を間違えない

20.2 命名規約を設計する

readability-identifier-naming は、識別子の種類ごとに命名形式を指定できます（第8章の図8-2）。設計するときは、次の表を埋める作業だと考えると進みます。

決まった内容を .clang-tidy に落とします。

CheckOptions:
  readability-identifier-naming.ClassCase: 'CamelCase'
  readability-identifier-naming.StructCase: 'CamelCase'
  readability-identifier-naming.EnumCase: 'CamelCase'
  readability-identifier-naming.EnumConstantCase: 'CamelCase'
  readability-identifier-naming.FunctionCase: 'camelBack'
  readability-identifier-naming.MethodCase: 'camelBack'
  readability-identifier-naming.ParameterCase: 'lower_case'
  readability-identifier-naming.VariableCase: 'lower_case'
  readability-identifier-naming.PrivateMemberCase: 'lower_case'
  readability-identifier-naming.PrivateMemberSuffix: '_'
  readability-identifier-naming.ConstantCase: 'UPPER_CASE'
  readability-identifier-naming.NamespaceCase: 'lower_case'
  readability-identifier-naming.MacroDefinitionCase: 'UPPER_CASE'
指定できる形式

lower_case / UPPER_CASE / camelBack / CamelCase / Camel_Snake_Case / camel_Snake_Back / aNy_CasE（何でも許可）などがあります。aNy_CasE は「この種類はチェックしない」を明示したいときに使えます。

20.3 一括リネームの威力と射程

このチェックには自動修正が付いており、定義と参照をまとめて書き換えます。ただし射程には限界があります。第10章のヘッダフィルタと第15章の実行範囲が、そのまま効いてきます。

20.4 構造を整えるチェック

命名以外にも、実用的なものが多数あります。自動修正付きで、意味を変えないものが中心です。

チェック内容
readability-braces-around-statements1行の if 文にも波括弧を付ける
readability-else-after-returnreturn の後の else を削り、ネストを浅くする
readability-isolate-declarationint a, *b; を分割する
readability-simplify-boolean-exprif (x) return true; else return false; → return x;
readability-container-size-emptyv.size() == 0 → v.empty()
readability-container-containsm.count(k) > 0 → m.contains(k)（C++20 以降）
readability-qualified-autoポインタを受ける auto に * を付けて明示する
readability-redundant-string-cstr不要な .c_str() を削る
readability-math-missing-parentheses優先順位が紛らわしい算術式に括弧を足す
readability-use-std-min-maxif (a < b) a = b; → a = std::max(a, b);
readability-duplicate-include重複した #include を削る

複雑さを測る

チェック内容
readability-function-size行数・文数・分岐数・引数の数・ネストの深さ・変数の数（第8章）
readability-function-cognitive-complexity「読んで理解する難しさ」を数値化する。ネストが深いほど重く数える
複雑さの制限には副次効果がある

第17章で見たとおり、フロー解析は関数が短いほど効きます。関数の複雑さに上限を設けることは、可読性の話であると同時に 静的解析の精度を上げる施策でもあります。この二つの理由を並べると、チームの合意が取りやすくなります。

20.5 荒れやすいチェック

チェックなぜ荒れるか
readability-implicit-bool-conversionif (ptr) や if (count) を全部書き換えさせる。件数が膨大になりやすい
readability-identifier-lengthi, x, n が全部引っかかる。除外の正規表現が必須（第8章）
readability-avoid-const-params-in-decls宣言側の const を削らせる。意見が分かれる
readability-uppercase-literal-suffix1.0f → 1.0F。好みの問題で、価値が薄いという意見も多い
readability-suspicious-call-argument引数名と変数名の類似から取り違えを推測する。偽陽性が出やすい

これらは 「入れない」も立派な判断です。第22章で、不採用の理由を記録に残す方法を扱います。

20.6 【ハンズオン】命名規約を確定して適用する

HANDS-ON 20　規約を決め、機械化し、維持する
  1. 現状を把握する。 命名について何も設定していない状態で、既定値のまま走らせて件数を見ます。 
    clang-tidy --checks="-*,readability-identifier-naming" config_loader.cpp config_loader.h -- -std=c++23
    設定していない種類には既定値が使われることを確認してください。意図しない規約が適用されている可能性があります。
  2. 設計シートを埋める。 図20-2 の表を、自分のプロジェクトの実態に合わせて埋めます。既存コードの多数派に合わせるのが、移行コストが最も小さい選択です。
  3. 設定を書く。 20.2 節の CheckOptions を .clang-tidy に追加します。決めていない種類は書かないでください。
  4. 違反を数える。 全体を回して件数を確認します（第15章）。 
    python "C:\Program Files\LLVM\bin\run-clang-tidy" -p out\build\ninja "" > naming.log 2>&1
findstr /c:"identifier-naming" naming.log | find /c /v ""
  5. 提案を先に読む。 --fix を付けずに -export-fixes で書き出し、何ファイルの何箇所が書き換わるかを確認します（第11章の手順3）。 
    python "C:\Program Files\LLVM\bin\run-clang-tidy" -p out\build\ninja -export-fixes naming-fixes
  6. 全体に一度で適用する。 作業ツリーをきれいにしてから、プロジェクト全体を対象に適用します。1ファイルずつ当ててはいけません（図20-3）。 
    python "C:\Program Files\LLVM\bin\run-clang-tidy" -p out\build\ninja -fix
git diff
  7. ビルドで安全網を張る。 ビルドが通ることを確認します。通らなければ、リネームが届かなかった参照があります。図20-3 の右側を確認してください。
  8. 文字列リテラルを確認する。 ログメッセージやエラー文言に古い名前が残っていないか、テキスト検索します。機械は文字列の中を書き換えません。 
    findstr /s /i "Buffer" *.cpp *.h
  9. 構造系チェックを足す。 意味を変えない自動修正のものから追加し、同じ手順で適用します。 
      readability-braces-around-statements,
  readability-else-after-return,
  readability-container-size-empty,
  readability-redundant-string-cstr,
  readability-simplify-boolean-expr
  10. 複雑さの上限を決める。 readability-function-size のしきい値を、現状より少し厳しい値に設定します（第8章）。既存コードが全滅しない値から始めてください。
  11. 維持する仕組みにする。 ここまでの設定を .clang-tidy にまとめ、CI の差分解析（第15章）で新規コードに効かせます。一括適用は一度きり、以後は差分で守る ── これが 20.1 節の④です。

この章のまとめ

  • readability-* は好みを扱う。合意 → 設定 → 一括適用 → CI で維持の順序を守る。合意を警告で作ろうとしない。
  • 命名規約は「識別子の種類 × 命名形式」の表を埋める作業。決めていない種類は設定に書かない（既定値が意図せず効く）。
  • readability-identifier-naming の自動リネームは定義と参照をまとめて書き換えるが、解析対象外のファイル・マクロ・文字列リテラルには届かない。
  • だからプロジェクト全体に一度で適用し、直後にビルドする。1ファイルずつ当ててはいけない。
  • 構造系（braces-around-statements, else-after-return, container-size-empty など）は意味を変えず安全。
  • 関数の複雑さに上限を設けることは、可読性と静的解析の精度の両方に効く。
  • implicit-bool-conversion や identifier-length は荒れやすい。「入れない」も立派な判断。

次章： 第21章「cppcoreguidelines-* / cert-* / misc-*」では、コーディング標準を機械化したモジュール群を扱います。全部入れると破綻する理由と、エイリアスによる二重警告の見分け方が主題です。
