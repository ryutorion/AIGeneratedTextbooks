第 6 章

チェック名の読み方

第5章では「Clang-Tidy チェック」欄に clang-analyzer-* と書きました。あの文字列には明確な文法があります。ワイルドカードで束ね、マイナスで削り、順番で上書きする。この文法を自在に扱えるかどうかが、Clang-Tidy を「使える」か「なんとなく使っている」かの分かれ目です。

6.1 名前の構造

チェック名は モジュール名-チェック名 という2部構成です。チェック名の側はハイフン区切りの単語列になります。

例外が一つあります。clang-analyzer- モジュールだけは、Clang Static Analyzer 側の命名をそのまま引き継ぐため、ドットを含む名前になります。

clang-analyzer-core.NullDereference
clang-analyzer-unix.Malloc
clang-analyzer-cplusplus.NewDelete

ドットの前は Static Analyzer 側の「パッケージ」です。clang-analyzer-core.* のように、ここもワイルドカードで束ねられます。

6.2 グロブの文法

チェックの指定は カンマ区切りのグロブのリスト です。規則は3つだけです。

記法意味
foo-barそのチェックを1つ有効にする
foo-*foo- で始まるチェックをすべて有効にする（* は任意の文字列）
-foo-bar / -foo-*先頭の - で、一致するものを無効化する

そして最も重要な規則が次です。

左から右へ順に適用され、後に書いたものが勝つ

グロブのリストは「フィルタの列」として、書いた順に評価されます。同じチェックが複数のグロブに一致する場合、最後に一致したグロブの符号（有効か無効か）が採用されます。この一点さえ理解していれば、あとは組み合わせるだけです。

順番を間違えるとどうなるか

次の2つは、書いてある要素は同じですが結果がまったく違います。

# ① 意図どおり：bugprone を全部有効にして、1件だけ除外
bugprone-*,-bugprone-easily-swappable-parameters

# ② 意図と違う：除外してから全部有効にしているので、除外が無効化される
-bugprone-easily-swappable-parameters,bugprone-*

②では最後の bugprone-* が bugprone-easily-swappable-parameters にも一致してしまうため、せっかくの除外が打ち消されます。除外は必ず後ろに書く、と覚えてください。

6.3 定石のパターン

実務で使う指定は、だいたい次の型に収まります。

パターンA：白紙から積み上げる（推奨）

-*,bugprone-*,clang-analyzer-*,performance-*

先頭の -* で全部落としてから、必要なモジュールだけを足します。「有効なチェックの集合が指定文字列だけで完全に決まる」 のが利点です。バージョンが上がって新しいチェックが増えても、勝手に有効になりません。チームで使うならこの形にすべきです。

パターンB：全部入れて削る

*,-llvmlibc-*,-fuchsia-*,-altera-*

実験や調査には便利ですが、運用には向きません。バージョンが上がるたびに新しいチェックが勝手に増え、警告件数が予告なく変動します。

パターンC：モジュールの一部だけ

-*,readability-identifier-naming,readability-braces-around-statements

モジュール全体は重いが、特定のチェックだけ使いたいときの形です。

重複するモジュールに注意

cppcoreguidelines-*、hicpp-*、cert-*、google-* には 同じ内容のチェックが別名で入っている ものが多数あります。たとえば hicpp-use-nullptr は modernize-use-nullptr の別名です。両方を有効にすると、同じ箇所に2件の警告が出ます。件数が不自然に多いときは別名の重複を疑ってください。

6.4 指定が意図どおりか確かめる

グロブは書けても、その結果が本当に意図どおりかは別問題です。確かめる手段が2つあります。

--list-checks ── 結果の集合を見る

> clang-tidy --checks="-*,bugprone-*,-bugprone-easily-swappable-parameters" --list-checks
Enabled checks:
    bugprone-argument-comment
    bugprone-assert-side-effect
    ...
    bugprone-use-after-move
    bugprone-virtual-near-miss

ここに bugprone-easily-swappable-parameters が含まれていなければ、除外が効いています。件数を数えるなら次のようにします。

> clang-tidy --checks="-*,bugprone-*" --list-checks | find /c "    "
(有効なチェック数)

--explain-config ── どこで有効になったかを見る

チェックが「なぜ」有効になっているのかを説明させられます。設定ファイルが階層になっていると、これが効きます（第7章）。

> clang-tidy --explain-config
'bugprone-use-after-move' is enabled in the C:\dev\TidyLab\.clang-tidy.
'readability-identifier-naming' is enabled in the command-line option '-checks'.
存在しないチェック名は黙って無視される

bugprone-use-after-mov のようにタイプミスをしても、エラーにはなりません。単に何にも一致しないグロブとして扱われます。「有効にしたはずのチェックが動かない」ときは、まず --list-checks でそのチェックが本当に有効になっているかを確認してください。

6.5 コマンドラインと設定ファイルの関係

第5章では Visual Studio のプロパティに直接チェックを書きました。あの値は、内部的に --checks オプションとして渡されます。一方、第3章でソリューション直下に置いた .clang-tidy にも Checks: があります。この2つはどう合成されるのでしょうか。

公式ドキュメントの --checks の説明にはこう書かれています。「このオプションの値は、.clang-tidy ファイルの Checks オプションの値があれば、その後ろに追記される」。

この仕組みが分かると、第5章のトラブルシュートで触れた現象も説明できます。.clang-tidy に Checks: '-*' と書いた状態で、プロパティに modernize-use-nullptr と入れた場合、実際の評価列は -*,modernize-use-nullptr となり、これは正しく動きます。逆に、プロパティを空にして設定ファイルだけ -* なら、有効なチェックは0件です。

推奨する運用

プロパティ側は空にして、.clang-tidy に一本化する のが最終的な姿です。設定がリポジトリに入り、コマンドラインでも CI でも同じ結果になります。プロパティ側は「一時的にこのチェックだけ足して試す」ための実験場として使います。この移行を第7章で行います。

6.6 【ハンズオン】チェックセットを組み立てる

HANDS-ON 6　グロブの挙動を体で覚える
  1. 全チェック数を数える。 開発者コマンドプロンプトで、 
    clang-tidy --checks=* --list-checks | find /c "    "
  2. モジュール単位で数える。 次の3つを実行し、件数を比べます。 
    clang-tidy --checks="-*,bugprone-*" --list-checks | find /c "    "
clang-tidy --checks="-*,modernize-*" --list-checks | find /c "    "
clang-tidy --checks="-*,readability-*" --list-checks | find /c "    "
  3. 順番の効果を確かめる。 次の2つの件数を比較します。差が1件出るはずです。 
    clang-tidy --checks="-*,bugprone-*,-bugprone-branch-clone" --list-checks | find /c "    "
clang-tidy --checks="-*,-bugprone-branch-clone,bugprone-*" --list-checks | find /c "    "
    後者では除外が打ち消されていることを、実際の一覧でも確認してください。
  4. タイプミスの挙動を確かめる。 
    clang-tidy --checks="-*,bugprone-use-after-mov" --list-checks
    エラーにならず、有効なチェックが0件になることを確認します。
  5. 別名の重複を観察する。 TidyLab のプロパティで「Clang-Tidy チェック」を次にしてビルドし、同じ箇所に2件警告が出ることを確認します。 
    -*,modernize-use-nullptr,hicpp-use-nullptr
  6. 自分のセットを決める。 題材コード config_loader.cpp に対して、次を出発点として警告件数を記録します。 
    -*,bugprone-*,clang-analyzer-*,performance-*
    第22章で、このセットを本格的に育てていきます。

この章のまとめ

  • チェック名は モジュール名-チェック名。clang-analyzer- だけは core.NullDereference のようにドットを含む。
  • 指定はカンマ区切りのグロブ列。* で束ね、先頭の - で除外する。
  • 左から右へ順に適用され、後に書いたものが勝つ。 除外は必ず後ろに書く。
  • 運用では -* で白紙にしてから積み上げる。* で全部入れる形はバージョンアップで挙動が変わる。
  • 存在しないチェック名は黙って無視される。意図どおりかは --list-checks と --explain-config で確認する。
  • コマンドラインの --checks は設定ファイルの Checks の後ろに連結される。だから衝突時はコマンドラインが勝つ。
  • cppcoreguidelines-* / hicpp-* / cert-* には別名の重複が多い。二重警告の原因になる。

次章： 第7章「.clang-tidy 設定ファイルへ移行する」では、プロパティに書いていた設定をファイルに移します。設定ファイルの探索規則と InheritParentConfig による階層的な設定が主題です。
