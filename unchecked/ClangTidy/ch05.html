第 5 章

はじめての Clang-Tidy 実行

準備が終わりました。この章で初めて解析を走らせます。ただし素直には成功しません。Clang-Tidy は 既定でチェックが1つも有効になっていない ため、何もしないと「警告0件」という無意味な結果が返ってきます。この罠を意図的に踏んでから、確実に警告が出る状態を作り、警告の読み方を身につけます。

5.1 プロパティページのどこにあるか

TidyLab プロジェクトのプロパティを開きます。Clang-Tidy に関わる設定は2つのページに分かれています。

5.2 最初の罠 ── 既定ではチェックが0件

「Clang-Tidy を有効にする」にチェックを入れてビルドしてみてください。おそらく何も起きません。

これは故障ではなく仕様です。Clang-Tidy は既定でどのチェックも有効にしません。 数百あるチェックには互いに矛盾するものも、特定のプロジェクトにしか意味のないものも含まれるため、「まず何も有効にしない」が出発点になっています。

したがって、有効にすべきチェックを自分で指定する必要があります。Microsoft の公式ドキュメントも、出発点として clang-analyzer-* を推奨しています。

「警告0件」の三つの意味

解析結果が空だったとき、可能性は3つあります。この区別ができないと、ずっと動いていないツールを信頼し続けることになります。

  • 本当に問題がない
  • チェックが1つも有効になっていない（本節）
  • clang-tidy 実行ファイル自体が見つかっていない、あるいはパースに失敗した（第4章の図4-3、第2章の 2.5 節）

だから最初は「必ず出る警告」で確かめる

ツールが動いていることを先に証明します。ソフトウェアのテストでいう スモークテスト です。次のような、疑いようのないコードを1本用意します。

// samples/ch05_first_run.cpp
#include <cstddef>

void smoke_test() {
    int* p = NULL;        // ← modernize-use-nullptr が必ず反応する
    (void)p;

    char* buf = new char[16];
    delete buf;           // ← new[] に delete。cppcoreguidelines 系が反応する
}

リスト5-1　解析が走っていることを確認するためのスモークテスト用コード

NULL を nullptr に直すべき、という指摘は modernize-use-nullptr が確実に出します。フロー解析も型の複雑な推論も要らない、単純な形の照合だからです（第2章の①方式）。これが出なければ、環境の問題です。

5.3 解析はいつ走り、結果はどこに出るか

バックグラウンド解析とビルド時解析

Visual Studio は既定で、コード分析をバックグラウンドで実行します。ビルドしなくても、編集の区切りで解析が走って波線が付きます。一方［全般］の「ビルドに対するコード分析を有効にする」をオンにすると、ビルドのたびに解析が走り、警告がビルド出力に混ざります。CI に近い挙動を手元で再現したいときはこちらです。速度への影響は第13章で扱います。

5.4 警告の読み方

Clang-Tidy の診断は決まった形をしています。コマンドラインで実行すると、次のように出ます。

実務で一番よく使うのは ⑤ のチェック名 です。この名前があれば、

  • 公式ドキュメントで詳細と根拠を調べられる
  • -checks でそのチェックだけを無効にできる（第6章）
  • // NOLINT(チェック名) でその1箇所だけ抑制できる（第9章）
  • オプションでしきい値を変えられる（第8章）

という具合に、次の行動がすべて決まります。警告を見たら、まずメッセージではなくチェック名を読む 癖をつけてください。

5.5 【ハンズオン】初めての解析を成功させる

HANDS-ON 5-A　スモークテストで「走っていること」を証明する
  1. スモークテスト用ファイルを追加する。 TidyLab プロジェクトに ch05_first_run.cpp を追加し、リスト5-1 の内容にします。
  2. Clang-Tidy を有効にする。 プロパティで 構成プロパティ > コード分析 > 全般 を開き、 「Clang-Tidy を有効にする」を「はい」 にします。
  3. チェックを1つだけ指定する。 構成プロパティ > コード分析 > Clang-Tidy の 「Clang-Tidy チェック」 に次を入力します。 
    modernize-use-nullptr
    最初はあえて1つに絞ります。大量に有効化してから動作確認をすると、切り分けができません。
  4. ビルドする。 エラー一覧の「警告」タブを確認します。次のような警告が出れば成功です。 
    use nullptr [modernize-use-nullptr]
  5. 出なかった場合の切り分け。 出力ウィンドウ（「ビルド」を選択）を開き、clang-tidy の起動に失敗していないか確認します。よくある原因は次のとおりです。
    • 「Windows 用 C++ Clang ツール」が未インストール（第3章）
    • Clang-Tidy ツール ディレクトリの指定ミス（第4章）
    • 設定した構成（Debug/Release、x64/x86）と、ビルドした構成が違う
    • .clang-tidy に Checks: '-*' と書いたまま（第3章の手順8）で、それが優先されている
プロパティの設定と .clang-tidy がぶつかったら

第3章でソリューション直下に置いた .clang-tidy には Checks: '-*'（全部無効）と書きました。プロパティ側の指定と設定ファイル側の指定は合成されるため、環境によっては打ち消し合って何も出なくなります。スモークテストが通らないときは、いったん .clang-tidy の中身を空にして 試してください。両者の優先順位は第7章で正確に扱います。

HANDS-ON 5-B　題材コードに解析をかける
  1. チェックを差し替える。 「Clang-Tidy チェック」を次のように変更します。 
    clang-analyzer-*
    これが Microsoft の推奨する出発点です。フロー解析（第2章の②方式）が有効になります。
  2. ビルドして待つ。 フロー解析は AST マッチングより明確に遅いので、初回は時間がかかります。「解析はタダではない」という感覚をここで掴んでおいてください。
  3. 警告を読む。 config_loader.cpp に対して、fopen の戻り値を確認せずに使っている経路に関する指摘が出るはずです。エラー一覧の「カテゴリ」列でソートすると、チェック名ごとにまとまります。
  4. チェックを足す。 今度は次のように広げます。 
    clang-analyzer-*,bugprone-*,performance-*
    警告が一気に増えます。第1章の表に挙げた問題のうち、いくつが検出されたかを数えてください。
  5. 数を記録する。 このときの警告件数をメモしておきます。第2部でチェックを整理し、第4部で標準チェックを学び、第6部で自作チェックを足していく過程で、この数がどう変わるかを追いかけます。
いきなり * を指定しないこと

Clang-Tidy チェック に * と書けば全チェックが有効になります。しかし実際にやると、数千件の警告が出て、互いに矛盾する指摘（「auto を使え」と「auto を使うな」が同時に出るなど）が並び、解析にも時間がかかり、結局誰も見なくなります。静的解析導入の最も一般的な失敗がこれです。 少数から始めて足していくのが正解で、その具体的な進め方は第22章と第39章で扱います。

5.6 コマンドラインでも同じことをしてみる

IDE の中だけで完結させていると、うまく動かないときに手詰まりになります。同じ解析をコマンドラインからも実行できることを、この段階で見ておきます。

> clang-tidy --checks=modernize-use-nullptr ch05_first_run.cpp -- -std=c++23
ch05_first_run.cpp:5:14: warning: use nullptr [modernize-use-nullptr]
    5 |     int* p = NULL;
      |              ^~~~
      |              nullptr

-- の後ろがコンパイラに渡す引数です。第3章の図3-2 で説明した「Clang 側にも規格を伝える」がここに現れています。-- を書き忘れると、Clang-Tidy はコンパイルデータベースを探しに行って失敗します。この形の詳細は第12章で扱います。

IDE とコマンドラインは同じものを実行している

Visual Studio の Clang-Tidy 統合は、内部でこの clang-tidy.exe を呼んでいるだけです。したがって、IDE で説明のつかない挙動に出会ったら、コマンドラインで再現して切り分けるのが定石になります。逆に、コマンドラインで確立した手順はそのまま CI に持っていけます（第40章）。

5.7 ここまでで手に入ったもの

第1部が終わりました。現在の状態を確認します。

できるようになったことまだできないこと
Visual Studio 上で Clang-Tidy を動かせるチェックを体系的に選べない（第2部）
警告が「本当に走った結果」か切り分けられる設定をファイルで共有できない（第7章）
診断メッセージからチェック名を読める個別の警告を抑制できない（第9章）
コマンドラインでも同じ解析を再現できる自分のルールを書けない（第6部）

次の第2部では、プロパティに直接書いていたチェック指定を .clang-tidy ファイルに移し、オプションで挙動を調整し、必要な箇所だけ抑制する ── つまり「Clang-Tidy を実運用に耐える形に整える」作業に入ります。

この章のまとめ

  • Clang-Tidy は 既定でチェックを1つも有効にしない。有効化しただけでは何も起こらない。
  • 「警告0件」には3つの意味がある。本当に問題がない／チェックが空／ツールが動いていない。まず modernize-use-nullptr のような確実に出るチェックでスモークテストする。
  • 解析はコンパイル成功後に走る。結果はエラー一覧・波線・出力ウィンドウの3か所に出る。動かないときは出力ウィンドウを見る。
  • 診断は ファイル:行:列: warning: メッセージ [チェック名] の形。チェック名がすべての起点。
  • 出発点としては clang-analyzer-*。いきなり * を指定してはいけない。
  • IDE の解析は内部で clang-tidy.exe を呼んでいるだけなので、コマンドラインで再現・切り分けができる。

次章： 第2部に入ります。第6章「チェック名の読み方」では、bugprone-* のようなワイルドカード指定と - による除外を組み合わせて、チェックセットを自在に組み立てられるようにします。
