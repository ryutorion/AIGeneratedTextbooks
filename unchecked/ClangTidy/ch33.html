第 33 章

実践2：型と所有権のルールを縛る

前章は「呼び出し」が対象でした。今回は「宣言」を対象にします。「生ポインタへの new を禁止」「この型はもう使わない」といった、設計に関わるルールです。宣言を対象にすると、型がどう書かれているかで見え方が変わるという新しい難しさが出てきます。

33.1 対象が変わると何が変わるか

33.2 ルール1：生ポインタへの new

第28章のレシピ D-3 を、実運用に耐える形にします。

  - Name: no-raw-owning-pointer
    Query: |
      match varDecl(
        hasType(pointerType()),
        hasInitializer(ignoringImplicit(cxxNewExpr().bind("alloc"))),
        isExpansionInMainFile()
      ).bind("var")
    Diagnostic:
      - BindName: var
        Message: "生ポインタで所有権を持たないでください。std::unique_ptr / std::make_unique を使ってください"
        Level: Warning
      - BindName: alloc
        Message: "ここで確保されています"
        Level: Note

取りこぼしを確認する

このクエリは「変数宣言の初期化式が new」を捕まえます。次のケースは捕まりません。

int* p;
p = new int(1);          // 宣言と代入が分かれている

class Widget {
    int* data_;
public:
    Widget() : data_(new int[16]) {}   // メンバ初期化子リスト
};

void f() {
    consume(new int(1));  // 一時オブジェクトとして渡している
}
取りこぼしをどう扱うか

全部を1つのクエリで捕まえようとすると、式が複雑になり保守できなくなります。実践的な選択肢は3つです。

  • チェックを分ける：no-raw-owning-pointer（宣言）と no-raw-new-in-member-init（メンバ初期化子）を別に作る
  • 対象を広げる：cxxNewExpr そのものを対象にして「new の使用」を全部拾い、例外を除外する
  • 割り切る：最も頻度の高い形だけを捕まえ、残りはレビューに任せる

3番目は敗北ではありません。 「8割を機械が拾い、2割を人間が見る」は、「0割を機械が拾う」より圧倒的に良い状態です。

広く捕まえる版

  - Name: no-raw-new
    Query: |
      match cxxNewExpr(
        isExpansionInMainFile(),
        unless(hasAncestor(cxxMethodDecl(ofClass(cxxRecordDecl(matchesName("Allocator$"))))))
      ).bind("alloc")
    Diagnostic:
      - BindName: alloc
        Message: "new の直接使用は禁止です。std::make_unique / std::make_shared を使ってください"
        Level: Warning

Allocator で終わるクラスの中だけは許す、という例外を入れてあります。「所有権を管理する層」を1か所に集めて、そこだけを例外にするのは、実務でよく使う設計です。

33.3 ルール2：C 形式のメモリ確保

  - Name: no-c-memory-api
    Query: |
      match callExpr(
        callee(functionDecl(hasAnyName("::malloc", "::calloc", "::realloc", "::free"))),
        isExpansionInMainFile()
      ).bind("call")
    Diagnostic:
      - BindName: call
        Message: "C 形式のメモリ管理は禁止です。コンテナまたはスマートポインタを使ってください"
        Level: Warning

第32章と同じ形なので、すぐ書けるはずです。禁止 API のパターンは、対象が変わっても構造が同じだと分かります。

33.4 ルール3：型の移行を進める

実務で最も価値が出るのがこれです。「LegacyString から std::string へ移行中」という状況を、機械に管理させます。

  - Name: no-legacy-string
    Query: |
      match varDecl(
        hasType(cxxRecordDecl(hasName("::LegacyString"))),
        isExpansionInMainFile()
      ).bind("var")
    Diagnostic:
      - BindName: var
        Message: "LegacyString は廃止予定です。std::string を使ってください（移行期限: 2027-03）"
        Level: Warning

33.5 型の書かれ方のゆれ

宣言系ルールで最も注意すべき点です。同じ型でも、書き方によって AST での見え方が変わります。

広く捕まえる書き方

変数だけでなく、引数・メンバ・戻り値まで含めたい場合は、対象ノードを増やします。

  # 変数・引数・メンバのいずれかで使われている
  - Name: no-legacy-string-decl
    Query: |
      match namedDecl(
        anyOf(varDecl(), parmVarDecl(), fieldDecl()),
        hasType(cxxRecordDecl(hasName("::LegacyString"))),
        isExpansionInMainFile()
      ).bind("decl")
    Diagnostic:
      - BindName: decl
        Message: "LegacyString は廃止予定です。std::string を使ってください"
        Level: Warning
必ず clang-query で確認する

上のような組み合わせは、書けるかどうかがバージョンに依存します。 Matcher の組み合わせに制約がある場合、clang-query がその場でエラーを出します（第24章）。動かなければ、チェックを分けて素直に書いてください。1つの凝ったクエリより、3つの素直なクエリのほうが保守できます。

33.6 【ハンズオン】所有権のルールを作る

HANDS-ON 33　宣言系ルールを組み立てる
  1. 網羅的な検証ファイルを作る。 tests\custom-checks\ownership.cpp に、図33-3 の全パターンを書きます。 
    #include <memory>
#include <vector>
#include <cstdlib>

struct LegacyString { char buf[64]; };
using LStr = LegacyString;
LegacyString makeLegacy();

struct Allocator {                       // 例外にする層
    int* create() { return new int(1); } // 検出しない
};

void cases() {
    int*  a = new int(1);                // 検出：宣言＋new
    auto* b = new int(2);                // 検出：auto* でも同じ
    int*  c;
    c = new int(3);                      // 検出しない（取りこぼし）
    auto  d = std::make_unique<int>(4);  // 検出しない
    void* m = malloc(16);                // 検出：C 形式
    free(m);                             // 検出：C 形式

    LegacyString s1;                     // 検出：型
    LStr         s2;                     // 要確認：エイリアス
    auto         s3 = makeLegacy();      // 要確認：auto
    std::vector<LegacyString> v;         // 要確認：コンテナの中身
}

void param(LegacyString s) {}            // 要確認：引数

struct Holder {
    LegacyString member;                 // 要確認：メンバ
    int*         owned = new int(5);     // 要確認：メンバ初期化子
};
  2. 1パターンずつ確認する。 clang-query で、33.2 節のクエリを実行します。 
    clang-query ownership.cpp -- -std=c++23
    set output diag
m varDecl(hasType(pointerType()), hasInitializer(ignoringImplicit(cxxNewExpr())), isExpansionInMainFile())
    a と b が検出され、c と d が検出されないことを確認します。
  3. 型のゆれを確認する。 
    m varDecl(hasType(cxxRecordDecl(hasName("::LegacyString"))), isExpansionInMainFile())
    s1 / s2 / s3 のうち、どれが検出されるかを実際に確認してください。図33-3 の予想と一致するかを見ます。
  4. 例外を作る。 Allocator クラスの中の new を除外する条件を書き、create() が検出されないことを確認します。 
    m cxxNewExpr(isExpansionInMainFile(), unless(hasAncestor(cxxMethodDecl(ofClass(cxxRecordDecl(matchesName("Allocator$")))))))
    ofClass が使えない場合は、hasAncestor(cxxRecordDecl(matchesName("Allocator$"))) でも試してください。 エラーメッセージを読んで調整するのが第24章の流儀です。
  5. 3つのチェックを設定ファイルに書く。 33.2 / 33.3 / 33.4 節の内容を .clang-tidy の CustomChecks に並べます。第32章のチェックも残したままにしてください。5つ以上のカスタムチェックが並んだ状態になります。
  6. 件数を突き合わせる。 
    clang-tidy --experimental-custom-checks ownership.cpp -- -std=c++23
    clang-query での確認結果と一致することを確認します。
  7. Note の位置を確認する。 no-raw-owning-pointer の警告について、warning: が変数宣言を、note: が new 式を指していることを確認します。列番号まで見てください。
  8. 移行計画を書く。 docs\clang-tidy-decisions.md に、no-legacy-string の Tier 遷移計画を書きます（図33-2）。 
    ## custom-no-legacy-string
- 現在: Tier 2（差分解析のみ）　残件 87
- Tier 1 に上げる条件: 残件 20 以下
- Tier 0 に上げる条件: 残件 0
- チェック削除の条件: LegacyString 型そのものを削除したとき
  9. 期待動作を記録する。 tests\custom-checks\README.md の表を更新します。「要確認」だったパターンについて、実際にどうだったかを必ず書いてください。 これが次にクエリを書くときの資産になります。

この章のまとめ

  • 宣言系ルールは、呼び出し系と違って型の書かれ方のゆれを扱う必要がある。
  • auto、型エイリアス、コンテナの要素型、引数・メンバ ── 全パターンを検証ファイルに書いて、1つずつ確認する。 推測しない。
  • 取りこぼしは必ず出る。「8割を機械が拾う」は「0割」より圧倒的に良い。 割り切りは敗北ではない。
  • 「所有権を管理する層」を1か所に集め、そこだけを例外にするのは実務的な設計。
  • 型の移行は、チェックの Tier 遷移として管理できる。 Tier 2 → Tier 1 → Tier 0 → 削除。
  • チェックは永続する必要がない。役目を終えたら削除する。
  • 凝った1つのクエリより、素直な3つのクエリのほうが保守できる。
