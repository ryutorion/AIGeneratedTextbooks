第 28 章

Matcher レシピ集

第5部の締めくくりです。実務で頻出するパターンを、そのまま使える形で揃えます。第6部で書くカスタムチェックは、ほぼすべてこのレシピの組み合わせになります。すべて clang-query で動作を確認してから使ってください ── これは本書を通じての鉄則です。

28.1 レシピの読み方

レシピは出発点であって完成品ではない

Matcher の名前や引数は、LLVM のバージョンによって追加・変更されます。本書のレシピをそのまま貼るのではなく、必ず clang-query で実行して件数を確認し、自分のコードベースに合わせて調整してください。 名前が存在しなければその場でエラーが出ます（第24章)。

28.2 A. 呼び出しを捕まえる

A-1　特定の関数の呼び出し
callExpr(callee(functionDecl(hasName("::strcpy")))).bind("call")

最も基本。:: を付けてグローバルの関数に限定する（第27章）。第32章の土台。

A-2　禁止 API のリスト
callExpr(callee(functionDecl(
  hasAnyName("::strcpy", "::strcat", "::sprintf", "::gets")
))).bind("call")

チームの禁止リストをそのまま並べる。増えたらここに足すだけ。

A-3　名前のパターンで捕まえる
callExpr(callee(functionDecl(
  matchesName("^::Legacy[A-Z]")
))).bind("call")

「Legacy で始まる関数はすべて非推奨」のような規約に。正規表現が使える。

A-4　特定クラスのメンバ関数の呼び出し
cxxMemberCallExpr(
  on(hasType(cxxRecordDecl(hasName("::Widget")))),
  callee(cxxMethodDecl(hasName("resize")))
).bind("call")

on(…) は「どのオブジェクトに対して呼んでいるか」へ移る Traversal Matcher。

A-5　戻り値を無視している呼び出し
callExpr(
  callee(functionDecl(hasName("::fopen"))),
  hasParent(compoundStmt())
).bind("call")

親が compoundStmt（＝文としてそのまま置かれている）なら、戻り値はどこにも使われていない。

A-6　特定の引数を渡している呼び出し
callExpr(
  callee(functionDecl(hasName("::memset"))),
  hasArgument(1, integerLiteral(equals(1)))
).bind("call")

「memset の第2引数に 1 を渡している」＝引数の順序を間違えている疑い。

28.3 B. 型と変数

B-1　非推奨の型の変数
varDecl(hasType(cxxRecordDecl(hasName("::LegacyString")))).bind("var")

型の移行を進めるときに使う。残っている箇所を一覧できる。

B-2　生ポインタのメンバ変数
fieldDecl(hasType(pointerType())).bind("field")

所有権の所在が曖昧な箇所を洗い出す。件数が多いはずなので、除外条件と併用する。

B-3　初期化されていないローカル変数
varDecl(
  hasLocalStorage(),
  unless(hasInitializer(anything())),
  unless(isImplicit())
).bind("var")

unless(hasInitializer(anything())) で「初期化式を持たない」を表現する。

B-4　特定の型を値で受け取る引数
parmVarDecl(hasType(cxxRecordDecl(hasName("::HeavyData")))).bind("param")

コピーコストの高い型を値渡ししている箇所。performance-* より対象を限定できる。

28.4 C. クラスと継承

C-1　特定の基底クラスの派生クラス
cxxRecordDecl(isDerivedFrom(hasName("::Component"))).bind("cls")

フレームワークの規約を機械化する出発点。

C-2　命名規約（基底クラスに応じた接尾辞）
cxxRecordDecl(
  isDerivedFrom(hasName("::Component")),
  unless(matchesName("Component$")),
  isExpansionInMainFile()
).bind("cls")

標準チェックでは表現できない、チーム固有のルールの典型。 第34章で扱う。

C-3　仮想関数を持つのに仮想デストラクタがない
cxxRecordDecl(
  isDefinition(),
  hasMethod(isVirtual()),
  unless(hasMethod(cxxDestructorDecl(isVirtual())))
).bind("cls")

cppcoreguidelines-virtual-class-destructor と同趣旨。自作すると仕組みが分かる。

C-4　public なメンバ変数
fieldDecl(isPublic(), hasParent(cxxRecordDecl(unless(isStruct())))).bind("field")

「struct は許すが class では許さない」といった細かい規約が表現できる。

28.5 D-1. メモリと所有権

D-1　new[] と delete の不一致
cxxDeleteExpr(
  unless(isArrayForm()),
  has(ignoringImplicit(declRefExpr(to(varDecl(
    hasInitializer(ignoringImplicit(cxxNewExpr(isArray()).bind("alloc")))
  )))))
).bind("del")

第27章で完成させたもの。2か所を bind して、警告と note を出し分ける（第35章）。

D-2　C 形式のメモリ確保
callExpr(callee(functionDecl(
  hasAnyName("::malloc", "::calloc", "::realloc", "::free")
))).bind("call")

C++ コードで C の確保関数を使っている箇所。

D-3　生ポインタへの new
varDecl(
  hasType(pointerType()),
  hasInitializer(ignoringImplicit(cxxNewExpr()))
).bind("var")

「スマートポインタを使え」という規約の機械化。第33章で扱う。

28.6 D-2. 制御構造

D-4　if の条件式で代入している
ifStmt(hasCondition(
  binaryOperator(hasOperatorName("="))
)).bind("if")

== と書くつもりの書き間違い。bugprone-assignment-in-if-condition と同趣旨。

D-5　空の catch ブロック
cxxCatchStmt(has(compoundStmt(statementCountIs(0)))).bind("catch")

例外を握りつぶしている箇所。

D-6　特定の関数の中だけを対象にする
callExpr(
  callee(functionDecl(hasName("::malloc"))),
  hasAncestor(functionDecl(matchesName("^::render")))
).bind("call")

「描画パスの中では動的確保を禁止」のような、文脈に依存するルール。

28.7 E. 除外の技法

どのレシピも、そのままでは大量にマッチします。除外条件を重ねて実用的な件数まで落とします。

除外条件効果
isExpansionInMainFile()ヘッダ由来を除外。ほぼ常用
unless(isExpansionInSystemHeader())システムヘッダのみ除外（自作ヘッダは残す）
unless(isInStdNamespace())std 名前空間の中を除外
unless(isImplicit())コンパイラが生成したノードを除外
unless(hasAncestor(functionDecl(matchesName("Test"))))テスト関数の中を除外
unless(isExpansionInFileMatching("generated"))生成コードのファイルを除外

28.8 リファレンスの引き方

レシピにないものを書きたくなったときの調べ方です。第25章の三分類が、そのまま検索の道具になります。

28.9 【ハンズオン】第6部の材料を揃える

HANDS-ON 28　3つのルールをクエリにする
  1. 題材を用意する。 samples\ch28_rules.cpp を作ります。各ルールについて、検出されるべきコードと、検出されるべきでないコードを両方入れるのが要点です。 
    #include <cstring>
#include <cstdlib>
#include <memory>

class Component { public: virtual ~Component() = default; };
class RenderComponent : public Component {};   // OK：接尾辞あり
class Physics : public Component {};           // NG：接尾辞なし
class Helper {};                               // 対象外：Component 派生ではない

void bad(char* dst, const char* src) {
    strcpy(dst, src);                          // NG
}
void good(char* dst, const char* src, size_t n) {
    strncpy(dst, src, n);                      // OK
}

void alloc() {
    int*  raw   = new int(1);                  // NG：生ポインタへの new
    auto  smart = std::make_unique<int>(1);    // OK
    void* mem   = malloc(16);                  // NG
    free(mem);
}
  2. 準備する。 
    clang-query ch28_rules.cpp -- -std=c++23
    set traversal IgnoreUnlessSpelledInSource
set output diag
  3. ルール1：禁止 API。 レシピ A-2 を使い、strcpy がマッチし、strncpy がマッチしないことを確認します。 
    m callExpr(callee(functionDecl(hasAnyName("::strcpy", "::strcat", "::sprintf"))), isExpansionInMainFile()).bind("call")
    期待件数は1件です。 合わなければ条件を見直してください。
  4. ルール2：生ポインタへの new。 レシピ D-3 を使い、raw がマッチして smart がマッチしないことを確認します。 
    m varDecl(hasType(pointerType()), hasInitializer(cxxNewExpr()), isExpansionInMainFile()).bind("var")
  5. ルール3：命名規約。 レシピ C-2 を使い、Physics だけがマッチすることを確認します。 
    m cxxRecordDecl(isDerivedFrom(hasName("::Component")), unless(matchesName("Component$")), isExpansionInMainFile()).bind("cls")
    RenderComponent と Helper がマッチしないことが重要な確認点です。
  6. bind の位置を確認する。 3つそれぞれについて、note: "…" binds here がソースの意図した位置を指しているか確認します。第26章の失敗パターンを思い出してください。
  7. 暗黙ノードに備える。 set traversal AsIs に戻して同じクエリを実行し、どれが動かなくなるかを確認します。動かなくなったものは、ignoringImplicit() を使った形に書き換えてください。これが設定ファイルに持っていける形です（第27章 27.2 節）。
  8. コストを測る。 
    set enable-profile true
    3つのクエリの実行時間を記録します。hasAncestor / hasDescendant を含むクエリと比べてみてください。
  9. 保存する。 queries\ に3つのクエリファイルを作ります。それぞれに、
    • 何を検出したいか（日本語のコメント）
    • 期待される件数
    • マッチしてはいけない例
    を書いておいてください。これがそのまま、第6部でカスタムチェックを書くときの仕様書になります。

第5部の終わりに

独自ルールを書くための土台が揃いました。

  • AST の形を読め、ノード名から Matcher 名を導ける（第23章）
  • clang-query で対話的に試行錯誤できる（第24章）
  • Node / Narrowing / Traversal の三分類でクエリを組み立てられる（第25章）
  • bind で診断を出す位置を指定できる（第26章）
  • 暗黙ノードを越え、マッチしない／しすぎるときのデバッグ手順を持っている（第27章）
  • 頻出パターンをレシピとして持っている（第28章）

そして手元には、clang-query で動作確認済みの3つのクエリがあります。

第6部では、これを .clang-tidy の CustomChecks に書き移します。C++ のコードは一行も書きません。設定ファイルにクエリと診断メッセージを書くだけで、あなたのチームにしか存在しないルールが、Visual Studio のエラー一覧に警告として出るようになります。

この章のまとめ

  • レシピは A：呼び出し／B：型と変数／C：クラスと継承／D：所有権と制御 の4分類。E：除外はすべてに重ねて使う。
  • レシピはそのまま貼らず、必ず clang-query で件数を確認してから使う。
  • 関数名は :: を付けて完全修飾で指定する。
  • 除外は重ねる。isExpansionInMainFile() → unless(isInStdNamespace()) → unless(isImplicit()) → テスト・生成コードの順で件数を落とす。
  • 除外しすぎに注意。 条件を足すたびに「検出したい実例」が消えていないか確認する。
  • リファレンスはノード型ごとに整理されている。AST を先に見てノード型を決めれば、探す範囲が絞れる。
  • クエリファイルには「何を検出したいか」「期待件数」「マッチしてはいけない例」を書く。これが第6部の仕様書になる。
