第 38 章

カスタムチェックを配布する

第6部の最終章です。自分の手元で動くチェックを、チーム全体・複数のプロジェクトに行き渡らせます。C++ 実装と違ってビルド成果物の配布は要りませんが、配るべきものはゼロではありません。 何を、どう配るかを整理します。

38.1 配るべき三つのもの

38.2 リポジトリ内の配置

設定を1つの巨大な .clang-tidy に押し込むと、レビューも保守も難しくなります。役割で分けます。

MyProject\ ├─ .clang-tidy ← 標準チェック＋カスタムチェック（Tier 0/1） ├─ tools\ │ ├─ clang-tidy-diff.yml ← Tier 2 用（第22章） │ ├─ analyze-all.cmd ← 全体解析（--experimental-custom-checks 込み） │ └─ analyze-diff.cmd ← 差分解析 ├─ tests\ │ ├─ .clang-tidy ← カスタムチェックを無効化 │ └─ custom-checks\ │ ├─ expect.cpp ← 回帰テスト用ソース（第37章） │ ├─ run_tests.py ← 回帰テストスクリプト │ └─ README.md ← 期待動作の表 ├─ third_party\ │ └─ .clang-tidy ← Checks: '-*' └─ docs\ ├─ clang-tidy-decisions.md ← 採用・不採用の判断記録（第22章） └─ clang-tidy-troubleshooting.md ← 切り分け手順（第36章）

38.3 階層で共有する

複数のモジュールがある大きなリポジトリでは、第7章の InheritParentConfig が効きます。

38.4 複数リポジトリで共有する

組織全体でルールを共有したい場合、方法は3つです。

方法やり方長所短所
コピー各リポジトリに .clang-tidy を複製単純。依存関係がない更新が行き渡らない。差異が生まれる
サブモジュール設定用リポジトリを git submodule で取り込む更新を取り込める。版を固定できるsubmodule の運用が要る
生成共通部分＋固有部分から .clang-tidy を生成するスクリプト柔軟。差分が明示できる生成物と原本の二重管理
まずはコピーでよい

リポジトリが3つまでなら、コピーで十分です。仕組みを作るコストが、それによって節約されるコストを上回らないようにしてください。 「更新が行き渡らない」問題が実際に起きてから、次の方法を検討すれば間に合います。

ただし、どの方法でも 「どこが原本か」を .clang-tidy の冒頭コメントに書いてください。 これだけで事故が大きく減ります。

---
# ============================================================
# MyProject 静的解析設定
#   原本: https://internal.example.com/cpp-standards/clang-tidy
#   このファイルを直接編集せず、原本に PR を出してください
#   同期日: 2026-08-29 / 対応 LLVM: 22.1
# ============================================================

38.5 バージョンを固定する

第29章で述べたとおり、Query Based Custom Check は実験的機能です。LLVM のバージョンが揃っていないと、人によって警告の出方が変わります。

場所固定の方法
開発者の環境導入手順書に版を明記。clang-tidy --version の確認をセットアップ手順に入れる
CIコンテナイメージまたはインストールコマンドで版を固定（第40章）
プロジェクト.clang-tidy のコメントに対応バージョンを書く
版が揃わないとどうなるか

古い版の開発者は、カスタムチェックが1つも動きません。 しかもエラーは出ません（第36章の症状①）。「自分の環境では警告が出なかったのに CI で落ちた」という、最も士気を下げる状況が生まれます。導入手順書に版の確認手順を書くことは、必須の作業です。

38.6 導入手順書を書く

新しいメンバーが最短で同じ環境に到達できるようにします。

# docs/setup-static-analysis.md

## 1. LLVM を導入する（必須）
winget install LLVM.LLVM
"C:\Program Files\LLVM\bin\clang-tidy.exe" --version
→ 22.1 以上であること

## 2. カスタムチェックが使えることを確認する
clang-tidy --help | findstr experimental-custom-checks
→ 行が出ること。出なければ手順1をやり直す

## 3. Visual Studio の設定
- 個別コンポーネント「Windows 用 C++ Clang ツール」を導入
- プロパティシート TidyLab.Analysis.props が全構成に追加されていることを確認
- ※ IDE では標準チェックのみ動作します（カスタムチェックは CI で実行）

## 4. 手元で全体解析を実行してみる
tools\analyze-all.cmd

## 5. 回帰テストを実行してみる
python tests\custom-checks\run_tests.py
→ PASS になること

## 困ったとき
docs\clang-tidy-troubleshooting.md を参照

38.7 【ハンズオン】配布可能な状態にする

HANDS-ON 38　チームに渡せる形に整える
  1. ファイルを整理する。 38.2 節の構造に従って、これまで作ったファイルを配置し直します。散らばっている .clang-tidy を整理してください。
  2. 実行スクリプトを作る。 tools\analyze-all.cmd を作ります。--experimental-custom-checks をここに埋め込むのが要点です。 
    @echo off
setlocal
if "%LLVM_BIN%"=="" set LLVM_BIN=C:\Program Files\LLVM\bin

"%LLVM_BIN%\clang-tidy.exe" --version | findstr /c:"LLVM version"
if errorlevel 1 (
    echo LLVM が見つかりません。docs\setup-static-analysis.md を参照してください
    exit /b 1
)

python "%LLVM_BIN%\run-clang-tidy" -p out\build\ninja -j 8 %*
endlocal
    run-clang-tidy 経由で --experimental-custom-checks を渡す方法を確認してください。 渡せない場合は、対象ファイルを列挙して clang-tidy を直接呼ぶ形に書き換えます。
  3. 階層設定を作る。 TidyLab にサブディレクトリを作り、図38-2 の構造を再現します。
    • TidyLab\legacy\.clang-tidy に InheritParentConfig: true と、カスタムチェックの一部を無効化する設定
    • --explain-config で、意図どおりに継承されていることを確認
  4. 原本の所在を書く。 .clang-tidy の冒頭に、38.4 節の形式でコメントを書きます。実在しない URL でも構いません。書く習慣をつけることが目的です。
  5. 導入手順書を書く。 38.6 節を参考に docs\setup-static-analysis.md を作ります。実際に手順どおりに実行して、抜けがないかを確認してください。
  6. 他人になって試す。 別のディレクトリにリポジトリをクローン（またはコピー）し、導入手順書だけを見て環境を再現できるか試します。詰まった箇所が、手順書の不足箇所です。
  7. 版の不一致を再現する。 可能なら、Visual Studio 同梱の古い clang-tidy を LLVM_BIN に指定して実行し、カスタムチェックが静かに動かなくなることを確認します。この体験が、手順書に版の確認を書く動機になります。
  8. チェックリストを作る。 新しいカスタムチェックを追加するときの手順を docs\ に書きます。 
    # カスタムチェックを追加する手順
1. clang-query でクエリを確定させる（期待件数を記録）
2. tests/custom-checks/expect.cpp に検証ケースを追加（EXPECT / NO-WARN）
3. .clang-tidy の CustomChecks に追加
4. python tests/custom-checks/run_tests.py が PASS することを確認
5. tools\analyze-all.cmd で実プロジェクトの件数を確認
6. docs/clang-tidy-decisions.md に Tier と引退条件を記載
7. プルリクエストを出す（レビュー観点: メッセージの分かりやすさ、除外の妥当性）
  9. レビュー観点を決める。 カスタムチェックのプルリクエストで、レビュアーが何を見るべきかを書きます。「メッセージを読んで直せるか」が最重要の観点です。

第6部の終わりに

本書の主題を、最後まで通しました。

  • Query Based Custom Check の仕組みと、実験的機能であることの意味を理解した（第29章）
  • .clang-tidy にクエリを書き、自作の警告を出せるようになった（第30・31章）
  • 禁止 API・所有権・命名規約・多点診断という4つの型を実装した（第32〜35章）
  • 動かないときの切り分け手順を持っている（第36章）
  • 回帰テストと件数監視で、実験的機能を実務で使う保険をかけた（第37章）
  • チームに配布できる形に整えた（第38章）

第1章で「コンパイラが黙る問題がある」と書きました。第4部で標準チェックがその多くを埋めることを見ました。そして第6部で、標準チェックにも埋められない最後の隙間 ── あなたのチームにしか存在しないルール ── を、自分の手で埋められるようになりました。

残るは運用です。第7部で CI に載せ、既存コードベースへ段階導入し、clang-format との役割を整理します。そして第8部で、クエリでは書けないルールに出会ったときの道を示して、本書を終えます。

この章のまとめ

  • 配るべきものは3つ。①設定ファイル（簡単）②LLVM のバージョン（最大の障壁）③実行手順（経路の選択次第）。
  • 設定は役割で分ける。.clang-tidy / Tier 2 用設定 / 実行スクリプト / 回帰テスト / 判断記録 / 切り分け手順。
  • 大きなリポジトリでは InheritParentConfig の階層で共有する。例外がディレクトリ構造に現れるのが利点。
  • 複数リポジトリでは、まずコピーで十分。「どこが原本か」を冒頭コメントに書くだけで事故が減る。
  • 版が揃わないと、古い環境ではカスタムチェックが静かに動かない。 導入手順書に版の確認を必ず入れる。
  • 実行手順はスクリプトに埋め込む。--experimental-custom-checks を人が覚えている状態にしない。
  • 新しいチェックを追加する手順とレビュー観点を文書化する。最重要の観点は「メッセージを読んで直せるか」。

次章： 第7部に入ります。第39章「既存コードベースへ段階導入する」では、本書で作った仕組みを、警告が数千件出るような実プロジェクトに実際に入れていく道筋を扱います。
