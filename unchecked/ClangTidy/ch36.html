第 36 章

カスタムチェックのデバッグ手順

ここまでのハンズオンで、必ず一度は「clang-query では動いたのに、設定ファイルでは何も出ない」に遭遇したはずです。原因は複数あり、しかも どれも静かに失敗します。この章で、切り分けの手順を体系化します。手順を持っていれば、5分で解決するものが1時間になりません。

36.1 静かに失敗する箇所

カスタムチェックは、次のどの段階でも「エラーを出さずに何も起きない」で終わりえます。

36.2 切り分けの手順

上から順に、各段階を確認するコマンドがあります。推測せず、段階ごとに事実を確認してください。

36.3 --dump-config の読み方

段階②の確認が最も情報量があります。設定ファイルがどう解釈されたかが、そのまま出ます。

> clang-tidy --experimental-custom-checks --dump-config notes.cpp -- -std=c++23
---
Checks:  '-*,custom-*'
…
CustomChecks:
  - Name:  array-delete-mismatch
    Query: |
      match cxxDeleteExpr(…
    Diagnostic:
      - BindName: del
        Message: '…'
        Level:   Warning
…
見えること意味
CustomChecks がないフラグを渡していないか、設定ファイルが読まれていない
CustomChecks はあるが自分のチェックがないYAML が壊れているか、別の設定ファイルが使われている（第7章）
チェックはあるが Query が途中で切れているYAML のリテラルブロックのインデントミス
Diagnostic が空インデントがずれてリストとして認識されていない
すべて正しく見える原因は④以降。clang-query に戻る
どの設定ファイルが使われているかを疑う

第7章で見たとおり、設定ファイルは解析対象ファイルの位置から親をたどって探されます。tests\ にも samples\ にも .clang-tidy を置いてきたので、意図しないものが使われている可能性があります。--explain-config で確認してください。

36.4 YAML の罠

罠症状確認方法
タブ文字設定が読まれないエディタで空白を可視化
リテラルブロックのインデント不足Query が空になる--dump-config

36.5 clang-query では動くのに設定では動かない

段階③まで通っているのにマッチしない場合、原因は次のいずれかです。

原因確認対処
set traversal に依存していたclang-query で set traversal AsIs にして同じ式を試すignoringImplicit() 等を式に入れる（第27章）
let で定義した名前を使っているクエリ文字列に let の名前が残っていないか展開して書く
match を書き忘れた／m のまま--dump-config で Query の中身を見るmatch に直す
コンパイルオプションが違うclang-query と clang-tidy で同じ -- 以降を使っているか揃える（第12章）
解析対象ファイルが違うそもそも別のファイルを見ていないか─
BindName の綴り違い--dump-config と Query を突き合わせる直す
最も多いのは走査モード

第27章で「起動したらまず set traversal IgnoreUnlessSpelledInSource」と習慣づけました。その習慣が、設定ファイルへの移行時に牙を剥きます。 clang-query では動いていたのは、そのモードのおかげだったのです。移行前に必ず set traversal AsIs で動作確認してください。

36.6 【ハンズオン】わざと壊して直す

HANDS-ON 36　6つの症状を体験する
  1. 正常動作を確認する。 第35章までに作ったチェックが動く状態から始めます。件数を記録してください。
  2. 症状① フラグを外す。 --experimental-custom-checks を外して実行。警告が消えることを確認したら、図36-2 の①のコマンドで切り分けできることを確認します。
  3. 症状② YAML を壊す。 Query: のインデントを1つ減らして実行。次に --dump-config を実行し、Query がどう見えるかを確認します。
  4. 症状③ 接頭辞を外す。 Checks を '-*,array-delete-mismatch'（custom- なし）にして実行。次に --list-checks で一覧に出てこないことを確認します。
  5. 症状④ 走査モードに依存させる。 クエリから ignoringImplicit() を削除して実行。マッチしなくなることを確認します。次に clang-query で、 
    set traversal IgnoreUnlessSpelledInSource
m cxxDeleteExpr(unless(isArrayForm()), has(declRefExpr(to(varDecl(hasInitializer(cxxNewExpr(isArray())))))))
set traversal AsIs
m cxxDeleteExpr(unless(isArrayForm()), has(declRefExpr(to(varDecl(hasInitializer(cxxNewExpr(isArray())))))))
    を実行し、モードによって件数が変わることを確認します。これが第27章の警告の実証です。
  6. 症状⑤ BindName を間違える。 BindName: del を BindName: dell にして実行。挙動を記録します。
  7. 症状⑥ フィルタで消す。 検証ファイルをヘッダ（.h）に移し、isExpansionInMainFile() のせいで検出されなくなることを確認します。実行末尾の Suppressed N warnings を読み、in non-user code の数を確認してください。
  8. 手順書を作る。 ここまでの体験をもとに、docs\clang-tidy-troubleshooting.md を作ります。 
    # カスタムチェックが動かないとき

1. clang-tidy --help | findstr experimental-custom-checks
2. clang-tidy --experimental-custom-checks --dump-config <file> --
3. clang-tidy --experimental-custom-checks --list-checks <file> --
4. clang-query で set traversal AsIs にして同じ式を実行
5. 実行末尾の Suppressed 行を読む

※ 1〜3 は 30 秒で終わる。必ず先に実行すること。
    この5行が、この章の成果物です。 チームで共有してください。
  9. すべて元に戻す。 壊した箇所を修復し、手順1の件数に戻ることを確認します。

この章のまとめ

  • カスタムチェックは6つの段階で失敗しうる。そのすべてが「警告が出ない」という同じ症状になる。
  • 推測せず、上から順に事実を確認する。①フラグ ②--dump-config ③--list-checks は 30 秒で終わる。
  • --dump-config は設定ファイルがどう解釈されたかをそのまま見せてくれる。最も情報量が多い。
  • 意図しない設定ファイルが使われていないか、--explain-config で確認する。
  • YAML はタブ・インデント・コロン・#・全角スペースで静かに壊れる。エディタで空白を可視化する。
  • clang-query では動くのに設定では動かない原因の第1位は 走査モードへの依存。移行前に set traversal AsIs で確認する。
  • 切り分け手順を文書にしてチームで共有する。

次章： 第37章「誤検出とどう付き合うか」では、動くようになった後の話をします。自作チェックの偽陽性は、標準チェックのそれより厄介です。 直せるのが自分たちしかいないからです。
