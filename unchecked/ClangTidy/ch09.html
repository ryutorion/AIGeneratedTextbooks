第 9 章

警告を抑制する作法

静的解析には必ず誤検出があり、また「分かっていてやっている」コードもあります。それらを個別に黙らせる仕組みが NOLINT です。ただしこれは劇薬で、安易に使うと解析が形骸化します。書式を覚えるのは5分で終わるので、この章の本題は いつ使ってよいか のほうです。

9.1 抑制が正当化される場面

抑制してよいのは、おおむね次の場合です。

場面例
誤検出解析器がフローを追いきれず、実際には起こりえない NULL 参照を指摘した
意図的な逸脱性能上の理由で、あえて規約に反する書き方をしている（測定根拠あり）
外部要因OS やサードパーティ API のシグネチャがそうなっているため避けられない
生成コードツールが生成したソースで、手で直せない
段階導入の途中既存コードに新ルールを入れる過程での一時的な措置（第39章）

逆に、抑制してはいけないのは 「意味が分からないから消した」 場合です。これが積み重なると、警告が出ないことに意味がなくなります。

9.2 三つの書式

抑制コメントは3種類あり、効く範囲が違います。

// ① 同じ行
strcpy(e.name, line);  // NOLINT

// ② 次の1行
// NOLINTNEXTLINE
strcpy(e.name, line);

// ③ 範囲
// NOLINTBEGIN
strcpy(e.name, line);
strcpy(e.value, val);
// NOLINTEND

チェック名を指定する

括弧の中にチェック名を書くと、そのチェックだけを抑制します。括弧なしの裸の NOLINT は、その行のすべてのチェックを止めます。これは強すぎます。

// 悪い：何を黙らせているのか分からない。将来別のバグも隠す
strcpy(e.name, line);  // NOLINT

// 良い：対象が明確
strcpy(e.name, line);  // NOLINT(clang-analyzer-security.insecureAPI.strcpy)

// 複数指定・グロブも使える
foo();  // NOLINT(bugprone-*, readability-magic-numbers)
否定グロブは無視される

公式ドキュメントに明記されています。「否定グロブはここでは無視される。警告を再有効化してしまうことになるため」。つまり // NOLINT(-bugprone-*) のような書き方はできません。抑制コメントは「止める」専用です。

9.3 抑制できないもの

NOLINT は Clang-Tidy の診断を止めるものです。Clang コンパイラ自体のエラー（構文エラー、意味解析のエラーなど）は抑制できません。 公式ドキュメントの言い方では「clang-tidy は正しいコードを必要とするため」です。

第2章 2.5 節で触れた「Clang でパースできないコード」の問題は、NOLINT では解決しません。解析対象から外す（第10章）か、コンパイルオプションを調整する（第12章）必要があります。

マクロの中の警告

マクロ展開の結果として出た警告は、診断がマクロの定義側に付くことも使用側に付くこともあります。NOLINT を置いたのに効かないときは、警告メッセージが指しているファイル・行を正確に読み、そちら側に置いてください。マクロ定義に NOLINT を付けると、そのマクロを使うすべての箇所で抑制が効いてしまう点にも注意が必要です。

9.4 抑制する前に考えること

抑制は最後の手段です。その前に検討すべき選択肢が4つあります。

9.5 抑制の書き方の作法

理由を必ず書く

NOLINT の直後に理由を書く欄はありませんが、隣接するコメントとして残せます。これを義務にしてください。 半年後の自分と、レビュアーのためです。

// この API は Windows SDK のシグネチャ上、非 const ポインタを要求する。
// 呼び出し先が書き換えないことはドキュメントで保証されている。
// NOLINTNEXTLINE(cppcoreguidelines-pro-type-const-cast)
auto* p = const_cast<wchar_t*>(path.c_str());

範囲を最小にする

NOLINTBEGIN〜NOLINTEND は便利ですが、範囲が広がりやすい書式です。「ファイルの先頭で BEGIN、末尾で END」は実質的にそのファイルを解析対象から外すのと同じで、しかも設定ファイルからは見えません。ファイル全体を外したいなら、第7章のディレクトリ単位の設定で明示的に行うべきです。

チェック名を必ず括弧に書く

裸の NOLINT は、将来そこに追加される別のチェックの警告まで隠します。題材コードの strcpy の行に裸の NOLINT を置くと、第32章で作る自作の「禁止 API チェック」まで効かなくなります。

9.6 抑制を可視化する

抑制は増えます。放置すると「解析は通っているが、実は半分が抑制されている」状態になります。定期的に数えてください。

> findstr /s /c:"NOLINT" *.cpp *.h | find /c /v ""
23

> findstr /s /c:"NOLINT" *.cpp *.h | findstr /v "("
(チェック名を書いていない裸の NOLINT を洗い出す)

Clang-Tidy 自身も、抑制した件数を実行の最後に報告します。

> clang-tidy config_loader.cpp -- -std=c++23
...
Suppressed 7 warnings (5 in non-user code, 2 NOLINT).

この行の NOLINT の数が増え続けているなら、ルールが実態に合っていないサインです。第8章のオプション調整か、そもそも Checks から外すことを検討してください。--quiet を付けるとこの統計は出なくなりますが、普段は出したままにしておくことをおすすめします。

「non-user code」とは

統計に出る「in non-user code」は、ヘッダフィルタによって表示されなかった診断の数です。NOLINT による抑制とは別物で、次章の主題になります。この2つの数字が分かれて表示されるのは、切り分けに役立ちます。

9.7 【ハンズオン】抑制を使い分ける

HANDS-ON 9　抑制の効き方を確かめる
  1. 抑制対象を用意する。 .clang-tidy の Checks に readability-magic-numbers が入っている状態で config_loader.cpp をビルドし、4096 / 4095 に警告が出ることを確認します。
  2. 裸の NOLINT を試す。 new char[4096]; の行末に // NOLINT を付けてビルドし、警告が消えることを確認します。
  3. 裸の NOLINT の副作用を確かめる。 Checks に cppcoreguidelines-owning-memory（またはお使いのバージョンで new に反応するチェック）を足してビルドします。裸の NOLINT がそちらの警告まで消してしまう ことを確認してください。
  4. チェック名を指定する。 // NOLINT(readability-magic-numbers) に書き換え、マジックナンバーの警告だけが消え、もう一方は残ることを確認します。
  5. NOLINTNEXTLINE を使う。 行が長くて行末コメントが読みにくい場合を想定し、前の行に移して同じ結果になることを確認します。
  6. 範囲抑制を試す。 load() の while ループ全体を NOLINTBEGIN(readability-magic-numbers) 〜 NOLINTEND(readability-magic-numbers) で囲み、範囲内だけ抑制されることを確認します。確認したら削除します。
  7. 統計を読む。 コマンドラインで解析し、末尾の Suppressed N warnings の行を確認します。 
    clang-tidy config_loader.cpp -- -std=c++23
  8. 棚卸しの練習。 手順で入れた NOLINT を findstr で数え、理由コメントが書かれていないものを洗い出します。最後に、すべて削除して元の状態に戻してください。この章の NOLINT は練習用であり、第10章以降には持ち込みません。
レビューでの合言葉

コードレビューで NOLINT を見つけたら、聞くべきことは一つです。「なぜ指摘が誤りだと言えるのか」。答えられるなら、その答えをコメントに書いてもらう。答えられないなら、それは抑制ではなく修正の対象です。この一問だけで、抑制の質はかなり保てます。

この章のまとめ

  • 抑制が正当なのは、誤検出・意図的な逸脱・外部要因・生成コード・段階導入の途中に限る。
  • 書式は // NOLINT（同じ行）、// NOLINTNEXTLINE（次の行）、// NOLINTBEGIN〜// NOLINTEND（範囲）。
  • 必ず括弧でチェック名を指定する。 裸の NOLINT は将来のチェックまで隠す。否定グロブは無視される。
  • Clang コンパイラ自身のエラーは NOLINT では抑制できない。
  • 抑制の前に、コードの修正 → オプション調整 → チェックの除外 → ディレクトリ単位の除外、を順に検討する。
  • 理由をコメントで残し、範囲は最小にする。抑制の件数は定期的に棚卸しする。
  • 実行末尾の Suppressed N warnings は、NOLINT による抑制とヘッダフィルタによる非表示を分けて教えてくれる。

次章： 第10章「ヘッダファイルの扱い」では、統計に出てきた「non-user code」の正体を扱います。同じヘッダが何度も解析されて同じ警告が重複する問題と、その制御方法が主題です。
