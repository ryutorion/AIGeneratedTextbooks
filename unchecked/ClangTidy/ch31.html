第 31 章

フィールドを正確に理解する

前章で動くものは作れました。この章では、各フィールドの意味と制約を一つずつ正確に押さえます。特に Warning と Note の使い分けは、診断が読み手に届くかどうかを左右します。仕組みが分かっている警告と、分からない警告では、直してもらえる確率がまったく違います。

31.1 全体構造

31.2 Name

公式の説明は「-checks オプションで使えるチェック名」です。custom- 接頭辞は自動で付きます（第30章）。

命名の指針

標準チェックの命名に倣うと、チーム内での一貫性が保てます。

形例使いどころ
no-〜no-raw-new, no-goto禁止するルール
use-〜use-safe-copy代替を促すルール
〜-namingcomponent-naming命名規約
prefer-〜prefer-span推奨するルール
名前は警告の一部として表示される

警告の末尾に [custom-no-raw-new] と出ます。この名前だけで「何を怒られているか」が分かるように付けてください。 custom-check1 のような名前は、半年後に誰も意味を思い出せません。

31.3 Query

公式の説明は「clang-query の文字列」です。押さえるべき点は3つです。

① match から始める

公式の例も match callExpr(...) となっています。前章で扱ったとおり、対話中の略記 m ではなく正式名で書きます。

② 必ず .bind() する

Diagnostic は BindName でノードを指定します。bind していないノードは指せません。 診断を出したい位置には、必ず名前を付けてください。

③ セッション設定は書けない

set traversal などは clang-query のセッションを設定するコマンドであって、Matcher 式ではありません。走査モードに依存するクエリは、ignoringImplicit() などを使って式の中で解決してください（第27章 27.2 節）。

実験的機能であることの反映

公式ドキュメントは「機能は完全に AST マッチャーライブラリに依存しているため、クエリの記述は AST マッチャーの更新に伴って変わりうる」と述べています。設定ファイルに書ける記法の範囲も、バージョンによって変わる可能性があります。 本書の記述と挙動が食い違ったら、まず自分のバージョンのドキュメントを確認してください。

31.4 Diagnostic

公式の説明は「報告する診断のリスト」です。リストであることが重要で、1つのマッチに対して複数の診断を出せます。

BindName

「Query の中で bind されたノードの名前」です。ここで指定した名前のノードのソース位置に、診断が出ます。

Message

「報告するメッセージ」です。書き方が診断の価値を決めます。

自作チェックにはドキュメントページがない

標準チェックなら、警告名で検索すれば公式の解説ページが出ます。自作チェックにはそれがありません。チェック名とメッセージだけが、読み手に与えられる情報のすべてです。 だからメッセージには、詳しい説明への導線（社内 Wiki の項目名など）を書き添える価値があります。

Level

取りうる値は Warning と Note の2つです。

31.5 Warning と Note の設計

公式の例（リスト30-1）を思い出してください。Note が先、Warning が後に書かれていました。順序と役割を整理します。

状況設計
問題が1か所で完結するWarning 1つだけ。Note は不要
原因が別の場所にある問題の場所に Warning、原因の場所に Note
規約違反で、根拠が別にある違反箇所に Warning、基底クラスの宣言などに Note
Note を付けるべきか迷ったら

基準は「読み手が Warning だけを見て、直す場所を特定できるか」です。特定できるなら Note は不要で、むしろノイズになります。new[] と delete の不一致のように、2か所の関係が問題である場合にだけ Note を付けてください。第35章で本格的に扱います。

31.6 よくある間違い

間違い症状
BindName が Query の .bind() と綴りが違うその診断が出ない
.bind() を書き忘れた同上
Level に Error と書いた受け付けられない（値は Warning / Note）。エラーにしたければ WarningsAsErrors を使う
Diagnostic に Note しか書かなかった主たる警告がないため、意図した形にならない
Checks に custom- を付け忘れた何も起きない（第30章の図30-1）
YAML のインデントがずれている設定が読まれない。--dump-config で確認する

31.7 【ハンズオン】フィールドを一つずつ壊す

HANDS-ON 31　各フィールドの効果を確かめる
  1. 基準となるチェックを作る。 samples\.clang-tidy に、第28章のルール2（生ポインタへの new）を書きます。 
    ---
Checks: '-*,custom-*'

CustomChecks:
  - Name: no-raw-new
    Query: |
      match varDecl(
        hasType(pointerType()),
        hasInitializer(ignoringImplicit(cxxNewExpr().bind("alloc"))),
        isExpansionInMainFile()
      ).bind("var")
    Diagnostic:
      - BindName: var
        Message: "生ポインタへの new は禁止です。std::unique_ptr を使ってください"
        Level: Warning
      - BindName: alloc
        Message: "ここで確保されています"
        Level: Note
...
    ch28_rules.cpp に対して実行し、raw だけが検出されることを確認します。
  2. Warning と Note の位置を確認する。 出力を読み、
    • warning: の行が int* raw の位置を指している
    • note: の行が new int(1) の位置を指している
    ことを確認します。列番号まで見てください。
  3. BindName を間違える。 BindName: var を BindName: vars に変えて実行します。どうなるかを観察してください。 診断が消えるのか、エラーになるのかを記録します。確認したら戻します。
  4. bind を消す。 Query の .bind("alloc") を削除し、Diagnostic はそのままにして実行します。同様に挙動を記録します。
  5. Level を変えてみる。
    • 両方を Warning にする → エラー一覧に2行出ることを確認
    • 両方を Note にする → 主たる警告がない状態を確認
    • Error と書いてみる → 受け付けられないことを確認
    確認したら元に戻します。
  6. エラー化する正しい方法を確認する。 設定に次を足し、警告がエラーになることを確認します。 
    WarningsAsErrors: 'custom-no-raw-new'
    Level: Error ではなく、こちらが正解です。
  7. メッセージを改善する。 図31-2 の3要素を意識して、メッセージを書き直します。 
            Message: "生ポインタへの new は所有権が不明確になるため禁止です。std::unique_ptr / std::make_unique を使ってください（詳細: 社内Wiki「メモリ管理規約」）"
    実際に出力してみて、長すぎて読みにくくないかを確認してください。エラー一覧では1行に表示されます。
  8. YAML を壊す。 Diagnostic のインデントを1つずらして実行し、どんなエラーが出るか、あるいは静かに無視されるかを記録します。 
    clang-tidy --experimental-custom-checks --dump-config ch28_rules.cpp -- -std=c++23
    --dump-config で CustomChecks がどう見えるかも確認してください。第36章のデバッグ手順で、この確認が主力になります。
  9. 記録する。 手順3〜5・8 で観察した挙動を、tests\custom-checks\README.md に書き留めます。「間違えたときにどうなるか」を知っていることが、デバッグ速度を決めます。

この章のまとめ

  • Name は -checks で使う名前（custom- は自動で付く）。名前だけで何を怒られているか分かるように付ける。
  • Query は clang-query 文字列。match から始め、診断を出したいノードは必ず .bind() する。セッション設定は書けない。
  • Diagnostic はリスト。1つのマッチに複数の診断を出せる。
  • BindName は Query の .bind() の文字列と一致していなければならない。
  • Message には ①何が問題か ②どうすればよいか ③例外の条件 を書く。自作チェックにはドキュメントページがないので、メッセージがドキュメントを兼ねる。
  • Level は Warning と Note の2つだけ。エラーにしたいときは WarningsAsErrors を使う。
  • Note は「2か所の関係が問題」のときだけ付ける。Warning だけで直す場所が分かるならノイズになる。
