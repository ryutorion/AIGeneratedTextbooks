第 19 章

performance-* ── 余計なコピーを消す

このモジュールは「無駄」を見つけます。ただし 無駄を消すことと速くなることは同じではありません。ホットパスでない場所のコピーを100個消しても、実行時間は1ミリ秒も変わらないことがあります。それでも入れる価値はある ── その理由と、正しい期待値を最初に定めます。

19.1 このモジュールが本当に言っていること

performance-* の警告は、「ここは遅い」ではありません。「ここに、なくても済む仕事がある」です。この違いが分かっていないと、二種類の失敗をします。

失敗中身
過大評価警告を全部潰して「最適化した」と考える。実際は測っていないので、速くなったかどうか分からない
過小評価「どうせ測ってないなら意味がない」と全部無視する。ホットパスの無駄も見逃す

正しい使い方は、「無駄の一覧」として受け取り、そのうちホットパスにあるものを優先して潰すことです。ホットパスがどこかは、静的解析では分かりません。プロファイラの仕事です。

19.2 コピーの三つの発生源

このモジュールの中核は「不要なコピー」の検出です。C++ でコピーが暗黙に起きる場所は、大きく3か所です。

③ は特に効く

for-range-copy は、ループの回数だけコピーが起きます。要素が重い型なら、これだけで目に見える差になることがあります。そして修正が & と const を足すだけで、意味も変わらない。 費用対効果が最も高いチェックの一つです。

19.3 ムーブ関連

チェック指摘内容
performance-move-const-argconst なオブジェクトに std::move を掛けている（ムーブにならずコピーになる）
performance-move-constructor-initムーブコンストラクタなのにメンバをコピー初期化している
performance-no-automatic-moveconst ローカル変数を返しているため、自動的なムーブが効かない
performance-noexcept-move-constructorムーブコンストラクタに noexcept がない
performance-noexcept-destructor / -swap同上（デストラクタ、swap）
noexcept の有無が性能に効く理由

std::vector は再確保のとき、要素のムーブコンストラクタが noexcept ならムーブし、そうでなければ例外安全性を保つためにコピーします。noexcept を1つ書き忘れただけで、コンテナの成長のたびに全要素がコピーされる ── これは「実測しないと気づけないが、静的解析なら一発で分かる」典型例です。

19.4 文字列とコンテナ

チェック指摘内容
performance-faster-string-finds.find("x") のような1文字の文字列検索 → s.find('x')
performance-inefficient-string-concatenationループ内で a = a + b のように連結している（+= にする）
performance-inefficient-vector-operationループで push_back する前に reserve していない
performance-inefficient-algorithm連想コンテナに std::find を使っている（メンバ関数の find を使う）
performance-implicit-conversion-in-loop範囲 for の要素型が実際の型と違い、毎回一時オブジェクトができている

inefficient-algorithm は特に価値があります。std::set に対する std::find は O(n)、メンバの find は O(log n) です。計算量が変わる指摘なので、無駄というより誤りに近い。

19.5 その他

チェック指摘内容
performance-avoid-endlstd::endl → '\n'（endl は毎回フラッシュする）
performance-enum-size列挙型の基底型が値域に対して大きすぎる
performance-type-promotion-in-math-fnfloat に対して double 版の数学関数を使っている
performance-trivially-destructible不要なデストラクタ定義があり、自明破棄でなくなっている
performance-no-int-to-ptr整数からポインタへの変換（最適化を阻害しうる）

19.6 【ハンズオン】題材コードのコピーを消す

HANDS-ON 19　コピーを見つけ、消し、測る
  1. 現状を見る。 題材コードの entries() は std::vector<Entry> を値で返しています。呼び出し側の main.cpp と合わせて解析します。 
    clang-tidy --checks="-*,performance-*" config_loader.cpp main.cpp -- -std=c++23
  2. 呼び出し側を悪化させて確認する。 main.cpp を一時的に次のように書き換え、①②③のすべてが出る状態を作ります。 
    #include "config_loader.h"
#include <print>

static void dump(std::vector<Entry> v) {          // ① 値渡し
    for (auto e : v) {                            // ③ 範囲 for のコピー
        std::println("{} = {}", e.name, e.value);
    }
}

int main() {
    ConfigLoader loader("app.ini");
    if (!loader.load()) return 1;
    auto entries = loader.entries();              // ② 初期化でのコピー
    dump(entries);
    return 0;
}
    解析して、3種類の警告が出ることを確認します。
  3. 自動修正を当てる。 第11章の手順です。作業ツリーをきれいにしてから、 
    clang-tidy --checks="-*,performance-for-range-copy,performance-unnecessary-value-param,performance-unnecessary-copy-initialization" --fix main.cpp -- -std=c++23
git diff
    const auto& が付くだけの、意味を変えない修正であることを差分で確認します。
  4. 根本を直す。 自動修正は呼び出し側を直しましたが、entries() が値返しであること自体は残っています。config_loader.h を変更します。 
    -    std::vector<Entry> entries();
+    const std::vector<Entry>& entries() const;
    .cpp 側も合わせて修正し、ビルドが通ることを確認します。静的解析が指摘するのは症状であって、原因は設計にあることが多いという例です。
  5. noexcept の効果を見る。 検証用に、ムーブコンストラクタを持つ型を作ります。 
    struct Buffer {
    std::vector<char> data;
    Buffer(Buffer&& other) { data = std::move(other.data); }   // noexcept なし
};
    performance-noexcept-move-constructor が反応することを確認し、noexcept を付けて消えることを確認します。
  6. 計算量が変わる指摘を見る。 
    #include <set>
#include <algorithm>
bool has(const std::set<int>& s, int v) {
    return std::find(s.begin(), s.end(), v) != s.end();
}
    performance-inefficient-algorithm が反応することを確認します。これは「無駄」ではなく計算量の誤りです。
  7. 測る。 手順4の修正について、実際に速くなったかを確認します。app.ini のエントリ数を数万件に増やし、entries() を繰り返し呼ぶループを書いて時間を測ってください。「エントリが3件のときは差がない」ことも同時に確認してください。 これが 19.1 節の主張の実証です。
  8. 後片付けと方針決定。 検証用コードを整理し、.clang-tidy に performance-* を加えます。全部入れて問題が少ないモジュールなので、除外は必要になってから考えます。
参照を返すときの寿命に注意

手順4で entries() を参照返しに変えました。これは ConfigLoader が生きている限り有効な参照です。呼び出し側が ConfigLoader より長く参照を保持すると、ダングリング参照になります。コピーを消すと、代わりに寿命の管理という責任が生まれます。 ここは bugprone-dangling-handle（第16章）や clang-analyzer-*（第17章）の守備範囲でもあります。性能と安全性はしばしばトレードオフになる、という点を意識してください。

この章のまとめ

  • performance-* が言っているのは「遅い」ではなく「なくても済む仕事がある」。優先順位はプロファイラが決める。
  • 不要なコピーの発生源は3つ。①引数の値渡し、②初期化、③範囲 for の変数。どれも自動修正がある。
  • for-range-copy は費用対効果が最も高い。& と const を足すだけで意味も変わらない。
  • noexcept の欠落は、コンテナ再確保時にムーブがコピーに落ちる原因になる。実測では気づきにくく、静的解析が得意な領域。
  • inefficient-algorithm は無駄ではなく計算量の誤り。優先度は高い。
  • 静的解析が指摘するのは症状。原因が設計にあることは多い（値返しの API など）。
  • コピーを消すと寿命管理の責任が生まれる。性能と安全性はトレードオフになりうる。
