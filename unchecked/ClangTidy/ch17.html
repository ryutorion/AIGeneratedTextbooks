第 17 章

clang-analyzer-* ── パス感度のある解析

前章までのチェックは、コードの「形」を見ていました。このモジュールだけは違います。プログラムの実行経路を仮想的にたどり、変数がどんな値を取りうるかを追跡します。だから「この分岐を通ったときだけ NULL になる」を見つけられます。強力な代わりに、遅く、見逃しがあり、偽陽性の性質も違います。それらすべてが同じ原理から来ていることを理解します。

17.1 「形」ではなく「経路」を見る

このモジュールの実体は Clang Static Analyzer という独立した解析エンジンです。Clang-Tidy はそれを呼び出し、結果を clang-analyzer- という名前で報告しています。--list-checks で見えるドットを含む名前は、Static Analyzer 側の チェッカーの名前がそのまま出ているものです。

17.2 パッケージ構成

パッケージ扱う領域代表的なチェッカー
core.言語共通の未定義動作core.NullDereference, core.DivideZero, core.CallAndMessage, core.uninitialized.*
cplusplus.C++ 特有の資源管理cplusplus.NewDelete, cplusplus.NewDeleteLeaks, cplusplus.InnerPointer
unix.C 標準ライブラリ・POSIX APIunix.Malloc, unix.MismatchedDeallocator, unix.cstring.*
deadcode.到達しない・使われないコードdeadcode.DeadStores
security.安全性security.insecureAPI.*
optin.既定では無効。明示的に有効化するoptin.cplusplus.VirtualCall など
使える チェッカーは環境によって違う

ターゲットプラットフォームやバージョンによって、有効になるチェッカーは変わります。unix. パッケージ名も、Windows で全部使えるとは限りません。推測せず、自分の環境で列挙してください。

clang-tidy --checks=clang-analyzer-* --list-checks

17.3 診断は「物語」として読む

フロー解析の診断は、警告1行では終わりません。問題に至る経路が note: の連鎖として示されます。 これを読まないと、なぜ警告されたのか理解できません。

偽陽性の判定手順

フロー解析の警告に対しては、次の順で判断します。

  1. Assuming の行をすべて読む。
  2. その仮定の組み合わせが、実際に起こりうるかを考える。
  3. 起こりうるなら → 直す。
  4. 起こりえないなら → なぜ起こりえないかをコードで表現できないか考える（アサート、早期リターン、型で表す）。それでも無理なら NOLINT に理由を添える（第9章）。

4番目が重要です。「解析器には分からないが人間には分かる」情報を、コードに書き足せることは多い。そうすると警告も消えるし、コードも良くなります。

17.4 なぜ遅いのか、なぜ見逃すのか

第13章のハンズオンで、clang-analyzer-* がコストの大半を占めることを測りました。その理由と、見逃しの理由は同じです。

17.5 bugprone-* とは偽陽性の性質が違う

AST 照合（bugprone-* など）パス探索（clang-analyzer-*）
偽陽性の原因ルールが自分のコードに合わない解析器の仮定が現実的でない
対処オプション調整、チェックを外す（第8章）コードで前提を表現する、NOLINT
再現性高い。同じコードなら常に同じ版・コンパイルオプションで変わりうる
見逃しルールの対象外なら出ない（明快）探索の打ち切りで出ないことがある（不明瞭）
速度速い遅い
診断の情報量1行note の連鎖で経路を示す
運用への落とし込み

この違いから、実務での置き場所が決まります。bugprone-* は日常のビルドに、clang-analyzer-* は CI に。 フロー解析は遅く、件数が版で揺れるので、ローカルのビルドを毎回止めるには向きません。一方 CI なら時間をかけられますし、夜間の全体解析（第15章）にちょうど合います。

17.6 【ハンズオン】経路を追う

HANDS-ON 17　パス感度を体感する
  1. 検証用ファイルを作る。 ch17_path.cpp を次の内容で追加します。 
    #include <cstdio>

int* make(bool ok) {
    if (!ok) return nullptr;
    return new int(42);
}

int use(bool ok) {
    int* p = make(ok);
    return *p;               // (A) ok == false の経路で NULL 参照
}

int divide(int a) {
    int d = 0;
    if (a > 10) d = a;
    return 100 / d;          // (B) a <= 10 の経路で 0 除算
}

void maybe_leak(bool early) {
    char* buf = new char[16];
    if (early) return;       // (C) early の経路でリーク
    delete[] buf;
}
  2. フロー解析だけを走らせる。 
    clang-tidy --checks="-*,clang-analyzer-*" ch17_path.cpp -- -std=c++23
    (A)(B)(C) のそれぞれに対して警告が出ることを確認します。チェッカー名（角括弧の中）を書き出してください。
  3. note を読む。 (A) の警告に続く note: の行をすべて読み、
    • どこで ok が false だと仮定されたか（Assuming）
    • どちらの分岐に入ったか（Taking … branch）
    • どこで NULL が返されたか（Returning null pointer）
    を特定します。関数をまたいで追跡していることが読み取れるはずです。
  4. AST 照合では見つからないことを確認する。 同じファイルに bugprone-* だけを当てます。 
    clang-tidy --checks="-*,bugprone-*" ch17_path.cpp -- -std=c++23
    (A)(B)(C) が検出されないことを確認します。これが第2章の①方式と②方式の違いです。
  5. 前提をコードで表現して消す。 divide() を次のように書き換え、警告が消えることを確認します。 
    int divide(int a) {
    if (a <= 10) return 0;   // 前提を明示
    return 100 / a;
}
    NOLINT ではなくコードで解決したという点が重要です。
  6. 解析器を迷わせる。 use() の make(ok) の間に、解析器が中身を知らない外部関数を挟みます。 
    extern void opaque(int**);   // 定義は別の翻訳単位にあるとする

int use(bool ok) {
    int* p = make(ok);
    opaque(&p);              // 解析器は p が何になるか分からない
    return *p;
}
    警告が消えることを確認します。これが「見逃し」の実例です。 解析器はモデル化できない関数に出会うと、それ以上の追跡を諦めます。
  7. コストを測る。 題材コードのプロジェクト全体に対して、bugprone-* のみ、clang-analyzer-* のみ、で実行時間を比較します（第13章の続き）。
  8. 運用方針を決める。 .clang-tidy は bugprone-* 中心にし、clang-analyzer-* は CI 用の設定に回す方針を検討します。具体的な分け方は第22章で確定させます。
「警告0件」の四つ目の意味

第5章で「警告0件」には3つの意味があると書きました。フロー解析を使うと、四つ目が加わります。「解析器が探索を打ち切ったので見つけられなかった」。静的解析はバグがないことの証明ではありません。テストもレビューも、引き続き必要です。

この章のまとめ

  • clang-analyzer-* の実体は Clang Static Analyzer。実行経路を仮想的にたどり、変数の取りうる値を追跡する。
  • だから「この分岐を通ったときだけ壊れる」を、条件つきで特定できる。AST 照合では原理的に不可能。
  • パッケージは core. / cplusplus. / unix. / deadcode. / security. / optin.。使えるものは環境依存なので --list-checks で確認する。
  • 診断は note の連鎖で経路を示す。Assuming の行が偽陽性判定の鍵。
  • 偽陽性は「コードで前提を表現する」ことで消せることが多い。NOLINT はその後。
  • 遅さ・見逃し・版による件数の揺れは、すべてパス爆発と探索の打ち切りという一つの事情から来る。
  • 関数を短くすることは、可読性の話であると同時に解析精度の話でもある。
  • 実務では bugprone-* をローカルに、clang-analyzer-* を CI に置く。
