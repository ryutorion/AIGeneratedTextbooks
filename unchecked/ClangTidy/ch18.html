第 18 章

modernize-* ── C++23 らしく書き直す

性格の異なるモジュールに移ります。modernize-* はほぼすべてのチェックに自動修正が付いています。バグを見つけるというより、一括変換ツールとして使うものです。そして本書の環境設定がここで効いてきます。-std=c++23 を正しく渡せているかどうかで、有効になるチェックの顔ぶれが変わります。

18.1 このモジュールの性格

bugprone-*（第16章）modernize-*
目的バグを見つける書き方を新しくする
自動修正少数派ほぼ全部にある
使い方常時オンにして番人にする一度当てて、終わったら外してもよい
指摘を無視した場合いつか壊れる古いまま。動きはする

この違いから、運用も変わります。modernize-* は 「移行作業として一括で当て、その後は新規コードの番人として最小限だけ残す」 のが実践的です。常時全部オンにしておくと、レビューが「書き方の指摘」で埋まります。

18.2 有効なチェックは -std で変わる

ここが本章で最も重要な点です。modernize-use-nullptr は C++11 以降でしか意味を持ちませんし、modernize-use-std-print は C++23 の std::print があって初めて成立します。Clang-Tidy は解析時の言語規格を見て、成立しないチェックを黙って無効にします。

確認方法

自分の設定で C++23 世代のチェックが本当に有効かは、次で確かめられます。

clang-tidy --checks="-*,modernize-*" --list-checks

ただしこの一覧は「登録されているチェック」であって、規格による無効化は解析時に起こります。確実なのは、printf を1行書いて modernize-use-std-print が反応するかを見ることです。ハンズオンでこれを行います。

18.3 C++23 世代のチェック

本書の環境で新しく使えるものを挙げます。どれも自動修正付きです。

チェック変換内容
modernize-use-std-printprintf / fprintf → std::print / std::println
modernize-use-std-format文字列生成を std::format に
modernize-use-starts-ends-withsubstr や compare による前方・後方一致 → starts_with / ends_with
modernize-use-designated-initializers集成体初期化を指示付き初期化子に
modernize-use-rangesstd::sort(v.begin(), v.end()) → std::ranges::sort(v)
modernize-use-std-numbers円周率などの手書き定数 → std::numbers
modernize-use-integer-sign-comparison符号付き／符号なしの比較 → std::cmp_less など
modernize-min-max-use-initializer-list入れ子の std::max(a, std::max(b, c)) → std::max({a, b, c})
modernize-use-scoped-lockstd::lock_guard → std::scoped_lock
modernize-use-constraintsSFINAE（enable_if）→ requires 節

最後の use-constraints は、テンプレートを多用しているコードでは効果が劇的です。std::enable_if_t の羅列が requires の一行になります。

18.4 基礎的なチェック

チェック変換内容注意
modernize-use-nullptrNULL / 0 → nullptr安全。最初に当てるべき
modernize-use-override仮想関数のオーバーライドに override安全。誤りが露見することがある（それが利点）
modernize-use-usingtypedef → using安全
modernize-use-equals-default空の特殊メンバ関数 → = default安全
modernize-use-default-member-initコンストラクタでの初期化 → メンバ宣言での初期化おおむね安全
modernize-use-emplacepush_back(T(x)) → emplace_back(x)意味が変わる場合がある
modernize-loop-convert添字ループ → 範囲 forループ内で添字を使っていると変換されない
modernize-pass-by-valueconst T& → 値渡し + std::move性能が落ちることがある（第11章）
modernize-make-unique / make-sharednew → std::make_unique など安全
modernize-avoid-c-arrays生配列 → std::array を促す自動修正なし。設計判断が要る
modernize-deprecated-headers<stdio.h> → <cstdio>安全

好みが分かれるもの

  • modernize-use-trailing-return-type：すべての関数を auto f() -> int の形にします。統一されて読みやすいという意見と、冗長という意見が真っ二つです。チームで合意が取れていないなら入れないこと。
  • modernize-use-auto：型を auto に置き換えます。オプション（MinTypeNameLength など）で適用範囲を絞れます。無条件に全部 auto にすると読みにくくなることがあります。
  • modernize-use-nodiscard：[[nodiscard]] を大量に付けます。効果は大きいですが、公開 API では利用側に影響します。
モジュールに関するチェックは扱わない

本書はモジュール（import / export）を使わない方針です（第3章 3.2 節）。したがって、モジュール移行を促す種類のチェックは対象外とします。ヘッダインクルード方式を前提に読み進めてください。

18.5 題材コードを C++23 化する

18.6 【ハンズオン】一括変換を実行する

HANDS-ON 18-A　C++23 世代のチェックが効いているか確かめる
  1. 検証コードを足す。 config_loader.cpp の load() の末尾に、次の1行を追加します。 
        printf("%zu entries loaded\n", entries_.size());
    <cstdio> は既にインクルードされています。
  2. C++23 で解析する。 
    clang-tidy --checks="-*,modernize-use-std-print" config_loader.cpp -- -std=c++23
    std::println への書き換えが提案されることを確認します。
  3. 規格を下げて比べる。 
    clang-tidy --checks="-*,modernize-use-std-print" config_loader.cpp -- -std=c++17
    何も出ないことを確認します。エラーにも警告にもならず、静かに無効化されるのが観察点です。
  4. IDE 側でも確認する。 .clang-tidy の Checks に modernize-use-std-print を足してビルドします。IDE でも警告が出れば、第3章で設定した C++23 の指定が Clang 側にも正しく届いています。出なければ、事前追加オプションに -std=c++23 を明示してください（第12章）。
HANDS-ON 18-B　安全なものから順に当てる
  1. 作業ツリーをきれいにする。 第11章の手順です。コミットしてから始めます。
  2. 第1段：use-nullptr。 
    clang-tidy --checks="-*,modernize-use-nullptr" --fix config_loader.cpp -- -std=c++23
git diff
    差分を読み、ビルドが通ることを確認してコミットします。
  3. 第2段：use-std-print。 
    clang-tidy --checks="-*,modernize-use-std-print" --fix config_loader.cpp -- -std=c++23
git diff
    <print> のインクルードが追加され、printf が std::println になることを確認します。書式文字列の変換まで行われる点を差分でよく見てください。
  4. 第3段：まとめて安全なもの。 
    clang-tidy --checks="-*,modernize-use-using,modernize-use-equals-default,modernize-deprecated-headers,modernize-use-default-member-init" --fix config_loader.cpp config_loader.h -- -std=c++23
    差分を読み、コミットします。
  5. 危険なものを「見るだけ」にする。 --fix を付けずに実行し、提案内容を読みます。 
    clang-tidy --checks="-*,modernize-pass-by-value,modernize-use-emplace,modernize-use-trailing-return-type" config_loader.cpp -- -std=c++23
    pass-by-value の提案について、呼び出し側が左辺値を渡しているか右辺値を渡しているかを確認し、本当に得になるかを自分で判断してください（第11章 11.3 節）。
  6. 自動修正がないものを確認する。 
    clang-tidy --checks="-*,modernize-avoid-c-arrays" config_loader.h -- -std=c++23
    char name[32] が指摘されるが修正案は付かないことを確認します。std::array<char, 32> にするのか std::string にするのかは設計判断であり、機械には決められません。
  7. 移行後の運用を決める。 一括変換が終わったら、modernize-* を全部有効のまま残すか、新規コードの番人として一部だけ残すかを決めます。おすすめは、自動修正が安全で意見が割れないものだけを残すことです。 
    Checks: >
  -*,
  bugprone-*,
  modernize-use-nullptr,
  modernize-use-override,
  modernize-use-using,
  modernize-use-equals-default,
  modernize-use-std-print,
  modernize-use-std-format
一括変換は「一度きりの作業」として計画する

modernize-* を全部有効にしたまま日常運用すると、レビューが書き方の指摘で埋まり、本当に見るべき bugprone-* の警告が埋もれます。移行は移行として、期間を区切って一度やる。 終わったら、新規コードに効かせたいものだけを残す。これが健全な使い方です。

この章のまとめ

  • modernize-* はほぼ全チェックに自動修正がある。バグ検出ではなく一括変換ツールとして扱う。
  • 有効なチェックは解析時の -std で変わる。 規格が届いていないチェックは、エラーも出さずに静かに無効化される。
  • C++23 世代では use-std-print / use-std-format / use-starts-ends-with / use-designated-initializers / use-ranges / use-constraints などが使える。
  • 安全なもの（use-nullptr, use-override, use-using, use-equals-default）から段階的に当てる。
  • pass-by-value と use-emplace は意味や性能が変わりうる。use-trailing-return-type は好みが割れる。
  • avoid-c-arrays のように自動修正がないものは、設計判断が必要という合図。
  • 移行は期間を区切って一度で終わらせ、その後は少数だけ番人として残す。
