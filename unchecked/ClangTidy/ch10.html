第 10 章

ヘッダファイルの扱い

Clang-Tidy は翻訳単位（.cpp 1本）ごとに解析します。ヘッダはその過程で何度も読まれ、その都度警告を生みます。何も設定しないと、同じ警告が10回も20回も並びます。逆に絞りすぎると、ヘッダに書いたコードが一切チェックされなくなります。この章では表示の仕組みを理解し、適切な線を引きます。

10.1 なぜヘッダの警告は重複するのか

C++ のビルドは翻訳単位ごとに独立しています。#include はテキストの取り込みなので、あるヘッダが5つの .cpp から include されていれば、そのヘッダは 5回パースされ、5回解析されます。

これを制御するのが、この章で扱う3つの設定です。

10.2 表示のフィルタは4段構え

ある診断が最終的に表示されるかどうかは、次の順で決まります。

10.3 三つの設定

HeaderFilterRegex

診断を出すヘッダを正規表現で指定します。現在の既定値は '.*'、つまり非システムヘッダはすべて表示されます。

古い記事との食い違いに注意

Web には「header-filter の既定は空なので、ヘッダの警告は表示されない」と説明した記事が多数あります。これは古いバージョンの挙動です。第4章で確認した自分のバージョンで、--dump-config を実行して実際の既定値を確かめてください。既定値がどちらかで、設定の書き方がまったく変わります。

clang-tidy --dump-config | findstr HeaderFilterRegex

既定が '.*' の場合、何もしないとサードパーティのヘッダまで診断対象になります。自分のコードだけに絞るなら、明示的に書きます。

# TidyLab 配下のヘッダだけを対象にする
HeaderFilterRegex: 'TidyLab'

ExcludeHeaderFilterRegex

逆に「これだけ外す」を書きます。HeaderFilterRegex と併用しなければなりません（コマンドラインの --exclude-header-filter は --header-filter と一緒に使う必要がある、と明記されています）。

HeaderFilterRegex: '.*'
ExcludeHeaderFilterRegex: 'third_party|generated|_pb\.h'

「基本は全部見るが、外部と生成物だけは除く」という、実務で最も使いやすい形です。

SystemHeaders

SystemHeaders: false   # 既定。<vector> などの診断を出さない

true にする場面はほとんどありません。標準ライブラリの実装に対する警告を読みたい、という特殊な調査のときだけです。

10.4 正規表現の書き方

これらのオプションは POSIX 拡張正規表現（ERE）で、ヘッダのパス（ファイル名を含む）に対して部分一致 で評価されます。完全一致ではないので、単純な部分文字列を書くだけでもかなり実用になります。

書き方意味
TidyLabパスに TidyLab を含むヘッダ
config_loader\.h$そのファイル名で終わるパス（. はエスケープ）
third_party|vendorどちらかを含む（| は OR）
^C:C ドライブ直下から始まるパス（絶対パス前提なので脆い）
Windows のパス区切り

正規表現の中で \ はエスケープ文字なので、パス区切りをそのまま書くと壊れます。ディレクトリ境界を明示したいときは [\\/] のように両方を許す文字クラスを使うのが無難です。ただし YAML の中でのバックスラッシュの扱いも絡むので、まずは区切り文字を含まない部分文字列（ディレクトリ名だけ）で書くのが確実です。

効いているか確かめる

正規表現は書いた本人でも間違えます。実際に何が表示され、何が抑制されたかは統計行で分かります（第9章）。

> clang-tidy config_loader.cpp -- -std=c++23
...
Suppressed 142 warnings (140 in non-user code, 2 NOLINT).

この in non-user code が、ヘッダフィルタとシステムヘッダ判定によって表示されなかった数です。この数が異常に大きいときは、フィルタが自分のコードまで巻き込んでいる疑いがあります。 逆に、フィルタを緩めたときにこの数が急減し、代わりにサードパーティの警告が溢れることもあります。両方を試して、間の値を探してください。

10.5 それでも重複する問題

フィルタは「表示するかどうか」の制御であって、「重複を除く」機能ではありません。config_loader.h を対象に含めた以上、include している翻訳単位の数だけ同じ警告が出ます。

これに対する現実的な手当ては次の3つです。

  • 気にしない：IDE で作業している間は、同じ箇所の警告が複数並んでも実害は小さい。直せば全部消えます。
  • 集計側で重複排除する：CI では出力を集約する際に「ファイル:行:チェック名」で一意化します（第40章）。
  • 修正の適用時は専用ツールを使う：自動修正を並列実行すると、複数のプロセスが同じヘッダを書き換えようとして壊れます。--export-fixes で修正案を書き出し、clang-apply-replacements で重複を解決しながら適用します（第11章・第15章）。

10.6 行単位で絞る ── --line-filter

もう一段細かい絞り込みとして、ファイルと行範囲を指定するオプションがあります。範囲は両端を含みます。

> clang-tidy --line-filter="[{\"name\":\"config_loader.cpp\",\"lines\":[[20,60]]}]" config_loader.cpp -- -std=c++23

手で書くものではありませんが、「変更した行だけをチェックする」仕組みの土台 になっています。既存コードベースへの段階導入で使う clang-tidy-diff は、内部でこれを使っています（第15章・第39章）。

10.7 【ハンズオン】フィルタを設計する

HANDS-ON 10　ヘッダの見え方を制御する
  1. 既定値を確認する。 
    clang-tidy --dump-config | findstr HeaderFilterRegex
    自分のバージョンでの既定値を記録します。以降の手順は、これを基準に読み替えてください。
  2. ヘッダに問題を仕込む。 config_loader.h の Entry に、警告が出るメンバを追加します。 
    struct Entry {
    char name[32];
    int  value;
    int* raw = NULL;   // ← modernize-use-nullptr が反応する
};
  3. 重複を観察する。 main.cpp と config_loader.cpp の両方がこのヘッダを include している状態でビルドし、エラー一覧に 同じ警告が2件 出ることを確認します。
  4. ヘッダを対象外にする。 .clang-tidy に次を書いてビルドし、ヘッダ由来の警告が消えることを確認します。 
    HeaderFilterRegex: 'nothing_matches_this'
    同時に、config_loader.cpp 内の警告は消えないことを確認してください。メインファイルの診断は常に表示されるからです（図10-2）。
  5. 自分のヘッダだけに絞る。 
    HeaderFilterRegex: 'TidyLab'
    ヘッダの警告が戻ってくることを確認します。
  6. 除外パターンを併用する。 third_party\legacy_api.h を作り、警告が出るコードを入れ、main.cpp から include します。そのうえで、 
    HeaderFilterRegex: '.*'
ExcludeHeaderFilterRegex: 'third_party'
    自分のヘッダの警告は出て、third_party のものは出ないことを確認します。
  7. 統計を読む。 手順4・5・6 のそれぞれで、末尾の Suppressed N warnings (M in non-user code, ...) の M がどう変化したかを記録します。
  8. 後片付け。 手順2で追加した int* raw = NULL; を削除し、.clang-tidy のフィルタ設定を実運用向けの形に整えます。TidyLab では次を採用します。 
    HeaderFilterRegex: '.*'
ExcludeHeaderFilterRegex: 'third_party'
SystemHeaders: false
どこに線を引くか

判断基準は 「そのヘッダを自分たちが直せるか」 です。直せるなら対象に含める。直せない（外部ライブラリ、生成コード、ベンダー提供）なら除外する。「直せるけど今は直さない」は除外ではなく、第39章の段階導入で扱う話です。フィルタで隠すと、直す気がなくなったこと自体が見えなくなります。

この章のまとめ

  • 翻訳単位ごとに解析するため、ヘッダの警告は include された数だけ重複する。これは仕様。
  • 表示は4段のフィルタで決まる。メインファイルの診断は常に表示され、フィルタの影響を受けない。
  • HeaderFilterRegex の現在の既定値は '.*'（非システムヘッダは全部表示）。古い記事は既定が違うので、自分の版で --dump-config して確認する。
  • ExcludeHeaderFilterRegex は HeaderFilterRegex との併用が前提。「全部見て、外部だけ除く」が実務的。
  • 正規表現は部分一致。Windows のパス区切りは扱いが面倒なので、ディレクトリ名だけの部分文字列が確実。
  • フィルタは重複排除ではない。自動修正の重複は --export-fixes と clang-apply-replacements で扱う。
  • 線引きの基準は「自分たちが直せるか」。

次章： 第11章「自動修正を体験する」で第2部が完結します。Clang-Tidy の警告の多くは修正案（FixIt）を伴います。これを安全に当てる手順と、当ててはいけない場面を扱います。
