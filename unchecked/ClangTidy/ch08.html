第 8 章

チェックのオプションを変える

チェックは「有効か無効か」の二択ではありません。多くのチェックは判定を調整するツマミを持っています。「関数が長すぎる」の“長すぎる”が何行なのか、「マジックナンバー」から何を除外するのか、識別子の命名規約はどの形式か ── これらはすべて設定可能です。オプションを使いこなせると、「このチェックは使えない」と諦めていたものが使えるようになります。

8.1 チェック＝判定ロジック＋ツマミ

オプションが役に立つ典型的な場面は次の3つです。

  • しきい値が自分の基準と合わない：「関数は50行まで」がチームの規約なのに、既定値が違う。
  • 正しいのに警告される（偽陽性）：意味のある定数まで「マジックナンバー」と言われる。
  • チームの規約を機械化したい：命名規則を強制する。

8.2 書き方

.clang-tidy の CheckOptions にキーと値の対を並べます。キーは チェック名.オプション名 という形です。

---
Checks: '-*,readability-function-size,readability-magic-numbers'

CheckOptions:
  readability-function-size.LineThreshold: '50'
  readability-function-size.ParameterThreshold: '5'
  readability-magic-numbers.IgnoredIntegerValues: '1;2;3;4;8;16;32;64;'
...
値はすべて文字列として書く

数値も真偽値も、クォートで囲んだ文字列として書くのが安全です（'50'、'true'）。また、複数の値を並べるオプションはセミコロン区切り で、末尾にもセミコロンを付ける流儀が一般的です。カンマではありません。

キーはチェックごとに独立している

オプション名はチェック名で名前空間が切られています。したがって、別名関係にあるチェック（第6章）でも、オプションはそれぞれに設定する必要があります。

# hicpp-function-size は readability-function-size の別名だが、
# オプションはそれぞれ独立して指定する
CheckOptions:
  readability-function-size.LineThreshold: '50'
  hicpp-function-size.LineThreshold: '50'

8.3 何が設定できるかを知る

オプション名を推測で書いても効きません。存在しないオプション名は無視される ので、間違いに気づけません。確実な調べ方は2つあります。

方法1：--dump-config で現在値を全部出す

第7章で見たコマンドです。有効なチェックが持つオプションが、既定値つきで全部並びます。

> clang-tidy --checks="-*,readability-function-size" --dump-config
---
Checks:  '-*,readability-function-size'
...
CheckOptions:
  readability-function-size.BranchThreshold:    '4294967295'
  readability-function-size.LineThreshold:      '4294967295'
  readability-function-size.NestingThreshold:   '4294967295'
  readability-function-size.ParameterThreshold: '4294967295'
  readability-function-size.StatementThreshold: '800'
  readability-function-size.VariableThreshold:  '4294967295'
...

ここに出た名前を、そのままコピーして使うのが最も確実です。

巨大な数値は「無効」の意味

4294967295 は 32bit 符号なし整数の最大値です。「しきい値なし＝このサブチェックは動かない」ことを表しています。つまり readability-function-size は既定では文数（800）しか見ておらず、行数・引数の数・ネストの深さは設定しない限りチェックされません。「有効にしたのに何も出ない」の原因がこれです。

方法2：公式ドキュメントのチェック個別ページ

各チェックには専用のドキュメントページがあり、オプションの一覧・既定値・意味・例が載っています。--dump-config は名前と現在値しか教えてくれないので、意味を知るにはこちらを見ます。第4章で確認したバージョンに対応するドキュメントを見るようにしてください。

8.4 よく使うオプション

関数の複雑さ ── readability-function-size

CheckOptions:
  readability-function-size.LineThreshold: '80'        # 行数
  readability-function-size.StatementThreshold: '100'  # 文の数
  readability-function-size.BranchThreshold: '20'      # 分岐の数
  readability-function-size.ParameterThreshold: '6'    # 引数の数
  readability-function-size.NestingThreshold: '4'      # ネストの深さ
  readability-function-size.VariableThreshold: '20'    # ローカル変数の数

既存コードベースに導入するときは、まず現状より少し厳しい値から始める のが実践的です。いきなり理想値にすると数百件出て、誰も見なくなります（第39章）。

マジックナンバー ── readability-magic-numbers

CheckOptions:
  readability-magic-numbers.IgnoredIntegerValues: '1;2;3;4;8;16;32;64;100;'
  readability-magic-numbers.IgnorePowersOf2IntegerValues: 'true'
  readability-magic-numbers.IgnoredFloatingPointValues: '0.5;1.0;100.0;'

このチェックは既定のままだと大量に反応します。0 と 1 だけ許して他は全部警告、という運用は現実的ではありません。ビットマスクを扱うコードなら IgnorePowersOf2IntegerValues が効きます。

短すぎる識別子 ── readability-identifier-length

CheckOptions:
  readability-identifier-length.MinimumVariableNameLength: '3'
  readability-identifier-length.IgnoredVariableNames: '^[ijkxyzn]$'
  readability-identifier-length.MinimumParameterNameLength: '3'

ループカウンタの i まで警告されると邪魔なので、正規表現で例外を作ります。

命名規約 ── readability-identifier-naming

オプション数が最も多く、最も実用価値の高いチェックです。識別子の種類ごとに 命名形式を指定できます。

題材コードの ConfigLoader に合わせて書くと、次のようになります。

CheckOptions:
  readability-identifier-naming.ClassCase: 'CamelCase'
  readability-identifier-naming.StructCase: 'CamelCase'
  readability-identifier-naming.FunctionCase: 'lower_case'
  readability-identifier-naming.VariableCase: 'lower_case'
  readability-identifier-naming.ParameterCase: 'lower_case'
  readability-identifier-naming.PrivateMemberCase: 'lower_case'
  readability-identifier-naming.PrivateMemberSuffix: '_'
  readability-identifier-naming.ConstantCase: 'UPPER_CASE'
  readability-identifier-naming.NamespaceCase: 'lower_case'

このチェックには 自動修正が付いています。規約に合わない識別子を、参照箇所も含めて一括リネームできます（第11章）。ただし影響範囲が大きいので、扱いには注意が必要です。

8.5 継承時のオプションの扱い

第7章の InheritParentConfig: true のとき、CheckOptions は キー単位でマージ されます。子で指定したキーだけが上書きされ、指定しなかったキーは親の値が残ります。

# ルートの .clang-tidy
CheckOptions:
  readability-function-size.LineThreshold: '80'
  readability-function-size.ParameterThreshold: '6'

# src/legacy/.clang-tidy
InheritParentConfig: true
CheckOptions:
  readability-function-size.LineThreshold: '300'   # ← ここだけ緩める

# legacy 配下での実効値
#   LineThreshold: 300      （子で上書き）
#   ParameterThreshold: 6   （親から引き継ぎ）

Checks が連結だったのに対し、CheckOptions はキー単位の上書きです。この違いを押さえておいてください。

8.6 【ハンズオン】命名規約を機械化する

HANDS-ON 8　オプションで挙動を変える
  1. 既定値を観察する。 開発者コマンドプロンプトで、 
    clang-tidy --checks="-*,readability-function-size" --dump-config
    LineThreshold が 4294967295、つまり事実上無効になっていることを確認します。
  2. しきい値を入れる。 TidyLab\.clang-tidy の Checks に readability-function-size を足し、次を書きます。 
    CheckOptions:
  readability-function-size.LineThreshold: '20'
  readability-function-size.StatementThreshold: '15'
    ビルドすると ConfigLoader::load() が引っかかるはずです。しきい値を 60 に上げて、警告が消えることを確認してください。同じコード・同じチェックで結果が変わる ことを体験するのが目的です。
  3. 命名規約を定める。 Checks に readability-identifier-naming を足し、8.4 節の CheckOptions をそのまま貼ります。
  4. 題材コードで確認する。 ビルドすると、config_loader.h の Entry のメンバや ConfigLoader のメンバ変数に対して指摘が出ます。buffer_ や path_ は PrivateMemberSuffix: '_' を満たしているので通り、満たさないものだけが警告されることを確認します。
  5. わざと違反させる。 config_loader.h のメンバを一時的に char* Buffer; に変えてビルドし、次のような警告が出ることを確認します。 
    invalid case style for private member 'Buffer' [readability-identifier-naming]
    確認したら元に戻します。
  6. マジックナンバーを調整する。 Checks に readability-magic-numbers を足してビルドし、config_loader.cpp の 4096 や 4095 が警告されることを確認します。次に 
      readability-magic-numbers.IgnorePowersOf2IntegerValues: 'true'
    を足すと 4096 だけが消え、4095 は残ることを確認します。
  7. 存在しないオプション名を試す。 
      readability-function-size.LineThresholdXX: '10'
    と書いてもエラーにならず、単に無視されることを確認します。タイプミスは静かに失敗する という感覚を持っておいてください。
オプションで黙らせるか、警告を受け入れるか

警告がうるさいとき、しきい値を緩めて消すのは簡単です。しかしそれは「ルールを自分に合わせた」のか「問題から目を逸らした」のか、区別が必要です。判断の目安は 「その値をチームの規約として文書に書けるか」 です。「関数は80行まで」は書けます。「この関数だけ例外」は書けません。後者は次章の NOLINT の出番です。

この章のまとめ

  • チェックは判定ロジックとオプションから成る。同じチェックでもオプション次第で結果が変わる。
  • 書式は CheckOptions に チェック名.オプション名: '値'。値は文字列、複数値はセミコロン区切り。
  • 設定できるオプションは --dump-config で確認する。存在しないオプション名は黙って無視される。
  • 4294967295 のような巨大な既定値は「そのサブチェックは無効」の意味。有効にしたのに何も出ない原因になる。
  • readability-identifier-naming は識別子の種類ごとにオプションを持ち、チーム規約の機械化に最も有効。
  • 継承時、Checks は連結、CheckOptions はキー単位の上書き。
  • しきい値を緩めるのは「規約として書けるとき」だけ。個別の例外は次章の抑制で扱う。

次章： 第9章「警告を抑制する作法」では、NOLINT 系のコメントで個別の箇所だけ警告を止める方法を扱います。安易に使えば静的解析は形骸化し、使わなければ運用が回らない ── その線引きが主題です。
