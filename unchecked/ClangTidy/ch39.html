既存コードベースへ段階導入する

第7部です。ここまでで道具は揃いました。残るは、それをすでに動いている実プロジェクトに入れる作業です。新規プロジェクトなら初日から全部有効にすればよい。難しいのは、10年分のコードがあって、有効にした瞬間に警告が3000件出るケースです。この章は、そこを通り抜けるための地図です。

39.3 「新規コードだけ厳しく」を実装する

第15章で作った差分解析が、ここで本領を発揮します。仕組みを整理します。

> git diff -U0 origin/main... | python clang-tidy-diff.py -p1 -path out\build\ninja ^
    -config-file tools\clang-tidy-diff.yml -j 8
比較対象を origin/main... にする

ドット3つ（...）を使うと、分岐点からの差分になります。ドット2つだと、main 側の変更まで差分に含まれ、自分が触っていない行まで検査対象になります。 CI の設定では特に注意してください。

39.4 90日の導入計画

実際の順序を、期間つきで示します。これは「守るべきスケジュール」ではなく「順序の型」として読んでください。

期間やること本書の該当章
第1〜2週
準備		LLVM のバージョンを揃える／.clang-tidy を作る／全体件数を測る（まだ CI には入れない）第4・7・22章
第3〜4週
合意形成		件数を見せて Tier を決める／命名規約を確定する／判断記録を作る第20・22章
第5〜6週
一括修正		安全な modernize-* と readability-* を全体に適用（1チェックずつコミット）第11・18・20章
第7〜8週
差分解析の導入		CI に差分解析を追加。最初は警告のみで、落とさない第15・40章
第9〜10週
ゲート化		Tier 0 のチェックで CI を落とすようにする第22・40章
第11〜12週
カスタムチェック		自作チェックを1つ導入。回帰テストも同時に第32・37章
継続件数の監視／Tier の昇格／不要チェックの引退第22・37章
最初の6週間、CI には何も入れない

これが最も重要な点です。合意ができていない状態で CI を落とすようにすると、静的解析そのものが敵になります。 最初はローカルでの警告表示だけにして、「便利だ」と思ってもらう期間を作ってください。ゲート化はその後です。

39.5 人が関わる部分

技術的な仕組みだけでは導入は進みません。

場面やること
提案するとき件数を示す。「bugprone-* で 23 件出ました。うち 5 件は実際のバグです」── 抽象論ではなく具体例で
規約を決めるとき既存コードの多数派に合わせる（第20章）。理想を持ち込むと移行コストが跳ね上がる
反対されたときそのチェックを Tier 3 にして理由を記録する。押し切らない（第22章）
周知するとき「何が変わるか」より「あなたのプルリクエストで何が起きるか」を書く
ゲート化するとき事前に予告する。 ある日突然 CI が落ちるようにしない
最初のチェックは「明らかなバグ」を選ぶ

導入初期に readability-* のような好みの分かれるチェックを持ち込むと、議論が命名規約の話に流れて本題に到達しません。最初は bugprone-use-after-move のような、誰も反対しないものから始めてください。 「静的解析は役に立つ」という共通認識ができてから、可読性の話をします。

39.6 進捗を可視化する

導入が進んでいることを、数字で見せられるようにします。

# tools/count-warnings.cmd
@echo off
setlocal
set LOG=%TEMP%\tidy-count.log
call tools\analyze-all.cmd > "%LOG%" 2>&1

echo === %DATE% ===
for %%c in (bugprone performance modernize readability custom) do (
    for /f %%n in ('findstr /c:"[%%c-" "%LOG%" ^| find /c /v ""') do echo %%c: %%n
)
endlocal

これを週次で実行し、記録を残します。数字が減っていくグラフは、次のチェックを導入する提案の最良の材料になります。

39.7 【ハンズオン】導入計画を作る

HANDS-ON 39　自分のプロジェクトの導入計画を立てる
  1. 現状を測る。 実際のプロジェクト（TidyLab でも、お手元の実プロジェクトでも）に対して、モジュール別の件数を出します。 
    tools\count-warnings.cmd
    この数字が計画の出発点です。
  2. 件数から戦略を選ぶ。 図39-2 の4戦略から、チェックごとに選びます。
    • 自動修正が確実で件数が多い → ① 一括修正
    • それ以外の大半 → ② 差分のみ
    • モジュール境界が明確 → ④ ファイル単位も併用
  3. 最初の1つを選ぶ。 「誰も反対しない」チェックを1つ選びます。bugprone-use-after-move や bugprone-undefined-memory-manipulation が候補です。件数が0〜数件であることを確認してください。
  4. 差分解析を試す。 適当なブランチを切り、数行変更してから、 
    git diff -U0 origin/main... | python clang-tidy-diff.py -p1 -path out\build\ninja
    を実行します。既存の警告が出ず、変更行だけが検査されることを確認してください。
  5. ... と .. の違いを確認する。 origin/main..（ドット2つ）で同じことを実行し、差分の範囲が変わることを確認します。
  6. 一括修正を1チェック分やる。 modernize-use-nullptr など安全なものを選び、第11章の手順（作業ツリーをきれいに → 書き出し → 適用 → 差分を全部読む → ビルド → コミット）で実行します。差分の行数を記録してください。 これがレビュー可能な量かどうかの判断材料になります。
  7. 90日計画を書く。 39.4 節の表を、自分のプロジェクトの事情に合わせて書き直します。docs\clang-tidy-rollout.md として保存してください。「いつ CI を落とすようにするか」を明記するのが要点です。
  8. 周知文を書く。 チームに送る想定で、次の3点を書きます。
    • いつから、何が変わるか
    • あなたのプルリクエストで何が起きるか（変更行に警告が出る／CI が落ちる場合の条件）
    • 困ったときの参照先（docs\clang-tidy-troubleshooting.md）
  9. 記録の仕組みを作る。 tools\count-warnings.cmd を実行し、結果を docs\warning-history.md に日付つきで追記します。週次で実行する担当を決めてください。

この章のまとめ

  • 導入の失敗は「大量の警告 → 後回し → 誰も見ない」の道筋で起きる。一度ノイズと認識されたものは二度と読まれない。
  • 導入の目標は「全部直す」ではなく 「これ以上悪化させない」。
  • 戦略は4つ。②差分のみを基本とし、①一括修正・③ベースライン・④ファイル単位を組み合わせる。
  • 差分解析なら導入初日から CI が緑で、しかも「触ったところは直す」が自動的に強制される。
  • git diff の比較対象は origin/main...（ドット3つ）。.. だと自分が触っていない行まで対象になる。
  • 最初の6週間、CI には何も入れない。 合意ができる前にゲート化すると、静的解析が敵になる。
  • 最初のチェックは「誰も反対しない明らかなバグ」を選ぶ。可読性の話は後。
  • 件数を週次で記録する。減っていく数字が、次の提案の最良の材料。
