第 34 章

実践3：命名・構造の規約をチェックする

第20章で readability-identifier-naming を設定しました。あれは強力ですが、扱えるのは「識別子の種類ごとの命名形式」だけです。「何を継承しているか」「どのインターフェイスを実装しているか」に応じたルールは表現できません。そこがカスタムチェックの独壇場です。

34.1 標準チェックとの境界

34.2 文脈依存ルールの構造

この種のルールは、すべて同じ形をしています。

34.3 ルール1：基底クラスに応じた接尾辞

  - Name: component-naming
    Query: |
      match cxxRecordDecl(
        isDerivedFrom(cxxRecordDecl(hasName("::Component")).bind("base")),
        unless(matchesName("Component$")),
        isDefinition(),
        isExpansionInMainFile()
      ).bind("cls")
    Diagnostic:
      - BindName: cls
        Message: "Component の派生クラスは、名前を Component で終わらせてください（例: PhysicsComponent）"
        Level: Warning
      - BindName: base
        Message: "この基底クラスを継承しています"
        Level: Note
Note で規約の根拠を指す

base を bind して Note を出しているのがポイントです。「なぜこの規約が適用されるのか」を、コードの上で示せます。 継承が深い場合、どの基底が原因かはコードを読むだけでは分かりません。第31章 31.5 節でいう「規約違反で、根拠が別にある」ケースです。

注意点：isDerivedFrom は間接継承も拾う

class Component {};
class RenderComponent : public Component {};        // 直接
class SpriteRenderComponent : public RenderComponent {};  // 間接

isDerivedFrom は間接的な派生も含みます。直接継承だけを対象にしたい場合は、別の Matcher が必要です。 clang-query で hasDirectBase のような名前を試し、使えるものを探してください（第24章のエラーメッセージが教えてくれます）。

34.4 ルール2：構造の制約

命名だけでなく、「持つべきもの」「持ってはいけないもの」も表現できます。

特定の基底の派生には仮想デストラクタを必須にする

  - Name: component-needs-virtual-dtor
    Query: |
      match cxxRecordDecl(
        isDerivedFrom(hasName("::Component")),
        isDefinition(),
        unless(hasMethod(cxxDestructorDecl(isVirtual()))),
        isExpansionInMainFile()
      ).bind("cls")
    Diagnostic:
      - BindName: cls
        Message: "Component の派生クラスには仮想デストラクタが必要です"
        Level: Warning

特定の名前空間の型を外部に公開させない

  - Name: no-detail-in-public-api
    Query: |
      match parmVarDecl(
        hasType(cxxRecordDecl(matchesName("^::mylib::detail::"))),
        hasAncestor(functionDecl(unless(matchesName("^::mylib::detail::")))),
        isExpansionInMainFile()
      ).bind("param")
    Diagnostic:
      - BindName: param
        Message: "detail 名前空間の型を公開 API の引数に使わないでください"
        Level: Warning

これは標準チェックには絶対にありません。 mylib という名前空間も detail という慣習も、あなたのプロジェクト固有だからです。

34.5 ルール3：テスト向けの規約

  - Name: mock-naming
    Query: |
      match cxxRecordDecl(
        isDerivedFrom(hasName("::IService")),
        matchesName("Mock"),
        unless(matchesName("^::.*::Mock[A-Z]")),
        isExpansionInMainFile()
      ).bind("cls")
    Diagnostic:
      - BindName: cls
        Message: "モックは Mock で始まる名前にしてください（例: MockUserService）"
        Level: Warning
正規表現は完全修飾名に対して評価される

matchesName が見るのは、名前空間を含む完全修飾名です。::mylib::PhysicsComponent のような文字列に対して正規表現が当たります。

  • "Component$" → 末尾が Component。名前空間があっても効く
  • "^Mock" → 効かない。先頭は ::mylib:: だから
  • "^::.*::Mock" または "::Mock[A-Z]" → こちらを使う

必ず clang-query で、名前空間ありとなしの両方のケースを確認してください。

34.6 メッセージには「例」を書く

命名規約のメッセージには、正しい例を具体的に書いてください。 抽象的な説明より、1つの実例のほうが速く伝わります。

✕○
「命名規約に違反しています」「Component の派生クラスは Component で終わらせてください（例: PhysicsComponent）」
「接尾辞が必要です」「Physics → PhysicsComponent のように変更してください」

34.7 【ハンズオン】文脈依存の規約を作る

HANDS-ON 34　条件つき命名規約を実装する
  1. 検証ファイルを作る。 tests\custom-checks\naming.cpp に、規約に合う例・合わない例・対象外の例をすべて書きます。 
    namespace mylib {

class Component { public: virtual ~Component() = default; };
class IService  { public: virtual ~IService() = default; };

class RenderComponent : public Component {};        // OK
class Physics        : public Component {};         // NG：接尾辞なし
class SpriteRenderComponent : public RenderComponent {};  // OK（間接継承）
class Sprite         : public RenderComponent {};   // NG：間接継承でも規約対象
class Helper {};                                    // 対象外

class BadComponent : public Component {             // NG：仮想デストラクタなし
public:
    ~BadComponent() {}
};

class MockUserService : public IService {};         // OK
class UserServiceMock : public IService {};         // NG：Mock で始まっていない

namespace detail { struct Impl {}; }
void publicApi(detail::Impl impl) {}                // NG：detail を公開 API に
namespace detail { void internalApi(Impl impl) {} } // OK：detail 内なら可

} // namespace mylib
  2. 規約をクエリに変換する。 図34-2 の手順で、規約の文を「条件 A かつ 条件 B の否定」に書き換えます。紙の上で日本語のままやってください。
  3. 接尾辞ルールを作る。 clang-query で確認します。 
    clang-query naming.cpp -- -std=c++23
    set output diag
m cxxRecordDecl(isDerivedFrom(hasName("::mylib::Component")), unless(matchesName("Component$")), isDefinition(), isExpansionInMainFile())
    Physics と Sprite が検出され、RenderComponent / SpriteRenderComponent / Helper が検出されないことを確認します。
  4. 正規表現の落とし穴を体験する。 
    m cxxRecordDecl(isDerivedFrom(hasName("::mylib::IService")), matchesName("^Mock"))
    0 件になることを確認してください。名前空間があるためです。次に、 
    m cxxRecordDecl(isDerivedFrom(hasName("::mylib::IService")), matchesName("::Mock[A-Z]"))
    で MockUserService が捕まることを確認します。
  5. 間接継承を確認する。 Sprite が検出されたことで、isDerivedFrom が間接継承も拾うことを確認しました。直接継承だけに限定したい場合の Matcher を、clang-query のエラーメッセージを頼りに探してみてください。
  6. Note を設計する。 34.3 節のクエリで base を bind し、設定ファイルに書きます。実行して、note: が基底クラスの宣言を指していることを確認します。Sprite の場合、note が指すのは Component か RenderComponent かを確認してください。
  7. 構造の制約を作る。 34.4 節の「仮想デストラクタ必須」を実装し、BadComponent だけが検出されることを確認します。
  8. 公開 API のルールを作る。 34.4 節の no-detail-in-public-api を実装します。これが最も難しいはずです。 publicApi が検出され、internalApi が検出されないところまで持っていってください。うまくいかない場合は、第36章のデバッグ手順に進む前に、条件を1つずつ削って確認します（第27章 27.5 節）。
  9. メッセージに例を入れる。 すべてのメッセージに、正しい形の具体例を入れます。実際に警告を出して、読んだ人がそのまま直せるかを自分で判定してください。
  10. 記録する。 期待動作の表を更新します。特に、正規表現が完全修飾名に当たることと、isDerivedFrom が間接継承を含むことを、注意事項として書き残してください。次に命名ルールを書く人が同じ罠にはまらずに済みます。

この章のまとめ

  • readability-identifier-naming は「識別子の種類 × 形式」しか扱えない。文脈に依存する規約はカスタムチェックの領分。
  • 規約「A ならば B であれ」は、クエリでは「A かつ B でない」と書く。
  • 条件の部分に AST の構造（継承関係、名前空間、メンバの有無）が使えるのが強み。
  • Note で規約の根拠（どの基底を継承しているか）を指せる。 継承が深いときに効く。
  • isDerivedFrom は間接継承も含む。直接継承だけに限定したいなら別の Matcher を探す。
  • matchesName は完全修飾名に対して評価される。 "^Mock" は名前空間があると効かない。
  • 命名規約のメッセージには正しい例を具体的に書く。抽象的な説明より速く伝わる。
