# 第16章　Google Benchmarkを組み込む

## この章のゴール

- ベンチマークをビルドシステムに組み込む意義を理解する
- `FetchContent` でGoogle Benchmarkを導入し、**不要なオプションを切る**
- `benchmark::benchmark` / `benchmark::benchmark_main` を使い分ける
- **Release構成でしか意味がないことを、仕組みで担保する**
- ベンチマークをCTestから分離する
- `--benchmark_out=json` と `compare.py` で変更前後を比較する
- CIでベンチマークを回すときの現実的な落としどころを知る

テストが「正しさ」を守るのに対し、ベンチマークは「速さ」を守る。ただし、**速さは正しさよりずっと壊れやすく、測りにくい。**

---

## 16.1　なぜビルドシステムに組み込むのか

### 「手元で測った」は続かない

性能改善をするとき、多くの人はこうする。

1. 適当なmain関数を書いて時間を測る
2. 最適化する
3. また測る
4. 満足したら、その計測コードを消す

この方法の問題は、**再現できないこと**だ。半年後に別の人が最適化を「戻す」変更を入れても、誰も気づかない。

### ビルドシステムに入れると何が変わるか

| 効果 | 説明 |
| --- | --- |
| **計測条件が固定される** | コンパイルフラグ、構成、入力データがCMakeで宣言される |
| **誰でも同じ手順で測れる** | `cmake --build --preset x64-release --target pixkit-bench` |
| **履歴が残る** | 計測コードがリポジトリにあるので、何を測っていたか分かる |
| **回帰を検出できる** | JSON出力を保存して比較する（16.6節） |

### テストとは別物として扱う

重要な区別がある。

| | ユニットテスト | ベンチマーク |
| --- | --- | --- |
| 判定 | 決定的（通る／落ちる） | **測定値。環境に依存する** |
| 構成 | 主にDebug | **Releaseのみ意味がある** |
| 実行時間 | 短い（ミリ秒） | 長い（秒〜分） |
| CIで毎回回すか | **回す** | 回すかは要検討（16.7節） |
| 失敗させるか | させる | **閾値の設定が難しい** |

この違いから、「ベンチマークはCTestに登録しない、あるいは別ラベルで分離する」という設計方針が導かれる（16.5節）。

## 16.2　`FetchContent` での導入とオプション制御

```cmake
include(FetchContent)

set(BENCHMARK_ENABLE_TESTING       OFF CACHE BOOL "" FORCE)
set(BENCHMARK_ENABLE_GTEST_TESTS   OFF CACHE BOOL "" FORCE)
set(BENCHMARK_ENABLE_INSTALL       OFF CACHE BOOL "" FORCE)
set(BENCHMARK_INSTALL_DOCS         OFF CACHE BOOL "" FORCE)
set(BENCHMARK_ENABLE_WERROR        OFF CACHE BOOL "" FORCE)

FetchContent_Declare(benchmark
    GIT_REPOSITORY https://github.com/google/benchmark.git
    GIT_TAG        ${PIXKIT_BENCHMARK_TAG}
    GIT_SHALLOW    TRUE
    EXCLUDE_FROM_ALL
)
FetchContent_MakeAvailable(benchmark)
```

### オプションを切る理由

| オプション | 既定 | なぜ切るか |
| --- | --- | --- |
| `BENCHMARK_ENABLE_TESTING` | `ON` | **Google Benchmark自身のテスト**をビルドする。不要 |
| `BENCHMARK_ENABLE_GTEST_TESTS` | `ON` | 上記のうちGoogleTestを使うもの。**別のGoogleTestを取ってこようとする** |
| `BENCHMARK_ENABLE_INSTALL` | `ON` | 第21章の `install()` を汚染する（第14章8節と同じ問題） |
| `BENCHMARK_INSTALL_DOCS` | `ON` | 同上 |
| `BENCHMARK_ENABLE_WERROR` | `ON` | **警告をエラーにする。** コンパイラの更新でビルドが落ちる |

**`BENCHMARK_ENABLE_GTEST_TESTS` を切り忘れると特に厄介だ。** Google Benchmark が自前でGoogleTestを `FetchContent` しようとし、あなたがすでに取り込んだGoogleTestと衝突する（ターゲット名の重複でエラーになる）。

```
CMake Error: add_library cannot create target "gtest" because another
target with the same name already exists.
```

`BENCHMARK_ENABLE_WERROR` も実害がある。新しいコンパイラで未知の警告が出た瞬間、**あなたのプロジェクトのビルドが落ちる**。他人のコードの警告で自分のビルドを止められる筋合いはない。

### バージョンの固定

第14章2節と同じく、変数にまとめる。

```cmake
set(PIXKIT_BENCHMARK_TAG "v1.9.5" CACHE STRING "Google Benchmarkのバージョン")
```

### 取得する場所

第14章7節と同じ考え方で、**`bench/CMakeLists.txt` の中で取得する。**

```cmake
if(PIXKIT_BUILD_BENCHMARKS)
    add_subdirectory(bench)
endif()
```

第8章で `PIXKIT_BUILD_BENCHMARKS` のプリセット既定値を「Debugでは `OFF`」にしておいたのは、この章のためだ。**日常の開発でベンチマークのビルドを待たされないようにする。**

## 16.3　ターゲットのリンク

| ターゲット | 中身 |
| --- | --- |
| `benchmark::benchmark` | 本体 |
| `benchmark::benchmark_main` | 本体 ＋ 既定の `main()` |

```cmake
add_executable(pixkit-bench bench_filter.cpp bench_codec.cpp)

target_link_libraries(pixkit-bench PRIVATE
    pixkit::core
    pixkit::filter
    pixkit::warnings
    benchmark::benchmark_main
)
```

GoogleTestと同じ構造だ。通常は `benchmark_main` を使う。

> **Windowsでの追加の依存**
> Google Benchmark はCPU情報の取得に `shlwapi.lib` を使う。CMakeのターゲットが依存関係として持っているので、通常は明示不要だ。もし `LNK2019: 未解決の外部シンボル __imp_PathMatchSpecA` のようなエラーが出たら、`target_link_libraries(pixkit-bench PRIVATE shlwapi)` を足す。

## 16.4　Release構成でしか意味がない

### 何が問題か

Debugビルドでベンチマークを走らせても、**得られる数値に意味はない。**

- 最適化されていない（`/Od`）ので、実際の10倍遅いこともある
- `/RTC1`（実行時チェック）が入っている
- STLのイテレータデバッグ（`_ITERATOR_DEBUG_LEVEL=2`）で、`std::vector` の添字アクセスが桁違いに遅い

最後の項目は特に大きい。画像処理のような添字アクセスの塊では、Debugビルドの数値は完全に別物になる。

### 対策1：ビルド構成で分ける（プリセット）

第4章・第8章で仕込んである。

```json
{
  "name": "x64-debug",
  "cacheVariables": {
    "CMAKE_BUILD_TYPE": "Debug",
    "PIXKIT_BUILD_BENCHMARKS": "OFF"
  }
},
{
  "name": "x64-release",
  "cacheVariables": {
    "CMAKE_BUILD_TYPE": "RelWithDebInfo",
    "PIXKIT_BUILD_BENCHMARKS": "ON"
  }
}
```

### 対策2：実行時に警告する

Google Benchmark 自身も気づいてくれる。Debugビルドの実行ファイルを走らせると、こう出る。

```
***WARNING*** Library was built as DEBUG. Timings may be affected.
```

### 対策3：構成時にエラーにする

もっと強く止めたいなら、こう書ける。

```cmake
if(PIXKIT_BUILD_BENCHMARKS AND NOT CMAKE_CONFIGURATION_TYPES)
    if(CMAKE_BUILD_TYPE STREQUAL "Debug")
        message(FATAL_ERROR
            "ベンチマークをDebug構成でビルドしようとしています。"
            "-DCMAKE_BUILD_TYPE=RelWithDebInfo を使うか、"
            "-DPIXKIT_BUILD_BENCHMARKS=OFF を指定してください")
    endif()
endif()
```

`NOT CMAKE_CONFIGURATION_TYPES` の条件が要ることに注意する（第12章2節）。マルチ構成ジェネレータでは `CMAKE_BUILD_TYPE` が空なので、この判定はできない。

### 対策4：最適化で消されないようにする

これは計測コード側の話だ。

```cpp
static void BM_Bad(benchmark::State& state)
{
    for (auto _ : state) {
        int x = compute();     // 結果を使っていない → まるごと消される
    }
}
```

コンパイラは「結果を使わない計算」を削除する。ベンチマークの時間が `0 ns` になったら、まずこれを疑う。

```cpp
static void BM_Good(benchmark::State& state)
{
    for (auto _ : state) {
        int x = compute();
        benchmark::DoNotOptimize(x);    // 「この値は使われる」と教える
    }
}
```

| 関数 | 意味 |
| --- | --- |
| `benchmark::DoNotOptimize(x)` | `x` が使われたことにする（レジスタから追い出す） |
| `benchmark::ClobberMemory()` | 「メモリが書き換わった」ことにする（ストアの削除を防ぐ） |

バッファを書き換える処理では、両方が必要になる。

```cpp
for (auto _ : state) {
    grayscale(img.view());
    benchmark::DoNotOptimize(img.pixels().data());
    benchmark::ClobberMemory();
}
```

## 16.5　CTestから分離する

### 選択肢

**選択肢A：CTestに登録しない（推奨）**

```cmake
add_executable(pixkit-bench ...)
# add_test は書かない
```

実行は明示的に行う。

```
cmake --build --preset x64-release --target pixkit-bench
out\build\x64-release\bin\pixkit-bench.exe
```

**ベンチマークは「測るもの」であって「通す／落とすもの」ではない**、という立場だ。本書はこれを基本にする。

**選択肢B：別ラベルで登録する**

「CIで動くことだけは確認したい」なら、ごく短い設定で登録する。

```cmake
add_test(NAME bench.smoke
         COMMAND $<TARGET_FILE:pixkit-bench>
                 --benchmark_min_time=0.01s
                 --benchmark_filter=BM_Grayscale/64)

set_tests_properties(bench.smoke PROPERTIES
    LABELS  "bench"
    TIMEOUT 120
)
```

そして、通常のテスト実行からは除外する。

```
ctest --preset x64-release -LE bench      # ベンチマークを除いて実行
ctest --preset x64-release -L  bench      # ベンチマークだけ実行
```

`testPresets` に書いておくこともできる。

```json
{
  "name": "x64-release",
  "configurePreset": "x64-release",
  "output": { "outputOnFailure": true },
  "filter": {
    "exclude": { "label": "bench" }
  }
}
```

**これは「速さの検証」ではなく「ベンチマークが壊れていないことの検証」だ。** 目的を取り違えないようにする。

### なぜ「閾値で失敗させる」を推奨しないのか

「前回より10%遅くなったらCIを落とす」は魅力的に聞こえるが、実際にやると破綻する。

- CIランナーは共有マシンで、**実行のたびに10〜30%はぶれる**
- 落ちるたびに再実行する習慣がつき、やがて誰も見なくなる
- 本当の回帰が、ノイズに埋もれる

現実的なのは、**「測って記録し、人間が定期的に見る」**運用だ。16.6節と16.7節で扱う。

## 16.6　結果を比較する

### JSON出力

```
pixkit-bench.exe --benchmark_out=before.json --benchmark_out_format=json
```

コードを変更してから、もう一度測る。

```
pixkit-bench.exe --benchmark_out=after.json --benchmark_out_format=json
```

### `compare.py`

Google Benchmark には比較スクリプトが同梱されている。`FetchContent` で取得したソースツリーにある。

```
python out\build\x64-release\_deps\benchmark-src\tools\compare.py benchmarks before.json after.json
```

```
Benchmark                        Time             CPU      Time Old      Time New       CPU Old       CPU New
-------------------------------------------------------------------------------------------------------------
BM_Grayscale/64               -0.3521         -0.3520            15             9            15             9
BM_Grayscale/256              -0.3489         -0.3488           238           155           238           155
BM_Grayscale/512              -0.3502         -0.3501           960           624           960           624
```

`-0.35` は「35%速くなった」という意味だ。**改善を数字で示せる。**

事前に依存パッケージが要る。

```
pip install -r out\build\x64-release\_deps\benchmark-src\tools\requirements.txt
```

### CMakeから使いやすくする

パスを毎回書くのは面倒なので、カスタムターゲットにしておく。

```cmake
add_custom_target(bench-run
    COMMAND $<TARGET_FILE:pixkit-bench>
            --benchmark_out=${CMAKE_BINARY_DIR}/bench-$<CONFIG>.json
            --benchmark_out_format=json
    DEPENDS pixkit-bench
    WORKING_DIRECTORY ${CMAKE_BINARY_DIR}
    COMMENT "ベンチマークを実行しています..."
    USES_TERMINAL
)
```

```
cmake --build --preset x64-release --target bench-run
```

`USES_TERMINAL` を付けると、進捗がリアルタイムに表示される（付けないとバッファリングされて、終わるまで何も見えない）。

### 統計的な安定性

1回の計測はぶれる。繰り返して統計を取る。

```
pixkit-bench.exe --benchmark_repetitions=10 --benchmark_report_aggregates_only=true
```

```
BM_Grayscale/256_mean       238 us
BM_Grayscale/256_median     237 us
BM_Grayscale/256_stddev    3.21 us
BM_Grayscale/256_cv        1.35 %
```

**`cv`（変動係数）を見る。** これが5%を超えているなら、計測環境がうるさい。他のアプリを閉じる、電源プランを「高パフォーマンス」にする、といった対処が要る。`compare.py` も、繰り返し計測したデータを渡すとU検定のp値を出してくれる。

## 16.7　CIでベンチマークを回すか

### 結論から言うと

**「回すが、落とさない」**のが現実的だ。

| やること | やらないこと |
| --- | --- |
| ビルドが通ることを確認する | 閾値で失敗させる |
| ごく短い実行（スモークテスト）をする | 全ベンチマークをフル実行する |
| 結果をアーティファクトとして保存する | PRごとに前回と比較して警告する |

### CIでの数値が信用できない理由

- **共有マシン**：他のジョブと同じ物理マシンで動いている
- **仮想化**：CPUの周波数もキャッシュも予測できない
- **サーマルスロットリング**：連続実行で遅くなる
- **ランナーの世代差**：GitHub Actions のマシンは時期によって変わる

同じコードで測った値が、日によって2倍違うことがある。これで回帰を判定するのは無理だ。

### 現実的なワークフロー

```yaml
  benchmark:
    runs-on: windows-2025
    steps:
      - uses: actions/checkout@v4
      - uses: ilammy/msvc-dev-cmd@v1
        with: { arch: x64 }

      - name: 構成とビルド
        run: |
          cmake --preset x64-release
          cmake --build --preset x64-release --target pixkit-bench

      - name: スモーク実行
        run: >
          out/build/x64-release/bin/pixkit-bench.exe
          --benchmark_min_time=0.01s
          --benchmark_out=bench.json
          --benchmark_out_format=json

      - name: 結果を保存
        uses: actions/upload-artifact@v4
        with:
          name: benchmark-results
          path: bench.json
```

**`--benchmark_min_time=0.01s` で実行時間を切り詰めている。** ここでの目的は「ベンチマークコードが壊れていないこと」の確認であって、性能の測定ではない。

### 本気で性能を追跡するなら

- **専用の物理マシン**を用意する（CIランナーではなく）
- 定期実行（夜間ビルドなど）にして、PRごとには回さない
- 結果を時系列で保存し、グラフ化する

そこまでやるプロジェクトは多くないので、まずは「手元で測れる仕組みを整え、CIではビルドだけ守る」で十分だ。

## ハンズオン：フィルタのベンチマークを作る

### 手順1：`bench/CMakeLists.txt` を書く

```cmake
# ============================================================
# Google Benchmark の取得
# ============================================================
include(FetchContent)

set(BENCHMARK_ENABLE_TESTING     OFF CACHE BOOL "" FORCE)
set(BENCHMARK_ENABLE_GTEST_TESTS OFF CACHE BOOL "" FORCE)
set(BENCHMARK_ENABLE_INSTALL     OFF CACHE BOOL "" FORCE)
set(BENCHMARK_INSTALL_DOCS       OFF CACHE BOOL "" FORCE)
set(BENCHMARK_ENABLE_WERROR      OFF CACHE BOOL "" FORCE)

FetchContent_Declare(benchmark
    GIT_REPOSITORY https://github.com/google/benchmark.git
    GIT_TAG        ${PIXKIT_BENCHMARK_TAG}
    GIT_SHALLOW    TRUE
    EXCLUDE_FROM_ALL
)
FetchContent_MakeAvailable(benchmark)

foreach(T benchmark benchmark_main)
    if(TARGET ${T})
        set_target_properties(${T} PROPERTIES FOLDER "external")
    endif()
endforeach()

# ============================================================
# Debug構成での実行を止める（16.4節）
# ============================================================
if(NOT CMAKE_CONFIGURATION_TYPES AND CMAKE_BUILD_TYPE STREQUAL "Debug")
    message(WARNING
        "ベンチマークをDebug構成でビルドしています。計測結果は参考になりません。"
        "-DCMAKE_BUILD_TYPE=RelWithDebInfo を使ってください")
endif()

# ============================================================
# ベンチマークターゲット
# ============================================================
add_executable(pixkit-bench
    bench_color.cpp
    bench_filter.cpp
    bench_codec.cpp
)

target_link_libraries(pixkit-bench PRIVATE
    pixkit::core
    pixkit::codec
    pixkit::filter
    pixkit::warnings
    benchmark::benchmark_main
)

target_compile_definitions(pixkit-bench PRIVATE
    PIXKIT_BENCH_DATA_DIR="${CMAKE_CURRENT_SOURCE_DIR}/../tests/codec/data"
)

set_target_properties(pixkit-bench PROPERTIES FOLDER "bench")

# ============================================================
# 実行を簡単にするターゲット
# ============================================================
add_custom_target(bench-run
    COMMAND $<TARGET_FILE:pixkit-bench>
            --benchmark_out=${CMAKE_BINARY_DIR}/bench-$<CONFIG>.json
            --benchmark_out_format=json
    DEPENDS pixkit-bench
    WORKING_DIRECTORY ${CMAKE_BINARY_DIR}
    COMMENT "ベンチマークを実行しています..."
    USES_TERMINAL
)

# ============================================================
# CTestには「壊れていないことの確認」だけ登録する（16.5節）
# ============================================================
add_test(NAME bench.smoke
         COMMAND $<TARGET_FILE:pixkit-bench>
                 --benchmark_min_time=0.01s
                 --benchmark_filter=BM_Grayscale/64)

set_tests_properties(bench.smoke PROPERTIES
    LABELS  "bench"
    TIMEOUT 300
)
```

トップレベルの `CMakeLists.txt` にバージョン変数を追加する。

```cmake
set(PIXKIT_BENCHMARK_TAG "v1.9.5" CACHE STRING "Google Benchmarkのバージョン")
```

### 手順2：色変換のベンチマーク

`bench/bench_color.cpp`

```cpp
#include <pixkit/core/color.hpp>

#include <benchmark/benchmark.h>

#include <vector>

static void BM_LuminanceU8(benchmark::State& state)
{
    const auto n = static_cast<std::size_t>(state.range(0));
    std::vector<pixkit::Rgb8> data(n, pixkit::Rgb8{10, 200, 90});

    for (auto _ : state) {
        std::uint32_t acc = 0;
        for (const auto& c : data) {
            acc += pixkit::luminance(c);
        }
        benchmark::DoNotOptimize(acc);
    }
    state.SetItemsProcessed(state.iterations() * static_cast<std::int64_t>(n));
}
BENCHMARK(BM_LuminanceU8)->Arg(1024)->Arg(65536);

static void BM_LuminanceF32(benchmark::State& state)
{
    const auto n = static_cast<std::size_t>(state.range(0));
    std::vector<pixkit::Rgb32f> data(n, pixkit::Rgb32f{0.1f, 0.8f, 0.35f});

    for (auto _ : state) {
        float acc = 0.0f;
        for (const auto& c : data) {
            acc += pixkit::luminance(c);
        }
        benchmark::DoNotOptimize(acc);
    }
    state.SetItemsProcessed(state.iterations() * static_cast<std::int64_t>(n));
}
BENCHMARK(BM_LuminanceF32)->Arg(1024)->Arg(65536);
```

`u8` 版と `f32` 版を並べているのは、**「どちらが速いか」を比べる**ためだ。`u8` 版は内部で `f32` に変換してから戻しているので、`f32` 版より遅いはずである。この予想が当たっているかを、実測で確認できる。

### 手順3：フィルタのベンチマーク

`bench/bench_filter.cpp`

```cpp
#include <pixkit/core/image.hpp>
#include <pixkit/filter/filters.hpp>

#include <benchmark/benchmark.h>

namespace {

pixkit::Image make_image(int n)
{
    pixkit::Image img(n, n);
    for (int y = 0; y < n; ++y) {
        for (int x = 0; x < n; ++x) {
            img[x, y] = pixkit::Rgb8{
                static_cast<std::uint8_t>(x & 0xff),
                static_cast<std::uint8_t>(y & 0xff),
                128 };
        }
    }
    return img;
}

}  // namespace

static void BM_Grayscale(benchmark::State& state)
{
    const int n = static_cast<int>(state.range(0));
    auto img = make_image(n);

    for (auto _ : state) {
        pixkit::filter::grayscale(img.view());
        benchmark::DoNotOptimize(img.pixels().data());
        benchmark::ClobberMemory();
    }

    state.SetItemsProcessed(state.iterations() * static_cast<std::int64_t>(n) * n);
    state.SetBytesProcessed(state.iterations() * static_cast<std::int64_t>(img.byte_size()));
}
BENCHMARK(BM_Grayscale)->Arg(64)->Arg(256)->Arg(512)->Unit(benchmark::kMicrosecond);

static void BM_Blur3x3(benchmark::State& state)
{
    const int n = static_cast<int>(state.range(0));
    auto src = make_image(n);
    pixkit::Image dst(n, n);

    for (auto _ : state) {
        pixkit::filter::blur3x3(src.view(), dst.view());
        benchmark::DoNotOptimize(dst.pixels().data());
        benchmark::ClobberMemory();
    }

    state.SetItemsProcessed(state.iterations() * static_cast<std::int64_t>(n) * n);
    state.SetBytesProcessed(state.iterations() * static_cast<std::int64_t>(src.byte_size()));
}
BENCHMARK(BM_Blur3x3)->Arg(64)->Arg(256)->Arg(512)->Unit(benchmark::kMicrosecond);
```

| 指定 | 意味 |
| --- | --- |
| `->Arg(64)` | `state.range(0)` に 64 を渡す |
| `->Unit(benchmark::kMicrosecond)` | 表示単位をマイクロ秒に |
| `state.SetItemsProcessed(...)` | `items_per_second` を計算させる |
| `state.SetBytesProcessed(...)` | `bytes_per_second` を計算させる |

**`SetBytesProcessed` は画像処理では特に有用だ。** 「メモリ帯域を使い切っているか」が分かる。

## この章のまとめ

- ベンチマークをビルドシステムに組み込むと、**計測条件が固定され、誰でも同じ手順で再現できる**
- `FetchContent` で導入し、**`BENCHMARK_ENABLE_TESTING` / `BENCHMARK_ENABLE_GTEST_TESTS` / `BENCHMARK_ENABLE_INSTALL` / `BENCHMARK_ENABLE_WERROR` を切る。** 特に `GTEST_TESTS` は、GoogleTestのターゲット名衝突を起こす
- リンクするのは `benchmark::benchmark_main`
- **Release構成でしか意味がない。** Debugでは20倍以上遅くなることがある。プリセットで構成を分け、必要なら構成時に警告・エラーにする
- 計測コードは **`benchmark::DoNotOptimize` と `benchmark::ClobberMemory`** で最適化による消滅を防ぐ。時間が `0 ns` になったらこれを疑う
- `SetItemsProcessed` / `SetBytesProcessed` を設定すると、スループットが表示される。**画素あたりの処理性能が見えるようになる**
- **ベンチマークはCTestに登録しないか、`LABELS "bench"` で分離する。** 閾値で失敗させる運用は、CIのノイズで破綻する
- 比較は `--benchmark_out=json` と `compare.py`。安定性は `--benchmark_repetitions` と `cv`（変動係数）で確認する
- CIでは「ビルドが通り、短時間実行できること」だけを守り、**数値で合否を決めない**

次の第17章で第4部を締めくくる。Clang-Tidyによる静的解析を組み込み、テスト（正しさ）・ベンチマーク（速さ）に続いて、**コードそのものの品質**を機械的に守る仕組みを入れる。Windows + MSVC 環境でClang-Tidyを動かすには固有の勘所があるので、そこを丁寧に扱う。
