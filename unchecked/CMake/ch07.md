# 第7章　C++23を有効にし、コンパイル設定を一元化する

## この章のゴール

- `target_compile_features` と `CXX_STANDARD` の違いを理解し、使い分けられる
- **MSVCに実際どの `/std` フラグが渡っているかを確認できる**
- C++23の機能を実際に使ってビルドできる
- 本書でC++モジュールを使わない理由を理解する
- 警告設定と文字コード設定を正しく行える
- 共通のコンパイル設定を `INTERFACE` ライブラリにまとめ、全ターゲットで共有する
- ジェネレータ式の基本形を読み書きできる

第6章で学んだ使用要件が、ここで実用的な形になる。

---

## 7.1　`target_compile_features` と `cxx_std_23`

C++の規格を指定する方法は2通りある。まず推奨されるほうから。

```cmake
add_library(pixkit-core INTERFACE)
target_compile_features(pixkit-core INTERFACE cxx_std_23)
```

これは「このターゲットは C++23 を必要とする」という**要求**を宣言する。指定できるのは `cxx_std_11` / `cxx_std_14` / `cxx_std_17` / `cxx_std_20` / `cxx_std_23` / `cxx_std_26` などだ（`cxx_std_23` はCMake 3.20以降）。

### なぜこちらが推奨されるのか

`target_compile_features` は第6章で学んだ `PUBLIC` / `PRIVATE` / `INTERFACE` を取る。つまり**規格の要求が伝播する**。

```cmake
add_library(pixkit-core INTERFACE)
target_compile_features(pixkit-core INTERFACE cxx_std_23)

add_executable(pixcli src/main.cpp)
target_link_libraries(pixcli PRIVATE pixkit::core)
```

`pixcli` 側には何も書いていないが、`pixkit-core` が C++23 を要求しているので、`pixcli` も C++23 でコンパイルされる。**ライブラリが「私を使うにはC++23が要ります」と宣言し、それが自動的に伝わる。**

これは配布の場面で決定的に重要になる。第22章で `find_package` 対応のパッケージを作ると、利用側は `target_link_libraries(app PRIVATE pixkit::core)` と書くだけで、必要な規格が自動的に設定される。

### 伝播の規則

複数のターゲットから異なる要求が来た場合、**最も高い要求が採用される**。

```cmake
target_compile_features(lib_a INTERFACE cxx_std_17)
target_compile_features(lib_b INTERFACE cxx_std_23)

target_link_libraries(app PRIVATE lib_a lib_b)   # app は C++23 でコンパイルされる
```

「C++17で十分なライブラリ」が「C++23が必要なライブラリ」と混ざっても、正しく動く。

### 個別の機能名は使わない

`target_compile_features` には `cxx_constexpr` や `cxx_lambda` のような**個別の機能名**も指定できるが、これは使わないほうがよい。C++20以降、CMakeは個別機能の追跡をやめており、実質的に `cxx_std_XX` だけが意味を持つ。

## 7.2　`CXX_STANDARD` プロパティ

もう1つの方法がプロパティ指定だ。

```cmake
set_target_properties(pixcli PROPERTIES
    CXX_STANDARD          23
    CXX_STANDARD_REQUIRED ON
    CXX_EXTENSIONS        OFF
)
```

| プロパティ | 意味 |
| --- | --- |
| `CXX_STANDARD` | 使いたい規格（`98`/`11`/`14`/`17`/`20`/`23`/`26`） |
| `CXX_STANDARD_REQUIRED` | **`ON` にしないと、対応していないコンパイラで黙って古い規格に落ちる** |
| `CXX_EXTENSIONS` | コンパイラ独自拡張。GCC/Clangで `-std=gnu++23` か `-std=c++23` かを決める。MSVCでは効果がない |

### `CXX_STANDARD_REQUIRED` を必ず ON にする

既定では `OFF` だ。この状態では、コンパイラがC++23に対応していない場合、CMakeは**エラーにせずC++20やC++17に落として**ビルドを続行する。これを「decay（減衰）」と呼ぶ。

親切なようでいて、実際には「なぜかC++23の機能が使えない」という不可解な症状を生む。**必ず `ON` にする。**

### 変数版でまとめて指定する

`CMAKE_CXX_STANDARD` という変数を設定すると、**それ以降に定義されるすべてのターゲット**の `CXX_STANDARD` プロパティの初期値になる。

```cmake
set(CMAKE_CXX_STANDARD 23)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)
```

手軽だが、第6章4節で述べたディレクトリ単位のグローバル設定と同じ性質を持つ。しかも、`FetchContent` で取り込んだ外部ライブラリ（第14章）にまで影響してしまう。

### 使い分け

| | `target_compile_features` | `CXX_STANDARD` |
| --- | --- | --- |
| 意味 | 「**最低限これが必要**」という要求 | 「**これでコンパイルする**」という指定 |
| 伝播 | する（`PUBLIC`/`INTERFACE`） | しない |
| インストール後も有効 | **する**（第22章） | しない |
| 上位規格でのビルド | 許容される | 固定される |

**ライブラリを作る側は `target_compile_features`、最終的な実行ファイルは好みでどちらでもよい。** 本書ではライブラリに `target_compile_features` を使い、共通設定ターゲット（7.7節）を経由して全体に行き渡らせる。

## 7.3　実際に渡っているフラグを確認する

ここは本書で特に注意して読んでほしい節だ。**CMakeが `cxx_std_23` をどのMSVCフラグに翻訳するかは、直感に反する。**

### MSVCの `/std` オプション

MSVCには次のオプションがある。

| フラグ | 意味 |
| --- | --- |
| `/std:c++17` | C++17 |
| `/std:c++20` | C++20 |
| `/std:c++23preview` | **C++23（プレビュー実装）** |
| `/std:c++latest` | 実装済みの最新機能すべて。**C++26の提案も含む** |

Visual Studio 2026 のツールセット v145（MSVC 14.5x 系）では、`/std:c++23preview` が C++23 を指す。将来、実装が完了した時点で `/std:c++23` が追加され、`/std:c++23preview` は非推奨になる予定だ。

### CMakeは `/std:c++latest` を渡す

ところが、本書執筆時点のCMake（4.4系）で、

```cmake
target_compile_features(app PRIVATE cxx_std_23)
# または
set_target_properties(app PROPERTIES CXX_STANDARD 23)
```

と書くと、MSVCに渡るのは **`/std:c++latest`** である。`/std:c++23preview` ではない。

CMake側で `/std:c++23preview` を選択する実装が一度入り、その後取り消された経緯がある。したがって、**「C++23を指定したのに、C++26の機能まで使えてしまう」**状態になる。

### なぜこれが問題なのか

```cpp
// C++26 で入る予定の機能を、うっかり使ってしまう
auto x = some_cpp26_feature();
```

`/std:c++latest` では通る。しかし、

- そのコードをGCC/Clangでビルドすると通らない
- 将来 `/std:c++23` に切り替えたときに通らなくなる
- C++26の仕様変更で、動作が変わる可能性がある

「C++23のプロジェクト」と言いながら、実際にはC++26のプレビュー環境でビルドしている、という状態になる。

### まず確認する

推測せず、確かめる。方法は3つある。

**方法1：`compile_commands.json` を見る**（第4章で有効化済み）

```
type out\build\x64-debug\compile_commands.json
```

`"command"` の中に `/std:c++latest` または `-std:c++latest` が入っているはずだ。

**方法2：詳細ログでビルドする**

```
cmake --build out/build/x64-debug --verbose
```

実際に実行される `cl.exe` のコマンドラインがそのまま表示される。

**方法3：コードから確認する**

```cpp
#include <iostream>

int main()
{
    std::cout << "__cplusplus = " << __cplusplus << '\n';
#ifdef _MSVC_LANG
    std::cout << "_MSVC_LANG  = " << _MSVC_LANG << '\n';
#endif
}
```

ここで落とし穴がある。**MSVCは既定で `__cplusplus` を `199711L` と報告する。** 20年以上前の互換性のためだ。正しい値を得るには `/Zc:__cplusplus` を渡す必要がある（7.6節）。

`_MSVC_LANG` はMSVC独自のマクロで、**`/Zc:__cplusplus` の有無にかかわらず正しい値**を報告する。移植性のあるコードでは次のように書く。

```cpp
#if defined(_MSVC_LANG)
#  define MY_CPLUSPLUS _MSVC_LANG
#else
#  define MY_CPLUSPLUS __cplusplus
#endif

static_assert(MY_CPLUSPLUS >= 202302L, "C++23 が有効になっていません");
```

| 値 | 規格 |
| --- | --- |
| `201703L` | C++17 |
| `202002L` | C++20 |
| `202302L` | C++23 |

### 明示的に `/std:c++23preview` を使いたい場合

「C++26の機能を誤って使わないようにしたい」なら、フラグを明示的に指定する。

```cmake
if(MSVC)
    target_compile_options(pixkit_options INTERFACE /std:c++23preview)
endif()
```

ただし、`target_compile_features(... cxx_std_23)` と併用すると `/std` が2回渡ることになる。MSVCは後勝ちで処理し、次の警告を出す。

```
cl : コマンド ライン warning D9025: '/std:c++latest' より '/std:c++23preview' が優先されます。
```

動作はするが、警告を `/WX` でエラーにしている場合は困る。どちらか一方に統一するのが実務的だ。

**本書の方針**：`target_compile_features(... cxx_std_23)` を使い、`/std:c++latest` が渡ることを**承知したうえで**進める。そのうえで、C++26の機能を誤用しないよう、CIでGCCやClangでもビルドする（第15章）か、`static_assert` で規格を検査する。

将来 `/std:c++23` が既定になり、CMakeがそれを選ぶようになれば、この節の注意は不要になる。**手元の環境で実際に何が渡っているかを一度確認する**、という習慣だけ持ち帰ってほしい。

## 7.4　C++23を味見する

設定ができたか、実際のコードで確かめる。

### `std::print`（`<print>`）

第2章で書いた `hello` を、いよいよ書き換える。

```cpp
#include <print>

int main()
{
    std::print("Hello, {}!\n", "CMake");
    std::println("{} + {} = {}", 2, 3, 2 + 3);
}
```

`std::cout` より速く、書式指定が型安全だ。`std::println` は末尾に改行を付ける。

### `std::expected`（`<expected>`）

エラーを例外なしで返す型だ。画像の読み込みのように「失敗しうる処理」と相性がよく、第9章以降で `pixkit` の設計に使う。

```cpp
#include <expected>
#include <print>
#include <string>

enum class ParseError { Empty, NotANumber };

std::expected<int, ParseError> parse(std::string_view s)
{
    if (s.empty()) {
        return std::unexpected(ParseError::Empty);
    }
    int value = 0;
    for (char c : s) {
        if (c < '0' || c > '9') {
            return std::unexpected(ParseError::NotANumber);
        }
        value = value * 10 + (c - '0');
    }
    return value;
}

int main()
{
    if (auto r = parse("123")) {
        std::println("ok: {}", *r);
    } else {
        std::println("error");
    }
}
```

### `std::mdspan`（`<mdspan>`）

多次元配列へのビューだ。画像処理では「1次元のバッファを幅×高さの2次元として見る」場面が頻出するので、`pixkit` の中核で使うことになる（第10章）。

```cpp
#include <mdspan>
#include <print>
#include <vector>

int main()
{
    std::vector<float> buffer(3 * 4, 0.0f);
    std::mdspan img(buffer.data(), 3, 4);   // 3行 × 4列

    img[1, 2] = 1.0f;                        // C++23 の多次元添字演算子

    std::println("extent(0)={} extent(1)={}", img.extent(0), img.extent(1));
    std::println("img[1,2]={}", img[1, 2]);
}
```

`img[1, 2]` という書き方はC++23で追加された多次元添字演算子だ。C++20以前ではコンパイルできない。**C++23が本当に有効になっているかの、良い試金石になる。**

### 標準ライブラリの実装状況には差がある

コンパイラがC++23を受け付けても、**標準ライブラリの個々の機能が実装されているとは限らない**。特に新しい機能を使うときは、実際にコンパイルして確かめるのが確実だ。ヘッダが存在するかどうかは、次の機能テストマクロでも調べられる。

```cpp
#if __has_include(<mdspan>)
#  include <mdspan>
#endif

#ifdef __cpp_lib_mdspan
// std::mdspan が使える
#endif
```

## 7.5　なぜ本書ではC++モジュールを使わないのか

C++20で導入されたモジュールは、ヘッダの `#include` を置き換える言語機能だ。ビルド時間の短縮とマクロ汚染の解消という明確な利点がある。CMakeも 3.28 以降で正式にサポートしている。

それでも本書では使わない。理由を挙げる。

### 理由1：本書の目的と直交する

本書のテーマは「CMakeでライブラリを作り、テストと静的解析を組み込み、パッケージとして公開する」ことだ。モジュールを導入すると、そこにビルドシステム側の複雑さが加わる。

- モジュールは**依存関係のスキャン**が必要になる（どのモジュールを先にコンパイルすべきかは、ソースを読まないと分からない）
- そのため使えるジェネレータが限られる（Ninja または Visual Studio）
- `FILE_SET CXX_MODULES` という専用の仕組みが必要になる

CMakeを初めて学ぶ人にとって、これは2つの難しい話を同時に抱えることになる。

### 理由2：周辺ツールが追いついていない

本書は第17章でClang-Tidy、第14〜16章でGoogleTest / Google Benchmarkを組み込む。

- Clang-Tidyがモジュールを扱うには追加の設定が必要で、MSVCとの組み合わせでは特に不安定
- `compile_commands.json` がモジュール依存を表現しきれない
- 多くのテストフレームワークは、まだヘッダ配布を前提にしている

本書の主要テーマ（静的解析の組み込み）が、モジュールを入れた瞬間に難易度が跳ね上がる。

### 理由3：配布の話がまだ固まっていない

第21〜24章で、ライブラリをインストールし、`find_package` 対応にし、vcpkgで公開する。**モジュールを含むライブラリのインストールと配布は、まだ標準的な手順が確立していない。** BMI（ビルド済みモジュールインターフェース）はコンパイラのバージョンごとに互換性がなく、そのまま配布できないからだ。

現状、モジュールを提供するライブラリは「モジュール版とヘッダ版の両方を用意する」という重い選択を迫られる。

### 本書の立場

**モジュールが不要だとは言っていない。** 単一のアプリケーションを自社内でビルドするなら、モジュールの利点は大きい。

しかし本書が扱うのは「他人に配るライブラリ」であり、そこでは**ヘッダによる配布が依然として現実解**だ。まず本書でCMakeの土台を身につけ、そのうえでモジュールに進むのが順序として正しい、というのが本書の判断である。

その代わり、本書ではモジュールが解決しようとした問題に、別の手段で向き合う。

- ビルド時間 → プリコンパイル済みヘッダ（`target_precompile_headers`）と、公開ヘッダを薄く保つ設計（第10章）
- マクロ汚染 → `PRIVATE` の徹底による、内部定義の非公開化（第6章、第9章）

## 7.6　警告設定と文字コード

C++23を有効にするだけでは足りない。実務で必要な設定を押さえる。

### 警告レベル

```cmake
target_compile_options(pixkit_warnings INTERFACE
    /W4          # 警告レベル4（実質的な最大。/Wall はノイズが多すぎる）
    /permissive- # 標準準拠モード
)
```

| フラグ | 意味 |
| --- | --- |
| `/W4` | 実務での標準。`/Wall` は標準ヘッダ由来の警告が数千出るので使わない |
| `/WX` | 警告をエラーにする。CIでは有効にする |
| `/permissive-` | MSVC独自の非標準な挙動を無効化する。**新規プロジェクトでは必須** |

`/permissive-` は特に重要だ。これがないと、他のコンパイラで通らないコードが書けてしまう。二段階名前探索（two-phase lookup）が正しく行われるようになるのもこのフラグだ。

> **CMP0092 のおかげで `/W3` の重複が起きない**
> かつてCMakeは、既定の `CMAKE_CXX_FLAGS` に `/W3` を含めていた。そこに `/W4` を追加すると、次の警告が出た。
> ```
> cl : コマンド ライン warning D9025: '/W3' より '/W4' が優先されます。
> ```
> 回避のために `string(REPLACE "/W3" "" CMAKE_CXX_FLAGS "${CMAKE_CXX_FLAGS}")` という汚い書き方が広まった。
> CMake 3.15のポリシー **CMP0092** でこれが解決され、既定フラグに警告オプションが入らなくなった。本書は `cmake_minimum_required(VERSION 3.28)` なのでこのポリシーは自動的に有効であり、**`/W3` を除去する小細工は不要**である。古い記事でこの手の処理を見かけたら、それは3.15以前向けの情報だ。

### 文字コード：`/utf-8`

**日本語環境では必須**の設定だ。

```cmake
target_compile_options(pixkit_options INTERFACE /utf-8)
```

MSVCは既定で、ソースファイルの文字コードをシステムのコードページ（日本語Windowsでは CP932）として解釈する。UTF-8で保存したソースに日本語コメントや文字列リテラルがあると、次が起きる。

- 文字化けする
- 警告 C4819 が大量に出る
- 最悪、コメント中の文字がバイト列としてエスケープと解釈され、**コンパイルエラーになる**

`/utf-8` は `/source-charset:utf-8` と `/execution-charset:utf-8` をまとめて指定するものだ。BOM無しUTF-8で保存し、このフラグを付ける、というのが現代の標準的な運用である。

### `/Zc:__cplusplus`

7.3節で述べたとおり、これがないと `__cplusplus` が `199711L` を返す。

```cmake
target_compile_options(pixkit_options INTERFACE /Zc:__cplusplus)
```

サードパーティのヘッダが `__cplusplus` を見て機能を切り替えていることがあるので、付けておくのが安全だ。

### その他

| フラグ | 意味 |
| --- | --- |
| `/EHsc` | 標準的な例外処理モデル。CMakeが既定で付けるので通常は不要 |
| `/MP` | 複数プロセスでの並列コンパイル。**Visual Studio ジェネレータでのみ有用**（Ninjaは自前で並列化する） |
| `/Zc:preprocessor` | 標準準拠のプリプロセッサ。可変引数マクロを厳密に扱う |
| `/bigobj` | オブジェクトファイルのセクション数上限を拡張。テンプレートを多用すると必要になる |

## 7.7　共通設定を `INTERFACE` ライブラリにまとめる

ここが本章の実践部分だ。

### 素朴なやり方の問題

```cmake
# ぜんぶのターゲットに同じことを書く
target_compile_options(pixkit-core   INTERFACE /W4 /permissive- /utf-8)
target_compile_options(pixkit-codec  PRIVATE   /W4 /permissive- /utf-8)
target_compile_options(pixkit-filter PRIVATE   /W4 /permissive- /utf-8)
target_compile_options(pixcli        PRIVATE   /W4 /permissive- /utf-8)
```

ターゲットが増えるたびに書き足すことになり、必ず書き忘れが出る。

かといって、グローバル変数に逃げるのも良くない。

```cmake
set(CMAKE_CXX_FLAGS "${CMAKE_CXX_FLAGS} /W4")   # 使わない
```

これは第6章4節で否定したディレクトリ単位の設定と同じで、`FetchContent` で取り込んだGoogleTestのソースにまで `/W4` が適用され、他人のコードの警告が大量に出ることになる。

### 解決策：設定を持つ `INTERFACE` ライブラリ

**設定そのものをターゲットにする。**

```cmake
# cmake/PixkitOptions.cmake

# --- 全ターゲット共通の基本設定 ---
add_library(pixkit_options INTERFACE)
add_library(pixkit::options ALIAS pixkit_options)

target_compile_features(pixkit_options INTERFACE cxx_std_23)

if(MSVC)
    target_compile_options(pixkit_options INTERFACE
        /utf-8              # ソースと実行文字セットをUTF-8に
        /permissive-        # 標準準拠モード
        /Zc:__cplusplus     # __cplusplus を正しく報告させる
        /Zc:preprocessor    # 標準準拠プリプロセッサ
        /EHsc
    )
endif()

# --- 警告設定（あえて分離する） ---
add_library(pixkit_warnings INTERFACE)
add_library(pixkit::warnings ALIAS pixkit_warnings)

option(PIXKIT_WARNINGS_AS_ERRORS "警告をエラーとして扱う" OFF)

if(MSVC)
    target_compile_options(pixkit_warnings INTERFACE
        /W4
        $<$<BOOL:${PIXKIT_WARNINGS_AS_ERRORS}>:/WX>
    )
endif()
```

使うときはリンクするだけだ。

```cmake
add_library(pixkit-codec STATIC src/ppm.cpp)
target_link_libraries(pixkit-codec
    PUBLIC  pixkit::options      # 規格・文字コードは利用側にも必要
    PRIVATE pixkit::warnings     # 警告設定は自分のビルドだけ
)
```

### `options` と `warnings` を分ける理由

これは意図的な設計だ。第6章3節の判断基準で考える。

| | `pixkit::options` | `pixkit::warnings` |
| --- | --- | --- |
| 内容 | C++23、`/utf-8`、`/permissive-` | `/W4`、`/WX` |
| 利用側にも必要か | **必要**（規格が合わないとヘッダが読めない） | **不要**（他人のコードの警告基準はその人が決める） |
| リンク方法 | `PUBLIC` | `PRIVATE` |

`/W4` を `PUBLIC` にすると、あなたのライブラリを使う人が `/W4` を強制されることになる。これは失礼な設計だ。**警告基準は各プロジェクトが自分で決めるもの**であり、ライブラリが押し付けてよいものではない。

### インストール時の注意（第22章への布石）

`pixkit-codec` が `pixkit::options` に `PUBLIC` でリンクしている、ということは、**`pixkit-codec` をインストールすると `pixkit_options` への参照も一緒にエクスポートされる**。利用側では `pixkit_options` というターゲットが存在しないので、`find_package` が失敗する。

これは第22章で正面から扱う典型的な落とし穴だ。解決策は「`pixkit_options` も一緒にインストール・エクスポートする」か、「`PUBLIC` にすべき最小限（`cxx_std_23`）だけを各ターゲットに直接書く」のいずれかになる。**いま覚えておく必要はないが、「設定ターゲットをPUBLICでリンクすると配布で問題になる」ことだけ頭の隅に置いてほしい。**

## 7.8　ジェネレータ式の基礎

7.7節で唐突に出てきた記法を説明する。

```cmake
$<$<BOOL:${PIXKIT_WARNINGS_AS_ERRORS}>:/WX>
```

これが**ジェネレータ式**だ。

### 構成時と生成時

第2章3節で「構成」と「生成」を区別した。ここでその区別が効く。

| | 評価される時期 | 書き方 |
| --- | --- | --- |
| 通常の `if` | **構成時** | `if(...)` |
| ジェネレータ式 | **生成時**（ターゲットごと、構成ごと） | `$<...>` |

なぜ2つ必要なのか。マルチ構成ジェネレータ（第2章7節）を思い出してほしい。Visual Studio ジェネレータでは、**1回の構成で Debug と Release の両方のビルド定義を作る**。だから構成時には「いまDebugなのかReleaseなのか」が決まっていない。

```cmake
# これは Visual Studio ジェネレータで動かない
if(CMAKE_BUILD_TYPE STREQUAL "Debug")
    target_compile_definitions(app PRIVATE PIXKIT_DEBUG)
endif()

# これは動く
target_compile_definitions(app PRIVATE $<$<CONFIG:Debug>:PIXKIT_DEBUG>)
```

**構成に依存する設定は、必ずジェネレータ式で書く。** これは本書で何度も繰り返すルールだ。

### 基本の形

ジェネレータ式は3つの形を覚えれば読める。

```cmake
$<条件:値>          # 条件が 1 なら「値」に、0 なら空文字列になる
$<問い合わせ>        # 情報を返す
$<関数:引数>        # 変換する
```

### よく使うもの

```cmake
# 構成による分岐
$<$<CONFIG:Debug>:/Od>
$<$<CONFIG:Release,RelWithDebInfo>:/O2>       # 複数指定できる

# コンパイラによる分岐
$<$<CXX_COMPILER_ID:MSVC>:/W4>
$<$<CXX_COMPILER_ID:GNU,Clang>:-Wall -Wextra>

# 言語による分岐（C と C++ が混在するとき）
$<$<COMPILE_LANGUAGE:CXX>:/std:c++23preview>

# 真偽値
$<$<BOOL:${SOME_VAR}>:値>
$<IF:$<CONFIG:Debug>,値A,値B>                  # 三項演算子

# ターゲット情報の問い合わせ
$<TARGET_FILE:pixcli>              # 実行ファイルのフルパス
$<TARGET_FILE_DIR:pixcli>          # そのディレクトリ
$<TARGET_RUNTIME_DLLS:pixcli>      # 実行に必要なDLLの一覧（第11章）

# パスの出し分け（第21〜22章の中核）
$<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
$<INSTALL_INTERFACE:include>
```

### 落とし穴

**ジェネレータ式は `message()` で表示できない。**

```cmake
message(STATUS "${MY_GENEX}")     # $<$<CONFIG:Debug>:/Od> という文字列がそのまま出る
```

構成時にはまだ評価されていないからだ。中身を確認したいときは、`compile_commands.json` を見るか、`file(GENERATE ...)` を使う。

```cmake
file(GENERATE OUTPUT "${CMAKE_BINARY_DIR}/genex-check-$<CONFIG>.txt"
     CONTENT "flags = $<TARGET_PROPERTY:pixkit-codec,COMPILE_OPTIONS>\n")
```

生成時に評価されてファイルに書き出されるので、それを読めばよい。

**リストの区切りに注意する。**

```cmake
# 間違い：スペース区切りで書くと1つの引数として扱われる
target_compile_options(app PRIVATE $<$<CXX_COMPILER_ID:GNU>:-Wall -Wextra>)

# 正しい
target_compile_options(app PRIVATE $<$<CXX_COMPILER_ID:GNU>:-Wall;-Wextra>)
# または
target_compile_options(app PRIVATE
    $<$<CXX_COMPILER_ID:GNU>:-Wall>
    $<$<CXX_COMPILER_ID:GNU>:-Wextra>
)
```

第5章5節で学んだ「リストはセミコロン区切り」が、ここでも効いてくる。

## この章のまとめ

- **`target_compile_features(... cxx_std_23)`** は「C++23が必要」という要求を宣言し、`PUBLIC`/`INTERFACE` で伝播する。ライブラリを作る側はこちらを使う
- `CXX_STANDARD` プロパティは「この規格でコンパイルする」という指定で、伝播しない。使う場合は **`CXX_STANDARD_REQUIRED ON` を必ず付ける**（付けないと黙って古い規格に落ちる）
- **CMakeが `cxx_std_23` に対してMSVCへ渡すのは `/std:c++latest` であり、`/std:c++23preview` ではない。** C++26の機能まで使えてしまうので、`compile_commands.json` で実際のフラグを確認する習慣を持つ
- `__cplusplus` はMSVCでは `/Zc:__cplusplus` がないと `199711L` を返す。`_MSVC_LANG` は常に正しい
- 日本語環境では **`/utf-8` が必須**。`/permissive-` も新規プロジェクトでは必須
- CMake 3.15の **CMP0092** により、既定フラグに `/W3` が入らなくなった。`/W3` を除去する小細工は不要
- 共通設定は **`INTERFACE` ライブラリ**（`pixkit::options` / `pixkit::warnings`）にまとめ、各ターゲットが `target_link_libraries` でリンクする。グローバル変数 `CMAKE_CXX_FLAGS` は使わない
- **警告設定は `PRIVATE`、規格や文字コードは `PUBLIC`。** 警告基準を利用側に押し付けない
- **ジェネレータ式 `$<...>` は生成時に評価される。** 構成に依存する設定（`$<$<CONFIG:Debug>:...>`）は必ずこれで書く。`if(CMAKE_BUILD_TYPE ...)` はマルチ構成ジェネレータで動かない

次の第8章では、ここまでの部品を組み合わせて `pixkit` プロジェクトの骨格を作る。ディレクトリ構成、`add_subdirectory`、バージョン管理、機能スイッチ、出力先の統一を扱い、第3部でライブラリを書き始める準備を整える。
