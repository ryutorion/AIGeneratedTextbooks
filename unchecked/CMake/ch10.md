# 第10章　ヘッダーオンリーライブラリ（`pixkit::core`）

## この章のゴール

- `add_library(... INTERFACE)` の性質を理解する
- **コンパイル対象を持たないターゲットを、IDEに表示させる**
- `FILE_SET HEADERS` でヘッダを宣言する（第21章のインストールへの布石）
- ヘッダーオンリーライブラリを**テストと静的解析の対象にする**方法を身につける
- `inline` / `constexpr` とODR、テンプレートのコストを理解する
- ヘッダーオンリー化の代償をビルド時間で測る
- 静的ライブラリ版とヘッダーオンリー版を切り替えられるようにする

第8章で作った `pixkit::core` は、バージョンヘッダしか持たない空箱だった。この章で中身を入れる。画素型と色空間変換だ。

## 10.1　`INTERFACE` ライブラリの性質

### コンパイルされないライブラリ

```cmake
add_library(pixkit-core INTERFACE)
add_library(pixkit::core ALIAS pixkit-core)
```

`INTERFACE` ライブラリは、**ビルド成果物を持たない**。`.lib` も `.obj` も作られない。あるのは「使用要件の束」だけだ。

第7章7節で作った `pixkit_options` / `pixkit_warnings` と、仕組みとしてはまったく同じものである。違うのは中身が「コンパイルオプション」か「ヘッダ群」かだけだ。

| | 通常のライブラリ | `INTERFACE` ライブラリ |
| --- | --- | --- |
| ソースのコンパイル | する | **しない** |
| `.lib` の生成 | する | **しない** |
| `target_*` のキーワード | `PUBLIC`/`PRIVATE`/`INTERFACE` | **`INTERFACE` のみ** |
| リンクされたとき | `.lib` が結合される | 使用要件だけが伝播する |

### なぜこの仕組みが必要か

第9章9節の実験を思い出してほしい。ヘッダしか列挙していない `STATIC` ライブラリを作ろうとすると、こうなった。

```
CMake Error: CMake can not determine linker language for target: pixkit-codec
```

CMakeにとってヘッダはソースではないので、「何をコンパイルして何をリンクするのか」が決まらない。ヘッダーオンリーライブラリには、**そもそもコンパイルもリンクもしないターゲット種別**が必要だったのだ。それが `INTERFACE` である。

### `INTERFACE` ライブラリでできること

```cmake
add_library(pixkit-core INTERFACE)

target_include_directories(pixkit-core INTERFACE ...)   # ヘッダの場所
target_compile_features   (pixkit-core INTERFACE cxx_std_23)
target_compile_definitions(pixkit-core INTERFACE PIXKIT_CORE=1)
target_link_libraries     (pixkit-core INTERFACE pixkit::options)
target_sources            (pixkit-core INTERFACE FILE_SET HEADERS ...)
```

リンクした相手に対して、通常のライブラリと同じことができる。**利用側から見れば、静的ライブラリとの区別はつかない。**

```cmake
target_link_libraries(pixcli PRIVATE pixkit::core pixkit::codec)
```

`pixkit::core` がヘッダーオンリーで `pixkit::codec` が静的、という違いを利用側は意識しなくてよい。これは第11章でDLLにしても同じで、**ライブラリの形態を後から変えても、利用側のコードは変わらない**。CMakeの設計の良いところだ。

## 10.2　IDEにヘッダを表示させる

### 問題

`INTERFACE` ライブラリには、既定では何のファイルも紐づかない。Visual Studio のCMakeターゲットビュー（第3章2節）を開いても、`pixkit-core` は空のまま表示される。ヘッダを編集したいのに、ソリューションエクスプローラから開けない。

### 解決：`PRIVATE` でソースを追加する

CMake 3.19以降、`INTERFACE` ライブラリにも**自分自身のソース**を持たせられるようになった。

```cmake
target_sources(pixkit-core
    PRIVATE
        include/pixkit/core/pixel.hpp
        include/pixkit/core/color.hpp
        include/pixkit/core/image.hpp
)
```

`INTERFACE` ライブラリなのに `PRIVATE` を指定する、というのは奇妙に見えるが、これで正しい。ここでの `PRIVATE` は「このターゲット自身に属するファイル」という意味であり、**利用側には伝播しない**。ヘッダはコンパイルされないので、ビルド動作には何の影響もない。**純粋にIDEの表示のためだけの記述**だ。

確認するにはプロパティを読む。

```cmake
get_target_property(S pixkit-core SOURCES)
message(STATUS "SOURCES = ${S}")
```

### `FILE_SET HEADERS` でヘッダを宣言する

もう1つ、別の目的の記述がある。CMake 3.23で追加された仕組みだ。

```cmake
target_sources(pixkit-core
    INTERFACE
        FILE_SET HEADERS
            BASE_DIRS ${CMAKE_CURRENT_SOURCE_DIR}/include
            FILES
                ${CMAKE_CURRENT_SOURCE_DIR}/include/pixkit/core/pixel.hpp
                ${CMAKE_CURRENT_SOURCE_DIR}/include/pixkit/core/color.hpp
                ${CMAKE_CURRENT_SOURCE_DIR}/include/pixkit/core/image.hpp
)
```

これは「このターゲットの公開ヘッダはこれで、`BASE_DIRS` からの相対パスで構造を保つ」という宣言だ。効果は2つある。

1. **`BASE_DIRS` が自動的にインクルードパスに追加される**（`target_include_directories` を書かなくてもよくなる）
2. **第21章の `install(TARGETS ... FILE_SET HEADERS)` で、ディレクトリ構造を保ったままインストールできる**

2番目が本命だ。従来は `install(DIRECTORY include/ DESTINATION include)` のようにディレクトリごとコピーしていたが、それだと「どのヘッダがどのターゲットのものか」がCMakeから見えなかった。`FILE_SET` はその情報をターゲットに持たせる。

### 2つは目的が違う

紛らわしいので整理する。

| 記述 | 目的 | 効果 |
| --- | --- | --- |
| `target_sources(... PRIVATE headers)` | **IDEに表示する** | `SOURCES` プロパティに入る |
| `target_sources(... INTERFACE FILE_SET HEADERS ...)` | **公開ヘッダを宣言する** | `INTERFACE_HEADER_SETS` に入る。インストール時に使う |

**`FILE_SET HEADERS` を書いても、`SOURCES` には入らない。** つまりIDEには表示されない。両方の効果が欲しければ、両方書く。

```cmake
target_sources(pixkit-core
    INTERFACE
        FILE_SET HEADERS
            BASE_DIRS ${CMAKE_CURRENT_SOURCE_DIR}/include
            FILES     ${PIXKIT_CORE_HEADERS}
    PRIVATE
        ${PIXKIT_CORE_HEADERS}
)
```

同じリストを2回書くことになるので、変数にまとめておくとよい。

> **ヘッダのリストを `file(GLOB)` で集めたくなるが**
> 第8章7節で述べたとおり、やめておく。ヘッダを追加する頻度は低く、明示のコストは小さい。

## 10.3　`INTERFACE` ライブラリへの指定はすべて `INTERFACE`

`INTERFACE` ライブラリに `PUBLIC` を指定するとエラーになる。

```cmake
target_compile_features(pixkit-core PUBLIC cxx_std_23)
```

```
CMake Error at libs/core/CMakeLists.txt:10 (target_compile_features):
  target_compile_features may only set INTERFACE properties on INTERFACE targets
```

理由は明快だ。`PUBLIC` は「自分にも、使う人にも」という意味だが、`INTERFACE` ライブラリには「自分のコンパイル」が存在しない。だから「使う人だけ」を意味する `INTERFACE` しか指定しようがない。

例外は10.2節の `target_sources(... PRIVATE ...)` だけで、これはコンパイルではなくIDE表示のための特別扱いである。

### 実務上の注意

第9章の `pixkit-codec` と書き方が違うことになる。

```cmake
# 静的ライブラリ
target_link_libraries(pixkit-codec
    PUBLIC  pixkit::core
    PRIVATE pixkit::warnings      # 自分のコンパイルにだけ適用
)

# ヘッダーオンリー
target_link_libraries(pixkit-core
    INTERFACE pixkit::options     # PRIVATE は書けない
)
```

`pixkit-core` に `pixkit::warnings` をリンクする方法はない（自分のコンパイルがないので意味がない）。**ヘッダーオンリーライブラリの警告は、それを `#include` する誰かのコンパイル時に出る。** これが次節の話につながる。

## 10.4　テストと静的解析の対象にする

### 何もしないと、誰も検査してくれない

ヘッダーオンリーライブラリの最大の弱点はこれだ。

- **コンパイルされないので、構文エラーにすら気づけない**
- 第17章のClang-Tidyは、コンパイル単位（`.cpp`）を解析対象にする。誰も `#include` しないヘッダは解析されない
- テンプレートは、インスタンス化されるまで大半の検査が行われない

「ヘッダを書き換えてコミットしたら、実は壊れていた」が普通に起きる。

### 解決策：コンパイル検査用のターゲットを作る

**すべての公開ヘッダを `#include` するだけの `.cpp` を用意し、それをコンパイルする。**

```cpp
// libs/core/compile_check/compile_check.cpp
//
// このファイルの目的は、pixkit::core の全公開ヘッダが
// 単体でコンパイルできることを保証すること。
// 実行はされない。Clang-Tidy（第17章）の解析対象にもなる。

#include <pixkit/core/color.hpp>
#include <pixkit/core/image.hpp>
#include <pixkit/core/pixel.hpp>
#include <pixkit/core/version.hpp>
```

```cmake
add_library(pixkit-core-compile-check OBJECT
    compile_check/compile_check.cpp
)
target_link_libraries(pixkit-core-compile-check
    PRIVATE pixkit::core pixkit::warnings
)
set_target_properties(pixkit-core-compile-check PROPERTIES FOLDER "libs/internal")
```

`OBJECT` ライブラリにしているのは、`.lib` を作る必要すらないからだ。`.obj` ができれば目的は達している。

これで得られるものは大きい。

| 効果 | 説明 |
| --- | --- |
| 構文エラーの検出 | ヘッダを壊せばビルドが落ちる |
| **インクルード漏れの検出** | 各ヘッダが単体で完結しているかが分かる |
| 警告の検査 | `pixkit::warnings` をリンクしているので `/W4` が効く |
| **Clang-Tidyの対象になる** | 第17章 |

2番目が特に重要だ。`color.hpp` が `pixel.hpp` の型を使っているのに `#include` していない場合、実際のコードではたまたま先に `pixel.hpp` が読まれていて動いてしまう。しかし**利用者が `color.hpp` だけを `#include` したら壊れる**。この事故は、ヘッダを個別にコンパイルしてみないと発見できない。

### さらに厳密にやるなら

ヘッダ1つにつき `.cpp` を1つ作れば、「単体で完結しているか」を1つずつ検証できる。

```cmake
set(PIXKIT_CORE_HEADERS pixel.hpp color.hpp image.hpp)

foreach(H IN LISTS PIXKIT_CORE_HEADERS)
    cmake_path(GET H STEM STEM)
    set(GEN "${CMAKE_CURRENT_BINARY_DIR}/compile_check/check_${STEM}.cpp")
    file(WRITE "${GEN}" "#include <pixkit/core/${H}>\n")
    list(APPEND GENERATED_CHECKS "${GEN}")
endforeach()

add_library(pixkit-core-compile-check OBJECT ${GENERATED_CHECKS})
target_link_libraries(pixkit-core-compile-check PRIVATE pixkit::core pixkit::warnings)
```

`file(WRITE)` で構成時にソースを生成している。第5章で学んだCMake言語が、ここで実用的に効いてくる。

### テストとの関係

第14章でGoogleTestを導入すると、テストコードが `pixkit::core` を `#include` するので、そちらでもコンパイル検査は行われる。しかし、

- テストがまだ書かれていないヘッダは検査されない
- テストは `PIXKIT_BUILD_TESTS=OFF` で切られることがある

ので、**コンパイル検査ターゲットは独立して持っておく価値がある。**

## 10.5　`inline` / `constexpr` とODR

### ODR（One Definition Rule）違反

ヘッダに関数の実体を書くと、それを `#include` した各翻訳単位に実体ができる。リンク時に重複定義エラーになる。

```cpp
// pixel.hpp
float clamp01(float v) { return ...; }    // 2つの .cpp から include すると LNK2005
```

回避方法は3つある。

| 方法 | 書き方 | 備考 |
| --- | --- | --- |
| `inline` | `inline float clamp01(float v)` | 最も基本 |
| `constexpr` | `constexpr float clamp01(float v)` | **関数は暗黙に `inline`** |
| テンプレート | `template<class T> T clamp01(T v)` | 暗黙に `inline` 相当 |

`constexpr` 関数とテンプレートは自動的に `inline` の性質を持つので、明示不要だ。

**変数には注意が要る。**

```cpp
// 悪い例：翻訳単位ごとに別の実体ができる（C++17より前）
constexpr int max_channels = 4;

// 良い例
inline constexpr int max_channels = 4;
```

C++17以降、`constexpr` 変数は暗黙に `inline` になる……のは**名前空間スコープの変数についてのみ**で、クラスの `static` メンバなどでは事情が異なる。**迷ったら `inline constexpr` と書く。** 第8章で作った `version.hpp` もそう書いてある。

### `inline` はインライン展開の指示ではない

念のため確認しておく。`inline` キーワードの現代的な意味は「**複数の翻訳単位に同じ定義があってよい**」であって、「インライン展開せよ」ではない。展開の判断はコンパイラが行う。

### テンプレートのコスト

ヘッダーオンリーライブラリは、テンプレートを使いたくなる。

```cpp
template <class T>
constexpr T clamp01(T v) { ... }
```

汎用性は上がるが、代償がある。

- **利用側のコンパイル時間が増える**（テンプレートの実体化はコンパイルのたびに行われる）
- エラーメッセージが長大になる
- ABI境界を越えられない（第11章5節）

**本書の `pixkit::core` では、テンプレートを最小限にする。** 画素型は `Rgb8` と `Rgb32f` の2つに限定し、それぞれに非テンプレートのオーバーロードを提供する。ヘッダーオンリーだからといってテンプレートにする必然性はない。

### `constexpr` の恩恵を確認する

`constexpr` にしておくと、コンパイル時に結果を検証できる。

```cpp
static_assert(to_gray(Rgb8{255, 255, 255}) == Rgb8{255, 255, 255});
static_assert(luminance(Rgb8{255, 0, 0}) == 76);
```

これは「テストの一部をコンパイル時に済ませる」ことでもある。ビルドが通れば、この検証は通っている。第14章で書くランタイムのテストと、役割分担ができる。

## 10.6　ヘッダーオンリー化の代償を測る

### 何が起きるか

ヘッダーオンリーライブラリは、**利用側のすべての翻訳単位でコンパイルされ直す**。`.cpp` が50個あれば50回だ。静的ライブラリなら1回で済む。

これは無視できるとは限らない。標準ライブラリのヘッダを大量に `#include` する公開ヘッダを書くと、利用側のビルド時間が目に見えて延びる。

### 測る

**方法1：単純に時間を測る**

```
cmake --build --preset x64-release --clean-first
```

PowerShellなら次のようにする。

```powershell
Measure-Command { cmake --build --preset x64-release --clean-first }
```

**方法2：MSVCのコンパイル時間レポート**

```cmake
target_compile_options(pixkit_options INTERFACE
    $<$<BOOL:${PIXKIT_PROFILE_BUILD}>:/Bt+>          # 各フェーズの所要時間
    $<$<BOOL:${PIXKIT_PROFILE_BUILD}>:/d1reportTime> # 関数・ヘッダごとの内訳
)
```

`/d1reportTime` は非公式のフラグだが、「どのヘッダのパースに何ミリ秒かかったか」を出してくれるので、重いヘッダの特定に有効だ。

**方法3：Ninjaのビルド統計**

```
ninja -C out/build/x64-release -t targets
ninja -C out/build/x64-release -d stats
```

Ninjaは `.ninja_log` に各ターゲットの所要時間を記録している。集計すれば、どのファイルが遅いかが分かる。

### 対策

| 対策 | 内容 | 扱う章 |
| --- | --- | --- |
| 公開ヘッダを薄く保つ | `<algorithm>` などを公開ヘッダで `#include` しない | 本章 |
| 前方宣言を使う | 型の完全定義が不要な場所では宣言だけにする | 本章 |
| プリコンパイル済みヘッダ | `target_precompile_headers` | 本章 |
| 静的ライブラリに切り出す | テンプレートでない部分を `.cpp` に移す | 10.7節 |

### プリコンパイル済みヘッダ

```cmake
target_precompile_headers(pixkit-codec PRIVATE
    <vector>
    <string>
    <filesystem>
)
```

指定したヘッダを1回だけコンパイルして再利用する。効果は大きいが、注意点がある。

- **`PUBLIC` にすると、利用側にも強制される**（利用側のビルドを壊しうる）。`PRIVATE` にする
- PCHに含めたヘッダを個々の `.cpp` で `#include` し忘れても通ってしまう。**他人がその `.cpp` を単体でコンパイルすると壊れる**
- `target_precompile_headers(tgt REUSE_FROM other)` で共有できる

本書では第16章のベンチマークで、ビルド時間の改善効果を実測する。

## 10.7　静的ライブラリ版と切り替えられるようにする

ヘッダーオンリーは配布が楽（ヘッダをコピーするだけ）だが、ビルド時間の代償がある。**両方を選べるようにする**のが親切な設計だ。

```cmake
option(PIXKIT_CORE_HEADER_ONLY "pixkit::core をヘッダーオンリーで使う" ON)

if(PIXKIT_CORE_HEADER_ONLY)
    add_library(pixkit-core INTERFACE)
    target_include_directories(pixkit-core INTERFACE
        $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
        $<INSTALL_INTERFACE:include>
    )
    target_compile_definitions(pixkit-core INTERFACE PIXKIT_CORE_HEADER_ONLY=1)
    target_link_libraries(pixkit-core INTERFACE pixkit::options)
else()
    add_library(pixkit-core STATIC src/core.cpp)
    target_include_directories(pixkit-core
        PUBLIC
            $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
            $<INSTALL_INTERFACE:include>
    )
    target_link_libraries(pixkit-core
        PUBLIC  pixkit::options
        PRIVATE pixkit::warnings
    )
endif()

add_library(pixkit::core ALIAS pixkit-core)
```

コード側は、マクロで実体の置き場所を切り替える。

```cpp
// pixkit/core/pixel.hpp
#ifdef PIXKIT_CORE_HEADER_ONLY
#  define PIXKIT_CORE_INLINE inline
#else
#  define PIXKIT_CORE_INLINE
#endif

PIXKIT_CORE_INLINE Rgb8 to_gray(Rgb8 c);   // ヘッダーオンリーなら定義もここに置く
```

### やりすぎないこと

この仕組みは**保守コストが高い**。2通りのビルド構成をCIで検証しなければならず、マクロが増えてコードが読みにくくなる。

`constexpr` 関数と小さな構造体しかないライブラリなら、素直にヘッダーオンリー一本でよい。**選択肢を用意するのは、実測してビルド時間が問題になってからで遅くない。**

本書の `pixkit::core` はヘッダーオンリー一本で進める。この節は「そういう選択肢がある」ことと、`ALIAS` を最後に1回だけ書けば**利用側は分岐を意識しなくてよい**（第6章6節）ことを示すために置いた。

## ハンズオン：画素型と色空間変換のライブラリ

### 手順1：画素型を書く

`libs/core/include/pixkit/core/pixel.hpp`

```cpp
#pragma once

#include <cstdint>

namespace pixkit {

struct Rgb8 {
    std::uint8_t r = 0;
    std::uint8_t g = 0;
    std::uint8_t b = 0;

    friend constexpr bool operator==(const Rgb8&, const Rgb8&) noexcept = default;
};

// PPMのバイナリと直接やり取りするので、パディングが入っては困る
static_assert(sizeof(Rgb8) == 3, "Rgb8 は3バイトでなければならない");

struct Rgb32f {
    float r = 0.0f;
    float g = 0.0f;
    float b = 0.0f;

    friend constexpr bool operator==(const Rgb32f&, const Rgb32f&) noexcept = default;
};

[[nodiscard]] constexpr float clamp01(float v) noexcept
{
    return v < 0.0f ? 0.0f : (v > 1.0f ? 1.0f : v);
}

[[nodiscard]] constexpr std::uint8_t to_u8(float v) noexcept
{
    return static_cast<std::uint8_t>(clamp01(v) * 255.0f + 0.5f);
}

[[nodiscard]] constexpr Rgb32f to_f32(Rgb8 c) noexcept
{
    return Rgb32f{ c.r / 255.0f, c.g / 255.0f, c.b / 255.0f };
}

[[nodiscard]] constexpr Rgb8 to_u8(Rgb32f c) noexcept
{
    return Rgb8{ to_u8(c.r), to_u8(c.g), to_u8(c.b) };
}

}  // namespace pixkit
```

`static_assert(sizeof(Rgb8) == 3)` は重要だ。**`Rgb8` の配列を、そのままPPMのバイト列として書き出す**ので、パディングが入ると壊れる。

### 手順2：色変換を書く

`libs/core/include/pixkit/core/color.hpp`

```cpp
#pragma once

#include <pixkit/core/pixel.hpp>

namespace pixkit {

// ITU-R BT.601 の輝度係数
[[nodiscard]] constexpr float luminance(Rgb32f c) noexcept
{
    return 0.299f * c.r + 0.587f * c.g + 0.114f * c.b;
}

[[nodiscard]] constexpr std::uint8_t luminance(Rgb8 c) noexcept
{
    return to_u8(luminance(to_f32(c)));
}

[[nodiscard]] constexpr Rgb8 to_gray(Rgb8 c) noexcept
{
    const std::uint8_t y = luminance(c);
    return Rgb8{ y, y, y };
}

[[nodiscard]] constexpr Rgb32f lerp(Rgb32f a, Rgb32f b, float t) noexcept
{
    return Rgb32f{ a.r + (b.r - a.r) * t,
                   a.g + (b.g - a.g) * t,
                   a.b + (b.b - a.b) * t };
}

// コンパイル時に検証する
static_assert(to_gray(Rgb8{255, 255, 255}) == Rgb8{255, 255, 255});
static_assert(to_gray(Rgb8{0, 0, 0}) == Rgb8{0, 0, 0});
static_assert(luminance(Rgb8{255, 0, 0}) == 76);

}  // namespace pixkit
```

`#include <pixkit/core/pixel.hpp>` を**忘れずに書く**。10.4節で述べたインクルード漏れの話は、まさにこれのことだ。

### 手順3：画像型とビューを書く

`libs/core/include/pixkit/core/image.hpp`

```cpp
#pragma once

#include <pixkit/core/pixel.hpp>

#include <cstddef>
#include <span>
#include <vector>

namespace pixkit {

// 所有権を持たない2次元ビュー
class ImageView {
public:
    constexpr ImageView() noexcept = default;
    constexpr ImageView(Rgb8* data, int width, int height) noexcept
        : data_(data), width_(width), height_(height) {}

    [[nodiscard]] constexpr int  width()  const noexcept { return width_; }
    [[nodiscard]] constexpr int  height() const noexcept { return height_; }
    [[nodiscard]] constexpr bool empty()  const noexcept { return width_ <= 0 || height_ <= 0; }

    // C++23 の多次元添字演算子
    [[nodiscard]] constexpr Rgb8& operator[](int x, int y) noexcept {
        return data_[static_cast<std::size_t>(y) * width_ + x];
    }
    [[nodiscard]] constexpr const Rgb8& operator[](int x, int y) const noexcept {
        return data_[static_cast<std::size_t>(y) * width_ + x];
    }

    [[nodiscard]] constexpr Rgb8* data() const noexcept { return data_; }

private:
    Rgb8* data_ = nullptr;
    int   width_  = 0;
    int   height_ = 0;
};

// 所有権を持つ画像
class Image {
public:
    Image() = default;
    Image(int width, int height)
        : width_(width), height_(height),
          pixels_(static_cast<std::size_t>(width) * height) {}

    [[nodiscard]] int  width()  const noexcept { return width_; }
    [[nodiscard]] int  height() const noexcept { return height_; }
    [[nodiscard]] bool empty()  const noexcept { return pixels_.empty(); }
    [[nodiscard]] std::size_t pixel_count() const noexcept { return pixels_.size(); }
    [[nodiscard]] std::size_t byte_size()   const noexcept { return pixels_.size() * sizeof(Rgb8); }

    [[nodiscard]] Rgb8& operator[](int x, int y) noexcept {
        return pixels_[static_cast<std::size_t>(y) * width_ + x];
    }
    [[nodiscard]] const Rgb8& operator[](int x, int y) const noexcept {
        return pixels_[static_cast<std::size_t>(y) * width_ + x];
    }

    [[nodiscard]] ImageView view() noexcept {
        return ImageView(pixels_.data(), width_, height_);
    }

    [[nodiscard]] std::span<Rgb8>       pixels()       noexcept { return pixels_; }
    [[nodiscard]] std::span<const Rgb8> pixels() const noexcept { return pixels_; }

    friend bool operator==(const Image&, const Image&) = default;

private:
    int width_  = 0;
    int height_ = 0;
    std::vector<Rgb8> pixels_;
};

}  // namespace pixkit
```

> **`std::mdspan` を使わないのはなぜか**
> C++23には多次元ビューの標準型 `std::mdspan` がある（第7章4節で触れた）。本来ならそれを使うべき場面だ。本書が独自の `ImageView` を書いているのは、
> - 実装状況がコンパイラ・標準ライブラリのバージョンによって差がある
> - 独自クラスのほうが、`operator[](int,int)` の仕組みを説明しやすい
> という教材上の都合による。実務では `std::mdspan` を検討してほしい。`ImageView` を `std::mdspan` に差し替えるのは良い練習になる（発展課題）。

### 手順9：`pixkit-codec` を `pixkit::core` の型に載せ替える

第9章の `pixkit-codec` は、独自の `ImageU8` を持っていた。これを `pixkit::Image` に統一する。

`libs/codec/include/pixkit/codec/ppm.hpp` を変更する。

```cpp
#pragma once

#include <pixkit/core/image.hpp>       // ← core の型を使う

#include <expected>
#include <filesystem>
#include <string_view>

namespace pixkit::codec {

enum class CodecError { /* 変更なし */ };

std::string_view to_string(CodecError e) noexcept;

[[nodiscard]] std::expected<Image, CodecError>
load_ppm(const std::filesystem::path& path);

[[nodiscard]] std::expected<void, CodecError>
save_ppm(const std::filesystem::path& path, const Image& image);

}  // namespace pixkit::codec
```

`ppm.cpp` も書き換える。**まず関数の定義側のシグネチャを、ヘッダに合わせて `ImageU8` → `Image` に直す**（ここを忘れると「宣言と定義が食い違う」という分かりにくいエラーの山になる）。

```cpp
std::expected<Image, CodecError> load_ppm(const std::filesystem::path& path)
std::expected<void, CodecError>  save_ppm(const std::filesystem::path& path, const Image& image)
```

そのうえで中身を直す。`Rgb8` が3バイトであることが保証されている（`static_assert` で確認済み）ので、バイト列との変換は `std::memcpy` 一発で済む。`<cstring>` の `#include` を追加すること。

```cpp
// 読み込み
Image image(*w, *h);
if (buf.size() - pos < image.byte_size()) {
    return std::unexpected(CodecError::TruncatedData);
}
std::memcpy(image.pixels().data(), buf.data() + pos, image.byte_size());
return image;

// 書き出し
out << "P6\n" << image.width() << ' ' << image.height() << "\n255\n";
out.write(reinterpret_cast<const char*>(image.pixels().data()),
          static_cast<std::streamsize>(image.byte_size()));
```

**CMake側の変更は必要ない。** 第9章ですでにこう書いてあるからだ。

```cmake
target_link_libraries(pixkit-codec
    PUBLIC  pixkit::core        # 公開ヘッダで core の型を使う → PUBLIC
    PRIVATE pixkit::warnings
)
```

いまや `ppm.hpp` が `<pixkit/core/image.hpp>` を `#include` しているので、`PUBLIC` である必然性がはっきりした。**第6章3節の判断基準「公開ヘッダが `#include` しているか」が、そのまま当てはまる。**

試しに `PRIVATE` に変えてビルドすると、`pixcli` 側で `pixkit/core/image.hpp` が見つからずに失敗する。

### 発展課題

1. `ImageView` を `std::mdspan` に置き換えてみる。`img[1, 2]` の添字の順序（行優先か列優先か）に注意すること
2. 手順4の `foreach` を使ったヘッダ個別のコンパイル検査（10.4節）を実装し、ヘッダ1つずつが単体で完結していることを検証する
3. `pixel.hpp` に `#include <vector>` を追加し（不要なインクルード）、`/Bt+` でビルド時間の変化を測る
4. `Rgb8` に `std::uint8_t a` を追加して `sizeof` が4になり、`static_assert` が落ちることを確認する
5. `target_precompile_headers(pixkit-codec PRIVATE <vector> <filesystem>)` を追加し、ビルド時間の変化を測る

## この章のまとめ

- `add_library(名前 INTERFACE)` は**ビルド成果物を持たない**ターゲット。指定できるキーワードは `INTERFACE` のみ（例外はIDE表示用の `target_sources(... PRIVATE ...)`）
- **`target_sources(... PRIVATE headers)` はIDE表示のため、`target_sources(... INTERFACE FILE_SET HEADERS ...)` は公開ヘッダの宣言のため。** 目的が違うので、必要なら両方書く。`FILE_SET` は第21章のインストールで使う
- ヘッダーオンリーライブラリは**誰もコンパイルしないので検査されない**。全公開ヘッダを `#include` するだけの `.cpp` を作り、`OBJECT` ライブラリとしてビルドする。**インクルード漏れの検出**とClang-Tidy（第17章）の対象化に効く
- ヘッダに実体を書くときは `inline` / `constexpr` / テンプレートのいずれかにする。変数は **`inline constexpr`** と書く
- `constexpr` + `static_assert` で、**テストの一部をコンパイル時に済ませられる**
- ヘッダーオンリーは利用側のコンパイル時間を増やす。`/Bt+` `/d1reportTime`、Ninjaの `.ninja_log`、`target_precompile_headers` を使って測り、対処する
- 静的ライブラリ版との切り替えは実現できるが**保守コストが高い**。必要になってからでよい。`ALIAS` を最後に定義すれば、利用側は分岐を意識しない

次の第11章では、3種類目のライブラリ形態である**動的ライブラリ（DLL）**を作る。エクスポートマクロ、DLL境界を越えてはいけないもの、実行時のDLL探索という、Windowsに固有の話が中心になる。ここまでで最も注意深く読む必要がある章だ。
