# 第15章　テストを育てる

## この章のゴール

- テストのディレクトリ構成とターゲット分割を設計する
- フィクスチャ、パラメタライズドテスト、型付きテストを使う
- **テストデータをどこに置き、どう参照するか**を決める
- 例外テスト・デステストとDLL境界の関係を理解する
- Windows環境でのカバレッジ計測（OpenCppCoverage）をCMakeから回す
- **`workflowPresets` でローカルとCIのコマンドを一本化する**
- GitHub Actions で構成 → ビルド → テストを回す

第14章でテストは動くようになった。この章は「動くテスト」を「保守できるテスト」にする。

---

## 15.1　テストのターゲットを分割する

### 1つの実行ファイルに全部入れる問題

第14章では `pixkit-tests` という1つの実行ファイルにすべてのテストを入れた。小規模なうちはこれでよい。しかし増えてくると、

- **ビルドが遅い**：1つのテストを直すたびに、全体がリンクし直される
- **関心が混ざる**：`pixkit::core` のテストが `pixkit::filter` の変更でリンクエラーになる
- **依存が肥大する**：core のテストだけ動かしたいのに、DLLまで必要になる

### ライブラリごとに分ける

```
tests/
├── CMakeLists.txt          ← GoogleTestの取得、共通設定
├── core/
│   ├── CMakeLists.txt
│   ├── test_pixel.cpp
│   ├── test_color.cpp
│   └── test_image.cpp
├── codec/
│   ├── CMakeLists.txt
│   └── test_ppm.cpp
├── filter/
│   ├── CMakeLists.txt
│   └── test_filters.cpp
└── cli/
    └── CMakeLists.txt      ← 第13章の add_test 群
```

**テスト対象のライブラリと1対1に対応させる。** どのテストがどのライブラリを検証しているかが構造から分かり、依存も最小になる。

### 共通処理を関数にまとめる

同じ記述を4回書くのは避けたい。第5章8節で学んだ `cmake_parse_arguments` を使う。

```cmake
# tests/CMakeLists.txt

function(pixkit_add_test_target NAME)
    set(multiValue SOURCES DEPENDS)
    cmake_parse_arguments(PARSE_ARGV 1 ARG "" "" "${multiValue}")

    if(ARG_UNPARSED_ARGUMENTS)
        message(FATAL_ERROR "pixkit_add_test_target: 不明な引数: ${ARG_UNPARSED_ARGUMENTS}")
    endif()
    if(NOT ARG_SOURCES)
        message(FATAL_ERROR "pixkit_add_test_target(${NAME}): SOURCES は必須です")
    endif()

    add_executable(${NAME} ${ARG_SOURCES})

    target_link_libraries(${NAME} PRIVATE
        ${ARG_DEPENDS}
        pixkit::warnings
        GTest::gtest_main
    )

    set_target_properties(${NAME} PROPERTIES FOLDER "tests")

    gtest_discover_tests(${NAME}
        DISCOVERY_MODE    PRE_TEST
        DISCOVERY_TIMEOUT 30
        PROPERTIES
            LABELS  "unit"
            TIMEOUT 30
    )
endfunction()
```

使う側はこうなる。

```cmake
# tests/core/CMakeLists.txt
pixkit_add_test_target(pixkit-core-tests
    SOURCES test_pixel.cpp test_color.cpp test_image.cpp
    DEPENDS pixkit::core
)
```

**第5章で学んだCMake言語が、ここで実用的な形になった。** テストターゲットの追加が3行で済むようになり、設定漏れも起きない。

### 分けすぎない

とはいえ、実行ファイルが増えるとリンク時間の合計は増える（GoogleTestが各実行ファイルに静的リンクされるため）。**ライブラリ単位くらいの粒度が実用的なバランス**だ。1テストファイル＝1実行ファイルにするのはやりすぎである。

## 15.2　フィクスチャとパラメタライズドテスト

### フィクスチャ（`TEST_F`）

複数のテストで同じ準備が必要なとき。

```cpp
class ColorFixture : public ::testing::Test {
protected:
    void SetUp() override    { img_ = pixkit::Image(2, 2); }
    void TearDown() override { /* 後始末が要ればここ */ }

    pixkit::Image img_;
};

TEST_F(ColorFixture, StartsBlack)
{
    EXPECT_EQ((img_[0, 0]), (pixkit::Rgb8{0, 0, 0}));
}

TEST_F(ColorFixture, CanWrite)
{
    img_[1, 1] = pixkit::Rgb8{1, 2, 3};
    EXPECT_EQ((img_[1, 1]), (pixkit::Rgb8{1, 2, 3}));
}
```

**`SetUp` はテストごとに呼ばれる。** テスト間で状態が共有されることはない。共有したい場合は `SetUpTestSuite`（静的メンバ）を使うが、テスト間の依存を生むので避けたほうがよい。

CTestからはこう見える。

```
  Test #16: ColorFixture.StartsBlack
  Test #17: ColorFixture.CanWrite
```

### パラメタライズドテスト（`TEST_P`）

同じ検証を複数の入力で行うとき。

```cpp
class ImageSize : public ::testing::TestWithParam<std::pair<int, int>> {
protected:
    void SetUp() override {
        const auto [w, h] = GetParam();
        img_ = pixkit::Image(w, h);
    }
    pixkit::Image img_;
};

TEST_P(ImageSize, ByteSizeMatches)
{
    const auto [w, h] = GetParam();
    EXPECT_EQ(img_.byte_size(), static_cast<std::size_t>(w) * h * 3);
}

INSTANTIATE_TEST_SUITE_P(Sizes, ImageSize,
    ::testing::Values(std::pair{1, 1}, std::pair{4, 3}, std::pair{64, 32}),
    [](const ::testing::TestParamInfo<std::pair<int, int>>& info) {
        return std::to_string(info.param.first) + "x" + std::to_string(info.param.second);
    });
```

第4引数は**テスト名の生成関数**だ。これを省略すると `ImageSize.ByteSizeMatches/0`、`/1`、`/2` という連番になり、失敗したときにどのケースか分からない。**必ず書く。**

CTestからはこう見える。

```
  Test #18: Sizes/ImageSize.ByteSizeMatches/1x1  # GetParam() = (1, 1)
  Test #19: Sizes/ImageSize.ByteSizeMatches/4x3  # GetParam() = (4, 3)
  Test #20: Sizes/ImageSize.ByteSizeMatches/64x32  # GetParam() = (64, 32)
```

**`gtest_discover_tests` が個別に登録している。** 第14章5節で `gtest_add_tests`（ソースの正規表現スキャン）ではなく `gtest_discover_tests` を選んだ理由がこれだ。ソースを見ただけでは、この3つのテストは検出できない。

CMake側の注意点として、`NO_PRETTY_VALUES` を指定すると `# GetParam() = ...` のコメント部分が抑制される。名前が長すぎて困る場合に使う。

### 型付きテスト（`TYPED_TEST`）

複数の型に対して同じ検証を行う。

```cpp
template <class T>
class PixelTypes : public ::testing::Test {};

using MyPixelTypes = ::testing::Types<pixkit::Rgb8, pixkit::Rgb32f>;
TYPED_TEST_SUITE(PixelTypes, MyPixelTypes);

TYPED_TEST(PixelTypes, DefaultConstructible)
{
    TypeParam c{};
    EXPECT_EQ(c, TypeParam{});
}
```

`pixkit` では型が2つしかないので出番は少ないが、テンプレートライブラリを書くときには強力だ。

## 15.3　テストデータをどう扱うか

第14章のPPMテストでは、`std::filesystem::temp_directory_path()` に一時ファイルを作った。実際のプロジェクトでは、**リポジトリに置いた入力ファイルを読む**ことが多い。ここには設計判断が要る。

### 問題：カレントディレクトリは何か

```cpp
auto img = pixkit::codec::load_ppm("data/sample.ppm");   // どこからの相対パス？
```

テストの作業ディレクトリは、CTestの `WORKING_DIRECTORY` プロパティで決まり、既定は**そのテストを登録した `CMakeLists.txt` に対応するビルドディレクトリ**だ（第13章3節）。

- コマンドラインから `ctest` で実行 → そのディレクトリ
- Visual Studio のテストエクスプローラから実行 → 同じ
- 実行ファイルを直接ダブルクリック → **違う**

「`ctest` では通るのに、デバッガで実行すると落ちる」の原因になる。

### 解決策1：パスをコンパイル時に埋め込む（推奨）

```cmake
target_compile_definitions(pixkit-codec-tests PRIVATE
    PIXKIT_TEST_DATA_DIR="${CMAKE_CURRENT_SOURCE_DIR}/data"
)
```

```cpp
namespace {
const std::filesystem::path data_dir{PIXKIT_TEST_DATA_DIR};
}

TEST(Ppm, LoadsSample)
{
    const auto img = pixkit::codec::load_ppm(data_dir / "sample.ppm");
    ASSERT_TRUE(img.has_value());
}
```

| 利点 | 欠点 |
| --- | --- |
| **どこから実行しても動く** | 絶対パスが実行ファイルに埋め込まれる |
| 作業ディレクトリに依存しない | ビルドしたマシンでしか動かない |

テスト実行ファイルは配布しないので、欠点は実質的に問題にならない。**本書はこの方法を採る。**

> **バックスラッシュに注意**
> Windowsのパスをマクロに埋め込むとき、`C:\work\...` の `\w` がエスケープシーケンスとして解釈されて壊れる。CMakeの `${CMAKE_CURRENT_SOURCE_DIR}` は**スラッシュ区切り**（`C:/work/...`）を返すので、そのまま使えば問題ない。手で書いたパスを渡すときだけ注意する。

### 解決策2：ビルドディレクトリにコピーする

```cmake
add_custom_command(TARGET pixkit-codec-tests POST_BUILD
    COMMAND ${CMAKE_COMMAND} -E copy_directory
            "${CMAKE_CURRENT_SOURCE_DIR}/data"
            "$<TARGET_FILE_DIR:pixkit-codec-tests>/data"
)
```

実行ファイルの隣に `data/` が置かれる。**テストが出力ファイルを書く場合**は、こちらのほうが素直だ（ソースツリーを汚さない）。

`copy_directory` はディレクトリ全体をコピーする。第5章9節で紹介した `cmake -E` が実用的に効く場面だ。

### 解決策3：`WORKING_DIRECTORY` を指定する

```cmake
gtest_discover_tests(pixkit-codec-tests
    WORKING_DIRECTORY "${CMAKE_CURRENT_SOURCE_DIR}"
    DISCOVERY_MODE PRE_TEST
)
```

単純だが、**デバッガから起動したときは効かない**。VSのデバッグ実行では `launch.vs.json`（第3章4節）の `currentDir` が使われるからだ。2か所を揃えて保守する必要がある。

### 出力ファイルの置き場所

テストが生成するファイルは、**必ずビルドツリーに書く。**

```cmake
target_compile_definitions(pixkit-codec-tests PRIVATE
    PIXKIT_TEST_DATA_DIR="${CMAKE_CURRENT_SOURCE_DIR}/data"
    PIXKIT_TEST_OUT_DIR="${CMAKE_CURRENT_BINARY_DIR}/test-output"
)
```

そして、並列実行（`ctest -j`）で衝突しないよう、**テストごとに一意な名前**を使う。

```cpp
std::filesystem::path out_path(std::string_view name)
{
    const auto dir = std::filesystem::path{PIXKIT_TEST_OUT_DIR};
    std::filesystem::create_directories(dir);
    return dir / name;
}

TEST(Ppm, RoundTrip)
{
    const auto path = out_path("roundtrip.ppm");   // テスト名と対応させる
    ...
}
```

同じファイル名を2つのテストが使うと、`-j` で並列実行したときにランダムに失敗する。**再現しないテスト失敗の原因として最も多いパターン**だ。どうしても共有せざるをえない場合は、第13章3節の `RESOURCE_LOCK` を使う。

## 15.4　例外テストとDLL境界

### 例外のテスト

```cpp
TEST(Image, ThrowsOnHugeAllocation)
{
    EXPECT_THROW(pixkit::Image(1'000'000, 1'000'000), std::bad_alloc);
}

TEST(Codec, DoesNotThrow)
{
    EXPECT_NO_THROW({
        (void)pixkit::codec::load_ppm("no_such_file.ppm");
    });
}
```

`pixkit` は `std::expected` でエラーを返す設計（第9章）なので、後者のような「例外を投げないこと」の検証のほうが本質的だ。

### デステスト

「アサーションが発火してプロセスが落ちること」を検証する。

```cpp
TEST(ImageDeathTest, SubscriptOutOfRange)
{
    pixkit::Image img(4, 4);
    EXPECT_DEATH((void)img[100, 100], "PIXKIT_ASSERT failed");
}
```

第12章で作った `PIXKIT_ASSERT` を検証している。ただし注意点がある。

- **Debugビルドでしか意味がない**（Releaseでは `PIXKIT_ASSERT` が消える）
- デステストは**プロセスをフォークして実行する**ため遅い
- Windowsではフォークができないので、GoogleTestは実行ファイルを再起動する方式を使う

構成による分岐が必要になる。

```cpp
#ifdef PIXKIT_DEBUG
TEST(ImageDeathTest, SubscriptOutOfRange) { ... }
#endif
```

テストスイート名に `DeathTest` を含めるのはGoogleTestの規約で、こうしておくと他のテストより先に実行される（スレッドが増える前に実行するため）。

### DLL境界とテスト

第11章5節で、DLL境界を越えてよいのはPODとポインタだけだと述べた。**テストコードも「DLLを使う側」なので、同じ制約を受ける。**

```cpp
// pixkit-filter は DLL（BUILD_SHARED_LIBS=ON のとき）
TEST(Filter, GrayscaleWorks)
{
    auto img = solid(4, 4, pixkit::Rgb8{10, 200, 90});
    pixkit::filter::grayscale(img.view());     // ImageView を渡す → 安全
    ...
}
```

`ImageView` を渡す設計にしてあるので問題ない。**もしAPIが `std::vector` を受け取っていたら、Debug/Release の混在でテストが不可解に落ちていた。**

そして重要なのは、**テストが両方の構成で通ることを確認する**ことだ。

```
cmake --preset x64-debug --fresh -DBUILD_SHARED_LIBS=ON
cmake --build --preset x64-debug && ctest --preset x64-debug

cmake --preset x64-debug --fresh -DBUILD_SHARED_LIBS=OFF
cmake --build --preset x64-debug && ctest --preset x64-debug
```

これはCI（15.7節）でマトリクスとして回すのに向いている。

## 15.5　Windowsでのカバレッジ計測

### 選択肢

GCCやClangには `--coverage`（gcov）や `-fprofile-instr-generate` があるが、**MSVCには標準のカバレッジ機能がない。**

| ツール | 性質 |
| --- | --- |
| **OpenCppCoverage** | 無償。PDBを使ってカバレッジを計測する。CIでも使える |
| Visual Studio Enterprise | IDE統合。**Enterpriseエディション限定** |
| clang-cl + llvm-cov | Clangツールチェインに切り替える必要がある |

現実的な選択は **OpenCppCoverage** だ。

### 仕組み

OpenCppCoverageは、コンパイラの計装（インストルメンテーション）を使わない。**PDBのデバッグ情報を読み、実行ファイルにブレークポイントを仕掛けて、どの行が実行されたかを記録する。**

つまり、

- **専用のビルドが不要**（Debugビルドをそのまま計測できる）
- PDBが必須（第12章6節）
- 実行は遅くなる

### CMakeから呼ぶ

```cmake
option(PIXKIT_ENABLE_COVERAGE "OpenCppCoverage でカバレッジを計測する" OFF)

if(PIXKIT_ENABLE_COVERAGE AND MSVC)
    find_program(PIXKIT_OPENCPPCOVERAGE_EXE NAMES OpenCppCoverage)

    if(NOT PIXKIT_OPENCPPCOVERAGE_EXE)
        message(WARNING "OpenCppCoverage が見つかりません。カバレッジは無効です")
    else()
        add_custom_target(coverage
            COMMAND "${PIXKIT_OPENCPPCOVERAGE_EXE}"
                    --sources "${PROJECT_SOURCE_DIR}\\libs"
                    --excluded_sources "${PROJECT_SOURCE_DIR}\\tests"
                    --excluded_sources "*\\_deps\\*"
                    --export_type "html:${CMAKE_BINARY_DIR}/coverage"
                    --export_type "cobertura:${CMAKE_BINARY_DIR}/coverage.xml"
                    --
                    "${CMAKE_CTEST_COMMAND}" -C $<CONFIG> --output-on-failure
            WORKING_DIRECTORY "${CMAKE_BINARY_DIR}"
            COMMENT "カバレッジを計測しています..."
            USES_TERMINAL
        )
    endif()
endif()
```

```
cmake --preset x64-debug -DPIXKIT_ENABLE_COVERAGE=ON
cmake --build --preset x64-debug --target coverage
```

いくつかポイントがある。

- **`--` 以降が計測対象のコマンド。** ここで `ctest` を実行することで、全テストをまとめて計測できる
- `${CMAKE_CTEST_COMMAND}` は、いま使っているCMakeに付属する `ctest` のフルパスに展開される
- `--excluded_sources "*\\_deps\\*"` で、`FetchContent` が取ってきたGoogleTestのコードを除外する（第14章8節の副作用対策）
- `--sources` にはバックスラッシュ区切りのパスを渡す（OpenCppCoverageの仕様）
- `USES_TERMINAL` を付けると、進捗が逐次表示される

### カバレッジ率を目標にしない

数値は目安であって目的ではない。**カバレッジ100%のテストが、まったくバグを見つけないことはある**（実行しただけでアサーションがない、など）。

有用な使い方は、**「まったくテストされていない領域」を見つけること**だ。カバレッジレポートで真っ赤な関数があれば、そこに手を入れる価値がある。

## 15.6　`workflowPresets` でコマンドを一本化する

第4章3節で作ったワークフロープリセットを、ここで実用に耐えるものにする。

```json
"workflowPresets": [
  {
    "name": "x64-debug",
    "displayName": "Debug: 構成→ビルド→テスト",
    "steps": [
      { "type": "configure", "name": "x64-debug" },
      { "type": "build",     "name": "x64-debug" },
      { "type": "test",      "name": "x64-debug" }
    ]
  },
  {
    "name": "x64-release",
    "displayName": "Release: 構成→ビルド→テスト",
    "steps": [
      { "type": "configure", "name": "x64-release" },
      { "type": "build",     "name": "x64-release" },
      { "type": "test",      "name": "x64-release" }
    ]
  }
]
```

対応する `testPresets` も追加する。

```json
"testPresets": [
  {
    "name": "x64-debug",
    "configurePreset": "x64-debug",
    "output":    { "outputOnFailure": true },
    "execution": { "noTestsAction": "error", "jobs": 0 }
  },
  {
    "name": "x64-release",
    "configurePreset": "x64-release",
    "output":    { "outputOnFailure": true },
    "execution": { "noTestsAction": "error", "jobs": 0 }
  }
]
```

`"jobs": 0` は「CPU数に合わせて並列実行」の意味だ（`ctest -j0` 相当）。

### これで得られるもの

```
cmake --workflow --preset x64-debug
```

**この1行が、ローカルでもCIでも同じことをする。** 「CIでだけ落ちる」の原因の多くは「実行しているコマンドが違う」ことなので、これを揃えるのは大きい。

開発者への案内も簡潔になる。

```markdown
## ビルドとテスト

    cmake --workflow --preset x64-debug
```

## 15.7　GitHub Actions で回す

### ワークフローファイル

`.github/workflows/ci.yml`

```yaml
name: CI

on:
  push:
    branches: [ main ]
  pull_request:

jobs:
  windows:
    runs-on: windows-2025
    strategy:
      fail-fast: false
      matrix:
        preset: [ x64-debug, x64-release ]

    steps:
      - uses: actions/checkout@v4

      - name: 開発者環境を設定する
        uses: ilammy/msvc-dev-cmd@v1
        with:
          arch: x64

      - name: CMake と Ninja のバージョンを表示
        run: |
          cmake --version
          ninja --version

      - name: 構成・ビルド・テスト
        run: cmake --workflow --preset ${{ matrix.preset }}

      - name: テスト結果をアップロード
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: test-results-${{ matrix.preset }}
          path: out/build/${{ matrix.preset }}/Testing/**/*.xml
```

### ポイント

**1. 開発者環境の設定が必要**

第1章7節・第2章6節で述べたとおり、**Ninjaジェネレータを使うには `cl.exe` が見つかる環境が要る。** GitHub Actions のWindowsランナーはVisual Studio が入っているが、環境変数は設定されていない。`ilammy/msvc-dev-cmd` のようなアクションでこれを設定する。

Visual Studio ジェネレータを使うプリセットなら、この手順は不要だ（CMakeが自分でVSを探す）。**「ローカルで動くのにCIで `No CMAKE_CXX_COMPILER could be found` になる」の原因はこれ**である。

**2. `fail-fast: false`**

既定では、1つのジョブが落ちると他もキャンセルされる。「Debugは通るがReleaseで落ちる」といった情報が欲しいので、`false` にする。

**3. 実行するのは1コマンド**

```yaml
run: cmake --workflow --preset ${{ matrix.preset }}
```

15.6節で一本化したおかげだ。CIの設定ファイルにビルド手順の知識が漏れ出していない。**プリセットを直せばCIも追随する。**

**4. テスト結果をアーティファクトに残す**

CTestは `Testing/` 以下にXMLを出力する。`gtest_discover_tests` の `XML_OUTPUT_DIR`（第14章5節）を設定していれば、JUnit形式のXMLも得られる。テスト結果を可視化するアクションと組み合わせると、失敗したテストがPR上で見えるようになる。

### 静的ライブラリ／動的ライブラリの両方を回す

15.4節で述べたマトリクスを追加する。

```yaml
    strategy:
      fail-fast: false
      matrix:
        preset:  [ x64-debug, x64-release ]
        shared:  [ ON, OFF ]

    steps:
      ...
      - name: 構成
        run: cmake --preset ${{ matrix.preset }} -DBUILD_SHARED_LIBS=${{ matrix.shared }}
      - name: ビルド
        run: cmake --build --preset ${{ matrix.preset }}
      - name: テスト
        run: ctest --preset ${{ matrix.preset }}
```

この場合、`--workflow` は使えない（構成に追加の引数を渡せないため）。**プリセットを増やして対応する**ほうが一貫性は保たれる。

### 手順2：`tests/CMakeLists.txt` を書き直す

```cmake
# ============================================================
# GoogleTest の取得（第14章）
# ============================================================
include(FetchContent)

set(gtest_force_shared_crt ON  CACHE BOOL "" FORCE)
set(BUILD_GMOCK            ON  CACHE BOOL "" FORCE)
set(INSTALL_GTEST          OFF CACHE BOOL "" FORCE)

FetchContent_Declare(googletest
    GIT_REPOSITORY https://github.com/google/googletest.git
    GIT_TAG        ${PIXKIT_GOOGLETEST_TAG}
    GIT_SHALLOW    TRUE
    EXCLUDE_FROM_ALL
)
FetchContent_MakeAvailable(googletest)

foreach(T gtest gtest_main gmock gmock_main)
    if(TARGET ${T})
        set_target_properties(${T} PROPERTIES FOLDER "external")
    endif()
endforeach()

include(GoogleTest)

# ============================================================
# テストターゲットを作るヘルパー
# ============================================================
function(pixkit_add_test_target NAME)
    set(multiValue SOURCES DEPENDS DEFINITIONS)
    cmake_parse_arguments(PARSE_ARGV 1 ARG "" "" "${multiValue}")

    if(ARG_UNPARSED_ARGUMENTS)
        message(FATAL_ERROR "pixkit_add_test_target: 不明な引数: ${ARG_UNPARSED_ARGUMENTS}")
    endif()
    if(NOT ARG_SOURCES)
        message(FATAL_ERROR "pixkit_add_test_target(${NAME}): SOURCES は必須です")
    endif()

    add_executable(${NAME} ${ARG_SOURCES})

    target_link_libraries(${NAME} PRIVATE
        ${ARG_DEPENDS}
        pixkit::warnings
        GTest::gtest_main
    )

    if(ARG_DEFINITIONS)
        target_compile_definitions(${NAME} PRIVATE ${ARG_DEFINITIONS})
    endif()

    set_target_properties(${NAME} PROPERTIES FOLDER "tests")

    gtest_discover_tests(${NAME}
        DISCOVERY_MODE    PRE_TEST
        DISCOVERY_TIMEOUT 30
        XML_OUTPUT_DIR    "${CMAKE_BINARY_DIR}/test-results"
        PROPERTIES
            LABELS  "unit"
            TIMEOUT 30
    )
endfunction()

# ============================================================
add_subdirectory(core)
add_subdirectory(codec)
add_subdirectory(filter)
add_subdirectory(cli)
```

## この章のまとめ

- テストは**ライブラリごとにターゲットを分ける。** 共通処理は `cmake_parse_arguments`（第5章8節）を使ったヘルパー関数にまとめる
- フィクスチャ（`TEST_F`）、パラメタライズドテスト（`TEST_P`）、型付きテスト（`TYPED_TEST`）を使い分ける。**`INSTANTIATE_TEST_SUITE_P` の名前生成関数は必ず書く**（連番だと失敗時に読めない）
- テストデータのパスは **`target_compile_definitions` でコンパイル時に埋め込む**のが最も堅い。作業ディレクトリに依存しないので、デバッガから起動しても動く
- **出力ファイルはビルドツリーに、テストごとに一意な名前で書く。** 並列実行での衝突は、再現しないテスト失敗の最大の原因
- デステストは Debug 限定。スイート名に `DeathTest` を含める規約がある
- **テストコードも「DLLを使う側」**なので、DLL境界の制約を受ける。`BUILD_SHARED_LIBS` の ON/OFF 両方でテストを回す
- Windowsのカバレッジは **OpenCppCoverage**。PDBを使うので専用ビルドが不要。`--` 以降で `ctest` を実行し、`_deps` を除外する。**カバレッジ率を目標にしない**
- **`workflowPresets` でローカルとCIのコマンドを一本化する。** CIの設定ファイルは `cmake --workflow --preset <name>` の1行になる
- GitHub Actions でNinjaを使うには、**MSVCの開発者環境を設定するステップが必要**（`No CMAKE_CXX_COMPILER could be found` の原因）

次の第16章では、Google Benchmark を組み込む。テストが「正しさ」を守るのに対し、ベンチマークは「速さ」を守る。Release構成でしか意味がないこと、CTestからどう分離するか、そして変更前後をどう比較するかを扱う。
