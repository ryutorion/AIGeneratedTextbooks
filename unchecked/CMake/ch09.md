# 第9章　静的ライブラリ（`pixkit::codec`）

## この章のゴール

- `add_library(... STATIC)` で静的ライブラリを作る
- 公開ヘッダと内部ヘッダを、ディレクトリとCMakeの記述の両方で分離する
- **`$<BUILD_INTERFACE:>` がなぜ必要なのか**を理解する
- 静的ライブラリ同士のリンクと、推移的な依存の解決を理解する
- `PRIVATE` 依存が利用側に漏れないことを、実際に確かめる
- `.lib` の中身を `lib` / `dumpbin` で覗く
- `POSITION_INDEPENDENT_CODE` のWindowsでの意味を知る

第8章で作った `pixkit` の骨格に、最初の実体のあるライブラリを追加する。**PPM画像の読み書きを行う静的ライブラリ `pixkit::codec`** だ。

---

## 9.1　`add_library(... STATIC)`

### 静的ライブラリとは何か

静的ライブラリ（`.lib`）は、**コンパイル済みオブジェクトファイル（`.obj`）を1つにまとめた書庫**にすぎない。実行ファイルにリンクすると、必要なオブジェクトがコピーされて実行ファイルに埋め込まれる。

| | 静的ライブラリ | 動的ライブラリ |
| --- | --- | --- |
| 実体 | `.obj` のアーカイブ | 実行可能なモジュール |
| リンク時 | 必要な部分が実行ファイルにコピーされる | 参照だけが記録される |
| 実行時 | 何も要らない | `.dll` が必要 |
| 更新 | 再リンクが必要 | DLLを差し替えるだけ |

第11章で動的ライブラリを扱うが、**Windowsでは静的ライブラリのほうが圧倒的に扱いが楽**だ。DLL境界の問題（第11章5節）がないからである。特に理由がなければ静的から始めるのがよい。

### 最小の記述

```cmake
add_library(pixkit-codec STATIC
    src/ppm.cpp
)
add_library(pixkit::codec ALIAS pixkit-codec)
```

第6章6節で学んだとおり、ALIASも同時に定義する。

### `STATIC` を省略した場合

```cmake
add_library(pixkit-codec src/ppm.cpp)     # STATIC/SHARED を省略
```

この場合、変数 `BUILD_SHARED_LIBS` の値で決まる。既定は `OFF` なので静的になる。

**ライブラリを配布する場合、省略するほうが親切だ。** 利用者が `-DBUILD_SHARED_LIBS=ON` で切り替えられるようになるからだ。ただし、DLLにするには第11章のエクスポート対応が必要になる。本書では、

- 第9章〜第10章：`STATIC` を明示する（話を単純にするため）
- 第11章8節：`BUILD_SHARED_LIBS` に対応させる

という順で進める。

## 9.2　公開ヘッダと内部ヘッダを分ける

### ディレクトリ構成

```
libs/codec/
├── CMakeLists.txt
├── include/
│   └── pixkit/
│       └── codec/
│           └── ppm.hpp              ← 公開ヘッダ
└── src/
    ├── ppm.cpp                      ← 実装
    └── detail/
        └── binary_io.hpp            ← 内部ヘッダ
```

境界は明快だ。

| 場所 | 性質 | 利用側から見えるか |
| --- | --- | --- |
| `include/pixkit/codec/` | 公開API | **見える** |
| `src/`、`src/detail/` | 実装の詳細 | **見えない** |

### インクルードの書き方を統一する

```cpp
// libs/codec/src/ppm.cpp
#include <pixkit/codec/ppm.hpp>      // 公開ヘッダは山括弧
#include "detail/binary_io.hpp"      // 内部ヘッダは引用符
```

この使い分けには実用的な意味がある。

- **山括弧 `<>`**：インクルードパス（`/I`）から探す。「これは公開されたインターフェースだ」という意思表示
- **引用符 `""`**：まず自分のファイルからの相対パスで探す。「これは内部の都合だ」という意思表示

自分のライブラリの公開ヘッダを `#include "ppm.hpp"` のように相対パスで書くと、**利用側と同じ経路でヘッダが解決されているかを検証できなくなる**。山括弧で書いておけば、公開ヘッダに書き漏らしがあれば自分のビルドで気づける。

### `detail` 名前空間

内部実装はC++の名前空間でも隠す。

```cpp
namespace pixkit::codec::detail {
    // 実装の詳細
}
```

`detail` という名前は「使うな」という慣習的なマーカーだ。CMake側で `PRIVATE` にしてヘッダを届かなくすることと合わせて、二重に守る。

## 9.3　`target_include_directories` と `$<BUILD_INTERFACE:>`

### 素朴な書き方

```cmake
target_include_directories(pixkit-codec
    PUBLIC  ${CMAKE_CURRENT_SOURCE_DIR}/include
    PRIVATE ${CMAKE_CURRENT_SOURCE_DIR}/src
)
```

これでビルドは通る。第6章のハンズオンでもこう書いた。しかし、**このライブラリを配布する段になると壊れる。**

### 何が問題か

`PUBLIC` に指定したパスは、`INTERFACE_INCLUDE_DIRECTORIES` プロパティに記録される（第6章5節）。その値は、

```
C:/work/pixkit/libs/codec/include
```

という**あなたのマシンの絶対パス**だ。

第21〜22章で `install(EXPORT)` を使ってパッケージを作ると、この情報が `pixkit-targets.cmake` に書き出される。利用者がそのパッケージをインストールした先に、`C:/work/pixkit/...` などというディレクトリは存在しない。

CMakeはこれを検出して、構成時にエラーを出す。

```
CMake Error: Target "pixkit-codec" INTERFACE_INCLUDE_DIRECTORIES property contains
path: "C:/work/pixkit/libs/codec/include" which is prefixed in the source directory.
```

### 解決：ビルド時とインストール時でパスを切り替える

```cmake
target_include_directories(pixkit-codec
    PUBLIC
        $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
        $<INSTALL_INTERFACE:include>
    PRIVATE
        ${CMAKE_CURRENT_SOURCE_DIR}/src
)
```

第7章8節で学んだジェネレータ式だ。

| ジェネレータ式 | 有効になる場面 | 展開結果 |
| --- | --- | --- |
| `$<BUILD_INTERFACE:X>` | ビルドツリー内から使うとき | `X` |
| `$<INSTALL_INTERFACE:X>` | インストール先から使うとき | `X`（インストール先からの相対パス） |

同じターゲットが、状況によって別のインクルードパスを提供する。これが「ライブラリを配布可能にする」ための最初の一歩だ。

### いまから書いておく

`$<INSTALL_INTERFACE:>` は第21章まで使わない。しかし、**後から全部書き直すより、最初から書いておくほうが圧倒的に楽**だ。本書ではこの時点から `$<BUILD_INTERFACE:>` と `$<INSTALL_INTERFACE:>` をセットで書く。

`PRIVATE` のほうはジェネレータ式が不要だ。自分のビルドにしか使われず、エクスポートされないからである。

> **`include` ディレクトリの階層をもう一度確認する**
> インクルードパスに追加するのは `libs/codec/include` までで、`libs/codec/include/pixkit/codec` ではない。だから利用側のコードは
> ```cpp
> #include <pixkit/codec/ppm.hpp>
> ```
> となる。この階層があるおかげで、他人のライブラリに `ppm.hpp` があっても衝突しない（第8章1節）。

## 9.4　静的ライブラリ同士のリンクと推移的依存

### 依存を宣言する

`pixkit-codec` は `pixkit::core`（バージョン情報など）を使う。

```cmake
target_link_libraries(pixkit-codec
    PUBLIC  pixkit::core        # 公開ヘッダで core の型を使う
    PRIVATE pixkit::warnings    # 警告設定は自分のビルドだけ（第7章7節）
)
```

第6章3節の判断基準そのままだ。

### 推移的な依存の解決

```
pixcli  →  pixkit-codec  →  pixkit-core
```

`pixcli` の `CMakeLists.txt` には `pixkit::codec` としか書かない。

```cmake
target_link_libraries(pixcli PRIVATE pixkit::codec)
```

それでも `pixkit-core` の使用要件（インクルードパス、C++23の要求）が届く。`pixkit-codec` が `PUBLIC` でリンクしているからだ。**依存の連鎖はCMakeが自動的にたどる。**

### 静的ライブラリでの `PRIVATE` の意味

ここは正確に理解しておく必要がある。`pixkit-codec` が `zlib` に `PRIVATE` でリンクしたとしよう。

```cmake
target_link_libraries(pixkit-codec PRIVATE ZLIB::ZLIB)
```

| | 伝播するか |
| --- | --- |
| zlibのインクルードパス | **しない**（`pixcli` は zlib のヘッダを見られない） |
| zlibのコンパイル定義 | **しない** |
| **zlibのリンク** | **する**（`pixcli` は zlib.lib とリンクされる） |

最後の行が重要だ。静的ライブラリは「オブジェクトファイルの束」でしかないので、`pixkit-codec.lib` の中には zlib への未解決の参照が残っている。最終的な実行ファイルを作るときには、どうしても `zlib.lib` が必要になる。

CMakeはこれを `INTERFACE_LINK_LIBRARIES` に `$<LINK_ONLY:ZLIB::ZLIB>` という形で記録する。「リンクだけ伝播させ、コンパイル時の使用要件は伝播させない」という指定だ。

**つまり `PRIVATE` は「実装の詳細を隠す」ものであって、「リンクを不要にする」ものではない。** 動的ライブラリなら本当に隠せる（第11章）。この違いが、静的と動的を選ぶ判断材料の1つになる。

### リンク順序を気にしなくてよい

コマンドラインでリンカを直接使っていた人は、静的ライブラリのリンク順序に悩まされた経験があるかもしれない。**CMakeでは気にしなくてよい。** 依存グラフから正しい順序を計算し、必要なら同じライブラリを複数回並べる（循環依存への対処）。

## 9.5　`PRIVATE` 依存が漏れないことを確かめる

第6章のハンズオンでも実験したが、実際のライブラリでもう一度確認する。ここでの確認手段は3つある。

### 手段1：コンパイルが失敗することで確認する

利用側から内部ヘッダを `#include` してみて、失敗すれば境界は守られている。

### 手段2：`compile_commands.json` を見る

`main.cpp` のコンパイルコマンドに、`libs/codec/src` へのインクルードパスが含まれていないことを確認する。

### 手段3：ターゲットのプロパティを読む

```cmake
get_target_property(V pixkit-codec INTERFACE_INCLUDE_DIRECTORIES)
message(STATUS "codec が伝播するインクルードパス: ${V}")
```

`include` だけが並び、`src` が含まれていなければ正しい。

ハンズオンで3つとも試す。

## 9.6　`.lib` の中身を覗く

CMakeの話から少し離れるが、**生成物が何であるかを一度自分の目で見ておく**と、以降の理解が変わる。開発者コマンドプロンプトで実行する。

### 収録されているオブジェクトを一覧する

```
lib /list out\build\x64-debug\lib\pixkit-codec.lib
```

```
pixkit-codec.dir\Debug\ppm.obj
```

`.cpp` 1つにつき `.obj` が1つ入っている。文字どおり「オブジェクトファイルの書庫」だ。

### シンボルを見る

```
dumpbin /symbols out\build\x64-debug\lib\pixkit-codec.lib | findstr "load_ppm"
```

```
008 00000000 SECT3  notype ()    External     | ?load_ppm@codec@pixkit@@YA?AV?$expected@UImageU8@codec@pixkit@@W4CodecError@23@@std@@AEBVpath@filesystem@std@@@Z
```

これがC++の**名前修飾（マングリング）**だ。関数名だけでなく、名前空間・引数の型・戻り値の型が符号化されている。読みやすくするには、

```
dumpbin /symbols out\build\x64-debug\lib\pixkit-codec.lib | findstr "load_ppm" > syms.txt
undname ?load_ppm@codec@pixkit@@YA?AV?$expected@UImageU8@codec@pixkit@@W4CodecError@23@@std@@AEBVpath@filesystem@std@@@Z
```

`undname` は名前を元に戻すツールだ。

### なぜこれが役に立つのか

**リンクエラーの読解に直結する。**

```
error LNK2019: 未解決の外部シンボル
"class std::expected<...> __cdecl pixkit::codec::load_ppm(class std::filesystem::path const &)"
が関数 main で参照されました。
```

このメッセージは「`load_ppm` の実体がどこにもない」と言っている。原因は、

- `ppm.cpp` を `add_library` のソースリストに書き忘れた
- `target_link_libraries` を書き忘れた
- ヘッダの宣言と実装で引数の型が微妙に違う（`const&` の有無など）

のいずれかだ。`.lib` の中にシンボルがあるかを `dumpbin` で確認すれば、どれなのかが切り分けられる。

| ツール | 用途 |
| --- | --- |
| `lib /list` | 収録オブジェクトの一覧 |
| `dumpbin /symbols` | シンボルの一覧 |
| `dumpbin /exports` | DLLのエクスポート一覧（第11章） |
| `dumpbin /dependents` | 依存しているDLLの一覧（第11章） |
| `undname` | 名前修飾を元に戻す |

## 9.7　`POSITION_INDEPENDENT_CODE` のWindowsでの意味

Unix系の解説でよく出てくるプロパティだ。

```cmake
set_target_properties(pixkit-codec PROPERTIES POSITION_INDEPENDENT_CODE ON)
```

Linuxでは `-fPIC` が渡り、「静的ライブラリを共有ライブラリに組み込む」ために必須になる。これがないとリンクエラーになる。

**Windowsでは、このプロパティは何もしない。** WindowsのDLLはもともと再配置可能な形式であり、`-fPIC` に相当するフラグが存在しないからだ。

### では書く必要はないのか

書いておいたほうがよい場面がある。

1. **将来Linuxでもビルドする可能性がある場合**
   Windowsでは無害、Linuxでは必要、という設定なので、書いておけば移植時に困らない。
2. **その静的ライブラリを、後でDLLに組み込む場合**
   本書では第11章で `pixkit-filter`（DLL）を作る。もし `pixkit-codec`（静的）を `pixkit-filter` に組み込むなら、Linuxでは PIC が必須になる。

本書ではWindows専用として進めるので必須ではないが、ライブラリを配布する立場なら**書いておくのが親切**だ。プロジェクト全体に適用するなら次のようにする。

```cmake
if(PROJECT_IS_TOP_LEVEL)
    set(CMAKE_POSITION_INDEPENDENT_CODE ON)
endif()
```

## ハンズオン：PPM画像の読み書きライブラリ

第8章で作った `C:\work\pixkit` を拡張する。

### PPM形式について

PPM（Portable PixMap）は、極めて単純な画像形式だ。外部ライブラリなしで読み書きできるので、教材に向いている。

```
P6
64 32
255
<RGB RGB RGB ... のバイナリデータ>
```

| 行 | 内容 |
| --- | --- |
| 1行目 | マジックナンバー `P6`（バイナリ形式のRGB） |
| 2行目 | 幅 高さ |
| 3行目 | 最大値（通常255） |
| 以降 | 1画素3バイト（R, G, B）のバイナリ |

`#` から行末まではコメントとして無視される。空白（スペース、タブ、改行）はどれも区切りとして扱われる。

### 手順1：公開ヘッダを書く

`libs/codec/include/pixkit/codec/ppm.hpp`

```cpp
#pragma once

#include <cstdint>
#include <expected>
#include <filesystem>
#include <string_view>
#include <vector>

namespace pixkit::codec {

enum class CodecError {
    FileNotFound,
    ReadFailed,
    WriteFailed,
    BadMagic,
    BadHeader,
    UnsupportedMaxValue,
    TruncatedData,
};

std::string_view to_string(CodecError e) noexcept;

struct ImageU8 {
    int width  = 0;
    int height = 0;
    static constexpr int channels = 3;
    std::vector<std::uint8_t> pixels;

    [[nodiscard]] std::size_t byte_size() const noexcept {
        return static_cast<std::size_t>(width) * height * channels;
    }
};

[[nodiscard]] std::expected<ImageU8, CodecError>
load_ppm(const std::filesystem::path& path);

[[nodiscard]] std::expected<void, CodecError>
save_ppm(const std::filesystem::path& path, const ImageU8& image);

}  // namespace pixkit::codec
```

第7章で確認した `std::expected` を使っている。例外を投げないので、DLL境界（第11章5節）でも安全だ。

### 手順2：内部ヘッダを書く

`libs/codec/src/detail/binary_io.hpp`

```cpp
#pragma once

#include <cstddef>
#include <cstdint>
#include <filesystem>
#include <fstream>
#include <optional>
#include <vector>

namespace pixkit::codec::detail {

inline std::optional<std::vector<std::uint8_t>>
read_all_bytes(const std::filesystem::path& path)
{
    std::ifstream in(path, std::ios::binary);
    if (!in) return std::nullopt;
    return std::vector<std::uint8_t>(std::istreambuf_iterator<char>(in),
                                     std::istreambuf_iterator<char>());
}

inline bool is_space(std::uint8_t c) noexcept
{
    return c == ' ' || c == '\t' || c == '\n' || c == '\r' || c == '\v' || c == '\f';
}

}  // namespace pixkit::codec::detail
```

**このファイルは利用側から見えてはいけない。** それを後で確認する。

### 手順3：実装を書く

`libs/codec/src/ppm.cpp`

```cpp
#include <pixkit/codec/ppm.hpp>

#include "detail/binary_io.hpp"

#include <charconv>
#include <fstream>

namespace pixkit::codec {

std::string_view to_string(CodecError e) noexcept
{
    switch (e) {
    case CodecError::FileNotFound:        return "file not found";
    case CodecError::ReadFailed:          return "read failed";
    case CodecError::WriteFailed:         return "write failed";
    case CodecError::BadMagic:            return "not a binary PPM (P6)";
    case CodecError::BadHeader:           return "malformed header";
    case CodecError::UnsupportedMaxValue: return "max value must be 255";
    case CodecError::TruncatedData:       return "pixel data is truncated";
    }
    return "unknown error";
}

namespace {

// ヘッダのトークンを1つ読む。'#' から行末まではコメントとして読み飛ばす。
std::expected<int, CodecError>
next_int(const std::vector<std::uint8_t>& buf, std::size_t& pos)
{
    while (pos < buf.size()) {
        if (detail::is_space(buf[pos])) { ++pos; continue; }
        if (buf[pos] == '#') {
            while (pos < buf.size() && buf[pos] != '\n') ++pos;
            continue;
        }
        break;
    }
    const std::size_t begin = pos;
    while (pos < buf.size() && !detail::is_space(buf[pos])) ++pos;
    if (begin == pos) return std::unexpected(CodecError::BadHeader);

    int value = 0;
    const char* first = reinterpret_cast<const char*>(buf.data() + begin);
    const char* last  = reinterpret_cast<const char*>(buf.data() + pos);
    if (std::from_chars(first, last, value).ec != std::errc{}) {
        return std::unexpected(CodecError::BadHeader);
    }
    return value;
}

}  // namespace

std::expected<ImageU8, CodecError> load_ppm(const std::filesystem::path& path)
{
    auto raw = detail::read_all_bytes(path);
    if (!raw) return std::unexpected(CodecError::FileNotFound);

    const auto& buf = *raw;
    if (buf.size() < 2 || buf[0] != 'P' || buf[1] != '6') {
        return std::unexpected(CodecError::BadMagic);
    }

    std::size_t pos = 2;
    auto w = next_int(buf, pos);
    if (!w) return std::unexpected(w.error());
    auto h = next_int(buf, pos);
    if (!h) return std::unexpected(h.error());
    auto maxv = next_int(buf, pos);
    if (!maxv) return std::unexpected(maxv.error());

    if (*w <= 0 || *h <= 0) return std::unexpected(CodecError::BadHeader);
    if (*maxv != 255)       return std::unexpected(CodecError::UnsupportedMaxValue);

    ++pos;  // 最大値の直後の空白1文字がデータの開始位置

    ImageU8 image;
    image.width  = *w;
    image.height = *h;
    if (buf.size() - pos < image.byte_size()) {
        return std::unexpected(CodecError::TruncatedData);
    }
    image.pixels.assign(buf.begin() + static_cast<std::ptrdiff_t>(pos),
                        buf.begin() + static_cast<std::ptrdiff_t>(pos + image.byte_size()));
    return image;
}

std::expected<void, CodecError>
save_ppm(const std::filesystem::path& path, const ImageU8& image)
{
    if (image.width <= 0 || image.height <= 0) {
        return std::unexpected(CodecError::BadHeader);
    }
    if (image.pixels.size() != image.byte_size()) {
        return std::unexpected(CodecError::TruncatedData);
    }

    std::ofstream out(path, std::ios::binary);
    if (!out) return std::unexpected(CodecError::WriteFailed);

    out << "P6\n" << image.width << ' ' << image.height << "\n255\n";
    out.write(reinterpret_cast<const char*>(image.pixels.data()),
              static_cast<std::streamsize>(image.pixels.size()));
    if (!out) return std::unexpected(CodecError::WriteFailed);
    return {};
}

}  // namespace pixkit::codec
```

`std::expected<void, E>` を返すとき、成功は `return {};` と書く。

### 手順4：`CMakeLists.txt` を書く

`libs/codec/CMakeLists.txt`

```cmake
add_library(pixkit-codec STATIC
    src/ppm.cpp
    # IDEに表示させるため、ヘッダも列挙しておく（コンパイル対象にはならない）
```

### 手順5：`pixcli` から使う

`apps/pixcli/src/main.cpp`

```cpp
#include <pixkit/codec/ppm.hpp>
#include <pixkit/core/version.hpp>

#include <print>

namespace {

pixkit::codec::ImageU8 make_gradient(int w, int h)
{
    pixkit::codec::ImageU8 img;
    img.width  = w;
    img.height = h;
    img.pixels.resize(img.byte_size());

    for (int y = 0; y < h; ++y) {
        for (int x = 0; x < w; ++x) {
            const std::size_t i = (static_cast<std::size_t>(y) * w + x) * 3;
            img.pixels[i + 0] = static_cast<std::uint8_t>(x * 255 / (w - 1));
            img.pixels[i + 1] = static_cast<std::uint8_t>(y * 255 / (h - 1));
            img.pixels[i + 2] = 128;
        }
    }
    return img;
}

}  // namespace

int main()
{
    std::println("pixkit {}", pixkit::version_string);

    const auto img = make_gradient(64, 32);

    if (auto r = pixkit::codec::save_ppm("gradient.ppm", img); !r) {
        std::println("save failed: {}", pixkit::codec::to_string(r.error()));
        return 1;
    }

    auto loaded = pixkit::codec::load_ppm("gradient.ppm");
    if (!loaded) {
        std::println("load failed: {}", pixkit::codec::to_string(loaded.error()));
        return 1;
    }

    std::println("loaded {}x{}, {} bytes", loaded->width, loaded->height, loaded->pixels.size());
    std::println("round-trip {}", (loaded->pixels == img.pixels) ? "OK" : "NG");

    auto bad = pixkit::codec::load_ppm("no_such_file.ppm");
    std::println("missing file -> {}", pixkit::codec::to_string(bad.error()));
}
```

`apps/pixcli/CMakeLists.txt` を更新する。

```cmake
add_executable(pixcli src/main.cpp)

    PRIVATE
        pixkit::codec        # core は codec 経由で自動的に届く

```

**`pixkit::core` を書いていない**ことに注目する。`pixkit-codec` が `PUBLIC` でリンクしているので、推移的に届く（9.4節）。

## この章のまとめ

- 静的ライブラリは**オブジェクトファイルの書庫**。`add_library(名前 STATIC ソース...)` で作る。`STATIC`/`SHARED` を省略すると `BUILD_SHARED_LIBS` に従う
- 公開ヘッダは `include/<プロジェクト>/<ライブラリ>/`、内部ヘッダは `src/` に置く。**公開ヘッダは山括弧、内部ヘッダは引用符**でインクルードすると、境界の破れに自分のビルドで気づける
- `target_include_directories` の `PUBLIC` には **`$<BUILD_INTERFACE:>` と `$<INSTALL_INTERFACE:>` をセットで書く。** 絶対パスをそのまま書くと、第21〜22章のエクスポートで失敗する
- 依存は `target_link_libraries` で宣言し、**推移的に解決される**。利用側は直接の依存だけ書けばよい
- 静的ライブラリの `PRIVATE` は**コンパイル時の使用要件を隠すが、リンクは伝播する**（`$<LINK_ONLY:...>`）。実装を隠せるが、依存ライブラリ自体は最終的に必要になる
- `lib /list` と `dumpbin /symbols` で `.lib` の中身が見える。**リンクエラーの切り分けに直結する**
- `POSITION_INDEPENDENT_CODE` はWindowsでは無意味だが、Linux移植や「静的ライブラリをDLLに組み込む」場合に必要になる

次の第10章では、`pixkit::core` を本格的なヘッダーオンリーライブラリとして作る。コンパイル対象を持たない `INTERFACE` ライブラリの扱い、IDEへの表示、テストと静的解析の対象にする方法、そしてヘッダーオンリー化のコストを扱う。最後に `pixkit-codec` を `pixkit::core` の型を使うようにリファクタリングして、`PUBLIC` の判断をもう一度復習する。
