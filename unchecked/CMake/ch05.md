# 第5章　CMake言語の文法

## この章のゴール

- CMakeスクリプトが「コマンド呼び出しの列」であり、上から順に**実行される**ことを理解する
- 「すべての値は文字列」という原則と、そこから来る落とし穴を避けられる
- 変数・リスト・`if`・ループ・関数を、意図したとおりに書ける
- `cmake -P` で実験し、`message()` でデバッグできる

この章は本書で唯一、ビルドを行わない章だ。ここで扱うのはCMake**言語**そのものであり、`add_executable` のようなビルド関連のコマンドは出てこない。

正直に言えば、この章はあまり楽しくない。CMakeの言語仕様は20年以上の後方互換性を引きずっており、素直でない部分が多いからだ。しかし**ここで数十分使っておくと、後の章で「なぜか動かない」に費やす時間が何時間も減る**。実務でCMakeに詰まる原因の多くは、ビルドの知識不足ではなく、この章の内容の取りこぼしにある。

## 5.1　CMakeスクリプトはコマンド呼び出しの列である

### 構文はこれだけ

CMake言語の構文は、驚くほど単純だ。**すべての行が「コマンド名(引数 引数 ...)」の形をしている。**

```cmake
command_name(argument1 argument2 argument3)
```

演算子はない。`x = 1` とは書けない。代入すら `set(x 1)` というコマンド呼び出しだ。制御構造も同じで、`if` も `foreach` もコマンドである。

```cmake
if(SOMETHING)       # if というコマンドの呼び出し
    message("yes")
endif()             # endif というコマンドの呼び出し
```

この一貫性は美点でもある。文法を覚える必要がほとんどない代わりに、**コマンドの挙動を1つずつ覚える**ことになる。

### 大文字・小文字

- **コマンド名は大文字小文字を区別しない。** `set` も `SET` も `Set` も同じ
- **変数名は区別する。** `${foo}` と `${FOO}` は別物

古いコードは `SET(FOO bar)` のように全部大文字で書かれていることが多い。現在の慣習は**コマンドは小文字、変数は大文字**だ。本書もこれに従う。

### コメントとスクリプトモード

```cmake
# 行コメント

#[[
複数行コメント。
角括弧の数は増やせる（#[==[ ... ]==]）
]]
```

そしてこの章で最も役に立つ道具を先に紹介する。**CMakeはスクリプト言語として単体実行できる。**

`play.cmake` というファイルを作り、

```cmake
message("hello from script mode")
```

こう実行する。

```
cmake -P play.cmake
```

```
hello from script mode
```

`CMakeLists.txt` を書いて構成して……という手間なしに、言語の挙動をその場で試せる。**この章の実験はすべて `cmake -P` で行う。** 手元に `play.cmake` を1つ作って、書き換えながら読み進めてほしい。

## 5.2　すべての値は文字列

CMakeには型がない。**あらゆる値は文字列である。**

```cmake
set(A 1)
set(B "1")
set(C 1.0)
```

`A` と `B` は完全に同一だ。`C` は文字列 `"1.0"` であって、数値の1ではない。

```cmake
set(N 10)
message("N is ${N}")          # N is 10
math(EXPR RESULT "${N} * 2")  # 算術演算は math() コマンドが必要
message("${RESULT}")          # 20
```

数値計算をするのに専用コマンドが要る、というのがCMakeの世界だ。

### 真偽値の判定ルール

型がないのに `if` は動く。CMakeは文字列を見て真偽を判定するのだが、**判定ルールが2種類ある**。ここはCMakeで最も誤解されている部分なので、正確に押さえる。

**ルールA：引数がクォートされておらず、定義済み変数の名前である場合**
→ **偽の定数でなければ真**

| 偽になるもの（偽の定数） |
| --- |
| `OFF`, `NO`, `FALSE`, `N`, `IGNORE`, `NOTFOUND` |
| 空文字列 |
| `0` |
| `-NOTFOUND` で終わる文字列 |

つまり `banana` のような**ただの文字列は真**になる。

**ルールB：引数がクォートされた文字列である場合（または未定義の名前である場合）**
→ **真の定数でなければ偽**

| 真になるもの（真の定数） |
| --- |
| `ON`, `YES`, `TRUE`, `Y` |
| 0でない数値 |

つまり `"banana"` は**偽**になる。

大文字小文字はどちらも区別しない。実際に確かめてみよう。

```cmake
set(V "banana")

if(V)          message(STATUS "A: 真")  endif()   # 出る   （ルールA）
if("${V}")     message(STATUS "B: 真")  endif()   # 出ない（ルールB）
if("banana")   message(STATUS "C: 真")  endif()   # 出ない（ルールB）
if("YES")      message(STATUS "D: 真")  endif()   # 出る   （ルールB／真の定数）
```

**A と B が逆の結果になる。** これは驚くべき挙動だが、CMakeの仕様どおりである。実務的な結論はこうだ。

> **変数の真偽を判定したいときは、クォートせずに `if(VAR)` と書く。**
> `if("${VAR}")` と書いてはいけない。第5章4節で「変数はクォートしろ」と言うが、**`if` の真偽判定だけは例外**である。

`NOTFOUND` と `-NOTFOUND` サフィックスが偽になるのは、`find_package` や `find_library` が失敗したときに `XXX-NOTFOUND` という値を返すからだ（第18章）。

```cmake
find_library(FOO_LIB foo)
if(FOO_LIB)               # 見つかればパス、見つからなければ FOO_LIB-NOTFOUND
    ...
endif()
```

この設計を知っていると、`if(FOO_LIB)` という書き方が自然に読める。

## 5.3　`set` / `unset` と3種類の変数

### 通常変数

```cmake
set(MY_NAME "pixkit")
message("${MY_NAME}")       # pixkit
unset(MY_NAME)
message("[${MY_NAME}]")     # []  （未定義の変数は空文字列に展開される）
```

**未定義の変数を参照してもエラーにならず、空文字列になる。** これがCMakeで最も多いバグの原因だ。`${PIXKIT_VERSION}` と書くべきところを `${PIXIT_VERSION}` とタイプミスしても、静かに空文字列になって進んでしまう。

対策は2つある。

```cmake
if(NOT DEFINED MY_VAR)
    message(FATAL_ERROR "MY_VAR is required")
endif()
```

```
cmake --warn-uninitialized -S . -B build    # 未初期化変数の使用を警告
```

### キャッシュ変数

第2章8節で見た `CMakeCache.txt` に保存される変数だ。

```cmake
set(PIXKIT_ENABLE_SIMD ON CACHE BOOL "SIMD最適化を有効にする")
```

| | 通常変数 | キャッシュ変数 |
| --- | --- | --- |
| 生存期間 | その構成の実行中のみ | `CMakeCache.txt` に永続化 |
| ユーザーからの上書き | できない | `-DPIXKIT_ENABLE_SIMD=OFF` |
| 型 | なし | `BOOL` / `STRING` / `PATH` / `FILEPATH` |
| 説明文 | なし | 必須（GUIに表示される） |

**重要な性質：`set(... CACHE ...)` は、すでにキャッシュに値があれば何もしない。** 一度ユーザーが `-D` で設定した値を、`CMakeLists.txt` が勝手に上書きしないためだ。強制的に上書きするには `FORCE` を付けるが、これはユーザーの指定を無視することになるので、基本的に使ってはいけない。

真偽値のキャッシュ変数を作る場合、`option()` という専用コマンドがある。第8章5節で扱う。

### 環境変数

```cmake
message("PATH = $ENV{PATH}")
set(ENV{MY_VAR} "value")      # このCMakeプロセス内でのみ有効
```

`${}` ではなく `$ENV{}` を使う。環境変数への依存はビルドの再現性を下げるので、必要最小限にする。

### 変数のスコープ

```cmake
function(my_func)
    set(X "inside")
    message("in function: ${X}")     # inside
endfunction()

set(X "outside")
my_func()
message("after call: ${X}")          # outside  （関数内の変更は外に漏れない）
```

関数は新しいスコープを作る。`add_subdirectory`（第8章2節）も同様だ。呼び出し元に値を返したいときは `PARENT_SCOPE` を使う（5.8節）。

## 5.4　変数展開とクォートの落とし穴

ここがCMake初学者を最も苦しめる箇所だ。

### クォートしない展開は「セミコロンで分割される」

まず、正確なルールを押さえる。**クォートしない `${VAR}` は、展開後の値をセミコロン `;` で分割し、複数の引数としてコマンドに渡す。** 分割されるのはセミコロンであって、空白ではない。

引数の個数を数える関数を作って確認しよう。

```cmake
function(count)
    message(STATUS "ARGC=${ARGC} ARGV=[${ARGV}]")
endfunction()

set(S "Hello World")     # 空白を含む
set(L "a;b;c")           # セミコロンを含む＝リスト

count(${S})              # ARGC=1 ARGV=[Hello World]
count("${S}")            # ARGC=1 ARGV=[Hello World]
count(${L})              # ARGC=3 ARGV=[a;b;c]      ← 3個に分割された
count("${L}")            # ARGC=1 ARGV=[a;b;c]      ← 1個のまま
```

空白を含む値は、クォートしなくても分割されない。分割されるのは**セミコロンを含む値＝リスト**だけだ。

> **紛らわしい点**：ソースコードに直接書いた空白は、パース時点で引数の区切りになる。
> ```cmake
> message(Hello World)      # HelloWorld （引数2個。message は連結して表示する）
> set(S "Hello World")
> message(${S})             # Hello World （引数1個）
> ```
> 「変数の値の空白」と「ソースに書いた空白」は別物だ。分割されるのは後者である。

### 空の変数が引数ごと消える

```cmake
set(E "")
count(BEFORE ${E} AFTER)      # ARGC=2 ARGV=[BEFORE;AFTER]
count(BEFORE "${E}" AFTER)    # ARGC=3 ARGV=[BEFORE;;AFTER]
```

クォートしなければ**引数そのものが消える**。クォートすれば空文字列という引数が1つ残る。表示上は区別しにくいが、他のコマンドに渡すときに致命的な差になる。

```cmake
set(MAYBE_FLAG "")
target_compile_options(app PRIVATE ${MAYBE_FLAG})   # 引数0個。安全
target_compile_options(app PRIVATE "${MAYBE_FLAG}") # 空文字列を1個渡す。エラーの元
```

このケースでは**クォートしないほうが正しい**。

### 使い分けの指針

丸暗記できる単純な規則はない。**「この引数は何個になってほしいのか」**を考えて選ぶ。

| 場面 | 書き方 |
| --- | --- |
| 1個の値として渡したい（パス、名前、メッセージ） | `"${VAR}"` |
| リストを複数の引数に展開したい | `${VAR}` |
| 空かもしれない値を渡す（空なら引数ごと消したい） | `${VAR}` |
| 文字列比較 `STREQUAL` の両辺 | `"${VAR}"` |
| **`if` での真偽判定** | **`VAR`**（`${}` も引用符も付けない。5.2節・5.6節） |

### 多重展開

```cmake
set(TARGET_NAME "pixkit")
set(pixkit_VERSION "1.2.3")
message("${${TARGET_NAME}_VERSION}")     # 1.2.3
```

`${TARGET_NAME}` が `pixkit` に展開され、`${pixkit_VERSION}` として再評価される。CMakeの標準ライブラリはこのパターンを多用する（`find_package` が定義する `Foo_FOUND` など）。読めるようにはなっておく必要があるが、自分のコードで乱用しないほうがよい。

### エスケープ

```cmake
message("セミコロンそのもの: \;")
message([[ブラケット引数の中では ${VAR} も展開されない]])
```

`[[ ]]` は**ブラケット引数**で、中身がまったく解釈されない生文字列だ。正規表現を書くときに便利になる。

## 5.5　リストの正体

### リストはセミコロン区切りの文字列である

CMakeに「リスト型」はない。リストとは**セミコロンで区切られた1個の文字列**のことだ。

```cmake
set(FRUITS apple banana cherry)
message("${FRUITS}")          # apple;banana;cherry
```

`set` に複数の引数を渡すと、セミコロンで連結される。逆に、

```cmake
set(FRUITS "apple;banana;cherry")   # 上とまったく同じ
```

この2つは完全に等価だ。

### クォートしない展開＝リストの展開

```cmake
set(FRUITS apple banana cherry)

foreach(F ${FRUITS})           # 3回まわる
    message("${F}")
endforeach()

foreach(F "${FRUITS}")         # 1回だけ。"apple;banana;cherry" が1要素
    message("${F}")
endforeach()
```

5.4節の「クォートすると1引数、しないと分割」がここに直結する。**クォートしない `${リスト}` は、コマンドに複数の引数として渡される。** `target_link_libraries(app PRIVATE ${LIBS})` が動くのはこの仕組みだ。

### `list()` コマンド

```cmake
set(FRUITS apple banana cherry)

list(LENGTH FRUITS N)                 # N = 3
list(GET FRUITS 1 SECOND)             # SECOND = banana
list(APPEND FRUITS durian)            # apple;banana;cherry;durian
list(INSERT FRUITS 0 avocado)         # 先頭に挿入
list(REMOVE_ITEM FRUITS banana)       # 値で削除
list(FIND FRUITS cherry IDX)          # 見つからなければ -1
list(SORT FRUITS)
list(REVERSE FRUITS)
list(JOIN FRUITS ", " TEXT)           # "avocado, apple, cherry, durian"
list(REMOVE_DUPLICATES FRUITS)
message("${TEXT}")
```

`list(APPEND ...)` は第1引数を**変数名として**取り、その変数を書き換える。`${}` を付けないことに注意する。

### セミコロンを含む値が壊れる

リストがセミコロン区切りの文字列である、という設計の代償がこれだ。

```cmake
set(WEIRD "a;b")
list(LENGTH WEIRD N)
message("${N}")           # 2  （1つの文字列のつもりが2要素扱い）
```

Windowsの `PATH` のような**セミコロン区切りの値をCMake変数に入れると壊れる。** 対処法はエスケープ（`a\;b`）だが、そもそもそういう値を変数に入れない設計にするほうがよい。

## 5.6　`if` の条件式

CMakeの `if` は独特で、ここを誤解したままのコードは大量に存在する。

### 最大の罠：`if(VAR)` と `if("${VAR}")` は別物

5.2節で見たルールAとルールBを、`if` の文脈でもう一度確認する。

```cmake
set(NAME "pixkit")

if(NAME)
    message(STATUS "A: 真")
else()
    message(STATUS "A: 偽")
endif()

if("${NAME}")
    message(STATUS "B: 真")
else()
    message(STATUS "B: 偽")
endif()
```

```
-- A: 真
-- B: 偽
```

**同じ変数を見ているのに、結果が逆になる。**

- `if(NAME)` … 引数がクォートされておらず、`NAME` という変数が存在する。だから**変数として**評価され、値 `"pixkit"` は偽の定数ではないので**真**
- `if("${NAME}")` … 展開されて `if("pixkit")` になる。クォートされた**文字列として**評価され、`"pixkit"` は真の定数（`ON`/`YES`/`TRUE`/`Y`/非ゼロ数値）ではないので**偽**

第5章4節で「1個の値として渡したいならクォートする」と書いたが、`if` の真偽判定はその例外にあたる。

```cmake
if(PIXKIT_ENABLE_SIMD)          # ← 正しい
if("${PIXKIT_ENABLE_SIMD}")     # ← 値が ON/1 のときしか真にならない。事故の元
```

ON/OFF しか入らない変数なら後者でも一応動いてしまうため、この間違いは長く生き残りやすい。「文字列が入っているかどうか」を判定したくなった瞬間に壊れる。

### なぜこんな仕様なのか

`if(<定義済み変数名>)` を「値が偽の定数でなければ真」としたのは、`find_library` の結果を素直に書けるようにするためだ。

```cmake
find_library(FOO_LIB foo)       # 成功なら "C:/lib/foo.lib"、失敗なら "FOO_LIB-NOTFOUND"
if(FOO_LIB)                     # パス文字列は真、-NOTFOUND は偽
```

パス文字列を真として扱いたいので、ルールAは「偽の定数でなければ真」でなければならなかった。一方、`if("YES")` のような直書きの文字列を真偽値として解釈できると便利なので、ルールBは「真の定数なら真」になった。両者を統合しないままここまで来た、というのが実情だ。

### 明示的に書く

意図を確実に伝えたいときは、比較演算子や `DEFINED` を使う。

```cmake
if(DEFINED FOO)                  # 定義されているか（値は問わない）
if(NOT DEFINED FOO)
if("${FOO}" STREQUAL "BAR")      # 値の比較。両辺をクォートするのが安全
```

なお、CMake 3.1で導入されたポリシー `CMP0054` により、**クォートされた引数が変数名として再解釈されることはない**（`cmake_minimum_required(VERSION 3.28)` で自動的に有効）。だから `"${FOO}" STREQUAL "BAR"` は素直に文字列比較になる。古いCMakeでは、`FOO` の値がたまたま変数名と一致すると比較対象がすり替わる、という事故があった。

### 比較演算子

```cmake
if(A STREQUAL B)          # 文字列が等しい
if(A MATCHES "^pix")      # 正規表現マッチ
if(A EQUAL 3)             # 数値として等しい
if(A LESS 3)              # 数値比較。GREATER / LESS_EQUAL / GREATER_EQUAL も
if(A VERSION_LESS 1.2.3)  # バージョン番号として比較（"1.10" > "1.9" になる）
if(NOT A)
if(A AND B)
if(A OR B)
```

`VERSION_LESS` は重要だ。文字列比較では `"1.10"` は `"1.9"` より小さくなってしまうが、`VERSION_LESS` は正しく比較する。

### ファイルとターゲットの検査

```cmake
if(EXISTS "${CMAKE_CURRENT_SOURCE_DIR}/config.h")
if(IS_DIRECTORY "${SOME_PATH}")
if(TARGET pixkit-core)          # そのターゲットが定義済みか
if(COMMAND my_function)         # そのコマンドが存在するか
if(WIN32)                       # プラットフォーム判定
if(MSVC)                        # コンパイラ判定
```

`if(TARGET ...)` は、依存ライブラリが既に取り込まれているかを調べるときに使う（第14章、第18章）。

### `elseif` と `endif`

```cmake
if(A)
elseif(B)
else()
endif()
```

古いコードでは `endif(A)` のように条件を繰り返す書き方を見かけるが、現在は不要だ。`endif()` と書く。

## 5.7　`foreach` と `while`

### 基本形と `IN LISTS`

```cmake
set(FRUITS apple banana cherry)

foreach(F ${FRUITS})            # 古い書き方
    message("${F}")
endforeach()

foreach(F IN LISTS FRUITS)      # 推奨。変数名をそのまま渡す
    message("${F}")
endforeach()
```

`IN LISTS` を推奨する理由は、**空リストと空要素を正しく扱えるから**だ。`${FRUITS}` が空のとき、前者は `foreach(F)` となり構文エラーになりうるが、後者は0回まわって正常終了する。

### バリエーション

```cmake
foreach(I RANGE 5)              # 0,1,2,3,4,5  （終端を含む！）
foreach(I RANGE 1 10 2)         # 1,3,5,7,9
foreach(X IN ITEMS a b c)       # 直接列挙
foreach(NAME VER IN ZIP_LISTS NAMES VERSIONS)   # 2つのリストを並行に
```

`RANGE 5` が6回まわる（0から5まで）のは他言語と違うので注意する。

### `while` と `break` / `continue`

```cmake
set(I 0)
while(I LESS 3)
    message("i = ${I}")
    math(EXPR I "${I} + 1")
endwhile()
```

`break()` と `continue()` も使える。ただし、CMakeでループを大量に書いているなら、たいていは設計を見直したほうがよい。ビルド定義に複雑な制御フローが必要になるのは、ターゲットの切り方が間違っているサインであることが多い。

## 5.8　`function` と `macro`

同じ設定を何度も書くようになったら、関数にまとめる。第8章以降で `pixkit_add_library` のようなヘルパーを作ることになる。

### `function` の基本

```cmake
function(greet NAME)
    message("Hello, ${NAME}!")
endfunction()

greet("pixkit")        # Hello, pixkit!
```

### 引数の受け取り方

```cmake
function(show_args A B)
    message("A     = ${A}")
    message("B     = ${B}")
    message("ARGC  = ${ARGC}")    # 引数の総数
    message("ARGV  = ${ARGV}")    # 全引数のリスト
    message("ARGN  = ${ARGN}")    # 名前付き引数より後ろの余り
    message("ARGV0 = ${ARGV0}")
endfunction()

show_args(one two three four)
```

```
A     = one
B     = two
ARGC  = 4
ARGV  = one;two;three;four
ARGN  = three;four
ARGV0 = one
```

### `function` と `macro` の違い

```cmake
function(f)
    set(X "from function")
endfunction()

macro(m)
    set(X "from macro")
endmacro()

set(X "original")
f()
message("${X}")       # original    （関数は独自スコープ）
m()
message("${X}")       # from macro  （マクロは呼び出し元のスコープで実行される）
```

| | `function` | `macro` |
| --- | --- | --- |
| スコープ | 新しいスコープを作る | 作らない（テキスト展開に近い） |
| 引数 | 変数として存在する | **文字列置換される** |
| `${ARGN}` の扱い | 素直 | 親の `ARGN` と混ざる事故が起きる |
| 推奨度 | **こちらを使う** | 明確な理由があるときだけ |

**原則として `function` を使う。** `macro` が必要なのは「呼び出し元の変数を書き換えたい」場合だが、それは `PARENT_SCOPE` で実現できる。

### 呼び出し元に値を返す

```cmake
function(make_upper INPUT OUTPUT_VAR)
    string(TOUPPER "${INPUT}" RESULT)
    set(${OUTPUT_VAR} "${RESULT}" PARENT_SCOPE)
endfunction()

make_upper("pixkit" UPPER_NAME)
message("${UPPER_NAME}")     # PIXKIT
```

「結果を入れる変数の名前を引数で受け取る」のがCMakeの流儀だ。`set(${OUTPUT_VAR} ... PARENT_SCOPE)` の `${}` の位置に注意する。

### 名前付き引数：`cmake_parse_arguments`

実務で書く関数は、こういう呼ばれ方をしてほしい。

```cmake
pixkit_add_library(pixkit-codec
    SOURCES     src/ppm.cpp src/bmp.cpp
    HEADERS     include/pixkit/codec.hpp
    DEPENDS     pixkit::core
    ENABLE_TESTS
)
```

これを実現するのが `cmake_parse_arguments` だ。

```cmake
function(pixkit_add_library TARGET_NAME)
    set(options ENABLE_TESTS)                    # フラグ（値を取らない）
    set(oneValueArgs OUTPUT_NAME)                # 値を1つ取る
    set(multiValueArgs SOURCES HEADERS DEPENDS)  # 値を複数取る

    cmake_parse_arguments(PARSE_ARGV 1 ARG
        "${options}" "${oneValueArgs}" "${multiValueArgs}")

    if(NOT ARG_SOURCES)
        message(FATAL_ERROR "pixkit_add_library(${TARGET_NAME}): SOURCES is required")
    endif()

    if(ARG_UNPARSED_ARGUMENTS)
        message(FATAL_ERROR "unknown arguments: ${ARG_UNPARSED_ARGUMENTS}")
    endif()

    message(STATUS "target  = ${TARGET_NAME}")
    message(STATUS "sources = ${ARG_SOURCES}")
    message(STATUS "tests   = ${ARG_ENABLE_TESTS}")
endfunction()
```

パースされた結果は、指定した接頭辞（ここでは `ARG`）を付けた変数に入る。`SOURCES` → `ARG_SOURCES`、`ENABLE_TESTS` → `ARG_ENABLE_TESTS`（指定されていれば `TRUE`）。

`PARSE_ARGV 1 ARG` は「1番目（0起点）の引数以降をパースし、接頭辞 `ARG` を使う」という意味だ。`PARSE_ARGV` 形式は空要素も正しく扱えるので、こちらを使う。

そして `ARG_UNPARSED_ARGUMENTS` の検査を必ず入れる。これがないと、`SOURCE`（複数形の `S` を忘れた）のようなタイプミスが**黙って無視される**。

## 5.9　`message()` でデバッグする

### メッセージの種類


## この章のまとめ

- CMakeスクリプトは**コマンド呼び出しの列**で、上から順に**実行される**。コマンド名は大文字小文字を区別しないが、変数名は区別する
- **すべての値は文字列。** 型はない。真偽判定には**2つのルール**がある。クォートなしの変数名は「偽の定数（`OFF`/`NO`/空/`0`/`*-NOTFOUND`）でなければ真」、クォートされた文字列は「真の定数（`ON`/`YES`/`TRUE`/`Y`/非ゼロ数値）でなければ偽」
- 変数は**通常変数・キャッシュ変数・環境変数**の3種類。未定義の変数は**エラーにならず空文字列**になる
- クォートしない `${VAR}` は**セミコロンで分割**されて複数引数になる（空白では分割されない）。空の変数は引数ごと消える。リストの展開はこの仕組みで動く
- リストは**セミコロン区切りの文字列**。操作は `list()` コマンドで行う
- **真偽判定は `if(VAR)` と書く。`if("${VAR}")` と書いてはいけない。** 値の比較は `if("${FOO}" STREQUAL "...")`、存在確認は `if(DEFINED FOO)`、バージョン比較は `VERSION_LESS`
- 関数は `function` を使う（`macro` はスコープを作らない）。値を返すには `PARENT_SCOPE`、名前付き引数には `cmake_parse_arguments(PARSE_ARGV ...)`。**`ARG_UNPARSED_ARGUMENTS` のチェックを忘れない**
- デバッグは `message(STATUS "VAR = [${VAR}]")` が基本。`cmake -P` でスクリプト単体を実行でき、実験に便利

これでCMake言語の道具は揃った。次の第6章では、本書の中核概念である**ターゲットと使用要件**に入る。`PUBLIC` / `PRIVATE` / `INTERFACE` の使い分けが分かれば、CMakeの8割は理解したと言ってよい。
