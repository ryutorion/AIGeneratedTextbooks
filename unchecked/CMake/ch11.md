# 第11章　動的ライブラリ（`pixkit::filter`）

## この章のゴール

- `add_library(... SHARED)` が生成する `.dll` と**インポートライブラリ `.lib`** の関係を理解する
- `__declspec(dllexport/dllimport)` の仕組みと、マクロの正しい与え方を知る
- **`generate_export_header` でエクスポートマクロを自動生成する**
- `WINDOWS_EXPORT_ALL_SYMBOLS` の使いどころと限界を判断できる
- **DLL境界を越えてはいけないもの**を理解し、それを踏まえてAPIを設計する
- `VERSION` / `SOVERSION` / `OUTPUT_NAME` / `DEBUG_POSTFIX` を使い分ける
- **`$<TARGET_RUNTIME_DLLS:...>` で実行時のDLLを配置する**
- `BUILD_SHARED_LIBS` で静的／動的を切り替えられる設計にする

本書で最も「Windows固有の知識」が要求される章だ。逆に言えば、ここを越えれば残りは楽になる。

---

## 11.1　`.dll` とインポートライブラリ `.lib`

### 生成物が2つある

```cmake
add_library(pixkit-filter SHARED src/filters.cpp)
```

Windowsでは、これが**2つのファイル**を生成する。

| ファイル | 中身 | いつ必要か |
| --- | --- | --- |
| `pixkit-filter.dll` | 実際のコード | **実行時** |
| `pixkit-filter.lib` | 関数名とDLL名の対応表 | **リンク時** |

後者を**インポートライブラリ**と呼ぶ。静的ライブラリと同じ `.lib` 拡張子だが、中身はまったく違う。コードは1バイトも入っておらず、「`blur3x3` を呼びたければ `pixkit-filter.dll` の何番目のエントリを見よ」という情報だけが入っている。

```
リンク時:  pixcli.exe  ←  pixkit-filter.lib （対応表を見て参照を埋め込む）
実行時:    pixcli.exe  →  pixkit-filter.dll （実際に呼ぶ）
```

### CMakeでの扱いの違い

第8章6節で出力ディレクトリを設定したときの表を思い出してほしい。

| 変数 | 何が置かれるか |
| --- | --- |
| `CMAKE_RUNTIME_OUTPUT_DIRECTORY` | `.exe` と **`.dll`** |
| `CMAKE_ARCHIVE_OUTPUT_DIRECTORY` | 静的ライブラリの `.lib` と **インポート `.lib`** |

**DLLは `RUNTIME`、インポートライブラリは `ARCHIVE` に分類される。** ここを取り違えると、第21章のインストールで DLL が `lib/` に入ってしまい、実行時に見つからなくなる。

### エクスポートしないと何も入らない

重要な事実がある。**Windowsでは、明示的にエクスポートを指定しない限り、DLLから何も公開されない。**

Linux（ELF）では逆で、既定ですべてのシンボルが公開される。この違いが、Windowsでのビルドを難しくしている最大の要因だ。

何もエクスポートしていない状態でリンクすると、こうなる。

```
error LNK2019: 未解決の外部シンボル "void __cdecl pixkit::filter::grayscale(...)"
error LNK1120: 1 件の未解決の外部参照
```

そして、**インポートライブラリ `.lib` そのものが生成されない**こともある（エクスポートすべきものが1つもないため）。「`.lib` が見つからない」というエラーの原因は、たいていこれだ。

## 11.2　`__declspec(dllexport)` と `dllimport`

### 2つの立場

同じヘッダが、2つの立場から読まれる。

| 誰が読むか | 必要な宣言 | 意味 |
| --- | --- | --- |
| DLLを**ビルドする側**（`filters.cpp`） | `__declspec(dllexport)` | この関数を公開する |
| DLLを**使う側**（`main.cpp`） | `__declspec(dllimport)` | この関数はDLLにある |

`dllimport` は省略しても動く場合があるが、付けたほうが速い（間接呼び出しの最適化が効く）。データをエクスポートする場合は**必須**だ。

### 素朴な実装

```cpp
// pixkit/filter/filters.hpp
#ifdef PIXKIT_FILTER_BUILDING
#  define PIXKIT_FILTER_API __declspec(dllexport)
#else
#  define PIXKIT_FILTER_API __declspec(dllimport)
#endif

PIXKIT_FILTER_API void grayscale(ImageView img) noexcept;
```

```cmake
target_compile_definitions(pixkit-filter PRIVATE PIXKIT_FILTER_BUILDING)
```

`PRIVATE` であることが決定的に重要だ。**自分のビルドのときだけ `dllexport` になり、利用側では `dllimport` になる。** ここを `PUBLIC` にすると、利用側も `dllexport` になってしまい、リンクエラーになる。

第6章3節で学んだ `PUBLIC` / `PRIVATE` の使い分けが、ここで最も鮮明な形で現れる。

### CMakeが自動で定義するマクロ

実は、自分で `target_compile_definitions` を書く必要はない。**CMakeは `SHARED` ライブラリをビルドするとき、`<ターゲット名>_EXPORTS` というマクロを自動的に `PRIVATE` 定義する。**

```cmake
add_library(pixkit-filter SHARED src/filters.cpp)
# → filters.cpp のコンパイル時に -Dpixkit_filter_EXPORTS が渡る
```

**ここに落とし穴がある。ターゲット名の `-`（ハイフン）が `_`（アンダースコア）に変換される。**

| ターゲット名 | 定義されるマクロ |
| --- | --- |
| `pixkit-filter` | `pixkit_filter_EXPORTS` |
| `pixkit_filter` | `pixkit_filter_EXPORTS` |
| `PixKit.Filter` | `PixKit_Filter_EXPORTS` |

英数字以外の文字がすべて `_` に置換されるためだ。`#ifdef pixkit-filter_EXPORTS` と書いてしまい、「なぜエクスポートされないのか」と悩む事故がよく起きる。

この名前は `DEFINE_SYMBOL` プロパティで変更できる。

```cmake
set_target_properties(pixkit-filter PROPERTIES DEFINE_SYMBOL "PIXKIT_FILTER_BUILDING")
```

なお、`get_target_property` で `DEFINE_SYMBOL` を読んでも、**明示的に設定していなければ `NOTFOUND` が返る**（CMakeが内部で既定値を計算しているだけで、プロパティには入っていない）。確認したいときは `compile_commands.json` を見るのが確実だ。

## 11.3　`generate_export_header` を使う

11.2節のマクロを手で書く必要はない。CMakeが生成してくれる。

```cmake
include(GenerateExportHeader)

generate_export_header(pixkit-filter
    BASE_NAME         PIXKIT_FILTER
    EXPORT_MACRO_NAME PIXKIT_FILTER_API
    EXPORT_FILE_NAME  ${CMAKE_CURRENT_BINARY_DIR}/gen/pixkit/filter/pixkit_filter_export.hpp
)
```

生成されるヘッダは、MSVCではこうなる（要点だけ抜粋）。

```cpp
#ifndef PIXKIT_FILTER_API_H
#define PIXKIT_FILTER_API_H

#ifdef PIXKIT_FILTER_STATIC_DEFINE
#  define PIXKIT_FILTER_API
#  define PIXKIT_FILTER_NO_EXPORT
#else
#  ifndef PIXKIT_FILTER_API
#    ifdef pixkit_filter_EXPORTS
        /* We are building this library */
#      define PIXKIT_FILTER_API __declspec(dllexport)
#    else
        /* We are using this library */
#      define PIXKIT_FILTER_API __declspec(dllimport)
#    endif
#  endif
#  ifndef PIXKIT_FILTER_NO_EXPORT
#    define PIXKIT_FILTER_NO_EXPORT
#  endif
#endif

#ifndef PIXKIT_FILTER_DEPRECATED
#  define PIXKIT_FILTER_DEPRECATED __declspec(deprecated)
#endif
...
```

手で書くものと同じだが、次の利点がある。

- **`_EXPORTS` マクロ名の変換規則を間違えない**（11.2節の落とし穴を回避できる）
- **`PIXKIT_FILTER_STATIC_DEFINE` に対応している**（静的ライブラリとして使うときの分岐。11.8節）
- `PIXKIT_FILTER_NO_EXPORT` や `PIXKIT_FILTER_DEPRECATED` も付いてくる
- GCC/Clangの `__attribute__((visibility("default")))` にも対応する

### 生成先はビルドツリー

生成したヘッダは `CMAKE_CURRENT_BINARY_DIR` の下に置く。第8章4節の `version.hpp` と同じ考え方だ。そして、そこへのインクルードパスを追加する。

```cmake
target_include_directories(pixkit-filter
    PUBLIC
        $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
        $<BUILD_INTERFACE:${CMAKE_CURRENT_BINARY_DIR}/gen>
        $<INSTALL_INTERFACE:include>
)
```

`PUBLIC` にすることが必須だ。**利用側もこのヘッダを読む**（`dllimport` の側）からである。

### 使い方

```cpp
#pragma once

#include <pixkit/core/image.hpp>
#include <pixkit/filter/pixkit_filter_export.hpp>   // 生成されたヘッダ

namespace pixkit::filter {

PIXKIT_FILTER_API void grayscale(ImageView img) noexcept;

}
```

### GCC/Clangでの補足

Linuxでは既定で全シンボルが公開されるので、`visibility` の設定を明示的に絞る。

```cmake
set_target_properties(pixkit-filter PROPERTIES
    CXX_VISIBILITY_PRESET     hidden
    VISIBILITY_INLINES_HIDDEN ON
)
```

**MSVCではこの設定は何もしない**（もともと隠されているため）が、書いておけばWindowsとLinuxで同じエクスポート集合になる。移植性のあるライブラリを作るなら、`generate_export_header` とセットで書くのが定石だ。

## 11.4　`WINDOWS_EXPORT_ALL_SYMBOLS`

エクスポートマクロを書くのが面倒なとき、CMakeには抜け道がある。

```cmake
set_target_properties(pixkit-filter PROPERTIES WINDOWS_EXPORT_ALL_SYMBOLS ON)
```

CMakeがオブジェクトファイルのシンボルを走査し、`.def` ファイルを自動生成してリンカに渡す。**ソースコードに一切マクロを書かずにDLLが作れる。**

### 便利だが、限界がある

| 項目 | 状況 |
| --- | --- |
| 関数 | ○ エクスポートされる |
| クラスのメンバ関数 | ○ エクスポートされる |
| **データ（グローバル変数、staticメンバ）** | **× エクスポートされない** |
| テンプレート | △ 実体化されたものだけ |
| `dllimport` の最適化 | × 効かない（利用側にマクロがないため） |
| C++の例外の伝播 | △ 場合による |

**データがエクスポートされない**のが最大の制約だ。CMakeの公式ドキュメントも明記している。グローバル変数を公開したければ、結局その変数にだけ `__declspec(dllexport)` を書くことになる。

さらに、エクスポートされるシンボル数が膨大になり、

- DLLのロードが遅くなる
- 内部実装のシンボルまで公開され、意図しない依存を招く
- 64K個のエクスポート上限に達することがある

### 使ってよい場面

- **社内限定の、素早いプロトタイプ**
- 既存の大規模なコードベースを、とりあえずDLL化したいとき
- テストのために、内部関数にアクセスしたいとき

### 使うべきでない場面

- **他人に配布するライブラリ**（本書の `pixkit` はこちら）
- 公開APIを意図的に絞りたいとき
- データをエクスポートする必要があるとき

**本書では `generate_export_header` を使う。** 「公開するものを自分で決める」ことは、ライブラリ設計そのものだからだ。

## 11.5　DLL境界を越えてはいけないもの

**この節が本章で最も重要だ。** ここを理解せずにDLLを作ると、原因不明のクラッシュに苦しむことになる。

### 問題の根源：ヒープとABIが別々

DLLと実行ファイルは、**別々にコンパイルされ、別々にリンクされた、独立したモジュール**だ。それぞれが自分のCランタイム（CRT）を持ちうる。

```
pixcli.exe   → CRT-A（自分のヒープ）
filter.dll   → CRT-B（自分のヒープ）
```

この状態で、DLL側で確保したメモリを実行ファイル側で解放すると、**別のヒープに返そうとして即座にクラッシュする**。

### 越えてはいけないものの一覧

| 越えてはいけないもの | 理由 |
| --- | --- |
| **`new` / `malloc` したポインタの所有権** | 確保と解放が別ヒープになる |
| **`std::vector` / `std::string` などのSTL型** | 内部でヒープを使う。**さらに実装が構成ごとに違う** |
| **`std::shared_ptr` / `std::unique_ptr`** | デリータが別モジュールのヒープを触る |
| **C++の例外** | 実装依存。特にコンパイラが違うと伝播しない |
| **iostream のストリームオブジェクト** | グローバル状態がモジュールごとに別 |
| **クラスのインライン関数のインライン化タイミング** | 片方だけ再ビルドするとレイアウトがずれる |

STL型が特に厄介だ。MSVCの `std::vector` は、Debugビルド（`_ITERATOR_DEBUG_LEVEL=2`）とReleaseビルドで**メモリレイアウトが違う**。DLLをReleaseで、実行ファイルをDebugでビルドすると、`std::vector` を渡した瞬間に壊れる。しかもコンパイルもリンクも通ってしまう。

### 対処法1：安全なAPIだけを境界に置く

**本書が採る方針。** DLL境界を越える関数の引数と戻り値を、**POD（トリビアルな構造体）とポインタだけ**に限定する。

```cpp
namespace pixkit::filter {

// --- DLL境界を越える関数：引数はPODとポインタだけ ---
PIXKIT_FILTER_API void grayscale(ImageView img) noexcept;
PIXKIT_FILTER_API void threshold(ImageView img, std::uint8_t level) noexcept;
PIXKIT_FILTER_API void blur3x3(ImageView src, ImageView dst) noexcept;

// --- 便利関数：ヘッダ内 inline なので、DLL境界を越えない ---
[[nodiscard]] inline Image blurred(Image& src)
{
    Image dst(src.width(), src.height());
    blur3x3(src.view(), dst.view());
    return dst;
}

}
```

設計のポイントは3つある。

1. **`ImageView` はポインタ＋整数2つだけ**のトリビアルな型なので、境界を安全に越えられる（第10章で `ImageView` を作った理由がこれだ）
2. **メモリの確保・解放は呼び出し側が行う。** DLLは渡されたバッファを書き換えるだけ
3. **`std::vector` を持つ `Image` を使う便利関数は `inline`** にしてヘッダに置く。呼び出し側でコンパイルされるので、境界を越えない
4. **`noexcept` を付けて例外を境界の外に出さない**

この形にしておけば、DLLと実行ファイルのビルド構成が違っていても壊れない。

### 対処法2：構成とランタイムを揃える

現実的な妥協案として、「DLLと実行ファイルを、同じコンパイラ・同じ構成・同じランタイムでビルドする」と決めてしまう方法がある。1つのCMakeプロジェクトの中で両方をビルドしている限り、これは自動的に守られる。

その場合は STL 型を境界で使ってもよい——ただし**そのDLLは配布できない**。利用者が別の構成でビルドしたら壊れるからだ。

第12章5節で `MSVC_RUNTIME_LIBRARY` を扱うが、これは「揃える」ための道具である。

### 対処法3：C言語のAPIにする

最も堅牢な方法だ。`extern "C"` で、C++の機能を一切使わないAPIを公開する。

```cpp
extern "C" PIXKIT_FILTER_API
int pixkit_filter_blur3x3(unsigned char* dst, const unsigned char* src,
                          int width, int height);
```

名前修飾もなくなるので、他の言語からも呼べる。プラグイン機構（`MODULE` ライブラリ）ではこの形が必須になる。

### まとめ

| 方針 | 配布できるか | 使いやすさ |
| --- | --- | --- |
| POD/ポインタだけのAPI＋inlineの便利関数 | **○** | ○ |
| 構成を揃える前提でSTL型を渡す | × | ◎ |
| `extern "C"` のCインターフェース | ◎ | △ |

静的ライブラリならこの問題は**まったく起きない**。第9章で「特に理由がなければ静的から始めるのがよい」と書いたのは、このためだ。

## 11.6　名前とバージョンのプロパティ

```cmake
set_target_properties(pixkit-filter PROPERTIES
    OUTPUT_NAME   "pixfilter"
    DEBUG_POSTFIX "d"
    VERSION       ${PROJECT_VERSION}
    SOVERSION     ${PROJECT_VERSION_MAJOR}
)
```

### `OUTPUT_NAME`

ターゲット名と出力ファイル名を分離する。ターゲット名は `pixkit-filter`（CMake内で一意）、ファイル名は `pixfilter.dll`（配布時の名前）、という使い分けができる。

### `DEBUG_POSTFIX`

Debugビルドの成果物に接尾辞を付ける。

```
pixfilter.dll     ← Release
pixfilterd.dll    ← Debug
```

**同じディレクトリにDebugとReleaseを共存させたいとき**に必要になる。第21章でインストールするとき、両方を同じ `bin/` に入れるなら必須だ。

注意点として、これは実行ファイルには**適用されない**（`DEBUG_POSTFIX` はライブラリのみ）。実行ファイルにも付けたければ `set_target_properties(pixcli PROPERTIES DEBUG_POSTFIX "d")` と個別に指定する。

### `VERSION` と `SOVERSION`

Unixでは、これがファイル名とシンボリックリンクを作る。

```
libpixfilter.so.1.2.3      ← 実体
libpixfilter.so.1          → SOVERSION（ABIバージョン）
libpixfilter.so            → 開発用リンク
```

**Windowsでは、ファイル名は変わらない。** `pixfilter.dll` のままだ。代わりに、`VERSION` の `<major>.<minor>` がバイナリの**イメージバージョン**として埋め込まれる（リンカの `/VERSION` 相当）。

つまりWindowsでは、`VERSION` / `SOVERSION` の実用的な効果は小さい。それでも書いておく理由は、

- Linuxに移植したときに正しく動く
- `dumpbin /headers` でバージョンが確認できる
- 意図の記録として機能する

DLLのバージョン管理をWindowsで真面目にやるなら、リソースファイル（`.rc`）にバージョン情報を埋め込むのが本筋になる。

## 11.7　実行時にDLLを見つけさせる

### 問題

ビルドは通った。実行しようとすると落ちる。

```
コード実行できません。pixkit-filter.dll が見つかりません。
```

Windowsは、実行時に次の順序でDLLを探す（簡略化した説明）。

1. 実行ファイルと同じディレクトリ
2. システムディレクトリ
3. `PATH` に含まれるディレクトリ

**ビルドツリーの中でDLLと実行ファイルが別のディレクトリにあると、1に該当せず失敗する。**

### 解決策1：出力ディレクトリを揃える（第8章6節）

```cmake
set(CMAKE_RUNTIME_OUTPUT_DIRECTORY "${CMAKE_BINARY_DIR}/bin")
```

DLLも `.exe` も `RUNTIME` 扱いなので、両方が `bin/` に出る。**自分のプロジェクト内のDLLは、これで解決する。**

第8章でこの設定を入れたのは、この章のためだった。

### 解決策2：`$<TARGET_RUNTIME_DLLS:...>`

外部ライブラリのDLL（第19章のvcpkgで入るもの）は、出力ディレクトリを変えられない。CMake 3.21で追加されたジェネレータ式を使う。

```cmake
add_custom_command(TARGET pixcli POST_BUILD
    COMMAND ${CMAKE_COMMAND} -E copy_if_different
            $<TARGET_RUNTIME_DLLS:pixcli> $<TARGET_FILE_DIR:pixcli>
    COMMAND_EXPAND_LISTS
)
```

`$<TARGET_RUNTIME_DLLS:pixcli>` は、**`pixcli` が実行時に必要とするDLLのパスの一覧**に展開される。推移的な依存もたどってくれる。

3つの注意点がある。

**注意1：`COMMAND_EXPAND_LISTS` が必須**

この式はセミコロン区切りのリストに展開される（第5章5節）。`COMMAND_EXPAND_LISTS` がないと、リスト全体が1つの引数として扱われて失敗する。

**注意2：非Windowsでは空になる**

DLLの概念がないプラットフォームでは空文字列になる。すると `cmake -E copy_if_different` の引数が足りなくなり、**ビルドが失敗する**。

```
CMake Error: cmake -E copy_if_different must be called with at least two arguments
```

必ずガードする。

```cmake
if(WIN32)
    add_custom_command(TARGET pixcli POST_BUILD
        COMMAND ${CMAKE_COMMAND} -E copy_if_different
                $<TARGET_RUNTIME_DLLS:pixcli> $<TARGET_FILE_DIR:pixcli>
        COMMAND_EXPAND_LISTS
    )
endif()
```

本書はWindows専用だが、この1行は書いておく。CIでLinuxビルドを追加したとき（第15章）に効いてくる。

**注意3：システムDLLは含まれない**

`kernel32.dll` やVisual C++ランタイム（`msvcp140.dll` など）は含まれない。それらの配布は別の話（付録C）になる。

### 解決策3：デバッグ時の `PATH`

Visual Studio でF5デバッグするときは、`launch.vs.json`（第3章4節）で環境変数を足す方法もある。

```json
{
  "type": "default",
  "projectTarget": "pixcli.exe",
  "env": {
    "PATH": "${workspaceRoot}\\out\\build\\x64-debug\\bin;%PATH%"
  }
}
```

ただし、これは「開発者の環境だけの対症療法」だ。**テスト実行（第14章6節）やCIでは効かない**ので、解決策1・2を基本にする。

## 11.8　`BUILD_SHARED_LIBS` に対応する

### 利用者に選ばせる

```cmake
add_library(pixkit-filter src/filters.cpp)     # STATIC/SHARED を書かない
```

こう書くと、`BUILD_SHARED_LIBS` が `ON` なら動的、`OFF`（既定）なら静的になる。利用者は次のように選べる。

```
cmake --preset x64-debug -DBUILD_SHARED_LIBS=ON
```

### 静的のときにエクスポートマクロを無効化する

問題は `PIXKIT_FILTER_API` だ。静的ライブラリなのに `__declspec(dllimport)` が付いていると、リンクエラーになる。

`generate_export_header` が生成するヘッダには、この分岐が用意されている。

```cpp
#ifdef PIXKIT_FILTER_STATIC_DEFINE
#  define PIXKIT_FILTER_API           // 空になる
#else
   ... dllexport / dllimport ...
#endif
```

だから、静的ビルドのときに `PIXKIT_FILTER_STATIC_DEFINE` を定義すればよい。**利用側にも必要なので `PUBLIC`** にする。

```cmake
add_library(pixkit-filter src/filters.cpp)

include(GenerateExportHeader)
generate_export_header(pixkit-filter
    BASE_NAME         PIXKIT_FILTER
    EXPORT_MACRO_NAME PIXKIT_FILTER_API
    EXPORT_FILE_NAME  ${CMAKE_CURRENT_BINARY_DIR}/gen/pixkit/filter/pixkit_filter_export.hpp
)

get_target_property(PIXKIT_FILTER_TYPE pixkit-filter TYPE)
if(PIXKIT_FILTER_TYPE STREQUAL "STATIC_LIBRARY")
    target_compile_definitions(pixkit-filter PUBLIC PIXKIT_FILTER_STATIC_DEFINE)
endif()
```

`get_target_property(... TYPE)` で実際の種別を問い合わせているのがポイントだ。`BUILD_SHARED_LIBS` を直接見るより確実である（個別に `STATIC` を指定された場合にも対応できる）。

### 静的にしたときのDLL問題は消える

`BUILD_SHARED_LIBS=OFF` なら、11.7節の話はまるごと不要になる。**「配布時は静的、開発時は動的」**という運用もありうる。動的リンクのほうが、ライブラリを直したときの再リンクが速いからだ。

### 本書の方針

第11章のハンズオンでは `SHARED` を明示してDLLの挙動を学ぶ。そのうえで、章の最後に `BUILD_SHARED_LIBS` 対応に書き換え、両方でビルドが通ることを確認する。

### 手順1：公開ヘッダを書く

`libs/filter/include/pixkit/filter/filters.hpp`

```cpp
#pragma once

#include <pixkit/core/image.hpp>
#include <pixkit/filter/pixkit_filter_export.hpp>   // 生成される

#include <cstdint>

namespace pixkit::filter {

// --- DLL境界を越える関数：引数はPODとポインタだけ（11.5節）---
PIXKIT_FILTER_API void grayscale(ImageView img) noexcept;
PIXKIT_FILTER_API void threshold(ImageView img, std::uint8_t level) noexcept;

[[nodiscard]] inline Image blurred(Image& src)
{

    blur3x3(src.view(), dst.view());
    return dst;
}

}  // namespace pixkit::filter
```

`blurred` が `Image&`（非const）を取っているのは、`Image::view()` が非constだからだ。const版のビューを追加するのは良い練習になる（発展課題）。

### 手順2：実装を書く

`libs/filter/src/filters.cpp`

```cpp
#include <pixkit/filter/filters.hpp>

#include <pixkit/core/color.hpp>

#include <algorithm>

namespace pixkit::filter {

void grayscale(ImageView img) noexcept
{
    for (int y = 0; y < img.height(); ++y) {
        for (int x = 0; x < img.width(); ++x) {
            img[x, y] = to_gray(img[x, y]);
        }
    }
}

void threshold(ImageView img, std::uint8_t level) noexcept
{
    for (int y = 0; y < img.height(); ++y) {
        for (int x = 0; x < img.width(); ++x) {
            const std::uint8_t v = luminance(img[x, y]) >= level ? 255 : 0;
            img[x, y] = Rgb8{v, v, v};
        }
    }
}

void blur3x3(ImageView src, ImageView dst) noexcept
{
    if (src.empty() || dst.empty()) return;
    if (src.width() != dst.width() || src.height() != dst.height()) return;

    const int w = src.width();
    const int h = src.height();

    for (int y = 0; y < h; ++y) {
        for (int x = 0; x < w; ++x) {
            int r = 0, g = 0, b = 0, n = 0;
            for (int dy = -1; dy <= 1; ++dy) {
                for (int dx = -1; dx <= 1; ++dx) {
                    const int sx = std::clamp(x + dx, 0, w - 1);
                    const int sy = std::clamp(y + dy, 0, h - 1);
                    const Rgb8 c = src[sx, sy];
                    r += c.r; g += c.g; b += c.b; ++n;
                }
            }
            dst[x, y] = Rgb8{ static_cast<std::uint8_t>(r / n),
                              static_cast<std::uint8_t>(g / n),
                              static_cast<std::uint8_t>(b / n) };
        }
    }
}

}  // namespace pixkit::filter
```

`noexcept` を付けているので、万一例外が飛べば `std::terminate` になる。**DLL境界の外に例外を出さない**という設計方針の表明だ（11.5節）。

## この章のまとめ

- `SHARED` ライブラリは `.dll`（実行時）と**インポートライブラリ `.lib`**（リンク時）の2つを生成する。**DLLは `RUNTIME`、インポートライブラリは `ARCHIVE`** に分類される
- **Windowsでは明示的にエクスポートしないと何も公開されない。** `__declspec(dllexport)` / `dllimport` をマクロで切り替える
- CMakeは `<ターゲット名>_EXPORTS` を自動的に `PRIVATE` 定義する。**英数字以外は `_` に置換される**（`pixkit-filter` → `pixkit_filter_EXPORTS`）
- **`generate_export_header` を使う。** マクロ名の変換規則を間違えず、静的ビルド用の分岐（`*_STATIC_DEFINE`）も付いてくる。生成先はビルドツリー、インクルードパスは `PUBLIC`
- `WINDOWS_EXPORT_ALL_SYMBOLS` は手軽だが、**データをエクスポートできない**。配布するライブラリでは使わない
- **DLL境界を越えてよいのは POD とポインタだけ。** `std::vector` などのSTL型、`new` したポインタの所有権、例外を越えさせない。境界の関数は `noexcept` にし、便利関数は `inline` でヘッダに置く
- Windowsでは `VERSION` / `SOVERSION` はファイル名を変えない（イメージバージョンになる）。`DEBUG_POSTFIX` は Debug/Release を共存させるために使う
- 実行時のDLL探索は、**出力ディレクトリを揃える**（第8章6節）ことが基本。外部のDLLは **`$<TARGET_RUNTIME_DLLS:...>`** をPOST_BUILDでコピーする。`COMMAND_EXPAND_LISTS` と `if(WIN32)` のガードを忘れない
- `add_library` で種別を省略すれば `BUILD_SHARED_LIBS` で切り替えられる。静的のときは `*_STATIC_DEFINE` を `PUBLIC` 定義する

これで3種類のライブラリが揃った。次の第12章では、これらを **Debug / Release でどう作り分けるか**を扱う。マルチ構成ジェネレータ、`MSVC_RUNTIME_LIBRARY`、PDBの扱い、ジェネレータ式の実践、そしてリンク時最適化まで、ここまで断片的に触れてきた話を整理する。第3部の締めくくりだ。
