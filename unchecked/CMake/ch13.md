# 第13章　CTest入門

## この章のゴール

- `enable_testing()` と `include(CTest)` の違いを説明できる
- `add_test` でテストを登録し、`ctest` で実行する
- テストプロパティ（`LABELS` / `TIMEOUT` / `WILL_FAIL` / `PASS_REGULAR_EXPRESSION` など）を使い分ける
- `ctest` の絞り込み・並列実行・出力オプションを使いこなす
- `testPresets`（第4章）とVisual Studio のテストエクスプローラを連携させる

第4部の入口として、まず**テストフレームワークなしで**CTestだけを扱う。GoogleTestを入れるのは次の章だ。順序を分けるのには理由がある。**CTestは「テストを実行して結果を集める仕組み」であって、テストを書くためのものではない。** この役割分担を先に理解しておくと、第14章の話がすっきり入る。

## 13.1　CTestとは何か

### CTestはテストランナーである

```
CTest がやること：
  ・登録されたコマンドを実行する
  ・終了コード（と、必要なら出力）を見て成功・失敗を判定する
  ・結果を集計して報告する

CTest がやらないこと：
  ・アサーションを提供する
  ・テストケースを書く手段を提供する
```

CTestから見れば、テストとは**「実行して、終了コード0を返すコマンド」**でしかない。それが1000個のアサーションを持つGoogleTestの実行ファイルでも、単なるバッチファイルでも、Pythonスクリプトでも構わない。

この単純さゆえに、CTestは何でも登録できる。

- ユニットテストの実行ファイル（第14章）
- CLIツールの動作確認（この章のハンズオン）
- 生成されたファイルの内容比較
- 静的解析の実行

### `enable_testing()` と `include(CTest)`

まぎらわしい2つがある。

```cmake
enable_testing()      # テスト機能を有効にするだけ
```

```cmake
include(CTest)        # 上に加えて、いろいろやる
```

`include(CTest)` は、内部で `enable_testing()` を呼ぶほか、次のことをする。

| すること | 説明 |
| --- | --- |
| `BUILD_TESTING` オプションを定義 | 既定 `ON`。`OFF` にすると `enable_testing()` を呼ばない |
| `CTestConfig.cmake` を読む | CDash（テスト結果のダッシュボード）への送信設定 |
| `Experimental` / `Nightly` などのターゲットを追加 | CDash連携用 |
| `DartConfiguration.tcl` を生成 | 同上 |

CDashを使わないなら、余計なものが増えるだけとも言える。しかし **`BUILD_TESTING` は事実上の標準オプション**であり、多くのプロジェクトが対応しているので、本書では `include(CTest)` を使う。第8章でそう書いた。

```cmake
if(PROJECT_IS_TOP_LEVEL)
    include(CTest)
endif()
```

**トップレベルのときだけ呼ぶ**のが重要だ（第8章3節）。他人のプロジェクトに取り込まれたとき、勝手に相手のテスト設定を触ってはいけない。

### 呼ぶ位置に注意

`enable_testing()`（および `include(CTest)`）は、**`add_test` を呼ぶすべてのディレクトリの、共通の祖先で呼ばなければならない。** 通常はトップレベルの `CMakeLists.txt` だ。

サブディレクトリで呼んでも、その下でしか効かない。「テストを登録したのに `ctest` に出てこない」原因の1つがこれである。

## 13.2　`add_test` の最小形

```cmake
add_test(NAME cli.version COMMAND pixcli --version)
```

| 引数 | 意味 |
| --- | --- |
| `NAME` | テスト名。`ctest -R` での絞り込みに使う |
| `COMMAND` | 実行するコマンドと引数 |

`COMMAND` の第1引数が**ターゲット名**の場合、CMakeがそれを実行ファイルのパスに置き換えてくれる。だから、

```cmake
add_test(NAME cli.version COMMAND pixcli --version)
add_test(NAME cli.version COMMAND $<TARGET_FILE:pixcli> --version)
```

はほぼ同じ意味になる。後者はジェネレータ式（第7章8節）を使った明示的な書き方で、`OUTPUT_NAME` や `DEBUG_POSTFIX`（第11章6節）を変えていても正しく解決される。**迷ったら `$<TARGET_FILE:...>` を使う。**

### テスト名の付け方

```cmake
add_test(NAME codec.ppm.roundtrip ...)
add_test(NAME cli.version ...)
add_test(NAME filter.blur.identity ...)
```

`.` 区切りで階層を作っておくと、`ctest -R "^codec\."` のような絞り込みが効く。GoogleTest（第14章）が自動生成する名前も `Suite.Case` の形なので、規約を揃えておくとよい。

### 実行する

```
cmake --build --preset x64-debug
cd out\build\x64-debug
ctest
```

**マルチ構成ジェネレータでは `-C` が必須**だ。

```
ctest -C Debug
```

これを忘れると、こうなる。

```
Test project C:/work/pixkit/out/build/x64-vs
No tests were found!!!
```

第2章7節・第12章1節で繰り返した「構成をいつ決めるか」の問題が、テストにも現れる。単一構成ジェネレータ（Ninja）では `-C` は不要だ。

## 13.3　テストプロパティ

登録したテストには、`set_tests_properties` で性質を付与できる。

```cmake
add_test(NAME cli.version COMMAND $<TARGET_FILE:pixcli> --version)

set_tests_properties(cli.version PROPERTIES
    PASS_REGULAR_EXPRESSION "pixcli [0-9]+\\.[0-9]+\\.[0-9]+"
    LABELS  "cli;smoke"
    TIMEOUT 10
)
```

### よく使うプロパティ

| プロパティ | 意味 |
| --- | --- |
| `LABELS` | 分類ラベル（セミコロン区切り）。`ctest -L` で絞れる |
| `TIMEOUT` | 秒数。超えたら失敗。**無限ループの保険として必ず付ける** |
| `WILL_FAIL` | 成功・失敗を反転する |
| `PASS_REGULAR_EXPRESSION` | 出力がこの正規表現にマッチしたら成功 |
| `FAIL_REGULAR_EXPRESSION` | マッチしたら失敗 |
| `SKIP_RETURN_CODE` | この終了コードなら「スキップ」扱い |
| `WORKING_DIRECTORY` | 実行時のカレントディレクトリ |
| `ENVIRONMENT` | 追加の環境変数（`KEY=VALUE` のリスト） |
| `DEPENDS` | 先に実行すべきテスト |
| `RESOURCE_LOCK` | 排他制御（同じ資源を使うテストを同時に走らせない） |
| `FIXTURES_SETUP` / `FIXTURES_REQUIRED` | 前準備・後始末のテストを結びつける |
| `DISABLED` | 一時的に無効化する |

### `PASS_REGULAR_EXPRESSION` の重要な副作用

**このプロパティを設定すると、終了コードは無視される。**

```cmake
add_test(NAME cli.bad_option COMMAND $<TARGET_FILE:pixcli> --bad)
set_tests_properties(cli.bad_option PROPERTIES
    PASS_REGULAR_EXPRESSION "bad option"
)
```

`pixcli --bad` が終了コード 2 を返しても、**出力に "bad option" が含まれていればテストは成功する。** 「エラーメッセージが正しく出ること」を検証したいときには、これが望ましい挙動だ。

逆に「終了コードも出力も両方見たい」場合は、`WILL_FAIL` と組み合わせるか、テストを2つに分ける。

### `TIMEOUT` は必ず付ける

CI上でテストが無限ループに陥ると、ジョブがタイムアウトするまで（30分〜数時間）マシンを占有し続ける。全体のタイムアウトは次のように設定できる。

```cmake
set(CTEST_TEST_TIMEOUT 60)
```

あるいはコマンドラインで指定する。

```
ctest --timeout 60
```

### 環境変数と作業ディレクトリ

```cmake
set_tests_properties(codec.ppm.roundtrip PROPERTIES
    WORKING_DIRECTORY "${CMAKE_CURRENT_BINARY_DIR}"
    ENVIRONMENT "PIXKIT_LOG_LEVEL=debug;PIXKIT_DATA_DIR=${CMAKE_CURRENT_SOURCE_DIR}/data"
)
```

`ENVIRONMENT` はセミコロン区切りのリストだ（第5章5節）。値の中にセミコロンを含めたい場合はエスケープが要る。

`WORKING_DIRECTORY` の既定値は**そのテストを登録した `CMakeLists.txt` に対応するビルドディレクトリ**だ。テストデータを相対パスで開くコードは、ここに強く依存する。第15章3節でこの問題を正面から扱う。

### `ENVIRONMENT_MODIFICATION`（CMake 3.22以降）

DLLの探索パスを足すような場面では、`PATH` を「置き換える」のではなく「追記する」必要がある。

```cmake
set_tests_properties(codec.ppm.roundtrip PROPERTIES
    ENVIRONMENT_MODIFICATION "PATH=path_list_prepend:$<TARGET_FILE_DIR:pixkit-filter>"
)
```

第14章6節で、DLLを使うテストの実行時パス問題を解決するときに使う。

## 13.4　`ctest` のオプション

### 一覧と絞り込み

```
ctest -N                      # 実行せず一覧表示
ctest -R "^cli\."             # 名前が正規表現にマッチするものだけ
ctest -E "slow"               # 名前がマッチするものを除外
ctest -L smoke                # ラベルで絞る
ctest -LE slow                # ラベルで除外
```

`-R` / `-E` は**正規表現**であって、ワイルドカードではない。`ctest -R cli*` は期待どおりに動かない（`cl` に `i` が0回以上、という意味になる）。

### 出力

```
ctest --output-on-failure     # 失敗したテストの出力を表示する
ctest -V                      # 常に詳細出力
ctest -VV                     # さらに詳細
ctest --progress              # 進捗を1行で更新表示（CMake 3.22以降）
```

**`--output-on-failure` は事実上必須**だ。これがないと、失敗しても「Failed」としか出ず、何が起きたのか分からない。第4章で `testPresets` に書いておいたのはこのためだ。

```json
"testPresets": [
  {
    "name": "x64-debug",
    "configurePreset": "x64-debug",
    "output": { "outputOnFailure": true },
    "execution": { "noTestsAction": "error" }
  }
]
```

### 並列実行

```
ctest -j 8                    # 8並列
ctest --parallel              # CPU数に合わせる
```

テストが互いに干渉する（同じファイルを読み書きする、同じポートを使う）場合は、`RESOURCE_LOCK` で排他制御する。

```cmake
set_tests_properties(test_a test_b PROPERTIES RESOURCE_LOCK "temp_file")
```

### 失敗したテストだけ再実行

```
ctest --rerun-failed
```

前回の結果を覚えているので、修正したあとの確認が速い。

### その他

```
ctest --repeat until-fail:10  # 10回繰り返す（不安定なテストの発見）
ctest --stop-on-failure       # 最初の失敗で止める
ctest --test-dir out/build/x64-debug   # ディレクトリを指定（CMake 3.20以降）
```

`--repeat until-fail` は、**たまに落ちるテスト**を炙り出すのに有効だ。

## 13.5　プリセットとVisual Studio

### `testPresets` を使う

第4章で用意したプリセットを使う。

```
ctest --preset x64-debug
```

ビルドディレクトリも出力オプションも書かなくてよい。**`ctest --test-dir out/build/x64-debug --output-on-failure` を毎回打つのと同じこと**が、これで済む。

### ワークフローで一括実行

```
cmake --workflow --preset x64-debug
```

構成 → ビルド → テストが1コマンドで走る。第4章のハンズオン手順6では、テストが0件でエラーになった。**この章でテストを追加すれば、初めて通るようになる。**

### Visual Studio のテストエクスプローラ

VSで**テスト → テストエクスプローラー**を開くと、CTestに登録されたテストが一覧表示される。実行・デバッグもできる。

| VSの操作 | 相当するコマンド |
| --- | --- |
| テスト → CTestの実行 | `ctest` |
| テスト → テストプリセットの実行 | `ctest --preset <name>` |
| テストエクスプローラーで個別実行 | `ctest -R "^<name>$"` |

テストが表示されない場合、まず確認するのは次の3つだ。

1. 構成が成功しているか（出力ウィンドウのCMake）
2. `include(CTest)` または `enable_testing()` がトップレベルにあるか
3. `ctest -N` をコマンドラインで実行して、そちらでは見えるか

3で見えてVSで見えないなら、IDE統合の問題だ。第3章6節の切り分け手順と同じ考え方である。

## ハンズオン：`pixcli` の動作をCTestで検証する

`pixkit` にはまだアサーションを書く手段がない。それでも**CLIツールの振る舞いは検証できる。**

### 手順1：`pixcli` に検証しやすい振る舞いを持たせる

`apps/pixcli/src/main.cpp` を書き換える。

```cpp
#include <pixkit/codec/ppm.hpp>
#include <pixkit/core/version.hpp>
#include <pixkit/filter/filters.hpp>

#include <print>
#include <string_view>

namespace {

pixkit::Image make_gradient(int w, int h)
{
    pixkit::Image img(w, h);
    for (int y = 0; y < h; ++y) {
        for (int x = 0; x < w; ++x) {
            img[x, y] = pixkit::Rgb8{
                static_cast<std::uint8_t>(x * 255 / (w - 1)),
                static_cast<std::uint8_t>(y * 255 / (h - 1)),
                128 };
        }
    }
    return img;
}

int usage()
{
    std::println(stderr, "usage: pixcli <command>");
    std::println(stderr, "  --version          バージョンを表示");
    std::println(stderr, "  --gen <out.ppm>    グラデーション画像を生成");
    std::println(stderr, "  --gray <in> <out>  グレースケール化");
    return 1;
}

}  // namespace

int main(int argc, char** argv)
{
    if (argc < 2) return usage();

    const std::string_view cmd = argv[1];

    if (cmd == "--version") {
        std::println("pixkit {}", pixkit::version_string);
        return 0;
    }

    if (cmd == "--gen" && argc == 3) {
        const auto img = make_gradient(64, 32);
        if (auto r = pixkit::codec::save_ppm(argv[2], img); !r) {
            std::println(stderr, "error: {}", pixkit::codec::to_string(r.error()));
            return 2;
        }
        std::println("wrote {}x{}", img.width(), img.height());
        return 0;
    }

    if (cmd == "--gray" && argc == 4) {
        auto loaded = pixkit::codec::load_ppm(argv[2]);
        if (!loaded) {
            std::println(stderr, "error: {}", pixkit::codec::to_string(loaded.error()));
            return 2;
        }
        pixkit::filter::grayscale(loaded->view());
        if (auto r = pixkit::codec::save_ppm(argv[3], *loaded); !r) {
            std::println(stderr, "error: {}", pixkit::codec::to_string(r.error()));
            return 2;
        }
        std::println("wrote {}x{}", loaded->width(), loaded->height());
        return 0;
    }

    return usage();
}
```

終了コードの規約を決めた。

| 終了コード | 意味 |
| --- | --- |
| 0 | 成功 |
| 1 | 使い方が間違っている |
| 2 | 処理に失敗した（ファイルがない等） |

**テストしやすさは設計で決まる。** 終了コードを分けておくと、外から振る舞いを検証できるようになる。

### 手順2：テストを登録する

`tests/CMakeLists.txt` を書き換える（第8章ではプレースホルダだった）。

```cmake
# ---- CLIの振る舞いテスト（テストフレームワーク不要）--------------------

add_test(NAME cli.version COMMAND $<TARGET_FILE:pixcli> --version)
set_tests_properties(cli.version PROPERTIES
    PASS_REGULAR_EXPRESSION "pixkit [0-9]+\\.[0-9]+\\.[0-9]+"
    LABELS  "cli;smoke"
    TIMEOUT 10
)

add_test(NAME cli.no_args COMMAND $<TARGET_FILE:pixcli>)
set_tests_properties(cli.no_args PROPERTIES
    WILL_FAIL TRUE
    LABELS    "cli"
    TIMEOUT   10
)

add_test(NAME cli.unknown_command COMMAND $<TARGET_FILE:pixcli> --nonexistent)
set_tests_properties(cli.unknown_command PROPERTIES
    PASS_REGULAR_EXPRESSION "usage: pixcli"
    LABELS  "cli"
    TIMEOUT 10
)

add_test(NAME cli.gen COMMAND $<TARGET_FILE:pixcli> --gen gen_out.ppm)
set_tests_properties(cli.gen PROPERTIES
    PASS_REGULAR_EXPRESSION "wrote 64x32"
    LABELS            "cli"
    TIMEOUT           30
    WORKING_DIRECTORY "${CMAKE_CURRENT_BINARY_DIR}"
    FIXTURES_SETUP    gen_image
)

add_test(NAME cli.gray COMMAND $<TARGET_FILE:pixcli> --gray gen_out.ppm gray_out.ppm)
set_tests_properties(cli.gray PROPERTIES
    PASS_REGULAR_EXPRESSION "wrote 64x32"
    LABELS            "cli"
    TIMEOUT           30
    WORKING_DIRECTORY "${CMAKE_CURRENT_BINARY_DIR}"
    FIXTURES_REQUIRED gen_image
)

add_test(NAME cli.gray_missing_input
         COMMAND $<TARGET_FILE:pixcli> --gray no_such_file.ppm out.ppm)
set_tests_properties(cli.gray_missing_input PROPERTIES
    PASS_REGULAR_EXPRESSION "error: file not found"
    LABELS            "cli"
    TIMEOUT           10
    WORKING_DIRECTORY "${CMAKE_CURRENT_BINARY_DIR}"
)
```

**`FIXTURES_SETUP` / `FIXTURES_REQUIRED` に注目してほしい。** `cli.gray` は `cli.gen` が作ったファイルを読む。この依存関係を宣言しておくと、

- `ctest -R cli.gray` と指定しても、`cli.gen` が自動的に先に実行される
- 並列実行（`-j`）でも順序が守られる

`DEPENDS` プロパティでも順序は指定できるが、`FIXTURES_*` のほうが「絞り込んで実行したときも前提が満たされる」点で優れている。

### 手順7：終了コードが無視されることを確認する

13.3節で述べた `PASS_REGULAR_EXPRESSION` の副作用を確かめる。

`cli.gray_missing_input` は、`pixcli` が**終了コード 2 を返す**ケースだ。それでもテストは成功している。出力に "error: file not found" が含まれているからだ。

試しに、正規表現を外してみる。

```cmake
set_tests_properties(cli.gray_missing_input PROPERTIES
    # PASS_REGULAR_EXPRESSION を削除
    LABELS "cli"
)
```

## この章のまとめ

- **CTestはテストランナー**であり、テストフレームワークではない。「実行して終了コード0を返すコマンド」なら何でも登録できる
- `include(CTest)` は `enable_testing()` に加えて **`BUILD_TESTING` オプション**とCDash連携を追加する。トップレベルでのみ呼ぶ
- `add_test(NAME ... COMMAND $<TARGET_FILE:target> ...)` で登録する。テスト名は `.` 区切りで階層化しておくと絞り込みやすい
- **マルチ構成ジェネレータでは `ctest -C Debug` が必須。** 忘れると "No tests were found!!!"
- プロパティで振る舞いを調整する。**`TIMEOUT` は必ず付ける。** `LABELS` で分類し、`FIXTURES_SETUP` / `FIXTURES_REQUIRED` で前提関係を宣言する
- **`PASS_REGULAR_EXPRESSION` を設定すると終了コードは無視される。** エラーメッセージの検証に向く
- `ctest -N` で一覧、`-R` / `-L` で絞り込み（`-R` は正規表現）、`-j` で並列、`-V` で詳細、`--rerun-failed` で再実行、`--repeat until-fail:N` で不安定なテストの発見
- **`--output-on-failure` は必須。** `testPresets`（第4章）に書いておけば毎回付けなくて済む

次の第14章では、いよいよGoogleTestを導入する。CTestが「実行と集計」を担い、GoogleTestが「アサーションとテストケース」を担う、という役割分担が見えてくるはずだ。`gtest_discover_tests` によって、GoogleTestの1つ1つのテストケースがCTestの個別のテストとして登録される仕組みも扱う。
