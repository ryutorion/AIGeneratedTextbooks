# 第8章　プロジェクトの骨格をつくる

## この章のゴール

- 実務で通用するディレクトリレイアウトを設計する
- `add_subdirectory` とスコープの関係を理解する
- **単体でも、他プロジェクトの一部としても使えるプロジェクト**の書き方を身につける
- `project(VERSION ...)` とバージョン変数を、コードから参照できるようにする
- `option()` と `BUILD_TESTING` で機能スイッチを設計する
- 出力先を1か所にまとめる
- `file(GLOB)` を使わない理由を理解する

この章の成果物が、第9章以降で育てていく `pixkit` の土台になる。**ここで作ったものは以降ずっと使い続ける。**

## 8.1　ディレクトリレイアウト

### 本書で使う構成

```
pixkit/
├── CMakeLists.txt              ← トップレベル
├── CMakePresets.json           ← 第4章
├── .gitignore
├── README.md
├── LICENSE
│
├── cmake/                      ← CMakeのヘルパー
│   ├── PixkitOptions.cmake     ← 第7章の共通設定
│   └── pixkit-config.cmake.in  ← 第22章で作る
│
├── libs/                       ← ライブラリ本体
│   ├── CMakeLists.txt
│   ├── core/                   ← ヘッダーオンリー（第10章）
│   │   ├── CMakeLists.txt
│   │   └── include/pixkit/core/
│   ├── codec/                  ← 静的ライブラリ（第9章）
│   │   ├── CMakeLists.txt
│   │   ├── include/pixkit/codec/
│   │   └── src/
│   └── filter/                 ← 動的ライブラリ（第11章）
│       ├── CMakeLists.txt
│       ├── include/pixkit/filter/
│       └── src/
│
├── apps/                       ← 実行ファイル
│   ├── CMakeLists.txt
│   └── pixcli/
│       ├── CMakeLists.txt
│       └── src/main.cpp
│
├── tests/                      ← GoogleTest（第13〜15章）
│   └── CMakeLists.txt
│
├── bench/                      ← Google Benchmark（第16章）
│   └── CMakeLists.txt
│
└── ports/                      ← vcpkgポート（第23章）
    └── pixkit/
```

### 設計の意図

**1. ライブラリごとに `include/` を持つ**

```
libs/codec/include/pixkit/codec/ppm.hpp
libs/codec/src/ppm.cpp
libs/codec/src/internal_buffer.hpp     ← 内部ヘッダ
```

トップレベルに `include/` を1つ置く流儀もあるが、本書はライブラリごとに分ける。理由は第6章の使用要件が素直に書けるからだ。

```cmake
target_include_directories(pixkit-codec
    PUBLIC  $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
    PRIVATE ${CMAKE_CURRENT_SOURCE_DIR}/src
)
```

「公開ヘッダは `include/` 、内部ヘッダは `src/`」という境界が、ディレクトリ構造とCMakeの記述の両方で一致する。

**2. `include/` の下にもう1段、名前空間ディレクトリを掘る**

```
libs/codec/include/pixkit/codec/ppm.hpp
                   ^^^^^^ ^^^^^
```

こうすることで、利用側のインクルードが次の形になる。

```cpp
#include <pixkit/codec/ppm.hpp>
```

インクルードパスに追加されるのは `libs/codec/include` までなので、他人のプロジェクトに `ppm.hpp` があっても衝突しない。**ライブラリを配布する場合、この階層は必須だと考えてよい。**

**3. `libs/` と `apps/` を分ける**

ライブラリと実行ファイルを混ぜない。第21章でインストール対象を決めるとき、「`libs/` の下はインストールする、`apps/` は場合による」と整理しやすくなる。

### 使わないほうがよい構成

```
pixkit/
├── src/            ← すべてのソースが平置き
├── include/        ← すべてのヘッダが平置き
└── CMakeLists.txt  ← 1つの巨大なファイル
```

小さいうちは問題ないが、ライブラリが3つになった時点で「どのヘッダがどのライブラリのものか」が分からなくなる。最初から分けておくコストは小さい。

## 8.2　`add_subdirectory` とスコープ

### 基本

```cmake
# トップレベルの CMakeLists.txt
add_subdirectory(libs)
add_subdirectory(apps)
```

`add_subdirectory(libs)` は `libs/CMakeLists.txt` を読み込んで実行する。処理はそこに移り、終わったら戻ってくる。

```cmake
# libs/CMakeLists.txt
add_subdirectory(core)
add_subdirectory(codec)
add_subdirectory(filter)
```

入れ子にできる。

### 変数のスコープ

**`add_subdirectory` は新しい変数スコープを作る。** 第5章3節の関数と同じだ。

```cmake
# トップレベル
set(MY_VAR "top")
add_subdirectory(libs)
message(STATUS "after: ${MY_VAR}")     # top（サブディレクトリでの変更は届かない）
```

```cmake
# libs/CMakeLists.txt
message(STATUS "in libs: ${MY_VAR}")   # top（親の変数は見える）
set(MY_VAR "libs")                     # ここでの変更は親に影響しない
```

**親→子は見えるが、子→親は見えない。** これは意図的な設計で、サブディレクトリが親を汚染しないようにするためだ。

子から親に値を渡したいときは `set(... PARENT_SCOPE)` を使うが、実務ではほとんど必要ない。**必要になったら、それはターゲットで表現すべき情報である可能性が高い。**

### ターゲットはグローバル

一方、**ターゲットはスコープを持たない。** どこで定義しても、プロジェクト全体から見える。

```cmake
# libs/core/CMakeLists.txt
add_library(pixkit-core INTERFACE)
```

```cmake
# apps/pixcli/CMakeLists.txt
target_link_libraries(pixcli PRIVATE pixkit-core)   # 別ディレクトリだが参照できる
```

ただし**順序には依存する**。`target_link_libraries` でリンクするだけなら順序は問わない（未定義のターゲット名も後で解決される）が、`get_target_property` などで問い合わせる場合は定義済みでなければならない。トップレベルで `add_subdirectory(libs)` を `add_subdirectory(apps)` より先に書くのは、この理由による。

### ディレクトリ関連の変数

混同しやすい変数を整理しておく。

| 変数 | 指すもの |
| --- | --- |
| `CMAKE_SOURCE_DIR` | **一番上の**ソースディレクトリ |
| `CMAKE_BINARY_DIR` | **一番上の**ビルドディレクトリ |
| `PROJECT_SOURCE_DIR` | 直近の `project()` を呼んだディレクトリ |
| `PROJECT_BINARY_DIR` | 同上のビルド側 |
| `CMAKE_CURRENT_SOURCE_DIR` | **いま処理中の** `CMakeLists.txt` のディレクトリ |
| `CMAKE_CURRENT_BINARY_DIR` | 同上のビルド側 |
| `<project>_SOURCE_DIR` | `project(pixkit ...)` なら `pixkit_SOURCE_DIR` |

**`CMAKE_SOURCE_DIR` を使ってはいけない。** これは「一番上」を指すので、あなたのプロジェクトが他人のプロジェクトに `add_subdirectory` や `FetchContent` で取り込まれた瞬間、**他人のディレクトリを指すようになる**。

```cmake
# 悪い例
target_include_directories(pixkit-codec PUBLIC ${CMAKE_SOURCE_DIR}/libs/codec/include)

# 良い例
target_include_directories(pixkit-codec PUBLIC ${CMAKE_CURRENT_SOURCE_DIR}/include)
```

**原則として `CMAKE_CURRENT_SOURCE_DIR` を使う。** プロジェクト全体を指したいときは `PROJECT_SOURCE_DIR` か `pixkit_SOURCE_DIR` を使う。

## 8.3　単体でも、部品としても使えるようにする

あなたのライブラリは、2通りの使われ方をする。

| 使われ方 | 状況 |
| --- | --- |
| **トップレベル** | 自分で開発している。テストもベンチマークも動かしたい |
| **サブプロジェクト** | 他人が `FetchContent` や `add_subdirectory` で取り込んでいる。テストは不要 |

後者で、あなたのテストやベンチマークが一緒にビルドされたら迷惑だ。ビルド時間が延び、CTestの一覧が汚染される。

### `PROJECT_IS_TOP_LEVEL`

CMake 3.21で追加された変数で、`project()` を呼ぶと自動的に設定される。

```cmake
cmake_minimum_required(VERSION 3.28)
project(pixkit VERSION 0.1.0 LANGUAGES CXX)

# 自分がトップレベルのときだけ、既定でONにする
option(PIXKIT_BUILD_TESTS      "テストをビルドする"       ${PROJECT_IS_TOP_LEVEL})
option(PIXKIT_BUILD_BENCHMARKS "ベンチマークをビルドする" ${PROJECT_IS_TOP_LEVEL})
option(PIXKIT_BUILD_APPS       "CLIツールをビルドする"    ${PROJECT_IS_TOP_LEVEL})
```

これで、

- `pixkit` を直接ビルド → テストもベンチもCLIも作られる
- 他人が取り込む → ライブラリだけが作られる
- 他人が明示的に `-DPIXKIT_BUILD_TESTS=ON` → テストも作られる

という振る舞いになる。**ライブラリを配布するなら、この配慮はほぼ必須**だと考えてよい。

### サブプロジェクトのときにやってはいけないこと

トップレベルでのみ行うべき設定がいくつかある。

```cmake
if(PROJECT_IS_TOP_LEVEL)
    # 出力ディレクトリの統一（8.6節）：取り込まれた側が親の出力先を変えてはいけない
    set(CMAKE_RUNTIME_OUTPUT_DIRECTORY "${CMAKE_BINARY_DIR}/bin")

    # CTestの有効化（第13章）
    include(CTest)

    # VSのソリューションフォルダ分け
    set_property(GLOBAL PROPERTY USE_FOLDERS ON)
endif()
```

これらはすべて「プロジェクト全体に影響する設定」なので、部品として取り込まれた側が勝手に変えると親の設定を壊す。

## 8.4　バージョンを一元管理する

### `project()` でバージョンを宣言する

```cmake
project(pixkit
    VERSION      0.1.0
    DESCRIPTION  "小さな画像処理ライブラリ群"
    HOMEPAGE_URL "https://github.com/example/pixkit"
    LANGUAGES    CXX
)
```

これで次の変数が自動的に設定される。

| 変数 | 値 |
| --- | --- |
| `pixkit_VERSION` | `0.1.0` |
| `pixkit_VERSION_MAJOR` | `0` |
| `pixkit_VERSION_MINOR` | `1` |
| `pixkit_VERSION_PATCH` | `0` |
| `PROJECT_VERSION` | `0.1.0`（直近の `project()` のもの） |

`PROJECT_VERSION` は「直近の `project()`」を指すので、サブプロジェクトを持つ場合は `pixkit_VERSION` のように**プロジェクト名を付けた変数を使う**ほうが安全だ。

このバージョンは以降の章で繰り返し使う。

- 第11章：DLLの `VERSION` / `SOVERSION`
- 第22章：`find_package(pixkit 0.1 REQUIRED)` のバージョン照合
- 第23章：vcpkgポートのバージョン

### バージョンをC++コードから見えるようにする

CMake側のバージョンと、コード内の `PIXKIT_VERSION` 定数が食い違う、というのはよくある事故だ。**片方から生成する。**

`libs/core/include/pixkit/core/version.hpp.in` を作る。

```cpp
#pragma once

#define PIXKIT_VERSION_MAJOR @pixkit_VERSION_MAJOR@
#define PIXKIT_VERSION_MINOR @pixkit_VERSION_MINOR@
#define PIXKIT_VERSION_PATCH @pixkit_VERSION_PATCH@
#define PIXKIT_VERSION_STRING "@pixkit_VERSION@"

namespace pixkit {
inline constexpr int  version_major = PIXKIT_VERSION_MAJOR;
inline constexpr int  version_minor = PIXKIT_VERSION_MINOR;
inline constexpr int  version_patch = PIXKIT_VERSION_PATCH;
inline constexpr auto version_string = PIXKIT_VERSION_STRING;
}
```

`@変数名@` の部分が、CMakeの変数で置換される。

```cmake
configure_file(
    "${CMAKE_CURRENT_SOURCE_DIR}/include/pixkit/core/version.hpp.in"
    "${CMAKE_CURRENT_BINARY_DIR}/include/pixkit/core/version.hpp"
    @ONLY
)
```

| 引数 | 意味 |
| --- | --- |
| 第1引数 | 入力テンプレート |
| 第2引数 | 出力先。**ソースツリーではなくビルドツリーに書く** |
| `@ONLY` | `@VAR@` だけを置換し、`${VAR}` は置換しない |

`@ONLY` を付ける理由は、C++コードには `${...}` に似た記述が出てくることがあるからだ。付けておくのが安全である。

**出力先をビルドツリーにする**のは重要だ。ソースツリーに生成すると、`.gitignore` の管理が面倒になるうえ、複数の構成でビルドしたときに上書きし合う。

生成したヘッダは、ビルドツリー側のインクルードパスを追加すれば見つかる。

```cmake
target_include_directories(pixkit-core INTERFACE
    $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
    $<BUILD_INTERFACE:${CMAKE_CURRENT_BINARY_DIR}/include>
)
```

`$<BUILD_INTERFACE:...>` は「ビルドツリーで使うときだけ有効」という意味のジェネレータ式だ。インストール後は別のパスになるので、第21章で `$<INSTALL_INTERFACE:...>` を足すことになる。**いまは「そういうものが要る」とだけ理解しておけばよい。**

> **`configure_file` はソースの変更を追跡する**
> `version.hpp.in` を編集すると、次のビルド時に自動的に再構成が走る。CMakeが依存関係として登録してくれるからだ。手動で構成し直す必要はない。

## 8.5　機能スイッチを設計する

### `option()`

```cmake
option(PIXKIT_BUILD_TESTS "テストをビルドする" ON)
```

`option()` は「BOOL型のキャッシュ変数を作る」ためのコマンドで、次と実質同じだ。

```cmake
set(PIXKIT_BUILD_TESTS ON CACHE BOOL "テストをビルドする")
```

ユーザーは `-DPIXKIT_BUILD_TESTS=OFF` で上書きできる。第4章のプリセットに書いておくこともできる。

```json
"cacheVariables": {
    "PIXKIT_BUILD_TESTS": "ON",
    "PIXKIT_WARNINGS_AS_ERRORS": "OFF"
}
```

### 命名規則

**必ずプロジェクト名を接頭辞に付ける。**

```cmake
option(BUILD_TESTS "..." ON)           # 悪い。他プロジェクトと衝突する
option(PIXKIT_BUILD_TESTS "..." ON)    # 良い
```

`FetchContent` で複数のライブラリを取り込むと、接頭辞のないオプションは容易に衝突する。「GoogleTestの `BUILD_TESTS` を切ったつもりが、自分のテストまで消えた」といった事故が起きる。

### `BUILD_TESTING` だけは例外

CTestの慣習として、`BUILD_TESTING` という共通のオプションがある。

```cmake
include(CTest)      # BUILD_TESTING オプションを定義し、既定ON。enable_testing() も呼ぶ
```

多くのプロジェクトがこれに従っているので、`-DBUILD_TESTING=OFF` で全部のテストを切れる。本書では両方を見る形にする。

```cmake
if(PIXKIT_BUILD_TESTS AND BUILD_TESTING)
    add_subdirectory(tests)
endif()
```

### オプションの状態を表示する

構成のたびに、いま何が有効なのかを表示しておくと親切だ。

```cmake
if(PROJECT_IS_TOP_LEVEL)
    message(STATUS "")
    message(STATUS "pixkit ${pixkit_VERSION} の構成:")
    message(STATUS "  ビルド構成      : ${CMAKE_BUILD_TYPE}")
    message(STATUS "  ジェネレータ    : ${CMAKE_GENERATOR}")
    message(STATUS "  テスト          : ${PIXKIT_BUILD_TESTS}")
    message(STATUS "  ベンチマーク    : ${PIXKIT_BUILD_BENCHMARKS}")
    message(STATUS "  CLIツール       : ${PIXKIT_BUILD_APPS}")
    message(STATUS "  共有ライブラリ  : ${BUILD_SHARED_LIBS}")
    message(STATUS "  警告をエラー化  : ${PIXKIT_WARNINGS_AS_ERRORS}")
    message(STATUS "")
endif()
```

「テストが実行されないと思ったらオプションがOFFだった」を防げる。地味だが効果は大きい。

> **`option()` と通常変数の関係**
> `option()` を呼ぶ前に同名の**通常変数**が設定されていると、`option()` はキャッシュ変数を作らず、その通常変数が使われる（ポリシー `CMP0077`、CMake 3.13以降）。これは `FetchContent` で取り込んだライブラリのオプションを、親から制御するために使われる。
> ```cmake
> set(BENCHMARK_ENABLE_TESTING OFF)   # 通常変数として先に設定
> FetchContent_MakeAvailable(benchmark)
> ```
> 第14章・第16章で実際にこの書き方を使う。

## 8.6　出力ディレクトリを統一する

### 問題

第6章のハンズオンで見たとおり、既定では成果物がサブディレクトリに散らばる。

```
build/libs/core/...
build/libs/codec/pixkit-codec.lib
build/libs/filter/pixkit-filter.dll
build/apps/pixcli/pixcli.exe
```

これは実用上とても困る。**`pixcli.exe` は `pixkit-filter.dll` を必要とするのに、別のディレクトリにある。** 実行しようとすると「DLLが見つかりません」で落ちる。

### 解決

出力先を1か所に集める。

```cmake
if(PROJECT_IS_TOP_LEVEL)
    set(CMAKE_RUNTIME_OUTPUT_DIRECTORY "${CMAKE_BINARY_DIR}/bin")   # .exe と .dll
    set(CMAKE_LIBRARY_OUTPUT_DIRECTORY "${CMAKE_BINARY_DIR}/lib")   # Unixの .so
    set(CMAKE_ARCHIVE_OUTPUT_DIRECTORY "${CMAKE_BINARY_DIR}/lib")   # .lib（静的・インポート）
endif()
```

| 変数 | Windowsで置かれるもの |
| --- | --- |
| `CMAKE_RUNTIME_OUTPUT_DIRECTORY` | `.exe`、**`.dll`** |
| `CMAKE_ARCHIVE_OUTPUT_DIRECTORY` | `.lib`（静的ライブラリ、DLLのインポートライブラリ） |
| `CMAKE_LIBRARY_OUTPUT_DIRECTORY` | Windowsではほぼ使われない（Unixの `.so` 用） |

**Windowsで重要なのは、DLLが `RUNTIME` 扱いになること**だ。`.exe` と同じディレクトリに出るので、実行時に見つかる。これで第11章のDLL問題の半分が解決する。

### マルチ構成ジェネレータでの注意

Visual Studio ジェネレータでは、指定したパスの下にさらに構成名のサブディレクトリが付く。

```
build/bin/Debug/pixcli.exe
build/bin/Release/pixcli.exe
```

これは正しい挙動だ（DebugとReleaseの成果物が混ざらない）。構成名を含めたくない場合は、次のように構成ごとの変数を指定するか、

```cmake
set(CMAKE_RUNTIME_OUTPUT_DIRECTORY_DEBUG   "${CMAKE_BINARY_DIR}/bin")
set(CMAKE_RUNTIME_OUTPUT_DIRECTORY_RELEASE "${CMAKE_BINARY_DIR}/bin")
```

ジェネレータ式を使う。

```cmake
set(CMAKE_RUNTIME_OUTPUT_DIRECTORY "${CMAKE_BINARY_DIR}/bin/$<CONFIG>")
```

**本書では既定の挙動（構成名のサブディレクトリが付く）をそのまま使う。** 混ざらないほうが安全だからだ。

### VSのソリューションを整理する

ターゲットが増えると、Visual Studio のソリューションエクスプローラが平坦で見づらくなる。`FOLDER` プロパティで整理できる。

```cmake
set_property(GLOBAL PROPERTY USE_FOLDERS ON)

set_target_properties(pixkit-core pixkit-codec pixkit-filter PROPERTIES FOLDER "libs")
set_target_properties(pixcli PROPERTIES FOLDER "apps")
```

`USE_FOLDERS` を `ON` にしないと `FOLDER` が無視される。CMake 3.26以降は既定でONだが、明示しておくと分かりやすい。

## 8.7　`file(GLOB)` を使わない

### よくある書き方

```cmake
file(GLOB SOURCES "src/*.cpp")
add_library(pixkit-codec STATIC ${SOURCES})
```

ソースを追加するたびに `CMakeLists.txt` を編集しなくて済む。魅力的に見える。**しかし使ってはいけない。**

### 理由1：新しいファイルが検出されない

`file(GLOB)` は**構成時**に1回だけ実行される。新しく `src/bmp.cpp` を追加しても、次の構成が走るまでCMakeはそれを知らない。しかも `CMakeLists.txt` は変更されていないので、**再構成のきっかけがない**。

結果として、「ファイルを追加したのにビルドされない」「他の人がpullしたらリンクエラー」という現象が起きる。原因が分かりにくく、`build` を消して作り直すまで解決しない。

### 理由2：`CONFIGURE_DEPENDS` も完全ではない

CMake 3.12で対策が入った。

```cmake
file(GLOB SOURCES CONFIGURE_DEPENDS "src/*.cpp")
```

これでビルドのたびにディレクトリをチェックし、変化があれば再構成するようになる。ただし、

- **毎回のビルドでディレクトリスキャンのコストがかかる**
- CMake公式ドキュメントも「すべてのジェネレータで信頼できるとは限らない」と述べている
- 結局、意図しないファイル（バックアップファイル、エディタの一時ファイル）を拾う問題は残る

### 理由3：明示のほうが情報量が多い

```cmake
add_library(pixkit-codec STATIC
    src/ppm.cpp
    src/bmp.cpp
    src/internal_buffer.hpp     # ヘッダも書いておくとIDEに表示される
)
```

このリストは「このライブラリが何でできているか」のドキュメントでもある。差分を見れば、ファイルの追加・削除がレビューできる。GLOBだと差分に何も現れない。

### 結論

**ソースファイルは明示的に列挙する。** ファイルの追加は数日に1回の作業であり、そのたびに1行書く手間は、上記の問題に比べれば無視できる。

なお、この判断は「ソースファイル」についてのものだ。テストデータのように、ビルドに影響しないファイルの収集には `file(GLOB)` を使ってもよい（第15章）。

## この章のまとめ

- ライブラリごとに `include/` を持ち、その下に `pixkit/<ライブラリ名>/` の階層を掘る。公開ヘッダと内部ヘッダをディレクトリで分離する
- `add_subdirectory` は**新しい変数スコープ**を作る（親→子は見えるが、子→親は見えない）。一方**ターゲットはグローバル**
- **`CMAKE_SOURCE_DIR` を使わない。** 取り込まれたときに他人のディレクトリを指す。`CMAKE_CURRENT_SOURCE_DIR` か `PROJECT_SOURCE_DIR` を使う
- **`PROJECT_IS_TOP_LEVEL`** で「単体ビルド」と「取り込まれたビルド」を分岐する。出力先の変更・`include(CTest)`・テストのビルドは、トップレベルのときだけ行う
- `project(... VERSION ...)` でバージョンを宣言し、`configure_file` で C++ ヘッダを生成する。出力先は**ビルドツリー**にする
- オプションは `option()` で定義し、**必ずプロジェクト名の接頭辞を付ける**。構成サマリを表示すると事故が減る
- 出力先は `CMAKE_RUNTIME_OUTPUT_DIRECTORY` などで1か所にまとめる。**Windowsでは DLL が RUNTIME 扱い**なので、`.exe` と同じ場所に出る
- **`file(GLOB)` でソースを集めない。** 明示的に列挙する

これで第2部は終わりだ。CMake言語（第5章）、ターゲットと使用要件（第6章）、C++23と共通設定（第7章）、プロジェクトの骨格（第8章）が揃った。

第3部からは、いよいよ実際のライブラリを書く。第9章で静的ライブラリ `pixkit::codec`、第10章でヘッダーオンリーの `pixkit::core`、第11章で動的ライブラリ `pixkit::filter` を作り、3種類のライブラリ形態の違いを手を動かして理解していく。
