# 第12章　ビルド構成を作り分ける

## この章のゴール

- 単一構成ジェネレータとマルチ構成ジェネレータの違いを、実務レベルで使い分けられる
- `CMAKE_BUILD_TYPE` と `CMAKE_CONFIGURATION_TYPES` の役割を区別する
- 標準の4構成が実際にどんなフラグを渡しているかを知る
- **`MSVC_RUNTIME_LIBRARY` で `/MD` `/MT` を制御する**
- PDB（デバッグ情報）の生成と配布を理解する
- ジェネレータ式で、構成ごと・ターゲットごとに設定を出し分ける
- リンク時最適化（LTCG）を安全に有効化する

第2章7節で触れた「マルチ構成と単一構成の違い」を、ここで正面から扱う。第3部の締めくくりとして、これまで作った3つのライブラリを Debug と Release で正しく作り分ける。

## 12.1　単一構成ジェネレータとマルチ構成ジェネレータ

### おさらい

| | 単一構成 | マルチ構成 |
| --- | --- | --- |
| 代表例 | Ninja、Makefile | **Visual Studio 18 2026**、Xcode、Ninja Multi-Config |
| 構成を決める時期 | **構成(configure)時** | **ビルド時** |
| 指定方法 | `-DCMAKE_BUILD_TYPE=Debug` | `--build --config Debug` |
| ビルドディレクトリ | 構成ごとに必要 | 1つで足りる |
| 出力パス | `bin/pixcli.exe` | `bin/Debug/pixcli.exe` |
| `CMAKE_BUILD_TYPE` | 有効 | **空** |

第4章で作ったプリセットは、この両方を用意していた。

- `x64-debug` / `x64-release`：Ninja（単一構成）
- `x64-vs`：Visual Studio（マルチ構成）

### 第3の選択肢：Ninja Multi-Config

```
cmake -S . -B build -G "Ninja Multi-Config"
cmake --build build --config Debug
cmake --build build --config Release
```

Ninjaの速度と、マルチ構成の利便性を両立する。1つのビルドディレクトリで Debug と Release が共存し、しかも高速だ。

| | Ninja | Ninja Multi-Config | Visual Studio |
| --- | --- | --- | --- |
| 速度 | ◎ | ◎ | ○ |
| 構成の共存 | × | **○** | ○ |
| `compile_commands.json` | ○ | ○ | **×** |
| `.sln` の生成 | × | × | ○ |

第17章のClang-Tidyには `compile_commands.json` が必要なので、その意味でもNinja系が有利だ。

> **`CMAKE_DEFAULT_BUILD_TYPE`**
> Ninja Multi-Config では、`--config` を省略したときの既定構成を指定できる。
> ```cmake
> set(CMAKE_DEFAULT_BUILD_TYPE "Debug")
> ```

### どれを使うべきか

本書の推奨は「**Ninja（構成ごとに別ディレクトリ）を主に使い、必要なときにVisual Studio ジェネレータを併用する**」だ。第4章のプリセットがそうなっている。

理由は、構成ごとにディレクトリが分かれているほうが、

- どの構成の成果物か迷わない
- 片方を消してもう片方は残す、といった操作が単純
- CIでキャッシュを扱いやすい

からだ。Ninja Multi-Config が悪いわけではないので、好みで選んでよい。

## 12.2　`CMAKE_BUILD_TYPE` と `CMAKE_CONFIGURATION_TYPES`

### 2つの変数

| 変数 | 使うジェネレータ | 意味 |
| --- | --- | --- |
| `CMAKE_BUILD_TYPE` | 単一構成 | いま何をビルドするか |
| `CMAKE_CONFIGURATION_TYPES` | マルチ構成 | どの構成を用意するか（リスト） |

```cmake
# マルチ構成のとき、用意する構成を絞る
set(CMAKE_CONFIGURATION_TYPES "Debug;Release" CACHE STRING "" FORCE)
```

既定では `Debug;Release;MinSizeRel;RelWithDebInfo` の4つが用意される。使わない構成を消すと、Visual Studio のドロップダウンがすっきりする。

### `CMAKE_BUILD_TYPE` が空のときの罠

単一構成ジェネレータで `CMAKE_BUILD_TYPE` を指定しないと、**最適化もデバッグ情報もない**中途半端なビルドになる。

```
cmake -S . -B build -G Ninja        # CMAKE_BUILD_TYPE が空
```

`/O2` も `/Od` も `/Zi` も付かない。「なぜかReleaseより遅く、Debugよりデバッグしにくい」という状態だ。

**プリセット（第4章）で必ず指定する。** それが最も確実な対策である。

保険として、次のように書いておく手もある。

```cmake
if(PROJECT_IS_TOP_LEVEL AND NOT CMAKE_BUILD_TYPE AND NOT CMAKE_CONFIGURATION_TYPES)
    message(STATUS "CMAKE_BUILD_TYPE が未指定です。RelWithDebInfo を使います")
    set(CMAKE_BUILD_TYPE "RelWithDebInfo" CACHE STRING "" FORCE)
endif()
```

`NOT CMAKE_CONFIGURATION_TYPES` の条件が重要だ。これがないと、マルチ構成ジェネレータのときにも `CMAKE_BUILD_TYPE` を設定してしまい、混乱を招く。

### `if(CMAKE_BUILD_TYPE STREQUAL ...)` を書かない

第2章7節・第7章8節で繰り返した話だが、もう一度。

```cmake
# 悪い例：Visual Studio ジェネレータで動かない
if(CMAKE_BUILD_TYPE STREQUAL "Debug")
    target_compile_definitions(app PRIVATE PIXKIT_DEBUG)
endif()

# 良い例
target_compile_definitions(app PRIVATE $<$<CONFIG:Debug>:PIXKIT_DEBUG>)
```

マルチ構成では `CMAKE_BUILD_TYPE` が空なので、前者は**常に偽**になる。しかもエラーにならず静かに無視されるので、気づきにくい。

## 12.3　標準の4構成

### それぞれの位置づけ

| 構成 | MSVCの主なフラグ | 用途 |
| --- | --- | --- |
| `Debug` | `/Od /Ob0 /RTC1 /MDd` | 開発。最適化なし、実行時チェックあり |
| `Release` | `/O2 /Ob2 /DNDEBUG /MD` | 配布。最適化最大、デバッグ情報なし |
| `RelWithDebInfo` | `/O2 /Ob1 /DNDEBUG /MD` + PDB | **性能計測・本番デバッグ** |
| `MinSizeRel` | `/O1 /Ob1 /DNDEBUG /MD` | サイズ優先 |

### `NDEBUG` に注目する

**`Debug` 以外のすべての構成で `NDEBUG` が定義される。** これは標準の `assert()` を無効化するマクロだ。

```cpp
#include <cassert>
assert(index < size);      // Release では消える
```

「Debugでは動くのにReleaseで落ちる」の典型的な原因がこれだ。`assert` の中に副作用のある式を書いてはいけない。

```cpp
assert(do_something());    // Release では do_something() が呼ばれない
```

### `RelWithDebInfo` を常用する

本書のプリセット（第4章）は、`x64-release` に `Release` ではなく `RelWithDebInfo` を割り当てている。理由は、

- **最適化された状態で、クラッシュしたときにスタックが読める**
- 第16章のベンチマークで、プロファイラがシンボルを解決できる
- 実行速度は `Release` とほぼ同じ（`/Ob1` と `/Ob2` の差だけ）

デバッグ情報は別ファイル（PDB）に出るので、配布時に添付しなければ利用者には見えない。**「デバッグ情報を持たないこと」に利点はほとんどない。**

### 独自の構成を追加する

たとえば「最適化ありでアサーションも有効」という構成が欲しいとする。

```cmake
if(PROJECT_IS_TOP_LEVEL)
    # マルチ構成ジェネレータに構成を追加
    if(CMAKE_CONFIGURATION_TYPES)
        list(APPEND CMAKE_CONFIGURATION_TYPES "Profile")
        list(REMOVE_DUPLICATES CMAKE_CONFIGURATION_TYPES)
        set(CMAKE_CONFIGURATION_TYPES "${CMAKE_CONFIGURATION_TYPES}" CACHE STRING "" FORCE)
    endif()

    # フラグを定義する（RelWithDebInfo から NDEBUG を抜いたもの）
    set(CMAKE_CXX_FLAGS_PROFILE        "/O2 /Ob1" CACHE STRING "")
    set(CMAKE_EXE_LINKER_FLAGS_PROFILE "/DEBUG"   CACHE STRING "")
    set(CMAKE_SHARED_LINKER_FLAGS_PROFILE "/DEBUG" CACHE STRING "")
endif()
```

**注意すべき落とし穴が1つある。** 独自構成を追加すると、`find_package` で見つけた外部ライブラリ（インポートターゲット）が「`Profile` 構成のバイナリがない」と言って壊れることがある。対処は `MAP_IMPORTED_CONFIG_*` だ。

```cmake
set(CMAKE_MAP_IMPORTED_CONFIG_PROFILE "RelWithDebInfo;Release;")
```

「`Profile` を要求されたら `RelWithDebInfo` を、なければ `Release` を使え」という指示になる。末尾の空要素は「構成指定なしのものも許す」という意味だ。

独自構成は便利だが、こうした余波がある。**本当に必要になるまでは標準の4構成で済ませる**のが賢明だ。

## 12.4　構成ごとのフラグ

### フラグはどこから来るのか

MSVCに渡るフラグは、大きく3か所から合成される。

```
CMAKE_CXX_FLAGS                 ← 全構成共通
CMAKE_CXX_FLAGS_<CONFIG>        ← 構成ごと（DEBUG / RELEASE / ...）
ターゲットの COMPILE_OPTIONS    ← target_compile_options で追加したもの
```

確認してみる。

```cmake
message(STATUS "共通    : ${CMAKE_CXX_FLAGS}")
message(STATUS "Debug   : ${CMAKE_CXX_FLAGS_DEBUG}")
message(STATUS "Release : ${CMAKE_CXX_FLAGS_RELEASE}")
```

```
-- 共通    : /DWIN32 /D_WINDOWS /EHsc
-- Debug   : /Ob0 /Od /RTC1
-- Release : /O2 /Ob2 /DNDEBUG
```

第7章6節で触れた **CMP0092** のおかげで、`/W3` は入っていない。

### 変数を直接いじらない

```cmake
# 悪い例
set(CMAKE_CXX_FLAGS "${CMAKE_CXX_FLAGS} /W4")
string(REPLACE "/O2" "/Ox" CMAKE_CXX_FLAGS_RELEASE "${CMAKE_CXX_FLAGS_RELEASE}")
```

第6章4節・第7章7節で述べたとおり、これはグローバル設定であり、`FetchContent` で取り込んだ外部ライブラリにも影響する。**ターゲットに対して指定する。**

```cmake
# 良い例
target_compile_options(pixkit_options INTERFACE
    $<$<CONFIG:Release>:/Ox>
)
```

### 構成ごとの定義を足す

```cmake
target_compile_definitions(pixkit_options INTERFACE
    $<$<CONFIG:Debug>:PIXKIT_DEBUG=1>
    $<$<NOT:$<CONFIG:Debug>>:PIXKIT_NDEBUG=1>
)
```

複数構成をまとめて指定することもできる。

```cmake
$<$<CONFIG:Release,RelWithDebInfo,MinSizeRel>:PIXKIT_OPTIMIZED=1>
```

## 12.5　MSVCランタイムライブラリ（`/MD` と `/MT`）

### 4つの選択肢

MSVCには、Cランタイムのリンク方法が4通りある。

| フラグ | 意味 | CMakeでの名前 |
| --- | --- | --- |
| `/MD` | 動的リンク（Release） | `MultiThreadedDLL` |
| `/MDd` | 動的リンク（Debug） | `MultiThreadedDebugDLL` |
| `/MT` | 静的リンク（Release） | `MultiThreaded` |
| `/MTd` | 静的リンク（Debug） | `MultiThreadedDebug` |

| | `/MD`（動的） | `/MT`（静的） |
| --- | --- | --- |
| 再配布 | **VC++再頒布可能パッケージが必要** | 不要 |
| サイズ | 小さい | 大きい |
| DLLとの混在 | **安全** | **危険**（ヒープが別々になる） |
| セキュリティ更新 | ランタイム側の更新で自動的に適用 | 再ビルドが必要 |

**DLLを使うなら `/MD` 一択**だ。`/MT` でビルドしたDLLと実行ファイルを組み合わせると、それぞれが独立したCRTとヒープを持つことになり、第11章5節の問題が最悪の形で発生する。

### CMakeでの制御

```cmake
set_target_properties(pixkit-filter PROPERTIES
    MSVC_RUNTIME_LIBRARY "MultiThreaded$<$<CONFIG:Debug>:Debug>DLL"
)
```

既定値がまさにこれ（Debugなら `/MDd`、それ以外は `/MD`）なので、通常は書く必要がない。プロジェクト全体を `/MT` にしたい場合は次のようにする。

```cmake
if(PROJECT_IS_TOP_LEVEL)
    set(CMAKE_MSVC_RUNTIME_LIBRARY "MultiThreaded$<$<CONFIG:Debug>:Debug>")
endif()
```

ジェネレータ式が使える。構成ごとに分岐する必要があるので、むしろ必須だ。

### ポリシー `CMP0091`

この仕組みはCMake 3.15で導入され、ポリシー `CMP0091` が `NEW` のときだけ有効になる。`cmake_minimum_required(VERSION 3.28)` なら自動的に `NEW` だ。

`OLD` の挙動では、`/MD` は `CMAKE_CXX_FLAGS_<CONFIG>` に直接埋め込まれていた。だから古い記事には、こういう文字列置換が載っている。

```cmake
# 3.15より前のやり方。真似しない
string(REPLACE "/MD" "/MT" CMAKE_CXX_FLAGS_RELEASE "${CMAKE_CXX_FLAGS_RELEASE}")
```

**いまは `MSVC_RUNTIME_LIBRARY` を使う。**

### 揃っていないとどうなるか

`/MD` の実行ファイルと `/MT` のライブラリをリンクすると、警告と大量のリンクエラーが出る。

```
LNK4098: defaultlib 'LIBCMT' が他のライブラリの使用と競合しています
LNK2005: "void * __cdecl operator new(unsigned __int64)" は既に MSVCRT.lib で定義されています
```

第19章でvcpkgのトリプレット（`x64-windows` と `x64-windows-static`）を扱うが、あれは**まさにこの選択**のことだ。ここで理解しておくと、第19章が楽になる。

## 12.6　PDB（デバッグ情報）

### PDBとは

MSVCは、デバッグ情報を実行ファイルではなく**別ファイル（`.pdb`）**に出力する。

| ファイル | 中身 |
| --- | --- |
| `pixcli.exe` | 実行コード |
| `pixcli.pdb` | 行番号、変数名、型情報 |

PDBがなくても実行できるが、デバッガでソースコードを追えなくなる。クラッシュダンプの解析にも必要だ。

### CMakeでの制御

CMake 3.25以降、デバッグ情報の形式は専用のプロパティで指定する。

```cmake
set_target_properties(pixcli PROPERTIES
    MSVC_DEBUG_INFORMATION_FORMAT "ProgramDatabase"
)
```

| 値 | フラグ | 意味 |
| --- | --- | --- |
| `Embedded` | `/Z7` | `.obj` に埋め込む（PDBを作らない） |
| `ProgramDatabase` | `/Zi` | 別ファイルのPDB |
| `EditAndContinue` | `/ZI` | 編集して続行に対応したPDB |
| `""` | なし | デバッグ情報なし |

既定値は次のとおりで、通常はこれで問題ない。

```
$<$<CONFIG:Debug,RelWithDebInfo>:ProgramDatabase>
```

つまり `Debug` と `RelWithDebInfo` でPDBが作られ、`Release` と `MinSizeRel` では作られない。**12.3節で `RelWithDebInfo` を常用する理由がこれだ。**

これもポリシー（`CMP0141`）に依存する。`cmake_minimum_required(VERSION 3.28)` なら `NEW` になり、`/Zi` は `CMAKE_CXX_FLAGS_<CONFIG>` から取り除かれてプロパティ経由になる。

### `Embedded` が有利な場面

`ccache` などのコンパイラキャッシュを使う場合、`/Zi` は複数のコンパイル単位が同じPDBファイルに書き込むため相性が悪い。`/Z7`（`Embedded`）にすると `.obj` が自己完結するので、キャッシュが効くようになる。

```cmake
set(CMAKE_MSVC_DEBUG_INFORMATION_FORMAT "$<$<CONFIG:Debug,RelWithDebInfo>:Embedded>")
```

### PDBの配布

**Releaseビルドを配布するとき、PDBは同梱しない**のが普通だ。内部構造の情報が含まれるからである。しかし、クラッシュレポートを解析するために**社内で保管しておく**必要がある。「シンボルサーバー」と呼ばれる運用だ。

CMakeでPDBのファイル名と場所を制御するには、次のプロパティを使う。

```cmake
set_target_properties(pixkit-filter PROPERTIES
    PDB_NAME              "pixkit-filter"
    PDB_OUTPUT_DIRECTORY  "${CMAKE_BINARY_DIR}/pdb"
    COMPILE_PDB_NAME      "pixkit-filter-compile"
)
```

| プロパティ | 対象 |
| --- | --- |
| `PDB_NAME` / `PDB_OUTPUT_DIRECTORY` | **リンカが作るPDB**（実行ファイル・DLL用） |
| `COMPILE_PDB_NAME` / `COMPILE_PDB_OUTPUT_DIRECTORY` | **コンパイラが作るPDB**（静的ライブラリ用） |

静的ライブラリはリンクされないので、リンカのPDBを持たない。だから `COMPILE_PDB_*` を使う。この区別を知らないと、「静的ライブラリのPDBが出力先に出てこない」と悩むことになる。

第21章5節で、PDBのインストールを扱う。

## 12.7　ジェネレータ式の実践

第7章8節で基本を学んだ。ここでは実際に使うパターンを整理する。

### 構成による分岐

```cmake
target_compile_definitions(pixkit_options INTERFACE
    $<$<CONFIG:Debug>:PIXKIT_DEBUG=1>
)

target_compile_options(pixkit_options INTERFACE
    $<$<CONFIG:Debug>:/JMC>              # 「マイコードのみ」デバッグ
)
```

### コンパイラによる分岐

```cmake
target_compile_options(pixkit_warnings INTERFACE
    $<$<CXX_COMPILER_ID:MSVC>:/W4>
    $<$<CXX_COMPILER_ID:GNU,Clang>:-Wall;-Wextra;-Wpedantic>
)
```

第5章5節で学んだ「リストはセミコロン区切り」がここで効く。スペース区切りで書くと1つの引数として扱われて壊れる。

### 条件を組み合わせる

```cmake
target_compile_options(pixkit_options INTERFACE
    $<$<AND:$<CXX_COMPILER_ID:MSVC>,$<CONFIG:Release>>:/GL>
)
```

`AND` / `OR` / `NOT` が使える。ただし、**入れ子が深くなると読めなくなる。** 2段までに留め、それ以上は変数に切り出す。

```cmake
set(IS_MSVC_RELEASE "$<AND:$<CXX_COMPILER_ID:MSVC>,$<CONFIG:Release>>")
target_compile_options(pixkit_options INTERFACE "$<${IS_MSVC_RELEASE}:/GL>")
```

### ターゲット情報の問い合わせ

```cmake
$<TARGET_FILE:pixcli>          # C:/.../bin/Debug/pixcli.exe
$<TARGET_FILE_NAME:pixcli>     # pixcli.exe
$<TARGET_FILE_DIR:pixcli>      # C:/.../bin/Debug
$<TARGET_PROPERTY:pixcli,COMPILE_OPTIONS>
$<TARGET_RUNTIME_DLLS:pixcli>  # 第11章7節
```

第14章のテスト登録、第15章のテストデータのコピー、第16章のベンチマーク実行で使うことになる。

### 検証する

構成時には評価されないので `message()` では見えない（第7章8節）。確実に確認するには `file(GENERATE)` を使う。

```cmake
file(GENERATE
    OUTPUT  "${CMAKE_BINARY_DIR}/flags-$<CONFIG>.txt"
    CONTENT "target : pixcli
config : $<CONFIG>
defs   : $<TARGET_PROPERTY:pixcli,COMPILE_DEFINITIONS>
opts   : $<TARGET_PROPERTY:pixcli,COMPILE_OPTIONS>
runtime: $<TARGET_PROPERTY:pixcli,MSVC_RUNTIME_LIBRARY>
"
)
```

マルチ構成ジェネレータなら、`flags-Debug.txt` と `flags-Release.txt` が両方生成される。**構成ごとに何が違うかが一目で分かる。**

## 12.8　リンク時最適化（LTCG）

### 何をするものか

通常、最適化は翻訳単位（`.cpp` 1つ）の中で完結する。リンク時最適化（LTO / MSVCでは LTCG）は、**リンクの段階でプログラム全体を見渡して最適化する**。

- 別の `.cpp` にある関数をインライン展開できる
- 呼ばれていない関数を削除できる

実行速度が数％〜十数％改善することがある。代わりに、**リンク時間が大幅に延びる**（大規模プロジェクトでは数分単位）。

### 安全な有効化

対応していないコンパイラでエラーになるのを避けるため、必ず検査してから有効にする。

```cmake
include(CheckIPOSupported)

check_ipo_supported(RESULT PIXKIT_IPO_SUPPORTED OUTPUT PIXKIT_IPO_MESSAGE)

if(PIXKIT_IPO_SUPPORTED)
    set_target_properties(pixkit-filter pixcli PROPERTIES
        INTERPROCEDURAL_OPTIMIZATION_RELEASE        ON
        INTERPROCEDURAL_OPTIMIZATION_RELWITHDEBINFO ON
    )
else()
    message(STATUS "LTOは利用できません: ${PIXKIT_IPO_MESSAGE}")
endif()
```

`INTERPROCEDURAL_OPTIMIZATION_<CONFIG>` という**構成ごとのプロパティ**を使っているのがポイントだ。Debugビルドで有効にすると、ビルドが遅くなるうえデバッグもしにくくなる。

`_<CONFIG>` の部分は**すべて大文字**にする（`RELWITHDEBINFO`）。ここは間違えやすい。

プロジェクト全体に適用するなら変数を使う。

```cmake
set(CMAKE_INTERPROCEDURAL_OPTIMIZATION_RELEASE ON)
```

### 注意点

- **静的ライブラリとの相性**：LTOを有効にした静的ライブラリは、通常のオブジェクト形式ではなく中間表現になる。それを LTO なしのプロジェクトにリンクすると失敗することがある。**配布する静的ライブラリでは有効にしない**
- **インクリメンタルリンクと排他**：`/GL` は `/INCREMENTAL` と併用できない。開発中のビルドが遅くなる
- **効果は測ってから判断する**：第16章のベンチマークで実測できる

### インクリメンタルリンク

開発中のリンク時間を短縮する仕組みだ。MSVCではDebugビルドで既定で有効になっている。

LTOやある種のリンカオプションと衝突するので、`Release` では無効にするのが普通だ。CMakeは構成ごとに適切な既定値を設定してくれるので、通常は意識しなくてよい。

### 手順2：Debug限定のアサーションを作る

`libs/core/include/pixkit/core/assert.hpp`

```cpp
#pragma once

#include <cstdio>
#include <cstdlib>

#if defined(PIXKIT_DEBUG)
#  define PIXKIT_ASSERT(cond)                                             \
      do {                                                                \
          if (!(cond)) {                                                  \
              std::fprintf(stderr, "PIXKIT_ASSERT failed: %s\n  at %s:%d\n", \
                           #cond, __FILE__, __LINE__);                    \
              std::abort();                                               \
          }                                                               \
      } while (false)
#else
#  define PIXKIT_ASSERT(cond) ((void)0)
#endif
```

`libs/core/CMakeLists.txt` の `PIXKIT_CORE_HEADERS` に追加し、`compile_check.cpp` にも `#include` を足す。

`image.hpp` の添字演算子で使う。

```cpp
#include <pixkit/core/assert.hpp>

[[nodiscard]] Rgb8& operator[](int x, int y) noexcept {
    PIXKIT_ASSERT(x >= 0 && x < width_);
    PIXKIT_ASSERT(y >= 0 && y < height_);
    return pixels_[static_cast<std::size_t>(y) * width_ + x];
}
```

### 手順6：`/MT` に切り替えてみる

トップレベルの `CMakeLists.txt` の `project()` の直後に追加する。

```cmake
if(PROJECT_IS_TOP_LEVEL)
    set(CMAKE_MSVC_RUNTIME_LIBRARY "MultiThreaded$<$<CONFIG:Debug>:Debug>")
endif()
```

```
cmake --preset x64-debug --fresh

dumpbin /dependents out\build\x64-debug\bin\pixcli.exe | findstr MSVC
```

何も出ない。**CRTが実行ファイルに静的リンクされた。**

次に、`BUILD_SHARED_LIBS=ON`（第11章9節）と組み合わせてみる。

### 発展課題

## この章のまとめ

- **単一構成**（Ninja）は構成時に `CMAKE_BUILD_TYPE` で、**マルチ構成**（Visual Studio、Ninja Multi-Config）はビルド時に `--config` で構成を決める。`CMAKE_BUILD_TYPE` はマルチ構成では**空**になる
- `CMAKE_BUILD_TYPE` を指定し忘れると、最適化もデバッグ情報もないビルドになる。**プリセットで必ず指定する**
- `Debug` 以外の全構成で **`NDEBUG` が定義され、`assert()` が消える**
- **`RelWithDebInfo` を常用する。** 最適化されていてスタックも読める
- フラグは `CMAKE_CXX_FLAGS` / `CMAKE_CXX_FLAGS_<CONFIG>` / ターゲットの `COMPILE_OPTIONS` から合成される。**変数を直接いじらず、ターゲットに指定する**
- MSVCランタイムは **`MSVC_RUNTIME_LIBRARY`**（既定 `MultiThreaded$<$<CONFIG:Debug>:Debug>DLL`）で制御する。文字列置換で `/MD` を `/MT` に書き換える古い手法は不要。**DLLを使うなら `/MD`**
- デバッグ情報は **`MSVC_DEBUG_INFORMATION_FORMAT`**（既定で `Debug` と `RelWithDebInfo` に `ProgramDatabase`）。静的ライブラリのPDBは `COMPILE_PDB_*` で制御する
- ジェネレータ式の内容は **`file(GENERATE)`** で構成ごとにファイルに書き出して確認する
- LTOは **`check_ipo_supported`** で検査してから `INTERPROCEDURAL_OPTIMIZATION_<CONFIG>`（大文字）で有効にする。配布する静的ライブラリでは有効にしない

これで第3部は終わりだ。ヘッダーオンリー・静的・動的の3種類のライブラリを作り、それらを構成ごとに正しく作り分けられるようになった。

しかし、いま `pixkit` には**テストが1つもない**。フィルタが本当に正しく動いているのか、誰も検証していない。第4部では、CTest（第13章）、GoogleTest（第14〜15章）、Google Benchmark（第16章）、Clang-Tidy（第17章）を組み込み、このプロジェクトに品質を担保する仕組みを入れていく。
