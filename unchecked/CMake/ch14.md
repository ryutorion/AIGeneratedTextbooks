# 第14章　GoogleTestを組み込む

## この章のゴール

- 依存の取り込み方（FetchContent / find_package / vcpkg）を比較し、選べる
- `FetchContent` でGoogleTestを取り込み、**バージョンを固定する**
- `gtest_force_shared_crt` でランタイム不一致を避ける
- `GTest::gtest` / `GTest::gtest_main` / `GTest::gmock` を使い分ける
- **`gtest_discover_tests` でテストケースを個別にCTestへ登録する**
- DLLに依存するテストの実行時パス問題を解決する
- `BUILD_TESTING` でテストのビルドを任意にする
- `FetchContent` で取り込んだライブラリが自分のビルドに与える副作用を制御する

第13章でCTestが「実行と集計」を担うことを見た。この章でGoogleTestが「アサーションとテストケース」を担う。

---

## 14.1　依存の取り込み方を選ぶ

外部ライブラリをCMakeプロジェクトに入れる方法は、大きく3つある。

| 方法 | 何をするか | 扱う章 |
| --- | --- | --- |
| **`find_package`** | すでにインストール済みのものを探す | 第18章 |
| **`FetchContent`** | ソースを取ってきて、自分のビルドの一部としてビルドする | **本章** |
| **vcpkg** | パッケージマネージャに任せる | 第19章 |

### それぞれの性質

| | `find_package` | `FetchContent` | vcpkg |
| --- | --- | --- | --- |
| 事前準備 | 利用者がインストール | **不要** | vcpkgのセットアップ |
| ネットワーク | 不要 | **構成時に必要** | 初回のみ |
| バージョン固定 | 難しい | **容易（Gitタグ）** | 容易（baseline） |
| ビルド時間 | 短い | **長い**（毎回ビルドする） | 短い（バイナリキャッシュ） |
| 設定の制御 | できない | **できる**（オプションを渡せる） | ポート次第 |
| オフラインビルド | ○ | △ | ○ |

### 本書での方針

本章では **`FetchContent`** を使う。理由は、

- **読者の環境準備が不要**（CMakeとネットワークだけあればよい）
- バージョンをリポジトリに記録でき、誰がビルドしても同じものが入る
- GoogleTestのビルドオプションを細かく制御できる

ただし、第19章でvcpkgを導入したら、**GoogleTestとGoogle Benchmarkをvcpkg経由に切り替える**。実務では、依存が増えたときにvcpkgのほうが管理しやすくなるからだ。「まずFetchContentで動かし、後でvcpkgに移行する」という流れ自体が、実際のプロジェクトでよく起きる展開でもある。

### GoogleTestの「ソースからビルドせよ」という方針

GoogleTestの公式ドキュメントは、**プリビルドのバイナリを配布・利用しないこと**を強く推奨している。理由は、テストフレームワークがコンパイルフラグ（特にランタイムライブラリやデバッグ設定）に敏感だからだ。

この方針は `FetchContent` と相性がよい。ソースを取ってきて、**自分のプロジェクトと同じフラグでビルドする**からである。

## 14.2　`FetchContent` でGoogleTestを取り込む

### 基本形

```cmake
include(FetchContent)

FetchContent_Declare(googletest
    GIT_REPOSITORY https://github.com/google/googletest.git
    GIT_TAG        v1.17.0
    GIT_SHALLOW    TRUE
    EXCLUDE_FROM_ALL
)

FetchContent_MakeAvailable(googletest)
```

| 引数 | 意味 |
| --- | --- |
| `GIT_REPOSITORY` | 取得元 |
| `GIT_TAG` | **必ず固定する**（後述） |
| `GIT_SHALLOW TRUE` | 履歴を取らず、指定タグだけを浅く取得する。速い |
| `EXCLUDE_FROM_ALL` | 「すべてビルド」の対象から外す。必要なターゲットだけがビルドされる |

`FetchContent_MakeAvailable` は、ダウンロード → `add_subdirectory` までを行う。つまり**GoogleTestのターゲットが、自分のプロジェクトのターゲットとして追加される。**

### `GIT_TAG` は必ず固定する

```cmake
GIT_TAG main            # 絶対にやらない
GIT_TAG v1.17.0         # タグを指定（推奨）
GIT_TAG 52eb8108c5bd... # コミットハッシュ（最も厳密）
```

`main` を指定すると、**ビルドするたびに違うコードが入る可能性がある。** 昨日通ったCIが今日落ちる、という事態を招く。

タグかコミットハッシュを指定する。タグは（悪意がなければ）動かないので、実用上は十分だ。より厳密にやるならコミットハッシュを使う。

> **`GIT_SHALLOW TRUE` の注意**
> 浅い取得はタグやブランチ名に対してのみ有効で、**コミットハッシュを指定した場合は使えない**（あるいは大量のデータを取ってしまう）ことがある。ハッシュ固定と `GIT_SHALLOW` を併用するときは、実際に速いか確認する。

### バージョンを1か所にまとめる

依存が増えてくると、バージョンが散らばる。1か所にまとめておくとよい。

```cmake
# cmake/PixkitDependencies.cmake
set(PIXKIT_GOOGLETEST_TAG "v1.17.0" CACHE STRING "GoogleTestのバージョン")
set(PIXKIT_BENCHMARK_TAG  "v1.9.5"  CACHE STRING "Google Benchmarkのバージョン")
```

`CACHE STRING` にしておけば、利用者が `-DPIXKIT_GOOGLETEST_TAG=v1.16.0` で差し替えられる。

### `FetchContent` はいつ実行されるか

**構成(configure)時**だ（第2章3節）。だから、

- 初回の構成に時間がかかる（ダウンロード＋Gitのチェックアウト）
- 2回目以降はキャッシュされる（`_deps/` の下）
- **ネットワークがないと構成できない**

ダウンロード先は既定で `${CMAKE_BINARY_DIR}/_deps` だ。ビルドディレクトリを消すと再ダウンロードになるので、複数のビルドディレクトリで共有したい場合は次のように設定する。

```cmake
set(FETCHCONTENT_BASE_DIR "${CMAKE_SOURCE_DIR}/.deps" CACHE PATH "")
```

（`.gitignore` に `.deps/` を追加すること）

## 14.3　`gtest_force_shared_crt` — ランタイム不一致を避ける

**Windowsでこの1行を忘れると、必ずリンクエラーになる。**

```cmake
set(gtest_force_shared_crt ON CACHE BOOL "" FORCE)
FetchContent_MakeAvailable(googletest)
```

### 何が起きるか

GoogleTestのCMakeLists.txtは、Windowsで**既定として `/MT`（静的CRT）を選ぶ**。歴史的な事情による設定だ。

一方、あなたのプロジェクトは既定で `/MD`（動的CRT）でビルドされる（第12章5節）。この2つをリンクすると、こうなる。

```
gtest.lib(gtest-all.obj) : error LNK2038: 'RuntimeLibrary' の不一致が検出されました。
値 'MT_StaticRelease' が 'MD_DynamicRelease' と一致しません
```

第12章5節で説明した `/MD` と `/MT` の話が、ここで最初の実害として現れる。

### なぜ `FORCE` が要るのか

`gtest_force_shared_crt` はGoogleTest側の `option()` だ。第8章5節で述べたポリシー `CMP0077` により、**`option()` を呼ぶ前に同名の通常変数があれば、そちらが優先される。**

```cmake
set(gtest_force_shared_crt ON)                       # 通常変数（これでも効く）
set(gtest_force_shared_crt ON CACHE BOOL "" FORCE)   # キャッシュ変数を強制上書き
```

どちらでも動くが、後者のほうが確実だ。`FORCE` を付けるのは、**すでにキャッシュに `OFF` が入っている場合に上書きするため**である（第5章3節：`set(... CACHE ...)` は既存の値を上書きしない）。

### `/MT` で統一している場合

プロジェクト全体を `/MT` にしているなら（第12章5節）、この設定は**不要**——というより、`OFF`（既定）のままにする。要は「揃っていること」が重要であって、どちらにするかは選択の問題だ。

より確実な方法として、CMake側の仕組みでGoogleTestにも同じランタイムを強制できる。

```cmake
set(CMAKE_MSVC_RUNTIME_LIBRARY "MultiThreaded$<$<CONFIG:Debug>:Debug>DLL")
```

`FetchContent_MakeAvailable` より**前**に書けば、GoogleTestのターゲットにも適用される。

## 14.4　ターゲットのリンク

GoogleTestは4つのターゲットを提供する。

| ターゲット | 中身 |
| --- | --- |
| `GTest::gtest` | テストフレームワーク本体 |
| `GTest::gtest_main` | 本体 ＋ **既定の `main()`** |
| `GTest::gmock` | モックフレームワーク |
| `GTest::gmock_main` | 上記 ＋ 既定の `main()` |

```cmake
add_executable(pixkit-tests test_color.cpp test_image.cpp)
target_link_libraries(pixkit-tests PRIVATE
    pixkit::core
    pixkit::warnings
    GTest::gtest_main
)
```

**通常は `GTest::gtest_main` を使う。** `main()` を自分で書く必要がなくなる。

自分で `main()` を書きたい場合（初期化処理を入れたい、など）は `GTest::gtest` を使う。

```cpp
#include <gtest/gtest.h>

int main(int argc, char** argv)
{
    ::testing::InitGoogleTest(&argc, argv);
    // 独自の初期化
    return RUN_ALL_TESTS();
}
```

### gmockが不要なら切る

```cmake
set(BUILD_GMOCK OFF CACHE BOOL "" FORCE)
set(INSTALL_GTEST OFF CACHE BOOL "" FORCE)
```

| オプション | 意味 |
| --- | --- |
| `BUILD_GMOCK` | gmockをビルドするか（既定 `ON`） |
| `INSTALL_GTEST` | **GoogleTestを `install()` の対象にするか**（既定 `ON`） |

**`INSTALL_GTEST OFF` は重要だ。** これを忘れると、第21章で `cmake --install` したときに、GoogleTestのヘッダとライブラリまでインストールされてしまう。テストフレームワークを配布物に混ぜてはいけない。

## 14.5　`gtest_discover_tests`

### 素朴なやり方の問題

```cmake
add_test(NAME pixkit-tests COMMAND pixkit-tests)
```

これでも動く。しかし、CTestから見れば**テストは1つ**だ。

- 個別のテストケースを絞り込めない（`ctest -R Color.Clamp` が効かない）
- 並列実行できない
- どのケースが失敗したのか、CTestの集計では分からない

### 解決：テストケースを個別に登録する

```cmake
include(GoogleTest)

gtest_discover_tests(pixkit-tests
    DISCOVERY_MODE    PRE_TEST
    DISCOVERY_TIMEOUT 30
    PROPERTIES
        LABELS  "unit"
        TIMEOUT 30
)
```

`gtest_discover_tests` は、テスト実行ファイルを `--gtest_list_tests` 付きで実行して**テストケースの一覧を取得し、1つずつ `add_test` する。**

結果、`ctest` の出力はこうなる。

```
    Start 1: Color.WhiteStaysWhite
1/3 Test #1: Color.WhiteStaysWhite ............   Passed    0.00 sec
    Start 2: Color.PureRedLuminance
2/3 Test #2: Color.PureRedLuminance ...........   Passed    0.00 sec
    Start 3: Color.Clamp
3/3 Test #3: Color.Clamp ......................   Passed    0.00 sec
```

**GoogleTestのテストケースが、CTestの個別のテストとして見えている。** これで絞り込みも並列実行もできる。

### `DISCOVERY_MODE` の選択

一覧の取得を**いつ**行うかを指定する。

| 値 | タイミング | 性質 |
| --- | --- | --- |
| `POST_BUILD`（既定） | ビルド直後 | ビルドのたびに実行ファイルを起動する |
| `PRE_TEST` | `ctest` の実行直前 | ビルドが速い。**クロスコンパイル時も安全** |

**`PRE_TEST` を推奨する。** 理由は、

- ビルドのたびにテスト実行ファイルを起動しなくて済む
- DLLの実行時パス問題（14.6節）が起きにくい
- CIで「ビルドだけして、テストは別マシンで」という構成が取れる

既定を変えるには変数を使う。

```cmake
set(CMAKE_GTEST_DISCOVER_TESTS_DISCOVERY_MODE PRE_TEST)
```

### `DISCOVERY_TIMEOUT`

一覧取得のタイムアウトで、**既定は5秒**だ。テスト実行ファイルの起動が遅い（DLLが多い、初期化が重い）と、これを超えて失敗する。

```
Error running test executable ... Process terminated due to timeout
```

30秒程度に伸ばしておくと安心だ。

### 主なオプション

```cmake
gtest_discover_tests(pixkit-tests
    TEST_PREFIX       "unit."          # 名前の前に付ける
    TEST_SUFFIX       ""
    TEST_FILTER       "Color.*"        # 一部だけ登録する
    WORKING_DIRECTORY "${CMAKE_CURRENT_BINARY_DIR}"
    DISCOVERY_MODE    PRE_TEST
    DISCOVERY_TIMEOUT 30
    XML_OUTPUT_DIR    "${CMAKE_BINARY_DIR}/test-results"
    PROPERTIES
        LABELS  "unit"
        TIMEOUT 30
)
```

`PROPERTIES` に書いたものは、**登録されるすべてのテストに適用される**（第13章3節のテストプロパティ）。

`XML_OUTPUT_DIR` は、GoogleTestのJUnit形式XMLを出力させる。CI（第15章7節）でテスト結果を可視化するときに使う。

### `gtest_add_tests` との違い

古い `gtest_add_tests` というコマンドもある。こちらは**ソースコードを正規表現でスキャンして** `TEST()` マクロを探す。

| | `gtest_add_tests` | `gtest_discover_tests` |
| --- | --- | --- |
| 検出方法 | ソースの正規表現スキャン | **実行ファイルに問い合わせる** |
| マクロで生成したテスト | 検出できない | 検出できる |
| パラメタライズドテスト | 検出できない | **検出できる** |
| 実行ファイルのビルド | 不要 | 必要 |

**`gtest_discover_tests` を使う。** 第15章2節でパラメタライズドテストを書くので、それだけでも理由になる。

## 14.6　DLLに依存するテストの実行時パス

### 問題

`pixkit-tests` が `pixkit::filter`（DLL、第11章）にリンクしていると、テスト実行時にDLLが見つからないことがある。

```
Unable to find executable: ... The application was unable to start correctly
```

第11章7節で扱った問題が、テストの文脈で再発する。

### 解決策1：出力ディレクトリの統一（すでにやってある）

第8章6節で `CMAKE_RUNTIME_OUTPUT_DIRECTORY` を `bin/` にまとめてある。テスト実行ファイルもDLLも `bin/` に出るので、**自分のプロジェクト内のDLLについては、これで解決している。**

### 解決策2：テストの環境変数に `PATH` を足す

vcpkg由来のDLL（第19章）など、`bin/` に出ないものがある場合はこうする。

```cmake
gtest_discover_tests(pixkit-tests
    DISCOVERY_MODE PRE_TEST
    PROPERTIES
        ENVIRONMENT_MODIFICATION
            "PATH=path_list_prepend:$<TARGET_FILE_DIR:pixkit-filter>"
)
```

`ENVIRONMENT_MODIFICATION`（CMake 3.22以降）は、既存の環境変数を**壊さずに追記**する。単に `ENVIRONMENT "PATH=..."` と書くと `PATH` を丸ごと置き換えてしまい、`cmd.exe` すら見つからなくなる。

### 解決策3：POST_BUILDでコピー

第11章7節と同じ方法だ。

```cmake
if(WIN32)
    add_custom_command(TARGET pixkit-tests POST_BUILD
        COMMAND ${CMAKE_COMMAND} -E copy_if_different
                $<TARGET_RUNTIME_DLLS:pixkit-tests> $<TARGET_FILE_DIR:pixkit-tests>
        COMMAND_EXPAND_LISTS
    )
endif()
```

### `DISCOVERY_MODE POST_BUILD` との相性

`POST_BUILD` モードでは、**ビルド直後にテスト実行ファイルを起動する**。このときDLLが揃っていないと、テストの検出そのものが失敗する。

```
CMake Error: Error running test executable
```

しかも、原因が「テストが壊れている」のか「DLLがない」のか分かりにくい。`PRE_TEST` モードなら、検出は `ctest` 実行時になるので、環境変数の設定（解決策2）が確実に効く。**14.5節で `PRE_TEST` を推奨した理由の1つがこれだ。**

## 14.7　テストのビルドを任意にする

第8章5節で用意したオプションを使う。

```cmake
# トップレベルの CMakeLists.txt
if(PIXKIT_BUILD_TESTS AND BUILD_TESTING)
    add_subdirectory(tests)
endif()
```

そして、**GoogleTestの取得もこの中で行う。**

```cmake
# tests/CMakeLists.txt
include(FetchContent)
FetchContent_Declare(googletest ...)
FetchContent_MakeAvailable(googletest)

add_executable(pixkit-tests ...)
```

こうすることで、`PIXKIT_BUILD_TESTS=OFF` のときは**ダウンロードすら発生しない。** 構成時間が大きく変わる。

```
cmake --preset x64-debug -DPIXKIT_BUILD_TESTS=OFF
```

第8章3節の `PROJECT_IS_TOP_LEVEL` と組み合わさって、「他人が `FetchContent` で pixkit を取り込んだとき、GoogleTestまで芋づる式にダウンロードされる」ことがなくなる。**ライブラリを配布するなら必須の配慮だ。**

## 14.8　`FetchContent` の副作用に注意する

`FetchContent_MakeAvailable` は、内部で `add_subdirectory` を呼ぶ。つまり**他人のCMakeLists.txtを、自分のプロジェクトの中で実行する。** いくつか副作用がある。

### 副作用1：ターゲットが増える

```
cmake --build --preset x64-debug --target help
```

`gtest`、`gtest_main`、`gmock`、`gmock_main` が現れる。`EXCLUDE_FROM_ALL` を付けておけば「すべてビルド」の対象からは外れるが、ターゲット自体は存在する。

Visual Studio のソリューションが賑やかになるのが気になるなら、フォルダにまとめる。

```cmake
foreach(T gtest gtest_main gmock gmock_main)
    if(TARGET ${T})
        set_target_properties(${T} PROPERTIES FOLDER "external")
    endif()
endforeach()
```

`if(TARGET ...)`（第5章6節）で存在確認してから触るのが安全だ。`BUILD_GMOCK OFF` のときは `gmock` が存在しない。

### 副作用2：警告設定が漏れる

第7章7節で「グローバル変数 `CMAKE_CXX_FLAGS` に `/W4` を足さない」と述べた理由がこれだ。グローバルに設定すると、GoogleTestのソースにも `/W4` が適用され、他人のコードの警告が大量に出る。

`pixkit::warnings` という **INTERFACEライブラリに閉じ込めてある**ので、この問題は起きない。第7章の設計が効いている。

逆に、GoogleTest側の警告を明示的に抑えたい場合は、こう書ける。

```cmake
if(TARGET gtest)
    target_compile_options(gtest PRIVATE $<$<CXX_COMPILER_ID:MSVC>:/W0>)
endif()
```

### 副作用3：オプション名の衝突

第8章5節で「オプションには必ずプロジェクト名の接頭辞を付ける」と述べた理由がこれだ。GoogleTestには `BUILD_GMOCK`、`INSTALL_GTEST`、`gtest_build_tests` などのオプションがある。自分が `BUILD_TESTS` のような一般的な名前を使っていると、意図せぬ相互作用が起きる。

### 副作用4：`install()` の汚染

14.4節で述べた `INSTALL_GTEST OFF` の話だ。取り込んだライブラリが `install()` を呼ぶと、自分の配布物に混入する。**第21章でインストールを実装するとき、`cmake --install` の結果を必ず目視で確認する。**

## ハンズオン：ユニットテストを書く

### 手順1：GoogleTestを取り込む

`tests/CMakeLists.txt` を書き換える。第13章で書いたCLIテストは残す。

```cmake
# ============================================================
# GoogleTest の取得
# ============================================================
include(FetchContent)

set(gtest_force_shared_crt ON  CACHE BOOL "" FORCE)   # /MD に揃える（14.3節）
set(BUILD_GMOCK            ON  CACHE BOOL "" FORCE)
set(INSTALL_GTEST          OFF CACHE BOOL "" FORCE)   # install() を汚染しない（14.4節）

FetchContent_Declare(googletest
    GIT_REPOSITORY https://github.com/google/googletest.git
    GIT_TAG        ${PIXKIT_GOOGLETEST_TAG}
    GIT_SHALLOW    TRUE
    EXCLUDE_FROM_ALL
)
FetchContent_MakeAvailable(googletest)

# IDEの表示を整理する（14.8節）
foreach(T gtest gtest_main gmock gmock_main)
    if(TARGET ${T})
        set_target_properties(${T} PROPERTIES FOLDER "external")
    endif()
endforeach()

# ============================================================
# ユニットテスト
# ============================================================
add_executable(pixkit-tests
    test_pixel.cpp
    test_color.cpp
    test_image.cpp
    test_ppm.cpp
    test_filters.cpp
)

target_link_libraries(pixkit-tests
    PRIVATE
        pixkit::core
        pixkit::codec
        pixkit::filter
        pixkit::warnings
        GTest::gtest_main
)

set_target_properties(pixkit-tests PROPERTIES FOLDER "tests")

include(GoogleTest)
gtest_discover_tests(pixkit-tests
    DISCOVERY_MODE    PRE_TEST
    DISCOVERY_TIMEOUT 30
    PROPERTIES
        LABELS  "unit"
        TIMEOUT 30
)

# ============================================================
# CLIの振る舞いテスト（第13章）
# ============================================================
```

### 手順2：画素型のテスト

`tests/test_pixel.cpp`

```cpp
#include <pixkit/core/pixel.hpp>

#include <gtest/gtest.h>

TEST(Pixel, Rgb8IsThreeBytes)
{
    EXPECT_EQ(sizeof(pixkit::Rgb8), 3u);
}

TEST(Pixel, DefaultIsBlack)
{
    const pixkit::Rgb8 c{};
    EXPECT_EQ(c.r, 0);
    EXPECT_EQ(c.g, 0);
    EXPECT_EQ(c.b, 0);
}

TEST(Pixel, Clamp01)
{
    EXPECT_FLOAT_EQ(pixkit::clamp01(-1.0f), 0.0f);
    EXPECT_FLOAT_EQ(pixkit::clamp01(0.5f),  0.5f);
    EXPECT_FLOAT_EQ(pixkit::clamp01(2.0f),  1.0f);
}

TEST(Pixel, RoundTripU8ToF32)
{
    for (int v = 0; v <= 255; ++v) {
        const auto c8 = pixkit::Rgb8{ static_cast<std::uint8_t>(v), 0, 0 };
        const auto back = pixkit::to_u8(pixkit::to_f32(c8));
        EXPECT_EQ(back.r, v) << "v = " << v;
    }
}
```

最後のテストは、`u8 → f32 → u8` の変換で値が保たれることを、**256通りすべてについて**検証している。`<< "v = " << v` を付けておくと、失敗したときにどの値で落ちたか分かる。

### 手順3：色変換のテスト

`tests/test_color.cpp`

```cpp
#include <pixkit/core/color.hpp>

#include <gtest/gtest.h>

TEST(Color, WhiteStaysWhite)
{
    EXPECT_EQ(pixkit::to_gray(pixkit::Rgb8{255, 255, 255}),
              (pixkit::Rgb8{255, 255, 255}));
}

TEST(Color, BlackStaysBlack)
{
    EXPECT_EQ(pixkit::to_gray(pixkit::Rgb8{0, 0, 0}), (pixkit::Rgb8{0, 0, 0}));
}

TEST(Color, PureRedLuminance)
{
    // BT.601: 0.299 * 255 ≒ 76
    EXPECT_EQ(pixkit::luminance(pixkit::Rgb8{255, 0, 0}), 76);
}

TEST(Color, GreenIsBrighterThanBlue)
{
    EXPECT_GT(pixkit::luminance(pixkit::Rgb8{0, 255, 0}),
              pixkit::luminance(pixkit::Rgb8{0, 0, 255}));
}

TEST(Color, GrayIsAchromatic)
{
    const auto g = pixkit::to_gray(pixkit::Rgb8{10, 200, 90});
    EXPECT_EQ(g.r, g.g);
    EXPECT_EQ(g.g, g.b);
}

TEST(Color, LerpEndpoints)
{
    const pixkit::Rgb32f a{0.0f, 0.0f, 0.0f};
    const pixkit::Rgb32f b{1.0f, 1.0f, 1.0f};
    EXPECT_EQ(pixkit::lerp(a, b, 0.0f), a);
    EXPECT_EQ(pixkit::lerp(a, b, 1.0f), b);
}
```

> **`EXPECT_EQ(x, (pixkit::Rgb8{255, 255, 255}))` の括弧**
> `EXPECT_EQ` はマクロなので、引数の中の `,` が引数の区切りと解釈される。ブレース初期化を渡すときは、**全体を括弧で囲む**必要がある。これはGoogleTestを使うと必ず一度は踏む罠だ。
>
> **C++23の多次元添字はさらに危ない。** `img[1, 2]` の `,` もマクロには区切りに見える。
> ```cpp
> EXPECT_EQ(img[1, 2], (pixkit::Rgb8{1, 2, 3}));    // コンパイルエラー
> ```
> ```
> error: macro "EXPECT_EQ" passed 3 arguments, but takes just 2
> ```
> ```cpp
> EXPECT_EQ((img[1, 2]), (pixkit::Rgb8{1, 2, 3}));  // 括弧で囲めば通る
> ```
> 第10章で `operator[](int, int)` を採用した以上、テストコードでは常にこの形になる。次の手順4で実際にこう書く。

### 手順4：画像型のテスト

`tests/test_image.cpp`

```cpp
#include <pixkit/core/image.hpp>

#include <gtest/gtest.h>

TEST(Image, DefaultIsEmpty)
{
    const pixkit::Image img;
    EXPECT_TRUE(img.empty());
    EXPECT_EQ(img.width(), 0);
    EXPECT_EQ(img.height(), 0);
}

TEST(Image, SizeAndByteSize)
{
    const pixkit::Image img(4, 3);
    EXPECT_EQ(img.width(), 4);
    EXPECT_EQ(img.height(), 3);
    EXPECT_EQ(img.pixel_count(), 12u);
    EXPECT_EQ(img.byte_size(), 36u);       // 12 px * 3 bytes
}

TEST(Image, SubscriptReadWrite)
{
    pixkit::Image img(4, 3);
    img[1, 2] = pixkit::Rgb8{1, 2, 3};
    EXPECT_EQ((img[1, 2]), (pixkit::Rgb8{1, 2, 3}));
    EXPECT_EQ((img[0, 0]), (pixkit::Rgb8{0, 0, 0}));
}

TEST(Image, ViewSharesStorage)
{
    pixkit::Image img(4, 3);
    auto v = img.view();
    v[2, 1] = pixkit::Rgb8{9, 9, 9};
    EXPECT_EQ((img[2, 1]), (pixkit::Rgb8{9, 9, 9}));   // 元の画像に反映される
}

TEST(Image, RowMajorLayout)
{
    pixkit::Image img(4, 3);
    img[0, 1] = pixkit::Rgb8{7, 7, 7};               // x=0, y=1
    // 行優先なら、先頭から width 個目の要素になるはず
    EXPECT_EQ(img.pixels()[4], (pixkit::Rgb8{7, 7, 7}));
}
```

`RowMajorLayout` のテストは、**メモリレイアウトの仮定を固定する**役割を持つ。第9章のPPMコーデックは「`Rgb8` の配列をそのまま書き出せる」ことを前提にしているので、この前提が壊れたら気づけるようにしておく。

### 手順5：コーデックのテスト

`tests/test_ppm.cpp`

```cpp
#include <pixkit/codec/ppm.hpp>

#include <gtest/gtest.h>

#include <filesystem>
#include <fstream>

namespace {

pixkit::Image make_test_image()
{
    pixkit::Image img(3, 2);
    img[0, 0] = pixkit::Rgb8{255,   0,   0};
    img[1, 0] = pixkit::Rgb8{  0, 255,   0};
    img[2, 0] = pixkit::Rgb8{  0,   0, 255};
    img[0, 1] = pixkit::Rgb8{255, 255, 255};
    img[1, 1] = pixkit::Rgb8{  0,   0,   0};
    img[2, 1] = pixkit::Rgb8{128, 128, 128};
    return img;
}

// テストごとに一意な一時ファイル名を作る
std::filesystem::path temp_path(std::string_view name)
{
    return std::filesystem::temp_directory_path() / name;
}

}  // namespace

TEST(Ppm, RoundTrip)
{
    const auto path = temp_path("pixkit_roundtrip.ppm");
    const auto src  = make_test_image();

    ASSERT_TRUE(pixkit::codec::save_ppm(path, src).has_value());

    const auto loaded = pixkit::codec::load_ppm(path);
    ASSERT_TRUE(loaded.has_value())
        << "load failed: " << pixkit::codec::to_string(loaded.error());

    EXPECT_EQ(loaded->width(),  src.width());
    EXPECT_EQ(loaded->height(), src.height());
    EXPECT_EQ(*loaded, src);

    std::filesystem::remove(path);
}

TEST(Ppm, MissingFile)
{
    const auto r = pixkit::codec::load_ppm(temp_path("pixkit_does_not_exist.ppm"));
    ASSERT_FALSE(r.has_value());
    EXPECT_EQ(r.error(), pixkit::codec::CodecError::FileNotFound);
}

TEST(Ppm, BadMagic)
{
    const auto path = temp_path("pixkit_bad_magic.ppm");
    {
        std::ofstream out(path, std::ios::binary);
        out << "P3\n1 1\n255\n255 0 0\n";     // P3（テキスト形式）は非対応
    }

    const auto r = pixkit::codec::load_ppm(path);
    ASSERT_FALSE(r.has_value());
    EXPECT_EQ(r.error(), pixkit::codec::CodecError::BadMagic);

    std::filesystem::remove(path);
}

TEST(Ppm, TruncatedData)
{
    const auto path = temp_path("pixkit_truncated.ppm");
    {
        std::ofstream out(path, std::ios::binary);
        out << "P6\n4 4\n255\n";
        out << "abc";                          // 48バイト必要なのに3バイトしかない
    }

    const auto r = pixkit::codec::load_ppm(path);
    ASSERT_FALSE(r.has_value());
    EXPECT_EQ(r.error(), pixkit::codec::CodecError::TruncatedData);

    std::filesystem::remove(path);
}

TEST(Ppm, HeaderComment)
{
    const auto path = temp_path("pixkit_comment.ppm");
    {
        std::ofstream out(path, std::ios::binary);
        out << "P6\n# created by pixkit\n1 1\n255\n";
        const char pixel[3] = {'\x0a', '\x14', '\x1e'};
        out.write(pixel, 3);
    }

    const auto r = pixkit::codec::load_ppm(path);
    ASSERT_TRUE(r.has_value());
    EXPECT_EQ(r->width(), 1);
    EXPECT_EQ(((*r)[0, 0]), (pixkit::Rgb8{10, 20, 30}));

    std::filesystem::remove(path);
}
```

`ASSERT_` と `EXPECT_` の使い分けが重要だ。

| | 失敗したとき |
| --- | --- |
| `EXPECT_*` | 記録して**続行する** |
| `ASSERT_*` | **その場でテスト関数から抜ける** |

「これが失敗したら後続の検証が意味をなさない」場面では `ASSERT_` を使う。`loaded.has_value()` が偽なのに `loaded->width()` を呼ぶと未定義動作になるので、ここは `ASSERT_` でなければならない。

> **一時ファイルの置き場所**
> ここでは `std::filesystem::temp_directory_path()` を使った。テストの `WORKING_DIRECTORY` に書く方法もあるが、並列実行（`ctest -j`）で衝突しやすい。テストデータの扱いは第15章3節で正面から設計し直す。

### 手順6：フィルタのテスト

`tests/test_filters.cpp`

```cpp
#include <pixkit/filter/filters.hpp>

#include <gtest/gtest.h>

namespace {

pixkit::Image solid(int w, int h, pixkit::Rgb8 c)
{
    pixkit::Image img(w, h);
    for (int y = 0; y < h; ++y)
        for (int x = 0; x < w; ++x)
            img[x, y] = c;
    return img;
}

}  // namespace

TEST(Filter, GrayscaleIsIdempotent)
{
    auto img = solid(4, 4, pixkit::Rgb8{10, 200, 90});
    pixkit::filter::grayscale(img.view());
    const auto once = img;
    pixkit::filter::grayscale(img.view());
    EXPECT_EQ(img, once) << "2回適用しても結果が変わらないはず";
}

TEST(Filter, GrayscaleMakesAchromatic)
{
    auto img = solid(4, 4, pixkit::Rgb8{10, 200, 90});
    pixkit::filter::grayscale(img.view());
    for (const auto& p : img.pixels()) {
        EXPECT_EQ(p.r, p.g);
        EXPECT_EQ(p.g, p.b);
    }
}

TEST(Filter, BlurOfUniformImageIsUnchanged)
{
    auto src = solid(8, 8, pixkit::Rgb8{100, 100, 100});
    const auto dst = pixkit::filter::blurred(src);
    EXPECT_EQ(dst, src) << "一様な画像をぼかしても変わらないはず（端も含めて）";
}

TEST(Filter, ThresholdProducesOnlyBlackOrWhite)
{
    auto img = solid(4, 4, pixkit::Rgb8{100, 150, 200});
    pixkit::filter::threshold(img.view(), 128);
    for (const auto& p : img.pixels()) {
        EXPECT_TRUE((p.r == 0 && p.g == 0 && p.b == 0) ||
                    (p.r == 255 && p.g == 255 && p.b == 255));
    }
}

TEST(Filter, BlurMismatchedSizeIsNoOp)
{
    auto src = solid(4, 4, pixkit::Rgb8{50, 50, 50});
    pixkit::Image dst(8, 8);
    const auto before = dst;
    pixkit::filter::blur3x3(src.view(), dst.view());
    EXPECT_EQ(dst, before) << "サイズ不一致なら何もしない契約";
}
```

`BlurOfUniformImageIsUnchanged` は良いテストだ。**具体的な数値を書かずに、性質だけを検証している。** 実装を変えても、この性質が保たれる限りテストは通る。「一様な画像を平均化しても一様のまま」は、境界処理の実装が正しいかも同時に検証している。

## この章のまとめ

- 依存の取り込みは `find_package` / `FetchContent` / vcpkg の3択。本章は **`FetchContent`**、第19章でvcpkgに移行する
- **`GIT_TAG` は必ず固定する。** `main` を指定しない。バージョンは変数にまとめて `CACHE STRING` にしておくと差し替えやすい
- **Windowsでは `gtest_force_shared_crt ON` が必須。** 忘れると `LNK2038: RuntimeLibrary の不一致`（第12章5節）
- **`INSTALL_GTEST OFF` を忘れない。** 第21章のインストールにテストフレームワークが混入する
- リンクするのは `GTest::gtest_main`（`main()` 込み）。自分で `main()` を書くなら `GTest::gtest`
- **`gtest_discover_tests` でテストケースを個別にCTestへ登録する。** `DISCOVERY_MODE PRE_TEST` と `DISCOVERY_TIMEOUT 30` を指定し、`PROPERTIES` でラベルとタイムアウトを付ける
- DLLを使うテストは、**出力ディレクトリの統一**（第8章6節）が基本。外部DLLは `ENVIRONMENT_MODIFICATION` で `PATH` に**追記**する（置き換えない）
- **GoogleTestの取得は `tests/CMakeLists.txt` の中で行う。** `PIXKIT_BUILD_TESTS=OFF` のときにダウンロードすら発生しない
- `FetchContent` は他人のCMakeLists.txtを自分のビルドで実行する。ターゲットの増加、警告設定の漏れ、オプション名の衝突、`install()` の汚染に注意する
- **マクロに渡すブレース初期化は括弧で囲む**：`EXPECT_EQ(x, (Rgb8{1,2,3}))`

次の第15章では、このテストを「育てる」。フィクスチャ、パラメタライズドテスト、テストデータの扱い、カバレッジ、そしてGitHub Actions でのCI実行までを扱う。テストは書いた瞬間から保守対象になるので、その構造を先に整えておく。
