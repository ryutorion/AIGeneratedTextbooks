# 第17章　Clang-Tidyによる静的解析を組み込む

## この章のゴール

- Windows + MSVC 環境でClang-Tidyを動かす選択肢を把握する
- **`CMAKE_CXX_CLANG_TIDY` がどのジェネレータで動くのか**を知る
- ターゲット単位で解析の有無を制御する
- `.clang-tidy` を書き、チェックの取捨選択とエラー化を設定する
- **サードパーティのコードを解析対象から確実に外す**
- `compile_commands.json` を生成し、`run-clang-tidy` で一括実行する
- **ヘッダーオンリーライブラリを解析対象に含める**
- Visual Studio のUI統合と、CIでのゲート化を組み立てる

第4部の締めくくりだ。テストが「正しさ」を、ベンチマークが「速さ」を守る。Clang-Tidyが守るのは**コードそのものの質**——バグになりうるパターン、古い書き方、非効率な実装である。

## 17.1　Windows + MSVC でClang-Tidyを動かす選択肢

### そもそもClang-Tidyとは

Clangのフロントエンドを使ってC++を構文解析し、**チェックのルール集**に照らして問題を報告するツールだ。コンパイラの警告より踏み込んだ指摘ができる。

```
warning: 'push_back' is called inside a loop; consider pre-allocating the container
         capacity before the loop [performance-inefficient-vector-operation]
warning: use range-based for loop instead [modernize-loop-convert]
warning: 42 is a magic number; consider replacing it with a named constant
         [readability-magic-numbers]
```

### 3つの入手経路

| 経路 | 入手方法 | 特徴 |
| --- | --- | --- |
| **Visual Studio 同梱** | インストーラの「C++ Clang-cl ビルドツール」 | 導入が簡単。VSのバージョンに追随 |
| **LLVM 公式インストーラ** | [llvm.org](https://releases.llvm.org/) から | 最新版が使える。バージョンを固定できる |
| **vcpkg / winget** | パッケージマネージャ経由 | 自動化しやすい |

第1章6節で「C++ Clang-cl ビルドツール」を入れておいたので、すでに使えるはずだ。

```
clang-tidy --version
```

### MSVCでビルドしながらClang-Tidyを使う

ここが最初の疑問点になる。**コンパイラはMSVC（`cl.exe`）のまま、解析だけClangにやらせる**ことができるのか。

答えは「できる」。CMakeの仕組みでは、

1. `cl.exe` が普通にコンパイルする
2. **同じソースと同じコンパイルオプションで、`clang-tidy` も起動する**
3. Clang-Tidyの指摘が、コンパイラの警告と同じようにビルドログに出る

つまり**二重にパースしている**。ビルド時間はその分増えるが、MSVCのコード生成とClangの解析を両立できる。

ただし1つ注意がある。Clang-Tidy はMSVC形式のオプション（`/W4` `/std:c++latest` など）をそのままでは解釈できない。**`--driver-mode=cl`** を指定すると、`cl.exe` 互換のオプション解釈になる。CMakeはMSVC系コンパイラを検出したときにこれを面倒見てくれるが、環境によっては明示が必要になる。

```cmake
set(CMAKE_CXX_CLANG_TIDY
    "${PIXKIT_CLANG_TIDY_EXE}"
    "--extra-arg-before=--driver-mode=cl"
)
```

`extra-arg-before` は「コンパイラのオプションより**前**に挿入する」という意味だ。うまく動かないときに、まず試す設定である。

### `clang-cl` に切り替える選択肢

もう1つの道は、**コンパイラごとClangに変える**ことだ。

```json
{
  "name": "x64-clangcl",
  "generator": "Ninja",
  "cacheVariables": {
    "CMAKE_C_COMPILER":   "clang-cl",
    "CMAKE_CXX_COMPILER": "clang-cl",
    "CMAKE_BUILD_TYPE":   "Debug"
  }
}
```

`clang-cl` はMSVC互換のドライバなので、`/W4` などのオプションがそのまま使える。

| | MSVC + Clang-Tidy | clang-cl + Clang-Tidy |
| --- | --- | --- |
| ビルド時間 | 二重パースの分だけ遅い | 速い（解析と同じフロントエンド） |
| 生成コード | MSVCと完全に同じ | **微妙に違う** |
| 設定の一致 | 完全 | ほぼ完全 |
| 用途 | 本番と同じバイナリで解析したい | 解析専用のビルドを分ける |

**本書はMSVC + Clang-Tidy を基本にする。** 「実際に配布するのと同じコンパイラでビルドしたものを解析する」ほうが素直だからだ。ただし、CIで `clang-cl` プリセットを追加して**両方の目で見る**のは良い運用である（発展課題）。

## 17.2　`CMAKE_CXX_CLANG_TIDY` で全体に適用する

### 最小の設定

```cmake
find_program(PIXKIT_CLANG_TIDY_EXE NAMES clang-tidy)

if(PIXKIT_CLANG_TIDY_EXE)
    set(CMAKE_CXX_CLANG_TIDY "${PIXKIT_CLANG_TIDY_EXE}")
endif()
```

この変数は、**それ以降に定義されるターゲット**の `CXX_CLANG_TIDY` プロパティの初期値になる（`CMAKE_CXX_STANDARD` と同じ仕組み。第7章2節）。

ビルドすると、コンパイルと同時にClang-Tidyが走る。

```
[1/2] Building CXX object libs/codec/CMakeFiles/pixkit-codec.dir/src/ppm.cpp.o
C:/work/pixkit/libs/codec/src/ppm.cpp:54:33: warning: 'reinterpret_cast' ...
```

### 決定的な制約：ジェネレータを選ぶ

**`CXX_CLANG_TIDY` は Makefile 系ジェネレータと Ninja でしか動かない。**

Visual Studio ジェネレータでは**黙って無視される**。エラーにも警告にもならず、ただ解析が行われない。「設定したのに何も出ない」と悩む原因はたいていこれだ。

第4章で用意したプリセットを思い出してほしい。

| プリセット | ジェネレータ | Clang-Tidy |
| --- | --- | --- |
| `x64-debug` / `x64-release` | Ninja | **動く** |
| `x64-vs` | Visual Studio 18 2026 | **動かない** |

日常のビルドをNinjaにしておいた判断が、ここで効いてくる。同じ理由で、次節の `compile_commands.json` もNinjaでしか生成されない（17.6節）。

### オプションとして切り替えられるようにする

Clang-Tidyを常時有効にすると、ビルドが目に見えて遅くなる。オプションにする。

```cmake
option(PIXKIT_ENABLE_CLANG_TIDY "ビルド時にClang-Tidyを実行する" OFF)

if(PIXKIT_ENABLE_CLANG_TIDY)
    find_program(PIXKIT_CLANG_TIDY_EXE NAMES clang-tidy)

    if(NOT PIXKIT_CLANG_TIDY_EXE)
        message(WARNING "clang-tidy が見つかりません。静的解析は無効です")
    else()
        message(STATUS "Clang-Tidy: ${PIXKIT_CLANG_TIDY_EXE}")
        set(CMAKE_CXX_CLANG_TIDY "${PIXKIT_CLANG_TIDY_EXE}")
    endif()
endif()
```

`find_program` は結果をキャッシュ変数に入れる。見つからなければ `PIXKIT_CLANG_TIDY_EXE-NOTFOUND` になり、`if` で偽と判定される（第5章2節の「偽の定数」）。

### 専用プリセットを用意する

```json
{
  "name": "x64-tidy",
  "displayName": "x64 Debug + Clang-Tidy",
  "inherits": "x64-debug",
  "cacheVariables": {
    "PIXKIT_ENABLE_CLANG_TIDY": "ON",
    "PIXKIT_BUILD_TESTS": "ON"
  }
}
```

日常は `x64-debug`（速い）、解析したいときとCIでは `x64-tidy`、という使い分けにする。

## 17.3　ターゲット単位で制御する

変数ではなくプロパティを直接設定すれば、ターゲットごとに制御できる。

```cmake
set_target_properties(pixkit-codec PROPERTIES
    CXX_CLANG_TIDY "${PIXKIT_CLANG_TIDY_EXE}"
)
```

### 特定のターゲットだけ除外する

**空文字列を設定すると、そのターゲットの解析が無効になる。**

```cmake
set_target_properties(gtest gtest_main PROPERTIES CXX_CLANG_TIDY "")
```

これが17.5節の中心的な道具になる。

確認するにはプロパティを読む。

```cmake
get_target_property(V pixkit-codec CXX_CLANG_TIDY)
message(STATUS "codec: [${V}]")
get_target_property(V2 gtest CXX_CLANG_TIDY)
message(STATUS "gtest: [${V2}]")
```

```
-- codec: [C:/Program Files/LLVM/bin/clang-tidy.exe]
-- gtest: []
```

### ヘルパー関数にまとめる

```cmake
function(pixkit_enable_clang_tidy)
    if(NOT PIXKIT_CLANG_TIDY_EXE)
        return()
    endif()
    foreach(T IN LISTS ARGN)
        if(TARGET ${T})
            set_target_properties(${T} PROPERTIES
                CXX_CLANG_TIDY "${PIXKIT_CLANG_TIDY_EXE}")
        endif()
    endforeach()
endfunction()

function(pixkit_disable_clang_tidy)
    foreach(T IN LISTS ARGN)
        if(TARGET ${T})
            set_target_properties(${T} PROPERTIES CXX_CLANG_TIDY "")
        endif()
    endforeach()
endfunction()
```

第5章8節で学んだ `function` と `ARGN`、第5章6節の `if(TARGET ...)` が組み合わさっている。**「変数でグローバルに有効にし、外したいターゲットだけ明示的に無効化する」**という運用にすると、新しいターゲットを追加したときに解析漏れが起きない。

## 17.4　`.clang-tidy` を書く

Clang-Tidyの設定は、プロジェクトルートに置く `.clang-tidy`（YAML）で行う。CMakeからは何も指定しなくてよい。**ソースファイルのあるディレクトリから上に向かって探索され、最初に見つかったものが使われる。**

### 本書で使う設定

```yaml
# .clang-tidy
Checks: >
  -*,
  bugprone-*,
  concurrency-*,
  cppcoreguidelines-*,
  misc-*,
  modernize-*,
  performance-*,
  portability-*,
  readability-*,

  -bugprone-easily-swappable-parameters,
  -cppcoreguidelines-avoid-magic-numbers,
  -cppcoreguidelines-pro-bounds-pointer-arithmetic,
  -cppcoreguidelines-pro-type-reinterpret-cast,
  -misc-non-private-member-variables-in-classes,
  -modernize-use-trailing-return-type,
  -readability-identifier-length,
  -readability-magic-numbers,

WarningsAsErrors: >
  bugprone-*,
  performance-*,

HeaderFilterRegex: '.*[/\\]pixkit[/\\].*'

FormatStyle: file
```

### `Checks` の書き方

**`-*` で全部無効にしてから、必要なものを足す。** これが定石だ。逆に「全部有効にしてから減らす」と、Clang-Tidyのバージョンが上がるたびに新しいチェックが増えてビルドが落ちる。

| 接頭辞 | 内容 |
| --- | --- |
| `bugprone-*` | **バグになりやすいパターン。最優先で入れる** |
| `performance-*` | 非効率な実装 |
| `modernize-*` | 古い書き方をモダンC++に |
| `readability-*` | 可読性 |
| `cppcoreguidelines-*` | C++ Core Guidelines 準拠 |
| `clang-analyzer-*` | 静的解析（パス感度あり）。**重いので注意** |
| `google-*` / `llvm-*` | 各社のスタイル規約。組織の方針次第 |

`-` を前置すると個別に無効化できる。

### 実際に無効化したくなるチェック

上の設定で外しているものには、それぞれ理由がある。

| 外したチェック | 理由 |
| --- | --- |
| `modernize-use-trailing-return-type` | `auto f() -> int` の形を強制する。好みの問題であり、既存コードを全面書き換えさせられる |
| `readability-magic-numbers` | 画像処理では `255` `0.299` などが大量に出る。定数化しても読みやすくならない |
| `readability-identifier-length` | `x`, `y`, `i` が全部怒られる |
| `bugprone-easily-swappable-parameters` | `blur3x3(src, dst)` のような同型引数がすべて指摘される |
| `cppcoreguidelines-pro-type-reinterpret-cast` | バイナリI/O（第9章のPPM）では必須 |

**「うるさいから外す」のではなく、「このプロジェクトでは意味がないから外す」と説明できることが重要だ。** 外した理由をコメントに書いておくとよい。

### `WarningsAsErrors`

指定したチェックの指摘を、**エラー（ビルド失敗）に格上げする。**

```yaml
WarningsAsErrors: >
  bugprone-*,
  performance-*,
```

全部をエラーにすると、既存コードがある場合に身動きが取れなくなる。**段階的に広げる**のが現実的だ。

1. まず全部を警告として見る
2. 既存の指摘を潰す
3. 潰し終わったカテゴリを `WarningsAsErrors` に追加する
4. 以後、そのカテゴリは増やせない

新しいコードだけ厳しくしたい場合は、17.7節の「差分だけ見る」運用と組み合わせる。

### `HeaderFilterRegex`

**これがないと、ヘッダの中の問題は報告されない。**

Clang-Tidyは既定で、**解析対象の `.cpp` そのもの**にしか指摘を出さない。`#include` したヘッダの中身は（システムヘッダも含めて大量にあるので）黙って無視される。

```yaml
HeaderFilterRegex: '.*[/\\]pixkit[/\\].*'
```

「パスに `pixkit/` を含むヘッダは解析する」という意味だ。`[/\\]` としているのは、Windowsのバックスラッシュ区切りにも対応するためである。

第10章で作ったヘッダーオンリーの `pixkit::core` は、**この設定がなければ一切解析されない。** 17.8節で詳しく扱う。

### その他のフィールド

| フィールド | 意味 |
| --- | --- |
| `FormatStyle` | `--fix` で自動修正したときの整形スタイル。`file` なら `.clang-format` に従う |
| `CheckOptions` | 個々のチェックの詳細設定 |
| `InheritParentConfig` | 親ディレクトリの `.clang-tidy` を継承するか |

`CheckOptions` の例を挙げる。

```yaml
CheckOptions:
  - key:   readability-function-cognitive-complexity.Threshold
    value: '30'
  - key:   readability-identifier-naming.ClassCase
    value: CamelCase
  - key:   readability-identifier-naming.FunctionCase
    value: lower_case
  - key:   readability-identifier-naming.PrivateMemberSuffix
    value: '_'
```

命名規約を機械的に検査できる。`pixkit` は `Image` / `to_gray` / `width_` という規約なので、上の設定がそのまま当てはまる。

### ディレクトリごとに設定を変える

`tests/` の下に別の `.clang-tidy` を置けば、テストコードだけ緩められる。

```yaml
# tests/.clang-tidy
InheritParentConfig: true
Checks: >
  -cppcoreguidelines-avoid-non-const-global-variables,
  -readability-function-cognitive-complexity,
```

`InheritParentConfig: true` で親の設定を引き継ぎ、差分だけ書く。**テストコードはGoogleTestのマクロを大量に使うので、本体と同じ基準では厳しすぎる。**

## 17.5　サードパーティのコードを除外する

これは実務で必ずぶつかる問題だ。放置すると、GoogleTestの警告が数百行出てビルドログが読めなくなる。

### 問題：`CMAKE_CXX_CLANG_TIDY` は後続の全ターゲットに効く

```cmake
set(CMAKE_CXX_CLANG_TIDY "${PIXKIT_CLANG_TIDY_EXE}")   # ここで設定すると
...
FetchContent_MakeAvailable(googletest)                  # gtest にも適用される
```

`FetchContent_MakeAvailable` は内部で `add_subdirectory` を呼ぶので（第14章8節）、そこで作られるターゲットにも初期値が伝わる。

### 対策1：取り込んだターゲットを明示的に無効化する

```cmake
FetchContent_MakeAvailable(googletest)

pixkit_disable_clang_tidy(gtest gtest_main gmock gmock_main)
```

17.3節のヘルパーを使う。`if(TARGET ...)` で存在確認しているので、`BUILD_GMOCK OFF` のときも安全だ。

### 対策2：設定する位置を後ろにする

```cmake
add_subdirectory(tests)          # ここで FetchContent が走る
set(CMAKE_CXX_CLANG_TIDY "...")  # その後で設定する
add_subdirectory(libs)
```

順序に依存するので、**壊れやすい。** 対策1のほうが意図が明確だ。

### 対策3：ヘッダ側は `HeaderFilterRegex` で守られている

17.4節の設定なら、`pixkit/` を含まないパスのヘッダは解析されない。GoogleTestのヘッダ（`gtest/gtest.h`）は対象外だ。

ただし、**あなたのテストコード（`.cpp`）は解析される。** GoogleTestのマクロが展開された結果に対して指摘が出ることがあるので、`tests/.clang-tidy` で緩めるのが実用的だ（17.4節）。

### 対策4：`SYSTEM` インクルードにする

CMake 3.25以降、依存を「システムヘッダ扱い」にできる。

```cmake
FetchContent_Declare(googletest
    GIT_REPOSITORY https://github.com/google/googletest.git
    GIT_TAG        ${PIXKIT_GOOGLETEST_TAG}
    GIT_SHALLOW    TRUE
    EXCLUDE_FROM_ALL
    SYSTEM                       # ← インクルードパスを SYSTEM 扱いにする
)
```

MSVCでは `/external:I` が使われ、**コンパイラの警告もClang-Tidyの指摘も抑制される。** 第7章6節で `/W4` を設定したときの「他人のコードの警告」問題にも効く。

### 生成コードの除外

`configure_file` や `generate_export_header` で生成したヘッダ（第8章4節、第11章3節）は、ビルドツリーにある。`HeaderFilterRegex` が `pixkit/` にマッチしてしまうので、必要なら除外する。

```yaml
HeaderFilterRegex: '.*[/\\]pixkit[/\\](?!.*_export\.hpp).*'
```

正規表現が複雑になるなら、生成物側に `// NOLINT` を入れるほうが早い場合もある。

### `// NOLINT` による個別抑制

どうしても消せない指摘は、コードで抑制する。

```cpp
auto* p = reinterpret_cast<const char*>(buf.data());  // NOLINT(cppcoreguidelines-pro-type-reinterpret-cast)

// NOLINTNEXTLINE(bugprone-narrowing-conversions)
const auto n = static_cast<int>(size);

// NOLINTBEGIN(readability-magic-numbers)
constexpr float kR = 0.299f;
constexpr float kG = 0.587f;
constexpr float kB = 0.114f;
// NOLINTEND(readability-magic-numbers)
```

**必ずチェック名を括弧で指定する。** 裸の `// NOLINT` はすべてのチェックを止めてしまい、後から別の問題が入り込む。

## 17.6　`compile_commands.json` を生成する

### 何のためのファイルか

「どのソースを、どんなオプションでコンパイルするか」を機械可読にしたものだ（第4章のハンズオン手順4で一度見た）。

```json
[
  {
    "directory": "C:/work/pixkit/out/build/x64-debug",
    "command": "C:\\...\\cl.exe /nologo /TP -DPIXKIT_DEBUG=1 -IC:/work/pixkit/libs/core/include ... ppm.cpp",
    "file": "C:/work/pixkit/libs/codec/src/ppm.cpp",
    "output": "libs/codec/CMakeFiles/pixkit-codec.dir/src/ppm.cpp.obj"
  },
  ...
]
```

これがあると、**ビルドとは独立にClang-Tidyを実行できる。**

### 生成する

```cmake
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)
```

第4章のプリセットで、`base` に入れておいた。

```json
"cacheVariables": {
    "CMAKE_EXPORT_COMPILE_COMMANDS": "ON"
}
```

### **Ninja または Makefile 系でしか生成されない**

17.2節と同じ制約だ。**Visual Studio ジェネレータでは生成されない。** MSBuildのビルドモデルが「1ファイル1コマンド」の形に落ちないからである。

これがNinjaを常用する3つ目の理由になる。

| 機能 | Ninja | Visual Studio |
| --- | --- | --- |
| ビルドの速さ | ◎ | ○ |
| `CXX_CLANG_TIDY` | **○** | **×** |
| `compile_commands.json` | **○** | **×** |

### ルートに置く

多くのツール（エディタのLSP、`run-clang-tidy`）は、プロジェクトルートの `compile_commands.json` を探す。ビルドディレクトリからコピーまたはリンクしておくと便利だ。

```cmake
if(PROJECT_IS_TOP_LEVEL AND CMAKE_EXPORT_COMPILE_COMMANDS)
    add_custom_target(copy-compile-commands ALL
        COMMAND ${CMAKE_COMMAND} -E copy_if_different
                "${CMAKE_BINARY_DIR}/compile_commands.json"
                "${CMAKE_SOURCE_DIR}/compile_commands.json"
        COMMENT "compile_commands.json をルートにコピーしています"
    )
endif()
```

`.gitignore` に `compile_commands.json` を追加すること。

## 17.7　`run-clang-tidy` で一括実行する

### ビルド統合との違い

| | `CXX_CLANG_TIDY`（ビルド統合） | `run-clang-tidy` |
| --- | --- | --- |
| いつ走るか | コンパイルのたび | **明示的に実行** |
| 並列化 | ビルドの並列度に従う | **自前で並列実行** |
| 対象の絞り込み | ターゲット単位 | **ファイル名の正規表現** |
| 自動修正 | できない | **`-fix` できる** |
| 用途 | 日常の開発、CIゲート | 一括点検、大規模修正 |

### 使い方

`run-clang-tidy` はLLVMに同梱されるPythonスクリプトだ。

```
run-clang-tidy -p out/build/x64-debug -j 8 "libs/.*"
```

| オプション | 意味 |
| --- | --- |
| `-p <dir>` | `compile_commands.json` のあるディレクトリ |
| `-j <N>` | 並列数 |
| 最後の引数 | 対象ファイルの正規表現 |
| `-fix` | **自動修正する** |
| `-checks=...` | `.clang-tidy` の設定を上書き |
| `-header-filter=...` | 同上 |

### 自動修正を使うときの注意

```
run-clang-tidy -p out/build/x64-debug -fix "libs/.*"
```

`modernize-use-nullptr` や `modernize-use-override` のような機械的な修正には強力だ。ただし、

- **必ずコミットしてから実行する**（差分を確認できるようにする）
- 並列実行で同じヘッダを複数のプロセスが修正すると壊れることがある
- 修正後は必ずビルドとテストを通す

```
git commit -am "before clang-tidy fix"
run-clang-tidy -p out/build/x64-debug -fix "libs/.*"
cmake --workflow --preset x64-debug
git diff
```

### 差分だけ見る運用

既存コードに大量の指摘がある場合、全部直すのは非現実的だ。**変更した行だけを見る**ツールがある。

```
git diff -U0 main | clang-tidy-diff.py -p1 -path out/build/x64-debug
```

`clang-tidy-diff.py` もLLVMに同梱されている。

これをCIに組み込めば、「既存の指摘は無視するが、新しく書いたコードは厳しく見る」という現実的な運用ができる。**新規プロジェクトなら最初から全体を綺麗に保てるので、`pixkit` ではこの仕組みは不要だ。**

## 17.8　ヘッダーオンリーライブラリを解析させる

第10章4節で作った「コンパイル検査ターゲット」が、ここで本領を発揮する。

### なぜ普通には解析されないのか

Clang-Tidyは**翻訳単位（`.cpp`）を解析する。** ヘッダは、それを `#include` している `.cpp` を経由してしか見られない。

`pixkit::core` はヘッダーオンリーなので、`.cpp` が1つもない。したがって、

- `CXX_CLANG_TIDY` を設定しても、解析するものがない
- `compile_commands.json` にもエントリが現れない

**誰も `#include` しなければ、そのヘッダは永遠に解析されない。**

### 解決：コンパイル検査ターゲットを解析対象にする

第10章で作ったものを思い出す。

```cmake
add_library(pixkit-core-compile-check OBJECT
    compile_check/compile_check.cpp
)
target_link_libraries(pixkit-core-compile-check
    PRIVATE pixkit::core pixkit::warnings
)
```

```cpp
// compile_check.cpp
#include <pixkit/core/color.hpp>
#include <pixkit/core/image.hpp>
#include <pixkit/core/pixel.hpp>
#include <pixkit/core/version.hpp>
```

このターゲットは実体のある `.cpp` を持つので、

1. `compile_commands.json` にエントリが作られる
2. `CXX_CLANG_TIDY` が適用される
3. `HeaderFilterRegex` が `pixkit/` にマッチするので、**ヘッダの中身が解析される**

**3つの条件が揃って初めて、ヘッダーオンリーライブラリが解析される。** どれか1つでも欠けると、静かに何も起こらない。

第10章で「インクルード漏れの検出」のために作ったターゲットが、そのまま静的解析の入口になった。**設計が効いている場面だ。**

### 確認方法

```
cmake --preset x64-tidy
type out\build\x64-tidy\compile_commands.json | findstr compile_check
```

エントリがあることを確認する。次に、ヘッダにわざと問題を仕込んでビルドすると、指摘が出るはずだ。ハンズオンで実際にやる。

### テストからも解析される

第14〜15章で書いたテストも `pixkit::core` のヘッダを `#include` している。だからテストターゲット経由でも解析される。

しかし、**テストは `PIXKIT_BUILD_TESTS=OFF` で切られることがある。** コンパイル検査ターゲットは常にビルドされるので、こちらを主たる入口として持っておく価値がある。

## 17.9　Visual Studio のUI統合とCIゲート化

### Visual Studio の設定

第4章5節で触れたベンダーフィールドを使う。

```json
{
  "name": "x64-tidy",
  "inherits": "x64-debug",
  "cacheVariables": {
    "PIXKIT_ENABLE_CLANG_TIDY": "ON"
  },
  "vendor": {
    "microsoft.com/VisualStudioSettings/CMake/1.0": {
      "enableClangTidyCodeAnalysis": true,
      "clangTidyChecks": "-*,bugprone-*,performance-*"
    }
  }
}
```

| キー | 意味 |
| --- | --- |
| `enableClangTidyCodeAnalysis` | VSのバックグラウンドコード分析でClang-Tidyを走らせる |
| `enableMicrosoftCodeAnalysis` | Microsoft独自のコード分析（`/analyze`）も走らせる |
| `clangTidyChecks` | チェックの指定（カンマ区切り） |

これを有効にすると、**エディタ上に波線で指摘が表示され、エラー一覧にも出る。** ビルドを待たずに気づけるので、開発体験は大きく変わる。

**`.clang-tidy` ファイルも認識される**ので、17.4節で書いた設定がそのまま使われる。`clangTidyChecks` を書かなければ `.clang-tidy` の内容が効く。設定を2か所に分散させないため、**本書では `clangTidyChecks` を書かず、`.clang-tidy` に一本化する。**

### CMakeの `CXX_CLANG_TIDY` との関係

紛らわしいので整理する。

| | `CXX_CLANG_TIDY`（CMake） | `enableClangTidyCodeAnalysis`（VS） |
| --- | --- | --- |
| 誰が実行するか | ビルドツール（Ninja） | **Visual Studio** |
| いつ | ビルド時 | バックグラウンド分析時 |
| 結果の出方 | ビルドログの警告 | **エディタの波線、エラー一覧** |
| CIで効くか | **効く** | 効かない |
| VSジェネレータで効くか | 効かない | 効く |

**両方を有効にしてよい。** 役割が違う。VSでの快適な開発体験と、CIでの確実なゲートを両立できる。

### CIでゲート化する

```yaml
  tidy:
    runs-on: windows-2025
    steps:
      - uses: actions/checkout@v4
      - uses: ilammy/msvc-dev-cmd@v1
        with: { arch: x64 }

      - name: clang-tidy のバージョンを確認
        run: clang-tidy --version

      - name: 構成
        run: cmake --preset x64-tidy

      - name: ビルド（Clang-Tidy込み）
        run: cmake --build --preset x64-tidy
```

`.clang-tidy` の `WarningsAsErrors` に指定したカテゴリで指摘が出れば、ビルドが失敗してジョブが落ちる。**これがゲートになる。**

### 段階的に導入する

既存プロジェクトにいきなり入れると、数千件の指摘が出て手がつけられなくなる。順序としては、

1. `WarningsAsErrors` を空にして、まず全体を見る
2. `bugprone-*` の指摘だけ潰す（**バグの可能性が最も高い**）
3. `WarningsAsErrors: bugprone-*` にする
4. 次のカテゴリに進む

新規プロジェクトなら最初から厳しくできる。`pixkit` はその立場だ。

## この章のまとめ

- Clang-Tidyは**MSVCでビルドしながら使える。** コンパイルと並行して、同じソースを別途Clangでパースする。MSVC形式のオプションは `--driver-mode=cl` で解釈させる
- **`CXX_CLANG_TIDY` は Ninja と Makefile 系でしか動かない。** Visual Studio ジェネレータでは黙って無視される。`compile_commands.json` も同じ制約
- `CMAKE_CXX_CLANG_TIDY` は**それ以降に定義されるターゲット**に適用される。個別に外すには **`CXX_CLANG_TIDY` に空文字列を設定する**
- `.clang-tidy` は **`-*` で全部無効にしてから足す。** 外すチェックには理由を持つ。`WarningsAsErrors` は段階的に広げる
- **`HeaderFilterRegex` がなければヘッダは解析されない。** これは最も見落とされやすい設定
- サードパーティは、`pixkit_disable_clang_tidy` による明示的な除外と、`FetchContent_Declare` の **`SYSTEM`** で守る
- 個別抑制は **`// NOLINT(チェック名)`。** 裸の `// NOLINT` を使わない
- **ヘッダーオンリーライブラリの解析には、第10章の「コンパイル検査ターゲット」が必要**。`.cpp` が存在し、それに `CXX_CLANG_TIDY` が設定され、`HeaderFilterRegex` がマッチして初めて解析される
- `run-clang-tidy` はビルドと独立した一括実行に向く。`-fix` は**必ずコミットしてから**
- Visual Studio の `enableClangTidyCodeAnalysis`（ベンダーフィールド）はエディタ上の即時フィードバック、CMakeの `CXX_CLANG_TIDY` はCIゲート。**役割が違うので両方使う**

これで第4部が終わった。`pixkit` は、

- **正しさ**をユニットテストとCTestで守り（第13〜15章）
- **速さ**をベンチマークで測り（第16章）
- **コードの質**をClang-Tidyで機械的に検査する（第17章）

という状態になった。しかもこれらはすべて、`cmake --workflow --preset x64-debug` と `cmake --build --preset x64-tidy` という2つのコマンドに集約され、ローカルとCIで同じように動く。

第5部からは、外の世界との接続に入る。第18章で `find_package` と `FetchContent` の使い分けを整理し、第19〜20章でvcpkgを導入する。ここまで `FetchContent` で取ってきたGoogleTestとGoogle Benchmarkを、vcpkg経由に置き換える作業も行う。
