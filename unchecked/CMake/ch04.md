# 第4章　CMakePresets.json で設定を持ち歩く

## この章のゴール

- `CMakePresets.json` が解決する問題を理解する
- `configurePresets` の主要フィールドを書ける
- `buildPresets` / `testPresets` / `packagePresets` / `workflowPresets` の役割を区別できる
- `hidden` と `inherits` で重複のないプリセットを設計する
- `CMakeUserPresets.json` で個人設定をチームから分離する
- **Visual Studio でもコマンドラインでも、まったく同じビルドを再現できる**状態にする

この章の成果物は、以降の全章で使い続ける `CMakePresets.json` だ。

---

## 4.1　なぜプリセットが必要か

第3章の終わりで指摘した問題を、もう一度はっきりさせる。いま、同じプロジェクトに3種類の「設定」が存在している。

| 誰が | どこにビルドするか | どんな設定で |
| --- | --- | --- |
| あなた（CLI） | `build\` | `-G "Visual Studio 18 2026" -A x64` |
| Visual Studio | `out\build\x64-debug\` | Ninja、Debug |
| CIサーバー（これから作る） | ？ | ？ |

これは「手元では通るのにCIで落ちる」を生産する構造だ。原因の切り分けに時間を溶かすことになる。

### 解決策：設定をリポジトリに置く

`CMakePresets.json` は、**ビルド設定に名前を付けてJSONで記述し、リポジトリにコミットする**仕組みだ。CMake 3.19で導入された。

```
cmake --preset x64-debug          # CLIから
```

```
[VSのドロップダウンで x64-debug を選ぶ]   # IDEから
```

```yaml
- run: cmake --preset x64-debug          # CIから
```

3者が**同一の設定**を使う。ビルドディレクトリも、ジェネレータも、キャッシュ変数も、すべて一致する。

### `CMakeSettings.json` との関係

Visual Studio には、以前から `CMakeSettings.json` というVS独自の設定ファイルがあった。役割は似ているが、**新規プロジェクトで使う理由はもうない**。

| | `CMakeSettings.json` | `CMakePresets.json` |
| --- | --- | --- |
| 策定者 | Microsoft | **CMake本体（Kitware）** |
| 使える場所 | Visual Studio のみ | **VS / VS Code / CLion / CLI / CI** |
| CLIからの利用 | できない | `cmake --preset` |

Microsoftも公式に `CMakePresets.json` を推奨しており、VSは両方あれば `CMakePresets.json` を優先する。本書では `CMakePresets.json` だけを使う。

### バージョン番号について

`CMakePresets.json` にはスキーマの `version` フィールドがある。機能が追加されるたびに上がっていく。

| version | 追加されたもの | 必要なCMake |
| --- | --- | --- |
| 1 | `configurePresets` | 3.19 |
| 2 | `buildPresets`, `testPresets` | 3.20 |
| 3 | `condition`, `include` | 3.21 |
| **6** | **`packagePresets`, `workflowPresets`** | **3.25** |
| 12 | 最新（4.4時点） | 4.4 |

本書では **version 6** を使う。ワークフロープリセット（4.3節）が使えて、かつ十分に枯れているからだ。新しい機能が必要になったら上げればよい。

## 4.2　`configurePresets` を書く

`C:\work\hello\CMakeLists.txt` と同じディレクトリに、`CMakePresets.json` を作る。**このファイル名も完全一致でなければならない。**

まずは最小の1つから。

```json
{
  "version": 6,
  "configurePresets": [
    {
      "name": "x64-debug",
      "displayName": "x64 Debug (Ninja)",
      "generator": "Ninja",
      "binaryDir": "${sourceDir}/out/build/${presetName}",
      "architecture": {
        "value": "x64",
        "strategy": "external"
      },
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Debug",
        "CMAKE_INSTALL_PREFIX": "${sourceDir}/out/install/${presetName}"
      }
    }
  ]
}
```

### 各フィールドの意味

| フィールド | 意味 |
| --- | --- |
| `name` | プリセットの識別子。`--preset` に渡す名前。**必須** |
| `displayName` | IDEに表示される名前。人間向け |
| `generator` | `-G` に相当。`"Ninja"` / `"Visual Studio 18 2026"` |
| `binaryDir` | `-B` に相当。ビルドディレクトリ |
| `architecture` | `-A` に相当 |
| `cacheVariables` | `-D` に相当。キャッシュ変数の辞書 |

### マクロ

`${sourceDir}` や `${presetName}` はプリセット専用のマクロだ。よく使うものを挙げる。

| マクロ | 展開されるもの |
| --- | --- |
| `${sourceDir}` | `CMakePresets.json` があるディレクトリ |
| `${presetName}` | そのプリセットの `name` |
| `${generator}` | ジェネレータ名 |
| `$env{VAR}` | 環境変数 `VAR` |
| `$penv{VAR}` | 親プロセスの環境変数（`environment` で上書きする前の値） |

`"binaryDir": "${sourceDir}/out/build/${presetName}"` という書き方は定番だ。プリセットを増やすたびに、自動的に別のビルドディレクトリが割り当てられる。

### `architecture` の `strategy`

ここは初見で必ず引っかかる。

```json
"architecture": {
  "value": "x64",
  "strategy": "external"
}
```

| strategy | 意味 |
| --- | --- |
| `"set"` | CMakeに `-A x64` として渡す。**Visual Studio ジェネレータ用** |
| `"external"` | CMakeには渡さない。「アーキテクチャは外部（＝呼び出し元の環境）で設定済み」の意味 |

**Ninjaジェネレータは `-A` を受け付けない。** 第2章6節で述べたとおり、Ninjaを使うときは開発者コマンドプロンプトの環境変数でアーキテクチャが決まる。だから `"external"` を指定して、CMakeには渡さないようにする。これを `"set"` にすると、

```
CMake Error: Generator Ninja does not support platform specification, but platform x64 was specified.
```

と怒られる。逆にVisual Studio ジェネレータでは `"set"`（または `architecture` を単に `"x64"` と書く短縮形）を使う。

> **Visual Studio が `"external"` のNinjaプリセットを扱えるのはなぜか**
> VSは自分でVisual Studio の環境を用意してからCMakeを呼ぶので、`"external"` でも正しくx64のツールチェインが使われる。コマンドラインの場合は、x64の開発者コマンドプロンプトから実行する必要がある。

### 使ってみる

```
cd C:\work\hello
cmake --preset x64-debug
```

```
Preset CMake variables:
  CMAKE_BUILD_TYPE="Debug"
  CMAKE_INSTALL_PREFIX="C:/work/hello/out/install/x64-debug"

-- The CXX compiler identification is MSVC 19.50.35211.0
...
-- Build files have been written to: C:/work/hello/out/build/x64-debug
```

`-S` も `-B` も `-G` も書いていないのに、すべて設定されている。ビルドはこうなる。

```
cmake --build out/build/x64-debug
```

しかしビルドディレクトリを手で書くのは、プリセットの意味が半減する。そこで次節だ。

### 利用可能なプリセットの一覧

```
cmake --list-presets
```

```
Available configure presets:

  "x64-debug" - x64 Debug (Ninja)
```

## 4.3　ビルド・テスト・パッケージ・ワークフロー

`configurePresets` 以外にも4種類のプリセットがある。

### `buildPresets`

```json
"buildPresets": [
  {
    "name": "x64-debug",
    "configurePreset": "x64-debug"
  }
]
```

`configurePreset` で「どの構成プリセットに対応するか」を指定する。名前は構成プリセットと同じにしてよい（名前空間が別なので衝突しない）。

```
cmake --build --preset x64-debug
```

これで `binaryDir` を書かずに済む。他に指定できるものを挙げる。

```json
{
  "name": "x64-debug-tests",
  "configurePreset": "x64-debug",
  "targets": [ "pixkit-tests" ],
  "jobs": 8,
  "cleanFirst": false,
  "configuration": "Debug"
}
```

`configuration` は、マルチ構成ジェネレータのときの `--config` に相当する。Ninja（単一構成）では不要だ。

### `testPresets`

```json
"testPresets": [
  {
    "name": "x64-debug",
    "configurePreset": "x64-debug",
    "output": {
      "outputOnFailure": true
    },
    "execution": {
      "noTestsAction": "error",
      "stopOnFailure": false
    }
  }
]
```

```
ctest --preset x64-debug
```

`outputOnFailure` は「失敗したテストの出力を表示する」設定で、これがないとCIのログを見ても何が起きたか分からない。**必ず入れる。** `noTestsAction: "error"` は「テストが1つも見つからなかったら失敗にする」設定で、テストの登録漏れに気づける。

第13章でCTestを扱うときに、このプリセットが活きてくる。

### `packagePresets`

CPack（付録C）用のプリセットだ。本書では付録で扱う。

### `workflowPresets`

構成 → ビルド → テストを**1コマンドで実行する**。

```json
"workflowPresets": [
  {
    "name": "x64-debug",
    "steps": [
      { "type": "configure", "name": "x64-debug" },
      { "type": "build",     "name": "x64-debug" },
      { "type": "test",      "name": "x64-debug" }
    ]
  }
]
```

```
cmake --workflow --preset x64-debug
```

これがCIスクリプトの中身になる。第15章では、GitHub Actions のワークフローファイルがほぼこの1行だけになる。**ローカルで `cmake --workflow --preset x64-debug` が通れば、CIも通る**という状態が理想だ。

## 4.4　`hidden` と `inherits` で重複を消す

プリセットを3つ4つと増やすと、`binaryDir` や `installPrefix` の記述が全部同じで、うんざりしてくる。ここで継承を使う。

### 基底プリセットを作る

```json
{
  "name": "base",
  "hidden": true,
  "binaryDir": "${sourceDir}/out/build/${presetName}",
  "installDir": "${sourceDir}/out/install/${presetName}",
  "cacheVariables": {
    "CMAKE_EXPORT_COMPILE_COMMANDS": "ON"
  }
}
```

`"hidden": true` を付けたプリセットは、

- `--preset` で直接指定できない
- `cmake --list-presets` に出てこない
- IDEのドロップダウンにも出ない
- `generator` や `binaryDir` を持たなくてもエラーにならない

つまり**継承されるためだけに存在する**。

### 継承する

```json
{
  "name": "x64-debug",
  "displayName": "x64 Debug (Ninja)",
  "inherits": "base",
  "generator": "Ninja",
  "architecture": { "value": "x64", "strategy": "external" },
  "cacheVariables": {
    "CMAKE_BUILD_TYPE": "Debug"
  }
}
```

`inherits` は配列も取れる。

```json
"inherits": [ "ninja-base", "x64-base" ]
```

複数指定した場合、**配列の先に書いたものが優先**される。

### `cacheVariables` はマージされる

継承で注意すべき点がある。`cacheVariables` は**辞書としてマージ**される。上の例では、`x64-debug` は次の両方を持つ。

```
CMAKE_EXPORT_COMPILE_COMMANDS = ON   （baseから）
CMAKE_BUILD_TYPE              = Debug（自分自身）
```

同じキーがあれば子が勝つ。これは便利だが、「なぜこの変数が設定されているのか分からない」の原因にもなるので、継承は2段程度に留めるのが実用的だ。

## 4.5　`condition` でプラットフォームを分ける

本書はWindows専用だが、プリセットを他のOSと共有するプロジェクトでは `condition` が要る。

```json
{
  "name": "x64-debug",
  "inherits": "base",
  "generator": "Ninja",
  "condition": {
    "type": "equals",
    "lhs": "${hostSystemName}",
    "rhs": "Windows"
  }
}
```

条件が偽になったプリセットは、`--list-presets` にも出ず、使おうとするとエラーになる。

使える `type` は `const` / `equals` / `notEquals` / `inList` / `matches` / `anyOf` / `allOf` / `not` など。`${hostSystemName}` は `Windows` / `Linux` / `Darwin` を返す。

### Visual Studio 向けの追加指定

VSには独自のベンダーフィールドがあり、プリセットの表示を制御できる。

```json
"vendor": {
  "microsoft.com/VisualStudioSettings/CMake/1.0": {
    "hostOS": [ "Windows" ]
  }
}
```

他のCMake実装はこの `vendor` セクションを**無視する**ので、書いても移植性は損なわれない。

## 4.6　`CMakeUserPresets.json`

`CMakePresets.json` はチームで共有する。しかし個人の都合はどうしても出てくる。

- vcpkgのインストール先が人によって違う（第19章）
- 自分だけAddressSanitizer付きの構成を使いたい
- ビルドディレクトリを高速なDドライブに置きたい

これを `CMakePresets.json` に書くと、他のメンバーの環境を壊す。そこで `CMakeUserPresets.json` を使う。

```json
{
  "version": 6,
  "configurePresets": [
    {
      "name": "my-fast",
      "inherits": "x64-debug",
      "displayName": "x64 Debug (Dドライブ)",
      "binaryDir": "D:/build/hello/${presetName}"
    }
  ]
}
```

| | `CMakePresets.json` | `CMakeUserPresets.json` |
| --- | --- | --- |
| フォーマット | 同一 | 同一 |
| バージョン管理 | **コミットする** | **コミットしない**（`.gitignore` へ） |
| 継承 | — | `CMakePresets.json` のプリセットを継承できる |

**`CMakeUserPresets.json` から `CMakePresets.json` のプリセットは継承できるが、逆はできない。** チーム設定が個人設定に依存してはいけないので、これは自然な制約だ。

VSもCLIも、両方のファイルを読んで**和集合**を表示する。

## 4.7　VS と CLI の対応関係

プリセットを導入すると、IDEの操作とコマンドが1対1で対応する。

| Visual Studio の操作 | 相当するコマンド |
| --- | --- |
| 構成のドロップダウンで選ぶ | `cmake --preset <name>` |
| プロジェクト → CMakeキャッシュの生成 | `cmake --preset <name>` |
| ビルド → すべてビルド | `cmake --build --preset <name>` |
| テスト → テストプリセットの実行 | `ctest --preset <name>` |

### VSでプリセットを有効にする

**ツール → オプション → CMake → 全般** で、`CMakePresets.json` を使う設定になっていることを確認する。設定を変更した場合は、**フォルダを閉じて開き直す**必要がある。

有効になっていれば、ツールバーのドロップダウンに `CMakePresets.json` の `displayName` が並ぶ。

### 動作確認の型

新しいプリセットを追加したら、必ず**両方で**動かして確認する習慣をつける。

```
cmake --preset x64-debug          # CLIで通るか
```

→ VSでフォルダを開き直し、ドロップダウンに出てくるか、構成が通るか

片方でしか確認しないと、`architecture` の `strategy` の指定ミスのように、片方でだけ壊れる問題を見逃す。

## ハンズオン：3つのプリセットを作る

`C:\work\hello` に、本書で使う基本形の `CMakePresets.json` を作る。

### 手順1：`CMakePresets.json` を作成する

```json
{
  "version": 6,
  "cmakeMinimumRequired": {
    "major": 3,
    "minor": 28,
    "patch": 0
  },
  "configurePresets": [
    {
      "name": "base",
      "hidden": true,
      "binaryDir": "${sourceDir}/out/build/${presetName}",
      "installDir": "${sourceDir}/out/install/${presetName}",
      "cacheVariables": {
        "CMAKE_EXPORT_COMPILE_COMMANDS": "ON"
      },
      "vendor": {
        "microsoft.com/VisualStudioSettings/CMake/1.0": {
          "hostOS": [ "Windows" ]
        }
      }
    },
    {
      "name": "ninja-base",
      "hidden": true,
      "inherits": "base",
      "generator": "Ninja",
      "architecture": {
        "value": "x64",
        "strategy": "external"
      }
    },
    {
      "name": "x64-debug",
      "displayName": "x64 Debug (Ninja)",
      "description": "日常の開発用。ビルドが速い",
      "inherits": "ninja-base",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Debug"
      }
    },
    {
      "name": "x64-release",
      "displayName": "x64 Release (Ninja)",
      "description": "性能計測とリリース用",
      "inherits": "ninja-base",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "RelWithDebInfo"
      }
    },
    {
      "name": "x64-vs",
      "displayName": "x64 (Visual Studio 18 2026)",
      "description": "VSのソリューションを生成したいとき。マルチ構成",
      "inherits": "base",
      "generator": "Visual Studio 18 2026",
      "architecture": {
        "value": "x64",
        "strategy": "set"
      }
    }
  ],
  "buildPresets": [
    {
      "name": "x64-debug",
      "configurePreset": "x64-debug"
    },
    {
      "name": "x64-release",
      "configurePreset": "x64-release"
    },
    {
      "name": "x64-vs-debug",
      "configurePreset": "x64-vs",
      "configuration": "Debug"
    },
    {
      "name": "x64-vs-release",
      "configurePreset": "x64-vs",
      "configuration": "Release"
    }
  ],
  "testPresets": [
    {
      "name": "x64-debug",
      "configurePreset": "x64-debug",
      "output": {
        "outputOnFailure": true
      },
      "execution": {
        "noTestsAction": "error"
      }
    }
  ],
  "workflowPresets": [
    {
      "name": "x64-debug",
      "displayName": "Debug: 構成→ビルド→テスト",
      "steps": [
        { "type": "configure", "name": "x64-debug" },
        { "type": "build",     "name": "x64-debug" },
        { "type": "test",      "name": "x64-debug" }
      ]
    }
  ]
}
```

### この設計の意図

いくつか説明しておく。

- **`base` と `ninja-base` の2段継承**
  `x64-vs` はNinja固有の設定（`strategy: external`）を継承したくないので、`base` から直接継承している。
- **`CMAKE_EXPORT_COMPILE_COMMANDS: ON`**
  第17章のClang-Tidyで必要になる `compile_commands.json` を出す設定。Ninjaでのみ効果があり、VSジェネレータでは無視される。今から入れておく。
- **Release ではなく `RelWithDebInfo`**
  最適化を効かせつつデバッグ情報も残す構成。性能計測（第16章）でスタックが読めないと困るので、本書ではこちらを常用する。純粋な `Release` は配布時に使う（第12章）。
- **`x64-vs` を残す理由**
  日常はNinjaで十分速いが、「VSのソリューションが欲しい」場面（プロジェクト構造を俯瞰したい、他のツールに `.sln` を食わせたい）は残るので、切り替えられるようにしておく。

### 手順7：Visual Studio から確認する

1. VSでフォルダを開き直す（すでに開いていれば閉じて開く）
2. ツールバーの構成ドロップダウンに、`x64 Debug (Ninja)` / `x64 Release (Ninja)` / `x64 (Visual Studio 18 2026)` の3つが出ることを確認
3. `x64 Debug (Ninja)` を選び、構成が走ることを確認
4. エクスプローラで `out\build\x64-debug\` が、**CLIで作ったものと同じディレクトリ**であることを確認

第3章では、VSとCLIが別々のビルドディレクトリを使っていた。いまはもう同じだ。**この章の目的はこれである。**

### 手順8：個人用プリセットを試す

`CMakeUserPresets.json` を作る。

```json
{
  "version": 6,
  "configurePresets": [
    {
      "name": "my-debug",
      "inherits": "x64-debug",
      "displayName": "【個人用】x64 Debug",
      "cacheVariables": {
        "CMAKE_CXX_FLAGS": "/W4"
      }
    }
  ]
}
```

```
cmake --list-presets
```

`my-debug` が一覧に加わることを確認する。次に `.gitignore` に追加する。

```gitignore
CMakeUserPresets.json
```

### 発展課題

1. `x64-debug` の `architecture.strategy` を `"set"` に変えて構成し、どんなエラーが出るか読む（4.2節の説明を確認する）
2. `condition` を使って `x64-debug` をLinux専用にし、`--list-presets` から消えることを確認する

## この章のまとめ

- `CMakePresets.json` は、ビルド設定に名前を付けてリポジトリにコミットする仕組み。**VS・CLI・CIが同じ設定を共有できる**
- `CMakeSettings.json` はVS専用の旧方式。新規プロジェクトでは使わない
- 5種類のプリセットがある：`configurePresets`（構成）、`buildPresets`（ビルド）、`testPresets`（テスト）、`packagePresets`（CPack）、`workflowPresets`（一括実行）
- Ninjaでは `architecture.strategy` を `"external"` に、Visual Studio ジェネレータでは `"set"` にする。ここは間違えやすい
- `hidden: true` の基底プリセットと `inherits` で重複を排除する。`cacheVariables` はマージされる
- 個人設定は `CMakeUserPresets.json` に書き、`.gitignore` に入れる
- `cmake --workflow --preset <name>` が、そのままCIのビルドコマンドになる

これで第1部は終わりだ。ここまでで、

- CMakeが何をするものか分かった（第1章）
- 最小のプロジェクトをビルドできる（第2章）
- IDEとCLIの両方で扱える（第3章）
- 設定を再現可能な形で管理できる（第4章）

という土台ができた。第2部では、`CMakeLists.txt` の中身に踏み込む。第5章でCMake言語そのものの文法を、第6章で本書の中核である**ターゲットと使用要件**を扱う。ここからが本番だ。
