# 第20章　vcpkgを実務で使いこなす

## この章のゴール

- **feature** を設計し、利用者が必要な依存だけを取れるようにする
- `builtin-baseline` / `overrides` / `version>=` を使い分け、**バージョンを固定・更新する**
- オーバーレイポートとオーバーレイトリプレットで、標準の挙動を上書きする
- **バイナリキャッシュ**でビルド時間を削る
- 依存ツリーを確認し、ビルド失敗のログを読む
- **CIでvcpkgを運用する**

第19章でvcpkgは動いた。この章は、それを「チームで何年も回せる状態」にする。第23〜24章で自分がポートを作る側に回るための準備でもある。

## 20.1　feature を設計する

### featureとは

**オプションの依存**をまとめた単位だ。第19章で `pixkit` に2つ定義した。

```json
"features": {
  "tests": {
    "description": "ユニットテストをビルドする",
    "dependencies": [ "gtest" ]
  },
  "benchmarks": {
    "description": "ベンチマークをビルドする",
    "dependencies": [ "benchmark" ]
  }
}
```

### 使う側から見たfeature

あなたが `opencv` に依存するとき、こう書ける。

```json
"dependencies": [
  {
    "name": "opencv",
    "default-features": false,
    "features": [ "png", "jpeg" ]
  }
]
```

| 指定 | 意味 |
| --- | --- |
| `"default-features": false` | **既定で有効なfeatureを全部切る** |
| `"features": [...]` | 明示的に有効にするものを列挙 |

opencvのようなライブラリは、既定で大量の機能（と依存）を持ち込む。**必要なものだけに絞ると、ビルド時間が桁違いに変わる。**

### `default-features`

自分のパッケージでも、既定で有効にするfeatureを指定できる。

```json
{
  "name": "pixkit",
  "features": {
    "tests":      { "description": "...", "dependencies": [ "gtest" ] },
    "benchmarks": { "description": "...", "dependencies": [ "benchmark" ] }
  },
  "default-features": []
}
```

**`pixkit` は `default-features` を空にする。** ライブラリの利用者が、テストフレームワークまでインストールさせられる筋合いはない。第14章7節・第19章2節と同じ配慮だ。

### featureの粒度

| 良いfeature | 悪いfeature |
| --- | --- |
| 依存が増減する単位 | 依存が変わらない単なるビルドスイッチ |
| `png` / `jpeg` / `tests` | `optimized` / `verbose-logging` |

**依存が変わらないなら、featureではなくCMakeの `option()` にする。** featureはあくまで「どのライブラリをインストールするか」を決める仕組みだ。

### CMake側との対応

第19章7節で書いたとおり、`VCPKG_MANIFEST_FEATURES` は `project()` より前に設定する。

```cmake
if(NOT DEFINED PIXKIT_BUILD_TESTS OR PIXKIT_BUILD_TESTS)
    list(APPEND VCPKG_MANIFEST_FEATURES "tests")
endif()
```

コマンドラインから直接指定することもできる。

```
vcpkg install --x-feature=tests --x-feature=benchmarks
```

### featureが依存する依存

featureの中でも `version>=` や `default-features` が使える。

```json
"features": {
  "tests": {
    "description": "ユニットテストをビルドする",
    "dependencies": [
      { "name": "gtest", "version>=": "1.17.0" }
    ]
  }
}
```

## 20.2　バージョンの固定と更新

ここがvcpkgの中核であり、最も誤解の多い部分だ。**3つの仕組みがある。**

| 仕組み | 役割 | 強さ |
| --- | --- | --- |
| `builtin-baseline` | **全パッケージの既定バージョン**を1つのコミットで決める | 基準 |
| `version>=` | 「これ以上」の下限を指定する | 引き上げのみ |
| `overrides` | **特定パッケージのバージョンを固定する** | 最強 |

### `builtin-baseline`

公式レジストリのGitコミットハッシュを指定する。「このコミット時点の `versions/baseline.json` に書かれたバージョンを使う」という意味だ。

```json
"builtin-baseline": "a1b2c3d4e5f6789..."
```

**これがバージョン管理の土台になる。** 設定しないと、vcpkgのローカルリポジトリの状態次第でバージョンが変わってしまう。

更新する。

```
vcpkg x-update-baseline
```

**このコマンドは、あなたのローカルのvcpkgリポジトリのHEADをbaselineに書き込む。** だから、更新するときは先にvcpkg自体を更新する。

```
cd %VCPKG_ROOT%
git pull
cd C:\work\pixkit
vcpkg x-update-baseline
cmake --preset x64-debug --fresh
cmake --workflow --preset x64-debug
```

**baselineの更新は、依存ライブラリのバージョンを一斉に上げる操作だ。** 必ずテストを回す。

### `version>=`

```json
"dependencies": [
  { "name": "gtest", "version>=": "1.17.0" }
]
```

baselineのバージョンが 1.16.0 なら 1.17.0 に**引き上げられる**。baselineが 1.18.0 なら、そのまま 1.18.0 が使われる（下げられない）。

**「この機能が必要だから、最低このバージョン」を表明するためのもの**であり、固定ではない。

### `overrides`

```json
"overrides": [
  { "name": "gtest", "version": "1.16.0" }
]
```

**baselineが何であろうと、必ずそのバージョンを使う。** 依存の依存が要求するバージョンも無視される。

使う場面は限られる。

- 新しいバージョンにバグがあり、一時的に戻したい
- 他の依存との組み合わせで問題があり、特定の組み合わせに固定したい
- 検証済みの構成をリリースまで凍結したい

**`overrides` は強力すぎるので、常用しない。** 「なぜこのバージョンに固定したのか」をコメントできないJSONだからこそ、別の場所（READMEやコミットメッセージ）に理由を残しておく。

### バージョンはどこから来るのか

vcpkgのリポジトリには `versions/` というディレクトリがある。

```
versions/
├── baseline.json          ← 各ポートの「既定バージョン」
├── g-/
│   └── gtest.json         ← gtest の全バージョンと、対応するコミット
└── b-/
    └── benchmark.json
```

`versions/g-/gtest.json` の中身はこうなっている。

```json
{
  "versions": [
    {
      "git-tree": "4a2cbb8b6c8e...",
      "version": "1.17.0",
      "port-version": 0
    },
    {
      "git-tree": "8f1e2d3c4b5a...",
      "version": "1.16.0",
      "port-version": 1
    }
  ]
}
```

`git-tree` は、そのバージョンのポート定義（`portfile.cmake` など）が入ったGitツリーのハッシュだ。**vcpkgはこれを使って、過去の任意のバージョンのポートを取り出せる。**

第24章で自分のレジストリを作るとき、この構造を自分で作ることになる。

### `port-version`

```json
{ "version": "1.17.0", "port-version": 2 }
```

**ライブラリ自体のバージョンは同じだが、ポートの定義（パッチやビルド設定）が更新された**ことを表す。表記は `1.17.0#2` となる。

```json
"overrides": [
  { "name": "gtest", "version": "1.17.0", "port-version": 2 }
]
```

### バージョンが解決できないとき

```
error: cannot find a version of gtest that satisfies the constraint version>=1.99.0
```

原因はたいてい次のどれかだ。

| 原因 | 対処 |
| --- | --- |
| baselineが古すぎる | `vcpkg x-update-baseline` |
| そのバージョンが存在しない | `versions/g-/gtest.json` を確認する |
| overridesで指定したバージョンが存在しない | 同上 |

**利用可能なバージョンを調べる。**

```
vcpkg search gtest
```

```
gtest                1.17.0#1         GoogleTest and GoogleMock testing frameworks
```

## 20.3　オーバーレイポートとオーバーレイトリプレット

### オーバーレイポート

**公式のポート定義を、自分のもので上書きする仕組み**だ。

```
C:\work\pixkit\ports\
└── gtest\
    ├── vcpkg.json
    └── portfile.cmake
```

指定する。

```json
{
  "name": "base",
  "cacheVariables": {
    "VCPKG_OVERLAY_PORTS": "${sourceDir}/ports"
  }
}
```

環境変数でも指定できる（Windowsではセミコロン区切り）。

```
set VCPKG_OVERLAY_PORTS=C:\work\pixkit\ports;C:\shared\ports
```

### 使う場面

| 場面 | 説明 |
| --- | --- |
| **上流にパッチを送る前の検証** | 修正版のポートを手元で試す |
| **公式にないライブラリ** | 社内ライブラリなど |
| **公式のビルド設定を変えたい** | オプションを変更したポートを作る |
| **第23章の自作ポートのテスト** | **本書で最も重要な用途** |

第23章8節で `pixkit` 自身のポートを書き、オーバーレイポートとして手元でテストする。**その仕組みをここで先に押さえておく。**

### 注意点

- **オーバーレイポートはバージョン管理の外にある。** `versions/` の情報を持たないので、`overrides` や `version>=` の対象にならない
- オーバーレイで指定したポートは、常にそのバージョンが使われる
- したがって、**恒久的な運用にはカスタムレジストリ（第24章）を使う**

オーバーレイは「一時的な上書き」、レジストリは「正式な配布」と考えるとよい。

### オーバーレイトリプレット

同じ仕組みでトリプレットも追加できる。

```
C:\work\pixkit\triplets\
└── x64-windows-static-md-release.cmake
```

```cmake
set(VCPKG_TARGET_ARCHITECTURE x64)
set(VCPKG_CRT_LINKAGE dynamic)
set(VCPKG_LIBRARY_LINKAGE static)
set(VCPKG_BUILD_TYPE release)          # Releaseだけビルドする
```

```json
"cacheVariables": {
  "VCPKG_OVERLAY_TRIPLETS": "${sourceDir}/triplets",
  "VCPKG_TARGET_TRIPLET": "x64-windows-static-md-release"
}
```

`VCPKG_BUILD_TYPE release` は**インストール時間を半分にする**。第19章5節で述べたとおり、vcpkgは既定でDebugとReleaseの両方をビルドするからだ。

**Release専用のCIジョブでは、この効果が大きい。** ただし、Debugビルドで依存ライブラリのデバッグができなくなるので、開発者の環境では使わない。

### ポート単位で設定を変える

トリプレットファイルの中で `PORT` 変数が使える。

```cmake
set(VCPKG_LIBRARY_LINKAGE static)

# このライブラリだけは動的リンクでなければ動かない
if(PORT MATCHES "^some-plugin-lib$")
    set(VCPKG_LIBRARY_LINKAGE dynamic)
endif()
```

第5章6節で学んだ `MATCHES`（正規表現）が、ここで使われている。

## 20.4　バイナリキャッシュ

### 既定で有効になっている

第19章のハンズオン手順9で見たとおり、**vcpkgのバイナリキャッシュは何も設定しなくても働いている。**

```
Restored 1 package(s) from C:\Users\you\AppData\Local\vcpkg\archives in 850 ms
```

既定の保存先はこの順で決まる。

1. `%VCPKG_DEFAULT_BINARY_CACHE%`
2. `%LOCALAPPDATA%\vcpkg\archives`
3. `%APPDATA%\vcpkg\archives`

### キャッシュのキー

vcpkgは、**そのパッケージのビルド結果に影響するすべて**からハッシュ（ABIハッシュ）を計算する。

- ポートの内容（`portfile.cmake`、パッチ）
- トリプレット
- コンパイラのバージョン
- 依存パッケージのABIハッシュ
- feature の組み合わせ

**どれか1つでも変われば別のキャッシュになる。** だから「コンパイラを更新したら全部ビルドし直しになった」は正常な動作だ。

### `VCPKG_BINARY_SOURCES`

キャッシュの場所と種類を制御する。

```
VCPKG_BINARY_SOURCES=clear;files,C:\vcpkg-cache,readwrite
```

| 要素 | 意味 |
| --- | --- |
| `clear` | **それまでのソース（既定含む）を全部消す** |
| `default[,<rw>]` | 既定の files プロバイダを追加する |
| `files,<絶対パス>[,<rw>]` | ローカルまたはネットワーク共有 |
| `nuget,<URI>[,<rw>]` | NuGetフィード |
| `nugetconfig,<path>[,<rw>]` | NuGet設定ファイル |
| `x-azblob,<baseuri>,<sas>[,<rw>]` | Azure Blob Storage（実験的） |
| `x-gcs,<prefix>[,<rw>]` | Google Cloud Storage（実験的） |

`<rw>` は `read`（既定）/ `write` / `readwrite` のいずれか。

### チームで共有する

ネットワーク共有を使うのが最も手軽だ。

```
VCPKG_BINARY_SOURCES=clear;files,\\fileserver\vcpkg-cache,readwrite
```

**「誰か1人がビルドすれば、全員がその成果を使える。」** 大きなライブラリ（Qt、Boost、OpenCVなど）を使うチームでは、これだけで数十分×人数の時間が浮く。

CIサーバーには `read` だけを与え、書き込みは信頼できるジョブからのみ行う、といった運用もできる。

```
VCPKG_BINARY_SOURCES=clear;files,\\fileserver\vcpkg-cache,read
```

### 無効にする

```
VCPKG_BINARY_SOURCES=clear
```

「キャッシュのせいで古いものが使われているのでは」という疑いを晴らすときに使う。

### ダウンロードキャッシュは別物

バイナリキャッシュ（ビルド済みパッケージ）と、**ダウンロードキャッシュ**（ソースのtarball）は別だ。

```
set VCPKG_DOWNLOADS=D:\vcpkg-downloads
```

こちらも共有すると、ネットワーク帯域が節約できる。

## 20.5　依存ツリーとトラブルシュート

### 依存関係を見る

```
vcpkg depend-info gtest
```

```
gtest:
```

GoogleTestは依存なしだ。もっと大きなものを見るとよく分かる。

```
vcpkg depend-info opencv4
```

```
opencv4: opencv4[core,default-features,dnn,jpeg,png,quirc,tiff,webp], protobuf, quirc, ...
libjpeg-turbo:
liblzma:
libpng: zlib
protobuf: zlib
zlib:
```

出力形式を変えることもできる。

```
vcpkg depend-info opencv4 --format=tree
vcpkg depend-info opencv4 --format=dot > deps.dot
```

**`--format=dot` はGraphvizで画像にできる。** 第6章7節でCMakeの `--graphviz` を使ったのと同じ発想だ。

### いま何が入っているか

```
vcpkg list
```

マニフェストモードでは、プロジェクトのビルドディレクトリを指定する。

```
dir out\build\x64-debug\vcpkg_installed\x64-windows\share
```

各パッケージの `share/<name>/` に、`copyright`（ライセンス）や `usage`（使い方）が置かれている。

**`copyright` ファイルは配布時に重要だ**（第18章7節）。ここを集めれば、依存ライブラリのライセンス表示が作れる。

### ビルド失敗のログを読む

vcpkgのビルドが失敗すると、こう出る。

```
error: building fmt:x64-windows failed with: BUILD_FAILED
See logs for more information:
  C:\work\pixkit\out\build\x64-debug\vcpkg_installed\vcpkg\blds\fmt\config-x64-windows-dbg-CMakeCache.txt.log
  C:\work\pixkit\out\build\x64-debug\vcpkg_installed\vcpkg\blds\fmt\install-x64-windows-dbg-out.log
```

**必ずログのパスが示される。** 読む順番は、

1. `install-*-out.log` — 実際のコンパイルエラー
2. `config-*-out.log` — 構成時のエラー
3. `*-CMakeCache.txt.log` — 設定値の確認

多くの場合、1つ目の末尾にコンパイラのエラーメッセージがそのまま入っている。

### よくある失敗と対処

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| `LNK2038: RuntimeLibrary の不一致` | トリプレットとプロジェクトの `/MD` `/MT` が不一致 | 第19章5節。トリプレットを見直す |
| `Could not find a package configuration file` | ツールチェインが渡っていない | プリセットの `CMAKE_TOOLCHAIN_FILE` を確認 |
| `cannot find a version of X that satisfies` | baselineが古い／バージョンが存在しない | 20.2節 |
| ビルドが毎回走る | ABIハッシュが変わっている | コンパイラ更新、トリプレット変更、feature変更を疑う |
| 古いバージョンが使われる | キャッシュに古いものがある | `--fresh` で構成し直す。それでも駄目なら `vcpkg_installed/` を削除 |
| 特定ポートだけビルドしたい | — | `vcpkg install fmt:x64-windows --overlay-ports=...` |

### 環境をきれいにする

段階的に強くする。

```
cmake --preset x64-debug --fresh              # CMakeキャッシュを捨てる
rmdir /s /q out\build\x64-debug               # ビルドディレクトリごと
rmdir /s /q %LOCALAPPDATA%\vcpkg\archives     # バイナリキャッシュも（最終手段）
```

第2章8節で述べた「困ったら `build` を消す」が、vcpkgでも同じように効く。

## 20.6　CIでvcpkgを運用する

### 問題：毎回全部ビルドすると遅い

CIランナーは毎回まっさらな状態で始まる。依存ライブラリを毎回ソースからビルドすると、数十分かかることも珍しくない。

### 解決：バイナリキャッシュを永続化する

**注意：かつて存在した `x-gha`（GitHub Actions 専用のキャッシュプロバイダ）は、vcpkg から削除されている。** 古い記事にはこれを使う例が多く残っているので、参考にするときは注意する。

現在の現実的な方法は2つある。

**方法A：`actions/cache` と `files` プロバイダを組み合わせる**

```yaml
  build:
    runs-on: windows-2025
    env:
      VCPKG_DEFAULT_BINARY_CACHE: ${{ github.workspace }}/vcpkg-cache

    steps:
      - uses: actions/checkout@v4

      - uses: ilammy/msvc-dev-cmd@v1
        with: { arch: x64 }

      - name: vcpkg を取得する
        uses: actions/checkout@v4
        with:
          repository: microsoft/vcpkg
          path: vcpkg
          fetch-depth: 0

      - name: vcpkg をブートストラップする
        run: .\vcpkg\bootstrap-vcpkg.bat

      - name: キャッシュディレクトリを作る
        run: New-Item -ItemType Directory -Force -Path $env:VCPKG_DEFAULT_BINARY_CACHE

      - name: バイナリキャッシュを復元する
        uses: actions/cache@v4
        with:
          path: ${{ env.VCPKG_DEFAULT_BINARY_CACHE }}
          key: vcpkg-${{ runner.os }}-${{ hashFiles('vcpkg.json') }}-${{ matrix.preset }}
          restore-keys: |
            vcpkg-${{ runner.os }}-${{ hashFiles('vcpkg.json') }}-
            vcpkg-${{ runner.os }}-

      - name: 構成・ビルド・テスト
        env:
          VCPKG_ROOT: ${{ github.workspace }}/vcpkg
        run: cmake --workflow --preset ${{ matrix.preset }}
```

ポイントを挙げる。

| 項目 | 理由 |
| --- | --- |
| `fetch-depth: 0` | **`builtin-baseline` のコミットを取得するために全履歴が要る** |
| `hashFiles('vcpkg.json')` | 依存が変わったらキャッシュキーも変わる |
| `restore-keys` | 完全一致しなくても、近いキャッシュを再利用する |
| `VCPKG_ROOT` を渡す | プリセットの `$env{VCPKG_ROOT}` が解決される（第19章3節） |

**`fetch-depth: 0` を忘れると、次のエラーになる。**

```
error: could not find baseline in commit a1b2c3...
```

**方法B：NuGetフィードを使う**

GitHub Packages や Azure Artifacts をNuGetフィードとして使う。設定はやや複雑だが、

- 複数のリポジトリでキャッシュを共有できる
- `actions/cache` のサイズ制限を受けない

という利点がある。大規模な組織向けだ。

### ビルド時間をさらに削る

```yaml
      - name: 構成
        env:
          VCPKG_ROOT: ${{ github.workspace }}/vcpkg
        run: cmake --preset x64-release-ci
```

Release専用トリプレット（20.3節）を使うプリセットを用意しておく。

```json
{
  "name": "x64-release-ci",
  "inherits": "x64-release",
  "cacheVariables": {
    "VCPKG_OVERLAY_TRIPLETS": "${sourceDir}/triplets",
    "VCPKG_TARGET_TRIPLET": "x64-windows-static-md-release"
  }
}
```

**Debug版をビルドしないので、依存のインストール時間が約半分になる。**

### vcpkg自体のバージョンを固定する

上のワークフローは vcpkg の最新をチェックアウトしている。**再現性を高めるなら、コミットを固定する。**

```yaml
      - uses: actions/checkout@v4
        with:
          repository: microsoft/vcpkg
          ref: a1b2c3d4e5f6...        # vcpkg.json の builtin-baseline と同じコミット
          path: vcpkg
          fetch-depth: 0
```

`builtin-baseline` と同じコミットを指定すれば、**ローカルとCIで完全に同じ依存が入る。**

より実務的には、vcpkgをGitのサブモジュールにする方法もある。

```
git submodule add https://github.com/microsoft/vcpkg.git vcpkg
```

## この章のまとめ

- **feature は「依存が増減する単位」で切る。** 依存が変わらないスイッチはCMakeの `option()` にする。ライブラリなら **`default-features` は空**にして、利用者に余計な依存を強制しない
- バージョン管理は3層。**`builtin-baseline`**（全体の基準）、**`version>=`**（下限、引き上げのみ）、**`overrides`**（強制固定、常用しない）
- `vcpkg x-update-baseline` は**ローカルのvcpkgのHEADを書き込む。** 更新するときは先に `git pull` し、更新後は必ずテストを回す
- **オーバーレイポート**は一時的な上書き（バージョン管理の外）、**カスタムレジストリ**（第24章）が恒久的な配布手段。オーバーレイトリプレットで `VCPKG_BUILD_TYPE release` にすると**インストール時間が半分**になる
- **バイナリキャッシュは既定で有効**（`%LOCALAPPDATA%\vcpkg\archives`）。`VCPKG_BINARY_SOURCES` でネットワーク共有に置けば、**チーム全体でビルド結果を共有できる**
- ビルド失敗時は**必ずログのパスが表示される。** `install-*-out.log` から読む
- CIでは `actions/cache` ＋ `VCPKG_DEFAULT_BINARY_CACHE` を使う。**`x-gha` プロバイダは削除済み**なので、古い記事の設定をそのまま使わない。**`fetch-depth: 0` を忘れると baseline が見つからない**
- ライセンス情報は `vcpkg_installed/<triplet>/share/<name>/copyright` にある
