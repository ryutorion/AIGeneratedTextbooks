# 第19章　vcpkg入門

## この章のゴール

- vcpkgをインストールし、**classicモードとmanifestモード**の違いを理解する
- `vcpkg.json` を書いて依存を宣言する
- **ツールチェインファイル**の役割を理解し、`CMakePresets.json` に組み込む
- Visual Studio 2026 でマニフェストモードを使う
- **トリプレット**（`x64-windows` / `x64-windows-static` / `x64-windows-static-md`）を選べる
- vcpkgが持ってきたDLLを実行時に見つけさせる
- **GoogleTest と Google Benchmark を `FetchContent` から vcpkg に置き換える**

第18章で `find_package` の仕組みを学んだ。vcpkgは、その `find_package` が見つけられる状態を**自動的に作ってくれる**道具だ。魔法ではない。

## 19.1　vcpkgとは何か

### やっていること

vcpkgの動作を一文で言うとこうなる。

> **依存ライブラリのソースを取得し、あなたの構成に合わせてビルドしてインストールし、CMakeがそれを `find_package` で見つけられるようにする。**

第18章のハンズオン手順3〜4で、GoogleTestを手動でビルドして `stage/` にインストールし、`CMAKE_PREFIX_PATH` を渡した。**vcpkgがやっているのは、あれを自動化することだ。**

だから、vcpkgを使っても `CMakeLists.txt` の書き方は変わらない。

```cmake
find_package(GTest CONFIG REQUIRED)
target_link_libraries(pixkit-tests PRIVATE GTest::gtest_main)
```

これはvcpkgを使っていても、使っていなくても同じである。**vcpkg固有のコマンドは1つも登場しない。** この性質は重要だ。あなたのプロジェクトがvcpkgに縛られない。

### インストール

```
git clone https://github.com/microsoft/vcpkg.git C:\dev\vcpkg
cd C:\dev\vcpkg
.\bootstrap-vcpkg.bat
```

`bootstrap-vcpkg.bat` は `vcpkg.exe` をビルド（またはダウンロード）する。数分かかる。

環境変数を設定しておく。**これ以降の設定で何度も参照する。**

```
setx VCPKG_ROOT C:\dev\vcpkg
```

（新しいコマンドプロンプトを開くと有効になる）

確認する。

```
vcpkg version
```

> **Visual Studio 同梱のvcpkg**
> Visual Studio Installer の個別コンポーネントに「vcpkg パッケージ マネージャー」がある。これを入れると、VSに紐づいたvcpkgが使えるようになる。手軽だが、**バージョンをリポジトリで固定しにくい**（VSの更新に追随してしまう）。本書ではGitクローン方式を使う。チーム開発では、全員が同じvcpkgのコミットを使えることが重要だからだ。

### classicモードとmanifestモード

vcpkgには2つの使い方がある。

| | classicモード | manifestモード |
| --- | --- | --- |
| 使い方 | `vcpkg install fmt` | `vcpkg.json` を書く |
| インストール先 | vcpkg配下の共通 `installed/` | **プロジェクトごとの `vcpkg_installed/`** |
| バージョン | 1つのライブラリにつき1バージョン | **プロジェクトごとに別バージョン可** |
| バージョン固定 | できない | **できる**（baseline / overrides） |
| カスタムレジストリ | 使えない | **使える**（第24章） |
| CMakeとの連携 | 手動 | **構成時に自動でインストール** |

**manifestモードを使う。** classicモードは「ちょっと試す」用途に留める。プロジェクトAが `fmt` 10 を、プロジェクトBが `fmt` 11 を必要とする、という状況がclassicモードでは扱えない。

## 19.2　`vcpkg.json` を書く

プロジェクトのルート（`CMakeLists.txt` と同じ場所）に置く。

```json
{
  "$schema": "https://raw.githubusercontent.com/microsoft/vcpkg-tool/main/docs/vcpkg.schema.json",
  "name": "pixkit",
  "version": "0.1.0",
  "description": "小さな画像処理ライブラリ群",
  "homepage": "https://github.com/example/pixkit",
  "license": "MIT",

  "builtin-baseline": "3426db05b996481ca31e95fff3734cf23e0f51bc",

  "dependencies": [],

  "features": {
    "tests": {
      "description": "ユニットテストをビルドする",
      "dependencies": [ "gtest" ]
    },
    "benchmarks": {
      "description": "ベンチマークをビルドする",
      "dependencies": [ "benchmark" ]
    }
  }
}
```

### 主なフィールド

| フィールド | 意味 |
| --- | --- |
| `name` | パッケージ名。**小文字とハイフンのみ** |
| `version` | バージョン。第23章でポート化するときに使う |
| `dependencies` | **常に必要な依存** |
| `features` | **オプションの依存**（19.7節、第20章1節） |
| `builtin-baseline` | **公式レジストリのどのコミット時点のバージョンを使うか** |
| `overrides` | 特定パッケージのバージョンを固定する（第20章2節） |
| `license` | SPDX形式のライセンス識別子 |

### `builtin-baseline` が最重要

これは**公式vcpkgリポジトリのGitコミットハッシュ**だ。「このコミット時点での各ライブラリのバージョンを使う」という宣言になる。

これがないと、vcpkgを更新するたびにライブラリのバージョンが変わってしまう。**第14章2節で `GIT_TAG` を固定した話と、まったく同じ動機だ。**

値を取得する。

```
cd C:\dev\vcpkg
git rev-parse HEAD
```

自動で書き込むこともできる。

```
cd C:\work\pixkit
vcpkg x-update-baseline --add-initial-baseline
```

### `dependencies` の書き方

```json
"dependencies": [
  "fmt",
  {
    "name": "opencv",
    "default-features": false,
    "features": [ "png", "jpeg" ]
  },
  {
    "name": "zlib",
    "version>=": "1.3.1"
  }
]
```

| 書き方 | 意味 |
| --- | --- |
| `"fmt"` | 単純に依存する |
| `"default-features": false` | そのライブラリの既定機能を無効にする |
| `"features": [...]` | 有効にする機能を指定 |
| `"version>=": "1.3.1"` | **最低バージョンの指定**（baselineがこれより古ければ引き上げる） |

**`version>=` は「最低限」であって「固定」ではない。** 固定したいなら `overrides` を使う（第20章2節）。

### `pixkit` の依存は空でよい

`pixkit` 自体は外部ライブラリに依存していない（PPMコーデックも自前、第9章）。テストとベンチマークだけが依存を持つので、それらを **feature** として宣言する。

こうすることで、**ライブラリの利用者は `gtest` をインストールせずに済む。** 第14章7節の `PIXKIT_BUILD_TESTS` と同じ配慮を、パッケージマネージャのレベルで行っている。

## 19.3　ツールチェインファイルとプリセット

### ツールチェインファイルの役割

vcpkgとCMakeをつなぐのは、たった1つのファイルだ。

```
<vcpkg root>/scripts/buildsystems/vcpkg.cmake
```

これを `CMAKE_TOOLCHAIN_FILE` に指定する。**`project()` の呼び出しより前に読まれる必要がある**ので、コマンドラインかプリセットで渡す。

```
cmake -S . -B build -DCMAKE_TOOLCHAIN_FILE=C:/dev/vcpkg/scripts/buildsystems/vcpkg.cmake
```

このファイルが何をしているかというと、

1. `vcpkg.json` があれば、構成時に `vcpkg install` を実行する
2. インストール先（`${CMAKE_BINARY_DIR}/vcpkg_installed/<triplet>`）を **`CMAKE_PREFIX_PATH` に追加する**
3. Windowsでは、実行ファイルの隣にDLLを自動コピーする仕掛けを入れる（19.6節）

**2番が本質だ。** 第18章3節で学んだ探索の仕組みが、そのまま使われている。vcpkgは `find_package` を置き換えるのではなく、`find_package` が見つけられる状態を作っているだけである。

### プリセットに組み込む

第4章で作った `CMakePresets.json` の `base` に追加する。

```json
{
  "name": "base",
  "hidden": true,
  "binaryDir": "${sourceDir}/out/build/${presetName}",
  "installDir": "${sourceDir}/out/install/${presetName}",
  "cacheVariables": {
    "CMAKE_EXPORT_COMPILE_COMMANDS": "ON",
    "CMAKE_TOOLCHAIN_FILE": "$env{VCPKG_ROOT}/scripts/buildsystems/vcpkg.cmake"
  }
}
```

`$env{VCPKG_ROOT}` は第4章2節で学んだプリセットのマクロだ。**環境変数を参照しているので、vcpkgの場所が人によって違っても動く。**

`VCPKG_ROOT` が設定されていない環境では、パスが `/scripts/buildsystems/vcpkg.cmake` になって失敗する。分かりやすいエラーにするなら、条件を付ける。

```json
{
  "name": "vcpkg",
  "hidden": true,
  "cacheVariables": {
    "CMAKE_TOOLCHAIN_FILE": "$env{VCPKG_ROOT}/scripts/buildsystems/vcpkg.cmake"
  },
  "condition": {
    "type": "notEquals",
    "lhs": "$env{VCPKG_ROOT}",
    "rhs": ""
  }
}
```

`condition`（第4章5節）で、環境変数がないときはそのプリセット自体を無効にする。

### 主なCMake変数

ツールチェインファイルが提供する変数のうち、押さえておくべきものを挙げる。

| 変数 | 既定値 | 意味 |
| --- | --- | --- |
| `VCPKG_TARGET_TRIPLET` | 自動判定 | どのトリプレットを使うか（19.5節） |
| `VCPKG_HOST_TRIPLET` | ネイティブ | ビルドツール用のトリプレット |
| `VCPKG_MANIFEST_MODE` | `vcpkg.json` があれば `ON` | マニフェストモードを使うか |
| `VCPKG_MANIFEST_INSTALL` | `VCPKG_MANIFEST_MODE` に従う | **構成時に自動でインストールするか** |
| `VCPKG_MANIFEST_FEATURES` | 空 | **有効にするfeature（19.7節）** |
| `VCPKG_INSTALLED_DIR` | `${CMAKE_BINARY_DIR}/vcpkg_installed` | インストール先 |
| `VCPKG_APPLOCAL_DEPS` | **`ON`** | 実行ファイルの隣にDLLを自動コピー（19.6節） |

`VCPKG_MANIFEST_INSTALL` が既定で `ON` なので、**`cmake --preset x64-debug` を実行するだけで依存がインストールされる。** 別途 `vcpkg install` を打つ必要はない。

## 19.4　Visual Studio 2026 で使う

プリセットに `CMAKE_TOOLCHAIN_FILE` を書いてあれば、**Visual Studio は何も追加設定なしでvcpkgを使う。** 第4章で「VSもCLIも同じ設定を共有する」状態を作った効果がここにも及ぶ。

フォルダを開き直して構成すると、出力ウィンドウ（CMake）にvcpkgのログが流れる。

```
1> [CMake] -- Running vcpkg install
1> [CMake] Detecting compiler hash for triplet x64-windows...
1> [CMake] Restored 0 package(s) from C:\Users\...\AppData\Local\vcpkg\archives in 0 us
1> [CMake] Installing 1/2 gtest:x64-windows...
1> [CMake] Building gtest:x64-windows...
1> [CMake] -- Running vcpkg install - done
```

**初回はライブラリをソースからビルドするので時間がかかる。** GoogleTestなら1〜2分、大きなライブラリなら数十分になることもある。2回目以降はバイナリキャッシュ（第20章4節）が効いて数秒で終わる。

### 進捗が見えないとき

大きなライブラリのビルド中、出力が止まったように見えることがある。実際には動いている。詳細を見たい場合は、コマンドラインから構成すれば逐次表示される。

### VSのvcpkg統合機能

Visual Studio には、vcpkgの依存を一覧表示する機能もある。ただし本書の構成（プリセット経由）では、**特別な設定は何も要らない。** ツールチェインファイルさえ渡っていれば、あとはCMakeの世界で完結する。

## 19.5　トリプレット

### トリプレットとは

「どのアーキテクチャ向けに、どういうリンク方法でビルドするか」を表す名前だ。

```
x64-windows
```

Windows向けの主なトリプレットは4つある。**中身は実際にvcpkgのリポジトリで確認できる。**

| トリプレット | ライブラリ | CRT | 意味 |
| --- | --- | --- | --- |
| **`x64-windows`**（既定） | 動的（DLL） | 動的（`/MD`） | 標準。DLLが配布物に必要 |
| **`x64-windows-static`** | 静的（`.lib`） | 静的（`/MT`） | 単体で動く実行ファイル |
| **`x64-windows-static-md`** | 静的（`.lib`） | **動的（`/MD`）** | DLL不要だがCRTは共有 |
| `x64-windows-release` | 動的 | 動的 | **Releaseのみビルド**（時間半減） |

`triplets/x64-windows-static-md.cmake` の中身はこうなっている。

```cmake
set(VCPKG_TARGET_ARCHITECTURE x64)
set(VCPKG_CRT_LINKAGE dynamic)
set(VCPKG_LIBRARY_LINKAGE static)
```

### 第12章5節の議論とつながる

**トリプレットの選択は、`/MD` か `/MT` かの選択そのものだ。**

第12章5節で述べた原則を思い出してほしい。

- あなたのプロジェクトが `/MD`（CMakeの既定）なら、vcpkgも `/MD` でなければならない
- 混ざると `LNK2038: RuntimeLibrary の不一致` になる

| あなたのプロジェクト | 選ぶトリプレット |
| --- | --- |
| `/MD`（既定）、DLLを配布してよい | **`x64-windows`** |
| `/MD`（既定）、DLLを減らしたい | **`x64-windows-static-md`** |
| `/MT`（`CMAKE_MSVC_RUNTIME_LIBRARY` を変更した） | `x64-windows-static` |

**`x64-windows-static-md` は見落とされがちだが、実務では最も使いやすいことが多い。** 依存ライブラリのDLLを配らずに済み、かつCRTは標準の `/MD` のままでいられる。

### 指定する

```json
{
  "name": "x64-debug",
  "inherits": "ninja-base",
  "cacheVariables": {
    "CMAKE_BUILD_TYPE": "Debug",
    "VCPKG_TARGET_TRIPLET": "x64-windows"
  }
}
```

**トリプレットを変えたら、ビルドディレクトリを作り直す。** `vcpkg_installed/` の中身がトリプレットごとに分かれるうえ、キャッシュに古い情報が残るからだ。

```
cmake --preset x64-debug --fresh
```

### Debug と Release の両方がビルドされる

vcpkgは既定で、1つのトリプレットにつき **Debug版とRelease版の両方**をビルドする。だから初回のインストールが遅い。

Releaseしか要らないなら `x64-windows-release` を使うか、カスタムトリプレット（第20章3節）で `VCPKG_BUILD_TYPE release` を指定する。CIでは効果が大きい。

## 19.6　DLLを実行時に見つけさせる

`x64-windows` トリプレットを使うと、依存ライブラリはDLLになる。第11章7節で扱った「実行時にDLLが見つからない」問題が再発しそうだが、**vcpkgはこれを自動で解決する。**

```cmake
option(VCPKG_APPLOCAL_DEPS "Automatically copy dependencies into the output directory for executables." ON)
```

これはvcpkgのツールチェインファイルにある実際の定義だ。**既定で `ON`。** 実行ファイルをビルドすると、必要なDLLが自動的に隣にコピーされる。

第11章7節で `$<TARGET_RUNTIME_DLLS:...>` を使って自前でやったのと、目的は同じである。vcpkgは自分が管理するDLLについて、これを肩代わりしてくれる。

### インストール時のコピー

`cmake --install`（第21章）でDLLもコピーしたい場合は、別のオプションが要る。

```cmake
set(X_VCPKG_APPLOCAL_DEPS_INSTALL ON)
```

こちらは既定 `OFF` で、名前のとおり実験的な機能だ。第21章5節で配布物の構成を考えるときに再訪する。

### 自動コピーを止めたいとき

```cmake
set(VCPKG_APPLOCAL_DEPS OFF)
```

ビルドが遅くなる、コピーが競合する、といった問題が起きた場合に使う。その場合はDLLの配置を自分で管理することになる。

## 19.7　`FetchContent` から vcpkg へ移行する

ここが本章の実践部分だ。第18章9節で `FIND_PACKAGE_ARGS` を追加してあるので、**`CMakeLists.txt` の変更はほとんど要らない。**

### 移行の流れ

```
1. vcpkg.json に feature として gtest / benchmark を宣言する
2. CMake側で VCPKG_MANIFEST_FEATURES を設定する
3. ツールチェインファイルをプリセットに追加する
4. 構成する → vcpkg が gtest をインストールする
   → FIND_PACKAGE_ARGS の find_package が成功する
   → ダウンロードが行われなくなる
```

**`FetchContent_Declare` は消さない。** vcpkgのない環境（vcpkgを使いたくない利用者）でも、そのままビルドできる状態を保てる。

### featureをCMakeから有効にする

`VCPKG_MANIFEST_FEATURES` は、**`project()` の呼び出しより前**に設定しなければならない。ツールチェインファイルが `project()` の中で `vcpkg install` を実行するからだ。

```cmake
cmake_minimum_required(VERSION 3.28)

# ---- vcpkg の feature を選ぶ（project() より前） ----
if(NOT DEFINED PIXKIT_BUILD_TESTS)
    set(PIXKIT_BUILD_TESTS ON)          # option() より前なので既定値を仮置きする
endif()

if(PIXKIT_BUILD_TESTS)
    list(APPEND VCPKG_MANIFEST_FEATURES "tests")
endif()
if(PIXKIT_BUILD_BENCHMARKS)
    list(APPEND VCPKG_MANIFEST_FEATURES "benchmarks")
endif()

project(pixkit VERSION 0.1.0 LANGUAGES CXX)
```

**この「`project()` より前」という制約は、CMakeの設計上とても扱いにくい。** `option()` はまだ呼べないし、`PROJECT_IS_TOP_LEVEL` も未定義だ。

現実的な書き方は、キャッシュ変数を直接見ることになる。

```cmake
cmake_minimum_required(VERSION 3.28)

# vcpkg の feature 選択（project() より前に評価する必要がある）
if(NOT DEFINED PIXKIT_BUILD_TESTS OR PIXKIT_BUILD_TESTS)
    list(APPEND VCPKG_MANIFEST_FEATURES "tests")
endif()
if(PIXKIT_BUILD_BENCHMARKS)
    list(APPEND VCPKG_MANIFEST_FEATURES "benchmarks")
endif()

project(pixkit VERSION 0.1.0 LANGUAGES CXX)

option(PIXKIT_BUILD_TESTS      "テストをビルドする"       ${PROJECT_IS_TOP_LEVEL})
option(PIXKIT_BUILD_BENCHMARKS "ベンチマークをビルドする" ${PROJECT_IS_TOP_LEVEL})
```

`-DPIXKIT_BUILD_TESTS=OFF` を渡した場合、キャッシュ変数として `project()` より前に見えるので正しく判定される。初回で何も指定していない場合は `tests` を有効にする、という挙動になる。

**プリセットで明示的に指定しておくのが最も確実だ。**

```json
{
  "name": "x64-debug",
  "cacheVariables": {
    "PIXKIT_BUILD_TESTS": "ON",
    "PIXKIT_BUILD_BENCHMARKS": "OFF"
  }
}
```

### 移行後に何が変わるか

| | `FetchContent` | vcpkg |
| --- | --- | --- |
| 初回の構成 | 十数秒（ダウンロード） | 数分（ソースからビルド） |
| **2回目以降** | ビルドディレクトリを消すと再取得 | **バイナリキャッシュから数秒** |
| ビルド対象 | 自分のビルドに含まれる | **別プロセスでビルド済み** |
| ターゲット | `gtest` などが自分のプロジェクトに現れる | **現れない**（インポートターゲットのみ） |
| バージョン管理 | `GIT_TAG` | baseline / overrides |

**「ターゲットが現れない」のは大きな利点だ。** 第14章8節で述べた副作用（IDEが賑やかになる、警告設定が漏れる、`install()` が汚染される、オプション名が衝突する）が、まるごと消える。

第17章5節で `pixkit_disable_clang_tidy(gtest gtest_main ...)` を書いたが、これも不要になる。**そもそもそれらのターゲットが存在しないからだ**（`if(TARGET ...)` で守ってあるので、書いたままでも害はない）。

## この章のまとめ

- **vcpkgがやっているのは、依存をビルドしてインストールし、`CMAKE_PREFIX_PATH` を設定すること。** 第18章の `find_package` の仕組みがそのまま使われている
- **manifestモードを使う。** `vcpkg.json` に依存を宣言し、`vcpkg_installed/` にプロジェクトごとインストールされる
- **`builtin-baseline` を必ず設定する。** `vcpkg x-update-baseline --add-initial-baseline` で追加できる。これがバージョン固定の土台になる
- 連携の要は **`CMAKE_TOOLCHAIN_FILE`**（`<vcpkg root>/scripts/buildsystems/vcpkg.cmake`）。プリセットの `cacheVariables` に `$env{VCPKG_ROOT}` を使って書く
- **トリプレットの選択は `/MD` か `/MT` かの選択そのもの。** `x64-windows`（動的・`/MD`）、`x64-windows-static`（静的・`/MT`）、**`x64-windows-static-md`（静的ライブラリ・`/MD`）**。不一致は `LNK2038` になる
- **`VCPKG_APPLOCAL_DEPS` は既定 `ON`。** vcpkgのDLLは自動的に実行ファイルの隣にコピーされる
- `VCPKG_MANIFEST_FEATURES` は **`project()` より前**に設定する必要がある。プリセットでオプションを明示しておくのが確実
- **`FIND_PACKAGE_ARGS`（第18章6節）と組み合わせると、vcpkgのある環境とない環境の両方で動く。** `FetchContent_Declare` は消さない
- vcpkgに移行すると、`FetchContent` の副作用（ターゲットの増加、警告の漏れ、`install()` の汚染）が消える

次の第20章では、vcpkgを実務レベルで使いこなす。featureの設計、バージョンの固定と更新、オーバーレイポート、バイナリキャッシュ、依存ツリーのトラブルシュート、CIでの運用を扱う。第5部の締めくくりであり、第23〜24章で「ポートを作る側」に回るための準備でもある。
