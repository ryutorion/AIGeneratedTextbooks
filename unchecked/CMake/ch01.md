# 第1章　CMakeとは何か

## この章のゴール

- CMakeが「ビルドシステム」ではなく「ビルドシステムジェネレータ」であることを説明できる
- `.sln` / `.vcxproj` 中心の開発と何が違うのかを言葉にできる
- 「モダンCMake」という言葉が何を指しているのかを理解する
- Visual Studio 2026 とコマンドラインの両方で、CMakeが動く状態を作る

まだ `CMakeLists.txt` は書かない。書くのは次の章からだ。この章では、これから何を学ぶのか、そしてなぜそれが必要なのかをはっきりさせておく。ここを飛ばしても手は動くが、飛ばした人は3か月後に「なんとなく動いているが誰も触れない `CMakeLists.txt`」を作ることになりやすい。

---

## 1.1　ビルドシステムと「ビルドシステムジェネレータ」

### ビルドとは何をすることか

C++のビルドは、乱暴に言えば次の2段階だ。

1. **コンパイル**：`.cpp` を1つずつ機械語に変換して `.obj` を作る
2. **リンク**：`.obj` とライブラリをつなぎ合わせて `.exe` や `.dll` を作る

ソースが1つなら、コマンドラインでこう書けば終わる。

```
cl /std:c++latest /EHsc hello.cpp
```

しかしソースが200個になると、話が変わる。

- 200回 `cl` を呼ぶ順序を管理しなければならない
- `a.cpp` だけ直したときに、200個すべてを再コンパイルするのは無駄だ
- しかし `common.h` を直したときは、それを `#include` している全部を再コンパイルしなければならない
- Debug版とRelease版でフラグが違う
- x64版とARM64版で出力先を分けたい

この「**何を、どういう順序で、どういう条件のときに実行するか**」を管理する仕組みが**ビルドシステム**だ。代表的なものを挙げる。

| ビルドシステム | 入力ファイル | 主な使われ方 |
| --- | --- | --- |
| MSBuild | `.vcxproj`（XML） | Visual Studio の標準 |
| Make | `Makefile` | Unix系の古典 |
| Ninja | `build.ninja` | 高速。人間が手書きすることは想定していない |

### CMakeはビルドシステムではない

ここが最初の、そして最大の勘違いポイントだ。**CMakeは上の表に入らない。** CMakeはビルドを実行しない。CMakeがやるのは、`CMakeLists.txt` という1つの記述から、上の表のような**ビルドシステムの入力ファイルを生成すること**だ。

```
                       ┌─→ MSBuild用 .vcxproj / .sln  ─→ MSBuild ─→ .exe
CMakeLists.txt ─ CMake ─┼─→ Ninja用 build.ninja        ─→ Ninja   ─→ .exe
                       └─→ Makefile                    ─→ make    ─→ .exe
```

だからCMakeは正確には**ビルドシステムジェネレータ**と呼ばれる。この「生成する側」という立ち位置が、CMakeのすべての設計に効いてくる。

たとえば、これから何度も出会う次の性質は、すべてここから来ている。

- **`CMakeLists.txt` を編集したら、まず「構成(configure)」をやり直す必要がある**
  生成物である `.vcxproj` や `build.ninja` を作り直さないと、変更が反映されないからだ。
- **生成された `.vcxproj` は編集してはいけない**
  次のconfigureで上書きされて消える。編集すべきは常に `CMakeLists.txt` の側だ。
- **`.vcxproj` はバージョン管理に入れない**
  ソースではなく生成物（ビルド成果物）だからだ。

> **覚えておくこと**
> Visual Studio でCMakeプロジェクトを扱うとき、`.vcxproj` は「コンパイラに渡す引数の中間表現」でしかない。人間が向き合うのは `CMakeLists.txt` だけになる。

## 1.2　`.sln` / `.vcxproj` 中心の開発が抱える課題

CMakeを学ぶ動機を、はっきりさせておこう。Visual Studioのソリューションとプロジェクトは、GUIで完結する限り極めて快適だ。問題は、そこから一歩出た瞬間に起きる。

### 課題1：設定がどこにあるのか分からなくなる

MSVCのプロジェクト設定は、次の場所に分散して格納され、しかも継承される。

- プロジェクトのプロパティ（構成×プラットフォームの組み合わせごと）
- プロパティシート（`.props`）
- ソリューション単位の設定
- 環境変数

「なぜかReleaseだけリンクが通らない」の原因が、3年前に誰かが `Release|x64` にだけ追加した `/FORCE:MULTIPLE` だった、という事故が起きる。GUIは、**設定されていない項目と、親から継承した項目と、明示的に上書きした項目の区別**を、太字という頼りない手がかりでしか示してくれない。

### 課題2：差分がレビューできない

`.vcxproj` はXMLだ。プロパティを1つ変えただけで、GUIDの並びやItemGroupの順序が変わることがある。プルリクエストで `.vcxproj` の差分が200行出てきたとき、そこに危険な変更が紛れていないと言い切れる人は多くない。

### 課題3：組み合わせが増えると破綻する

構成（Debug/Release/RelWithDebInfo）× プラットフォーム（x64/ARM64）× 静的/動的 × テスト有無、と掛け合わせていくと、GUIでの設定は現実的でなくなる。「x64のReleaseだけ設定し忘れる」は必ず起きる。

### 課題4：Visual Studio の外に持ち出せない

- CIサーバーにVisual Studioを丸ごと入れるのか？
- clang-clでもビルドして警告を比べたい
- そのライブラリを社外にも配りたい。相手はVisual Studioを使っていない
- 静的解析ツールに `compile_commands.json` を渡したい（第17章で必要になる）

`.vcxproj` はMSBuild専用の入力であり、これらのどれにも答えられない。

### 課題5：外部ライブラリの取り込みが手作業になる

GoogleTestを使いたい。ヘッダのインクルードパスを追加し、`.lib` のパスを追加し、リンクするライブラリ名を追加し、Debug/Releaseで別の `.lib` を指定し、DLLを出力ディレクトリにコピーする。これを**構成×プラットフォームの数だけ**繰り返す。ライブラリが5つになれば、もう誰も全体を把握できない。

### ただし、`.vcxproj` が悪いわけではない

強調しておきたいのは、**`.vcxproj` そのものは優秀なビルドシステムの入力形式**だということだ。問題は「人間が手で書き、手で保守する」点にある。CMakeを導入しても `.vcxproj` は消えない。ただ、それは**生成物**になり、人間が触らなくてよいものになる。Visual Studio の快適なデバッガも、ソリューションエクスプローラも、そのまま使える。失うものは基本的にない。

## 1.3　CMakeが解決すること／解決しないこと

過度な期待は失望を生むので、範囲をはっきりさせておく。

### CMakeが解決すること

| できること | 本書で扱う章 |
| --- | --- |
| 1つの記述から Visual Studio / Ninja / Makefile を生成する | 第2章 |
| ビルド設定をテキストで記述し、差分をレビュー可能にする | 全章 |
| ライブラリの「使い方」（インクルードパス、必要な定義、依存）を、ライブラリ自身に持たせて自動的に伝播させる | 第6章 |
| 静的／動的／ヘッダーオンリーの切り替えを構造的に扱う | 第9〜11章 |
| テストの登録と実行（CTest） | 第13章 |
| 外部ライブラリの発見と取り込み（`find_package` / `FetchContent`） | 第18章 |
| インストールとパッケージ化、他人が `find_package` で使える形での配布 | 第21〜22章 |

### CMakeが解決しないこと

- **依存ライブラリのダウンロードとビルド**
  CMakeは「あるライブラリを見つける」ことはできるが、「取ってくる」のは本来の仕事ではない。ここを埋めるのがvcpkg（第19章）やFetchContent（第14章）だ。
- **コンパイラの差異の完全な吸収**
  `/W4` と `-Wall` は別物だ。CMakeはこれを自動で翻訳しない。抽象化されるのは「C++23を使う」のような、概念として共通する部分だけだ（第7章）。
- **設計の悪さ**
  巨大な密結合のコードベースは、CMakeにしても巨大な密結合のままだ。ただ、ターゲット間の依存関係が `CMakeLists.txt` に明示されるので、**どこが絡まっているかは見えるようになる**。

### そして、CMakeの言語は美しくない

正直に書いておく。CMakeのスクリプト言語は、20年以上の後方互換性を引きずっており、癖が強い。すべての値は文字列で、リストはセミコロン区切りの文字列で、`if` の条件式には独特のルールがある（第5章で正面から扱う）。

しかし本書の立場ははっきりしている。**CMake言語の全機能を使いこなす必要はない。** 実務で必要なのは、`CMakeLists.txt` の9割を占める十数個のコマンドを正確に使うことであり、それは十分に学べる量だ。

## 1.4　「モダンCMake」とは — ディレクトリ中心からターゲット中心へ

Web検索でCMakeの情報を探すと、書き方がまったく違う2つの流派に出会う。これが初学者を最も混乱させる。

### 古い書き方（ディレクトリ中心）

```cmake
# これは「悪い例」。真似しないこと
include_directories(${CMAKE_SOURCE_DIR}/include)
add_definitions(-DUSE_FEATURE_X)
link_directories(${CMAKE_SOURCE_DIR}/lib)

add_executable(app main.cpp)
target_link_libraries(app mylib)
```

`include_directories` や `add_definitions` は、**そのディレクトリと、その下のすべてのディレクトリの、すべてのターゲット**に影響する。つまりグローバル変数と同じだ。ターゲットが3つなら問題は起きない。50個になると、「なぜこのターゲットにこのマクロが定義されているのか誰も分からない」状態になる。

### 新しい書き方（ターゲット中心）

```cmake
# これが本書の書き方
add_library(mylib STATIC src/mylib.cpp)

target_include_directories(mylib
    PUBLIC  include      # mylibを使う人にも必要
    PRIVATE src          # mylibのビルドにだけ必要
)
target_compile_definitions(mylib PRIVATE USE_FEATURE_X)

add_executable(app main.cpp)
target_link_libraries(app PRIVATE mylib)
```

こちらは、設定がすべて**特定のターゲットに結びついている**。そして重要なのは `PUBLIC` / `PRIVATE` の区別だ。

`mylib` の `target_include_directories` に `PUBLIC include` と書いてあるので、`app` は `target_link_libraries(app PRIVATE mylib)` と書くだけで、**`include` へのインクルードパスを自動的に受け取る**。`app` 側で `include_directories` を書く必要はない。

この「ライブラリが自分の使い方を知っていて、リンクした相手に自動的に伝える」性質を**使用要件（usage requirements）**と呼ぶ。これがモダンCMakeの核心であり、本書が第6章をまるごと使って扱うテーマだ。

> **記事を読むときの判定基準**
> ネット上のCMake記事を見たら、まず `include_directories` と `target_include_directories` のどちらを使っているかを見る。前者なら、その記事は少なくとも2014年以前の作法で書かれている。内容が古いとは限らないが、そのままコピーしてはいけない。

## 1.5　CMake 4系での注意点

本書はCMake 4.4系を前提にする。CMake 3系の記事や書籍は大量に存在するが、4系では実際に**動かなくなった**ものがあるので、先に押さえておく。

### 3.5未満との互換性が削除された

CMake 4.0で、**CMake 3.5より古いバージョンとの互換性が削除された**。具体的には、`CMakeLists.txt` の先頭がこうなっているプロジェクトは、**エラーで止まる**。

```cmake
cmake_minimum_required(VERSION 3.0)   # CMake 4系ではエラー
```

GitHubから拾ってきた少し古いライブラリが、これでビルドできないことがある。応急処置として、次の変数で最低ポリシーバージョンを底上げできる。

```
cmake -S . -B build -DCMAKE_POLICY_VERSION_MINIMUM=3.5
```

ただしこれは**その場しのぎ**だ。そのプロジェクトが3.0時代の挙動を前提にしている場合、動くように見えて微妙に壊れる可能性がある。本来は上流を修正すべきで、この変数は「上流の修正を待つ間だけ」使うものだと理解しておく。

### 本書が要求するバージョン

本書は `cmake_minimum_required(VERSION 3.28)` を基準にする。なぜ3.28なのかというと、本書で使う機能の要求バージョンが次のようになっているからだ。

| 機能 | 必要なCMake | 使う章 |
| --- | --- | --- |
| `$<TARGET_RUNTIME_DLLS:...>`（DLLの実行時コピー） | 3.21 | 第11章 |
| `FILE_SET HEADERS`（ヘッダのインストール） | 3.23 | 第21章 |
| `workflowPresets` / `packagePresets` | 3.25 | 第4章 |
| `FETCHCONTENT_TRY_FIND_PACKAGE_MODE` | 3.24 | 第18章 |
| `CMAKE_MSVC_DEBUG_INFORMATION_FORMAT` など各種ポリシーの安定 | 3.25以降 | 第12章 |

「最低バージョンは低いほど親切」と思いがちだが、それは**古い書き方を強制されること**とのトレードオフだ。Windows + Visual Studio 2026 環境で新規に始めるなら、低くする理由はない。

### `cmake_minimum_required` の本当の意味

ここで誤解を1つ潰しておく。`cmake_minimum_required(VERSION 3.28)` は「CMake 3.28以上をインストールしてください」という意味**だけ**ではない。より重要なのは、**「CMake 3.28時点のポリシー（挙動のルール）で解釈してください」**という宣言である点だ。

CMakeは後方互換性を保つため、挙動を変えるときに「ポリシー」という仕組みを使う。`CMP0077` のような番号が振られ、`cmake_minimum_required` で指定したバージョン以前のポリシーは「新しい挙動」で、それ以降は「古い挙動（＋警告）」で動く。つまりこの1行は、**プロジェクト全体の解釈モードを決めるスイッチ**だ。だから必ず最初の行に書く。

## 1.6　Visual Studio 2026 のインストール

### 必要なワークロード

Visual Studio Installer を起動し、**「C++によるデスクトップ開発」** ワークロードにチェックを入れる。これで最低限のC++コンパイラとWindows SDKが入る。

### 追加で選ぶ個別コンポーネント

「個別のコンポーネント」タブで、次を確認する。本書ではすべて使う。

| コンポーネント | 使う章 | 補足 |
| --- | --- | --- |
| **Windows用C++ CMakeツール** | 全章 | CMake本体とNinjaが入る。必須 |
| **C++ Clang-cl ビルドツール** | 第17章 | Clang-Tidyも同梱される |
| **Windows 11 SDK**（最新版） | 全章 | ワークロードで自動的に入るはず |
| **C++ AddressSanitizer** | 第15章（任意） | 必須ではないが便利 |

「Windows用C++ CMakeツール」を外すと、`.vcxproj` は作れてもCMakeプロジェクトが開けない。ここは必ず入れる。

### C++23を使うための確認

本書はC++23を使う。Visual Studio 2026 のC++コンパイラ（ツールセット **v145**）は、`std::print` や `std::expected` を含む主要なC++23機能を実装している。ただし**標準ライブラリの実装状況は機能ごとに異なる**ので、`std::mdspan` のような比較的新しいものを使う際は、実際にコンパイルして確かめるのが確実だ。第7章で、有効になっているC++のバージョンをコードから確認する方法を扱う。

なお、C++モジュール（`import std;` など）は本書では**使わない**。理由は第7章5節で説明する。ここでは「使わない方針である」とだけ覚えておいてほしい。

## 1.7　コマンドラインの準備

Visual Studio のGUIだけでもCMakeは使える。しかし本書では、**必ずコマンドラインからも同じことができる状態**を作る。理由は3つある。

1. CMakeが実際に何をしているかは、コマンドラインの方がはるかに見えやすい
2. CIサーバー（第15章）にはGUIがない
3. GUIの表示が期待と違うとき、CLIで確かめれば「CMakeの問題」か「IDE統合の問題」かを切り分けられる

### 開発者コマンドプロンプトを使う

スタートメニューから **「Developer Command Prompt for VS 2026」** または **「Developer PowerShell for VS 2026」** を起動する。

普通のコマンドプロンプトではなく、これを使う理由は明快だ。MSVCのコンパイラ `cl.exe` は、単体では動かない。次の環境変数が設定されている必要がある。

| 環境変数 | 意味 |
| --- | --- |
| `PATH` | `cl.exe`、`link.exe` の場所 |
| `INCLUDE` | 標準ヘッダとWindows SDKヘッダの場所 |
| `LIB` | 標準ライブラリとWindows SDKライブラリの場所 |

開発者コマンドプロンプトは、これらを設定した状態で起動するシェルだ。

> **ハマりどころ**
> 「普通のPowerShellでcmakeを実行したらコンパイラが見つからないと言われる」は、CMake入門者が最初に踏む地雷の1つだ。ただし、後述する `Visual Studio 18 2026` ジェネレータを使う場合はCMakeが自動的にVisual Studioを探すため、普通のシェルでも動く。**Ninjaジェネレータのときだけ**、開発者コマンドプロンプトが必須になる。この違いは第2章6節で詳しく扱う。

### CMakeが2つ入る問題

注意すべき点がある。CMakeは次の2経路で入ることがあり、**バージョンが違う**。

1. Visual Studio 2026 に同梱されるCMake（VSのインストールディレクトリ配下）
2. [cmake.org](https://cmake.org/download/) からインストールしたCMake（`C:\Program Files\CMake\bin`）

開発者コマンドプロンプトでは前者が、普通のコマンドプロンプトでは後者が使われる、という状況が起きうる。「VSでは通るのにコマンドラインでは通らない」の原因がこれであることは多い。

どちらを使ってもよいが、**どちらを使っているか把握しておく**こと。確認方法は次のとおり。

```
where cmake
cmake --version
```

本書では、CMake 4.4以降であればどちらでもかまわない。

## ハンズオン：環境が揃っていることを確認する

ここからは実際に手を動かす。所要時間は5分程度だ。

### 手順1：開発者コマンドプロンプトを開く

スタートメニュー →「Developer Command Prompt for VS 2026」

### 手順2：CMakeのバージョンを確認する

```
cmake --version
```

**期待する出力**（バージョン番号は環境による）:

```
cmake version 4.4.3

CMake suite maintained and supported by Kitware (kitware.com/cmake).
```

- **4.x が表示されればOK。**
- 3.x が表示された場合：古いCMakeがPATHの先にいる。`where cmake` で確認し、PATHを整理するか、cmake.orgから最新版を入れる。
- 「'cmake' は内部コマンドまたは外部コマンドとして認識されていません」：Visual Studio Installer で「Windows用C++ CMakeツール」を追加する。

### 手順3：利用可能なジェネレータを確認する

```
cmake --help
```

出力の末尾に `Generators` の一覧が出る。次の2つがあることを確認する。

```
  Visual Studio 18 2026        = Generates Visual Studio 2026 project files.
                                 Use -A option to specify architecture.
* Ninja                        = Generates build.ninja files.
```

`*` は既定のジェネレータを示す。

> `Visual Studio 18 2026` という名前に戸惑うかもしれない。「18」は**Visual Studio の内部バージョン番号**（VS 2022 は 17、VS 2019 は 16）で、「2026」は製品名だ。このジェネレータはCMake 4.2で追加された。もし一覧に出てこないなら、CMakeが4.2より古い。

### 手順4：コンパイラを確認する

```
cl
```

**期待する出力**:

```
Microsoft(R) C/C++ Optimizing Compiler Version 19.xx.xxxxx for x64
Copyright (C) Microsoft Corporation.  All rights reserved.

usage: cl [ option... ] filename... [ /link linkoption... ]
```

`for x64` の部分を確認しておく。`for x86` なら32bit用のシェルを開いている。本書はx64を前提にするので、「x64 Native Tools Command Prompt for VS 2026」を使うのが確実だ。

### 手順5：Ninjaを確認する

```
ninja --version
```

**期待する出力**: `1.12.1` のようなバージョン番号。

Ninjaは第4章と第17章（Clang-Tidy用の `compile_commands.json` 生成）で必要になる。

### 手順6：Clang-Tidyを確認する（第17章の先取り）

```
clang-tidy --version
```

**期待する出力**:

```
LLVM (http://llvm.org/):
  LLVM version 19.x.x
  Optimized build.
```

見つからない場合は、Visual Studio Installer で「C++ Clang-cl ビルドツール」を追加する。第17章まで使わないので、今すぐでなくてもよい。

### チェックリスト

## この章のまとめ

- CMakeは**ビルドシステムジェネレータ**であり、`CMakeLists.txt` から `.vcxproj` や `build.ninja` を生成する。生成物は編集しないし、バージョン管理にも入れない。
- `.vcxproj` を手で保守する開発は、設定の分散・差分のレビュー不能・IDE外で使えない、という問題を抱える。CMakeはこれを解く。
- モダンCMakeとは、`include_directories` のようなディレクトリ単位のグローバル設定をやめ、`target_*` コマンドで**ターゲットに設定を結びつける**書き方のこと。ライブラリが自分の使い方を伝える「使用要件」が中心概念になる。
- CMake 4系では3.5未満との互換性が削除されている。本書は `cmake_minimum_required(VERSION 3.28)` を使う。
- Visual Studio 2026 では「C++によるデスクトップ開発」＋「Windows用C++ CMakeツール」が必要。ジェネレータ名は `Visual Studio 18 2026`、既定ツールセットは **v145**。

次の第2章では、実際に3行の `CMakeLists.txt` を書き、コマンドラインだけで `hello.exe` をビルドする。IDEを使うのはその次の章からだ。CMakeが何をしているのかを、まず自分の目で見てもらう。
