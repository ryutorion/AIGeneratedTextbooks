# 第24章　カスタムレジストリで公開・運用する

## この章のゴール

- レジストリの仕組み（Gitレジストリ／ファイルシステムレジストリ）を理解する
- `ports/` と `versions/` のディレクトリ構造、`baseline.json` の役割を知る
- **`vcpkg x-add-version` でバージョンを登録する**
- 利用側の `vcpkg-configuration.json` を書く
- バージョン更新とベースライン運用、破壊的変更の扱いを設計する
- GitHub Actions でポートを自動テストする
- 公式レジストリ（microsoft/vcpkg）へPRを出す場合の追加要件を知る
- リリース前チェックリストを作る

本書の最終章だ。第23章で作ったポートを、**チームや世界に向けて公開する。**

## 24.1　レジストリの仕組み

### レジストリとは何か

**ポートの集合と、そのバージョン履歴を持つリポジトリ**だ。第19〜20章で使ってきた「公式レジストリ」（microsoft/vcpkg）も、その1つにすぎない。

```
レジストリ = ports/（ポート定義） + versions/（バージョン履歴）
```

利用者は複数のレジストリを組み合わせられる。

```
既定のレジストリ（microsoft/vcpkg）  → gtest, benchmark, fmt, ...
自社のレジストリ                     → pixkit, other-internal-lib
```

### 3つの種類

| 種類 | `kind` | 用途 |
| --- | --- | --- |
| **組み込み** | `builtin` | vcpkg同梱の公式レジストリ |
| **Git** | `git` | **Gitリポジトリ。最も一般的** |
| **ファイルシステム** | `filesystem` | ローカルディレクトリ。試作・社内共有 |

**本書はGitレジストリを作る。** ファイルシステムレジストリは手軽だが、バージョン履歴を `git-tree` で管理できないので、本格運用には向かない。

### オーバーレイポートとの違い

第20章3節・第23章8節で使ったオーバーレイポートと、何が違うのか。

| | オーバーレイポート | カスタムレジストリ |
| --- | --- | --- |
| 指定方法 | 利用者が `--overlay-ports` を渡す | **`vcpkg-configuration.json` に書く** |
| バージョン管理 | **なし**（常に1つのバージョン） | **あり**（履歴・baseline・overrides） |
| 複数バージョンの共存 | できない | **できる** |
| 用途 | 一時的な上書き、開発中の検証 | **恒久的な配布** |

**オーバーレイは開発用、レジストリは公開用**だ。第23章で `--overlay-ports` を使ったのは、レジストリを作る前の検証段階だったからである。

## 24.2　レジストリのディレクトリ構造

```
pixkit-registry/
├── ports/
│   └── pixkit/
│       ├── vcpkg.json
│       ├── portfile.cmake
│       └── usage
└── versions/
    ├── baseline.json
    └── p-/
        └── pixkit.json
```

### `ports/`

第23章で作ったポートを、そのまま置く。**複数のポートを1つのレジストリに入れられる。**

```
ports/
├── pixkit/
├── our-network-lib/
└── our-logging-lib/
```

### `versions/<prefix>-/<name>.json`

**ポート名の頭文字**でディレクトリを分ける。`pixkit` なら `p-/pixkit.json` だ。ファイル数が増えたときのファイルシステム負荷を分散するための工夫である。

```json
{
  "versions": [
    {
      "git-tree": "a3f5c9e1b2d4867fa0c3e5d7b9f1a2c4e6d8b0f2",
      "version": "0.1.0",
      "port-version": 0
    }
  ]
}
```

| フィールド | 意味 |
| --- | --- |
| `git-tree` | **そのバージョンのポート定義が入ったGitツリーのSHA** |
| `version` | 上流のバージョン（`version-semver` / `version-date` / `version-string` も可） |
| `port-version` | **ポート定義の改訂番号**（第20章2節） |

### `git-tree` の意味

これがレジストリの核心だ。**Gitのツリーオブジェクトのハッシュ**を記録している。

```
git -C ports ls-tree --format='%(objectname)' <commit> -- pixkit
```

vcpkgはこのハッシュを使って、**過去の任意のバージョンのポート定義を取り出せる。** `ports/pixkit/` の中身が変わっても、古い `git-tree` を指せば当時の定義が復元される。

だから、

- **ポートを更新しても、古いバージョンを使い続けられる**
- `overrides` で「0.1.0 を使え」と指定すれば、その時点のポートが使われる

**この仕組みがあるから、`ports/` は常に最新版だけを持てばよい。** バージョンごとにディレクトリを分ける必要はない。

### `versions/baseline.json`

```json
{
  "default": {
    "pixkit": {
      "baseline": "0.1.0",
      "port-version": 0
    }
  }
}
```

**「バージョンを指定しなかった場合に使うバージョン」**を定義する。第19章2節の `builtin-baseline` が指していたのは、公式レジストリのこのファイルだ。

`"default"` は必須のキーで、Gitレジストリでは基本的にこれだけを使う。

## 24.3　`vcpkg x-add-version` でバージョンを登録する

`versions/` の中身を手で書く必要はない。**コマンドが生成してくれる。**

```
cd C:\work\pixkit-registry
vcpkg x-add-version pixkit
```

このコマンドは、

1. `ports/pixkit/vcpkg.json` からバージョンを読む
2. **`ports/pixkit/` の現在のGitツリーハッシュを計算する**
3. `versions/p-/pixkit.json` に追記する
4. `versions/baseline.json` を更新する

### 前提：コミットしてから実行する

`git-tree` はコミットされた内容から計算されるので、**未コミットの変更があると失敗する。**

```
error: The port pixkit has uncommitted changes.
```

正しい手順はこうだ。

```
git add ports/pixkit
git commit -m "pixkit 0.1.0"
vcpkg x-add-version pixkit
git add versions
git commit --amend --no-edit
```

**`--amend` で1つのコミットにまとめる**のが慣習だ。「ポートの変更」と「バージョンの登録」が別コミットだと、途中の状態で `git-tree` が合わなくなる。

### `--overwrite-version`

同じバージョンを登録し直したいとき（ポート定義を修正したが、`port-version` を上げたくない開発中など）に使う。

```
vcpkg x-add-version pixkit --overwrite-version
```

**公開後には使わない。** 「同じバージョン番号なのに中身が違う」という状態を作ってしまう。

### すべてのポートを登録する

```
vcpkg x-add-version --all
```

レジストリ全体を検査して、登録漏れがあれば追加する。CIで使うと、登録忘れを検出できる（24.6節）。

## 24.4　利用側の `vcpkg-configuration.json`

利用者がレジストリを使うには、`vcpkg-configuration.json` を書く。

```json
{
  "default-registry": {
    "kind": "builtin",
    "baseline": "3426db05b996481ca31e95fff3734cf23e0f51bc"
  },
  "registries": [
    {
      "kind": "git",
      "repository": "https://github.com/example/pixkit-registry.git",
      "baseline": "9f8e7d6c5b4a39281706f5e4d3c2b1a098765432",
      "packages": [ "pixkit" ]
    }
  ]
}
```

| フィールド | 意味 |
| --- | --- |
| `default-registry` | **どこにも該当しないパッケージの取得元** |
| `registries[].kind` | `git` / `filesystem` / `builtin` |
| `registries[].repository` | GitのURL |
| `registries[].baseline` | **そのレジストリの「どのコミットの baseline.json を使うか」** |
| `registries[].packages` | **このレジストリから取るパッケージ名の一覧** |

### `packages` が振り分けを決める

```json
"packages": [ "pixkit" ]
```

「`pixkit` はこのレジストリから、それ以外は `default-registry` から」という振り分けになる。**同じ名前のパッケージが複数のレジストリにあっても、曖昧にならない。**

`"packages": [ "our-*" ]` のようなパターンも使える（vcpkgのバージョンによる）。

### `baseline` はコミットハッシュ

紛らわしいが、**`registries[].baseline` に書くのはブランチ名ではなくコミットハッシュ**だ。`versions/baseline.json` の内容を「どの時点で」読むかを指定している。

```
cd C:\work\pixkit-registry
git rev-parse HEAD
```

### 置き場所

| ファイル | 置き場所 |
| --- | --- |
| `vcpkg.json` | プロジェクトルート |
| `vcpkg-configuration.json` | **同じくプロジェクトルート** |

`vcpkg.json` の中に埋め込むこともできる。

```json
{
  "name": "my-app",
  "version": "1.0.0",
  "dependencies": [ "pixkit", "fmt" ],
  "vcpkg-configuration": {
    "default-registry": {
      "kind": "builtin",
      "baseline": "3426db05b996481ca31e95fff3734cf23e0f51bc"
    },
    "registries": [
      {
        "kind": "git",
        "repository": "https://github.com/example/pixkit-registry.git",
        "baseline": "9f8e7d6c5b4a39281706f5e4d3c2b1a098765432",
        "packages": [ "pixkit" ]
      }
    ]
  }
}
```

**ファイルが1つで済むので、こちらのほうが管理しやすい。** ただし、`vcpkg-configuration.json` を別にすると、複数のプロジェクトで共有しやすくなる。

### `builtin-baseline` との関係

`vcpkg-configuration.json` で `default-registry` を明示した場合、`vcpkg.json` の `builtin-baseline` は**使われなくなる**。二重に書く必要はない。

## 24.5　バージョンを更新する

### リリースの流れ

`pixkit` を 0.2.0 にする場合の手順を整理する。

**1. ライブラリ側（`pixkit` リポジトリ）**

```cmake
project(pixkit VERSION 0.2.0 ...)
```

```
git commit -am "bump version to 0.2.0"
git tag v0.2.0
git push origin main v0.2.0
```

第8章4節で `configure_file` によりバージョンをコード側に伝播させたので、**`version.hpp` は自動的に追随する。**

**2. ポート側（`pixkit-registry` リポジトリ）**

```json
{
  "name": "pixkit",
  "version": "0.2.0",
  ...
}
```

`portfile.cmake` の `REF "v${VERSION}"` は `${VERSION}` を参照しているので、**書き換え不要**だ（第23章2節）。

SHA512は変わるので、更新する。

```cmake
SHA512 0
```

```
vcpkg install pixkit --overlay-ports=ports
```

エラーメッセージから新しいハッシュを取り、書き戻す。

**3. バージョンを登録する**

```
git add ports/pixkit
git commit -m "pixkit 0.2.0"
vcpkg x-add-version pixkit
git add versions
git commit --amend --no-edit
git push
```

**4. 利用側**

```
cd C:\work\my-app
```

`vcpkg-configuration.json` の `baseline` を新しいコミットに更新する。

```json
"baseline": "（pixkit-registry の新しい HEAD）"
```

```
cmake --preset x64-debug --fresh
```

### `port-version` を上げる場合

**ライブラリのコードは変わっていないが、ポート定義を直した**とき。

- ビルドオプションの修正
- パッチの追加
- `usage` の修正

```json
{
  "name": "pixkit",
  "version": "0.1.0",
  "port-version": 1,
  ...
}
```

```
vcpkg x-add-version pixkit
```

利用者から見ると `0.1.0#1` になる。**上流のバージョンとポートの改訂を分離できる**のが、この仕組みの価値だ。

### 破壊的変更の扱い

第22章4節で `COMPATIBILITY SameMajorVersion` を選んだ。この方針に従うなら、

| 変更の種類 | バージョン |
| --- | --- |
| APIの削除・シグネチャ変更 | **メジャーを上げる**（0.x → 1.0） |
| 機能追加（後方互換） | マイナーを上げる |
| バグ修正 | パッチを上げる |
| ポート定義のみの修正 | `port-version` を上げる |

**0.x.y の間はメジャーが0のまま**なので、`SameMajorVersion` の保護が弱い。セマンティックバージョニングでは「0.x は不安定」という約束なので、それでよい。**1.0.0 を出す時点で、APIを固める覚悟が要る。**

### 古いバージョンを使い続けたい利用者

```json
"overrides": [
  { "name": "pixkit", "version": "0.1.0" }
]
```

第20章2節の仕組みが、自社のレジストリでもそのまま使える。**`git-tree` を記録してあるので、当時のポート定義が復元される**（24.2節）。

## 24.6　GitHub Actions でポートをテストする

レジストリのCIは、**ライブラリ本体のCIとは別に必要**だ。ポートが壊れていても、ライブラリのテストは通ってしまう。

`.github/workflows/test-ports.yml`

```yaml
name: Test ports

on:
  push:
    branches: [ main ]
  pull_request:

jobs:
  test:
    runs-on: windows-2025
    strategy:
      fail-fast: false
      matrix:
        triplet:
          - x64-windows
          - x64-windows-static
          - x64-windows-static-md

    steps:
      - uses: actions/checkout@v4

      - name: vcpkg を取得する
        uses: actions/checkout@v4
        with:
          repository: microsoft/vcpkg
          path: vcpkg
          fetch-depth: 0

      - name: ブートストラップ
        run: .\vcpkg\bootstrap-vcpkg.bat

      - name: バージョン登録の漏れを検査する
        run: .\vcpkg\vcpkg.exe x-add-version --all --verify-version-database

      - name: ポートをビルドする
        run: >
          .\vcpkg\vcpkg.exe install pixkit:${{ matrix.triplet }}
          --overlay-ports=ports
          --x-install-root=${{ github.workspace }}/installed

      - name: 消費者プロジェクトで検証する
        run: |
          cmake -S test/consumer -B out/consumer -G Ninja `
                -DCMAKE_BUILD_TYPE=Release `
                -DCMAKE_TOOLCHAIN_FILE=vcpkg/scripts/buildsystems/vcpkg.cmake `
                -DVCPKG_OVERLAY_PORTS=${{ github.workspace }}/ports `
                -DVCPKG_TARGET_TRIPLET=${{ matrix.triplet }}
          cmake --build out/consumer
```

### ポイント

**1. 3つのトリプレットで回す**

第23章6節・9節で確認した「static / dynamic 両対応」を、CIで守る。**片方だけ壊れる変更は、手元では気づきにくい。**

**2. バージョン登録の検査**

```
vcpkg x-add-version --all --verify-version-database
```

`versions/` の内容が `ports/` と整合しているかを検査する。**`vcpkg x-add-version` を忘れてマージしてしまう事故**を防ぐ。これはレジストリのCIで最も価値のあるステップだ。

**3. 消費者プロジェクトでの検証**

第22章7節と同じ考え方だ。**インストールできることと、使えることは別。**

**4. `fetch-depth: 0`**

第20章6節と同じ理由。baselineのコミットを解決するために全履歴が要る。

### バイナリキャッシュ

ポートのビルドは時間がかかる。第20章6節の設定をそのまま使える。

```yaml
    env:
      VCPKG_DEFAULT_BINARY_CACHE: ${{ github.workspace }}/vcpkg-cache
```

ただし、**ポート自体を変更するとABIハッシュが変わる**ので、キャッシュは効かない。効くのは依存パッケージ（`vcpkg-cmake` など）の部分だけだ。

## 24.7　公式レジストリへPRを出す場合

`pixkit` を世界に公開したいなら、microsoft/vcpkg にPRを出す選択肢がある。**追加の要件がある。**

### 必須の条件

| 要件 | 内容 |
| --- | --- |
| **公開されていること** | ソースが誰でも取得できる |
| **ライセンスが明確** | `vcpkg.json` の `license` にSPDX識別子を書く |
| **安定したバージョン** | タグが打たれている（ブランチを指さない） |
| **SHA512の固定** | `vcpkg_from_github` にハッシュを書く |
| **ダウンストリームを壊さない** | 既存のポートに影響しない |

### 品質の要件

- **ポリシーチェックをすべて通る**（第23章4〜5節で潰したもの）
- 主要なトリプレットでビルドできる（`supports` で対象外を宣言すればよい）
- `usage` ファイルを提供する
- **`vcpkg x-add-version` によるバージョン登録が正しい**

### 出す前にやること

```
vcpkg format-manifest ports/pixkit/vcpkg.json
```

`vcpkg.json` を公式のフォーマットに整形する。**フィールドの順序やインデントが規約に合わせられる。** これをやっていないPRはレビューで指摘される。

```
vcpkg x-add-version pixkit --overwrite-version
```

公式レジストリでは、PRのたびにバージョン登録が必要になる。

### 出さないという選択

**すべてのライブラリが公式レジストリに入る必要はない。**

| 状況 | 選択 |
| --- | --- |
| 社内ライブラリ | **カスタムレジストリ**（この章の内容） |
| 特定の顧客向け | カスタムレジストリ（非公開リポジトリ） |
| 広く使われることを目指す | 公式レジストリへPR |
| 実験的・不安定 | 自分のレジストリで様子を見る |

公式レジストリに入ると、**あなたのライブラリの更新がvcpkgのリリースサイクルに縛られる**という側面もある。カスタムレジストリなら、自分のペースで更新できる。

## 24.8　リリース前チェックリスト

`pixkit` を 0.2.0 として出す前に確認することを、本書全体から拾い上げる。

### ビルドとテスト

- [ ] `cmake --workflow --preset x64-debug` が通る（第15章6節）
- [ ] `cmake --workflow --preset x64-release` が通る
- [ ] `BUILD_SHARED_LIBS` の ON / OFF 両方でテストが通る（第15章4節）
- [ ] `cmake --build --preset x64-tidy` が通る（第17章）
- [ ] ベンチマークがビルドでき、極端な劣化がない（第16章）

### パッケージ

- [ ] `cmake --install` の出力に、意図しないファイルが混ざっていない（第21章6節）
- [ ] 内部ヘッダ（`detail/`）がインストールされていない（第21章手順6）
- [ ] GoogleTest / Google Benchmark がインストールされていない（第14章4節、第16章2節）
- [ ] ライセンスファイルがインストールされている（第21章5節）
- [ ] Debug / Release の両方をインストールしても衝突しない（`DEBUG_POSTFIX`、第22章8節）

### `find_package` 対応

- [ ] 消費者プロジェクトがビルドできる（第22章7節）
- [ ] エクスポートされた名前が `pixkit::core` になっている（`EXPORT_NAME`、第22章2節）
- [ ] バージョン照合が期待どおり動く（第22章4節）
- [ ] 依存が増えていれば `find_dependency` を追加した（第22章5節）

### vcpkgポート

- [ ] `vcpkg.json` の `version` が更新されている
- [ ] SHA512 が新しいタグのものになっている（第23章2節）
- [ ] `x64-windows` / `x64-windows-static` / `x64-windows-static-md` でビルドできる（第23章9節）
- [ ] `usage` の内容が正しい（第23章7節）
- [ ] `vcpkg x-add-version` を実行し、`versions/` をコミットした（24.3節）

### ドキュメント

- [ ] `README.md` の使い方が最新
- [ ] 破壊的変更があれば、変更履歴に記載した
- [ ] `CHANGELOG` を更新した

**このチェックリストの各項目が、本書の各章に対応している。** 逆に言えば、本書はこのチェックリストを作れるようになるために書かれている。

## ハンズオン：レジストリを作って公開する

### 手順1：レジストリのリポジトリを作る

```
mkdir C:\work\pixkit-registry
cd C:\work\pixkit-registry
git init
mkdir ports
mkdir versions
```

### 手順2：ポートを移す

第23章で作ったポートをコピーする。

```
xcopy /e /i C:\work\pixkit\ports\pixkit C:\work\pixkit-registry\ports\pixkit
```

**`portfile.cmake` を本番用に直す。** ローカルパス（`file:///C:/work/pixkit`）のままではレジストリとして機能しない。

本書のハンズオンでは、GitHubに公開していない前提で進めるため、`vcpkg_from_git` でローカルリポジトリを指したままにする。**実際に公開するときは `vcpkg_from_github` に切り替える。**

## この章のまとめ

- レジストリは **`ports/`（ポート定義）＋ `versions/`（バージョン履歴）**。種類は `builtin` / `git` / `filesystem` で、**Gitレジストリが標準**
- **オーバーレイポートは開発用、レジストリは公開用。** レジストリだけがバージョン履歴を持てる
- `versions/<prefix>-/<name>.json` に **`git-tree`**（ポート定義のGitツリーSHA）を記録する。**これがあるから、`ports/` は最新版だけを持てばよく、過去のバージョンも復元できる**
- `versions/baseline.json` は「バージョンを指定しなかったときのバージョン」
- **`vcpkg x-add-version` が `versions/` を生成する。** 手で書かない。**コミットしてから実行し、`git commit --amend` でまとめる**
- 利用側は **`vcpkg-configuration.json`**（または `vcpkg.json` の `vcpkg-configuration` フィールド）で、`default-registry` と `registries` を宣言する。**`packages` が振り分けを決める**
- 更新は「ライブラリのタグ → ポートの `version` と SHA512 → `x-add-version` → 利用側の `baseline`」の順
- **`port-version`** は、上流のバージョンを変えずにポート定義だけ直したときに上げる
- レジストリのCIでは、**3つのトリプレットでのビルド**と **`x-add-version --all --verify-version-database`** による登録漏れ検査を回す
- 公式レジストリへのPRには追加要件がある（`vcpkg format-manifest`、SHA512の固定、ポリシーチェック）。**すべてのライブラリが公式に入る必要はない**

# 本書のまとめ

`pixkit` は、第2章の3行の `CMakeLists.txt` から始まった。24章を経て、いまはこうなっている。

```json
{
  "dependencies": [ "pixkit" ]
}
```

```cmake
find_package(pixkit CONFIG REQUIRED)
target_link_libraries(app PRIVATE pixkit::codec pixkit::filter)
```

**利用者が書くのは、これだけだ。** インクルードパスもライブラリのパスも、C++23の指定も、Debug/Releaseの切り替えも、DLLの配置も、すべて自動的に解決される。

この2行の裏側にあるものを、本書は順に積み上げてきた。

| 部 | 積み上げたもの |
| --- | --- |
| 第1部 | ビルドシステムジェネレータという役割、再現可能な設定（プリセット） |
| 第2部 | **ターゲットと使用要件** — 本書の中核 |
| 第3部 | 3種類のライブラリ形態と、構成による作り分け |
| 第4部 | テスト・ベンチマーク・静的解析による品質の担保 |
| 第5部 | 依存関係の管理と再現性 |
| 第6部 | インストール・エクスポート・パッケージ公開 |

とりわけ第6章の **`PUBLIC` / `PRIVATE` / `INTERFACE`** は、全編を通じて繰り返し現れた。

- 第9〜11章：公開ヘッダと内部ヘッダの境界
- 第7章：警告設定は `PRIVATE`、規格は `PUBLIC`
- 第11章：`*_STATIC_DEFINE` を `PUBLIC` にしないと静的リンクが壊れる
- 第22章：`PUBLIC` の依存は `find_dependency` で再解決する

**「この設定は、使う人にも必要か」**——この問いに正しく答え続けることが、モダンCMakeそのものだった。

ここから先は、あなたのプロジェクトで同じことをする番だ。付録には、本書で使ったコマンドの早見表、ジェネレータ式のチートシート、CPackによるインストーラ作成、よくあるエラーと対処、既存の `.vcxproj` からの移行、完成版の `CMakeLists.txt` 一覧を収めた。手元に置いて使ってほしい。
