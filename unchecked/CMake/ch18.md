# 第18章　外部ライブラリの取り込み方を整理する

## この章のゴール

- `find_package` の**Moduleモードと Configモード**の違いを説明できる
- Configパッケージが提供する**インポートターゲット**の正体を理解する
- `CMAKE_PREFIX_PATH` / `<Pkg>_ROOT` と探索順序を把握する
- `FetchContent` と `ExternalProject` の違いを理解する
- `FETCHCONTENT_SOURCE_DIR` で開発中の依存に差し替える
- **「あればfind_package、なければFetchContent」**を実現する
- 取り込み方がライセンス・配布に与える影響を判断できる

第14章と第16章で `FetchContent` を使った。この章では**もう一方の柱である `find_package`** を正面から扱う。第19章のvcpkg、第22章の「自作ライブラリを `find_package` 対応にする」の両方が、ここの理解の上に乗る。

---

## 18.1　`find_package` のふたつのモード

```cmake
find_package(GTest CONFIG REQUIRED)
```

一見単純なこのコマンドは、**まったく仕組みの違う2つのモード**を持つ。ここを混同していると、「なぜ見つからないのか」がいつまでも分からない。

### Moduleモード

CMakeが（あるいはあなたが）用意した **`FindXxx.cmake`** というスクリプトを実行し、その中でヘッダやライブラリを手探りで探す。

```cmake
find_package(ZLIB REQUIRED)          # FindZLIB.cmake が実行される
```

`FindZLIB.cmake` の中身は、おおよそこういうことをしている。

```cmake
find_path(ZLIB_INCLUDE_DIR zlib.h ...)
find_library(ZLIB_LIBRARY NAMES z zlib ...)
# 見つかったら ZLIB::ZLIB というインポートターゲットを作る
```

**探す側が、探される側のことを知っている。** CMake本体には100以上の `FindXxx.cmake` が同梱されており、`cmake --help-module-list` で一覧できる。

| 利点 | 欠点 |
| --- | --- |
| ライブラリ側がCMakeを知らなくても使える | **CMake側がライブラリごとに対応を書く必要がある** |
| 古いライブラリでも扱える | 情報が不正確・古くなりがち |
| | バージョンや構成の情報が取れないことが多い |

### Configモード

**ライブラリ側が用意した `XxxConfig.cmake`** を探して読み込む。

```cmake
find_package(GTest CONFIG REQUIRED)  # GTestConfig.cmake を探す
```

このファイルはライブラリのインストール時に一緒に置かれる。中身には「どこにヘッダがあり、どこに `.lib` があり、何に依存しているか」が**正確に記録されている**。

| 利点 | 欠点 |
| --- | --- |
| **情報が正確**（ライブラリ自身が書いている） | ライブラリ側がCMake対応している必要がある |
| バージョン・構成・依存関係が完全に分かる | |
| Debug/Release の切り替えも正しく行われる | |

**Configモードが本命だ。** 第22章で作るのは、まさにこの `pixkitConfig.cmake` である。

### モードの指定

```cmake
find_package(Foo)               # Module → 見つからなければ Config の順に試す
find_package(Foo MODULE)        # Module のみ
find_package(Foo CONFIG)        # Config のみ
```

**`CONFIG` を明示することを推奨する。** 理由は2つある。

1. どちらのモードで解決されたかが読んで分かる
2. CMakeに同梱の `FindXxx.cmake` が古くて、ライブラリ側の正しい `Config.cmake` を隠してしまう事故を防げる

vcpkg（第19章）が提供するライブラリは、ほぼすべてConfigモードで見つかる。

### 探すファイル名

Configモードで探されるファイル名は決まっている。

```
<PackageName>Config.cmake
<lowercase-name>-config.cmake
```

そして、バージョン照合用に次も読まれる。

```
<PackageName>ConfigVersion.cmake
```

第22章4節で、これを `write_basic_package_version_file` で生成する。

## 18.2　インポートターゲットの正体

Configパッケージを読み込むと、`GTest::gtest` のようなターゲットが使えるようになる。これは**インポートターゲット**（第6章1節）だ。

### 中身を覗く

実際にインストールされた GoogleTest に対して `find_package` して、プロパティを見てみる。

```cmake
find_package(GTest CONFIG REQUIRED)

message(STATUS "GTest_FOUND   = ${GTest_FOUND}")
message(STATUS "GTest_DIR     = ${GTest_DIR}")
message(STATUS "GTest_VERSION = ${GTest_VERSION}")

get_target_property(INC GTest::gtest INTERFACE_INCLUDE_DIRECTORIES)
message(STATUS "include = ${INC}")

get_target_property(LOC GTest::gtest IMPORTED_LOCATION_RELEASE)
message(STATUS "lib     = ${LOC}")
```

```
-- GTest_FOUND   = 1
-- GTest_DIR     = C:/work/stage/lib/cmake/GTest
-- GTest_VERSION = 1.17.0
-- include = C:/work/stage/include
-- lib     = C:/work/stage/lib/gtest.lib
```

**自分でビルドしたターゲットと同じように、プロパティを持っている。** 違いは「ビルドする方法」ではなく「すでにビルド済みの場所」を持っている点だけだ。

| プロパティ | 意味 |
| --- | --- |
| `INTERFACE_INCLUDE_DIRECTORIES` | 使う側に渡すインクルードパス |
| `INTERFACE_LINK_LIBRARIES` | 依存する他のライブラリ |
| `INTERFACE_COMPILE_DEFINITIONS` | 使う側に渡す定義 |
| `IMPORTED_LOCATION_<CONFIG>` | **構成ごとの `.lib` / `.dll` の場所** |
| `IMPORTED_IMPLIB_<CONFIG>` | DLLのインポートライブラリ（第11章1節） |

`IMPORTED_LOCATION_RELEASE` と `IMPORTED_LOCATION_DEBUG` が別々に記録されているのが重要だ。**Debug/Release で正しい `.lib` が自動的に選ばれる。** 手作業でパスを書いていた時代の最大の事故要因が、これで消える。

### `find_package` が変数も定義する

伝統的に、`find_package` は変数も定義してきた。

```cmake
find_package(ZLIB REQUIRED)
message(STATUS "${ZLIB_INCLUDE_DIRS}")
message(STATUS "${ZLIB_LIBRARIES}")
target_include_directories(app PRIVATE ${ZLIB_INCLUDE_DIRS})   # 古い書き方
target_link_libraries(app PRIVATE ${ZLIB_LIBRARIES})
```

**インポートターゲットがあるなら、変数は使わない。**

```cmake
target_link_libraries(app PRIVATE ZLIB::ZLIB)                  # こちら
```

第6章で学んだ使用要件の伝播が、変数経由では働かないからだ。ネット上の記事で `${XXX_LIBRARIES}` を見かけたら、その記事は古い。

### 見つからなかったとき

```cmake
find_package(Foo CONFIG REQUIRED)
```

`REQUIRED` があれば、見つからなければ即座にエラーで止まる。ないときは、

```cmake
find_package(Foo CONFIG)
if(Foo_FOUND)
    target_link_libraries(app PRIVATE Foo::Foo)
    target_compile_definitions(app PRIVATE HAVE_FOO=1)
endif()
```

**`<Pkg>_FOUND` 変数の大文字小文字は、パッケージ名と一致する。** `GTest_FOUND` であって `GTEST_FOUND` ではない（古いModuleモジュールは大文字版も定義することがあるので混乱しやすい）。

## 18.3　探索の仕組み

「なぜ見つからないのか」を解決するには、CMakeがどこを探しているかを知る必要がある。

### 探索パスの主なもの

Configモードで `find_package(Foo)` すると、CMakeは各探索プレフィックス `<prefix>` の下で次を探す。

```
<prefix>/
<prefix>/(cmake|CMake)/
<prefix>/<name>*/
<prefix>/lib/cmake/<name>*/
<prefix>/lib/<name>*/
<prefix>/share/<name>*/
...
```

そして `<prefix>` の候補になるのが、次の変数たちだ。**上にあるものほど優先される。**

| 変数 | 用途 |
| --- | --- |
| **`Foo_ROOT`** | そのパッケージ専用の指定（CMake 3.12以降） |
| **`CMAKE_PREFIX_PATH`** | **最もよく使う。** 複数のプレフィックスをセミコロン区切りで |
| `CMAKE_FRAMEWORK_PATH` など | プラットフォーム固有 |
| `PATH` 環境変数 | Windowsでは `bin/` の親を推測する |
| システムの標準的な場所 | `C:/Program Files/` など |

```
cmake --preset x64-debug -DCMAKE_PREFIX_PATH="C:/work/stage;C:/libs/opencv"
```

環境変数としても指定できる。

```
set CMAKE_PREFIX_PATH=C:\work\stage
```

vcpkgのツールチェインファイル（第19章3節）は、内部でこの `CMAKE_PREFIX_PATH` を設定している。**特別な魔法ではない。**

### デバッグする

見つからないときは、CMakeに「どこを探したか」を全部言わせる。

```
cmake --preset x64-debug --debug-find
```

出力は膨大だが、確実だ。パッケージを絞ることもできる。

```
cmake --preset x64-debug --debug-find-pkg=GTest
```

```
CMake Debug Log:
  find_package considered the following paths for GTestConfig.cmake:
    C:/work/stage/GTestConfig.cmake
    C:/work/stage/cmake/GTestConfig.cmake
    C:/work/stage/lib/cmake/GTest/GTestConfig.cmake
  The file was found at
    C:/work/stage/lib/cmake/GTest/GTestConfig.cmake
```

**「探したパスの一覧」が出るので、置き場所が1階層ずれている、といった問題がすぐ分かる。**

### 典型的な失敗と対処

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| `Could not find a package configuration file provided by "Foo"` | プレフィックスが渡っていない | `CMAKE_PREFIX_PATH` を指定 |
| Debugビルドなのに Release の `.lib` がリンクされる | Configパッケージが Debug 用の情報を持っていない | ライブラリを両構成でインストールする |
| 見つかるが古いバージョンが使われる | 別のプレフィックスに古いものがある | `Foo_ROOT` で明示 |
| vcpkgを使っているのに見つからない | ツールチェインが渡っていない（第19章3節） | プリセットを確認 |

## 18.4　`FetchContent` と `ExternalProject`

CMakeには、外部プロジェクトを扱うモジュールが2つある。名前は似ているが、**動作するタイミングがまるで違う。**

| | `FetchContent` | `ExternalProject` |
| --- | --- | --- |
| ダウンロード・展開 | **構成時** | **ビルド時** |
| 統合の仕方 | `add_subdirectory` して自分のビルドの一部にする | 独立したビルドとして実行する |
| ターゲットの可視性 | **見える**（`GTest::gtest` を直接リンクできる） | **見えない**（成果物のパスを手で指定する） |
| 同じコンパイラ設定 | **共有される** | 明示的に渡す必要がある |
| 用途 | ライブラリの取り込み | ツールチェインが違うもの、巨大なもの |

### `FetchContent` を選ぶべき場面

**ほとんどの場合はこちらだ。**

- 相手がCMakeプロジェクトである
- 自分と同じコンパイラ・同じフラグでビルドしてよい
- ターゲットとして直接リンクしたい

第14章のGoogleTest、第16章のGoogle Benchmarkがこれに当たる。

### `ExternalProject` を選ぶべき場面

- **相手がCMakeを使っていない**（`./configure && make` など）
- クロスコンパイルで、ホスト用ツールをビルドする必要がある
- 相手のビルドが自分のビルドに干渉する（グローバル設定を汚す）
- 相手が巨大で、並列ビルドの単位を分けたい

```cmake
include(ExternalProject)

ExternalProject_Add(some_lib
    URL               https://example.com/some_lib-1.2.3.tar.gz
    URL_HASH          SHA256=abc123...
    CONFIGURE_COMMAND <SOURCE_DIR>/configure --prefix=<INSTALL_DIR>
    BUILD_COMMAND     make -j
    INSTALL_COMMAND   make install
)
```

そして、成果物を**インポートターゲットとして手で定義する**ことになる。

```cmake
add_library(SomeLib::SomeLib STATIC IMPORTED GLOBAL)
set_target_properties(SomeLib::SomeLib PROPERTIES
    IMPORTED_LOCATION             "${INSTALL_DIR}/lib/somelib.lib"
    INTERFACE_INCLUDE_DIRECTORIES "${INSTALL_DIR}/include"
)
add_dependencies(SomeLib::SomeLib some_lib)
```

**手間が段違いに多い。** だからこそ、この面倒を肩代わりしてくれるvcpkg（第19章）に価値がある。

### 歴史的な補足

`FetchContent` は内部で `ExternalProject` の**ダウンロード機能だけ**を、構成時に実行する形で使っている。だから `FetchContent_Declare` の引数（`GIT_REPOSITORY`、`URL`、`URL_HASH` など）は `ExternalProject_Add` と共通だ。

## 18.5　`FetchContent` を実務で使う

### ダウンロード先とキャッシュ

既定では `${CMAKE_BINARY_DIR}/_deps` に展開される。

```
out/build/x64-debug/_deps/
├── googletest-src/       ← ソース
├── googletest-build/     ← ビルド
└── googletest-subbuild/  ← ダウンロード処理用
```

ビルドディレクトリを消すと再ダウンロードになる。共有したいなら場所を変える。

```cmake
set(FETCHCONTENT_BASE_DIR "${CMAKE_SOURCE_DIR}/.deps" CACHE PATH "")
```

### オフラインビルド

一度取得したあとは、更新チェックを止められる。

```
cmake --preset x64-debug -DFETCHCONTENT_FULLY_DISCONNECTED=ON
```

`FETCHCONTENT_UPDATES_DISCONNECTED=ON` なら「ダウンロードはするが更新チェックはしない」になる。CIで毎回タグを確認しにいくのを避けたいときに使う。

### 開発中の依存に差し替える

これは非常に便利な機能だ。あなたが `pixkit` と、それが依存する別のライブラリの**両方を同時に開発している**とする。

```
cmake --preset x64-debug -DFETCHCONTENT_SOURCE_DIR_GOOGLETEST=C:/work/my-googletest
```

変数名は `FETCHCONTENT_SOURCE_DIR_<大文字の依存名>` だ。これを指定すると、**ダウンロードを行わず、指定したローカルディレクトリをソースとして使う。**

`FetchContent_Declare` を書き換える必要はない。ローカルの変更を試して、済んだら変数を外すだけでよい。**依存ライブラリにバグを見つけたとき、その場で直して検証できる。**

`CMakeUserPresets.json`（第4章6節）に書いておくと、自分だけの設定として管理できる。

```json
{
  "version": 6,
  "configurePresets": [
    {
      "name": "my-debug",
      "inherits": "x64-debug",
      "cacheVariables": {
        "FETCHCONTENT_SOURCE_DIR_GOOGLETEST": "C:/work/my-googletest"
      }
    }
  ]
}
```

### 依存が依存を持つ場合

GoogleTestのように依存のないライブラリは楽だ。しかし、A が B に依存し、あなたも B に依存している場合、**同じ B が2回宣言される。**

`FetchContent` はこれを正しく扱う。**最初に `FetchContent_Declare` されたものが勝つ**（後の宣言は無視される）というルールだ。だから、

```cmake
# 自分の CMakeLists.txt で、先に宣言しておく
FetchContent_Declare(zlib GIT_TAG v1.3.1 ...)   # ← 自分が使いたいバージョン

FetchContent_MakeAvailable(some_lib)             # some_lib も zlib を宣言するが、無視される
```

とすれば、バージョンを自分で決められる。**トップレベルのプロジェクトが依存バージョンの決定権を持つ**、という設計だ。

ただし、これは「バージョンが合わなくても黙って動く」ことも意味する。依存が増えたら、vcpkgのバージョン解決（第20章2節）に移行するほうが安全になる。

## 18.6　「あればfind_package、なければFetchContent」

### 動機

`FetchContent` は便利だが、次の問題がある。

- ビルド時間が増える（毎回ソースからビルドする）
- ネットワークが必要
- パッケージマネージャで入れたものを使い回せない

一方 `find_package` は、事前にインストールされていることが前提だ。

**両方に対応したい。** CMake 3.24 でこれが公式に可能になった。

### `FIND_PACKAGE_ARGS`

```cmake
FetchContent_Declare(googletest
    GIT_REPOSITORY https://github.com/google/googletest.git
    GIT_TAG        v1.17.0
    GIT_SHALLOW    TRUE
    EXCLUDE_FROM_ALL
    SYSTEM
    FIND_PACKAGE_ARGS NAMES GTest CONFIG
)

FetchContent_MakeAvailable(googletest)
```

`FIND_PACKAGE_ARGS` が付いていると、`FetchContent_MakeAvailable` はまず

```cmake
find_package(googletest NAMES GTest CONFIG)
```

を試す。**見つかればそれを使い、見つからなければダウンロードしてビルドする。**

`NAMES GTest` を指定しているのは、依存の名前（`googletest`）とパッケージ名（`GTest`）が違うからだ。

動作を確認するには、どちらが使われたかを表示するとよい。

```cmake
FetchContent_MakeAvailable(googletest)

if(googletest_SOURCE_DIR)
    message(STATUS "GoogleTest: ダウンロードしてビルドしました")
else()
    message(STATUS "GoogleTest: システムにあるものを使いました")
endif()
```

`FetchContent` がソースを取得した場合のみ `<name>_SOURCE_DIR` が設定されるので、これで判別できる。

### 注意点

**`REQUIRED` を書いてはいけない。**

```cmake
FIND_PACKAGE_ARGS NAMES GTest CONFIG REQUIRED    # 悪い
```

見つからなかった時点でエラーになり、`FetchContent` へのフォールバックが起きなくなる。

### `FETCHCONTENT_TRY_FIND_PACKAGE_MODE`

全体の挙動を変数で制御できる。

| 値 | 挙動 |
| --- | --- |
| `OPT_IN`（既定） | `FIND_PACKAGE_ARGS` を書いた依存だけ `find_package` を試す |
| `ALWAYS` | **すべての依存で `find_package` を試す** |
| `NEVER` | `find_package` を試さない（`FIND_PACKAGE_ARGS` も無視） |

```
cmake --preset x64-debug -DFETCHCONTENT_TRY_FIND_PACKAGE_MODE=NEVER
```

`NEVER` は「システムに入っているものに影響されず、必ずソースからビルドする」ことを保証したいとき（再現性が最優先のCIなど）に使う。

### `OVERRIDE_FIND_PACKAGE`

逆方向の統合もある。

```cmake
FetchContent_Declare(SomeLib
    GIT_REPOSITORY ...
    OVERRIDE_FIND_PACKAGE
)
```

こう書くと、**あとから誰かが `find_package(SomeLib)` を呼んだときに、`FetchContent` が代わりに応答する。** 「依存の依存が `find_package` を呼んでいて、それを自分の管理下に置きたい」場面で効く。

`FIND_PACKAGE_ARGS` とは併用できない。

## 18.7　取り込み方が配布に与える影響

技術的な話に見えて、実は法務とリリースの話でもある。

### ソースを取り込むということ

`FetchContent` は依存のソースを取得し、**あなたのバイナリに静的にリンクする**（既定では静的ライブラリになる）。これは配布物の性質を変える。

| 依存の形態 | 配布物への影響 |
| --- | --- |
| 静的リンク | 依存のコードが**あなたのバイナリの一部になる** |
| 動的リンク | DLLとして分離される |
| ヘッダーオンリー | 同じくバイナリの一部になる |

### ライセンスの確認

静的リンクは、ライセンスによって義務が変わる。

| ライセンス | 静的リンクしたとき |
| --- | --- |
| MIT / BSD / Apache-2.0 | **著作権表示を配布物に含める**必要がある |
| LGPL | 差し替え可能にする義務が生じる（動的リンクなら比較的容易） |
| GPL | **あなたのコード全体に伝播する** |

GoogleTest（BSD-3-Clause）とGoogle Benchmark（Apache-2.0）は、**テストとベンチマークにしか使っていないので配布物に含まれない。** これは重要な区別だ。

- **配布物にリンクされる依存** → ライセンス表示が必要
- **開発時にしか使わない依存** → 通常は不要

第14章4節で `INSTALL_GTEST OFF` にしたのは、この境界を守る意味もある。テストフレームワークが配布物に混入しないようにしている。

### 依存の一覧を出せるようにする

配布のたびに手作業で確認するのは現実的でない。CMakeから依存を列挙できるようにしておく。

```cmake
if(PROJECT_IS_TOP_LEVEL)
    message(STATUS "配布物に含まれる依存:")
    foreach(T pixkit-core pixkit-codec pixkit-filter)
        get_target_property(DEPS ${T} INTERFACE_LINK_LIBRARIES)
        message(STATUS "  ${T}: ${DEPS}")
    endforeach()
endif()
```

第6章7節の `--graphviz` も使える。第20章5節では、vcpkgの `depend-info` でこれをより体系的に行う。

### 選択の指針

| 状況 | 推奨 |
| --- | --- |
| テスト・ベンチマークなど、配布物に含まれないもの | **`FetchContent`**（手軽さ優先） |
| 配布物にリンクされる依存 | **vcpkg**（バージョンとライセンスを管理しやすい） |
| 相手がCMake非対応 | vcpkg（ポートが面倒を見てくれる）、なければ `ExternalProject` |
| 社内の別チームが作っているライブラリ | vcpkgのカスタムレジストリ（第24章） |

第19章でvcpkgに移行するのは、この表の2行目に該当する依存がこれから増えるからだ。

## ハンズオン：同じ依存を3通りの方法で解決する

GoogleTestを題材に、3つのやり方を実際に試して違いを体感する。**このハンズオンは `pixkit` とは別のディレクトリで行う。**

### 手順1：作業用プロジェクトを作る

`C:\work\deps-demo\`

`main.cpp`

```cpp
#include <gtest/gtest.h>

TEST(Sanity, Works)
{
    EXPECT_EQ(1 + 1, 2);
}
```

### 手順2：方法A — `FetchContent` で取ってくる

`CMakeLists.txt`

```cmake
cmake_minimum_required(VERSION 3.28)
project(deps-demo LANGUAGES CXX)
set(CMAKE_CXX_STANDARD 23)

include(FetchContent)
set(gtest_force_shared_crt ON  CACHE BOOL "" FORCE)
set(INSTALL_GTEST          OFF CACHE BOOL "" FORCE)

FetchContent_Declare(googletest
    GIT_REPOSITORY https://github.com/google/googletest.git
    GIT_TAG        v1.17.0
    GIT_SHALLOW    TRUE
    EXCLUDE_FROM_ALL
    SYSTEM
)
FetchContent_MakeAvailable(googletest)

add_executable(t main.cpp)
target_link_libraries(t PRIVATE GTest::gtest_main)
```

```
cd C:\work\deps-demo
cmake -S . -B build-fetch -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build-fetch
build-fetch\t.exe
```

構成に十数秒かかる（ダウンロード）ことと、`build-fetch\_deps\` にソースが展開されていることを確認する。

### 手順4：方法B — `find_package` で見つける

`CMakeLists.txt` を書き換える。

```cmake
cmake_minimum_required(VERSION 3.28)
project(deps-demo LANGUAGES CXX)
set(CMAKE_CXX_STANDARD 23)

find_package(GTest CONFIG REQUIRED)

message(STATUS "GTest_FOUND   = ${GTest_FOUND}")
message(STATUS "GTest_DIR     = ${GTest_DIR}")
message(STATUS "GTest_VERSION = ${GTest_VERSION}")

message(STATUS "include = ${INC}")

message(STATUS "lib     = ${LOC}")

add_executable(t main.cpp)
target_link_libraries(t PRIVATE GTest::gtest_main)
```

```
cmake -S . -B build-find -G Ninja -DCMAKE_BUILD_TYPE=Release ^
      -DCMAKE_PREFIX_PATH=C:/work/deps-demo/stage
```


### 手順6：方法C — あればfind_package、なければFetchContent

```cmake
cmake_minimum_required(VERSION 3.28)
project(deps-demo LANGUAGES CXX)
set(CMAKE_CXX_STANDARD 23)

include(FetchContent)
set(gtest_force_shared_crt ON  CACHE BOOL "" FORCE)
set(INSTALL_GTEST          OFF CACHE BOOL "" FORCE)

FetchContent_Declare(googletest
    GIT_REPOSITORY https://github.com/google/googletest.git
    GIT_TAG        v1.17.0
    GIT_SHALLOW    TRUE
    EXCLUDE_FROM_ALL
    SYSTEM
    FIND_PACKAGE_ARGS NAMES GTest CONFIG
)
FetchContent_MakeAvailable(googletest)

if(googletest_SOURCE_DIR)
    message(STATUS "==> ダウンロードして自前でビルドしました")
else()
    message(STATUS "==> システムにあるものを使いました")
endif()

add_executable(t main.cpp)
target_link_libraries(t PRIVATE GTest::gtest_main)
```

**プレフィックスを渡した場合：**

```
cmake -S . -B build-hybrid-a -G Ninja -DCMAKE_BUILD_TYPE=Release ^
      -DCMAKE_PREFIX_PATH=C:/work/deps-demo/stage
```

```
-- ==> システムにあるものを使いました
```

**渡さない場合：**

```
cmake -S . -B build-hybrid-b -G Ninja -DCMAKE_BUILD_TYPE=Release
```

```
-- ==> ダウンロードして自前でビルドしました
```

**同じ `CMakeLists.txt` が、環境に応じて振る舞いを変えた。** 両方ともビルドして実行できることを確認する。

### 手順7：`NEVER` で強制する

```
cmake -S . -B build-never -G Ninja -DCMAKE_BUILD_TYPE=Release ^
      -DCMAKE_PREFIX_PATH=C:/work/deps-demo/stage ^
      -DFETCHCONTENT_TRY_FIND_PACKAGE_MODE=NEVER
```

```
-- ==> ダウンロードして自前でビルドしました
```

**プレフィックスを渡しているのに、ダウンロードした。** 再現性を最優先するCIで使う設定だ（18.6節）。

### 手順9：`pixkit` に適用する

```cmake
    SYSTEM
```

```cmake
    SYSTEM

```

### 発展課題

1. `--debug-find-pkg=GTest` の出力を保存し、探索されたパスの数を数える
2. `GTest_ROOT` 変数を使って、`CMAKE_PREFIX_PATH` なしで見つけさせる
3. `stage` を Debug 構成でもインストールし、`GTestTargets-debug.cmake` が追加されることを確認する
4. `find_package(GTest MODULE REQUIRED)` に変えて、CMake同梱の `FindGTest.cmake` で解決されることを確認し、`GTest_DIR` が設定されないことを見る
5. `FETCHCONTENT_FULLY_DISCONNECTED=ON` でネットワークを切った状態の構成を試す

## この章のまとめ

- `find_package` には **Moduleモード**（CMakeが用意した `FindXxx.cmake`）と **Configモード**（ライブラリが提供する `XxxConfig.cmake`）がある。**`CONFIG` を明示するのが安全**
- Configパッケージは**インポートターゲット**を提供する。`IMPORTED_LOCATION_<CONFIG>` により、**Debug/Release で正しい `.lib` が自動的に選ばれる**
- `${XXX_LIBRARIES}` のような変数ではなく、**インポートターゲットをリンクする**（使用要件が伝播する）
- 探索の主役は **`CMAKE_PREFIX_PATH`** と **`<Pkg>_ROOT`**。見つからないときは **`--debug-find-pkg=<name>`** で探索経路を出す
- **`FetchContent` は構成時**にソースを取得して `add_subdirectory` する。**`ExternalProject` はビルド時**に独立したビルドとして実行する。CMakeプロジェクトなら前者
- **`FETCHCONTENT_SOURCE_DIR_<NAME>`** でローカルのソースに差し替えられる。依存を同時に開発するときに効く
- **`FIND_PACKAGE_ARGS`**（CMake 3.24以降）で「あればfind_package、なければFetchContent」が実現できる。**`REQUIRED` は書かない**。全体制御は `FETCHCONTENT_TRY_FIND_PACKAGE_MODE`（`OPT_IN` / `ALWAYS` / `NEVER`）
- 取り込み方は**ライセンスと配布**に影響する。テスト用の依存は配布物に含まれない、という境界を保つ

次の第19章では、vcpkgを導入する。この章で学んだ `find_package` の仕組みが、vcpkgの正体を理解する鍵になる。**vcpkgがやっているのは、要するに「ライブラリをビルドしてインストールし、`CMAKE_PREFIX_PATH` を設定すること」**なのだ。
