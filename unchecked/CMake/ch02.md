# 第2章　最初のCMakeプロジェクト

## この章のゴール

- 3行の `CMakeLists.txt` を書いて `hello.exe` をビルドする
- **構成(configure)・生成(generate)・構築(build)** の3段階を区別できる
- `cmake -S . -B build` と `cmake --build build` を手が覚えている状態にする
- アウトオブソースビルドがなぜ必須なのかを理解する
- Visual Studio ジェネレータと Ninja ジェネレータの違いを、出力を見て説明できる
- `CMakeCache.txt` の役割と、消すべきタイミングを知る

この章ではIDEを開かない。すべてコマンドラインで行う。遠回りに見えるが、ここでCMakeの動きを目で見ておくと、第3章以降でIDEが裏で何をしているかが分かるようになる。

---

## 2.1　3行の `CMakeLists.txt`

作業用のディレクトリを作る。場所はどこでもよいが、本書では `C:\work\` 以下を使う。

```
mkdir C:\work\hello
cd C:\work\hello
```

### ソースファイル

`main.cpp` を作る。

```cpp
// main.cpp
#include <iostream>

int main()
{
    std::cout << "Hello, CMake!\n";
    return 0;
}
```

> C++23の本なのに `std::cout` なのか、と思ったかもしれない。`std::print` を使うにはコンパイラに `/std:c++23` 相当のフラグを渡す必要があり、それはCMakeの仕事だ。**まだその設定をしていない**ので、今は素の状態で通るコードを使う。第7章でC++23を有効にしたら、真っ先にここを `std::print` に書き換える。

### `CMakeLists.txt`

同じディレクトリに `CMakeLists.txt` を作る。**ファイル名は完全一致でなければならない**（`CMakelists.txt` や `cmakelists.txt` は不可。Windowsのファイルシステムは大文字小文字を区別しないので手元では動いてしまうが、CIのLinuxで壊れる）。

```cmake
cmake_minimum_required(VERSION 3.28)
project(hello LANGUAGES CXX)
add_executable(hello main.cpp)
```

これで全部だ。この3行を1つずつ見ていく。

---

## 2.2　`cmake_minimum_required` / `project` / `add_executable`

### `cmake_minimum_required(VERSION 3.28)`

**必ず最初の行に書く。** 第1章5節で述べたとおり、これは「CMake 3.28以上が必要」という要求であると同時に、「3.28時点のポリシーで解釈せよ」という宣言だ。

この行がないと、CMakeは警告を出す。そして、その警告を放置したプロジェクトは、CMakeのバージョンが上がったときに挙動が変わって壊れる。

### `project(hello LANGUAGES CXX)`

プロジェクト名を宣言する。単なる名札ではなく、この呼び出しで**大量の処理が走る**。

- 使用する言語（`CXX` = C++）のコンパイラを探す
- 見つけたコンパイラが実際に動くかテストコンパイルする
- コンパイラのID（MSVC / Clang / GNU）とバージョンを判定する
- `PROJECT_NAME`、`PROJECT_SOURCE_DIR`、`PROJECT_BINARY_DIR` などの変数を設定する

`LANGUAGES CXX` を明示しているのは、**既定では `C` と `CXX` の両方を探しに行く**からだ。Cコンパイラを使わないなら、明示しておくほうが構成が速く、意図もはっきりする。

第8章では、ここに `VERSION 0.1.0` を追加して、ライブラリのバージョン管理に使う。

### `add_executable(hello main.cpp)`

**ターゲット**を1つ作る。第1引数 `hello` がターゲット名で、これがそのまま出力ファイル名 `hello.exe` になる。第2引数以降がソースファイルだ。

ここで作られる「ターゲット」こそがCMakeの中心概念で、以降のすべての設定はこのターゲットに対して行われる（第6章）。

> **命名の注意**
> ターゲット名は**プロジェクト全体でユニーク**でなければならない。第8章以降で複数のライブラリを作るときは、`pixkit-core` のように接頭辞を付けて衝突を避ける。

## 2.3　構成・生成・構築の3段階

CMakeを使ったビルドは、必ず次の3段階を通る。用語を正確に区別しておくと、エラーメッセージの意味が分かるようになる。

| 段階 | 英語 | 何をするか | 実行するもの |
| --- | --- | --- | --- |
| **構成** | configure | `CMakeLists.txt` を読んで実行し、コンパイラを探し、設定をキャッシュに書く | CMake |
| **生成** | generate | 構成の結果から `.vcxproj` や `build.ninja` を書き出す | CMake |
| **構築** | build | 実際にコンパイルとリンクを行う | MSBuild / Ninja |

構成と生成はほぼ常にセットで実行されるので、まとめて「configure」と呼ばれることが多い。本書でも、区別が必要なとき以外は「構成」でまとめて指す。

重要なのは、**構成は「CMakeスクリプトの実行」である**という点だ。`CMakeLists.txt` はデータファイルではなく、上から順に実行されるプログラムだ。`message()` を書けば構成時にメッセージが出るし、`if` は構成時に評価される。「ビルド時に条件分岐したい」場合はまったく別の仕組み（ジェネレータ式、第7章8節）が必要になる。この区別は後々とても効いてくる。

## 2.4　`cmake -S . -B build` と `cmake --build build`

では実行する。開発者コマンドプロンプトで、`C:\work\hello` にいることを確認して次を打つ。

### 構成する

```
cmake -S . -B build
```

- `-S .` : **ソース**ディレクトリ（`CMakeLists.txt` があるところ）
- `-B build` : **ビルド**ディレクトリ（生成物を置くところ。なければ作られる）

**期待する出力**（抜粋）:

```
-- Building for: Visual Studio 18 2026
-- Selecting Windows SDK version 10.0.26100.0 to target Windows 10.0.26100.
-- The CXX compiler identification is MSVC 19.50.35211.0
-- Detecting CXX compiler ABI info
-- Detecting CXX compiler ABI info - done
-- Check for working CXX compiler: C:/Program Files/Microsoft Visual Studio/2026/... - skipped
-- Detecting CXX compile features
-- Detecting CXX compile features - done
-- Configuring done (2.1s)
-- Generating done (0.1s)
-- Build files have been written to: C:/work/hello/build
```

最後の3行が重要だ。`Configuring done` が構成、`Generating done` が生成、そして生成物が `build` に書かれたことを示している。

### 構築する

```
cmake --build build
```

**期待する出力**（抜粋）:

```
  main.cpp
  hello.vcxproj -> C:\work\hello\build\Debug\hello.exe
```

### 実行する

```
build\Debug\hello.exe
```

```
Hello, CMake!
```

動いた。ここまでで、Visual Studio を一度も開かずにビルドが通っている。

### `cmake --build` を使う理由

「MSBuildを直接呼べばいいのでは」と思うかもしれない。実際そうもできるが、`cmake --build` を使う理由がある。**ジェネレータが何であっても同じコマンドで済む**からだ。

```
cmake --build build            # 裏でMSBuildを呼ぶ / Ninjaを呼ぶ / makeを呼ぶ
```

CIスクリプトや手順書を、ジェネレータ非依存で書けるようになる。

### よく使うオプション

```
cmake --build build --config Release        # 構成を指定（マルチ構成ジェネレータで必須）
cmake --build build --target hello          # 特定のターゲットだけ
cmake --build build --parallel              # 並列ビルド
cmake --build build --clean-first           # クリーンしてからビルド
cmake --build build -- /verbosity:detailed  # -- 以降はビルドツールへそのまま渡される
```

`--config Release` を付けずに `Release` のバイナリを期待して、`Debug` のものが出てきて混乱する、というのはよくある事故だ。理由は2.7節で説明する。

### 覚えるコマンドは実質2つ

```
cmake -S . -B build          # 構成
cmake --build build          # 構築
```

CMakeの日常操作の9割はこの2つだ。第4章でプリセットを導入すると、これがさらに `cmake --preset x64-debug` のような形に短縮される。

## 2.5　アウトオブソースビルド

`cmake -S . -B build` の `-B build` は、単なる好みではない。**必須の作法**だ。

`build` ディレクトリの中を覗いてみよう。

```
dir build
```

```
CMakeCache.txt
CMakeFiles\
cmake_install.cmake
Debug\
hello.sln
hello.vcxproj
hello.vcxproj.filters
ALL_BUILD.vcxproj
ZERO_CHECK.vcxproj
x64\
...
```

ソースは `main.cpp` 1つだけなのに、これだけのファイルが生成される。これらが `main.cpp` と同じディレクトリに散らかっていたら、どうなるか想像してほしい。

**アウトオブソースビルドの利点：**

| 利点 | 内容 |
| --- | --- |
| ソースツリーが汚れない | `.gitignore` に `build/` の1行を書くだけで済む |
| やり直しが簡単 | おかしくなったら `build` を丸ごと削除して構成し直せば、確実に初期状態に戻る |
| 複数構成を並べられる | `build-vs/` と `build-ninja/`、`build-x64/` と `build-arm64/` を共存させられる |

なお、CMake 3.13以降は**インソースビルド（ソースディレクトリで直接構成すること）を明示的に拒否する**プロジェクトも書けるが、そもそも `-B` を常に付ける習慣にすれば問題は起きない。

> **`.gitignore` に書くもの（この時点）**
> ```
> build/
> out/
> .vs/
> ```
> `out/` は Visual Studio が既定で使うビルドディレクトリ、`.vs/` はVSのローカル設定だ（第3章）。

## 2.6　ジェネレータを選ぶ

`cmake -S . -B build` では `Visual Studio 18 2026` が自動的に選ばれた。これを明示的に指定するには `-G` を使う。

### Visual Studio ジェネレータ

```
cmake -S . -B build-vs -G "Visual Studio 18 2026" -A x64
```

- `-G "Visual Studio 18 2026"` : ジェネレータ名。**スペースを含むのでクォート必須**
- `-A x64` : ターゲットアーキテクチャ。`Win32` / `x64` / `ARM` / `ARM64` が指定できる
- `-T <toolset>` : ツールセット。既定は **v145**。`-T v143` で1世代前を、`-T ClangCL` でclang-clを使う

`-A` を省略すると、既定のプラットフォームが選ばれる。**明示するほうが安全**だ。

生成されるのは `.sln` と `.vcxproj` で、`build-vs\hello.sln` をダブルクリックすればVisual Studio が開く。

### Ninja ジェネレータ

```
cmake -S . -B build-ninja -G Ninja
cmake --build build-ninja
```

**注意：Ninjaジェネレータは開発者コマンドプロンプトからでないと動かない。** 普通のコマンドプロンプトで実行すると、こうなる。

```
CMake Error at CMakeLists.txt:2 (project):
  No CMAKE_CXX_COMPILER could be found.
```

理由は第1章7節で説明したとおりだ。Visual Studio ジェネレータの場合、CMakeはレジストリからVisual Studio を探し出してMSBuildに任せるので環境変数がなくても動く。しかしNinjaジェネレータの場合、CMakeは**自分で `cl.exe` を探し、自分でコンパイラを起動する**ので、`PATH` / `INCLUDE` / `LIB` が設定されている必要がある。

### どちらを使うべきか

| | Visual Studio 18 2026 | Ninja |
| --- | --- | --- |
| 種別 | マルチ構成 | 単一構成 |
| ビルド速度 | 普通 | **速い** |
| VS でのデバッグ | そのまま使える | VSの「フォルダーを開く」経由で使える |
| 環境変数の準備 | 不要 | **開発者コマンドプロンプトが必須** |
| `compile_commands.json` の生成 | **できない** | できる（第17章で必要） |
| Debug/Release の切り替え | ビルド時に `--config` で | 構成時に別ディレクトリを作る |

結論としては**両方使う**。本書では、

- 日常のIDE開発 → Visual Studio ジェネレータ
- 高速ビルド、Clang-Tidy、CI → Ninja

という使い分けをする。第4章でこの2つをプリセットとして登録し、いつでも切り替えられるようにする。

### 全ジェネレータの一覧

```
cmake --help
```

の末尾に出る。`Ninja Multi-Config` という選択肢もあり、これは「Ninjaの速さ＋マルチ構成」を両立するもので、有力な第3の選択肢だ（第12章で触れる）。

## 2.7　生成物はどこに出るか

先ほど `hello.exe` は `build\Debug\` に出た。この `Debug\` というサブディレクトリが、初学者を混乱させる。

### マルチ構成ジェネレータの場合

Visual Studio ジェネレータは**マルチ構成ジェネレータ**だ。1回の構成で、Debug / Release / RelWithDebInfo / MinSizeRel の**すべての構成のビルド定義**が作られる。どれをビルドするかは、構成時ではなく**ビルド時**に決まる。

```
cmake -S . -B build -G "Visual Studio 18 2026" -A x64   # ここでは構成を選ばない
cmake --build build --config Debug                       # ここで選ぶ
cmake --build build --config Release                     # 同じビルドディレクトリで両方作れる
```

結果、出力はこうなる。

```
build\Debug\hello.exe
build\Release\hello.exe
```

**`--config` を省略すると `Debug` になる。** これが「Releaseのつもりが遅い」事故の正体だ。

### 単一構成ジェネレータの場合

Ninjaは**単一構成ジェネレータ**だ。1つのビルドディレクトリは1つの構成しか持てず、構成を**構成時に**決める。

```
cmake -S . -B build-ninja-debug   -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake -S . -B build-ninja-release -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build-ninja-release
```

出力に `Debug\` のようなサブディレクトリは付かない。

```
build-ninja-release\hello.exe
```

そして `--config Release` を付けても**無視される**（警告すら出ないことがある）。

### この違いが引き起こす問題

| | マルチ構成（VS） | 単一構成（Ninja） |
| --- | --- | --- |
| 構成の指定 | `cmake --build ... --config X` | `cmake -DCMAKE_BUILD_TYPE=X ...` |
| `CMAKE_BUILD_TYPE` | **空になる**（使ってはいけない） | 有効 |
| 出力パス | `build/<Config>/hello.exe` | `build/hello.exe` |
| ビルドディレクトリ | 1つで足りる | 構成ごとに必要 |

`CMakeLists.txt` の中で `if(CMAKE_BUILD_TYPE STREQUAL "Debug")` と書くコードをネットでよく見かけるが、これは**Visual Studio ジェネレータでは動かない**。マルチ構成では `CMAKE_BUILD_TYPE` が空だからだ。正しい書き方は**ジェネレータ式** `$<CONFIG:Debug>` を使うことで、第7章8節と第12章で詳しく扱う。

この落とし穴は本書で何度も出てくるので、ここで印を付けておいてほしい。

## 2.8　`CMakeCache.txt` の役割

`build\CMakeCache.txt` をテキストエディタで開いてみる。数百行あるが、中身はこういう `キー:型=値` の羅列だ。

```
CMAKE_BUILD_TYPE:STRING=
CMAKE_CXX_COMPILER:FILEPATH=C:/Program Files/Microsoft Visual Studio/2026/.../cl.exe
CMAKE_CXX_FLAGS:STRING=/DWIN32 /D_WINDOWS /EHsc
CMAKE_INSTALL_PREFIX:PATH=C:/Program Files (x86)/hello
CMAKE_GENERATOR:INTERNAL=Visual Studio 18 2026
hello_BINARY_DIR:STATIC=C:/work/hello/build
```

### 何のためにあるか

1. **時間のかかる検出結果を覚えておくため**
   コンパイラの探索やテストコンパイルを毎回やると遅い。2回目以降の構成が速いのはキャッシュのおかげだ。
2. **ユーザーが指定した設定を保持するため**
   `-D` で渡した値はキャッシュに書かれ、次回以降も維持される。

### `-D` で値を渡す

```
cmake -S . -B build -DCMAKE_INSTALL_PREFIX=C:/work/hello/stage
```

一度書かれたキャッシュ値は、**次回から `-D` を省略しても維持される**。これは便利であると同時に、事故の元でもある。「昔うっかり指定した値がずっと効いている」が起きる。

### キャッシュの中身を見る

```
cmake -L build            # ユーザー向けのキャッシュ変数を一覧
cmake -LAH build          # 内部変数もヘルプ付きで全部
```

GUIで見たい場合は `cmake-gui` が使える。

### キャッシュを消すべきタイミング

これは実務で頻繁に必要になる判断だ。

| 状況 | 対処 |
| --- | --- |
| `CMakeLists.txt` を編集した | **何もしなくてよい**。`cmake --build` が自動で再構成する |
| ソースファイルを追加した | `CMakeLists.txt` に書き足せば自動で再構成される |
| ジェネレータを変えたい | **ビルドディレクトリごと削除**。同じディレクトリでのジェネレータ変更は不可 |
| コンパイラを変えたい | **ビルドディレクトリごと削除** |
| キャッシュ変数を1つ消したい | `cmake -U <変数名> build` |
| 原因不明の変な挙動 | **ビルドディレクトリごと削除**して構成し直す |

最後の行が重要だ。CMakeで困ったときの第一手は、常に「`build` を消してやり直す」である。アウトオブソースビルドにしておけば、これは1コマンドで済み、しかも完全に安全だ。

```
rmdir /s /q build
cmake -S . -B build
```

> **`ZERO_CHECK` プロジェクトの正体**
> Visual Studio でCMakeが生成したソリューションを開くと、`ZERO_CHECK` という見慣れないプロジェクトがある。これは「`CMakeLists.txt` が変更されていないかを調べ、されていたら再構成する」ためのターゲットだ。だから `CMakeLists.txt` を編集してVSでビルドするだけで、自動的に構成がやり直される。`ALL_BUILD` は「全ターゲットをビルドする」ためのまとめターゲットである。

## ハンズオン：同じソースを2つのジェネレータでビルドする

第2章の内容を通しで確認する。

### 手順1：プロジェクトを用意する

`C:\work\hello` に `main.cpp` と `CMakeLists.txt` を配置する（2.1節のもの）。

### 手順2：Visual Studio ジェネレータでビルドする

```
cd C:\work\hello
cmake -S . -B build-vs -G "Visual Studio 18 2026" -A x64
cmake --build build-vs --config Debug
cmake --build build-vs --config Release
```

出力を確認する。

```
dir /b build-vs\Debug build-vs\Release
```

```
build-vs\Debug:
hello.exe
hello.pdb

build-vs\Release:
hello.exe
```

**確認ポイント：1回の構成で、DebugとReleaseの両方が同じビルドディレクトリに作られた。**

### 手順3：Ninja ジェネレータでビルドする

```
cmake -S . -B build-ninja -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build-ninja
dir /b build-ninja\*.exe
```

```
hello.exe
```

**確認ポイント：`Release\` サブディレクトリは作られず、直下に出た。**

### 手順4：ビルドの速さを比べる

```
cmake --build build-vs --config Release --clean-first
cmake --build build-ninja --clean-first
```

ソース1つでは差は出ないが、第8章以降で数十ファイルになると、体感できるほど違ってくる。

### 手順5：キャッシュを覗く

```
cmake -L build-ninja
```

`CMAKE_BUILD_TYPE:STRING=Release` があることを確認する。次に、Visual Studio 側を見る。

```
cmake -L build-vs
```

`CMAKE_BUILD_TYPE:STRING=`（**空**）になっているはずだ。2.7節で述べた「マルチ構成では `CMAKE_BUILD_TYPE` が空」を、自分の目で確認しておく。

### 手順6：ジェネレータを変えようとして怒られてみる

失敗を体験しておくと記憶に残る。既存の `build-vs` に対して、別のジェネレータで構成してみる。

```
cmake -S . -B build-vs -G Ninja
```

```
CMake Error: Error: generator : Ninja
Does not match the generator used previously: Visual Studio 18 2026
Either remove the CMakeCache.txt file and CMakeFiles directory or choose a different binary directory.
```

エラーメッセージが対処法まで書いてくれている。指示どおりディレクトリを消せば通る。

```
rmdir /s /q build-vs
cmake -S . -B build-vs -G Ninja
```

### 発展課題

1. `add_executable(hello main.cpp)` のターゲット名を `greeter` に変えて再ビルドし、出力ファイル名がどうなるか確認する
2. `cmake -S . -B build-arm -G "Visual Studio 18 2026" -A ARM64` で構成し、成功するか確かめる（コンパイルはできる。実行はできない）
3. `CMakeLists.txt` の1行目を削除して構成し、どんな警告が出るか読む

## この章のまとめ

- 最小の `CMakeLists.txt` は `cmake_minimum_required` / `project` / `add_executable` の3行
- CMakeの操作は **構成 `cmake -S . -B build`** と **構築 `cmake --build build`** の2コマンドが基本
- ビルドディレクトリは必ずソースと分ける（アウトオブソースビルド）。困ったら消してやり直す
- `-G` でジェネレータを選ぶ。Visual Studio 用は `"Visual Studio 18 2026"`、アーキテクチャは `-A x64`
- **マルチ構成**（VS）はビルド時に `--config` で構成を選び、出力は `build/<Config>/` に出る。**単一構成**（Ninja）は構成時に `CMAKE_BUILD_TYPE` で決め、出力は直下に出る。`CMAKE_BUILD_TYPE` はマルチ構成では空になるので、条件分岐に使ってはいけない
- `CMakeCache.txt` は検出結果とユーザー設定を保持する。ジェネレータやコンパイラを変えるときはビルドディレクトリごと削除する

次の第3章では、いま作ったこのプロジェクトを Visual Studio 2026 で開く。`.sln` をダブルクリックするのではなく、「フォルダーを開く」を使う方法を学ぶ。そこでVSが裏で `cmake -S . -B ...` を実行していることが見えるはずだ。
