# 第3章　Visual Studio 2026 でCMakeプロジェクトを扱う

## この章のゴール

- 「フォルダーを開く」でCMakeプロジェクトを開き、VSが裏で何をしているか理解する
- CMakeターゲットビューとソリューションエクスプローラを使い分ける
- 構成の切り替えとキャッシュの再生成をIDEから行う
- `launch.vs.json` でデバッグ時の引数・作業ディレクトリ・環境変数を設定する
- CMakeのエラーメッセージを読めるようになる
- IntelliSenseが効かないときの調査手順を身につける

第2章で作った `C:\work\hello` をそのまま使う。

---

## 3.1　「フォルダーを開く」でCMakeプロジェクトを開く

CMakeプロジェクトをVisual Studio で開く方法は2つある。

### 方法A：生成された `.sln` を開く（**推奨しない**）

```
cmake -S . -B build-vs -G "Visual Studio 18 2026" -A x64
start build-vs\hello.sln
```

これでも開けるし、ビルドもデバッグもできる。しかし本書ではこの方法を採らない。理由は次のとおりだ。

- `.sln` は生成物なので、消えたり作り直されたりする
- `CMakeLists.txt` がソリューションエクスプローラに出るが、それを編集してもCMake側の再構成はVSが `ZERO_CHECK` 経由でしか面倒を見ない
- 何より、**ジェネレータがVisual Studio に固定される**。Ninjaに切り替えられない

### 方法B：フォルダーを開く（**本書の方法**）

Visual Studio 2026 を起動し、**「ローカル フォルダーを開く」**（またはメニューの **ファイル → 開く → フォルダー**）で `C:\work\hello` を選ぶ。

VSはフォルダ直下に `CMakeLists.txt` を見つけると、それをCMakeプロジェクトとして認識し、**自動的に構成を開始する**。出力ウィンドウ（表示 → 出力、「CMake」を選択）にこう出るはずだ。

```
1> CMake の生成が開始されました。
1> 作業ディレクトリ: C:\work\hello\out\build\x64-debug
1> [CMake] -- The CXX compiler identification is MSVC 19.50.35211.0
1> [CMake] -- Configuring done
1> [CMake] -- Generating done
1> [CMake] -- Build files have been written to: C:/work/hello/out/build/x64-debug
1> CMake の生成が完了しました。
```

第2章でコマンドラインから見たものと、まったく同じログだ。**VSは裏で `cmake` を実行しているに過ぎない。**

### VSが使うビルドディレクトリ

注目してほしいのは作業ディレクトリだ。

```
C:\work\hello\out\build\x64-debug
```

コマンドラインで使っていた `build\` ではなく、`out\build\<構成名>\` が使われている。これがVisual Studio の既定のレイアウトだ。第4章でプリセットを導入すると、この場所は自分で決められるようになる。

`.gitignore` に `out/` を入れておく理由がこれだ。

### `.vs` フォルダ

同時に `.vs\` という隠しフォルダも作られる。ここにはIntelliSenseのデータベースやウィンドウレイアウトなど、**そのマシン固有の情報**が入る。バージョン管理には絶対に入れない。

```
# .gitignore
build/
out/
.vs/
```

## 3.2　CMakeターゲットビューとソリューションエクスプローラ

ソリューションエクスプローラの上部に、フォルダアイコンの切り替えボタンがある。ここで表示を切り替えられる。

### フォルダービュー（既定）

ディスク上のディレクトリ構造がそのまま表示される。`main.cpp` と `CMakeLists.txt` が並んでいるだけだ。ファイルを探すときはこれが速い。

### CMake ターゲット ビュー

ソリューションエクスプローラのツールバーにある切り替えメニューから **「CMake ターゲット ビュー」** を選ぶ。表示が変わる。

```
hello プロジェクト
└── hello (実行可能ファイル)
    └── Source Files
        └── main.cpp
```

こちらは**CMakeが認識しているターゲット構造**を表示する。第8章以降でライブラリが増えてくると、このビューの価値が分かる。

| ビュー | 何が見えるか | いつ使うか |
| --- | --- | --- |
| フォルダー | ディスク上のファイル | ファイルを開く・追加する |
| CMake ターゲット | ターゲットとその構成ファイル | **ターゲット単位でビルド・デバッグしたいとき** |

CMakeターゲットビューでは、ターゲットを右クリックして「ビルド」を選べる。これは `cmake --build ... --target hello` に相当する。第14章でテストターゲットとベンチマークターゲットが増えると、「テストだけビルドする」といった操作がここからできるようになる。

> **ターゲットビューに出てこないファイル**
> ヘッダファイルは `add_executable` / `add_library` に列挙しない限り、このビューに出てこない。ヘッダを表示させたい場合は、ソースリストに書き足す。CMakeはヘッダをコンパイル対象とはみなさないので、書いても害はなく、IDEでの見た目が良くなる。この扱いは第10章（ヘッダーオンリーライブラリ）で重要になる。

## 3.3　構成の切り替えとキャッシュの操作

### 構成の切り替え

ツールバーに構成のドロップダウンがある。既定では `x64-Debug` になっているはずだ。ここを `x64-Release` に切り替えると、VSは**自動的に再構成を開始する**。

出力ウィンドウを見ると、新しいビルドディレクトリが使われることが分かる。

```
作業ディレクトリ: C:\work\hello\out\build\x64-release
```

第2章7節で学んだとおり、これは単一構成ジェネレータ（VSの既定はNinja）の流儀だ。構成ごとに別のビルドディレクトリが作られている。

> **VSの既定ジェネレータはNinjaである**
> 意外に思うかもしれないが、Visual Studio が「フォルダーを開く」でCMakeプロジェクトを扱うとき、既定のジェネレータは **Ninja** だ（`Visual Studio 18 2026` ではない）。速度のためである。この事実は第17章で効いてくる。Clang-Tidyに必要な `compile_commands.json` はNinjaジェネレータでしか生成できないからだ。

### キャッシュの操作

メニューの **プロジェクト** に、CMake関連の項目が並ぶ。

| メニュー項目 | 相当するコマンド | 使う場面 |
| --- | --- | --- |
| **CMake キャッシュの生成** | `cmake -S . -B out/build/...` | 手動で再構成したいとき |
| **キャッシュの削除と再生成** | `rmdir /s build` してから構成 | **困ったときの第一手** |
| **キャッシュの表示** | `CMakeCache.txt` を開く | 設定値を確認したいとき |

「キャッシュの削除と再生成」は、第2章8節で述べた「`build` を消してやり直す」をGUIから行うものだ。CMakeで原因不明の問題に遭遇したら、まずこれを試す。

### 自動構成を止めたいとき

VSは既定で、`CMakeLists.txt` を保存すると自動的に再構成する。大きなプロジェクトでは、編集のたびに数十秒待たされることになる。

**ツール → オプション → CMake → 全般** に「構成ステップを自動的に実行しない」相当の設定がある。ここをオフにすると、明示的に「CMake キャッシュの生成」を実行するまで再構成されなくなる。

## 3.4　デバッグと `launch.vs.json`

### 起動項目を選ぶ

ツールバーの緑の実行ボタンの隣に、起動項目のドロップダウンがある。CMakeプロジェクトでは、**実行可能ファイルのターゲットが自動的に列挙される**。

```
hello.exe
```

これを選んで F5 を押せば、デバッガ付きで起動する。`main.cpp` にブレークポイントを置けば、普通のVSプロジェクトとまったく同じようにデバッグできる。**CMakeにしてもデバッグ体験は何も失われない。** これは強調しておきたい。

### 引数や環境変数を渡す — `launch.vs.json`

コマンドライン引数を渡したい場合、`launch.vs.json` を編集する。作り方は、

- CMakeターゲットビューでターゲットを右クリック →「デバッグ構成の追加」
- または、起動項目のドロップダウンから「デバッグと起動の設定」

すると `.vs\launch.vs.json` が作られる（プロジェクトルートに作られる場合もある）。

```json
{
  "version": "0.2.1",
  "defaults": {},
  "configurations": [
    {
      "type": "default",
      "project": "CMakeLists.txt",
      "projectTarget": "hello.exe",
      "name": "hello.exe",
      "args": [
        "--input",
        "sample.ppm"
      ],
      "currentDir": "${workspaceRoot}/data",
      "env": {
        "PIXKIT_LOG_LEVEL": "debug"
      }
    }
  ]
}
```

| フィールド | 意味 |
| --- | --- |
| `projectTarget` | どのCMakeターゲットを起動するか |
| `args` | コマンドライン引数の配列 |
| `currentDir` | 作業ディレクトリ。**既定は実行ファイルのある場所** |
| `env` | 追加の環境変数 |

`currentDir` は地味に重要だ。テスト用のデータファイルを相対パスで開くプログラムは、作業ディレクトリが違うだけで動かなくなる。第15章でテストデータの扱いを設計するときに、この問題を正面から扱う。

> **`launch.vs.json` はバージョン管理に入れるか**
> 入れてよい。チームで共通の起動設定を共有したいなら、`.vs\` の外（プロジェクトルート）に置いてコミットする。ただし絶対パスや個人の環境変数を書かないよう注意する。

## 3.5　CMakeのエラーメッセージを読む

CMakeのエラーは独特の形をしている。読み方を知っておくと、デバッグ時間が大きく変わる。

### わざとエラーを起こしてみる

`CMakeLists.txt` を次のように壊す。

```cmake
cmake_minimum_required(VERSION 3.28)
project(hello LANGUAGES CXX)
add_executable(hello main.cpp missing.cpp)   # 存在しないファイル
```

保存すると再構成が走り、出力ウィンドウにこう出る。

```
CMake Error at CMakeLists.txt:3 (add_executable):
  Cannot find source file:

    missing.cpp

  Tried extensions .c .C .c++ .cc .cpp .cxx .cu .mpp .m .M .mm .ixx .cppm ...


CMake Error at CMakeLists.txt:3 (add_executable):
  No SOURCES given to target: hello
```

### 読み方

```
CMake Error at CMakeLists.txt:3 (add_executable):
              ^^^^^^^^^^^^^^ ^  ^^^^^^^^^^^^^^
              ファイル      行  コマンド
```

**「どのファイルの何行目の、どのコマンドで」**が必ず示される。まずここを見る。

### コールスタックが出る場合

自作の関数や `add_subdirectory` の中でエラーが起きると、呼び出し履歴が付く。

```
CMake Error at cmake/PixkitHelpers.cmake:12 (message):
  pixkit_add_library: SOURCES is required
Call Stack (most recent call first):
  src/core/CMakeLists.txt:5 (pixkit_add_library)
  src/CMakeLists.txt:2 (add_subdirectory)
  CMakeLists.txt:20 (add_subdirectory)
```

**下から上に読む。** 一番下がトップレベルの `CMakeLists.txt`、一番上が実際にエラーが起きた場所だ。第5章で自作関数を書くようになると、この形式を頻繁に見ることになる。

### 「エラーではない」エラー表示に注意

CMakeプロジェクトを開いた直後、まだ構成が終わっていない段階では、エラー一覧ウィンドウに大量の赤い波線が出ることがある。これは**IntelliSenseがまだ情報を持っていないだけ**で、CMakeのエラーではない。区別する方法は、

- **出力ウィンドウの「CMake」** に出るもの → 本物のCMakeエラー
- **エラー一覧の「IntelliSense」** に出るもの → 構成が終われば消えることが多い

構成が `Build files have been written to:` で終わっているのに赤線が残る場合は、次節に進む。

## 3.6　IntelliSenseが効かないときに見る場所

CMakeプロジェクトでIntelliSenseが壊れると、開発効率が大きく落ちる。原因は毎回だいたい同じ場所にある。上から順に確認する。

### 1. 構成が成功しているか

出力ウィンドウ（CMake）の最後が `Build files have been written to:` で終わっているか。ここが失敗していると、IntelliSenseは何の情報も得られない。まずCMakeエラーを直す。

### 2. そのファイルがターゲットに含まれているか

**IntelliSenseはCMakeのターゲット情報から設定を取得する。** `add_executable` にも `add_library` にも含まれていないファイルを開くと、インクルードパスもマクロ定義も分からないため、ヘッダが見つからず赤線だらけになる。

新しく `.cpp` を追加したのに `CMakeLists.txt` に書き忘れている、というのが最頻出の原因だ。

### 3. インクルードパスが本当に通っているか

`target_include_directories` の書き忘れや、`PRIVATE` にすべきものを書き間違えているケース。これは**IntelliSenseが正しく壊れている**状態で、実際にビルドしても失敗するはずだ。ビルドが通るかどうかで切り分ける。

### 4. キャッシュを作り直す

**プロジェクト → キャッシュの削除と再生成**。VSのIntelliSenseデータベースが古い情報を掴んだままになっている場合、これで直る。

### 5. `.vs` フォルダを消す

VSを閉じて `.vs\` を削除し、開き直す。IntelliSenseのデータベースが壊れた場合の最終手段だ。ビルド結果には影響しないので安全に試せる。

### 切り分けの原則

```
コマンドラインで cmake -S . -B build && cmake --build build が通るか？
    ├─ 通らない → CMakeLists.txt の問題。IntelliSenseは無関係
    └─ 通る     → VSのIDE統合の問題。キャッシュ再生成 → .vs 削除
```

第2章でコマンドラインからのビルドを覚えたのは、この切り分けができるようにするためでもある。

## 3.7　バージョン管理に入れるもの・入れないもの

この時点での `.gitignore` をまとめておく。

```gitignore
# CMakeのビルドディレクトリ
build/
build-*/
out/

# Visual Studio のローカル設定
.vs/

# 個人用プリセット（第4章）
CMakeUserPresets.json
```

| ファイル | コミットする？ | 理由 |
| --- | --- | --- |
| `CMakeLists.txt` | **する** | ソースそのもの |
| `CMakePresets.json` | **する** | チームで共有するビルド設定（第4章） |
| `CMakeUserPresets.json` | しない | 個人の環境依存設定（第4章） |
| `launch.vs.json` | してもよい | チーム共通のデバッグ設定なら |
| `build/`, `out/` | しない | 生成物 |
| `.vs/` | しない | IDEのローカルキャッシュ |
| `CMakeCache.txt` | **絶対にしない** | 絶対パスが埋め込まれている |
| 生成された `.sln` / `.vcxproj` | **絶対にしない** | 生成物 |

`CMakeCache.txt` には `C:/Users/あなたの名前/...` のような絶対パスが大量に入っている。これをコミットすると、他のメンバーの環境で謎の失敗を起こす。

## ハンズオン：VSで開いてデバッグする

### 手順1：フォルダーを開く

Visual Studio 2026 を起動 → **ファイル → 開く → フォルダー** → `C:\work\hello`

出力ウィンドウを **表示 → 出力** で開き、ドロップダウンから **「CMake」** を選ぶ。構成のログが流れることを確認する。

### 手順2：ビルドディレクトリを確認する

エクスプローラで `C:\work\hello` を見る。`out\build\x64-debug\` ができているはずだ。第2章で自分が作った `build\` とは別物であることを確認する。

### 手順3：CMakeターゲットビューに切り替える

ソリューションエクスプローラのツールバーから「CMake ターゲット ビュー」を選ぶ。`hello` ターゲットが見えることを確認する。

### 手順4：デバッグする

1. `main.cpp` の `std::cout` の行にブレークポイント（F9）を置く
2. 起動項目のドロップダウンが `hello.exe` になっていることを確認
3. F5 で実行

ブレークポイントで止まれば成功だ。

### 手順5：引数を受け取れるようにして、`launch.vs.json` で渡す

`main.cpp` を書き換える。

```cpp
#include <iostream>

int main(int argc, char** argv)
{
    std::cout << "Hello, CMake!\n";
    std::cout << "argc = " << argc << '\n';
    for (int i = 0; i < argc; ++i) {
        std::cout << "  argv[" << i << "] = " << argv[i] << '\n';
    }
    return 0;
}
```

CMakeターゲットビューで `hello` を右クリック →「デバッグ構成の追加」→ `launch.vs.json` に `args` を追加する。

```json
"args": [ "alpha", "beta" ]
```

F5 で実行し、出力を確認する。

```
Hello, CMake!
argc = 3
  argv[0] = C:\work\hello\out\build\x64-debug\hello.exe
  argv[1] = alpha
  argv[2] = beta
```

### 手順6：構成を切り替える

ツールバーの構成を `x64-Release` に変更する。出力ウィンドウで再構成が走ることと、`out\build\x64-release\` が新たに作られることを確認する。

### 手順7：わざとエラーを出して読む

`CMakeLists.txt` の3行目を次のように壊して保存する。

```cmake
add_executable(hello main.cpp missing.cpp)
```

出力ウィンドウに出るエラーの、**ファイル名・行番号・コマンド名**を読み取る。確認したら元に戻す。

### 発展課題

1. **プロジェクト → キャッシュの削除と再生成** を実行し、`out\build\x64-debug\` が作り直される様子を出力ウィンドウで追う
2. `launch.vs.json` に `"currentDir": "${workspaceRoot}"` を追加し、`argv[0]` の表示がどう変わるか（変わらないか）を確認する
3. コマンドラインで `cmake --build out\build\x64-debug` を実行し、VSが作ったビルドディレクトリをCLIからもビルドできることを確かめる

## この章のまとめ

- CMakeプロジェクトは `.sln` ではなく **「フォルダーを開く」** で開く。VSは裏で `cmake` を実行しているだけで、出力ウィンドウの「CMake」でそのログが読める
- VSの既定のビルドディレクトリは `out\build\<構成名>\`、既定のジェネレータは **Ninja**
- ソリューションエクスプローラは**フォルダービュー**と **CMakeターゲットビュー**を切り替えられる。ターゲット単位のビルドは後者から行う
- デバッグ体験は通常のVSプロジェクトと変わらない。引数・作業ディレクトリ・環境変数は `launch.vs.json` で設定する
- CMakeエラーは「ファイル:行 (コマンド)」の形で出る。コールスタックは**下から上に**読む
- IntelliSenseが壊れたら、①構成成功の確認 → ②ターゲットに含まれているか → ③キャッシュ再生成 → ④`.vs` 削除、の順に見る。コマンドラインでビルドが通るかどうかが切り分けの基準になる
- `build/`、`out/`、`.vs/`、`CMakeCache.txt`、生成された `.sln` はコミットしない

ここまでで、VSとコマンドラインの両方からCMakeを扱えるようになった。しかし現状には問題がある。**VSが使う設定（`out\build\x64-debug`）と、コマンドラインで自分が使う設定（`build\`）が別物**なのだ。これでは「手元では通るがCIで落ちる」が起きる。

次の第4章では、`CMakePresets.json` を導入して、**VSとコマンドラインとCIが完全に同じ設定を共有する**状態を作る。
