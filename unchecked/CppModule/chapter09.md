# 第9章 モジュールパーティション入門

## この章について

第3部に入ります。ここまでは `Vector` という1つの型を育ててきましたが、ここからは**複数の部品をどう組み立てるか**が主題になります。

この章で扱うのは**モジュールパーティション**です。1つのモジュールを、複数のファイルに分割する仕組みです。

大事なのは、これが何を解決して、何を解決しないかです。先に結論を書いておきます。

- パーティションは、**ファイルが大きすぎる**という問題を解決します
- パーティションは、**利用者が余計なものまで取り込んでしまう**という問題を解決しません

2番目が意外に思えるかもしれません。9.5 で実際に確かめます。この性質を知らずにパーティションを使うと、期待した効果が得られずに困惑することになります。

そして、この章では第4章で立てた計画を一度**保留**にします。当時はパーティションを知らなかったので、選択肢が1つしかありませんでした。いま2つ目の選択肢が手に入るので、最終的な構成は第12章まで決めずにおきます。

## 9.1 ファイルが増えてきた ── 分割の動機

### 9.1.1 いまの `Vector.ixx`

第8章を終えた時点で、`Vector.ixx` の中身はこうなっています。

| 内容 | だいたいの行数 |
|---|---|
| `FloatingPoint` コンセプト | 3 |
| `kEpsilon` | 2 |
| `Vector<T, N>` テンプレート | 70 |
| エイリアス4つ | 5 |
| 演算子と `Dot` / `Cross` | 50 |
| `Orthogonal` の宣言 | 3 |
| `BasisPair` と `MakeBasis` | 10 |

150行ほどです。まだ読める量ですが、性質の違うものが同居し始めています。「ベクトルの演算」と「座標系の構築」は、別の関心事です。

### 9.1.2 これから足すもの

そして、これから追加する予定のものがあります。

- `Matrix4x4` と変換行列(第13章)
- `Quaternion` と補間(第14章)
- `AABB` / `Sphere` / `Ray` / `Plane` と衝突判定(第15章)

これらを全部 `Vector.ixx` に書き足すと、1000行を超えます。1つのファイルとしては明らかに大きすぎます。

分割が必要です。問題は、**どう分割するか**です。

### 9.1.3 選択肢1 ── モジュールを増やす

第4章 4.5.5 で示した方法です。型ごとに独立したモジュールを作ります。

```cpp
// Vector.ixx
export module gamemath.vector;
namespace gamemath { export struct Vector { /* ... */ }; }
```

```cpp
// Matrix.ixx
export module gamemath.matrix;
import gamemath.vector;
namespace gamemath { export struct Matrix4x4 { /* ... */ }; }
```

利用者はこう書きます。

```cpp
import gamemath.vector;
import gamemath.matrix;
```

**長所は、利用者が必要なものだけを取り込めること**です。`Vector` しか使わないファイルは、`Matrix` の `.ifc` を読み込みません。ビルド時間に直結します。

**短所もあります。**

第一に、**利用者がライブラリの内部構造を知る必要があります。** 「`Cross` はどのモジュール?」「`Transform` は?」と、いちいち調べなければなりません。ヘッダの時代に `#include "GameMath/Vector3.h"` と書いていたのと変わりません。

第二に、**どこにも属さない関数が出てきます。** たとえば「行列でベクトルを変換する関数」は、ベクトルの機能でしょうか、行列の機能でしょうか。どちらに置いても不自然です。

第三に、**利用者のコードが壊れやすくなります。** ライブラリの内部構成を変えると、利用者の `import` を書き直してもらう必要があります。

### 9.1.4 選択肢2 ── パーティション

もう1つの方法があります。**モジュールは1つのまま、ファイルだけを分ける**というやり方です。

```cpp
// GameMath.ixx  ── 表の顔
export module gamemath;
export import :vector;
export import :matrix;
```

```cpp
// Vector.ixx  ── 中身の一部
export module gamemath:vector;
namespace gamemath { export struct Vector { /* ... */ }; }
```

利用者はこう書きます。

```cpp
import gamemath;
```

1行です。何がどのファイルにあるかを知る必要がありません。ライブラリの内部構成を変えても、利用者は影響を受けません。

これが**モジュールパーティション**です。

代償があります。**利用者は全部を取り込むことになります。** `Vector` しか使わなくても、`Matrix` も `Quaternion` も込みです。

### 9.1.5 第4章の計画を保留にする

第4章 4.5.6 で、こういう表を示しました。

| モジュール名 | 名前空間 |
|---|---|
| `gamemath.vector` | `gamemath` |
| `gamemath.matrix` | `gamemath` |
| ... | ... |

あれは選択肢1の構成です。当時はパーティションを知らなかったので、そう書くしかありませんでした。

いま、選択肢が2つになりました。そして実は、**両方を組み合わせる**という第3の道もあります。第12章で決めます。

この章では、まずパーティションを使える状態にします。**`gamemath.vector` を、モジュール `gamemath` のパーティション `:vector` に作り替えます。**

## 9.2 `gamemath:vector` パーティションを作る

### 9.2.1 `Vector.ixx` をパーティションにする

`Vector.ixx` の1行目だけを変えます。

```cpp
// Vector.ixx
export module gamemath:vector;   // ← ドットがコロンになった
```

たった1文字の違いですが、意味はまったく違います。

| 書き方 | 意味 |
|---|---|
| `export module gamemath.vector;` | **`gamemath.vector`** という名前の、独立したモジュール |
| `export module gamemath:vector;` | モジュール **`gamemath`** の、**`vector`** という名前のパーティション |

ドット(`.`)は名前の一部にすぎませんでした(第3章 3.2.4)。コロン(`:`)は違います。**コロンの左がモジュール名、右がパーティション名**という、文法上の意味を持っています。

このファイルは**モジュールインターフェイスパーティション単位**になりました。`.ifc` は生成されます。拡張子は `.ixx` のままで構いません。

### 9.2.2 プライマリモジュールインターフェイス単位を作る

いま、`gamemath` というモジュールにはパーティションしかありません。「表の顔」がない状態です。

第5章 5.2.4 の表を思い出してください。

> **プライマリモジュールインターフェイス単位** ── `export module M;` ── モジュールの外向きの顔。**1モジュールに1つだけ**

これを作ります。新しいファイル `GameMath.ixx` を追加してください。

```cpp
// GameMath.ixx
export module gamemath;
```

1行だけです。

### 9.2.3 利用側を書き換える

`main.cpp` の `import` を変えます。

```cpp
// main.cpp
import std;
import gamemath;      // ← gamemath.vector ではなくなった
```

### 9.2.4 ビルドすると失敗する

ビルドしてください。エラーになります。

```
error C2065: 'Vector3': 定義されていない識別子です。
```

`main.cpp` は `gamemath` を `import` しましたが、`gamemath` の表の顔(`GameMath.ixx`)には何も書いてありません。`Vector` は `:vector` パーティションの中にありますが、そのことを表の顔が知らないからです。

さらに、パーティションについての規則違反も起きています。

**モジュールのすべてのインターフェイスパーティションは、プライマリモジュールインターフェイス単位から(直接または間接に)`import` されていなければなりません。**

これは C++ の規則です。「作ったのに誰も使っていないパーティション」は許されません。表の顔が、自分のモジュールの全パーツを把握している必要があります。

つなぎます。

## 9.3 `export import :vector;` でつなぐ

### 9.3.1 プライマリから `import` する

`GameMath.ixx` に1行足します。

```cpp
// GameMath.ixx
export module gamemath;

export import :vector;
```

ビルドして実行してください。**通ります。** 第8章と同じ出力になるはずです。

```
a + b      = (5.00, 7.00, 9.00)
Cross      = (-3.00, 6.00, -3.00)
...
```

### 9.3.2 `import :vector;` という書き方

書き方に注目してください。

```cpp
export import :vector;
```

**モジュール名を書きません。** `import gamemath:vector;` ではありません。コロンから始まります。

パーティションは、そのモジュールの中からしか `import` できません(9.5 で確認します)。だから「どのモジュールのパーティションか」は自明で、書く必要がないのです。

書ける場所も限られます。**モジュールプリアンブル**(モジュール宣言の直後、最初の宣言より前)です。第6章 6.4.2 で `import std;` について説明したのと同じ位置です。

### 9.3.3 【実験】`export` を外すとどうなるか

`export` を外してみてください。

```cpp
// GameMath.ixx
export module gamemath;

import :vector;      // ← export を削除
```

ビルドしてください。**エラーになります。**

```
error C2065: 'Vector3': 定義されていない識別子です。
```

規則違反は解消しました(プライマリが `:vector` を `import` しているので)。しかし `main.cpp` からは `Vector3` が見えません。

違いはこうです。

| 書き方 | `GameMath.ixx` の中から使えるか | `import gamemath;` した側から使えるか |
|---|---|---|
| `import :vector;` | ○ | **✕** |
| `export import :vector;` | ○ | ○ |

`export import` は、**取り込んだうえで、それを自分の公開インターフェイスの一部として再公開する**という指定です。「再エクスポート」と呼びます。

`import` だけなら、取り込むだけで再公開はしません。プライマリの中でだけ使える状態です。

**`export` を戻してください。**

> **`export import` は標準ライブラリにも使える**
>
> `export import std;` と書けば、`import gamemath;` した側で `std::` の中身が使えるようになります。
>
> **やらないでください。** 第6章 6.5.4 で書いたとおり、利用者の環境を選ぶライブラリになってしまいます。`import std;`(`export` なし)にとどめるのが正解です。
>
> `export import` を使うのは、パーティションをつなぐときと、第12章で作る「傘」のモジュールだけです。

### 9.3.4 名前空間との関係

ここで1つ、紛らわしいことが起きています。

- **モジュール名**が `gamemath` になりました
- **名前空間**も `gamemath` です

第4章 4.5 で「モジュール名と名前空間は別物」と繰り返し確認しました。いま、その2つがたまたま同じ名前になっています。

混乱しないでください。相変わらず別物です。

```cpp
export module gamemath:vector;    // ← モジュール gamemath のパーティション vector

namespace gamemath {              // ← 名前空間 gamemath
    export struct Vector { /* ... */ };
}
```

パーティション名 `vector` は、名前空間には何の影響も与えません。`gamemath::vector::Vector3` などという名前は存在しません。相変わらず `gamemath::Vector3` です。

第4章 4.5.6 で書いたとおり、名前を揃えるのは人間のための慣習です。今回それが「モジュール名 = 名前空間名」という形になっただけです。

## 9.4 パーティションを増やす

パーティションが1つでは、分割した意味がありません。増やします。

### 9.4.1 `:basis` パーティションを作る

`Vector.ixx` から、座標系の構築に関するもの ── `Orthogonal`、`BasisPair`、`MakeBasis` ── を切り出します。

新しいファイル `Basis.ixx` を追加してください。

```cpp
// Basis.ixx
export module gamemath:basis;

import :vector;

namespace gamemath {

export template <FloatingPoint T>
Vector<T, 3> Orthogonal(const Vector<T, 3>& v);

export struct BasisPair
{
    Vector3 tangent;
    Vector3 bitangent;
};

export BasisPair MakeBasis(const Vector3& normal);

} // namespace gamemath
```

`Vector.ixx` からは、対応する3つを削除します。

### 9.4.2 パーティションからパーティションを `import` する

`Basis.ixx` の2行目に注目してください。

```cpp
import :vector;
```

`Basis.ixx` は `Vector` と `FloatingPoint` を使っています。だから `:vector` パーティションを `import` する必要があります。

**同じモジュールのパーティションどうしでも、`import` は必要です。** 「同じモジュールだから自動的に見える」ということはありません。

ここで、`export import` ではなく `import` にしている点も重要です。`:basis` が `:vector` を再エクスポートする必要はありません。`GameMath.ixx` が両方を `export import` するので、利用者には両方届きます。

もう1つ、覚えておくべき性質があります。

**同じモジュールのパーティションを `import` すると、`export` されていない宣言も見えます。**

普通のモジュールを `import` したときは、`export` されたものだけが見えました(第7章 7.4.3)。パーティションは違います。同じモジュールの一部なので、内部事情まで共有されます。

だから `Basis.ixx` は、`Vector.ixx` にある `kEpsilon`(`export` していない)も使えます。この性質は、第10章の内部パーティションで本格的に使うことになります。

### 9.4.3 プライマリにつなぐ

`GameMath.ixx` に足します。

```cpp
// GameMath.ixx
export module gamemath;

export import :vector;
export import :basis;
```

`:basis` も、プライマリから `import` されていなければなりません(9.2.4 の規則)。

### 9.4.4 実装単位はどうなるか

`Vector.cpp` には `Orthogonal` の定義(と明示的インスタンス化)、`MakeBasis` の定義が入っています。ファイル名を `Basis.cpp` に変え、モジュール宣言を書き換えてください。

```cpp
// Basis.cpp
module gamemath;              // ← gamemath.vector から変更

import std;

namespace gamemath {

template <FloatingPoint T>
Vector<T, 3> Orthogonal(const Vector<T, 3>& v)
{
    // ...(変更なし)
}

template Vector<float, 3>  Orthogonal(const Vector<float, 3>&);
template Vector<double, 3> Orthogonal(const Vector<double, 3>&);

BasisPair MakeBasis(const Vector3& normal)
{
    // ...(変更なし)
}

} // namespace gamemath
```

`module gamemath;` と書いています。パーティション名は付けません。**これはモジュール `gamemath` 全体の実装単位**です。

第5章 5.4.1 で「実装単位はプライマリインターフェイス単位を暗黙に `import` する」と説明しました。プライマリ(`GameMath.ixx`)が `:vector` と `:basis` を `export import` しているので、この実装単位からは両方の中身が見えます。だから `import :vector;` などを書く必要はありません。

ただし `import std;` は必要です。第6章 6.4.3 で確認したとおり、`import` は伝播しないからです。

ビルドして実行してください。第8章と同じ出力になれば成功です。

### 9.4.5 パーティション名の決まりごと

整理しておきます。

**書式は `モジュール名:パーティション名`**

```cpp
export module gamemath:vector;
```

コロンは1つだけです。`gamemath:core:vector` のような入れ子はできません。**パーティションは1階層だけ**です。

**パーティション名にドットは使える**

```cpp
export module gamemath:geometry.shapes;   // 有効
```

ただし、これも階層構造を作るわけではありません。ドットは名前の一部です(第3章 3.2.4 と同じ)。

**モジュール内で一意**

同じモジュールに `:vector` を2つ作ることはできません。

**外からは見えない名前**

パーティション名は、モジュールの内部でしか使いません。利用者は知る必要も、知る手段もありません(9.5)。

### 9.4.6 ファイル配置との対応

言語仕様は、パーティション名とファイル名の対応を**一切規定していません**。第3章 3.2.4 でモジュール名について書いたのと同じです。

とはいえ、規約は必要です。本書では次のようにします。

| パーティション | ファイル(インターフェイス) | ファイル(実装) |
|---|---|---|
| `gamemath:vector` | `Vector.ixx` | ── |
| `gamemath:basis` | `Basis.ixx` | `Basis.cpp` |
| (プライマリ) | `GameMath.ixx` | ── |

**規約1: パーティション名 = ファイル名(大文字始まり)**

`:vector` → `Vector.ixx`。探しやすさのためです。

**規約2: プライマリはモジュール名と同じファイル名**

`gamemath` → `GameMath.ixx`。ソリューションエクスプローラーで見たとき、これが「表の顔」だと一目で分かります。

**規約3: 実装単位は対応するインターフェイスと同じ名前の `.cpp`**

`Basis.ixx` の実装は `Basis.cpp`。ヘッダと `.cpp` の対応と同じ感覚です。

規約はプロジェクトごとに決めて構いませんが、**決めて守ること**が大事です。モジュール名とファイル名の対応が言語で保証されない以上、規約だけが手がかりになります。

### 9.4.7 現時点の全体像

```
GameMath/
├── GameMath.ixx    export module gamemath;         ← プライマリ
│                   export import :vector;
│                   export import :basis;
│
├── Vector.ixx      export module gamemath:vector;  ← インターフェイスパーティション
├── Basis.ixx       export module gamemath:basis;   ← インターフェイスパーティション
│                   import :vector;
│
├── Basis.cpp       module gamemath;                ← 実装単位
│
└── main.cpp        import gamemath;
```

利用者から見えるのは、いちばん下の `import gamemath;` だけです。上の4ファイルがどう分かれていようと、利用者には関係ありません。

**これがパーティションの本質です。** 内部構成を、外から見た姿と切り離せる。

## 9.5 パーティションは外部から直接 `import` できない

さて、9.1.4 で書いた「代償」を確認します。

### 9.5.1 【実験】やってみる

`Vector` しか使わないファイルは、`:vector` だけを取り込みたくなります。試してみましょう。

```cpp
// main.cpp
import std;
import gamemath:vector;      // ← パーティションを直接指定
```

ビルドしてください。**エラーになります。**

「パーティションは、同じモジュールの中からしか `import` できない」という趣旨のメッセージが出ます。

**元に戻してください**(`import gamemath;`)。

### 9.5.2 これは制限ではなく設計

「不便だ」と感じるかもしれません。しかし、これは意図された設計です。

パーティションは、**モジュールの内部構造**です。内部構造とは、作者が自由に変えてよいもののことです。

もし利用者が `import gamemath:vector;` と書けたら、パーティションの構成は公開 API の一部になってしまいます。`:vector` を `:vector_core` と `:vector_ops` に分けたくなっても、利用者のコードを壊すことになります。

「内部構造を外から見えなくする」── これは第7章 7.2 で `export` について確認したことと、まったく同じ発想です。C++20 のモジュールは、**公開するものと隠すものを分ける**という原則を、宣言のレベルでも、ファイル構成のレベルでも一貫して適用しています。

### 9.5.3 パーティションと「サブモジュール」

紛らわしいので、はっきり区別しておきます。

C++ には、`gamemath.vector` のようにドットで名付けた**独立したモジュール**を「サブモジュール」と呼ぶ慣習があります(言語仕様上の用語ではありません)。

| | パーティション | サブモジュール |
|---|---|---|
| 書き方 | `export module gamemath:vector;` | `export module gamemath.vector;` |
| 区切り | コロン | ドット(名前の一部) |
| 実体 | **1つのモジュールの一部** | **独立したモジュール** |
| 外から `import` できるか | **できない** | できる |
| プライマリへの `import` | **必須** | 不要 |
| 利用者の書き方 | `import gamemath;` | `import gamemath.vector;` |
| 目的 | ファイルの分割 | 依存の分割 |

見た目が1文字しか違わないのに、性質は正反対です。

**パーティションは「ファイルを分けたい」ときに使います。**
**サブモジュールは「利用者に選ばせたい」ときに使います。**

第9章の冒頭で書いた結論に戻ります。

> パーティションは、ファイルが大きすぎるという問題を解決します。
> パーティションは、利用者が余計なものまで取り込んでしまうという問題を解決しません。

### 9.5.4 では、どちらを選ぶべきか

`GameMath` はどうすべきでしょうか。

- 利用者に `import gamemath;` の1行で済ませたい → パーティション
- `Vector` しか使わない人に `Quaternion` を読ませたくない → サブモジュール

両方欲しい、というのが正直なところです。そして実際、**両方を組み合わせることができます。**

```
gamemath.core       ← サブモジュール(独立して import できる)
  :vector           ← パーティション(内部の分割)
  :matrix
  :quaternion

gamemath.geometry   ← サブモジュール
  :shapes
  :intersect

gamemath            ← 傘。export import で両方を再公開
```

利用者は、必要に応じて選べます。

```cpp
import gamemath;           // 全部欲しい人
import gamemath.core;      // 数学だけでいい人
```

これが第12章で組み立てる構成です。この章では、その部品である**パーティション**を手に入れました。

いまの `GameMath` は「1つのモジュール + 2つのパーティション」という、最も単純な形です。第13章以降で型が増えたところで、第12章の設計に作り替えます。

## 9.6 この章のまとめ

- **モジュールパーティション**は、1つのモジュールを複数のファイルに分割する仕組み
- 書き方は `export module モジュール名:パーティション名;`。**コロンは文法上の意味を持つ**(ドットとは違う)
- **プライマリモジュールインターフェイス単位**(`export module M;`)は1つだけ。すべてのインターフェイスパーティションを直接または間接に `import` しなければならない
- プライマリから `export import :P;` すると、パーティションの公開内容が利用者に届く
- `export` なしの `import :P;` だと、プライマリの中でしか使えない
- パーティションを `import` するときはモジュール名を書かない(`import :vector;`)
- **同じモジュールのパーティションどうしでも `import` は必要**
- ただし、パーティションを `import` すると `export` されていない宣言も見える
- 実装単位(`module M;`)は、プライマリを暗黙に `import` するので、パーティションの内容も届く
- パーティション名は1階層のみ。ファイル名との対応は言語仕様では決まっていないので、規約で決める
- **パーティションは外部から直接 `import` できない。** これは内部構造を隠すための設計
- パーティション(ファイルの分割)とサブモジュール(依存の分割)は、目的が違う。組み合わせて使える

## 次章に向けて

この章で作ったパーティションは、どちらも `export` するもの ── **インターフェイスパーティション**でした。

しかし、`Basis.ixx` は `Vector.ixx` の内部事情(`kEpsilon`)を使っています。9.4.2 で触れたとおり、パーティションどうしでは非公開の宣言も見えるからです。

では、**複数のパーティションで共有したいが、絶対に外へ出したくない**ものはどこに置けばよいでしょうか。`Vector.ixx` に紛れ込ませるのは、置き場所として不自然です。

第10章では、**内部パーティション**(`module M:P;`)という、`export` を一切書けないパーティションを扱います。実装単位に似ていますが、`.ifc` を生成する点が違います。「モジュール内部の共有ヘッダ」のような位置づけです。

インターフェイスパーティションと内部パーティションの使い分けは、慣れるまで迷いやすいところです。早見表を用意します。
