# 第7章 エクスポートされるもの・されないもの

## この章について

この章には、新しい構文が1つも出てきません。

代わりに扱うのは、**「公開する」とは何を意味するのか**という問題です。第3章で `export` を覚え、第5章で実装単位を作り、第6章で標準ライブラリを取り込みました。道具は揃っています。しかし、その道具が正確には何をしているのかを、私たちはまだ曖昧にしたまま進んできました。

具体的には、こういう問いに答えられるようにします。

- `export` していない関数は、`.ifc` の中に存在するのか。しないのか
- 存在するとしたら、それは「隠れている」と言えるのか
- `static` を付けるのと `export` しないのは、何が違うのか
- 公開した関数の戻り値の型を公開し忘れたら、どうなるのか

最後の問いが、この章の山です。答えは「**エラーにならず、しかも使える。ただし型に名前が付けられない**」という奇妙なものになります。

このあたりの挙動を、C++ の規格は **「見える(visible)」** と **「到達可能(reachable)」** という2つの言葉で説明します。第3章 3.5.5 で予告し、以来ずっと先送りにしてきた区別です。

地味なテーマです。しかし、ここを飛ばすと第8章のテンプレートで必ず行き詰まります。急がずに読んでください。

## 7.1 マクロは決してエクスポートされない

まず、いちばんはっきりしているところから。

### 7.1.1 これまでに確認したこと

すでに2回、実物で確認しています。

- 第3章 3.6.4 ── `hello.ixx` で `#define HELLO_VERSION 100` を定義しても、`import` した側では使えなかった
- 第6章 6.3.3 ── グローバルモジュールフラグメントで定義したマクロも漏れない

規則は単純です。

**名前付きモジュールは、マクロをエクスポートしません。例外はありません。**

`export` を付ける方法もありません。`export #define` という構文は存在しないからです。

### 7.1.2 なぜ原理的に不可能なのか

これは「そう決めた」というより、「そうするしかない」という話です。

マクロはプリプロセッサの世界のものです。プリプロセッサは、コンパイラが C++ を理解し始める**前**に動きます(第1章 1.1.2)。

一方、`.ifc` に入っているのは、コンパイラが**解析した後**の構造化データです。宣言、型、関数の本体 ── C++ の意味の世界のものです。

この2つは、そもそも住んでいる時間軸が違います。`.ifc` を読み込む時点では、プリプロセッサの仕事はとっくに終わっています。マクロを渡す先がないのです。

第1章 1.3.1 で「モジュールはテキストではなく意味を取り込む」と書きました。マクロが漏れないのは、その性質の必然的な帰結です。

### 7.1.3 マクロの代わりに何を使うか

ヘッダの世界でマクロが担っていた役割は、いくつかに分けられます。それぞれに、モジュールで使える代替があります。

**定数** → `constexpr` 変数

```cpp
// ヘッダ時代
#define GAMEMATH_PI 3.14159265f

// モジュール
export constexpr float kPi = 3.14159265f;
```

型が付き、名前空間に入り、デバッガで見えます。マクロより優れています。

**小さな関数** → `constexpr` 関数

```cpp
// ヘッダ時代
#define SQUARE(x) ((x) * (x))

// モジュール
export constexpr float Square(float x) { return x * x; }
```

括弧の付け忘れによる事故が起きません。引数が2回評価される問題もありません。

**型の選択** → テンプレートとコンセプト(第8章)

**設定の切り替え** → ここが問題です

```cpp
#ifdef GAMEMATH_USE_SIMD
// ...
#endif
```

これはモジュール境界を越えられません。利用者が `#define GAMEMATH_USE_SIMD` してもモジュールには届かず、モジュールの中で `#define` しても利用者には届きません。

**マクロで設定を切り替えるという設計は、モジュールでは成立しません。** これは第16章で正面からぶつかる問題です。SIMD の有効・無効をどう切り替えるか ── そこでコンセプトによる代替に書き換えることになります。

### 7.1.4 唯一の例外

「例外はありません」と書きましたが、正確には1つだけあります。

**ヘッダユニット**は、マクロをエクスポートします。

```cpp
import <cstdio>;   // ヘッダユニット。EOF などのマクロも入ってくる
```

ヘッダユニットは「ヘッダファイルをモジュールのように取り込む」仕組みで、名前付きモジュールとは別物です。既存のヘッダを書き換えずに移行するための機能なので、マクロも一緒に運ばれます。

第18章で扱います。ここでは「名前付きモジュールとヘッダユニットは、マクロの扱いが正反対」とだけ覚えておいてください。

## 7.2 モジュールリンケージ

### 7.2.1 3つのリンケージ

第3章 3.5.4 で、C++20 が3つ目のリンケージを追加したことを見ました。整理し直します。

| リンケージ | 名前が通用する範囲 | 従来からあるか |
|---|---|---|
| **内部リンケージ** | その翻訳単位の中だけ | あり |
| **モジュールリンケージ** | **同じモジュールの中だけ** | C++20 で追加 |
| **外部リンケージ** | プログラム全体 | あり |

「同じモジュールの中」というのは、**そのモジュールを構成するすべてのモジュール単位**という意味です。`gamemath.vector` なら、`Vector3.ixx` と `Vector3.cpp` の両方です。

第5章 5.4.2 で、`Vector3.cpp` から非公開の `AbsFloat` を呼べたのは、この範囲に入っていたからです。

### 7.2.2 何がどのリンケージになるか

判定表を作っておきます。

| 宣言の書き方 | 書いた場所 | リンケージ |
|---|---|---|
| `export` あり | モジュールインターフェイス単位の購買域 | 外部リンケージ |
| `export` なし | モジュールの購買域(インターフェイス/実装どちらでも) | **モジュールリンケージ** |
| `static` 付き | モジュールの購買域 | 内部リンケージ |
| 無名名前空間の中 | モジュールの購買域 | 内部リンケージ |
| 何でも | グローバルモジュールフラグメント | 従来どおり(モジュールに属さない) |
| 何でも | 普通の `.cpp`(モジュール宣言なし) | 従来どおり |

大事な点を1つ。**`export` の有無だけで決まるのは、購買域に書いた場合の話です。** GMF に `#include` したヘッダの中身は、モジュールに属さないので従来どおりのリンケージを保ちます。第6章 6.1.5 で見たとおり、これが GMF の存在理由でした。

### 7.2.3 【実験】名前が衝突しない

モジュールリンケージの実用的な効果を確かめます。

`main.cpp` の先頭に、`GameMath` の内部定数と同じ名前の定数を定義してみてください。

```cpp
// main.cpp
import std;
import gamemath.vector;

constexpr float kEpsilon = 999.0f;   // ← 追加。GameMath の内部にも同名がある

int main()
{
    std::println("main の kEpsilon = {}", kEpsilon);
    // ...
}
```

ビルドしてください。**通ります。**

```
main の kEpsilon = 999
```

`gamemath.vector` の中にも `kEpsilon` があります(第6章 6.6.3 で定義しました)。しかし衝突しません。あちらはモジュールリンケージを持っていて、`main.cpp` からは存在しないのと同じだからです。

`gamemath::kEpsilon` と書いてみてください。「識別子が見つかりません」になります。

さらに言えば、`main.cpp` の `kEpsilon` は名前空間 `gamemath` の外にありますが、仮に `namespace gamemath { constexpr float kEpsilon = 999.0f; }` と書いたとしても衝突しません。名前空間が同じでも、モジュールが違えば別物です。

**名前空間が同じでも、モジュールが違えば衝突しない。** これがモジュールリンケージの実用的な価値です。

**確認できたら、追加した行を削除してください。**

### 7.2.4 ヘッダ時代との比較

第1章 1.1.6 で、`detail` 名前空間の限界について書きました。並べて比べます。

| | ヘッダ | モジュール |
|---|---|---|
| 内部ヘルパーの置き場所 | `namespace detail` | `export` しないだけ |
| 利用者から呼べるか | **呼べる**(お願いベース) | 呼べない(言語による保証) |
| 別のライブラリと名前が衝突するか | する | しない |
| 自衛策 | `static` を付ける、名前を長くする | 不要 |
| 実装ファイル間で共有できるか | ヘッダに書けば可能(=公開される) | 可能(かつ非公開のまま) |

最後の行が特に効きます。ヘッダの世界では「複数の `.cpp` で共有したい」と「利用者には見せたくない」が両立しませんでした。共有するにはヘッダに書くしかなく、ヘッダに書けば見えてしまうからです。

モジュールでは両立します。インターフェイス単位に `export` なしで書けば、実装単位からは使えて、外からは見えません。

## 7.3 `static` と無名名前空間の扱い

### 7.3.1 モジュールの中で `static` は何を意味するか

「`export` しなければ隠れるなら、`static` はもう要らないのでは?」

そう思うのが自然です。しかし違います。**隠れる範囲が違います。**

- `export` しない → **モジュール全体**で通用する。他のモジュール単位からは使える
- `static` を付ける → **その1ファイル**でだけ通用する。同じモジュールの他のファイルからも使えない

`static` は従来どおり、内部リンケージを与えます。モジュールが登場しても、この意味は変わりません。

### 7.3.2 【実験】`static` にすると実装単位から見えなくなる

実際に確かめます。2段階で進めます。

**段階1: `kEpsilon` を実装単位から使う**

`Vector3.cpp` の `Orthogonal` に、ゼロベクトルの処理を足します。これは実際に必要な処理でもあります。

```cpp
// Vector3.cpp
module gamemath.vector;

import std;

namespace gamemath {

Vector3 Orthogonal(const Vector3& v)
{
    if (v.LengthSquared() <= kEpsilon) {          // ← kEpsilon を使う
        return Vector3{ 1.0f, 0.0f, 0.0f };
    }

    const float ax = std::abs(v.x);
    const float ay = std::abs(v.y);
    const float az = std::abs(v.z);

    if (ax <= ay && ax <= az) {
        return Cross(v, Vector3{ 1.0f, 0.0f, 0.0f });
    }
    if (ay <= az) {
        return Cross(v, Vector3{ 0.0f, 1.0f, 0.0f });
    }
    return Cross(v, Vector3{ 0.0f, 0.0f, 1.0f });
}

} // namespace gamemath
```

ビルドしてください。通ります。`kEpsilon` は `Vector3.ixx` にあり、`export` されていませんが、同じモジュールなので使えます。

**段階2: `static` を付けてみる**

`Vector3.ixx` の `kEpsilon` に `static` を付けます。

```cpp
// Vector3.ixx
namespace gamemath {

static constexpr float kEpsilon = 1e-6f;   // ← static を追加
```

ビルドしてください。**エラーになります。**

```
error C2065: 'kEpsilon': 定義されていない識別子です。
```

エラーが出ているのは `Vector3.cpp` です。`static` によって `kEpsilon` は内部リンケージになり、`Vector3.ixx` という**ファイルの中**でしか通用しなくなりました。同じモジュールでも、別のファイルからは見えません。

**`static` を削除して、元に戻してください。**

### 7.3.3 使い分け

判断は単純です。

| やりたいこと | 書き方 |
|---|---|
| 外からは隠したいが、同じモジュールの他のファイルからは使いたい | **`export` しないだけ** |
| そのファイルの中だけで使う | **`static` / 無名名前空間** |
| 誰からでも使えるようにする | **`export`** |

実務では、1つ目がほとんどです。

`static` を使うのは、実装単位の中で完全に閉じたヘルパーを書くときぐらいでしょう。それも、モジュールリンケージで足りることが多いので、無理に使う理由はありません。

なお、無名名前空間 ── `namespace { ... }` ── も `static` と同じく内部リンケージを与えます。歴史的に、`static` が使えない場面(型の定義など)のために使われてきましたが、モジュールではその必要も減りました。

### 7.3.4 補足 ── `const` 変数の非対称

細かい話ですが、知らないと混乱するので触れておきます。

C++ では従来、名前空間スコープの `const` 変数は**暗黙に内部リンケージ**を持ちました。ヘッダに `const int kMax = 100;` と書いても、`#include` した翻訳単位ごとに別の実体ができる ── という仕様です。

C++20 では、この規則に例外が追加されました。

**モジュールインターフェイス単位の購買域に書かれた `const` 変数は、暗黙の内部リンケージにならない。**

だから第6章の `constexpr float kEpsilon` は、内部リンケージではなくモジュールリンケージを持ちます。7.3.2 の実験で `Vector3.cpp` から使えたのは、そのおかげです。

一方、**実装単位**に書いた `const` 変数は、従来どおり内部リンケージになります。

```cpp
// Vector3.ixx(インターフェイス単位)
constexpr float kEpsilon = 1e-6f;    // モジュールリンケージ

// Vector3.cpp(実装単位)
constexpr float kLocal = 0.5f;       // 内部リンケージ(このファイルだけ)
```

覚える必要はありません。「定数はインターフェイス単位に置けばモジュール全体で共有できる」とだけ知っておけば十分です。`GameMath` でもそうしています。

## 7.4 「見える」と「到達可能」の違い

ここからが本題です。

### 7.4.1 2つの言葉

C++20 の規格は、モジュールをまたいだ宣言の扱いを、2つの独立した概念で説明します。

**見える(visible)** ── その名前を**書ける**こと。

名前解決(name lookup)が、その宣言を見つけられる状態です。`gamemath::Vector3` と書いてコンパイルが通るなら、`Vector3` は見えています。

**到達可能(reachable)** ── コンパイラが、その宣言の**中身を知っている**こと。

クラスなら、メンバの構成やサイズ。関数なら、本体。テンプレートなら、定義そのもの。これらの情報にコンパイラがアクセスできる状態です。

この2つは独立しています。**見えないが到達可能**、という状態が存在します。

### 7.4.2 なぜ「到達可能」という概念が必要なのか

「公開したものだけを `.ifc` に入れればいいのでは?」と思うかもしれません。

できません。理由を3つ挙げます。

**理由1: インライン展開**

第5章 5.6.1 で見たとおり、コンパイラが関数をインライン展開するには、その**本体**が必要です。`export` された関数の本体は `.ifc` に入っています。ではその関数が、非公開のヘルパー関数を呼んでいたら? ヘルパーの本体も必要です。

**理由2: 型の完全性**

```cpp
export struct Vector3 { float x, y, z; };
```

利用者が `Vector3 v;` と書けるためには、コンパイラが `Vector3` のサイズと構成を知っている必要があります。「名前が見える」だけでは足りません。

**理由3: テンプレート**

これが最大の理由です。テンプレートは、使われた場所で実体化されます。実体化するには**定義そのもの**が必要です。だからテンプレートは、たとえ非公開のヘルパーであっても、定義が届いていなければなりません。

第8章で `Vector<T, N>` を書くとき、この性質が前面に出てきます。

つまり、**モジュールが正しく動くためには、公開していないものも含めて、情報は届いている必要がある**のです。届いているが、名前で呼ぶことは許さない ── それが「到達可能だが見えない」という状態です。

### 7.4.3 規則

規則そのものは短く言えます。

**モジュールを `import` すると、そのモジュールのインターフェイス単位に書かれた宣言は、すべて到達可能になる。そのうち `export` されたものだけが、見える。**

表にすると、こうなります。

| | 見える | 到達可能 |
|---|---|---|
| `export` した宣言(インターフェイス単位) | ○ | ○ |
| `export` しない宣言(インターフェイス単位) | ✕ | **○** |
| 実装単位に書いた宣言 | ✕ | ✕ |
| `static` / 無名名前空間 | ✕ | ✕ |

2行目が、この章の核心です。**`export` しないことは、情報を消すことではありません。** 名前で呼べなくするだけです。

3行目にも注目してください。実装単位に書いたものは、到達可能ですらありません。だから第5章 5.6.1 で、実装単位に移した関数はインライン展開できなくなりました。あれは「到達可能でない」ということだったのです。

### 7.4.4 【実験】到達可能性を確かめる

言葉だけでは実感が湧かないので、動かして確認します。

`Vector3.ixx` に、**`export` を付けない**構造体と、それを返す**`export` 付き**の関数を追加してください。

```cpp
// Vector3.ixx(namespace gamemath の中、Cross の後ろあたり)

// export なし
struct Hidden
{
    float value;
};

// export あり
export Hidden MakeHidden()
{
    return Hidden{ 42.0f };
}
```

`main.cpp` で使ってみます。

```cpp
// main.cpp
int main()
{
    auto h = gamemath::MakeHidden();          // ①
    std::println("h.value = {}", h.value);    // ②

    // gamemath::Hidden x;                    // ③
    // ...
}
```

ビルドして実行してください。

```
h.value = 42
```

**①も②も通ります。**

- ① `MakeHidden()` は `export` されているので呼べます。戻り値を `auto` で受けています
- ② `h.value` にアクセスできています。つまりコンパイラは `Hidden` の中身を知っています

`Hidden` は `export` していないのに、その定義がちゃんと届いているわけです。**これが「到達可能」です。**

では③のコメントを外してみてください。

```
error C2065: 'Hidden': 定義されていない識別子です。
```

**型に名前を付けようとした瞬間に失敗します。** `Hidden` は見えないからです。

まとめると、`main.cpp` からは次のことができます。

| やりたいこと | 可否 |
|---|---|
| `MakeHidden()` を呼ぶ | ○ |
| 戻り値を `auto` で受ける | ○ |
| メンバ `value` を読む | ○ |
| `decltype(gamemath::MakeHidden())` と書く | ○ |
| `gamemath::Hidden x;` と書く | **✕** |
| クラスのメンバ変数として持つ | **✕**(型名が書けないため) |
| 関数の引数や戻り値の型に書く | **✕** |

奇妙な状態です。使えるのに、名前が付けられない。

**確認できたら、`Hidden` と `MakeHidden` を削除してください。** 7.5 で、より現実的な形で扱い直します。

### 7.4.5 到達可能であることのコスト

もう1つ、重要な帰結があります。

**`export` していない宣言も、`.ifc` に入っています。**

到達可能にするために必要だからです。ということは ──

- **`.ifc` のサイズが増えます。** 非公開だからといってタダではありません
- **`import` する側のコンパイル時間に影響します。** 読み込む量が増えるからです
- **非公開の実装を変更しても、`.ifc` が変わり、`import` している側は再コンパイルされます**

3つ目は、第5章 5.1.3 で実際に体験しました。あのとき「実装の一時変数を1つ増やすだけで、依存する全ファイルが再コンパイルされる」と書きました。理由がこれです。インターフェイス単位に書いたものは、公開・非公開を問わず `.ifc` の一部だからです。

第1章 1.3.2 で「カプセル化が言語機能として保証される」と書きました。それは正しいのですが、**カプセル化されているのは名前であって、情報ではありません。**

では、情報そのものを `.ifc` から追い出す手段はないのか ── あります。**プライベートモジュールフラグメント**という仕組みで、第11章で扱います。実装単位に追いやるのとは別の、第3の選択肢です。

## 7.5 エクスポートしていない型が戻り値に出てきたら

7.4.4 は人工的な実験でした。同じことが `GameMath` で起きたらどうなるかを見ていきます。

### 7.5.1 `MakeBasis` を書く

法線ベクトルから、それに垂直な2本のベクトル(接ベクトルと従接ベクトル)を作る関数を追加します。法線マッピングやパーティクルの向き付けで使う、実用的な処理です。

2つの値を返したいので、構造体を用意します。

`Vector3.ixx` に追加してください。**まず `export` を付けずに書きます。**

```cpp
// Vector3.ixx(namespace gamemath の中)

struct BasisPair                     // ← export なし(あとで直します)
{
    Vector3 tangent;
    Vector3 bitangent;
};

export BasisPair MakeBasis(const Vector3& normal);
```

`Vector3.cpp` に定義を書きます。行数もあり、呼び出し頻度も低いので、実装単位が適切です(第5章 5.6.5 の基準)。

```cpp
// Vector3.cpp(namespace gamemath の中)

BasisPair MakeBasis(const Vector3& normal)
{
    const Vector3 n = normal.Normalized();
    const Vector3 t = Orthogonal(n).Normalized();
    const Vector3 b = Cross(n, t);
    return BasisPair{ t, b };
}
```

### 7.5.2 使ってみる

`main.cpp` で呼び出します。

```cpp
// main.cpp(main の中)

const gamemath::Vector3 n = a.Normalized();
const auto basis = gamemath::MakeBasis(n);       // auto で受ける

std::println("MakeBasis: |t| = {:.4f}  |b| = {:.4f}",
             basis.tangent.Length(), basis.bitangent.Length());
std::println("           Dot(n,t) = {:.4f}  Dot(n,b) = {:.4f}  Dot(t,b) = {:.4f}",
             gamemath::Dot(n, basis.tangent),
             gamemath::Dot(n, basis.bitangent),
             gamemath::Dot(basis.tangent, basis.bitangent));
```

ビルドして実行してください。

```
MakeBasis: |t| = 1.0000  |b| = 1.0000
           Dot(n,t) = 0.0000  Dot(n,b) = 0.0000  Dot(t,b) = 0.0000
```

3つの内積がすべて 0 で、長さが 1 ── 正しく直交基底ができています。

**動いてしまいました。** `BasisPair` を `export` していないのに、です。

コンパイラは何も文句を言いません。警告すら出ません。7.4 で学んだとおり、`BasisPair` は到達可能だからです。

### 7.5.3 しかし、利用者は困る

問題は、利用者がこれを**保存しようとしたとき**に現れます。

たとえば、計算した基底をクラスのメンバとして持ちたいとします。

```cpp
// main.cpp
struct Renderer
{
    gamemath::BasisPair basis;   // ← エラー
};
```

```
error C2065: 'BasisPair': 定義されていない識別子です。
```

書けません。型に名前が付けられないからです。

関数に渡すこともできません。

```cpp
void Draw(const gamemath::BasisPair& basis);   // ← エラー
```

`auto` で受けてその場で使い切る分には動くのに、少しでも構造化しようとした瞬間に壁にぶつかります。

しかも、エラーメッセージは「`BasisPair` が定義されていない」です。「`export` されていません」とは言ってくれません。ライブラリの利用者からすれば、**関数は呼べるのに型が存在しない**という理解不能な状況です。

### 7.5.4 これは良い設計か

答えははっきりしています。**悪い設計です。**

原則として、こう覚えてください。

**公開する宣言のシグネチャに現れる型は、必ず公開する。**

- 戻り値の型
- 引数の型
- 公開するクラスの `public` メンバの型
- 公開するテンプレートの引数の型

これらを `export` し忘れると、「動くけれど使いものにならない」という中途半端な状態になります。

コンパイラは警告してくれません。到達可能である以上、規格上は正しいコードだからです。**これは設計者が気をつけるしかない領域です。**

第4章 4.3.2 で「クラスを `export` しても自由関数は `export` されない」という落とし穴を扱いました。今回はその裏返しです。**関数を `export` しても、その型は `export` されません。** どちらも「`export` は宣言単位である」という同じ原則から出てきています。

### 7.5.5 `export` する

直します。

```cpp
// Vector3.ixx
export struct BasisPair              // ← export を追加
{
    Vector3 tangent;
    Vector3 bitangent;
};

export BasisPair MakeBasis(const Vector3& normal);
```

`main.cpp` で、型名を明示できることを確認してください。

```cpp
const gamemath::BasisPair basis = gamemath::MakeBasis(n);   // auto でなくてよい
```

ビルドして、同じ結果になることを確認します。これで `MakeBasis` は、まともに使える API になりました。

### 7.5.6 例外的に、隠したままにする場面

原則は上のとおりですが、意図的に「名前を付けられない型」を返す設計も存在します。代表的なものを挙げておきます。

**遅延評価のための中間型(式テンプレート)**

```cpp
// a + b が Vector3 ではなく、計算式を表す中間型を返す設計
export auto operator+(const Vector3& a, const Vector3& b);
```

利用者が中間型を保存すると、参照していた元のオブジェクトが消えた後に評価されて壊れます。だから**あえて名前を付けられなくして、保存を防ぐ**という設計があり得ます。

**実装の詳細である型**

イテレータの実装型、タグ型、`std::ranges` のビューのような型です。利用者は `auto` で受けるだけで、名前を書く必要がありません。

ただし、これらは**熟慮のうえでそう設計した**場合の話です。うっかり `export` を忘れたのと、意図的に隠したのとでは、コードは同じでも意味がまったく違います。

意図的に隠す場合は、その旨をコメントに書いてください。半年後の自分が「`export` 忘れだ」と思って直してしまいます。

`GameMath` では、この手法は使いません。**シグネチャに出る型はすべて `export` する**方針で統一します。

## 7.6 判断のための早見表

この章の内容を、実務で使える形にまとめます。

**何をどこに書くか**

| 書きたいもの | 場所 | `export` |
|---|---|---|
| 公開する型・関数 | インターフェイス単位 | **付ける** |
| 公開する関数の実装(短い・ホットパス) | インターフェイス単位 | 宣言に付ける |
| 公開する関数の実装(長い・低頻度) | 実装単位 | 付けない(付けられない) |
| モジュール内で共有する定数・ヘルパー | インターフェイス単位 | 付けない |
| 1ファイル内だけのヘルパー | そのファイル | `static` |
| 標準ライブラリ | プリアンブルで `import std;` | ── |
| 標準以外のヘッダ | グローバルモジュールフラグメント | ── |

**`export` を忘れやすいもの**

- 演算子オーバーロード(第4章 4.3.2)
- `Dot` / `Cross` などの自由関数(同上)
- **公開関数の戻り値・引数に現れる型**(この章 7.5)
- 公開クラスの `public` メンバの型

**「隠す」の3段階**

| 手段 | 名前が見えるか | 情報が届くか | `.ifc` に入るか | 変更すると再コンパイル |
|---|---|---|---|---|
| インターフェイス単位に `export` なしで書く | ✕ | ○ | ○ | **される** |
| 実装単位に書く | ✕ | ✕ | ✕ | されない |
| プライベートモジュールフラグメント(第11章) | ✕ | ✕ | 一部 | されない |

「隠す」にも段階があり、目的によって選ぶ手段が違う ── これがこの章のいちばんの収穫かもしれません。

## 7.7 この章のまとめ

- 名前付きモジュールはマクロをエクスポートしない。プリプロセッサと `.ifc` は時間軸が違うので、原理的に不可能。例外はヘッダユニット(第18章)だけ
- マクロによる設定の切り替えは、モジュール境界を越えられない(第16章の課題)
- リンケージは3種類。**`export` しない = モジュールリンケージ**、**`static` = 内部リンケージ**
- `export` しないと**モジュール全体**で共有できる。`static` にすると**1ファイル**に閉じる
- モジュールが違えば、名前空間が同じでも名前は衝突しない
- **「見える」と「到達可能」は別の概念**
  - 見える = 名前を書ける
  - 到達可能 = コンパイラが中身を知っている
- **`import` すると、インターフェイス単位の宣言はすべて到達可能になる。`export` されたものだけが見える**
- 実装単位に書いたものは到達可能ですらない。だからインライン展開もできない
- **`export` しないことは、情報を消すことではない。** `.ifc` には入るし、変更すれば利用側は再コンパイルされる
- **公開する宣言のシグネチャに現れる型は、必ず公開する。** 忘れても動いてしまうが、利用者は型名を書けない

## 次章に向けて

「到達可能」という概念が必要になる理由として、7.4.2 で3つ挙げました。そのうち最大のものが**テンプレート**です。

第8章では、`Vector3` を `Vector<T, N>` に一般化します。3次元だけでなく2次元・4次元も、`float` だけでなく `double` も扱えるようにします。

そこで、この章で学んだ区別が実際に効いてきます。

- テンプレートの定義を実装単位に置けないのはなぜか
- コンセプトを `export` し忘れるとどうなるか
- 明示的インスタンス化をモジュールでどう書くか

第7章を読み飛ばしていたら意味不明だったであろう話が、続きます。
