# 第11章 プライベートモジュールフラグメント

## この章について

第7章から第10章まで、「隠す」ための手段を積み上げてきました。

| 手段 | 章 |
|---|---|
| インターフェイスに `export` なしで書く | 第7章 |
| 実装単位に書く | 第5章 |
| 内部パーティションに書く | 第10章 |

この章で、4つ目が加わります。**プライベートモジュールフラグメント**(private module fragment)です。

```cpp
export module M;

// ここまでがインターフェイス

module :private;

// ここから先は、外に一切届かない
```

1つのファイルの中に線を引いて、「ここから下は実装です」と宣言する仕組みです。ファイルを分けずにインターフェイスと実装を分離できます。

ただし、先に正直に書いておきます。

**この道具は、いまの `GameMath` には使えません。**

厳しい制約があるからです。11.1.5 でその制約を、11.4.3 で `GameMath` に使えない理由を説明します。

では学ぶ意味がないのか ── そうではありません。小さくて自己完結したモジュールには、これがいちばん適した手段です。この章では、`GameMath` に**新しいモジュールを1つ追加**して、そこで使います。乱数生成器です。

そして、この章を終えると「隠す4つの手段」の比較表が完成します。第7章 7.6 から少しずつ埋めてきた表です。

---

## 11.1 `module :private;` とは

### 11.1.1 これまでの手段の弱点

第10章までの3つの手段には、それぞれ弱点があります。

**インターフェイスに `export` なしで書く** ── 名前は隠れますが、情報は `.ifc` に載ります(第7章 7.4.5)。変更すれば利用者は再コンパイルされます。

**実装単位に書く** ── 完全に隠れますが、**ファイルが増えます**。そして第5章・第8章で見たとおり、インライン展開もテンプレートも `constexpr` も使えなくなります。

**内部パーティションに書く** ── これもファイルが増えます。しかも Visual Studio では専用の設定が必要でした(第10章 10.2.2)。

3行の関数を1つ隠すために、ファイルを追加してコンパイル設定を変える ── 大げさすぎます。

**プライベートモジュールフラグメントは、ファイルを増やさずに隠します。**

### 11.1.2 書き方

```cpp
export module M;

import std;

// ── インターフェイス ──

export void DoSomething();

// ── ここから下は実装 ──

module :private;

void DoSomething()
{
    // ...
}
```

`module :private;` という1行を書くだけです。それより後ろに書いたものは、`import M;` した側に**一切届きません**。

第6章のグローバルモジュールフラグメント(`module;`)と対になる構文です。あちらはファイルの先頭、こちらは終わりのほうです。

### 11.1.3 ファイルは4つの領域を持てる

インターフェイス単位のファイルは、最大で4つの領域に分かれます。

```cpp
module;                          // ┐ ① グローバルモジュールフラグメント
#include <immintrin.h>           // ┘   (第6章)

export module M;                 //   ② モジュール宣言

import std;                      // ┐ ③ モジュールプリアンブル
import gamemath;                 // ┘   (第6章 6.4.2)

export void f();                 // ┐
struct Hidden;                   // │ ④ 購買域(インターフェイス)
                                 // ┘

module :private;                 //   ⑤ 境界

struct Hidden { int x; };        // ┐ ⑥ プライベートモジュールフラグメント
void f() { /* ... */ }           // ┘
```

①②③④は第6章までに出てきました。⑤⑥がこの章です。

領域ごとの性質を並べると、こうなります。

| 領域 | 所属 | 利用者に届くか |
|---|---|---|
| ① グローバルモジュールフラグメント | グローバルモジュール | 届かない |
| ④ 購買域 | このモジュール | `export` したものは届く。していないものも**到達可能** |
| ⑥ プライベートモジュールフラグメント | このモジュール | **一切届かない** |

④と⑥の違いが、この章の要点です。④は「名前は隠れるが情報は届く」、⑥は「情報も届かない」。

### 11.1.4 何を書けるか、書けないか

⑥に書けるものには制限があります。C++ の規格に、この制限を示す例が載っています。

```cpp
export module A;

export inline void fn_e();    // エラー: エクスポートされたインライン関数が
                              //        境界より前に定義されていない
inline void fn_m();           // エラー: インライン関数が定義されていない
static void fn_s();           // OK
export struct X;              // OK(不完全型として公開)

export void g(X* x)
{
    fn_s();                   // OK。同じ翻訳単位の static 関数を呼べる
}

export X* factory();          // OK

module :private;

struct X {};                  // 定義は利用者に届かない
X* factory() { return new X(); }
void fn_e() {}
void fn_m() {}
void fn_s() {}
```

読み取れることを整理します。

**⑥に書けるもの**

- **通常の(インラインでない)関数の定義** ── `factory()` がそうです
- **クラスの定義** ── `X` がそうです。前で `export struct X;` と不完全型を宣言しておけます
- **`static` 関数の定義** ── 同じ翻訳単位からは呼べます
- 定数、内部ヘルパー

**⑥に書けないもの**

- **`inline` 関数の定義** ── `fn_e` と `fn_m` がエラーになっています。**`export` の有無に関係ありません**
- **`constexpr` 関数の定義** ── `constexpr` は暗黙に `inline` なので、同じくエラーです
- **テンプレートの定義**

書けない理由は、第8章 8.5.5 でまとめたとおりです。

> インライン展開・テンプレートの実体化・`constexpr` 評価は、すべて「到達可能」を要求する

⑥は到達可能でない領域です。だから、到達可能性を必要とするものは置けません。**「隠せるものと隠せないものの線引きは、実装単位のときと同じ」**と覚えてください。

### 11.1.5 最大の制約 ── モジュール単位は1つだけ

そしてここが本題です。C++ の規格は、こう定めています。

> プライベートモジュールフラグメントは、プライマリモジュールインターフェイス単位にしか書けない。
> **プライベートモジュールフラグメントを持つモジュール単位は、そのモジュールの唯一のモジュール単位でなければならない。**

後半が強烈です。噛み砕くと、こうなります。

**プライベートモジュールフラグメントを使うなら、そのモジュールは1ファイルで完結していなければならない。**

- 実装単位を持てません
- パーティションを持てません(インターフェイスも内部も)

「モジュールを1つの翻訳単位で表現しつつ、中身を全部公開してしまうことを避ける」── それがこの機能の設計目的です。ファイルを分けたければ、実装単位やパーティションを使えばよいのです。両方を混ぜる必要はない、という判断です。

なお、規格には「診断は要求されない」と書かれています。つまり、違反してもコンパイラがエラーを出す義務はありません。実際には多くのコンパイラが検出しますが、期待しすぎないほうがよいでしょう。

## 11.2 単一ファイルで実装を隠す

### 11.2.1 題材 ── 乱数生成器

`GameMath` に足りない機能を1つ追加します。**決定論的な乱数生成器**です。

ゲーム開発では `std::mt19937` のような重いものより、軽くて状態が小さく、シード値から完全に再現できる生成器が求められます。リプレイ、ネットワーク同期、プロシージャル生成 ── どれも再現性が要ります。

そして、この機能は**プライベートモジュールフラグメントに理想的に適合します**。

- インターフェイスは小さい(クラス1つとメソッド数個)
- 実装は隠したい(アルゴリズムを後から差し替えたい)
- テンプレートも `constexpr` も要らない
- 他のパーティションと共有するものがない ── **1ファイルで完結する**

### 11.2.2 インターフェイスを書く

`Random.ixx` を追加してください。**内部パーティションではないので、コンパイル設定の変更は不要**です。`.ixx` のまま(`/interface`)で構いません。

```cpp
// Random.ixx
export module gamemath.random;

import std;

namespace gamemath {

export class Random
{
public:
    // シード値から生成器を作る。同じシードなら常に同じ列が得られる
    explicit Random(std::uint64_t seed);

    // [0, 1) の一様乱数
    float NextFloat();

    // [lo, hi) の一様乱数
    float NextFloat(float lo, float hi);

    // [lo, hi] の一様な整数
    int NextInt(int lo, int hi);

private:
    std::uint64_t state_;
};

} // namespace gamemath
```

ここまでは、これまでどおりのインターフェイス定義です。メンバ関数の**宣言だけ**を書いています。

新しいモジュールになっていることに注意してください。モジュール名は `gamemath.random` です。`gamemath` のパーティションではありません。

**理由は 11.1.5 の制約です。** `gamemath` にはすでにパーティションと実装単位があります。だから `gamemath` の中でプライベートモジュールフラグメントは使えません。独立したモジュールとして作るしかないのです。

これは本書で初めて、1つのプロジェクトに2つのモジュールが並ぶ形になります(`gamemath` と `gamemath.random`)。第12章で、この2つの関係を整理します。

### 11.2.3 実装を書く

同じファイルの続きに、境界と実装を書きます。

```cpp
// Random.ixx(続き)

// ─────────────────────────────────────
module :private;
// ─────────────────────────────────────

namespace gamemath {

// 以下は利用者に一切届かない

constexpr std::uint64_t kMultiplier = 6364136223846793005ULL;
constexpr std::uint64_t kIncrement  = 1442695040888963407ULL;

// 状態を1回進めて、上位31ビットを取り出す
static std::uint32_t Advance(std::uint64_t& state)
{
    state = state * kMultiplier + kIncrement;
    return static_cast<std::uint32_t>(state >> 33);
}

Random::Random(std::uint64_t seed)
    : state_(seed)
{
    Advance(state_);   // シードをかき混ぜる
}

float Random::NextFloat()
{
    return static_cast<float>(Advance(state_)) * (1.0f / 2147483648.0f);
}

float Random::NextFloat(float lo, float hi)
{
    return lo + NextFloat() * (hi - lo);
}

int Random::NextInt(int lo, int hi)
{
    const std::uint32_t span = static_cast<std::uint32_t>(hi - lo) + 1u;
    return lo + static_cast<int>(Advance(state_) % span);
}

} // namespace gamemath
```

境界より下は、普通の `.cpp` を書くのと同じ感覚です。`namespace gamemath { }` で囲む必要がある点も同じです。

`constexpr` の定数はここに書けます。**`constexpr` 関数は書けませんが、`constexpr` 変数は書けます。** 変数は「到達可能でなければならない」対象ではないからです(利用者が使わないかぎり)。

### 11.2.4 動かして確認する

`main.cpp` に追加します。

```cpp
// main.cpp
import std;
import gamemath;
import gamemath.random;        // ← 追加

int main()
{
    // ...(既存のコード)

    // --- 乱数の確認 ---
    gamemath::Random rng{ 12345 };

    float minV = 1.0f;
    float maxV = 0.0f;
    float sum  = 0.0f;

    for (int i = 0; i < 10000; ++i) {
        const float v = rng.NextFloat();
        minV = std::min(minV, v);
        maxV = std::max(maxV, v);
        sum += v;
    }

    std::println("Random: min = {:.4f}  max = {:.4f}  mean = {:.4f}",
                 minV, maxV, sum / 10000.0f);

    // 再現性の確認
    gamemath::Random r1{ 999 };
    gamemath::Random r2{ 999 };
    std::println("Reproducible: {}", r1.NextFloat() == r2.NextFloat());

    return 0;
}
```

ビルドして実行してください。

`min` が 0 に近く、`max` が 1 に近く、`mean` が 0.5 前後になっていれば、一様分布が出ています。`Reproducible` が `true` なら、同じシードから同じ列が得られています。

### 11.2.5 【実験】隠れていることを確かめる

`main.cpp` から、実装の中身に触ろうとしてみてください。

```cpp
std::println("{}", gamemath::kMultiplier);      // ①
std::uint64_t s = 0;
gamemath::Advance(s);                           // ②
```

どちらもエラーになります。

```
error C2065: 'kMultiplier': 定義されていない識別子です。
error C2065: 'Advance': 定義されていない識別子です。
```

第7章 7.4.4 で `Hidden` を使った実験を思い出してください。あのとき、`export` していない型は「名前は書けないが、`auto` で受ければ使えた」のでした。**到達可能だったからです。**

今回は違います。プライベートモジュールフラグメントの中身は到達可能でもありません。**回り道も存在しません。**

**これらの行を削除してください。**

### 11.2.6 不完全型を公開するという技法

11.1.4 の規格の例に、こういう行がありました。

```cpp
export struct X;              // 不完全型として公開
export X* factory();

module :private;

struct X {};                  // 定義は届かない
```

`X` の**名前だけ**を公開し、**中身を隠す**という技法です。利用者は `X*` を持ち回せますが、`X` のメンバにはアクセスできず、サイズも知りません。

第1章 1.2.4 で扱った **Pimpl イディオム**が、言語機能で実現できたようなものです。しかもポインタの間接参照を1段減らせます。

ただし、利用者は `X` の実体を作れません。`factory()` のような生成関数を用意する必要があります。用途は限られますが、「型を完全に隠したい」場面では強力です。

`Random` ではこの技法を使いませんでした。利用者に `Random rng{ 12345 };` と書いてもらいたいからです。そのためにはクラス定義が公開されている必要があります。

### 11.2.7 【実験】`inline` を付けてみる

11.1.4 で「`inline` 関数の定義は書けない」と述べました。確認しておきましょう。

`NextFloat()` を `inline` にしてみてください。

```cpp
// Random.ixx のインターフェイス側
class Random
{
public:
    // ...
    inline float NextFloat();      // ← inline を追加
    // ...
};
```

ビルドすると、エラーになります。「インライン関数が定義されていない」という趣旨のメッセージです。

境界より下の定義は、`inline` 関数の定義として認められません。定義がないのと同じ扱いになります。

`constexpr` でも同じことが起きます。試してみてください。

**`inline` を削除して、元に戻してください。**

なお、**クラス定義の中に書いたメンバ関数は暗黙に `inline` になります。** だから `Random` のメンバ関数は、クラス定義の中では宣言だけにしています。中身を書いてしまうとインライン関数になり、境界より下に定義を置けなくなります。

これは実務でよく踏む落とし穴です。「クラスの中に短い関数を書いてしまい、あとで実装をプライベートモジュールフラグメントに移そうとして詰まる」という形で現れます。

## 11.3 ABI 的な意味と再コンパイル範囲

### 11.3.1 到達可能でないことの意味

プライベートモジュールフラグメントの中身は、`.ifc` に載りません(正確には、利用者から到達可能な形では載りません)。

これが意味することを整理します。

**利用者のコンパイルに影響しない。** `.ifc` を読む量が増えません。

**アルゴリズムを差し替えても、インターフェイスは変わらない。** `Advance` の実装を PCG から xorshift に変えても、`Random.ixx` の上半分は1文字も変わりません。

**利用者は実装に依存できない。** 「たまたま `kMultiplier` が見えていたから使ってしまった」という事故が起こりません。

### 11.3.2 【実験】再コンパイル範囲を測る

第5章 5.1.3 と第5章 5.6.4 でやった実験を、もう一度します。

**まず、インターフェイス側を変更**してください。たとえばコメントを1行足します。

```cpp
// Random.ixx(境界より上)
export class Random
{
public:
    // シード値から生成器を作る(コメントを追加)
    explicit Random(std::uint64_t seed);
    // ...
```

ビルドします。`main.cpp` が再コンパイルされます。当然です。

**次に、境界より下を変更**してください。

```cpp
module :private;

// ...

static std::uint32_t Advance(std::uint64_t& state)
{
    // コメントを1行追加
    state = state * kMultiplier + kIncrement;
    return static_cast<std::uint32_t>(state >> 33);
}
```

ビルドして、出力ウィンドウを確認してください。

**`main.cpp` が再コンパイルされないのが、規格の意図する動作です。** 境界より下は利用者から到達可能でないので、`main.cpp` の意味に影響しないからです。

ただし、実際に省略されるかどうかは**ビルドシステムの実装次第**です。`Random.ixx` というファイルが変更されたので `.ifc` が作り直され、その `.ifc` のタイムスタンプが更新されたら `main.cpp` も再コンパイルする ── という単純な依存判定をしていれば、再コンパイルされます。

再コンパイルされたとしても、それはビルドシステムがまだ最適化していないだけです。**「規格上は不要」と「実際に省略される」の間には、実装の成熟度という距離があります。**

第21章で、この種の計測の仕方を扱います。

### 11.3.3 「隠す」4つの手段 ── 表の完成

第7章 7.6 から少しずつ埋めてきた表が、これで完成します。

| 手段 | 名前が<br>見えるか | 到達<br>可能か | ファイルが<br>増えるか | インライン/<br>テンプレート | 変更で<br>再コンパイル |
|---|---|---|---|---|---|
| インターフェイスに `export` なし | ✕ | ○ | 増えない | **使える** | される |
| 実装単位 | ✕ | ✕ | 増える | 使えない | されない |
| 内部パーティション | ✕ | モジュール内のみ | 増える<br>(+設定) | モジュール内のみ | モジュール内のみ |
| **プライベートモジュール<br>フラグメント** | ✕ | ✕ | **増えない** | 使えない | されない<br>(規格上) |

読み取れる使い分けはこうです。

- **インライン展開・テンプレート・`constexpr` が必要** → 1行目しかない
- **ファイルを増やしたくない、モジュールが1ファイルで完結する** → 4行目
- **モジュール内の複数の単位で共有したい** → 3行目
- **上記以外で、実装を隠したい** → 2行目

### 11.3.4 それでも隠れないもの

万能ではありません。`Random` のクラス定義を見てください。

```cpp
export class Random
{
public:
    // ...
private:
    std::uint64_t state_;      // ← これは公開されている
};
```

**`private` メンバ変数は隠れていません。**

第1章 1.1.6 と第4章 4.3.5 で確認したとおりです。`private` は「アクセスできない」だけで、「見えない」わけではありません。クラス定義の一部として `.ifc` に載ります。

だから、次のことが利用者に伝わってしまいます。

- `Random` のサイズは 8 バイトである
- 状態は 64 ビット整数1つである

そして、これを変更すると ── たとえば状態を2つに増やすと ── **利用者は再コンパイルが必要になります**。クラスのレイアウトが変わるからです。

これは **ABI(Application Binary Interface)** の問題です。プライベートモジュールフラグメントは、関数の実装を隠せますが、**データレイアウトは隠せません**。

完全に隠したければ、11.2.6 の不完全型か、従来どおりの Pimpl が必要です。そして第1章 1.4.3 で書いたとおり、**C++ の ABI 問題そのものはモジュールでは解決しません。**

## 11.4 いつ使い、いつ使わないか

### 11.4.1 向いている場面

**1ファイルで完結する小さなモジュール**

これが必須条件です(11.1.5)。パーティションも実装単位も要らない規模。

**インターフェイスが小さく、実装が大きい**

`Random` がまさにそうでした。公開するのはクラス1つとメソッド3つ、実装は定数と内部関数を含めて40行ほど。この比が大きいほど効果があります。

**アルゴリズムを差し替える可能性がある**

乱数生成器、ハッシュ関数、ノイズ生成、圧縮 ── 「入出力の仕様は変えずに中身を良くしていく」性質のものです。

**インライン展開が要らない**

`Random::NextFloat()` は、レンダリングの内側のループで毎ピクセル呼ばれるわけではありません。関数呼び出しのコストが許容できる粒度です。

### 11.4.2 向いていない場面

**モジュールが複数のファイルに分かれている**

11.1.5 の制約により、そもそも使えません。

**テンプレートが中心**

第8章で見たとおり、テンプレートの定義は到達可能でなければなりません。境界より下には置けません。

**インライン展開が性能に直結する**

数学ライブラリの演算子、コンテナのアクセサ、ゲッタ・セッタ。

**将来ファイルを分けたくなるかもしれない**

これが実務では意外に重要です。プライベートモジュールフラグメントを使ったモジュールが育ってパーティションに分けたくなったら、**境界より下のコードを全部、実装単位や内部パーティションに移す作業**が発生します。

最初から実装単位に分けておけば、その作業は要りませんでした。「小さいままでいる」という見通しがあるときだけ使うべき機能です。

### 11.4.3 なぜ `GameMath` 本体では使えないのか

理由を3つ、はっきりさせておきます。

**理由1: モジュール単位が複数ある**

`gamemath` は `GameMath.ixx` / `Vector.ixx` / `Basis.ixx` / `Detail.ixx` / `Basis.cpp` の5つのモジュール単位でできています。11.1.5 の制約に真正面から違反します。これだけで決定的です。

**理由2: 中身がほとんどテンプレート**

仮に1ファイルにまとめられたとしても、`Vector<T, N>` とその演算子はすべてテンプレートです。境界より下には置けません。隠せるものが残りません。

**理由3: インライン展開が生命線**

第5章 5.6.1 で扱ったとおりです。`Dot` や `Cross` を隠したら、それは性能を捨てることになります。

つまり `GameMath` の本体は、**この機能が想定している対象の真逆**にあります。テンプレート中心で、インライン展開が必須で、複数ファイルに分かれた大きなライブラリ。

一方 `gamemath.random` は、真ん中に当たりました。だから使いました。

**同じライブラリの中でも、モジュールの性質によって手段が変わる** ── これがこの章のいちばんの収穫だと思います。

### 11.4.4 実装単位との使い分け

最後に、いちばん迷いやすい2択を整理します。プライベートモジュールフラグメントと実装単位は、隠す能力がほぼ同じです。

| | プライベートモジュールフラグメント | 実装単位 |
|---|---|---|
| ファイル数 | 1 | 2 |
| モジュール単位を増やせるか | **不可** | 可 |
| 複数の実装ファイルに分けられるか | ✕ | ○ |
| 実装を並列コンパイルできるか | ✕ | ○ |
| インターフェイスと実装が近い | ○(利点でも欠点でも) | ✕ |

最後から2行目は、規模が大きくなると効いてきます。実装単位が5つあれば、5並列でコンパイルできます。プライベートモジュールフラグメントは1ファイルなので、並列化の余地がありません。

**判断の目安**

- 実装が 100 行を超えそう → 実装単位
- 将来ファイルを分けそう → 実装単位
- 小さくて完結している → プライベートモジュールフラグメント

迷ったら実装単位を選んでください。**後から変更する手間が小さいほう**です。プライベートモジュールフラグメントから実装単位への移行は、コードを移すだけでなくモジュールの構成を変える作業になります。

## 11.5 この章のまとめ

- **プライベートモジュールフラグメント**は `module :private;` で始まる領域。それより後ろは利用者に一切届かない
- 書けるのは**プライマリモジュールインターフェイス単位だけ**
- **最大の制約: プライベートモジュールフラグメントを持つモジュール単位は、そのモジュールの唯一のモジュール単位でなければならない。** パーティションも実装単位も持てない
- 境界より下に書けるもの ── 通常の関数の定義、クラスの定義、`static` 関数、`constexpr` **変数**
- 書けないもの ── **`inline` 関数**、**`constexpr` 関数**、**テンプレート**の定義。`export` の有無は関係ない
- クラス定義の中に書いたメンバ関数は暗黙に `inline` になるので、境界より下に定義を置けなくなる
- `export struct X;` と不完全型を公開し、定義を境界より下に置けば、型を完全に隠せる(Pimpl の言語機能版)
- 境界より下を変更しても、規格上は利用者の再コンパイルは不要。ただし実際に省略されるかはビルドシステム次第
- **`private` メンバ変数は隠れない。** データレイアウトは公開され、変更すれば ABI が変わる
- 向いているのは「1ファイルで完結し、インターフェイスが小さく実装が大きく、インライン展開が要らない」モジュール
- **`GameMath` 本体はこの条件の真逆**なので使えない。`gamemath.random` は条件に合ったので使った
- 迷ったら実装単位。後から変更する手間が小さい

## 次章に向けて

第9章から第11章で、モジュールを分割する道具がすべて揃いました。

- サブモジュール(独立したモジュール)
- インターフェイスパーティション
- 内部パーティション
- 実装単位
- プライベートモジュールフラグメント

そして、いまの `GameMath` は少し中途半端な状態です。

- `gamemath` ── パーティション2つ + 内部パーティション1つ + 実装単位1つ
- `gamemath.random` ── 独立したモジュール1つ

この2つの関係が整理されていません。利用者は `import gamemath;` と `import gamemath.random;` の2行を書く必要があり、なぜそう分かれているのかを推測するしかありません。

第12章では、**`GameMath` 全体の構成を設計します。** 第9章 9.5.4 で予告した階層 ── `gamemath.core` / `gamemath.geometry` / 傘としての `gamemath` ── を実際に組み立てます。

道具の説明はここで終わりです。次章からは、それをどう使うかという設計の話になります。
