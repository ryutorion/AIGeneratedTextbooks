# 第17章 エラー処理と診断

## この章について

第4部の最後は、地味ですが実務では毎日使う話です。

1. `assert` と `NDEBUG` をモジュールでどう扱うか(17.1)
2. デバッグ用の出力ヘルパーをどこに置くか(17.2)
3. **コンパイルエラーメッセージの読み方**(17.3)

3番目が本題です。

ここまでの章で、何度もわざとエラーを出してきました。「モジュールが見つかりません」「識別子が見つかりません」「循環した依存関係」── モジュール特有のエラーは、慣れないうちは本当に読めません。エラーが出た場所と原因の場所が違うことも多く、メッセージを字面どおり受け取ると迷走します。

しかし、**原因の候補は決まっています。** 順番に潰していけば必ず解決します。17.3 でその手順を整理します。

そして 17.1 と 17.2 には、第16章の続きのような性質があります。`assert` はマクロです。デバッグ出力には `std::string` が要ります。どちらも、これまで扱ってきた「マクロは境界を越えない」「標準ライブラリの型を公開しない」という制約に、正面からぶつかります。

## 17.1 `assert` / `NDEBUG` とモジュール

### 17.1.1 `import std;` では `assert` が使えない

`GameMath` の関数に表明(assertion)を入れたいとします。

```cpp
// Geometry/Intersect.cpp
RayHit Intersect(const Ray& r, const Sphere& s)
{
    assert(NearlyEqual(r.direction.LengthSquared(), 1.0f));   // ← 書いてみる
    // ...
}
```

このファイルには `import std;` があります。それで足りるでしょうか。

ビルドしてください。**エラーになります。**

```
error C3861: 'assert': 識別子が見つかりませんでした
```

理由は第7章 7.1 のとおりです。

> 名前付きモジュールは、マクロをエクスポートしません。例外はありません。

**`assert` はマクロです。** `<cassert>` が提供するプリプロセッサマクロであって、関数ではありません。だから `import std;` では入ってきません。

同じ理由で、次のものも `import std;` では使えません。

| 使えないもの | 提供元 |
|---|---|
| `assert` | `<cassert>` |
| `NULL` | `<cstddef>` など |
| `offsetof` | `<cstddef>` |
| `errno` | `<cerrno>` |
| `INT_MAX` などの `<climits>` の定数 | `<climits>` |
| `va_start` / `va_arg` | `<cstdarg>` |

`import std;` が提供するのは、**`std::` 名前空間の中身**です。マクロは対象外です。

`INT_MAX` は `std::numeric_limits<int>::max()` で代替できます。`NULL` は `nullptr` を使います。しかし `assert` には、標準の代替がありません。

### 17.1.2 グローバルモジュールフラグメントに書く

第6章 6.6.1 の方針3が、ここでも発動します。

> グローバルモジュールフラグメントは、`import` できないヘッダのために取っておく。

`Geometry/Intersect.cpp` の先頭を書き換えてください。

```cpp
// Geometry/Intersect.cpp
module;

#include <cassert>

module gamemath.geometry;

import std;

namespace gamemath {

RayHit Intersect(const Ray& r, const Sphere& s)
{
    // direction は正規化済みであることが前提(第15章 15.2.1)
    assert(NearlyEqual(r.direction.LengthSquared(), 1.0f, 1.0e-4f));

    const Vector3 oc = r.origin - s.center;
    // ...(以下変更なし)
}

} // namespace gamemath
```

実装単位にもグローバルモジュールフラグメントを書けます(第6章 6.3.5)。`module;` はファイルの最初のトークンでなければなりません(6.3.1)。

ビルドして実行してください。通ります。

第15章 15.2.1 で、こう決めました。

> 正規化などの前提は関数内で検査せず、ドキュメントに明記する。

その判断を、**デバッグビルドでだけ検査する**という形に洗練させました。リリースビルドでは `NDEBUG` によって `assert` が消えるので、性能は落ちません。開発中は前提違反を早期に発見できます。

これが表明の本来の使い方です。

### 17.1.3 【重要】`assert` の有効・無効はいつ決まるか

ここからがモジュール特有の話です。

`assert` は `NDEBUG` の有無で切り替わります。では、**`NDEBUG` はいつ、どのファイルの状態が使われるのでしょうか。**

答えは明確です。

> **`assert` は、そのマクロが書かれているファイルがプリプロセスされた時点の `NDEBUG` の状態で確定する。**

`Intersect.cpp` の中の `assert` は、`Intersect.cpp` をコンパイルしたときの `NDEBUG` で決まります。当たり前に聞こえますが、**インターフェイスに書いた場合**に意味が変わってきます。

こういうコードを考えてください。

```cpp
// Core/Vector.ixx(説明のための例。実際には書きません)
module;
#include <cassert>
export module gamemath.core:vector;

// ...

export template <FloatingPoint T, std::size_t N>
struct Vector
{
    // ...
    T At(std::size_t i) const
    {
        assert(i < N);        // ← インターフェイスに書いた assert
        return e[i];
    }
};
```

この `assert` は、**`Vector.ixx` をコンパイルしたときの `NDEBUG`** で確定します。

そして、その結果が `.ifc` に焼き付けられます。利用者の翻訳単位で `At()` が実体化されるとき、`assert` はすでに展開済みです。**利用者側の `NDEBUG` は関係ありません。**

### 17.1.4 ヘッダ時代との違い

ヘッダなら、逆でした。

```cpp
// Vector.h(ヘッダ時代)
#include <cassert>

struct Vector3
{
    float At(int i) const
    {
        assert(i < 3);
        return e[i];
    }
};
```

このヘッダを `#include` した翻訳単位ごとに、テキストが展開されます。だから **`assert` は、それを `#include` した側の `NDEBUG` で決まりました。**

デバッグビルドのアプリケーションが、リリースビルドされたライブラリのヘッダを `#include` すれば、表明は有効でした。

**モジュールでは、モジュールをビルドしたときの設定が勝ちます。**

第16章 16.4.2 で確認したことと、同じ構図です。

> モジュールは、ビルド全体で1回だけコンパイルされる。

翻訳単位ごとに違う設定でコンパイルすることが構造的にできないので、`NDEBUG` についても1通りに決まります。

**実用上、これが問題になることは多くありません。** Visual Studio のプロジェクトでは、Debug 構成と Release 構成でそれぞれ別の `.ifc` が生成されるからです(第2章 2.4.1 で中間ディレクトリを見たとおりです)。Debug ビルドなら、モジュールも Debug でコンパイルされます。

問題になるのは、**ビルド済みの `.ifc` を配布した場合**です。しかし第1章 1.4.3 で確認したとおり、`.ifc` は配布物ではありません。だから、この問題に遭遇する機会は限られます。

とはいえ、覚えておく価値はあります。**「利用者に `NDEBUG` で表明を切ってもらう」という設計は成立しません。** 表明の有無はライブラリのビルド構成で決まります。

### 17.1.5 `static_assert` はマクロではない

対比として押さえておきます。

**`static_assert` はキーワードです。** マクロではありません。だから `<cassert>` も `import std;` も不要で、どこにでも書けます。

本書でも、第8章 8.5.2 以来ずっと使ってきました。

```cpp
static_assert(gamemath::Dot(ca, cb) == 32.0f);
```

そして `static_assert` は `NDEBUG` の影響を受けません。常に有効です。

**コンパイル時に判定できるものは、`assert` ではなく `static_assert` を使ってください。** 実行時のコストがゼロで、失敗したらビルドが止まるので、見逃しようがありません。

第14章 14.4.3 で挙げた不変条件のうち、定数で確認できるものは `static_assert` で書けます。

### 17.1.6 `GameMath` の表明の方針

まとめると、こうします。

| 検査したいもの | 手段 |
|---|---|
| コンパイル時に確定する条件 | **`static_assert`** |
| 実行時の前提条件(正規化済みなど) | **`assert`**(`<cassert>` を GMF で) |
| 利用者が回復すべきエラー | 戻り値(第15章 15.3.5 の `RayHit` など) |
| 型で表現できる制約 | **コンセプト**(第8章 8.3) |

そして重要な原則を1つ。

**`assert` は、インターフェイスパーティションではなく実装単位に書く。**

理由は 17.1.3 のとおりです。インターフェイスに書いた `assert` は `.ifc` に焼き付けられ、利用者のビルド構成と食い違う可能性があります。実装単位に書けば、モジュールの `.obj` の中で完結します。

もっとも、実装単位に置けない関数(テンプレート、インライン、`constexpr`)には表明を入れられない、ということでもあります。そこはコンセプトで型として制約するか、諦めるかです。

> **C++26 の契約(Contracts)**
>
> C++26 では、前提条件・事後条件を言語機能として書ける「契約」が導入される見込みです。
>
> ```cpp
> // イメージ(構文は確定していません)
> RayHit Intersect(const Ray& r, const Sphere& s)
>     pre(NearlyEqual(r.direction.LengthSquared(), 1.0f));
> ```
>
> これはマクロではなく言語機能なので、モジュール境界を越えられます。`assert` の抱える問題の多くが解消される見込みです。
>
> それまでは `assert` を、上記の制約を理解したうえで使うことになります。

## 17.2 デバッグ用の出力ヘルパーをモジュール内に閉じ込める

### 17.2.1 デバッグ出力が欲しい

`Vector3` や `Matrix4x4` の中身を確認したい場面は、開発中に山ほどあります。

`main.cpp` では、こう書いてきました。

```cpp
std::println("a + b = ({:.2f}, {:.2f}, {:.2f})", sum.x(), sum.y(), sum.z());
```

面倒です。こう書きたい。

```cpp
std::println("a + b = {}", gamemath::ToString(sum));
```

### 17.2.2 素直に書くと、方針に反する

`ToString` は `std::string` を返します。

```cpp
export std::string ToString(const Vector3& v);
```

第12章 12.3.2 の規則により、これを公開するなら `export import std;` が必要です。

そして第6章 6.5.4 で、こう決めました。

> `export import std;` はやってはいけない。利用者の環境を選ぶライブラリになってしまう。

第15章 15.3.3 で `std::optional` について検討したのと、同じ壁です。

### 17.2.3 4つの案

**案1: 標準ライブラリの型を使わない**

```cpp
export int Format(const Vector3& v, char* buffer, int size);
```

C 風のインターフェイスです。標準ライブラリに依存しません。しかし呼ぶ側が面倒で、デバッグのための機能としては本末転倒です。

**案2: 出力だけする**

```cpp
export void Print(const Vector3& v);      // 標準出力に書く
```

シグネチャに `std` の型が出ません。しかし出力先を選べず、ログシステムに流せません。

**案3: 諦めて `export import std;` を書く**

方針に反します。全利用者に影響します。

**案4: 別のモジュールに隔離する**

デバッグ機能だけを独立したモジュールにして、そこでだけ `export import std;` を書きます。**それを取り込むかどうかは利用者が決めます。**

### 17.2.4 案4 ── `gamemath.debug` を作る

`Debug/Debug.ixx` を作ってください。

```cpp
// Debug/Debug.ixx
export module gamemath.debug;

export import gamemath.core;
export import gamemath.geometry;
export import std;                  // ← あえて書く

namespace gamemath {

export template <FloatingPoint T, std::size_t N>
std::string ToString(const Vector<T, N>& v)
{
    std::string s = "(";
    for (std::size_t i = 0; i < N; ++i) {
        if (i > 0) {
            s += ", ";
        }
        s += std::format("{:.4f}", v[i]);
    }
    s += ")";
    return s;
}

export std::string ToString(const Quaternion& q);
export std::string ToString(const Matrix4x4& m);
export std::string ToString(const AABB& box);
export std::string ToString(const RayHit& hit);

} // namespace gamemath
```

`Debug/Debug.cpp` に定義を書きます。

```cpp
// Debug/Debug.cpp
module gamemath.debug;

import std;

namespace gamemath {

std::string ToString(const Quaternion& q)
{
    return std::format("({:.4f}, {:.4f}, {:.4f}, {:.4f})", q.x, q.y, q.z, q.w);
}

std::string ToString(const Matrix4x4& m)
{
    std::string s;
    for (std::size_t i = 0; i < 4; ++i) {
        s += std::format("| {:8.4f} {:8.4f} {:8.4f} {:8.4f} |\n",
                         m(i, 0), m(i, 1), m(i, 2), m(i, 3));
    }
    return s;
}

std::string ToString(const AABB& box)
{
    return std::format("AABB[{:.2f},{:.2f},{:.2f} - {:.2f},{:.2f},{:.2f}]",
                       box.min.x(), box.min.y(), box.min.z(),
                       box.max.x(), box.max.y(), box.max.z());
}

std::string ToString(const RayHit& hit)
{
    if (!hit.hit) {
        return "RayHit{ miss }";
    }
    return std::format("RayHit{{ t={:.4f}, p=({:.2f},{:.2f},{:.2f}) }}",
                       hit.distance,
                       hit.point.x(), hit.point.y(), hit.point.z());
}

} // namespace gamemath
```

`Vector` 版だけがテンプレートなのでインターフェイスに定義があります(第8章 8.2)。残りは実装単位です。

### 17.2.5 ここでは `export import std;` を書く

第6章で禁じたことを、あえてやっています。理由をはっきりさせておきます。

**`gamemath.debug` は、取り込むかどうかを利用者が決めるモジュールだからです。**

- `import gamemath.debug;` と書いた人は、「デバッグのために標準ライブラリの依存を受け入れる」と決めた人です
- 書かない人には、まったく影響しません

第6章 6.5.4 で `export import std;` を禁じた理由は、「利用者の環境を選ぶライブラリになる」ことでした。**選ぶ余地を与えれば、その理由は成立しません。**

**規則には、成立する条件があります。** 条件を確認せずに規則だけ守ろうとすると、案1や案2のような不便な設計になります。

そして、**この分離ができるのはモジュールのおかげです。** ヘッダの時代、「デバッグ機能だけ別のヘッダに」と分けても、それを `#include` した瞬間にマクロも型も全部流れ込みました。モジュールでは、境界が本当に境界として機能します。

### 17.2.6 傘に入れない

**重要です。** `GameMath.ixx`(傘)を変更してはいけません。

```cpp
// GameMath.ixx ── 変更しない
export module gamemath;

export import gamemath.core;
export import gamemath.geometry;
export import gamemath.random;
// export import gamemath.debug;   ← 書かない
```

書いてしまうと、`import gamemath;` と書いた全員に `std` が再エクスポートされます。隔離した意味がなくなります。

**傘は「全部入り」ではありません。「既定で欲しいもの」を集めたものです。**

第12章 12.3.4 で「傘は便利さと引き換えにビルド時間を払う選択肢」と書きました。そこに条件が1つ加わります。**傘に入れるかどうかは、そのモジュールが全利用者にとって望ましいかで決めます。**

`gamemath.debug` は、リリースビルドの利用者にとっては不要です。だから入れません。

### 17.2.7 内部専用のダンプは内部パーティションに

ライブラリの開発者だけが使うダンプ関数 ── たとえば「行列の直交性の崩れ具合を確認する」といったもの ── は、利用者に見せる必要がありません。

その場合は、第10章の**内部パーティション**が適所です。

```cpp
// Core/Detail.ixx(内部パーティション)
module gamemath.core:detail;

import :vector;
import std;

namespace gamemath {

// 開発中の確認用。利用者には見えない
void DebugDump(const Vector3& v)
{
    std::println("[gamemath] ({:.6f}, {:.6f}, {:.6f})", v.x(), v.y(), v.z());
}

// ...(MinorAxis / SafeAcos は変更なし)

} // namespace gamemath
```

第10章 10.3.3 の原則により、**実装単位からしか呼べません**。インターフェイスのインライン関数からは呼ばないでください。

用途としては、これでちょうどよいはずです。デバッグ出力を入れたいのは、たいてい複雑なアルゴリズムの中 ── つまり実装単位に置いた関数の中です。

### 17.2.8 動作確認

`main.cpp` で使ってみます。

```cpp
// main.cpp
import std;
import gamemath;
import gamemath.debug;        // ← 明示的に取り込む

int main()
{
    // ...

    std::println("a          = {}", gamemath::ToString(a));
    std::println("q(Z,90)    = {}", gamemath::ToString(qz));
    std::println("Sphere box = {}", gamemath::ToString(sphereBox));
    std::println("Ray x Sph  = {}", gamemath::ToString(sphereHit));
    std::println("RotationZ  =\n{}", gamemath::ToString(fromR));

    return 0;
}
```

ビルドして実行してください。

```
a          = (1.0000, 2.0000, 3.0000)
q(Z,90)    = (0.0000, 0.0000, 0.7071, 0.7071)
Sphere box = AABB[-2.00,-2.00,-2.00 - 2.00,2.00,2.00]
Ray x Sph  = RayHit{ t=8.0000, p=(0.00,2.00,0.00) }
RotationZ  =
| -0.0000  -1.0000   0.0000   0.0000 |
|  1.0000  -0.0000   0.0000   0.0000 |
|  0.0000   0.0000   1.0000   0.0000 |
|  0.0000   0.0000   0.0000   1.0000 |
```

**`import gamemath.debug;` の行を消すと、`ToString` は使えなくなります。** 試してみてください。隔離が機能しています。

> **コラム: `std::formatter` を特殊化する手もある**
>
> C++20 では、`std::formatter` を自分の型に対して特殊化すれば、`std::format` や `std::println` に直接渡せるようになります。
>
> ```cpp
> std::println("a = {}", a);      // ToString を挟まずに書ける
> ```
>
> 書き味は明らかに良くなります。しかし、モジュールと組み合わせると考えることが増えます。特殊化がどの翻訳単位から見えている必要があるのか、`std` の型を特殊化することがモジュールの所属とどう関わるのか ── このあたりはコンパイラごとの実装差も出やすい領域です。
>
> 本書では扱いませんが、`gamemath.debug` のような隔離されたモジュールでなら試す価値があります。うまくいかなければ `ToString` に戻せばよいので、リスクも限定的です。

## 17.3 コンパイルエラーメッセージの読み方

### 17.3.1 モジュールのエラーには3つの特徴がある

まず、心構えです。

**特徴1: エラーが出た場所と、原因の場所が違う**

`export` を書き忘れたのはライブラリ側なのに、エラーが出るのは利用者側です。第13章 13.3.2 で体験したとおりです。

だから、**利用側でエラーが出たら、まずライブラリ側を疑ってください。** メッセージが指しているファイルを何時間眺めても、原因はそこにありません。

**特徴2: メッセージが原因を教えてくれない**

「`export` が付いていません」とは言いません。「識別子が見つかりません」と言うだけです。第4章 4.3.1 以来、繰り返し見てきました。

**特徴3: 1つの原因から大量のエラーが出る**

モジュールが1つ見つからなければ、そこから使っている名前がすべてエラーになります。数百行のエラーが出ることも珍しくありません。

だから、**最初のエラーだけを見てください。** 2番目以降はたいてい派生物です。

### 17.3.2 まず確認する4つのこと

エラーの内容を読む前に、機械的に確認することがあります。

**1. どのファイルでエラーが出ているか**

`.ixx` か、実装単位の `.cpp` か、利用側の `.cpp` か。これで原因の範囲が絞れます。

| エラーの場所 | 疑うべきところ |
|---|---|
| `.ixx` の中 | そのファイルの `import` 漏れ、依存の循環 |
| 実装単位の `.cpp` | `import` 漏れ、宣言と定義の食い違い |
| 利用側の `.cpp` | **ライブラリ側の `export` 漏れ** |

**2. 出力ウィンドウでビルド順序を確認する**

```
1>Vector.ixx
1>Matrix.ixx
1>main.cpp
```

期待した順序になっているか。`.ixx` が `.cpp` より後にコンパイルされていたら、ビルドシステムが依存を認識できていません。

**3. リビルドしてみる**

`.ifc` が古い状態で残っていることがあります。**[ビルド] → [ソリューションのリビルド]** で解決するなら、コードの問題ではありません。

**4. IntelliSense のエラーか、ビルドのエラーか**

エディタに赤い波線が出ていても、ビルドが通るなら、コードは正しい可能性が高いのです。第2章 2.5.1 のとおりです。**エラー一覧ウィンドウで「ビルドのみ」に絞り込んでください。**

### 17.3.3 症状 ── 「モジュールが見つかりません」

上から順に確認します。

1. **`.ixx` がプロジェクトに追加されているか。** エクスプローラーにファイルを置いただけでは駄目です(第2章 2.5.1)
2. **モジュール名の綴りが一致しているか。** `export module gamemath.core;` と `import gamemath.core;`。大文字小文字も区別されます
3. **コンパイル言語の選択が正しいか。** 内部パーティションなら `/internalPartition` が必要です(第10章 10.2.2)。**これがいちばん忘れられます**
4. **C++ 言語標準が C++20 以上か**(第2章 2.2.3)
5. **`import std;` なら**、「ISO C++23 標準ライブラリ モジュールのビルド」が「はい」か(第2章 2.3.3)
6. **依存が循環していないか。** 循環していると、コンパイラは「見つからない」と報告することがあります
7. **ビルド順序の問題か。** ビルドのたびに出たり出なかったりするなら 17.3.9 へ

### 17.3.4 症状 ── 「識別子が見つかりません」(C2065 / C3861)

**モジュールで最も多いエラーです。** 原因の候補を全部挙げます。

| # | 原因 | 参照 |
|---|---|---|
| 1 | `export` を書き忘れた | 第3章 3.5 |
| 2 | クラスは `export` したが、自由関数・演算子を忘れた | 第4章 4.3.2 |
| 3 | 関数は `export` したが、シグネチャに出る**型**を忘れた | 第7章 7.5 |
| 4 | エイリアス(`using`)やコンセプトの `export` を忘れた | 第8章 8.1.4 / 8.3.4 |
| 5 | オーバーロード集合の一部だけ `export` した | 第14章 14.1.4 |
| 6 | 別モジュールの**非公開**の実体を使おうとした | 第15章 15.4.1 |
| 7 | 依存モジュールを `export import` していない | 第12章 12.3.1 |
| 8 | 到達可能だが見えない型に、名前を付けようとした | 第7章 7.4.4 |
| 9 | マクロが境界を越えると期待した | 第16章 16.4.1 |
| 10 | `import` 自体を書き忘れた | ── |

数が多く見えますが、次の項の方法で一気に絞り込めます。

### 17.3.5 `auto` で切り分ける

**これがいちばん役に立つ診断法です。**

エラーになっている型や関数を、`auto` で受けてみてください。

```cpp
// 元のコード(エラー)
gamemath::BasisPair basis = gamemath::MakeBasis(n);

// 試す
auto basis = gamemath::MakeBasis(n);
```

**結果で原因が分かります。**

| `auto` にすると | 意味 | 原因 |
|---|---|---|
| **通る** | 実体は届いている。名前だけが見えない | **`export` 漏れ**(17.3.4 の 3, 4, 6, 7, 8) |
| **通らない** | 実体そのものが届いていない | **`import` 漏れ**、モジュールが見つかっていない、`export` 漏れ(1, 2, 5, 10) |

第7章 7.4 で学んだ「見える」と「到達可能」の区別が、そのまま診断に使えます。

- **到達可能だが見えない** → `auto` で受けられる → 誰かが `export` を忘れている
- **到達可能でもない** → `auto` でも駄目 → そもそも届いていない

`auto` で通った場合、次はその型がどこで定義されているかを探し、`export` が付いているか確認します。付いていれば、その型を持つモジュールが `export import` されているかを確認します(第12章 12.3.2)。

### 17.3.6 症状 ── 循環した依存関係

メッセージは分かりやすいのですが、対処には設計の見直しが要ります。

**手順1: 依存グラフを紙に描く**

各 `.ixx` の先頭にある `import` を全部書き出して、矢印でつなぎます。第10章 10.4.4 や第14章 14.2.8 のような図です。

**手順2: 循環している輪を特定する**

**手順3: 第10章 10.4.5 の3つの対処から選ぶ**

1. 共通部分を下の層に抽出する
2. 依存の向きを1つに決める
3. 宣言と定義を分ける ── ただし**宣言が両方の型を必要とする場合は使えません**(第14章 14.2.3)

第14章 14.2 で、`Matrix4x4` と `Quaternion` の相互変換について、この手順を実際に踏みました。

**注意:** 実装単位は循環に関与しません(第10章 10.4.4)。実装単位の `import` は、いくらあっても循環の原因になりません。グラフを描くときは、インターフェイス単位と内部パーティションだけを見てください。

### 17.3.7 症状 ── リンクエラー(LNK2019)

コンパイルは通ったが、リンクで失敗する場合です。

| # | 原因 | 参照 |
|---|---|---|
| 1 | **テンプレートの定義が実装単位にある** | 第8章 8.2 |
| 2 | 明示的インスタンス化していない型で、テンプレートを使った | 第8章 8.4.3 |
| 3 | 宣言だけあって、定義を書き忘れた | 第5章 5.3.1 |
| 4 | 利用側で同じ名前を自分で宣言してしまった | 第3章 3.5.3 |
| 5 | 実装単位がプロジェクトに追加されていない | ── |

1番がモジュール特有で、最も多い原因です。**テンプレートをインターフェイスに移すか、明示的インスタンス化を書く**かのどちらかです。

4番は見落としやすいので補足します。モジュールの外で `int Sub(int, int);` のように宣言すると、それはモジュール内の同名関数とは**別の実体**になります(モジュールリンケージ)。定義が見つからずリンクエラーになります。

### 17.3.8 症状 ── 警告 C5244 / C5201

第6章 6.1 で扱ったものです。**警告なのでビルドは通ってしまいます。**

| 警告 | 意味 | 対処 |
|---|---|---|
| **C5244** | 購買域に `#include` がある | グローバルモジュールフラグメントに移す |
| **C5201** | モジュール宣言の前に何か書いてあるのに `module;` がない | ファイル先頭に `module;` を追加 |

**警告を無視しないでください。** 第6章 6.1.5 で説明したとおり、購買域の `#include` は取り込んだ宣言をモジュールに所属させ、他所の同名の実体と別物にします。動いているように見えても、後で壊れます。

プロジェクトの警告レベルを上げ、可能なら `/WX`(警告をエラーとして扱う)を有効にしておくことを勧めます。

### 17.3.9 症状 ── ビルドのたびに出たり出なかったりする

**ビルド順序の問題です。** 依存関係が正しく認識されていないと、並列ビルドで「`.ifc` がまだない」状態が発生します。

対処は2つです。

**対処1: モジュール依存関係のスキャンを有効にする**

**[C/C++] → [全般] → モジュール依存関係のソースをスキャンする** を「はい」にします。

第2章 2.3.2 で「`.ixx` は設定に関係なく常にスキャンされる」と説明しました。しかし、モジュールに属する `.cpp`(実装単位)は既定ではスキャン対象外です。実装単位が増えてくると、この設定が必要になります(第5章 5.2.5 のコラム)。

**対処2: 中間ディレクトリを削除してリビルドする**

古い `.ifc` が残っていて、依存判定を狂わせていることがあります。

### 17.3.10 チェックリスト

行き詰まったときに、上から順に試してください。

```
□ 最初のエラーだけを見ているか
□ エラーが出ているファイルは .ixx / 実装単位 / 利用側のどれか
□ ビルドのエラーか、IntelliSense のエラーか
□ 出力ウィンドウのビルド順序は妥当か
□ auto で受けたら通るか(export 漏れか import 漏れかの切り分け)
□ 内部パーティションの /internalPartition 設定を確認したか
□ 依存グラフを紙に描いたか
□ 警告 C5244 / C5201 が出ていないか
□ リビルドしたか
□ 中間ディレクトリを削除したか
□ .vs フォルダーを削除したか
□ 第2章 2.5.3 の最小構成に戻して確認したか
```

最後の項目が重要です。**動く状態がどこかにあることを確認してから、そこに戻って一歩ずつ進める。** 第2章 2.5.2 で書いた原則です。

## 17.4 この章のまとめ

- **`import std;` ではマクロが使えない。** `assert`、`NULL`、`offsetof`、`errno`、`INT_MAX` などは対象外
- `assert` を使うには `<cassert>` をグローバルモジュールフラグメントに書く
- **`assert` の有効・無効は、そのファイルをコンパイルした時点の `NDEBUG` で確定する**
- インターフェイスに書いた `assert` は `.ifc` に焼き付けられ、利用者の `NDEBUG` は影響しない
- ヘッダ時代は逆だった。「利用者に `NDEBUG` で表明を切ってもらう」設計は成立しない
- **`assert` は実装単位に書く。** インターフェイスには置かない
- `static_assert` はキーワードなのでマクロの問題を持たない。**コンパイル時に判定できるものは `static_assert` を使う**
- デバッグ用の整形出力は `std::string` を必要とし、公開インターフェイスの方針に反する
- **解決は「別モジュールに隔離する」。** `gamemath.debug` でだけ `export import std;` を書く
- **規則には成立する条件がある。** 「利用者の環境を選ぶ」ことが問題なら、選ぶ余地を与えれば規則は不要になる
- **傘には入れない。** 傘は「全部入り」ではなく「既定で欲しいもの」
- 内部専用のダンプは内部パーティションに置く(実装単位からのみ使用)
- モジュールのエラーは、**出た場所と原因の場所が違う**。利用側で出たらライブラリ側を疑う
- **`auto` で受けてみるのが最も有効な切り分け** ── 通れば `export` 漏れ、通らなければ `import` 漏れ
- 循環依存は、依存グラフを描いてから第10章 10.4.5 の3つの対処を選ぶ。実装単位は循環に関与しない
- リンクエラーの筆頭原因は「テンプレートの定義が実装単位にある」
- **C5244 / C5201 は警告だが無視してはいけない**
