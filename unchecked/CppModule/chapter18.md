# 第18章 ヘッダユニットと既存コードの共存

## この章について

第5部に入ります。ここからは `GameMath` を実務に持ち込む話です。

この章で扱う**ヘッダユニット**は、`GameMath` では使いません。第11章のプライベートモジュールフラグメントと同じで、この本のライブラリには適合しない道具です。

それでも1章を割く理由は、**実務では必ず必要になるから**です。

現実のプロジェクトには、書き換えられないヘッダがあります。サードパーティのライブラリ、社内の共通ヘッダ、何年も前から使われている巨大な `Common.h` ── これらをモジュール化されたコードから使う必要があります。

そのための道具がヘッダユニットです。そして、**名前付きモジュールとは扱いが正反対**の性質を1つ持っています。

> **ヘッダユニットは、マクロをエクスポートします。**

第7章 7.1.4 で「唯一の例外」として予告した機能です。

そしてこの章は、**第2章 2.3.2 で「変更するタイミングは第18章で指示します」と予告した設定**を、ついに変更する回でもあります。

内容は4つです。

1. ヘッダユニットとは何か(18.1)
2. Visual Studio でビルドする(18.2)
3. 名前付きモジュールとの違い(18.3)
4. サードパーティのヘッダオンリーライブラリをどう扱うか(18.4)

## 18.1 ヘッダユニット `import <vector>;` とは

### 18.1.1 3つ目の取り込み方

これまでに2つの取り込み方を学びました。ここに3つ目が加わります。

```cpp
#include <vector>        // ① テキストの貼り付け(第1章)
import gamemath;         // ② 名前付きモジュール(第3章)
import <vector>;         // ③ ヘッダユニット  ← この章
```

③の書き方に注目してください。`import` に続けて、**山括弧や引用符でヘッダファイルを指定します**。名前付きモジュールとは構文が違います。

自作のヘッダなら引用符です。

```cpp
import "MyHeader.h";
```

### 18.1.2 何が起きるのか

ヘッダユニットは、**ヘッダファイルを1つの翻訳単位としてコンパイルし、`.ifc` を作ったもの**です。

やっていることは名前付きモジュールと似ています。

- ヘッダを1回だけ解析する
- 結果を `.ifc` に保存する
- `import` した側は `.ifc` を読む

だから、ビルド時間の面では名前付きモジュールと同じ利点があります。第1章 1.1.4 で見た掛け算の構造が、足し算に変わります。

**ソースコードを1行も書き換えずに**、これが得られるのが最大の魅力です。`#include <vector>` を `import <vector>;` に変えるだけ ── あるいは、後述する設定を使えば、書き換えすら不要です。

### 18.1.3 決定的な違い ── マクロがエクスポートされる

名前付きモジュールとの違いは1つです。**しかし、それが決定的です。**

> **ヘッダユニットは、そのヘッダが定義したマクロをエクスポートします。**

第7章 7.1 で、名前付きモジュールについてこう書きました。

> 名前付きモジュールは、マクロをエクスポートしません。例外はありません。

そして 7.1.4 で「唯一の例外はヘッダユニット」と予告しました。

なぜこうなっているのか。**ヘッダユニットの目的が「既存のヘッダを、意味を変えずに取り込むこと」だから**です。

既存のヘッダは、マクロを提供しているものが大量にあります。`assert`、`EOF`、`INT_MAX`、Windows API の各種定数 ── これらが消えてしまったら、`#include` を `import` に置き換えることができません。

だから、ヘッダユニットは**マクロを運びます**。

裏を返せば、**第1章 1.1.5 で扱ったマクロ汚染の問題は、ヘッダユニットでは解決しません。** `import <Windows.h>;` と書けば、`min` と `max` のマクロは容赦なく降ってきます。

### 18.1.4 取り込めるヘッダ、取り込めないヘッダ

どんなヘッダでもヘッダユニットにできるわけではありません。

**取り込めるもの**

- C++ 標準ライブラリのヘッダ(`<vector>`、`<string>`、`<algorithm>` など)
- ヘッダユニットとして成立するように書かれた自作ヘッダ
- 多くのヘッダオンリーライブラリ

**取り込めないもの**

- **C 由来のヘッダ**(`<cassert>`、`<cerrno>` など)。マクロを中心に構成されており、複数回インクルードして状態を変える使い方が想定されているためです
- 取り込む順序や、事前に定義されたマクロによって中身が変わるヘッダ
- インクルードガードのないヘッダ

最後の2つは実務でよく引っかかります。「`#define FOO` してから `#include` すると挙動が変わる」という設計のヘッダは、ヘッダユニットにできません。**ヘッダユニットも1回しかコンパイルされない**からです。第16章 16.4.2 で名前付きモジュールについて説明したのと同じ理屈が、ここでも効きます。

### 18.1.5 `import std;` があるいま、標準ライブラリには不要

ヘッダユニットが登場した当初、いちばん期待されていた用途は**標準ライブラリの高速化**でした。

```cpp
import <vector>;
import <string>;
import <algorithm>;
```

これで `<vector>` の解析が1回で済む ── 確かに効果はありました。

**いまは、その用途はほぼ不要です。** C++23 で `import std;` が入ったからです(第6章 6.4)。

| | ヘッダユニット | `import std;` |
|---|---|---|
| 書き方 | `import <vector>;` を並べる | 1行 |
| 取り込む量 | 指定したものだけ | 標準ライブラリ全体 |
| マクロ | 入ってくる | 入らない |
| 名前空間の汚染 | `::printf` なども入る | `std::` だけ |
| 設定 | ヘッダユニットのビルドが必要 | 標準ライブラリモジュールのビルド |

`import std;` のほうが単純で、マクロ汚染もありません。第6章 6.6.1 で `GameMath` の方針として `import std;` を選んだのは、これが理由でした。

**では、ヘッダユニットは何のために残るのか。**

**自分で書き換えられないヘッダのため**です。サードパーティのライブラリ、社内の共通ヘッダ、レガシーコード ── これらは `import std;` では解決しません。18.4 の主題です。

## 18.2 Visual Studio でヘッダユニットをビルドする

### 18.2.1 題材を用意する

実験用に、小さなヘッダオンリーライブラリを用意します。サードパーティ製という想定です。

`ThirdParty/tiny_log.h` を作ってください(「ヘッダー ファイル」に追加します)。

```cpp
// ThirdParty/tiny_log.h
#pragma once

#define TINY_VERSION_MAJOR 1
#define TINY_VERSION_MINOR 2

// 呼び出し位置を記録するマクロ
#define TINY_HERE() ::tiny::MakeLocation(__FILE__, __LINE__)

namespace tiny {

struct Location
{
    const char* file;
    int         line;
};

inline Location MakeLocation(const char* file, int line)
{
    return Location{ file, line };
}

inline int Version()
{
    return TINY_VERSION_MAJOR * 100 + TINY_VERSION_MINOR;
}

} // namespace tiny
```

**マクロと `inline` 関数と型が混在した、ごく普通のヘッダオンリーライブラリ**です。標準ヘッダを1つも `#include` していないので、実験の邪魔になるものがありません。

### 18.2.2 方法1 ── ファイルを明示的にヘッダユニットにする

まず、明示的な方法です。

**手順**

1. ソリューションエクスプローラーで **`tiny_log.h` を右クリック** → **[プロパティ]**
2. **[構成] を「すべての構成」、[プラットフォーム] を「すべてのプラットフォーム」** に(第2章 2.2.2)
3. **[C/C++] → [詳細設定] → コンパイル言語の選択** を **「C++ ヘッダー ユニットとしてコンパイル (/exportHeader)」** に変更

第2章 2.3.1 で見た表の、3番目の選択肢です。第10章 10.2.2 で内部パーティションのために `/internalPartition` を選んだのと、同じ場所です。

| 選択肢 | 意味 | 章 |
|---|---|---|
| C++ モジュール コードとしてコンパイル (`/interface`) | インターフェイス単位 | 第3章 |
| C++ 内部パーティションとしてコンパイル (`/internalPartition`) | 内部パーティション | 第10章 |
| **C++ ヘッダー ユニットとしてコンパイル (`/exportHeader`)** | **ヘッダユニット** | **第18章** |

これで3つとも登場しました。

**使ってみる**

`main.cpp` に追加します。

```cpp
// main.cpp
import std;
import gamemath;
import gamemath.debug;

import "ThirdParty/tiny_log.h";      // ← ヘッダユニットを取り込む

int main()
{
    // ...

    const tiny::Location here = TINY_HERE();     // ← マクロが使えている
    std::println("tiny version = {}", tiny::Version());
    std::println("here = {}:{}", here.file, here.line);

    return 0;
}
```

ビルドして実行してください。

```
tiny version = 102
here = C:\...\main.cpp:123
```

**`TINY_HERE()` というマクロが使えました。** 名前付きモジュールでは絶対に不可能なことです。

### 18.2.3 【第2章の宿題】依存関係のスキャンを有効にする

うまくいかなかった場合、あるいは次の項に進む準備として、設定を1つ変更します。

第2章 2.3.2 で確認した設定です。

**[C/C++] → [全般] → モジュール依存関係のソースをスキャンする** を **「はい」** に変更してください。

第2章では、こう説明しました。

> `.ixx` 拡張子のファイルは、この設定に関係なく常にスキャンされる。ヘッダユニットとしてコンパイルするよう設定されたファイルも同様。

だから 18.2.2 の方法1は、この設定なしでも動きました。

**「はい」にすると、すべての C++ ソースがスキャン対象になります。** ビルドシステムはプロジェクト全体の依存グラフを構築し、`import` されているモジュールやヘッダユニットが、それを使うファイルより先にビルドされることを保証します。

第2章から予告してきた「変更するタイミング」が、ここです。

なお、この設定は**実装単位が増えたプロジェクトでも意味を持ちます**。第5章 5.2.5 のコラムと第17章 17.3.9 で触れたとおり、ビルド順序が不安定なときの対処でもあります。`GameMath` は実装単位が5つになったので、そういう意味でも有効にしておく価値があります。

代償はビルド前のスキャン時間です。第2章 2.3.2 のコラムで書いたとおり、大規模なプロジェクトでは依存グラフが正確になって並列度が上がり、かえって速くなることもあります。第21章で計測します。

### 18.2.4 方法2 ── 自動でスキャンさせる

方法1では、ヘッダごとにプロパティを設定する必要がありました。ヘッダが100個あれば100回です。

**自動化する方法があります。**

「モジュール依存関係のソースをスキャンする」が「はい」になっていれば、コンパイラはソースの中の `import "..."` や `import <...>` を探し、**必要なヘッダユニットを自動的にビルドします。**

つまり、`tiny_log.h` のプロパティを既定に戻しても、`main.cpp` に `import "ThirdParty/tiny_log.h";` と書いてあれば動きます。試してみてください。

Microsoft のドキュメントは、この方法について次のように述べています。

> この方法は便利だが、最適なビルドスループットを保証しないため、小規模なプロジェクトに向いている。

すべてのソースをスキャンし、必要なヘッダユニットをその都度ビルドするので、オーバーヘッドがあります。大規模なプロジェクトでは、方法1で「これをヘッダユニットにする」と明示的に指定するほうが制御しやすくなります。

### 18.2.5 `#include` を書き換えずに済ませる

もう一段、進んだ機能があります。

**`/translateInclude`(インクルードをインポートに変換する)** です。

これを有効にすると、コンパイラは `#include` を見つけたとき、対応するヘッダユニットの `.ifc` が存在すれば、**`#include` の代わりに `import` として扱います。**

つまり、**ソースコードを1行も書き換えずに、ヘッダユニットの恩恵を受けられます。**

**[C/C++] → [全般] → インクルードをインポートに変換する** を「はい」にすると有効になります。

ただし条件があります。**すべての `#include` が変換されるわけではありません。**

変換されるのは、**`header-units.json` という許可リストに載っているヘッダだけ**です。このファイルは、ヘッダと同じディレクトリに置きます。載っていないヘッダは、通常どおり `#include` として処理されます。

なぜ許可リストが必要なのか ── 18.1.4 で述べたとおり、**ヘッダユニットにできないヘッダがある**からです。無条件に変換すると壊れます。だから「これは変換してよい」と明示する仕組みになっています。

`/translateInclude` は `/std:c++20` 以上が必要です。

**この機能は、第19章の移行戦略で重要になります。** 既存の巨大なコードベースを、ソースを触らずに段階的に速くできるからです。

### 18.2.6 注意 ── プリプロセッサが切り替わる

1つ、見落としやすい落とし穴があります。

Microsoft のドキュメントには、こう書かれています。

> ヘッダユニットの作成と使用には、標準準拠のプリプロセッサが必要である。`/exportHeader` を何らかの形で使うと、コンパイラは暗黙に `/Zc:preprocessor` をコマンドラインに追加する。これを無効にしようとするとコンパイルエラーになる。

MSVC には歴史的に2つのプリプロセッサがあります。従来の独自実装と、標準に準拠した新しい実装です。**ヘッダユニットを使うと、後者が強制的に有効になります。**

そして、ドキュメントはこう続けます。

> 新しいプリプロセッサを有効にすると、可変引数マクロの処理に影響する。

つまり、**`__VA_ARGS__` を使った複雑なマクロが、動作を変える可能性があります。**

古いコードベースには、可変引数マクロを駆使したログ機能やアサーション機能がよくあります。ヘッダユニットを導入した途端に、そういうマクロが壊れることがあります。

**移行の前に、`/Zc:preprocessor` を単独で有効にして、ビルドが通るか確認してください。** ヘッダユニットとは無関係に確認できるので、切り分けが楽になります。

## 18.3 名前付きモジュールとの違いと使いどころ

### 18.3.1 比較表

3つの取り込み方を並べます。

| | `#include` | **ヘッダユニット** | 名前付きモジュール |
|---|---|---|---|
| 書き方 | `#include <x>` | `import <x>;` | `import m;` |
| 解析の回数 | 翻訳単位ごと | **1回** | 1回 |
| **マクロ** | 漏れる | **漏れる** | **漏れない** |
| 取り込む順序 | 影響する | **影響する場合がある** | 影響しない |
| 非公開のものを隠せるか | 隠せない | **隠せない** | 隠せる |
| ソースの書き換え | ── | **ほぼ不要** | 大規模に必要 |
| インクルードガード | 必要 | 必要 | 不要 |

**ヘッダユニットは、`#include` と名前付きモジュールの中間にあります。**

得られるのは「解析が1回で済む」という**ビルド時間の利点だけ**です。マクロは漏れ、隠蔽もできません。第1章で挙げた5つの問題のうち、解決するのは1つだけです。

代わりに、**ソースをほとんど書き換えずに済みます。** これが唯一にして最大の価値です。

### 18.3.2 【実験】マクロが通ることを確認する

18.2.2 ですでに確認しましたが、対比のためにもう一度整理します。

```cpp
// main.cpp
import "ThirdParty/tiny_log.h";

int main()
{
    const tiny::Location here = TINY_HERE();          // ← マクロ。通る
    static_assert(TINY_VERSION_MAJOR == 1);           // ← マクロ。通る
    const int v = tiny::Version();                    // ← 関数。通る
}
```

**マクロも関数も型も、全部そのまま使えます。** ヘッダを `#include` したときと、ほとんど区別がつきません。

### 18.3.3 【実験】名前付きモジュールでは通らない

同じヘッダを、名前付きモジュールでラップしてみます。

`ThirdParty/TinyLogModule.ixx` を作ってください。

```cpp
// ThirdParty/TinyLogModule.ixx
module;

#include "tiny_log.h"          // グローバルモジュールフラグメントで取り込む

export module tinylog;

namespace tinylog {

// 関数は、呼び直す形で公開できる
export int Version()
{
    return tiny::Version();
}

export tiny::Location Here(const char* file, int line)
{
    return tiny::MakeLocation(file, line);
}

// マクロは公開できない。export #define という構文は存在しない

} // namespace tinylog
```

`main.cpp` で試します。

```cpp
import tinylog;

int main()
{
    std::println("{}", tinylog::Version());     // ← 通る

    // TINY_HERE();                             // ← エラー。マクロは届かない
    // TINY_VERSION_MAJOR                       // ← エラー。同上
}
```

コメントを外して確かめてください。

```
error C2065: 'TINY_HERE': 定義されていない識別子です。
```

第3章 3.6.4 と第16章 16.4.1 で確認したことが、サードパーティのヘッダでも同じように起きています。

そして、このラッパーには**もう1つの限界**があります。

**元の名前をそのまま引き継げません。** `tiny::Version` を `tiny::Version` として公開しようとすると、グローバルモジュールフラグメントの `tiny::Version` と衝突します。だから `tinylog::Version` という別の名前にせざるを得ませんでした。

利用者から見れば、名前が変わったということです。既存コードの書き換えが必要になります。

> `export using` を使って名前を引き継ぐ手法もありますが、名前空間の扱いが込み入り、コンパイラによって挙動が違うことがあります。**ラッパーモジュールは、思ったほど透過的ではない** ── そう理解しておいてください。

### 18.3.4 混ぜてはいけない

第6章 6.5.1 で引用した Microsoft の注意を、もう一度確認します。

> ヘッダユニットと名前付きモジュールを混ぜないこと。たとえば、同じファイルの中で `import <vector>;` と `import std;` を併用してはいけない。

理由は第6章 6.5.2 のとおりです。同じ実体が2つの経路から入ってきて、コンパイラが同一視しきれない場面が生じます。

具体的には、こういうコードを書かないでください。

```cpp
// 危険
import std;
import <vector>;         // 標準ライブラリを2つの経路で取り込んでいる
```

```cpp
// 危険
import std;
import "ThirdParty/heavy.h";     // heavy.h が #include <vector> していたら
```

2つ目が厄介です。**サードパーティのヘッダが内部で標準ヘッダを `#include` していると、それがヘッダユニット経由で入ってきます。**

`tiny_log.h` を標準ヘッダなしで書いたのは、この問題を避けるためでした。実際のライブラリは、まず間違いなく標準ヘッダを使っています。

**対策**

- 標準ライブラリの取り込み方を、翻訳単位ごとに統一する
- サードパーティのヘッダをヘッダユニットにする翻訳単位では、`import std;` を使わず `#include` で揃える
- あるいは、ヘッダユニットにせず 18.4 の別の案を選ぶ

### 18.3.5 Microsoft の公式な立場

ドキュメントには、はっきりとこう書かれています。

> これらの機能はレガシーコードのために設計されている。新しいコードでは、ヘッダユニットや `#include` ではなくモジュールに移行すること。

**ヘッダユニットは移行のための道具であって、目的地ではありません。**

本書の立場も同じです。新しく書くコードは名前付きモジュールにします。ヘッダユニットは、書き換えられないものを扱うための一時的な手段です。

### 18.3.6 いつ使うか

判断は単純です。

**使う**

- 自分で書き換えられないヘッダがある
- そのヘッダのマクロが必要
- 移行の途中で、既存のヘッダと共存する必要がある
- ソースの書き換えなしでビルド時間を改善したい

**使わない**

- 標準ライブラリ(`import std;` を使う)
- 自分で書けるコード(名前付きモジュールにする)
- マクロを持ち込みたくないヘッダ

## 18.4 サードパーティライブラリ(ヘッダオンリー)を取り込む

### 18.4.1 現実の問題

ゲーム開発でよく使うヘッダオンリーライブラリを思い浮かべてください。JSON パーサ、数式パーサ、画像読み込み、ログ、テストフレームワーク ── どれも `#include` するだけで使える手軽さが売りです。

これらを `GameMath` のようなモジュール化されたコードから使うには、どうすればよいか。

**3つの案があります。**

### 18.4.2 案1 ── グローバルモジュールフラグメントで `#include`

第6章 6.2 で学んだ方法です。

```cpp
// MyModule.ixx
module;

#include "ThirdParty/json.hpp"

export module myapp.config;

import std;

namespace myapp {

export bool LoadConfig(const char* path);

} // namespace myapp
```

**長所**

- 確実に動きます。ヘッダユニットにできないヘッダでも大丈夫です
- 設定が不要です
- 第6章 6.3.3 で確認したとおり、**マクロは利用者に漏れません**

**短所**

- ヘッダの解析が、それを取り込んだモジュール単位ごとに発生します。ビルド時間の改善はありません
- そのヘッダを複数のモジュールで使うと、それぞれで解析されます

**この案が基本です。** 迷ったらこれを選んでください。

### 18.4.3 案2 ── ヘッダユニットにする

```cpp
// MyModule.ixx
export module myapp.config;

import "ThirdParty/json.hpp";     // ヘッダユニット
import std;                       // ← 危険。18.3.4 参照
```

**長所**

- 解析が1回で済みます

**短所**

- 18.1.4 の条件を満たすヘッダでなければ使えません
- 18.3.4 の混在問題があります
- 18.2.6 のプリプロセッサ切り替えの影響を受けます
- **マクロが利用者に漏れます**

最後の点に注意してください。案1では漏れなかったマクロが、案2では漏れます。「サードパーティのマクロが、自分のライブラリの利用者に届いてしまう」── これは、第1章 1.1.5 で批判したマクロ汚染そのものです。

### 18.4.4 案3 ── ラッパーモジュールを書く

サードパーティのヘッダを、自分のモジュールで包んでしまう方法です。18.3.3 で試したものです。

```cpp
// ThirdParty/Json.ixx
module;

#include "ThirdParty/json.hpp"

export module myapp.json;

import std;

namespace myapp {

// 必要な機能だけを、自分の言葉で公開する
export struct JsonValue { /* ... */ };
export JsonValue Parse(const char* text);

} // namespace myapp

```

**長所**

- **サードパーティの型もマクロも、利用者に一切漏れません。** 第7章 7.2 で得たカプセル化が、外部ライブラリに対しても効きます
- ライブラリを差し替えるとき、ラッパーの中だけを直せば済みます
- 自分のコードベースの命名規則に揃えられます
- 必要な機能だけを公開できます

**短所**

- **書く手間がかかります。** 使いたい機能の数だけラッパーを書きます
- 18.3.3 で見たとおり、**元の名前をそのまま引き継ぐのが難しい**ので、利用者の書き方が変わります
- 型を通したい場合、結局その型を公開することになり、隔離が破れます

### 18.4.5 判断の目安

| 状況 | 案 |
|---|---|
| とりあえず動かしたい | **案1**(GMF で `#include`) |
| そのヘッダを1〜2個のモジュールでしか使わない | **案1** |
| 多数のモジュールで使い、ビルド時間が問題になっている | 案2(ヘッダユニット) |
| そのライブラリのマクロが必要 | 案2 |
| 将来ライブラリを差し替える可能性がある | **案3**(ラッパー) |
| サードパーティの型を自分の API に出したくない | **案3** |
| 依存を最小限に保ちたいライブラリを作っている | **案3** |

`GameMath` のような**再配布するライブラリ**を作っているなら、案3を強く勧めます。第6章 6.5.4 で「公開インターフェイスに標準ライブラリの型を出さない」と決めた理由と同じです。**利用者に、自分が選んだ依存関係を押しつけない**という原則です。

一方、**アプリケーション側のコード**なら案1で十分なことがほとんどです。依存関係を隠す相手がいないからです。

### 18.4.6 `GameMath` はどうするか

**`GameMath` は、サードパーティのライブラリを使いません。**

依存しているのは標準ライブラリだけで、それは `import std;` で取り込んでいます(第6章 6.6.1)。

これは偶然ではありません。**数学ライブラリは、依存を持たないことに価値があります。** どんなプロジェクトにも組み込めるからです。

第22章で実際のゲームコードから使うとき、逆の立場になります。ゲーム側のコードは描画 API やウィンドウ管理のヘッダを使うので、そこで案1が登場します。

**この章で作った `ThirdParty/tiny_log.h` と `TinyLogModule.ixx` は、実験用です。** プロジェクトから削除して構いません。残しておいても害はありませんが、`GameMath` の一部ではありません。

## 18.5 この章のまとめ

- **ヘッダユニット**は3つ目の取り込み方。`import <vector>;` / `import "MyHeader.h";`
- ヘッダを1回だけ解析して `.ifc` にする。**ソースをほとんど書き換えずにビルド時間を改善できる**
- **名前付きモジュールと違い、マクロをエクスポートする。** 既存のヘッダを意味を変えずに取り込むための設計
- 裏を返せば、**マクロ汚染は解決しない**
- C 由来のヘッダ、取り込む順序で挙動が変わるヘッダは、ヘッダユニットにできない
- **`import std;` があるいま、標準ライブラリ用途では不要**。残る用途は書き換えられないヘッダ
- Visual Studio では、ファイルの**コンパイル言語の選択**を `/exportHeader` にするか、**モジュール依存関係のソースをスキャンする**を「はい」にして自動化する
- **第2章から予告してきた設定の変更は、ここで行う**
- **`/translateInclude`**(インクルードをインポートに変換する)を使えば、`#include` のまま自動変換できる。ただし `header-units.json` の許可リストに載ったヘッダだけ
- `/exportHeader` を使うと**標準準拠プリプロセッサが強制される**。可変引数マクロの挙動が変わる可能性がある
- ヘッダユニットは `#include` と名前付きモジュールの**中間**。解決するのはビルド時間だけ
- **ヘッダユニットと名前付きモジュールを混ぜてはいけない**。サードパーティのヘッダが標準ヘッダを `#include` している場合も同様
- Microsoft の公式見解 ── **「レガシーコードのための機能。新しいコードではモジュールに移行せよ」**
- サードパーティのヘッダオンリーライブラリの扱いは3案 ── GMF で `#include` / ヘッダユニット / **ラッパーモジュール**
- **再配布するライブラリを作るならラッパー。** 利用者に自分の依存関係を押しつけない
- `GameMath` は標準ライブラリ以外に依存しないので、いずれも使わない
