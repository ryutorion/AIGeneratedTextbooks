# 第10章 内部パーティションと実装の共有

## この章について

第9章で作ったパーティションは、どちらも `export module gamemath:...;` で始まる**インターフェイスパーティション**でした。外に公開するものを書く場所です。

この章で扱うのは、その反対です。**内部パーティション**(internal partition)── `export` を一切書けないパーティションです。

用途ははっきりしています。**モジュールの実装で共有したいものを置く場所**です。ヘッダの世界でいえば、「公開しない社内向けヘッダ」に相当します。

内容は4つです。

1. なぜそんなものが必要になるのか(10.1)
2. どう作るのか ── Visual Studio では設定が1つ必要です(10.2)
3. インターフェイスパーティションとの使い分け(10.3)
4. 依存関係を循環させないための設計(10.4)

3番目には、単なる好みではない**技術的な線引き**があります。「内部パーティションに置いてはいけないもの」があるのです。理由は第7章の到達可能性に戻ります。

4番目は、パーティションが増えてくると必ず直面する問題です。ここで原則を作っておかないと、第13章以降で身動きが取れなくなります。

## 10.1 複数の実装で使う共通ヘルパーを置きたい

### 10.1.1 いまの構成

第9章を終えた時点の `GameMath` です。

```
GameMath.ixx    export module gamemath;          ← プライマリ
Vector.ixx      export module gamemath:vector;   ← インターフェイスパーティション
Basis.ixx       export module gamemath:basis;    ← インターフェイスパーティション
Basis.cpp       module gamemath;                 ← 実装単位
```

実装単位は `Basis.cpp` の1つだけです。しかし、これから増えます。

- `Matrix.cpp`(第13章)
- `Quaternion.cpp`(第14章)
- `Intersect.cpp`(第15章)

そして、これらは**同じヘルパーを必要とします**。

### 10.1.2 共有したいものの例

具体例を2つ挙げます。どちらも実際に必要になるものです。

**例1: 最小成分の軸を返す**

第5章から使っている `Orthogonal` の中身を見てください。

```cpp
const T ax = std::abs(v.x());
const T ay = std::abs(v.y());
const T az = std::abs(v.z());

if (ax <= ay && ax <= az) { return Cross(v, Vector<T, 3>{ T(1), T(0), T(0) }); }
if (ay <= az)             { return Cross(v, Vector<T, 3>{ T(0), T(1), T(0) }); }
return Cross(v, Vector<T, 3>{ T(0), T(0), T(1) });
```

「3成分のうち、絶対値が最小の軸を選ぶ」という処理です。これは第13章で行列から回転軸を取り出すときにも、第15章で衝突判定の分離軸を選ぶときにも使います。

**例2: 定義域を丸めてから `acos` する**

2つのベクトルのなす角を求める処理を考えます。

```cpp
const float d = Dot(a.Normalized(), b.Normalized());
return std::acos(d);
```

数学的には `d` は必ず `[-1, 1]` に収まります。しかし浮動小数点の誤差で、`1.0000001` になることがあります。すると `std::acos` は **NaN** を返します。

ゲーム開発で悪名高いバグです。ほとんどの場合は正しく動き、たまにキャラクターの向きが吹き飛ぶ ── という形で現れます。

だから実務では、必ず定義域を丸めてから呼びます。この処理は、ベクトルでもクォータニオン(第14章の `Slerp`)でも必要です。

### 10.1.3 どこに置くか ── 3つの候補と、その問題

**候補1: 各実装単位にコピーする**

`Basis.cpp` にも `Quaternion.cpp` にも同じ関数を書く。

論外です。第1章から一貫して批判してきた「同じコードが複数箇所にある」状態そのものです。

**候補2: インターフェイスパーティションに `export` なしで書く**

`Vector.ixx` に `export` を付けずに書く方法です。第9章 9.4.2 で確認したとおり、パーティションどうしでは非公開の宣言も見えるので、これは**動きます**。

しかし2つの問題があります。

第一に、**置き場所として不自然です。** 「ベクトルのインターフェイス」を定義するファイルに、実装の都合で使うヘルパーが混ざります。ファイルを開いた人が、どこまでが公開インターフェイスなのか判断しづらくなります。

第二に、**`.ifc` に載ります。** 第7章 7.4.5 で確認したとおり、インターフェイス単位に書いたものは公開・非公開を問わず `.ifc` の一部になります。利用者が読み込む量が増え、そこを変更すれば利用者は再コンパイルされます。

**候補3: 内部パーティション**

`export` を書けない、専用のパーティションを作ります。これが正解です。

- インターフェイスとは別のファイルになるので、置き場所が明確
- `export` を書けないので、うっかり公開する事故が起きない
- モジュール内のどの単位からも `import` できる

## 10.2 内部パーティション(非エクスポートパーティション)を作る

### 10.2.1 ファイルを追加する

`Detail.ixx` を追加してください。「C++ モジュール インターフェイス ユニット (.ixx)」で構いません(中身は消してください)。

拡張子を `.ixx` にする理由は、**内部パーティションは `.ifc` を生成するから**です。普通の `.cpp` とは違い、他のファイルから `import` される「読み込まれる側」です。インターフェイス単位の仲間として扱うほうが、探しやすくなります。

ただし、そのままではビルドできません。設定が1つ必要です。

### 10.2.2 【重要】コンパイル方法を設定する

第2章 2.3.1 で、`.ixx` は自動的に `/interface` としてコンパイルされることを確認しました。そして、こういう表を見ました。

| 選択肢 | 意味 | 本書での扱い |
|---|---|---|
| C++ モジュール コードとしてコンパイル (`/interface`) | モジュールインターフェイス単位 | 第3章以降ずっと |
| C++ 内部パーティションとしてコンパイル (`/internalPartition`) | 内部パーティション | **第10章** |
| C++ ヘッダー ユニットとしてコンパイル (`/exportHeader`) | ヘッダユニット | 第18章 |

いま、2番目を使うときが来ました。

**手順**

1. ソリューションエクスプローラーで **`Detail.ixx` を右クリック** → **[プロパティ]**(プロジェクトではなく、**ファイル**のプロパティです)
2. ダイアログ上部の **[構成] を「すべての構成」、[プラットフォーム] を「すべてのプラットフォーム」** に(第2章 2.2.2)
3. **[C/C++] → [詳細設定] → コンパイル言語の選択** を **「C++ 内部パーティションとしてコンパイル (/internalPartition)」** に変更

**この設定を忘れると、ビルドに失敗します。** しかもエラーメッセージは分かりにくいものになります。内部パーティションを追加したら、真っ先にこの設定を確認してください。

> **なぜ専用のコンパイル方法が必要なのか**
>
> `/interface` は「このファイルはモジュールインターフェイス単位である」という指定です。インターフェイス単位のモジュール宣言には `export` が必要です。
>
> 内部パーティションのモジュール宣言には `export` を書けません。`/interface` とは前提が食い違うので、別の指定が要ります。
>
> これは MSVC 固有の事情ではなく、C++ の言語仕様上、両者が別種のモジュール単位であることの反映です。ただし「コンパイラオプションで区別する」という解決の仕方は MSVC 固有です。他のコンパイラでは扱いが違います(付録E)。

### 10.2.3 中身を書く

```cpp
// Detail.ixx
module gamemath:detail;      // ← export なし

import :vector;
import std;

namespace gamemath {

// 3成分のうち、絶対値が最小の軸に対応する単位ベクトルを返す
template <FloatingPoint T>
Vector<T, 3> MinorAxis(const Vector<T, 3>& v)
{
    const T ax = std::abs(v.x());
    const T ay = std::abs(v.y());
    const T az = std::abs(v.z());

    if (ax <= ay && ax <= az) {
        return Vector<T, 3>{ T(1), T(0), T(0) };
    }
    if (ay <= az) {
        return Vector<T, 3>{ T(0), T(1), T(0) };
    }
    return Vector<T, 3>{ T(0), T(0), T(1) };
}

// 定義域を [-1, 1] に丸めてから acos する
template <FloatingPoint T>
T SafeAcos(T x)
{
    if (x <= T(-1)) {
        return std::numbers::pi_v<T>;
    }
    if (x >= T(1)) {
        return T(0);
    }
    return std::acos(x);
}

} // namespace gamemath
```

1行目に注目してください。

```cpp
module gamemath:detail;
```

**`export` がありません。** これが内部パーティションの目印です。

第5章 5.2.2 で見た形と同じです。

| 書き方 | 種類 |
|---|---|
| `export module gamemath;` | プライマリモジュールインターフェイス単位 |
| `export module gamemath:vector;` | インターフェイスパーティション |
| `module gamemath:detail;` | **内部パーティション** |
| `module gamemath;` | 実装単位 |

`export` の有無が「インターフェイスかどうか」を、コロンの有無が「パーティションかどうか」を決めています。4通りの組み合わせが、そのまま4種類のモジュール単位に対応します。

`import :vector;` を書いている点にも注意してください。`Vector` と `FloatingPoint` を使うので必要です。**同じモジュールの中でも `import` は必要**です(第9章 9.4.2)。

### 10.2.4 実装単位から使う

`Basis.cpp` を書き換えます。

```cpp
// Basis.cpp
module gamemath;

import :detail;              // ← 追加
import std;

namespace gamemath {

template <FloatingPoint T>
Vector<T, 3> Orthogonal(const Vector<T, 3>& v)
{
    if (v.LengthSquared() <= kEpsilon<T>) {
        return Vector<T, 3>{ T(1), T(0), T(0) };
    }
    return Cross(v, MinorAxis(v));       // ← すっきりした
}

template Vector<float, 3>  Orthogonal(const Vector<float, 3>&);
template Vector<double, 3> Orthogonal(const Vector<double, 3>&);

BasisPair MakeBasis(const Vector3& normal)
{
    const Vector3 n = normal.Normalized();
    const Vector3 t = Orthogonal(n).Normalized();
    const Vector3 b = Cross(n, t);
    return BasisPair{ t, b };
}

float AngleBetween(const Vector3& a, const Vector3& b)
{
    const float d = Dot(a.Normalized(), b.Normalized());
    return SafeAcos(d);
}

} // namespace gamemath
```

`import :detail;` が必要です。実装単位はプライマリを暗黙に `import` しますが、プライマリは `:detail` を `import` していないので、自分で書きます。

`AngleBetween` を新しく追加しました。これを公開するために、`Basis.ixx` にも1行足します。

```cpp
// Basis.ixx
export module gamemath:basis;

import :vector;

namespace gamemath {

export template <FloatingPoint T>
Vector<T, 3> Orthogonal(const Vector<T, 3>& v);

export struct BasisPair
{
    Vector3 tangent;
    Vector3 bitangent;
};

export BasisPair MakeBasis(const Vector3& normal);

export float AngleBetween(const Vector3& a, const Vector3& b);   // ← 追加

} // namespace gamemath
```

`Basis.ixx` は `:detail` を `import` していません。**必要ないからです。** `AngleBetween` の宣言は `SafeAcos` を使っていません。使っているのは定義のほうで、それは `Basis.cpp` にあります。

これは重要なポイントです。**インターフェイスは内部パーティションを知らなくてよい。**

### 10.2.5 動作確認

`main.cpp` に確認用の行を足します。

```cpp
const float angle = gamemath::AngleBetween(a, b);
std::println("Angle(a,b) = {:.4f} rad = {:.2f} deg",
             angle, angle * 180.0f / std::numbers::pi_v<float>);
```

ビルドして実行してください。

```
Angle(a,b) = 0.2257 rad = 12.93 deg
```

`(1,2,3)` と `(4,5,6)` のなす角、約 12.93 度です。

### 10.2.6 【実験】`export` を書いてみる

内部パーティションに `export` を書くとどうなるか、確かめておきましょう。

```cpp
// Detail.ixx
module gamemath:detail;

// ...

export template <FloatingPoint T>      // ← export を追加
Vector<T, 3> MinorAxis(const Vector<T, 3>& v)
{
    // ...
}
```

**エラーになります。** 内部パーティションでは `export` を使えません。

モジュール宣言に `export` を付けてみるのはどうでしょうか。

```cpp
export module gamemath:detail;   // ← インターフェイスパーティションになってしまう
```

これは文法的には正しいのですが、内部パーティションではなくなります。しかも `/internalPartition` でコンパイルしているので、設定と食い違ってエラーになります。

さらに、プライマリから再エクスポートしようとしても駄目です。

```cpp
// GameMath.ixx
export import :detail;   // ← エラー。内部パーティションはエクスポートできない
```

**内部パーティションを外に出す方法は、存在しません。** 言語仕様として明示的に禁じられています。

これが候補2(インターフェイスパーティションに `export` なしで書く)との決定的な違いです。あちらは「うっかり `export` を付けてしまう」事故が起こり得ます。内部パーティションなら、コンパイラが止めてくれます。

**実験が終わったら、元に戻してください。**

### 10.2.7 プライマリから `import` する必要はない

第9章 9.2.4 で、こういう規則を確認しました。

> モジュールのすべてのインターフェイスパーティションは、プライマリモジュールインターフェイス単位から `import` されていなければならない。

**内部パーティションには、この規則は適用されません。**

`GameMath.ixx` は、いまも `:vector` と `:basis` だけを `export import` しています。`:detail` については何も書いていません。それで正しいのです。

理由を考えると納得できます。この規則は「モジュールの公開インターフェイスが、プライマリを見れば全部分かる」ことを保証するためのものでした(第5章 5.5.2 と同じ発想)。内部パーティションは公開インターフェイスの一部ではないので、プライマリが知る必要がありません。

## 10.3 インターフェイスパーティションとの使い分け

### 10.3.1 4種類のモジュール単位

ここまでで、モジュール単位が4種類すべて出そろいました。整理します。

| | プライマリ | インターフェイス<br>パーティション | 内部<br>パーティション | 実装単位 |
|---|---|---|---|---|
| 書き出し | `export module M;` | `export module M:P;` | `module M:P;` | `module M;` |
| MSVC の設定 | `.ixx` で自動 | `.ixx` で自動 | **`/internalPartition`** | `.cpp` のまま |
| `.ifc` を生成 | ○ | ○ | ○ | ✕ |
| `export` を書けるか | ○ | ○ | **✕** | ✕ |
| 1モジュールにいくつ | **1つだけ** | 何個でも | 何個でも | 何個でも |
| プライマリからの `import` | ── | **必須** | 不要 | ── |
| モジュール内から `import` | できる | できる | できる | **できない** |
| 外部から `import` | できる | できない | できない | できない |

いちばん下から2行目に注目してください。**実装単位だけは `import` できません。** `.ifc` を生成しないからです。実装単位に書いたものを他のファイルから使うことはできません。

第5章 5.4.3 で「実装単位どうしはお互いを見ない」と書いた理由がこれです。そして、その問題への答えが内部パーティションだった、というわけです。

### 10.3.2 どれを選ぶか

判断の順番はこうなります。

**1. 利用者に公開するか?**

する → **インターフェイスパーティション**に `export` 付きで書く。

**2. 公開しないなら、インライン展開・テンプレート・`constexpr` が必要か?**

必要 → **インターフェイスパーティション**に `export` なしで書く。

**3. 複数のモジュール単位から使うか?**

使う → **内部パーティション**。

**4. 1つのファイルの中だけか?**

そう → **実装単位**に直接書く。

2番目の分岐が、この章で最も注意が必要なところです。次の項で説明します。

### 10.3.3 なぜ `kEpsilon` は `:vector` に残したのか

10.1.2 で共有したいものの例を挙げたとき、`kEpsilon` を含めませんでした。あれも `Vector::Normalized()` と `Orthogonal()` の両方で使われている、共有されたヘルパーです。なぜ内部パーティションに移さなかったのでしょうか。

理由は、**`Normalized()` がインターフェイスに書かれたインライン関数テンプレートだから**です。

第8章 8.5.5 の表を思い出してください。

| やりたいこと | 定義がどこにあれば良いか |
|---|---|
| インライン展開させたい | **到達可能** |
| テンプレートを実体化したい | **到達可能** |
| `constexpr` でコンパイル時評価したい | **到達可能** |

`main.cpp` が `v.Normalized()` を呼ぶと、その場で `Normalized<float, 3>` が実体化されます。そのとき、中で使っている `kEpsilon<float>` の定義も必要になります。

`kEpsilon` が `:vector`(インターフェイスパーティション)にあれば、`.ifc` を通じて `main.cpp` に届きます。第7章 7.4.3 の表の2行目 ── `export` していなくても到達可能 ── のとおりです。

では内部パーティションに移したら、どうなるでしょうか。

**保証がありません。** 内部パーティションはインターフェイス単位ではないので、`import` した外部の翻訳単位から到達可能になるかどうかは、規格上**規定されていません**。動くコンパイラもあれば、動かないコンパイラもあり得ます。

そこで、次の原則を守ります。

> **内部パーティションに置いてよいのは、実装単位から使うものだけ。**
> **インターフェイスに書いたインライン関数・テンプレート・`constexpr` 関数から、内部パーティションのものを呼んではいけない。**

`MinorAxis` と `SafeAcos` は、`Basis.cpp`(実装単位)からしか呼ばれません。`Basis.cpp` は自分で `import :detail;` しているので、その翻訳単位の中で定義が確実に手に入ります。だから安全です。

`kEpsilon` は `Normalized()`(インターフェイスのインラインテンプレート)から呼ばれます。だから `:vector` に置いたままにします。

この線引きは、慣れるまで見落としがちです。**「誰がそれを呼ぶのか」を確認してから置き場所を決めてください。**

### 10.3.4 `detail` 名前空間はもう要らない

`Detail.ixx` の中身を見返してください。`MinorAxis` と `SafeAcos` は `namespace gamemath` に直接置いています。`namespace gamemath::detail` にはしていません。

ヘッダの時代なら、`detail` 名前空間に入れるのが定石でした。「これは内部用です、触らないでください」という意思表示です。

いまは不要です。第7章 7.2.4 で確認したとおり、`detail` 名前空間は**お願いにすぎませんでした**。呼ぼうと思えば呼べたのです。

内部パーティションに置いたものは、言語仕様として外から見えません。名前で意思表示する必要がありません。

ファイル名が `Detail.ixx` であること、パーティション名が `:detail` であること ── それだけで十分です。

## 10.4 依存関係が循環しないように設計する

パーティションが4つになりました。ここから先、増えるほどに厄介になるのが**依存の向き**です。

### 10.4.1 【実験】循環させてみる

`Detail.ixx` は `:vector` を `import` しています。では、`:vector` から `:detail` を使いたくなったらどうなるでしょうか。

`Vector.ixx` に1行足してみてください。

```cpp
// Vector.ixx
export module gamemath:vector;

import :detail;      // ← 追加(実験)
import std;

// ...
```

ビルドしてください。**エラーになります。** 「循環した依存関係がある」という趣旨のメッセージが出ます。

```
:vector  →  :detail  →  :vector  →  ...
```

コンパイラは `:vector` の `.ifc` を作るために `:detail` の `.ifc` を必要とし、`:detail` の `.ifc` を作るために `:vector` の `.ifc` を必要とします。どちらも先に作れません。

**この行を削除してください。**

### 10.4.2 ヘッダ時代との違い

ヘッダの世界では、循環インクルードは「なんとかなる」ことがありました。前方宣言を使う、インクルードガードに助けられる、`#include` の順序を工夫する ── 汚いながらも回避策がありました。

モジュールでは回避できません。**`.ifc` の生成順序が決まらないからです。**

これは第1章 1.3.3 で「モジュールが持ち込む新しいコスト」として挙げたビルド順序の依存が、設計上の制約として現れたものです。

厳しく見えますが、**循環依存はそもそも設計の失敗です。** モジュールはそれを設計時に強制的に発見させてくれる、と考えるほうが正確でしょう。ヘッダの世界では、循環依存が何年も放置されて絡まっていく現場を、多くの人が見てきたはずです。

### 10.4.3 層で考える

循環を避ける方法は1つしかありません。**依存を一方向にすることです。**

そのために、パーティションを**層**として並べます。

```
上の層(利用する側)
        ↑
        │ import
        ↓
下の層(される側)
```

矢印は一方向だけ。逆向きの矢印を引きたくなったら、設計を見直します。

### 10.4.4 `GameMath` の依存グラフ

現時点の構成を、層として描きます。

```
┌─────────────────────────────────────┐
│  gamemath   (プライマリ)              │  ← 利用者はこれだけを見る
│  export import :vector;              │
│  export import :basis;               │
└─────────────────────────────────────┘
              ↓
┌─────────────────────────────────────┐
│  :basis                             │  BasisPair / MakeBasis /
│  import :vector;                    │  Orthogonal / AngleBetween
└─────────────────────────────────────┘
              ↓
┌─────────────────────────────────────┐
│  :detail   (内部パーティション)        │  MinorAxis / SafeAcos
│  import :vector;                    │
└─────────────────────────────────────┘
              ↓
┌─────────────────────────────────────┐
│  :vector                            │  FloatingPoint / Vector /
│  (何も import しない)                │  演算子 / Dot / Cross / kEpsilon
└─────────────────────────────────────┘
```

いちばん下の `:vector` が、何にも依存しない**土台**です。この上に他が乗ります。

なお、実装単位 `Basis.cpp` はこの図の外にいます。実装単位は誰からも `import` されないので、依存の循環に関与しません。**好きなだけ `import` してよい**のが実装単位の気楽なところです。

第13章以降で層が増えますが、原則は変わりません。

- 土台に近いものほど、他に依存しない
- 内部パーティションは、インターフェイスパーティションに依存してよい
- インターフェイスパーティションが内部パーティションに依存するのは、避ける(10.3.3 の理由もある)

### 10.4.5 循環しそうになったときの3つの対処

設計していると、どうしても双方向に依存したくなる場面が来ます。第13章で `Matrix4x4` と `Quaternion` の相互変換を書くとき、実際にぶつかります。

対処は3つです。

**対処1: 共通部分を下の層に抽出する**

`A` と `B` が互いを必要とするなら、両方が使っている部分を `C` として切り出し、`A → C ← B` にします。

これがいちばん健全な解決です。たいていの場合、循環は「2つの関心事が混ざっている」ことのサインです。

**対処2: 依存の向きを1つに決める**

`Matrix` と `Quaternion` の相互変換で言えば、変換関数を片方だけに置きます。

```cpp
// :matrix に置く
export Matrix4x4 ToMatrix(const Quaternion& q);
export Quaternion ToQuaternion(const Matrix4x4& m);
```

`:matrix` が `:quaternion` を `import` し、`:quaternion` は `:matrix` を知らない ── という一方通行にします。

「どちらに置くべきか」に絶対の答えはありません。**下位の概念に依存させる**、つまり「より基本的なほうを下に置く」のが目安です。

**対処3: 宣言と定義を分ける**

インターフェイスには宣言だけを置き、定義を実装単位に持っていきます。実装単位は依存の循環に関与しないので(10.4.4)、そこで両方を `import` できます。

```cpp
// :matrix(インターフェイス)
export Matrix4x4 ToMatrix(const Quaternion& q);   // 宣言だけ
```

```cpp
// Matrix.cpp(実装単位)
module gamemath;
import :matrix;
import :quaternion;      // 両方 import してよい

Matrix4x4 ToMatrix(const Quaternion& q) { /* ... */ }
```

ただし、この方法には第5章と第8章で扱った代償があります。インライン展開されず、テンプレートにもできません。第14章では、この判断を実際に迫られます。

## 10.5 この章のまとめ

- **内部パーティション**は `module M:P;`(`export` なし)で始まる。`export` を1つも書けない
- Visual Studio では、ファイルのプロパティで**コンパイル言語の選択を `/internalPartition` に変更**する必要がある。忘れるとビルドできない
- 内部パーティションは `.ifc` を生成し、モジュール内のどの単位からでも `import` できる
- 実装単位だけは `.ifc` を生成しないので、`import` できない。**実装で共有したいものは内部パーティションに置く**
- インターフェイスパーティションと違い、**プライマリから `import` する必要はない**。`export import` することは禁じられている
- モジュール単位は4種類。`export` の有無が「インターフェイスか」を、コロンの有無が「パーティションか」を決める
- **内部パーティションに置いてよいのは、実装単位から使うものだけ。** インターフェイスのインライン関数・テンプレート・`constexpr` 関数から呼ぶのは避ける(到達可能性が保証されないため)
- 内部パーティションを使えば、`detail` 名前空間は不要になる
- **パーティションの依存は循環できない。** ヘッダ時代のような回避策はない
- 依存は**層**として一方向に設計する。実装単位は層の外にいるので、循環に関与しない
- 循環しそうになったら ── 共通部分を下の層に抽出する / 依存の向きを1つに決める / 宣言と定義を分ける

## 次章に向けて

この章で、「隠す」ための手段がもう1つ増えました。第7章 7.6 で示した表を更新します。

| 手段 | 名前が見えるか | 情報が届くか | `.ifc` に載るか | 変更で再コンパイル |
|---|---|---|---|---|
| インターフェイスに `export` なしで書く | ✕ | ○ | ○ | される |
| **内部パーティションに書く** | ✕ | モジュール内のみ | 別の `.ifc` | **モジュール内のみ** |
| 実装単位に書く | ✕ | ✕ | ✕ | されない |
| プライベートモジュールフラグメント(**第11章**) | ✕ | ✕ | 一部 | されない |

まだ埋まっていない行が1つあります。

第11章では **プライベートモジュールフラグメント**(`module :private;`)を扱います。これは「1つのファイルの中で、ここから先は実装です」と宣言する仕組みです。インターフェイスと実装を、**ファイルを分けずに**分離できます。

小さなモジュールでは、ファイルを増やすほうが煩わしいことがあります。そういうときの選択肢です。ただし、使いどころが限られる機能でもあるので、「いつ使わないか」も含めて整理します。
