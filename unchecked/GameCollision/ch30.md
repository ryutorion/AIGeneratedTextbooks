# 第 30 章　均一グリッドと空間ハッシュ

> **この章のゴール**
> 空間を格子に切り、同じセルに入った物体どうしだけを判定する。実装は 100 行に満たないのに、n = 10,000 で 50 倍速くなる。
>
> ただし**セルサイズの決め方**と**大きな物体への弱さ**という二つの弱点がある。どちらも「そういう性質がある」で終わらせず、数字で押さえる。そして、`/fp:fast` の下でもグリッドが取りこぼさないことには、きちんと証明できる理由がある。

---

## 30.1 考え方とセルサイズの決め方

### 仕組み

空間を一辺 `c` の正方形（3D なら立方体）に区切る。各物体を、その AABB が重なるすべてのセルに登録する。**同じセルに登録された物体どうしだけ**を候補にする。

物体 A と B の AABB が重なっているなら、重なり領域に含まれるセルには両方が登録される。だから**取りこぼしはない**（30.3 節で厳密に確かめる）。

```cpp
// collision/broadphase/grid_index.h
#pragma once
#include <cmath>
#include <cstdint>
#include "collision/shapes/aabb.h"

namespace collision {

struct CellIndex {
    std::int32_t x{};
    std::int32_t y{};
    [[nodiscard]] friend constexpr bool operator==(CellIndex, CellIndex) noexcept = default;
};

// 座標 → セル番号。min 側と max 側で必ずこの同じ関数を通すこと（30.3 節）
[[nodiscard]] inline CellIndex to_cell(Vec2 p, float inv_cell) noexcept {
    return CellIndex{
        static_cast<std::int32_t>(std::floor(p.x * inv_cell)),
        static_cast<std::int32_t>(std::floor(p.y * inv_cell)),
    };
}

} // namespace collision
```

**セル番号への変換を関数に切り出す**のは、単なる整理ではない。30.3 節で説明するとおり、これが正しさの前提になる。

### セルサイズは何で決まるか

大きすぎても小さすぎても遅くなる。両側から挟むと分かりやすい。

**セルが小さすぎると：** 一つの物体が多くのセルにまたがり、登録の回数が増える。辺の長さ `s` の物体は各軸で約 `s/c + 1` 個のセルを占めるので、2D なら `(s/c + 1)²` 回の登録になる。

**セルが大きすぎると：** 一つのセルに多数の物体が入り、セル内の総当たりが効いてくる。密度 `ρ` なら 1 セルに `ρc²` 個、そのペア数は `(ρc²)²/2` に比例する。

**総コストは `n(s/c + 1)² + n·ρ²c⁴/2` のような形になり、`c` が `s` と同じくらいのところに最小がある。** 実際に測ってみよう。

### 測る

n = 2,000、平均サイズ 1.25、世界は 200×200（密度は一定）。

| セルサイズ | 登録回数 | 候補ペア数 | 使用セル数 |
|---:|---:|---:|---:|
| 0.5 | 24,510 | 2,136 | 22,518 |
| 1.0 | 10,013 | 1,372 | 8,770 |
| 1.25 | 8,072 | 1,387 | 6,845 |
| **2.0** | **5,181** | **1,428** | 3,987 |
| **2.5** | **4,542** | **1,680** | 3,228 |
| 4.0 | 3,420 | 2,290 | 1,884 |
| 8.0 | 2,624 | 5,234 | 646 |
| 16.0 | 2,312 | 15,793 | 191 |
| 32.0 | 2,183 | 55,661 | 63 |

**登録回数は単調に減り、候補ペア数は 1.25 を底に増えていく。** 二つの和が最小になるのは、セルサイズが 2.0〜2.5 のあたりである。

**平均サイズが 1.25 なので、その 1.6〜2 倍**にあたる。これが定番の目安「セルサイズ = 平均物体サイズの 2 倍」の根拠である。

そして表の下の方を見てほしい。セルサイズ 32 では候補ペアが 55,661 にまで膨れている。総当たりの 1,999,000 に比べればまだ 36 分の 1 だが、最適値の 33 倍である。**セルサイズを一桁間違えると、グリッドを入れた意味がほとんどなくなる。**

> **平均か、最大か**
> 「平均サイズの 2 倍」と書いたが、サイズのばらつきが大きいときは平均が役に立たない。大小が混在するなら、**中央値**か、あるいは「よく動く物体のサイズ」を基準に採るほうが実際に合う。
>
> いずれにせよ、**シーンを作ったら 29.4 節のカウンタで候補ペア数を測り、セルサイズを何段階か変えて比べる。** 計算で決めるより速い。

> **なぜ最適値の周りは平らなのか**
> 表の 2.0 と 2.5 と 4.0 は、登録回数と候補ペア数の和で見ると 6,609 / 6,222 / 5,710 とあまり変わらない。**一方 0.5 では 26,646、32.0 では 57,844 と桁が違う。**
>
> これは「セルサイズは大雑把に合っていればよい」という朗報である。物体サイズが 2 倍ばらついていても、それほど困らない。**一桁外さないことだけを気にすればよい。**
>
> なお「登録 1 回」と「候補ペア 1 件」のコストは同じではない。候補ペアは AABB 判定を伴うので数倍高い。重みを付けて評価すると、最適値はもう少し小さいセルサイズ側へ寄る。**厳密な最適値を求めるより、実測で当たりを付けるほうが速い。**

### 実装

```cpp
// collision/broadphase/uniform_grid.h
#pragma once
#include <unordered_map>
#include <vector>
#include "collision/broadphase/grid_index.h"
#include "collision/broadphase/counters.h"

namespace collision {

struct CellHash {
    [[nodiscard]] std::size_t operator()(CellIndex c) const noexcept {
        // 30.3 節で説明する空間ハッシュ関数
        const auto x = static_cast<std::uint32_t>(c.x) * 73856093u;
        const auto y = static_cast<std::uint32_t>(c.y) * 19349663u;
        return static_cast<std::size_t>(x ^ y);
    }
};

class UniformGrid {
public:
    explicit UniformGrid(float cell) noexcept
        : cell_(cell), inv_cell_(1.0f / cell) {}

    void clear() noexcept {
        // バケットは残し、中身だけ空にする（毎フレームの確保を避ける）
        for (auto& [key, list] : cells_) list.clear();
    }

    void insert(std::uint32_t id, const Aabb& box) {
        boxes_.resize(std::max<std::size_t>(boxes_.size(), id + 1));
        boxes_[id] = box;

        const CellIndex lo = to_cell(box.min, inv_cell_);
        const CellIndex hi = to_cell(box.max, inv_cell_);
        for (std::int32_t y = lo.y; y <= hi.y; ++y)
            for (std::int32_t x = lo.x; x <= hi.x; ++x)
                cells_[CellIndex{x, y}].push_back(id);
    }

    BroadphaseCounters collect_pairs(std::vector<Pair>& out) const;

private:
    float cell_{};
    float inv_cell_{};
    std::vector<Aabb> boxes_;
    std::unordered_map<CellIndex, std::vector<std::uint32_t>, CellHash> cells_;
};

} // namespace collision
```

**`clear()` でバケットの `vector` を破棄しない**のが要点である。毎フレーム作り直すと、確保と解放が計測に乗るほど効いてくる。`clear()` は容量を保ったまま要素数をゼロにする。

### 同じペアを二度出さない

一つの問題がある。**A と B が二つのセルを共有していると、ペアが 2 回出てくる。** 実測では候補 2,992 に対して実ペアは 1,141、つまり半分以上が重複だった。

素直な対策は「集めてからソートして `unique`」だが、毎フレームのソートは無視できない。

**もっと安い方法がある。** ペア (A, B) が共有するセルのうち、**「最も小さいセル」でだけ出力する**のである。

```cpp
BroadphaseCounters UniformGrid::collect_pairs(std::vector<Pair>& out) const {
    BroadphaseCounters counters{};
    out.clear();

    for (const auto& [cell, list] : cells_) {
        for (std::size_t a = 0; a < list.size(); ++a) {
            for (std::size_t b = a + 1; b < list.size(); ++b) {
                const std::uint32_t i = list[a];
                const std::uint32_t j = list[b];
                ++counters.aabb_tests;
                if (!intersect(boxes_[i], boxes_[j])) continue;

                // 二つの AABB の重なり領域の「左下の角」が属するセルでだけ出力する。
                // 共有セルは必ずこのセルを含むので、ちょうど 1 回だけ出力される。
                const Vec2 corner{std::max(boxes_[i].min.x, boxes_[j].min.x),
                                  std::max(boxes_[i].min.y, boxes_[j].min.y)};
                if (to_cell(corner, inv_cell_) != cell) continue;

                out.emplace_back(std::min(i, j), std::max(i, j));
                ++counters.candidate_pairs;
            }
        }
    }
    return counters;
}
```

**重なり領域の左下の角は、A と B が共有するセルのうち最も小さいものに属する。** だから「そのセルで処理しているときだけ出力する」ことで、重複がなくなる。ソートも一時集合も要らない。

この方法は 400 ケースのランダム検証で、重複ゼロ・総当たりと集合一致を確認した。

## 30.2 大きな物体・まばらな分布への弱さ

### 巨大な物体が一つ混ざるだけで壊れる

グリッドの最大の弱点である。**世界全体を覆う AABB を持つ物体が一つあると、それだけで全セルに登録される。**

先ほどと同じシーン（n = 2,000、世界 200×200）に、世界全体を覆う物体を 1 個だけ足して測った。

| セルサイズ | 登録回数（大物なし） | 登録回数（大物 1 個） | 増分 |
|---:|---:|---:|---:|
| 1.25 | 8,072 | 33,872 | **+25,800** |
| 2.5 | 4,542 | 11,059 | +6,517 |
| 5.0 | 2,904 | 4,819 | +1,915 |

**セルサイズ 1.25 では、たった 1 個の物体が 25,600 個（160×160）のセルに登録される。** 残り 2,000 個の物体を合わせた登録回数の 3 倍以上である。

しかもその 25,600 セルすべてで、そのセルの全物体とのペア判定が発生する。実質的に総当たりに戻っている。

### 対策

**対策 1：大きすぎる物体を別扱いにする。**

```cpp
// 一定サイズを超える物体は、グリッドに入れずに別のリストへ回す。
// このリストの物体は「全物体と組む」として扱う。
[[nodiscard]] bool is_oversized(const Aabb& b, float cell) noexcept {
    const Vec2 e = b.max - b.min;
    return e.x > cell * 8.0f || e.y > cell * 8.0f;
}
```

大物が `m` 個なら追加コストは O(nm) になる。**`m` が数個なら実用上まったく問題にならない。** 「巨大な物体はそもそも数が少ない」という現実のシーンの性質に乗った対策である。

**対策 2：静的な巨大物体は木に載せる。** 地形や建物は動かないので、第 32 章の BVH に置いて別にクエリする。実際のエンジンではこの構成が多い。

**対策 3：階層グリッド。** セルサイズの異なるグリッドを複数持ち、物体を自分のサイズに合ったレベルへ入れる。柔軟だがレベル間の判定が煩雑になる。本書では扱わない。

**本書は対策 1 を採り、静的地形については第 32.5 節の BVH に譲る。**

### まばらな分布とメモリ

世界が 10 km 四方でセルサイズが 1 m なら、セルは 1 億個ある。配列で持てば 1 セル 8 バイトでも 800 MB である。**そして物体が数千個なら、そのほとんどは空である。**

だから**セルを配列ではなくハッシュ表で持つ**。実際に使われたセルだけがメモリを占める。先ほどの表の「使用セル数」列を見返してほしい。セルサイズ 2.0 のとき、使用セルはわずか 3,987 個だった。

これが次節の空間ハッシュである。

### 3D ではセルサイズの影響が強くなる

セル数は `c` の次元乗で効く。**2D でセルサイズを半分にすると登録が 4 倍、3D では 8 倍**になる。

先ほどの表を 3D で作り直すと、最適なセルサイズは 2D より大きい側へずれる。**「平均サイズの 2 倍」という目安は 2D 向けであり、3D では 2〜3 倍を出発点にするとよい。**

そして大きな物体の害も次元乗で効く。2D で 25,600 セルだったものが、3D では 160³ = 4,096,000 セルになる。**3D では `is_oversized` による分離が、あってもなくてもよい最適化ではなく、必須である。**

### セル内の並び順

もう一つ、測ってみないと気づかない点がある。**セル内の物体リストが、メモリ上でばらばらの `Aabb` を指している**ことである。

```cpp
for (std::size_t a = 0; a < list.size(); ++a)
    for (std::size_t b = a + 1; b < list.size(); ++b)
        if (!intersect(boxes_[list[a]], boxes_[list[b]])) continue;   // ← 間接参照
```

`boxes_[list[a]]` は添字の間接参照であり、キャッシュミスを生みやすい。**AABB そのものをセルのリストに複製して持たせる**設計もある。

```cpp
struct Entry {
    std::uint32_t id{};
    Aabb          box{};      // 複製。間接参照をなくす
};
```

メモリは増えるが、セル内の走査が連続アクセスになる。**どちらが速いかはシーン次第なので、両方書いて測るしかない。** 本書は読みやすさを採って添字版で進めるが、性能が問題になったら真っ先に試す価値がある（第 42 章）。

## 30.3 空間ハッシュによる無限空間への対応

### ハッシュ関数

セル座標 `(x, y, z)` から表の添字を作る。定番は各軸に大きな素数を掛けて排他的論理和を取る形である。

```cpp
[[nodiscard]] constexpr std::uint32_t
spatial_hash(std::int32_t x, std::int32_t y, std::int32_t z) noexcept {
    return  static_cast<std::uint32_t>(x) * 73856093u
          ^ static_cast<std::uint32_t>(y) * 19349663u
          ^ static_cast<std::uint32_t>(z) * 83492791u;
}

// 表の大きさは 2 のべき乗にして、剰余をビットマスクで済ませる
[[nodiscard]] constexpr std::uint32_t
bucket_of(std::uint32_t h, std::uint32_t mask) noexcept { return h & mask; }
```

**符号付き整数の符号なしへの変換は、C++20 以降は 2 の補数として規定されている**ので、負のセル座標も安全に扱える（実装定義ではない）。

表の大きさは**物体数の 2 倍程度、2 のべき乗**にするとよい。小さすぎると衝突が増え、大きすぎるとキャッシュに乗らない。

### ハッシュ衝突をどう扱うか

異なるセルが同じバケツに落ちることがある。二つの設計がある。

**設計 A：バケツにセル座標も保存し、比較する。** 厳密。ただしメモリと比較のコストが増える。

**設計 B：比較しない。異なるセルの物体が混ざるのを許す。**

**設計 B でも結果は正しい。** バケツの中で必ず AABB の重なり判定をするので、無関係な物体はそこで落ちる。増えるのは候補の数だけである。

ただし 30.1 節の「最小セル法」による重複排除は、設計 B では**セル座標が要る**。バケツのキーではなく、登録時のセル座標を要素と一緒に保存する必要がある。

```cpp
struct Entry {
    std::uint32_t id{};
    CellIndex     cell{};   // 重複排除に使う（バケツのキーではない）
};
```

**本書は設計 B ＋ セル座標の保存を採る。** 表の探索が単純な配列添字で済み、しかも重複排除ができる。

### 毎フレームのクリアを避ける

n = 10,000 で表が 16,384 バケツあると、毎フレーム全バケツを `clear()` するだけで無視できない時間になる。

**フレーム番号のスタンプを使う。**

```cpp
struct Bucket {
    std::uint32_t stamp{};            // 最後に使ったフレーム番号
    std::vector<Entry> entries;
};

void SpatialHash::begin_frame() noexcept { ++frame_; }

void SpatialHash::insert_cell(CellIndex c, std::uint32_t id) {
    Bucket& b = buckets_[bucket_of(spatial_hash(c.x, c.y, 0), mask_)];
    if (b.stamp != frame_) { b.entries.clear(); b.stamp = frame_; }  // 遅延クリア
    b.entries.push_back(Entry{id, c});
}
```

**触られたバケツだけがクリアされる。** 使われていないバケツは一度も触らない。走査時も `stamp != frame_` のバケツは飛ばす。

`std::uint32_t` のフレーム番号は 4,294,967,295 フレームで一周する。60 fps で約 2.3 年なので実用上は問題ないが、気になるなら一周時に全バケツの `stamp` をゼロにすればよい。

### `/fp:fast` の下でグリッドは壊れないのか

**ここが本章で最も重要な節である。**

セル番号は `std::floor(p.x * inv_cell)` で計算している。`/fp:fast` では `inv_cell` の値も、掛け算の結果も、`precise` ビルドとは 1 ULP 違うかもしれない。境界ちょうどにいる物体が、隣のセルに入ってしまうかもしれない。

**取りこぼしは起きないのだろうか。**

起きない。理由は単純である。

> **命題。** 座標からセル番号への写像 `f` が**単調非減少**であれば、AABB が重なる二つの物体は必ずセルを共有する。

**証明。** A と B の AABB が軸 x で重なるとは、`A.min ≤ B.max` かつ `B.min ≤ A.max` が成り立つことである。`f` が単調非減少なら、両辺に `f` を適用して不等号は保たれる。

```
f(A.min) ≤ f(B.max)   かつ   f(B.min) ≤ f(A.max)
```

これは整数区間 `[f(A.min), f(A.max)]` と `[f(B.min), f(B.max)]` が重なる条件そのものである。よって共有するセル番号が必ず存在する。∎

**`floor(x * inv_cell)` は、`inv_cell` がどんな値でも（正である限り）`x` について単調非減少である。** 掛け算の誤差がどうであれ、`x` が増えて結果が減ることはない。

だから、`/fp:fast` でも FTZ/DAZ でも、**グリッドは取りこぼさない**。境界にいる物体がどちらのセルに入るかは揺れるが、それは候補が 1 個増えたり減ったりするだけで、最終的な AABB 判定が答えを決める。

**ただし条件が一つある。** `min` 側と `max` 側で**同じ式を使う**ことである。

```cpp
// これは危険：片方が除算、もう片方が逆数の掛け算になっている
const int lo = static_cast<int>(std::floor(box.min.x / cell_));
const int hi = static_cast<int>(std::floor(box.max.x * inv_cell_));
```

`/fp:fast` では `/ cell_` が `* (1/cell_)` に置き換わるとは限らず、二つの式が別々に評価される。同じ座標に対して違う結果が出うる。**単調性は「同一の写像」であることを前提にしている。**

だから 30.1 節で `to_cell` を関数に切り出した。**これは整理のためではなく、正しさの前提を一箇所に固定するためである。**

> **`(int)` キャストと `floor` の違い**
> 「負の座標では `(int)` キャストではなく `std::floor` を使え。さもないと取りこぼす」——よく見る助言である。**しかし前半は正しく、後半は正しくない。**
>
> `(int)` キャストはゼロ方向への切り捨てなので、`-0.5 → 0`、`-1.5 → -1` となる。`floor` なら `-1`、`-2` である。だが `(int)` キャストによる写像もまた**単調非減少**なので、上の命題により**取りこぼしは起きない**。実際に 300 ケースで検証し、集合はどちらも総当たりと一致した。
>
> **本当の問題は性能である。** `(int)` キャストではセル 0 の幅が 2 倍（`-c < x < c`）になる。原点付近に物体が集まるシーンで測ると、候補ペアが 543,401 → 716,841 と **32% 増えた**。
>
> 「取りこぼす」という誤った理由づけでも、結論（`floor` を使う）は正しい。だが**理由が間違っていると、似た場面で判断を誤る。** 単調性という本当の条件を押さえておくほうが、応用が効く。

### グリッドはレイキャストに向かない

もう一つ、実用上重要な性質がある。**グリッドは「全ペアの列挙」は得意だが、「レイに沿った探索」は苦手である。**

レイをグリッドで辿るには、DDA（デジタル微分解析）でセルを順に踏んでいく必要がある。長いレイは多数のセルを踏むので、**セルサイズを大きくしたいという要求が生まれる**——ペア列挙とは逆方向である。

第 33 章のクエリ API は、レイキャストとスイープを主要な機能として持つ。**そこまで見越すと、第 32 章の木のほうが総合力で勝る。** グリッドは「大量の同サイズの物体が均等に散らばる」場面での特化解として捉えるのがよい。

public:
    TEST_METHOD(総当たりと同じペア集合を返すこと) {
        for (std::uint32_t seed = 0; seed < 200; ++seed) {

### 性質：セルサイズに依存しないこと

**結果がセルサイズに依存しないことは、実装が正しいことの強い証拠になる。** セルサイズは性能のパラメータであって、答えを変えてはならない。

```cpp
    TEST_METHOD(セルサイズを変えても同じ集合になること) {
        const auto boxes = make_scene(200, /*seed=*/3100);
        const auto expected = brute_force_pairs(boxes);

        for (const float cell : {0.05f, 0.5f, 1.0f, 3.0f, 17.3f, 1000.0f}) {
            collision::UniformGrid grid(cell);
            for (std::uint32_t i = 0; i < boxes.size(); ++i) grid.insert(i, boxes[i]);
            std::vector<collision::Pair> got;
            grid.collect_pairs(got);
            assert_same_pairs(expected, std::move(got));
        }
    }
```

**`1000.0f` は「セルが 1 個しかない」状況、`0.05f` は「物体が数百セルにまたがる」状況である。** 両極端で同じ答えになれば、セル走査のループ境界はまず正しい。

### 重複が出ないこと

最小セル法が効いているかを直接見る。

    TEST_METHOD(同じペアが二度出ないこと) {

### 効率：候補ペア数が閾値以下

第 29.4 節の方針どおり、時間ではなく仕事量を見る。

```cpp
    TEST_METHOD(候補ペア数が総当たりの二十分の一以下であること) {
        const auto boxes = make_scene(2000, /*seed=*/3400);   // 平均サイズ 1.25
        collision::UniformGrid grid(2.5f);
        for (std::uint32_t i = 0; i < boxes.size(); ++i) grid.insert(i, boxes[i]);

        std::vector<collision::Pair> got;
        const auto counters = grid.collect_pairs(got);

        constexpr std::uint64_t brute = 2000ull * 1999ull / 2ull;
        Assert::IsTrue(counters.aabb_tests * 20 < brute,
            std::format(L"AABB 判定 {} 回（総当たり {} 回）",
                        counters.aabb_tests, brute).c_str());
    }
```

**この値が急に増えたら、セルサイズの設定ミスか、大きな物体の混入を疑う。** 29.4 節で述べたとおり、決定論的な量だから閾値を安心して置ける。

### 退化ケース

```cpp
    TEST_METHOD(退化した入力で壊れないこと) {
        collision::UniformGrid grid(1.0f);

        // 面積ゼロの AABB（点）
        grid.insert(0, collision::Aabb{Vec2{0,0}, Vec2{0,0}});
        grid.insert(1, collision::Aabb{Vec2{0,0}, Vec2{0,0}});

        // セル境界ちょうどに乗る AABB
        grid.insert(2, collision::Aabb{Vec2{1,1}, Vec2{2,2}});
        grid.insert(3, collision::Aabb{Vec2{2,2}, Vec2{3,3}});

        // 負の座標（floor と (int) キャストで結果が変わる領域）
        grid.insert(4, collision::Aabb{Vec2{-0.5f,-0.5f}, Vec2{-0.1f,-0.1f}});
        grid.insert(5, collision::Aabb{Vec2{-0.3f,-0.3f}, Vec2{ 0.3f, 0.3f}});

        std::vector<collision::Pair> got;
        grid.collect_pairs(got);
        // (0,1) 同一点、(2,3) 角で接触、(4,5) 負領域で重なる
        Assert::IsTrue(std::ranges::contains(got, collision::Pair{0, 1}));
        Assert::IsTrue(std::ranges::contains(got, collision::Pair{2, 3}));
        Assert::IsTrue(std::ranges::contains(got, collision::Pair{4, 5}));
    }
};
```

**`(2,3)` は角で接するだけの組である。** 第 10 章の `intersect(Aabb, Aabb)` は接触を重なりと見なすので、これは候補に入る。境界が閉じているのか開いているのかを、テストで明示しておく価値がある。

### 単調性を性質として検査する

30.3 節の命題を、そのままテストにできる。

```cpp
    TEST_METHOD(セル写像が単調非減少であること) {
        constexpr float inv = 1.0f / 2.5f;
        Rng rng(3500);
        for (int i = 0; i < 200000; ++i) {
            const float a = rng.uniform(-1000.0f, 1000.0f);
            const float b = a + rng.uniform(0.0f, 50.0f);   // b >= a
            const auto ca = collision::to_cell(Vec2{a, 0.0f}, inv);
            const auto cb = collision::to_cell(Vec2{b, 0.0f}, inv);
            Assert::IsTrue(ca.x <= cb.x, L"セル写像が単調でありません");
        }
    }
```

**`/fp:fast` の下でも通ることを確認しておくと、30.3 節の議論が現実に成り立っていることの確認になる。** 実装を書き換えたときの安全網にもなる。

## この章のまとめ

- 均一グリッドは**同じセルに登録された物体だけを候補にする**。実装は 100 行に満たない
- **セルサイズ ≒ 平均物体サイズの 2 倍**が目安。実測では最適値の周りは平らだが、一桁外すと台無しになる
- 登録回数と候補ペア数はセルサイズに対して逆向きに動く。**両方をカウンタで測って決める**
- **重複排除は「重なり領域の左下の角が属するセルでだけ出力する」**。ソートも一時集合も不要
- **大きな物体はグリッドの天敵。** 1 個で 25,600 セルに登録されることがある。別リストへ回すか、木に載せる
- まばらな空間には**空間ハッシュ**。素数を掛けて XOR、表は 2 のべき乗
- ハッシュ衝突は許してよい。AABB 判定が最終的に落とす。ただし重複排除にはセル座標が要る
- **フレーム番号のスタンプ**で、触ったバケツだけを遅延クリアする
- **座標 → セルの写像が単調非減少なら、`/fp:fast` でも取りこぼさない。** これは証明できる
- そのために **`min` 側と `max` 側で同じ関数を通す。** これは正しさの前提である
- `(int)` キャストでも集合は正しい。`floor` を使う理由は**性能**（原点付近で候補が 32% 増えた）

### 落とし穴と練習問題

**落とし穴 1：セルサイズを世界の広さから決める。**　決めるべき基準は**物体のサイズ**である。世界の広さは無関係（ハッシュを使えば無限でよい）。

**落とし穴 2：`min` と `max` で違う式を使う。**　`/fp:fast` で結果が食い違い、まれに取りこぼす。`to_cell` を必ず通す。

**落とし穴 3：毎フレーム `unordered_map` を作り直す。**　確保と解放が支配的になる。`clear()` かスタンプで再利用する。

**落とし穴 4：重複ペアをそのままナローフェーズへ流す。**　同じ接触が二重に生成され、第 VII 部の応答で押し出しが 2 倍になる。
