# 第 41 章　デバッグを助ける仕組み

> **この章のゴール**
> テストが落ちた。ログには数字が並んでいる。**そこから「何が起きたのか」を人間が理解するまでが、いちばん時間を食う。**
>
> その時間を削る道具を作る。**形状をテキストへ直列化し、失敗ケースを SVG として吐き出して目で見る。** 描画エンジンは要らない——本書が第 1 章で「描画を本文に登場させない」と決めたことと矛盾しない形で、視覚化は手に入る。
>
> そして `/fp:fast` 特有の三つの問題に道具を用意する。**リプレイはどこまで再現するのか**、**`NaN` はどこで生まれたのか**、**MXCSR は今どうなっているのか。**

## 41.1 形状とシーンをテキストへ直列化する

### なぜテキストなのか

失敗した入力を保存したい。バイナリでもよいが、**テキストには三つの利点がある。**

1. **目で読める。** `circle 0.5 at (1.2, 3.4)` を見れば状況が分かる
2. **手で書ける。** 反例を思いついたら、その場でテストデータにできる
3. **差分が取れる。** 前フレームとの違いを `diff` で見られる

**形状は少数の型しかない**（第 33.1 節の `Shape2`）ので、直列化は短く書ける。

```cpp
// collision/debug/serialize.h
#pragma once
#include <format>
#include <string>
#include "collision/world/shape.h"

namespace collision::debug {

// C++23 の std::formatter を特殊化しておくと、std::format にそのまま渡せる
} // namespace collision::debug

template <>
struct std::formatter<collision::Circle> : std::formatter<std::string> {
    auto format(const collision::Circle& c, auto& ctx) const {
        return std::formatter<std::string>::format(
            std::format("circle r={:.6g}", c.radius), ctx);
    }
};

template <>
struct std::formatter<collision::ConvexPolygon> : std::formatter<std::string> {
    auto format(const collision::ConvexPolygon& p, auto& ctx) const {
        std::string s = "poly";
        for (const Vec2 v : p.vertices())
            s += std::format(" ({:.6g},{:.6g})", v.x, v.y);
        return std::formatter<std::string>::format(s, ctx);
    }
};
```

**`{:.6g}` を使うのが要点である。** `float` の有効桁は約 7 桁なので、6 桁あれば読みやすさと情報量が釣り合う。**完全な往復（round-trip）が必要なら `{:a}`（16 進浮動小数点）を使う。**

```cpp
// ビット単位で復元したいとき
std::format("{:a}", value)     // 0x1.8p+1 のような表記。float の全ビットが保たれる
```

**「読みやすい形式」と「完全に復元できる形式」は両立しない。** 本書は読みやすさを既定にし、往復が要る場面（回帰テストの入力保存）だけ 16 進を使う。

### シーン全体を吐く

```cpp
[[nodiscard]] std::string dump_scene(const World& w) {
    std::string out;
    out += std::format("# frame {}\n", w.frame());
    for (std::uint32_t i = 0; i < w.body_count(); ++i) {
        const RigidBody& b = w.body(i);
        out += std::format("body {} {} pos=({:.6g},{:.6g}) rot={:.6g} "
                           "vel=({:.6g},{:.6g}) w={:.6g}\n",
                           i, to_string(b.type),
                           b.position.x, b.position.y, b.rotation,
                           b.velocity.x, b.velocity.y, b.angular_velocity);
    }
    for (const auto& [key, pair] : w.pairs())
        out += std::format("contact {} {} n=({:.4g},{:.4g}) depth={:.4g}\n",
                           key.first(), key.second(),
                           pair.manifold.normal.x, pair.manifold.normal.y,
                           pair.manifold.points[0].depth);
    return out;
}
```

**接触も一緒に吐く**のが大事である。位置だけ見ても「なぜその位置にいるか」は分からない。**接触の法線と深さが、その理由を語る。**

## 41.2 失敗したテストの入力を SVG として吐き出す

### 描画エンジンなしで図を得る

**SVG はテキストである。** `<circle>` や `<polygon>` を並べたファイルを書き出し、ブラウザで開けばよい。**描画ライブラリも GUI も要らない。**

本書が第 1 章で「描画を本文に登場させない」と決めたのは、**検証を描画に依存させない**ためだった。**SVG は検証手段ではなく、人間が理解するための補助**なので、この方針と矛盾しない。

```cpp
// collision/debug/svg.h
class SvgWriter {
public:
    SvgWriter(float min_x, float min_y, float max_x, float max_y, float margin = 1.0f)
        : min_x_(min_x - margin), min_y_(min_y - margin),
          w_(max_x - min_x + margin * 2), h_(max_y - min_y + margin * 2) {}

    void circle(Vec2 c, float r, std::string_view stroke = "black") {
        // ★ Y 軸を反転する。数学は上が +Y、SVG は下が +Y
        body_ += std::format(
            R"(<circle cx="{:.4g}" cy="{:.4g}" r="{:.4g}" )"
            R"(fill="none" stroke="{}" stroke-width="{:.4g}"/>)" "\n",
            c.x, -c.y, r, stroke, w_ * 0.003f);
    }

    void polygon(std::span<const Vec2> pts, std::string_view stroke = "black") {
        std::string d;
        for (const Vec2 p : pts) d += std::format("{:.4g},{:.4g} ", p.x, -p.y);
        body_ += std::format(
            R"(<polygon points="{}" fill="none" stroke="{}" stroke-width="{:.4g}"/>)" "\n",
            d, stroke, w_ * 0.003f);
    }

    void arrow(Vec2 from, Vec2 to, std::string_view stroke = "red") { /* ... */ }
    void label(Vec2 at, std::string_view text) { /* ... */ }

    [[nodiscard]] std::string str() const {
        return std::format(
            R"(<svg xmlns="http://www.w3.org/2000/svg" viewBox="{:.4g} {:.4g} {:.4g} {:.4g}">)"
            "\n{}</svg>\n",
            min_x_, -min_y_ - h_, w_, h_, body_);
    }

private:
    float min_x_{}, min_y_{}, w_{}, h_{};
    std::string body_;
};
```

**`-c.y` による Y 軸の反転を忘れると、図が上下逆になる。** 一度書いたら二度と触らない場所なので、**この 1 箇所に集約しておく。**

### テストが落ちたときに自動で吐く

```cpp
// tests/svg_on_failure.h
// 落ちたときだけ SVG を書き出す。通ったときは何もしない
class SvgOnFailure {
public:
    explicit SvgOnFailure(std::string name) : name_(std::move(name)) {}
    void succeed() noexcept { ok_ = true; }
    SvgWriter& writer() noexcept { return svg_; }

    ~SvgOnFailure() {
        if (ok_) return;
        const auto path = std::format("{}/{}.svg", failure_dir(), name_);
        std::ofstream(path) << svg_.str();
        Logger::WriteMessage(std::format("失敗ケースを書き出しました: {}\n", path).c_str());
    }

private:
    std::string name_;
    SvgWriter   svg_{-10.0f, -10.0f, 10.0f, 10.0f};
    bool        ok_{false};
};
```

使い方はこうなる。

```cpp
TEST_METHOD(GJK と SAT が一致すること) {
    for (std::uint32_t seed = 0; seed < 30000; ++seed) {
        SvgOnFailure svg(std::format("gjk_vs_sat_{}", seed));

        const auto [a, b] = random_polygons(Rng(seed));
        svg.writer().polygon(a.vertices(), "blue");
        svg.writer().polygon(b.vertices(), "green");

        const bool by_gjk = collision::gjk_intersect(a, b);
        const bool by_sat = collision::sat_intersect(a, b).has_value();
        Assert::AreEqual(by_sat, by_gjk,
            std::format(L"seed = {} で不一致", seed).c_str());

        svg.succeed();   // ここまで来たら書き出さない
    }
}
```

**デストラクタで書き出す**ので、`Assert` が例外を投げても確実に残る。**そして通ったケースは 1 バイトも書かない。** 30,000 回まわしても、失敗した 1 件だけがファイルになる。

> **この道具が最も効いた場面**
> 第 13.1 節で「凸性判定が甘くて、自己交差する星形多角形を受け入れていた」バグを見つけたときである。
>
> 数値だけ見ていたときは「GJK がおかしい」としか思えなかった。**SVG を開いて、入力が星形だと分かった瞬間に原因が確定した。**
>
> 図にしたら 3 秒で分かることに、数字だけで何時間もかけていた。**「目で見る」道具は、早い段階で作るほど元が取れる。**

### 接触を図に描く

**形状だけ描いても、なぜその判定になったのかは分からない。** 法線と接触点を重ねると、一気に読めるようになる。

```cpp
void draw_manifold(SvgWriter& svg, const ContactManifold& m) {
    for (const ContactPoint& p : m.points | std::views::take(m.point_count)) {
        svg.circle(p.position, 0.03f, "red");                    // 接触点
        svg.arrow(p.position, p.position + m.normal * 0.5f, "red");  // 法線
        svg.label(p.position + Vec2{0.05f, 0.05f},
                  std::format("d={:.4g}", p.depth));             // めり込み深さ
    }
}
```

**「法線がどちらを向いているか」は、矢印にすれば一目で分かる。** 第 22 章の符号のバグは、この図があれば数分で見つかっていたはずである。

**そして深さを数値として図に書き込む。** 図だけでは大きさが分からず、数字だけでは位置が分からない。**両方あって初めて理解できる。**

### 前後のフレームを重ねる

「なぜ物体がここへ移動したのか」を調べるには、**移動前と移動後を同じ図に描く。**

```cpp
svg.polygon(shape_at(prev_transform), "gray");    // 前フレーム（薄く）
svg.polygon(shape_at(curr_transform), "black");   // 今フレーム
svg.arrow(prev_transform.position, curr_transform.position, "blue");
```

**第 38.2 節で「鋭角の谷でキャラクタが横に 34 cm 飛ぶ」不具合を見つけたときは、この重ね描きが決め手だった。** 数値の列を見ても「x が増えている」としか分からないが、図にすると**斜面に沿って二度滑った軌跡**がそのまま見える。

### 時系列を 1 枚にする

シナリオテスト（第 33.5 節）の失敗を調べるときは、**全フレームを 1 枚に重ねる**とよい。

```cpp
// 透明度を時間で変える。古いほど薄い
for (std::size_t f = 0; f < history.size(); ++f) {
    const float alpha = 0.15f + 0.85f * static_cast<float>(f) / history.size();
    svg.polygon(history[f], std::format("rgba(0,0,0,{:.2f})", alpha));
}
```

**軌跡が 1 枚の絵になる。** どこで跳ねたか、どこで引っかかったかが、スクロールせずに見える。

## 41.3 リプレイ ― どこまで再現できるのか

### 三段階の再現性

`/fp:fast` を選んだ以上、「どこまで再現するか」を正確に理解しておく必要がある。

| 条件 | 再現するか | 根拠 |
|---|---|---|
| 同じ実行ファイル・同じマシン | **する** | 同じ命令列が同じ CPU で走る |
| 同じ実行ファイル・別のマシン（同じ命令セット） | **おおむねする** | ただし CPU の実装差が残りうる |
| 再ビルドした実行ファイル | **しない** | インライン展開・命令選択が変わる |
| 別のコンパイラ・別のプラットフォーム | **しない** | 演算順序も命令も違う |

**「おおむねする」を保証と呼んではいけない。** `/arch:AVX2` を指定していても、実際に選ばれる命令は CPU によらず同じである。だが**未定義の領域（`NaN` の伝播、非正規化数の扱い）は保証されない**し、MXCSR の状態が違えば結果も違う（第 5 章）。

### 実用上十分な再現性を確保する運用

**「入力の記録 ＋ シード固定」で、日常のデバッグには十分足りる。**

```cpp
// collision/debug/replay.h
struct InputFrame {
    std::uint32_t frame{};
    std::uint32_t rng_seed{};       // そのフレームで使った乱数のシード
    std::vector<Command> commands;  // ゲームロジックからの入力
};

class ReplayRecorder {
public:
    void record(const InputFrame& f) { frames_.push_back(f); }
    void save(const std::filesystem::path& p) const;

    // ★ 実行ファイルの同一性を確認するための指紋
    static std::string build_fingerprint() {
        return std::format("{} {} {} fp={} arch={}",
            __DATE__, __TIME__, COLLISION_VERSION,
            COLLISION_FP_MODEL, COLLISION_ARCH);
    }
private:
    std::vector<InputFrame> frames_;
};
```

**ビルドの指紋をリプレイファイルに埋める**のが要点である。読み込むときに一致しなければ警告する。

```cpp
if (file.fingerprint != ReplayRecorder::build_fingerprint()) {
    std::print("警告：ビルドが異なります。完全な再現は期待できません\n"
               "  記録時: {}\n  現在  : {}\n",
               file.fingerprint, ReplayRecorder::build_fingerprint());
}
```

**「再現しないかもしれない」と明示的に言うことが、この機能の価値の半分である。** 黙って違う結果を出すのが最悪である。

### クロスプラットフォーム決定論が要るなら

**ロックステップ通信対戦や、リプレイの配布が要件なら、`/fp:fast` は使えない。**

これは調整ではなく、**設計の分岐点**である。何を捨てることになるかを整理しておく。

| 手段 | 得られるもの | 捨てるもの |
|---|---|---|
| `/fp:strict` ＋ 命令セット固定 | 同一 ISA なら一致 | **速度（本書比で 2 割前後）**、それでも異なる ISA 間は保証されない |
| ソフトウェア浮動小数点 | 完全な一致 | **速度（一桁）** |
| **固定小数点演算** | 完全な一致 | **本書の実装をほぼ全面的に書き直す**。`sqrt`・除算・範囲の設計をやり直す |

**判断は最初にする。** 43 章分を書いたあとで「実は決定論が要る」と分かると、書き直しになる。

**そして「本当に要るのか」を疑う価値はある。** 対戦がクライアント・サーバ型（サーバが権威を持つ）なら不要である。リプレイも、入力ではなく**結果**（位置の列）を記録すれば配布できる。**要件を変えられるなら、そのほうが安い。**

---

### 再現性そのものをテストする

**「同じ入力なら同じ結果」は、テストで確認できる。**

```cpp
TEST_METHOD(同一プロセス内で結果が再現すること) {
    const auto run = [] {
        auto world = make_scenario_world();
        for (int f = 0; f < 500; ++f) world.step(1.0f / 60.0f);
        return world.snapshot_positions();
    };
    // 同じ実行ファイル・同じプロセスなら厳密に一致する
    expect_near(run(), run(), 0.0f, 0.0f);
}
```

**厳密比較（許容誤差 0）を使う**のが要点である。ここで差が出るなら、**浮動小数点の問題ではなく、未初期化の値かコンテナの走査順序**（第 33.2 節）である。

**このテストは「`/fp:fast` でもここまでは保証される」という線を、コードで示している。** 文書に書くだけでは、いつの間にか崩れる。

### ログの予算

デバッグ用の出力は、**あればあるほどよいわけではない。**

| 粒度 | 量（60 fps） | 実用性 |
|---|---|---|
| 毎フレーム全物体 | 数百 KB/秒 | 数秒ぶんしか追えない |
| **変化があったときだけ** | 数 KB/秒 | **数分追える** |
| イベントのみ | 数百 B/秒 | 長時間追えるが詳細がない |

**「変化があったときだけ」が実用的な既定である。** 41.5 節の MXCSR の監視も、この方針で書いた。

**そしてログを出す判断は、条件式の中でする。**

```cpp
// 悪い：文字列の整形コストが常に発生する
log_verbose(std::format("body {} pos {}", i, b.position));

// 良い：出さないときは整形もしない
if (log_enabled(LogLevel::Verbose))
    log_verbose(std::format("body {} pos {}", i, b.position));
```

**`std::format` は安くない。** 「出力先が無効だから安い」という思い込みは、プロファイラで裏切られる。

## 41.4 `NaN` の発生源を突き止める

### `/fp:fast` では `NaN` が静かに伝播する

第 4.5 節で見たとおり、`/fp:fast` は「`NaN` は来ない」と仮定してよいという前提でコンパイルする。**`std::isnan` や `x != x` が最適化で消えることがある。**

**そして `NaN` は伝播する。** 一つ生まれると、それに触れた値がすべて `NaN` になる。**気づいたときには全物体が消えている。**

### ビットで見る

```cpp
// collision/debug/float_check.h
// 浮動小数点演算を通らないので、/fp:fast の影響を受けない
[[nodiscard]] inline bool is_finite_bits(float x) noexcept {
    const auto bits = std::bit_cast<std::uint32_t>(x);
    return (bits & 0x7F800000u) != 0x7F800000u;   // 指数部が全 1 なら Inf か NaN
}

[[nodiscard]] inline bool is_finite_bits(Vec2 v) noexcept {
    return is_finite_bits(v.x) && is_finite_bits(v.y);
}
```

**`std::bit_cast` は C++20 以降の標準機能で、`constexpr` でも使える。** 共用体や `memcpy` を書く必要はない。

### チェックポイントを仕込む

**「どこで生まれたか」を知るには、パイプラインの節目で検査する。**

```cpp
// デバッグビルドでのみ有効にする。Release では完全に消える
#if defined(COLLISION_DEBUG_NAN)
  #define COLLISION_CHECK_FINITE(expr, label)                                   \
      do { if (!::collision::debug::is_finite_bits(expr))                        \
             ::collision::debug::report_nan(label, std::source_location::current()); \
      } while (false)
#else
  #define COLLISION_CHECK_FINITE(expr, label) ((void)0)
#endif
```

```cpp
void World::step(float dt) {
    COLLISION_CHECK_FINITE(bodies_[0].velocity, "step 開始");
    integrate_velocity(dt);
    COLLISION_CHECK_FINITE(bodies_[0].velocity, "速度の積分後");
    solve_contacts(dt);
    COLLISION_CHECK_FINITE(bodies_[0].velocity, "ソルバ後");
    integrate_position(dt);
    COLLISION_CHECK_FINITE(bodies_[0].position, "位置の積分後");
}
```

**`std::source_location` を使うと、報告にファイル名と行番号が自動で入る。** マクロに `__FILE__` と `__LINE__` を書く必要はない。

**チェックポイントは二分探索の道具である。** 「ソルバ後で `NaN`、速度の積分後は正常」と分かれば、探す範囲が一気に狭まる。

### 本番でも最低限は見る

第 37.5 節の `guard_against_divergence` は Release でも動く。**フレームの終わりに一度だけ全物体を検査し、見つけたらゼロに戻してカウンタを上げる。**

```cpp
// 黙って直さない。カウンタに残す（第 29.4 節の思想）
if (!is_finite_bits(b.velocity)) { ++counters_.nan_resets; b.velocity = Vec2{}; }
```

**`nan_resets` がゼロでないビルドは、原因を調べるまで出荷しない。** 症状は消えているが、バグは残っている。

## 41.5 MXCSR の状態を可視化する

### 「なぜか急に遅い」ときに真っ先に疑う場所

第 5 章で FTZ/DAZ を有効にした。**だが MXCSR はスレッドローカルであり、外部の DLL が書き換えることもある。**

**症状は「特定の場面だけ急に重い」である。** アルゴリズムは変えていないのに、あるレベルに入った瞬間にフレームレートが落ちる。**非正規化数が大量に発生し、FTZ が効いていない。**

### フレーム単位でログに出す

```cpp
// collision/debug/mxcsr.h
struct MxcsrState {
    bool flush_to_zero{};
    bool denormals_are_zero{};
    std::uint32_t raw{};
};

[[nodiscard]] inline MxcsrState read_mxcsr() noexcept {
    const std::uint32_t r = _mm_getcsr();
    return MxcsrState{
        .flush_to_zero      = (r & (1u << 15)) != 0,   // ビット 15
        .denormals_are_zero = (r & (1u <<  6)) != 0,   // ビット 6
        .raw                = r,
    };
}

[[nodiscard]] inline std::string to_string(const MxcsrState& s) {
    return std::format("MXCSR=0x{:04X} FTZ={} DAZ={}",
                       s.raw, s.flush_to_zero ? "on" : "OFF",
                       s.denormals_are_zero ? "on" : "OFF");
}
```

**フレームごとに検査し、変わったときだけログに出す。**

```cpp
void World::check_float_environment() {
    const MxcsrState now = read_mxcsr();
    if (now.raw == last_mxcsr_.raw) return;         // 変化なし。何も出さない

    std::print("フレーム {}: MXCSR が変化しました\n  前: {}\n  今: {}\n",
               frame_, to_string(last_mxcsr_), to_string(now));
    last_mxcsr_ = now;

    if (!now.flush_to_zero || !now.denormals_are_zero) {
        std::print("  ★ FTZ/DAZ が無効になっています。性能低下の原因になります\n");
    }
}
```

**「変わったときだけ出す」のが要点である。** 毎フレーム出すとログが埋まり、誰も見なくなる。

### 非正規化数の発生数を数える

**MXCSR は「非正規化数が起きた」ことを記録している。**

```cpp
// ビット 1 が Denormal Exception Flag。一度立つと明示的に消すまで残る
[[nodiscard]] inline bool denormal_occurred() noexcept {
    return (_mm_getcsr() & (1u << 1)) != 0;
}

inline void clear_denormal_flag() noexcept {
    _mm_setcsr(_mm_getcsr() & ~(1u << 1));
}
```

```cpp
// フレームの先頭でクリアし、末尾で見る
void World::step(float dt) {
    debug::clear_denormal_flag();
    // ... 1 フレームの処理 ...
    if (debug::denormal_occurred()) ++counters_.denormal_frames;
}
```

**`denormal_frames` が増え続けるなら、設計で非正規化数を潰す余地がある**（第 42.3 節）。**FTZ が有効なら性能への影響は小さいが、「起きている」こと自体が設計の綻びを示している。**

### スレッド起動時の設定を強制する

```cpp
// 第 5.6 節で作ったラッパを、テストでも本番でも必ず通す
class FloatEnvironmentGuard {
public:
    FloatEnvironmentGuard() : saved_(_mm_getcsr()) { collision::enable_flush_to_zero(); }
    ~FloatEnvironmentGuard() { _mm_setcsr(saved_); }
    FloatEnvironmentGuard(const FloatEnvironmentGuard&) = delete;
    FloatEnvironmentGuard& operator=(const FloatEnvironmentGuard&) = delete;
private:
    std::uint32_t saved_{};
};
```

**RAII で元に戻す。** ライブラリが呼び出し元の環境を勝手に変えたまま返すのは行儀が悪い（第 43.3 節で契約として整理する）。

### 症状から疑う場所への対応表

第 5 章と本節の内容を、実務的な形にまとめておく。

| 症状 | まず疑う | 確認方法 |
|---|---|---|
| **特定の場面だけ急に重い** | 非正規化数の大量発生 | `denormal_frames` を見る |
| **ジョブスレッドだけ遅い** | MXCSR がスレッドローカル | 各スレッドで `read_mxcsr()` |
| **途中から遅くなった** | 他モジュールが MXCSR を変更 | フレーム毎の変化検出 |
| **FTZ を立てたのに遅いまま** | DAZ が未設定（入力側が非正規化数） | `read_mxcsr().denormals_are_zero` |
| **テストだけ挙動が違う** | テスト側の MXCSR が未設定 | `TEST_MODULE_INITIALIZE` を確認 |
| **物体が予定より早く止まる** | 減衰速度が FTZ でゼロ化 | 明示クランプへ（第 35.5 節） |

**上から三つは、どれも「アルゴリズムは変えていないのに遅い」という同じ症状に見える。** 区別するには MXCSR を見るしかない。**だから可視化する道具が要る。**

## 41.6 アサーションと契約的プログラミング

### 三段階の検査

| 手段 | いつ効くか | 何を検査するか |
|---|---|---|
| `static_assert` | **コンパイル時** | 型・定数の関係（第 5.9 節の閾値の妥当性） |
| `assert` | Debug のみ | 前提条件・不変条件 |
| 実行時の検査 ＋ `std::expected` | 常に | 外部から来る値 |

**判断基準は「誰の責任か」である。**

- **プログラマの責任**（呼び出し方が間違っている）→ `assert`
- **外部の責任**（利用者の入力が不正）→ `std::expected` などで返す

```cpp
// プログラマの責任：正規化されていない法線を渡すのは呼び出し側のバグ
void solve_normal(ContactPoint& c, Vec2 n) noexcept {
    assert(std::fabs(length_squared(n) - 1.0f) < 1.0e-4f && "n は単位長でなければならない");
    // ...
}

// 外部の責任：ユーザが与えた多角形が凸でないことはありうる
[[nodiscard]] std::expected<ConvexPolygon, ShapeError>
make_convex_polygon(std::span<const Vec2> pts) {
    if (pts.size() < 3)      return std::unexpected(ShapeError::too_few_vertices);
    if (!is_convex_ccw(pts)) return std::unexpected(ShapeError::not_convex);
    return build(pts);
}
```

**第 13 章の凸性判定は、後者に置くべきだった。** `assert` にしていたら、Release で自己交差する多角形が黙って通り、GJK が壊れる。

### アサーションのメッセージ

```cpp
// 悪い：何が起きたのか分からない
assert(depth >= 0.0f);

// 良い：値が出る
assert(depth >= 0.0f && "めり込み深さが負");
```

**さらに良いのは、値そのものを出すことである。**

```cpp
#define COLLISION_ASSERT_MSG(cond, ...)                                   \
    do { if (!(cond)) {                                                    \
        std::print(stderr, "アサーション失敗: {}\n  {}\n  {}:{}\n",        \
                   #cond, std::format(__VA_ARGS__),                        \
                   std::source_location::current().file_name(),            \
                   std::source_location::current().line());                \
        std::abort();                                                      \
    } } while (false)

COLLISION_ASSERT_MSG(depth >= 0.0f, "depth = {:.6g}, normal = ({:.4g},{:.4g})",
                     depth, n.x, n.y);
```

**第 3 章で `expect_near` に `diff` を出させ、第 29.4 節で「不足」と「余分」を分けて報告したのと、同じ思想である。**

**落ちたときに次の一手が分かるメッセージを書く。** これは本書全体を通じて繰り返し現れた原則であり、デバッグ機構の設計指針そのものである。

### `/fp:fast` の下でのアサーション

**浮動小数点の等号を `assert` に書いてはいけない。**

```cpp
// 悪い：/fp:fast では成り立たない
assert(length(n) == 1.0f);

// 良い：許容誤差つき。値は第 40.5 節の表から取る
assert(std::fabs(length_squared(n) - 1.0f) < 1.0e-4f);
```

**そして `assert` の条件式が副作用を持ってはいけない。** Release では条件式ごと消えるので、副作用も消える。

## この章のまとめ

- 失敗した入力は**テキストに直列化する**。読める・書ける・差分が取れる
- `{:.6g}` を既定に、**完全な往復が要るときだけ `{:a}`（16 進浮動小数点）**
- 位置だけでなく**接触の法線と深さも吐く。** それが「なぜその位置か」を語る
- **SVG はテキスト。** 描画エンジンなしで図が得られ、「描画に依存しない検証」という方針と両立する
- Y 軸の反転は**1 箇所に集約する**
- **落ちたときだけ SVG を書き出す。** デストラクタで書けば `Assert` の例外でも残る
- 第 13.1 節のバグは、**図にした瞬間に原因が確定した**
- 再現性は三段階。**同一実行ファイル・同一マシンなら再現、再ビルドしたらしない**
- リプレイに**ビルドの指紋を埋める。** 「再現しないかもしれない」と言えることが半分の価値
- クロスプラットフォーム決定論は**設計の分岐点**。最初に決める。要件を疑う価値もある
- `NaN` は**ビットで検査する**（`std::bit_cast` ＋ 指数部が全 1）。`x != x` は消えうる
- チェックポイントは**二分探索の道具**。`std::source_location` で場所が自動で入る
- **本番でも `nan_resets` を数える。** 黙って直したらバグが残る
- MXCSR は**変化したときだけログに出す**。毎フレーム出すと誰も見なくなる
- **非正規化数の発生はビット 1 で数えられる。** FTZ があっても「起きている」ことは設計の綻び
- 環境の変更は **RAII で元に戻す**
- **接触の法線と深さを図に重ねる。** 矢印にすれば符号の間違いが一目で分かる
- 前後のフレームを重ねると軌跡が見える。**第 38.2 節の不具合はこれが決め手だった**
- **再現性そのものをテストする。** 厳密比較で差が出るなら未初期化か走査順序
- ログは**変化があったときだけ**。整形コストは条件式の中で避ける
- アサーションの判断基準は**「誰の責任か」**。プログラマなら `assert`、外部なら `std::expected`
- **落ちたときに次の一手が分かるメッセージを書く**——本書全体を貫く原則

### 落とし穴と練習問題

**落とし穴 1：`float` を `{:.3f}` で吐く。**　有効桁が落ちて、読み込んでも同じケースを再現できない。

**落とし穴 2：SVG の Y 軸反転を各所で書く。**　どこかで忘れて、図だけ上下逆になる。

**落とし穴 3：リプレイに指紋を入れない。**　再現しないことに気づかず、存在しないバグを追う。

**落とし穴 4：`std::isnan` で検出する。**　`/fp:fast` では消えうる。ビットで見る。

**落とし穴 5：`assert` の条件式に副作用を書く。**　Release で挙動が変わる。

**落とし穴 6：外部入力の検証を `assert` で書く。**　Release で検査が消え、不正な形状が通る。

**落とし穴 7：ログを毎フレーム全物体ぶん出す。**　数秒ぶんしか追えず、しかも出力自体が重い。

**落とし穴 8：`std::format` の呼び出しを条件式の外に置く。**　出力しないときも整形コストを払う。

**落とし穴 9：MXCSR の警告を毎フレーム出す。**　ログが埋まり、やがて誰も読まなくなる。一度だけ出す。
