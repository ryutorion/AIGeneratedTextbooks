# 第 6 章　2 次元ベクトル `Vec2` を作る

> **この章のゴール**
> 本書のすべてが乗る土台、`Vec2` を実装する。加減算やスカラー倍といった当たり前の演算に加えて、内積・外積の幾何的な意味を押さえ、正規化を安全に書く。
>
> 地味な章に見えるかもしれない。だが `normalize` という一つの関数の中に、第 0 部で議論したことがほぼすべて現れる。`rsqrt` 近似の精度（第 4 章）、ゼロ長のガード、FTZ で二乗長が潰れる問題、単位系から決めた閾値（第 5 章）。準備が無駄でなかったことが、この章で分かる。

---

## 6.1 構造体の設計方針

### まず最小のものを書く

```cpp
// collision/math/vec2.h
#pragma once

namespace collision {

struct Vec2 {
    float x{};
    float y{};
};

} // namespace collision
```

これだけである。`private` もコンストラクタもない。理由を三つ挙げる。

**集成体（aggregate）であること。** コンストラクタを書かない型は集成体になり、`Vec2 v{1.0f, 2.0f}` という初期化が使える。加えて C++20 以降は指示付き初期化子も使える。

```cpp
Vec2 a{1.0f, 2.0f};
Vec2 b{.x = 1.0f, .y = 2.0f};   // どちらが x か明示できる
Vec2 c{};                        // 両方ゼロ
```

集成体はメモリ上のレイアウトが単純で、`memcpy` で扱え、SIMD レジスタへの読み書きとも相性がよい（第 42 章）。カプセル化の恩恵より、この単純さのほうがずっと価値がある。

**メンバ初期化子 `{}` を付けていること。** `Vec2 v;` と書いたときにゼロ初期化される。未初期化の浮動小数点は、`/fp:fast` 下では特に厄介なバグを生む（第 4 章）。ゼロで初期化されるコストは、この安全性に見合う。

ただし「常にゼロ初期化される」ことに依存したコードは書かないでほしい。大量の `Vec2` を配列で確保するとき、この初期化がコストになる場面がある。そのときは `std::vector::reserve` と `emplace_back` を使う、といった対処になる。

**値渡しすること。** `Vec2` は 8 バイトである。x64 の呼び出し規約では、この大きさなら XMM レジスタに乗る。`const Vec2&` で渡すとポインタ経由になり、かえって遅くなることがある。

```cpp
// 良い
constexpr Vec2 operator+(Vec2 a, Vec2 b) noexcept;

// 良くない（8 バイトの型に参照は過剰）
constexpr Vec2 operator+(const Vec2& a, const Vec2& b) noexcept;
```

本書では、`Vec2` と `Vec3`（12 バイト）は値渡し、それより大きい形状型は `const&` で渡す。境界はおおよそ 16 バイトである。

### 演算はメンバ関数か、自由関数か

本書は**複合代入演算子だけメンバ関数、それ以外は自由関数**とする。

```cpp
struct Vec2 {
    float x{};
    float y{};

    constexpr Vec2& operator+=(Vec2 r) noexcept { x += r.x; y += r.y; return *this; }
    constexpr Vec2& operator-=(Vec2 r) noexcept { x -= r.x; y -= r.y; return *this; }
    constexpr Vec2& operator*=(float s) noexcept { x *= s; y *= s; return *this; }
    constexpr Vec2& operator/=(float s) noexcept { x /= s; y /= s; return *this; }
};
```

複合代入は左辺を書き換えるので、メンバであることに意味がある。一方 `operator+` のような二項演算は、左右対称に扱えるほうが素直である。特にスカラー倍は `2.0f * v` と `v * 2.0f` の両方を書けるようにしたいので、自由関数でなければならない。

## 6.2 演算子オーバーロード

### 実装

```cpp
// collision/math/vec2.h（続き）

// 単項
[[nodiscard]] constexpr Vec2 operator+(Vec2 v) noexcept { return v; }
[[nodiscard]] constexpr Vec2 operator-(Vec2 v) noexcept { return Vec2{-v.x, -v.y}; }

// 二項
[[nodiscard]] constexpr Vec2 operator+(Vec2 a, Vec2 b) noexcept {
    return Vec2{a.x + b.x, a.y + b.y};
}
[[nodiscard]] constexpr Vec2 operator-(Vec2 a, Vec2 b) noexcept {
    return Vec2{a.x - b.x, a.y - b.y};
}

// スカラー倍（両方向）
[[nodiscard]] constexpr Vec2 operator*(Vec2 v, float s) noexcept {
    return Vec2{v.x * s, v.y * s};
}
[[nodiscard]] constexpr Vec2 operator*(float s, Vec2 v) noexcept {
    return v * s;
}
[[nodiscard]] constexpr Vec2 operator/(Vec2 v, float s) noexcept {
    return Vec2{v.x / s, v.y / s};
}
```

`[[nodiscard]]` をすべてに付けている。`a + b;` と書いて結果を捨てるのは、ほぼ確実に書き間違いである。

### 定義しない演算子

**`operator*(Vec2, Vec2)` は定義しない。** ベクトルどうしの `*` が何を意味するかは自明でないからである。内積か、外積か、成分ごとの積か。読み手によって解釈が割れる記号は、使わないほうがよい。内積は `dot(a, b)`、外積は `cross(a, b)` と名前で書く。

ただし成分ごとの積は、AABB のスケーリングなどで実際に必要になる。名前を付けて用意しておく。

```cpp
[[nodiscard]] constexpr Vec2 hadamard(Vec2 a, Vec2 b) noexcept {
    return Vec2{a.x * b.x, a.y * b.y};
}
```

「アダマール積」という正式名があるので、それを使う。`multiply_componentwise` より短く、意味も一意である。

### `/fp:fast` と除算

`operator/` は素直に `x / s` と書いている。`/fp:fast` の下では、コンパイラがこれを `x * (1/s)` に変換してよい。二成分で同じ除数を使うので、逆数を一度計算して二回掛けるほうが速い。**コンパイラに任せてよい**部分である。

自分で `const float inv = 1.0f / s; return Vec2{v.x * inv, v.y * inv};` と書く必要はない。書いても間違いではないが、`/fp:precise` に切り替えたときに意味が変わってしまう（自分で書いた逆数化は残り、精度が落ちたままになる）。**コンパイラオプションで一括して切り替えられる形に保つ**ほうが望ましい。

## 6.3 比較演算子 ― `==` を定義してよいのか

### 既定化された `operator==`

C++20 以降、比較演算子は既定化できる。

```cpp
struct Vec2 {
    float x{};
    float y{};

    [[nodiscard]] friend constexpr bool operator==(Vec2, Vec2) noexcept = default;
};
```

これで `a == b` と `a != b` の両方が使えるようになる（`!=` は `==` から自動的に導出される）。

ここで立ち止まる必要がある。**第 3 章と第 4 章で「浮動小数点に `==` を使ってはいけない」と繰り返し述べた。それなのに `operator==` を定義してよいのか。**

### 使ってよい場面と、いけない場面

答えは「定義はするが、用途を限定する」である。

`operator==` が行うのは**厳密な値の一致**の判定である。これが正しい用途は次のようなものである。

- **番兵値との比較。** `if (v == Vec2{})` のように、意図的にゼロを代入した値を検出する
- **同一性の確認。** 「代入した値がそのまま入っているか」を確かめる
- **コンテナのキー。** `std::unordered_map<Vec2, T>` のように、値そのものを同一視したい場合

一方、**幾何学的な「ほぼ同じ位置」の判定に使ってはいけない**。計算で得られた二つの位置が一致するかを `==` で調べるのは、常に間違いである。そのためには第 3 章の `expect_near` に相当するものを使う。

この区別を型で強制する方法もある（`==` を `delete` して `exactly_equal(a, b)` という名前の関数にする、など）。本書はそこまでしない。名前を長くしても、書きたい人は書いてしまう。**コードレビューとテストで担保するほうが現実的**である。

### `operator<=>` は定義しない

三方比較演算子（宇宙船演算子）も既定化できるが、本書では定義しない。

理由は、**ベクトルに自然な順序が存在しない**からである。`(1, 5)` と `(3, 2)` のどちらが「大きい」かは、決められない。既定化すると辞書式順序（x を比べ、同じなら y を比べる）になるが、これに幾何学的な意味はない。

「意味のない演算子を提供すると、意味があると誤解される」というのが避けたい事態である。ソートしたい場面が出てきたら、その場で比較関数を書けばよい。

```cpp
// 必要な場所で明示的に書く
std::ranges::sort(points, [](Vec2 a, Vec2 b) { return a.x < b.x; });
```

何で並べているかがコードに現れるので、こちらのほうが読みやすい。

## 6.4 長さ、長さの二乗、正規化

この節がこの章の中核である。

### 平方根を避ける

二点間の距離を比べるだけなら、平方根は要らない。

```cpp
[[nodiscard]] constexpr float length_squared(Vec2 v) noexcept {
    return v.x * v.x + v.y * v.y;
}
```

平方根は、加減乗算に比べて明確に遅い命令である。そして**大小関係を比べるだけなら、二乗のままで結論が変わらない**。`a > 0` かつ `b > 0` なら `a > b ⇔ a² > b²` である。

この習慣は本書全体を貫く。「距離が半径より小さいか」ではなく「距離の二乗が半径の二乗より小さいか」と考える。第 8 章の円の判定で、さっそくこの形が出てくる。

数値的な利点もある。平方根を取ると、その時点で丸めが一回入る。二乗のまま比較すれば、その丸めがない。

### 長さ

とはいえ、実際の距離が必要な場面はある。

```cpp
#include <cmath>

[[nodiscard]] inline float length(Vec2 v) noexcept {
    return std::sqrt(length_squared(v));
}
```

`constexpr` が付いていないことに注意してほしい。理由は後述する（6.8 節）。

### 正規化 ― 素朴な実装が壊れる過程

まず素朴に書いてみる。

```cpp
// 危険な実装。このままでは使わない
[[nodiscard]] inline Vec2 normalize_naive(Vec2 v) noexcept {
    return v / length(v);
}
```

`v` がゼロベクトルなら、ゼロ除算で `NaN` が出る。`/fp:fast` の下では `NaN` が静かに伝播し、どこかずっと後で「位置が表示されない」という形で症状が出る。原因の特定は難しい。

では、ガードを入れる。

```cpp
// まだ問題がある実装
[[nodiscard]] inline Vec2 normalize_v2(Vec2 v) noexcept {
    const float len2 = length_squared(v);
    if (len2 > 0.0f) {
        return v / std::sqrt(len2);
    }
    return Vec2{};
}
```

**この `len2 > 0.0f` が、第 5 章で扱った問題を踏む。**

`v` の各成分が `1e-20` 程度のとき、`len2` は `1e-40` になり、非正規化域に落ちる。FTZ が有効なら、これはゼロに潰される。すると `len2 > 0.0f` が偽になり、ゼロベクトルが返る。

一見「安全側に倒れた」ように見えるが、問題は**境界がどこにあるかが単位系と無関係に決まってしまう**ことである。`1.09e-19` という値は、`float` の表現限界と「二乗する」という実装の都合から出てきた数字であって、ゲームの世界の意味とは何の関係もない。

さらに悪いことに、FTZ の設定次第で境界が動く。設定を忘れたスレッド（第 5.5 節）では、非正規化数が保持されるので `len2 > 0.0f` が真になり、除算が行われる。同じコードがスレッドによって違う結果を返す。

### 単位系から閾値を決める

第 5.9 節で決めた定数を使う。

```cpp
// collision/math/vec2.h（続き）
#include "collision/math/scalar.h"
#include <optional>

// 正規化を試みる。向きを持たないと判断した場合は nullopt。
[[nodiscard]] inline std::optional<Vec2> try_normalize(Vec2 v) noexcept {
    const float len2 = length_squared(v);
    if (len2 < min_length2) {       // min_length2 = 1e-8f（第 5 章）
        return std::nullopt;
    }
    return v / std::sqrt(len2);
}
```

閾値を `min_length2 = 1e-8f` に取ると、非正規化域（`1.18e-38`）とは 30 桁離れる。**FTZ が有効でも無効でも、この判定の結果は変わらない。** スレッドごとの設定漏れにも影響されない。

意味も明快である。「長さが 0.1 ミリメートル未満のベクトルは、向きを持たないとみなす」。1 単位 = 1 メートルという単位系から直接読める。

> **`min_length2` と比較する理由**
> `length(v) < min_length` と書いても同じことのように見えるが、そちらは平方根を計算してから比較することになる。`length_squared(v) < min_length2` なら平方根が不要である。`min_length2` を定数として持っておく価値はここにある。

### 呼び出し側で困らないための補助

`std::optional` を返すと、呼び出し側は毎回チェックすることになる。それが正しい場面も多いが、「ゼロなら適当な向きでよい」場面もある。

```cpp
// 正規化できなければ指定した向きを返す
[[nodiscard]] inline Vec2 normalize_or(Vec2 v, Vec2 fallback) noexcept {
    return try_normalize(v).value_or(fallback);
}
```

`std::optional::value_or` を使うと一行で書ける。第 8 章で、中心が一致した円の法線を決めるときにこれを使う。

**`normalize` という名前の、ガードなしの関数は用意しない。** 用意すると必ず使われ、必ず `NaN` の発生源になる。「正規化には常に判断が伴う」ことを、API の形で強制する。

### `rsqrt` 近似の影響を測る

第 4.4 節で、`/fp:fast` の下では `1.0f / std::sqrt(x)` が近似命令に置き換わりうる、と述べた。`try_normalize` の中の `v / std::sqrt(len2)` も、コンパイラの判断で `v * rsqrt(len2)` に変換されうる。

どれくらい精度が落ちるのか。測ってみる。

```cpp
TEST_METHOD(正規化後の長さがどれだけ1に近いか) {
    Rng rng(20260813);
    float worst = 0.0f;

    for (int i = 0; i < 100000; ++i) {
        const Vec2 v{rng.uniform(-1000.0f, 1000.0f), rng.uniform(-1000.0f, 1000.0f)};
        const auto n = collision::try_normalize(v);
        if (!n) continue;

        const float err = std::fabs(1.0f - collision::length(*n));
        worst = std::max(worst, err);
    }

    Logger::WriteMessage(std::format("正規化後の長さの最大誤差 = {:.9g}\n", worst).c_str());
    Assert::IsTrue(worst < 1.0e-5f, L"正規化の精度が想定より悪い");
}
```

`/fp:fast` と `/fp:precise` の両方でこのテストを走らせ、最大誤差を比べてほしい。差が出るなら、それが `rsqrt` 近似のコストである。

**判断の基準はこうである。** 法線の長さが `1 ± 1e-5` の範囲に収まっていれば、コリジョンの用途では十分である。この法線は最終的に「どちらへ何メートル押し戻すか」に使われる。深度が 1 ミリメートル（`1e-3`）のとき、法線の誤差 `1e-5` が生む位置の誤差は `1e-8` メートル、すなわち 10 ナノメートルである。問題にならない。

もし精度が足りないと判断したら、その関数だけ `#pragma float_control(precise, on, push)` で囲む（第 4.6 節）。ただし `try_normalize` は最も呼び出し回数の多い関数の一つなので、**まず測ってから判断する**こと。安易に `precise` にすると、`/fp:fast` を選んだ意味が大きく損なわれる。

## 6.5 内積の幾何的意味

### 定義と三つの読み方

```cpp
[[nodiscard]] constexpr float dot(Vec2 a, Vec2 b) noexcept {
    return a.x * b.x + a.y * b.y;
}
```

式は単純だが、意味は豊かである。本書では次の三つの読み方を使い分ける。

**読み方 1：射影の長さ。** `b` が単位ベクトルのとき、`dot(a, b)` は「`a` を `b` の向きに射影した長さ」である。符号付きなので、逆向きなら負になる。

これが第 11 章の分離軸定理（SAT）の核心になる。形状を軸に投影するとは、各頂点と軸の内積を取ることに他ならない。

**読み方 2：角度の余弦。** `dot(a, b) = |a| |b| cos θ`。両方が単位ベクトルなら、内積はそのまま `cos θ` である。

角度そのものを求めたくなったら `std::acos(dot(a, b))` だが、**逆余弦は避けるべき**である。遅いうえに、引数が 1 をわずかに超えると `NaN` を返す（丸め誤差で普通に起きる）。「角度が 45 度以内か」を判定したいなら、`dot(a, b) > std::cos(std::numbers::pi_v<float> / 4)` のように、**閾値の側を余弦に変換する**。第 38 章で斜面の登坂角を扱うときに、この形が出てくる。

**読み方 3：符号による向きの判定。** `dot(a, b) > 0` なら「おおむね同じ向き」、`< 0` なら「おおむね逆向き」、`≈ 0` なら「直交」。

法線の向きを揃える処理で頻繁に使う。

```cpp
// n が d と逆向きなら反転させる
if (dot(n, d) < 0.0f) {
    n = -n;
}
```

### 距離の二乗を内積で書く

```cpp
[[nodiscard]] constexpr float distance_squared(Vec2 a, Vec2 b) noexcept {
    const Vec2 d = b - a;
    return dot(d, d);
}

[[nodiscard]] inline float distance(Vec2 a, Vec2 b) noexcept {
    return std::sqrt(distance_squared(a, b));
}
```

`length_squared(v)` は `dot(v, v)` と同じである。どちらで書いてもよいが、本書では「長さを問題にしている」文脈では `length_squared`、「内積の計算として自然な」文脈では `dot` を使う。読み手に意図が伝わるほうを選ぶ。

## 6.6 2D の外積 ― 擬似外積

### 3D の外積との関係

外積は本来 3 次元の演算で、二つのベクトルに垂直な third ベクトルを返す。2 次元には「垂直な方向」が平面外にしかないので、そのまま持ち込めない。

代わりに、2D では **Z 成分だけを取り出したスカラー**を使う。3D の外積 `(a.x, a.y, 0) × (b.x, b.y, 0)` を計算すると、結果は `(0, 0, a.x*b.y - a.y*b.x)` になる。この Z 成分がすべての情報を持っている。

```cpp
// 2D の擬似外積（perp dot product）。スカラーを返す
[[nodiscard]] constexpr float cross(Vec2 a, Vec2 b) noexcept {
    return a.x * b.y - a.y * b.x;
}
```

「擬似外積」「perp dot product」「wedge product」などと呼ばれる。本書では単に `cross` と呼ぶ。

### 二つの意味

**意味 1：符号付き面積。** `cross(a, b)` の絶対値は、`a` と `b` が張る平行四辺形の面積である。三角形の面積ならその半分。

```cpp
// 三角形 abc の符号付き面積
[[nodiscard]] constexpr float signed_area(Vec2 a, Vec2 b, Vec2 c) noexcept {
    return 0.5f * cross(b - a, c - a);
}
```

これは第 9.3 節の重心座標、第 13 章の凸性判定で使う。

**意味 2：回転の向き。** 符号が向きを表す。

- `cross(a, b) > 0` … `a` から `b` へは反時計回り（左回り）
- `cross(a, b) < 0` … 時計回り（右回り）
- `cross(a, b) ≈ 0` … 平行または反平行

第 1 章で「2D の回転は反時計回りが正」と決めたので、この符号の解釈は本書全体で一貫する。

点が直線のどちら側にあるかの判定も、これで書ける。

```cpp
// 点 p は、a から b へ向かう直線の左側にあるか
[[nodiscard]] constexpr bool is_left_of(Vec2 p, Vec2 a, Vec2 b) noexcept {
    return cross(b - a, p - a) > 0.0f;
}
```

多角形のクリッピング（第 14 章）で多用する。

### 垂直ベクトル

2D 特有の便利な演算として、90 度回転がある。

```cpp
// 反時計回りに 90 度回転
[[nodiscard]] constexpr Vec2 perpendicular(Vec2 v) noexcept {
    return Vec2{-v.y, v.x};
}
```

`cross(v, perpendicular(v)) = v.x * v.x + v.y * v.y = length_squared(v) > 0` なので、確かに反時計回りである。

辺から法線を作るときに使う。多角形の辺 `b - a` に対して、`perpendicular(b - a)` は法線方向を向く。ただし内向きか外向きかは、多角形の頂点の回り順に依存する。この規約は第 13 章で決める。

> **`cross` と `dot` の関係**
> `cross(a, b) = dot(perpendicular(a), b)` が成り立つ。「perp dot product」という呼び名はここから来ている。片方を 90 度回してから内積を取る、という理解である。
>
> この関係は暗記する必要はないが、知っていると式変形が楽になる。内積についての知識が、そのまま外積にも使える。

## 6.7 `std::print` で出力できるようにする

### `std::formatter` の特殊化

デバッグ中に `Vec2` の値を見たい場面は多い。C++23 の `std::print` でそのまま出せるようにする。

```cpp
// collision/math/vec2.h（続き）
#include <format>

template <>
struct std::formatter<collision::Vec2> : std::formatter<float> {
    template <class FormatContext>
    auto format(const collision::Vec2& v, FormatContext& ctx) const {
        auto out = ctx.out();
        *out++ = '(';
        out = std::formatter<float>::format(v.x, ctx);
        *out++ = ',';
        *out++ = ' ';
        ctx.advance_to(out);
        out = std::formatter<float>::format(v.y, ctx);
        *out++ = ')';
        return out;
    }
};
```

`std::formatter<float>` を継承しているのが要点である。これによって `parse` を自前で書く必要がなくなり、**`float` 用の書式指定子がそのまま使える**。

```cpp
Vec2 v{1.0f / 3.0f, 2.0f / 3.0f};

std::println("{}",      v);   // (0.33333334, 0.6666667)
std::println("{:.3f}",  v);   // (0.333, 0.667)
std::println("{:.9g}",  v);   // (0.333333343, 0.666666687)
```

第 4 章で述べたとおり、誤差を議論するときは `{:.9g}` を使う。`float` の全ビットを復元できる桁数である。

### なぜ `operator<<` ではないのか

伝統的には `std::ostream` の `operator<<` を定義するところである。本書が `std::formatter` を選ぶ理由は三つある。

- **速い。** `std::format` 系は書式文字列をコンパイル時に検査し、ストリームの状態管理を必要としない
- **書式指定が型安全。** `{:.3f}` に整数を渡すとコンパイルエラーになる
- **`std::format` でも使える。** 文字列を組み立てる場面（テストのメッセージなど）でそのまま使える

第 3 章の `expect_near` は `std::format` でメッセージを組み立てていた。`Vec2` 版を書くとき、この特殊化があれば `std::format("expected={} actual={}", e, a)` と書ける。

## 6.8 `constexpr` として使えることを保証する

### `static_assert` で固める

`constexpr` を付けただけでは、本当にコンパイル時に評価できるかは分からない。実際に評価させて確かめる。

```cpp
// collision/math/vec2.h の末尾
namespace collision::detail {

// コンパイル時評価の検証。実行時のコストはゼロ
static_assert(Vec2{1.0f, 2.0f}.x == 1.0f);
static_assert((Vec2{1.0f, 2.0f} + Vec2{3.0f, 4.0f}) == Vec2{4.0f, 6.0f});
static_assert((Vec2{1.0f, 2.0f} * 2.0f) == Vec2{2.0f, 4.0f});
static_assert(dot(Vec2{1.0f, 0.0f}, Vec2{0.0f, 1.0f}) == 0.0f);
static_assert(cross(Vec2{1.0f, 0.0f}, Vec2{0.0f, 1.0f}) == 1.0f);
static_assert(length_squared(Vec2{3.0f, 4.0f}) == 25.0f);
static_assert(perpendicular(Vec2{1.0f, 0.0f}) == Vec2{0.0f, 1.0f});

} // namespace collision::detail
```

ここでは `==` による厳密比較を使っている。「浮動小数点に `==` を使うな」の例外である。理由は、**選んだ値がすべて `float` で正確に表現できるから**である。`1.0f`、`2.0f`、`3.0f`、`4.0f`、`25.0f` はいずれも二進数で正確に表せる。加算も乗算も、結果が正確に表せる範囲に収まっている。誤差が入る余地がない。

`static_assert` にこういう値を選ぶのは意図的である。`0.1f` を使った途端に成立しなくなる。

### `length` が `constexpr` でない理由

`length_squared` は `constexpr` だが、`length` はそうではない。`std::sqrt` が `constexpr` でないからである。

C++23 では、この状況を改善する提案（P0533R9「`<cmath>` と `<cstdlib>` の `constexpr` 化」）が採択されている。これが実装されれば `std::sqrt` はコンパイル時に評価できるようになり、`length` も `constexpr` にできる。

ただし、**本書の執筆時点の MSVC ではまだ利用できない。** この機能は今後のバージョンで実装される見込みである。読者の環境で使えるかどうかは、機能テストマクロで確認できる。

```cpp
#include <version>

#if defined(__cpp_lib_constexpr_cmath) && __cpp_lib_constexpr_cmath >= 202202L
    #define COLLISION_CONSTEXPR_SQRT constexpr
#else
    #define COLLISION_CONSTEXPR_SQRT
#endif

[[nodiscard]] COLLISION_CONSTEXPR_SQRT inline float length(Vec2 v) noexcept {
    return std::sqrt(length_squared(v));
}
```

将来の環境では自動的に `constexpr` になり、現在の環境ではそうならない。第 2 章で述べた「標準のバージョンではなく、機能の有無を問う」という方針の実践例である。

### `if consteval` を使う手もある

もう一つの道がある。C++23 の `if consteval` を使って、**コンパイル時と実行時で実装を切り替える**。

```cpp
namespace collision::detail {

// コンパイル時用の平方根。ニュートン法で十分な精度まで反復する
[[nodiscard]] constexpr float sqrt_ct(float x) noexcept {
    if (x <= 0.0f) return 0.0f;
    float guess = x;
    // float の精度に達するまで。10 回もあれば収束する
    for (int i = 0; i < 20; ++i) {
        const float next = 0.5f * (guess + x / guess);
        if (next == guess) break;
        guess = next;
    }
    return guess;
}

} // namespace collision::detail

[[nodiscard]] constexpr float length(Vec2 v) noexcept {
    const float len2 = length_squared(v);
    if consteval {
        return detail::sqrt_ct(len2);       // コンパイル時：自前実装
    } else {
        return std::sqrt(len2);             // 実行時：ハードウェア命令
    }
}
```

`if consteval` は C++23 の機能で、MSVC でも利用できる。「この関数は今コンパイル時に評価されているか」を問い、分岐する。

**実行時の性能はまったく落ちない。** 実行時には `else` 側しか通らず、`if consteval` 自体もコード生成に影響しない。

ただし注意点がある。**コンパイル時と実行時で結果が違いうる。** `sqrt_ct` のニュートン法と、ハードウェアの `vsqrtss` 命令は、最後の 1〜2 ビットが一致しない可能性がある。しかも実行時は `/fp:fast` の影響を受けるが、コンパイル時の定数評価は受けない（第 42 章で扱う罠である）。

本書ではこの手法を採用しない。`length` をコンパイル時に評価したい場面が実際にはほとんどないためである。ただし、**このパターンを知っておくことには価値がある**。定数テーブルをコンパイル時に生成したい場面などで役に立つ。

## 6.9 テスト

### 代数法則を検証する

具体的な値ではなく、**性質**を検証する（第 3.5 節の原則 2）。

```cpp
// test_vec2.cpp
#include "CppUnitTest.h"
#include "test_helpers.h"
#include "collision/math/vec2.h"

using namespace Microsoft::VisualStudio::CppUnitTestFramework;
using collision::Vec2;

namespace collision_tests {

TEST_CLASS(Vec2Algebra) {
public:
    TEST_METHOD(加算が可換であること) {
        Rng rng(1);
        for (int i = 0; i < 1000; ++i) {
            const Vec2 a{rng.uniform(-100.0f, 100.0f), rng.uniform(-100.0f, 100.0f)};
            const Vec2 b{rng.uniform(-100.0f, 100.0f), rng.uniform(-100.0f, 100.0f)};
            expect_near(a + b, b + a);
        }
    }

    TEST_METHOD(内積が可換であること) {
        Rng rng(2);
        for (int i = 0; i < 1000; ++i) {
            const Vec2 a{rng.uniform(-100.0f, 100.0f), rng.uniform(-100.0f, 100.0f)};
            const Vec2 b{rng.uniform(-100.0f, 100.0f), rng.uniform(-100.0f, 100.0f)};
            expect_near(collision::dot(a, b), collision::dot(b, a));
        }
    }

    TEST_METHOD(外積が反可換であること) {
        Rng rng(3);
        for (int i = 0; i < 1000; ++i) {
            const Vec2 a{rng.uniform(-100.0f, 100.0f), rng.uniform(-100.0f, 100.0f)};
            const Vec2 b{rng.uniform(-100.0f, 100.0f), rng.uniform(-100.0f, 100.0f)};
            expect_near(collision::cross(a, b), -collision::cross(b, a));
        }
    }

    TEST_METHOD(スカラー倍が分配則を満たすこと) {
        Rng rng(4);
        for (int i = 0; i < 1000; ++i) {
            const Vec2 a{rng.uniform(-100.0f, 100.0f), rng.uniform(-100.0f, 100.0f)};
            const Vec2 b{rng.uniform(-100.0f, 100.0f), rng.uniform(-100.0f, 100.0f)};
            const float s = rng.uniform(-10.0f, 10.0f);
            expect_near((a + b) * s, a * s + b * s);
        }
    }
};

} // namespace collision_tests
```

**加算の結合則を検証していない**ことに気づいただろうか。`(a + b) + c` と `a + (b + c)` は、浮動小数点では一致しないことがある（第 4.4 節）。しかも `/fp:fast` の下ではコンパイラが自由に入れ替えてよい。**検証してはいけない性質**である。

「数学的に成り立つ法則」と「浮動小数点で検証してよい法則」は違う。この区別が、`/fp:fast` の下でテストを書くということの実質である。

### `Vec2` 版の `expect_near`

上のテストで `expect_near(Vec2, Vec2)` を使った。第 3.4 節で予告したものを、ここで書く。

```cpp
// test_helpers.h に追加
#include "collision/math/vec2.h"

namespace collision_tests {

inline void expect_near(collision::Vec2 expected, collision::Vec2 actual,
                        float abs_tol = default_abs_tol,
                        float rel_tol = default_rel_tol,
                        std::source_location loc = std::source_location::current()) {
    if (nearly_equal(expected.x, actual.x, abs_tol, rel_tol) &&
        nearly_equal(expected.y, actual.y, abs_tol, rel_tol)) {
        return;
    }
    const auto msg = std::format("expected={:.9g} actual={:.9g} at {}:{}",
                                 expected, actual, loc.file_name(), loc.line());
    Microsoft::VisualStudio::CppUnitTestFramework::Assert::Fail(
        detail::widen(msg).c_str());
}

} // namespace collision_tests
```

`std::format("{:.9g}", expected)` が動くのは、6.7 節で `std::formatter` を特殊化したからである。

**成分ごとに比較している**点について、一言述べておく。ベクトルの差のノルムで比較する流儀もある。

```cpp
// 別案：差のノルムで見る
if (collision::length(expected - actual) < tol) { ... }
```

どちらが良いかは場合による。成分ごとの比較は、片方の成分だけが大きくずれている場合を確実に捕まえる。ノルムでの比較は、方向を問わず「どれだけ離れているか」を素直に表す。

本書は成分ごとを採る。理由は、**失敗したときにどちらの成分が問題かが分かる**からである。デバッグのしやすさを優先した。

### 正規化のテスト

```cpp
TEST_CLASS(Vec2Normalize) {
public:
    TEST_METHOD(正規化したベクトルの長さが1であること) {
        Rng rng(10);
        for (int i = 0; i < 10000; ++i) {
            const Vec2 v{rng.uniform(-1000.0f, 1000.0f), rng.uniform(-1000.0f, 1000.0f)};
            const auto n = collision::try_normalize(v);
            if (!n) continue;
            expect_near(1.0f, collision::length(*n));
        }
    }

    TEST_METHOD(正規化しても向きが変わらないこと) {
        Rng rng(11);
        for (int i = 0; i < 1000; ++i) {
            const Vec2 v{rng.uniform(-100.0f, 100.0f), rng.uniform(-100.0f, 100.0f)};
            const auto n = collision::try_normalize(v);
            if (!n) continue;
            // 元のベクトルと正規化後は平行（外積がゼロ）かつ同じ向き（内積が正）
            expect_near(0.0f, collision::cross(v, *n), 1.0e-4f, 1.0e-4f);
            Assert::IsTrue(collision::dot(v, *n) > 0.0f, L"向きが反転している");
        }
    }

    TEST_METHOD(ゼロベクトルの正規化がnulloptを返すこと) {
        Assert::IsFalse(collision::try_normalize(Vec2{}).has_value());
        Assert::IsFalse(collision::try_normalize(Vec2{0.0f, 0.0f}).has_value());
    }

    TEST_METHOD(閾値未満の極小ベクトルがnulloptを返すこと) {
        // min_length = 1e-4 なので、長さ 1e-5 のベクトルは向きを持たない扱い
        Assert::IsFalse(collision::try_normalize(Vec2{1.0e-5f, 0.0f}).has_value());
        // 長さ 1e-3 なら正規化される
        Assert::IsTrue(collision::try_normalize(Vec2{1.0e-3f, 0.0f}).has_value());
    }

    TEST_METHOD(非正規化数を含む入力でも破綻しないこと) {
        // 第 5 章の議論の実証。FTZ の有無にかかわらず nullopt になるべき
        const Vec2 tiny{1.0e-30f, 1.0e-30f};
        Assert::IsFalse(collision::try_normalize(tiny).has_value());

        // 結果に NaN が混入していないことも確認
        const Vec2 fallback = collision::normalize_or(tiny, Vec2{1.0f, 0.0f});
        Assert::IsTrue(collision::is_finite_bits(fallback.x));
        Assert::IsTrue(collision::is_finite_bits(fallback.y));
    }
};
```

「外積がゼロ」の検証で許容誤差を `1e-4f` と大きく取っている。`v` の長さが最大 140 程度あるので、`cross(v, n)` の値も相応のスケールになり、既定の `1e-6f` では厳しすぎるためである。**許容誤差は、比較する量のスケールに応じて調整する**（第 4.3 節）。

最後のテストが、この章と第 5 章をつなぐ要である。`1e-30` という値そのものは正規化数だが、二乗すると `1e-60` になり、非正規化域どころか完全にアンダーフローしてゼロになる。それでも `try_normalize` は `min_length2` で先に弾くので、`NaN` は出ない。**閾値を単位系から決めておけば、`float` の表現限界を意識せずに済む。**

## この章のまとめ

- `Vec2` は集成体。コンストラクタを書かず、メンバ初期化子でゼロ初期化する。値渡しする
- `operator*(Vec2, Vec2)` は定義しない。内積は `dot`、外積は `cross`、成分積は `hadamard`
- `operator==` は定義するが、番兵値の比較と同一性の確認にのみ使う。幾何学的な一致判定には使わない
- `operator<=>` は定義しない。ベクトルに自然な順序はない
- 平方根は避ける。比較は `length_squared` で行う
- **正規化には常に判断が伴う。** `try_normalize` は `std::optional` を返す。ガードなしの `normalize` は用意しない
- 正規化の閾値は `min_length2`（単位系から決めた値）で判定する。二乗長をゼロと比べてはいけない
- 内積は「射影・角度・向き」の三つの読み方。2D の外積はスカラーで「面積と回転の向き」
- `std::formatter` を特殊化して `std::print` / `std::format` に対応させる
- 検証してよい代数法則と、してはいけない法則（結合則）を区別する

### 落とし穴と練習問題

**落とし穴 1：`length_squared(v) > 0.0f` というガード。**　この章で最も強調した点である。FTZ の有無で挙動が変わる。必ず `min_length2` と比較する。

**落とし穴 2：`std::acos` で角度を求める。**　遅いうえに、引数が丸め誤差で 1 を超えると `NaN` になる。閾値の側を余弦に変換する。

**落とし穴 3：`static_assert` に `0.1f` のような値を使う。**　厳密比較なので、正確に表現できる値だけを使う。
