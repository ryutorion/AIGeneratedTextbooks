# 第 5 章　非正規化数と FTZ/DAZ ― 見えない速度低下を潰す

> **この章のゴール**
> 非正規化数とは何かを理解し、それが引き起こす速度低下を自分の環境で実測する。FTZ と DAZ という二つのスイッチを正しく理解して有効にし、その副作用を把握する。そのうえで「この世界で意味のある最小の長さ」を決め、以降の章で使う閾値の根拠を確立する。
>
> 前章の主題は**精度**だった。この章の主題は**速度**である。しかも対処はコンパイラオプションではなく、実行時の CPU の状態設定になる。この違いが、この章を独立させた理由である。

---

## 5.1 非正規化数（subnormal）とは何か

### `float` の表現の下限

前章で見たとおり、`float` は符号 1 ビット、指数 8 ビット、仮数 23 ビットで構成される。値は概念的にこう表される。

```
value = (-1)^符号 × 1.仮数 × 2^(指数 - 127)
```

仮数の前に暗黙の `1.` が付いている点に注目してほしい。この「隠れた 1」があるおかげで、仮数 23 ビットで 24 ビット分の精度が得られる。うまい設計である。

問題は下限である。指数部が取りうる最小値（特殊な扱いを除く）は `2^-126` なので、この形式で表せる最小の正の値は `1.0 × 2^-126` ≒ `1.18e-38` になる。

では、それより小さい値はどうなるのか。単純にゼロへ落とす、という設計もありえた。しかし IEEE 754 はそうしなかった。

### 緩やかなアンダーフロー

指数部のビットがすべてゼロのとき、**隠れた 1 を外して `0.仮数` として解釈する**という特別ルールが用意されている。これによって表現される値が **非正規化数**（subnormal number、あるいは denormal number）である。

```
value = (-1)^符号 × 0.仮数 × 2^-126
```

隠れた 1 がない分、有効桁数は減る。仮数が小さくなるほど精度は落ち、最終的に `2^-149` ≒ `1.4e-45` で完全にゼロになる。

つまり `float` の正の値の並びは、こうなっている。

```
0 ─── 非正規化数の領域 ─── 1.18e-38 ─── 正規化数の領域 ─── 3.4e38 ─── Inf
      (精度が徐々に落ちる)              (相対精度 1.2e-7 で一定)
```

急にゼロになるのではなく、精度を落としながら緩やかにゼロへ近づく。これを **緩やかなアンダーフロー**（gradual underflow）と呼ぶ。

### ビットで確かめる

言葉より、実際のビットを見るほうが早い。

```cpp
#include <bit>
#include <print>
#include <cstdint>

void dump(float x, const char* label) {
    const auto b = std::bit_cast<std::uint32_t>(x);
    std::println("{:<24} {:.9g}  bits={:08X}  exp={:3}  frac={:06X}  subnormal={}",
                 label, x, b,
                 (b >> 23) & 0xFF,      // 指数部
                 b & 0x7FFFFF,          // 仮数部
                 ((b >> 23) & 0xFF) == 0 && (b & 0x7FFFFF) != 0);
}

int main() {
    dump(1.0f,      "1.0");
    dump(1.18e-38f, "最小の正規化数付近");
    dump(1.0e-40f,  "非正規化数");
    dump(1.4e-45f,  "最小の非正規化数");
    dump(0.0f,      "ゼロ");
}
```

`1.0e-40f` の行を見ると、指数部が `0` になり、仮数部にだけ値が入っていることが分かる。これが非正規化数である。

標準ライブラリにも判定関数がある。

```cpp
std::fpclassify(x) == FP_SUBNORMAL     // 非正規化数か
std::isnormal(x)                       // 正規化数か（ゼロ・非正規化数・NaN・Inf は false）
```

ただし前章で見たとおり、`/fp:fast` の下ではこれらの関数も最適化の影響を受けうる。確実を期すならビットを直接見る。この章で使う判定関数を用意しておこう。

```cpp
// collision/math/fp_bits.h に追加
[[nodiscard]] inline bool is_subnormal_bits(float x) noexcept {
    const auto b = std::bit_cast<std::uint32_t>(x);
    return ((b & 0x7F800000u) == 0u) && ((b & 0x007FFFFFu) != 0u);
}
```

### なぜこの設計になっているのか

非正規化数を用意した理由は、次の性質を守るためである。

**`x - y == 0` ならば `x == y`。**

これは当たり前に見えるが、非正規化数がなければ成り立たない。`x` と `y` が異なる値でも、その差が最小の正規化数より小さければ、差はゼロに丸められてしまう。すると「差がゼロなのに等しくない」という状態が生まれる。

この性質は、数値計算のコードで暗黙のうちに使われていることが多い。

```cpp
if (a - b != 0.0f) {
    result = 1.0f / (a - b);     // ゼロ除算は起きないはず
}
```

このコードは、非正規化数があれば安全である。ないと、`a - b` がゼロに丸められた後で割り算に到達する経路が生まれる。

**この節は伏線である。** 本章でこれから FTZ/DAZ を有効にすると、この性質は失われる。5.8 節でその意味を扱う。

## 5.2 なぜ遅いのか ― まず実測する

### ハードウェアの事情

非正規化数の演算は、多くの x86 実装で正規化数より大幅に遅い。

理由は実装の都合である。演算器は「隠れた 1 がある」正規化数を前提に最適化されている。非正規化数はその前提を外れるため、専用の処理が必要になる。多くの実装では、この処理をハードウェアの高速経路ではなく**マイクロコードによる補助処理**（アシスト）で行う。この切り替えのコストが大きい。

どれくらい遅いかは CPU の世代とベンダによって大きく違う。数倍で済むこともあれば、数十倍になることもある。新しい世代では改善されている部分もある。

したがって、**信頼できるのは自分の環境での実測だけである。** 一般論を読んで納得するのではなく、測ってほしい。

### 測るコードを書く

同じ計算を、正規化数の範囲と非正規化数の範囲でそれぞれ行い、時間を比べる。

```cpp
// test_denormal_bench.cpp
#include "CppUnitTest.h"
#include "test_helpers.h"
#include <chrono>
#include <vector>
#include <print>

using namespace Microsoft::VisualStudio::CppUnitTestFramework;

namespace collision_tests {

namespace {

// 減衰させ続けるループ。scale の値で、途中から非正規化域に入るかどうかが決まる
__declspec(noinline) float decay_loop(float initial, int iterations) {
    float acc = 0.0f;
    float v = initial;
    for (int i = 0; i < iterations; ++i) {
        v *= 0.5f;
        acc += v;
        if (v == 0.0f) v = initial;   // 完全にゼロになったら戻す
    }
    return acc;
}

template <class F>
double measure_ms(F&& f) {
    const auto t0 = std::chrono::steady_clock::now();
    f();
    const auto t1 = std::chrono::steady_clock::now();
    return std::chrono::duration<double, std::milli>(t1 - t0).count();
}

} // namespace

TEST_CLASS(DenormalBenchmark) {
public:
    TEST_METHOD(非正規化数を含む計算の速度を測る) {
        constexpr int N = 20'000'000;
        volatile float sink = 0.0f;

        // (1) 正規化数の範囲だけを通る
        const double normal_ms = measure_ms([&] {
            sink = decay_loop(1.0f, N);
        });

        // (2) 非正規化域を通り続ける
        const double subnormal_ms = measure_ms([&] {
            sink = decay_loop(1.0e-38f, N);
        });

        Logger::WriteMessage(std::format(
            "正規化数のみ  : {:8.1f} ms\n"
            "非正規化数あり: {:8.1f} ms\n"
            "比率          : {:8.2f} 倍\n",
            normal_ms, subnormal_ms, subnormal_ms / normal_ms).c_str());
    }
};

} // namespace collision_tests
```

いくつか工夫がある。

**`volatile float sink`。** 結果を捨てるとループごと最適化で消える。`volatile` な変数に書き込むことで、計算が実際に行われることを保証する。

**`__declspec(noinline)`。** インライン展開されると、呼び出しごとの最適化の差でベンチマークの条件が揃わなくなる。

**`decay_loop` の中身。** `v *= 0.5f` を繰り返すと、`v` は指数関数的に小さくなる。`initial` を `1.0f` にすると 20,000,000 回のうち大半は正規化数の範囲を通る（126 回で下限に達するので実際にはすぐ抜けるが、`v == 0` で戻すため周期的に繰り返す）。`1.0e-38f` から始めると、ごく数回で非正規化域に入り、そこに長く留まる。

**Release 構成で実行すること。** Debug では最適化されないので、演算以外のオーバーヘッドが支配的になり、差が埋もれる。

### 何が見えるか

テストエクスプローラーの出力ウィンドウに、二つの時間と比率が表示される。環境によるが、はっきりした差が出るはずである。

この差が意味することは重い。**同じコードが、入力の値によって数倍〜数十倍遅くなる。** しかも入力が特定の範囲に入ったときだけである。

これがゲームで問題になる典型的な形はこうである。オブジェクトが減速して静止に近づく。速度の値がじりじり小さくなり、あるとき非正規化域に入る。その瞬間から、物理演算のコストが跳ね上がる。プロファイラで見ると「同じ関数が、特定の場面でだけ重い」という不可解な結果になる。

**平均フレーム時間ではなく最悪値を見る**べき理由がここにある。平均では埋もれるが、実際にはその場面だけカクつく。

### 発生源を捕まえる

「非正規化数が発生しているか」を調べる方法もある。浮動小数点のアンダーフロー例外を一時的に有効にすると、非正規化数が生成された時点で例外が飛ぶ。

ただしこの手法は扱いが難しい。第 4 章で見たとおり、例外の意味論を有効にするには `precise` が必要で、プラグマの順序にも制約がある。加えて、標準ライブラリの内部でも非正規化数が生じることがあり、自分のコード以外で引っかかる。

より実用的な方法は、疑わしい箇所にチェックを仕込むことである。

```cpp
// デバッグビルドでのみ有効にするカウンタ
#ifdef _DEBUG
inline std::atomic<std::uint64_t> g_subnormal_count{0};
inline void check_subnormal(float x) noexcept {
    if (is_subnormal_bits(x)) g_subnormal_count.fetch_add(1, std::memory_order_relaxed);
}
#else
inline void check_subnormal(float) noexcept {}
#endif
```

第 41 章で、これをフレーム単位のデバッグ表示に組み込む。

## 5.3 FTZ と DAZ は別物

### 二つのスイッチ

非正規化数による速度低下を避ける方法は、**非正規化数を扱わないこと**である。具体的には、非正規化数が現れたらゼロに潰す。

x64 の SSE では、これを二つの独立したスイッチで制御する。**この二つが別物であることが、この節の最重要事項である。**

| スイッチ | 正式名 | 何をするか | MXCSR |
|---|---|---|---|
| **FTZ** | Flush To Zero | 演算の**結果**が非正規化数になったら、ゼロにする | ビット 15 |
| **DAZ** | Denormals Are Zero | 演算の**入力**が非正規化数だったら、ゼロとみなす | ビット 6 |

MXCSR は SSE の制御・状態レジスタで、丸めモードや例外マスクもここに入っている。

### なぜ両方必要なのか

FTZ だけを有効にした場合を考えてみよう。「演算の結果が非正規化数ならゼロにする」ので、計算の中で新たに非正規化数が生まれることはなくなる。

ところが、**外から入ってくる非正規化数**は防げない。

- ファイルやネットワークから読み込んだデータに非正規化数が含まれていた
- 別のモジュール（FTZ が有効でないコードでコンパイルされた DLL など）が計算した値
- FTZ を有効にする前にメモリへ書き込まれていた値

これらが入力として演算器に渡ると、非正規化数の処理が発生する。DAZ は、入力の段階でこれをゼロとみなすことでその経路を塞ぐ。

逆に DAZ だけでも不十分である。入力が正規化数どうしでも、結果が非正規化域に落ちることはある（`1e-20f * 1e-20f` など）。それを潰すのが FTZ である。

**片方だけでは取りこぼす。必ず両方を立てる。**

### 現在の状態を覗く

まず、自分のプログラムが今どういう状態にあるかを確認できるようにする。

```cpp
// collision/math/fp_control.h
#pragma once

#include <xmmintrin.h>   // _mm_getcsr, _MM_SET_FLUSH_ZERO_MODE
#include <pmmintrin.h>   // _MM_SET_DENORMALS_ZERO_MODE (SSE3)
#include <cstdint>

namespace collision {

struct FpuState {
    bool flush_to_zero;      // FTZ
    bool denormals_are_zero; // DAZ
    std::uint32_t raw;       // MXCSR の生の値
};

[[nodiscard]] inline FpuState get_fpu_state() noexcept {
    const std::uint32_t csr = _mm_getcsr();
    return FpuState{
        .flush_to_zero      = (csr & _MM_FLUSH_ZERO_MASK)      == _MM_FLUSH_ZERO_ON,
        .denormals_are_zero = (csr & _MM_DENORMALS_ZERO_MASK)  == _MM_DENORMALS_ZERO_ON,
        .raw                = csr,
    };
}

} // namespace collision
```

C++20 の指示付き初期化子（designated initializer）を使っている。フィールド名が明示されるので、`bool` が二つ並んでいても取り違えない。

これをテストから呼んで表示してみる。

```cpp
TEST_METHOD(現在のFPU状態を表示する) {
    const auto s = collision::get_fpu_state();
    Logger::WriteMessage(std::format(
        "MXCSR = 0x{:08X}  FTZ={}  DAZ={}\n",
        s.raw, s.flush_to_zero, s.denormals_are_zero).c_str());
}
```

**この時点では、おそらく両方とも `false` と表示されるはずである。**

ここが重要な発見になる。第 2 章で `/fp:fast` を設定したにもかかわらず、実行時の MXCSR は既定の状態のままである、ということが確認できる。次節でこれを設定する。

## 5.4 有効化する

### 二通りの方法

FTZ/DAZ を有効にする方法は、大きく二つある。

**方法 1：SSE の組み込み関数を使う。**　FTZ と DAZ を個別に制御できる。

```cpp
// collision/math/fp_control.h（続き）
namespace collision {

inline void enable_flush_denormals() noexcept {
    _MM_SET_FLUSH_ZERO_MODE(_MM_FLUSH_ZERO_ON);
    _MM_SET_DENORMALS_ZERO_MODE(_MM_DENORMALS_ZERO_ON);
}

inline void disable_flush_denormals() noexcept {
    _MM_SET_FLUSH_ZERO_MODE(_MM_FLUSH_ZERO_OFF);
    _MM_SET_DENORMALS_ZERO_MODE(_MM_DENORMALS_ZERO_OFF);
}

} // namespace collision
```

これらのマクロは MXCSR の該当ビットを読み書きするだけの、ごく薄いラッパである。

**方法 2：CRT の `_controlfp_s` を使う。**　より移植性のある書き方である。

```cpp
#include <cfloat>

unsigned int current = 0;
_controlfp_s(&current, _DN_FLUSH, _MCW_DN);
```

`_MCW_DN` は「非正規化数の制御」を表すマスク、`_DN_FLUSH` は「ゼロへ潰す」を表す値である。ドキュメントによれば、x64 では MXCSR の制御語だけが影響を受ける（x86 では x87 と SSE2 の両方が対象になる）。ARM プラットフォームでも同様に機能する。

二つの方法の違いは、**粒度**である。`_controlfp_s` は「非正規化数を潰すかどうか」という一つの設定として扱い、FTZ と DAZ を分けない。組み込み関数なら個別に制御できる。

本書では**組み込み関数のほう**を使う。FTZ と DAZ が別物であることを意識し続けたいのと、片方だけ有効にして挙動を比べるテスト（5.10 節）を書きたいためである。

### `/fp:fast` を付けただけでは足りない

前節で確認したとおり、`/fp:fast` を指定してもプログラム開始時点の MXCSR は既定のままである可能性が高い。第 2 章で述べたことを、ここで改めて強調しておく。

**`/fp:fast` はコンパイル時のスイッチであり、実行時の CPU の状態を設定するものではない。**

コンパイラは「非正規化数を無視した最適化をしてよい」と考えてコードを生成するかもしれないが、実際に CPU が非正規化数をゼロに潰すかどうかは、MXCSR の状態次第である。この二つは独立している。

読者の環境で `/fp:fast` が自動的に FTZ/DAZ を設定していたとしても、**それに依存すべきではない**。コンパイラのバージョンやリンクの構成によって変わりうる暗黙の挙動に頼るより、明示的に設定して明示的に検証するほうが確実である。

### 効いていることを検証する

設定したら、必ず効果を確認する。

```cpp
[[nodiscard]] inline bool verify_denormals_flushed() noexcept {
    // 最適化で畳み込まれないよう volatile を経由
    volatile float tiny = 1.0e-38f;
    volatile float half = 0.5f;
    const float result = tiny * half;   // 非正規化域に落ちる計算

    return result == 0.0f;   // FTZ が効いていればゼロ
}
```

`1.0e-38f` は正規化数の下限付近である。これを半分にすると非正規化域に入る。FTZ が有効ならゼロになる。

`volatile` を挟んでいるのは、コンパイル時に定数畳み込みされるのを防ぐためである。定数畳み込みは**コンパイル時**に行われるので、実行時の MXCSR とは無関係に計算されてしまう。この落とし穴は第 42 章の `constexpr` の話とも通じる。

### DAZ の可用性

DAZ は SSE2 以降の機能で、CPUID で対応を確認できる。ただし、現代の x64 プロセッサで DAZ に対応していないものは事実上存在しない。`pmmintrin.h`（SSE3）をインクルードできる環境であれば、まず問題にならない。

厳密を期すなら、`_mm_getcsr` で読んだ値に対して設定を書き込み、読み戻して反映されているかを確かめればよい。上の `verify_denormals_flushed` は、結果として同じことを検証している（より直接的に）。

## 5.5 MXCSR はスレッドごと ― 最大の落とし穴

### スレッドローカルな状態である

**MXCSR はスレッドごとの状態である。** これがこの章で最も見落とされやすい事実である。

OS がスレッドを切り替えるとき、MXCSR はスレッドのコンテキストの一部として保存・復元される。つまり、あるスレッドで FTZ/DAZ を有効にしても、**他のスレッドには一切影響しない**。

これが引き起こす症状は独特である。

- メインスレッドで初期化時に設定した → メインスレッドの処理は速い
- ワーカスレッドでは設定されていない → 並列化した物理演算だけが遅い
- プロファイラで見ると、同じ関数がスレッドによって性能が違う

「並列化したのに期待ほど速くならない」の原因がこれ、ということが実際にある。スレッド数を増やすほど、設定されていないスレッドの割合が増えるので、症状は悪化する。

### 設定漏れを構造的に防ぐ

「新しいスレッドを作ったら FTZ/DAZ を設定する」というルールを人間の注意力で守るのは無理がある。仕組みで防ぐ。

**スレッドの起動を一箇所のラッパに集約する。**

```cpp
// collision/math/fp_control.h（続き）
#include <thread>
#include <utility>

namespace collision {

// このライブラリの前提（FTZ/DAZ 有効）を満たすスレッドを起動する。
// 生の std::jthread を直接使わず、必ずこれを通す規約とする。
template <class F>
[[nodiscard]] std::jthread spawn_thread(F f) {
    return std::jthread([fn = std::move(f)]() mutable {
        enable_flush_denormals();   // ここで必ず設定される
        fn();
    });
}

} // namespace collision
```

引数を取らない呼び出し可能物だけを受ける形にしてある。引数を渡したければ、呼び出し側でラムダに捕捉させればよい。可変長引数の完全転送に対応させることもできるが、この程度の用途では簡潔さを優先する。

```cpp
auto worker = collision::spawn_thread([&world, dt] {
    world.step(dt);
});
```

`std::jthread` は C++20 で追加されたスレッド型で、デストラクタで自動的に `join` する。生の `std::thread` より安全なので、本書ではこちらを使う。

**スレッドプールを使うなら、ワーカの起動時に一度設定する。** タスクごとに設定する必要はない。MXCSR はスレッドに紐づくので、一度設定すればそのスレッドが生きている間は有効である。

**外部のライブラリやフレームワークがスレッドを作る場合**は、この方法が使えない。多くのタスクシステムには「ワーカスレッド開始時のフック」が用意されているので、そこに設定を差し込む。フックがない場合は、タスクの先頭で毎回設定する（コストは数ナノ秒なので、実害はほぼない）。

### アプリケーション側の責任

ここで、ライブラリ設計上の判断が一つ必要になる。

**`collision` ライブラリは、自分で MXCSR を設定すべきか。**

やってしまうと、呼び出し元の状態を勝手に変えることになる。呼び出し元が意図的に非正規化数を保持していたら、それを壊す。ライブラリとしては行儀が悪い。

本書の方針は、**設定はアプリケーション側の責任とし、ライブラリは前提を文書化して検証だけ行う**である。

```cpp
// デバッグビルドでは前提が満たされているかを検査する
inline void assert_fpu_state() noexcept {
#ifdef _DEBUG
    const auto s = get_fpu_state();
    assert(s.flush_to_zero && s.denormals_are_zero &&
           "collision ライブラリは FTZ/DAZ 有効を前提としています。"
           "enable_flush_denormals() を呼んでください。");
#endif
}
```

設定されていなくても**正しく動く**（遅くなるだけ）という点が重要である。これは第 43 章で「性能契約」として文書化する。

## 5.6 他人に書き換えられる ― 状態を守る

### MXCSR は共有された可変状態である

MXCSR はスレッドごとではあるが、そのスレッドの中では**グローバルな可変状態**である。同じスレッドで動くあらゆるコードが読み書きできる。

実際に書き換えるものは存在する。オーディオ処理のライブラリやドライバは、非正規化数による処理落ちを避けるために FTZ を有効にすることがある。逆に、厳密な数値計算を行うライブラリが `precise` な状態を要求して設定を戻すこともある。プラグインアーキテクチャを持つアプリケーションでは、読み込んだ DLL が何をするか予測できない。

つまり、**起動時に一度設定すれば以後ずっと安全、とは限らない**。

### RAII ガード

区間限定で状態を保証したいなら、RAII で書く。

```cpp
// collision/math/fp_control.h（続き）
namespace collision {

// このスコープの間、FTZ/DAZ が有効であることを保証する。
// スコープを抜けると元の状態へ戻す。
class ScopedDenormalFlush {
public:
    ScopedDenormalFlush() noexcept : saved_(_mm_getcsr()) {
        enable_flush_denormals();
    }

    ~ScopedDenormalFlush() {
        _mm_setcsr(saved_);
    }

    ScopedDenormalFlush(const ScopedDenormalFlush&) = delete;
    ScopedDenormalFlush& operator=(const ScopedDenormalFlush&) = delete;

private:
    std::uint32_t saved_;
};

} // namespace collision
```

物理更新の入口で使う。

```cpp
void World::step(float dt) {
    collision::ScopedDenormalFlush guard;   // この間は確実に FTZ/DAZ
    // ... 判定と応答 ...
}   // 呼び出し元の状態へ戻る
```

MXCSR の読み書きは数十サイクル程度なので、フレームに一度なら無視できるコストである。ただし**内側のループで使ってはいけない**。判定関数ごとにガードを置くと、そのコストが積み上がる。

このガードは、呼び出し元の状態を壊さないという点でも行儀がよい。5.5 節で「ライブラリは勝手に設定すべきでない」と書いたが、**スコープを抜けたら元に戻す**なら話は別である。

### 変化を検出する

「いつの間にか状態が変わっていた」を捕まえるには、定期的に検査する。

```cpp
// フレームの区切りで呼ぶ
inline void check_fpu_state_each_frame() {
#ifdef _DEBUG
    static bool warned = false;
    const auto s = get_fpu_state();
    if (!(s.flush_to_zero && s.denormals_are_zero) && !warned) {
        warned = true;
        std::println(stderr,
            "警告: FTZ/DAZ が無効になっています (MXCSR=0x{:08X})。"
            "どこかのモジュールが書き換えた可能性があります。", s.raw);
    }
#endif
}
```

`static bool warned` で一度しか警告しないようにしているのは、毎フレーム出ると出力が埋まって他の情報が見えなくなるためである。

第 41 章では、これをもう少し整備してデバッグ表示に組み込む。

## 5.7 コリジョンコードで非正規化数はどこから来るのか

「そんな極端に小さい値、うちのコードには出てこない」と思うかもしれない。実際には、驚くほど自然に発生する。

### 発生源 1：減衰する速度（最も典型的）

物理演算では、速度に減衰係数を掛けることが多い。

```cpp
velocity *= 0.99f;   // 毎フレーム 1% 減衰
```

初速が 1.0 だとして、60 fps で何秒後に非正規化域（`1.18e-38`）に入るか計算してみよう。`0.99^n < 1.18e-38` を解くと `n > 8700` 程度。60 fps なら約 145 秒である。

**2 分半、物体を放置するだけで非正規化数が発生する。** そしてそのまま静止していれば、以後ずっとその状態が続く。放置されたオブジェクトが多いシーンほど、じわじわ遅くなる。

この事例が示唆することは重要である。非正規化数は「異常な入力」ではなく、**正常な運用の帰結として発生する**。

### 発生源 2：二乗した値

本書は「平方根を避けて二乗のまま比較する」という方針を取る（第 4 章、第 6 章）。これは速度と数値安定性の両面で正しいのだが、**非正規化数の観点では不利に働く**。

二乗すると指数部が倍になる。

```cpp
float d = 1.0e-20f;        // 正規化数。まったく問題ない
float d2 = d * d;          // 1.0e-40 → 非正規化数！
```

`1e-20` は、1 単位 = 1 メートルなら 10 ゼプトメートルという非現実的な長さではあるが、**計算の途中で現れる値としては十分にありえる**。ほぼ同じ位置にある二点の距離を計算し、その二乗を取る、という処理は普通に書く。

正規化数の下限が `1.18e-38` なので、**二乗した値が非正規化域に落ちない条件は、元の値が `1.09e-19` 以上であること**である。この境界は覚えておく価値がある。

### 発生源 3：逆数

質量の逆数（inverse mass）は、剛体シミュレーションの定番である。静的な物体を「質量無限大」として扱うために、逆質量をゼロにする、という設計がよく使われる。

```cpp
float inv_mass = (mass > 0.0f) ? 1.0f / mass : 0.0f;
```

質量が極端に大きい物体（`1e40` など）を「無限大の代わり」として設定していると、その逆数は非正規化数になる。慣性モーメントの逆数についても同様である。

これは設計上の問題でもある。無限大を表したいなら、大きな値ではなく明示的にゼロを入れるべきである（第 35 章）。

### 発生源 4：収束する反復計算

GJK や EPA、ソルバの反復では、残差が反復ごとに小さくなる。収束が速いアルゴリズムほど、残差が非正規化域に入るのも速い。

```cpp
while (residual > tolerance) {
    // ... 更新 ...
    residual = compute_residual();   // 反復ごとに小さくなる
}
```

`tolerance` が適切に設定されていれば、非正規化域に入る前にループを抜ける。逆にいえば、**閾値を「できるだけ小さく」しようとすると非正規化数を踏む**。5.9 節で扱う「意味のある最小の値」という考え方が、ここでも効いてくる。

### 発生源 5：重心座標と正規化された比率

重心座標や補間係数のように「合計が 1 になる比率」も、片方が極端に小さいときに非正規化域へ落ちうる。三角形の頂点の極めて近くにある点の重心座標を計算すると、二つの成分がごく小さな値になる。

## 5.8 何を失うか ― FTZ/DAZ の副作用

有効にすると速度は安定する。代わりに失うものがある。正直に列挙しておく。

### 「`x - y == 0` ならば `x == y`」が成り立たなくなる

5.1 節で伏線として書いたものの回収である。FTZ/DAZ を有効にすると、非常に近い二つの値の差はゼロに潰される。

```cpp
float a = 1.0e-38f;
float b = 1.0e-38f + 1.0e-44f;   // わずかに違う値
// FTZ 有効なら a - b == 0.0f になりうるが、a != b である
```

これが直接的に生む危険は、**ゼロ除算の新しい経路**である。

```cpp
if (a != b) {
    float t = 1.0f / (a - b);    // ゼロ除算！
}
```

このコードは FTZ/DAZ 無効なら安全だが、有効にすると破綻する。

**対処の原則：割る前に、割る値そのものをチェックする。**

```cpp
const float denom = a - b;
if (std::fabs(denom) > epsilon) {
    float t = 1.0f / denom;
}
```

「差がゼロでないこと」を `a != b` で代用してはいけない。差そのものを見る。これは本書全体の規則とする。

### 二乗長がゼロに潰れる

5.7 節の発生源 2 と組み合わさると、正規化のガードが壊れる。

```cpp
// 危ない書き方
float len2 = v.x*v.x + v.y*v.y;
if (len2 > 0.0f) {                  // FTZ でゼロに潰れると false
    v /= std::sqrt(len2);
}
```

`v` の各成分が `1e-20` 程度のとき、`len2` は非正規化域に落ち、FTZ でゼロになる。すると「長さゼロのベクトル」と判定される。実際にはゼロではないのに。

これ自体は「ゼロ扱いになる」だけで、ゼロ除算は起きない（`if` で弾かれるので）。問題は、**どこからが「ゼロ扱い」になるかが、単位系と切り離されて決まってしまう**ことである。`1.09e-19` という境界は、二乗という実装の都合から出てきた数字であって、ゲームの世界の意味とは何の関係もない。

**対処：閾値を単位系から決め、二乗値ではなく元のスケールで判断する。**

```cpp
// 本書の方針（第 6 章で実装する）
inline constexpr float min_meaningful_length  = 1.0e-4f;   // 0.1 mm
inline constexpr float min_meaningful_length2 = min_meaningful_length * min_meaningful_length;
                                                            // = 1.0e-8f。非正規化域には遠い

float len2 = v.x*v.x + v.y*v.y;
if (len2 > min_meaningful_length2) {
    v /= std::sqrt(len2);
} else {
    // このベクトルは「向きを持たない」とみなす
}
```

閾値を `1e-8` に取れば、非正規化域（`1.18e-38`）とは 30 桁も離れている。FTZ の影響を受けようがない。**単位系から決めた閾値を使えば、非正規化数の問題は自動的に回避される。** これがこの章の実践的な結論である。

### 極小スケールの世界が扱えなくなる

当然の帰結として、`1e-30` メートルのような世界は表現できなくなる。分子スケールのシミュレーションをするなら FTZ/DAZ は使えない。

ゲームでこれが問題になることは、まずない。ただし「単位をどう取るか」の設計次第では起こりうる。たとえば 1 単位 = 1 キロメートルとして小さな物体を扱うと、値が小さい側に寄る。**単位系は、扱う値が `float` の中央付近に来るように選ぶ**のが原則である。

### スリープ判定が意図せず早く効く

速度が FTZ でゼロになると、「速度ゼロ＝静止」と判定するコードがそれを拾う。結果として、物体が予定より早く眠りにつく。

これは一見すると好都合に見える（実際、非正規化数の発生も同時に止まる）。しかし**制御できない挙動**である。いつ停止するかが、単位系でも設定値でもなく、`float` の表現限界によって決まってしまう。

**正しい対処は、FTZ に頼らず明示的な閾値で止めることである。**

```cpp
// 第 35 章で実装する
if (length_squared(velocity) < sleep_threshold2) {
    velocity = Vec2{0.0f, 0.0f};    // 明示的にゼロへ
}
```

`sleep_threshold` を「秒速 1 ミリメートル」のように単位系から決めておけば、挙動は予測可能になり、非正規化数も発生しない。第 35 章でこの議論を再訪する。

## 5.9 単位系を決める ― この議論の帰結

### 「意味のある最小の値」を明文化する

ここまでの議論は、一つの結論に収束する。

**扱う量ごとに「この世界で意味のある最小の値」を決めておけば、非正規化数の問題は構造的に発生しない。**

本書では次のように定める。1 単位 = 1 メートル、時間の単位は秒である。

| 量 | 記号 | 値 | 意味 |
|---|---|---|---|
| 意味のある最小の長さ | `min_length` | `1e-4f` | 0.1 ミリメートル |
| 意味のある最小の長さの二乗 | `min_length2` | `1e-8f` | 上の二乗 |
| 意味のある最小の速度 | `min_speed` | `1e-3f` | 秒速 1 ミリメートル |
| 許容するめり込み（スロップ） | `slop` | `1e-3f` | 1 ミリメートル |
| テスト検証の絶対許容誤差 | `abs_tol` | `1e-6f` | 1 マイクロメートル（第 4 章） |

これらを一箇所にまとめる。

```cpp
// collision/math/scalar.h
#pragma once

namespace collision {

// 本書の世界の縮尺：1 単位 = 1 メートル、時間の単位は秒。
// これらの定数はすべて、その前提から導かれている。

inline constexpr float min_length   = 1.0e-4f;                  // 0.1 mm
inline constexpr float min_length2  = min_length * min_length;  // 1e-8
inline constexpr float min_speed    = 1.0e-3f;                  // 1 mm/s
inline constexpr float contact_slop = 1.0e-3f;                  // 1 mm

// 非正規化数の下限との距離を確認しておく。
// min_length2 (1e-8) は 1.18e-38 の 30 桁上にあるので、
// FTZ の影響を受けることはない。
static_assert(min_length2 > 1.0e-30f,
              "閾値が非正規化域に近すぎます。単位系を見直してください");

} // namespace collision
```

`static_assert` を入れているのが要点である。将来この値を小さくしようとした人に、**なぜそれが危険なのかをコンパイル時に伝える。** コメントで書くより強い。

### 値が `float` の中央付近に来るように単位を選ぶ

一般則として、扱う数値が `float` の表現範囲の中央（絶対値で `1e-10` 〜 `1e10` くらい）に収まるように単位を選ぶ。

人間サイズのゲームなら、1 単位 = 1 メートルはよい選択である。キャラクターが 1.8、部屋が 5、街が 1000。二乗しても `1e6` 程度で、まったく余裕がある。

もし宇宙スケールを扱いたくなったら、単位を天文単位に取り替える。そのとき、この節の定数もすべて見直すことになる。だから一箇所にまとめておく。

### 極端なスケールを扱いたくなったら

どうしても極小と極大が混在するなら、いくつかの逃げ道がある。

- **座標系を分割する。** 領域ごとにローカル座標を持ち、判定はローカル座標で行う。原点からの距離が抑えられるので、精度も改善する
- **スケールを正規化してから計算する。** 判定の入口で、形状の代表長さで全体を割る。計算後に戻す
- **その部分だけ `double` を使う。** 局所的に精度を上げる。速度は落ちるが、範囲を限定すれば許容できることが多い

いずれも本書の範囲を超えるが、選択肢があることは知っておいてほしい。

## 5.10 テスト

### テストハーネスを本番と同じ状態にする

**この節は、この章で最も重要である。**

FTZ/DAZ はスレッドごとの実行時状態である。テストを実行するスレッドで設定されていなければ、**テストは本番とは違う条件でコードを検証していることになる**。

第 3 章で用意しておいた `TEST_MODULE_INITIALIZE` に、ここで設定を追加する。

```cpp
// test_main.cpp（第 3 章で作ったものを更新）
#include "CppUnitTest.h"
#include "test_helpers.h"
#include "collision/math/fp_control.h"

using namespace Microsoft::VisualStudio::CppUnitTestFramework;

namespace collision_tests {

TEST_MODULE_INITIALIZE(ModuleSetup) {
    // [追加] 本番と同じ実行時状態でテストする。
    // これを忘れると、テストは本番とは違う条件でコードを検証することになる。
    collision::enable_flush_denormals();

    const auto s = collision::get_fpu_state();
    Assert::IsTrue(s.flush_to_zero,      L"FTZ を有効にできませんでした");
    Assert::IsTrue(s.denormals_are_zero, L"DAZ を有効にできませんでした");

    Logger::WriteMessage(std::format(
        "collision_tests: MXCSR = 0x{:08X} (FTZ/DAZ 有効)\n", s.raw).c_str());
}

} // namespace collision_tests
```

`TEST_MODULE_INITIALIZE` はテスト DLL 全体で一度だけ呼ばれる。テストランナーが複数スレッドでテストを並列実行する場合は、この一度きりの設定では足りない可能性がある点に注意してほしい。並列実行を有効にしているなら、`TEST_METHOD_INITIALIZE` で毎回設定するか、並列実行を切るのが確実である。

### FTZ/DAZ の効果を検証する

```cpp
TEST_CLASS(DenormalControl) {
public:
    TEST_METHOD(FTZが有効なとき非正規化数がゼロに潰れること) {
        collision::ScopedDenormalFlush guard;

        volatile float tiny = 1.0e-38f;
        volatile float half = 0.5f;
        const float result = tiny * half;

        Assert::AreEqual(0.0f, result, 0.0f, L"FTZ が効いていない");
    }

    TEST_METHOD(FTZを切ると非正規化数が保持されること) {
        collision::disable_flush_denormals();

        volatile float tiny = 1.0e-38f;
        volatile float half = 0.5f;
        const float result = tiny * half;

        const bool is_sub = collision::is_subnormal_bits(result);

        // 後片付け（例外で飛んでもテストの前提が壊れないよう、本来は RAII にすべき）
        collision::enable_flush_denormals();

        Assert::IsTrue(is_sub, L"非正規化数が生成されていない");
    }

    TEST_METHOD(状態の保存と復元が対称であること) {
        collision::disable_flush_denormals();
        const auto before = collision::get_fpu_state();

        {
            collision::ScopedDenormalFlush guard;
            const auto inside = collision::get_fpu_state();
            Assert::IsTrue(inside.flush_to_zero && inside.denormals_are_zero);
        }

        const auto after = collision::get_fpu_state();
        Assert::IsTrue(before.raw == after.raw, L"MXCSR が復元されていない");

        collision::enable_flush_denormals();   // テスト全体の前提に戻す
    }
};
```

二つ目のテストで `disable` した後に `enable` で戻しているが、途中でアサーションが失敗すると戻らない。**本来は RAII で書くべきである**。練習問題としておく。

### 閾値が非正規化域から十分離れていることを検証する

5.9 節の `static_assert` の実行時版である。定数を変更したときに気づけるようにしておく。

```cpp
TEST_METHOD(閾値が非正規化域から十分に離れていること) {
    constexpr float min_normal = 1.175494351e-38f;   // float の最小正規化数

    // 二乗しても非正規化域に落ちないこと
    Assert::IsTrue(collision::min_length2 > min_normal * 1.0e10f,
                   L"min_length2 が非正規化域に近すぎる");
    Assert::IsTrue(collision::min_speed * collision::min_speed > min_normal * 1.0e10f,
                   L"min_speed の二乗が非正規化域に近すぎる");
}
```

### ベンチマークを回帰テストとして残す

5.2 節で書いたベンチマークは、消さずに残しておく。FTZ/DAZ を切った状態と入れた状態で比べれば、設定が効いていることが数字で確認できる。

```cpp
TEST_METHOD(FTZの有無で速度差があることを確認する) {
    constexpr int N = 5'000'000;
    volatile float sink = 0.0f;

    collision::disable_flush_denormals();
    const double without = measure_ms([&] { sink = decay_loop(1.0e-38f, N); });

    collision::enable_flush_denormals();
    const double with = measure_ms([&] { sink = decay_loop(1.0e-38f, N); });

    Logger::WriteMessage(std::format(
        "FTZ 無効: {:8.1f} ms\nFTZ 有効: {:8.1f} ms\n改善率  : {:8.2f} 倍\n",
        without, with, without / with).c_str());

    // 環境によって差の大きさは違うので、失敗にはしない。数字を残すのが目的
}
```

**あえてアサーションを置いていない。** 速度差は CPU に強く依存するので、閾値を決めると環境によって落ちる。数字を出力しておけば、後から人間が読める。

一方、第 42 章で性能の回帰を検出する仕組みを作るときには、この判断を見直す。「将来 MXCSR の設定が失われたら気づける」ようにするには、何らかの形で自動検出が要る。そのときは速度そのものではなく、5.10 節の最初に書いた**状態の検査**を使うほうが安定する。

## この章のまとめ

- 非正規化数は `float` の下限（約 `1.18e-38`）より小さい値を、精度を落としながら表現する仕組み
- 多くの x86 実装で、非正規化数の演算は大幅に遅い。**必ず自分の環境で実測する**
- **FTZ**（結果を潰す）と **DAZ**（入力を潰す）は別のスイッチ。片方だけでは取りこぼす
- `/fp:fast` はコンパイル時の許可であり、実行時の MXCSR を設定しない。**明示的に設定し、検証する**
- **MXCSR はスレッドごと。** ワーカスレッドでの設定漏れが典型的な落とし穴
- 他のモジュールに書き換えられうる。`ScopedDenormalFlush` で区間を守る
- 発生源：減衰する速度、二乗した値、逆数、収束する反復、重心座標
- 副作用：`x - y == 0` から `x == y` が言えなくなる。二乗長がゼロに潰れる
- **対処の本筋は、単位系から決めた閾値を使うこと。** FTZ/DAZ は保険である
- テストハーネスも本番と同じ MXCSR で走らせる。さもなければテストは意味を失う

### 落とし穴と練習問題

**落とし穴 1：Debug で測って「差がない」と判断する。**　最適化されていないコードでは演算以外のコストが支配的になり、差が埋もれる。必ず Release で測る。

**落とし穴 2：`constexpr` や定数畳み込みで検証してしまう。**　コンパイル時に計算された値は、実行時の MXCSR と無関係である。検証には必ず `volatile` を挟む。

**落とし穴 3：スレッドプールのワーカに設定し忘れる。**　「並列化したのに速くならない」の隠れた原因になりうる。

**落とし穴 4：FTZ に暗黙に依存する。**　「速度が小さくなれば自然にゼロになる」に頼ると、挙動が `float` の表現限界に支配される。明示的な閾値で制御する。

---

**練習問題 5-1**　5.2 節のベンチマークを自分の環境で走らせ、比率を記録しよう。次に `decay_loop` の初期値を変えて、非正規化域を通る割合を変化させたときに比率がどう動くかを観察する。

**練習問題 5-2**　`disable_flush_denormals` を呼んだ後、例外やアサーション失敗で `enable` に到達しなくても状態が戻るように、RAII クラス（`ScopedDenormalFlush` の逆版）を書こう。5.10 節の二つ目のテストをそれで書き直す。

**練習問題 5-3**　`v *= 0.99f` を繰り返して、実際に何回目で非正規化域に入るかを測ってみよう。`is_subnormal_bits` を使えば検出できる。5.7 節の計算（約 8700 回）と合うだろうか。減衰係数を `0.999f` や `0.9f` に変えると、回数はどう変わるか。

**練習問題 5-4**　`min_length` を `1e-4f` ではなく `1e-18f` に変えると、`static_assert` が発火するはずである。実際に試して、エラーメッセージを確認しよう。次に `1e-15f` にするとどうなるか。二乗した値が非正規化域に落ちる境界（元の値が `1.09e-19`）と、`static_assert` の閾値の関係を確かめてみてほしい。

**練習問題 5-5**（発展）　ワーカスレッドで FTZ/DAZ が設定されないとどうなるかを実験しよう。`std::jthread` を直接使ってスレッドを立て、その中で `get_fpu_state` を呼び、メインスレッドと比べる。次に `spawn_thread` を使って同じことをして、違いを確認する。
