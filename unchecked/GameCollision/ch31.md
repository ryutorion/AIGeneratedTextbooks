# 第 31 章　Sweep and Prune

> **この章のゴール**
> 1 本の軸に投影して並べ、区間が重なる範囲だけを調べる。グリッドと違って**調整すべきセルサイズがない**。
>
> このアルゴリズムの本質は、ソートそのものではなく**フレーム間コヒーレンシ**である。物体は 1 フレームでほとんど動かないので、前フレームの順序はほぼ正しい。実測すると、初回のソートで 100 万回必要だった交換が、2 回目以降は 700 回で済む。**1,400 倍の差**が、このアルゴリズムを成立させている。

---

## 31.1 1 軸への投影と区間の重なり

### 考え方

AABB を 1 本の軸（まずは X 軸）に投影すると、区間 `[min.x, max.x]` になる。

**二つの AABB が重なるなら、その X 区間も必ず重なる。** 逆は成り立たない（X で重なっても Y でずれていれば AABB は重ならない）。つまり **X 区間の重なりは必要条件**である。

そこで、**X 区間が重ならない組を先に捨てる**。

物体を `min.x` の昇順に並べておくと、これが素直に書ける。

```
並び：  A[0,3]   B[1,5]   C[4,6]   D[9,12]
        |----|
              |------|
                   |--|
                            |----|
```

`A` から始めて右へ進む。`B.min.x = 1 ≤ A.max.x = 3` なので候補。`C.min.x = 4 > 3` なので、**ここで打ち切ってよい**。以降の物体はすべて `min.x ≥ 4` なので、`A` と重なることはありえない。

**「打ち切れる」ことが、ソートしておく理由のすべてである。**

### 実装

```cpp
// collision/broadphase/sweep_prune.h
#pragma once
#include <vector>
#include <algorithm>
#include "collision/shapes/aabb.h"
#include "collision/broadphase/counters.h"

namespace collision {

class SweepAndPrune {
public:
    void add(std::uint32_t id, const Aabb& box) {
        boxes_.resize(std::max<std::size_t>(boxes_.size(), id + 1));
        boxes_[id] = box;
        order_.push_back(id);
        sorted_ = false;
    }

    void update(std::uint32_t id, const Aabb& box) noexcept { boxes_[id] = box; }

    BroadphaseCounters collect_pairs(std::vector<Pair>& out);

private:
    void sort_axis();

    std::vector<Aabb>          boxes_;
    std::vector<std::uint32_t> order_;      // sweep_axis_ の min 昇順
    int  sweep_axis_{0};                    // 0 = X, 1 = Y
    bool sorted_{false};
};

} // namespace collision
```

掃く処理はこうなる。

```cpp
BroadphaseCounters SweepAndPrune::collect_pairs(std::vector<Pair>& out) {
    BroadphaseCounters counters{};
    sort_axis();
    out.clear();

    const std::size_t n = order_.size();
    for (std::size_t k = 0; k < n; ++k) {
        const std::uint32_t i = order_[k];
        const float i_max = axis_max(boxes_[i], sweep_axis_);

        for (std::size_t m = k + 1; m < n; ++m) {
            const std::uint32_t j = order_[m];

            // 掃引軸で離れたら、以降はすべて離れている
            if (axis_min(boxes_[j], sweep_axis_) > i_max) break;

            ++counters.aabb_tests;
            if (!intersect(boxes_[i], boxes_[j])) continue;

            out.emplace_back(std::min(i, j), std::max(i, j));
            ++counters.candidate_pairs;
        }
    }
    return counters;
}
```

**重複が原理的に出ない**のが、グリッドに対する明確な利点である。各ペアは「並び順で前にいる方」から一度だけ見つかる。第 30.1 節のような排除の工夫が要らない。

`axis_min` / `axis_max` は軸番号で成分を選ぶだけの小さな関数である。

```cpp
[[nodiscard]] constexpr float axis_min(const Aabb& b, int axis) noexcept {
    return axis == 0 ? b.min.x : b.min.y;
}
[[nodiscard]] constexpr float axis_max(const Aabb& b, int axis) noexcept {
    return axis == 0 ? b.max.x : b.max.y;
}
```

3D へ拡張するときは `Aabb3` 版を足すだけである。**掃引そのもののコードは次元に依存しない。** グリッドがセルの走査で次元に縛られていたのと対照的である。

### 計算量

ソートが O(n log n)、掃引が O(n + k)。`k` は候補ペア数である。

**物体が広く散らばっていれば `k` は O(n) 程度に収まり、全体で O(n log n) になる。** 逆に全物体が同じ X 区間に密集していると `k` が O(n²) に戻る。最悪ケースは総当たりと同じである。

### 端点リスト方式との違い

古典的な SAP は、**AABB ごとに「開始」「終了」の 2 個の端点を並べた列**を持つ。

```
  ┃A開  ┃B開  ┃A終  ┃C開  ┃B終  ┃C終
```

左から走査し、「開」で走査中集合に加え、「終」で取り除く。集合に入っている間の物体どうしがペアになる。

**この形の利点は、端点の交換 1 回ごとにペアの増減が局所的に決まることである。** 「A終 と B開 が入れ替わった → ペア (A,B) が発生した」と分かるので、ペア集合を毎フレーム作り直さず、差分だけ更新できる。

**欠点は状態が増えることである。** 端点列（2n 要素）、走査中集合、ペア集合の三つを常に整合させ続ける必要がある。挿入・削除のたびに三つを更新し、どれか一つでもずれると症状が出るのは何フレームも後になる。

**本書は端点リストを使わず、毎フレームペアを作り直す形を採る。** 理由は実測にある。31.4 節のとおり n = 10,000 でも 0.95 ミリ秒であり、**差分更新で削れるのは、そのうちのごく一部でしかない。**

**状態を減らせるなら減らす。** バグの入る余地は状態の数に比例する。これは性能の話ではなく設計の話である。

## 31.2 挿入ソートの利用

### 毎フレーム `std::sort` は無駄である

素朴に書けば、毎フレーム `std::sort` を呼ぶことになる。O(n log n) だから悪くないように見える。

**だがこれは、前フレームの仕事を捨てている。**

ゲームでは、物体は 1 フレームに数センチしか動かない。**前フレームの並び順は、ほとんどそのまま正しい。** ソート済みに近い列に対して `std::sort`（イントロソート）は特に速くならない。

**ほとんどソート済みの列を速く並べ替えられるアルゴリズムがある。挿入ソートである。**

```cpp
void SweepAndPrune::sort_axis() {
    if (!sorted_) {
        // 初回、または軸を切り替えた直後：まともなソートを使う
        std::ranges::sort(order_, {}, [&](std::uint32_t id) {
            return axis_min(boxes_[id], sweep_axis_);
        });
        sorted_ = true;
        return;
    }

    // 2 回目以降：ほぼ整列済みなので挿入ソート
    for (std::size_t k = 1; k < order_.size(); ++k) {
        const std::uint32_t cur = order_[k];
        const float key = axis_min(boxes_[cur], sweep_axis_);

        std::size_t j = k;
        while (j > 0 && axis_min(boxes_[order_[j - 1]], sweep_axis_) > key) {
            order_[j] = order_[j - 1];
            --j;
        }
        order_[j] = cur;
    }
}
```

**挿入ソートの計算量は O(n + 交換回数)** である。すでに整列していれば交換ゼロで、単なる 1 回の走査になる。

### どれだけ違うのか

n = 2,000 の物体を配置し、毎フレーム各軸へランダムに ±0.1 だけ動かして、挿入ソートの交換回数を数えた。

| 状況 | 交換回数 |
|---|---:|
| 初回（ランダムな順序から） | **1,000,795** |
| 2 フレーム目 | 678 |
| 3 フレーム目 | 697 |
| 4 フレーム目 | 685 |
| 5 フレーム目 | 685 |
| 6 フレーム目 | 720 |

**初回は約 100 万回、2 回目以降は約 700 回。1,400 倍の差**である。

初回の 1,000,795 は、ランダムな列に対する挿入ソートの期待値 `n²/4 = 1,000,000` とほぼ一致している。**これが「初回だけは `std::sort` を使う」理由である。** 挿入ソートに任せると、最初のフレームだけ確実にスパイクする。

2 回目以降の 700 回は `n = 2,000` の 3 分の 1 でしかない。**掃引のコストのほうがはるかに大きく、ソートは実質タダになっている。**

> **これが「コヒーレンシを利用する」ということ**
> 挿入ソートは、教科書では「O(n²) だから使うな」と教わるアルゴリズムである。だが**入力の性質が分かっていれば、話は変わる。**
>
> ゲームの物体は連続的に動く。瞬間移動しない。この性質を知っているからこそ、最悪 O(n²) のアルゴリズムを安心して選べる。
>
> **逆に言えば、瞬間移動が頻繁に起きるゲーム**（弾を大量にプールから出し入れする、ワープが多い）**では、この前提が崩れる。** そのときは 29.4 節のカウンタに「交換回数」を足して監視するとよい。数字が跳ね上がったら前提が壊れたということである。

### 交換回数もカウンタに入れる

```cpp
struct BroadphaseCounters {
    // ... 既存のメンバ
    std::uint64_t sort_swaps{};   // 挿入ソートの交換回数
};
```

**決定論的で、シーンの性質を直接映す指標である。** 「コヒーレンシが効いているか」を、時間を測らずに確認できる。

## 31.3 軸の選び方

### どの軸で掃くかは、性能を 180 倍変える

X で掃くか Y で掃くかは、単なる好みではない。

**横に広く、縦に薄いシーン**を作って測った。n = 3,000、X は ±500 に散らばり、Y は 0〜10 の狭い範囲（地面の上に並んだキャラクタのようなシーン）。

| 掃引軸 | 中心座標の分散 | 候補ペア | 実ペア |
|---|---:|---:|---:|
| **X 軸** | 82,366 | **9,001** | 3,210 |
| Y 軸 | 8.4 | **1,615,902** | 3,210 |
| （総当たり） | — | 4,498,500 | 3,210 |

**Y 軸で掃くと、候補が 180 倍になる。** そして総当たりの 4,498,500 に対して 1,615,902 なので、**わずか 2.8 分の 1 にしか減っていない**。ブロードフェーズとしてほとんど機能していない。

理由ははっきりしている。**Y 方向には全物体が幅 10 の中にひしめいているので、区間がほぼ全部重なる。** 打ち切りが効かない。

### 分散が最大の軸を選ぶ

**判断基準は「中心座標のばらつきが最も大きい軸」である。** ばらつきが大きいほど、区間が離れやすく、打ち切りが早く効く。

```cpp
// 中心座標の分散が最大の軸を返す
[[nodiscard]] int best_sweep_axis(std::span<const Aabb> boxes) noexcept {
    if (boxes.empty()) return 0;

    // 総和と二乗和から分散を出す（1 パスで済む）
    Vec2 sum{}, sum2{};
    for (const Aabb& b : boxes) {
        const Vec2 c = (b.min + b.max) * 0.5f;
        sum  += c;
        sum2 += Vec2{c.x * c.x, c.y * c.y};
    }
    const float inv_n = 1.0f / static_cast<float>(boxes.size());
    const Vec2 mean = sum * inv_n;
    const Vec2 var{sum2.x * inv_n - mean.x * mean.x,
                   sum2.y * inv_n - mean.y * mean.y};

    return (var.x >= var.y) ? 0 : 1;
}
```

**O(n) で済む。** 掃引そのものが O(n + k) なので、無視できるコストである。

> **`/fp:fast` と分散の計算**
> `E[x²] − E[x]²` という式は、**桁落ちが起きやすい**ことで知られている。座標が 1000 付近に集まっていると、`sum2` は 10⁶ 台になり、そこから同じくらいの値を引くことになる。有効桁が大きく失われる。
>
> `/fp:fast` では、この式の評価順序も自由になる。**分散が負になることさえある。**
>
> だが**ここでは問題にならない。** 求めたいのは「どちらの軸が大きいか」という比較だけであり、値そのものではないからである。桁落ちで多少ずれても、82,366 対 8.4 のような差が逆転することはない。
>
> **精度が要るのか、大小関係だけでよいのか**を見極めることが、`/fp:fast` の下で書く技術である。第 4.6 節の「`precise` に戻す判断基準」を、逆側から適用した例になっている。もし本当に分散の値が要るなら、平均を引いてから二乗する二パス版を使う。

### 軸を切り替えるときの注意

**軸を変えると、`order_` のソート基準が変わる。** そのままでは並びが無効になり、挿入ソートが O(n²) に落ちる（初回と同じ状況になる）。

```cpp
void SweepAndPrune::set_axis(int axis) noexcept {
    if (axis == sweep_axis_) return;
    sweep_axis_ = axis;
    sorted_ = false;      // 次回は std::sort を使わせる
}
```

そして**軸をコロコロ切り替えてはいけない。** 二つの軸の分散が拮抗していると、フレームごとに行ったり来たりして、毎フレーム全体ソートが走る。

**ヒステリシスを入れる。**

```cpp
// 現在の軸の分散を 1.3 倍したものを超えて初めて切り替える
void SweepAndPrune::maybe_switch_axis() noexcept {
    const Vec2 var = center_variance(boxes_);
    const float cur   = (sweep_axis_ == 0) ? var.x : var.y;
    const float other = (sweep_axis_ == 0) ? var.y : var.x;
    if (other > cur * 1.3f) set_axis(1 - sweep_axis_);
}
```

**さらに、毎フレーム判定する必要もない。** 60 フレームに 1 回で十分である。シーンの形は 1 秒で劇的には変わらない。

### 掃引軸の分散が意味するもの

分散を使う理由を、もう少し掘り下げておく。

**掃引が打ち切れるのは、区間が離れているときである。** 物体 A の後ろに続く物体のうち、`min > A.max` になるまでの個数が候補数を決める。

物体が幅 `w` の範囲に `n` 個並んでいるなら、AABB の長さ `s` の区間に入る個数の期待値は `n·s/w` である。**候補ペアの総数はおよそ `n²s/(2w)` になる。**

つまり**候補数は「散らばりの幅 `w`」に反比例する。** 分散はこの `w` の代理指標である（標準偏差が `w` に比例する）。

先の表で確かめてみよう。X 方向は `w ≈ 1000`、物体の幅は 1 なので、`n²s/(2w) = 3000²/2000 = 4,500`。実測は 9,001 で、同じ桁である。Y 方向は `w = 10` なので `3000²·2/(2·10) = 900,000`。実測 1,615,902 と、これも同じ桁である。

**大雑把な見積もりが実測と桁で一致する**なら、理解はおおむね正しい。細かいずれは分布の形（一様でない）から来ている。

### 3D では軸の選択がさらに重要になる

3D のゲームでは、**Y（高さ）方向のばらつきが X・Z より一桁小さい**ことが多い。地面の上を歩き回るゲームなら当然である。

**3D で Y 軸を掃引軸に選ぶと、ほぼ確実に破綻する。** 上の表の Y 軸の行が、そのまま起きる。

分散による自動選択を入れておけば事故は防げるが、**「なぜ Y を選んではいけないか」を理解しておく**ほうが大事である。デバッグ中に掃引軸を固定して試すことは普通にあり、そのとき何が起きるか分かっていないと原因を見失う。

### 物体の追加と削除

ゲームでは物体が生まれたり消えたりする。**SAP でこれをどう扱うか。**

**追加は末尾に積み、次のソートに任せる。** 挿入ソートが正しい位置まで運んでくれる。運ぶ距離は最悪 n だが、1 フレームに数十個の追加なら問題にならない。

**削除は「穴を開けない」ことが大事である。**

```cpp
void SweepAndPrune::remove(std::uint32_t id) {
    // order_ から取り除く。詰めるので整列は保たれる
    const auto it = std::ranges::find(order_, id);
    if (it != order_.end()) order_.erase(it);
    free_ids_.push_back(id);
}
```

`erase` は O(n) の移動を伴うが、**整列が保たれる**ので次のソートが安く済む。逆に「末尾と入れ替えて `pop_back`」という定番の手を使うと、**整列が壊れて挿入ソートが大きく動く**。

**データ構造の性質を壊さない削除を選ぶ。** ここでも、単体の操作コストではなく次フレームへの影響で判断している。

## 31.4 性能の比較

第 29 章の総当たり、第 30 章のグリッド、本章の SAP を、同じシーン・同じマシンで比較した。物体は毎フレーム移動し、SAP は前フレームの順序を引き継いでいる。

| n | 総当たり | 均一グリッド | **SAP** | 実ペア数 |
|---:|---:|---:|---:|---:|
| 500 | 0.451 ms | 0.104 ms | **0.016 ms** | 27 |
| 2,000 | 7.614 ms | 0.455 ms | **0.108 ms** | 81 |
| 5,000 | 47.83 ms | 1.588 ms | **0.366 ms** | 219 |
| 10,000 | 191.2 ms | 3.753 ms | **0.948 ms** | 465 |

三者とも**まったく同じペア集合**を返すことを、同一フレームの状態で確認したうえでの計測である。

**n = 10,000 で 191 ms が 0.948 ms になった。200 倍である。** 第 29.3 節で `/fp:fast` が 1.2 倍だったことと比べてほしい。

グリッドが SAP より遅く出ているが、これは実装の差が大きい。ここでのグリッドは `std::unordered_map` を使っており、セルごとのハッシュ計算と間接参照を払っている。第 30.3 節の空間ハッシュを配列で実装すれば、差は縮まる。

**それでも、このシーンでは SAP が素直に速い。** 物体がまばらで、1 軸のばらつきが十分にあるからである。逆に物体が均等に密集したシーンではグリッドが有利になる。

> **どちらを選ぶか**
> | | 均一グリッド | Sweep and Prune |
> |---|---|---|
> | 調整項目 | セルサイズ（重要） | 掃引軸（自動化できる） |
> | 密集したシーン | 強い | 弱い（1 軸に潰れる） |
> | 細長いシーン | 弱くない | **軸が合えば非常に強い** |
> | 大きな物体 | **非常に弱い** | 区間が長くなるだけ。耐える |
> | 瞬間移動 | 影響なし | ソートが乱れる |
> | 実装の手数 | 中（重複排除が要る） | **小** |
>
> **本書は次章の動的 AABB 木を最終的な推奨とするが、SAP は実装が小さいわりに強い。** 「まず SAP を入れて、足りなければ木にする」は妥当な進め方である。

## 31.5 テスト

### 正しさと性質

グリッドと同じ三点に加えて、SAP 固有の性質を検査する。**特に「打ち切りの `break` が正しいか」は、正しさのテストでは絶対に見つからない**ので、意識して仕掛けを用意する。

```cpp
// test_sweep_prune.cpp
TEST_CLASS(SweepAndPruneTest) {
public:
    TEST_METHOD(総当たりと同じペア集合を返すこと) {
        for (std::uint32_t seed = 0; seed < 300; ++seed) {
            const auto boxes = make_scene(2 + seed % 60, 3600 + seed);
            collision::SweepAndPrune sap;
            for (std::uint32_t i = 0; i < boxes.size(); ++i) sap.add(i, boxes[i]);
            std::vector<collision::Pair> got;
            sap.collect_pairs(got);
            assert_same_pairs(brute_force_pairs(boxes), std::move(got));
        }
    }

    TEST_METHOD(掃引軸を変えても同じ集合になること) {
        const auto boxes = make_scene(200, /*seed=*/3700);
        const auto expected = brute_force_pairs(boxes);
        for (const int axis : {0, 1}) {
            collision::SweepAndPrune sap;
            sap.set_axis(axis);
            for (std::uint32_t i = 0; i < boxes.size(); ++i) sap.add(i, boxes[i]);
            std::vector<collision::Pair> got;
            sap.collect_pairs(got);
            assert_same_pairs(expected, std::move(got));
        }
    }

    TEST_METHOD(掃引後に順序が整列していること) {
        auto boxes = make_scene(500, /*seed=*/3800);
        collision::SweepAndPrune sap;
        for (std::uint32_t i = 0; i < boxes.size(); ++i) sap.add(i, boxes[i]);
        std::vector<collision::Pair> tmp;
        sap.collect_pairs(tmp);

        const auto& order = sap.order_for_test();
        for (std::size_t k = 1; k < order.size(); ++k)
            Assert::IsTrue(collision::axis_min(boxes[order[k-1]], 0)
                        <= collision::axis_min(boxes[order[k]],   0),
                           L"掃引軸に沿って整列していません");
    }
```

**整列の不変条件を直接検査する**のが、SAP ならではのテストである。挿入ソートを自分で書いた以上、それが本当に整列を保っているかを確かめる必要がある。

### コヒーレンシが効いていること

31.2 節の主張そのものをテストにする。

```cpp
    TEST_METHOD(二フレーム目以降の交換回数が激減すること) {
        constexpr int n = 2000;
        auto boxes = make_scene(n, /*seed=*/3900);
        collision::SweepAndPrune sap;
        for (std::uint32_t i = 0; i < boxes.size(); ++i) sap.add(i, boxes[i]);

        std::vector<collision::Pair> pairs;
        sap.collect_pairs(pairs);                  // 初回（std::sort）

        Rng rng(3901);
        std::uint64_t worst = 0;
        for (int frame = 0; frame < 10; ++frame) {
            for (std::uint32_t i = 0; i < boxes.size(); ++i) {
                const Vec2 d{rng.uniform(-0.1f, 0.1f), rng.uniform(-0.1f, 0.1f)};
                boxes[i].min += d; boxes[i].max += d;
                sap.update(i, boxes[i]);
            }
            worst = std::max(worst, sap.collect_pairs(pairs).sort_swaps);
        }

        // 交換回数が n を超えたら、コヒーレンシの前提が壊れている
        Assert::IsTrue(worst < static_cast<std::uint64_t>(n),
            std::format(L"交換回数 {} が n = {} を超えました", worst, n).c_str());
    }
```

**「時間ではなく仕事量をテストする」（第 29.4 節）の実例である。** 交換回数は決定論的なので、CI で安心して閾値を置ける。

### ペアの開始・終了イベント

物体が動けば、ペアは現れたり消えたりする。**その差分が正しく取れることを確かめる。**

```cpp
    TEST_METHOD(フレーム間のペア差分が総当たりの差分と一致すること) {
        auto boxes = make_scene(80, /*seed=*/4000);
        collision::SweepAndPrune sap;
        for (std::uint32_t i = 0; i < boxes.size(); ++i) sap.add(i, boxes[i]);

        std::vector<collision::Pair> cur, prev;
        sap.collect_pairs(prev);
        auto brute_prev = brute_force_pairs(boxes);

        Rng rng(4001);
        for (int frame = 0; frame < 100; ++frame) {
            for (std::uint32_t i = 0; i < boxes.size(); ++i) {
                const Vec2 d{rng.uniform(-0.5f, 0.5f), rng.uniform(-0.5f, 0.5f)};
                boxes[i].min += d; boxes[i].max += d;
                sap.update(i, boxes[i]);
            }
            sap.collect_pairs(cur);
            const auto brute_cur = brute_force_pairs(boxes);

            // 追加されたペアと削除されたペアを、両者で突き合わせる
            assert_same_pairs(set_difference(brute_cur, brute_prev),
                              set_difference(normalized(cur), normalized(prev)));
            assert_same_pairs(set_difference(brute_prev, brute_cur),
                              set_difference(normalized(prev), normalized(cur)));

            prev = cur;
            brute_prev = brute_cur;
        }
    }
};
```

**毎フレーム集合が一致していれば差分も一致するので、このテストは論理的には冗長である。** それでも書く価値がある。第 33.2 節でペアを永続化してイベントを発行するとき、**差分こそが本体になる**からである。ここで差分の取り方を固めておくと、そのまま次章で使える。

そして「毎フレーム 0.5 ずつランダムに動かす」という入力は、31.2 節の穏やかな動き（±0.1）より荒い。**イベントが実際に発生する状況を作らないと、差分のテストは何も検証しない。**

### 打ち切りが効いていること

```cpp
    TEST_METHOD(打ち切りが効いて候補が総当たりより十分少ないこと) {
        // X 方向に細長く広げたシーン。打ち切りが強く効くはず
        auto boxes = make_scene(3000, /*seed=*/4100);
        for (auto& b : boxes) { b.min.x *= 8.0f; b.max.x *= 8.0f; }

        collision::SweepAndPrune sap;
        sap.set_axis(0);
        for (std::uint32_t i = 0; i < boxes.size(); ++i) sap.add(i, boxes[i]);

        std::vector<collision::Pair> got;
        const auto counters = sap.collect_pairs(got);

        constexpr std::uint64_t brute = 3000ull * 2999ull / 2ull;
        Assert::IsTrue(counters.aabb_tests * 100 < brute,
            std::format(L"AABB 判定 {} 回（総当たり {} 回）",
                        counters.aabb_tests, brute).c_str());
    }
```

**`break` を `continue` に書き換えると、このテストだけが落ちる。** 答えは正しいままなので、他のどのテストも通ってしまう。**「正しいが遅い」を検出する専用のテストが要る**理由である。

### 退化ケース

```cpp
    TEST_METHOD(物体がゼロ個・一個でも壊れないこと) {
        collision::SweepAndPrune sap;
        std::vector<collision::Pair> out;
        sap.collect_pairs(out);
        Assert::IsTrue(out.empty());

        sap.add(0, collision::Aabb{Vec2{0,0}, Vec2{1,1}});
        sap.collect_pairs(out);
        Assert::IsTrue(out.empty());
    }

    TEST_METHOD(全物体が同一位置でも正しい集合を返すこと) {
        // 最悪ケース：候補が n(n-1)/2 に戻る。落ちないことだけ確認する
        std::vector<collision::Aabb> boxes(200,
            collision::Aabb{Vec2{0,0}, Vec2{1,1}});
        collision::SweepAndPrune sap;
        for (std::uint32_t i = 0; i < boxes.size(); ++i) sap.add(i, boxes[i]);
        std::vector<collision::Pair> got;
        const auto counters = sap.collect_pairs(got);
        Assert::AreEqual(std::size_t{200 * 199 / 2}, got.size());
        Assert::IsTrue(counters.aabb_tests == 200ull * 199ull / 2ull);
    }
```

**最悪ケースを「落ちないこと」だけでなく「本当に O(n²) になること」まで確認しておく。** 打ち切りが効かない状況を、テストとして明示的に持っておく意味がある。将来この数字が変わったら、実装の性質が変わったということである。

## この章のまとめ

- SAP は **1 軸に投影して整列し、区間が離れたら打ち切る**。重複ペアが原理的に出ない
- 掃引のコードは**次元に依存しない**。3D 化は `axis_min` / `axis_max` の追加だけ
- **本質はソートではなくフレーム間コヒーレンシ。** 初回 1,000,795 回 → 2 回目以降 700 回の交換（1,400 倍）
- **初回だけ `std::sort`、以降は挿入ソート。** 挿入ソートに初回を任せると必ずスパイクする
- 教科書的には「使うな」と言われる挿入ソートが、**入力の性質を知っていれば最適になる**
- **掃引軸は中心座標の分散が最大のものを選ぶ。** 誤ると候補が 180 倍になる
- 分散の計算は桁落ちしやすいが、**大小の比較だけなら問題にならない**
- 軸の切り替えは並びを無効化する。**ヒステリシスを入れ、毎フレーム判定しない**
- 3D では Y（高さ）を選ぶとほぼ確実に破綻する
- 実測：n = 10,000 で総当たり 191 ms に対し SAP は **0.948 ms（200 倍）**
- 候補数は**散らばりの幅に反比例**する。`n²s/(2w)` という見積もりが実測と桁で一致する
- 古典的な**端点リスト方式**は差分更新できるが状態が三つに増える。**再構築版で十分速い**
- 削除は `erase` で詰める。**末尾と入れ替えると整列が壊れ、次フレームのソートが跳ねる**
- テストは「集合の一致」「整列の不変条件」「交換回数の上限」「フレーム間差分」「打ち切りの効き」の五点
- **`break` を `continue` にする間違いは、正しさのテストでは絶対に見つからない**

### 落とし穴と練習問題

**落とし穴 1：毎フレーム `std::sort` を呼ぶ。**　コヒーレンシの利益を全部捨てている。

**落とし穴 2：初回から挿入ソート。**　最初のフレームだけ確実に O(n²) のスパイクが出る。

**落とし穴 3：掃引軸を固定する。**　シーンの形が変わると突然遅くなる。分散で自動選択する。

**落とし穴 4：軸をヒステリシスなしで切り替える。**　拮抗したシーンで毎フレーム全体ソートが走る。

**落とし穴 5：`break` を `continue` と書き間違える。**　答えは正しいまま、性能だけが総当たりに戻る。**正しさのテストでは検出できない。** だからこそ 29.4 節のカウンタが要る。

---

**練習問題 31-1**　`break` を `continue` に変えて、31.5 節のテストを全部走らせよう。どのテストが落ちるだろうか。落ちなかったテストがあるとしたら、それは何を意味するだろうか。

**練習問題 31-2**　`sort_swaps` を記録し、物体の 1 フレームあたりの移動量を 0.01, 0.1, 1.0, 10.0 と変えて測ろう。交換回数はどう増えるだろうか。「瞬間移動が多いと SAP が弱い」という主張を、数字で裏づけてほしい。

**練習問題 31-3**　2 軸で掃く版（X で絞ったあと Y でも絞る）を実装し、候補ペア数と時間を 1 軸版と比べよう。細長いシーンと密集したシーンの両方で測ってほしい。

**練習問題 31-4**　`best_sweep_axis` の分散計算を、二パス版（平均を引いてから二乗）に置き換えよう。座標を 10,000 付近に平行移動したシーンで、1 パス版と結果が変わるかどうか確かめてほしい。

**練習問題 31-5**（発展）　増分版の SAP を実装しよう。挿入ソートの交換ごとに「区間の重なりが始まった・終わった」を検出し、ペア集合を毎フレーム作り直さずに更新する。正しさは本章のテストで担保できる。実装してみると、**再構築版のほうが単純で、しかも十分速い**ことが分かるかもしれない。それも一つの結論である。
