# 第 18 章　連続衝突判定（CCD）を実運用に載せる

> **この章のゴール**
> 前章までで、平行移動する形状の正確な衝突時刻が求まるようになった。この章では、それを実際のゲームに載せるための判断を扱う。
>
> **いつ CCD が必要か**（18.1）、**任意の凸形状にどう適用するか**（18.2）、**サブステッピングとどちらを選ぶか**（18.3）、**回転をどうするか**（18.4）。そして `/fp:fast` の下で反復アルゴリズムが無限ループに陥る事故を、具体的な形で見る（18.5）。
>
> 完全には解けない問題が残る章でもある。**どこで割り切るかを自分で決められるようになる**ことが、この章の本当のゴールである。

## 18.1 トンネリングが起きる条件を見積もる

### 条件を式にする

物体 A が 1 フレームで `d` だけ移動し、厚さ `w` の壁を通過するとき、離散判定がすり抜けを見逃す条件を考える。

A 自身の厚さ（移動方向の幅）を `a` とすると、A が壁と重なっている「区間」の長さは `a + w` である。フレームの始点と終点のどちらでもこの区間に入らないためには、

```
d > a + w
```

が必要である。**すり抜けの条件は、「1 フレームの移動量が、自分の厚さと壁の厚さの和を超えること」である。**

### 具体的な数値で

60 fps を前提に、いくつかのケースを見る。

| 物体 | 速度 | 1 フレームの移動量 | 自分の厚さ | 通過できる壁の厚さ |
|---|---|---|---|---|
| 歩くキャラクター | 5 km/h | 0.023 m | 0.5 m | すり抜けない |
| 走るキャラクター | 20 km/h | 0.093 m | 0.5 m | すり抜けない |
| 車 | 100 km/h | 0.46 m | 2.0 m | すり抜けない |
| 投擲物 | 30 m/s | 0.5 m | 0.2 m | 0.3 m 未満 |
| 拳銃弾 | 350 m/s | 5.8 m | 0.01 m | **5.8 m 未満** |
| ライフル弾 | 900 m/s | 15 m | 0.01 m | **15 m 未満** |

**キャラクターの移動には CCD が要らない。** これは重要な結論である。CCD にはコストがかかるので、必要ないものに適用するのは無駄である。

一方、弾丸は壊滅的である。厚さ 15 メートル未満の壁を、すべてすり抜ける。ほとんどの建物の壁は通過してしまう。

### 判定を実装する

```cpp
// collision/narrow/ccd.h
#pragma once

#include "collision/narrow/sweep.h"

namespace collision {

// CCD が必要かどうかの見積もり。
// thickness は移動方向における物体の厚さ（保守的に最小幅を使う）。
[[nodiscard]] inline bool needs_ccd(Vec2 delta, float thickness,
                                    float min_obstacle_thickness) noexcept {
    return length_squared(delta) >
           (thickness + min_obstacle_thickness) * (thickness + min_obstacle_thickness);
}

} // namespace collision
```

`min_obstacle_thickness` は、シーンに存在する最も薄い障害物の厚さである。**これはアプリケーション側が知っている情報**であり、ライブラリ側では決められない。

実務では、物体ごとに「CCD を有効にする」フラグを持たせるのが一般的である。弾丸には立て、キャラクターには立てない。第 33 章のパイプラインで、この仕組みを組み込む。

### 保守的な見積もり

上の式は、移動方向に沿った厚さを使っている。実際には、物体の向きによって「移動方向の厚さ」は変わる。

**保守的に、物体の最小幅を使う。** 細長い物体が細い方向を向いていた場合を想定すれば、見逃しがない。

```cpp
// AABB の最小幅
[[nodiscard]] constexpr float min_width(const Aabb& b) noexcept {
    const Vec2 s = size(b);
    return std::min(s.x, s.y);
}
```

「CCD を有効にしすぎて遅くなる」ほうが、「無効にしすぎてすり抜ける」より、はるかにましである。**安全側に倒す。**

## 18.2 保守的前進

### 任意の凸形状に使える手法

前章の方法（ミンコフスキー差＋レイキャスト）は、ミンコフスキー差を明示的に構築できる形状にしか使えない。円と AABB では簡単だったが、凸多角形どうしでは辺の数が増えた複雑な形になる（第 16 章の練習問題 16-2）。

**保守的前進**（conservative advancement）は、ミンコフスキー差を構築せずに TOI を求める手法である。必要なのは「二つの形状の距離を求める関数」だけである。

### 考え方

時刻 `t = 0` から始める。次の手順を繰り返す。

1. 現在の時刻での、A と B の距離 `d` を求める
2. 距離がほぼゼロなら、そこが TOI である。終了
3. 相対速度の大きさを `v` とすると、**どんなに速くても `d / v` の時間だけは衝突しない**
4. 時刻を `d / v` だけ進める
5. 1 に戻る

**3 の論法が肝心である。** 距離が `d` あるなら、相対速度 `v` で近づいても、`d / v` 時間は絶対に接触しない。だから安全に進める。「保守的」というのは、この「絶対に安全な量だけ進む」という性質を指す。

反復のたびに距離が縮まるので、TOI に単調に近づく。**必ず収束する**（浮動小数点の事情を除けば）。

### 実装

```cpp
// collision/narrow/ccd.h（続き）

// 「二つの形状の距離を返せる」ことを要求するコンセプト
template <class A, class B>
concept HasDistance = requires(const A& a, const B& b) {
    { distance_between(a, b) } -> std::convertible_to<float>;
};

struct ToiResult {
    float t{};                // 衝突時刻（0〜1）
    bool  converged{true};    // 反復が収束したか
    int   iterations{};       // 反復回数（診断用）
};

// 保守的前進による TOI 計算。
// translate は「形状を平行移動する」操作を与える。
template <class A, class B, class Translate>
[[nodiscard]] std::optional<ToiResult>
conservative_advance(A a, Vec2 delta, const B& b, Translate translate,
                     float target_distance = contact_slop) noexcept
    requires HasDistance<A, B>
{
    const float speed = length(delta);
    if (speed < min_length) {
        // ほとんど動かない。開始時点で接触しているかだけを見る
        return (distance_between(a, b) <= target_distance)
            ? std::optional{ToiResult{.t = 0.0f}} : std::nullopt;
    }

    constexpr int max_iterations = 32;

    float t = 0.0f;
    A moved = a;

    for (int iter = 0; iter < max_iterations; ++iter) {
        const float d = distance_between(moved, b);

        // 目標距離まで近づいたら終了
        if (d <= target_distance) {
            return ToiResult{.t = t, .converged = true, .iterations = iter};
        }

        // 安全に進める時間
        const float advance = (d - target_distance) / speed;

        // [重要] 前進量がゼロに潰れると無限ループになる（18.5 節）
        if (!can_advance(advance)) {
            return ToiResult{.t = t, .converged = false, .iterations = iter};
        }

        t += advance;
        if (t >= 1.0f) {
            return std::nullopt;      // フレーム内では衝突しない
        }

        moved = a;
        translate(moved, delta * t);
    }

    // 反復上限に達した。安全側に倒して、現在の t を返す
    return ToiResult{.t = t, .converged = false, .iterations = max_iterations};
}
```

### 三つの設計判断

**1. `target_distance` を置いている。**

距離がちょうどゼロになるまで反復すると、収束が非常に遅くなる（進む量が幾何級数的に小さくなる）。第 5.9 節で決めた `contact_slop`（1 ミリメートル）まで近づけば十分とする。

これは第 17.3 節で「`contact_slop` だけ引き戻す」としたのと同じ配慮である。**接触ぎりぎりを狙わない。**

**2. 反復上限を置いている。**

上限に達しても、それまでに求まった `t` を返す。`nullopt` を返すのは危険である。「収束しなかった」を「衝突しない」と扱うと、すり抜ける。

`converged` フラグで呼び出し側に伝える。診断とテストで使う。

**3. 距離関数を外部から要求している。**

`distance_between` の実装は形状ペアごとに違う。円どうしなら簡単、凸多角形どうしなら GJK が要る（第 21 章）。

**本書の現時点では、円との距離しか求められない。** そこで、使える範囲の実装を用意する。

```cpp
// collision/narrow/distance.h
#pragma once

#include "collision/narrow/closest_point.h"

namespace collision {

[[nodiscard]] inline float
distance_between(const Circle& a, const Circle& b) noexcept {
    const float d = distance(a.center, b.center) - a.radius - b.radius;
    return std::max(d, 0.0f);
}

// 円と、最近接点を求められる任意の形状（第 9 章のコンセプト）
template <HasClosestPoint S>
[[nodiscard]] float distance_between(const Circle& a, const S& b) noexcept {
    const Vec2 q = closest_point(a.center, b);
    return std::max(distance(a.center, q) - a.radius, 0.0f);
}

} // namespace collision
```

**凸多角形どうしの距離は、第 21 章の GJK まで待つ。** そこで `distance_between(ConvexPolygon, ConvexPolygon)` が実装され、`conservative_advance` がそのまま任意の凸形状に使えるようになる。第 23 章でこれを扱う。

**コンセプトで要求だけしておき、実装は後の章で埋める**という構成にしたのは、この見通しを先に示すためである。

### 前章の方法とどちらを使うか

| 手法 | 適用範囲 | 精度 | コスト |
|---|---|---|---|
| ミンコフスキー差＋レイキャスト（第 17 章） | 差を構築できる形状のみ | 解析的（厳密） | 低い |
| 保守的前進（この章） | 距離を求められる形状すべて | 反復（`target_distance` まで） | 反復回数に比例 |

**構築できるなら前章の方法を使う。** 円どうし、AABB どうしは解析的に解けるので、反復する理由がない。

保守的前進は、解析的に解けない場合の汎用手段である。

## 18.3 サブステッピングとの使い分け

### サブステッピングとは

CCD の代わりに、**時間刻みを細かくする**という単純な対処がある。1 フレームを N 分割し、各分割で通常の離散判定を行う。

```cpp
// サブステッピングの概略
void step_with_substeps(World& world, float dt, int substeps) {
    const float sub_dt = dt / static_cast<float>(substeps);
    for (int i = 0; i < substeps; ++i) {
        world.integrate(sub_dt);      // 位置を進める
        world.detect_and_resolve();   // 離散判定と応答
    }
}
```

18.1 節の式に照らすと、移動量が `1/N` になるので、すり抜けの条件 `d > a + w` を満たしにくくなる。

### コストの比較

拳銃弾（1 フレーム 5.8 m 移動）が厚さ 1 cm の壁をすり抜けないようにするには、`5.8 / N < 0.01 + 0.01` から `N > 290` が必要になる。

**290 分割は現実的でない。** シーン全体の物理演算を 290 回行うことになる。

一方 CCD なら、その弾丸 1 個について 1 回のスイープ判定で済む。

### 使い分けの基準

| 状況 | 選択 | 理由 |
|---|---|---|
| 一部の物体だけが高速 | **CCD** | 高速な物体だけにコストを払える |
| 全体的に速い（レースゲームなど） | サブステップ | 個別 CCD より一括処理が効率的 |
| 積み上がった物体の安定性が欲しい | サブステップ | 応答の反復回数が増えて安定する |
| 薄い壁が多い | **CCD** | サブステップでは分割数が足りない |

**両方使うのが実際の答えである。** サブステップを 2〜4 程度に設定して全体の安定性を上げつつ、高速な物体には個別に CCD を適用する。

サブステッピングには、CCD にない利点がある。**衝突応答も細かく刻まれる**ため、積み上げた物体が安定しやすい。CCD は「いつ当たるか」を正確にするだけで、応答の質は改善しない。第 37 章のソルバで、この話を再訪する。

## 18.4 回転を伴う運動

### なぜ難しいのか

ここまでの手法は、すべて**平行移動のみ**を前提としている。

回転が入ると、ミンコフスキー差が時間とともに形を変える。第 16.4 節の帰着で使った `(A + v) ⊖ B = (A ⊖ B) + v` という性質は、回転には成り立たない。

保守的前進はどうか。こちらは距離関数さえあれば動くので、回転する形状にも適用できる。**ただし「安全に進める時間」の計算が変わる。**

回転する物体では、重心から遠い点ほど速く動く。半径 `r` の位置にある点は、角速度 `ω` で `r·ω` の速度を持つ。したがって、最大速度は

```
v_max = |linear_velocity| + r_max · |angular_velocity|
```

となる（`r_max` は重心から最も遠い点までの距離）。この `v_max` を使えば、保守的前進はそのまま機能する。

```cpp
// 回転を含む場合の最大速度
[[nodiscard]] inline float
max_point_speed(Vec2 linear, float angular, float bounding_radius) noexcept {
    return length(linear) + std::fabs(angular) * bounding_radius;
}
```

### なぜ実用上つらいのか

理論的には解ける。問題は**効率**である。

`v_max` は保守的に見積もった値なので、実際の接近速度よりずっと大きい。すると「安全に進める時間」が短く見積もられ、反復回数が増える。

高速回転する細長い物体では、`r_max · ω` が支配的になり、`v_max` が実際の接近速度の何十倍にもなりうる。反復が収束しない。

### 実用上の割り切り

ゲームでは、次のいずれかを採るのが一般的である。

**1. 回転を無視して CCD を行う。** 平行移動成分だけでスイープし、回転は考えない。ほとんどの場合これで十分である。回転が原因ですり抜けるのは、細長い物体が高速回転している場合に限られる。

**2. CCD 中は回転を止める。** TOI を求めるときは回転させず、衝突後に回転を適用する。物理的には不正確だが、破綻はしない。

**3. 高速回転する物体には CCD を適用しない。** そもそもそういう物体が壁をすり抜けても、見た目に分からないことが多い。

**本書は 1 を採る。** 実装は単純で、実用上の破綻がほとんどない。

```cpp
// CCD では平行移動成分のみを使う（回転は無視する）という方針をコードに残す
// 注：細長い物体が高速回転している場合、この近似では見逃しが生じうる。
//     そのようなケースが問題になるなら、18.4 節の方法 2 または 3 を検討すること。
```

**コメントで割り切りを明記しておく**のが重要である。将来「なぜか回転する棒がすり抜ける」という報告があったとき、ここを見れば原因が分かる。

### 完全に解こうとしないこと

商用の物理エンジンでも、回転を含む CCD は近似的にしか扱われていない。厳密解は、時間についての高次方程式を解くことになり、実時間では不可能である。

**「完全に解けない問題がある」と認識しておくことが、実務では重要である。** 完璧を目指して時間を溶かすより、割り切りの位置を自覚して先へ進むほうがよい。

## 18.5 収束判定を `precise` で守る

### 無限ループの事故

18.2 節の実装に `can_advance(advance)` という関数があった。これを説明する。

保守的前進は、反復ごとに `advance = (d - target) / speed` だけ時刻を進める。距離が縮まるにつれて `advance` は小さくなる。

**問題は、`advance` が `t` に加えても `t` が変わらないほど小さくなったときである。**

```cpp
t += advance;    // advance が t の ULP より小さいと、t が変わらない
```

`t = 0.9` のとき、`float` の ULP は約 `6e-8` である。`advance` がそれより小さいと、`t += advance` は `t` を変えない。すると次の反復も同じ距離を計算し、同じ `advance` を得る。**無限ループになる。**

反復上限（32 回）があるので実際には止まるが、**32 回まで無駄に回る**ことになる。しかもその間、`t` は進んでいない。

### `/fp:fast` が悪化させる

第 5 章で扱った FTZ が、この状況に絡む。

`advance` が非正規化域に落ちると、FTZ によってゼロに潰される。`t += 0.0f` は当然 `t` を変えない。**FTZ が有効かどうかで、この事故の起きやすさが変わる。**

さらに `/fp:fast` では、コンパイラが `t += advance` を含む式を再結合しうる。`t` の更新が期待どおりの順序で行われる保証がない。

### `precise` で守る

第 4.6 節で決めた判断基準を思い出してほしい。

> **戻すのは「回数が少なく、かつ判定を誤ると制御フローが壊れる箇所」だけ**

保守的前進の収束判定は、まさにこれに該当する。反復は多くて 32 回であり、判定を誤ると無限ループになる。

```cpp
// collision/narrow/ccd.h（続き）

#pragma float_control(precise, on, push)

// 前進量が意味のある大きさかを判定する。
// /fp:fast の下では、この判定が最適化で崩れると無限ループになるため
// precise で守る（第 4.6 節の判断基準を適用）。
__declspec(noinline)
[[nodiscard]] inline bool can_advance(float advance) noexcept {
    // 時刻 t は 0〜1 の範囲なので、1.0 の ULP を基準にする。
    // これより小さい前進は t を変化させられない。
    constexpr float min_advance = 1.0e-6f;   // 1.0 の ULP（約 1.2e-7）の 8 倍
    return advance > min_advance;
}

#pragma float_control(pop)
```

`__declspec(noinline)` を併用しているのは、第 4.6 節で述べた「インライン展開で pragma が漏れる」問題への対処である。

**閾値 `1e-6f` の根拠。** `t` の範囲は 0〜1 なので、最も粗い場所（`t ≈ 1`）での ULP が約 `1.2e-7` である。その 8 倍を取ることで、確実に `t` が変化する量だけを許す。第 4.3 節で `default_abs_tol` を `1e-6f` にしたのと同じ考え方である。

### 前進しなくなったときの扱い

`can_advance` が偽になったら、そこで反復を打ち切る。

そのとき何を返すか。**それまでに求まった `t` を返し、`converged = false` を立てる。**

`nullopt` を返してはいけない。距離が `target_distance` まで縮まっていなくても、そこまで接近しているのは事実である。「衝突しない」と扱うと、すり抜ける。

**収束しなかったことを呼び出し側に伝え、判断させる。** 第 7.5 節で `std::expected` を導入したときの考え方と同じである。

## 18.6 テスト

### 保守的前進が解析解と一致すること

円どうしなら、第 17 章の解析的な方法で厳密な答えが求まる。それをリファレンスにする。

```cpp
// test_ccd.cpp
TEST_CLASS(ConservativeAdvance) {
public:
    TEST_METHOD(円どうしで解析解と一致すること) {
        Rng rng(1200);
        int checked = 0;

        for (int i = 0; i < 5000; ++i) {
            const Circle a{{rng.uniform(-5.0f, 5.0f), rng.uniform(-5.0f, 5.0f)},
                           rng.uniform(0.2f, 1.0f)};
            const Circle b{{rng.uniform(-5.0f, 5.0f), rng.uniform(-5.0f, 5.0f)},
                           rng.uniform(0.2f, 1.0f)};
            const Vec2 delta{rng.uniform(-10.0f, 10.0f), rng.uniform(-10.0f, 10.0f)};

            if (collision::overlaps(a, b)) continue;

            const auto exact = collision::sweep(a, delta, b);       // 第 17 章
            const auto ca = collision::conservative_advance(a, delta, b,
                [](Circle& c, Vec2 d) { c.center += d; });

            Assert::AreEqual(exact.has_value(), ca.has_value(),
                             L"衝突の有無が食い違う");
            if (!exact || !ca) continue;

            Assert::IsTrue(ca->converged, L"保守的前進が収束しなかった");

            // 保守的前進は target_distance だけ手前で止まるので、
            // 厳密解より必ず小さい（または等しい）
            Assert::IsTrue(ca->t <= exact->t + 1.0e-4f,
                detail::widen(std::format("CA の t が厳密解を超えた: {:.6g} > {:.6g}",
                                          ca->t, exact->t)).c_str());

            // ただし大きく手前で止まってはいけない
            const float speed = collision::length(delta);
            const float slack = (collision::contact_slop / std::max(speed, 1.0e-3f)) + 1.0e-3f;
            expect_near(exact->t, ca->t, slack, 1.0e-2f);
            ++checked;
        }

        Logger::WriteMessage(std::format("照合できた事例 {} 件\n", checked).c_str());
        Assert::IsTrue(checked > 500, L"照合できた事例が少なすぎる");
    }
};
```

**「保守的」であることを検証している**のが要点である。`ca->t <= exact->t` は、保守的前進の定義そのものである。厳密解より先に進むことは絶対にない。

同時に「大きく手前で止まってはいけない」も検証する。`target_distance` を速度で割った量が、許される遅れの目安になる。

### 時間刻みを変えても TOI が収束すること

```cpp
TEST_CLASS(ToiConvergence) {
public:
    TEST_METHOD(target_distanceを小さくすると厳密解に近づくこと) {
        const Circle a{{-5.0f, 0.0f}, 1.0f};
        const Circle b{{ 0.0f, 0.0f}, 1.0f};
        const Vec2 delta{10.0f, 0.0f};

        const auto exact = collision::sweep(a, delta, b);
        Assert::IsTrue(exact.has_value());

        float prev_error = std::numeric_limits<float>::infinity();
        for (float target : {0.1f, 0.01f, 0.001f, 0.0001f}) {
            const auto ca = collision::conservative_advance(a, delta, b,
                [](Circle& c, Vec2 d) { c.center += d; }, target);

            Assert::IsTrue(ca.has_value());
            const float err = std::fabs(exact->t - ca->t);

            Assert::IsTrue(err <= prev_error + 1.0e-6f,
                detail::widen(std::format(
                    "target={:.6g} で誤差が増えた: {:.6g} → {:.6g}",
                    target, prev_error, err)).c_str());
            prev_error = err;

            Logger::WriteMessage(std::format(
                "target={:<8.5g} t={:.7g} 誤差={:.3g} 反復={}\n",
                target, ca->t, err, ca->iterations).c_str());
        }
    }

    TEST_METHOD(フレーム分割してもTOIの絶対時刻が変わらないこと) {
        // 1 フレームで delta 進むのと、2 分割して delta/2 ずつ進むので、
        // 衝突する「絶対的な位置」は同じはず
        const Circle b{{0.0f, 0.0f}, 1.0f};
        const Vec2 full_delta{10.0f, 0.0f};
        const Circle a0{{-5.0f, 0.0f}, 1.0f};

        const auto h1 = collision::sweep(a0, full_delta, b);
        Assert::IsTrue(h1.has_value());
        const float hit_x_1 = a0.center.x + full_delta.x * h1->t;

        // 2 分割：前半で当たらなければ後半を試す
        float hit_x_2 = 0.0f;
        bool found = false;
        Circle a = a0;
        for (int k = 0; k < 2 && !found; ++k) {
            const Vec2 half = full_delta * 0.5f;
            if (const auto h = collision::sweep(a, half, b)) {
                hit_x_2 = a.center.x + half.x * h->t;
                found = true;
            } else {
                a.center += half;
            }
        }

        Assert::IsTrue(found, L"分割すると衝突を見逃した");
        expect_near(hit_x_1, hit_x_2, 1.0e-3f, 1.0e-4f);
    }
};
```

二つ目のテストが重要である。**「フレームの刻み方を変えても、衝突する場所は同じ」**という性質は、CCD が正しく機能していることの強い証拠になる。

これが成り立たないなら、CCD は「たまたま今の刻み幅で動いているだけ」ということになる。

### 収束しないケースの検出

18.5 節で扱った事故を、テストで再現する。

```cpp
TEST_CLASS(CcdRobustness) {
public:
    TEST_METHOD(前進量がゼロに潰れても無限ループにならないこと) {
        // 極端に近い位置から、極端に遅い速度で近づく
        const Circle a{{-1.0f - 1.0e-7f, 0.0f}, 0.5f};
        const Circle b{{ 0.0f, 0.0f}, 0.5f};
        const Vec2 delta{1.0e-5f, 0.0f};   // ほとんど動かない

        const auto ca = collision::conservative_advance(a, delta, b,
            [](Circle& c, Vec2 d) { c.center += d; });

        // 結果がどうであれ、返ってくること（＝無限ループしていないこと）
        if (ca) {
            Assert::IsTrue(collision::is_finite_bits(ca->t));
            Assert::IsTrue(ca->t >= 0.0f && ca->t <= 1.0f);
            Assert::IsTrue(ca->iterations <= 32);
        }
    }

    TEST_METHOD(can_advance の閾値が t を実際に変化させること) {
        // 18.5 節の閾値の根拠を検証する
        for (float t : {0.0f, 0.5f, 0.9f, 0.999f}) {
            constexpr float min_advance = 1.0e-6f;
            const float next = t + min_advance;
            Assert::IsTrue(next > t,
                detail::widen(std::format(
                    "t={:.6g} で min_advance を足しても値が変わらない", t)).c_str());
        }
    }

    TEST_METHOD(収束しなかった場合でも t を返すこと) {
        // converged が false でも nullopt にはしない、という規約の確認
        Rng rng(1201);
        int not_converged = 0;

        for (int i = 0; i < 20000; ++i) {
            const Circle a{{rng.uniform(-2.0f, 2.0f), rng.uniform(-2.0f, 2.0f)},
                           rng.uniform(0.2f, 1.0f)};
            const Circle b{{rng.uniform(-2.0f, 2.0f), rng.uniform(-2.0f, 2.0f)},
                           rng.uniform(0.2f, 1.0f)};
            const Vec2 delta{rng.uniform(-0.1f, 0.1f), rng.uniform(-0.1f, 0.1f)};

            if (collision::overlaps(a, b)) continue;

            const auto ca = collision::conservative_advance(a, delta, b,
                [](Circle& c, Vec2 d) { c.center += d; });
            if (!ca) continue;

            Assert::IsTrue(collision::is_finite_bits(ca->t));
            if (!ca->converged) ++not_converged;
        }

        Logger::WriteMessage(std::format(
            "収束しなかった事例: {} 件\n", not_converged).c_str());
    }
};
```

二つ目のテストが、**閾値の根拠そのものを検証している**。`1e-6f` を足せば必ず `t` が変化することを、`t` の全範囲で確かめる。将来この定数を変更したとき、根拠が崩れれば落ちる。

三つ目で「収束しなかった件数」を記録している。これも第 11.6 節と同じ発想で、**将来この数が急増したら異常の兆候**である。

### すり抜け条件の見積もり

18.1 節の式を検証する。

```cpp
TEST_METHOD(すり抜け条件の見積もりが実際と合うこと) {
    // 厚さ w の壁を、厚さ a の物体が d だけ移動して通過するとき、
    // d > a + w なら離散判定が見逃しうる
    for (float w : {0.05f, 0.1f, 0.5f}) {
        const Aabb wall{{-w * 0.5f, -5.0f}, {w * 0.5f, 5.0f}};
        constexpr float a = 0.1f;

        // d を境界の前後で振って、離散判定が見逃すかを調べる
        const float threshold = a + w;

        // 見逃しうる移動量：始点と終点の両方で外れる配置が存在する
        const float d_big = threshold * 1.5f;
        bool found_miss = false;
        for (int i = 0; i < 500 && !found_miss; ++i) {
            const float x = -d_big + static_cast<float>(i) * d_big / 500.0f;
            const Aabb obj{{x - a * 0.5f, -0.05f}, {x + a * 0.5f, 0.05f}};
            const Aabb moved{obj.min + Vec2{d_big, 0.0f}, obj.max + Vec2{d_big, 0.0f}};

            if (!collision::overlaps(obj, wall) && !collision::overlaps(moved, wall)
                && collision::sweep(obj, Vec2{d_big, 0.0f}, wall)) {
                found_miss = true;
            }
        }
        Assert::IsTrue(found_miss,
            detail::widen(std::format("w={} で見逃しが再現しなかった", w)).c_str());
    }
}
```

## この章のまとめ

- **すり抜けの条件：1 フレームの移動量 > 自分の厚さ ＋ 障害物の厚さ**
- キャラクターの移動には CCD が要らない。弾丸には必須である
- 保守的前進：距離だけ安全に進めることを繰り返す。**距離関数さえあれば任意の凸形状に使える**
- `target_distance`（`contact_slop`）まで近づけば終了。厳密なゼロを狙わない
- 反復上限に達しても、それまでの `t` を返す。`nullopt` はすり抜けを招く
- **凸多角形どうしの距離は第 21 章の GJK まで待つ。** コンセプトで要求だけしておく
- サブステッピングは全体の安定性に効くが、弾丸には分割数が足りない。**両方を併用する**
- 回転を含む CCD は理論的には解けるが、保守的な速度見積もりのせいで収束が悪い
- **本書は「CCD では回転を無視する」と割り切る。** 割り切りをコードにコメントで残す
- `can_advance` を `precise` で守る。前進量がゼロに潰れると無限ループになる（第 4.6 節の適用）
- テストは、解析解との照合・分割不変性・収束しないケース・すり抜け条件の 4 系統

### 第 III 部を終えて

第 1 章の対応表でいえば、**「第 18 章：弾丸がすり抜けない高速移動体の判定」に到達した**。

| できること | 章 |
|---|---|
| レイキャスト（円・AABB・線分・凸多角形） | 第 15 章 |
| 交差・距離・深度・TOI の統一的な見方 | 第 16 章 |
| 平行移動する形状の正確な TOI | 第 17 章 |
| 任意の凸形状への CCD の枠組み | この章 |
| CCD が必要かどうかの判断基準 | 18.1 節 |

**残っているもの。** 凸多角形どうしの距離関数がまだない。そのため、保守的前進が実際に使えるのは「円が絡むペア」に限られている。

これを解決するのが第 IV 部である。GJK は、ミンコフスキー差を構築せずに交差判定・距離・貫通深度を求める。第 16 章で導入した見方が、そこで完全な形をとる。

### 落とし穴と練習問題

**落とし穴 1：収束しなかったときに `nullopt` を返す。**　すり抜けの原因になる。`converged` フラグで伝える。

**落とし穴 2：`target_distance` をゼロにする。**　収束が極端に遅くなり、反復上限に達する。

**落とし穴 3：回転を CCD に含めようとして反復が終わらない。**　割り切りの位置を決める。

---

**練習問題 18-1**　18.1 節の表を、自分のゲームの設定で作り直してみよう。フレームレート、物体の大きさ、最も薄い壁の厚さから、どの物体に CCD が必要かを判断する。

**練習問題 18-2**　`can_advance` の `precise` 指定を外し、`/fp:fast` の Release ビルドで 18.6 節のロバスト性テストを走らせよう。挙動に違いは出るだろうか。`.asm` を出力して、判定がどうコンパイルされているかを確認してほしい。

**練習問題 18-3**　保守的前進の反復回数を記録し、`target_distance` を変えたときにどう変化するかをグラフにしてみよう。理論上は幾何級数的に収束するはずである。実測と合うだろうか。

**練習問題 18-4**　18.4 節の方法 2（CCD 中は回転を止める）を実装してみよう。回転する棒が壁に当たる場面で、方法 1（回転を完全に無視）との違いを観察してほしい。

**練習問題 18-5**（発展）　二分探索による TOI 計算を実装し、保守的前進と比較しよう。二分探索は「交差する時刻」と「交差しない時刻」を挟み込んでいく方法である。収束は速いが、**開始時に交差する時刻を見つけておく必要がある**（そのために離散判定を刻む）。どちらが実用的か考えてみてほしい。

第 IV 部では、本書で最も抽象度が高い部分に入る。**サポート写像**という一つの窓口を通せば、円も、箱も、凸多角形も、まったく同じアルゴリズムで扱えるようになる。第 16 章で導入したミンコフスキー差の見方が、そこで本来の力を発揮する。GJK と EPA は難所だが、越えれば視界が開ける。
