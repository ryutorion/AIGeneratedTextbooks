# 第 20 章　GJK ― 交差しているか

> **この章のゴール**
> GJK（Gilbert–Johnson–Keerthi）アルゴリズムを実装する。**ミンコフスキー差を構築せずに、原点が含まれるかを判定する。**
>
> 第 16 章で「交差判定は原点がミンコフスキー差に含まれるかと同値」と述べた。第 19 章でサポート写像という窓口を作った。この二つを合わせると、任意の凸形状どうしの判定が、形状の種類を知らないまま書ける。
>
> 本書で最も抽象度が高い章である。難所だが、越えれば円も箱も多角形も楕円も、すべて同じ一つの関数で扱えるようになる。

---

## 20.1 問題の言い換えを確認する

### 出発点

第 16.2 節の等価性を再掲する。

> **A と B が交差する ⇔ 原点が `A ⊖ B` に含まれる**

そして第 19.3 節で、`A ⊖ B` のサポート点が求まるようになった。

```
support(A ⊖ B, d) = support(A, d) - support(B, -d)
```

**手元にあるのは、この「問い合わせ窓口」だけである。** `A ⊖ B` の頂点が何個あるかも、どんな形かも分からない。分かるのは「この向きの最遠点はここ」だけ。

その情報だけで「原点が中に入っているか」を判定する。それが GJK である。

### 基本的な戦略

原点を含む三角形を、ミンコフスキー差の中に見つけようとする。

三角形が見つかれば、原点は確実に内部にある（三角形はミンコフスキー差の部分集合なので）。**見つからないことが確定すれば、交差していない。**

この「原点を囲もうとする三角形」を**シンプレックス**（単体）と呼ぶ。2D では点・線分・三角形の三段階がある。

### なぜサポート点だけで足りるのか

ミンコフスキー差は凸である（凸形状どうしのミンコフスキー差は凸になる）。凸形状に原点が含まれないなら、**原点を分離する直線が存在する**（第 11.1 節の分離軸定理）。

その分離直線の法線を `d` とすると、`support(A ⊖ B, d)` は原点より `d` 方向の手前にある。つまり `dot(support(d), d) < 0` になる。

**これが「交差していない」の判定条件である。** 一つでもそういう `d` が見つかれば確定する。

逆に、そんな `d` がどうしても見つからず、原点を囲む三角形が作れたら、交差している。

## 20.2 シンプレックスを育てる

### アルゴリズムの骨格

```
1. 適当な向き d を選ぶ
2. p = support(A⊖B, d) を求め、シンプレックスに入れる
3. d = -p （原点へ向かう向き）とする
4. 繰り返す：
     p = support(A⊖B, d)
     もし dot(p, d) < 0 なら → 交差していない（確定）
     p をシンプレックスに加える
     シンプレックスを処理する：
       原点を含んでいれば → 交差している（確定）
       そうでなければ、原点に最も近い部分だけを残し、
       新しい探索方向 d を決める
```

**「原点に近づく方向へサポート点を取り続ける」**のが基本の動きである。取れなくなったら（`dot(p, d) < 0`）交差していない。

### 早期脱出の条件

`dot(p, d) < 0` は何を意味するか。

`p` は `d` 方向の最遠点である。それが原点より手前にある（内積が負）なら、**`d` を法線とする直線が原点とミンコフスキー差を分離している**。これ以上調べる必要はない。

この判定が、GJK が高速な理由の一つである。**離れている形状ほど早く決着する。** ゲームでは判定するペアの大半が交差していないので、この性質はありがたい。

### シンプレックスの型

```cpp
// collision/narrow/gjk.h
#pragma once

#include "collision/narrow/support.h"
#include <array>
#include <cstdint>

namespace collision {

// GJK が保持する単体。2D では最大 3 点。
struct Simplex {
    std::array<MinkowskiPoint, 3> point{};
    std::uint32_t count{};

    void push(const MinkowskiPoint& p) noexcept {
        // 新しい点は末尾に入れる（末尾が「最新の点 A」）
        point[count++] = p;
    }
};

} // namespace collision
```

**末尾が最新の点である**という規約を置く。以降の場合分けでは、この最新の点を `A` と呼ぶ。原点へ向かう方向は常に `-A` の側にあるので、`A` を基準に考えると場合分けが整理される。

## 20.3 単体の場合分け

### 線分の場合

シンプレックスが 2 点 `[B, A]` になった（`A` が最新）。

原点はどこにあるか。**`A` を加える直前に `d` 方向へ進んだので、原点は `A` から見て `-A` の側にある。** そして `B` は前回のサポート点なので、原点が `B` より外側にあることはない。

したがって、可能性は二つに絞られる。

- **辺 `AB` の側**（`AB` に垂直な方向に原点がある）
- **頂点 `A` の側**（`A` から見て `B` と反対方向に原点がある）

判定は `dot(AB, AO)` の符号で行う（`AO = -A` は `A` から原点へ向かうベクトル）。

```cpp
namespace detail {

// 線分の場合。原点に近い部分を残し、次の探索方向を返す。
// 戻り値：原点を含んでいれば true（2D の線分では起こらないので常に false）
[[nodiscard]] inline bool
simplex_line(Simplex& s, Vec2& d) noexcept {
    const Vec2 a = s.point[1].diff;   // 最新
    const Vec2 b = s.point[0].diff;

    const Vec2 ab = b - a;
    const Vec2 ao = -a;

    if (dot(ab, ao) > 0.0f) {
        // 原点は辺 AB の側。AB に垂直で原点を向く方向へ
        d = perpendicular(ab);
        if (dot(d, ao) < 0.0f) d = -d;
        // シンプレックスは [B, A] のまま
    } else {
        // 原点は A の側。B を捨てる
        s.point[0] = s.point[1];
        s.count = 1;
        d = ao;
    }
    return false;
}
```

**`perpendicular` を使っている**点に注目してほしい。3D の GJK では三重積 `(AB × AO) × AB` を使うのが定石だが、**2D なら 90 度回転して符号を合わせるだけで済む**。乗算が減り、意味も明快になる。

```cpp
// 3D で使われる一般形（2D では上のほうが安い）
// triple_product(a, b, c) = b * dot(a, c) - a * dot(b, c)
```

第 27 章で 3D に進むとき、この一般形が必要になる。

### 三角形の場合

シンプレックスが 3 点 `[C, B, A]` になった（`A` が最新）。

原点は、`A` から見て `-A` の側にある。三角形の周りの領域のうち、`A` に隣接する二つの辺領域（`AB` の外側、`AC` の外側）と、三角形の内部のいずれかである。

- **`AB` の外側にある** → `C` を捨てて線分 `[B, A]` にする
- **`AC` の外側にある** → `B` を捨てて線分 `[C, A]` にする
- **どちらでもない** → 原点は三角形の内部。**交差している**

```cpp
// 三角形の場合。原点を含んでいれば true。
[[nodiscard]] inline bool
simplex_triangle(Simplex& s, Vec2& d) noexcept {
    const Vec2 a = s.point[2].diff;   // 最新
    const Vec2 b = s.point[1].diff;
    const Vec2 c = s.point[0].diff;

    const Vec2 ao = -a;
    const Vec2 ab = b - a;
    const Vec2 ac = c - a;

    // 辺 AB の、C と反対側を向く法線
    Vec2 ab_perp = perpendicular(ab);
    if (dot(ab_perp, ac) > 0.0f) ab_perp = -ab_perp;

    // 辺 AC の、B と反対側を向く法線
    Vec2 ac_perp = perpendicular(ac);
    if (dot(ac_perp, ab) > 0.0f) ac_perp = -ac_perp;

    if (dot(ab_perp, ao) > 0.0f) {
        // 原点は AB の外側。C を捨てる → [B, A]
        s.point[0] = s.point[1];
        s.point[1] = s.point[2];
        s.count = 2;
        d = ab_perp;
        return false;
    }

    if (dot(ac_perp, ao) > 0.0f) {
        // 原点は AC の外側。B を捨てる → [C, A]
        s.point[1] = s.point[2];
        s.count = 2;
        d = ac_perp;
        return false;
    }

    // どちらでもない → 原点は三角形の内部
    return true;
}
```

**法線の向きを「三角形の外側」に揃えている**のが要点である。`ab_perp` は辺 `AB` に垂直で、`C` と反対を向く。これが「`AB` の外側」の向きになる。

`dot(ab_perp, ao) > 0` なら、原点はその外側にある。

### 辺 `BC` を調べなくてよい理由

三角形の辺は 3 本あるのに、`AB` と `AC` しか調べていない。**`BC` の外側は調べなくてよいのか。**

よい。`B` と `C` は前の反復で残された点であり、その時点で「原点は `BC` の外側にはない」と判定されている。`A` を加えても、その判定は覆らない。

**この省略が、GJK の場合分けを簡潔に保っている。** 「最新の点 `A` を基準に考える」という規約の見返りである。

### まとめる

```cpp
[[nodiscard]] inline bool handle_simplex(Simplex& s, Vec2& d) noexcept {
    switch (s.count) {
    case 2:  return simplex_line(s, d);
    case 3:  return simplex_triangle(s, d);
    default: d = -s.point[0].diff; return false;   // 1 点のとき
    }
}

} // namespace detail
```

## 20.4 本体の実装

```cpp
// collision/narrow/gjk.h（続き）

enum class GjkStatus {
    intersecting,     // 交差している。simplex は原点を含む三角形
    separated,        // 交差していない
    not_converged,    // 反復上限に達した（判定できず）
};

struct GjkResult {
    GjkStatus status{};
    Simplex   simplex{};
    int       iterations{};
};

inline constexpr int gjk_max_iterations = 32;

template <SupportShape A, SupportShape B>
[[nodiscard]] GjkResult gjk(const A& a, const B& b) noexcept {
    // 初期方向。何でもよいが、形状の位置関係から選ぶと収束が速い
    Vec2 d = support_point(b, Vec2{1.0f, 0.0f}) - support_point(a, Vec2{-1.0f, 0.0f});
    if (length_squared(d) < min_length2) d = Vec2{1.0f, 0.0f};

    Simplex s{};
    s.push(support_diff(a, b, d));
    d = -s.point[0].diff;

    for (int iter = 0; iter < gjk_max_iterations; ++iter) {
        // 原点がシンプレックス上に乗っている
        if (length_squared(d) < min_length2) {
            return GjkResult{.status = GjkStatus::intersecting,
                             .simplex = s, .iterations = iter};
        }

        const MinkowskiPoint p = support_diff(a, b, d);

        // 原点より手前でしか点が取れない → 分離軸が見つかった
        if (dot(p.diff, d) < 0.0f) {
            return GjkResult{.status = GjkStatus::separated,
                             .simplex = s, .iterations = iter};
        }

        // 進展がない（同じ点が返ってきた）→ これ以上原点に近づけない
        if (detail::is_duplicate(s, p.diff)) {
            return GjkResult{.status = GjkStatus::separated,
                             .simplex = s, .iterations = iter};
        }

        s.push(p);

        if (detail::handle_simplex(s, d)) {
            return GjkResult{.status = GjkStatus::intersecting,
                             .simplex = s, .iterations = iter};
        }
    }

    return GjkResult{.status = GjkStatus::not_converged,
                     .simplex = s, .iterations = gjk_max_iterations};
}

// 交差判定だけが欲しい場合
template <SupportShape A, SupportShape B>
[[nodiscard]] bool overlaps_gjk(const A& a, const B& b) noexcept {
    return gjk(a, b).status == GjkStatus::intersecting;
}

} // namespace collision
```

### 初期方向の選び方

`support_point(b, +X) - support_point(a, -X)` という式を使っている。これは大雑把に「B から A へ向かう向き」を表す。

初期方向は何でも正しく動くが、**良い初期方向を選ぶと反復回数が減る**。形状の位置関係に沿った向きから始めれば、原点へ早く近づける。

中心を使う実装もある（`b.center - a.center`）が、`SupportShape` コンセプトは中心を要求していない。**サポート関数だけで済む形にした**のは、コンセプトの要求を増やさないためである。

### 三つの終了状態

`GjkStatus` が三値である点が重要である。第 7.5 節で述べた「交差していない」と「計算できなかった」の区別が、ここで具体的な形をとる。

`not_converged` を `separated` として扱ってはいけない。**すり抜けの原因になる**（第 18.5 節と同じ議論）。呼び出し側に判断させる。

### GJK と SAT のどちらを使うか

同じ問題を解く二つのアルゴリズムが揃った。使い分けの指針を示す。

| 項目 | SAT（第 11〜13 章） | GJK（この章） |
|---|---|---|
| 扱える形状 | 頂点と辺を持つ凸多角形のみ | **任意の凸形状**（円・楕円も可） |
| 計算量 | 軸の本数 × 頂点数（決定的） | 反復回数 × 頂点数（入力依存） |
| 離れている場合 | 早期脱出が効く | **さらに速い**（数反復で決着） |
| 深く重なっている場合 | 変わらない | 反復が増える |
| 貫通深度 | そのまま得られる | **EPA が別途必要**（第 22 章） |
| 実装の複雑さ | 低い | 高い |
| 混合ペア（円 vs 多角形） | 不可 | **可能** |

**形状が多角形に限られ、貫通深度が要るなら SAT が素直である。** 実装が単純で、深度が副産物として得られる。

**形状の種類が多様なら GJK である。** 円、カプセル、楕円、そしてそれらの組み合わせを一つのコードで扱える。形状ペアごとに実装を書く必要がない。

実務では**両方持つ**のが普通である。多角形どうしは SAT、円が絡むペアは GJK、というように使い分ける。本書もそうしている。

### 反復回数の見積もり

GJK の反復回数は、理論上はミンコフスキー差の頂点数で抑えられる。2D では `n + m`（両形状の頂点数の和）程度である。

実際には、**もっとずっと少ない**。

- **明らかに離れている**：1〜2 反復。最初のサポート点で分離軸が見つかる
- **接近しているが分離**：3〜5 反復
- **交差している**：3〜6 反復。原点を囲む三角形が早く見つかる

平均すると 4〜5 反復程度になる。1 反復あたりサポート写像を 2 回呼ぶので、**判定 1 回で 8〜10 回のサポート写像呼び出し**が目安である。

20.6 節で実際に測る。**見積もりと実測を照らし合わせる**のは、性能を理解するうえで重要な習慣である。

## 20.5 終了条件と無限ループの防止

### 重複サポート点の検出

```cpp
namespace detail {

[[nodiscard]] inline bool
is_duplicate(const Simplex& s, Vec2 p) noexcept {
    for (std::uint32_t i = 0; i < s.count; ++i) {
        if (distance_squared(s.point[i].diff, p) < min_length2) return true;
    }
    return false;
}

} // namespace detail
```

**これが GJK で最も重要な安全弁である。**

同じサポート点が返ってきたということは、その方向にはもう進めないということである。ミンコフスキー差の同じ頂点を何度も選び続けても、原点には近づかない。

この検出がないと、GJK は**同じ二点や三点を行き来し続けて反復上限まで回る**。正しさは保たれる（上限で `not_converged` になる）が、無駄が大きい。そして `not_converged` を返してしまうと、呼び出し側が困る。

閾値に `min_length2`（第 5.9 節）を使っている。ミンコフスキー差の空間での距離なので、元の形状のスケールと同じ単位である。**単位系から決めた閾値をそのまま使える。**

### 反復上限

```cpp
inline constexpr int gjk_max_iterations = 32;
```

2D の GJK は、理論上は形状の頂点数程度の反復で収束する。頂点数の上限が 8（第 13.1 節）なので、32 回あれば十分な余裕がある。

**それでも上限を置く。** 浮動小数点の誤差で理論どおりに収束しないことがあるからである。無限ループは、ゲームでは即座にフリーズとして現れる。最も避けたい事故である。

第 18.2 節の保守的前進でも同じ配慮をした。**反復アルゴリズムには必ず上限を置く**、というのが本書の規則である。

## 20.6 `/fp:fast` と反復アルゴリズム

### 収束判定が振動する

ここで、第 4 章で予告した問題が具体的な形で現れる。

GJK の反復は、次の二つの判定で終わる。

- `dot(p.diff, d) < 0.0f` … 分離軸が見つかった
- `is_duplicate(s, p.diff)` … 進展がない

**どちらも、値が境界付近にあるときに揺れる。**

`dot(p.diff, d)` がちょうどゼロ付近のとき、`/fp:fast` の下では計算順序や FMA の融合によって符号が変わりうる。ある反復では負、次の反復では正、という振動が起きる。

そうなると、シンプレックスの更新が行ったり来たりして、収束しない。反復上限まで回って `not_converged` になる。

### 判断基準に照らす

第 4.6 節で決めたルールを再掲する。

> **戻すのは「回数が少なく、かつ判定を誤ると制御フローが壊れる箇所」だけ**

GJK の収束判定は、この条件に該当する。

- **回数が少ない**：反復は最大 32 回。判定は 1 反復あたり 2 回
- **判定を誤ると制御フローが壊れる**：振動して収束しない、あるいは誤った結論を返す

一方、`support_point` の内積計算は該当しない。**多角形の頂点数だけ呼ばれ、値がわずかにずれても結論は変わらない。** ここを `precise` にすると、GJK 全体が遅くなる。

### `precise` 領域として囲う

```cpp
// collision/narrow/gjk.h（続き）

namespace detail {

#pragma float_control(precise, on, push)

// GJK の収束判定。/fp:fast の下では符号が揺れて振動しうるため
// precise で守る（第 4.6 節の判断基準を適用）。
// 反復あたり数回しか呼ばれないので、コストは無視できる。
__declspec(noinline)
[[nodiscard]] inline bool
is_separating(Vec2 support, Vec2 direction) noexcept {
    return dot(support, direction) < 0.0f;
}

__declspec(noinline)
[[nodiscard]] inline bool
no_progress(const Simplex& s, Vec2 p) noexcept {
    for (std::uint32_t i = 0; i < s.count; ++i) {
        const Vec2  d  = s.point[i].diff - p;
        const float d2 = d.x * d.x + d.y * d.y;
        if (d2 < min_length2) return true;
    }
    return false;
}

#pragma float_control(pop)

} // namespace detail
```

本体の判定をこれらに置き換える。

```cpp
        if (detail::is_separating(p.diff, d)) {
            return GjkResult{.status = GjkStatus::separated, ...};
        }
        if (detail::no_progress(s, p.diff)) {
            return GjkResult{.status = GjkStatus::separated, ...};
        }
```

`__declspec(noinline)` を併用しているのは、第 4.6 節で述べた「インライン展開で pragma が漏れる」問題への対処である。

### コストを測る

`precise` にした効果とコストは、必ず実測する（第 4.6 節）。

```cpp
            transformed_poly(random_convex_polygon_checked(rng, 3 + (i % 6)),
                             {rng.uniform(-2.0f, 2.0f), rng.uniform(-2.0f, 2.0f)},
                             rng.uniform(0.0f, 6.28f)));
    }

    volatile int sink = 0;
    const auto t0 = std::chrono::steady_clock::now();
    int total_iter = 0;
    for (const auto& [a, b] : pairs) {
        const auto r = collision::gjk(a, b);
        total_iter += r.iterations;
        sink += (r.status == collision::GjkStatus::intersecting) ? 1 : 0;
    }
    const auto t1 = std::chrono::steady_clock::now();

    Logger::WriteMessage(std::format(
        "GJK {} 件: {:.1f} ms, 平均反復 {:.2f} 回\n",
        pairs.size(),
        std::chrono::duration<double, std::milli>(t1 - t0).count(),
        static_cast<double>(total_iter) / static_cast<double>(pairs.size())).c_str());
}
```

**平均反復回数を記録している**のが重要である。`precise` を外したときにこれが増えるなら、それは振動が起きている証拠である。速度だけを見ていては分からない。

## 20.7 テスト：SAT をリファレンスにする

### 大量ランダム比較

第 11.6 節で導入したリファレンス比較を、この章の主役に適用する。**SAT（第 13 章）が GJK の答え合わせをする。**

```cpp
// test_gjk.cpp
TEST_CLASS(GjkVsSat) {
public:
    TEST_METHOD(凸多角形の交差判定がSATと一致すること) {
        Rng rng(1410);
        int mismatch = 0, total = 0, intersecting = 0;

        for (int i = 0; i < 100000; ++i) {
            const auto a = transformed_poly(random_convex_polygon_checked(rng, 3 + (i % 6)),
                {rng.uniform(-1.5f, 1.5f), rng.uniform(-1.5f, 1.5f)}, rng.uniform(0.0f, 6.28f));
            const auto b = transformed_poly(random_convex_polygon_checked(rng, 3 + (i % 6)),
                {rng.uniform(-1.5f, 1.5f), rng.uniform(-1.5f, 1.5f)}, rng.uniform(0.0f, 6.28f));

            const bool by_sat = collision::overlaps(a, b);
            const bool by_gjk = collision::overlaps_gjk(a, b);

            ++total;
            if (by_sat) ++intersecting;
            if (by_sat != by_gjk) ++mismatch;
        }

        Logger::WriteMessage(std::format(
            "GJK vs SAT: 不一致 {} / {} ({:.4f}%), 交差 {}\n",
            mismatch, total, 100.0 * mismatch / total, intersecting).c_str());

        // 境界近傍では判定が割れうる（第 3.5 節の原則 3）。
        // 割合で管理し、閾値を超えたら失敗とする
        Assert::IsTrue(mismatch * 10000 < total, L"不一致が 0.01% を超えている");
        Assert::IsTrue(intersecting > total / 10, L"交差した事例が少なすぎる");
    }
};
```

**一致率で管理している**のが第 3.5 節の原則 3 の実践である。境界ぎりぎりの配置では、二つのまったく異なるアルゴリズムが違う結論を出しうる。それを異常とはみなさない。

閾値を 0.01% に置いた根拠を述べておく。**筆者が検証した範囲では、凸性を厳密に保証した入力に対して不一致はゼロだった。** それでも閾値をゼロにしないのは、環境やコンパイラの違いで境界の揺れ方が変わりうるからである。

> **不一致が出たときの調べ方**
> 不一致は、たいてい「境界近傍だから」ではなく「入力が凸でない」ことに起因する。第 13.1 節で述べたとおり、局所的な外積だけを見る凸性判定は不十分である。
>
> 不一致が閾値を超えたら、まず入力の凸性を `is_convex_ccw` で確かめてほしい。次に、ミンコフスキー差を陽に構築して原点を含むかを直接調べる。それが最終的な判定基準になる。

## この章のまとめ

- **GJK は、ミンコフスキー差を構築せずに「原点が含まれるか」を判定する**
- サポート写像だけを通して形状に触れるので、形状の種類を知らずに動く
- 戦略：原点を囲む三角形（単体）を見つけようとする
- **`dot(p, d) < 0` なら分離軸が見つかった。** 離れている形状ほど早く決着する
- 単体の場合分けは「最新の点 `A` を基準に考える」。辺 `BC` を調べなくてよい
- 2D では三重積の代わりに `perpendicular` と符号調整で済む（3D では三重積が要る）
- **重複サポート点の検出が最重要の安全弁。** ないと無駄に反復上限まで回る
- 反復上限を必ず置く。`not_converged` を `separated` として扱わない
- **収束判定を `precise` で守る**（第 4.6 節の判断基準）。`support_point` は戻さない
- 平均反復回数を記録する。`precise` を外して増えるなら振動している証拠
- テストは SAT をリファレンスに一致率で管理する。円と点は SAT では扱えない領域

### 落とし穴と練習問題

**落とし穴 1：重複検出を入れ忘れる。**　反復上限まで回り、`not_converged` が多発する。

**落とし穴 2：`not_converged` を「交差なし」と扱う。**　すり抜けの原因になる。

**落とし穴 3：単体の法線の向き。**　「三角形の外側」に揃える。`dot(ab_perp, ac) > 0` なら反転する。

---

**練習問題 20-1**　重複検出を外して 20.6 節の反復回数テストを走らせよう。平均反復回数はどれだけ増えるだろうか。`not_converged` の割合はどうか。

**練習問題 20-2**　初期方向を `Vec2{1,0}` に固定してみよう。平均反復回数はどう変わるか。良い初期方向を選ぶ価値を実測してほしい。

**練習問題 20-3**　`simplex_line` と `simplex_triangle` を、`perpendicular` ではなく三重積で書き直そう。結果が一致することを確認し、速度を比べる。3D への布石になる。

**練習問題 20-4**　楕円（練習問題 19-1）どうしの判定を GJK で行ってみよう。SAT では不可能な組み合わせである。反復回数は多角形より増えるだろうか。

**練習問題 20-5**（発展）　GJK が `not_converged` を返す入力を意図的に作ってみよう。極端に細長い形状、極端にスケールの違う形状、ほぼ接している配置。見つかったら、反復上限を増やすと解決するか、それとも構造的な問題かを調べてほしい。
