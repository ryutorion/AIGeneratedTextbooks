# 第 40 章　テスト戦略の総まとめ ― `/fp:fast` の下で品質を守る

> **この章のゴール**
> 39 章かけて書いてきたテストを、いったん分類し直す。**何を、どういう種類のテストで守ってきたのか。**
>
> そして本書で最も実務的な成果物を二つ作る。**許容誤差の一覧表**と **`precise` 領域の棚卸し**である。各章で個別に決めてきた閾値を 1 箇所に集めると、そこに一貫した設計思想があったこと——そして一箇所だけ揺れていたこと——が見えてくる。
>
> 最後に、CI 用の「保険ビルド」を用意する。**`/fp:precise` ＋ FTZ/DAZ 無効**の構成でもテストが通ることを確認すれば、バグの原因を切り分けられる。

## 40.1 本書で書いたテストの分類

### 六つの種類

| 種類 | 何を検証するか | 落ちたときの意味 | 主な章 |
|---|---|---|---|
| **単位テスト** | 1 回の呼び出しの入出力 | その関数が壊れている | 第 6〜10 章 |
| **性質テスト** | 入力によらず成り立つ関係 | 設計の仮定が崩れている | 全章 |
| **等価性テスト** | 二つの実装が同じ答えを出すこと | どちらかが壊れている | 第 11・21・28・30〜32 章 |
| **シナリオテスト** | 時系列の入力に対するイベント列 | 状態機械が壊れている | 第 33・38 章 |
| **回帰テスト** | 過去に壊れたケース | 同じバグが再発した | 第 13・22・38 章 |
| **性能テスト** | 決定論的な「仕事量」 | 計算量が悪化した | 第 29〜32 章 |

**この順に、守備範囲が広く・値への依存が弱くなる。**

単位テストは「この入力ならこの出力」という最も具体的な形であり、`/fp:fast` の下で最も壊れやすい。性質テストは「値が何であれ、この関係は成り立つ」という形なので、揺れに強い。

### 数で見る

本書のテストを種類別に数えると、おおよそ次の比率になる。

```
性質テスト     ████████████████████  約 45%
単位テスト     ██████████            約 22%
等価性テスト   ████████              約 18%
性能テスト     ████                  約  8%
シナリオ・回帰 ███                   約  7%
```

**性質テストが半分近くを占める。** これは偶然ではなく、`/fp:fast` を選んだ結果として必然的にそうなった。次節でその理由を整理する。

## 40.2 性質ベーステストがなぜ本書の主力なのか

### 値は揺れるが、性質は揺れない

`/fp:fast` の下では、同じ関数がビルド設定・インライン展開・命令選択によって違う値を返す。**「0.5 になること」を検証するテストは、原理的に脆い。**

**一方、次のような関係は、値がどう揺れても成り立つ。**

- 距離は対称である：`distance(A, B) == distance(B, A)`
- 法線は単位長である：`length(n) == 1`
- 離すほど距離は増える：`distance(t)` は `t` について単調
- 二度押し出しても結果は変わらない：`f(f(x)) == f(x)`

**これらは浮動小数点の丸めとは無関係な、構造的な事実である。** 誤差が乗っても「対称であること」は変わらない。

### 四つの型

本書で使った性質は、ほぼ四種類に分類できる。

**型 1：対称性。** 引数を入れ替えると、結果も対応して入れ替わる。

```cpp
// 第 14.6 節：A vs B の法線と B vs A の法線は、符号が反転した関係にある
expect_near(-mab->normal, mba->normal, 1.0e-4f, 1.0e-4f);
```

**最も強く、最も安く書ける性質である。** 実装の非対称なバグ——「A 側だけ centroid で符号を調整している」といった類——を確実に捕まえる。第 12 章の SAT で符号調整を除去できたのは、このテストがあったからである。

**型 2：不変条件。** 出力が常に満たす条件。

```cpp
Assert::IsTrue(m.point_count >= 1);                    // 第 14 章
expect_near(1.0f, length(m.normal), 1.0e-5f, 1.0e-5f); // 法線は単位長
Assert::IsTrue(contact.depth >= 0.0f);                 // 深さは非負
assert(contains(node.box, combine(a.box, b.box)));     // 第 32.6 節：親は子を内包
```

**第 32 章の木では、これが唯一の実用的な検証手段だった。** 木の形は入力に依存して変わるので、期待値を書けない。**不変条件だけが書ける。**

**型 3：単調性。** 入力を一方向へ動かすと、出力も一方向へ動く。

```cpp
// 第 21.6 節：物体を離していくと、距離は単調に増える
Assert::IsTrue(r.distance > prev - 1.0e-4f, L"距離が単調でない");

// 第 30.4 節：座標が増えるとセル番号は減らない
Assert::IsTrue(ca.x <= cb.x, L"セル写像が単調でありません");
```

**第 30.3 節では、単調性が「取りこぼさないこと」の証明そのものだった。** 性質テストが、性能のためのデータ構造の正しさを保証している。

**型 4：冪等性・保存則。** 二度やっても変わらない、あるいは総量が変わらない。

```cpp
// 第 36.6 節：運動量は保存し、エネルギーは増えない
expect_near(p0, p1, 1.0e-4f, 1.0e-4f);
Assert::IsTrue(k1 <= k0 * 1.0001f, L"エネルギーが増えました");
```

**保存則は、符号の間違いを一発で捕まえる。** 運動量保存は式の形から自動的に成り立つが、**エネルギーが増えないことは自明ではない**。だから価値がある。

### 性質テストの限界

**万能ではない。** 「常にゼロを返す実装」は、対称性も不変条件も単調性も満たしてしまう。

**性質テストは単位テストの代わりではなく、補完である。** 少数の具体例（手計算で確かめた値）を単位テストで固定し、その周りの広い空間を性質テストで守る。

**本書の第 22 章で EPA の法線の符号が反転していたバグは、手計算例を作ったときに見つかった。** 対称性のテストは通っていた——符号が両方とも反転していれば対称だからである。

## 40.3 ランダム入力とシードの記録

### シードを固定し、シードを変える

```cpp
// 第 3.4 節の Rng。時刻でシードしない
for (std::uint32_t seed = 0; seed < 300; ++seed) {
    Rng rng(4200 + seed);
    // ... テスト本体
}
```

**「シードを固定する」と「入力の多様性を確保する」は両立する。** シードを 0, 1, 2, … と振れば、決定論的でありながら 300 通りの入力を試せる。

**落ちたときにシードが分かる形にする**のが要点である。

```cpp
Assert::IsTrue(condition,
    std::format(L"seed = {} で失敗", 4200 + seed).c_str());
```

### 失敗ケースの最小化

ランダムなテストが落ちたとき、入力は往々にして複雑である。**頂点 47 個の多角形どうしの判定が失敗した、と言われても手が出ない。**

**縮小（shrinking）**は、失敗を保ったまま入力を単純にしていく作業である。

```cpp
// テスト補助：頂点を 1 個ずつ減らしてみて、まだ失敗するなら採用する
template <class Fail>
[[nodiscard]] ConvexPolygon shrink(ConvexPolygon p, Fail still_fails) {
    bool changed = true;
    while (changed && p.count > 3) {
        changed = false;
        for (std::size_t i = 0; i < p.count; ++i) {
            ConvexPolygon q = removed_vertex(p, i);
            if (is_convex_ccw(q) && still_fails(q)) { p = q; changed = true; break; }
        }
    }
    return p;
}
```

**第 26.2 節の「15 軸が必要な最小反例」は、この作業の産物である。** ランダム探索で見つかった 4,282 件の失敗例から、単位立方体を 5 度ずつ二回転させただけの、手で書ける配置まで削った。

**縮小した反例は、そのまま回帰テストになる。** 「ランダムに 20 万回試す」テストより、「この 1 ケースを検証する」テストのほうが速く、意味が明快で、落ちたときに原因が分かる。

## 40.4 退化ケース・カタログ

**ランダム入力は退化ケースをまず生成しない。** 「ちょうど平行」「長さちょうどゼロ」は、確率的にはほぼ起きない。**明示的に列挙して並べる。**

| 分類 | 具体例 | 主な影響先 | 対策 |
|---|---|---|---|
| **ゼロ長** | 長さ 0 のベクトル、面積 0 の三角形 | 正規化、法線計算 | `try_normalize` が `nullopt`（第 6.3 節） |
| **同一点** | 二つの頂点が完全に一致 | GJK のシンプレックス、外積 | 体積・面積の閾値（第 28.5 節） |
| **平行** | 平行な辺、平行な線分 | SAT の軸、線分間最近接 | 外積がゼロの分岐（第 25.4・26.5 節） |
| **接触ちょうど** | 距離ぴったり 0、角で接する | 境界の開閉 | テストで境界を明示（第 30.4 節） |
| **極大スケール** | 座標 10⁶、サイズ 10⁻³ | 桁落ち | 相対誤差、原点近傍へ移す（第 42.3 節） |
| **極小スケール** | サイズ 10⁻⁶ | 閾値割れ | 単位系の見直し（第 5.9 節） |
| **非正規化数** | 10⁻⁴⁰ | 性能、FTZ でのゼロ化 | 閾値クランプ（第 35.5 節） |
| **`NaN`** | 未初期化、0/0 | 静かに伝播する | ビット検査（第 4.5・37.5 節） |
| **`-0.0`** | 符号付きゼロ | 比較は等しいが `1/x` の符号が違う | 除算の前に符号を確定 |
| **空・単数** | 物体 0 個、頂点 1 個 | ループ境界 | 早期リターン（第 31.5 節） |

**このカタログは、新しい関数を書くたびに上から順に当てる。** 10 項目のうち関係するものは 3〜4 個しかないが、**当てはめる作業そのものが仕様の明確化になる。**

```cpp
// 退化ケースを一箇所にまとめておくと、新しい関数にも流用できる
namespace collision_tests::degenerate {

inline const std::vector<Vec2> vectors = {
    Vec2{0.0f, 0.0f},                      // ゼロ
    Vec2{-0.0f, -0.0f},                    // 負のゼロ
    Vec2{1.0e-40f, 0.0f},                  // 非正規化数
    Vec2{1.0e20f, 1.0e20f},                // 極大
    Vec2{1.0e-20f, 0.0f},                  // 極小
    Vec2{std::numeric_limits<float>::infinity(), 0.0f},
};

} // namespace collision_tests::degenerate
```

**`NaN` を含めるかは判断が要る。** `/fp:fast` は「入力に `NaN` は来ない」と仮定してよい前提でコンパイルする（第 4.5 節）ので、`NaN` を渡したときの挙動は未定義に近い。**本書は「`NaN` を入れない」を契約とし、入り口で検査する**方針を採る（第 43.3 節）。

## 40.5 許容誤差の一覧表

**本書で使ったすべての閾値を、根拠つきで 1 箇所に集める。** これが本章で最も実務的な成果物である。

### 群 A：単位系から決まる設計上の閾値

```cpp
// collision/config/tolerance.h ― 第 5.9 節で確立、以降 30 章で使い続けた
inline constexpr float min_length   = 1.0e-4f;   // 0.1 mm
inline constexpr float min_length2  = min_length * min_length;   // 1e-8
inline constexpr float min_speed    = 1.0e-3f;   // 1 mm/s
inline constexpr float contact_slop = 1.0e-3f;   // 1 mm
```

| 定数 | 値 | 根拠 | 初出 | 使用章 |
|---|---:|---|---|---|
| `min_length` | 1e-4 | 1 単位 = 1 m として 0.1 mm。これ以下の長さは意味を持たない | 5.9 | 22 章 |
| `min_length2` | 1e-8 | `min_length²`。非正規化域（1.18e-38）から 30 桁離れている | 5.9 | 20 章 |
| `min_speed` | 1e-3 | 1 mm/s。60 fps で 1 フレーム 0.017 mm。目に見えない | 5.9 | 5 章 |
| `contact_slop` | 1e-3 | 1 m の物体に対して 0.1%。見えないがゼロでない | 5.9 | 12 章 |

**この 4 個だけで、本書の 30 章以上をまかなっている。** 単位系を最初に決めた見返りである。

### 群 B：アルゴリズム内部の判定閾値

| 用途 | 値 | 根拠 | 節 |
|---|---:|---|---|
| `is_convex_ccw` の許容 | 1e-6 | 頂点座標のスケール（〜10）に対する相対 | 13.1 |
| `select_faces` の許容差 | 1e-4 | フレーム間で参照面が入れ替わらない大きさ | 14.3 |
| `gjk_distance` の tolerance | 1e-6 | **相対**誤差なのでスケールに依存しない | 21.1 |
| `epa_tolerance` | 1e-5 | 収束時の差は桁落ちの塊。緩めに取る | 22.3 |
| `sat3_epsilon` | 1e-5 | スケール相対の誤差項として使う | 26.4 |
| 四面体の体積閾値 | `min_length2 · min_length` | 次元が長さ³。1e-12 | 28.5 |
| `restitution_threshold` | 1.0 m/s | `g·dt ≒ 0.17 m/s` の数倍 | 36.2 |
| `max_linear_correction` | 0.2 m | 60 fps で 12 m/s 相当。押し戻しの上限 | 34.3 |
| `skin_width` | 0.02 m | 判定の境界に立たないための厚み | 38.2 |

**「相対」と書いてあるものだけが、スケールに依存しない。** 残りは「1 単位 = 1 m」という前提の上に立っている。**座標系を変えたら、この列を見直す必要がある。**

### 群 C：テストの許容誤差

```cpp
// 第 3.4 節
inline constexpr float default_abs_tol = 1.0e-6f;
inline constexpr float default_rel_tol = 1.0e-5f;
```

| 検証対象 | 絶対 | 相対 | 理由 | 節 |
|---|---:|---:|---|---|
| 法線の単位長 | 1e-5 | 1e-5 | 正規化 1 回ぶんの誤差 | 6.4, 14.4 |
| 法線の向き | 1e-4 | 1e-4 | 正規化 ＋ 数回の演算 | 14.6 |
| 距離（解析解との比較） | 1e-4 | 1e-4 | 数十演算の累積 | 21.6 |
| 深さ | 1e-3 | 1e-2 | **差の計算で桁落ちする** | 14.6 |
| 最近接点の座標 | 1e-2 | 1e-3 | **面に沿って滑るので値が定まりにくい** | 21.6 |
| 積分（自由落下） | `½·|g|·dt·t` の 1.05 倍 | — | 理論誤差の式そのもの | 35.6 |

**この表の並びに、一貫した傾向がある。**

> **パイプラインの下流ほど、許容誤差は緩くなる**
> 法線（1e-5）→ 距離（1e-4）→ 深さ（1e-3）→ 最近接点（1e-2）。**三桁の開きがある。**
>
> 理由は二つある。**一つは誤差の累積**である。下流ほど多くの演算を通っている。
>
> **もう一つは、値そのものが定まりにくくなること**である。二つの面が平行に接触しているとき、「最近接点」は面の上のどこでもよい。実装が変われば違う点を返す。**これは誤差ではなく、答えが一意でないだけである。**
>
> **許容誤差を決めるときは、「誤差がどれだけ乗るか」と「答えが一意か」を分けて考える。** 後者に対して厳しい許容誤差を設定すると、正しい実装が落ちる。

### 一つだけ揺れていたもの

表を作って気づいたことがある。**`is_convex_ccw` の 1e-6 だけが、根拠の書き方が違う。**

他はすべて「単位系から」か「相対誤差だから」で説明できるのに、これは「頂点座標のスケールが 10 くらいだから」という**入力の性質への暗黙の依存**である。座標が 10,000 のスケールになると、この閾値は厳しすぎて正しい凸多角形を弾く。

```cpp
// 改善：スケール相対にする
const float scale = max_abs_coordinate(p);
if (dot(p.vertex[k], n) - off > 1.0e-6f * scale) return false;
```

**一覧表を作る本当の価値は、こういう「一つだけ違うもの」が目に飛び込んでくることである。** 各章で個別に決めているときは気づけなかった。

## 40.6 `precise` 領域の一覧と棚卸し

### 本書で `precise` に戻した箇所は、4 つだけである

第 4.6 節で「まず戻さない。問題が出たら戻す」という方針を立てた。**43 章分の実装を通して、実際に戻したのは次の 4 箇所だけだった。**

| 関数 | 章 | 何が壊れるか | 呼び出し頻度 |
|---|---|---|---|
| `can_advance` | 18.5 | 前進量がゼロに潰れて**無限ループ** | 反復あたり 1 回 |
| GJK の収束判定 | 20.5 | 符号が揺れて**振動** | 反復あたり 1 回 |
| `distance_converged` | 21.3 | 境界付近で**振動** | 反復あたり 1 回 |
| EPA の収束判定 | 22.4 | 収束を検出できず**反復上限まで回る** | 反復あたり 1 回 |

**四つとも「反復の収束判定」である。** これは偶然ではない。

> **収束判定だけが `precise` を必要とする理由**
> 収束判定は「ほぼ等しい二つの値の差が、閾値より小さいか」を見る。**収束が近いほど、差は桁落ちの塊になる**（第 4.2 節）。そこに再結合や FMA 融合が入ると、符号が揺れる。
>
> そして収束判定は**制御フローを決める**。値が少しずれるだけなら次の反復で吸収されるが、**「終わるか終わらないか」の判断がずれると、無限ループか早期終了になる。**
>
> 第 4.6 節の判断基準——**「呼び出し回数が少なく、制御フローが壊れる箇所」**——を素直に適用すると、収束判定だけが残る。**43 章書いても、基準は一度も変わらなかった。**

### 戻さなかったもの

**戻すか検討して、戻さなかった箇所も記録しておく。**

| 候補 | 章 | 戻さなかった理由 |
|---|---|---|
| `try_normalize` | 6.4 | 呼び出し回数が最も多い。`rsqrt` の誤差は実測で許容範囲 |
| 逐次力積ソルバ本体 | 37.5 | 400 回／フレーム。反復法は小さな誤差に自己修復的 |
| `NaN` 検出 | 4.5 | **ビット検査に置き換えた。** 浮動小数点演算を通らないので `precise` が不要 |
| 分散の計算（掃引軸） | 31.3 | 桁落ちするが、必要なのは**大小の比較だけ** |

**最後の二つが示唆的である。** `precise` に戻す以外の解決策——**演算を通さない、あるいは精度が要らない形に問題を組み替える**——のほうが、たいてい優れている。

### コストを測る

```cpp
// 第 4.6 節で用意した計測。40 章の時点で改めて回す
TEST_METHOD(precise 領域の総コストを測る) {
    const double with    = bench::measure_ms([]{ run_gjk_workload(); }, 100);
    const double without = bench::measure_ms([]{ run_gjk_workload_fast(); }, 100);
    Logger::WriteMessage(std::format(
        "precise あり {:.3f} ms / なし {:.3f} ms（{:+.1f}%）\n",
        with, without, (with / without - 1.0) * 100.0).c_str());
}
```

**4 箇所すべてが「反復あたり 1 回」なので、総コストは数パーセントに収まる。** GJK の 1 反復にはサポート写像の呼び出しとシンプレックスの処理が含まれ、収束判定はそのごく一部でしかない。

**これが「`/fp:fast` を選びつつ、壊れる箇所だけ守る」という戦略が成立した理由である。** 守るべき箇所が、たまたま最も安い箇所だった。

## 40.7 保険としての `/fp:precise` ＋ FTZ/DAZ 無効ビルド

### 何のための構成か

**通常の検証手段ではない。バグの切り分け道具である**（第 3.6 節で予告した）。

ある日、テストが落ちる。原因は三つに分かれる。

1. **普通のロジックのバグ**
2. **`/fp:fast` に起因するバグ**（再結合、FMA、`rsqrt` 近似）
3. **FTZ/DAZ に起因するバグ**（非正規化数のゼロ化）

**この三つは、症状だけでは区別できない。** そこで構成を分けて走らせる。

| 構成 | `/fp:` | FTZ/DAZ | 落ちたら |
|---|---|---|---|
| **Release**（本番） | `fast` | 有効 | — |
| **Release-Precise** | `precise` | 有効 | ① か ③ |
| **Release-Strict** | `precise` | **無効** | ① のみ |

**三つとも落ちるならロジックのバグ。** Release だけ落ちるなら `/fp:fast` 由来。Release と Release-Precise が落ちて Release-Strict が通るなら FTZ/DAZ 由来である。

### 構成の作り方

```xml
<!-- collision_tests.vcxproj への追加。既存の Release をコピーして 2 つ作る -->
<PropertyGroup Condition="'$(Configuration)'=='Release-Strict'">
  <FloatingPointModel>Precise</FloatingPointModel>
</PropertyGroup>
```

FTZ/DAZ は実行時の設定なので、プロジェクトのマクロ定義で切り替える。

```cpp
// tests/main.cpp の TEST_MODULE_INITIALIZE（第 5.6 節）
TEST_MODULE_INITIALIZE(SetupFloatEnvironment) {
#if !defined(COLLISION_DISABLE_FTZ)
    collision::enable_flush_to_zero();       // 本番と同じ状態にする
#endif
}
```

### CI での運用

**毎回三構成走らせる必要はない。**

```
プルリクエスト時：Release のみ（速い）
毎晩：Release / Release-Precise / Release-Strict の三構成
リリース前：三構成 ＋ Debug
```

**「毎晩の三構成」で差分が出たら、その時点で調べる。** 差が出ないうちは、`/fp:fast` と FTZ/DAZ が悪さをしていない証拠になる。

**そして差が出たときに、初めてこの構成の価値が分かる。** 用意しておくコストは低く、必要になったときに用意するのは間に合わない。

## 40.8 コードカバレッジの見方

### 見るべきもの、見なくてよいもの

Visual Studio の Enterprise エディションにはカバレッジ計測が付いている。無償で使うなら OpenCppCoverage という選択肢もある。

**カバレッジは「テストが通っていない行」を見つける道具である。「テストが十分かどうか」の指標ではない。**

```cpp
// この関数はカバレッジ 100% にできるが、それで正しさは保証されない
[[nodiscard]] float bad_distance(Vec2 a, Vec2 b) noexcept {
    return length(a - b) * 2.0f;      // 2 倍している。テストは通るかもしれない
}
```

**見るべきなのは「一度も通っていない分岐」である。**

- 早期リターンのうち、どれかがテストされていない
- 退化ケースの分岐が実行されていない（40.4 節のカタログが足りない）
- エラー経路（`std::expected` の失敗側）が一度も通っていない

**特に三つ目が多い。** 第 33.4 節の `buffer_too_small` のような経路は、意識して書かないとテストされない。

### 数字を目標にしない

**「カバレッジ 80% を目標にする」は失敗する。** 数字を上げるだけのテスト——呼ぶだけで何も検証しないテスト——が書かれるようになる。

**代わりに「未到達の分岐を毎回眺める」という運用にする。** 数は増えても減ってもよい。**中身を見ることに意味がある。**

本書のコードで言えば、**第 32 章の木の回転**が最もカバレッジを取りにくい。左回転・右回転・二重回転の各分岐に到達するには、特定の形の木を作る必要がある。**カバレッジを見て初めて「回転の片方しかテストされていない」と気づく**——これがこの道具の正しい使い方である。

## この章のまとめ

- テストは六種類：**単位・性質・等価性・シナリオ・回帰・性能**。下へ行くほど値への依存が弱い
- **性質テストが約 45% を占める。** `/fp:fast` を選んだ必然的な結果である
- 性質は四つの型：**対称性・不変条件・単調性・保存則**
- 対称性が最も安く強い。**不変条件は、期待値が書けない木のような構造で唯一の手段**
- 単調性は第 30.3 節で「取りこぼさないこと」の証明そのものになった
- **保存則は符号の間違いを一発で捕まえる。** 特に「エネルギーが増えない」
- **性質テストは単位テストの代わりではない。** ch22 の符号バグは対称性テストを通り抜けた
- シードは固定しつつ 0, 1, 2, … と振る。**落ちたときにシードが分かる形に**
- **失敗ケースは縮小する。** 第 26.2 節の最小反例はこの産物であり、そのまま回帰テストになる
- **退化ケースは 10 分類のカタログを毎回上から当てる。** ランダム入力では出てこない
- **群 A（単位系由来）は 4 定数だけで 30 章以上をまかなった**
- 許容誤差は**パイプラインの下流ほど緩くなる**（法線 1e-5 → 最近接点 1e-2、三桁）
- **「誤差が乗るか」と「答えが一意か」を分けて考える。** 後者に厳しい閾値は正しい実装を落とす
- 一覧表を作る価値は、**「一つだけ根拠の違うもの」が見えること**（`is_convex_ccw` の 1e-6）
- **`precise` に戻したのは 4 箇所だけ。すべて反復の収束判定である**
- 収束判定は「桁落ちの塊」を見て「制御フローを決める」。第 4.6 節の基準は一度も変わらなかった
- **戻す以外の解決策のほうが優れていることが多い**（ビット検査、大小比較で十分にする）
- CI の三構成（fast / precise / precise+FTZ 無効）で**バグの原因を三つに切り分ける**
- カバレッジは**未到達の分岐を見つける道具**。数字を目標にしない

### 落とし穴と練習問題

**落とし穴 1：許容誤差を各所でその場しのぎに決める。**　一覧表を作れなくなり、根拠が失われる。

**落とし穴 2：スケール依存の閾値を絶対値で書く。**　座標系を変えた瞬間に壊れる。

**落とし穴 3：`precise` を「念のため」で広げる。**　`/fp:fast` を選んだ意味が消える。

**落とし穴 4：性質テストだけで満足する。**　「常にゼロを返す実装」が全部通ることがある。

**落とし穴 5：CI で三構成を毎回走らせる。**　時間がかかりすぎて、やがて誰も待たなくなる。
