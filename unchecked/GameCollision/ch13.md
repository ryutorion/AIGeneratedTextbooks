# 第 13 章　凸多角形へ一般化する

> **この章のゴール**
> 任意の凸多角形どうしの判定を実装する。三角形も、五角形も、OBB も、同じコードで扱えるようになる。
>
> SAT の骨組みは前章から変わらない。増えるのは軸の本数だけである。だがその「本数が増える」ことによって、初めて意味を持つ話が二つ出てくる。**凸性という前提をどう守るか**と、**早期脱出をどう効かせるか**である。そして、ランダムな凸多角形を生成できるようになることで、テストの質が一段上がる。

---

## 13.1 凸多角形の表現と、凸性の検証

### 表現

```cpp
// collision/shapes/polygon.h
#pragma once

#include "collision/math/vec2.h"
#include <array>
#include <span>
#include <cstdint>

namespace collision {

// 凸多角形の頂点数の上限。
// 動的確保を避けるため固定長にする。8 は実用上ほぼ十分な値。
inline constexpr std::size_t max_polygon_vertices = 8;

// 凸多角形。頂点は反時計回りに並んでいること。
struct ConvexPolygon {
    std::array<Vec2, max_polygon_vertices> vertex{};
    std::uint32_t count{};
};

[[nodiscard]] inline std::span<const Vec2> vertices(const ConvexPolygon& p) noexcept {
    return std::span<const Vec2>(p.vertex.data(), p.count);
}

} // namespace collision
```

**固定長配列を使う判断について説明しておく。**

`std::vector<Vec2>` のほうが素直に見える。だが判定関数はフレームあたり数千回から数万回呼ばれ、そのたびに動的確保が走るのは避けたい。ヒープ確保は数十から数百サイクルかかり、判定そのものより高くつく。

上限を 8 にしたのは、実用上の経験則である。ゲームで使う凸多角形は、三角形・四角形が大半で、複雑なものでも 8 頂点あれば足りることが多い。それ以上必要なら、複数の凸多角形に分割する。

サイズは `8 × 8 + 4 = 68` バイトになる。値渡しには大きいので、`const&` で渡す（第 6.1 節の基準）。

### 巻き方向の規約

**頂点は反時計回り（CCW）に並んでいることを不変条件とする。**

第 1 章で「2D の回転は反時計回りが正」と決めたので、それに合わせる。この規約が守られていれば、辺の外向き法線が一意に決まる。

反時計回りの多角形で、頂点 `v[i]` から `v[i+1]` へ向かう辺を `e` とすると、**外向き法線は `(e.y, -e.x)`** である。第 6.6 節で定義した `perpendicular(v) = (-v.y, v.x)`（反時計回りに 90 度）の逆向き、すなわち `-perpendicular(e)` になる。

確かめておこう。反時計回りの正方形 `(0,0), (1,0), (1,1), (0,1)` の最初の辺は `e = (1,0)`（下辺）である。外向き法線は下向き `(0,-1)` であるべきで、`(e.y, -e.x) = (0, -1)` と一致する。

紛らわしいので、専用の関数を用意する。

```cpp
// 時計回りに 90 度回す。反時計回り多角形の辺から外向き法線を得るのに使う。
[[nodiscard]] constexpr Vec2 right_perpendicular(Vec2 v) noexcept {
    return Vec2{v.y, -v.x};
}
```

### 辺と法線

```cpp
// collision/shapes/polygon.h（続き）

// i 番目の辺のベクトル（v[i] → v[i+1]）
[[nodiscard]] inline Vec2 edge(const ConvexPolygon& p, std::size_t i) noexcept {
    const std::size_t j = (i + 1) % p.count;
    return p.vertex[j] - p.vertex[i];
}

// SAT インターフェース（第 11.4 節の SatShape コンセプト）
[[nodiscard]] inline std::size_t axis_count(const ConvexPolygon& p) noexcept {
    return p.count;
}

[[nodiscard]] inline Vec2 axis(const ConvexPolygon& p, std::size_t i) noexcept {
    // 外向き法線。SAT では正規化されている必要がある（第 11.2 節）
    return normalize_or(right_perpendicular(edge(p, i)), Vec2{1.0f, 0.0f});
}
```

**`axis` を呼ぶたびに正規化している。** 第 11.4 節で「軸を配列で返さず添字でアクセスする形にした」と述べた設計が、ここで効いている。事前計算した法線配列を持たなくてよいので、`ConvexPolygon` の構造が単純に保たれる。

代償は、同じ法線を何度も計算しうることである。実際、SAT の中で各軸は一度しか使わないので、無駄はない。**マニフォールド生成（第 14 章）では法線を繰り返し参照するので、そこでは局所変数にキャッシュする。**

正規化に平方根が入るので、多角形の辺の数だけ平方根を計算することになる。OBB の 4 軸（平方根ゼロ）に比べると重い。これが「凸多角形は OBB より遅い」ことの主因である。**用途に応じて形状を選ぶ**根拠になる。

### 凸性の検証

不変条件は、テストで守る（第 3.8 節）。

**まず、よくある不十分な判定を見ておく。**

反時計回りの凸多角形では、隣り合う辺の外積がすべて非負になる。だから「全部の外積が非負なら凸」と書きたくなる。

```cpp
// これは不十分。凸でない多角形を通してしまう
[[nodiscard]] inline bool is_convex_ccw_broken(const ConvexPolygon& p) noexcept {
    for (std::size_t i = 0; i < p.count; ++i) {
        if (cross(edge(p, i), edge(p, (i + 1) % p.count)) < 0.0f) return false;
    }
    return true;
}
```

**この判定は「局所的に左へ曲がっている」ことしか見ていない。** 各頂点で常に左へ曲がっていても、全体で 2 周してしまう自己交差した星形は作れる。そのとき外積はすべて正のまま、多角形は凸でない。

具体的には、各頂点でほぼ 180 度近く折り返すような「棘」のある形状がこれに該当する。外積は正だが値がごく小さく、辺の向きが逆走している。総回転角が 360 度ではなく 720 度になる。

**この形状を SAT に流すと、交差判定が誤る。** 分離軸定理は凸形状にしか成り立たないからである。しかも生成器がこれを作ってしまうと、テストが「バグを見つけた」と誤って報告する。

### 確実な判定

検証用の関数なので、速度より確実さを取る。**各辺について、他のすべての頂点が内側にあることを確かめる。**

```cpp
// collision/shapes/polygon.h（続き）

// 凸性と巻き方向を検証する。デバッグとテストで使う。
// 各辺について全頂点が内側にあることを確認する O(n²) の確実な判定。
// n ≤ 8 なので、検証用途では十分に速い。
[[nodiscard]] inline bool is_convex_ccw(const ConvexPolygon& p) noexcept {
    if (p.count < 3) return false;

    for (std::size_t i = 0; i < p.count; ++i) {
        const Vec2 n   = right_perpendicular(edge(p, i));   // 外向き法線（未正規化）
        const float off = dot(p.vertex[i], n);

        for (std::uint32_t k = 0; k < p.count; ++k) {
            // 外側に出ている頂点が一つでもあれば凸でない
            if (dot(p.vertex[k], n) - off > 1.0e-6f) return false;
        }
    }
    return true;
}

// 符号付き面積。反時計回りなら正になる。
[[nodiscard]] inline float signed_area(const ConvexPolygon& p) noexcept {
    float a2 = 0.0f;
    for (std::size_t i = 0; i < p.count; ++i) {
        const std::size_t j = (i + 1) % p.count;
        a2 += cross(p.vertex[i], p.vertex[j]);
    }
    return 0.5f * a2;
}
```

`signed_area` は、いわゆる靴紐の公式である。頂点を順に外積して足すだけで面積が求まる。**符号が巻き方向を教えてくれる**ので、検証に使える。

`is_convex_ccw` の許容差 `1e-6f` は、法線が正規化されていないぶんスケールに依存する。厳密にやるなら辺の長さで割るべきだが、検証用途では固定値で足りる。一直線上に並んだ頂点（外積がちょうどゼロ）は、凸性を損なわないので許容される。

> **なぜ確実な判定にこだわるのか**
> 筆者はこの本を書く過程で、実際にこの罠を踏んだ。局所的な外積だけを見る判定を使ったテスト生成器が、総回転角 720 度の自己交差した多角形を作っていた。それを SAT に流したところ判定が誤り、**GJK（第 20 章）にバグがあるように見えた**。
>
> 実際には GJK は正しく、生成器と検証関数が誤っていた。ミンコフスキー差を陽に構築して照合するまで、原因が分からなかった。
>
> **テストデータ生成器と、その妥当性を保証する検証関数は、被テストコードと同じかそれ以上に信頼できなければならない。** 13.5 節でこの点を改めて扱う。

### 生成ヘルパ

```cpp
// 反時計回りの長方形を作る
[[nodiscard]] inline ConvexPolygon make_box(Vec2 center, Vec2 half) noexcept {
    ConvexPolygon p{};
    p.count = 4;
    p.vertex[0] = center + Vec2{-half.x, -half.y};
    p.vertex[1] = center + Vec2{ half.x, -half.y};
    p.vertex[2] = center + Vec2{ half.x,  half.y};
    p.vertex[3] = center + Vec2{-half.x,  half.y};
    return p;
}

// OBB から作る（第 12 章の corners は反時計回りに並んでいる）
[[nodiscard]] inline ConvexPolygon from_obb(const Obb& o) noexcept {
    ConvexPolygon p{};
    p.count = 4;
    const auto cs = corners(o);
    for (std::size_t i = 0; i < 4; ++i) p.vertex[i] = cs[i];
    return p;
}
```

`from_obb` は、13.6 節の等価性テストで使う。**前章の OBB 実装がリファレンスになる。**

## 13.2 SAT を任意の凸多角形対へ拡張する

### 骨組みは変わらない

第 11.4 節で書いた汎用 SAT が、そのまま使える。`ConvexPolygon` が `SatShape` コンセプトを満たしているからである。

とはいえ、専用版を書いたほうが読みやすいので、多角形用に一つ書く。

```cpp
// collision/narrow/polygon_polygon.h
#pragma once

#include "collision/shapes/polygon.h"
#include "collision/narrow/sat.h"

namespace collision {

namespace detail {

// s の軸だけを調べる。分離軸が見つかったら nullopt。
[[nodiscard]] inline std::optional<SatResult>
poly_axes(const ConvexPolygon& s,
          const ConvexPolygon& a, const ConvexPolygon& b) noexcept {
    SatResult best{.axis = Vec2{}, .depth = std::numeric_limits<float>::infinity()};

    const auto va = vertices(a);
    const auto vb = vertices(b);

    for (std::size_t i = 0; i < s.count; ++i) {
        const Vec2 n = axis(s, i);
        const Penetration p = penetration(project(va, n), project(vb, n));

        if (p.amount <= 0.0f) return std::nullopt;      // 分離軸を発見
        if (p.amount < best.depth) {
            best = SatResult{.axis = p.along_axis ? n : -n, .depth = p.amount};
        }
    }
    return best;
}

} // namespace detail

[[nodiscard]] inline std::optional<SatResult>
sat_polygon(const ConvexPolygon& a, const ConvexPolygon& b) noexcept {
    const auto ra = detail::poly_axes(a, a, b);
    if (!ra) return std::nullopt;

    const auto rb = detail::poly_axes(b, a, b);
    if (!rb) return std::nullopt;

    SatResult best = (ra->depth <= rb->depth) ? *ra : *rb;

    // 押し出し方向 → 法線（A から B へ）へ変換する（第 11.2 節）
    best.axis = -best.axis;
    return best;
}

[[nodiscard]] inline bool
overlaps(const ConvexPolygon& a, const ConvexPolygon& b) noexcept {
    return sat_polygon(a, b).has_value();
}

[[nodiscard]] inline std::optional<Contact>
intersect(const ConvexPolygon& a, const ConvexPolygon& b) noexcept {
    const auto r = sat_polygon(a, b);
    if (!r) return std::nullopt;

    return Contact{
        .normal = r->axis,
        .depth  = r->depth,
        .point  = centroid(vertices(a)),   // 暫定。第 14 章で正しく求める
    };
}

} // namespace collision
```

**`overlaps` を `sat_polygon` の呼び出しで済ませている**点は、第 7.1 節で述べた方針（`overlaps` は独立して速い実装を持つ）から外れている。

正直に理由を書く。凸多角形の SAT では、`overlaps` と `intersect` で計算量がほとんど変わらないからである。円や AABB では「平方根を省ける」「深度の計算を省ける」という明確な差があったが、多角形では投影の計算がコストの大半を占め、それは両方で必要である。

**省ける部分がないなら、実装を分けても速くならない。** 一つにしておくほうが、両者の結果が食い違う心配もなくなる（第 7.7 節の `check_overlaps_matches_intersect` が自明に通る）。

### 円との判定はどうするか

第 9 章の統一実装は `closest_point` を要求していた。凸多角形に対してこれを実装すれば、円 vs 凸多角形も自動的に使えるようになる。

```cpp
// collision/narrow/closest_point.h に追加
[[nodiscard]] inline Vec2 closest_point(Vec2 p, const ConvexPolygon& poly) noexcept {
    // 内部にあるなら p 自身（第 9.5 節の制約がここにも当てはまる）
    bool inside = true;
    for (std::size_t i = 0; i < poly.count; ++i) {
        if (dot(axis(poly, i), p - poly.vertex[i]) > 0.0f) { inside = false; break; }
    }
    if (inside) return p;

    // 各辺の最近接点のうち、最も近いものを選ぶ
    Vec2  best{};
    float best_d2 = std::numeric_limits<float>::infinity();
    for (std::size_t i = 0; i < poly.count; ++i) {
        const std::size_t j = (i + 1) % poly.count;
        const Vec2  q  = closest_point_on_segment(p, poly.vertex[i], poly.vertex[j]);
        const float d2 = distance_squared(p, q);
        if (d2 < best_d2) { best_d2 = d2; best = q; }
    }
    return best;
}
```

内外判定に外向き法線を使っている。**すべての辺について「点が内側にある」なら内部**である。これは SAT の点版といえる。

第 9 章の統一実装と組み合わせれば、`intersect(Circle, ConvexPolygon)` が動く。ただし第 9.5 節で述べた制約（円の中心が内部にあると深度が正しくない）は残る。**これを正しく解くには、多角形版の「最も近い辺を選んで押し出す」処理が要る**（第 10.5 節で AABB についてやったのと同じこと）。練習問題としておく。

## 13.3 早期脱出と軸の順序

### 軸が増えると効いてくる

OBB では 4 軸だったので、早期脱出の効果は限定的だった。三角形どうしなら 6 軸、八角形どうしなら 16 軸になる。**交差していないペアでは、最初の 1 軸で決着がつけばそれ以降を省ける。**

そしてゲームでは、判定するペアの大半は交差していない。ブロードフェーズ（第 VI 部）で絞り込んだ後でも、実際に交差しているのは一部である。**早期脱出は、平均的なコストを大きく下げる。**

### 良い軸から調べる

早期脱出を効かせるには、**分離軸である可能性が高い軸を先に調べる**のがよい。

一つの実用的なヒューリスティックは、「重心を結ぶ方向に最も近い軸から調べる」ことである。二つの形状が離れているなら、その方向で分離している可能性が高い。

```cpp
// 重心を結ぶ方向に最も近い軸の添字を返す
[[nodiscard]] inline std::size_t
best_first_axis(const ConvexPolygon& s, Vec2 dir) noexcept {
    std::size_t best_i = 0;
    float best_dot = -std::numeric_limits<float>::infinity();
    for (std::size_t i = 0; i < s.count; ++i) {
        const float d = std::fabs(dot(axis(s, i), dir));
        if (d > best_dot) { best_dot = d; best_i = i; }
    }
    return best_i;
}
```

**ただし、この最適化を本書では採用しない。**

理由は、`best_first_axis` 自体が全軸を走査するので、軸の走査を一巡分余計に行うことになるからである。軸ごとの投影（頂点数に比例）に比べれば軽いが、それでも「良い軸を探すコスト」と「早期脱出で節約できるコスト」が拮抗する。

**8 頂点程度なら、素直に先頭から調べるほうが速い。** 頂点数が数十になる場合には検討の価値があるが、そのときはそもそも凸分解を考えるべきである。

### 前フレームの軸を再利用する

より効果的な最適化がある。**前フレームで分離軸だった軸を、次のフレームでも最初に試す。**

フレーム間で物体はわずかしか動かないので、前フレームで分離していた軸は、今フレームでも分離している可能性が高い。当たれば 1 軸で決着する。

```cpp
struct SatCache {
    std::uint32_t last_separating_axis{0};
    bool from_a{true};
};
```

この「フレーム間コヒーレンシ」の利用は、第 31 章の Sweep and Prune でも中心的な役割を果たす。**同じ発想が、ナローフェーズとブロードフェーズの両方に現れる。**

本書では実装しない。キャッシュの管理（どこに持つか、いつ無効化するか）がパイプライン全体の設計に関わり、第 33 章まで踏み込まないと形にならないからである。第 33 章の練習問題としておく。

### コストを数えてみる

「凸多角形は OBB より遅い」と 13.1 節で述べた。どれくらい遅いのか、演算回数を数えてみる。

**OBB どうし（第 12 章）。** 軸 4 本。各軸で `project(Obb, n)` を 2 回呼び、1 回あたり内積 3 回。合計 `4 × 2 × 3 = 24` 回の内積。平方根はゼロ。

**四角形どうし（この章）。** 軸 8 本（各 4 辺）。軸の生成に正規化（平方根 1 回）が 8 回。各軸で `project(span, n)` を 2 回呼び、1 回あたり頂点数ぶんの内積（4 回）。合計 `8 × 2 × 4 = 64` 回の内積と、8 回の平方根。

**同じ形（長方形）を表すのに、内積が 2.7 倍、平方根が 8 回増える。** 平方根は内積の数倍のコストがあるので、体感の差はさらに大きい。

**八角形どうし。** 軸 16 本、各軸で `16 × 2 × 8 = 256` 回の内積、16 回の平方根。頂点数の二乗で効いてくる。

この計算から二つのことが言える。

**1. 形状は必要最小限の表現を選ぶ。** 長方形を凸多角形として扱うのは、正しいが無駄である。第 12 章の OBB を使う。

**2. 早期脱出の価値が頂点数とともに上がる。** 八角形どうしで最初の軸で分離が判明すれば、256 回のうち 16 回で済む。

### 実測してから判断する

最適化の話を二つ挙げて、両方とも「採用しない」で終えた。これは意図的である。

**「速くなりそう」という直感で最適化を入れると、たいてい外れる。** 上の演算回数の見積もりも、あくまで目安である。実際にはメモリアクセスのパターンや分岐予測の当たり外れが効き、演算回数どおりの比にはならない。

第 29 章でベンチマークの取り方を扱った後に、改めて判断すべき事柄である。この段階では、**読んで正しいと分かるコードを保つ**ほうが価値が高い。

## 13.4 点群から凸包を作る

### なぜ必要か

ここまで、凸多角形は「すでに凸である」ことを前提にしてきた。実際には、点の集合から凸多角形を作りたい場面がある。

- レベルエディタでユーザーが置いた点から当たり判定を作る
- スプライトの輪郭から自動生成する
- 13.6 節のテストで、ランダムな点集合から確実に凸な形状を作る

**凸包**（convex hull）は、与えられた点集合をすべて含む最小の凸多角形である。

### アンドリューのモノトーンチェイン法

実装が簡単で確実な方法として、モノトーンチェイン法を使う。

1. 点を X 座標（同じなら Y 座標）でソートする
2. 左から右へ走査して「下側の包絡線」を作る
3. 右から左へ走査して「上側の包絡線」を作る
4. 二つをつなぐ

各走査では、新しい点を追加するたびに「直前の 2 点と合わせて右に曲がっていないか」を調べ、曲がっていれば直前の点を捨てる。

```cpp
// collision/shapes/polygon.h（続き）
#include <algorithm>

// 点群の凸包を求める。結果は反時計回り。
// 頂点数が max_polygon_vertices を超える場合は nullopt を返す。
[[nodiscard]] inline std::optional<ConvexPolygon>
convex_hull(std::span<const Vec2> points) noexcept {
    if (points.size() < 3) return std::nullopt;

    // ソート用にコピー（上限を超える入力も受け付けたいので vector を使う）
    std::vector<Vec2> pts(points.begin(), points.end());
    std::ranges::sort(pts, [](Vec2 a, Vec2 b) {
        return (a.x != b.x) ? (a.x < b.x) : (a.y < b.y);
    });

    // 重複点を除く
    pts.erase(std::ranges::unique(pts, [](Vec2 a, Vec2 b) {
        return distance_squared(a, b) < min_length2;
    }).begin(), pts.end());

    if (pts.size() < 3) return std::nullopt;

    std::vector<Vec2> hull;
    hull.reserve(pts.size() * 2);

    // 下側の包絡線 → 上側の包絡線 の順に構築する
    for (int pass = 0; pass < 2; ++pass) {
        const std::size_t start = hull.size();
        const auto range = (pass == 0)
            ? std::vector<Vec2>(pts.begin(), pts.end())
            : std::vector<Vec2>(pts.rbegin(), pts.rend());

        for (const Vec2 p : range) {
            // 右に曲がる（外積が非正）なら、直前の点を捨てる
            while (hull.size() >= start + 2 &&
                   cross(hull[hull.size() - 1] - hull[hull.size() - 2],
                         p - hull[hull.size() - 2]) <= 0.0f) {
                hull.pop_back();
            }
            hull.push_back(p);
        }
        hull.pop_back();   // 終点は次の走査の始点と重複するので落とす
    }

    if (hull.size() < 3 || hull.size() > max_polygon_vertices) return std::nullopt;

    ConvexPolygon result{};
    result.count = static_cast<std::uint32_t>(hull.size());
    for (std::size_t i = 0; i < hull.size(); ++i) result.vertex[i] = hull[i];
    return result;
}
```

**`std::vector` を使っている**点について。13.1 節で「動的確保を避ける」と述べたのと矛盾するように見えるが、`convex_hull` は**判定のホットパスでは呼ばれない**。形状を作るのは初期化時か、エディタでの編集時である。フレームごとに呼ぶものではない。

**確保を避けるべき場所とそうでない場所を区別する**のは、実務的に重要な判断である。すべてを最適化しようとすると、コードが読みにくくなるだけで得るものが少ない。

`std::ranges::sort` と `std::ranges::unique` は C++20 の範囲版アルゴリズムである。イテレータのペアを渡さずに済むので、書き間違いが減る。

### 上限を超えたらどうするか

`max_polygon_vertices`（8）を超える凸包が求まった場合、`nullopt` を返している。呼び出し側の選択肢は三つある。

- **点を減らす。** 凸包の頂点のうち、寄与の小さいものを削る（単純化）
- **複数の凸多角形に分ける。** 凸分解
- **上限を上げる。** 用途が限定的なら現実的

本書では最初の選択肢を採らない。単純化のアルゴリズム（頂点を削ったときの誤差をどう評価するか）は、それ自体が一つの話題になるからである。**扱える範囲を明示して、超えたら失敗を返す**のが、入門書として誠実な設計だと考える。

## 13.5 ランダムな凸多角形を生成する

### なぜ生成器が要るか

前章までのテストでは、手で用意した形状か、ランダムな AABB / OBB を使っていた。凸多角形になると、ランダムに頂点を置いただけでは凸にならない。

**凸性を保証しながらランダムに生成する方法**が要る。これができると、テストの質が一段上がる。何万通りもの形状ペアに対して、対称性や不変条件を検証できるようになる。

### 楕円上に点を置く

最も簡単で確実な方法は、**楕円（または円）の周上に点を置く**ことである。円周上の任意の点集合は、角度順に並べれば必ず凸多角形になる。

```cpp
// test_helpers.h に追加

// ランダムな凸多角形を生成する。
// 円周上に点を取り、角度順に並べることで凸性を保証する。
[[nodiscard]] inline collision::ConvexPolygon
random_convex_polygon(Rng& rng, std::size_t n, float radius_min, float radius_max) {
    n = std::clamp<std::size_t>(n, 3, collision::max_polygon_vertices);

    // ランダムな角度を n 個作り、昇順に並べる
    std::array<float, collision::max_polygon_vertices> angles{};
    for (std::size_t i = 0; i < n; ++i) {
        angles[i] = rng.uniform(0.0f, 2.0f * std::numbers::pi_v<float>);
    }
    std::sort(angles.begin(), angles.begin() + n);

    collision::ConvexPolygon p{};
    p.count = static_cast<std::uint32_t>(n);
    for (std::size_t i = 0; i < n; ++i) {
        const float r = rng.uniform(radius_min, radius_max);
        p.vertex[i] = collision::Vec2{r * std::cos(angles[i]), r * std::sin(angles[i])};
    }
    return p;
}
```

**半径を頂点ごとに変えているのに凸性が保たれるのか**、と疑問に思うかもしれない。保たれない。半径がバラバラだと凹む可能性がある。

正しくは、半径を固定するか、生成後に凸性を検証して弾く必要がある。後者を採る。

```cpp
// 凸性が保証された多角形を得る。凸でなければ作り直す。
[[nodiscard]] inline collision::ConvexPolygon
random_convex_polygon_checked(Rng& rng, std::size_t n) {
    for (int attempt = 0; attempt < 100; ++attempt) {
        auto p = random_convex_polygon(rng, n, 0.5f, 2.0f);
        if (collision::is_convex_ccw(p)) return p;
    }
    // 100 回失敗したら、半径固定の確実な版を返す
    return random_convex_polygon(rng, n, 1.0f, 1.0f);
}
```

**この「生成して検証、駄目なら再試行」という形は、テストデータ生成の定石である。** 生成器が複雑になるより、単純な生成器と検証を組み合わせるほうが、正しさを確認しやすい。

`is_convex_ccw` が生成器の妥当性を保証しているので、**生成器のバグがテスト全体を汚染することがない**。これは重要な性質である。生成器が壊れていると、テストが通っても意味がない。

### 平行移動と回転

生成した多角形を配置する。

```cpp
[[nodiscard]] inline collision::ConvexPolygon
transformed(const collision::ConvexPolygon& p, collision::Vec2 t, float angle) {
    const float c = std::cos(angle), s = std::sin(angle);
    collision::ConvexPolygon r = p;
    for (std::uint32_t i = 0; i < p.count; ++i) {
        const auto v = p.vertex[i];
        r.vertex[i] = collision::Vec2{v.x * c - v.y * s, v.x * s + v.y * c} + t;
    }
    return r;
}
```

回転と平行移動は凸性を保つので、変換後も検証は不要である。

### OBB との等価性

```cpp
// test_polygon.cpp
TEST_CLASS(PolygonVsObbReference) {
public:
    TEST_METHOD(OBBから作った多角形がOBB実装と同じ結果を返すこと) {
        Rng rng(700);
        for (int i = 0; i < 20000; ++i) {
            const Obb oa = collision::obb_from_angle(
                {rng.uniform(-3.0f, 3.0f), rng.uniform(-3.0f, 3.0f)},
                {rng.uniform(0.3f, 2.0f), rng.uniform(0.3f, 2.0f)},

            const Obb ob = collision::obb_from_angle(
                {rng.uniform(-3.0f, 3.0f), rng.uniform(-3.0f, 3.0f)},
                {rng.uniform(0.3f, 2.0f), rng.uniform(0.3f, 2.0f)},
                rng.uniform(0.0f, 6.28f));

            const auto pa = collision::from_obb(oa);
            const auto pb = collision::from_obb(ob);

            const auto via_obb  = collision::intersect(oa, ob);
            const auto via_poly = collision::intersect(pa, pb);

            Assert::AreEqual(via_obb.has_value(), via_poly.has_value(),
                             L"交差の有無が食い違う");
            if (!via_obb) continue;

            check_contact_invariants(*via_poly);
            expect_near(via_obb->depth, via_poly->depth, 1.0e-4f, 1.0e-4f);
        }

```

**この等価性は非常に強い。** OBB 実装は投影の公式（第 12.2 節）を使い、多角形実装は頂点を列挙する。まったく違う計算経路で同じ答えが出れば、両方が正しい可能性は高い。

境界近傍で差が出ることはあるが、`AreEqual` で厳密に比較している。もし落ちるようなら、その入力を記録して調べる価値がある。実際には、軸平行に近い配置以外ではほとんど落ちない。

## この章のまとめ

- 凸多角形は固定長配列で表す。上限 8 頂点。動的確保を避けるため
- **頂点は反時計回り。外向き法線は `right_perpendicular(edge) = (e.y, -e.x)`**
- `axis(i)` は呼び出しごとに正規化する。事前計算した法線配列を持たない設計
- 平方根が辺の数だけ入るので、OBB より遅い。**用途に応じて形状を選ぶ根拠**
- 凸性の検証は「隣り合う辺の外積がすべて非負」。`signed_area` の符号で巻き方向も分かる
- 多角形では `overlaps` と `intersect` の計算量がほぼ同じ。**分けても速くならないので一つにする**
- 四角形どうしの SAT は、同じ形を OBB で扱うより内積 2.7 倍・平方根 8 回ぶん高い
- 早期脱出は軸が増えるほど効く。ただし「良い軸を先に探す」最適化は割に合わない
- 点群から凸包を作る（モノトーンチェイン法）。**ホットパスではないので動的確保を許す**
- フレーム間コヒーレンシの利用は有効だが、パイプライン設計が要る（第 33 章）
- **ランダム凸多角形の生成器は「生成して検証、駄目なら再試行」。** 生成器自体もテストする
- 外向き法線の向きは、SAT では症状が出ない。第 14 章まで潜伏するのでここで検証する

### 第 II 部の到達点（あと一歩）

回転する箱と任意の凸多角形の判定ができるようになった。第 1 章の対応表でいえば「第 14 章：回転する箱・凸多角形の判定と押し戻し」の一歩手前である。

**残っているのは接触点だけである。** 第 11 章から一貫して「暫定」と書いてきた `Contact::point` を、次章で正しく求める。

### 落とし穴と練習問題

**落とし穴 1：巻き方向の取り違え。**　時計回りの多角形を渡すと、法線がすべて内を向く。SAT では症状が出ないので発見が遅れる。`is_convex_ccw` で検証する。

**落とし穴 2：`perpendicular` と `right_perpendicular` の混同。**　第 6.6 節の `perpendicular` は反時計回り 90 度。外向き法線には逆向きが要る。

**落とし穴 3：生成器を検証しない。**　凹な多角形をテストに流すと、SAT が誤判定して「バグを見つけた」と誤解する。
