# 第 43 章　ライブラリとして仕上げる

> **この章のゴール**
> ここまで書いてきたコードを、**他人が使えるもの**にする。自分だけが使うなら暗黙で済んでいたことを、すべて文書にする。
>
> 最も重要なのは**契約の明文化**である。本書は `/fp:fast` と FTZ/DAZ を前提に 42 章を書いてきた。**その前提を、利用者に伝える責任がある。** 「ビット単位の再現性を保証しない」と書くこと、「FTZ/DAZ を有効にすること」という**性能契約**を書くこと——どちらも、書かなければ利用者が踏む地雷になる。
>
> 最後に、ここから先へ進むための地図を置く。

## 43.1 公開ヘッダの整理と名前空間

### 何を公開し、何を隠すか

**公開ヘッダは「利用者が `#include` してよいもの」である。** それ以外は内部実装として扱う。

```
include/collision/          ← 公開
    collision.h                 便宜ヘッダ（全部を含む）
    math/vec2.h  vec3.h  mat3.h
    shapes/circle.h  aabb.h  obb.h  polygon.h  capsule.h
    narrow/contact.h  manifold.h  gjk.h  epa.h
    broad/dynamic_tree.h  uniform_grid.h  sweep_prune.h
    world/world.h  filter.h  query.h
    dynamics/rigid_body.h  solver.h
    character/controller.h
    config/tolerance.h          ← 第 5.9 節の閾値
    config/build_contract.h     ← 43.3 節

src/collision/              ← 非公開
    detail/*.h  *.cpp
```

**`detail` 名前空間を実際に使う。** 第 20〜22 章の収束判定など、公開すべきでないものはここに置いた。

```cpp
namespace collision {
namespace detail {
    // 利用者が呼ぶべきでないもの。ヘッダに置いてもよいが、名前で意図を示す
    [[nodiscard]] bool distance_converged(float, float, float) noexcept;
}
    // 公開 API
    [[nodiscard]] std::optional<ContactManifold> collide(...);
}
```

**モジュールを使わない本書の構成では、`detail` 名前空間が唯一の「隠す」手段である。** 強制力はないが、意図は伝わる。

### 便宜ヘッダの功罪

```cpp
// include/collision/collision.h
#include "collision/math/vec2.h"
#include "collision/shapes/circle.h"
// ... 全部
```

**便利だが、コンパイル時間が増える。** 「まず使ってみる」段階では便宜ヘッダ、実プロジェクトでは個別ヘッダ、という使い分けを文書に書いておく。

### `[[nodiscard]]` と `noexcept` の方針

本書では次の規則で統一した。

| 種類 | `[[nodiscard]]` | `noexcept` |
|---|---|---|
| 値を返す純粋関数 | **必ず付ける** | 確保しないなら付ける |
| 状態を変える関数 | 付けない | 確保しないなら付ける |
| 確保する関数（`std::vector` を返すなど） | 付ける | **付けない** |

**`[[nodiscard]]` は「戻り値を捨てたらバグ」という意思表示である。** 判定関数の戻り値を捨てるコードには意味がないので、必ず付ける。

**`noexcept` は慎重に。** 一度公開すると外せない。**確保する可能性がある関数には付けない。**

### バージョンと互換性

**ヘッダオンリーではないライブラリを配るなら、バージョンを埋める。**

```cpp
// include/collision/config/version.h
namespace collision {

inline constexpr int version_major = 1;
inline constexpr int version_minor = 0;
inline constexpr int version_patch = 0;

// ヘッダと実装（.lib）の食い違いを検出する。
// リンク時ではなく実行時に分かるのが利点である
[[nodiscard]] int runtime_version() noexcept;   // .cpp 側で version_major*10000+... を返す

inline void check_version() {
    const int compiled = version_major * 10000 + version_minor * 100 + version_patch;
    if (runtime_version() != compiled)
        throw std::runtime_error("collision: ヘッダとライブラリのバージョンが違います");
}

} // namespace collision
```

**ヘッダだけ更新してリビルドを忘れる**のは、静的ライブラリで最も多い事故である。**構造体のサイズが変わっていると、静かに壊れる。**

そして「何を変えたら互換性が壊れるか」を決めておく。

| 変更 | 互換性 | 例 |
|---|---|---|
| 公開構造体にメンバを追加 | **壊れる**（ABI） | `ContactManifold` に点を足す |
| 関数の引数を追加 | 壊れる（API） | `collide` に設定を渡す |
| 既定値の変更 | **壊れないが挙動が変わる** | `contact_slop` を 1 mm → 5 mm |
| 内部実装の変更 | 壊れない | ソルバの反復順序 |

**三行目が最も厄介である。** ビルドは通り、テストも通り、**ゲームの挙動だけが変わる。** 閾値の既定値を変えるときは、変更履歴に必ず書く。

## 43.2 単位系・座標系の明文化

### 暗黙の前提を全部書き出す

**利用者が最初に知りたいのは、この三つである。**

```cpp
// include/collision/config/conventions.h
//
// ■ 単位系
//   長さ  : 1 単位 = 1 メートル
//   時間  : 1 単位 = 1 秒
//   質量  : 1 単位 = 1 キログラム
//   角度  : ラジアン
//
//   → この前提のもとに config/tolerance.h の閾値が決まっている（第 5.9 節）。
//     別の単位系（1 単位 = 1 センチメートルなど）を使う場合、
//     tolerance.h の値をすべてスケールし直すこと。
//
// ■ 座標系（2D）
//   +X は右、+Y は上。回転は反時計回りが正。
//   多角形の頂点は反時計回り (CCW) に並べる。
//
// ■ 座標系（3D）
//   右手系。+X は右、+Y は上、+Z は手前（画面から自分の方向）。
//   三角形の頂点は、表から見て反時計回りに並べる。
//
// ■ 接触法線の向き
//   collide(a, b) が返す normal は、常に「A から B へ」向く。
//   A を -normal 方向へ、B を +normal 方向へ動かすと離れる。
```

**「Y 軸は上か」と「右手系か」は、他のライブラリやエンジンと繋ぐときに必ず問題になる。** DirectX は左手系、OpenGL は右手系が慣習である。**変換が必要かどうかを、利用者が判断できるようにする。**

### 法線の向きは最も間違えやすい

**本書でも第 22 章で符号を間違えた。** `A ⊖ B` と `B ⊖ A` を取り違えたためである。

**文書に書くだけでなく、コードで保証する。**

```cpp
// tests/test_conventions.cpp
TEST_METHOD(法線が常に A から B へ向くこと) {
    Rng rng(9000);
    for (int i = 0; i < 50000; ++i) {
        const auto [a, b] = random_overlapping_pair(rng);
        const auto m = collision::collide(a, b);
        Assert::IsTrue(m.has_value());

        // A の中心から B の中心へ向かうベクトルと、法線の向きが一致する
        const Vec2 a_to_b = center(b) - center(a);
        Assert::IsTrue(dot(m->normal, a_to_b) > 0.0f,
            std::format(L"i = {} で法線が逆向き", i).c_str());
    }
}
```

**「約束をテストにする」——これが文書化の最も確実な形である。** 文書は古くなるが、テストは落ちる。

**ただし完全ではない。** 深くめり込んで中心が入れ替わった状況では、この検査は成り立たない。**そういう入力を除外していることを、テストのコメントに書いておく。**

## 43.3 ビルド要件・実行時要件を契約として文書化する

**本章で最も重要な節である。**

### 三種類の契約

| 種類 | 破ったときに起きること | 本書での例 |
|---|---|---|
| **正しさの契約** | 結果が間違う・未定義 | `NaN` を入れない、多角形は凸で CCW |
| **ビルドの契約** | 期待した性質が失われる | `/fp:fast` 前提。ビット再現性なし |
| **性能の契約** | **正しく動くが遅い** | FTZ/DAZ を有効にすること |

**三つ目の「性能の契約」は見落とされやすい。** 「動くのだから問題ない」と思われるが、**特定の場面で 10 倍遅くなる**（第 5 章）。

### ビルドの契約を書く

```cpp
// include/collision/config/build_contract.h
//
// ============================================================
//  ビルド要件
// ============================================================
//
// 【必須】
//   - C++23 (/std:c++23preview 以降)
//   - x64。SSE2 以上。/arch:AVX2 を推奨
//   - /permissive- （適合性モード）
//
// 【前提】
//   本ライブラリは /fp:fast を前提に設計・検証されています。
//
//   ★ ビット単位の再現性を保証しません。
//     同一の実行ファイルを同一のマシンで実行する限り結果は再現しますが、
//     再ビルド・コンパイラの更新・別プラットフォームでは値が変わります。
//
//   ★ クロスプラットフォーム決定論（ロックステップ通信対戦、
//     リプレイの配布）が必要な用途には使用できません。
//     その場合は固定小数点実装への置き換えが必要です（第 41.3 節）。
//
//   /fp:precise でのビルドも動作します（テストは通ります）が、
//   検証は /fp:fast で行われています。速度は 1〜2 割低下します。
//
// 【禁止】
//   - /fp:except（例外の意味論）。本ライブラリは対応していません
//   - /fp:strict。動作しますが、性能上の意味がありません

#if defined(_MSC_VER)
  #if defined(_M_FP_EXCEPT)
    #error "collision: /fp:except には対応していません"
  #endif
  #if !defined(_M_X64)
    #error "collision: x64 のみ対応しています"
  #endif
#endif
```

**`#error` で機械的に弾けるものは弾く。** 文書を読まない利用者のほうが多い。

**そして「保証しない」ことを明記する責任がある。** 「たぶん再現する」と黙っているのが最悪である。利用者はリプレイ機能を作り、出荷後に壊れる。

### 性能の契約を書く

```cpp
// ============================================================
//  実行時要件
// ============================================================
//
// 【推奨】呼び出し側で FTZ/DAZ を有効にしてください。
//
//   collision::enable_flush_to_zero();   // 各スレッドで一度
//
//   ★ これは正しさの要件ではありません。無効でも結果は同じです。
//   ★ ただし非正規化数が発生する場面で最大 10 倍程度遅くなります。
//
//   MXCSR はスレッドローカルです。物理計算を行うすべてのスレッドで
//   設定してください（ジョブシステムのワーカースレッドを含む）。
//
// 【本ライブラリは MXCSR を勝手に変更しません】
//   理由：呼び出し側の意図しない副作用を避けるため（下記参照）。
```

**「正しさの要件ではない」と明記する**のが要点である。そう書いておかないと、利用者は「設定しないと壊れる」と誤解して、必要以上に身構える。

### ライブラリが MXCSR を勝手に変えるべきか

**判断が分かれるところなので、根拠を書いておく。**

| 方針 | 利点 | 欠点 |
|---|---|---|
| **勝手に変える** | 利用者が忘れない | 呼び出し元の他の処理に影響する |
| **RAII で一時的に変える** | 影響が局所的 | 毎フレーム 2 回の MXCSR 読み書き |
| **変えない（呼び出し側に委ねる）** | 副作用がない | **忘れられる** |

**本書は「変えない」を採る。** 理由は二つある。

**一つ目。ライブラリが呼び出し元の浮動小数点環境を変えるのは、行儀が悪い。** 同じスレッドで動く他のコード——オーディオ処理、乱数生成、スクリプトエンジン——が影響を受ける。**そして原因が極めて追いにくい。**

**二つ目。RAII で戻す方式は、コストがゼロではない。** `_mm_getcsr` / `_mm_setcsr` はパイプラインをフラッシュする。フレームに数回なら無視できるが、細かい粒度で呼ぶと効いてくる。

**代わりに、忘れられたことを検出できるようにする。**

```cpp
// デバッグビルドでのみ、環境を検査する
void World::step(float dt) {
#if defined(COLLISION_DEBUG)
    if (!debug::read_mxcsr().flush_to_zero) {
        static bool warned = false;
        if (!std::exchange(warned, true))
            std::print(stderr,
                "collision: FTZ が無効です。enable_flush_to_zero() を呼んでください\n"
                "（正しさには影響しませんが、性能が低下します）\n");
    }
#endif
    // ...
}
```

**一度だけ警告する。** 毎フレーム出すと無視されるようになる。

### 正しさの契約

```cpp
// ============================================================
//  入力に対する契約
// ============================================================
//
// 【呼び出し側が保証すべきこと】
//   - 座標・速度に NaN / Inf を含めない
//   - ConvexPolygon は凸であり、頂点は CCW 順である
//     （make_convex_polygon() を使えば検証されます）
//   - Aabb は min <= max を満たす
//   - 法線を引数に取る関数には、単位長のベクトルを渡す
//
// 【ライブラリが保証すること】
//   - 上記が満たされていれば、結果は 40.5 節の許容誤差の範囲で正しい
//   - 上記が満たされていない場合の動作は未定義（Debug ビルドでは assert）
```

**「未定義」と書くのは無責任ではない。** すべての不正入力を検査すると、正常系のコストが上がる。**契約を明示し、Debug で検査するのが実務的な落としどころである。**

**そして検証つきの入口を用意する**（第 41.6 節の `make_convex_polygon`）。「速い道」と「安全な道」の両方を提供し、選択を利用者に委ねる。

## 43.4 API ドキュメントと使用例

### 使用例が最良のドキュメントである

**関数のリファレンスより、動く例のほうが読まれる。**

```cpp
// examples/01_minimal.cpp ― 最小の使用例
#include <collision/collision.h>
#include <print>

int main() {
    collision::enable_flush_to_zero();          // 性能契約（43.3 節）

    collision::World world;

    const auto ground = world.add_static(
        collision::Aabb{{-10.0f, -1.0f}, {10.0f, 0.0f}});
    const auto box = world.add_dynamic(
        collision::Obb{.extents = {0.5f, 0.5f}},
        collision::Transform2{.position = {0.0f, 5.0f}});

    for (int frame = 0; frame < 300; ++frame) {
        world.step(1.0f / 60.0f);
        for (const auto& e : world.events())
            std::println("frame {}: {} {} と {}",
                         frame, to_string(e.kind), e.key.first(), e.key.second());
    }
    std::println("最終位置 y = {:.4f}", world.body(box).position.y);
    return 0;
}
```

**この 20 行に、本書の主要な要素が全部入っている。** 環境設定、世界の構築、ステップ、イベントの取得。

**例は「動くこと」をテストで保証する。**

```cpp
// examples をビルドしてテストから実行する。壊れた例ほど有害なものはない
TEST_METHOD(使用例がすべてビルドでき_期待どおりに動くこと) {
    for (const auto& example : all_examples())
        Assert::AreEqual(0, run_example(example), L"使用例が失敗しました");
}
```

### 段階的な例を並べる

| 例 | 何を示すか | 参照する章 |
|---|---|---|
| `01_minimal` | 最小構成 | 第 33 章 |
| `02_shapes` | 各形状の判定 | 第 6〜14 章 |
| `03_raycast` | レイキャストとスイープ | 第 15〜18 章 |
| `04_broadphase` | ブロードフェーズの差し替え | 第 30〜32 章 |
| `05_stacking` | 積み上げとソルバ設定 | 第 34〜37 章 |
| `06_character` | キャラクターコントローラ | 第 38 章 |
| `07_determinism` | 再現性の確認方法 | 第 41.3 節 |

**`07_determinism` を独立した例にする**のは、43.3 節の契約と対応させるためである。「どこまで再現するか」を、利用者が自分で確かめられる。

### リファレンスに書くべきこと

各公開関数に、次の四つを書く。

```cpp
/// 二つの形状の接触を判定し、マニフォールドを返す。
///
/// @param a  形状 A（ワールド変換込み）
/// @param b  形状 B
/// @return   接触していれば ContactManifold、していなければ nullopt。
///           normal は常に A から B へ向く（43.2 節の規約）。
///
/// @pre  a, b の座標に NaN / Inf を含まないこと
/// @post 戻り値がある場合、length(normal) は 1 ± 1e-5 の範囲にある
///
/// 計算量：形状の頂点数を n, m として O(n + m)（GJK/EPA 経由の場合は反復回数に依存）
[[nodiscard]] std::optional<ContactManifold> collide(const Shape2& a, const Shape2& b);
```

**`@pre` と `@post` を書くことが、43.3 節の契約を関数単位に落とし込む作業である。** そして `@post` はそのままテストになる。

**計算量を書く**のも忘れない。利用者が「1 フレームに何回呼べるか」を見積もれる。

### 設定をひとまとめにする

**閾値やソルバのパラメータを、利用者が触れる形で 1 箇所に集める。**

```cpp
// include/collision/config/settings.h
struct WorldSettings {
    // 積分（第 35 章）
    Vec2  gravity{0.0f, -9.81f};
    float fixed_dt{1.0f / 60.0f};

    // ソルバ（第 37 章）
    int   velocity_iterations{10};
    float baumgarte_beta{0.2f};
    float slop{contact_slop};
    float max_linear_correction{0.2f};

    // スリープ（第 37.4 節）
    float sleep_linear_threshold{min_speed};
    float time_to_sleep{0.5f};

    // ブロードフェーズ（第 32 章）
    float aabb_margin{0.1f};

    // 安全弁（第 37.5 節）
    float max_speed{340.0f};              // 音速。これを超えたら異常
    float max_angular_speed{50.0f};       // rad/s
};
```

**既定値だけで実用になることが重要である。** 「まず動かす」ときに 12 個のパラメータを埋めさせてはいけない。

**そして各値に「どの章で決めたか」をコメントで残す。** 利用者が調整するとき、根拠を追える。第 40.5 節の一覧表が、そのまま調整ガイドになる。

### よくある質問を先回りする

**文書に FAQ を置くと、同じ質問を何度も受けずに済む。** 本書の内容から予測できるものを並べておく。

| 質問 | 答え | 参照 |
|---|---|---|
| 物体が震えます | `slop` を上げるか、ソルバの反復を増やす | 34.3, 37.2 |
| 高速な物体がすり抜けます | スイープ判定を有効にする。`fixed_dt` を小さくする | 17, 18 |
| 積み上げが沈みます | ウォームスタートが有効か確認する | 37.2 |
| 特定の場面だけ急に重くなります | **FTZ/DAZ が有効か確認する** | 5, 41.5 |
| 再ビルドしたら結果が変わりました | **仕様です。** ビット再現性は保証しない | 41.3, 43.3 |
| キャラクタが壁で引っかかります | `skin_width` と滑りの反復回数を確認する | 38.2 |
| 値が `NaN` になります | 入力に `NaN` がないか。安全弁のカウンタを見る | 37.5, 41.4 |

**四行目と五行目は、本書の前提そのものに関わる質問である。** この二つを FAQ の上のほうに置いておくと、利用者が地雷を踏む前に読んでもらえる。

## 43.5 ここから先の学習地図

### 読むべきもの

**書籍。**

- **Christer Ericson, *Real-Time Collision Detection*（2004）** — 本書が扱った判定手法の網羅的な参考書。GJK・BVH・空間分割の詳細はここに戻るとよい
- **Gino van den Bergen, *Collision Detection in Interactive 3D Environments*（2003）** — GJK の原著者による解説。第 19〜23 章の理論的な背景

## この章のまとめ

- 公開ヘッダと `detail` 名前空間を分ける。**モジュールを使わない構成での唯一の「隠す」手段**
- 便宜ヘッダは「まず使う」用。実プロジェクトでは個別ヘッダを勧める
- `[[nodiscard]]` は判定関数に必ず。**`noexcept` は一度公開すると外せない**ので慎重に
- **単位系・座標系・法線の向きを明文化する。** 他のエンジンと繋ぐときに必ず問われる
- **約束はテストにする。** 文書は古くなるが、テストは落ちる
- 契約は三種類：**正しさ・ビルド・性能**
- **「性能の契約」は見落とされやすい。** 正しく動くが 10 倍遅い、という状態が起きる
- **「ビット単位の再現性を保証しない」と明記する責任がある。** 黙っているのが最悪
- 機械的に弾けるものは `#error` で弾く。**文書を読まない利用者のほうが多い**
- ライブラリは **MXCSR を勝手に変えない。** 呼び出し元の他の処理に影響し、原因が追えない
- 代わりに **Debug ビルドで一度だけ警告する**
- 「未定義」と書くのは無責任ではない。**契約を明示し、Debug で検査し、検証つきの入口も用意する**
- **使用例が最良のドキュメント。** そして例が動くことをテストで保証する
- リファレンスには **`@pre` / `@post` / 計算量**を書く。`@post` はそのままテストになる
- **バージョンをヘッダと実装の両方に埋める。** ヘッダだけ更新する事故が最も多い
- **既定値の変更は「ビルドは通るが挙動が変わる」**。変更履歴に必ず書く
- 設定は一箇所に集め、**既定値だけで実用になる**ようにする
- FAQ に「再ビルドで結果が変わる」「急に重い」を上のほうへ置く
- 次に伸ばすなら**関節拘束・TGS・PBD**。どれも本書のコードから数百行で始められる
- **出荷前チェックリスト**（43.6 節）で、43 章分の判断を機械的に見直す

## おわりに

43 章、ここまでお疲れさまでした。

**第 1 章で「判定・情報生成・応答の三層」という地図を描いた。** 振り返ると、本書はその三層をそれぞれ 10 章ずつかけて埋めてきたことになる。

**そして全体を貫いていたのは、三層の図ではなく、もっと地味な三つの習慣だった。**

**一つ目は、動かして測ること。** 「O(n²) は遅い」ではなく「n = 1,000 で 1.66 ミリ秒」。「ウォームスタートは効く」ではなく「23.2 mm が 5.00 mm になる」。**数字にすると、判断が変わる場面が何度もあった。** 第 42.2 節で「SoA にしただけでは速くならない」と分かったのも、測ったからである。

**二つ目は、性質でテストすること。** `/fp:fast` を選んだ時点で、値の一致に頼れなくなった。代わりに手に入れたのが、対称性・不変条件・単調性・保存則という道具である。**制約から生まれた手法が、結果としてより強い検証になった。** 第 30.3 節では、性質（単調性）が正しさの証明そのものになった。

**三つ目は、間違いを記録すること。** 本書には「筆者はここで間違えた」という記述が何度も出てくる。凸性判定の甘さ、SAT の押し出し量、EPA の法線の符号、位置補正の二重適用、そして自分で書いた警告に二度引っかかったベンチマーク。**どれも、間違えた過程のほうが、正解より多くを語っていた。**

**衝突判定は、正しく書くのが難しい分野である。** 数学は素直なのに、浮動小数点と退化ケースと性能要求が絡んで、教科書どおりに書いたものが動かない。だからこそ、**測る・性質で縛る・間違いを残す**という習慣が効いてくる。

本書のコードは完成品ではない。**あなたのゲームに必要なものは、ここにないかもしれない。** そのときは、第 39.4 節と第 43.5 節の地図を頼りに進んでほしい。土台はもう手の中にある。

**そして何かを作ったら、まず測ってほしい。** それが、本書がいちばん伝えたかったことである。
