# 第 7 章　結果の型を設計する ― 判定の「戻り値」で本の骨格が決まる

> **この章のゴール**
> コリジョン判定が何を返すべきかを決める。`Contact` 型を設計し、法線の向きの規約を定め、「当たっていない」と「計算できなかった」を型で区別する。
>
> まだ判定のアルゴリズムは書かない。それでもこの章を独立させるのは、**戻り値の型が本書全体の骨格を決めてしまう**からである。第 8 章の円と円から第 28 章の 3D GJK まで、すべての判定関数がここで決めた型を返す。後から変えるのは高くつく。

---

## 7.1 `bool` を返すだけでは足りない理由

### 実際に困る場面

第 1 章で三層の話をした。ここで具体的に見る。

キャラクター（半径 0.5 の円）が壁（AABB）に向かって歩き、めり込んだ。次のフレームで、どう処理すればよいか。

```cpp
if (intersects(player_circle, wall_box)) {
    // ここで何をする？
}
```

やりたいのは「めり込みを解消する」ことである。そのために必要な情報は二つ。**どの向きに**動かすか、**どれだけ**動かすか。`bool` からは、どちらも復元できない。

「じゃあ、前フレームの位置に戻せばいいのでは」と考えるかもしれない。それは動くが、操作感が悪い。壁に斜めに当たったとき、プレイヤーは壁に沿って滑ってほしいのに、完全に停止してしまう。壁ずりの移動（第 38 章）を実装するには、**壁の法線**が要る。

### 必要な情報を洗い出す

用途を並べて、それぞれ何が要るかを考える。

| 用途 | 必要な情報 |
|---|---|
| めり込みの解消 | 法線、貫通深度 |
| 壁ずり移動 | 法線 |
| 着弾エフェクトの配置 | 接触点、法線 |
| 跳ね返り（反射） | 法線 |
| 回転を生む力の適用 | 接触点、法線、深度 |
| ダメージ判定 | 交差の有無だけでよい |
| トリガー領域への進入 | 交差の有無だけでよい |

最後の二つを除けば、**法線・深度・接触点**の三つがあれば足りる。逆にいえば、この三つを揃えれば大半の用途をカバーできる。

### 「有無だけでよい」場合も残す

一方、交差の有無だけを知りたい場面もある。そのとき、法線や深度まで計算するのは無駄である。特にブロードフェーズ（第 VI 部）では、大量のペアに対して「明らかに当たっていない」を高速に判定したい。

そこで本書では、**二つの API を並べる**。

```cpp
// 有無だけ。速い
[[nodiscard]] bool overlaps(const Circle& a, const Circle& b) noexcept;

// 詳細な情報つき。遅い
[[nodiscard]] std::optional<Contact> intersect(const Circle& a, const Circle& b) noexcept;
```

命名を分けているのが要点である。`overlaps` は「重なっているか」、`intersect` は「交差情報を求める」。呼び分けを意識させる。

**両者の結果は一致しなければならない。** `overlaps` が `true` を返すのに `intersect` が `nullopt` を返す、あるいはその逆は、バグである。これは 7.7 節でテストにする。

## 7.2 `Contact` 型

### 定義

```cpp
// collision/narrow/contact.h
#pragma once

#include "collision/math/vec2.h"

namespace collision {

// 二つの形状 A と B が交差しているときの、その交差の記述。
struct Contact {
    // A から B へ向かう単位ベクトル。A を -normal 方向へ動かせば離れる。
    Vec2 normal{};

    // 重なりの深さ。非負。normal 方向に depth だけ動かすと接触状態になる。
    float depth{};

    // 接触している位置（ワールド座標）。
    Vec2 point{};
};

} // namespace collision
```

三つのフィールドだけである。それぞれについて説明する。

### 法線 `normal`

**単位ベクトルであることを不変条件とする。** 長さが 1 でない法線を返す関数は、バグである。

なぜ単位長を強制するのか。呼び出し側が「これは単位ベクトルだ」と仮定して計算できるからである。反射ベクトルの計算 `v - 2 * dot(v, n) * n` は、`n` が単位ベクトルであることを前提にしている。長さが 1 でないと結果が狂う。

「呼び出し側で正規化すればよい」という考えもあるが、それだと**誰が正規化の責任を持つのかが曖昧になる**。二重に正規化して無駄なコストを払うか、どちらも正規化せずにバグを出すか、どちらかになる。ライブラリ側で保証するほうがよい。

### 貫通深度 `depth`

**非負であることを不変条件とする。** 「どれだけ重なっているか」なので、負になるはずがない。

「離れているときの距離」を負の深度として表す設計もありえる。実際、そういう API を持つライブラリもある。本書はそうしない。理由は、**`Contact` は「交差している」ことを前提とした型**だからである。交差していないなら `Contact` は存在しない、というのが本書の立場である（7.4 節）。

距離が必要なら、別の関数で求める。

```cpp
// 交差していないときの最短距離を求める（第 21 章で実装）
[[nodiscard]] float distance_between(const Shape auto& a, const Shape auto& b) noexcept;
```

### 接触点 `point`

**ワールド座標で表す。** どちらかの形状のローカル座標にすると、呼び出し側が変換の責任を負うことになる。

一つ悩ましい点がある。二つの形状が重なっているとき、「接触点」はどこか。厳密には、重なった領域全体が接触している。本書では次の規約を採る。

**`point` は、A の表面上の、最も深くめり込んでいる点とする。**

円と円なら、A の中心から B の中心へ向かって半径だけ進んだ点である。この規約は、押し戻しの計算やエフェクトの配置に自然に使える。

### 複数の接触点はどうするのか

箱が床に平らに乗っているとき、接触点は二つ必要である（第 1 章）。この `Contact` 型は一つしか持てない。

これは意図的である。**第 14 章まで、接触点は一つで進む。** 円と円、円と AABB のような滑らかな形状どうしでは、接触点は本質的に一つしかない。複数点が必要になるのは、面と面が接するとき、つまり多角形どうしの判定に進んでからである。

第 14 章で `ContactManifold` 型を導入し、`Contact` を複数持てるようにする。そのとき `Contact` 型自体は変えない（法線と深度はマニフォールド全体で共有し、点だけを複数持つ形にする）。**今の設計は、その拡張を妨げない。**

## 7.3 法線の向きの規約を決める

### 規約：A から B へ

`intersect(a, b)` が返す法線の向きを、**A から B へ向かう向き**と定める。本書全体でこれを守る。

言い換えると、こうなる。

- `a` を `-normal * depth` だけ動かすと、重なりが解消する
- `b` を `+normal * depth` だけ動かしても、同じく解消する
- 両方を半分ずつ動かしてもよい

```cpp
const auto c = intersect(a, b);
if (c) {
    // A だけを動かして解消する
    a.center -= c->normal * c->depth;
}
```

### なぜ規約が要るのか

規約がないと、呼び出し側で毎回「この法線はどっち向きだったか」を確認することになる。そして必ず間違える。符号を間違えると、押し戻すつもりが**さらにめり込ませる**。しかも一見それらしく動いてしまうことがあるので、発見が遅れる。

規約は、**テストで守る**（第 3.8 節）。文章で書いただけでは守られない。

```cpp
TEST_METHOD(法線がAからBへ向いていること) {
    const Circle a{{0.0f, 0.0f}, 1.0f};
    const Circle b{{1.5f, 0.0f}, 1.0f};   // 右にある

    const auto c = collision::intersect(a, b);
    Assert::IsTrue(c.has_value());
    Assert::IsTrue(c->normal.x > 0.0f, L"法線が A から B へ向いていない");
}
```

### 引数を入れ替えたときの関係

`intersect(a, b)` と `intersect(b, a)` の関係も、規約から導かれる。

- `normal` は反転する
- `depth` は同じ
- `point` は**変わる**（A の表面上の点、という規約なので）

`point` が変わる点に注意してほしい。対称性のテストを書くとき、`point` まで一致すると期待すると落ちる。

```cpp
TEST_METHOD(引数を入れ替えると法線が反転すること) {
    Rng rng(100);
    for (int i = 0; i < 1000; ++i) {
        const Circle a{{rng.uniform(-2.0f, 2.0f), rng.uniform(-2.0f, 2.0f)}, 1.0f};
        const Circle b{{rng.uniform(-2.0f, 2.0f), rng.uniform(-2.0f, 2.0f)}, 1.0f};

        const auto ab = collision::intersect(a, b);
        const auto ba = collision::intersect(b, a);

        Assert::AreEqual(ab.has_value(), ba.has_value(), L"交差の有無が食い違う");
        if (!ab) continue;

        expect_near(-ab->normal, ba->normal);
        expect_near(ab->depth,   ba->depth);
        // point は一致しない（それぞれの形状の表面上の点なので）
    }
}
```

このテストは、すべての形状ペアに対して書く価値がある。第 13 章では、任意の凸多角形ペアに対してこれを回す汎用のテストヘルパを作る。

## 7.4 「当たっていない」を表す ― `std::optional`

### 型で表現する

交差していないとき、何を返すべきか。

```cpp
// 案 1：bool と出力引数
bool intersect(const Circle& a, const Circle& b, Contact* out);

// 案 2：深度が 0 以下なら非交差
Contact intersect(const Circle& a, const Circle& b);

// 案 3：std::optional
std::optional<Contact> intersect(const Circle& a, const Circle& b);
```

本書は**案 3** を採る。

**案 1 の問題。** 出力引数は呼び出し側のコードが冗長になる。`Contact c; if (intersect(a, b, &c)) { ... }` と、二行に分かれる。加えて、`false` のときに `c` の中身が何になっているかが不定になりやすい。

**案 2 の問題。** 「交差していない状態の `Contact`」という、意味のない値が存在してしまう。法線は何を指すのか。深度が 0 のとき、それは「ちょうど接している」のか「離れている」のか。呼び出し側が `if (c.depth > 0)` を書き忘れれば、ゼロベクトルの法線で計算が進み、静かに壊れる。

**案 3 の利点。** 「値がない」ことが型で表現される。`operator*` や `->` でアクセスするとき、値があることを一度は意識する。`value_or`、`and_then`、`transform` といったモナディック操作も使える（7.6 節）。

### `std::optional` のコスト

`std::optional<Contact>` のサイズは、`Contact`（20 バイト）＋フラグ（1 バイト）＋パディングで 24 バイトになる。生の `Contact` より 4 バイト大きい。

この差が問題になる場面は、本書の範囲ではまずない。判定関数は値を返した直後に使われ、大量に保存されることは少ないからである。大量に保存する場面（マニフォールドのプール）では、そもそも `optional` ではなく別の設計を採る（第 14 章）。

### `overlaps` との併用

7.1 節で述べた `overlaps` は、`intersect` の結果を捨てる形で実装してもよいが、それでは速くならない。**独立して、必要最小限の計算だけを行う実装を書く**。

```cpp
// 円と円（第 8 章で実装する）
[[nodiscard]] constexpr bool overlaps(const Circle& a, const Circle& b) noexcept {
    const float r = a.radius + b.radius;
    return distance_squared(a.center, b.center) < r * r;
}
```

平方根も除算も正規化もない。乗算と減算だけである。これが `intersect` より速いのは明らかである。

## 7.5 「計算できなかった」を表す ― `std::expected`

### 三つ目の状態

ここまでで、判定の結果は二つの状態を取る。「交差している（`Contact` あり）」と「交差していない（`nullopt`）」。

実は三つ目がある。**「計算できなかった」**である。

具体例を挙げる。

- 半径が負の円が渡された
- 頂点が 2 個しかない「多角形」が渡された
- 座標に `NaN` が含まれていた
- GJK の反復が上限に達しても収束しなかった（第 20 章）
- EPA のポリトープが退化した（第 22 章）

これらを `nullopt` で返すのは、明確に間違いである。「交差していない」と「判定できなかった」はまったく違う。前者を信じて処理を進めるのは正常だが、後者を「交差していない」と扱うと、**壁をすり抜ける**。

### `/fp:fast` の下でこれが特に重要になる

第 4 章で見たとおり、`/fp:fast` の下では `NaN` が静かに伝播する。`x != x` による検出は最適化で消えうる。

つまり、**`NaN` が発生したことに気づく仕組みを、自分で作らなければならない**。エラーを値として返す設計は、そのための最も素直な手段である。

例外を投げる選択肢もあるが、本書では採らない。判定関数はフレームあたり数万回呼ばれることがあり、例外機構のコストと、`noexcept` を付けられなくなる不都合が大きい。

### `std::expected` を使う

C++23 の `std::expected<T, E>` は、「成功なら `T`、失敗なら `E`」を表す型である。

```cpp
// collision/narrow/contact.h（続き）
#include <expected>

namespace collision {

enum class CollisionError {
    invalid_shape,       // 形状のパラメータが不正（負の半径など）
    non_finite_input,    // 入力に NaN / Inf が含まれる
    degenerate,          // 退化した配置で法線が定義できない
    not_converged,       // 反復アルゴリズムが収束しなかった
};

// 交差していない場合も「成功」である点に注意。
// 交差の有無は std::optional で、計算の成否は std::expected で表す。
using ContactResult = std::expected<std::optional<Contact>, CollisionError>;

} // namespace collision
```

`std::expected<std::optional<Contact>, CollisionError>` という二重の入れ子になった。読みづらいので `ContactResult` という別名を付ける。

三つの状態が、それぞれ型で表現されている。

| 状態 | 表現 | 判定 |
|---|---|---|
| 交差している | `Contact` の値 | `r && r->has_value()` |
| 交差していない | `std::nullopt` | `r && !r->has_value()` |
| 計算できなかった | `CollisionError` | `!r` |

### すべての関数がこれを返すべきか

**否である。** 単純な形状の判定は、失敗しようがない。円と円の判定で「計算できない」状況は、入力が不正な場合しかない。

本書の方針はこうする。

| 判定の種類 | 戻り値 | 理由 |
|---|---|---|
| 単純な形状（円、AABB、OBB） | `std::optional<Contact>` | 失敗しない。入力の検証は呼び出し側の責任 |
| 反復アルゴリズム（GJK、EPA） | `ContactResult` | 収束しないことがある |
| 公開 API（`World` のクエリ） | `ContactResult` | 利用者に不正な入力を検出させる |

**内側は `optional`、外側は `expected`。** 性能が要求される内部では単純な型を使い、境界で検証してエラーを値に変える。これは実用的な妥協である。

第 8 章から第 14 章までは `std::optional<Contact>` だけで進む。`ContactResult` が実際に必要になるのは第 20 章（GJK）からである。

### 入力の検証

`expected` を返す層では、入力を検証する。

```cpp
// collision/narrow/validate.h
#include "collision/math/fp_bits.h"

namespace collision {

[[nodiscard]] inline bool is_finite(Vec2 v) noexcept {
    return is_finite_bits(v.x) && is_finite_bits(v.y);
}

[[nodiscard]] inline std::expected<void, CollisionError>
validate(const Circle& c) noexcept {
    if (!is_finite(c.center) || !is_finite_bits(c.radius)) {
        return std::unexpected(CollisionError::non_finite_input);
    }
    if (c.radius < 0.0f) {
        return std::unexpected(CollisionError::invalid_shape);
    }
    return {};
}

} // namespace collision
```

`is_finite_bits` は第 4.5 節で作ったビットパターン検査版である。`std::isfinite` を使わないのは、`/fp:fast` で最適化されうるためである。**エラー検出の要になる箇所では、必ずビット検査を使う。**

`std::expected<void, E>` は「成功なら値なし、失敗ならエラー」を表す。返り値を使わない検証関数に適している。

## 7.6 モナディック操作による連結

### `and_then` と `transform`

`std::optional` と `std::expected` は、C++23 でモナディック操作を持つようになった。

| 操作 | 意味 |
|---|---|
| `and_then(f)` | 値があれば `f` を適用する。`f` は同じ種類の包み型を返す |
| `transform(f)` | 値があれば `f` を適用する。`f` は素の値を返し、自動的に包まれる |
| `or_else(f)` | 値がなければ `f` を呼ぶ |
| `value_or(v)` | 値があればそれを、なければ `v` を返す（`optional` のみ） |

第 6 章の `normalize_or` で `value_or` を使った。ここではもう少し実用的な例を見る。

### 使いどころ：エラーを伝播させる

検証してから判定する、という処理を素直に書くとこうなる。

```cpp
// 素直な書き方
ContactResult intersect_checked(const Circle& a, const Circle& b) noexcept {
    if (auto v = validate(a); !v) return std::unexpected(v.error());
    if (auto v = validate(b); !v) return std::unexpected(v.error());
    return intersect(a, b);
}
```

これで十分読める。無理にモナディック操作を使う必要はない。

一方、**変換が連なるとき**は効果が出る。

```cpp
// 深度だけが欲しい場面
const float depth = intersect(a, b)
    .transform([](const Contact& c) { return c.depth; })
    .value_or(0.0f);
```

`if` と一時変数を書かずに済む。「交差していれば深度、していなければ 0」という意図が一行に収まる。

### 使いすぎない

モナディック操作は便利だが、**深く連ねると読みにくくなる**。特にラムダの中でさらに `optional` を返す処理があると、型の対応を追うのが難しくなる。

本書の方針は、**二段までなら使い、それ以上は素直に `if` で書く**である。読みやすさが第一で、記法の統一は二の次でよい。

```cpp
// これは読みやすい
const auto n = try_normalize(d).value_or(Vec2{1.0f, 0.0f});

// これは読みにくい
const auto result = validate(a)
    .and_then([&] { return validate(b); })
    .and_then([&] { return intersect(a, b).transform(...); })
    .transform([](auto&& c) { return ...; });
```

後者は `if` を三つ書いたほうが速く読める。

## 7.7 テスト：規約違反を検出する

### 規約検査ヘルパ

`Contact` に課した不変条件を、一箇所で検査できるようにする。以降のすべての判定のテストで、これを呼ぶ。

```cpp
// test_helpers.h に追加
#include "collision/narrow/contact.h"

namespace collision_tests {

// Contact の不変条件をすべて検査する。
// 判定を実装したら必ずこれを通すこと。
inline void check_contact_invariants(
        const collision::Contact& c,
        std::source_location loc = std::source_location::current()) {

    using namespace Microsoft::VisualStudio::CppUnitTestFramework;

    // (1) 値が有限であること
    Assert::IsTrue(collision::is_finite_bits(c.normal.x) &&
                   collision::is_finite_bits(c.normal.y) &&
                   collision::is_finite_bits(c.depth)    &&
                   collision::is_finite_bits(c.point.x)  &&
                   collision::is_finite_bits(c.point.y),
                   detail::widen(std::format(
                       "Contact に非有限値が含まれる at {}:{}",
                       loc.file_name(), loc.line())).c_str());

    // (2) 法線が単位長であること
    expect_near(1.0f, collision::length(c.normal), 1.0e-5f, 1.0e-5f, loc);

    // (3) 深度が非負であること
    Assert::IsTrue(c.depth >= 0.0f,
                   detail::widen(std::format(
                       "深度が負: {:.9g} at {}:{}",
                       c.depth, loc.file_name(), loc.line())).c_str());
}

} // namespace collision_tests
```

法線の許容誤差を `1e-5f` としているのは、第 6.4 節で測った `rsqrt` 近似の精度に合わせたものである。既定値の `1e-6f` では、`/fp:fast` の下で落ちる可能性がある。

**(1) の有限値チェックを最初に置いている**のが要点である。`NaN` が混入している場合、(2) の長さの比較は「`NaN` は何とも一致しない」ため必ず失敗するが、メッセージが「長さが 1 でない」となって原因が分かりにくい。先に `NaN` を検出すれば、正しい診断が出る。

### `overlaps` と `intersect` の整合性

7.1 節で述べた「両者の結果は一致しなければならない」を、テストにする。形状の種類ごとに書けるよう、テンプレートにしておく。

```cpp
// test_helpers.h に追加
template <class A, class B>
void check_overlaps_matches_intersect(const A& a, const B& b,
        std::source_location loc = std::source_location::current()) {
    using namespace Microsoft::VisualStudio::CppUnitTestFramework;

    const bool fast = collision::overlaps(a, b);
    const bool slow = collision::intersect(a, b).has_value();

    if (fast != slow) {
        Assert::Fail(detail::widen(std::format(
            "overlaps={} だが intersect={} at {}:{}",
            fast, slow, loc.file_name(), loc.line())).c_str());
    }
}
```

**このテストは、境界ぎりぎりの入力では落ちうる**（第 3.5 節の原則 3）。`overlaps` と `intersect` は違う式で計算するので、ちょうど接する状態では判定が食い違いうる。

対処として、ランダムテストでは境界付近を避けるか、食い違いの割合が閾値以下であることを検証する。第 13 章で凸多角形の等価性テストを書くとき、この考え方を本格的に使う。

### 対称性のテストヘルパ

7.3 節で書いた対称性のテストも、汎用化しておく。

```cpp
template <class A, class B>
void check_symmetry(const A& a, const B& b,
        std::source_location loc = std::source_location::current()) {
    using namespace Microsoft::VisualStudio::CppUnitTestFramework;

    const auto ab = collision::intersect(a, b);
    const auto ba = collision::intersect(b, a);

    Assert::AreEqual(ab.has_value(), ba.has_value(),
                     L"引数の順序で交差の有無が食い違う");
    if (!ab) return;

    check_contact_invariants(*ab, loc);
    check_contact_invariants(*ba, loc);

    expect_near(-ab->normal, ba->normal, 1.0e-5f, 1.0e-5f, loc);
    expect_near(ab->depth,   ba->depth,  1.0e-5f, 1.0e-5f, loc);
    // point は形状ごとに違うので比較しない
}
```

### 押し戻しの冪等性

第 3.5 節で挙げた「押し戻したらもう交差しない」という性質も、汎用ヘルパにできる。ただし形状を動かす方法が型ごとに違うので、動かし方をラムダで受け取る形にする。

```cpp
// A を translate で動かせる場合に使う
template <class A, class B, class Translate>
void check_separation_resolves(A a, const B& b, Translate translate,
        std::source_location loc = std::source_location::current()) {
    using namespace Microsoft::VisualStudio::CppUnitTestFramework;

    const auto c = collision::intersect(a, b);
    if (!c) return;   // もともと交差していないなら検証対象外

    // わずかに余分に動かす（境界ぎりぎりで判定が揺れるのを避ける）
    constexpr float margin = 1.0e-3f;
    translate(a, -c->normal * (c->depth + margin));

    Assert::IsFalse(collision::overlaps(a, b),
        detail::widen(std::format(
            "押し戻したのに交差が解消していない (depth={:.9g}) at {}:{}",
            c->depth, loc.file_name(), loc.line())).c_str());
}
```

`margin` を足しているのが実務的な工夫である。ちょうど `depth` だけ動かすと接触状態になり、判定が誤差で揺れる。1 ミリメートル余分に動かせば確実に離れる。

**この `margin` は、第 34 章で導入する「スロップ」の予告でもある。** 位置補正では、めり込みをゼロまで解消せず、わずかに残すのが実用的である。理由はまさにこの「境界での揺れ」を避けるためである。

### 型が守る規約と、テストが守る規約

この章で決めた規約を、何が守っているかを整理しておく。

| 規約 | 守るもの |
|---|---|
| 交差していないときに `Contact` を返さない | **型**（`std::optional`） |
| 計算失敗を交差なしと混同しない | **型**（`std::expected`） |
| 法線が単位長である | **テスト**（`check_contact_invariants`） |
| 深度が非負である | **テスト**（同上） |
| 法線が A から B へ向く | **テスト**（`check_symmetry`） |
| 押し戻せば解消する | **テスト**（`check_separation_resolves`） |

**型で守れるものは型で守り、守れないものはテストで守る。** これが本書の方針である。すべてを型で表現しようとすると（たとえば「単位ベクトル」型を作るなど）、コードが煩雑になり、変換のコストも増える。バランスを取る。

## この章のまとめ

- 判定関数の戻り値は `bool` では足りない。法線・貫通深度・接触点が要る
- `overlaps`（有無だけ・速い）と `intersect`（詳細つき・遅い）を並べる。結果は必ず一致させる
- `Contact` の不変条件：法線は単位長、深度は非負、接触点はワールド座標で A の表面上
- **法線は A から B へ向かう。** `a` を `-normal * depth` 動かせば解消する
- 「交差していない」は `std::optional`、「計算できなかった」は `std::expected` で表す
- 三つ目の状態を混同すると、壁をすり抜ける。`/fp:fast` 下の `NaN` 伝播を考えると特に重要
- 内側の単純な判定は `optional`、外側の公開 API と反復アルゴリズムは `expected`
- モナディック操作は二段まで。深く連ねると読みにくい
- 規約はテストにして初めて実効性を持つ。`check_contact_invariants` を全判定で通す

### 落とし穴と練習問題

**落とし穴 1：`optional` の中身を確認せずに `*` でアクセスする。**　`c->depth` と書く前に `if (c)` を通す。`value()` を使えば例外が飛ぶので、デバッグ中は `value()` のほうが安全である。

**落とし穴 2：`point` まで対称だと期待する。**　引数を入れ替えると接触点は変わる。

**落とし穴 3：`std::isfinite` を使う。**　`/fp:fast` では最適化されうる。`is_finite_bits` を使う。
