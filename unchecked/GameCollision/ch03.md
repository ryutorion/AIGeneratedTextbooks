# 第 3 章　テスト環境を整える

> **この章のゴール**
> 単体テストを書いて走らせられる状態にする。浮動小数点を比較するためのヘルパを自作し、`/fp:fast` の下でも壊れないテストの書き方を確立する。この章が終わると、以降のすべての章で使う検証の道具立てが揃う。
>
> 本書には描画がない。テストが緑になることが「動いた」の唯一の証拠である。だからこの章は、他の入門書における「ウィンドウを出す章」に相当する。ここを疎かにすると、以降ずっと足場のないまま進むことになる。

## 3.1 Visual Studio 同梱の C++ 単体テストフレームワークを使う

### 何を使うか

本書は外部ライブラリを使わない方針である。テストフレームワークも例外ではない。

幸い、Visual Studio には **Microsoft Unit Testing Framework for C++**（以下、単に「テストフレームワーク」と呼ぶ）が同梱されている。前章で「ネイティブ単体テスト プロジェクト」を作った時点で、すでに使える状態になっている。追加のインストールもパッケージマネージャも要らない。

世の中には Catch2 や doctest、GoogleTest といった優れたテストフレームワークがあり、機能面ではそれらのほうが充実している。それでも本書が同梱のものを選ぶ理由は三つある。

- **入手の手間がゼロ**。読者が最初の一歩でつまずく可能性を減らせる
- **テストエクスプローラーと統合されている**。IDE 上で結果を眺め、失敗したテストだけをデバッガで再実行できる
- **本書に必要な機能はすべて揃っている**。アサーション、セットアップ／ティアダウン、メッセージ出力があれば足りる

不足分は自分で書く。実際 3.4 節では、このフレームワークに欠けている「浮動小数点の賢い比較」を自作することになる。むしろそれが本書の主題に近い。

### 基本の書き方

テストプロジェクトに生成された `collision_tests.cpp` を開くと、こんな骨組みが入っている。

```cpp
#include "pch.h"
#include "CppUnitTest.h"

using namespace Microsoft::VisualStudio::CppUnitTestFramework;

namespace collision_tests
{
    TEST_CLASS(collision_tests)
    {
    public:
        TEST_METHOD(TestMethod1)
        {
        }
    };
}
```

登場する要素は少ない。

| 要素 | 役割 |
|---|---|
| `TEST_CLASS(名前)` | テストをまとめる単位。クラスとして展開される |
| `TEST_METHOD(名前)` | 個々のテスト。この中の処理が一件のテストとして実行される |
| `Assert::...` | 検証。失敗するとその場でテストが失敗扱いになる |
| `Logger::WriteMessage` | テスト出力への文字列出力。デバッグ時に便利 |

テストプロジェクトの成果物は実行ファイルではなく **DLL** である。テストエクスプローラーがこの DLL を読み込み、`TEST_METHOD` を列挙して呼び出す。`main` 関数は書かない。

### プリコンパイル済みヘッダを外す

生成されたコードの一行目に `#include "pch.h"` がある。前章でライブラリ側のプリコンパイル済みヘッダを外したのと同様に、テストプロジェクト側も外しておく。

1. `pch.h` と `pch.cpp` をプロジェクトから削除する
2. プロパティ → C/C++ → プリコンパイル済みヘッダー → **プリコンパイル済みヘッダー** を「使用しない」にする（すべての構成で）
3. `collision_tests.cpp` の `#include "pch.h"` を消す

本書の規模ではコンパイル時間が問題にならず、設定を一つ減らせるほうが得である。

## 3.2 最初のテスト：`Assert::AreEqual(1 + 1, 2)` を緑にする

### 書いて、走らせる

ファイル名を `test_smoke.cpp` に変え、中身を次のように書き換える。

```cpp
#include "CppUnitTest.h"

using namespace Microsoft::VisualStudio::CppUnitTestFramework;

namespace collision_tests {

TEST_CLASS(SmokeTest) {
public:
    TEST_METHOD(環境が動いていること) {
        Assert::AreEqual(2, 1 + 1);
    }
};

} // namespace collision_tests
```

テスト名に日本語を使えるのかと思われるかもしれないが、使える。`TEST_METHOD` はマクロで、渡した名前がそのまま C++ の識別子になる。C++11 以降、識別子には非 ASCII 文字を使えるので問題ない。テストエクスプローラーの一覧にも日本語で表示される。

**ソースファイルの文字コードには注意が必要である。** MSVC は BOM のない UTF-8 ファイルを、システムのロケールに応じた文字コードとして解釈することがある。プロジェクトのプロパティ → C/C++ → コマンドライン → 追加のオプション に次を加えておくと確実である。

```
/utf-8
```

これは「ソースは UTF-8、実行文字セットも UTF-8」を指定するオプションである。前章で作った `Common.props` に入れておくとよい。

日本語のテスト名に抵抗があれば、英語で書いても構わない。本書では、テストが何を検証しているかが一覧で読み取れることを優先して日本語を使う。

### `Assert::AreEqual` の引数の順序

上のコードで `Assert::AreEqual(2, 1 + 1)` と書いた。**第一引数が期待値、第二引数が実際の値**である。逆にしても結果は同じだが、失敗時のメッセージが「期待値 3 に対して実際は 2」のように出るので、順序を守らないと読み違える。

本書では一貫して「期待値、実際の値」の順で書く。

### ビルドして実行する

**テスト → テスト エクスプローラー** でウィンドウを開き、ソリューションをビルドする。テストが一覧に現れるはずである。実行すると緑のチェックが付く。

ここまで来れば環境は動いている。この `SmokeTest` は消さずに残しておくとよい。環境が壊れたときに、まずこれが通るかを見れば「ビルド環境の問題か、自分のコードの問題か」を切り分けられる。

## 3.3 テストエクスプローラーの使い方

### 覚えておくと効く操作

日常的に使うのは次の操作である。

| 操作 | 効果 |
|---|---|
| **すべてのテストを実行** | 全件実行。コミット前に必ず |
| **失敗したテストを実行** | 直前に落ちたものだけ再実行。修正のループが速くなる |
| テストを右クリック → **デバッグ** | ブレークポイントを置いてそのテストだけ実行 |
| 一覧の**グループ化**を「クラス」に | `TEST_CLASS` 単位でまとまり、見通しがよくなる |
| 検索欄に文字列 | テスト名で絞り込み |

特に「失敗したテストをデバッグ実行」は多用することになる。テストが落ちたら、まずブレークポイントを置いて値を覗く。これが最短の調査経路である。

### 失敗の読み方

わざと失敗させてみよう。

```cpp
Assert::AreEqual(2, 1 + 2);
```

テストエクスプローラーの下部に、こんなメッセージが出る。

```
Assert failed. Expected:<2> Actual:<3>
```

そして、失敗した行へジャンプできるスタックトレースが付く。

`AreEqual` が値を表示できるのは、その型の文字列化方法をフレームワークが知っているからである。`int` や `double` のような組み込み型は最初から対応している。自作の型（`Vec2` など）を `AreEqual` に渡すと、**コンパイルエラーになる**。これは 3.4 節で解決する。

### メッセージを添える

アサーションには第三引数（型によっては第四引数）としてメッセージを渡せる。型は `const wchar_t*` である。

```cpp
Assert::IsTrue(result.has_value(), L"交差しているはずなのに値が返っていない");
```

`L` プレフィックスが必要な点に注意。このワイド文字列という制約が地味に面倒で、`std::format` で組み立てた文字列を渡そうとすると変換が要る。3.4 節でこの手当てもする。

## 3.4 補助ヘッダ `test_helpers.h` を書く

ここからが本題である。標準のアサーションだけでは、浮動小数点を扱うテストは書けない。

### なぜ `Assert::AreEqual(float, float)` ではいけないのか

次のテストを書いて実行してみてほしい。

```cpp
TEST_METHOD(浮動小数点の素朴な比較) {
    float sum = 0.0f;
    for (int i = 0; i < 10; ++i) {
        sum += 0.1f;
    }
    Assert::AreEqual(1.0f, sum);   // 落ちる
}
```

`0.1f` を 10 回足しても `1.0f` にはならない。`0.1` は二進数で有限桁に表せないので、`0.1f` は「0.1 に最も近い `float`」でしかなく、足すたびに誤差が積み上がる。実際の値は `1.0000001` あたりになる。

これは `/fp:fast` のせいではない。IEEE 754 に厳密に従っても同じである。**浮動小数点に厳密な等値比較を使ってはいけない**というのは、この分野の最も基本的な作法である。

そして `/fp:fast` を選んだ本書では、この作法がさらに重要になる。コンパイラが演算の順序を入れ替えてよくなるので、誤差の出方そのものが最適化の効き具合によって変わる。Debug と Release で結果のビットが違う、ということが実際に起きる。

### 許容誤差つきの比較

テストフレームワークには許容誤差を取るオーバーロードがある。

```cpp
Assert::AreEqual(1.0f, sum, 0.0001f);   // 通る
```

これで済むならヘルパは要らない。ところが実用にはならない。理由は、**適切な許容誤差が値の大きさによって変わる**からである。

`float` の刻み幅は、値が大きいほど粗くなる。1.0 付近では約 `1.2e-7` だが、1000.0 付近では約 `6.1e-5`、100000.0 付近では約 `7.8e-3` になる。つまり、

- `0.0001f` という固定の許容誤差は、1.0 付近では緩すぎるかもしれないが、
- 100000.0 付近では**そもそも `float` で表現できない精度を要求している**ことになり、絶対に通らない

コリジョンのテストでは、原点付近の小さな図形も、原点から遠く離れた図形も扱う。固定の許容誤差では、どちらかが必ず破綻する。

### 絶対誤差と相対誤差を併用する

解決策は、絶対誤差と相対誤差の両方を見て、**どちらかを満たせば合格**とすることである。

```cpp
// test_helpers.h
#pragma once

#include <cmath>
#include <algorithm>

namespace collision_tests {

// ゼロ近傍で使う絶対許容誤差。1 単位 = 1 メートルなので、1 マイクロメートル相当
inline constexpr float default_abs_tol = 1.0e-6f;

// 値の大きさに比例する相対許容誤差
inline constexpr float default_rel_tol = 1.0e-5f;

[[nodiscard]] inline bool nearly_equal(float expected, float actual,
                                       float abs_tol = default_abs_tol,
                                       float rel_tol = default_rel_tol) noexcept {
    const float diff = std::fabs(expected - actual);

    // (1) 絶対誤差での判定。ゼロ近傍ではこちらが効く
    if (diff <= abs_tol) {
        return true;
    }

    // (2) 相対誤差での判定。大きな値ではこちらが効く
    const float scale = std::max(std::fabs(expected), std::fabs(actual));
    return diff <= rel_tol * scale;
}

} // namespace collision_tests
```

二段構えにする理由をもう少し説明しておく。

**相対誤差だけでは、ゼロ近傍で機能しない。** 期待値が `0.0f` のとき `rel_tol * scale` はほぼゼロになるので、事実上の厳密比較になってしまう。「本来ゼロになるはずの値が計算誤差で `1e-9` になった」というごく普通の状況で落ちる。

**絶対誤差だけでは、大きな値で機能しない。** 前述のとおり、`float` の表現能力を超えた精度を要求してしまう。

両方を見れば、どちらの領域でも妥当に振る舞う。ちなみに、この二つの定数の値をどう決めたのかは次章（4.3 節）で扱う。今は「1 単位 = 1 メートル、1 マイクロメートルの差は無視してよい」という単位系からの逆算だと理解しておけばよい。

### アサーションとして使えるようにする

`nearly_equal` は `bool` を返す関数なので、`Assert::IsTrue` に渡せば動く。だが失敗したときに「何と何を比べて落ちたのか」が分からない。値を表示するようにする。

```cpp
// test_helpers.h（続き）
#include "CppUnitTest.h"
#include <format>
#include <string>
#include <source_location>

namespace collision_tests {

namespace detail {

// std::format の結果をワイド文字列へ。CppUnitTest がワイド文字列しか受け取らないため
[[nodiscard]] inline std::wstring widen(std::string_view s) {
    return std::wstring(s.begin(), s.end());   // ASCII 前提の簡易版
}

} // namespace detail

inline void expect_near(float expected, float actual,
                        float abs_tol = default_abs_tol,
                        float rel_tol = default_rel_tol,
                        std::source_location loc = std::source_location::current()) {
    if (nearly_equal(expected, actual, abs_tol, rel_tol)) {
        return;
    }

    const float diff = std::fabs(expected - actual);
    const auto msg = std::format(
        "expected={:.9g} actual={:.9g} diff={:.9g} (abs_tol={:g} rel_tol={:g}) at {}:{}",
        expected, actual, diff, abs_tol, rel_tol,
        loc.file_name(), loc.line());

    Microsoft::VisualStudio::CppUnitTestFramework::Assert::Fail(
        detail::widen(msg).c_str());
}

} // namespace collision_tests
```

いくつか説明を要する点がある。

**`{:.9g}` という書式。** `float` の値を 10 進で書き出して読み戻したとき、元のビットパターンが完全に復元されるのに必要な桁数は 9 桁である。これより少ないと、「表示上は同じ値なのにテストが落ちる」という混乱が起きる。誤差の議論をするときは、必ず 9 桁で出す。

**`std::source_location`。** C++20 の機能で、既定引数として書いておくと呼び出し元の位置が自動的に入る。マクロを使わずに「どの行で失敗したか」を表示できる。テストフレームワークにも行番号を渡す仕組み（`__LINEINFO__`）はあるが、マクロを増やすよりこちらが素直である。

**`widen` の手抜き。** `std::string` から `std::wstring` への変換を一文字ずつのコピーで済ませている。これは ASCII の範囲でしか正しくないが、この関数が出力するのは数値と ASCII のファイルパスなので実用上は困らない。日本語を含むメッセージを渡したくなったら、`MultiByteToWideChar` を使う実装に差し替える。

### 自作の型を表示できるようにする

第 6 章で `Vec2` を作ると、`Assert::AreEqual(expected_vec, actual_vec)` と書きたくなる。そのままではコンパイルエラーになるが、フレームワークに文字列化の方法を教えれば通るようになる。

```cpp
// vec2.h を作った後で test_helpers.h に追加する
namespace Microsoft::VisualStudio::CppUnitTestFramework {

template <>
inline std::wstring ToString<collision::Vec2>(const collision::Vec2& v) {
    return collision_tests::detail::widen(std::format("({:.9g}, {:.9g})", v.x, v.y));
}

} // namespace ...
```

`ToString` をこの名前空間で特殊化しておくと、`Assert::AreEqual` も `Assert::IsTrue` の失敗メッセージも、この形式で値を表示してくれる。ただし `AreEqual` は厳密比較なので、`Vec2` に対して使うのは推奨しない。**ベクトル用の `expect_near` を別に用意する**のが正しい。

```cpp
// 第 6 章で追加する
inline void expect_near(const collision::Vec2& expected,
                        const collision::Vec2& actual, ...) {
    expect_near(expected.x, actual.x, ...);
    expect_near(expected.y, actual.y, ...);
}
```

成分ごとに比較する形になる。これでよいかは議論の余地があり（ベクトルの差のノルムで見る流儀もある）、第 6 章で改めて検討する。

### 乱数生成器

多くのテストでランダムな入力を使う。共通の生成器をここで用意しておく。

```cpp
// test_helpers.h（続き）
#include <random>

namespace collision_tests {

// テストごとに新しく作り、シードは常に固定する
class Rng {
public:
    explicit Rng(std::uint32_t seed) : engine_(seed) {}

    [[nodiscard]] float uniform(float lo, float hi) {
        return std::uniform_real_distribution<float>(lo, hi)(engine_);
    }

private:
    std::mt19937 engine_;
};

} // namespace collision_tests
```

**シードは必ず明示的に固定する。** 時刻でシードすると、失敗したテストが再現できなくなる。「昨日は通ったのに今日落ちた」の原因調査に何時間も溶かすことになる。

固定シードだと入力の多様性が下がるのでは、という懸念はもっともである。対処としては、シードを変えた複数のテストを並べる、あるいはループの中でシードを `0, 1, 2, ...` と変える。いずれにせよ、**どのシードで落ちたかが分かる形**にしておくことが肝心である。

なお、乱数エンジン自体は整数演算で動くので、`/fp:fast` の影響を受けない。同じシードなら常に同じ整数列が出る。`uniform_real_distribution` による `float` への変換部分は浮動小数点演算だが、同一バイナリなら再現する。

## 3.5 `/fp:fast` の下で崩れないテストの書き方

ここは本書の方針に直結する節である。前章で `/fp:fast` を選んだ以上、テストの書き方も相応に変える必要がある。

### 原則 1：ビット一致を要求しない

**`Assert::AreEqual(float, float)` の二引数版は使わない。** これはチームの規約として明文化してよいレベルの話である。

`/fp:fast` の下では、コンパイラは演算の順序を入れ替え、`a*b+c` を FMA 命令に融合し、除算を逆数の乗算に置き換える。同じ数式でも、インライン展開されるかどうかによって生成される命令列が変わり、結果のビットが変わる。Debug と Release で違う値になるのは異常ではなく、想定内の挙動である。

使ってよいのは三引数版（許容誤差つき）か、自作の `expect_near` である。本書では後者に統一する。

例外は、**厳密にゼロや厳密に整数値になるべき場面**である。たとえば「交差していない」を表す `std::nullopt` が返ることの確認や、接触点の個数が 2 であることの確認は、整数・真偽値の比較なので厳密でよい。

### 原則 2：値ではなく性質を検証する

これが `/fp:fast` に強いテストの核心である。

具体的な数値を期待するテストは、誤差の影響を直接受ける。一方、**性質**を検証するテストは、値が多少揺れても成立する。コリジョンのコードで検証できる性質には、たとえばこういうものがある。

| 性質 | 具体例 |
|---|---|
| **不変条件** | 返される法線は常に単位長である。貫通深度は常に非負である |
| **対称性** | `intersect(a, b)` と `intersect(b, a)` は、法線の向きが反転する以外は一致する |
| **単調性** | 二つの円を離していくと、距離は単調に増加する |
| **冪等性** | 押し戻しを適用した後にもう一度判定すると、もう交差していない |
| **等価性** | GJK の結果は、SAT の結果と（境界近傍を除いて）一致する |

たとえば「円 A と円 B の判定」を、こう書く代わりに：

```cpp
// 誤差に弱い書き方
expect_near(0.5f, contact->depth);
```

こう書く：

```cpp
// 性質を検証する書き方
Assert::IsTrue(contact.has_value());
expect_near(1.0f, length(contact->normal));       // 法線は単位長
Assert::IsTrue(contact->depth >= 0.0f);           // 深度は非負
// 押し戻したらもう交差しない
Circle moved = a;
moved.center -= contact->normal * contact->depth;
Assert::IsFalse(intersect(moved, b).has_value());
```

後者は、実装の細部が変わっても壊れにくい。そして、**バグを見つける能力はむしろ高い**。「深度が 0.5 である」ことより「押し戻したら交差が解消する」ことのほうが、本当に検証したい性質だからである。

もちろん、具体値のテストが不要なわけではない。解析解が分かっている単純なケース（中心間距離 3、半径 2 と 2 の円なら深度 1）は、具体値で検証する価値がある。両方を書くのが理想である。

### 原則 3：境界ぎりぎりの入力をテストしない

二つの図形がちょうど接している状態、つまり距離がぴったりゼロの状態は、テスト入力として不適切である。交差していると判定されるか、していないと判定されるかは、誤差の出方次第で変わる。どちらが正解とも言えない。

代わりに、**境界の近くで結果が単調に変化すること**を検証する。

```cpp
TEST_METHOD(接触の境界付近で結果が単調に変化すること) {
    // 半径 1 の円を、距離 1.9 から 2.1 まで動かす
    bool was_intersecting = true;
    for (float d = 1.9f; d <= 2.1f; d += 0.005f) {
        const bool now = intersect(Circle{{0,0},1.0f}, Circle{{d,0},1.0f}).has_value();
        // 一度離れたら、二度と交差しない（単調性）
        Assert::IsTrue(was_intersecting || !now, L"判定が交差→非交差→交差と揺れた");
        was_intersecting = now;
    }
}
```

境界がぴったり 2.0 にあるかどうかは問わない。「行ったり来たりしない」ことだけを問う。これが `/fp:fast` の下で意味のある検証である。

### 原則 4：Debug と Release で違ったら、まず許容誤差を疑う

構成によって結果が変わったとき、最初に疑うべきは最適化のバグではなく、**自分の許容誤差の設計**である。

前章で `/fp:fast` を両構成に揃えたので、残る差はインライン展開の有無に起因するものが主である。インライン展開されると中間結果がレジスタに保持され、されないと一度メモリへ書き戻される。この差が、丸めのタイミングの差になって現れる。

これは正常な動作である。この差で落ちるテストは、許容誤差が実態に対して厳しすぎる。

順序としては、次のように調べる。

1. 落ちたときの `expected` と `actual` の差（`expect_near` が表示する `diff`）を見る
2. その差が、値の大きさに対して `1e-7` オーダーなら、単なる丸めの差である。許容誤差を緩める
3. `1e-3` オーダー以上なら、丸めでは説明できない。アルゴリズムかコードにバグがある

### 原則 5：乱数のシードは固定する

3.4 節で述べたとおりである。加えて、**ランダムテストで落ちたときは、その入力を固定値のテストとして書き足す**習慣を持つとよい。回帰テストが自然に増えていく。

## 3.6 テストプロジェクトだけ `/fp:precise` にしてはいけない理由

一見すると魅力的な案がある。「ライブラリは `/fp:fast` で速く、テストは `/fp:precise` で厳密に検証する」というものである。

これは**やってはいけない**。理由を説明する。

### テストが本番と違うコードを検証してしまう

本書のライブラリはヘッダ主体である。`Vec2` の演算も、円と円の判定も、多くはヘッダに書かれたインライン関数である。つまり、**その実体はテストプロジェクト側でコンパイルされる**。

テストプロジェクトを `/fp:precise` にすると、テストが検証するのは `/fp:precise` でコンパイルされた関数である。利用者が `/fp:fast` でコンパイルして使う関数とは、生成される命令列が違う。

テストが緑でも、本番で同じように動く保証がない。これはテストとして意味をなさない。

### 「厳密に検証する」は幻想である

そもそも、`/fp:precise` にしたところで結果が一意に決まるわけではない。インライン展開や最適化レベルによる差は依然として残る。「精度モデルを厳密にすればビット一致でテストできる」という期待は、`/fp:strict` でも完全には満たされない。

正しい方向は逆である。**結果が揺れることを前提にしたテストを書く**。3.5 節の五原則はそのための指針である。

### 例外：切り分けのための追加構成

ただし、`/fp:precise` のビルドがまったく無用というわけではない。第 40 章では、CI 用の追加構成として「`/fp:precise` かつ FTZ/DAZ 無効」のビルドを用意することを勧める。これは**通常の検証手段ではなく、バグの切り分け道具**である。

あるテストが落ちたとき、精度優先ビルドでも落ちるならアルゴリズムのバグ、精度優先ビルドでは通るなら `/fp:fast` に起因する問題、という切り分けができる。第一の構成は常に `/fp:fast` であり、精度優先ビルドはあくまで保険である。この区別を混同しないでほしい。

## 3.7 テストフィクスチャの雛形

### モジュール単位の初期化フック

テストフレームワークには、テスト実行の前後に呼ばれるフックがいくつかある。

| マクロ | 呼ばれるタイミング |
|---|---|
| `TEST_MODULE_INITIALIZE(名前)` | テスト DLL 全体で最初に一度 |
| `TEST_MODULE_CLEANUP(名前)` | テスト DLL 全体で最後に一度 |
| `TEST_CLASS_INITIALIZE(名前)` | 各 `TEST_CLASS` の最初に一度 |
| `TEST_METHOD_INITIALIZE(名前)` | 各 `TEST_METHOD` の前に毎回 |
| `TEST_METHOD_CLEANUP(名前)` | 各 `TEST_METHOD` の後に毎回 |

このうち `TEST_MODULE_INITIALIZE` に、テスト全体の前提を設定する場所を作っておく。今は空でよいが、**第 5 章でここに重要な処理を追加する**。

```cpp
// test_main.cpp
#include "CppUnitTest.h"
#include "test_helpers.h"

using namespace Microsoft::VisualStudio::CppUnitTestFramework;

namespace collision_tests {

TEST_MODULE_INITIALIZE(ModuleSetup) {
    // ここでテスト実行環境の前提を揃える。
    // 第 5 章で、浮動小数点ユニットの設定（FTZ/DAZ）をここに追加する。
    // 本番と同じ実行時状態でテストしないと、テストの意味が失われるため。
    Logger::WriteMessage(L"collision_tests: module initialized\n");
}

} // namespace collision_tests
```

なぜ今のうちに空のフックを置くのか。第 5 章になってから「テストの初期化はどこに書くのか」を探すより、**置き場所が先に決まっている**ほうが素直に読めるからである。

もう一つ実務的な理由がある。`TEST_MODULE_INITIALIZE` はテスト DLL 全体で一度しか呼ばれないので、**複数のテストクラスに散らばった重複した初期化を防げる**。設定を一箇所に集約する場所として、最初に確保しておく価値がある。

### `TEST_METHOD_INITIALIZE` を安易に使わない

テストごとに共通の準備をしたくなったら `TEST_METHOD_INITIALIZE` が使えるが、本書ではほとんど使わない。

理由は、テストの独立性を保ちたいからである。フィクスチャで作った状態を複数のテストが共有すると、「どのテストが何に依存しているか」が読みづらくなる。本書のテストは入力データが小さいので、各テストの中で必要なものをその場で作るほうが読みやすい。

共通の生成処理が本当に必要なら、フィクスチャよりも**ヘルパ関数**を勧める。呼び出し側に明示的に書かれるので、依存関係が見える。

## 3.8 「テストを先に書く」流儀を本書でどう運用するか

### 厳密な TDD はやらない

テスト駆動開発（TDD）の作法では、失敗するテストを書き、それを通す最小限の実装をし、リファクタリングする、というサイクルを回す。本書はこの流儀を全面的には採用しない。

理由は、コリジョンの実装には**数学的な導出が先にある**からである。線分と線分の最近接点を求める式は、テストを先に書いても出てこない。紙の上で導出してから実装するほうが自然であり、その順序を歪めたくない。

### 本書が守る三つのこと

代わりに、次の三つを守る。

**1. 実装の直後に必ずテストを書く。**　章をまたがない。関数を書いたら、その章のうちにテストを書く。「後でまとめて」は必ず先送りされる。

**2. 失敗を先に見る場面を意図的に作る。**　特に退化ケースについては、まずナイーブな実装を書き、それが壊れる入力をテストで示してから、修正する。「なぜこの分岐が必要なのか」が体感として残る。

たとえば第 8 章の円と円の判定では、まず中心が一致するケースを考えずに実装し、そこで法線がゼロ除算になることをテストで暴いてから、対処を入れる。

**3. バグを見つけたら、まず再現するテストを書く。**　修正より先にテストを書く。これは TDD の中で最も価値のある部分で、本書でも徹底する。

### テストの粒度

一つの `TEST_METHOD` で検証することは、一つに絞る。落ちたときに原因が特定しやすい。

```cpp
// 良くない：何が壊れたのか分からない
TEST_METHOD(円の判定) {
    // 離れているケース、接触ケース、めり込みケース、同心ケースを全部詰め込む
}

// 良い：落ちた時点で状況が分かる
TEST_METHOD(離れた円は交差しないこと) { ... }
TEST_METHOD(めり込んだ円の法線が中心を結ぶ向きであること) { ... }
TEST_METHOD(同心の円でも法線が単位長であること) { ... }
```

テスト名は「〜であること」「〜しないこと」の形で、**検証している性質そのもの**を書く。`Test1` のような名前は、失敗一覧を見たときに何も伝えない。

### テストは仕様書である

本書のテストは、単なる品質保証の道具ではない。「この関数は何を保証するのか」を実行可能な形で書き残したものである。

たとえば「法線は常に A から B への向き」という規約（第 7 章で決める）は、文章で書いても守られる保証がない。テストで書けば、破ったときに落ちる。**規約はテストにすることで初めて実効性を持つ。**

このため本書では、規約を決めるたびに、それを検査するテストを対で用意する。第 7 章で `Contact` 型を設計するとき、この方針が具体的な形になる。

## この章のまとめ

- テストフレームワークは Visual Studio 同梱のものを使う。不足分は自作する
- `Assert::AreEqual(float, float)` の二引数版は使わない。`expect_near` に統一する
- 許容誤差は絶対誤差と相対誤差の併用。どちらかを満たせば合格とする
- `/fp:fast` の下では、**値ではなく性質を検証する**のが主戦略。不変条件・対称性・単調性・冪等性・等価性
- 境界ぎりぎりの入力はテストしない。境界近傍での単調性を見る
- 乱数のシードは必ず固定する
- テストプロジェクトだけ `/fp:precise` にしてはいけない。テストが本番と違うコードを検証することになる
- `TEST_MODULE_INITIALIZE` を用意しておく。第 5 章でここに実行時の浮動小数点設定を追加する

### 落とし穴と練習問題

**落とし穴 1：文字コード。**　日本語のテスト名やメッセージが文字化けするなら `/utf-8` オプションを確認する。

**落とし穴 2：テストが一覧に出ない。**　テストプロジェクトが DLL としてビルドされているか、ビルドが成功しているかを確認する。ビルドエラーがあると、古い DLL のテストが表示されたままになることがある。

**落とし穴 3：`ToString` の特殊化を書く場所。**　`Microsoft::VisualStudio::CppUnitTestFramework` 名前空間の中でなければ効かない。かつ、そのテスト型を使う `.cpp` より前にインクルードされている必要がある。

---

**練習問題 3-1**　`nearly_equal` に、両方が `NaN` の場合の入力を与えるとどうなるか確認しよう。`NaN != NaN` なので `diff` は `NaN` になり、あらゆる比較が `false` になる。つまり「`NaN` は何とも一致しない」という振る舞いになる。これは望ましいだろうか。テストで `NaN` が返ったことを検出したい場合、どう書けばよいか考えてみてほしい（第 4 章で `/fp:fast` 下の `NaN` 検出を扱う）。

**練習問題 3-2**　`expect_near` の許容誤差を極端に小さく（`1e-9f`）して、3.4 節の「`0.1f` を 10 回足す」テストを走らせてみよう。失敗メッセージに表示される `diff` の値を記録する。次に足す回数を 100 回、1000 回に増やし、`diff` がどう増えるかを観察する。誤差は回数に対してどう増えるだろうか。

**練習問題 3-3**　同じ加算を、`float` ではなく `double` で行うとどうなるか比べてみよう。次章で扱う「精度」の話の予習になる。

**練習問題 3-4**（発展）　`widen` の実装は ASCII 以外で壊れる。`MultiByteToWideChar` を使った正しい実装に差し替えてみよう。ただし Windows API に依存することになるので、本書のライブラリ本体では使えない（テストコード限定なら問題ない）。この「テストコードは本体より制約が緩い」という考え方は、実務でも有用である。

---

次章では、テストを支える理論的な足場を固める。浮動小数点の刻み幅、許容誤差の決め方、そして `/fp:fast` がコンパイラに何を許可したのかを具体的に見ていく。この章で `1.0e-6f` と `1.0e-5f` という数値を天下り的に使ったが、その根拠もそこで示す。
