# 第 38 章　キャラクターコントローラ

> **この章のゴール**
> プレイヤーが操作するキャラクタを、**ここまで作った剛体シミュレーションで動かしてはいけない。**
>
> 理由をまず述べ、代わりに使う **collide-and-slide** を実装する。壁に当たったら滑る、坂は登る、崖では落ちる——ゲームの「気持ちよさ」を作るのは物理法則ではなく、意図的に設計された規則である。
>
> そして collide-and-slide 固有の落とし穴を数字で押さえる。**鋭角の谷に真下へ落とすと、キャラクタは横に 34 センチずれる。**

---

## 38.1 剛体シミュレーションを使わないという選択

### 何が困るのか

第 35〜37 章の剛体をプレイヤーに使うと、次のことが起きる。

**1. 止まらない。** 走って入力を止めても、慣性で滑る。摩擦を上げると今度は加速が鈍い。「キビキビ動く」と「物理的に正しい」は両立しない。

**2. 転ぶ。** 段差に足を引っかけると回転する。カプセルにすれば転がる。**プレイヤーが望んでいないのに姿勢が変わる**のは、操作感を根本から壊す。

**3. 坂で滑り落ちる。** 摩擦係数を上げれば止まるが、そうすると急な坂も登れてしまう。「45 度までは登れて、それ以上は登れない」という規則を、摩擦係数で表現することはできない。

**4. 押し出しが読めない。** 狭い場所で複数の壁に挟まれると、ソルバの反復結果に位置が委ねられる。**プレイヤーの入力と結果の対応が壊れる。**

### 代わりに何をするか

**キャラクタは「動かしたい量」を毎フレーム宣言し、それを geometry が許す範囲まで進める。**

```cpp
// collision/character/controller.h
struct CharacterController {
    Vec2  position{};
    Vec2  velocity{};          // ゲームロジックが直接書き換えてよい
    float radius{0.4f};
    float height{1.8f};

    // 設計パラメータ（物理量ではなく、ゲームの規則）
    float max_slope_angle{45.0f};    // これより急な面は「壁」
    float step_height{0.35f};        // これ以下の段差は乗り越える
    float skin_width{0.02f};         // 面から常に離しておく厚み
};
```

**`max_slope_angle` は物理量ではない。** 摩擦から導かれるものでもない。**ゲームデザインの数値である。** ここが剛体との決定的な違いである。

### キネマティック剛体として世界に置く

キャラクタ自身は剛体ソルバの対象外だが、**他の物体は押せる**必要がある。

**第 35.4 節のキネマティック剛体として登録する。** 位置はコントローラが決め、他の物体はそれに押される。押し返されはしない。

**「重い箱は押せない」という挙動が欲しいなら、押した相手の質量を見て、コントローラ側で進む量を減らす。** 物理ではなく規則として実装する。

## 38.2 collide-and-slide の実装

### 基本の形

移動したい量 `delta` を与える。**進めるところまで進み、当たったら残りを面に沿わせて、また進む。** これを数回繰り返す。

```cpp
Vec2 CharacterController::move(const World& world, Vec2 delta) const {
    Vec2 pos = position;
    Vec2 remaining = delta;

    for (int iteration = 0; iteration < max_slide_iterations; ++iteration) {
        if (length_squared(remaining) < min_length2) break;    // 第 5.9 節

        // 第 32.4 節のスイープクエリ ＋ 第 17 章のスイープ判定
        const auto hit = world.sweep(shape_at(pos), remaining, filter);
        if (!hit) { pos += remaining; break; }                  // 何にも当たらない

        // 面の手前 skin_width まで進む
        const float advance = std::max(0.0f, hit->t - skin_width / length(remaining));
        pos += remaining * advance;

        // 残りを面に射影する ＝ 滑る
        const Vec2 rest = remaining * (1.0f - advance);
        remaining = rest - hit->normal * dot(rest, hit->normal);
    }
    return pos;
}
```

**要点は 1 行、`rest - n·dot(rest, n)` である。** 残りの移動量から法線成分を取り除く。これが「面に沿って滑る」の全てである。

第 24.4 節で `build_basis` を作ったときと同じ、**射影による成分の除去**である。

### skin_width が要る理由

面にぴったり寄せると、次のフレームの判定で「めり込んでいる」と「離れている」の境界に立つことになる。**`/fp:fast` の下では、どちらに転ぶか分からない。**

**常に少しだけ離しておく。** `skin_width = 0.02`（2 cm）程度で十分である。

これは第 34.3 節の `slop` と目的が逆であることに注意してほしい。**剛体では「接触を保つために少しめり込ませる」、キャラクタでは「境界を避けるために少し離す」。**

理由の違いは、**キャラクタには接触の永続性が要らない**ことにある。毎フレーム独立にスイープするので、接触が消えても困らない。

### 反復回数と、鋭角の谷の問題

30 度の傾斜が向かい合う鋭角の谷に、キャラクタを真下へ落とす実験をした。**左右対称なので、横方向にずれるはずがない。**

| 最大反復 | 最終位置 (x, y) | 実際の反復数 |
|---:|---|---:|
| 1 | (0.00000, 0.57977) | 1 |
| 2 | (0.00210, 0.57856) | 2 |
| **3** | **(0.34255, 0.77513)** | 2 |
| 4 | (0.34255, 0.77513) | 2 |
| 8 | (0.34255, 0.77513) | 2 |

**反復を 3 回以上許すと、キャラクタが横に 34 センチ飛ぶ。**

原因は連鎖である。左の斜面に沿って滑る → その方向が右の斜面に向かう → 右の斜面に沿って滑る → その方向が上向き成分を持つ → 谷から押し出される。

**「滑る」を繰り返すと、入力にない方向へ動くことがある。** 対策は三つある。

**対策 1：反復回数を抑える。** 2〜4 回が実用値である。多いほど「正しく」滑るが、こうした暴走が起きやすい。

**対策 2：進行方向の逆行を禁じる。**

```cpp
// 滑った結果が、元の移動方向と逆を向いたら止める
if (dot(remaining, delta) < 0.0f) break;
```

**対策 3：当たった面を覚えておき、二度目以降は両方の面に沿う方向へ射影する（crease）。**

```cpp
// 2 枚目の面に当たったら、2 面の交線方向へ射影する
if (previous_normal) {
    const Vec2 crease = perpendicular(hit->normal);   // 2D では交線は 1 方向
    remaining = crease * dot(rest, crease);
    if (dot(hit->normal, *previous_normal) < -0.9f) remaining = Vec2{};  // 挟まれた
}
```

**本書は対策 1 と 2 を採る。** 実装が小さく、症状の 9 割が消える。対策 3 は 3D で必要性が上がる（面が 3 枚以上あるため）。

## 38.3 斜面の登坂角、段差の乗り越え、地面接地判定

### 登坂角

**面の法線が上を向いている度合いで、「床」か「壁」かを決める。**

```cpp
[[nodiscard]] bool is_walkable(Vec2 normal, float max_slope_angle) noexcept {
    // 法線と真上のなす角が max_slope_angle 以下なら歩ける
    return normal.y >= std::cos(max_slope_angle * std::numbers::pi_v<float> / 180.0f);
}
```

**`cos` の比較で済む。** 逆三角関数を呼ぶ必要はない。`cos(45°) = 0.7071` をあらかじめ計算して保持しておけば、実行時のコストはゼロである。

歩けない面は**壁として扱う**。つまり、滑らせるときに上向きの成分を取り除く。

```cpp
Vec2 slide_direction(Vec2 rest, Vec2 normal, bool walkable) noexcept {
    Vec2 out = rest - normal * dot(rest, normal);
    if (!walkable) out.y = std::min(out.y, 0.0f);   // 壁を「登れない」ようにする
    return out;
}
```

**この 1 行がないと、急斜面を滑って登れてしまう。** 滑る方向には上向き成分が含まれるからである。

### 自然な登坂の限界

`is_walkable` を入れない場合でも、傾斜が急になれば自然に登りにくくなる。1 フレーム 0.1 m 前進、重力 0.02 m/フレームで 60 フレーム走らせた。

| 斜面 | 60 フレーム後の水平到達距離（平地なら 6.0 m） |
|---:|---:|
| 0° | 6.0000 |
| 15° | 6.0000 |
| 30° | 5.9663 |
| 45° | 5.4000 |
| 60° | **0.9804** |

**60 度でようやく登れなくなる。** つまり「自然に任せると、かなり急な坂まで登れてしまう」。

**`max_slope_angle` を明示的に設けるのは、この自然な falloff がゲームの意図と合わないからである。** 「45 度でぴたりと止まる」という挙動は、規則として書かないと得られない。

### 段差の乗り越え

小さな段差でつっかえると、階段が登れない。**当たった相手が段差なら、いったん持ち上げてから進む。**

```cpp
std::optional<Vec2> try_step_up(const World& world, Vec2 pos, Vec2 delta) const {
    // ① step_height だけ上へ持ち上げる（頭がつかえないか確認する）
    const Vec2 lifted = pos + Vec2{0.0f, step_height};
    if (world.overlap(shape_at(lifted), filter)) return std::nullopt;

    // ② 水平に進む
    const Vec2 advanced = move_horizontal(world, lifted, delta);
    if (length_squared(advanced - lifted) < min_length2) return std::nullopt;

    // ③ 下へ落とし、着地点が歩ける面ならその位置を採る
    const auto ground = world.sweep(shape_at(advanced),
                                    Vec2{0.0f, -step_height * 1.1f}, filter);
    if (!ground || !is_walkable(ground->normal, max_slope_angle)) return std::nullopt;

    return advanced + Vec2{0.0f, -step_height * 1.1f * ground->t};
}
```

**「上げる → 進む → 下ろす」の三段構えである。** ①〜③ のどれかが失敗したら段差ではないので、通常の滑りに戻す。

**② で進めなかったら諦める**のが要点である。持ち上げても進めないなら、それは段差ではなく壁である。

### 地面接地判定

「地面に触れているか」は、ジャンプ・アニメーション・落下ダメージのすべてが参照する。**キャラクターコントローラで最も多くのバグを生む判定でもある。**

```cpp
struct GroundInfo {
    bool  grounded{};
    Vec2  normal{0.0f, 1.0f};
    std::uint32_t body{};
};

GroundInfo CharacterController::probe_ground(const World& world, Vec2 pos) const {
    // 足元へ少しだけスイープする。skin_width の 2 倍程度
    const auto hit = world.sweep(shape_at(pos), Vec2{0.0f, -skin_width * 2.0f}, filter);
    if (!hit || !is_walkable(hit->normal, max_slope_angle)) return GroundInfo{};
    return GroundInfo{.grounded = true, .normal = hit->normal, .body = hit->body};
}
```

**距離をケチると、坂を下るときに接地が途切れる。** 逆に長すぎると、崖から落ちても接地したままになる。

**実務上は「コヨーテタイム」を入れる。** 接地が切れてから数フレームはジャンプを許す。

```cpp
// 接地が切れてから 6 フレーム（0.1 秒）はジャンプできる
if (ground.grounded) coyote_timer_ = coyote_frames;
else if (coyote_timer_ > 0) --coyote_timer_;

const bool can_jump = coyote_timer_ > 0;
```

**これは物理的には間違っているが、操作感は劇的に良くなる。** キャラクターコントローラが物理シミュレーションと別物である理由が、ここに凝縮されている。

### 動く床に乗る

エレベータや動く足場（第 35.4 節のキネマティック剛体）に乗ったとき、**キャラクタは一緒に運ばれてほしい。**

**剛体なら摩擦が運んでくれるが、キャラクタには摩擦がない。** 明示的に実装する。

```cpp
void CharacterController::apply_platform_motion(const World& world, float dt) {
    if (!ground_.grounded) { platform_ = std::nullopt; return; }

    const RigidBody& p = world.body(ground_.body);
    if (p.type != BodyType::Kinematic) { platform_ = std::nullopt; return; }

    // 床の、キャラクタが立っている点の速度（第 35.2 節）
    const Vec2 r = position - p.position;
    position += point_velocity(p, r) * dt;
    platform_ = ground_.body;
}
```

**接地している床の「その点の」速度を使う**のが要点である。回転する足場では、中心から離れるほど速く運ばれる。

**そして床の移動を先に適用してから、プレイヤーの入力を処理する。** 逆にすると、足場が動いた分だけ入力が食われる。

### めり込んだ状態から始まったら

キャラクタがスポーンした瞬間、壁の中にいることがある。**スイープでは救えない**（スイープは「離れているところから当たる」を扱う手法である）。

**重なり判定で押し出す専用の処理が要る。**

```cpp
// スイープの前に一度だけ、重なりを解消する
Vec2 pos = depenetrate(world, position);     // 38.4 節
```

**毎フレーム呼んでよい。** 通常は重なりがないので即座に返る。**「異常時だけの処理」を通常経路に置いておくと、異常が起きたときに勝手に回復する。**

第 34 章の位置補正と同じ考え方だが、**キャラクタでは `slop` を使わず、`skin_width` ぶん余分に離す**（38.2 節）。

### しゃがみと高さの変化

高さを縮めるのは安全だが、**戻すときは頭上を確認する必要がある。**

```cpp
bool CharacterController::try_stand(const World& world) {
    const float saved = height;
    height = standing_height;
    if (world.overlap(shape_at(position), filter)) {   // 頭がつかえる
        height = saved;
        return false;
    }
    return true;
}
```

**確認せずに戻すと、天井に頭がめり込んだ状態になる。** そこから `depenetrate` が働くと、**キャラクタが床を突き抜けて下へ押し出される**ことがある。38.4 節で床を最優先にしたのは、こうした事故を減らすためでもある。

## 38.4 天井・壁との押し戻しの優先順位

### 複数の面に同時に当たる

角に押し込まれたキャラクタは、床・壁・天井の三つに同時に接することがある。**すべてを同時に満たせないとき、何を優先すべきか。**

**優先順位を明示的に決める。**

| 優先 | 対象 | 理由 |
|---:|---|---|
| 1 | **床（歩ける面）** | 地面をすり抜けると即座にゲームが壊れる |
| 2 | 壁（歩けない面） | すり抜けると壁抜けバグになる |
| 3 | 天井 | 押し戻せなくても、頭がめり込んで見えるだけ |

```cpp
Vec2 CharacterController::depenetrate(const World& world, Vec2 pos) const {
    std::array<Hit, 8> hits{};
    const auto n = world.overlap_all(shape_at(pos), filter, hits);
    if (!n) return pos;      // std::expected（第 33.4 節）

    // 優先度順に並べ替える
    std::ranges::sort(hits | std::views::take(*n), {}, [&](const Hit& h) {
        if (is_walkable(h.normal, max_slope_angle)) return 0;   // 床
        if (h.normal.y > -0.5f)                     return 1;   // 壁
        return 2;                                                // 天井
    });

    Vec2 out = pos;
    for (const Hit& h : hits | std::views::take(*n))
        out += h.normal * (h.depth + skin_width);
    return out;
}
```

**優先順位は「押し戻す順」ではなく「重要な順」である。** 先に処理したものが、後の処理で打ち消されにくい。第 34.2 節の順序依存を、**設計として利用している。**

### 天井に頭をぶつけたら速度を殺す

```cpp
// 上向きの速度を持っているときに天井へ当たったら、その成分を消す
if (hit && hit->normal.y < -0.5f && velocity.y > 0.0f) velocity.y = 0.0f;
```

**これがないと、天井にめり込んだまま上向きの速度を持ち続ける。** 天井を離れた瞬間に飛び上がる、という挙動になる。

第 34.1 節で `cancel_normal_velocity` を書いたのと同じ処理である。**キャラクタでも、速度の後始末は要る。**

## 38.5 入力から移動量までの設計

`move()` に渡す `delta` を、ゲームロジックがどう作るか。**ここに操作感の大半が宿る。**

### 速度は自分で管理する

剛体と違い、キャラクタの速度はソルバに書き換えられない。**すべてゲームロジックの責任である。**

```cpp
void CharacterController::update(const World& world, const Input& in, float dt) {
    // ① 水平方向：目標速度へ「素早く」寄せる
    const float target = in.move_x * max_speed;
    const float accel  = ground_.grounded ? ground_accel : air_accel;
    velocity.x = move_toward(velocity.x, target, accel * dt);

    // ② 垂直方向：重力と跳躍
    if (ground_.grounded && in.jump_pressed) velocity.y = jump_speed;
    velocity.y -= gravity * dt;

    // ③ 実際に動かす
    const Vec2 moved = move(world, velocity * dt) - position;
    position += moved;

    // ④ ★ 進めなかった分だけ、速度も落とす
    if (dt > 0.0f) velocity = closest_consistent_velocity(velocity, moved / dt);

    ground_ = probe_ground(world, position);
}
```

**④ を忘れるのがよくある不具合である。** 壁に押し付けたまま入力を続けると、`velocity.x` が最大値に張り付く。壁から離れた瞬間、**キャラクタが横に飛ぶ。**

同じことが垂直方向にも起きる。**着地しても `velocity.y` を戻さないと、落下速度が積み上がり続ける。** 落下ダメージの計算がおかしくなる。

```cpp
// 進めた方向の成分だけを残す素直な実装
[[nodiscard]] Vec2 closest_consistent_velocity(Vec2 wanted, Vec2 actual) noexcept {
    return Vec2{
        (std::fabs(actual.x) < std::fabs(wanted.x)) ? actual.x : wanted.x,
        (std::fabs(actual.y) < std::fabs(wanted.y)) ? actual.y : wanted.y,
    };
}
```

### 空中と地上で規則を変える

**空中制御（air control）はほぼすべてのゲームで「物理的に間違っている」。** 空中では加速する手段がないはずだが、ないと操作感が極端に悪い。

```cpp
inline constexpr float ground_accel = 60.0f;    // m/s²。0.1 秒で最高速へ
inline constexpr float air_accel    = 15.0f;    // 地上の 4 分の 1
```

**比率をパラメータにしておくと、調整が一箇所で済む。** 「空中では地上の何割動けるか」はゲームの性格を決める数値であり、何度も調整することになる。

### ジャンプの高さから速度を逆算する

`jump_speed` を勘で決めると、レベルデザインと噛み合わない。**「何メートル跳びたいか」から逆算する。**

```cpp
// 高さ h まで跳ぶのに必要な初速：v = sqrt(2 g h)
[[nodiscard]] constexpr float jump_speed_for(float height, float gravity) noexcept {
    return std::sqrt(2.0f * gravity * height);
}
```

**レベルデザイナは「2 m の段差」と言う。プログラマは `jump_speed_for(2.0f, gravity)` と書く。** 会話が噛み合う。

第 5.9 節で単位系を明文化したことが、ここでも効いている。**「1 単位＝1 メートル」が守られているから、この式がそのまま使える。**

## 38.6 テスト：入力列に対する回帰テスト

### ゴールデンデータを「値」で持たない

キャラクターコントローラのテストは、本質的に**シナリオテスト**（第 33.5 節）である。入力列を与え、結果を検証する。

**「100 フレーム後の位置が (12.3456, 3.4567) であること」というテストを書いてはいけない。**

理由は二つある。

1. **`/fp:fast` の下で、ビット単位の再現は保証されない**（第 3.5 節）
2. **パラメータを 1 つ調整しただけで、全部書き直しになる**

**代わりに、許容範囲つきで記録する。**

```cpp
// test_character.cpp
TEST_CLASS(CharacterControllerTest) {
public:
    TEST_METHOD(平地を直進したときの到達距離) {
        auto world = make_flat_ground();
        CharacterController c{.position = Vec2{0.0f, 1.0f}};

        for (int f = 0; f < 60; ++f) c.position = c.move(world, Vec2{0.1f, -0.02f});

        // 期待値は「理論値 6.0 m」であって、実測値のコピーではない
        expect_near(6.0f, c.position.x, 0.05f, 0.0f);   // 5 cm の許容
        expect_near(1.0f, c.position.y, 0.05f, 0.0f);
    }
```

**期待値を「理論値」で書けるようにシナリオを設計する**のが要点である。1 フレーム 0.1 m × 60 フレーム = 6.0 m は、実装を見なくても書ける。**実測値をコピーした期待値は、間違った実装をそのまま固定してしまう。**

### 性質で縛る

理論値が書けない場合は、**性質を検査する。**

```cpp
    TEST_METHOD(壁に沿って滑ること) {
        auto world = make_ground_with_wall(/*wall_x=*/5.0f);
        CharacterController c{.position = Vec2{0.0f, 1.0f}};

        for (int f = 0; f < 200; ++f)
            c.position = c.move(world, Vec2{0.1f, 0.05f});    // 斜め上へ進み続ける

        // ① 壁を越えていない
        Assert::IsTrue(c.position.x < 5.0f - c.radius + 1.0e-3f, L"壁を抜けました");
        // ② 壁に貼り付いて止まっていない（上へは進めているはず）
        Assert::IsTrue(c.position.y > 5.0f, L"壁で引っかかっています");
    }

    TEST_METHOD(登坂角より急な斜面を登れないこと) {
        for (const float deg : {30.0f, 40.0f, 50.0f, 60.0f}) {
            auto world = make_slope(deg);
            CharacterController c{.max_slope_angle = 45.0f};
            const float y0 = c.position.y;

            for (int f = 0; f < 120; ++f) c.position = c.move(world, Vec2{0.1f, -0.02f});

            const bool climbed = (c.position.y - y0) > 0.5f;
            Assert::AreEqual(deg < 45.0f, climbed,
                std::format(L"{}度の斜面: 登った={}", deg, climbed).c_str());
        }
    }

    TEST_METHOD(左右対称な谷で横にずれないこと) {
        // 38.2 節で見つけた不具合の回帰テスト
        auto world = make_symmetric_valley(/*half_angle_deg=*/30.0f);
        CharacterController c{.position = Vec2{0.0f, 3.0f}};

        for (int f = 0; f < 60; ++f) c.position = c.move(world, Vec2{0.0f, -0.1f});

        // 対称なシーンに対称な入力。x が動くのは実装の不具合である
        expect_near(0.0f, c.position.x, 1.0e-2f, 0.0f);
    }
```

**三つ目は 38.2 節で実際に見つけた不具合の回帰テストである。** 「対称なシーンに対称な入力を与えたら、結果も対称であるべき」という性質は、**実測値を一切使わずに強く縛れる。**

第 40.2 節で「対称性は性質ベーステストの主力」と整理するが、その最も分かりやすい実例がこれである。

### 決定論の検査

```cpp
    TEST_METHOD(同じ入力列で同じ結果になること) {
        const auto run = [] {
            auto world = make_obstacle_course();
            CharacterController c{.position = Vec2{0.0f, 1.0f}};
            Rng rng(8100);                      // 入力もシードで固定する
            for (int f = 0; f < 500; ++f)
                c.position = c.move(world,
                    Vec2{rng.uniform(-0.15f, 0.15f), rng.uniform(-0.15f, 0.05f)});
            return c.position;
        };
        expect_near(run(), run(), 0.0f, 0.0f);   // 同一バイナリなら厳密に一致する
    }
};
```

**同一バイナリ・同一マシンでの再現は、`/fp:fast` でも保証される**（第 41.3 節）。ここで厳密比較を使えるのは、そのためである。

**このテストが落ちたら、どこかに `unordered_map` の走査順序や、未初期化の値が紛れ込んでいる。** 第 33.2 節で潰した種類のバグを、キャラクタ側でも検出できる。

## この章のまとめ

- **キャラクタに剛体シミュレーションを使わない。** 止まらない・転ぶ・坂で滑る・押し出しが読めない
- `max_slope_angle` や `step_height` は**物理量ではなくゲームデザインの数値**である
- キャラクタは**キネマティック剛体**として世界に置く。押せるが押し返されない
- collide-and-slide の本体は 1 行、**`rest - n·dot(rest, n)`**（法線成分の除去）
- `skin_width` で**常に面から離しておく**。剛体の `slop`（めり込ませる）とは目的が逆
- **鋭角の谷では、滑りの連鎖で横に 34 cm 飛ぶ。** 反復は 2〜4 回に抑え、逆行を禁じる
- 歩ける面かどうかは **`normal.y >= cos(max_slope)`** で判定する。逆三角関数は要らない
- 壁として扱う面では**滑る方向の上向き成分を消す**。忘れると急斜面を滑って登れる
- 自然に任せると 60 度まで登れてしまう。**明示的な登坂角が必要な理由**
- 段差の乗り越えは「**上げる → 進む → 下ろす**」の三段。進めなければ諦める
- 接地判定は短いスイープ。**コヨーテタイム**は物理的に誤りだが操作感を大きく改善する
- 押し戻しの優先順位は**床 → 壁 → 天井**。順序依存を設計として利用する
- 動く床は**その点の速度**（`v + ω × r`）で運ぶ。床の移動を入力より先に適用する
- スポーン時のめり込みは**重なり判定で押し出す。** 毎フレーム呼んでよい
- しゃがみから戻すときは**頭上を確認する。** 確認漏れは床抜けにつながる
- **進めなかった分だけ速度も落とす。** 忘れると壁から離れた瞬間に飛ぶ
- 空中制御は物理的に誤りだが必須。**地上との比率をパラメータにする**
- ジャンプ速度は `sqrt(2gh)` で**跳びたい高さから逆算する**
- テストは**理論値で書ける形にシナリオを設計する**。実測値のコピーを期待値にしない
- **「対称なシーンに対称な入力なら結果も対称」**が最も強い性質
- 同一バイナリでの再現性だけは厳密比較でよい

### 落とし穴と練習問題

**落とし穴 1：滑りの反復を増やしすぎる。**　谷や角で入力にない方向へ飛ぶ。

**落とし穴 2：`skin_width` を入れない。**　面の境界で判定が揺れ、貼り付きやすり抜けが出る。

**落とし穴 3：歩けない面でも普通に滑らせる。**　垂直に近い壁を滑って登れる。

**落とし穴 4：接地判定の距離を短くしすぎる。**　坂を下るときに一歩ごとに接地が切れ、ジャンプできない。

**落とし穴 5：期待値に実測値をコピーする。**　間違った実装がそのまま仕様になる。

**落とし穴 6：進めなかった分の速度を落とさない。**　壁に押し付けたあと離れた瞬間に飛ぶ。着地しても落下速度が積み上がり続ける。

**落とし穴 7：しゃがみから戻すときに頭上を確認しない。**　天井にめり込み、押し出しで床を突き抜けることがある。

**落とし穴 8：動く床の速度を床の中心で取る。**　回転する足場では、乗っている位置によって速度が違う。`v + ω × r` を使う。

**落とし穴 9：プレイヤーの入力を先に処理してから床の移動を足す。**　足場が動いた分だけ入力が食われ、動く床の上で操作が重くなる。
