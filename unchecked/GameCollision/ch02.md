## 2.1 必要なワークロードとコンポーネントの選択

### インストーラを起動する

Visual Studio 2026 をまだ入れていなければ、Microsoft の配布ページからインストーラを取得する。すでに入っている場合は、スタートメニューから **Visual Studio Installer** を起動し、インストール済みの項目の「変更」を選ぶ。

Visual Studio 2026 には **Stable** と **Insiders** の二つの更新チャネルがある。本書は Stable チャネルを前提にする。Insiders は週次に近い頻度で更新され、新しいコンパイラ機能をいち早く試せるが、その分だけ挙動が動く。学習中は Stable のほうが落ち着いて進められる。

### 選ぶワークロード

ワークロードの一覧から、次の一つだけを選ぶ。

- ☑ **C++ によるデスクトップ開発**（Desktop development with C++）

これで足りる。本書は Windows API も DirectX も使わないので、「C++ によるゲーム開発」ワークロードは不要である。あれは DirectX や Unreal Engine の統合を含むもので、サイズが大きい割に本書では一切使わない。

「Linux と埋め込み開発」「.NET デスクトップ開発」なども不要である。後から追加できるので、この段階で欲張る意味はない。

### 個別コンポーネントの確認

ワークロードを選ぶと、右側のサマリーに含まれるコンポーネントが並ぶ。次の三つが入っていることを確認してほしい。既定で選択されているはずだが、目視で確認する価値はある。

| コンポーネント | 用途 |
|---|---|
| **MSVC Build Tools for x64/x86（最新）** | コンパイラ本体。これが無ければ何も始まらない |
| **Windows 11 SDK**（最新版） | 標準ライブラリの一部と、テストフレームワークが依存する |
| **C++ のテスト アダプター** ないし単体テスト関連の項目 | 第 3 章で使うテストエクスプローラーの連携に必要 |

任意で入れておくと後の章で役立つものも挙げておく。今すぐでなくてよい。

- **C++ プロファイリング ツール** … 第 29 章と第 42 章で計測に使う
- **C++ AddressSanitizer** … メモリ破壊の検出。BVH のノード管理（第 32 章）でお世話になるかもしれない
- **Windows 用 C++ CMake ツール** … 本書では使わないが、他プロジェクトへ移植する際に

### インストール後の確認

インストールが終わったら、コンパイラが期待どおりのバージョンかを確認しておく。スタートメニューから **Developer Command Prompt for VS 2026** を開き、次を実行する。

```
cl
```

引数なしで `cl` を実行すると、バージョン情報だけを表示して終了する。

```
Microsoft(R) C/C++ Optimizing Compiler Version 19.51.36231 for x64
```

`19.51` 系であれば MSVC Build Tools v14.51 である。表示される二つの番号の対応は紛らわしいので整理しておく。

| 呼び方 | 例 | どこで見るか |
|---|---|---|
| コンパイラバージョン | 19.51.36231 | `cl` の出力、`_MSC_VER` = 1951 |
| ツールセットバージョン | 14.51.36231 | インストーラのコンポーネント名、`_MSC_FULL_VER` の元 |
| Visual Studio バージョン | 18.9 | ヘルプ → Microsoft Visual Studio のバージョン情報 |

同じビルドを指しているのに三種類の番号があるのは歴史的な事情による。ドキュメントを検索するときはツールセットの `14.5x` で当たると見つかりやすい。

> **落とし穴：複数バージョンの併存**
> Visual Studio 2022 と 2026 を同じマシンに入れている場合、プロジェクトがどちらのツールセットでビルドされているかを意識する必要がある。プロジェクトのプロパティ → 構成プロパティ → 全般 → **プラットフォーム ツールセット** で確認できる。本書では 2026 に同梱される最新のものを使う。

## 2.2 ソリューションを 2 プロジェクトで作る

### なぜ二つに分けるのか

ライブラリ本体とテストを別プロジェクトにする。理由は単純で、**ライブラリが利用者から見てどう見えるかを、テスト自身が検証してくれる**からである。

一つのプロジェクトにテストを同居させると、`#include "../src/internal_thing.h"` のような、外からは使えない経路でうっかり内部に触れてしまう。別プロジェクトにして公開ヘッダ越しにしかアクセスできない状態にしておけば、公開 API だけで機能が完結しているかが自動的に保証される。

もう一つ、成果物の性質も違う。ライブラリはスタティックライブラリ（`.lib`）、テストは Visual Studio のテストランナーが読み込む DLL（`.dll`）になる。分けるほうが自然である。

### ソリューションとライブラリプロジェクトを作る

Visual Studio を起動し、**新しいプロジェクトの作成** を選ぶ。

1. テンプレートの検索欄で「スタティック ライブラリ」を探し、**スタティック ライブラリ (C++)** を選ぶ
2. プロジェクト名に `collision`、ソリューション名に `GameCollision` と入力する
3. 「ソリューションとプロジェクトを同じディレクトリに配置する」は**チェックしない**。二つ目のプロジェクトを足すので、ソリューション直下に並べたい
4. 作成する

テンプレートが生成する `pch.h`、`pch.cpp`、`framework.h`、`collision.cpp` は削除してよい。プリコンパイル済みヘッダは、本書の規模では設定の手間に見合わない。削除したら、プロジェクトのプロパティ → C/C++ → プリコンパイル済みヘッダー → **プリコンパイル済みヘッダー** を「使用しない」に変更しておく。この設定を忘れると、削除したはずの `pch.h` が見つからないというエラーになる。

### テストプロジェクトを追加する

ソリューションエクスプローラーでソリューション名を右クリックし、**追加 → 新しいプロジェクト**。

1. 「ネイティブ単体テスト」で検索し、**ネイティブ単体テスト プロジェクト**（Native Unit Test Project）を選ぶ
2. プロジェクト名は `collision_tests`
3. 作成する

生成される `collision_tests.cpp` には、空のテストクラスが入っている。第 3 章でこれを書き換える。

この時点でソリューションエクスプローラーはこうなっているはずである。

```
ソリューション 'GameCollision' (2/2 プロジェクト)
├─ collision
└─ collision_tests
```

### ディレクトリを整える

前章で示したディレクトリ構成を作っておく。エクスプローラー上で、`collision` プロジェクトのフォルダに次を作る。

```
collision/
├─ include/
│   └─ collision/
│       ├─ math/
│       ├─ shapes/
│       ├─ narrow/
│       ├─ broad/
│       └─ dynamics/
└─ src/
```

インクルードパスが `collision/include` を指すようにしておけば（2.6 節）、利用側は `#include <collision/math/vec2.h>` と書ける。`include` の下にもう一段 `collision/` を挟むのは、他のライブラリとヘッダ名が衝突しないようにするための定石である。

なお Visual Studio のソリューションエクスプローラー上の「フィルター」は、実際のディレクトリ構造とは独立している。ファイルを追加するときは、実ディレクトリに置いてから **既存の項目の追加** で取り込むのが確実である。

> **補足：ソリューションファイルの形式**
> Visual Studio 2026 では、従来の `.sln` に加えて XML ベースの `.slnx` 形式が使える。差分が読みやすくバージョン管理と相性がよいので、Git で管理するなら `.slnx` を勧める。ファイル → **ソリューションに名前を付けて保存** から変換できる。本書の手順はどちらでも変わらない。

## 2.3 C++23 を有効にする

### 言語標準を指定する

デフォルトでは、新規に作った MSBuild プロジェクトの C++ 言語標準は **C++20** になっている。これを引き上げる。

**両方のプロジェクトを選択した状態で**（ソリューションエクスプローラーで Ctrl を押しながら二つとも選ぶ）プロパティを開き、構成プロパティ → 全般 → **C++ 言語標準** を変更する。

選択肢はおおむね次のようになっている。

- ISO C++20 標準 (`/std:c++20`)
- **ISO C++23 標準 (プレビュー) (`/std:c++23preview`)** ← これを選ぶ
- プレビュー - 最新の C++ 作業ドラフトの機能 (`/std:c++latest`)

`/std:c++23preview` を選ぶ。名前に「プレビュー」と付いているのが気になるかもしれないが、これは MSVC における C++23 の実装がまだ全機能を満たしていないことを表しているだけで、個々の機能が不安定という意味ではない。

> **バージョンによる違い**
> MSVC は将来的に `/std:c++23preview` を `/std:c++23` に置き換える予定を公表している（v14.52 系で追加され、`/std:c++23preview` は非推奨になる見込み）。読者の環境に `ISO C++23 標準 (/std:c++23)` という選択肢があれば、そちらを選んで構わない。本書のコードはどちらでもビルドできる。
>
> `/std:c++latest` を選んでも本書のコードは通るが、C++26 以降の実験的な機能まで有効になるため、意図せずそれらに依存してしまう危険がある。学習中は範囲を絞っておくほうがよい。

**重要な注意点。** 構成プロパティの設定は、**構成（Debug / Release）とプラットフォーム（x64 / x86）の組み合わせごとに独立している**。プロパティページ上部の「構成」を **すべての構成**、「プラットフォーム」を **すべてのプラットフォーム** にしてから変更すること。これを忘れると「Debug ではビルドが通るのに Release で通らない」という不可解な状況になる。本章の以降の設定すべてに同じ注意が当てはまる。

### 適合性オプションを揃える

C++ の標準を指定しただけでは、MSVC は完全に標準準拠の動作にはならない。互換性のために残されている非標準の挙動を、明示的に切っていく。

C/C++ → 言語 の下に、次の項目がある。

| 項目 | 設定 | オプション |
|---|---|---|
| 準拠モード | はい | `/permissive-` |
| `__cplusplus` 更新マクロ | はい | `/Zc:__cplusplus` |
| C++ 演算子の代替宣言 | はい | `/Zc:preprocessor` は下記参照 |

**`/permissive-`** は、標準に反するコードを受け付けないようにするスイッチである。新規プロジェクトでは既定で有効になっているはずだが、確認しておく。二段階名前検索（テンプレート内の名前解決を標準どおりに行う）などが有効になり、他のコンパイラでも通るコードを書くことになる。

**`/Zc:__cplusplus`** は地味だが重要である。これを付けないと、MSVC は `__cplusplus` マクロの値を常に `199711L`（C++98 相当）と報告する。標準ライブラリやサードパーティのヘッダには `#if __cplusplus >= 202002L` のような条件分岐を含むものがあり、この値が正しくないと本来使えるはずのコードパスが選ばれない。互換性のために既定でオフになっているという歴史的経緯があるので、**自分で明示的にオンにする必要がある**。

**`/Zc:preprocessor`** は、C/C++ → プリプロセッサ → **準拠モードのプリプロセッサを使用する** で設定する。これも「はい」にしておく。可変長引数マクロの展開など、従来の MSVC プリプロセッサには標準と異なる挙動がいくつかあった。本書では複雑なマクロをほとんど使わないので影響は小さいが、揃えておいて損はない。

### 設定できたか確かめる

`collision_tests` の `collision_tests.cpp` に一時的に次を書いて、ビルドしてみる。

```cpp
#include <version>
#include <print>

// C++20 より後の標準が有効になっていること
static_assert(__cplusplus > 202002L, "C++23 が有効になっていません");

// 本書で使う主要な C++23 ライブラリ機能が揃っていること
static_assert(__cpp_lib_expected >= 202202L, "std::expected が使えません");
static_assert(__cpp_lib_print   >= 202207L, "std::print が使えません");

// 実際の値を目で見る
#pragma message("__cplusplus  = " _CRT_STRINGIZE(__cplusplus))
#pragma message("_MSVC_LANG   = " _CRT_STRINGIZE(_MSVC_LANG))
```

`<version>` は、標準ライブラリの機能テストマクロだけを集めたヘッダである。実装が何を提供しているかを問い合わせるためだけに存在し、実体は何も持ち込まない。

三つとも通ればこの節の設定は完了である。一つ目で落ちるなら `/Zc:__cplusplus` か言語標準の設定を、二つ目・三つ目で落ちるなら言語標準が C++23 になっているかを見直す。確認できたら、これらは消してよい。

> **`__cplusplus` の値に依存しすぎない**
> 一つ目の `static_assert` を `>= 202302L`（C++23 の正式な値）ではなく `> 202002L`（C++20 より後）にしているのには理由がある。
>
> MSVC は、標準がまだ完全には実装されていない段階の `/std:` オプションに対して、正式な値ではなく「一つ前の標準より大きい暫定値」を報告することがある。実際 `/std:c++latest` は長らく `202004L` を報告していた。`/std:c++23preview` が何を報告するかは版によって変わりうるので、正式な値との厳密な一致を要求するとビルドが通らなくなる。
>
> 一方 `__cpp_lib_expected` のような**機能テストマクロは、その機能が実際に使えるかどうかを直接表す**。「C++23 が有効か」ではなく「使いたい機能が使えるか」を問うほうが、はるかに壊れにくい。本書ではこの方針をとる。
>
> なお MSVC には `_MSVC_LANG` という独自のマクロもあり、こちらは `/Zc:__cplusplus` の有無にかかわらず `/std:` の指定を反映する。`#pragma message` で両方の実際の値を出力しているので、自分の環境で何が報告されるかを確認しておくとよい。

## 2.4 警告をエラーにする

### `/W4 /WX` を設定する

C/C++ → 全般 で、次の二つを設定する。

| 項目 | 設定 | オプション |
|---|---|---|
| 警告レベル | **レベル4 (/W4)** | `/W4` |
| 警告をエラーとして扱う | **はい (/WX)** | `/WX` |

入門書でここまで厳しくするのか、と思われるかもしれない。むしろ逆で、**入門書だからこそ厳しくする**。

理由は、本書が扱う領域と警告の種類が噛み合っているからである。浮動小数点を扱うコードで出る警告には、実際にバグである確率が高いものが多い。

- **C4244 / C4267**（縮小変換）… `double` の値をうっかり `float` へ、`size_t` を `int` へ入れている。前者は精度が落ち、後者は 64 ビット環境で桁が飛ぶ
- **C4305**（切り捨て）… `float x = 0.1;` のように `double` リテラルを `float` に入れている。`0.1f` と書くべき箇所
- **C4701**（初期化されていない可能性のある変数の使用）… 分岐によっては未初期化のまま読まれる。浮動小数点の未初期化はデバッグビルドでも気づきにくい
- **C4189**（初期化されたが参照されないローカル変数）… 計算したのに使っていない。式を書き間違えている可能性が高い

こうした警告を「後で直す」と放置すると、出力ウィンドウが警告で埋まり、**本当に重要な警告が見えなくなる**。`/WX` はそれを構造的に防ぐ。

### 外部ヘッダの警告を切る

`/W4 /WX` をそのまま適用すると、Windows SDK や標準ライブラリのヘッダから出る警告でビルドが止まることがある。自分では直しようがないので、外部ヘッダは警告の対象から外す。

C/C++ → 外部インクルード に次の項目がある。

| 項目 | 設定 | オプション |
|---|---|---|
| 外部ヘッダーの警告レベル | **警告をオフにする (/external:W0)** | `/external:W0` |
| 山かっこインクルードを外部として扱う | **はい (/external:anglebrackets)** | `/external:anglebrackets` |

これで `#include <...>` の形で取り込んだヘッダは警告の対象外になり、`#include "..."` で取り込んだ自分のコードだけが `/W4` の検査を受ける。

ここで一つ判断が要る。本書のライブラリを利用側から `#include <collision/...>` と書かせる方針（2.2 節）と、この設定は衝突する。**自分のライブラリのヘッダまで警告対象から外れてしまう**のである。

対処は二通りある。

- **テストプロジェクトからは `""` でインクルードする**。`#include "collision/math/vec2.h"` と書けば `/W4` が効く。利用側の視点を再現したいときだけ `<>` を使う
- **`/external:I` で外部扱いするディレクトリを明示する**。山かっこ一律ではなく、Windows SDK のパスなどを個別に指定する

本書は前者を採る。テストコードでは `""` を使い、ライブラリのヘッダにも警告が届くようにする。読者のプロジェクトに組み込む段階では `<>` に切り替えればよい。

> **落とし穴：`/WX` が邪魔になったとき**
> 意図的に警告を出すコードを書きたい場面（第 4 章で `/fp:fast` の挙動を確認する実験など）では、`#pragma warning(push)` / `#pragma warning(disable : 4xxx)` / `#pragma warning(pop)` で局所的に抑制する。プロジェクト全体の `/WX` を外すのは最後の手段にしてほしい。一度外すと戻らない。

## 2.5 浮動小数点モデルを `/fp:fast` に設定する

### 三つのモデル

C/C++ → コード生成 → **浮動小数点モデル** で、コンパイラが浮動小数点演算をどこまで変形してよいかを指定する。選択肢は三つある。

| モデル | オプション | コンパイラに許すこと |
|---|---|---|
| Precise | `/fp:precise` | 既定。演算の順序と結果を保つ。IEEE 754 の意味論をおおむね維持する |
| **Fast** | **`/fp:fast`** | 数学的に等価な変形を許す。順序の入れ替え、FMA への融合、除算の逆数化など |
| Strict | `/fp:strict` | 例外と丸めモードの変更まで厳密に守る。最も遅い |

本書は **Fast (`/fp:fast`)** を選ぶ。ライブラリとテストの両プロジェクトで、**すべての構成・すべてのプラットフォーム**に対して設定する。

### なぜ Fast を選ぶのか、そして何を失うのか

前章で述べたとおり、ゲームでは 1 mm のずれより 1 フレームの遅延のほうが問題になる。`/fp:fast` は、その価値観に沿った選択である。

具体的にコンパイラは次のような変形をしてよくなる。

- **再結合**　`(a + b) + c` を `a + (b + c)` にしてよい。総和の順序が変わるので、結果のビットは変わりうる
- **FMA への融合**　`a * b + c` を単一の `vfmadd` 命令にしてよい。丸めが 1 回減るので、結果は「より正確な方向に」ずれる
- **除算の逆数化**　`x / y` を `x * (1 / y)` にしてよい。ループ内で同じ除数を使うとき特に効く
- **`rsqrt` 近似の使用**　`1 / sqrt(x)` を専用の近似命令に置き換えてよい
- **ゼロや符号に関する仮定**　`-0.0` と `+0.0` を同一視してよい。`x != x` による NaN 判定が消える可能性がある

得られるものと失うものを一行でまとめるとこうなる。**速度と引き換えに、ビット単位の再現性と、IEEE 754 の特殊値（NaN、Inf、`-0.0`）の保証を失う。**

この選択が具体的にどう跳ね返ってくるかは第 4 章で、非正規化数の扱いは第 5 章で、それぞれ丸ごと一章を使って扱う。ここでは「そういう選択をした」という事実を設定に反映させるだけでよい。

### `/fp:fast` は「そう最適化してよい」という許可にすぎない

一つ、この段階で釘を刺しておきたいことがある。

`/fp:fast` は**コンパイル時**のスイッチである。コンパイラに対して「数学的に等価な変形をしてよい」と許可を与えるものであって、**プログラム実行時の CPU の状態を設定するものではない**。

具体的には、非正規化数をゼロに潰す FTZ/DAZ という機能は CPU の MXCSR レジスタで制御されるが、`/fp:fast` を付けただけでその状態が保証されるとは考えないほうがよい。しかも MXCSR はスレッドごとの状態であり、他のモジュールに書き換えられることもある。ここは第 5 章で、実行時に明示的に設定する形で扱う。

「コンパイラへの許可」と「実行時の CPU の状態」は別物である。この区別は、後で「設定したはずなのに効いていない」と悩まないために覚えておいてほしい。

### 併せて有効にするもの

**拡張命令セット。**　C/C++ → コード生成 → **拡張命令セットを有効にする** を **AVX2 (/arch:AVX2)** にする。AVX2 は 2013 年以降の Intel/AMD の x64 CPU にほぼ載っているので、現代のゲーム向けとしては妥当な下限である。FMA 命令が使えるようになり、`/fp:fast` の効果が実際に出るようになる。

配布対象がもっと古い環境を含むなら `/arch:SSE2`（x64 では既定）に落とす。逆に AVX-512 を狙うのは、対応状況とサーマル特性の両面で慎重になったほうがよい。

**自動ベクトル化のレポート。**　C/C++ → コマンド ライン → 追加のオプション に `/Qvec-report:2` を書き加える。これはループがベクトル化されたか、されなかったならその理由は何かを、ビルド時のメッセージとして出力させるものである。

最初のうちは大量のメッセージが出て鬱陶しいので、常時有効にする必要はない。第 42 章で性能を詰めるときに使う道具として、設定方法だけ知っておけばよい。今は追加しておいて、うるさければ外して構わない。

## 2.6 インクルードパスとプロジェクト参照の設定

### プロパティシートで共通設定をまとめる

ここまで、二つのプロジェクトに同じ設定を手で入れてきた。プロジェクトが二つ、構成が Debug/Release の二つで、合計四箇所に同じ値を入れる作業である。設定が増えるほど、どこかを入れ忘れるリスクが上がる。

Visual Studio には **プロパティシート**（`.props` ファイル）という仕組みがあり、共通の設定を一箇所にまとめて複数のプロジェクトから参照できる。ここで導入しておく。

1. 表示 → **その他のウィンドウ** → **プロパティ マネージャー** を開く
2. `collision` を右クリック → **新しいプロジェクト プロパティ シートの追加**
3. 名前を `Common.props`、場所をソリューション直下にする
4. 追加された `Common` をダブルクリックして、通常のプロパティページと同じように設定を入れる
5. `collision_tests` を右クリック → **既存のプロパティ シートの追加** で、同じ `Common.props` を指定する

`Common.props` に入れるのは、2.3〜2.5 節で設定した項目である。

- C++ 言語標準（`/std:c++23preview`）
- 準拠モード、`/Zc:__cplusplus`、`/Zc:preprocessor`
- 警告レベル `/W4`、警告をエラーとして扱う `/WX`
- 外部ヘッダーの警告レベル `/external:W0`、`/external:anglebrackets`
- 浮動小数点モデル `/fp:fast`
- 拡張命令セット `/arch:AVX2`
- 追加のインクルードディレクトリ（次項）

プロパティシートに移したら、各プロジェクト側の同じ項目は「既定値から継承」に戻しておく。プロジェクト側の設定はプロパティシートより優先されるので、両方に値が入っていると、後からプロパティシートを直しても反映されない。この優先順位は混乱のもとなので、**共通設定はプロパティシートだけに書く**と決めておくのがよい。

> **なぜ最初からプロパティシートで説明しなかったのか**
> 各設定が何をするものかを知らないまま `.props` に放り込むと、後で何を設定したのか分からなくなるからである。一度手で入れて意味を理解してから、まとめる。実際の開発でも、この順序が結局は速い。

### インクルードディレクトリを通す

`Common.props` の C/C++ → 全般 → **追加のインクルード ディレクトリ** に次を追加する。

```
$(SolutionDir)collision\include
```

`$(SolutionDir)` は MSBuild のマクロで、ソリューションファイルのあるディレクトリに展開される（末尾に `\` が付く）。絶対パスを直接書くと他のマシンでビルドできなくなるので、必ずマクロを使う。

これで、どちらのプロジェクトからも次のように書ける。

```cpp
#include "collision/math/vec2.h"     // テストから（/W4 が効く）
#include <collision/math/vec2.h>     // 利用者の視点を再現したいとき
```

使えるマクロは他にもある。プロパティの値を編集するとき、ドロップダウンから「編集...」を選ぶと、下部に「マクロ」ボタンがあり、利用可能なマクロと展開結果の一覧を確認できる。

| マクロ | 展開されるもの |
|---|---|
| `$(SolutionDir)` | ソリューションのディレクトリ |
| `$(ProjectDir)` | プロジェクトのディレクトリ |
| `$(Configuration)` | `Debug` / `Release` |
| `$(Platform)` | `x64` / `Win32` |
| `$(OutDir)` | 出力ディレクトリ |

### プロジェクト参照を追加する

テストプロジェクトからライブラリの関数を呼ぶには、リンクの設定が必要である。手で `.lib` を指定することもできるが、**プロジェクト参照**を使うほうがよい。

1. `collision_tests` を右クリック → **追加** → **参照**
2. 「プロジェクト」の一覧から `collision` にチェックを入れる
3. OK

これだけでリンクの設定が済む。加えて、**ビルド順序が自動的に解決される**という利点がある。`collision_tests` をビルドすると、必要なら先に `collision` がビルドされる。手で `.lib` を指定した場合、この依存関係は伝わらない。

### 出力ディレクトリを整理する（任意）

既定では、各プロジェクトの下に `x64/Debug/` のようなディレクトリができる。散らかるのが気になるなら、`Common.props` の 構成プロパティ → 全般 で次のように揃えておくとよい。

| 項目 | 値 |
|---|---|
| 出力ディレクトリ | `$(SolutionDir)build\$(Platform)\$(Configuration)\` |
| 中間ディレクトリ | `$(SolutionDir)build\intermediate\$(Platform)\$(Configuration)\$(ProjectName)\` |

Git で管理するなら `.gitignore` に `build/` を書いておく。これは好みの問題なので、既定のままでも本書の内容には影響しない。

## 2.7 ビルド構成 Debug / Release と、両方でテストを走らせる習慣

### 二つの構成の違い

MSBuild のプロジェクトには既定で Debug と Release の二つの構成がある。主な違いはこうなっている。

| 項目 | Debug | Release |
|---|---|---|
| 最適化 | 無効 (`/Od`) | 速度優先 (`/O2`) |
| インライン展開 | 無効 | 有効 |
| ランタイムチェック | 有効 (`/RTC1`) | 無効 |
| ランタイムライブラリ | デバッグ版 (`/MDd`) | 製品版 (`/MD`) |
| `NDEBUG` マクロ | 未定義（`assert` が有効） | 定義済み（`assert` が無効） |
| デバッグ情報 | あり | あり（既定で生成される） |

Debug はブレークポイントが素直に効き、変数の値が最適化で消えない。Release は速い。開発中は Debug、性能を測るときは Release、というのが基本的な使い分けになる。

### `/fp:fast` は Debug でも有効にする

ここが本書に固有の判断である。

浮動小数点モデルの設定は、通常「Release だけ速く」と考えて Release にのみ適用したくなる。本書ではそうしない。**Debug でも `/fp:fast` を有効にする。**

理由は、構成間の差を減らしたいからである。`/fp:fast` は計算結果を変えうるスイッチである。Debug と Release で浮動小数点モデルが違うと、「Debug ではテストが通るのに Release で落ちる」という現象が起きる。そして原因の切り分けは難しい。最適化のせいなのか、浮動小数点モデルの違いのせいなのか、判断がつかないからである。

両方を `/fp:fast` に揃えておけば、構成間で結果が変わったときの容疑者が「最適化とインライン展開」に絞られる。2.6 節で設定を `Common.props` にまとめたので、この方針は自動的に守られる。

同じ理由で、第 5 章で導入する FTZ/DAZ の設定も両構成で有効にする。

> **それでも Debug と Release で結果は完全には一致しない**
> インライン展開の有無によって、中間結果がレジスタに保持されるか一度メモリに書き戻されるかが変わり、それが精度の差になることがある。`/fp:fast` を揃えてもこの差は残る。だからこそ、テストは許容誤差ベースで書く（第 3 章）。ビット一致を期待するテストを一つでも書くと、この差に必ず引っかかる。

### 両方の構成でテストを走らせる

習慣として、次を守ってほしい。

**コミットする前に、Debug と Release の両方でテストを緑にする。**

Release でしか出ない問題は実在する。未初期化変数は Debug では `0xCC` などのパターンで埋められて症状が安定するが、Release では前に使われていた値がそのまま残る。最適化によって未定義動作が顕在化することもある。

テストエクスプローラーは、現在選択されている構成のテストを実行する。構成を切り替えて二回実行する、という単純な運用でよい。

### x64 に固定する

プラットフォームは **x64** のみを使う。ツールバーのプラットフォーム選択が `x86` や `Win32` になっていたら x64 に変更する。

32 ビットのビルドを扱わないのは、単に必要がないからである。加えて、x86 の浮動小数点演算には x87 という古い方式が絡み、80 ビットの中間精度という厄介な要素が入ってくる。x64 では浮動小数点演算は SSE を使うので、この問題は存在しない。混乱の種を一つ減らせる。

不要な構成は、ビルド → **構成マネージャー** から削除できる。整理しておくと、うっかり x86 でビルドして悩む事故を防げる。

- `/fp:fast` は Release だけでなく Debug でも有効にする
- プラットフォームは x64 に固定する
- コミット前に Debug と Release の両方でテストを緑にする

### 落とし穴と練習問題

**落とし穴 1：構成ごとの設定漏れ。**　この章で最も起こりやすい事故である。プロパティページ上部の「構成」が `Debug` のままになっていないか、常に確認する癖をつける。`Common.props` に移した設定については、プロパティシート側は構成を持たないので（プロパティマネージャーで Debug/Release それぞれの下に同じシートが並ぶ形になる）、追加時にどちらの構成に足したかを確認すること。

**落とし穴 2：プロジェクト側の設定がプロパティシートを上書きする。**　プロパティシートに書いたのに反映されないときは、プロジェクト側に同じ項目の値が残っている。プロパティページで値が**太字**で表示されていれば、それはそのプロジェクトで明示的に設定された値である。「既定値から継承」を選んでクリアする。

**落とし穴 3：`pch.h` の残骸。**　テンプレートが生成したファイルを消したのにプリコンパイル済みヘッダの設定を戻していないと、`fatal error C1083: include ファイルを開けません。'pch.h'` で止まる。2.2 節を参照。

---

**練習問題 2-1**　`Common.props` をテキストエディタで開き、中身を眺めてみよう。設定した項目が XML の要素としてどう表現されているかを確認する。手でこのファイルを編集して設定を変更できることが分かるはずである。

**練習問題 2-2**　`cl` コマンドに `/Bv` を付けて実行し、コンパイラを構成するツールのバージョンを表示させてみよう。`/help` でオプションの一覧も出る。IDE のプロパティページの各項目が、どのコマンドラインオプションに対応しているかを確かめる習慣は、後で問題を検索するときに役立つ。

**練習問題 2-3**　わざと警告を出すコードを書き、`/WX` によってビルドが止まることを確認しよう。たとえば `float x = 0.1;` の一行でよい（C4305 が出る）。次に `0.1f` に直して通ることを確認する。この警告が実際に何を防いでいるのかは、第 4 章を読むと腑に落ちるはずである。

**練習問題 2-4**（発展）　`/fp:fast` と `/fp:precise` で、同じ簡単な関数がどう違う機械語になるかを見てみよう。C/C++ → 出力ファイル → **アセンブリの出力** を「アセンブリ コード (/FA)」にすると `.asm` ファイルが生成される。`float f(float a, float b, float c) { return a * b + c; }` のような関数で、`vfmadd` 系の命令が現れるかどうかを比べる。第 4 章でこの作業を本格的に行うので、その予行演習になる。
