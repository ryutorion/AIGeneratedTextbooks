## 33.1 ブロードフェーズ → ナローフェーズ の接続

### ブロードフェーズを差し替え可能にする

第 30〜32 章で三つの実装を書いた。**どれを使うかはシーン次第**なので、差し替えられるようにしておきたい。

仮想関数を使う手もあるが、**コンセプトで縛ってテンプレートにする**ほうが本書の方針に合う（第 9 章、第 19 章と同じ判断である）。

```cpp
// collision/world/broadphase_concept.h
#pragma once
#include <concepts>
#include "collision/shapes/aabb.h"

namespace collision {

template <class B>
concept BroadPhase = requires(B& b, const B& cb,
                              std::int32_t h, std::uint32_t id, const Aabb& box,
                              std::vector<Pair>& pairs) {
    { b.create_proxy(box, id) } -> std::same_as<std::int32_t>;
    { b.destroy_proxy(h)     } -> std::same_as<void>;
    { b.move_proxy(h, box)   } -> std::same_as<void>;
    { b.collect_pairs(pairs) } -> std::same_as<BroadphaseCounters>;
};

} // namespace collision
```

**`create_proxy` が返す `std::int32_t` はハンドルであり、物体 ID とは別物である。** 木の内部節点の添字を返す実装（第 32 章）と、単に ID をそのまま返す実装（第 30・31 章）の両方を、この形で受けられる。

### 形状の組をどう捌くか

ブロードフェーズが返すのは ID の組である。**そこから実際の形状の判定へ振り分ける必要がある。**

形状は円・AABB・OBB・凸多角形・カプセルと種類が多く、その組は種類数の二乗ある。素直に `switch` を二重に書くと手に負えない。

**`std::variant` と `std::visit` を使う。**

```cpp
// collision/world/shape.h
using Shape2 = std::variant<Circle, Aabb, Obb, ConvexPolygon, Capsule>;

[[nodiscard]] std::optional<ContactManifold>
collide(const Shape2& a, const Transform2& xa,
        const Shape2& b, const Transform2& xb) {
    return std::visit([&](const auto& sa, const auto& sb)
                          -> std::optional<ContactManifold> {
        return collide_impl(sa, xa, sb, xb);
    }, a, b);
}
```

`collide_impl` は、これまでの章で書いてきた関数のオーバーロード群である。**組み合わせのうち一部だけ専用実装を書き、残りはサポート写像経由の GJK/EPA（第 19〜23 章）に落とす**のが実際的である。

```cpp
// 専用実装があるもの
std::optional<ContactManifold> collide_impl(const Circle&, const Transform2&,
                                            const Circle&, const Transform2&);
std::optional<ContactManifold> collide_impl(const Aabb&, const Transform2&,
                                            const Aabb&, const Transform2&);

// それ以外はすべてこれに落ちる（第 19 章の SupportShape を満たす形状）
template <SupportShape A, SupportShape B>
std::optional<ContactManifold> collide_impl(const A& a, const Transform2& xa,
                                            const B& b, const Transform2& xb) {
    return gjk_epa_manifold(a, xa, b, xb);
}
```

**専用実装は「速いから」ではなく「頻度が高いから」書く。** 円どうし・AABB どうしは大量に出るので割に合う。カプセル対凸多角形のような稀な組に専用実装を書く価値は薄い。

> **`std::visit` のコスト**
> `std::visit` は種類数の二乗のジャンプテーブルを作る。5 種類なら 25 分岐で、間接呼び出しが 1 回入る。
>
> ナローフェーズの中身（GJK なら数十回の反復）に比べれば無視できる。**ただし、円どうしのような一瞬で終わる判定が大量にある場合は、比率が変わる。**
>
> 気になるなら、**種類の組で先にソートしてから処理する**とよい。同じ組が連続すれば分岐予測が当たる。これは第 42 章の話題である。**まず動くものを作り、測ってから考える。**

### 1 フレームの流れ

```cpp
template <BroadPhase B>
void World<B>::step(float dt) {
    counters_.reset();

    // 1. AABB を更新し、ブロードフェーズへ反映する
    for (Body& body : bodies_) {
        if (body.is_static) continue;
        broadphase_.move_proxy(body.proxy, fatten(body.compute_aabb(), body.velocity, dt));
    }

    // 2. 候補ペアを集める
    counters_ += broadphase_.collect_pairs(pair_buffer_);

    // 3. フィルタし、ナローフェーズへ
    ++frame_;
    for (const auto [ia, ib] : pair_buffer_) {
        const Body& a = bodies_[ia];
        const Body& b = bodies_[ib];
        if (!should_collide(a.filter, b.filter)) continue;   // 33.3 節
        if (a.is_static && b.is_static) continue;

        if (auto m = collide(a.shape, a.transform, b.shape, b.transform)) {
            touch(ia, ib, *m);                                // 33.2 節
        }
    }

    // 4. 触られなかったペアを終了扱いにする
    expire_stale_pairs();

    // 5. 応答（第 VII 部）
    // solve_contacts(dt);
}
```

**この 5 段が、以降ずっと変わらない骨格である。** 第 VII 部で追加されるのは 5 番目だけである。

## 33.2 ペアの永続化 ― 接触の開始・継続・終了

### なぜ永続化が要るのか

毎フレーム接触を作り直すだけなら、単純である。**だが三つの用途で、フレームをまたいだ同一性が要る。**

1. **ウォームスタート（第 37.2 節）。** 前フレームの力積を初期値に使うと、ソルバの収束が劇的に速くなる。前フレームの「同じ接触」が分からなければ使えない
2. **ゲームロジック。** 「触れた瞬間」にダメージ、「離れた瞬間」にエフェクト終了、といった処理は開始・終了のイベントを必要とする
3. **マニフォールドの点の対応づけ（第 14 章）。** 接触点が前フレームのどの点に対応するかが分かると、摩擦力積を引き継げる

### キーの設計

二つの ID から一意なキーを作る。

```cpp
// collision/world/pair_key.h
struct PairKey {
    std::uint64_t value{};

    // 常に (小さい方, 大きい方) で構成する。順序が入れ替わっても同じキーになる
    [[nodiscard]] static constexpr PairKey make(std::uint32_t a,
                                                std::uint32_t b) noexcept {
        const std::uint32_t lo = (a < b) ? a : b;
        const std::uint32_t hi = (a < b) ? b : a;
        return PairKey{(static_cast<std::uint64_t>(lo) << 32) | hi};
    }

    [[nodiscard]] constexpr std::uint32_t first()  const noexcept {
        return static_cast<std::uint32_t>(value >> 32); }
    [[nodiscard]] constexpr std::uint32_t second() const noexcept {
        return static_cast<std::uint32_t>(value); }

    [[nodiscard]] friend constexpr bool operator==(PairKey, PairKey) noexcept = default;
    [[nodiscard]] friend constexpr auto operator<=>(PairKey, PairKey) noexcept = default;
};
```

**正規化（小さい方を上位に）を `make` の中に閉じ込める**のが要点である。呼び出し側が順序を気にしなくてよくなる。

`operator<=>` を既定で入れておくと、`std::map` に入れることも、ソートして差分を取ることもできる。

### フレームスタンプによる寿命管理

「今フレーム触られたか」を、フラグではなく**フレーム番号**で持つ。

```cpp
struct ContactPair {
    ContactManifold manifold{};
    std::uint32_t   stamp{};        // 最後に触られたフレーム番号
    bool            was_touching{}; // 前フレームに実際に接触していたか
};

void World::touch(std::uint32_t a, std::uint32_t b, const ContactManifold& m) {
    const PairKey key = PairKey::make(a, b);
    auto [it, inserted] = pairs_.try_emplace(key);
    ContactPair& p = it->second;

    if (inserted || !p.was_touching) {
        events_.push_back(ContactEvent{key, ContactEvent::Kind::Begin});
    } else {
        events_.push_back(ContactEvent{key, ContactEvent::Kind::Stay});
    }

    match_and_warm_start(p.manifold, m);   // 前フレームの力積を引き継ぐ（第 37 章）
    p.manifold    = m;
    p.stamp       = frame_;
    p.was_touching = true;
}

void World::expire_stale_pairs() {
    std::erase_if(pairs_, [&](auto& kv) {
        ContactPair& p = kv.second;
        if (p.stamp == frame_) return false;       // 今フレーム触られた
        if (p.was_touching) {
            events_.push_back(ContactEvent{kv.first, ContactEvent::Kind::End});
        }
        return true;                                // 表から取り除く
    });
}
```

**`std::erase_if` は C++20 で入った連想コンテナ向けのオーバーロードである。** 走査しながら消す定型のイテレータ操作を書かずに済む。

### ブロードフェーズの重なりと、実際の接触は違う

**ここが混乱しやすい。**

- ブロードフェーズが返すのは **fat AABB の重なり**（第 32.1 節）。実際には離れているかもしれない
- ナローフェーズが `std::nullopt` を返せば、**AABB は重なっていても形状は接触していない**
- ゲームロジックが欲しいのは、ほぼ常に**後者**である

```
         fat AABB 重なり ⊃ 実 AABB 重なり ⊃ 形状の接触
         （ブロードフェーズ）              （ナローフェーズ）
```

**`Begin` / `End` イベントは、いちばん内側の「形状の接触」に対して発行する。** 上のコードで `touch` がナローフェーズの成功時にだけ呼ばれ、`was_touching` を見ているのはそのためである。

一方、**ペアの表そのものは fat AABB の重なりで維持する**ほうが得である。物体が一瞬離れてまた触れる（振動する接触）ときに、表から消して作り直すとウォームスタートの情報が失われるからである。

**「表の寿命」と「イベントの条件」を分けるのが正解である。** 上の実装では `stamp` が表の寿命を、`was_touching` がイベントを担当している。

> **筆者が最初に間違えたところ**
> 最初の実装では、`pairs_` からの削除と `End` イベントを同一視していた。すると、床の上で微妙に振動している箱が **`Begin` と `End` を毎フレーム交互に発行し続けた**。ゲームロジック側では「着地音」が毎フレーム鳴った。
>
> **原因は接触判定ではなく、イベントの定義だった。** 第 34.3 節で扱う接触スロップ（`contact_slop`、第 5.9 節）を使い、「離れた」の判定に少し余裕を持たせることでも改善するが、まず**表の寿命とイベントの条件を分ける**のが構造的な解である。

### 走査順序を決定論的にする

**`std::unordered_map` の走査順序は規定されていない。** 実装が変われば変わるし、同じ実装でも挿入順や要素数で変わる。

第 VII 部のソルバは、接触を**順に**解いていく（第 37.1 節）。**順序が変わると結果が変わる。** 浮動小数点の非結合性のためであり、`/fp:fast` かどうかとは無関係な、より根の深い問題である。

症状は「同じ入力なのに、物体を追加した順序が違うと積み木の崩れ方が変わる」といった形で出る。**再現しないバグほど厄介なものはない。**

対策は単純である。**ソルバに渡す前に、キーでソートする。**

```cpp
void World::build_solve_order() {
    solve_order_.clear();
    for (const auto& [key, pair] : pairs_)
        if (pair.was_touching) solve_order_.push_back(key);
    std::ranges::sort(solve_order_);      // PairKey の operator<=> を使う
}
```

**`PairKey` に `operator<=>` を入れておいたのは、このためでもある。** ソートのコストは接触数 `k` に対して O(k log k) で、ソルバの反復に比べれば無視できる。

第 41.3 節でリプレイの再現性を扱うとき、ここに戻ってくる。**「同一バイナリ・同一マシンで再現する」ためには、`/fp:fast` の扱いだけでなく、コンテナの走査順序まで押さえる必要がある。**

### イベントを消費する側

```cpp
// 1 フレーム分のイベントを、まとめて読む
[[nodiscard]] std::span<const ContactEvent> World::events() const noexcept {
    return events_;
}
```

**コールバックではなく、配列を返す。** 理由は三つある。

1. コールバックの中から `World` を変更されると壊れる（物体の削除など）
2. イベントの順序を呼び出し側が制御できる
3. **テストしやすい**（33.5 節でそのまま期待値と比較する）

呼び出し側は `step()` のあとで読み、次の `step()` の先頭でクリアされる。

## 33.3 レイヤーとマスクによるフィルタリング

### 何と何が当たるかを表現する

プレイヤーの弾は敵に当たるが味方には当たらない、カメラ用のコリジョンは弾を止めない——こうした関係を宣言的に書きたい。

**定番はビットマスクである。**

```cpp
// collision/world/filter.h
enum class Layer : std::uint32_t {
    None      = 0,
    Player    = 1u << 0,
    Enemy     = 1u << 1,
    PlayerAmmo= 1u << 2,
    EnemyAmmo = 1u << 3,
    Terrain   = 1u << 4,
    Trigger   = 1u << 5,
    CameraOnly= 1u << 6,
    All       = 0xFFFFFFFFu,
};

[[nodiscard]] constexpr Layer operator|(Layer a, Layer b) noexcept {
    return static_cast<Layer>(std::to_underlying(a) | std::to_underlying(b));
}

struct Filter {
    Layer category{Layer::All};   // 自分は何者か
    Layer mask{Layer::All};       // 自分は何と当たりたいか
};
```

`std::to_underlying`（C++23）を使うと `static_cast<std::underlying_type_t<Layer>>` と書かずに済む。

### 判定は「かつ」である

```cpp
[[nodiscard]] constexpr bool should_collide(Filter a, Filter b) noexcept {
    return (std::to_underlying(a.mask) & std::to_underlying(b.category)) != 0
        && (std::to_underlying(b.mask) & std::to_underlying(a.category)) != 0;
}
```

**`&&` であることが決定的に重要である。** これにより関係が**対称**になる。「A は B と当たりたいが、B は A と当たりたくない」場合、当たらない。

`||` にすると非対称になり、片方から見ると当たり、もう片方から見ると当たらない、という状態が生まれる。**衝突応答は両方の物体に力を与えるので、非対称な関係は物理的に意味をなさない。**

```cpp
static_assert(should_collide(Filter{Layer::Player,     Layer::Enemy},
                             Filter{Layer::Enemy,      Layer::Player}));
static_assert(!should_collide(Filter{Layer::Player,    Layer::Enemy},
                              Filter{Layer::PlayerAmmo,Layer::Enemy}));
// 片側だけが望んでも当たらない
static_assert(!should_collide(Filter{Layer::Player,    Layer::All},
                              Filter{Layer::Enemy,     Layer::None}));
```

**`constexpr` にしておけば `static_assert` でフィルタ設計そのものをテストできる。** 実行時テストより早く、確実である。

### どこでフィルタするか

**できるだけ早く。** 遅いほど無駄な仕事が増える。

| フィルタ位置 | 落とせるコスト | 実装のしやすさ |
|---|---|---|
| ブロードフェーズの木の中 | 節点の走査ごと | 難しい（節点にマスクの和が要る） |
| **候補ペアのループ** | **ナローフェーズ全体** | **易しい** |
| ナローフェーズの内部 | ほぼ何も落とせない | — |

**本書は候補ペアのループで行う**（33.1 節の `step` のとおり）。ナローフェーズは候補 1 件あたり最も高い処理なので、その手前で落とせば十分である。

**ただしクエリ API（次節）は話が別である。** 「Terrain レイヤーだけにレイを飛ばす」ようなクエリでは、木を降りる段階で落とせると大きい。節点にマスクの論理和を持たせて枝ごと捨てる最適化が効く。

## 33.4 クエリ API の設計

### 接触点の対応づけ

もう一つ、永続化がなければできないことがある。**マニフォールドの点を、前フレームの点と対応づける**ことである。

第 14 章のマニフォールドは最大 2 点（3D なら 4 点以上）を持つ。フレームが進むと、点の位置も個数も変わる。**「この点は前フレームのどの点の続きか」が分からないと、摩擦力積を引き継げない。**

対応づけには、**接触点がどの特徴（頂点・辺）から生まれたかの ID** を使う。

```cpp
// 接触点がどの特徴の組から生まれたかを表す
struct ContactId {
    std::uint8_t ref_face{};    // 参照面の番号（第 14 章）
    std::uint8_t inc_face{};    // 入射面の番号
    std::uint8_t ref_vertex{};
    std::uint8_t inc_vertex{};

    [[nodiscard]] friend constexpr bool operator==(ContactId, ContactId) noexcept
        = default;
};

void match_and_warm_start(const ContactManifold& old_m, ContactManifold& new_m) {
    for (auto& np : new_m.points) {
        for (const auto& op : old_m.points) {
            if (np.id == op.id) {            // 同じ特徴の組から生まれた点
                np.normal_impulse  = op.normal_impulse;
                np.tangent_impulse = op.tangent_impulse;
                break;
            }
        }
    }
}
```

**位置の近さで対応づけてはいけない。** 物体が高速で動くと点は大きく動くし、点が 2 個あるとどちらに対応するのか曖昧になる。**特徴の ID は離散なので、`/fp:fast` の影響も受けない。**

第 14 章で `select_faces` に面の番号を持たせておいたのは、ここで使うためである。**部品を作るときに「後で何に使うか」を織り込んでおくと、つなぐ段階で楽になる。**

### 三種類のクエリ

ゲームロジックが必要とするのは、だいたい次の三つである。

| クエリ | 用途 | 実装 |
|---|---|---|
| `overlap(shape, filter)` | 範囲攻撃、トリガー領域 | 木の領域クエリ ＋ ナローフェーズ |
| `raycast(ray, filter)` | 射線判定、地面の高さ取り | 第 32.4 節 ＋ 第 15・27 章 |
| `sweep(shape, delta, filter)` | 移動可能判定、CCD | 第 32.4 節 ＋ 第 17・18 章 |

### 確保しない設計

**クエリはフレームに何百回も呼ばれる。** 毎回 `std::vector` を返すと、確保と解放が積み上がる。

**呼び出し側が用意した `std::span` に書き込み、書き込んだ数を返す。** 溢れたときは `std::expected` でエラーを返す。

```cpp
// collision/world/query.h
enum class QueryError { buffer_too_small };

// 結果を out に書き込み、件数を返す。溢れたら buffer_too_small
template <BroadPhase B>
[[nodiscard]] std::expected<std::size_t, QueryError>
World<B>::overlap(const Shape2& shape, const Transform2& xf, Filter filter,
                  std::span<std::uint32_t> out) const;
```

**溢れを黙って切り捨てない**ことが要点である。「範囲攻撃が 32 体までしか当たらない」というバグは、切り捨てを黙認したときに生まれる。`std::expected` なら、呼び出し側は無視できない。

```cpp
std::array<std::uint32_t, 64> hits{};
if (const auto n = world.overlap(blast, xf, enemy_filter, hits)) {
    for (const std::uint32_t id : hits | std::views::take(*n)) apply_damage(id);
} else {
    // バッファが足りない。広げて再試行するか、設計を見直す
    std::print("範囲攻撃の対象が 64 体を超えました\n");
}
```

**便利さのために、`std::vector` を返す薄い包みも用意しておく。** 性能が問題にならない場所ではこちらを使えばよい。

```cpp
[[nodiscard]] std::vector<std::uint32_t>
World<B>::overlap(const Shape2& shape, const Transform2& xf, Filter filter) const {
    std::vector<std::uint32_t> out;
    broadphase_.query(bounds_of(shape, xf), [&](std::uint32_t id) {
        if (should_collide(filter, bodies_[id].filter) && narrow_overlap(id, shape, xf))
            out.push_back(id);
    });
    return out;
}
```

**「確保しない版が本体、確保する版が便利包み」という順序が大事である。** 逆にすると、性能が要る場所で逃げ道がなくなる。

### レイキャストの二つの形

```cpp
// 最も近い 1 件だけが欲しい（射線判定、地面の高さ）
[[nodiscard]] std::optional<RayHit>
raycast_closest(const Ray& ray, Filter filter) const;

// 全部欲しい（貫通する弾、視界の判定）
[[nodiscard]] std::expected<std::size_t, QueryError>
raycast_all(const Ray& ray, Filter filter, std::span<RayHit> out) const;
```

**`raycast_closest` のほうが圧倒的に速い。** 第 32.4 節の `t_max` 縮小が効くからである。`raycast_all` では枝刈りができないので、訪問節点数が数倍になる。

**API を分けておくと、呼び出し側が「本当に全部要るのか」を意識する。** 一つの関数に `bool find_all` を渡す設計にすると、深く考えずに `true` が渡される。

## 33.5 シナリオテストという考え方

### 単体テストでは足りないもの

ここまでのテストは、**1 回の呼び出しの入出力**を検証してきた。「この二つの円は交差し、深さは 0.5」。

**だがイベントは状態機械である。** `Begin` は「前フレームに接触していなかった」ときにだけ出る。1 回の呼び出しを見ても正しさは分からない。

**シナリオテスト**は、時系列の入力に対する**イベント列**を検証する。

### 小さなシナリオ記述

```cpp
// tests/scenario.h
namespace collision_tests {

struct Step {
    std::uint32_t body{};
    Vec2          move{};      // このフレームでの移動量
};

struct Scenario {
    std::vector<Step> steps;   // 1 フレーム 1 要素
};

// イベント列を「種類と相手」の列に潰す（座標は比較しない）
[[nodiscard]] std::vector<std::string> run(collision::World<Bp>& world,
                                           const Scenario& s) {
    std::vector<std::string> log;
    for (const Step& st : s.steps) {
        world.translate(st.body, st.move);
        world.step(1.0f / 60.0f);
        for (const auto& e : world.events()) {
            log.push_back(std::format("{} {} {}",
                to_string(e.kind), e.key.first(), e.key.second()));
        }
    }
    return log;
}

} // namespace collision_tests
```

**イベントを文字列に潰す**のは手抜きに見えるが、意図がある。**失敗したときのメッセージが読める**からである。`Assert` が `期待 "Begin 0 1" / 実際 "Stay 0 1"` と出せば、原因が一目で分かる。第 3 章で `expect_near` に `diff` を出させたのと同じ思想である。

### 落ちて、乗って、転がり落ちる

```cpp
TEST_METHOD(床に落ちて滑り落ちるまでのイベント列が正しいこと) {
    collision::World<collision::DynamicTree> world;
    const auto floor = world.add_static(collision::Aabb{Vec2{-5,-1}, Vec2{5,0}},
                                        Filter{Layer::Terrain, Layer::All});
    const auto ball  = world.add_dynamic(collision::Circle{0.5f},
                                         Transform2{Vec2{0.0f, 3.0f}},
                                         Filter{Layer::Player, Layer::All});

    Scenario s;
    for (int i = 0; i < 10; ++i) s.steps.push_back(Step{ball, Vec2{0.0f, -0.4f}});  // 落下
    for (int i = 0; i < 5;  ++i) s.steps.push_back(Step{ball, Vec2{0.6f,  0.0f}});  // 横移動
    for (int i = 0; i < 5;  ++i) s.steps.push_back(Step{ball, Vec2{0.0f, -0.4f}});  // 床の外で落下

    const auto log = run(world, s);

    // 期待するイベントの「形」を検証する。フレーム番号は含めない
    Assert::AreEqual(std::string("Begin 0 1"), log.front());
    Assert::AreEqual(std::string("End 0 1"),   log.back());
    Assert::IsTrue(std::ranges::count(log, std::string("Begin 0 1")) == 1,
                   L"Begin が 2 回以上出ています（振動している可能性）");
    Assert::IsTrue(std::ranges::count(log, std::string("End 0 1")) == 1);
    Assert::IsTrue(std::ranges::all_of(log | std::views::drop(1)
                                           | std::views::take(log.size() - 2),
                   [](const std::string& e) { return e.starts_with("Stay"); }));
}
```

**`Begin` がちょうど 1 回であることを検査するのが要点である。** 33.2 節のコラムで述べた「毎フレーム Begin/End が交互に出る」バグは、まさにこれで捕まる。

### `/fp:fast` の下でシナリオを設計する

**イベントの発生フレームを厳密に検証してはいけない。**

接触の開始は「深さが 0 を跨ぐ」瞬間である。ちょうど境界にいるとき、`/fp:fast` の再結合で符号が変わりうる。**フレーム 7 で `Begin` が出るか、フレーム 8 で出るかは保証できない。**

対策は二つある。

**対策 1：シナリオを余裕を持って作る。** 上の例では 1 フレームに 0.4 動くのに対し、球の半径は 0.5 である。**境界をかすめる動きを含めない。** 意図的にはっきり接触させ、はっきり離す。

**対策 2：フレーム番号を許容範囲で検証する。**

```cpp
// 「7 フレーム目あたりで Begin」を ±2 フレームの幅で検証する
const auto begin_frame = find_event_frame(log_with_frames, "Begin 0 1");
Assert::IsTrue(begin_frame.has_value());
Assert::IsTrue(std::abs(static_cast<int>(*begin_frame) - 7) <= 2,
               std::format(L"Begin が {} フレーム目（期待 7±2）", *begin_frame).c_str());
```

**イベントの「種類の列」は離散なので厳密に比較してよい。時刻は連続量なので許容範囲で比較する。** この区別が、`/fp:fast` の下でシナリオテストを安定させる鍵である。

第 3.5 節で「ビット一致を要求しない」と決めたことの、いちばん外側での適用にあたる。

### シナリオを回帰テストとして残す

**バグを見つけたら、それを再現する最小のシナリオをテストとして残す。** 第 38.5 節のキャラクターコントローラでも同じ手を使う。

```cpp
// 回帰：v0.4 で「角に乗ると Begin/End が振動する」不具合が出たときのシナリオ
TEST_METHOD(回帰_角に乗ったとき振動しないこと) { ... }
```

**シナリオは短いほどよい。** 30 フレームを超えるシナリオは、落ちたときに原因を追いにくい。**再現する最小の長さまで削ってから残す。**

## この章のまとめ

- ブロードフェーズは**コンセプトで縛って差し替え可能に**する。仮想関数は使わない
- 形状の組は **`std::variant` ＋ `std::visit`**。頻度の高い組にだけ専用実装を書き、残りは GJK/EPA へ落とす
- 1 フレームは **AABB 更新 → 候補収集 → フィルタとナローフェーズ → 期限切れ処理 → 応答**の 5 段
- ペアのキーは**小さい方を上位にした 64 ビット**。正規化を `make` に閉じ込める
- 寿命は**フレームスタンプ**で管理する。触られなかったペアを走査の最後に消す
- **「表の寿命」と「イベントの条件」を分ける。** 一緒にすると振動する接触で `Begin`/`End` が交互に出続ける
- イベントは**配列で返す**。コールバックにしない（安全・順序制御・テストしやすさ）
- レイヤーとマスクの判定は **`&&`**。これで関係が対称になる。`||` は物理的に意味をなさない
- フィルタは**候補ペアのループで**行う。クエリ API では木の中で落とせると効く
- クエリは **`std::span` ＋ `std::expected` が本体**、`std::vector` を返すのは便利包み
- **溢れを黙って切り捨てない。** 「32 体までしか当たらない」バグはそこから生まれる
- `raycast_closest` と `raycast_all` は分ける。前者だけが `t_max` の枝刈りを使える
- **シナリオテストは時系列の入力に対するイベント列を検証する。** 状態機械は単体テストでは守れない
- **イベントの種類の列は厳密に、発生フレームは許容範囲で比較する。** `/fp:fast` の下での鉄則

### 落とし穴と練習問題

**落とし穴 1：`Begin` をブロードフェーズの重なりで発行する。**　fat AABB が重なっただけで「当たった」ことになる。

**落とし穴 2：レイヤー判定を `||` で書く。**　非対称な衝突関係が生まれ、応答が破綻する。

**落とし穴 3：イベントのコールバックの中で物体を削除する。**　走査中のコンテナが壊れる。配列で返して後で処理する。

**落とし穴 4：シナリオで境界すれすれの動きを使う。**　`/fp:fast` でフレームがずれ、テストが不安定になる。

**落とし穴 5：クエリの結果を無言で切り捨てる。**　症状が「たまに当たらない」になり、原因究明が極めて難しい。

**練習問題 33-1**　`should_collide` を `||` に書き換えて、33.3 節の `static_assert` がどれだけ落ちるか確かめよう。落ちなかったものがあれば、それはなぜだろうか。

**練習問題 33-2**　`expire_stale_pairs` から `was_touching` の判定を外し、「表から消える ＝ `End`」にしてみよう。床の上で静止している箱のシナリオで、何が起きるだろうか。

**練習問題 33-3**　ブロードフェーズを `UniformGrid`・`SweepAndPrune`・`DynamicTree` と差し替えて、33.5 節のシナリオテストを走らせよう。**イベント列は完全に一致するはずである。** 一致しなければ、いずれかの実装にバグがある。

**練習問題 33-4**　`overlap` の `std::span` 版で、バッファをわざと小さくして `buffer_too_small` が返ることを確認しよう。次に、必要な件数を返して呼び出し側が再確保できる設計に変えてみてほしい。どちらの API が使いやすいだろうか。

**練習問題 33-5**　第 29.4 節の `BroadphaseCounters` を `World` に集約し、1 フレームの「候補ペア数」「ナローフェーズ呼び出し回数」「フィルタで落ちた数」を出力しよう。フィルタで落ちる割合が高いなら、木の中でフィルタする価値がある。

**練習問題 33-6**（発展）　節点にマスクの論理和を持たせ、レイキャストで枝ごと捨てる最適化を実装しよう。`Terrain` だけを対象にしたレイで、訪問節点数がどれだけ減るだろうか。マスクの更新コストと釣り合うだろうか。

## 第 VI 部を終えて

第 29 章で「n = 1,000 で総当たりが破綻する」ことを測り、第 30〜32 章で三つの解を実装し、第 33 章でつないだ。n = 10,000 で 191 ミリ秒だったものが 1 ミリ秒を切るところまで来た。

**この部で繰り返し使った道具は二つである。**

**一つは「総当たりと同じ集合を返すこと」という等価性テスト。** ブロードフェーズは近似ではない。速いだけで、答えは総当たりと完全に一致しなければならない。この基準があったから、三つの実装すべてを同じテストで検証できた。

**もう一つは「時間ではなく仕事量を測る」という発想。** 候補ペア数、訪問節点数、ソートの交換回数——どれも決定論的で、CI に載せられる。**性能をテストできる形にしたことが、この部の隠れた成果である。**

次の第 VII 部では、いよいよ**衝突応答**に入る。ここまでは「当たったかどうか」を答えるだけだった。これからは「当たったあとどうなるか」を作る。第 34 章は最も素朴な方法——**めり込んだ分だけ押し戻す**——から始める。それだけでどこまで戦えるのか、そしてどこで破綻するのかを見ていく。
