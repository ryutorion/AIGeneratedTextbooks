### 本書の方針

| 項目 | 方針 |
|---|---|
| 環境 | Visual Studio 2026 / MSVC `/std:c++23preview`（または `/std:c++latest`）/ x64 |
| 言語機能 | C++23 を積極活用。ただし **モジュールは使わない**（従来のヘッダ + `.cpp` 構成） |
| 外部ライブラリ | 使わない。数学型・コンテナ補助・テスト基盤まで自作（標準ライブラリは全面活用） |
| 検証手段 | **すべて単体テストで確認**。描画・GUI は本文に登場させない |
| 浮動小数点 | **`/fp:fast` ＋ FTZ/DAZ を既定とする**（ゲーム用途として速度優先）。壊れる箇所だけ `#pragma float_control` で局所的に `precise` へ戻す |
| 進め方 | 1 章＝1 つの小さな機能。必ず「動くコード → 失敗するテスト → 通す」のサイクル |
| 読者 | C++ の文法・クラス・テンプレートの基礎は既知。数学とゲーム物理は初学者 |

> **`/fp:fast` を選ぶということ**
> 速度と引き換えに、コンパイラは式の再結合・FMA 契約・`x/y → x*(1/y)` の置換・非正規化数のフラッシュ (FTZ/DAZ) を自由に行ってよくなる。結果として **ビット単位の再現性は失われ、`NaN`/`Inf`/`-0.0` の挙動も保証されなくなる**。
> 本書はこれを「後で困る罠」ではなく **最初から設計に織り込むべき前提**として扱う。具体的には —
> - テストは常に**許容誤差ベース**で書く。ビット一致に依存するテストは一切書かない（第 3 章）
> - `NaN` 検出・区間の端の厳密比較・EPA の収束判定など、`/fp:fast` では成立しない箇所を**特定して局所的に `precise` へ戻す**（第 4 章で判断基準を確立し、以降の各章で適用）
> - **非正規化数は MXCSR の FTZ/DAZ で明示的に潰す**。`/fp:fast` を付けただけでは実行時の状態は保証されない（第 5 章）
> - リプレイの再現性は「同一バイナリ・同一マシン」に限定する。クロスプラットフォーム決定論が要る場合の分岐点は第 41 章で示す

各章は次の 5 ブロックで統一する。

1. **この章のゴール**（何が判定できるようになるか）
2. **考え方**（図と数式、なぜそうなるか）
3. **実装**（コードを少しずつ、差分で追う）
4. **テスト**（この章で追加する具体的なテストケース一覧）
5. **落とし穴と練習問題**

### 第 3 章　テスト環境を整える
- 3.1 Visual Studio 同梱の C++ 単体テストフレームワークを使う
- 3.2 最初のテスト：`Assert::AreEqual(1 + 1, 2)` を緑にする

- 3.4 補助ヘッダ `test_helpers.h` を書く

  - ベクトル・接触情報の比較用ヘルパ
  - 失敗時に値を表示する ― `std::format` によるメッセージ生成
- 3.5 **`/fp:fast` の下で崩れないテストの書き方**
  - ビット一致を要求しない ― `Assert::AreEqual(float, float)` を封印し、必ず許容誤差版を使う

  - 「答え」ではなく **性質**を検証する（法線は単位長か、対称か、単調か）― `/fp:fast` に強いテストの基本戦略
  - Debug と Release で結果が変わったときの調査手順（最適化の効きを疑う前に、許容誤差の設計を疑う）
  - 乱数は必ずシード固定（`std::mt19937` を固定シードで）― 乱数列自体は整数演算なので `/fp:fast` の影響を受けない
- 3.6 テストプロジェクトだけ `/fp:precise` にしてはいけない理由（テストと本番で挙動が変わる）
- 3.7 テストフィクスチャの雛形 ― **全テスト共通の初期化フックを 1 箇所に作る**（第 5 章で MXCSR 設定をここに追加する）
- 3.8 「テストを先に書く」流儀を本書でどう運用するか

### 第 4 章　浮動小数点と `/fp:fast` ― 本書で最も重要な準備
- 4.1 `float` の刻み幅 ― ULP という考え方
- 4.2 「等しい」を判定してはいけない ― キャンセルと誤差の蓄積
- 4.3 スケール相対の許容誤差を設計する（ゲーム世界の単位を決める）
- 4.4 **`/fp:fast` でコンパイラに許可したこと**を具体的に見る
  - 再結合 ― `(a+b)+c` を `a+(b+c)` にしてよい。総和の順序が変わる
  - FMA 契約 ― `a*b+c` が丸め 1 回に融合され、結果が「より正確に」ズレる
  - 除算の逆数置換と `rsqrt` 近似 ― `x/y`、`1/sqrt(x)` の精度低下
  - `-0.0` と `+0.0` の同一視、`x != x` による NaN 判定の消滅
  - 非正規化数の扱い ― これは大きな主題なので次章で独立して扱う
  - 逆アセンブリで実際に確認する（`vfmadd` 命令、`vrsqrtps` 命令を探す）
- 4.5 **`/fp:fast` で壊れるコードのパターンと書き換え**
  - `if (x != x)` → `std::isnan` も最適化されうる。ビットパターン検査による確実な NaN 検出
  - `if (d > 0 && d < eps)` のような閾値の両側比較が非対称に壊れる例
  - 判別式 `b*b - 4*a*c` の符号 ― わずかな負値で `sqrt` が NaN を返す。クランプを必ず入れる
  - 正規化前のゼロ長チェックを FTZ 前提で書き直す
- 4.6 **`#pragma float_control` による局所的な精度の取り戻し方**
  - `#pragma float_control(precise, on, push)` / `pop` の使い方とスコープ
  - `__declspec(noinline)` との併用、インライン展開で pragma が漏れる問題
  - **どこを `precise` に戻すかの判断基準**（本書全体で適用するルールをここで決める）
    - 反復アルゴリズムの収束判定 → 戻す
    - NaN/Inf のガード → 戻す
    - 大量に回る内積・外積・距離計算 → 戻さない（`/fp:fast` のまま）
  - コストの測定：`precise` に戻した関数がどれだけ遅くなるかを実測する
- 4.7 テスト：意図的に誤差を起こす入力（極大・極小スケール、桁落ち）で比較ヘルパと各ガードの妥当性を検証する

### 第 5 章　非正規化数と FTZ/DAZ ― 見えない速度低下を潰す
- 5.1 非正規化数（subnormal）とは何か
  - 指数部の下限と「緩やかなアンダーフロー」― `float` でおよそ 1.2e-38 未満の世界
  - ビット表現を実際に並べて見る（`std::bit_cast` で覗く）
  - IEEE 754 がこれを用意した理由 ―「`x - y == 0` ならば `x == y`」を保証するため
- 5.2 **なぜ遅いのか** ― まず実測する
  - 非正規化数を意図的に大量発生させるベンチマークを書く
  - 同じコードが数倍〜数十倍遅くなる様子を目で見る
  - ハードウェアの事情：多くの x86 実装でマイクロコードアシストが走る。CPU 世代・ベンダで差が大きいので**自分の環境で必ず測る**
  - 「特定の場面でだけフレームが落ちる」の正体になりうる ― 平均値でなく最悪値を見る
- 5.3 **FTZ と DAZ は別物** ― 2 つのスイッチを正しく理解する
  - **FTZ**（Flush To Zero）― 演算の**結果**が非正規化数ならゼロにする。MXCSR bit 15
  - **DAZ**（Denormals Are Zero）― 演算の**入力**が非正規化数ならゼロとみなす。MXCSR bit 6
  - 片方だけでは取りこぼす理由（メモリから読んだ値・他モジュールが作った値は FTZ では防げない）― **必ず両方立てる**
  - MXCSR を実際に読み出して現在の状態を表示するデバッグ関数を書く
- 5.4 有効化する
  - `_MM_SET_FLUSH_ZERO_MODE(_MM_FLUSH_ZERO_ON)` / `_MM_SET_DENORMALS_ZERO_MODE(_MM_DENORMALS_ZERO_ON)`
  - `_controlfp_s(_DN_FLUSH, _MCW_DN)` という CRT 経由の方法との使い分け
  - **`/fp:fast` を付けただけでは足りない** ― コンパイル時の最適化許可と、実行時の MXCSR の状態は別の話
  - DAZ の可用性を CPUID で確認する（現代の x64 では実質常に利用可能だが、確認手順は示す）
  - 効いていることをアサーションで検証する
- 5.5 **MXCSR はスレッドごと** ― 最大の落とし穴
  - ワーカスレッド・スレッドプール・`std::jthread` すべてで個別に設定が必要
  - メインスレッドだけ速く、ジョブスレッドだけ遅いという不可解な現象
  - 設定漏れを構造的に防ぐ ― スレッド起動を 1 つのラッパに集約する
- 5.6 **他人に書き換えられる** ― 状態を守る
  - DLL・オーディオドライバ・他社ライブラリが MXCSR を変更することがある
  - RAII ガード `ScopedDenormalFlush` を書く（構築時に設定、破棄時に復元）
  - 逆に、自分のライブラリが呼び出し元の MXCSR を壊さない責任
  - Debug ビルドでフレーム境界ごとに MXCSR を検査するアサーション
- 5.7 **コリジョンコードで非正規化数はどこから来るのか**
  - 減衰していく速度 ― `v *= 0.99f` を繰り返すと必ず非正規化域に入る。**最も典型的な発生源**
  - 二乗長・二乗距離 ― 二乗すると指数が倍になるため、`1e-20` 程度の値が一気に非正規化域へ落ちる
  - 逆質量・逆慣性モーメント（質量が極端に大きい静的物体）
  - 収束していく反復計算の残差、極小の貫通深度、重心座標
  - 発生箇所を突き止める手法（アンダーフロー例外のマスクを一時的に外して捕まえる）
- 5.8 **何を失うか** ― FTZ/DAZ の副作用
  - 「`x - y == 0` ならば `x == y`」が成り立たなくなる ― **ゼロ除算の新しい経路が生まれる**
  - 二乗長がゼロに潰れる ― 正規化のガードを二乗値ではなく元のスケールで判定する書き換え
  - 極小スケールの世界が扱えなくなる ― 単位系の設計と直結する
  - スリープ判定が意図せず早く効いてしまうことの功罪（第 35 章で再訪）
- 5.9 **単位系を決める** ― この議論の帰結
  - 「この世界で意味のある最小の長さ・最小の速度」を明文化し、閾値をそこから逆算する
  - 1 単位＝1 メートルとしたとき、非正規化域はゲーム的に無意味であることを確認する
  - 極端に大きい／小さいオブジェクトを扱いたくなったときの逃げ道
- 5.10 テスト
  - **テストハーネスも本番と同じ MXCSR で走らせる** ― 第 3 章のフィクスチャに組み込む（ここを揃えないとテストは無意味になる）
  - FTZ/DAZ を ON/OFF 切り替えて挙動差を確認するテスト（切り替えヘルパを用意する）
  - 非正規化数を直接入力に与え、各ガードが働くことの検証
  - ベンチマークを回帰テストとして残す ― 将来 MXCSR 設定が失われたら性能テストが落ちる仕組み

  | 症状 | 原因 | 対処 |
  |---|---|---|
  | NaN 判定が効かない | `x != x` / `isnan` の除去 | ビットパターン検査、`precise` 領域 |

  | 軸平行レイが当たらない | `1/0` が `Inf` にならない | 分岐で明示処理 |
  | コンパイル時と実行時で値が違う | `constexpr` は `precise` 相当 | 定数畳み込みを期待しない |
  | Debug と Release で結果が違う | インライン展開による最適化差 | 許容誤差の設計を見直す |
- **付録 D**　**非正規化数・FTZ/DAZ カタログ**
  | 症状 | 原因 | 対処 |
  |---|---|---|
  | 特定の場面だけ急に重い | 非正規化数の大量発生 | FTZ/DAZ を有効化、発生源を設計で潰す |
  | ジョブスレッドだけ遅い | MXCSR がスレッドローカル | スレッド起動ラッパで全スレッドに設定 |
  | 途中から遅くなった | 他モジュールが MXCSR を変更 | RAII ガード、フレーム毎の検査アサート |
  | FTZ を立てたのに遅いまま | DAZ が未設定（入力側が非正規化数） | 両方立てる |
  | 物体が予定より早く止まる | 減衰速度が FTZ でゼロ化 | 明示的な速度しきい値でクランプ |
  | ゼロ除算が新たに発生 | `x-y` が FTZ でゼロ化 | 差分ではなく元の値でガード |
  | テストだけ挙動が違う | テスト側の MXCSR が未設定 | フィクスチャで本番と同じ状態にする |
  - `_MM_SET_FLUSH_ZERO_MODE` / `_MM_SET_DENORMALS_ZERO_MODE` / `_controlfp_s` 早見表、MXCSR ビット配置図
