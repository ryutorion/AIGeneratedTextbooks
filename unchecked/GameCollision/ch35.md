# 第 35 章　剛体の運動（2D）

> **この章のゴール**

## 35.1 質量・重心・慣性モーメント

### 剛体が持つもの

```cpp
// collision/dynamics/rigid_body.h
#pragma once
#include "collision/math/vec2.h"

namespace collision {

struct RigidBody {
    // 位置と姿勢
    Vec2  position{};
    float rotation{};            // ラジアン

    // 速度
    Vec2  velocity{};
    float angular_velocity{};    // ラジアン毎秒

    // 蓄積された力（毎フレームの最後にゼロへ戻す）
    Vec2  force{};
    float torque{};

    // 質量特性。逆数で持つ（静的剛体をゼロで表せる）
    float inv_mass{};
    float inv_inertia{};

    // 減衰
    float linear_damping{0.0f};
    float angular_damping{0.05f};
};

} // namespace collision
```

**質量ではなく逆質量を持つ**のが定石である。理由は三つある。

1. **静的剛体を `inv_mass = 0` で表せる。** 「無限大の質量」を特別扱いしなくてよい
2. 応答の計算で使うのはほぼ常に逆数のほうである（第 36 章）
3. 除算が消える。`/fp:fast` でも除算は乗算より遅い

### 形状ごとの導出

**慣性モーメントは「回しにくさ」である。** 質量が「動かしにくさ」であるのと対応している。

```cpp
// 密度 density から質量と慣性モーメントを求める

// 円（半径 r）
[[nodiscard]] constexpr MassData compute_mass(const Circle& c, float density) noexcept {
    const float mass = density * std::numbers::pi_v<float> * c.radius * c.radius;
    return MassData{
        .mass    = mass,
        .inertia = 0.5f * mass * c.radius * c.radius,      // m r² / 2
        .center  = Vec2{},
    };
}

// 長方形（幅 w、高さ h）
[[nodiscard]] constexpr MassData compute_mass(const Obb& b, float density) noexcept {
    const float w = b.extents.x * 2.0f;
    const float h = b.extents.y * 2.0f;
    const float mass = density * w * h;
    return MassData{
        .mass    = mass,
        .inertia = mass * (w * w + h * h) / 12.0f,          // m(w² + h²) / 12
        .center  = Vec2{},
    };
}
```

1 m 角・密度 1 の箱なら、質量 1、慣性モーメント `1 × (1 + 1) / 12 = 0.166667` である。この値は後の検算に何度も使う。

### 凸多角形

一般の凸多角形は、**原点と各辺で三角形に分割**して積分する。

```cpp
[[nodiscard]] MassData compute_mass(const ConvexPolygon& p, float density) noexcept {
    float area = 0.0f, inertia = 0.0f;
    Vec2  centroid{};

    for (std::size_t i = 0; i < p.count; ++i) {
        const Vec2 a = p.vertex[i];
        const Vec2 b = p.vertex[(i + 1) % p.count];

        const float cross_ab = cross(a, b);          // 三角形 (0,a,b) の面積 × 2
        const float tri_area = 0.5f * cross_ab;
        area     += tri_area;
        centroid += (a + b) * (tri_area / 3.0f);     // 三角形の重心は頂点の平均

        // 三角形 (0,a,b) の原点まわりの慣性モーメント
        inertia += cross_ab * (dot(a, a) + dot(a, b) + dot(b, b)) / 12.0f;
    }

    const float mass = density * area;
    centroid /= area;

    // 平行軸の定理で、原点まわり → 重心まわりへ移す
    inertia = density * inertia - mass * dot(centroid, centroid);

    return MassData{.mass = mass, .inertia = inertia, .center = centroid};
}
```

**平行軸の定理**——重心から `d` 離れた軸まわりの慣性モーメントは `I_重心 + m d²`——が最後の 1 行である。積分は原点まわりで計算するほうが簡単なので、あとから移す。

**この関数は、長方形を入力すると `m(w²+h²)/12` を返す。** 専用実装と一般実装が一致することは、必ずテストで確かめる（35.6 節）。

### 重心をどう扱うか

**本書は「形状の原点＝重心」と約束する。** 多角形の重心が原点からずれている場合、形状の頂点を平行移動して原点を重心に合わせる。

```cpp
void RigidBody::set_shape(ConvexPolygon p, float density) {
    const MassData md = compute_mass(p, density);
    for (std::size_t i = 0; i < p.count; ++i) p.vertex[i] -= md.center;  // 重心を原点へ
    shape_       = p;
    inv_mass_    = (md.mass    > 0.0f) ? 1.0f / md.mass    : 0.0f;
    inv_inertia_ = (md.inertia > 0.0f) ? 1.0f / md.inertia : 0.0f;
}
```

**この約束があると、以降の式から重心オフセットが全部消える。** 回転は必ず原点まわりになり、`position` はそのまま重心の位置になる。**約束を一つ置くだけで、あとの章のコードが目に見えて短くなる。**

## 35.2 速度と角速度、力とトルク

### 剛体上の点の速度

剛体が並進速度 `v` と角速度 `ω` を持つとき、**重心から `r` だけ離れた点の速度**は次のようになる。

```cpp
// 重心からの相対位置 r にある点の、ワールド座標での速度
[[nodiscard]] constexpr Vec2 point_velocity(const RigidBody& b, Vec2 r) noexcept {
    // v + ω × r。2D では ω はスカラーなので、外積は 90 度回転になる
    return b.velocity + Vec2{-b.angular_velocity * r.y, b.angular_velocity * r.x};
}
```

**`ω × r` が 90 度回転になる**のは、第 24.1 節で確認した「2D の外積はスカラー」の帰結である。3D なら本物の外積になる（第 39.1 節）。

**この関数が、第 36 章の全体を支える。** 接触点の相対速度を求めるのに使う。

### 力とトルク

```cpp
// 重心に力を加える（回転は生じない）
constexpr void apply_force(RigidBody& b, Vec2 f) noexcept { b.force += f; }

// 点 p（ワールド座標）に力を加える
constexpr void apply_force_at(RigidBody& b, Vec2 f, Vec2 p) noexcept {
    b.force  += f;
    b.torque += cross(p - b.position, f);      // r × F
}
```

**トルクは `r × F` である。** 2D では外積がスカラーなので、トルクもスカラーになる。

### 力積を使うほうが多い

ゲームでは「力」より**力積**を使う場面のほうが多い。爆発、ジャンプ、被弾のノックバック——どれも一瞬で速度を変えたい。

```cpp
constexpr void apply_impulse_at(RigidBody& b, Vec2 impulse, Vec2 p) noexcept {
    b.velocity         += impulse * b.inv_mass;
    b.angular_velocity += b.inv_inertia * cross(p - b.position, impulse);
}
```

**力積は速度を直接変える。** 力は積分を通して速度を変えるので、`dt` に依存する。「ジャンプで 5 m/s の上向き速度を与えたい」なら、力積のほうが素直である。

第 36 章の衝突応答は、全面的に力積で書く。理由は 36.1 節で述べる。

## 35.3 半陰的オイラー法による積分

### 二つの順序

速度と位置を進める順序には二通りある。

```cpp
// 前進（陽的）オイラー：位置を先に更新する
position += velocity * dt;
velocity += (force * inv_mass + gravity) * dt;

// 半陰的（シンプレクティック）オイラー：速度を先に更新する
velocity += (force * inv_mass + gravity) * dt;
position += velocity * dt;
```

**違いは 2 行の順序だけである。** それでも性質は大きく変わる。

### 自由落下で測る

`g = −9.81`、`dt = 1/60` で自由落下させ、解析解 `y = ½gt²` と比べた。

| ステップ | 時刻 | 数値解 | 解析解 | 誤差 | 誤差 ÷ (½·\|g\|·dt·t) |
|---:|---:|---:|---:|---:|---:|
| 1 | 0.017 | −0.002725 | −0.001362 | 0.001362 | **1.000000** |
| 60 | 1.000 | −4.986750 | −4.905000 | 0.081750 | **1.000000** |
| 180 | 3.000 | −44.390250 | −44.145000 | 0.245250 | **1.000000** |
| 600 | 10.000 | −491.3175 | −490.5000 | 0.817500 | **1.000000** |

**右端の列が完全に 1.000000 である。** つまり誤差はぴったり次の式になる。

```
誤差 = ½ · |g| · dt · t
```

**誤差は時刻 `t` に比例して増える。** これは偶然ではなく、1 ステップあたり `½ g dt²` の誤差が `t/dt` 回積み上がった結果である。

**前進オイラーは、同じ大きさの誤差を逆向きに出す。** 5 秒後で比べると、半陰的が −123.034（落ちすぎ）、前進が −122.216（落ち足りない）、解析解が −122.625。誤差はどちらも 0.40875 である。

### では、なぜ半陰的を選ぶのか

自由落下では引き分けだが、**振動する系で差がつく。**

ばねに繋がれた物体（あるいは接触の押し戻し）のように、**位置に応じて力が変わる系**では、前進オイラーはエネルギーが増え続けて発散する。半陰的オイラーは**エネルギーが有界に保たれる**（正確には、わずかにずれた別のエネルギー量が厳密に保存される）。

**振動しても発散しない。** これがゲーム物理で半陰的オイラーが選ばれる唯一にして決定的な理由である。

```cpp
void integrate_velocity(RigidBody& b, Vec2 gravity, float dt) noexcept {
    if (b.inv_mass <= 0.0f) return;                     // 静的剛体は動かさない
    b.velocity         += (b.force * b.inv_mass + gravity) * dt;
    b.angular_velocity += b.torque * b.inv_inertia * dt;

    apply_damping(b, dt);                                // 35.5 節
}

void integrate_position(RigidBody& b, float dt) noexcept {
    if (b.inv_mass <= 0.0f) return;
    b.position += b.velocity * dt;
    b.rotation += b.angular_velocity * dt;
    b.force = Vec2{}; b.torque = 0.0f;                   // 蓄積をクリア
}
```

**速度の積分と位置の積分を別の関数に分ける。** 間に衝突応答（第 36・37 章）が入るからである。

```
速度を積分 → 衝突検出 → 速度を修正（力積） → 位置を積分
```

**この順序が、第 VII 部を通じての骨格になる。**

### 重力は力ではなく加速度として扱う

重力を `force += mass * gravity` として加えることもできるが、**加速度として直接足すほうがよい。**

```cpp
// 悪くはないが冗長：質量を掛けて、あとで逆質量で割る
b.force += gravity / b.inv_mass;
b.velocity += b.force * b.inv_mass * dt;

// 良い：重力は質量によらず同じ加速度である
b.velocity += (b.force * b.inv_mass + gravity) * dt;
```

**「重力加速度は質量によらない」という物理をそのままコードにしたほうが、掛けて割る往復が消える。** そして `inv_mass = 0` の物体で `gravity / 0` を書かずに済む。

### 力の蓄積とクリアの寿命

`force` と `torque` は**1 フレームぶんの蓄積**である。積分し終わったらゼロに戻す。

```cpp
// 悪い：クリアを忘れると、力が毎フレーム積み上がって加速し続ける
// 悪い：積分の前にクリアすると、そのフレームの力が捨てられる
```

**クリアの位置は「速度の積分の直後」である。** 上の `integrate_position` に置いたのは、**位置の積分がフレームの最後だから**であって、意味的には速度の積分とセットである。

```cpp
void integrate_velocity(RigidBody& b, Vec2 gravity, float dt) noexcept {
    if (b.inv_mass <= 0.0f) { b.force = Vec2{}; b.torque = 0.0f; return; }
    b.velocity         += (b.force * b.inv_mass + gravity) * dt;
    b.angular_velocity += b.torque * b.inv_inertia * dt;
    b.force = Vec2{}; b.torque = 0.0f;      // ★ ここでクリアするほうが安全
    apply_damping(b, dt);
}
```

**静的剛体でもクリアする**のを忘れないこと。忘れると、静的物体に加えられた力が永久に残り、動的剛体に変換した瞬間に飛んでいく。

### 固定タイムステップ

`dt` は毎フレーム変えてはいけない。**可変にすると、フレームレートによって挙動が変わる。**

上の誤差の式を見れば理由が分かる。誤差は `dt` に比例するので、**120 fps で走らせると 60 fps の半分しか落ちない。** 「速いマシンだとジャンプが低い」という現象になる。

```cpp
// 固定タイムステップ。余りは次フレームへ持ち越す
void World::update(float real_dt) {
    accumulator_ += std::min(real_dt, 0.25f);   // 極端な遅延で暴走しないよう上限を切る
    while (accumulator_ >= fixed_dt) {
        step(fixed_dt);
        accumulator_ -= fixed_dt;
    }
}
```

**上限（ここでは 0.25 秒）を切る**のが実務上の要点である。デバッガで止めたあと再開すると `real_dt` が数十秒になり、`while` が数千回まわって完全に固まる。

### 描画は補間する

固定ステップにすると、**描画のタイミングと物理のタイミングがずれる。** そのまま描くと、60 fps の物理を 144 Hz のディスプレイに出したときにカクつく。

**残りの `accumulator_` を使って、前フレームと現フレームの間を補間する。**

```cpp
// 描画用の姿勢を得る。物理の状態は変更しない
[[nodiscard]] Transform2 World::interpolated(std::uint32_t id) const noexcept {
    const float alpha = accumulator_ / fixed_dt;      // 0.0 〜 1.0
    const RigidBody& b = bodies_[id];
    return Transform2{
        .position = lerp(previous_[id].position, b.position, alpha),
        .rotation = lerp_angle(previous_[id].rotation, b.rotation, alpha),
    };
}
```

**`previous_` は前ステップの状態のコピーである。** `step()` の先頭で保存する。

**角度の補間は `lerp` では足りない。** 3.14 から −3.14 へ変わったとき（1 周した）、素朴な線形補間は逆回りする。差を `[-π, π]` に畳んでから補間する。

```cpp
[[nodiscard]] inline float lerp_angle(float a, float b, float t) noexcept {
    float d = std::remainder(b - a, 2.0f * std::numbers::pi_v<float>);  // [-π, π]
    return a + d * t;
}
```

**`std::remainder` は `std::fmod` と違い、結果が `[-半分, +半分]` に入る。** ここでちょうど欲しい振る舞いである。

> `std::remainder` は `/fp:fast` の影響を受けない（ライブラリ関数であり、コンパイラが式として再結合することはない）。**周期的な量を扱うときの安全な選択肢**として覚えておくとよい。

## 35.4 静的剛体・動的剛体・キネマティック剛体

三種類を区別する。

| 種類 | `inv_mass` | 積分される | 力を受ける | 用途 |
|---|---|---|---|---|
| **動的** | > 0 | する | 受ける | 箱、樽、キャラクタ |
| **静的** | 0 | しない | 受けない | 地面、壁、建物 |
| **キネマティック** | 0 | **する** | 受けない | 動く床、エレベータ、扉 |

**キネマティックが便利である。** ゲームロジックが速度を設定すると、その通りに動く。当たった物体は押されるが、自分は押し返されない。

```cpp
enum class BodyType : std::uint8_t { Static, Kinematic, Dynamic };

[[nodiscard]] constexpr bool is_movable(BodyType t) noexcept {
    return t != BodyType::Static;
}
[[nodiscard]] constexpr bool responds_to_force(BodyType t) noexcept {
    return t == BodyType::Dynamic;
}
```

**「静的とキネマティックはどちらも `inv_mass = 0`」という点が重要である。** 第 36 章の力積の式は、どちらに対しても「動かない相手」として正しく振る舞う。**種類を増やしても、応答の式は増えない。**

一方、ブロードフェーズ（第 33.1 節）では区別が要る。**静的どうしのペアは判定不要**だが、キネマティックと静的は衝突しうる。

### キネマティック剛体の速度を「逆算」する

動く床をゲームロジックが「次はここへ」と指定する場合、**位置を直接書き換えてはいけない。**

```cpp
// 悪い：位置を直接書き換えると、接触判定が「瞬間移動」を見ることになる
platform.position = target;

// 良い：目標位置から速度を逆算し、積分に任せる
platform.velocity = (target - platform.position) / dt;
```

**速度を経由すると、二つのことが正しくなる。**

1. **床の上の物体が一緒に運ばれる。** 摩擦（第 36.4 節）は相対速度を見るので、床が速度を持っていないと物体を引きずれない
2. **スイープ判定（第 17 章）が働く。** 速い床が薄い物体を貫通しなくなる

**「位置を書き換える」と「速度を与える」は、シミュレーションの中では別物である。** ゲームロジック側から見れば同じ結果に見えるが、応答の扱いがまったく違う。

## 35.5 減衰する速度と非正規化数

### 減衰は何のためにあるのか

現実の物体は空気抵抗で止まる。ゲームでも、**減衰がないと物体が永久に転がり続ける。**

```cpp
void apply_damping(RigidBody& b, float dt) noexcept {
    // dt に依存しない形にする（60 fps でも 120 fps でも同じ減り方）
    b.velocity         *= 1.0f / (1.0f + dt * b.linear_damping);
    b.angular_velocity *= 1.0f / (1.0f + dt * b.angular_damping);
}
```

`v *= 0.99` と直接書くと `dt` に依存してしまうので、`1/(1 + dt·d)` の形にする。**フレームレートを変えても挙動が変わらない。**

### 第 5.7 節の回収 ― いつ非正規化域に落ちるのか

第 5 章で「減衰の繰り返しは非正規化数を生む典型例だ」と予告した。**実際にいつ落ちるのかを測った。**

初速 10 m/s から `v *= 0.99` を繰り返す。

| 到達点 | フレーム数 | 60 fps での時間 |
|---|---:|---:|
| 1 mm/s（`min_speed`、第 5.9 節） | 917 | 15.3 秒 |
| 1 μm/s（実用上ゼロ） | 1,604 | 26.7 秒 |
| **非正規化域（1.18e−38）** | **8,920** | **148.7 秒** |

**「実用上ゼロ」になってから、非正規化域に入るまで 7,316 フレーム（約 2 分）ある。**

減衰係数を変えても構造は同じである。

| 減衰 | 1 μm/s まで | 非正規化域まで | 差 |
|---|---:|---:|---:|
| `× 0.999` | 16,111 | 89,595 | 73,484 |
| `× 0.99` | 1,604 | 8,920 | 7,316 |
| `× 0.95` | 315 | 1,748 | 1,433 |
| `× 0.9` | 153 | 851 | 698 |

### 二つの結論

**結論 1：閾値でクランプすれば、非正規化数には到達しない。**

第 5.9 節で決めた `min_speed = 1.0e-3f`（1 mm/s）でゼロクランプすれば、上の表の一段目で止まる。**非正規化域の 8,920 フレーム目に到達することは、そもそもない。**

```cpp
void clamp_tiny_velocity(RigidBody& b) noexcept {
    if (length_squared(b.velocity) < min_speed * min_speed) b.velocity = Vec2{};
    if (std::fabs(b.angular_velocity) < min_angular_speed)  b.angular_velocity = 0.0f;
}
```

**結論 2：FTZ に任せると、挙動が「見えない」。**

FTZ（第 5 章）を有効にしていれば、非正規化数はハードウェアがゼロに潰す。速度が消えるので、結果としては同じところに落ち着く。

**だが到達するまでに 148 秒かかる。** その間、物体は「止まっているように見えるが、内部的には動いている」状態でいる。スリープ処理（第 37.4 節）の判定が入るとさらに複雑になる。

**そして FTZ は MXCSR の状態に依存する。** 第 5.6 節で見たとおり、MXCSR はスレッドローカルであり、外部ライブラリが書き換えることもある。**「FTZ が効いているはずだから大丈夫」という前提は、プログラムの正しさの根拠として弱すぎる。**

| | 明示的クランプ | FTZ に依存 |
|---|---|---|
| ゼロになるタイミング | **仕様として決まる**（1 mm/s） | ハードウェア次第（1.18e−38） |
| MXCSR の状態への依存 | なし | **あり** |
| コードを読んで分かるか | **分かる** | 分からない |
| 速度 | 比較 1 回ぶん遅い | 速い |

**FTZ は「性能のための保険」であって、「設計」ではない。** 非正規化数による性能低下を防ぐために FTZ を有効にするのは正しい。**だがゼロになるタイミングを FTZ に決めさせてはいけない。**

第 5 章で「FTZ/DAZ を有効にする」と決めたことと、この結論は矛盾しない。**両方やる。** FTZ で性能の底を守り、明示的クランプで挙動を決める。

## 35.6 テスト：自由落下の解析解との比較

### 許容誤差をステップ数の関数にする

35.3 節で `誤差 = ½·|g|·dt·t` を確かめた。**この式をそのままテストの許容誤差に使う。**

```cpp
// test_integration.cpp
TEST_CLASS(IntegrationTest) {
public:
    TEST_METHOD(自由落下が解析解と一致すること) {
        constexpr float dt = 1.0f / 60.0f;
        constexpr float g  = -9.81f;

        collision::RigidBody body{};
        body.inv_mass = 1.0f;

        for (int step = 1; step <= 600; ++step) {
            integrate_velocity(body, Vec2{0.0f, g}, dt);
            integrate_position(body, dt);

            const float t          = static_cast<float>(step) * dt;
            const float analytic   = 0.5f * g * t * t;
            // 半陰的オイラーの理論誤差（35.3 節）＋ float の丸め分の余裕
            const float tolerance  = 0.5f * std::fabs(g) * dt * t * 1.05f + 1.0e-4f;

            expect_near(analytic, body.position.y, tolerance, 0.0f);
        }
    }
```

**許容誤差が `t` の関数になっている**のが要点である。定数にすると、短い時間では緩すぎ、長い時間では厳しすぎる。

**`× 1.05` の余裕は `float` の丸め分である。** 理論誤差ちょうどに置くと、累積した丸めで落ちる。

### 理論誤差より小さくならないことも確かめる

```cpp
    TEST_METHOD(半陰的オイラーの誤差が理論値どおりであること) {
        constexpr float dt = 1.0f / 60.0f, g = -9.81f;
        collision::RigidBody body{}; body.inv_mass = 1.0f;

        for (int step = 0; step < 600; ++step) {
            integrate_velocity(body, Vec2{0.0f, g}, dt);
            integrate_position(body, dt);
        }
        const float t = 600.0f * dt;
        const float error = std::fabs(body.position.y - 0.5f * g * t * t);
        const float theory = 0.5f * std::fabs(g) * dt * t;

        // 誤差が理論値の 0.95〜1.05 倍に収まること
        expect_near(1.0f, error / theory, 0.05f, 0.0f);
    }
```

**「誤差が小さすぎないこと」も検査している。** もし誰かが積分を変えて誤差がゼロになったら、それは前進オイラーとの取り違えか、解析解を計算してしまったかである。**期待と違う「良い結果」も、テストで捕まえる価値がある。**

### 質量特性の検算

```cpp
    TEST_METHOD(専用実装と一般実装の慣性モーメントが一致すること) {
        // 2×3 の長方形を、Obb としても ConvexPolygon としても作る
        const auto box = collision::Obb{.extents = Vec2{1.0f, 1.5f}};
        const auto poly = collision::make_rectangle(2.0f, 3.0f);

        const auto md1 = collision::compute_mass(box,  1.0f);
        const auto md2 = collision::compute_mass(poly, 1.0f);

        expect_near(md1.mass,    md2.mass,    1.0e-4f, 1.0e-4f);
        expect_near(md1.inertia, md2.inertia, 1.0e-4f, 1.0e-4f);
        expect_near(6.0f,        md1.mass,    1.0e-5f, 1.0e-5f);   // 2 × 3 × 密度 1
        expect_near(6.0f * (4.0f + 9.0f) / 12.0f, md1.inertia, 1.0e-4f, 1.0e-4f);
    }

    TEST_METHOD(平行軸の定理が成り立つこと) {
        // 重心をずらした多角形の慣性モーメントが、移動後に一致すること
        Rng rng(5200);
        for (int i = 0; i < 2000; ++i) {
            const auto poly = random_convex_polygon(rng);
            const Vec2 shift{rng.uniform(-10.0f, 10.0f), rng.uniform(-10.0f, 10.0f)};

            const auto a = collision::compute_mass(poly, 1.0f);
            const auto b = collision::compute_mass(translated(poly, shift), 1.0f);

            // 重心まわりの慣性モーメントは平行移動で変わらない
            expect_near(a.inertia, b.inertia, 1.0e-3f, 1.0e-3f);
            expect_near(a.center + shift, b.center, 1.0e-3f, 1.0e-3f);
        }
    }
};
```

**平行移動に対する不変性は、性質ベーステストの典型である**（第 40.2 節）。値そのものを計算せずに、正しさを強く縛れる。

### 減衰のクランプ

```cpp
    TEST_METHOD(減衰した速度が有限フレームでゼロになること) {
        collision::RigidBody b{};
        b.inv_mass = 1.0f; b.linear_damping = 0.6f;
        b.velocity = Vec2{10.0f, 0.0f};

        int frames = 0;
        while (b.velocity.x != 0.0f) {
            apply_damping(b, 1.0f / 60.0f);
            clamp_tiny_velocity(b);
            if (++frames > 2000) Assert::Fail(L"2000 フレームでゼロにならない");
        }
        Logger::WriteMessage(std::format("{} フレームでゼロ\n", frames).c_str());

        // 非正規化域に到達する前にゼロになっていること
        Assert::IsTrue(frames < 3000);
    }
```

**「`!= 0.0f`」という厳密比較を、ここでは意図的に使っている。** 第 3.5 節で禁じたのは「計算結果の一致をビットで比較する」ことであって、**「明示的にゼロを代入したかどうか」の確認は別である。**

## この章のまとめ

- 剛体は**逆質量・逆慣性**で持つ。静的剛体をゼロで表せ、除算が消える
- 長方形の慣性モーメントは `m(w²+h²)/12`、円は `mr²/2`。1 m 角・密度 1 なら 0.166667
- 凸多角形は三角形に分割して積分し、**平行軸の定理**で重心まわりへ移す
- **「形状の原点＝重心」と約束する。** 以降の式から重心オフセットが全部消える
- 剛体上の点の速度は `v + ω × r`。2D では `ω × r` が 90 度回転になる
- **半陰的オイラーは速度を先に更新する。** 前進オイラーとの違いは 2 行の順序だけ
- 自由落下の誤差は**ぴったり `½·|g|·dt·t`**。実測で比が 1.000000 になる
- 誤差は `t` に比例して増える。**許容誤差はステップ数の関数として設計する**
- 半陰的を選ぶ理由は**振動する系で発散しないこと**。自由落下だけなら前進と引き分け
- `dt` は固定する。**可変だとフレームレートで挙動が変わる。** 上限も切る
- 重力は**力ではなく加速度**として足す。掛けて割る往復が消える
- 力とトルクのクリアは**速度の積分の直後**。静的剛体でもクリアする
- 描画は `accumulator_` を使って**補間**する。角度は `std::remainder` で差を畳んでから
- キネマティック剛体は**位置を書き換えず、目標から速度を逆算する。** 摩擦とスイープが正しく働く
- 静的・キネマティック・動的の三種。**どちらも `inv_mass = 0` なので応答の式は増えない**
- 減衰は `1/(1 + dt·d)` の形にして `dt` 非依存にする
- `v *= 0.99` は 1,604 フレームで実用上ゼロ、**8,920 フレームで非正規化域**。約 2 分の開き
- **明示的な `min_speed` クランプなら、非正規化域には到達しない**
- **FTZ は性能の保険であって設計ではない。** ゼロになるタイミングを FTZ に決めさせない

### 落とし穴と練習問題

**落とし穴 1：位置を先に積分する。**　前進オイラーになり、振動する系で発散する。

**落とし穴 2：`dt` に実時間をそのまま渡す。**　フレームレートで挙動が変わる。デバッガ復帰で固まる。

**落とし穴 3：重心が原点にない形状をそのまま使う。**　回転の中心がずれ、押すと勝手に回る。

**落とし穴 4：慣性モーメントをゼロのままにする。**　`inv_inertia` が無限大になり、少し触っただけで高速回転する。

**落とし穴 5：減衰を `v *= 0.99` と直接書く。**　`dt` 依存になる。120 fps で 2 倍速く減る。

**落とし穴 6：描画で物理の位置をそのまま使う。**　高リフレッシュレートでカクつく。補間する。

**落とし穴 7：角度を `lerp` で補間する。**　π をまたぐときに逆回りする。`std::remainder` で差を畳む。

**落とし穴 8：キネマティック剛体の位置を直接書き換える。**　摩擦が効かず、上の物体が置いていかれる。スイープも働かない。
