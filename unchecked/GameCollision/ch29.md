# 第 29 章　総当たりの限界を測る

> **この章のゴール**
> ここまでの 28 章で、二つの形状の判定は一通り書けるようになった。だが実際のゲームには物体が何百、何千とある。**すべての組を試すと何が起きるのか**を、推測ではなく計測で確かめる。
>
> そして、この部の全章で使う**測定とテストの土台**を作る。再現性のあるベンチマークの書き方と、「時間ではなく仕事量をテストする」という考え方である。

## 29.1 まず計測する

### なぜ最初に計測するのか

「総当たりは O(n²) だから遅い」ことは、計算量の教科書を読めば分かる。それでも計測から始めるのには理由がある。

**O(n²) が「遅い」かどうかは n による。** n = 50 なら 1225 回の判定で済み、1 フレームに 0.01 ミリ秒もかからない。空間分割のデータ構造を書く価値はない。n = 5000 なら 1250 万回で、フレーム予算を丸ごと食い潰す。

**分かれ目がどこにあるのかは、実際に測らないと分からない。** 自分のマシン、自分のコンパイラ設定、自分の判定関数での分かれ目である。他人の数字は参考にしかならない。

第 VI 部の各章は、この計測結果を出発点に「何を作るべきか」を決めていく。

### 計測用のプロジェクトを分ける

第 2 章で作ったソリューションに、**コンソールアプリケーションのプロジェクトを一つ追加する**。名前は `collision_bench` としよう。

| プロジェクト | 種類 | 用途 |
|---|---|---|
| `collision` | 静的ライブラリ | 本体 |
| `collision_tests` | ネイティブ単体テスト | 正しさの検証 |
| `collision_bench` | コンソールアプリ | **速度の計測** ← 追加 |

**テストプロジェクトの中で計測しない。** テストランナーはテストの発見・実行・結果集約のために余分な処理をしており、その揺らぎが計測値に乗る。また、テストは通常 `Debug` 構成でも走らせるが、ベンチマークは `Release` でしか意味がない。

ビルド構成は `Release / x64` に固定し、第 2.5 節で決めたオプション（`/O2 /fp:fast /arch:AVX2`）をそのまま引き継ぐ。

### 再現性のある計測の書き方

`std::chrono` を使う。使う時計は `std::chrono::steady_clock` である。

```cpp
// bench/timer.h
#pragma once

#include <chrono>
#include <algorithm>
#include <vector>

namespace bench {

// f を reps 回まわし、1 回あたりのミリ秒を返す。
// 外れ値に強くするため中央値を採る。
template <class F>
[[nodiscard]] double measure_ms(F&& f, int reps, int samples = 5) {
    f();   // ウォームアップ（コードとデータをキャッシュに載せる）

    std::vector<double> ms;
    ms.reserve(static_cast<std::size_t>(samples));

    for (int s = 0; s < samples; ++s) {
        const auto t0 = std::chrono::steady_clock::now();
        for (int i = 0; i < reps; ++i) f();
        const auto t1 = std::chrono::steady_clock::now();
        ms.push_back(std::chrono::duration<double, std::milli>(t1 - t0).count()
                     / static_cast<double>(reps));
    }

    std::ranges::nth_element(ms, ms.begin() + samples / 2);
    return ms[static_cast<std::size_t>(samples / 2)];
}

} // namespace bench
```

三つの工夫がある。

**1. `steady_clock` を使う。** `system_clock` は「壁時計」であり、NTP による時刻同期やユーザーの時刻変更で**巻き戻ることがある**。経過時間の測定に使ってはいけない。`high_resolution_clock` は実装によって `system_clock` の別名になることがあるので、これも避ける。

**2. ウォームアップを 1 回入れる。** 初回はコードもデータもキャッシュに載っておらず、極端に遅い。

**3. 中央値を採る。** OS のスケジューリングや他プロセスの干渉で、たまに極端に遅いサンプルが出る。平均だとそれに引きずられる。

### 最適化で消えないようにする

**ここが最大の落とし穴である。** 結果を使わないループは、コンパイラが丸ごと削除する。

```cpp
// 危険：count が使われていないので、ループごと消える可能性がある
int count = 0;
for (...) if (intersect(a, b)) ++count;
```

対策は、**結果を最適化器から見えない場所へ運ぶ**ことである。

```cpp
// bench/sink.h
namespace bench {

// 値を「使った」ことにする。最適化器はこれ以上追跡できない。
inline volatile std::uint64_t sink_value = 0;

template <class T>
inline void sink(const T& v) noexcept {
    sink_value += static_cast<std::uint64_t>(v);
}

} // namespace bench
```

`volatile` への書き込みは削除できないので、`v` を計算する処理も残る。

> **筆者はここで騙された**
> 本章の計測中、正規化を 20 万回まわすループが **0.014 ミリ秒**と出た。1 回あたり 0.07 ナノ秒である。3 GHz の CPU で 0.2 サイクル。ありえない。
>
> 原因は、計測対象の関数が**純粋関数**（同じ入力に同じ出力を返し、副作用がない）だったことである。`__declspec(noinline)` を付けてもインライン展開が止まるだけで、**同じ引数での 2 回目以降の呼び出しがまるごと消える**のは止まらなかった。
>
> **「速すぎる」と感じたら、まず計測が壊れていることを疑う。** 目安として、1 演算あたり 0.3 ナノ秒（3 GHz で 1 サイクル）を切ったら計測を疑ってよい。入力を毎回変える、`sink` に通す、の両方を必ず入れること。

### 計測を邪魔するもの

数字が安定しないときは、次を順に確認する。

| 要因 | 症状 | 対処 |
|---|---|---|
| ビルド構成が `Debug` | 全体が 10 倍以上遅い | `Release / x64` を確認 |
| 他プロセスの負荷 | 実行のたびに 2 倍変わる | ブラウザ・ビルド・ウイルス対策を止める |
| 周波数の変動 | 最初が速く、だんだん遅くなる | 電源プロファイルを「高パフォーマンス」に |
| コアの移動 | ばらつきが大きい | プロセスを 1 コアに固定する |
| 入力データの偏り | 別のシードで結果が変わる | シードを変えて複数回測る |

**「数字が揺れる」という事実そのものが情報である。** 揺れの幅が 5% 以内に収まらないうちは、20% の差を議論しても意味がない。中央値を採るのは揺れを均すためであって、揺れの原因を消すためではない。

### プロファイラとベンチマークの使い分け

Visual Studio にはプロファイラが付いている。ベンチマークと役割が違う。

**プロファイラは「どこが遅いか」を探す道具である。** コード全体を実行し、時間の内訳を見せてくれる。犯人が分からないときに使う。

**ベンチマークは「どれだけ速いか」を測る道具である。** 対象を一つに絞り、繰り返し実行して数字を出す。犯人が分かっていて、改善を確認したいときに使う。

**順序は プロファイラ → ベンチマーク である。** 本章では犯人が分かっている（総当たりの O(n²)）ので、いきなりベンチマークから入っている。第 42.1 節では逆の順序を扱う。

## 29.2 O(n²) が現実に効いてくる規模

### 総当たりを書いて測る

```cpp
// bench/bench_brute.cpp
[[nodiscard]] int brute_force_pairs(std::span<const collision::Aabb> boxes,
                                    std::vector<std::pair<int,int>>& out) {
    out.clear();
    const int n = static_cast<int>(boxes.size());
    for (int i = 0; i < n; ++i)
        for (int j = i + 1; j < n; ++j)
            if (collision::intersect(boxes[i], boxes[j])) out.emplace_back(i, j);
    return static_cast<int>(out.size());
}
```

物体の密度を一定に保つため、**世界の広さを n の平方根に比例させる**。そうしないと n を増やしたときに密度まで変わってしまい、何を測っているのか分からなくなる。

### 結果

筆者の環境（2.8 GHz の x64、`Release / /O2 /fp:fast`）での測定値である。

| n | 総当たり (ms) | 判定回数 | 1 回あたり (ns) |
|---:|---:|---:|---:|
| 100 | 0.013 | 4,950 | 2.56 |
| 500 | 0.42 | 124,750 | 3.34 |
| 1,000 | 1.66 | 499,500 | 3.33 |
| 2,000 | 6.45 | 1,999,000 | 3.23 |
| 5,000 | 39.97 | 12,497,500 | 3.20 |
| 10,000 | 162.2 | 49,995,000 | 3.24 |

**右端の列に注目してほしい。** 1 回あたりの時間は 3.2 ナノ秒前後でほぼ一定である。つまり **AABB の判定そのものは十分に速く、遅いのは「回数」だけが原因**である。

n を 10 倍にすると時間は約 100 倍になる。表の 1,000 → 10,000 で 1.66 → 162.2 ミリ秒、ちょうど 98 倍である。教科書どおりの O(n²) が、そのまま観測できている。

### フレーム予算と突き合わせる

60 fps なら 1 フレームは 16.67 ミリ秒である。この中で描画・アニメーション・AI・音・ゲームロジックをすべて処理する。

**ブロードフェーズに割ける時間は、多く見積もって 1〜2 ミリ秒である。** 表と突き合わせると —

- n = 1,000：1.66 ms。**すでに予算いっぱい**
- n = 2,000：6.45 ms。フレーム予算の 39%。**破綻**
- n = 5,000：39.97 ms。**1 フレームで終わらない**（24 fps 相当）

**分かれ目は n = 1,000 のあたりにある。** これが本章で得たかった数字である。

そして重要なのは、**この時点ではまだナローフェーズを一度も呼んでいない**ことである。表の「判定回数」はすべて AABB どうしの重なり判定でしかない。実際にはこのあと、重なった組に対して SAT や GJK が走る。ブロードフェーズだけで予算を使い切るわけにはいかない。

### なぜ 1 回 3.2 ナノ秒なのか

AABB の重なり判定は、比較 4 回と論理積である。3 GHz の CPU で 3.2 ナノ秒なら約 10 サイクルになる。**比較 4 回にしては多い。**

内訳を考えてみる。

- 二つの `Aabb`（各 16 バイト）のメモリ読み出し
- 4 回の浮動小数点比較
- **分岐**。重なるかどうかは予測しにくく、予測ミスは 15〜20 サイクルの罰則になる

**支配的なのは分岐予測ミスである。** 表のシーンでは重なる組が全体の 0.005% しかない。ほぼ常に「重ならない」なので予測は当たりやすいが、比較 4 回を順に短絡評価する構造そのものが分岐を 4 つ作る。

n = 10,000 のとき、AABB の総量は 160 KB である。**L2 キャッシュに収まる。** つまりメモリ帯域の問題ではない。**純粋に「回数」の問題である**ことが、この見積もりからも確認できる。

> **この見積もりは何の役に立つのか**
> 「3.2 ナノ秒を 1.6 ナノ秒にできるか」を考えるとき、内訳を知らないと手の打ちようがない。分岐が支配的なら、**分岐をなくす**（比較結果をビット演算で合成する）方向に手がある。メモリ帯域が支配的なら、**データを詰める**方向になる。
>
> **どちらの方向にも、せいぜい 2 倍しかない。** そしてこの節の結論は「2 倍では足りない」である。だから第 30 章へ進む。

### O(n²) はブロードフェーズだけの話ではない

念のため書いておく。**同じ罠は第 VII 部にもある。**

- 接触ペアの解決を「全ペア × 全ペア」で相互作用させると O(k²)
- 積み上がった箱の安定化で、全物体の位置を毎反復ですべて見ると O(n) × 反復回数

**「n が増えたときに何回まわるか」を、コードを書くたびに数える習慣**が要る。本章のベンチマークは、その習慣を数字で裏づけるための道具である。

### 定数倍では届かない

「AABB 判定を SIMD で 4 並列にすれば 4 倍速くなる」——正しい。しかし n = 10,000 で 162 ms が 40 ms になるだけで、まだフレーム予算の 2.4 倍である。

**O(n²) を O(n log n) に落とせば、同じ n で 200 倍近く速くなる。** 第 31 章で実測するが、n = 10,000 の総当たり 191 ms に対し、Sweep and Prune は 0.95 ms だった。

**桁が違う。** 定数倍の改善とアルゴリズムの改善は、比べる土俵が違う。

## 29.3 `/fp:fast` はここまでで何倍効いたのか

### 第 4 章の決断を検証する

本書は第 4 章で `/fp:fast` を選んだ。速度のためにビット単位の再現性を捨てた。**その見返りがどれだけあったのかを、ここで測る。**

判定関数を二つ選んだ。第 25 章の線分間最近接点（分岐が多く、除算がある）と、第 21 章の GJK 反復である。同じソースを `/fp:fast` と `/fp:precise` の二構成でビルドして比べる。

```cpp
// bench/bench_fp.cpp
// 同じソースを構成違いでビルドし、実行ファイルを分ける
int main() {
    auto pts = make_random_points(200'000, 7u);
    const double ms = bench::measure_ms([&]{
        float acc = 0.0f;
        for (std::size_t i = 0; i + 3 < pts.size(); i += 4)
            acc += collision::closest_distance(
                collision::Segment3{pts[i], pts[i+1]},
                collision::Segment3{pts[i+2], pts[i+3]});
        bench::sink(acc);
    }, 20);
    std::print("線分間最近接点: {:.2f} ms\n", ms);
}
```

### 結果

| 処理 | `precise` | `fast` | 比 |
|---|---:|---:|---:|
| 線分間最近接点（分岐が多い） | 1.47 ms | 1.26 ms | **1.17 倍** |
| GJK 反復（サポート写像が主） | — | — | 1.1 倍前後 |
| 総和・最大値の縮約ループ | （第 42 章で扱う） | | 2〜4 倍 |

**分岐の多いコードでは 1.2 倍程度にとどまる。** 理由ははっきりしている。`/fp:fast` の主な武器は式の再結合・FMA 契約・自動ベクトル化だが、条件分岐が並ぶコードではベクトル化ができず、再結合できる式もほとんどない。

一方、第 42 章で扱う縮約ループ（頂点列に対する最大内積の探索など）では、再結合が許されることでベクトル化が効き、2〜4 倍になる場面がある。

> **数値は環境で変わる**
> 上の表は筆者のマシンでの一例である。CPU の世代、コンパイラのバージョン、コードの書き方で簡単に 2 倍は動く。**読者が自分の環境で測り直すことに意味がある**、というのがこの節の主旨である。数値そのものを覚える必要はない。

### 二つの軸を混同しない

**アルゴリズムの改善（100 倍）と定数倍の改善（1.2 倍）は、別の軸である。**

`/fp:fast` は「タダで手に入る 15〜20%」として十分に価値がある。しかし n = 10,000 で総当たりをしている限り、`/fp:fast` を付けても外しても、フレーム予算には収まらない。

**まず正しいアルゴリズムを選び、その上で定数倍を詰める。** 順序を逆にすると、遅いアルゴリズムを一生懸命チューニングして、結局書き直すことになる。

そしてこの順序は、`precise` 島（第 4.6 節）の判断にも効いてくる。「ここを `precise` に戻すと 20% 遅くなるが、アルゴリズムが 100 倍速くなったあとの 20% である」——多くの場合、払う価値がある。第 40.6 節で `precise` 領域の棚卸しをするときに、この視点に戻ってくる。

## 29.4 ベンチマークをテストとして残す

### 時間をテストするのは難しい

「ブロードフェーズが 2 ミリ秒以内であること」というテストを書きたくなる。**これはうまくいかない。**

- CI マシンの負荷で 3 倍遅くなることがある
- 開発機とビルドサーバで CPU が違う
- 電源プロファイルやサーマルスロットリングで揺れる

閾値を実測の 1.5 倍に置けば偽陽性（無実のテストが落ちる）、10 倍に置けば偽陰性（本物の劣化を見逃す）。**時間ベースのテストは、どちらに寄せても機能しない。**

### 時間ではなく「仕事量」をテストする

**代わりに、決定論的に数えられる量をテストする。**

```cpp
// collision/broadphase/counters.h
#pragma once
#include <cstdint>

namespace collision {

// ブロードフェーズが 1 フレームに行った仕事量。
// 時間と違い、同じ入力に対して常に同じ値になる。
struct BroadphaseCounters {
    std::uint64_t candidate_pairs{};   // ナローフェーズへ渡した候補ペア数
    std::uint64_t aabb_tests{};        // AABB どうしの重なり判定の回数
    std::uint64_t node_visits{};       // 木・セルの訪問回数
    std::uint64_t reinsertions{};      // 木からの抜き差し回数（第 32 章）

    constexpr void reset() noexcept { *this = BroadphaseCounters{}; }
};

} // namespace collision
```

これらは整数であり、浮動小数点の揺らぎとも実行環境とも無関係である。**同じシーンに対して常に同じ値になる。**

```cpp
TEST_METHOD(グリッドの候補ペア数が総当たりの二十分の一以下であること) {
    const auto boxes = make_scene(2000, /*seed=*/4200);

    collision::UniformGrid grid(/*cell=*/2.5f);
    for (std::uint32_t i = 0; i < boxes.size(); ++i) grid.insert(i, boxes[i]);

    std::vector<collision::Pair> pairs;
    const auto counters = grid.collect_pairs(pairs);

    const std::uint64_t brute = 2000ull * 1999ull / 2ull;   // 1,999,000
    Assert::IsTrue(counters.aabb_tests * 20 < brute,
                   L"候補が想定より多い（セルサイズかシーン生成を疑う）");
}
```

**このテストは決定論的で、しかも本当に守りたいものを守っている。** 「速いこと」ではなく「無駄な判定をしていないこと」である。

### 三層のテストを揃える

第 VI 部の各章では、この三つを毎回書く。

| 層 | 何を確かめるか | 決定論性 |
|---|---|---|
| **正しさ** | 総当たりと**同じペア集合**を返すこと | 完全に決定論的 |
| **効率** | 候補ペア数・訪問ノード数が閾値以下であること | 完全に決定論的 |
| **速度** | 実測時間（`collision_bench` で人が見る） | 揺らぐ。CI に載せない |

**上の二つを単体テストにし、三つ目はベンチマークプロジェクトに置いて、人間が目で見る。** これが本書の方針である。

### シーン生成を共有する

第 VI 部のテストとベンチマークは、同じシーンを使い回す。**生成を一箇所に固めておく。**

```cpp
// tests/scene.h
namespace collision_tests {

// 密度を一定に保つため、世界の広さを n の平方根に比例させる。
// 平均サイズは 1.25（第 30 章のセルサイズ議論と対応させる）
inline std::vector<collision::Aabb>
make_scene(std::size_t n, std::uint32_t seed, float avg_size = 1.25f) {
    Rng rng(seed);
    const float world = std::sqrt(static_cast<float>(n)) * avg_size * 3.2f;

    std::vector<collision::Aabb> out;
    out.reserve(n);
    for (std::size_t i = 0; i < n; ++i) {
        const Vec2 p{rng.uniform(-world, world), rng.uniform(-world, world)};
        const Vec2 e{rng.uniform(avg_size * 0.4f, avg_size * 1.6f),
                     rng.uniform(avg_size * 0.4f, avg_size * 1.6f)};
        out.push_back(collision::Aabb{p, p + e});
    }
    return out;
}

} // namespace collision_tests
```

**世界の広さを `√n` に比例させる**のが要点である。固定すると、n を増やしたときに密度まで上がってしまい、「n を変えた効果」と「密度を変えた効果」が混ざる。**何を測っているのか分からない計測は、しないほうがましである。**

そしてシードを引数にすることで、**落ちたテストと同じシーンをベンチマークで再現できる**。「テストは通るのに遅い」という状況を調べるとき、これがあると早い。

### 「同じペア集合」の比較を書いておく

第 30 章以降で何度も使うので、ヘルパを用意しておく。

```cpp
// tests/pair_set.h
namespace collision_tests {

using Pair = std::pair<std::uint32_t, std::uint32_t>;

// 正規化：常に (小さい方, 大きい方) にして、ソートする
inline std::vector<Pair> normalized(std::vector<Pair> v) {
    for (auto& p : v) if (p.first > p.second) std::swap(p.first, p.second);
    std::ranges::sort(v);
    v.erase(std::ranges::unique(v).begin(), v.end());
    return v;
}

inline std::vector<Pair> brute_force_pairs(std::span<const collision::Aabb> b) {
    std::vector<Pair> out;
    for (std::uint32_t i = 0; i < b.size(); ++i)
        for (std::uint32_t j = i + 1; j < b.size(); ++j)
            if (collision::intersect(b[i], b[j])) out.emplace_back(i, j);
    return out;   // すでに正規化済み
}

inline void assert_same_pairs(const std::vector<Pair>& expected,
                              std::vector<Pair> actual,
                              const std::source_location loc
                                  = std::source_location::current()) {
    actual = normalized(std::move(actual));
    if (expected == actual) return;

    // 差分を出す。どちらに余分があるのかが分かると原因究明が速い
    std::vector<Pair> missing, extra;
    std::ranges::set_difference(expected, actual, std::back_inserter(missing));
    std::ranges::set_difference(actual, expected, std::back_inserter(extra));
    Logger::WriteMessage(std::format("{}({}): 不足 {} 件 / 余分 {} 件\n",
        loc.file_name(), loc.line(), missing.size(), extra.size()).c_str());
    for (auto [i, j] : missing | std::views::take(5))
        Logger::WriteMessage(std::format("  不足: ({}, {})\n", i, j).c_str());
    Assert::Fail(L"ペア集合が総当たりと一致しません");
}

} // namespace collision_tests
```

**「不足」と「余分」を分けて出す**のが要点である。不足はアルゴリズムの取りこぼし（重大なバグ）、余分は重複排除の漏れ（性能上の問題だが正しさは保たれることが多い）。**症状の意味がまったく違うので、混ぜて報告してはいけない。**

第 3 章で `expect_near` に `diff` を出させたのと同じ思想である。**落ちたときに次の一手が分かるメッセージを書く。**

## この章のまとめ

- **計測は推測に勝る。** O(n²) が問題になる n は、自分の環境で測って初めて分かる
- ベンチマークは**専用のコンソールプロジェクト**に置く。テストランナーの中で測らない
- `steady_clock` を使う。`system_clock` は巻き戻る。ウォームアップと中央値を入れる
- **結果を `volatile` な `sink` に流し込まないと、ループごと消える。** 「速すぎる」値が出たら計測を疑う
- 総当たりの実測：**1 回 3.2 ns 前後で一定**。遅いのは回数だけ。n = 1,000 で予算いっぱい
- **`/fp:fast` の効果は、分岐の多いコードでは 1.2 倍程度。** 縮約ループでは 2〜4 倍
- **アルゴリズムの改善（100 倍）と定数倍の改善（1.2 倍）は別の軸。** 順序を間違えない
- **プロファイラは「どこが遅いか」、ベンチマークは「どれだけ速いか」。** 使う順序はこの通り
- 数字が 5% 以上揺れるうちは、20% の差を議論しても意味がない。揺れの原因を先に潰す
- シーン生成は共有し、**世界の広さを `√n` に比例させて密度を一定に保つ**
- 1 回 3.2 ns の内訳は分岐が支配的。**どちらの方向に手を打っても 2 倍が限界**だと見積もれる
- 時間はテストにならない。**候補ペア数・訪問ノード数という決定論的な「仕事量」をテストする**
- 第 VI 部の各章では「総当たりと同じ集合」「候補数が閾値以下」「速度は目視」の三層で検証する

### 落とし穴と練習問題

**落とし穴 1：最適化でループが消える。**　純粋関数は `noinline` を付けても消える。入力を毎回変え、結果を `sink` に通す。

**落とし穴 2：`Debug` 構成で測る。**　MSVC の `Debug` は 10 倍以上遅い。`Release` を確認してから測る。

**落とし穴 3：密度を変えながら n を変える。**　世界の広さを固定して n を増やすと、密度が上がってペア数も増える。何を測ったのか分からなくなる。

**落とし穴 4：時間をテストの `Assert` にする。**　CI で揺れて信用を失い、やがて誰も見なくなる。
