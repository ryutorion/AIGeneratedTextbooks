# 第 42 章　性能を詰める

> **この章のゴール**
> 第 29 章で「アルゴリズムの改善（200 倍）と定数倍の改善（1.2 倍）は別の軸」と書いた。**アルゴリズムはもう選び終えている。この章は定数倍の話である。**
>
> `/fp:fast` を選んだ最大の見返りは、実は式の再結合そのものではなく、**それによって自動ベクトル化が可能になること**である。その効果を実測すると、**同じ処理が 15 倍速くなる。** ただし、ただ `/fp:fast` を付けるだけでは 1 倍のままである。**書き方を変えないと効かない。**
>
> そして最後に、`constexpr` 評価に潜む `/fp:fast` 特有の罠を扱う。**コンパイル時と実行時で、同じ式が違う値になる。**

## 42.1 まずプロファイルする

### ベンチマークとは順序が逆

第 29 章では犯人が分かっていたので、いきなりベンチマークから入った。**この章では犯人を探すところから始める。**

Visual Studio の **CPU 使用率**プロファイラを `Release` 構成で走らせる。デバッグ情報（`/Zi`）を付けたまま最適化を有効にしておくと、行単位まで追える。

**見るべきは三つである。**

| 指標 | 意味 | 疑うべきこと |
|---|---|---|
| **包括的（Inclusive）** | 呼び出した先も含めた時間 | どのサブシステムが重いか |
| **排他的（Exclusive）** | その関数自身の時間 | 実際に時間を使っている関数 |
| **呼び出し回数** | — | O(n²) が隠れていないか |

**排他的な時間が上位に来る関数が、最適化の候補である。** 包括的な時間だけ見ると、`World::step` が 100% になって何も分からない。

### 筆者はここでも騙された

本章のベンチマークを書いていて、**AABB の判定 10 万回が 0.004 ミリ秒**と出た。1 回あたり 40 ピコ秒である。

**第 29.1 節で自分が書いた警告に、そのまま引っかかった。** クエリがループ不変だったので、コンパイラが 200 回の呼び出しをまとめて 1 回にしていた。`__attribute__((noinline))` 相当を付けていても、**純粋関数の共通部分式除去は止まらない。**

```cpp
// 悪い：クエリが毎回同じなので、200 回の呼び出しが 1 回に畳まれる
for (int k = 0; k < 200; ++k) r += count_overlaps(boxes, n, query);

// 良い：毎回わずかに変える
for (int k = 0; k < 200; ++k) {
    const Aabb q{query.min + Vec2{k * 0.01f, 0.0f}, query.max + Vec2{k * 0.01f, 0.0f}};
    r += count_overlaps(boxes, n, q);
}
```

**「速すぎる」と感じたら、まず計測を疑う。** 第 29.1 節に書いた原則を、自分で二度目に踏んだ。**この種の間違いは知識では防げない。毎回疑うしかない。**

## 42.2 `/fp:fast` を活かしきる ― 自動ベクトル化

### 実測 ― 4 つの実装を比べる

10 万個の AABB に対して、一つの領域と重なる個数を数える。同じ処理を 4 通りに書いた。

| 実装 | 時間 | 対 AoS |
|---|---:|---:|
| **AoS**（`Aabb` の配列）| 0.702 ms | 1.0 倍 |
| **SoA**（成分ごとの配列、分岐あり）| 0.707 ms | **1.0 倍** |
| **SoA ＋ 分岐なし**（自動ベクトル化）| 0.198 ms | **3.5 倍** |
| **SoA ＋ AVX2 組み込み関数**（8 並列）| 0.046 ms | **15 倍** |

**二行目に注目してほしい。SoA にしただけでは、まったく速くならない。**

「構造体の配列より配列の構造体のほうが速い」という通説は、**この場面では成り立たない。** 4 つの成分をすべて使うので、読み込むデータ量は同じだからである。

**SoA の価値は、それ自体ではなく「ベクトル化を可能にすること」にある。**

### 分岐を消すとベクトル化される

```cpp
// ベクトル化されない：条件分岐がある
for (int i = 0; i < n; ++i)
    if (b.min_x[i] <= q.max_x && q.min_x <= b.max_x[i] &&
        b.min_y[i] <= q.max_y && q.min_y <= b.max_y[i]) ++count;

// ベクトル化される：分岐がなく、比較結果を足し込むだけ
for (int i = 0; i < n; ++i) {
    const bool hit = (b.min_x[i] <= q.max_x) & (q.min_x <= b.max_x[i])
                   & (b.min_y[i] <= q.max_y) & (q.min_y <= b.max_y[i]);
    count += static_cast<int>(hit);
}
```

**`&&` を `&` に変えるのが要点である。** `&&` は短絡評価なので分岐が必要になる。`&` は両辺を必ず評価するので、分岐が消える。

**これで 3.5 倍になった。** ソースの変更は演算子 2 文字ぶんである。

### 再結合が許されるからベクトル化できるループ

**総和や最小値の探索は、`/fp:precise` ではベクトル化できない。**

```cpp
float sum = 0.0f;
for (int i = 0; i < n; ++i) sum += v[i];
```

ベクトル化するには「4 個ずつ足して、最後に 4 つを合算する」形にする必要がある。**これは加算の順序を変えるので、`/fp:precise` では許されない。**

**`/fp:fast` なら許される。** 第 29.3 節で「縮約ループでは 2〜4 倍」と書いたのは、この効果である。

**本書のコードで該当するのは、次のような箇所である。**

- 第 19 章のサポート写像：頂点列に対する**最大内積の探索**
- 第 35.1 節の質量特性：多角形の頂点に対する**面積と慣性の総和**
- 第 31.3 節の分散：中心座標の**総和と二乗和**

### `/Qvec-report` で理由を読む

MSVC は、なぜベクトル化しなかったかを教えてくれる。

```
/Qvec-report:2
```

`Release` 構成のコンパイラオプションに追加すると、ビルド出力に情報が出る。

```
info C5002: ループはベクター化されませんでした。理由 '1200'
info C5001: ループはベクター化されました
```

主な理由コードは次のとおりである。

| コード | 意味 | 対処 |
|---|---|---|
| 1200 | ループ本体に依存関係がある | 依存を切る、添字を見直す |
| 1105 | 関数呼び出しがある | インライン化を促す、自前で書く |
| 1106 | 制御フローが複雑 | **分岐を `&` に置き換える** |
| 500 | ループが最適化で消えた | 計測の間違い（42.1 節） |
| 501 | 誘導変数が単純でない | 添字の計算を単純にする |

**1106 が出たら 42.2 節の書き換えを試す。** 本章の実測でも、`&&` → `&` の変更でこの理由が消えた。

### `precise` 領域がベクトル化を阻害していないか

**第 40.6 節で棚卸しした 4 箇所は、いずれも収束判定であり、ループの中ではない。** だからベクトル化を妨げていない。

**確認は `/Qvec-report` で行う。** `precise` 領域を含むループが 1105（関数呼び出し）で弾かれていたら、`__declspec(noinline)` の位置を見直す価値がある。

**本書では該当がなかったが、これは設計の結果である。** 収束判定を「反復あたり 1 回」の位置に置いたので、内側のループには入っていない。

## 42.3 非正規化数を出さない設計

### FTZ/DAZ は保険、設計での回避が本筋

第 5 章で FTZ/DAZ を有効にした。**それは「非正規化数が発生しても性能が落ちない」ようにする保険である。**

**本筋は、そもそも非正規化数を作らないことである。** 理由は三つある。

1. **MXCSR はスレッドローカルで、外部が書き換えうる**（第 41.5 節）
2. FTZ でゼロになるタイミングが**仕様として決まらない**（第 35.5 節）
3. **非正規化数が出ること自体が、たいてい設計の綻びを示している**

### 手 1：演算の入口でクランプする

```cpp
// 第 5.9 節の閾値。非正規化域（1.18e-38）から 30 桁離れている
if (length_squared(v) < min_length2) return std::nullopt;
```

**本書の `try_normalize` が最初からこの形なのは、この理由による。** 極小のベクトルを正規化しようとすると、二乗の時点で非正規化域に入る。

**「小さすぎる値は、演算に入れる前に落とす」**——これが最も安く確実な方法である。

### 手 2：スケールを正規化する

**座標が原点から遠いと、差の計算で桁落ちする。**

```
座標 100,000 の 2 点の差を取ると、有効桁が 5 桁失われる
```

**対策は、計算を原点近傍で行うことである。**

```cpp
// 悪い：ワールド座標のまま判定する
const auto m = collide(shape_a, world_transform_a, shape_b, world_transform_b);

// 良い：A の位置を原点として相対座標で計算し、最後に戻す
const Vec2 origin = world_transform_a.position;
const auto m = collide(shape_a, local(world_transform_a, origin),
                       shape_b, local(world_transform_b, origin));
```

**二つの物体が接触しているなら、その距離は必ず小さい。** 原点を片方に移せば、扱う数値がすべて「物体のサイズ程度」に収まる。

**これは非正規化数の対策であると同時に、桁落ちの対策でもある。** 広い世界を扱うゲーム（オープンワールド）では必須の設計になる。

### 手 3：単位系を見直す

**極端に小さい値を扱っているなら、単位が合っていない可能性がある。**

第 5.9 節で「1 単位 = 1 メートル」と決めた。**もし扱う物体が 0.1 mm 単位なら、1 単位 = 1 ミリメートルに変えるべきである。** そうすれば閾値も含めて全部が 1000 倍され、非正規化域から遠ざかる。

**単位の選択は、精度の設計そのものである。**

### 発生を監視する

第 41.5 節の `denormal_occurred()` をフレームごとに見る。

```cpp
if (debug::denormal_occurred()) ++counters_.denormal_frames;
```

**`denormal_frames` がゼロなら、FTZ を外しても性能は変わらない。** つまり設計での回避が成功している。**ゼロでないなら、どこで生まれているかを調べる価値がある。**

## 42.4 データ配置 ― AoS から SoA へ

### いつ SoA にするか

42.2 節の実測が示すとおり、**「全部の成分を使う処理」では SoA にしても速くならない。**

**SoA が効くのは次の場合である。**

| 条件 | 理由 |
|---|---|
| **一部の成分しか使わない** | 使わない成分をキャッシュに載せずに済む |
| **ベクトル化したい** | 連続した同じ成分を一度に読める |
| 要素数が非常に多い | 帯域が支配的になる |

**第 31 章の Sweep and Prune が、一つ目の典型である。** 掃引の内側ループでは `min.x` しか読まない。

```cpp
// AoS：min.x を読むために 16 バイトのキャッシュラインを消費する
if (axis_min(boxes_[order_[m]], 0) > i_max) break;

// SoA：min.x だけの配列を持てば、同じキャッシュラインに 16 個入る
if (min_x_[order_[m]] > i_max) break;
```

**「打ち切りまで何個読むか」がそのままキャッシュミスの回数になる**ので、ここは効く。

### `std::mdspan` を使う場面

C++23 の `std::mdspan` は、**連続したメモリに多次元の見方を与える**道具である。所有せず、参照するだけである。

```cpp
#include <mdspan>

// n 個の AABB を、成分ごとの 4 行 × n 列として見る
std::vector<float> storage(4 * n);
std::mdspan<float, std::extents<std::size_t, 4, std::dynamic_extent>>
    boxes(storage.data(), 4, n);

// C++23 の多次元添字。boxes[0, i] が min_x[i]
for (std::size_t i = 0; i < n; ++i)
    if (boxes[0, i] <= q.max_x && q.min_x <= boxes[2, i]) ++count;
```

**利点は「レイアウトを型で表現できる」ことである。** `layout_left` と `layout_right` を差し替えるだけで、AoS と SoA を切り替えられる。

**注意点は、コンパイラがまだ完全には最適化しきれない場合があることである。** 生ポインタ版と `mdspan` 版を両方書いて測り、差が出ないことを確認してから採用する。

**本書のコードでは採用していない。** 4 成分固定なら、`std::array<std::vector<float>, 4>` のほうが素直で速い。**`mdspan` は次元数が可変・大きいときに真価が出る。**

## 42.5 分岐削減と早期脱出の設計

### 早期脱出は「当たらない」ほうが多いときに効く

```cpp
// AABB 判定。最初の比較で 9 割落ちるなら、これが最速
if (a.max.x < b.min.x) return false;
if (b.max.x < a.min.x) return false;
if (a.max.y < b.min.y) return false;
return b.max.y >= a.min.y;
```

**分岐予測が当たるなら、早期脱出は非常に速い。** 第 29.2 節で測った 3.2 ns は、この形での値である。

**逆に、予測が当たらない（半々で分かれる）なら、分岐は高くつく。** 予測ミスは 15〜20 サイクルである。

**判断基準：ヒット率が極端（1% 未満か 99% 超）なら分岐、半々なら分岐なし。**

### 分岐をなくす書き方

```cpp
// 分岐あり
const float d = (a > b) ? a : b;

// 分岐なし（コンパイラが maxss 命令にする）
const float d = std::max(a, b);
```

**`std::max` / `std::min` / `std::clamp` は、たいてい分岐なしの命令になる。** 自分で三項演算子を書くより、まず標準のものを使う。

**`/fp:fast` では `std::max` の `NaN` の扱いが変わりうる**ことに注意する。本書は「`NaN` は入らない」を契約にしている（第 43.3 節）ので問題にならない。

### ソートして分岐予測を助ける

第 33.1 節で触れた手である。**同じ種類の処理が連続すれば、分岐予測が当たる。**

```cpp
// 形状の組でソートしてから処理すると、std::visit の分岐が予測しやすくなる
std::ranges::sort(pairs, {}, [&](const Pair& p) {
    return shape_type_pair_key(body(p.first).shape, body(p.second).shape);
});
```

**ソートのコストと、予測ミスの削減が釣り合うかは実測でしか分からない。** 接触が数十個なら割に合わず、数千個なら効いてくる。

## 42.6 `constexpr` 評価と `/fp:fast` の罠

### コンパイル時と実行時で値が違う

**これは `/fp:fast` に特有の、そして最も見落とされやすい罠である。**

**定数式の評価は、必ず「抽象機械の意味論」に従う。** つまり `/fp:fast` の再結合も `rsqrt` 近似も適用されない。**`constexpr` 評価は常に `precise` 相当である。**

一方、同じ式が実行時に評価されると `/fp:fast` の変換を受ける。**同じソースが、評価される場所によって違う値になる。**

```cpp
constexpr float inv_len(float x, float y) { return 1.0f / std::sqrt(x * x + y * y); }

constexpr float compile_time = inv_len(3.0f, 4.0f);   // 常に厳密に 0.2
float run_time = inv_len(a, b);                        // rsqrt 近似が入りうる
```

**実測してみた。** 20 万点について、実行時の値とコンパイル時相当の値をビット比較した。

| ビルド | ビット不一致 | 最大相対差 |
|---|---:|---:|
| `precise` 相当 | 51,047 / 200,000 | 1.192e−07（丸め 1 ULP ぶん） |
| **`fast` 相当（`rsqrt` 近似）** | **76,043 / 200,000** | **2.574e−07** |

**`fast` では 38% の入力でビットが違い、相対差は 2 ULP 程度になる。** 値としては十分に近いが、**ビット一致を期待するコードは壊れる。**

### 何が問題になるか

```cpp
// 危険：コンパイル時に畳まれるか、実行時に計算されるかで結果が変わる
constexpr float threshold = compute_threshold(scale);
if (measured == threshold) { /* ... */ }     // ビット一致を期待している
```

**そもそも浮動小数点の等号比較をしないので**（第 3.5 節）、本書のコードでは実害が出ない。**だが「定数畳み込みを期待した最適化」を書くと、そこで食い違う。**

### 対処

**対処 1：畳み込まれることを前提にしない。** 定数として書いたものが、実行時に計算されても同じ意味を持つように書く。

**対処 2：`if consteval` で意図的に分ける。**

```cpp
[[nodiscard]] constexpr float fast_inv_sqrt(float x) noexcept {
    if consteval {
        return 1.0f / std::sqrt(x);       // コンパイル時は素直に
    } else {
        return runtime_rsqrt(x);           // 実行時は近似で速く
    }
}
```

**C++23 の `if consteval` は、この使い分けをそのまま書ける。** 「コンパイル時は正確に、実行時は速く」という設計が明示される。

**対処 3：`static_assert` の許容誤差を緩める。**

```cpp
// 厳密比較は避ける。constexpr でも許容誤差で書く
static_assert(std::fabs(inv_len(3.0f, 4.0f) - 0.2f) < 1.0e-6f);
```

**第 3.5 節の「ビット一致を要求しない」という原則は、コンパイル時にも適用される。**

## 42.7 SIMD 組み込み関数の入り口

### 4 つの AABB を同時に判定する

自動ベクトル化で 3.5 倍、**手で書けば 15 倍**だった（42.2 節）。差は、コンパイラが安全側に倒す部分にある。

```cpp
#include <immintrin.h>

// 8 個の AABB を一度に判定し、重なった個数を返す（AVX2、SoA 前提）
[[nodiscard]] int count_overlaps_avx2(const BoxSoA& b, int n, Aabb q) noexcept {
    const __m256 qmaxx = _mm256_set1_ps(q.max.x), qminx = _mm256_set1_ps(q.min.x);
    const __m256 qmaxy = _mm256_set1_ps(q.max.y), qminy = _mm256_set1_ps(q.min.y);

    int count = 0, i = 0;
    for (; i + 8 <= n; i += 8) {
        const __m256 bminx = _mm256_loadu_ps(&b.min_x[i]);
        const __m256 bmaxx = _mm256_loadu_ps(&b.max_x[i]);
        const __m256 bminy = _mm256_loadu_ps(&b.min_y[i]);
        const __m256 bmaxy = _mm256_loadu_ps(&b.max_y[i]);

        const __m256 m = _mm256_and_ps(
            _mm256_and_ps(_mm256_cmp_ps(bminx, qmaxx, _CMP_LE_OQ),
                          _mm256_cmp_ps(qminx, bmaxx, _CMP_LE_OQ)),
            _mm256_and_ps(_mm256_cmp_ps(bminy, qmaxy, _CMP_LE_OQ),
                          _mm256_cmp_ps(qminy, bmaxy, _CMP_LE_OQ)));

        count += std::popcount(static_cast<unsigned>(_mm256_movemask_ps(m)));
    }
    for (; i < n; ++i)   // 端数はスカラーで処理する
        if (overlaps_scalar(b, i, q)) ++count;
    return count;
}
```

**`_mm256_movemask_ps` で 8 個の比較結果を 8 ビットの整数にし、`std::popcount`（C++20）で数える。** ループの中に分岐がまったくない。

### 組み込み関数は `/fp:fast` の影響を受けない

**これが重要な性質である。** 組み込み関数は特定の CPU 命令に一対一で対応するので、**コンパイラが再結合したり `rsqrt` に置き換えたりしない。**

つまり、**組み込み関数で書いた部分だけは、精度を自分で決められる。**

| | コンパイラ任せ | 組み込み関数 |
|---|---|---|
| 演算順序 | `/fp:fast` が決める | **自分が決める** |
| `rsqrt` 近似 | `/fp:fast` が決める | **自分が決める**（`_mm_rsqrt_ps` を呼ぶかどうか） |
| 移植性 | 高い | **低い**（命令セットに依存） |
| 保守コスト | 低い | **高い** |

**「精度が要るがベクトル化したい」という場面では、組み込み関数が唯一の選択肢になる。** ただし保守コストは高い。

### どこに使うか

**本書の実装で、組み込み関数を書く価値があるのは 1 箇所だけである。ブロードフェーズの一括 AABB 判定**（第 30〜32 章）である。

理由は三つある。

1. **呼び出し回数が桁違いに多い**（n = 10,000 で数万回／フレーム）
2. **処理が単純で、分岐がない**
3. **SoA にする自然な理由がある**

**ナローフェーズ（GJK、SAT、EPA）は分岐だらけなので、組み込み関数にしても速くならない。** 第 29.3 節で `/fp:fast` の効果が 1.2 倍にとどまったのと同じ理由である。

**「まず測る、次に絞る」**——組み込み関数は最後の手段であり、絞り込んだ 1 箇所にだけ使う。

## 42.8 マルチスレッド化の検討ポイント

### 並列化しやすいところ、しにくいところ

| 処理 | 並列化 | 理由 |
|---|---|---|
| AABB の更新 | **容易** | 物体ごとに独立 |
| ブロードフェーズのクエリ | **容易** | 読み取りのみ |
| ナローフェーズ | **容易** | ペアごとに独立（書き込み先が別） |
| **ソルバ** | **困難** | Gauss-Seidel は逐次性が本質 |
| 積分 | 容易 | 物体ごとに独立 |

**ナローフェーズまでは素直に並列化できる。** ペアごとに独立で、結果を別々の場所に書けばよい。

**ソルバが壁である。** 第 37.1 節の逐次力積法は「一つ解いた結果を次に反映する」ことで速く収束する。**並列にすると Jacobi に近づき、収束が悪化する**（第 34.2 節で見たトレードオフそのものである）。

### 並列リダクションの順序と再現性

**総和を並列に取ると、加算の順序がスレッド数と実行タイミングで変わる。**

```cpp
// 危険：結果が実行のたびに変わりうる
float total = std::transform_reduce(std::execution::par, v.begin(), v.end(), 0.0f, ...);
```

**第 41.3 節の再現性が、ここで崩れる。** 「同一実行ファイル・同一マシンなら再現する」という保証すら失われる。

**対策は「固定した分割で部分和を取り、決まった順序で合算する」ことである。**

```cpp
// スレッド数によらず、常に同じ分割・同じ順序で合算する
constexpr int chunk_count = 8;                  // ★ スレッド数ではなく固定値
std::array<float, chunk_count> partial{};
parallel_for(0, chunk_count, [&](int c) {
    partial[c] = sum_range(v, c * n / chunk_count, (c + 1) * n / chunk_count);
});
float total = 0.0f;
for (const float p : partial) total += p;       // 常に同じ順序
```

**分割数をスレッド数ではなく固定値にする**のが要点である。実行環境が変わっても結果が変わらない。

### MXCSR は全スレッドに設定する

**第 5.6 節で述べたとおり、MXCSR はスレッドローカルである。** ワーカースレッドで FTZ/DAZ を設定し忘れると、**そのスレッドだけ非正規化数で遅くなる。**

```cpp
// スレッドプールの起動ラッパで必ず通す（第 41.5 節の RAII ガード）
void worker_main() {
    FloatEnvironmentGuard guard;    // このスレッドでも FTZ/DAZ を有効にする
    run_jobs();
}
```

**症状は「ジョブスレッドだけ遅い」である。** 原因を知らないと、まず疑わない場所である。

- プロファイラで犯人を探し、ベンチマークで改善を測る。**順序は第 29 章と逆**

- SoA が効くのは**一部の成分しか使わないとき**（第 31 章の SAP の内側ループ）

- 早期脱出はヒット率が極端なとき。**半々なら分岐なしに書く**

- 並列リダクションは**分割数を固定して、決まった順序で合算する**
