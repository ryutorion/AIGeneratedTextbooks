## 4.1 `float` の刻み幅 ― ULP という考え方

### `float` は数直線ではない

`float` は 32 ビットで実数を表す。内訳は符号 1 ビット、指数 8 ビット、仮数 23 ビットである。

ここから導かれる最も重要な帰結は、**`float` で表せる値は等間隔ではない**ということである。指数部が値の桁を、仮数部が桁の中での位置を表すので、値が 2 倍になるたびに刻み幅も 2 倍になる。

隣り合う二つの `float` の差を **ULP**（Unit in the Last Place、最後の桁の単位）と呼ぶ。実際に測ってみよう。`std::nextafter` は「指定した方向にある次の表現可能な値」を返す。

```cpp
#include <cmath>
#include <print>

void print_ulp(float x) {
    const float next = std::nextafter(x, std::numeric_limits<float>::infinity());
    std::println("{:>12.1f} の ULP = {:.9g}", x, next - x);
}

int main() {
    for (float x : {1.0f, 10.0f, 100.0f, 1000.0f, 10000.0f, 100000.0f, 1000000.0f}) {
        print_ulp(x);
    }
}
```

結果はおおよそ次のようになる。

| 値 | ULP（刻み幅） | 1 単位 = 1 m とすると |
|---|---|---|
| 1.0 | 1.19e-07 | 0.12 マイクロメートル |
| 10.0 | 9.54e-07 | 0.95 マイクロメートル |
| 100.0 | 7.63e-06 | 7.6 マイクロメートル |
| 1,000.0 | 6.10e-05 | 0.061 ミリメートル |
| 10,000.0 | 9.77e-04 | 0.98 ミリメートル |
| 100,000.0 | 7.81e-03 | 7.8 ミリメートル |
| 1,000,000.0 | 6.25e-02 | 6.3 センチメートル |

この表は本書を通じて参照することになる。読み取れることが二つある。

**原点付近では十分すぎる精度がある。** 1 メートル付近で 0.12 マイクロメートル刻み。人間の目には見えない。

**遠方では急速に粗くなる。** 原点から 100 km 離れた場所では、位置の刻み幅が 8 ミリメートルになる。オブジェクトが 8 mm 単位でしか置けない世界である。これは目に見える。オープンワールドのゲームで、遠くの物体が細かく震える現象が起きるのはこのためである（対処は座標系を分割することだが、本書の範囲外）。

### `float` の相対精度は一定

刻み幅は絶対値としては変わるが、**値に対する比率としてはほぼ一定**である。上の表で「ULP ÷ 値」を計算すると、どれも約 `1.2e-7` になる。

これが `float` の本質である。`float` は「絶対的な精度」ではなく「相対的な精度」を持つ。有効数字でいえば約 7 桁。この 7 桁がどの桁に位置するかは、値の大きさによって動く。

この性質が、前章で許容誤差を絶対誤差と相対誤差の併用にした理由である。相対誤差の側が、この「相対精度が一定」という性質に対応している。

### 機械イプシロン

`std::numeric_limits<float>::epsilon()` は `1.0f` の ULP、すなわち約 `1.19e-7` を返す。これを **機械イプシロン** と呼ぶ。

紛らわしいので注意してほしいのだが、**機械イプシロンをそのまま許容誤差に使うのは、ほぼ常に間違いである**。

```cpp
// これは意味をなさない
if (std::fabs(a - b) < std::numeric_limits<float>::epsilon()) { ... }
```

機械イプシロンは「1.0 付近での 1 ULP」でしかない。値が 100 なら 1 ULP は `7.6e-6` なので、この条件は「完全に一致する場合のみ」とほぼ同義になる。逆に値が 0.001 なら、`1.19e-7` は 1000 ULP 以上に相当し、緩すぎる。

許容誤差は、機械イプシロンからではなく、**扱う問題の単位系から決める**。次節でそれをやる。

## 4.2 「等しい」を判定してはいけない

### 誤差はどこから来るか

浮動小数点の誤差には、大きく二つの起源がある。

**表現誤差。** `0.1` は二進数で無限小数になるので、`float` で正確に表せない。`0.1f` の実際の値は `0.100000001490116119384765625` である。リテラルを書いた瞬間から誤差がある。

**丸め誤差。** 演算の結果が表現可能な値の間に落ちたとき、最も近い値へ丸められる。1 回の演算で最大 0.5 ULP の誤差が入る。演算を重ねるとこれが蓄積する。

前章で見た「`0.1f` を 10 回足すと `1.0f` にならない」は、両方が効いた結果である。

### 桁落ち（キャンセル）

誤差の中でも特に厄介なのが**桁落ち**である。**近い値どうしを引き算すると、有効桁数が激減する**。

例を見よう。

```cpp
float a = 1000.0001f;
float b = 1000.0000f;
std::println("{:.9g}", a - b);   // 0.000122070313 と出る
```

期待するのは `0.0001` だが、出てくるのは `0.000122...` である。相対誤差は 22% にもなる。

理由は明快で、1000 付近の `float` は `6.1e-5` 刻みでしか値を持てないからである。`1000.0001f` として書いた値は、実際には `1000.00012207...` に丸められている。この時点で `0.0001` という差の情報の大半が失われている。引き算はその失われた情報を復元できない。

**コリジョンのコードは桁落ちの温床である。** 座標どうしの引き算はいたるところに出てくる。二つの物体が近づくほど、その差の精度は落ちる。

対処の原則は、**引き算を後回しにする**、または**引き算そのものを避ける形に式を変形する**ことである。具体例は各章で扱うが、代表的なものを一つ挙げておく。

```cpp
// 距離を求めてから引く（桁落ちしやすい）
float d = std::sqrt(dx*dx + dy*dy);
bool hit = (d < r1 + r2);

// 二乗のまま比較する（引き算も平方根も不要）
float d2 = dx*dx + dy*dy;
float r  = r1 + r2;
bool hit = (d2 < r*r);
```

後者は速いだけでなく、数値的にも素直である。第 8 章で円と円の判定を書くときに、この形が出てくる。

### 三つの比較の書き方

浮動小数点の比較には、状況に応じた三つの書き方がある。

**1. 絶対誤差での比較。** ゼロ近傍で使う。

```cpp
if (std::fabs(x) < abs_tol) { /* x はゼロとみなす */ }
```

**2. 相対誤差での比較。** 大きな値どうしで使う。

```cpp
if (std::fabs(a - b) < rel_tol * std::max(std::fabs(a), std::fabs(b))) { ... }
```

**3. ULP での比較。** 「何 ULP 以内か」で判定する。ビットパターンを整数として引き算すれば求まる。

```cpp
[[nodiscard]] inline std::int32_t ulp_distance(float a, float b) noexcept {
    // 符号が違う場合はこの方法では測れない（ゼロをまたぐため）
    if (std::signbit(a) != std::signbit(b)) {
        return std::numeric_limits<std::int32_t>::max();
    }
    const auto ia = std::bit_cast<std::int32_t>(a);
    const auto ib = std::bit_cast<std::int32_t>(b);
    return ia > ib ? ia - ib : ib - ia;
}
```

`std::bit_cast` は C++20 の機能で、ビットパターンを保ったまま型を読み替える。IEEE 754 の巧妙な設計により、**同符号の `float` はビットパターンを整数として見ても大小関係が保たれる**ので、整数の差がそのまま「何個離れているか」になる。

ULP 比較は理論的には最も筋がよい。ただし本書では主に前二者を使う。理由は、**ゼロ近傍で使えない**（`0.0f` と `1e-40f` は ULP 距離が巨大になる）ことと、`/fp:fast` の下では最適化によって数 ULP のずれが日常的に発生し、閾値を決めにくいことである。ULP は診断の道具として使う。

## 4.3 スケール相対の許容誤差を設計する

### 単位系から逆算する

第 1 章で「1 単位 = 1 メートル」と決めた。ここから許容誤差を導く。

**問い：位置の誤差が何メートルまでなら、ゲームとして許容できるか。**

現実的な答えは 1 ミリメートル程度である。キャラクターが壁から 1 mm 浮いていても、1 mm めり込んでいても、誰も気づかない。むしろ、それより厳しくしようとすると物体が震え始める（第 34 章）。

一方、テストで検証するときは、実装が正しければ本来もっと近い値になるはずである。テストの許容誤差を「ゲームとして許容できる誤差」まで緩めると、バグを見逃す。

そこで本書では、二つの水準を使い分ける。

| 用途 | 絶対誤差 | 意味 |
|---|---|---|
| **テストの検証** | `1e-6f` | 1 マイクロメートル。実装が正しければこの精度で合うはず |
| **アルゴリズム内部の判定** | `1e-4f` 〜 `1e-3f` | 0.1〜1 ミリメートル。ゲームとして無視してよい差 |

前章の `default_abs_tol = 1.0e-6f` は前者である。「1 メートル付近で 1 ULP が 0.12 マイクロメートル」なので、`1e-6` はおよそ 8 ULP に相当する。数回の演算による丸め誤差は吸収でき、しかし実際のバグは見逃さない、という水準である。

### 相対誤差の値

`default_rel_tol = 1.0e-5f` はどう決めたか。

`float` の相対精度は約 `1.2e-7` である。これは 1 回の演算での話であって、複数の演算を重ねれば誤差は増える。コリジョンの計算は、内積・平方根・除算などが 10 回程度連なることが多い。誤差が単純に加算されるとして 10 倍、`/fp:fast` による順序入れ替えの影響を見込んでさらに数倍。安全側に見て **100 倍程度**を許容範囲とし、`1.2e-7 × 100 ≒ 1.2e-5`、丸めて `1e-5` とした。

この見積もりに厳密な根拠はない。**重要なのは、数値を天下り的に決めないこと**である。テストが落ちたときに「なぜこの値なのか」を説明できれば、緩めてよいのか、それともバグなのかを判断できる。

第 40 章では、本書で使ったすべての許容誤差を一覧表にして棚卸しする。そのとき、この節の議論が根拠として参照される。

### スケールに応じた許容誤差ヘルパ

座標の大きさが分かっている文脈では、そこから許容誤差を作るヘルパが便利である。

```cpp
// 「この世界のスケール」から許容誤差を作る
[[nodiscard]] constexpr float tolerance_for(float scale) noexcept {
    return std::max(default_abs_tol, default_rel_tol * std::fabs(scale));
}
```

原点から 1000 離れた場所で判定するなら `tolerance_for(1000.0f)` は `1e-2` になる。これは 1000 付近の ULP（`6.1e-5`）の約 160 倍で、妥当な水準である。

## 4.4 `/fp:fast` でコンパイラに許可したこと

### 許可の中身

第 2 章で `/fp:fast` を設定した。コンパイラに何を許可したのかを、ここで具体的に見る。

一言でいえば、**「数学的に等価な変形をしてよい」**という許可である。ここでいう「数学的に等価」は実数の代数における等価であって、浮動小数点演算における等価ではない。この乖離がすべての起点である。

#### 再結合（reassociation）

実数なら `(a + b) + c = a + (b + c)` である。浮動小数点ではそうならない。

```cpp
float a = 1e10f, b = -1e10f, c = 1.0f;
// (a + b) + c = 0 + 1 = 1
// a + (b + c) = 1e10 + (-1e10 + 1) = 1e10 + (-1e10) = 0   ← 1 が消える
```

`/fp:fast` は、コンパイラがこの入れ替えを行うことを許す。総和のループをベクトル化する（複数の部分和を並列に計算して最後に合算する）ためには、この許可が必須である。だから速くなる。同時に、結果は変わりうる。

#### FMA への融合（contraction）

`a * b + c` は、通常なら乗算で 1 回、加算で 1 回、計 2 回丸められる。FMA（Fused Multiply-Add）命令を使うと、乗算の結果を丸めずに加算し、最後に 1 回だけ丸める。

丸めが減るので、**結果はより正確になる**。ところがこれが問題を起こすことがある。

```cpp
// a*b と c が数学的にちょうど等しいとき、差はゼロになってほしい
float d = a * b - c;
```

丸め 2 回なら `a*b` は `c` と同じ値に丸められ、`d` はちょうどゼロになる。FMA だと `a*b` の丸め前の値から `c` を引くので、`d` は微小な非ゼロになる。「正確になったせいで、期待した性質が崩れる」という現象である。第 15 章のレイと円の判定で、判別式がこの影響を受ける。

#### 除算の逆数化

`x / y` を `x * (1 / y)` に置き換えてよい。除算は乗算よりずっと遅いので、特に同じ除数で複数回割る場面で効く。逆数を取る時点で丸めが 1 回増えるため、結果は変わりうる。

さらに `/fp:fast` では、`1 / sqrt(x)` を `vrsqrtps` のような**近似命令**に置き換えることも許される。この命令の精度は 12 ビット程度で、`float` の 24 ビットには遠く及ばない（通常はニュートン法で 1 回補正して精度を上げるが、それでも完全ではない）。正規化を多用するコリジョンのコードでは、この点は意識しておく価値がある（第 6 章）。

#### ゼロと特殊値に関する仮定

`/fp:fast` の下では、次のような仮定が置かれうる。

- `-0.0` と `+0.0` を区別しない
- 引数が `NaN` や `Inf` にならないと仮定してよい
- `x - x` を `0` に、`x * 0` を `0` に畳み込んでよい（`x` が `Inf` や `NaN` なら本来は `NaN`）

最後の項目が特に効く。`x != x` は「`x` が `NaN` のときだけ真」というイディオムだが、コンパイラが「`NaN` は来ない」と仮定すれば、この式は常に偽に畳み込める。**`NaN` 判定が消える。**

### 逆アセンブリで確認する

言葉での説明より、実物を見るほうが早い。前章の練習問題 2-4 で触れた手順を、ここで本格的に使う。

`collision_tests` に次の関数を書く。テストからは呼ばなくてよい。最適化で消えないよう `__declspec(noinline)` を付ける。

```cpp
__declspec(noinline) float fma_check(float a, float b, float c) {
    return a * b + c;
}

__declspec(noinline) float rsqrt_check(float x) {
    return 1.0f / std::sqrt(x);
}

__declspec(noinline) float sum4(float a, float b, float c, float d) {
    return a + b + c + d;
}
```

プロパティ → C/C++ → 出力ファイル → **アセンブリの出力** を「アセンブリ コード (/FA)」にして、**Release 構成で**ビルドする。中間ディレクトリに `.asm` ファイルが生成される。

`fma_check` を探すと、`/fp:fast` かつ `/arch:AVX2` なら次のような命令が現れる。

```
vfmadd213ss xmm0, xmm1, xmm2
```

一命令になっている。`/fp:precise` に切り替えてビルドし直すと、

```
vmulss  xmm0, xmm0, xmm1
vaddss  xmm0, xmm0, xmm2
```

と二命令に分かれる。**これが「許可した」ことの具体的な姿である。**

`rsqrt_check` では `vrsqrtss` 命令とニュートン法の補正らしき乗算・加算の並びが見えるはずである。`/fp:precise` では `vsqrtss` と `vdivss` になる。

> **見るべきものが見つからないとき**
> Debug 構成では最適化されないので違いが出ない。必ず Release で確認すること。また、関数が呼ばれていないと丸ごと削除されることがある。テストから一度呼ぶか、`volatile` 変数に結果を代入しておくとよい。

この作業は一度やっておく価値がある。「コンパイラが式を書き換える」という抽象的な話が、具体的な命令の差として目に見えると、以降の議論が腑に落ちる。

## 4.5 `/fp:fast` で壊れるコードのパターンと書き換え

ここからが実用編である。よくある四つのパターンを挙げる。

### パターン 1：`NaN` 判定が消える

**壊れるコード。**

```cpp
if (x != x) {                    // NaN 判定のイディオム
    return handle_nan();
}
if (std::isnan(x)) {             // これも最適化されうる
    return handle_nan();
}
```

`/fp:fast` は「`NaN` は来ない」と仮定してよいので、これらの条件は常に偽に畳み込まれる可能性がある。実際に畳み込まれるかは最適化の状況次第で、**動くこともあれば動かないこともある**という最も厄介な形の不具合になる。

**書き換え：ビットパターンを直接検査する。**

```cpp
[[nodiscard]] inline bool is_nan_bits(float x) noexcept {
    const auto bits = std::bit_cast<std::uint32_t>(x);
    // 指数部が全 1 かつ仮数部が非ゼロなら NaN
    return (bits & 0x7F800000u) == 0x7F800000u && (bits & 0x007FFFFFu) != 0u;
}

[[nodiscard]] inline bool is_finite_bits(float x) noexcept {
    const auto bits = std::bit_cast<std::uint32_t>(x);
    return (bits & 0x7F800000u) != 0x7F800000u;   // 指数部が全 1 なら Inf か NaN
}
```

`std::bit_cast` を通した後は**整数演算**なので、浮動小数点の最適化の対象外である。コンパイラがどう最適化しても、この判定は消えない。

これらを `collision/math/fp_bits.h` に置き、本書を通じて `NaN` 検査にはこれを使う。

### パターン 2：判別式のわずかな負値で `sqrt` が `NaN` を返す

**壊れるコード。**

```cpp
const float disc = b * b - 4.0f * a * c;
if (disc < 0.0f) return std::nullopt;      // 交差なし
const float t = (-b - std::sqrt(disc)) / (2.0f * a);
```

数学的には `disc` がちょうどゼロになる（接する）ケースで、丸め誤差により `-1e-9` のような微小な負値になることがある。上のコードは `disc < 0` で弾くので一見安全に見えるが、それは「接するケースを取りこぼす」ことを意味する。逆に `disc <= 0` を避ける書き方をしていると `sqrt(負値)` で `NaN` が出る。

FMA が絡むとさらに読みにくくなる。`b*b - 4*a*c` の一部が FMA に融合されると、`disc` の値が丸め回数の違いだけずれる。

**書き換え：クランプする。**

```cpp
float disc = b * b - 4.0f * a * c;
if (disc < -tolerance) return std::nullopt;   // 明確に負なら交差なし
disc = std::max(disc, 0.0f);                  // 微小な負値はゼロへ
const float t = (-b - std::sqrt(disc)) / (2.0f * a);
```

「明確に負」の判定に許容誤差を使い、境界付近はゼロに丸める。これで接するケースを取りこぼさず、`NaN` も出ない。第 15 章のレイ vs 円で、この形が実際に登場する。

**平方根に渡す値は、必ず非負であることを保証してから渡す。** これは本書全体を通じた規則である。

### パターン 3：閾値の両側比較が非対称に壊れる

**壊れるコード。**

```cpp
if (d > 0.0f && d < epsilon) {
    // 「ほぼゼロだが正」の処理
}
```

`d` の計算過程が最適化によって変わると、本来ゼロになるはずの値が `+1e-9` になったり `-1e-9` になったりする。上のコードは正の側だけを拾うので、符号が揺れると挙動が変わる。

**書き換え：絶対値で判定する。**

```cpp
if (std::fabs(d) < epsilon) {
    // 「ほぼゼロ」の処理。符号は別途、必要なら記録しておく
}
```

「ゼロ近傍」を扱うときは、**必ず絶対値で判定する**。片側だけを見る条件は、誤差で符号が反転した瞬間に破綻する。

### パターン 4：`1 / 0` が `Inf` になると期待する

**壊れるコード。**

```cpp
// レイ vs AABB のスラブ法
const float inv_dx = 1.0f / ray.dir.x;   // dir.x == 0 なら Inf を期待
const float t1 = (box.min.x - ray.origin.x) * inv_dx;
```

軸に平行なレイ（`dir.x == 0`）に対して `Inf` が生まれ、後続の比較が正しく働く、というのが IEEE 754 の下でのスラブ法の定石である。`/fp:fast` は特殊値の扱いを保証しないので、この定石が成立しない可能性がある。

**書き換え：分岐で明示的に処理する。**

```cpp
if (std::fabs(ray.dir.x) < epsilon) {
    // 軸に平行：X スラブの内側にいなければ交差しない
    if (ray.origin.x < box.min.x || ray.origin.x > box.max.x) {
        return std::nullopt;
    }
    // 内側なら X 方向の制約はなし。t の区間は変更しない
} else {
    const float inv_dx = 1.0f / ray.dir.x;
    // ...
}
```

分岐が増えるので、`Inf` に頼る書き方より遅くなる。それでも、動作が保証されるほうを取る。第 15 章で実装する。

なお、この書き換えには副次的な利点がある。`Inf` を経由する計算では、`0 * Inf = NaN` という別の罠が待っている。分岐で処理すればその心配もない。

## 4.6 `#pragma float_control` による局所的な精度の取り戻し方

### 構文

MSVC には、浮動小数点の意味論を局所的に切り替えるプラグマがある。

```cpp
#pragma float_control(precise, on, push)
// この範囲は /fp:precise 相当でコンパイルされる
#pragma float_control(pop)
```

使える形は次のとおり。

```
#pragma float_control( precise, { on | off } [, push ] )
#pragma float_control( except,  { on | off } [, push ] )
#pragma float_control( { push | pop } )
```

`push` を付けると現在の設定をスタックに積んでから変更し、`pop` で戻す。ヘッダの中で使うときは、必ず `push` / `pop` で対にすること。そうしないと、そのヘッダをインクルードした後のコード全体の設定が変わってしまう。

いくつか制約がある。MSVC のドキュメントに明記されているものを挙げる。

- `except` を `on` にできるのは、`precise` が有効なときだけ
- 例外の意味論が有効なとき（`/fp:except` またはプラグマによる）、`precise` を `off` にできない
- `fenv_access` を有効にできるのは `precise` が有効なときだけ

本書では `except` と `fenv_access` は使わないので、実質的に気にする必要はない。ただし第 5 章でアンダーフロー例外を一時的に使う場面があり、そこでは順序が問題になる。

### 関数の外に置く

このプラグマは**関数の外**に置き、関数単位で効かせるのが確実である。

```cpp
namespace collision::detail {

#pragma float_control(precise, on, push)

// 収束判定はこの関数の中で行う。/fp:fast の影響を受けさせない
[[nodiscard]] bool has_converged(float prev, float curr, float tol) noexcept {
    return std::fabs(curr - prev) <= tol;
}

#pragma float_control(pop)

} // namespace collision::detail
```

関数の途中に書くこともできるが、効果の範囲が読みにくくなる。「この関数は precise である」と関数単位で言えるようにしておくほうが、後から棚卸しするときに楽である（第 40 章でこの一覧を作る）。

### インライン展開に注意する

大きな落とし穴がある。**`precise` にした関数が、`fast` の呼び出し元にインライン展開されたとき、どちらの設定が適用されるかは自明でない。**

確実を期すなら `__declspec(noinline)` を併用する。

```cpp
#pragma float_control(precise, on, push)

__declspec(noinline)
[[nodiscard]] bool has_converged(float prev, float curr, float tol) noexcept {
    return std::fabs(curr - prev) <= tol;
}

#pragma float_control(pop)
```

呼び出しのオーバーヘッドが増えるが、`precise` にする箇所は「反復の収束判定」のように呼び出し回数が限られる場所なので、実害は小さい。

そして必ず、**逆アセンブリで意図どおりになっているか確認する**。4.4 節でやった手順をここでも使う。プラグマを書いただけで安心しないこと。

### どこを `precise` に戻すかの判断基準

本書全体で適用するルールをここで決める。以降の章では、このルールを参照する形で判断する。

| 対象 | 判断 | 理由 |
|---|---|---|
| **反復アルゴリズムの収束判定** | **戻す** | 判定が振動すると無限ループになる。呼び出し回数も少ない |
| **`NaN` / `Inf` のガード** | **戻す**（またはビット検査） | 消されると防御が機能しない |
| **区間の端の厳密な比較** | 場合による | 誤差を織り込んだ判定に書き換えるほうが良いことが多い |
| **内積・外積・距離の計算** | **戻さない** | 最も回数が多い。ここを遅くしては `/fp:fast` の意味がない |
| **行列・ベクトルの変換** | **戻さない** | 同上 |
| **ソルバの反復本体** | **戻さない**（測って判断） | 回数が多い。安定性の問題は別の手段で解く（第 37 章） |

原則を一行でいえば、**「回数が少なく、かつ判定を誤ると制御フローが壊れる箇所」だけを戻す**。数値がわずかにずれるだけの箇所は戻さない。

この判断はまず「戻さない」から始め、問題が出たら戻す、という順序で行う。最初から広く `precise` にすると、`/fp:fast` を選んだ意味がなくなる。

### コストを測る

`precise` に戻した関数がどれだけ遅くなるかは、実測しておく価値がある。

```cpp
TEST_METHOD(precise 領域のコストを測る) {
    constexpr int N = 10'000'000;
    Rng rng(42);
    std::vector<float> data(N);
    for (auto& v : data) v = rng.uniform(-1.0f, 1.0f);

    const auto t0 = std::chrono::steady_clock::now();
    float acc = 0.0f;
    for (int i = 1; i < N; ++i) {
        acc += collision::detail::has_converged(data[i-1], data[i], 1e-6f) ? 1.0f : 0.0f;
    }
    const auto t1 = std::chrono::steady_clock::now();

    Logger::WriteMessage(std::format("elapsed = {} ms, acc = {}\n",
        std::chrono::duration_cast<std::chrono::milliseconds>(t1 - t0).count(), acc).c_str());
}
```

`acc` を使っているのは、ループが最適化で消えるのを防ぐためである。結果を捨てるとコンパイラは計算ごと削除してしまう。

同じ関数からプラグマを外したバージョンと比べれば、コストが分かる。判断材料のない議論より、数字のほうが早い。

## 4.7 テスト：誤差を意図的に起こして検証する

この章で作ったものを、テストで固めておく。

### ULP の表が正しいこと

```cpp
TEST_METHOD(floatのULPが値に比例して粗くなること) {
    float prev_ulp = 0.0f;
    for (float x : {1.0f, 10.0f, 100.0f, 1000.0f, 10000.0f}) {
        const float ulp = std::nextafter(x, INFINITY) - x;
        Assert::IsTrue(ulp > prev_ulp, L"ULP が単調増加していない");
        // 相対精度はおおむね一定であること
        expect_near(1.19e-7f, ulp / x, 1e-8f, 0.5f);
        prev_ulp = ulp;
    }
}
```

相対許容誤差を `0.5f`（50%）と大きく取っているのは、この検証が「桁が合っていること」を見るものだからである。**許容誤差は検証したい内容に応じて調整してよい**。既定値を機械的に使う必要はない。

### 桁落ちが実際に起きること

```cpp
TEST_METHOD(近い値の引き算で有効桁が失われること) {
    const float a = 1000.0001f;
    const float b = 1000.0000f;
    const float diff = a - b;

    // 期待は 0.0001 だが、そこまでの精度は出ない
    Assert::IsFalse(nearly_equal(0.0001f, diff, 1e-9f, 1e-9f),
                    L"桁落ちが起きていない？ 環境を確認すること");

    // 1000 付近の ULP のオーダーの誤差が乗っている
    const float ulp_at_1000 = std::nextafter(1000.0f, INFINITY) - 1000.0f;
    Assert::IsTrue(std::fabs(diff - 0.0001f) < ulp_at_1000);
}
```

「壊れることを確認するテスト」である。奇妙に見えるかもしれないが、これは**環境の前提を検証している**。将来この本のコードを別の環境に持っていったとき、前提が成り立つかを教えてくれる。

### `NaN` 検査が最適化で消えないこと

```cpp
TEST_METHOD(ビット検査によるNaN判定が機能すること) {
    // 最適化で畳み込まれないよう volatile を経由させる
    volatile float zero = 0.0f;
    const float nan_value = zero / zero;

    Assert::IsTrue(is_nan_bits(nan_value), L"NaN を検出できていない");
    Assert::IsFalse(is_finite_bits(nan_value));

    Assert::IsFalse(is_nan_bits(1.0f));
    Assert::IsTrue(is_finite_bits(1.0f));
}
```

**このテストは Release 構成でこそ意味がある。** Debug では最適化されないので、素朴な `x != x` でも通ってしまう。第 2 章で「両方の構成でテストを走らせる」と決めたのは、こういうテストのためである。

余裕があれば、比較として素朴な判定も並べておくとよい。

```cpp
    // 参考：これは環境によっては失敗する（そういうものだと知るためのテスト）
    // Assert::IsTrue(nan_value != nan_value);
```

コメントアウトしてあるのは、失敗するかしないかが環境依存だからである。有効にして Release で走らせ、自分の環境がどちらかを確認してみてほしい。

### 極端なスケールで許容誤差が機能すること

```cpp
TEST_METHOD(許容誤差が極端なスケールでも機能すること) {
    // 原点近傍：絶対誤差が効く
    Assert::IsTrue(nearly_equal(0.0f, 1e-8f));
    Assert::IsFalse(nearly_equal(0.0f, 1e-3f));

    // 遠方：相対誤差が効く
    Assert::IsTrue(nearly_equal(100000.0f, 100000.5f));   // 相対 5e-6 なので許容内
    Assert::IsFalse(nearly_equal(100000.0f, 110000.0f));  // 相対 10% は明らかに不一致

    // 遠方で絶対誤差だけを使うと、そもそも表現できず必ず失敗することの確認
    Assert::IsFalse(nearly_equal(100000.0f, 100000.001f, 1e-6f, 0.0f));
}
```

最後の一件が、前章で「絶対誤差だけでは大きな値で機能しない」と述べたことの実証である。`100000.0f` と `100000.001f` は、そもそも同じ `float` に丸められている可能性すらある。

## この章のまとめ

- `float` の刻み幅（ULP）は値に比例して粗くなる。相対精度は約 `1.2e-7` で一定
- 機械イプシロンをそのまま許容誤差に使ってはいけない。許容誤差は単位系から逆算する
- 本書の既定値：テスト検証は絶対 `1e-6f` / 相対 `1e-5f`、アルゴリズム内部の判定は `1e-4f` 〜 `1e-3f`
- 近い値どうしの引き算は桁落ちを起こす。二乗のまま比較するなど、引き算を避ける形へ
- `/fp:fast` が許可するのは、再結合・FMA 融合・除算の逆数化・`rsqrt` 近似・特殊値の仮定
- 壊れる四つのパターン：`NaN` 判定の消失、判別式の微小な負値、片側だけの閾値比較、`1/0` への依存
- `#pragma float_control(precise, on, push)` で局所的に精度を戻せる。`__declspec(noinline)` を併用し、逆アセンブリで確認する
- **戻すのは「回数が少なく、判定を誤ると制御フローが壊れる箇所」だけ**

### 落とし穴と練習問題

**落とし穴 1：プラグマの効果範囲。**　`push` / `pop` を対にしないと、ヘッダをインクルードした先まで設定が漏れる。

**落とし穴 2：Debug で確認して満足する。**　`/fp:fast` に起因する問題の多くは Release でしか現れない。この章のテストは必ず Release でも走らせること。

**落とし穴 3：`precise` の乱用。**　「念のため」で広く適用すると、`/fp:fast` を選んだ意味がなくなる。まず戻さず、問題が出てから戻す。

**練習問題 4-1**　4.4 節の逆アセンブリの手順を実際に行い、`/fp:fast` と `/fp:precise` で `fma_check` の生成コードがどう変わるかを自分の目で確認しよう。`/arch:AVX2` を `/arch:SSE2` に落とすとどうなるかも試してみてほしい（FMA 命令が使えなくなる）。

**練習問題 4-2**　`sum4(1e10f, -1e10f, 1.0f, 1.0f)` の結果を、`/fp:fast` と `/fp:precise` で比べてみよう。値が変わるだろうか。変わらないなら、コンパイラが再結合を行わなかったということである。どういう場合に再結合が起きるのかを、`.asm` を見ながら調べてみてほしい。

**練習問題 4-3**　`ulp_distance` を実装し、「`0.1f` を 10 回足した値」と「`1.0f`」の ULP 距離を測ってみよう。何 ULP 離れているだろうか。次に 100 回、1000 回で測り、誤差の増え方を観察する。ランダムウォークのように √n で増えるだろうか、それとも n に比例するだろうか。

**練習問題 4-4**（発展）　4.5 節のパターン 2 について、実際に `NaN` が発生する入力を見つけてみよう。半径 1 の円と、それにちょうど接するレイを用意し、レイの方向をごくわずかずつ変えながら判別式の符号を観察する。境界のどちら側で `NaN` が出るかを確かめる。

次章では、`/fp:fast` に関連するもう一つの大きな主題、**非正規化数**を扱う。この章で見た「精度」の話とは違い、次章の主題は**速度**である。特定の値の範囲に落ちた計算が、数十倍遅くなることがある。そしてその対処は、コンパイラオプションではなく実行時の CPU の設定で行う。
