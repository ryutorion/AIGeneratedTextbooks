# 第 1 章　本書の歩き方と、作るものの全体像

> **この章のゴール**
> 本書が何を作る本なのかを掴む。「コリジョン」という言葉が指す範囲を三層に整理し、最終的に手元へ残るライブラリの姿を先に見ておく。コードはまだ書かない。次章から手を動かすための地図を作る章である。
>
> なお本書の各章は「ゴール → 考え方 → 実装 → テスト → 落とし穴と練習問題」の 5 ブロックで統一されているが、この第 1 章だけは導入のため例外的な構成をとる。

## 1.1 ゲームにおける「コリジョン」とは何か ― 判定・情報生成・応答の三層

### 「当たったかどうか」で終わらない

コリジョン判定と聞いて最初に思い浮かぶのは、おそらくこういう関数だろう。

```cpp
bool intersects(const Circle& a, const Circle& b);
```

二つの円が重なっているかを `bool` で返す。間違ってはいない。だがこれだけでゲームが作れるかというと、まったく作れない。

キャラクターが壁に向かって歩き、壁にめり込んだとしよう。`intersects` は `true` を返す。それで？　めり込んだキャラクターを引き剥がすには、**どちらの向きに、どれだけ動かせばよいか**を知らなければならない。`true` という一ビットの情報からは、それは復元できない。

弾丸が壁に当たったとしよう。着弾エフェクトを出したい。**どの位置に、どの向きで**出せばよいか。やはり `true` からは何も分からない。

床の上に箱を置いたとしよう。箱は静止してほしい。ところが接触している点を一つしか知らないと、箱はその一点を支点にしてゆっくり傾き、やがて転がり落ちる。**平らに接しているという事実**を表現するには、接触点が二つ必要になる（3D なら三つ以上）。

つまり、実際のゲームで必要とされるのは `bool` ではない。本書では、コリジョンにまつわる処理を次の三層に分けて考える。この分類は本書全体を貫く骨格になる。

### 第 1 層：判定 (detection)

二つの形状が重なっているか否かを決める。返り値は `bool`。第 2 層以降の前提になる、最も基本的な層である。

この層だけで完結する用途も実際にある。たとえば「プレイヤーがトリガー領域に入ったらイベントを発火する」「敵の索敵範囲にプレイヤーがいるか」といった判定は、重なっているかどうかさえ分かればよい。こうした「重なりの有無だけを問う判定」は一般に**オーバーラップ判定**と呼ばれ、後の層を計算しない分だけ速い。

### 第 2 層：情報生成 (information)

重なっているとき、**どのように**重なっているかを記述する。本書ではこの記述を `Contact` という型にまとめる。中身は次の三つである。

- **法線 (normal)**　押し戻すべき向き。単位ベクトル。
- **貫通深度 (penetration depth)**　その向きにどれだけ押し戻せば重なりが解消されるか。非負のスカラー。
- **接触点 (contact point)**　どこで触れているか。位置ベクトル。複数個になることもある。

この三つが揃うと、途端にできることが増える。法線と深度があれば押し戻せる。接触点があればエフェクトを出せるし、重心から離れた位置に力を加えて回転を生むこともできる。

「複数個になることもある」と書いた接触点の集合を**接触マニフォールド (contact manifold)** と呼ぶ。箱が床に平らに乗っているとき、マニフォールドは二点（3D なら四点）からなる。この生成は第 14 章のテーマである。

第 1 層から第 2 層へ進むことが、実は本書のかなりの部分を占める。「重なっているか」を答えるアルゴリズムは、たいてい「どう重なっているか」も答えられるように拡張できる。逆にいえば、拡張しやすい形で第 1 層を実装しておくことが重要になる。第 7 章で返り値の型を先に設計するのは、そのためである。

### 第 3 層：応答 (response)

第 2 層で得た情報をもとに、物体を実際に動かす。押し戻す、跳ね返す、滑らせる、回転させる。

ここには段階がある。最も素朴なのは、めり込んだ分だけ位置を直接動かす**位置補正**である（第 34 章）。次に、速度を書き換えて跳ね返りや摩擦を表現する**力積による応答**（第 36 章）。さらに、複数の接触が同時に存在する状況を反復で解く**ソルバ**（第 37 章）。積み上がった箱が崩れずに静止するには、ここまで必要になる。

一方で、プレイヤーキャラクターの移動は剛体シミュレーションに任せないほうが操作感がよい、という事情もある。壁に沿って滑る挙動を手続き的に書く方法は第 38 章で扱う。

### この三層が本書の目次に対応している

改めて本書の構成を三層に対応づけると、こうなる。

| 層 | 対応する部 | 章 |
|---|---|---|
| 準備 | 第 0 部 | 第 1〜5 章 |
| 第 1 層・第 2 層 | 第 I〜V 部 | 第 6〜28 章 |
| （数を捌く仕組み） | 第 VI 部 | 第 29〜33 章 |
| 第 3 層 | 第 VII 部 | 第 34〜39 章 |
| 仕上げ | 第 VIII 部 | 第 40〜43 章 |

判定と情報生成に全体の半分以上を割いている。これは誇張ではなく実態を反映している。物理エンジンの実装で最も泥臭く、最も退化ケースに悩まされるのは、応答よりも判定側だからである。

### ゲームならではの事情

コリジョン判定は計算幾何学の一分野でもあるが、ゲームで使うときには学術的な文脈とは違う制約がかかる。三つ挙げておく。

**時間が離散的である。**　ゲームは 1 秒間に 60 回といった頻度で世界を更新する。フレームとフレームの間、物体は連続的に動いているのではなく、**ワープしている**。時速 300 km で飛ぶ弾丸は 1 フレームで 1.4 m 進む。厚さ 10 cm の壁は、その 1.4 m のジャンプの中に丸ごと収まってしまう。前のフレームでは壁の手前、次のフレームでは壁の向こう。どちらのフレームでも重なっていない。弾はすり抜ける。これが**トンネリング**であり、第 III 部（第 15〜18 章）で正面から扱う。

**数が多い。**　オブジェクトが 1,000 個あるとき、総当たりのペア数は約 50 万になる。1 ペアあたり 100 ナノ秒で判定できたとしても 50 ミリ秒かかり、これだけで 1 フレーム（16.7 ミリ秒）の予算を三倍超過する。判定を速くするだけでは追いつかず、**そもそも判定しない**仕組みが要る。これが第 VI 部のブロードフェーズである。

**正しさより「それらしさ」と速度が優先される。**　橋梁の構造解析なら 0.1% の誤差が問題になるが、ゲームでは箱が 1 mm めり込んでいても誰も気づかない。むしろ、めり込みをゼロにしようとして物体が震えるほうがずっと目立つ。この本が `float` を使い、`/fp:fast` を選び、非正規化数を切り捨てる（第 5 章）のは、この価値観に立っている。

ただし、**近似したことを自覚していない**のは危険である。「なんとなく動いているが、たまに変になる」の大半は、どこを近似したか把握していないことに起因する。本書が各章に「落とし穴」の節を置き、退化ケースをしつこく列挙するのは、この自覚を持ってもらうためである。

### 用語の整理

本書で繰り返し登場する言葉を、ここでまとめて定義しておく。今すぐ暗記する必要はない。読んでいて意味を忘れたらここに戻ってきてほしい。

| 用語 | 意味 | 初出 |
|---|---|---|
| ブロードフェーズ | 「明らかに当たっていない」ペアを大量に捨てる粗い前処理 | 第 VI 部 |
| ナローフェーズ | 残ったペアに対して精密な判定を行う処理 | 第 I 部〜 |
| マニフォールド | 接触点の集合。面と面が接するときは複数点になる | 第 14 章 |
| MTV | Minimum Translation Vector。重なりを解消する最小の移動ベクトル | 第 10 章 |
| TOI | Time of Impact。フレーム内で最初に衝突する時刻（0〜1 の比） | 第 17 章 |
| サポート写像 | ある向きについて形状の最も遠い点を返す関数。凸形状を統一的に扱う鍵 | 第 19 章 |
| 退化ケース | ゼロ長ベクトル、同一点、平行な辺など、式が破綻する入力 | 全章 |

## 1.2 完成物の姿：ヘッダ主体のライブラリ `collision` と、それを叩くテストプロジェクト

### 二つのプロジェクト

本書を通じて作るのは、一つのソリューションに収まった二つのプロジェクトである。

```
GameCollision/                     ← ソリューション
├─ collision/                      ← スタティックライブラリ
│   ├─ include/collision/
│   │   ├─ math/       vec2.h, vec3.h, scalar.h, fp_control.h
│   │   ├─ shapes/     circle.h, aabb.h, obb.h, polygon.h, capsule.h, ...
│   │   ├─ narrow/     contact.h, sat.h, gjk.h, epa.h, raycast.h, sweep.h
│   │   ├─ broad/      grid.h, sap.h, bvh.h
│   │   ├─ dynamics/   rigid_body.h, solver.h, character_controller.h
│   │   └─ world.h                 ← すべてを束ねる入口
│   └─ src/                        ← 実装が長くなるものだけ .cpp に出す
└─ collision_tests/                ← ネイティブ単体テストプロジェクト（DLL）
    ├─ test_helpers.h              ← 比較ヘルパ、ランダム生成器
    ├─ test_vec2.cpp
    ├─ test_circle.cpp
    └─ ...                         ← 章ごとに増えていく
```

「ヘッダ主体」と書いたのは、実装の多くをヘッダに置くという意味である。ベクトル演算や単純な判定関数は短く、インライン展開されることに価値がある。一方で GJK や BVH のように行数が多く、テンプレートである必然性の薄いものは `.cpp` に分ける。この線引きは絶対的なものではないので、迷ったらヘッダに書いておいて後で移せばよい。

### C++ モジュールを使わない理由

C++20 で導入されたモジュールは、ヘッダの抱える問題（重複インクルード、マクロ汚染、コンパイル時間）に対する正攻法の解決策である。それでも本書はモジュールを使わない。理由は三つある。

第一に、**本書の主題を薄めたくない**。モジュールはビルドシステムとの関わりが深く、うまくいかないときの調査に相応の知識を要求する。コリジョンのアルゴリズムを学びに来た読者を、ビルドの沼で足止めさせたくない。

第二に、**読者が自分のプロジェクトへ持ち込みやすい**。ヘッダで書かれたライブラリは、既存のプロジェクトにディレクトリごとコピーしてインクルードパスを通せば使える。モジュール化されたコードを既存のヘッダベースのプロジェクトへ混ぜるのは、それより一手間かかる。

第三に、**本書のコードは短い**。モジュールの恩恵が最も大きいのは大規模なコードベースにおけるコンパイル時間の削減だが、本書で書く量ならヘッダでも十分に速い。

なお、モジュール以外の C++23 の機能は積極的に使う。`std::expected`、`std::print`、`std::mdspan`、コンセプト、`if consteval`、明示的オブジェクトパラメータ（deducing this）など、コリジョンの実装を素直に書くのに役立つものが多い。それぞれ登場する章で説明する。

### 最終的にこう書けるようになる

到達点のイメージを先に見せておく。第 33 章まで進むと、利用側のコードはこう書ける。

```cpp
#include <collision/world.h>

collision::World world;

// 静的な地形
world.add_static(collision::Aabb{{-50.0f, -1.0f}, {50.0f, 0.0f}});

// 動く物体
auto player = world.add_dynamic(collision::Circle{{0.0f, 5.0f}, 0.5f});

// 毎フレーム
world.step(1.0f / 60.0f);

// クエリ
if (auto hit = world.raycast({0.0f, 5.0f}, {0.0f, -1.0f}, 100.0f)) {
    std::println("地面まで {:.2f} m", hit->distance);
}
```

そして内部では、こうした低レベルの関数が支えている。第 8 章の終わりには、もう最初の一つが書けている。

```cpp
// 第 8 章
std::optional<Contact> intersect(const Circle& a, const Circle& b);

// 第 12 章
std::optional<Contact> intersect(const Obb& a, const Obb& b);

// 第 22 章
std::expected<Contact, GjkError> intersect_gjk(const Shape auto& a,
                                               const Shape auto& b);
```

一行目から三行目へ向かう道のりが本書である。形は似ているが、`Circle` 専用の実装から、任意の凸形状を受け取る汎用の実装へと一般化されていく。

### テストプロジェクトが「実行画面」である

本書には描画がない。ウィンドウも出なければ、円が転がる様子も見えない。代わりに、**テストが緑になることが唯一の「動いた」の証拠**になる。

これは制約であると同時に、意図的な選択でもある。描画を入れると、コリジョンとは無関係な話（ウィンドウプロシージャ、メッセージループ、デバイスコンテキスト）に紙面を割くことになる。それらは面白いが、本書の主題ではない。

そして実務的にも、この選択は理に適っている。目視での確認は「たまたま今回はうまく動いた」を見逃す。テストは、退化ケースを含む何百通りの入力を毎回自動で検査してくれる。GJK と EPA のような複雑なアルゴリズムを、目視だけで正しく実装しきるのは現実的でない。

とはいえ、失敗したときに数字の羅列だけを睨むのは辛い。そこで第 41 章では、失敗したテストの入力を SVG ファイルとして書き出し、ブラウザで開いて目で確認する仕組みを用意する。「普段はテスト、詰まったら可視化」という運用になる。

## 1.3 なぜ既製の物理エンジンを使わず自分で書くのか

### 実務では既製品を使うべきである

先に結論を書いておく。実際に製品を作るなら、成熟した物理エンジンを使うべきである。それらは長年にわたって膨大な数の退化ケースを踏み抜き、修正され、最適化されてきた。同等のものを個人が短期間で書くことはできない。

では、なぜ自分で書くのか。

### 「パラメータをいじって祈る」から抜け出すため

物理エンジンを使っていると、必ずこういう場面に出くわす。

- 高速で動く弾がたまに壁をすり抜ける
- 積み上げた箱が、静止しているはずなのに小刻みに震える
- 平らな床を歩いているのに、タイルの継ぎ目で見えない段差に引っかかる
- 斜面に置いた箱が、止まるはずの角度でじりじり滑り落ちる

このとき、中身を知らなければ打てる手は限られる。設定項目の一覧を眺め、それらしい名前のパラメータを動かし、症状が消えるまで試す。消えたとしても、なぜ消えたのかは分からない。別の場面で再発する。

これらの症状には、それぞれ明確な原因がある。本書を読み終えた時点で、上の四つはこう読めるようになっているはずである。

- すり抜け → 離散時間ステップとトンネリング。連続衝突判定が効いていない（第 17〜18 章）
- 震え → 位置補正の過剰な適用。スロップとソフト拘束の設定（第 34、37 章）
- 継ぎ目の引っかかり → 内部エッジ問題。隣接三角形の法線が考慮されていない（第 27 章）
- 斜面の滑り → 静止摩擦の扱いと、ソルバの反復回数（第 36、37 章）

原因が言語化できれば、既製エンジンのドキュメントのどこを読めばよいかも分かる。**自作は、既製品をうまく使うための投資でもある。**

### 自作が正解になる場面もある

すべてが学習目的というわけでもない。次のような場合、自前のコリジョンが現実的な選択肢になる。

- **必要な機能がごく一部**。2D の弾幕ゲームに、関節拘束もソフトボディも要らない。円と AABB の判定だけなら数百行で済む
- **依存関係を増やしたくない**。ライブラリのライセンス、ビルド時間、バイナリサイズが問題になる環境
- **特殊な要件がある**。固定小数点で動かしたい、独自のメモリアロケータに載せたい、決定論を厳密に保証したい
- **既存エンジンの拡張**。新しい形状ペアの判定を自分で足す場合、結局は本書の内容が必要になる

### 学習の順序として

コリジョンや物理シミュレーションの解説は世の中に多くある。それでも「読んだが実装できない」という感想をよく聞く。理由の一つは、解説の多くが完成形のアルゴリズムを提示するからだと思う。GJK の説明を読んで、シンプレックスの更新規則を理解しても、それだけでは動くコードにならない。実際に書くと、終了条件、数値誤差、退化した単体、反復の上限といった、解説には書かれていない問題が山ほど出てくる。

本書はその逆をいく。小さく動くものを作り、テストで固め、少しずつ一般化する。第 8 章で書く円と円の判定は 10 行にも満たないが、そこには「重なりの判定」「法線の計算」「深度の計算」「退化ケースの処理」という、後の章で何度も繰り返される構造がすべて含まれている。第 22 章の EPA も、規模が大きいだけで構造は同じである。

## 1.4 本書のコードの読み方

### 差分表記の凡例

本書のコードは、一度書いて終わりではない。同じ関数が章をまたいで何度も書き換えられる。そこで、変更箇所を次の凡例で示す。

```cpp
struct Circle {
    Vec2  center;
    float radius;

    // [追加] 第 10 章で必要になった
    [[nodiscard]] constexpr Aabb bounds() const noexcept;
};
```

- `// [追加]` … 新しく書き足した行
- `// [変更]` … 既存の行を書き換えた
- `// [削除]` … この行を消す（消した後の姿を示すため、消す行自体は掲載しない場合もある）
- `// ...` … 変更のない既存のコードを省略している

長いコードの一部だけを示すときは、前後の文脈が分かるように関数のシグネチャや `struct` の宣言を残す。全文を再掲する必要があるほど大きく変わったときは、その旨を明記する。

### 完成形から始めない

本書は「まず完成したコードを見せて、それから解説する」というスタイルをとらない。動く小さなものを作り、テストを通し、不満が出てきたところで拡張する、という順序を守る。

たとえば `Contact` 型は、第 7 章で法線と深度と接触点を持つ形に設計するが、そこに至る前に「`bool` では何が足りないか」を実感してもらう。第 14 章でマニフォールドが必要になったときも、いきなり複数点を返す設計にはせず、「一点だと箱が転がる」という失敗を先に見る。

遠回りに見えるかもしれないが、**なぜその設計なのかが腑に落ちていないコードは、応用が利かない**。読者が自分のゲームに合わせて改造するとき、この「なぜ」が効いてくる。

### コードは手元で打つ

写経を推奨する。コピー＆ペーストでも動くものはできるが、打っている最中に気づくことが多い。特に本書は、コンパイルエラーや失敗するテストを**意図的に通過させる**場面がある。「まずこう書くと、こういう理由で失敗する」を体験してから直す構成になっているので、飛ばさずに付き合ってほしい。

### 命名と書式の約束

本書のコードは次の規約に従う。

| 対象 | 規約 | 例 |
|---|---|---|
| 名前空間 | 小文字 | `collision`, `collision::detail` |
| 型 | パスカルケース | `Vec2`, `Aabb`, `ContactManifold` |
| 関数・変数 | スネークケース | `length_squared`, `closest_point` |
| 定数 | スネークケース | `constexpr float epsilon` |
| メンバ変数 | スネークケース（接頭辞なし） | `center`, `radius` |
| テンプレート引数 | パスカルケース | `template <class Shape>` |

標準ライブラリと同じスネークケースを関数に使うのは、`std::` の関数と自作の関数が混在したときに違和感が少ないためである。型だけパスカルケースにしているのは、`Vec2` のような数学型が標準ライブラリの型と紛れないようにするため。

`[[nodiscard]]` は、返り値を捨てると意味がない関数すべてに付ける。コリジョン判定の結果を捨てるのはほぼ確実にバグなので、これは実用的な防御になる。`noexcept` も、例外を投げ得ない関数には明示する。

### 座標系と単位系の約束

本書では次のように決める。この約束は第 5 章（非正規化数と単位系）と第 43 章（ライブラリの契約）で改めて重要になる。

- **1 単位 = 1 メートル**。人間サイズのキャラクターが 1.8、地面のタイルが 1.0 程度になる縮尺
- **2D では X が右、Y が上**。数学の教科書と同じ向き。画面座標（Y が下）とは異なるので、描画側で反転させる前提
- **2D の回転は反時計回りが正**
- **3D では右手系、Y が上**（第 24 章で改めて確認する）
- **角度はラジアン**。度数法は入出力の境界でのみ使う

単位を決めておくことには実質的な意味がある。「めり込みをどこまで許すか」「速度がどれだけ小さければ静止とみなすか」といった閾値は、単位が決まっていなければ数値を決めようがない。本書では 1 mm = 0.001 を基準に、しきい値を組み立てていく。

### `float` を使う

本書の浮動小数点型は一貫して `float`（単精度、32 ビット）である。`double` は使わない。

理由は速度とメモリである。SIMD 命令は同じレジスタ幅で `float` を `double` の倍の個数処理できるし、キャッシュに乗る座標の数も倍になる。ブロードフェーズのように大量のデータを舐める処理では、この差がそのまま効く。

代償として精度は下がる。`float` の有効桁数はおよそ 7 桁で、原点から 10,000 離れた場所では位置の刻み幅が約 1 mm になる。広大なオープンワールドを扱うなら問題になるが、その場合の対処（座標系を分割してローカル座標で計算する）は本書の範囲外である。精度の話は第 4 章で詳しく扱う。

### 部ごとの見取り図

**第 0 部（第 1〜5 章）準備。**　環境構築、テストの土台、浮動小数点の性質。コリジョンのコードは一行も出てこないが、**ここを飛ばすと後で必ず戻ってくることになる**。特に第 4 章と第 5 章は、本書が `/fp:fast` と FTZ/DAZ という速度優先の選択をしている以上、その前提を共有するための必読部分である。

**第 I 部（第 6〜10 章）2D の数学と最小の判定。**　`Vec2` を作り、`Contact` 型を設計し、円と AABB の判定を書く。ここで確立する「最近接点さえ求まれば円との判定は全部同じ形になる」という視点は、以降ずっと効いてくる。

**第 II 部（第 11〜14 章）凸形状と分離軸定理。**　SAT を学び、OBB と凸多角形へ広げ、接触マニフォールドを生成する。2D の物理エンジンとして実用になる水準はここで到達する。

**第 III 部（第 15〜18 章）レイキャストと連続衝突判定。**　時間が離散的であることに起因する問題群。ミンコフスキー和という道具が登場し、「移動する形状の判定」が「静止形状へのレイキャスト」に帰着することを見る。

**第 IV 部（第 19〜23 章）GJK と EPA。**　本書で最も抽象度が高い部分。サポート写像という一つの窓口を通せば、あらゆる凸形状が同じアルゴリズムで扱えるようになる。難所だが、ここを越えると視界が開ける。

**第 V 部（第 24〜28 章）3 次元へ。**　2D で作ったものを 3D へ拡張する。新しい概念は少なく、多くは次元が増えただけである。ただし線分と線分の最近接点（第 25 章）と 3D の SAT の 15 軸（第 26 章）は、それ自体が山場になる。

**第 VI 部（第 29〜33 章）ブロードフェーズ。**　アルゴリズムの正しさから、規模への対処へ話題が移る。グリッド、Sweep and Prune、動的 AABB 木。ここは計算量の話が主で、幾何の難しさは一段落する。

**第 VII 部（第 34〜39 章）衝突応答。**　判定した後どうするか。剛体の運動、力積、反復ソルバ、キャラクターコントローラ。物理シミュレーションの入口であり、それだけで一冊書ける領域なので、本書では簡易的な実装に留める。

**第 VIII 部（第 40〜43 章）仕上げ。**　テスト戦略の総括、デバッグの仕組み、性能の詰め、ライブラリとしての体裁。

### 飛ばし読みの指針

- **2D しか要らない**　第 24〜28 章（第 V 部）を飛ばせる。第 VI 部以降は 2D のまま読める
- **判定だけ欲しい、応答は既製品に任せる**　第 34〜39 章（第 VII 部）を飛ばせる
- **GJK は後回しにしたい**　第 19〜23 章（第 IV 部）は、第 V 部の第 28 章を除けば後続章の前提になっていない。SAT（第 II 部）だけで第 VI 部・第 VII 部へ進める
- **とにかく最短で動かしたい**　第 1〜10 章を読み、第 34 章の位置補正まで飛ぶ。円と AABB だけの世界だが、それでも遊べるものは作れる

一方、**飛ばさないでほしい**のは第 3〜5 章である。テストの書き方と浮動小数点の前提は、後続のすべての章がその上に乗っている。特に第 5 章の FTZ/DAZ の設定は、これを知らずに書いたコードが「なぜか特定の場面でだけ重い」という形で後から跳ね返ってくる。

## この章のまとめ

- コリジョンは「判定」「情報生成」「応答」の三層に分けて考える。`bool` を返すだけでは実用にならない
- ゲーム特有の制約は三つ。時間が離散的であること、数が多いこと、速度が正確さより優先されること
- 作るのはスタティックライブラリ `collision` と、それを検証する単体テストプロジェクト。C++ モジュールは使わない
- 描画はしない。テストが緑になることが「動いた」の証拠である
- 既製の物理エンジンを使うにせよ、中身を知っていることが症状の切り分けを可能にする
- 単位は 1 = 1 メートル、型は `float`、2D は X 右・Y 上

次章では Visual Studio 2026 を設定し、二つのプロジェクトを作り、コンパイラオプションを整える。まだコリジョンのコードは書かないが、第 3 章で最初のテストを緑にするための土台がここで完成する。
