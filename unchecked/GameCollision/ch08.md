## 8.1 距離の二乗による交差判定

### 円の定義

```cpp
// collision/shapes/circle.h
#pragma once

#include "collision/math/vec2.h"

namespace collision {

struct Circle {
    Vec2  center{};
    float radius{};
};

} // namespace collision
```

`Vec2` と同じく集成体である。`Circle{{0.0f, 0.0f}, 1.0f}` と書ける。

**不変条件として `radius >= 0` を課す**が、コンストラクタで強制はしない。第 7.5 節で決めたとおり、内側の関数は入力を信頼し、検証は境界で行う。

### 交差の条件

二つの円が重なるのは、中心間の距離が半径の和より小さいときである。

```
distance(a.center, b.center) < a.radius + b.radius
```

これをそのまま書くと平方根が入る。第 6.4 節で決めた習慣に従い、両辺を二乗する。

```cpp
// collision/narrow/circle_circle.h
#pragma once

#include "collision/shapes/circle.h"
#include "collision/narrow/contact.h"

namespace collision {

[[nodiscard]] constexpr bool overlaps(const Circle& a, const Circle& b) noexcept {
    const float r = a.radius + b.radius;
    return distance_squared(a.center, b.center) < r * r;
}

} // namespace collision
```

両辺が非負なので、二乗しても大小関係は変わらない。平方根が消え、乗算と減算だけになった。

この関数は `constexpr` である。`std::sqrt` を使っていないので、コンパイル時に評価できる。

### `<` か `<=` か

境界、つまり二つの円がちょうど接している状態をどう扱うか。

本書は **`<` を使い、「ちょうど接している」は交差していないものとする**。理由は二つある。

**深度がゼロの `Contact` を作りたくない。** 接している状態では貫通深度がゼロになる。第 7.2 節で「`Contact` は交差していることを前提とした型」と決めたので、深度ゼロの `Contact` は中途半端である。

**そもそも「ちょうど」は起こらない。** 浮動小数点で `distance_squared` がぴったり `r*r` に一致する確率は無視できる。この選択が実際の挙動を変えることはほぼない。

**重要なのは、この判断が実質的でないと理解しておくこと**である。第 3.5 節の原則 3 で述べたとおり、境界ぎりぎりの入力に対する結果は、誤差によってどちらにも転ぶ。`<` と `<=` のどちらを選んでも、境界の位置は誤差の範囲でぶれる。「`<` にしたから接触は非交差だ」と厳密に信じてはいけない。

## 8.2 貫通深度と法線を求める

### 導出

交差しているとき、押し戻すべき向きと量を求める。図を頭に描いてほしい。

二つの円が重なっている。中心 A と中心 B を結ぶ直線を考える。**押し戻すべき向きは、この直線に沿った向き**である。それ以外の向きに動かすと、同じ量だけ動かしても重なりが解消しない。

量はどうか。中心間距離を `d`、半径の和を `r` とすると、重なっている長さは `r - d` である。これが貫通深度になる。

```
normal = (B.center - A.center) を正規化したもの
depth  = (a.radius + b.radius) - distance(a.center, b.center)
point  = A.center + normal * a.radius    （A の表面上の点）
```

法線の向きは、第 7.3 節の規約「A から B へ」に合っている。`B - A` の向きである。

**ここで平方根が必要になる。** 深度は実際の長さなので、二乗のままでは求められない。`overlaps` が平方根なしで済むのに対し、`intersect` は平方根を一回使う。この差が、二つの API を分けた理由である。

### 実装（第一版）

```cpp
// collision/narrow/circle_circle.h（続き）

[[nodiscard]] inline std::optional<Contact>
intersect(const Circle& a, const Circle& b) noexcept {
    const Vec2  d  = b.center - a.center;
    const float r  = a.radius + b.radius;
    const float d2 = length_squared(d);

    if (d2 >= r * r) {
        return std::nullopt;             // 交差していない
    }

    const float dist   = std::sqrt(d2);
    const Vec2  normal = d / dist;        // ← 危険：dist がゼロなら NaN

    return Contact{
        .normal = normal,
        .depth  = r - dist,
        .point  = a.center + normal * a.radius,
    };
}
```

C++20 の指示付き初期化子で `Contact` を組み立てている。フィールド名が明示されるので、`normal` と `point` を取り違えることがない。20 バイトの構造体に `Vec2` が二つあるとき、この明示は価値がある。

**この実装には問題がある。** `dist` がゼロのとき、ゼロ除算で `NaN` が出る。次節で塞ぐ。

なお、`d2 >= r * r` の判定と `overlaps` の `d2 < r * r` は、否定の関係になっている。**両者が食い違わないことは、第 7.7 節の `check_overlaps_matches_intersect` が保証する。**

## 8.3 中心が完全に一致した場合

### 退化ケースを見つける

`dist` がゼロになるのは、二つの円の中心が完全に一致したときである。

「そんな状況、実際に起こるのか」と思うかもしれない。起こる。

- 敵をスポーンさせる位置が重なった
- リセット処理で複数のオブジェクトを原点に置いた
- 剛体シミュレーションで、二つの物体が完全に同じ位置へ収束した
- テストで意図的に同じ座標を渡した

そして**一度でも `NaN` が出ると、そこから広範囲に伝播する**。位置が `NaN` になり、それを使った次のフレームの判定もすべて `NaN` になり、画面から物体が消える。`/fp:fast` の下では検出も難しい（第 4 章）。

### 何を返すべきか

中心が一致しているとき、押し戻すべき「向き」は定義できない。どの向きへ動かしても等価だからである。

三つの選択肢がある。

**案 1：`nullopt` を返す。**　「判定できない」を「交差していない」と表現することになる。第 7.5 節で述べたとおり、これは危険である。完全に重なっているのに「当たっていない」と返すのは、明らかにおかしい。

**案 2：`std::expected` でエラーを返す。**　正確ではある。ただし、この程度のことで呼び出し側にエラー処理を強いるのは重い。円と円の判定は最も基本的な操作であり、ここに `expected` を持ち込むと本書全体が煩雑になる。

**案 3：任意の向きを選んで返す。**　どの向きでも等価なので、一つ決めてしまう。押し戻しは正しく機能する（重なりは解消する）。

本書は**案 3** を採る。第 7.5 節で決めた「内側は `optional`」の方針に沿っている。

### 実装（第二版）

```cpp
[[nodiscard]] inline std::optional<Contact>
intersect(const Circle& a, const Circle& b) noexcept {
    const Vec2  d  = b.center - a.center;
    const float r  = a.radius + b.radius;
    const float d2 = length_squared(d);

    if (d2 >= r * r) {
        return std::nullopt;
    }

    // [変更] 中心が一致する退化ケースを吸収する。
    // 向きが定義できないので、任意の向き（+X）を選ぶ。
    // 押し戻しは正しく機能する（どの向きでも等価なため）。
    const Vec2 normal = normalize_or(d, Vec2{1.0f, 0.0f});

    // [変更] dist は normal と d から復元せず、二乗長から求める。
    //        d2 が min_length2 未満のときは dist = 0 とみなす。
    const float dist = (d2 < min_length2) ? 0.0f : std::sqrt(d2);

    return Contact{
        .normal = normal,
        .depth  = r - dist,
        .point  = a.center + normal * a.radius,
    };
}
```

第 6.4 節で作った `normalize_or` がここで効いている。「正規化には常に判断が伴う」という設計が、呼び出し側を一行で済ませてくれる。

`dist` の計算にも `min_length2` を使っている。`d2` が閾値未満なら平方根を計算せずゼロとする。**`normalize_or` の内部判定と、この判定の閾値を揃えている**のが要点である。揃えないと、「法線はフォールバックなのに `dist` は微小な非ゼロ」という不整合な状態が生まれうる。

### 中心が一致したときの深度

このとき `depth = r - 0 = r` になる。半径の和がそのまま深度である。

これは正しい。完全に重なった二つの円を引き離すには、半径の和だけ動かす必要がある。押し戻し後は、ちょうど接した状態になる。

### 「任意の向き」の副作用

+X 方向を選んだことで、一つ副次的な効果がある。**同じ位置に重なった複数の物体が、すべて同じ向きに押し出される**。

物理シミュレーションでは、これが好ましくないことがある。10 個の円を同じ位置に置くと、全部が右へ一列に並ぶ。現実感がない。

対処としては、物体の ID や位置のハッシュから疑似的に向きを散らす方法がある。ただし本書では採らない。**決定論を保ちたい**からと、この状況自体が正常な運用では起きないからである。第 37 章のソルバでは、こうした縮退した配置が反復によって自然に解消されることを見る。

## 8.4 内包の扱い

### もう一つの退化ケース

小さな円が、大きな円の内部に完全に収まっている場合を考える。

```cpp
const Circle big  {{0.0f, 0.0f}, 10.0f};
const Circle small{{1.0f, 0.0f},  1.0f};
```

`d = 1`、`r = 11` なので、`d2 = 1 < 121 = r*r` により交差と判定される。深度は `11 - 1 = 10` になる。

**この結果は正しいだろうか。**

「押し戻して重なりを解消する」という意味では正しい。`small` を +X 方向に 10 動かせば `x = 11` となり、`big` の外側でちょうど接する。

だが、**それが望ましい挙動とは限らない**。ゲームによっては、小さい物体を大きい物体の外へ 10 メートルも瞬間移動させるのは不自然である。近い側の縁（`x = 10`）へ押し出すほうが自然に見えることもある。

### 本書の立場

**深度は「重なりを完全に解消するのに必要な最小の移動量」と定義する。** 内包の場合、それは半径の和から距離を引いた値であり、上の計算は定義どおりである。

「近い縁へ押し出す」という別の解釈を採ると、深度の定義が場合分けになり、`overlaps` との整合性も崩れる。定義は単純に保つ。

そのうえで、**内包を特別扱いしたい場合は呼び出し側で判断する**。判定の結果から内包かどうかは復元できる。

```cpp
// b が a に完全に含まれているか
[[nodiscard]] constexpr bool contains(const Circle& a, const Circle& b) noexcept {
    if (b.radius > a.radius) return false;
    const float slack = a.radius - b.radius;
    return distance_squared(a.center, b.center) <= slack * slack;
}
```

この関数も二乗のまま比較している。`slack` が非負であることを事前に確認しているので、二乗しても大小関係は保たれる。**先に `b.radius > a.radius` を弾いているのは、そのためでもある**（`slack` が負だと二乗して符号情報が失われる）。

### 深度が半径を超えることの含意

内包のケースでは、深度が形状の大きさを超えうる。`depth = 10` に対して `small.radius = 1` である。

第 34 章の位置補正では、この点が問題になる。深度をそのまま位置に加算すると、物体が大きく飛ぶ。1 フレームで 10 メートル移動すれば、その途中にあった別の物体をすり抜ける。

対処は二つある。一つは、1 フレームあたりの補正量に上限を設けること。もう一つは、複数フレームに分けて徐々に解消すること。第 34 章で詳しく扱う。

ここでは、**判定側は正しい値を返し、どう使うかは応答側の判断である**という役割分担を確認しておけばよい。判定関数が「動かしすぎるといけないから」と深度を勝手に小さくすべきではない。

## 8.5 テスト

### 四つの系統

第 3.8 節の方針に従い、一つのテストで一つのことを検証する。円と円の場合、入力の配置は四つの系統に分けられる。

| 系統 | 配置 | 期待 |
|---|---|---|
| 離れている | `d > r` | `nullopt` |
| 接している | `d ≈ r` | 誤差次第（境界としてテストしない） |
| めり込んでいる | `0 < d < r` | `Contact`、深度は `r - d` |
| 同心 | `d = 0` | `Contact`、深度は `r`、法線は任意の単位ベクトル |

### 基本のテスト

```cpp
// test_circle_circle.cpp
#include "CppUnitTest.h"
#include "test_helpers.h"
#include "collision/narrow/circle_circle.h"

using namespace Microsoft::VisualStudio::CppUnitTestFramework;
using collision::Circle;
using collision::Vec2;

namespace collision_tests {

TEST_CLASS(CircleCircle) {
public:
    TEST_METHOD(離れた円は交差しないこと) {
        const Circle a{{0.0f, 0.0f}, 1.0f};
        const Circle b{{3.0f, 0.0f}, 1.0f};   // 中心間 3、半径の和 2

        Assert::IsFalse(collision::overlaps(a, b));
        Assert::IsFalse(collision::intersect(a, b).has_value());
    }

    TEST_METHOD(めり込んだ円の深度が正しいこと) {
        const Circle a{{0.0f, 0.0f}, 1.0f};
        const Circle b{{1.5f, 0.0f}, 1.0f};   // 中心間 1.5、半径の和 2 → 深度 0.5

        const auto c = collision::intersect(a, b);
        Assert::IsTrue(c.has_value());
        check_contact_invariants(*c);

        expect_near(0.5f, c->depth);
        expect_near(Vec2{1.0f, 0.0f}, c->normal);      // A から B へ、+X 方向
        expect_near(Vec2{1.0f, 0.0f}, c->point);       // A の表面上
    }

    TEST_METHOD(法線がAからBへ向いていること) {
        // 8 方向すべてで確認する
        const Circle a{{0.0f, 0.0f}, 1.0f};
        for (int i = 0; i < 8; ++i) {
            const float ang = static_cast<float>(i) * std::numbers::pi_v<float> / 4.0f;
            const Vec2 dir{std::cos(ang), std::sin(ang)};
            const Circle b{dir * 1.5f, 1.0f};

            const auto c = collision::intersect(a, b);
            Assert::IsTrue(c.has_value());
            check_contact_invariants(*c);
            expect_near(dir, c->normal, 1.0e-5f, 1.0e-5f);
        }
    }

    TEST_METHOD(同心の円でも法線が単位長であること) {
        const Circle a{{5.0f, 5.0f}, 1.0f};
        const Circle b{{5.0f, 5.0f}, 2.0f};   // 完全に同じ中心

        const auto c = collision::intersect(a, b);
        Assert::IsTrue(c.has_value());
        check_contact_invariants(*c);       // ここで NaN と非単位長を検出する

        expect_near(3.0f, c->depth);        // 半径の和がそのまま深度
    }

    TEST_METHOD(内包された円の深度が半径の和から距離を引いた値であること) {
        const Circle big  {{0.0f, 0.0f}, 10.0f};
        const Circle small{{1.0f, 0.0f},  1.0f};

        const auto c = collision::intersect(big, small);
        Assert::IsTrue(c.has_value());
        check_contact_invariants(*c);

        expect_near(10.0f, c->depth);       // 11 - 1
        Assert::IsTrue(collision::contains(big, small));
    }
};

} // namespace collision_tests
```

**すべてのテストで `check_contact_invariants` を呼んでいる**点に注目してほしい。第 7.7 節で作ったヘルパである。個々のテストが検証したいことに加えて、共通の不変条件を毎回チェックする。

同心のテストで、この習慣が効く。もし 8.3 節の対処を入れ忘れていたら、`normal` は `NaN` になる。`check_contact_invariants` の (1) がそれを検出し、「Contact に非有限値が含まれる」という明確なメッセージを出す。深度の検証（`expect_near(3.0f, c->depth)`）だけだったら、深度は `NaN` でないので通ってしまい、バグを見逃す。

### 性質ベースのテスト

具体値の検証に加えて、性質を検証する（第 3.5 節の原則 2）。

```cpp
        Rng rng(202);
        for (int i = 0; i < 5000; ++i) {

                           rng.uniform(0.5f, 2.0f)};
            const Circle b{{rng.uniform(-3.0f, 3.0f), rng.uniform(-3.0f, 3.0f)},

```

単調性のテストで許容誤差 `1e-6f` を加えているのは、境界近傍で深度が微小に揺れうるためである。「厳密に単調」ではなく「誤差の範囲で単調」を検証している。

### 退化入力のテスト

第 5 章と第 6 章の議論が、ここで実を結ぶ。

```cpp
TEST_CLASS(CircleCircleDegenerate) {
public:
    TEST_METHOD(半径ゼロの円が点として振る舞うこと) {
        const Circle point{{0.5f, 0.0f}, 0.0f};
        const Circle c    {{0.0f, 0.0f}, 1.0f};

        const auto r = collision::intersect(c, point);
        Assert::IsTrue(r.has_value());
        check_contact_invariants(*r);
        expect_near(0.5f, r->depth);       // 1.0 - 0.5
    }

    TEST_METHOD(両方が半径ゼロで同じ位置でも破綻しないこと) {
        const Circle p1{{1.0f, 2.0f}, 0.0f};
        const Circle p2{{1.0f, 2.0f}, 0.0f};

        // d2 = 0、r = 0 なので d2 >= r*r（0 >= 0）→ 交差しない
        Assert::IsFalse(collision::intersect(p1, p2).has_value());
    }

    TEST_METHOD(極めて近い二つの円で法線がNaNにならないこと) {
        // 中心の差が min_length 未満。第 6 章の閾値が効く場面
        const Circle a{{0.0f, 0.0f},        1.0f};
        const Circle b{{1.0e-6f, 0.0f},     1.0f};

        const auto c = collision::intersect(a, b);
        Assert::IsTrue(c.has_value());
        check_contact_invariants(*c);      // NaN でないこと、単位長であること

        // 深度は半径の和にほぼ等しい（距離がゼロ扱いされるため）
        expect_near(2.0f, c->depth, 1.0e-5f, 1.0e-5f);
    }

    TEST_METHOD(非正規化数レベルの差でも破綻しないこと) {
        const Circle a{{0.0f, 0.0f},     1.0f};
        const Circle b{{1.0e-30f, 0.0f}, 1.0f};

        const auto c = collision::intersect(a, b);
        Assert::IsTrue(c.has_value());
        check_contact_invariants(*c);
    }

    TEST_METHOD(遠く離れた位置でも正しく判定できること) {
        // 原点から 10km。float の ULP が約 1mm になる領域（第 4 章）
        const Vec2 far{10000.0f, 10000.0f};
        const Circle a{far,                    1.0f};
        const Circle b{far + Vec2{1.5f, 0.0f}, 1.0f};

        const auto c = collision::intersect(a, b);
        Assert::IsTrue(c.has_value());
        check_contact_invariants(*c);

        // この距離では絶対誤差が効かないので、相対誤差で検証する
        expect_near(0.5f, c->depth, 1.0e-2f, 1.0e-3f);
    }
};
```

最後のテストが重要である。原点から 10 km 離れた場所では、座標の ULP が約 1 ミリメートルになる（第 4.1 節の表）。`10000.0f` と `10001.5f` の差を計算すると桁落ちが起き、`0.5` という深度の精度は大幅に落ちる。

**許容誤差を `1e-2f`（1 センチメートル）まで緩めている**のは、そのためである。これは「テストを通すために緩めた」のではなく、**その距離では物理的にそれ以上の精度が出ないから**である。第 4.3 節で述べた「許容誤差は根拠を持って決める」の実践例になっている。

このテストは、遠方での精度低下がどの程度かを記録する意味もある。将来オープンワールドを扱うことになったとき、ここが判断材料になる。

## この章のまとめ

- 交差判定は二乗のまま比較する。`distance_squared(a, b) < (ra + rb)²`
- 深度を求めるときだけ平方根が要る。これが `overlaps` と `intersect` を分ける根拠
- 法線は `B.center - A.center` の向き。第 7.3 節の規約どおり
- 深度は `半径の和 - 中心間距離`。接触点は A の表面上
- **退化ケース 1：中心が一致。** 法線が定義できない。`normalize_or` で任意の向きを選ぶ
- **退化ケース 2：内包。** 深度が形状の大きさを超えうる。判定側は正しい値を返し、扱いは応答側の判断
- `normalize_or` の内部閾値と `dist` の判定閾値を揃える。揃えないと不整合な `Contact` が生まれる
- テストは四系統（離れている・接触・めり込み・同心）＋性質＋退化入力
- **すべてのテストで `check_contact_invariants` を呼ぶ。** これが `NaN` を確実に捕まえる

### 落とし穴と練習問題

**落とし穴 1：`dist` を `length(d)` で求めてしまう。**　`normalize_or` の内部で使う閾値と揃わなくなる。二乗長 `d2` から一貫して導く。

**落とし穴 2：同心のケースをテストし忘れる。**　最も見落とされやすく、最も被害が大きい退化ケースである。

**落とし穴 3：接触点を `b.center - normal * b.radius` と書く。**　これは B の表面上の点である。規約は「A の表面上」なので `a.center + normal * a.radius`。両者は重なっているとき一致しない。

**練習問題 8-1**　8.3 節の対処を外して（`normalize_or` を単純な `d / dist` に戻して）、同心のテストを走らせてみよう。どのアサーションが、どういうメッセージで落ちるだろうか。`check_contact_invariants` があるおかげで診断がどう改善されているかを確認してほしい。

**練習問題 8-3**　円と点（半径ゼロの円ではなく `Vec2`）の判定関数 `intersect(const Circle&, Vec2)` を書こう。戻り値の型と法線の向きの規約はどうすべきか。第 7 章の規約を点に対してどう解釈するか考えてみてほしい。
