# 第4章 はじめての Natvis

準備が整いました。この章で初めて `.natvis` に中身を書きます。

扱うのは `<DisplayString>` ひとつだけですが、あわせて**開発ループの回し方**を身につけます。Natvis は試行錯誤の道具なので、「書いて、見て、直す」を速く回せるかどうかが、その後の学習速度をそのまま決めます。

## 4.1 3行書く

第2章で作った `vizkit\vizkit.natvis` を開き、`<Type>` を1つ足します。

```xml
<?xml version="1.0" encoding="utf-8"?>
<AutoVisualizer xmlns="http://schemas.microsoft.com/vstudio/debugger/natvis/2010">

  <Type Name="vizkit::point2">
    <DisplayString>({x}, {y})</DisplayString>
  </Type>

</AutoVisualizer>
```

読み方はそのままです。

- `<Type Name="...">` ―― **どの型に**適用するか。**名前空間を含む完全修飾名**で書く
- `<DisplayString>` ―― 値列に**何を表示するか**
- `{x}` ―― 中括弧の中は**式**。ここでは `this->x` のことなので、単に `x` と書けばよい
- 中括弧の外はリテラル。`(`、`, `、`)` はそのまま出力される

F5 でデバッグ実行します（`main.cpp` は第3章のものをそのまま使います）。

```
名前          値                              型
──────────────────────────────────────────────────────────
  p           (12.500000000000000, -4.000000000000000)   vizkit::point2
▷ box         {_min=(0.0..., 0.0...) _max=(640.0..., 480.0...) }   vizkit::rect
▷ pts         {(0.000..., 0.000...), (1.000..., 0.000...), ...}    vizkit::point2[4]
```

3つのことが同時に起きました。

**(1) `p` の表示が変わった。** `{x=12.500000 y=-4.000000 }` から `(12.5..., -4.0...)` になりました。

**(2) `box` の中の `point2` にも自動的に適用された。** `rect` には何も書いていないのに、そのメンバーである `_min` / `_max` の表示が変わっています。Natvis は**型に対して**適用されるので、その型が現れる場所すべてに効きます。

**(3) 配列の要素にも適用された。** `pts` の各要素も新しい表示になっています。

この波及効果が Natvis の費用対効果を高くしている部分です。よく使う小さな型に1つ Natvis を書くと、その型を含むあらゆる表示が改善されます。

## 4.2 桁数を整える

とはいえ `12.500000000000000` は冗長です。`double` の既定表示は有効桁数を最大限見せる形式なので、座標のような用途には向きません。

書式指定子 `g`（指数表記と固定小数点の短いほう）を使います。

```xml
<Type Name="vizkit::point2">
  <DisplayString>({x,g}, {y,g})</DisplayString>
</Type>
```

`{式,指定子}` という書き方は、第3章でウォッチウィンドウに打ち込んだ `color.r,d` とまったく同じ構文です。ウォッチ式で使える指定子は、`DisplayString` の中でもそのまま使えます。

結果：

```
  p           (12.5, -4)          vizkit::point2
```

狙いどおりです。書式指定子の一覧は第6章でカタログとしてまとめます。ここでは「ウォッチで試した指定子はそのまま Natvis に持ち込める」ことだけ押さえてください。

## 4.3 .natvisreload ―― 高速な開発ループ

いま、この修正のためにデバッグを停止してビルドし直しましたか？ その必要はありません。

**デバッグを継続したまま** `.natvis` を編集して保存し、**イミディエイトウィンドウ**（デバッグ > ウィンドウ > イミディエイト、Ctrl+Alt+I）で次を実行します。

```
.natvisreload
```

```
Natvis ファイルが再読み込みされました。
```

ウォッチウィンドウの表示が即座に更新されます。ビルドもデバッグの再起動も不要です。

これが Natvis 開発の基本ループになります。

```
   ┌─────────────────────────────────────────┐
   │ 1. ブレークポイントで止める              │
   │ 2. ウォッチウィンドウで式を試す          │
   │ 3. うまくいった式を .natvis に写す       │
   │ 4. 保存して .natvisreload                │
   │ 5. 表示を確認 → 気に入らなければ 2 へ    │
   └─────────────────────────────────────────┘
```

第6部の `CustomListItems` のような複雑な定義を書くときは、このループを何十回も回すことになります。いま慣れておいてください。

> **補足：自動で更新されることもある**
> ソリューション内の `.natvis` を保存すると、Visual Studio が自動的にローカル／ウォッチウィンドウを更新することがあります。ただし確実ではないので、「変えたのに反映されない」と思ったら `.natvisreload` を打つ、と覚えておくのが安全です。
>
> なお、**PDB に埋め込まれた** `.natvis`（第40章）はデバッグ中に変更できません。開発中はプロジェクト内のファイルとして扱うのが基本です。

## 4.4 診断メッセージを有効にする

Natvis の最も不親切な性質は、**間違っていても黙っている**ことです。型名を打ち間違えただけで、ルールは静かに無視されます。「書いたのに何も起きない」で30分溶かすのは、Natvis 初学者の通過儀礼のようなものですが、避けられます。

診断メッセージを有効にしてください。

1. **ツール > オプション**
2. **デバッグ > 全般** を選択
3. 下のほうの **「出力ウィンドウ」> 「全般出力設定」** の中にある
4. **「Natvis 診断メッセージ (C++ のみ)」** を **Error** / **Warning** / **Verbose** のいずれかに変更

学習中は **Verbose** を推奨します。読み込まれたファイル、マッチした型、評価に失敗した式が、すべて**出力**ウィンドウ（「デバッグ」表示）に流れます。実務では **Error** か **Warning** にしておくと、ノイズが減ります。

設定したらデバッグを再起動し、出力ウィンドウを見てください。

```
Natvis: C:\...\vizkit\vizkit.natvis を読み込んでいます。
Natvis: 型 'vizkit::point2' の視覚化が見つかりました。
```

**「読み込んでいます」の行が出ないなら、そもそもファイルがデバッガに届いていません。** 第2章の「項目の種類 = Natvis」を見直してください。

## 4.5 わざと壊して、診断を読む

診断メッセージの読み方を先に体験しておきます。3つの典型的な失敗を、意図的に作ります。

### 失敗1：型名の名前空間を忘れる

```xml
<Type Name="point2">          <!-- vizkit:: が抜けている -->
  <DisplayString>({x,g}, {y,g})</DisplayString>
</Type>
```

`.natvisreload` すると、表示は素の `{x=12.500000 y=-4.000000 }` に戻ります。出力ウィンドウには……**何も出ません**。

これが Natvis の一番いやらしいところです。型名がマッチしないのは「エラー」ではなく「該当なし」なので、警告すら出ないのです。

**教訓：表示がまったく変わらないときは、まず型名を疑う。** ウォッチウィンドウで変数の「型」列に出ている文字列を、そのままコピーして `Name` に貼るのが確実です。

### 失敗2：存在しないメンバーを参照する

```xml
<Type Name="vizkit::point2">
  <DisplayString>({x,g}, {z,g})</DisplayString>   <!-- z は存在しない -->
</Type>
```

`.natvisreload` すると、こちらは違う症状になります。

```
  p           <エラー: 識別子 "z" が定義されていません>    vizkit::point2
```

出力ウィンドウにも診断が出ます。

```
Natvis: 型 'vizkit::point2' の DisplayString の評価に失敗しました:
        識別子 "z" が定義されていません
```

**式の評価エラーは、ちゃんと報告されます。** 型名のマッチ失敗（沈黙）と、式の評価失敗（エラー表示）は、まったく別の症状として現れる。この2つを区別できるようになると、切り分けが一気に速くなります。

### 失敗3：xmlns を消す

```xml
<AutoVisualizer>              <!-- xmlns 属性を削除 -->
```

`.natvisreload` すると、この `.natvis` ファイル**全体**が効かなくなります。出力ウィンドウには読み込みエラーが記録されます。

第2章で「`xmlns` の URL は1文字も間違えられない」と書いたのはこれです。

3つとも元に戻しておいてください。

## 4.6 rgba を直す ―― 文字か数値か

第2章で気になっていた `rgba` の表示に取りかかります。

```
▷ color     {r=204 'Ì' g=102 'f' b=51 '3' a=255 'ÿ' }    vizkit::rgba
```

`std::uint8_t` は `unsigned char` の別名なので、デバッガが「文字」として解釈しています。色成分としては意味がありません。書式指定子 `d` で10進整数に固定します。

```xml
<Type Name="vizkit::rgba">
  <DisplayString>RGBA({r,d}, {g,d}, {b,d}, {a,d})</DisplayString>
</Type>
```

```
  color       RGBA(204, 102, 51, 255)         vizkit::rgba
  transparent RGBA(0, 0, 0, 0)                vizkit::rgba
```

読めるようになりました。

> **`typedef` には当たらない、を実感する**
> ここで「`std::uint8_t` に Natvis を当てて常に10進表示にすればいいのでは」と考えたくなります。できません。`std::uint8_t` は `unsigned char` の別名（typedef）であり、Natvis は typedef にも基本型にもマッチしないからです（第1章 1.5節）。
> **表示を直せるのは、それを含む構造体の側だけ**です。これは制約であると同時に、Natvis の設計思想でもあります。意味は文脈が決めるのであって、`unsigned char` という型が決めるわけではない、ということです。

## 4.7 rect ―― 計算した値を見せる

最後に、`rect` に Natvis を当てます。ここで初めて「メンバーをそのまま出す」以上のことをします。

第3章の演習で、ウォッチウィンドウで `box._max.x - box._min.x` が `640` を返すことを確認しました。その式をそのまま持ち込みます。

```xml
<Type Name="vizkit::rect">
  <DisplayString>[{_min}, {_max}] {_max.x - _min.x,g}x{_max.y - _min.y,g}</DisplayString>
</Type>
```

```
  box         [(0, 0), (640, 480)] 640x480       vizkit::rect
  degenerate  [(5, 5), (5, 9)] 0x4                vizkit::rect
```

2つのポイントがあります。

**(1) `{_min}` は再帰的に評価される。** `_min` は `point2` なので、`point2` の `DisplayString` が適用されて `(0, 0)` になります。Natvis の定義はこうして合成されます。

**(2) 式の中で計算ができる。** `width()` は呼べませんが、`_max.x - _min.x` は書けます。第3章で述べた「アクセサではなく生メンバーから式を組む」を実際にやったことになります。

### Condition の予告

`degenerate` の表示が `0x4` になっています。幅が 0 の矩形なので、本来は「空である」と分かるほうが親切です。`Condition` 属性を使うと、条件に応じて表示を切り替えられます。

```xml
<Type Name="vizkit::rect">
  <DisplayString Condition="_max.x &lt;= _min.x || _max.y &lt;= _min.y">[empty]</DisplayString>
  <DisplayString>[{_min}, {_max}] {_max.x - _min.x,g}x{_max.y - _min.y,g}</DisplayString>
</Type>
```

```
  box         [(0, 0), (640, 480)] 640x480       vizkit::rect
  degenerate  [empty]                            vizkit::rect
```

`Condition` 付きの `DisplayString` を**上から順に**評価し、最初に条件が成立したものが採用されます。条件なしのものは常に成立するので、**フォールバックとして必ず最後に置きます**。

ここで XML の作法が1つ。`<` は XML では使えないので `&lt;` と書きます。`>` はそのまま書けますが、対称性のために `&gt;` と書く流儀もあります。`&` は `&amp;` です。この地味なエスケープは Natvis を書いていると頻繁に出てくるので、いま慣れておいてください。

| 書きたい記号 | XML での表記 |
|---|---|
| `<` | `&lt;` |
| `>` | `&gt;`（そのままでも可） |
| `&` | `&amp;`（`&&` は `&amp;&amp;`） |
| `"` | `&quot;`（属性値の中） |

`Condition` の本格的な使い方は第7章で扱います。

## 4.9 Natvis の最小構造

この章で触れた構造をまとめます。

```
AutoVisualizer                    ルート要素。xmlns 必須
 └─ Type Name="完全修飾型名"       型ごとの視覚化ルール
     └─ DisplayString              値列に出す文字列
         ├─ {式}                   式を埋め込む
         ├─ {式,書式指定子}        書式を指定して埋め込む
         └─ Condition="条件式"     条件付き（上から最初に成立したものを採用）
```

以降の章では、この `<Type>` の中に `<Expand>` を足して**子行**を作り（第3部）、`<ArrayItems>` や `<CustomListItems>` でコンテナを列挙し（第4部〜第6部）、`Name` にワイルドカードを書いてテンプレートに対応させます（第7部）。骨格はここから変わりません。

## 4.10 この章のまとめ

- `<Type Name="完全修飾名">` ＋ `<DisplayString>` が Natvis の最小単位。
- `{式}` で値を埋め込み、`{式,指定子}` で書式を指定する。指定子はウォッチ式のものと共通。
- 型に対して適用されるので、**メンバーとして現れても配列の要素として現れても効く**。
- `.natvisreload`（イミディエイトウィンドウ）で、デバッグを止めずに反映できる。
- **診断メッセージは必ず有効にする**（ツール > オプション > デバッグ > 全般 > 出力ウィンドウ > Natvis 診断メッセージ）。
- **型名のマッチ失敗は沈黙し、式の評価失敗はエラーを出す。** この違いが切り分けの起点になる。
- Natvis の中では関数を呼べないが、**メンバーからの計算式は書ける**。
- XML なので `<` は `&lt;`、`&&` は `&amp;&amp;`。

## 4.11 演習

1. `point2` の `DisplayString` から `,g` を外し、`,e`（指数表記）に変えて表示を比べてください。どの用途にどれが向くか考えてみてください。
2. `rgba` の表示を `#CC6633` のような16進表記に変えようとすると、`{r,x}` では `0xcc` になってしまいます。なぜ `#` と 6 桁に揃えるのが素直に書けないか考えてみてください（答えは第6章で扱います）。
3. `rect` の `Condition` を、`_max.x &lt; _min.x` のように `<` で書いた場合、`degenerate` はどう表示されますか。理由を説明してください。
4. `.natvis` の `<Type Name="vizkit::rect">` を `<Type Name="vizkit::Rect">` に変えて `.natvisreload` し、**出力ウィンドウに何も出ないこと**を確認してください。この「沈黙」を体験しておくことが、この章で最も重要な演習です。
