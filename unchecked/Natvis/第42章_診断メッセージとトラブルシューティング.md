# 第42章 診断メッセージとトラブルシューティング

Natvis のデバッグは、Natvis そのものよりも時間を食うことがあります。エラーが出ないケースが多く、症状から原因を推測する必要があるためです。

この章では、本書の各章で散発的に扱ってきた切り分け手法を、**症状別の逆引き**としてまとめます。実務で最も参照回数が多くなる章です。

## 42.1 診断メッセージを読む

第4章 4.4節で設定した項目の確認です。

**ツール > オプション > デバッグ > 全般 > 出力ウィンドウ > 全般出力設定 > Natvis 診断メッセージ (C++ のみ)**

| 設定 | 出力される内容 |
|---|---|
| `Off` | 何も出ない（既定） |
| `Error` | 式の評価失敗など、エラーのみ |
| `Warning` | エラー ＋ 警告 |
| `Verbose` | **ファイルの読み込み、型のマッチ、すべての評価** |

**Natvis を書いている間は `Verbose`、通常のデバッグでは `Error` か `Warning`。** これが実務的な設定です。`Verbose` はノイズが多く、通常のデバッグでは出力ウィンドウが埋まります。

出力ウィンドウは **デバッグ > ウィンドウ > 出力**、表示は「デバッグ」を選びます。

### 出力の3種類

```
Natvis: C:\dev\vizkit\vizkit\vizkit.natvis を読み込んでいます。
```
**読み込みの記録。** これが出ないファイルはデバッガに届いていません（第39章 39.8節）。

```
Natvis: 型 'vizkit::dynamic_array<int>' の視覚化が見つかりました。
```
**マッチの記録。** どの型にどの定義が当たったか。

```
Natvis: 型 'vizkit::point2' の DisplayString の評価に失敗しました:
        識別子 "z" が定義されていません
```
**評価エラー。** 式が間違っている場合に出ます。

## 42.2 症状別逆引き

### 症状1：まったく表示が変わらない。エラーも出ない

**最頻出の症状です。** 原因は型がマッチしていないか、ファイルが届いていないかのどちらかです。

```
1. 出力ウィンドウに「読み込んでいます」が出ているか
   → 出ていない : ファイルが届いていない（症状2へ）
   → 出ている   : 2 へ

2. ウォッチウィンドウの「型」列と Type Name を1文字ずつ照合する
   - 名前空間は完全修飾か（vizkit:: を忘れていないか）
   - テンプレート引数の個数は合っているか
   - &lt; &gt; のエスケープは正しいか

3. 他のファイルの定義に負けていないか（症状5へ）
```

第29章 29.4節のチェックリストと同じです。**型名のコピーは「型」列から**（第29章 29.1節）。

### 症状2：ファイルが読み込まれない

```
1. 項目の種類 = Natvis になっているか（第2章 2.5節、第40章 40.1節）
2. xmlns の URL が正確か
   http://schemas.microsoft.com/vstudio/debugger/natvis/2010
   → 1文字でも違えばファイル全体が無視される
3. XML として妥当か
   → &lt; &gt; &amp; のエスケープ漏れ
   → タグの閉じ忘れ
4. ファイルの文字エンコーディング
   → UTF-8 で保存されているか（非 ASCII 文字を使っている場合）
5. 配置場所は正しいか（第39章）
   → VS 2026 のユーザーフォルダは Documents\Visual Studio 18\Visualizers
```

**XML の妥当性は、Visual Studio の XML エディタで開けば分かります。** `.natvis` を開くと、構文エラーが波線で表示されます。第45章 45.2節で扱う XSD 検証を設定しておくと、要素名や属性名の誤りまで検出できます。

### 症状3：`<エラー: ...>` と表示される

**これは良い症状です。** 原因がメッセージに書いてあります。

| メッセージ | 原因 |
|---|---|
| 識別子 "xxx" が定義されていません | メンバー名の誤り。`[Raw View]` で確認する |
| 式にはクラス型が必要です | キャストの誤り、`$T1` を値として使っている |
| アクセス違反 | null ポインタを読んでいる。`Condition` でガードする（第7章 7.4節） |
| 関数の評価にはすべてのスレッドを実行する必要があります | 関数を呼ぼうとしている（第5章 5.5節） |

多くは第5章・第7章で扱った制約に帰着します。

### 症状4：展開したときだけおかしい

`DisplayString` は正しいのに、開くと空になる、あるいはエラーになる。

```
1. Expand の中にも Condition を付けたか
   → DisplayString だけ守っても、Item が未初期化領域を読む（第34章 34.5節）

2. Size と実際の出力件数が食い違っていないか
   → CustomListItems の Size は「出力件数」（第25章 25.3節）

3. ArrayItems / CustomListItems の Condition が全部外れていないか
   → SBO のような分岐で、どちらも false になると黙って空になる（第18章 18.7節）

4. CustomListItems のループが途中で止まっていないか
   → 式の評価失敗でループは黙って終わる（第23章 23.6節）
```

### 症状5：期待と違う定義が使われている

複数の `.natvis` が同じ型を定義している場合です。

```
1. 診断メッセージ（Verbose）で、どのファイルが読み込まれているか一覧する
2. 疑わしいファイルを一時的にリネームして読み込まれないようにする
3. 表示が変われば、そのファイルが原因
```

**二分探索が有効です。** ファイルが多い場合、半分をリネームして切り分けを繰り返します。

優先順位の理解も必要です。

- **ファイル間の優先順位は配置場所で決まる**（第39章 39.1節）
- **`Priority` はファイルをまたがない**（第31章 31.2節）
- **同じファイル内では、先に書いたものが使われる**（第31章 31.1節）

### 症状6：デバッガが固まる / 極端に遅い

```
1. 無限ループになっていないか
   → CustomListItems にカウンタの Break を入れる（第23章 23.7節）
   → 循環リストで Size を省略していないか（第20章 20.3節）

2. 壊れた値で巨大な件数を表示しようとしていないか
   → Size を Condition 付きで2つ並べ、上限で打ち切る（第19章 19.5節）
   → _size > 4096 のようなガードを入れる（第9章 9.4節）

3. 要素数が多いのに CustomListItems を使っていないか
   → 専用要素に切り替える、またはビューで分ける（第28章 28.4節）
```

**固まったら、まず疑うのは無限ループと巨大な件数です。**

### 症状7：Release ビルドでだけ動かない

第43章で詳しく扱います。

```
1. 最適化で変数が消えていないか
2. PDB が生成されているか（/DEBUG）
3. /NATVIS が無視されていないか（第40章 40.2節）
```

## 42.3 切り分けの道具

症状に関わらず使える道具を整理します。

### `,!` ―― Natvis を無効化する

```
box,!
```

素の表示に戻ります。**「いまの表示は Natvis が作ったのか、元からそうなのか」**を切り分けられます（第6章 6.6節）。

### `[Raw View]` ―― 生の構造を見る

Natvis の式が触れられる名前の唯一の情報源です（第3章 3.4節）。メンバー名が分からなくなったら、まずここを開きます。

### ウォッチウィンドウで式を試す

**Natvis に書く前に、ウォッチウィンドウで評価する。** 本書が第4章 4.3節から一貫して勧めている手順です。

`.natvis` に書いてから `.natvisreload` して確認するより、ウォッチウィンドウで直接試すほうが速く、エラーメッセージも詳細です。

### `.natvisreload`

イミディエイトウィンドウで実行します。デバッグを止めずに `.natvis` を再読み込みします（第4章 4.3節）。

**PDB に埋め込まれたものには効きません**（第39章 39.5節）。開発中はプロジェクト内のファイルとして扱ってください。

### プローブを仕掛ける

分からないときは表示させます。

```xml
<Item Name="[T1]">($T1*)0</Item>        <!-- $T1 の正体（第29章 29.3節） -->
<Item Name="[dbg p]">p</Item>            <!-- ループ変数（第23章 23.6節） -->
<Item Name="[sizeof]">sizeof(*this)</Item>
```

**`CustomListItems` のデバッグは、この方法が最も確実です。** 診断メッセージが限定的なためです。

## 42.4 切り分けの手順（総まとめ）

```
┌─────────────────────────────────────────────────────────┐
│ 1. 診断メッセージを Verbose にする                       │
│                                                          │
│ 2. 「読み込んでいます」が出ているか                       │
│      No  → 症状2（届いていない）                          │
│      Yes ↓                                               │
│                                                          │
│ 3. obj,! と obj を比べる                                 │
│      同じ → 型がマッチしていない（症状1）                 │
│      違う ↓ Natvis は効いている                          │
│                                                          │
│ 4. エラーが表示されているか                              │
│      Yes → メッセージを読む（症状3）                      │
│      No  ↓                                               │
│                                                          │
│ 5. 値の列は正しいが展開がおかしい                        │
│      → 症状4（Condition、Size、ループ）                   │
│                                                          │
│ 6. 別の定義が使われている疑い                            │
│      → 症状5（ファイルの二分探索）                        │
│                                                          │
│ 7. どうしても分からない                                  │
│      → プローブを仕掛けて変数を表示させる                 │
└─────────────────────────────────────────────────────────┘
```

## 42.5 予防する

トラブルを減らす習慣です。

**(1) 診断メッセージを常時 `Error` にしておく。**
オフにしていると、エラーが表示されている型に気づけません。

**(2) ウォッチで試してから `.natvis` に写す。**
第4章 4.3節の開発ループ。これだけで大半の問題を未然に防げます。

**(3) フォールバックを必ず置く。**
条件なしの `DisplayString` を最後に置くと、すべての条件が外れたときに素の表示に戻らず、`[型名]` のような印が出ます（第8章 8.7節）。**「Natvis が効いているが条件が外れた」と「Natvis が効いていない」を区別できます。**

**(4) `Optional` を付けすぎない。**
自分のライブラリで、壊れたら気づきたい箇所には付けない（第8章 8.5節）。全部に付けると、壊れても沈黙します。

**(5) `[Raw View]` を隠さない。**
`HideRawView="true"` は開発が終わった型にだけ（第13章 13.8節）。

**(6) XSD で構文を検証する。**
第45章 45.2節。要素名や属性名の誤りを、デバッグ前に検出できます。

## 42.6 この章のまとめ

- 診断メッセージは **Natvis を書いている間は `Verbose`、通常は `Error` か `Warning`**。
- 出力は3種類 ―― **読み込みの記録・マッチの記録・評価エラー**。
- **「まったく変わらない、エラーも出ない」が最頻出。** 型のマッチかファイルの到達を疑う。
- **`<エラー: ...>` は良い症状。** 原因がメッセージに書いてある。
- **展開したときだけおかしい**なら、`Item` の `Condition`、`Size` の意味、分岐の網羅、ループの停止を確認する。
- **固まったら無限ループと巨大な件数を疑う。** カウンタの `Break` と `Size` の上限打ち切り。
- 切り分けの道具は **`,!` / `[Raw View]` / ウォッチウィンドウ / `.natvisreload` / プローブ**。
- 手順は「**Verbose → 読み込み確認 → `,!` と比較 → エラー確認 → 展開の確認 → ファイルの二分探索 → プローブ**」。
- 予防は「**診断は常時オン、ウォッチで試してから写す、フォールバックを置く、`Optional` を付けすぎない、`[Raw View]` を隠さない、XSD で検証**」。

## 42.7 演習

1. 本書のここまでで作った `vizkit.natvis` の型名を1つ意図的に壊し、症状1のチェックリストに従って原因を特定するまでの時間を計ってください。
2. `xmlns` の URL の末尾を `2011` に変え、出力ウィンドウにどんなエラーが出るか確認してください。
3. `CustomListItems` の `<Exec>` を1つ削除して無限ループを作り、`MaxItemsPerView="10"` を指定した場合としない場合で挙動を比べてください。
4. ユーザーフォルダとプロジェクト内の両方に、同じ型を違う表示で定義する `.natvis` を置き、症状5の二分探索でどちらが使われているかを特定してください。
5. 42.4節の手順を印刷するか、チームの Wiki に貼ってください。実務で最も使う1ページになります。
