# 第20章 双方向リストと番兵ノードの罠

前章のリストは NULL 終端でした。実用的な双方向リストの多くは、**番兵（sentinel）ノード**を使って終端を表現します。

番兵は実装を単純にする一方で、Natvis を書くときの典型的なバグを2つ生みます。「1個多く出る」と「無限に辿る」です。この章では、その両方を実際に踏んでから直します。

## 20.1 型を作る

`vizkit\include\vizkit\node\list.hpp`

```cpp
#pragma once

#include <cstddef>

namespace vizkit {

// 番兵ノードを1つ持つ循環双方向リスト。
//   空のとき: _sentinel.next == _sentinel.prev == &_sentinel
//   要素があるとき: _sentinel.next が先頭、_sentinel.prev が末尾
// 番兵の value は決して使われない。
template <class T>
class list {
public:
    struct node {
        node* next = nullptr;
        node* prev = nullptr;
        T     value{};
    };

    list() noexcept { _sentinel.next = &_sentinel; _sentinel.prev = &_sentinel; }
    ~list() { clear(); }

    list(const list&) = delete;
    list& operator=(const list&) = delete;

    void push_back(const T& v) {
        node* n = new node{ &_sentinel, _sentinel.prev, v };
        _sentinel.prev->next = n;
        _sentinel.prev = n;
        ++_size;
    }

    void clear() noexcept {
        node* p = _sentinel.next;
        while (p != &_sentinel) { node* nx = p->next; delete p; p = nx; }
        _sentinel.next = &_sentinel;
        _sentinel.prev = &_sentinel;
        _size = 0;
    }

    [[nodiscard]] std::size_t size() const noexcept { return _size; }

private:
    node        _sentinel{};
    std::size_t _size = 0;
};

} // namespace vizkit
```

`main.cpp`：

```cpp
#include <vizkit/node/list.hpp>
// ...
    vizkit::list<int> dl;
    dl.push_back(10);
    dl.push_back(20);
    dl.push_back(30);

    vizkit::list<int> dl_empty;
```

## 20.2 罠その1 ―― 番兵が1個多く出る

前章と同じ感覚で書いてみます。

```xml
<!-- 間違い -->
<Type Name="vizkit::list&lt;*&gt;">
  <DisplayString>{{ size={_size} }}</DisplayString>
  <Expand>
    <LinkedListItems>
      <HeadPointer>&amp;_sentinel</HeadPointer>
      <NextPointer>next</NextPointer>
      <ValueNode>value</ValueNode>
    </LinkedListItems>
  </Expand>
</Type>
```

```
     [0]        0          ← 番兵の value（意味のないゴミ）
     [1]        10
     [2]        20
     [3]        30
     [4]        0          ← 番兵に戻ってきた
     [5]        10         ← 2 周目
     ...
```

2つの問題が同時に起きています。

**(1) 番兵自身が要素として並んでいる。** `HeadPointer` に番兵を渡したので当然です。

**(2) 循環しているので終わらない。** `Size` を書かなかったため、デバッガは NULL に当たるまで辿ろうとしますが、循環リストには NULL がありません。

実際には、デバッガ側の内部上限で止まるか、ウォッチウィンドウが長時間応答しなくなります。**これは Natvis を書いていて最も体力を削られる失敗**なので、原因をはっきり理解しておいてください。

## 20.3 直す ―― HeadPointer は「最初の実要素」

修正は2点です。

```xml
<Type Name="vizkit::list&lt;*&gt;">
  <DisplayString Condition="_size == 0">[empty]</DisplayString>
  <DisplayString>{{ size={_size} }}</DisplayString>
  <Expand>
    <Item Name="[size]" ExcludeView="simple">_size</Item>
    <LinkedListItems>
      <Size>_size</Size>
      <HeadPointer>_sentinel.next</HeadPointer>
      <NextPointer>next</NextPointer>
      <ValueNode>value</ValueNode>
    </LinkedListItems>
  </Expand>
</Type>
```

```
▷ dl             { size=3 }
     [size]      3
     [0]         10
     [1]         20
     [2]         30
```

**(1) `HeadPointer` は `&_sentinel` ではなく `_sentinel.next`。** つまり「番兵の次」＝最初の実要素です。

**(2) `Size` を必ず書く。** 循環リストでは `Size` が終端の役割を果たします。`_size` 個だけ辿ったら止まります。

原則としてまとめます。

> **循環リストでは `Size` は省略できない。** NULL 終端でないため、辿る回数を外から与えるしかない。

空リストのときは `_sentinel.next == &_sentinel` なので、`HeadPointer` は番兵自身を指します。しかし `Size` が 0 なので1つも辿られません。破綻しません。

## 20.4 なぜ std::list はこう書かれているのか

MSVC の `std::list` は、同じ構造を持っています。`STL.natvis` を見ると、こう書かれています。

```xml
<LinkedListItems>
  <Size>_Mypair._Myval2._Mysize</Size>
  <HeadPointer>_Mypair._Myval2._Myhead-&gt;_Next</HeadPointer>
  <NextPointer>_Next</NextPointer>
  <ValueNode>_Myval</ValueNode>
</LinkedListItems>
```

`_Myhead->_Next` ―― やはり「番兵の次」です。本章で書いたものと構造が完全に一致しています。

**番兵を使う双方向リストの Natvis は、実装が誰であっても同じ形になります。** `std::list` の定義を読めるようになったことを確認しておいてください。

## 20.5 罠その2 ―― ValueNode に this と書くと

第19章で「`ValueNode` に `this` を書くとノードそのものが値になる」と学びました。双方向リストでこれをやると、危険な表示になります。

```xml
<ValueNode>this</ValueNode>
```

```
   ▷ [0]        {next=0x... prev=0x... value=10 }
        ▷ next  {next=0x... prev=0x... value=20 }
           ▷ next ...                                  ← いくらでも潜れる
        ▷ prev  {next=0x... prev=0x... value=0 }        ← 番兵
```

ノードを開くと `next` と `prev` が出てくるので、**リスト全体を何度でも辿り直せてしまいます**。しかも `prev` を辿れば番兵に出られ、その中身は意味のないゴミです。

`forward_list` でも同じことは起きますが、双方向リストでは `prev` があるぶん混乱が倍になります。

対策は、**ノードの型に Natvis を当てて、値だけを見せる**ことです。

```xml
<Type Name="vizkit::list&lt;*&gt;::node">
  <DisplayString>{value}</DisplayString>
  <Expand>
    <Item Name="value">value</Item>
    <Item Name="[next]" IncludeView="detail">next</Item>
    <Item Name="[prev]" IncludeView="detail">prev</Item>
  </Expand>
</Type>
```

`next` / `prev` を `IncludeView="detail"` に閉じ込めました。既定ビューでは値しか見えず、リンク構造を追いたいときだけ `,view(detail)` で開けます。

**入れ子クラスにも Natvis を当てられる**という点も、ここで押さえてください。`vizkit::list&lt;*&gt;::node` のように `::` でつなげます。次章の `bst` では、この技法が主役になります。

## 20.6 壊れたリストからデバッガを守る

リストのバグを追っているとき、リストはたいてい壊れています。壊れたリストは Natvis にとって危険です。

### 不変条件を書く

`list` の不変条件は次のとおりです。

- `_sentinel.next` と `_sentinel.prev` は常に非 NULL
- 空なら `_sentinel.next == &_sentinel`
- `_size == 0` と `_sentinel.next == &_sentinel` は同値

これらを `DisplayString` に落とします。

```xml
<DisplayString Condition="_sentinel.next == nullptr || _sentinel.prev == nullptr">[corrupt: sentinel has null links]</DisplayString>
<DisplayString Condition="_size == 0 &amp;&amp; _sentinel.next != &amp;_sentinel">[corrupt: size=0 but list is not empty]</DisplayString>
<DisplayString Condition="_size != 0 &amp;&amp; _sentinel.next == &amp;_sentinel">[corrupt: size={_size} but list is empty]</DisplayString>
<DisplayString Condition="_size == 0">[empty]</DisplayString>
<DisplayString>{{ size={_size} }}</DisplayString>
```

第15章・第17章・第18章と同じパターンです。**不変条件を Natvis に書き込むと、デバッガが不変条件チェッカーになる。** 第5部でもこの方針を続けます。

### 上限で打ち切る

`_size` そのものが壊れている場合に備えて、第19章 19.5節の複数 `Size` を使います。

```xml
<LinkedListItems>
  <Size Condition="_size &lt;= 10000">_size</Size>
  <Size>10000</Size>
  <HeadPointer>_sentinel.next</HeadPointer>
  <NextPointer>next</NextPointer>
  <ValueNode>value</ValueNode>
</LinkedListItems>
```

`_size` に `0xCCCCCCCC` が入っていても、10000 件で止まります。デバッガが固まりません。

### 双方向の整合性をチェックする

双方向リストには「`a->next->prev == a`」という不変条件もあります。これはノードごとのチェックなので、ノードの型に書きます。

```xml
<Type Name="vizkit::list&lt;*&gt;::node">
  <DisplayString Condition="next != nullptr &amp;&amp; next->prev != this">[!broken link] {value}</DisplayString>
  <DisplayString>{value}</DisplayString>
  <Expand>
    <Item Name="value">value</Item>
    <Item Name="[!]" Condition="next != nullptr &amp;&amp; next->prev != this">"next->prev != this"</Item>
    <Item Name="[next]" IncludeView="detail">next</Item>
    <Item Name="[prev]" IncludeView="detail">prev</Item>
  </Expand>
</Type>
```

リストの途中でリンクが壊れていれば、**その要素の行にだけ `[!broken link]` が出ます**。100 要素のうちどこが壊れているかを、スクロールしながら目で探せる。これは実際に効きます。

**チェックはコンテナではなくノードに書く。** ノードごとに独立して判定できる条件は、ノードの `Type` に置くのが正解です。この方針は第22章の赤黒木で本格的に使います。

## 20.7 現時点の list の Natvis

```xml
  <Type Name="vizkit::list&lt;*&gt;">
    <DisplayString Condition="_sentinel.next == nullptr || _sentinel.prev == nullptr">[corrupt: null links]</DisplayString>
    <DisplayString Condition="_size == 0 &amp;&amp; _sentinel.next != &amp;_sentinel">[corrupt: size=0 but not empty]</DisplayString>
    <DisplayString Condition="_size != 0 &amp;&amp; _sentinel.next == &amp;_sentinel">[corrupt: size={_size} but empty]</DisplayString>
    <DisplayString Condition="_size == 0">[empty]</DisplayString>
    <DisplayString>{{ size={_size} }}</DisplayString>

    <Expand>
      <Item Name="[size]" ExcludeView="simple">_size</Item>
      <Item Name="[front]" ExcludeView="simple" Condition="_size != 0">_sentinel.next->value</Item>
      <Item Name="[back]"  ExcludeView="simple" Condition="_size != 0">_sentinel.prev->value</Item>

      <LinkedListItems>
        <Size Condition="_size &lt;= 10000">_size</Size>
        <Size>10000</Size>
        <HeadPointer>_sentinel.next</HeadPointer>
        <NextPointer>next</NextPointer>
        <ValueNode>value</ValueNode>
      </LinkedListItems>

      <Synthetic Name="[reverse]" IncludeView="detail" Condition="_size != 0">
        <DisplayString>末尾から辿った結果</DisplayString>
        <Expand>
          <LinkedListItems>
            <Size Condition="_size &lt;= 10000">_size</Size>
            <Size>10000</Size>
            <HeadPointer>_sentinel.prev</HeadPointer>
            <NextPointer>prev</NextPointer>
            <ValueNode>value</ValueNode>
          </LinkedListItems>
        </Expand>
      </Synthetic>
    </Expand>
  </Type>

  <Type Name="vizkit::list&lt;*&gt;::node">
    <DisplayString Condition="next != nullptr &amp;&amp; next->prev != this">[!broken link] {value}</DisplayString>
    <DisplayString>{value}</DisplayString>
    <Expand>
      <Item Name="value">value</Item>
      <Item Name="[!]" Condition="next != nullptr &amp;&amp; next->prev != this">"next->prev != this"</Item>
      <Item Name="[next]" IncludeView="detail">next</Item>
      <Item Name="[prev]" IncludeView="detail">prev</Item>
    </Expand>
  </Type>
```

`[reverse]` に注目してください。`NextPointer` に `prev` を書けば、**同じ `LinkedListItems` で逆順に辿れます**。順方向と逆方向の結果が食い違えば、リンクの片方向だけが壊れていることが分かります。

## 20.8 この章のまとめ

- **番兵を使うリストでは、`HeadPointer` に番兵ではなく「番兵の次」を書く。** `&_sentinel` ではなく `_sentinel.next`。
- **循環リストでは `Size` を省略できない。** NULL がないため、辿る回数を外から与えるしかない。
- `std::list` の `STL.natvis` も `_Myhead->_Next` と書いている。構造は同じ。
- `ValueNode` に `this` を書くと、`next` / `prev` からリスト全体を何度でも辿れてしまう。**ノードの型に Natvis を当て、リンクは `IncludeView="detail"` に閉じ込める**。
- 入れ子クラスには `Type Name="外側&lt;*&gt;::内側"` で Natvis を当てられる。
- **ノードごとに判定できる不変条件は、コンテナではなくノードの `Type` に書く。** 壊れた要素の行にだけ印が出る。
- `Size` を `Condition` 付きで2つ並べ、異常値のときに上限で打ち切る。
- `NextPointer` に `prev` を書けば逆順ビューが作れる。順逆の食い違いで片方向の破損を検出できる。

## 20.9 演習

1. `HeadPointer` を `&amp;_sentinel` に戻し、番兵が `[0]` として並ぶことを確認してください。そのうえで `Size` を消し、デバッガの挙動を観察してください（重くなるので、確認したらすぐ戻してください）。
2. デバッガから `dl` の2番目のノードの `next->prev` を書き換え、`[!broken link]` がその要素にだけ出ることを確認してください。
3. `dl,view(detail)` で `[reverse]` を開き、`30, 20, 10` の順に並ぶことを確認してください。
4. `_size` を `5` に書き換え、`LinkedListItems` が番兵を越えて2周目に入ることを確認してください。`Size` が実態と一致していることが前提だという意味を体感できます。
5. `vizkit::list&lt;*&gt;::node` の Natvis を削除し、`ValueNode` を `this` に変えたときの表示と比べてください。
