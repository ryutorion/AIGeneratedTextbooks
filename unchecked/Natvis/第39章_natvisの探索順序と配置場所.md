# 第39章 natvis ファイルの探索順序と配置場所

第9部に入ります。ここからは、**書いた Natvis を届ける**段階です。

どんなに良い Natvis を書いても、デバッガに読み込まれなければ何も起きません。しかも第4章 4.5節で見たとおり、読み込まれていないことはエラーとして現れません。この章では、デバッガがどこを探しているかを正確に把握します。

## 39.1 5つの場所と優先順位

デバッガは、次の順に `.natvis` を探します。**上にあるものが優先されます。**

```
1. デバッグ中の .pdb に埋め込まれた .natvis
     ただし、同名のファイルがプロジェクトにあればそちらが優先される

2. 読み込まれている C++ プロジェクト内の .natvis

3. VSIX パッケージ経由でインストール・登録された .natvis

4. ユーザー別ディレクトリ
     %USERPROFILE%\Documents\Visual Studio 18\Visualizers

5. システム全体のディレクトリ
     <Visual Studio インストール先>\Common7\Packages\Debugger\Visualizers
```

第31章 31.2節で述べた `Priority` 属性は、**この順序を覆しません**。仕様の言葉では「特定のファイルまたはディレクトリ内で」優先度が効く、とされています。ファイルをまたぐ優先順位は、この5段階で決まります。

## 39.2 Visual Studio 2026 のユーザーフォルダ

**ここが最も間違えやすい点です。**

Visual Studio 2019 / 2022 では、ユーザー別のビジュアライザーフォルダは次の場所でした。

```
%USERPROFILE%\Documents\Visual Studio 2019\Visualizers
%USERPROFILE%\Documents\Visual Studio 2022\Visualizers
```

**Visual Studio 2026 では、内部バージョン番号を使った名前に変わっています。**

```
%USERPROFILE%\Documents\Visual Studio 18\Visualizers
```

Visual Studio 2026 の内部バージョンが 18 だからです。西暦ベースの名前を期待して `Visual Studio 2026\Visualizers` を作っても、読み込まれません。

このフォルダは**自動では作られないことがあります**。存在しなければ、手で作ってください。

```
> mkdir "%USERPROFILE%\Documents\Visual Studio 18\Visualizers"
```

### ユーザーフォルダの用途

ここに置いた `.natvis` は、**そのユーザーのすべてのプロジェクトに適用されます**。

向いている用途：

- 自分だけが使うデバッグ用の一時的な Natvis
- チームで共有していない、個人的な `Priority="High"` の上書き
- 他人のライブラリに対して自分用に書いた Natvis

向いていない用途：

- **チームで共有すべき Natvis。** 他の人の環境には存在しません
- **ライブラリに付属すべき Natvis。** 利用者に届きません

チームで共有するなら、次節以降の方法を使ってください。

## 39.3 システム全体のディレクトリ

```
<Visual Studio インストール先>\Common7\Packages\Debugger\Visualizers
```

第27章 27.1節で `STL.natvis` を読んだ場所です。同じディレクトリに `concurrency.natvis`、`atlmfc.natvis`、`winrt.natvis` などがあります。

**ここに自分のファイルを置いてはいけません。**

- Visual Studio の更新で消えるか、上書きされる
- 管理者権限が必要
- そのマシンのすべてのプロジェクトに影響する
- チームの他のメンバーには届かない

読むためだけの場所だと考えてください。

## 39.4 プロジェクト内 ―― 開発中の基本

**開発中は、これが最も扱いやすい場所です。**

`.natvis` をプロジェクトに追加し、項目の種類を `Natvis` にする（第2章 2.5節）だけで、そのソリューションをデバッグしているときに読み込まれます。

利点：

- **`.natvisreload` で即座に反映できる**（第4章 4.3節）。PDB 埋め込みではこれができません
- ソース管理に入るので、チームで共有できる
- 特別なビルド設定が要らない

本書がここまで、`vizkit` プロジェクトに `vizkit.natvis` を置いてきたのはこの理由です。

### 「読み込まれているプロジェクト」の意味

デバッグ中のソリューションに含まれる C++ プロジェクトなら、実行しているプロジェクトでなくても読み込まれます。`vizkit`（静的ライブラリ）に置いた `.natvis` が、`playground`（実行可能ファイル）のデバッグで効いているのがその例です。

ただし、**ソリューションに含まれていないライブラリの Natvis は届きません**。NuGet や vcpkg で入れたライブラリのプロジェクトはソリューションにないので、その `.natvis` は読み込まれません。これが次章の PDB 埋め込みが必要になる理由です。

## 39.5 PDB 埋め込み ―― 配布の本命

`.natvis` の内容を `.pdb` に埋め込むと、**ライブラリの利用者に自動的に届きます**。プロジェクトを開いていなくても、`.natvis` ファイルを配らなくても、デバッガが PDB から読み取ります。

```
1. デバッグ中の .pdb に埋め込まれた .natvis
```

優先順位が最上位である点にも注目してください。ライブラリ作者が意図した表示が、既定で使われます。

ただし条件があります。

> 同名のファイルがプロジェクトにあれば、そちらが優先されます。

つまり利用者は、**同じ名前の `.natvis` を自分のプロジェクトに置くことで上書きできます**。作者の意図を尊重しつつ、利用者に逃げ道を残す設計になっています。第31章 31.4節で述べた「優先度は譲る方向に設計する」という発想が、仕様のレベルで実現されているわけです。

そしてもう1つ重要な制約があります。**PDB に埋め込まれた `.natvis` は、デバッグ中に変更できません。** `.natvisreload` の対象外です。

したがって実務的な運用はこうなります。

> **開発中はプロジェクト内のファイルとして扱い、配布時に PDB へ埋め込む。**

埋め込みの具体的な手順は第40章で扱います。

## 39.6 VSIX

Visual Studio 拡張として `.natvis` を配布する方法です。優先順位は3番目です。

社内共通のライブラリ群があり、多数のソリューションで使われている、といった場合には選択肢になります。ただし VSIX の作成・配布・更新のコストがかかるので、**まず PDB 埋め込みを検討してください**。

第38章 38.5節で触れた「`Expression` を省略した `Intrinsic`」を実装したい場合は、VSIX が必須になります。

## 39.7 どこに置くべきか

用途ごとに整理します。

| 状況 | 置き場所 |
|---|---|
| 開発中（自分のライブラリを書いている） | **プロジェクト内** |
| ライブラリを配布する | **PDB 埋め込み**（第40章） |
| チームで共有する（ライブラリではない） | プロジェクト内 ＋ ソース管理 |
| 自分だけの一時的な実験 | ユーザー別ディレクトリ |
| 他人のライブラリに自分用の Natvis を書いた | ユーザー別ディレクトリ、または自分のプロジェクト内 |
| 社内共通・多数のソリューションで使う | VSIX |
| （どんな場合も） | **システム全体のディレクトリには置かない** |

## 39.8 読み込まれているか確認する

第4章 4.4節で有効にした診断メッセージが、ここでも中心的な道具です。

**ツール > オプション > デバッグ > 全般 > 出力ウィンドウ > Natvis 診断メッセージ (C++ のみ)** を `Verbose` にすると、読み込みが出力ウィンドウに記録されます。

```
Natvis: C:\dev\vizkit\vizkit\vizkit.natvis を読み込んでいます。
Natvis: C:\Program Files\...\Visualizers\STL.natvis を読み込んでいます。
Natvis: C:\Users\...\Documents\Visual Studio 18\Visualizers\mytest.natvis を読み込んでいます。
```

**「読み込んでいます」の行が出ないファイルは、デバッガに届いていません。** 表示が変わらないときに最初に確認すべきことです。

読み込まれているのに表示が変わらないなら、原因は型名のマッチか、他のファイルの定義に負けているかのどちらかです（第29章 29.4節、第42章）。

### どのファイルの定義が使われたか

`Verbose` にすると、型ごとにどの定義がマッチしたかも記録されます。

```
Natvis: 型 'vizkit::dynamic_array<int>' の視覚化が見つかりました。
```

複数のファイルが同じ型を定義している場合、この記録が切り分けの手がかりになります。疑わしいファイルを一時的にリネームして読み込まれないようにし、表示が変わるかを見る、という二分探索も有効です（第42章 42.6節）。

## 39.9 複数のソリューションで同じ型を扱う

実務でよくある状況です。ライブラリ `vizkit` を、複数のアプリケーションから使っているとします。

**選択肢1：各ソリューションに `vizkit` プロジェクトを含める。**
`.natvis` はプロジェクト内にあるので自動的に読み込まれます。ソースからビルドする運用なら、これが最も簡単です。

**選択肢2：PDB に埋め込んで配布する。**
`vizkit.lib` と `vizkit.pdb` をバイナリ配布する運用なら、これが正解です。第40章で扱います。

**選択肢3：`.natvis` ファイルを配って、各自でユーザーフォルダに置いてもらう。**
動きますが、更新のたびに全員に配り直す必要があります。**避けたほうがよい運用**です。

## 39.10 この章のまとめ

- 探索順序は **PDB 埋め込み > プロジェクト内 > VSIX > ユーザー別 > システム全体**。
- **`Priority` 属性はこの順序を覆さない。** ファイル間の優先順位は配置場所で決まる。
- **Visual Studio 2026 のユーザーフォルダは `Documents\Visual Studio 18\Visualizers`。** 西暦ではなく内部バージョン 18。存在しなければ手で作る。
- **システム全体のディレクトリには置かない。** 更新で消え、管理者権限が要り、チームに届かない。読むための場所。
- **開発中はプロジェクト内が基本。** `.natvisreload` が使えるのが決定的。
- **配布は PDB 埋め込み。** 優先順位が最上位で、利用者は同名ファイルで上書きできる。ただし**デバッグ中に変更できない**。
- 運用の原則は「**開発中はプロジェクト内、配布時に PDB へ埋め込む**」。
- **診断メッセージを `Verbose` にして「読み込んでいます」の行を確認する。** 出ないファイルは届いていない。

## 39.11 演習

1. `%USERPROFILE%\Documents\Visual Studio 18\Visualizers` を作り、`point2` の `DisplayString` を変える `.natvis` を置いてください。プロジェクト内の定義とどちらが優先されるか確認してください。
2. 診断メッセージを `Verbose` にして、デバッグ開始時に読み込まれるファイルの一覧を出力ウィンドウで確認してください。`STL.natvis` を含め、いくつのファイルが読み込まれているか数えてみてください。
3. `vizkit.natvis` の「項目の種類」を `Natvis` から `なし` に変え、読み込まれなくなることを診断メッセージで確認してください。
4. ユーザーフォルダの `.natvis` に `Priority="Low"` を、プロジェクト内の同じ型に `Priority` なし（Medium）を指定し、どちらが使われるか確認してください。`Priority` がファイル間で効かないことの確認です。
5. `<Visual Studio インストール先>\Common7\Packages\Debugger\Visualizers` を開き、どんなファイルが置かれているか一覧してください。`STL.natvis` 以外に何があるかを見ておくと、他のライブラリのデバッグで役立ちます。
