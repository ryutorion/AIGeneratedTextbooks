# 第22章 赤黒木を見やすくする

前章の `bst` は平衡化しませんでした。実用的な木は赤黒木や AVL 木で平衡を保ちます。

赤黒木は `TreeItems` で列挙できる点では `bst` と変わりません。違うのは、**ノードが持つ情報が増える**ことと、**守るべき不変条件が複雑になる**ことです。この章では、その両方を Natvis に落とします。

## 22.1 型を作る

`vizkit\include\vizkit\node\rb_tree.hpp`

```cpp
#pragma once

#include <cstddef>
#include <cstdint>

namespace vizkit {

enum class rb_color : std::uint8_t { red = 0, black = 1 };

// 赤黒木。挿入時の回転・再彩色は省略せずに実装する想定だが、
// ここでは Natvis の題材として必要な構造だけを示す。
template <class K, class V>
class rb_tree {
public:
    struct node {
        node*    left   = nullptr;
        node*    right  = nullptr;
        node*    parent = nullptr;
        rb_color color  = rb_color::red;
        K        key{};
        V        value{};
    };

    rb_tree() = default;
    ~rb_tree() { destroy(_root); }

    rb_tree(const rb_tree&) = delete;
    rb_tree& operator=(const rb_tree&) = delete;

    void insert(const K& k, const V& v);   // 実装は省略（回転・再彩色を行う）

    [[nodiscard]] std::size_t size() const noexcept { return _size; }

private:
    static void destroy(node* n) noexcept {
        if (!n) return;
        destroy(n->left); destroy(n->right); delete n;
    }

    node*       _root = nullptr;
    std::size_t _size = 0;
};

} // namespace vizkit
```

`bst` との差は3つです。`parent` ポインタ、`color`、そして根が必ず黒になるという規則。

## 22.2 列挙そのものは bst と同じ

`TreeItems` の書き方は前章と変わりません。

```xml
<Type Name="vizkit::rb_tree&lt;*,*&gt;">
  <DisplayString Condition="_root == nullptr">[empty]</DisplayString>
  <DisplayString>{{ size={_size} }}</DisplayString>
  <Expand>
    <Item Name="[size]" ExcludeView="simple">_size</Item>
    <TreeItems>
      <Size Condition="_size &lt;= 10000">_size</Size>
      <Size>10000</Size>
      <HeadPointer>_root</HeadPointer>
      <LeftPointer>left</LeftPointer>
      <RightPointer>right</RightPointer>
      <ValueNode>this</ValueNode>
    </TreeItems>
  </Expand>
</Type>
```

**列挙の仕組みは木の種類に依存しません。** 赤黒木だろうが AVL 木だろうが、`left` と `right` があれば `TreeItems` で中順に並びます。

この章の本題は、そこから先 ―― **ノードをどう見せるか**です。

## 22.3 色を表示する

`rb_color` は enum です。素のままだと数値が出ます。

```
     [0]        {left=... color=black (1) key=20 ... }
```

第6章 6.7節の書式指定子 `en` を使うと、列挙子の名前だけになります。

```xml
<Type Name="vizkit::rb_tree&lt;*,*&gt;::node">
  <DisplayString>[{color,en}] {key} =&gt; {value}</DisplayString>
</Type>
```

```
     [0]        [black] 20 => "twenty"
     [1]        [red] 30 => "thirty"
     [2]        [black] 40 => "forty"
```

しかし、これでも色が目立ちません。木のバランスを目で追うときは、**赤と黒が一目で区別できる**ほうが役に立ちます。記号を使います。

```xml
<Type Name="vizkit::rb_tree&lt;*,*&gt;::node">
  <DisplayString Condition="color == vizkit::rb_color::red">● {key} =&gt; {value}</DisplayString>
  <DisplayString>○ {key} =&gt; {value}</DisplayString>
</Type>
```

```
     [0]        ○ 20 => "twenty"
     [1]        ● 30 => "thirty"
     [2]        ○ 40 => "forty"
     [3]        ○ 50 => "fifty"
     [4]        ● 60 => "sixty"
     [5]        ○ 70 => "seventy"
```

赤が偏っているかどうかが、スクロールしながら分かります。

`Condition` の中で `vizkit::rb_color::red` と**完全修飾名**で書いている点に注意してください。スコープ付き enum の列挙子は、Natvis でも完全修飾が必要です。うまくいかない場合は数値で `color == 0` と書いても構いませんが、実装側で値の割り当てを変えたときに壊れます。

## 22.4 親ポインタを見せる ―― 無限に潜らせない

`parent` があると、木を上にも辿れます。便利ですが、Natvis では危険です。

```xml
<!-- 危険 -->
<Item Name="[parent]">parent</Item>
```

`[parent]` を開くと親ノードが出て、その `[parent]` を開くと祖父が出て……そして親の `left` を開けば元のノードに戻ってきます。**上下に無限に行き来できてしまう**。

対策は、**ノードそのものではなく、識別できる情報だけを見せる**ことです。

```xml
<Item Name="[parent]" Condition="parent != nullptr">parent->key</Item>
<Item Name="[parent]" Condition="parent == nullptr">"(root)"</Item>
```

```
   ▷ [3]           ○ 50 => "fifty"
        key        50
        value      "fifty"
        [parent]   "(root)"

   ▷ [1]           ● 30 => "thirty"
        key        30
        value      "thirty"
        [parent]   50
```

`parent->key` はスカラー値なので、それ以上開けません。木の構造を追うには十分な情報でありながら、再帰の入り口を塞いでいます。

**「開けるものを渡さない」というのは、Natvis における再帰対策の基本形**です。第12章 12.4節の `,nd` も、第20章 20.5節の `IncludeView="detail"` も、同じ発想でした。

## 22.5 不変条件をノードに書く

赤黒木の不変条件のうち、**ノード単体で判定できるもの**があります。第20章 20.6節で確立した方針どおり、それらはノードの `Type` に書きます。

| 不変条件 | 判定できる場所 |
|---|---|
| 根は黒 | コンテナ |
| 赤ノードの子は赤でない | **ノード**（自分と子を見れば分かる） |
| 親の子が自分である | **ノード**（自分と親を見れば分かる） |
| 左の子のキー < 自分のキー < 右の子のキー | **ノード** |
| 任意の葉までの黒の数が等しい | どちらでも書けない（ループが要る） |

上から4つを書きます。

```xml
<Type Name="vizkit::rb_tree&lt;*,*&gt;::node">
  <Intrinsic Name="is_red" Expression="color == vizkit::rb_color::red" />

  <Intrinsic Name="bad_red_child"
             Expression="is_red() &amp;&amp; ((left  != nullptr &amp;&amp; left->color  == vizkit::rb_color::red)
                                     || (right != nullptr &amp;&amp; right->color == vizkit::rb_color::red))" />

  <Intrinsic Name="bad_parent_link"
             Expression="parent != nullptr &amp;&amp; parent->left != this &amp;&amp; parent->right != this" />

  <Intrinsic Name="bad_order"
             Expression="(left  != nullptr &amp;&amp; !(left->key  &lt; key))
                      || (right != nullptr &amp;&amp; !(key &lt; right->key))" />

  <Intrinsic Name="has_violation" Expression="bad_red_child() || bad_parent_link() || bad_order()" />

  <DisplayString Condition="has_violation()">[!] {is_red() ? "●" : "○"} {key} =&gt; {value}</DisplayString>
  <DisplayString Condition="is_red()">● {key} =&gt; {value}</DisplayString>
  <DisplayString>○ {key} =&gt; {value}</DisplayString>

  <Expand>
    <Item Name="[!] red-red"     Condition="bad_red_child()">"赤ノードの子が赤です"</Item>
    <Item Name="[!] parent link" Condition="bad_parent_link()">"parent->left/right のどちらも this ではありません"</Item>
    <Item Name="[!] order"       Condition="bad_order()">"探索木の順序が壊れています"</Item>

    <Item Name="key">key</Item>
    <Item Name="value">value</Item>
    <Item Name="color">color,en</Item>
    <Item Name="[parent]" Condition="parent != nullptr">parent->key</Item>
    <Item Name="[parent]" Condition="parent == nullptr">"(root)"</Item>
    <Item Name="[left]"   IncludeView="detail">left</Item>
    <Item Name="[right]"  IncludeView="detail">right</Item>
  </Expand>
</Type>
```

回転処理にバグがあれば、**壊れたノードの行にだけ `[!]` が付きます**。木全体を眺めながら、問題のある場所を目で探せる。

```
   ▷ [0]        ○ 20 => "twenty"
   ▷ [1]        ● 30 => "thirty"
   ▷ [2]        [!] ● 40 => "forty"      ← ここが壊れている
   ▷ [3]        ○ 50 => "fifty"
```

`Intrinsic` を細かく分けているのは、**条件と表示の両方から同じ判定を参照する**ためです（第7章 7.6節）。判定式を1か所に定義しておけば、記号を変えたくなっても診断メッセージを増やしたくても、直す場所が散らばりません。

### 根が黒か ―― コンテナ側で見る

根の色は、木全体を見なければ判定できません。コンテナの `Type` に書きます。

```xml
<Type Name="vizkit::rb_tree&lt;*,*&gt;">
  <DisplayString Condition="_root != nullptr &amp;&amp; _root->color == vizkit::rb_color::red">[!] {{ size={_size} }} 根が赤です</DisplayString>
  <DisplayString Condition="_root == nullptr &amp;&amp; _size != 0">[corrupt: size={_size} but root is null]</DisplayString>
  <DisplayString Condition="_root == nullptr">[empty]</DisplayString>
  <DisplayString>{{ size={_size} }}</DisplayString>
  ...
```

**判定に必要な情報がある場所に、チェックを置く。** ノードで完結する条件はノードへ、木全体を見る条件はコンテナへ。この切り分けが、Natvis で不変条件を扱うときの設計原則です。

## 22.6 黒高さは書けない ―― CustomListItems への橋渡し

残る不変条件「任意の葉までの黒ノードの数が等しい」は、この章の道具では書けません。

理由は明快で、**Natvis の式にはループがない**からです。各パスの黒の数を数えるには、根から葉まで辿る必要があります。三項演算子を深く入れ子にすれば固定深さまでは書けますが、実用になりません。

```xml
<!-- 深さ 3 までしか見られない。実用にならない -->
<Item Name="[bh?]">(_root->color == vizkit::rb_color::black ? 1 : 0)
                 + (_root->left == nullptr ? 0 : (_root->left->color == ... ))</Item>
```

これができるようになるのが、第6部で扱う **`<CustomListItems>`** です。`<Variable>` で変数を宣言し、`<Loop>` で繰り返し、`<Exec>` で値を更新できます。

```xml
<!-- 第23章以降で書けるようになる形（先取り） -->
<CustomListItems>
  <Variable Name="p" InitialValue="_root" />
  <Variable Name="bh" InitialValue="0" />
  <Loop Condition="p != nullptr">
    <If Condition="p->color == vizkit::rb_color::black">
      <Exec>bh = bh + 1</Exec>
    </If>
    <Exec>p = p->left</Exec>
  </Loop>
  <Item Name="[black height]">bh</Item>
</CustomListItems>
```

第5部で扱った `LinkedListItems` / `TreeItems` は、「決まった形のデータ構造を辿る」ための宣言的な要素でした。**形が決まっていない構造や、辿りながら計算が必要な場合には、手続き的な `CustomListItems` が要る。** その境界がここです。

## 22.7 std::map の実装と比べる

MSVC の `std::map` は赤黒木です。ノードの `[Raw View]` を開くと、次のようなメンバーが見えます。

```
_Left       ← 本書の left
_Parent     ← 本書の parent
_Right      ← 本書の right
_Color      ← 本書の color
_Isnil      ← 番兵かどうか
_Myval      ← key と value の pair
```

本書の `rb_tree` とほぼ同じ構造です。違うのは `_Isnil` があること ―― `std::map` は NULL の代わりに番兵ノードを使うためです（第21章 21.7節）。

```xml
<HeadPointer>_Myhead-&gt;_Parent</HeadPointer>
<ValueNode Condition="!((bool)_Isnil)">_Myval</ValueNode>
```

もし本書の `rb_tree` を番兵方式に変更するなら、同じ2点の対応が必要になります。

- `HeadPointer` を一段間接にする
- `ValueNode` に「番兵でないこと」の `Condition` を付ける

`_Color` の値の割り当て（赤が 0 か 1 か）は実装の内部事情なので、**ウォッチウィンドウで実物を確認してください**。本書の `rb_color` は `red = 0, black = 1` としていますが、これは決まりではありません。他人のライブラリに Natvis を書くときは、必ず実データで確かめる ―― 第3章から一貫している姿勢です。

## 22.8 第5部のまとめ

第19章から第22章までで、ポインタで繋がれた構造の可視化を扱いました。

```
LinkedListItems      リンクリストを辿る
 ├─ Size             要素数（省略可。循環リストでは必須）
 ├─ HeadPointer      最初のノード         ← コンテナの文脈
 ├─ NextPointer      次のノード           ← ノードの文脈
 └─ ValueNode        値（空 or this でノード自身） ← ノードの文脈

TreeItems            二分木を中順に辿る
 ├─ Size             要素数
 ├─ HeadPointer      根                   ← コンテナの文脈
 ├─ LeftPointer      左の子               ← ノードの文脈
 ├─ RightPointer     右の子               ← ノードの文脈
 └─ ValueNode        値                   ← ノードの文脈
```

第5部を通じての要点は3つでした。

1. **評価の文脈が2つある。** コンテナとノードを取り違えると動かない。
2. **番兵と循環に注意する。** `HeadPointer` は「番兵の次」、`Size` は省略しない。
3. **不変条件は判定できる場所に置く。** ノードで完結するものはノードの `Type` へ。

そして最後に、この道具立ての限界が見えました。**ループが必要な処理は書けない。** 次の第6部は、その限界を超えるための章です。

## 22.9 この章のまとめ

- 列挙の仕組み（`TreeItems`）は木の種類に依存しない。赤黒木でも `bst` と同じ。
- enum は `,en` で名前表示になるが、**記号（`●` `○`）にすると一覧性が上がる**。スコープ付き enum の列挙子は完全修飾で書く。
- 親ポインタは**ノードそのものではなくキーだけを見せる**。「開けるものを渡さない」のが再帰対策の基本形。
- ノード単体で判定できる不変条件（赤-赤、親リンク、順序）は**ノードの `Type`** に、木全体を見る条件（根は黒）は**コンテナの `Type`** に書く。
- 判定は `Intrinsic` に分けて定義し、条件・表示・診断メッセージから共通に参照する。
- **黒高さのようなループが要る計算は、この章の道具では書けない。** `CustomListItems`（第6部）が必要。
- `std::map` は番兵方式の赤黒木。`HeadPointer` の一段間接と `ValueNode` の `Condition` が、その帰結。

## 22.10 演習

1. `DisplayString` の `●` / `○` を `[R]` / `[B]` に変え、どちらが一覧しやすいか比べてください。等幅フォントでの見え方も確認してください。
2. デバッガから任意のノードの `color` を `red` に書き換え、`[!] red-red` が該当するノードにだけ出ることを確認してください。
3. `[parent]` を `parent`（ノードそのもの）に変え、上下に無限に潜れることを確認してください。確認したら戻してください。
4. `bad_order()` の判定を `left->key &lt; key` から `left->key &lt;= key` に変えると何が変わるか考えてください。重複キーを許す木ではどちらが正しいでしょうか。
5. `rb_tree` を番兵方式（NULL の代わりに共有の nil ノードを使う）に変更し、`HeadPointer` と `ValueNode` をどう書き換える必要があるか実際に試してください。
