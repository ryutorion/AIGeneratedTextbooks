# 第1章 Natvis とは何か

## 1.1 デバッガはあなたの型を知らない

C++ でライブラリを書いていると、必ずこの瞬間が来ます。

自分で設計したコンテナにバグがある。ブレークポイントを張って、ウォッチウィンドウでその中身を見ようとする。しかし表示されるのは、あなたが「見たいもの」ではありません。

デバッガが知っているのは、PDB に記録された**メモリレイアウト**だけです。「この構造体には `double` が2つ並んでいる」「このメンバーは `T*` 型のポインタである」――そこまでは分かる。しかし「その2つの `double` は座標である」とか「そのポインタは要素数 `_size` の配列の先頭を指している」といった**意味**は、どこにも書かれていません。

Natvis は、その欠けている意味をデバッガに教えるための仕組みです。

## 1.2 素の表示はどれくらい読みにくいのか

段階を追って見てみましょう。以下はすべて、本書で作っていくライブラリ **vizkit** の型です（実装は次章以降で書きます）。

### 段階1：単純な構造体

```cpp
vizkit::point2 p{ 12.5, -4.0 };
```

ウォッチウィンドウ：

```
名前     値                             型
──────────────────────────────────────────────────
▷ p      {x=12.500000 y=-4.000000 }     vizkit::point2
```

これはまだ読めます。メンバーが2つしかなく、名前も短く、値も数値だからです。デバッガは既定で「メンバーを順に並べる」という表示を作ってくれます。

ただし、これが `point2` の配列100個になった途端、`{x=12.500000 y=-4.000000 }` という冗長さが効いてきます。`(12.5, -4)` と出てほしい。

### 段階2：ポインタと長さを持つ型

```cpp
vizkit::dynamic_array<int> v;
v.push_back(10);
v.push_back(20);
v.push_back(30);
```

```
名前     値                                                      型
────────────────────────────────────────────────────────────────────────────
▷ v      {_begin=0x000001f4a2c31240 {10} _end=0x000001f4a2c3124c ...}   vizkit::dynamic_array<int>
   ▷ _begin   0x000001f4a2c31240 {10}     int *
   ▷ _end     0x000001f4a2c3124c {...}    int *
   ▷ _cap     0x000001f4a2c31250 {...}    int *
```

一気に厳しくなりました。要素が3つ入っているという事実すら見えません。`_begin` を展開しても、デバッガはポインタの**先頭1個**しか見せてくれない。10 は見えるが、20 と 30 は見えない。

要素数を知るには、頭の中で `(_end - _begin)` を計算するか、ウォッチウィンドウに `v._begin, [3]` と手で打ち込む必要があります。デバッグのたびに毎回です。

### 段階3：内部に複雑な構造を持つ型

```cpp
vizkit::chain_map<std::string, int> m;   // チェイン法のハッシュマップ
m.insert("apple", 3);
m.insert("banana", 7);
m.insert("cherry", 1);
```

```
名前     値                                            型
──────────────────────────────────────────────────────────────────────
▷ m      {_buckets=0x000001f4a2c33a80 {_head=0x0...} _bucket_count=8 _size=3 ...}
   ▷ _buckets       0x000001f4a2c33a80 {_head=0x0000000000000000}   vizkit::detail::bucket *
     _bucket_count  8                                              unsigned __int64
     _size          3                                              unsigned __int64
   ▷ _hasher        {...}                                          std::hash<std::string>
```

もはや、何ひとつ分かりません。`apple` も `banana` も `cherry` も画面上のどこにもない。実際にキーと値を見ようとすれば、バケット配列を手でたどり、空でないバケットを探し、その `_head` から `_next` を追って……という作業を、ウォッチウィンドウに式を打ち込みながら繰り返すことになります。

**これが Natvis を書く動機です。** `std::unordered_map` がデバッガで普通に読めるのは、MSVC が `STL.natvis` という Natvis ファイルを同梱しているからであって、C++ のコンテナが本質的に読みやすいからではありません。

## 1.3 Natvis を当てるとどうなるか

本書を最後まで進めると、同じ3つの型が次のように見えるようになります。

```
名前     値                                             型
──────────────────────────────────────────────────────────────────────
  p      (12.5, -4)                                     vizkit::point2

▷ v      { size=3 } [10, 20, 30]                        vizkit::dynamic_array<int>
     [size]        3
     [capacity]    4
     [0]           10
     [1]           20
     [2]           30
   ▷ [Raw View]    {...}

▷ m      { size=3, buckets=8 }                          vizkit::chain_map<std::string,int>
     [size]           3
     [bucket_count]   8
     [load_factor]    0.375
     ["apple"]        3
     ["banana"]       7
     ["cherry"]       1
   ▷ [Raw View]      {...}
```

`chain_map` の最後の3行に注目してください。バケット配列とノードリストという二段構造を、デバッガが自動的にたどって、**キーと値のペアとしてフラットに並べている**。これは Natvis の `CustomListItems` という機能で実現します（第6部）。

## 1.4 Natvis の正体

Natvis の実体は、拡張子 `.natvis` の**XMLファイル1枚**です。

```xml
<?xml version="1.0" encoding="utf-8"?>
<AutoVisualizer xmlns="http://schemas.microsoft.com/vstudio/debugger/natvis/2010">
  <Type Name="vizkit::point2">
    <DisplayString>({x}, {y})</DisplayString>
  </Type>
</AutoVisualizer>
```

たったこれだけで、段階1の表示が `(12.5, -4)` に変わります。

ここで押さえておきたい性質が3つあります。

**(1) アプリケーションのコードを1行も変えない**

Natvis はデバッガ側の機能です。ライブラリ本体に `operator<<` を足すのとも、`ToString()` を生やすのとも違います。リリースバイナリには一切影響しません。デバッグ表示のためだけにクラスへメンバーを足す、といった妥協が要らないということです。

**(2) 再ビルドすら不要な場合がある**

`.natvis` を編集して保存し、デバッグ中にイミディエイトウィンドウで `.natvisreload` と打てば、その場で表示が更新されます。「書く → 見る → 直す」のループが数秒で回る。これが Natvis の学習を楽にしてくれます（第4章で実際にやります）。

**(3) 宣言的である**

Natvis に書くのは「どう表示するか」であって、「どう計算するか」ではありません。書けるのは**式**であり、`Loop` や `If` はあるものの、あくまでデバッガが安全に評価できる範囲に限られます。この制約は本書を通じて何度も顔を出します。

## 1.5 Natvis が扱えるもの・扱えないもの

先に限界を知っておくと、後で無駄に悩みません。

**適用できる対象**

| 対象 | 可否 | 備考 |
|---|---|---|
| クラス・構造体 | ○ | Natvis の主戦場 |
| 共用体 | ○ | タグと組み合わせて `Condition` で分岐（第34章） |
| テンプレートクラス | ○ | ワイルドカードと `$T1` で対応（第7部） |
| enum | △ | 型そのものには当てられないが、書式指定子 `en` がある（第37章） |
| `typedef` / エイリアス | × | 別名には当たらない。**実体の型名で書く必要がある** |
| `int` などの基本型 | × | 型としては指定できない |
| 基本型へのポインタ | × | ウォッチ式の書式指定子 `,[n]` で代用する |

`typedef` に当たらないというのは、実務でよくハマる点です。`using entity_id = std::uint32_t;` に Natvis を当てて意味のある表示にする、ということはできません。この制約を回避するために「強い型（strong typedef）」として構造体でラップする、という設計判断が生まれます（第36章）。

**式として書けないこと**

- 自作関数の呼び出し（`obj.size()` は**呼べない**。`_end - _begin` のように**メンバーから計算する**）
- 副作用のある式（代入、`++`、`new`）
- 例外を投げうる処理

「関数が呼べない」は初学者が最もつまずくところです。Natvis は常に**生のメンバー変数**を出発点にします。したがって「natvis を書きやすいクラス設計」というものが存在し、それは本書の裏テーマでもあります。

## 1.6 Natvis が効くための前提

Natvis はデバッグ情報の上に成り立っています。次の条件が崩れると、正しく書いた Natvis でも期待どおりに動きません。

- **PDB が存在し、デバッガが読めていること。** 型情報がなければ、そもそも型名でのマッチができません。
- **最適化でメンバーが消えていないこと。** Release ビルドでは変数がレジスタに載ったり、構造体が分解されたりして「値を表示できません」になることがあります（第43章）。
- **型名が完全一致していること。** 名前空間を含めた完全修飾名で書きます。`point2` ではなく `vizkit::point2` です。

本書は原則として **Debug 構成**で進めます。Release との付き合い方は第43章でまとめて扱います。

## 1.7 本書の進め方

本書は「読む本」ではなく「作る本」です。全章を通して、**vizkit** という自作コンテナライブラリを1つずつ育てていきます。

各章の基本形は次のとおりです。

1. **型を実装する** ―― `ring_buffer<T, N>` を書く、など
2. **素の表示を観察する** ―― デバッガで何が見えて何が見えないかを確認する
3. **Natvis を書く** ―― その章で学ぶ機能を使って表示を作る
4. **壊して直す** ―― わざと失敗させ、診断メッセージの読み方を身につける

vizkit のディレクトリ構成は次のようになります。章が進むにつれてファイルが増えていきます。

```
vizkit/
  core/   point2, rgba, fixed_string, strong_id, flags
  seq/    fixed_array, dynamic_array, matrix, ring_buffer, small_vector, deque
  node/   intrusive_list, bst, rb_tree
  assoc/  flat_map, open_map（オープンアドレス法）, chain_map（チェイン法）
  util/   optional_like, expected_like, variant_like, ref_ptr, any_like
  vizkit.natvis    ← 本書を通して育て続ける1ファイル
```

最終的に `vizkit.natvis` は数百行になりますが、それは1章あたり10〜30行ずつ積み上げた結果です。いきなり全体を書こうとする必要はありません。

## 1.8 この章のまとめ

- デバッガはメモリレイアウトを知っているだけで、型の**意味**は知らない。
- Natvis はその意味を教えるXMLファイルであり、アプリのコードを変えず、リリースにも影響しない。
- 単純な構造体では恩恵は小さいが、**ポインタと長さで表現されるコンテナ**、**内部に複雑な構造を持つ型**では、可読性が根本的に変わる。
- `typedef` には当たらない、関数は呼べない、といった制約が最初から存在する。
- `std::unordered_map` が読めるのは `STL.natvis` のおかげであり、自作型は自分で書くしかない。
