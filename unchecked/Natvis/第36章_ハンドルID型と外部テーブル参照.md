# 第36章 ハンドル／ID 型と外部テーブル参照

ゲームエンジンやリソース管理では、ポインタの代わりに**整数のハンドル**を使う設計が広く使われています。

```cpp
using texture_id = std::uint32_t;
texture_id tex = load_texture("diffuse.png");
```

デバッガで `tex` を見ても、`4711` としか出ません。それが何のテクスチャなのかは分かりません。この章では、そこに意味を持たせる方法と、その限界を扱います。

## 36.1 typedef には Natvis を当てられない

まず制約の確認です。第1章 1.5節・第29章 29.5節で述べたとおり、`using texture_id = std::uint32_t;` に Natvis を当てることはできません。エイリアスは型ではないからです。

したがって、**ハンドルに意味のある表示を与えたければ、構造体でラップするしかありません**。

`vizkit\include\vizkit\core\strong_id.hpp`

```cpp
#pragma once

#include <cstdint>

namespace vizkit {

// タグで型を分ける「強い型」。
// texture_id と mesh_id を取り違えるとコンパイルエラーになる。
template <class Tag>
struct strong_id {
    std::uint32_t value = 0;

    [[nodiscard]] constexpr bool valid() const noexcept { return value != 0; }
    [[nodiscard]] friend constexpr bool operator==(strong_id, strong_id) noexcept = default;
};

struct texture_tag {};
struct mesh_tag {};

using texture_id = strong_id<texture_tag>;
using mesh_id    = strong_id<mesh_tag>;

} // namespace vizkit
```

**Natvis のためだけに構造体でラップするのではありません。** 型安全性という本来の利点があり、Natvis を書けるようになるのはその副産物です。とはいえ、デバッグしやすさを設計判断の材料に加えてよい、というのが本書の立場です（第33章 33.5節）。

Natvis：

```xml
<Type Name="vizkit::strong_id&lt;vizkit::texture_tag&gt;">
  <DisplayString Condition="value == 0">[none]</DisplayString>
  <DisplayString>texture#{value}</DisplayString>
</Type>

<Type Name="vizkit::strong_id&lt;vizkit::mesh_tag&gt;">
  <DisplayString Condition="value == 0">[none]</DisplayString>
  <DisplayString>mesh#{value}</DisplayString>
</Type>
```

```
  tex        texture#4711        vizkit::strong_id<vizkit::texture_tag>
  m          mesh#12             vizkit::strong_id<vizkit::mesh_tag>
  none       [none]              vizkit::strong_id<vizkit::texture_tag>
```

タグごとに `Type` を書くのは冗長ですが、**型名にタグが出るので区別できる**という利点があります。汎用の定義を1つ書いてフォールバックにしておけば、タグを増やしたときも最低限は動きます（第31章 31.7節）。

```xml
<Type Name="vizkit::strong_id&lt;*&gt;" Priority="Low">
  <DisplayString Condition="value == 0">[none]</DisplayString>
  <DisplayString>#{value}</DisplayString>
</Type>
```

## 36.2 世代カウンタ付きハンドル

実務でよく使われるのが、インデックスと世代を1つの整数に詰める形式です。解放済みのスロットが再利用されたときに、古いハンドルを検出できます。

```cpp
struct handle {
    std::uint32_t bits = 0;      // 上位 8 ビット = 世代、下位 24 ビット = インデックス
};
```

第5章 5.5節で扱った `version` と同じ、ビット分解の問題です。`Intrinsic` で名前を付けます。

```xml
<Type Name="vizkit::handle">
  <Intrinsic Name="gen"   Expression="bits >> 24" />
  <Intrinsic Name="index" Expression="bits &amp; 0xFFFFFF" />
  <DisplayString Condition="bits == 0">[null handle]</DisplayString>
  <DisplayString>[{index()}] gen={gen()}</DisplayString>
  <Expand>
    <Item Name="[index]">index()</Item>
    <Item Name="[generation]">gen()</Item>
    <Item Name="[bits]" IncludeView="detail">bits,X</Item>
  </Expand>
</Type>
```

```
  h          [17] gen=3          vizkit::handle
```

**インデックスと世代が分離されました。** 「同じインデックスなのに世代が違う」ハンドルを見つけたら、それは解放済みのスロットを指しています。

## 36.3 グローバルなテーブルを引く

ここからが本題です。`texture#4711` より、`texture#4711 "diffuse.png"` と出るほうが役に立ちます。

そのためには、ID から実体を引く必要があります。実体はグローバルなレジストリにあるとしましょう。

```cpp
namespace vizkit {

struct texture_entry {
    name32 name{};
    int    width = 0, height = 0;
};

struct texture_registry {
    texture_entry entries[4096]{};
    std::size_t   count = 0;
};

// グローバルなインスタンス
inline texture_registry g_textures;

} // namespace vizkit
```

**Natvis の式からは、グローバル変数を完全修飾名で参照できます。**

```xml
<Type Name="vizkit::strong_id&lt;vizkit::texture_tag&gt;">
  <DisplayString Condition="value == 0">[none]</DisplayString>
  <DisplayString Optional="true">texture#{value} {vizkit::g_textures.entries[value].name}</DisplayString>
  <DisplayString>texture#{value}</DisplayString>
  <Expand>
    <Item Name="[id]">value</Item>
    <Item Name="[entry]" Optional="true">vizkit::g_textures.entries[value]</Item>
  </Expand>
</Type>
```

```
  tex        texture#4711 "diffuse.png"      vizkit::strong_id<vizkit::texture_tag>
```

**ID が意味を持ちました。** これは実際に強力で、ゲームエンジンのデバッグでは体感できるほど効きます。

### なぜ Optional="true" が必要か

グローバル変数の参照は、成功するとは限りません。次のような場合に失敗します。

- **シンボルが解決できない。** 最適化で消えている、PDB に含まれていない
- **別のモジュールにある。** DLL 側のグローバルを EXE 側のコンテキストから引けないことがある
- **まだ初期化されていない。** 静的初期化の順序によっては、ブレークした時点で空

`Optional="true"` を付け、**失敗したらフォールバックの `DisplayString` に落ちる**ようにしておきます（第8章 8.7節）。ID だけでも表示されるほうが、エラーが出るよりましです。

### 引けない条件を知っておく

グローバル参照が使えない典型的な状況です。

| 状況 | 可否 |
|---|---|
| 名前空間スコープのグローバル変数 | ○（完全修飾名で参照） |
| クラスの `static` メンバー | ○（`vizkit::registry::instance` など） |
| 無名名前空間・`static` の翻訳単位ローカル変数 | △（シンボル名が装飾される。環境依存） |
| 関数内の `static` 変数 | △（同上） |
| `thread_local` 変数 | ×（どのスレッドのものか指定できない） |
| ヒープに確保され、ポインタで保持されるレジストリ | ○（ポインタ変数がグローバルなら） |
| 別 DLL のグローバル | △（モジュールを明示すれば引ける場合がある） |

**シングルトンを `static` ローカル変数（Meyers singleton）で実装していると、Natvis から引きにくくなります。** 名前空間スコープのグローバルにしておくほうが、デバッグしやすい設計です。これも「Natvis で見たいなら、見えるように作る」（第33章 33.5節）の一例です。

### モジュールを明示する

別のモジュールにあるグローバルは、モジュール名を前置して参照できることがあります。

```xml
<Item Name="[entry]" Optional="true">((vizkit::texture_registry*)&amp;renderer.dll!vizkit::g_textures)->entries[value]</Item>
```

`モジュール名!シンボル名` の形式です。ウォッチウィンドウでも同じ記法が使えるので、**まずウォッチで試してから Natvis に写す**という手順（第4章 4.3節）が特に有効です。

## 36.4 引けないときは「引くための式」を提示する

グローバル参照が使えない場合の、実務的な回避策があります。

**ウォッチウィンドウにコピーするための式を、Natvis から表示するのです。**

```xml
<Type Name="vizkit::strong_id&lt;vizkit::texture_tag&gt;">
  <DisplayString Condition="value == 0">[none]</DisplayString>
  <DisplayString Optional="true">texture#{value} {vizkit::g_textures.entries[value].name}</DisplayString>
  <DisplayString>texture#{value}</DisplayString>
  <Expand>
    <Item Name="[id]">value</Item>
    <Item Name="[entry]" Optional="true">vizkit::g_textures.entries[value]</Item>
    <Synthetic Name="[watch]" IncludeView="detail">
      <DisplayString>renderer.dll!vizkit::g_textures.entries[{value}]</DisplayString>
    </Synthetic>
  </Expand>
</Type>
```

```
tex,view(detail)
  ├ [id]      4711
  └ [watch]   renderer.dll!vizkit::g_textures.entries[4711]
```

`[watch]` の値をコピーしてウォッチウィンドウに貼れば、実体が見られます。**Natvis が自動で引けなくても、引き方を教えることはできる。**

第11章 11.2節で述べた「Natvis はチームの知識を配布する手段でもある」の、最も実用的な形です。「このハンドルの中身を見るにはこう打つ」という知識を、デバッガの画面に置いておけます。

## 36.5 ポインタを持たせるという選択肢

そもそもの設計を見直す選択肢もあります。デバッグビルドでのみ、ハンドルに実体へのポインタを持たせるのです。

```cpp
struct texture_id {
    std::uint32_t value = 0;
#ifdef VIZKIT_DEBUG_HANDLES
    const texture_entry* _debug_ptr = nullptr;   // デバッグ専用
#endif
};
```

```xml
<DisplayString Optional="true">texture#{value} {_debug_ptr->name}</DisplayString>
<DisplayString>texture#{value}</DisplayString>
```

**確実に引けます。** グローバル参照の不確実さがありません。

代償は、ハンドルのサイズが 4 バイトから 16 バイトに増えることです。ハンドルを何十万個も持つ設計なら、この代償は受け入れられません。

判断基準はこうです。

| 状況 | 選択 |
|---|---|
| ハンドルの個数が少ない（数千まで） | デバッグポインタを持たせる |
| ハンドルが大量にある / キャッシュ効率が重要 | グローバル参照 ＋ `[watch]` の提示 |
| レジストリが引けない設計になっている | まず設計を見直す |

## 36.7 この章のまとめ

- `typedef` には Natvis を当てられないので、**ハンドルに意味を持たせたければ構造体でラップする**。型安全性という本来の利点があり、Natvis はその副産物。
- タグごとに `Type` を書き、`Priority="Low"` の汎用定義をフォールバックに置く。
- ビットに詰めたハンドル（インデックス＋世代）は `Intrinsic` で分解する。**世代の食い違いが解放済みスロットの手がかりになる。**
- **Natvis の式からグローバル変数を完全修飾名で参照できる。** ID から実体を引いて表示できる。
- ただし失敗しうるので **`Optional="true"` とフォールバックを必ず置く**。
- **Meyers singleton（関数内 `static`）や `thread_local` は引きにくい。** 名前空間スコープのグローバルにしておくほうがデバッグしやすい。
- 別モジュールのシンボルは `モジュール名!シンボル名` で参照できる場合がある。**まずウォッチウィンドウで試す。**
- 引けない場合は、**ウォッチウィンドウに貼るための式を `Synthetic` で提示する**。Natvis が引けなくても、引き方は教えられる。
- デバッグビルド限定で実体へのポインタを持たせる選択肢もある。**ハンドルの個数とのトレードオフ。**

## 36.8 演習

1. `vizkit::g_textures` を定義し、Natvis からグローバル参照が動くことを確認してください。動かない場合は、まずウォッチウィンドウで `vizkit::g_textures.entries[0]` を評価して切り分けてください。
2. `g_textures` を関数内 `static`（`texture_registry& textures() { static texture_registry r; return r; }`）に変え、Natvis から引けなくなることを確認してください。
3. `Optional="true"` を外し、グローバルが引けない状態で `DisplayString` がどうなるか確認してください。
4. `handle` の `bits` に `0x03000011` を設定し、`[17] gen=3` と表示されることを確認してください。ビット幅を変えたときに `Intrinsic` の修正が1か所で済むことも確認します。
5. `strong_id<texture_tag>` と `strong_id<mesh_tag>` の変数を並べ、型名で区別できることを確認してください。`Priority="Low"` の汎用定義だけにした場合との違いも見てください。
