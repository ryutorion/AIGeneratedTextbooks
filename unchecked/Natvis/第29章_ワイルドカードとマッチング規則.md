# 第29章 ワイルドカードとマッチング規則

第7部に入ります。ここまで場当たり的に使ってきたワイルドカードと `$T1` を、正面から扱います。

Natvis が動かない原因の大半は、**型がマッチしていない**ことです。しかも第4章 4.5節で見たとおり、マッチ失敗はエラーを出さず、静かに何も起きません。この章では、マッチングの仕組みと、マッチしないときの切り分け方を体系化します。

## 29.1 型名は「型」列からコピーする

まず、最も確実な出発点を再確認します。

ウォッチウィンドウの**「型」列に表示されている文字列が、マッチさせるべき型名**です。

```
名前        値                 型
──────────────────────────────────────────────────
nums        { size=5 }         vizkit::fixed_array<int,5>
cm          { size=5 }         vizkit::chain_map<vizkit::name32,int>
```

ここから具体的な引数を `*` に置き換えれば、`Name` 属性の値が得られます。

```xml
<Type Name="vizkit::fixed_array&lt;*,*&gt;">
<Type Name="vizkit::chain_map&lt;*,*&gt;">
```

推測で書かないこと。**必ず実物の型列を見る。** 第3章から一貫している方針です。

### 3つの書き換え規則

型列の文字列から `Name` 属性を作るときの規則です。

| 型列 | `Name` 属性 |
|---|---|
| `<` | `&lt;` |
| `>` | `&gt;` |
| `&`（参照型など） | `&amp;` |

XML のエスケープです。ここを間違えると、XML パーサーがファイル全体を拒否することもあります。

## 29.2 名前空間は完全修飾

第1章 1.6節で触れたとおりです。

```xml
<!-- 動かない -->
<Type Name="fixed_array&lt;*,*&gt;">

<!-- 正しい -->
<Type Name="vizkit::fixed_array&lt;*,*&gt;">
```

`using namespace vizkit;` を書いていても関係ありません。Natvis はソースコードのスコープを知りません。**PDB に記録された完全修飾名**とだけ照合します。

入れ子の名前空間も同様です。

```xml
<Type Name="vizkit::detail::bucket_impl&lt;*&gt;">
```

## 29.3 ワイルドカードの個数

ここが本章の中心です。

**基本方針は「テンプレート引数の個数だけ `*` を書く」。**

```cpp
template <class T, std::size_t N> struct fixed_array;
```

```xml
<Type Name="vizkit::fixed_array&lt;*,*&gt;">
```

これが最も意図が明確で、`$T1` / `$T2` の対応も迷いません。

### 末尾の `*` は残りをまとめて受ける

一方で、`STL.natvis` は次のように書いています。

```xml
<Type Name="std::vector&lt;*&gt;">
<Type Name="std::unordered_map&lt;*&gt;">
```

`std::vector` の宣言は `template <class T, class Allocator> class vector;` で、引数は2つです。`std::unordered_map` に至っては5つあります。それでも `*` は1つです。

そして、これらの定義は実際に動いています。したがって、**末尾の `*` は残りの引数をまとめて受ける**ように振る舞います。

この性質は、次のような場面で便利です。

- **アロケータ引数を無視したい。** `std::vector<int>` も `std::vector<int, my_allocator<int>>` も、同じ表示でよい
- **既定引数がある。** ユーザーが省略していても、型名には現れる
- **引数の個数が将来増えるかもしれない。** ライブラリの後方互換な拡張に耐える

### では `$T2` はどうなるか

`std::vector<*>` にマッチしたとき、`$T2` は何を指すのでしょうか。アロケータでしょうか、それとも `*` が吸収した「残り全部」でしょうか。

**`STL.natvis` は、`*` が1つの定義で `$T2` を使っていません。** 意図的に避けているようにも読めます。

したがって本書の推奨はこうです。

> **`$Tn` を使うなら、テンプレート引数の個数だけ `*` を書く。**
> `*` 1つの書き方は、「引数を参照しないが、型にはマッチさせたい」場合の便利な省略形として使う。

第14章以降で `fixed_array<*,*>` や `matrix<*,*,*>` と書いてきたのは、この方針によるものです。

### 自分の環境で確かめる

ワイルドカードの細かい挙動はデバッガの実装に依存する部分があります。本書の記述を鵜呑みにせず、確かめる方法を用意しておいてください。

`$Tn` が何を指しているかを見る、簡単な仕掛けがあります。

```xml
<Type Name="vizkit::fixed_array&lt;*&gt;">
  <DisplayString>probe</DisplayString>
  <Expand>
    <Item Name="[T1]">($T1*)0</Item>
    <Item Name="[T2]">$T2</Item>
  </Expand>
</Type>
```

`($T1*)0` は「`$T1` へのヌルポインタ」です。値は `0x0` ですが、**「型」列に `$T1` が何なのかが表示されます**。

```
     [T1]       0x0000000000000000     int *
     [T2]       5                      unsigned __int64
```

`$T2` が値なら、そのまま表示されます。型なら評価に失敗してエラーになります。**`$T1` は型、`$T2` は値**という区別（第14章 14.4節）を、この方法で確認できます。

このプローブは、他人のライブラリに Natvis を書くときにも役立ちます。**分からなければ表示させて見る。** Natvis のデバッグはこれに尽きます。

## 29.4 マッチしないときのチェックリスト

「Natvis を書いたのに表示が変わらない」ときの手順です。第4章 4.4節で有効にした診断メッセージを併用します。

```
1. 診断メッセージが Verbose になっているか
   ツール > オプション > デバッグ > 全般 > 出力ウィンドウ > Natvis 診断メッセージ

2. 出力ウィンドウに「.natvis を読み込んでいます」が出ているか
   → 出ていない  : ファイルがデバッガに届いていない（第2章 2.5節、第39章）
   → 出ている    : 3 へ

3. 型名がウォッチウィンドウの「型」列と一致しているか
   → 名前空間、テンプレート引数の個数、空白の有無を1文字ずつ照合する

4. XML エスケープが正しいか
   → &lt; &gt; &amp; が生の < > & になっていないか

5. xmlns 属性が正しいか（第2章 2.5節）
   → 1文字でも違うとファイル全体が無視される

6. 他の .natvis が優先されていないか
   → 第31章（Priority）、第39章（探索順序）

7. typedef やエイリアスに当てようとしていないか
   → 29.5 節
```

**1〜5 で解決しないケースはまれです。** ほとんどは型名の打ち間違いか、ファイルが届いていないかのどちらかです。

## 29.5 typedef とエイリアステンプレートには当たらない

第1章 1.5節で触れた制約を、詳しく見ます。

```cpp
namespace vizkit {
    using int_array = fixed_array<int, 5>;                  // typedef
    template <class T> using vec4 = fixed_array<T, 4>;      // エイリアステンプレート
}
```

```xml
<!-- どちらもマッチしない -->
<Type Name="vizkit::int_array">
<Type Name="vizkit::vec4&lt;*&gt;">
```

理由は、**エイリアスは型ではないから**です。コンパイル後には実体の型名しか残りません。ウォッチウィンドウの「型」列を見れば、`vizkit::fixed_array<int,5>` と表示されているはずです。

したがって、エイリアスに固有の表示を与えたい場合は、**エイリアスではなく別の型として定義する**必要があります。

```cpp
// これなら Natvis を当てられる
struct int_array : fixed_array<int, 5> {};
```

ただしこれは Natvis のために設計を歪めることになります。**多くの場合、実体の型に当てれば十分**です。

第36章で扱う「強い型（strong typedef）」は、この制約への正面からの対応です。`using entity_id = std::uint32_t;` に意味のある表示を与えたければ、構造体でラップするしかありません。

## 29.6 入れ子クラス

第20章以降で使ってきた書き方です。

```xml
<Type Name="vizkit::list&lt;*&gt;::node">
<Type Name="vizkit::chain_map&lt;*,*&gt;::bucket">
```

外側のテンプレート引数を `*` にしたうえで、`::` でつなげます。**入れ子側の `$T1` は、外側のテンプレート引数を指します。**

```xml
<Type Name="vizkit::chain_map&lt;*,*&gt;::node">
  <DisplayString>{key} =&gt; {value}</DisplayString>
  <Expand>
    <Item Name="[key type]">($T1*)0</Item>     <!-- chain_map の K -->
  </Expand>
</Type>
```

第16章 16.4節で触れた制約をここでも思い出してください。**入れ子クラスの型も、実体化されていなければデバッグ情報に存在しません。** `chain_map<name32,int>` を使っていなければ、その `node` 型も PDB にありません。

## 29.7 可変長テンプレート

```cpp
template <class... Ts> class variant_like;
```

型列には具体的な引数が並びます。

```
v        vizkit::variant_like<int,double,vizkit::name32>
```

引数の個数が使い方によって変わるので、個数を揃えて書くことができません。**末尾の `*` に頼るしかない**場面です。

```xml
<Type Name="vizkit::variant_like&lt;*&gt;">
```

`$T1` は最初の型を指しますが、`$T2` 以降が確実に取れるかは環境依存です。第34章で `variant_like` を扱うときは、**テンプレート引数ではなく実行時のタグ（`_index`）を使って分岐する**設計にします。可変長テンプレートに Natvis を当てる現実的な方法は、これしかありません。

## 29.8 const / volatile / 参照

Natvis はクラス型に対して定義されます。`const` や参照が付いていても、指している型の Natvis が適用されます。

```
p            (12.5, -4)          vizkit::point2
cp           (12.5, -4)          const vizkit::point2
rp           (12.5, -4)          vizkit::point2 &
pp           0x... (12.5, -4)    vizkit::point2 *
```

`const vizkit::point2` のために別の `Type` を書く必要はありません。

ポインタは、アドレスの後ろに指し先の `DisplayString` が付きます。アドレスが邪魔なら、参照する側で `,na` を使います（第6章 6.6節）。

## 29.9 型名の空白に注意

MSVC の型名には、テンプレート引数の区切りに空白が入らないのが通常です。

```
vizkit::chain_map<vizkit::name32,int>          ← カンマの後に空白なし
```

しかし、入れ子のテンプレートが `>>` で終わる場合など、実装によっては空白が入ることがあります。

```
std::vector<std::vector<int> >                 ← 古い表記
```

**「型」列からコピーすれば、この問題は起きません。** 手で打つと空白の有無でハマります。第29章 29.1節の方針を守ってください。

なお、`*` は空白も含めてマッチするので、テンプレート引数の中身については心配ありません。問題になるのはワイルドカードの外側だけです。

## 29.10 この章のまとめ

- **型名はウォッチウィンドウの「型」列からコピーする。** 推測で書かない。
- `<` `>` `&` は `&lt;` `&gt;` `&amp;` にエスケープする。
- **名前空間は完全修飾。** `using namespace` は関係ない。
- 基本方針は**テンプレート引数の個数だけ `*` を書く**。`$Tn` を使うなら特にそうする。
- **末尾の `*` は残りの引数をまとめて受ける。** `std::vector<*>` が 2 引数の `vector` にマッチするのはこのため。アロケータや既定引数を無視したいときに便利。
- `($T1*)0` を `Item` に置くと、**「型」列に `$T1` の正体が出る**。分からなければ表示させて確かめる。
- **`typedef` とエイリアステンプレートには当たらない。** 実体の型に当てるか、構造体でラップする（第36章）。
- 入れ子クラスは `外側&lt;*&gt;::内側`。`$T1` は外側の引数を指す。**実体化されていなければ PDB に存在しない。**
- 可変長テンプレートは末尾 `*` に頼るしかない。**実行時のタグで分岐する設計**にするのが現実的（第34章）。
- `const` / 参照 / ポインタには、指している型の Natvis が適用される。

## 29.11 演習

1. `vizkit::fixed_array&lt;*&gt;`（`*` 1つ）と `vizkit::fixed_array&lt;*,*&gt;` の両方を試し、あなたの環境でどちらがマッチするか確認してください。両方書いた場合にどちらが使われるかも観察してください（答えは第31章）。
2. 29.3節のプローブを `chain_map<*,*>` に仕掛け、`[T1]` と `[T2]` の「型」列に何が出るか確認してください。
3. `using int_array = vizkit::fixed_array<int, 5>;` を宣言し、`vizkit::int_array` に Natvis を当てようとして失敗することを確認してください。ウォッチウィンドウの「型」列が何と表示されるかも見てください。
4. `Type Name` の `&lt;` を生の `<` に書き換えて `.natvisreload` し、出力ウィンドウにどんなエラーが出るか確認してください。ファイル全体が無視されることも確かめてください。
5. `std::vector<int>` と `std::vector<vizkit::point2>` を作り、どちらも同じ `std::vector<*>` の定義で表示されていることを確認してください。要素型が違っても1つの定義で足りることの確認です。
