# 第31章 特殊化と優先順位

ここまで、1つの型に1つの `Type` を書いてきました。実務では、**複数の定義が同じ型にマッチする**状況が普通に起こります。

- 汎用的な `my_map<*,*>` と、キーが文字列の場合だけ別扱いしたい定義
- ライブラリが提供する Natvis と、プロジェクト側で上書きしたい定義
- ライブラリのバージョンごとに構造が違う場合

この章では、その競合を制御する `Priority`、`AlternativeType`、`Version` を扱います。

## 31.1 複数マッチしたらどうなるか

まず既定の挙動を確認します。同じ型にマッチする `Type` を2つ書いてみてください。

```xml
<Type Name="vizkit::fixed_array&lt;*,*&gt;">
  <DisplayString>A: {{ size={$T2} }}</DisplayString>
</Type>

<Type Name="vizkit::fixed_array&lt;*,*&gt;">
  <DisplayString>B: {{ size={$T2} }}</DisplayString>
</Type>
```

**同じファイル内では、先に書いたほうが使われます。** この例では `A:` が表示されます。

しかしこれは、ファイル内の順序に依存する脆い規則です。複数のファイルにまたがる場合や、意図的に上書きしたい場合には使えません。そこで `Priority` が用意されています。

## 31.2 Priority 属性

```xml
<Type Name="vizkit::fixed_array&lt;*,*&gt;" Priority="High">
```

| 値 | |
|---|---|
| `High` | 最も先に検査される |
| `MediumHigh` | |
| `Medium` | **既定値** |
| `MediumLow` | |
| `Low` | 最も後に検査される |

仕様の記述は次のとおりです。

> 型のマッチングにおいて、このエントリに割り当てる優先度を指定します。**特定のファイルまたはディレクトリ内で**、優先度の高いエントリが先に検査されます。

「特定のファイルまたはディレクトリ内で」という限定に注意してください。**`Priority` はファイル間の優先順位を覆しません。** ファイル間の順序は、`.natvis` がどこに置かれているかで決まります（第39章）。

`Priority` が効くのは、**同じ場所にある複数の定義の間**です。

## 31.3 汎用と特殊化を共存させる

具体例です。`flat_map` のキーが `name32` のときだけ、名前の列を引用符なしにしたいとします。

```xml
<!-- 特殊化: キーが name32 のとき -->
<Type Name="vizkit::flat_map&lt;vizkit::name32,*&gt;" Priority="High">
  <DisplayString>{{ size={_size} }}</DisplayString>
  <Expand>
    <CustomListItems>
      <Variable Name="i" InitialValue="0" />
      <Size>_size</Size>
      <Loop Condition="i &lt; (int)_size">
        <Item Name="[{_data[i].key._buf,[_data[i].key._len]s8b}]">_data[i].value</Item>
        <Exec>i++</Exec>
      </Loop>
    </CustomListItems>
  </Expand>
</Type>

<!-- 汎用: それ以外のキー型 -->
<Type Name="vizkit::flat_map&lt;*,*&gt;">
  <DisplayString>{{ size={_size} }}</DisplayString>
  <Expand>
    <CustomListItems>
      <Variable Name="i" InitialValue="0" />
      <Size>_size</Size>
      <Loop Condition="i &lt; (int)_size">
        <Item Name="[{_data[i].key}]">_data[i].value</Item>
        <Exec>i++</Exec>
      </Loop>
    </CustomListItems>
  </Expand>
</Type>
```

**ワイルドカードの一部を具体的な型名に置き換えたものが「特殊化」です。** C++ のテンプレート特殊化と同じ発想ですが、Natvis では優先順位を自動で判定してくれません。`Priority="High"` を明示する必要があります。

とはいえ、第24章 24.4節で示した「キー型の側にビューを持たせる」方法のほうが、この例では素直です。

```xml
<Type Name="vizkit::name32" IncludeView="bare">
  <DisplayString>{_buf,[_len]s8b}</DisplayString>
</Type>
```

```xml
<Item Name="[{_data[i].key,view(bare)}]">_data[i].value</Item>
```

**特殊化はコンテナ側の定義を丸ごと複製することになる**ので、保守コストが高くなります。ビューで済むならビューを使ってください。特殊化が本当に必要なのは、**構造そのものが違う**場合です。

## 31.4 STL.natvis が MediumLow を使う理由

`STL.natvis` を調べると、`Priority` が付いているのは主に**イテレータ**の定義です。

```
std::_Vector_iterator<*>              MediumLow / Medium
std::_Array_iterator<*>               MediumLow / Medium
std::reverse_iterator<*>              Medium / MediumHigh
std::map<*>                           Medium / MediumHigh
std::unordered_map<*>                 Medium / MediumHigh
```

同じ型名に対して2つの優先度が付いた定義が並んでいます。これは、**より限定的な条件のものを高く、汎用的なものを低く**設定して、順に試させる形です。

そして、コンテナ本体（`std::vector`、`std::list`、`std::deque`）には `Priority` が付いていません。既定の `Medium` です。

ここから読み取れる実務的な指針があります。

> **ライブラリが提供する Natvis は `Medium`（既定）にしておく。**
> 利用者がプロジェクト側で `High` を指定して上書きできる余地を残すため。

自分のライブラリの Natvis に `High` を付けて回ると、利用者が上書きしづらくなります。**優先度は「譲る」方向に設計する**のが親切です。

## 31.5 AlternativeType

内部構造が同じ複数の型に、1つの定義を共有させる要素です。

```xml
<Type Name="std::unordered_map&lt;*&gt;" Priority="Medium">
  <AlternativeType Name="std::unordered_multimap&lt;*&gt;" />
  <AlternativeType Name="std::unordered_set&lt;*&gt;" />
  <AlternativeType Name="std::unordered_multiset&lt;*&gt;" />
  <DisplayString>{_List}</DisplayString>
  ...
</Type>
```

`Type` の直下、`DisplayString` より前に置きます。ワイルドカードも使えます。

`vizkit` で使えそうな場面を考えます。`open_map` と、それを set として使う `open_set` を作ったとしましょう。

```xml
<Type Name="vizkit::open_map&lt;*,*&gt;">
  <AlternativeType Name="vizkit::open_set&lt;*&gt;" />
  ...
</Type>
```

ただし注意点があります。**`$Tn` の対応が型ごとに変わります。** `open_map<K,V>` の `$T2` は値型ですが、`open_set<K>` には `$T2` がありません。`$Tn` を使っている定義を共有させるときは、この食い違いに気をつけてください。

`Optional` で吸収する手もあります（第8章 8.4節、第30章 30.6節）。

`AlternativeType` にも `Inheritable` 属性が付けられます。次章で扱います。

### 実装型とインターフェース型

`AlternativeType` のもう1つの用途が、**実装の詳細型を同じ表示にする**ことです。

```cpp
namespace vizkit {
    namespace detail { template <class T> class vector_impl { ... }; }
    template <class T> class dynamic_array : public detail::vector_impl<T> { ... };
}
```

```xml
<Type Name="vizkit::dynamic_array&lt;*&gt;">
  <AlternativeType Name="vizkit::detail::vector_impl&lt;*&gt;" />
  ...
</Type>
```

デバッガ上で `detail::vector_impl` が単独で現れる場面（イテレータの内部など）でも、同じ表示になります。

## 31.6 Version ―― モジュールのバージョンで限定する

他人のライブラリに Natvis を書くとき、**バージョンによって内部構造が変わる**問題があります。第8章 8.5節では `Optional` で吸収しましたが、より明示的な手段が `<Version>` です。

```xml
<Type Name="ThirdParty::Buffer">
  <Version Name="thirdparty.dll" Min="2.0.0.0" Max="2.9.9.9" />
  <DisplayString>{_size} bytes @ {_data}</DisplayString>
  ...
</Type>

<Type Name="ThirdParty::Buffer">
  <Version Name="thirdparty.dll" Min="3.0.0.0" />
  <DisplayString>{_len} bytes @ {_ptr}</DisplayString>
  ...
</Type>
```

- `Name` ―― モジュール名（DLL / EXE）
- `Min` / `Max` ―― バージョン範囲。**どちらも含む**

`Min` だけ、`Max` だけの指定もできます。条件に合わないモジュールの型には、この定義が適用されません。

**静的リンクのライブラリには使えません。** モジュール名で照合するので、実行中のプロセスに独立したモジュールとして存在している必要があります。自作の静的ライブラリには適用できないと考えてください。

`STL.natvis` は `Version` を使っていません。標準ライブラリは同梱の Natvis がバージョンと一緒に更新されるため、必要がないのです。**`Version` が要るのは、1つの `.natvis` で複数バージョンをサポートする場合**に限られます。

### Optional と Version の使い分け

| | `Optional` | `Version` |
|---|---|---|
| 判定 | 式が解析できるか | モジュールのバージョン |
| 対象 | ノード単位 | `Type` 全体 |
| 静的ライブラリ | 使える | **使えない** |
| 記述量 | 少ない | 定義を丸ごと複製 |
| 意図の明確さ | 低い（なぜ optional か分からない） | 高い |

実務では、**まず `Optional` で済ませ、構造が根本的に違う場合だけ `Version` で分ける**という順序が現実的です。

## 31.7 実務での優先度設計

複数の `.natvis` が関わる状況を整理します。詳しい探索順序は第39章で扱いますが、設計方針を先に示します。

```
[高]  プロジェクト固有の上書き        Priority="High"
      （特定の型だけ表示を変えたい）

      ライブラリ本体の .natvis        Priority 指定なし（Medium）
      （vizkit.natvis）

[低]  汎用のフォールバック            Priority="Low"
      （「この名前空間の型は全部これ」のような包括的な定義）
```

`Low` の使いどころは、**包括的なフォールバック**です。

```xml
<!-- vizkit の型で、専用の定義がないものに共通の印を付ける -->
<Type Name="vizkit::*" Priority="Low">
  <DisplayString>[vizkit type, no visualizer]</DisplayString>
</Type>
```

こう書いておくと、Natvis を書き忘れた型が一目で分かります。第8章 8.7節で述べた「フォールバックを置く」という考え方の、型名レベルでの適用です。

**ただし、この包括定義は諸刃の剣です。** 意図せず既存の定義を潰す可能性があるので、`Priority="Low"` を必ず付け、導入したら全型の表示を一度確認してください。

## 31.8 この章のまとめ

- 同じファイル内で複数マッチしたら、**先に書いたほうが使われる**。順序依存は脆いので `Priority` を使う。
- `Priority` は `High` / `MediumHigh` / `Medium`（既定）/ `MediumLow` / `Low` の5段階。**高いものが先に検査される。**
- **`Priority` はファイル間の優先順位を覆さない。** 効くのは同じファイル・同じディレクトリ内。
- ワイルドカードの一部を具体型に置き換えたものが「特殊化」。**優先順位は自動判定されないので `Priority` を明示する。**
- **特殊化は定義の複製になる。** ビューで済むならビューを使う（第24章 24.4節）。
- **ライブラリが提供する Natvis は `Medium`（既定）にしておく。** 利用者が `High` で上書きできる余地を残す。優先度は「譲る」方向に設計する。
- `<AlternativeType>` は同構造の型に定義を共有させる。**`$Tn` の対応が型ごとに変わる点に注意。**
- `<Version Name="モジュール名" Min="..." Max="..."/>` はモジュールのバージョンで限定する。**静的リンクには使えない。**
- `Optional`（式単位・記述量少）と `Version`（型単位・意図が明確）を使い分ける。まず `Optional`。
- `Priority="Low"` の包括定義で「Natvis を書き忘れた型」を可視化できる。ただし慎重に。

## 31.9 演習

1. 同じ型に対する `Type` を2つ、`DisplayString` を変えて並べ、先に書いたほうが使われることを確認してください。次に後ろのほうに `Priority="High"` を付け、逆転することを確認してください。
2. 第29章の演習1（`fixed_array<*>` と `fixed_array<*,*>` を両方書く）に戻り、どちらが使われるか、`Priority` で制御できるかを確認してください。
3. `vizkit::flat_map&lt;int,*&gt;` という特殊化を書き、キーが `int` のときだけ表示が変わることを確認してください。`Priority` を付けない場合に何が起きるかも見てください。
4. `<Type Name="vizkit::*" Priority="Low">` の包括定義を追加し、Natvis を書いていない型（`vizkit::list_hook` など）に印が付くことを確認してください。既存の型の表示が壊れていないかも確認してください。
5. `AlternativeType` で `point2` と `rect` を共有させようとして、何が起きるか観察してください。構造が違う型を共有させてはいけない理由が分かります。
