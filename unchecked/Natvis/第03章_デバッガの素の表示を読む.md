# 第3章 デバッガの素の表示を読む

Natvis を書く作業は、実質的には「生のメンバー変数から、意味のある式を組み立てる」作業です。したがって出発点は、**デバッガが素の状態で何を見せているか**を正確に把握することになります。

この章では Natvis をまだ書きません。デバッガ側のウィンドウを一通り歩いて、Natvis の式が触れられる名前の集合を確認します。急がば回れの章です。

## 3.1 題材を1つ増やす

入れ子とアクセス指定子の話をしたいので、`rect` を追加します。

`vizkit\include\vizkit\core\rect.hpp`

```cpp
#pragma once

#include <vizkit/core/point2.hpp>

namespace vizkit {

class rect {
public:
    constexpr rect() = default;
    constexpr rect(point2 mn, point2 mx) noexcept : _min(mn), _max(mx) {}

    [[nodiscard]] constexpr point2 min() const noexcept { return _min; }
    [[nodiscard]] constexpr point2 max() const noexcept { return _max; }

    [[nodiscard]] constexpr double width()  const noexcept { return _max.x - _min.x; }
    [[nodiscard]] constexpr double height() const noexcept { return _max.y - _min.y; }
    [[nodiscard]] constexpr bool   empty()  const noexcept { return width() <= 0.0 || height() <= 0.0; }

private:
    point2 _min{};
    point2 _max{};
};

} // namespace vizkit
```

`playground\main.cpp` を次のように書き換えます。

```cpp
#include <vizkit/core/point2.hpp>
#include <vizkit/core/rgba.hpp>
#include <vizkit/core/rect.hpp>

#include <cstdio>

int main() {
    vizkit::point2 p{ 12.5, -4.0 };

    vizkit::rect box{ vizkit::point2{ 0.0, 0.0 }, vizkit::point2{ 640.0, 480.0 } };
    vizkit::rect degenerate{ vizkit::point2{ 5.0, 5.0 }, vizkit::point2{ 5.0, 9.0 } };

    vizkit::point2 pts[4] = {
        { 0.0, 0.0 }, { 1.0, 0.0 }, { 1.0, 1.0 }, { 0.0, 1.0 }
    };
    vizkit::point2* head = pts;          // 配列の先頭を指すポインタ
    vizkit::point2& second = pts[1];     // 参照

    vizkit::rgba color = vizkit::from_argb(0xFF3366CCu);

    const char* name = "vizkit";
    double values[5] = { 1.5, 2.5, 3.5, 4.5, 5.5 };
    double* vp = values;

    std::printf("%f %d %s\n", box.width(), static_cast<int>(color.r), name);  // ← ブレークポイント
    return 0;
}
```

`std::printf` の行にブレークポイントを張って F5 で実行してください。以降、この状態で観察していきます。

## 3.2 4つのウィンドウの役割分担

| ウィンドウ | 出し方 | 役割 |
|---|---|---|
| **自動変数** | デバッグ > ウィンドウ > 自動変数 | 現在行の周辺で使われている変数を自動で拾う。手軽だが範囲は VS の判断任せ |
| **ローカル** | 同 > ローカル | 現在のスコープの全ローカル変数 |
| **ウォッチ** | 同 > ウォッチ > ウォッチ 1 | **任意の式**を打ち込める。Natvis 開発の主戦場 |
| **クイックウォッチ** | 変数を選んで Shift+F9 | 使い捨ての式評価。長い式を試すときに便利 |

Natvis を書いているときに最も使うのは**ウォッチ**です。「Natvis に書きたい式」をまずウォッチウィンドウで手打ちして、正しく評価されることを確かめてから `.natvis` に写す、という進め方が最短だからです。この手順は本書の全章で繰り返し使います。

## 3.3 「値」列はどう作られているのか

ウォッチウィンドウは3列（名前・値・型）です。Natvis が関わるのは主に**値**列と、行を展開したときの**子行**です。

Natvis が当たっていない型について、デバッガは次のルールで値列を作ります。

- **基本型**：そのまま値を書く（`12.5`、`204`）
- **ポインタ**：アドレスを書き、続けて**指し先を1つだけ**中括弧で添える（`0x000001f4... {x=0.0 y=0.0}`）
- **クラス・構造体**：メンバーを `名前=値` の形で、宣言順に空白区切りで並べ、全体を `{ }` で囲む
- **配列**：先頭からいくつかの要素を `[0]=..., [1]=...` 形式で並べる

`box` を見てみましょう。

```
名前          値                                                          型
─────────────────────────────────────────────────────────────────────────────
▷ box         {_min={x=0.000000 y=0.000000 } _max={x=640.000000 y=480.000000 } }   vizkit::rect
   ▷ _min     {x=0.000000 y=0.000000 }                                     vizkit::point2
        x     0.000000                                                     double
        y     0.000000                                                     double
   ▷ _max     {x=640.000000 y=480.000000 }                                 vizkit::point2
        x     640.000000                                                   double
        y     480.000000                                                   double
```

ここから2つのことが分かります。

**(1) 入れ子は入れ子のまま展開される。** `rect` を開くと `_min` と `_max` があり、それぞれを開くと `x` と `y` がある。この階層構造そのものは、Natvis の `<Expand>` で自由に組み替えられます（第3部）。

**(2) `private` は無関係。** `_min` と `_max` は private メンバーですが、デバッガには完全に見えています。デバッガはメモリレイアウトを扱っているだけで、アクセス指定子はコンパイル時の概念だからです。

この(2)は Natvis を書くうえで決定的に重要です。**Natvis の式は private メンバーに自由にアクセスできます。** そのために `friend` を宣言する必要も、アクセサを用意する必要もありません。

一方で、その裏返しの制約もあります。

```
ウォッチウィンドウに box.width() と入力すると:

  box.width()    関数の評価にはすべてのスレッドを実行する必要があります   
```

環境によっては関数評価が動くこともありますが、**Natvis の中では関数を呼べません**。`width()` の値が欲しければ、Natvis には `_max.x - _min.x` と書くことになります。「アクセサではなく生メンバーから式を組む」というのが Natvis の基本姿勢です。

## 3.4 生ビュー（Raw View）とは何か

いま見た「メンバーを宣言順に並べる」表示のことを、**生ビュー（Raw View）** と呼びます。

Natvis を当てていない型では、素の表示がそのまま生ビューです。しかし Natvis を当てた型では、既定の表示が Natvis の定義に置き換わり、代わりに末尾に `[Raw View]` という行が追加されます。

```
▷ v      { size=3 } [10, 20, 30]        ← Natvis が作った表示
     [size]        3
     [0]           10
     [1]           20
     [2]           30
   ▷ [Raw View]                          ← 素のメンバーはここに退避する
        ▷ _begin  0x000001f4a2c31240 {10}
        ▷ _end    0x000001f4a2c3124c
        ▷ _cap    0x000001f4a2c31250
```

**`[Raw View]` は、Natvis を書くときの唯一の情報源です。** ここに出ている名前が、Natvis の式で使える名前のすべてだと考えてください。

- メンバー名が実装のリファクタリングで変わったら、まず `[Raw View]` を開いて新しい名前を確認する
- 他人のライブラリに Natvis を書くときも、`[Raw View]` を開いて内部構造を読むことから始める
- Natvis が「なぜか空になる」ときは、`[Raw View]` を見て、そもそも自分が思っている構造になっているかを確かめる

第27章で MSVC 同梱の `STL.natvis` を読みますが、あそこに出てくる `_Mypair._Myval2._Myfirst` のような長い名前も、`std::vector` の `[Raw View]` を開けば全部書いてあります。Natvis は「読めない内部構造を推測して書く」ものではなく、「見えている内部構造を並べ替える」ものです。

なお、生ビューを最初から開いた状態にしたい場合は、**ツール > オプション > デバッグ > 全般** の **「変数ウィンドウで生の構造を表示する」** をオンにできます。Natvis を書いている間はオンにしておくと便利です。

## 3.5 ポインタ・配列・参照の既定表示

ここが Natvis の必要性がいちばん露骨に現れる場所です。ウォッチウィンドウで確認します。

### 配列

```
▷ pts        0x00000078abcff5a8 {{x=0.000000 y=0.000000 }, {x=1.000000 y=0.000000 }, ...}   vizkit::point2[4]
   ▷ [0]     {x=0.000000 y=0.000000 }
   ▷ [1]     {x=1.000000 y=0.000000 }
   ▷ [2]     {x=1.000000 y=1.000000 }
   ▷ [3]     {x=0.000000 y=1.000000 }
```

配列は問題ありません。**要素数が型情報に含まれている**（`point2[4]`）ので、デバッガは全要素を出せます。

### ポインタ

```
▷ head       0x00000078abcff5a8 {x=0.000000 y=0.000000 }    vizkit::point2 *
   ▷ x       0.000000
   ▷ y       0.000000
```

同じメモリを指しているのに、**1個しか見えません**。`head` の型は `point2*` であり、「4個ある」という情報はどこにもないからです。

自作コンテナがまさにこの状態です。`dynamic_array` が持っているのはポインタと長さであり、その2つを結びつけているのは**あなたの頭の中の約束**だけです。デバッガはそれを知りません。Natvis の `ArrayItems`（第14章）は、この約束を明文化するための機能です。

### 参照

```
▷ second     {x=1.000000 y=0.000000 }    vizkit::point2 &
```

参照は指し先そのものとして表示されます。Natvis 的には、参照は透過的だと考えて構いません。

### 文字列ポインタ

```
  name       0x00007ff6a1b2c3d0 "vizkit"    const char *
```

`const char*` だけは特別扱いされ、NUL 終端文字列として表示されます。ただしこれは「`char` へのポインタだから」という理由による特別扱いであって、あなたの `fixed_string` には適用されません（第9章）。

## 3.6 ウォッチ式の書式指定子を予習する

ウォッチウィンドウでは、式の後ろにカンマ区切りで**書式指定子**を書けます。これは Natvis の `DisplayString` の中でも同じ構文が使えるので、いま慣れておきます。

ウォッチウィンドウに次を1つずつ入力してみてください。

| 入力する式 | 結果 | 意味 |
|---|---|---|
| `color.r` | `204 'Ì'` | 既定（`unsigned char` は文字扱い） |
| `color.r,d` | `204` | 10進数として表示 |
| `color.r,x` | `0xcc` | 16進数として表示 |
| `vp` | `0x... {1.5000000000000000}` | ポインタなので1個だけ |
| `vp,[5]` | `0x... {1.5, 2.5, 3.5, 4.5, 5.5}` | **5要素の配列とみなす** |
| `values,[3]` | `{1.5, 2.5, 3.5}` | 先頭3要素だけに絞る |
| `box,!` | `{_min=... _max=...}` | Natvis を無効化して生の表示を強制 |
| `p.x,e` | `1.250000e+01` | 指数表記 |

`vp,[5]` に注目してください。「ポインタ＋要素数」を人間が手で与えれば、デバッガはちゃんと配列として見せてくれる。**Natvis がやっているのは、この `,[5]` を型ごとに自動化することです。**

`,!` も覚えておくと便利です。Natvis を書き進めていて「いまの表示は Natvis のせいなのか、元からそうなのか」を切り分けたいとき、`,!` を付ければ素の表示に戻せます。

## 3.7 メモリウィンドウで裏を取る

Natvis が期待どおりに動かないとき、最後の手段はメモリを直接見ることです。

**デバッグ > ウィンドウ > メモリ > メモリ 1** を開き、アドレス欄に `&box` と入力します。

```
0x00000078ABCFF5C8  00 00 00 00 00 00 00 00  00 00 00 00 00 00 00 00
0x00000078ABCFF5D8  00 00 00 00 00 00 84 40  00 00 00 00 00 00 7e 40
```

`_min = (0, 0)` の 16 バイトに続いて、`_max = (640, 480)` の 16 バイト（`0x4084000000000000` = 640.0、`0x407E000000000000` = 480.0）が並んでいることが確認できます。

ウォッチウィンドウで `sizeof(vizkit::rect)` を評価すると `32` が返るはずです。`sizeof` と `&` はウォッチ式で使えるので、レイアウトの確認に重宝します。

小ネタとして、メモリウィンドウのアドレス欄には**式**が書けます。`head + 2` と入力すれば、3番目の要素の先頭にジャンプします。ポインタ演算が Natvis の式でも同じように使えることの確認になります。

## 3.8 この章のまとめ

- Natvis の式が触れられるのは、**`[Raw View]` に見えている名前**だけ。ここが唯一の情報源。
- `private` はデバッガから見えている。アクセサや `friend` は不要。
- **関数は呼べない。** `width()` ではなく `_max.x - _min.x` と書く。
- 配列は要素数が型に含まれるので全部見えるが、**ポインタは1個しか見えない**。この差を埋めるのが Natvis の中心的な仕事。
- ウォッチ式の書式指定子（`,d` `,x` `,[n]` `,!`）は Natvis の中でもそのまま使える。
- 「Natvis に書きたい式は、まずウォッチウィンドウで試す」。この手順を身につけておくと、以降の章が格段に楽になる。
