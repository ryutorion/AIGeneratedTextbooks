# 第43章 最適化ビルドと大規模データ

本書はここまで、Debug / x64 / `/Od` を前提に進めてきました（第2章 2.3節）。実務ではそうもいきません。

- パフォーマンス問題は Release でしか再現しない
- 顧客から届くクラッシュダンプは Release ビルド
- データ量が実運用規模になると、Debug では遅すぎて動かない

この章では、その2つの現実 ―― **最適化**と**大規模データ** ―― への対処を扱います。

## 43.1 Release で何が起きるか

最適化ビルドでは、Natvis の前提が崩れます。

### 変数が消える

```
  v          <利用できません>          vizkit::dynamic_array<int>
```

変数がレジスタに載っている、あるいは完全に削除されている場合です。Natvis 以前の問題で、デバッガがその変数を見つけられません。

### メンバーが最適化で消える

構造体そのものが分解され、メンバーがレジスタに散らばることがあります（スカラー置換）。この場合、`_begin` は見えても `_end` が見えない、といった状態になります。

Natvis からは「識別子が定義されていません」に見えるので、**メンバー名を間違えたのか最適化で消えたのかの区別がつきません**。

### インライン化でスコープが変わる

関数がインライン化されると、その関数のローカル変数がどのスコープに属するかが曖昧になります。デバッガは推測しますが、常に正しいとは限りません。

### 何が変わらないか

一方、**ヒープ上のオブジェクトの構造は変わりません**。`new` で確保したノードのレイアウトは、最適化とは無関係です。

したがって、次の傾向があります。

| 対象 | Release での見え方 |
|---|---|
| スタック上のローカル変数 | **消えやすい** |
| 関数の引数 | 消えやすい |
| ヒープ上のオブジェクト | **ほぼ確実に見える**（ポインタさえ辿れれば） |
| グローバル変数・静的変数 | 見える |
| メンバー変数（オブジェクトが見えていれば） | 見える |

**コンテナの中身を見る Natvis は、Release でも比較的よく動きます。** ヒープにあるからです。困るのは「そのコンテナへの参照がどこにも見つからない」という状況です。

## 43.2 デバッグ情報を厚くする

Release でもある程度デバッグしやすくする設定です。

### /Zi と /DEBUG

Release でも PDB を生成します。

```
C/C++ > 全般 > デバッグ情報の形式        = /Zi
リンカー > デバッグ > デバッグ情報の生成 = はい (/DEBUG)
```

**実行速度には影響しません。** PDB のサイズが増え、リンク時間が延びるだけです。配布バイナリから PDB を外せばよいので、Release でも常に有効にしておくことを勧めます。第40章 40.2節で述べた `/NATVIS` の前提にもなります。

### /Zo

`/Zo`（Enhance Optimized Debugging）は、**最適化されたコードのデバッグ情報を強化する**オプションです。インライン化された関数のローカル変数や、レジスタに載った変数の情報が追加されます。

新しい MSVC では `/Zi` と併用したときに既定で有効になっていることが多いので、明示的に指定する必要はふつうありません。**「Release で変数が見えない」ときに確認する項目**として覚えておいてください。

### 部分的に最適化を切る

問題の関数だけ最適化を止めるという手もあります。

```cpp
#pragma optimize("", off)
void problematic_function() {
    // この関数だけ最適化されない
}
#pragma optimize("", on)
```

デバッグのための一時的な措置です。コミットしないよう注意してください。

### 変数を消させない

```cpp
volatile auto* keep = &v;   // 最適化で消えないようにする
(void)keep;
```

これも一時的な措置です。`volatile` はコード生成に影響するので、性能を測っている最中には使えません。

## 43.3 Natvis 側でできること

最適化で消えたメンバーに対して、Natvis 側で打てる手は限られます。

### Optional で部分的に生かす

第8章 8.2節の性質を利用します。

```xml
<Type Name="vizkit::dynamic_array&lt;*&gt;">
  <Intrinsic Name="size" Expression="(int)(_end - _begin)" />
  <DisplayString Optional="true">{{ size={size()} }}</DisplayString>
  <DisplayString>[dynamic_array]</DisplayString>
  <Expand>
    <Item Name="[size]" Optional="true">size()</Item>
    <ArrayItems Optional="true">
      <Size>size()</Size>
      <ValuePointer>_begin</ValuePointer>
    </ArrayItems>
    <Item Name="[begin]" Optional="true">_begin</Item>
  </Expand>
</Type>
```

`_end` が消えていれば `size()` が解析に失敗し、`ArrayItems` と `[size]` が飛ばされます。しかし `_begin` は生きているかもしれないので、`[begin]` だけは表示されます。

**「全部見えないか、全部見えるか」ではなく、「見えるものだけ見せる」形にする。**

ただし第8章 8.5節の警告を思い出してください。**Debug ビルドでも壊れたときに沈黙する**ようになります。Release 専用のビューに閉じ込めるという手もあります。

```xml
<ArrayItems IncludeView="release" Optional="true">
```

### 手動で件数を与える

`_end` が見えず `_begin` だけが見える場合、ウォッチウィンドウで直接指定できます。

```
v._begin,[10]
```

第6章 6.5節のサイズ指定子です。**Natvis が動かないときの最後の手段**として、この書き方を覚えておいてください。

## 43.4 大規模データの表示コスト

もう1つの現実です。要素数が数万・数百万になると、Natvis の書き方が体感速度を決めます。

### 列挙方法ごとのコスト

第28章 28.4節の表を再掲します。

| 列挙方法 | 1要素あたり | ランダムアクセス |
|---|---|---|
| `ArrayItems` | アドレス計算のみ | **できる**（100 万件目に直接ジャンプ） |
| `IndexListItems` | `ValueNode` を1回評価 | **できる** |
| `LinkedListItems` / `TreeItems` | `NextPointer` / `ValueNode` を評価 | できない（先頭から辿る） |
| `CustomListItems` | ループ内のすべての式を評価 | できない（先頭から辿る） |

**ランダムアクセスできるかどうかが決定的です。** `ArrayItems` なら、ウォッチウィンドウをスクロールして 100 万件目に飛んでも一瞬です。`CustomListItems` は 100 万回ループします。

### デバッガ側の仮想化

デバッガは、**画面に見えている行だけを評価します**。10 万要素のコンテナを開いても、最初は先頭の数十件しか読みません。

この仮組みが効くのは、ランダムアクセスできる列挙方法の場合だけです。`CustomListItems` では、スクロール位置まで毎回ループする必要があります。

`<Skip>` 要素（第28章 28.5節）は、この制約を緩和するためのものですが、利用例は少なく環境依存です。

### 実務的な指針

```
要素数が数千を超えうるコンテナでは:

1. 専用要素（ArrayItems / IndexListItems）で書けないか再検討する
2. 書けないなら、既定ビューは打ち切り付きにする
3. 全件表示は IncludeView="all" などの別ビューに回す
4. 統計や検証は IncludeView="detail" に閉じ込める
```

第24章 24.6節の `flat_map`、第28章 28.4節の `deque` で実践した形です。

### 打ち切りを明示する

**打ち切ったことを表示に残す**のを忘れないでください（第28章 28.4節）。

```xml
<Synthetic Name="[...]" Condition="_size &gt; 200">
  <DisplayString>残り {(int)_size - 200} 件は表示されていません（,view(all) で全件）</DisplayString>
</Synthetic>
```

**Natvis が嘘をつかないようにする**ための1行です。

## 43.5 デバッガ側の設定

Visual Studio 側にも、表示コストに関わる設定があります。

**ツール > オプション > デバッグ > 全般** の中で、次の項目が関係します。

| 設定 | 意味 |
|---|---|
| プロパティ評価とその他の暗黙的な関数呼び出しを有効にする | オフにすると、関数評価が行われなくなる。Natvis には直接関係しないが、全体の応答が改善することがある |
| 文字列の値の長さを制限する | 巨大な文字列の表示を打ち切る |
| 変数ウィンドウで生の構造を表示する | `[Raw View]` を既定で開く（Natvis 開発中はオン推奨） |

これらは Natvis の書き方では制御できない部分です。**チームで「デバッガが遅い」と言われたら、Natvis だけでなくこちらも確認してください。**

## 43.6 クラッシュダンプでの Natvis

顧客から届くダンプファイルのデバッグでも、Natvis は効きます。

必要なもの：

- **ダンプファイルと一致する PDB**
- **`.natvis`**（PDB に埋め込まれていれば自動、なければプロジェクト内かユーザーフォルダに）

第40章の PDB 埋め込みが、ここで大きく効きます。**リリース時点の Natvis が PDB と一緒に保存されている**ので、後から「当時のバージョンの Natvis」を探す必要がありません。

注意点として、**ミニダンプでは読めるメモリが限られます**。ヒープを含まないミニダンプでは、ポインタを辿った先が読めず、コンテナの中身が表示できません。

```
  v          { size=3 }
     [0]     <メモリを読み取れません>
```

これは Natvis の問題ではないので、ダンプの取得設定（`MiniDumpWithFullMemory` など）を見直す必要があります。

## 43.7 この章のまとめ

- Release では**スタック上のローカル変数が消えやすい**が、**ヒープ上のオブジェクトの構造は変わらない**。コンテナの中身を見る Natvis は比較的よく動く。
- **Release でも `/Zi` と `/DEBUG` を有効にする。** 実行速度に影響せず、`/NATVIS` の前提にもなる。
- `/Zo` は最適化コードのデバッグ情報を強化する。「変数が見えない」ときに確認する。
- Natvis 側では **`Optional="true"` で「見えるものだけ見せる」**形にできる。ただし Debug で沈黙するようになるので、`IncludeView` で分けることも検討する。
- 最後の手段は**ウォッチウィンドウで `ptr,[n]`** と手動で件数を与える書き方。
- 大規模データでは**ランダムアクセスできるかが決定的**。`ArrayItems` / `IndexListItems` は飛べるが、`LinkedListItems` / `CustomListItems` は先頭から辿る。
- 要素数が数千を超えうるなら、**既定ビューは打ち切り付き、全件は別ビュー、統計は `detail`**。
- **打ち切ったことを表示に残す。** Natvis が嘘をつかないようにする。
- クラッシュダンプでも Natvis は効く。**PDB 埋め込みが、当時のバージョンの Natvis を保存してくれる。**
- ミニダンプではヒープが読めず、コンテナの中身が表示できないことがある。ダンプの取得設定の問題。

## 43.8 演習

1. `vizkit` を Release 構成でビルドし、`playground` の変数がどれだけ見えるか確認してください。ヒープ上のコンテナとスタック上の `point2` で差があるかも見てください。
2. Release 構成で `/Zi` と `/DEBUG` を無効にし、Natvis がまったく効かなくなることを確認してください。
3. `dynamic_array` に 100 万要素を入れ、`ArrayItems` 版でウォッチウィンドウを末尾までスクロールしてください。次に `CustomListItems` 版で同じことを試し、体感速度を比べてください。
4. `#pragma optimize("", off)` で1つの関数だけ最適化を止め、その関数内の変数が Release でも見えるようになることを確認してください。
5. `playground` をクラッシュさせてミニダンプを取得し、そのダンプを Visual Studio で開いて Natvis が効くか確認してください。`MiniDumpNormal` と `MiniDumpWithFullMemory` で差が出ることも確かめてください。
