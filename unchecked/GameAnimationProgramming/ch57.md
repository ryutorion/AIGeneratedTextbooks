# 第 57 章　マルチスレッド更新

**この章で作るもの**：キャラクター単位でアニメーション更新を並列化する仕組み。`std::jthread` と `std::barrier` を使い、外部ライブラリは使いません。

そして 2 つのことを実測します。**スレッドを毎フレーム作ると利得の 3 割が消えること**、そして **FTZ/DAZ をワーカーで設定し忘れると 24 倍遅くなること**です。

---

## 57.1　何を並列にできるか

第 52 章で「何が独立しているか」を数えました。同じ問いを、今度はスレッドの粒度で考えます。

**① キャラクター間** ―― 完全に独立。100 体のアニメーション更新は、互いに何も共有しません。**これが答えです。**

**② パイプラインの段階間**（サンプル → 階層 → IK → パレット）―― 依存があります。順番にしか実行できません。ただし**別のキャラクターの別の段階**は同時に走れるので、パイプライン並列という手はあります。複雑さに見合わないので採りません。

**③ ボーン間** ―― 親子の依存があります（第 52 章）。兄弟同士は独立ですが、粒度が細かすぎてスレッド化のオーバーヘッドに負けます。

**④ 頂点間**（スキニング）―― 完全に独立。ただしこれは第 58 章で GPU に渡します。

**キャラクター単位の並列**だけをやります。データ共有がなく、実装が単純で、キャラクター数が増えるほどよく効く。

---

## 57.2　共有状態を排除する

並列化で最も危険なのは、**気づかずに共有しているもの**です。第 52 章の `AnimationSystem` を、共有の観点で点検します。

| データ | 読み書き | 共有してよいか |
|---|---|---|
| `Skeleton` | 読むだけ | **よい**（`const` で渡す） |
| `Clip` / `CompressedClip` | 読むだけ | **よい** |
| 逆バインド行列 | 読むだけ | **よい** |
| `Pose` / `PoseBatch` | キャラクターごとに書く | **よい**（範囲が重ならないなら） |
| パレット | キャラクターごとに書く | **よい**（同上） |
| `SampleContext`（探索ヒント） | キャラクターごとに書く | **キャラクターごとに持つこと** |
| `PoseBufferPool`（第 44 章） | ブレンド中に確保・解放 | **危険** |
| `FootIkState`（第 51 章） | 書く | **キャラクターごとに持つこと** |

**`PoseBufferPool` が地雷**です。第 44 章でブレンドツリーの評価用に作ったバッファプールは、複数スレッドから同時に `Acquire()` されると壊れます。

選択肢は 3 つ。

1. **ミューテックスで守る** ―― 毎フレーム何百回もロックすることになり、並列化の意味がなくなる
2. **スレッドローカルにする** ―― `thread_local` は便利ですが、スレッド数ぶんのメモリを持つことになり、破棄のタイミングが読みにくい
3. **ワーカーごとに 1 つ持ち、引数で渡す** ―― 明示的

**3 を選びます。**

```cpp
// ワーカー 1 本が持つ作業領域。共有しない。
struct WorkerScratch {
    PoseBufferPool  poolA, poolB;
    std::vector<Transform> global;
    std::vector<Mat4>      palette;
    SampleContext          sampleCtx;
};
```

**「暗黙に共有されているもの」を「明示的に渡すもの」に変える** ―― これが並列化の作業の実体で、`std::thread` を書くこと自体はその後の 10 行です。

`thread_local` を避ける理由も書いておきます。便利ですが、**「どのスレッドがどのバッファを使ったか」がコードから見えなくなります**。デバッグのとき、そして「ワーカーを 4 本から 8 本に増やしたらメモリが倍になった」ときに、原因を追いにくい。

## 57.3　いちばん素朴な実装

`std::jthread`（C++20）を使います。`std::thread` と違い、**デストラクタで自動的に `join()` されます**。

```cpp
void UpdateAll(const Skeleton& s, const Clip& clip, std::span<const Mat4> invBind,
               std::span<Character> chars, int threadCount) {
    const int M = static_cast<int>(chars.size());
    std::vector<std::jthread> workers;
    workers.reserve(threadCount);

    for (int w = 0; w < threadCount; ++w)
        workers.emplace_back([&, w] {
            ScopedDenormalsAreZero ftz;              // ← 第 4 章。理由は 57.6 で
            const int lo = M *  w      / threadCount;
            const int hi = M * (w + 1) / threadCount;
            for (int i = lo; i < hi; ++i) UpdateOne(s, clip, invBind, chars[i]);
        });
    // workers のデストラクタで全員を join
}
```

**分割は連続チャンク**（0〜199、200〜399、…）です。`i % threadCount == w` のような**ストライド分割にしてはいけません**。隣り合うキャラクターのデータが別のスレッドに散り、同じキャッシュラインを 2 つのコアが書き合う **false sharing** が起きます。

連続チャンクなら、境界の 1 ラインだけが共有される可能性があり、それも `Character` が十分大きければ実害はありません。

測定します。400 体 × 60 ボーン、この原稿を書いた環境は **物理 2 コア**です。

| | 時間 | 対シングル |
|---|---|---|
| シングルスレッド（そのまま） | `2693.5` µs | 1.00× |
| 1 スレッド（`jthread` 経由） | `2835.5` µs | **0.95×** |
| 2 スレッド | `1619.2` µs | 1.66× |
| 4 スレッド | `2171.7` µs | **1.24×** |

読み取れることが 3 つあります。

**① 1 スレッドにすると遅くなる（0.95×）。** スレッドを作って壊すコストが、そのまま損失として出ています。

**② 2 コアで 1.66 倍。** 2.0 倍にはなりません。

**③ 4 スレッドは 2 スレッドより遅い（1.24×）。** 2 コアしかないので、4 本走らせても OS が切り替えるだけです。**コンテキストスイッチと、スレッド作成コストの 2 倍化**で、かえって遅くなりました。

> **スレッド数は「コア数」であって「仕事の数」ではない。** `std::thread::hardware_concurrency()` を上限にする。

## 57.4　スレッドを作らない

② の「1.66 倍」の原因を測ります。

```cpp
// 何もしないスレッドを 2 本作って捨てるだけ
for (int r = 0; r < reps; ++r) {
    std::vector<std::jthread> w;
    for (int i = 0; i < 2; ++i) w.emplace_back([]{});
}
```

**`107.2` µs。**

2 スレッド版の実測は 1619.2 µs。もしスレッド作成が無料なら 2693.5 / 2 = 1346.8 µs のはずで、差は 272 µs。**その 4 割が、スレッドを作って壊すコストです。**

毎フレーム 60 回これをやるなら、1 秒あたり 6.4 ms を捨てていることになります。

**答えは「作らない」。** ワーカーを起動時に 1 回だけ作り、**フレームごとに起こして働かせ、また眠らせる**。同期には `std::barrier`（C++20）を使います。

```cpp
class AnimationJobSystem {
public:
    explicit AnimationJobSystem(int threadCount)
        : count_(threadCount), sync_(threadCount + 1) {   // +1 はメインスレッド
        for (int w = 0; w < count_; ++w)
            workers_.emplace_back([this, w] {
                ScopedDenormalsAreZero ftz;               // スレッドの生存期間ずっと有効
                for (;;) {
                    sync_.arrive_and_wait();              // ① 開始を待つ
                    if (stop_.load(std::memory_order_relaxed)) return;
                    RunChunk(w);
                    sync_.arrive_and_wait();              // ② 終了を知らせる
                }
            });
    }
    ~AnimationJobSystem() {
        stop_.store(true);
        sync_.arrive_and_wait();                          // 起こして、終了させる
    }

    void RunFrame() {
        sync_.arrive_and_wait();                          // ① ワーカーを起こす
        sync_.arrive_and_wait();                          // ② 全員の完了を待つ
    }
private:
    void RunChunk(int w);
    int count_;
    std::atomic<bool> stop_{false};
    std::barrier<> sync_;
    std::vector<std::jthread> workers_;
};
```

**`std::barrier` を 2 回通す**のがこの形の要点です。1 回目で「始めるぞ」、2 回目で「終わったぞ」。メインスレッドも参加者に数えるので、生成時のカウントは `threadCount + 1` です。

**`ScopedDenormalsAreZero` の位置**にも注目してください。ワーカーのループの**外側**、スレッド関数の先頭にあります。スレッドが生きているあいだずっと有効で、フレームごとに設定し直すコストがありません。

測定します。

| | 時間 | 対シングル |
|---|---|---|
| シングルスレッド | `2693.5` µs | 1.00× |
| 2 スレッド（毎フレーム作成） | `1619.2` µs | 1.66× |
| **2 スレッド（使い回し）** | **`1401.7` µs** | **1.92×** |

**2 コアで 1.92 倍。** 理論上限の 96% です。

残る 4% は、バリアの同期コストと、チャンクの仕事量のばらつき（あるキャラクターがブレンドツリーを持っていて重い、など）です。

## 57.5　単体テスト：決定性

マルチスレッドで最も怖いのは、**「たまに結果が違う」**ことです。100 回に 1 回だけポーズが微妙にずれるバグは、再現しないので直せません。

キャラクター単位の並列化は、設計上**完全に決定的**であるべきです。各スレッドは自分のキャラクターしか触らないので、実行順序が結果に影響する余地がない。

**それをテストで主張します。** しかも許容誤差ではなく、**ビット単位で**。

```cpp
TEST_METHOD(ParallelIsBitIdenticalToSerial) {
    /* 400 体を用意 */
    std::vector<Character> ref = MakeChars();
    for (int i = 0; i < M; ++i) UpdateOne(s, clip, invBind, ref[i]);   // 直列

    for (int T : {2, 4}) {
        std::vector<Character> mt = MakeChars();
        UpdateAll(s, clip, invBind, mt, T);                            // 並列

        for (int i = 0; i < M; ++i)
            for (int b = 0; b < 60; ++b)
                Assert::AreEqual(0, std::memcmp(&ref[i].palette[b],
                                                &mt[i].palette[b], sizeof(Mat4)));
    }
}
```

`std::memcmp` を使っているのが意図です。**`float` の比較ではなく、バイト列の比較。** 「ほぼ同じ」ではなく「同じ」を主張します。

実測 ―― **2 スレッド、4 スレッドとも、400 体 × 60 ボーンのパレットがビット単位で一致**。

**このテストは一度緑になったら終わりではありません。** 誰かが「ワーカー間で作業バッファを共有すれば速くなる」と考えたとき、あるいは「浮動小数の合計をスレッド間で足し合わせる」処理を足したとき、このテストが止めてくれます。

**逆に言えば、決定的でなくなる設計を選ぶなら、このテストを消すことになります。** そのときは「なぜ消すのか」を必ず議論することになる ―― それがテストの価値です。

### 決定的でなくなる典型例

- **スレッド間で浮動小数を合計する。** 足す順序が実行ごとに変わると、結果のビットが変わります（第 53 章の FMA と同じ話）。
- **ワークスティーリング。** 仕事の割り当てが動的に変わると、上と同じ問題が起きます。**キャラクター単位で完全に独立なら影響しません**が、共有する集計があると壊れます。
- **`std::atomic` で「最後に書いた人が勝つ」形。** 誰が最後かは実行ごとに変わります。

## 57.6　FTZ/DAZ はスレッドごとの設定

第 4 章で、**非正規化数**（denormal / subnormal）の話をしました。`float` の表現できる最小の正規化数（約 `1.18e-38`）より小さい値は、精度を落として表現されます。多くの CPU では、この処理が**マイクロコードにフォールバックして極端に遅くなります**。

対策は FTZ（Flush To Zero）と DAZ（Denormals Are Zero）を有効にすること。第 4 章で RAII クラスを作りました。

```cpp
class ScopedDenormalsAreZero {
public:
    ScopedDenormalsAreZero() {
        oldFtz_ = _MM_GET_FLUSH_ZERO_MODE();
        oldDaz_ = _MM_GET_DENORMALS_ZERO_MODE();
        _MM_SET_FLUSH_ZERO_MODE(_MM_FLUSH_ZERO_ON);
        _MM_SET_DENORMALS_ZERO_MODE(_MM_DENORMALS_ZERO_ON);
    }
    ~ScopedDenormalsAreZero() {
        _MM_SET_FLUSH_ZERO_MODE(oldFtz_);
        _MM_SET_DENORMALS_ZERO_MODE(oldDaz_);
    }
    ScopedDenormalsAreZero(const ScopedDenormalsAreZero&) = delete;
    ScopedDenormalsAreZero& operator=(const ScopedDenormalsAreZero&) = delete;
private:
    unsigned oldFtz_, oldDaz_;
};
```

**ここが本題です。この設定は MXCSR レジスタに入っており、MXCSR は「スレッドごと」の状態です。**

メインスレッドで設定しても、**`std::jthread` で作った新しいスレッドには引き継がれません**。新しいスレッドは既定値（FTZ/DAZ ともにオフ）で始まります。

### まず、結果が変わることを確かめる

```cpp
TEST_METHOD(FtzChangesResultsPerThread) {
    auto measure = [](bool ftz) {
        volatile float sink = 0.0f;
        float result = 0.0f;
        std::jthread th([&] {
            if (ftz) { _MM_SET_FLUSH_ZERO_MODE(_MM_FLUSH_ZERO_ON);
                       _MM_SET_DENORMALS_ZERO_MODE(_MM_DENORMALS_ZERO_ON); }
            else     { _MM_SET_FLUSH_ZERO_MODE(_MM_FLUSH_ZERO_OFF);
                       _MM_SET_DENORMALS_ZERO_MODE(_MM_DENORMALS_ZERO_OFF); }
            volatile float src = 1.0e-38f;              // ← 定数畳み込みを防ぐ
            float v = src;
            for (int i = 0; i < 3; ++i) { v *= 0.1f; sink = v; }
            result = v;
        });
        th.join();
        return result;
    };
    Assert::AreNotEqual(measure(true), measure(false));
}
```

実測：

```
FTZ あり: 0.000000e+00 / FTZ なし: 9.999666e-42
```

**同じコードが、同じ入力に対して、違う値を返しました。**

**`volatile float src` が必要だった**のは、最初これを書かずに測ったら**両方 `9.999666e-42` になった**からです。`1.0e-38f * 0.1f * 0.1f * 0.1f` はコンパイル時に定数畳み込みされ、**実行時に SSE 命令が 1 つも走っていませんでした**。FTZ は「命令の結果」に効くので、命令がなければ効きません。

**マイクロベンチマークで「効果がない」と出たら、まずコードが実行されているかを疑う。** 第 IX 部で何度も出てくる教訓です。

### 次に、速さの差を測る

```cpp
auto bench = [](bool ftz) {
    /* スレッド内で FTZ を設定し、非正規化数を含むループを 200 回まわす */
    for (int r = 0; r < 2000; ++r) {
        float v = 1.0e-38f;
        for (int i = 0; i < 200; ++i) v = v*0.999f + 1.0e-45f;
        sink += v;
    }
};
```

実測：

```
非正規化数を含む 200 回のループ: FTZ あり 0.390 us / なし 9.437 us
```

**24.2 倍。**

これがアニメーションで起きるのか ―― 起きます。

- **フェードアウトしかけたブレンドの重み。** 第 39 章のクロスフェードで、重みが 0 に近づく最後の数フレーム。
- **ほぼゼロのスキニングウェイト。** 第 17 章で正規化した後の、4 番目の影響ボーン。
- **収束しかけた IK の残差。** 第 48 章で `1e-6` まで落ちた後の計算。
- **ゼロに近い平行移動やスケール。**

そして、**ワーカースレッドで設定を忘れると、メインスレッドだけ速くて、ワーカーだけ 24 倍遅い**という、極めて発見しにくい状況が生まれます。

「並列化したのに 1.2 倍にしかならない」―― プロファイラを見ても、命令数は同じです。**MXCSR を見る発想がなければ、永久に見つかりません。**

> **スレッドローカルな状態は、スレッドを作った人が設定する責任を持つ。**
>
> MXCSR（FTZ/DAZ、丸めモード、例外マスク）、ロケール、乱数の種。**新しいスレッドは「既定値」で始まる**ということを、忘れないこと。

対策は簡単です。**ワーカー関数の先頭に 1 行**置くだけ。

```cpp
workers_.emplace_back([this, w] {
    ScopedDenormalsAreZero ftz;      // ← これ
    for (;;) { /* ... */ }
});
```

そして、テストで守ります。

```cpp
TEST_METHOD(WorkersHaveFtzEnabled) {
    unsigned observed = 0;
    // ジョブシステムのワーカー内で MXCSR を読み取って報告させる
    system.RunFrameWithProbe([&]{ observed = _MM_GET_FLUSH_ZERO_MODE(); });
    Assert::AreEqual(static_cast<unsigned>(_MM_FLUSH_ZERO_ON), observed);
}
```

**「速さ」ではなく「設定」をテストする。** 速さのテストは環境で揺れますが、MXCSR の値は決定的です。

## 57.7　どこまで並列化するか

**アニメーションだけを並列化しても、ゲーム全体は速くなりません。** アニメーション更新が 2.7 ms から 1.4 ms になっても、フレーム全体が 16.7 ms なら 8% の改善です。

実務では、アニメーションは**より大きなジョブシステムの一部**として動きます。物理、AI、カリング、描画コマンド生成 ―― これらが同じワーカープールを共有し、依存関係グラフで順序づけられる。この本のジョブシステムは、その形を最小限で示したものです。

**アニメーション側が守るべき約束**は 3 つです。

1. **仕事を「独立した小さな塊」として提供できること。** キャラクター単位、あるいは 16 体単位。
2. **どのスレッドで実行されても同じ結果になること。** 57.5 のテスト。
3. **実行前に必要な入力がすべて揃っていること。** 更新中にコリジョンへ問い合わせたりしない（第 51 章でフット IK の地形問い合わせを外に出したのは、このためです）。

3 番目が、設計に一番効きます。**「更新中に外の世界へ問い合わせる」処理があると、並列化はそこで止まります。** 第 51 章で `GroundQuery` を関数ポインタで受け取り「実務では事前に問い合わせて配列で渡す」と書いたのは、この章のためでした。

## 57.8　この章の測定環境について

**この原稿を書いた環境は物理 2 コアです。** 8 コアや 16 コアでの数字は測れていません。

一般に、コア数を増やすと次のことが起きます。

- **理想的なスケールには届かなくなる。** メモリ帯域が共有されているため、第 53 章で見た「1000 体で帯域律速」がより早く訪れます。
- **バリアのコストが増える。** 全員が揃うのを待つ形式は、参加者が増えるほど「いちばん遅い人」に引きずられます。
- **仕事の粒度が重要になる。** 400 体を 16 スレッドに分けると 1 スレッド 25 体。そのくらいならまだ十分ですが、100 体を 16 スレッドなら 1 スレッド 6 体で、同期コストが目立ってきます。

**測っていないことは、測っていないと書く。** 2 コアでの 1.92 倍という数字を「よくスケールする」の根拠にはできません。読者の環境で測り直してください ―― そのためのベンチマークコードは、この本のテストに入っています。

## この章のまとめ

- 並列化の単位は**キャラクター**。段階間には依存があり、ボーン間は粒度が細かすぎ、頂点は第 58 章で GPU へ渡す。
- 並列化の作業の実体は、**「暗黙に共有されているもの」を「明示的に渡すもの」に変える**こと。`std::thread` を書くのはその後の 10 行。
- 地雷は **`PoseBufferPool`（第 44 章）、`SampleContext`、`FootIkState`（第 51 章）**。`thread_local` ではなく**ワーカーごとの `WorkerScratch` を引数で渡す**（どのスレッドが何を使ったかがコードから見える）。
- 分割は**連続チャンク**。ストライド分割は false sharing を招く。
- **スレッド数はコア数であって仕事の数ではない。** 2 コアで 4 スレッドは 2 スレッドより遅い（1.24× 対 1.66×）。
- **`std::jthread` を毎フレーム作ると `107.2` µs が消える** ―― 2 スレッドの利得の約 4 割。
- **`std::barrier` を 2 回通す**形（開始・完了）でワーカーを使い回すと、**1.66× → 1.92×**。2 コアで理論上限の 96%。
- 決定性のテストは**許容誤差ではなく `std::memcmp`** で書く。実測、400 体 × 60 ボーンのパレットが 2/4 スレッドともビット単位で一致。**決定的でなくなる設計を選ぶなら、このテストを消す議論をすることになる。**
- **FTZ/DAZ（MXCSR）はスレッドごとの状態。新しいスレッドは既定値（オフ）で始まる。** 実測、同じ計算が **`0.0` と `9.999666e-42`** に分かれる。
- 速度差は **24.2 倍**（`0.390` µs 対 `9.437` µs）。ワーカーだけ 24 倍遅い状況は、**プロファイラでは命令数が同じに見えるので発見が極めて難しい**。
- **マイクロベンチで「効果がない」と出たら、まずコードが実行されているかを疑う** ―― `volatile` を入れるまで、定数畳み込みで SSE 命令が 1 つも走っていなかった。
- **速さではなく設定をテストする。** 速さのテストは環境で揺れるが、MXCSR の値は決定的。
- アニメーション側が守る約束：**独立した小さな塊、どこで実行しても同じ結果、実行前に入力が揃っている**。3 番目のために、第 51 章で地形問い合わせを外に出した。
- **測っていないことは、測っていないと書く。** この章の数字は物理 2 コアのもの。
