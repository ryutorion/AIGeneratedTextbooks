# 第 62 章　総合演習

**この章で作るもの**：これまでの 61 章のすべてを、1 本のプログラムに結合します。glTF モデルを読み、クリップを圧縮し、速度でブレンドし、足を地形に接地させ、右手に武器を持たせ、足音を鳴らし、GPU 形式のパレットを出力する。

そして ―― **結合してはじめて出てくるバグ**を踏みます。

---

## 62.1　テストデータを作る

第 VI 部で作った円柱モデル（ボーン 2 本、158 頂点）では、脚も手もありません。総合演習には**人型**が要ります。

用意したのは `biped.gltf` ―― 21 ボーン、800 頂点、1280 三角形、3 クリップ。生成スクリプトの中身は付録 D に譲りますが、方針だけ書いておきます。

**スケルトンは 21 ボーン**。腰・背骨・胸・首・頭、左右の肩・上腕・前腕・手、左右の腿・すね・足・つま先。glTF の `skins[0].joints` に**トポロジカル順**で並べます（第 13 章の不変条件 `parents[i] < i` を、ファイル側で満たしておく）。

**メッシュは、各ボーン区間を囲む先細りの筒**を並べたもの。1 区間あたり 5 リング × 8 面。頂点のウェイトは、区間の始点側で親ボーン 1.0、終点側で子ボーン 1.0、中間で滑らかに遷移させます。

**クリップは 3 本**。

| 名前 | 長さ | サンプリング | 前進速度 |
|---|---|---|---|
| Idle | 2.0 秒 | 15 Hz | 0 m/s |
| Walk | 1.0 秒 | 30 Hz | 1.4 m/s |
| Run | 0.6 秒 | 30 Hz | 4.5 m/s |

回転はボーンごとに位相と振幅を変えた正弦波、ルートには前進と上下動を入れています。**「本物のモーションキャプチャ」ではありません**が、脚が交互に振れて腕が逆位相で振れる程度には歩行らしく、この章の検証には十分です。

**テストデータを自分で生成できることの価値**は、第 1 章から一貫しています。ボーン数も、クリップの長さも、サンプリング周波数も、パラメータを変えて測り直せる。**外から持ってきたモデルでは、そうはいきません。**

実行結果：

**最初に確かめるのは、第 16 章の不変条件です。**

> **バインドポーズでスキニング行列パレットを作ると、すべて単位行列になる。**

```cpp
TEST_METHOD(PaletteIsIdentityAtBindPose) {
    std::vector<Transform> g(model.skeleton.BoneCount());
    ComputeGlobalPose(model.skeleton, model.skeleton.RestLocals(), g);
    std::vector<Mat4> palette(model.skeleton.BoneCount());
    BuildSkinPalette(g, model.inverseBind, palette);

    float worst = 0.0f;
    for (const Mat4& m : palette) {
        const Mat4 id = Identity();
        for (int r=0;r<4;++r) for (int c=0;c<4;++c)
            worst = std::fmax(worst, std::fabs(m.m[r][c] - id.m[r][c]));
    }
    Assert::IsTrue(worst < 1e-6f);
}
```

実測 **`0.000000119`**。

**この 1 つのテストが、実に多くのことを同時に検証しています。**

- ノード階層を正しく読めている（親子が逆なら破綻する）
- ボーンのローカル変換を正しく読めている
- 逆バインド行列の**転置**が正しい（第 34 章）
- `ComputeGlobalPose` と `BuildSkinPalette` の合成順序が正しい（第 16 章）

**glTF の読み込みで最初に書くべきテストは、これです。** 絵を出す前に、この 1 行が通るかを見る。通らなければ、その先はすべて無駄になります。

## 62.3　② 圧縮する

```cpp
for (std::size_t i = 0; i < model.clips.size(); ++i)
    packed[i].Build(model.clips[i], 1.0e-4f, 0.2f*kPi/180.0f, model.skeleton.RestLocals());
```

```
== ② クリップを圧縮する ==
  13776 B -> 8784 B（63.8%、1.6 倍）
  うちボーンヘッダ 4704 B（53.6%）… 短いクリップでは固定費が支配的
  sizeof(CompressedBone) = 72 B
  ワールド位置の最大誤差 0.002515 m
```

**1.6 倍。** 第 56 章では 12.7 倍だったのに。

理由は表示のとおりです。**圧縮後の 53.6% がボーンヘッダ**（`CompressedBone` が 72 バイト × 21 ボーン × 3 クリップ）。このクリップは 0.6〜2.0 秒と短く、キーの絶対数が少ないので、**固定費が支配的**になります。

第 56 章のテストクリップは 60 ボーン・2 秒・30 Hz で 10,980 キーありました。今回は 3 本合わせても 2,000 キー程度です。

**これは第 56 章の測定が間違っていたということではありません。** どちらも正しく、**クリップの性質でまったく違う数字が出る**というだけです。

> **圧縮率を「12.7 倍」と一言で語らない。** 何を、どんな条件で測ったかがすべて。

改善の方向も見えます。`CompressedBone` の 72 バイトのうち 24 バイトは `Vec3Range` で、**平行移動トラックがないボーンでは丸ごと無駄**です。定数ボーンと可変ボーンで構造体を分ければ、ヘッダは半分以下になります。ただし ―― 第 IX 部の教訓に従って、**それが問題になってから直します**。

**誤差は `0.002515` m（2.5 mm）。** 許容 0.2 度に対して妥当な値です。

## 62.4　③ 速度でブレンドする

第 42 章の 1D ブレンドスペースです。

```cpp
BlendSpace1D locomotion;
locomotion.Add(0.0f, &model.clips[0]);      // Idle
locomotion.Add(1.4f, &model.clips[1]);      // Walk
locomotion.Add(4.5f, &model.clips[2]);      // Run
locomotion.Finalize();
```

**サンプル点の位置は、クリップの前進速度そのもの**です。Walk は 1.4 m/s で進むので 1.4 に置く。こうしておくと、キャラクターの移動速度をそのままパラメータにでき、**足が滑りません**（足の接地速度と移動速度が一致する）。

```
speed=0.0 -> Idle 1.000 / Walk 0.000 / Run 0.000 （合計 1.000000）
speed=0.7 -> Idle 0.500 / Walk 0.500 / Run 0.000 （合計 1.000000）
speed=1.4 -> Idle 0.000 / Walk 1.000 / Run 0.000 （合計 1.000000）
speed=3.0 -> Idle 0.000 / Walk 0.484 / Run 0.516 （合計 1.000000）
speed=4.5 -> Idle 0.000 / Walk 0.000 / Run 1.000 （合計 1.000000）
speed=6.0 -> Idle 0.000 / Walk 0.000 / Run 1.000 （合計 1.000000）
```

**重みの合計が常に 1.000000。** 第 42・43 章で立てた不変条件が、実データでも成り立っています。範囲外（6.0 m/s）は端点にクランプされます。

**注意点が 1 つ。** 実務ではこれだけでは足りません。Walk と Run は長さが違う（1.0 秒 と 0.6 秒）ので、ブレンド中に**足の接地タイミングがずれます**。「フェーズ同期」と呼ばれる仕組み ―― 両クリップの再生位置を歩行サイクルの位相で合わせる ―― が要ります。この本では扱いませんが、第 63 章の地図に載せます。

## 62.6　⑥ 1 フレームの全体像

```cpp
for (int frame = 0; frame < 60; ++frame) {
    const float dt = 1.0f/60.0f;
    const float speed = 5.0f * frame / 59.0f;      // 0 → 5 m/s へ加速

    // --- 時刻を進める ---
    locomotion.ComputeWeights(speed, weights);
    const PlaybackStep stepWalk = players[1].Update(dt);
    const PlaybackStep stepRun  = players[2].Update(dt);
    players[0].Update(dt);

    // --- イベント（重みが十分あるクリップだけ）---
    frameEvents.clear();
    if (weights[1] > 0.3f) CollectEvents(walkEvents, model.clips[1], stepWalk, frameEvents);
    if (weights[2] > 0.3f) CollectEvents(runEvents,  model.clips[2], stepRun,  frameEvents);

    // --- サンプル + ブレンド（圧縮形式のまま）---
    bool first = true;
    for (std::size_t i = 0; i < 3; ++i) {
        if (weights[i] <= 0.0f) continue;
        packed[i].Sample(players[i].Time(), first ? blended : tmp);
        if (!first) BlendPose(blended, tmp, weights[i], blended);
        first = false;
    }

    // --- 階層 ---
    ComputeGlobalPose(model.skeleton, blended.Locals(), global);

    // --- フット IK ---
    SolveFootIk(model.skeleton, blended, global, hips, legs, Terrain, ikCfg, ikState, dt);

    // --- ソケット ---
    sockets.ResolveNoScale(global, socketWorld);

    // --- パレット（GPU 形式：3 本の float4）---
    BuildSkinPalette(global, model.inverseBind, palette);
    for (std::size_t b = 0; b < NB; ++b)
        std::memcpy(&gpuPalette[b*12], palette[b].m, 12*sizeof(float));
}
```

**第 1 章のパイプライン図が、そのままコードになりました。**

```
① クリップをサンプル    ← packed[i].Sample
② ブレンド              ← BlendPose
③ 階層を解く            ← ComputeGlobalPose
④ IK で補正             ← SolveFootIk
⑤ パレットを作る        ← BuildSkinPalette
⑥ 頂点を変形            ← GPU（第 58 章）
```

地形は「x > 1.0 から 15 度の坂」。キャラクターは 1 秒で 0 → 5 m/s へ加速しながら前進し、途中から坂を登ります。

結果：

```
足音イベント: 4 回（左 2 回 / 右 2 回）
最終フレームの武器位置: (-0.719932, 1.285124, 1.728144)
最終フレームの足首 y: L=0.073646 R=0.073674 （腰 y=0.834672）
ゴールデンハッシュ: 0x6495e0456455400e
```

**足首の y が 0.0736** ―― `footHeight` に設定した 0.06 に近い値です。地面は坂の上なので、0.06 より少し高い位置。**接地しています。**

**腰の y が 0.834672。** レストポーズでは 0.95 なので、11 cm 下がっています。坂に合わせて第 51 章の腰下げが働いた結果です。

## 62.7　結合してはじめて出たバグ

この章のコードを最初に走らせたとき、出力はこうでした。

```
最終フレームの足首 y: L=0.467323 R=0.467323 （腰 y=0.467323）
```

**両足と腰が、まったく同じ高さ。**

3 つの値が完全に一致するのは偶然ではありません。**すべてのボーンが同じ位置に潰れている**ということです。

原因を追います。`ComputeGlobalPose` は `Combine(global[parent], local[i])` を積み上げます。すべてのボーンが親と同じ位置に来るということは、**すべてのローカル平行移動が `(0,0,0)` になっている**。

犯人は `CompressedClip::Build` でした。

```cpp
// 元のコード
if (pos.IsEmpty()) {
    cb.constPos = {0,0,0};          // ← トラックが無いボーンは 0
}
```

この glTF では、**平行移動チャンネルを持つのは腰（ノード 0）だけ**です。他の 20 ボーンには回転チャンネルしかありません ―― これは実リグとして完全に正常で、第 54 章で「平行移動は 59/60 が定数」と測ったのと同じ状況です。

問題は、`Clip` と `CompressedClip` で**「トラックがない」の意味が違っていた**ことです。

```cpp
// Clip::Sample（第 26 章）
if (!b.translation.IsEmpty()) tr.translation = b.translation.Sample(t);
//   ↑ トラックが無ければ out[i] を触らない
//     → 呼び出し側が「レストポーズで埋めておく」ことが前提
```

```cpp
// CompressedClip::Sample（第 56 章）
tr.translation = cb.constPos;
//   ↑ 常に書く
```

**`Clip` は「持っているものだけ上書きする」、`CompressedClip` は「全部書く」。**

どちらも単体では筋が通っています。単体テストも通ります（第 56 章のテストクリップは全ボーンに全トラックがあったので、差が出ませんでした）。**2 つを結合して、片方の前提を満たさないデータを流したときにはじめて壊れる。**

修正は、`Build` にレストポーズを渡すことです。

```cpp
void Build(const Clip& clip, float posTolerance, float rotTolerance,
           std::span<const Transform> defaults = {});

// 中で
const Transform def = (b < defaults.size()) ? defaults[b] : TransformIdentity();
if (pos.IsEmpty())  cb.constPos   = def.translation;
if (rot.IsEmpty())  cb.constRot   = PackQuat(def.rotation);
cb.constScale = src.scale.IsEmpty() ? def.scale : src.scale.Key(0).value;
```

**`CompressedClip` を「自己完結」にしました。** 呼び出し側が事前にポーズを埋める必要がなくなり、`Clip` より安全な API になっています。

そして ―― **同じバグを、誤差の測定コードでも踏みました。**

```cpp
Pose a(model.skeleton.BoneCount());        // 単位変換で初期化される
model.clips[i].Sample(t, a);               // ← レストポーズで埋めていない
packed[i].Sample(t, b);
// a と b を比較 → 当然ずれる
```

`Clip::Sample` の前提を、測定側でも満たしていなかった。

```cpp
a = Pose::FromRest(model.skeleton);        // ← これが必要
model.clips[i].Sample(t, a);
```

> **同じ概念に 2 つの実装があるとき、危ないのは「計算の中身」ではなく「暗黙の前提」。**
>
> 第 52 章で「一致テストが赤いとき、容疑者は 3 人 ―― 新実装、旧実装、測り方」と書きました。ここでは**3 人とも犯人**でした。`CompressedClip` が前提を無視し、`Clip` が前提を要求し、測定コードが前提を満たしていなかった。

**そして、この壊れ方は「派手」でした。** 全ボーンが 1 点に潰れ、腰が 0.5 m 沈む。第 58 章で書いた「微妙に間違っているより、派手に壊れるほうがいい」が、また効きました。

## 62.8　⑦ コストの内訳

```
== ⑦ 1 フレームあたりのコスト（21 ボーン / 800 頂点）==
    サンプル + ブレンド    2.109 us
    階層解決               0.336 us
    フット IK              4.066 us
    パレット生成           0.472 us
    ------------------------------
    CPU 側の合計           6.983 us
    （CPU スキニング       5.106 us ← GPU へ渡す分）
  60 fps で 1 フレーム 16667 us。CPU 側だけなら 2387 体ぶん
```

**フット IK が全体の 58% を占めています。**

第 51 章で「両脚で 2.17 µs」と測ったときより高いのは、骨格が 7 ボーンから 21 ボーンになったからです。第 51 章の実装は、腰を動かすたびに `ComputeGlobalPose` を全体に対して呼び直します（第 48 章の `UpdateChainGlobals` が使えない ―― 腰を動かすとチェーンの親が変わるため）。**ボーン数に比例します。**

**最適化するなら、まずここです。** 方向は 3 つ。

1. **部分木だけ再計算する。** 腰を動かしたあと必要なのは腰の子孫だけで、上半身は関係ありません。
2. **脚チェーンだけ `UpdateChainGlobals` を使う。** 腰の移動を先に確定させてしまえば、その後は第 48 章の最適化が効きます。
3. **距離で間引く。** 第 59 章。遠くのキャラクターはフット IK を切る ―― 足が地面から数センチ浮いていても、50 m 先では見えません。

**3 が圧倒的に効きます。** そして実装が一番簡単です。第 59 章の結論そのままです。

**「サンプル + ブレンド」が 2.1 µs** なのは、3 クリップ中 2 つを毎フレーム評価しているからです。重みが 0 のクリップはスキップしていますが、ブレンド区間では常に 2 本走ります。

**「CPU スキニング 5.1 µs」は、GPU に渡せば消えます。** 800 頂点でこの値なので、実際のキャラクター（3 万頂点）なら 190 µs。**GPU スキニングが必須になる規模**が、この数字から見えます。

## 62.9　⑧ ゴールデンテスト

第 1 章で挙げた 4 種類のテストのうち、**④ ゴールデンテスト**をここで使います。

1 秒（60 フレーム）ぶんのシミュレーションを回し、毎フレームの**パレット全体とソケットのワールド変換**を FNV-1a ハッシュに流し込みます。

```cpp
golden = Fnv(gpuPalette.data(), gpuPalette.size()*sizeof(float), golden);
golden = Fnv(&socketWorld[0], sizeof(Transform), golden);
```

```
ゴールデンハッシュ: 0x6495e0456455400e
2 回目のハッシュ:   0x6495e0456455400e  一致=1
```

**同じ入力から同じ出力。ビット単位で。**

このテストが守っているものを列挙します。

- glTF の読み込み（ノード階層、逆バインド行列、アニメーションチャンネル）
- クリップの圧縮（キー削減、量子化、パッキング）
- 圧縮形式のサンプリング（時刻の量子化、探索、補間）
- ブレンドスペースの重み計算
- ポーズのブレンド（符号合わせを含む）
- 階層解決
- フット IK（2 ボーン IK、腰下げ、時間平滑化）
- ソケットの解決
- パレット生成と GPU 形式への変換

**これらのどれか 1 つでも挙動が変われば、ハッシュが変わります。**

**ゴールデンテストの正しい使い方**について、繰り返しておきます。

**① 「正しさ」は保証しない。** 保証するのは「変わっていない」だけです。最初のハッシュが間違った実装から出たものなら、間違いを固定するだけです。だから**ゴールデンテストは、他のテストの代わりにはなりません**。62.2 の「バインドポーズで単位行列」のような、意味のある不変条件が別途要ります。

**② 変わったら、必ず考える。** ハッシュが変わったとき、「まあ最適化したから」と機械的に更新してはいけません。**意図した変更なのか、事故なのか**を判断する。判断できないなら、その変更は理解できていないということです。

**③ 更新の手順を決めておく。** 環境変数やコマンドライン引数で「ゴールデンを再生成するモード」を用意し、生成したら差分をレビューする。この本のテストなら、ハッシュだけでなく**最終フレームのパレットをテキストでダンプ**しておくと、何が変わったかが読めます。

**④ 環境をまたぐと変わりうる。** 第 53 章で見たとおり、FMA の融合の有無でビットが変わります。異なるコンパイラ、異なる最適化レベル、異なる CPU で、同じハッシュにならないことがあります。**ゴールデンテストは「同じ環境で回帰していないこと」を見る道具**であって、移植性の検証には使えません。CI で使うなら、ビルド設定を固定します。

## 62.10　まだ足りないもの

このプログラムは「動く」レベルには達していますが、製品には足りません。正直に列挙します。

**① フェーズ同期。** 62.4 で触れたとおり、Walk と Run のブレンドで足の接地タイミングがずれます。実際に見ると「足が細かく震える」ように見えます。

**② ルートモーションとゲームロジックの結合。** 第 28 章でルートモーションを抽出しましたが、この演習では使っていません。実際には「アニメーションが進めた距離だけキャラクターを動かす」か「ゲームが決めた速度にアニメーションを合わせる」かを選ぶ必要があります。

**③ ステートマシン。** 第 45 章で作ったのに、この演習ではブレンドスペース 1 本だけです。攻撃、被弾、ジャンプを入れるなら要ります。

**④ 上半身と下半身の分離。** 第 41 章のボーンマスク。走りながら撃つ、歩きながら手を振る。

**⑤ LOD と間引き。** 第 59 章。1 体しか動かしていないので出番がありませんでした。

**⑥ マルチスレッド。** 第 57 章。同上。

**⑦ 描画。** そもそも絵が出ません。

**⑦ が一番大きな「足りないもの」です。** この本は「描画なしで、テストだけで検証する」方針を貫きました。それは実装と検証の分離という点では成功していますが、**最終的に絵として自然かどうかは、目で見るしかありません**。

数値が正しくても、絵が不自然なことはあります。逆に、数値が少しずれていても絵として問題ないことも多い ―― 第 54 章で「16.5 mm の誤差」を許容したのは、まさにそういう判断でした。

**この本を終えたら、次にやるべきは描画を繋ぐことです。** そして、そのときにはじめて「テストが緑なのに絵が変」という状況に出会います。それはこの本の敗北ではなく、**予定された次のステップ**です。

## この章のまとめ

- テストデータ（`biped.gltf`：21 ボーン、800 頂点、3 クリップ）を**自分で生成する**。ボーン数もサンプリング周波数も変えて測り直せる ―― 外から持ってきたモデルではそうはいかない。
- **glTF 読み込みで最初に書くテストは「バインドポーズでパレットが単位行列」**（実測 `0.000000119`）。ノード階層・ローカル変換・逆バインド行列の転置・合成順序を、1 行で同時に検証する。**絵を出す前にこれが通るかを見る。**
- 圧縮率は **1.6 倍**（第 56 章では 12.7 倍）。**圧縮後の 53.6% がボーンヘッダ** ―― 短いクリップでは固定費が支配的。**圧縮率を一言で語らない。何を、どんな条件で測ったかがすべて。**
- ブレンドスペースのサンプル点は**クリップの前進速度そのもの**に置く。足が滑らない。重みの合計は実データでも `1.000000`。
- 第 1 章のパイプライン図が、そのままコードになった。
- **結合してはじめて出たバグ**：`Clip::Sample` は「持っているトラックだけ上書きする」（呼び出し側がレストポーズで埋める前提）、`CompressedClip::Sample` は「全部書く」。**「トラックがない」の意味が 2 つの実装で違っていた。** 平行移動チャンネルが腰にしかない実リグで、全ボーンが 1 点に潰れた。
- **同じ概念に 2 つの実装があるとき、危ないのは「計算の中身」ではなく「暗黙の前提」。** 修正は `CompressedClip::Build` にレストポーズを渡し、**自己完結にする**こと。そして同じ前提を、測定コードでも破っていた（**容疑者 3 人が全員犯人**）。
- コスト内訳（21 ボーン / 800 頂点、1 体 1 フレーム）：サンプル+ブレンド `2.109` µs、階層 `0.336` µs、**フット IK `4.066` µs（58%）**、パレット `0.472` µs、合計 **`6.983` µs**。CPU スキニングは別途 `5.106` µs。
- **フット IK が支配的**なのは、腰を動かすたびに全体の階層を解き直すから（ボーン数に比例）。最適化するなら部分木の再計算、または**距離で間引く**（第 59 章 ―― 一番効いて一番簡単）。
- ゴールデンテストは 60 フレームぶんのパレットとソケットを FNV-1a に流し込み、**2 回目もビット単位で一致**（`0x6495e0456455400e`）。読み込みから GPU 形式変換まで 9 段すべてを一度に守る。
- ゴールデンテストの心得：**① 正しさは保証しない**（他のテストの代わりにならない）、**② 変わったら必ず考える**（機械的に更新しない）、**③ 更新手順を決めておく**、**④ 環境をまたぐと変わりうる**（FMA、第 53 章）。
- まだ足りないもの：フェーズ同期、ルートモーションの結合、ステートマシン、上下半身の分離、LOD、マルチスレッド、そして**描画**。
- **数値が正しくても絵が不自然なことはある。** この本を終えたら次は描画を繋ぐ ―― それは敗北ではなく、予定された次のステップ。

次章が最終章です。この本で**扱わなかった領域の地図**を描きます。
