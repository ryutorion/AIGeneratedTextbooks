# 第 20 章　スキニングを速くする

**この章で作るもの**：LBS の最適化版 2 つ（影響ボーン数で特化した版、SoA 版）と、それらを守る**ゴールデンテスト**。素朴な実装を消さずに残し、新旧の一致を検証しながら速くします。

---

## 20.1　まず測る

最適化の第一歩は測定です。10 万頂点（影響ボーン最大 4 本）を、第 18 章の素朴な実装で変形します。

```
naive 4-influence loop : 1.222 ms / 100k 頂点
```

これが基準です。10 万頂点のキャラクターを 60 fps で動かすなら、1 体で 7.3% のフレーム時間を使います。第 16 章で測ったポーズ計算（3.99 µs）の **300 倍**であり、**アニメーションのコストは圧倒的に頂点変形に偏っている**ことが分かります。

第 IX 部で本格的に取り組む前に、この章では「アルゴリズムを変えずにデータの並べ方と分岐を整理するだけで、どこまで速くなるか」を見ます。

---

## 20.2　影響ボーン数の分布を知る

素朴な実装は、常に 4 回ループします。

```cpp
for (int k = 0; k < kMaxInfluences; ++k) {
    const float w = v.weights[k];
    if (w == 0.0f) { continue; }   // ← 大半がここで抜ける
    ...
}
```

ウェイトが 0 の枠を `continue` で飛ばしていますが、**分岐そのもののコストは払っています**。そして重要なのは、飛ばされる回数が多いことです。

第 17 章で述べたとおり、人型キャラクターの頂点の大半は 1〜2 本のボーンにしか属しません。測定に使ったデータでは **55.1% が 1 本だけ**でした。

つまり、半分以上の頂点で「4 回ループして、3 回は何もせずに抜ける」ことをしています。

---

## 20.3　影響ボーン数で特化する

素直な改善は、影響数ごとに専用の経路を持つことです。

```cpp
// AnimLib/include/anim/Skinning.h

// 影響ボーン数で分岐する版。
// 1 本・2 本のケースを専用に書き、ループと分岐を消す。
[[nodiscard]] inline Vec3 SkinPositionLBSFast(const SkinnedVertex& v,
                                              std::span<const Mat4> palette) {
    // ウェイトは降順にソートされている（第 17 章）ので、
    // weights[1] が 0 なら影響は 1 本だけ、と判断できる。
    if (v.weights[1] == 0.0f) {
        return TransformPoint(palette[v.joints[0]], v.position);
    }
    if (v.weights[2] == 0.0f) {
        return v.weights[0] * TransformPoint(palette[v.joints[0]], v.position)
             + v.weights[1] * TransformPoint(palette[v.joints[1]], v.position);
    }
    // 3 本以上は素朴なループに任せる（頻度が低い）
    return SkinPositionLBS(v, palette);
}
```

**第 17 章でウェイトを降順にソートしておいたことが、ここで効きます。** `weights[1] == 0` を見るだけで「影響は 1 本」と判定できるのは、ソート済みだからです。ソートしていなければ、4 つ全部を調べる必要があります。

結果は次のとおり。

| 実装 | 10 万頂点 | 素朴比 |
| --- | --- | --- |
| 素朴（4 回ループ） | 1.222 ms | 1.00× |
| 影響数で特化 | **0.943 ms** | **1.30×** |

30% 速くなりました。悪くありませんが、劇的ではありません。

## 20.4　SoA へ

もう一段進めます。ここまでの `SkinnedVertex` は AoS（Array of Structures）―― 72 バイトの構造体が並んでいます。しかし**位置の変形に必要なのは、位置・ジョイント・ウェイトだけ**です。法線・接線・UV の 36 バイトは読む必要がないのに、キャッシュラインには乗ってきます。

SoA（Structure of Arrays）に組み替えます。

```cpp
// スキニング専用に組み替えた頂点データ。
// ロード時に SkinnedMesh から構築する（第 37 章で焼き込む対象）。
struct SkinningSoA {
    // 位置を成分ごとに分ける
    std::vector<float> positionX;
    std::vector<float> positionY;
    std::vector<float> positionZ;

    // 影響 2 本ぶん（3 本以上の頂点は別扱い）
    std::vector<BoneIndex> joint0;
    std::vector<BoneIndex> joint1;
    std::vector<float>     weight0;
    std::vector<float>     weight1;

    // 頂点を影響ボーン数で分類したインデックスリスト。
    // ロード時に一度作る。
    std::vector<std::uint32_t> oneBoneVertices;
    std::vector<std::uint32_t> twoBoneVertices;
    std::vector<std::uint32_t> manyBoneVertices;
};
```

**ポイントは 2 つ**あります。

**① 成分ごとの配列。** 位置を `x[], y[], z[]` に分けます。これは第 53 章の SIMD 化への準備でもあります（4 頂点の `x` を 1 命令でロードできる）。

**② 影響ボーン数で頂点を分類したリスト。** 「1 本だけの頂点はこれとこれ」というインデックスの配列をロード時に作っておけば、**ランタイムの分岐が完全に消えます**。

```cpp
void SkinPositionsSoA(const SkinningSoA& soa,
                      std::span<const Mat4> palette,
                      std::span<float> outX,
                      std::span<float> outY,
                      std::span<float> outZ) {
    // 影響 1 本：分岐なし、ウェイトの乗算もなし
    for (const std::uint32_t i : soa.oneBoneVertices) {
        const Mat4& m = palette[soa.joint0[i]];
        const float x = soa.positionX[i];
        const float y = soa.positionY[i];
        const float z = soa.positionZ[i];
        outX[i] = m.m[0][0]*x + m.m[0][1]*y + m.m[0][2]*z + m.m[0][3];
        outY[i] = m.m[1][0]*x + m.m[1][1]*y + m.m[1][2]*z + m.m[1][3];
        outZ[i] = m.m[2][0]*x + m.m[2][1]*y + m.m[2][2]*z + m.m[2][3];
    }

    // 影響 2 本
    for (const std::uint32_t i : soa.twoBoneVertices) {
        const Mat4& a = palette[soa.joint0[i]];
        const Mat4& b = palette[soa.joint1[i]];
        const float x = soa.positionX[i];
        const float y = soa.positionY[i];
        const float z = soa.positionZ[i];
        const float wa = soa.weight0[i];
        const float wb = soa.weight1[i];
        outX[i] = wa*(a.m[0][0]*x + a.m[0][1]*y + a.m[0][2]*z + a.m[0][3])
                + wb*(b.m[0][0]*x + b.m[0][1]*y + b.m[0][2]*z + b.m[0][3]);
        outY[i] = wa*(a.m[1][0]*x + a.m[1][1]*y + a.m[1][2]*z + a.m[1][3])
                + wb*(b.m[1][0]*x + b.m[1][1]*y + b.m[1][2]*z + b.m[1][3]);
        outZ[i] = wa*(a.m[2][0]*x + a.m[2][1]*y + a.m[2][2]*z + a.m[2][3])
                + wb*(b.m[2][0]*x + b.m[2][1]*y + b.m[2][2]*z + b.m[2][3]);
    }

    // 3 本以上は素朴な経路へ（省略）
}
```

行列の要素を展開して書いているのは、`TransformPoint` が `Vec3` を返すのに対して、ここでは 3 本の配列に別々に書き込みたいからです。読みやすさは犠牲になりますが、この関数は**すでに参照実装が別にある**ので、可読性より速度を優先してよい場所です。

結果です。

| 実装 | 10 万頂点 | 素朴比 |
| --- | --- | --- |
| 素朴（4 回ループ） | 1.222 ms | 1.00× |
| 影響数で特化（AoS） | 0.943 ms | 1.30× |
| **SoA + 分類済みリスト** | **0.455 ms** | **2.68×** |

**2.7 倍。** アルゴリズムは何も変えていません。データの並べ方と、ランタイムの分岐をロード時に前倒ししただけです。

第 13 章で「キャッシュの議論はこの規模では成り立たない」と書きましたが、**10 万頂点になると話が変わります**。72 バイト × 10 万 = 7.2 MB を舐めるか、必要な 24 バイトぶんだけを舐めるかで、これだけ差が出ます。

## 20.5　ゴールデンテスト

新しい実装が正しいことを、どう保証するか。

**素朴な実装を消さないこと**が第一です。第 7 章から繰り返している「独立した 2 実装の一致」を、ここでも使います。

```cpp
TEST_METHOD(FastMatchesNaive) {
    // ... 素朴な実装と特化版の結果を全頂点で比較 ...
}
```

これに加えて、この章では**ゴールデンテスト**を導入します。「ある時点で正しいと確認した出力を保存しておき、以降の変更でそれが変わらないことを確かめる」テストです。

なぜ実装間の比較だけでは足りないのか。**両方を同時に壊す変更がありうるから**です。たとえばパレットの構築を「改善」してしまえば、素朴版も最適化版も同じように間違った答えを出し、比較テストは通ってしまいます。

```cpp
// AnimLib.Tests/TestSupport/GoldenData.h

namespace anim::test {

// ゴールデンデータの保存と比較。
// データはテストプロジェクト内の TestData/ に置く。
class GoldenBuffer {
public:
    // 環境変数 ANIM_UPDATE_GOLDEN が設定されていれば、比較せずに上書きする。
    static void CompareOrUpdate(std::string_view name,
                                std::span<const Vec3> actual,
                                float tolerance,
                                const std::source_location& loc =
                                    std::source_location::current());
};

}  // namespace anim::test
```

**更新の仕組みを最初から用意しておく**のが要点です。ゴールデンデータは、意図的な仕様変更のたびに更新が必要になります。更新が面倒だと、人は「テストのほうを消す」という間違った対処をします。環境変数ひとつで再生成できるようにしておけば、その誘惑は消えます。

そして更新したときは、**差分を必ず目で確認する**。ゴールデンテストは「変わったことを教えてくれる」だけで、「変わってよいかどうか」は判断してくれません。

### 許容誤差か、ビット一致か

ゴールデンデータの比較に許容誤差を使うべきか、ビット単位の一致を要求すべきか。

今回の測定では、**素朴版と SoA 版の最大の食い違いは `0`** でした。ビット単位で完全に一致しています。演算の順序が同じで、コンパイラが同じ命令列を選んだためです。

しかし**これに依存してはいけません**。第 4 章で見たとおり `/fp:fast` は演算を再結合しますし、第 53 章で SIMD 化すれば加算の順序が変わってビット一致は崩れます。

本書の方針は次のとおりです。

- **比較は許容誤差ベース**（`kEpsPos = 1.0e-4`）。壊れやすいテストを作らない。
- **ただしビット一致した場合はログに残す**。一致しなくなったときに「なぜ変わったか」を考えるきっかけになる。

```cpp
    TEST_METHOD(SoaMatchesNaive) {
        // ... 略 ...
        float worst = 0.0f;
        int exactCount = 0;
        for (std::size_t i = 0; i < n; ++i) {
            const Vec3 a = naive[i];
            const Vec3 b = fast[i];
            worst = std::fmax(worst, Length(a - b));
            if (a.x == b.x && a.y == b.y && a.z == b.z) { ++exactCount; }
        }
        Logger::WriteMessage(std::format(
            L"max diff = {:.3g}, bit-exact = {}/{}\n", worst, exactCount, n).c_str());
        Assert::IsTrue(worst < test::kEpsPos);
    }
```

## 20.6　まだやらないこと

2.7 倍で止めます。まだ手はあります。

**SIMD 化**（第 53 章）。SoA にしたのは、そのための下準備です。4 頂点の `x` をまとめて処理できます。

**マルチスレッド化**（第 57 章）。頂点変形は完全に並列で、依存関係がありません。

**GPU へ移す**（第 58 章）。そもそも CPU でやる必要がありません。

**変形しない**（第 59 章）。遠くのキャラクターは、そもそも毎フレーム変形しなくてよい。

最後のものが、いちばん効きます。**やらずに済ませるのが、最強の最適化です。**

この章で止める理由は 2 つあります。第一に、**まだ本を読み進める必要があるから**。SIMD やマルチスレッドは、それぞれ独立した話題として第 IX 部でまとめて扱うほうが理解しやすい。

第二に、**次章で LBS そのものを疑うから**です。速くしたコードが、そもそも間違った見た目を出しているかもしれない ―― それが第 21 章の主題です。**速くする前に、正しいかどうかを確かめる。** 順序としてはむしろ逆であるべきでしたが、あえてこの順にしたのは、「最適化して満足していたら根本問題が残っていた」という、実務でよくある展開を体験してもらうためです。

## 20.7　テストを書く

`AnimLib.Tests/SkinningOptimizationTests.cpp`：

```cpp
#include "CppUnitTest.h"

#include "TestSupport/GoldenData.h"
#include "TestSupport/MathAssert.h"
#include "TestSupport/MeshSupport.h"
#include "TestSupport/TestRandom.h"
#include "TestSupport/Tolerance.h"

#include "anim/Skinning.h"
#include "anim/SkinningSoA.h"

#include <format>

using namespace Microsoft::VisualStudio::CppUnitTestFramework;
using namespace anim;
using anim::test::AssertNear;

namespace AnimLibTests {

TEST_CLASS(SkinningOptimizationTests) {
public:

    // --- 実装間の一致 ---------------------------------------------

    TEST_METHOD(FastPathMatchesNaive) {
        const SkinnedMesh mesh = test::MakeCylinder(24, 24, 1.0f, 0.15f);
        const std::vector<Mat4> palette{
            MakeTranslation({1, 0, 0}) * ToMat4(MakeQuatAxisAngle({0, 0, 1}, 0.8f)),
            MakeTranslation({0, 1, 0}) * ToMat4(MakeQuatAxisAngle({1, 0, 0}, 1.3f))};

        for (const SkinnedVertex& v : mesh.vertices) {
            AssertNear(SkinPositionLBS(v, palette),
                       SkinPositionLBSFast(v, palette), test::kEpsPos);
        }
    }

    // 影響 3 本・4 本の頂点も含めて検査する。
    // 円柱は最大 2 本なので、専用のデータを作る。
    TEST_METHOD(FastPathHandlesThreeAndFourInfluences) {
        test::TestRandom rng;
        std::vector<Mat4> palette;
        for (int i = 0; i < 4; ++i) {
            palette.push_back(MakeTranslation(rng.NextVec3(2.0f))
                              * ToMat4(rng.NextQuat()));
        }

        for (int influences = 1; influences <= 4; ++influences) {
            for (int trial = 0; trial < 200; ++trial) {
                SkinnedVertex v{};
                v.position = rng.NextVec3(1.0f);
                std::vector<Influence> in;
                for (int k = 0; k < influences; ++k) {
                    in.push_back({static_cast<BoneIndex>(k), rng.NextRange(0.1f, 1.0f)});
                }
                SortAndTruncate(in, v);

                AssertNear(SkinPositionLBS(v, palette),
                           SkinPositionLBSFast(v, palette), test::kEpsPos);
            }
        }
    }

    TEST_METHOD(SoaMatchesNaive) {
        const SkinnedMesh mesh = test::MakeCylinder(24, 24, 1.0f, 0.15f);
        const SkinningSoA soa = BuildSkinningSoA(mesh);
        const std::vector<Mat4> palette{
            MakeTranslation({1, 0, 0}) * ToMat4(MakeQuatAxisAngle({0, 0, 1}, 0.8f)),
            MakeTranslation({0, 1, 0}) * ToMat4(MakeQuatAxisAngle({1, 0, 0}, 1.3f))};

        const std::size_t n = mesh.vertices.size();
        std::vector<float> x(n), y(n), z(n);
        SkinPositionsSoA(soa, palette, x, y, z);

        float worst = 0.0f;
        std::size_t exact = 0;
        for (std::size_t i = 0; i < n; ++i) {
            const Vec3 a = SkinPositionLBS(mesh.vertices[i], palette);
            const Vec3 b{x[i], y[i], z[i]};
            worst = std::fmax(worst, Length(a - b));
            if (a.x == b.x && a.y == b.y && a.z == b.z) { ++exact; }
        }
        Logger::WriteMessage(std::format(
            L"SoA vs naive: max diff = {:.3g}, bit-exact = {}/{}\n",
            worst, exact, n).c_str());
        Assert::IsTrue(worst < test::kEpsPos);
    }

    // SoA の分類が全頂点をちょうど 1 回ずつ含むこと
    TEST_METHOD(SoaClassificationCoversEveryVertexOnce) {
        const SkinnedMesh mesh = test::MakeCylinder(16, 16, 1.0f, 0.15f);
        const SkinningSoA soa = BuildSkinningSoA(mesh);

        std::vector<int> count(mesh.vertices.size(), 0);
        for (const std::uint32_t i : soa.oneBoneVertices)  { ++count[i]; }
        for (const std::uint32_t i : soa.twoBoneVertices)  { ++count[i]; }
        for (const std::uint32_t i : soa.manyBoneVertices) { ++count[i]; }

        for (const int c : count) {
            Assert::AreEqual(1, c);
        }
    }

    // --- ゴールデンテスト -----------------------------------------

    TEST_METHOD(DeformedCylinderMatchesGolden) {
        const SkinnedMesh mesh = test::MakeCylinder(24, 24, 1.0f, 0.15f);
        const std::vector<Mat4> palette{
            Identity(),
            MakeTranslation({0.5f, 0, 0})
                * ToMat4(MakeQuatAxisAngle({0, 0, 1}, 1.0f))
                * MakeTranslation({-0.5f, 0, 0})};

        std::vector<Vec3> out(mesh.vertices.size());
        SkinMeshLBS(mesh, palette, out);

        test::GoldenBuffer::CompareOrUpdate("cylinder_bend_1rad", out, test::kEpsPos);
    }

    // ゴールデンデータの仕組み自体が働いていること
    TEST_METHOD(GoldenDetectsChange) {
        const std::vector<Vec3> reference{{1, 2, 3}, {4, 5, 6}};
        std::vector<Vec3> modified = reference;
        modified[1].y += 0.01f;    // 許容誤差を超える変更

        test::GoldenBuffer::CompareOrUpdate("golden_selftest", reference, test::kEpsPos);
        Assert::ExpectException<std::exception>([&] {
            test::GoldenBuffer::CompareOrUpdate("golden_selftest", modified, test::kEpsPos);
        });
    }
};

}  // namespace AnimLibTests
```

`FastPathHandlesThreeAndFourInfluences` を別に書いた理由は重要です。**円柱メッシュの影響ボーンは最大 2 本**なので、円柱だけをテストしていると `SkinPositionLBSFast` の 3 本目以降の経路が一度も実行されません。第 9 章で「シェパードの 4 分岐すべてに到達しているか」を確かめたのと同じ問題です。**テストデータがコードのすべての経路を通っているか**は、意識して確認しないと見落とします。

`SoaClassificationCoversEveryVertexOnce` も、地味ですが重要です。分類リストに漏れや重複があると、「一部の頂点が変形されない」「一部が二重に処理される」という症状になります。前者は静かに間違った結果を出すので、特に見つけにくい。

`GoldenDetectsChange` は、**ゴールデンテストの仕組みそのものをテスト**しています。「ゴールデンデータの読み込みに失敗しても静かに成功扱いになる」といった実装ミスがあると、その後のすべてのゴールデンテストが無意味になります。第 3 章で `IsNear` をテストしたのと同じ発想です。

## 20.8　つまずきやすいところ

**最適化版だけ結果が違う**
まず影響ボーン数を確認してください。`SkinPositionLBSFast` は「ウェイトが降順にソートされている」ことを前提にしています（第 17 章）。ソートされていないデータを渡すと、`weights[1] == 0` の判定が誤ります。

**ゴールデンテストが毎回落ちる**
コンパイラの最適化設定を変えた、`/fp:fast` を切り替えた、あるいは別の CPU で実行した ―― いずれも結果を変えます。許容誤差の範囲に収まっているか確認してください。収まらないなら、それは実装の変更が原因です。

**ゴールデンデータを更新したら、他のテストが落ちた**
更新前に差分を確認していますか。ゴールデンテストは「変わった」ことだけを教えます。「変わってよいか」の判断は人間の仕事です。

**SoA 版で一部の頂点が変形されない**
分類リストに漏れがあります。`SoaClassificationCoversEveryVertexOnce` を実行してください。

**測ったら遅くなった**
Debug ビルドで測っていませんか。`/Od` では SoA の利点はまったく出ません。**性能の測定は必ず Release で。** そしてテスト自体は Debug でも通る必要があります（アサートを効かせるため）。

**SoA を導入したらコードが読めなくなった**
そのとおりです。だから**素朴な実装を残します**。仕様を知りたいときは素朴版を読み、速さが必要なときは SoA 版を使う。両者が一致することはテストが保証します。

## この章のまとめ

- 頂点変形は**アニメーションのコストの大半**を占める。10 万頂点で 1.222 ms は、ポーズ計算（3.99 µs）の 300 倍。
- 頂点の **55.1% は影響ボーンが 1 本だけ**。常に 4 回ループするのは無駄。
- **影響数で特化**すると 1.30×。**SoA + 分類済みリスト**にすると **2.68×**。アルゴリズムは何も変えていない。
- 第 17 章の**降順ソート**が、`weights[1] == 0` だけで影響数を判定できる根拠になっている。設計の伏線が回収された形。
- 第 13 章では「キャッシュの議論はこの規模では成り立たない」だったが、**10 万頂点なら成り立つ**。7.2 MB を舐めるか 2.4 MB で済むかの差。
- **素朴な実装を消さない。** 仕様の記述であり、テストの相手であり、読んで理解するためのコード。
- **ゴールデンテストは更新の仕組みとセットで作る。** 更新が面倒だと、人はテストのほうを消す。
- 比較は**許容誤差ベース**で。ビット一致は嬉しい偶然として記録するに留める（`/fp:fast` や SIMD で必ず崩れる）。
- **テストデータがすべての経路を通っているか確認する。** 円柱は影響 2 本までなので、3 本以上の経路には別のデータが要る。

次章、速くしたこの実装が、そもそも正しい見た目を出していないことを数値で確かめます。
