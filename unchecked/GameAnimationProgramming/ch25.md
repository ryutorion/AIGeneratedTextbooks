# 第 25 章　サンプリング

**この章で作るもの**：時刻からキー区間を探す処理。線形探索から始めて、二分探索、そして**前フレームの結果を使うヒント探索**へ進みます。実測で **41 倍**まで速くなりますが、**速くならない場面もある**ことも同じ厳しさで測ります。

---

## 25.1　問題設定

`Track::Sample(time)` がやることは 2 段階です。

1. **時刻 `time` を含むキー区間を探す**（`keys[i].time <= time < keys[i+1].time` となる `i`）
2. その区間で補間する（第 24 章）

補間は定数時間です。**コストのほとんどは探索**にあります。そして探索は、100 ボーン × 3 トラック = 300 回、毎フレーム、キャラクターの数だけ実行されます。

---

## 25.2　線形探索

いちばん素朴な実装です。

```cpp
template <typename T>
int Track<T>::FindIndexLinear(float time) const {
    if (keys_.size() < 2) {
        return 0;
    }
    // 後ろから探す。最後の区間は size-2 が上限。
    for (std::size_t i = keys_.size() - 2; i > 0; --i) {
        if (time >= keys_[i].time) {
            return static_cast<int>(i);
        }
    }
    return 0;
}
```

**上限が `size - 2` である**ことに注意してください。区間は `[keys[i], keys[i+1]]` なので、区間の開始として有効な最大のインデックスは `size - 2` です。

筆者は最初これを `size - 1` から回してしまい、時刻がトラックの末尾を超えたときに `size - 1` を返していました。二分探索版は `size - 2` を返すので、**2 つの実装の結果が食い違い**、25.10 節のテストが落ちて気づきました。**独立した 2 実装を突き合わせるテストは、こういう境界の取り違えをよく捕まえます。**

## 25.3　二分探索

```cpp
template <typename T>
int Track<T>::FindIndexBinary(float time) const {
    if (keys_.size() < 2) {
        return 0;
    }
    std::size_t lo = 0;
    std::size_t hi = keys_.size() - 1;
    while (hi - lo > 1) {
        const std::size_t mid = (lo + hi) / 2;
        if (keys_[mid].time <= time) {
            lo = mid;
        } else {
            hi = mid;
        }
    }
    return static_cast<int>(lo);
}
```

`std::upper_bound` を使わずに手で書いているのは、**返したいのが「区間の開始インデックス」であって「挿入位置」ではない**からです。標準アルゴリズムを使うと `-1` の調整や境界の特別扱いが必要になり、かえって読みにくくなります。

不変条件は `keys[lo].time <= time < keys[hi].time`。ループは `hi - lo` が 1 になるまで縮めます。

## 25.4　ヒント付き探索

ここからが本題です。

アニメーションの再生では、**時刻はほぼ単調に増えます**。60 fps なら 1 フレームで 16.7 ms しか進まない。キーが 30 fps 間隔なら、**前フレームと同じ区間にいる確率が半分**、隣の区間に移る確率が半分です。

なのに毎フレーム二分探索でゼロから探すのは、明らかに無駄です。**前回の答えを覚えておいて、まずそこを試します。**

```cpp
template <typename T>
int Track<T>::FindIndexHint(float time, int hint) const {
    const int lastSegment = static_cast<int>(keys_.size()) - 2;
    if (lastSegment < 0) {
        return 0;
    }
    if (hint < 0 || hint > lastSegment) {
        return FindIndexBinary(time);      // ヒントが無効
    }
    // ① 同じ区間にいる（最頻）
    if (time >= keys_[hint].time && time < keys_[hint + 1].time) {
        return hint;
    }
    // ② 次の区間に進んだ（順再生）
    if (hint + 1 <= lastSegment
        && time >= keys_[hint + 1].time && time < keys_[hint + 2].time) {
        return hint + 1;
    }
    // ③ 前の区間に戻った（逆再生）
    if (hint - 1 >= 0
        && time >= keys_[hint - 1].time && time < keys_[hint].time) {
        return hint - 1;
    }
    // ④ 大きく飛んだ。素直に二分探索
    return FindIndexBinary(time);
}
```

4 段階のうち、**①②で 99% 以上が解決します**。③ を入れているのは逆再生のためで、④ はシークやループの折り返しに備えた保険です。

**ヒントが間違っていても、答えは常に正しい**という点が重要です。ヒントは速さのためだけの情報であり、正しさには一切関与しません。だから「ヒントが壊れてバグる」ということが起こりません。

## 25.5　実測

キー数を変えて、3 つの実装を測りました。1 クエリあたりのナノ秒です。

**順再生（時刻が単調に増える）**

| キー数 | 線形 | 二分 | **ヒント** |
| --- | --- | --- | --- |
| 10 | 4.5 | 4.9 | **4.1** |
| 50 | 23.0 | 10.1 | **3.6** |
| 200 | 98.0 | 16.3 | **3.7** |
| 1000 | 453.3 | 21.1 | **3.4** |

**ヒント探索はキー数に依存しません。** 1000 キーでも 3.4 ns で、線形探索の **133 倍**、二分探索の **6.2 倍**速い。O(1) なので当然ですが、実測で確認できると安心します。

線形探索がキー数に比例して悪化するのも、教科書どおりです。**10 キー以下なら線形でも二分探索と変わらない**（4.5 対 4.9 ns）というのは、覚えておくと役に立つ事実です。定数トラックに近い、キーが数個しかないトラックは実際に多くあります。

## 25.6　ヒントが遅くなる場合

同じ測定を、**ランダムな時刻**で行いました。

| キー数 | 線形 | 二分 | ヒント |
| --- | --- | --- | --- |
| 10 | 19.2 | **10.9** | 22.5 |
| 50 | 36.7 | **19.4** | 29.6 |
| 200 | 98.9 | **28.3** | 35.9 |
| 1000 | 450.1 | **21.9** | 39.3 |

**ヒント探索が二分探索より遅い。** 1000 キーで 39.3 対 21.9 ns、**1.8 倍遅い**という結果です。

理由は明快で、ランダムアクセスではヒントがほぼ必ず外れるからです。①②③ の 3 つの判定をすべて空振りし、**そのうえで二分探索を実行する**ので、二分探索の純粋なコストに判定のぶんが上乗せされます。

「ヒント探索は常に速い」という思い込みは、ここで否定されます。**ヒントが効くのは、時刻が連続的に変化する場合だけ**です。

実務上の結論は次のとおりです。

**通常の再生ではヒントを使う。** 時刻は連続的に動くので、必ず効きます。

**シークしたらヒントを捨てる。** タイムラインを飛ばした、別のクリップに切り替えた、ループの先頭に戻した ―― こういう場面ではヒントを `-1`（無効）にリセットします。次のフレームから、また効き始めます。

```cpp
// シーク時にヒントを無効化する
void SampleContext::Invalidate() {
    std::fill(hints_.begin(), hints_.end(), -1);
}
```

`FindIndexHint` は `hint < 0` を「無効」として二分探索に落とすので、リセットは `-1` を入れるだけで済みます。

## 25.7　ヒントをどこに置くか

設計上、これは自明ではありません。**トラックの中に持たせてはいけない**からです。

第 13 章で「スケルトンは 1 つ、ポーズは 1000 個」と分離したのと同じ話です。`Clip` は**モデル固有で不変**であり、1000 体のキャラクターで共有されます。それぞれが違う時刻を再生しているので、**トラックにヒントを持たせると全員が干渉します**。しかも第 57 章でマルチスレッド化したら、データ競合になります。

ヒントは**再生している側**が持ちます。

```cpp
// AnimLib/include/anim/Clip.h

// サンプリングの作業状態。キャラクター 1 体につき 1 つ持つ。
// クリップは共有されるので、状態はこちら側に置く。
class SampleContext {
public:
    void Reset(std::size_t boneCount) {
        hints_.assign(boneCount * 3, -1);   // 平行移動・回転・スケールで 3 本
    }
    void Invalidate() {
        std::fill(hints_.begin(), hints_.end(), -1);
    }

    [[nodiscard]] int& Hint(BoneIndex bone, int channel) {
        return hints_[static_cast<std::size_t>(bone) * 3 + channel];
    }
    [[nodiscard]] std::size_t Size() const noexcept { return hints_.size(); }

private:
    std::vector<int> hints_;
};
```

100 ボーンで `int` 300 個 = 1.2 KB。キャラクターあたりのメモリが 1.2 KB 増えますが、**サンプリングが 3 倍速くなる**ならお釣りが来ます。

> **`SampleContext` は「キャッシュ」ではなく「作業状態」**
> 名前を `Cache` にしなかったのは、これが**正しさに関与しない**ことを強調するためです。捨てても、壊しても、他人のものを使っても、結果は変わりません。速度だけの話です。この性質があるからこそ、シーク時に迷わずリセットできます。

## 25.8　クリップ全体でのコスト

トラック単体ではなく、実際のサンプリングで測ります。**100 ボーン × 3 トラック × 各 60 キー**のクリップを 1 回サンプルするコストです。

| 探索方法 | 1 ポーズあたり |
| --- | --- |
| 二分探索 | 8.14 µs |
| **ヒント** | **2.54 µs（3.21 倍）** |

トラック単体では 6.2 倍でしたが、クリップ全体では 3.21 倍に落ち着きます。補間そのもののコスト（`Nlerp` など）が乗るためです。

第 16 章で測った値と合わせると、キャラクター 1 体の 1 フレームは次のようになります。

| 処理 | 1 体あたり |
| --- | --- |
| クリップのサンプリング（ヒント） | 2.54 µs |
| 階層の解決 | 1.87 µs |
| パレット構築 | 2.12 µs |
| **合計** | **6.53 µs** |

1000 体で **6.53 ms** ―― 16.7 ms のフレーム時間の **39%** です。第 16 章の時点では 24% でした。**まだブレンドも IK も頂点変形も入っていません。**

そしてヒント探索を使わなければ、これが 12.1 ms（**73%**）になります。この 1 つの工夫の価値が分かります。

## 25.9　逆再生・シーク・ループ境界

ヒント探索が壊れやすいのは、時刻が単調でなくなる場面です。3 つとも検査します。

**逆再生。** `FindIndexHint` の ③ が担当します。速度が負の再生では、毎フレーム 1 つ前の区間へ移ります。

**シーク。** ④ に落ちます。1 回だけ二分探索のコストを払い、以後はまた ①② で済みます。明示的に `Invalidate()` を呼べば、判定 3 回ぶんも節約できます。

**ループの折り返し。** 時刻が末尾から先頭に飛ぶので、④ に落ちます。**毎ループ 1 回だけ**なので、実質的に無視できるコストです。

これら 3 つで**二分探索と同じ結果が返る**ことを、テストで保証します。ヒントは正しさに関与しない ―― この設計上の約束を、実行可能な形で確認します。

## 25.10　テストを書く

`AnimLib.Tests/KeySearchTests.cpp`：

```cpp
#include "CppUnitTest.h"

#include "TestSupport/MathAssert.h"
#include "TestSupport/TestRandom.h"
#include "TestSupport/Tolerance.h"

#include "anim/Track.h"

#include <cmath>

using namespace Microsoft::VisualStudio::CppUnitTestFramework;
using namespace anim;

namespace {

Track<float> MakeDenseTrack(int keyCount) {
    Track<float> t;
    for (int i = 0; i < keyCount; ++i) {
        t.AddKey(static_cast<float>(i) * 0.033f, std::sin(static_cast<float>(i) * 0.1f));
    }
    t.Finalize();
    return t;
}

}  // namespace

namespace AnimLibTests {

TEST_CLASS(KeySearchTests) {
public:

    // --- 3 実装の一致（この章で最重要）----------------------------

    TEST_METHOD(AllThreeSearchesAgreeOnRandomTimes) {
        const Track<float> t = MakeDenseTrack(200);
        const float endTime = 199 * 0.033f;

        test::TestRandom rng;
        int hint = 0;
        for (int i = 0; i < 100000; ++i) {
            const float x = rng.NextRange(-1.0f, endTime + 1.0f);
            const int linear = t.FindIndexLinear(x);
            const int binary = t.FindIndexBinary(x);
            const int hinted = t.FindIndexHint(x, hint);
            Assert::AreEqual(linear, binary);
            Assert::AreEqual(binary, hinted);
        }
    }

    TEST_METHOD(HintIsCorrectDuringForwardPlayback) {
        const Track<float> t = MakeDenseTrack(200);
        const float endTime = 199 * 0.033f;

        int hint = 0;
        for (int i = 0; i <= 2000; ++i) {
            const float x = static_cast<float>(i) / 2000.0f * endTime;
            hint = t.FindIndexHint(x, hint);
            Assert::AreEqual(t.FindIndexBinary(x), hint);
        }
    }

    TEST_METHOD(HintIsCorrectDuringReversePlayback) {
        const Track<float> t = MakeDenseTrack(200);
        const float endTime = 199 * 0.033f;

        int hint = static_cast<int>(t.KeyCount()) - 2;
        for (int i = 2000; i >= 0; --i) {
            const float x = static_cast<float>(i) / 2000.0f * endTime;
            hint = t.FindIndexHint(x, hint);
            Assert::AreEqual(t.FindIndexBinary(x), hint);
        }
    }

    // ループの折り返し（末尾から先頭への大ジャンプ）
    TEST_METHOD(HintSurvivesLoopWrap) {
        const Track<float> t = MakeDenseTrack(200);
        const float endTime = 199 * 0.033f;

        int hint = 0;
        for (int loop = 0; loop < 5; ++loop) {
            for (int i = 0; i <= 100; ++i) {
                const float x = static_cast<float>(i) / 100.0f * endTime;
                hint = t.FindIndexHint(x, hint);
                Assert::AreEqual(t.FindIndexBinary(x), hint);
            }
            // 次のループの先頭へ飛ぶ
        }
    }

    // 無効なヒントを渡しても正しい答えが返ること
    TEST_METHOD(InvalidHintStillGivesCorrectAnswer) {
        const Track<float> t = MakeDenseTrack(50);
        const float endTime = 49 * 0.033f;

        test::TestRandom rng;
        for (int i = 0; i < 1000; ++i) {
            const float x = rng.NextRange(0.0f, endTime);
            for (const int badHint : {-1, -999, 0, 48, 49, 100, 99999}) {
                Assert::AreEqual(t.FindIndexBinary(x), t.FindIndexHint(x, badHint));
            }
        }
    }

    // --- 境界 -----------------------------------------------------

    TEST_METHOD(SearchClampsToValidSegmentRange) {
        const Track<float> t = MakeDenseTrack(10);
        const int lastSegment = 8;   // キー 10 個 → 区間 0..8

        Assert::AreEqual(0, t.FindIndexBinary(-100.0f));
        Assert::AreEqual(0, t.FindIndexLinear(-100.0f));
        Assert::AreEqual(lastSegment, t.FindIndexBinary(100.0f));
        Assert::AreEqual(lastSegment, t.FindIndexLinear(100.0f));
        Assert::AreEqual(lastSegment, t.FindIndexHint(100.0f, 0));
    }

    TEST_METHOD(SingleKeyAndEmptyTracksAreSafe) {
        Track<float> single;
        single.AddKey(1.0f, 5.0f);
        single.Finalize();
        Assert::AreEqual(0, single.FindIndexBinary(0.0f));
        Assert::AreEqual(0, single.FindIndexHint(99.0f, 7));

        const Track<float> empty;
        Assert::AreEqual(0, empty.FindIndexBinary(0.0f));
        Assert::AreEqual(0, empty.FindIndexHint(0.0f, 0));
    }

    // キー時刻ちょうどでの挙動
    TEST_METHOD(ExactKeyTimesLandOnTheStartingSegment) {
        Track<float> t;
        t.AddKey(0.0f, 0.0f);
        t.AddKey(1.0f, 1.0f);
        t.AddKey(2.0f, 2.0f);
        t.Finalize();

        Assert::AreEqual(0, t.FindIndexBinary(0.0f));
        Assert::AreEqual(1, t.FindIndexBinary(1.0f));   // 区間 [1,2] の開始
        Assert::AreEqual(1, t.FindIndexBinary(2.0f));   // 末尾は最後の区間
    }

    // --- サンプリング結果の一致 -----------------------------------

    TEST_METHOD(SampledValuesAreIdenticalAcrossSearches) {
        const Track<float> t = MakeDenseTrack(200);
        const float endTime = 199 * 0.033f;

        test::TestRandom rng;
        int hint = 0;
        for (int i = 0; i < 20000; ++i) {
            const float x = rng.NextRange(-1.0f, endTime + 1.0f);
            hint = t.FindIndexHint(x, hint);
            // ビット単位で同一であるべき（同じ区間・同じ式）
            Assert::IsTrue(t.SampleAt(x, t.FindIndexBinary(x)) == t.SampleAt(x, hint));
        }
    }
};

}  // namespace AnimLibTests
```

`SampledValuesAreIdenticalAcrossSearches` が `==` による**厳密な比較**を使っている点に注目してください。第 20 章では「ビット一致に依存するな」と書きましたが、ここは事情が違います。**同じ区間・同じ入力・同じ式**を通るので、結果はビット単位で一致しなければおかしいのです。許容誤差で比べると、区間が 1 つずれていても「近い値」なので通ってしまいます。

`InvalidHintStillGivesCorrectAnswer` は、25.4 節で述べた設計上の約束 ―― **ヒントは正しさに関与しない** ―― を直接検査しています。この約束があるから、シーク時のリセットを気軽に行えます。

## 25.11　つまずきやすいところ

**線形探索と二分探索の結果が食い違う**
末尾の扱いです。区間の開始インデックスの上限は `size - 2` であって `size - 1` ではありません（25.2 節）。

**ヒントを使ったら結果が変わった**
ヒントは正しさに関与しない設計になっているはずです。`FindIndexHint` の判定条件（半開区間 `[a, b)`）を確認してください。`<=` と `<` の取り違えが典型です。

**マルチスレッドでクラッシュする、または結果が乱れる**
ヒントをトラック（共有オブジェクト）に持たせています。`SampleContext` に移してください（25.7 節）。

**シーク直後だけ遅い**
仕様です。二分探索 1 回ぶんのコストがかかります。気になるなら `Invalidate()` を明示的に呼んでください。

**ランダムアクセスが多い用途で遅くなった**
25.6 節です。ヒントは連続的な再生でのみ有効です。タイムラインエディタのスクラブのような用途では、二分探索のほうが速くなります。

**キーが数個しかないトラックでヒントのオーバーヘッドが気になる**
10 キー以下なら線形探索と二分探索の差はほぼありません（4.5 対 4.9 ns）。トラックのキー数で実装を切り替えるのも手ですが、分岐のコストと引き換えなので、実測してから判断してください。

## この章のまとめ

- `Sample` のコストのほとんどは**キー区間の探索**。100 ボーン × 3 トラック × キャラクター数だけ毎フレーム走る。
- **順再生では、ヒント探索が圧勝**。1000 キーで 3.4 ns、線形の 133 倍、二分探索の 6.2 倍。しかも**キー数に依存しない**。
- **ランダムアクセスでは、ヒント探索のほうが遅い**（1000 キーで 39.3 対 21.9 ns）。ヒントが外れたうえで二分探索を走らせるため。**「ヒントは常に速い」は間違い。**
- だから**シークではヒントを捨てる**。`-1` を入れるだけ。
- **ヒントは正しさに関与しない。** 壊れていても、他人のものでも、答えは変わらない。この約束をテストで保証してあるから、リセットを気軽に行える。
- ヒントは**トラックではなく再生側**（`SampleContext`）に持つ。クリップは 1000 体で共有されるため。第 13 章の「形と姿勢の分離」と同じ構造。
- クリップ全体では **8.14 µs → 2.54 µs（3.21 倍）**。1 体あたりの合計は 6.53 µs になり、1000 体で**フレーム時間の 39%**。第 16 章の 24% から上がった。
- 10 キー以下なら**線形探索でも変わらない**（4.5 対 4.9 ns）。

次章でトラックをクリップにまとめ、ループと再生速度を扱います。
