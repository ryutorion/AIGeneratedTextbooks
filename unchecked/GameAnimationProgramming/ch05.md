# 第 5 章　ベクトル

**この章で作るもの**：`Vec3` と `Vec4`、そしてそれらを検証するためのテスト支援（`ToString` 特殊化、`AssertNear` のベクトル版、決定論的な乱数生成器）。あわせて本書の**座標系**を決定します。

---

## 5.1　なぜ自分で書くのか

`DirectXMath` にも `glm` にも、よくできた `Vec3` があります。それでも自分で書きます。

理由は、この先の章で**メモリレイアウトを自分の都合で変えるから**です。第 20 章では頂点を SoA（Structure of Arrays）に並べ替えます。第 53 章では 4 つのベクトルを同時に処理する SIMD 版を作ります。第 55 章では位置を 16 ビット整数に量子化します。これらはすべて「`Vec3` の中身が自分のものである」ことを前提にした改造です。

もう一つの理由は、この章のコードが**驚くほど短い**ことです。ライブラリの使い方を調べる時間より、書いてしまう時間のほうが短いくらいです。

---

## 5.2　本書の座標系を決める

外積を定義する前に、座標系を決めなければなりません。外積の向きは座標系の向き（利き手）そのものだからです。

**本書は右手系・Y-up・-Z 前方を採用します。**

```
        +Y (上)
         │
         │
         └────── +X (右)
        ╱
      +Z (手前 = カメラ側)
```

つまり、キャラクターは **-Z 方向を向いて**立っています。右手の親指を +X、人差し指を +Y に向けると、中指が +Z を指します。

この選択の理由は一つ、**glTF がこの座標系だから**です。第 34 章でモデルを読み込むとき、座標系の変換が一切不要になります。座標系の変換は間違えやすく、しかも間違えても「なんとなく動いてしまう」ことがあるので、避けられるなら避けるのが賢明です。

単位はメートル、角度はラジアンです。度数法は人間が読み書きする境界（テストのコード、デバッグ出力）でのみ使い、内部では一切使いません。

## 5.3　`Vec3` を定義する

`AnimLib/include/anim/Vec3.h` を作ります。

```cpp
#pragma once

#include <cmath>

namespace anim {

struct Vec3 {
    float x;
    float y;
    float z;
};

}  // namespace anim
```

これだけです。**コンストラクタを書きません。** 意図的な選択なので、理由を説明します。

コンストラクタを持たない構造体は**集成体（aggregate）**であり、次の性質を得ます。

**① 波括弧で初期化できる。** `Vec3 v{1.0f, 2.0f, 3.0f};` と書けます。さらに `Vec3 v{};` はすべてゼロで初期化されます。

**② トリビアルにコピーできる。** `std::memcpy` で運べます。第 32 章で glTF のバイナリバッファから頂点配列を読むとき、`memcpy` 一発で済むかどうかは実装の簡潔さに直結します。

**③ 定数式で使える。** `constexpr Vec3 kUp{0, 1, 0};` が書けます。

**④ 初期化の抜けが分かる。** `Vec3 v;`（初期化なし）と `Vec3 v{};`（ゼロ初期化）が区別されます。前者は `/W4` で「初期化されていない変数の使用」として警告されます。コンストラクタを書くと、この区別が消えます。

代償は `Vec3(1.0f)` のような便利なコンストラクタが書けないことですが、`Vec3{1.0f, 1.0f, 1.0f}` で困ることはありません。

> **`float x, y, z;` を 1 行で書かない理由**
> 1 メンバ 1 行にしておくと、第 55 章で `x` だけ型を変えるといった改造のときに差分が読みやすくなります。趣味の問題ではありますが、本書ではこの流儀で統一します。

## 5.4　演算子

同じヘッダに追記します。

```cpp
constexpr Vec3 operator+(Vec3 a, Vec3 b) { return {a.x + b.x, a.y + b.y, a.z + b.z}; }
constexpr Vec3 operator-(Vec3 a, Vec3 b) { return {a.x - b.x, a.y - b.y, a.z - b.z}; }
constexpr Vec3 operator-(Vec3 a)         { return {-a.x, -a.y, -a.z}; }

constexpr Vec3 operator*(Vec3 a, float s) { return {a.x * s, a.y * s, a.z * s}; }
constexpr Vec3 operator*(float s, Vec3 a) { return a * s; }
constexpr Vec3 operator/(Vec3 a, float s) { return {a.x / s, a.y / s, a.z / s}; }

constexpr Vec3& operator+=(Vec3& a, Vec3 b) { a = a + b; return a; }
constexpr Vec3& operator-=(Vec3& a, Vec3 b) { a = a - b; return a; }
constexpr Vec3& operator*=(Vec3& a, float s) { a = a * s; return a; }

constexpr bool operator==(Vec3 a, Vec3 b) {
    return a.x == b.x && a.y == b.y && a.z == b.z;
}
```

**引数は参照ではなく値渡し**です。`Vec3` は 12 バイトで、x64 の呼び出し規約ではレジスタに載ります。`const Vec3&` にすると、かえってメモリ経由になることがあります。

`operator==` を定義しましたが、**浮動小数点なので使う場面はほとんどありません**。第 3 章で議論したとおりです。ここで定義するのは、`std::vector<Vec3>` に対する `std::find` のような標準アルゴリズムを使いたくなったとき、あるいは「バイト単位で同一か」を確かめたいときのためです。実際の比較はほぼ常に `AssertNear` 系を使います。

**`operator*` を「ベクトル同士の掛け算」に使わない**ことにも注意してください。ベクトル同士の `*` は、内積・外積・成分ごとの積のどれとも読めて曖昧です。成分ごとの積は名前を付けます。

```cpp
// 成分ごとの積。主にスケールの適用に使う（第 11 章）。
constexpr Vec3 MulPerComponent(Vec3 a, Vec3 b) {
    return {a.x * b.x, a.y * b.y, a.z * b.z};
}
```

## 5.5　内積

```cpp
constexpr float Dot(Vec3 a, Vec3 b) {
    return a.x * b.x + a.y * b.y + a.z * b.z;
}
```

内積は `|a||b|cosθ` です。本書では次の用途で繰り返し登場します。

- **符号だけを見る**：`Dot(a, b) > 0` で「同じ方向を向いているか」。第 10 章のクォータニオンの最短経路判定がこれです。
- **正規化されたベクトル同士**：値がそのまま `cosθ` になり、`acos` で角度が取れます（第 47 章の 2 ボーン IK）。
- **射影**：`Dot(v, n) * n` で `v` の `n` 方向成分。第 19 章の法線の扱いで使います。

## 5.6　外積

```cpp
constexpr Vec3 Cross(Vec3 a, Vec3 b) {
    return {a.y * b.z - a.z * b.y,
            a.z * b.x - a.x * b.z,
            a.x * b.y - a.y * b.x};
}
```

3 行が巡回していることに注目してください。`x` の行は `(y, z)`、`y` の行は `(z, x)`、`z` の行は `(x, y)` を使います。**`y` の行だけ順序が逆に見える**のが間違えやすい点で、`z*b.x - x*b.z` を `x*b.z - z*b.x` と書いてしまうと、外積が左手系になります。

この定義が右手系であることは、基底ベクトルで確かめられます。

```
Cross({1,0,0}, {0,1,0}) = {0,0,1}     X × Y = Z
Cross({0,1,0}, {0,0,1}) = {1,0,0}     Y × Z = X
Cross({0,0,1}, {1,0,0}) = {0,1,0}     Z × X = Y
```

この 3 本をテストに書いておけば、外積の符号ミスは二度と起きません。

## 5.7　長さと正規化 ―― ゼロ長をどうするか

```cpp
constexpr float LengthSquared(Vec3 a) { return Dot(a, a); }

[[nodiscard]] inline float Length(Vec3 a) { return std::sqrt(LengthSquared(a)); }
```

`LengthSquared` を分けて持つのは、**長さの比較には平方根が要らない**からです。「半径 r 以内か」は `LengthSquared(v) < r*r` で判定できます。`sqrt` は数十サイクルかかる命令なので、内側のループでは避けたいところです。第 25 章のキー検索や第 48 章の IK 収束判定で効いてきます。

`Length` は `std::sqrt` を呼ぶため `constexpr` にできません（C++23 時点の `<cmath>` は定数評価に対応していません）。

さて、正規化です。ここで最初の設計判断が必要になります。**長さ 0 のベクトルを正規化しようとしたら、どうすべきか。**

考えられる選択肢は 3 つあります。

**① 例外を投げる。** ゲームのランタイムでは採用できません。毎フレーム数万回呼ばれる関数に例外処理のコストは載せられませんし、そもそも「例外を投げてゲームを止める」という復旧方法がありません。

**② 常に安全な値（ゼロや既定の軸）を返す。** 安全ですが、**分岐が常に入ります**。そして何より、バグが隠れます。「正規化したら (0,0,0) が返ってきて、そのまま計算が進み、10 段先で NaN になる」という追跡困難な状況を作ります。

**③ 呼び出し側の責任とする（契約）。** 「長さが 0 でないベクトルを渡すこと」を前提とし、デバッグビルドでのみ検査します。

本書は **③ を既定とし、② を明示的に選べる形で併置します。**

```cpp
// 前提：a の長さが 0 でないこと。
// 長さ 0 を渡した場合の動作は未定義（結果は NaN になる）。
[[nodiscard]] inline Vec3 Normalize(Vec3 a) {
    ANIM_ASSERT(LengthSquared(a) > 0.0f);
    return a * (1.0f / Length(a));
}

// 長さが 0 に近いときは fallback を返す。
// 「向きが定まらないことが起こりうる」と分かっている場所でだけ使う。
[[nodiscard]] inline Vec3 NormalizeSafe(Vec3 a, Vec3 fallback) {
    const float len2 = LengthSquared(a);
    if (len2 < kTinyLengthSquared) {
        return fallback;
    }
    return a * (1.0f / std::sqrt(len2));
}
```

しきい値は、二乗した値が非正規化数の領域に落ちないところに置きます。

```cpp
// 長さがこれ未満なら「方向を持たない」とみなす。
// float の最小正規化数 (約 1.18e-38) から十分離した値。
inline constexpr float kTinyLengthSquared = 1.0e-30f;
```

第 4 章で見たとおり、非正規化数は速度低下の原因になります。`1.0e-30f` は二乗する前の長さで約 `1.0e-15`。この長さのベクトルに意味のある方向が入っていることはありません。

### `ANIM_ASSERT`

契約を書くためのマクロを用意します。`AnimLib/include/anim/Assert.h`：

```cpp
#pragma once

#if defined(_DEBUG) || defined(ANIM_ENABLE_ASSERT)
    #include <crtdbg.h>
    #define ANIM_ASSERT(expr) _ASSERTE(expr)
#else
    #define ANIM_ASSERT(expr) ((void)0)
#endif
```

Release ビルドでは完全に消えます。**契約の検査はデバッグ時の道具であって、実行時の防御ではありません。** この区別は重要です。防御が必要な場所（外部ファイルから読んだ値など）では、第 31 章で `std::expected` を使った明示的なエラー処理を導入します。

## 5.8　`Vec4`

`AnimLib/include/anim/Vec4.h`：

```cpp
#pragma once

#include "anim/Vec3.h"

namespace anim {

struct Vec4 {
    float x;
    float y;
    float z;
    float w;
};

constexpr Vec4 operator+(Vec4 a, Vec4 b) { return {a.x+b.x, a.y+b.y, a.z+b.z, a.w+b.w}; }
constexpr Vec4 operator-(Vec4 a, Vec4 b) { return {a.x-b.x, a.y-b.y, a.z-b.z, a.w-b.w}; }
constexpr Vec4 operator*(Vec4 a, float s) { return {a.x*s, a.y*s, a.z*s, a.w*s}; }
constexpr Vec4 operator*(float s, Vec4 a) { return a * s; }

constexpr float Dot(Vec4 a, Vec4 b) {
    return a.x*b.x + a.y*b.y + a.z*b.z + a.w*b.w;
}

// w = 1 は「点」、w = 0 は「方向」を表す慣習。
constexpr Vec4 MakePoint(Vec3 v)  { return {v.x, v.y, v.z, 1.0f}; }
constexpr Vec4 MakeVector(Vec3 v) { return {v.x, v.y, v.z, 0.0f}; }
constexpr Vec3 XYZ(Vec4 v)        { return {v.x, v.y, v.z}; }

}  // namespace anim
```

`w` の意味（1 なら点、0 なら方向）は第 6 章で行列を掛けるときに効いてきます。**点は平行移動の影響を受け、方向は受けない**という区別が、`w` の値だけで自動的に処理されます。

なお、本書のライブラリで `Vec4` が主役になる場面はそれほど多くありません。頂点のスキンウェイト（第 17 章）とシェーダとのやりとり（第 58 章）が主な用途です。ボーンの姿勢は `Vec3` + `Quat` で持ちます。

## 5.9　テストの支援を整える

第 3 章で予告した `ToString` の特殊化を、ここで回収します。あわせて、この先ずっと使う道具を 2 つ追加します。

### `ToString` と型ごとの `AssertNear`

`AnimLib.Tests/TestSupport/MathAssert.h` を新規作成します。

```cpp
#pragma once

#include "TestSupport/Near.h"

#include "anim/Vec3.h"
#include "anim/Vec4.h"

#include <array>
#include <format>
#include <string>

// テストエクスプローラーの失敗メッセージに型の中身を出すための特殊化。
namespace Microsoft::VisualStudio::CppUnitTestFramework {

template<>
inline std::wstring ToString<anim::Vec3>(const anim::Vec3& v) {
    return std::format(L"Vec3({:.9g}, {:.9g}, {:.9g})", v.x, v.y, v.z);
}

template<>
inline std::wstring ToString<anim::Vec4>(const anim::Vec4& v) {
    return std::format(L"Vec4({:.9g}, {:.9g}, {:.9g}, {:.9g})", v.x, v.y, v.z, v.w);
}

}  // namespace Microsoft::VisualStudio::CppUnitTestFramework

namespace anim::test {

// Vec3 の比較は、第 3 章の span 版へそのまま転送する。
inline void AssertNear(const anim::Vec3& expected, const anim::Vec3& actual,
                       float absTol = kDefaultAbsTol,
                       float relTol = kDefaultRelTol,
                       const std::source_location& loc =
                           std::source_location::current()) {
    const std::array<float, 3> e{expected.x, expected.y, expected.z};
    const std::array<float, 3> a{actual.x, actual.y, actual.z};
    AssertNearSpan(e, a, absTol, relTol, loc);
}

inline void AssertNear(const anim::Vec4& expected, const anim::Vec4& actual,
                       float absTol = kDefaultAbsTol,
                       float relTol = kDefaultRelTol,
                       const std::source_location& loc =
                           std::source_location::current()) {
    const std::array<float, 4> e{expected.x, expected.y, expected.z, expected.w};
    const std::array<float, 4> a{actual.x, actual.y, actual.z, actual.w};
    AssertNearSpan(e, a, absTol, relTol, loc);
}

}  // namespace anim::test
```

第 3 章で `AssertNearSpan` を `std::span<const float>` で書いておいた設計が、ここで報われます。新しい型が増えるたびに、成分を並べて転送するだけです。`>> <<` による該当成分のハイライトも、失敗位置の報告もそのまま効きます。

`loc` を明示的に転送している点に注意してください。転送を忘れると、行番号が `MathAssert.h` を指してしまいます（第 3 章のハマりどころで触れたとおりです）。

### 決定論的な乱数

これから何度も「ランダムな入力を 1000 個流して、性質が成り立つことを確かめる」というテストを書きます。そのための乱数生成器が要ります。

要件は 2 つです。**毎回同じ列を出すこと**（失敗が再現できないテストは役に立ちません）と、**軽いこと**です。`std::mt19937` でも構いませんが、状態が 2.5 KB あり、テストごとに作るには重すぎます。xorshift で十分です。

`AnimLib.Tests/TestSupport/TestRandom.h`：

```cpp
#pragma once

#include "anim/Vec3.h"

#include <cstdint>

namespace anim::test {

// 決定論的な擬似乱数。テストを再現可能にすることだけが目的で、
// 統計的な品質は求めていない（xorshift32）。
class TestRandom {
public:
    explicit TestRandom(std::uint32_t seed = 0x12345678u) noexcept : state_(seed) {
        ANIM_ASSERT(seed != 0);   // xorshift は 0 から抜け出せない
    }

    [[nodiscard]] std::uint32_t NextUInt() noexcept {
        state_ ^= state_ << 13;
        state_ ^= state_ >> 17;
        state_ ^= state_ << 5;
        return state_;
    }

    // [0, 1)
    [[nodiscard]] float NextUnit() noexcept {
        // 上位 24 ビットを使う（float の仮数部が 24 ビットのため）
        return static_cast<float>(NextUInt() >> 8) * (1.0f / 16777216.0f);
    }

    [[nodiscard]] float NextRange(float lo, float hi) noexcept {
        return lo + (hi - lo) * NextUnit();
    }

    [[nodiscard]] anim::Vec3 NextVec3(float range = 2.0f) noexcept {
        return {NextRange(-range, range),
                NextRange(-range, range),
                NextRange(-range, range)};
    }

private:
    std::uint32_t state_;
};

}  // namespace anim::test
```

第 8 章でランダムなクォータニオンを、第 13 章でランダムなスケルトンを、それぞれこのクラスに足していきます。

> **なぜテストにランダムを使うのか**
> 具体的な値でのテスト（`Cross({1,0,0},{0,1,0}) == {0,0,1}`）は、想定した状況しか検査しません。一方「どんな `a`, `b` でも `Cross(a,b)` は `a` に垂直」という性質は、1000 個のランダムな入力で検査できます。前者は**仕様の確認**、後者は**バグの発見**に強い。両方書きます。

## 5.10　テストを書く

`AnimLib.Tests/Vec3Tests.cpp`：

```cpp
#include "CppUnitTest.h"

#include "TestSupport/MathAssert.h"
#include "TestSupport/TestRandom.h"
#include "TestSupport/Tolerance.h"

#include "anim/Vec3.h"

using namespace Microsoft::VisualStudio::CppUnitTestFramework;
using namespace anim;
using anim::test::AssertNear;

namespace AnimLibTests {

TEST_CLASS(Vec3Tests) {
public:

    // --- 具体値：仕様の確認 ---------------------------------------

    TEST_METHOD(CrossProductIsRightHanded) {
        AssertNear(Vec3{0, 0, 1}, Cross({1, 0, 0}, {0, 1, 0}));   // X × Y = Z
        AssertNear(Vec3{1, 0, 0}, Cross({0, 1, 0}, {0, 0, 1}));   // Y × Z = X
        AssertNear(Vec3{0, 1, 0}, Cross({0, 0, 1}, {1, 0, 0}));   // Z × X = Y
    }

    TEST_METHOD(CrossProductIsAntiCommutative) {
        const Vec3 a{1, 2, 3};
        const Vec3 b{4, 5, 6};
        AssertNear(-Cross(a, b), Cross(b, a));
    }

    TEST_METHOD(DotOfOrthogonalIsZero) {
        anim::test::AssertNear(0.0f, Dot({1, 0, 0}, {0, 1, 0}), test::kEpsDir);
    }

    // --- 性質：バグの発見 -----------------------------------------

    TEST_METHOD(NormalizeGivesUnitLength) {
        test::TestRandom rng;
        for (int i = 0; i < 1000; ++i) {
            const Vec3 v = rng.NextVec3();
            if (LengthSquared(v) < 1.0e-6f) {
                continue;   // ほぼゼロは対象外
            }
            anim::test::AssertNear(1.0f, Length(Normalize(v)), test::kEpsUnit);
        }
    }

    TEST_METHOD(TriangleInequality) {
        test::TestRandom rng;
        for (int i = 0; i < 1000; ++i) {
            const Vec3 a = rng.NextVec3();
            const Vec3 b = rng.NextVec3();
            Assert::IsTrue(Length(a + b) <= Length(a) + Length(b) + test::kEpsPos);
        }
    }

    TEST_METHOD(CrossIsPerpendicularToBothInputs) {
        test::TestRandom rng;
        for (int i = 0; i < 1000; ++i) {
            const Vec3 a = rng.NextVec3();
            const Vec3 b = rng.NextVec3();
            const Vec3 c = Cross(a, b);
            // a, b の大きさに比例して誤差も大きくなるので、相対で見る
            const float scale = Length(a) * Length(b) + 1.0f;
            anim::test::AssertNear(0.0f, Dot(c, a) / scale, test::kEpsDir);
            anim::test::AssertNear(0.0f, Dot(c, b) / scale, test::kEpsDir);
        }
    }

    // ラグランジュの恒等式：|a×b|² = |a|²|b|² - (a·b)²
    // 内積と外積の実装が独立に正しいことを、一本の式で同時に検査できる
    TEST_METHOD(LagrangeIdentity) {
        test::TestRandom rng;
        for (int i = 0; i < 1000; ++i) {
            const Vec3 a = rng.NextVec3();
            const Vec3 b = rng.NextVec3();
            const float lhs = LengthSquared(Cross(a, b));
            const float rhs = LengthSquared(a) * LengthSquared(b) - Dot(a, b) * Dot(a, b);
            anim::test::AssertNear(lhs, rhs, test::kEpsAccum, 1.0e-4f);
        }
    }

    // --- 境界 -----------------------------------------------------

    TEST_METHOD(NormalizeSafeHandlesZero) {
        const Vec3 up{0, 1, 0};
        AssertNear(up, NormalizeSafe({0, 0, 0}, up));
        AssertNear(up, NormalizeSafe({1.0e-20f, 0, 0}, up));
        // 十分な長さがあれば fallback は使われない
        AssertNear(Vec3{1, 0, 0}, NormalizeSafe({5, 0, 0}, up));
    }
};

}  // namespace AnimLibTests
```

**`LagrangeIdentity` に注目してください。** これは `Dot` と `Cross` を結びつける恒等式で、片方だけが間違っていれば必ず破れます。「1 本のテストで 2 つの関数の整合性を検査する」という、性質テストのうまみが出ている例です。

許容誤差に `test::kEpsAccum`（1.0e-3）を使っているのは、ここで扱う量が**長さの 4 乗のオーダー**になるためです。成分が ±2 なら `|a|²|b|²` は 100 を超えます。第 4 章で決めた「量に応じた許容誤差」の考え方が、こういう場面で効いてきます。

## 5.11　つまずきやすいところ

**`error C2440` : `Vec3` を `{}` で初期化できない**
コンストラクタやプライベートメンバを追加していないか確認してください。集成体でなくなると波括弧初期化ができなくなります。

**`AssertNear` があいまいだと言われる**
`anim::test::AssertNear`（float 版、`Near.h`）と、`anim::test::AssertNear`（Vec3 版、`MathAssert.h`）が同じ名前空間にあります。これは意図した多重定義なので、両方のヘッダがインクルードされていれば正しく解決されます。`using anim::test::AssertNear;` を書く場合、片方のヘッダしか見えていないと候補が足りません。`MathAssert.h` は `Near.h` を include しているので、`MathAssert.h` だけを include すれば足ります。

**外積の符号が逆になる**
`y` 成分を `a.x*b.z - a.z*b.x` と書いていませんか。正しくは `a.z*b.x - a.x*b.z` です。`CrossProductIsRightHanded` のテストが即座に捕まえます。

**`Normalize` がデバッグビルドでアサートに引っかかる**
これは仕様どおりの動作です。呼び出し元が長さ 0 のベクトルを渡しています。その場所で「なぜ長さ 0 になりうるのか」を考えてください。答えが「起こりうる」なら `NormalizeSafe` に置き換え、「起こらないはず」なら上流のバグです。

**`ToString` の特殊化が効かない**
特殊化は**使用する前に**見えていなければなりません。`MathAssert.h` を `CppUnitTest.h` より後にインクルードしていれば大丈夫です。また、名前空間を閉じる位置を間違えると（`anim::test` の中に書いてしまうなど）静かに無視されます。

## この章のまとめ

- 本書は**右手系・Y-up・-Z 前方**、単位はメートルとラジアン。glTF と一致させることで、第 34 章の座標系変換を不要にした。
- `Vec3` は**コンストラクタを持たない集成体**にした。`memcpy` 可能・`constexpr` 可能・初期化漏れが警告される、という 3 つの性質を得るため。
- 正規化のゼロ長問題には**契約（`Normalize` + `ANIM_ASSERT`）と明示的な安全版（`NormalizeSafe`）を併置**した。安全側を既定にするとバグが隠れる。
- `LengthSquared` を分けて持つ。長さの**比較**に平方根は要らない。
- テストは**具体値（仕様の確認）と性質（バグの発見）の二本立て**。`LagrangeIdentity` のように、複数の関数の整合性を 1 本で検査できる恒等式は特に価値が高い。
- `AssertNearSpan` に転送する形にしたので、新しい型が増えても数行で対応できる。

次章では `Mat4` を作ります。その前に、**行優先か列優先か、行ベクトルか列ベクトルか**という、この分野で最も多くの人が混乱する 2 つの選択に決着をつけます。
