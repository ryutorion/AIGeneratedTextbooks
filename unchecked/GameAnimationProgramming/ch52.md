# 第 52 章　データ指向へ再設計する

**この章で作るもの**：キャラクター 1 体ずつではなく、**100 体をまとめて更新する**データ構造。そして ―― この章の結論を先に書いておきます。**データ指向に並べ替えただけでは、速くなりませんでした。むしろ 1000 体で 2.7 倍遅くなりました。**

なぜそれでもやるのか。その答えは第 53 章にあります。

---

## 52.1　第 IX 部で何をするか

ここまでの 51 章で、アニメーションシステムは完成しています。glTF を読み、クリップを再生し、ブレンドし、IK で足を接地させ、スキニング行列パレットを出力する。**1 体を正しく動かす**という目標は達成しました。

第 IX 部の目標は違います。**100 体を、60 fps で動かす。**

まず現状を測ります。60 ボーンの骨格、1 体の更新（サンプル → 階層解決 → パレット生成）にかかる時間は ―― 実測 **`6.734` µs**。

```
100 体 → 673 µs
1 フレームの予算（60 fps）→ 16,667 µs
```

4% です。「もう足りているのでは?」と思うかもしれません。しかし実際のゲームでは、この 16.7 ms のほとんどを描画・物理・AI・ゲームロジックが使います。**アニメーションに割り当てられるのは、せいぜい 1〜2 ms**。そして 100 体では済まず、群衆シーンでは 500 体、1000 体になります。

第 IX 部で使う道具は 5 つです。

| 章 | 手段 | 効くところ |
|---|---|---|
| 52 | データ指向レイアウト | 53 章の土台 |
| 53 | SIMD | 計算そのもの |
| 54〜56 | キーフレーム圧縮 | メモリ帯域とロード時間 |
| 57 | マルチスレッド | コア数ぶんの並列 |
| 58 | GPU スキニング | 頂点変形の丸投げ |
| 59 | 更新の間引きと LOD | **やらずに済ませる** |

最後の 59 章が、たいてい一番効きます。**最も速いコードは、実行されないコードです。**

## 52.2　最適化の前に、盾を用意する

第 IX 部でやることは、**すべて「動いているものを書き換える」作業**です。第 I 部から第 VIII 部までで、テストは数百個あります。これが盾になります。

> **第 IX 部のルールは 1 つ。「既存のテストが 1 つも赤くならないこと」。**

ただし、それだけでは足りません。速い実装を追加したとき、それが遅い実装と同じ答えを出すことを確かめる必要があります。第 1 章で挙げた**③ 実装間の一致テスト**です。

```cpp
TEST_METHOD(FastMatchesReference) {
    // 同じ入力を両方に与えて、出力が一致することを確かめる
    // 「一致」の許容範囲をいくつにするかが、実は一番の設計判断
}
```

そして**④ ゴールデンテスト**。ある時点の出力をファイルに保存しておき、以降の変更でそれが変わらないことを確かめます。

```cpp
TEST_METHOD(GoldenPaletteUnchanged) {
    // 1 秒分のシミュレーションを回してパレットを全部ダンプし、
    // 保存済みのバイナリと突き合わせる
}
```

**ゴールデンテストは「正しさ」を保証しません。** 保証するのは「変わっていないこと」だけです。それでも、大規模なリファクタリングでは命綱になります。何かが変わったら、それが**意図した変更なのか事故なのか**を、必ず考えることになるからです。

## 52.3　AoS ―― 今の形

現在のデータ構造を確認します。

```cpp
struct Transform {
    Vec3 translation;   // 12 バイト
    Quat rotation;      // 16 バイト
    Vec3 scale;         // 12 バイト
};                      // 合計 40 バイト

class Pose {
    std::vector<Transform> locals_;
};
```

`Transform` という構造体が並んだ配列 ―― **AoS（Array of Structures、構造体の配列）** です。

100 体分のポーズは、`Pose` が 100 個。1 体ずつ更新します。

```cpp
for (int c = 0; c < characterCount; ++c)
    for (std::size_t i = 0; i < boneCount; ++i) {
        const BoneIndex p = skeleton.ParentOf(i);
        global[c][i] = (p == kNoParent) ? local[c][i] : Combine(global[c][p], local[c][i]);
    }
```

この形の何が問題か。**問題はありません。** 実際、キャッシュの観点ではむしろ良い形です。1 体分のデータは `60 × 40 × 2 = 4.8` KB で L1 に収まり、順番に読むので先読みも効きます。

問題は、**SIMD にできない**ことです。

`Combine` の中身は「クォータニオンの積 + ベクトルの回転 + スケールの掛け算」。1 つの `Transform` を処理するのに使う演算は、4 要素にも 8 要素にも揃いません。`Quat` は 4 成分ですが `Vec3` は 3 成分で、しかも計算の途中で内積や外積が出てきて、レーン間の足し算（水平加算）が必要になります。**SIMD レジスタの幅を使い切れません。**

そして根本的な障害があります。**階層があるので、1 体の中では並列化できません。** 子の計算には親の結果が要る。60 本のボーンは、依存関係のある鎖です。

---

## 52.4　並列にできるものは何か

行き詰まったら、「何が独立しているか」を数え直します。

- **同じキャラクターの、親と子** → 依存する。並列にできない。
- **同じキャラクターの、兄弟ボーン** → 独立している。でも兄弟の数は場所によってバラバラで、SIMD の幅に揃わない。
- **違うキャラクターの、同じボーン** → **完全に独立している。**

3 つ目です。100 体の「ボーン 5 番」は、互いにまったく関係ありません。しかも**同じ計算**をします。**100 個ぶんの、まったく同じ形の仕事**が並んでいる。これが SIMD の理想形です。

やるべきデータの並べ替えが決まりました。

```
今（AoS）:
  キャラ 0: [ボーン0][ボーン1][ボーン2] ...
  キャラ 1: [ボーン0][ボーン1][ボーン2] ...

これから（キャラクター方向の SoA）:
  ボーン 0 の tx: [キャラ0][キャラ1][キャラ2] ... [キャラ99]
  ボーン 0 の ty: [キャラ0][キャラ1][キャラ2] ... [キャラ99]
  ...
  ボーン 1 の tx: [キャラ0][キャラ1][キャラ2] ... [キャラ99]
```

**ボーンごとに、成分ごとに、キャラクター数だけ並んだ配列。** これなら「ボーン 5 番の tx を 8 個まとめて読む」が 1 命令でできます。

## 52.5　PoseBatch

```cpp
// AnimLib/include/anim/PoseBatch.h
#pragma once

#include "anim/Skeleton.h"

namespace anim {

// キャラクター方向に SoA 化したポーズ群。
// 添字は [bone * Stride() + character]。
class PoseBatch {
public:
    PoseBatch() = default;
    PoseBatch(std::size_t bones, std::size_t characters)
        : bones_(bones), count_(characters),
          cap_((characters + 15) / 16 * 16) {          // 16 の倍数へ切り上げ
        const std::size_t n = bones_ * cap_;
        tx_.assign(n,0.0f); ty_.assign(n,0.0f); tz_.assign(n,0.0f);
        qx_.assign(n,0.0f); qy_.assign(n,0.0f); qz_.assign(n,0.0f); qw_.assign(n,1.0f);
        sx_.assign(n,1.0f); sy_.assign(n,1.0f); sz_.assign(n,1.0f);
    }

    [[nodiscard]] std::size_t BoneCount() const noexcept { return bones_; }
    [[nodiscard]] std::size_t Count()     const noexcept { return count_; }
    [[nodiscard]] std::size_t Stride()    const noexcept { return cap_; }
    [[nodiscard]] std::size_t Index(std::size_t bone, std::size_t ch) const noexcept {
        return bone*cap_ + ch;
    }

    void Set(std::size_t bone, std::size_t ch, const Transform& t);
    [[nodiscard]] Transform Get(std::size_t bone, std::size_t ch) const;

    std::vector<float> tx_, ty_, tz_, qx_, qy_, qz_, qw_, sx_, sy_, sz_;
private:
    std::size_t bones_ = 0, count_ = 0, cap_ = 0;
};

}  // namespace anim
```

**3 つの設計判断**があります。

**① `cap_` を 16 の倍数に切り上げる。** キャラクター数が 100 でも、確保するのは 112 個ぶん。SIMD が 8 個ずつ（AVX2）や 16 個ずつ（AVX-512）処理するとき、**末尾の端数処理を書かなくて済む**ようにするためです。余った分にはゴミが入りますが、誰も読みません。数キロバイトの無駄と引き換えに、ループが 1 本になります。

**② 配列を 10 本に分ける。** `Vec3` を 1 本の配列にせず、`x`・`y`・`z` を別々にします。SIMD で「8 体ぶんの x」を連続で読みたいからです。

**③ メンバを公開している。** `tx_` などを `public` にしています。行儀は悪いですが、SIMD のコードは配列の先頭ポインタを直接欲しがります。**「速さのための構造体」に、アクセサでフタをするのは無意味**です ―― `data()` を返すアクセサを 10 個並べるくらいなら、公開したほうが正直です。

代わりに、**`Set` / `Get` で `Transform` との相互変換**を用意しておきます。テストと、SoA 化していないコードとの橋渡しです。

```cpp
void PoseBatch::Set(std::size_t bone, std::size_t ch, const Transform& t){
    const std::size_t i = Index(bone,ch);
    tx_[i]=t.translation.x; ty_[i]=t.translation.y; tz_[i]=t.translation.z;
    qx_[i]=t.rotation.x; qy_[i]=t.rotation.y; qz_[i]=t.rotation.z; qw_[i]=t.rotation.w;
    sx_[i]=t.scale.x; sy_[i]=t.scale.y; sz_[i]=t.scale.z;
}
Transform PoseBatch::Get(std::size_t bone, std::size_t ch) const {
    const std::size_t i = Index(bone,ch);
    return { {tx_[i],ty_[i],tz_[i]}, {qx_[i],qy_[i],qz_[i],qw_[i]}, {sx_[i],sy_[i],sz_[i]} };
}
```

## 52.6　SoA 版の階層解決

`Combine` を手で展開します。ループの内側にキャラクターが来ます。

```cpp
inline void ComputeGlobalSoA(const Skeleton& s, const PoseBatch& local, PoseBatch& global){
    const std::size_t n = s.BoneCount();
    const std::size_t m = local.Count();
    const std::size_t stride = local.Stride();

    for (std::size_t b = 0; b < n; ++b) {          // ボーンが外
        const BoneIndex p = s.ParentOf(static_cast<BoneIndex>(b));
        const std::size_t o = b * stride;

        if (p == kNoParent) {                       // ルート：そのままコピー
            for (std::size_t c = 0; c < m; ++c) { /* 10 本の配列をコピー */ }
            continue;
        }

        const std::size_t q = static_cast<std::size_t>(p) * stride;
        for (std::size_t c = 0; c < m; ++c) {       // キャラクターが内
            const float pqx=global.qx_[q+c], pqy=global.qy_[q+c],
                        pqz=global.qz_[q+c], pqw=global.qw_[q+c];
            const float psx=global.sx_[q+c], psy=global.sy_[q+c], psz=global.sz_[q+c];
            const float cqx=local.qx_[o+c], cqy=local.qy_[o+c],
                        cqz=local.qz_[o+c], cqw=local.qw_[o+c];

            // 回転の合成（Quat operator* をそのまま展開）
            global.qx_[o+c] = pqw*cqx + pqx*cqw + pqy*cqz - pqz*cqy;
            global.qy_[o+c] = pqw*cqy - pqx*cqz + pqy*cqw + pqz*cqx;
            global.qz_[o+c] = pqw*cqz + pqx*cqy - pqy*cqx + pqz*cqw;
            global.qw_[o+c] = pqw*cqw - pqx*cqx - pqy*cqy - pqz*cqz;

            // スケール
            global.sx_[o+c] = psx*local.sx_[o+c];
            global.sy_[o+c] = psy*local.sy_[o+c];
            global.sz_[o+c] = psz*local.sz_[o+c];

            // 平行移動：Rotate() と同じ順序で書く
            //   t = 2(u × v);   v + w·t + (u × t)
            const float vx = psx*local.tx_[o+c], vy = psy*local.ty_[o+c], vz = psz*local.tz_[o+c];
            const float tx = 2.0f*(pqy*vz - pqz*vy);
            const float ty = 2.0f*(pqz*vx - pqx*vz);
            const float tz = 2.0f*(pqx*vy - pqy*vx);
            global.tx_[o+c] = global.tx_[q+c] + (vx + pqw*tx + (pqy*tz - pqz*ty));
            global.ty_[o+c] = global.ty_[q+c] + (vy + pqw*ty + (pqz*tx - pqx*tz));
            global.tz_[o+c] = global.tz_[q+c] + (vz + pqw*tz + (pqx*ty - pqy*tx));
        }
    }
}
```

**「`Rotate()` と同じ順序で書く」というコメント**が、この関数で最も重要な行かもしれません。

`Rotate(q, v)` の中身は第 8 章でこう決めました。

```cpp
inline Vec3 Rotate(const Quat& q, Vec3 v) {
    const Vec3 u{q.x,q.y,q.z};
    const Vec3 t = 2.0f * Cross(u, v);
    return v + q.w * t + Cross(u, t);
}
```

数学的に等価な書き方はいくらでもあります。`2.0f*(pqw*ux + wx)` と書いても答えは同じ ―― **実数なら**。`float` では、**足す順序が変わると結果のビットが変わります**。

ここで結果がビット単位で一致していれば、③ 実装間の一致テストの許容範囲を **`0`** にできます。「だいたい合っている」ではなく「完全に同じ」を主張できる。これは後々、とても効いてきます。

## 52.7　単体テスト：AoS と一致するか

```cpp
TEST_METHOD(SoaMatchesAos) {
    Skeleton s = MakeHumanoid(60);
    const int M = 1000;

    // 同じ内容を AoS と SoA の両方に入れる
    std::vector<std::vector<Transform>> aosL(M), aosG(M);
    PoseBatch soaL(60, M), soaG(60, M);
    /* ... ランダムな回転で埋める ... */

    ComputeGlobalAoS(s, aosL, aosG);
    ComputeGlobalSoA(s, soaL, soaG);

    float worstPos = 0.0f, worstRot = 0.0f;
    for (int c = 0; c < M; ++c)
        for (int b = 0; b < 60; ++b) {
            const Transform a = aosG[c][b], d = soaG.Get(b, c);
            worstPos = std::fmax(worstPos, Length(a.translation - d.translation));
            worstRot = std::fmax(worstRot,
                std::fabs(a.rotation.x-d.rotation.x) + std::fabs(a.rotation.y-d.rotation.y) +
                std::fabs(a.rotation.z-d.rotation.z) + std::fabs(a.rotation.w-d.rotation.w));
        }
    Assert::AreEqual(0.0f, worstPos, 0.0f);     // ビット単位で一致すること
    Assert::AreEqual(0.0f, worstRot, 0.0f);
}
```

実測 ―― **`平行移動の最大差 0.000000000 / 回転の最大差 0.000000000`**。60,000 個の `Transform` すべてがビット単位で一致しました。

### 測り方を間違えた話

最初に書いた回転の比較は、これでした。

```cpp
worstRot = std::fmax(worstRot, std::fabs(1.0f - std::fabs(Dot(a.rotation, d.rotation))));
```

「2 つの単位クォータニオンの内積は 1 のはず」という発想です。結果は **`0.000001132`** ―― 一致していないように見えました。

しかし `a` と `d` は**ビット単位で同じ値**でした。内積が 1 にならなかったのは、**このクォータニオンが単位長ではなかった**からです。階層を 8 段たどる過程で、掛け算の誤差が積もっている（第 48 章で見たのと同じ現象です）。`Dot(a, a) = |a|²` が `1 ± 1e-6` になっていた。

**私が測っていたのは「一致度」ではなく「単位長からのずれ」でした。** 成分ごとの差に書き換えたら、答えは `0.000000000` でした。

> **一致テストが赤いとき、疑うべき容疑者は 3 人いる。** 新しい実装、古い実装、そして**測り方**。第 55 章でも、まったく同じ罠を踏むことになります。

## 52.8　測定 ―― そして、速くならない

同じ計算を、AoS と SoA で。1 体あたりのナノ秒です。

| キャラクター数 | AoS | SoA | 倍率 |
|---|---|---|---|
| 16 | `447.0` ns | `388.4` ns | 1.15× |
| 100 | `437.1` ns | `386.5` ns | 1.13× |
| 1000 | `421.3` ns | **`1161.6` ns** | **0.36×** |
| 4000 | `469.0` ns | **`1262.2` ns** | **0.37×** |

**100 体までは 1.13〜1.15 倍。1000 体では 2.7 倍遅い。**

データ指向にすると速くなる、と一般に言われます。実測はそうなりませんでした。

### 犯人を探す

**仮説 1：エイリアシングで自動ベクトル化が止まっている。** `local.qx_` と `global.qx_` が同じメモリを指す可能性をコンパイラが排除できず、スカラーのままになっている ―― ありそうです。`__restrict` を付けて確かめます。

| キャラクター数 | SoA | SoA + `__restrict` |
|---|---|---|
| 100 | `386.5` ns | `379.3` ns |
| 1000 | `1161.6` ns | `1153.1` ns |
| 4000 | `1262.2` ns | `1289.5` ns |

**変わりませんでした。** 仮説 1 は棄却。

**仮説 2：キャッシュに乗り切っていない。** 1000 体では `PoseBatch` 1 つが `60 × 1008 × 10 × 4 = 2.4` MB、入力と出力で 4.8 MB。L2 を超えています。だとすれば、**キャラクターを小分けにして処理すれば直る**はずです。タイル化してみます。

| タイル幅 | 1000 体 | 4000 体 |
|---|---|---|
| なし | `1316.5` ns | `1252.4` ns |
| 8 | `1183.8` ns | `1049.3` ns |
| 16 | `1097.8` ns | `1031.8` ns |
| 32 | `1183.2` ns | `1220.5` ns |
| 64 | `1239.5` ns | `1303.9` ns |
| 256 | `1358.8` ns | `1353.9` ns |

多少は改善しますが（`1316 → 1098`）、AoS の `421` ns には遠く及びません。**仮説 2 も、これだけでは説明できません。**

**残った説明。** AoS は 1 体分のデータを**連続して**読みます。ハードウェアの先読み器にとって理想的なパターンです。SoA は 1 ボーンの処理ごとに、10 本の入力配列と 10 本の出力配列、さらに親の 10 本 ―― **同時に 20〜30 本の飛び飛びの流れ**を追いかけます。先読み器が追跡できるストリーム数には上限があり、それを超えると効きません。そしてスカラーコードは 1 回のループで 4 バイトしか進まないので、キャッシュミスを重ねて隠すこともできない。

## 52.9　それでも、この形にする理由

ここで引き返すべきでしょうか。

**引き返しません。** 第 53 章の先取りになりますが、同じ `PoseBatch` を AVX2 で 8 体同時に処理すると、こうなります。

| キャラクター数 | AoS | SoA（スカラー） | SoA + AVX2 |
|---|---|---|---|
| 16 | `447.0` ns | `388.4` ns (1.15×) | **`117.6` ns (3.80×)** |
| 100 | `437.1` ns | `379.3` ns (1.15×) | **`142.1` ns (3.08×)** |
| 1000 | `421.3` ns | `1153.1` ns (0.37×) | **`259.6` ns (1.62×)** |
| 4000 | `469.0` ns | `1289.5` ns (0.36×) | **`310.3` ns (1.51×)** |

**SoA 単体では 0.37 倍。SIMD と組み合わせると 1.51〜3.80 倍。**

52.8 で書いた「1 回のループで 4 バイトしか進まない」が、そのまま答えになっています。AVX2 は 1 回で 32 バイト進みます。同じキャッシュミスを、8 分の 1 の命令数で処理する。**先読みが効かない場所を、命令レベルの並列性で埋めている。**

> **データ指向レイアウトは、それ自体が最適化ではない。SIMD を可能にするための前提条件である。**
>
> 前提条件だけ整えて、本体をやらなければ、遅くなるだけです。

## 52.10　システム単位の更新へ

レイアウトを変えたので、更新の書き方も変えます。

これまでは「キャラクターが自分を更新する」形でした。

```cpp
class Character {
public:
    void Update(float dt) {              // 1 体が全部やる
        player_.Advance(dt);
        player_.Evaluate(pose_);
        ComputeGlobalPose(*skeleton_, pose_.Locals(), global_);
        BuildSkinPalette(global_, invBind_, palette_);
    }
};
```

データ指向では「**システムが全員を、段階ごとに更新する**」形にします。

```cpp
class AnimationSystem {
public:
    void Update(float dt) {
        AdvanceAllTimes(dt);          // 全員の時刻を進める
        SampleAllClips();             // 全員をサンプル       → PoseBatch
        SolveAllHierarchies();        // 全員の階層を解く     → PoseBatch
        SolveAllIk();                 // 全員の IK
        BuildAllPalettes();           // 全員のパレット
    }
private:
    const Skeleton* skeleton_;
    PoseBatch localPoses_, globalPoses_;
    std::vector<float> times_;
    std::vector<Mat4>  palettes_;
};
```

**同じ処理を、全員ぶん、まとめてやる。** これがデータ指向設計の核心で、レイアウトの話はその結果にすぎません。

この形には、SIMD 以外にも 3 つの利点があります。

**① 分岐が減る。** 「このキャラクターは IK を使うか」「ブレンドツリーはあるか」といった判定を、1 体ずつ聞いて回る代わりに、**先に仕分けて**、それぞれのリストをまとめて処理できます。

**② 並列化の単位が明確になる。** 「`SampleAllClips` を 4 スレッドで分割する」と言えます。第 57 章はこの形の上に乗ります。

**③ 依存関係がコードに現れる。** `SolveAllHierarchies` は `SampleAllClips` の後でなければならない ―― それが関数の並び順として見えます。1 体ずつの `Update()` に埋もれていると、この順序は暗黙のままです。

**欠点も正直に書いておきます。** キャラクター 1 体の処理を追いかけるのが難しくなります。デバッガで「このキャラクターがなぜ変なポーズになるのか」を調べるとき、AoS なら 1 つのオブジェクトを見れば済みますが、SoA では 10 本の配列の同じ添字を見て回ることになります。`Get(bone, ch)` を用意したのは、そのためでもあります。

## 52.11　どこまで SoA にするか

すべてを SoA にする必要はありません。**測って、効くところだけ**です。

| データ | SoA にするか | 理由 |
|---|---|---|
| ポーズ（local / global） | **する** | 全員に同じ計算。SIMD が効く |
| スキニング行列パレット | **する** | 同上 |
| 頂点データ | **する**（第 20 章で済み） | 同上 |
| クリップのキーフレーム | しない | 探索が主で、計算は少ない |
| ステートマシンの状態 | しない | 分岐だらけで SIMD にならない |
| IK チェーン | しない | チェーンの長さがバラバラ |

**IK を SoA にしない**のは、少し説明が要ります。キャラクターごとに IK チェーンの本数も長さも違い、反復回数も収束によって変わります。「8 体まとめて 4 反復」とやると、1 体だけ 12 反復必要な場合に全員が 12 反復することになり、SIMD の利得を無駄が食い潰します。**揃っていない仕事は SIMD に向きません。**

## この章のまとめ

- 第 IX 部の目標は「1 体を正しく」から「**100 体を速く**」へ。現状の実測は **1 体 `6.734` µs**。
- **最適化の前に盾を用意する。** 既存のテストが 1 つも赤くならないこと + 実装間の一致テスト + ゴールデンテスト。
- 階層があるので **1 体の中では並列化できない**。独立しているのは「**違うキャラクターの、同じボーン**」。だからキャラクター方向に SoA 化する。
- `PoseBatch` の設計判断：**16 の倍数に切り上げ**て端数処理を消す、**成分ごとに配列を分ける**、**メンバを公開する**（速さのための構造体にフタをしない）。
- SoA 版は **`Rotate()` とまったく同じ演算順序**で書く。`float` は足す順序で結果のビットが変わる。揃えておけば、一致テストの許容範囲を **`0`** にできる。
- 実測は **60,000 個の `Transform` すべてがビット単位で一致**。
- **測り方を間違えた**：内積で比較したら `1.13e-6` の差が出たが、それは一致度ではなく**クォータニオンの単位長からのずれ**だった。**一致テストが赤いとき、容疑者は 3 人 ―― 新実装、旧実装、そして測り方。**
- **そして、速くならなかった。** 100 体で 1.15 倍、**1000 体で 0.36 倍（2.7 倍遅い）**。`__restrict` も効かず、タイル化も焼け石に水。原因は、同時に追う飛び飛びのストリームが 20〜30 本になり、先読みが効かなくなること。
- それでも進む理由：**同じレイアウトを AVX2 で 8 体同時に処理すると 1.51〜3.80 倍**になる。
- **データ指向レイアウトは、それ自体が最適化ではない。SIMD を可能にするための前提条件である。**
- 更新は「キャラクターが自分を更新する」から「**システムが全員を段階ごとに更新する**」へ。分岐が減り、並列化の単位が明確になり、依存関係がコードに現れる。
- **すべてを SoA にしない。** 揃っていない仕事（IK、ステートマシン）は SIMD に向かない。

次章で、その SIMD を書きます。そして ―― **素直に SIMD 化したスキニングは、スカラー版より 2 倍遅くなりました。** そこからどう直したかが、第 53 章の中身です。
