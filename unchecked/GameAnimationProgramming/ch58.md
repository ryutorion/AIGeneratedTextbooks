# 第 58 章　GPU スキニング

**この章で作るもの**：頂点変形を GPU へ移す設計と HLSL のシェーダ。そして ―― **描画せずに検証する**方法。

この本で唯一、D3D12 に触れる章です。そして、**行列のパッキング規約で必ず一度は壊れる**章でもあります。4 通り全部を測って、どれが正しいかを確かめます。

---

## 58.1　なぜ GPU なのか

第 53 章で、CPU スキニングを AVX2 で 4.61 倍にしました。1 頂点あたり `7.11` ns が `1.54` ns。4 万頂点のキャラクターで `62` µs です。

100 体なら **6.2 ms**。60 fps の 1 フレーム 16.7 ms のうち、37% をスキニングだけで使うことになります。しかも 2 コアで並列化しても 3.2 ms。

GPU に渡す理由は、単に速いからではありません。**データの流れが素直になる**からです。

```
CPU スキニング:
  パレットを作る → CPU で頂点を変形 → 変形後の頂点を GPU へ転送 → 描画
                                        ↑ 毎フレーム 40,000 頂点 × 24 B = 960 KB

GPU スキニング:
  パレットを作る → パレットを GPU へ転送 → 頂点シェーダで変形しながら描画
                    ↑ 毎フレーム 60 ボーン × 48 B = 2.8 KB
```

**転送量が 340 分の 1 になります。** 頂点データ（位置・法線・ジョイント・ウェイト）は変形前のもので、**毎フレーム変わりません**。一度 GPU に置けば、あとはパレットだけを送ればいい。

第 53 章で「1000 体ではメモリ帯域が律速」と測りました。GPU スキニングは、その帯域を根本から減らします。

## 58.2　パレットをどう送るか

送るのは第 16 章のスキニング行列パレット ―― `ToMat4(global[i]) * invBind[i]` です。

```cpp
struct Mat4 { float m[4][4]; };     // 行優先格納、列ベクトル規約（第 6 章）
```

60 ボーンで `60 × 64 = 3,840` バイト。定数バッファ（cbuffer）の上限は 64 KB なので入りますが、**構造化バッファ（StructuredBuffer）** を使うほうが素直です。

- 定数バッファはサイズ上限があり、キャラクター 100 体分（384 KB）は入らない
- 構造化バッファならインデックスで引ける（`palette[instanceID * boneCount + jointIndex]`）
- インスタンス描画で 100 体を 1 ドローコールにまとめられる

```hlsl
StructuredBuffer<float3x4> g_palette : register(t0);
```

**なぜ `float4x4` でなく `float3x4` か。** スキニング行列の最下行は常に `(0, 0, 0, 1)` です（回転・スケール・平行移動の合成にはせん断も射影もない）。送る必要がありません。

```
4x4: 64 バイト × 60 ボーン = 3,840 B
3x4: 48 バイト × 60 ボーン = 2,880 B    （25% 削減）
```

1000 体なら **3,750 KB → 2,812 KB**。毎フレームの転送でこれは効きます。

## 58.3　行優先・列優先の罠

ここが本章の山場です。

第 6 章で、この本の規約を決めました。

- **列ベクトル**：`v' = M v`。合成は右のものが先に適用される
- **行優先格納**：`m[row][col]`、メモリ上は `m[0][0], m[0][1], m[0][2], m[0][3], m[1][0], ...`
- 平行移動は float の 3, 7, 11 番目

HLSL の既定は違います。**`float4x4` は既定で `column_major` にパッキングされます。**

「パッキング」とは、**メモリ上の 16 個の `float` を、論理的な行列のどこに割り当てるか**という規則です。

```
column_major（HLSL の既定）:
  レジスタ k = 論理行列の「列 k」
  → M[row][col] = floats[4*col + row]

row_major（明示指定した場合）:
  レジスタ k = 論理行列の「行 k」
  → M[row][col] = floats[4*row + col]
```

**この本の `Mat4` をそのまま送ると、HLSL は転置された行列として読みます。**

```
CPU 上のメモリ:  m00 m01 m02 m03 | m10 m11 m12 m13 | m20 m21 m22 m23 | m30 m31 m32 m33
                 ← 行 0 →         ← 行 1 →

HLSL が読む:     ← 列 0 →         ← 列 1 →
                 M[0][0]=m00      M[0][1]=m10
                 M[1][0]=m01      M[1][1]=m11
                 ...
                 → 論理的には Mᵀ
```

**平行移動が最下行に入り、回転が転置され、絵が完全に壊れます。** しかも「なんとなく歪む」のではなく、原点から吹き飛びます。

対処は 2 つ、どちらか一方だけを選びます。

**① 転送前に CPU 側で転置する。**

```cpp
const Mat4 t = Transpose(palette[b]);
std::memcpy(dst, t.m, sizeof(float)*16);
```

**② HLSL で `row_major` を明示する。**

```hlsl
StructuredBuffer<row_major float4x4> g_palette : register(t0);
```

**両方やると、また壊れます。** 転置の転置は元に戻るので、①と②を同時にやると最初と同じ間違いになります。

## 58.4　描画せずに検証する

「絵が壊れます」と書きましたが、**この本では描画しません**。では、どうやって確かめるか。

第 1 章で決めた方針 ―― **アニメーションシステムの出力はスキニング行列パレットであり、描画は含まれない** ―― をここでも守ります。

やることは 2 つです。

**① HLSL のパッキング規則を、CPU 上で再現する。**

```cpp
struct HlslMatrix { float f[16]; };      // 定数バッファ上の 16 float

// HLSL の mul(M, v)（v は列ベクトル）を、既定パッキングで
static Vec4 HlslMulColumnMajor(const HlslMatrix& m, Vec4 v){
    auto M = [&](int r, int c){ return m.f[4*c + r]; };      // ← 既定
    return { M(0,0)*v.x + M(0,1)*v.y + M(0,2)*v.z + M(0,3)*v.w,
             M(1,0)*v.x + M(1,1)*v.y + M(1,2)*v.z + M(1,3)*v.w,
             M(2,0)*v.x + M(2,1)*v.y + M(2,2)*v.z + M(2,3)*v.w,
             M(3,0)*v.x + M(3,1)*v.y + M(3,2)*v.z + M(3,3)*v.w };
}
// row_major 指定時
static Vec4 HlslMulRowMajor(const HlslMatrix& m, Vec4 v){
    auto M = [&](int r, int c){ return m.f[4*r + c]; };      // ← こちら
    /* 同じ式 */
}
```

**この 2 つの関数の違いは、添字の式 1 つだけです。** `4*c + r` と `4*r + c`。そこにすべてが凝縮されています。

**② コンピュートシェーダを CPU でエミュレートする。**

```cpp
static void EmulateSkinningCS(std::span<const GpuVertex> in,
                              std::span<const HlslMatrix> palette,
                              std::span<Vec3> outPos,
                              bool rowMajorDecl){
    for (std::size_t i = 0; i < in.size(); ++i) {
        const GpuVertex& v = in[i];
        Vec4 p{0,0,0,0};
        for (int k = 0; k < 4; ++k) {
            const float w = v.weights[k];
            if (w == 0.0f) continue;
            const Vec4 src{v.position.x, v.position.y, v.position.z, 1.0f};
            const Vec4 t = rowMajorDecl ? HlslMulRowMajor   (palette[v.joints[k]], src)
                                        : HlslMulColumnMajor(palette[v.joints[k]], src);
            p.x += t.x*w; p.y += t.y*w; p.z += t.z*w; p.w += t.w*w;
        }
        outPos[i] = {p.x, p.y, p.z};
    }
}
```

これを第 18 章の CPU スキニング（`SkinPositionLBS`）と突き合わせます。

```cpp
TEST_METHOD(PackingConventionsMatrix) {
    /* パレットとメッシュを用意し、CPU の結果を基準にする */
    std::vector<Vec3> cpu(mesh.vertices.size());
    for (std::size_t i = 0; i < mesh.vertices.size(); ++i)
        cpu[i] = SkinPositionLBS(mesh.vertices[i], palette);

    /* 4 通り試す */
}
```

実測（206 頂点の円柱、ボーン 3 本を大きく曲げた状態）：

| 送り方 | HLSL 側の宣言 | CPU との最大差 |
|---|---|---|
| そのまま | 既定（`column_major`） | **`5.943733`** ← 壊れる |
| **転置して送る** | 既定（`column_major`） | **`0.000000000`** ← 正しい |
| **そのまま** | **`row_major` 明示** | **`0.000000000`** ← 正しい |
| 転置して送る | `row_major` 明示 | **`5.943733`** ← 二重に間違えて壊れる |

**壊れ方も見ておきます。**

```
頂点 40: CPU (2.3231, 0.8623, 0.2330) / 転置忘れ (0.4126, -0.6744, 0.4330)
```

**5.9 メートルずれています。** キャラクターの身長が 2 m 程度なら、頂点が体の 3 倍の距離に飛ぶということです。「なんとなく変」ではなく、**一目で分かる壊れ方**をします。

これは救いです。**微妙に間違っているより、派手に壊れるほうがいい。** 微妙な間違い（たとえば `y` と `z` の入れ替え)は、「アーティストのモデルが悪いのでは」と疑いながら何日も溶かすことになります。

**このテストは、GPU を 1 度も起動せずに書けます。** D3D12 デバイスも、シェーダのコンパイルも、GPU そのものも要りません。**規約の正しさは、規約を再現するコードで検証できる。**

## 58.5　行列型を使わないという選択

パッキング規則の問題を**根本から回避する**方法があります。**行列型を使わない。**

`float3x4` の代わりに、**3 本の `float4`** として送ります。

```cpp
struct SkinRow3 { float f[12]; };        // row0, row1, row2

// 本書の Mat4 は行優先格納なので、先頭 12 float がそのまま行 0〜2
std::memcpy(packed.f, palette[b].m, sizeof(float)*12);
```

HLSL 側では、行列として解釈せず、`float4` の内積で書きます。

```hlsl
struct SkinRow3 { float4 r0, r1, r2; };
StructuredBuffer<SkinRow3> g_palette : register(t0);

float3 SkinPosition(float3 pos, uint4 joints, float4 weights) {
    float4 p = float4(pos, 1.0);
    float3 result = 0;
    [unroll] for (uint k = 0; k < 4; ++k) {
        SkinRow3 m = g_palette[joints[k]];
        result += weights[k] * float3(dot(m.r0, p), dot(m.r1, p), dot(m.r2, p));
    }
    return result;
}
```

**`float4` にパッキング規則はありません。** 4 つの `float` が順に入るだけです。`dot(m.r0, p)` は、行優先格納の行 0 と `(pos, 1)` の内積 ―― まさに `v' = M v` の第 1 成分です。

**規約の食い違いが起こる余地がなくなります。**

検証：

```
3 本の float4 で送る: 最大差 0.000000000  (192 → 144 バイト, 25% 削減)
```

CPU と完全一致。しかも 4x4 より 25% 小さい。

**私はこちらを推します。** 理由は 3 つ。

1. **パッキング規則を覚えなくていい。** `row_major` を書き忘れる事故が起きません。
2. **転置のコストがない。** CPU 側は `memcpy` 12 float だけ。
3. **転送量が 25% 少ない。**

代償は、シェーダのコードが `mul(M, v)` から `dot` 3 本になることですが、**生成されるコードは同じ**です（`mul` は内部で内積 4 本に展開されます)。

> **規約が 2 つあって噛み合わないなら、規約が要らない形にできないか考える。**

## 58.6　頂点シェーダ

実際のスキニング頂点シェーダです。

```hlsl
// Skinning.hlsl

struct SkinRow3 { float4 r0, r1, r2; };
StructuredBuffer<SkinRow3> g_palette : register(t0);

cbuffer PerFrame : register(b0) {
    float4x4 g_viewProj;
    uint     g_bonesPerInstance;
};

struct VsIn {
    float3 position : POSITION;
    float3 normal   : NORMAL;
    uint4  joints   : BLENDINDICES;
    float4 weights  : BLENDWEIGHT;
    uint   instance : SV_InstanceID;
};

struct VsOut {
    float4 position : SV_Position;
    float3 normal   : NORMAL;
};

VsOut main(VsIn i) {
    const uint base = i.instance * g_bonesPerInstance;

    float3 pos = 0;
    float3 nrm = 0;
    [unroll] for (uint k = 0; k < 4; ++k) {
        const float w = i.weights[k];
        const SkinRow3 m = g_palette[base + i.joints[k]];
        pos += w * float3(dot(m.r0, float4(i.position, 1.0)),
                          dot(m.r1, float4(i.position, 1.0)),
                          dot(m.r2, float4(i.position, 1.0)));
        // 法線は平行移動を含めない（w = 0）
        nrm += w * float3(dot(m.r0.xyz, i.normal),
                          dot(m.r1.xyz, i.normal),
                          dot(m.r2.xyz, i.normal));
    }

    VsOut o;
    o.position = mul(g_viewProj, float4(pos, 1.0));
    o.normal   = normalize(nrm);
    return o;
}
```

**法線には `w = 0`** ―― `float4(normal, 0)` 相当として、行列の上 3×3 だけを使います。平行移動は方向ベクトルに効いてはいけません（第 19 章）。

**第 19 章の警告を思い出してください。** 非一様スケールがある場合、法線には**逆転置行列**が必要です。上のシェーダは「非一様スケールはない」という前提で書かれています。ゲームのリグではほぼ常に成り立ちますが、成り立たないなら逆転置行列を別のバッファで送るしかありません（シェーダ内で逆行列を計算するのは高すぎます）。

**`[unroll]` を付ける**のは、ループを展開して分岐をなくすためです。ウェイトが 0 の影響ボーンをスキップする `if` は、GPU では**逆効果**です ―― SIMD ワープ内で分岐が分かれると両方の経路を実行するので、`if` を書くとむしろ遅くなります。**ウェイト 0 を掛けて足す**ほうが速い。CPU と真逆の判断です。

### 第 22 章の DQS 版

デュアルクォータニオンスキニングも同じ形で書けます。

```hlsl
struct DualQuat { float4 real, dual; };
StructuredBuffer<DualQuat> g_dqPalette : register(t0);

float3 SkinPositionDQS(float3 pos, uint4 joints, float4 weights, uint base) {
    float4 real = 0, dual = 0;
    const float4 ref = g_dqPalette[base + joints[0]].real;   // 符号合わせの基準

    [unroll] for (uint k = 0; k < 4; ++k) {
        DualQuat dq = g_dqPalette[base + joints[k]];
        const float s = (dot(dq.real, ref) < 0.0) ? -weights[k] : weights[k];
        real += s * dq.real;
        dual += s * dq.dual;
    }
    const float len = length(real);
    real /= len; dual /= len;

    // p' = p + 2·cross(real.xyz, cross(real.xyz, p) + real.w·p)
    //        + 2·(real.w·dual.xyz − dual.w·real.xyz + cross(real.xyz, dual.xyz))
    const float3 t = 2.0 * (real.w*dual.xyz - dual.w*real.xyz + cross(real.xyz, dual.xyz));
    return pos + 2.0*cross(real.xyz, cross(real.xyz, pos) + real.w*pos) + t;
}
```

**符号合わせ（第 22 章）を忘れないこと。** ここでは `joints[0]` を基準にしていますが、第 38 章で測ったとおり、**最大ウェイトのものを基準にする**のが正しい。GPU でそれをやるには `max` を取る前処理が要るので、ウェイトを降順にソートして格納しておく（第 17 章の `SortAndTruncate` がすでにそうしています）と、`joints[0]` が最大ウェイトになります。

**第 17 章の判断が、第 58 章で回収されました。**

## 58.7　コンピュートシェーダで読み戻して検証する

エミュレーションでパッキングは検証できましたが、**実機の GPU が本当に同じ結果を出すか**は別の話です。描画せずにそれを確かめる方法があります。

**コンピュートシェーダで変形して、結果をバッファに書き、CPU に読み戻す。**

```hlsl
// SkinningCS.hlsl
StructuredBuffer<SkinRow3>  g_palette  : register(t0);
StructuredBuffer<GpuVertex> g_vertices : register(t1);
RWStructuredBuffer<float3>  g_output   : register(u0);

[numthreads(64, 1, 1)]
void main(uint3 id : SV_DispatchThreadID) {
    const uint i = id.x;
    uint count, stride;
    g_vertices.GetDimensions(count, stride);
    if (i >= count) return;

    const GpuVertex v = g_vertices[i];
    g_output[i] = SkinPosition(v.position, v.joints, v.weights);
}
```

CPU 側は、

1. D3D12 デバイスを作る（`D3D12CreateDevice`）
2. 頂点バッファとパレットバッファをアップロード
3. `Dispatch((vertexCount + 63) / 64, 1, 1)`
4. リードバックヒープへコピーして `Map`
5. 第 18 章の `SkinPositionLBS` の結果と比較

```cpp
TEST_METHOD(GpuMatchesCpu) {
    if (!GpuAvailable()) { Logger::WriteMessage("GPU なし。スキップ\n"); return; }
    /* ... Dispatch して読み戻す ... */
    float worst = 0.0f;
    for (std::size_t i = 0; i < n; ++i) worst = std::fmax(worst, Length(gpu[i] - cpu[i]));
    Logger::WriteMessage(std::format("GPU vs CPU: {:.9f}\n", worst).c_str());
    Assert::IsTrue(worst < 1e-4f);       // ビット一致は期待しない
}
```

**許容誤差を `1e-4` にしているのは意図的です。** GPU と CPU でビット単位の一致は期待できません。

- GPU は積和融合（FMA）を積極的に使います（第 53 章）
- `rcp` / `rsqrt` は近似命令で、精度が仕様で保証された範囲にしかありません
- コンパイラ（DXC）の式の並べ替えは CPU コンパイラと違います

**「GPU と CPU をビット一致させる」を目標にしてはいけません。** 目標は「**目に見える差がないこと**」で、それは頂点位置で 0.1 mm 程度です。

### この章のコードについて

正直に書きます。**この原稿を書いた環境には D3D12 が使える GPU がなく、58.7 節のコードは実行していません。** 検証したのは 58.4 節のエミュレーション（パッキング規則の 4 通り）と 58.5 節の 3 行形式で、こちらはすべて `0.000000000` です。

パッキングの規則そのものは、エミュレーションで完全に確かめられます。実機で追加で確かめるべきは、**D3D12 の API の使い方**（バッファの作り方、ルートシグネチャ、リソースバリア）であって、アニメーションの数学ではありません。

**測っていないものは、測っていないと書く。** 第 57 章と同じです。

## 58.8　GPU スキニングを選ばない場合

**GPU が常に正解ではありません。**

**① 変形後の頂点が CPU で必要な場合。** 布や髪の物理シミュレーション、頂点単位のコリジョン、正確なヒット判定。GPU で変形すると、CPU 側に結果がありません（読み戻しは 1 フレーム遅れます）。

**② 同じメッシュを複数回描く場合。** シャドウマップ、深度プリパス、複数のカスケード ―― パスごとに頂点シェーダが走るので、**同じスキニングを何度も計算します**。パスが 4 つあれば 4 倍。この場合は「コンピュートシェーダで 1 回だけ変形して、結果のバッファを各パスで使う」ほうが速くなります（**ストリームアウト / 頂点キャッシュ**と呼ばれる手法）。

**③ ボーン数が非常に多い場合。** パレットの転送量がボトルネックになります。1000 体 × 200 ボーン × 48 B = 9.6 MB / フレーム。この場合は LOD でボーン数を落とします（第 59 章）。

**④ 頂点数が少ない場合。** 数百頂点のメッシュなら、ドローコールとバッファ更新のオーバーヘッドのほうが大きい。

**判断基準**はこうです。

```
GPU スキニングが有利: 頂点数が多い × パスが少ない × CPU で結果が要らない
CPU スキニングが有利: 頂点数が少ない × CPU で結果が要る
コンピュートで 1 回:  パスが多い（シャドウ + 深度 + 本描画）
```

## この章のまとめ

- GPU スキニングの本質は速度より**転送量**。CPU スキニングは変形後の頂点（40,000 × 24 B = 960 KB）を毎フレーム送るが、GPU スキニングはパレット（60 × 48 B = 2.8 KB）だけ。**340 分の 1。**
- パレットは**構造化バッファ**で送る（上限がなく、インスタンス描画でインデックス参照できる）。最下行は常に `(0,0,0,1)` なので **3x4 で 25% 削減**。
- **HLSL の `float4x4` は既定で `column_major` パッキング。** この本の行優先データをそのまま送ると**転置として解釈される**。
- 対処は「**転送前に転置する**」か「**`row_major` を明示する**」の**どちらか一方だけ**。両方やると元に戻って壊れる。
- **描画せずに検証できる。** パッキング規則を CPU 上で再現し（違いは添字が `4*c+r` か `4*r+c` かだけ）、コンピュートシェーダをエミュレートして第 18 章の結果と突き合わせる。実測：4 通りのうち正しい 2 通りが **`0.000000000`**、間違った 2 通りが **`5.943733`**。
- 壊れ方は**派手**（頂点が体の 3 倍の距離に飛ぶ）。**微妙に間違っているより、派手に壊れるほうがいい。**
- **推奨は「行列型を使わない」。** 3 本の `float4` として送り、シェーダでは `dot` 3 回。**`float4` にパッキング規則はない** ―― 規約の食い違いが起こる余地が消える。転置も不要で、転送量も 25% 少ない。
- **規約が 2 つあって噛み合わないなら、規約が要らない形にできないか考える。**
- 法線は `w = 0`（第 19 章）。非一様スケールがあるなら逆転置行列が別途要る。
- GPU では**ウェイト 0 をスキップする `if` を書かない**。ワープ内で分岐が分かれると両方の経路を実行するので、**0 を掛けて足すほうが速い** ―― CPU と真逆。
- DQS の符号合わせは `joints[0]` を基準にできる。**第 17 章でウェイトを降順ソートしておいたおかげ**で、`joints[0]` が最大ウェイトになる。
- 実機検証は**コンピュートシェーダで読み戻す**。ただし**ビット一致を目標にしない**（GPU は FMA と近似命令を使う）。目標は「目に見える差がないこと」＝ 0.1 mm 程度。
- **この章の 58.7 節のコードは、原稿の執筆環境に D3D12 が使える GPU がなく、実行していない。** 検証したのはエミュレーション部分。**測っていないものは、測っていないと書く。**
- GPU が常に正解ではない。**CPU で結果が要る / パスが多い / 頂点が少ない**場合は別の選択がある。
