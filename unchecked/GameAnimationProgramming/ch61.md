# 第 61 章　ソケットとアタッチメント

**この章で作るもの**：ボーンに物をくっつける仕組み。武器、盾、エフェクトの発生位置、カメラの追従点。

短い章です。数学は第 11 章の `Combine` と `Inverse` だけで足ります。**そのぶん、設計判断のほうが本題**になります。

---

## 61.1　ソケットとは

**ソケット**は、「あるボーンから見た、固定のオフセット」です。

```
    handR（ボーン）
      │
      └── weapon_r（ソケット）: 手のひらから 4 cm、少し傾けた位置
              │
              └── 剣（アタッチメント）
```

なぜボーンを直接使わないのか。「右手のボーンに剣をくっつければいい」ように思えます。

**理由は 3 つ。**

**① ボーンの原点は、物を持つのに都合のいい場所ではない。** `handR` の原点は手首です。剣のグリップは手のひらの中心にあってほしい。回転も、ボーンのローカル軸と剣の向きは一致しません。

**② 1 つのボーンに複数の物をつけたい。** 右手に「武器」と「エフェクト発生点」と「IK の目標」。ボーンを増やすとスケルトンが太り、第 IX 部で測ったコストが上がります。

**③ 追加や調整に、リグの作り直しが要らない。** ソケットはメタデータです。「剣の握り位置を 2 mm 下げる」ためにスケルトンを変更してモデルを再エクスポートする、というのは避けたい。

## 61.2　データ構造

```cpp
// AnimLib/include/anim/Socket.h
#pragma once
#include "anim/AnimEvent.h"

namespace anim {

struct Socket {
    BoneIndex   bone   = 0;
    Transform   offset = TransformIdentity();   // 親ボーンのローカル空間でのオフセット
    std::string name;
};

class SocketSet {
public:
    std::size_t Add(std::string name, BoneIndex bone, const Transform& offset);
    [[nodiscard]] std::size_t Count() const;
    [[nodiscard]] const Socket& At(std::size_t i) const;
    [[nodiscard]] std::size_t Find(std::string_view name) const;
    static constexpr std::size_t kNotFound = static_cast<std::size_t>(-1);

    void Resolve(std::span<const Transform> global, std::span<Transform> out) const;
    void ResolveNoScale(std::span<const Transform> global, std::span<Transform> out) const;
private:
    std::vector<Socket> sockets_;
};
}
```

**`Find` は名前で引きます** が、これは**初期化時に 1 回だけ**呼ぶことを想定しています。毎フレーム名前で引くのは、第 13 章の `Skeleton::FindBone` と同じで論外です。取得したインデックスを保持してください。

**ソケットを `Skeleton` の中ではなく別のオブジェクトに置いた**のは、スケルトンを共有できるようにするためです。100 体のキャラクターは同じ `Skeleton` を参照しますが（第 57 章）、ソケットの構成は装備によって変わるかもしれません。**変わるものと変わらないものを分ける。**

## 61.3　解決

計算は 1 行です。

```cpp
void SocketSet::Resolve(std::span<const Transform> global, std::span<Transform> out) const {
    for (std::size_t i = 0; i < sockets_.size(); ++i)
        out[i] = Combine(global[sockets_[i].bone], sockets_[i].offset);
}
```

第 11 章の `Combine(parent, child)` は「親の変換を適用したあとに子の変換」―― つまり `parent ∘ child` です。ボーンのグローバル変換にオフセットを重ねれば、ソケットのワールド変換になります。

**呼ぶタイミング**が重要です。パイプラインのどこか。

```
① クリップをサンプル
② ブレンド
③ 階層を解く          ← global[] が確定
④ IK で補正           ← global[] が変わる
⑤ ソケットを解決      ← ここ
⑥ パレットを作る
⑦ 頂点を変形
```

**IK の後**です。第 51 章のフット IK は腰を下げ、脚を曲げます。武器を持つ手に IK がかかっているなら（両手持ちの銃など）、その結果を反映しなければなりません。

## 61.4　単体テスト：追従すること

腕を模した 4 ボーンの骨格で確かめます。

```cpp
TEST_CLASS(SocketTests) {
    static Skeleton MakeArm() {
        Skeleton s; Transform t = TransformIdentity();
        t.translation = {0, 1.4f, 0};    s.AddBoneRaw("chest",    kNoParent, t);
        t.translation = {0.2f, 0.2f, 0}; s.AddBoneRaw("upperArm", 0, t);
        t.translation = {0.28f, 0, 0};   s.AddBoneRaw("lowerArm", 1, t);
        t.translation = {0.25f, 0, 0};   s.AddBoneRaw("hand",     2, t);
        return s;
    }
public:
    TEST_METHOD(SocketMatchesManualComputation) {
        Skeleton s = MakeArm();
        Pose pose = Pose::FromRest(s);
        std::vector<Transform> g(s.BoneCount());
        ComputeGlobalPose(s, pose.Locals(), g);

        SocketSet sockets;
        Transform grip = TransformIdentity();
        grip.translation = {0.05f, 0.0f, 0.02f};
        grip.rotation = MakeQuatAxisAngle({0,0,1}, 0.3f);
        sockets.Add("weapon_r", 3, grip);

        std::vector<Transform> world(1);
        sockets.Resolve(g, world);

        const Transform expected = Combine(g[3], grip);
        Assert::IsTrue(Length(world[0].translation - expected.translation) < 1e-6f);
    }
};
```

レストポーズの手は `(0.7300, 1.6000, 0.0000)`（`0.2 + 0.28 + 0.25 = 0.73`、`1.4 + 0.2 = 1.6`）。ソケットは `(0.780000, 1.600000, 0.020000)` ―― オフセットの `(0.05, 0, 0.02)` がそのまま足されています。レストポーズでは回転がないので、当然です。

**ポーズを変えても追従することを確かめます。**

```cpp
TEST_METHOD(SocketFollowsPose) {
    /* ... */
    pose[1].rotation = MakeQuatAxisAngle({0,0,1}, 0.9f);
    pose[2].rotation = MakeQuatAxisAngle({0,1,0}, 0.6f);
    ComputeGlobalPose(s, pose.Locals(), g);
    sockets.Resolve(g, world);
    Assert::IsTrue(Length(world[0].translation - Combine(g[3], grip).translation) < 1e-6f);
}
```

曲げた後のソケットは `(0.534982, 2.022130, -0.152886)`。腕が上がって、ひねられた結果です。

## 61.5　単体テスト：剛体であること

これが**性質のテスト**です。

> **ソケットは、親ボーンから見て動かない。** どんなポーズでも、ボーン原点からソケットまでの距離は一定。

```cpp
TEST_METHOD(SocketKeepsRigidDistance) {
    /* 任意のポーズにする */
    const float offsetLength = Length(grip.translation);
    const float actual = Length(world[0].translation - g[3].translation);
    Assert::AreEqual(offsetLength, actual, 1e-5f);
}
```

実測、どちらも **`0.053852`**（`√(0.05² + 0.02²)`）。

「当たり前では?」と思うかもしれませんが、**当たり前でなくなる条件が 1 つあります**。次の節です。

## 61.6　スケールをどう扱うか

`Combine` は親のスケールを子の平行移動に掛けます（第 11 章）。

```cpp
Transform Combine(const Transform& parent, const Transform& child) {
    r.scale       = MulPerComponent(parent.scale, child.scale);
    r.rotation    = parent.rotation * child.rotation;
    r.translation = parent.translation
                  + Rotate(parent.rotation, MulPerComponent(parent.scale, child.translation));
    return r;
}
```

だから、**手のボーンにスケールがかかっていると、ソケットの位置もオフセットも伸びます**。

測ります。手を 2 倍に拡大したときの、ボーン原点からソケットまでの距離。

```
手を 2 倍に拡大: Resolve=0.107703 / ResolveNoScale=0.053852（元 0.053852）
```

**`Resolve` は距離が 2 倍になりました。**

これは正しいのでしょうか。**用途によります。**

**スケールを反映すべき場合** ―― キャラクター全体を 1.5 倍にした（巨大化アイテム）。武器も一緒に大きくなり、位置も比例して離れるべきです。

**スケールを反映すべきでない場合** ―― アニメータが手のボーンを一時的に拡大した（握りの表現、漫画的な誇張）。**剣まで 2 倍になってはいけません。**

後者のほうがはるかに多いので、専用の関数を用意します。

```cpp
void SocketSet::ResolveNoScale(std::span<const Transform> global, std::span<Transform> out) const {
    for (std::size_t i = 0; i < sockets_.size(); ++i) {
        Transform parent = global[sockets_[i].bone];
        parent.scale = {1,1,1};                       // 親のスケールを捨てる
        out[i] = Combine(parent, sockets_[i].offset);
    }
}
```

**両方を用意して、呼び出し側に選ばせます。** どちらが「正しい」かは、アニメーションシステムには判断できません。

```cpp
TEST_METHOD(ScaleHandlingIsExplicit) {
    pose[3].scale = {2.0f, 2.0f, 2.0f};
    ComputeGlobalPose(s, pose.Locals(), g);

    sockets.Resolve(g, world);
    Assert::AreEqual(offsetLength*2.0f, Length(world[0].translation - g[3].translation), 1e-5f);

    sockets.ResolveNoScale(g, world);
    Assert::AreEqual(offsetLength,      Length(world[0].translation - g[3].translation), 1e-5f);
}
```

**この 2 行のテストが、設計判断を文書化しています。** 「スケールは伝播する」「しない版もある」の両方が仕様として固定されました。将来だれかが `Resolve` の挙動を変えたら、テストが止めます。

> **どちらが正しいか決められない選択には、名前をつけて 2 つ用意する。** `Resolve` と `ResolveNoScale`。呼び出し側が選ぶという事実を、API に現す。

## 61.7　オフセットをどう決めるか

ソケットの `offset` は誰が決めるのでしょうか。

**① DCC ツールで作る。** Blender や Maya で、剣を持たせた状態を作り、そこから相対変換を書き出す。最も確実で、アーティストが直接調整できます。glTF なら、ソケットを**ジョイントに含まれないノード**として持たせられます。

**② ワールド座標から逆算する。** 「レストポーズで、剣をここに置きたい」から親ボーン相対のオフセットを求める。

```cpp
// 「ワールドのここに置きたい」→「親から見たらどこか」
inline Transform MakeSocketOffset(const Transform& boneGlobal, const Transform& desiredWorld){
    return Combine(Inverse(boneGlobal), desiredWorld);
}
```

`Combine(bone, offset) = desired` を `offset` について解くと `offset = bone⁻¹ ∘ desired`。第 11 章の `Inverse(Transform)` がそのまま使えます。

```cpp
TEST_METHOD(MakeSocketOffsetRoundTrips) {
    Transform desired = TransformIdentity();
    desired.translation = {0.9f, 1.7f, 0.15f};
    const Transform off  = MakeSocketOffset(g[3], desired);
    const Transform back = Combine(g[3], off);
    Assert::IsTrue(Length(back.translation - desired.translation) < 1e-5f);
}
```

実測、復元した位置は **`(0.900000, 1.700000, 0.150000)`** ―― 完全一致。

**この往復テストの価値**は、`Inverse(Transform)` の実装を守ることにあります。第 11 章で書いた

```cpp
Transform Inverse(const Transform& t) {
    r.scale       = {1/t.scale.x, 1/t.scale.y, 1/t.scale.z};
    r.rotation    = Conjugate(t.rotation);
    r.translation = -Rotate(r.rotation, MulPerComponent(r.scale, t.translation));
    return r;
}
```

の `translation` の行は、**逆行列の平行移動成分**という間違えやすい式です。往復テストは、それが正しいことを常に確認してくれます。

**③ エディタで対話的に調整する。** ①と②の組み合わせ。ゲーム内のデバッグ UI でギズモを動かし、結果を `MakeSocketOffset` でオフセットに変換して保存する。実務ではこれが一番使われます。

## 61.8　アタッチメント ―― 骨格を持つ物をつける

剣が単なる静的メッシュなら、ソケットのワールド変換をそのままモデル行列にすれば終わりです。

しかし**アタッチメント自身がアニメーションする**場合があります。銃のスライド、盾のギミック、リボルバーのシリンダー。この場合、アタッチメントは自前のスケルトンとクリップを持ちます。

```cpp
struct Attachment {
    const Skeleton* skeleton = nullptr;
    std::size_t     socket   = 0;
    Transform       localOffset = TransformIdentity();
};

inline Transform ResolveAttachment(std::span<const Transform> socketWorld, const Attachment& a){
    return Combine(socketWorld[a.socket], a.localOffset);
}
```

更新の順序は、

```
1. キャラクターのポーズを解く（① 〜 ④）
2. ソケットを解決（⑤）
3. アタッチメントのルート変換 = ソケットのワールド変換 ∘ localOffset
4. アタッチメント自身のポーズを解く（その骨格のルートに 3 を掛ける）
5. それぞれのパレットを作る
```

**キャラクターとアタッチメントは、別々のスケルトン・別々のパレット・別々のドローコール**です。1 つのスケルトンに統合する手もありますが、

- 武器を持ち替えるたびにスケルトンが変わる
- 同じ武器を複数のキャラクターが持つとき、共有できない
- 第 IX 部で測ったボーン数のコストが、装備で変動する

**分けておくほうが素直です。**

## 61.9　ソケットの典型的な使い道

| ソケット名 | 親ボーン | 用途 |
|---|---|---|
| `weapon_r` / `weapon_l` | 手 | 武器の装着 |
| `sheath_back` / `sheath_hip` | 背中・腰 | 納刀時の武器 |
| `muzzle` | 武器側の骨格 | 銃口フラッシュ、弾の発生位置 |
| `foot_l` / `foot_r` | 足首 | 足音・土煙の発生位置（第 60 章のイベントと組む） |
| `head_look` | 頭 | カメラの注視点、視線の起点（第 50 章） |
| `camera_follow` | 腰 | 追従カメラの目標（ボーンそのものだと揺れすぎる） |

**最後の 2 つが、ソケットの真価を示しています。**

`camera_follow` を腰ボーンそのものにすると、歩行の上下動がカメラに直接乗って、プレイヤーが酔います。ソケットにしておけば、「腰から少し上、少し後ろ」に置いたうえで、**カメラ側で平滑化**できます（第 51 章の `SmoothTowards` がそのまま使えます）。

**抜刀のような「持ち替え」**は、アタッチメントの `socket` を切り替えるだけです。

```cpp
weapon.socket = drawn ? weaponSocketIndex : sheathSocketIndex;
```

そして**切り替える瞬間**は、第 60 章のイベントで決めます。

```cpp
for (const FiredEvent& e : firedEvents)
    if (e.id == kDrawWeapon) weapon.socket = weaponSocketIndex;
```

**第 60 章と第 61 章は、こうして組み合わさります。**

## 61.10　コスト

```
ソケット 8 個の解決: 0.0852 us
```

**85 ナノ秒で 8 個。** 1 個あたり約 10 ns ―― `Combine` 1 回ぶんです。

第 62 章で測るキャラクター 1 体の更新（約 7 µs）に対して 1.2%。**気にする必要はありません。**

ただし、注意点が 1 つ。**ソケットの解決は、階層解決とは別のパスです。** `global[]` を全部計算したあとで、ソケットぶんだけ追加の `Combine` をします。もし「ソケットを普通のボーンとしてスケルトンに入れる」設計にしていたら、このコストは階層解決に埋もれて同じでした。

**別にしたのはコストのためではなく、構造のため**です ―― 変わるもの（装備）と変わらないもの（骨格）を分ける。61.2 で書いたとおりです。**「速いから分ける」ではなく「意味が違うから分ける」。**

## この章のまとめ

- **ソケットは「あるボーンから見た固定のオフセット」。** ボーンを直接使わない理由は、① ボーン原点が物を持つのに都合が悪い、② 1 ボーンに複数つけたい、③ **リグの作り直しなしで調整したい**。
- 計算は `Combine(global[bone], offset)` の 1 行。**呼ぶのは IK の後**（第 51 章の腰下げや脚の補正を反映するため）。
- ソケットは `Skeleton` の中ではなく別オブジェクトに置く。**変わるもの（装備）と変わらないもの（骨格）を分ける。**
- 性質のテスト：**ソケットは親ボーンから見て動かない**。どんなポーズでも距離は `0.053852` で一定。
- **スケールは伝播する。** 手を 2 倍にすると `Resolve` は距離も 2 倍（`0.107703`）。多くの場合これは望ましくないので `ResolveNoScale` を用意した（`0.053852` のまま）。
- **どちらが正しいか決められない選択には、名前をつけて 2 つ用意する。** 呼び出し側が選ぶという事実を API に現す。テストで両方の挙動を仕様として固定する。
- オフセットの決め方は ① DCC ツール、② `MakeSocketOffset`（`offset = bone⁻¹ ∘ desired`）で逆算、③ エディタで対話的に。**往復テストが第 11 章の `Inverse(Transform)` を守る**（実測、完全一致）。
- 骨格を持つアタッチメントは、**キャラクターとは別のスケルトン・別のパレット・別のドローコール**にする。持ち替えでスケルトンが変わらず、共有もできる。
- `camera_follow` ソケット ―― 腰ボーンを直接使うと歩行の上下動でカメラが酔う。ソケットにして**カメラ側で平滑化**する（第 51 章の `SmoothTowards`）。
- **抜刀は「アタッチメントの `socket` を切り替えるだけ」、切り替える瞬間は第 60 章のイベントで決める。** 2 つの章がここで組み合わさる。
- コストは **8 個で 0.0852 µs**。分けたのは速さのためではなく、**意味が違うから**。

次章は総合演習。**glTF モデルを読み、速度でブレンドし、足を接地させ、武器を持ち、圧縮クリップを再生し、GPU 形式のパレットを出力する** ―― これまでのすべてを 1 本のプログラムに結合します。そして、結合してはじめて出てくるバグを 1 つ踏みます。
