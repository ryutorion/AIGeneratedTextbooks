# 第 29 章　glTF 2.0 の構造

**この章で作るもの**：コードはほとんど書きません。glTF の全体像を把握し、**テストに使うモデルを自分で生成する仕組み**を用意します。第 VI 部の地図です。

---

## 29.1　手書きデータからの卒業

ここまで、テストデータはすべて自分で作ってきました。

- 4 ボーンの腕（第 13 章）
- 円柱メッシュ（第 17 章）
- 手で組んだクリップ（第 23〜28 章）

これで第 V 部まで来られたのは、**アニメーションの本質が数十行のデータで表現できる**からです。しかし、そろそろ限界があります。

**① 実データの「汚さ」を経験できない。** 0 スケールのボーン、ウェイトの合計が 1 でない頂点、レストポーズと違うバインドポーズ、トポロジカル順でないノード配列 ―― これまで「実在する」と書いてきたものを、実際に扱っていません。

**② 規模が小さい。** 158 頂点・2 ボーンでは、第 IX 部の最適化の効果が測れません。

**③ 達成感。** 自分の書いたコードが本物のモデルを動かすのは、単純に嬉しいものです。

第 VI 部で、この 3 つを解決します。

---

## 29.2　なぜ glTF なのか

3D モデルのフォーマットは数多くあります。本書が glTF 2.0 を選んだ理由は 4 つです。

**① 仕様が公開されていて、短い。** Khronos Group が管理する仕様書は、JSON スキーマを含めて読み通せる分量です。FBX は仕様が非公開で、実質的に SDK を使うしかありません。

**② JSON + バイナリという素直な構造。** テキスト部分は人間が読めるので、デバッグのときにエディタで開けます。バイナリ部分は「型とオフセットが分かれば読める」だけの単純な配列です。

**③ 座標系と規約が本書と一致する。** 右手系・Y-up（第 5 章）、列ベクトル規約（第 6 章）。**本書はこの一致を得るために規約を選びました。** 違いは行列の格納順（列優先）だけで、転置 1 回で済みます。

**④ 外部ライブラリが要らない。** JSON パーサさえ書けば読めます。それが第 30・31 章です。

Collada（`.dae`）は XML で冗長すぎ、FBX は SDK 依存。**「自分で全部書く」という本書の方針に合うのは glTF だけ**でした。

---

## 29.3　3 つの形態

glTF のファイルは 3 つの形で存在します。**中身は同じ**で、入れ物が違うだけです。

| 形態 | 構成 | 用途 |
| --- | --- | --- |
| `.gltf` + `.bin` | JSON テキスト + 別ファイルのバイナリ | 編集しやすい。デバッグ向き |
| `.gltf`（埋め込み） | JSON テキストのみ（バイナリを Base64 で内包） | 1 ファイルで完結。サイズは 1.33 倍 |
| `.glb` | 1 つのバイナリファイル（JSON チャンク + BIN チャンク） | 配布用。読み込みが速い |

**3 つとも読めるようにします。** そして、**3 つから読んだデータがビット単位で一致すること**をテストで確認します（第 36 章）。これは「入れ物が違うだけ」という主張の、実行可能な形での検証です。

---

## 29.4　全体像

glTF の JSON は、いくつかの**配列**を並べたものです。要素どうしは**配列の添字**で参照し合います。

```
scene ──→ nodes[]
             │
             ├─ mesh ──→ meshes[]
             │              └─ primitives[]
             │                    ├─ attributes: POSITION → accessors[]
             │                    │              NORMAL   → accessors[]
             │                    │              JOINTS_0 → accessors[]
             │                    │              WEIGHTS_0→ accessors[]
             │                    └─ indices    → accessors[]
             │
             ├─ skin ──→ skins[]
             │              ├─ joints[]              → nodes[] の添字
             │              └─ inverseBindMatrices   → accessors[]
             │
             └─ children[] → nodes[]（階層）

animations[]
   ├─ samplers[] ─ input  → accessors[]（時刻）
   │               output → accessors[]（値）
   └─ channels[] ─ sampler + target{node, path}

accessors[] ──→ bufferViews[] ──→ buffers[]
  型・個数        範囲・ストライド     生バイト列
```

**すべてが添字による参照**です。ポインタもキーも使いません。この設計のおかげで、パースは「配列を読んで、添字を辿る」だけになります。

第 13 章で「ボーン階層を親インデックス配列で持つ」と決めたのと、発想が同じです。**添字は保存でき、比較でき、コピーしても壊れません。**

---

## 29.5　なぜ三層なのか ―― accessor / bufferView / buffer

初めて見ると過剰に見える三層構造には、それぞれ理由があります。

**`buffer`** は生のバイト列です。ファイル全体、あるいは Base64 の塊。**中身の意味を持ちません。**

**`bufferView`** は buffer の一部分を切り出します。「オフセット 1024 から 4096 バイト」。ここで**ストライド**（要素の間隔）も指定できます。GPU の頂点バッファに 1 対 1 で対応する単位です。

**`accessor`** は bufferView を「型のついた配列」として解釈します。「float の VEC3 が 158 個」。

なぜ分けるのか。**同じメモリを複数の解釈で使いたいから**です。

```
buffer:      [────────────── 生バイト列 ──────────────]
                    │
bufferView:         [── 位置と法線がインターリーブ、stride=24 ──]
                     │                    │
accessor A:          └─ VEC3 float ×158 （オフセット 0）  = 位置
accessor B:                               └─ VEC3 float ×158（オフセット 12）= 法線
```

位置と法線を交互に並べる（インターリーブ）と、GPU が頂点を読むときのキャッシュ効率が上がります。しかし「位置の配列」「法線の配列」としても参照したい。**bufferView がメモリ配置を、accessor が意味を担当する**ことで、これが両立します。

第 20 章で AoS と SoA を行き来したのと同じ話が、ファイルフォーマットの層で起きています。

## 29.6　テスト用のモデルを自分で生成する

ここが、この章の実装部分です。

サンプルモデルをネットから取ってくることもできますが、本書は**自分で生成します**。理由は 3 つあります。

**① 正解が分かる。** 第 17 章の円柱を出力すれば、頂点数も体積も既知です。読み込んだ結果を照合できます。

**② テストが自己完結する。** 外部ファイルへの依存がないので、リポジトリをクローンしただけでテストが通ります。

**③ 書き出し側も理解できる。** フォーマットを「読む」だけでなく「書く」ことで、仕様の理解が確実になります。

`AnimLib.Tests/TestSupport/GltfWriter.h` を作ります。

```cpp
namespace anim::test {

// 第 17 章の円柱を、2 ボーンのスキン + ねじりアニメーション付きの
// glTF として書き出す。3 つの形態すべてを出力できる。
enum class GltfContainer { Separate, Embedded, Binary };

// 出力先ディレクトリに cylinder.gltf / cylinder.bin / cylinder.glb を作る。
void WriteCylinderGltf(const std::filesystem::path& directory, GltfContainer container);

}  // namespace anim::test
```

生成するモデルの中身を決めておきます。**第 17 章の円柱と、第 21 章のねじり**をそのまま glTF にします。

```
メッシュ  : 円柱（12 × 12 分割、長さ 1 m、半径 0.15 m）
            158 頂点、312 三角形
スケルトン: joint0（原点）→ joint1（x = 0.5）
ウェイト  : x に応じて joint0 → joint1 へ線形に遷移
アニメ    : joint1 を X 軸まわりに 0 → 180 度（1 秒）
```

**このモデルは、第 IV 部と第 V 部のテストをそのまま再現できるように設計してあります。**

- 読み込んだバインドポーズでパレットが単位行列になるか（第 16 章）
- t = 0 でバインドポーズになるか（第 15 章）
- t = 1（180 度ねじり）で断面が潰れるか（第 21 章）

**手書きデータで確かめたことを、実データでもう一度確かめる。** これが第 VI 部の検証方針です。

書き出しコードの詳細は第 32〜36 章と対になるので、各章で少しずつ触れます。ここでは、生成されるファイルの規模だけ見ておきます。

```
cylinder.gltf           3,193 バイト（JSON テキスト）
cylinder.bin            9,680 バイト（バイナリ）
cylinder_embedded.gltf  約 16 KB（Base64 で 1.33 倍）
cylinder.glb            約 13 KB
```

**バイナリが JSON の 3 倍**あることに注目してください。頂点データは JSON に書くには大きすぎます。もし 158 頂点ぶんの位置・法線・ジョイント・ウェイトをすべて JSON の数値として書けば、12 KB を超えます。10 万頂点なら 8 MB のテキストです。**glTF が二層構造（JSON + バイナリ）である理由が、この比率に表れています。**

## 29.7　本書が扱う範囲

glTF の仕様は広く、本書はその一部しか使いません。境界をはっきりさせておきます。

### 読むもの

| 要素 | 章 |
| --- | --- |
| `asset`（バージョン確認） | 31 |
| `buffers` / `bufferViews` / `accessors` | 32 |
| `meshes` / `primitives` / attributes / indices | 33 |
| `nodes`（階層と TRS） | 34 |
| `skins`（joints, inverseBindMatrices） | 34 |
| `animations`（samplers, channels） | 35 |
| GLB コンテナ | 36 |

### 読まないもの

**マテリアルとテクスチャ。** `materials`, `textures`, `images`, `samplers`（テクスチャの）。描画をしないので不要です。

**カメラとライト。** `cameras`、`KHR_lights_punctual`。

**モーフターゲット。** `primitives.targets` と `weights`。表情アニメーションで使いますが、スキニングとは別の仕組みです（第 63 章で触れます）。

**スパースアクセサ。** `accessor.sparse`。値の大半が同じ配列を圧縮する仕組みで、実装は難しくありませんが、スキニングのデータで使われることは稀です。

**拡張（extensions）。** Draco 圧縮（`KHR_draco_mesh_compression`）など。

**扱わないものは、無視するのではなく検出して報告します。** 知らない拡張が必須指定（`extensionsRequired`）されていたら、読み込みを失敗させるべきです。「読めたつもりで壊れたデータを使う」のが最悪の結果だからです。

```cpp
// 必須拡張が指定されていたら、対応していないので失敗させる
if (json.Has("extensionsRequired")) {
    for (const JsonValue& ext : json["extensionsRequired"].AsArray()) {
        return std::unexpected(GltfError{
            "未対応の必須拡張: " + ext.AsString()});
    }
}
```

## 29.8　第 VI 部の進み方

9 章を使いますが、**アニメーションの話はほとんど出てきません**。ファイルを読む話です。

```
第 30・31 章  JSON パーサを書く          ← 純粋なパーサの話
第 32 章      バッファとアクセサ          ← バイト列の解釈
第 33 章      メッシュ                    ← 第 17 章の型へ
第 34 章      ノード階層とスキン          ← 第 III 部の型へ。転置がここ
第 35 章      アニメーション              ← 第 V 部の型へ
第 36 章      GLB                        ← 入れ物の違い
第 37 章      ランタイム形式へ焼き込む    ← 読んだ後の話
```

**山場は第 34 章**です。行列の転置、トポロジカルソート、joints とボーンの対応表 ―― 間違えやすいものが集中しています。そして第 16 章で書いた「バインドポーズでパレットが単位行列」というテストが、そのすべてを一度に検査します。

## この章のまとめ

- 手書きデータには 3 つの限界がある ―― **実データの汚さを経験できない・規模が小さい・達成感がない**。
- glTF を選んだのは、**仕様が公開されていて短い・JSON + バイナリという素直な構造・座標系と規約が本書と一致する・外部ライブラリが要らない**の 4 点。規約の一致は、第 5・6 章でそう選んだ結果。
- 形態は 3 つ（`.gltf`+`.bin` / 埋め込み / `.glb`）。**中身は同じ**で、それをテストで確認する。
- 要素間の参照は**すべて配列の添字**。第 13 章の親インデックス配列と同じ発想。
- **accessor / bufferView / buffer の三層**は、「メモリ配置」と「意味」を分離するため。インターリーブされた頂点データを、位置の配列・法線の配列として別々に参照できる。
- テストモデルは**自分で生成する**。正解が分かり、テストが自己完結し、書く側からも仕様を理解できる。
- 生成した円柱は、**第 16 章・第 15 章・第 21 章のテストをそのまま再現できる**ように設計した。
- **扱わない機能は、無視せず検出して報告する。** 必須拡張が指定されていたら失敗させる。
