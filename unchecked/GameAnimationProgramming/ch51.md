# 第 51 章　フット IK

**この章で作るもの**：地形に合わせて足を接地させる仕組み。段差、くぼみ、坂 ―― 平らな床を前提に作られた歩行アニメーションを、実行時に地面へ合わせます。第 VIII 部の総仕上げです。

そして第 46 章 46.3 で予告した「**前フレームの補正結果に重ねてはいけない**」を、実測で確かめます。

---

## 51.1　何が問題なのか

歩行アニメーションは、平らな床を歩く前提で作られます。アニメータは足が床にぴったり付くようにキーを打ちます。

その同じアニメーションを、階段や坂で再生するとどうなるか。

```
        アニメーションが想定する床（平ら）
   ────────────────────────────
        ●  ●          ← 足はここに来る
   ─────┘  └─────      実際の地形（段差）
        ↑     ↑
     めり込む  浮く
```

**上がっている段には足がめり込み、下がっている段では宙に浮きます。** 数センチの段差でも、めり込みは一発でバレます。

やるべきことは 4 つです。

1. **足を地面の高さへ動かす**（2 ボーン IK）
2. **足首の姿勢を地面の傾きに合わせる**
3. **足が届かないなら、腰を下げる**
4. **急な変化をならす**（時間方向の平滑化）

順に作ります。

---

## 51.2　地面の情報をどう受け取るか

足の下に何があるかを調べるのは、**アニメーションシステムの仕事ではありません**。物理エンジンやコリジョンシステムのレイキャストです。

だから、インターフェースだけ切って、中身は外から渡してもらいます。

```cpp
struct GroundHit {
    bool  hit    = false;      // そもそも地面があったか（崖の上、空中など）
    float height = 0.0f;       // 接地点のワールド Y
    Vec3  normal {0,1,0};      // 接地面の法線
};

using GroundQuery = GroundHit(*)(Vec3 worldPos);
```

関数ポインタにしていますが、実務ではキャプチャを取れるように `std::function` か、テンプレート引数か、あるいは「あらかじめ両足分の `GroundHit` を計算して配列で渡す」形にします。**アニメーションの更新がコリジョンシステムを直接叩く設計は避けたい** ―― 第 57 章でマルチスレッド化するときに、そこが必ず問題になるからです。事前に問い合わせて配列で渡すのが最も安全です。

テストでは地形を関数で書きます。

```cpp
static GroundHit FlatGround (Vec3)   { return {true, 0.0f, {0,1,0}}; }
static GroundHit StepGround (Vec3 p) { return {true, (p.x < 0.0f) ? 0.2f : 0.0f, {0,1,0}}; }
static GroundHit SlopeGround(Vec3 p) {
    const float k = std::tan(20.0f * kIkPi / 180.0f);
    return {true, p.x * k, Normalize(Vec3{-k, 1, 0})};
}
```

**地形をコードで書けるのは、描画なしで検証するこの本の方針の恩恵です。** 20 度の坂を用意するのに、モデリングツールも物理エンジンも要りません。

## 51.3　設定と状態を分ける

フット IK は、この本で初めて**時間方向の状態を持つ IK** です。平滑化のために「前フレームの値」を覚えておく必要があります。

第 46 章 46.3 の原則 ―― IK は状態を持たない関数として書く ―― に対して、これは例外です。だから**例外であることが目に見えるように、状態を明示的に外へ出します**。

```cpp
struct FootIkSettings {          // 静的な設定（キャラクターごとに固定）
    float footHeight   = 0.10f;  // 足首から接地面までの高さ
    float maxLift      = 0.50f;  // これ以上は持ち上げない
    float maxDrop      = 0.50f;  // 腰を下げる上限
    float maxFootPitch = 0.7f;   // 足首を地形に合わせる最大角（ラジアン）
    float smoothTime   = 0.15f;  // 指数平滑の時定数（秒）
};

struct FootIkState {             // フレームをまたぐ状態（キャラクターごとに 1 つ）
    float pelvisOffset = 0.0f;
    std::vector<float> footOffset;
    void Resize(std::size_t n) { footOffset.assign(n, 0.0f); }
};

struct LegChain {
    BoneIndex thigh = 0, shin = 0, foot = 0;
    Vec3 poleOffset{0,0,1};      // 膝を向けたい方向
};
```

**`Settings` と `State` を別の型にする**のは、意図の表明です。`Settings` は読み取り専用で共有でき、`State` はキャラクターごとに 1 つずつ持つ。混ぜて 1 つの構造体にすると、「これは設定か状態か」が呼び出し側から分からなくなります。

## 51.4　指数平滑

時間方向のならしには、指数平滑（一次遅れ）を使います。

```cpp
inline float SmoothTowards(float current, float goal, float smoothTime, float dt) {
    if (smoothTime <= 0.0f) return goal;
    const float k = 1.0f - std::exp(-dt / smoothTime);
    return current + (goal - current) * k;
}
```

素朴に書くと `current + (goal - current) * 0.2f` のような固定係数になりますが、**それだとフレームレートに依存します**。60 fps と 30 fps で追従速度が変わってしまう。

`1 − exp(−dt/τ)` を使うと、`dt` が半分になれば係数も適切に小さくなり、**実時間で同じ速さで追いつきます**。`τ`（`smoothTime`）は「目標との差が `1/e ≈ 37%` まで縮むのにかかる秒数」です。

この形は第 39 章のクロスフェードでも、第 59 章の LOD 補間でも使います。**`dt` に依存しない平滑化**は、覚えておく価値のある道具です。

## 51.5　実装

```cpp
struct FootIkResult { float pelvisDrop = 0.0f; std::vector<float> lift; };

inline FootIkResult SolveFootIk(const Skeleton& s, Pose& local,
                                std::vector<Transform>& global,
                                BoneIndex pelvis, std::span<const LegChain> legs,
                                GroundQuery ground, const FootIkSettings& cfg,
                                FootIkState& state, float dt) {
    FootIkResult out;
    const std::size_t n = legs.size();
    if (state.footOffset.size() != n) state.Resize(n);
    out.lift.assign(n, 0.0f);

    ComputeGlobalPose(s, local.Locals(), global);

    // (1) 各足の目標の持ち上げ量
    std::vector<float> rawLift(n, 0.0f);
    std::vector<GroundHit> hits(n);
    for (std::size_t i = 0; i < n; ++i) {
        const Vec3 footPos = global[legs[i].foot].translation;
        hits[i] = ground(footPos);
        if (!hits[i].hit) continue;
        const float desiredY = hits[i].height + cfg.footHeight;
        rawLift[i] = std::fmin(cfg.maxLift, desiredY - footPos.y);
    }

    // (2) 腰の下げ量 ＝ 最も深く沈む足に合わせる
    float rawDrop = 0.0f;
    for (std::size_t i = 0; i < n; ++i) rawDrop = std::fmin(rawDrop, rawLift[i]);
    rawDrop = std::fmax(-cfg.maxDrop, rawDrop);

    // (3) 時間方向に平滑化
    state.pelvisOffset = SmoothTowards(state.pelvisOffset, rawDrop, cfg.smoothTime, dt);
    for (std::size_t i = 0; i < n; ++i)
        state.footOffset[i] = SmoothTowards(state.footOffset[i], rawLift[i], cfg.smoothTime, dt);
    out.pelvisDrop = state.pelvisOffset;

    // (4) 腰を下げる
    local[pelvis].translation.y += state.pelvisOffset;
    ComputeGlobalPose(s, local.Locals(), global);

    // (5) 各脚を 2 ボーン IK で目標へ
    for (std::size_t i = 0; i < n; ++i) {
        const Vec3 footPos = global[legs[i].foot].translation;
        const Vec3 target{footPos.x,
                          footPos.y + state.footOffset[i] - state.pelvisOffset,
                          footPos.z};
        const Vec3 pole = global[legs[i].thigh].translation + legs[i].poleOffset * 10.0f;
        SolveTwoBoneIk(s, local, global, legs[i].thigh, legs[i].shin, legs[i].foot, target, pole);
        out.lift[i] = state.footOffset[i];

        // (6) 足首を地形の法線に合わせる
        if (hits[i].hit) {
            ComputeGlobalPose(s, local.Locals(), global);
            const Quat cur = global[legs[i].foot].rotation;
            const Vec3 up  = Rotate(cur, Vec3{0,1,0});
            const float cosA = std::fmin(1.0f, std::fmax(-1.0f, Dot(up, hits[i].normal)));
            const float ang  = std::fmin(std::acos(cosA), cfg.maxFootPitch);
            const Vec3 axis  = Cross(up, hits[i].normal);
            if (LengthSquared(axis) > 1.0e-12f)
                SetGlobalRotation(s, local, global, legs[i].foot,
                                  MakeQuatAxisAngle(Normalize(axis), ang) * cur);
        }
    }

    ComputeGlobalPose(s, local.Locals(), global);
    return out;
}
```

**(4) で腰を下げたあとに全体を再計算している**のに注目してください。第 48 章の `UpdateChainGlobals` は「チェーンの根元の親は動かない」という前提でした。腰を動かすとその前提が崩れるので、ここは全体の再計算が要ります。**最適化の前提条件を書き留めておくと、それが破れる場所が見つけられます。**

**(5) の目標の計算**が少し込み入っています。腰を `pelvisOffset` だけ下げたので、足首も同じだけ下がっています。本来置きたいのは「元の足首位置 + `footOffset`」なので、

```
target.y = (下げた後の足首 y) − pelvisOffset + footOffset
```

となります。腰の移動をキャンセルしてから、持ち上げ量を足す。

**(6) の足首合わせ**は、`SolveLookAt`（第 50 章）と同じ形です。足の裏の上方向 `(0,1,0)` を、地形の法線へ向けます。角度に上限を付けるのは、崖のような急な法線で足首がねじ切れないようにするためです。

## 51.6　テスト用の骨格

```cpp
struct Rig { Skeleton skel; BoneIndex pelvis, thighL, shinL, footL, thighR, shinR, footR; };

static Rig MakeBiped() {
    Rig r;
    Transform t = TransformIdentity();
    t.translation = {0, 1.0f, 0};    r.pelvis = r.skel.AddBoneRaw("pelvis", kNoParent, t);
    t.translation = {-0.15f, 0, 0};  r.thighL = r.skel.AddBoneRaw("thighL", r.pelvis, t);
    t.translation = {0, -0.45f, 0};  r.shinL  = r.skel.AddBoneRaw("shinL",  r.thighL, t);
    t.translation = {0, -0.45f, 0};  r.footL  = r.skel.AddBoneRaw("footL",  r.shinL,  t);
    t.translation = { 0.15f, 0, 0};  r.thighR = r.skel.AddBoneRaw("thighR", r.pelvis, t);
    t.translation = {0, -0.45f, 0};  r.shinR  = r.skel.AddBoneRaw("shinR",  r.thighR, t);
    t.translation = {0, -0.45f, 0};  r.footR  = r.skel.AddBoneRaw("footR",  r.shinR,  t);
    return r;
}
```

腰が `y = 1.0`、腿とすねが各 `0.45`。レストポーズでの足首は `y = 0.1` ―― `footHeight` と一致するので、**平らな床の上に立った状態**が初期条件です。

```cpp
TEST_METHOD(RestPoseStandsOnFlatGround) {
    Rig rig = MakeBiped();
    Pose p = Pose::FromRest(rig.skel);
    std::vector<Transform> g(rig.skel.BoneCount());
    ComputeGlobalPose(rig.skel, p.Locals(), g);
    Assert::AreEqual(0.1f, g[rig.footL].translation.y, 1e-6f);
}
```

**テストの初期条件を、まずテストで確かめる。** これを飛ばすと、後のテストが失敗したときに「IK が悪いのか、骨格が悪いのか」が分かりません。

## 51.7　単体テスト：平らな床では何も起きない

最も基本的な性質です。

```cpp
TEST_METHOD(FlatGroundChangesNothing) {
    Rig rig = MakeBiped();
    std::vector<Transform> g(rig.skel.BoneCount());
    const LegChain legs[2] = {
        {rig.thighL, rig.shinL, rig.footL, {0,0,1}},
        {rig.thighR, rig.shinR, rig.footR, {0,0,1}},
    };
    FootIkSettings cfg; FootIkState st; st.Resize(2);

    FootIkResult r{};
    for (int i = 0; i < 120; ++i) {
        Pose p = Pose::FromRest(rig.skel);           // ← 毎フレーム素のポーズから
        r = SolveFootIk(rig.skel, p, g, rig.pelvis, legs, FlatGround, cfg, st, 1.0f/60.0f);
    }
    Assert::AreEqual(0.0f, r.pelvisDrop, 1e-5f);
    Assert::AreEqual(0.1f, g[rig.footL].translation.y, 3e-4f);
}
```

実測：

```
平地: 腰の下げ -0.000000  足 L=-0.000000 R=-0.000000  足首 y L=0.100100 R=0.100100
```

腰は動かず、持ち上げ量もゼロ。足首は `0.100100`。

**`0.0001` はどこから来たか。** 第 47 章 47.4 の `epsilon` です。レストポーズの脚は完全に伸びきっていて（腿 0.45 + すね 0.45 = 0.9、股関節から足首まで 0.9）、2 ボーン IK は `maxReach = l1 + l2 − 1e-4` にクランプします。結果、膝がごくわずかに曲がり、足首が 0.1 mm 持ち上がる。

**予測できていた誤差なので、許容範囲を `3e-4` にして通します。** 「なんかちょっとずれるから緩めた」のではありません。**由来の分かっている誤差だけを許す。**

## 51.8　単体テスト：段差

左足の下だけ `0.2` 高い地形を用意します。

|---|---|---|---|
| 1 | `-0.000000` | `0.121032` | `0.100100` |
| 3 | `-0.000000` | `0.156694` | `0.100100` |

## 51.9　【誤】前フレームの結果に重ねる

ここまでのテストは、すべて**毎フレーム `Pose::FromRest` で素のポーズを作り直して**います。実際のゲームでは、毎フレームアニメーションを評価するので、これが自然な形です。

第 46 章 46.3 で「前フレームの補正結果に重ねてはいけない」と書きました。破ってみます。`Pose` をループの外で 1 度だけ作り、使い回します。

```cpp
Pose p = Pose::FromRest(rig.skel);      // ← ループの外（バグ）
for (int i = 1; i <= 120; ++i)
    r = SolveFootIk(rig.skel, p, g, rig.pelvis, legs, StepGround, cfg, st, 1.0f/60.0f);
```

| フレーム | 腰 | 左足首 y（正解 `0.3`） |
|---|---|---|
| 6 | `-0.001305` | **`0.357220`** |
| 12 | `-0.049567` | **`0.369942`** |
| 30 | `-0.023960` | `0.333456` |
| 60 | `-0.003769` | `0.295942` |
| 120 | `-0.000120` | `0.300090` |

**目標を 23% 行き過ぎ、腰が 5 cm 勝手に沈み、2 秒かけて振動しながら戻ってきます。**

原因は明快です。`rawLift` を「**現在の**足首の位置」から計算しているからです。

```cpp
rawLift[i] = desiredY - footPos.y;      // footPos は「今の」足首
```

1 フレーム目：足首は `0.1`、目標は `0.3`、持ち上げ量 `0.2`。平滑化を通して `0.021` だけ上げる。
2 フレーム目：足首は `0.121` に**上がっている**。しかしプログラムはそれが「アニメーションが作った位置」だと思い込み、目標との差 `0.179` をさらに持ち上げる ―― **前フレームで上げた分を、二重に数えています**。

これは**正のフィードバックループ**です。平滑化が付いているので発散はしませんが、行き過ぎと振動が出ます。腰が `-0.0496` まで沈んでいるのは、行き過ぎた足の位置が「地面より上にある」と判定され、腰下げのロジックが暴れた結果です。

**そして最後に見てほしいのは、120 フレーム目の `0.300090` です。** ほぼ正解に見えます。**静止状態で長く待てば、間違った実装でも正しい答えに落ち着く。** だから、

- 「最終値だけを見るテスト」では、このバグは**見つかりません**
- 実際のゲームでは、地形は毎フレーム変わります。**静止状態は永遠に来ません**

> **時間方向の挙動は、時間方向にテストする。** 収束後の値だけでなく、**途中経過を記録して比較する**。

これが第 VIII 部で得た、最も実務的な教訓かもしれません。

## 51.10　単体テスト：くぼみと腰下げ

右足の下だけ `−0.25` 低い地形です。脚は伸びきっているので、**足を下ろすには腰を下げるしかありません**。

```cpp
TEST_METHOD(PitDropsThePelvis) {
    auto Pit = [](Vec3 p) -> GroundHit { return {true, (p.x > 0.0f) ? -0.25f : 0.0f, {0,1,0}}; };
    // ... 200 フレーム
    Assert::IsTrue(r.pelvisDrop < -0.2f);
    Assert::AreEqual( 0.1f,  g[rig.footL].translation.y, 3e-3f);
    Assert::AreEqual(-0.15f, g[rig.footR].translation.y, 3e-3f);
}
```

実測：

```
くぼみ: 腰の下げ -0.250000  足首 y L=0.100000 R=-0.149900
```

腰がちょうど `0.25` 下がり、右足は `−0.15`（地面 `−0.25` + `footHeight` `0.1`）、**左足は `0.1` のまま動いていません**。

左足が動かないのが重要です。腰が下がった分、左足も一緒に下がろうとしますが、(5) の目標計算で `− pelvisOffset` を引いているので、IK が元の高さへ引き戻しています。**腰を下げても、地面に着いている足は動かない。** これが正しい挙動です。

腰下げの量を「最も深く沈む足に合わせる」（`min` を取る）のもポイントです。両足の平均にすると、深いほうの足が届かなくなります。**片方でも届かない足があってはいけない**ので、最悪ケースに合わせます。

## 51.11　単体テスト：坂と足首の姿勢

20 度の坂です。

```cpp
TEST_METHOD(FootAlignsToSlopeNormal) {
    // ... 200 フレーム、SlopeGround
    const Vec3 up = Rotate(g[rig.footL].rotation, Vec3{0,1,0});
    const Vec3 n  = Normalize(Vec3{-std::tan(20.0f*kIkPi/180.0f), 1, 0});
    const float err = std::acos(std::fmin(1.0f, std::fmax(-1.0f, Dot(up, n)))) * 180.0f / kIkPi;
    Assert::AreEqual(0.0f, err, 0.05f);
}
```

実測：`左足の上向き (-0.342020, 0.939693, -0.000000) 法線との差 0.000000 度`。

`(−0.342020, 0.939693, 0)` は `sin(−20°) = −0.34202`、`cos(20°) = 0.93969` ―― **ちょうど 20 度傾いています**。足の裏が坂に平行になりました。

「法線との差 0.000000 度」というのは、`float` の精度で完全一致という意味です。手計算の値と突き合わせられるので、これはゴールデンテストとしても機能します。

## 51.12　単体テスト：平滑化は何を防いでいるのか

段差を「瞬間的に」またぐ場面 ―― 30 フレーム目に地面が `0` から `0.2` へ跳ね上がる ―― で、1 フレームあたりの足首の最大移動量を測ります。

```cpp
TEST_METHOD(SmoothingLimitsPerFrameMovement) {
    for (float smooth : {0.0f, 0.05f, 0.15f}) {
        FootIkSettings c; c.smoothTime = smooth;
        // ... 60 フレーム、30 フレーム目で地面が跳ね上がる
        // 1 フレームあたりの足首 y の変化の最大値を記録
    }
}
```

| `smoothTime` | 1 フレームあたりの最大移動量 |
|---|---|
| `0.00` 秒（平滑化なし） | `0.199900` |
| `0.05` 秒 | `0.056594` |
| `0.15` 秒 | `0.020932` |

平滑化なしだと、**1 フレームで 20 cm 足が飛びます**。60 fps なら 12 m/s。目に見えるポップです。

`0.15` 秒の平滑化を入れると `2 cm`、10 分の 1 に落ちます。

**トレードオフは追従の遅れです。** 51.8 の表で見たとおり、`0.15` 秒だと `0.3` に到達するまで実質 1 秒かかります。歩行中に段差を踏むとき、足が着地してから 1 秒かけて正しい高さになる ―― これは遅すぎます。

実務では、

- **接地している足には短い時定数**（`0.03`〜`0.05` 秒）、**浮いている足には長い時定数**を使う
- **足の接地状態をアニメーションからメタデータとして持つ**（第 60 章のアニメーションイベントと同じ仕組み）
- 速度に応じて時定数を変える

といった作り込みをします。**この本の実装は「平滑化がなぜ要るか」を示すところまで**で、実用にはもう一段の作り込みが要ります。

## この章のまとめ

- 地形の問い合わせは**アニメーションシステムの外**。`GroundHit` を配列で受け取る形にすれば、第 57 章のマルチスレッド化でも困らない。
- **`Settings` と `State` を別の型にする**。フット IK はこの本で唯一、時間方向の状態を持つ IK ―― 例外であることが型から見えるようにする。
- 指数平滑は **`1 − exp(−dt/τ)`**。固定係数だとフレームレートに依存する。理論値（`0.1` 秒で 49%、`0.2` 秒で 74%）と実測が一致することまで確認できる。
- 腰の下げ量は**最も深く沈む足に合わせる**（平均ではなく `min`）。腰を下げても、**地面に着いている足は動かない**（目標計算で `− pelvisOffset`）。
- 平らな床での足首 `0.100100` は、第 47 章の `epsilon` そのもの。**由来の分かっている誤差だけを許す。**
- 足首の法線合わせは実測 **`0.000000` 度**、上向きベクトルは `(−0.342020, 0.939693, 0)` ＝ ちょうど 20 度。
- 平滑化なしだと **1 フレームで 20 cm** 足が飛ぶ。`0.15` 秒で `2 cm`。ただし追従が 1 秒遅れる ―― **接地状態に応じて時定数を変える**のが実務。
- **踏んではいけないバグ**：前フレームの補正結果に IK を重ねると、**目標を 23% 行き過ぎ、腰が 5 cm 沈み、2 秒かけて振動しながら戻る**。原因は正のフィードバックループ。
- そしてそのバグは、**静止状態で長く待てば正しい値に落ち着く**（`0.300090`）。**最終値だけを見るテストでは見つからない。時間方向の挙動は、時間方向にテストする。**

## 第 VIII 部を終えて

第 1 章のパイプラインが、これで全段そろいました。

```
① クリップをサンプル    ← ✅ 第 V 部
② ブレンド              ← ✅ 第 VII 部
③ 階層を解く            ← ✅ 第 14 章
④ IK で補正             ← ✅ 第 VIII 部
⑤ パレットを作る        ← ✅ 第 16 章
⑥ 頂点を変形            ← ✅ 第 18・22 章
```

**アニメーションシステムとして、動くものが完成しました。** glTF モデルを読み込み、クリップを再生し、ブレンドし、IK で地面に足を合わせ、スキニング行列パレットを出力するところまで。

第 VIII 部で繰り返した方針を振り返ります。

**測って初めて分かることがある。** 第 48 章の CCD は、コードを何度読んでも「正しい」ように見えました。実際、リミットサイクルの原因は `FromToRotation` の中の `0.99999` という数字 1 つで、CCD 側には何の問題もありませんでした。**しきい値を振ってプラトーの高さが比例することを確かめる** ―― この実験なしに、原因を特定できたとは思えません。

**バグを直すと別のバグが顔を出す。** クォータニオンの正規化を入れたら、収束していた CCD が収束しなくなりました。ドリフトのノイズが、たまたま収束を助けていた。**「今動いているから正しい」は成り立ちません。**

**制御したい量と、制御している量を一致させる。** 第 50 章のルックアットは、「1 回で回す量」を制限して「累積のひねり」を制限したつもりになっていました。第 28 章（ループ回数とサンプル時刻）、第 45 章（遷移元の状態と時刻）に続く 3 度目です。形は毎回違いますが、**測らないと分からない**という点は共通しています。

**冪等性は、テストできる性質である。** 「何回呼んでも同じ結果になる」は、「上限を超えない」よりも強く、しかも書きやすいテストです。フレームごとに何度呼ばれるか分からない処理では、これを満たしていることが安全の根拠になります。

**時間方向の挙動は、時間方向にテストする。** 第 51 章のフィードバックループは、収束後の値を見るテストでは絶対に見つかりません。**途中経過を記録して並べる**。表を作る手間は、バグ 1 つ分に見合います。

**壊れているほうも、テストで固定する。** `FromToRotationAcos` が小角度で何もしないこと、`SolveLookAt` が 2 回呼ぶと制限を破ること。これらは「直すべきバグ」ではなく「**この実装の性質**」として記録しました。将来だれかが親切に「直して」しまったら、本文の説明と食い違います。

第 VIII 部で書いたテストは 63 個、すべて緑です。

次章から第 IX 部。ここまでは「1 体を正しく動かす」話でした。**第 IX 部は「100 体を速く動かす」話**です。データ指向への再設計、SIMD、キーフレーム圧縮、マルチスレッド、GPU スキニング。

そして第 IX 部の全編を通じて盾になるのが、**ここまでに書いたテストのすべて**です。第 52 章の再設計は、既存のテストが 1 つも赤くならないことを条件に進めます。「速くしたが壊れた」を許さないための装備は、もう整っています。
