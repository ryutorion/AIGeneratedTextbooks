# 第 4 章　浮動小数点とアニメーション

**この章で作るもの**：`/fp:fast` を有効にしたビルド設定、非正規化数を切る `ScopedDenormalsAreZero`、そして本書全体で使う許容誤差の定数群。あわせて、誤差が実際にどう蓄積するかを測るテストを書きます。

前章では「許容誤差で比較する」という方針を立て、暫定的に `1.0e-5f` という値を置きました。この章では、その値に根拠を与えます。

---

## 4.1　誤差はどこで生まれるのか

アニメーションのコードで誤差が生まれる場所は、大きく 3 つです。

**① 補間** ―― 2 つのキーフレームのあいだを補間するたびに、乗算と加算が走ります。1 回あたりの誤差は小さいのですが、これが毎フレーム、全ボーンぶん行われます。

**② 変換の連鎖** ―― 指先のワールド姿勢を求めるには、指 → 手 → 前腕 → 上腕 → 肩 → 胸 → 脊椎 → 腰 → ルート、と 9 段ほど行列を掛けます。誤差は段数に応じて増えていきます。人型のスケルトンで深さ 10 前後は普通です。

**③ 正規化のドリフト** ―― クォータニオンを掛け合わせていくと、長さが少しずつ 1 からずれます。放置すると回転にスケール成分が混ざり、モデルが膨らんだり潰れたりします。

このうち ③ が、いちばん厄介です。①② の誤差は「その場限り」ですが、③ は**状態に蓄積して育つ**からです。実感しておきましょう。

`AnimLib.Tests/FloatBehaviorTests.cpp` を新規作成し、次のテストを書きます。クォータニオンはまだないので、2 次元の回転で代用します。原理は同じです。

```cpp
#include "CppUnitTest.h"

#include "TestSupport/Near.h"

#include <cmath>
#include <format>

using namespace Microsoft::VisualStudio::CppUnitTestFramework;

namespace AnimLibTests {

TEST_CLASS(FloatBehaviorTests) {
public:

    // 正規化しないまま回転を掛け続けると、長さが 1 から離れていく
    TEST_METHOD(RotationDriftsWithoutNormalization) {
        const float angle = 0.01f;          // 1 ステップの回転角（ラジアン）
        const float c = std::cos(angle);
        const float s = std::sin(angle);

        float x = 1.0f;
        float y = 0.0f;
        for (int i = 0; i < 100000; ++i) {
            const float nx = x * c - y * s;
            const float ny = x * s + y * c;
            x = nx;
            y = ny;
        }

        const float length = std::sqrt(x * x + y * y);
        Logger::WriteMessage(
            std::format(L"length after 100000 rotations = {:.9g}\n", length).c_str());

        // 「1 に近い」はずだが、どれくらい近いかは環境で変わる。
        // まずは緩い上限だけ置いて、実際の値をログで見る。
        Assert::IsTrue(std::fabs(length - 1.0f) < 0.1f);
    }
};

}  // namespace AnimLibTests
```

実行して、出力ペイン（テストエクスプローラーで該当テストを選び［出力］リンク）に出た `length` の値を見てください。筆者の環境では `0.999138594`、つまり 10 万回で長さが 0.09% 縮みました。

面白いのは、**この角度では `c*c + s*s` が float で厳密に 1.0 になる**ことです（手元で確かめてみてください）。それでも長さはドリフトします。原因は 1 ステップあたり 6 回行われる乗算・加算それぞれの丸めで、1 回あたり 1e-7 程度のずれが、たまたま縮む方向にわずかに偏っているのです。

ここから 2 つのことが言えます。**「掛ける値が正確なら大丈夫」ではない。** そして **1e-7 は 10 万回で 1e-3 になる**。60 fps なら 10 万フレームは 28 分です。

これがクォータニオンで起きると、キャラクターがじわじわ膨らみます（あるいは縮みます）。対策は単純で、**定期的に正規化する**だけです。第 8 章でクォータニオンを作るとき、この経験が効いてきます。

## 4.2　`/fp:fast` を選ぶ

さて、速度の話をします。

MSVC の既定は `/fp:precise` です。これは IEEE 754 の意味論をかなり忠実に守るモードで、コンパイラは演算順序を勝手に入れ替えたりしません。

ゲームのアニメーションでは、この保守性は基本的に**割に合いません**。1000 体のキャラクター、各 100 ボーン、毎フレーム。ここで数割の差が出るなら、それは無視できない差です。そこで本書は `/fp:fast` を採用します。

### 設定する

第 2 章で作った `AnimBook.props` の `<ClCompile>` に 1 行足します。

```xml
      <!-- 浮動小数点モデル：速度優先 -->
      <FloatingPointModel>Fast</FloatingPointModel>
```

ビルドして、`/fp:fast` がコマンドラインに現れることを確認してください。ここでも「プロパティシートに書く」ことが効いています。ライブラリだけ `/fp:fast`、テストだけ `/fp:precise` という状態は、**テストが本番と違う計算をする**ことを意味し、最悪の種類の不一致を生みます。

### `/fp:fast` は何を許すのか

主なものを挙げます。

**再結合（reassociation）** ―― `(a + b) + c` を `a + (b + c)` に組み替えます。数学的には同じですが、浮動小数点では結果が変わります。ループの加算を 4 本に分けて SIMD 化するといった最適化は、これが許されて初めて可能になります。

**FMA への融合（contraction）** ―― `a * b + c` を 1 命令の `fma(a, b, c)` にまとめます。**中間の丸めが 1 回減るので、むしろ精度は上がります。** ただし「精度が上がる」ことも変化には違いなく、`/fp:precise` のもとでは（VS 2022 以降の既定では）行われません。

**除算の乗算化** ―― `x / y` を `x * (1 / y)` に。ループ内で同じ `y` で割るとき、逆数を 1 回だけ計算して使い回せます。ウェイトの正規化などで効きます。

**特殊値の仮定** ―― NaN や ±0 の符号を「気にしなくてよい」ものとして扱います。`x * 0.0f` を `0.0f` に畳む、`x - x` を `0.0f` に畳む、といった最適化が入ります。

最後のものが、次節の問題を生みます。

## 4.3　`/fp:fast` が壊すもの

`/fp:fast` のもとで壊れるコードには、はっきりしたパターンがあります。

**パターン 1：NaN の検出** ―― `x != x` で NaN を判定するイディオムは、`x == x` が常に真だと仮定されると消えます。`std::isnan` も、実装によっては同様に最適化されえます。

**パターン 2：補正項を使う数値アルゴリズム** ―― カハンの加算アルゴリズム（次節で使います）は、`(sum + y) - sum - y` という「数学的にはゼロだが浮動小数点ではゼロでない値」を取り出すことで精度を稼ぎます。再結合が許されると、この式は `0` に畳まれ、アルゴリズムまるごとが無意味な足し算に変わります。**エラーも警告も出ずに、静かに壊れます。**

**パターン 3：厳密な一致に依存する処理** ―― 「この 2 つの計算経路は同じ結果を出すはず」という前提は、片方だけ FMA に融合されると崩れます。

つまり `/fp:fast` を採用するというのは、**「誤差の大きさを気にしないコード」には最適で、「誤差そのものを扱うコード」には使えない**、という選択です。本書のライブラリの 99% は前者ですが、後者もわずかに存在します。前章の `IsNear` がまさにそれでした。

## 4.4　局所的に `/fp:precise` へ戻す

`#pragma float_control` を使うと、ファイル全体の設定を上書きして、一部だけ厳密な意味論に戻せます。

```cpp
#pragma float_control(precise, on, push)
// ここに書いた関数は /fp:precise 相当でコンパイルされる
#pragma float_control(pop)
```

**このプラグマは関数の外（グローバルまたは名前空間スコープ）に書きます。** 関数本体の途中には置けません。挟む範囲は関数定義の単位です。

前章の `IsNear` に適用しましょう。`TestSupport/Near.h` の `IsNear` を、次のように囲みます。

```cpp
namespace anim::test {

// この関数は NaN と無限大を正しく扱うことが仕事なので、
// /fp:fast の「特殊値は起きない」という仮定を無効にする。
#pragma float_control(precise, on, push)

[[nodiscard]] inline bool IsNear(float a, float b,
                                 float absTol = kDefaultAbsTol,
                                 float relTol = kDefaultRelTol) noexcept {
    // （中身は第 3 章のまま）
    ...
}

#pragma float_control(pop)

}  // namespace anim::test
```

前章で書いた `NanIsNeverNear` と `InfinityCompares` のテストが、`/fp:fast` を有効にしたあとも緑のままであることを確認してください。**もしプラグマを外して赤くなるなら、それはこのプラグマが実際に仕事をしている証拠です。**一度試してみる価値があります。

本書でこの扱いをする箇所は、結局のところ次の 4 つだけです。

| 場所 | 章 | 理由 |
| --- | --- | --- |
| `IsNear` | 3 | NaN・無限大を正しく判定する |
| カハンの加算 | 4（本章） | 補正項が畳まれると壊れる |
| クォータニオンの `acos` 前のクランプ | 10 | 定義域外の値を確実に弾く |
| 圧縮誤差の計測コード | 55 | 誤差そのものを測る |

`/fp:fast` を全体に効かせ、必要な 4 箇所だけ戻す。この配分が、ゲーム向けのコードでは妥当なバランスです。

## 4.5　非正規化数 ―― 静かに遅くなる

float の指数部が下限に達すると、それ以上は仮数部の精度を削ることで、より 0 に近い値を表します。これが**非正規化数（denormal / subnormal）**です。float では約 `1.18e-38` を下回る値がこれにあたります。

問題は、多くの x86 CPU で**非正規化数が絡む演算が極端に遅い**ことです。マイクロアーキテクチャによりますが、乗除算で数十サイクルのペナルティが乗ることがあります。近年の CPU では加減算のペナルティはほぼ解消されていますが、乗除算では依然として発生しうる、と考えておくのが安全です。

そしてアニメーションのコードは、**非正規化数を作りやすい構造をしています。**

- クロスフェードの終盤、ブレンドウェイトが 0 に向かって指数的に減衰していく
- 加算ブレンドの差分クォータニオンが、ほぼ単位回転（差が 0 に漸近）
- キーフレーム間の補間係数が、キー直前で極小になる
- IK の収束判定近く、残差が 0 に漸近する

いずれも「値が小さくなること自体は正常」なケースばかりです。だから**バグとしては現れず、フレームレートが落ちるだけ**という形で問題化します。プロファイラで見ても、特定の行が理由もなく遅い、という不可解な結果になります。

対策は、CPU に「非正規化数はゼロとして扱え」と指示することです。x86 には 2 つのフラグがあります。

- **FTZ（Flush To Zero）**：演算**結果**が非正規化数になったら 0 にする
- **DAZ（Denormals Are Zero）**：演算**入力**が非正規化数なら 0 とみなす

両方を立てれば、非正規化数はパイプラインから消えます。失うのは 1e-38 未満の精度ですが、アニメーションでこの領域に意味のある情報が入ることはありません。

## 4.6　FTZ / DAZ を明示的に設定する

コンパイラオプションによって既定が変わることがありますが、**依存しないのが正解です。** 自分で設定し、テストで確認します。

さらに重要な性質があります。**この設定はスレッドごと**です（x64 では MXCSR レジスタの状態そのもの）。ワーカースレッドを起こすたびに設定し直さなければなりません。第 57 章でジョブシステムを作るとき、この点が効いてきます。

RAII で扱えるようにしましょう。これはテスト専用ではなくライブラリの機能なので、`AnimLib` 側に置きます。

**`AnimLib/include/anim/FloatEnv.h`**

```cpp
#pragma once

namespace anim {

// このスコープのあいだ、非正規化数をゼロとして扱う（FTZ + DAZ）。
// x64 では MXCSR を書き換えるため、効果は「現在のスレッドのみ」。
// ワーカースレッドでは、そのスレッド上で別途構築すること。
class ScopedDenormalsAreZero {
public:
    ScopedDenormalsAreZero() noexcept;
    ~ScopedDenormalsAreZero();

    ScopedDenormalsAreZero(const ScopedDenormalsAreZero&) = delete;
    ScopedDenormalsAreZero& operator=(const ScopedDenormalsAreZero&) = delete;

private:
    unsigned int savedDenormalControl_ = 0;
};

// 現在のスレッドで非正規化数がゼロに潰されるかを実測する。
// 設定の確認とテスト用。
[[nodiscard]] bool DenormalsAreCurrentlyFlushed() noexcept;

}  // namespace anim
```

**`AnimLib/src/FloatEnv.cpp`**

```cpp
#include "anim/FloatEnv.h"

#include <float.h>

namespace anim {

ScopedDenormalsAreZero::ScopedDenormalsAreZero() noexcept {
    unsigned int current = 0;
    // 第 2・第 3 引数を 0 にすると、変更せずに現在値を読み出せる
    _controlfp_s(&current, 0, 0);
    savedDenormalControl_ = current & _MCW_DN;

    unsigned int ignored = 0;
    _controlfp_s(&ignored, _DN_FLUSH, _MCW_DN);
}

ScopedDenormalsAreZero::~ScopedDenormalsAreZero() {
    unsigned int ignored = 0;
    _controlfp_s(&ignored, savedDenormalControl_, _MCW_DN);
}

// 実測する。コンパイル時に畳み込まれないよう volatile を使う。
#pragma float_control(precise, on, push)
bool DenormalsAreCurrentlyFlushed() noexcept {
    volatile float small  = 1.0e-37f;    // これは正規化数
    volatile float scaled = small * 0.01f;  // 1e-39 → 非正規化数のはず
    return scaled == 0.0f;
}
#pragma float_control(pop)

}  // namespace anim
```

`volatile` が要るのは、そうしないとコンパイラが `1.0e-37f * 0.01f` をコンパイル時に計算してしまい、実行時の CPU の状態を測れないからです。

### テスト

`FloatBehaviorTests.cpp` に追加します。

```cpp
    // 環境の既定がどうなっているかを記録する（判定はしない）
    TEST_METHOD(ReportDefaultDenormalBehavior) {
        const bool flushed = anim::DenormalsAreCurrentlyFlushed();
        Logger::WriteMessage(flushed
            ? L"default: denormals ARE flushed\n"

        Assert::IsTrue(anim::DenormalsAreCurrentlyFlushed());

    // ガードを抜けたら元に戻る

        const bool before = anim::DenormalsAreCurrentlyFlushed();

```

1 つ目のテストは何も検証しません。**あなたの環境の既定を記録するだけ**です。ログに出た結果を見て、「なるほど、明示的に設定する必要があるのか（あるいは既に潰されているのか）」を確認してください。テストを「事実を記録する道具」として使うのも、正当な用法です。

実際のゲームでは、メインループとワーカースレッドの起動時に一度ずつガードを構築します。本書では第 57 章まで並列化しないので、それまではこのクラスは出番待ちです。

## 4.7　誤差の蓄積を測る

`/fp:fast` を有効にしたところで、実際どれくらいの誤差が出るのかを測っておきます。題材は**時刻の積算**です。アニメーションの再生時刻は、毎フレーム `t += dt` で進めるのが素朴な実装だからです。

```cpp
    TEST_METHOD(TimeAccumulationDrifts) {
        constexpr int   kFrames = 100000;
        constexpr float kDt     = 1.0f / 60.0f;

        float accumulated = 0.0f;
        for (int i = 0; i < kFrames; ++i) {
            accumulated += kDt;
        }

        // 参照値：同じ kDt を double で kFrames 倍したもの。
        // これで「1/60 が float で表せない」ぶんの誤差を除き、
        // 積算そのものによる誤差だけを見る。
        const double reference = static_cast<double>(kDt) * kFrames;
        const double error     = std::fabs(static_cast<double>(accumulated) - reference);

        Logger::WriteMessage(std::format(
            L"accumulated = {:.9g}, reference = {:.9g}, error = {:.4g} sec\n",
            accumulated, reference, error).c_str());

        // 100000 フレーム = 約 28 分。この程度の再生でどれだけずれるか。
        Assert::IsTrue(error < 10.0);
    }
```

ログに出た `error` を見てください。筆者の環境では **約 1.99 秒**でした。

もう一度書きます。**28 分の再生で、時刻が 2 秒ずれます。** 60 fps なら約 120 フレームぶんです。アニメーションイベント（足音、攻撃判定、エフェクト発生）の発火タイミングを考えれば、これは到底許容できません。

なぜこれほど大きくなるのか。`accumulated` が 1600 付近まで育つと、その領域での float の刻みは約 1.2e-4 です。そこに 0.0167 を足すたびに、最大でその半分がこぼれます。これが 10 万回積み重なりました。**誤差は値が大きくなるほど加速する**のです。

なお `/fp:fast` によるループのベクトル化（部分和への分割）が効くと、この値は逆に**小さくなる**ことがあります。部分和それぞれが小さい値に留まるためです。テストのしきい値を `10.0` と緩めに置いてあるのは、この振れ幅を許容するためです。ここで見たいのは正確な値ではなく、**桁**です。

### もっと悪いケース

積算誤差より深刻な問題があります。

```cpp
    TEST_METHOD(TimeStopsAdvancingWhenLarge) {
        constexpr float kDt = 1.0f / 60.0f;

        float t = 1.0e6f;      // 約 11.6 日ぶんの経過時間
        const float before = t;
        t += kDt;

        // 何も起きない
        Assert::IsTrue(t == before, L"時刻が進んでしまった");
    }
```

`1.0e6f` 付近での float の刻みは約 0.0625 で、加えようとしている `1/60 ≒ 0.0167` はその半分（0.03125）に満たないため、**加算結果が元の値に丸め戻されます。時刻が凍結します。**

これは実在するバグの型です。「起動しっぱなしにしていたら、しばらくしてアニメーションが止まった」という不具合の典型的な原因がこれです。

対策は 3 つあり、本書では 3 つとも使います。

1. **時刻を絶対値で持たない。** クリップ内の再生位置は常に `[0, duration)` に折り返す（第 26 章）。
2. **長い時間を扱う変数は `double` にする。** ゲーム全体の経過時間など（第 27 章）。
3. **積算せず、フレーム数から計算する。** 固定ステップの場面で有効です。

### カハンの加算 ―― `/fp:fast` の落とし穴の実例

どうしても積算が必要な場合、カハンの加算アルゴリズムで誤差を大幅に減らせます。ここで 4.3 節の話が具体的になります。

次の関数は、`#pragma float_control` を使う都合上、**`TEST_CLASS` の外**（`FloatBehaviorTests.cpp` の名前空間スコープ）に置いてください。

```cpp
// 補正項が畳まれないよう、必ず precise で。
// このプラグマを外すと、下のテストは赤くなる（かもしれない）。
#pragma float_control(precise, on, push)
float KahanSum(float value, int count) noexcept {
    float sum          = 0.0f;
    float compensation = 0.0f;   // 前回こぼれた分
    for (int i = 0; i < count; ++i) {
        const float y = value - compensation;
        const float t = sum + y;
        // (t - sum) は「実際に sum に加算された量」。
        // y との差が、丸めでこぼれた分になる。
        compensation = (t - sum) - y;
        sum = t;
    }
    return sum;
}
#pragma float_control(pop)
```

```cpp
    TEST_METHOD(KahanSumIsMoreAccurate) {
        constexpr int   kFrames = 100000;
        constexpr float kDt     = 1.0f / 60.0f;

        float naive = 0.0f;
        for (int i = 0; i < kFrames; ++i) {
            naive += kDt;
        }
        const float kahan = KahanSum(kDt, kFrames);

        const double reference  = static_cast<double>(kDt) * kFrames;
        const double naiveError = std::fabs(static_cast<double>(naive) - reference);
        const double kahanError = std::fabs(static_cast<double>(kahan) - reference);

        Logger::WriteMessage(std::format(
            L"naive error = {:.4g}, kahan error = {:.4g}\n",
            naiveError, kahanError).c_str());

        Assert::IsTrue(kahanError <= naiveError);
    }
```

筆者の環境では `naive error = 1.99`、`kahan error = 5.5e-06` でした。**36 万倍の改善**です。カハンの加算のコストは 1 回あたり減算 2 回ぶんで、これだけの差が付きます。

**実験してみてください。** `KahanSum` を囲んでいる `#pragma float_control` の 2 行をコメントアウトして再実行すると、`kahan error` が `naive error` と同じ値に化ける可能性があります。再結合によって `compensation` が常に 0 に畳まれ、ただの素朴な加算になったということです。

コンパイラのバージョンや最適化の判断によっては変化しないこともありますが、**「壊れても何のメッセージも出ない」という点こそが重要**です。だから `/fp:fast` を使うプロジェクトでは、「誤差を扱うコード」を明示的に隔離する規律が要るのです。

## 4.8　許容誤差の値を決める

ここまでの観察をもとに、本書で使う許容誤差を決めます。基準は一つ、**「そのずれは画面上で見えるか」**です。

換算してみましょう。身長 1.8 m のキャラクターが画面の高さいっぱい（仮に 1080 px）に映っているとき、1 px はおよそ 1.7 mm に相当します。つまり **0.1 mm（1.0e-4 m）のずれは、1 px の 1/17** です。どう頑張っても見えません。

角度も同じように換算できます。腕の付け根で 1.0e-4 ラジアン（約 0.0057 度）ずれたとき、腕の長さを 0.6 m とすれば指先のずれは 0.6 × 1.0e-4 = 0.06 mm。これも見えません。

一方、**正規化されたベクトルやクォータニオンの長さ**については、もっと厳しくすべきです。長さが 1.0e-4 ずれているというのは、そこに 0.01% のスケールが混入しているということで、これは第 4.1 節で見たとおり**蓄積して育つ**種類の誤差です。入口で厳しく止めます。

`AnimLib.Tests/TestSupport/Tolerance.h` を作ります。

```cpp
#pragma once

namespace anim::test {

// --- 単位量（長さ 1 であるべきもの）-----------------------------------
// クォータニオン・法線・回転行列の各軸の長さ。
// 蓄積して育つ種類の誤差なので、入口で厳しく見る。
inline constexpr float kEpsUnit = 1.0e-6f;

// --- 方向・成分 -------------------------------------------------------
// 正規化済みベクトルの各成分、内積の値など。
inline constexpr float kEpsDir = 1.0e-5f;

// --- 位置（メートル）--------------------------------------------------
// 1.0e-4 m = 0.1 mm。1080p で身長いっぱいに映して 1/17 px。
inline constexpr float kEpsPos = 1.0e-4f;

// --- 角度（ラジアン）--------------------------------------------------
// 1.0e-4 rad ≒ 0.0057 度。腕の長さ 0.6 m の先端で 0.06 mm。
inline constexpr float kEpsAngle = 1.0e-4f;

// --- 蓄積後 -----------------------------------------------------------
// 深い階層をたどった後、または多数フレーム回した後の比較に使う。
// これを超えたら、誤差ではなくアルゴリズムを疑う。
inline constexpr float kEpsAccum = 1.0e-3f;

}  // namespace anim::test
```

第 5 章以降、テストではこの名前付き定数を使います。`1.0e-4f` とベタ書きするのに比べて、

- **なぜその値なのかが名前に書いてある**
- **後から一括で見直せる**
- **不適切な緩和が目立つ**（位置の比較に `kEpsAccum` を使っていたら、レビューで気づけます）

という利点があります。テストで許容誤差を緩めたくなったときは、まず「本当にその誤差は妥当か」を疑ってください。テストを通すために許容誤差を上げるのは、**火災報知器の電池を抜く**のと同じ行為です。

> **単精度と倍精度**
> 本書のライブラリは一貫して `float` を使います。ボーンあたりの `Transform` は 10 個の float（位置 3・回転 4・スケール 3）で 40 バイト。100 ボーンで 4 KB、1000 体で 4 MB です。`double` にすれば 8 MB になり、キャッシュに乗る量が半分になります。アニメーションはメモリ帯域律速になりやすい処理なので、この差は速度に直結します。
> `double` を使うのは、時刻（第 27 章）と、誤差そのものを測るテストコードだけです。

## 4.9　つまずきやすいところ

**`warning C4996: '_controlfp' が非推奨です`**
`_controlfp` ではなく `_controlfp_s` を使ってください。`/WX` があるので警告はビルドを止めます。

**`error C2374` などが `#pragma float_control` の行で出る**
プラグマを関数の内側に書いています。関数定義の外（グローバルまたは名前空間スコープ）に置いてください。

**`#pragma float_control(precise, off)` を書いたらエラーになる**
`precise` を `off` にするには、先に `except` を `off` にしておく必要があります。本書では `precise, on` の方向にしか使わないので、この状況には遭遇しないはずです。

**`ScopedDenormalsAreZero` を使ってもテストで効果が見えない**
`volatile` を外していないか確認してください。`volatile` がないと、コンパイル時に定数畳み込みされてしまい、実行時の CPU の状態と無関係な結果になります。

**別スレッドで非正規化数が潰されない**
仕様どおりです。FTZ/DAZ はスレッドごとの設定です。そのスレッドで改めてガードを構築してください。

**`/fp:fast` にしたら既存のテストが赤くなった**
まず、そのテストが**厳密一致**を要求していないか確認してください（`Assert::AreEqual` を float に使っている、など）。`AssertNear` に置き換えるべき場所かもしれません。そうでない場合、そのコードは 4.3 節のパターンのどれかに該当している可能性があります。`#pragma float_control(precise, on, push)` で囲んで赤が消えるなら、パターンに当たりです。

## この章のまとめ

- 誤差の生まれる場所は **補間・変換の連鎖・正規化のドリフト**。このうちドリフトだけが状態に蓄積して育つので、定期的な正規化が要る。
- **`/fp:fast` を全体に適用**し、必要な数箇所だけ `#pragma float_control(precise, on, push)` で戻す。本書ではその箇所は 4 つだけ。
- `/fp:fast` は**エラーも警告も出さずに**カハンの加算のような補正アルゴリズムを壊す。「誤差を扱うコード」の隔離は規律の問題。
- **非正規化数**はアニメーションのコードで自然に発生し、バグではなく**速度低下**として現れる。FTZ/DAZ を明示的に設定し、テストで確認する。設定はスレッドごと。
- `float` の時刻は、**大きくなると加算が効かなくなって凍結する**。時刻はクリップ長で折り返し、長い経過時間は `double` で持つ。
- 許容誤差は「**画面上で見えるか**」を基準に決めた。位置 `1.0e-4`（= 0.1 mm）、角度 `1.0e-4` rad、単位量 `1.0e-6`、蓄積後 `1.0e-3`。テストを通すために許容誤差を上げるのは、火災報知器の電池を抜くのと同じ。

これで第 I 部は完了です。テストの土台が整い、数値の扱い方の方針も決まりました。次章から第 II 部に入り、`Vec3` から順に数学の道具を組み上げていきます。ようやくアニメーションらしいコードが始まります。
