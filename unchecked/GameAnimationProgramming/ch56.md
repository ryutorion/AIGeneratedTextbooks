# 第 56 章　圧縮データのサンプリング

**この章で作るもの**：第 54・55 章の圧縮形式を、**展開せずにそのまま読む**サンプラー。185.9 KB のクリップを **14.6 KB** にして、しかも**サンプリングが速くなります**。

---

## 56.1　「展開しない」ということ

圧縮したデータの使い方には、2 通りあります。

**① ロード時に展開する。** ディスクから読んで、メモリ上で元の形式に戻す。ロード時間とディスク容量は減りますが、**実行時のメモリは 1 バイトも減りません**。

**② 圧縮したまま読む。** メモリ上に圧縮形式のまま置き、サンプリングのたびにその場で復元する。

第 53 章で「1000 体ではメモリ帯域が律速」と測りました。だから **② でなければ意味がありません**。①だと、第 IX 部の主目的が達成できない。

②の代償は、サンプリングごとの復元コストです。`UnpackQuat` は平方根 1 回と割り算 3 回。**これが探索と補間のコストに見合うのか** ―― それを最後に測ります。

## 56.2　メモリレイアウトを決める

まず、ボーンごとのヘッダ。

```cpp
struct CompressedBone {
    std::uint32_t rotOffset = 0;  std::uint16_t rotCount = 0;   // 0 なら定数
    std::uint32_t posOffset = 0;  std::uint16_t posCount = 0;   // 0 なら定数
    Vec3Range     posRange;                                     // 平行移動の量子化範囲
    std::uint64_t constRot   = 0;                               // rotCount == 0 のとき
    Vec3          constPos   {0,0,0};
    Vec3          constScale {1,1,1};
};
```

キーの中身は、**1 本の連続したバイト配列**にまとめて置きます。

```
data_ のレイアウト（ボーンごとに可変長）

  [回転]  uint16 time[n]      … 2n バイト
          uint8  value[6n]    … Smallest Three 48 bit × n

  [平行移動] uint16 time[n]   … 2n バイト
          uint16 qxyz[3n]     … 6n バイト
```

**なぜ 1 本の配列にまとめるのか。** 第 37 章で「ランタイム形式へ焼き込む」ときに同じ判断をしました。`std::vector` をボーンごとに持つと、ポインタを追いかけることになり、メモリがばらけます。1 本の連続バッファなら、**ファイルへの保存が `write(data_.data(), data_.size())` の 1 行**で済み、読み込みも 1 回のアロケーションで終わります。

**時刻と値を分けて並べている**のも意図的です。キー探索の間は時刻の配列だけを読みます。時刻が `uint16` で連続していれば、**1 本のキャッシュライン（64 バイト）に 32 個のキー時刻が乗ります**。値と交互に並べると 8 個しか乗りません。

**アラインメントの注意。** `reinterpret_cast<const std::uint16_t*>(data_.data() + offset)` を安全に行うには、`offset` が偶数でなければなりません。回転が `2n + 6n = 8n` バイト、平行移動が `2n + 6n = 8n` バイト。**すべてのオフセットが 8 の倍数になる**ので、この条件は自動的に満たされます。設計の副産物ですが、コメントに書いておく価値があります。

## 56.3　構築

```cpp
inline void CompressedClip::Build(const Clip& clip, float posTolerance, float rotTolerance){
    duration_ = clip.Duration();
    bones_.assign(clip.BoneCount(), CompressedBone{});
    data_.clear();

    auto toU16Time = [&](float t){
        const float u = (duration_ > 0.0f) ? std::fmin(1.0f, std::fmax(0.0f, t/duration_)) : 0.0f;
        return static_cast<std::uint16_t>(u * 65535.0f + 0.5f);
    };

    for (std::size_t b = 0; b < clip.BoneCount(); ++b) {
        const BoneTracks& src = clip.Bone(static_cast<BoneIndex>(b));
        CompressedBone& cb = bones_[b];

        cb.constScale = src.scale.IsEmpty() ? Vec3{1,1,1} : src.scale.Key(0).value;

        // ---- 回転 ----
        Track<Quat> rot = src.rotation;
        if (rot.IsEmpty()) {
            cb.constRot = PackQuat(QuatIdentity());
        } else if (IsConstantTrack(rot, rotTolerance)) {      // 第 54 章
            cb.constRot = PackQuat(rot.Key(0).value);
        } else {
            ReduceTrack(rot, rotTolerance);                   // 第 54 章
            cb.rotOffset = static_cast<std::uint32_t>(data_.size());
            cb.rotCount  = static_cast<std::uint16_t>(rot.KeyCount());

            data_.resize(data_.size() + rot.KeyCount()*2);
            auto* times = reinterpret_cast<std::uint16_t*>(data_.data() + cb.rotOffset);
            for (std::size_t k = 0; k < rot.KeyCount(); ++k) times[k] = toU16Time(rot.Key(k).time);

            const std::size_t valOff = data_.size();
            data_.resize(data_.size() + rot.KeyCount()*6);
            for (std::size_t k = 0; k < rot.KeyCount(); ++k)
                WriteU48(data_.data() + valOff + k*6, PackQuat(rot.Key(k).value));  // 第 55 章
        }

        // ---- 平行移動（同じ形）----
        /* ... */
    }
}
```

**`data_.resize()` のあとにポインタを取り直している**点に注意。`std::vector` の `resize` は再確保でポインタを無効にします。「resize → ポインタ取得 → 書き込み」の順を守り、**取ったポインタを次の resize をまたいで使わない**。これは C++ の基本ですが、可変長バッファを組み立てるコードでは事故が起きやすい場所です。

**スケールは定数しか扱いません。** 第 54 章で「60/60 が定数」と測ったので、可変スケールのために形式を複雑にする理由がありません。**必要になったら足せばよく、必要ないものを先に作らない。** ただし、定数でないスケールを渡されたら黙って最初の値で近似してしまうので、**構築時に警告を出す**べきです。

```cpp
if (!src.scale.IsEmpty() && !IsConstantTrack(src.scale, 1e-4f))
    Warn("bone {}: スケールが定数ではありません。最初の値で近似します", b);
```

**黙って壊す形式を作らない。** 第 17 章でウェイトを 4 本に切り詰めたときにも同じことを書きました。

## 56.4　サンプリング

```cpp
void CompressedClip::Sample(float time, Pose& out) const {
    const float t = (duration_ > 0.0f) ? std::fmin(std::fmax(time, 0.0f), duration_) : 0.0f;
    const float u = (duration_ > 0.0f) ? t/duration_ : 0.0f;
    const std::uint16_t qt = static_cast<std::uint16_t>(u * 65535.0f + 0.5f);   // ← 一度だけ

    for (std::size_t b = 0; b < bones_.size(); ++b) {
        const CompressedBone& cb = bones_[b];
        Transform& tr = out[static_cast<BoneIndex>(b)];
        tr.scale = cb.constScale;

        // ---- 回転 ----
        if (cb.rotCount == 0) {
            tr.rotation = UnpackQuat(cb.constRot);
        } else {
            const auto* times = reinterpret_cast<const std::uint16_t*>(data_.data()+cb.rotOffset);
            const std::uint8_t* vals = data_.data() + cb.rotOffset + cb.rotCount*2;

            const int i = FindIndex(times, cb.rotCount, qt);
            const Quat a = UnpackQuat(ReadU48(vals + i*6));
            if (i+1 >= cb.rotCount) {
                tr.rotation = a;
            } else {
                const Quat bq = UnpackQuat(ReadU48(vals + (i+1)*6));
                const float span = static_cast<float>(times[i+1] - times[i]);
                const float f = (span > 0.0f) ? (static_cast<float>(qt) - times[i]) / span : 0.0f;
                tr.rotation = Nlerp(a, bq, std::fmin(1.0f, std::fmax(0.0f, f)));
            }
        }
        // ---- 平行移動（同じ形）----
    }
}
```

**時刻を最初に 1 回だけ量子化する。** 60 ボーン × 2 トラック = 120 回の探索がありますが、`float → uint16` の変換は 1 回で済みます。以降の比較はすべて整数です。

**補間は「復元してから」行います。** 量子化された整数のまま補間して最後に復元する、という手もありますが、**Smallest Three は線形空間ではありません**（捨てた成分が違えばビット列の意味も違う）。復元してからでないと補間できません。平行移動なら整数のまま補間できますが、コードが 2 通りになるので揃えています。

探索は `uint16` の二分探索です。

```cpp
static int FindIndex(const std::uint16_t* times, std::uint16_t n, std::uint16_t t){
    if (n < 2) return 0;
    std::size_t lo = 0, hi = n - 1;
    while (hi - lo > 1) {
        const std::size_t mid = (lo + hi) / 2;
        (times[mid] <= t ? lo : hi) = mid;
    }
    return static_cast<int>(lo);
}
```

第 25 章の二分探索と同じ形です。**`lo` が常に「区間の始まり」を指す**不変条件を保ちます（第 25 章で `FindIndexLinear` がこれを破っていて、3 実装の一致テストが見つけてくれました）。

そして第 25 章のヒント版も用意します。

```cpp
static int FindIndexHint(const std::uint16_t* times, std::uint16_t n, std::uint16_t t, int& hint){
    if (n < 2) return 0;
    int i = std::min(std::max(hint, 0), static_cast<int>(n)-2);
    if (times[i] <= t) { while (i+1 <= static_cast<int>(n)-2 && times[i+1] <= t) ++i; }
    else               { while (i > 0 && times[i] > t) --i; }
    hint = i;
    return i;
}
```

## 56.5　単体テスト：どれだけ小さくなったか

```cpp
TEST_METHOD(CompressionRatio) {
    Skeleton s = MakeHumanoid(60);
    const Clip original = MakeWalkClip(s, 2.0f, 30);

    for (float tolDeg : {0.1f, 0.5f, 1.0f}) {
        CompressedClip cc;
        cc.Build(original, 1e-5f, tolDeg * kPi / 180.0f);
        const PoseError e = MeasureError(s, original,
            [&](float t, Pose& p){ cc.Sample(t, p); }, 600);
        Logger::WriteMessage(std::format(
            "許容 {:.1f} 度: {} B ({:.1f} KB, 元の {:.1f}%), 回転 {:.4f} 度, ワールド {:.6f} m\n",
            tolDeg, cc.ByteSize(), cc.ByteSize()/1024.0,
            100.0*cc.ByteSize()/RawBytes(original), e.maxRot*180/kPi, e.maxWorld).c_str());
    }
    CompressedClip cc; cc.Build(original, 1e-5f, 0.5f*kPi/180.0f);
    Assert::IsTrue(cc.ByteSize() * 10 < RawBytes(original));    // 10% 未満
}
```

| 許容 | サイズ | 元の | 回転誤差 | ワールド位置誤差 |
|---|---|---|---|---|
| 0.1° | `23,064` B（22.5 KB） | 12.1% | `0.0996°` | `0.002381` m |
| **0.5°** | **`14,976` B（14.6 KB）** | **7.9%** | `0.4989°` | `0.016484` m |
| 1.0° | `11,928` B（11.6 KB） | 6.3% | `0.9970°` | `0.028081` m |

**185.9 KB → 14.6 KB。12.7 倍。** ワールド位置の誤差は 16.5 mm。

### 量子化は誤差をほとんど増やしていない

第 54 章の表と並べます。

| 許容 0.5° | ワールド位置の誤差 |
|---|---|
| キー削減だけ（`float` のまま） | `0.016487` m |
| キー削減 + 量子化 | `0.016484` m |

**差は 3 マイクロメートル。しかも減っています**（誤差の合成なので、たまたま打ち消し合ったのでしょう）。

第 55 章で予測したとおりです。量子化の誤差は腕の長さで 70 µm、キー削減の誤差は 16.5 mm。**240 倍の開きがあるので、足しても見えません。**

> **圧縮の品質を語るとき、支配的な要因を特定する。** ここでは「量子化のビット数」をいくら議論しても無駄で、**動かせるのはキー削減の許容値だけ**です。

## 56.6　単体テスト：測り方をまた間違えた話

上の測定を最初に走らせたとき、ワールド誤差はこうなりました。

```
許容 0.1 度: 回転 0.0996 度 / ワールド 2.800064 m
許容 0.5 度: 回転 0.4989 度 / ワールド 2.800064 m
許容 1.0 度: 回転 0.9970 度 / ワールド 2.800064 m
```

**2.8 メートル。** しかも許容値を変えても**まったく同じ値**。

「まったく同じ」が手がかりです。誤差が許容値に依存しないなら、それは圧縮のせいではありません。そして **2.8 m という数字に見覚えがありました** ―― テスト用クリップのルートは 2 秒で `z` 方向に 2.8 m 進みます。**ルートモーションが丸ごと失われている**ように見えた。

原因は、圧縮でもルートモーションでもありませんでした。**比較のループです。**

```cpp
for (int i = 0; i <= steps; ++i) {
    const float t = ref.Duration() * i / steps;     // ← i == steps のとき t == duration
    ref.Sample(t, a);
    compressed.Sample(t, b);
    /* 比較 */
}
```

`ref` は `LoopMode::Loop` のクリップです。第 26 章の `AdjustTime` は、`t == duration` を **`0` に折り返します**。一方、`CompressedClip::Sample` は `[0, duration]` にクランプするだけ（`Once` 相当）。

**最後の 1 点だけ、片方が先頭のポーズ、片方が末尾のポーズを返していた。** 差はルートモーション 1 周ぶん、ちょうど 2.8 m。

```cpp
// 末尾ちょうどは Loop モードで 0 に折り返される（第 26 章）ので手前で止める
const float t = ref.Duration() * i / (steps + 1);
```

**第 26 章で自分が書いた警告を、自分で踏みました。** 第 VI 部でも同じことをやっています（glTF のテストで `clip.Sample(1.0f)` が 0 に折り返された）。

反省として、比較ヘルパー側に対策を入れておきます。

```cpp
template<typename SampleFn>
PoseError MeasureError(const Skeleton& s, const Clip& ref, SampleFn sample, int steps){
    // ループの折り返しを避けるため、末尾ちょうどはサンプルしない
    for (int i = 0; i <= steps; ++i) {
        const float t = ref.Duration() * i / (steps + 1);
        /* ... */
    }
}
```

> **同じ罠に 3 回はまったなら、それは「気をつける」で解決する問題ではない。** 道具の側で踏めなくする。第 26 章で `PlaybackStep` を作ったのと同じ発想です。

## 56.7　測定：サンプリングの速さ

本題です。**圧縮したデータを読むのは、遅いのか。**

```cpp
TEST_METHOD(SamplingSpeed) {
    /* 60 ボーン、2 秒、許容 0.5 度で圧縮 */
    bench("非圧縮 Sample",         [&](float t){ original.Sample(t, p); });
    bench("非圧縮 SampleWithHint", [&](float t){ original.SampleWithContext(t, ctx, p); });
    bench("圧縮 Sample",           [&](float t){ cc.Sample(t, p); });
    bench("圧縮 SampleWithHints",  [&](float t){ cc.SampleWithHints(t, hints, p); });
}
```

60 ボーン 1 体を 1 回サンプリングする時間です。

| | 時間 | 非圧縮比 |
|---|---|---|
| 非圧縮・二分探索 | `5.145` µs | 1.00× |
| 非圧縮・ヒント付き | `1.752` µs | 2.94× |
| **圧縮・二分探索** | **`2.518` µs** | **2.04×** |
| **圧縮・ヒント付き** | **`2.118` µs** | **2.43×** |

**圧縮したほうが 2 倍速い。**

`UnpackQuat` の平方根と割り算を払っているのに、なぜ速いのか。理由は 3 つです。

**① キーが 35% しかない。** 第 54 章で 3660 → 1288 に減っています。二分探索の段数が減り、読むデータそのものが減る。

**② データが 12.7 分の 1。** 60 ボーン分のキーが 14.6 KB なら、**L1 キャッシュ（32〜48 KB）に丸ごと乗ります**。非圧縮の 185.9 KB は L2 にすら収まりません。

**③ 時刻が `uint16`。** 探索中に触るキャッシュラインが半分になります。

**復元のコストより、メモリを触らないことの利得が大きい。** 第 13 章（ポインタツリー対配列）、第 20 章（AoS 対 SoA）、第 53 章（ギャザー対ブロードキャスト）と、この本で何度も出てきた構図です。

### ヒントの効きが小さい理由

面白いのは、**ヒントの効果が非圧縮では 2.94 倍なのに、圧縮では 1.19 倍しかない**ことです。

非圧縮では、二分探索がキャッシュミスを連発します（61 キー × 40 バイトのキーフレーム配列を、飛び飛びに 6 段たどる）。ヒントで線形に 1〜2 歩進むだけなら、ミスはほぼゼロ。だから劇的に効きます。

圧縮版では、そもそも時刻配列がキャッシュに乗っているので、**二分探索してもミスしません**。ヒントで減るのは命令数だけ ―― 1.19 倍。

> **最適化どうしは足し算にならない。** 片方が効くと、もう片方の効き目が消えることがあります。**両方入れたあとで測り直す。**

とはいえ、ヒントは入れておく価値があります。キー数の多いクリップ（削減が効かない高周波モーション）では、圧縮版でも二分探索の段数が増えるからです。

## 56.8　実務での使い分け

**すべてのクリップを同じ設定で圧縮しない。**

| クリップの種類 | 許容 | 理由 |
|---|---|---|
| 主人公の待機・歩行 | 厳しく（0.05〜0.1°） | 常に画面中央にいる。何百時間も見られる |
| 主人公の戦闘モーション | 中（0.2°） | 速いので粗が見えにくいが、当たり判定に効く |
| NPC・群衆 | 緩く（1〜2°） | 数が多い。メモリのほとんどはここ |
| カットシーン | **圧縮しない**、または最も厳しく | 顔のアップに耐える必要がある |

**「メモリのほとんどは、誰も注目していないデータ」** というのが実際のところで、そこを 6.3% にできるなら、主人公のクリップは非圧縮でも構わない、という判断もありえます。

**圧縮の設定はアセットのメタデータとして持つ。** 第 45 章のステートマシン、第 50 章の関節制限と同じ結論です ―― **コードに埋め込まない。ツールで編集できるようにする。**

## 56.9　第 54〜56 章で得たもの

3 章分の成果を、1 つの表にまとめます。

```
元のクリップ:  60 ボーン, 2.0 秒 @30Hz, 10,980 キー, 190,320 バイト（185.9 KB）

  ① 定数トラックの除去         → 68.7% 削減（スケール 60/60, 移動 59/60, 回転 12/60）
  ② キー削減（許容 0.5 度）    → 回転キー 3,660 → 1,288（35.2%）
  ③ 量子化（48 bit / 16 bit）  → キー 1 個 20 B → 8 B

  結果: 14,976 バイト（14.6 KB）= 元の 7.9%、12.7 倍の圧縮
  誤差: 局所の回転 0.4989 度、ワールド位置 0.016484 m
  速度: サンプリング 5.145 µs → 2.518 µs（2.04 倍速い）
```

**小さくなり、速くなり、誤差は 16.5 mm。** そして、その 16.5 mm の**ほぼ全部がキー削減由来**で、量子化の寄与は 3 マイクロメートルです。

## この章のまとめ

- 圧縮には「ロード時に展開する」と「**圧縮したまま読む**」がある。**実行時のメモリ帯域が問題なら後者しか意味がない**（第 53 章のボトルネック）。
- レイアウトは**1 本の連続バッファ**（ファイル入出力が 1 行、アロケーションが 1 回）。**時刻と値は分けて並べる**（探索中は時刻だけ読むので、`uint16` なら 1 キャッシュラインに 32 キー乗る）。
- キーが `2n + 6n = 8n` バイトなので、**すべてのオフセットが自動的に 8 の倍数**になり、`uint16` へのキャストが安全。
- `data_.resize()` はポインタを無効にする。**「resize → ポインタ取得 → 書き込み」の順**を守る。
- スケールは定数のみ対応。ただし**定数でない入力に警告を出す** ―― **黙って壊す形式を作らない。**
- 時刻の量子化は**サンプリングの最初に 1 回だけ**。以降の比較はすべて整数。
- **実測：185.9 KB → 14.6 KB（元の 7.9%、12.7 倍）**、ワールド位置誤差 `0.016484` m。
- **量子化の寄与は 3 マイクロメートル。** キー削減だけで `0.016487`、量子化を足して `0.016484`。**支配的な要因を特定する** ―― 動かせるのはキー削減の許容値だけ。
- **測り方をまた間違えた**：比較ループの末尾で `t == duration` をサンプルし、Loop モードの折り返しで `2.800064 m`（ルートモーション 1 周ぶん）の誤差が出た。**第 26 章で自分が書いた警告を、自分で 3 回目に踏んだ。** 対策は「気をつける」ではなく、**比較ヘルパー側で踏めなくする**こと。
- **圧縮したほうが 2 倍速い**（`5.145` → `2.518` µs）。理由は ① キーが 35%、② **14.6 KB は L1 に乗る**、③ 時刻が `uint16`。**復元のコストより、メモリを触らないことの利得が大きい。**
- **最適化どうしは足し算にならない。** ヒント付き探索は非圧縮で 2.94 倍効くが、圧縮版では 1.19 倍。片方が効くともう片方の効き目が消える。**両方入れたあとで測り直す。**
- 圧縮の設定は**クリップごとに変える**。メモリのほとんどは「誰も注目していないデータ」。設定は**アセットのメタデータとして持つ**（第 45・50 章と同じ結論）。

次章では、ここまでで軽くした処理を**複数のコアに分けます**。そして第 4 章で作った `ScopedDenormalsAreZero` が、なぜワーカースレッドごとに必要なのかを実測します ―― **24 倍の差**が出ます。
