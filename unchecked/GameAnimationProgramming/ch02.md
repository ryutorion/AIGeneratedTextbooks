# 第 2 章　ソリューションを作る

**この章で作るもの**：静的ライブラリ `AnimLib` と、それを検証するテストプロジェクト `AnimLib.Tests` からなるソリューション。テストエクスプローラーで緑のチェックが 2 つ並ぶところまで進めます。

---

## 2.1　なぜプロジェクトを 2 つに分けるのか

最初から少し面倒なことをします。1 つの実行ファイルに全部詰め込むほうが手軽なのに、静的ライブラリとテストの 2 プロジェクト構成にします。

理由は、**アニメーションのコードを「アプリケーションから切り離された状態」で書き続けるため**です。

`main()` を持つプロジェクトの中で書いていると、どうしても「とりあえずここでコンソールに出して確認」という誘惑に負けます。それ自体は悪くないのですが、そうやって書かれたコードは `std::cout` や、その場しのぎのグローバル変数と絡み合っていき、あとから切り出すのが難しくなります。

ライブラリ側に `main()` が存在しないという物理的な制約を最初に作っておくと、この誘惑は自然に消えます。ライブラリが外界と接する方法は「関数を呼ばれて値を返す」だけになり、それはそのまま**テストしやすい形**でもあります。

副次的な利点として、リンクエラーが早期に発見できます。ヘッダに書いた宣言に対応する定義を書き忘れたら、テストプロジェクトのリンク時に必ず落ちます。

---

## 2.2　ディレクトリ構成

先に、これから作るファイル配置を示します。

```
AnimBook/
├─ AnimBook.sln
├─ AnimBook.props              ← 両プロジェクト共通のコンパイル設定
├─ AnimLib/
│  ├─ AnimLib.vcxproj
│  ├─ include/
│  │  └─ anim/
│  │     └─ Version.h
│  └─ src/
│     └─ Version.cpp
└─ AnimLib.Tests/
   ├─ AnimLib.Tests.vcxproj
   └─ SetupTests.cpp
```

`include/anim/` という 2 段構えにしているのは、インクルードを常に

```cpp
#include "anim/Vec3.h"
```

の形で書くためです。プレフィックス付きで書いておくと、将来ほかのコードベースに `AnimLib` を持ち込んだとき、`Vec3.h` という名前がありふれていて衝突する、という事故を防げます。

---

## 2.3　ソリューションと静的ライブラリを作る

Visual Studio 2026 を起動し、**［新しいプロジェクトの作成］**を選びます。

1. テンプレート一覧から **［スタティック ライブラリ (C++)］** を選択（検索ボックスに「スタティック」と入れると早いです）。
2. プロジェクト名に `AnimLib`、場所は任意、**ソリューション名を `AnimBook`** に変更します。
3. **［ソリューションとプロジェクトを同じディレクトリに配置する］はチェックしない**でください。2.2 の構成にするためです。
4. ［作成］。

生成された `pch.h` `pch.cpp` `framework.h` `AnimLib.cpp` は、この本では使いません。ソリューションエクスプローラーですべて選択し、右クリック → **［削除］**（［プロジェクトから除外］ではなくファイルごと削除して構いません）。

プリコンパイル済みヘッダも切ります。`AnimLib` を右クリック → **［プロパティ］** → 構成を **［すべての構成］**、プラットフォームを **［すべてのプラットフォーム］** にしてから、**［C/C++］→［プリコンパイル済みヘッダー］→［プリコンパイル済みヘッダー］** を **［プリコンパイル済みヘッダーを使用しない］** に変更します。

> **なぜ PCH を使わないのか**
> PCH はビルドを速くするための仕組みですが、「どのヘッダが何に依存しているか」を曖昧にします。本書のライブラリは最終的にも数十ファイル規模で、PCH なしでもビルドは数秒です。依存関係が明示される利点のほうが上回ります。

最後に、プラットフォームを **x64** のみにします。ソリューション構成のドロップダウン → **［構成マネージャー］** → アクティブソリューションプラットフォームの **［編集］** から `x86`（`Win32`）を削除してください。x86 を残しておくと、あとで「テストが動かないと思ったら x86 構成でビルドしていた」という事故に遭います。

## 2.4　共通のコンパイル設定をプロパティシートにまとめる

コンパイルオプションを 2 つのプロジェクトに別々に設定すると、片方だけ設定し忘れて奇妙な不一致に悩むことになります。**プロパティシート**（`.props` ファイル）に一度書いて、両方から読み込む形にします。

`AnimBook.sln` と同じ階層に、テキストエディタで `AnimBook.props` を作り、次の内容を書きます。

```xml
<?xml version="1.0" encoding="utf-8"?>
<Project ToolsVersion="4.0"
         xmlns="http://schemas.microsoft.com/developer/msbuild/2003">
  <ItemDefinitionGroup>
    <ClCompile>
      <!-- C++23 -->
      <LanguageStandard>stdcpplatest</LanguageStandard>
      <!-- 警告は最大限、そしてエラー扱い -->
      <WarningLevel>Level4</WarningLevel>
      <TreatWarningAsError>true</TreatWarningAsError>
      <!-- 標準準拠モード -->
      <ConformanceMode>true</ConformanceMode>
      <!-- 外部ヘッダ（<> で囲むもの）の警告は抑制する -->
      <ExternalWarningLevel>TurnOffAllWarnings</ExternalWarningLevel>
      <TreatAngleIncludeAsExternal>true</TreatAngleIncludeAsExternal>
      <!-- 並列ビルド -->
      <MultiProcessorCompilation>true</MultiProcessorCompilation>
      <!-- AnimLib のヘッダをどちらのプロジェクトからも見えるように -->
      <AdditionalIncludeDirectories>
        $(SolutionDir)AnimLib\include;%(AdditionalIncludeDirectories)
      </AdditionalIncludeDirectories>
    </ClCompile>
  </ItemDefinitionGroup>
</Project>
```

各設定の意味を補足します。

**`stdcpplatest`（`/std:c++latest`）**
C++23 の機能を有効にします。Visual Studio のバージョンによっては［C++ 言語標準］のドロップダウンに「ISO C++23 標準」が独立して現れます。その場合はそちらを選んでも構いません。本書は `std::span`、`std::format`、`std::expected`、`if consteval`、`std::mdspan` などを使います。

**`Level4` + `TreatWarningAsError`（`/W4 /WX`）**
警告をエラーにするのは厳しく感じますが、数値計算のコードでは特に効果があります。`float` と `double` の暗黙変換（C4244）、符号付き／符号なしの比較（C4018）、`size_t` から `int` への切り詰め（C4267）——これらはアニメーションのコードで実際にバグになる警告です。最初から潰しておくほうが安上がりです。

**`ConformanceMode`（`/permissive-`）**
テンプレートの二段階名前検索など、MSVC 独自の緩さを切ります。標準準拠のコードを書くための保険です。

**`ExternalWarningLevel` + `TreatAngleIncludeAsExternal`（`/external:W0 /external:anglebrackets`）**
`/W4 /WX` をそのまま適用すると、`<windows.h>` や標準ライブラリのヘッダから出る警告でビルドが止まることがあります。`<>` で囲んだインクルードを「外部ヘッダ」とみなして警告を切ることで、自分のコードだけを厳しく扱えます。これが、自分のヘッダを `""` で、標準ヘッダを `<>` でインクルードする習慣が実利を持つ場面です。

### プロパティシートを適用する

**［表示］→［その他のウィンドウ］→［プロパティ マネージャー］** を開きます。`AnimLib` → `Debug | x64` を右クリック → **［既存のプロパティ シートの追加］** → `AnimBook.props` を選択。同じことを `Release | x64` にも行います。

> **ヒント**：`Debug | x64` に追加したあと、追加された `AnimBook` ノードを `Release | x64` へドラッグしてもコピーできます。

設定が効いているか確認しましょう。`AnimLib` のプロパティ →［C/C++］→［コマンド ライン］に `/std:c++latest /W4 /WX /permissive-` が並んでいれば成功です。プロパティシート由来の設定は、プロジェクトのプロパティ画面では**太字にならず**に表示されます（太字はそのプロジェクト固有の上書きを意味します）。

## 2.5　モジュールを使わない、そのかわりの規約

本書は C++ モジュールを使いません。ビルド構成の問題で読者が詰まる余地を減らすためです。そのかわり、ヘッダの書き方に 4 つの規約を設けます。

**規約 1：インクルードガードは `#pragma once`**
MSVC を含む主要なコンパイラすべてが対応しています。手書きのマクロガードは名前の衝突事故が起きます。

**規約 2：ヘッダは自己完結する**
どのヘッダも、それ単体で `#include` してコンパイルが通らなければなりません。「`Vec3.h` の前に `Mat4.h` を include しないとエラーになる」ようなヘッダは書きません。

**規約 3：`""` は自分のヘッダ、`<>` は標準・システムヘッダ**
2.4 の外部警告設定がこの規約に依存しています。

**規約 4：名前空間は `anim`**
すべての型と関数を `namespace anim { ... }` に入れます。ヘッダで `using namespace` は書きません。

インクルードの順序も決めておきます。上から順に、

1. （`.cpp` の場合）対応するヘッダ
2. 自分のプロジェクトのヘッダ
3. 標準ヘッダ

自分のヘッダを先頭に置くのは、規約 2 が守れているかを自動的に検査するためです。`Vec3.cpp` の 1 行目が `#include "anim/Vec3.h"` なら、`Vec3.h` が何かに依存し忘れていればそこで落ちます。

## 2.6　最初のコードを書く

リンクが正しく通っているかを確認するためのコードを書きます。**あえてヘッダに全部書かず、宣言と定義を分けます。** ヘッダだけで完結させてしまうと、ライブラリが本当にリンクされているかを確かめられないからです。

ソリューションエクスプローラーで `AnimLib` を右クリック →［追加］→［新しいフィルター］で `include` と `src` を作り、その中にファイルを追加していきます。フィルターは表示上のグループでしかないので、**ファイルの実際の保存先は自分で `AnimLib\include\anim\` などに指定してください**（新規項目の追加ダイアログで場所を編集できます）。

**`AnimLib/include/anim/Version.h`**

```cpp
#pragma once

namespace anim {

// ライブラリのバージョン。第 37 章のシリアライズで、
// 焼き込み済みデータの互換性判定に使う。
inline constexpr int kVersionMajor = 0;
inline constexpr int kVersionMinor = 1;

// 意図的に .cpp 側で定義する。
// この関数が呼べる = AnimLib.lib が正しくリンクされている。
[[nodiscard]] int VersionNumber() noexcept;

}  // namespace anim
```

**`AnimLib/src/Version.cpp`**

```cpp
#include "anim/Version.h"

namespace anim {

int VersionNumber() noexcept {
    return kVersionMajor * 100 + kVersionMinor;
}

}  // namespace anim
```

`Ctrl+Shift+B` でビルドします。`AnimLib.lib` が生成されれば成功です。

## 2.7　テストプロジェクトを追加する

ソリューションを右クリック →［追加］→［新しいプロジェクト］。テンプレートから **［ネイティブ単体テスト プロジェクト］**（Native Unit Test Project）を選び、名前を `AnimLib.Tests` にします。

このテンプレートが生成するのは、実は**実行ファイルではなく DLL** です。テストの実体は DLL にエクスポートされたクラスで、Visual Studio のテストアダプターがそれを読み込んで実行します。この事実は、あとでリンクエラーの原因を考えるときに効いてきます。

生成された `pch.h` `pch.cpp` は削除し、2.3 と同じ手順でプリコンパイル済みヘッダを無効化します。`AnimLib.Tests.cpp` は残しますが、中身は書き換えるので名前を `SetupTests.cpp` にリネームしておきましょう。

続いて 2.4 と同じ手順で、`AnimLib.Tests` にも `AnimBook.props` を適用します。**両方のプロジェクトが同じ設定でコンパイルされることが重要です。**

### ライブラリへの参照を追加する

`AnimLib.Tests` を右クリック → **［追加］→［プロジェクト参照］** → `AnimLib` にチェック → ［OK］。

これだけで、`AnimLib.lib` のリンクと、`AnimLib` のビルド依存関係の両方が設定されます。［リンカー］→［入力］に手で `AnimLib.lib` と書く必要はありません。

## 2.8　最初のテストを書く

`AnimLib.Tests/SetupTests.cpp` の中身をすべて消して、次のように書きます。

```cpp
#include "CppUnitTest.h"

#include "anim/Version.h"

using namespace Microsoft::VisualStudio::CppUnitTestFramework;

namespace AnimLibTests {

TEST_CLASS(SetupTests) {
public:

    // ① テストの仕組みそのものが動いているか
    TEST_METHOD(FrameworkIsAlive) {
        Assert::AreEqual(2, 1 + 1);
    }

    // ② AnimLib.lib がリンクされているか
    //    ヘッダの inline constexpr ではなく、.cpp 側で定義した関数を呼ぶ
    TEST_METHOD(LibraryIsLinked) {
        Assert::AreEqual(1, anim::VersionNumber());
    }
};

}  // namespace AnimLibTests
```

構文を確認しておきます。

- **`TEST_CLASS(名前)`** はテストをまとめる単位です。展開されると `class` 定義になるので、**末尾のセミコロンが必要**です。忘れると意味不明なエラーが出ます。
- **`TEST_METHOD(名前)`** が 1 つのテストです。展開後は `public` なメンバ関数になる必要があるため、`TEST_CLASS` の直後に `public:` を書きます（テンプレートが `class` を使うため、既定は `private` です）。
- **`Assert::AreEqual(期待値, 実測値)`** の引数順は「期待値が先」です。逆にしても通りますが、失敗メッセージの「Expected / Actual」が入れ替わって混乱します。

`Assert::AreEqual(2, 1 + 1)` は一見無意味ですが、意味があります。テストが失敗したとき「自分のコードが悪いのか、テスト環境が壊れているのか」を切り分ける最下層の基準になります。以降、環境がおかしいと感じたらまずこのテストを見てください。

## 2.9　テストを実行する

**［テスト］→［テスト エクスプローラー］** を開きます（`Ctrl+E, T`）。ソリューションをビルドすると、`AnimLibTests::SetupTests` の下に 2 つのテストが現れます。

`Ctrl+R, A` で全テストを実行。緑のチェックが 2 つ並べば、この章は完了です。

覚えておくと便利なショートカットを挙げておきます。

| 操作 | ショートカット |
| --- | --- |
| 全テストを実行 | `Ctrl+R, A` |
| 失敗したテストだけ再実行 | `Ctrl+R, F` |
| カーソル位置のテストを実行 | `Ctrl+R, T` |
| カーソル位置のテストをデバッグ実行 | `Ctrl+R, Ctrl+T` |

最後の**デバッグ実行**が特に重要です。テストの中にブレークポイントを置いて `Ctrl+R, Ctrl+T` を押せば、そこで止まります。本書ではこれから、行列の中身やクォータニオンの成分をウォッチウィンドウで睨む場面が何度もあります。描画しない代わりに、デバッガが目の役割を果たします。

## 2.10　つまずきやすいところ

**テストエクスプローラーに何も表示されない**
① ソリューション構成が `Debug | x64` になっているか。② ソリューション全体がビルドされているか（テストプロジェクトだけビルドしても、一覧の更新には全体ビルドが要ることがあります）。③［ビルド］→［構成マネージャー］で `AnimLib.Tests` の［ビルド］にチェックが入っているか。

**`LNK2038: '_ITERATOR_DEBUG_LEVEL' の不一致が検出されました`**
`AnimLib` を Release で、`AnimLib.Tests` を Debug でビルドしています。両方の構成を揃えてください。プロジェクト参照を設定していれば通常は起きませんが、片方だけ手動ビルドしたときに発生します。

**`LNK2038: 'RuntimeLibrary' の不一致`**
［C/C++］→［コード生成］→［ランタイム ライブラリ］が両プロジェクトで違います。Debug なら両方 `/MDd`（マルチスレッド デバッグ DLL）、Release なら両方 `/MD` に揃えます。テストプロジェクトのテンプレートは DLL 版を既定にするので、ライブラリ側を合わせるのが簡単です。

**`error C2065: 'TEST_CLASS': 識別子が見つかりません`**
`#include "CppUnitTest.h"` を書き忘れているか、`using namespace Microsoft::VisualStudio::CppUnitTestFramework;` がありません。

**`fatal error C1083: 'anim/Version.h' を開けません`**
`AdditionalIncludeDirectories` が効いていません。プロパティマネージャーで `AnimBook.props` が `AnimLib.Tests` にも追加されているか確認してください。また `$(SolutionDir)` は末尾に `\` を含むので、`$(SolutionDir)\AnimLib\include` と書くと `\\` になって解決に失敗することがあります。

**`error C2220: 警告をエラーとして扱っています`**
`/WX` が仕事をしています。警告そのものを読んで直してください。どうしても抑制が必要な箇所だけ、`#pragma warning(push)` / `disable` / `pop` で範囲を限定します。ファイル全体やプロジェクト全体で切るのは避けます。

## この章のまとめ

- **静的ライブラリ + テスト DLL** の 2 プロジェクト構成にした。`main()` がないという制約が、テストしやすい設計を強制する。
- コンパイル設定は **`AnimBook.props`** に集約し、両プロジェクトから読み込んだ。設定の不一致は後々の不可解なバグの温床になる。
- **`/std:c++latest /W4 /WX /permissive-`** を採用。警告をエラーにするのは、数値コードでは特に割に合う。
- ヘッダ規約を 4 つ決めた（`#pragma once` / 自己完結 / `""` と `<>` の使い分け / 名前空間 `anim`）。
- `Assert::AreEqual(2, 1 + 1)` は無意味に見えて、環境が壊れていないことを示す最下層の基準になる。

次章では、この `Assert` が**浮動小数点にはそのまま使えない**という問題に取り組み、本書を最後まで支えるテストヘルパーを作ります。
