# 第 13 章　ボーンと階層

**この章で作るもの**：`Skeleton`。ボーンの親子関係を親インデックス配列で表し、不正な階層を検出する仕組みまで作ります。第 II 部で作った道具を、初めて「アニメーションらしいもの」に組み上げる章です。

---

## 13.1　スケルトンは「形」であって「姿勢」ではない

最初に、混同しやすい 2 つを分離しておきます。

**スケルトン（skeleton）** は、ボーンの集合と親子関係、そして各ボーンの名前です。**これは時間とともに変化しません。** モデルをロードした時点で決まり、以後は読み取り専用です。

**ポーズ（pose）** は、ある瞬間の全ボーンの姿勢です。毎フレーム変わります。次章の主題です。

この分離が効くのは、**1 つのスケルトンを何体ものキャラクターで共有できる**からです。同じモデルを 1000 体表示するとき、スケルトンは 1 つ、ポーズは 1000 個。第 IX 部でこの構造がそのまま最適化の土台になります。

本書では、さらに `Skeleton` に**レストポーズ**（各ボーンの既定の姿勢）も持たせます。これもモデル固有で時間変化しないからです。

```
Skeleton（1 つ、読み取り専用）        Pose（キャラクターごと、毎フレーム更新）
┌────────────────────┐              ┌──────────────────┐
│ parents  : 親インデックス │              │ locals : Transform 配列 │
│ names    : ボーン名      │              └──────────────────┘
│ restLocal: 既定の姿勢    │
└────────────────────┘
```

## 13.2　なぜポインタのツリーにしないのか

ボーンの階層は木構造です。素直に書けば、こうなるでしょう。

```cpp
// 本書では採用しない設計
struct Bone {
    std::string name;
    Transform local;
    Bone* parent;
    std::vector<std::unique_ptr<Bone>> children;
};
```

本書はこれを採用せず、**配列 + 親インデックス**にします。

```cpp
std::vector<BoneIndex> parents;   // parents[i] = ボーン i の親のインデックス
```

理由を並べる前に、**よく言われる理由のうち 1 つは、実は成り立たないこと**を先に書いておきます。

### 「キャッシュに優しいから」は、この規模では成り立たない

配列レイアウトの利点として真っ先に挙げられるのは「メモリが連続しているのでキャッシュに乗る」です。測ってみました。100 ボーンの人型スケルトン（背骨 + 四肢、分岐あり）でグローバルポーズを計算し、20 万回の平均を取ります。

| 実装 | 1 ポーズあたり |
| --- | --- |
| 配列 + 親インデックス（1 パス） | 1.87 µs |
| ポインタツリー（連続確保） | 1.92 µs |
| ポインタツリー（**意図的に断片化**して確保） | 1.90 µs |

**差はありません。** 断片化させても変わりませんでした。

理由は単純で、100 ボーンぶんの `Transform` は 4 KB しかなく、断片化させたところで L1/L2 キャッシュに収まってしまうからです。そしてこの処理の時間は、メモリアクセスではなく `Combine`（クォータニオンの積 16 乗算 + 回転の適用）の**算術に支配されています**。

キャッシュの議論が本当に効いてくるのは、**1000 体ぶんのポーズをまとめて処理するとき**です。そこでは 4 MB を舐めることになり、レイアウトが決定的になります。それは第 52 章の話です。

**測らずに「キャッシュに優しいから」と言わないこと。** 本書は測ってから言います。

### 実際の理由 4 つ

では、なぜ配列にするのか。

**① そのまま保存・読み込みできる。** 親インデックス配列は `memcpy` でファイルに書けます。ポインタツリーはシリアライズのたびにポインタをインデックスに直し、ロード時に戻す（ポインタフィックスアップ）必要があります。第 37 章でランタイム形式に焼き込むとき、この差がそのまま実装量になります。

**② インデックスが安定した識別子になる。** 「ボーン 17」は、スケルトン、ポーズ、逆バインド行列、スキンウェイト、ボーンマスク、IK チェーンのすべてで同じボーンを指します。ポインタでは、コピーしたスケルトンとの対応が取れません。頂点データが持つのも、当然インデックスです（第 17 章）。

**③ アロケーションが起きない。** ポーズを 1 つ作るのに `vector` を 1 本確保するだけ。ノードを 100 個 `new` する必要はありません。第 57 章でワーカースレッドからポーズを作るとき、これが効きます。

**④ ループが素直に書ける。** 次章で見ますが、トポロジカル順序さえ保証すれば、階層の解決は**再帰なしの単純な前方ループ 1 本**になります。

つまり、選ぶ理由は速度ではなく**構造の単純さ**です。そしてそれは、第 52 章で速度の理由に変わります。

## 13.3　インデックスの型を決める

```cpp
// AnimLib/include/anim/Skeleton.h
#pragma once

#include "anim/Transform.h"

#include <cstdint>
#include <span>
#include <string>
#include <string_view>
#include <vector>

namespace anim {

// ボーンを指すインデックス。
// 人型で 50〜150 本、多いモデルでも数百本なので 16 ビットで足りる。
// 頂点データに 4 本ぶん埋め込む（第 17 章）ので、小さいことに意味がある。
using BoneIndex = std::uint16_t;

inline constexpr BoneIndex kInvalidBone = 0xFFFFu;
inline constexpr BoneIndex kNoParent    = kInvalidBone;   // ルートの親

}  // namespace anim
```

`std::uint16_t` を選んだ理由は、第 17 章の頂点フォーマットです。頂点 1 つがボーンインデックスを 4 本持つので、`uint32_t` なら 16 バイト、`uint16_t` なら 8 バイト。10 万頂点で 800 KB の差になります。glTF も `JOINTS_0` を `unsigned byte` か `unsigned short` で格納すると定めています。

`kNoParent` を `kInvalidBone` と同じ値にしているのは、「範囲外のインデックス」と「親がいない」を同じ検査で弾けるようにするためです。`0` を「親なし」にすると、ボーン 0 を親に持つボーンと区別できなくなります（実際、ルートはボーン 0 であることが多いので、これは現実の問題です）。

## 13.4　トポロジカル順序という約束

配列にするだけでは足りません。**もう 1 つ、決定的な約束を導入します。**

> **不変条件**：すべての `i` について、`parents[i] < i` または `parents[i] == kNoParent`。
> つまり、**親は必ず自分より前のインデックスにいる**。

この一行が、この先の章のコードを劇的に簡単にします。

**次章のグローバルポーズ計算が 1 パスで終わります。** インデックス順に前から処理すれば、自分の番が来たとき親の結果は必ず計算済みです。訪問済みフラグも、再帰も、スタックも要りません。

**ボーンマスクの階層への伝播（第 41 章）も 1 パス**です。親のマスク値を子に伝えるだけ。

**逆向きのループで、末端から根元への処理**もできます。CCD IK（第 48 章）がこれです。

この約束を「守られていることを祈る」のではなく、**構造的に守らせます**。次節のビルダーがそれを行います。

## 13.5　`Skeleton`

```cpp
namespace anim {

class Skeleton {
public:
    Skeleton() = default;

    [[nodiscard]] std::size_t BoneCount() const noexcept { return parents_.size(); }
    [[nodiscard]] bool IsEmpty() const noexcept { return parents_.empty(); }

    [[nodiscard]] BoneIndex ParentOf(BoneIndex i) const { return parents_[i]; }
    [[nodiscard]] bool IsRoot(BoneIndex i) const { return parents_[i] == kNoParent; }
    [[nodiscard]] std::string_view NameOf(BoneIndex i) const { return names_[i]; }
    [[nodiscard]] const Transform& RestLocal(BoneIndex i) const { return restLocal_[i]; }

    // ループで使うためのビュー
    [[nodiscard]] std::span<const BoneIndex> Parents() const noexcept { return parents_; }
    [[nodiscard]] std::span<const Transform> RestLocals() const noexcept { return restLocal_; }

    // 見つからなければ kInvalidBone。
    // ロード時にしか呼ばない前提の線形探索（13.7 節）。
    [[nodiscard]] BoneIndex FindBone(std::string_view name) const;

private:
    friend class SkeletonBuilder;

    std::vector<BoneIndex> parents_;
    std::vector<std::string> names_;
    std::vector<Transform> restLocal_;
};

}  // namespace anim
```

**3 つの `vector` に分けている**ことに注目してください。`struct Bone { BoneIndex parent; std::string name; Transform rest; }` の配列にすることもできますが、そうしません。

理由は、**使われ方が違うから**です。`parents_` は毎フレーム全部読まれます。`restLocal_` はロード時とリセット時だけ。`names_` に至っては、ランタイムでは一度も読まれません（第 37 章で焼き込んだあとは、名前解決は済んでいます）。

これらを 1 つの構造体にまとめると、毎フレーム舐める `parents_`（200 バイト）のあいだに、使わない `std::string`（32 バイト × ボーン数）が挟まります。第 52 章で SoA に再設計する話をしますが、**その一部はここで先取りしています。**

`friend class SkeletonBuilder` は、**`Skeleton` を外から組み立てられなくするため**です。次節の理由によります。

## 13.6　ビルダーで不変条件を強制する

トポロジカル順序を守らせるいちばん確実な方法は、**そもそも破れないようにすること**です。

```cpp
namespace anim {

// Skeleton を構築する唯一の手段。
// 「親は既に追加済みでなければならない」という制約により、
// トポロジカル順序が構造的に保証される。
class SkeletonBuilder {
public:
    // ルートを追加する。
    BoneIndex AddRoot(std::string name, const Transform& restLocal = TransformIdentity());

    // 既存のボーンの子として追加する。
    // parent は既に追加済みでなければならない（そうでなければ kInvalidBone を返す）。
    BoneIndex AddBone(std::string name, BoneIndex parent,
                      const Transform& restLocal = TransformIdentity());

    // 名前で親を指定する版（テストコードで読みやすい）
    BoneIndex AddBone(std::string name, std::string_view parentName,
                      const Transform& restLocal = TransformIdentity());

    [[nodiscard]] Skeleton Build();

private:
    Skeleton skeleton_;
};

}  // namespace anim
```

実装は素直です。

```cpp
BoneIndex SkeletonBuilder::AddRoot(std::string name, const Transform& restLocal) {
    return AddInternal(std::move(name), kNoParent, restLocal);
}

BoneIndex SkeletonBuilder::AddBone(std::string name, BoneIndex parent,
                                   const Transform& restLocal) {
    // ここが不変条件の門番。
    // parent は「既に追加済み」= 自分より小さいインデックス、でなければならない。
    if (parent >= skeleton_.parents_.size()) {
        ANIM_ASSERT(false && "親がまだ追加されていない");
        return kInvalidBone;
    }
    return AddInternal(std::move(name), parent, restLocal);
}

BoneIndex SkeletonBuilder::AddBone(std::string name, std::string_view parentName,
                                   const Transform& restLocal) {
    const BoneIndex parent = skeleton_.FindBone(parentName);
    if (parent == kInvalidBone) {
        ANIM_ASSERT(false && "親の名前が見つからない");
        return kInvalidBone;
    }
    return AddBone(std::move(name), parent, restLocal);
}
```

`AddBone` は「親が既に配列にある」ことしか許しません。**親のインデックスは必ず自分より小さくなります。** これでトポロジカル順序が構造的に保証されました。

> **glTF はこの順序になっていない**
> glTF のノード配列は、親子関係と無関係な順序で並んでいることがあります。第 34 章では、読み込んだノードをトポロジカルソートしてから `SkeletonBuilder` に流し込みます。**順序の保証は、外部データとの境界で一度だけ行う。** 第 6 章で行列規約について述べたのと同じ方針です。

## 13.7　名前からインデックスを引く

```cpp
BoneIndex Skeleton::FindBone(std::string_view name) const {
    for (std::size_t i = 0; i < names_.size(); ++i) {
        if (names_[i] == name) {
            return static_cast<BoneIndex>(i);
        }
    }
    return kInvalidBone;
}
```

線形探索です。**ハッシュマップを使いません。**

100 ボーンの線形探索は、文字列比較 100 回。マイクロ秒のオーダーです。そしてこの関数は、**毎フレーム呼ばれてはいけません**。

名前でボーンを引きたくなる場面 ―― IK チェーンの設定、ボーンマスクの定義、ソケットの取り付け ―― は、すべて**セットアップ時**です。ランタイムではインデックスを保持しておきます。

```cpp
// 良い：セットアップ時に一度だけ引く
struct FootIkSetup {
    BoneIndex hip;
    BoneIndex knee;
    BoneIndex ankle;
};

FootIkSetup MakeLeftFootIk(const Skeleton& s) {
    return { s.FindBone("LeftUpLeg"),
             s.FindBone("LeftLeg"),
             s.FindBone("LeftFoot") };
}

// 悪い：毎フレーム名前で引く
void UpdateBad(const Skeleton& s, Pose& pose) {
    pose[s.FindBone("LeftFoot")] = /* ... */;   // ← 文字列比較が毎フレーム走る
}
```

ハッシュマップを置くと、後者が「そこそこ速い」ので放置されます。**線形探索のままにしておくことで、プロファイラに現れやすくなり、設計の誤りに気づけます。** 意図的に最適化しない、という判断です。

## 13.8　検証する

ビルダーを通せば不変条件は守られますが、**ファイルから読み込んだデータ**や、**テストで意図的に壊したデータ**には効きません。検証関数を用意します。

```cpp
namespace anim {

enum class SkeletonError {
    None,
    TooManyBones,        // BoneIndex で表せる数を超えた
    ParentOutOfRange,    // 親インデックスが範囲外
    ParentNotBefore,     // 親が自分より後ろにいる（トポロジカル順序違反）
    SelfParent,          // 自分が自分の親
    NoRoot,              // ルートが 1 つもない（= 循環している）
    DuplicateName        // 名前が重複している
};

[[nodiscard]] SkeletonError Validate(const Skeleton& s);
[[nodiscard]] std::string_view ToString(SkeletonError e);

}  // namespace anim
```

```cpp
SkeletonError Validate(const Skeleton& s) {
    const std::size_t n = s.BoneCount();
    if (n >= kInvalidBone) {
        return SkeletonError::TooManyBones;
    }

    bool anyRoot = false;
    for (std::size_t i = 0; i < n; ++i) {
        const BoneIndex parent = s.ParentOf(static_cast<BoneIndex>(i));
        if (parent == kNoParent) {
            anyRoot = true;
            continue;
        }
        if (parent == i)  { return SkeletonError::SelfParent; }
        if (parent >= n)  { return SkeletonError::ParentOutOfRange; }
        if (parent > i)   { return SkeletonError::ParentNotBefore; }
    }
    if (n > 0 && !anyRoot) {
        return SkeletonError::NoRoot;
    }

    // 名前の重複（O(n²) だがロード時にしか呼ばない）
    for (std::size_t i = 0; i < n; ++i) {
        for (std::size_t j = i + 1; j < n; ++j) {
            if (s.NameOf(static_cast<BoneIndex>(i)) == s.NameOf(static_cast<BoneIndex>(j))) {
                return SkeletonError::DuplicateName;
            }
        }
    }
    return SkeletonError::None;
}
```

### 循環参照はどこへ消えたのか

木構造の検証といえば「循環参照の検出」が定番で、通常は訪問済みフラグを持って深さ優先探索します。**この実装にはそれがありません。**

必要ないからです。**トポロジカル順序（`parent < i`）が成り立っていれば、循環は原理的に存在できません。** ボーン `i` の親は必ず `i` より小さく、その親はさらに小さく…と単調に減っていくので、有限回で `kNoParent` に到達します。

`NoRoot` の検査だけ残しているのは、`ParentNotBefore` をすり抜けるケース ―― たとえば全ボーンが「自分より前の誰か」を親に持ちつつルートがない、という状況が理論上ありうるか確認するためです。実際には `parents[0]` は必ず `kNoParent` になるので到達しませんが、**検証関数は「ありえない」に頼らないほうが安全**です。

**1 つの不変条件を強く保証すると、それに依存する検査群がまるごと不要になる。** これは設計上の大きな見返りです。

## 13.9　テストを書く

`AnimLib.Tests/SkeletonTests.cpp`：

```cpp
#include "CppUnitTest.h"

#include "TestSupport/MathAssert.h"
#include "TestSupport/Tolerance.h"

#include "anim/Skeleton.h"

using namespace Microsoft::VisualStudio::CppUnitTestFramework;
using namespace anim;

namespace AnimLibTests {

// 本書を通じて使うテスト用スケルトン。
// root → shoulder → elbow → hand の 4 ボーン。単位はメートル。
//
//   root     : 原点
//   shoulder : root から (0, 1.5, 0)     肩の高さ
//   elbow    : shoulder から (0.3, 0, 0)  上腕 30 cm
//   hand     : elbow から (0.25, 0, 0)    前腕 25 cm
//
// レストポーズでは腕を +X 方向にまっすぐ伸ばしている。
Skeleton MakeArmSkeleton() {
    SkeletonBuilder b;
    b.AddRoot("root");
    b.AddBone("shoulder", "root",     Transform{{0.0f,  1.5f, 0.0f}, QuatIdentity(), {1, 1, 1}});
    b.AddBone("elbow",    "shoulder", Transform{{0.3f,  0.0f, 0.0f}, QuatIdentity(), {1, 1, 1}});
    b.AddBone("hand",     "elbow",    Transform{{0.25f, 0.0f, 0.0f}, QuatIdentity(), {1, 1, 1}});
    return b.Build();
}

TEST_CLASS(SkeletonTests) {
public:

    TEST_METHOD(BuilderProducesExpectedStructure) {
        const Skeleton s = MakeArmSkeleton();
        Assert::AreEqual(std::size_t{4}, s.BoneCount());
        Assert::IsTrue(s.IsRoot(0));
        Assert::AreEqual<int>(0, s.ParentOf(1));
        Assert::AreEqual<int>(1, s.ParentOf(2));
        Assert::AreEqual<int>(2, s.ParentOf(3));
    }

    TEST_METHOD(BuilderGuaranteesTopologicalOrder) {
        const Skeleton s = MakeArmSkeleton();
        for (BoneIndex i = 0; i < s.BoneCount(); ++i) {
            const BoneIndex p = s.ParentOf(i);
            Assert::IsTrue(p == kNoParent || p < i);
        }
        Assert::IsTrue(Validate(s) == SkeletonError::None);
    }

    TEST_METHOD(FindBoneWorks) {
        const Skeleton s = MakeArmSkeleton();
        Assert::AreEqual<int>(2, s.FindBone("elbow"));
        Assert::AreEqual<int>(kInvalidBone, s.FindBone("tail"));
        Assert::AreEqual<int>(kInvalidBone, s.FindBone(""));
    }

    TEST_METHOD(RestPoseIsPreserved) {
        const Skeleton s = MakeArmSkeleton();
        anim::test::AssertNear(Vec3{0.3f, 0.0f, 0.0f}, s.RestLocal(2).translation);
    }

    // 分岐のある階層も扱えること
    TEST_METHOD(BranchingHierarchy) {
        SkeletonBuilder b;
        b.AddRoot("root");
        b.AddBone("spine", "root");
        b.AddBone("leftArm",  "spine");
        b.AddBone("rightArm", "spine");
        const Skeleton s = b.Build();

        Assert::AreEqual<int>(1, s.ParentOf(2));
        Assert::AreEqual<int>(1, s.ParentOf(3));
        Assert::IsTrue(Validate(s) == SkeletonError::None);
    }

    // --- 検証 -----------------------------------------------------
    // Validate は「壊れたデータ」に対する防衛なので、
    // ビルダーを通さずに作った不正なスケルトンで検査する。
    // （テスト専用のヘルパーで直接組み立てる）

    TEST_METHOD(DetectsParentOutOfRange) {
        const Skeleton s = test::MakeRawSkeleton({kNoParent, 5}, {"a", "b"});
        Assert::IsTrue(Validate(s) == SkeletonError::ParentOutOfRange);
    }

    TEST_METHOD(DetectsTopologicalOrderViolation) {
        // ボーン 0 の親がボーン 1 = 親が後ろにいる
        const Skeleton s = test::MakeRawSkeleton({1, kNoParent}, {"a", "b"});
        Assert::IsTrue(Validate(s) == SkeletonError::ParentNotBefore);
    }

    TEST_METHOD(DetectsSelfParent) {
        const Skeleton s = test::MakeRawSkeleton({kNoParent, 1}, {"a", "b"});
        Assert::IsTrue(Validate(s) == SkeletonError::SelfParent);
    }

    TEST_METHOD(DetectsDuplicateName) {
        const Skeleton s = test::MakeRawSkeleton({kNoParent, 0}, {"a", "a"});
        Assert::IsTrue(Validate(s) == SkeletonError::DuplicateName);
    }

    TEST_METHOD(EmptySkeletonIsValid) {
        Assert::IsTrue(Validate(Skeleton{}) == SkeletonError::None);
    }
};

}  // namespace AnimLibTests
```

`test::MakeRawSkeleton` は、**ビルダーを迂回して不正なスケルトンを作る**テスト専用のヘルパーです。`TestSupport/SkeletonSupport.h` に置き、`Skeleton` の `friend` にしておきます。

```cpp
// TestSupport/SkeletonSupport.h
// Validate をテストするために、あえて不正なスケルトンを組み立てる。
// 製品コードからは使えない（テストプロジェクトにしか存在しない）。
namespace anim::test {

Skeleton MakeRawSkeleton(std::initializer_list<BoneIndex> parents,
                         std::initializer_list<const char*> names);

}  // namespace anim::test
```

**「正しい入力しか作れない API」と「不正な入力を検査する関数」を両方持ち、後者のテストのために前者を迂回する裏口を用意する。** これは検証コードを書くときの定石です。裏口をテストプロジェクト側に閉じ込めておけば、製品コードから誤用される心配はありません。

`MakeArmSkeleton()` も `TestSupport/SkeletonSupport.h` へ移します。第 14 章以降、このスケルトンを繰り返し使います。

## 13.10　つまずきやすいところ

**`AddBone` が `kInvalidBone` を返す**
親をまだ追加していません。ビルダーは根元から順に追加していく必要があります。分岐がある場合も、深さ優先でも幅優先でも構いませんが、**親が先**という条件だけは守ってください。

**glTF から読んだスケルトンで `ParentNotBefore` が出る**
仕様どおりです。glTF のノード順は親子関係と無関係です。第 34 章でトポロジカルソートしてから流し込みます。

**`ParentOf(i)` が巨大な値を返す**
`kNoParent`（65535）です。ルートボーンを指しています。`IsRoot(i)` を使うか、`p == kNoParent` を明示的に検査してください。`if (p >= 0)` のような検査は、`BoneIndex` が符号なしなので常に真になり、意味がありません。

**ボーンが 65535 本を超えた**
`Validate` が `TooManyBones` を返します。実際のモデルでこの数に達することはまずありませんが、プロシージャルに大量のボーンを生成した場合は起こりえます。`BoneIndex` を `std::uint32_t` に変えれば動きますが、第 17 章の頂点サイズが 2 倍になります。

**`FindBone` が遅い**
毎フレーム呼んでいます。設計の問題です。13.7 節を読み直してください。

**`Skeleton` をコピーしたら重い**
`std::string` の配列があるので、コピーは安くありません。**スケルトンは共有するもの**です。`const Skeleton&` で渡すか、`std::shared_ptr<const Skeleton>` で保持してください。

## この章のまとめ

- **スケルトン（形、不変）とポーズ（姿勢、毎フレーム）を分離する。** 1 つのスケルトンを 1000 体で共有できるこの構造が、第 IX 部の最適化の土台になる。
- ボーン階層は**配列 + 親インデックス**で表す。ただし理由は「キャッシュに優しいから」**ではない** ―― 100 ボーン規模では実測で差が出なかった（1.87 µs vs 1.90 µs）。実際の理由は**シリアライズの容易さ・インデックスの安定性・アロケーションの排除・ループの単純さ**。
- **`parents[i] < i`（親は自分より前）という不変条件**を、ビルダーで構造的に強制する。これ 1 つで、次章の階層解決が 1 パスのループになり、循環参照の検出すら不要になる。
- `BoneIndex` は `uint16_t`。第 17 章の頂点サイズに直結する。
- `FindBone` は**あえて線形探索のまま**にする。速くするとランタイムでの誤用が隠れる。
- **正しい入力しか作れない API と、不正な入力を検査する関数を両方持つ。** 後者のテストのための裏口は、テストプロジェクト側に閉じ込める。

次章では、このスケルトンにポーズを与えて、実際に腕を曲げます。手先がどこに来るかを紙の上で計算し、コードと突き合わせます。
