# 第 53 章　SIMD

**この章で作るもの**：AVX2 のイントリンシックで書いた階層解決とスキニング。外部ライブラリは使いません。

そして、この章にも失敗があります。**素直に SIMD 化したスキニングは、スカラー版の 2 倍遅くなりました。** 原因と直し方が、この章の山場です。

---

## 53.1　SIMD とは

**SIMD**（Single Instruction, Multiple Data）は、1 つの命令で複数のデータを同時に処理する仕組みです。

```
スカラー:  a0 + b0 = c0        1 命令で 1 個
           a1 + b1 = c1
           a2 + b2 = c2
           a3 + b3 = c3        → 4 命令

SIMD:     [a0 a1 a2 a3]
        + [b0 b1 b2 b3]
        = [c0 c1 c2 c3]        → 1 命令
```

x86 の系譜は、レジスタの幅で分かれています。

| 命令セット | 幅 | `float` の数 | 登場 |
|---|---|---|---|
| SSE / SSE2 | 128 bit | 4 | 1999 / 2001 |
| AVX | 256 bit | 8 | 2011 |
| AVX2 | 256 bit | 8（整数演算も 256 bit） | 2013 |
| AVX-512 | 512 bit | 16 | 2016 |

この章では **AVX2** を基準にします。2013 年以降のほぼすべての x86 CPU で使え、8 個の `float` を同時に扱えます。AVX-512 はサーバ向けが中心で、コンシューマ機での普及が限定的なうえ、動作クロックが下がる実装もあるため、ゲームの既定にはしにくい。

**この本では外部ライブラリを使いません**（DirectXMath も glm も）。MSVC の**イントリンシック**を直接書きます。イントリンシックは「1 つの CPU 命令に 1 対 1 で対応する関数」で、`<immintrin.h>` に入っています。

```cpp
#include <immintrin.h>

__m256 a = _mm256_loadu_ps(ptr);        // 8 個の float を読む
__m256 b = _mm256_set1_ps(2.0f);        // 8 レーン全部に 2.0
__m256 c = _mm256_mul_ps(a, b);         // 8 個同時に掛ける
_mm256_storeu_ps(out, c);               // 8 個書き戻す
```

命名規則さえ分かれば読めます。`_mm256_` は 256 bit、`_ps` は packed single（`float` を詰めたもの）。`loadu` の `u` は unaligned（アドレスが 32 バイト境界でなくてもよい）。

## 53.2　階層解決を 8 体同時に

第 52 章の `ComputeGlobalSoA` を、そのまま AVX2 に置き換えます。**スカラー版と 1 行ずつ対応させて書く**のがコツです。

```cpp
// AnimLib/include/anim/PoseBatchSimd.h
#pragma once
#include "anim/PoseBatch.h"
#include <immintrin.h>

namespace anim {

inline void ComputeGlobalAvx2(const Skeleton& s, const PoseBatch& local, PoseBatch& global){
    const std::size_t n = s.BoneCount(), m = local.Count(), stride = local.Stride();

    // ポインタを先に取り出しておく（毎回 vector を経由しない）
    const float* __restrict Ltx = local.tx_.data();
    /* ... 10 本ぶん ... */
    float* __restrict Gtx = global.tx_.data();
    /* ... 10 本ぶん ... */

    const __m256 two = _mm256_set1_ps(2.0f);

    for (std::size_t b = 0; b < n; ++b) {
        const BoneIndex p = s.ParentOf(static_cast<BoneIndex>(b));
        const std::size_t o = b * stride;

        if (p == kNoParent) {
            for (std::size_t c = 0; c < m; c += 8) {
                _mm256_storeu_ps(Gtx+o+c, _mm256_loadu_ps(Ltx+o+c));
                /* ... 10 本ぶん ... */
            }
            continue;
        }

        const std::size_t q = static_cast<std::size_t>(p) * stride;
        for (std::size_t c = 0; c < m; c += 8) {
            // 親（8 体ぶん）
            const __m256 pqx = _mm256_loadu_ps(Gqx+q+c), pqy = _mm256_loadu_ps(Gqy+q+c);
            const __m256 pqz = _mm256_loadu_ps(Gqz+q+c), pqw = _mm256_loadu_ps(Gqw+q+c);
            const __m256 psx = _mm256_loadu_ps(Gsx+q+c), psy = _mm256_loadu_ps(Gsy+q+c),
                         psz = _mm256_loadu_ps(Gsz+q+c);
            // 子（8 体ぶん）
            const __m256 cqx = _mm256_loadu_ps(Lqx+o+c), cqy = _mm256_loadu_ps(Lqy+o+c);
            const __m256 cqz = _mm256_loadu_ps(Lqz+o+c), cqw = _mm256_loadu_ps(Lqw+o+c);

            #define MUL _mm256_mul_ps
            #define ADD _mm256_add_ps
            #define SUB _mm256_sub_ps

            // 回転（スカラー版と同じ順序）
            _mm256_storeu_ps(Gqx+o+c, SUB(ADD(ADD(MUL(pqw,cqx),MUL(pqx,cqw)),MUL(pqy,cqz)),MUL(pqz,cqy)));
            _mm256_storeu_ps(Gqy+o+c, ADD(ADD(SUB(MUL(pqw,cqy),MUL(pqx,cqz)),MUL(pqy,cqw)),MUL(pqz,cqx)));
            _mm256_storeu_ps(Gqz+o+c, ADD(SUB(ADD(MUL(pqw,cqz),MUL(pqx,cqy)),MUL(pqy,cqx)),MUL(pqz,cqw)));
            _mm256_storeu_ps(Gqw+o+c, SUB(SUB(SUB(MUL(pqw,cqw),MUL(pqx,cqx)),MUL(pqy,cqy)),MUL(pqz,cqz)));

            // スケール
            _mm256_storeu_ps(Gsx+o+c, MUL(psx,_mm256_loadu_ps(Lsx+o+c)));
            _mm256_storeu_ps(Gsy+o+c, MUL(psy,_mm256_loadu_ps(Lsy+o+c)));
            _mm256_storeu_ps(Gsz+o+c, MUL(psz,_mm256_loadu_ps(Lsz+o+c)));

            // 平行移動
            const __m256 vx = MUL(psx,_mm256_loadu_ps(Ltx+o+c));
            const __m256 vy = MUL(psy,_mm256_loadu_ps(Lty+o+c));
            const __m256 vz = MUL(psz,_mm256_loadu_ps(Ltz+o+c));
            const __m256 tx = MUL(two, SUB(MUL(pqy,vz), MUL(pqz,vy)));
            const __m256 ty = MUL(two, SUB(MUL(pqz,vx), MUL(pqx,vz)));
            const __m256 tz = MUL(two, SUB(MUL(pqx,vy), MUL(pqy,vx)));
            _mm256_storeu_ps(Gtx+o+c, ADD(_mm256_loadu_ps(Gtx+q+c),
                             ADD(ADD(vx,MUL(pqw,tx)), SUB(MUL(pqy,tz),MUL(pqz,ty)))));
            _mm256_storeu_ps(Gty+o+c, ADD(_mm256_loadu_ps(Gty+q+c),
                             ADD(ADD(vy,MUL(pqw,ty)), SUB(MUL(pqz,tx),MUL(pqx,tz)))));
            _mm256_storeu_ps(Gtz+o+c, ADD(_mm256_loadu_ps(Gtz+q+c),
                             ADD(ADD(vz,MUL(pqw,tz)), SUB(MUL(pqx,ty),MUL(pqy,tx)))));

            #undef MUL
            #undef ADD
            #undef SUB
        }
    }
}
}  // namespace anim
```

**マクロを使っている**ことについて。`_mm256_mul_ps(a,b)` と書き続けると、式が横に伸びて構造が読めなくなります。3 行のマクロで `MUL`・`ADD`・`SUB` にすると、**スカラー版と目で対応が取れる**ようになります。関数のスコープを出る前に `#undef` するのを忘れずに。

**`c += 8` で端数処理がない**のは、第 52 章で `cap_` を 16 の倍数に切り上げたおかげです。設計判断が 1 章あとで回収されました。

## 53.3　測定

第 52 章の表を再掲します。1 体あたりのナノ秒。

| キャラクター数 | AoS | SoA（スカラー） | SoA + AVX2 | AVX2 / AoS |
|---|---|---|---|---|
| 16 | `447.0` | `388.4` | **`117.6`** | **3.80×** |
| 100 | `437.1` | `379.3` | **`142.1`** | **3.08×** |
| 1000 | `421.3` | `1153.1` | **`259.6`** | **1.62×** |
| 4000 | `469.0` | `1289.5` | **`310.3`** | **1.51×** |

**8 レーンあるのに、なぜ 8 倍にならないのか。**

**16〜100 体で 3.1〜3.8 倍。** ここが計算律速の領域です。8 倍に届かないのは、ロード / ストアの命令が計算と同じくらいあるからです。1 ボーンの処理で 17 回ロード、10 回ストア、約 40 回の演算。**メモリアクセスは 8 倍に減りません**（読むバイト数は同じ）。

**1000 体以上で 1.5〜1.6 倍。** ここはメモリ帯域律速です。データが L2 に乗らなくなり、DRAM から読む速度が上限を決めます。**計算をいくら速くしても、データが届かなければ意味がない。**

> **SIMD の効果は「命令の数」ではなく「どこがボトルネックか」で決まる。**
>
> 100 体なら 3 倍、1000 体なら 1.5 倍。同じコードです。ボトルネックが移動しただけ。

1000 体で頭打ちになるなら、**次に効くのはデータを小さくすること**です ―― それが第 54〜56 章の圧縮であり、**やらずに済ませること** ―― それが第 59 章の LOD です。第 IX 部の章が、この順に並んでいる理由です。

## 53.4　単体テスト：スカラー版と一致するか

第 1 章の**③ 実装間の一致テスト**。ここで許容範囲をいくつにするかが問題になります。

```cpp
TEST_METHOD(Avx2MatchesScalar) {
    /* ... 同じ入力を両方へ ... */
    ComputeGlobalSoA (s, L, G1);
    ComputeGlobalAvx2(s, L, G2);

    float worst = 0.0f;
    for (int c = 0; c < M; ++c)
        for (int b = 0; b < 60; ++b)
            worst = std::fmax(worst, Length(G1.Get(b,c).translation - G2.Get(b,c).translation));

    Assert::AreEqual(0.0f, worst, ???);
}
```

最初の実測は **`0.000000602`**。ビット単位では一致していません。

原因は **FMA（Fused Multiply-Add）** です。`a*b + c` を 1 命令で計算する仕組みで、**途中で丸めが入らない**ぶん精度が高い。コンパイラは最適化として、勝手にこの融合を行います。

問題は、**スカラー版と AVX2 版で融合される場所が違う**ことです。同じ数式でも、どこで丸めるかが変われば結果が変わります。**FMA のほうが「正確」ですが、「同じ」ではありません。**

MSVC では、この挙動を制御できます。

```cpp
#pragma float_control(precise, on, push)
// ここでは融合を抑制する
#pragma float_control(pop)
```

あるいはプロジェクト設定で `/fp:precise`（既定）と `/fp:fast` を切り替えます。GCC / Clang なら `-ffp-contract=off`。

融合を止めて測り直すと ―― **`0.000000000`**。**ビット単位で完全一致**しました。

```cpp
Assert::AreEqual(0.0f, worst, 0.0f);      // 融合を止めればここまで言える
```

**どちらを選ぶか。** 私の判断はこうです。

- **テストのビルドでは融合を止める。** 一致テストを `0` で書けることの価値は大きい。「だいたい合っている」の「だいたい」を毎回議論しなくて済みます。
- **製品のビルドでは融合を許す。** FMA は速く、精度も高い。
- **決定性が要る場所では止める。** リプレイ、ネットワーク同期、そして第 57 章のマルチスレッド決定性テスト。

第 4 章で `/fp:fast` の話をしたときと、同じ構図です。**「速い」と「同じ結果になる」は別の要求で、両立しないことがある。** どちらが要るかは、機能ごとに決まります。

## 53.5　スキニングを SIMD 化する ―― そして失敗する

次はスキニングです。第 20 章で SoA 化したメッシュがあります。パレットは第 58 章に合わせて **3 本の `float4`（12 float）** 形式にしておきます（最下行は常に `(0,0,0,1)` なので送る必要がない）。

スカラー版はこうです。

```cpp
for (std::size_t i = 0; i < n; ++i) {
    float x=0, y=0, z=0;
    for (int k = 0; k < 4; ++k) {
        const float w = W[k][i];
        if (w == 0.0f) continue;
        const float* f = &palette[ J[k][i] * 12 ];       // ← 頂点ごとに違うボーン
        x += w*(f[0]*px[i] + f[1]*py[i] + f[2]*pz[i] + f[3]);
        y += w*(f[4]*px[i] + f[5]*py[i] + f[6]*pz[i] + f[7]);
        z += w*(f[8]*px[i] + f[9]*py[i] + f[10]*pz[i] + f[11]);
    }
    ox[i]=x; oy[i]=y; oz[i]=z;
}
```

8 頂点同時にしたい。しかし**8 つの頂点は、それぞれ違うボーンを参照します**。`palette` の飛び飛びの場所から 8 個の値を集めてこなければならない。

AVX2 には、そのための命令があります。**ギャザー（gather）** です。

```cpp
__m256i idx = _mm256_setr_epi32(J[k][i+0]*12, J[k][i+1]*12, /* ... */ J[k][i+7]*12);
__m256 f0 = _mm256_i32gather_ps(base + 0, idx, 4);   // 8 か所から f[0] を集める
__m256 f1 = _mm256_i32gather_ps(base + 1, idx, 4);   // 8 か所から f[1] を集める
// ... 12 本
```

素直な実装です。書いて、測りました。

| 頂点数 | スカラー | AVX2（ギャザー） |
|---|---|---|
| 1,642 | `10.89` µs | **`22.04` µs（0.49×）** |
| 40,202 | `285.81` µs | **`561.96` µs（0.51×）** |

**2 倍遅い。** 結果はビット単位で一致（`0.000000000`）しているので、間違ってはいません。ただ遅い。

## 53.6　ギャザーは遅い

`vgatherdps` は「1 命令」ですが、**中では 8 回のメモリアクセスが順に行われます**。マイクロコードで展開され、レイテンシは数十サイクル。しかも、この関数では 4 つの影響ボーン × 12 本の要素 = **48 回のギャザー**を 8 頂点ごとに実行しています。

ギャザーが速いのは「メモリ帯域が本当のボトルネックで、スカラーだと命令数が足りない」ような場合に限られます。ここでは逆で、**ギャザー自体が新しいボトルネックになりました**。

**SIMD 命令を使ったから速くなる、ということはありません。** レーンを埋める方法が高くつくなら、埋めないほうが速い。

---

## 53.7　ギャザーを消す ―― データの並べ替えで

問題は「8 つの頂点が違うボーンを見る」ことです。だったら、**同じボーンを見る頂点を集めればいい。**

スキンメッシュには、実は強い性質があります。**隣り合う頂点は、たいてい同じボーンの組に影響されます。** 上腕の表面の頂点は、みな「肩と肘」に紐づいている。実際、この本の円柱メッシュ（ボーン 3 本）で、頂点が持つジョイントの組は **3 種類**しかありませんでした。

そこで、**頂点をジョイントの組でソートし、同じ組ごとの区間（バケット）に分けます**。

```cpp
struct Bucket { std::uint16_t j[4]; std::size_t begin, end; };

std::vector<Bucket> BucketByJoints(SoaMesh& m) {
    // (j0,j1,j2,j3) をキーにして頂点を並べ替える
    std::vector<std::size_t> order(m.n);
    std::iota(order.begin(), order.end(), 0);
    auto key = [&](std::size_t i){
        return (std::uint64_t)m.j0[i]<<48 | (std::uint64_t)m.j1[i]<<32
             | (std::uint64_t)m.j2[i]<<16 | m.j3[i];
    };
    std::sort(order.begin(), order.end(), [&](auto a, auto b){ return key(a) < key(b); });
    /* order の順に SoA を詰め直す */

    // 連続する同じ組を 1 バケットにまとめる
    std::vector<Bucket> out;
    std::size_t b = 0;
    while (b < m.n) {
        std::size_t e = b + 1;
        while (e < m.n && m.j0[e]==m.j0[b] && m.j1[e]==m.j1[b]
                       && m.j2[e]==m.j2[b] && m.j3[e]==m.j3[b]) ++e;
        out.push_back({{m.j0[b],m.j1[b],m.j2[b],m.j3[b]}, b, e});
        b = e;
    }
    return out;
}
```

**この並べ替えはロード時に 1 回だけ**行います。実行時のコストはゼロです。三角形のインデックスを付け替える必要がありますが、それも 1 回きり。

バケットの中では、全頂点が同じ 4 ボーンを見ます。だから**ギャザーではなくブロードキャスト**（`_mm256_set1_ps`、1 つの値を 8 レーンに複製）が使えます。

```cpp
void SkinAvx2Bucketed(const SoaMesh& m, const std::vector<Bucket>& buckets,
                      const std::vector<float>& palette,
                      std::vector<float>& ox, std::vector<float>& oy, std::vector<float>& oz) {
    for (const Bucket& b : buckets) {
        // このバケットで使う 4 本の行列を、ループの外で決める
        const float* F[4] = { &palette[b.j[0]*12], &palette[b.j[1]*12],
                              &palette[b.j[2]*12], &palette[b.j[3]*12] };

        std::size_t i = b.begin;
        const std::size_t last = b.begin + ((b.end - b.begin) & ~std::size_t(7));
        for (; i < last; i += 8) {
            __m256 X = _mm256_setzero_ps(), Y = _mm256_setzero_ps(), Z = _mm256_setzero_ps();
            const __m256 px = _mm256_loadu_ps(&m.px[i]);
            const __m256 py = _mm256_loadu_ps(&m.py[i]);
            const __m256 pz = _mm256_loadu_ps(&m.pz[i]);
            const float* WW[4] = {&m.w0[i], &m.w1[i], &m.w2[i], &m.w3[i]};

            for (int k = 0; k < 4; ++k) {
                const __m256 w = _mm256_loadu_ps(WW[k]);
                const float* f = F[k];
                #define S(o) _mm256_set1_ps(f[o])          // ← ギャザーではなく複製
                X = _mm256_fmadd_ps(w, _mm256_add_ps(
                        _mm256_fmadd_ps(S(0),px,_mm256_fmadd_ps(S(1),py,_mm256_mul_ps(S(2),pz))), S(3)), X);
                Y = _mm256_fmadd_ps(w, _mm256_add_ps(
                        _mm256_fmadd_ps(S(4),px,_mm256_fmadd_ps(S(5),py,_mm256_mul_ps(S(6),pz))), S(7)), Y);
                Z = _mm256_fmadd_ps(w, _mm256_add_ps(
                        _mm256_fmadd_ps(S(8),px,_mm256_fmadd_ps(S(9),py,_mm256_mul_ps(S(10),pz))), S(11)), Z);
                #undef S
            }
            _mm256_storeu_ps(&ox[i], X);
            _mm256_storeu_ps(&oy[i], Y);
            _mm256_storeu_ps(&oz[i], Z);
        }
        for (; i < b.end; ++i) { /* 端数はスカラーで */ }
    }
}
```

`_mm256_set1_ps(f[0])` はレジスタへの 1 回のブロードキャストで、**ほぼ無料**です。さらに、この値はループ内で不変なので、コンパイラは 8 頂点ぶんの外へ持ち上げられます。

測り直します。

| 頂点数 | スカラー | AVX2 ギャザー | AVX2 バケット |
|---|---|---|---|
| 1,642 | `10.89` µs | `22.04` µs（0.49×） | **`2.37` µs（4.60×）** |
| 40,202 | `285.81` µs | `561.96` µs（0.51×） | **`62.03` µs（4.61×）** |

**0.49 倍から 4.60 倍へ。** 実に 9.4 倍の差です。結果はどちらもスカラー版とビット単位で一致（`0.000000000`）。

**変えたのは命令ではなく、データの並びです。** ギャザー版とバケット版は、どちらも AVX2 で同じ演算をしています。違いは「値をどうやってレーンに詰めるか」だけ。

> **SIMD で効くのは、レーンを埋める方法である。**
>
> 第 52 章の結論と表裏一体です ―― データ指向レイアウトは SIMD の前提条件であり、SIMD の性能はレイアウトで決まる。

**1 頂点あたり `7.11` ns が `1.54` ns になりました。** 4 万頂点のキャラクターで、285 µs → 62 µs。100 体なら 28.5 ms → 6.2 ms です（もっとも、100 体ぶんの CPU スキニングは第 58 章で GPU へ渡すことになります）。

## 53.8　実行時のフォールバック

AVX2 は 2013 年以降の CPU にしかありません。それ以前の CPU で AVX2 命令を実行すると、**未定義命令例外でクラッシュ**します。コンパイル時に `/arch:AVX2` を指定するだけでは足りません ―― 実行時に調べる必要があります。

MSVC には `__cpuid` / `__cpuidex` があります。

```cpp
// AnimLib/include/anim/CpuFeatures.h
#pragma once
#include <intrin.h>

namespace anim {

struct CpuFeatures {
    bool sse42 = false, avx = false, avx2 = false, fma = false;

    static CpuFeatures Detect() {
        CpuFeatures f;
        int info[4]{};
        __cpuid(info, 0);
        const int maxLeaf = info[0];

        if (maxLeaf >= 1) {
            __cpuid(info, 1);
            f.sse42 = (info[2] & (1 << 20)) != 0;   // ECX bit 20
            f.fma   = (info[2] & (1 << 12)) != 0;   // ECX bit 12
            const bool osxsave = (info[2] & (1 << 27)) != 0;
            const bool avxBit  = (info[2] & (1 << 28)) != 0;
            // OS が YMM レジスタの保存に対応しているかも確認する
            if (osxsave && avxBit) {
                const unsigned long long xcr0 = _xgetbv(0);
                f.avx = ((xcr0 & 0x6) == 0x6);
            }
        }
        if (maxLeaf >= 7 && f.avx) {
            __cpuidex(info, 7, 0);
            f.avx2 = (info[1] & (1 << 5)) != 0;     // EBX bit 5
        }
        return f;
    }
};

// プロセス起動時に 1 回だけ調べる
inline const CpuFeatures& Cpu() {
    static const CpuFeatures f = CpuFeatures::Detect();
    return f;
}
}  // namespace anim
```

**`_xgetbv` の確認を省いてはいけません。** CPU が AVX に対応していても、**OS が YMM レジスタをコンテキストスイッチで保存してくれなければ使えません**。CPUID の AVX ビットだけを見て分岐すると、古い OS で壊れます。`XCR0` の bit 1・2（SSE 状態と AVX 状態）が立っているかを確認します。

呼び分けは関数ポインタで。

```cpp
using SkinFn = void(*)(const SoaMesh&, const std::vector<Bucket>&,
                       const std::vector<float>&,
                       std::vector<float>&, std::vector<float>&, std::vector<float>&);

inline SkinFn SelectSkinFunction() {
    return Cpu().avx2 && Cpu().fma ? &SkinAvx2Bucketed : &SkinScalarBucketed;
}
```

**分岐は「1 頂点ごと」ではなく「1 回だけ」**にします。`if (Cpu().avx2)` をループの中に書くと、分岐予測が効いてもレジスタ圧が上がり、せっかくの利得を削ります。

### コンパイル単位を分ける

MSVC で `/arch:AVX2` を指定すると、**そのコンパイル単位全体**が AVX2 命令を使うようになります。スカラー版のフォールバックが同じ `.cpp` にあると、フォールバックのはずのコードが AVX2 命令を含んでしまい、古い CPU でクラッシュします。

```
AnimLib/
  src/
    SkinScalar.cpp     ← /arch:SSE2（既定）
    SkinAvx2.cpp       ← /arch:AVX2 をこのファイルだけに設定
```

Visual Studio では、ファイルのプロパティで個別に設定できます（プロジェクト全体の設定を上書きします）。**この分離を忘れるのが、SIMD で最もよくある事故**です。

## 53.10　SIMD 化しないもの

第 52 章の表と同じ判断ですが、SIMD の観点で整理し直します。

**向くもの ―― 同じ計算を、たくさん、依存関係なく。**

- 階層解決（キャラクター方向） → **3.08×**
- スキニング（頂点方向） → **4.61×**
- パレット生成（行列の積） → 同様に効くはず
- ブレンド（第 38 章） → ポーズ全体の重み付き和なので効く

**向かないもの ―― 分岐、可変長、依存の連鎖。**

- **キーフレームの探索。** 二分探索は分岐だらけで、しかもトラックごとにキー数が違います。第 25 章のヒント付き探索（前フレームの位置から線形に探す）のほうが、はるかに効きます。
- **IK。** 反復回数が入力によって変わります。8 体まとめて処理すると、1 体だけ収束が遅いときに全員がその回数を払います。
- **ステートマシン。** 分岐そのものが仕事です。
- **`Slerp`。** `acos` と `sin` が入ります。SIMD 版の三角関数を自作すれば効きますが、それは別の本の話です ―― そして第 10 章で見たとおり、ブレンドの角度差が小さい場面では `Nlerp` で足ります。**そもそも呼ばないのが一番速い。**

## この章のまとめ

- SIMD は「1 命令で複数データ」。この本は **AVX2（256 bit、`float` 8 個）** を基準に、イントリンシックを直接書く。
- SIMD コードは**スカラー版と 1 行ずつ対応させて書く**。`MUL`/`ADD`/`SUB` の 3 マクロで、式の構造が目で追えるようになる。
- 階層解決は **3.80×（16 体）／3.08×（100 体）／1.62×（1000 体）**。8 レーンあっても 8 倍にならないのは、ロード / ストアが 8 倍に減らないから。1000 体では**ボトルネックがメモリ帯域へ移動**する。
- **SIMD の効果は「命令の数」ではなく「どこがボトルネックか」で決まる。**
- FMA の融合により、スカラー版と AVX2 版の結果が **`6.02e-7`** ずれた。融合を止める（MSVC `/fp:precise`、`#pragma float_control(precise, on, push)`）と **`0.000000000`**。**テストでは止め、製品では許し、決定性が要る場所では止める。**
- **素直に SIMD 化したスキニングは 0.49 倍 ―― 2 倍遅かった。** 原因は `vgatherdps`。1 命令に見えて中身は 8 回のメモリアクセスで、それ自体が新しいボトルネックになる。
- 直し方は命令ではなく**データの並べ替え**。頂点をジョイントの組でソートしてバケットに分ければ、ギャザーが**ブロードキャスト**に変わる。実測 **0.49× → 4.61×（9.4 倍の差）**、結果はビット単位で一致。並べ替えはロード時 1 回で、実行時コストはゼロ。
- **SIMD で効くのは、レーンを埋める方法である。**
- 実行時判定は `__cpuid` + **`_xgetbv`**（OS が YMM を保存するか）。**`/arch:AVX2` はコンパイル単位ごとに設定し、フォールバックは別の `.cpp` に置く** ―― これを忘れるのが最頻の事故。
- 分岐だらけのもの（キー探索、IK、ステートマシン）は SIMD 化しない。**そもそも呼ばないのが一番速い。**

次章から 3 章かけて、**キーフレーム圧縮**をやります。1000 体でボトルネックがメモリ帯域に移った以上、次に効くのは**データを小さくすること**です。185.9 KB のクリップを 14.6 KB にします。
