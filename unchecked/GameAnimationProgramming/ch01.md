# 第 1 章　本書の地図

この章ではコードを一行も書きません。その代わり、これから 60 章以上かけて作るものの全体像を、一度だけ最後まで見通しておきます。アニメーションプログラミングは、個々の要素はどれも難しくないのに、用語と登場人物が多いせいで迷子になりやすい分野です。最初に地図を持っておくと、あとの章で「今どこにいるのか」を見失わずに済みます。

---

## 1.1　キャラクターは毎フレーム何をしているのか

画面の中でキャラクターが走っているとき、プログラムが 1 フレームのあいだに行っている計算は、驚くほど単純な形にまとめられます。

```
        時刻 t
          │
          ▼
  ┌────────────────┐
  │ ① クリップをサンプルする │  アニメーションデータから、時刻 t での
  └────────────────┘  「各ボーンの姿勢」を取り出す
          │
          ▼   ローカルポーズ（親から見た各ボーンの姿勢）
  ┌────────────────┐
  │ ② ポーズをブレンドする  │  歩きと走りを 3:7 で混ぜる、上半身だけ
  └────────────────┘  別の動きにする、など
          │
          ▼   ローカルポーズ
  ┌────────────────┐
  │ ③ 階層を解いて         │  親をたどって、各ボーンのワールド姿勢を求める
  │    グローバルポーズを作る │
  └────────────────┘
          │
          ▼   グローバルポーズ
  ┌────────────────┐
  │ ④ IK で補正する        │  足を地面に着ける、手を武器に合わせる
  └────────────────┘
          │
          ▼   グローバルポーズ（補正済み）
  ┌────────────────┐
  │ ⑤ スキニング行列パレット │  逆バインド行列を掛けて、頂点変形用の
  │    を作る              │  行列の配列にする
  └────────────────┘
          │
          ▼   Mat4 の配列（ボーン数ぶん）
  ┌────────────────┐
  │ ⑥ 頂点を変形する       │  各頂点を、影響するボーンの行列で
  └────────────────┘  重み付き変形する（CPU または GPU）
          │
          ▼
        変形後の頂点 → 描画へ
```

本書は、この 6 つの箱を左上から順に、しかし**作りやすい順に組み替えて**実装していきます。具体的には ③ → ⑤ → ⑥ →（実データ読み込み）→ ① → ② → ④ の順です。理由は 1.5 節で説明します。

重要なのは、この図の**どこにも「描画」が入っていない**ことです。⑥ の出力は「変形後の頂点座標の配列」であって、それをどう画面に出すかは別の話です。だからこそ本書は、描画を一切せずにアニメーションを実装し、その正しさを確認できます。

## 1.2　登場人物を先に紹介しておく

以降の章で何度も出てくる言葉を、ここで一度に定義します。今は「そういう名前のものがある」と眺めるだけで構いません。第 13 章から第 16 章で、コードとして一つずつ組み上げていきます。

**ボーン（bone）／ジョイント（joint）**
キャラクターの骨組みを構成する 1 つの節。実体は「親から見た相対的な姿勢」を持つだけのデータで、太さも長さもありません。glTF では joint と呼びます。本書では区別せず「ボーン」で通します。

**スケルトン（skeleton）**
ボーンの集合と、その親子関係（階層構造）。人型なら 50〜150 本程度が典型です。スケルトンは**形の定義**であって、時間とともに変化しません。

**ポーズ（pose）**
ある瞬間の、全ボーンの姿勢のスナップショット。ボーン数ぶんの `Transform`（平行移動・回転・スケール）の配列です。**スケルトンが「骨格」なら、ポーズは「今の格好」**です。

- **ローカルポーズ**：各ボーンの姿勢を、親ボーンから見た相対値で表したもの。アニメーションデータが持っているのはこちら。
- **グローバルポーズ**：各ボーンの姿勢を、モデル空間の絶対値で表したもの。親から順にたどって計算します。

**バインドポーズ（bind pose）**
メッシュがスケルトンに紐づけられた瞬間の、基準となるポーズ。多くの場合、両手を横に広げた T ポーズや A ポーズです。「メッシュの頂点座標は、このポーズのときの座標として記録されている」という約束を担います。

**逆バインド行列（inverse bind matrix）**
バインドポーズにおけるボーンのグローバル行列の逆行列。頂点をいったん「ボーンから見たローカル座標」に引き戻すために使います。第 15 章の主役です。

**スキニング行列パレット（skinning matrix palette）**
`グローバルポーズ行列 × 逆バインド行列` をボーンごとに計算した、行列の配列。頂点シェーダに渡すのはこれです。**アニメーションシステムの最終出力**だと思ってください。

**スキニング（skinning）**
頂点を、影響するボーンの行列で重み付き変形すること。単純に行列を重み付き平均する手法を**リニアブレンドスキニング（LBS）**と呼びます（第 18 章）。

**クリップ（clip）**
「歩き」「走り」「ジャンプ」といった、一続きのアニメーションデータ。ボーンごと・チャンネル（平行移動／回転／スケール）ごとの**キーフレームの列**を持ちます。

## 1.3　本書で作るもの、作らないもの

### 作るもの

`AnimLib` という 1 つの静的ライブラリを、62 章かけて育てます。最終形はおおよそこうなります。

| 領域 | 中身 |
| --- | --- |
| 数学 | `Vec3` `Vec4` `Mat4` `Quat` `Transform` `DualQuat` |
| スケルトン | `Skeleton` `Pose` `SkinMatrixPalette` |
| メッシュ | `SkinnedMesh` `LinearBlendSkinner` `DualQuatSkinner` |
| クリップ | `Track` `Clip` `ClipPlayer` `RootMotionExtractor` |
| 読み込み | `JsonParser` `GltfLoader` `GlbReader` `RuntimeAssetBaker` |
| ブレンド | `PoseBlender` `BlendTree` `BlendSpace1D` `BlendSpace2D` `StateMachine` |
| IK | `TwoBoneIK` `CcdSolver` `FabrikSolver` `LookAt` `FootIK` |
| 最適化 | SoA 版ポーズ、SIMD スキニング、`CompressedClip`、GPU スキニング |

外部ライブラリは使いません。JSON パーサも、数学も、テスト用のメッシュ生成も自分で書きます。理由は 2 つあります。1 つは、アニメーションの本質は数式ではなく**データの流し方**にあり、それはライブラリの向こう側に隠れると見えなくなるからです。もう 1 つは、依存関係がゼロなら、この本を 5 年後に開いた読者もそのままビルドできるからです。

唯一の例外が第 58 章の GPU スキニングで、ここだけ Direct3D 12 に触れます。それでも描画はせず、コンピュートシェーダで変形した結果を CPU に読み戻して照合するだけに留めます。この章は独立して読み飛ばせるように書いてあります。

### 作らないもの

- **描画**。レンダラ、マテリアル、ライティング、シャドウは範囲外です。
- **モデリングツール連携**。FBX SDK や DCC ツールのプラグインは扱いません。glTF に一本化します。
- **物理シミュレーション**。髪や布のセカンダリモーション、ラグドールは扱いません（第 63 章で地図だけ示します）。
- **リターゲティング**。別のスケルトンへのモーション移植は扱いません。

## 1.4　前提とする知識と環境

### 読者に期待すること

C++ の基本文法を読み書きできることだけを前提とします。クラス、テンプレート、`std::vector`、参照とポインタの違いが分かれば十分です。ムーブセマンティクスやコンセプトを知らなくても、使う場面で説明します。

**線形代数の知識は前提としません。** ベクトル・行列・クォータニオンは第 II 部で必要な分だけ、しかもゲームで使う形に絞って一から作ります。大学の線形代数の講義とは順序も強調点も違いますが、それは意図的なものです。

### 環境

- **Visual Studio 2026**（Community 版で構いません）。ワークロードは「C++ によるデスクトップ開発」。
- **C++23**（`/std:c++latest`）。
- **C++ モジュールは使いません。** 従来どおりヘッダとソースで構成します。ビルドシステムの都合で読者が詰まる余地を減らすためです。ただし言語機能としての C++23 は積極的に使います（`std::span`、`std::format`、`std::expected`、`if consteval` など）。
- **x64 のみ**。x86 構成は削除して構いません。

Visual Studio 2026 以外を使いたい場合、第 2 章のプロジェクト設定と第 3 章のテストヘルパーだけは読み替えが必要ですが、第 5 章以降のコードは標準 C++ の範囲に収まっており、そのまま移植できます。

## 1.5　描画しないで、どうやって正しさを確認するのか

これが本書のいちばん特徴的な選択なので、少し丁寧に説明します。

アニメーションプログラミングの入門記事の多くは、画面にキャラクターを出して「動いた！」で終わります。しかしこのやり方には 3 つの困りごとがあります。

**第一に、見た目では小さな間違いが分からない。** 回転の合成順序が逆でも、行列が転置されていても、体の一部が微妙にねじれるだけで「そういうモーションかな」と見過ごせてしまいます。数フレームだけ 0.5 度ずれる、という種類のバグは目視ではまず見つかりません。

**第二に、間違いが見つかっても場所が分からない。** キャラクターが爆発したような見た目になったとき、原因はクォータニオンの符号かもしれないし、逆バインド行列かもしれないし、ウェイトの正規化かもしれません。パイプラインの 6 段全部が容疑者です。

**第三に、描画コードを書くまで何も確認できない。** ウィンドウを作り、デバイスを初期化し、シェーダを書き、ようやく最初の三角形が出る。本題に入る前に数百行が必要になります。

そこで本書は、**すべての章を単体テストで検証します**。使うのは Visual Studio に同梱されている Microsoft Native Unit Test で、追加のインストールは不要です。

具体的には、次の 4 種類のテストを組み合わせます。

**① 手計算との照合。** ボーン 2 本の腕を 90 度曲げたとき、手先はどこに来るか。紙の上で出せる答えとコードの出力を突き合わせます。単純ですが、これが最も強力です。

**② 性質のテスト（プロパティテスト）。** 「逆行列を掛ければ単位行列になる」「ブレンドウェイトの合計は常に 1」「ボーンの長さは IK の前後で変わらない」。具体的な値を知らなくても、成り立つべき性質は検証できます。ランダムな入力を大量に流し込めるのが強みです。

**③ 実装間の一致テスト。** 遅くて確実な素朴な実装と、速い最適化実装を両方持ち、同じ入力に対して同じ出力になることを確かめます。第 20 章の SoA 化、第 53 章の SIMD、第 58 章の GPU スキニングは、すべてこの形で検証します。

**④ ゴールデンテスト。** ある時点で「正しい」と確認した出力を保存しておき、以降の変更でそれが変わらないことを確かめます。大規模なリファクタリングのときの命綱です。

そして、この方針は**実装の順序**にも影響します。冒頭の図で ③⑤⑥ を先にやると書いたのは、それらが**時間を含まない**からです。時刻もキーフレームも補間も出てこない、純粋な「ポーズ → 頂点」の変換なので、入力を手で書けばテストが書けます。時間の絡む ①② は、静的な部分が固まってから取りかかるほうがはるかに楽です。

## 1.7　この本の読み方

各章は次の形で書かれています。

1. **この章で作るもの** ― 1〜2 文
2. **動機** ― 前章までのコードの何が足りないのか
3. **実装** ― 10〜40 行ずつの小さな追加
4. **単体テスト** ― 何を、なぜ、そのしきい値で検証するのか
5. **まとめ** ― 次章への橋渡し

**コードは必ず手で打ってください。** 写経は退屈ですが、アニメーションのコードは「符号が 1 つ違う」「掛ける順序が逆」といった間違いが本質的な理解の分かれ目になっていて、それはコピー&ペーストでは通り抜けてしまいます。テストが赤くなり、原因を探し、緑になる。その往復が、この本で得られるものの大半です。

**テストが緑になってから次の章へ進んでください。** 各章のテストは、その章の内容だけでなく、それ以前のすべてを守っています。1 つ赤いまま先に進むと、3 章先で原因不明の破綻に出会います。

意図的に**失敗するテスト**を書く章もあります（第 3 章、第 21 章）。「壊れていることを確認する」のもテストの正当な使い方です。

## この章のまとめ

- アニメーションの 1 フレームは、**サンプル → ブレンド → 階層解決 → IK → パレット生成 → 頂点変形**の 6 段。
- アニメーションシステムの最終出力は**スキニング行列パレット**であり、そこに描画は含まれない。だから描画なしで実装・検証できる。
- 本書は 4 種類のテスト（**手計算照合／性質／実装間一致／ゴールデン**）で全章を守る。
- 時間を含まない部分（スケルトン・スキニング）から先に作り、時間を含む部分（クリップ・ブレンド）へ進む。

次章では、`AnimLib` と `AnimLib.Tests` の 2 つのプロジェクトを作り、`Assert::AreEqual(2, 1 + 1)` が緑になるところまで進めます。
