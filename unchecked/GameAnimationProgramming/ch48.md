# 第 48 章　CCD IK

**この章で作るもの**：任意の長さのチェーンを扱える反復ソルバ **CCD**（Cyclic Coordinate Descent、循環座標降下法）。そして ―― この章の主題は実のところソルバそのものではなく、**それが収束しなかった 2 つの理由**です。

---

## 48.1　1 関節ずつ、末端から根元へ

CCD の考え方は、拍子抜けするほど単純です。

> **関節を 1 つだけ選び、その関節を回して、エフェクタをできるだけ目標に近づける。**
> **それを、末端に近い関節から根元へ向かって順に繰り返す。**

「1 つの関節だけを回して、エフェクタを目標に最も近づける回転」は、考えるまでもなく一意です。

```
       関節 J
         ●
        ╱ ＼
       ╱    ＼  ← この扇形の上をエフェクタが動く
      ╱  E    ＼
     ╱   ●     ＼        E: 現在のエフェクタ位置
    ╱      ＼    ＼       T: 目標
   ╱         ● T  ＼
```

`J` を中心にエフェクタを回すのだから、エフェクタは `J` を中心とする球面上しか動けません。その球面上で `T` に最も近い点は、**`J` から `T` へ向かう直線と球面の交点**です。つまり、

> **ベクトル J→E を、ベクトル J→T の向きへ回す。**

これは第 46 章の `FromToRotation` そのものです。道具はもうあります。

**なぜ末端から根元へなのか。** 根元から回すと、根元を大きく動かした結果を末端が引き受けることになり、全身がぐらぐら揺れます。末端から回すと、まず手首だけで届くところまで詰め、足りない分を肘、それでも足りない分を肩、という順になります。**動く量が最小限で済み、絵として自然**です。

## 48.2　実装（第 1 版）

```cpp
// AnimLib/include/anim/Ik.h（追記）

inline IkSolveResult SolveCcd(const Skeleton& s, Pose& local,
                              std::vector<Transform>& global,
                              const IkChain& chain, Vec3 target,
                              int maxIterations = 16, float tolerance = 1.0e-3f) {
    IkSolveResult r{};
    if (chain.Size() < 2) return r;
    const BoneIndex effector = chain.bones.back();

    for (int iter = 0; iter < maxIterations; ++iter) {
        r.iterations = iter + 1;

        // 末端の 1 つ手前から根元へ
        for (std::size_t k = chain.Size() - 1; k-- > 0; ) {
            ComputeGlobalPose(s, local.Locals(), global);
            const BoneIndex joint = chain.bones[k];
            const Vec3 jointPos   = global[joint].translation;
            const Vec3 toEffector = global[effector].translation - jointPos;
            const Vec3 toTarget   = target - jointPos;
            if (LengthSquared(toEffector) < 1.0e-12f) continue;

            const Quat delta = FromToRotation(toEffector, toTarget);
            SetGlobalRotation(s, local, global, joint, delta * global[joint].rotation);
        }

        ComputeGlobalPose(s, local.Locals(), global);
        r.residual = Length(target - global[effector].translation);
        if (r.residual < tolerance) { r.converged = true; break; }
    }
    return r;
}
```

**`k-- > 0` という書き方**について。`std::size_t` は符号なしなので `for (std::size_t k = n-1; k >= 0; --k)` は無限ループになります（`k = 0` から `--k` すると巨大な値）。`k-- > 0` は「`k` が 0 より大きいか判定してから 1 減らす」ので、ループ本体では `k` が `n-2` から `0` まで動き、`k == 0` の判定で抜けます。この本では第 43 章の三角形分割でも同じ形を使いました。

**エフェクタ自身は回さない。** `k` は `chain.Size()-2` から始まります。エフェクタのローカル回転を変えても、エフェクタの**位置**は動かないからです（位置は親の変換で決まる）。ここを間違えると、1 反復が無駄になります。

**`delta * global[joint].rotation` の順序**。第 6 章で決めた「列ベクトル × 行優先」の規約により、合成は**右のものが先**に適用されます。`delta` を左に置くのは「現在のグローバル回転を適用した**あとで**、さらに `delta` をワールド空間で掛ける」という意味です。逆にすると、`delta` がローカル軸で解釈されて別物になります。

## 48.4　バグ その 1 ―― 単位長から離れていくクォータニオン

犯人は `SetGlobalRotation` です。

```cpp
local[bone].rotation = Conjugate(parentRot) * newGlobalRot;   // 第 46 章
```

クォータニオンの積は、**両方が単位長なら結果も単位長**です。数学的には。しかし `float` の掛け算と足し算には丸め誤差があります。第 4 章で回転行列について測ったのと、まったく同じ現象です。

CCD は 1 反復あたり 3 関節、26 反復で 78 回。しかも `delta * global[joint].rotation` という積も毎回入るので、**同じクォータニオンに 150 回以上の積が積み重なります**。1 回あたり `1e-7` のずれでも、150 回で `1e-5`。実際にはもっと悪く、`9e-4` まで育ちました。

**なぜ長さが変わるのか。** 第 11 章の `Combine` を思い出します。

```cpp
Transform Combine(const Transform& parent, const Transform& child) {
    Transform out;
    out.rotation    = parent.rotation * child.rotation;
    out.scale       = MulPerComponent(parent.scale, child.scale);
    out.translation = parent.translation
                    + Rotate(parent.rotation, MulPerComponent(parent.scale, child.translation));
    return out;
}
```

`Rotate(q, v)` は `q` が単位長であることを前提にしています。単位長から `ε` ずれたクォータニオンで回すと、**ベクトルの長さが約 `1 + 2ε` 倍になります**。これが親から子へ掛け算で伝播する。ボーンが伸びるのは、この拡大です。

修正は 1 行です。

```cpp
inline void SetGlobalRotation(const Skeleton& s, Pose& local,
                              std::span<const Transform> global,
                              BoneIndex bone, const Quat& newGlobalRot) {
    const BoneIndex p = s.ParentOf(bone);
    const Quat parentRot = (p == kNoParent) ? QuatIdentity() : global[p].rotation;
    // 回転を掛け続けると単位長から離れる。ここで必ず正規化する
    local[bone].rotation = Normalize(Conjugate(parentRot) * newGlobalRot);
}
```

再測定：

| | ボーン長の最大誤差 |
|---|---|
| 正規化なし | `0.000904918` |
| 正規化あり | `0.000000358` |

**2500 倍の改善。** `float` の精度の限界近くまで来ました。

> **原則：クォータニオンを蓄積する場所には、必ず正規化を置く。**
>
> 第 4 章では「毎フレーム回転を掛け続けると誤差が溜まる」ことを 100,000 フレームで測りました。IK では**1 フレームの中で**同じことが起きます。反復ソルバは、時間軸を圧縮した誤差蓄積装置です。

`Normalize` は平方根 1 回と割り算 4 回。反復ソルバの中では無視できないコストですが、**正しさとの引き換えなら安い**。

## 48.5　バグ その 2 ―― 直したら収束しなくなった

正規化を入れて、収束テストを流し直します。

```
32 反復、残差 0.001570344
FAILED: r.converged
```

**収束しなくなりました。**

バグを直したら別のテストが赤くなる ―― これは珍しいことではありません。**ボーン長のドリフトが、収束を「助けて」いた**のです。ボーンが伸び縮みするノイズがランダムウォークのように働き、たまたま許容誤差の中に落ちた。26 反復で収束していたのは、そういう偶然でした。

**正しくなったコードの、本当の姿がこれです。** 反復ごとの残差を並べます。

```
 1 回: 0.857219636
 2 回: 0.366409421
 3 回: 0.018223787
 4 回: 0.001570344
 5 回: 0.001570614   ← 増えた
 6 回: 0.001570344
 7 回: 0.001570614   ← 2 値を往復している
 8 回: 0.001570344
```

4 反復で `0.00157` まで一気に落ちて、そこから**まったく動かなくなります**。しかも 2 つの値を交互に往復している ―― 完全な**リミットサイクル**です。

CCD は理論上、単調に収束します（各ステップがエフェクタと目標の距離を減らすか、そのまま）。距離が増える 5 反復目は、理論に反します。**数値誤差以外にありえません。**

## 48.6　容疑者を特定する

第 46 章 48.8 節で測ったあの表を思い出してください。

```
真の角度        acos 版の誤差
0.00100000    1.000e-03      ← 誤差 = 角度そのもの（何も回していない）
```

`FromToRotation` の `if (d > 0.99999f) return QuatIdentity();` ―― **0.004472 ラジアン（0.26 度）より小さい回転は起こりません**。

CCD が終盤で必要とする回転は、まさにそのサイズです。エフェクタが目標から `0.0015` の距離にあり、関節までの距離が 1 なら、必要な回転は約 `0.0015` ラジアン。**デッドゾーンの中です。** どの関節も「もう十分近い」と判断して何もしない。だから残りません。

推測を確かめます。**しきい値を変えて、プラトーの高さがそれに比例するかを見る。**

```cpp
// しきい値を差し替えられるようにしたテスト用の FromToRotationAcos で、
// 100 反復回したあとの残差を測る
```

| しきい値 `1−d` | デッドゾーンの角 | 100 反復後の残差 |
|---|---|---|
| `1e-03` | `0.044725` rad | `0.021997422` |
| `1e-04` | `0.014143` rad | `0.006571315` |
| `1e-05` | `0.004475` rad | `0.001570344` |
| `1e-06` | `0.001424` rad | `0.000518687` |
| `1e-07` | `0.000488` rad | `0.000538254` |
| 三角関数なし版 | ― | **`0.000000000`** |

**プラトーの高さは、デッドゾーンの角にほぼ比例しています**（比 0.35〜0.49）。これで因果関係は確定です。

最後の 2 行も重要です。しきい値を `1e-7` まで下げても残差は `5e-4` で止まり、`1e-6` のときより**悪化**しています。デッドゾーンを消しても、今度は `acos` そのものの精度が床になる。**しきい値の調整では解決しません。**

そして三角関数なし版は `0.000000000`。第 46 章で用意した実装に差し替えるだけで、問題は消えます。

## 48.8　届かない目標

CCD には 2 ボーン IK のような明示的なクランプがありません。それでも正しく振る舞います。

```cpp
TEST_METHOD(UnreachableTargetExtendsFully) {
    Skeleton s = MakeChain(5, 1.0f);        // 全長 4
    Pose p = Pose::FromRest(s);
    std::vector<Transform> g(s.BoneCount());
    const auto r = SolveCcd(s, p, g, IkChain{{0,1,2,3,4}}, {0,20,0}, 32, 1e-4f);

    Assert::IsFalse(r.converged);
    Assert::AreEqual(16.0f, r.residual, 1e-2f);    // 20 − 4
}
```

実測 `16.000002`。すべての関節が目標方向を向き、チェーンが一直線に伸びます。**「解がないときの答え」が、追加のコードなしで正しく出る**のは CCD の美点です。

ただし `converged == false` が返るので、`maxIterations` を無駄に回します。呼び出し側で「明らかに届かない」を先に弾くほうが速い場合があります。

```cpp
// チェーンの全長を事前に計算しておけば、1 回の比較で済む
if (LengthSquared(target - rootPos) > totalLength * totalLength) { /* 諦める or 1 回だけ解く */ }
```

第 24 章と同じで、**`sqrt` を避けて二乗のまま比較**します。

## 48.9　コスト ―― 内側の `ComputeGlobalPose`

ここまで測っていなかったコストがあります。48.2 のコードは、**関節を 1 つ回すたびに骨格全体のグローバルポーズを計算し直しています**。

```cpp
for (std::size_t k = chain.Size() - 1; k-- > 0; ) {
    ComputeGlobalPose(s, local.Locals(), global);   // ← ここ
    ...
}
```

骨格が `N` ボーン、チェーンが `M` ボーン、反復が `I` 回なら、`Combine` の呼び出しは **`I × M × N` 回**。ゲームの骨格は 60〜100 ボーン、脚の IK チェーンは 3 ボーンです。`8 × 3 × 67 = 1608` 回 ―― **99% が、IK が触っていないボーンの再計算です。**

必要なのは、**チェーンの中のボーンだけ**です。チェーンは直系なので、根元から末端へ 1 パス回せば済みます。

```cpp
// chain.bones は根元→末端の直系であることを前提にする。
// チェーン根元の親は IK が触らないので、global[parent] は有効なまま。
inline void UpdateChainGlobals(const Skeleton& s, const Pose& local,
                               std::span<Transform> global, const IkChain& chain) {
    for (std::size_t i = 0; i < chain.Size(); ++i) {
        const BoneIndex b = chain.bones[i];
        const BoneIndex p = s.ParentOf(b);
        global[b] = (p == kNoParent) ? local[b] : Combine(global[p], local[b]);
    }
}

inline IkSolveResult SolveCcdFast(const Skeleton& s, Pose& local,
                                  std::vector<Transform>& global,
                                  const IkChain& chain, Vec3 target,
                                  int maxIterations = 16, float tolerance = 1.0e-3f) {
    IkSolveResult r{};
    if (chain.Size() < 2) return r;
    const BoneIndex effector = chain.bones.back();
    ComputeGlobalPose(s, local.Locals(), global);      // 全体は最初の 1 回だけ

    for (int iter = 0; iter < maxIterations; ++iter) {
        r.iterations = iter + 1;
        for (std::size_t k = chain.Size() - 1; k-- > 0; ) {
            const BoneIndex joint = chain.bones[k];
            const Vec3 jointPos   = global[joint].translation;
            const Vec3 toEffector = global[effector].translation - jointPos;
            if (LengthSquared(toEffector) < 1.0e-12f) continue;

            const Quat delta = FromToRotation(toEffector, target - jointPos);
            SetGlobalRotation(s, local, global, joint, delta * global[joint].rotation);
            UpdateChainGlobals(s, local, global, chain);      // チェーンだけ
        }
        r.residual = Length(target - global[effector].translation);
        if (r.residual < tolerance) { r.converged = true; break; }
    }
    return r;
}
```

**チェーンの根元の親を IK が触らない**ことが、この最適化の前提です。チェーン外のボーンのグローバル変換は最初の 1 回から変わらないので、再計算する理由がありません。前提が壊れると（たとえば第 51 章のように腰を動かす場合）、動かしたあとで全体を計算し直す必要があります。

第 1 章の**③ 実装間の一致テスト**の出番です。

```cpp
TEST_METHOD(FastVersionMatchesReference) {
    for (int filler : {0, 20, 60}) {
        Rig rig = MakeBiped(filler);                 // 7 / 27 / 67 ボーン
        const IkChain chain{{rig.thighL, rig.shinL, rig.footL}};
        std::vector<Transform> g(rig.skel.BoneCount());

        Pose a = Pose::FromRest(rig.skel);
        SolveCcd    (rig.skel, a, g, chain, {-0.3f,0.3f,0.3f}, 8, 1e-4f);
        const Vec3 refPos = g[rig.footL].translation;

        Pose b = Pose::FromRest(rig.skel);
        SolveCcdFast(rig.skel, b, g, chain, {-0.3f,0.3f,0.3f}, 8, 1e-4f);

        Assert::IsTrue(Length(refPos - g[rig.footL].translation) < 1e-5f);
    }
}
```

実測 ―― **3 通りとも位置差 `0.000000000`**。ビット単位で一致しています。当然です。同じ順序で同じ計算をしていて、省いたのは結果に影響しない部分だけなのですから。

速度：

| 骨格のボーン数 | 全体再計算 | チェーンのみ | 倍率 |
|---|---|---|---|
| 7 | `3.777` µs | `2.114` µs | 1.8× |
| 27 | `12.703` µs | `2.599` µs | 4.9× |
| 67 | `30.686` µs | `3.469` µs | **8.8×** |

全体再計算はボーン数に比例して重くなります（`3.8 → 12.7 → 30.7`）。チェーンのみはほぼ横ばい（`2.1 → 2.6 → 3.5`）。**67 ボーンの骨格で 8.8 倍。** キャラクター 1 体につき脚 2 本 + 腕 2 本の IK を回すなら、フレームあたり `123 µs → 14 µs` の差です。

チェーンのみ版がわずかに増えているのは、`Pose::FromRest`（ベンチマークのループ内で毎回作っている）が骨格サイズに比例するためで、ソルバ自体のコストではありません。

## 48.10　CCD の癖

CCD は単純で丈夫ですが、性格があります。

**根元が動きにくい。** 末端から順に回すので、末端に近い関節ほど大きく動きます。手先をちょっと動かしたいだけなら手首だけが曲がり、肩は動かない ―― これは多くの場合、望ましい挙動です。

**逆に、根元を大きく動かしてほしい場面では不利。** 長いチェーン（尻尾、触手）で「全体をなめらかに曲げたい」ときには、末端だけがくねくねして根元が伸びたままになりがちです。第 49 章の FABRIK は、この点で挙動が違います。

**回転が「ねじれる」ことがある。** CCD は「エフェクタが目標に届く」ことしか見ていないので、途中の関節が不自然にねじれた解を返すことがあります。膝が横を向く、肘が裏返る。これを止めるのが第 50 章の関節制限です。

**反復回数は打ち切りが前提。** ゲームでは `maxIterations` を 4〜8 に固定し、収束しなければそのまま使います。1 フレームで届かなくても、次のフレームでまた続きを解けばよい ―― ただし**そのためには、前フレームのポーズではなく、その時点のアニメーションが作った素のポーズから解き直す**必要があります（第 46 章 46.3）。「前回の続きから」は、目標が動き続ける実際のゲームでは正しく機能しません。

## この章のまとめ

- CCD は「**1 関節ずつ、末端から根元へ、`FromToRotation` で目標方向を向ける**」を繰り返すだけ。任意の長さのチェーンを扱える。
- **エフェクタ自身は回さない**（回しても位置が変わらない）。ループは `chain.Size()-2` から `0` まで。
- **バグ その 1**：`SetGlobalRotation` にクォータニオンの正規化がなく、ボーン長が **`0.000904918`** ずれた。反復ソルバは 1 フレームの中で 150 回以上の積を重ねる ―― **時間軸を圧縮した誤差蓄積装置**。`Normalize` を 1 行入れて `0.000000358` へ。
- **バグ その 2**：正規化を入れたら、今度は**収束しなくなった**（`0.00157` でリミットサイクル）。ドリフトのノイズが、たまたま収束を助けていた。**バグを直すと別のバグが顔を出す。**
- 原因は `FromToRotation` の `d > 0.99999f` 早期リターン。**しきい値を変えるとプラトーの高さがそれに比例する**（`0.0447 rad → 0.0220`、`0.00447 → 0.00157`、`0.00142 → 0.00052`）ことで因果関係を確定。しきい値をさらに下げても `acos` 自身の精度が床（`5e-4`）になる。**調整では解けない。**
- 第 46 章の三角関数なし版に差し替えて、**残差 `0.000000000`**。7 反復で `float` の床まで到達。
- 内側ループの `ComputeGlobalPose` は `I × M × N` 回の `Combine` を呼ぶ。**チェーンだけ更新すれば `I × M × M`**。67 ボーンの骨格で **8.8 倍**、結果はビット単位で一致。
- CCD は**末端がよく動き、根元が動きにくい**。関節がねじれた解を返すことがある（第 50 章で制限する）。

次章では、まったく違うアプローチの **FABRIK** を書きます。回転ではなく**位置**を直接いじる解法で、CCD と実測で比べます ―― 反復回数と、1 反復あたりのコストの両方で。
