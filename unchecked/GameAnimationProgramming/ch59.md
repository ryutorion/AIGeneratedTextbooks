# 第 59 章　更新の間引きと LOD

**この章で作るもの**：遠くのキャラクターの更新を減らす仕組み。**更新頻度の間引き**と、**ボーン LOD**。

第 IX 部の 7 章は「速くやる」話でした。この章は「**やらない**」話です。そして ―― たいてい、これが一番効きます。

---

## 59.1　やらないことの効果

第 52 章で測った 1 体の更新コストは `6.734` µs。第 53 章の SIMD で 3 倍、第 56 章の圧縮で 2 倍、第 57 章の並列化で 2 倍 ―― かけ合わせて 12 倍にできたとしましょう。1 体 `0.56` µs。1000 体で `0.56` ms。立派な成果です。

しかし、**更新頻度を 4 分の 1 にすれば、それだけで 4 倍**です。しかも実装は数十行で、SIMD もマルチスレッドも要りません。

**なぜそれが許されるのか。** 遠くのキャラクターは、画面上で数ピクセルしかありません。

```
距離 50 m のキャラクター（身長 1.8 m）
  垂直視野 60 度、画面高さ 1080 px のとき
  → 画面上の高さ ≈ 1.8 / (2 × 50 × tan(30°)) × 1080 ≈ 34 ピクセル

  1 ボーンあたり ≈ 0.5 ピクセル
```

**0.5 ピクセルの世界で、60 fps の滑らかさは意味を持ちません。**

第 IX 部の最適化は「同じ結果を速く出す」ものでした。この章だけは違います。**結果を落とします。** だから、**落ちる量を測る**ことが、この章の主題になります。

---

## 59.2　間引きの 3 つのやり方

`interval` フレームに 1 回だけアニメーションをサンプルし、残りのフレームをどう埋めるか。3 通りあります。

**① 保持（Hold）** ―― 最後に計算したポーズをそのまま使う。実装 1 行。カクつく。

**② 外挿（Extrapolate）** ―― 前回と前々回のポーズから、その先を予測する。

```
out = Lerp(prev, curr, 1.0 + phase/interval)
```

**③ 先読み補間（LookAhead）** ―― **次の更新時刻のポーズを先に計算しておき**、そのあいだを補間する。

```
更新時 t0: curr = pose(t0)、next = pose(t0 + interval·dt) を両方持つ
その後 :   out = Lerp(curr, next, phase/interval)
```

③ は 1 回の更新で 2 つのポーズが要るように見えますが、**前回の `next` が今回の `curr` になる**ので、サンプル回数は 1 回のままです。

```cpp
struct DecimatedPlayer {
    const Clip* clip = nullptr;
    int   interval = 1;
    SkipMode mode = SkipMode::LookAhead;
    Pose  prev, curr, next, out;
    int   phase = 0;
    float dt = 1.0f/60.0f;
    float time = 0.0f;

    void Init(const Clip& c, std::size_t bones){
        clip = &c;
        prev = curr = next = out = Pose(bones);
        clip->Sample(0.0f, curr);
        prev = curr;
        next = curr;                     // ← 最初の Step で curr に入る
        phase = 0; time = 0.0f;
    }

    const Pose& Step(){
        if (phase == 0) {
            prev = curr;
            if (mode == SkipMode::LookAhead) {
                curr = next;                                 // 前回の先読みが今の値
                clip->Sample(time + dt*interval, next);      // 次の更新時刻を先読み
            } else {
                clip->Sample(time, curr);
            }
        }
        const float f = static_cast<float>(phase) / interval;
        switch (mode) {
        case SkipMode::Hold:        out = curr; break;
        case SkipMode::Extrapolate: LerpPose(prev, curr, 1.0f + f, out); break;
        case SkipMode::LookAhead:   LerpPose(curr, next, f, out); break;
        }
        time += dt;
        phase = (phase + 1) % interval;
        return out;
    }
};
```

**`Init` で `next = curr` にしているのが、この構造で唯一のトリッキーな点です。** ここを `clip->Sample(dt*interval, next)` にすると、最初の `Step()` で `curr = next` としたときに **1 更新ぶん先のポーズ**が入り、以降ずっと遅れたままになります。

（最初に書いたときは、まさにそう書いていました。`interval = 1` でも誤差が `0.038141` ―― ちょうど 1 フレームぶんの移動量 ―― 出ていて気づきました。**`interval = 1` は「間引かない」なので、誤差ゼロでなければおかしい**。**恒等ケースをテストに入れておくと、こういうずれが即座に出ます。**)

## 59.3　測定：どれだけ誤差が出るか

60 fps で 2 秒間、60 ボーンのキャラクターを走らせ、**ワールド位置の最大誤差**を測ります。

```cpp
TEST_METHOD(DecimationErrorSweep) {
    for (int interval : {1,2,3,4,6,8,12}) {
        for (int m = 0; m < 3; ++m) {
            DecimatedPlayer p; p.interval = interval; p.mode = static_cast<SkipMode>(m);
            p.Init(clip, s.BoneCount());
            float worst = 0.0f;
            for (int f = 0; f < 120; ++f) {
                const Pose& got = p.Step();
                clip.Sample(f/60.0f, ref);
                /* 両方の階層を解いて、全ボーンのワールド位置を比較 */
            }
            /* 記録 */
        }
        if (interval >= 4) Assert::IsTrue(err[LookAhead] < err[Hold]);
    }
}
```

| 更新間隔 | 保持のみ | 外挿 | **先読み補間** |
|---|---|---|---|
| 1（間引かない） | `0.000005` | `0.000005` | `0.000005` |
| 2 | `0.107236` | `0.038141` | **`0.000005`** |
| 3 | `0.209792` | `0.076132` | **`0.017093`** |
| 4 | `0.310828` | `0.138328` | **`0.025561`** |
| 6 | `0.515456` | `0.341007` | **`0.050148`** |
| 8 | `0.621644` | `0.560036` | **`0.100499`** |
| 12 | `0.944945` | `0.920993` | **`0.216796`** |

単位はメートル。

**先読み補間が圧倒的です。** 間隔 4 で、保持の `0.311` m に対して `0.026` m ―― **12 倍良い**。間隔 12 でも `0.217` m で、保持の `0.945` m より 4 倍良い。

**外挿は思ったほど効きません。** 間隔 8 以上ではほぼ「保持」と同じです。理由は明確で、**アニメーションは直線的に動かない**からです。歩行の腕の振りは正弦波に近く、折り返し点で外挿すると**行き過ぎます**。第 51 章のフィードバックループと同じ形の失敗です。

**間隔 2 での `0.000005`** は測定の床（`float` の精度）です。2 フレームおきに更新して、あいだを線形補間 ―― サンプル位置の中点なので、たまたまほぼ正確になっています。

## 59.4　先読み補間の代償：遅延

先読み補間はタダではありません。**`interval` フレームぶんの遅延**が入ります。

現在のフレームで表示しているのは「前回の更新時刻のポーズ」と「次の更新時刻のポーズ」の補間です。**未来のポーズを使っている**ので、正確には遅延ではなく「未来を先取りしている」のですが、いずれにせよ**入力に対する反応が interval フレームぶん鈍ります**。

```
間隔 4（15 Hz 更新）→ 最大 4 フレーム = 67 ms の反応遅れ
```

**主人公には使えません。** プレイヤーがボタンを押してから攻撃モーションが始まるまで 67 ms 遅れたら、操作感が壊れます。

しかし、**距離に応じて間引く**なら問題ありません。

| 距離 | 更新間隔 | 更新頻度 | 遅延 |
|---|---|---|---|
| 主人公 / 会話相手 | 1 | 60 Hz | 0 |
| 〜10 m | 1 | 60 Hz | 0 |
| 10〜25 m | 2 | 30 Hz | 33 ms |
| 25〜50 m | 4 | 15 Hz | 67 ms |
| 50 m 〜 | 8 | 7.5 Hz | 133 ms |
| 画面外 | 更新しない | ― | ― |

**遠くのキャラクターの反応が 133 ms 遅れても、誰も気づきません。**

**LOD の切り替わりに注意。** 距離が境界をまたぐたびに `interval` が変わると、そこでポーズが飛びます。対策は 2 つ。

1. **ヒステリシス**：上がるときと下がるときで境界をずらす（25 m で 2→4、23 m で 4→2）
2. **切り替え時に補間する**：`interval` が変わったら、0.2 秒かけて前のポーズからブレンドする（第 39 章のクロスフェード）

**LOD の境界は、必ず往復する。** キャラクターが 25 m 付近をうろうろしたら、毎フレーム切り替わります。ヒステリシスは必須です。

## 59.5　測定：どれだけ速くなるか

```cpp
for (int interval : {1,2,4,8}) {
    DecimatedPlayer p; p.interval = interval; p.mode = SkipMode::LookAhead;
    /* Step() + ComputeGlobalPose() を 1 フレームぶんとして計測 */
}
```

1 体・1 フレームあたり：

| 更新間隔 | 時間 | 対 interval=1 |
|---|---|---|
| 1 | `6.023` µs | 1.00× |
| 2 | `3.743` µs | 1.61× |
| 4 | `2.410` µs | 2.50× |
| 8 | `1.772` µs | 3.40× |

**間隔 8 で 3.4 倍。** 8 倍にならないのは、**間引けない処理が残っている**からです。

- `LerpPose`（60 ボーンの補間）は**毎フレーム**必要
- `ComputeGlobalPose`（階層解決）も**毎フレーム**必要（描画に使うので）
- 間引けるのは `Clip::Sample`（キー探索と補間）だけ

つまり、**間引きが効くのはサンプリングのコストの部分だけ**です。第 56 章で圧縮によってサンプリングを 2 倍速くしてしまった今、この比率はさらに下がります。**最適化どうしは足し算にならない**（第 56 章）の、もう 1 つの例です。

### もっと間引く

階層解決まで間引くこともできます。**グローバルポーズを補間する**のです。

```
毎フレーム:  globalPose = LerpTransforms(globalCurr, globalNext, f)
```

こうすると `ComputeGlobalPose` も間引けます。ただし ―― **グローバル変換の補間は、ローカル変換の補間と同じ結果になりません。** 回転を含む階層を線形補間すると、ボーン長がわずかに縮みます（第 21 章の LBS のキャンディラッパー現象と同じ原理です）。

遠景では見えませんが、**性質が変わる**ことは意識しておく必要があります。第 IX 部の他の最適化が「同じ結果を速く」だったのに対し、これは「違う結果を速く」です。

## 59.6　ボーン LOD

もう 1 つの軸は、**更新するボーンを減らす**ことです。

指、髪、服、顔 ―― 遠くでは見えないボーンがたくさんあります。それらを**レストポーズのまま固定**すれば、その分の計算が丸ごと消えます。

第 13 章の不変条件 `parents[i] < i` があるので、**深さで切る**のが簡単です。

```cpp
std::vector<int> ComputeDepths(const Skeleton& s){
    std::vector<int> depth(s.BoneCount(), 0);
    for (std::size_t i = 0; i < s.BoneCount(); ++i) {
        const BoneIndex p = s.ParentOf(static_cast<BoneIndex>(i));
        depth[i] = (p == kNoParent) ? 0 : depth[p] + 1;      // 親は必ず先に処理済み
    }
    return depth;
}
```

`parents[i] < i` のおかげで、**1 パスで深さが計算できます**。第 13 章で決めた不変条件が、また効きました。

測定します。深さ `cut` 未満のボーンだけを更新し、それ以外はレストポーズのまま。

| 更新するボーン | 更新数 | ワールド位置の最大誤差 |
|---|---|---|
| 深さ 8 未満 | 59/60 | `0.000000` m |
| 深さ 7 未満 | 58/60 | `0.023306` m |
| 深さ 6 未満 | 56/60 | `0.091303` m |
| 深さ 5 未満 | 51/60 | `0.138971` m |
| 深さ 4 未満 | 40/60 | `0.181893` m |
| 深さ 3 未満 | 25/60 | `0.351911` m |
| 深さ 2 未満 | 9/60 | `0.501996` m |
| 深さ 1 未満 | 1/60 | `0.702965` m |

**深さ 5 未満（51/60 ボーン）で誤差 14 cm。深さ 4 未満（40/60）で 18 cm。**

**効率が悪いことに気づきます。** ボーンを 15% 減らして 14 cm、33% 減らして 18 cm。一方、更新間隔 4 の先読み補間は **2.6 cm で 2.5 倍**でした。

**更新頻度の間引きのほうが、圧倒的に費用対効果が良い。**

理由は明快です。ボーン LOD で切るのは末端のボーンですが、**この本のテスト骨格はランダムな親子関係で作られていて、末端でも大きく動くボーンが含まれています**。実際のリグなら、末端は指や髪で、動く量が小さい。

**それでも、順序としては「頻度が先、ボーンが後」です。**

- 頻度の間引きは**すべてのボーンに一様に効く**
- ボーン LOD は**そのボーンだけに効く**が、**アセット側の作り込みが必要**（どのボーンを切ってよいかは、リグごとに人が決める）

### ボーン LOD の実務的なやり方

深さで切るのは乱暴です。実際には**リグにメタデータを持たせます**。

```cpp
struct BoneLodInfo {
    std::uint8_t minLod = 0;      // このレベル以上で更新する
};
// LOD0: 全ボーン（近景）
// LOD1: 指と顔を除く（中景）
// LOD2: 胴体・四肢の主要ボーンのみ（遠景）
// LOD3: 腰と足だけ（超遠景、あるいはインポスター）
```

**ボーンの並び順を LOD 順にしておく**と、実装が劇的に単純になります。

```
添字 0..19  : LOD3 でも更新する（腰、脚）
添字 20..39 : LOD2 から更新（腕、胸）
添字 40..55 : LOD1 から更新（首、頭）
添字 56..79 : LOD0 のみ（指、髪、顔）
```

こうすると、更新は **`for (i = 0; i < lodBoneCount[level]; ++i)`** という単なるループの上限になります。分岐もマスクも要りません。

ただし、この並べ替えは**第 13 章の不変条件 `parents[i] < i` を保ったまま**行う必要があります。「LOD 順」と「トポロジカル順」を同時に満たす並べ替えが存在するかは、リグの構造次第です（親が子より高い LOD レベルに属していれば矛盾します ―― 通常はそうならないので大丈夫ですが、**検証は必要**です)。

```cpp
TEST_METHOD(LodOrderPreservesTopology) {
    // 親は必ず子より小さい添字、かつ 親の minLod <= 子の minLod
    for (BoneIndex i = 0; i < s.BoneCount(); ++i) {
        const BoneIndex p = s.ParentOf(i);
        if (p == kNoParent) continue;
        Assert::IsTrue(p < i);
        Assert::IsTrue(lod[p].minLod <= lod[i].minLod);
    }
}
```

## 59.7　もっと粗い LOD

さらに先があります。この本では実装しませんが、地図として。

**① 画面外カリング。** 視錐台の外のキャラクターは更新しない。ただし**完全に止めると、画面に入った瞬間にポーズが飛びます**。時刻だけは進めておき、入ったフレームでサンプルする。あるいは 1 秒に 1 回だけ更新する。

**② インポスター。** 十分遠いキャラクターは、事前レンダリングした板ポリゴンに置き換える。アニメーションの更新は完全にゼロになります。

**③ ポーズの共有。** 同じアニメーションを同じ時刻で再生している群衆は、**同じポーズを共有できます**。100 体の兵士が行進しているなら、時刻をいくつかのグループに丸めて、グループごとに 1 回だけ計算する。パレットも共有できます。

**④ 更新の分散。** 100 体を 4 フレームに分けて、1 フレームあたり 25 体ずつ更新する。総コストは変わりませんが、**フレーム時間のばらつきが小さくなります**。60 fps を守るうえでは、平均より最悪値のほうが重要です。

**④ は特に重要です。** 「平均 8 ms、たまに 20 ms」より「常に 10 ms」のほうが、ゲームとしては良い。**最適化の目標は平均ではなくフレーム落ちの根絶**です。

## この章のまとめ

- 第 IX 部の他の章は「速くやる」、この章は「**やらない**」。更新頻度を 4 分の 1 にすれば、それだけで 4 倍で、実装は数十行。
- **この章だけは結果が落ちる。** だから**落ちる量を測る**のが主題。
- 間引いたフレームの埋め方は 3 通り。実測（ワールド位置の最大誤差、単位 m）：

  | 間隔 | 保持 | 外挿 | 先読み補間 |
  |---|---|---|---|
  | 4 | `0.311` | `0.138` | **`0.026`** |
  | 12 | `0.945` | `0.921` | **`0.217`** |

- **先読み補間が圧倒的**（間隔 4 で保持の 12 倍良い）。**外挿は効かない** ―― アニメーションは直線的に動かず、折り返し点で行き過ぎる（第 51 章と同じ形の失敗）。
- 実装で唯一トリッキーなのは `Init` の `next = curr`。ここを間違えると 1 更新ぶん遅れ続ける。**`interval = 1`（恒等ケース）をテストに入れておくと即座に出る。**
- 先読み補間の代償は **`interval` フレームぶんの反応遅れ**。主人公には使えないが、**距離に応じて間引く**なら問題ない（50 m 先の 133 ms 遅れは誰も気づかない）。
- **LOD の境界は必ず往復する。** ヒステリシスか、切り替え時のブレンドが必須。
- 速度は間隔 8 で **3.40 倍**。8 倍にならないのは `LerpPose` と `ComputeGlobalPose` が毎フレーム必要だから。**間引けるのはサンプリングだけ** ―― 第 56 章で圧縮によってそこを 2 倍速くした分、効き目が下がっている（**最適化どうしは足し算にならない**）。
- ボーン LOD は**深さで切れる**（第 13 章の `parents[i] < i` のおかげで深さが 1 パスで求まる）。実測、51/60 ボーンで `0.139` m、40/60 で `0.182` m。
- **更新頻度の間引きのほうが費用対効果が高い**（2.6 cm で 2.5 倍 対 14 cm で 15% 削減）。順序は「**頻度が先、ボーンが後**」。
- ボーン LOD は**リグのメタデータ**として持ち、**ボーンを LOD 順に並べておく**とループの上限を変えるだけになる。ただし**第 13 章の不変条件を保てるか、テストで検証すること**。
- さらに先：画面外カリング（時刻だけは進める）、インポスター、**ポーズの共有**（群衆で時刻を丸める）、**更新の分散**。
- **最適化の目標は平均ではなくフレーム落ちの根絶。** 「平均 8 ms、たまに 20 ms」より「常に 10 ms」。

## 第 IX 部を終えて

8 章かけて、1 体 `6.734` µs のアニメーション更新に手を入れてきました。効果をまとめます。

| 章 | 手段 | 効果 | 副作用 |
|---|---|---|---|
| 52 | データ指向レイアウト | **0.36〜1.15×** | ―（SIMD の前提） |
| 53 | SIMD（階層解決） | 1.51〜**3.80×** | FMA でビット一致が崩れる |
| 53 | SIMD（スキニング） | 0.49× → **4.61×** | ロード時に頂点の並べ替えが要る |
| 54〜56 | 圧縮 | サイズ **12.7×**、サンプリング **2.04×** | ワールド位置 16.5 mm の誤差 |
| 57 | マルチスレッド | **1.92×**（2 コア） | 共有状態の排除が必要 |
| 58 | GPU スキニング | 転送量 **340×** | CPU 側に結果が残らない |
| 59 | 更新の間引き | **3.40×** | 反応が `interval` フレーム遅れる |

第 IX 部で繰り返し出てきた教訓を、最後に並べます。

**測るまで分からない。** データ指向にしたら 2.7 倍遅くなり（第 52 章）、SIMD にしたら 2 倍遅くなり（第 53 章）、圧縮したら 2 倍速くなりました（第 56 章）。**3 つとも予想と逆でした。** 「一般にこうすると速くなる」という知識は、測定の代わりにはなりません。

**前提条件と最適化は別物。** データ指向レイアウトは、それ自体では遅くなります。SIMD の前提条件としてのみ意味を持つ。**前提だけ整えて本体をやらなければ、損をするだけ**です。

**レイアウトが性能を決める。** ギャザーからブロードキャストへ変えただけで 9.4 倍（第 53 章）。命令は同じ、変えたのはデータの並びだけでした。

**最適化どうしは足し算にならない。** 圧縮でキャッシュに乗るようにしたら、ヒント付き探索の効果が 2.94 倍から 1.19 倍に落ちました（第 56 章）。間引きの効果も、圧縮のあとでは小さくなります（第 59 章）。**すべて入れたあとで、もう一度測る。**

**測り方を疑う。** 第 52 章で単位長のずれを一致度と取り違え、第 55 章で `acos` の分解能を実装の誤差と取り違え、第 56 章で Loop の折り返しを圧縮の誤差と取り違えました。**3 回とも、コードは最初から正しかった。** 一致テストが赤いとき、容疑者は 3 人 ―― 新実装、旧実装、**そして測り方**。

**測っていないことは、測っていないと書く。** マルチスレッドは 2 コアでしか測っていません。GPU スキニングは実機で走らせていません。**数字がないところに数字を書かない。**

**そして、やらないのが一番速い。** 第 59 章の間引きは、第 52〜58 章のすべてより実装が簡単で、効果が大きい。**最適化を始める前に、その仕事が本当に必要かを問う。**
