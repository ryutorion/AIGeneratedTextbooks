# 第 60 章　アニメーションイベント

**この章で作るもの**：クリップの特定の時刻で「何かを起こす」仕組み。足音、エフェクト、攻撃判定の発生。

そして、この本で 4 度目の同じ問題に出会います ―― **時刻の折り返しとイベントの発火を、別々の場所で決めると壊れる**。今度は、その問題を**構造的に消す**方法を採ります。

---

## 60.1　アニメーションが「起こす」もの

ここまでの 59 章で作ってきたのは、**ポーズを計算する仕組み**でした。しかしゲームにおけるアニメーションは、絵を作るだけではありません。

- **足が地面についた瞬間**に、足音を鳴らし、土煙のエフェクトを出す
- **剣を振り下ろす途中**の 0.2 秒間だけ、当たり判定を有効にする
- **投擲モーションの手を離す瞬間**に、手榴弾を生成する
- **抜刀のタイミング**で、武器をソケットに付け替える（第 61 章）

これらは全部「**クリップの、この時刻で**」と指定するのが自然です。ゲームロジック側で `if (animTime > 0.35f)` と書くこともできますが、

- クリップを差し替えたらタイミングがずれる
- 再生速度を変えたら追随しない
- ブレンド中にどちらのクリップの時刻なのか分からなくなる
- **アーティストが調整できない**

最後の理由が決定的です。「足音のタイミングが半フレーム早い」を直せるのは、プログラマではなくアニメータであるべきです。第 45 章のステートマシン、第 50 章の関節制限、第 56 章の圧縮設定と同じ結論 ―― **データとして持ち、ツールで編集できるようにする**。

## 60.2　データ構造

```cpp
// AnimLib/include/anim/AnimEvent.h
#pragma once
#include "anim/Clip.h"

namespace anim {

struct AnimEvent {
    float         time    = 0.0f;   // クリップ内の時刻
    std::uint32_t id      = 0;      // 何のイベントか
    float         payload = 0.0f;   // 付随する値（音量、強さ、など）
};

struct FiredEvent {
    std::uint32_t id      = 0;
    float         payload = 0.0f;
    float         time    = 0.0f;   // クリップ内の時刻
    double        at      = 0.0;    // 折り返さない時刻（並べ替えのキー）
};
}
```

**`id` を文字列ではなく `std::uint32_t` にする**のは、比較を速くするためです。1 フレームに数十回の比較が起きるので、`std::string` の比較は避けたい。ツール側では文字列名を使い、ビルド時にハッシュへ変換します（`"footstep_left"` → `0x8f3a...`）。

**`payload` を `float` 1 個に絞った**のは意図的です。「イベントに任意のデータを持たせたい」という要求は必ず出ますが、そこで `std::variant` や `std::any` を入れると、**アニメーションシステムがゲームロジックの型を知ることになります**。境界は狭く保ち、複雑なデータが要るなら `id` から引ける別のテーブルを用意します。

**`FiredEvent::at`（折り返さない時刻）** の意味は、60.5 節で分かります。

## 60.3　素朴な実装と、その罠

「前フレームの時刻と今フレームの時刻のあいだにあるイベントを発火する」―― これが基本です。

```cpp
// 素朴な版
void Collect(float prevTime, float currTime, std::vector<FiredEvent>& out) const {
    for (const AnimEvent& e : events_)
        if (e.time >= prevTime && e.time < currTime)
            out.push_back({e.id, e.payload, e.time});
}
```

問題は 4 つあります。

**① ループをまたぐと、`currTime < prevTime` になる。** 2 秒のクリップで `prevTime = 1.9`、`currTime = 0.05`。この条件式では何も発火しません。**1.9 秒から 2.0 秒のあいだにあるイベントが、毎周回ごとに取りこぼされます。**

**② dt が大きいとクリップを飛び越える。** ロード直後のヒッチで `dt = 0.5` 秒、クリップが 0.6 秒なら、ほぼ 1 周ぶん飛びます。`dt = 5` 秒なら 8 周。**それぞれの周回でイベントが発火しなければなりません。**

**③ 逆再生。** `speed < 0` なら区間は逆向きで、発火の順序も逆になるべきです。

**④ PingPong。** 折り返しの前後で方向が変わります。

第 28 章で `PlaybackStep` を作ったとき、まさにこの種の問題に対処しました ―― 「ループ回数とサンプル時刻を別々の場所で計算すると境界でずれる」。第 45 章のステートマシンでも同じ構造のバグを踏み、第 50 章のルックアットでも「制御したい量と制御している量が違う」形で出会いました。

**今回は、問題そのものを消します。**

## 60.4　折り返さない時刻

`PlaybackStep` は「折り返した後の時刻」を持っています。`previousTime = 1.9`、`currentTime = 0.05`、`loopsCompleted = 1`。ここから元の区間を**復元**しようとするから難しくなります。

**復元しなければいい。折り返す前の値を、そのまま持っておく。**

```cpp
struct PlaybackStep {
    float previousTime = 0.0f;
    float currentTime  = 0.0f;
    int   loopsCompleted = 0;
    bool  finished = false;
    // 第 60 章で追加：折り返す前の連続時刻。イベント収集はこちらを使う。
    double unwrappedFrom = 0.0;
    double unwrappedTo   = 0.0;
};
```

`ClipPlayer` 側の変更は 4 行です。

```cpp
PlaybackStep Update(float dt){
    /* ... */
    step.previousTime  = (float)time_;
    step.unwrappedFrom = unwrapped_;                    // ← 追加
    double next = time_ + (double)dt * (double)speed_;
    unwrapped_ += (double)dt * (double)speed_;          // ← 追加
    step.unwrappedTo = unwrapped_;                      // ← 追加
    /* ... 従来どおり折り返す ... */
}
```

**`double` にしている**のは、長時間の再生で精度が落ちないようにするためです。`float` だと 1 時間（3600 秒）再生した時点で分解能が `0.00024` 秒 ―― 60 fps の 1 フレームが `0.0167` 秒なので、まだ足りますが、余裕はありません。`double` なら数千年もちます。第 26 章で `ClipPlayer::time_` を `double` にしたのと同じ判断です。

**Once モードだけは例外です。** 末尾で止まったあとも `unwrapped_` が進み続けると、区間が意味を失います。クランプします。

```cpp
case LoopMode::Once:
    if (next >= d) { next = d; step.finished = true; }
    if (next < 0.0) { next = 0.0; step.finished = true; }
    unwrapped_ = next;              // 折り返さない時刻もクランプする
    step.unwrappedTo = next;
    break;
```

## 60.5　イベントが「折り返さない時刻軸のどこに現れるか」

発想を変えます。

> **クリップ内時刻 `e` のイベントは、折り返さない時刻軸の上で、どこに現れるか。**

再生モードごとに、これは単純な式で書けます。

**Loop**：クリップは `d` 秒ごとに繰り返すので、イベントは `e + k·d`（`k` は任意の整数）に現れます。

```
折り返さない時刻 →
    0        d        2d       3d
    |--e-----|--e-----|--e-----|
       ↑        ↑        ↑
     e+0d     e+1d     e+2d
```

**Once**：1 回だけ、`e` に現れます。

**PingPong**：`[0, d)` は前進、`[d, 2d)` は後退 … と交互になります。区間 `n` が偶数なら `n·d + e`、奇数なら `(n+1)·d − e` です。

```
    0        d        2d       3d
    |--e---->|<---e---|--e---->|
       ↑           ↑     ↑
      0d+e      2d-e   2d+e
```

あとは、**その値が区間 `[from, to)` に入るかを調べるだけ**です。

```cpp
inline void CollectEventsUnwrapped(const EventTrack& track, LoopMode mode, float duration,
                                   double from, double to, std::vector<FiredEvent>& out){
    if (duration <= 0.0f || from == to) return;
    const double d = duration;
    const bool forward = (to > from);
    const double lo = forward ? from : to;
    const double hi = forward ? to   : from;
    const std::size_t begin = out.size();

    switch (mode) {
    case LoopMode::Once:
        for (const AnimEvent& e : track.All())
            if (e.time >= lo && e.time < hi)
                out.push_back({e.id, e.payload, e.time, (double)e.time});
        break;

    case LoopMode::Loop:
        for (const AnimEvent& e : track.All()) {
            // e + k·d ∈ [lo, hi) となる整数 k をすべて拾う
            long long k = static_cast<long long>(std::ceil((lo - e.time) / d));
            for (double at = e.time + (double)k * d; at < hi; at = e.time + (double)(++k) * d)
                if (at >= lo) out.push_back({e.id, e.payload, e.time, at});
        }
        break;

    case LoopMode::PingPong: {
        const long long n0 = static_cast<long long>(std::floor(lo / d));
        const long long n1 = static_cast<long long>(std::floor((hi - 1e-12) / d));
        for (long long n = n0; n <= n1; ++n) {
            const double a = std::fmax(lo, (double)n * d);
            const double b = std::fmin(hi, (double)(n+1) * d);
            if (a >= b) continue;
            const bool even = ((n % 2) + 2) % 2 == 0;
            for (const AnimEvent& e : track.All()) {
                const double at = even ? ((double)n * d + e.time)
                                       : ((double)(n+1) * d - e.time);
                if (at >= a && at < b) out.push_back({e.id, e.payload, e.time, at});
            }
        }
        break;
    }
    }

    // 通過した順に並べる（逆再生なら降順）
    auto first = out.begin() + static_cast<std::ptrdiff_t>(begin);
    if (forward) std::stable_sort(first, out.end(),
                     [](const FiredEvent& a, const FiredEvent& b){ return a.at < b.at; });
    else         std::stable_sort(first, out.end(),
                     [](const FiredEvent& a, const FiredEvent& b){ return a.at > b.at; });
}
```

**60.3 で挙げた 4 つの問題が、すべて消えました。**

- ループをまたぐ → `k` が 1 増えるだけ
- 巨大な `dt` → `k` のループが何周かするだけ
- 逆再生 → `lo` と `hi` を入れ替えて、最後に降順で並べるだけ
- PingPong → 三角波の式を書くだけ

**分岐が「再生モードごとの 3 通り」に収束し、境界の特別扱いが 1 つもありません。**

`((n % 2) + 2) % 2` は、`n` が負でも正しい剰余を得るためのイディオムです。C++ の `%` は負の被除数に対して負を返すので、`-3 % 2 == -1`。そのままでは偶奇判定が壊れます。**逆再生で `n` が負になる**ので、これは必要です。

## 60.6　単体テスト：dt に依存しないこと

このシステムの**本質的な性質**は 1 つです。

> **同じ時間だけ進めたなら、`dt` の刻み方によらず、発火するイベントの集合は同じ。**

これをテストにします。基準は「1 ミリ秒刻みで 10 秒」、比較対象は「1/120 秒刻み」から「10 秒を 1 ステップ」まで。

```cpp
TEST_METHOD(EventSetIsIndependentOfTimestep) {
    /* 2 秒のクリップ、イベント 3 個（0.35 / 1.10 / 1.85 秒） */

    std::map<std::uint32_t,int> refTally;
    { ClipPlayer p; p.SetClip(&clip);
      std::vector<FiredEvent> ref;
      for (int i = 0; i < 10000; ++i) {
          const auto st = p.Update(0.001f);
          CollectEvents(events, clip, st, ref);
      }
      refTally = Tally(ref); }

    for (float dt : {1.0f/120, 1.0f/60, 1.0f/30, 0.5f, 1.0f, 2.5f, 5.0f, 10.0f}) {
        const int steps = static_cast<int>(std::lround(10.0f/dt));
        std::vector<FiredEvent> got;
        ClipPlayer p; p.SetClip(&clip);
        for (int i = 0; i < steps; ++i) {
            const auto st = p.Update(dt);
            CollectEvents(events, clip, st, got);
        }
        Assert::IsTrue(Tally(got) == refTally);
    }
}
```

実測です。

```
基準（dt=1ms × 10000）: 合計 15 回
  dt= 0.0083 秒 ( 1200 ステップ): 合計  15 回  基準と一致=1
  dt= 0.0167 秒 (  600 ステップ): 合計  15 回  基準と一致=1
  dt= 0.0333 秒 (  300 ステップ): 合計  15 回  基準と一致=1
  dt= 0.5000 秒 (   20 ステップ): 合計  15 回  基準と一致=1
  dt= 1.0000 秒 (   10 ステップ): 合計  15 回  基準と一致=1
  dt= 2.5000 秒 (    4 ステップ): 合計  15 回  基準と一致=1
  dt= 5.0000 秒 (    2 ステップ): 合計  15 回  基準と一致=1
  dt=10.0000 秒 (    1 ステップ): 合計  15 回  基準と一致=1
```

**10 秒を 1 ステップで進めても、5 周ぶんの 15 イベントがすべて発火します。**

3 イベント × 5 周 = 15。理屈どおりです。

これがどれくらい重要かというと ―― **ロード中のヒッチ、デバッガでのブレークポイント、フレームレートの急落**。どれも「巨大な `dt`」を生みます。そこで足音が消えたり、当たり判定が発生しなかったりするバグは、**再現が難しく、原因も分かりにくい**。テストで固定しておく価値があります。

## 60.7　単体テスト：速度、逆再生、モード

**再生速度を変えても、通過したクリップ時間が同じなら総数は同じ。**

```cpp
TEST_METHOD(EventCountIsIndependentOfSpeed) {
    for (float speed : {0.25f, 0.5f, 1.0f, 2.0f, 4.0f}) {
        ClipPlayer p; p.SetClip(&clip); p.SetSpeed(speed);
        std::vector<FiredEvent> fired;
        const int steps = static_cast<int>(std::lround(8.0f/speed*60.0f));  // クリップ内 8 秒ぶん
        for (int i = 0; i < steps; ++i) {
            const auto st = p.Update(1.0f/60.0f);
            CollectEvents(events, clip, st, fired);
        }
        Assert::AreEqual(12u, static_cast<unsigned>(fired.size()));   // 4 周 × 3 イベント
    }
}
```

実測、**5 通りの速度すべてで 12 回**。

**逆再生は降順に発火する。**

```
発火数 4、順序: 3@1.85  2@1.10  1@0.35  4@0.00
```

イベント ID 3（`swing`、1.85 秒）から始まって、0.00 秒の `start` まで。**時刻の降順**です。

**Once は何秒回しても 1 回だけ。**

```
5 秒ぶん回しても 発火数 4（クリップは 2 秒）
```

**PingPong は往復で 2 回ずつ。**

```
4 秒（往復 1 回）: 合計 8 回  start=2 footL=2 footR=2 swing=2
```

2 秒のクリップを 4 秒 = 前進 1 回 + 後退 1 回。各イベントがちょうど 2 回。

## 60.8　境界にあるイベント

1 つだけ、原理的に曖昧なケースがあります。**`t = 0`（または `t = duration`）に置かれたイベント**です。

ループ再生では `t = 0` と `t = duration` は同じ瞬間です。だから `Finalize` で畳み込みます。

```cpp
void Finalize(float duration = 0.0f){
    if (duration > 0.0f)
        for (AnimEvent& e : events_) if (e.time >= duration) e.time = 0.0f;
    std::stable_sort(/* time 順 */);
}
```

それでも、**再生開始の瞬間に発火するかどうか**が残ります。時刻 0 から始めて `dt` 進めると、区間は `[0, dt)` で、`t = 0` のイベントは中に入ります。**発火します。**

これは「正しい」とも「正しくない」とも言えません。**規約として決めるしかない**話です。この本の実装は「発火する」を選びました。歩行の 1 歩目の足音が鳴るのは自然だからです。

そして、この境界は **`float` の精度に敏感**です。

```
dt=0.01667: 10 秒で t=0 のイベントが 6 回（折り返さない時刻の終端 10.0000005）
dt=10.00000: 10 秒で t=0 のイベントが 5 回（折り返さない時刻の終端 10.0000000）
```

**同じ 10 秒なのに、6 回と 5 回。**

理由は右端の数字にあります。`1.0f/60.0f` は `float` では `0.016666668`（正確な 1/60 よりわずかに大きい）。600 回足すと **`10.0000005`** ―― 10.0 をわずかに超えます。だから 5 回目の `t = 0`（折り返さない時刻 10.0）が区間 `[.., 10.0000005)` に入って発火する。`dt = 10.0` を 1 回なら区間は `[0, 10.0)` で、右端は開いているので入りません。

**これはバグではなく、境界に置いたイベントの本質です。**

- 実装は正しい（半開区間の定義に忠実）
- `dt` の累積誤差は避けられない
- 「10 秒ちょうど」という瞬間は、浮動小数では表現しきれない

**対策は 2 つ。**

1. **アセット側の規約**：イベントを `t = 0` ちょうどに置かない。`t = 0.001` にする。
2. **テスト側の規約**：`dt` 非依存性のテストには、境界にイベントを置かないトラックを使う（60.6 のテストがそうしています）。

> **境界にあるものを、境界のまま扱おうとしない。** どちらかに倒す規約を決めて、それをアセットパイプラインで強制する。

## 60.9　ブレンド中のイベント

実際のゲームでは、複数のクリップが同時に再生されています（第 VII 部）。歩きと走りを 50:50 でブレンドしているとき、**足音は 2 回鳴るべきでしょうか。**

鳴るべきではありません。しかし「どちらか一方」を選ぶのも乱暴です。歩きの足音と走りの足音は、タイミングも音も違います。

実務でよく使われる方針は 3 つです。

**① 重みのしきい値。** 重みが一定以上（たとえば 0.5）のクリップのイベントだけを発火する。

```cpp
if (weight > 0.5f) CollectEvents(track, clip, step, out);
```

単純で、ほとんどの場合これで足ります。境界（重み 0.5 付近）で行ったり来たりすると二重に鳴る可能性がありますが、ヒステリシスで防げます。

**② 最大重みのクリップだけ。** ブレンドツリー全体で「支配的な」クリップを 1 つ決め、そこからだけ発火する。第 38 章で加算ブレンドの符号合わせに「最大重みのポーズを基準にする」を選んだのと同じ発想です。

**③ 重みを payload に載せる。** 両方発火させ、`payload` に重みを入れて、ゲームロジック側で音量を決める。足音のような「重なっても不自然でない」イベントには有効です。攻撃判定には使えません。

**第 62 章の総合演習では ①** を使います（しきい値 0.3）。

**どれを選ぶにせよ、アニメーションシステムが決めることではありません。** イベントの意味を知っているのはゲームロジックだけです。システムは「どのクリップのどのイベントが、どの重みで発火可能か」を報告し、判断は上のレイヤーに渡す ―― 第 50 章の「見えないものは見えないと正直に返す」と同じ設計です。

## 60.10　コスト

```
イベント 4 個の収集: 0.0223 us / フレーム
```

**22 ナノ秒。** 第 62 章で測るキャラクター 1 体の更新コスト（約 7 µs）の 0.3% です。

ただしこれは「イベント 4 個の 1 トラック」の値です。実際には、

- ブレンドツリーの中で複数のクリップが同時に走る
- クリップによってはイベントが数十個ある
- キャラクターが 100 体いる

100 体 × 3 クリップ × 20 イベントなら、線形探索の回数は 6,000。それでも 1 ms には遠く及びませんが、**イベント数が増えたら二分探索に切り替える**余地はあります（第 25 章のキー探索と同じ話）。

**現時点で最適化しない理由**は、測ったら安かったからです。第 IX 部で繰り返した「測るまで分からない」の裏返しで、**測って安ければ、そのままにする**。

## この章のまとめ

- イベントは**データとして持ち、ツールで編集できるようにする**。「足音のタイミングが半フレーム早い」を直すのはアニメータであるべき（第 45・50・56 章と同じ結論）。
- `id` は `std::uint32_t`（比較が速い）、`payload` は `float` 1 個（**アニメーションシステムにゲームロジックの型を知らせない**）。
- 素朴な「前フレームと今フレームのあいだ」実装は、**ループ跨ぎ・巨大な dt・逆再生・PingPong** の 4 つで壊れる。
- 解決は、折り返した時刻から区間を**復元しないこと**。`PlaybackStep` に**折り返さない時刻**（`unwrappedFrom` / `unwrappedTo`、`double`）を持たせる。`ClipPlayer` の変更は 4 行。
- 発想の転換：「区間にイベントが入るか」ではなく「**イベントが折り返さない時刻軸のどこに現れるか**」。Loop なら `e + k·d`、PingPong なら偶数区間 `n·d + e` / 奇数区間 `(n+1)·d − e`。
- **4 つの問題がすべて消える。** 境界の特別扱いがゼロになる。
- **本質的な性質は「dt の刻み方によらず発火集合が同じ」。** 実測：**10 秒を 1 ステップで進めても 5 周ぶんの 15 イベントが全部発火**（8 通りの dt すべて一致）。
- 速度を変えても総数は同じ（5 通りの速度すべてで 12 回）。逆再生は**降順**に発火。Once は 5 秒回しても 4 回。PingPong は往復で 2 回ずつ。
- `((n % 2) + 2) % 2` ―― C++ の `%` は負の被除数に負を返す。**逆再生で `n` が負になる**ので必要。
- **境界（`t = 0`）のイベントは原理的に曖昧。** 実測、同じ 10 秒でも `dt=1/60` で 6 回、`dt=10` で 1 回だと 5 回（`1.0f/60.0f` を 600 回足すと `10.0000005`）。**バグではなく、境界に置いたことの本質。** 対策はアセット規約で `t=0` ちょうどを避けること。
- **境界にあるものを、境界のまま扱おうとしない。**
- ブレンド中は「重みのしきい値」「最大重みのクリップだけ」「重みを payload に載せる」の 3 択。**判断はゲームロジックに渡す。**
- コストは **0.0223 µs/フレーム**。**測って安ければ、そのままにする。**

次章では、ボーンに物を**くっつけます**。武器、盾、エフェクトの発生位置 ―― ソケットとアタッチメントです。
