# 第14章 プロットとシーン分割

第12章で企画を決め、第13章で設定資料を作りました。この章では、それらをもとに**プロット**を作ります。

プロットは、物語の設計図です。第7章の一発生成で見た「後半が駆け足になる」「伏線が回収されない」といった問題は、書き始める前に物語の流れを決めていないことが原因でした。人間の書き手と同じように、先に物語全体を**章**と**シーン**に分け、シーンごとに何が起きるかを決めておきます。

シーンごとの設計には、**シーンカード**を使います。シーンカードには、そのシーンの**目的・葛藤・結果**を書きます。第15章では、このシーンカードを1枚ずつLLMに渡して、シーンごとに本文を書かせます。

## 14.1 シーンカード

### 目的・葛藤・結果

物語は、いくつもの**シーン**（場面）の連なりでできています。1つのシーンは、ある場所で、ある時間に、ある人物たちの間で起きる、ひとまとまりの出来事です。

読者を引き込むシーンには、共通する形があります。視点人物が何かを**しようとし**（目的）、それを**阻むもの**があり（葛藤）、その結果として**状況が変わる**（結果）。そして、その変わった状況が、次のシーンの目的につながっていきます。

```text
シーン1                          シーン2
目的: 朝まで静かにやり過ごす      目的: 金庫が開いた理由を確かめる ←┐
葛藤: 葉子がしつこく話しかけてくる  葛藤: 黒川が部屋に入れようとしない  │
結果: 葉子の切符に不審な点がある ──→（切符の不審 → 駅長室へ）──────────┘
```

逆に、目的も葛藤もないシーンは、「登場人物が会話しているだけ」「景色を説明しているだけ」になり、物語が前に進みません。LLMに本文を書かせると、こうした「何も起きないシーン」が生まれがちです。シーンカードで目的・葛藤・結果を先に決めておくことで、それを防ぎます。

### シーンカードの項目

本書のシーンカードには、次の項目を持たせます。

| 項目 | 内容 | 使い道 |
|---|---|---|
| 見出し | シーンの短い名前 | 表示、ファイル名 |
| 場所 | 設定資料の場所の名前 | 執筆のときに、場所の描写の手がかりを参照する |
| 視点人物 | 誰の目から語るか | 視点のぶれを防ぐ（第8章） |
| 登場人物 | このシーンに出てくる人物 | 執筆のときに、その人物の口調などを参照する |
| 目的・葛藤・結果 | 上で説明したもの | シーンの骨組み |
| 出来事（beats） | シーンの中で起きることを、起きる順に | 執筆の指示。シーンの中の展開を決めておく |
| 文字数 | 目安の文字数 | 長さの配分（第8章） |

「出来事」は、映画の脚本などで**ビート**（beat）と呼ばれるものです。シーンカードの目的・葛藤・結果だけでは、シーンの中で何がどの順に起きるかまでは決まりません。出来事まで決めておくと、第15章で本文を書かせるときに、展開がぶれにくくなります。

### 設定資料と照合する

シーンカードの場所と人物は、設定資料の名前を使います。第13章の人間関係と同じく、ここでも**表記の揺れ**が問題になります。「沢渡透」を「沢渡」と書いたり、設定資料にない「ホーム」という場所を使ったりすると、第15章で設定資料を参照できなくなります。

第13章では、人間関係の名前を、同じモデルの中の登場人物の一覧と照合しました。今回は、プロットの外にある**設定資料**と照合する必要があります。さらに、シーンの文字数の合計が、作品の目標の文字数（第12章の `target_chars`）に近いかも確かめたいところです。

こうした「モデルの外の情報」を使った検証には、Pydanticの**検証のコンテキスト**（validation context）を使います。

## 14.2 プロットのモデル

**`src/novelist/schemas/plot.py`**（新規）

```python
"""プロットとシーンカード（第14章）。"""

from pydantic import BaseModel, Field, ValidationInfo, model_validator

from novelist.schemas.bible import CharacterSheet, WorldSheet

SCENE_MIN_CHARS = 500  # 1シーンの目安の文字数の下限
SCENE_MAX_CHARS = 4000  # 1シーンの目安の文字数の上限
LENGTH_TOLERANCE = 0.2  # 目標の文字数からのずれの許容範囲（±20%）


class Scene(BaseModel):
    """シーンカード。1つの場面で何が起きるかをまとめたもの。"""

    title: str = Field(description="シーンの見出し", max_length=30)
    place: str = Field(description="場面の場所。設定資料の場所の名前と同じ表記にする")
    pov: str = Field(description="視点人物の名前。登場人物の名前と同じ表記にする")
    characters: list[str] = Field(
        description="この場面に登場する人物の名前（視点人物を含む）", min_length=1, max_length=6
    )
    goal: str = Field(description="視点人物がこの場面で達成しようとすること", max_length=100)
    conflict: str = Field(description="目的を阻むもの", max_length=100)
    outcome: str = Field(description="場面の結果。次の場面へつながる状況の変化", max_length=100)
    beats: list[str] = Field(
        description="場面の中で起きる出来事を、起きる順に", min_length=2, max_length=6
    )
    chars: int = Field(description="目安の文字数", ge=SCENE_MIN_CHARS, le=SCENE_MAX_CHARS)


class Chapter(BaseModel):
    """章。"""

    title: str = Field(description="章の見出し", max_length=30)
    summary: str = Field(description="この章で起きることの要約", max_length=150)
    scenes: list[Scene] = Field(min_length=1, max_length=6)


class Plot(BaseModel):
    """作品全体のプロット。"""

    chapters: list[Chapter] = Field(min_length=1, max_length=8)

    def scenes(self) -> list[tuple[int, int, Scene]]:
        """すべてのシーンを、(章の番号, シーンの番号, シーン) の組で返す（番号は1から）。"""
        return [
            (i, j, scene)
            for i, chapter in enumerate(self.chapters, start=1)
            for j, scene in enumerate(chapter.scenes, start=1)
        ]

    def total_chars(self) -> int:
        """シーンの目安の文字数の合計。"""
        return sum(scene.chars for _, _, scene in self.scenes())

    @model_validator(mode="after")
    def _check_against_bible(self, info: ValidationInfo) -> "Plot":
        """設定資料と目標の文字数に合っているかを確かめる。

        検証に使う情報は、model_validate の context で受け取る（plot_context() を参照）。
        context がなければ、この検証は行わない。
        """
        context = info.context or {}
        names = context.get("character_names")
        places = context.get("place_names")
        target = context.get("target_chars")

        errors = []
        for i, j, scene in self.scenes():
            label = f"第{i}章のシーン{j}「{scene.title}」"
            if names is not None:
                for name in [scene.pov, *scene.characters]:
                    if name not in names:
                        errors.append(f"{label}の人物「{name}」は登場人物にいません")
                if scene.pov not in scene.characters:
                    errors.append(f"{label}の視点人物「{scene.pov}」が登場人物の欄にいません")
            if places is not None and scene.place not in places:
                errors.append(f"{label}の場所「{scene.place}」は設定資料にありません")
        if target is not None:
            low = int(target * (1 - LENGTH_TOLERANCE))
            high = int(target * (1 + LENGTH_TOLERANCE))
            total = self.total_chars()
            if not low <= total <= high:
                errors.append(f"シーンの文字数の合計（{total}字）を、{low}〜{high}字にしてください")
        if errors:
            hint = ""
            if names is not None:
                hint += f"\n使える人物: {'、'.join(sorted(names))}"
            if places is not None:
                hint += f"\n使える場所: {'、'.join(sorted(places))}"
            raise ValueError("\n".join(errors) + hint)
        return self


def plot_context(
    world: WorldSheet, characters: CharacterSheet, target_chars: int
) -> dict[str, object]:
    """Plot の検証に渡す context を作る。"""
    return {
        "character_names": {c.name for c in characters.characters},
        "place_names": {p.name for p in world.places},
        "target_chars": target_chars,
    }
```

**`Scene`、`Chapter`、`Plot`**

14.1節のシーンカードの項目を、そのままフィールドにしています。`Plot` → `Chapter` → `Scene` と3段の入れ子になっているので、JSONスキーマには入れ子の `$ref` ができます。第10章で `$ref` を展開する `inline_refs` を作っておいたのは、このためでした。

`chars`（目安の文字数）には、1シーンあたりの下限と上限（500〜4000字）を指定しています。整数の範囲なので、第10章で見たとおり、文法でも制約できます。

**`scenes()` と `total_chars()`**

`scenes()` は、すべてのシーンを `(章の番号, シーンの番号, シーン)` の組のリストにして返します。章とシーンの2重のループを、あちこちで書かずに済むようにするためです。内包表記で `for` を2つ並べると、2重のループと同じ意味になります。

**`_check_against_bible` と検証のコンテキスト**

`model_validator` のメソッドに、2番目の引数として `info: ValidationInfo` を書くと、検証のときの情報を受け取れます。`info.context` には、`model_validate(..., context=...)` に渡した辞書が入っています。

```python
Plot.model_validate_json(text, context={"character_names": {...}, "place_names": {...}, "target_chars": 10000})
```

これを使って、次のことを確かめています。

- 視点人物と登場人物が、設定資料の登場人物にいるか
- 視点人物が、そのシーンの登場人物の欄に含まれているか
- 場所が、設定資料の場所にあるか
- シーンの文字数の合計が、目標の±20%の範囲にあるか

コンテキストが渡されなかった場合（`info.context` が `None`）は、これらの検証を行いません。こうしておくと、設定資料がない場面（テストなど）でも、`Plot` のモデルとして使えます。

問題が見つかったら、すべての問題をまとめて `ValueError` にします。1つずつエラーにすると、LLMに直させるたびに1つしか直らず、何度もやり直すことになるからです。エラーメッセージの最後には、使える人物と場所の一覧を付けています（第13章と同じ考え方です）。

**`plot_context`**

検証のコンテキストを、設定資料と目標の文字数から作る関数です。コンテキストのキーの名前を1か所にまとめておくと、書き間違いを防げます。

```python
    state: PlanState, runtime: Runtime[PlanContext]
) -> Literal["load_plot", "make_plot"]:
    """プロットがすでにあれば読み込み、なければ（または作り直すなら）作る。

    設定資料を作り直した場合は、人物や場所が変わっているので、プロットも作り直す。
    """
    redo = state.get("redo", [])
    if runtime.context.work.has_plot() and "plot" not in redo and "bible" not in redo:
        return "load_plot"
    return "make_plot"


def load_plot(state: PlanState, runtime: Runtime[PlanContext]) -> dict:
    """保存してあるプロットを読み込む。"""
    plot = runtime.context.work.load_plot()
    return {"plot": plot, "log": ["既存のプロットを使います"]}


def make_plot(state: PlanState, runtime: Runtime[PlanContext]) -> dict:
    """企画と設定資料から、章とシーンカードからなるプロットを作る。"""
    ctx = runtime.context
    meta = state["meta"]
    messages = ctx.prompts.render(
        "plot",
        meta=meta,
        world=state["world"],
        characters=state["characters"],
        scene_min=SCENE_MIN_CHARS,
        scene_max=SCENE_MAX_CHARS,
        schema=schema_text(Plot),
    )
    sampling = ctx.config.sampling_for(PROFILE)
    # プロットはシーンの数だけ長くなるので、多めに確保しておく
    sampling = sampling.model_copy(update={"max_tokens": max(sampling.max_tokens, 8192)})
    context = plot_context(state["world"], state["characters"], meta.target_chars)
    plot = generate_structured(ctx.client, messages, Plot, sampling, validation_context=context)
    n_scenes = len(plot.scenes())
    return {
        "plot": plot,
        "log": [
            f"プロット: {len(plot.chapters)}章 {n_scenes}シーン（合計 {plot.total_chars():,}字）"
        ],
    }


def save_plot(state: PlanState, runtime: Runtime[PlanContext]) -> dict:
    """プロットを作品のディレクトリに保存する。"""
    work = runtime.context.work
    work.save_plot(state["plot"])
    return {"log": [f"プロットを保存しました → {work.plot_path}"]}
```

**`route_plot`**

プロットがすでにあれば読み込み、なければ作ります。ただし、**設定資料を作り直した場合は、プロットも作り直します**。設定資料を作り直すと、登場人物の名前や場所が変わるので、古いプロットはそのままでは使えないからです。このように、ある工程の成果物が別の工程の成果物に依存している場合は、元の工程をやり直したら、依存している工程もやり直す必要があります。

**`make_plot`**

プロンプトを展開し、`plot_context` で作った検証のコンテキストを `generate_structured` に渡します。プロットはシーンの数だけ出力が長くなるので、`max_tokens` は少なくとも8192から始めます。

## 14.6 設計のグラフにつなぐ

第13章の設計のグラフに、プロットの工程を加えます。変更が大きいので、変更後の全文を載せます。

**`src/novelist/graph/build.py`**（変更後の全文）

```python
"""作品の設計のグラフを組み立てる（第13章・第14章）。

START ─┬→ load_bible ──────────────────────────────────┐
       └→ make_world → make_characters → save_bible ───┤
                                                       ↓
                          ┌──────────── (route_plot) ──┤
                          ↓                            ↓
                      load_plot ──→ END        make_plot → save_plot → END
"""

from langgraph.graph import END, START, StateGraph
from langgraph.graph.state import CompiledStateGraph

from novelist.graph.nodes.bible import (
    load_bible,
    make_characters,
    make_world,
    route_bible,
    save_bible,
)
from novelist.graph.nodes.plot import load_plot, make_plot, route_plot, save_plot
from novelist.graph.state import PlanContext, PlanState

# --redo で指定できる工程
PLAN_STEPS = ("bible", "plot")


def build_plan_graph() -> CompiledStateGraph:
    """設計のグラフを組み立てる。"""
    builder = StateGraph(PlanState, context_schema=PlanContext)
    builder.add_node("load_bible", load_bible)
    builder.add_node("make_world", make_world)
    builder.add_node("make_characters", make_characters)
    builder.add_node("save_bible", save_bible)
    builder.add_node("load_plot", load_plot)
    builder.add_node("make_plot", make_plot)
    builder.add_node("save_plot", save_plot)

    # 設定資料
    builder.add_conditional_edges(START, route_bible, ["load_bible", "make_world"])
    builder.add_edge("make_world", "make_characters")
    builder.add_edge("make_characters", "save_bible")
    # プロット（設定資料の読み込み・保存のどちらのあとからも進む）
    builder.add_conditional_edges("load_bible", route_plot, ["load_plot", "make_plot"])
    builder.add_conditional_edges("save_bible", route_plot, ["load_plot", "make_plot"])
    builder.add_edge("make_plot", "save_plot")
    builder.add_edge("save_plot", END)
    builder.add_edge("load_plot", END)
    return builder.compile()
```

第13章では、`load_bible` と `save_bible` のあとは `END` に進んでいました。これを、どちらのあとからも、条件付きエッジ `route_plot` でプロットの工程に進むように変えています。

```text
            設定資料の工程                           プロットの工程
START ─┬→ load_bible ────────────────┐
       │                             ├─(route_plot)─┬→ load_plot ──────────→ END
       └→ make_world → make_characters → save_bible ┘ └→ make_plot → save_plot → END
```

`add_conditional_edges` は、1つのノードから出る条件付きエッジを定義します。2つのノードから同じ条件で分岐したいときは、このように2回書きます。

`PLAN_STEPS` に `"plot"` を加えたので、`--redo plot` でプロットだけを作り直せるようになります。

## 14.9 文字数がオーバーしたときは

### 何が起きるか

実際のモデルで `plan` を実行すると、次のようなエラーで止まることがあります。

```console
$ uv run novelist plan kiri-no-eki
「霧の終着駅」の設計を始めます
[load_bible] 既存の設定資料を使います
3回試しましたが、正しい形式の出力が得られませんでした: 1 validation error for Plot
  Value error, シーンの文字数の合計（15600字）を、8000〜12000字にしてください
使える人物: 三枝葉子、小野寺健、戸田文江、沢渡透、黒川源三
使える場所: ホーム、待合室、駅長室 [type=value_error, ...]
```

14.2節で作った検証が、シーンの文字数の合計が目標の±20%に収まっていないことを見つけ、LLMに直させました。しかし、3回試しても直らなかったのです。修正の指示を見たLLMは、あるシーンを減らすと別のシーンを増やしてしまったり、減らしすぎて今度は下回ったりします。

### LLMは足し算が苦手

原因は、LLMが**数の合計を合わせるのが苦手**なことです。

第3章で見たとおり、LLMは前から順にトークンを1つずつ生成します。プロットのJSONの中で、`"chars": 900` の数字を出力するとき、LLMはそれまでに出力したシーンの文字数を足し合わせて、残りがいくつかを計算しているわけではありません。12個のシーンの数字は、それぞれ「このシーンなら、このくらいの長さ」という感覚で決まります。合計が目標に合うかどうかは、ほとんど偶然です。

LLMは、**数を数えることや足し合わせることを、確実にはできません**。シーンの数が多くなるほど、合計のずれは大きくなります。

思い出してください。第8章では、目標の文字数を起承転結の4つの場面に割り振る計算を、LLMではなくPython（`default_structure`）で行っていました。今回のプロットでは、この割り振りまでLLMに任せてしまったことが、つまずきの原因です。

### 役割を分ける：比はLLM、合計はプログラム

そこで、仕事を分けます。

| 決めること | 担当 | 理由 |
|---|---|---|
| どのシーンを長くし、どのシーンを短くするか（比） | LLM | 物語の内容から判断する必要がある |
| 合計が目標の文字数になるように、実際の数を決める | プログラム | 単純な計算で、確実にできる |
| 目標の文字数に合わせられるだけの、シーンの数があるか | 検証（LLMに直させる） | シーンを足したり減らしたりするのは、LLMにしかできない |

LLMには、シーンどうしの長さの**比**だけを考えさせます。山場のシーンを長く、つなぎのシーンを短くする判断は、物語の内容がわかるLLMにしかできません。一方、その比を保ったまま合計を1万字にするのは、ただの掛け算です。これはプログラムで行えば、必ず合います。

ただし、プログラムで合わせられない場合もあります。1シーンの文字数は500〜4000字の範囲にしているので、たとえば3シーンでは、どう配分しても12000字を超えられません。**シーンの数**が足りない（または多すぎる）場合だけは、LLMにシーンを足したり減らしたりしてもらう必要があります。そこで、検証では合計の文字数ではなく、シーンの数を確かめるように変えます。シーンの数を数えるのはプログラムで、LLMへの指示は「〇〜〇個にしてください」という、LLMでも直しやすい形になります。

この考え方は、この先も何度も出てきます。**LLMには判断を、プログラムには計算と数え上げを**任せます。

### それでもうまくいかないときは

**シーンの数のエラーで止まる**

「シーンの数（〇個）を、〇〜〇個にしてください」というエラーで止まる場合は、LLMがシーンの数を直せなかったということです。次のどれかを試してください。

- `uv run novelist plan kiri-no-eki --redo plot` で、もう一度作らせる。出力は毎回変わるので、やり直すだけで通ることがよくあります
- `works/kiri-no-eki/work.toml` の `target_chars` を、モデルが作りやすい長さに変える。長い作品ほど多くのシーンが必要になり、小さいモデルでは難しくなります
- `novelist.toml` の `precise` プロファイルの `temperature` を下げる（第10章）

**配分を自分で直したい**

`plot.json` の `chars` を直接書き換えてもかまいません。プロットを読み込むときには、シーンの数は確かめますが、合計の文字数は確かめないので、手で決めた配分がそのまま使われます。直したあとは、`novelist plot` で合計を確かめてください。

**あとから目標の文字数を変えた**

`work.toml` の `target_chars` を変えても、保存してあるプロットの文字数は変わりません。`--redo plot` でプロットを作り直してください。

**本文の長さが目安と合わない**

この章で決めたのは、あくまで**目安**の文字数です。LLMに実際に本文を書かせると、目安どおりの長さにはなりません（第8章）。本文の長さを目安に近づける方法は、第15章で扱います。

## 14.10 まとめ

- プロットは、物語を**章**と**シーン**に分けた設計図です。シーンごとに**シーンカード**を作ります
- シーンカードの中心は**目的・葛藤・結果**です。結果が次のシーンの目的につながるようにすると、物語が前に進み続けます。シーンの中の**出来事**（beats）まで決めておくと、執筆のときの展開がぶれにくくなります
- シーンの人物と場所が設定資料にあるか、文字数の合計が目標に近いかを、Pydanticの**検証のコンテキスト**を使って確かめました。問題はまとめてエラーにし、使える名前の一覧を添えてLLMに直させます
- プロットを読み込むときにも今の設定資料と照合し、設定資料を手で直したあとの食い違いに気づけるようにしました
- LLMは数の合計を合わせるのが苦手です。シーンの長さの**比**はLLMに決めさせ、合計が目標になるように**プログラムで配分し直す**ようにしました。検証では、合わせられるだけのシーンの数があるかを確かめます
- 設計のグラフにプロットの工程をつなぎました。**設定資料を作り直したら、それに依存するプロットも作り直す**ようにしています
- `novelist plan` で設定資料からプロットまでを作り、`novelist plot` で木の形で表示できるようになりました

次の第15章では、いよいよシーンカードをもとに**本文を書く**ノードを作ります。各シーンを書くときに、設定資料のどの部分と、直前のシーンの何を渡すかを考えていきます。
