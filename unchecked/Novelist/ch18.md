# 第18章 ローカル埋め込みモデル

第III部で、企画から推敲までの工程がそろいました。短編なら、これで一通り書けます。しかし、作品が長くなるほど、**設定の食い違い**が目立つようになります。作品の第1章で「雪の夜は駅の外へ出られない」と決めたのに、第4章で登場人物が外へ出てしまう。前のシーンで硬券を手にした人物が、次のシーンでは持っていない。こうした食い違いです。

第15章では、シーンを書くときに、シーンカードに書かれた人物と場所の設定だけを、プログラムで選んで渡しました。しかし、シーンに関係する設定は、人物と場所だけではありません。切符をめぐるシーンなら「硬券」という用語の設定が要りますし、「駅の外へは出られない」という決まりも関係します。どの設定が関係するかは、**シーンの内容**によって決まります。

第IV部では、シーンの内容に関係する設定を、**意味の近さで検索**して渡す仕組みを作ります。この仕組みは、**RAG**（Retrieval-Augmented Generation、検索拡張生成）と呼ばれます。この章では、その土台となる**埋め込み**（embedding）を扱います。文章を数値のベクトルに変換し、ベクトルどうしの近さで、文章の意味の近さを測る技術です。

この章で作るものは次のとおりです。

| ファイル・コマンド | 内容 |
|---|---|
| `scripts/start-embedding-server.sh`（`.ps1`） | 埋め込み用の llama-server を起動する |
| `src/novelist/config.py` | 埋め込み用のサーバーの設定を追加 |
| `src/novelist/llm/embedding.py` | 文章をベクトルにするクライアントと、類似度の計算 |
| `src/novelist/rag/documents.py` | 設定資料を、検索の対象にする文書に分ける |
| `novelist embed` | 文章の類似度を表示するコマンド |
| `novelist search` | 設定資料から、内容の近い項目を探すコマンド |

第19章では、本文も含めた大量の文書を、データベースに保存して高速に検索できるようにします。第20章では、検索した結果を、トークンの予算の中でプロンプトに詰める方法を扱います。

## 18.1 埋め込みとは

### 文章をベクトルにする

**埋め込みモデル**は、文章を受け取り、決まった長さの数値の並び（**ベクトル**）を返すモデルです。ベクトルの長さ（**次元数**）は、モデルごとに決まっていて、たとえば768個の数値になります。

```text
「駅長は金庫の鍵を持っている」 → [0.021, -0.113, 0.057, ..., 0.008]  （768個）
「黒川は金庫を開けられる」     → [0.034, -0.098, 0.061, ..., -0.012] （768個）
「雪で列車が止まった」         → [-0.071, 0.045, -0.022, ..., 0.093] （768個）
```

埋め込みモデルは、**意味の近い文章が、近い向きのベクトルになる**ように学習されています。「駅長は金庫の鍵を持っている」と「黒川は金庫を開けられる」は、使っている言葉は違いますが、どちらも金庫を開けられる人の話なので、近い向きのベクトルになります。「雪で列車が止まった」は、別の話なので、離れた向きになります。

### コサイン類似度

2つのベクトルの向きの近さは、**コサイン類似度**で測ります。2つのベクトルのなす角のコサインで、-1から1の値になります。

```text
コサイン類似度 = (a と b の内積) ÷ (a の長さ × b の長さ)

  1に近い  … 向きがほぼ同じ（意味が近い）
  0に近い  … 直交している（関係がない）
```

内積は、2つのベクトルの同じ位置の数値を掛けて、足し合わせたものです。長さは、各数値の2乗の和の平方根です。llama-server は、返すベクトルの長さをあらかじめ1にそろえて（**正規化**して）いるので、実際には内積だけで同じ値になります。

実際の埋め込みモデルでは、まったく関係のない文章どうしでも、類似度が0.3〜0.6くらいになることがよくあります。大事なのは値そのものではなく、**ほかの文章と比べて高いか低いか**です。検索では、類似度の高い順に並べて、上から何件かを使います。

### キーワード検索との違い

文字列が一致するかどうかで探す**キーワード検索**と比べると、埋め込みによる検索には、次のような違いがあります。

| | キーワード検索 | 埋め込みによる検索 |
|---|---|---|
| 言い換え（「金庫」と「鍵のかかった箱」） | 見つからない | 見つかることが多い |
| 内容で探す（「誰が切符の行方を知っているか」） | 難しい | 得意 |
| 固有名詞や型番の完全一致 | 得意 | 苦手なことがある |
| 必要なもの | 文字列だけ | 埋め込みモデル |

小説の設定資料を探すときは、「このシーンに関係する設定」のように、内容で探したい場面がほとんどです。一方、登場人物の名前のような固有名詞は、第15章のように、プログラムで確実に選べます。本書では、両方を組み合わせて使います。

### 本文を書くモデルとは別のモデル

埋め込みには、本文を書くモデル（チャットモデル）とは別の、**埋め込み専用のモデル**を使います。チャットモデルは、次のトークンを予測するように学習されていて、文章全体の意味を1つのベクトルにまとめるようには学習されていないからです。

埋め込みモデルは、チャットモデルに比べてずっと小さく、数千万〜数億パラメータ程度です。生成はせず、入力を読んでベクトルを返すだけなので、計算も軽く済みます。

### クエリと文書のプレフィックス

検索では、短い**クエリ**（「切符の持ち主を知っている人物」）で、長い**文書**（人物の設定の全文）を探します。クエリと文書は、長さも書き方も違います。そこで、多くの埋め込みモデルは、**クエリと文書で、先頭に付ける文字列（プレフィックス）を変える**ように学習されています。

```text
クエリ: 「task: search result | query: 切符の持ち主を知っている人物」
文書:   「title: none | text: 三枝葉子（さえぐさ ようこ、27歳、相棒）。…」
```

プレフィックスはモデルごとに決まっていて、間違えたり付け忘れたりすると、検索の精度が下がります。使うモデルのモデルカード（Hugging Faceのモデルのページ）で、必ず確かめてください。主なモデルのプレフィックスは、次の節の表にまとめます。

## 18.2 日本語向けの埋め込みモデルを選ぶ

### 選ぶ基準

埋め込みモデルは、次の基準で選びます。

| 基準 | 確かめること |
|---|---|
| 日本語の性能 | 日本語の評価（**JMTEB**）のスコア。特に検索（Retrieval）のスコア |
| 入力の長さの上限 | 1つの文書に使えるトークン数。第19章で、文書を分割する大きさに関係する |
| 次元数 | ベクトルの長さ。大きいほど保存に場所をとり、検索が遅くなる |
| llama.cpp で動くか | モデルのアーキテクチャに llama.cpp が対応しているか。GGUF版があるか |
| ライセンス | 商用利用などの条件 |
| プレフィックス | クエリと文書に付ける文字列 |
| 大きさ | メモリの使用量と速度 |

**JMTEB**（Japanese Massive Text Embedding Benchmark）は、日本語の埋め込みモデルの評価によく使われるベンチマークです。検索、分類、クラスタリングなど、いくつもの課題の成績をまとめたものです。ただし、評価に使うデータセットの数が途中で増えたり、平均のとり方がモデルカードによって違ったりするので、**異なる出どころのスコアを並べて比べるときは注意が必要**です。スコアは大まかな目安にとどめ、最後は自分の作品の設定資料で、18.7節の `search` コマンドを使って確かめるのが確実です。

### 主な候補

本書の執筆時点（2026年9月）で、llama.cpp で動かせる、日本語に使える主な埋め込みモデルは次のとおりです。新しいモデルは次々に出るので、選ぶときには最新の情報も確かめてください。

| モデル | パラメータ | 次元数 | 入力の上限 | 日本語 | GGUF | ライセンス |
|---|---|---|---|---|---|---|
| EmbeddingGemma-300m | 3億 | 768（512・256・128にも縮められる） | 2,048トークン | 多言語（100以上の言語） | 公式（ggml-org） | Gemma |
| ruri-v3-310m | 3億 | 768 | 8,192トークン | 日本語に特化 | 有志による変換 | Apache 2.0 |
| ruri-v3-30m / 70m / 130m | 0.4億〜1.3億 | 256〜512 | 8,192トークン | 日本語に特化 | 有志による変換 | Apache 2.0 |
| Qwen3-Embedding-0.6B | 6億 | 1,024 | 32,768トークン | 多言語 | 公式（Qwen） | Apache 2.0 |
| multilingual-e5-large | 5.6億 | 1,024 | 512トークン | 多言語 | 有志による変換 | MIT |

- **EmbeddingGemma-300m**：Googleの小さな多言語の埋め込みモデルです。llama.cpp の開発元（ggml-org）がGGUF版を公開していて、llama-server には、このモデルを使うための `--embd-gemma-default` というオプションまであります。対応が確実なので、**本書では、このモデルを既定にします**。
- **ruri-v3**：名古屋大学のグループによる、日本語に特化した埋め込みモデルです。JMTEBでは、同じくらいの大きさの多言語モデルより高いスコアを出していて、いちばん小さい30mでも、大きな多言語モデルに並ぶと報告されています。ModernBERTというアーキテクチャで、公式のGGUF版はありません。有志が変換したGGUF版がありますが、変換に手を加えた llama.cpp を使ったと説明されているので、自分の llama.cpp で正しく動くかを、18.7節の `embed` コマンドで確かめてから使ってください。
- **Qwen3-Embedding-0.6B**：Qwenの多言語の埋め込みモデルです。入力の上限が長いのが特徴です。ただし、JMTEBで測った日本語の成績は、ruri-v3より低かったという報告があります。llama-server で使うときは、`--pooling last` の指定が必要です（18.3節）。
- **multilingual-e5-large**：以前から日本語の検索によく使われてきた多言語モデルです。入力の上限が512トークンと短いので、長い文書は分割する必要があります。

各モデルの、クエリと文書のプレフィックスは次のとおりです。

| モデル | クエリ | 文書 |
|---|---|---|
| EmbeddingGemma | `task: search result \| query: ` | `title: none \| text: ` |
| ruri-v3 | `検索クエリ: ` | `検索文書: ` |
| Qwen3-Embedding | `Instruct: （課題の説明）\nQuery: ` | なし |
| multilingual-e5 | `query: ` | `passage: ` |

Qwen3-Embedding の「課題の説明」には、たとえば `Given a question, retrieve passages that answer the question` のように、何を探すのかを英語で書きます。

### VRAMとの兼ね合い

第4章で、本文を書くモデルとKVキャッシュでVRAMをほぼ使い切るように、モデルを選びました。埋め込みモデルは、そこにもう1つモデルを加えることになります。

| モデル | GGUFの大きさの目安 |
|---|---|
| EmbeddingGemma-300m（QAT Q4_0） | 約0.2〜0.3GB |
| ruri-v3-310m（Q8_0） | 約0.34GB |
| Qwen3-Embedding-0.6B（Q8_0） | 約0.64GB |

どれも、本文を書くモデルに比べればずっと小さいものです。また、埋め込みは生成をしないので、文章を読むだけの計算で済み、**CPUでも十分に実用的な速さ**で動きます。そこで本書では、埋め込みモデルを**CPUで動かす**ことを既定にします。VRAMは、これまでどおり本文を書くモデルのために使います。VRAMに余裕がある場合は、GPUに載せればさらに速くなります。

## 18.3 埋め込み用のサーバーを起動する

### モデルをダウンロードする

第5章と同じく、`hf` コマンドで、EmbeddingGemma のGGUF版を `models/` にダウンロードします。

```console

    embeddinggemma-300M-qat-Q4_0.gguf \

```

EmbeddingGemma は、ダウンロードする前に、Hugging Faceのモデルのページで利用条件（Gemmaのライセンス）への同意が必要な場合があります。ダウンロードで認証のエラーになる場合は、ページを開いて同意してから、`hf auth login` でログインしてください。

### 起動スクリプト

埋め込み用の llama-server は、本文を書くための llama-server（第5章、ポート8080）とは別に、ポート8081で起動します。2つのサーバーを同時に動かしておき、用途によって使い分けます。

**`scripts/start-embedding-server.sh`**（新規）

```bash
#!/usr/bin/env bash
# 埋め込み用の llama-server を起動する（Linux / macOS、第18章）
#
# 使い方:
#   MODEL=models/xxx.gguf scripts/start-embedding-server.sh [llama-server に渡す追加のオプション]
#
# 本文を書くための llama-server（scripts/start-server.sh、ポート8080）とは別に、
# ポート8081で起動する。2つを同時に動かしておく。
set -euo pipefail

LLAMA_CPP_DIR="${LLAMA_CPP_DIR:-$HOME/src/llama.cpp}"
MODEL="${MODEL:-models/embeddinggemma-300M-qat-Q4_0.gguf}"
CTX="${CTX:-2048}"   # 1つの文章に使えるトークン数の上限
NGL="${NGL:-0}"      # 既定はCPUで動かす。VRAMに余裕があれば 999 にする
PORT="${PORT:-8081}"

exec "$LLAMA_CPP_DIR/build/bin/llama-server" \
  --model "$MODEL" \
  --alias embedding \
  --embedding \
  --ctx-size "$CTX" \
  --batch-size "$CTX" \
  --ubatch-size "$CTX" \
  --n-gpu-layers "$NGL" \
  --parallel 1 \
  --host 127.0.0.1 \
  --port "$PORT" \
  "$@"
```

**`scripts/start-embedding-server.ps1`**（新規）

```powershell
# 埋め込み用の llama-server を起動する（Windows、第18章）
#
# 使い方:
#   scripts\start-embedding-server.ps1 -Model models\xxx.gguf [llama-server に渡す追加のオプション]
#
# 本文を書くための llama-server（scripts\start-server.ps1、ポート8080）とは別に、
# ポート8081で起動する。2つを同時に動かしておく。
param(

    [int]$Ngl = 0,

    [string[]]$Rest = @()
)

& $server `
    --model $Model `
    --alias embedding `
    --embedding `
    --ctx-size $Ctx `
    --batch-size $Ctx `
    --ubatch-size $Ctx `
    --n-gpu-layers $Ngl `
    --parallel 1 `
    --host 127.0.0.1 `
    --port $Port `
    @Rest
```

第5章の起動スクリプトとの違いは、次のとおりです。

- **`--embedding`**：埋め込みだけに使うサーバーとして起動します。このオプションがないサーバーに埋め込みを頼むと、エラー（501）になります。
- **`--ctx-size`、`--batch-size`、`--ubatch-size` を同じ値に**：埋め込みモデルの多くは、文章全体を一度に読んでからベクトルを作ります。そのため、1つの文章は、1回の計算の単位（**物理バッチ**、`--ubatch-size`）に収まっている必要があります。既定の物理バッチは512トークンなので、そのままでは512トークンを超える文章でエラーになります。3つを同じ値にして、コンテキスト長いっぱいまでの文章を扱えるようにしています。
- **`--n-gpu-layers` の既定を0に**：18.2節のとおり、CPUで動かします。GPUに載せる場合は、`NGL=999`（PowerShellでは `-Ngl 999`）を指定します。
- **`--flash-attn` と `--cache-type-k/v` がない**：埋め込みでは文章を読むだけで、長い会話のKVキャッシュを持ち続けることがないので、指定していません。
- **`--alias embedding`**：本文用のサーバーの `novelist` と区別するための名前です。

**プーリング**の指定（`--pooling`）もありません。プーリングは、文章の各トークンのベクトルを、1つのベクトルにまとめる方法です。平均をとる（`mean`）、最初のトークンを使う（`cls`）、最後のトークンを使う（`last`）などがあり、モデルごとに決まっています。多くのGGUFには正しい方法が記録されているので、省略すればそれが使われます。Qwen3-Embedding のように、明示する必要があるモデルでは、追加のオプションとして渡します。

モデルごとの起動のしかたは、次のようになります。

```console
$ scripts/start-embedding-server.sh                          # EmbeddingGemma（既定）
$ MODEL=models/ruri-v3-310m-q8_0.gguf CTX=8192 scripts/start-embedding-server.sh
$ MODEL=models/Qwen3-Embedding-0.6B-Q8_0.gguf CTX=8192 scripts/start-embedding-server.sh --pooling last
```

Windowsでは、次のように実行します。

```console
PS> powershell -ExecutionPolicy Bypass -File scripts\start-embedding-server.ps1
PS> powershell -ExecutionPolicy Bypass -File scripts\start-embedding-server.ps1 -Model models\Qwen3-Embedding-0.6B-Q8_0.gguf -Ctx 8192 --pooling last
```

### 動作を確かめる

本文用のサーバーとは別のターミナルで、埋め込み用のサーバーを起動します。起動したら、`curl` で試してみます（Windowsでは、第5章で説明したとおり `curl.exe` を使い、JSONはファイルに保存して渡してください）。

```console
$ curl -s http://127.0.0.1:8081/v1/embeddings \
    -H "Content-Type: application/json" \
    -d '{"input": ["雪の駅", "金庫の鍵"], "model": "embedding"}' | head -c 300
{"model":"embedding","object":"list","usage":{"prompt_tokens":12,"total_tokens":12},"data":[{"embedding":[-0.0386,0.0112,...
```

`/v1/embeddings` は、OpenAI互換の埋め込みのAPIです。`input` に文章か文章のリストを渡すと、`data` の中に、文章ごとのベクトル（`embedding`）が返ってきます。

```python
"""埋め込み用の llama-server で、文章をベクトルに変換する（第18章）。"""

import math
from dataclasses import dataclass
from typing import Any

import httpx

from novelist.config import EmbeddingConfig
from novelist.llm.client import LLMError

Vector = list[float]


class EmbeddingError(LLMError):
    """埋め込みに失敗したときの例外。"""


@dataclass
class EmbeddingInfo:
    """埋め込み用のサーバーで動いているモデルの情報。"""

    model: str  # モデル名（--alias）
    n_embd: int | None  # ベクトルの次元数
    n_ctx: int | None  # 1つの文章に使えるトークン数の上限（実行時）
    n_ctx_train: int | None  # 学習時のコンテキスト長


def _error_hint(status: int, message: str) -> str:
    """llama-server のエラーに、対処のしかたを添える。"""
    if status == 501:
        return (
            f"{message}\n埋め込み用ではないサーバーにつながっています。"
            "novelist.toml の [embedding] の url が、--embedding を付けて起動した"
            "サーバー（scripts/start-embedding-server）を指しているか確かめてください"
        )
    if "too large" in message:
        return (
            f"{message}\n文章が長すぎます。文章を短く分けるか、埋め込み用のサーバーの"
            "--ubatch-size と --ctx-size を大きくしてください"
        )
    return message


def _check_not_empty(texts: list[str]) -> None:
    """空の文章があればエラーにする。llama-server は、空の文章をエラーにするため。"""
    if any(not text.strip() for text in texts):
        raise ValueError("空の文章は埋め込めません")


class EmbeddingClient:
    """llama-server の /v1/embeddings を呼び出すクライアント。"""

    def __init__(
        self, config: EmbeddingConfig, transport: httpx.BaseTransport | None = None
    ) -> None:
        headers = {"Authorization": f"Bearer {config.api_key}"} if config.api_key else {}
        self.config = config
        self._http = httpx.Client(
            base_url=config.url, headers=headers, timeout=config.timeout, transport=transport
        )

    def close(self) -> None:
        self._http.close()

    def __enter__(self) -> "EmbeddingClient":
        return self

    def __exit__(self, *exc: object) -> None:
        self.close()

    def _request(self, method: str, path: str, payload: dict[str, Any] | None = None) -> Any:
        try:
            response = self._http.request(method, path, json=payload)
        except httpx.HTTPError as e:
            raise EmbeddingError(
                f"埋め込み用のサーバー {self.config.url} に接続できません: {e}\n"
                "scripts/start-embedding-server で起動しているか確かめてください"
            ) from e
        if response.status_code != 200:
            try:
                message = response.json()["error"]["message"]
            except (ValueError, KeyError, TypeError):
                message = response.text
            raise EmbeddingError(
                f"{path} がエラーを返しました（{response.status_code}）: "
                + _error_hint(response.status_code, message)
            )
        return response.json()

    def info(self) -> EmbeddingInfo:
        """動いているモデルの情報を取得する。"""
        model = self._request("GET", "/v1/models")["data"][0]
        meta = model.get("meta") or {}
        return EmbeddingInfo(
            model=model["id"],
            n_embd=meta.get("n_embd"),
            n_ctx=meta.get("n_ctx"),
            n_ctx_train=meta.get("n_ctx_train"),
        )

    def embed(self, texts: list[str]) -> list[Vector]:
        """文章のリストを、同じ順のベクトルのリストにする。プレフィックスは付けない。

        batch_size 件ずつに分けてリクエストする。
        """
        _check_not_empty(texts)
        vectors: list[Vector] = []
        size = self.config.batch_size
        for start in range(0, len(texts), size):
            batch = texts[start : start + size]
            data = self._request(
                "POST", "/v1/embeddings", {"input": batch, "model": self.config.model}
            )
            # 応答の順番は保証されないので、index で並べ直す
            items = sorted(data["data"], key=lambda item: item["index"])
            vectors.extend(item["embedding"] for item in items)
        return vectors

    def embed_query(self, text: str) -> Vector:
        """検索する文（クエリ）を、クエリ用のプレフィックスを付けてベクトルにする。"""
        _check_not_empty([text])
        return self.embed([self.config.query_prefix + text])[0]

    def embed_documents(self, texts: list[str]) -> list[Vector]:
        """検索される文書を、文書用のプレフィックスを付けてベクトルにする。"""
        _check_not_empty(texts)
        return self.embed([self.config.document_prefix + text for text in texts])


def cosine_similarity(a: Vector, b: Vector) -> float:
    """2つのベクトルのコサイン類似度（-1〜1）。向きが近いほど1に近い。"""
    dot = sum(x * y for x, y in zip(a, b, strict=True))
    norm = math.sqrt(sum(x * x for x in a)) * math.sqrt(sum(y * y for y in b))
    return dot / norm if norm else 0.0


def most_similar(
    query: Vector, vectors: list[Vector], top_k: int | None = None
) -> list[tuple[int, float]]:
    """query に近い順に、(vectors の中の番号, 類似度) を並べる。"""
    scores = [(i, cosine_similarity(query, v)) for i, v in enumerate(vectors)]
    scores.sort(key=lambda item: item[1], reverse=True)
    return scores[:top_k] if top_k else scores
```

**`EmbeddingClient`**

第6章の `LLMClient` と同じく、`httpx` で llama-server を呼び出します。埋め込み用のサーバーは別のURLにあり、呼び出すAPIも違うので、別のクラスにしています。

- **`info`**：`/v1/models` から、モデルの名前と、ベクトルの次元数（`n_embd`）、コンテキスト長を取り出します。第6章の `server_info` と同じAPIです。
- **`embed`**：文章のリストを、`batch_size` 件ずつ `/v1/embeddings` に送ります。応答の `data` は、送った順に並んでいるとは限らないので、各項目の `index` で並べ直してから返します。
- **`embed_query` と `embed_documents`**：それぞれのプレフィックスを付けてから `embed` を呼びます。検索するときは、クエリには `embed_query`、文書には `embed_documents` を使います。プレフィックスを付けずに試したいときは、`embed` を直接呼びます。

**`_check_not_empty`**

llama-server は、空の文章を送るとエラーを返します。プレフィックスを付けると空ではなくなってしまうので、付ける前の文章で確かめています。

**`_error_hint`**

llama-server のエラーに、対処のしかたを添えます。よく出会うのは、次の2つです。

| エラー | 原因 |
|---|---|
| `This server does not support embeddings. Start it with --embeddings`（501） | 本文用のサーバー（`--embedding` なし）につながっている |
| `input (6000 tokens) is too large to process. increase the physical batch size`（500） | 文章が物理バッチより長い |

エラーの応答のJSONから `error.message` を取り出して、メッセージを組み立てています。

**`cosine_similarity` と `most_similar`**

18.1節のコサイン類似度を計算する関数と、クエリに近い順にベクトルを並べる関数です。`most_similar` は、ベクトルのリストの**番号**と類似度の組を返します。番号を返すのは、ベクトルに対応する文書（設定資料の項目など）を、呼び出し側で取り出せるようにするためです。

ここでは、すべてのベクトルとの類似度を計算してから並べています。これを**総当たり**の検索と呼びます。設定資料の項目が数十件なら一瞬ですが、本文を含めて数千件になると遅くなります。第19章では、ベクトル検索のためのデータベースを使って、これを速くします。

```python
"""設定資料を、検索の対象にする文書に分ける（第18章）。"""

from dataclasses import dataclass

from novelist.schemas.bible import CharacterSheet, WorldSheet


@dataclass
class BibleDoc:
    """検索の対象にする、設定資料の1項目。"""

    kind: str  # 種類（"世界"、"場所"、"用語"、"人物"）
    name: str  # 項目の名前
    text: str  # 埋め込む文章


def _sentence(text: str) -> str:
    """文の終わりに句点がなければ付ける。"""
    text = text.strip()
    return text if text.endswith(("。", "！", "？")) else text + "。"


def bible_documents(world: WorldSheet, characters: CharacterSheet) -> list[BibleDoc]:
    """設定資料を、項目ごとの文書にする。

    文章には、項目の名前も含める。「黒川源三」で検索したときに、
    黒川源三の項目が見つかるようにするため。
    """
    w = world.world
    overview = [f"時代: {w.era}", f"舞台: {w.place}", f"雰囲気: {w.atmosphere}", *w.rules]
    docs = [BibleDoc("世界", "世界の概要", "".join(_sentence(s) for s in overview))]
    for p in world.places:
        text = _sentence(p.name) + _sentence(p.description) + _sentence(p.sensory)
        docs.append(BibleDoc("場所", p.name, text))
    for t in world.terms:
        docs.append(BibleDoc("用語", t.name, _sentence(t.name) + _sentence(t.description)))
    for c in characters.characters:
        parts = [
            f"{c.name}（{c.reading}、{c.age}歳、{c.role}）",
            f"性格: {c.personality}",
            f"話し方: {c.speech_style}",
            f"目的: {c.goal}",
            f"秘密: {c.secret}",
            *(
                f"{r.target}との関係: {r.relation}"
                for r in characters.relationships
                if r.source == c.name
            ),
        ]
        docs.append(BibleDoc("人物", c.name, "".join(_sentence(s) for s in parts)))
    return docs
```

第13章の設定資料を、世界の概要、場所、用語、人物の、項目ごとの文書にします。

- **1項目を1文書に**：1つの文書に、複数の項目を混ぜないようにしています。1つのベクトルには、文書全体の意味がまとめられるので、複数の話題が混ざると、どの話題で探しても中くらいの類似度になり、見つけにくくなります。
- **名前を文書に含める**：人物の文書には、名前と読みを入れています。人物の名前で探したときに、その人物の文書が上位に来るようにするためです。
- **人間関係は、元の人物の文書に入れる**：「沢渡透 → 黒川源三: 元上司」は、沢渡透の文書に入れます。沢渡透のことを調べるときに、誰とどういう関係かも一緒にわかるようにするためです。
- **`_sentence`**：項目の値の最後に句点がなければ付けて、文として区切ります。区切らずにつなぐと、「〜ですね」目的: 駅で…のように、別の項目とつながって読めてしまいます。

## 18.9 うまくいかないときは

**「埋め込み用ではないサーバーにつながっています」と表示される**

`novelist.toml` の `[embedding]` の `url` が、本文用のサーバー（ポート8080）を指しているか、埋め込み用のサーバーを `--embedding` なしで起動しています。`scripts/start-embedding-server` で起動し、ポートが8081になっているかを確かめてください。

**「文章が長すぎます」と表示される**

文章のトークン数が、物理バッチ（`--ubatch-size`）を超えています。起動スクリプトの `CTX` を大きくしてください（`CTX` の値が、`--ubatch-size` にも使われます）。ただし、モデルの入力の上限（EmbeddingGemma なら2,048トークン）を超えることはできません。上限を超える文章は、第19章の方法で分割します。

**どの文章どうしも、類似度が0.99くらいになる**

プーリングの方法が、モデルに合っていない可能性があります。Qwen3-Embedding では `--pooling last` を指定しているか確かめてください。埋め込み用ではない、チャットモデルのGGUFを指定している場合も、こうなります。

**検索の結果がおかしい**

`novelist.toml` のプレフィックスが、使っているモデルのものか確かめてください。モデルを変えたのに、プレフィックスが EmbeddingGemma のままになっている、というのがよくある間違いです。それでもよくならない場合は、別のモデルを試してみてください。18.2節のとおり、日本語の成績はモデルによってかなり違います。

**モデルが読み込めない（unknown model architecture など）**

使っている llama.cpp が、そのモデルのアーキテクチャに対応していません。llama.cpp を新しいバージョンに更新してください（第5章）。有志が変換したGGUFは、変換に使った llama.cpp の版によっては、読み込めなかったり、読み込めても正しいベクトルにならなかったりします。その場合は、公式のGGUFがあるモデル（EmbeddingGemma、Qwen3-Embedding）を使ってください。

## 18.10 まとめ

- **埋め込み**は、文章を決まった長さのベクトルにする技術です。意味の近い文章は近い向きのベクトルになり、その近さは**コサイン類似度**で測ります。言い換えや内容による検索が得意で、固有名詞の完全一致は、プログラムで選ぶ方法と組み合わせます
- 埋め込みには、本文を書くモデルとは別の、小さな**埋め込み専用のモデル**を使います。多くのモデルは、クエリと文書で異なる**プレフィックス**を付けるように学習されているので、モデルカードで確かめて設定します
- 日本語向けのモデルは、日本語の性能（JMTEB）、入力の上限、次元数、llama.cpp の対応、ライセンスで選びます。本書では、llama.cpp の対応が確実な **EmbeddingGemma** を既定にし、日本語に特化した **ruri-v3** なども紹介しました
- 埋め込み用の llama-server を、本文用とは別に、`--embedding` を付けて**CPUで**起動しました。1つの文章を一度に読めるように、物理バッチをコンテキスト長と同じ大きさにしています
- `novelist embed` で文章の類似度を確かめ、`novelist search` で設定資料から内容の近い項目を探せるようになりました

次の第19章では、設定資料だけでなく、書き終えた本文も**チャンク**に分割して埋め込み、**sqlite-vec** というSQLiteの拡張でベクトルを保存・検索できるようにします。
