# 第9章 サンプリングを理解する

第3章で、LLMは「次のトークンの確率」を計算し、そこから1つを選ぶことを繰り返して文章を作る、と説明しました。この「確率から1つを選ぶ」処理を**サンプリング**と呼びます。

これまでは、`temperature` と `top_p` を設定ファイルに書いて、なんとなく使ってきました。第7章では、同じ条件で何度書かせても似た展開になる「単調さ」を見ました。第8章のプロンプトの工夫でも、この問題は解決しきれていません。

この章では、サンプリングの仕組みを基礎から理解し、小説の生成に合った設定を探ります。

- 次のトークンの候補と確率を、実際に目で見る（`novelist probs`）
- `temperature`、`top_k`、`top_p`、`min_p` が、候補をどう変えるかを理解する
- 繰り返しを抑える `repeat_penalty` と **DRY**、ありきたりな選択を避ける **XTC** を知る
- パラメータを変えながら同じ条件で書かせ、比べる（`novelist sweep`）

あわせて、第6章の設定ファイルの弱点だった「パラメータの書き間違いが黙って無視される」問題も直します。

## 9.1 次のトークンの候補を見る

まずは、LLMが実際にどんな候補を考えているのかを見てみましょう。この章で作る `novelist probs` コマンドを使うと、ある文字列の続きとして、次にどんなトークンがどのくらいの確率で来るかを表示できます。

```console
$ uv run novelist probs "窓の外は白く" -n 12
   「窓の外は白く」の次のトークン  temperature=0.8  top_k=40
                     top_p=0.95  min_p=0.05
┏━━━━━━┳━━━━━━━━━━┳━━━━━━━━━━┳━━━━━━━━━━┳━━━━━━━━┳━━━━━━━━━━━━━┓
┃ 順位 ┃ トークン ┃ 元の確率 ┃          ┃ 適用後 ┃             ┃
┡━━━━━━╇━━━━━━━━━━╇━━━━━━━━━━╇━━━━━━━━━━╇━━━━━━━━╇━━━━━━━━━━━━━┩
│    1 │ '塗'     │    41.2% │ ████████ │  55.2% │ ███████████ │
│    2 │ '、'     │    18.7% │ ████     │  20.6% │ ████        │
│    3 │ '染'     │    12.1% │ ██       │  11.9% │ ██          │
│    4 │ '霞'     │     6.4% │ █        │   5.4% │ █           │
│    5 │ '光'     │     4.3% │ █        │   3.3% │ █           │
│    6 │ '曇'     │     3.1% │ █        │   2.2% │             │
│    7 │ '濁'     │     2.2% │          │   1.4% │             │
│    8 │ '凍'     │     1.7% │          │      - │             │
│    9 │ '煙'     │     1.2% │          │      - │             │
│   10 │ '。'     │     0.9% │          │      - │             │
│   11 │ '冴'     │     0.6% │          │      - │             │
│   12 │ 'ぼ'     │     0.4% │          │      - │             │
└──────┴──────────┴──────────┴──────────┴────────┴─────────────┘
候補は上位12個だけを使って計算しています
```

「元の確率」は、モデルが計算した確率そのものです。「窓の外は白く」の次には、「塗（りつぶされ）」が41%、「、」が19%、「染（まり）」が12%……と続きます。

「適用後」は、サンプリングの設定（表の上に表示）を適用したあとの確率です。実際には、この確率に従って1つが選ばれます。いくつかの候補は「-」になっていて、選ばれる可能性がなくなっています。確率の高い「塗」はさらに高くなり、低い候補はさらに低くなっています。

このように、サンプリングの設定は**モデルが出した確率を加工して、どの候補をどのくらいの確率で選ぶかを決める**ものです。以下で、それぞれの設定が何をしているかを順に見ていきます。

※ この章の `probs` の出力は、説明のための例です。候補と確率は、モデルによって異なります。

## 9.2 temperature

### 確率の差を強めたり弱めたりする

**temperature**（温度）は、確率の差を強めたり弱めたりする設定です。モデルは内部で、各トークンに**ロジット**と呼ばれるスコアを計算し、それを確率に変換しています。temperatureは、このスコアをTで割ってから確率に変換します。

```text
確率 ∝ exp(ロジット ÷ T)
```

同じことを、もとの確率 p を使って書くと、次のようになります。

```text
新しい確率 ∝ p^(1/T)    （計算したあと、合計が1になるように割り直す）
```

- **T = 1**：もとの確率のまま
- **T < 1**：確率を1より大きい数で累乗するので、差が**強まる**。確率の高い候補がより選ばれやすくなる
- **T > 1**：確率を1より小さい数で累乗するので、差が**弱まる**。確率の低い候補も選ばれやすくなる
- **T = 0**：いつも、いちばん確率の高い候補を選ぶ（**貪欲法**）

`probs` で、temperatureだけを変えて比べてみます。

```console
$ uv run novelist probs "窓の外は白く" -n 12 --temperature 0.3
...
│    1 │ '塗'     │    41.2% │ ████████ │  91.6% │ ██████████████████ │
│    2 │ '、'     │    18.7% │ ████     │   6.6% │ █                  │
│    3 │ '染'     │    12.1% │ ██       │   1.5% │                    │
│    4 │ '霞'     │     6.4% │ █        │   0.2% │                    │
...
```

temperatureが0.3だと、「塗」が9割以上を占めます。何度生成しても「白く塗りつぶされ」になり、文章は安定しますが、第7章で見たような「ありきたりな表現」ばかりになります。

```console
$ uv run novelist probs "窓の外は白く" -n 12 --temperature 1.5 --top-k 0 --top-p 1.0 --min-p 0
...
│    1 │ '塗'     │    41.2% │ ████████ │  30.7% │ ██████ │
│    2 │ '、'     │    18.7% │ ████     │  18.1% │ ████   │
│    3 │ '染'     │    12.1% │ ██       │  13.6% │ ███    │
│    4 │ '霞'     │     6.4% │ █        │   8.9% │ ██     │
...
│   10 │ '。'     │     0.9% │          │   2.4% │        │
│   11 │ '冴'     │     0.6% │          │   1.8% │        │
│   12 │ 'ぼ'     │     0.4% │          │   1.4% │        │
```

temperatureを1.5にし、ほかの設定を無効にすると、分布が平らになり、「冴」「ぼ」のような確率の低い候補も選ばれやすくなります。

### temperatureを上げると崩れる理由

表示しているのは上位12個だけですが、実際の語彙には15万以上のトークンがあります。そのほとんどは、この文脈にまったく合わない候補（英単語の断片、記号、関係のない漢字など）で、1つ1つの確率はごくわずかです。しかし、数が多いので、**全部を合わせるとそれなりの確率**になります。

temperatureを上げると、こうした「合わない候補」の確率がまとめて持ち上がります。1回の選択で合わない候補を引く確率は小さくても、数千トークンの文章を生成すれば、どこかで必ず引いてしまいます。そして一度おかしなトークンを選ぶと、LLMはそれを前提に続きを書くので、文章がそこから崩れていきます。

「変化はほしいが、崩れてほしくない」。これを両立させるには、**合わない候補をあらかじめ切り捨ててから、残った候補の中で変化をつける**必要があります。それが次の節の設定です。

## 9.3 候補を切り捨てる：top_k・top_p・min_p

### top_k

確率の高い順に **k個だけ**を残し、それ以外を切り捨てます。`llama-server` の既定値は40です。

わかりやすい方法ですが、文脈によって「妥当な候補の数」は大きく変わるので、固定の個数では合わないことがあります。「窓の外は白く」の次は数個に絞るべきですが、物語の書き出しの1文字目なら、何百もの妥当な候補があるかもしれません。

### top_p

確率の高い順に足していき、**合計がpに達するまで**の候補を残します。`top_p = 0.95` なら、上位の候補で確率の95%を占めるところまでを残します。

top_kより柔軟ですが、確率の低い候補がたくさん並んでいる場合は、それらを大量に残してしまいます。上の例で言えば、「残りの5%」を捨てるだけなので、合わない候補の多くが残ります。

### min_p

**いちばん確率の高い候補の、min_p倍に満たない候補**を切り捨てます。`min_p = 0.05` なら、トップの候補の5%未満の確率しかない候補を除きます。

```text
トップが「塗」41.2% → しきい値は 41.2% × 0.05 = 2.06%
→ 「凍」1.7%、「煙」1.2%、…… は切り捨て
```

min_pのよいところは、**モデルの自信に合わせて、残す範囲が自動で変わる**ことです。

- トップの候補の確率が高い（モデルが自信を持っている）とき → しきい値が高くなり、候補が少数に絞られる
- トップの候補の確率が低い（いろいろな続け方がありうる）とき → しきい値が低くなり、多くの候補が残る

小説のように「ここは決まった言い回しで、ここは自由に」という場面が混ざる文章では、この性質がとても役に立ちます。

### 適用される順番

`llama-server` は、既定で次の順番でサンプラーを適用します（`llama-server --help` の `--samplers` で確認できます）。

```text
penalties → dry → top_n_sigma → top_k → typ_p → top_p → min_p → xtc → temperature
```

注目してほしいのは、**temperatureが最後**だということです。つまり、top_kやtop_p、min_pによる切り捨ては、temperatureで分布を変える**前の**、モデルそのものの確率で行われます。

この順番のおかげで、**min_pで合わない候補を切り捨ててから、temperatureを上げて残りの候補の中で変化をつける**ことができます。

```console
$ uv run novelist probs "窓の外は白く" -n 12 -p creative --temperature 1.5
  「窓の外は白く」の次のトークン  temperature=1.5  top_k=0
                   top_p=1.0  min_p=0.05
...
│    1 │ '塗'     │    41.2% │ ████████ │  34.9% │ ███████ │
│    2 │ '、'     │    18.7% │ ████     │  20.6% │ ████    │
│    3 │ '染'     │    12.1% │ ██       │  15.4% │ ███     │
│    4 │ '霞'     │     6.4% │ █        │  10.1% │ ██      │
│    5 │ '光'     │     4.3% │ █        │   7.7% │ ██      │
│    6 │ '曇'     │     3.1% │ █        │   6.2% │ █       │
│    7 │ '濁'     │     2.2% │          │   5.0% │ █       │
│    8 │ '凍'     │     1.7% │          │      - │         │
...
```

temperatureは1.5と高いのに、「凍」以下は切り捨てられたままです。残った7つの候補の中では、「霞」「光」「曇」のような、ありきたりでない表現が選ばれやすくなっています。本書では、小説の本文を書くときには **top_kとtop_pを無効にし、min_pで候補を絞ってからtemperatureで変化をつける**方針をとります。

## 9.4 繰り返しを抑える

第7章の実験で、長い文章を書かせると同じ表現を繰り返す傾向があることを見ました。繰り返しを抑える設定もいくつかあります。

### repeat_penalty

直前の一定数のトークン（`repeat_last_n`、既定は64）に出てきたトークンの確率を下げます。1.0で無効、1.1〜1.3程度がよく使われます。

ただし、**日本語では注意が必要**です。「の」「は」「を」「、」「。」のような助詞や句読点は、どんな文章でも何度も出てきます。repeat_penaltyは、これらの確率まで一律に下げてしまうので、強くかけると「助詞が抜ける」「句読点が極端に減る」といった不自然な文章になります。`presence_penalty` と `frequency_penalty` も、同じ問題があります。

### DRY

**DRY**（Don't Repeat Yourself）は、個々のトークンではなく、**トークンの並び**の繰り返しを抑える方法です。

たとえば、「窓の外は白く塗りつぶされていた」という文を一度書いたあとで、また「窓の外は白く」まで書いたとします。DRYは、「このまま進むと、前に書いた並びをそのまま繰り返すことになる」と判断し、前と同じ続き（「塗」）の確率を下げます。繰り返しが長くなるほど、強く下げます。

| パラメータ | 意味 | 既定値 | 本書での値 |
|---|---|---|---|
| `dry_multiplier` | 強さ。0で無効 | 0.0 | 0.8 |
| `dry_base` | 繰り返しが長くなるほど強くする度合い | 1.75 | 既定値 |
| `dry_allowed_length` | この長さまでの繰り返しは許す | 2 | 既定値 |
| `dry_penalty_last_n` | さかのぼって調べるトークン数 | 64 | 既定値 |

短い繰り返し（`dry_allowed_length` 以下）は許されるので、助詞や句読点は影響を受けません。長い言い回しや文の繰り返しだけを抑えられるので、日本語の小説ではrepeat_penaltyよりDRYのほうが扱いやすい方法です。

`dry_sequence_breakers` は、繰り返しの判定をそこで区切る文字の一覧です。既定では改行、`:`、`"`、`*` です。

## 9.5 ありきたりな選択を避ける：XTC

**XTC**（Exclude Top Choices）は、ほかの方法とは逆の発想のサンプラーです。確率が一定以上（`xtc_threshold`）の候補が複数あるとき、**そのうちいちばん確率の低いもの以外を取り除きます**。これを、`xtc_probability` の確率で行います。

「窓の外は白く」の例で、`xtc_threshold = 0.1` とすると、10%以上の候補は「塗」「、」「染」の3つです。XTCが働くと、このうち「染」だけを残し、「塗」と「、」を取り除きます。結果として、「白く染まり」という、もっともありふれた「白く塗りつぶされ」とは違う表現が選ばれます。

最有力の候補を意図的に避けるので、第7章で見た「よくある展開・よくある表現」を崩すのに効果があります。一方で、文法的にそれしかありえない場面でも、候補が複数あれば最有力を外すことがあるので、使いすぎると文章が不自然になります。本書では、意外性を重視したいときの `wild` プロファイルにだけ使います。

## 9.6 シードと再現性

サンプリングは確率に従ってランダムに選ぶので、同じ条件でも実行するたびに結果が変わります。**シード**（`seed`）を固定すると、乱数の出方が固定され、同じ条件なら同じ結果が得られます。

パラメータの効果を比べる実験では、シードを固定して、**パラメータ以外の条件をそろえる**ことが大切です。この章の `sweep` コマンドでは、既定でシードを42に固定します。

ただし、シードを固定しても、GPUの計算のわずかな誤差や、`llama-server` のバージョン、同時に処理しているリクエストなどによって、結果が変わることがあります。「だいたい同じ条件で比べられる」程度に考えてください。

## 9.7 設定ファイルを直す

### 第6章の設定ファイルの問題

第6章では、`SamplingConfig` を `extra="allow"` にして、定義していないパラメータもそのままリクエストに含めるようにしました。`llama-server` の独自のパラメータを、すべて定義しなくても使えるようにするためです。

しかし、この方法には問題がありました。たとえばプロファイルに `temprature = 1.0` と**書き間違えても、エラーにならない**のです。`temprature` という名前の「独自のパラメータ」として送られ、`llama-server` はそれを無視します。temperatureは既定値のまま生成され、利用者は設定が効いていないことに気づけません。

この章で主なパラメータを学んだので、`SamplingConfig` にそれらを明示的に定義し、`extra="forbid"` に変えて、書き間違いをエラーにします。さらに、プロファイルの中身も、**設定ファイルを読み込んだ時点で**検証するようにします。

**`src/novelist/config.py`**（変更後の全文）

```python
"""設定ファイル（novelist.toml）を読み込む。"""

import tomllib
from pathlib import Path
from typing import Any

from pydantic import BaseModel, ConfigDict, Field, ValidationError, model_validator

DEFAULT_CONFIG_PATH = Path("novelist.toml")


class ServerConfig(BaseModel):
    """llama-server への接続設定。"""

    model_config = ConfigDict(extra="forbid")

    url: str = "http://127.0.0.1:8080"  # llama-server のURL（/v1 は付けない）
    model: str = "novelist"  # llama-server の --alias で付けた名前
    api_key: str | None = None  # llama-server の --api-key を使う場合だけ指定
    timeout: float = 600.0  # 1回のリクエストの制限時間（秒）


class SamplingConfig(BaseModel):
    """生成のパラメータ。

    None のパラメータはリクエストに含めず、llama-server の既定値を使う。
    """

    model_config = ConfigDict(extra="forbid")

    temperature: float = 0.8
    top_p: float = 0.95
    max_tokens: int = 1024
    seed: int | None = None
    # ここから下は llama-server 独自のパラメータ（第9章）
    top_k: int | None = None
    min_p: float | None = None
    repeat_penalty: float | None = None
    repeat_last_n: int | None = None
    presence_penalty: float | None = None
    frequency_penalty: float | None = None
    dry_multiplier: float | None = None
    dry_base: float | None = None
    dry_allowed_length: int | None = None
    dry_penalty_last_n: int | None = None
    dry_sequence_breakers: list[str] | None = None
    xtc_probability: float | None = None
    xtc_threshold: float | None = None


class Config(BaseModel):
    """novelist.toml 全体。"""

    model_config = ConfigDict(extra="forbid")

    prompts_dir: Path = Path("prompts")  # プロンプトのテンプレートを置くディレクトリ
    server: ServerConfig = Field(default_factory=ServerConfig)
    sampling: SamplingConfig = Field(default_factory=SamplingConfig)
    profiles: dict[str, dict[str, Any]] = Field(default_factory=dict)

    @model_validator(mode="after")
    def _check_profiles(self) -> "Config":
        """読み込んだ時点で、すべてのプロファイルを検証する。"""
        for name in self.profiles:
            try:
                self.sampling_for(name)
            except ValidationError as e:
                raise ValueError(f"プロファイル '{name}' の設定が正しくありません: {e}") from e
        return self

    def sampling_for(self, profile: str | None = None) -> SamplingConfig:
        """プロファイルの設定で [sampling] を上書きした、生成のパラメータを返す。"""
        if profile is None:
            return self.sampling
        if profile not in self.profiles:
            names = ", ".join(self.profiles) or "(なし)"
            raise KeyError(f"プロファイル '{profile}' がありません。定義済み: {names}")
        merged = self.sampling.model_dump() | self.profiles[profile]
        return SamplingConfig.model_validate(merged)


def load_config(path: Path | None = None) -> Config:
    """設定ファイルを読み込む。ファイルがなければ既定値を使う。"""
    path = path or DEFAULT_CONFIG_PATH
    if not path.exists():
        return Config()
    with path.open("rb") as f:
        data = tomllib.load(f)
    return Config.model_validate(data)
```

**`SamplingConfig`**

- `extra="forbid"` に変えました。定義していない名前のパラメータはエラーになります。
- この章で学んだパラメータを追加しました。既定値はすべて `None` です。第6章の `LLMClient` は `model_dump(exclude_none=True)` でリクエストを作るので、`None` のパラメータは送られず、`llama-server` の既定値が使われます。

**`_check_profiles`**

### サンプラーを再現するモジュール

`probs` コマンドでは、`llama-server` から「サンプラーを適用する前の確率」を受け取り、Python側でサンプラーを適用して「適用後の確率」を計算します。サンプラーの動きを、自分で書いて確かめるためです。

**`src/novelist/llm/sampling.py`**（新規）

```python
"""サンプリングの仕組みを、次のトークンの候補を使って再現する（第9章）。

llama-server は、既定では次の順番でサンプラーを適用する。
  penalties → dry → top_n_sigma → top_k → typ_p → top_p → min_p → xtc → temperature
このモジュールでは、そのうち top_k・top_p・min_p・temperature を、同じ順番で再現する。
"""

import math
from dataclasses import dataclass, replace


@dataclass
class Candidate:
    """次のトークンの候補。"""

    id: int  # トークンのID
    token: str  # トークンの文字列
    prob: float  # 確率


def normalize(candidates: list[Candidate]) -> list[Candidate]:
    """確率の合計が1になるように割り直す。"""
    total = sum(c.prob for c in candidates)
    if total == 0:
        return candidates
    return [replace(c, prob=c.prob / total) for c in candidates]


def apply_top_k(candidates: list[Candidate], k: int) -> list[Candidate]:
    """確率の高い順に k 個だけ残す。k が 0 以下なら何もしない。"""
    if k <= 0:
        return candidates
    return sorted(candidates, key=lambda c: -c.prob)[:k]


def apply_top_p(candidates: list[Candidate], p: float) -> list[Candidate]:
    """確率の高い順に足していき、合計が p に達するまでの候補を残す。"""
    if p >= 1.0:
        return candidates
    kept: list[Candidate] = []
    total = 0.0
    for c in sorted(candidates, key=lambda c: -c.prob):
        kept.append(c)
        total += c.prob
        if total >= p:
            break
    return kept


def apply_min_p(candidates: list[Candidate], min_p: float) -> list[Candidate]:
    """いちばん確率の高い候補の min_p 倍に満たない候補を除く。"""
    if min_p <= 0.0 or not candidates:
        return candidates
    threshold = max(c.prob for c in candidates) * min_p
    return [c for c in candidates if c.prob >= threshold]


def apply_temperature(candidates: list[Candidate], temperature: float) -> list[Candidate]:
    """温度で確率分布の形を変える。0 以下なら、いちばん確率の高い候補だけにする。

    温度 T は、確率 p を p^(1/T) に変えてから割り直すのと同じ。
    """
    if not candidates:
        return candidates
    if temperature <= 0.0:
        best = max(candidates, key=lambda c: c.prob)
        return [replace(best, prob=1.0)]
    logs = [math.log(c.prob) / temperature for c in candidates]
    top = max(logs)  # 大きな数の exp で桁あふれしないように、最大値を引いておく
    weights = [math.exp(x - top) for x in logs]
    total = sum(weights)
    return [replace(c, prob=w / total) for c, w in zip(candidates, weights, strict=True)]


def simulate(
    candidates: list[Candidate],
    *,
    temperature: float,
    top_k: int,
    top_p: float,
    min_p: float,
) -> list[Candidate]:
    """llama-server と同じ順番（top_k → top_p → min_p → temperature）でサンプラーを適用する。"""
    result = normalize(candidates)
    result = normalize(apply_top_k(result, top_k))
    result = normalize(apply_top_p(result, top_p))
    result = normalize(apply_min_p(result, min_p))
    return apply_temperature(result, temperature)
```

- **`Candidate`**：候補のトークンのID、文字列、確率です。トークンのIDを持たせているのは、別のトークンが同じ文字列になることがあるからです（文字の一部のバイトだけのトークンは、どれも「�」と表示されます）。
- **`dataclasses.replace`**：データクラスの一部の値だけを変えたコピーを作ります。確率だけを変えて、IDと文字列はそのまま引き継ぎます。
- **`apply_temperature`**：9.2節の式 p^(1/T) を、対数を使って計算しています。確率の対数をTで割り、最大値を引いてから `exp` で戻しています。最大値を引くのは、`exp` に大きな数を渡して桁あふれするのを防ぐためです（どの値からも同じ数を引いているので、割り直したあとの確率は変わりません）。
- **`simulate`**：`llama-server` の既定の順番（top_k → top_p → min_p → temperature）で、各サンプラーを適用します。各段階で `normalize` して、合計を1に戻しています。

```console

```

```console

```

1.3以上では、助詞が抜けたり、「、」がほとんど使われなくなったりした不自然な文章になるはずです。

### サンプラーのテスト

**`tests/test_sampling.py`**（新規）

```python
import pytest

from novelist.llm.sampling import (
    Candidate,
    apply_min_p,
    apply_temperature,
    apply_top_k,
    apply_top_p,
    simulate,
)

CANDIDATES = [
    Candidate(0, "塗", 0.50),
    Candidate(1, "、", 0.30),
    Candidate(2, "染", 0.15),
    Candidate(3, "霞", 0.05),
]


def tokens(candidates: list[Candidate]) -> list[str]:
    return [c.token for c in candidates]


def test_top_k() -> None:
    assert tokens(apply_top_k(CANDIDATES, 2)) == ["塗", "、"]
    assert tokens(apply_top_k(CANDIDATES, 0)) == ["塗", "、", "染", "霞"]  # 0 は無効


def test_top_p() -> None:
    # 0.50 + 0.30 = 0.80 で 0.8 に達する
    assert tokens(apply_top_p(CANDIDATES, 0.8)) == ["塗", "、"]
    assert tokens(apply_top_p(CANDIDATES, 0.9)) == ["塗", "、", "染"]


def test_min_p() -> None:
    # いちばん高い 0.50 の 0.2 倍 = 0.10 未満を除く
    assert tokens(apply_min_p(CANDIDATES, 0.2)) == ["塗", "、", "染"]


def test_temperature() -> None:
    # 温度1では変わらない
    assert apply_temperature(CANDIDATES, 1.0)[0].prob == pytest.approx(0.50)
    # 温度0.5では確率を2乗して割り直す → 分布がとがる
    squares = [0.25, 0.09, 0.0225, 0.0025]
    assert apply_temperature(CANDIDATES, 0.5)[0].prob == pytest.approx(0.25 / sum(squares))
    # 温度2では分布が平らになる
    assert apply_temperature(CANDIDATES, 2.0)[0].prob < 0.50
    # 温度0ではいちばん確率の高い候補だけ
    assert tokens(apply_temperature(CANDIDATES, 0.0)) == ["塗"]


def test_simulate_applies_min_p_before_temperature() -> None:
    result = simulate(CANDIDATES, temperature=2.0, top_k=0, top_p=1.0, min_p=0.2)
    # 温度を上げても、min_p で除かれた「霞」は復活しない
    assert tokens(result) == ["塗", "、", "染"]
    assert sum(c.prob for c in result) == pytest.approx(1.0)
```

4つの候補（確率0.50、0.30、0.15、0.05）を使って、各サンプラーの結果を手計算と比べています。

- top_pは、0.50＋0.30＝0.80で0.8に達するので、2つが残ります。
- min_pは、0.50×0.2＝0.10未満の「霞」（0.05）を除きます。
- temperatureが0.5のときは、各確率を2乗（1/0.5＝2）してから割り直した値になります。
- `test_simulate_applies_min_p_before_temperature` では、temperatureを2.0に上げても、min_pで除かれた候補は復活しないこと、つまり**min_pがtemperatureより先に適用される**ことを確かめています。

## 9.10 まとめ

- サンプリングは、モデルが出した次のトークンの確率を加工し、どの候補をどのくらいの確率で選ぶかを決める処理です。`novelist probs` で、候補と確率を目で見られるようになりました
- **temperature**は確率の差を強めたり弱めたりします。上げると変化が出ますが、合わない候補の確率も上がり、文章が崩れやすくなります
- **top_k・top_p・min_p**は候補を切り捨てます。**min_p**はモデルの自信に合わせて残す範囲が変わるので、小説に向いています
- `llama-server` では**temperatureが最後に適用される**ので、min_pで切り捨ててからtemperatureで変化をつけられます
- 繰り返しを抑えるには、日本語では **repeat_penaltyよりDRY** が扱いやすく、ありきたりな選択を避けるには **XTC** が使えます
- `novelist sweep` で、シードを固定してパラメータを変えながら書かせ、統計と読み比べで効果を確かめられるようになりました
- `SamplingConfig` にパラメータを明示し、プロファイルの書き間違いを**読み込んだ時点で**エラーにしました

次の第10章では、LLMの出力を**JSONの形式に強制する**構造化出力を学びます。第III部で、企画、設定資料、プロットをプログラムで扱うための土台になります。
