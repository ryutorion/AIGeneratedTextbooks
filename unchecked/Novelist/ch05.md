# 第5章 llama.cppをビルドしてllama-serverを起動する

第4章で、自分のVRAMに合うモデルの選び方を学びました。この章では、実際にそのモデルを動かします。

LLMの推論エンジンである **llama.cpp** をソースからビルドし、付属のHTTPサーバー **llama-server** を起動します。起動したら、ログと `nvidia-smi` で実際のメモリ使用量を確かめ、第4章の見積もりと比べます。最後に、`novelist` から毎回同じ設定でサーバーを起動できるように、起動スクリプトを作ります。

章の終わりには、次の状態になっています。

- `llama-server` がGPUを使って動き、`http://127.0.0.1:8080` でリクエストを受け付けている
- `curl` でチャットのリクエストを送り、応答と生成速度を確認できる
- `scripts/start-server.sh`（Windowsでは `scripts/start-server.ps1`）でサーバーを起動できる

## 5.1 llama.cppとllama-server

**llama.cpp** は、C/C++で書かれたLLMの推論エンジンです。第3章で扱ったGGUF形式は、もともとこのプロジェクトのために作られました。NVIDIA（CUDA）、AMD（HIP / Vulkan）、Apple Silicon（Metal）、CPUなど、幅広い環境で動きます。

llama.cppには、いくつかのプログラムが含まれています。本書で使うのは次の2つです。

| プログラム | 役割 |
|---|---|
| `llama-server` | HTTPサーバー。OpenAI互換のAPIで、チャットの応答やトークン数の計算などを提供する |
| `llama-bench` | 生成速度を計測するベンチマークツール |

第1章で説明したように、`novelist` はPythonから `llama-server` にHTTPでリクエストを送ってLLMを使います。

### ビルドするか、ビルド済みのものを使うか

llama.cppは、ビルド済みのファイルも配布されています（GitHubのReleasesページ、Windowsの `winget install llama.cpp`、macOSやLinuxの `brew install llama.cpp` など）。手軽に試すだけならこれでもかまいません。

本書では、次の理由から**ソースからビルド**します。

- 自分のGPUに合わせて最適化したプログラムを作れる
- 本書で動作を確認したバージョンに合わせられる
- llama.cppは更新がとても速いので、新しいモデルに対応した版をすぐに使える

ビルドといっても、必要なツールをそろえれば、実行するコマンドは2行だけです。

## 5.2 ビルドの準備

使っている環境に合わせて、必要なツールをインストールします。

### Linux（NVIDIA GPU）

Ubuntuの場合、コンパイラとCMake、Gitをインストールします。

```console
$ sudo apt update
$ sudo apt install build-essential cmake git
```

GPUを使うには、**CUDA Toolkit** も必要です。NVIDIAの公式サイト（CUDA Toolkitのダウンロードページ）の手順に従ってインストールしてください。インストールできたら、`nvcc`（CUDAのコンパイラ）が使えることを確認します。

```console
$ nvcc --version
nvcc: NVIDIA (R) Cuda compiler driver
...
Cuda compilation tools, release 12.x, ...
```

`nvcc` が見つからない場合は、CUDA Toolkitの `bin` ディレクトリ（通常は `/usr/local/cuda/bin`）をPATHに追加します。

### Windows（NVIDIA GPU）

次の3つをインストールします。

1. **Visual Studio 2022**（Community版、またはBuild Tools）：インストーラーで「**C++ によるデスクトップ開発**」を選びます。CMakeもこれに含まれています。
2. **Git for Windows**
3. **CUDA Toolkit**：Visual Studioの後にインストールしてください。CUDA ToolkitがVisual Studioと連携するための設定を、インストール時に組み込むためです。

ビルドは、スタートメニューの「**Developer PowerShell for VS 2022**」から実行します。普通のPowerShellでは、コンパイラが見つからないことがあります。

### macOS（Apple Silicon）

Xcodeのコマンドラインツールと、CMakeをインストールします。

```console
$ xcode-select --install
$ brew install cmake
```

Apple SiliconのGPU（Metal）は、特に設定しなくても自動で使われます。

### AMD GPU

AMDのGPUでは、**Vulkan** を使うのがいちばん手軽です。Windows / Linuxとも、Vulkan SDK（LunarG）をインストールしてからビルドします。Linuxでは、パッケージでもインストールできます。

```console
$ sudo apt install libvulkan-dev glslc spirv-headers
$ vulkaninfo --summary     # GPUが表示されることを確認
```

ROCm（HIP）を使う方法もありますが、対応するGPUとOSが限られるので、本書では扱いません。

## 5.3 ソースを取得する

llama.cppのソースは、`novelist` プロジェクトとは別の場所に置きます。本書では `~/src/llama.cpp`（Windowsでは `%USERPROFILE%\src\llama.cpp`）に置くことにします。

```console
$ mkdir -p ~/src
$ cd ~/src
$ git clone https://github.com/ggml-org/llama.cpp
$ cd llama.cpp
```

llama.cppは毎日のように更新され、オプションの名前や既定値が変わることもあります。本書で動作を確認したバージョン（`b11180`）に合わせておきましょう。llama.cppでは、リリースごとに `b` ＋通し番号のタグが付いています。

```console
$ git checkout b11180
```

新しいバージョンを使いたい場合は、`git checkout master` と `git pull` で最新にできます。そのときは、この章のオプションが変わっていないか、`llama-server --help` で確認してください。

## 5.4 ビルドする

`~/src/llama.cpp` で、使っている環境に合わせたコマンドを実行します。1行目（`cmake -B build ...`）でビルドの設定を作り、2行目（`cmake --build ...`）で実際にコンパイルします。

**NVIDIA GPU（Linux / Windows）**

```console
$ cmake -B build -DGGML_CUDA=ON
$ cmake --build build --config Release -j 8
```

**Apple Silicon（macOS）**

```console
$ cmake -B build
$ cmake --build build --config Release -j 8
```

**AMD GPU（Vulkan）**

```console
$ cmake -B build -DGGML_VULKAN=ON
$ cmake --build build --config Release -j 8
```

**CPUのみ**

```console
$ cmake -B build
$ cmake --build build --config Release -j 8
```

`-j 8` は、同時に8つのコンパイルを走らせる指定です。CPUのコア数に合わせて調整してください。CUDAを有効にしたビルドは、数十分かかることがあります。

ビルドが終わると、プログラムは次の場所にできます。

| OS | 場所 |
|---|---|
| Linux / macOS | `~/src/llama.cpp/build/bin/llama-server` |
| Windows | `%USERPROFILE%\src\llama.cpp\build\bin\Release\llama-server.exe` |

### GPUが認識されているか確認する

`--list-devices` で、`llama-server` が使えるGPUを表示します。

```console
$ ~/src/llama.cpp/build/bin/llama-server --list-devices
Available devices:
  CUDA0: NVIDIA GeForce RTX 4070 Ti SUPER (16375 MiB, 15321 MiB free)
```

GPUが表示されていれば成功です。`(none)` と表示された場合は、GPUを使わない設定でビルドされています。CUDA ToolkitやVulkan SDKが正しくインストールされているか確認し、`build` ディレクトリを削除してからビルドし直してください。

```console
$ rm -rf build
```

## 5.5 本番用のモデルをダウンロードする

第4章の手順で選んだモデルをダウンロードします。第3章と同じく `hf` コマンドを使い、`novelist` プロジェクトの `models/` に保存します。以下のコマンドは、`novelist` プロジェクトのルートで実行してください。

```console
$ uvx --from huggingface_hub hf download \
    <リポジトリ名> \
    <ファイル名>.gguf \
    --local-dir models
```

`<リポジトリ名>` と `<ファイル名>` は、Hugging Faceのモデルのページで確認します。GGUF版のリポジトリには、量子化タイプごとにファイルが並んでいるので、第4章で決めた量子化タイプ（Q4_K_Mなど）のファイルを選びます。

大きなモデルは、`...-00001-of-00003.gguf` のように複数のファイルに分割されていることがあります。その場合は、`--include "*Q4_K_M*"` のように指定して、すべてのファイルをダウンロードしてください。`llama-server` には、1つ目のファイル（`-00001-of-`）を指定すれば、残りも自動で読み込まれます。

ダウンロードしたら、第4章で作った `vram-check` で確認しておきます。

```console
$ uv run novelist vram-check models/my-model-14b-Q4_K_M.gguf --kv-type q8_0
...
判定: OK 全層をGPUに載せられます
  llama-server の目安: -ngl 999 -c 32768
```

この章の以降の説明では、第4章と同じ14B級のモデル `models/my-model-14b-Q4_K_M.gguf` を使う例で説明します。自分がダウンロードしたファイル名に読み替えてください。まだ本番用のモデルを用意していない場合は、第3章の練習用モデル（`models/qwen2.5-0.5b-instruct-q4_k_m.gguf`）で試してもかまいません。

## 5.6 llama-serverを起動する

いよいよサーバーを起動します。`novelist` プロジェクトのルートで、次のコマンドを実行します。

```console
$ ~/src/llama.cpp/build/bin/llama-server \
    --model models/my-model-14b-Q4_K_M.gguf \
    --alias novelist \
    --ctx-size 32768 \
    --n-gpu-layers 999 \
    --flash-attn on \
    --cache-type-k q8_0 \
    --cache-type-v q8_0 \
    --parallel 1 \
    --host 127.0.0.1 \
    --port 8080
```

しばらくすると、次のように表示されて、リクエストを待つ状態になります。

```text
... srv  llama_server: model loaded
... srv  llama_server: listening on http://127.0.0.1:8080
```

サーバーを止めるときは、`Ctrl+C` を押します。

### オプションの意味

| オプション | 短い形 | 意味 | 本書での値 |
|---|---|---|---|
| `--model` | `-m` | GGUFファイルのパス | 選んだモデル |
| `--alias` | `-a` | APIで使うモデルの名前 | `novelist` |
| `--ctx-size` | `-c` | コンテキスト長 | `vram-check` で決めた値 |
| `--n-gpu-layers` | `-ngl` | GPUに載せる層の数 | `999`（全層） |
| `--flash-attn` | `-fa` | Flash Attentionを使うか | `on` |
| `--cache-type-k` | `-ctk` | キー（K）のキャッシュの型 | `q8_0` |
| `--cache-type-v` | `-ctv` | 値（V）のキャッシュの型 | `q8_0` |
| `--parallel` | `-np` | 同時に処理するリクエストの数 | `1` |
| `--host` | | 受け付けるアドレス | `127.0.0.1` |
| `--port` | | 受け付けるポート番号 | `8080` |

いくつか補足します。

- **`--alias novelist`**：APIでモデルを指定するときの名前です。付けないとファイル名がモデル名になります。別名を固定しておけば、モデルを入れ替えても `novelist` 側の設定を変えずに済みます。
- **`--n-gpu-layers 999`**：モデルの層の数より大きな値を指定すると、全層をGPUに載せます（`all` と書くこともできます）。部分オフロードにする場合は、`vram-check` が表示した層の数を指定します。
- **`--flash-attn on`**：第4章で説明したように、値（V）のキャッシュを量子化するにはFlash Attentionが必要です。
- **`--cache-type-k` と `--cache-type-v`**：同じ型にそろえてください。CUDA版は、既定では同じ型どうしの組み合わせ（`q8_0` と `q8_0` など）に最適化された処理だけをビルドしていて、異なる組み合わせでは遅い処理に切り替わります。
- **`--host 127.0.0.1`**：自分のPCからの接続だけを受け付けます。`llama-server` には、既定では認証がありません。ネットワークの他のPCに公開しないようにしてください。

MoEモデルでエキスパートの一部をCPUに置く場合は、`vram-check` が表示した `--n-cpu-moe` のオプションを追加します。

### すべてのオプションを明示する理由

最近の `llama-server` は、オプションを省略しても、それなりに動くように作られています。

- `--ctx-size` を省略すると、モデルの学習時のコンテキスト長を使う
- `--n-gpu-layers` や `--parallel` を省略すると、自動で決める
- **`--fit`** という機能（既定で有効）が、指定しなかった設定を、メモリに収まるように自動で調整する

便利ですが、これに任せると、**コンテキスト長がいつの間にか短くなっていた**、**同時処理の数が4になっていて、1つのリクエストで使える長さが減っていた**、といったことが起こりえます。小説の生成では、コンテキスト長がエージェントの設計を左右するので（第3章）、本書ではすべてを明示して、第4章で見積もったとおりの設定で動かします。`--fit` は、指定されなかった設定だけを調整するので、明示した値は変わりません。

`--port` も既定値（8080）と同じですが、将来のバージョンで既定値が変わる予定があるため、明示しています。

## 5.7 ログを読む

`llama-server` は起動時に、モデルの情報やメモリの割り当てをログに出力します。既定の出力は控えめなので、`-lv 4` を付けて詳しいログを表示してみましょう（`-lv` はログの詳しさで、既定は3です）。

```console
$ ~/src/llama.cpp/build/bin/llama-server \
    --model models/my-model-14b-Q4_K_M.gguf \
    ... （5.6節と同じオプション） ...
    -lv 4
```

たくさんの行が表示されますが、メモリに関する行を抜き出すと、次のようになっています（14B級のモデルの例です）。

```text
print_info: file type   = Q4_K - Medium
print_info: file size   = 8.37 GiB (4.87 BPW)
print_info: n_ctx_train           = 131072
print_info: n_layer               = 48
print_info: n_head                = 40
print_info: n_head_kv             = 8
load_tensors: offloaded 49/49 layers to GPU
load_tensors:   CPU_Mapped model buffer size =   417.66 MiB
load_tensors:        CUDA0 model buffer size =  8132.41 MiB
llama_context: n_ctx                 = 32768
llama_context: flash_attn            = enabled
llama_kv_cache:      CUDA0 KV buffer size =  3264.00 MiB
llama_kv_cache: size = 3264.00 MiB ( 32768 cells,  48 layers,  1/1 seqs), K (q8_0): 1632.00 MiB, V (q8_0): 1632.00 MiB
sched_reserve:      CUDA0 compute buffer size =   307.00 MiB
sched_reserve:  CUDA_Host compute buffer size =    74.01 MiB
```

第4章の見積もりと照らし合わせてみましょう。

| 行 | 内容 | 第4章の見積もり |
|---|---|---|
| `offloaded 49/49 layers to GPU` | 48層と出力層がすべてGPUに載った | 判定: OK（全層） |
| `CPU_Mapped model buffer size` | CPU側に置かれた重み。主に語彙の埋め込み | ― |
| `CUDA0 model buffer size` | GPUに置かれた重み | 重み 8.35 GiB（CPU側との合計） |
| `CUDA0 KV buffer size` | KVキャッシュ | 3.19 GiB（= 3264 MiB） |
| `CUDA0 compute buffer size` | 計算用のバッファ | 余白 1.00 GiB に含まれる |

KVキャッシュの `3264.00 MiB` は、第4章で計算した値（1トークンあたり102 KiB × 32768トークン）と完全に一致しています。KとVがちょうど半分ずつ（1632 MiB）であることも確認できます。

`offloaded` の行が `49/49` ではなく `30/49` のようになっていたら、一部の層しかGPUに載っていません。`--n-gpu-layers` の値を確認してください。

※ 上のログは、14B級のモデルをVRAM 16GBのGPUで動かした場合の例です。数値はモデルや環境によって異なります。

## 5.8 動作を確認する

サーバーを起動したまま、**別のターミナル**を開いて、リクエストを送ってみます。

### サーバーの状態

```console
$ curl http://127.0.0.1:8080/health
{"status":"ok"}
```

モデルの読み込み中は `{"error":{"code":503,"message":"Loading model",...}}` が返ります。

### モデルの情報

```console
$ curl http://127.0.0.1:8080/v1/models
```

`"id": "novelist"` と、コンテキスト長（`"n_ctx": 32768`）やパラメータ数などの情報が返ってきます。

### チャットのリクエスト

OpenAI互換のチャットAPI（`/v1/chat/completions`）に、第3章で使ったのと同じメッセージを送ってみます。

```console
$ curl http://127.0.0.1:8080/v1/chat/completions \
    -H "Content-Type: application/json" \
    -d '{
      "model": "novelist",
      "messages": [
        {"role": "system", "content": "あなたは小説家です。"},
        {"role": "user", "content": "雪の駅を舞台に、書き出しの一文を書いてください。"}
      ],
      "max_tokens": 200
    }'
```

Windows の PowerShell では、JSONの引用符の扱いが違うため、このままでは動きません。JSONをファイルに保存して `-d "@request.json"` のように指定するか、第6章で作るPythonのクライアントを待ってください。PowerShellで `curl` と入力すると別のコマンドが実行されることがあるので、`curl.exe` と入力します。

応答は次のようなJSONです（見やすく整形しています）。

```json
{
  "choices": [
    {
      "finish_reason": "stop",
      "index": 0,
      "message": {
        "role": "assistant",
        "content": "終電の去ったホームに、雪だけが律儀に降り続けていた。"
      }
    }
  ],
  "model": "novelist",
  "object": "chat.completion",
  "usage": {
    "completion_tokens": 18,
    "prompt_tokens": 35,
    "total_tokens": 53
  },
  "timings": {
    "prompt_n": 35,
    "prompt_ms": 41.2,
    "prompt_per_second": 849.5,
    "predicted_n": 18,
    "predicted_ms": 318.6,
    "predicted_per_second": 56.5
  }
}
```

| フィールド | 内容 |
|---|---|
| `choices[0].message.content` | 生成された文章 |
| `choices[0].finish_reason` | 生成が止まった理由。`stop` は終了のトークンが出た、`length` は `max_tokens` に達した |
| `usage` | 入力（prompt）と出力（completion）のトークン数 |
| `timings` | 処理時間。`llama-server` 独自の情報 |

`timings` の `prompt_per_second` は入力を読み込む速度、`predicted_per_second` は文章を生成する速度（トークン/秒）です。この例では、1秒あたり約56トークンを生成しています。

### トークン数を数える

第3章で、日本語の文章が何トークンになるかはモデルによって違う、と説明しました。`llama-server` の `/tokenize` を使うと、今動かしているモデルでの実際のトークン数を確かめられます。

```console
$ curl http://127.0.0.1:8080/tokenize \
    -H "Content-Type: application/json" \
    -d '{"content": "窓の外は白く塗りつぶされていた", "with_pieces": true}'
```

`tokens` の配列に、トークンのIDと、そのトークンに対応する文字列（`piece`）が返ってきます。配列の長さがトークン数です。いろいろな文章で試して、1文字あたりのトークン数を確かめてみてください。この機能は、第6章以降でプロンプトの長さを管理するときに使います。

### Web UI

`llama-server` には、ブラウザで使えるチャット画面も付いています。ブラウザで `http://127.0.0.1:8080` を開くと、そのままモデルと会話できます。本書で作るのはCLIですが、モデルの調子をちょっと確かめたいときに便利です。

## 5.9 メモリの実測と速度の計測

### VRAMの使用量を実測する

サーバーを起動した状態で、`nvidia-smi` でVRAMの使用量を確認します。

```console
$ nvidia-smi --query-gpu=memory.total,memory.used --format=csv
memory.total [MiB], memory.used [MiB]
16376 MiB, 12650 MiB
```

起動前のアイドル時の使用量（1.9節で調べた値、この例では812 MiB）を引くと、`llama-server` が使っている量がわかります。

```text
12650 − 812 = 11838 MiB ≒ 11.56 GiB
```

第4章の見積もり（合計 12.54 GiB）より、約1 GiB少なくなりました。この例では、語彙の埋め込み（約0.4 GiB）がCPU側に置かれたことと、計算用のバッファが余白（1 GiB）より小さかったことが理由です。

見積もりが実測より**少なかった**場合は、`vram-check` の `--overhead` を増やして、実測に合わせてください。見積もりが多めになる分には、安全側なので問題ありません。

### llama-benchで速度を計測する

生成速度は、`llama-bench` で計測できます。サーバーと同時に動かすとVRAMが足りなくなるので、**サーバーを止めてから**実行してください。

```console
$ ~/src/llama.cpp/build/bin/llama-bench \
    -m models/my-model-14b-Q4_K_M.gguf \
    -ngl 999 -fa 1 -ctk q8_0 -ctv q8_0 \
    -p 512 -n 128
| model                   |     size |  params | backend | ngl | type_k | type_v | fa |  test |           t/s |
| ----------------------- | -------: | ------: | ------- | --: | -----: | -----: | -: | ----: | ------------: |
| qwen2 14B Q4_K - Medium | 8.37 GiB | 14.77 B | CUDA    | 999 |   q8_0 |   q8_0 |  1 | pp512 | 2850.12 ± 9.4 |
| qwen2 14B Q4_K - Medium | 8.37 GiB | 14.77 B | CUDA    | 999 |   q8_0 |   q8_0 |  1 | tg128 |  57.83 ± 0.12 |
```

| テスト | 意味 |
|---|---|
| `pp512` | 512トークンの入力を読み込む速度（Prompt Processing） |
| `tg128` | 128トークンを生成する速度（Text Generation） |

生成速度（`tg128`）は約58トークン/秒です。第4章4.5節の式で見積もった上限と比べてみましょう。このGPUのメモリ帯域は約672 GB/sなので、重み（8.37 GiB ≒ 9.0 GB）で割ると約75トークン/秒になります。実測値は、その8割程度です。

入力を読み込む速度（`pp512`）は、生成速度よりずっと速くなっています。入力はまとめて並列に計算できますが、生成は1トークンずつしか進められないためです。長い設定資料を入力に入れても、読み込み自体はそれほど時間がかかりません。時間がかかるのは、生成する文章の長さです。

※ 上の結果は、14B級のモデルを RTX 4070 Ti SUPER で動かした場合の例です。

## 5.10 起動スクリプトを作る

毎回長いオプションを入力するのは大変ですし、間違えのもとです。起動のコマンドを、`novelist` プロジェクトのスクリプトにまとめておきましょう。

### Linux / macOS

**`scripts/start-server.sh`**（新規）

```bash
#!/usr/bin/env bash
# llama-server を novelist 用の設定で起動する（Linux / macOS）
#
# 使い方:
#   MODEL=models/xxx.gguf scripts/start-server.sh [llama-server に渡す追加のオプション]
set -euo pipefail

LLAMA_CPP_DIR="${LLAMA_CPP_DIR:-$HOME/src/llama.cpp}"
MODEL="${MODEL:-models/qwen2.5-0.5b-instruct-q4_k_m.gguf}"
CTX="${CTX:-32768}"
KV_TYPE="${KV_TYPE:-q8_0}"
NGL="${NGL:-999}"
PORT="${PORT:-8080}"

exec "$LLAMA_CPP_DIR/build/bin/llama-server" \
  --model "$MODEL" \
  --alias novelist \
  --ctx-size "$CTX" \
  --n-gpu-layers "$NGL" \
  --flash-attn on \
  --cache-type-k "$KV_TYPE" \
  --cache-type-v "$KV_TYPE" \
  --parallel 1 \
  --host 127.0.0.1 \
  --port "$PORT" \
  "$@"
```

- **`set -euo pipefail`**：エラーが起きたら止まる、未定義の変数を使ったらエラーにする、という安全のための設定です。
- **`${MODEL:-...}`**：環境変数 `MODEL` が設定されていればその値を、なければ `:-` の後ろの値（既定値）を使います。モデルやコンテキスト長を、スクリプトを書き換えずに変えられます。
- **`exec`**：スクリプト自身を `llama-server` に置き換えて実行します。`Ctrl+C` がそのまま `llama-server` に届きます。
- **`"$@"`**：スクリプトに渡した引数を、そのまま `llama-server` に渡します。`--n-cpu-moe 27` や `-lv 4` のような追加のオプションを指定できます。

実行できるように権限を付けてから起動します。

```console
$ chmod +x scripts/start-server.sh
$ MODEL=models/my-model-14b-Q4_K_M.gguf scripts/start-server.sh
```

設定を変えて起動する例です。

```console
$ MODEL=models/my-model-14b-Q4_K_M.gguf CTX=16384 scripts/start-server.sh
$ MODEL=models/my-moe-30b-a3b-Q4_K_M.gguf scripts/start-server.sh --n-cpu-moe 27
```

### Windows

**`scripts/start-server.ps1`**（新規）

```powershell
# llama-server を novelist 用の設定で起動する（Windows）
#
# 使い方:
#   scripts\start-server.ps1 -Model models\xxx.gguf [llama-server に渡す追加のオプション]
param(
    [string]$Model = "models\qwen2.5-0.5b-instruct-q4_k_m.gguf",
    [int]$Ctx = 32768,
    [string]$KvType = "q8_0",
    [int]$Ngl = 999,
    [int]$Port = 8080,
    [string]$LlamaCppDir = "$HOME\src\llama.cpp",
    [Parameter(ValueFromRemainingArguments = $true)]
    [string[]]$Rest = @()
)

$server = Join-Path $LlamaCppDir "build\bin\Release\llama-server.exe"

& $server `
    --model $Model `
    --alias novelist `
    --ctx-size $Ctx `
    --n-gpu-layers $Ngl `
    --flash-attn on `
    --cache-type-k $KvType `
    --cache-type-v $KvType `
    --parallel 1 `
    --host 127.0.0.1 `
    --port $Port `
    @Rest
```

PowerShellでは、`param(...)` で名前付きの引数を定義します。`ValueFromRemainingArguments` を指定した `$Rest` には、定義していない残りの引数がすべて入り、`@Rest` で `llama-server` にそのまま渡されます。

PowerShellの既定の設定では、ダウンロードしたスクリプトや自分で作ったスクリプトの実行が制限されています。次のように `-ExecutionPolicy Bypass` を付けて実行してください。

```powershell
PS> powershell -ExecutionPolicy Bypass -File scripts\start-server.ps1 -Model models\my-model-14b-Q4_K_M.gguf
PS> powershell -ExecutionPolicy Bypass -File scripts\start-server.ps1 -Model models\my-moe-30b-a3b-Q4_K_M.gguf --n-cpu-moe 27
```

## 5.11 うまくいかないとき

**`cmake` で「CUDA Toolkit not found」などのエラーが出る**

CUDA Toolkitがインストールされていないか、`nvcc` がPATHにありません。5.2節の手順で `nvcc --version` が動くことを確認してから、`build` ディレクトリを削除してやり直してください。Windowsでは、「Developer PowerShell for VS 2022」から実行しているかも確認します。

**`--list-devices` でGPUが表示されない / 生成がとても遅い**

GPUを使う設定でビルドされていません。`cmake -B build` のオプション（`-DGGML_CUDA=ON` など）を確認し、`build` ディレクトリを削除してビルドし直します。起動時に `warning: no usable GPU found` と表示されるのも同じ原因です。

**起動時に「out of memory」や「failed to allocate」と表示される**

VRAMが足りません。次の順に試してください。

1. `--cache-type-k q8_0 --cache-type-v q8_0` になっているか確認する
2. `--ctx-size` を小さくする（`vram-check` の「最大コンテキスト長」を参考にする）
3. ブラウザなど、VRAMを使うほかのアプリケーションを閉じる
4. 小さいモデル、または低いビット数の量子化のモデルに替える

**生成がやけに遅い（Windows）**

第4章のコラムで説明した「共有GPUメモリ」を使っている可能性があります。タスクマネージャーで「共有GPUメモリ」の使用量を確認してください。

**「address already in use」と表示される**

ポート8080を、ほかのプログラム（前に起動した `llama-server` など）が使っています。前のサーバーを止めるか、`PORT=8081 scripts/start-server.sh` のように別のポートを使ってください。

**応答に `<|im_end|>` のような文字列が混ざる / 応答が終わらない**

チャットテンプレートが正しく使われていない可能性があります。第3章の `novelist inspect --render` で、モデルにチャットテンプレートが含まれているか確認してください。古いGGUFファイルでは、テンプレートが含まれていないことがあります。

## 5.12 まとめ

- llama.cppをソースからビルドしました。GPUに合わせて `-DGGML_CUDA=ON`、`-DGGML_VULKAN=ON` などを指定します
- `llama-server` は、コンテキスト長、GPUに載せる層の数、KVキャッシュの型、同時処理の数などを**すべて明示して**起動します
- ログと `nvidia-smi` で実際のメモリ使用量を確かめ、第4章の見積もりと一致することを確認しました。KVキャッシュは計算どおりの大きさになります
- `/v1/chat/completions` でチャットの応答を、`/tokenize` でトークン数を確認できます。応答の `timings` や `llama-bench` で生成速度を計測できます
- 起動のコマンドを `scripts/start-server.sh`（Windowsでは `scripts/start-server.ps1`）にまとめました
