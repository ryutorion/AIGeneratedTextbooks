# 第10章 構造化出力

これまでの章では、LLMに小説の本文、つまり**自由な文章**を書かせてきました。しかし、第III部で作るパイプラインでは、LLMの出力を**プログラムで扱う**場面が増えていきます。

- 企画案を3つ出させ、その中から1つを選ぶ
- 登場人物の名前、年齢、口調を設定資料として保存し、あとの工程で参照する
- プロットを章とシーンに分け、シーンごとに執筆の指示を組み立てる
- 推敲の工程で、批評を「スコア」と「指摘のリスト」として受け取る

こうした出力を自由な文章で受け取ると、そこから必要な情報を取り出すのが大変です。この章では、LLMの出力を**JSONの形式に制約する**方法と、受け取ったJSONを**Pydanticのモデルとして検証する**方法を学びます。

この章で作るものは次のとおりです。

| ファイル・コマンド | 内容 |
|---|---|
| `src/novelist/llm/structured.py` | JSONスキーマで出力を制約して生成し、検証する。選択肢から選ばせる |
| `src/novelist/schemas/character.py` | 登場人物の設定を表すPydanticのモデル |
| `prompts/cast/` | 登場人物を考えさせるプロンプト |

## 10.1 プロンプトだけで頼むと何が起きるか

まずは、プロンプトで「JSONで出力してください」と頼むだけの方法を考えてみます。

```text
次の条件のミステリー短編に登場する人物を3人考えてください。
次の形式のJSONだけを出力してください。
{"characters": [{"name": "氏名", "age": 年齢, "role": "主人公/相棒/敵対者/脇役"}]}
```

最近のモデルは、多くの場合この指示どおりにJSONを出力します。しかし、**多くの場合**では困るのです。何十回、何百回と呼び出すパイプラインの中では、次のような失敗が必ずどこかで起きます。

- JSONの前後に「以下が登場人物です。」のような説明が付く
- JSONを ```` ```json ```` のコードブロックで囲む
- 閉じかっこを忘れる、最後の要素の後ろに余計な `,` を付ける
- `"age": "34歳"` のように、数値ではなく文字列にする
- `"role": "ヒロイン"` のように、決めた選択肢以外の値を使う
- 項目名を `"名前"` のように日本語に変えてしまう

第8章の `clean_story_text` のように後処理で直す方法もありますが、JSONの壊れ方は多様で、すべてに対応するのは困難です。そこで、**LLMが形式に合わないトークンを選べないようにする**、という根本的な方法をとります。

## 10.2 文法で出力を制約する

### 仕組み

第9章で、サンプリングは「次のトークンの候補から1つを選ぶ」処理だと説明しました。**文法による制約**（grammar-constrained decoding）は、この候補の中から、**決められた文法に合わない候補を取り除いてから**選ぶ方法です。

たとえば、JSONの `{"age": ` まで生成したところで、`age` の値は整数だと決まっているとします。このとき、次の候補のうち、整数として続けられないもの（「三」「"」「歳」など）の確率を0にします。

```text
{"age": ▮
  候補: 「3」40%  「"」25%  「三」15%  「4」10%  「歳」5% ...
                   ↓ 整数として続けられない候補を除く
  候補: 「3」80%  「4」20%
```

モデルがどれだけ「"34歳"」と書きたがっても、文法に合わないトークンは選べないので、**出力は必ず文法どおりになります**。第9章の `temperature` などのサンプラーは、残った候補に対して、いつもどおり働きます。

### GBNF

llama.cppでは、文法を **GBNF**（GGML BNF）という形式で書きます。BNF（バッカス・ナウア記法）は、プログラミング言語などの文法を書くための記法です。

たとえば、「はい」か「いいえ」のどちらかだけを出力させる文法は、次のようになります。

```text
root ::= "はい" | "いいえ"
```

- `root` は、出力全体を表す規則です。
- `::=` の右側が、その規則の中身です。
- `"..."` は、その文字列そのもの、`|` は「または」を表します。

`llama-server` のリクエストに `"grammar"` としてこの文字列を渡すと、LLMは「はい」か「いいえ」のどちらかしか出力できなくなります。第21章の一貫性チェックで「この文章には矛盾がありますか？」と聞くときなどに使えます。

GBNFでは、繰り返しや文字の範囲も書けます。llama.cppのリポジトリの `grammars/` ディレクトリに、JSONや日本語の文字だけに制限する文法などの例があります。

### JSONスキーマから文法を作る

JSONの構造をGBNFで一から書くのは大変です。そこで、`llama-server` には、**JSONスキーマ**を渡すと、それを自動でGBNFに変換してくれる機能があります。

**JSONスキーマ**は、JSONの構造（どんな項目があり、それぞれどんな型か）を、JSONで記述するための標準的な形式です。

```json
{
  "type": "object",
  "properties": {
    "name": {"type": "string", "maxLength": 20},
    "age": {"type": "integer", "minimum": 0, "maximum": 120},
    "role": {"enum": ["主人公", "相棒", "敵対者", "脇役"]}
  },
  "required": ["name", "age", "role"]
}
```

チャットのAPIでは、次のように `response_format` にJSONスキーマを入れて送ります。

```json
{
  "messages": [...],
  "response_format": {
    "type": "json_schema",
    "json_schema": {"schema": { ...JSONスキーマ... }}
  }
}
```

### 制約できること・できないこと

`llama-server` がGBNFに変換できるのは、JSONスキーマの一部の機能です。本書でよく使うものを挙げます。

| 機能 | 例 | 制約できるか |
|---|---|---|
| 型 | `"type": "integer"` | できる |
| 必須の項目 | `"required": [...]` | できる |
| 選択肢 | `"enum": ["主人公", ...]` | できる |
| 文字数 | `"maxLength": 20` | できる |
| 配列の要素数 | `"minItems": 3, "maxItems": 6` | できる |
| 整数の範囲 | `"minimum": 0, "maximum": 120` | できる（整数だけ。小数は不可） |
| 正規表現 | `"pattern": "^[ぁ-ん]+$"` | できる（`^` で始まり `$` で終わる必要がある） |
| 入れ子の参照 | `"$ref": "#/$defs/..."` の中にさらに `$ref` | うまく動かないことがある |
| 項目どうしの関係 | 「主人公はちょうど1人」 | できない |

変換できない機能は、**エラーにならずに黙って無視されます**。また、「主人公はちょうど1人」のように、複数の項目にまたがる条件は、そもそもJSONスキーマでは表せません。そのため、文法で制約したあとも、受け取ったJSONを**プログラムで検証する**必要があります。

### スキーマはプロンプトに入らない

もう1つ大事な注意点があります。`response_format` に渡したJSONスキーマは、**出力の制約にだけ使われ、LLMへの入力には含まれません**。LLMは、どんな項目をどんな意味で埋めればよいのかを知らないまま、文法の制約だけを受けることになります。

これでは、たとえば `secret`（秘密）という項目に何を書けばよいのかわからず、的外れな内容を書いてしまいます。そこで、**プロンプトにもスキーマ（各項目の説明）を書いて**、何を求めているかを伝えます。

```text
プロンプト  ：「何を書くか」を伝える（スキーマの説明を含める）
文法の制約  ：「どんな形で書くか」を強制する
Pydantic   ：「条件を満たしているか」を確かめる
```

この3つを組み合わせるのが、本書の構造化出力の基本形です。

```python
"""登場人物の設定（第10章）。"""

from typing import Literal

from pydantic import BaseModel, Field, model_validator


class Character(BaseModel):
    """登場人物1人の設定。"""

    name: str = Field(description="氏名（漢字）", max_length=20)
    reading: str = Field(description="氏名の読み（ひらがな）", pattern=r"^[ぁ-んー　 ]{1,30}$")
    age: int = Field(description="年齢", ge=0, le=120)
    role: Literal["主人公", "相棒", "敵対者", "脇役"] = Field(description="物語での役割")
    personality: str = Field(description="性格（50字程度）", max_length=100)
    speech_style: str = Field(description="話し方の特徴。一人称と語尾の例を含める", max_length=100)
    goal: str = Field(description="物語の中で求めているもの", max_length=100)
    secret: str = Field(description="ほかの登場人物に隠していること", max_length=100)


class Cast(BaseModel):
    """登場人物の一覧。"""

    characters: list[Character] = Field(min_length=3, max_length=6)

    @model_validator(mode="after")
    def _check_cast(self) -> "Cast":
        """JSONスキーマでは表せない条件を確かめる。"""
        protagonists = [c.name for c in self.characters if c.role == "主人公"]
        if len(protagonists) != 1:
            raise ValueError(f"主人公はちょうど1人にしてください（現在 {len(protagonists)} 人）")
        names = [c.name for c in self.characters]
        duplicates = sorted({n for n in names if names.count(n) > 1})
        if duplicates:
            raise ValueError(f"名前が重複しています: {', '.join(duplicates)}")
        return self
```

**`Field` の引数**

`Field` に渡した引数は、JSONスキーマの対応する機能に変換されます。

| Pydantic | JSONスキーマ | この例での意味 |
|---|---|---|
| `description="..."` | `"description"` | 項目の説明。プロンプトに埋め込んで、LLMに意味を伝える |
| `max_length=20` | `"maxLength": 20` | 20文字まで |
| `pattern=r"^...$"` | `"pattern"` | 正規表現に合う文字列だけ |
| `ge=0, le=120` | `"minimum": 0, "maximum": 120` | 0以上120以下 |
| `min_length=3, max_length=6`（リスト） | `"minItems": 3, "maxItems": 6` | 3〜6人 |

`Literal["主人公", "相棒", "敵対者", "脇役"]` は、4つのうちどれかの文字列という型で、JSONスキーマの `enum` になります。

**`reading` の正規表現**

`reading`（読み）には、`^[ぁ-んー　 ]{1,30}$` という正規表現を指定しています。ひらがなと長音、全角・半角の空白だけからなる1〜30文字、という意味です。この正規表現も文法に変換されるので、LLMは**読みの欄にひらがな以外を書けなくなります**。

**`model_validator` による検証**

`Cast` の `_check_cast` は、10.2節の表で「できない」とした、JSONスキーマでは表せない条件を確かめます。

- 主人公がちょうど1人であること
- 名前が重複していないこと

条件を満たさない場合は `ValueError` を発生させます。Pydanticは、これを `ValidationError` にまとめて、どのモデルでどんな問題があったかを報告します。

### 生成されるJSONスキーマ

`model_json_schema()` が作るJSONスキーマを見てみましょう（一部）。

```json
{
  "$defs": {
    "Character": {
      "description": "登場人物1人の設定。",
      "properties": {
        "name": {"description": "氏名（漢字）", "maxLength": 20, "title": "Name", "type": "string"},
        "reading": {"description": "氏名の読み（ひらがな）", "pattern": "^[ぁ-んー　 ]{1,30}$", ...},
        "age": {"description": "年齢", "maximum": 120, "minimum": 0, "title": "Age", "type": "integer"},
```

`Cast` の中の `Character` は、`$defs` に定義され、`$ref` で参照される形になっています。10.2節の表で見たように、`llama-server` は入れ子になった `$ref` をうまく扱えないことがあります。第14章のプロットでは「プロット → 章 → シーン」のように入れ子が深くなるので、`$ref` を展開して、参照を含まないスキーマに変換してから渡すことにします。

```python
"""LLMの出力を形式に沿って制約し、プログラムで扱える形で受け取る（第10章）。"""

import json
from typing import Any

from pydantic import BaseModel, ValidationError

from novelist.config import SamplingConfig
from novelist.llm.client import ChatResult, LLMClient, LLMError, Message


class StructuredOutputError(LLMError):
    """指定した形式の出力が得られなかったときの例外。"""


def inline_refs(schema: dict[str, Any]) -> dict[str, Any]:
    """$defs と $ref を展開して、参照を含まないスキーマにする。

    llama.cpp は、入れ子になった $ref をうまく扱えないため。
    """
    defs = schema.get("$defs", {})

    def resolve(node: Any) -> Any:
        if isinstance(node, dict):
            if "$ref" in node:
                name = node["$ref"].split("/")[-1]
                return resolve(defs[name])
            return {key: resolve(value) for key, value in node.items() if key != "$defs"}
        if isinstance(node, list):
            return [resolve(item) for item in node]
        return node

    return resolve(schema)


def json_schema_for(model: type[BaseModel]) -> dict[str, Any]:
    """Pydanticのモデルから、llama-server に渡すJSONスキーマを作る。"""
    return inline_refs(model.model_json_schema())


def schema_text(model: type[BaseModel]) -> str:
    """プロンプトに埋め込むための、読みやすいJSONスキーマの文字列。"""
    return json.dumps(json_schema_for(model), ensure_ascii=False, indent=2)


# 出力が途中で切れたときに、max_tokens を増やしてよい上限
DEFAULT_MAX_TOKENS_LIMIT = 16384


def _truncated_message(result: ChatResult, max_tokens: int) -> str:
    """出力が max_tokens で途中で切れたときの、エラーメッセージを作る。"""
    message = f"出力が max_tokens（{max_tokens}）に達して、JSONが途中で切れました。"
    if result.reasoning:
        message += (
            f"出力のうち、思考（reasoning）に{len(result.reasoning)}文字が使われています。"
            'novelist.toml のプロファイルに reasoning_effort = "none" を指定すると、'
            "思考を止められます。"
        )
    else:
        message += "項目の文字数の上限（max_length）が大きすぎないか確かめてください。"
    return message


def generate_structured[T: BaseModel](
    client: LLMClient,
    messages: list[Message],
    model: type[T],
    sampling: SamplingConfig,
    retries: int = 2,
    max_tokens_limit: int = DEFAULT_MAX_TOKENS_LIMIT,
) -> T:
    """JSONスキーマで出力を制約して生成し、Pydanticのモデルとして返す。

    - 出力が max_tokens で途中で切れたら、max_tokens を2倍にしてやり直す（max_tokens_limit まで）
    - 検証に失敗したら、エラーの内容を伝えて書き直させる（最大 retries 回）
    """
    extra = {
        "response_format": {
            "type": "json_schema",
            "json_schema": {"schema": json_schema_for(model)},
        }
    }
    history = list(messages)
    last_error = ""
    failures = 0
    while failures <= retries:
        try:
            result = client.chat(history, sampling, extra=extra)
        except LLMError as e:
            last_error = str(e)
            failures += 1
            continue
        if result.finish_reason == "length":
            # JSONが途中で切れている。上限まで max_tokens を増やしてやり直す
            if sampling.max_tokens >= max_tokens_limit:
                raise StructuredOutputError(_truncated_message(result, sampling.max_tokens))
            new_max = min(sampling.max_tokens * 2, max_tokens_limit)
            sampling = sampling.model_copy(update={"max_tokens": new_max})
            continue
        try:
            return model.model_validate_json(result.text)
        except ValidationError as e:
            last_error = str(e)
            failures += 1
            history = [
                *messages,
                {"role": "assistant", "content": result.text},
                {
                    "role": "user",
                    "content": "出力が次の条件を満たしていません。"
                    f"修正したJSONだけを出力してください。\n\n{e}",
                },
            ]
    raise StructuredOutputError(
        f"{retries + 1}回試しましたが、正しい形式の出力が得られませんでした: {last_error}"
    )


def choice_grammar(options: list[str]) -> str:
    """選択肢のどれか1つだけを出力させるGBNFの文法を作る。"""
    alternatives = " | ".join(json.dumps(option, ensure_ascii=False) for option in options)
    return f"root ::= {alternatives}"


def generate_choice(
    client: LLMClient,
    messages: list[Message],
    options: list[str],
    sampling: SamplingConfig,
) -> str:
    """選択肢のどれか1つを選ばせる。"""
    result = client.chat(messages, sampling, extra={"grammar": choice_grammar(options)})
    answer = result.text.strip()
    if answer not in options:
        raise StructuredOutputError(f"選択肢にない出力です: {answer!r}")
    return answer
```

**`inline_refs`**

JSONスキーマの `$ref` を、`$defs` に定義された中身で置き換えます。入れ子になった関数 `resolve` が、辞書やリストを再帰的にたどり、`$ref` を見つけたら参照先の定義に置き換え（参照先の中にさらに `$ref` があれば、それも置き換え）、`$defs` 自体は取り除きます。

**`json_schema_for` と `schema_text`**

`json_schema_for` は、Pydanticのモデルから `$ref` を展開したJSONスキーマを作ります。`schema_text` は、それをプロンプトに埋め込むための、インデント付きのJSONの文字列にします。`ensure_ascii=False` を指定しないと、日本語の説明が `\u6c0f\u540d...` のようなエスケープになってしまいます。

**`generate_structured`**

構造化出力の中心となる関数です。

1. `response_format` にJSONスキーマを入れて、生成します。
2. `finish_reason` が `length` なら、`max_tokens` に達してJSONが途中で切れています。`max_tokens` を2倍にしてやり直します。上限（`max_tokens_limit`、既定は16384）まで増やしても切れる場合は、`StructuredOutputError` にします。
3. `model.model_validate_json()` で、JSONの文字列を直接Pydanticのモデルに変換し、検証します。
4. 検証に失敗したら、**LLM自身に直させます**。元のメッセージに、LLMの出力（`assistant`）と、エラーの内容（`user`）を付け加えて、もう一度生成します。

4の「直させる」処理は、文法では制約できない条件（主人公が2人いる、など）に対応するためのものです。Pydanticのエラーメッセージは、どの項目がどう間違っているかを具体的に書いてくれるので、そのままLLMへの指示として使えます。

```text
[user]      登場人物を3人考えてください。…
[assistant] {"characters": [{"name": "沢渡透", ..., "role": "主人公"}, {"name": "三枝葉子", ..., "role": "主人公"}, ...]}
[user]      出力が次の条件を満たしていません。修正したJSONだけを出力してください。

            1 validation error for Cast
              Value error, 主人公はちょうど1人にしてください（現在 2 人） ...
```

`llama-server` がエラーを返した場合（`LLMError`）も、何回かやり直します。検証の失敗とエラーは `failures` で数え、`retries` 回までやり直します。一方、2の「途中で切れた」場合は、`max_tokens` が上限に達するまでやり直すので、`failures` には数えていません。

**`_truncated_message`**

途中で切れたときのエラーメッセージを作ります。原因によって対策が違うので、思考の部分があるかどうかで、案内を変えています（次の「思考モデルと max_tokens」を参照）。

**型パラメーター**

`def generate_structured[T: BaseModel](..., model: type[T], ...) -> T` は、Python 3.12から使える**型パラメーター**の書き方です。「`BaseModel` を継承した何かのクラス `T` を受け取り、`T` のインスタンスを返す」という意味です。こう書いておくと、`generate_structured(..., Cast, ...)` の戻り値は `Cast` 型だとエディタが理解し、`result.characters` などの補完が効くようになります。

**`choice_grammar` と `generate_choice`**

選択肢のどれか1つだけを出力させるGBNFを作り、`grammar` として渡して生成します。選択肢の文字列は `json.dumps` でダブルクォートで囲み、中の `"` や `\` をエスケープしています。GBNFの文字列の書き方は、JSONの文字列とほぼ同じだからです。

### 思考モデルと max_tokens

JSONが途中で切れる原因として、特に注意が必要なのが**思考モデル**です。第3章で説明したように、思考モデルは、答えを出力する前に、考えた過程を出力します。この思考の部分も、生成したトークンとして `max_tokens` に数えられます。

```text
max_tokens = 4096 のとき
[思考 ………………………………………… 3500トークン][JSON …… 596トークンで打ち切り]
                                                 ↑ JSONが途中で切れる
```

企画や設定資料のように「よく考えてから答える」課題では、思考が数千トークンに及ぶこともあります。JSONの部分は2000トークン程度でも、思考と合わせると `max_tokens` を超えてしまうのです。

`generate_structured` は、途中で切れたら `max_tokens` を増やしてやり直すので、多くの場合はそのまま動きます。ただし、思考が長いと、そのぶん生成に時間がかかります。構造化出力では、思考を止めたほうが速く、確実なことが多いです。

`llama-server` では、リクエストに `"reasoning_effort": "none"` を指定すると、思考を止められます（対応しているモデルの場合）。これを設定ファイルのプロファイルで指定できるように、`SamplingConfig` に追加します。

```diff
+    受け取ったリクエストは requests に記録する。
+    """
+
+    def __init__(
+        self, contents: list[str], finish_reason: str = "stop", reasoning: str = ""
+    ) -> None:
+        self.contents = list(contents)
+        self.finish_reason = finish_reason
+        self.reasoning = reasoning  # 思考モデルの思考（reasoning_content）として返す文字列
+        self.requests: list[dict] = []
+
+    def __call__(self, request: httpx.Request) -> httpx.Response:
+        body = json.loads(request.content)
+        self.requests.append(body)
+        content = self.contents.pop(0)
+        return httpx.Response(
+            200,
+            json={
+                "choices": [
+                    {
+                        "message": {
+                            "role": "assistant",
+                            "content": content,
+                            "reasoning_content": self.reasoning,
+                        },
+                        "finish_reason": self.finish_reason,
+                    }
+                ]
+            },
+        )
+
+    @property
+    def transport(self) -> httpx.MockTransport:
+        return httpx.MockTransport(self)
```

- **`CAST_DATA`**：3人の登場人物の、正しい形式のデータです。テストでは、これを `copy.deepcopy` でコピーしてから一部を書き換え、わざと条件を満たさないデータを作ります。
- **`ChatRecorder`**：第6章の `fake_llama_server` と違い、用意した応答を**順番に**返します。1回目は間違った出力、2回目は正しい出力、のように、やり直しの処理をテストするのに使います。受け取ったリクエストは `requests` に記録されるので、何が送られたかを確かめられます。`reasoning` を指定すると、思考モデルの思考の部分（`reasoning_content`）も返します。`__call__` を定義したクラスのインスタンスは関数のように呼び出せるので、`httpx.MockTransport` にそのまま渡せます。

`CAST_DATA` と `ChatRecorder` は、テストファイルから `from conftest import ...` で読み込んで使います。pytestは、テストを実行するときに `tests/` ディレクトリを読み込み先に加えるので、このように書けます。

## 10.7 まとめ

- LLMの出力をプログラムで扱うには、形式を**プロンプトで頼むだけでなく、文法で強制する**必要があります
- **文法による制約**は、文法に合わない候補を取り除いてからサンプリングする方法です。llama.cppでは文法を**GBNF**で書きます
- `llama-server` は、**JSONスキーマ**を自動でGBNFに変換します。チャットのAPIでは `response_format` で渡します
- JSONスキーマは**LLMへの入力には含まれない**ので、プロンプトにもスキーマの説明を書きます
- **Pydantic**のモデル1つから、JSONスキーマの生成と、受け取ったJSONの検証の両方ができます。文法で表せない条件は `model_validator` で検証し、満たさなければ**エラーの内容を伝えてLLMに直させます**
- `llama-server` は入れ子の `$ref` が苦手なので、`$ref` を展開してから渡します
- JSONが `max_tokens` で途中で切れたら、`max_tokens` を増やしてやり直します。**思考モデルでは思考の部分も `max_tokens` に数えられる**ので、構造化出力では `reasoning_effort = "none"` で思考を止めるのが確実です
- `novelist cast` で、登場人物の設定を、決まった形式のJSONで作れるようになりました

次の第11章では、**LangGraph**を使って、ここまでに作った部品（プロンプト、サンプリングのプロファイル、構造化出力）を「工程」としてつなぐ方法を学びます。第II部の最後の章で、第III部の多段パイプラインの土台になります。
