# 第28章 好みをフィードバックする — 評価ログから好みルールを抽出し、プロンプトへ反映

第27章で、2つの文章を読み比べて、どちらが好みかと、その理由を記録できるようになりました。記録がたまると、`prefs show` で、どの条件の文章が好まれたかがわかります。しかし、それだけでは、次に書く文章は変わりません。

この章では、記録した好みを、生成に**フィードバック**します。記録の「理由」をLLMに読ませて、「台詞のあとに、その意味を説明する地の文を足さない」のような**好みのルール**を取り出し、本文を書くプロンプトに入れます。また、好みのルールを第26章のルーブリックの観点に加えて、好みに沿っているかを測れるようにします。最後に、第25章の比較実験と第27章の読み比べで、ルールを入れた効果を確かめます。

この章で作るものは次のとおりです。

| ファイル・コマンド | 内容 |
|---|---|
| `src/novelist/feedback.py` | 理由から好みのルールを取り出し、保存し、ルーブリックに加える |
| `prompts/prefs_extract/` | 理由から好みのルールを提案させるプロンプト |
| `prompts/_parts/preferences.md` | 好みのルールを、本文を書くプロンプトに入れる部品 |
| `preferences/rules.md` | 好みのルール（人間が読んで直せるMarkdown） |
| `novelist prefs rules` | 好みのルールを取り出し、1件ずつ確かめて保存する |
| `novelist prefs rubric` | 好みのルールを観点に加えたルーブリックを作る |
| `novelist write --prefs/--no-prefs` | 好みのルールを入れて書くか |

## 28.1 好みを生成に返す方法

### 3つの方法

記録した好みを生成に返す方法は、大きく3つあります。

| 方法 | 内容 | 本書 |
|---|---|---|
| ルールにしてプロンプトに入れる | 好みを言葉のルールにまとめ、本文を書くプロンプトに入れる | この章 |
| 選ばれた文章を見本にする | 好まれた文章を、第23章の文体の見本として入れる | （この章の最後で触れる） |
| モデルに焼き込む | 選ばれた文章と選ばれなかった文章の組で、モデルを追加学習する | 第29章 |

この章では、1つめの方法を使います。ルールは、次の点で扱いやすい方法です。

- **読める・直せる**：ルールは普通の文章なので、何が反映されているのかが、読めばわかります。おかしなルールは、手で直したり消したりできます
- **すぐに効く**：プロンプトに入れるだけなので、学習の時間もGPUも要りません
- **元に戻せる**：`--no-prefs` で、ルールなしで書けます。効果があったかを、比較実験で確かめられます

### 誰が何をするか

本書では、ここまで「LLMには判断を、プログラムには確実にできることを任せる」という方針で作ってきました。この章でも、仕事を3つに分けます。

```text
preferences/ratings.jsonl（理由）
        │
        ▼  LLM: 理由に共通する好みを、ルールとして提案する（根拠の id を挙げる）
  ルールの提案
        │
        ▼  プログラム: 根拠の id が実在するかを確かめ、根拠の数を数え、少ないものを除く
  ルールの候補
        │
        ▼  人間: 1件ずつ読んで、採用・不採用・直して採用を決める
preferences/rules.md
        │
        ├─▶ 本文を書くプロンプト（scene・scene_revise）
        └─▶ ルーブリック rubrics/mine.toml（観点「好み」）
```

LLMは、ばらばらの言葉で書かれた理由から、共通する好みを見つけるのが得意です。「台詞のあとの説明がない」「会話で状況を説明しすぎていない」が同じ好みだと気づけます。一方、LLMは、1件の理由だけから大げさなルールを作ったり、根拠にならない理由を根拠に挙げたりもします。そこで、根拠の数はプログラムで数え、最後は人間が確かめます。

### 好みのルールの落とし穴

好みのルールを作るときには、次のことに気をつけます。

- **少ない記録からの決めつけ**：1回「短い台詞が良い」と答えただけで「台詞はすべて短くする」というルールを作ると、別の場面では合わないことがあります。根拠が `min_support`（既定は2）件に満たないルールは、候補にしません
- **作品に固有のルール**：「葉子の台詞を短くする」のようなルールは、ほかの作品では意味がありません。人物名を使わず、ほかの作品にも当てはまるように書かせます
- **ルールの入れすぎ**：ルールが20も30もあると、プロンプトが長くなり、ひとつひとつのルールが守られにくくなります。プロンプトに入れるのは、根拠の多い順に `max_rules`（既定は10）件までにします
- **ルールどうしの食い違い**：「説明を短くする」と「情景を丁寧に描く」は、場面によってはぶつかります。人間が確かめるときに、気づいたら直します

## 28.2 好みのルールのファイル

好みのルールは、`preferences/rules.md` に、次の形で保存します。

```markdown
# 好みのルール

<!--
novelist prefs rules で、記録した好みから作ります。手で書き足したり、直したりしてかまいません。
「- 」で始まる行が、本文を書くプロンプトに入ります。
「x 」で始まる行は、無効にしたルールです（同じルールが、再び提案されないように残しておきます）。
-->

## 台詞
- 台詞のあとに、その意味を説明する地の文を足さない（根拠 3件）

## 構成
- 説明の段落は短くし、動作と台詞で伝える（根拠 2件）
x 冒頭の段落で、事件か謎を示す（根拠 2件）
```

- `## 種類` の見出しの下に、その種類のルールを並べます。種類は、文章・台詞・描写・人物・構成・その他の6つです。
- `- ` で始まる行が、有効なルールです。`x ` で始まる行は、無効にしたルールです。
- `（根拠 N件）` は、そのルールの根拠になった理由の数です。プロンプトに入れるルールを選ぶときに、根拠の多い順に並べるのに使います。プロンプトには入りません。
- 無効にしたルールを消さずに残しておくのは、次に `prefs rules` を実行したときに、同じルールが再び提案されないようにするためです。

JSONではなくMarkdownにしたのは、人間が直接読んで直すファイルだからです。自分で思いついた好み（「悪役にも事情を持たせる」など）を、手で書き足してもかまいません。

## 28.3 好みのルールを取り出す

**`src/novelist/feedback.py`**（新規）

```python
"""記録した好みから、好みのルールを取り出し、生成と評価に反映する（第28章）。

ルールは preferences/rules.md に、人間が読んで直せるMarkdownとして保存する。
"""

import re
from dataclasses import dataclass
from pathlib import Path
from typing import Literal

from pydantic import BaseModel, Field, ValidationInfo, model_validator

from novelist.config import Config
from novelist.judge import Rubric, RubricCriterion
from novelist.llm.client import LLMClient
from novelist.llm.structured import generate_structured, schema_text
from novelist.preferences import Rating
from novelist.prompts import PromptLibrary

RULES_FILE = "rules.md"
EXTRACT_PROFILE = "precise"
EXTRACT_MAX_TOKENS = 4096
CATEGORIES = ["文章", "台詞", "描写", "人物", "構成", "その他"]
Category = Literal["文章", "台詞", "描写", "人物", "構成", "その他"]


# ---- 理由を集める ----


@dataclass
class ReasonItem:
    """LLMに渡す、理由1件。"""

    id: str  # 記録の id
    line: str  # プロンプトに入れる1行


def reason_items(ratings: list[Rating], limit: int | None = None) -> list[ReasonItem]:
    """理由の書かれた記録を、新しいものから limit 件、プロンプトに入れる形にする。"""
    items = []
    for r in ratings:
        if not r.reason:
            continue
        if r.kind == "score":
            if r.score is None or r.score == 3:
                continue  # 「普通」の採点は、好みの手がかりになりにくい
            head = "好みに合う" if r.score >= 4 else "好みに合わない"
            items.append(ReasonItem(r.id, f"[{r.id}] {head}（採点 {r.score}）: {r.reason}"))
        elif r.choice == "tie":
            items.append(ReasonItem(r.id, f"[{r.id}] どちらも同じくらい: {r.reason}"))
        else:
            items.append(ReasonItem(r.id, f"[{r.id}] 選んだ理由: {r.reason}"))
    return items[-limit:] if limit else items


# ---- LLMに提案させる ----


class RuleProposal(BaseModel):
    """好みのルールの提案1件。"""

    rule: str = Field(
        description="本文を書くときに守る、好みのルール。「〜する」「〜しない」で終わる1文。"
        "人物名や作品に固有の言葉を使わず、ほかの作品にも当てはまるように書く",
        max_length=60,
    )
    category: Category = Field(description="ルールの種類")
    evidence: list[str] = Field(
        description="このルールの根拠になる理由の id。2件以上", min_length=1, max_length=20
    )
    counter: list[str] = Field(
        default_factory=list, description="このルールに反する理由の id。なければ空にする"
    )


class RuleExtraction(BaseModel):
    """好みのルールの提案のリスト。"""

    rules: list[RuleProposal] = Field(description="根拠の多い順に、最大8件", max_length=8)

    @model_validator(mode="after")
    def _check_ids(self, info: ValidationInfo) -> "RuleExtraction":
        """根拠の id が、渡した理由の中にあるかを確かめる（第14章と同じ、検証のコンテキスト）。"""
        ids = (info.context or {}).get("ids")
        if ids is None:
            return self
        unknown = sorted({i for r in self.rules for i in [*r.evidence, *r.counter] if i not in ids})
        if unknown:
            raise ValueError(f"渡した理由にない id があります: {', '.join(unknown)}")
        return self


@dataclass
class Proposal:
    """プログラムで根拠を数えた、ルールの提案。"""

    rule: str
    category: str
    support: int  # 根拠の数（重なりを除く）
    against: int  # 反する理由の数
    reasons: list[str]  # 根拠になった理由（表示用）


def _normalize(text: str) -> str:
    return re.sub(r"[\s。、]", "", text)


def extract_rules(
    client: LLMClient,
    prompts: PromptLibrary,
    config: Config,
    items: list[ReasonItem],
    existing: list["PreferenceRule"],
    min_support: int,
) -> tuple[list[Proposal], list[Proposal]]:
    """理由から好みのルールを提案させ、根拠の数で、採用候補と除外に分ける。

    根拠の数を数えるのはプログラム。LLMが「多くの理由に共通する」と言っても、
    実際に根拠の id が min_support 件以上なければ、候補にしない。
    """
    messages = prompts.render(
        "prefs_extract",
        items=items,
        existing=existing,
        categories=CATEGORIES,
        schema=schema_text(RuleExtraction),
    )
    sampling = config.sampling_for(EXTRACT_PROFILE)
    sampling = sampling.model_copy(
        update={"max_tokens": max(sampling.max_tokens, EXTRACT_MAX_TOKENS)}
    )
    ids = {item.id for item in items}
    result = generate_structured(
        client, messages, RuleExtraction, sampling, validation_context={"ids": ids}
    )
    by_id = {item.id: item.line for item in items}
    known = {_normalize(r.text) for r in existing}
    kept, dropped = [], []
    for p in result.rules:
        evidence = sorted(set(p.evidence))
        against = set(p.counter) - set(evidence)
        proposal = Proposal(
            p.rule, p.category, len(evidence), len(against), [by_id[i] for i in evidence]
        )
        if _normalize(p.rule) in known:
            continue  # すでにあるルール（無効にしたものも含む）は、提案しない
        known.add(_normalize(p.rule))
        ok = proposal.support >= min_support and proposal.support > proposal.against
        (kept if ok else dropped).append(proposal)
    kept.sort(key=lambda p: p.support, reverse=True)
    return kept, dropped


# ---- rules.md ----


@dataclass
class PreferenceRule:
    """好みのルール1つ。"""

    text: str
    category: str
    support: int = 0
    active: bool = True  # False なら、プロンプトに入れない（再び提案されないように残しておく）


RULE_LINE_RE = re.compile(r"^(?P<mark>[-x]) (?P<text>.+?)(?:（根拠 (?P<n>\d+)件）)?$")

RULES_HEADER = """# 好みのルール

<!--
novelist prefs rules で、記録した好みから作ります。手で書き足したり、直したりしてかまいません。
「- 」で始まる行が、本文を書くプロンプトに入ります。
「x 」で始まる行は、無効にしたルールです（同じルールが、再び提案されないように残しておきます）。
-->
"""


def rules_path(preferences_dir: Path) -> Path:
    return preferences_dir / RULES_FILE


def load_rules(path: Path) -> list[PreferenceRule]:
    """rules.md を読み込む。見出し（## 種類）と、ルールの行だけを読み、ほかの行は無視する。"""
    if not path.is_file():
        return []
    rules, category = [], "その他"
    for line in path.read_text(encoding="utf-8").splitlines():
        line = line.strip()
        if line.startswith("## "):
            category = line[3:].strip()
            continue
        m = RULE_LINE_RE.match(line)
        if m:
            support = int(m.group("n")) if m.group("n") else 0
            rules.append(PreferenceRule(m.group("text"), category, support, m.group("mark") == "-"))
    return rules


def save_rules(path: Path, rules: list[PreferenceRule]) -> None:
    """rules.md に、種類ごとにまとめて書く。"""
    categories = [c for c in CATEGORIES if any(r.category == c for r in rules)]
    categories += sorted({r.category for r in rules} - set(categories))
    lines = [RULES_HEADER]
    for category in categories:
        lines.append(f"## {category}")
        for r in rules:
            if r.category == category:
                mark = "-" if r.active else "x"
                support = f"（根拠 {r.support}件）" if r.support else ""
                lines.append(f"{mark} {r.text}{support}")
        lines.append("")
    path.parent.mkdir(parents=True, exist_ok=True)
    path.write_text("\n".join(lines), encoding="utf-8")


def active_rules(path: Path, max_rules: int) -> list[str]:
    """プロンプトに入れるルール。根拠の多い順に、max_rules 件まで。"""
    rules = [r for r in load_rules(path) if r.active]
    rules.sort(key=lambda r: r.support, reverse=True)  # 並べ替えは安定なので、同数ならファイルの順
    return [r.text for r in rules[:max_rules]]


# ---- ルーブリックへの反映 ----


def preference_rubric(base: Rubric, rules: list[str], name: str, weight: float = 1.5) -> Rubric:
    """基のルーブリックに、好みのルールに沿っているかを問う観点「好み」を加える。"""
    question = "次の好みに、どのくらい沿っているか: " + " / ".join(rules)
    taste = RubricCriterion(
        key="taste",
        name="好み",
        question=question,
        weight=weight,
        levels=[
            "好みのほとんどに反している",
            "好みに沿っている点より、反している点のほうが多い",
            "好みに沿っている点と、反している点が同じくらい",
            "好みのほとんどに沿っている。反している点は小さい",
            "好みのすべてに、はっきり沿っている",
        ],
    )
    criteria = [c for c in base.criteria if c.key != "taste"] + [taste]
    description = f"{base.description}（好みのルール {len(rules)}件を加えたもの）"
    return Rubric(name=name, description=description, criteria=criteria)
```

### 理由を集める

`reason_items` は、理由の書かれた記録を、プロンプトに入れる1行にします。

| 記録 | 1行 |
|---|---|
| 読み比べ | `[f8e01c30] 選んだ理由: 台詞のあとの説明がない` |
| 読み比べ（同じくらい） | `[2a9c4e17] どちらも同じくらい: どちらも説明が多い` |
| 採点（4・5） | `[7b3d0f52] 好みに合う（採点 5）: 冒頭ですぐ事件が起きる` |
| 採点（1・2） | `[9c0e1a33] 好みに合わない（採点 2）: 説明が長くて退屈` |

本文は渡しません。読み比べの記録には本文がまるごと入っていますが、30件の記録の本文を合わせると、数十万字になってしまいます。理由だけなら、数十件でも数千字に収まります。採点が3（普通）の記録は、好きとも嫌いとも言えないので、使いません。

行の先頭の `[f8e01c30]` は、記録の `id` です。LLMには、ルールの根拠として、この `id` を挙げさせます。

### 提案させて、根拠を数える

- **`RuleProposal`**：ルールの提案1件です。ルール、種類、根拠の `id`（`evidence`）、反する理由の `id`（`counter`）を書かせます。
- **`RuleExtraction`**：提案のリストです。`model_validator` で、根拠の `id` が、渡した理由の中にあるかを確かめます。第22章の `StateUpdate` と同じく、検証のコンテキスト（`validation_context`）に、渡した `id` の集合を入れて確かめます。ない `id` を挙げていれば、第10章の `generate_structured` が、エラーの内容を伝えて書き直させます。
- **`extract_rules`**：提案を受け取ったら、プログラムで次のことをします。
  1. 根拠の `id` の重なりを除いて、根拠の数（`support`）を数えます。LLMが同じ `id` を2回挙げても、1件と数えます。
  2. 反する理由の数（`against`）を数えます。根拠にも挙がっている `id` は除きます。
  3. すでにあるルール（無効にしたものも含む）と同じルールは、除きます。句読点と空白を除いて比べます。
  4. 根拠が `min_support` 件以上あり、反する理由より多いものを候補（`kept`）にし、ほかを除外（`dropped`）にします。

### ファイルに読み書きする

- **`load_rules`**：`rules.md` を1行ずつ読み、`## ` の見出しと、`- `・`x ` で始まる行だけを読みます。手で書いたメモなど、ほかの行は無視します。`（根拠 N件）` がない行は、根拠0件として読みます。
- **`save_rules`**：種類ごとにまとめて書きます。
- **`active_rules`**：有効なルールを、根拠の多い順に、`max_rules` 件まで返します。Pythonの `sort` は安定なので、根拠の数が同じなら、ファイルに書かれた順のままです。

### ルーブリックに加える

`preference_rubric` は、第26章のルーブリックに、観点「好み」（`taste`）を加えます。問いには好みのルールを並べ、水準は「好みのほとんどに反している」から「好みのすべてに、はっきり沿っている」までの5段階にします。すでに「好み」の観点があれば、置き換えます。

## 28.4 プロンプト

### 好みのルールを取り出すプロンプト

**`prompts/prefs_extract/system.md`**（新規）

```jinja
{# 記録した好みの理由から、好みのルールを取り出す（第28章）。categories、schema を受け取る #}
あなたは、小説の読者の好みを分析する編集者です。
読者が2つの文章を読み比べたときの「選んだ理由」と、文章を採点したときの理由を読み、
読者の好みを、本文を書くときに守れるルールにまとめます。

# ルールの書き方
- 「〜する」「〜しない」で終わる、1文の具体的な指示にする。小説家がそのまま守れるように書く。
- 複数の理由に共通する好みだけをルールにする。1件の理由だけにもとづくルールは作らない。
- 人物の名前や、作品に固有の言葉を使わない。ほかの作品を書くときにも当てはまるように書く。
- 根拠（evidence）には、そのルールの根拠になる理由の id を、すべて挙げる。
- そのルールに反する理由があれば、その id を counter に挙げる。
- 種類は、{{ categories | join("・") }} のどれかにする。
- すでにあるルールと同じ内容のルールは、作らない。

# 出力の形式
次のJSONスキーマに従ったJSONだけを出力する。

{{ schema }}
```

**`prompts/prefs_extract/user.md`**（新規）

```jinja
次の理由から、読者の好みのルールを取り出してください。
{% if existing %}

# すでにあるルール（これと同じ内容は作らない）
{% for r in existing %}
- {{ r.text }}
{% endfor %}
{% endif %}

# 理由
{% for item in items %}
{{ item.line }}
{% endfor %}
```

「1件の理由だけにもとづくルールは作らない」と指示していますが、守られるとは限りません。プログラムで根拠を数えるので、守られなくても、根拠の少ないルールは候補になりません。

### 好みのルールを、本文を書くプロンプトに入れる

**`prompts/_parts/preferences.md`**（新規）

```jinja
{# 好みのルール（第28章）。PromptLibrary の globals で preferences（文字列のリスト）が渡されたときだけ入る #}
{% if preferences is defined and preferences %}
# 好み
この小説の読者（作者自身）の好みです。ここまでの方針と食い違わない範囲で、できるだけ沿ってください。
```

好みのルールを入れて、本当に好みの文章になったのでしょうか。第25章から第27章で作った道具で確かめます。

### 比較実験の条件

**`benches/kiri-prefs/bench.toml`**（新規）

```toml
# 好みのルールの効果を確かめる（第28章）
description = "好みのルールあり・なしの比較"
work = "kiri-no-eki"
scenes = ["1-1", "2-1", "3-1"]
seeds = [1, 2, 3]

[[variants]]
name = "no-prefs"
preferences = false   # 好みのルールを入れない（基準）

[[variants]]
name = "prefs"
preferences = true    # preferences/rules.md の有効なルールを入れる
```

`preferences` に `false` を書いた条件は、好みのルールを入れずに書きます。`true` の条件は、`rules.md` の有効なルールを入れて書きます。

### 3つの方法で比べる

```console
$ uv run novelist bench run kiri-prefs
$ uv run novelist bench judge kiri-prefs --rubric mine
$ uv run novelist bench report kiri-prefs
$ uv run novelist bench compare kiri-prefs prefs no-prefs --rubric mine
$ uv run novelist bench rate kiri-prefs -n 9
$ uv run novelist prefs show
```

1. **点数**（`bench judge --rubric mine` と `bench report`）：好みのルーブリックで採点します。「好み」の観点の点数は、ルールを入れた条件のほうが高くなるはずです。
2. **一対比較**（`bench compare`）：LLMに、2つの条件の本文を比べさせます。
3. **読み比べ**（`bench rate` と `prefs show`）：自分で、条件を伏せて読み比べます。

ここで注意が必要です。1と2は、**ルールを入れたことを、ルールで測っている**ことになります。プロンプトに「台詞のあとに説明を足さない」と書いて書かせた文章を、「台詞のあとに説明を足さないか」という観点で採点すれば、点数が上がるのは当然です。これは、ルールが**守られたか**の確認にはなりますが、ルールが**好みを正しく表しているか**の確認にはなりません。

ルールが好みを正しく表しているかは、3の読み比べでしか確かめられません。`prefs show` の「条件ごとの成績」で、`prefs` が `no-prefs` に勝っていれば、ルールは好みを捉えています。勝っていなければ、ルールが好みとずれているか、ルールを守ろうとして、ほかの部分（テンポや描写など）が犠牲になっている可能性があります。`bench report` で、「好み」以外の観点の点数が下がっていないかも確かめてください。

```text
                条件ごとの成績
┏━━━━━━━━━━┳━━━━━━┳━━━━━━┳━━━━━━━━━━━━┳━━━━━━┓
┃ 条件     ┃ 勝ち ┃ 負け ┃ 同じくらい ┃ 勝率 ┃
┡━━━━━━━━━━╇━━━━━━╇━━━━━━╇━━━━━━━━━━━━╇━━━━━━┩
│ prefs    │ 6    │ 2    │ 1          │ 75%  │
│ no-prefs │ 2    │ 6    │ 1          │ 25%  │
└──────────┴──────┴──────┴────────────┴──────┘
```

※ 上の結果は例です。

### ループを回す

好みのフィードバックは、1回で終わりではありません。

```text
書く ─▶ 読み比べる（理由を書く）─▶ ルールを取り出す ─▶ ルールを入れて書く ─▶ 読み比べる ─▶ …
```

ルールを入れて書いた文章を読み比べると、ルールでは直しきれていない好みが、新しい理由として記録されます。それを `prefs rules` にかけると、新しいルールが提案されます。すでにあるルールは提案されないので、ループを回すたびに、ルールが少しずつ増え、好みに近づいていきます。

ルールが `max_rules` を超えるほど増えたら、根拠の少ないルールや、似たルールを、`rules.md` で整理してください。

> **選ばれた文章を、文体の見本にする**
>
> 28.1節の2つめの方法、好まれた文章を第23章の文体の見本にする方法も、試す価値があります。`ratings.jsonl` から、何度も選ばれた条件の文章を選び、`styles/<名前>/samples/` に入れるだけです。ただし、第23章で見たとおり、見本の内容が本文に持ち込まれやすくなります。同じ作品の文章を見本にすると、人物や出来事がそのまま出てくるので、別の作品を書くときに使ってください。

## 28.10 うまくいかないときは

**ルールが1件も提案されない**

理由の書かれた記録が少ないか、理由がばらばらで、共通する好みが見つかっていません。`prefs show` の「最近の理由」を見て、理由が具体的に書けているかを確かめてください（第27章の27.1節）。「こっちが好き」のような理由からは、ルールを取り出せません。

**提案されるルールが、ありきたり**

「読みやすい文章にする」のような、誰にでも当てはまるルールは、好みのルールとしては役に立ちません。不採用にしてください。不採用にしたルールは、次から提案されません。理由に具体的なことが書かれていないと、ありきたりなルールになりがちです。

**直して採用したルールの、元の文が再び提案される**

`e` で直して採用すると、`rules.md` に残るのは直したあとの文です。元の文は残らないので、次に同じ内容が、元の文のまま提案されることがあります。そのときは不採用にしてください。無効なルールとして残るので、それ以降は提案されません。

**ルールを入れたら、文章がぎこちなくなった**

ルールを守ろうとして、不自然な文章になることがあります。とくに「〜しない」という禁止のルールが多いと、LLMは書き方の選択肢を狭められて、文章が硬くなりがちです。`--no-prefs` と読み比べて、ぎこちなくなったと感じたら、ルールを減らすか、「〜しない」を「〜する」の形に書き直してください（「説明を足さない」→「感情は動作と台詞で示す」）。

**`StructuredOutputError` になる**

理由が多すぎて、プロンプトか出力が長くなりすぎています。`-n 50` のように、使う記録の数を絞ってください。

## 28.11 まとめ

- 記録した好みの**理由**から、LLMに好みの**ルール**を提案させました。根拠の数はプログラムで数え、根拠の少ないルールは候補にしません。最後は人間が、根拠を読んで、採用するかを決めます
- ルールは、人間が読んで直せる `preferences/rules.md` に保存します。不採用にしたルールも、無効なルールとして残し、同じルールが再び提案されないようにしました
- 好みのルールを、Jinjaの**グローバル変数**で、本文を書くプロンプトと推敲のプロンプトに入れました
- 好みのルールを、第26章のルーブリックに観点「好み」として加えられるようにしました
- ルールの効果は、ルールで測るだけでは確かめられません。第27章の**読み比べ**で、自分の好みに近づいたかを確かめます

ルールは、言葉にできる好みを反映する方法です。しかし、好みの中には、言葉にしにくいものもあります。読み比べの記録には、「選ばれた文章」と「選ばれなかった文章」の組がたまっています。第29章では、この組を学習データにして、好みをモデルそのものに焼き込む**LoRA**の流れを扱います。
