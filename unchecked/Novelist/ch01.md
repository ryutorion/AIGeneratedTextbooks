# 第1章 この本で作るもの

本書では、自分のPCで動く**ローカルLLM**を使って、小説を書く**エージェント**を一から実装します。できあがるのは `novelist` というコマンドラインツールです。ジャンルや好みのタグを渡すと、企画・設定・プロット・本文・推敲・矛盾チェックまでを順に進め、1本の小説を仕上げます。

この章ではまだコードを書きません。完成形の動きと全体の構成を先に確認し、第2章以降で何を作るのかを把握しておきます。最後に、手元のマシンのGPUとメモリを確認します。この結果は第4章でモデルを選ぶときに使います。

## 1.1 「小説を書くエージェント」とは

LLMに「ミステリーの短編を書いて」と頼むだけでも、それらしい文章は出てきます。しかし実際にやってみると、次のような問題にすぐぶつかります。

- 数千字を超えると話がまとまらなくなり、途中で終わったり同じ展開を繰り返したりする
- 登場人物の名前や口調、設定が途中で変わる
- 文章が平板で、どの作品も似た雰囲気になる
- 自分の好みを毎回プロンプトに書き直す必要がある

人間の書き手も、いきなり本文を書き始めることはあまりありません。企画を立て、設定を作り、プロットを組み、シーンごとに書き、読み返して直します。本書でいう**エージェント**とは、この工程をプログラムとして組み立て、**状態（設定資料、プロット、ここまでの本文、評価結果など）を持ちながら**LLMを何度も呼び分けて作品を仕上げる仕組みのことです。

工程を分けると、次のような利点があります。

- 1回の呼び出しで扱う範囲が狭くなり、小さめのモデルでも品質を保ちやすい
- 途中の成果物（設定・プロット）を人間が確認して直せる
- 失敗した工程だけやり直せる
- 工程ごとにプロンプトやサンプリング設定を最適化できる

## 1.2 なぜローカルLLMなのか

クラウドのAPIを使えば高性能なモデルをすぐに使えます。それでも本書がローカルLLMを選ぶのは、小説生成という用途と相性が良いからです。

| 観点 | ローカルLLMの利点 |
|---|---|
| コスト | 長編では数十万〜数百万トークンを生成・再生成する。ローカルなら電気代だけで何度でも試せる |
| 制御 | サンプリングパラメータや文法制約、KVキャッシュまで自分で調整できる。文体の制御にはこの自由度が効く |
| 再現性 | モデルファイルとseedを固定すれば、同じ条件で比較実験できる。モデルが勝手に更新されることもない |
| プライバシー | 書きかけの原稿や設定資料が手元から出ていかない |
| 学び | モデルサイズ・量子化・コンテキスト長とVRAMの関係を体感しながら理解できる |

一方で、ローカルLLMは同世代のクラウドの大規模モデルより性能で劣ります。本書では、その差を**工程の分割・設定資料の検索（RAG）・推敲ループ・評価**といったエージェント側の工夫で埋めていきます。これが本書のいちばん大事なテーマです。

## 1.4 全体アーキテクチャ

`novelist` は大きく4つの層に分かれます。

```text
┌───────────────────────────────────────────────────────────────┐
│ CLI 層  (Typer + Rich)                                         │
│   new / plan / write / check / rate / export / vram-check ...  │
└───────────────┬───────────────────────────────────────────────┘
                │ 呼び出し
┌───────────────▼───────────────────────────────────────────────┐
│ パイプライン層  (LangGraph)                                     │
│                                                               │
│  企画 → 設定 → プロット ─┬─▶ シーン執筆 → 推敲 ⇄ 批評          │
│                         │        │                             │
│                         │        ▼                             │
│                         │   一貫性チェック ──▶ 次のシーンへ     │
│                         └──────────────────────────┘          │
│  チェックポイント（中断・再開・人間の介入）                     │
└───────┬───────────────────────┬───────────────────┬───────────┘
        │                       │                   │
┌───────▼─────────┐  ┌──────────▼─────────┐  ┌──────▼──────────┐
│ 知識層           │  │ LLMクライアント層   │  │ 評価層           │
│ ・設定資料RAG     │  │ ・OpenAI互換API     │  │ ・ルーブリック採点 │
│   (sqlite-vec)   │  │ ・サンプリング設定   │  │ ・A/B好み記録     │
│ ・ストーリー状態  │  │ ・構造化出力        │  │ ・好みルール抽出  │
│ ・伏線トラッカー  │  │ ・トークン予算管理   │  │                  │
└─────────────────┘  └──────────┬─────────┘  └─────────────────┘
                                │ HTTP
                    ┌───────────▼────────────┐
                    │ llama-server (llama.cpp) │
                    │   GGUFモデル  on GPU     │
                    └────────────────────────┘
```

| 層 | 役割 | 主に扱う章 |
|---|---|---|
| CLI層 | ユーザーからの入力、進捗表示、ファイルの入出力 | 2, 6, 各部 |
| パイプライン層 | 工程の順序、分岐、ループ、状態の保存 | 11〜17, 30〜32 |
| 知識層 | 設定資料の検索、登場人物の現在状態、伏線の管理 | 18〜22, 31 |
| LLMクライアント層 | llama-serverとの通信、サンプリング、構造化出力 | 6, 8〜10, 20 |
| 評価層 | 生成物の採点、好みの記録と反映 | 16, 25〜29 |

LLM本体（llama-server）はPythonとは**別プロセス**で動かし、HTTPで通信します。こうしておくと、次の利点があります。

- Pythonの仮想環境とGPU向けのビルドを切り離せる。llama.cppをCUDA付きでビルドし直しても、Python側には影響しない
- サーバーの起動パラメータ（GPUに載せる層の数やコンテキスト長など）を、コードを変えずに試せる
- OpenAI互換APIで話すので、必要なら別の推論エンジンに差し替えられる

## 1.5 技術スタック

| 用途 | 採用するもの | 選んだ理由 |
|---|---|---|
| プロジェクト管理 | **uv** | Pythonのインストール、仮想環境、依存関係の解決とロックを1つのツールで高速に扱える |
| 言語 | Python 3.12 | LLM周辺のライブラリがそろっている |
| 推論エンジン | **llama.cpp**（llama-server） | GGUF形式の量子化モデルを、NVIDIA / AMD / Apple Silicon / CPU で動かせる。量子化やKVキャッシュを細かく指定できる |
| モデル形式 | **GGUF** | 1ファイルに重みとメタデータ（層の数、チャットテンプレートなど）が入っている。第4章のVRAM見積もりでもこのメタデータを読む |
| HTTPクライアント | httpx | llama-serverのAPIを直接呼ぶ。独自のパラメータや処理時間の情報も素直に扱える（第6章） |
| エージェント構築 | **LangGraph** | 状態を持つグラフとして工程を組める。チェックポイントと人間の介入を標準で扱える |
| データ構造 | Pydantic | 設定資料やプロットを型付きで扱い、LLMの出力を検証する |
| CLI | Typer + Rich | サブコマンドの定義が簡潔。進捗やストリーミングの表示がきれいに出せる |
| ベクトル検索 | sqlite-vec | SQLiteの拡張として動くので、別のサーバーが要らない。作品ごとに1ファイルで管理できる |
| 開発補助 | pytest, ruff | テストとLint/フォーマット |

ライブラリの正確なバージョンは、第2章から作るプロジェクトの `uv.lock` に固定します。本書の手順どおりに進めれば、同じバージョンで再現できます。

## 1.9 ハンズオン：自分のマシンを確認する

第4章でモデルを選ぶときに使う値を、今のうちに調べておきましょう。**GPUの名前とVRAM容量**、**メインメモリの容量**、**ストレージの空き容量**の3つです。

### NVIDIA GPU（Windows / Linux）

ドライバが入っていれば `nvidia-smi` が使えます。Windowsでは PowerShell、Linuxではターミナルで実行します。

```console
$ nvidia-smi --query-gpu=name,memory.total,memory.used,driver_version --format=csv
name, memory.total [MiB], memory.used [MiB], driver_version
NVIDIA GeForce RTX 4070 Ti SUPER, 16376 MiB, 812 MiB, 5xx.xx
```

`memory.used` にも注目してください。画面表示やブラウザが、すでにVRAMの一部を使っています。LLMに使えるのは `memory.total - memory.used` です。GPUが2枚以上ある場合は、1行に1枚ずつ表示されます。

### AMD GPU

- Linux：`rocm-smi --showmeminfo vram`
- Windows：タスクマネージャー →「パフォーマンス」→ GPU →「専用GPUメモリ」

### Apple Silicon（macOS）

## 1.10 本書のコード表記

本書では、コードの掲載方法を次のルールで統一します。

### ルール1：すべてのコードにファイルパスを付ける

コードの直前に、プロジェクトのルート（`novelist/`）からのパスを書きます。

### ルール2：新しいファイルは全文を掲載する

初めて出てくるファイルは、省略せずに全文を載せます。そのまま書き写せば動きます。

**`examples/notation/greet.py`**（新規）

```python
def greet(name: str) -> str:
    return f"こんにちは、{name}さん"


if __name__ == "__main__":
    print(greet("読者"))
```

### ルール3：既存ファイルの変更は差分で示す

すでにあるファイルを変更するときは、`diff` 形式で示します。行頭の `+` は追加、`-` は削除した行です。記号のない行は変更していない前後の行で、どこを変えたかの目印です。

**`examples/notation/greet.py`**（変更）

```diff
-def greet(name: str) -> str:
-    return f"こんにちは、{name}さん"
+def greet(name: str, polite: bool = True) -> str:
+    if polite:
+        return f"こんにちは、{name}さん"
+    return f"やあ、{name}"


 if __name__ == "__main__":
     print(greet("読者"))
+    print(greet("読者", polite=False))
```

変更が大きい場合や、差分だと読みにくい場合は、変更後の全文を載せます。その場合は見出しに「（変更後の全文）」と書きます。

### ルール4：コマンドと出力を区別する

- `$` で始まる行は、あなたが入力するコマンドです（`$` 自体は入力しません）
- `PS>` で始まる行は、Windows PowerShell で入力するコマンドです
- 記号のない行は出力です
- LLMの出力例は、モデルや設定によって毎回変わります

コマンドは、特に断りがない限り**プロジェクトのルートディレクトリ**で実行します。
