# 第20章 コンテキスト予算の管理

第18章と第19章で、設定資料と本文を、意味の近さで検索できるようになりました。この章では、その検索を**本文の執筆に組み込みます**。シーンを書くたびに、そのシーンに関係する設定資料と過去の本文を探して、プロンプトに入れます。

ここで問題になるのが、**プロンプトの大きさ**です。第15章から、シーンを書くプロンプトには、シーンカード、登場人物、これまでのあらすじ、直前の文章を入れてきました。そこに検索の結果が加わります。しかも、作品が長くなるほど、あらすじは増え、検索で見つかる本文も増えます。何も考えずに入れていくと、いつかモデルのコンテキスト長を超えてしまいます。

コンテキスト長を超えなくても、入れすぎには害があります。第15章で見たとおり、長い入力の中ほどは読み落とされやすく、関係の薄い情報は、かえって本文を混乱させます。入力が長ければ、読み込みにも時間がかかります。

この章では、プロンプトに使えるトークン数を**予算**として計算し、入れたい情報に**優先順位**を付けて、予算に収まるものだけを選ぶ仕組みを作ります。

この章で作るものは次のとおりです。

| ファイル・コマンド | 内容 |
|---|---|
| `src/novelist/context.py` | トークン数を数え、優先順位に沿って予算に詰める |
| `src/novelist/rag/retrieve.py` | シーンに関係する設定資料と過去の本文を検索する |
| `src/novelist/graph/nodes/context.py` | シーンを書く前に、プロンプトに入れる情報を選ぶノード |

| `novelist context` | シーンのプロンプトの予算の内訳を表示するコマンド |

## 20.1 プロンプトの予算

### 何にトークンを使うか

1つのシーンを書くとき、コンテキスト長は、次のように使われます。

```text
┌───────────────────────── コンテキスト長（例: 32,768トークン）─────────────────────────┐
│ 必ず入れる部分 │ あらすじ │ 関連する設定 │ 過去の本文 │ 生成する本文と推敲 │ 余白 │
│  （固定）      │ ←─────── 予算に合わせて選ぶ ───────→ │  （目安の文字数×3） │      │
└──────────────────────────────────────────────────────────────────────────────────────┘
```

| 部分 | 内容 | 扱い |
|---|---|---|
| 必ず入れる部分 | システムプロンプト、作品と世界の設定、用語、場所、このシーンの登場人物、シーンカード、直前の文章、次のシーン | 省けない |
| あらすじ | これまでのシーンの要約 | 古いものから省く |
| 関連する設定 | 検索した設定資料 | 類似度の低いものから省く |
| 過去の本文 | 検索した過去の本文のチャンク | 類似度の低いものから省く |
| 生成する本文と推敲 | 本文の生成（`max_tokens`）と、推敲のときにプロンプトに入れる原稿 | あらかじめ確保する |
| 余白 | チャットテンプレートの記号など | あらかじめ確保する |

**生成する本文の分を、先に確保する**ことが大事です。llama-server では、入力と出力のトークン数の合計が、コンテキスト長を超えられません。入力で使い切ってしまうと、本文を書く余地がなくなります。

本文を書くときの `max_tokens` は、第15章で、目安の文字数の2倍にしました。さらに、第16章の推敲では、書いた原稿をプロンプトに入れてから、もう一度書き直させます。そのため、推敲のときの入力は、原稿の分（目安の文字数くらい）だけ長くなります。この両方に備えて、**目安の文字数の3倍**を確保します。

**余白**は、チャットテンプレート（第3章）が、メッセージの前後に付ける記号などのためのものです。トークン数を数えるのはメッセージの本文だけなので、その分を見込んでおきます。

「必ず入れる部分」「生成する本文と推敲」「余白」を、コンテキスト長から引いた残りが、**使える予算**です。あらすじ、関連する設定、過去の本文は、この予算の中に収まるだけ入れます。

### トークン数を数える

予算はトークン数で決まるので、プロンプトに入れる文字列のトークン数を数える必要があります。第6章で作った `count_tokens` は、llama-server の `/tokenize` で、**本文を書くモデルのトークナイザー**を使って数えます。第3章で見たとおり、同じ日本語でも、トークナイザーによってトークン数はかなり違うので、実際に使うモデルで数えるのが確実です。

ただし、`/tokenize` は、呼ぶたびにサーバーとのやりとりが発生します。同じあらすじは、シーンを書くたびに何度も数えることになるので、一度数えたものは覚えておくようにします（**キャッシュ**）。

### 優先順位と割り当て

使える予算に、あらすじ、関連する設定、過去の本文の3つを詰めます。詰め方は、次のようにします。

1. **区画ごとに、まず割り当てる**：あらすじに予算の40%、関連する設定に30%、過去の本文に30%を割り当て、それぞれ、その範囲に収まるだけ入れます。
2. **余りを使う**：どれかの区画が割り当てを使い切らなかった場合（たとえば、最初のほうのシーンで、あらすじが少ない場合）は、余った予算を、あらすじ、関連する設定、過去の本文の順に使って、さらに入れます。

区画の中では、**大事な順**に入れていきます。

- **あらすじ**は、新しいものほど大事です。直前のいくつかのシーンで何が起きたかは、次のシーンを書くのに欠かせません。一方、物語の序盤の細かい出来事は、要約の要約があれば足ります。そこで、**古いあらすじから省きます**。省いたことは、「最初の3シーンのあらすじは省略」のように、プロンプトに書いておきます。
- **関連する設定**と**過去の本文**は、検索の類似度の高い順です。

情報は、**途中で切らずに、1件ずつ丸ごと**入れます。あらすじの途中や、設定の説明の途中で切ると、意味が変わってしまうことがあるからです。入らない情報があれば、そこで止めます。小さな情報なら入るとしても、大事な順を飛ばして入れることはしません。

最初のあらすじまでさかのぼるような、長い物語全体の要約は、第VII部で、章ごとの要約を積み上げる方法として扱います。

```python
"""プロンプトに入れる情報を、トークンの予算の中に収める（第20章）。"""

import math
from collections.abc import Callable
from dataclasses import dataclass

from novelist.rag.index import SearchResult
from novelist.writing import SceneBrief

# 使える予算のうち、まず各区画に割り当てる割合。余った分は、あとで前の区画から順に使う
SUMMARY_SHARE = 0.4  # これまでのあらすじ
BIBLE_SHARE = 0.3  # 検索した設定資料
SCENE_SHARE = 0.3  # 検索した過去の本文


class ContextBudgetError(Exception):
    """予算が足りず、プロンプトを組み立てられないときの例外。"""


class TokenCounter:
    """文字列のトークン数を数える。同じ文字列は、一度数えたら覚えておく。"""

    def __init__(self, count: Callable[[str], int]) -> None:
        self._count = count
        self._cache: dict[str, int] = {}

    def __call__(self, text: str) -> int:
        if text not in self._cache:
            self._cache[text] = self._count(text)
        return self._cache[text]

    @classmethod
    def by_chars(cls, ratio: float = 1.0) -> "TokenCounter":
        """文字数から見積もる（1文字 = ratio トークン）。テストや、サーバーがないときに使う。"""
        return cls(lambda text: math.ceil(len(text) * ratio))


@dataclass
class Item:
    """予算に詰める情報の1件。"""

    text: str
    order: int  # プロンプトに並べる順番


@dataclass
class Section:
    """予算に詰める情報の区画。"""

    name: str
    items: list[Item]  # 大事な順に並べる
    share: float  # 予算のうち、まず割り当てる割合


def pack(
    sections: list[Section], budget: int, count: Callable[[str], int]
) -> tuple[dict[str, list[Item]], dict[str, int]]:
    """区画ごとに、大事な順に、予算に収まるだけの情報を選ぶ。

    1回目は、各区画に割り当てた範囲（予算 × share）で詰める。
    2回目は、余った予算を、前の区画から順に使って、さらに詰める。
    情報は途中で切らず、1件ずつ丸ごと入れる。
    戻り値は、区画ごとに選んだ情報（order の順に並べ直したもの）と、使ったトークン数。
    """
    chosen: dict[str, list[Item]] = {s.name: [] for s in sections}
    used: dict[str, int] = {s.name: 0 for s in sections}

    def fill(section: Section, limit: int) -> None:
        for item in section.items[len(chosen[section.name]) :]:
            n = count(item.text)
            if used[section.name] + n > limit or sum(used.values()) + n > budget:
                break  # 大事な順に並んでいるので、入らなければ、そこで止める
            chosen[section.name].append(item)
            used[section.name] += n

    for section in sections:
        fill(section, int(budget * section.share))
    for section in sections:
        fill(section, budget)
    return {name: sorted(items, key=lambda i: i.order) for name, items in chosen.items()}, used


@dataclass
class ContextPlan:
    """1つのシーンのプロンプトの、トークンの予算と、選んだ情報。"""

    total: int  # コンテキスト長
    fixed: int  # 必ず入れる部分（シーンカード、登場人物、直前の文章など）
    reserved: int  # 生成する本文と、推敲で入れる原稿のための分
    margin: int  # チャットテンプレートなどのための余白
    summaries: list[str]  # 入れるあらすじ（古い順）
    omitted_summaries: int  # 省いた古いあらすじの数
    related_bible: list[str]
    related_scenes: list[str]
    used: dict[str, int]  # 区画ごとに使ったトークン数

    @property
    def available(self) -> int:
        """あらすじと検索の結果に使える予算。"""
        return self.total - self.fixed - self.reserved - self.margin

    def describe(self) -> str:
        """ログに出す説明。"""
        n_summaries = len(self.summaries) + self.omitted_summaries
        return (
            f"文脈: あらすじ {len(self.summaries)}/{n_summaries}件、"
            f"関連する設定 {len(self.related_bible)}件、過去の本文 {len(self.related_scenes)}件"
            f"（{sum(self.used.values()):,}/{self.available:,}トークン）"
        )


def plan_scene_context(
    brief: SceneBrief,
    count: Callable[[str], int],
    total: int,
    fixed: int,
    reserved: int,
    margin: int,
    bible: list[SearchResult],
    scenes: list[SearchResult],
) -> ContextPlan:
    """これまでのあらすじと検索の結果から、予算に収まるものを選ぶ。

    bible と scenes は、近い順に並んだ検索の結果。
    """
    available = total - fixed - reserved - margin
    if available < 0:
        raise ContextBudgetError(
            f"コンテキスト長（{total:,}トークン）が足りません。必ず入れる部分に{fixed:,}、"
            f"本文の生成と推敲に{reserved:,}トークンが必要です。llama-server の --ctx-size を"
            "大きくするか、プロットのシーンの目安の文字数を減らしてください"
        )
    summaries = [Item(text, n) for n, text in enumerate(brief.story_so_far)]
    sections = [
        # あらすじは、新しいものほど大事。古いものから省く
        Section("summaries", summaries[::-1], SUMMARY_SHARE),
        Section(
            "bible",
            [Item(f"{r.chunk.label}: {r.chunk.text}", n) for n, r in enumerate(bible)],
            BIBLE_SHARE,
        ),
        Section(
            "scenes",
            [Item(f"{r.chunk.label}\n{r.chunk.text}", n) for n, r in enumerate(scenes)],
            SCENE_SHARE,
        ),
    ]
    chosen, used = pack(sections, available, count)
    return ContextPlan(
        total=total,
        fixed=fixed,
        reserved=reserved,
        margin=margin,
        summaries=[item.text for item in chosen["summaries"]],
        omitted_summaries=len(summaries) - len(chosen["summaries"]),
        related_bible=[item.text for item in chosen["bible"]],
        related_scenes=[item.text for item in chosen["scenes"]],
        used=used,
    )
```

**`TokenCounter`**

トークン数を数える関数を包んで、結果を辞書に覚えておくクラスです。インスタンスを関数のように呼べるように、`__call__` を定義しています（第19章の `CountingEmbedder` と同じです）。`by_chars` は、サーバーを使わずに、文字数から見積もる `TokenCounter` を作ります。テストで使います。

**`Item` と `Section`**

予算に詰める情報の1件と、情報の区画です。`Item` の `order` は、プロンプトに並べるときの順番です。区画の中では大事な順に並べて詰めますが、プロンプトには、元の順（あらすじなら古い順）に並べ直して入れます。

**`pack`**

20.1節の詰め方を実装した関数です。内側に定義した `fill` 関数で、1つの区画に、上限（`limit`）まで情報を詰めます。1回目は、各区画の割り当て（`budget * section.share`）を上限にし、2回目は、予算全体を上限にして、1回目の続きから詰めます。

`fill` は、外側の関数の `chosen` と `used` を書き換えています。辞書の中身を書き換えるだけで、変数そのものに別の値を代入するわけではないので、`nonlocal` の宣言は要りません。

戻り値は、区画ごとに選んだ情報と、使ったトークン数の2つです。

**`ContextPlan`**

1つのシーンの予算の内訳と、選んだ情報をまとめたものです。`describe` は、ログに出す1行の説明を作ります。

**`plan_scene_context`**

あらすじと検索の結果を、3つの区画にして `pack` に渡します。

- あらすじは、`summaries[::-1]` で、新しい順に並べ替えてから渡します。`[::-1]` は、リストを逆順にする書き方です。
- 使える予算が負になる場合は、必ず入れる部分だけでコンテキスト長が足りないということです。どうすればよいかを示して、`ContextBudgetError` にします。

```python
"""シーンを書くときに、関係する設定資料と過去の本文を検索する（第20章）。"""

from novelist.llm.embedding import EmbeddingClient
from novelist.rag.index import SearchResult, VectorIndex
from novelist.schemas.plot import Plot
from novelist.schemas.scene import scene_key
from novelist.writing import SceneBrief

# 設定資料のうち、プロンプトに必ず入れるので、検索の結果から除く種類
ALWAYS_INCLUDED = ("世界:", "用語:")


def scene_query(brief: SceneBrief) -> str:
    """シーンカードから、検索に使う文を作る。"""
    scene = brief.scene
    return "\n".join([scene.title, scene.goal, scene.conflict, scene.outcome, *scene.beats])


def retrieve_for_scene(
    index: VectorIndex,
    embedder: EmbeddingClient,
    brief: SceneBrief,
    plot: Plot,
    bible_k: int,
    scene_k: int,
) -> tuple[list[SearchResult], list[SearchResult]]:
    """シーンに関係する設定資料と、それより前のシーンの本文を、近い順に返す。

    プロンプトにすでに入っている情報（このシーンの人物と場所、世界の概要、用語）と、
    このシーン以降の本文（書き直しのときに残っている、古い版の本文）は除く。
    除いたあとで件数が足りるように、多めに検索してから絞り込む。
    """
    query = embedder.embed_query(scene_query(brief))
    included = {f"人物:{c.name}" for c in brief.characters} | {f"場所:{brief.scene.place}"}
    bible = [
        r
        for r in index.search(query, (bible_k + len(included)) * 2, "bible")
        if r.chunk.ref not in included and not r.chunk.ref.startswith(ALWAYS_INCLUDED)
    ][:bible_k]

    order = [scene_key(i, j) for i, j, _ in plot.scenes()]
    earlier = set(order[: order.index(brief.key)])
    scenes = [r for r in index.search(query, scene_k * 4, "scene") if r.chunk.ref in earlier]
    return bible, scenes[:scene_k]
```

**`scene_query`**

シーンカードの見出し、目的、葛藤、結果、出来事を、改行でつないで、検索のクエリにします。これから書くシーンに何が出てくるかを、いちばんよく表しているのがシーンカードだからです。

**`retrieve_for_scene`**

設定資料と本文を、別々に検索します。第19章で見たとおり、まとめて検索すると、設定資料が上位を占めがちだからです。

検索の結果からは、次のものを除きます。

- **プロンプトにすでに入っている設定資料**：このシーンの登場人物と場所、世界の概要、用語は、必ず入れる部分に含まれているので、検索の結果として入れると、同じ情報が二重になります。
- **このシーン以降の本文**：`--from` で書き直すとき（第15章）は、インデックスに、書き直す前の古い本文が残っています。これから書き直すシーンや、その先のシーンの古い本文を参考にすると、古い展開に引きずられてしまいます。

除く分を見込んで、多めに検索してから絞り込み、上限の件数（`bible_k`、`scene_k`）までにします。

```python
"""シーンを書く前に、プロンプトに入れる情報を予算に合わせて選ぶノード（第20章）。"""

from dataclasses import replace

from langgraph.runtime import Runtime

from novelist.context import ContextBudgetError, ContextPlan, TokenCounter, plan_scene_context
from novelist.graph.nodes.write import WRITE_TOKENS_RATIO, scene_brief
from novelist.graph.state import WriteContext, WriteState
from novelist.rag.index import update_work_index
from novelist.rag.retrieve import retrieve_for_scene
from novelist.schemas.bible import WorldSheet
from novelist.schemas.plot import Plot
from novelist.schemas.work import WorkMeta
from novelist.writing import SceneBrief


def plan_for_scene(
    ctx: WriteContext, meta: WorkMeta, world: WorldSheet, plot: Plot, brief: SceneBrief
) -> tuple[ContextPlan, list[str]]:
    """1つのシーンのプロンプトの予算を計算し、入れる情報を選ぶ。ログに出す行も返す。

    グラフのノード（gather_context）と、context コマンドの両方から使う。
    """
    settings = ctx.config.context
    count = ctx.tokens or TokenCounter(ctx.client.count_tokens)
    total = settings.max_tokens or ctx.client.server_info().n_ctx
    if total is None:
        raise ContextBudgetError(
            "コンテキスト長がわかりません。"
            "novelist.toml の [context] に max_tokens を指定してください"
        )

    log = []
    bible, scenes = [], []
    if ctx.embedder is not None and ctx.index is not None:
        # 直前に書いたシーンも探せるように、インデックスを更新してから検索する
        stats = update_work_index(ctx.index, ctx.work, ctx.embedder)
        if stats.added or stats.removed:
            log.append(
                f"インデックスを更新しました（追加 {stats.added}件、削除 {stats.removed}件）"
            )
        bible, scenes = retrieve_for_scene(
            ctx.index, ctx.embedder, brief, plot, settings.bible_k, settings.scene_k
        )

    # 必ず入れる部分：あらすじと検索の結果を除いた、プロンプト全体
    skeleton = replace(brief, story_so_far=[])
    messages = ctx.prompts.render("scene", meta=meta, world=world, brief=skeleton, feedback=None)
    fixed = sum(count(message["content"]) for message in messages)
    # 生成する本文（max_tokens）と、推敲のときにプロンプトに入れる原稿の分
    reserved = int(brief.scene.chars * (WRITE_TOKENS_RATIO + 1))

    plan = plan_scene_context(brief, count, total, fixed, reserved, settings.margin, bible, scenes)
    log.append(plan.describe())
    return plan, log


def gather_context(state: WriteState, runtime: Runtime[WriteContext]) -> dict:
    """関係する設定資料と過去の本文を検索し、あらすじと合わせて、予算に収まるだけ選ぶ。"""
    brief = scene_brief(state, runtime, with_context=False)
    plan, log = plan_for_scene(runtime.context, state["meta"], state["world"], state["plot"], brief)
    return {
        "context_summaries": plan.summaries,
        "context_omitted": plan.omitted_summaries,
        "context_bible": plan.related_bible,
        "context_scenes": plan.related_scenes,
        "log": log,
    }
```

**`plan_for_scene`**

1つのシーンの予算を計算し、入れる情報を選びます。グラフのノードと、20.5節の `context` コマンドの両方から使うので、ノードとは別の関数にしています。

1. **コンテキスト長**：設定の `max_tokens` があればそれを、なければ、第6章の `server_info` で、llama-server の値を取り出します。
2. **検索**：検索の道具があれば、まずインデックスを更新してから検索します。直前に書き終えたシーンの本文も、次のシーンから探せるようにするためです。第19章の `update_work_index` は、変わった部分だけを埋め込むので、1シーン分の本文を埋め込むだけで済みます。
3. **必ず入れる部分**：あらすじを空にした `SceneBrief` で、実際に「scene」のプロンプトを展開し、そのトークン数を数えます。プロンプトのテンプレートを変えても、自動的に正しい値になります。
4. **確保する分**：目安の文字数の3倍（`WRITE_TOKENS_RATIO + 1`）です。
5. **選ぶ**：`plan_scene_context` で、予算に収まるものを選びます。

**`gather_context`**

`plan_for_scene` の結果を、状態に入れます。ログには、`ContextPlan.describe` の1行が出ます。

- **`--rag/--no-rag`**：検索を使うかどうかを、コマンドで切り替えます。Typerでは、`"--rag/--no-rag"` のように2つの名前を `/` でつなぐと、オンとオフのフラグになります。既定値を `None` にしておき、どちらも指定されなければ、`novelist.toml` の `retrieval` に従います。
- **エラー**：インデックスのエラーと、予算が足りないエラーも表示します。

## 20.7 うまくいかないときは

**「コンテキスト長が足りません」と表示される**

必ず入れる部分と、本文の生成と推敲の分だけで、コンテキスト長を超えています。次のどれかを試してください。

- 本文用の llama-server の `--ctx-size` を大きくする。第4章の `vram-check` で、VRAMに収まるかを確かめてから変えてください
- プロットのシーンの目安の文字数を減らす。1シーンが長いほど、確保する分が増えます
- `novelist.toml` の `[context]` の `max_tokens` が、小さすぎる値になっていないか確かめる

llama-server は、`--ctx-size` にモデルの学習時のコンテキスト長より大きい値を指定すると、学習時の長さに縮めて起動することがあります。`context` コマンドのコンテキスト長が、指定した値より小さい場合は、llama-server の起動時のログを確かめてください。

**llama-server の `--parallel` を2以上にしている**

`--parallel` を2以上にすると、コンテキスト長がスロットの数で分けられ、1つのリクエストで使える長さが短くなります。第5章の起動スクリプトのとおり、`--parallel 1` で起動してください。

**「SQLite objects created in a thread can only be used in that same thread」と表示される**

`VectorIndex` の `sqlite3.connect` に、`check_same_thread=False` を指定しているか確かめてください（20.4節）。

**「埋め込み用のサーバーに接続できません」と表示される**

`write` は、既定で検索を使うので、埋め込み用のサーバー（第18章）が必要です。起動するか、`--no-rag` を付けて検索を使わずに書いてください。

**検索した人物が、シーンに登場してしまう**

関連する設定に入った人物を、LLMがシーンに登場させてしまうことがあります。`[context]` の `bible_k` を小さくするか、0にして、設定資料の検索を止めてください。第21章の一貫性チェッカーでは、シーンカードにない人物の登場も、確かめる対象にします。

**過去の本文の表現が、そのまま繰り返される**

検索した過去の本文を、LLMがそのまま書き写してしまう場合は、`scene_k` を小さくしてください。第16章の批評で「描写の重複」として指摘されることもあります。

## 20.8 まとめ

- プロンプトに使えるトークン数を**予算**として計算しました。コンテキスト長から、必ず入れる部分、**生成する本文と推敲の分**、余白を引いた残りが、あらすじと検索の結果に使える予算です
- トークン数は、本文を書くモデルのトークナイザー（`/tokenize`）で数え、一度数えたものは**キャッシュ**しました
- あらすじ、関連する設定、過去の本文の3つの区画に、まず予算を**割り当て**、余りを優先順位の高い区画から使いました。区画の中では**大事な順**に、情報を丸ごと入れます。あらすじは古いものから省き、省いたことをプロンプトに書きます
- シーンカードから検索のクエリを作り、設定資料と過去の本文を別々に検索しました。プロンプトにすでにある情報と、このシーン以降の古い本文は除きます
- 執筆のグラフに `gather_context` ノードを加え、本文、批評、推敲で同じ情報を使うようにしました。`novelist context` で、予算の内訳と選ばれる情報を確かめられます

次の第21章では、書いたシーンと設定資料・これまでの本文を突き合わせて、人物や時系列、設定の**矛盾を見つける**一貫性チェッカーを作ります。
