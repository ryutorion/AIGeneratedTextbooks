# 第8章 プロンプト設計

第7章の一発生成では、次のような素朴なプロンプトを使いました。

```text
[system]
あなたは日本語で娯楽小説を書く小説家です。

[user]
次の条件で短編小説を書いてください。
- ジャンル: ミステリー
- 取り入れる要素: 鉄道、冬
- 長さ: 5000字程度
- 1行目にタイトルを書き、1行空けて本文を続けてください。
```

この章では、このプロンプトを改善しながら、**LLMへの指示の書き方**の基本を学びます。

- システムプロンプトとユーザーの指示に、それぞれ何を書くか
- 指示をどのくらい具体的に書くか
- 「〜しない」という禁止事項をどう書くか
- 出力の形式をどう指定し、守られなかったときにどう対処するか

あわせて、プロンプトをPythonのコードから切り離して、**テンプレートファイル**として管理する仕組みを作ります。第III部以降では、企画、設定、プロット、執筆、推敲と、工程ごとにたくさんのプロンプトを使います。その土台になる仕組みです。

プロンプトを工夫しても、第7章で見た一発生成の限界がすべて解決するわけではありません。それでも、各工程でLLMを1回呼び出すときの質は、プロンプトで大きく変わります。ここで学ぶ書き方は、本書の最後まで使い続けます。

## 8.1 プロンプトの構成要素

LLMへの指示には、次のような要素が含まれます。

| 要素 | 内容 | 小説の例 |
|---|---|---|
| 役割 | LLMに、どんな立場で仕事をしてほしいか | 経験豊富な娯楽小説家 |
| 方針 | どの仕事でも守ってほしい規則 | 視点を途中で変えない、説明より描写 |
| 課題 | 今回やってほしいこと | 短編小説を書く |
| 条件 | 今回の課題の条件 | ジャンル、要素、長さ、視点 |
| 入力 | 課題に使う材料 | 設定資料、プロット、前のシーン（第III部以降） |
| 出力形式 | 結果をどんな形で返してほしいか | 1行目にタイトル、本文だけ |
| 例 | 望む出力の見本 | 文体の見本（第23章） |

第7章のプロンプトには、役割・課題・条件・出力形式がありますが、**方針**がありません。また、条件も「ジャンル」「要素」「長さ」だけで、どんな物語にしてほしいかがほとんど伝わっていません。

## 8.2 システムプロンプトとユーザーの指示の分担

第6章で見たように、チャットのメッセージには `system`（システムプロンプト）と `user`（ユーザーの指示）の役割があります。どちらに何を書くかは、次のように考えます。

- **システムプロンプト**：**どの作品でも変わらないもの**。役割、方針、出力形式
- **ユーザーの指示**：**作品ごとに変わるもの**。課題、条件、入力

こう分ける理由は3つあります。

**1. モデルがそのように学習している**

インストラクションモデルは、システムプロンプトを「会話全体を通して守るべき前提」、ユーザーの指示を「今回の依頼」として扱うように訓練されています。方針をシステムプロンプトに書くと、より安定して守られやすくなります。

**2. 使い回せる**

第III部では、同じ方針のまま、シーン1、シーン2、……と何度も執筆を依頼します。変わらない部分をシステムプロンプトにまとめておけば、変わる部分だけを差し替えて使い回せます。

**3. llama-serverのキャッシュが効く**

`llama-server` は、直前のリクエストと**先頭が同じ部分**の計算結果（KVキャッシュ）を再利用します。第6章でストリーミングの最後に届いた `timings` に、`cache_n`（キャッシュから再利用したトークン数）という値が含まれていたのはこのためです。

```text
1回目: [system: 方針 ……… 800トークン][user: シーン1の指示 300トークン]
2回目: [system: 方針 ……… 800トークン][user: シーン2の指示 300トークン]
        └────── 再利用（計算しない）──────┘└────── ここだけ計算 ──────┘
```

変わらない部分を**先頭**に、変わる部分を**後ろ**に置くと、2回目以降は変わった部分の計算だけで済みます。第III部で設定資料や前のシーンを入力に入れるようになると、入力が数千トークンになるので、この差が効いてきます。

## 8.3 指示の粒度

### 抽象的な指示は伝わらない

「面白い小説を書いてください」「魅力的な登場人物にしてください」という指示は、ほとんど効果がありません。LLMにとっての「面白い」「魅力的」は、学習した文章の平均的なイメージにすぎず、結局はありきたりな文章になります（第7章の実験3）。

指示は、**書かれた文章を読めば、守られているかどうかを確かめられる**言葉で書きます。

| 抽象的な指示 | 具体的な指示 |
|---|---|
| 面白くしてください | 転換の場面で、予想を裏切る出来事を起こす |
| 描写を豊かに | 人物の感情は、行動・表情・台詞で示す |
| 読みやすく | 会話文は「」で囲み、誰の台詞かがわかるようにする |
| 5000字くらいで | 4つの場面に分け、それぞれ約1000字、1500字、1500字、1000字で書く |

最後の例は、第7章の実験1で見た「長く書けない、後半が駆け足になる」問題への対策です。全体の長さだけを伝えるより、**場面ごとの役割と長さ**を伝えたほうが、LLMは配分を意識して書きます。これは第III部の「プロットを作ってからシーンごとに書く」方法の、ごく簡単な先取りでもあります。

### 指示の書き方の原則

1. **観察できる言葉で書く**：読んで確かめられる形にします。
2. **数字を使う**：「長め」ではなく「約1500字」、「いくつか」ではなく「4つ」と書きます。
3. **重要なものから書き、多くしすぎない**：指示が多すぎると、一部が無視されます。特に小さいモデルほどその傾向が強くなります。方針の箇条書きは、多くても10項目程度にとどめ、本当に大事なものに絞ります。
4. **見出しと箇条書きで構造化する**：`# 条件`、`# 構成` のようにMarkdownの見出しで区切ると、LLMにとっても、あとで読み返す人間にとってもわかりやすくなります。

## 8.4 禁止事項の書き方

### 「〜しない」は効きにくい

第7章の一発生成の問題を防ごうとして、次のような禁止事項を並べたくなります。

```text
- 説明的な文章にしないでください。
- 同じ文末を繰り返さないでください。
- 教訓やまとめで終わらないでください。
- 前置きを書かないでください。
```

しかし、こうした「〜しない」という指示は、思ったほど効きません。理由は2つあります。

- **書いた言葉に引っ張られる**：LLMは、入力に出てきた言葉に関連する内容を生成しやすくなります。「教訓で終わらないで」と書くと、「教訓」という言葉がかえって意識されてしまうことがあります。
- **代わりに何をすればよいかがわからない**：「説明的にしない」と言われても、では何をすればよいのかは伝わっていません。

### 「〜する」に書き換える

禁止事項は、できるだけ**代わりにしてほしいこと**に書き換えます。

| 禁止の形 | 肯定の形 |
|---|---|
| 説明的な文章にしない | 人物の感情は、行動・表情・台詞で示す |
| 同じ文末を繰り返さない | 「〜た。」が続いたら、現在形や体言止めを混ぜる |
| 教訓やまとめで終わらない | 最後は人物の行動か台詞で締めくくる |
| 前置きを書かない | 出力するのはタイトルと本文だけにする |
| 見出しを付けない | 場面と場面の間は、空行を1行入れるだけで区切る |

どうしても禁止事項が必要なときは、数を絞り、**肯定の形の指示と組にして**書きます。たとえば「出力するのはタイトルと本文だけにする。前置き、あとがき、解説は書かない。」のように、してほしいことを先に書き、してほしくないことを具体的に列挙します。

## 8.5 出力形式と後処理

出力形式を指示しても、LLMがいつも守るとは限りません。一発生成では、次のような出力がよく見られます。

```text
はい、承知しました。以下が短編小説です。

# 霧の終着駅

ストーブの上で薬缶が鳴っていた。……
```

```text
**タイトル：『霧の終着駅』**

ストーブの上で薬缶が鳴っていた。……
```

プロンプトを工夫すれば減らせますが、ゼロにはできません。そこで、**プロンプトで頼み、コードで確かめる**という方針をとります。LLMの出力を受け取ったら、前置きの行や、タイトルに付いた記号を取り除く後処理を入れておきます。

この後処理の関数 `clean_story_text` は、8.7節で `oneshot.py` に追加します。第10章では、出力をJSONの形式に**強制する**方法を学びます。形式を厳密に守らせたい出力（設定資料やプロット）には、そちらを使います。

## 8.6 プロンプトをファイルに分ける

第7章では、プロンプトをPythonのコード（文字列）として書いていました。プロンプトを改善していくと、次のような不便が出てきます。

- 長い日本語の文章が、Pythonのコードの中に埋もれて読みにくい
- プロンプトを少し変えるたびに、コードを変更することになる
- 古いプロンプトと新しいプロンプトを比べる実験がしにくい

そこで、プロンプトを**テンプレートファイル**としてコードから切り離します。

### テンプレートの置き場所

プロジェクトのルートに `prompts/` ディレクトリを作り、プロンプトごとにサブディレクトリを作ります。その中に、システムプロンプト（`system.md`）とユーザーの指示（`user.md`）を置きます。

```text
prompts/
├── oneshot_basic/       # 第7章の素朴なプロンプト
│   ├── system.md
│   └── user.md
└── oneshot/             # この章で改善したプロンプト
    ├── system.md
    └── user.md
```

ファイルの拡張子を `.md` にしているのは、プロンプトの中でMarkdownの見出しや箇条書きを使うので、エディタで見やすく表示されるからです。

### Jinja2のテンプレート

テンプレートの書式には、第3章でチャットテンプレートを展開するのに使った**Jinja2**を使います。よく使う書き方は次のとおりです。

| 書き方 | 意味 |
|---|---|
| `{{ genre }}` | 変数 `genre` の値を埋め込む |
| `{{ tags \| join("、") }}` | リスト `tags` を「、」でつなげて埋め込む（`\|` は**フィルター**） |
| `{{ a if 条件 else b }}` | 条件によって `a` か `b` を埋め込む |
| `{% for x in items %}…{% endfor %}` | リストの要素ごとに繰り返す。`loop.index` で1から始まる番号が使える |
| `{% if 条件 %}…{% endif %}` | 条件が成り立つときだけ出力する |
| `{# … #}` | コメント。展開すると消えるので、LLMには送られない |

`{# … #}` のコメントには、そのプロンプトの目的や注意点など、**プロンプトを書く人へのメモ**を書いておきます。

### プロンプトを読み込むモジュール

**`src/novelist/prompts.py`**（新規）

```python
"""プロンプトのテンプレートを読み込んで展開する。"""

from pathlib import Path
from typing import Any

from jinja2 import Environment, FileSystemLoader, StrictUndefined, TemplateNotFound, UndefinedError

from novelist.llm.client import Message


class PromptError(Exception):
    """プロンプトのテンプレートを展開できなかったときの例外。"""


class PromptLibrary:
    """prompts/ ディレクトリにあるプロンプトのテンプレートを扱う。

    prompts/<名前>/system.md と prompts/<名前>/user.md を、1組のプロンプトとする。
    system.md は省略できる。
    """

    def __init__(self, root: Path) -> None:
        self.root = root
        self._env = Environment(
            loader=FileSystemLoader(root, encoding="utf-8"),
            undefined=StrictUndefined,  # 渡し忘れた変数をエラーにする
            trim_blocks=True,
            lstrip_blocks=True,
            autoescape=False,
        )

    def names(self) -> list[str]:
        """使えるプロンプトの名前の一覧。"""
        if not self.root.is_dir():
            return []
        return sorted(p.name for p in self.root.iterdir() if (p / "user.md").is_file())

    def render(self, name: str, /, **variables: Any) -> list[Message]:
        """プロンプトを展開して、LLMに渡すメッセージのリストにする。"""
        messages: list[Message] = []
        for role in ("system", "user"):
            try:
                template = self._env.get_template(f"{name}/{role}.md")
            except TemplateNotFound as e:
                if role == "system":
                    continue
                raise PromptError(
                    f"プロンプト '{name}' が見つかりません（{self.root / name / 'user.md'}）"
                ) from e
            try:
                text = template.render(**variables)
            except UndefinedError as e:
                raise PromptError(f"プロンプト '{name}/{role}.md' の変数が足りません: {e}") from e
            messages.append({"role": role, "content": text.strip()})
        return messages
```

**`Environment`**

Jinja2でテンプレートを扱うための設定です。

- `FileSystemLoader(root, encoding="utf-8")`：`root` ディレクトリからテンプレートファイルを読み込みます。Windowsでも文字化けしないように、文字コードを明示しています。
- `undefined=StrictUndefined`：テンプレートの中で使っている変数を渡し忘れたら、エラーにします。Jinja2の既定では、渡し忘れた変数は**空文字列**になり、エラーになりません。プロンプトの一部が黙って消えてしまうと、生成の質が下がった原因を見つけるのがとても難しくなるので、必ずエラーにしておきます。
- `trim_blocks` と `lstrip_blocks`：`{% for %}` などの行の前後の改行や空白を取り除きます。第3章のチャットテンプレートと同じ設定です。
- `autoescape=False`：HTMLを生成するわけではないので、`<` や `&` を変換しないようにします。

**`render`**

プロンプト名から `<名前>/system.md` と `<名前>/user.md` を読み込んで展開し、第6章の `LLMClient` に渡せるメッセージのリストにします。`system.md` がない場合は、ユーザーの指示だけにします。

引数の `/` は、**位置専用引数**の印です。`/` より前の引数（`name`）は、`render("oneshot", ...)` のように位置でしか渡せなくなります。こうしておくと、テンプレートの中で `name` という名前の変数を使いたいときに、`render("greet", name="山田")` と書いても、プロンプト名の `name` とぶつかりません。

テンプレートが見つからない場合や、変数が足りない場合は、`PromptError` にまとめて、どのファイルで何が起きたかがわかるメッセージにします。

ユーザーの指示には、作品ごとに変わる**課題**と**条件**を書きます。

### 一発生成のモジュールを書き直す

`build_messages` はテンプレートに置き換わったので削除し、場面の割り振りを計算する関数と、出力の後処理の関数を追加します。変更が大きいので、変更後の全文を載せます。

**`src/novelist/oneshot.py`**（変更後の全文）

```python
"""1回の呼び出しで短編を書かせる（第7章・第8章）。"""

import re
from dataclasses import dataclass


@dataclass
class ScenePlan:
    """一発生成で指定する、場面ごとの役割と長さ。"""

    role: str  # 場面の役割（導入、展開など）
    goal: str  # その場面で書くこと
    chars: int  # 目安の文字数


# 起承転結の4つの場面と、全体に占める割合
STRUCTURE = [
    ("導入", "舞台と主人公を示し、日常が揺らぐきっかけを置く", 0.2),
    ("展開", "謎や問題が深まり、主人公が行動を起こす", 0.3),
    ("転換", "予想を裏切る出来事が起き、状況が大きく変わる", 0.3),
    ("結末", "問題に決着をつけ、最後は人物の行動か台詞で締めくくる", 0.2),
]


def default_structure(length: int) -> list[ScenePlan]:
    """目標の文字数を、起承転結の4つの場面に割り振る。"""
    return [
        ScenePlan(role, goal, round(length * ratio / 100) * 100) for role, goal, ratio in STRUCTURE
    ]


def max_tokens_for(length: int, n_ctx: int, prompt_tokens: int) -> int:
    """目標の文字数から、生成するトークン数の上限を決める。

    1文字 ≒ 1トークンとして、目標の1.5倍まで書けるようにする。
    ただし、コンテキスト長から入力の分を引いた残りを超えないようにする。
    """
    wanted = int(length * 1.5)
    available = n_ctx - prompt_tokens
    return max(0, min(wanted, available))


# 本文の前に付きがちな前置き（「はい、承知しました。」など）
PREAMBLE_RE = re.compile(r"^(はい|承知|かしこまりました|了解|以下|それでは)")


def clean_story_text(text: str) -> str:
    """LLMの出力から、本文以外の余計な部分を取り除く。"""
    lines = text.strip().splitlines()
    # 前置きの行、コードブロックの記号（```）、空行を取り除く
    while lines and (
        not lines[0].strip() or PREAMBLE_RE.match(lines[0]) or lines[0].startswith("```")
    ):
        lines.pop(0)
    while lines and (not lines[-1].strip() or lines[-1].startswith("```")):
        lines.pop()
    if not lines:
        return ""
    # タイトル行の飾り（# 、**、「タイトル：」）を取り除く
    title = lines[0].strip()
    title = re.sub(r"^#+\s*", "", title)
    title = title.strip("*").strip()
    title = re.sub(r"^タイトル\s*[:：]\s*", "", title)
    title = title.strip("『』「」")
    lines[0] = title
    return "\n".join(lines).strip()
```

**`ScenePlan` と `default_structure`**

起承転結の4つの場面の役割と、全体に占める割合を `STRUCTURE` にまとめています。`default_structure` は、目標の文字数をこの割合で割り振り、100字単位に丸めて `ScenePlan` のリストにします。テンプレートの中では、`scene.role` や `scene.chars` のように属性として参照できます。

各場面の「書くこと」（`goal`）も、8.3節の原則に従って、読んで確かめられる形で書いています。結末の「最後は人物の行動か台詞で締めくくる」は、第7章で見た「まとめで終わる」問題への対策です。

**`clean_story_text`**

8.5節の後処理です。

1. 先頭から、空行、前置き（「はい」「承知」「以下」などで始まる行）、コードブロックの記号（` ``` `）を取り除きます。末尾の空行とコードブロックの記号も取り除きます。
2. 1行目をタイトルとみなし、Markdownの見出し記号（`#`）、太字の記号（`**`）、「タイトル：」、かぎかっこ（『』「」）を取り除きます。

前置きの判定は、行の先頭の言葉だけを見る単純なものです。本文が「はい」で始まる小説だと誤って削除してしまいますが、実際にはまれなので、ここではこの単純な方法で十分とします。

改善したプロンプトでは、次のような変化が見られるはずです。

- **長さ**：場面ごとに文字数を指定したことで、目標に近い長さまで書くようになる
- **文末**：「た。」の割合が下がり、「る。」（現在形）などが増える
- **会話**：「行動・表情・台詞で示す」という方針により、会話の割合がやや増える
- **形式**：前置きやタイトルの記号が減る。残っていても、`clean_story_text` で取り除かれる

- 場面の分量は守られても、各場面の中身（何が起きるか）はLLM任せなので、展開のご都合主義や伏線の未回収は残る
- 登場人物の名前や人数の矛盾は、あいかわらず起きる
- 追加の指示を増やしすぎると、どれかが守られなくなる

プロンプトは、**1回の呼び出しの質**を上げる道具です。物語全体の設計や一貫性は、1回の呼び出しの中では解決できません。これが、第III部で工程を分ける理由です。

## 8.10 まとめ

- プロンプトは、役割・方針・課題・条件・入力・出力形式・例の要素でできています
- **システムプロンプトには変わらないもの**（役割、方針、出力形式）を、**ユーザーの指示には変わるもの**（課題、条件、入力）を書きます。変わらない部分を先頭に置くと、`llama-server` のキャッシュが効きます
- 指示は、**読んで確かめられる言葉**と**数字**で書きます。場面ごとの役割と長さを指定すると、長さの配分が改善します
- 禁止事項は、できるだけ**「〜する」の形に書き換え**ます
- 出力形式は、**プロンプトで頼み、コードで確かめ**ます
- プロンプトを `prompts/` のJinja2テンプレートとして管理し、`PromptLibrary` で展開するようにしました。`StrictUndefined` で変数の渡し忘れをエラーにし、`--dry-run` で展開結果を確かめられます

次の第9章では、プロンプトと並んで生成の質を左右する**サンプリング**を学びます。第7章で見た「ありきたりな展開」と、`temperature` を上げたときの「文章の崩れ」の間で、ちょうどよい設定を探っていきます。
