# 第13章 キャラクターと世界設定シート

第12章で、作品の企画を決めました。この章では、その企画をもとに**設定資料**を作ります。

小説家や脚本家は、書き始める前に、登場人物の名前・年齢・口調・秘密や、舞台となる場所の様子などをまとめた資料を作ることがよくあります。長い物語を書いているうちに設定が揺らがないよう、いつでも見返せるようにしておくためです。こうした資料は、**バイブル**（bible）と呼ばれることもあります。

第7章の一発生成では、人物の名前や口調が途中で変わる問題がありました。第11章では、登場人物を先に決めて執筆の指示に含めることで、この問題が減ることを確かめました。この章では、それをさらに進めて、次の2つの**設定シート**を作ります。

| シート | 内容 |
|---|---|
| 世界設定 | 時代、舞台、雰囲気、物語の中で変わらない決まり、場所、固有の用語 |
| 登場人物 | 人物の設定（第10章の `Character`）と、人物どうしの関係 |

作った設定資料は、作品のディレクトリの `bible/` に保存します。第14章のプロット、第15章の執筆、第IV部の設定資料の検索と一貫性のチェックなど、これ以降のすべての工程で参照します。

この章では、第11章で学んだLangGraphを使って、作品の**設計のグラフ**を作り始めます。この章では設定資料を作るところまで、第14章でプロットを作るノードを加え、第17章で途中で止めて人間が確認できるようにします。

この章で作るものは次のとおりです。

| `src/novelist/graph/state.py` | 設計のグラフの状態 |

## 13.1 設定資料の設計

### 何を設定しておくか

設定資料には、何でも書いておけばよいわけではありません。項目が多すぎると、LLMへの指示が長くなり、生成にも時間がかかります。**あとの工程で実際に使うもの**に絞ります。

| 項目 | 使う場面 |
|---|---|
| 時代・舞台・雰囲気 | 執筆のときに、描写の方向性を決める |
| 決まり | 「大雪で列車が止まっている」のような、物語の最初から最後まで変わらない状況。第21章の一貫性チェックで、これに反する描写がないかを確かめる |
| 場所 | 各シーンの舞台。描写の手がかり（音・匂い・温度）は、執筆のときの描写に使う |
| 用語 | 物語に固有の組織・道具・出来事。表記の揺れを防ぐ |
| 登場人物 | 名前・読み・年齢・役割・性格・口調・目的・秘密（第10章の `Character`） |
| 人間関係 | 誰が誰をどう思っているか。会話や対立の場面で使う |

### 1回で作るか、分けて作るか

世界設定と登場人物をまとめて1回で作らせることもできますが、この章では**2回に分けて**作ります。

```text
企画 ─→ 世界設定を作る ─→ 登場人物を作る
                 │                ↑
                 └── 場所・決まり ─┘
```

分ける理由は次のとおりです。

- **出力を短くする**：1回の出力が長くなるほど、途中で切れたり（第10章）、後半の質が下がったりしやすくなります。
- **前の結果を次の入力にする**：世界設定を先に決めておけば、登場人物を作るときに「雪に閉ざされた駅」という状況を踏まえた人物を考えさせられます。第11章で学んだ「先に決めたことを、あとの工程の入力にする」という考え方です。
- **やり直しやすい**：登場人物だけが気に入らない場合に、そこだけ作り直せるようにしやすくなります。

### 名前の整合性を検証する

人間関係は、「沢渡透から見た黒川源三は元上司」のように、登場人物の名前で表します。ここでよく起きるのが、**名前の表記の揺れ**です。登場人物の一覧では「黒川源三」なのに、関係では「黒川」や「源三」と書いてしまうのです。

表記が揺れていると、あとでプログラムが人物を照合できなくなります。そこで、関係に出てくる名前が、すべて登場人物の一覧にあることを `model_validator` で検証します。違っていれば、第10章の仕組みで、エラーの内容を伝えてLLMに直させます。

## 13.2 設定資料のモデル

**`src/novelist/schemas/bible.py`**（新規）

```python
"""設定資料（第13章）。"""

from pydantic import BaseModel, Field, model_validator

from novelist.schemas.character import Cast


class World(BaseModel):
    """物語の世界の概要。"""

    era: str = Field(description="時代", max_length=40)
    place: str = Field(description="主な舞台となる地域や場所", max_length=60)
    atmosphere: str = Field(description="物語全体の雰囲気", max_length=100)
    rules: list[str] = Field(
        description="物語の中で常に守られる状況や決まり（例: 大雪で列車が止まっている）",
        min_length=1,
        max_length=5,
    )


class Place(BaseModel):
    """物語に登場する場所。"""

    name: str = Field(description="場所の名前", max_length=30)
    description: str = Field(description="見た目と、物語の中での役割", max_length=150)
    sensory: str = Field(description="描写に使える音・匂い・温度などの手がかり", max_length=100)


class Term(BaseModel):
    """物語に登場する固有の用語（組織、道具、出来事など）。"""

    name: str = Field(description="用語", max_length=30)
    description: str = Field(description="意味と、物語の中での役割", max_length=150)


class WorldSheet(BaseModel):
    """世界設定のシート。"""

    world: World
    places: list[Place] = Field(min_length=1, max_length=5)
    terms: list[Term] = Field(max_length=8)

    @model_validator(mode="after")
    def _check_names(self) -> "WorldSheet":
        for label, names in (
            ("場所", [p.name for p in self.places]),
            ("用語", [t.name for t in self.terms]),
        ):
            duplicates = sorted({n for n in names if names.count(n) > 1})
            if duplicates:
                raise ValueError(f"{label}の名前が重複しています: {', '.join(duplicates)}")
        return self


class Relationship(BaseModel):
    """2人の登場人物の関係。"""

    source: str = Field(description="人物の名前")
    target: str = Field(description="相手の人物の名前")
    relation: str = Field(
        description="source から見た target との関係（例: 元同僚。密かに疑っている）",
        max_length=60,
    )


class CharacterSheet(Cast):
    """登場人物のシート。第10章の Cast に、人物どうしの関係を加えたもの。"""

    relationships: list[Relationship] = Field(min_length=1, max_length=12)

    @model_validator(mode="after")
    def _check_relationships(self) -> "CharacterSheet":
        names = {c.name for c in self.characters}
        for r in self.relationships:
            unknown = [n for n in (r.source, r.target) if n not in names]
            if unknown:
                raise ValueError(
                    f"関係に、登場人物にない名前が使われています: {', '.join(unknown)}"
                    f"（登場人物: {', '.join(sorted(names))}）"
                )
            if r.source == r.target:
                raise ValueError(f"自分自身との関係になっています: {r.source}")
        return self

    def protagonist(self) -> str:
        """主人公の名前。"""
        return next(c.name for c in self.characters if c.role == "主人公")
```

**`World`、`Place`、`Term`、`WorldSheet`**

世界設定のシートです。各項目の `description` は、第10章で説明したとおり、プロンプトに埋め込んでLLMに項目の意味を伝えるためのものです。「決まり」には例を添えて、どんなことを書けばよいかがわかるようにしています。

`WorldSheet` の `_check_names` は、場所と用語の名前の重複を検証します。`for label, names in (...)` のように、検証の内容が同じものをタプルにまとめて、1つのループで処理しています。

**`Relationship`**

2人の関係です。`source`（人物）から見た `target`（相手）との関係を書きます。「AはBを疑っているが、BはAを信頼している」のように、関係は一方向で異なることがあるので、向きを持たせています。

**`CharacterSheet`**

第10章の `Cast` を**継承**して、`relationships` を加えています。Pydanticのモデルは、ふつうのクラスと同じように継承でき、親クラスのフィールドと検証（`_check_cast` による主人公の人数と名前の重複のチェック）も引き継がれます。

`_check_relationships` では、関係に出てくる名前が登場人物の一覧にあるか、自分自身との関係になっていないかを確かめます。エラーメッセージには、正しい名前の一覧も含めています。第10章の「直させる」処理では、このメッセージがそのままLLMへの指示になるので、正しい表記を示しておくと、LLMが直しやすくなります。

`protagonist()` は、主人公の名前を返すメソッドです。`next()` は、ジェネレーター式から最初の1つを取り出します。`Cast` の検証で主人公がちょうど1人いることが保証されているので、必ず見つかります。

```python
"""作品の設計（設定・プロット）のグラフの状態（第13章）。"""

import operator
from dataclasses import dataclass
from typing import Annotated, TypedDict

from novelist.config import Config
from novelist.llm.client import LLMClient
from novelist.prompts import PromptLibrary
from novelist.schemas.bible import CharacterSheet, WorldSheet
from novelist.schemas.work import WorkMeta
from novelist.work import Work


class PlanState(TypedDict, total=False):
    """設計のグラフで共有する状態。"""

    meta: WorkMeta  # 作品のメタデータ（採用した企画を含む）
    redo: list[str]  # 既存の成果物があっても作り直す工程（"bible" など）
    world: WorldSheet  # 世界設定
    characters: CharacterSheet  # 登場人物
    log: Annotated[list[str], operator.add]


@dataclass
class PlanContext:
    """設計のグラフのノードが使う道具。"""

    client: LLMClient
    prompts: PromptLibrary
    config: Config
    work: Work
```

第11章の `StoryState` と `GraphContext` と同じ考え方です。

- **`PlanState`**：作品のメタデータ（`meta`）から始まり、世界設定（`world`）と登場人物（`characters`）が加わっていきます。`redo` は、すでに成果物があっても作り直す工程の名前のリストです。
- **`PlanContext`**：第11章の `GraphContext` に、作品のディレクトリ（`work`）を加えています。

```python
"""設定資料を作るノード（第13章）。"""

from typing import Literal

from langgraph.runtime import Runtime

from novelist.graph.state import PlanContext, PlanState
from novelist.llm.structured import generate_structured, schema_text
from novelist.schemas.bible import CharacterSheet, WorldSheet

PROFILE = "precise"  # 設定資料は、条件を正確に守ることを優先する


def route_bible(
    state: PlanState, runtime: Runtime[PlanContext]
) -> Literal["load_bible", "make_world"]:
    """設定資料がすでにあれば読み込み、なければ（または作り直すなら）作る。"""
    if runtime.context.work.has_bible() and "bible" not in state.get("redo", []):
        return "load_bible"
    return "make_world"


def load_bible(state: PlanState, runtime: Runtime[PlanContext]) -> dict:
    """保存してある設定資料を読み込む。"""
    world, characters = runtime.context.work.load_bible()
    return {
        "world": world,
        "characters": characters,
        "log": ["既存の設定資料を使います"],
    }


def _sampling(ctx: PlanContext):
    sampling = ctx.config.sampling_for(PROFILE)
    return sampling.model_copy(update={"max_tokens": max(sampling.max_tokens, 4096)})


def make_world(state: PlanState, runtime: Runtime[PlanContext]) -> dict:
    """企画から、世界設定（時代・舞台・場所・用語）を作る。"""
    ctx = runtime.context
    messages = ctx.prompts.render("world", meta=state["meta"], schema=schema_text(WorldSheet))
    world = generate_structured(ctx.client, messages, WorldSheet, _sampling(ctx))
    return {
        "world": world,
        "log": [f"世界設定: 場所 {len(world.places)}件、用語 {len(world.terms)}件"],
    }


def make_characters(state: PlanState, runtime: Runtime[PlanContext]) -> dict:
    """企画と世界設定から、登場人物と人間関係を作る。"""
    ctx = runtime.context
    messages = ctx.prompts.render(
        "characters",
        meta=state["meta"],
        world=state["world"],
        schema=schema_text(CharacterSheet),
    )
    characters = generate_structured(ctx.client, messages, CharacterSheet, _sampling(ctx))
    names = "、".join(c.name for c in characters.characters)
    return {"characters": characters, "log": [f"登場人物: {names}"]}


def save_bible(state: PlanState, runtime: Runtime[PlanContext]) -> dict:
    """設定資料を作品のディレクトリに保存する。"""
    work = runtime.context.work
    work.save_bible(state["world"], state["characters"])
    return {"log": [f"設定資料を保存しました → {work.bible_dir}"]}
```

**`route_bible`**

グラフの最初の条件付きエッジです。設定資料がすでに保存されていて、作り直しの指定もなければ `load_bible` へ、そうでなければ `make_world` へ進みます。

第11章の条件付きエッジの関数は、状態だけを受け取りました。ノードと同じように `runtime` を受け取ることもでき、ここでは `runtime.context.work` から、設定資料が保存されているかを調べています。

**なぜ「既存のものを使う」のか**

`novelist plan` は、第14章でプロットを作る工程が加わり、第17章では途中で止まって人間の確認を待つようになります。設定資料を作ったあとでプロットの工程が失敗したり、人間が設定資料を手で直したりすることもあるでしょう。そのたびに設定資料を作り直していては、時間がかかるうえに、直した内容が消えてしまいます。

そこで、**すでにあるものは読み込んで使い、作り直したいときだけ `--redo` で指定する**ようにします。こうしておけば、`bible/characters.json` をエディタで直してから `novelist plan` を実行し直すと、直した設定資料をもとに次の工程に進めます。

**`make_world` と `make_characters`**

第10章の `generate_structured` で、それぞれのシートを作ります。設定資料は条件を正確に守ることを優先するので、`precise` プロファイルを使います。`max_tokens` は、第12章と同じく少なくとも4096から始め、途中で切れたら `generate_structured` が自動で増やします。

**`save_bible`**

2つのシートを `Work.save_bible` で保存します。LLMを呼ぶノードとファイルを書くノードを分けておくと、それぞれを単独でテストしやすく、あとから「保存の前に人間の確認を挟む」（第17章）といった変更もしやすくなります。

### グラフを組み立てる

**`src/novelist/graph/build.py`**（新規）

```python
"""作品の設計のグラフを組み立てる（第13章）。

START ─┬→ load_bible ─────────────────────────────────┬→ END
       └→ make_world → make_characters → save_bible ──┘
"""

from langgraph.graph import END, START, StateGraph
from langgraph.graph.state import CompiledStateGraph

from novelist.graph.nodes.bible import (
    load_bible,
    make_characters,
    make_world,
    route_bible,
    save_bible,
)
from novelist.graph.state import PlanContext, PlanState

# --redo で指定できる工程
PLAN_STEPS = ("bible",)


def build_plan_graph() -> CompiledStateGraph:
    """設計のグラフを組み立てる。"""
    builder = StateGraph(PlanState, context_schema=PlanContext)
    builder.add_node("load_bible", load_bible)
    builder.add_node("make_world", make_world)
    builder.add_node("make_characters", make_characters)
    builder.add_node("save_bible", save_bible)

    builder.add_conditional_edges(START, route_bible, ["load_bible", "make_world"])
    builder.add_edge("make_world", "make_characters")
    builder.add_edge("make_characters", "save_bible")
    builder.add_edge("save_bible", END)
    builder.add_edge("load_bible", END)
    return builder.compile()
```

- `add_conditional_edges(START, route_bible, ...)` のように、`START` から条件付きエッジを出すこともできます。
- `load_bible` のあとは、そのまま `END` に進みます。第14章では、ここと `save_bible` のあとに、プロットを作るノードをつなぎます。
- `PLAN_STEPS` は、`--redo` で指定できる工程の名前の一覧です。第14章で `"plot"` を加えます。

**`tests/test_graph_plan.py`**（新規）

```python
import json
from pathlib import Path

from conftest import CHARACTER_SHEET_DATA, WORLD_DATA, ChatRecorder, create_work

from novelist.config import Config
from novelist.graph.build import build_plan_graph
from novelist.graph.state import PlanContext
from novelist.llm.client import LLMClient
from novelist.prompts import PromptLibrary
from novelist.work import Work

PROJECT_PROMPTS = Path(__file__).parent.parent / "prompts"
CONFIG = Config.model_validate({"profiles": {"precise": {"temperature": 0.3}}})
BIBLE_RESPONSES = [
    json.dumps(WORLD_DATA, ensure_ascii=False),
    json.dumps(CHARACTER_SHEET_DATA, ensure_ascii=False),
]


def run_plan(work: Work, responses: list[str], redo: list[str] | None = None):
    server = ChatRecorder(responses)
    with LLMClient(CONFIG.server, transport=server.transport) as client:
        context = PlanContext(
            client=client, prompts=PromptLibrary(PROJECT_PROMPTS), config=CONFIG, work=work
        )
        state = build_plan_graph().invoke(
            {"meta": work.load_meta(), "redo": redo or []}, context=context
        )
    return state, server


def test_plan_creates_bible(tmp_path: Path) -> None:
    work = create_work(tmp_path)
    state, server = run_plan(work, BIBLE_RESPONSES)

    assert work.has_bible()
    world, characters = work.load_bible()
    assert world.places[0].name == "待合室"
    assert characters.protagonist() == "沢渡透"
    assert state["log"] == [
        "世界設定: 場所 2件、用語 1件",
        "登場人物: 沢渡透、三枝葉子、黒川源三",
        f"設定資料を保存しました → {work.bible_dir}",
    ]
    # 世界設定の指示には企画が、登場人物の指示には世界設定の場所が含まれる
    world_prompt = server.requests[0]["messages"][-1]["content"]
    assert "霧の終着駅" in world_prompt
    characters_prompt = server.requests[1]["messages"][-1]["content"]
    assert "場所: 待合室、駅長室" in characters_prompt


def test_plan_reuses_existing_bible(tmp_path: Path) -> None:
    work = create_work(tmp_path)
    run_plan(work, BIBLE_RESPONSES)
    state, server = run_plan(work, [])  # 2回目はLLMを呼ばない
    assert server.requests == []
    assert state["log"] == ["既存の設定資料を使います"]
    assert state["characters"].protagonist() == "沢渡透"


def test_plan_redo_bible(tmp_path: Path) -> None:
    work = create_work(tmp_path)
    run_plan(work, BIBLE_RESPONSES)
    _, server = run_plan(work, BIBLE_RESPONSES, redo=["bible"])
    assert len(server.requests) == 2  # 作り直した
```

- `test_plan_creates_bible`：世界設定と登場人物のJSONを順に返す偽のサーバーで、グラフを実行します。設定資料が保存されること、`log` の内容、世界設定の指示に企画のタイトルが、登場人物の指示に世界設定の場所が含まれることを確かめています。
- `test_plan_reuses_existing_bible`：2回目の実行では、LLMを1回も呼ばずに（`server.requests` が空）、既存の設定資料を使うことを確かめています。
- `test_plan_redo_bible`：`redo` に `"bible"` を指定すると、作り直すことを確かめています。

## 13.8 まとめ

- 設定資料（バイブル）には、あとの工程で**実際に使うもの**に絞って、世界設定と登場人物をまとめます
- 世界設定を先に作り、それを入力にして登場人物を作ります。**前の結果を次の入力にする**ことで、設定どうしが噛み合います
- 人間関係の名前が登場人物の一覧にあることを `model_validator` で検証し、表記の揺れを防ぎます。エラーメッセージに正しい名前を含めると、LLMが直しやすくなります
- 第10章の `Cast` を継承して `CharacterSheet` を作りました。Pydanticのモデルは、フィールドも検証も継承できます
- 共通のプロンプトの部品を `prompts/_parts/` に置き、`{% include %}` で取り込みました
- LangGraphで**設計のグラフ**を作り始めました。設定資料がすでにあれば読み込んで使い、`--redo` で作り直せます。手で直した設定資料も、そのまま次の工程に使えます
- `novelist plan` で設定資料を作り、`novelist bible` で表示できるようになりました

次の第14章では、設計のグラフに**プロット**を作るノードを加えます。企画のあらすじと設定資料をもとに、物語を章とシーンに分け、シーンごとに「目的・葛藤・結果」を決めたシーンカードを作ります。
