# 第7章 一発生成で短編を書く

第I部で、ローカルLLMを動かしてPythonから呼び出す準備が整いました。第II部では、いよいよ小説を書かせます。

最初にやるのは、いちばん素朴な方法です。**LLMに1回だけ「短編小説を書いてください」と頼む**。これを本書では**一発生成**と呼びます。

「そんな方法でうまくいくはずがない」と思うかもしれません。そのとおりで、この章の目的は、一発生成が**どこで、どのようにうまくいかないのか**を自分の目で確かめることです。何が問題なのかがわかれば、第III部以降で作る仕組み（プロット、シーン分割、設定資料の検索、推敲ループなど）が、なぜ必要なのかが見えてきます。

この章で作るものは次のとおりです。

| ファイル・コマンド | 内容 |
|---|---|
| `src/novelist/oneshot.py` | 一発生成のプロンプトを組み立てる |
| `src/novelist/story_file.py` | 生成した小説を、設定などの情報と一緒に保存する |
| `src/novelist/analysis.py` | 文章の統計（文字数、文末の偏り、繰り返しなど）を計算する |
| `novelist oneshot` | 一発生成で短編を書かせ、ファイルに保存する |
| `novelist stats` | 保存した小説の統計を表示する |

## 7.1 一発生成のプロンプト

LLMに渡すメッセージは、第6章の `ask` と同じく、システムプロンプトとユーザーの指示の2つです。ユーザーの指示には、ジャンル、取り入れる要素（タグ）、長さを書きます。

```text
[system]
あなたは日本語で娯楽小説を書く小説家です。

[user]
次の条件で短編小説を書いてください。
- ジャンル: ミステリー
- 取り入れる要素: 鉄道、冬
- 長さ: 5000字程度
- 1行目にタイトルを書き、1行空けて本文を続けてください。
```

プロンプトの書き方にはいろいろな工夫がありますが、それは第8章で扱います。この章では、あえてこの素朴なプロンプトのまま進めます。

### 生成するトークン数の上限

第6章の `ask` では、`max_tokens`（生成するトークン数の上限）に設定ファイルの値をそのまま使いました。小説を書かせる場合は、目標の文字数に合わせて決める必要があります。上限が小さすぎると、書いている途中で切れてしまうからです。

第3章で見たように、日本語はおおむね1文字 ≒ 0.7〜1トークンです。そこで、目標の文字数の1.5倍を上限にします。ただし、第3章で説明したとおり、**入力と出力を合わせてコンテキスト長に収まる**必要があります。

```text
max_tokens = min(目標の文字数 × 1.5, コンテキスト長 − 入力のトークン数)
```

### プロンプトを組み立てるモジュール

**`src/novelist/oneshot.py`**（新規）

```python
"""1回の呼び出しで短編を書かせる（第7章）。"""

from novelist.llm.client import Message

SYSTEM_PROMPT = "あなたは日本語で娯楽小説を書く小説家です。"


def build_messages(genre: str, tags: list[str], length: int) -> list[Message]:
    """短編を書かせるためのメッセージを組み立てる。"""
    tag_text = "、".join(tags) if tags else "特になし"
    user = (
        "次の条件で短編小説を書いてください。\n"
        f"- ジャンル: {genre}\n"
        f"- 取り入れる要素: {tag_text}\n"
        f"- 長さ: {length}字程度\n"
        "- 1行目にタイトルを書き、1行空けて本文を続けてください。"
    )
    return [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": user},
    ]


def max_tokens_for(length: int, n_ctx: int, prompt_tokens: int) -> int:
    """目標の文字数から、生成するトークン数の上限を決める。

    1文字 ≒ 1トークンとして、目標の1.5倍まで書けるようにする。
    ただし、コンテキスト長から入力の分を引いた残りを超えないようにする。
    """
    wanted = int(length * 1.5)
    available = n_ctx - prompt_tokens
    return max(0, min(wanted, available))
```

- `build_messages` は、ジャンル・タグ・長さから、第6章の `LLMClient` に渡すメッセージのリストを作ります。タグは「、」でつなげ、指定がなければ「特になし」とします。
- `max_tokens_for` は、上の式のとおりに生成するトークン数の上限を計算します。

## 7.2 生成した小説を保存する

一発生成の結果は、あとで読み比べたり統計を取ったりできるように、ファイルに保存します。そのとき、**どんな条件で生成したか**も一緒に記録しておきます。同じ指示でも、設定が違えば結果が変わるからです。

ファイルの形式は、先頭に `---` で囲んだ**front matter**（メタデータ）を付けたMarkdownにします。ブログやドキュメントのツールでよく使われる形式です。

```markdown
---
genre: ミステリー
tags: 鉄道, 冬
target_length: 5000
profile: creative
temperature: 1.0
max_tokens: 7500
finish_reason: stop
prompt_tokens: 83
completion_tokens: 2415
---

霧の終着駅

ストーブの上で薬缶が鳴っていた。……
```

**`src/novelist/story_file.py`**（新規）

```python
"""生成した小説を、メタデータ付きのMarkdownファイルとして保存・読み込みする。"""

from pathlib import Path
from typing import Any


def write_story(path: Path, meta: dict[str, Any], text: str) -> None:
    """先頭にメタデータ（front matter）を付けて保存する。"""
    lines = ["---"]
    lines += [f"{key}: {value}" for key, value in meta.items()]
    lines += ["---", "", text.strip(), ""]
    path.parent.mkdir(parents=True, exist_ok=True)
    path.write_text("\n".join(lines), encoding="utf-8")


def read_story(path: Path) -> tuple[dict[str, str], str]:
    """メタデータと本文を読み込む。メタデータがなければ空の辞書を返す。"""
    content = path.read_text(encoding="utf-8")
    if not content.startswith("---\n"):
        return {}, content
    header, _, body = content[4:].partition("\n---\n")
    meta = {}
    for line in header.splitlines():
        key, sep, value = line.partition(": ")
        if sep:
            meta[key] = value
    return meta, body.strip()
```

- `write_story` は、メタデータを `キー: 値` の形で1行ずつ書き、`---` で囲んでから本文を書きます。`path.parent.mkdir(parents=True, exist_ok=True)` で、保存先のディレクトリがなければ作ります。
- `read_story` は、ファイルの先頭が `---` で始まっていれば、次の `---` までをメタデータとして読み取ります。`str.partition()` は、文字列を最初に見つかった区切りの前・区切り・後ろの3つに分けるメソッドです。値はすべて文字列として読み込まれます。

メタデータの形式は、本格的には **YAML** と呼ばれる形式です。ここでは `キー: 値` の単純な形だけを扱うので、ライブラリを使わずに自分で読み書きしています。

## 7.3 文章を観察する道具

生成された小説は、もちろん自分で読んで評価するのがいちばんです。しかし、何本も生成して比べるときには、数値で傾向をつかめると便利です。ここでは、一発生成の問題を観察するための簡単な統計を計算するモジュールを作ります。

| 統計 | 内容 | 何がわかるか |
|---|---|---|
| 文字数 | 空白と改行を除いた文字数 | 目標の長さに届いているか |
| 段落 | 空でない行の数 | 文章の区切り方 |
| 会話 | 会話文（「」の中）の文字の割合 | 会話と地の文のバランス |
| 地の文の文末 | 各文の最後の2文字（「た。」「る。」など）の割合の上位3つ | 文末が単調になっていないか |
| 繰り返し | 2回以上出てくる10文字の並びが占める割合 | 同じ表現や段落を繰り返していないか |

**文末**は、日本語の文章の単調さがいちばん表れやすいところです。「〜た。」「〜た。」「〜た。」と過去形の文末ばかりが続くと、読んでいてリズムが単調に感じられます。人間の書き手は、「〜た。」の間に現在形（「〜る。」）や体言止め、「〜のだ。」などを混ぜて変化をつけます。

**繰り返し**は、LLMの生成でときどき起きる「同じ文や段落をぐるぐる繰り返す」現象を検出するためのものです。普通の文章では、10文字の並びがまったく同じ形で2回出てくることはあまりないので、この値は小さくなります（多くの場合、数％以下）。

**`src/novelist/analysis.py`**（新規）

```python
"""生成した文章を観察するための簡単な統計。"""

import re
from collections import Counter
from dataclasses import dataclass

DIALOGUE_RE = re.compile(r"「[^」]*」")
SENTENCE_END_RE = re.compile(r"(?<=[。！？])")


@dataclass
class TextStats:
    """文章の統計。"""

    chars: int  # 空白と改行を除いた文字数
    paragraphs: int  # 段落（空でない行）の数
    dialogue_ratio: float  # 会話文（「」の中）の文字の割合
    top_endings: list[tuple[str, float]]  # 地の文の文末（最後の2文字）と、その割合
    repeated_ratio: float  # 2回以上出てくる10文字の並びが占める割合


def _compact(text: str) -> str:
    """空白と改行を取り除く。"""
    return re.sub(r"\s", "", text)


def sentence_endings(text: str) -> Counter[str]:
    """地の文の各文の、最後の2文字（「た。」など）を数える。"""
    narrative = DIALOGUE_RE.sub("", text)
    endings: Counter[str] = Counter()
    for sentence in SENTENCE_END_RE.split(narrative):
        sentence = _compact(sentence)
        if len(sentence) >= 2 and sentence[-1] in "。！？":
            endings[sentence[-2:]] += 1
    return endings


def repeated_ratio(text: str, n: int = 10) -> float:
    """n文字の並びのうち、文章中に2回以上出てくるものの割合。"""
    compact = _compact(text)
    ngrams = [compact[i : i + n] for i in range(len(compact) - n + 1)]
    if not ngrams:
        return 0.0
    counts = Counter(ngrams)
    return sum(1 for g in ngrams if counts[g] >= 2) / len(ngrams)


def text_stats(text: str) -> TextStats:
    """文章の統計を計算する。"""
    compact = _compact(text)
    dialogue = sum(len(_compact(m)) for m in DIALOGUE_RE.findall(text))
    endings = sentence_endings(text)
    total_endings = sum(endings.values())
    top = [(e, c / total_endings) for e, c in endings.most_common(3)] if total_endings else []
    paragraphs = [line for line in text.splitlines() if line.strip()]
    return TextStats(
        chars=len(compact),
        paragraphs=len(paragraphs),
        dialogue_ratio=dialogue / len(compact) if compact else 0.0,
        top_endings=top,
        repeated_ratio=repeated_ratio(text),
    )
```

- **`DIALOGUE_RE`**：`「` から `」` までを見つける正規表現です。`[^」]*` は「`」` 以外の文字が0個以上」という意味です。会話文の割合を計算するのと、文末を数えるときに会話文を取り除くのに使います。
- **`SENTENCE_END_RE`**：`(?<=[。！？])` は「直前が `。！？` のどれかである位置」を表します。この位置で分割すると、句点を残したまま文に分けられます。
- **`sentence_endings`**：会話文を取り除いた地の文を文に分け、各文の最後の2文字を `Counter` で数えます。`Counter` は、要素の出現回数を数える辞書です。
- **`repeated_ratio`**：空白を除いた文章から、10文字の並び（**n-gram**）をすべて取り出して数えます。そのうち、2回以上出てくる並びが占める割合を返します。

**`oneshot`**

1. 設定ファイルとプロファイルを読み込みます。本文を書かせるので、既定のプロファイルは `creative` にしています。
2. `--tags` のカンマ区切りの文字列をリストにし、`build_messages` でメッセージを作ります。
3. `server_info()` で実行時のコンテキスト長を、`count_tokens()` で入力のトークン数を調べ、`max_tokens_for` で生成するトークン数の上限を決めます。チャットテンプレートで役割の区切りなどが加わる分として、入力のトークン数に32を足しています。
4. `sampling.model_copy(update=...)` で、`max_tokens` だけを差し替えたコピーを作ります。Pydanticのモデルは、`model_copy` で一部の値を変えたコピーを作れます。元の設定は変わりません。
5. 第6章の `ask` と同じようにストリーミングで表示しながら生成します。
6. 生成が終わったら、`works/oneshot/` に「年月日-時分秒.md」という名前で保存し、文字数と目標に対する割合、終了の理由を表示します。上限に達して途中で切れた場合（`finish_reason` が `length`）は、警告を表示します。

**`stats`**

指定したファイル（複数可）を読み込み、統計を表で表示します。メタデータに目標の文字数（`target_length`）があれば、目標に対する割合も表示します。第2章で `.gitignore` に `works/` を追加したので、生成した小説はGitの管理対象にはなりません。

目標を2000字にした場合はほぼ目標どおりですが、5000字、10000字、20000字と増やしても、実際の長さは**3000〜4000字程度で頭打ち**になっています。終了理由はどれも `stop` で、`max_tokens` の上限で切れたのではなく、**モデル自身が「書き終わった」と判断して止まった**ことがわかります。

### なぜ長く書けないのか

インストラクションモデルは、「指示に対して適切な長さで答える」ように訓練されています。訓練に使われた応答の多くは、数百〜数千字程度です。そのため、「20000字で」と指示されても、モデルにとって自然な長さで話をまとめて、終了のトークンを出してしまいます。

長い目標を与えた生成結果を読むと、次のような特徴が見つかるはずです。

- **展開が駆け足になる**：序盤は丁寧に描写しているのに、後半になると「そして三日後、事件は解決した」のように、要約のような文章で一気に結末まで進む
- **「まとめ」で終わる**：最後の段落が、物語の教訓や登場人物の心境の総括になる
- **繰り返しが増える**：目標が長いほど「繰り返し」の値が大きくなる傾向がある。長く書こうとして、同じ描写や言い回しを使い回している

逆に、`max_tokens` を小さくしすぎると、今度は**文の途中で切れて**終わります（終了理由が `length` になります）。一発生成では、「ちょうどよい長さで、きちんと完結した物語」を得るのは難しいのです。

## 7.7 実験2：一貫性

次に、10000字を目標に生成した結果を、じっくり読んでみましょう。次の観点でチェックします。

| 観点 | チェックすること |
|---|---|
| 人物 | 名前や呼び方が途中で変わっていないか。登場人物の人数が合っているか |
| 口調 | 同じ人物の話し方（一人称、語尾）が変わっていないか |
| 時間 | 時刻や日付、出来事の順番に矛盾がないか |
| 場所 | 部屋の配置や、人物がどこにいるかに矛盾がないか |
| 設定 | 最初に示した設定（雪で列車が止まっている、など）が守られているか |
| 伏線 | 序盤で示した手がかりや謎が、最後に回収されているか |

生成された文章では、たとえば次のような問題が見つかることがあります。

- 最初に「乗客は四人」と書いたのに、後半で五人目が当然のように会話に加わっている
- 「僕」と名乗っていた人物が、後半で「俺」になっている
- 序盤で「駅員室の鍵がなくなった」という謎が示されたのに、最後まで触れられない
- 「午後十時」の出来事の後に「夕方になり」という描写が出てくる

### なぜ一貫性が崩れるのか

第3章で説明したように、LLMは1トークンずつ、それまでの文字列だけを見て続きを選んでいます。生成した文章はすべて入力に含まれているので、原理的には前の内容を「見る」ことはできます。しかし、次の理由で矛盾が起きます。

- **計画がない**：物語の全体像（誰が犯人で、どの手がかりをどこで回収するか）を決めずに書き始めているので、書きながら辻褄を合わせるしかない
- **注意が薄まる**：文章が長くなるほど、序盤のささいな設定（人数、一人称など）に注意が向きにくくなる
- **書き直せない**：一度出力したトークンは取り消せない。矛盾に気づいても、戻って直すことができない

人間の書き手が、プロットを立て、設定をメモし、書いたあとで読み返して直すのは、まさにこの問題を避けるためです。

## 7.8 実験3：単調さ

最後に、同じ条件で3回生成して、読み比べてみます。

```console
$ for i in 1 2 3; do uv run novelist oneshot -t 鉄道,冬 -l 3000; done
```

3本を並べて読むと、次のような共通点に気づくはずです。

- **似た書き出し**：3本とも「雪」「静寂」「ストーブ」「薬缶」といった同じような描写で始まる
- **似た人物**：老いた駅長、訳ありの若い女性、無口な男といった、よく見る組み合わせになる
- **似た展開**：「実は全員が〇〇でつながっていた」「犯人は意外にも〜」のような、ありがちな結末に落ち着く
- **文末の偏り**：`stats` で見ると、地の文の文末の7割以上が「た。」になっている

```text
│ 20260926-143512.md │   2890 │    96% │   42 │  26% │ た。 75% る。 8% い。 5% │     1.1% │
│ 20260926-143618.md │   3102 │   103% │   45 │  23% │ た。 79% る。 6% だ。 4% │     0.9% │
│ 20260926-143729.md │   2954 │    98% │   40 │  28% │ た。 73% る。 9% い。 5% │     1.4% │
```

### なぜ単調になるのか

LLMは、次のトークンの確率に従って文章を選びます。確率の高い選択肢とは、言い換えれば「**学習した大量の文章の中で、よくある選択肢**」です。そのため、特に指定がなければ、よくある舞台、よくある人物、よくある展開が選ばれやすくなります。

`temperature` を上げれば、確率の低い選択肢も選ばれるようになり、変化が出ます。しかし上げすぎると、今度は文章そのものが崩れてきます。第9章では、「変化はほしいが、崩れてほしくない」を両立させるサンプリングの方法を学びます。

また、インストラクションモデルは、「無難で読みやすい応答」をするように訓練されています。小説では、この「無難さ」が「ありきたりさ」として表れます。これをどう崩していくかは、第V部（文体制御）と第VI部（好みの学習）のテーマです。

## 7.9 限界のまとめ

3つの実験でわかった一発生成の限界と、それを本書のどこで解決するかをまとめます。

| 問題 | 主な原因 | 本書での対策 |
|---|---|---|
| 長く書けない、後半が駆け足になる | 1回の応答で話をまとめようとする | 第III部：プロットを作り、シーンごとに分けて書く |
| 途中で切れる | `max_tokens` とコンテキスト長の制約 | 第III部：シーン単位で書く。第20章：コンテキストの予算管理 |
| 人物や設定が変わる | 計画がない、序盤の設定に注意が向かない | 第13章：設定シート。第IV部：設定資料の検索と一貫性チェック |
| 伏線が回収されない | 全体の構成を決めずに書いている | 第14章：プロット。第31章：伏線トラッカー |
| 書き直せない | 一度出力したら取り消せない | 第16章：推敲ループ |
| 展開・人物がありきたり | 確率の高い＝よくある選択肢が選ばれる | 第9章：サンプリング。第12章：企画を複数出して選ぶ |
| 文末や表現が単調 | 同上。無難な応答をするよう訓練されている | 第V部：文体制御。第VI部：好みの学習 |

**「1回で全部書かせる」のをやめて、人間の書き手と同じように工程を分ける**。これが、第III部以降の基本方針です。

ただし、その前に、1回の呼び出しの質を上げるための基本を押さえておく必要があります。プロンプトの書き方（第8章）、サンプリング（第9章）、構造化出力（第10章）です。これらは、工程を分けたあとの各工程でも、そのまま使う技術です。

import pytest

from novelist.analysis import repeated_ratio, sentence_endings, text_stats

TEXT = """雪が降っていた。駅は静かだった。
「誰かいるのか」と彼は言った。
返事はない。彼は歩き出した。"""


def test_sentence_endings_ignore_dialogue() -> None:
    endings = sentence_endings(TEXT)
    # 会話文「誰かいるのか」は除き、地の文の文末だけを数える
    assert endings == {"た。": 4, "い。": 1}


def test_repeated_ratio() -> None:
    assert repeated_ratio("あいうえおかきくけこさしすせそ") == 0.0
    # 同じ文を2回繰り返すと、ほとんどの並びが2回以上出てくる
    assert repeated_ratio("雪が降っていた。駅は静かだった。" * 2) > 0.5


def test_text_stats() -> None:
    st = text_stats(TEXT)
    assert st.chars == len(TEXT.replace("\n", ""))
    assert st.paragraphs == 3
    assert st.dialogue_ratio == pytest.approx(len("「誰かいるのか」") / st.chars)
    assert st.top_endings[0] == ("た。", 0.8)

## 7.11 まとめ

- LLMに1回だけ短編を書かせる `novelist oneshot` を作りました。生成した小説は、生成の条件と一緒に `works/oneshot/` に保存されます
- 文字数、文末の偏り、繰り返しなどを計算する `novelist stats` を作りました
- 3つの実験で、一発生成の限界を確かめました
  - **長さ**：目標を大きくしても、モデルが自分で話をまとめて止まってしまう
  - **一貫性**：計画がなく、書き直せないので、人物や設定、伏線に矛盾が生じる
  - **単調さ**：確率の高い＝よくある選択肢が選ばれ、似た展開や単調な文末になる
- これらの問題は、第III部以降で工程を分けることで解決していきます

次の第8章では、プロンプトの設計を学びます。システムプロンプトとユーザーの指示の役割分担、指示の粒度、禁止事項の書き方などを、この章の一発生成を題材に改善していきます。
