# 第15章 シーン執筆ノード

第14章で、物語をシーンに分け、シーンごとに**シーンカード**を作りました。この章では、いよいよ本文を書きます。シーンカードを1枚ずつLLMに渡して、シーンごとに本文を書かせ、最後に1つの原稿にまとめます。

シーンごとに書くと、第7章で見た「後半が駆け足になる」問題は起きにくくなります。1回に書く量が少なく、何を書くかがシーンカードで決まっているからです。その代わりに、新しい問題が生まれます。**LLMは、前のシーンで何を書いたかを覚えていない**という問題です。

LLMのAPIは、呼び出しのたびに独立しています。2つめのシーンを書くとき、LLMは1つめのシーンの本文を知りません。知らせるには、プロンプトに入れて渡すしかありません。この章の中心は、**シーンを書くときに、何を、どれだけ渡すか**です。

この章で作るものは次のとおりです。

| ファイル・コマンド | 内容 |
|---|---|
| `src/novelist/schemas/scene.py` | 書き終えたシーンの記録と要約のモデル |
| `src/novelist/writing.py` | シーンを書くために渡す情報を組み立てる。書かれた本文を整える |
| `src/novelist/work.py` | シーンの保存と読み込み、原稿の書き出しを追加 |
| `prompts/scene/` | シーンの本文を書くプロンプト |
| `prompts/scene_summary/` | 書いたシーンを要約するプロンプト |

| `novelist write` | プロットに沿って本文を書くコマンド |

## 15.1 シーンごとに何を渡すか

### 渡す情報

1つのシーンを書くときに、LLMに渡す情報を整理します。

| 情報 | 役割 | 出どころ |
|---|---|---|
| シーンカード（目的・葛藤・結果・出来事） | 何を書くか | プロット（第14章） |
| 場所と、このシーンの登場人物 | 設定と食い違わないように書く | 設定資料（第13章） |
| これまでのあらすじ | 物語の流れを踏まえる | 書き終えたシーンの**要約** |
| 直前の文章 | 文章を自然につなげる | 直前のシーンの本文の末尾 |
| 次のシーン | どこで書くのを止めるか | プロット（第14章） |

図にすると、次のようになります。

```text
             設定資料 ──→ 場所・このシーンの人物だけ ──┐
             プロット ──→ シーンカード・次のシーン ────┤
                                                      ↓
  シーン1の要約 ─┐                               ┌──────────┐
  シーン2の要約 ─┼→ これまでのあらすじ ─────────→│ シーン3を │→ 本文 → 要約 → シーン4へ
  シーン2の本文 ──→ 末尾の300字（直前の文章）───→│   書く   │
                                                 └──────────┘
```

### なぜ、前の本文をすべて渡さないのか

前のシーンの本文を、すべてプロンプトに入れて渡せば、LLMは何が書かれたかを完全に知ることができます。しかし、次の理由で、それはしません。

- **コンテキスト長が足りなくなる**：日本語の本文は、1文字あたりおよそ0.7〜1トークンです（第3章）。1万字の短編なら、最後のシーンを書くときには、入力だけで1万トークン近くになります。第VII部の長編（10万字）では、そもそもコンテキストに入りません。第4章で見たとおり、コンテキスト長を伸ばすと、KVキャッシュのためのVRAMが増えます。
- **長い入力の中ほどは、読み落とされやすい**：LLMは、入力が長くなると、最初と最後の部分はよく参照しますが、中ほどにある情報を見落としやすくなることが知られています。1つめのシーンに書いた手がかりは、長い入力の中ほどに埋もれてしまいます。
- **遅くなる**：第5章で見たとおり、入力の読み込みは生成より速いものの、シーンのたびに長い入力を読み込むことになります。

そこで、書き終えたシーンは**要約**にして渡します。1シーンの要約を200字以内にすれば、12シーンでも2400字ほどです。要約には、次のシーン以降で必要になること（人物が知ったこと、ついた嘘、物の移動など）を優先して残させます。

要約だけでは、文章の調子や、シーンの最後の瞬間の状況が伝わりません。そこで、**直前のシーンの末尾**だけは、本文をそのまま渡します。LLMは、この続きとして、新しいシーンを書き始めます。

どのくらいの量を渡すのがよいかは、モデルのコンテキスト長によって変わります。この章では、短編に十分な単純な方法をとります。入力をトークンの予算の中に収める方法は、第20章で扱います。

### 設定資料は、必要な部分だけ渡す

設定資料も、すべてを渡すのではなく、**このシーンの場所と、このシーンに登場する人物だけ**を渡します。人間関係も、このシーンの人物どうしのものだけにします。

これは、コンテキストを節約するためだけではありません。LLMは、プロンプトに書かれた人物を、登場させたがる傾向があります。このシーンにいないはずの人物の設定を渡すと、その人物が勝手に登場したり、話題に上ったりしがちです。渡さなければ、登場のしようがありません。

どの設定を渡すかは、この章ではシーンカードの人物と場所から、プログラムで決めます。本文の内容に応じて、関係のある設定を検索して渡す方法は、第19章で扱います。

### 長さを目安に近づける

第14章では、シーンごとに目安の文字数を決めました。しかし、LLMに「約900字で書いて」と指示しても、その通りの長さにはなりません。この章では、次の3つの工夫で、本文の長さを目安に近づけます。

1. **出来事ごとに文字数を示す**：シーンの目安の文字数を出来事の数で割り、「運休の放送が流れる（約300字）」のように、出来事ごとの目安をプロンプトに書きます。第8章で、全体の文字数を場面ごとに割り振ったのと同じ考え方です。全体の長さより、小さな単位の長さのほうが、LLMは守りやすくなります。
2. **生成するトークン数に上限を設ける**：目安の文字数の2倍を `max_tokens` にします。LLMが次のシーンの出来事まで書き進めてしまっても、どこかで止まります。上限で止まったときは、最後の文の終わりより後ろを切り捨てます。
3. **短すぎたら書き直す**：書いた本文が目安の7割に届かなければ、足りなかったことを伝えて、1回だけ書き直させます。第11章の最小のグラフと同じ方法です。

長すぎる場合は、書き直しません。少し長いくらいなら、読む上で困ることはないからです。長すぎる原因の多くは、次のシーンの出来事まで書いてしまうことで、これは推敲（第16章）で直します。

## 15.2 シーンの記録

書き終えたシーンは、本文と一緒に、**記録**を保存します。記録には、要約と、目安と実際の文字数などを入れます。要約は、次のシーン以降を書くときに使います。

**`src/novelist/schemas/scene.py`**（新規）

```python
"""書き終えたシーンの記録（第15章）。"""

import re
from datetime import datetime

from pydantic import BaseModel, Field

SCENE_KEY_RE = re.compile(r"^(\d+)-(\d+)$")


def scene_key(chapter: int, scene: int) -> str:
    """シーンを指す文字列（"2-1" のような、章の番号とシーンの番号の組）。"""
    return f"{chapter}-{scene}"


def parse_scene_key(key: str) -> tuple[int, int]:
    """「2-1」のような文字列を、(章の番号, シーンの番号) にする。"""
    m = SCENE_KEY_RE.match(key)
    if not m:
        raise ValueError(f"シーンは「章の番号-シーンの番号」の形で指定してください: {key}")
    return int(m.group(1)), int(m.group(2))


class SceneSummary(BaseModel):
    """LLMに作らせる、シーンの要約。"""

    summary: str = Field(
        description="この場面で起きたこと。誰が何をして、何がわかり、状況がどう変わったか",
        max_length=200,
    )


class SceneRecord(BaseModel):
    """書き終えたシーンの記録。本文と一緒に scenes/ に保存する。"""

    chapter: int  # 章の番号（1から）
    scene: int  # 章の中のシーンの番号（1から）
    title: str
    target_chars: int  # プロットでの目安の文字数
    chars: int  # 実際の文字数
    attempts: int  # 書いた回数
    summary: str  # 次のシーン以降に渡す要約
    written_at: datetime

    @property
    def key(self) -> str:
        return scene_key(self.chapter, self.scene)
```

**`scene_key` と `parse_scene_key`**

シーンを「2-1」（第2章のシーン1）のような文字列で指すことにします。第14章の `plot` コマンドの表示と同じ形です。コマンドの `--from 2-1` のように、利用者がシーンを指定するときにも使います。

**`SceneSummary`**

LLMに作らせる要約のモデルです。第10章の構造化出力で、`max_length=200` によって、要約が長くなりすぎないことを保証します。要約は1つの文字列だけですが、構造化出力にしておくと、前置きや解説が混ざらず、長さの制約も文法で守られます。

**`SceneRecord`**

保存する記録です。要約のほかに、目安の文字数（`target_chars`）と実際の文字数（`chars`）、書いた回数（`attempts`）を残しておきます。あとで、どのシーンが目安からずれやすいか、何回書き直したかを調べられます。

`key` は `@property` で、`record.key` のように、属性として `"2-1"` を返します。

## 15.3 執筆に渡す情報を組み立てる

15.1節の情報を集めて、1つのシーンを書くための「指示書」にまとめるモジュールを作ります。

**`src/novelist/writing.py`**（新規）

```python
"""シーンの執筆に渡す情報を組み立て、書かれた本文を整える（第15章）。"""

import re
from dataclasses import dataclass

from novelist.oneshot import PREAMBLE_RE
from novelist.schemas.bible import CharacterSheet, Place, Relationship, WorldSheet
from novelist.schemas.character import Character
from novelist.schemas.plot import Chapter, Plot, Scene
from novelist.schemas.scene import SceneRecord, scene_key

PREVIOUS_TAIL_CHARS = 300  # 直前のシーンの本文から、末尾を何文字渡すか
BEAT_CHARS_UNIT = 50  # 出来事ごとの文字数を丸める単位

# 文の終わり（句点・感嘆符・疑問符と、そのあとに続く閉じかっこ）
SENTENCE_END_RE = re.compile(r"[。！？!?][」』）)]*")


@dataclass
class Beat:
    """シーンの中の出来事と、その目安の文字数。"""

    text: str
    chars: int


@dataclass
class SceneBrief:
    """1つのシーンを書くために、LLMに渡す情報。"""

    chapter_no: int
    scene_no: int
    chapter: Chapter
    scene: Scene
    beats: list[Beat]
    place: Place | None  # 設定資料の場所（プロットの検証で、必ず見つかるはず）
    characters: list[Character]  # このシーンに登場する人物だけ
    relationships: list[Relationship]  # このシーンの人物どうしの関係だけ
    story_so_far: list[str]  # これまでのシーンの要約（書いた順）
    previous_tail: str  # 直前のシーンの本文の末尾
    next_scene: Scene | None  # 次のシーン（最後のシーンなら None）

    @property
    def key(self) -> str:
        return scene_key(self.chapter_no, self.scene_no)


def beat_budget(scene: Scene) -> list[Beat]:
    """シーンの目安の文字数を、出来事ごとに等分する。"""
    per_beat = scene.chars / len(scene.beats)
    chars = max(BEAT_CHARS_UNIT, round(per_beat / BEAT_CHARS_UNIT) * BEAT_CHARS_UNIT)
    return [Beat(text, chars) for text in scene.beats]


def tail_text(text: str, max_chars: int = PREVIOUS_TAIL_CHARS) -> str:
    """本文の末尾を、段落の区切りから max_chars 文字以内で取り出す。

    段落の途中から始まると、LLMがその続きを書こうとしてしまうので、段落の先頭から渡す。
    最後の段落だけで max_chars を超える場合は、文の区切りから始める。
    """
    paragraphs = [p for p in text.strip().splitlines() if p.strip()]
    picked: list[str] = []
    total = 0
    for paragraph in reversed(paragraphs):
        if total + len(paragraph) > max_chars:
            break
        picked.insert(0, paragraph)
        total += len(paragraph)
    if picked:
        return "\n".join(picked)
    if not paragraphs:
        return ""
    # 最後の段落が長すぎる。max_chars 文字以内に収まる、文の先頭を探す
    last = paragraphs[-1]
    for m in SENTENCE_END_RE.finditer(last):
        if len(last) - m.end() <= max_chars:
            return last[m.end() :]
    return last[-max_chars:]


def build_brief(
    plot: Plot,
    world: WorldSheet,
    characters: CharacterSheet,
    chapter_no: int,
    scene_no: int,
    records: dict[str, SceneRecord],
    previous_text: str,
) -> SceneBrief:
    """プロット・設定資料・これまでの記録から、1つのシーンを書くための情報を集める。

    records は、書き終えたシーンの記録（キーは "1-2" のような文字列）。
    previous_text は、直前のシーンの本文（最初のシーンなら空文字列）。
    """
    order = plot.scenes()
    index = next(n for n, (i, j, _) in enumerate(order) if (i, j) == (chapter_no, scene_no))
    _, _, scene = order[index]
    names = set(scene.characters)
    story_so_far = [
        f"{i}-{j}「{s.title}」: {records[scene_key(i, j)].summary}"
        for i, j, s in order[:index]
        if scene_key(i, j) in records
    ]
    return SceneBrief(
        chapter_no=chapter_no,
        scene_no=scene_no,
        chapter=plot.chapters[chapter_no - 1],
        scene=scene,
        beats=beat_budget(scene),
        place=next((p for p in world.places if p.name == scene.place), None),
        # 人物は、プロットに書かれた順に並べる
        characters=[
            c for name in scene.characters for c in characters.characters if c.name == name
        ],
        relationships=[
            r for r in characters.relationships if r.source in names and r.target in names
        ],
        story_so_far=story_so_far,
        previous_tail=tail_text(previous_text) if previous_text else "",
        next_scene=order[index + 1][2] if index + 1 < len(order) else None,
    )


def trim_incomplete(text: str) -> str:
    """途中で切れた文章の、最後の文の終わりより後ろを取り除く。"""
    ends = list(SENTENCE_END_RE.finditer(text))
    if not ends:
        return text
    return text[: ends[-1].end()]


# シーンの本文の前に付きがちな見出し（「# 第1章」「**シーン1**」「第1章 シーン2」など）
HEADING_RE = re.compile(r"^(#|\*\*|第\d+章|シーン\s*\d+|[-=*]{3,}$)")


def clean_scene_text(text: str) -> str:
    """LLMの出力から、シーンの本文以外の余計な部分を取り除く。

    第7章の clean_story_text と違い、1行目をタイトルとして扱わない。
    """
    lines = text.strip().splitlines()
    while lines and (
        not lines[0].strip()
        or PREAMBLE_RE.match(lines[0])
        or HEADING_RE.match(lines[0].strip())
        or lines[0].startswith("```")
    ):
        lines.pop(0)
    while lines and (
        not lines[-1].strip() or lines[-1].startswith("```") or re.match(r"^[-=*]{3,}$", lines[-1])
    ):
        lines.pop()
    return "\n".join(lines).strip()
```

**`SceneBrief`**

1つのシーンを書くために渡す情報を、1つにまとめたデータクラスです。プロンプトのテンプレートには、この `brief` を1つ渡すだけで済むようにします。第13章の `PlanContext` と同じく、`@dataclass` を使っています。Pydanticのモデルにしないのは、JSONに保存したり、LLMの出力を検証したりする必要がないからです。

**`beat_budget`**

シーンの目安の文字数を、出来事の数で等分します。3500字で出来事が3つなら、1つあたり約1167字ですが、50字単位に丸めて1150字にします。目安なので、細かい端数は必要ありません。

出来事によって重さは違いますが、ここでは等分にしています。出来事ごとの長さまでプロットで決めさせると、第14章で見たとおり、LLMは数の扱いが苦手なので、かえって不安定になります。

**`tail_text`**

直前のシーンの本文の、末尾の300字ほどを取り出します。ただし、**段落の途中から始めない**ようにしています。段落の途中から渡すと、LLMは「文章の途中」だと思って、その段落の続きを書こうとするからです。段落を後ろから1つずつ加えていき、300字を超える手前で止めます。

最後の段落だけで300字を超える場合は、文の区切り（`。」` など）を探して、300字以内に収まる最初の文から渡します。`SENTENCE_END_RE` は、句点・感嘆符・疑問符と、そのあとに続く閉じかっこをまとめて「文の終わり」とみなす正規表現です。「そうか」と彼は言った。のような文で、`」` の手前で切ってしまわないようにするためです。

**`build_brief`**

プロット・設定資料・書き終えたシーンの記録から、`SceneBrief` を作ります。

- `plot.scenes()`（第14章）で、すべてのシーンを順に並べ、書くシーンが何番目かを探します。それより前のシーンの要約が「これまでのあらすじ」、1つ後ろのシーンが「次のシーン」です。
- 登場人物は、シーンカードの `characters` に書かれた順に並べます。1つめが視点人物になることが多いので、その順のほうが、LLMが視点人物を取り違えにくくなります。
- 人間関係は、`source` と `target` の両方がこのシーンにいるものだけを残します。
- `place` は、第14章のプロットの検証で、設定資料にある場所だけを使うようにしたので、必ず見つかるはずです。それでも、手で `plot.json` を書き換えた場合などに備えて、見つからなければ `None` にしています。

**`trim_incomplete`**

`max_tokens` で生成が止まった場合、本文は文の途中で切れています。最後の「文の終わり」より後ろを取り除きます。

**`clean_scene_text`**

第7章の `clean_story_text` と同じく、LLMが本文の前後に付けがちな余計な部分を取り除きます。シーンの本文にはタイトルがないので、1行目をタイトルとして扱わない点が違います。「はい、書きます。」のような前置きの判定には、第7章の `PREAMBLE_RE` をそのまま使います。そのほかに、次のような見出しや区切り線も取り除きます。

```text
# 第1章 シーン1          ← 「#」で始まる見出し
**終電のあと**           ← 「**」で囲んだ見出し
---                      ← 区切り線
```

def prepare(state: WriteState, runtime: Runtime[WriteContext]) -> dict:
    """設定資料・プロット・書き終えたシーンの記録を読み込み、これから書くシーンを決める。"""
    work = runtime.context.work
    world, characters = work.load_bible()
    plot = work.load_plot()
    records = work.load_scene_records(plot)
    keys = [scene_key(i, j) for i, j, _ in plot.scenes()]

def write_scene(state: WriteState, runtime: Runtime[WriteContext]) -> dict:
    """シーンカードと、これまでの流れをもとに、シーンの本文を書く。"""
    ctx = runtime.context
    brief = _brief(state, runtime)
    messages = ctx.prompts.render(
        "scene",
        meta=state["meta"],
        world=state["world"],
        brief=brief,
        feedback=state.get("feedback"),
    )
    sampling = ctx.config.sampling_for(WRITE_PROFILE)
    max_tokens = int(brief.scene.chars * WRITE_TOKENS_RATIO)
    sampling = sampling.model_copy(update={"max_tokens": max_tokens})

    # 生成中の文字列を、グラフの外（CLI）へ流す
    writer = get_stream_writer()
    result = ctx.client.stream_chat(messages, sampling, lambda text: writer({"text": text}))

    if not result.text.strip() and result.reasoning:
        # 思考（reasoning）だけで max_tokens を使い切り、本文が1文字も書かれなかった
        raise LLMError(_reasoning_message(len(result.reasoning), max_tokens))

    text = result.text
    if result.finish_reason == "length":
        # max_tokens で途中で切れた。最後の文の終わりまでにする
        text = trim_incomplete(text)
    text = clean_scene_text(text)
    chars = text_stats(text).chars
    attempts = state["attempts"] + 1
    message = f"{attempts}回目: {chars:,}字（終了理由: {result.finish_reason}）"
    if result.reasoning:
        message += f"（思考: {len(result.reasoning):,}文字）"
    return {"text": text, "chars": chars, "attempts": attempts, "log": [message]}

    target = _current_scene(state).chars
    chars = state["chars"]
    ratio = chars / target
    if ratio >= MIN_RATIO:
        return {"feedback": None, "log": [f"長さ: 目安の{ratio:.0%}（合格）"]}
    if state["attempts"] >= MAX_ATTEMPTS:
        return {
            "feedback": None,
            "log": [f"長さ: 目安の{ratio:.0%}（不足。書き直しの上限なので進みます）"],
        }
    feedback = (
        f"前回の原稿は{chars}字で、目安の{target}字に足りませんでした。"
        "出来事を省いたり、次のシーンの出来事を書いたりせずに、"
        "それぞれの出来事の描写と会話を増やしてください。"
    )
    return {"feedback": feedback, "log": [f"長さ: 目安の{ratio:.0%}（不足。書き直します）"]}


def route_after_check(state: WriteState) -> Literal["write_scene", "summarize_scene"]:
    """指摘があれば書き直し、なければ要約へ進む。"""
    return "write_scene" if state.get("feedback") else "summarize_scene"


def summarize_scene(state: WriteState, runtime: Runtime[WriteContext]) -> dict:
    """書いたシーンを要約する。要約は、次のシーン以降を書くときに渡す。"""
    ctx = runtime.context
    brief = _brief(state, runtime)
    messages = ctx.prompts.render(
        "scene_summary", brief=brief, text=state["text"], schema=schema_text(SceneSummary)
    )
    sampling = ctx.config.sampling_for(SUMMARY_PROFILE)
    result = generate_structured(ctx.client, messages, SceneSummary, sampling)
    return {"summary": result.summary, "log": [f"要約: {result.summary}"]}


def save_scene(state: WriteState, runtime: Runtime[WriteContext]) -> dict:
    """シーンの本文と記録を保存する。"""
    work = runtime.context.work
    i, j = parse_scene_key(state["current"])
    scene = _current_scene(state)
    record = SceneRecord(
        chapter=i,
        scene=j,
        title=scene.title,
        target_chars=scene.chars,
        chars=state["chars"],
        attempts=state["attempts"],
        summary=state["summary"],
        written_at=datetime.now().astimezone(),
    )
    work.save_scene(record, state["text"])
    return {
        "records": {**state["records"], record.key: record},
        "log": [f"保存しました → {work.scene_text_path(i, j)}"],
    }


def export(state: WriteState, runtime: Runtime[WriteContext]) -> dict:
    """すべてのシーンを書き終えていれば、原稿を1つのファイルに書き出す。"""
    work = runtime.context.work
    n_scenes = len(_scene_keys(state))
    if len(state["records"]) < n_scenes:
        return {
            "log": [
                f"書き終えたシーン: {len(state['records'])}/{n_scenes}件。"
                f"続きは novelist write {work.slug} で書けます"
            ]
        }
    chars = work.write_manuscript(state["plot"])
    return {"log": [f"原稿を書き出しました → {work.manuscript_path}（{chars:,}字）"]}

**`prepare`**

設定資料・プロット・書き終えたシーンの記録を読み込み、これから書くシーンの待ち行列を作ります。

- `start` が指定されていなければ、**まだ書いていない最初のシーン**から最後までを書きます。途中で止めても、もう一度実行すれば、続きから書けます。
- `start` が指定されていれば、そのシーンから最後までを**書き直します**。ただし、それより前のシーンがすべて書き終わっている必要があります。前のシーンの要約がないと、「これまでのあらすじ」を渡せないからです。
- `limit` が指定されていれば、書くシーンの数をそこまでにします。遅いモデルで、まず数シーンだけ試したいときに使います。

問題があれば、`WorkError` を送出します。ノードの中で起きた例外は、グラフの実行（`invoke` や `stream`）の呼び出し元に、そのまま伝わります。

**`start_scene`**

待ち行列の先頭のシーンを取り出して、`current` にします。`key, *rest = state["queue"]` は、リストの先頭を `key` に、残りをリストで `rest` に代入する書き方です。書き直しの回数（`attempts`）と指摘（`feedback`）は、シーンごとにリセットします。

**`_brief`**

`write_scene` と `summarize_scene` の両方で使う、`SceneBrief` を作る関数です。直前のシーンの本文は、ファイルから読み込みます。直前のシーンは、1つ前の周回で保存したばかりなので、必ずファイルにあります。`--from` で書き直す場合も、それより前のシーンは書き終わっていることを `prepare` で確かめています。

**`write_scene`**

プロンプトを展開し、`creative` プロファイルで本文を書きます。

- `max_tokens` は、目安の文字数の2倍にします（15.1節）。プロファイルの `max_tokens` は使いません。シーンによって目安の文字数が違うからです。
- 第11章と同じく、`get_stream_writer()` で、生成中の文字列をグラフの外（CLI）へ流します。
- 終了理由が `"length"`（`max_tokens` で止まった）なら、`trim_incomplete` で最後の文の終わりまでにします。
- 本文が空で、思考（reasoning）だけが返ってきた場合は、エラーにします。詳しくは次の項で説明します。
- ログには、書いた回数・文字数・終了理由を出します。思考モデルの場合は、思考に使われた文字数も出します。

### 思考モデルで本文が0字になる

思考モデル（第10章）を使っていると、次のように、本文が0字のまま `max_tokens` で止まることがあります。

```console
[write_scene] 1回目: 0字（終了理由: length）
[check_scene] 長さ: 目安の0%（不足。書き直します）
[write_scene] 2回目: 0字（終了理由: length）
[check_scene] 長さ: 目安の0%（不足。書き直しの上限なので進みます）
```

原因は、**思考だけで `max_tokens` を使い切っている**ことです。思考モデルは、本文を書く前に、どう書くかを考える文章（思考）を出力します。第6章で作り、第10章で手を加えた `stream_chat` は、思考を `reasoning_content` として本文とは別に集めていて、画面には表示しません。`write_scene` では `max_tokens` を目安の文字数の2倍（900字のシーンなら1800）にしているので、思考が長いと、本文を書き始める前に上限に達してしまいます。生成中の画面に何も表示されないまま、しばらく待たされるのが特徴です。

第10章では、`precise` プロファイルに `reasoning_effort = "none"` を指定して、思考を止める方法を紹介しました。しかし、本文は `creative` プロファイルで書くので、そちらの思考は止まっていません。思考モデルを使う場合は、`creative` プロファイルにも指定します。`novelist.toml` に、その案内を加えておきます。

## 15.10 うまくいかないときは

**次のシーンの出来事まで書いてしまう**

シーンの結果より先まで書き進めてしまうことがあります。「次のシーン（ここは書かない）」を渡していても、小さいモデルでは起きやすい問題です。次のことを試してください。

- `creative` プロファイルの `temperature` を少し下げる（第9章）。指示を守りやすくなります
- `WRITE_TOKENS_RATIO` を小さくして（たとえば1.5）、書きすぎる前に止める

書きすぎたシーンは、第16章の推敲で、批評の観点の1つとして直します。

**毎回、舞台や人物の紹介から始まる**

シーンの冒頭で、毎回「雪国の小さな駅の待合室には…」と舞台を説明し直すことがあります。「直前の文章」が渡されていれば起きにくいのですが、章の変わり目などで起きやすくなります。`prompts/scene/system.md` の「シーンの書き方」に、「冒頭で、舞台や人物を紹介し直さない」という一文を加えてみてください。

**人物の口調がシーンによって変わる**

登場人物の「口調」は渡していますが、それでも口調が揺れることがあります。口調は、説明より例のほうが伝わりやすいものです。第13章の設定資料の `speech_style` に、「一人称は『わたし』、語尾は『〜ですね』」のように、具体的な例を入れておくと安定します。文体をさらに細かく制御する方法は、第V部で扱います。

**本文が0字になる**

「0字（終了理由: length）」が続く場合や、思考だけで止まったというエラーが出る場合は、思考モデルの思考が原因です。`novelist.toml` の `[profiles.creative]` に `reasoning_effort = "none"` を指定してください（15.6節）。

**要約で失敗する（StructuredOutputError）**

要約の途中で `max_tokens` に達する場合は、第10章の自動の増加で対処されます。思考モデルを使っていて思考に多くのトークンが使われている場合は、`precise` プロファイルに `reasoning_effort = "none"` を指定してください（第10章）。

**遅い**

1シーンにつき、本文と要約で少なくとも2回、LLMを呼び出します。12シーンなら24回以上です。生成の速さは、主に出力するトークンの数で決まります（第5章）。まずは `-n 2` で数シーンだけ書いて、本文の質と速さを確かめてから、全体を書くとよいでしょう。

## 15.11 まとめ

- シーンカードを1枚ずつLLMに渡して、シーンごとに本文を書くグラフを作りました
- LLMは、前のシーンで何を書いたかを覚えていません。**これまでのあらすじ**（書き終えたシーンの要約）と**直前の文章**（前のシーンの末尾）をプロンプトに入れて、物語の流れと文章のつながりを伝えました。前の本文をすべて渡すのは、コンテキスト長と、長い入力の読み落としの点で避けました
- 設定資料は、**このシーンの場所と人物だけ**を渡しました。いない人物の設定を渡すと、勝手に登場させてしまうからです
- 本文の長さは、**出来事ごとの目安の文字数**、**生成するトークン数の上限**、**短すぎたときの書き直し**の3つで、目安に近づけました
- 書いたシーンは、本文と記録（要約など）を `scenes/` に保存しました。途中で止めても**続きから書け**、`--from` で**指定したシーンから書き直せ**ます。すべて書き終えたら `manuscript.md` に書き出します
- `novelist write` で、生成中の本文を表示しながら、シーンを順に書けるようになりました

次の第16章では、書いたシーンをLLMに**批評**させ、その指摘をもとに**書き直す**、推敲のループを作ります。どうなったら推敲を終えるか、という終了条件も考えます。
