# 第26章 評価ルーブリックを作る — LLM-as-judge、判定のブレ対策

第16章では、LLMに原稿を批評させ、観点ごとに1〜10点を付けさせました。第25章では、その点数で条件を比べました。しかし、第25章の結果を見ると、点数の差はどれも標準偏差と同じくらいで、「差があるとは言えない」ものばかりでした。

これには理由があります。第16章の批評は、**推敲のための批評**です。シーンカードどおりに書けているか、視点がぶれていないかなど、「直すべきところ」を見つけるための観点になっています。一方、第25章で知りたかったのは、「どちらが**読んでおもしろい**か」でした。目的の違う物差しで測っていたのです。また、1〜10点の採点では、LLMはたいてい7〜8点を付けるので、差が出にくくなります。

この章では、読者として文章の質を測るための**評価ルーブリック**を作ります。ルーブリックとは、評価の観点と、観点ごとの水準（「この水準なら、こういう状態」という説明）を表にしたものです。そのうえで、LLMの採点のぶれを減らす工夫を組み込みます。

この章で作るものは次のとおりです。

| ファイル・コマンド | 内容 |
|---|---|
| `rubrics/novel.toml` | 娯楽小説の1シーンを、読者として評価するルーブリック |
| `src/novelist/judge.py` | ルーブリックで採点する・2つの文章を比べる |
| `prompts/rubric_judge/`・`prompts/rubric_pair/` | 採点と比較のプロンプト |
| `novelist judge` | 文章をルーブリックで採点する |
| `novelist compare` | 2つの文章を観点ごとに比べる |
| `novelist bench judge --rubric`・`bench compare` | 第25章の比較実験で、ルーブリックを使う |

## 26.1 LLMの採点は、なぜぶれるのか

### LLM-as-a-judge の弱点と対策

第16章で、LLMに評価させる方法（LLM-as-a-judge）の弱点を4つ挙げました。ここでは、比較実験に使うことを考えて、もう少し詳しく見ていきます。

| 弱点 | 起きること | この章の対策 |
|---|---|---|
| 基準があいまい | 「7点」の意味が、呼び出すたびに変わる | 水準ごとに、読んで判断できる説明を書く（アンカー） |
| 中心に寄る | どの文章にも、同じような点を付ける | 1〜10点をやめて1〜5の水準にし、水準の違いをはっきりさせる |
| 1回ごとにぶれる | 同じ文章でも、点数が変わる | 何回か採点して、中央値をとる。ぶれの大きさも表示する |
| 絶対評価は差が出にくい | 2つの文章に、どちらも「4」を付ける | 2つの文章を並べて、どちらが良いかを選ばせる（一対比較） |
| 位置の偏り | 先に（または後に）見せた文章を選びがち | 順番を入れ替えて2回比べ、2回とも同じ判定のときだけ勝ち負けにする |
| 長さの偏り | 長い文章を良いと判断しがち | 長さで判断しないように指示する。同じシーンどうしで比べる |
| 観点が影響し合う | 全体の印象で、すべての観点の点がそろう | 観点ごとに根拠を書かせ、別々に判断するように指示する |
| 自己選好 | 自分の書いた文章を高く評価する | 採点には、書いたモデルと別のモデルを使う（第25章） |
| 根拠のでっち上げ | 文章にない文を根拠にする | 根拠を引用させ、文章にあるかを確かめる（第16章） |

1つずつ説明します。

### 水準に説明を付ける（アンカー）

「描写: 1〜5点」とだけ書くと、「4点」が何を意味するのかは、LLMの解釈しだいです。解釈は呼び出すたびに少しずつ変わるので、点数もぶれます。

そこで、水準ごとに、**読んで判断できる説明**を付けます。

```text
描写: 場面が目に浮かぶか
- 1: 場所も人物の様子も、ほとんど思い浮かばない
- 2: 場所はわかるが、説明的で、具体的な物や感覚がない
- 3: 具体的な描写はあるが、ありきたりな言葉が多い
- 4: 五感に訴える具体的な描写があり、場面が思い浮かぶ
- 5: この場面ならではの細部があり、情景がくっきり思い浮かぶ
```

このような説明を、**アンカー**（目印）と呼びます。アンカーがあると、LLMは「この文章は、どの説明にいちばん近いか」を選べばよくなり、判断が安定します。

水準の数は5つにします。10段階では、隣り合う水準の違いを説明で書き分けられません。3段階では、差が見えにくくなります。

### 何回か採点して、中央値をとる

アンカーを付けても、採点は1回ごとにぶれます。そこで、同じ文章を、シードを変えて何回か（既定は3回）採点し、観点ごとに**中央値**をとります。平均ではなく中央値を使うのは、たまたま大きく外れた1回の採点に引っぱられないようにするためです。

何回か採点すると、**ぶれの大きさ**もわかります。3回の水準が「4 4 4」なら安定していますが、「2 4 5」なら、その観点の採点は信用できません。ぶれが大きい観点は、アンカーの説明があいまいな可能性があります。

### 並べて比べる（一対比較）

人間も、1つの文章に「100点満点で何点か」を付けるのは難しいものです。しかし、2つの文章を並べて「どちらが良いか」を選ぶのは、ずっと簡単です。LLMも同じで、2つの文章を並べて比べさせたほうが、差を見分けやすくなります。これを**一対比較**（pairwise comparison）と呼びます。

一対比較には、**位置の偏り**という弱点があります。LLMは、同じ2つの文章でも、先に見せたほう（モデルによっては後に見せたほう）を選びがちです。そこで、順番を入れ替えて2回比べます。

| 1回目（Aを先に） | 2回目（Bを先に） | 判定 |
|---|---|---|
| A | A | A の勝ち |
| B | B | B の勝ち |
| A | B | 引き分け（順番で判定が変わった） |
| 引き分け | 引き分け | 引き分け |

2回とも同じ判定だったときだけ、勝ち負けにします。順番で判定が変わったものは、位置の偏りで決まった可能性が高いので、引き分けにします。順番を入れ替えても同じ判定だった割合（**一致率**）は、採点するモデルがどれだけ信用できるかの目安になります。

## 26.2 ルーブリックを書く

ルーブリックは、プロジェクトの `rubrics/` に、1つのルーブリックを1つのTOMLファイルとして置きます。

**`rubrics/novel.toml`**（新規）

```toml
# 娯楽小説の1シーンを、読者として評価するルーブリック（第26章）
# 水準（levels）は、1から5の順に書く。どの水準にも、読んで判断できる具体的な説明を書く
description = "娯楽小説の1シーンを、読者として評価する"

[[criteria]]
key = "hook"
name = "引き込み"
question = "読者は、この先を読みたくなるか"
weight = 1.5
levels = [
  "途中で読むのをやめたくなる。何が起きているのか、なぜ読むのかがわからない",
  "最後まで読めるが、続きへの関心はわかない",
  "続きが少し気になる。ただし、疑問や緊張は弱く、ありきたり",
  "はっきりした疑問や緊張があり、続きを読みたくなる",
  "場面の終わりで強く引かれ、すぐに続きを読みたくなる",
]

[[criteria]]
key = "imagery"
name = "描写"
question = "場面が目に浮かぶか"
levels = [
  "場所も人物の様子も、ほとんど思い浮かばない",
  "場所はわかるが、説明的で、具体的な物や感覚がない",
  "具体的な描写はあるが、ありきたりな言葉が多い",
  "五感に訴える具体的な描写があり、場面が思い浮かぶ",
  "この場面ならではの細部があり、情景がくっきり思い浮かぶ",
]

[[criteria]]
key = "character"
name = "人物"
question = "人物が、台詞と行動で生きているか"
levels = [
  "人物の区別がつかない。誰が話しているのかわからない",
  "人物の区別はつくが、筋を進めるための駒になっている",
  "人物に個性はあるが、感情を地の文で説明しすぎている",
  "台詞と行動から、人物の個性と感情が伝わる",
  "台詞のひとことや小さな仕草で、人物の内面まで伝わる",
]

[[criteria]]
key = "pacing"
name = "テンポ"
question = "説明と場面の配分がよく、間延びや駆け足がないか"
levels = [
  "説明や要約ばかりで、場面として読めない",
  "間延びしている部分と、駆け足の部分が目立つ",
  "おおむね読めるが、ところどころで流れが止まる",
  "場面の緩急があり、流れよく読める",
  "緩急が効いていて、一気に読める",
]

[[criteria]]
key = "prose"
name = "文章"
question = "読みやすく、単調でなく、紋切り型に頼っていないか"
levels = [
  "読みにくい。文の意味がとれない箇所がある",
  "読めるが、同じ言い回しや文末が続いて単調",
  "読みやすいが、紋切り型の表現（「胸が締め付けられる」など）が目立つ",
  "読みやすく、言葉の選び方に工夫がある",
  "文章そのものに味わいがあり、読むこと自体が楽しい",
]
```

- `key` は、LLMに書かせるJSONの項目名になります。英小文字と数字と `_` で書きます。
- `question` は、その観点で問うことを1文で書きます。
- `weight` は、総合点を計算するときの重みです。この例では、娯楽小説にとっていちばん大事な「引き込み」を1.5にしています。
- `levels` は、水準1から5の順に、5つの説明を書きます。

### よいアンカーの書き方

アンカーは、次の点に気をつけて書きます。

- **文章を読んで確かめられることを書く**：「優れた描写」のような言葉は、何が優れているのかがわかりません。「五感に訴える具体的な描写がある」のように、文章の中に探せることを書きます
- **隣の水準との違いを1つにする**：水準3と4の違いは「ありきたりな言葉が多い」か「五感に訴える具体的な描写がある」か、というように、1段上がるごとに何が変わるのかをはっきりさせます
- **水準3を「普通」にする**：多くの文章が水準3になるように書くと、良い文章と悪い文章の差が、水準2と4として現れます
- **観点どうしを重ねない**：「文章」の観点に「描写が具体的」を入れると、「描写」の観点と同じことを2回測ることになります

このルーブリックは、あくまで出発点です。「自分が読みたい小説」の基準は、人によって違います。第27章で自分の好みを記録し、第28章で、好みをルーブリックやプロンプトに反映していきます。

## 26.3 採点と比較のモジュール

**`src/novelist/judge.py`**（新規）

```python
"""評価ルーブリックで、文章を採点・比較する（第26章）。

rubrics/<名前>.toml に、評価の観点と、観点ごとの水準（1〜5）の説明を書く。
"""

import re
import statistics
import tomllib
from dataclasses import dataclass, field
from pathlib import Path
from typing import Literal

from pydantic import BaseModel, ConfigDict, Field, ValidationError, create_model, field_validator

from novelist.config import Config, SamplingConfig
from novelist.llm.client import LLMClient
from novelist.llm.structured import generate_structured, schema_text
from novelist.prompts import PromptLibrary

LEVELS = 5  # 水準の数（1〜5）
JUDGE_PROFILE = "precise"
JUDGE_MAX_TOKENS = 4096  # 観点ごとの根拠と理由を書くので、多めに確保する
Winner = Literal["A", "B", "tie"]


class JudgeError(Exception):
    """ルーブリックを読み込めないときの例外。"""


# ---- ルーブリック ----


class RubricCriterion(BaseModel):
    """評価の観点1つ。"""

    model_config = ConfigDict(extra="forbid")

    key: str = Field(pattern=r"^[a-z][a-z0-9_]*$")  # JSONで使う名前
    name: str  # 表示に使う名前
    question: str  # この観点で問うこと
    weight: float = Field(default=1.0, gt=0)  # 総合点を計算するときの重み
    levels: list[str] = Field(min_length=LEVELS, max_length=LEVELS)  # 水準1〜5の説明


class Rubric(BaseModel):
    """評価ルーブリック（rubrics/<名前>.toml）。"""

    model_config = ConfigDict(extra="forbid")

    name: str = ""  # ファイル名（拡張子を除く）。読み込むときに入れる
    description: str = ""
    criteria: list[RubricCriterion] = Field(min_length=1)

    @field_validator("criteria")
    @classmethod
    def _check_keys(cls, criteria: list[RubricCriterion]) -> list[RubricCriterion]:
        keys = [c.key for c in criteria]
        duplicates = sorted({k for k in keys if keys.count(k) > 1})
        if duplicates:
            raise ValueError(f"観点の key が重なっています: {', '.join(duplicates)}")
        return criteria


def list_rubrics(rubrics_dir: Path) -> list[str]:
    if not rubrics_dir.is_dir():
        return []
    return sorted(p.stem for p in rubrics_dir.glob("*.toml"))


def load_rubric(rubrics_dir: Path, name: str) -> Rubric:
    """rubrics/<name>.toml を読み込む。"""
    path = rubrics_dir / f"{name}.toml"
    if not path.is_file():
        names = ", ".join(list_rubrics(rubrics_dir)) or "(なし)"
        raise JudgeError(f"ルーブリック '{name}' が見つかりません（{path}）。あるもの: {names}")
    try:
        with path.open("rb") as f:
            return Rubric.model_validate(tomllib.load(f) | {"name": name})
    except (tomllib.TOMLDecodeError, ValidationError) as e:
        raise JudgeError(f"{path} を読み込めません: {e}") from e


# ---- LLMに書かせる形 ----


class CriterionJudgement(BaseModel):
    """1つの観点の判定。根拠 → 理由 → 水準の順に書かせる。"""

    evidence: str = Field(
        description="判断の根拠になる箇所。文章から一字一句そのまま、30字程度を引用する",
        max_length=80,
    )
    reason: str = Field(description="その水準だと判断した理由", max_length=150)
    level: int = Field(description="水準（1〜5の整数）", ge=1, le=LEVELS)


class PairChoice(BaseModel):
    """1つの観点での、2つの文章の比較。違い → 勝者の順に書かせる。"""

    reason: str = Field(description="この観点での、2つの文章の違い", max_length=150)
    winner: Winner = Field(description='良いほう。"A" か "B"。差がわずかなら "tie"')


def judgement_model(rubric: Rubric) -> type[BaseModel]:
    """ルーブリックの観点を項目に持つ、判定のモデルを作る。

    観点ごとに項目を作るので、JSONスキーマ（第10章）で、すべての観点を、決まった順に
    書かせられる。観点の書き忘れや、名前の書き間違いが起きない。
    """
    fields = {
        c.key: (CriterionJudgement, Field(description=f"{c.name}: {c.question}"))
        for c in rubric.criteria
    }
    return create_model("RubricJudgement", **fields)


def pair_model(rubric: Rubric) -> type[BaseModel]:
    """ルーブリックの観点を項目に持つ、比較のモデルを作る。"""
    fields = {
        c.key: (PairChoice, Field(description=f"{c.name}: {c.question}")) for c in rubric.criteria
    }
    return create_model("PairJudgement", **fields)


def _sampling(config: Config, seed: int) -> SamplingConfig:
    sampling = config.sampling_for(JUDGE_PROFILE)
    return sampling.model_copy(
        update={"seed": seed, "max_tokens": max(sampling.max_tokens, JUDGE_MAX_TOKENS)}
    )


def _compact(text: str) -> str:
    return re.sub(r"\s", "", text)


# ---- 採点 ----


@dataclass
class CriterionScore:
    """1つの観点の、何回かの採点の結果。"""

    key: str
    name: str
    weight: float
    levels: list[int] = field(default_factory=list)  # 採点ごとの水準
    evidences: list[str] = field(default_factory=list)
    reasons: list[str] = field(default_factory=list)
    unverified: int = 0  # 根拠の引用が、文章に見つからなかった回数

    @property
    def median(self) -> float:
        """水準の中央値。平均より、外れた1回の採点に引っぱられにくい。"""
        return statistics.median(self.levels)

    @property
    def spread(self) -> int:
        """いちばん高い水準と、いちばん低い水準の差（採点のぶれ）。"""
        return max(self.levels) - min(self.levels)


@dataclass
class RubricScore:
    """ルーブリックでの採点の結果。"""

    rubric: str
    criteria: list[CriterionScore]

    @property
    def score(self) -> float:
        """総合点（1〜5）。観点ごとの中央値の、重み付きの平均。"""
        total = sum(c.weight for c in self.criteria)
        return round(sum(c.median * c.weight for c in self.criteria) / total, 2)

    def medians(self) -> dict[str, float]:
        return {c.key: c.median for c in self.criteria}


def judge_text(
    client: LLMClient,
    prompts: PromptLibrary,
    config: Config,
    rubric: Rubric,
    text: str,
    context: str = "",
    repeat: int = 1,
    seed: int = 1,
) -> RubricScore:
    """文章を、ルーブリックで repeat 回採点する。回ごとにシードを変える。"""
    model = judgement_model(rubric)
    messages = prompts.render(
        "rubric_judge", rubric=rubric, text=text, context=context, schema=schema_text(model)
    )
    scores = [CriterionScore(c.key, c.name, c.weight) for c in rubric.criteria]
    compact = _compact(text)
    for i in range(repeat):
        result = generate_structured(client, messages, model, _sampling(config, seed + i))
        for score in scores:
            judgement: CriterionJudgement = getattr(result, score.key)
            score.levels.append(judgement.level)
            score.evidences.append(judgement.evidence)
            score.reasons.append(judgement.reason)
            if _compact(judgement.evidence) not in compact:
                score.unverified += 1
    return RubricScore(rubric.name, scores)


# ---- 比較 ----


def _swap(winner: Winner) -> Winner:
    return {"A": "B", "B": "A", "tie": "tie"}[winner]


@dataclass
class PairResult:
    """2つの文章の比較の結果。順番を入れ替えて2回比べる。"""

    rubric: Rubric
    forward: dict[str, Winner]  # A を先に見せたときの判定
    backward: dict[str, Winner]  # B を先に見せたときの判定（A・B に読み替えたもの）
    reasons: dict[str, str]  # A を先に見せたときの理由

    def winner(self, key: str) -> Winner:
        """観点ごとの判定。2回の判定が食い違えば、引き分けにする。"""
        first, second = self.forward[key], self.backward[key]
        return first if first == second else "tie"

    @property
    def consistency(self) -> float:
        """順番を入れ替えても、同じ判定だった観点の割合。"""
        same = sum(1 for c in self.rubric.criteria if self.forward[c.key] == self.backward[c.key])
        return same / len(self.rubric.criteria)

    @property
    def overall(self) -> Winner:
        """総合の判定。勝った観点の重みの合計が多いほう。"""
        balance = 0.0
        for c in self.rubric.criteria:
            winner = self.winner(c.key)
            balance += c.weight if winner == "A" else -c.weight if winner == "B" else 0.0
        return "A" if balance > 0 else "B" if balance < 0 else "tie"


def compare_texts(
    client: LLMClient,
    prompts: PromptLibrary,
    config: Config,
    rubric: Rubric,
    a: str,
    b: str,
    context: str = "",
    seed: int = 1,
) -> PairResult:
    """2つの文章を、観点ごとに比べる。

    LLMは、先に（または後に）見せた文章を良いと判断しがちである（位置の偏り）。
    そこで、順番を入れ替えてもう一度比べ、2回の判定が一致した観点だけを勝ち負けにする。
    """
    model = pair_model(rubric)

    def ask(first: str, second: str) -> BaseModel:
        messages = prompts.render(
            "rubric_pair",
            rubric=rubric,
            a=first,
            b=second,
            context=context,
            schema=schema_text(model),
        )
        return generate_structured(client, messages, model, _sampling(config, seed))

    forward = ask(a, b)
    backward = ask(b, a)
    keys = [c.key for c in rubric.criteria]
    return PairResult(
        rubric,
        forward={k: getattr(forward, k).winner for k in keys},
        backward={k: _swap(getattr(backward, k).winner) for k in keys},
        reasons={k: getattr(forward, k).reason for k in keys},
    )
```

### ルーブリックのモデル

`Rubric` と `RubricCriterion` で、ルーブリックのファイルを検証します。水準が5つでない、`key` が重なっている、といった間違いは、読み込んだ時点でエラーになります。

### 観点ごとに項目を持つモデルを作る

`judgement_model` は、Pydanticの `create_model` で、ルーブリックの観点を項目に持つモデルを、実行時に作ります。`novel.toml` なら、次のクラスを書いたのと同じことになります。

```python
class RubricJudgement(BaseModel):
    hook: CriterionJudgement = Field(description="引き込み: 読者は、この先を読みたくなるか")
    imagery: CriterionJudgement = Field(description="描写: 場面が目に浮かぶか")
    character: CriterionJudgement = Field(description="人物: 人物が、台詞と行動で生きているか")
    pacing: CriterionJudgement = Field(description="テンポ: …")
    prose: CriterionJudgement = Field(description="文章: …")
```

観点ごとに項目を作るのには、2つの理由があります。

- **観点を書き忘れない**：第10章のJSONスキーマによる制約で、すべての観点を、ルーブリックの順に書かせられます。観点のリストを書かせる形（`[{"criterion": "hook", ...}, ...]`）にすると、観点を1つ飛ばしたり、`key` を書き間違えたりすることがあります
- **観点ごとの問いが、スキーマに入る**：項目の `description` に、観点の問いが入ります

`CriterionJudgement` は、根拠（`evidence`）→ 理由（`reason`）→ 水準（`level`）の順に書かせます。第16章の批評で、指摘を先に、点数をあとに書かせたのと同じ考え方です。先に根拠と理由を書かせると、水準がそれに沿ったものになります。

### 採点する

`judge_text` は、同じ文章を `repeat` 回採点します。回ごとにシードを変えるので、採点のぶれが現れます。

- `CriterionScore` は、1つの観点の、回ごとの水準・根拠・理由を集めます。`median` が中央値、`spread` がいちばん高い水準といちばん低い水準の差です。
- 根拠の引用が文章に見つからなかった回数を、`unverified` に数えます。第16章の `verify_issues` と違って、採点の結果は捨てずに、数だけを表示します。根拠のでっち上げが多い観点は、アンカーを見直すか、採点するモデルを変えるきっかけになります。
- `RubricScore.score` は、観点ごとの中央値を、重みで平均した総合点（1〜5）です。第14章からの方針どおり、平均はプログラムで計算します。

### 比べる

`compare_texts` は、2つの文章を、Aを先に見せて1回、Bを先に見せて1回比べます。2回目の判定は、`_swap` で A と B を読み替えて、1回目と同じ向きにそろえます。

`PairResult` は、2回の判定から、観点ごとの判定（`winner`）、一致率（`consistency`）、総合の判定（`overall`）を計算します。総合の判定は、勝った観点の重みの合計が多いほうです。

## 26.8 採点するモデルを確かめる

ルーブリックとプロンプトを工夫しても、採点するモデルが力不足なら、判定は信用できません。採点に使うモデルを決めたら、次の3つを確かめてください。

**1. 同じ文章の採点が、どのくらいぶれるか**

同じ文章を、多めの回数（5回など）採点します。

```console
$ uv run novelist judge works/kiri-no-eki/scenes/01-01.md -n 5
```

多くの観点で、ぶれ（いちばん高い水準といちばん低い水準の差）が1段階以内なら、十分に安定しています。2段階以上ぶれる観点が多ければ、アンカーの説明を具体的にするか、採点するモデルを大きなものに変えてください。

**2. 順番を入れ替えても、同じ判定になるか**

`compare` と `bench compare` の一致率を見ます。一致率が7割を下回るなら、そのモデルの判定の多くは、文章の中身ではなく、見せた順番で決まっています。

**3. 自分の判定と、どのくらい合うか**

いちばん大事なのは、採点するモデルの判定が、**自分の判定**と合うかどうかです。いくつかの文章の組を、まず自分で読んで、どちらが良いかを決めておきます。そのあとで `compare` にかけ、自分の判定とどのくらい一致するかを数えます。

これを手作業でするのは大変なので、第27章で、自分の判定を記録する仕組みを作ります。記録がたまれば、採点するモデルと自分の判定の一致率を、自動で計算できるようになります。

## 26.10 うまくいかないときは

**どの文章も、すべての観点が3になる**

中心に寄る偏りです。アンカーの説明が抽象的で、どの水準にも当てはまるように読めている可能性があります。26.2節の「よいアンカーの書き方」に沿って、水準3と4、3と2の違いを、文章の中で確かめられることで書き直してください。それでも変わらない場合は、`compare` で一対比較を使ってください。

**「根拠の引用が文章に見つからない回」が多い**

採点するモデルが、文章を言い換えて引用しています。小さなモデルで起きやすい問題です。採点の結果は使えますが、根拠を確かめられないので、判定の理由を読んで納得できるかを確かめてください。気になる場合は、採点するモデルを大きなものに変えてください。

**`StructuredOutputError` になる**

観点ごとに根拠と理由を書かせるので、出力のJSONは長くなります。`JUDGE_MAX_TOKENS`（4096）で足りない場合は、第10章の `generate_structured` が `max_tokens` を増やしてやり直しますが、上限に達するとエラーになります。観点を減らすか、`judge.py` の `JUDGE_MAX_TOKENS` を増やしてください。思考モデルを採点に使う場合は、`precise` プロファイルで思考を止めてください（第15章）。

**時間がかかる**

ルーブリックでの採点は、1件につき `repeat` 回（既定は3回）、一対比較は1組につき2回、LLMを呼び出します。第25章の比較実験を24件採点すると、72回の呼び出しになります。まず `--repeat 1` で全体の傾向を見て、差を確かめたい条件だけを、回数を増やして採点し直してください。

## 26.11 まとめ

- 読者として文章の質を測るための**評価ルーブリック**を、観点・問い・重み・水準ごとの説明（**アンカー**）として書きました
- LLMの採点の弱点に、次の対策を組み込みました
  - 水準を1〜5にし、アンカーで意味をはっきりさせる
  - 根拠 → 理由 → 水準の順に書かせる
  - 何回か採点して**中央値**をとり、**ぶれ**も表示する
  - 2つの文章を並べて比べる**一対比較**を使い、**順番を入れ替えて**2回比べて、位置の偏りを打ち消す
- Pydanticの `create_model` で、ルーブリックの観点を項目に持つモデルを作り、すべての観点を決まった順に書かせました
- 第25章の比較実験で、ルーブリックでの採点と、条件どうしの一対比較ができるようにしました
- 採点するモデルは、ぶれ・一致率・自分の判定との一致の3つで確かめます

LLMの採点をどれだけ工夫しても、最後に「良い」を決めるのは、読者である自分です。第27章では、2つの文章を読み比べて、自分の好みを記録するコマンドを作ります。記録した好みは、採点するモデルの確かめにも、第28章での生成への反映にも使います。
