## 33.2 原稿を書き出す

### export の仕様

第15章から、執筆のグラフの最後（`export` ノード）で、すべてのシーンを書き終えていれば `manuscript.md` を書き出してきました。ただし、次のことはできませんでした。

- シーンを手で直したあとに、書き出し直す
- 書いている途中の長編を、書き終えた分だけ読む
- 見出しの記号（`#`）のない、プレーンテキストにする
- 作品のディレクトリの外に書き出す

`novelist export` で、これらをできるようにします。

| オプション | 内容 |
|---|---|
| `-o`・`--output` | 書き出すファイル。省略すると、作品のディレクトリの `manuscript.md`（`-f txt` なら `manuscript.txt`） |
| `-f`・`--format` | `md`（Markdown）か `txt`（プレーンテキスト） |
| `--partial` | 書いていないシーンを飛ばして、書き終えたシーンだけを書き出す |

## 33.3 コード全体を見直す

### 繰り返し使った設計の型

32章をかけて作ったコードを見直すと、同じ考え方を何度も使ってきたことがわかります。

| 型 | 中身 | 主に使った章 |
|---|---|---|
| LLMは判断、プログラムは計算と照合 | 合計の文字数・章の配分・seed はプログラムで決める。LLMの指摘・食い違い・伏線は、本文からの引用が実際にあるかを確かめてから使う | 14・16・21・26・30・31・32 |
| 構造化出力と、検証して書き直させる | JSONスキーマで形を縛り、Pydantic の検証（設定資料にある名前か、章の番号が範囲にあるかなど）に通らなければ、エラーを伝えて書き直させる | 10・13・14・30・31 |
| 成果物はファイルに、進み具合はチェックポイントに | 人間が読める JSON・Markdown に保存し、手で直せるようにする。グラフの途中の状態は SQLite に保存して、止まったところから再開する | 12・15・17・32 |
| 設定ファイルで決めて、記録する | サンプリングはプロファイル、機能のオン・オフは `novelist.toml`。実行ごとに、使った設定を記録する | 6・9・20〜24・32 |
| 偽のサーバーでテストする | `ChatRecorder` が用意した応答を順に返し、受け取ったリクエストを記録する。GPU なしで、プロンプトの中身まで確かめる | 6・12〜32 |

## 33.5 次の一歩

ここからは、`novelist` をさらに広げるためのアイデアです。どれも、ここまでのコードのどこを変えればよいかを書いておきます。

### 役割ごとにモデルを分ける

今は、企画・執筆・要約・判定のすべてを、`[server]` の1つのモデルで行っています。役割ごとに得意なモデルは違います。

- 本文は、表現の豊かな大きいモデル
- 要約や状態の更新は、速くて正確な小さいモデル
- 判定は、執筆とは別のモデル（自己選好を避ける）

第25章の比較実験では、条件（`Variant`）ごとにサーバーのURLを変えられるようにしました。同じように、`novelist.toml` に `[servers.judge]` のような役割ごとのサーバーを書けるようにし、`WriteContext` に役割ごとの `LLMClient` を持たせます。ノードの中では、`ctx.client` の代わりに `ctx.clients["summary"]` のように使い分けます。

### 並列に生成する

llama-server は、`-np`（`--parallel`）で、複数のリクエストを同時に処理できます。1つずつより、全体の速さ（1秒あたりのトークン数の合計）が上がります。

- 第27章の読み比べで使う2つの候補を、同時に書かせる
- 第25章の比較実験で、条件・シーン・シードの組み合わせを同時に走らせる
- 長編で、章の要約と、次の章のシーンカード作りを同時に行う

`httpx` には非同期のクライアント（`httpx.AsyncClient`）があり、LangGraph も非同期のノードを扱えます。ただし、第32章で見たとおり、同時に処理すると、seed をそろえても出力が変わることがあります。再現性と速さのどちらを取るかを、用途ごとに決めてください。

### 文章の検査を増やす

第24章の規則の検査は、正規表現とプログラムで行っています。LLMを使わないので、速く、何度でも実行できます。次のような検査を足せます。

- **表記ゆれ**：「出来る／できる」「子供／子ども」のような、作品の中での表記の揺れ。作品ごとの表記の辞書を `styles/<名前>/style.toml` に持たせ、`normalize` で直すか、`lint` で警告する
- **話者の口調**：登場人物ごとの一人称や語尾を設定資料（`Character`）に持たせ、台詞の「」の中が合っているかを確かめる。台詞が誰のものかの判断は、LLMに任せる
- **固有名詞の誤字**：設定資料の人物名・地名に近いが一致しない文字列（「沢渡透」に対する「沢度透」など）を、編集距離で探す

### 本として仕上げる

`export` の Markdown は、[Pandoc](https://pandoc.org/) で、ほかの形式に変換できます。

```console
$ pandoc works/kiri-no-eki/manuscript.md -o kiri.epub --metadata title="霧の終着駅"
```

縦書きの電子書籍にするには、EPUB の CSS で `writing-mode: vertical-rl` を指定します。ルビ（「硬券《こうけん》」のような記法）や、傍点、縦中横（縦書きの中の半角数字）を扱うなら、`export` に変換の処理を足します。

### ほかのツールから使う

`novelist` の工程は、どれも「作品のIDを受け取り、ファイルを読み書きする」関数として、CLI から呼んでいます。この関数を、MCP（Model Context Protocol）のサーバーとして公開すれば、Claude のようなほかのAIエージェントから、「この作品の第3章を書いて」「伏線の一覧を見せて」と頼めるようになります。人間とエージェントが同じ作品のディレクトリを見ながら、分担して書くこともできます。

### 評価を回帰テストにする

プロンプトを直したら、出来がよくなったのか悪くなったのかを、毎回確かめたくなります。第25章の比較実験と、第26章のルーブリックの採点を組み合わせると、「直す前のプロンプト」と「直したあとのプロンプト」を、同じプロットとシードで比べられます。第32章で記録しているプロンプトのハッシュを、比較実験の結果にも残しておけば、どの版のプロンプトの結果かを取り違えません。

### 好みの学習を回し続ける

第27章〜第29章では、好みを集める・ルールにする・LoRAに焼き込む、を1回ずつ行いました。これを定期的に回すと、使うほど自分の好みに近づくエージェントになります。

```text
書く（write・batch） → 読み比べる（rate） → ルールにする（prefs rules）
   ↑                                                  │
   └──────── LoRAを学習し直す（prefs export → train） ←──┘
```

学習し直したLoRAを、前のLoRAと第25章の比較実験で比べ、よくなったときだけ入れ替えるようにすると、好みから外れていく失敗を防げます。

## 33.7 おわりに

ローカルLLMで小説を書くエージェントを、33章かけて作ってきました。振り返ると、モデルの性能そのものより、モデルの周りに置く仕組みのほうが、出来を大きく左右していたことに気づくはずです。

- 一度に書かせず、企画・設定・プロット・シーンに分けて、それぞれを確かめながら進める
- 書かせたものを、別の観点（批評・一貫性・規則・伏線）で確かめ、直させる
- LLMが苦手な計算と照合は、プログラムが引き受ける
- 作者がいつでも途中のファイルを読み、直し、続きから再開できるようにする
- 何を、どの条件で書かせたかを記録し、比べられるようにする

これらは、小説に限らず、LLMを使って長く複雑な仕事をさせるときに、どこでも通用する考え方です。

ローカルLLMは、これからも速く、賢くなっていきます。そのときも、`novelist.toml` のモデルを差し替え、第25章の比較実験で確かめれば、この本で作った仕組みはそのまま使えます。新しいモデルで、あなたの好みに合った物語を書かせてみてください。
