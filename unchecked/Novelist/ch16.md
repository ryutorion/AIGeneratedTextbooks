# 第16章 推敲ループ

第15章で、シーンカードに沿ってシーンごとに本文を書けるようになりました。構成と長さは安定しましたが、文章は1回書いただけのものです。同じ描写の繰り返し、視点のぶれ、説明的すぎる台詞など、読めば気になる点が残っているはずです。

人間の書き手は、書いたものを読み返して直します。編集者に読んでもらい、指摘を受けて直すこともあります。この章では、LLMに**編集者**の役を与えて原稿を**批評**させ、その指摘をもとに**作家**の役のLLMに**推敲**させます。そして、それを繰り返す**推敲のループ**を、第15章の執筆のグラフに組み込みます。

ループを作るときに、いちばん大事なのは**いつ終えるか**です。LLMの編集者は、いつまでも何かしらの指摘を出しますし、推敲するたびに良くなるとも限りません。この章では、終了の条件を4つ決め、推敲した版の中から最も良いものを選ぶようにします。

この章で作るものは次のとおりです。

| ファイル・コマンド | 内容 |
|---|---|
| `src/novelist/schemas/review.py` | 批評（指摘と点数）のモデル |
| `src/novelist/review.py` | 批評を呼び出し、指摘を確かめ、推敲を続けるかを決める |
| `prompts/_parts/scene_brief.md` | シーンの情報を書き出す、プロンプトの共通部品 |

| `novelist write -r` | 推敲の回数の上限を指定する |
| `novelist review` | 書き終えたシーンを批評して表示するコマンド |

## 16.1 推敲のループを設計する

### 批評と推敲を分ける

LLMに「書いた原稿を見直して、良くなるように直して」と1回で頼むこともできます。しかし、この方法はうまくいきません。

- **直す箇所があいまいになる**：何が問題かを言葉にしないまま直すので、表面的な言い換えに終わりがちです。
- **自分の文章に甘い**：LLMは、渡された文章をもっともらしいものとして受け取り、大きく変えようとしません。
- **良くなったかがわからない**：直した結果を測るものがないので、続けるべきか、やめるべきかを決められません。

そこで、仕事を2つに分けます。

| 役 | すること | プロファイル |
|---|---|---|
| 編集者（批評） | 原稿を読み、問題のある箇所を**引用して**指摘し、観点ごとに**点数**を付ける | `precise` |
| 作家（推敲） | 指摘された箇所を直した原稿を、全文書き直す | `creative` |

同じモデルでも、プロンプトで役割と観点を変えれば、書いたときとは違う目で原稿を読ませることができます。批評には、ぶれの少ない `precise` プロファイルを使います。点数が呼び出しのたびに大きく変わると、ループを続けるかどうかの判断が不安定になるからです。

### ループの流れ

1つのシーンの流れは、次のようになります。第15章の長さの確認のあとに、推敲のループが入ります。

```text
初稿を書く（第15章）
   ↓
長さを確かめる（第15章）
   ↓
┌→ 批評する ── 合格、またはやめる ──→ いちばん点数の高い版を採用 → 要約・保存（第15章）
│    │
│    └ 推敲する
│       ↓
└── 推敲した版
```

### 終了の条件

推敲のループは、次のどれかで終えます。

| 条件 | 判定 | 理由 |
|---|---|---|
| 点数が合格点（8.0点）以上 | 合格 | 十分に良い |
| 指摘が1件もない（引用を確かめたあと） | やめる | 直す手がかりがない |
| 推敲しても、それまでの最高点より上がらない | やめる | これ以上続けても良くならない見込みが高い |
| 推敲の回数が上限（既定は2回）に達した | やめる | 時間とトークンを使いすぎない |

3つめの条件が大事です。LLMの推敲は、いつも原稿を良くするとは限りません。指摘された箇所を直す代わりに、指摘されていなかった良い部分を崩したり、新しい問題を持ち込んだりすることがあります。推敲するたびに良くなったり悪くなったりを繰り返すこともあります。

そこで、推敲した版をすべて批評し、**いちばん点数の高い版**を覚えておきます。ループを終えたら、最後の版ではなく、いちばん点数の高い版を採用します。推敲したら悪くなった場合は、初稿に戻ることになります。

### LLMの批評を、どこまで信じるか

LLMに文章を評価させる方法は、**LLM-as-a-judge**（審査員としてのLLM）と呼ばれます。便利な方法ですが、次のような弱点が知られています。

- **甘い**：どんな文章にも、7〜8点くらいを付けがちです。
- **自分の文章をひいきする**：自分（同じモデル）が書いた文章を、高く評価しがちです。
- **ぶれる**：同じ文章でも、呼び出すたびに点数が少し変わります。
- **ありもしない問題を指摘する**：原稿にない文を「引用」して、それを問題にすることがあります。

この章では、次の工夫で、これらの弱点をやわらげます。

1. **採点の基準を示す**：「9〜10: 直すところがない」「7〜8: 小さな問題がある」のように、点数の意味を具体的に書きます。「甘く採点しない」「指摘した問題があれば、その観点は8点以下にする」とも指示します。
2. **指摘を先に、点数をあとに書かせる**：LLMは前から順に生成します（第3章）。先に具体的な問題を書き出させると、そのあとの点数は、書き出した問題に沿ったものになります。
3. **平均はプログラムで計算する**：観点ごとの点数だけをLLMに付けさせ、全体の点数（平均）はプログラムで計算します。第14章で見たとおり、LLMは計算が苦手です。
4. **引用を確かめる**：指摘には、問題の箇所を原稿からそのまま引用させます。引用が原稿に見つからない指摘は、プログラムで取り除きます。

それでも、点数は目安にすぎません。点数のぶれを測り、評価を安定させる方法は、第VI部（第26章）で扱います。

## 16.2 批評のモデル

**`src/novelist/schemas/review.py`**（新規）

```python
"""シーンの批評（第16章）。"""

from typing import Literal

from pydantic import BaseModel, Field

# 批評の観点。キーはJSONで使う名前、値は表示に使う名前
CRITERIA = {
    "card": "シーンカード",
    "continuity": "つながり",
    "pov": "視点",
    "prose": "文章",
    "dialogue": "台詞",
}

Criterion = Literal["card", "continuity", "pov", "prose", "dialogue"]


class Issue(BaseModel):
    """批評の指摘1件。"""

    criterion: Criterion = Field(description="どの観点の問題か")
    label: str = Field(description="指摘の短い名前（例: 視点のぶれ、描写の重複）", max_length=15)
    quote: str = Field(
        description="問題のある箇所。原稿から一字一句そのまま、30字程度を引用する", max_length=80
    )
    problem: str = Field(description="何が問題か", max_length=100)
    suggestion: str = Field(description="どう直せばよいか。具体的に", max_length=100)


class Scores(BaseModel):
    """観点ごとの点数（1〜10）。"""

    card: int = Field(
        description="目的・葛藤・結果と出来事が、順にすべて書かれているか。"
        "次のシーンの出来事を書いていないか",
        ge=1,
        le=10,
    )
    continuity: int = Field(
        description="直前の文章から自然に続いているか。これまでのあらすじや設定と矛盾がないか",
        ge=1,
        le=10,
    )
    pov: int = Field(
        description="視点人物が見聞きしたことだけを書いているか。ほかの人物の心の中を書いていないか",
        ge=1,
        le=10,
    )
    prose: int = Field(
        description="同じ言い回しや描写の繰り返し、単調な文末、説明しすぎの文がないか",
        ge=1,
        le=10,
    )
    dialogue: int = Field(
        description="台詞が人物の口調に合っているか。台詞で状況を説明しすぎていないか",
        ge=1,
        le=10,
    )


class Critique(BaseModel):
    """シーンの批評。

    指摘（issues）を先に、点数（scores）をあとに書かせる。LLMは前から順に生成するので、
    先に具体的な問題を書き出させてから点数を付けさせたほうが、点数が指摘に沿ったものになる。
    """

    issues: list[Issue] = Field(
        description="重要な順に、最大5件。問題がなければ空にする", max_length=5
    )
    scores: Scores

    def score(self) -> float:
        """観点ごとの点数の平均（小数点以下1桁）。合計や平均はLLMに計算させない。"""
        values = list(self.scores.model_dump().values())
        return round(sum(values) / len(values), 1)
```

**`CRITERIA` と `Criterion`**

批評の観点は5つです。第15章の執筆のプロンプトで指示した方針（視点、描写、台詞など）と、シーンカード、前のシーンとのつながりに対応しています。JSONではローマ字の名前（`card` など）を使い、表示のときに日本語の名前に変えます。

`Criterion` は、第10章の `Literal` で、指摘がどの観点のものかを5つのどれかに制限しています。

**`Issue`**

指摘1件です。`label` は「視点のぶれ」のような短い名前で、ログに一覧として出します。`quote` は、問題の箇所の引用です。`description` で「一字一句そのまま」と念を押しています。

**`Scores`**

観点ごとの点数です。1〜10の整数にしています（`ge=1, le=10`）。各フィールドの `description` に観点の説明を書いておくと、JSONスキーマを通してLLMにも伝わります（第10章）。

**`Critique`**

批評の全体です。フィールドの**順番**に意味があります。JSONスキーマで出力を制約すると、LLMはスキーマのフィールドの順に出力します。`issues` を先に置いたので、LLMは先に指摘を書き、そのあとで点数を付けます（16.1節の工夫の2）。

`score()` は、観点ごとの点数の平均を、小数点以下1桁に丸めて返します。`self.scores.model_dump()` は、`{"card": 8, "continuity": 7, ...}` のような辞書を返すので、その値の平均をとります。

## 16.3 批評を確かめ、続けるかを決める

**`src/novelist/review.py`**（新規）

```python
"""シーンを批評し、推敲を続けるかを決める（第16章）。"""

import re
from typing import Literal

from novelist.config import Config
from novelist.llm.client import LLMClient
from novelist.llm.structured import generate_structured, schema_text
from novelist.prompts import PromptLibrary
from novelist.schemas.bible import WorldSheet
from novelist.schemas.review import Critique, Issue
from novelist.schemas.work import WorkMeta
from novelist.writing import SceneBrief

CRITIC_PROFILE = "precise"  # 批評は、ぶれの少なさを優先する
PASS_SCORE = 8.0  # この点数以上なら合格
DEFAULT_MAX_REVISIONS = 2  # 1つのシーンを推敲する回数の上限の既定値

Verdict = Literal["pass", "revise", "stop"]


def critique_scene_text(
    client: LLMClient,
    prompts: PromptLibrary,
    config: Config,
    meta: WorkMeta,
    world: WorldSheet,
    brief: SceneBrief,
    text: str,
) -> Critique:
    """シーンの原稿を、シーンカードと設定に照らして批評させる。"""
    messages = prompts.render(
        "scene_critique",
        meta=meta,
        world=world,
        brief=brief,
        text=text,
        schema=schema_text(Critique),
    )
    sampling = config.sampling_for(CRITIC_PROFILE)
    sampling = sampling.model_copy(update={"max_tokens": max(sampling.max_tokens, 4096)})
    return generate_structured(client, messages, Critique, sampling)


def _compact(text: str) -> str:
    """空白と改行を取り除く（引用の照合用）。"""
    return re.sub(r"\s", "", text)


def verify_issues(issues: list[Issue], text: str) -> tuple[list[Issue], list[Issue]]:
    """指摘を、引用が原稿に見つかるもの（採用）と、見つからないもの（除外）に分ける。

    LLMは、原稿にない文を「引用」してしまうことがある。存在しない箇所への指摘は、
    直しようがないうえに、推敲のときに原稿にない問題を作り出す原因になる。
    """
    compact = _compact(text)
    kept = [issue for issue in issues if _compact(issue.quote) in compact]
    dropped = [issue for issue in issues if _compact(issue.quote) not in compact]
    return kept, dropped


def decide(
    score: float,
    n_issues: int,
    best_score: float | None,
    revisions: int,
    max_revisions: int,
) -> tuple[Verdict, str]:
    """批評の結果から、推敲を続けるかを決める。

    - score: 今の版の点数
    - n_issues: 今の版への指摘の数（引用を確かめたあと）
    - best_score: これまでの版の最高点（今の版を含まない。初稿なら None）
    - revisions: これまでに推敲した回数
    - max_revisions: 推敲の回数の上限

    戻り値は、判定（"pass" 合格、"revise" 推敲する、"stop" 推敲をやめる）と、その理由。
    """
    if score >= PASS_SCORE:
        return "pass", "合格"
    if n_issues == 0:
        return "stop", "直す箇所が示されなかったので、推敲を終えます"
    if best_score is not None and score <= best_score:
        return "stop", "推敲しても点数が上がらなかったので、推敲を終えます"
    if revisions >= max_revisions:
        return "stop", "推敲の回数の上限に達しました"
    return "revise", "推敲します"
```

**`critique_scene_text`**

批評のプロンプトを展開し、第10章の `generate_structured` で `Critique` を受け取ります。指摘には引用や説明が含まれ、出力が長くなるので、`max_tokens` は少なくとも4096にします。この関数は、グラフのノードと、16.7節の `review` コマンドの両方から使うので、ノードとは別のモジュールに置いています。

**`verify_issues`**

指摘を、引用が原稿に見つかるものと、見つからないものに分けます。LLMは、引用するときに改行を省いたり空白を入れたりすることがあるので、空白と改行を取り除いてから照合します。

引用が見つからない指摘を取り除くのは、存在しない箇所への指摘を推敲の指示に入れると、作家役のLLMが混乱するからです。「この文を直して」と言われても、その文は原稿にありません。LLMは、それらしい箇所を探して、問題のない部分まで書き換えてしまいます。

**`decide`**

16.1節の終了の条件を、そのまま関数にしたものです。判定（`"pass"`、`"revise"`、`"stop"`）と、ログに出す理由を返します。グラフのノードの中に書かずに独立した関数にしておくと、LLMを呼ばずに、条件の組み合わせをテストで確かめられます。

条件を確かめる順番にも意味があります。たとえば、合格点に達していれば、推敲の回数が上限に達していても「合格」とします。点数が上がらなかった場合は、上限に達しているかどうかに関係なく「改善しなかった」と伝えるほうが、ログを読んだときに状況がわかりやすくなります。

### 批評のプロンプト

**`prompts/scene_critique/system.md`**（新規）

```markdown
{# シーンの原稿を批評する（第16章） #}
あなたは娯楽小説の編集者です。
作家が書いたシーンの原稿を読み、シーンカードと設定に照らして、推敲のための批評をします。

# 批評の観点
- シーンカード: 目的・葛藤・結果と出来事が、順にすべて書かれているか。次のシーンの出来事を先に書いていないか
- つながり: 直前の文章から自然に続いているか。これまでのあらすじや設定資料と矛盾していないか
- 視点: 視点人物が見聞きしたことだけを書いているか。ほかの人物の心の中を書いていないか
- 文章: 同じ言い回しや描写の繰り返し、単調な文末、説明しすぎの文がないか
- 台詞: 台詞が人物の口調に合っているか。台詞で状況を説明しすぎていないか

# 指摘の書き方
- 直すべき問題を、重要な順に最大5件挙げる。良い点は書かなくてよい。
- 問題のある箇所は、原稿から一字一句そのまま引用する。言い換えたり、要約したりしない。
- 直し方は、作家がそのまま手を動かせるように具体的に書く。
- 直すべき問題がなければ、指摘は空にする。

# 点数の付け方
観点ごとに、1〜10の整数で採点する。
- 9〜10: 直すところがない
- 7〜8: 小さな問題がある
- 4〜6: 読者が気づく問題がある
- 1〜3: 書き直しが必要
```

```python
WRITE_PROFILE = "creative"  # 本文は、表現の豊かさを優先する
SUMMARY_PROFILE = "precise"  # 要約は、正確さを優先する
WRITE_TOKENS_RATIO = 2.0  # 目安の文字数の何倍まで、トークンを生成してよいか
MIN_RATIO = 0.7  # 目安の文字数の7割に届かなければ書き直す

def _scene_keys(state: WriteState) -> list[str]:
    """プロットのすべてのシーンを、順に並べたもの。"""
    return [scene_key(i, j) for i, j, _ in state["plot"].scenes()]


def current_scene(state: WriteState) -> Scene:
    """今書いているシーンのシーンカード。"""
    i, j = parse_scene_key(state["current"])
    return state["plot"].chapters[i - 1].scenes[j - 1]


def prepare(state: WriteState, runtime: Runtime[WriteContext]) -> dict:
    """設定資料・プロット・書き終えたシーンの記録を読み込み、これから書くシーンを決める。"""
    work = runtime.context.work
    world, characters = work.load_bible()
    plot = work.load_plot()
    records = work.load_scene_records(plot)
    keys = [scene_key(i, j) for i, j, _ in plot.scenes()]

    start = state.get("start")
    if start is None:
        # まだ書いていない最初のシーンから
        start_index = next((n for n, key in enumerate(keys) if key not in records), len(keys))
    else:
        if start not in keys:
            raise WorkError(f"シーン {start} はプロットにありません（{keys[0]}〜{keys[-1]}）")
        start_index = keys.index(start)
        missing = [key for key in keys[:start_index] if key not in records]
        if missing:
            raise WorkError(f"先に書いておく必要があるシーンがあります: {', '.join(missing)}")
    queue = keys[start_index:]
    if state.get("limit"):
        queue = queue[: state["limit"]]

    if queue:
        message = f"書くシーン: {len(queue)}件（{queue[0]}〜{queue[-1]}）"
    else:
        message = "すべてのシーンを書き終えています"
    return {
        "world": world,
        "characters": characters,
        "plot": plot,
        "records": records,
        "queue": queue,
        "total": len(queue),
        "log": [message],

def _reasoning_message(reasoning_chars: int, max_tokens: int) -> str:
    """思考だけで本文が書かれなかったときの、エラーメッセージを作る。"""
    return (
        f"本文が書かれないまま、思考（reasoning）で max_tokens（{max_tokens}）に達しました"
        f"（思考: {reasoning_chars:,}文字）。"
        f'novelist.toml の [profiles.{WRITE_PROFILE}] に reasoning_effort = "none" を'
        "指定して、思考を止めてください。"
    )


@dataclass
class Draft:
    """生成した本文（第16章で、write_scene から取り出した）。"""

    text: str
    chars: int
    finish_reason: str | None
    reasoning_chars: int  # 思考に使われた文字数

    def describe(self) -> str:
        """ログに出す説明。"""
        message = f"{self.chars:,}字（終了理由: {self.finish_reason}）"
        if self.reasoning_chars:
            message += f"（思考: {self.reasoning_chars:,}文字）"
        return message


def stream_scene(ctx: WriteContext, messages: list[Message], max_tokens: int) -> Draft:
    """本文を生成して、グラフの外（CLI）へ流しながら受け取り、整える。

    本文を書くノードと推敲するノードの両方で使う（第16章）。
    """
    sampling = ctx.config.sampling_for(WRITE_PROFILE)
    sampling = sampling.model_copy(update={"max_tokens": max_tokens})

    # 生成中の文字列を、グラフの外（CLI）へ流す
    writer = get_stream_writer()
    result = ctx.client.stream_chat(messages, sampling, lambda text: writer({"text": text}))

    if not result.text.strip() and result.reasoning:
        # 思考（reasoning）だけで max_tokens を使い切り、本文が1文字も書かれなかった
        raise LLMError(_reasoning_message(len(result.reasoning), max_tokens))

    text = result.text
    if result.finish_reason == "length":
        # max_tokens で途中で切れた。最後の文の終わりまでにする
        text = trim_incomplete(text)
    text = clean_scene_text(text)
    return Draft(text, text_stats(text).chars, result.finish_reason, len(result.reasoning))


def write_scene(state: WriteState, runtime: Runtime[WriteContext]) -> dict:
    """シーンカードと、これまでの流れをもとに、シーンの本文を書く。"""
    ctx = runtime.context
    brief = scene_brief(state, runtime)
    messages = ctx.prompts.render(
        "scene",
        meta=state["meta"],
        world=state["world"],
        brief=brief,
        feedback=state.get("feedback"),
    )
    draft = stream_scene(ctx, messages, int(brief.scene.chars * WRITE_TOKENS_RATIO))
    attempts = state["attempts"] + 1
    return {
        "text": draft.text,
        "chars": draft.chars,
        "attempts": attempts,
        "log": [f"{attempts}回目: {draft.describe()}"],
    }


def check_scene(state: WriteState) -> dict:
    """長さを確かめ、足りなければ書き直すための指摘を作る。"""
    target = current_scene(state).chars
    chars = state["chars"]
    ratio = chars / target
    if ratio >= MIN_RATIO:
        return {"feedback": None, "log": [f"長さ: 目安の{ratio:.0%}（合格）"]}
    if state["attempts"] >= MAX_ATTEMPTS:
        return {
            "feedback": None,
            "log": [f"長さ: 目安の{ratio:.0%}（不足。書き直しの上限なので進みます）"],
        }
    feedback = (
        f"前回の原稿は{chars}字で、目安の{target}字に足りませんでした。"
        "出来事を省いたり、次のシーンの出来事を書いたりせずに、"
        "それぞれの出来事の描写と会話を増やしてください。"
    )
    return {"feedback": feedback, "log": [f"長さ: 目安の{ratio:.0%}（不足。書き直します）"]}


def route_after_check(

    if state.get("feedback"):
        return "write_scene"
    if state.get("max_revisions", 0) > 0:
        return "critique_scene"
    return "summarize_scene"

    ctx = runtime.context
    brief = scene_brief(state, runtime)
    messages = ctx.prompts.render(

    return {"summary": result.summary, "log": [f"要約: {result.summary}"]}

    work = runtime.context.work
    i, j = parse_scene_key(state["current"])
    scene = current_scene(state)
    record = SceneRecord(
        chapter=i,
        scene=j,
        title=scene.title,
        target_chars=scene.chars,
        chars=state["chars"],

        summary=state["summary"],
        written_at=datetime.now().astimezone(),
        revisions=state.get("revisions", 0),

    return {
        "records": {**state["records"], record.key: record},
```

- **名前の変更**：`_current_scene` と `_brief` を、`current_scene` と `scene_brief` にしました。Pythonでは、名前の先頭の `_` は「このモジュールの中だけで使う」という目印です。推敲のノード（`revise.py`）からも使うようになったので、`_` を外しています。`scene_brief` は、直前のシーンの本文を `previous_scene_text` で読み込むようにしました。
- **`Draft` と `stream_scene`**：`write_scene` から、本文を生成して整える部分を取り出しました。第15章の最後に加えた、思考だけで本文が空になったときのエラーも、ここに含まれます。`Draft.describe()` は、ログに出す「3,500字（終了理由: stop）」のような説明を作ります。
- **`start_scene`**：推敲の状態（`revisions`、`best_text` など）も、シーンごとにリセットします。リセットしないと、前のシーンの「いちばん良い版」が残ってしまいます。
- **`route_after_check`**：長さが足りていれば、`max_revisions` が1以上なら批評へ、0なら第15章と同じく要約へ進みます。
- **`save_scene`**：記録に、推敲した回数と点数を加えます。

### 批評と推敲のノード

**`src/novelist/graph/nodes/revise.py`**（新規）

```python
"""シーンを批評し、推敲するノード（第16章）。"""

from typing import Literal

from langgraph.runtime import Runtime

from novelist.graph.nodes.write import (
    MIN_RATIO,
    WRITE_TOKENS_RATIO,
    current_scene,
    scene_brief,
    stream_scene,
)
from novelist.graph.state import WriteContext, WriteState
from novelist.review import critique_scene_text, decide, verify_issues
from novelist.schemas.review import CRITERIA


def _version_name(revision: int) -> str:
    """版の呼び名（0回目は初稿）。"""
    return "初稿" if revision == 0 else f"推敲{revision}回目の版"


def critique_scene(state: WriteState, runtime: Runtime[WriteContext]) -> dict:
    """今の版を批評し、点数と指摘から、推敲を続けるかを決める。"""
    ctx = runtime.context
    brief = scene_brief(state, runtime)
    critique = critique_scene_text(
        ctx.client, ctx.prompts, ctx.config, state["meta"], state["world"], brief, state["text"]
    )
    issues, dropped = verify_issues(critique.issues, state["text"])
    score = critique.score()
    revisions = state["revisions"]

    scores = " / ".join(
        f"{CRITERIA[name]} {value}" for name, value in critique.scores.model_dump().items()
    )
    log = [f"批評（{_version_name(revisions)}）: {score:.1f}点（{scores}）"]
    if issues:
        log.append(f"指摘 {len(issues)}件: {'、'.join(issue.label for issue in issues)}")
    if dropped:
        log.append(f"引用が原稿に見つからない指摘 {len(dropped)}件を除きました")

    # いちばん点数の高い版を覚えておく。ただし、推敲で短くなりすぎた版は採用しない
    best_score = state.get("best_score")
    update: dict = {}
    too_short = revisions > 0 and state["chars"] < current_scene(state).chars * MIN_RATIO
    if too_short:
        log.append("推敲で短くなりすぎたので、この版は採用しません")
    elif best_score is None or score > best_score:
        update = {
            "best_text": state["text"],
            "best_chars": state["chars"],
            "best_score": score,
            "best_revision": revisions,
        }

    verdict, reason = decide(
        score, len(issues), best_score, revisions, state.get("max_revisions", 0)
    )
    log.append(reason)
    return {**update, "issues": issues, "verdict": verdict, "log": log}


def route_after_critique(state: WriteState) -> Literal["revise_scene", "finalize_scene"]:
    """推敲を続けるなら推敲へ、そうでなければ版を確定する。"""
    return "revise_scene" if state["verdict"] == "revise" else "finalize_scene"


def revise_scene(state: WriteState, runtime: Runtime[WriteContext]) -> dict:
    """批評の指摘に沿って、シーンを推敲する。"""
    ctx = runtime.context
    brief = scene_brief(state, runtime)
    messages = ctx.prompts.render(
        "scene_revise",
        meta=state["meta"],
        world=state["world"],
        brief=brief,
        text=state["text"],
        issues=state["issues"],
    )
    draft = stream_scene(ctx, messages, int(brief.scene.chars * WRITE_TOKENS_RATIO))
    revisions = state["revisions"] + 1
    return {
        "text": draft.text,
        "chars": draft.chars,
        "revisions": revisions,
        "log": [f"推敲{revisions}回目: {draft.describe()}"],
    }


def finalize_scene(state: WriteState) -> dict:
    """これまでの版のうち、いちばん点数の高いものを採用する。"""
    revision = state["best_revision"]
    return {
        "text": state["best_text"],
        "chars": state["best_chars"],
        "score": state["best_score"],
        "log": [f"採用: {_version_name(revision)}（{state['best_score']:.1f}点）"],
    }
```

**`critique_scene`**

今の版（`state["text"]`）を批評し、次の順に処理します。

1. `verify_issues` で、引用が原稿に見つからない指摘を取り除きます。
2. 点数と指摘をログに出します。観点ごとの点数も「シーンカード 8 / つながり 7 / …」のように並べるので、どの観点が弱いかがわかります。
3. いちばん点数の高い版を更新します。ただし、推敲した版が目安の文字数の7割（第15章の `MIN_RATIO`）より短くなった場合は、採用の候補にしません。LLMは、推敲で文章を削りすぎることがあり、短い文章は問題も少ないので、点数が高くなりがちだからです。
4. `decide` で、推敲を続けるかを決めます。`decide` には、今の版を含まない**それまでの**最高点を渡します。今の版が、それまでの最高点を超えたかどうかを判定するためです。

`update` を別の辞書にしてから `{**update, ...}` で返しているのは、最高点を更新したときだけ `best_*` の値を返すためです。返さなかったキーは、状態の値がそのまま残ります。

**`revise_scene`**

批評の指摘を渡して、推敲した全文を書かせます。本文を書くときと同じく、`stream_scene` で生成中の文字列をCLIに流します。

**`finalize_scene`**

いちばん点数の高い版を、`text` と `chars` に戻します。このあとの `summarize_scene` と `save_scene`（第15章）は、`text` を要約して保存するので、採用した版が保存されます。

## 16.9 うまくいかないときは

**初稿がいつも合格してしまう**

批評が甘すぎます。次のことを試してください。

- `review` で何度か批評させて、指摘の内容を読む。指摘が的外れでなければ、`PASS_SCORE` を8.5などに上げる
- `prompts/scene_critique/system.md` の点数の付け方に、「初稿で8点以上になることはまれ」のような一文を加える
- 批評だけ、本文を書くモデルとは別のモデルに任せる。同じモデルは、自分の書いた文章に甘くなりがちです。ただし、llama-server をもう1つ起動し、批評ではそちらにつなぐように変更する必要があります

**いつまでも合格しない**

どの版も7点台で止まる場合は、モデルの実力と合格点が合っていない可能性があります。`PASS_SCORE` を下げるか、`-r 1` で推敲の回数を減らしてください。上限まで推敲しても、いちばん点数の高い版が採用されるので、原稿が悪くなることはありません。

**同じ指摘が繰り返される**

推敲しても、同じ「描写の重複」が毎回指摘されることがあります。推敲の指示が抽象的すぎて、作家役のLLMが何を直せばよいかわからない場合に起きます。批評のプロンプトの「直し方は具体的に」を、「どの文を、どう書き換えるか」まで書かせるように強めてみてください。

**推敲で文章が大きく変わってしまう**

指摘されていない部分まで書き換えられる場合は、推敲の `creative` プロファイルの `temperature` が高すぎる可能性があります。推敲用のプロファイルを別に作り（たとえば `temperature = 0.7`）、`stream_scene` に使うプロファイルを渡せるようにして、`revise_scene` ではそのプロファイルを使うように変えてみてください。

**引用が見つからない指摘が多い**

引用の照合で除かれる指摘が多い場合は、モデルが長い文を正確に写すのを苦手としています。`Issue` の `quote` の `max_length` を小さくし（たとえば40字）、プロンプトの「30字程度」を「15字程度」に変えると、短く正確に引用するようになります。

**遅い**

推敲を2回行うと、1シーンにつき、本文の生成が最大3回、批評が最大3回になります。まず `-r 0` で全体を書き、気になるシーンだけ `review` で確かめてから、`--from` と `-n 1` で推敲しながら書き直す、という使い方もできます。

## 16.10 まとめ

- LLMに**編集者**の役を与えて原稿を**批評**させ、その指摘をもとに**作家**の役のLLMに**推敲**させるループを作りました。批評と推敲を分けることで、直す箇所がはっきりし、良くなったかを点数で測れるようになります
- 批評では、問題の箇所を**引用**させ、観点ごとに**点数**を付けさせました。LLMの批評の弱点（甘さ、ぶれ、ありもしない問題）に対して、採点の基準を示す、**指摘を先に書かせる**、**平均はプログラムで計算する**、**引用が原稿にあるかを確かめる**、という工夫をしました
- 推敲のループは、**合格**、**指摘なし**、**改善しない**、**回数の上限**の4つの条件で終えます。推敲で悪くなることもあるので、すべての版を批評し、**いちばん点数の高い版を採用**しました
- `novelist write -r` で推敲の回数を指定でき、`novelist review` で書き終えたシーンを批評できるようになりました
