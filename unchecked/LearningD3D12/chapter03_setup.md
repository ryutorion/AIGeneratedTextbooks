# 第3章 開発環境のセットアップ

前章でハードウェアを確認しました。本章では、そのハードウェアを叩くためのコードを書く場所を整えます。

正直に言えば、地味な章です。プロジェクトを作り、チェックボックスを入れ、パスを通すだけで、画面には何も出ません。最後に表示されるのは "Hello" の一行です。

それでもこの章に相応の分量を割くのは、**本書が採用する C++23 の `import std;` と、Windows SDK のヘッダ群が、素直には共存してくれない**からです。ここを雰囲気で設定すると、第7章あたりで「なぜか `min` が定義されていない」「PCH をビルドすると内部コンパイラエラーになる」といった、本題とまったく関係のない問題で足止めを食います。

本章の後半は、その地雷の位置を一つずつ示していく作業になります。

**本章のゴール**
x64 の空のプロジェクトから、C++23 と `import std;` が有効な状態を作り、`std::println` で文字列を出力する。あわせて Aftermath SDK のパスを通し、DLL が出力先にコピーされることを確認する。

## 3.1 Visual Studio 2026 のインストールとワークロード選択

### 3.1.1 必要なワークロードとコンポーネント

Visual Studio Installer を起動し、**「C++ によるデスクトップ開発」** ワークロードを選択します。本書に必要なのはこれ一つです。

ワークロードを選ぶと、右側の「インストールの詳細」に個別コンポーネントが並びます。次の項目にチェックが入っていることを確認してください。

| コンポーネント | 必要な理由 |
|---|---|
| MSVC v145 - VS 2026 C++ x64/x86 ビルドツール | コンパイラ本体 |
| Windows 11 SDK(最新版) | `d3d12.h`、`dxgi1_6.h`、`wrl/client.h` の供給元 |
| C++ CMake ツール | 本書では使いませんが、外部サンプルの参照時にあると便利 |
| Just-In-Time デバッガー | クラッシュ時の解析に使います |

**逆に、不要なもの**を挙げておきます。ディスク容量を節約したい場合は外して構いません。

- Windows 10 SDK(古い版)
- v143 以前のツールセット(既存プロジェクトを開かないなら不要)
- C++/CLI サポート
- MFC / ATL

### 3.1.2 Windows SDK のバージョンについて

Direct3D 12 のヘッダは Windows SDK に含まれています。**最新版を入れてください。**

「Agility SDK を使うのだから、Windows SDK は古くてもよいのでは」と思うかもしれません。実際、ランタイムは Agility SDK 側に差し替わります(第4章)。しかし**ヘッダとインポートライブラリは Windows SDK のものを使います**。SDK が古いと、新しい構造体や列挙値の定義が存在せず、コンパイルすら通りません。

なお、Agility SDK の NuGet パッケージには最新のヘッダも同梱されており、そちらを優先させる設定も可能です。本書ではその方式を第4章で採用します。それでも、土台となる Windows SDK は新しいものを入れておいてください。

インストール後、`ヘルプ → Microsoft Visual Studio のバージョン情報` を開きます。

## 3.2 テンプレートを使わず空のプロジェクトから始める

### 3.2.1 なぜテンプレートを使わないのか

Visual Studio には「Windows デスクトップアプリケーション」というテンプレートがあり、選ぶだけでウィンドウが出るコードが生成されます。便利ですが、本書では使いません。

理由は 3 つあります。

**理由 1:生成されたコードの由来がわからない**
テンプレートが吐く `WinMain` とメッセージループには、意味のわからない行がいくつも含まれます。アクセラレータテーブル、文字列リソース、アイコン。どれも本書では使いません。使わないコードが残っていると、後で問題が起きたときに切り分けの邪魔になります。

**理由 2:プロジェクト設定がテンプレート由来のままになる**
テンプレートはリソースファイル、マニフェスト、文字セット設定などをまとめて構成します。本書ではこれらを自分で決めたいので、白紙から始めます。

**理由 3:本書の趣旨と一致する**
`d3dx12.h` を使わずに構造体を手で埋めるのと同じ理屈です。**何がどこから来ているかを全部知っている状態**を作るところに、この本の価値があります。

### 3.2.2 ソリューションとプロジェクトを作る

1. `ファイル → 新規作成 → プロジェクト` を開く
2. 言語を「C++」、プラットフォームを「Windows」に絞り込む
3. **「空のプロジェクト」** を選択して「次へ」
4. 次のように入力する

| 項目 | 値 |
|---|---|
| プロジェクト名 | `D3D12Book` |
| 場所 | 任意(パスに日本語やスペースを含めないこと) |
| ソリューション名 | `D3D12Book` |
| ソリューションとプロジェクトを同じディレクトリに配置 | **チェックを外す** |

> **パスに日本語やスペースを入れない**
>
> MSVC 自体は日本語パスを扱えますが、後の章で使う DXC のコマンドライン呼び出しや、Aftermath のシェーダーデバッグ情報の紐付けで、思わぬところに影響が出ることがあります。`C:\dev\D3D12Book` のような素直なパスにしておいてください。

作成直後のプロジェクトには、ファイルが一つもありません。これが出発点です。

### 3.2.3 構成を x64 のみにする

空のプロジェクトは、既定で `x64` と `x86`(Win32)の 2 構成を持ちます。**x86 は削除します。**

第2章で触れた通り、Aftermath SDK は 32bit の D3D12 アプリケーションでの動作が不安定であることが公式に知られています。使わない構成を残しておくと、うっかりビルドして原因不明の挙動に悩むことになります。

1. ツールバーのプラットフォーム選択(既定では `x64`)から `構成マネージャー` を開く
2. 「アクティブ ソリューション プラットフォーム」のドロップダウンから `編集`
3. `x86` と `Win32` を選択して `削除`

構成は `Debug` と `Release` の 2 つ、プラットフォームは `x64` のみになります。

### 3.2.4 出力先を整理する

既定の出力先は `プロジェクトフォルダ\x64\Debug\` です。悪くありませんが、中間ファイルとソースが同じ階層に混在するので、`build` にまとめます。

`プロジェクトのプロパティ → 構成プロパティ → 全般` で、**構成を「すべての構成」、プラットフォームを「すべてのプラットフォーム」** にしてから設定してください。

| 項目 | 値 |
|---|---|
| 出力ディレクトリ | `$(SolutionDir)build\$(Platform)\$(Configuration)\` |
| 中間ディレクトリ | `$(SolutionDir)build\int\$(ProjectName)\$(Platform)\$(Configuration)\` |
| ターゲット名 | `$(ProjectName)` |
| 構成の種類 | アプリケーション (.exe) |
| C++ 言語標準 | (次節で設定) |

### 3.2.5 ディレクトリ構成を決める

第2章で Aftermath SDK を置いた `external/` と合わせて、次の構成で進めます。

```
D3D12Book/
├─ D3D12Book.sln
├─ external/
│   └─ NsightAftermath/
│       ├─ include/
│       │   ├─ GFSDK_Aftermath.h
│       │   └─ ...
│       └─ lib/x64/
│           ├─ GFSDK_Aftermath_Lib.x64.lib
│           └─ GFSDK_Aftermath_Lib.x64.dll
├─ build/                    ← ビルド生成物(バージョン管理対象外)
└─ D3D12Book/                ← プロジェクトフォルダ
    ├─ D3D12Book.vcxproj
    ├─ pch.h
    ├─ pch.cpp
    └─ src/
        └─ main.cpp
```

Git を使う場合は、`build/` を `.gitignore` に入れておいてください。`external/` は SDK のライセンスの都合上、リポジトリに含めず、README に入手手順を書く形が無難です。

**✅ ここまでの確認**
空のプロジェクトができ、構成が `Debug|x64` と `Release|x64` の 2 つだけになっている。

## 3.3 C++23 を有効にする

### 3.3.1 /std:c++23preview と /std:c++latest

`プロジェクトのプロパティ → 構成プロパティ → C/C++ → 言語 → C++ 言語標準` を開きます。

選択肢は次のようになっています。

| 表示 | オプション | 内容 |
|---|---|---|
| ISO C++14 標準 | `/std:c++14` | |
| ISO C++17 標準 | `/std:c++17` | |
| ISO C++20 標準 | `/std:c++20` | 空のプロジェクトの既定値 |
| **ISO C++23 標準 (プレビュー)** | **`/std:c++23preview`** | **本書で使用** |
| プレビュー - 最新の C++ 作業ドラフトの機能 | `/std:c++latest` | C++26 の一部を含む |

**本書は `/std:c++23preview` を選びます。**

`/std:c++latest` でも本書のコードは動きますが、C++26 の実装途中の機能まで有効になり、コンパイラのバージョンによって挙動が変わりうる領域が広がります。「C++23 を使う」と決めたなら、そこで線を引いたほうが再現性が高くなります。

> **`preview` という名前について**
>
> MSVC において C++23 サポートは、本書執筆時点でも「プレビュー」の位置づけです。これは機能が未完成という意味ではなく、**標準ライブラリの ABI 安定性を保証しないという宣言**です。実際、C++23 の主要機能は一通り実装されており、実用上の問題はほとんどありません。
>
> ただし後述の `import std;` については、実装がまだ枯れていない領域が残っています。3.4.6 節で退避策を用意します。

### 3.3.2 あわせて設定するオプション

同じくプロジェクトのプロパティから、以下も設定します。**すべて「すべての構成」に対して行ってください。**

#### C/C++ → 全般

| 項目 | 値 | 理由 |
|---|---|---|
| 警告レベル | `/W4` | `/Wall` は Windows SDK ヘッダが大量に警告を出すので非現実的 |
| 複数プロセッサによるコンパイル | はい (`/MP`) | ビルド時間の短縮 |
| デバッグ情報の形式 | `/Zi` | (Debug 構成) |

#### C/C++ → 言語

| 項目 | 値 | 理由 |
|---|---|---|
| 準拠モード | はい (`/permissive-`) | 既定で有効。無効にしないこと |
| C++ 言語標準 | `/std:c++23preview` | 前節の通り |

#### C/C++ → コマンドライン → 追加のオプション

```
/utf-8
```

**これは日本語環境では必須級の設定です。** ソースファイルに日本語のコメントや文字列リテラルを書いたとき、`/utf-8` がないとコンパイラがソースを Shift_JIS として解釈しようとし、文字化けや警告 C4819 が発生します。

`/utf-8` は「ソースの文字セットも実行時の文字セットも UTF-8 とみなす」という指定です。本書のコードは UTF-8(BOM なし)で保存する前提で書かれています。

> **`/Zc:preprocessor` について**
>
> 標準準拠のプリプロセッサに切り替えるオプションです。可変引数マクロの挙動が正しくなるなど利点はありますが、**Windows SDK のヘッダの一部と相性問題を起こすことがあります**。本書では有効にしません。必要になったら、そのとき個別に検討してください。

#### リンカー → システム

| 項目 | 値 |
|---|---|
| サブシステム | コンソール (`/SUBSYSTEM:CONSOLE`) |

本章ではコンソールアプリケーションとして作ります。第5章でウィンドウを作る際に `Windows (/SUBSYSTEM:WINDOWS)` へ変更します。

**✅ ここまでの確認**
プロジェクトのプロパティで `/std:c++23preview` と `/utf-8` が設定されている。

## 3.4 `import std;` と Windows ヘッダの共存

ここからが本章の本題です。

### 3.4.1 `std` と `std.compat`

C++23 は、標準ライブラリを名前付きモジュールとして提供します。2 種類あります。

| モジュール | 内容 |
|---|---|
| `std` | `std::` 名前空間の全て。`<cstdio>` などの C ラッパーヘッダの内容も `std::printf` の形で含む。**グローバル名前空間の `::printf` は含まない** |
| `std.compat` | `std` の全て + C ランタイムのグローバル名前空間版(`::printf`、`::size_t`、`::strlen` など) |

Windows のヘッダは C の API なので、グローバル名前空間の名前を大量に使います。であれば `std.compat` を使うべきかと思いきや、**そうではありません。**

Windows SDK のヘッダは、必要な C ランタイムの宣言を**自分で `#include` して持ち込みます**。`Windows.h` は内部で `<stdlib.h>` や `<string.h>` を読み込むので、`::size_t` も `::memcpy` も、`import std;` に頼らずとも揃います。

本書は **`import std;` を使います。** 理由は、グローバル名前空間に持ち込む名前が少ないほうが、名前衝突の事故が減るからです。

### 3.4.2 標準ライブラリモジュールのビルドを有効にする

`import std;` を使うには、`std` モジュールをバイナリ形式(`.ifc` ファイル)にコンパイルしておく必要があります。コマンドラインでは `%VCToolsInstallDir%\modules\std.ixx` を自分でコンパイルしますが、**MSBuild プロジェクトでは自動化されています。**

`プロジェクトのプロパティ → 構成プロパティ → C/C++ → 言語` に、次の項目があります。

| 項目 | 値 |
|---|---|
| **ISO C++23 標準ライブラリ モジュールのビルド** | **はい** |

`.vcxproj` 上では次のプロパティに対応します。UI で見つからない場合は、`.vcxproj` を直接編集しても構いません。

```xml
<PropertyGroup>
  <BuildStlModules>true</BuildStlModules>
</PropertyGroup>
```

これを有効にすると、ビルド時に `std.ixx` が自動でコンパイルされ、`std.ifc` と `std.obj` が中間ディレクトリに生成されます。

> **構成ごとに別々にビルドされます**
>
> モジュールは、**それを利用するコードと同じコンパイラオプションでビルドされていなければなりません。** したがって Debug と Release では別々の `std.ifc` が作られます。
>
> 「Debug では通るのに Release でリンクエラーになる」という現象に遭遇したら、まず中間ディレクトリを消して再ビルドしてください。オプションを変更した後に古い `.ifc` が残っていると起きます。

### 3.4.3 守るべき 3 つの鉄則

`import std;` と Windows ヘッダを同居させる際、次の 3 つを守ってください。**どれか一つでも破ると、意味不明なエラーの山に埋もれます。**

#### 鉄則 1:`#include` が先、`import` が後

```cpp
// ✅ 正しい
#include <Windows.h>
import std;
```

```cpp
// ❌ 壊れる
import std;
#include <Windows.h>
```

同じ内容をヘッダとモジュールの両方から持ち込むこと自体は許されています。ただし**順序が決まっています。** `#include` を先に書けば、コンパイラは重複を処理できます。逆順にすると、「〜は既に宣言されています」というエラーが延々と出ます。

この制約は、外部ライブラリを使うときに厄介になります。あるライブラリのヘッダが内部で `import std;` していると、そのヘッダより後に別の標準ヘッダを `#include` した時点で壊れます。本書はライブラリをほとんど使わないので影響は限定的ですが、頭には入れておいてください。

#### 鉄則 2:PCH の中に `import` を書かない

**これが最大の地雷です。**

> MSVC は、プリコンパイル済みヘッダの中にモジュールの `import` 宣言を書くと、**内部コンパイラエラー(ICE)を起こします。**

「共通のものは全部 PCH にまとめよう」という発想で `pch.h` に `import std;` を書きたくなりますが、これはコンパイラを落とします。エラーメッセージからは原因が読み取れないので、知らないと数時間溶かします。

正しい構成は次の通りです。

- **PCH には `#include` だけを置く**(Windows SDK のヘッダ群)
- **`import std;` は各 `.cpp` に個別に書く**

具体的な形は 3.5 節で示します。

#### 鉄則 3:標準ヘッダと `import std;` を混ぜない

```cpp
// ❌ 避ける
#include <vector>
import std;
```

技術的には(鉄則 1 の順序を守れば)通ることもありますが、Microsoft の公式ドキュメントは明確に非推奨としています。ヘッダユニットと名前付きモジュールの混在も同様です。

**本書のルール:C++ 標準ライブラリは `import std;` からのみ取得する。`<vector>` や `<string>` を `#include` しない。**

例外は次項で述べるマクロ関連だけです。

### 3.4.4 プリプロセッサ定義を設定する

Windows ヘッダの挙動を制御するマクロを、**プロジェクト全体の設定として**定義します。ソースコード中の `#define` に頼らないのは、順序に依存させないためです。

`プロジェクトのプロパティ → 構成プロパティ → C/C++ → プリプロセッサ → プリプロセッサの定義` に、以下を追加します。

```
WIN32_LEAN_AND_MEAN
NOMINMAX
STRICT
UNICODE
_UNICODE
%(PreprocessorDefinitions)
```

それぞれの意味は次の通りです。

| マクロ | 効果 | これがないと |
|---|---|---|
| `WIN32_LEAN_AND_MEAN` | `Windows.h` から Winsock、OLE、DDE などの巨大なサブセットを除外する | コンパイルが遅くなり、名前衝突が増える |
| `NOMINMAX` | `min` / `max` マクロを定義させない | `std::min` の呼び出しが `std::(...)` のように展開されて壊れる |
| `STRICT` | ハンドル型(`HWND` など)を型安全な別型として扱う | `HWND` と `HDC` を取り違えてもコンパイルが通る |
| `UNICODE` / `_UNICODE` | Win32 API の `A`/`W` 選択で `W`(ワイド文字)版を使う | `CreateWindow` が ANSI 版になる |

`UNICODE` と `_UNICODE` は、`構成プロパティ → 詳細 → 文字セット` を「Unicode 文字セットを使用する」にしても設定されます。どちらでも構いませんが、**両方の場所を確認して、確実に定義されている状態にしてください。** 片方だけ設定されている中途半端な状態が一番厄介です。

> **`NOMINMAX` の重要性**
>
> `Windows.h` は `min` と `max` を**関数形式マクロとして**定義します。
>
> ```cpp
> #define max(a,b) (((a) > (b)) ? (a) : (b))
> ```
>
> これがあると、`std::max(a, b)` は `std::(((a) > (b)) ? (a) : (b))` に展開され、意味不明な構文エラーになります。第17章で自作の数学ライブラリを書くとき、確実にぶつかります。

### 3.4.5 マクロとモジュールが衝突したときの対処

`import std;` を使ううえで、避けて通れない制約があります。

#### 名前付きモジュールはマクロを提供しない

モジュールはマクロをエクスポートしません。したがって、**次のものは `import std;` では手に入りません。**

| 使えないもの | 提供元 | 対処 |
|---|---|---|
| `assert` | `<cassert>` | 第6章で自作のアサートに置き換える |
| `errno` | `<cerrno>` | 本書では使わない |
| `offsetof` | `<cstddef>` | 必要なら `#include <cstddef>` |
| `va_arg` 等 | `<cstdarg>` | 本書では使わない |
| `INT_MAX` 等 | `<climits>` | `std::numeric_limits` を使う |

本書では `assert` を使いません。第6章で `std::source_location` を使った自作のアサートマクロを書き、そちらに統一します。マクロが必要なら、自分で定義したほうが制約に悩まずに済むからです。

#### Windows ヘッダのマクロが自分のコードを壊す

`Windows.h` は膨大なマクロを定義します。とりわけ危険なものを挙げます。

**A/W サフィックスのマクロ**

```cpp
#define GetMessage  GetMessageW
#define CreateWindow CreateWindowW
#define LoadImage   LoadImageW
```

自分のクラスに `GetMessage` というメンバ関数を作ると、`GetMessageW` に化けます。エラーメッセージには存在しないはずの `W` 付き名前が現れ、混乱の元になります。

**`ERROR` マクロ**

```cpp
// wingdi.h
#define ERROR 0
```

これが第6章で本当に問題になります。ログのレベルを列挙型で定義しようとして、

```cpp
enum class LogLevel { Info, Warning, ERROR };   // ❌ 壊れる
```

と書くと、`ERROR` が `0` に展開され、`Warning, 0` という意味不明な列挙子定義になります。

**対処は 2 通りあります。**

1. **そもそもぶつかる名前を使わない**(推奨)
   `ERROR` ではなく `Error`、`GetMessage` ではなく `PumpMessage` のように命名する。

2. **局所的に `#undef` する**
   ```cpp
   #include <Windows.h>
   #undef ERROR
   ```
   ただし、後で `Windows.h` を使う他のコードに影響する可能性があるので、乱用は避けてください。

本書は 1 の方針を採ります。**命名規約として、Win32 API と同じ綴りの識別子を避ける**というルールを設けます。

### 3.4.6 うまくいかないときの退避策

正直に書いておきます。**MSVC のモジュール実装は、本書執筆時点でまだ枯れていません。**

Microsoft の月次リリースノートには、`import std;` に関する不具合の修正と、新たな不具合の報告が今も並んでいます。ツールセットを更新した途端にビルドが通らなくなる、という事態は起こりえます。

そこで、**モジュールを使わない構成にいつでも戻せるように**しておきます。

プロジェクトに次のヘッダを一つ用意してください。

```cpp
// D3D12Book/std_import.h
//
// 標準ライブラリの取り込み方を、この一箇所に集約する。
// モジュールに問題が起きたら USE_STD_MODULE を 0 にする。

#pragma once

#define USE_STD_MODULE 1

#if !USE_STD_MODULE
    #include <cstdint>
    #include <string>
    #include <string_view>
    #include <vector>
    #include <memory>
    #include <span>
    #include <expected>
    #include <optional>
    #include <format>
    #include <print>
    #include <source_location>
    #include <filesystem>
    #include <algorithm>
    #include <ranges>
    #include <chrono>
#endif
```

そして各 `.cpp` では次のように書きます。

```cpp
#include "pch.h"
#include "std_import.h"
#if USE_STD_MODULE
import std;
#endif
```

**冗長ですが、これは保険として機能します。** `USE_STD_MODULE` を `0` にすれば、`import std;` が一切消えて従来のヘッダ方式に戻ります。本書のコードは `std::` 修飾を常に付けて書くので、どちらの方式でもそのまま通ります。

> **この保険を勧める理由**
>
> 「新しい機能を学ぶ」と「動くものを作る」は、両立させるべきですが、優先順位はあります。モジュールが原因でビルドが通らない日に、第20章のテクスチャ転送のデバッグができなくなるのは本末転倒です。
>
> スイッチ一つで退避できるようにしておけば、モジュールを安心して試せます。

## 3.5 プリコンパイル済みヘッダの構成

### 3.5.1 モジュールの時代に PCH が残る理由

Microsoft のドキュメントは、PCH よりモジュールやヘッダユニットを推奨しています。にもかかわらず、本書は PCH を使います。

理由は単純です。**Windows SDK と Direct3D 12 のヘッダは、モジュール化されていないからです。**

`d3d12.h` も `dxgi1_6.h` も `Windows.h` も、依然として巨大なテキストファイルです。これらを毎回パースするコストは無視できません。C++ 標準ライブラリだけがモジュール化された現状では、次のハイブリッド構成が現実的な最適解になります。

| 対象 | 取り込み方 |
|---|---|
| C++ 標準ライブラリ | `import std;`(モジュール) |
| Windows SDK / D3D12 | PCH に `#include`(従来方式) |

そして 3.4.3 の鉄則 2 により、**この 2 つは物理的に分離しなければなりません。** PCH に `import` を書けないので、自然とこの形に落ち着きます。

### 3.5.2 `pch.h` と `pch.cpp` を作る

プロジェクトフォルダ直下に 2 つのファイルを作ります。

**`pch.h`**

```cpp
// pch.h
//
// Windows SDK / Direct3D 12 のヘッダをまとめる。
//
// 【重要】このファイルに import 宣言を書いてはならない。
// MSVC は PCH 内の import で内部コンパイラエラーを起こす。
// 標準ライブラリは各 .cpp で import std; する。

#pragma once

// ---------------------------------------------------------
// Windows
// ---------------------------------------------------------
// WIN32_LEAN_AND_MEAN / NOMINMAX / STRICT / UNICODE は
// プロジェクトのプリプロセッサ定義で設定済み。
// ここでは #define しない(設定箇所を一元化するため)。

#include <Windows.h>

// ---------------------------------------------------------
// COM
// ---------------------------------------------------------
#include <wrl/client.h>          // Microsoft::WRL::ComPtr

// ---------------------------------------------------------
// Direct3D 12 / DXGI
// ---------------------------------------------------------
// 第7章で以下を追加する:
// #include <d3d12.h>
// #include <dxgi1_6.h>
// #include <dxgidebug.h>

// ---------------------------------------------------------
// Nsight Aftermath
// ---------------------------------------------------------
// 第8章で以下を追加する:
// #include <GFSDK_Aftermath.h>
```

**`pch.cpp`**

```cpp
// pch.cpp
// PCH を生成するためだけの空のファイル。
#include "pch.h"
```

コメントで「第7章で追加する」と明示してあるのは、章の進行に合わせてこのファイルが育っていくからです。**今の時点で `d3d12.h` を書かないでください。** まだデバイスを作っていないのに D3D12 のヘッダが入っていると、「どこまで進んだか」が見えなくなります。

### 3.5.3 `/Yc` と `/Yu` の設定

PCH は「生成する側」と「使う側」で設定が異なります。

**プロジェクト全体の設定**

`プロジェクトのプロパティ → 構成プロパティ → C/C++ → プリコンパイル済みヘッダー`

| 項目 | 値 |
|---|---|
| プリコンパイル済みヘッダー | 使用 (`/Yu`) |
| プリコンパイル済みヘッダー ファイル | `pch.h` |

**`pch.cpp` だけの設定**

ソリューションエクスプローラーで `pch.cpp` を右クリック → プロパティ

| 項目 | 値 |
|---|---|
| プリコンパイル済みヘッダー | **作成 (`/Yc`)** |
| プリコンパイル済みヘッダー ファイル | `pch.h` |

この非対称な設定が PCH の仕組みです。`pch.cpp` をコンパイルしたときに `.pch` ファイルが生成され、他のすべての `.cpp` はそれを読み込むだけになります。

> **よくあるエラー:C1010**
>
> ```
> fatal error C1010: プリコンパイル済みヘッダーの検索中に予期しない
> ファイルの終わりを検出しました。'#include "pch.h"' をソースに
> 追加しましたか?
> ```
>
> `/Yu` が有効なのに、その `.cpp` の先頭に `#include "pch.h"` がない場合に出ます。**`.cpp` の一行目は必ず `#include "pch.h"` です。** その前に何か書いてはいけません(コメントは可)。

### 3.5.4 すべての `.cpp` が従う書き出しの型

以上をまとめると、本書のすべてのソースファイルは次の形で始まります。

```cpp
// ---- 定型 ----
#include "pch.h"          // ① Windows / D3D12 ヘッダ(PCH)
#include "std_import.h"   // ② 標準ライブラリの取り込み方の切り替え
#if USE_STD_MODULE
import std;               // ③ 標準ライブラリ(モジュール)
#endif
// ---- ここから本文 ----
```

**この順序には意味があります。**

- ① が最初なのは、PCH の制約(C1010)による
- ② と ③ が ① の後なのは、鉄則 1(`#include` が先、`import` が後)による
- ③ が `#if` で囲まれているのは、退避策(3.4.6)のため

以降の章では、この 5 行を省略して本文だけを載せることがあります。**すべての `.cpp` の冒頭にこれがあるものとして読んでください。**

**✅ ここまでの確認**
`pch.h` / `pch.cpp` / `std_import.h` の 3 ファイルが作成され、PCH の設定が完了している。

## 3.6 Aftermath SDK のリンク設定と DLL コピー

第2章 2.4.3 節でダウンロードした Aftermath SDK を、プロジェクトから使えるようにします。**実際に使い始めるのは第8章ですが、パスの設定は今のうちに済ませておきます。**

### 3.6.1 インクルードパスとライブラリパス

`プロジェクトのプロパティ`(すべての構成、x64)

**C/C++ → 全般 → 追加のインクルード ディレクトリ**

```
$(SolutionDir)external\NsightAftermath\include
%(AdditionalIncludeDirectories)
```

**リンカー → 全般 → 追加のライブラリ ディレクトリ**

```
$(SolutionDir)external\NsightAftermath\lib\x64
%(AdditionalLibraryDirectories)
```

**リンカー → 入力 → 追加の依存ファイル**

```
GFSDK_Aftermath_Lib.x64.lib
%(AdditionalDependencies)
```

`$(SolutionDir)` を使うことで、プロジェクトを別の場所に移動しても設定が壊れません。絶対パスを書かないでください。

### 3.6.2 ビルド後イベントで DLL をコピーする

`GFSDK_Aftermath_Lib.x64.dll` は、実行ファイルと同じディレクトリに存在しなければなりません。手でコピーすると必ず忘れるので、ビルドの一部にします。

**ビルド イベント → ビルド後のイベント → コマンド ライン**

```
xcopy /Y /D "$(SolutionDir)external\NsightAftermath\lib\x64\GFSDK_Aftermath_Lib.x64.dll" "$(OutDir)"
```

**説明**

```
xcopy /Y /D "$(SolutionDir)external\NsightAftermath\lib\x64\GFSDK_Aftermath_Lib.x64.dll" "$(OutDir)"
      │  │
      │  └─ /D : コピー先が新しい場合はスキップ(毎回コピーしない)
      └──── /Y : 上書き確認をしない
```

**説明** の欄には、ビルド出力に表示される文字列を入れておくと親切です。

```
Copying Nsight Aftermath DLL...
```

> **`xcopy` はディレクトリと解釈されるとエラーになる**
>
> コピー先のパスの末尾に `\` を付けてください。`$(OutDir)` は末尾に `\` を含む形で定義されているので、上記のままで問題ありません。もし `File not found` や `Invalid path` が出る場合は、パスに含まれるフォルダ名を確認してください。

### 3.6.3 この時点で確認できること

第8章まで Aftermath の関数は呼びません。しかし、以下の 2 点は今すぐ確認できます。

1. **インクルードパスが正しいか** → `GFSDK_Aftermath.h` を読み込み、バージョン定数を表示する
2. **DLL がコピーされているか** → 実行時にファイルの存在を調べる

次節でこれを実装します。

## ✅ 本章のゴール:"Hello" を出す

### Step 1:`main.cpp` を作る

`D3D12Book/src/main.cpp` を新規作成し、次の内容を書きます。

```cpp
// src/main.cpp
#include "pch.h"
#include "std_import.h"
#if USE_STD_MODULE
import std;
#endif

#include <GFSDK_Aftermath.h>

namespace
{
    // Aftermath SDK のバージョンを "x.y" の形に整形する。
    // GFSDK_Aftermath_Version_API は 0x0000MMmm の形式で定義されている。
    std::string FormatAftermathVersion()
    {
        constexpr std::uint32_t version = GFSDK_Aftermath_Version_API;
        const std::uint32_t major = (version >> 16) & 0xFFFF;
        const std::uint32_t minor = version & 0xFFFF;
        return std::format("{}.{}", major, minor);
    }

    // 実行ファイルと同じディレクトリを取得する。
    std::filesystem::path GetExecutableDirectory()
    {
        wchar_t buffer[MAX_PATH]{};
        const DWORD length = ::GetModuleFileNameW(nullptr, buffer, MAX_PATH);
        if (length == 0 || length == MAX_PATH)
        {
            return {};
        }
        return std::filesystem::path(buffer).parent_path();
    }
}

int main()
{
    std::println("Hello, Direct3D 12!");
    std::println("");

    // --- ビルド環境の確認 ---
    std::println("C++ standard   : {}", __cplusplus);
    std::println("MSVC compiler  : {}", _MSC_VER);

#if USE_STD_MODULE
    std::println("std library    : import std (module)");
#else
    std::println("std library    : #include (header)");
#endif

    std::println("");

    // --- Aftermath SDK の確認 ---
    std::println("Aftermath SDK  : {}", FormatAftermathVersion());

    const auto exeDir = GetExecutableDirectory();
    const auto dllPath = exeDir / L"GFSDK_Aftermath_Lib.x64.dll";
    const bool dllFound = std::filesystem::exists(dllPath);

    std::println("Aftermath DLL  : {}", dllFound ? "found" : "NOT FOUND");

    if (!dllFound)
    {
        std::println("");
        std::println("  Expected at: {}", dllPath.string());
        std::println("  Check the post-build event in project properties.");
        return 1;
    }

    return 0;
}
```

### Step 2:ビルドする

`Ctrl + Shift + B` でビルドします。

初回ビルドは、`std` モジュールのコンパイルが走るため時間がかかります(数十秒程度)。2 回目以降は速くなります。

### Step 3:実行する

`Ctrl + F5`(デバッグなしで開始)で実行します。

**期待される出力**

```
Hello, Direct3D 12!

C++ standard   : 202302
MSVC compiler  : 1951

std library    : import std (module)

Aftermath SDK  : 2025.5
Aftermath DLL  : found
```

`__cplusplus` が `202302` になっていれば C++23 が有効です。`199711` と表示された場合は `/Zc:__cplusplus` が無効ですが、これは表示上の問題であり、実際の言語標準には影響しません(気になる場合はコンパイラオプションに `/Zc:__cplusplus` を追加してください)。

`_MSC_VER` は MSVC のバージョンです。`1950` が MSVC 14.50、`1951` が 14.51 に対応します。

## まとめ

本章の要点は 4 つです。

**1. 空のプロジェクトから始める。**
テンプレートが生成するコードには、本書で使わないものが多く含まれます。何がどこから来ているかを全部知っている状態を作ることが、後の章のデバッグを楽にします。

**2. `import std;` と Windows ヘッダには 3 つの鉄則がある。**
`#include` が先で `import` が後。PCH に `import` を書かない。標準ヘッダと `import std;` を混ぜない。特に 2 番目は内部コンパイラエラーになるため、原因の特定が困難です。

**3. 標準ライブラリはモジュール、Windows SDK は PCH。**
D3D12 のヘッダがモジュール化されていない以上、このハイブリッド構成が現実的な最適解です。そして鉄則 2 により、この分離は選択ではなく必然です。

**4. 退避経路を用意しておく。**
`std_import.h` のスイッチ一つでヘッダ方式に戻せるようにしました。モジュールの不具合で本題が止まらないための保険です。

次章では DirectX Agility SDK を導入します。デバイスを作る前にこれを済ませておかないと、第30章の Enhanced Barriers や第33章のバインドレスに進んだ段階で、初期化コードの設計をやり直す羽目になります。
