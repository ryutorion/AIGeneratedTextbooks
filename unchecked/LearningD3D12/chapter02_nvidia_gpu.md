# 第2章 NVIDIA GPU という前提を理解する

Direct3D 11 までのグラフィックスプログラミングでは、GPU の中身を知らなくてもそれなりに戦えました。ドライバが賢く働いてくれるので、多少おかしな使い方をしても「遅いけれど動く」に着地してくれたからです。

Direct3D 12 はその親切心を捨てたAPIです。メモリの確保も、状態の遷移も、同期も、すべてこちらが指示します。指示が間違っていれば、絵が壊れるか、GPU ごと止まります。そして止まったとき、API が教えてくれるのは `0x887A0006` という数字ひとつです。

このとき助けになるのは、抽象化された「GPU 一般」の知識ではなく、**目の前で動いている具体的なハードウェアの知識**です。だから本書は最初に、対象ハードウェアを NVIDIA GPU に固定し、その素性を確認するところから始めます。

本章ではまだ一行もコードを書きません。カタログを読み、ドライバを整え、ツールを入れ、自分の環境を紙に書き出します。地味ですが、ここを飛ばすと第8章以降で必ず戻ってくることになります。

**本章のゴール**
自分の GPU の製品名・アーキテクチャ世代・ドライバのバージョンを 3 通りの方法で確認でき、本書の各機能が自分の環境で使えるかどうかを判断できるようになること。

## 2.1 アーキテクチャ世代と機能対応

### 2.1.1 Turing / Ampere / Ada / Blackwell

NVIDIA は 2 年前後の周期で GPU アーキテクチャを刷新しています。世代名は物理学者や天文学者の名前から取られており、製品名(GeForce RTX xx シリーズ)とは別の軸で管理されています。

Direct3D 12 プログラミングの観点から重要な世代を、古い順に見ていきます。

#### Pascal(2016 / GeForce GTX 10 シリーズ)

DirectX 12 世代の入口ではありますが、レイトレーシング専用回路(RT Core)もメッシュシェーダーも持ちません。DXR は後にドライバ側のソフトウェア実行として有効化されましたが、実用的な速度ではありません。

**本書は Pascal を対象外とします。** 第4部までは動作する可能性が高いものの、第5部の内容が丸ごと動きません。

#### Turing(2018 / GeForce RTX 20 シリーズ、GTX 16 シリーズ)

本書が要求する**最低ライン**です。この世代で、後に「DirectX 12 Ultimate」としてまとめられる機能群が出揃いました。

- 第1世代 RT Core によるハードウェアレイトレーシング(DXR Tier 1.0 / 1.1)
- メッシュシェーダー、Amplification シェーダー
- 可変レートシェーディング(VRS)Tier 1 / Tier 2
- サンプラーフィードバック
- 独立スレッドスケジューリング(後述の warp の挙動が Pascal 以前と変わる)
- INT32 演算ユニットを FP32 とは別に持つ構成

> **コラム:GTX 16 シリーズの罠**
>
> GTX 1650 / 1660 などの GTX 16 シリーズは、アーキテクチャとしては Turing です。しかし **RT Core と Tensor Core が搭載されていません**。メッシュシェーダーや VRS は動きますが、レイトレーシングは Pascal と同じくソフトウェア実行になります。
>
> 「Turing なのに第37章が動かない」という事故の典型がこれです。製品名に "RTX" が付いているかどうかが、実質的な判定基準になります。

#### Ampere(2020 / GeForce RTX 30 シリーズ)

演算能力の底上げが主眼の世代です。

- SM あたりの FP32 演算ユニットが実質倍増(詳細は 2.3 節)
- 第2世代 RT Core
- Resizable BAR への対応(第21章の GPU Upload Heaps に関係します)

本書としては、この世代以降を**推奨環境**とします。

#### Ada Lovelace(2022 / GeForce RTX 40 シリーズ)

レイトレーシングの「無駄をなくす」ための機構が入った世代です。

- 第3世代 RT Core
- Opacity Micromap(OMM):アルファテスト付きジオメトリの高速化
- Shader Execution Reordering(SER):レイの発散を並べ替えて実行効率を上げる
- Displaced Micro-Mesh(DMM)

OMM と SER は、当初は NVIDIA 独自の拡張(NVAPI 経由)としてのみ利用できました。しかし後に Direct3D 12 の標準機能として取り込まれています。この経緯は 2.5 節で改めて触れます。

#### Blackwell(2025 / GeForce RTX 50 シリーズ)

本書執筆時点(2026 年 7 月)における最新のコンシューマ向け世代です。

- 第4世代 RT Core
- INT32 と FP32 の演算ユニットが統合され、全ユニットが両方を実行可能に
- ニューラルシェーディング / Cooperative Vectors 向けの強化

なお、データセンター向けでは Rubin 世代が登場していますが、**コンシューマ向け GeForce の Rubin 世代製品は本書執筆時点で発表されていません**。本書のコードは標準的な Direct3D 12 のみを使うため、将来の世代でもそのまま動作するはずですが、第5部の一部の記述(推奨パラメータなど)は最新世代に合わせて読み替えてください。

#### 世代早見表

| 世代 | 主な製品 | ダイ名 | 登場 | 本書での扱い |
|---|---|---|---|---|
| Pascal | GTX 10 シリーズ | GP10x | 2016 | 対象外 |
| Turing | RTX 20 / GTX 16 | TU10x | 2018 | **最低ライン** |
| Ampere | RTX 30 シリーズ | GA10x | 2020 | 推奨 |
| Ada Lovelace | RTX 40 シリーズ | AD10x | 2022 | 推奨 |
| Blackwell | RTX 50 シリーズ | GB20x | 2025 | 推奨 |

製品名からアーキテクチャを見分ける単純な規則があります。**RTX の後の千の位が世代番号**です。RTX **2**080 は Turing、RTX **3**070 は Ampere、RTX **4**060 は Ada、RTX **5**090 は Blackwell。ノート PC 向けの "Laptop GPU" も同じ規則に従います。

**この表を信用しすぎないでください。** Enhanced Barriers や Shader Model 6.6 のように、ハードウェアではなくドライバと Agility SDK のバージョンで決まる機能があります。GPU Upload Heaps に至っては、マザーボードの UEFI 設定(Resizable BAR の有効/無効)まで絡みます。

正しい答えは、実行時に `ID3D12Device::CheckFeatureSupport` に聞くことでしか得られません。第7章でこの問い合わせを実装し、起動時に対応機能を一覧出力する仕組みを作ります。**この表は「そもそも買い替えが必要か」を判断するための目安**であり、コード中の判定条件にしてはいけません。

### 2.1.3 自分の GPU がどれかを確認する

もっとも手軽なのは、Windows 標準の DirectX 診断ツールです。

`Win + R` で「ファイル名を指定して実行」を開き、以下を入力します。

```
dxdiag
```

「ディスプレイ」タブに製品名とドライバのバージョンが表示されます。GPU が複数搭載されている PC(ノート PC など)では「ディスプレイ 1」「ディスプレイ 2」のようにタブが分かれます。

> **コラム:ノート PC のハイブリッドグラフィックス**
>
> ノート PC の多くは、CPU 内蔵 GPU(Intel Iris Xe / AMD Radeon Graphics)と NVIDIA GPU の両方を積んでいます。省電力のため、通常は内蔵 GPU が使われ、負荷の高いアプリのときだけ NVIDIA GPU に切り替わります。
>
> 問題は、この切り替えが**アプリごとの設定**で決まることです。Visual Studio から起動した自作アプリが内蔵 GPU で動いてしまい、「Aftermath が初期化できない」「メッシュシェーダーが非対応と出る」と悩むケースが実際にあります。
>
> 対処は 2 段階です。まず Windows の「設定 → システム → ディスプレイ → グラフィックス」で、自分の実行ファイルに対して「高パフォーマンス」を指定します。そのうえで、**第7章でアダプタ列挙のコードを書く際に、NVIDIA のアダプタを明示的に選ぶ**ようにします。設定に頼らずコードで確定させるのが確実です。

より詳しい情報は NVIDIA App(旧 GeForce Experience / NVIDIA コントロールパネル)からも見られます。NVIDIA コントロールパネルの「ヘルプ → システム情報」に、ドライバのバージョン、CUDA コア数、メモリ量、対応する Direct3D の機能レベルなどが並びます。

## 2.2 ドライバの選び方とバージョン確認

Direct3D 12 において、ドライバは「あれば動くもの」ではなく**開発対象そのもの**です。Agility SDK の新機能も、Aftermath のクラッシュダンプも、ドライバ側の実装がなければ動きません。

### 2.2.1 Game Ready と Studio の違い

NVIDIA は GeForce 向けに 2 系統のドライバを配布しています。

**Game Ready Driver(GRD)**
新作ゲームの発売に合わせて頻繁に更新されます。新しいゲームへの最適化と、新機能への追従が最優先です。おおむね月に 1〜2 回のペースで出ます。

**Studio Driver(SD)**
クリエイティブ系アプリケーション(3DCG、映像編集など)での安定動作を重視したドライバです。更新頻度は低く、リリース前の検証期間が長めに取られています。

**バージョン番号の体系は共通です。** 610.88 という番号は Game Ready でも Studio でも同じ意味を持ちます。同じ番号なら、含まれる Direct3D の実装もほぼ同じです。違いは「どのバージョンを、いつ、どういう検証を経て出すか」という配布ポリシーにあります。

本書の読者にとっての選び方は次の通りです。

| 状況 | 推奨 |
|---|---|
| 第5部(メッシュシェーダー、DXR、バインドレス)を進めたい | Game Ready |
| Agility SDK の新しいバージョンを試したい | Game Ready |
| 手元の環境を安定させて第1〜3部を確実に進めたい | Studio |
| 業務で使っている PC を兼用している | Studio |

迷ったら Game Ready で構いません。ただし、**開発中に不可解な挙動に遭遇したとき、直前にドライバを更新していないかを必ず疑ってください。** 自分のコードのバグとドライバの回帰バグは、症状が驚くほど似ています。ドライバのバージョンをメモしておく習慣は、後で必ず役に立ちます。

### 2.2.2 Aftermath / Agility SDK が要求する最低ドライバ

本書が依存する 2 つの SDK には、それぞれドライバの要件があります。

#### Nsight Aftermath SDK

Aftermath は、ライブラリ側とドライバ側が対になって機能します。**アプリにリンクした SDK のバージョンに対して、ドライバが古いと動きません。**

NVIDIA は SDK バージョンとドライバブランチの対応表を公開しています。本書執筆時点の主な対応は次の通りです。

| ドライバブランチ | 対応する Aftermath SDK |
|---|---|
| R590 以降 | 2025.5 |
| R580 | 2025.4 |
| R570 | 2025.1 |
| R565 | 2024.3 |

「ブランチ」とは、バージョン番号の上位 3 桁のことです。610.88 なら R610 ブランチになります。本書執筆時点の最新ドライバは 610.88(2026 年 7 月 28 日リリース)ですので、R590 以降という要件は問題なく満たせます。

SDK 全体としての下限は、**ドライバ 531.41 以降、GPU は Pascal 以降**です。ただし本書は Turing 以降を前提としており、また新しいアーキテクチャへの対応が SDK 側で順次追加される構造になっています。たとえば Blackwell 対応のクラッシュダンプ生成は Aftermath 2025.1 で追加されました。**新しい GPU を使うなら、SDK も新しいものを使ってください。**

#### DirectX Agility SDK

Agility SDK は、OS 標準の Direct3D 12 ランタイムをアプリ単位で差し替える仕組みです(詳細は第4章)。ランタイムだけを新しくしても、ドライバがその機能を実装していなければ意味がありません。

たとえば DXR 1.2 の Shader Execution Reordering と Opacity Micromap は、Agility SDK 1.619(2026 年 2 月リリース、Shader Model 6.9 と同時)で正式版になりました。これを実際に動かすには、Agility SDK 1.619 以降、対応ドライバ、そして Ada 以降の GPU という 3 つの条件がすべて揃う必要があります。

**「Agility SDK を入れたのに新機能が使えない」場合、疑うべき順番は次の通りです。**

1. `D3D12SDKVersion` のエクスポートを書き忘れていないか(第4章)
2. `D3D12Core.dll` が実行ファイルの隣に配置されているか(第4章)
3. ドライバが古くないか(本節)
4. GPU の世代が要件を満たしているか(2.1 節)

経験上、圧倒的に多いのは 1 と 2 です。

### 2.2.3 バージョンを確認する 3 つの方法

ドライバのバージョンは複数の経路で確認できます。それぞれ表示形式が異なるので、対応関係を理解しておくと混乱せずに済みます。

#### 方法 1:dxdiag

前述の通り、「ディスプレイ」タブの「ドライバー」欄に表示されます。ここでは Windows 内部の形式(例:`33.0.61.088`)で出ることがあります。

**Windows 内部形式から NVIDIA のバージョンへの変換規則**は次の通りです。末尾の 2 セグメントの数字をつなげて、下 5 桁を取り出し、上 3 桁と下 2 桁の間に小数点を打ちます。

```
33.0.61.088  →  "61" + "088" = "61088"  →  下5桁 "61088"  →  610.88
32.0.15.7688 →  "15" + "7688" = "157688" → 下5桁 "57688"  →  576.88
```

#### 方法 2:PowerShell

コマンドで取得できると、後々スクリプト化できて便利です。

```powershell
Get-CimInstance Win32_VideoController |
    Select-Object Name, DriverVersion, DriverDate, AdapterRAM |
    Format-List
```

複数の GPU が搭載されている場合はすべて列挙されます。`Name` に "NVIDIA" を含むものが目的の GPU です。

`DriverVersion` は Windows 内部形式で出るので、上記の規則で読み替えてください。

#### 方法 3:nvidia-smi

NVIDIA ドライバに同梱されるコマンドラインツールです。データセンター向けの印象がありますが、GeForce にもインストールされています。

```
nvidia-smi
```

出力の上部に、ドライバのバージョンが NVIDIA 形式のまま表示されます。GPU 名、メモリ使用量、温度なども一覧できます。

必要な項目だけを取り出すこともできます。

```
nvidia-smi --query-gpu=name,driver_version,memory.total --format=csv
```

```
name, driver_version, memory.total [MiB]
NVIDIA GeForce RTX 4070, 610.88, 12282 MiB
```

さらに詳しい情報は `-q` オプションで出せます。

```
nvidia-smi -q
```

**この 3 つのうち、`nvidia-smi` を第一の手段として覚えてください。** 変換規則を経由せずに NVIDIA 形式のバージョンが直接読めるのは、これだけです。

> **メモ:表示される「CUDA Version」について**
>
> `nvidia-smi` の出力右上には「CUDA Version」も表示されます。これは**ドライバが対応している CUDA のバージョン**であり、CUDA Toolkit がインストールされていることを意味しません。本書では CUDA を使わないので、この欄は無視して構いません。

### 2.2.4 クリーンインストールが必要になる場面

NVIDIA のドライバインストーラには「クリーンインストールの実行」というチェックボックスがあります。通常は不要ですが、以下の場面では最初から使ったほうが早いです。

- **Game Ready と Studio を切り替えるとき**
- **大きくバージョンを飛ばして更新するとき**(例:R550 台から R610 台へ)
- **ドライバ更新後に不可解な TDR やハングが出始めたとき**
- **Nsight のツール群が GPU を認識しなくなったとき**

チェックボックスによるクリーンインストールで解決しない場合は、DDU(Display Driver Uninstaller)というサードパーティ製ツールをセーフモードで実行し、ドライバの痕跡を完全に消してから入れ直します。これは最終手段ですが、開発機では年に一度くらい必要になることがあります。

> **重要:ドライバのバージョンを記録する習慣**
>
> 第31章で Aftermath のクラッシュダンプを解析する際、**そのダンプがどのドライバで生成されたか**が解析可能性を左右します。開発中は、ログの起動時出力にドライバのバージョンを必ず含めるようにしてください。第7章でその仕組みを作ります。
>
> 「先週は動いていたのに」という現象の原因が、Windows Update によるドライバの自動更新だった、というのは珍しくありません。

## 2.3 NVIDIA ハードウェアの基礎語彙

ここでは、後の章で繰り返し出てくる 3 つの言葉だけを押さえます。GPU アーキテクチャの解説書ではないので、深入りはしません。**「なぜその数字を選ぶのか」を説明できる程度**を目標にします。

### 2.3.1 SM、warp、occupancy

#### SM(Streaming Multiprocessor)

NVIDIA GPU の演算コアの基本単位です。GPU 全体は、この SM を数十個並べたものだと考えてください。

たとえば RTX 4070 なら SM が 46 個、RTX 4090 なら 128 個といった具合です。SM の数がそのまま並列処理能力の目安になります。

各 SM は、以下を内部に持っています。

- FP32 / INT32 の演算ユニット(世代により構成が異なる)
- レジスタファイル(65,536 個の 32bit レジスタ)
- L1 キャッシュと共有メモリ(HLSL の `groupshared` の実体)
- Tensor Core、RT Core(Turing 以降の RTX 製品)
- ワープスケジューラ

重要なのは、**HLSL のスレッドグループ(`[numthreads]` で指定するまとまり)は、必ず 1 つの SM 上で実行される**という点です。スレッドグループが SM をまたぐことはありません。だからこそ `groupshared` メモリによるスレッド間の高速な情報共有が可能になります。

#### warp(ワープ)

**NVIDIA GPU は、32 スレッドをひとまとまりにして実行します。** この 32 スレッドの束を warp と呼びます。

これが本節でもっとも重要な事実です。GPU は 1 スレッドずつ実行しているのではなく、常に 32 個セットで動いています。1 スレッドだけ起動しても、32 レーン分の回路が動き、31 レーン分は捨てられます。

この性質から、2 つの帰結が生まれます。

**帰結 1:スレッド数は 32 の倍数にする**

`[numthreads(8, 8, 1)]` は 64 スレッド、つまり 2 warp ちょうどです。無駄がありません。

`[numthreads(10, 10, 1)]` は 100 スレッドです。100 ÷ 32 = 3.125 なので、GPU は 4 warp = 128 レーンを起動し、**28 レーンを無駄にします**。22% の演算資源が捨てられている計算です。

**帰結 2:warp 内で分岐すると両方の経路を実行する**

同じ warp に属する 32 スレッドは、原則として同じ命令を同時に実行します。ここで条件分岐が入り、16 スレッドが `if` 側、16 スレッドが `else` 側に行くとどうなるか。

GPU は **両方の経路を順番に実行し、それぞれで不要なレーンをマスクします**。結果として、実行時間は分岐なしの場合の 2 倍になります。これを「ダイバージェンス(divergence)」と呼びます。

なお、Turing 以降は「独立スレッドスケジューリング」により、warp 内のスレッドが独立したプログラムカウンタを持てるようになりました。これによりデッドロックしにくくなりましたが、**性能上のダイバージェンスのコストは変わりません**。

> **注意:32 という数字をコードに埋め込まない**
>
> warp サイズが 32 なのは NVIDIA の話です。AMD は世代によって 32 または 64、Intel は可変です。
>
> HLSL には `WaveGetLaneCount()` という組み込み関数があり、実行時のレーン数を取得できます。Wave Intrinsics を使うコード(第32章)では、この関数を使ってください。**本書が NVIDIA を前提にするのは「どの値を選ぶか」の判断のためであり、その値をハードコードするためではありません。**

#### occupancy(占有率)

SM は、複数の warp を同時に「抱えて」おり、ある warp がメモリ待ちで止まっている間に別の warp を実行することで、メモリレイテンシを隠蔽します。

**occupancy とは、SM が同時に抱えられる warp の最大数に対して、実際に何 warp を抱えられているかの比率**です。

抱えられる warp 数を制限する要因は 3 つあります。

| 制限要因 | 内容 |
|---|---|
| レジスタ | シェーダーが 1 スレッドあたり多くのレジスタを使うと、抱えられる warp が減る |
| 共有メモリ | `groupshared` を大量に使うと、同時に載せられるスレッドグループが減る |
| スレッドグループサイズ | 極端に大きい/小さいと端数が出る |

occupancy が低いと、メモリ待ちを隠蔽できず、演算ユニットが遊びます。ただし **occupancy は高ければ高いほど良い、という単純な指標ではありません。** レジスタを潤沢に使って 1 スレッドあたりの効率を上げたほうが速い場合もあります。

大事なのは、「遅い」と感じたときに **occupancy を測る手段を持っていること**です。それが 2.4 節で導入する Nsight Graphics です。

### 2.3.2 後の章で効いてくる理由

ここまでの 3 語が、本書のどこで顔を出すかをまとめておきます。今は「そういうものか」と流して構いません。該当章に来たときに戻ってきてください。

| 概念 | 登場する章 | どう効くか |
|---|---|---|
| warp = 32 | 第32章 コンピュートシェーダー | `[numthreads]` の値を 32 の倍数にする根拠。`[numthreads(8,8,1)]` が定番である理由 |
| warp = 32 | 第32章 Wave Intrinsics | `WaveActiveSum` などが「32 スレッド単位」で動く前提 |
| ダイバージェンス | 第37章 レイトレーシング | レイの向きがバラバラだと同じ warp 内で別々のマテリアルを処理することになる。SER はこれを並べ替えて解消する仕組み |
| occupancy | 第29章 Nsight Graphics | GPU Trace で occupancy を実測し、ボトルネックを特定する |
| occupancy | 第38章 最適化 | レジスタ使用量とのトレードオフを判断する |
| SM とスレッドグループ | 第32章 | `groupshared` が高速な理由。サイズ上限(D3D12 では 32KB)の由来 |
| クアッド(2×2) | 第36章 メッシュシェーダー | ピクセルシェーダーは 2×2 単位で実行される。小さい三角形が多いとレーンが無駄になり、これがメッシュレット設計の動機になる |

### 2.4.1 Nsight Graphics

NVIDIA 製のグラフィックスデバッガです。本書でもっとも使用頻度が高くなるツールです。

**主な機能**

- **Frame Debugger**:1 フレームをキャプチャし、ドローコールを 1 つずつ遡って、その時点のレンダーターゲット、リソースの中身、パイプラインステートを確認できる
- **GPU Trace**:SM の稼働率、メモリ帯域、各ユニットのボトルネックを時系列で可視化
- **Shader Profiler**:シェーダーのどの命令で時間を使っているかを特定
- **Aftermath クラッシュダンプビューア**:`.nv-gpudmp` ファイルを開いて解析(第31章)

**入手**

NVIDIA Developer サイトからダウンロードします。NVIDIA Developer Program(無料)への登録が必要です。

**初回起動時の確認**

インストール後に起動し、GPU が正しく認識されるかを見ておきます。起動時のダイアログで対象アプリケーションを指定する画面が出ますが、**この時点ではまだアプリがないので、起動できることだけ確認して閉じて構いません**。

`Help → About` でバージョンを確認し、メモしておいてください。Aftermath のダンプは、生成時の SDK バージョンより新しい Nsight Graphics でないと開けない場合があります。

> **バージョンの組み合わせについて**
>
> Nsight Graphics には Aftermath の解析機能が同梱されており、**Nsight Graphics 2023.1 以降**であれば Aftermath ダンプを開けます。実務では「Aftermath SDK・Nsight Graphics・ドライバの 3 つを同じ時期のものに揃える」のが一番トラブルが少ないやり方です。

### 2.4.2 Nsight Systems

こちらは**システム全体**のプロファイラです。Nsight Graphics が「1 フレームの中身」を見るのに対し、Nsight Systems は「CPU スレッドと GPU の仕事が時間軸上でどう噛み合っているか」を見ます。

本書では第35章(マルチスレッド化)と第38章(最適化)で使います。

- CPU スレッドごとの実行状況
- コマンドリストの記録と実行のタイミング
- CPU が GPU を待っている時間、GPU が CPU を待っている時間
- API 呼び出しのタイムライン

### 2.4.4 PIX for Windows(併用と排他)

Microsoft が提供するグラフィックスデバッガです。ベンダを問わず動作します。

**Nsight Graphics と PIX、どちらを使うべきか。**

本書の立場は「両方入れておき、目的で使い分ける」です。

| 目的 | 向いているツール |
|---|---|
| ドローコールを追う、リソースを目で見る | どちらでも可(好みで) |
| SM 稼働率、メモリ帯域などハードウェア寄りの解析 | **Nsight Graphics** |
| Aftermath ダンプの解析 | **Nsight Graphics**(唯一の選択肢) |
| D3D12 の API 使用状況の検証、DRED の確認 | **PIX** |
| 他ベンダの GPU でも同じ手順で解析したい | **PIX** |

**併用に関する重要な制約**

グラフィックスデバッガは、アプリと D3D12 ランタイムの間に割り込んで動作します。したがって、**複数のデバッガを同時にアタッチすることはできません**。Nsight Graphics でキャプチャ中に PIX をアタッチしようとすると、どちらかが失敗します。

さらに重要な制約があります。

> **Aftermath は、グラフィックスデバッガがアタッチされている間は動作しません。**

Nsight Graphics や PIX を通してアプリを起動している状態では、Aftermath のクラッシュダンプは生成されません。これは仕様です。デバッガが GPU の実行を横取りしているため、Aftermath が本来見るべきドライバの状態が取れないのです。

つまり、**「Nsight でキャプチャしながらクラッシュ原因を調べる」という使い方はできません**。ワークフローは次のように分けます。

1. まず**素の状態**で実行し、Aftermath にダンプを吐かせる
2. 生成された `.nv-gpudmp` を、後から Nsight Graphics で**開いて**解析する

この分離を理解していないと、第31章で「なぜダンプが出ないのか」と延々悩むことになります。本章のうちに頭に入れておいてください。

**PIX の入手**

Microsoft の PIX on Windows サイトからダウンロードします。GPU キャプチャを行うには Windows の**開発者モード**を有効にする必要があるので、この機会に「設定 → システム → 開発者向け」から有効にしておいてください。第4章で Agility SDK を扱う際にも開発者モードが必要になります。

## 2.5 NVAPI について — 本書で扱わない理由

NVIDIA は **NVAPI** という独自の API を公開しています。ドライバに直接話しかけ、Direct3D の標準機能では届かない領域にアクセスするための仕組みです。

NVAPI でできることの例:

- ディスプレイ設定、G-SYNC の制御
- NVIDIA Reflex による低遅延化
- DLSS の統合
- 標準化前の先行機能へのアクセス

**本書はこれを扱いません。** 理由は 3 つあります。

### 理由 1:本書の設計方針と衝突する

第1章 1.3 節で述べた線引きを思い出してください。本書は「レンダラの設計判断を肩代わりするものは自作し、ハードウェア/ドライバ層に触れる基盤は既製品を使う」という基準で道具を選んでいます。

NVAPI はこの基準では「使ってよい」側に見えます。しかし NVAPI が提供するのはドライバ層への窓口であると同時に、**Direct3D 12 とは別体系の API**です。読者が学ぶべき対象が二重になり、「D3D12 を理解する」という本書の目的を薄めてしまいます。

Aftermath は、これとは事情が異なります。Aftermath はレンダリングには一切関与せず、**クラッシュしたときだけ働く**、隔離された機能です。第8章で見る通り、その組み込みはコード上の一箇所に閉じ込められます。

### 理由 2:主要な機能が標準化された

かつて NVAPI でしか使えなかった機能のうち、重要なものは Direct3D 12 側に取り込まれています。

- **Opacity Micromap(OMM)** と **Shader Execution Reordering(SER)** は、Agility SDK 1.619 で **DXR 1.2** の一部として正式版になりました(2026 年 2 月)。Shader Model 6.9 と組み合わせて、標準の HLSL から利用できます。

つまり、第37章で SER と OMM を扱う際、**NVAPI は必要ありません。** 標準の D3D12 API と `CheckFeatureSupport` による対応確認だけで完結します。これは本書にとって非常に都合の良い変化でした。

なお、SER は API としては他ベンダの GPU でも呼び出せますが、実際に並べ替えが行われるかはハードウェア次第です。DXR 1.2 では「デバイスが実際にリオーダーを行うか」を問い合わせられるようになっています。NVIDIA では **Ada 世代以降**が実効性を持ちます。

### 理由 3:コードのベンダ依存を最小化したい

**本書は NVIDIA を「対象」として固定しますが、「依存先」にはしません。**

この区別は重要です。本書のコードは、標準の Direct3D 12 API だけで書かれます。NVIDIA を前提にするのは、

- どの機能が使えるかを断定できる(2.1 節の表)
- 「では実際どの値にすべきか」に踏み込める(warp = 32 を前提とした `[numthreads]` の選択など)
- クラッシュ解析の具体的な手順を示せる(Aftermath と Nsight)

といった、**説明の解像度を上げるため**です。ベンダ非依存を装った教科書が「環境によります」で終わらせるところを、本書は具体的な数字で答えます。

その代償として、Aftermath という NVIDIA 専用ライブラリを 1 つだけ使います。これは 1 ファイルに隔離するので、他ベンダの環境で動かしたい場合はそのファイルを差し替えるだけで済みます(付録 J を参照)。NVAPI まで持ち込むと、この隔離が成立しなくなります。

### では NVAPI が必要になるのは

以下を実装したくなったときです。

- **DLSS**(Super Resolution / Frame Generation / Ray Reconstruction)
- **NVIDIA Reflex**(入力遅延の低減)
- 標準化されていない最新の実験的機能

これらは本書の範囲外ですが、入り口だけは付録 H にまとめてあります。本書を終えた読者が次に進む先として、有力な候補です。

## まとめ

本章では、これから書くコードが動く土台を確認しました。要点は 4 つです。

**1. GPU の世代が、書けるコードの範囲を決める。**

**2. ドライバは開発対象の一部である。**

ただしコードに埋め込むのではなく、`WaveGetLaneCount()` で取得します。NVIDIA を前提にするのは判断のためであり、依存するためではありません。

**4. Aftermath とグラフィックスデバッガは排他である。**
素の状態で走らせてダンプを取り、後から Nsight で開く。この 2 段階を最初に理解しておくと、第31章で悩まずに済みます。
