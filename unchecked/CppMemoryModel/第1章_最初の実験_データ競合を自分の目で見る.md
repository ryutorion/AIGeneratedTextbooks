# 第1章 最初の実験 ― データ競合を自分の目で見る

並行プログラミングのバグには、独特のたちの悪さがあります。テストでは一度も落ちないのに本番で月に一度だけ落ちる。デバッガをつなぐと再現しなくなる。printfを一行足しただけで消える。こうした「幽霊」のようなバグの正体を突き止めるには、まず幽霊を自分の手で呼び出せるようにならなければなりません。

この章では、もっとも古典的で、もっとも単純なデータ競合を自分のマシンで再現します。理論の説明は最小限にとどめ、とにかく**壊れる様子を自分の目で観測する**ことを目標にします。x64マシンとARMマシンの両方をお持ちの方は、ぜひ両方で実験してください。この章のバグは両方で発生しますが、壊れ方の「表情」が微妙に違うことに気づくはずです。その違いの意味は、第3章でTSOを学んだときに明らかになります。

> **この章の実験環境**
> 本文中の実行例は次の2台で採取しました。読者の環境では数値が異なりますが、それこそがこの章の主題です。
> - x64: Intel Core i7(8コア)、Ubuntu 24.04、GCC 13
> - ARM: Apple M2(8コア)、macOS、Apple Clang 15(AArch64)
>
> ビルドコマンドは各リストの直後に示します。第0章で構築した環境なら、そのままコピー&ペーストで動きます。

## 1.1 【コード】2スレッドで`counter++`を100万回 ― 結果が毎回違うことを確認する

最初の実験プログラムはこれ以上ないほど単純です。グローバル変数`counter`を、2本のスレッドがそれぞれ100万回インクリメントします。

**リスト1-1: race1.cpp ― 最初の(壊れた)カウンタ**

```cpp
#include <cstdio>
#include <thread>

int counter = 0;                    // 2スレッドで共有する変数
constexpr int N = 1'000'000;

void worker() {
    for (int i = 0; i < N; ++i) {
        counter++;                  // ← 事件現場
    }
}

int main() {
    std::thread t1(worker);
    std::thread t2(worker);
    t1.join();
    t2.join();
    std::printf("counter = %d (期待値 %d)\n", counter, 2 * N);
}
```

まずは最適化を切って(`-O0`)ビルド・実行します。

```console
$ g++ -std=c++20 -O0 -pthread race1.cpp -o race1
$ ./race1
counter = 1103942 (期待値 2000000)
$ ./race1
counter = 1244035 (期待値 2000000)
$ ./race1
counter = 1039817 (期待値 2000000)
```

期待値200万に対して、110万前後。しかも**毎回違う値**です。1回の実行だけでは偶然かもしれないので、シェルで100回まわして統計を取りましょう。

**リスト1-2: 100回実行して分布を見る**

```console
$ for i in $(seq 100); do ./race1; done | awk '{print $3}' | sort -n | uniq -c | head
```

筆者のx64環境では、最小値1,021,553、最大値1,996,218、そして200万ちょうどは100回中0回でした。ARM(Apple M2)でも同様に壊れますが、興味深いことに分布の形が少し違い、200万にかなり近い値が出る頻度が高めでした。この「壊れ方の癖」の違いは頭の片隅に置いておいてください。

ここで確認したいことは1つだけです。

> **観測事実1**: 2スレッドから同じ`int`を`++`すると、インクリメントが「消失」する。消える量は実行のたびに変わる。

`counter++`は1行のコードです。1行のコードの、いったいどこに割り込む隙間があるのでしょうか。その答えは1.3節でアセンブリを読んで突き止めますが、その前にもうひとつ、奇妙な現象を観測しておきます。

## 1.2 【コード】同じコードを-O0と-O2でコンパイルして結果が変わる様子を観察する

ソースコードは一切変更せず、最適化レベルだけを`-O2`に上げてみます。

```console
$ g++ -std=c++20 -O2 -pthread race1.cpp -o race1_O2
$ ./race1_O2
counter = 2000000 (期待値 2000000)
$ ./race1_O2
counter = 2000000 (期待値 2000000)
$ ./race1_O2
counter = 1000000 (期待値 2000000)
$ ./race1_O2
counter = 2000000 (期待値 2000000)
```

壊れ方が一変しました。`-O0`では「110万前後のばらばらな値」だったのに、`-O2`では**ちょうど100万か、ちょうど200万のどちらか**しか出ません。中間の値は一切観測されなくなりました。

なぜでしょうか。コンパイラが何をしたのか、逆アセンブルで確かめます(読み方は次節で説明するので、いまは雰囲気だけつかんでください)。

```console
$ objdump -d race1_O2 | grep -A6 '<_Z6workerv>:'
0000000000001320 <_Z6workerv>:
    1320:  add    DWORD PTR [rip+0x2cf6],0xf4240   # counter += 1000000
    132a:  ret
```

驚くべきことに、**100万回のループが消えています**。コンパイラは「このループは`counter`に100万(=0xf4240)を足すのと同じだ」と見抜き、たった1命令の`add`に畳み込みました。単一スレッドの世界ではこれは完全に正しい最適化です。C++コンパイラは「as-ifルール」――観測可能な動作が変わらない限り、どんな書き換えも許される――に従って動いており、そして**データ競合のあるプログラムに『観測可能な動作』の保証はそもそも存在しない**ため、この書き換えは合法なのです。

その結果、実行時の動きはこうなります。各スレッドは「`counter`を読む→100万を足す→書き戻す」を1回だけ行います。2スレッドの読み書きが運よく直列に並べば200万、双方が「0」を読んでから書き戻し合えば片方の100万が丸ごと上書きされて100万。だから中間値が消えたのです。

> **観測事実2**: 最適化レベルを変えるとバグの症状が変わる。コンパイラは、データ競合のあるコードを「別のプログラム」に書き換えることがある。

この観測事実2は実務上きわめて重要です。「デバッグビルドでは再現するのにリリースビルドでは再現しない」「その逆」という現象の正体の一端がこれです。バグはコードの中に一貫して存在しているのに、コンパイラの書き換えによって**症状だけが変わる**のです。

そしてもうひとつ、不吉な予告をしておきます。コンパイラがループを`counter += 1000000`に畳み込めたということは、コンパイラは**メモリアクセスを自由に並べ替えたり統合したりする**ということです。第2章では、この「コンパイラによる並べ替え」と「CPUによる並べ替え」が二重に襲ってくる様子を観測します。

## 1.3 なぜ壊れたのか ― `counter++`が3命令に分解されることをアセンブリで確認する

`-O0`版に戻って、`worker`関数のループ本体を逆アセンブルします。

**x64(GCC 13, -O0)の場合:**

```console
$ objdump -d race1 | grep -A4 'counter'
```

ループ本体から`counter++`に対応する部分を抜き出すと、次の3命令です。

```asm
mov    eax, DWORD PTR [counter]   ; ① counterをレジスタeaxに読み込む(Load)
add    eax, 1                     ; ② レジスタ上で1を足す
mov    DWORD PTR [counter], eax   ; ③ eaxをcounterに書き戻す(Store)
```

**ARM(AArch64, Clang, -O0)の場合:**

```asm
adrp   x8, counter@PAGE
ldr    w9, [x8, counter@PAGEOFF]  ; ① counterをレジスタw9に読み込む(Load)
add    w9, w9, #1                 ; ② レジスタ上で1を足す
str    w9, [x8, counter@PAGEOFF]  ; ③ w9をcounterに書き戻す(Store)
```

命令の名前こそ違え、構造はまったく同じです。ソースコード上は1行・1個の演算子に見えた`counter++`は、機械語のレベルでは**読む・足す・書く**の3ステップに分解されています。これをリード・モディファイ・ライト(read-modify-write、RMW)操作と呼びます。

3ステップあるということは、ステップの「あいだ」に他スレッドが割り込めるということです。インクリメントが消失する典型的なシナリオを追ってみましょう。`counter`の値が42のときに2スレッドが同時に`++`を実行したとします。

```
時刻   スレッド1                     スレッド2                counterの値
----   --------------------------   ----------------------   -----------
 t1    ① load  → eax = 42                                    42
 t2                                  ① load  → eax = 42      42
 t3    ② add   → eax = 43                                    42
 t4                                  ② add   → eax = 43      42
 t5    ③ store → counter = 43                                43
 t6                                  ③ store → counter = 43  43  ← 44になるはずが!
```

2回インクリメントしたのに、`counter`は1しか増えていません。スレッド2の書き込みがスレッド1の結果を**上書き**したためです。これが「消失したインクリメント(lost update)」の正体です。1.1節で観測した「110万前後」という値は、200万回のRMWのうちおよそ90万回がこの形で衝突していたことを意味します。

ここで素朴な疑問が湧くかもしれません。「たった3命令の隙間に、そんなに高頻度で割り込むものだろうか?」――割り込みます。現代のCPUでは2つのコアが**物理的に同時に**この3命令を実行しており、OSのタイムスライスを待つ必要すらありません。さらに言えば、各コアのキャッシュとストアバッファ(第3章と第4章の主役です)が絡むため、話は「命令の交互実行」よりもっと複雑です。しかし本章の範囲では、次の理解で十分です。

> **本章の中心的教訓**: ソースコード1行のアトミック性(不可分性)は、誰も保証してくれない。`counter++`は不可分な操作**ではない**。

なお、鋭い読者は1.2節との矛盾に気づいたかもしれません。`-O2`では`add DWORD PTR [rip+...], 0xf4240`という**1命令**になっていました。1命令なら不可分では? ――残念ながら違います。x64のメモリ宛て`add`命令は、`lock`プレフィックスが付かない限り、CPU内部では依然として「読む・足す・書く」のマイクロ操作に分解されて実行され、他コアの割り込みを排除しません(`lock add`との違いは第8章でベンチマークとともに扱います)。ARMに至っては、そもそもメモリ宛ての演算命令が存在しないロード・ストアアーキテクチャなので、必ず3命令に分かれます。

## 1.4 【コード】volatileにしてみる → 直らないことを確認する(よくある誤解の実験的否定)

ここで多くのC出身プログラマが手を伸ばしがちな「薬」があります。`volatile`です。「コンパイラの最適化が悪さをするなら、最適化を抑止する`volatile`を付ければいいのでは?」――もっともらしい仮説です。仮説は実験で検証しましょう。

**リスト1-3: race2.cpp ― volatileで直る……のか?**

```cpp
#include <cstdio>
#include <thread>

volatile int counter = 0;           // ← 変更点はここだけ
constexpr int N = 1'000'000;

void worker() {
    for (int i = 0; i < N; ++i) {
        counter = counter + 1;      // volatile変数への ++ はC++20で非推奨のため書き換え
    }
}

int main() {
    std::thread t1(worker);
    std::thread t2(worker);
    t1.join();
    t2.join();
    std::printf("counter = %d (期待値 %d)\n", counter, 2 * N);
}
```

`-O2`でビルドして実行します。

```console
$ g++ -std=c++20 -O2 -pthread race2.cpp -o race2
$ ./race2
counter = 1187265 (期待値 2000000)
$ ./race2
counter = 1290047 (期待値 2000000)
$ ./race2
counter = 1153392 (期待値 2000000)
```

**直っていません。** それどころか、`-O2`なのに壊れ方が`-O0`のとき(110万前後のばらばらな値)に戻りました。逆アセンブルすると理由がわかります。

```asm
; race2 の worker ループ本体(x64, -O2)
.L2:
    mov    eax, DWORD PTR counter[rip]   ; ① load  ← 消せない
    add    eax, 1                        ; ②
    mov    DWORD PTR counter[rip], eax   ; ③ store ← 消せない
    sub    edx, 1
    jne    .L2
```

`volatile`は確かに仕事をしました。コンパイラは「`volatile`変数へのアクセスは観測可能な副作用であり、削除・統合・並べ替えをしてはならない」という規則に従い、1.2節で見たループ畳み込み(`counter += 1000000`への統合)を**しなくなりました**。100万回のload/storeが律儀に生成されています。

しかしそれだけです。生成されたのは1.3節とまったく同じ「素の3命令」であり、**CPUレベルでの割り込みに対しては無防備なまま**です。`volatile`が抑止するのはコンパイラの振る舞いだけで、複数コアの同時実行という物理現象には何の影響も与えません。実験結果はこう要約できます。

> **観測事実3**: `volatile`はコンパイラによる症状の変化(1.2節)を打ち消しただけで、データ競合そのもの(1.1節)は1ビットも直していない。

C++の`volatile`の正しい用途は、メモリマップドI/Oのように「メモリへのアクセスそれ自体が副作用を持つ」場面に限られます。スレッド間同期の道具では**ありません**。この誤解が根強いのは、(a) Javaの`volatile`には本物の同期機能があること、(b) x64のような強いメモリモデルの上では`volatile`だけで**偶然動いてしまう**コードが書けてしまうこと、の2つが原因です。(b)は本書全体を貫くテーマ「TSOへのただ乗り」の最初の顔見せでもあります。x64(TSO)では偶然助かるが、ARMでは確実に死ぬ――そういうコードを、第2章と第7.8節で実際に作って壊します。

さらにもうひとつ重要な点があります。C++の規格の観点では、リスト1-3は依然として**データ競合を含む未定義動作(undefined behavior)**のプログラムです。未定義動作とは「変な値になる」ではなく「何が起きても文句を言えない」という意味です。ThreadSanitizer(第5.2節で本格的に使います)にかけると、`volatile`の有無にかかわらず同じ警告が出ることを確認できます。

```console
$ g++ -std=c++20 -O2 -pthread -fsanitize=thread race2.cpp -o race2_tsan
$ ./race2_tsan 2>&1 | head -5
==================
WARNING: ThreadSanitizer: data race (pid=31337)
  Write of size 4 at 0x... by thread T2:
    #0 worker() race2.cpp:9
==================
```

## 1.5 【コード】std::atomicに変えて直す ― ただし「なぜ直ったか」は第2部までお預け

それでは正解を見ましょう。C++11以降の正しい道具は`std::atomic`です。

**リスト1-4: race3.cpp ― std::atomicによる修正版**

```cpp
#include <atomic>
#include <cstdio>
#include <thread>

std::atomic<int> counter{0};        // ← int を std::atomic<int> に
constexpr int N = 1'000'000;

void worker() {
    for (int i = 0; i < N; ++i) {
        counter++;                  // ソースの見た目は元のまま
    }
}

int main() {
    std::thread t1(worker);
    std::thread t2(worker);
    t1.join();
    t2.join();
    std::printf("counter = %d (期待値 %d)\n", counter.load(), 2 * N);
}
```

```console
$ g++ -std=c++20 -O2 -pthread race3.cpp -o race3
$ for i in $(seq 100); do ./race3; done | sort | uniq -c
    100 counter = 2000000 (期待値 2000000)
```

100回実行して100回とも200万。ついに直りました。ARM機でも同じ結果になります。ThreadSanitizerも沈黙します。

何が変わったのか、いつものように逆アセンブルで確認します。

**x64:**

```asm
.L2:
    lock add DWORD PTR counter[rip], 1   ; lockプレフィックス付きRMW
    sub    edx, 1
    jne    .L2
```

**ARM(AArch64, LSE命令が使える場合):**

```asm
.L2:
    mov    w9, #1
    ldaddal w9, w9, [x8]                 ; アトミックなload-add(acquire+release)
    subs   w10, w10, #1
    b.ne   .L2
```

x64では`add`に`lock`プレフィックスが付き、ARMでは`ldaddal`という専用のアトミック命令に変わりました。どちらも「読む・足す・書く」を**ハードウェアが不可分な1操作として実行する**ことを保証する命令です。もう他コアが3ステップの隙間に割り込むことはできません。1.3節の教訓――「不可分性は誰も保証してくれない」――に対して、`std::atomic`は「明示的に頼めばハードウェアが保証してくれる」という答えを与えたわけです。

ただし、タダではありません。壊れた版(リスト1-1、`-O0`)と修正版で実行時間を比べてみます。

```console
$ time ./race1        # 壊れた版(結果は間違っている)
real    0m0.004s
$ time ./race3        # atomic版(結果は正しい)
real    0m0.021s
```

正しさの代償として約5倍遅くなりました(この数値はコア間のキャッシュライン争奪の激しさで大きく変わります。詳細な計測とチューニングは第12章で行います)。「アトミック操作はなぜ遅いのか」「いつなら安いのか」も、本書後半の重要テーマです。

### この章で直せたもの、まだ直せていないもの

さて、めでたしめでたし――と言いたいところですが、正直に告白しなければならないことがあります。この章で`std::atomic`が解決したのは、データ競合の中でも**いちばん分かりやすい症状**、すなわち「1つの変数へのRMWの衝突」だけです。

実は`counter++`は、`std::atomic`のデフォルト設定(`memory_order_seq_cst`)よりずっと弱い保証で正しく動かせます。第7.4節で、このカウンタを`memory_order_relaxed`に緩めてもなお正しいこと、そしてARMではそれが実測できるほど速くなることを確認します。逆に言えば、いまの修正版は「効きすぎる薬」を使っており、私たちはまだ**どこまでが必要な保証なのか**を説明できていません。

さらに、次章ではもっと不気味な現象が待っています。この章のバグは「1つの変数」の中で完結していました。しかし変数が2つになった瞬間、「書いた順番どおりに、他のスレッドから見えるとは限らない」という、直感に真っ向から逆らう世界が始まります。しかもその壊れ方は、**x64とARMでまったく異なります**。x64では絶対に観測できないのにARMでは簡単に観測できる並べ替え――それを自分の目で見ることが、次章の目標です。

### 第1章のまとめ

- **観測事実1**: `counter++`の並行実行はインクリメントを消失させる。`counter++`は3命令(load/add/store)のRMWであり、不可分ではない(1.1節、1.3節)。
- **観測事実2**: 最適化レベルはバグの「症状」を変える。コンパイラはデータ競合のあるコードを合法的に別物へ書き換える(1.2節)。
- **観測事実3**: `volatile`はコンパイラの書き換えを止めるだけで、データ競合は直せない。規格上も未定義動作のまま(1.4節)。
- **修正**: `std::atomic`はハードウェアのアトミックRMW命令(x64: `lock add` / ARM: `ldaddal`)を生成させ、不可分性を保証する。ただし性能コストがあり、保証の「適量」はまだ論じていない(1.5節)。
- **次章への伏線**: x64で`volatile`が「偶然動いてしまう」ことがあるのはなぜか。変数が2つに増えたとき何が起きるか。

### 章末演習

1. リスト1-1のスレッド数を2から4、8に増やし、消失するインクリメントの割合がどう変わるか計測せよ。
2. `counter`を`int`から`long long`に変えて32bit ARM(または`-m32`)でビルドし、`-O0`での壊れ方が悪化する(値の「引き裂き」= tearingが起きる)ことを確認せよ。ヒント: 64bit値の読み書きが2命令に分かれる。
3. リスト1-4で`counter++`を`counter = counter + 1`に書き換えて実行し、**atomicなのに壊れる**ことを確認せよ。なぜか(第6.5節で正式に扱うが、逆アセンブルすれば自力で推理できる)。
4. `taskset -c 0 ./race1`(Linuxの場合)で全スレッドを1コアに縛って実行し、結果の分布がどう変わるか観察せよ。マルチコアの同時実行とOSのプリエンプションの寄与を切り分けてみよ。
