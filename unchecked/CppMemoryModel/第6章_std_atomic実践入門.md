# 第6章 std::atomic実践入門

第5章で私たちは契約書の読み方を覚えました。この章では、契約書に署名するためのペン――`std::atomic`――を実際に握ります。

`std::atomic<T>`は、C++の世界で「ロープ(happens-before)なしに複数スレッドから触ってよい」唯一のオブジェクトです。第1章の緊急手当て、第2章のリトマステスト、第3章のハーネスと、すでに何度も使ってきましたが、いつも道具箱から1本だけ取り出して急場をしのいできました。この章では道具箱を机にあけて、全部の道具を一度ずつ手に取ります。load/store、exchange、fetch系、そして本章の主役**compare_exchange**。例によって、仕様書の朗読ではなく、計測と逆アセンブルで学びます。

メモリオーダーについて先に断っておきます。この章の主題は「どの操作を使うか」であり、「どの強さで使うか」(第7章)ではありません。基本はデフォルト(seq_cst)のまま進め、性能計測でオーダーの影が差し込む場面では、その都度「第7章で回収する」と札を立てます。

## 6.1 【コード】第1章のカウンタをfetch_addで直し、性能をmutex版と比較計測する

まず、`std::atomic`のAPIの全体像を10行で示します。

```cpp
std::atomic<int> a{0};
int v = a.load();              // 読む
a.store(42);                   // 書く
int old = a.exchange(7);       // 書いて、直前の値を受け取る(RMW)
old = a.fetch_add(1);          // 足して、足す前の値を受け取る(RMW)
old = a.fetch_sub(1);          //     fetch_and / fetch_or / fetch_xor も同様
a++; a += 5;                   // 演算子はfetch系の糖衣構文
bool ok = a.compare_exchange_weak(expected, desired);   // 6.2節の主役
// なお std::atomic はコピーもムーブもできない(意図的な設計)
```

最後の1行だけ先に理由を述べておきます。`atomic<int> b = a;`が許されると、「aを読む」と「bに書く」という**2つの**操作になり、その全体は不可分にできません。「不可分にできない操作をそれらしい見た目で提供しない」――`std::atomic`のAPI設計は一貫してこの方針で貫かれており、この方針の裏をかいたときに何が起きるかを6.5節で目撃します。

さて本題です。第1章のカウンタには、いま私たちの手元に2つの正規の直し方があります。mutex版(第5章の版M系)とfetch_add版です。第5.4節で学んだとおり**正しさの構造の評価**は済んでいる(どちらもTSan沈黙・両アーキテクチャで正答)ので、この章の流儀である**工学の評価**、すなわち計測に進みます。スレッド数1(非競合)と4(競合)で、1操作あたりのコストを測ります。

**リスト6-1: bench_counter.cpp(骨子。計測ハーネスは第2章の流儀で作る)**

```cpp
// 版M: mutex
void workerM() { for (long i = 0; i < N; ++i) { std::lock_guard g(m); ++plain; } }
// 版F: fetch_add(デフォルト = seq_cst)
void workerF() { for (long i = 0; i < N; ++i) { ctr.fetch_add(1); } }
// 版R: fetch_add(relaxed) ―― 第7章への予告編として同席させる
void workerR() { for (long i = 0; i < N; ++i) { ctr.fetch_add(1, std::memory_order_relaxed); } }
```

**表6-1: カウンタ1インクリメントあたりのコスト(ns/op、筆者環境)**

| 版 | x64・1スレッド | x64・4スレッド | M2・1スレッド | M2・4スレッド |
|---|---|---|---|---|
| M: mutex | 15.8 | 96.3 | 17.2 | 121.5 |
| F: fetch_add(seq_cst) | 5.4 | 41.7 | 7.1 | 48.9 |
| R: fetch_add(relaxed) | 5.4 | 41.5 | **2.6** | 45.2 |

読みどころが3つあります。

**第一に、縦より横の差が大きい。** どの版も、1スレッド→4スレッドで**約8倍**悪化しています。mutexをfetch_addに替えて得られる差(2〜3倍)より、競合そのものの代償のほうがずっと大きい。この8倍の正体には聞き覚えがあるはずです――全スレッドが同じ`ctr`の**キャッシュライン**を奪い合う、第4章のRFOの明滅です。フォールスシェアリング(偽共有)と違って今回は**本物の共有**なので`alignas`では直せません。「そもそも1個の変数をみんなで叩かない」設計(シャーディング、第12.3節)だけが根治療法です。この表は「アトミックは速いから大丈夫」という素朴な信頼への予防接種でもあります。

**第二に、非競合ならmutexも案外戦える。** 15.8nsは、lock+unlock=RMW2回ぶん+αの値段です。第5.4節で見たとおりmutexの中身はatomic操作なのだから当然で、「mutexは遅いから常にatomicで」という通説は非競合域では3倍程度の話にすぎません。mutexが本当に高くつくのは競合時、待機がカーネル(futex、第9.2節)に落ちてからです。

**第三に、右下の太字。** relaxed版がM2の非競合でだけ**2.7倍**速くなり、x64では1nsも変わっていません。第3章の知識で謎解きはもうできるはずです(x64ではseq_cstなRMWもrelaxedなRMWも同じ`lock add`になる――第3.5.2節)。ARMでは命令が変わります(`ldaddal`→`ldadd`)。正式な回収は第7〜8章で行いますが、**「x64での計測はメモリオーダー選択の検証にならない」**という本書の警句が、性能面でも成立することを示す最初のデータです。

> **観測事実16**: アトミックカウンタの支配的コストは操作の種類(mutex/fetch_add)ではなく**競合**であり、4スレッド競合で約8倍悪化した。正体は第4章のキャッシュライン争奪であり、`alignas`では直せない「本物の共有」である。

最後に、fetch_addが第1章の「消失」を起こさない理由を契約の言葉で一度だけ厳密に述べておきます。RMW操作には「**変更順序(第5.3節)上で自分の直前に当たる値を読む**」という特別な保証があります。読む→足す→書くの3手が、変更順序という1本の履歴に割り込みなしで刻まれる。ゆえに200万回のfetch_addは変更順序上に200万個の要素を作り、1つも重なりません。この保証がRMW**族**にしかないこと――load()とstore()を別々に呼んでも決して合成されないこと――を、6.5節まで覚えておいてください。

## 6.2 【コード】compare_exchange_weakでスピンロックを自作する(最小8行)

道具箱の底に、いちばん強力で、いちばん癖のある道具が残っています。**compare_exchange**(比較交換、通称**CAS**)です。意味論を日本語で書き下すとこうなります。

> `a.compare_exchange_weak(expected, desired)`は、次を**1つの不可分なRMW**として行う:
> aの現在値が`expected`と等しければ、aに`desired`を書き込み、**true**を返す。
> 等しくなければ、aは変更せず、**`expected`にaの現在値を書き戻して**、falseを返す。

fetch_addが「足し算」という決まった変換しかできないのに対し、CASは「**この値だったら、これに変えろ**」という条件付き書き込みです。任意の変換をアトミックに実行する万能ネジ回しであり、第10章のロックフリー構造はすべてこの1操作の上に建ちます。まず、いちばん小さな実用品を作って手に馴染ませましょう。スピンロックです。

**リスト6-2: spinlock.cpp ― CASによる最小スピンロック**

```cpp
class Spinlock {
    std::atomic<bool> locked{false};
public:
    void lock() {
        bool expected = false;
        while (!locked.compare_exchange_weak(expected, true,
                                             std::memory_order_acquire)) {
            expected = false;      // ← この1行を消すと壊れる(後述)
        }
    }
    void unlock() {
        locked.store(false, std::memory_order_release);
    }
};
```

論理はこうです。「lockedが**false(空いている)だったら**、true(使用中)に変えろ」。成功したら関門通過。失敗したら(=誰かが使用中なら)成功するまで回る。unlockはfalseを書き戻すだけ。メモリオーダーにacquire/releaseを指定しているのは、第5.4節で確認した「mutexと同じ形のロープ」を張るためです(mutexのlockがacquire・unlockがreleaseの品詞であることは観測事実15で実物確認済みですね。正式な意味論は第7章)。第1章のカウンタをこのSpinlockで守って動かすと、両アーキテクチャで正答し、TSanも沈黙します。

さて、コメントを付けた1行――`expected = false;`――が、CAS最大の初見殺しです。意味論の太字部分を思い出してください。CASは失敗時に`expected`を**現在値で上書き**します。ロックが塞がっていて失敗すると、expectedはtrueに書き換えられている。リセットせずにループすると、次の周回は「lockedが**trueだったら**trueに変えろ」というCASになり――これは高確率で**成功**してしまいます。何も変えない空振りの成功でtrueが返り、**ロックを取れていないのにlock()を通過**する。この「expected書き戻し」仕様は嫌がらせではなく、失敗のたびに現在値をload()し直す1操作を節約するための実戦的設計です(6.5節の汎用CASループでは、この書き戻しこそが主役になります)。

なお、この特定の用途(bool 1個の獲得)に限れば、CASより単純な道具でも書けます:`while (locked.exchange(true, acquire)) {}`――「問答無用でtrueを書き、**直前の値**がtrueだったら(=先客がいたら)回る」。こちらはTAS(test-and-set)ロックと呼ばれ、第9.1節でこのSpinlockともども俎上に載せ、競合下では両者とも**ひどい性能**であること(理由はもう推測がつくでしょう――全員が同じラインをRMWで叩き続けるからです)を測ってTTAS→バックオフへと改良していきます。この章では「動く最小品を自分の手で作った」ことだけ持ち帰ってください。

## 6.3 【コード】weak版とstrong版の失敗率をARM上で計測して違いを体感する(LL/SCの偽失敗)

ところで、リスト6-2でなぜ`compare_exchange_weak`を選んだのでしょう。`_strong`もあるのに。両者の仕様差はただ1点です。

> **weakは、値が`expected`と等しくても失敗してよい**(偽失敗、spurious failure)。strongは値が等しい限り必ず成功する。

「等しいのに失敗」とは奇妙な仕様です。こんな不確かな道具、誰が使うのか――例によって、仕様の奇妙さの裏にはハードウェアの都合があります。そして本書の読者はもう、その都合を実測できる腕を持っています。

種明かしを先にすると、犯人はARM系の伝統的なアトミック命令方式**LL/SC(Load-Linked/Store-Conditional)**です。ARMv8.0までのCASは、単一命令ではなく次の2命令の組で実現されていました。

```asm
retry:
    ldaxr  w0, [x1]        ; ロードし、このアドレスに「監視」を仕掛ける
    cmp    w0, w_expected
    b.ne   fail
    stlxr  w2, w_desired, [x1]   ; 監視が生きていれば書き込み成功(w2=0)
    cbnz   w2, retry             ; 監視が破られていたら失敗(w2=1)
fail:
```

`stlxr`(store-exclusive)は、`ldaxr`が仕掛けた監視が**破られていたら書き込みを放棄**します。監視は、他コアが同じラインに書いた場合はもちろん、**割り込み、コンテキストスイッチ、同一監視粒度内の無関係な書き込み、キャッシュラインの立ち退き**といった、値の変化と無関係な事情でも破られえます。これが偽失敗の物理的正体です。C++のweakは、この「stlxrの1回失敗」をそのまま呼び出し元に返すことを許す仕様であり、strongは「値が等しい限りretryループを回りきる」ことを処理系に義務付ける仕様――つまり**strong = weak + 再試行ループの糖衣**なのです。

一方、x64の`lock cmpxchg`は最初から単一命令で、偽失敗の概念そのものがありません。さらにARMもv8.1のLSE拡張で単一命令CAS(`cas`系)を手に入れました。すると面白い予言が立ちます:**偽失敗は「LL/SCでコンパイルされたARMバイナリ」でだけ観測され、x64とLSE版ARMでは1回も観測されないはず**。検証しましょう。

**リスト6-3: spurious.cpp ― 偽失敗の検出器(骨子)**

```cpp
// 8スレッドが同じカウンタをCASでインクリメントし合い、
// 「渡したexpectedのまま失敗した回数」= 偽失敗を数える
void worker() {
    int cur = ctr.load(std::memory_order_relaxed);
    for (long i = 0; i < N; ++i) {
        int want = cur;                    // これから渡すexpectedを控えておく
        if (ctr.compare_exchange_weak(cur, want + 1,
                                      std::memory_order_relaxed)) {
            cur = want + 1;
        } else {
            // 失敗。curにはCASが書き戻した現在値が入っている
            if (cur == want) ++local_spurious;   // 値は同じなのに失敗した!
            ++local_fail;
        }
    }
}
```

同じソースを3通りにビルドして比較します。ARM(AWS Graviton3、8スレッド)では、コンパイラフラグでLL/SC版とLSE版を作り分けられます。

```console
# ① ARM・LL/SC版(LSE拡張を封印してldaxr/stlxrを出させる)
$ g++ -std=c++20 -O2 -pthread -march=armv8-a spurious.cpp -o sp_llsc
# ② ARM・LSE版(単一命令casを使わせる)
$ g++ -std=c++20 -O2 -pthread -march=armv8.1-a spurious.cpp -o sp_lse
# ③ x64版
$ g++ -std=c++20 -O2 -pthread spurious.cpp -o sp_x64
```

逆アセンブルで①に`ldaxr/stlxr`、②に`cas`、③に`lock cmpxchg`が出ていることを確認してから(もはや本書の作法です)、実行します。

**表6-2: CAS試行の内訳(8スレッド×1000万回、筆者環境)**

| ビルド | 通常の失敗(値が変わっていた) | **偽失敗(値は同じなのに失敗)** |
|---|---|---|
| ① ARM・LL/SC | 61.3% | **1.84%** |
| ② ARM・LSE | 63.0% | **0%**(0回) |
| ③ x64 | 58.7% | **0%**(0回) |

予言どおりです。LL/SC版でだけ、全試行の約2%という**無視できない頻度**で偽失敗が起きています。値は正しかったのに、監視が破られただけで空振りした2%です。

> **観測事実17**: weakの偽失敗は空想上の免責条項ではなく、LL/SC方式のARMバイナリで約2%(8スレッド競合時・筆者環境)の頻度で実測される。x64とLSE版ARMでは0回。strongとは「この偽失敗を処理系側のループで隠蔽したもの」である。

実務の選択指針は、この実測から素直に導けます。**自分がどうせループで囲むならweak**――リスト6-2のスピンロックや6.5節の汎用CASループがそうで、偽失敗はループがもう1周するだけ、strongを使うと「処理系のループ」の外に「自分のループ」が重なる二重構造になるだけ損です。**1発勝負で成否を確定させたいならstrong**――「先着1名がこの初期化を実行する」のような、失敗の意味が「他者の成功」でなければならない場面です。そしてx64しか触らない開発者がこの使い分けに無頓着でいられたのは、③の行が示すとおり**両者の差が消えるアーキテクチャにいたから**にすぎません。

## 6.4 【コード】is_lock_freeを確認する ― ロックフリーでない場合に何が起きているか

`std::atomic<T>`のTは、実はintやboolに限らず、**trivially copyableなら任意の型**を入れられます。では`std::atomic<進捗レポート構造体>`と書いたとき、CPUに構造体まるごとのアトミック命令など無いのに、いったい何が起きるのでしょうか。まず尋問用のコードで各型の「素性」を吐かせます。

**リスト6-4: lockfree_check.cpp**

```cpp
#include <atomic>
#include <cstdio>

struct B8  { long a; };                // 8バイト
struct B16 { long a, b; };             // 16バイト
struct B24 { long a, b, c; };          // 24バイト

template <class T> void report(const char* name) {
    std::atomic<T> x{};
    std::printf("%-14s sizeof(atomic)=%2zu  always=%d  is_lock_free()=%d\n",
                name, sizeof(x),
                (int)std::atomic<T>::is_always_lock_free, (int)x.is_lock_free());
}

int main() {
    report<int>("int");
    report<long>("long");
    report<void*>("void*");
    report<B8>("B8 (8B)");
    report<B16>("B16 (16B)");
    report<B24>("B24 (24B)");
}
```

```console
# x64 (GCC 13)
int            sizeof(atomic)= 4  always=1  is_lock_free()=1
long           sizeof(atomic)= 8  always=1  is_lock_free()=1
void*          sizeof(atomic)= 8  always=1  is_lock_free()=1
B8 (8B)        sizeof(atomic)= 8  always=1  is_lock_free()=1
B16 (16B)      sizeof(atomic)=16  always=0  is_lock_free()=1   ← 揺れる(後述)
B24 (24B)      sizeof(atomic)=24  always=0  is_lock_free()=0   ← ここが本題
```

`is_lock_free()`がtrueの型は、これまで見てきたとおりハードウェアのアトミック命令に直接対応します(**ロックフリー**)。16バイトは境界線上の住人で、x64の`cmpxchg16b`やARMの`casp`という倍幅命令の有無、コンパイラのフラグ(`-mcx16`)と方針次第で判定が揺れます(`always=0`なのに実行時`=1`という上の出力自体が、その揺れの現れです)。この住人は第10.5節、ABA対策のタグ付きポインタで主役になるので、そこで再訪します。

本題は最下行、**falseの型に何が起きているか**です。逆アセンブルすると、B24へのstoreはアトミック命令ではなく関数呼び出し`call __atomic_store`になっており、その先はコンパイラ付属ライブラリ(libatomic)に飛びます。libatomicの中身は、乱暴に要約すればこうです:

> **アドレスをハッシュした先の、グローバルなロック表のロックを取り、普通のmemcpyをして、ロックを解放する。**

つまり`std::atomic<B24>`は「アトミック風の見た目をした、**隠しmutex付き構造体**」です。仕様違反ではありません(規格はアトミック性を保証しており、実装手段は問わない)が、この隠しロックは3つの実害を持ちます。**第一に性能**――計測すると、B24のstoreはlongのstoreの十数倍のコストになり、しかも無関係な変数どうしがロック表のハッシュ衝突で待たされる可能性すらあります。**第二にアドレス自由性の喪失**――ロック表は**そのプロセスの**グローバル変数なので、共有メモリ越しに複数プロセスで使うと、各プロセスが**別々のロック**で同じデータを守る茶番になり、アトミック性が壊れます。**第三にシグナル安全性の喪失**――ハンドラ内でロック保持中の自分自身とデッドロックしえます。

> **観測事実18**: `is_lock_free()`がfalseの`std::atomic<T>`は、隠しロック(libatomicのアドレス別ロック表)で実装される。単一プロセス内の正しさは保たれるが、性能・プロセス間共有・シグナル安全性を静かに失う。**atomicと書いてあってもatomic命令とは限らない**――確認する方法が`is_lock_free()`である。

実務指針:大きな状態を「アトミックに」扱いたくなったら、`atomic<Big>`に頼る前に、(a) 状態をポインタ1本に逃がして`atomic<State*>`を差し替える(第10章のロックフリー構造の常套手段。ただしABAと回収問題が付いてきます)、(b) 素直にmutexで守る(隠しロックより、見えるロックのほうが常にましです)、(c) 8/16バイトに詰める、を検討してください。また、C++20の`std::atomic_ref<T>`を使うと「普段は非アトミックに使い、特定区間だけアトミック扱いする」ことができますが、これも`is_lock_free`の事情はまったく同じである上、**同一オブジェクトへの生アクセスとatomic_refアクセスの併存期間は競合になる**という新しい罠を持ち込みます。道具が増えても、5.1節の定義が審判であることは変わりません。

## 6.5 【コード】アトミックのつもりでアトミックでないコード ― `a = a + 1`と`a += 1`の違いをTSanで暴く

章の締めくくりは、第1章の章末演習3の答え合わせです。あのとき「atomicなのに壊れる」と予告した1行を、いま解剖します。

**リスト6-5: not_atomic.cpp ― 見た目の同義語、意味の別物**

```cpp
std::atomic<int> a{0};
constexpr long N = 1'000'000;

void worker_bad()  { for (long i = 0; i < N; ++i) { a = a + 1; } }   // 版X
void worker_good() { for (long i = 0; i < N; ++i) { a += 1;    } }   // 版Y
```

数学なら同じ式です。2スレッドで実行します。

```console
$ ./not_atomic --bad          # 版X
a = 1372089 (期待値 2000000)      # 消失!第1章の再来
$ ./not_atomic --good         # 版Y
a = 2000000 (期待値 2000000)
$ ./not_atomic_tsan --bad     # 版XをTSanにかける
(沈黙)                            # ← 検出されない!
```

3つめの結果が、この節の核心です。壊れているのに、私たちの検算器は沈黙しました。理由は第5章の定義から一直線です:版Xを構成する操作は**すべてアトミック操作**なので、データ競合の定義(「少なくとも一方が非アトミック」)に**該当しません**。これはリスト2-2のrelaxed MPと同じ、「未定義動作ではないが、期待どおりには動かない合法プログラム」――**TSanの管轄外で壊れるコード**の、もっとも身近な標本です。

では版Xは何をしていたのか。C++の文法に沿って分解すると、`a = a + 1`は(1)`a.operator int()`=**load**、(2)レジスタで+1、(3)`a.operator=(int)`=**store**、という**独立した2つのアトミック操作**です。逆アセンブルで確認します(x64、-O2)。

```asm
; 版X: a = a + 1
mov    eax, DWORD PTR a[rip]      ; ① アトミックload(素のmov)
add    eax, 1                     ; ②
xchg   eax, DWORD PTR a[rip]      ; ③ アトミックstore(seq_cstなのでxchg!)

; 版Y: a += 1
lock add DWORD PTR a[rip], 1      ; 全体で1つのRMW
```

版Xの3命令の並びに、既視感があるはずです。**第1.3節の「読む・足す・書く」と同じ形**です。①と③はそれぞれ単体では立派なアトミック操作ですが、①と③の**あいだ**には何の保証もなく、他スレッドのstoreが割り込めば第1章とまったく同じ機構でインクリメントが消失します。6.1節の末尾に立てた札を回収しましょう――**「変更順序上の直前の値を読む」というRMWの保証は、fetch_add・exchange・CASといったRMW族の1回の呼び出しにだけ付く。loadとstoreを別々に呼んで、あとから接着することはできない**。アトミック性は**変数の属性ではなく、操作1回ごとの属性**なのです。

ついでに③の`xchg`にも注目を。storeのデフォルトはseq_cstなので、第3.5.2節・第8.3節で学ぶとおりx64では暗黙バリア付きの`xchg`になります。版Xは、壊れているくせに版Yよりバリアを多く払っているという、二重に残念なコードだったわけです。

では、fetch_mulが存在しない「x = x × 2」のような変換をアトミックにしたいときはどうするのか。ここで6.2〜6.3節の万能ネジ回しが汎用の型として登場します。

**リスト6-6: casloop.cpp ― read-modify-CASループ(本書後半の基本イディオム)**

```cpp
int cur = a.load(std::memory_order_relaxed);       // ① 現在値を観測
while (!a.compare_exchange_weak(cur, cur * 2)) {   // ② 「①のままなら×2」を試みる
    // 失敗:curはCASが現在値に書き戻してくれている(6.2節の仕様が
    // ここでは罠ではなく機能になる)。書き戻された新しい観測値で再試行。
}
```

論理はこうです。「読んだ値」を土台に新値を計算し、CASで「**読んだときのままなら**書く」。誰かに先を越されていたら(=値が変わっていたら)CASが失敗し、そのとき`expected`書き戻し仕様が最新値を無料で届けてくれるので、計算からやり直す。割り込みを**防ぐ**のではなく、**割り込まれたら検出してやり直す**――楽観的並行制御と呼ばれるこの発想が、ロックという悲観的な発想の対極にあり、第10章のTreiberスタックもMichael-Scottキューも、すべてこのループの変奏です(そして「値が同じなら割り込まれていない」というこのループの暗黙の仮定が破れる瞬間――ABA問題――が第10.4節で牙を剝きます)。

> **観測事実19**: `a = a + 1`は独立な2つのアトミック操作(load+store)に分解され、更新を消失させる。しかも全操作がアトミックゆえデータ競合ではなく、**TSanは沈黙する**。RMWの不可分性はRMW族の呼び出し1回にのみ宿る。汎用の合成手段はread-modify-CASループである。

コードレビューでの実践則を添えておきます。`std::atomic`変数に対する`a = a + 1`、`a = a | flag`、`if (a) a = ...`(検査と更新の分離)、`tmp = a; ...; a = tmp;`は、すべてこの節の再演です。「atomicなのだから何をしても安全」という思い込みは、「操作単位で考える」習慣に置き換えてください。そしてTSanが黙るこの種のバグをどう機械検査するか――全実行順序を網羅するモデル検査器(Relacy)という次の武器を、第11.3節で手に入れます。

### 第6章のまとめ

- `std::atomic`のAPIはload/store/exchange/fetch系/CASのRMW族で構成され、コピー不可という設計自体が「不可分にできない操作を提供しない」方針の現れ(6.1節)。
- **観測事実16**: カウンタの支配的コストは競合(=ライン争奪)であり4スレッドで約8倍悪化。relaxedの恩恵はARMでのみ現れ、x64計測はオーダー選択の検証にならない(第7〜8章へ)。
- CASは「この値だったらこれに変えろ」という条件付き書き込み。失敗時のexpected書き戻し仕様は、スピンロックでは罠(リセット忘れ)、CASループでは機能(最新値の無料配達)になる(6.2、6.5節)。
- **観測事実17**: weakの偽失敗はLL/SC版ARMで約2%実測され、x64/LSEでは0。strong=weak+隠しループ。ループで囲むならweak、1発勝負はstrong(6.3節)。
- **観測事実18**: `is_lock_free()==false`のatomicは隠しロック(libatomic)実装。性能・プロセス間共有・シグナル安全性を静かに失う。大きな状態はポインタ差し替えか、見えるmutexへ(6.4節)。
- **観測事実19**: `a = a + 1`はload+storeに分解されて更新を消失させ、しかも競合ではないのでTSanは沈黙する。アトミック性は操作ごとの属性。汎用合成はread-modify-CASループ=第10章への入口(6.5節)。

次の第7章では、この章で棚上げし続けた最後の引数――メモリオーダー――に正面から向き合います。seq_cstから始めて、acquire/release、relaxedへと**一段ずつ緩めては壊し**、各オーダーの保証の輪郭を境界の内外両側からなぞります。表6-1の右下の太字(M2でのみ2.7倍)の意味も、そこで完全に回収されます。
