# 第3章 TSOを解剖する ― x64はなぜ「強い」のか

第2章の終わりに、私たちは実験データから1つの仮説を立てました。「x64は4種類の並べ替えのうちStore→Loadだけを許すのではないか」――この章の仕事は、この仮説を**単なる観測の要約から、まだやっていない実験の結果まで予測できる機械モデル**へ鍛え上げることです。

良い理論は暗記を減らします。この章を終えると、「x64でこのコードは壊れるか?」という問いに、リオーダリング表を暗記していなくても、頭の中で小さな機械を動かすだけで答えられるようになります。そしてその機械に**存在しない部品**を確認することで、ARMがなぜ・どのように違うのかも一望できます。

---

## 3.1 TSOの定義 ― 「全ストアに全コアが合意する単一の順序がある」とはどういうことか

TSOは Total Store Order の略です。直訳すれば「ストアの全順序」。この名前自体が定義の核心を言い当てています。

> **TSOの中核的な約束**: システム内で発生したすべてのストアについて、**全コアが合意する1本の順序(全順序)が存在する**。どのコアから観測しても、ストアたちはこの1本の順序と矛盾しない形で見える。さらに、各コアのストアはプログラム順のままこの全順序に組み込まれる。

「全順序が存在する」のありがたみは、存在しない世界を想像すると分かります。もしストアに全員が合意する順序がなければ、「コアAはx=1がy=1より先に起きたと観測し、コアBは逆を観測する」という、**歴史がコアごとに分岐する世界**になります(この分岐を直接検出するのが3.6.3節のIRIWテストです)。TSOの世界では歴史は1本です。

では、TSOの世界でなぜ第2章のSBテスト(両方0)は起きたのでしょうか。歴史が1本なら、逐次一貫性(sequential consistency、SC)――「全操作を1本に並べたインターリーブで全実行を説明できる」という最強の保証――と同じでは?

違いはただ1点、**自分のストアがその全順序に「載る」タイミングと、自分の後続ロードの実行タイミングのずれ**にあります。TSOでは、コアは自分のストアが全順序に組み込まれる(=メモリに反映される)のを**待たずに**、次のロードを実行してよいのです。これがStore→Loadリオーダリングの正体であり、SCとTSOを分かつ唯一の隙間です。

言葉ではまだ曖昧です。次節で、この約束をそのまま形にした「機械」を組み立てます。

## 3.2 TSOの機械モデル ― 各コアにFIFOストアバッファが1本ずつある世界

TSOは、次のおもちゃのような機械として完全に記述できます。部品は3つだけです。

```
  コア0                コア1                コア2
 ┌──────┐            ┌──────┐            ┌──────┐
 │ 実行 │            │ 実行 │            │ 実行 │
 └──┬───┘            └──┬───┘            └──┬───┘
    │store              │store              │store
 ┌──▼───┐            ┌──▼───┐            ┌──▼───┐
 │FIFO  │            │FIFO  │            │FIFO  │   ← 各コア専用の
 │ストア │            │ストア │            │ストア │      ストアバッファ
 │バッファ│            │バッファ│            │バッファ│      (他コアからは見えない)
 └──┬───┘            └──┬───┘            └──┬───┘
    │ドレイン(FIFO順)   │                   │
 ┌──▼───────────────────▼───────────────────▼───┐
 │            共有メモリ(全コア共通・1つ)          │
 └──────────────────────────────────────────────┘
```

**機械の動作規則(これがTSOのすべてです):**

1. **ストア**: コアがストアを実行すると、値は共有メモリに直接書かれるのではなく、**自分のストアバッファの末尾に積まれる**。
2. **ドレイン**: ストアバッファは、**先入れ先出し(FIFO)の順序で**、任意のタイミングで中身を共有メモリへ吐き出す(ドレインする)。いつ吐き出すかは機械の気分次第。
3. **ロード**: コアがロードを実行するときは、まず**自分のストアバッファ**を新しい方から検索する。同じアドレスへのストアが見つかればその値を使う(**ストアフォワーディング**、3.3節)。見つからなければ共有メモリから読む。**他コアのストアバッファの中は決して見えない。**
4. **ロードとストアの実行はプログラム順**: 各コアは命令をプログラム順に実行する。並べ替えはこの機械のどこにも明示的には存在しない。

規則4に注目してください。この機械は命令を1つも並べ替えていません。それなのに、これから見るとおり、外から観測するとStore→Loadリオーダリングが「起きたように見える」のです。リオーダリングとは命令の入れ替えではなく、**ストアバッファという待合室の副作用**だ――これがこの章最大の発見です。

### 3.2.1 【コード】SBテストをストアバッファモデルの図上でトレースし、「両方0」が導出できることを確認する

第2章のリスト2-1、SBテストをこの機械の上で動かします。トレース対象は本体の4命令だけです。

```text
コア0: x = 1;  r1 = y;        コア1: y = 1;  r2 = x;
```

機械の状態を「(コア0のバッファ | 共有メモリ | コア1のバッファ)」で追います。初期状態は`x=0, y=0`、両バッファ空です。

```
ステップ  操作                          コア0バッファ   共有メモリ      コア1バッファ
------  --------------------------   ------------   ------------   ------------
  0     (初期状態)                     []             x=0, y=0       []
  1     コア0: store x=1  → 規則1     [x=1]          x=0, y=0       []
  2     コア1: store y=1  → 規則1     [x=1]          x=0, y=0       [y=1]
  3     コア0: load y     → 規則3
         自バッファにyは無い →
         共有メモリから読む → r1 = 0   [x=1]          x=0, y=0       [y=1]
  4     コア1: load x     → 規則3
         自バッファにxは無い →
         共有メモリから読む → r2 = 0   [x=1]          x=0, y=0       [y=1]
  5     コア0バッファがドレイン → 規則2  []             x=1, y=0       [y=1]
  6     コア1バッファがドレイン → 規則2  []             x=1, y=1       []
```

**r1 = 0, r2 = 0。** 導出できました。各コアは自分の命令をプログラム順どおり律儀に実行しています。犯人は、ステップ3〜4の時点で両方のストアがまだ**待合室(バッファ)に滞留していた**こと。互いのバッファの中は見えない(規則3)ので、両者とも古い共有メモリを読んだのです。

このトレースを、モデル検証ツールで機械的に確認することもできます。herd7(第11.2節で本格導入します)にx86モデルとSBテストを与えると、全実行を列挙して(0,0)を含む4通りすべてが許容(Allowed)と判定されます。手トレースとツールの答え合わせは良い習慣なので、この章の演習にも入れてあります。

そして重要な系がひとつ。**このずれはコア自身には見えません。** コア0にとって自分のストアx=1は、規則3のフォワーディングによって直後のロードからちゃんと見えます。ずれが観測できるのは**他コアとの突き合わせ**をしたときだけ。第2.4節で「単一コアではCPUの並べ替えは原理的に起こりえない」としてコンパイラを現行犯逮捕できたのは、この性質のおかげだったのです。

### 3.2.2 【コード】MPテストを同じモデルでトレースし、TSOでは壊れようがないことを証明的に確認する

次はMPテスト(リスト2-2)です。x64で10億回まわして一度も壊れなかった、あの実験です。

```text
コア0(送信): data = 42;  ready = 1;
コア1(受信): while (ready == 0) {}   r = data;
```

今度は「壊れるトレースを探す」のではなく、「**壊れるトレースが存在しない**ことを規則から示す」ことを試みます。壊れるとは、コア1が`ready == 1`を観測した後に`data == 0`を読むことです。

コア1が`ready == 1`を読めた経路を規則3で場合分けします。コア1は`ready`に書いていないので自バッファからのフォワーディングはありえず、**共有メモリから読んだ**の一択です。つまりその時点で、コア0のストア`ready = 1`は**ドレイン済み**です。

ここで規則2(FIFO)が効きます。コア0のバッファには`data = 42`が`ready = 1`より**先に**積まれました(規則4:プログラム順)。FIFOバッファは追い越しを許さないので、`ready = 1`がドレイン済みなら**`data = 42`は必ずそれ以前にドレイン済み**です。よって共有メモリの`data`はすでに42。

最後にコア1のロード順です。規則4により、コア1は`ready`のロード(ループの最終回)を終えてから`data`のロードを実行します。その時点の共有メモリの`data`は42であり、コア1自身は`data`に書いていないのでフォワーディングで古い値を拾う経路もありません。ゆえに**r = 42。壊れるトレースは存在しません。**

```
壊れるために必要なこと           TSO機械で可能か
----------------------------  --------------------------------------
送信側: readyがdataを追い越して   不可能(規則2: バッファはFIFO)
        先にメモリに到達する
受信側: dataのロードがreadyの     不可能(規則4: ロードはプログラム順。
        ロードより先に実行される           バッファが関与するのはストアだけ)
```

第2章の観測事実5「x64でMPは10億回壊れなかった」は、幸運でも統計的偶然でもなく、**この機械の構造的必然**でした。同時に、この証明は逆向きにも読めます。ARMでMPが壊れたということは、**ARMの機械はこの2つの「不可能」のどちらか(実は両方)を可能にする構造を持っている**ということです。それが3.6節の主題です。

## 3.3 ストアフォワーディングの観測

規則3の前半――「ロードはまず自分のバッファを検索する」――は、ここまで脇役でした。しかしこのストアフォワーディングこそ、TSOを逐次一貫性から隔てる第2の(そして最後の)要素です。

### 3.3.1 【コード】自分の書き込みだけが早く見えるコード ― n6リトマステストの実装

フォワーディングの効果を単独で観測するのは一工夫要ります。自分のストアが自分に早く見えること自体は、単一スレッドでは「当たり前」にしか見えないからです。他コアとの突き合わせで初めて異常が浮かび上がる、歴史的に有名なテストがあります。x86-TSOモデル(3.4節)の原論文に登場する **n6** です。

```text
初期状態: x = 0, y = 0

コア0:                     コア1:
  x = 1;                     y = 2;
  r1 = x;   ← 自分で書いたxを読む
  r2 = y;                    x = 2;

問い: 終了時に r1 == 1 かつ r2 == 0 かつ x == 1(!)はありうるか?
```

奇妙さを味わってください。r2 == 0ということは、コア0のロード時点でコア1のy = 2は未反映、つまり**コア1はまだ何もメモリに書いていない**ように見えます。ならばコア1の2つのストア(y=2、x=2)は両方ともコア0の観測より「後」のはず。後から`x = 2`が書かれたのなら、最終的な`x`は2になるはずです。ところが最終値が**1**――時系列がねじれています。

**リスト3-1: n6.cpp(ハーネスは第2章と共通。テスト本体と判定部のみ示す)**

```cpp
// コア0のテスト本体
x.store(1, memory_order_relaxed);
r1 = x.load(memory_order_relaxed);   // 自分のストアを読み返す
r2 = y.load(memory_order_relaxed);

// コア1のテスト本体
y.store(2, memory_order_relaxed);
x.store(2, memory_order_relaxed);

// mainの判定(両スレッド完了後)
if (r1 == 1 && r2 == 0 && x.load(memory_order_relaxed) == 1) {
    ++weird;
}
```

x64で実行します。

```console
$ g++ -std=c++20 -O2 -pthread n6.cpp -o n6
$ ./n6
ねじれた結果が 1471 / 1000000 回観測されました
```

観測されました。私たちのストアバッファ機械でトレースすると、種明かしは簡単です。

```
ステップ  操作                              コア0バッファ  共有メモリ       コア1バッファ
------  ------------------------------   -----------   -------------  -----------
  1     コア0: store x=1                  [x=1]         x=0, y=0       []
  2     コア0: load x → 規則3前半:
         自バッファにx=1を発見!
         → フォワーディングで r1 = 1       [x=1]         x=0, y=0       []
  3     コア0: load y → 共有メモリ → r2=0  [x=1]         x=0, y=0       []
  4     コア1: store y=2, store x=2       [x=1]         x=0, y=0       [y=2, x=2]
  5     コア1バッファがドレイン(FIFO)      [x=1]         x=2, y=2       []
  6     コア0バッファがドレイン            []            x=1, y=2       ← x=1が後勝ち!
```

ポイントはステップ2です。コア0は、**まだ世界に公開されていない自分のストア**を読みました。r1 = 1という観測は「x = 1がすでに起きた世界」の証言ですが、その世界はコア0の頭の中(バッファ)にしか存在していません。各コアが「自分の書き込みだけ先に反映された私家版の歴史」を見ている――フォワーディングとはそういう現象です。

> **観測事実7**: x64では、コアは自分のストアだけを他コアより早く観測できる(n6のねじれ)。「全コアが合意する1本の歴史」という3.1節の約束には、「ただし各コアは自分のストアに限り、歴史に載る前に読める」という但し書きが付く。

### 3.3.2 「TSO = 逐次一貫性 + ストアバッファ + フォワーディング」という等式

これで部品が出揃いました。この章の機械は、逐次一貫性の機械(共有メモリに全コアが直接読み書きする世界)に対して、**FIFOストアバッファ**と**フォワーディング**というたった2つの部品を足したものです。そして:

- SBテストの(0,0) → ストアバッファ(滞留)で説明された(3.2.1)
- MPテストの不壊 → バッファのFIFO性+ロードのプログラム順で証明された(3.2.2)
- n6のねじれ → フォワーディングで説明された(3.3.1)
- 第2章のリオーダリング表でx64が許すのはStore→Loadだけ → 「後続ロードはバッファのドレインを待たない」ことの言い換え

**x64のメモリモデルに関して覚えるべきことは、この機械1台で全部です。** 以後、本書で「TSOでは〜」と述べるときは、常にこの機械での導出可能性を意味します。

## 3.4 x86-TSO形式モデル ― Sewellらの研究とIntel/AMDマニュアルの読み方

ここまで「機械」と呼んできたモデルには正式な出自があります。少しだけ歴史の話をします。実は2000年代まで、**x86のメモリモデルの厳密な定義は存在しませんでした**。IntelとAMDのマニュアルは自然言語の箇条書き(「ロードは他のロードと並べ替えられない」等)で挙動を説明しており、版によって記述が揺れ、あるときはn6のような実機で観測できる挙動を禁止しているように読める記述すらありました。「実機で起きることをマニュアルが禁止している」――これでは正しいコードの書きようがありません。

この混乱に決着をつけたのが、ケンブリッジ大学のPeter Sewellらのグループが2010年前後に発表した **x86-TSO** モデルです。彼らは(1)本章の機械モデルとまったく同じ「抽象機械」による定義と、(2)数学的な公理による定義の2本立てでx86の挙動を定式化し、両者が等価であることを証明し、さらに大量のリトマステストを実機で走らせてモデルと突き合わせました。本章のn6も、彼らが「ベンダー文書の記述では説明できない実機挙動」の証拠として提示したテストです。現在のIntel SDM(Software Developer's Manual)Vol.3の「Memory Ordering」節の記述は、実質的にこのx86-TSOと整合するものになっています。

実務家にとっての教訓は2つです。第一に、**マニュアルの自然言語記述を読むときは、背後にx86-TSO機械を置いて読む**と迷子になりません。たとえばSDMの「Loads are not reordered with older stores to the same location」という一文は、機械の規則3(フォワーディング)の言い換えです。第二に、この「厳密なモデル+実機テストによる検証」という方法論はアーキテクチャを問わず標準になっており、ARMも後に同じ道(公理的モデルの公開とherdツールでの検証)をたどりました。第11.2節で使うherd7は、この研究系譜の直系の道具です。

## 3.5 TSOが保証しないもの

機械モデルが手に入ったので、今度は**制御**の話ができます。TSOが唯一許す隙間――ストアバッファの滞留――を、必要なときに閉じる手段がx64には2系統あります。実験で確かめましょう。

### 3.5.1 【コード】Store→Loadリオーダリングを止めるMFENCEの効果を実測する

`mfence`命令は「これ以前の全メモリ操作が完了する(ストアバッファがドレインされる)まで、これ以降のメモリ操作を始めない」というバリアです。C++からは`std::atomic_thread_fence(std::memory_order_seq_cst)`がx64ではこの命令(または同等の命令)にコンパイルされます。SBテストのストアとロードの間に挟んでみます。

Clang 21からlock orに変更
MSVC 2019ではxchg
16.1でlock cmpxchgに
16.7でlock incに

**リスト3-2: sb_fence.cpp(リスト2-1との差分のみ)**

```cpp
// コア0のテスト本体
x.store(1, memory_order_relaxed);
std::atomic_thread_fence(std::memory_order_seq_cst);   // ← 追加
r1 = y.load(memory_order_relaxed);

// コア1も対称に fence を追加
```

```console
$ g++ -std=c++20 -O2 -pthread sb_fence.cpp -o sb_fence
$ objdump -d sb_fence | grep -A3 mfence      # まず本当にmfenceが出ているか確認
    mov    DWORD PTR x[rip], 1
    mfence
    mov    eax, DWORD PTR y[rip]
$ ./sb_fence
(r1,r2)=(0,0) が 0 / 1000000 回観測されました
```

100万回中3万回出ていた(0,0)が、完全に消えました。機械モデルでの解釈は明快です。mfenceはロードの実行前にバッファのドレインを強制するので、ステップ3(3.2.1のトレース)の時点で`x = 1`は必ず共有メモリに到達済み。もう(0,0)を導出する経路がありません。

タダではないことも計測しておきます。テストハーネス全体の実行時間比較です(筆者のx64環境)。

```console
$ time ./sb          # fenceなし
real    0m0.71s
$ time ./sb_fence    # fenceあり
real    0m1.43s
```

mfence1個あたりに換算するとおよそ30〜50サイクル。ストアバッファという「非同期化装置」を同期的に空にする対価です。x64のseq_cstが高くつく理由(第8.3節)の正体がこれです。

### 3.5.2 【コード】LOCKプレフィックス命令が暗黙のフェンスになることの確認実験

もう1系統は、第1.5節で出会った`lock`プレフィックスです。`lock add`のようなロック付きRMW命令は、アトミック性の保証に加えて、**mfenceと同等の全順序バリア効果**を暗黙に持ちます。SBテストのストアを`exchange`(x64では`xchg`命令になり、メモリオペランドの`xchg`は`lock`が暗黙に付きます)に置き換えて確かめます。

**リスト3-3: sb_xchg.cpp(差分のみ)**

```cpp
// コア0のテスト本体: store を exchange に変更(fenceは無し)
x.exchange(1, memory_order_relaxed);    // relaxed指定でも命令はxchg
r1 = y.load(memory_order_relaxed);
```

```console
$ ./sb_xchg
(r1,r2)=(0,0) が 0 / 1000000 回観測されました
```

こちらでも(0,0)は消滅します。**メモリオーダー指定はrelaxedのまま**なのに、です。C++の意味論としてはrelaxedなRMWに順序保証はありませんが、x64という**特定のターゲット上では**、RMWを実現する`lock`命令の副作用としてバリアが付いてくる――これは「TSOへのただ乗り」のさらに一段深い形、「**lock命令の副作用へのただ乗り**」です。このコードをARMに持っていけば、relaxedなRMW(`ldadd`等)にバリア効果はなく、(0,0)は復活します(章末演習3)。

> **観測事実8**: x64でストアバッファの隙間を閉じる手段は、mfence(明示バリア)とlock付きRMW(暗黙バリア)の2系統。どちらもSBの(0,0)を完全に消すが、数十サイクルの対価を取る。

第8章でC++のメモリオーダーとx64命令の対応表を作るとき、この2系統が`seq_cst`ストアの2つの実装戦略(`mov`+`mfence` vs `xchg`)として再登場します。

## 3.6 TSOではないアーキテクチャ ― ARMの弱いモデルとの対比

ここからは、私たちの機械モデルが**通用しない**世界の話です。

### 3.6.1 ARMには「全員が合意するストア順序」を待つ義務がない ― 4種類のリオーダリングの許容

ARM(AArch64)のメモリモデルを、TSO機械との差分で捉えます。決定的な違いは2つです。

**第一に、ストアバッファ相当の機構がFIFOである義務がありません。** さらにロードも、先行する別アドレスへのロード・ストアの完了を待たずに実行できます。結果として、依存関係もバリアもない限り、**4種類のリオーダリングすべてが許容**されます。3.2.2節のMP不壊証明を思い出してください。証明はFIFO性(送信側)とロードのプログラム順(受信側)の2本柱に立っていました。ARMはその**両方の柱を外している**のです。だからMPは壊れました。しかも理屈の上では送信側・受信側どちら単独でも壊せます。

**第二に――こちらは朗報ですが――ARMv8は「他コアへの見え方」については規律を保っています。** ARMv8のモデルは other-multi-copy-atomic(他マルチコピーアトミック)と呼ばれる性質を持ちます。「あるコアのストアが自分以外の誰かに見えた瞬間、他の全員にも見える(自分だけはフォワーディングで早く見てよい)」という保証です。実はこれ、3.3節でx64について確認した「但し書き付きの1本の歴史」とちょうど同じ強さです。歴史的には、ARMv7と初期のARMv8仕様はこの保証すらない(コアごとに歴史が分岐しうる)モデルでしたが、実装がその弱さを活用していなかったこともあり、2017年ごろの仕様改定でARMv8は現在の形に強化されました。つまりARMとx64の違いは「歴史が1本かどうか」では**なく**、「自分の操作がプログラム順で歴史に載るかどうか」に集約されたのです。

### 3.6.2 【コード】第2章のテストにバリアを片側ずつ立てて、壊している犯人を特定する

第2章で「MPの破れが送信側(Store→Store)の犯行か受信側(Load→Load)の犯行かは、まだ切り分けられない」と保留しました。回収します。ARMには半分だけのバリア――送信側専用の`stlr`(store-release)と受信側専用の`ldar`(load-acquire)――があるので、**片側ずつ柵を立てて、それでも壊れるか**を見ればよいのです。C++からはメモリオーダー指定で制御できます(意味論の正式な説明は第7章で行い、ここでは命令を出させる道具として使います)。

**リスト3-4: mp_variants.cpp ― 4通りのMPテスト(テスト本体の差分のみ)**

```cpp
// 変種A: 両側relaxed(第2章のオリジナル)
// 変種B: 送信側のみ release
data_.store(42, memory_order_relaxed);
ready.store(1,  memory_order_release);        // → stlr になる
// 受信側はrelaxedのまま

// 変種C: 受信側のみ acquire
while (ready.load(memory_order_acquire) == 0) {}  // → ldar になる
r = data_.load(memory_order_relaxed);
// 送信側はrelaxedのまま

// 変種D: 両側(release + acquire)
```

ARM(Apple M2)での結果です。逆アセンブルで変種Bに`stlr`、変種Cに`ldar`が出ていることを確認済みとします。

```console
$ ./mp_variants
変種A (relaxed/relaxed):  r != 42 が 203 / 1000000 回
変種B (release/relaxed):  r != 42 が  57 / 1000000 回   ← まだ壊れる!
変種C (relaxed/acquire):  r != 42 が  88 / 1000000 回   ← まだ壊れる!
変種D (release/acquire):  r != 42 が   0 / 1000000 回   ← 完治
```

決定的な結果です。**送信側を完全に柵で固めても(変種B)、受信側のロードが勝手に並べ替わって壊れる。受信側を固めても(変種C)、送信側のストアが追い越し合って壊れる。** つまりARMのMP破れは送信側・受信側の**両方が独立の犯人**であり、両方に柵を立てて初めて直る――3.6.1節の「両方の柱を外している」の実験的証明です。

> **観測事実9**: ARMではStore→Store(送信側)とLoad→Load(受信側)の並べ替えがそれぞれ独立に観測される。MPパターンの修正には、releaseとacquireの**ペア**が必要十分。

ついでにx64で同じ4変種を走らせると、全変種で0回です。当然です――TSO機械では変種Aですら壊れる経路がないのですから。**「変種AやB、Cで書かれた不完全なコードは、x64では検出不可能」**。本書が何度も鳴らす警鐘を、ここでもう一度鳴らしておきます。

### 3.6.3 【コード】IRIWテスト ― 「歴史は1本か」を直接問う

最後に、3.1節と3.6.1節で言葉だけで述べた「歴史の1本性」を直接テストします。**IRIW(Independent Reads of Independent Writes)** ――独立した2つの書き込みを、独立した2人の読者が読む――という4コアのテストです。

```text
初期状態: x = 0, y = 0

コア0:      コア1:      コア2:                 コア3:
  x = 1;      y = 1;      r1 = x;  r2 = y;       r3 = y;  r4 = x;

問い: r1==1, r2==0, r3==1, r4==0 はありうるか?
      (コア2は「xが先」、コア3は「yが先」と、歴史の順序で食い違う)
```

ただし1つ罠があります。読者側のロードが並べ替わってしまうと、歴史が1本でもこの結果は出てしまいます(単なるLoad→Load並べ替え)。問いたいのは歴史の分岐なので、**読者のロード順を柵で固定した上で**なお食い違うか、を見なければなりません。読者側を`acquire`にします。

**リスト3-5: iriw.cpp(テスト本体、読者はacquireで順序固定)**

```cpp
// コア2のテスト本体
r1 = x.load(memory_order_acquire);
r2 = y.load(memory_order_acquire);
// コア3は逆順(y→x)で同様に acquire
```

結果です(4コア以上の物理コアに各スレッドを配置)。

```console
# x64 (Core i7)
歴史の食い違いが 0 / 10000000 回観測されました
# ARM (Apple M2)
歴史の食い違いが 0 / 10000000 回観測されました
```

**どちらも0回。** x64はTSO(全順序の存在)ゆえに禁止。ARMv8もother-multi-copy-atomicゆえに禁止で、これは3.6.1節で述べた仕様改定の恩恵です。「観測されない」ことは一般に「禁止」の証明にはなりませんが、この2つについては形式モデル上も禁止(Forbidden)であることがherd7で確認できます(演習5)。

一方、世の中にはこの結果が**実機で観測されるアーキテクチャが実在します**。IBM POWERです。POWERは非マルチコピーアトミックなモデルを持ち、あるコアのストアが「近くのコアには早く、遠くのコアには遅く」届くことを許します。歴史がコアごとに分岐する世界は、思考実験ではないのです。x64→ARMの移植で学んだ教訓は、ARM→POWERでもう一段深くなる――本書はPOWERを深追いしませんが、リオーダリング表には刻んでおきます。

## 3.7 リオーダリング許容表の完成 ― TSO(x64)/ ARM / POWER / RISC-V

第2章の表2-1を、この章の理解で完成させます。この表は付録Bの早見表の原型であり、本書の残り全部で参照します。

**表3-1: 主要アーキテクチャのメモリモデル比較(通常のload/store、依存・バリアなしの場合)**

| 性質 | x86-64 (TSO) | AArch64 (ARMv8) | POWER | RISC-V (RVWMO) |
|---|---|---|---|---|
| Load→Load 並べ替え | 禁止 | **許容** | **許容** | **許容** |
| Load→Store 並べ替え | 禁止 | **許容** | **許容** | **許容** |
| Store→Store 並べ替え | 禁止 | **許容** | **許容** | **許容** |
| Store→Load 並べ替え | **許容** | **許容** | **許容** | **許容** |
| 自ストアの先読み(フォワーディング) | あり | あり | あり | あり |
| 歴史の1本性(他コアへの見え方) | 保証(MCA) | 保証(other-MCA) | **保証なし** | 保証(other-MCA) |
| SBテスト (0,0) | 観測される | 観測される | 観測される | 観測される |
| MPテスト破れ | **起きない** | 起きる | 起きる | 起きる |
| IRIW食い違い(読者順序固定) | 起きない | 起きない | **起きる** | 起きない |
| 主なバリア/順序付き命令 | mfence, lock | dmb, stlr/ldar | sync, lwsync | fence, .aq/.rl |

読み方の要点です。**Store→Loadの行だけは全員が「許容」**――ストアバッファはどのアーキテクチャも捨てられない、性能の生命線だからです。違いはそこから上、「どこまで追加の緩みを許すか」にあります。x64はゼロ。ARM/POWER/RISC-Vは全部。そして最下段のバリア列が、第8章で作る「C++メモリオーダー→機械語」対応表の材料になります。

RISC-Vについて一言。RVWMO(RISC-V Weak Memory Ordering)は2018年に**最初から形式モデルとして**設計されました。x86が実機と非公式文書の混乱をSewellらの事後的な定式化で収拾し(3.4節)、ARMが仕様改定でモデルを強化した(3.6.1節)歴史の教訓を、新しいアーキテクチャは設計段階で取り込んだわけです。

## 3.8 SPARC TSOという先例 ― 「TSO」という名前の由来と歴史

最後に、名前の出自を記しておきます。「TSO」という用語はx86のために作られたものではありません。初出は1990年代のSPARCアーキテクチャ仕様です。SPARC V8/V9の仕様書は、TSO(Total Store Order)・PSO(Partial Store Order)・RMO(Relaxed Memory Order)という**3段階のメモリモデルを形式的に定義し、選択可能なモード**として提供していました。ベンダー仕様が数学的なメモリモデル定義を持つこと自体が当時としては先進的で、実際に出荷されたSPARCマシンは事実上TSOモードで動いていました。

つまり歴史の順序はこうです。SPARCが「TSO」を形式的に定義し(1990年代)、x86は長らく無定義のまま「だいたいSPARC TSOと同じらしい」と経験的に知られ、Sewellらが2010年に「x86はまさにTSOである(+フォワーディングの精密化)」と定式化して現在に至る。私たちが第2章の実験データから立てた仮説は、30年がかりで整備されてきたこの系譜を、自分の手でなぞり直したものだったのです。

### 第3章のまとめ

- TSOとは「全ストアに全コアが合意する全順序が存在し、各コアの操作はプログラム順でそこに載る。ただし各コアは自分のストアに限り早く読める」という約束(3.1、3.3節)。
- その約束は「逐次一貫性+FIFOストアバッファ+ストアフォワーディング」という3部品の機械で完全に再現できる。SBの(0,0)は導出でき(3.2.1)、MPの不壊は証明できる(3.2.2)。**リオーダリングとは命令の入れ替えではなく、ストアバッファの滞留の副作用**。
- **観測事実7**: n6テストのねじれ=フォワーディングにより、各コアは自分のストアだけ早く見える。
- **観測事実8**: x64の隙間(Store→Load)はmfenceまたはlock付きRMWで閉じられる。対価は数十サイクル。
- **観測事実9**: ARMはFIFO性とロード順の両方の柱を外しており、MPは送信側・受信側それぞれ単独の犯行で壊れる。修正にはrelease/acquireのペアが必要。
- ARMv8はother-multi-copy-atomicであり「歴史の1本性」はx64と同格。IRIWはどちらでも起きない(POWERでは起きる)。x64とARMの真の違いは、自分の操作がプログラム順で歴史に載るか否か(3.6、3.7節)。
- ここから先、本書は「x64で壊れるか」をこの機械での導出可能性として、「ARMで壊れるか」を表3-1として答える。次の第4章では、この機械の物理的実体(実際のストアバッファ、キャッシュ、MESI)を覗く。
