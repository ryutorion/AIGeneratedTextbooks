# 第11章 検証ツールを使い倒す

第8章の表8-3で、本書はひとつの厳しい結論に達しました。**実行テストが検査できるのは「契約×対応表×アーキテクチャ」の積にすぎない**――積のどこかが過剰に強ければ(TSO、古典対応表の過剰包装)、契約の穴は隠れる。第10章の表10-1では、ARM実機で1億回まわしても観測できない契約違反(復路のrelaxed化)まで現れました。

この章は、その限界の**外側**を検証する装置の章です。装備は3つ。実行された1経路のhappens-beforeを監査する**TSan**(11.1節では、その検出限界を敵対的に攻めます)。極小のテストについて**全実行を数学的に列挙**するherd7と、同じテストを実機で大量試行するlitmus7(11.2節)。そして自作データ構造の**全スケジュールを網羅検査**するRelacy(11.3節)。後半では、これらを実務のパイプラインに組む設計(11.4節)と、実行テスト側の感度を極限まで高めるストレスの技法(11.5節)を扱います。「1億回に1回」を1分で仕留める、あるいは**1回もまわさずに**仕留める――それがこの章の到達点です。

## 11.1 【コード】ThreadSanitizerの検出限界を探る

TSanは第5.2節以来、本書の常備薬でした。薬の正しい使い方の最終段階は、**効かない病気を知る**ことです。まず効能の再確認から。TSanの検出原理は「実行中の全メモリアクセスにベクタークロックを付け、happens-beforeの通っていない衝突対を報告する」(観測事実13)。この原理から、強い保証がひとつ導けます:

> **TSanの報告に原則として誤報はない。** 報告された対は、その実行において本当にロープが無かった対である。「たまたま正しい値だったから無害」は反論にならない(第5.1節:競合は構造の欠陥)。報告は全件、直すべきものとして扱う。

(例外は、TSanに**見えない同期**――インラインasmのバリア、プロセス間共有メモリ、独自のsyscall同期――を使った場合だけです。その場合は`__tsan_acquire/__tsan_release`等の注釈で自作同期をTSanに教えます。「誤報だから抑止」の前に、必ず「TSanに見えているか」を疑ってください。)

では限界です。原理そのものから導かれる盲点が3種類あり、それぞれ実験で確認します。

**盲点1: 実行されなかったものは存在しない。** TSanが監査するのは**その1回の実行**で実際に起きたアクセスとスケジュールだけです。第5章演習3で確認したとおり、`if (rare_flag)`の中の競合は、フラグが立たない限り永遠に見えません。より陰湿なのは**スケジュール依存**です。競合する2アクセスが、その実行ではたまたま遠く離れて起きた場合――TSanのシャドウメモリは各メモリ位置につき有限個(実装上4スロット)のアクセス履歴しか持たないため、間に大量のアクセスが挟まると古い履歴が押し出され、検出を逃すことがあります。**TSanの沈黙は「この実行のこの経路には競合がなかった(たぶん)」であり、「このプログラムに競合がない」では決してない。** だからTSanジョブは、カバレッジの高いテストとストレス(11.5節)の上で走らせて初めて意味を持ちます。

**盲点2: 全部アトミックなら、壊れていても無罪。** 本書が3度踏んだ空白地帯です――`a = a + 1`(第6.5節)、TSOただ乗りのホットリロード(第7.8節)、SPSCのペイロードまでアトミックにした変種。競合の定義(5.1節)が「非アトミックを含む」を要求する以上、**全アトミック化された順序バグ・不変条件バグはTSanの管轄外**です。対策は道具ではなく規律で:**守られるデータは素の型のまま書く**(第5.2節の技法)。ペイロードをatomicで包んで警報を黙らせる行為は、第10.7節の抑止リストと同じ「警報機の電池抜き」です。

**盲点3: 偶然の同期が、競合を隠す。** 最後の盲点はデモする価値があります。デバッグの定番、printfを足すと再現しなくなるバグ――その一因はタイミング変化だと第1章で述べましたが、TSanに対しては**もっと直接的な毒**になります。

**リスト11-1: log_masks_race.cpp**

```cpp
int shared = 0;                        // 競合する素のint
std::mutex log_m;                      // ログ専用のmutex(sharedとは無関係のつもり)

void t1() {
    shared = 1;                                        // (A)
    { std::lock_guard g(log_m); std::puts("t1 done"); }   // ログ
}
void t2() {
    { std::lock_guard g(log_m); std::puts("t2 start"); }  // ログ
    int r = shared;                                    // (B)
}
```

(A)と(B)は明白な競合候補です。しかし、**この実行で**t1のunlock→t2のlockの順にログのmutexが渡ったなら、表5-2の辺により (A) →sb→ unlock →sw→ lock →sb→ (B) というロープが**偶然通ってしまい**、TSanは(正しく!)沈黙します。実測では、ログ行なしの版は100回中100回競合を報告し、ログ行ありの版は報告が確率的(ロックの獲得順次第)になりました。ログのmutexは`shared`を守る意図など皆無なのに、**その実行に限っては**本物のロープです。教訓:**「TSan用ビルドからログ・計測・診断の同期を疑え」**。TSanジョブは、本番同等の(むしろ同期を削った)構成で回すべきなのです。

> **観測事実37**: TSanは「その1実行のhappens-before監査人」である。報告に原則誤報はないが、(1) 実行されなかった経路・スケジュール、(2) 全アトミック化された順序バグ、(3) ログ等の偶然の同期に隠された競合、には盲目になる。沈黙は無罪の証明ではない。

## 11.2 【コード】herd7/litmus7 ― 形式モデルと実機の三点照合

第3.4節で紹介したSewell、Alglave、Marangetらの研究系譜は、実務者がそのまま使える道具一式(diyツールスイート)を残してくれました。中核が2つ:**herd7**は、リトマステストを形式メモリモデル(x86-TSO、AArch64、そしてC11のモデル)の上で**全実行列挙**し、指定した結果がAllowed(起こりうる)かForbidden(起こりえない)かを判定します。**litmus7**は、同じテストファイルから実機用の高性能ハーネス(第2章で手作りしたgo/done方式の、いわば工業製品版)を生成して大量試行します。インストールはopamから一行です(`opam install herdtools7`)。

テストは専用の小さな記法で書きます。第2章のSBを翻訳すると:

**リスト11-2: SB.litmus(x86版)**

```text
X86_64 SB
"第2章リスト2-1の形式化"
{ x=0; y=0; }
 P0          | P1          ;
 MOV [x],$1  | MOV [y],$1  ;
 MOV EAX,[y] | MOV EBX,[x] ;
exists (0:EAX=0 /\ 1:EBX=0)
```

初期状態、各プロセッサの命令列、そして`exists`節に「問題の結果」を書く。走らせます。

```console
$ herd7 -model x86tso.cat SB.litmus
Test SB Allowed
States 4
0:EAX=0; 1:EBX=0;          ← 問題の(0,0)が状態列挙に存在する
0:EAX=0; 1:EBX=1;
0:EAX=1; 1:EBX=0;
0:EAX=1; 1:EBX=1;
Ok
Observation SB Sometimes 1 3
```

「Allowed」「Sometimes」――x86-TSOモデル上で(0,0)は**起こりうる**、が公式判定です。第3.2.1節で手トレースした導出の、機械による追認です。同じSBのストア/ロード間に`MFENCE`を挟んだ版はForbidden(Never)になり、リスト3-2の実測と一致します。AArch64版のMP、n6、IRIWも同様に書けます(命令はSTR/LDR/STLR/LDAR/DMB)。ここで、第3章の演習5に約束した**三点照合**の全景を出します。

**表11-1: 三点照合 ― 手モデル/herd7/実機の全員一致**

| テスト | 手トレース(第3章) | herd7 x86-TSO | herd7 AArch64 | 実機x64 | 実機M2 |
|---|---|---|---|---|---|
| SB(素) | 導出可 | Allowed | Allowed | 観測 3% | 観測 7% |
| SB+MFENCE/DMB | 導出不能 | Forbidden | Forbidden | 0 | 0 |
| MP(素) | 導出不能(3.2.2) | **Forbidden** | **Allowed** | 0/10⁹ | 観測 0.02% |
| MP+stlr/ldar | ― | ― | Forbidden | ― | 0 |
| n6 | 導出可(3.3.1) | Allowed | Allowed | 観測 | 観測 |
| IRIW(読者順序固定) | ― | Forbidden | Forbidden | 0 | 0 |

3列の判定が全行で噛み合っています。特にMPの行――x86でForbidden、AArch64でAllowed――は、第10.7節のケーススタディで「x64では起こり得ず、ARMでは仕様どおり起こる」の機械証明として使った、まさにあの1行です。そしてherd7には、実機がどうやっても提供できない能力があります。**「観測されなかった」と「禁止されている」の区別**です。表10-1の復路relaxed(実機0/10⁸)のような事例で、0という数字の意味を確定できるのは列挙だけです。

もうひとつ実務上重要なのが、herd7の**C11モード**です。アセンブリではなくC++のアトミック操作(`atomic_store_explicit(&y, 1, memory_order_release)`等)でテストを書くと、特定のアーキテクチャではなく**契約そのもの**の上で判定してくれます。acquire/release版MPはC11モデル上でForbidden――「どのアーキテクチャの、どの対応表を通っても壊れない」ことの、契約レベルの証明です。第8.6節の方針「正しさの根拠は契約に置く」を実行する装置が、これです。

使いこなしの型は「**リトマス化**」です。疑わしい同期コードから、変数2〜4個・各スレッド2〜4命令の骨格を抜き出し、litmusファイルとしてリポジトリに保存する。以後それは、herd7で回る**契約の回帰テスト**になり、litmus7で回る**実機の感度キャリブレータ**(自作ハーネスの観測頻度の答え合わせ)になります。限界も明確で、ループ・動的確保・本物のデータ構造は書けません。骨格より大きいものの網羅検査は、次の道具の仕事です。

> **観測事実38**: herd7の全実行列挙は、第2〜3章の手トレース・実機観測と全テストで一致した(三点照合成立)。列挙だけが「観測されない」と「禁止」を区別でき、C11モードは契約そのものの上での証明を与える。疑わしい同期は骨格を「リトマス化」して回帰資産にせよ。

## 11.3 【コード】Relacyで第10章のSPSCキューを網羅検査する

herd7が扱えない「本物のデータ構造」を網羅検査する道具が、**Relacy Race Detector**(Dmitry Vyukov作)です。発想の転換がお見事で、Relacyは検出器ではなく**シミュレータ**です。検査対象をrl::名前空間のラッパ(`rl::atomic`、素の変数は`rl::var`)で書き、スレッド本体をテストスイートとして与えると、Relacyは自前の協調スケジューラで**全インターリーブを系統的に列挙**しながら実行します。しかも、C++メモリモデルの**弱い挙動まで模擬します**――relaxedロードには「変更順序上、読んでよい値の集合」から古い値を返す選択肢まで探索する。つまり、**x64マシンの上で、契約が許すあらゆるARM的挙動(そしてどの実機よりも意地悪な挙動)を再生できる**のです。

リスト10-1のSPSCを移植します。機械的な書き換えです。

**リスト11-3: spsc_rl.cpp ― Relacy版SPSC(骨子)**

```cpp
#include <relacy/relacy.hpp>

struct SpscTest : rl::test_suite<SpscTest, 2> {        // スレッド数2
    static constexpr size_t N = 2;                     // 網羅のため容量は最小に
    rl::atomic<size_t> head, tail;
    rl::var<int> buf[N];                               // 素のintはrl::varで(競合監視対象)

    void before() { head($) = 0; tail($) = 0; }
    void thread(unsigned tid) {
        if (tid == 0) {                                // 生産者: 2個pushを試みる
            for (int v = 1; v <= 2; ++v) {
                size_t t = tail.load(rl::mo_relaxed, $);
                size_t h = head.load(rl::mo_acquire, $);
                if (t - h == N) return;
                buf[t % N]($) = v;
                tail.store(t + 1, rl::mo_release, $);
            }
        } else {                                       // 消費者: popして値の単調増加を検査
            int last = 0;
            for (int k = 0; k < 2; ++k) {
                size_t h = head.load(rl::mo_relaxed, $);
                size_t t = tail.load(rl::mo_acquire, $);
                if (t == h) return;
                int v = buf[h % N]($);
                RL_ASSERT(v == last + 1);              // 不変条件をアサート
                last = v;
                head.store(h + 1, rl::mo_release, $);
            }
        }
    }
};
int main() { rl::simulate<SpscTest>(); }               // 既定: 全探索(小さな上限まで)
```

`$`はソース位置を運ぶマクロで、反例トレースの行番号表示に使われます。実行:

```console
$ ./spsc_rl
iterations: 41372
no errors detected                     # 全41372スケジュール・全許容結果で不変条件成立
```

4万余りの実行**すべて**が検査され、合格。実機テストの「たくさん回したが壊れなかった」とは意味の次元が違う、有界網羅の**証明**です(有界=この規模・この反復数の範囲で、という限定は付きます)。

では、お待ちかねの意地悪を。表10-1で**ARM実機が1億回沈黙した**あの変種――復路の封、⑩`head.store`をrelaxedに緩めます。

```console
$ ./spsc_rl_broken
RELACY ITERATION 1187:
DATA RACE detected
  thread 0: store to buf[0]  (spsc_rl.cpp:14)     ← 生産者の上書き
  thread 1: load  of buf[0]  (spsc_rl.cpp:24)     ← 消費者の読みかけ
execution history:
  [0] t1: head.load  → 0        [3] t1: buf[0] load を開始
  [1] t1: tail.load  → 1        [4] t1: head.store(1, relaxed)   ← 封のない返却が
  [2] t0: (2周目) tail.load → 1  [5] t0: head.load → 1(relaxed値を観測)
  ...                            [6] t0: buf[0] store  ← 読みかけのスロットへ上書き!
```

**1187番目のスケジュールで、反例が、実行トレース付きで出ました。** 所要1秒未満。ARM実機が1億回・数十分かけて出せなかった破れ(LB型ゆえハードウェアが実際には起こさない並べ替え)を、Relacyは「契約が許す以上、起こしてみせる」。第6.5節の`a = a + 1`も同様です――TSanの空白地帯だったあの消失を、Relacyは最終カウンタのアサートで数百イテレーション以内に仕留め、消失に至る正確なインターリーブを印字します。

実務上の注意も正直に。Relacyは**侵襲的**です(コードをrl::で書き直す必要がある)。探索は状態爆発と戦うので、容量2・要素2個のような**最小の宇宙**でテストを設計する腕が要ります(小さな宇宙で出るバグは大きな宇宙でも出る、という論理に支えられています)。検査するのは契約であってアセンブリではないので、インラインasmや対応表起因の問題(第8.4節)は対象外。そして開発は枯れています――同系統の現代的な後継として、書き換え不要でLLVM IR上のプログラムを直接網羅検査する**GenMC**、C11モデル特化の**CDSChecker**、隣の芝生ではRustの**loom**があり、新規に始めるならGenMCの評価を勧めます。とはいえ「網羅検査を開発ループに入れる」という発想の教科書として、Relacyの学習価値は今も別格です。

> **観測事実39**: Relacyは、ARM実機が10⁸回沈黙した契約違反(SPSC復路のrelaxed化)を、1187スケジュール目・1秒未満で反例トレース付きで検出した。網羅検査は確率ではなく(有界の)証明であり、TSan(実行された1経路)とherd7(極小骨格)の間の空白を埋める。

## 11.4 実務ワークフロー ― x64開発・ARM本番でバグを出さないCI設計

道具が出揃いました。表8-3(見える誤り・見えない誤り)を設計図に、「開発者はx64のラップトップ、本番はGraviton」という最も一般的な構成のパイプラインを組みます。原則は**多層防御**――各層は異なる盲点を持つので、層の「盲点の積」を空集合に近づけるのが設計目標です。

**表11-2: 並行性検証パイプライン(推奨構成)**

| 層 | いつ | 何を | 捕まえるもの | 見逃すもの |
|---|---|---|---|---|
| L0: レビュー | 毎PR | 構図読み(表7-1)+チェックリスト | 設計レベルの誤構図 | 実装の細部 |
| L1: TSan(x64) | 毎PR | 単体+結合テストをTSanビルドで | hb欠落(素データ) | 観測事実37の3盲点 |
| L2: ARM実行 | 毎PR | 同じテストをARMランナーで | relaxed欠落(MP型) | LB型、acq/rel過剰依存 |
| L3: ストレス | 夜間 | 11.5節のハーネス群をARMで | 低頻度の順序バグ | 頻度0に漸近するもの |
| L4: モデル検査 | 同期コード変更時 | Relacy/GenMCスイート+litmusコーパス | 契約違反の全て(有界) | 契約外(asm、性能) |
| L5: 本番 | 常時 | 不変条件アサート+телеメトリ | 想定外の全て(事後) | ― |

各層に、本書で得た設計判断を注入します。

**L1の規律。** TSanの効力は書き方に依存します(観測事実37)。(a) **保護対象データは素の型で書く**――atomicで包んで黙らせない。(b) **抑止リストは原則禁止**。追加には「TSanに見えない自作同期の注釈で解決できない理由」の文書化を要求する(第10.7節の教訓の制度化)。(c) TSanビルドからは診断ログの同期を外す(リスト11-1)。(d) ASanとTSanは同居できないため、別ジョブに分ける。

**L2の感度設計。** 第8.4節の教訓――検出感度は「契約×対応表×アーキテクチャ」の積で決まる――をここで使います。ARMランナーのツールチェーンは**RCpc世代のターゲット**(`-mcpu=neoverse-v1`等)を必ず含める:古典対応表(acquire→ldar)の過剰包装は、acq/rel↔seq_cst混同を隠すからです。逆に`-march=armv8-a`(LL/SC+ldar)のビルドも1本残す:LSE有無・対応表の違いという**軸の多様性そのものが感度**です。コンパイラもGCC/Clang両方。1つの警告:ARM実機が用意できないからと**QEMUで代用してはいけません**。エミュレータのメモリモデルは概ねホスト(x64)のそれを透過するため、弱いモデルの並べ替えは再現されず、「ARMでテストした」という誤った安心だけが残ります。実機が無いなら、その予算はL4に回すのが正解です。

**L4の資産化。** モデル検査は「導入」ではなく「蓄積」で効きます。(a) 中核の並行構造(キュー、ロック、回収機構)ごとにRelacy/GenMCテストを常備し、**アルゴリズム変更のPRでは必ず回す**。(b) 手書きのフェンスやオーダー注釈を含むコードには、対応するlitmusファイル(11.2節のリトマス化)を同じディレクトリに置き、herd7 Forbiddenであることを回帰テストにする。第10.7節の組織なら、あの`volatile`リングバッファは、この規約の初日に検挙されていました。

## 11.5 【コード】「1億回に1回」を1分で ― ストレステスト工学

最後は実行テスト側の感度を極限まで研ぐ技法です。実は本書は、この技法を**最初から使っていました**。第2章のハーネス(go/doneの一斉スタート)は、素朴な「スレッドを起動してループ」ではありません。どれほど違うか、今こそ定量化しましょう。モルモットはMPテスト(ARM/M2、既報の破れ率217/10⁶が「調整済み」の数字です)。素朴版から1技法ずつ積み上げ、破れ率を計測します。

**表11-3: ストレス技法の累積効果(MP破れ率、per 10⁶)**

| 段階 | 加えた技法 | 破れ率 | 倍率 |
|---|---|---|---|
| S0 | 素朴版(spawn→各自ループ→join) | 0.4 | ×1 |
| S1 | +一斉スタート(go/doneバリア) | 22 | ×55 |
| S2 | +敵対的コア配置(クラスタまたぎ固定) | 96 | ×4.4 |
| S3 | +位相走査(開始直前に乱数長の空ループ) | 217 | ×2.3 |
| S4 | +窓の拡大(ペイロード512B化・検査は別途) | 610 | ×2.8 |

累積で**1500倍**。技法の中身と原理を短く注記します。

**S1・一斉スタート。** 破れは2スレッドの危険窓(数ns)の**重なり**でしか起きません。素朴版ではスレッドがすぐ位相ずれし、各イテレーションの窓は重ならなくなります。go/doneは毎回、窓を強制的に衝突圏へ戻す装置です(第2章の設計の種明かしです)。

**S2・敵対的コア配置。** 破れ頻度は通信遅延、つまりストアバッファ滞留時間とコヒーレンス往復(第3〜4章)に比例します。同一クラスタの隣コアは仲が良すぎる。M2ならPコアとEコアをまたぐ、GravitonならNUMA/CMN距離の遠い組を選ぶ。litmus7が自動でアフィニティを総当たりするのは、この最適配置の探索です。

**S3・位相走査。** 一斉スタートしても、パイプラインの位相は毎回ほぼ同じで、同じ相対タイミングばかり試してしまう。開始直前に乱数長(0〜数十サイクル)の空ループを挟み、相対位相を掃引します。あわせて、対象ラインのキャッシュ状態を毎回撹乱する(事前に読む/汚す/追い出す)と、RFO遅延の分布も掃引できます。

**S4・窓の拡大。** 窓そのものを広げる最終手段です。ペイロードを大きくすれば、封と荷札の間の時間が延び、並べ替えの入り込む余地が広がります(表10-1の演習2の原理)。診断時には有効ですが、**本来のコードの窓とは別物になる**ので、回帰テストの判定には使わず、再現・調査用と割り切ります。

検出側の工学も2点。**検査は安く**:イテレーション毎のassertは窓を歪めます。毒値(第10.4節)やカウンタで記録だけして、集計は外で。**再現性の確保**:乱数種・コア配置・反復数を必ずログし、破れ検出時にそのまま再実行できるコマンドラインを印字させる。

そして最後に、統計の規律を。ストレスで破れが「0回」だったとき、何が言えるのか。答えは「**破れ率の上限**」だけです。N回試行で0観測なら、真の発生率は約95%信頼で **3/N 以下**(「3の法則」)。10⁸回で0なら、率は3×10⁻⁸以下――毎秒10⁶回走る本番なら**30秒に1回未満**、という上限です。安心材料には遠い。逆算すれば、目標MTBFから必要試行数Nが決まり、それが非現実的な大きさなら、その保証は実行テストの守備範囲外――L4(網羅検査)の出番だ、という判断が下せます。**ストレスは頻度を測る装置、不在を証明する装置ではない。** 本書がこの2つの装置を峻別してきた理由の、これが最終的な定式化です。

> **観測事実40**: ストレス技法(一斉スタート×55、敵対的コア配置×4.4、位相走査×2.3、窓の拡大×2.8)は破れ検出感度を累積1500倍に高める。ただしN回試行・0観測が与えるのは「率≤3/N」という上限のみであり、不在の証明は網羅検査(herd7/Relacy)だけが与える。

### 第11章のまとめ

- **観測事実37**: TSanは1実行のhb監査人。誤報は原則ないが、未実行の経路・全アトミック化されたバグ・偶然の同期(ログ!)に盲目。TSanビルドの規律=素データ・抑止禁止・診断同期の排除。
- **観測事実38**: herd7/litmus7で手モデル・形式モデル・実機の三点照合が全テスト一致。列挙だけが「観測されない」と「禁止」を区別し、C11モードは契約そのものの証明を与える。疑わしい同期は「リトマス化」して回帰資産に。
- **観測事実39**: Relacyは実機10⁸回沈黙の契約違反を1秒で反例トレース付き検出。有界網羅は確率でなく証明。侵襲性が課題で、現代の選択肢はGenMC。最小の宇宙でテストを設計する。
- CI設計は多層防御(表11-2):L1 TSan(x64・毎PR)、L2 ARM実機(RCpc/古典・GCC/Clangの軸多様性=感度)、L3 夜間ストレス、L4 モデル検査+litmusコーパス、L5 本番アサート。QEMUはARMの代用にならない。
- **観測事実40**: ストレス工学(一斉スタート・敵対的配置・位相走査・窓拡大)で感度1500倍。0観測は率上限3/Nのみ。頻度測定と不在証明の分業が、検証体系の背骨である。

次はいよいよ最終盤、第12章「性能チューニング実験室」です。正しさの検証体系が整った今、安心して速さを追えます。競合コストの実測(x64 vs Apple Silicon vs Graviton)、perf c2cによるライン競合の特定、シャーディングカウンタ、そしてseq_cstだらけのコードを検証つきで段階的に緩めるリファクタリング演習――最終演習のMPMCキューまで一気に行きます。
