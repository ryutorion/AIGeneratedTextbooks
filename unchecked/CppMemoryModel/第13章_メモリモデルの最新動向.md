# 第13章 メモリモデルの最新動向 ― 実験室の窓から地平線を眺める

45個の観測事実を積み上げた実験は、前章で完結しました。この最終章は毛色が違います。ベンチマークも壊し戻しも(1つの例外を除いて)ありません。代わりに、実験室の窓を開けて、この分野がいまどこへ向かっているのかを眺めます。

なぜ最終章がこれなのか。理由は2つあります。第一に、**契約は生きた文書**だからです。本書が「C++メモリモデル」と呼んできたものは、C++11で完成した石版ではなく、いまも改定され続けており、しかも未解決の穴を抱えています(13.2節)。第二に、本書を終えた読者は、この分野の**一次情報を読める数少ない実務家**になっているからです。標準化委員会の提案文書(P論文)も、アーキテクチャの形式モデルも、研究論文も、その中心にはリトマステストとAllowed/Forbiddenの表が置かれています――第2章からずっと、私たちが使ってきたあの言葉です。

## 13.1 C++20以降の契約改定 ― 標準は何を直し、何を諦めたか

C++11の契約はその後、3回の改定(C++14/17/20)と現在進行中の作業(C++23/26)で手を入れられてきました。本書に関係する改定を、**「精密化」「追加」「撤退」**の3分類で棚卸しします。読者はそのほとんどに、実は既に出会っています。

**精密化 ― 定義の穴を塞ぐ改定。** 最重要はC++20のP0668「Revising the C++ memory model」です。背景が痛快で、後述(13.4節)の形式化研究が、**C++11のseq_cstの定義と、Power向けの標準的な対応表(第8章の意味での「翻訳表」)の間に不整合がある**――つまり規格どおりに翻訳すると規格の要求を満たさない――ことを数学的に示してしまったのです。C++20はseq_cstの定義(全順序Sとhappens-beforeの整合条件)を修正し、あわせてseq_cstフェンスの保証を強化しました。もうひとつの精密化が、第7.6節で学んだリリースシーケンスの縮小(P0982、C++20)です。「同一スレッドの素のストアも列を継げる」という旧規定は、実装困難と誤用の温床を理由に**削除**されました。保証を狭める改定が「精密化」に分類される点に注意してください――曖昧に広い保証より、狭くても実装可能で検証可能な保証のほうが、契約としては上等なのです。

**追加 ― 道具箱の拡充。** 本書で使った現代的な道具の多くがここに入ります。`atomic_ref`(C++20、第6.4節)は「アトミック性はオブジェクトの属性ではなくアクセスの属性である」という、観測事実19と同じ思想の制度化です。`atomic::wait/notify`と`counting_semaphore`/`latch`/`barrier`(C++20、第9.6節)は、futexという20年物のOS機能への標準玄関でした。そしてC++26では、第10.6節で予告したとおり`std::hazard_pointer`と`std::rcu`が入り、安全なメモリ回収――ロックフリー実用化の最後の関門――が標準装備になります。`fetch_max`/`fetch_min`のようなRMWの語彙拡充も進んでいます。

**撤退 ― consumeの長い葬列。** 第7.7節で葬った`memory_order_consume`のその後です。C++17で「一時的に使用を推奨しない」と明記されたまま、依存関係を言語レベルで定義し直す試みはどれも合意に至らず、関連属性`[[carries_dependency]]`は実装が現れないまま削除の方向で処理されました。撤退が続く根本理由――**「依存関係」はコンパイラ最適化の通過後には定義できない**――は、次節の主役と同じ病です。

この棚卸しから読み取るべきは個々の変更より、**改定の駆動力の変化**です。C++11の契約は委員会の英知で書かれましたが、C++20以降の改定は、形式化研究が発見した欠陥と、実装(コンパイラ・ライブラリ)の経験報告で駆動されています。契約は「書かれるもの」から「検証されるもの」に変わった――本書が第11章で個人の開発フローに導入した転換と、同じことが標準そのものに起きているのです。

## 13.2 Out-of-thin-air問題 ― 契約に空いたままの穴

さて、その検証されるようになった契約に、10年以上塞がっていない穴があります。分野の誰もが知る未解決問題、**out-of-thin-air(OOTA、無からの値)**です。本書の読者への説明は簡単です。第2章の演習1で扱ったLB(Load Buffering)テストに、ほんの少し細工をします。

```cpp
// 初期状態: x = y = 0(すべてrelaxedアトミック)
// スレッド1:                     // スレッド2:
r1 = x.load(relaxed);             r2 = y.load(relaxed);
y.store(r1, relaxed);             x.store(r2, relaxed);
//         ^^                     //         ^^
//   読んだ値をそのまま書く          読んだ値をそのまま書く
```

問い:**r1 == r2 == 42 はありうるか?** 42という値は、初期値にも、どのスレッドのコードにも現れません。もし観測されたら、その42は文字どおり**無から湧いた**ことになります。「そんな馬鹿な」と全員が同意します。ハードウェアは起こしません(ストアの値はロードにデータ依存しており、ARMですら依存ロード→ストアは並べ替えません――第7.7節)。コンパイラも起こしません。**問題は、C++の契約の形式的な読みが、これを禁止できていない**ことです。

なぜ禁止できないのか。契約の公理的モデルは「候補実行(各ロードがどのストアを読むかの割り当て)を列挙し、公理に反するものを捨てる」という構造です(herd7が第11.2節でやっていたこと、そのものです)。ではr1=r2=42の候補実行を検査してみましょう――スレッド1のy=42はr1=42に正当化され、r1=42はスレッド2のx=42に正当化され、x=42はr2=42に、r2=42はスレッド1のy=42に正当化される。**正当化が円環を成して閉じており**、relaxedの公理(コヒーレンスのみ)はどこにも違反がありません。モデルはこの循環を許してしまう。

「では循環を禁じればよい」――そう思いますよね。ここが罠です。細工を1つ戻した、正真正銘のLBテストと比べてください。

```cpp
// スレッド1:                     // スレッド2:
r1 = x.load(relaxed);             r2 = y.load(relaxed);
y.store(1, relaxed);              x.store(1, relaxed);   // ← 定数を書く(依存なし)
```

こちらの(1,1)は、契約が**許容すべき**結果です(依存がないのでハードウェアはロードとストアを並べ替えてよく、契約はそれを許すと決めた)。2つのテストの候補実行は、グラフの形(読み書きの依存円環)としては**同型**で、違いは「ストアの値がロードに**意味的に**依存しているか」だけ。そして意味的依存は、第7.7節でconsumeを殺したのと同じ理由で、定義できません――コンパイラは`y = r1 * 0`の構文的依存を消し、`if (r1 == 42) y = 42; else y = 42;`を`y = 42`に潰します。最適化の通過後に残る「本物の依存」を公理の言葉で書けた者は、まだいないのです。

現在の規格の対応は、率直に言って苦肉の策です。規格本文に**「実装はout-of-thin-airな値を生成すべきでない(should not)」という非規範的な勧告**を置く――つまり、定義できないものを、お願いで塞いでいる。研究側の主要な回答は2系統あります。**RC11**(Repaired C11、2017)は「プログラム順と読み出し関係の循環を一律禁止」する外科手術で、単純明快にOOTAを殺せますが、代償として正当なLBの(1,1)まで言語レベルで禁止します(relaxedの翻訳をARM等で強化しないと健全性が保てず、その値上げを実装は受け入れていません)。**Promising semantics**(2017)系は「スレッドが将来のストアを約束し、約束を自力で果たせることを証明した場合だけ先に見せてよい」という操作的モデルで、正当な並べ替えとOOTAを見事に切り分けますが、複雑さゆえ規格文書への搭載に至っていません。第11章のモデル検査器たちも他人事ではなく、各ツールはどれかの「修理済みモデル」を選んで実装しています(GenMCのRC11系など)。**relaxedを使うすべてのコードの形式的検証が、この選択の上に立っている**――穴は、理論家の道楽ではなく、私たちの検証装置の土台の話なのです。

実務者への現実的な結論は3行で済みます。(1) 現実のコンパイラとCPUでOOTAは起きない。恐れる必要はない。(2) ただしrelaxedの意味論の「最終形」は未確定であり、relaxedへの依存が深いコードほど、将来の規格・ツールの選択の影響を受けうる。(3) この問題の帰趨は、依存関係を型や注釈で明示する方向(consumeの再挑戦)と絡んで動く。P論文の表題に「out-of-thin-air」を見かけたら、それは本節の続報です。

## 13.3 アーキテクチャの地平線 ― ARMv9、RISC-V、CHERI、そして「選べるメモリモデル」

ハードウェア側の動向は、本書の読者には嬉しい方向に流れています。一言で言えば、**弱いモデルの形式化が完了し、強いモデルが「互換モード」として選べる時代**が来ました。

**ARMv9は、メモリモデルについては「変えない」を選びました。** v8で確立した形式モデル(other-multi-copy-atomic、第3.6.1節)はそのまま引き継がれ、追加はSVE2やCCAといった別軸の機能です。注目はMTE(Memory Tagging Extension)――ポインタとメモリに色タグを付け、use-after-freeや範囲外アクセスをハードウェアが検出する機能で、第10章の事件(a)のような病をASan相当のコストなしに本番環境で捕まえられます。モデルの安定と、安全機構の追加。成熟したアーキテクチャの姿です。

**そして、本書の物語の見事な回収がここにあります。** Apple SiliconのCPUには、**プロセス単位で切り替えられるTSOモード**がハードウェアとして実装されています。x86バイナリを走らせるRosetta 2は、翻訳したコードをこのTSOモードで実行します――x86バイナリはTSOを前提に書かれている(第7.8節の「ただ乗り」コードを含めて!)ので、素のARMモードで走らせたら壊れるからです。つまり同じ物理コアが、モードビット1つで第3章の機械(TSO)にも第3.6節の機械(弱いモデル)にもなる。確かめられます。本書最後のデモです。

```console
# Apple M2。第2章のMPテスト(relaxed版)を2通りにビルドして同じマシンで実行
$ clang++ -arch arm64 -O2 mp.cpp -o mp_native && ./mp_native
r != 42 が 214 / 1000000 回観測されました          # ネイティブ: 弱いモデル、壊れる

$ clang++ -arch x86_64 -O2 mp.cpp -o mp_rosetta && ./mp_rosetta
r != 42 が 0 / 10000000 回観測されました           # Rosetta 2: 同じコアがTSOになり、壊れない
```

**同じシリコン、同じソース、同じ日。** 違いはプロセスに立ったTSOビットだけ。第2章で「アーキテクチャの違い」として観測した現象が、実は「モードの違い」にまで蒸留可能だった――メモリモデルとは物理の宿命ではなく、**設計され、選択される契約**なのだという本書の主張の、これ以上ない物証です。

**RISC-V**は、この「選べる契約」を仕様の建て付けにしました。基本はRVWMO(第3.7節)――史上初めて、**誕生時から形式モデルとして定義された**メモリモデルです(仕様書に公理モデルが同梱され、herdで実行できます)。その上に、**Ztso拡張**という公式のTSOモードが用意されています。x86からの移植市場を見据えた互換ブリッジで、AppleのTSOビットと同じ発想が、今度はISA仕様のオプション拡張として標準化されているわけです。命令セット側では、AMO命令とLR/SCが`.aq`/`.rl`ビットを持ち(第8章の対応表のRISC-V列)、素のロード/ストアへのacquire/release付与(ldar/stlr相当)は拡張として整備が進んでいます。

**CHERI**は別方向の未来です。ポインタを「番地」から「ケーパビリティ」(範囲と権限を持つ128ビットの資格証+検証タグ)に置き換え、メモリ安全性をアーキテクチャに焼き込む研究系譜で、Armとの実機Morelloが存在します。並行性との接点が面白く、ケーパビリティは**タグ込みで不可分に**読み書きされねばならず(半分だけ書かれた資格証は偽造の穴になる)、第6.4節で学んだ「何バイトまでロックフリーか」の問いが、安全性の要件として再登場します。ポインタの出自(provenance)が仕様の一級市民になることは、第10章のタグ付きポインタ芸(整数への詰め込み)の作法をも変えるでしょう。

最後に、視界の端の大きな影を2つ。**GPUとヘテロジニアス計算**――GPUのメモリモデルはスコープ付きアトミック(「このブロック内で」「デバイス全体で」と可視範囲を指定する操作)という、C++にない語彙を持ち、既に形式化が進んでいます。CPU側のC++にもスコープの概念を輸入する議論があり、料金表(第12.1節)に「距離」の次元が正式に加わる未来がありえます。そして**永続メモリ/CXL**――電源断を越えて残るメモリの「どの順で永続化されるか」は、本書のモデルにflushの次元を足した拡張モデル(Px86、PArm)として研究されています。ストアバッファの次は、永続化バッファ。第3章の機械の増築は続きます。

## 13.4 形式手法によるメモリモデル研究 ― 仕様書が実行可能になった

本書は第3.4節でSewellらのx86-TSOに出会い、第11.2節でその直系の道具(herd7)を実務に使いました。最終節では、この研究系譜の現在地を、1本の物語として通します。物語の主題は「**仕様書の地位の変化**」です。

**第1幕(2000年代)**: 仕様は自然言語で書かれ、実機と食い違い、誰も正しいコードの書き方を証明できなかった。Sewellらのx86-TSO(2010)が「抽象機械+公理+実機での大量検証」という方法論を確立し、事後的に秩序を回復した(第3章で私たちが追体験した物語です)。

**第2幕(2010年代)**: 方法論が道具になった。Alglave、Marangetらのcat言語は、メモリモデルそのものを**実行可能なプログラム**として記述する形式で、herd7はその処理系です。決定的だったのはArmの対応で、ARMv8の公理モデルを**公式仕様の一部として機械可読形式で公開**し、研究者を招き入れ、第3.6.1節で触れた仕様改定(multi-copy atomicityの強化)も形式モデル上で設計・検証されました。RISC-Vに至っては第3幕を待たず、誕生時から形式モデル同梱(13.3節)。**「仕様書に対してテストを実行する」ことが、できるようになった**のです。命令セット全体の意味論を記述するSail言語のような基盤も整い、ARMやRISC-Vの「黄金モデル」が機械可読で存在します。

**第3幕(同時進行)**: 矛先が言語仕様に向いた。Battyらは、まだ策定中だったC++11のメモリモデルをまるごと定理証明器上に形式化し、**発行前の規格から欠陥を発見して修正させました**(規格が出版前に形式検証された、おそらく史上初の事例です)。その後も検証は続き、C++11のseq_cst定義とPower向け翻訳の不整合の発見が、13.1節で見たC++20の修正(P0668)に直結しました。翻訳(第8章の対応表)そのものの健全性証明――「この対応表を通せば、契約の全保証がこのアーキテクチャで成立する」の数学的証明――も研究の定番題材になっています。第8.1節で私たちが「R⊆Hなら素の命令」と略式に導出したものの、厳密版がそこにあります。

**未解決の戦線**は、本章で触れたものを含めて一覧できます。OOTA(13.2節、言語意味論の本丸)。**混合サイズアクセス**(同じバイト列を異なる幅のアトミックで読み書きしたときの意味論――ハードウェア側の形式化は進みましたが、C++の契約は実質未定義のまま)。永続メモリとGPUスコープ(13.3節)。そして**投機実行と情報漏洩**――Spectre系の攻撃は、「投機ストアは外から見えない」(第10.2節で私たちも依拠した抽象)がキャッシュ状態という側路では破れていることを示し、機能的正しさだけを扱ってきたメモリモデル研究に、マイクロアーキテクチャの漏洩まで含めた新しいモデルの構築という宿題を課しました。

この戦線の一覧を眺めて、気づいてほしいことがあります。研究の最前線で使われている方法論は、リトマステストを書き、モデルで判定し、実機で突き合わせる――**第2章から第11章まで、あなたが自分の手でやってきたことと同じ**です。この分野は、実務家と研究者の距離が異様に近い。P論文の議論に実装経験で貢献することも、新しいアーキテクチャのモデルにリトマステストで穴を見つけることも、本書を終えた読者の射程内にあります。

## 結び ― counter++から地平線まで

第1章で、私たちは2スレッドの`counter++`が壊れる様を見ました。あのとき手元にあったのは、期待値に届かない数字への当惑だけでした。

45の観測事実を経た今、道具箱には次のものが揃っています。壊れ方を再現する腕(リトマステストとストレス工学)。壊れる理由を導出する機械(TSOモデルと弱いモデル、MESIとストアバッファ)。壊れないことを記述する契約(happens-beforeとメモリオーダー)。契約と機械をつなぐ翻訳表。契約の上に建つ実戦の構造物(ロック、seqlock、SPSC、MPMC)。そして契約そのものを検査する装置(TSan、herd7、Relacy)。

最後に、本書を貫いた規律を3行に圧縮して、餞とします。

**実行テストを信じすぎない。** それが検査するのは契約×対応表×アーキテクチャの積であり、x64は、そして時に古典ARMツールチェーンすら、あなたの誤りを隠す(観測事実24、27)。

**契約で考え、機械で裏を取る。** 構図(表7-1)で設計し、台帳で記帳し、モデル検査で証明し、アセンブリで監査し、ARMで値付けする(観測事実44)。

**最速の同期は、同期しないことである。** オーダーの緩和は数割、競合の除去は一桁を返す。局所に書き、まれに集計せよ(観測事実41、43、45)。

そして何より――**メモリモデルは、実験できる**。本書のリポジトリ(付録A)のハーネスは、次のアーキテクチャが来ても、次の規格改定が来ても、そのまま使えます。新しいCPUを手に入れたら、まずSBとMPを走らせてみてください。数字があなたに、そのマシンの契約を教えてくれます。

### 章末演習
