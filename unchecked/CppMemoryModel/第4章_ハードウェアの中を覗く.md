# 第4章 ハードウェアの中を覗く

第3章で組み立てた「機械」は、よくできたおもちゃでした。SBの(0,0)を導出し、MPの不壊を証明し、n6のねじれまで説明してくれました。しかし、あれは本物なのでしょうか。実際のCPUの中に、FIFOストアバッファや「共有メモリ」に相当する部品は本当にあるのでしょうか。そもそも、各コアが専用キャッシュを持つ現代のCPUに、「全コア共通の共有メモリ」(3.2節の機械の一番下の箱)などというものが存在できるのはなぜでしょうか。

この章では、ベンチマークという聴診器でハードウェアの中を探ります。キャッシュラインの実寸を測り(4.1節)、コア間でキャッシュラインを取り合う音を性能低下として聴き(4.2〜4.3節)、そのうえで第3章の機械の各部品を物理実体と対応付けます(4.4節)。最後に、この章で学ぶキャッシュコヒーレンスが**メモリモデルの話とどう違うのか**という、混同されがちな境界線を実験で引きます(4.5節)。

なお、この章の主役であるキャッシュラインの寸法は、本書の2台の実験機で**違います**。x64は64バイト、Apple M2は128バイト。この違い自体が最初の実験のネタです。

## 4.1 【コード】キャッシュラインサイズを実測するベンチマーク

CPUとメモリの間のデータのやり取りは、1バイト単位ではなく**キャッシュライン**という固定長のかたまり単位で行われます。1バイト読むだけでも、そのバイトを含むライン全体がキャッシュに運び込まれます。この「かたまりの寸法」を、カタログを見ずにベンチマークだけで割り出してみましょう。

原理は単純です。大きな配列を「s バイトおき」に一定個数だけ書き換える仕事を、s を変えながら計測します。s がラインサイズより小さいうちは、複数の書き込みが同じラインに相乗りするので、メモリから運ぶライン数は書き込み数より少なくて済みます。s がラインサイズに達した瞬間、**1書き込み=1ライン輸送**になり、それ以上 s を増やしても輸送量は変わりません。つまり「1書き込みあたりの時間」は s とともに増加し、ラインサイズでぴたりと頭打ちになるはずです。

**リスト4-1: linesize.cpp ― ストライド走査でラインサイズを推定する**

```cpp
#include <chrono>
#include <cstdio>
#include <vector>

int main() {
    constexpr size_t TOUCH = 1 << 22;                // 書き込み回数は常に一定(約400万回)
    for (size_t stride = 8; stride <= 512; stride *= 2) {
        std::vector<char> buf(TOUCH * stride);        // ストライドに応じて領域を確保
        for (auto& c : buf) c = 1;                    // ページを確定させる(初回タッチ)

        auto t0 = std::chrono::steady_clock::now();
        for (size_t rep = 0; rep < 4; ++rep) {
            for (size_t i = 0; i < buf.size(); i += stride) {
                buf[i]++;                             // s バイトおきに1回書く
            }
        }
        auto t1 = std::chrono::steady_clock::now();
        double ns = std::chrono::duration<double, std::nano>(t1 - t0).count()
                    / (4.0 * TOUCH);
        std::printf("stride %4zu : %.2f ns/書き込み\n", stride, ns);
    }
}
```

計測のコツを2つ。書き込み**回数**を固定して領域**サイズ**を変えている(逆ではない)こと、そして領域をL3キャッシュよりずっと大きく取って、必ずメモリからの輸送が発生するようにしていることです。実行します。

```console
# x64 (Core i7)
$ g++ -std=c++20 -O2 linesize.cpp -o linesize && ./linesize
stride    8 : 0.61 ns/書き込み
stride   16 : 1.19 ns/書き込み
stride   32 : 2.35 ns/書き込み
stride   64 : 4.68 ns/書き込み
stride  128 : 4.71 ns/書き込み   ← ここから増えない
stride  256 : 4.74 ns/書き込み
stride  512 : 4.79 ns/書き込み
```

```console
# ARM (Apple M2)
$ clang++ -std=c++20 -O2 linesize.cpp -o linesize && ./linesize
stride    8 : 0.42 ns/書き込み
stride   16 : 0.80 ns/書き込み
stride   32 : 1.58 ns/書き込み
stride   64 : 3.10 ns/書き込み
stride  128 : 6.05 ns/書き込み
stride  256 : 6.11 ns/書き込み   ← 頭打ちが1段遅い
stride  512 : 6.15 ns/書き込み
```

x64は**64バイト**、Apple M2は**128バイト**で頭打ちになりました。OSに答え合わせをしてもらいます。

```console
# Linux (x64)
$ getconf LEVEL1_DCACHE_LINESIZE
64
# macOS (Apple Silicon)
$ sysctl hw.cachelinesize
hw.cachelinesize: 128
```

> **観測事実10**: メモリはキャッシュライン単位(実験機ではx64: 64B、Apple M2: 128B)で運ばれる。寸法はアーキテクチャどころか実装ごとに違い、ベンチマークで実測できる。

「64バイト」という数字を定数として暗記しているベテランは多いのですが、Apple Siliconの128バイトのように、その暗記が裏切られる実装は現に主流製品の中にあります。この寸法差は4.3節で実害として跳ね返ってきます。

## 4.2 【コード】フォールスシェアリングを意図的に起こして10倍の性能差を計測する

ラインが「かたまり」だということは、**論理的に無関係な変数どうしが、物理的には同じかたまりに同居しうる**ということです。ここに複数コアが絡むと何が起きるか。第1章の教訓に従い、まず起こして測ります。

題材は第1章の共有カウンタ……の、**正しく直した版**です。スレッドごとに専用カウンタを持たせれば、そもそも共有がないのでアトミックRMWの取り合い(第1.5節)すら起きない。完璧な並列化のはずです。

**リスト4-2: false_sharing.cpp ― 「共有していない」のに遅いカウンタ**

```cpp
#include <atomic>
#include <chrono>
#include <cstdio>
#include <thread>
#include <vector>

constexpr int  NTHREAD = 4;
constexpr long N = 100'000'000;

struct Counters {
    std::atomic<long> v[NTHREAD];    // v[0..3] が隙間なく並ぶ(計32バイト)
};
Counters c;

void worker(int tid) {
    for (long i = 0; i < N; ++i) {
        c.v[tid].fetch_add(1, std::memory_order_relaxed);   // 自分専用の要素だけ触る
    }
}

int main() {
    auto t0 = std::chrono::steady_clock::now();
    std::vector<std::thread> ts;
    for (int i = 0; i < NTHREAD; ++i) ts.emplace_back(worker, i);
    for (auto& t : ts) t.join();
    auto t1 = std::chrono::steady_clock::now();
    std::printf("経過: %.2f 秒\n",
                std::chrono::duration<double>(t1 - t0).count());
}
```

各スレッドは`v[tid]`、つまり**自分専用の要素**しか読み書きしません。データ競合はなく(TSanも沈黙します)、論理的な共有はゼロです。比較対象として、1スレッドだけで`v[0]`をN回インクリメントする逐次版も用意して、両方計測します。

```console
# x64 (4物理コアに配置)
$ ./false_sharing
経過: 3.41 秒        # 4スレッド並列
$ ./false_sharing_single
経過: 0.52 秒        # 1スレッド逐次(仕事量は1/4)
```

逐次版の4倍の仕事を4コアでやったのだから、理想は同じ0.5秒前後のはずです。現実は**3.41秒**。並列化したのに、1コアあたりの効率が7倍近く悪化しています。ARM(M2)でも同様に、並列版が異様に遅い結果になります。

原因は観測事実10です。`v[0]`〜`v[3]`は合計32バイト、**全員が同じ1本のキャッシュラインに同居**しています。そしてコアがラインに**書く**ためには、そのラインの所有権を独占しなければなりません(理由は4.4節のMESIで説明します)。4つのコアが、論理的には無関係な4つの変数を更新するために、物理的には**たった1本のラインの所有権を奪い合い続ける**――ラインは1回のfetch_addごとにコア間を宅配便のように往復し、その輸送コスト(数十〜百数十サイクル)が計算そのもの(数サイクル)を圧倒するのです。

この現象を**フォールスシェアリング(false sharing、偽共有)**と呼びます。「共有」はプログラマの論理上は偽(false)なのに、ハードウェアの物理上は真である、という命名です。

> **観測事実11**: 論理的に無関係な変数でも、同一キャッシュラインに同居していれば、コア間でラインの所有権の奪い合いが起き、並列化がかえって逆効果になりうる(実測で逐次比7倍の効率悪化)。

## 4.3 【コード】alignasで直して再計測 ― hardware_destructive_interference_size

診断がつけば処方は明快です。**奪い合いの単位=ライン**なのだから、変数を1人1ラインに引っ越しさせて相部屋を解消すればよい。C++の`alignas`でカウンタをライン境界に整列させ、ライン1本ぶんの間隔を空けます。

**リスト4-3: padded.cpp(リスト4-2との差分)**

```cpp
#include <new>   // hardware_destructive_interference_size

#if defined(__cpp_lib_hardware_interference_size)
constexpr size_t LINE = std::hardware_destructive_interference_size;
#else
constexpr size_t LINE = 128;   // 保守的な既定値(4.1節の実測を思い出すこと)
#endif

struct alignas(LINE) PaddedCounter {
    std::atomic<long> v;
    // alignasにより、この構造体はLINEバイト境界に置かれ、
    // 配列にしたとき要素間隔もLINEバイトになる(=1人1ライン)
};
PaddedCounter c[NTHREAD];

void worker(int tid) {
    for (long i = 0; i < N; ++i) {
        c[tid].v.fetch_add(1, std::memory_order_relaxed);
    }
}
```

```console
# x64
$ ./padded
経過: 0.54 秒        # 3.41秒 → 0.54秒、6.3倍の改善。ほぼ理想値
# ARM (Apple M2)
$ ./padded
経過: 0.49 秒
```

**逐次版と同じ時間で4倍の仕事**が終わるようになりました。変更したのはメモリ上の「席順」だけで、実行する命令列は1本も変わっていません。並行プログラムの性能が、アルゴリズムでも命令数でもなく**バイトの配置**で1桁変わる――これがこの実験の教訓です。

`std::hardware_destructive_interference_size`(C++17)は、この用途のために標準が用意した「これだけ離せば破壊的干渉(=フォールスシェアリング)を避けられる」という距離の定数です。ただし実務では3つの注意があります。

第一に、**これはコンパイル時定数であり、実行するCPUの実寸ではありません**。x64向けのGCC/Clangは64を返しますが、そのバイナリがどのCPUで動くかまでは知りません。第二に、**処理系の対応にむらがあります**。libstdc++は提供しますがGCCは「ABIの一部にすると危うい」趣旨の警告(-Winterference-size)を出しますし、libc++は長らく未提供でした。リスト4-3のようにフィーチャーテストマクロで存在確認し、無ければ保守的な値に倒すのが定石です。第三に、その「保守的な値」は**もはや64ではありません**。4.1節で実測したとおりApple Siliconは128バイトです。64で詰めた構造体をM2で走らせると、2要素が1ラインに相部屋してフォールスシェアリングが半分だけ復活します(章末演習3で実測します)。x64とARMの違いは、リオーダリングのような派手な話だけでなく、こういう地味な寸法にも潜んでいるのです。

## 4.4 ストアバッファの物理実体 ― MESIの世界に第3章の機械を重ねる

道具が揃ったので、冒頭の問いに答えます。「各コアが専用キャッシュを持つのに、なぜ**共有**メモリが存在できるのか」。

### キャッシュコヒーレンス ― 「1本のライン、1人の書き手」

答えは**キャッシュコヒーレンスプロトコル**です。各コアのキャッシュは、ラインごとに状態タグを持ち、コア間で通信しながら次の不変条件を守り続けます。

> **コヒーレンスの不変条件**: どのキャッシュラインについても、任意の瞬間に「書ける状態で持つコアは高々1つ」または「読める状態で持つコアは複数」のどちらか。**書き手が2人同時に存在することはない。**

代表的なプロトコルがMESIです。名前は各キャッシュがラインに付ける4状態の頭文字です。

```
M (Modified)  : 自分だけが持ち、書き換え済み。メモリより新しい唯一の写し
E (Exclusive) : 自分だけが持つが、未変更。黙って書いてよい(書くとMへ)
S (Shared)    : 複数コアが読み取り用に持つ。書くには昇格が必要
I (Invalid)   : 無効。持っていないのと同じ
```

4.2節の奪い合いの正体を、この語彙で言い直せます。コアが`fetch_add`するには、ラインをM/E状態で独占する必要があります。他コアがS/Mで持っていれば「無効化しろ(Invalidate)」というメッセージを送り付け、全員の写しをIにしてから自分がMになる。この**所有権請求(RFO: Read For Ownership)**の往復が数十〜百数十サイクルかかり、直後に別のコアが同じことをするので、ラインの状態は M→I→M→I… とコア間で激しく明滅します。リスト4-2の3.41秒は、この明滅の音だったのです(この明滅をperfのハードウェアカウンタで直接観測する方法は第12.2節で扱います)。

そしてこれが冒頭の問いの答えです。**第3章の機械の一番下にあった「共有メモリ」の箱の物理実体は、DRAMではなく、コヒーレンスプロトコルによって『1本の歴史』を保証されたキャッシュ階層全体**です。物理的には写しが散らばっていても、不変条件のおかげで、各ラインについて「書き込みの順序」は全コアが合意する1本になります。

### では、なぜリオーダリングが起きるのか ― 待合室としてのストアバッファ

ここで当然の疑問が湧きます。MESIがそこまで厳密に一貫性を守るなら、第2章のSBテストはなぜ壊れたのでしょう。

鍵はRFOの**遅さ**です。ストアを実行するたびに所有権請求の往復(数十〜百数十サイクル)を待って完全に停止していたら、CPUは仕事になりません。そこで実際のコアは、ストアを即座にキャッシュへ書くのではなく、**いったん待合室に預けて先へ進みます**。RFOが完了して所有権が届いたら、待合室から順にキャッシュへ反映(コミット)する――この待合室こそ、物理的な**ストアバッファ**です。第3章の機械は、おもちゃではなく実物の設計図だったのです。対応表を完成させましょう。

| 第3章のTSO機械の部品 | 物理実体 |
|---|---|
| 一番下の「共有メモリ」 | MESIで一貫化されたキャッシュ階層(+DRAM) |
| FIFOストアバッファ | ストアバッファ = RFO完了待ちのストアの待合室 |
| 「ドレイン」 | RFO完了時の、バッファからキャッシュへのコミット |
| フォワーディング(規則3前半) | store-to-load forwarding回路(自コアのバッファを連想検索) |
| mfenceの効果(3.5節) | 待合室が空になるまで後続メモリ操作を発行停止 |

こうして見ると、**リオーダリングとはコヒーレンスの敗北ではなく、コヒーレンスの遅延を隠すための工夫の副作用**だと分かります。MESIは1本の歴史を守っている。ただしその歴史に「載せる」処理が遅いので、載せ終わる前に各コアが先へ進んでしまう。そのずれが、外からはリオーダリングに見えるのです。

### x64とARMの分岐点 ― 待合室の運用規則

物理的なストアバッファは、x64にもARMにもあります。両者を分けるのは待合室の**運用規則**です。

**x64は待合室をFIFOで運用します。** 預かった順にしかコミットしない。だからStore→Storeの追い越しは起きず、第3.2.2節のMP不壊証明が成立します。さらにロード側も、プログラム順で結果が観測されることを保証する仕組み(投機実行して、順序違反を検出したらやり直す機構)を備えます。残る緩みは「待合室に預けたまま先のロードを実行する」ことだけ――Store→Loadです。

**ARMは待合室の追い越しを許します。** 先に所有権が取れたストアから先にコミットしてよい(Store→Storeの並べ替え)。たとえばMPテストで、`ready`のラインがたまたま手元にE状態であり、`data`のラインが他コアにあってRFO待ちなら、後から預けた`ready = 1`が先に世界へ公開されます。ロード側も同様に、アドレスが違えば後のロードを先に実行してかまいません(Load→Loadの並べ替え。古典的な教科書ではコヒーレンスメッセージの処理を遅延させる**無効化キュー**という部品で説明されます。現代の高性能コアでは投機的なアウトオブオーダーロードとして実装され、x64との違いは「順序違反を検出してやり直すか、放置してよいか」の規則の差になりますが、外から観測できる結果は同じです)。

つまりx64とARMの違いは、部品表の違いではありません。ほぼ同じ部品を持ちながら、**「プログラム順を外から見ても守っているふりをする」義務をどこまで負うかという契約の違い**です。ARMはその義務を放棄する代わりに、ハードウェアを単純化し電力効率を稼ぎ、順序が本当に必要な場所だけプログラマに`stlr`/`ldar`/`dmb`で申告させる。x64は互換性の歴史からTSOという重い契約を負い続け、その代わりプログラマは(第2章で見たとおり)多くの過ちに気づかずに済んでしまう。どちらが良い悪いではなく、**トレードオフの置き場所が違う**のです。

## 4.5 【コード】コヒーレンス ≠ メモリモデル ― 1変数の世界は今もまともである

この章の最後に、初学者が最も混同しやすい境界線を、実験で引いておきます。「ARMは弱いモデルだ」と聞くと、こう不安になりませんか――**1つの変数の値すら、コアによって新旧が入れ替わって見えたりするのでは?**

しません。それを保証するのがまさにコヒーレンス(4.4節の不変条件)であり、コヒーレンスは**ARMでも常時フル稼働**しています。確かめましょう。テストは **CoRR(Coherence, Read-Read)** ――同じ変数を2回続けて読んだとき、「新しい値→古い値」の順で見えることはあるか、を問います。

**リスト4-4: corr.cpp(ハーネスは共通。テスト本体のみ)**

```cpp
// 書き手コア
x.store(1, memory_order_relaxed);

// 読み手コア
r1 = x.load(memory_order_relaxed);   // 同じxを
r2 = x.load(memory_order_relaxed);   // 2回読む

// 異常判定: r1 == 1 && r2 == 0 (新→旧の逆行)
```

MPを軽々と壊したARM(M2)で、relaxedのまま実行します。

```console
$ ./corr
値の逆行が 0 / 100000000 回観測されました
```

1億回まわしてゼロ。これは偶然ではなく、AArch64のモデル上も禁止(Forbidden)です。同一アドレスに関する限り、ロードの追い越しは許されません。

> **観測事実12**: 弱いメモリモデルのARMでも、**単一の変数**の履歴は常に1本であり、どのコアもその履歴を逆行しては観測しない(CoRR禁止)。壊れるのは常に**複数の変数をまたぐ順序**である。

境界線を言葉にします。**コヒーレンスは「1つの場所」についての合意**であり、ハードウェアが無条件・無指定で保証します。**メモリモデル(コンシステンシ)は「複数の場所をまたぐ順序」についての契約**であり、アーキテクチャごとに強弱があり、弱い部分はプログラマが埋めます。第1章のカウンタが(値こそ消失したものの)「44の次に43が観測される」ような時間逆行だけは決して起こさなかったのも、コヒーレンスの仕事でした。

そしてこの境界線は、そのままC++の仕様の語彙に翻訳されます。C++メモリモデルは、各アトミック変数に**変更順序(modification order)**という1本の履歴を保証し(コヒーレンスに対応)、変数をまたぐ順序は**happens-before**という関係でプログラマが組み立てる(コンシステンシに対応)――第2部の主役となるこの2つの概念に、私たちはハードウェア側からすでに出会っていたわけです。

---

### 第4章のまとめ

- **観測事実10**: メモリはキャッシュライン単位で動く。寸法は実測でき、x64は64B、Apple M2は128B。「64バイト」は定数ではない。
- **観測事実11**: 同一ラインに同居した無関係な変数は、コア間のライン所有権(RFO)の奪い合いを引き起こす(フォールスシェアリング)。実測で並列化が逐次比7倍非効率になった。
- 処方は`alignas(hardware_destructive_interference_size)`による1人1ライン化。ただしこの定数はコンパイル時のものであり、処理系対応と実寸(64 vs 128)の罠がある(4.3節)。
- MESIコヒーレンスが「書き手は常に1人」を守ることで、物理的に散らばったキャッシュが論理的な「共有メモリ=1本の歴史」を実現する。第3章の機械の全部品(共有メモリ、FIFOバッファ、ドレイン、フォワーディング、mfence)に物理実体が対応する(4.4節)。
- リオーダリングはコヒーレンスの敗北ではなく、RFOの遅延を隠すストアバッファ等の**副作用**。x64とARMの差は部品ではなく、待合室の運用契約(FIFO義務・順序監視義務の有無)の差。
- **観測事実12**: 1変数の履歴はARMでも逆行しない(CoRR禁止)。コヒーレンス=1つの場所の合意(無償)、メモリモデル=場所をまたぐ順序の契約(自己申告制)。この対が、C++の変更順序とhappens-beforeに対応する。

これでハードウェア側の探検は一段落です。私たちは「何が起きるか」(第1〜2章)、「なぜ起きるか」(第3〜4章)を手に入れました。次の第5章からは舞台をC++の仕様に移します。個々のCPUの癖をすべて忘れても正しいコードが書けるように、C++11が用意した抽象契約――データ競合の正確な定義と、happens-beforeという万国共通の語彙――を、これまでの全実験を素材にして学び直します。

### 章末演習

1. リスト4-1を手元の全マシン(可能ならクラウドのGravitonインスタンスも)で実行し、ラインサイズの実測値とOS報告値の一覧表を作れ。ヒント: AWS Graviton2/3は64Bである。Apple Siliconとの違いに注意。
2. リスト4-2のスレッド数を1〜8で振り、経過時間をプロットせよ。フォールスシェアリングがある場合、スレッドを増やすほど**遅くなる**区間が現れることを確認し、4.4節のRFO明滅モデルで説明せよ。
3. リスト4-3の`LINE`を意図的に64に固定してApple M2で実行し、隣り合う2要素が128Bラインに相部屋することによる部分的な性能劣化を計測せよ。x64(64Bライン)では劣化しないことも確認すること。
4. `PaddedCounter`のパディングを`alignas`ではなく`char pad[LINE - sizeof(std::atomic<long>)]`による手動詰め物で書き、両者のsizeofとアドレスを印字して等価性を確認せよ。構造体配列とは別に、「ヒープ確保した2つのオブジェクトが偶然同居する」ケースをどう防ぐかも考察せよ。
5. CoRRの親戚であるCoWW(同一変数への2ストアの順序)とCoRW1(読んでから書く)のリトマステストを設計し、ARMで観測されないことを確認せよ。C++規格の「変更順序の一貫性」4規則(coherence rules)との対応を第5章を先読みして整理してもよい。
6. **発展**: 4.2節の実験で、要素型を`std::atomic<long>`から素の`long`(スレッドごとに専用なのでデータ競合ではない)に変えて再計測せよ。フォールスシェアリングはアトミック操作固有の現象ではないことを確認し、なぜアトミックRMWだとより顕著になるのかを、RFOとストアバッファの語彙で説明せよ。
