# 第1章 はじめに

## 1.1 Direct3D 12 とは

### 1.1.1 何が変わったのか

**Direct3D 11 までのグラフィックス API は、多くのことを肩代わりしてくれました。**

リソースが GPU で使用中かどうかを追跡し、メモリを適切に配置し、状態の遷移を挿入し、コマンドをまとめて投入する。**すべてドライバの仕事でした。**

**Direct3D 12 は、それらをアプリケーションに返しました。**

| 項目 | Direct3D 11 | **Direct3D 12** |
|---|---|---|
| メモリの確保 | ドライバが判断 | **自分で指定** |
| リソースの状態 | ドライバが追跡 | **自分で管理** |
| コマンドの投入 | 呼んだら実行される | **記録して、明示的に投入** |
| CPU と GPU の同期 | ドライバが自動 | **すべて自分で** |
| マルチスレッド | 内部でロック | **共有しないことが前提** |

**この変更には、明確な動機があります。**

**D3D11 のドライバは、アプリケーションが何をしたいのかを推測していました。** その推測は多くの場合正しく、しかし常に安全側に倒れていました。**「たぶん後で使うから、まだ解放しないでおこう」「念のため同期しておこう」**

**アプリケーションは、自分が何をするか知っています。** その知識を活かせるようにしたのが D3D12 です。

### 1.1.2 代償

**当然、代償があります。**

**本書で、次のようなコードを繰り返し書くことになります。**

```cpp
//--- リソースの状態を、自分で追跡する ---
const auto barrier = MakeTransitionBarrier(
    backBuffer,
    D3D12_RESOURCE_STATE_PRESENT,      // ← 今の状態を知っている前提
    D3D12_RESOURCE_STATE_RENDER_TARGET);
```

**D3D12 は、リソースが今どの状態にあるかを教えてくれません**(第11章 11.5.1 節)。**間違えれば、絵が壊れるか、GPU がクラッシュします。**

**そして、エラーメッセージはこれだけです。**

```
DXGI_ERROR_DEVICE_HUNG (0x887A0006)
```

**本書が第2章から第8章まで、絵を一切出さずに準備を重ねるのは、この一行に耐えるためです。**

## 1.3 使うもの・使わないもの

### 1.3.1 線引き

**本書は「フルスクラッチ」を掲げていますが、何もかも自作するわけではありません。**

**判断基準は 1 つです。**

> **レンダラの設計判断を伴うものは自作する。**
> **ハードウェア/ドライバ層に触れる基盤は既製品を使う。**

| 使う | 使わない |
|---|---|
| Windows SDK | **`d3dx12.h`** |
| **DirectX Agility SDK** | **DirectXMath** |
| `Microsoft::WRL::ComPtr` | **DirectXTK12** |
| DXC(HLSL コンパイラ) | **WIC** |
| **NVIDIA Nsight Aftermath SDK** | **Assimp** |
| Nsight Graphics / Systems | NVAPI |

### 1.3.2 なぜ `d3dx12.h` を使わないのか

**`d3dx12.h` は、Microsoft が提供するヘルパーヘッダです。**

```cpp
//--- d3dx12.h があれば 1 行 ---
auto barrier = CD3DX12_RESOURCE_BARRIER::Transition(
    backBuffer,
    D3D12_RESOURCE_STATE_PRESENT,
    D3D12_RESOURCE_STATE_RENDER_TARGET);
```

**本書では、こう書きます。**

```cpp
D3D12_RESOURCE_BARRIER barrier{};
barrier.Type  = D3D12_RESOURCE_BARRIER_TYPE_TRANSITION;
barrier.Flags = D3D12_RESOURCE_BARRIER_FLAG_NONE;
barrier.Transition.pResource   = backBuffer;
barrier.Transition.Subresource = D3D12_RESOURCE_BARRIER_ALL_SUBRESOURCES;
barrier.Transition.StateBefore = D3D12_RESOURCE_STATE_PRESENT;
barrier.Transition.StateAfter  = D3D12_RESOURCE_STATE_RENDER_TARGET;
```

**面倒です。** しかし、この 7 行を書くことで、次のことが分かります。

- バリアには**種類**がある(遷移、エイリアシング、UAV)
- **共用体**であり、種類によって有効なメンバが違う
- **サブリソース単位**で遷移できる
- **遷移前の状態を、自分が知っている必要がある**

**最後が決定的です。**

**`CD3DX12_RESOURCE_BARRIER::Transition()` を使っていると、「遷移前の状態を自分で追跡している」という事実が見えにくくなります。**

**第26章でレンダーパスが 6 つになったとき、第30章で Enhanced Barriers へ移行するとき、この理解が土台になります。**

> **代償の実測値**
>
> **本書で自作したヘルパーは、最終的に 18 個でした**(第38章の総括)。
>
> ```
> OffsetHandle、MakeTransitionBarrier、DefaultRasterizerDesc、
> DefaultBlendDesc、DefaultDepthStencilDesc、
> DefaultGraphicsPipelineStateDesc、MakeHeapProperties、
> MakeBufferDesc、AlignUp、MakeTexture2DDesc、AlphaBlendDesc、
> AdditiveBlendDesc、MakeTextureBarrier、MakeBufferBarrier、
> MakeUavBufferBarrier、PipelineStateSubobject、
> DefaultMeshShaderPipelineStateStream、StateObjectBuilder
> ```
>
> **ファイル数枚に収まります。** これが「`d3dx12.h` を使わない代償」のすべてです。

### 1.3.3 なぜ `ComPtr` と Agility SDK は使ってよいのか

**`ComPtr` は、COM の参照カウント規約を機械的に守るだけの道具です。**

**自作しても、規約を再実装するだけで、学びは「規約を理解した」以上には広がりません。**

**そして、実務で事故が多いのは自作の失敗ではなく、既製品の誤用です。**

```cpp
device->CreateFence(0, flags, IID_PPV_ARGS(fence.GetAddressOf()));  // ❌ リーク
device->CreateFence(0, flags, IID_PPV_ARGS(&fence));                // ✅
```

**`operator&` と `GetAddressOf()` の違いを知らないと、静かにリークします**(第6章 6.2.3 節)。

**本書は `ComPtr` を使ったうえで、その挙動を正確に理解することに紙面を割きます。**

**Agility SDK も同様です。**

**これは「Direct3D 12 のランタイム本体をアプリが同梱する」仕組みです**(第4章 4.1 節)。自作という概念がありません。

**そして、これがなければ本書の後半が成立しません。** Enhanced Barriers(第30章)、バインドレス(第33章)、DXR 1.2(第37章)は、すべて Agility SDK を前提とします。

### 1.3.4 なぜ Aftermath は「例外」ではないのか

**Nsight Aftermath SDK は、再頒布 DLL を伴う、まぎれもないライブラリです。**

**それでも使うのは、同じ基準によります。**

**Aftermath は、GPU がクラッシュしたときにドライバ内部の実行状態を読み出す機能です。** レンダラの設計には一切関与せず、**自作もそもそも不可能です。**

**そして実際問題として、本書のスタイルでは Aftermath が必要です。**

**構造体を手で埋める以上、埋め忘れや値の取り違えが起こります。** その結果はしばしば `DXGI_ERROR_DEVICE_HUNG` です。

```
Aftermath なし:  0x887A0006 という数字だけ
Aftermath あり:  ParticleUpdate.hlsl の 78 行目
```

**この差が、本書の後半を進められるかどうかを決めます。**

**だから第8章、まだ三角形も出ていない段階で組み込みます。**

## 1.4 なぜ NVIDIA を前提とするのか

### 1.4.1 対象と依存先は違う

**本書は NVIDIA GPU(Turing 世代以降)を前提とします。**

**しかし、コードは標準の Direct3D 12 API だけで書かれています。**

**この区別が重要です。**

| | 説明 |
|---|---|
| **対象** | **本書が想定する実行環境** |
| **依存先** | **なければ動かないもの** |

**NVIDIA を「対象」にすることで、次が可能になります。**

**① どの機能が使えるかを断定できる**

```
Turing 以降  →  メッシュシェーダー、DXR、Shader Model 6.6 が使える
Ada 以降     →  SER、Opacity Micromap が使える
```

**「環境によります」で終わらせずに済みます。**

**② 「では実際どの値にすべきか」に踏み込める**

**NVIDIA の warp サイズは 32 です。**

**この事実から、次が導かれます。**

| 判断 | 章 |
|---|---|
| `[numthreads(8, 8, 1)]` が 2D の定番である理由 | 第32章 32.3.4 節 |
| メッシュレットを 64 頂点にする理由 | 第36章 36.4.1 節 |
| Wave Intrinsics が効く理由 | 第32章 32.4 節 |

**ベンダ非依存の教科書が「一般に 32 または 64」とぼかすところを、本書は根拠つきで断定します。**

**③ クラッシュ解析の具体的な手順を示せる**

**第29章から第31章、そして第38章。** Nsight Graphics、Aftermath、Nsight Systems を使った手順を、具体的に書けます。

### 1.4.2 依存は 1 ファイルに閉じる

**唯一のベンダ依存は、Aftermath です。**

**これは 1 つのソースファイルに隔離します。** 他ベンダの環境で動かしたい場合、そのファイルを差し替えるだけで済みます(付録 J)。

**そして、原則を守ります。**

> **32 という数字をコードに埋め込まない。**

**HLSL には `WaveGetLaneCount()` があります**(第2章 2.3.1 節、第32章 32.4.2 節)。

**実行時に取得できる値を、ハードコードしません。**

**32 を前提にするのは判断のためであり、依存するためではありません。**

### 1.4.3 他ベンダの環境で読む場合

**第3部(第28章)までは、AMD や Intel の GPU でも動作します。**

**第5部の一部に制約があります。**

| 章 | 他ベンダでの状況 |
|---|---|
| 第32章(コンピュート) | 動く。wave サイズが異なる場合がある |
| 第33章(バインドレス) | 動く |
| 第34章(`ExecuteIndirect`) | 動く |
| 第35章(マルチスレッド) | 動く |
| 第36章(メッシュシェーダー) | 対応 GPU なら動く |
| **第37章(DXR 1.2)** | **SER の効果はベンダ依存** |

**そして、第31章の Aftermath は動きません。**

**代わりに、第38章の DRED を使ってください。** ベンダ非依存で、同等の情報の一部が得られます。

**相違点は付録 J にまとめます。**

## 1.5 本書の構成上の判断

### 1.5.1 なぜ準備が長いのか

**第2章から第14章まで、13 章を準備に費やします。**

**三角形が出るのは第15章です。**

**「早く絵を出したい」という気持ちには反します。** しかし、この順序には理由があります。

**Direct3D 12 では、多くの設定が「黙って失敗する」からです。**

| 設定 | 失敗したときの症状 |
|---|---|
| Agility SDK のエクスポート(第4章) | **何のエラーも出ず、OS 標準版が使われる** |
| デバッグレイヤーの有効化位置(第7章) | **何のエラーも出ず、検証されない** |
| シェーダーの PDB 出力(第13章) | **後から気づいても手遅れ** |
| `SampleMask = 0`(第14章) | **PSO 生成は成功し、何も描かれない** |

**どれも、後から気づいたときの手戻りが大きいものです。**

**とくに第13章のシェーダー PDB は決定的です。**

> デバッグ情報なしでビルドしたシェーダーがクラッシュしても、そのときのダンプには機械語のアドレスしか残りません。**再ビルドしたバイナリは別物なので、既に取得したダンプとは対応しません。**

**準備の各章には、必ず「動作確認」があります。**

**第4章では実行時に Agility SDK が有効かを確認し、第7章では GPU の対応機能を一覧出力し、第9章では意図的にエラーを起こしてデバッグレイヤーの動作を確かめます。**

**「何も見えないまま進む」ことはありません。**

### 1.5.2 なぜデバッグ手法が第4部なのか

**多くの入門書は、デバッグ手法を巻末に置きます。**

**本書は、モダンな機能(第5部)の前に置きました。**

**理由は単純です。**

**第32章以降は、「書いたつもりが動かない」ことが日常的に起こる領域だからです。**

```
コンピュートシェーダーで、範囲外アクセス       → ページフォルト
バインドレスで、NonUniformResourceIndex を忘れる → たまに壊れる
メッシュシェーダーで、SetMeshOutputCounts を忘れる → 何も描画されない
レイトレーシングで、ペイロードサイズ不足       → デバイスロスト
```

**これらは、デバッグレイヤーのメッセージだけでは追えません。**

**第29章で Nsight Graphics、第30章で GPU-Based Validation、第31章で Aftermath を揃えてから第5部へ進む**という順序は、**先に道具を持たせる**という判断です。

**そして、第4部で第0部〜第2部の準備がすべて回収されます。**

| 準備 | 回収 |
|---|---|
| 第4章 Agility SDK | 最新機能の解析が可能に |
| 第6章 デバッグ名 | リソースの特定 |
| 第7章 デバッグレイヤー | API 誤用の検出 |
| 第13章 シェーダー PDB | **クラッシュ位置を HLSL の行番号で** |
| 第8章 Aftermath | クラッシュダンプの生成 |

### 1.5.3 章をまたぐ設計判断

**本書には、複数の章にわたって効く決定がいくつかあります。**

**これらは、決めた章で理由を説明し、効いてくる章で回収します。**

| 決定 | 決めた章 | 主な回収先 |
|---|---|---|
| **すべてのオブジェクトに名前を付ける** | 第6章 6.5 節 | 第21章、第29章、第31章、第38章 |
| **シェーダーの PDB を分離出力する** | 第13章 13.6 節 | 第29章、第31章 |
| **行ベクトル × 行優先、転置しない** | 第17章 17.3 節 | 第18章以降すべて |
| **`{}` を必ず付ける** | 第9章 9.3.3 節 | 第14章、第36章 |
| **フレームごとに巻き戻す** | 第12章、第21章 | 第25章、第35章 |
| **`DescriptorHandle` に `index` を持たせる** | 第21章 21.1.3 節 | 第33章 |
| **Reversed-Z を定数で切り替える** | 第19章 19.5.5 節 | 第25章、第27章、第37章 |

**「なぜ今これをやるのか」が分からない箇所があれば、この表を参照してください。**

## 1.7 読み進め方

### 1.7.1 順番に読む

**本書は、通して読むことを想定しています。**

**各章は、前の章で作ったコードの上に積まれます。**

```
第11章:  MakeTransitionBarrier を自作
    ↓
第16章:  それを使って DEFAULT ヒープへ転送
    ↓
第26章:  それを使ってオフスクリーンの状態遷移
    ↓
第30章:  Enhanced Barriers へ移行
```

**飛ばして読むと、「このヘルパーはどこから来たのか」が分からなくなります。**

### 1.7.2 実験を飛ばさない

**各章の ✅ セクションには、意図的に壊す実験があります。**

**これを飛ばすと、本書の価値は半減します。**

**例を挙げます。**

**第15章 Step 2〜5** では、三角形が消える原因を 4 つ再現します。

```
巻き順の誤り        → デバッグレイヤーは何も言わない
シザー矩形の設定漏れ → 同上
SampleMask = 0      → 同上
書き込みマスク = 0  → 同上
```

**4 つとも「黙って壊れる」ため、症状を知らなければ切り分けに何時間もかかります。**

**一度自分の手で再現しておけば、次は 1 分です。**

**第31章 Step 6** では、シェーダーの PDB を隠します。

```
PDB あり:  CrashTest.hlsl の 14 行目
PDB なし:  0x00000148: STG.E [R2], R3
```

**第13章で「後から設定しても手遅れ」と書いた意味が、ここで実感できます。**

## 1.10 本書の主張

**最後に、本書を貫く 3 つの立場を述べます。**

### 1.10.1 中身を知ることには価値がある

**`d3dx12.h` を使えば、コードは短くなります。** DirectXMath を使えば、速くもなります。

**それでも自作するのは、次のことを知るためです。**

- **リソースバリアが何を指定する構造体なのか**
- **`SampleMask` が何をしているのか**
- **`GetCopyableFootprints` が何を計算しているのか**
- **行ベクトルと列ベクトルのどちらを選んだのか**

**これらを知らないまま進むと、壊れたときに追えません。**

**そして D3D12 では、壊れます。**

### 1.10.2 「動いた」は検証ではない

**本書が各章で意図的に壊す実験を用意したのは、この立場からです。**

**正常系だけを確認しても、次のことは分かりません。**

- その検証機構が本当に働いているか
- 失敗したときにどう見えるか
- 別の環境で同じ結果になるか

**第22章 Step 7 では、リモートデスクトップでのみ再現する不具合を扱います。**

> **通常のローカル環境では再現しません。** だからこそ、**「自分の環境で動いた」で済ませてはいけない**箇所です。

### 1.10.3 測ってから判断する

**本書には、次の記述が繰り返し現れます。**

> 最適化は、測定してから行うべきです(第25章)
> 効果は測らなければ分かりません(第35章)
> どちらを優先すべきかは、測ってから決めるべき判断です(第25章)

**そして第38章で、その手段を整えます。**

**「速くなるはず」という思い込みが、いかに当てにならないか。** 第38章 Step 6 で、実際に確認できます。
